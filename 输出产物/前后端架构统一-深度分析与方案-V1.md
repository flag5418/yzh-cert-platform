## 一、结论先行

### 1.1 一个必须先纠正的认知

**YZH 不是与 Vol 并列的第二套框架，它是长在 Vol 之上的增量层。**

两条硬证据：

```csharp
// YZH-Framework/YZH.Core/Services/YZHServiceBase.cs:80
public abstract class YZHServiceBase<TEntity, TRepository>
    : ServiceBase<TEntity, TRepository>          // ← 继承 Vol 的 ServiceBase
    where TEntity : BaseEntity                   // ← 约束为 Vol 的 BaseEntity
    where TRepository : IRepository<TEntity>     // ← 依赖 Vol 的仓储接口

// vol.api/VOL.Entity/Admin/Platform/Base/YZHBaseEntity.cs:28
public abstract class YZHBaseEntity : BaseEntity  // ← 继承 Vol 的 BaseEntity（空标记类）
```

且这是**主动设计而非历史遗留**。`docs/60-AI工程设计/YZH-知识库/06-YZH与Vol边界定义.md` 的 ADR-003 原文：

> 后端 Service 继承 Vol ServiceBase —— 理由："获取分页/增删改查能力"

`docs/00-工程体系/YZH-建设原则-V1.md` 更直白：

> **YZH 不是 Vol 的替代品，而是 Vol 的增量补强**

### 1.2 那么"难受"从哪来

既然不是并列的两套，痛点的真实来源是这三件事，按严重程度排序：

| 排序 | 真实痛点 | 量化 | 性质 |
|---|---|---|---|
| 1 | **YZH 层没长完**：Vol 的 ServiceBase 有 20 个 virtual 方法，YZH 只覆写了 6 个，**且全是同步版**。业务代码已在用 `GetPageDataAsync`，走异步即绕过 YZH 的校验与生命周期管道 | 14 个方法无覆盖 | **功能性缺陷**，不只是美观问题 |
| 2 | **基类分裂**：40 个实体用 `YZHBaseEntity`，但 8 个自有业务实体仍用 Vol `BaseEntity`（AIUsageLog、CertMessage、StandardDirectoryConfig/File/Folder、SysConfig、UploadTask、YzhFieldConfig、YzhPageConfig） | 8 个实体 | 一致性问题 |
| 3 | **死代码堆积**：后端 `vol.api.sqlsugar` 372 文件零引用；Vol 未使用模块约 4,608 行；前端 Vol 组件约 9,500 行零引用 | 后端 ~5,980 行 + 前端 ~9,500 行 | 认知负担 |

**重点**：第 1 条意味着现在系统里已经存在"同一业务操作走两条不同管道"的隐患——同步走 YZH（有校验、有生命周期钩子、有统一删除策略），异步走 Vol（全绕过）。这才是真正该修的东西，而不是架构统一。

### 1.3 方案建议（详见第五章）

| 方案 | 后端 | 前端 | 总人日 | 风险 | 建议 |
|---|---|---|---|---|---|
| A 彻底脱离 Vol | 60-80 | 25-35 | 85-115 | 高 | 不推荐 |
| **B 削 Vol + 长 YZH** | 15-20 | 15-25 | **30-45** | 中低 | **推荐** |
| C 只清死代码 | 3 | 2 | 5 | 低 | 作为 B 的第一步 |

**推荐 B**：把 Vol 从"无处不在的底座"削成"薄薄的运行时依赖"，同时把 YZH 层补完。同样的"一套架构"体验，代价是 A 的三分之一，且全程可回滚、可交付。

## 二、全景：两套代码的真实拓扑

```
后端
├── YZH.Core（85 文件 / 7,611 行）  ← 自建层
│   ├── 零依赖 Vol：AI(701) Workflow(1162) Extractor(1348) Skills/Audit/CodeRule/Attributes(781)
│   │              → 合计 3,992 行（52%），理论可零改动剥离
│   ├── 半依赖：Queue(1683) Validation(480) Exception(273) → 用 DBServerProvider/WebResponseContent（软）
│   └── 硬绑定：Services(821) → 继承 ServiceBase + IRepository + BaseEntity 泛型约束
│
└── Vue.NetCore / vol.api（911 文件 / 96,726 行）  ← Vol 底座
    ├── VOL.Core：ServiceBase(670) + ApplicationServiceBase(337) + IRepository(332) + RepositoryBase(672)
    ├── VOL.Sys：Sys_User/Role/Menu/WorkFlow 等框架自带服务（16 个服务继承原生 ServiceBase）
    ├── VOL.CERT：业务服务（5 个继承 YZH 基类）+ 实体（40 YZHBaseEntity / 30 BaseEntity）
    └── vol.api.sqlsugar（372 文件）← 死代码副本

前端 vol.web/src
├── yzh（40 文件 / 8,690 行）        ← 自建层，95% 自包含
├── certcore（14 文件 / 1,109 行）   ← 认证通用层
├── views/cert（70 文件 / 20,287 行）← 业务页（admin/ + auditor/）
└── Vol 侧
    ├── components（118 文件 / 25,918 行）
    ├── api/http.js（533 行，含 IE 死代码 + 硬编码 baseURL）
    ├── store（113 行 Vuex）
    └── uitils / extension（拼写错误的 utils）
```

**关键比例**：自建代码后端 7,611 行 vs Vol 底座 96,726 行（7.9%）；前端自建 30,086 行 vs Vol 侧 27,745 行（52%）。

> 后端 YZH 是"薄层"，前端 YZH 已接近"半壁江山"。这决定了两侧的统一难度完全不对等。

## 三、后端深度分析

### 3.1 YZH.Core 对 Vol 的依赖分布

| 模块 | 文件/行数 | 是否碰 Vol | 绑定性质 |
|---|---|---|---|
| Workflow | 19 / 1,162 | 否 | 零依赖 |
| AI | 18 / 701 | 否 | 零依赖 |
| Extractor | 17 / 1,348 | 否 | 零依赖 |
| Skills / Audit / CodeRule / Attributes | 8 / 781 | 否 | 零依赖 |
| Queue | 9 / 1,683 | 是 | 半硬（3 实体继承 BaseEntity；`YzhQueueManager` 24 处 `GetRequiredService<VOLContext>()`） |
| Validation | 4 / 480 | 是 | 软（`DBServerProvider.SqlDapper` 3 处） |
| Exception | 3 / 273 | 是 | 软（`WebResponseContent` / `Logger`） |
| **Services** | **5 / 821** | **是** | **硬**（继承 ServiceBase + 泛型约束） |

**结论**：`VOL.Entity/SystemModels/BaseEntity.cs` 全文 8 行，是**空标记类**，所以 Queue 那 3 处"继承"实为纸老虎。真正焊死的只有 Services 821 行。

### 3.2 YZH 层"没长完"的具体缺口（最高优先级）

Vol `ServiceBase.cs`（670 行）有 20 个 virtual 方法，YZH 覆写情况：

| 已覆写（6 个，全同步） | 未覆盖（14 个，走异步即绕过 YZH 管道） |
|---|---|
| `Add` (YZHServiceBase:115) | `AddAsync`(161)、`UpdateAsync`(269)、`DelAsync`(377) |
| `Update` (:204) | `GetPageDataAsync`(67)、`GetDetailPage`(96) |
| `Del` (:300) | `Upload`(428)、`DownLoadTemplate`(440)、`Import`(449)、`Export`(549) |
| `GetPageData`（YZHTable:41 / YZHTree:31 / YZHTreeTable:55） | `Audit`(593)、`RestartWorkFlowAudit`(622)、`SubmitWorkFlowAudit`(640) 及各自的 Async 版 |

**已确认的风险实例**：`VOL.CERT/Services/Admin/Platform/Partial/ValidationRuleService.cs:28` 等业务代码正在使用 `GetPageDataAsync`——即**异步调用完全绕过 YZH 的校验管道、生命周期钩子、统一删除策略**。

另：父类 `ApplicationServiceBase.cs`（337 行）的 8 个工作流钩子（`AddWorkFlowExecuting` 等，157-282 行）YZH **一个都没接**。

### 3.3 "彻底脱离 Vol"需要重写什么

若把 `YZHServiceBase` 从"继承 Vol ServiceBase"改为自有实现：

| 需自研项 | 行数估算 |
|---|---|
| 仓储抽象（IRepository 71 成员 + RepositoryBase + Sql 扩展） | ~1,330 |
| 查询/分页（SearchExtensions 385 + SearchDetail 157） | ~540 |
| 增删改（UpdateOrAdd 371 + Delete 368） | ~740 |
| 导入导出/上传/主从表/Config | ~510 |
| 表达式树与字典转换（必需子集） | ~1,500 |
| EF DbContext 接入 + 审计字段反射填充 | ~300 |
| **合计** | **≈ 4,900 - 5,500 行** |

外加 Vol 生态周边：权限过滤（`[Editable]`/`[PermissionTable]`，VOL.CERT 有 56 处 `using VOL.Core.BaseProvider`）、字典、菜单、工作流。

**判断**：这 5,000 行是**纯基础设施重写**，不产生任何业务价值，且会引入全新的 bug 面。除非有"必须脱离 Vol 授权/技术栈"的硬约束，否则不划算。

### 3.4 死代码盘点（零风险可删）

| 项 | 规模 | 判定依据 |
|---|---|---|
| `vol.api.sqlsugar/` | 372 文件 | 不在任何 `.sln` 中；全仓 `.sln/.csproj/.sh/.json` 零引用；与 vol.api 有 **243 个同名 .cs**，独有仅 33 个（SqlSugar 适配层）；目录内无 VOL.CERT 业务代码 |
| Vol 未引用模块 | ~4,608 行 | `WorkFlow/` 11 文件 2,495 行、`Quartz/` 7 文件 739 行、`KafkaManager/` 6 文件 667 行、`ObjectActionValidator/` 7 文件 670 行、`Tenancy/` 1 文件 37 行 |

> VOL.CERT 实际只用到 9 个 `VOL.Core.*` 命名空间：Extensions(61)、BaseProvider(56)、EFDbContext(32)、Utilities(23)、ManageUser(10)、Enums(2)、SignalR(1)、DBManager(1)、CacheManager(1)。

## 五、方案对比与推荐

### 方案 A：彻底脱离 Vol（自研基础设施）

- **做法**：后端自研 ServiceBase + 仓储（~5,000 行）、自研权限/字典/菜单/工作流；前端重写 17 个 view-grid 页 + 外壳
- **代价**：后端 60-80 人日 + 前端 25-35 人日 = **85-115 人日**
- **风险**：高。5,000 行基础设施重写不产生业务价值；Vol 的工作流/权限/导入导出生态要重造；期间业务功能停摆
- **适用**：仅当有"必须去除 Vol 依赖"的硬约束（授权、技术栈战略）

### 方案 B：削 Vol + 长 YZH（推荐）

- **做法**：后端把 YZH 层"补完"（补齐异步路径、统一实体基类）+ 删死代码 + 裁剪未用 Vol 模块；前端把 17 个 view-grid 页迁到 YzhCrudV3 + 删 9,500 行 Vol 组件
- **代价**：后端 15-20 人日 + 前端 15-25 人日 = **30-45 人日**
- **风险**：中低。全程可回滚（每步 git tag）；每阶段都有可交付成果
- **收益**：达成"一套架构"的使用体验——开发者日常只接触 YZH 层，Vol 退化为不可见的运行时依赖；代码总量减少约 15,000 行；消除异步绕过管道的功能隐患
- **代价承认**：Vol 仍在依赖树里，但接触面从"96,726 行底座"缩到"几个 using"

### 方案 C：只清死代码

- **做法**：删 sqlsugar 372 文件 + Vol 未用模块 + 前端 Vol 死组件
- **代价**：5 人日
- **收益**：减少认知负担，但不解决基类分裂与异步绕过
- **定位**：作为 B 的第一步

### 推荐：B（含 C 作为第一步）

**理由**：你的诉求是"长期稳定、长期维护、不再难受"。这三点 B 全能满足，A 只能多给一个"依赖树干净"的心理安慰，代价是三倍工时和全新 bug 面。
