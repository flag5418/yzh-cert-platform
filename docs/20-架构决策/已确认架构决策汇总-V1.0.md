## 一、产品定位与商业模式

### 1.1 ✅ 已确认

| 决策项 | 决策内容 | 来源 |
|--------|---------|------|
| **产品形态** | 统一 SaaS 平台（不再区分"企业方案"和"个人工具"两条线） | 总体设计-V2 |
| **目标客户** | 认证机构（CB）和独立审核员/审核团队 —— 按年付费订阅 | 总体设计-V2 |
| **企业端定位** | 免费协作方（免费受邀使用，不计入付费账号） | 总体设计-V2 |
| **收费模式** | 按年付费 SaaS（不按报告次数收费） | 总体设计-V2 |
| **过期策略** | ❌ 不做数据清空。付费结束后不能新建项目或编辑原项目。商业模式待系统完善后再考虑 | 用户反馈 2026-07-27 |
| **移动端优先** | Flutter App 作为第一操作平台，内嵌 Web Service 供 PC 浏览器访问 | 总体设计-V2 |
| **PC端用途** | 报告编写等深度操作（持续 PC 使用场景） | 用户反馈 2026-07-27 |

### 1.2 ✅ 核心任务定义

```
第一阶段核心任务 = 「审核报告的自动生成」+「报告审核辅助」

能力链：
  资料输入(上传+OCR) → 数据处理(校验+提取) → AI智能(填充+增强) → 输出(预览+导出)

成功标准：用户上传资料 → 一键生成可用的审核报告
```

**来源**：核心任务确认与总体设计策略-V1.0

### 1.3 ✅ 三阶段演进路线

| Phase | 定位 | 关键交付 |
|:-----:|------|---------|
| **P1** | MVP —— 单审核员可用 + 企业可协作 | 审核任务 CRUD、检查表填写、NC 管理、拍照取证、离线模式、报告一键生成、企业端协作基础 |
| **P2** | 团队协作 | 多审核员协作、任务共享、SignalR 实时通知、云端化 |
| **P3** | 平台完善 | 完整 RBAC、证书全生命周期、认证决定流程、统计分析 |

**来源**：总体设计-V2

## 三、核心领域模型

### 3.1 ✅ 已确认的核心实体（V3.0 企业中心模型更新）

> **⚠️ 重要变更（2026-07-28）**：领域模型从 V2.0 的"任务中心"重构为 V3.0 的**"企业中心"**模型。
>
> **核心变化**：
> - Enterprise 成为一**级入口和核心组织单元**
> - 新增 **EnterprisePhase（阶段）** 实体，表达认证生命周期
> - 任务分离为 **AuditTask（审计）** + **ReportTask（报告）**
> - 文件管理升级为 **FileRepository（树形目录 + 版本历史）**

#### V3.0 核心实体

| 实体 | 说明 | 层级 | 关键字段概要 |
|------|------|:---:|------------|
| **Enterprise** | 🏢 企业（一级入口） | L1 | name, credit_code, cert_scope, contacts, status(active/archived) |
| **EnterprisePhase** | 📋 阶段（新增） | L2 | enterprise_id, phase_type(initial_stage1/surveillance_1/etc), sequence_order, status |
| **AuditTask** | 🔍 审计任务 | L3 | phase_id, task_type(file/site/document), standard_id, status(queued→progress→completed) |
| **ReportTask** | 📄 报告任务（新增，分离） | L3 | phase_id, report_type, based_on_audit_id, template_id, output_format |
| **FileRepository** | 📁 文件目录（核心证据库） | L1* | enterprise_id, parent_id(tree), current_version, tags |
| **FileVersion** | 📝 文件版本历史（新增） | — | file_repo_id, version_number, file_hash, change_description |
| **NonConformity(NC)** | 不符合项 | — | audit_task_id, severity, clause_ref, description, nc_status |
| **ChecklistItem** | 检查表条目 | — | audit_task_id, clause_id, result, remark, evidence_ids |
| **AuditEvidence** | 审核证据 | — | audit_task_id, evidence_type, file_path, file_hash, metadata |
| **Rectification** | 整改记录 | — | nc_id, submitted_by, correction, corrective_action, version |
| **Standard / ISOClause** | 标准与条款（预置） | — | code, name, clauses[] |
| **User** | 用户 | — | org_id, role, contact_info |

**层级关系**：`Enterprise (L1) → EnterprisePhase (L2) → AuditTask / ReportTask (L3)`

**来源**：总体设计-V3.0 + 用户反馈 2026-07-28

### 3.2 ✅ AuditActivity 范式（保留作为审计任务的内部概念）

```
AuditActivity = 将审核员的日常工作固化为「标准化操作单元」
⚠️ 在 V3.0 中，AuditActivity 不再是独立数据库实体，
   而是作为 AuditTask.task_type 的实现方式嵌入到审计任务执行流程中。

每种 Activity Type 对应一种 task_type：
  ├─ document_review → task_type = 'document_review'
  ├─ site_visit → task_type = 'site_audit'
  ├─ interview → 可归入 site_audit 的子类型
  └─ ...

价值保持不变：审核员选择任务类型 → 系统引导其有序完成资料收集
```

**来源**：头脑风暴成果汇总 + 用户反馈 + V3.0 重构适配

## 五、AI 能力策略

### 5.1 ✅ 已确认的 AI 功能清单

| # | 功能 | 描述 | 优先级 |
|---|------|------|:-----:|
| F1 | **OCR 文字识别** | 证件/文件/表格识别（通用 + 表格 + 结构化） | 🔴 P0 |
| F2 | **AI 增强语音转文字** | STT + LLM 后处理（上下文增强规范化） | 🔴 P0 |
| F3 | **报告自动生成** | NC + 检查表 → 报告正文（一键生成） | 🔴 P0 |
| F4 | **标准条款智能推荐** | 根据部门/过程推荐相关条款 | 🟡 P1 |
| F5 | **NC 预测/风险提示** | 基于历史数据预测可能的问题 | 🟢 P2 |
| F6 | **审核助手/QA 问答** | 回答审核相关问题 | 🟢 P2 |
| F7 | **轻量路径自动分析** | 上传资料 → 自动分析完整度 → 生成报告 | 🟡 P1 |

**来源**：AI工程化分析-体系认证平台.md

### 5.2 ✅ AI 工程化方向（重大决策）

| 决策项 | 内容 |
|--------|------|
| **❌ 不自研 AI 引擎** | 不再计划自建 7 层 AI 工作流引擎（Prompt系统、模型路由器、工作流DAG引擎等） |
| **✅ 采用开源工作流平台** | 计划使用 Dify 或 n8n 等开源平台替代自研 AI 编排层 |
| **✅ 规则配置平台化** | 构建「规则配置中心」—— 可视化配置界面 + 导航树分组管理 + DSL 存储 |
| **✅ 规则即资产** | 规则库是核心竞争力，支持复制/导入/版本管理，大学生可参与配置 |
| **✅ 模型可替换** | 要求支持开源模型接入，不被单一 AI 厂商锁定，兼顾性价比 |

**来源**：2026-07-28 讨论

### 5.3 ✅ AI 工程化的 7 层认知（参考框架）

```
L1 数据层      → 准备好"喂"给AI的数据（结构化+非结构化+向量）
L2 嵌入层      → 文本→向量（语义理解）
L3 检索层      → 找到最相关知识（RAG）
L4 提示层      → 设计 Prompt（指令工程）
L5 模型层      → 选择和调用 AI 模型（DeepSeek/通义/开源）
L6 编排层      → 组合多个 AI 步骤（⭐ 用开源平台替代自研）
L7 观测层      → 监控和评估效果

关键变化：L6 编排层从「自研」改为「基于开源平台(Dify/n8n)」
```

**来源**：AI工程化分析-体系认证平台.md

## 九、不做什么（边界）

### 9.1 ✅ 明确排除

| 不做 | 原因 |
|------|------|
| ❌ 不做电子签名（Phase 1） | 法律效力问题，留待后期 |
| ❌ 不做区块链存证 | 过度工程化 |
| ❌ 不做视频会议 | 集成第三方即可 |
| ❌ 不做在线文档协同编辑 | 复杂度过高 |
| ❌ 不做多租户数据隔离（Phase 1） | 初期单租户够用 |
| ❌ 不做国际版 | 聚焦国内市场 |
| ❌ 不自研 AI 工作流引擎 | 采用开源平台（Dify/n8n） |
| ❌ 不按报告次数收费 | 按年 SaaS 订阅制 |
