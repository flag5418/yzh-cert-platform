## 一、背景与定位

### 1.1 行业背景

体系认证行业（ISO 9001/14001/45001 等）目前仍高度依赖人工操作：审核员逐份翻阅文件、逐条对照条款、手动撰写 NC 和审核报告。一个完整审核周期的报告编写占审核员工作量的 40% 以上。

当前市面上的审核辅助工具大多停留在"电子检查表"阶段，缺乏 AI 自动提取、自动校验、自动生成报告的能力。

### 1.2 项目定位

**聚焦审核员核心工作——自动化 NC 生成 + 一键报告生成。**

不做大而全的认证管理系统（证书管理、审核方案、认证决定等留待后续迭代），先把这个核心做到极致，让审核员认可后再逐步扩展。

### 1.3 核心假设

> **一个机构 × 一个标准 × 一个阶段 = 一套标准配置**

每个认证机构对每个标准在每个阶段下，都有标准的企业文件目录结构。每个文件夹下有标准命名的文件，每个文件都有特定的作用和需要提取的字段。

这套配置由行业专家维护，一次配置、多次复用。不同企业使用同一套配置，只是上传的文件内容不同。

## 二、核心架构思想

### 2.1 三大设计支柱

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│  ① 配置驱动          ② 工作流编排        ③ Skill 组件化  │
│                                                     │
│  标准条款、文件目录    一套工作流体系         Skill是可复用  │
│  提取规则、校验规则    支撑三个引擎          的节点组件     │
│  报告模板——全部       提取/校验/报告          OCR/提取/比较  │
│  可配置，引擎不变      共用一套工作流引擎       /判断/生成/API │
│                                                     │
└─────────────────────────────────────────────────────┘
```

| 支柱 | 核心思想 | 数据库支撑 |
|------|---------|-----------|
| **配置驱动** | 规则、模板、标准全部可配置，新增标准/机构只加配置不改代码 | 域 A（A-01~A-13）全部为配置表 |
| **工作流编排** | 提取、校验、报告三个引擎共用一套工作流体系，通过 DAG 编排 Skill 节点 | 域 F（F-01~F-04） |
| **Skill 组件化** | 每种数据处理能力封装为 Skill，可跨标准跨阶段复用 | F-01 Skill 表 |

### 2.2 系统两端

```
后台管理端（配置层）              审核端（业务层）
┌──────────────────┐            ┌──────────────────┐
│ 认证机构管理       │            │ 企业管理           │
│ ISO标准管理       │            │ 阶段管理           │
│ 条款库维护        │            │ 文件上传           │
│ 文件目录定义      │            │ 自动审核           │
│ 提取规则配置      │            │ NC管理             │
│ 校验规则配置      │            │ 报告生成           │
│ 报告模板管理      │            │                    │
│ Skill管理        │            │                    │
│ 工作流配置        │            │                    │
│ 字段标签管理      │            │                    │
└──────────────────┘            └──────────────────┘
     配置一次，多次复用                每次审核产生新数据
```

## 三、引擎一：数据提取

### 3.1 工作原理

```
文件上传
  │
  ▼
资料质量预审（强制第一步）
  │  检查可读性（加密/损坏）、清晰度（DPI/倾斜）、
  │  格式合规、内容完整性（缺页/空表）
  │  → 阻断性问题必须返回修改
  │  → 警告可继续但需确认
  ▼
按文件类型选择 Skill
  │  PDF → PDF提取Skill
  │  PNG/JPG → OCR Skill
  │  Word/DOCX → Word提取Skill
  │  Excel/XLSX → Excel提取Skill
  ▼
按提取规则提取字段/表格
  │  每个文件对应一条 ExtractionRule
  │  ExtractionRule 引用一个 Skill（用什么方法提取）
  │  ExtractionRule 下挂多个 ExtractionField（提取哪些字段）
  │  每个字段有 label_tag（全局唯一引用键）
  ▼
存储提取结果（含位置信息+可信度）
  │  字段级结果 → ExtractionResult
  │  表格级结果 → TableExtractionResult
  │  每条结果附带：页码/行号/列号 + AI可信度(0.00-1.00)
  ▼
完成（提取结果持久化，供审核阶段直接读取）
```

### 3.2 关键设计

#### 3.2.1 文件类型 → Skill 映射

不同文件类型需要不同的文字提取技术。每种提取方法封装为一个 Skill。

| 文件类型 | Skill 类型 | 技术方案 | 数据库 |
|---------|-----------|---------|--------|
| PDF（文字层） | pdf_extract | PDF.js / pdfplumber | F-01 Skill |
| PDF（扫描件） | ocr | 腾讯云/百度 OCR | F-01 Skill |
| PNG/JPG | ocr | 腾讯云/百度 OCR | F-01 Skill |
| Word/DOCX | word_extract | python-docx / EPPlus | F-01 Skill |
| Excel/XLSX | excel_extract | openpyxl / EPPlus | F-01 Skill |

**数据库引用**：
- `A-08 ExtractionRule.skill_id` → `F-01 Skill.id`（规则级指定使用哪个 Skill）
- `A-09 ExtractionField.skill_id` → `F-01 Skill.id`（字段级可覆盖规则级 Skill）

#### 3.2.2 字段标签命名空间

所有可提取字段使用统一命名格式，作为工作流引用字段的唯一键。

```
格式：[机构_标准_阶段_文档_字段]

示例：
[ISO9001_企业基础资料_营业执照_企业名称]
[ISO9001_企业基础资料_营业执照_统一信用代码]
[ISO9001_企业基础资料_质量手册_编制日期]
[ISO9001_一监_管理评审记录_评审日期]
[ISO9001_一监_管理评审记录_评审结论]
```

**数据库引用**：
- `F-02 FieldLabelMapping.label_tag` → 存储标签（UNIQUE）
- `F-02 FieldLabelMapping.field_code` → 对应的字段编码
- `F-02 FieldLabelMapping.skill_id` → `F-01 Skill.id`（提取此字段的 Skill）
- `A-09 ExtractionField.label_tag` → 冗余存储，便于查询
- `B-08 ExtractionResult.label_tag` → 冗余存储，工作流运行时直接按标签查询

**核心价值**：标签是"接口契约"——工作流节点配置中只写标签名，不关心底层怎么提取。只要标签不变，提取方法变了也不影响工作流。

#### 3.2.3 提取结果存储

提取结果分字段级和表格级两种存储。

| 结果类型 | 存储表 | 说明 |
|---------|--------|------|
| 字段级 | `B-08 ExtractionResult` | 每个字段一条记录，含提取值+可信度+位置信息 |
| 表格级 | `B-09 TableExtractionResult` | 每个表格一条记录，内容以 JSON 存储 |

**数据库引用**：
- `B-08 ExtractionResult.file_id` → `B-04 EnterpriseFile.id`（源文件）
- `B-08 ExtractionResult.rule_id` → `A-08 ExtractionRule.id`（用的哪条规则）
- `B-08 ExtractionResult.field_id` → `A-09 ExtractionField.id`（提取的哪个字段）
- `B-08 ExtractionResult.position_info` → JSON，如 `{"page": 3, "line_start": 12, "line_end": 12}`

### 3.3 提取阶段在整体流程中的位置

> **预计算模式**：提取在上传阶段完成并存储，审核阶段直接读取已存数据，无 OCR/LLM 延迟。

```
上传阶段（异步，可排队）：
  文件上传 → 预审 → Skill提取 → 结果存入 B-08/B-09
  ↑ 耗时操作全部在这一步

审核阶段（同步，用户等待）：
  读取已存 B-08/B-09 → 执行校验工作流 → 生成结果
  ↑ 纯内存计算，毫秒级
```

## 四、引擎二：规则校验

### 4.1 工作原理

```
审核员点击"审核"
  │
  ▼
系统加载当前阶段的所有校验规则
  │  ValidationRule（A-10）按 标准×阶段 查出所有 active 规则
  │  每条规则关联一个 WorkflowDefinition（F-03）
  ▼
逐条执行校验工作流
  │  工作流引擎加载 workflow_config（JSON DAG）
  │  按 DAG 拓扑序执行节点：
  │
  │  节点1: get_field [标签A] → 从 B-08 读取已存提取值
  │  节点2: get_field [标签B] → 从 B-08 读取已存提取值
  │  节点3: compare_date_diff(节点1输出, 节点2输出) → 计算结果
  │  节点4: compare(节点3输出, >, 12) → 布尔结果
  │
  │  每个节点调用对应 Skill（F-01）执行
  │  每个节点的输入/输出记录到 WorkflowExecutionLog（F-04）
  ▼
生成合规检查结果
  │  每条规则的结果存入 FileComplianceCheck（B-07）
  │  check_status: pass / fail / warning / blocked
  ▼
fail → 自动生成 NC
  │  NonConformity（C-03）自动创建
  │  source_type='auto_rule'
  │  source_check_id → B-07（关联到触发的检查记录）
  │  rule_id → A-10（关联到触发的校验规则）
  │  severity 从 ValidationRule.severity_if_violated 取
  │  description 从 ValidationRule.nc_description_template 取
  ▼
审核员复核确认
  │  审核员查看自动结果 + 溯源到源文件
  │  确认 → AuditFinding（C-04）记录
  │  修改 → 调整NC严重度/描述
  │  新增 → 手动创建NC（source_type='manual'）
  ▼
形成NC清单
```

### 4.2 校验规则分类

不管多复杂的审核规则，都能细分为以下几种模式。每种模式对应不同的 Skill 组合。

| 规则模式 | 典型场景 | 工作流节点组成 | 是否需要AI | 数据库 |
|---------|---------|-------------|:---:|--------|
| **文件存在性检查** | "管理评审记录是否存在？" | get_file_list → check_not_empty | ❌ 纯逻辑 | A-10 + F-03 |
| **字段存在性检查** | "质量手册是否包含审批签字页？" | get_field → check_not_empty | ❌ 纯逻辑 | A-10 + F-03 |
| **日期有效性检查** | "管理评审日期距审核日期是否超过12个月？" | get_field×2 → date_diff → compare | ❌ 纯逻辑 | A-10 + F-03 |
| **交叉文档一致性** | "管理评审参与人员是否与组织架构图一致？" | get_field×2 → set_contains | ❌ 纯逻辑 | A-10 + F-03 |
| **数量关系检查** | "培训人数是否≥需培训岗位人数？" | get_field×2 → count → compare | ❌ 纯逻辑 | A-10 + F-03 |
| **语义判断** | "质量手册适用范围是否覆盖认证范围？" | get_field×2 → llm_judge | ✅ 需AI | A-10 + F-03 |
| **完整性判断** | "程序文件被修改但未提供培训记录，整改是否充分？" | get_field×N → llm_judge | ✅ 需AI | A-10 + F-03 |

**关键设计决策**：纯逻辑节点走自研解释器（确定性、快、免费），语义节点走 LLM（灵活、但需结构化约束+可信度标注+人工复核兜底）。工作流引擎按节点类型自动路由。

### 4.3 工作流 DAG 结构

每条校验规则对应一个工作流 DAG，存储为 JSON。

```json
{
  "nodes": [
    {
      "node_id": "n1",
      "skill_code": "get_field",
      "inputs": { "label_tag": "[ISO9001_一监_管理评审记录_评审日期]" },
      "output": "review_date"
    },
    {
      "node_id": "n2",
      "skill_code": "get_field",
      "inputs": { "label_tag": "[ISO9001_一监_阶段审核日期]" },
      "output": "audit_date"
    },
    {
      "node_id": "n3",
      "skill_code": "compare_date_diff",
      "inputs": { "date_a": "{{n1.output}}", "date_b": "{{n2.output}}", "unit": "month" },
      "output": "diff_months"
    },
    {
      "node_id": "n4",
      "skill_code": "compare",
      "inputs": { "value": "{{n3.output}}", "operator": ">", "threshold": 12 },
      "output": "is_violation"
    }
  ],
  "edges": [
    {"from": "n1", "to": "n3"},
    {"from": "n2", "to": "n3"},
    {"from": "n3", "to": "n4"}
  ],
  "output_config": {
    "on_violation": {
      "severity": "minor",
      "nc_template": "管理评审记录距审核日期超过12个月，可能已过期"
    }
  }
}
```

**数据库引用**：
- `A-10 ValidationRule.workflow_id` → `F-03 WorkflowDefinition.id`（规则引用工作流定义）
- `F-03 WorkflowDefinition.workflow_config` → 存储上述 JSON
- `F-03 WorkflowDefinition.workflow_type` = `'validation'`
- `F-04 WorkflowExecutionLog` → 记录每个节点的实际输入/输出/状态/耗时

### 4.4 校验规则溯源

每条校验规则记录其判定的文件来源，确保 NC 可追溯。

**数据库引用**：
- `A-11 ValidationRuleSource.rule_id` → `A-10 ValidationRule.id`
- `A-11 ValidationRuleSource.file_requirement_id` → `A-07 FileRequirement.id`
- `A-11 ValidationRuleSource.source_path` → 文件内位置描述

当审核员质疑"这个NC依据的是哪份文件的哪个位置"时，通过此表追溯到原始文件。

### 4.5 自动 NC 链路

这是自动化 NC 的核心数据链路：

```
A-10 ValidationRule（校验规则）
  │  severity_if_violated = 'minor'
  │  nc_description_template = "管理评审记录距审核日期超过12个月..."
  │  workflow_id → F-03（工作流定义）
  │
  ▼ 工作流执行，判定 fail
  │
B-07 FileComplianceCheck（合规检查结果）
  │  check_status = 'fail'
  │  rule_id → A-10
  │  workflow_execution_id → F-04（执行日志）
  │
  ▼ 自动触发NC生成
  │
C-03 NonConformity（不符合项）
  │  source_type = 'auto_rule'          ← 自动生成
  │  source_check_id → B-07             ← 关联到触发的检查记录
  │  rule_id → A-10                     ← 关联到触发的校验规则
  │  severity = 'minor'                 ← 从 A-10.severity_if_violated 取
  │  description = "管理评审记录距..."   ← 从 A-10.nc_description_template 取
```

## 五、引擎三：报告生成

### 5.1 工作原理

```
审核员点击"生成报告"
  │
  ▼
系统加载报告模板
  │  ReportTemplate（A-12）按 机构×标准×阶段 查出
  │  section_config JSON 定义了报告有哪些章节
  │  每个章节关联一个 workflow_id（报告组装工作流）
  ▼
逐章节执行报告工作流
  │  工作流节点从已存的审核结果中取数据：
  │
  │  节点1: get_field [标签A] → 从 B-08 取提取结果
  │  节点2: get_nc_list [条款X] → 从 C-03 取NC清单
  │  节点3: stat_checklist → 统计检查表结果（符合X/不符合Y/不适用Z）
  │  节点4: assemble_text → 拼接段落文本
  │  节点5: llm_generate → AI生成概述段落（可选）
  │
  │  每个节点的输入/输出记录到 WorkflowExecutionLog（F-04）
  ▼
组装报告章节内容
  │  每章节内容存入 ReportSection（D-03）
  │  每章节关联 workflow_id，可追溯生成过程
  ▼
内容溯源
  │  每段内容附带 ReportSectionSource（D-04）
  │  source_type: extraction / finding / nc / compliance / manual / template
  │  source_id → 指向具体记录（B-08/C-04/C-03/B-07等）
  │  confidence → AI可信度
  │
  │  审核员点击报告任意段落 → 查看来源 → 定位到源文件
  ▼
报告编辑+导出
  │  审核员可编辑报告内容（AuditReport.full_content）
  │  导出 PDF/Word
```

### 5.2 报告模板配置

报告模板按 机构×标准×阶段 配置，每个模板定义章节结构。

**数据库引用**：
- `A-12 ReportTemplate.cb_id` → `A-01 CertificationBody.id`
- `A-12 ReportTemplate.standard_id` → `A-02 ISOStandard.id`
- `A-12 ReportTemplate.phase_id` → `A-04 PhaseDefinition.id`
- `A-12 ReportTemplate.template_file_path` → 空白文档的 MinIO 路径
- `A-12 ReportTemplate.section_config` → JSON，定义每章节的名称、clause_id、workflow_id

`section_config` JSON 示例：
```json
[
  {"section_name": "一、审核概况", "clause_id": null, "workflow_id": 101, "sort_order": 1},
  {"section_name": "二、审核发现", "clause_id": null, "workflow_id": 102, "sort_order": 2},
  {"section_name": "7.1 资源", "clause_id": 15, "workflow_id": 103, "sort_order": 3},
  {"section_name": "三、审核结论", "clause_id": null, "workflow_id": 104, "sort_order": 99}
]
```

### 5.3 报告内容按条款填充

报告内容按 ISO 标准条款组织，每个条款对应一个章节。这是 ISO 审核报告的行业标准做法。

**数据库引用**：
- `D-03 ReportSection.clause_id` → `A-03 ISOClause.id`（可空，概述/结论章节不映射条款）
- `D-03 ReportSection.workflow_id` → `F-03 WorkflowDefinition.id`（生成此章节的工作流）
- `D-03 ReportSection.section_content` → 生成的章节文本

### 5.4 报告内容溯源

每段报告内容可追溯到具体数据来源，这是建立审核员信任的关键。

**数据库引用**：
- `D-04 ReportSectionSource.section_id` → `D-03 ReportSection.id`
- `D-04 ReportSectionSource.source_type` → 来源类型枚举
- `D-04 ReportSectionSource.source_id` → 来源记录主键（多态引用）

| source_type | source_id 指向 | 含义 |
|------------|-------------|------|
| extraction | B-08 ExtractionResult | 来自字段提取结果 |
| finding | C-04 AuditFinding | 来自审核发现 |
| nc | C-03 NonConformity | 来自不符合项 |
| compliance | B-07 FileComplianceCheck | 来自合规检查结果 |
| manual | — | 审核员手动输入 |
| template | — | 模板默认内容 |

### 5.5 报告任务关联审核任务

报告生成基于审核数据，需要明确关联基于哪个审核任务。

**数据库引用**：
- `D-01 ReportTask.based_on_audit_task_id` → `C-01 AuditTask.id`
- `D-01 ReportTask.phase_id` → `B-02 EnterprisePhase.id`
- `D-01 ReportTask.template_id` → `A-12 ReportTemplate.id`

## 六、工作流引擎设计

### 6.1 引擎选型

引入标准开源工作流引擎处理编排和状态管理（节点排序、依赖解析、错误重试），节点全部自研。

| 职责 | 归属 | 说明 |
|------|------|------|
| 工作流编排 | 开源引擎 | DAG 拓扑排序、节点状态管理、错误处理、重试 |
| 节点实现 | 自研 Skill | 数据获取、提取、比较、判断、组装、AI调用等 |

### 6.2 工作流定义存储

工作流配置以 JSON 存储在 `F-03 WorkflowDefinition.workflow_config` 字段中。

**数据库引用**：
- `F-03 WorkflowDefinition.workflow_code` → 唯一编码（如 WF_ISO9001_S2_MR_DATE_CHECK）
- `F-03 WorkflowDefinition.workflow_type` → `enum('extraction','validation','report')`
- `F-03 WorkflowDefinition.workflow_config` → JSON（完整 DAG：节点+边+输出配置）
- `F-03 WorkflowDefinition.version` → 版本号（支持迭代修改）

### 6.3 工作流执行日志

每次工作流执行的每个节点都记录输入/输出/状态/耗时，用于排查问题和建立审核员信任。

**数据库引用**：
- `F-04 WorkflowExecutionLog.workflow_id` → `F-03 WorkflowDefinition.id`
- `F-04 WorkflowExecutionLog.business_type` → `enum('audit_task','report_task','file_upload')`
- `F-04 WorkflowExecutionLog.business_id` → 关联的业务ID
- `F-04 WorkflowExecutionLog.node_id` → 节点ID
- `F-04 WorkflowExecutionLog.skill_code` → 执行的 Skill 编码
- `F-04 WorkflowExecutionLog.input_data` → JSON（实际输入）
- `F-04 WorkflowExecutionLog.output_data` → JSON（实际输出）
- `F-04 WorkflowExecutionLog.status` → `enum('pending','running','success','failed','skipped')`

### 6.4 三个引擎的工作流引用关系

```
引擎          引用方                        引用字段                    → 工作流
─────────────────────────────────────────────────────────────────────────
提取          A-13 ClauseExtractionRule     .workflow_id               → F-03 (type=extraction)
校验          A-10 ValidationRule           .workflow_id               → F-03 (type=validation)
报告          A-12 ReportTemplate           .section_config[].workflow_id → F-03 (type=report)
报告          D-03 ReportSection            .workflow_id               → F-03 (type=report)
```

三个引擎共用同一张 `F-03 WorkflowDefinition` 表，通过 `workflow_type` 区分。配置一次，引擎不变。

## 七、数据流转全景图

### 7.1 配置层 → 业务层的驱动关系

```
配置层（域A + 域F）                           业务层（域B + 域C + 域D）
─────────────────                             ──────────────────────

A-01 认证机构
  └→ A-02 ISO标准
       └→ A-03 标准条款 ─────────────────────→ C-02 ChecklistItem.clause_id
       └→ A-05 StandardPhaseConfig ─────────→ B-02 EnterprisePhase（企业创建阶段时引用）

A-06 DirectoryTemplate ─────────────────────→ B-03 EnterpriseDocument（企业创建目录时引用）
  └→ A-07 FileRequirement ──────────────────→ B-04 EnterpriseFile（企业上传文件时引用）

A-08 ExtractionRule ────────────────────────→ B-08 ExtractionResult.rule_id
  └→ A-09 ExtractionField ──────────────────→ B-08 ExtractionResult.field_id
       └→ label_tag ────────────────────────→ F-02 FieldLabelMapping（工作流引用字段）

A-10 ValidationRule ────────────────────────→ B-07 FileComplianceCheck.rule_id
  └→ workflow_id → F-03 ────────────────────→ F-04 WorkflowExecutionLog（执行时记录）
  └→ A-11 ValidationRuleSource ─────────────→ 溯源到 A-07 FileRequirement

A-12 ReportTemplate ────────────────────────→ D-01 ReportTask.template_id
  └→ section_config[].workflow_id → F-03 ───→ D-03 ReportSection.workflow_id
```

### 7.2 业务层内部的数据链路

```
① 上传阶段
  B-01 Enterprise → B-02 EnterprisePhase → B-03 EnterpriseDocument → B-04 EnterpriseFile
  B-04 → B-05 FileVersion（版本历史，只追加）
  B-04 → B-06 FilePreCheckResult（质量预审）
  B-04 + A-08 + F-01 → B-08 ExtractionResult + B-09 TableExtractionResult（提取结果）
  执行记录 → F-04 WorkflowExecutionLog（type=file_upload）

② 审核阶段
  C-01 AuditTask（auditor_id 直接在任务上，无分配表）
  C-01 → C-02 ChecklistItem（逐条款检查项，初始态 pending）
  C-01 + B-08 + A-10 + F-03 → B-07 FileComplianceCheck（校验结果）
  B-07 (fail) → C-03 NonConformity（自动NC，source_type=auto_rule）
  C-02 → C-04 AuditFinding（审核发现，关联NC）
  C-01 → C-05 AuditEvidence（审核证据，只追加+废弃标记）
  C-03 → C-06 Rectification（整改记录，简化版）
  执行记录 → F-04 WorkflowExecutionLog（type=audit_task）

③ 报告阶段
  D-01 ReportTask（based_on_audit_task_id → C-01）
  D-01 + A-12 + B-08 + C-03 + C-04 + F-03 → D-02 AuditReport
  D-02 → D-03 ReportSection（章节内容，关联workflow_id）
  D-03 → D-04 ReportSectionSource（内容溯源，多态引用）
  执行记录 → F-04 WorkflowExecutionLog（type=report_task）
```

### 7.3 溯源链路

```
报告章节内容（D-03）
  → D-04 ReportSectionSource（溯源）
    → source_type='extraction' → B-08 ExtractionResult（提取结果）
      → B-04 EnterpriseFile（源文件）
      → A-09 ExtractionField.label_tag（字段标签）
      → A-08 ExtractionRule → F-01 Skill（提取方法）
    → source_type='nc' → C-03 NonConformity（NC）
      → source_type='auto_rule' → B-07 FileComplianceCheck（检查记录）
        → A-10 ValidationRule → F-03 WorkflowDefinition（校验工作流）
          → F-04 WorkflowExecutionLog（执行过程，逐节点）
    → source_type='finding' → C-04 AuditFinding（审核发现）
      → C-02 ChecklistItem（检查表条目）
      → A-03 ISOClause（条款）
```

审核员点击报告任意段落 → 查看来源 → 定位到源文件的具体位置 → 查看AI可信度 → 查看工作流执行过程。全链路可追溯。

## 八、扩展性论证

### 8.1 不同企业

同一套配置（域A+域F）不变，不同企业只是上传的文件内容不同。提取出的值不同，校验结果不同，报告内容不同。

**数据库层面**：配置表（A-01~A-13, F-01~F-04）不随企业变化。业务表（B/C/D）按企业实例化。

### 8.2 不同标准

新增 ISO 14001 = 新增配置数据，引擎代码不变。

| 操作 | 涉及表 | 工作内容 |
|------|--------|---------|
| 新增标准 | A-02 | 注册 ISO 14001 |
| 新增条款树 | A-03 | 录入 14001 条款结构 |
| 新增阶段配置 | A-05 | 配置 14001 各阶段的条款覆盖和文件要求 |
| 新增文件目录模板 | A-06, A-07 | 定义 14001 各阶段的文件目录和文件要求 |
| 新增提取规则 | A-08, A-09 | 定义每个文件的提取规则和字段 |
| 新增字段标签 | F-02 | 注册 [ISO14001_xxx_xxx_xxx] 标签 |
| 新增校验规则 | A-10, A-11 | 编写 14001 的校验规则和工作流 |
| 新增报告模板 | A-12 | 设计 14001 的报告模板和章节工作流 |

**Skill 不需要新增**——OCR、Word提取、日期比较等 Skill 是跨标准通用的。

### 8.3 不同规则

新增一条校验规则 = 在 `A-10 ValidationRule` 新增记录 + 在 `F-03 WorkflowDefinition` 新增工作流 JSON。引擎代码不变。

### 8.4 单独定制

某机构有特殊规则 = 在 `A-10` 新增该机构专属规则，通过 `A-01 CertificationBody.id` 隔离。不影响其他机构。

## 十、稳定性与效率策略

### 10.1 预计算模式

耗时操作（OCR、LLM提取）全部在上传阶段完成并持久化。审核阶段只做纯逻辑运算（字段查询+比较+判断），毫秒级完成。

```
上传阶段（异步，可排队）：
  OCR/LLM → 提取结果存入 B-08/B-09
  预审结果存入 B-06

审核阶段（同步）：
  读取 B-08/B-09 → 执行工作流 → 结果存入 B-07 → 自动NC存入 C-03
  纯内存计算，无 IO 瓶颈

报告阶段（同步或异步）：
  读取 B-08/B-07/C-03/C-04 → 执行报告工作流 → 组装 D-03
  大部分内存组装，LLM段落可选异步
```

### 10.2 队列策略

上传阶段的提取任务走队列，避免并发时系统过载。审核阶段无需队列（纯逻辑运算）。

### 10.3 稳定性优先于效率

审核行业容错率低，稳定性是第一位的。工作流执行日志（F-04）是排查问题的核心基础设施。

### 10.4 AI 输出约束

| 约束 | 说明 | 数据库支撑 |
|------|------|-----------|
| 结构化输出 | AI 节点必须返回 JSON Schema 约束的结构化结果 | F-01 Skill.output_schema |
| 可信度标注 | 所有 AI 结果附带可信度(0.00-1.00) | B-08/B-07/D-04 .confidence |
| 人工复核兜底 | 所有关键判定（特别是 Major NC）必须有人工确认环节 | C-03.status（auto_rule NC 初始为 open，需人工确认） |
| 低可信度标记 | 可信度低于阈值自动标记"待人工复核" | 工作流 output_config 中配置阈值 |
