# 技术研究-文档解析开源方案与轻量部署-V1

> **版本**：V1.0 | **日期**：2026-08-25 | **状态**：成熟态
>
> **背景**：体系认证平台需提取审核员提交的各类文档资料（Word/PDF/Excel 等）并进入 AI 分析链路。本文研究两个开源方案（Firecrawl anydoc、OpenDataLab MinerU）的适用性，并结合目标部署环境（轻量云服务器：2 核 / 1G 内存 / 50G 硬盘 / OSS 存储）给出可行性结论与部署建议。
>
> **关联文档**：`80-功能设计/01-系统管理/基础资料管理/文件数据提取能力落地-V1.md`（Extractor 模块，OcrRequired 分流机制）、`80-功能设计/01-系统管理/基础资料管理/文档数据提取系统-设计文档-V3.md`

## 1. 研究结论速览

| 方案 | 定位 | 能否用于本项目 | 轻量服务器(2核/1G)本地部署 | 结论 |
|------|------|---------------|--------------------------|------|
| anydoc | 电子文档 → Markdown 轻量转换 | ✅ 能 | ✅ 可行（资源占用极小） | **建议采用**，承接电子版/文本型文档提取 |
| MinerU | 高精度文档解析（VLM+OCR 双引擎） | ✅ 能 | ❌ 不可行（最低 16G 内存） | **不在目标服务器本地部署**，改走云端 API 或独立解析节点 |

两方案**互补而非互斥**：anydoc 处理电子版（毫秒级、低资源），MinerU 补 OCR 空白（扫描件/复杂版面）。但受限于轻量服务器配置，落地形态需调整。

## 2. anydoc 技术研究

### 2.1 项目概览

- **项目**：[Firecrawl anydoc](https://github.com/firecrawl/anydoc)，Firecrawl 开源的 Rust 库 + CLI
- **定位**：将 Word / PowerPoint / Excel / OpenDocument / RTF / EPUB / CSV / PDF 统一转换为干净的 GitHub-Flavored Markdown
- **技术形态**：纯 Rust，无 ML 模型、无外部服务；提供 Rust / Node.js / Python / WebAssembly 四种绑定，另有 CLI（`npx @firecrawl/anydoc`）与 Agent Skill
- **许可证**：MIT

### 2.2 核心能力

| 能力 | 说明 |
|------|------|
| 格式覆盖 | 14 种格式（doc/docx/docm、ppt/pptx、xls/xlsx/xlsb、odt/ods/odp、rtf、epub、csv、pdf），官方基准中唯一全格式覆盖且各格式得分最高 |
| 统一输出 | 所有格式解析进同一 Document 模型，经同一 Markdown 序列化器输出，风格一致 |
| 结构保留 | 标题锚点、表格（合并单元格/表头行）、嵌套/任务列表、脚注、演讲者备注、代码块 |
| 公式 | Word/PowerPoint（OMML）、OpenDocument/EPUB（MathML）公式转 LaTeX |
| 嵌入资源 | 图片转 alt text，原始字节保留在 document model |
| 格式检测 | 基于文件内容识别格式（PDF header / OLE stream / ZIP mimetype），扩展名错误也能正确转换 |
| 性能 | 单文档转换中位数 < 5ms（官方基准：LibreOffice 约 1130ms，anydoc 约 4.4ms） |
| PDF | 文本型 PDF 本地直接转换；**扫描版 PDF 不内置 OCR** |
| 错误分类 | Unsupported / Malformed / Encrypted / ResourceLimit / MissingPart / Io，便于批量任务容错 |

### 2.3 与项目匹配度

| 需求点 | 匹配情况 |
|--------|----------|
| 审核材料格式多样性（docx/pdf/xlsx 为主） | ✅ 全覆盖，比现有 NPOI+PdfPig 覆盖面更广（另支持 ppt、rtf、odt 等） |
| 提取为可供 LLM 分析的文本 | ✅ 输出统一 Markdown，与 AI 分析链路天然衔接 |
| 批处理速度 | ✅ 毫秒级 |
| 本地化/私有化 | ✅ 纯本地、无 API Key、无外部服务 |
| 扫描版 PDF / 纯图片材料 | ❌ 不内置 OCR，需走现有 OcrRequired 分流 |
| 语义抽取/理解本身 | ❌ 仅格式转换，分析仍需上层 AI 链路 |

### 2.4 Docker 化与接入方式

anydoc **无官方 Docker 镜像**，但容器化成本极低（自带预编译二进制）：

```dockerfile
FROM node:22-slim
RUN npm install -g @firecrawl/anydoc
ENTRYPOINT ["anydoc"]
```

两种接入形态：
1. **CLI 形态**：`.NET` 进程调用 `anydoc <file> -o <output.md>`，改动最小；
2. **HTTP 服务形态**：基于 Node 绑定包一层 `POST /convert`（上传文件返回 Markdown），`.NET` 走 HTTP 调用，与现有 LibreOffice 容器模式一致，且支持异步任务队列。

> **替代关系**：可替换现有 `docker/compose.yml` 中的 `yzh-libreoffice` 容器（格式覆盖更全、快约 250 倍、质量分 81 vs 40）。

## 3. MinerU 技术研究

### 3.1 项目概览

- **项目**：[OpenDataLab MinerU](https://github.com/opendatalab/MinerU)，上海 AI Lab 系开源的高精度文档解析引擎（GitHub 58k+ star）
- **定位**：将 PDF / DOCX / PPTX / XLSX / 图片 / 网页转换为结构化 Markdown / JSON，VLM+OCR 双引擎，109 种语言
- **技术形态**：Python 包（`pip install "mineru[all]"`），内置 CLI / FastAPI（mineru-api）/ Gradio WebUI / MCP Server；支持 Docker 部署；支持纯 CPU 与 GPU/MPS 加速
- **许可证**：MinerU Open Source License（基于 Apache 2.0 附加条件；v3.1 起由 AGPLv3 放宽，商用门槛大幅降低）

### 3.2 核心能力

| 能力 | 说明 |
|------|------|
| 输入 | PDF、图片、DOCX、PPTX、XLSX（原生解析） |
| 自动 OCR | **自动检测扫描版/乱码 PDF 并启用 OCR**，109 种语言，支持手写体 |
| 复杂版面 | 多栏布局、跨页表格合并、表格内图片/公式、竖排文字、印章文字识别 |
| 公式/表格 | 公式转 LaTeX、表格转 HTML，按人类阅读顺序输出 |
| 清洗 | 自动去除页眉/页脚/页码/脚注，保证语义连贯 |
| 输出 | 多模态 Markdown / NLP Markdown / 按阅读顺序的 JSON / 富中间格式 / 版面可视化 |
| 部署 | 三种后端（pipeline / vlm-engine / hybrid-engine）、mineru-router 多 GPU 负载均衡、异步任务接口 `POST /tasks` |

### 3.3 三种后端对比

| 后端 | 准确率(OmniDocBench v1.6) | 硬件要求 | 特点 |
|------|--------------------------|----------|------|
| pipeline | 86.47 | **纯 CPU 可跑**，GPU 最低 4GB，**RAM 最低 16G（推荐 32G+）** | 稳定快速、低幻觉、资源占用最低 |
| vlm-engine | 95.39 | GPU 8GB+（vLLM/LMDeploy/mlx），不支持纯 CPU | 高精度，图像/图表分析 |
| hybrid-engine | 95.30 | GPU 8GB+ | 高精度 + 原生文本提取低幻觉 |

**磁盘**：最低 20G（模型文件），SSD 推荐；**Python**：3.10-3.13。

### 3.4 与项目匹配度

## 4. 轻量服务器部署可行性分析（2核 / 1G / 50G / OSS）

### 4.1 目标环境约束

| 维度 | 配置 | 影响 |
|------|------|------|
| CPU | 2 核 | 够用：.NET 8 API + Nginx + Redis 常规负载可承受；anydoc 毫秒级转换无压力 |
| 内存 | 1G | **核心瓶颈**：全栈自托管内存超限 |
| 磁盘 | 50G | 够用：系统 + 代码 + 镜像 + MySQL 数据（文件走 OSS 后磁盘压力小） |
| 存储 | OSS | ✅ 正确决策：替代 MinIO 容器，省内存省磁盘 |
| 成本 | 项目刚启动，不愿在云资源过多投入 | 需优先保证核心业务可运行，重组件外置 |

### 4.2 组件内存预算（1G 内存场景）

| 组件 | 预估占用 | 1G 下可行性 |
|------|----------|-------------|
| 操作系统 + 基础进程 | ~200MB | ✅ |
| Nginx + Vue 静态资源 | ~50MB | ✅ |
| .NET 8 API（核心业务） | 200-300MB | ✅ |
| Redis | 50-100MB | ✅ |
| MySQL 8.0 | 300-500MB（需调优） | ⚠️ 勉强，建议云数据库或轻量调优 + swap |
| anydoc 容器 | 80-150MB | ✅ 可行 |
| **MinerU（任一后端）** | **最低 16G** | ❌ **完全不可行** |
| MinIO | 不部署（改用 OSS） | — 节省约 200-400MB |

**结论：1G 内存下，仅能承载核心业务 + anydoc 轻量解析；MinerU 无法本地部署。**

### 4.3 部署可行性结论

| 方案 | 可行性 | 说明 |
|------|--------|------|
| 核心业务（.NET + Vue + Redis + 轻量 MySQL） | ⚠️ 可行但紧张 | 需 MySQL 调优（innodb_buffer_pool 调小）、必要时加 swap；建议最低 **2G** 内存更稳 |
| anydoc 本地容器化 | ✅ 推荐 | 资源占用极小，覆盖电子版/文本型文档提取 |
| MinerU 本地部署 | ❌ 不可行 | 最低 16G 内存要求与 1G 服务器差距 16 倍，强上必 OOM |
| 扫描版 OCR 落地形态 | ➡️ 外置 | 见 4.4 |
| OSS 存储 | ✅ 推荐 | 替代 MinIO，符合现有 `OSS存储结构重新设计-V1.md` |

### 4.4 扫描版文档（OcrRequired）的三种落地形态

| 形态 | 方案 | 成本 | 适用阶段 |
|------|------|------|----------|
| A. 云端 API | 使用 [mineru.net](https://mineru.net) 在线解析（按量付费） | 低 | **当前阶段推荐**：项目刚启动、扫描件量小 |
| B. 独立解析节点 | 单独一台 GPU/高内存机器部署 MinerU，业务服务器通过 API 调用 | 中 | 扫描件量大后 |
| C. 延后本地化 | 先由 anydoc 处理电子版，扫描件标记待处理，后续预算允许再补 MinerU | 最低 | 若扫描件占比很低 |

## 5. 总体落地建议

```
审核员上传文档 → OSS
        │
        ▼
.NET 提取链路(IFileExtractor)
   ├─ 文本型/电子文档(docx/xlsx/pdf有文本层) ─→ anydoc 容器(本地) ─→ Markdown
   └─ 扫描版/复杂文档(OcrRequired) ─→ MinerU 云端API 或 独立解析节点 ─→ Markdown/JSON
                                        │
                                        ▼
                                  LLM 分析 → 结构化结果
```

1. **轻量服务器（2核/1G/50G）**：建议内存至少 **2G**（1G 太紧张，随时 OOM 风险）；CPU/磁盘/OSS 方案均可行。
2. **anydoc**：本地容器化采用（新增 `yzh-anydoc` service，挂 yzh-net；或 CLI 进程调用），替代 LibreOffice 容器定位；与现有 `IFileExtractor` 对接，Autofac 挂载新实现。
3. **MinerU**：不在目标服务器本地部署；当前用 **mineru.net 云端 API** 承接 OcrRequired 分支（形态 A），后续量大再评估独立解析节点（形态 B）。
4. **存储**：OSS 替代 MinIO，符合既有 OSS 存储设计。
5. **先验证后落地**：用真实审核样张（中文 + 表格 + 扫描件）对 anydoc 本地与 MinerU 云端分别压测，确认解析质量后再固化到正式设计。
