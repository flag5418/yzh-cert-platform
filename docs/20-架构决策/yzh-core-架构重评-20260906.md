# yzh-core 架构重评（第一轮优化后复核）

- 版本：v1.1（对照 v1.0 改进意见书复核）
- 日期：2026-09-06
- 评审对象：`src/yzh-core`（Stand / DataBase / Api / Web 四工程，优化后最新代码）
- 对照基线：`docs/20-架构决策/yzh-core-架构改进意见-20260906.md`（v1.0，下称"改进意见书"）
- 评审方式：csproj 引用实测 + 关键文件逐行核对 + 16 项自检清单逐项验收

---

## 一、结论摘要

代码层较 v1.0 已**实质收敛**：三套基类已合并为单一 `YzhControllerBase<T>`、软删全局过滤已落地、`DeleteBatch` 的 `int.Parse(GUID)` 崩溃已修复、审计链路雏形与 `YzhWebBuilder` 接线封装均已就位，`SysUserController` 成为新基类首个真实继承者。

但当前停在**"框架已就绪、宿主未切换"的中间态**：

1. 宿主 `Program.cs` 既不调用 `UseYzhCore`、也不注册 `BaseDbContext`、更无 `AddApplicationPart(typeof(SysUserController).Assembly)` —— 新用户管理控制器在宿主进程内**路由不可达或 DI 不可解析**，新框架全部能力（软删过滤/审计/GridConfig/缓存管理器/幂等过滤器）在运行时处于"写好没插电"状态；
2. 登录链路仍运行在 Vol 兼容带（`AuthController` + `VOLContext` + Vol 实体 + AES 可逆校验），与新的 `SysUserController` 同库同表双轨并存，且因 Vol 实体感知不到 `IsDeleted` 列，**被软删的用户仍可正常登录并获取新 Token**（本轮新暴露的安全漏洞）；
3. v1.0 中 P0-4（密码哈希化）、P0-5（密钥外置）、P0-6（软删过滤）**部分保留**，其中软删过滤已在新仓储层完成，但密码与密钥两项未动。

16 项二次评审自检清单验收结果：**达成 2 项、部分达成 4 项、未达成 10 项**（详见第四节）。

## 五、本轮新暴露问题

### N-1（P0）宿主断链：新框架"写好没插电"

- **现象**：`YZH.Core.Web/Program.cs` 全程手写接线，未调用已封装好的 `builder.UseYzhCore(...)` / `app.UseYzhPipeline(...)`；未注册 `BaseDbContext`（仅注册 Vol 的 `VOLContext`）；未 `AddApplicationPart(typeof(SysUserController).Assembly)`。
- **后果**：
  - ASP.NET Core 默认只扫描 Web 程序集控制器，Api 程序集的 `SysUserController` **路由不可达（404）**；
  - 即便可达，其依赖 `EntityService<Sys_User>` → `IRepository<Sys_User>` → `BaseDbContext` 均未注册，**DI 解析即 500**；
  - `WorkUnit` / `ICacheManager` / `IDictService` / `ISqlBaseService` / `GlobalExceptionFilter` / `IdempotentFilter` 全部空转（这些仅在 `YzhWebBuilder` 中注册，宿主未调用）。
- **影响面**：新基类、软删过滤、审计、GridConfig JSON 等所有新能力在宿主运行时零生效；v1.0 改进无法被真实接口验证。

### N-2（P0）双轨同表：被软删用户仍可登录（安全）

- **链路 A（新）**：`SysUserController` 软删 → 仅置 `IsDeleted/DeleteTime/DeleteBy`，`Enable` 不动。
- **链路 B（老）**：`AuthController` 用 Vol 实体 `Sys_User`（无 `IsDeleted` 属性）经 `VOLContext` 直查 `UserName`，仅检查 `Enable == 0` 与 AES 密码。
- **后果**：管理员在用户管理页"删除"某账号后，该账号**仍能登录**并获取新 JWT；审计上该账号同时存在"已删除"与"活跃会话"状态。
- **同类隐患**：两套实体同写 `Sys_User` 表，新链路新增列靠 migration 脚本补，老链路完全无感知；角色仍是 `RoleId int`（新链路 switch 硬编码 1/10/20/21/22/30，老链路 `Role_Id.ToString()`）。

### N-3（P1）Sys_UserController 的"角色硬编码 + 权限魔法值"扩散

- `OnQueried` 中 `RoleId switch { 1 => 超级管理员, 10 => 总管理员, ... }`；
- `MenuController` 中 `isSuperAdmin = roleCodes.Contains("1") || roleCodes.Contains("super_admin")`；
- 双轨各自维护角色语义，新增角色/机构化角色后两处都要改，且与"Code 为锚"理念相悖。

## 六、遗留问题（v1.0 已列、本轮复核确认未变）

1. **密码可逆存储（P0-4）**：AES + 固定 IV + 无盐，DB 泄露即口令全量可还原；`AuthController.VerifyDes` 仍在使用。
2. **密钥与口令（P0-5）**：`Program.cs` 内 JWT Secret / PasswordSecret 的硬编码默认值（配置缺失时静默降级为弱默认）；appsettings.json 明文库口令；连接串 `AllowLoadLocalInfile=true`。
3. **构造内虚方法（P0-3）**：`LoadConfig()` 在构造函数触发。
4. **事务双实现（P1-3）**：`WorkUnit`（依赖 BaseDbContext）无消费者；仓储 `BeginTransaction` 是唯一实际使用的事务入口（DeleteBatch/UpdateBatch 用），两套并存容易误导后续主从表设计。
5. **实体缓存闭环缺失（P1-5）**：`YZHCacheEntityAttribute.AutoInvalidate` 语义（默认 true）与现状（无人清缓存）矛盾——属性声明了能力，运行路径从未触发。
6. **僵尸 `BaseController<T>`（P1-2/P2 范畴）**：保留了一组无软删判断的物理删除端点（`Delete/DeleteBatch` 直接 `DbSet.Remove`），若未来被误继承将绕过软删策略。
7. **`BaseDbContext.OnModelCreating` 反射全量扫描 AppDomain**：自动注册所有 `BaseEntity` 子类，随业务实体增多存在启动性能与误注册风险，建议改显式配置或按模块注册。

## 七、下一步建议（更新收敛路线）

| 阶段 | 动作 | 验证方式 |
|---|---|---|
| 阶段 0：接线（本轮新增，优先级最高） | `Program.cs` 改调 `UseYzhCore`；注册 `BaseDbContext`（`UseYzhDatabase`）；`AddApplicationPart(typeof(SysUserController).Assembly)`；补 `BaseDbContext` 的 DbSet/实体注册 | 起服务后 `GET /api/sysuser/page`、`/api/sysuser/config` 返回真实数据；确认旧 5 接口回归不受影响 |
| 阶段 1：堵双轨漏洞 | `AuthController` 登录查询补 `IsDeleted` 过滤（或改走新用户服务）；明确登录链路迁移点；角色收敛为 RoleCode 一处维护 | 软删用户登录返回 401；启用/禁用即时生效 |
| 阶段 2：安全收敛 | 密码哈希化（PBKDF2/BCrypt + 一次性迁移）；密钥移出仓库/去代码兜底；移除 `AllowLoadLocalInfile` | 新密入库不可逆；老用户登录自动迁移成功；扫描仓库无明文密钥 |
| 阶段 3：闭环验证 | `OnAfterCommitted` 默认实现接 `InvalidateEntity<T>`（按 `YZHCacheEntityAttribute.AutoInvalidate`）；删/并僵尸 `BaseController`；`LoadConfig` 移出构造；ExecuteAction 特性化；基类类级默认 `[Authorize]` | 写操作后缓存即时失效；权限默认收敛 |
| 阶段 4：整洁收尾 | 模型类移出控制器文件、注释清理、IP 可信代理开关、BaseDbContext 显式注册 | 16 项自检清单全绿 |

**优先级判断**：N-1 宿主断链是当前唯一阻塞项——它让 v1.0 的全部改进处于"不可验证"状态；N-2 软删可登录是双轨期独有的安全漏洞，应在首批控制器切换时一并关闭。其余按 v1.0 路线推进即可。
