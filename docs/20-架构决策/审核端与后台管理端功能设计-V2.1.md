# 体系认证平台 —— 审核端 & 后台管理端 功能设计

> **版本**：V2.2 | **日期**：2026-07-28
>
> **定位**：本文档描述「审核端」和「后台管理端」两个 PC Web 端的功能设计。
>
> **前提确认**：
> - 技术栈：.NET Core + Vue 3 + MySQL + MinIO
> - 纯 PC Web 端（不做移动端）
> - 核心模型：以企业为中心，企业 → 阶段 → 任务
> - 企业资料分两层：企业基础资料（共享）+ 阶段资料（隔离）
> - 后台核心引擎：标准文件目录 + Skill 提取 + 规则引擎 + AI 提示词解释器
> - 工作流引擎：引入轻量级工作流组件（Temporal / Prefect 等），做 Skill 串联和状态管理；不嵌入 Dify
> - 所有 AI 结果可编辑，有可信度标注 + 源文件位置溯源，人工有最终裁决权
> - Phase 1 仅支持 ISO 9001 一种标准，预设规则，不开放自定义

---

## 一、核心业务模型

### 1.1 企业生命周期

```
企业创建
  │
  ▼
初审 S1 ──→ 初审 S2 ──→ 一监 ──→ 二监 ──→ 再认证
  │ (完成)     │ (完成)     │ (进行中)  │ (待开始)
  │            │            │           │
  ▼            ▼            ▼           ▼
阶段资料      阶段资料      阶段资料     阶段资料
隔离冻结      隔离冻结      工作区       未生成
```

每个阶段可独立操作（新建、打开、关闭归档、取档重新激活），不存在强制线性约束。

### 1.2 企业资料分层模型

| 层级 | 内容 | 生命周期 | 可见范围 | 数据隔离 |
|------|------|---------|---------|---------|
| **企业基础资料** | 营业执照、质量手册、程序文件、组织架构图、资质证书 | 随企业存续，可更新 | 全阶段共享 | 所有阶段引用同一份 |
| **阶段资料** | 该阶段的运行记录、检查记录、证据附件、NC 整改证据、审核报告 | 随阶段创建，阶段归档后冻结 | 仅该阶段可见 | 不同阶段完全隔离 |

### 1.3 核心数据结构

```
企业 (Enterprise)
  ├── 基础信息（名称、信用代码、联系人、认证范围）
  ├── 企业基础资料（共享层）
  │   ├── 营业执照
  │   ├── 质量手册
  │   ├── 程序文件汇编
  │   ├── 组织架构图
  │   └── 资质证书 / 许可证
  │
  └── 阶段列表（每个阶段独立管理）
      └── 每个阶段下：
          ├── 阶段资料（隔离层）
          │   ├── 运行记录（管理评审、内审计划、合规评价等）
          │   ├── 检查记录（自动审核产出）
          │   ├── 证据附件（现场照片、抽样记录等）
          │   ├── NC 整改证据
          │   └── 审核报告
          │
          ├── 审计任务
          └── 报告任务
```

### 1.4 双路径模式

| 路径 | 适用场景 | 流程 |
|------|---------|------|
| **轻量路径** | 上传资料→自动分析→生成报告 | 自动创建临时企业和当前阶段，完成后归档 |
| **完整路径** | 审核员管理长期客户，完整生命周期 | 手动建企业 → 手动建阶段 → 上传资料 → 复核 → 报告 |

**树形导航的关键交互**：

| 交互 | 说明 |
|------|------|
| 点击阶段节点 | 右侧显示该阶段的概览（任务状态、审核进度、NC 数量） |
| 展开阶段的子节点 | 直接进入资料分类（运行记录/检查记录/NC整改/审核报告） |
| 点击具体文件/文件夹 | 右侧显示该目录下的文件列表 + 自动审核结果 |
| 右键阶段节点 | 菜单：新建审计任务、关闭阶段（归档）、取档重新激活 |
| 拖拽 | 不支持（结构由系统定义，不可随意移动） |

**为什么废弃线性时间线**：
- 日常工作中审核员关注的是当前阶段，不需要看到 3 年前的阶段占满屏幕
- 树形结构与资料管理的直觉一致——文件夹即阶段，文件即产出
- 每个阶段可独立关闭/取档，不受其他阶段状态约束

### 2.4 上传流程（资料质量预审 → 即时提取 → 完整性检查）

**设计原则**：文件上传后，系统不直接进入字段提取，而是先完成一轮「资料质量预审」——将每个文件的可读性、清晰度、格式合规、加密保护等问题一次性摊开给使用者。如果关键文件存在问题（如加密无法读取、扫描模糊导致 OCR 不可靠），系统给出强提示，明确告知"这些问题不解决，后续审核结果不可靠"。只有使用者确认问题已处理（或明确选择忽略）后，才进入字段提取和规则执行。

```
文件上传
  │
  ├─→ 0. 资料质量预审（步骤 0，强制第一步）
  │    对每个上传文件执行逐项检查：
  │
  │    a. 可读性检查
  │       · 文件是否加密/受密码保护 → ❌ 直接阻断，无法继续
  │       · 文件是否损坏/无法打开 → ❌ 直接阻断
  │       · PDF 是否为纯图片扫描件（无文字层） → ⚠️ 提示需 OCR
  │
  │    b. 清晰度评估（图片/扫描件类）
  │       · DPI 低于 150 → ⚠️ 清晰度不足，可能影响 OCR 准确率
  │       · 倾斜角度 > 5° → ⚠️ 建议重新上传端正版本
  │       · 遮挡、模糊、水印覆盖关键区域 → ⚠️ 标注具体区域
  │
  │    c. 格式合规
  │       · 对照文件定义检查格式（PDF/DOCX/XLSX/JPG/PNG）
  │       · 多页文档页数是否异常（如文件定义要求≥3页，实际仅1页）
  │
  │    d. 内容完整性初检
  │       · 扫描件是否缺页（总页数 vs 实际页数）
  │       · 表格类文件是否包含有效数据行
  │
  │    → 预审结果面板（强制展示，不可跳过）：
  │      ┌──────────────────────────────────────────────┐
  │      │  资料质量预审                       共 8 个文件 │
  │      │  ──────────────────────────────────────────── │
  │      │  ✅ 营业执照.pdf              已识别，清晰度良好│
  │      │  ✅ 质量手册.docx             已识别，完整可读  │
  │      │  ⚠️ 管理评审记录.pdf          清晰度偏低(120DPI)│
  │      │                                可能影响OCR准确率│
  │      │  ❌ 程序文件汇编.docx         加密文件，无法读取 │
  │      │  ❌ 合规评价报告.xlsx         文件已损坏，无法打开│
  │      │  ⚠️ 内审计划.docx             扫描件倾斜约8°    │
  │      │  ✅ 检验记录.xlsx             已识别，数据完整   │
  │      │  ✅ 培训记录.docx             已识别，格式正确   │
  │      │  ⚠️ 供应商评价表.xlsx         仅1页，文件定义要求≥2页│
  │      │  ──────────────────────────────────────────── │
  │      │  🔴 检测到 1 个阻断性问题（加密文件无法读取），   │
  │      │     将导致以下字段完全无法提取：                 │
  │      │     · 程序文件编号                             │
  │      │     · 程序文件版本                             │
  │      │     · 程序文件批准日期                         │
  │      │  ──────────────────────────────────────────── │
  │      │   ⚠️ 2 个文件存在质量问题，建议处理后再继续     │
  │      │  ──────────────────────────────────────────── │
  │      │  [返回修改]              [我已知晓，继续处理]   │
  │      └──────────────────────────────────────────────┘
  │
  │    交互规则：
  │    · 存在 ❌ 阻断性问题（加密/损坏）→ [继续处理] 按钮置灰，
  │      必须返回修改，不可跳过
  │    · 存在 ⚠️ 警告 → [继续处理] 可用，但点击时弹出二次确认：
  │      "以下文件存在质量问题，继续处理可能导致提取结果不准确。
  │       确认继续吗？" → [确认继续] / [返回修改]
  │    · 全部 ✅ → 自动进入下一步（无阻塞）
  │
  ├─→ 1. 完整性检查
  │    对照当前阶段 + 标准的 File Checklist：
  │    · 应提交 12 个文件，当前已提交 10 个
  │    · 缺失：管理评审记录、合规评价报告
  │    → 即时提示（红色标出缺失项）
  │
  ├─→ 2. 格式校验
  │    对照文件定义：
  │    · 管理评审记录：要求 PDF/Word → 实际上传 DOCX → ✅
  │    · 营业执照：要求 PDF/JPG/PNG → 实际上传 XLSX → ❌ 格式不符
  │    → 即时提示，允许强制接受或替换
  │
  ├─→ 3. Skill 字段提取
  │    匹配文件位置 → 选择对应 Skill → 提取字段：
  │    · 营业执照 → OCR Skill → [企业名称, 信用代码, 法人...]
  │    · 管理评审记录 → Word提取 Skill → [评审日期, 评审结论...]
  │    → 结果存入 DB，关联 [标签]
  │    → 附带位置信息（页码/行号/列号/单元格）
  │
  └─→ 4. 规则自动执行
       运行该文件关联的所有校验规则：
       输出：✅ 通过 / ⚠️ 待复核（含可信度+位置溯源）/ ❌ 不通过（含原因）
```

**即时反馈在树形导航中的体现**：

```
📁 一监 🔄
  ├─ 📁 运行记录
  │   ├─ 📄 管理评审记录      ✅ 已提取 4 个字段
  │   ├─ 📄 内审计划          ✅ 已提取 3 个字段
  │   └─ 📄 合规评价报告      ❌ 格式不符
  ├─ 📁 检查记录             ⚠️ 3 项待复核
  ├─ 📁 NC整改
  └─ 📄 审核报告             ⏳ 需 12 个文件，缺 2 个
```

**核心功能**：

|------|------|
| 自动审核结果列表 | 上传完成后即时生成，展示每个文件 + 每个字段的判定状态 |

### 2.6.1 增量审核

**设计目标**：当用户对某个阶段中已审核完成的部分文件进行替换或补充后，系统仅对变更的那几个文件重新执行审核，不改动的文件保持原有判定结果。这是整个审核体验的核心效率保证。

**触发方式**：

| 触发方式 | 说明 |
|---------|------|
| 替换文件 | 在审计复核页对某文件点击「替换」→ 上传新版本 → 仅该文件重新跑完整流程（预审 → 提取 → 规则执行） |
| 补充文件 | 上传之前缺失的文件 → 仅新文件进入审核流程 |
| 批量替换 | 同时替换多个文件 → 仅替换的文件重新审核 |
| 手动触发 | 用户点击「重新审核」，可选择重审范围：全部文件 / 仅 ⚠️ 待复核项 / 指定文件 |

**与全量审核的对比**：

```
全量审核（首次上传）：                    增量审核（替换/补充文件后）：
                                       
┌──────────────────────────┐          ┌──────────────────────────┐
│ 12 个文件，全部重新提取   │          │ 替换了 2 个文件            │
│ · 营业执照.pdf          │          │                           │
│ · 质量手册.docx         │   ──→    │ · 管理评审记录.docx  ← 变更│
│ · 程序文件汇编.docx     │          │ · 合规评价报告.xlsx  ← 变更│
│ · 管理评审记录.pdf      │          │                           │
│ · 内审计划.docx         │          │ 其余 10 个文件              │
│ · 合规评价报告.xlsx     │          │ 保持原判定不变 ← 不动      │
│ · ...                   │          │                           │
│ 耗时：按全部文件计算     │          │ 耗时：仅算 2 个文件        │
└──────────────────────────┘          └──────────────────────────┘
```

**技术实现**：
- 每个文件在数据库中记录 `file_hash`（SHA-256），作为"是否变更"的判定依据
- 增量审核时对比 hash：hash 未变 → 跳过，直接复用上次结果；hash 变化 → 重新跑完整流程
- 同一阶段内，未变更文件的字段提取结果和规则判定结果完整保留，不做任何覆盖

**源文件定位的交互**：

```
审核员看到：

⚠️ 管理评审记录 - 评审结论  可信度 68%
   └─ 来源: 2026年管理评审记录.docx
   └─ 位置: P3 L12-L15（第3页 第12-15行）
   └─ 原文: "经评审，体系运行基本有效..."

点击 [定位源文件]
  → 浏览器新窗口打开 DOCX 在线预览（或本地 Office 打开）
  → 自动滚到第3页，第12-15行高亮显示
  → 审核员一眼确认原文 → 返回系统点击 [确认] 或 [修正]
  → 2-5 秒完成一项复核
```

这个设计让复核效率提升一个数量级。审核员不需要自己翻文件找对应段落。

### 3.5 规则引擎（自研，替代 Dify 嵌入）

**设计原则**：放弃 Dify 可视化编辑器嵌入，改为自研规则定义引擎。规则以结构化 JSON 定义，系统自动生成 AI 提示词并调用 LLM，结果结构化返回。

**规则分类**：

| 规则类型 | 执行方式 | 示例 |
|---------|---------|------|
| **格式校验** | 纯逻辑，不调 AI | 文件是否为要求的格式（PDF/DOCX） |
| **必填校验** | 纯逻辑，不调 AI | 文件的某个字段是否为空 |
| **数值比较** | 纯逻辑，不调 AI | 管理评审日期是否在审核日期前 12 个月内 |
| **枚举匹配** | 纯逻辑，不调 AI | 审核结论是否在许可的枚举范围内 |
| **语义判断** | 调 AI | 质量手册的适用范围是否涵盖企业的认证范围 |
| **一致性判断** | 调 AI | 管理评审的参与人员是否与组织架构图一致 |
| **完整性判断** | 调 AI | NC 整改证据是否充分——修改了程序文件但未提供培训记录 |

**规则执行流程**：

```
1. Skill 提取完成，字段值存入 DB
2. 规则引擎读取该文件关联的所有规则
3. 纯逻辑规则 → 直接执行条件 → 输出判定
4. 语义判断规则 → 从模板生成 Prompt → 调 LLM → 解析 JSON 返回
5. 汇总所有规则结果 → 展示为审核结果列表
```

### 3.6 工作流引擎（轻量选型）

**定位**：不嵌入 Dify，引入一个轻量级工作流组件（Temporal / Prefect / LangGraph），仅做两件事：

1. **Skill 串联**：定义节点执行顺序（先 OCR 营业执照 → 再 Word 提取质量手册 → 再比较字段）
2. **状态管理**：跟踪每个节点的执行状态（成功/失败/超时），支持重试

**为什么不选 Dify**：
- Dify 的嵌入需要维护 DSL 翻译层、双向同步、编辑器 UI 嵌入——这是 5 个独立的工程难题
- 你的场景不需要可视化拖拽工作流——规则的触发机制是固定的（文件上传），不需要配置员自由编排
- 轻量工作流组件只负责执行层面的编排，规则逻辑由 3.5 的规则引擎驱动

**工作流定义示例**：

```json
{
  "workflow_id": "WF_ISO9001_FILE_UPLOAD",
  "workflow_name": "ISO 9001 文件上传审核流程",

    {
      "id": "step_1",
      "type": "skill",
      "skill_name": "validate_file_format",
      "input": { "file_path": "{{trigger.file_path}}" }
    },
    {
      "id": "step_2",
      "type": "skill",
      "skill_name": "extract_file_fields",
      "input": { "file_path": "{{trigger.file_path}}", "file_def_id": "{{trigger.file_def_id}}" },
      "depends_on": ["step_1"]
    },
    {
      "id": "step_3",
      "type": "rule_engine",
      "input": { "file_def_id": "{{trigger.file_def_id}}", "extracted_fields": "{{step_2.output}}" },
      "depends_on": ["step_2"]
    }
  ]
}
```

### 3.7 规则测试沙箱

**功能目标**：配置员搭建完规则后，用预设的测试案例验证逻辑是否正确。

**配置规则的口语化描述**：通过规则引擎配置界面，选中 `[标签]` 字段，加入条件节点，用自然语言描述条件。

```
示例规则：
「如果管理评审记录的评审日期 距离当前阶段审核日期 超过12个月，标记为风险项」

规则节点表达：
  [ISO9001_初审S1_管理评审记录_评审日期] → 条件节点 → 输出
    条件：DATEDIFF(month, [评审日期], [阶段审核日期]) > 12
    结果：标记为风险项 "管理评审记录超过12个月有效期"
```

**规则测试沙箱**：每条规则支持输入模拟数据，输出执行结果，配置员可验证逻辑是否正确。测试案例由行业专家（你的顾问朋友）提供。

### 4.2 核心 AI 场景

| 场景 | 触发时机 | AI 角色 | 可信度策略 |
|------|---------|--------|-----------|
| 文件字段提取 | 上传时即时执行 | 从文件中提取字段值 + 位置信息 | 字段级可信度，低于阈值标黄 |
| 语义判断 | 规则引擎触发 | 判断字段内容的语义是否合规 | 输出置信度，标为待复核/通过/不通过 |
| 报告生成 | 审核员手动触发 | 从已复核字段组装报告初稿 | 段落级可信度标注 |
| NC 辅助 | 审核员标记 NC | 润色审核员输入的业务语言 | 「AI 建议」标注，审核员必须确认 |

### 4.3 内容校验的可靠性基础

同一公司 + 同一标准 + 同一阶段 → 文件命名和格式统一。

这意味着内容校验不是「从任意文件中猜测内容」，而是：

- 系统知道「管理评审记录」一定是 Word 文档
- 系统知道它必须包含「评审日期」「评审结论」「参与人员」等字段
- 如果文件名正确但内容是空的，或填了错误的文件 → 字段提取为空或提取到非预期内容 → 可信度极低 → 自动标记为待复核
