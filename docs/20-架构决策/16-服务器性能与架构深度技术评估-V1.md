## 一、负载建模

### 1.1 用户行为画像

**前提**：200+ 审核员是总数，不是并发数。认证审核的工作模式是周期性的，不是持续在线。

| 指标 | 估算值 | 依据 |
|------|--------|------|
| 审核员总数 | 200 人 | 用户确认 |
| 人均年审核量 | 15-25 单 | 行业标准：每单约 2-5 天现场 + 1-2 天报告 |
| 年审核总量 | 3000-5000 单 | 200 × 20 均值 |
| 日均活跃用户 | 50-80 人 | 约 25-40% 在线率（含现场和办公室） |
| 峰值并发（读操作） | 30-50 人 | 审核员同时查企业档案、填检查表、录入发现 |
| 峰值并发（写操作） | 10-20 人 | 同步提交报告、保存发现、上传文件 |
| 峰值并发（AI 报告生成） | 5-10 人 | AI 生成耗时 30-90s，同时触发的用户不会太多 |

### 1.2 负载曲线

```
月负载分布（以 5000 单/年为例）：
                                                          ██
                                                ██  ██  ██
                                          ██  ██  ██  ██  ██
                                    ██  ██  ██  ██  ██  ██  ██
                              ██  ██  ██  ██  ██  ██  ██  ██  ██
                        ██  ██  ██  ██  ██  ██  ██  ██  ██  ██  ██
    1月  2月  3月  4月  5月  6月  7月  8月  9月  10月 11月 12月
    ▲                   ▲                   ▲
    春节前冲刺            年中审核季           年末冲刺+监督审核到期
```

**结论**：系统需要承受的峰值是平时负载的 3-4 倍，但整体绝对量并不大——数据库写入峰值约 10-20 条/秒，远低于住房监测平台的传感器写入（数千条/秒）。

### 1.3 数据量估算

| 数据类型 | 单条大小 | 年增量 | 5 年总量 | 说明 |
|---------|---------|--------|---------|------|
| 审核报告记录 | ~20KB | 4000 条 = 80MB | 400MB | JSON 格式的结构化数据 |
| 审核报告 PDF | ~500KB | 4000 份 = 2GB | 10GB | 不含附件 |
| 现场附件（照片/扫描件） | ~5MB/审核 | 4000 × 5MB = 20GB | 100GB | 检查表照片、NC 证据 |
| 证书文件 | ~200KB | 3000 份 = 600MB | 3GB | 含作废版本 |
| 审计日志 | ~500B/条 | 200万条 = 1GB | 5GB | 高频操作审计 |
| 系统日志 | ~200B/条 | 500万条 = 1GB | 5GB | 建议定期归档 |
| **合计** | | **~25GB/年** | **~125GB** | 含 50% 冗余 |

**与住房监测平台对比**：住房平台 5 年 25 亿条时序数据 + 7TB 文件，审核平台只是其数据量的 **1.8%**。存储压力极小。

### 2.3 为什么单机足够

| 担心 | 实际 | 说明 |
|------|------|------|
| "200 人会不会把服务器压垮" | 峰值 QPS < 100 | 审核员的查询/保存操作频率远低于电商/C 端。填写一个检查表可能需要 30 分钟，期间只产生几次 AJAX 请求 |
| "AI 生成报告会不会 OOM" | 单次占用 ~4GB | GPU 16GB 可以并行跑 2-3 个推理任务，CPU 推理也可以排队串行处理 |
| "数据库会不会慢" | 年增量 80MB 结构化 | MySQL 轻松处理百万级记录的查询，而且 VOL 框架自带分页 + 缓存 |
| "要不要上 K8s/微服务" | 不要 | 单体应用 + Docker Compose 对 200 人完全够用。微服务的复杂度 > 它的收益 |

**核心原则**：你担心的不是"单机够不够"，而是"单机哪里是瓶颈"。下面逐项分析。

## 三、性能瓶颈分析

### 3.1 瓶颈链全景图

```
用户请求
  │
  ├─ ① Nginx 反向代理 ──────── 几乎无瓶颈（单机轻松 10000 QPS）
  │
  ├─ ② .NET 8 Kestrel ─────── 无瓶颈（异步 IO，单实例 5000+ 并发连接）
  │   └─ 危险点：未限流导致 AI 任务堆积
  │
  ├─ ③ Redis 缓存 ──────────── 无瓶颈（单线程 10 万 QPS）
  │   └─ 危险点：大 Key 导致阻塞（不要缓存 PDF 文件内容）
  │
  ├─ ④ MySQL 查询 ──────────── 基本无瓶颈
  │   └─ 危险点：未建索引的模糊搜索、JOIN 过多的大表
  │
  ├─ ⑤ RabbitMQ 消息队列 ──── 无瓶颈（单机 2 万条/秒）
  │   └─ 作用：削峰——AI 生成任务异步化
  │
  ├─ ⑥ MinIO 对象存储 ──────── 轻微瓶颈
  │   └─ 危险点：大量并发文件上传时 IO 争抢
  │       缓解：NVMe SSD + 上传限速
  │
  └─ ⑦ AI 推理 ─────────────── **核心瓶颈**
      └─ 单次报告生成：30-90 秒
      └─ 并发能力：GPU 可并行 2-3 个 | CPU 串行 1 个
      └─ 缓解：异步队列 + 生成中进度提示 + 非高峰期预生成
```

### 3.2 各瓶颈的量化分析

#### 瓶颈 1：AI 推理（最关键）

| 参数 | 值 |
|------|-----|
| 模型 | Qwen2.5-14B（本地 ollama）/ DeepSeek-V3（API） |
| 单次报告推理时间 | 30-90 秒（含 PDF 解析 + 规则引擎 + LLM 生成） |
| GPU 并发 | 2-3 个推理任务（RTX 4060 Ti 16GB 可装 14B 量化模型） |
| GPU 处理能力 | 120-360 份报告/小时 |
| 日处理需求 | 日均 15 份（4000/260 工作日），峰值 50 份 |
| 结论 | **GPU 绰绰有余，CPU 推理在峰值时需要排队 5-10 分钟** |

#### 瓶颈 2：PDF 解析

| 参数 | 值 |
|------|-----|
| 单文件解析 | 2-10 秒（取决于页数和复杂度） |
| 内存占用 | 100-500MB/文件 |
| 并发处理 | 受 Python 进程数限制，建议 4 个 Worker |
| 优化方案 | 解析结果缓存，同一文件不重复解析 |

#### 瓶颈 3：数据库（基本无压力）

```
最大表估算（5 年后）：
┌──────────────────┬──────────┬──────────┐
│ 表名              │ 行数      │ 大小      │
├──────────────────┼──────────┼──────────┤
│ 审核报告表        │ ~20,000  │ ~400MB   │
│ NC 不符合项表     │ ~80,000  │ ~200MB   │
│ 检查表明细表      │ ~500,000 │ ~1GB     │ ← 最大表，但也只有 50 万行
│ 审计日志表        │ ~10,000,000│ ~5GB    │ ← 行数多但查询模式固定
│ 证书表            │ ~15,000  │ ~100MB   │
└──────────────────┴──────────┴──────────┘

对比：MySQL 单表千万行以内，索引合理的情况下查询 < 10ms。
50 万行的检查表用索引 (audit_id + clause_id) 查询 < 5ms。
```

#### 瓶颈 4：文件上传（可优化）

| 场景 | 流量 | 影响 |
|------|------|------|
| 单个审核员上传附件 | 10-50MB | 无感 |
| 10 人同时上传（极端） | 100-500MB | SSD 可承受，但网络带宽可能成为瓶颈 |
| 上传带宽需求 | 建议 ≥ 50Mbps 上行 | 10MB 文件 ≈ 2 秒 (50Mbps) / 10 秒 (10Mbps) |

### 3.3 性能保障清单

| # | 措施 | 优先级 | 说明 |
|---|------|--------|------|
| 1 | AI 推理异步化（RabbitMQ 队列） | P0 | 不能让用户等着报告生成，提交后后台跑，完成后通知 |
| 2 | 数据库核心字段建索引 | P0 | `audit_id`, `enterprise_id`, `auditor_id`, `cert_id` |
| 3 | Redis 缓存字典 + 企业信息 | P0 | 减少重复查询，VOL 框架自带 |
| 4 | API 限流（AspNetCoreRateLimit） | P0 | 防止恶意/意外的高频请求 |
| 5 | 文件上传分片 + 限速 | P1 | 大文件用分片上传，前端限制并发数 |
| 6 | 审计日志异步写入 | P1 | 不阻塞业务操作 |
| 7 | PDF 解析结果缓存 | P1 | 同一文件不重复解析 |
| 8 | 数据库连接池合理配置 | P1 | max pool size = 100（默认）足够 |
| 9 | 读写分离 | P2 | 当前量级不需要，未来可加只读副本 |
| 10 | CDN / OSS加速 | P2 | 纯内网场景不需要 |

## 四、安全架构

### 4.1 威胁模型

| 威胁 | 风险等级 | 场景 |
|------|---------|------|
| 审核报告数据泄露 | 🔴 高 | 客户商业机密（生产流程、供应链、财务数据） |
| 未授权访问 | 🟡 中 | 审核员越权查看其他分公司的报告 |
| 数据篡改 | 🔴 高 | 篡改审核结论、NC 记录，影响证书效力 |
| 证书伪造 | 🔴 高 | 生成虚假认证证书 |
| 钓鱼/社工 | 🟡 中 | 通过审核员账号进入系统 |
| DDoS | 🟢 低 | 内网系统，不暴露公网 |

### 4.2 分层安全架构

```
┌─────────────────────────────────────────────────────────────┐
│                       安全层                                 │
├─────────────────────────────────────────────────────────────┤
│  传输层                                                     │
│  ├─ Nginx HTTPS (TLS 1.3)                                   │
│  ├─ 内部服务走 Docker 内部网络，不暴露端口                    │
│  └─ API 签名 + 时间戳防重放                                 │
├─────────────────────────────────────────────────────────────┤
│  认证层                                                     │
│  ├─ JWT Token（VOL 框架自带）                               │
│  ├─ Token 有效期 2h + Refresh Token 7d                      │
│  ├─ 登录失败 5 次锁定 15 分钟                               │
│  └─ 异地登录检测 + 强制下线                                 │
├─────────────────────────────────────────────────────────────┤
│  授权层                                                     │
│  ├─ RBAC（角色：审核员/组长/技术专家/管理员）                │
│  ├─ 数据权限：按分公司/审核组隔离（VOL 框架自带）            │
│  └─ API 权限：接口级别控制（VOL 框架自带）                   │
├─────────────────────────────────────────────────────────────┤
│  数据层                                                     │
│  ├─ 数据库连接加密（TLS）                                   │
│  ├─ 敏感字段 AES-256 加密（企业联系人/内部备注）             │
│  ├─ 审核报告 + 附件 MinIO 存储加密                          │
│  └─ 数据库定时备份（每日全量 + binlog 实时）                 │
├─────────────────────────────────────────────────────────────┤
│  审计层                                                     │
│  ├─ 所有敏感操作记录审计日志（VOL 框架自带）                 │
│  ├─ 审核报告修改：变更前后 diff 记录                        │
│  ├─ 日志不可删除（数据库级防止 DELETE）                      │
│  └─ 定期导出审计报告（CNAS 评审时提供）                     │
├─────────────────────────────────────────────────────────────┤
│  防篡改层                                                   │
│  ├─ 文件上传 SHA-256 哈希记录                               │
│  ├─ 审核报告关键字段版本快照                                │
│  ├─ 证书编号唯一防伪码                                      │
│  └─ P2 可选：区块链存证（提高公信力）                        │
└─────────────────────────────────────────────────────────────┘
```

### 4.4 不需要过度设计的

| 经常被高估的安全措施 | 为什么不必要 |
|---------------------|------------|
| WAF（Web 应用防火墙） | 内网系统，公网只暴露 Nginx 443，无需 WAF |
| 堡垒机 | 2 人团队，直接 SSH 管理即可 |
| SIEM（安全信息事件管理） | 审核平台的审计需求 > 安全监控需求 |
| 等保三级全套 | Phase 1 做不到也不需要，等有 3 家以上认证机构客户再说 |
| DDoS 防护 | 不暴露公网 |
| 双因素认证硬件 Key | APP 验证码 / 微信扫码即可 |

## 五、2 人 + AI Vibe Coding 开发策略

### 5.1 什么是 Vibe Coding 在这个项目的含义

```
传统开发模式：
  需求 → 设计 → 编码 → 测试 → 部署
  人写 100% 代码

Vibe Coding 模式（2 人 + AI）：
  需求 → AI 辅助设计 → VOL 代码生成器生成 60% 代码
                     → AI 辅助编写 30% 业务逻辑
                     → 人工编写 10% 核心算法
       → AI 辅助测试 → 部署
```

### 5.2 人力分配模型

| 角色 | 职责 | 工具 |
|------|------|------|
| 开发者 A（后端+AI） | .NET 后端、数据库、AI 引擎、部署 | Rider + Cursor/Copilot + ChatGPT |
| 开发者 B（前端+移动） | Vue3 管理后台、Uniapp 移动端 | VS Code + Cursor/Copilot + ChatGPT |

### 5.3 开发效率估算

| 模块 | 传统开发 | Vibe Coding | 提效 |
|------|---------|------------|------|
| CRUD 页面（企业档案/用户管理等） | 2 天/表 | **0.2 天/表**（代码生成器） | 10x |
| 复杂表单（审核检查表） | 5 天 | **2 天**（AI 辅助模板） | 2.5x |
| 规则引擎 | 15 天 | **10 天**（核心逻辑仍需人工） | 1.5x |
| AI 报告生成 | 20 天 | **12 天**（AI 辅助 Prompt 调优） | 1.7x |
| 移动端 APP | 30 天 | **15 天**（Uniapp 脚手架 + AI） | 2x |
| 部署运维 | 5 天 | **3 天**（Docker Compose 模板） | 1.7x |

### 5.4 开发纪律（与住房平台一致）

| 纪律 | 说明 |
|------|------|
| **代码生成器优先** | 所有标准 CRUD 页面先用生成器产出，再在 Partial 文件中写自定义逻辑 |
| **禁止手写框架代码** | 用户/角色/菜单/字典/日志，全部用框架自带，不造轮子 |
| **Partial 模式** | 自定义 Service/Controller 写在 `Partial/` 目录，不被生成器覆盖 |
| **EF LINQ 优先** | 标准查询用 EF LINQ + repository，复杂报表才用原生 SQL |
| **Git 分支策略** | `main` 只合可运行的代码，每个功能一个分支，AI 生成的代码必须 Review |
| **文档即代码** | API 用 Swagger 自动生成，数据库用 EF CodeFirst 迁移 |

| 风险 | 概率 | 影响 | 缓解 | 触发条件 |

## 九、总结：你真正需要担心的和你不需要担心的

### 你需要担心的

1. **AI 报告质量**——这是产品核心，决定用户是否接受
2. **AI 推理性能**——唯一的真正性能瓶颈，需要异步队列 + 进度反馈
3. **数据安全**——认证审核涉及客户商业机密，安全投入不能省
4. **2 人团队的精力分配**——砍掉一切非核心功能，先让报告能跑通

### 你不需要担心的

1. **200 人会把服务器压垮**——峰值 QPS < 100，MySQL 年增量 80MB，单机绰绰有余
2. **需要微服务/K8s**——2 人团队 + 单体架构 + Docker Compose 是最优解
3. **需要等保三级**——单家认证机构内网部署，不需要对外提供 SaaS 服务
4. **需要自研框架**——VOL 框架 + 代码生成器已经解决了 60% 的代码量
5. **存储容量不够**——5 年 125GB，1TB SSD 只用 12.5%

### 一句话

> **一台 1 万元的服务器 + 2 个人 + AI 辅助 + VOL 框架，8 周跑通自动审核核心引擎，然后慢慢加功能。这个项目最大的风险不是技术，而是 AI 生成的报告是否能让审核员愿意用。**
