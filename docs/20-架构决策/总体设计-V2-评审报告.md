## 二、项目方向评估

### 2.1 项目定位判断：**非常精准**

当前定位：「**面向审核员和认证机构的 SaaS 平台，企业为协作方（免费受邀使用）**」

**为什么这个定位好？**

| 维度 | 分析 |
|------|------|
| **目标客户清晰** | 认证机构（B端付费）+ 审核员（使用者）+ 企业（协作方免费） |
| **商业模式成立** | 按年付费SaaS，企业端免费降低推广阻力 |
| **切入点正确** | 从"审核执行"切入（Intact已验证此路径），不做大而全 |
| **边界清晰** | 明确不做HR/OA/电子签章等，聚焦核心 |

### 2.2 双路径设计：**极具战略眼光**

#### 2.2.1 轻量路径（快速通道）

```
上传资料 → 自动分析 → 一键生成报告
```

**对标产品**：智审100（zhishen100.cn）——"ISO智能审核，一键生成"

**战略价值**：
- **降低解释成本**：新用户不需要理解复杂流程就能产出价值
- **快速验证**：用户30秒内看到结果，建立信任
- **自然转化**：轻量用户尝到甜头后升级到完整路径
- **技术练兵**：OCR + AI 分析能力在此路径中得到充分锻炼

**适用场景**：
- 初次接触系统的潜在用户
- 需要快速出具报告的简单审核任务
- 作为产品的"钩子"功能吸引新用户注册

#### 2.2.2 完整路径（标准工作台）

```
企业档案 → 创建任务 → 活动式审核 → 整改跟踪 → 报告归档
```

**目标用户**：
- 有一定使用基础的审核员
- 需要完整管理审核全流程的认证机构
- 复杂审核任务（多部门、多条款、多NC）

**战略价值**：
- 用户留存和深度使用的主要场景
- 产生订阅收入的核心路径
- 积累数据资产的基础

#### 2.2.3 设计原则确认

> ✅ **轻量路径不阉割功能**——自动化填补用户跳过的步骤
> 
> ✅ **两条路径共享同一套底层引擎**——输出质量一致
> 
> ✅ **轻量用户可随时升级到完整路径**——数据和报告完整保留

### 2.3 商业模式评价

| 维度 | 评价 | 建议 |
|------|------|------|
| 按年付费（非按次数） | ✅ 正确 | 降低高频使用者心理负担 |
| 企业端免费 | ✅ 正确 | 协作方免费降低审核员推广阻力 |
| 独立审核员低价版 | ✅ 正确 | 种子用户获取策略 |
| 过期3个月缓冲期 | ⚠️ 可优化 | 建议改为：到期后只读6个月，数据永久保留但新建需续费 |

## 三、系统架构评估

### 3.1 架构总评：**优秀**

当前架构选择：

```
┌─────────────────────────────────────────────────────┐
│                   云端 SaaS                          │
│  ┌──────────┐  ┌─────────────┐  ┌───────────────┐  │
│  │  Nginx   │→ │ .NET Core   │  │ PostgreSQL    │  │
│  │  HTTPS   │  │  Web API    │  │ + MinIO       │  │
│  └──────────┘  └─────────────┘  └───────────────┘  │
└─────────────────────────────────────────────────────┘
         ↕ HTTPS              ↕ HTTPS
┌──────────────────┐    ┌──────────────────┐
│  Flutter App     │    │  企业端 Web       │
│  (移动端+PC端)    │    │  (Vue 3 SPA)     │
│  ┌────────────┐  │    │                  │
│  │ SQLite     │  │    │  受邀登录         │
│  │ (离线缓存)  │  │    │  免费协作         │
│  └────────────┘  │    └──────────────────┘
│  ┌────────────┐  │
│  │ 内嵌 Web   │  │ ← PC浏览器访问
│  │ (shelf)    │──┼── localhost:8080
│  └────────────┘  │
└──────────────────┘
```

### 3.2 核心架构决策评价

#### 决策1：Flutter + 内嵌 Web 服务 ⭐⭐⭐⭐⭐

**这是整个方案最大的亮点和创新点。**

| 对比维度 | 传统方案 | 您的方案 | 优势 |
|---------|---------|---------|------|
| 移动端 | Flutter/App | Flutter App | 相同 |
| PC端 | 独立桌面客户端/Web应用 | Flutter内嵌Web服务 | **零部署** |
| 代码量 | 两套UI代码 | 一套Flutter + 一套Vue3 | **减少30%** |
| 数据一致性 | 需要同步机制 | 同一份SQLite | **天然一致** |
| 部署复杂度 | 用户需安装两个软件 | 只装一个App | **用户体验极佳** |

**实际使用场景**：

```
现场审核时：
  审核员用手机App → 选择活动类型 → 检查表填写 / 拍照取证 / 开具NC
  
回酒店写报告时：
  手机连酒店WiFi → 打开电脑浏览器 → 访问 http://手机IP:8080
  → 使用完整的PC端界面编写报告
  → 数据和手机端完全同步
```

**结论**：这个设计必须保留，是核心竞争力之一。

#### 决策2：云端为主 + SQLite离线缓存 ⭐⭐⭐⭐⭐

```
✓ 正确做法：以云端为主，SQLite只是离线临时缓存
✗ 错误做法：以本地为主，同步到云端（数据冲突噩梦）
```

**优势**：
- 数据权威源唯一（云端）
- 冲突场景少（主要是离线期间的单向新增）
- 多设备切换无问题

#### 决策3：单体架构起步 ⭐⭐⭐⭐⭐

对于1人团队，单体架构是唯一正确的选择。

```
❌ 微服务 = 运维复杂度 × N = 自杀
✅ 单体架构 = 简单部署 + 快速迭代 = 生存之道
```

未来如果需要（P3阶段），可以从单体中拆分出服务，但不是现在考虑的问题。

#### 决策4：模块化功能开关 ⭐⭐⭐⭐

```
轻量路径 vs 完整路径 + 模块可配置关闭
= 同一套代码服务不同规模客户
```

这为商业化扩展打下基础。

### 3.3 核心创新：「活动范式」（AuditActivity）设计 ⭐⭐⭐⭐⭐

> **这是本次评审中最重要的发现——项目发起人的「活动范式」设计思想比原始 DailyRecord 设计优秀得多。**

#### 3.3.1 原始设计的局限

```
原始设计：AuditTask → DailyRecord（按天） → ChecklistItem

问题：
  - 强制按"日"组织，但审核活动不是按天划分的
  - 开会、拍照、访谈、开NC是不同性质的活动，混在一条"日报"里
  - 审核员不知道"下一步该做什么"
  - 资料收集没有结构化引导，容易遗漏关键证据
```

#### 3.3.2 「活动范式」设计思想

根据项目发起人的设计理念，审核过程应该被建模为一组**结构化的活动（Activity）**，每种活动都有固定的操作范式：

```
升级设计：AuditTask → AuditActivity（按活动类型） → ActivityTemplate（活动模板）

核心思想：
  ├─ 审核员选择一个活动类型
  ├─ 系统给出对应的表单 / 必填项 / 操作引导
  ├─ 每种活动有固定的操作范式（模板化）
  └─ 有序收集资料 + 简化操作负担 + 确保证据完整
```

**这个设计的精妙之处**：

| 维度 | 传统设计（DailyRecord） | 活动范式设计（AuditActivity） |
|------|------------------------|------------------------------|
| **组织方式** | 按时间（天） | **按活动类型**（开会/巡视/访谈/...） |
| **操作引导** | 无（审核员自己想） | **系统告诉TA下一步做什么** |
| **资料完整性** | 靠经验 | **每种活动有强制必填项** |
| **灵活性** | 僵硬（必须按天） | **自由（按实际节奏安排）** |
| **可扩展性** | 差 | **新增审核类型只需增加模板** |
| **移动端友好** | 长列表滚动 | **每个活动是一个独立卡片** |
| **学习成本** | 高（需培训） | **跟着流程走就不会错** |
| **新审核员友好** | 需要资深审核员指导 | **系统引导即可完成基本操作** |

#### 3.3.3 审核活动类型定义（建议）

```yaml
活动类型枚举 (AuditActivityType):

1. 首次会议 (opening_meeting)
   场景: 审核开始时，与企业管理层召开正式会议
   必填资料:
     - 会议签到表（照片或签名）
     - 审核计划确认文件
     - 参会人员名单
   输出: Task.notes 更新
   预计时长: 30-60分钟
   
2. 文件审查 (document_review)
   场景: 在办公室审阅企业的体系文件、质量记录等
   必填资料:
     - 选择审查的文件类别（质量手册/程序文件/作业指导书/记录）
     - 逐条检查表填写（符合/不符合/不适用）
     - 不符合时一键开NC
   输出: ChecklistItem + 可能的 NC
   预计时长: 2-4小时
   
3. 现场巡视 (site_visit)
   场景: 走访车间、仓库、实验室等现场
   必填资料:
     - 巡视部门/区域选择
     - 拍照取证（强制，自动水印+GPS）
     - 观察记录（文字描述）
     - 发现问题时一键开NC
   输出: AuditEvidence + 可能的 NC
   预计时长: 2-4小时
   
4. 人员访谈 (interview)
   场景: 与不同岗位员工交谈，确认流程执行情况
   必填资料:
     - 访谈对象信息（姓名/岗位/工龄）
     - 访谈问题清单（基于标准条款生成）
     - 访谈记录（文字/可选录音）
     - 发现问题时一键开NC
   输出: ChecklistItem + AuditEvidence + 可能的 NC
   预计时长: 1-2小时/人
   
5. NC讨论 (nc_discussion)
   场景: 与企业代表确认NC事实，沟通整改要求
   必填资料:
     - 选择讨论的NC
     - 企业代表确认（签名或拍照）
     - 整改要求沟通记录
   输出: NC.status 更新为 acknowledged
   预计时长: 30-60分钟/个
   
6. 末次会议 (closing_meeting)
   场景: 审核结束时，向管理层汇报发现
   必填资料:
     - 会议签到表
     - NC清单宣读确认
     - 审核结论宣布
   输出: Task.notes + Task.audit_conclusion
   预计时长: 30-60分钟
   
7. 报告编写 (report_writing) 【★ PC端核心场景 ★】
   场景: 汇总所有资料，编写审核报告
   操作:
     - 汇总所有活动的资料
     - AI辅助生成报告正文
     - 审核员修改/确认
     - 导出PDF/Word
   输出: AuditReport
   预计时长: 1-3小时（系统目标：缩短到30分钟内）
```

#### 3.3.4 数据模型调整建议

```yaml
新增实体: AuditActivity（审核活动）

字段:
  - id: UUID PK
  - task_id: UUID FK → AuditTask
  - activity_type: ENUM 
      (opening_meeting / document_review / site_visit / 
       interview / nc_discussion / closing_meeting / report_writing)
  - title: VARCHAR(200)  # 如 "生产车间现场巡视"
  - description: TEXT  # 补充说明
  - status: ENUM (pending / in_progress / completed)
  - started_at: TIMESTAMP
  - completed_at: TIMESTAMP
  - location: VARCHAR(200)  # 地点（如 "三楼会议室" / "A车间"）
  - participants: JSON  # 参与人员 [{name, role, department}]
  - sort_order: INT  # 活动顺序
  - created_at / updated_at: TIMESTAMP

关联关系:
  AuditActivity 1:N ChecklistItem    # 文件审查/访谈产生的检查项
  AuditActivity 1:N AuditEvidence    # 现场巡视/会议产生的证据
  AuditActivity M:N NonConformity   # 讨论的NC（通过中间表或JSON）

保留 DailyRecord 的价值（降级为聚合视图）:
  - 作为 AuditActivity 的时间线聚合视图（可选）
  - 按 date 分组展示当天完成的活动列表
  - 不再作为强制实体，而是聚合查询结果
```

#### 3.3.5 活动模板引擎（ActivityTemplate）—— P2实现

```yaml
ActivityTemplate 设计（未来扩展）:

目的: 让认证机构自定义活动类型和必填项

结构:
  template_id: UUID
  activity_type: ENUM  # 继承预置类型或自定义
  name: VARCHAR  # 模板名称
  description: TEXT
  required_fields: JSON  # 必填字段定义
    [
      { field: "sign_photo", type: "image", label: "签到表照片", required: true },
      { field: "attendees", type: "participant_list", label: "参会人员", required: true },
      { field: "notes", type: "text", label: "会议纪要", required: false }
    ]
  checklist_template_id: UUID FK  # 关联的检查表模板（如有）
  standard_clause_ids: UUID[]  # 涉及的标准条款
  estimated_duration: INT  # 预估时长（分钟）
  
P1阶段:
  - 活动类型硬编码（上述7种）
  - 必填项在后端代码中定义
  
P2阶段:
  - 活动模板可配置
  - 机构管理员可自定义活动类型
  - 支持不同认证标准的活动模板集
```

**结论**：「活动范式」设计比原始的 DailyRecord 设计**优秀得多**，强烈建议采纳。这是系统的核心竞争力之一——让审核员的操作变得**结构化、引导式、不易出错**。

### 3.4 核心创新2：AI增强语音转文字（Voice Memo with AI Enhancement）⭐⭐⭐⭐⭐

> **项目发起人的洞察**：语音转文字不仅要能转，还要引入AI根据上下文自动生成完整文案，大幅提高效率。回到电脑后可以反复重听、查阅手机记录的信息。

#### 3.4.1 为什么需要AI增强（而非普通STT）？

```
普通STT（如讯飞/百度）：
  输入：审核员现场口述 "这个他们的检验记录好像没有签名"
  输出："这个他们的检验记录好像没有签名"
  
  ❌ 问题：
     - 口语化、不完整
     - 缺少上下文（哪个部门？哪份记录？）
     - 需要审核员回到酒店后大量修改
  
AI增强STT（LLM后处理）：
  输入：同上 + 上下文（当前活动类型=现场巡视，当前部门=生产部）
  输出："在生产车间现场巡视时发现，成品检验记录（编号QR-2026-045）存在多处
        未签署检验员姓名的情况，涉及2026年3月至7月的批次产品。
        此情况不符合ISO 9001:2015条款8.6关于'产品和服务的放行'的要求。"
        
  ✅ 优势：
     - 自动补全上下文信息
     - 自动关联标准条款
     - 生成专业、规范的审核语言
     - 可直接用于NC描述或报告素材
```

### 3.5 核心创新3：计划安排 / 工作日历 / 工作卡片（AuditPlan）⭐⭐⭐⭐⭐

#### 3.5.1 为什么需要这个功能？

```
现实痛点：
  审核员去企业出差2-3天
  → 需要提前规划每天的工作安排
  → 传统方式：Excel表格打印出来 / 手机备忘录
  → 问题：没有提醒、不能动态调整、与实际执行脱节
  
您的解决方案：
  → 出发前在工作台设置"工作卡片"
  → 按天/半天规划活动（首次会议、文件审查、现场巡视...）
  → 日历视图展示
  → 当天有提醒推送
  → 执行时直接从日历进入对应活动
  → 实际执行 vs 计划对比（便于总结和改进）
```

**这个设计的战略意义**：让系统从「记录工具」升级为「工作助手」！

### 3.6 其他架构细节

#### 细节：NC状态机可以更精简

**当前设计**（6个状态）：
```
opened → acknowledged → rectifying → pending_verification → closed / rejected
```

**建议P1精简为**（4个状态）：
```
opened → rectifying → closed / rejected
```

| 被移除的状态 | 替代方案 |
|-------------|---------|
| `acknowledged` | 用 `acknowledged_at` 时间戳表示 |
| `pending_verification` | 用 `submitted_at` 时间戳 + `verified_result IS NULL` 表示 |

**收益**：每减少一个状态，前端+后端+测试的工作量显著降低。

### 6.1 认证审核的本质（通俗解释）

```
认证审核 = 给企业做"体检"，然后发"健康证书"
```

**类比理解**：
- **认证机构** = 体检中心（第三方，公正客观）
- **审核员** = 医生（执行检查的专业人员）
- **企业** = 体检者（被检查的对象）
- **认证标准** = 体检项目清单（如ISO 9001就是"质量管理体检套餐"）
- **NC（不符合项）** = 体检发现的异常指标
- **审核报告** = 体检报告
- **认证证书** = 健康证明（证明企业符合标准要求）

### 6.2 审核的核心业务流程

```
第1步：企业申请认证
       ↓ "我想获得ISO 9001证书"
       
第2步：认证机构受理
       ↓ "好的，我们派审核员去检查你"
       
第3步：文件初审（Stage 1）【通常1天】
       ↓ 审核员先看企业的"体系文件"
       ↓ 确认：文件是否齐全？写得是否合格？
       ↓ 地点：企业办公室或远程进行
       
第4步：现场审核（Stage 2）【★ 这是本系统的核心场景 ★】
       ↓ 通常2-3人天（小型企业1天，大型企业3-5天）
       ↓ 审核方式：
          ├─ 文件审查（25%）：看质量记录、检验报告、培训记录等
          ├─ 现场巡视（30%）：走访车间、仓库、实验室
          ├─ 人员访谈（20%）：与员工交谈，确认流程执行
          └─ 抽样检测（25%）：查看产品、设备状态
       ↓ 发现问题 → 开具 NC（不符合项）
       
第5步：末次会议
       ↓ 向企业管理层汇报审核发现
       ↓ 宣读 NC 清单
       ↓ 企业确认 NC 事实
       
第6步：报告编写【★ PC端核心场景 ★】
       ↓ 审核员汇总所有发现
       ↓ 给出审核结论：
          ✓ 推荐认证通过
          ⚠ 有条件推荐（有小问题，承诺改正）
          ✗ 不推荐（重大问题，需整改后重新审核）
       ↓ 耗时：手工操作2-3天，本系统目标：1小时内完成
           
第7步：认证决定
       ↓ 认证机构技术委员会审批报告
       ↓ 最终决定：发证 / 不发证 / 暂缓
       
第8步：后续
       ├─ 证书有效期3年
       ├─ 每年监督审核（年度体检）
       └─ 3年后再认证（全面复查）
```

### 6.3 NC（不符合项）详解

**什么是NC？**

```
NC = Non-Conformity（不符合项）
   = 审核员发现的"不合规问题"
   
三种典型情况：
   ① 企业做的 ≠ 标准要求的（实际操作不符合标准规定）
   ② 企业说做的 ≠ 实际做的（文件写的和干的不一致）
   ③ 应该有的证据找不到（无法证明符合要求）
```

**NC的三种严重程度**：

| 严重度 | 符号 | 含义 | 示例 | 整改期限 |
|--------|:----:|------|------|---------|
| **严重不符合** | Major | 系统性失效或区域性失效 | 整个生产过程都没有检验记录；质量管理体系完全未运行 | 15-30天 |
| **一般不符合** | Minor | 个别孤立的不符合 | 某台设备的校准过期了；某份记录缺少签名 | 30-60天 |
| **观察项** | Observation | 偏离趋势，尚未构成不符合 | 记录不够规范但不影响合规性 | 建议改进（无强制） |

**NC的生命周期（本系统必须完整支持）**：

```
  开 具 ──→ 企业确认 ──→ 企业整改 ──→ 审核员验证 ──→ 关 闭
(现场)    (收到通知)   (上传证据)   (复核通过)    (闭环)
  │                                                    │
  └────────────────→ 退回重改 ←────────────────────────┘
                        (证据不足/整改不到位)
```

**为什么NC管理是系统的核心价值？**
- NC是审核的"产出物"——没有NC就不叫审核
- NC驱动后续所有动作：整改、验证、报告、认证决定
- NC的质量直接影响认证的有效性和公信力

### 6.4 审核员的日常工作解剖

#### 一个典型的2天现场审核时间分配

| 时间段 | 活动 | 占比 | 本系统支撑（活动范式） |

### 6.5 OCR在本系统中的具体应用场景

根据您朋友的反馈，OCR是**基础能力**，不是可选项。具体场景包括：

#### 场景1：企业证件识别（结构化OCR）

```
输入：拍摄/上传营业执照照片
输出：自动提取并填入：
  - 企业名称
  - 统一社会信用代码
  - 法定代表人
  - 注册资本
  - 成立日期
  - 经营范围
  - 注册地址
```

**涉及的证件类型**：
- 营业执照
- 组织机构代码证
- 各类经营许可证（食品生产/医疗器械/特种设备等）
- ISO证书（过往认证历史）

#### 场景2：检查表/表格识别（表格OCR）

```
输入：拍摄现有的纸质检查表或Excel截图
输出：
  - 识别表格结构（行列）
  - 提取检查项文本
  - 导入为系统中的 ChecklistItem
  - 自动关联匹配的标准条款
```

#### 场景3：质量记录批量识别（通用OCR）

```
输入：批量上传文件夹（各种PDF/图片/Word）
输出：
  - 自动识别文件类型
  - 提取文件名、日期、编号等元数据
  - 分类归档到企业资料库
  - 标记哪些检查项已有证据支撑
```

#### 场景4：历史报告提取（语义OCR/LLM）

```
输入：上传企业过往的审核报告（PDF/Word）
输出：
  - 提取历史NC清单
  - 提取审核结论
  - 标记上次发现的问题本次是否仍存在
  → 辅助本次审核重点关注
```

**注意**：场景4依赖LLM语义理解，建议Phase 2实现。

## 附录A：对标产品分析（智审100）

### A.1 产品定位

智审100（zhishen100.cn）是一个 **ISO 智能审核报告生成工具**。

**核心卖点**：
- "ISO智能审核，一键生成"
- "自动提取关键数据、深度分析逻辑、生成专业结论报告"
- "告别繁琐人工核对，让合规审核更快、更准、更省力"

### A.2 使用流程（极简）

```
1. 注册/登录
2. 进入「工作台」
3. 填写项目信息 + 选择报告类型
4. 点击「生成」
5. 等待 → 获得报告
```

**特点**：
- ✅ 极低的使用门槛（3步完成）
- ✅ 快速出结果（吸引用户尝试）
- ✅ 积分制付费（降低首次使用门槛）
- ❌ 似乎只有AI报告生成，没有完整的审核流程管理

### A.3 对我们的启示

**可以学习的**：
- ✅ 极简的首屏体验（建立任务→上传→生成）
- ✅ 快速展示价值（用户30秒内看到结果）
- ✅ 积分/邀请机制（低成本获客）

**我们可以做得更好的**：
- ✅ 他只有"轻量路径"，我们有"轻量+完整"双路径
- ✅ 他只有Web端，我们有移动端+PC端+离线
- ✅ 他似乎没有企业协作端，我们有
- ✅ 他没有审核流程管理（检查表/NC/整改），这是我们的核心
- ✅ 他没有「活动范式」引导，这是我们的独创

### A.4 战略定位差异

```
智审100：工具型产品（AI报告生成器）
         ↓
         适合：偶尔需要出报告的人
         不适合：专业审核员的日常工作

我们的平台：工作台型产品（审核全流程管理 + 活动范式引导）
         ↓
         适合：专业审核员/认证机构
         附加：也有轻量路径（类似智审的功能）
         
关系：我们的轻量路径 ⊃ 智审100的功能
     （我们包含他的功能，还远不止于此）
     
差异化杀手锏：「活动范式」引导式操作
     （智审100和其他竞品都没有这个）
```
