## 一、设计基础

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **聚焦核心** | 仅围绕"自动化NC"和"一键报告生成"两个核心功能设计，不做企业登录、审核小组、证书管理等 |
| **配置与业务分离** | 管理员维护的模板/规则/Skill/工作流（配置层）与审核员操作产生的数据（业务层）分属不同数据域 |
| **一套工作流，三个引擎** | 提取、校验、报告共用一套工作流编排体系，通过 WorkflowDefinition 统一管理 |
| **预计算模式** | 耗时操作（OCR/LLM提取）在上传阶段完成并存储，审核阶段纯逻辑运算无延迟 |
| **证据只追加** | 文件版本、审核证据每条新建记录，不覆盖旧记录 |
| **全链路溯源** | 从提取结果→校验结果→审核发现→NC→报告章节，每环都有位置信息和可信度标注 |
| **行业标准术语** | 所有表名、字段名使用 ISO 17021 认证行业标准术语（附录A） |
| **预留扩展** | 表结构预留多机构、多标准扩展能力，但 Phase 1 仅实现单机构单标准 |
| **基类统一** | ⭐ 所有业务表必须继承 BaseEntity 基类，包含 id/code/审计字段/删除字段 |
| **Code 关联** | ⭐ 表间外键关联统一使用 `code`（GUID）字段，而非 `id`（自增主键） |
| **前缀分类** | ⭐ 所有表按数据域添加前缀，便于快速识别和管理 |

## 一、基类规范（BaseEntity）⭐ V2.1新增

### 1.3 基类定义

所有业务表**必须**包含以下基类字段。C# 实体类必须继承 `BaseEntity` 基类。

#### 1.3.1 数据库基类字段

| 字段 | 类型 | 约束 | 说明 | 默认值 |
|------|------|------|------|--------|
| `id` | bigint | PRIMARY KEY, AUTO_INCREMENT | 主键，自增 | 自动递增 |
| `code` | varchar(36) | NOT NULL, UNIQUE | 全局唯一编码（GUID），用于表间关联 | NEWID() |

> **审计字段命名双轨制**（2026-08-12 修正）：
> - **PascalCase 轨**（Cert 业务表，40+ 张）：`CreateID`, `Creator`, `CreateDate`, `ModifyID`, `Modifier`, `ModifyDate`, `DeleteID`, `Deleter`, `DeleteTime`, `OrgCode`
> - **snake_case 轨**（配置/工作流表，7 张）：`create_id`, `creator`, `create_date`, `modify_id`, `modifier`, `modify_date`, `delete_id`, `deleter`, `delete_time`, `org_code`
> - C# 实体属性统一使用 PascalCase，通过 `[Column]` 特性适配 snake_case 表

| `create_id` / `CreateID` | int | NULL | 创建人ID（关联 Sys_User.Id） | 当前登录用户 |
| `creator` / `Creator` | varchar(50) | NULL | 创建人姓名 | 当前登录用户姓名 |
| `create_date` / `CreateDate` | datetime | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 | 当前时间 |
| `modify_id` / `ModifyID` | int | NULL | 修改人ID | — |
| `modifier` | varchar(50) | NULL | 修改人姓名 | — |
| `modify_date` | datetime | NULL | 修改时间 | — |
| `delete_id` | int | NULL | 删除人ID（逻辑删除时使用） | — |
| `deleter` | varchar(50) | NULL | 删除人姓名 | — |
| `delete_time` | datetime | NULL | 删除时间（逻辑删除时使用） | — |

> **审计字段命名双轨制**（2026-08-12 修正）：
> - **PascalCase 轨**（Cert 业务表）：列名与 C# 属性名一致，无需 `[Column]` 映射
> - **snake_case 轨**（yzh_*/wf_* 配置表）：通过 `[Column("snake_case")]` 显式映射
> - Vol 框架内置表（`Sys_User`, `Sys_Menu`）使用 PascalCase 列名，与 YZHBaseEntity 默认行为一致

#### 1.3.2 C# BaseEntity 类定义

```csharp
/// <summary>
/// 实体基类 - 所有业务实体必须继承此类
/// </summary>
public class BaseEntity
{
    /// <summary>
    /// 主键ID（自增）
    /// </summary>
    [Key, DatabaseGenerated(DatabaseGeneratedOption.Identity)]
    public long Id { get; set; }
    
    /// <summary>
    /// 全局唯一编码（GUID），用于表间关联
    /// 创建时自动生成，也支持手动传入
    /// </summary>
    [Required, StringLength(36)]
    [Column("code")]
    public string Code { get; set; }
    
    /// <summary>
    /// 创建人ID（默认当前登录用户）
    /// </summary>
    [Column("create_id")]
    public int? CreateID { get; set; }
    
    /// <summary>
    /// 创建人姓名
    /// </summary>
    [Column("creator")]
    [MaxLength(50)]
    public string Creator { get; set; }
    
    /// <summary>
    /// 创建时间（默认当前时间）
    /// </summary>
    [Column("create_date")]
    public DateTime? CreateDate { get; set; } = DateTime.Now;
    
    /// <summary>
    /// 修改人ID
    /// </summary>
    [Column("modify_id")]
    public int? ModifyID { get; set; }
    
    /// <summary>
    /// 修改人姓名
    /// </summary>
    [Column("modifier")]
    [MaxLength(50)]
    public string Modifier { get; set; }
    
    /// <summary>
    /// 修改时间
    /// </summary>
    [Column("modify_date")]
    public DateTime? ModifyDate { get; set; }
    
    /// <summary>
    /// 删除人ID（逻辑删除时使用）
    /// </summary>
    [Column("delete_id")]
    public int? DeleteID { get; set; }
    
    /// <summary>
    /// 删除人姓名
    /// </summary>
    [Column("deleter")]
    [MaxLength(50)]
    public string Deleter { get; set; }
    
    /// <summary>
    /// 删除时间（逻辑删除时使用）
    /// </summary>
    [Column("delete_time")]
    public DateTime? DeleteTime { get; set; }
}
```

#### 1.3.3 基类使用规则

| 规则 | 说明 |
|------|------|
| **强制继承** | 所有业务实体类必须继承 `BaseEntity`，不得省略基类字段 |
| **Code 生成** | 新建记录时自动生成 GUID，支持手动传入（数据迁移场景） |
| **创建人默认值** | `CreateBy` 默认填充当前登录用户 ID，`CreateTime` 默认当前时间 |
| **更新审计** | 更新操作时自动填充 `UpdateBy` 和 `UpdateTime` |
| **逻辑删除** | 基类包含删除字段，具体表按需决定是否启用逻辑删除 |
| **用户表例外** | 对于高频查询的用户关联（如 created_by），可保留 bigint 直接关联 user_id |

## 三、关联关系规范 ⭐ V2.1新增

### 3.1 Code 关联原则

**核心原则**：表间外键关联统一使用 `code`（GUID）字段，而非 `id`（自增主键）。

#### 3.1.1 为什么用 Code 而非 ID？

| 特性 | ID（自增） | Code（GUID） |
|------|-----------|-------------|
| 唯一性 | 仅表内全局 | 全局唯一 |
| 可预测性 | 可预测（安全隐患） | 不可预测（安全） |
| 分布式支持 | 需要集中分配 | 天然支持 |
| 数据迁移 | ID 可能冲突 | GUID 不冲突 |
| 关联稳定性 | ID 可能变化 | Code 永不变 |

#### 3.1.2 关联字段命名规范

| 场景 | 外键字段名格式 | 示例 |
|------|---------------|------|
| 关联某张表 | `{表名去掉前缀}_code` | `standard_code` → 关联 cert_iso_standard.code |
| 自引用（树形） | `parent_code` | parent_code → 关联同表的 code |
| 多态关联 | `{域}_code` + `{域}_type` | `source_code` + `source_type` |

#### 3.1.3 用户关联例外

对于高频查询的用户关联字段（如 `created_by`, `auditor_id` 等），**允许保留 bigint 类型直接关联 `Sys_User.id`**，原因：

- 用户表查询频率极高，JOIN 性能优先
- 用户 ID 不会跨系统迁移
- 减少不必要的 JOIN 开销

**示例**：
```sql
-- ✅ 正确：用户关联用 bigint
CREATE TABLE ent_enterprise (
    ...
    create_by bigint COMMENT '创建人ID',
    FOREIGN KEY (create_by) REFERENCES sys_user(id)
);

-- ✅ 正确：业务表关联用 code
CREATE TABLE cert_iso_clause (
    ...
    standard_code varchar(36) NOT NULL COMMENT '所属标准编码',
    FOREIGN KEY (standard_code) REFERENCES cert_iso_standard(code)
);
```

### 1.2 术语约定

| 术语 | 英文 | 说明 |
|------|------|------|
| 认证机构 | Certification Body (CB) | 执行认证并颁发证书的组织 |
| 审核员 | Auditor | 执行审核任务的人员 |
| 企业 | Enterprise / Auditee | 受审核方，一级核心实体 |
| 阶段 | Phase | 认证生命周期节点：初审S1 → 初审S2 → 一监 → 二监 → 再认证 |
| 条款 | Clause | ISO 标准的层次化要求项（如 7.1） |
| 不符合项 | Nonconformity (NC) | 未满足标准要求的审核发现 |
| 审核发现 | Audit Finding | 审核过程中记录的观察结果 |
| 纠正措施 | Corrective Action | 消除不符合原因，防止再发生 |
| Skill | — | 自研节点组件，封装一种数据处理能力（OCR/提取/比较/判断/生成等） |
| 字段标签 | Field Label | `[机构-标准-阶段-文档-字段]` 格式的全局唯一字段引用键 |
| 工作流 | Workflow | 由节点和边组成的 DAG，描述一次数据处理/校验/报告生成的完整流程 |

### 2.2 核心数据流

```
① 上传阶段（异步，可排队）
  文件上传 → 资料质量预审 → Skill提取 → 结果存入 ExtractionResult/TableExtractionResult

② 审核阶段（同步，用户等待）
  用户点击"审核" → 读取已存提取结果 → 执行校验工作流
  → 生成 FileComplianceCheck → 自动触发NC（fail时）
  → 审核员复核确认 → 生成 AuditFinding

③ 报告阶段（同步或异步）
  用户点击"生成报告" → 读取审核结果+NC+提取结果
  → 执行报告工作流 → 组装章节内容 → 生成 AuditReport
  → 每段内容附带 ReportSectionSource 溯源
```

### 7.3 字典分类体系（cert_dict）⭐ V2.5 新增

> **强制规则**：体系认证相关的所有业务字典**必须**统一挂载在 `cert_dict`（认证平台字典，Dic_ID=107，ParentId=0）分类下。禁止在 `系统字典`（Dic_ID=87）或其他分类下创建认证业务字典。

#### 7.3.1 字典管理强制规则

| 规则 | 说明 |
|------|------|
| **统一分类** | 所有体系认证业务字典的 `ParentId` 必须为 107（cert_dict）。禁止散落在系统字典（87）下 |
| **DicNo 唯一** | `Sys_Dictionary.DicNo` 全库唯一，禁止创建同名的重复字典 |
| **字典项唯一** | 同一 `Dic_ID` 下 `(DicValue, DicName)` 组合唯一，禁止重复插入 |
| **防重复插入** | SQL 脚本必须使用 `INSERT ... SELECT ... WHERE NOT EXISTS` 模式，禁止裸 `INSERT ... VALUES ... ON DUPLICATE KEY UPDATE` |
| **值与代码对齐** | 字典 `DicValue` 必须与后端 C# 代码中实际写入/读取的值完全一致，禁止臆造 |
| **静态 vs 动态分离** | 静态枚举值（如证书状态、NC 严重程度）使用字典；动态业务数据（如认证机构列表、ISO 标准列表）从业务表实时查询，不建静态字典 |
| **文档同步** | 新增/修改字典后，必须同步更新本章节 |

#### 7.3.2 已删除的冗余字典（V2.5 清理）

| 已删除 DicNo | 原名称 | 删除原因 |
|-------------|--------|---------|
| `cert_type` | 认证类型 | 代码无引用，与 ISO 标准模块重复（QMS/EMS/OHSAS/ISMS 与 cert_iso_standard 业务表重复） |
| `standard_type` | 标准类型 | 代码无引用，ISO 标准数据由 cert_iso_standard 业务表管理 |
| `audit_phase` | 审核阶段 | 代码无引用，审核阶段数据由 cert_cert_stage 业务表管理 |
| `cb_list` | 认证机构列表 | 认证机构数据由 cert_certification_body 业务表管理，前端用 Vol 动态字典从业务表取数 |

#### 7.3.5 字典 SQL 脚本规范

新建字典的 SQL 脚本**必须**使用以下防重复模式：

```sql
-- 1. 创建字典分类（防重复）
INSERT INTO `Sys_Dictionary` (`DicNo`, `DicName`, `OrderNo`, `Remark`, `Enable`, `CreateDate`, `ParentId`)
SELECT '字典编号', '字典名称', 排序号, '说明', 1, NOW(), 107
FROM DUAL
WHERE NOT EXISTS (SELECT 1 FROM `Sys_Dictionary` WHERE `DicNo` = '字典编号');

SET @dict_id = (SELECT `Dic_ID` FROM `Sys_Dictionary` WHERE `DicNo` = '字典编号');

-- 2. 创建字典项（逐条防重复，同时检查 DicValue 和 DicName）
INSERT INTO `Sys_DictionaryList` (`Dic_ID`, `DicName`, `DicValue`, `OrderNo`, `Remark`, `Enable`, `CreateDate`)
SELECT @dict_id, '项名称', '项值', 排序号, '说明', 1, NOW()
WHERE NOT EXISTS (
  SELECT 1 FROM `Sys_DictionaryList`
  WHERE `Dic_ID` = @dict_id AND `DicValue` = '项值'
)
AND NOT EXISTS (
  SELECT 1 FROM `Sys_DictionaryList`
  WHERE `Dic_ID` = @dict_id AND `DicName` = '项名称'
);
```

> **禁止**使用 `INSERT ... VALUES ... ON DUPLICATE KEY UPDATE` —— `Sys_DictionaryList` 无 `(Dic_ID, DicValue)` 唯一约束，此语法无法防止重复插入。

> **重要提示**：以下内容基于实际开发中遇到的问题总结，务必在后续开发前阅读。

### B.1 CertificationBody 关联字段说明

#### 问题描述

`cert_certification_body` 表有两个关键字段：
- `Code`（varchar(36)）：GUID 格式，BaseEntity 基类自带，用于表间关联
- `CbCode`（varchar(50)）：CNAS 认可编号（如 "CB001"）

**关键发现**：`cert_org_standard` 和 `cert_org_stage` 表中的 `CbCode` 字段存储的是 `cert_certification_body.Code`（GUID），**不是** `cert_certification_body.CbCode`（CNAS编号）。

#### 实际数据示例

```sql
-- cert_certification_body 表
SELECT Code, CbCode, Name FROM cert_certification_body;
-- Code                              | CbCode | Name
-- 084beebb-8ef1-11f1-a2e2-e6bd9a193da2 | CB001  | 河北雄安尚龙认证有限公司
-- 4e14785245324dc2b6049c748900adff       | 1      | 11
-- 710f761a4f8c43948b25191ec7e98f57       | 2      | 21

-- cert_org_standard 表（关联字段存储的是 Code/GUID，不是 CbCode）
SELECT CbCode, StdCode FROM cert_org_standard;
-- CbCode                              | StdCode
-- 084beebb-8ef1-11f1-a2e2-e6bd9a193da2 | 21
-- 084beebb-8ef1-11f1-a2e2-e6bd9a193da2 | 31
```

#### 正确的关联查询

```sql
-- ✅ 正确：使用 cert_certification_body.Code 关联
SELECT cb.Name, os.StdCode
FROM cert_org_standard os
JOIN cert_certification_body cb ON cb.Code = os.CbCode;

-- ❌ 错误：使用 cert_certification_body.CbCode 关联（会返回空结果）
SELECT cb.Name, os.StdCode
FROM cert_org_standard os
JOIN cert_certification_body cb ON cb.CbCode = os.CbCode;
```

#### C# 代码中的关联

```csharp
// ✅ 正确：使用 org.Code（GUID）关联
var orgStdIds = orgStandards
    .Where(x => x.CbCode == org.Code)  // org.Code 是 GUID
    .Select(x => x.StdId)
    .ToList();

// ❌ 错误：使用 org.CbCode 关联（值不匹配）
var orgStdIds = orgStandards
    .Where(x => x.CbCode == org.CbCode)  // org.CbCode 是 "CB001"
    .Select(x => x.StdId)
    .ToList();
```

### B.2 EF Core 继承映射问题

#### 问题描述

项目采用 T+V 模式（Table + View），视图类继承实体类：
- `CertOrgStageView : CertOrgStage` → 映射到视图 `v_cert_org_stage`
- `CertOrgStandardView : CertOrgStandard` → 映射到视图 `v_cert_org_standard`
- `CertStageView : CertStage` → 映射到视图 `v_cert_stage`

**问题**：EF Core 默认会将子类的 `[Table]` 属性覆盖父类的表名映射，导致：
- `Set<CertOrgStandard>().ToList()` 查询的是视图而非表
- DELETE 操作会尝试删除视图数据（报错）

#### 解决方案

1. **视图类添加 `[NotMapped]` 特性**：
```csharp
[NotMapped]  // 防止 EF Core 映射到视图
public class CertOrgStageView : CertOrgStage
{
    // 视图特有字段...
}
```

2. **视图查询使用原生 SQL**：
```csharp
// ✅ 正确：使用 FromSqlRaw 查询视图
var stages = await _db.Set<CertStage>()
    .FromSqlRaw("SELECT * FROM v_cert_stage")
    .ToListAsync();

// ❌ 错误：直接查询视图类（会触发继承映射问题）
var stages = await _db.Set<CertStageView>().ToListAsync();
```

3. **删除操作使用原生 SQL**：
```csharp
// ✅ 正确：使用 ExecuteSqlRaw 删除
await _db.Database.ExecuteSqlRawAsync(
    $"DELETE FROM cert_org_standard WHERE CbCode = '{cbCode}'");

### B.3 编码生成规则

#### 目录编码

```csharp
// 后端生成规则（CodeGeneratorService.cs）
public string GenerateDirectoryCode(string standardCode, string phaseCode)
{
    var cleanStandard = standardCode.Replace(":", "").Replace("-", "").Replace(" ", "");
    var cleanPhase = phaseCode.Replace(":", "").Replace("-", "").Replace(" ", "");
    return $"SDC-{cleanStandard}|{cleanPhase}";
}

// 示例
// Input:  standardCode = "ISO 13485:2016", phaseCode = "STAGE-01"
// Output: "SDC-ISO134852016|STAGE01"

### B.4 数据库表关系速查

```
cert_certification_body (认证机构)
  ├── Code (GUID) ← 被 cert_org_standard.CbCode 引用
  ├── Code (GUID) ← 被 cert_org_stage.CbCode 引用
  └── CbCode (CNAS编号) ← 仅用于显示，不用于关联

cert_org_standard (机构-标准关联)
  ├── CbCode → cert_certification_body.Code ⚠️ 注意：是Code不是CbCode
  └── StdId → cert_iso_standard.Id

cert_org_stage (机构-阶段关联)
  ├── CbCode → cert_certification_body.Code ⚠️ 注意：是Code不是CbCode
  └── StageId → cert_cert_stage.Id

cert_standard_directory_config (目录配置)
  └── DirectoryCode = "SDC-{StandardCode}|{PhaseCode}"

cert_standard_directory_folder (文件夹)
   ├── DirectoryCode → cert_standard_directory_config.DirectoryCode
   ├── ParentCode → cert_standard_directory_folder.FolderCode (自引用)
   ├── Depth → 层级深度（1=根文件夹，2=子文件夹，...）
   ├── IsValid → TINYINT(1)，0=无效(预创建)，1=有效(已确认)
   └── FullPath → VARCHAR(1024)，从根到当前文件夹的名称路径（如"4记录文件/内审记录"）

cert_standard_directory_file (文件)
   ├── DirectoryCode → cert_standard_directory_config.DirectoryCode
   ├── FolderCode → cert_standard_directory_folder.FolderCode
   ├── IsValid → TINYINT(1)，0=无效(预创建)，1=有效(已确认)
   ├── FullPath → VARCHAR(1024)，从根到当前文件的完整名称路径（如"4记录文件/内审记录/陪审人员.doc"）
   ├── StoragePath → MinIO 原文件存储路径
   └── ConvertedStoragePath → MinIO 转换后文件存储路径（.doc→.docx 等）
```

> UPDATE cert_standard_directory_file  SET IsValid = 1 WHERE IsValid IS NULL;
> -- FullPath 需通过服务层 BuildFolderFullPath / BuildFileFullPath 重新计算后回填
> ```
