## 二、三层用户体系详解

### 2.1 用户层级总览

```
Layer 1: 平台管理层（管理后台）
├── 超级管理员     Role_Id=1    → 全部权限，系统内置
├── 总管理员       Role_Id=10   → 平台全部管理功能
├── 运维人员       Role_Id=13   → 系统监控/日志/备份
├── 配置人员       Role_Id=14   → 认证配置/标准/工作流
└── 质量专员       Role_Id=15   → 质量审核（可选）

Layer 2: 机构管理层（审核端 - 多租户）
├── 审核管理员     Role_Id=20   → 虚拟机构负责人，最高权限
├── 审核组长       Role_Id=21   → 管理组内审核员，分配任务
└── 普通审核员     Role_Id=22   → 执行审核任务，只能看自己权限范围

Layer 3: 企业层（受审核方）
└── 企业账号       Role_Id=30   → 上传文件/查看进度/下载报告
```

### 2.2 角色详细定义

#### Layer 1: 平台管理层

| 角色 ID | 角色名称 | 上级角色 | 部门归属 | 职责描述 |
|:------:|----------|:--------:|----------|----------|
| 1 | 超级管理员 | - | 系统内置 | 全部权限，不可删除 |
| 10 | 总管理员 | 1 | 总经办 | 平台全部管理功能、用户管理、角色分配 |
| 13 | 运维人员 | 10 | 运维部 | 系统监控、日志查看、备份恢复、性能优化 |
| 14 | 配置人员 | 10 | 技术部 | 认证机构配置、ISO标准维护、工作流配置 |
| 15 | 质量专员 | 10 | 质量部 | 质量体系审核、合规性检查（可选） |

#### Layer 2: 机构管理层（多租户）

| 角色 ID | 角色名称 | 上级角色 | 数据范围 | 职责描述 |
|:------:|----------|:--------:|----------|----------|
| 20 | 审核管理员 | 10 | 本机构全部 | ⭐ 虚拟机构负责人，可创建子账号、管理企业、查看机构全部数据 |
| 21 | 审核组长 | 20 | 本组+下属 | 管理组内审核员、分配审核任务、审核进度跟踪 |
| 22 | 普通审核员 | 21/20 | 个人分配 | 执行具体审核任务、填写检查清单、开具 NC |

**关键特性**：
- ✅ **数据隔离**：不同机构的审核管理员看不到对方的数据
- ✅ **层级管理**：审核管理员 → 组长 → 审核员的树形结构
- ✅ **虚拟机构**：每个审核管理员相当于一个独立的"认证机构"

#### Layer 3: 企业层

| 角色 ID | 角色名称 | 上级角色 | 数据范围 | 职责描述 |
|:------:|----------|:--------:|----------|----------|
| 30 | 企业账号 | 20 | 本企业 | 上传认证文件、查看审核进度、回复不符合项、下载报告 |

## 三、多租户数据隔离方案

### 3.1 隔离策略

采用 **Org_Code（机构编码）+ 数据过滤** 方案：

| 隔离维度 | 实现方式 | 说明 |
|----------|----------|------|
| **机构级** | Org_Code 字段 | 不同机构的数据完全隔离 |
| **部门级** | DeptIds 字段 | 同机构内按部门可见 |
| **个人级** | CreateID/AuditorId | 只能看自己创建/负责的数据 |

### 3.2 数据库扩展

#### 3.2.1 Sys_User 表扩展

```sql
-- ============================================================
-- Sys_User 表扩展字段
-- ============================================================

-- 方式 1：直接添加字段（推荐）
ALTER TABLE `Sys_User` 
ADD COLUMN `User_Type` TINYINT NOT NULL DEFAULT 0 
  COMMENT '用户类型: 0=系统内置 1=平台管理员 2=机构用户 3=企业用户' 
  AFTER `AppType`,
  
ADD COLUMN `Org_Code` VARCHAR(50) DEFAULT NULL 
  COMMENT '所属机构编码（用于多租户数据隔离）' 
  AFTER `User_Type`,
  
ADD COLUMN `Org_Id` INT DEFAULT NULL 
  COMMENT '所属机构ID（关联 cert_certification_body.id ）' 
  AFTER `Org_Code`,
  
ADD COLUMN `Parent_UserId` INT DEFAULT NULL 
  COMMENT '上级用户ID（用于机构层级管理）' 
  AFTER `Org_Id`,
  
ADD COLUMN `Employee_No` VARCHAR(50) DEFAULT NULL 
  COMMENT '工号' 
  AFTER `Parent_UserId`;

-- 添加索引
CREATE INDEX `idx_sys_user_org_code` ON `Sys_User`(`Org_Code`);
CREATE INDEX `idx_sys_user_user_type` ON `Sys_User`(`User_Type`);
CREATE INDEX `idx_sys_user_parent_user` ON `Sys_User`(`Parent_UserId`);
```


```
    ↓
```

```
[后端处理]
├── 校验数据完整性
├── 检查用户名是否已存在
├── 检查手机号格式
├── 创建 cert_registration 记录（状态=pending）

│   ├── [通过] → 创建 Sys_User 账号 + 设置密码 + 发送通知
│   └── [拒绝] → 记录拒绝原因 + 发送通知
    ↓
[申请人收到结果通知]
├── 通过 → 使用临时密码登录 → 修改密码 → 开始使用
└── 拒绝 → 可重新申请或联系管理员
```

## 十、关键决策点（需确认）

在开始实施前，请确认以下问题：

### Q1: 关于多入口的实现方式

**选项 A**：同一个 vol.web 项目，通过路由区分（推荐）
- 优点：代码统一，共享组件和 API
- 缺点：打包体积较大

**选项 B**：完全独立的项目（vol.web / auditor-web / enterprise-web）
- 优点：完全独立，可独立部署
- 缺点：重复代码多，维护成本高

**建议**：选择 A，后续如果 auditor 端确实需要很大差异化，再拆分。

### Q2: 关于审核员的自助注册

**选项 A**：完全开放（任何人可注册，需审核）
- 优点：用户体验好，降低门槛
- 缺点：可能有垃圾注册

**选项 B**：需要邀请码（只有拿到邀请码的人才能注册）
- 优点：可控，安全
- 缺点：门槛较高

**选项 C**：混合模式（公开注册 + 邀请码注册）（推荐）
- 审核管理员可开启/关闭自助注册
- 邀请码由审核管理员生成，发给特定人员

### Q3: 关于企业端的实现时机

**选项 A**：现在就实现（Phase 2-3 一起做）
- 优点：一步到位
- 缺点：工作量较大

**选项 B**：先实现管理端和审核端，企业端后期再做（推荐）
- 优点：聚焦核心，快速迭代
- 缺点：企业用户暂时无法使用

### Q4: 关于数据库扩展的执行时机

**建议**：确认本文档后立即执行 Phase 1 的数据库扩展，因为后续所有开发都依赖这些表结构。
