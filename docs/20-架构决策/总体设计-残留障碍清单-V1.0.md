**影响**：多人协作、权限隔离的基础

**需要补充**（简化版，符合您"管理员可不受限创建账号"的要求）：
```sql
-- 组织（认证机构）
CREATE TABLE organization (
    id UUID PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    admin_user_id UUID NOT NULL,  -- 创建者即为管理员

    subscription_expires_at TIMESTAMP,

    max_enterprise_users INT DEFAULT 50, -- 最大企业用户数（-1=不限）
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

-- 用户（统一用户表，通过 role 区分角色）
CREATE TABLE app_user (
    id UUID PRIMARY KEY,
    organization_id UUID REFERENCES organization(id),
    email VARCHAR(200) UNIQUE NOT NULL,
    phone VARCHAR(20),
    password_hash VARCHAR(255) NOT NULL,
    name VARCHAR(100) NOT NULL,
    role ENUM('org_admin','auditor','trainee','enterprise_admin',
              'enterprise_viewer') NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    last_login_at TIMESTAMP,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    
    -- 企业用户关联
    enterprise_id UUID REFERENCES enterprise(id)  -- 仅 enterprise_* 角色有值
);

-- 权限矩阵（简化版RBAC）
-- role → permission 映射在后端代码中硬编码（Phase 0-1）
-- Phase 2 可迁移到数据库配置
```

**关键设计点**（根据您的最新决定）：
- ✅ `max_auditors` 和 `max_enterprise_users` 设为 -1 表示不限（当前阶段不强制限制）
- ✅ `org_admin` 可以创建任意数量的 `auditor` / `enterprise_admin` / `enterprise_viewer`
- ✅ `enterprise_admin` 可以创建本企业的 `enterprise_viewer`
- ✅ 到期后 `subscription_status = 'expired'`，不能新建任务/编辑已有任务

## 二、业务流程闭环（4个障碍）

### 🔴 B-01：轻量路径→完整路径升级流程未定义

**现状**：
- §1.5 定义了双路径，提到"随时可升级到完整路径"
- 但**没有定义升级的具体操作和数据迁移逻辑**

**问题**：
- 轻量路径自动创建了"临时企业"和"临时任务"
- 用户点击"转为正式任务"时：
  - 临时企业是否变为正式企业？信息如何补全？
  - 临时任务的 ID 是否保留？（影响已有关联数据）
  - 如果用户已经上传了资料，这些资料是否跟随迁移？

**需要补充的设计**：
```yaml
升级流程:
  触发: 用户点击「转为正式任务」
  
  Step 1: 企业正式化
    IF 临时企业存在:
      将 Enterprise.is_temporary = false
      要求用户补全: 统一社会信用代码、法人、详细地址
      （如果用户不补全，保持临时状态但功能不受限）
  
  Step 2: 任务关联
    临时 Task 关联到正式 Enterprise
    Task.task_source 标记为 'upgraded_from_light'
  
  Step 3: 数据保留
    所有已上传的资料、OCR结果、AI分析结果全部保留
    新增 AuditActivity 时使用正式的任务流程
  
  UI 引导:
    弹出向导: 「完善企业信息」→ 「确认审核计划」→ 「进入完整工作台」
```

**建议状态**：🔴 **P0 必须补充**

### 🟡 B-03：报告编写→定稿→导出的完整流程不够清晰

**现状**：
- M05 报告生成器定义为"一键合成"
- 但实际PC端场景是多轮交互：生成初稿 → 审核/编辑 → 再生成 → 定稿 → 导出

**缺失的细节**：
- 报告草稿的版本管理？
- 多人协作时的编辑锁？
- 定稿后是否允许修改？（应该不允许，只能作废重开）
- 导出格式切换时是否需要重新渲染？

**建议补充**：
```yaml
报告生命周期:
  draft（草稿）→ reviewing（审核中）→ finalized（已定稿）→ archived（已归档）
  
  draft 状态:
    - 可多次 AI 重新生成
    - 可手动编辑
    - 版本自动保存（每次生成/编辑创建新版本）
    
  reviewing 状态:
    - 提交审核（如有多级审核）
    - 只读或批注模式
    
  finalized 状态:
    - 锁定，不可编辑
    - 可导出 PDF/Word/Excel
    - 如需修改 → 作废当前版 → 回到 draft（保留历史）
    
  archived 状态:
    - 随任务关闭自动归档
    - 只读
```

**建议状态**：🟡 P1

## 三、技术可行性（3个障碍）

### 🟡 T-01：Flutter 内嵌 Web 服务的性能和兼容性风险

**现状**：
- 方案看起来很优雅，但有一些潜在问题未讨论：

| 风险点 | 说明 | 应对 |
|--------|------|------|
| 手机发热 | Web服务+Flutter同时运行 | 监控CPU/内存，提供降级选项 |

**特别关注**：⚠️ **iOS 是否允许 App 运行 HTTP Server？**
- Android：✅ 允许
- iOS：需要验证（可能需要特殊处理）

**建议**：Phase 0 时做一个技术验证原型（最小可行内嵌Web服务）

**建议状态**：🟡 **P0 必须验证**

## 四、合规性（2个障碍）

### 🔴 C-01：数据保留策略与 ISO 17021 冲突【已部分解决】

**您的最新决定**：
> "数据修改为不做清空，付费结束后不能新建项目或针对原项目进行编辑"

**剩余需要落实到文档的内容**：

```yaml
更新 §1.2 商业模式的过期策略:

旧: "订阅到期后 3 个月缓冲期，期间数据保留但不可新建任务；超过 3 个月服务器数据清空"

新: "订阅到期后数据永久保留（符合 ISO 17021 要求，审核记录需保存至少5年）；到期后系统进入只读模式：可查看/导出所有历史数据，但不能新建任务、编辑已有任务或执行任何写操作。续费后恢复正常访问权限。"

同时需要在 AuditTask 表增加:
  - is_readonly: BOOLEAN  -- 到期后标记为只读
  - readonly_since: TIMESTAMP  -- 进入只读的时间
```

**还需要考虑的成本问题**：
- 永久保留意味着存储成本持续累积
- 建议：对只读数据进行冷存储压缩（如归档到低成本对象存储）

**建议状态**：🔴 **P0 必须在改文档时更新**
