## 二、对总体设计V2的影响评估

### 2.1 必须修改的部分（影响现有设计）

| 影响域 | 当前设计 | 需要变更为 | 影响程度 |
|--------|---------|-----------|:-------:|
| **用户模型** | 简单的User + role | Organization + Team + User(多角色) + RBAC | 🔴 **重大重构** |
| **领域模型** | DailyRecord(可选) | AuditActivity(核心) + AuditPlan + VoiceMemo | 🔴 **重大新增** |
| **数据过期策略** | 过期3个月→清空 | 永久保留 + 只读降级（符合ISO 17021） | 🟡 **必须修改** |
| **企业联系人** | 单一联系人字段 | EnterpriseContact多联系人实体 | 🟡 **必须新增** |
| **消息通信** | 仅SignalR通知 | MessageThread + Message完整消息系统 | 🟡 **重大新增** |

### 2.2 新增的实体清单

```
新增核心实体（12个）：

组织与用户：
  ├─ Organization（机构/组织）
  ├─ Team（小组/审核组）
  └─ EnterpriseContact（企业联系人）

审核执行：
  ├─ AuditActivity（审核活动）⭐ 核心
  ├─ AuditPlan（审核计划）
  ├─ AuditPlanItem（计划项）
  ├─ VoiceMemo（语音备忘录+AI增强文字）
  └─ DailySummary（每日总结）

沟通协作：
  ├─ MessageThread（消息会话）
  └─ Message（消息）

文档管理：
  ├─ EnterpriseDocument（企业文档）
  └─ DocumentVersion（文档版本+Hash）

系统支撑：
  ├─ Template（模板）⭐ 可复用
  ├─ ProductTODO（产品待办）⭐ 内置机制
  └─ AuditLog（操作审计日志）⭐ 必须
```

### 2.3 整体影响判断

```
影响等级：🔴 重大（但方向正确）

原因：
  1. 用户模型从简单→复杂（符合真实场景）
  2. 领域模型从扁平→层次化（AuditPlan→AuditActivity→Evidence）
  3. 新增约12个实体（但都有明确的设计依据）
  4. 数据库DDL需要重写（但这是Phase 0的工作）

正面影响：
  ✅ 设计更完整、更符合实际业务
  ✅ 为后续扩展打好基础
  ✅ 竞争力显著提升

风险：
  ⚠️ Phase 0的工作量增加（主要是数据库设计和API定义）
  ⚠️ 需要更多时间梳理清楚再动手编码

建议：
  💡 不要急着写代码！先把所有实体关系理清，画出完整的ER图，
     再开始Phase 0的骨架搭建。
```

## 三、风险评估报告

### 3.1 按严重程度排序的风险清单

#### 🔴 P0 - 必须在开发前解决（阻塞性风险）

| # | 风险 | 说明 | 影响 | 建议应对 |
|---|------|------|------|---------|
| R1 | **用户模型过于简化** | 当前设计假设单兵作战，实际是小组协作 | 所有功能的基础 | 重构为Organization+Team+RBAC |
| R2 | **数据保留策略违规** | "3个月清空"不符合ISO 17021要求（需保存5年+） | 合规风险 | 改为永久保留+只读降级 |
| R3 | **企业联系人缺失** | 企业有多角色联系人，单一字段无法满足 | 企业协作基础 | 新增EnterpriseContact实体 |
| R4 | **AuditLog缺失** | 操作审计是安全合规必需，且有助于问题追溯 | 安全+追溯 | 全量设计并实现 |

#### 🟡 P1 - 强烈建议在Phase 0-1解决（高风险）

| # | 风险 | 说明 | 影响 | 建议应对 |
|---|------|------|------|---------|
| R5 | **沟通模块缺失** | 企业-审核员缺乏有效的即时沟通渠道 | 协作效率 | 新增MessageThread+Message |
| R6 | **模板系统缺失** | 无预制模板增加新手门槛，无法沉淀知识 | 用户体验+竞争力 | 新增Template实体 |
| R7 | **审核前准备流程不明确** | 审核员出发前缺少结构化的准备指引 | 执行效率 | 作为AuditActivity的一种类型 |
| R8 | **文件版本控制缺失** | 企业文件可能被偷偷修改，无法追溯历史 | 合规+证据有效性 | Hash值管理方案 |
| R9 | **机构管理员功能偏弱** | 付费客户需要基本的管理能力 | 商业化基础 | 最简版：账号+任务指派+列表 |
| R10 | **订阅/到期管理缺失** | SaaS商业化必需的基本能力 | 收入保障 | 到期提醒+只读降级 |

#### 🟢 P2 - 建议在Phase 1-2解决（中风险）

| # | 风险 | 说明 | 影响 | 建议应对 |
|---|------|------|------|---------|
| R11 | 审核员Dashboard缺失 | 缺乏工作总览，任务多了会混乱 | 用户体验 | 任务统计卡片 |
| R12 | 审核邀请确认流程不清晰 | 企业协作起点模糊 | 流程完整性 | 发送邀请→确认→开始 |
| R13 | 企业预审资料上传缺失 | 无法提前查阅企业文件，现场效率低 | 审核效率 | 企业端资料室 |
| R14 | NC分级评审流程缺失 | Major NC通常需要技术专家复核 | 质量控制 | P2引入审批流 |
| R15 | 每日总结模块缺失 | 缺少复盘机制，经验难以积累 | 个人成长 | DailySummary |

#### ⚪ P3 - 可以延后（低风险）

| # | 风险 | 说明 | 建议 |
|---|------|------|------|
| R16 | 审核范围(Scope)详细定义不够结构化 | Phase 1先用简单字段 | Phase 2完善 |
| R17 | 抽样计划(Sampling Plan) | 初期使用频率不高 | Phase 2考虑 |
| R18 | 公正性声明电子签署 | 合规强化 | Phase 2-3 |
| R19 | 统计报表 | 机构管理层需求 | Phase 3 |
| R20 | 帮助中心/FAQ | 降低支持成本 | Phase 2 |
| R21 | 数据导出(全量) | 机构数据主权 | Phase 2-3 |

| # | 风险点 | 复杂度 | 应对建议 |
|---|--------|:-----:|---------|
| T1 | 离线数据冲突 | 🔴 高 | Phase 0-1用"最后写入胜"，Phase 2版本控制 |
