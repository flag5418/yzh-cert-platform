## 一、.NET Core 技术栈全面替代方案

### 1.1 原方案 vs .NET Core 对照

| 层 | 原方案（Python） | .NET Core 方案 | 选择理由 |
|----|-----------------|---------------|---------|
| 后端框架 | FastAPI | **ASP.NET Core 9 Minimal API** | 性能接近 FastAPI，原生 AOT 编译 |
| ORM | SQLAlchemy | **Entity Framework Core 9** | 类型安全，迁移管理成熟 |
| 数据库 | PostgreSQL | **PostgreSQL（不变）** | Npgsql 驱动成熟 |
| 缓存 | Redis | **Redis + StackExchange.Redis** | .NET 生态首选 Redis 客户端 |
| 任务队列 | Celery | **Hangfire** 或 **Coravel** | Hangfire 内置 Dashboard，SQL Server/PostgreSQL/Redis 持久化 |
| OCR | 百度 API / PaddleOCR | **PaddleOCR 通过 Process.Start 调用** | 或 **Tesseract .NET 绑定**做轻量场景 |
| NLP | spaCy / 规则引擎 | **ML.NET + 自定义规则引擎（C#）** | ML.NET 原生集成，无需 Python 互操作 |
| 向量检索 | ChromaDB | **ChromaDB 保持不变（独立进程）** | HTTP API 调用，语言无关 |
| 本地 LLM | ollama / llama.cpp | **ollama 独立进程** + **LLamaSharp**（.NET 绑定） | 或通过 ONNX Runtime 加载 GGUF 模型 |
| 文件存储 | 本地磁盘 → OSS | **本地磁盘 → MinIO**（自建 S3） | 私有机房首选，后续无缝对接云 OSS |
| 部署 | Docker 单机 | **Docker + .NET AOT 编译** | Single-file 发布，镜像体积 < 50MB |

### 1.4 自购服务器配置建议

根据此前分析（4C16G 够用 MVP），考虑本地 AI 模型额外开销：

| 配置项 | 建议规格 | 说明 |
|--------|---------|------|
| CPU | **Intel i7-14700 或 AMD 7950X**（16 核+） | 本地 AI 推理吃核心数 |
| 内存 | **64 GB DDR5** | 16G 给应用 + 16G 给 OS + 32G 给 LLM |
| GPU | **RTX 4060 Ti 16GB**（最低）/ **RTX 4090 24GB**（推荐） | 本地 LLM 推理核心 |
| 系统盘 | **1TB NVMe SSD** | OS + 应用 + Docker |
| 数据盘 | **4TB NVMe SSD**（RAID 1 双盘） | 文件存储 + 数据库 |
| 备份盘 | **8TB HDD** | 定期冷备份 |
| 网络 | 千兆网卡 + UPS | |

**整机预算**：约 1.2-1.8 万元（含 GPU）。

**架构要点**：

| 层 | 方案 | 月费 |
|----|------|------|
| 云服务器 | 阿里云轻量 2C4G 5Mbps | ~68 元/月 |
| 隧道方案 | ZeroTier（免费 25 节点）+ 云服务器做 moon 中继 | 免费 |
| 域名 + SSL | 任意域名 + Let's Encrypt 免费证书 | ~50 元/年 |
| 本地服务器 | 自购，电费 | ~150 元/月 |
| **合计** | | **约 230 元/月** |

**ZeroTier 原理**：所有设备加入同一个虚拟网络，通过加密 P2P 隧道直连。云服务器同时作为 ZeroTier moon 节点和 HTTPS 入口，对外暴露 443 端口，对内通过 ZeroTier IP 转发请求到本地服务器。不需要公网 IP，不需要端口映射。

**为什么这样做**：
- 数据完全在本地，满足认证机构对客户数据的合规要求
- 审核现场照片、企业文件不经过任何第三方云
- AI 推理在本地 GPU 完成，无 API 调用费用
- ZeroTier 加密隧道保证传输安全
- 云服务器仅做流量入口，不存储任何业务数据

## 二、企业与审核机构工作流体系

### 2.1 审核全流程梳理

一次 ISO 13485 认证审核的完整生命周期：

```
┌─────────────────────────────────────────────────────────────────────┐
│                     认证审核全生命周期                                │
│                                                                     │
│  [申请阶段]    [准备阶段]    [审核阶段]    [整改阶段]    [发证阶段]    │
│      │            │            │            │            │          │
│  企业提交    ←→ 机构审核    ←→ Stage 1   ←→ 企业整改   ←→ 机构发证  │
│  认证申请       申请材料       现场审核      NC关闭       证书维护    │
│      │            │            │            │            │          │
│      │            │         Stage 2                    年度监督审核  │
│      │            │         现场审核                                   │
│      ▼            ▼            ▼            ▼            ▼          │
│  ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐          │
│  │企业端│    │双向  │    │机构端│    │双向  │    │机构端│          │
│  │操作  │    │协作  │    │操作  │    │协作  │    │操作  │          │
│  └──────┘    └──────┘    └──────┘    └──────┘    └──────┘          │
└─────────────────────────────────────────────────────────────────────┘
```

其中 **准备阶段** 和 **整改阶段** 是企业与机构沟通最频繁的时期，沟通量占比 70%+。

### 2.2 需要工作流支撑的典型场景

| 场景 | 当前痛点 | 工作流方案 |
|------|---------|-----------|
| 申请材料提交与初审 | 微信/邮件来回传文件，版本混乱，无人追踪进度 | 在线提交流程：企业上传 → 机构初审 → 退回补交/通过 |
| 审核计划排期 | Excel 表格管理，冲突频发 | 审核员日历 + 企业可选时段 + 自动冲突检测 |
| 文件缺失补交 | 审核员口头/微信通知，企业遗忘 | 系统自动下发缺失清单 → 企业按清单上传 → 自动关联 |
| 不符合项整改 | NC 报告纸质传递，整改证据散落 | NC 在线下发 → 企业上传整改证据 → 审核员在线验证关闭 |
| 审核报告确认 | 邮件发送 PDF，来回修改 | 在线预览 → 企业确认/异议 → 审核员修改 → 电子签名 |
| 年度监督审核提醒 | 审核员手动翻日历提醒 | 系统自动计算监督审核到期日，提前 1 月通知双方 |
| 证书到期续期 | 企业忘记续期导致证书中断 | 到期前 3/2/1 月自动提醒，一键续期申请 |

### 2.4 核心工作流定义

#### 工作流 1：认证申请与材料初审

```
状态流转：
  企业提交申请 → [待初审] → 机构初审
                              ├─ 通过 → [待排期] → 审核员指定日期
                              └─ 退回 → [待补交] → 企业补交 → 重新进入[待初审]

关键节点：
  - 机构超过 3 个工作日未初审 → 自动催办通知审核组长
  - 企业超过 7 个自然日未补交 → 自动提醒 + 标记为"可能放弃"
```

#### 工作流 2：不符合项整改闭环

```
状态流转：
  审核员开具 NC → [待企业确认] → 企业确认
                                    └─ [整改中] → 企业上传证据
                                                     └─ [待验证] → 审核员验证
                                                                      ├─ 通过 → [已关闭]
                                                                      └─ 不通过 → 退回[整改中]（附说明）

关键节点：
  - NC 开具后 24h 内企业未确认 → 短信催办
  - NC 超过约定期限未关闭 → 升级通知审核组长 + 企业管理者代表
  - 同一 NC 退回超过 2 次 → 标记为"重点关注"，下次审核重点检查
```

#### 工作流 3：审核排期协作

```
状态流转：
  审核员发布可选时段 → [企业选择] → 企业选择 3 个偏好时段
                                       └─ [审核员确认] → 审核员确认最终时间
                                                            └─ [已排期] → 双方日历同步

关键节点：
  - 企业超过 3 天未选择 → 自动提醒
  - 排期冲突检测：审核员同时段已有其他项目 → 自动标记不可选
```

### 2.5 消息与通知通道
