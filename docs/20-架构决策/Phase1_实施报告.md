## 📊 数据库变更详情

### 1. Sys_User 表扩展

新增字段：

| 字段名 | 类型 | 说明 | 示例值 |
|--------|------|------|--------|
| `UserType` | TINYINT | 用户类型（核心字段） | 1=超级管理员, 10=总管理员, ..., 30=企业账号 |
| `OrgCode` | VARCHAR(50) | 机构编码（多租户隔离） | NULL=平台层, 'CB001'=尚龙认证 |
| `OrgId` | BIGINT(20) | 机构 ID（关联 cert_org_config.id） | 1, 2, 3... |
| `ParentUserId` | INT(11) | 上级用户 ID（层级管理） | 用于企业子账号 |

新增索引：
- `idx_sys_user_org_code` (OrgCode) - 提升多租户查询性能
- `idx_sys_user_user_type` (UserType) - 提升按类型筛选性能

### 2. 新增表

#### cert_org_config（认证机构配置表）
```sql
用途：存储所有认证机构的基本信息和配置
关键字段：
  - id (主键), code (GUID), OrgCode (唯一编码)
  - org_name, org_short_name, org_type
  - registration_no (批准号)
  - theme_config (JSON, 前端主题定制)
  - login_config (JSON, 登录页定制)
  - max_users, max_enterprises (配额限制)
  - expire_date (服务到期日)
```

#### cert_registration（注册申请表）
```sql
用途：处理机构注册和企业注册申请
支持两种注册类型：
  - registration_type = 1: 认证机构注册
  - registration_type = 2: 企业用户注册
工作流：待审核 → 已通过/已拒绝 → （可撤销）
```

## ⚠️ 注意事项

### 数据库层面：
1. **OrgCode 字段的重要性**
   - 这是多租户隔离的核心字段
   - 所有业务查询都必须带上 OrgCode 条件
   - 后端 Service 层需要统一封装过滤逻辑

2. **UserType 字段的扩展性**
   - 当前定义了 9 种用户类型
   - 如果未来需要增加新类型，只需扩展 CASE WHEN 即可
   - 建议在后端定义枚举类统一管理

3. **索引优化**
   - 已为 OrgCode 和 UserType 创建索引
   - 如果数据量大，可能还需要复合索引（OrgCode + status 等）

### 应用层面：
1. **向后兼容**
   - 现有的 admin 账号已被设置为 UserType=1（超级管理员）
   - 未设置 UserType 的老用户默认为 NULL，需要在代码中做兼容处理
   - 建议：NULL 或 0 视为普通用户或拒绝登录

2. **安全性**
   - OrgCode 不能由前端传入，必须从 Token 或 Session 中获取
   - 防止用户通过修改请求参数越权访问其他机构数据
   - 建议在 API 层增加全局过滤器自动注入 OrgCode

3. **性能考虑**
   - 多租户查询会增加 WHERE 条件，注意索引命中
   - 对于统计报表类查询，可以考虑缓存或预聚合

## 📞 问题排查指南

### 常见问题：

**Q1: 登录后看不到菜单？**
- 检查 Sys_RoleAuth 表是否有该角色的权限记录
- 检查 Sys_Menu 表中的菜单是否 Enable=1
- 查看浏览器控制台是否有报错

**Q2: 能看到菜单但点击没反应？**
- 检查菜单的 Url 字段是否正确配置
- 检查前端路由是否注册了对应组件
- 查看 Network 请求是否返回 404

**Q3: 能看到其他机构的数据？**
- 检查后端查询是否添加了 OrgCode 过滤
- 检查 Token 中是否包含正确的 OrgCode
- 检查是否有接口绕过了过滤器

**Q4: 新增用户失败？**
- 检查必填字段是否完整（UserName, UserPwd, Role_Id, UserType）
- 检查 OrgCode 是否与 cert_org_config 表中的记录匹配
- 检查是否有唯一索引冲突（如 UserName 重复）
