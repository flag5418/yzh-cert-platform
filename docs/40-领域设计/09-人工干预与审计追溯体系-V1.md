# 人工干预与审计追溯体系设计
> 日期：2026-07-27
> 前置文档：01-08

---

## 一、问题本质

当前系统流程是单向的：

```
上传文件 → AI 分析 → 生成报告 → 导出
```

但真实审核场景是迭代的：

```
上传文件 → AI 分析 → ────→ 人工复核/修改 → 生成报告 → 导出
                        ↑         │
                        │         ▼
                        └── 有异议 ← 退回重新判断
                            或补充证据
```

**核心矛盾**：AI 可以提速 80%，但剩下 20% 必须由人兜底。如果系统不允许人修改 AI 的输出、或者修改了却无迹可寻，审核员不敢用，CNAS 审核也过不了。

---

## 二、需要人工干预的典型场景

| 场景 | 示例 | 干预类型 |
|------|------|---------|
| **AI 判定过严** | AI 识别到管理手册缺少 8.3 条款，判为严重不符合；但审核员知道该企业确实无设计活动，8.3 不适用 | 修改判定 + 补充理由 |
| **AI 判定过松** | AI 认为文件基本完整给"符合"；审核员发现文件是旧版本 | 降级判定 + 补充证据 |
| **条款匹配错误** | AI 把"供应商评价缺失"匹配到 7.4.3 而非 7.4.1 | 修正条款引用 |
| **证据描述不准确** | AI 提取的审核证据措辞有歧义，需要审核员润色 | 编辑文本 |
| **补充遗漏证据** | AI 漏识别了一份关键文件，审核员手动补充 | 新增审核发现 |
| **撤销错误发现** | AI 误判——一份文件实际存在但因格式问题未被识别 | 删除/标记无效 |
| **行业经验覆盖** | AI 无法判断"该企业的洁净车间压差记录缺少关键时段数据"这种专业判断 | 人工新增发现 |
| **尺度调整** | 审核组长判断该企业整体体系运行良好，决定将某轻微不符合降为观察项，给企业整改机会 | 修改严重度 + 备注原因 |

## 三、解决方案：三层可干预架构

```
┌─────────────────────────────────────────────────────┐
│                  审核项目                            │
│                                                     │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐          │
│  │ AI 初稿  │ →  │ 人工复核 │ →  │ 最终定稿 │          │
│  │ (只读)   │    │ (可编辑) │    │ (锁定)   │          │
│  └────┬────┘    └────┬────┘    └────┬────┘          │
│       │              │              │               │
│       │        每次修改自动           │               │
│       │        记录变更日志           │               │
│       ▼              ▼              ▼               │
│  ┌──────────────────────────────────────┐           │
│  │          变更审计日志（不可删除）       │           │
│  │  谁 / 什么时间 / 改了什么 / 为什么改   │           │
│  └──────────────────────────────────────┘           │
└─────────────────────────────────────────────────────┘
```

### 3.1 层级一：AI 初稿（只读基线）

AI 生成的所有内容标记为 `source: "ai"`，作为不可篡改的基线版本。

```
每条审核发现的数据结构：

{
  "finding_id": "F-2026-003",
  "clause": "ISO 9001:2015 / 4.4",
  "severity": "major_nc",        // AI 原始判定
  "evidence": "管理手册.doc 无法被系统识别或提取正文文本",
  "source": "ai",                // ← 标识来源
  "ai_confidence": 0.92,         // ← AI 置信度（低置信度高亮提醒人工复核）
  "created_at": "2026-07-27 10:15:00",
  "created_by": "system",
  
  "history": [],                 // ← 变更历史，初始为空
  
  // 人工可修改字段 ↓
  "current_severity": "major_nc",   // 当前生效的严重度
  "current_evidence": "...",        // 当前生效的证据描述
  "current_clause": "...",          // 当前生效的条款
  "status": "pending_review",       // 待复核 / 已确认 / 已修改 / 已删除
  "reviewer": null,
  "reviewed_at": null
}
```

### 3.2 层级二：人工复核（所有字段可编辑）

审核员在复核界面看到的每条 AI 发现，都有两个操作入口：

```
┌─────────────────────────────────────────────────────┐
│  发现 #03                          AI置信度: 92%    │
│                                                     │
│  条款：[ISO 9001:2015 / 9.3 管理评审    ] [✎ 修改] │
│  严重度：[严重不符合 ▼]                    [✎ 修改] │
│                                                     │
│  AI 审核证据（原文）：                               │
│  ┌─────────────────────────────────────────────┐    │
│  │ "受审核方提供的审核资料清单中未包含《内部   │    │
│  │  审核报告》文件，仅有内审签到表，无法验证   │    │
│  │  内审过程的完整性和结论的有效性。"          │    │
│  └─────────────────────────────────────────────┘    │
│                                     [✎ 编辑证据]    │
│                                                     │
│  人工补充说明（选填）：                              │
│  ┌─────────────────────────────────────────────┐    │
│  │                                             │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  [✓ 确认]  [✎ 修改后确认]  [↩ 退回重判]  [✕ 删除] │
└─────────────────────────────────────────────────────┘
```

**关键设计**：

| 操作 | 触发条件 | 记录内容 |
|------|---------|---------|
| 直接确认 | 审核员认为 AI 判定完全正确 | `action: "confirmed", reviewer: "张三", time: "..."` |
| 修改后确认 | 审核员改了任何字段后保存 | `action: "modified", changes: [{field, old, new}], reason: "..."` |
| 退回重判 | 审核员补充证据/修正参数后让 AI 重新分析 | `action: "rejudge", reason: "补充了XX文件，请重新分析"` |
| 删除 | AI 判定完全错误 | `action: "deleted", reason: "原因"` |
| 手动新增 | 审核员自行添加 AI 未发现的项 | `source: "manual", created_by: "张三"` |
| 补充证据 | 上传新文件/追加说明 | `action: "evidence_appended", files: [...], note: "..."` |

### 3.3 层级三：变更审计日志

所有修改记录在 `history[]` 数组中，永久保存，不可删除。

```json
{
  "finding_id": "F-2026-003",
  "ai_original": {
    "severity": "major_nc",
    "clause": "ISO 9001:2015 / 9.3",

    "evidence": "未包含《内部审核报告》文件，仅有内审签到表..."
  },
  "history": [
    {
      "timestamp": "2026-07-27 14:22:00",
      "user": "张三（审核组长）",
      "action": "severity_change",
      "field": "severity",
      "old_value": "major_nc",
      "new_value": "minor_nc",

      "user": "张三（审核组长）",
      "action": "text_edit",
      "field": "evidence",
      "old_value": "未包含《内部审核报告》文件...",
      "new_value": "未包含《内部审核报告》文件，仅有内审签到表...",
      "reason": "补充了签到表信息，使证据描述更完整"
    }
  ]
}
```

## 四、审核员"尺度放开"的合规设计

"放开尺度"在 CNAS 审核中是一个敏感但现实的需求。不能让审核员在系统里偷偷改，必须有合理合规的路径。

### 4.1 尺度调整的规范路径

| 场景 | 允许的操作 | 必须的条件 |
|------|-----------|-----------|
| 严重 → 轻微 | ✅ 允许 | 必须填写降级理由 + 组长审批（如果操作人是组员） |
| 轻微 → 观察项 | ✅ 允许 | 必须填写理由 |
| 严重 → 观察项（跳级降） | ⚠️ 需审批 | 必须有组长 + 技术负责人双重审批 |
| 轻微 → 严重（升级） | ✅ 自由 | 审核员可直接操作，仅需填写理由 |
| 删除一条发现 | ⚠️ 需审批 | 组长审批，且记录不会真正删除，仅标记为 `status: "voided"` |

### 4.2 UI 交互设计

当审核员将严重不符合降级时：

```
┌─────────────────────────────────────────────────┐
│  ⚠️ 严重度变更确认                               │
│                                                 │
│  您正在将发现 #03 的严重度从                      │
│  【严重不符合】 降级为 【轻微不符合】             │
│                                                 │
│  降级理由 *（将记录在审核日志和报告中）：          │
│  ┌─────────────────────────────────────────┐    │
│  │ 企业已提供内审签到表，表明内审活动已开展， │    │
│  │ 仅缺正式报告格式文件，不构成系统性缺失。   │    │
│  └─────────────────────────────────────────┘    │
│                                                 │
│  □ 我确认此变更符合审核准则和机构程序             │
│                                                 │
│  [取消]  [确认降级]                              │
└─────────────────────────────────────────────────┘
```

### 4.3 审核组长审批流（跳级降级/删除场景）

```
组员提交降级/删除申请
       │
       ▼
  组长收到待审批通知
       │
       ├─ 同意 → 变更生效，记录审批人+时间
       │
       ├─ 驳回 → 恢复原值，记录驳回理由
       │
       └─ 退回修改 → 组员重新填写理由
```

MVP 阶段不需要复杂的审批流引擎——一个状态字段 + 通知即可。

## 五、审计追溯的三个视角

### 5.1 逐条发现的变更时间线

```
发现 #03 变更时间线
──────────────────────────────────────
10:15  [系统]   AI 生成，严重度=严重不符合
14:22  [张三]   严重度：严重 → 轻微（理由：企业已提供签到表）
14:25  [张三]   编辑证据描述（补充了签到表信息）
14:30  [李四]   组长审批通过本次变更
──────────────────────────────────────
最终状态：轻微不符合，已组长审批
```

### 5.2 按审核员的修改统计（管理视角）

| 审核员 | 总发现数 | 修改数 | 修改率 | 降级次数 | 升级次数 | 删除次数 |
|--------|---------|--------|--------|---------|---------|---------|
| 张三 | 45 | 8 | 17.8% | 3 | 2 | 0 |
| 李四 | 52 | 3 | 5.8% | 1 | 1 | 1 |
| 王五 | 38 | 12 | 31.6% | 6 | 0 | 1 |

高修改率或频繁降级可能是审核员经验不足，也可能是 AI 模型在该领域准确度不够——可作为模型优化的反馈信号。

### 5.3 终版报告中的修改痕迹

最终导出的报告可以选择性展示修改标记：

```
审核证据：
未包含《内部审核报告》文件，仅有内审签到表，无法验证内审过程的完整性
和结论的有效性。[人工补充]

严重度：轻微不符合  [原始AI判定：严重不符合，已由审核组长张三调整]
```

CNAS 审核时如果需要验证过程，可以导出完整审计日志。

## 六、数据模型设计

### 6.1 核心表结构

```sql
-- 审核发现表（核心）
CREATE TABLE audit_findings (
    id              UUID PRIMARY KEY,
    project_id      UUID NOT NULL,           -- 所属审核项目
    finding_no      VARCHAR(20) NOT NULL,    -- 发现编号 F-2026-003
    source          VARCHAR(10) NOT NULL,    -- 'ai' | 'manual'
    ai_confidence   DECIMAL(3,2),            -- AI 置信度（仅 ai 来源）
    
    -- 当前生效值
    clause          VARCHAR(100) NOT NULL,
    severity        VARCHAR(20) NOT NULL,    -- major_nc / minor_nc / observation / conforming
    evidence        TEXT NOT NULL,
    status          VARCHAR(20) NOT NULL,    -- pending_review / confirmed / modified / voided
    
    -- 审核人信息
    reviewer_id     UUID,
    reviewed_at     TIMESTAMP,
    
    created_at      TIMESTAMP NOT NULL,
    created_by      VARCHAR(50) NOT NULL     -- 'system' 或用户ID
);

-- 变更历史表（只追加，不修改不删除）
CREATE TABLE finding_change_logs (
    id              UUID PRIMARY KEY,
    finding_id      UUID NOT NULL REFERENCES audit_findings(id),
    sequence        INT NOT NULL,            -- 变更序号 1,2,3...
    
    action          VARCHAR(30) NOT NULL,    -- severity_change / text_edit / clause_change / delete / confirm / rejudge
    field           VARCHAR(50),             -- 被修改的字段
    old_value       TEXT,                    -- 原始值（JSON或文本）
    new_value       TEXT,                    -- 新值
    
    changed_by      VARCHAR(50) NOT NULL,    -- 操作人
    changed_at      TIMESTAMP NOT NULL,      -- 操作时间
    reason          TEXT NOT NULL,           -- 变更理由（必填）
    
    -- 审批相关（仅需要审批的操作）
    approval_required BOOLEAN DEFAULT FALSE,
    approved_by    VARCHAR(50),
    approved_at    TIMESTAMP,
    approval_status VARCHAR(20)              -- pending / approved / rejected
);

-- 确保变更日志不可删除（数据库层面）
REVOKE DELETE, UPDATE ON finding_change_logs FROM app_user;
```

## 九、一句话总结

系统应该这样定位：**AI 负责写草稿，审核员负责改稿子，系统负责记下谁改了哪里、为什么改。** 这三者缺一不可——没有 AI 太慢，没有人工不可信，没有审计日志无法通过 CNAS 核查。所有修改必须填理由，重大降级或删除必须组长审批，变更日志数据库层面禁止删改。
