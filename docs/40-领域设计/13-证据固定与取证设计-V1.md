# 证据固定——上传文件签名、水印与现场取证的证据链设计
> 日期：2026-07-27
> 前置文档：01-12

---

## 一、为什么要做证据固定

审核活动的本质是"证据收集→判定→出具结论"。如果证据本身可以被质疑，整个审核结论就站不住。证据固定的目的不是防君子，是防纠纷：

| 纠纷场景 | 没有证据固定 | 有证据固定 |
|---------|------------|-----------|
| 企业声称"我们交了文件，审核员弄丢了" | 审核员口说无凭 | 上传时间戳+哈希值+企业签收记录，铁证 |
| 企业声称"这份文件不是我们当时提供的，被掉包了" | 双方扯皮 | SHA-256 哈希值比对，文件是否被修改一目了然 |
| 审核员声称"现场照片就是这张" | 照片无时间地点，可被质疑拍摄时间 | 照片自带 GPS+时间戳水印，APP 端不可篡改 |
| 药监局飞检发现严重问题，企业推责"审核机构没查到" | 审核记录无不可否认的证据 | 原始上传文件+现场取证照片，完整证据链 |
| 审核员把不符合项悄悄改轻了 | 没有修改痕迹（09号已解决） | 原始文件+原始判定+变更日志，完整的双重保险 |

**一句话**：证据固定是 09/10 号追溯体系的前置环节——没有原始证据固定，追溯分析就没有可信的起点。

## 三、第一类：企业上传文件的证据固定

### 3.1 流程设计

```
企业管理员登录 → 进入项目 → 上传文件
                         │
       ┌─────────────────┘
       ▼
  ┌─────────────────────────────────────┐
  │ 系统在服务端计算 SHA-256 哈希         │
  │ 记录上传人 / IP / 时间戳（服务端时间） │
  │                                     │
  │ 文件存入证据库                         │
  │  ├── 原始文件（只读，永不修改）          │
  │  └── metadata.json（含哈希+上传信息）   │
  └─────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────┐
  │ 生成上传回执（供企业留存）              │
  │ ┌─────────────────────────────────┐ │
  │ │ 文件上传回执                      │ │
  │ │                                 │ │
  │ │ 项目编号：PRJ-2026-089           │ │
  │ │ 文件名称：质量管理手册V3.2.pdf     │ │
  │ │ 文件哈希：SHA-256:a3f8b2c...     │ │
  │ │ 上传时间：2026-03-10 14:22:05    │ │
  │ │ 上传人：李总（企业管理员）         │ │
  │ │ 文件大小：3.2 MB                 │ │
  │ │                                 │ │
  │ │ 此回执由系统自动生成，证明上述文件  │ │
  │ │ 已于所示时间上传至审核平台。      │ │
  │ └─────────────────────────────────┘ │
  └─────────────────────────────────────┘
```

### 3.2 是否加水印？

不建议对原始文件做破坏性水印（覆盖文字），而是在**预览层叠加**：

```
文件预览时的视觉水印（非破坏性）：

┌─────────────────────────────────────────┐
│  上传人：XX医疗器械有限公司               │
│  上传时间：2026-03-10 14:22:05           │
│  项目编号：PRJ-2026-089                  │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │                                 │    │
│  │    （原文件内容）                  │    │
│  │                                 │    │
│  │     上传人：XX医疗               │    │  ← 半透明水印
│  │     2026-03-10 14:22            │    │
│  │                                 │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**水印策略**：

| 方案 | 场景 | 推荐度 |
|------|------|--------|
| 预览层叠加水印 | 审核员在平台内查看文件时，自动叠加半透明水印 | ✅ 推荐 |
| 导出带水印 | 审核员下载文件时，可选择"带水印下载" | ✅ 推荐 |
| 原文件加水印 | 上传时直接修改文件 | ❌ 不推荐（破坏原始凭据） |
| 纯元数据 | 仅在 metadata 中记录，文件本身无可见标识 | ⚠️ 仅元数据不够直观 |

### 3.3 哈希值的作用

```sql
-- 文件证据表
CREATE TABLE evidence_files (
    id              UUID PRIMARY KEY,
    project_id      UUID NOT NULL,
    file_name       VARCHAR(255) NOT NULL,
    file_path       VARCHAR(500) NOT NULL,      -- 存储路径
    file_size       BIGINT NOT NULL,
    sha256_hash     VARCHAR(64) NOT NULL,        -- SHA-256 哈希
    mime_type       VARCHAR(100),
    
    -- 上传信息
    uploaded_by     VARCHAR(50) NOT NULL,        -- 上传人（企业方）
    uploaded_by_role VARCHAR(20) NOT NULL,       -- enterprise_admin / auditor
    uploaded_at     TIMESTAMP NOT NULL,          -- 服务端时间
    upload_ip       VARCHAR(45),                 -- 上传IP
    
    -- 文件来源
    source          VARCHAR(20) NOT NULL,        -- enterprise_upload / auditor_collect / system_generated
    
    -- 完整性校验
    integrity_checked BOOLEAN DEFAULT TRUE,      -- 上传时已校验
    integrity_last_check TIMESTAMP               -- 最后一次完整性校验时间
    
    -- 注意：此表数据永不删除，不物理修改
);
```

**哈希验证的工具价值**：

```
纠纷场景：
企业声称："我提交的是V3版本，审核员用了V2版本的漏洞来判我不符合"

处理流程：
1. 调出该文件的上传记录，获取 SHA-256 哈希值
2. 哈希 = a3f8b2c1d4e5...
3. 找到存储服务器上的原始文件，重新计算哈希
4. 哈希匹配 → 文件未被修改 → 企业上传的就是V2
5. 哈希不匹配 → 文件被修改过 → 调出操作日志追查
```

### 3.4 数字签名（强合规可选）

如果企业有电子签章（UKey/手机盾），上传时可做数字签名：

```
流程：
  企业选择文件 → 系统计算哈希 → 企业对哈希签名 → 
  签名值 + 证书 + 时间戳 存入 metadata

效力：
  《电子签名法》认可的数字签名 = 纸质签字盖章的法律效力
  无需额外部署TSA（可信时间戳），已在电子签章体系中内置
```

MVP 阶段不建议强制要求数字签名（中小企业不一定有电子签章），但架构预留接口。

## 四、第二类：审核员现场 App 取证的证据固定

### 4.1 拍摄照片的证据固定

现场照片最容易产生争议——拍摄时间、地点、内容是否真实，都可能被质疑。

```
审核员现场拍照流程：

  打开 App → 进入审核项目 → 拍照
       │
       ▼
  App 自动采集元数据：
  ┌─────────────────────────────────────┐
  │ 设备信息：审核员手机型号、设备ID      │
  │ GPS坐标：31.2304, 121.4737          │
  │ GPS地址：上海市浦东新区XX路XX号       │
  │ 拍摄时间：2026-03-15 10:22:05        │
  │ 审核项目：PRJ-2026-089              │
  │ 关联条款：7.5 生产和服务提供（可选）   │
  │ 审核员：张三                         │
  │ 照片哈希：SHA-256:b7f9a3...          │
  └─────────────────────────────────────┘
       │
       ▼
  照片写入EXIF + 叠加视觉水印：
  ┌─────────────────────────────────────┐
  │                                     │
  │  ┌─────────────────────────────┐    │
  │  │                             │    │
  │  │     （现场拍摄的照片）         │    │
  │  │                             │    │
  │  │  ┌─────────────────────┐    │    │
  │  │  │ 2026-03-15 10:22:05 │    │    │  ← 时间戳水印
  │  │  │ 上海市浦东新区XX路     │    │    │  ← GPS水印
  │  │  │ 审核员：张三          │    │    │
  │  │  │ 关联条款：7.5        │    │    │
  │  │  │ 照片哈希：b7f9a3...  │    │    │
  │  │  └─────────────────────┘    │    │
  │  └─────────────────────────────┘    │
  │                                     │
  └─────────────────────────────────────┘
       │
       ▼
  上传至服务端 → SHA-256入库 → 存为只读
```

### 4.2 关键防篡改措施

| 措施 | 目的 | 实现 |
|------|------|------|
| **禁止相册选图** | 防止审核员用非现场拍摄的旧照片 | App 拍照入口只能调用相机，禁用相册；如需补充已有照片，标记为"非现场拍摄" |
| **GPS 强制获取** | 证明拍摄地点在企业现场 | 拍照时 App 强制读取 GPS（可与企业注册地址做距离校验） |
| **服务端时间戳** | 防手机时间被篡改 | App 上传瞬间使用服务端时间，而非手机本地时间 |
| **拍照即锁定** | 防止拍照后 PS 再上传 | App 拍照→计算哈希→立即上传，中间无编辑环节。如需标注，在上传后通过系统标注功能完成 |
| **哈希链** | 防单张照片被替换 | 每张照片的哈希写入不可修改的记录表 |

### 4.3 录音/录像的证据固定

与照片同理，录音文件同样需要固定：

```
录音文件元数据：
├── 开始时间（服务端时间）
├── 结束时间
├── GPS 坐标
├── 设备ID
├── 审核员ID
├── 关联条款/发现
├── SHA-256 哈希
└── 语音转文本结果（自动，方便检索）
```

### 4.4 现场取证与发现的关联

现场拍摄的照片/录音不应孤立存在，必须关联到具体审核发现：

```
审核员现场发现洁净车间压差表不工作
    │
    ├── 拍照1：压差表显示为零（关联发现 F-2026-015）
    ├── 拍照2：车间全景（关联发现 F-2026-015）
    └── 录音：与车间主任的对话（关联发现 F-2026-015）

在审核报告中：
  发现 #F-2026-015：洁净车间压差未监测
  证据包含：
    📷 2026-03-15 10:22 压差表显示为零.jpg
    📷 2026-03-15 10:23 车间全景.jpg
    🎙 2026-03-15 10:25 现场访谈录音.mp3
  [以上证据均已固定哈希值和时间戳]
```

## 五、证据链完整导出

当 CNAS 评审或发生纠纷时，系统应能一键导出完整证据包：

```
证据链导出包 PRJ-2026-089

├── 证据清单.pdf（含每条证据的哈希值、时间戳、来源）
├── 企业上传文件/
│   ├── 质量管理手册V3.2.pdf
│   ├── 内审报告_2024.docx
│   └── metadata.json（每条的上传记录）
├── 现场取证/
│   ├── IMG_20260315_102205.jpg（压差表）
│   ├── IMG_20260315_102305.jpg（车间全景）
│   ├── AUD_20260315_102530.mp3（访谈录音）
│   └── metadata.json
├── 哈希校验工具.html（离线HTML，可验证所有文件哈希）
└── 操作日志_2026.csv（完整操作审计记录）
```

`哈希校验工具.html` 是一个自包含的验证页面，评审人员无需安装任何软件，浏览器打开即可验证每个文件的哈希是否与记录一致。

## 六、方案选择：做到什么程度

| 层级 | 内容 | 实现成本 | MVP 建议 |
|------|------|---------|---------|
| **基础层** | 上传文件 SHA-256 哈希 + 服务端时间戳 + IP 记录 + 预览层水印 | 3 人天 | ✅ 必须做 |
| **基础层** | 现场拍照 GPS+时间水印 + 禁止相册 + 拍照即锁定 | 4 人天 | ✅ 必须做 |
| **增强层** | 录音证据固定 + 语音转文字 | 3 人天 | ✅ 建议做 |
| **增强层** | 证据链一键导出（含离线校验工具） | 2 人天 | ✅ 建议做 |
| **合规层** | 企业电子签章（数字签名） | 5 人天 | ⚠️ 预留接口，MVP 不做 |
| **合规层** | 哈希链/区块链存证 | 8 人天 | ❌ MVP 严重过度 |
| **合规层** | 对接司法鉴定中心 | 按需 | ❌ 产品化后再说 |

MVP 合理范围：**基础层 7 人天 + 增强层 5 人天 = 12 人天**。

## 八、一句话总结

证据固定不是"加个水印"——它是对审核活动中所有数字证据的**不可否认性锚定**。上传文件算哈希、拍照加水印、录音锁 GPS、所有操作记录服务端时间戳，形成一条从"企业上传原始凭据"到"最终报告每一个结论"的完整证据链。CNAS 来评审时一键导出证据包，哈希校验工具离线验证——这才叫经得起推敲。
