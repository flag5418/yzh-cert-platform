### 1.4 `cert_dict` 的真实形态（重要澄清）

**`cert_dict` 不是一张业务表，不存在 `CREATE TABLE cert_dict`。** 它的定义是：

> 体系认证相关的所有业务字典**必须**统一挂载在 `cert_dict`（认证平台字典，**Dic_ID=107**，ParentId=0）分类下。禁止在 `系统字典`（Dic_ID=87）或其他分类下创建认证业务字典。
> —— `数据库表设计-V2.md` §7.3（L1266-1272）

即：字典的物理载体仍是 Vol 内置的 `Sys_Dictionary` / `Sys_DictionaryList`，`cert_dict` 只是**分类归属约定**。§7.3.3 给出 cert_dict 下**现存 12 个字典、共 72 个字典项**（L1290-1305）：

| # | DicNo | 字典名称 | OrderNo | 项数 | 与标准/阶段模型的关系 |
|---:|---|---|---:|---:|---|
| 1 | `cert_status` | 证书状态 | 30 | 5 | 产出物侧（证书生命周期） |
| 2 | `standard_status` | ISO标准状态 | 35 | 3 | **标准**（draft/published/deprecated） |
| 3 | `audit_conclusion` | 审核结论 | 40 | 5 | 产出物侧（pass/pass_with_nc/fail/…） |
| 4 | `stage_category` | 认证阶段分类 | 40 | 3 | **阶段**（process/audit/post） |
| 5 | `stage_status` | 认证阶段状态 | 41 | 2 | **阶段**（active/inactive） |
| 6 | `iso_category` | ISO标准分类 | 42 | 7 | **标准**（quality/environment/safety/info/food/medical/energy） |
| 7 | `nc_severity` | 不符合项严重程度 | 50 | **4** | 产出物侧（major/minor/observation/**suggestion**） |
| 8 | `application_status` | 申请状态 | 70 | 9 | 流程侧 |
| 9 | `task_status` | 任务状态 | 80 | 6 | 流程侧 |
| 10 | `org_status` | 机构状态 | 90 | 4 | 机构侧 |

### 1.7 标准侧缺口（面向"体系→标准→版本→条款"分层）

| 缺口 | 证据 | 影响 |
|---|---|---|
| 无"体系"实体表 | 体系仅体现为 `category` 字典值（iso_category 7 项）；`cert_type`/`standard_type` 字典已被删 | 无法表达"一个体系（如质量）下有多个标准"的层级与继承 |
| 无"版本"实体表 | 版本仅 `version_year` int 字段 | 无法表达同标准多版本并存、版本切换、条款随版本变化 |
| `parent_code` / `is_leaf` 预留未启用 | 字段注释显式写"始终 null / 始终 true" | 字段层可复用，但语义需重新定义（父指向"体系"还是"标准"） |
| 标准与机构强绑定 | `cert_iso_standard.cb_code` NOT NULL 语义（FK） | 若标准要作为跨机构公共基础资料，需拆分"标准库"与"机构授权"两层 |
| 条款树无 FK 约束且空表 | DDL 无 FK；数据 0 行 | 分层改造时条款树的完整性校验缺失 |

### 2.3 `cert_cert_stage`（流程九阶段，**未被删除**）

**双重键设计（两版建表语句并存，字段名不同）**：

- 版本 1（`cert_phase_refactor.sql` L70-96，注释 `'认证阶段(全局基础资料, 基于 ISO/IEC 17021-1)'`）：
  `Id`、`Code`(业务编码)、**`StageCode`**(STAGE-01~09)、`StageName`、`SortOrder`、`Category`（**process=流程阶段 / audit=审核类型 / post=证后**）、`Status`(active/inactive)、`Remark` + YZHBaseEntity 审计字段（`OrgCode/Enable/CreateID/Creator/CreateDate/ModifyID/Modifier/ModifyDate/DeleteID/Deleter/DeleteTime`）。
- 版本 2（`restore_standard_directory_and_message.sql` L136+）：字段名为 **`PhaseCode` / `PhaseName`**，`Enable` / `Status` 等。
- 当前视图 `v_cert_stage`（DDL L2550）取的是 **`phase_code` / `phase_name` / `sort_order` / `category` / `status`** 这一套 → 说明线上实际结构偏向版本 2 命名。

```
CREATE ALGORITHM=UNDEFINED VIEW v_cert_stage AS
SELECT s.id, s.code, s.phase_code, s.phase_name, s.description, s.sort_order,
       s.category, cat.DicName AS CategoryName,
       s.status, (CASE s.status WHEN 'active' THEN '启用' WHEN 'inactive' THEN '停用' ...) AS StatusName,
       ...
FROM cert_cert_stage s
LEFT JOIN sys_dictionarylist cat
   ON cat.DicValue = s.category
  AND cat.Dic_ID = (SELECT Dic_ID FROM sys_dictionary WHERE DicNo='stage_category' LIMIT 1)
```

## 三、各阶段产出物设计描述（报告 / NC / 检查表 / 认证决定）

### 3.1 三条引擎与产出物的映射（主干设计）

`核心工作原理-V1.md` 定义三个引擎，产出物与阶段流转如下：

| 引擎 | 章节 | 输入 | 产出物（落表） |
|---|---|---|---|
| 引擎一：文档提取 | §三 | 企业上传文件 | `ent_extraction_result`（B-08，提取字段值），**上传阶段预计算** |
| 引擎二：合规校验 | §四 | 阶段校验规则 `cert_validation_rule`（按 **标准×阶段** 查 active） | `ent_file_compliance_check`(B-07，pass/fail/warning/blocked) → fail 自动生成 **NC** `audit_nonconformity`(C-03)，`source_type='auto_rule'`，`severity` 取 `ValidationRule.severity_if_violated` → 审核员复核确认后落 `audit_finding`(C-04) → 形成 **NC 清单** |
| 引擎三：报告生成 | §五 | 报告模板 `cert_report_template`（按 **机构×标准×阶段** 查） | `rpt_report_section`(D-03) 章节内容 + `rpt_report_section_source`(D-04) 段落溯源（source_type: extraction/finding/nc/compliance/manual/template，含 confidence）→ `rpt_audit_report.full_content`，导出 PDF/Word |

关键设计细节（出处同上）：
- **报告按条款组织**：`rpt_report_section.ClauseCode` → `cert_iso_clause.Code`（概述/结论章节可空），`WorkflowCode` → `wf_workflow_definition.Code`，每章节的生成过程可追溯。
- **报告模板 `section_config` JSON** 示例定义了"一、审核概况 / 二、审核发现 / 7.1 资源 / 三、审核结论"等章节，每项含 `section_name` / `clause_id` / `workflow_id` / `sort_order`。
- **报告内容从已复核字段组装，不重新提取**（避免二次提取偏差）。
- **报告独立原则**：每个标准独立出报告（行业现实：每张证书独立）（审核员端功能设计-V1.md §4.5）。

### 3.2 按"审核类型（阶段）"的产出物（最接近"阶段产出物"的显式设计）

`docs/20-体系认证/04-延展规划/40-领域设计/12-证据溯源与证书全生命周期管理-V1.md` §六（L213-222）给出**唯一一张按审核类型逐行列出产出物的表**：

| 审核类型 | 目的 | 范围 | 人天公式 | **产出物** | 与初审的区别 |
|---|---|---|---|---|---|
| 初审（一阶段） | 评估企业文件体系是否完备 | 全条款文件审查 | 初审人天 × 30% | **一阶段审核报告**（无证书） | 只看文件，不去现场（大部分） |
| 初审（二阶段） | 验证体系运行有效性 | 全条款现场审核 | 初审人天 × 70% | **二阶段审核报告 + 证书** | 全面深度审核 |
| 一监 | 维持证书，查关键条款 | 约 1/3 条款 | 初审人天 × 1/3 | **监督审核报告** | 条款减量，重点关注持续运行与改进 |
| 二监 | 维持证书，查另一批条款 | 约 1/3 条款（与一监错开） | 初审人天 × 1/3 | **监督审核报告** | 互补于一监的条款覆盖 |
| 再认证 | 换发新证，全面复查 | 全条款（可基于历史信任减量） | 初审人天 × 2/3 | **再认证报告 + 新证书** | 略轻于初审，但仍是全面审核 |
| 特殊审核 | 应对变更/投诉/事故 | 仅限变更涉及范围 | 按范围估算 | **特殊审核报告** | 非周期性，触发式 |
| 转机构审核 | 接收从其他机构转入的企业 | 按剩余有效期定 | 按比例折算 | **转机构报告 + 新证书** | 需审查原机构历史审核记录 |

### 3.6 认证决定

- **当前范围明确排除**：`审核员端功能设计-V1.md` 开篇"不做大而全的认证管理系统（**证书管理、审核方案、认证决定等留待后续迭代**）"；同文档多处重申"审核员端**不做认证决定**，NC 与报告独立按标准出具，复核后生效"。
- **流程侧有描述**：`CertPlatform业务流程与数据链路-V2.1.md` 中审核项目含 5 个阶段任务 **T01–T05（申请受理 / 文件评审 / 一阶段 / 二阶段 / 认证决定）**，`PhaseCode` 走字典 `audit_phase` 关联；认证决定作为流程终点存在，未落成独立业务表结构描述。
- **九阶段表中存在该环节**：`cert_cert_stage` STAGE-06 = "认证决定"（category=process）。
- **产出物**：文档未见"认证决定报告/决定书"的落表设计；证书侧由 `12-证据溯源…V1.md` 的 certificates 模型承载（含 `cert_no` 如 `ACM-13485-2024-001`、状态机含 Issued/Expired/Scope Changed/Transferred/Cancelled 等）。

### 3.7 关于"某些阶段不出报告、只出 NC"的核查结论（重要）

**核查动作**：在 `docs/20-体系认证`（82 个 md）全量检索 `不出报告` / `只出NC` 等表述 → **无命中**。
**结论（基于现有文档可证部分）**：

1. **文档中不存在"某阶段只出 NC、不出报告"的显式设计条款**。现有设计是**两条相互独立的链路**：
   - NC 链路：引擎二（合规校验）→ `ent_file_compliance_check` → `audit_nonconformity` → `audit_finding` → NC 清单；
   - 报告链路：引擎三（报告生成）→ `cert_report_template` → `rpt_report_section` → 报告。
   两者**不互为条件**：不生成报告并不影响 NC 产出；反过来报告章节也可引用 NC（`rpt_report_section_source.source_type='nc'`）。
2. **但"阶段之间存在产出物差异"是文档明确承认的事实**（见 §3.2 表）：例如**初审一阶段只出"一阶段审核报告"、不出证书**；特殊审核出特殊审核报告；只有二阶段/再认证/转机构审核才"报告 + 证书"。NC 则未按阶段做差异约定。
3. **支撑"某阶段不出报告"的机制是"配置缺省"而非"显式开关"**：报告由 `cert_report_template`（机构×标准×阶段）驱动，**不给该阶段配置模板 → 该阶段自然无报告**。全库检索未见"阶段是否产出报告 / 是否产出证书"的布尔字段（`cert_phase_definition` 只有 `code/phase_code/phase_name/sequence_order/description/IsValid`）。
4. **因此该设计目前"可实现但未被显式建模"**：判定"某阶段不出报告只出 NC"是否合理，**缺少字段级依据与业务规则条文**，属需用户裁决的设计缺口。可考虑的最小改动是在阶段定义上增加产出物开关（如 `produces_report` / `produces_certificate` / `produces_nc`），再与 §3.2 表逐行对齐校验。
5. 事实参考：ISO/IEC 17021-1 语境下，一阶段审核虽有结论但通常并入"一阶段+二阶段"整体报告体系；本项目的做法是按阶段各出一份报告（§3.2）。
