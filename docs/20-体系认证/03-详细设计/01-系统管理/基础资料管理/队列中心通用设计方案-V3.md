## 一、背景与目标

### 1.1 背景

- 现状：上传确认后 .doc/.xls 异步转换，但用户在"文档提取规则"页看到的是"该文档不支持预览"，无法区分"正在转换"与"真的不支持"。
- 痛点：几十个审核员可能同时上传；同一机构/标准/阶段下多批上传 + 多个转换任务叠加，目录结构随时被增删改，任务与数据不一致。
- 未来：自动核验、报告生成都是长任务，执行期间不允许用户改文件（如生成报告时用户改了源文件）。必须有一个统一、可靠的队列底座 + 清晰的进度/状态呈现 + 完整的结果通知。

### 1.2 目标

1. **统一**：一套主表/子表/资源锁、一套状态机、一套执行引擎、一套监控页面，覆盖所有后台队列。
2. **互斥**：队列运行期间，其涉及资源被锁定；新上传批次在同一范围被拒绝。
3. **透明**：审核员/操作员随时知道"后台正在执行什么、多少子任务、完成多少、失败多少、什么时候开始/结束"。
4. **必达通知**：任务完成/失败，任何页面实时置顶弹窗；即使当时不在线/关了页面，下次进入第一时间看到未读提醒，消息记录完整可查。
5. **可恢复**：失败可重试（单任务/整队），卡死可回收，取消可终止，杜绝"任务永远 pending/processing"。

## 二、核心概念

| 概念 | 说明 | 例子 |
|------|------|------|
| 队列（Queue） | 一次业务动作 = 一个队列实例，对应**主表一行** | "上传批次 #abc 的 12 个 doc/xls 转换" |
| 任务（Task） | 队列下的一个最小可执行单元，对应**子表一行** | "附录一.doc → .docx" |
| 资源锁（Resource Lock） | 队列对具体资源的占用标记 | "cert_standard_directory_file / FL-xxx" |
| 队列类型（queue_type） | 区分不同业务 | `file_convert` / `auto_verify` / `report_generate` |
| scope_key | 按类型约定格式的范围键，用于同类型范围互斥与筛选 | `CB001\|ISO134852016\|STAGE05` |
| Handler | 每种队列类型的执行实现 | 转换 Handler、核验 Handler、报告 Handler |

## 三、逻辑设计

### 3.1 数据模型（三张表）—— 最终落地为 yzh_ 框架级表

> **V3.3 落地说明**：按用户要求，队列中心整体提取为 yzh 核心框架（后端 `YZH-Framework/YZH.Core/Queue`，前端 `src/yzh/views/QueueMonitor` + `useYzhQueue`），表名统一 `yzh_` 前缀、snake_case 列、`code`(GUID) + 审计字段 + `org_code`，与项目业务表（cert_ 前缀）严格区分。DDL 见 `DB/mysql/phase5_queue_yzh.sql`（含数据迁移与删旧表）。

#### 3.1.1 主表 `yzh_queue`（队列主表）—— 通用，不含业务列

```sql
CREATE TABLE yzh_queue (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  code          VARCHAR(36)  NOT NULL COMMENT '全局唯一编码(GUID)，表间关联用',
  queue_code    VARCHAR(64)  NOT NULL COMMENT '队列编码：Q-{yyyyMMdd}-{6位随机}（短、唯一、人读）',
  queue_type    VARCHAR(30)  NOT NULL COMMENT '队列类型：file_convert/auto_verify/report_generate',
  queue_name    VARCHAR(200) NULL     COMMENT '队列名称（人话）：文档转换-12个文件',
  -- 范围键（按类型约定格式，供范围互斥与筛选；业务维度不枚举列）
  scope_key     VARCHAR(200) NULL     COMMENT '按类型规则拼接，如 file_convert=机构|标准|阶段',
  scope_info    JSON         NULL     COMMENT '冗余展示数据：{orgCode,orgName,standardCode,phaseCode,directoryCode,...}',
  -- 来源（防重复入队：同一来源只能建一次队列）
  source_type   VARCHAR(30)  NULL COMMENT '来源：upload_task/verify_req/report_req',
  source_id     VARCHAR(64)  NULL COMMENT '来源ID：上传任务taskId等',
  -- 状态与进度
  status        VARCHAR(20)  NOT NULL DEFAULT 'pending' COMMENT 'pending/running/completed/failed/cancelled',
  total_count   INT DEFAULT 0,
  pending_count INT DEFAULT 0,
  processing_count INT DEFAULT 0,
  completed_count  INT DEFAULT 0,
  failed_count     INT DEFAULT 0,
  cancelled_count  INT DEFAULT 0,
  progress      INT DEFAULT 0 COMMENT '0-100',
  start_time    DATETIME NULL,
  end_time      DATETIME NULL,
  remark        VARCHAR(500) NULL,
  org_code      VARCHAR(50)  NULL COMMENT '机构编码（多租户）',
  create_id     INT NULL, creator VARCHAR(50) NULL, create_date DATETIME DEFAULT CURRENT_TIMESTAMP,
  modify_id     INT NULL, modifier VARCHAR(50) NULL, modify_date DATETIME NULL,
  delete_id     INT NULL, deleter VARCHAR(50) NULL, delete_time DATETIME NULL,
  UNIQUE KEY uk_code (code),
  UNIQUE KEY uk_queue_code (queue_code),
  UNIQUE KEY uk_source (source_type, source_id),        -- 防重复入队（上传确认被重试时不会建两个队列）
  KEY idx_scope_status (queue_type, scope_key, status),
  KEY idx_status (status),
  KEY idx_create_date (create_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='yzh队列主表（通用队列中心）';
```

设计要点：
- **不枚举业务列**（用户提议）：机构/标准/阶段等维度放 `scope_key` + `scope_info`，各业务页面按 `queue_type` 约定自行生成/解析。
- `uk_source (source_type, source_id)`：**防重复入队**。上传确认接口被网络重试/重复点击时，第二次 INSERT 撞唯一键 → 返回已有队列，而不是建出两个队列（成熟实践：幂等入队）。
- `idx_scope`：范围互斥查询走索引等值匹配。
- 进度计数冗余在主表，列表/页面查询无需实时聚合子表。

#### 3.1.3 资源锁定表 `yzh_queue_resource_lock` —— 用户提议，采纳并调整

```sql
CREATE TABLE yzh_queue_resource_lock (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  code          VARCHAR(36)  NOT NULL COMMENT '全局唯一编码(GUID)，子任务 lock_codes 引用',
  queue_code    VARCHAR(64)  NOT NULL COMMENT '所属队列',
  resource_table VARCHAR(50) NOT NULL COMMENT '资源表名：cert_standard_directory_file / cert_standard_directory_folder / cert_standard_directory / cert_report ...',
  resource_code VARCHAR(200) NOT NULL COMMENT '资源唯一编码（各表 Code/FileCode/FolderCode/DirectoryCode）',
  resource_name VARCHAR(200) NULL COMMENT '资源名称快照（锁定时记录，显示用）',
  task_no       INT NULL COMMENT '占用该资源的子任务序号（NULL=队列级锁，如目录锁）',
  status        VARCHAR(20) DEFAULT 'locked' COMMENT 'locked/released',
  active_key    VARCHAR(260) NULL COMMENT '活跃锁键:{resource_table}|{resource_code}，释放时置NULL；uk_active唯一索引实现同一资源同时仅一个活跃锁',
  create_time   DATETIME DEFAULT CURRENT_TIMESTAMP,
  release_time  DATETIME NULL,
  expire_at     DATETIME NULL COMMENT '锁租约安全网：回收任务扫描超时锁强制释放（与终态批量释放双保险）',
  org_code      VARCHAR(50) NULL,
  create_id     INT NULL, creator VARCHAR(50) NULL, create_date DATETIME DEFAULT CURRENT_TIMESTAMP,
  modify_id     INT NULL, modifier VARCHAR(50) NULL, modify_date DATETIME NULL,
  delete_id     INT NULL, deleter VARCHAR(50) NULL, delete_time DATETIME NULL,
  UNIQUE KEY uk_code (code),
  UNIQUE KEY uk_active (active_key),              -- 同一资源同时仅一个活跃锁（INSERT 撞冲突即被其它队列持有）
  KEY idx_queue (queue_code, status),
  KEY idx_locked (resource_table, resource_code, status),
  KEY idx_expire (status, expire_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='yzh队列资源锁定表';
```

> **对用户提议的 3 处调整**：
> 1. **子任务完成 → `status` 置 `released`（带 release_time），不物理删除**：保留审计，队列详情可展示"持有/已释放锁"。
> 2. **队列进入终态（完成/失败/取消/崩溃回收）→ 批量释放该队列全部锁（一条 UPDATE）**：防止取消/崩溃的队列永久锁死资源 —— 最容易埋的死锁坑，必须兜底。
> 3. **锁集 = 目录（队列级，task_no=NULL）+ 每个待处理文件（任务级）+ 涉及文件夹**：只锁文件不够，文件夹重命名会改路径影响转换；页面操作资源时查"自身 + 祖先链"（见 §3.3）。

**锁的生命周期**：

```
队列创建（事务内）：
  ① 批量 INSERT 资源锁（目录 1 条 + 每文件 1 条 + 涉及文件夹若干条，status=locked）
  ② 任一 INSERT 撞唯一键 (resource_table, resource_code, status) → 该资源已被别的队列持有
     → 回滚，返回："资源「xxx」正被队列 Q-yyy（类型）处理中，请稍后操作"
  ③ 插入主表（含 uk_source 防重复）+ 子表（子表 lock_codes 记录任务持有的锁编码）

子任务完成：UPDATE cert_queue_resource_lock SET status='released', release_time=NOW()
            WHERE code IN (task.lock_codes)     -- 用户提议"每完成一个子任务释放对应锁"

队列终态：  UPDATE cert_queue_resource_lock SET status='released', release_time=NOW()
            WHERE queue_code=? AND status='locked'   -- 批量释放兜底（含取消/失败/回收）
```

### 3.2 状态机

**主表状态**：

```
                    ┌─────────┐
   创建 ───────────▶│ pending │──领取到执行资源──▶┌─────────┐
                    └─────────┘                   │ running │
                    （排队中，等待并发额度）          └────┬────┘
                                                       │
                    ┌───────────────────────────────────┤
                    ▼                ▼                  ▼
              ┌────────┐      ┌────────┐         ┌────────┐
              │completed│      │ failed │         │cancelled│
              └────────┘      └────────┘         └────────┘
```

- `running`：有任一子任务 pending/processing。
- `completed`：所有子任务均 completed。
- `failed`：子任务全部结束、且存在 failed（含重试耗尽）。
- `cancelled`：全部被取消。
- （暂停/恢复已砍，V3.3 简化。）

**子任务状态**：`pending → processing → completed / failed / cancelled`，failed 可自动重试（retryable 且 `retry_count < max_retry_count`）或手动重试（回 pending）。

**主表状态由子表汇总**（`RefreshQueueProgress`）：每次子任务状态变更后重算计数 + 进度 + 主表状态，一次事务内完成；进入终态时同步批量释放资源锁，并触发终态通知（§3.7）。

### 3.3 双控制面：资源锁 + 范围互斥

| 控制面 | 机制 | 管什么 | 冲突文案 |
|--------|------|--------|---------|
| 资源锁（细粒度、跨类型） | `yzh_queue_resource_lock` + 祖先链检查 | 已有资源的增删改/替换/移动 | "资源「xxx」正被队列 Q-yyy（类型）处理中，请稍后操作" |
| 范围互斥（同类型内） | `queue_type + scope_key` 非终态查询 | 新上传批次（资源还不存在，锁表管不到"未来资源"） | "该机构/标准/阶段下已有队列 Q-yyy（类型）正在执行，请等待完成后再上传" |

- 锁表管"具体资源"，scope_key 管"新上传"，职责不同、缺一不可。
- 资源锁天然支持**跨类型冲突**：报告队列要锁的文件已被转换队列锁着 → 创建报告队列即被拒。

#### 3.3.1 资源锁检查（页面操作前）

- 页面要对某个资源操作时，调用统一查询：`yzh_queue_resource_lock` 中 `resource_table=? AND resource_code IN (自身 + 祖先链编码) AND status='locked'`。
- 祖先链：文件夹沿 `ParentCode` 向上走到目录（`cert_standard_directory`）。

操作拦截清单（命中即拒绝）：

| 操作 | 检查的资源 |
|------|-----------|
| 重命名/删除文件夹 | 该文件夹 + 祖先链 |
| 新建子文件夹（在锁定目录下） | 父文件夹 + 祖先链 |
| 重命名/删除/替换文件 | 该文件 + 祖先链 |
| 新建文件（在锁定目录下） | 父文件夹 + 祖先链 |
| 上传新批次 | 范围互斥（scope_key），见下 |

#### 3.3.2 范围互斥（新上传拦截）

- 上传发起（upload-init）与确认（upload-confirm）时查询：`yzh_queue` 中 `queue_type='file_convert' AND scope_key=? AND status IN ('pending','running')`（走 `idx_scope_status` 索引）。
- 命中 → 拒绝："该机构/标准/阶段下已有队列 Q-yyy 正在执行"。
- scope_key 生成规则（file_convert 约定）：`{orgCode}|{standardCode}|{phaseCode}`，由**业务页面/服务按类型规则生成**，主表不感知字段含义。

#### 3.3.3 为什么业务信息不进 queue_code

用户提议把 `机构｜标准｜阶段｜日期` 编进队列编码。原则（主表通用、页面自解析）采纳，机制调整为 `scope_key` 列：

1. **查询性能**："该范围有没有 running 队列"是最高频查询（每次上传/目录操作）。拼字符串进编码 → LIKE/全表扫；`scope_key` 列 + 索引 → 等值匹配。
2. **编码脆弱**：现有编码体系中 `|` 已是分隔符（FileCode=`FL-FD-SDC-ISO134852016|STAGE05|L02|S001|文件名`），再拼一层分隔符解析易错位。
3. **可读性**：queue_code 既要唯一又要人读，嵌业务信息后监控页/消息中又长又乱。
4. **结论**：`queue_code` 保持短唯一码，业务维度放 `scope_key` + `scope_info`，**同样满足"页面按类型规则控制"**，且查询快、零解析风险。

### 3.4 执行引擎（Worker）—— 租约 + 幂等 + 错误分类

```
QueueHostedService（BackgroundService）
   │ 每 3s 轮询
   ▼
QueueManager.GetNextPendingTask()
   -- 领取条件：status='pending' AND next_retry_at <= NOW() AND retry_count < max_retry_count
   -- 用 FOR UPDATE SKIP LOCKED 防重复领取
   ▼ 领取即租约：status='processing', locked_until=NOW()+租约(5分钟), worker_id=本Worker
   ▼ 按 task.queue_code 查主表 → 校验 scope 锁仍有效（文件未被删/替换）→ 失效则置 failed(permanent)
   ▼
SemaphoreSlim 全局并发额度（默认 5，可从系统参数调整）
   │
   ▼ 按 queue_type 分发
IFileConvertHandler（LibreOffice/NPOI）  IVerifyHandler（未来）  IReportHandler（未来）
   │ 执行中定期续期 locked_until（防长任务被误回收）
   ▼ 每个任务：CancellationToken 超时（默认 300s）
   ▼ 完成 → 释放本任务资源锁 → RefreshQueueProgress → 终态通知
```

**租约与卡死回收（调研吸收）**：
- 任务被领取时写 `locked_until`，Worker 正常执行中定期续期（如每 60s 续到 now+5min）。
- 回收扫描：`status='processing' AND locked_until < NOW()` 的任务视为 Worker 已死 → 重新置回 pending（`retry_count+1`）或按错误分类置 failed，同时释放其锁。
- 进程重启/崩溃后任务最多"消失"一个租约周期（5 分钟），不会永久卡死。

**幂等执行（调研吸收，必须）**：
- 接受"至少一次投递"：网络抖动/Worker 崩溃后同一任务可能执行两次，处理必须幂等。
- 文件转换天然幂等：目标路径确定、重复转换覆盖同一 MinIO 对象。**执行前检查目标已存在且来源未变 → 直接成功，不再转换**。
- 未来报告生成等写结果类任务：结果写回时带 `worker_id` 校验（fencing token 轻量版），防止"迟到的旧 Worker 覆盖新结果"。

**错误分类（调研吸收）**：
- `permanent`：文件不存在、格式非法、校验失败 —— 重试无意义，立即 failed 进终态（等价死信队列，不堵主队列）。
- `retryable`：LibreOffice 超时、MinIO 抖动、临时资源不足 —— 退避重试。
- 分类由各 Handler 抛出错误时声明（转换 Handler 统一归类：超时=retryable，缺文件/非法格式=permanent）。

**执行前有效性校验**：执行前校验 `ref_id` 指向的文件仍存在且未被替换（比对 storage path / convert status / update date）。文件已被删/替换 → 子任务置 failed(permanent)，错误信息"文件已被修改或删除，请确认后重新执行"，避免静默错乱。

### 3.5 失败重试与整队重跑

| 场景 | 行为 |
|------|------|
| 单任务失败（retryable） | `next_retry_at = now + 指数退避 + 抖动`（5s→15s→45s→120s，上限 5 分钟），到期才可再次领取 |
| 单任务失败（permanent） | 不重试，立即 failed |
| 单任务手动重试 | 监控页明细行"重试"：failed/cancelled → pending（重置 retry_count、next_retry_at=NOW、重新加锁），主表回 running |
| 整队重跑 | 监控页主表"重试"：所有 failed/cancelled 子任务 → pending（重新加锁） |
| 转换失败（重试耗尽） | 文件恢复有效 + ConvertStatus=failed，提取页可见标红，可下载原文件、可重新转换 |

### 3.6 取消

- **取消**（必须项）：终止所有 processing 子任务（取消 CancellationToken、杀 LibreOffice 进程）→ 未处理子任务置 cancelled → **批量释放全部资源锁** → 主表 cancelled + end_time → 终态通知。
- 取消入口：监控页主表/详情"取消"按钮 + 上传确认冲突时的自动放弃；二次确认弹窗。

### 3.8 文件状态联动（解决"不支持"误导）

| 阶段 | 文件 ConvertStatus | 文件 IsValid | 提取规则页表现 |
|------|-------------------|--------------|----------------|
| 上传确认入队 | pending | **false（置为无效）** | 不显示（天然隐藏，杜绝误操作） |
| 转换中 | converting | false | 不显示 |
| 转换成功 | converted | **true（恢复）** | 显示，正常预览 .docx/.xlsx |
| 转换失败（重试耗尽） | failed | **true（恢复）** | 显示 + 红色"转换失败"徽标，可下载原文件、可重新转换 |
| 队列取消 | cancelled | true（恢复） | 显示 + "未转换"提示，可重新转换 |

配套：
- **DocPreview 兜底**：`ConvertStatus=pending/converting` 显示"文件正在队列处理中，转换完成后即可预览"；`failed` 显示失败原因 + 下载原文件；只有"确实不支持且未入队"的格式才显示"不支持"。
- **安全防护（必须）**：`CleanupOrphanData` 与 `UploadCancel` 必须跳过 `ConvertStatus in (pending, converting)` 的文件，否则会把队列中文件当脏数据清掉。
- **完成后自动刷新**：提取规则页监听 `cert-queue-progress`，队列完成时刷新文件树。

### 3.9 目录操作保护

资源锁 + 祖先链是主防线（§3.3.1）。补充两道保险：
1. **执行前校验**：Worker 领取后校验资源仍有效（§3.4）。
2. **删除/重命名二次校验**：`FolderFileManager` 删除/重命名时也查资源锁，存在则拒绝（双保险）。

### 3.11 与成熟队列体系的对照（调研吸收点汇总）

| 成熟实践（Hangfire/SQS/DB-as-queue） | 本方案对应 | 结论 |
|--------------------------------------|-----------|------|
| DB 持久化任务队列 | MySQL 三表 + Worker 轮询领取 | ✅ 一致（单实例规模足够，不引入 Redis/Kafka） |
| 至少一次投递 + 幂等处理 | §3.4 幂等执行原则 | ✅ 补上 |
| 可见性超时/领取租约 | `locked_until` 租约 + 回收 | ✅ 补上（替代永久 processing + 手动扫描） |
| 退避重试 + 抖动 | `next_retry_at` 指数退避 | ✅ 补上 |
| 死信队列（DLQ） | failed 终态 + permanent 错误分类 | ✅ 等价（坏任务不堵主队列） |
| 重试/取消/Dashboard | 监控页 + 重试/取消按钮 | ✅ 一致 |
| 幂等入队 | `uk_source` 唯一键 | ✅ 补上 |
| 分布式锁防泄漏 | 终态批量释放 + expire_at 安全网 | ✅ 补上 |
| 事务性出站（outbox） | 队列+锁与业务变更同事务创建 | ✅ 一致（已要求） |
| 历史数据清理 | 留存策略（D13） | ✅ 补上 |

## 九、风险与边界

| 风险 | 说明 | 对策 |
|------|------|------|
| 锁泄漏（取消/崩溃后资源永久锁死） | 队列非正常结束时只释放了部分锁 | 终态批量释放 + expire_at 安全网 + 租约回收 |
| 多实例部署 | 锁依赖单库唯一约束 | 单机足够；多机时锁表仍可用，队列领取需分布式锁（接口已抽象） |
| 大文件/慢转换 | 超时、内存、磁盘 | 单任务超时 + 最大重试 + 并发限制 |
| 进程重启卡死任务 | processing 永久占用 | 租约回收（必须实现项） |
| 锁误伤（范围过宽） | 目录级锁阻塞整阶段操作 | D9 可后续放宽；状态透明（监控页可看锁列表） |
| 文件在队列中被外部改 | 转换结果错乱 | 目录锁 + 祖先链 + 执行前有效性校验 + 明确报错 |
| 表膨胀（队列/锁/子表历史） | 长期运行后历史数据拖慢查询 | 留存策略定期归档（D13） |
| scope_key 格式漂移 | 不同类型格式不一致导致解析错误 | 格式按类型约定并文档化；scope_info JSON 兜底展示 |

## 十、一句话总结

**三张表（主表 + 子表 + 资源锁）、两个控制面（细粒度资源锁管已有资源、scope_key 范围互斥管新上传）、三层通知（实时置顶弹窗 + 未读补漏 + 完整消息记录）**：队列运行期间锁死其涉及资源，文件在队列中隐藏并明示状态，完成后自动恢复；完成/失败必达通知，失败可重试、卡死可回收、取消可终止 —— 这个底座同时支撑文件转换、自动核验、报告生成，且每一步状态对审核员透明。
