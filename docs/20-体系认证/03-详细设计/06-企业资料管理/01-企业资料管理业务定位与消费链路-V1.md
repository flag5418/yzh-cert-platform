## 一、模块定位（纠偏后的权威表述）

**本模块服务的企业状态**：企业已经按体系认证的要求，把材料**整理成标准格式的文档**（成册文件、清单表格，命名基本规整）。平台不需要替企业"整理资料"，需要的是：

```
把这家企业的这套材料收进来 → 知道齐不齐 → 把内容提取成数据 → 让 NC 规则和报告规则去用
```

四步对应四个能力：**采集归档 / 完整性检查（FileCheck）/ 定向提取 / 供下游消费**。

**用图书馆比喻**：企业交来的是**已经按索书号排好的书**，本模块是**入库、编目、检查缺藏、把书里数据录入索引台**的图书馆系统——不是"帮企业把散书整理成套"的装订车间（那是下一步的规范化）。

## 二、和「企业资料规范化」的分界（必须先钉死）

| 判据 | 企业资料管理（本模块，本期） | 企业资料规范化（05 册，下一步） |
|------|------------------------------|--------------------------------|
| 输入 | 企业**已备好**的标准格式材料 | 企业**散乱**原始资料 |
| 核心动作 | 采集、归档、检查、提取、喂数 | 画像、匹配、人工裁决、填充 |
| 谁定义"有什么文件" | 管理端「标准目录管理」模板行 | 同左（共用模板行做靶子） |
| 产出 | 企业行文件 + B-08/B-09 提取数据 | **填好的标准文档实例**（最终也汇入企业行+提取数据） |
| 是否用匹配引擎（04 号册） | ❌ 不用（材料已对号入座，至多按文件名轻量推荐归位） | ✅ 三阶段匹配是其核心 |
| 是否用画像链（D3） | ❌ 不用（定向链即可） | ✅ 画像→定向双链 |

**两线唯一共享的底座** = D11 统一表架构（`cert_standard_directory_config/file` 的模板行/企业行 + `StandardFileCode` 枢纽）。共享存储 ≠ 共享流程——实现时严禁把匹配/裁决逻辑塞进本模块页面与服务。

**演进关系**：规范化上线后，其产物（填好的标准文档）进入本模块的企业行容器，后续提取、版本、NC/报告消费链**完全复用**，下游无感。这就是"下一步"能接上的原因，也是本期必须先把容器和提取做扎实的原因。

## 三、消费链路全景（资料 → 提取 → NC → 报告）

```
[1]采集           [2]机读化            [3]提取              [4]判定              [5]产出
上传/确认    →   file_convert 队列 →  定向提取规则    →   工作流执行        →  NC 检查报告
(企业行落库)     (PDF + Markdown)     (B-08/B-09 按        (NC 规则 A-10 校验    体系认证报告
                                       EnterpriseCode     企业提取值)           (章节从 B-08
                                       ×FileCode 隔离)                                      取数)
```

## 八、缺失判定依据链与多标准上传规则（2026-09-28 用户澄清，权威口径）

### 8.1 三元组从哪来（上下文推定，零手工输入）

| 维度 | 来源 |
|------|------|
| `OrgCode` | **专家注册即绑定唯一机构**（一专家一机构），专家登录态天然持有机构 Code |
| `EnterpriseCode` | 页面左侧企业树选中的企业 |
| `StageCode` | 选中的阶段（企业-阶段关联） |
| `StandardCode` | 该阶段关联的标准集合（单标准=唯一定位；多标准=逐个 Tab 切换） |

### 8.2 缺失判定的依据链

```
(OrgCode, StandardCode, StageCode) ──唯一定位──▶ 标准目录模板（uk 恰为这三列）
        │ 关联建立时复制（13号 E7，Phase E-5 改钩子）
        ▼
企业清单行（EnterpriseCode=真实企业，每文件一"槽位"）
        │ FileCheck 逐槽位对账
        ▼
缺失 = IsRequired 且 StoragePath 为空的槽位；部分覆盖 = 有文件但 ExtractStatus ≠ completed
```

企业侧永远不需要"知道标准目录长什么样"——结构由平台按三元组自动复制、自动对账。

### 8.3 多标准上传规则（2026-09-28 二次澄清定稿：双入口 + Tab 布局）

**页面布局裁决：标准 Tab 页**（每个关联标准一个 Tab，Tab 内含该标准全部操作与目录分组展示）。卡片式布局否决——每标准目录多、操作多，卡片不直观不利操作。

**双入口模型**：

| 入口 | 位置 | 行为 | 与 P11 的关系 |
|------|------|------|---------------|
| **阶段级统一上传**（跨标准批量） | 右侧顶部全局操作栏 | 拖入混合文件夹 → 系统对**每个关联标准**的缺失槽位分别匹配推荐 → 人工逐条确认归属（一文件可多标准勾选）→ 确认后**按标准拆分落库** | 是 P11 的**前置分发器**：落库动作仍逐标准独立，规则不破 |
| **标准级补充上传** | 各 Tab 内 | **先选目标文件夹、再选文件**（P15 裁决）：对话框第一步选定当前标准目录内的目标文件夹，第二步多选文件直传该文件夹；**作用域天然限定在当前标准**，不存在跨标准误传；若所选文件名命中其他标准的槽位，仅提示不断言归属 | P11 原始形态的交互具化 |

核心不变式（P11 沿用）：一份文件 3 个标准都要求 = 3 个标准下**各存一份、各自提取**（分发复制语义，非去重引用）；提取按 StandardFileCode 逐标准各跑一遍（同内容不同契约，提示词不同，天然不浪费）。

**13 号 §3.3 的改判范围（缩小）**：「批量上传（多标准）+ 自动推荐映射」设计**保留**（对应统一入口），不作废；须改的仅是 `SuggestMappingsAsync`（`EnterpriseFileService.cs:319-336`）——从跨标准单 best-match 改为**按标准分组的完整候选列表**（含每个候选槽位、命中/未命中标记），供逐条确认；前端补多标准勾选确认交互。

**版本联动说明**：多标准下同一文件是独立行、独立版本链；某标准下替换**不自动同步**其他标准（页面提示"该文件同时存在于其他 N 个标准，是否一并更新"，由人确认——跨标准版本一致性不做隐式保证）。

### 8.4 虚拟企业复用设计的安全收口（2026-09-28 评估结论）

复用 `cert_standard_directory_config/file` + 虚拟企业 `YZH-STD-ENT` 的架构**判定合理**（同一模型、两个实例域：模板=规格，企业行=订单；FileCheck 单表自比对、规范化产物有天然容器）。MinIO 结构（库前缀对称 / `_archive` 版本 / 产物派生段）**判定合理**。但三项隐患必须在实施前收口：

| # | 隐患 | 现状证据 | 收口动作 |
|---|------|----------|----------|
| A-1 | 魔法常量无锚点 | **Q1 裁决（2026-09-28）：不建虚拟企业行**。实测 `cert_enterprise` 已带 `OrgCode`（`Enterprise.cs:30`，uk 均含机构列），且专家端建档已由后端 `OnBuildingFilter` 强制 `OrgCode=登录用户工作区`（`pages/enterprises/logic.ts:8`） | 机构维度**从企业行 OrgCode + 专家登录态直取**，无需任何虚拟企业种子；`YZH-STD-ENT` 仅作为 config/file 模板行的 `EnterpriseCode` 标记值存在，收敛为单一常量 |
