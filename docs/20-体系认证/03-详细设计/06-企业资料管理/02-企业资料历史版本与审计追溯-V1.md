## 一、为什么认证平台必须管版本（业务根据）

认证是**有法律效力的判定活动**：报告里引用的每一个数值，评审组、认可机构、监管在若干年后都可能要求回溯——"当时依据的是哪份文件、哪个版本、文件长什么样"。因此版本管理不是工程洁癖，而是认可规则（ISO/IEC 17021 记录保留要求）下的**可追溯义务**。落到本平台的三条硬要求：

| 要求 | 含义 | 对应设计 |
|------|------|----------|
| R-1 可回溯 | 任一时点的报告数值能定位到当时的原始文件内容 | 版本表 + 提取结果带版本（§四、§五） |
| R-2 不丢证据 | 删除/替换是"处置"，不是"毁灭" | 删除只软删 + MinIO 对象**不得物理删除**（§六） |
| R-3 有人负责 | 每次处置有据可查（谁/何时/为什么） | 操作留痕表 + `Reason` 必填（§六） |

## 二、版本模型（单一权威定义）

```
逻辑锚点：StandardDirectoryFile 企业行的 Code（FileCode，GUID，永不变）
           │
           ├─ 当前版本 = 该行本身（StoragePath / FileName / FileSize / VersionNumber）
           │
           └─ 历史版本 = cert_enterprise_file_version 行（每个被替换下来的版本一条）
                物理归档 = _archive/{原文件名}.v{n}（源文件与 PDF/MD 产物同算法）
```

| 规则 | 定义 | 现状 |
|------|------|------|
| V-1 锚点不变 | 前后端传参、提取结果外键、审计引用一律用 `FileCode`；替换/改名不产生新行（符合双关键字准则 A） | ✅ 符合（`EnterpriseFileService.cs:239-276`） |
| V-2 版本号 | 首次上传=1；每次替换 `GetNextVersionNumberAsync` 递增；**删除不递增**；恢复=一次新版本（单调向前，不做回拨，见 §五-3） | ⚠️ 首次上传未写 VersionNumber（`EnterpriseFileService.cs:203-209`）、替换未更新该列（:266-275）→ 见下方「版本号口径」 |
| V-3 归档命名 | `_archive/{name}.v{n}`，禁止二次归档（抛异常即状态机 bug） | ⚠️ **13 号文档写 `History/` 与实际代码 `_archive/` 不一致 → 以 `PathBuilder.Archive`（:124-156）为准，13 号需勘误** |
| V-4 产物同版本 | 源文件、预览 PDF、Markdown 三者一起归档，共享同一 `v{n}` 后缀 | ✅ 同算法（`PathBuilder.cs:127-133`） |

### 版本号口径（2026-09-28 钉死，修复实现前必须先立此规）

1. **每个文件槽位（企业行 `Code`）各自从 1 起**，跨标准互不影响（独立版本链，联动替换须人工确认，见 01 号 §8.3）；
2. **替换时旧内容按它自己的版本号归档**：`_archive/{name}.v{n}` 中 `n` = 被替换掉的当前版本号（= `GetNextVersionNumberAsync` 返回值），随后当前行 `VersionNumber` 置 `n+1` —— 不存在"v2 内容归档成 .v1"的错位；
3. **当前行 `VersionNumber` 必须显式落库**：`ConfirmUploadAsync`（:203-209）补写 `=1`；`ReplaceFileAsync`（:266-275）更新列表补 `nameof(VersionNumber)` —— 否则 B-08 四元组 `(FileCode, VersionNumber)` 无对账基准；
4. **B-08/B-09 的 `VersionNumber` = 提取所依据的文件版本号**（不是恒写 1，呼应 §三 G-1）。

> ⚠️ **实现注意（名实不符）**：`GetNextVersionNumberAsync`（`EnterpriseFileService.cs:349-355`）返回的是**被归档内容的版本号**（无历史时 = 1，即首个被替换掉的 v1），不是"新版本号"。修复时应重命名为 `GetArchivedVersionNumberAsync`，新当前版本号 = 其返回值 + 1。

## 三、缺口盘点（版本链路断在哪，证据到行）

| # | 缺口 | 证据 | 严重度 |
|---|------|------|--------|
| G-1 | **B-08/B-09 无版本留存**：提取落库时物理删除全部旧结果（`Deleteable :303-308`），`VersionNumber` 恒写死 1（:327,:358）；且唯一键 `UniqueField(FileCode, EnterpriseCode, FieldCode/TableIndex)` **不含版本列**（`ExtractionResult.cs:37-38`、`TableExtractionResult.cs:37-38`）→ 表结构本身不容许多版本共存 | 报告引用的旧数值在下次提取后**永久丢失**，R-1 不成立 | 🔴 核心断点 |
| G-2 | **删除物理销毁证据**：`DeleteFileAsync` 直接 `_storage.DeleteAsync` 删 MinIO 对象（:286-288） | 违反 R-2 | 🔴 |
| G-3 | **归档失败静默吞**：Replace 中归档 catch 后仅 LogWarning 继续（:247-248），旧文件可能滞留原路径，与新文件形成"双当前" | 数据不一致，且无绊线 | 🟡 |
| G-4 | **操作留痕几乎为零**：除版本表行的 `CreateBy/CreateTime` 外，上传/删除/触发提取无任何记录；13 号设计的 `/History` 端点未实现，`GetVersions` 只查版本表 | 违反 R-3 | 🟡 |
| G-5 | **并发无约束**：Replace 读-改-写无锁，两审核员同时替换同一文件会后写覆盖前写且只归档一份 | 低频但破坏 R-1 | 🟢（登记即可） |
| G-6 | **列语义债**：B-08/B-09 的 `EnterpriseCode` 属性映射到 DB `OrgCode` 列（`ExtractionResult.cs:22-23`），而 13 号新增列均为 `EnterpriseCode` —— 同域两义 | 真企业数据接入前不清算，后续查询必踩 | 🟡 |

## 四、提取结果的版本化方案（对 G-1 的裁决建议）

两个路线：

| 路线 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **甲：B-08 自带版本** | 唯一键扩为 `(FileCode, EnterpriseCode, FieldCode, VersionNumber)`；落库不再物理删除旧行，改为 `IsValid=0` 归档旧版本 + 插入新版本行；`VersionNumber` 写真实值 | 报告溯源单表单查；与文件版本天然对齐 | 改唯一键 + 改 `SyncExtractionResultToB08B09Async` 删除逻辑；数据量随版本线性增长（可控：单文件字段数 × 替换次数） |
| 乙：快照独立表 | B-08 只存当前值，新增 `cert_extraction_result_snapshot` 供审计回查 | 不动现有表 | 双表同步复杂度 + 报告溯源要跨表拼，**违背"单点权威"** |

**建议：甲路线**。理由：`VersionNumber` 列和字段早已预留（说明原始设计意图就是甲）；报告溯源（D-04 `rpt_report_section_source`）未来只需携带 `(FileCode, VersionNumber)` 二元组即可定位历史证据，链路最短。

配套规则：

1. **重算语义**：文件替换后 `ExtractStatus=none`（现状 :270 ✅），新版本提取完成时按上述方式归档旧行；
2. **人工编辑保护**：`IsManualEdited=1` 的行**不被自动重算覆盖**，只生成新版本行并存，页面展示最新版并标注人工修订痕迹（呼应 01 号 P9：下游不得直接改 B-08）；
3. **消费端取数**：`GetFieldSkill`/`docField` 节点默认取 `(FileCode, MAX(VersionNumber))` 且 `IsValid=1`；报告章节若引用了特定版本，D-04 源表须存版本号（延后到 D-03/D-04 实施时定，此处只登记接口）。

## 五、替换 / 删除 / 恢复 操作语义（对 G-2/G-3/G-5 的方案）

### 1. 替换（Replace）——修正时序，消除"双当前"

现行顺序（归档→上传→改库）的风险：归档失败仍继续。改为**先落新、后归旧、库最后**，且归档失败即中止：

```
① 上传新文件到最终路径（PathBuilder.EnterpriseFile）
② MoveObject 旧文件/PDF/MD → _archive/*.v{n}（PathBuilder.Archive；失败→ 删除①的新对象，整体报错）
③ 事务内：插版本表行 + 更新企业行（StoragePath/FileName/FileSize/VersionNumber=n+1/ConvertStatus=pending/ExtractStatus=none）
④ 入 file_convert 队列
```

并发（G-5）：企业行更新走**乐观锁**（BaseEntity `LastModifyTime` 比对，冲突则提示"文件刚被他人更新，请刷新"）。

### 2. 删除（Delete）——处置而非毁灭

- **去掉 `_storage.DeleteAsync` 物理删除**（:287）：MinIO 对象原地保留，仅软删 DB 行（`IsValid=0` + `IsDeleted`）；
- 被删文件如从未替换过，无版本表行 → 删除动作本身由操作留痕表（§六）承担记录职责；
- 页面"删除"文案改「移除（保留档案）」，避免使用者误以为文件被销毁。

### 3. 恢复（Restore）——新增端点，单调向前

`POST /restore`：把某个 `_archive/*.v{n}` 对象**复制回当前路径**（用 Copy，不 Move，保留归档件），生成新版本 `n+1`（Reason=`恢复自v{n}`），重走转换+提取。**不做版本号回拨**——历史链永远单调，审计只读。

> ⚠️ 依赖：`IObjectStorage` 当前**无 CopyObject**（`YZH.Core.Stand/Interfaces/IObjectStorage.cs` 仅 Upload/Download/Delete/Rename/List/Exists）。恢复与 13 号 §2.2 的"确认后直接 Copy 到最终路径"都需要先补框架层接口——按 AGENTS.md ⑪「框架层改造准入」5 条申报（理由=真实功能缺口，非风格统一）。`Rename` 现有实现若为 Copy+Delete，可先复用其 Copy 半程过渡。

### 4. 批量上传中的"覆盖已存在企业行"

映射确认时若目标文件位已有当前版本 → 提示走替换流程（复用 §五-1），禁止静默覆盖。

## 六、操作留痕方案（对 G-4）

沿用 07 号册「只追加」审计模式，新建**轻量操作日志表**（唯一新表，命名续 13 号风格）：

```sql
CREATE TABLE IF NOT EXISTS `cert_enterprise_file_op_log` (
  `Id` bigint NOT NULL AUTO_INCREMENT,
  `Code` varchar(36) NOT NULL COMMENT '业务键GUID',
  `CreateTime` datetime NOT NULL,
  `CreateBy` varchar(64) DEFAULT NULL COMMENT '操作人Code',
  `UpdateTime` datetime DEFAULT NULL COMMENT '更新时间（BaseEntity 强制列）',
  `UpdateBy` varchar(64) DEFAULT NULL COMMENT '更新人Code（BaseEntity 强制列）',
  `EnterpriseCode` varchar(36) NOT NULL,
  `StageCode` varchar(36) DEFAULT NULL,
  `FileCode` varchar(36) NOT NULL COMMENT '→ cert_standard_directory_file.Code（企业行）',
  `OpType` varchar(20) NOT NULL COMMENT 'upload/replace/delete/restore/extract_trigger/extract_done',
  `VersionNumber` int DEFAULT NULL COMMENT '本次操作产生的版本号（无关操作为NULL）',
  `Detail` varchar(1000) DEFAULT NULL COMMENT 'JSON：文件名/大小/映射来源/失败原因等',
  `IsDeleted` tinyint(1) NOT NULL DEFAULT '0',
  `IsValid` int NOT NULL DEFAULT '1',
  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_code` (`Code`),
  KEY `idx_enterprise_time` (`EnterpriseCode`,`CreateTime`),
  KEY `idx_file` (`FileCode`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='企业文件操作日志（只追加）';
```

> **G-0 落底勘误（2026-09-28）**：BaseEntity 强制列含 `UpdateTime/UpdateBy`（框架 INSERT 按实体属性映射列，缺列即运行时报 Unknown column），本 DDL 已补齐；同期发现 `cert_enterprise_file_version`（13 号 §1.4 同款缺列）已由迁移脚本 `scripts/db/20260928_enterprise_file_oplog_V1.sql` 一并 ALTER 补漏。

规则：

- **只追加、不修改不删除**；`OpType` 枚举扩展走新增不改语义;
- 13 号 `/History` 端点按此表实现（时间线 = op_log ∪ 版本表，按 CreateTime 排序）；
- `Reason`（替换/删除原因）在**前端对话框强制填写**，落 op_log.Detail + 版本表 Reason 双写；
- 提取链补 `extract_done`（含成功/失败、耗时、MaxConfidence），使"文件→提取质量"也可追溯。

**保留期限**：一期物理全保留（认证记录年限要求长，存储量 = 文件数×平均版本数×~2MB，可控）；生命周期策略（如 N 年以上归档转冷存储）登记为待办，不在本期拍板。
