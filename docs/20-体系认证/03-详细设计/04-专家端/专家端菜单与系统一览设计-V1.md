## 第零篇 结论摘要

| 项 | 结论 |
|---|---|
| 一级菜单 | **6 个**：系统一览 / 企业管理 / 任务中心 / 资料库 / 组织与成员 / 系统设置 |
| 二级菜单 | **12 个**（菜单记录合计 18 条） |

### 1.3 三处口径冲突（必须先收敛）

同一套导航，三份文档给了三种结构：

| 来源 | 一级导航 | 问题 |

| 界面设计 V1 §2 | **5 项**：工作台 / 企业管理 / 资源管理 / 消息中心 / 个人中心 | 企业导向，但**丢了"任务"与"日志"**；文档自称"导航重组、功能不削减"，实际削减了 |
| V4 计划 §4.8 | **技术目录**：workspace / enterprises / tasks / organization / system-profile | 是代码目录树，不是菜单；且只有 5 项，与上两者都对不上 |

**收敛原则（本文采用）**：

1. **以产品逻辑定菜单，不以功能模块定菜单** —— 模块是"系统有什么"，菜单是"专家要干什么"
2. **一级菜单不超过 6 个** —— 个人 SaaS 工具，超过 6 个就开始找不到东西
3. **一级菜单即落地页**，二级菜单才是可独立寻址的功能页（避免"点了一级还要再点一次"）
4. **任务不是一级实体** —— 任务是企业 × 标准 × 阶段的派生物，收进"任务中心"作为**视图**，不与"企业管理"平级争注意力

## 第二篇 菜单机制事实（源码级核实，2026-09-23）

> 这一篇是后面所有设计的依据。**其中"`Tag` 不参与过滤"是本轮最重要的发现** —— 它推翻了"给菜单设 `Tag='auditor'` 就能隔离"的常见误判。

### 2.1 过滤链路：只认 `Sys_RoleMenu`

`YZH.Core.Api/Services/MenuPermissionService.cs` 的 `GetVisibleMenusAsync()` 实际逻辑：

```
① 取全部菜单 → 排除 Enable == 0
② 若当前用户是 ROLE_SUPER_ADMIN → 直接返回全部（不看授权）
③ 否则取用户全部 RoleCode（来自 JWT claims）
④ 查 Sys_RoleMenu WHERE RoleCode IN (...) → 得到已授权 MenuCode 集合
⑤ 若授权集合为空 → 返回空列表（一个菜单都不给）
⑥ 祖先补全（避免父菜单未授权导致子菜单断链）
⑦ 按 MenuCode 过滤 + 按 OrderNo 排序
```

**关键结论**：

| 事实 | 影响 |
|---|---|
| **`Tag` 字段完全不参与过滤** | 设 `Tag='auditor'` **不会**让 admin 菜单对专家不可见，也**不会**让 auditor 菜单对管理员不可见 |
| `Sys_Menu.Enable = 0` → 不出现 | 这是**唯一**的"开关"手段（不需要删数据） |
| 超管绕过一切授权 | 用超管账号登录专家端会看到**全部 26 条管理端菜单** —— 测试时别被误导 |
| `Sys_RoleMenu` 为 0 → 菜单全空 | 当前 `ROLE_AUDIT_CLIENT_ADMIN` 正是 **0 条** → 注册用户登录后**侧边栏是空的**（阶段 1 未完成的直接后果） |

> `Tag` 的真实用途：① 后台菜单管理页的分类标签；② Vol 兼容端点 `getTreeMenu` 把它当 `tableName` 返回。**它不是隔离机制。**

### 2.2 端点与字段

| 端点 | 认证 | 返回 | 用途 |
|---|---|---|---|
| `GET /api/System/MenuManagement/tree` | `[Authorize]` | `ApiResponse<List<Sys_Menu>>` —— **扁平**列表，PascalCase | ✅ **运行时菜单树，前端用这个** |
| `GET /api/System/Menu/tree` | `[AllowAnonymous]` | `{ menu: [...] }`（`MenuNode` DTO，字段名是 `Name` 不是 `MenuName`） | ⛔ Vol 兼容，**不要用** |
| `GET /api/System/MenuManagement/tree/all` | `[Authorize]` | 全量，不过滤 | 菜单管理页维护用 |

字段语义（`docs/10-YZH架构/14-框架核心功能设计-V1.md` §5.1）：

| 字段 | 用途 |
|---|---|
| `Code` / `ParentCode` | 树结构（`ParentCode = '0'` 为根） |
| `Url` | **前端路由 path**（`/overview`） |
| `Icon` | Element Plus 图标名（字符串） |
| `OrderNo` | 排序（现有约定 100 / 200 / 300…） |
| `Enable` | 1=显示，0=隐藏 |
| `Tag` | 分组标记（**不参与过滤**） |
| `Auth` | **按钮级权限标识** —— 当前全库未使用，属预留 |

前端消费链（`cert-admin` 已跑通的模式，专家端照搬）：
`store/menu.ts` → `loadMenus()` → `api/system/menu.ts#getMenuTree()` → `MenuManagement/tree` → 前端 `buildTree()` → `AdminLayout.vue` 用 `el-sub-menu` / `el-menu-item` 渲染。

### 2.3 现状数据（实测）

| 表 / 项 | 实测值 | 说明 |
|---|---|---|
| `Sys_Menu` | **26 条** | 全部为管理端菜单（系统管理 10 + 业务管理 16） |
| `Sys_Menu.Tag` | **全 NULL** | `admin\|auditor\|enterprise\|common` 分流机制**从未启用** |
| `Sys_RoleMenu` | **23 条 / 6 个角色** | `ROLE_000002`(6) / `ROLE_000004`(5) / `ROLE_000100`(5) / `ROLE_000101`(2) / `ROLE_000102`(2) / `ROLE_SUPER_ADMIN`(3) |
| `ROLE_AUDIT_CLIENT_ADMIN` 的菜单 | **0 条** | ⛔ **注册用户登录后侧边栏为空** |
| `sys_api` | **399 条** | 含本轮新增的 `api/AuditorAuth/GetOrgList`(Id 440) / `Register`(Id 441) |
| `sys_role_api` | **90 条**（其中该角色 87 条，全 `Foundation/*` 只读） | |
| `Sys_RoleAuth` | **330 条** | 旧接口权限载体，**仍在使用**，不可删 |
| 专家端接口是否已授权 | **否** | `AuditorAuth/*` 两个端点**未关联**到 `ROLE_AUDIT_CLIENT_ADMIN`（当前靠 `[AllowAnonymous]` 放行） |

> ⚠️ **文档已过时**：`docs/10-YZH架构/14-框架核心功能设计-V1.md` §4.5 写"`sys_api` / `sys_role_api` **均未创建**" —— 实际两表已建且已有 399 / 90 条数据。该节需修订，否则会误导下一个开发者去"新建"已存在的表。

### 2.4 由事实导出的五条硬约束

1. **专家端菜单必须写 `Sys_RoleMenu`**（`RoleCode='ROLE_AUDIT_CLIENT_ADMIN'` × 18 条 MenuCode），只写 `Sys_Menu` 不生效
2. **绝不给该角色授权任何管理端菜单** —— 现有 26 条全是后台配置页，专家是**只读消费方**，不参与配置
3. **`Enable` 是唯一开关**，用于分期开放（§3.5），不要用删数据实现"暂不开放"
4. **`Tag` 照设但不指望它**：设成 `auditor` 便于后台辨识，同时在文档/注释里写明"不构成隔离"
5. **新增受保护接口后必须跑 ApiSync 并关联 `sys_role_api`**，否则非超管调用 **403**（`ApiCode = SHA256("{METHOD}|{控制器名}|{动作名小写}")`）

## 第三篇 菜单信息架构设计

### 3.1 设计原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **按专家的动作路径组织，不按系统模块组织** | 专家的路径是「看全局 → 管企业 → 跑任务 → 查资料 → 管人 → 管自己」 |
| 2 | **一级菜单 = 6 个封顶** | 超过 6 个在侧边栏就开始需要"找"，个人 SaaS 工具的容忍度更低 |
| 3 | **一级即落地页** | 点"企业管理"直接进企业列表，不再展开一层"企业列表"子菜单 |
| 4 | **任务降级为视图** | 任务是企业×标准×阶段的派生物。保留"任务中心"承载**跨企业的任务视角**（NC 任务 / 报告任务 / 我的关注），但排在"企业管理"之后 |
| 5 | **能力边界显式化** | 专家最容易困惑的是"我能做什么"。菜单里不体现，改由驾驶舱的"能力就绪度"承担（§4.2 ②） |
| 6 | **P2/P3 功能只占位不实现** | 账户与用量、消息设置、目录模板等先种菜单 + 占位页，避免首版侧边栏空洞 |

### 3.2 推荐方案（6 项）

```
映智汇认证专家平台
├─ ① 系统一览        /overview                     ← 驾驶舱，登录后落地页
├─ ② 企业管理        /enterprises
│    ├─ 企业档案        /enterprises               （列表 + 筛选 + 归档 Tab）
│    └─ 新建企业        /enterprises/new           （向导：基本信息 → 选标准 → 开阶段）
├─ ③ 任务中心        /tasks
│    ├─ NC 检查         /tasks/nc                  （按企业/标准/阶段筛选的任务列表）
│    ├─ 报告生成        /tasks/report
│    └─ 我的关注        /tasks/focused             （is_focused=1）
├─ ④ 资料库          /resources
│    ├─ 资料检索        /resources                 （跨企业全局检索）
│    └─ 目录模板        /resources/templates       （本机构可用目录模板，只读）
├─ ⑤ 组织与成员      /organization
│    ├─ 成员管理        /organization/members      （管理员/审核员/审核组长/企业用户）
│    └─ 角色分组        /organization/roles        （4 个默认分组的只读展示）
└─ ⑥ 系统设置        /settings
     ├─ 个人信息        /settings/profile
     ├─ 账户与用量      /settings/account          （P2 计费，先占位）
     ├─ 消息设置        /settings/notify           （P3，先占位）
     └─ 操作日志        /settings/logs             （操作留痕 + 队列执行日志）
```

**隐藏路由（不进菜单，但可独立寻址）**：

| 路由 | 说明 |
|---|---|
| `/enterprises/:code` | 企业详情（内含次级导航：基本信息 / 阶段 / 资料 / 联系人 / 归档记录） |
| `/enterprises/:code/phases/:phaseCode` | 阶段详情（四 Tab：资料库 / NC 检查 / 报告 / 标准目录） |
| `/tasks/:taskCode` | 任务详情（六 Tab：企业信息 / 资料管理 / 执行情况 / 检查结论 / 报告 / 标准条款） |
| `/login`、`/register` | 匿名页（`meta.anonymous`） |

> 任务详情用**同一路由**承载 NC 任务与报告任务（功能设计 V1 §6.2 的设计），靠 Tab 可用性区分，不拆两个页面。

### 3.3 方案对比

| 方案 | 一级菜单 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A（本文推荐）** | 6 项，见 §3.2 | 覆盖完整形态；任务与企业各归其位；预留位清晰 | 首版有 3 个占位菜单 | ✅ **采用** |
| **B（MVP 极简）** | 4 项：系统一览 / 企业管理 / 任务中心 / 系统设置 | 无占位，每个菜单都能用 | 资料库、成员管理塞进二级，后续要"搬家"，用户会看到菜单变动 | 备选 |
| **C（照抄 8 模块）** | 8 项 | 与功能设计 V1 一致 | 任务导向、与"关注核心是企业"矛盾；协同系统/费用管理首版空置 | ⛔ 否 |
| **D（照抄 5 项）** | 5 项：工作台/企业管理/资源管理/消息中心/个人中心 | 与界面设计 V1 一致 | 丢了"任务"这一核心操作入口；"工作台"与"系统一览"职责重叠 | ⛔ 否 |

**为什么推荐 A 而不是 B**：菜单一旦上线，用户就会形成肌肉记忆。B 方案省下的两个菜单，代价是后续"资料库从二级提升为一级"这类变更 —— 这类变更对老用户是负体验。**菜单一次性种全，用 `Enable` 控制开放**（§3.5），是代价最小的做法。

**A 与 D 的关键差异**：D 的"工作台"被我拆成了两个东西 ——「系统一览」（驾驶舱，看全局状态）与「任务中心」（干活的入口）。理由：**看板与工作台是两种不同的心智**，混在一起会导致页面既想当仪表盘又想当待办列表，最后两者都做不好。

## 第四篇 系统一览（驾驶舱）设计

### 4.1 设计目标与心智模型

**要回答的唯一问题**：「我现在该干什么？」

**两个心智维度**（这是整个页面的骨架）：

| 维度 | 问题 | 数据特征 |
|---|---|---|
| **能力** | 我选的机构**给了我什么**？ | 来自后台配置，**真实有数据**（3 标准 / 23 阶段 / 4 NC 规则 / 2 报告模板） |
| **业务** | 我用这些能力**做了什么**？ | 来自我自己的工作区，**当前全 0 行** |

> ★ **关键设计洞察**：新注册的专家工作区是空的，但"能力"不是空的。所以驾驶舱在 MVP 阶段**不是靠业务统计撑起来的，而是靠"能力就绪度"** —— 它把 V4 §1.2 的产品逻辑（选机构 = 选能力）变成用户看得见的东西。业务指标区**允许为空**，用引导态替代。

**明确不做的事**：不做花哨的图表（0 数据时图表是噪音）；不做实时刷新（首版按需刷新 + 手动刷新按钮）；不做可拖拽自定义布局（个人 SaaS 不需要）。

**③ 企业进度矩阵 —— 为什么它是"全局视觉"的核心**

- 完成度 = 四环节加权（资料 30% + NC 40% + 报告 30%），权重后续可由后台配置
- 排序：完成度升序（**最需要关注的排最上面**），而非按时间

### 4.4 空态与降级策略

| 场景 | 表现 |
|---|---|
| 全部业务数据为 0（新注册） | ① 显示引导条「暂无待办 · 去创建第一家企业 →」；③ 显示引导卡；④ 显示引导卡；⑤ 快捷入口仅「新建企业」可用 |
| 能力数据为 0（机构未配标准） | ② 显示警告态「该机构尚未配置可用标准，请联系平台运营」—— **这是异常，必须显式提示**，不能静默显示 0 |
| 某个聚合查询失败 | 该区独立降级为「数据加载失败 · 点击重试」，**其余区正常渲染**；响应带 `Partial=true` + `Missing[]`（沿用 `AuditTask/detail` 的降级契约） |

**原则**：**任一区失败都不允许整页白屏**。驾驶舱是登录后第一屏，白屏等于系统不可用。

| `cert_certification_body.Code` | GUID | `5833c904-a802-11f1-9d10-96af2c2a4a1a` |
| `cert_certification_body.CbCode` | 业务码 | `CB001` |
| `cert_org_standard.OrgCode` | **= 机构 `Code`（GUID）** | `5833c904-…` |
| `cert_org_stage.OrgCode` | **= 机构 `Code`（GUID）** | `5833c904-…` |
| 注册时写入的 `Sys_Organization.OrgCode` | **= 机构 `CbCode`** | `CB001` ⛔ |

→ 若驾驶舱按"工作区 `OrgCode` = 能力表 `OrgCode`"查询，**匹配 0 行**，页面显示"可用标准 0 个"，且**不会有任何报错**。

**这正是列名铁律要防的那类问题**：字段名一样，语义不一样，静默失配。

**修复方案（三选一，建议 A）**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 注册时改为写 `Sys_Organization.OrgCode = certBody.Code`（GUID），与能力表对齐 | 改动最小（1 行代码 + 1 条数据修正脚本），语义仍成立（`OrgCode` 是"机构编码"）；`CbCode` 另找位置存 |
| B | 能力表 `OrgCode` 全部改存 `CbCode` | ⛔ 破坏存量数据与后台配置页，不可接受 |
| C | 驾驶舱查询时做 `CbCode → Code` 转换 | 只是把问题藏在查询层，下一个调用方还会踩 |

**附加要求**：`cert_auditor_org.CbCode`（V4 §4.6 设计的工作区 Attach 表）应尽快建表 —— 它是存放 `CbCode` / 配额 / 到期的正位，能把"机构归属"从 `Sys_Organization` 的语义借用中解放出来。

#### 阻塞 2：注册用户登录后侧边栏为空

`ROLE_AUDIT_CLIENT_ADMIN` 的 `Sys_RoleMenu` = **0 条** → 按 `MenuPermissionService` 逻辑，非超管用户拿到的菜单列表是**空数组**。

**修复**：执行 §3.4 的种子 SQL 第 ② 步。

#### 阻塞 3：机构下拉混入无 `CbCode` 的脏数据

`cert_certification_body` 中 3 条 `IsValid=1 AND Status='active'`，但只有 1 条有 `CbCode`：

| Name | CbCode | 评价 |
|---|---|---|
| 河北雄安尚龙认证有限公司 | `CB001` | ✅ 真实可用 |
| 接口驱动测试 | **NULL** | ⛔ 测试数据 |
| 6 | **NULL** | ⛔ 测试数据 |

→ 专家注册下拉里会看到"6"和"接口驱动测试"，选中后 `OrgCode` 写入 NULL、能力边界为空。

**修复**：`AuditorRegisterService.GetCertBodyOptionsAsync()` 的查询条件加 `&& !string.IsNullOrEmpty(x.CbCode)`；同时把两条测试数据置为 `Status='inactive'` 或 `IsValid=0`。

> 这三条都不大，但**都在关键路径上**：不修，驾驶舱做出来就是"全是 0 和 —"，会让人误以为驾驶舱本身没做完。

### 5.2 实施顺序建议

| 序 | 事项 | 依赖 | 交付 |
|---|---|---|---|
| 1 | 修 §5.1 三个阻塞 | — | 数据正确 + 菜单可见 |
| 2 | 种菜单 + 授权（§3.4 SQL） | 1 | 侧边栏出现 6 个一级菜单 |
| 3 | `store/menu.ts` + `AuditorLayout.vue` 动态菜单 | 2 | 菜单由后台驱动，不再是写死的 1 条 |
| 4 | 路由骨架 + `_placeholder` 兜底页 | 3 | 18 条菜单全部可点，不白屏 |
| 5 | `GET /api/Overview/summary` 后端（**先只实现 Capability，其余返回空结构**） | 1 | 驾驶舱能出真数据 |
| 6 | `pages/overview/index.vue` 驾驶舱五区 | 5 | 首屏可用 |
| 7 | ApiSync + `sys_role_api` 关联 `Overview/*` | 5 | 专家调用不 403 |
| 8 | 逐区把 ①③④ 从"降级空态"升级为真实数据 | 阶段 3/4 业务接口 | 驾驶舱完整 |

**关键点**：第 5 步**刻意只实现 Capability 一个区**。理由 —— 接口契约先定死（`OverviewSummaryDto` 全字段返回，其余给空结构），前端一次成型，后续只是后端填数，**前端不用改**。这样能把"驾驶舱"和"业务接口"解耦，不被阶段 3/4 阻塞。
