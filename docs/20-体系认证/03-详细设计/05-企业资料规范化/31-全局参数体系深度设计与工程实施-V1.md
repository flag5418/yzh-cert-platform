# 全局参数体系深度设计与工程实施-V1.md

> **状态**：**工程级深度设计 —— 待审批**
> **目标**：实现严谨的参数继承体系（机构 -> 标准 -> 阶段），确保“专家看到的”与“文档生成的”绝对一致。

---

## 一、 核心逻辑：多级继承与冲突解决（Specificity 算法）

系统必须支持在不同粒度定义同名参数（如 `company_name`），并在运行时根据当前上下文（Context）自动决策生效值。

### 1.1 作用域定义
| 作用域类型 | `StandardCode` | `StageCode` | 权重 (Score) | 语义 |
| :--- | :--- | :--- | :--- | :--- |
| **通用 (Global)** | `null`/`""` | `null`/`""` | 0 | 只要在同一个机构下，所有文档均生效 |
| **标准专属 (Standard)** | `S001` | `null`/`""` | 2 | 仅在该标准（如 9001）下的所有阶段生效 |
| **阶段专属 (Stage)** | `null`/`""` | `P001` | 1 | 仅在该阶段（如初审）下的所有标准生效 |
| **全限定 (Full)** | `S001` | `P001` | 3 | 仅在特定标准 × 特定阶段下生效（最高优先级） |

### 1.2 决策算法 (C# 实现)
```csharp
public static List<FillParamDef> PickMostSpecific(IEnumerable<FillParamDef> defs) =>
    defs.GroupBy(d => d.ParamCode)
        .Select(g => g.OrderByDescending(d => {
            var score = 0;
            if (!string.IsNullOrWhiteSpace(d.StandardCode)) score += 2;
            if (!string.IsNullOrWhiteSpace(d.StageCode)) score += 1;
            return score;
        }).ThenBy(d => d.Id).First())
        .OrderBy(d => d.SortOrder)
        .ToList();
```

## 二、 数据库设计 (DDL)

### 2.1 全局定义表 (`cert_fill_param_def`)
```sql
CREATE TABLE `cert_fill_param_def` (
  `Id` bigint NOT NULL AUTO_INCREMENT,
  `Code` varchar(36) NOT NULL COMMENT '业务编码',
  `OrgCode` varchar(50) NOT NULL COMMENT '所属机构',
  `StandardCode` varchar(36) DEFAULT '' COMMENT '空代表不限标准',
  `StageCode` varchar(36) DEFAULT '' COMMENT '空代表不限阶段',
  `ParamCode` varchar(100) NOT NULL COMMENT '参数标识(如 company_name)',
  `ParamName` varchar(200) NOT NULL COMMENT '显示名称',
  `GroupName` varchar(100) DEFAULT '基础信息' COMMENT '参数分组',
  `ValueType` varchar(20) DEFAULT 'text' COMMENT 'text|number|date|enum',
  `SourceKind` varchar(20) DEFAULT 'auto' COMMENT 'auto(档案)|manual(手工)|ai(AI)|default',
  `SourceExpr` varchar(500) DEFAULT '' COMMENT '取值表达式(如 enterprise.Name)',
  `MaintainMode` varchar(20) DEFAULT 'both' COMMENT 'auto(只读)|manual(手工)|both(带出可改)',
  `DefaultValue` longtext COMMENT '默认值',
  `SortOrder` int DEFAULT '0',
  `IsValid` int NOT NULL DEFAULT '1',
  `IsDeleted` tinyint(1) NOT NULL DEFAULT '0',
  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_scope_param` (`OrgCode`,`StandardCode`,`StageCode`,`ParamCode`),
  KEY `idx_param_code` (`ParamCode`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;
```

## 三、 前端交互深度设计 (左树右表)

### 3.1 树节点点击逻辑
- **点「机构」节点**：右表显示 `StandardCode='' AND StageCode=''` 的**通用参数**。
- **点「标准」节点**：右表显示 `StandardCode='Selected' AND StageCode=''` 的**标准专属参数**。
- **点「阶段」节点**：右表显示**叠加后的最终生效集**（即：通用 + 该标准专属 + 该阶段专属，按权重去重）。

### 3.2 专家端 (Auditor) 的参数完善
- **合并策略**：后台定义（Def）+ 企业历史值（Value）+ 企业档案（EnterpriseInfo）。
- **冲突处理**：如果企业在 9001 阶段改了 `company_name`，但在 14001 阶段没改，系统应支持按三元组分别存储，或通过“同步至全局”按钮将改动推回企业档案。

## 五、 稳定性与规范性保障
1. **一致性拦截**：所有文档生成前的 `Resolve` 逻辑必须强制调用 `ParamValueResolver.PickMostSpecific`，禁止在各 Resolver 中私自实现取值逻辑。
2. **变更追溯**：`cert_fill_param_value` 必须记录 `UpdateBy` 和 `UpdateTime`，专家对参数的每一次手动覆盖都必须有迹可循。
3. **性能优化**：对 `PickMostSpecific` 的结果进行内存缓存（按三元组 Key），仅在 `FillParamDef` 发生变更时清除缓存。
