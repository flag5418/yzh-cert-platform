## 一、评估方法

- **主对象**：`01-总体设计与能力地图`（五层 / 能力地图 / 衔接矩阵）与 `03-业务流程与状态机`（泳道 / 四条状态机 / 触发点）。
- **佐证**：`README`（D1–D11 / P1–P6）、`99`（统一表哲学）、`14`（D12–D28）、`16-V2`（L5 载体）、`15` §二/§五（问题分级）、`17`（规模与死线）。
- **判据**：① 方向是否自洽且可落地；② 端到端流程是否**闭环**（每条路径都有出口，含最坏路径）；③ 模块**边界与依赖**是否单向、无循环、无二义归属；④ 是否存在**明显缺陷/缺失**。
- **不做**：不重复 `15` 的 A/B/C 事实清单，不重复 `17` 的排期结论。

## 二、全局方向合理性（✅ 认可，不要动）

1. **命题清晰、目标单一**：「企业散乱资料 → 标准目录中的标准文档」。输入/处理/输出三句话可复述，符合「先有全局方向」的要求。
2. **三条链物理分离（转换链 / 画像链 / 定向链，D3）**：画像链服务匹配、定向链服务填充，互不写对方的表——这是本设计最关键的**解耦决策**，避免了「先有匹配结果才能画像」的因果倒置。
3. **三阶段匹配（D7）**：指纹（零 LLM）→ 召回（零/低 LLM）→ 精排（Top-K、批式）。理由不是省钱，而是「同一评委、同一场比赛」的**可比性**——属架构级论证。
4. **人工裁决底线（D9）**：AI 只产候选、最终归属必须人工；`IsConflicted=1` 禁自动确认。符合认证合规。
5. **降级底线**：LLM 全线不可用时退化为「规则识别 + 人工全量裁决」，业务不中断。
6. **五层依赖单向**：L1（接入）→ L2（加工前置）→ L3（认知）→ L4（匹配决策）→ L5（填充输出），无环，符合分层原则。

**判定**：全局方向**不需要重新论证**。下面全部是**同一方向内的完整性缺口**。

## 三、端到端流程闭环审查（泳道级）

`03` §1 的泳道画的是**理想全链**（上传→转换→画像→召回→精排→裁决→定向提取→填充）。逐路径检查「有没有出口」：

| 路径 | 是否有出口 | 判定 |
|------|-----------|------|
| 正常链（有高分候选 → 裁决 accept → 填充） | ✅ 有 | 闭环 |
| 转换失败 | ✅ 有（`convert_failed`，可重试/放弃，仍可人工指定） | 闭环 |
| 画像失败 | ✅ 有（`profile_failed`，可重跑） | 闭环 |
| 画像跳过（无 Markdown / 图片型 PDF） | ✅ 有（`skipped`，等 OCR） | 闭环 |
| 裁决 reject | ✅ 有（候选 `rejected`） | 闭环 |
| **召回为空 / 全部低于复核线** | ⚠️ **仅 `03` §6 异常表一行文字**（「进无归属清单」），**未进四条状态机、未进泳道、无可操作终态** | ⛔ **缺口 G-01** |
| 契约缺失 | ✅ 有（该标准文档不参与匹配） | 闭环 |
| 文件替换/删除 | ✅ 有（状态归零 + 回退） | 闭环 |

**结论**：泳道在**最坏情况**（一份企业文档谁都不匹配、也不该匹配任何标准文档）没有建模出口。详见 `G-01`。

## 四、模块关系与依赖审查（边界）

### 4.1 依赖方向（✅ 健康）

- **上→下**：L4 依赖 L3 的画像，L5 依赖 L4 的裁决；反向无依赖。✅
- **新→旧复用**：L1/L2、契约 3/4/5 号要素、`cert_extraction_result`、AI/队列底座全部复用，本模块只新建 L3/L4/L5。✅
- **与工作流的边界（D4）**：匹配引擎不进 Skill 体系，但结果可被 `ai_node` 读取——单向消费，无环。✅

### 4.2 边界债（⚠️ 需在总体层声明）

| 债 | 现象 | 影响 |
|----|------|------|
| **L5 载体未冻结（G-02）** | `01` 的 L5 只有「模板填充 + 实例版本 + 审计」；真正的填充引擎在 `16` 号，而 `16-V2` 自述「非实施规格，§13 待决」 | 架构图里 L5 是**黑盒**：L4→L5 的接口（候选→填充什么文档、什么产物）无法确定 |
| **跨册边界（G-11）** | `13` 号物理在 05 册、业务属 06 册；`05`（下一步）与 `06`（本期）**共享同一存储底座**（`cert_standard_directory_file` / `StandardFileCode`） | 底座共享但流程分线，若不在总体层画清「共享哪些表/状态列」，两线实现易互相污染 |
| **统一表架构的代价（已识别）** | D11 让模板行/企业行共表，查询谓词纪律、模板行写保护成为硬约束（`T-06`） | 已登记，非新问题；但它是**全局方向的最大耦合点**，须在总体层显式承接 |

## 六、结论与先决项

### 6.1 结论

1. **骨架可保留，不必重做** —— 全局方向、五层依赖、三链分离、三阶段匹配、人工裁决底线均成立。
2. **补齐对象是「总体层的完整性」，不是「换方案」** —— 缺口集中在 **L5 与横切能力**：L1–L4 画得完整，L5 与「可信度/人工干预总线」还停在名词。
3. **流程闭环差一个终态（`G-01`），L5 差一个冻结（`G-02`）** —— 这两项不解决，总体设计不闭环，也不宜进入任何实施排期。

### 6.2 总体设计先决项（按依赖顺序）

```text
① G-01 拒识 / 无归属终态            → 流程闭环（不依赖他人）
② G-02 L5 冻结（16 号 §13 A 批）    → 骨架最后一环落地（依赖 16 号收敛）
③ G-03 横向「可信度与人工干预总线」  → 与 ② 同轮（决定置信度字段与页面契约）
④ G-04 状态所有权矩阵               → 与 ③ 同轮（跨服务契约）
⑤ G-05 产物实例主权与生命周期        → 依赖 ②（实例形态）
⑥ G-06 角色 × 阶段责任矩阵          → 可与 ③/④ 并行；关闭 P4
⑦ G-07 契约生命周期                 → 依赖 ③（命名冻结）
⑧ G-08/G-09/G-10/G-11 补强          → 收尾，随总体设计定稿统一落
```

> **判定**：先决项 ①–⑦ **全部是总体设计层的工作**（画图、定契约、冻结命名），**不是数据库或接口细节**。完成后再去逐条过 `15` §十二 的 `Q-01…Q-25`，才不会「在未定型的地基上裁决细节」。
