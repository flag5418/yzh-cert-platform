## 一、功能定位与边界

### 1.1 一句话定位

> **把「有内容的标准文档」变成「可自动填写的空白模板（带锚点）」，并为每个锚点配置「值从哪来」。**

它是**写侧的规则定义页** —— 只**定义**规则，**不执行**填充（填充在专家端 ⑥ 企业资料规范化）。

### 1.2 与相邻菜单的边界（**三张表对比，一图看懂**）

| 菜单 | 方向 | 输入 | 手段 | 产物 | 执行期 |
|------|------|------|------|------|--------|
| `MENU_00207` 标准资料清单 | — | 文件 | 上传/改名/删除 | 标准目录树（168 份） | 定义期 |
| `MENU_00208` 文档提取规则 | **读** | 有数据的标准文档 | LLM + 验证 | `cert_doc_field_def` / `_table_def` | 定义期 |
| `MENU_00210` 文档语义规则 | **读** | 有数据的标准文档 | LLM | `cert_standard_doc_contract`（分类/作用） | 定义期 |
| **`MENU_00218` 标准文档填写规则** | **写** | **空白模板** | **零 LLM 扫描 + 人工配规则** | `cert_doc_template` / `_anchor` / `cert_doc_fill_prompt` | 定义期 |
| ⑥ 企业资料规范化（专家端） | 执行 | 画像 + 模板 | 引擎 + Resolver | 填好的 docx/xlsx | **执行期** |

> ⚠️ **本页是「定义期」**。22 号 §13.6 的判据：**定义期 = 低频 / 重 / 需人工编排 / 需留痕 ⇒ 适合画布与人工配置**；
> **填充期 = 高频 / 毫秒级 / 确定性 ⇒ 走引擎**。本页只做前者。

### 1.3 在六步顺序中的位置

```

② 封装 NPOI（层 1 写入器） ✅ 已完成（Office/ 15 源文件 + 4 测试，148/148 全绿）
③ 全局参数替换 + 填写     ← 剩余「把层 1 原语接到端点/页面上」
④ 企业资料上传 + 语义提取 + markdown
⑤ 后台文档填写规则页      ← ★★ 本设计
⑥ 企业资料自动填写页
```

**依赖关系（有向，不可乱序）**：

```
② 层 1 写入器 ──┐
① 全局参数    ──┼──→ ⑤ 本页（定义规则）──→ ⑥ 填充执行
```

⇒ 本页**不阻塞** ③ 的收尾（③ 是把已有原语接到端点上），但 **⑥ 阻塞于本页**（没有规则就没有可执行的东西）。

### 1.6 ★★ 语义分析按 `DocCategory` 分流（**你本轮新提的「细化」**）

**你的原话**：
> 「针对这些文档，**语义也得有**，因为我们进行匹配的机制也是靠**标签和文档的语义**来分析的，
>  其实这个针对我们的语义分析还需要**进行细化**，如果是**固定格式的文档，应该和其他的 office 文档有差异**」

#### （1）为什么 `fixed` 也必须有语义 —— 匹配链有两个入口

```
企业上传 300 份乱资料  ←→  标准目录 168 个槽位
        │                        │
        ├─ editable 资料 ──→ 标签 + 语义 + 关键词（R1~R4 召回）──→ LLM 精排（04 §3~§4）
        └─ fixed 资料    ──→ 【指纹链】零 LLM ──→ 命中即定归属（04 §2）
                                  ↑
                    指纹规则来自**标准侧契约的 FingerprintJson**
```

⇒ **`fixed` 不是「不需要语义」，而是「语义的载体不同」**：
它的语义**不在画像里现算**，而是**预先固化在契约里** —— 因为证件格式恒定，算一次就够，
这正是 `04` 号 §2.1 的原话：「国家固定格式文档**格式恒定、字段恒定**，LLM 是昂贵且引入不确定性的绕路」。

#### （2）两条语义链的差异（★ 本节结论）

| | **A 链：`editable` 语义分析**（已有，`MENU_00210`） | **B 链：`fixed` 语义**（本设计补充） |
|---|---|---|
| 触发 | `AnalyzePolicy=analyze` | 指纹命中 ⇒ `AnalyzePolicy=skip`；未命中才 `analyze` |
| 输入 | Markdown **全文** | **文件名 + 表头 + 关键字段**（**不读全文**） |
| 手段 | LLM 读全文 | **零 LLM**（指纹）+ 可选 LLM 只判「这是什么证件」 |
| 产出 | 标签 + 四段作用 + **字段 / 表格定义** | 标签 + 四段作用 + **关键字段清单**（带正则） |
| 落点 | `cert_doc_field_def` / `_table_def` | `cert_standard_doc_contract.FingerprintJson.keyFields[]` + `InfoItemsJson` |
| 去向 | ⑧ 定向提取 → ⑨ 契约填充（**写**） | OCR / 抽取 → 回流全局参数（**读**） |
| 提示词 | `doc_group` / `doc_content`（已有 3 条种子） | **⛔ 不新增 `PromptType`**（见下） |

#### （3）⛔ 为什么不给 `fixed` 新增 `PromptType`

- `33` 号 §4.1 铁律：「**沿用 `wf_prompt_template` 现有 `PromptType`，⛔ 不改枚举**」；
- `04` 号 §2.5 明确：「**每份固定文档的指纹规则由管理员在契约页维护，系统不内置硬编码规则**」。

⇒ `fixed` 的语义**天然是人工配置物**，不是 LLM 产物。
**新增提示词类型会诱导把它做成 LLM 推断 —— 方向错误**（等于花 token 去猜一个恒定格式）。

**唯一需要 LLM 的场合**：企业侧上传了一份**从未配过指纹**的证件 → 画像判「这是什么」。
这走的是**现有 `doc_group` 提示词**（只判标签），**不新增类型**。

#### （4）⇒ 对本页（37 号）的三个直接后果

1. **`fixed` 文档选中时，右栏第一个页签不能是「锚点与字段规则」** —— 它没有锚点、没有填写规则 ⇒ 换成「**指纹规则**」（§3.6）
2. **契约表必须能独立承载 `fixed` 的全部语义** —— 因为 `fixed` 走零 LLM，语义只能来自契约
3. **`InfoItemsJson` 对两类含义不同**：
   - `editable`：「这份文档**包含**哪些信息」→ 供**覆盖度计算**
   - `fixed`：「这份证件**能抽出**哪些字段」→ 供 **OCR 回填**（`14` 号 §D16：营业执照 → 统一社会信用代码 / 法人 / 经营范围）

### 3.5 来源链编辑器（★ 本页最「非标准」的 UI）

**这是 22 号最核心的设计**：「取值来源是**有序列表**，不是单值」。

```
┌ 取值来源链 ───────────────────────────────────────────────────────┐
│ 组合方式： (•) 顺序回退 firstHit   ( ) 拼接 concat   ( ) 模板 template │
│ ─────────────────────────────────────────────────────────────────│
│ ⠿ 1  ▾ 全局参数       参数 [ENT_CREDIT_CODE ▾]      缺失时 [取下一个 ▾] │
│ ⠿ 2  ▾ 企业资料画像    文档 [营业执照 ▾] 字段 [统一社会信用代码] 置信≥[0.85] │
│ ⠿ 3  ▾ 人工录入                                      缺失时 [挂待办 ▾]  │
│                                                    [＋ 添加来源]     │
│ ─────────────────────────────────────────────────────────────────│
│ 预览：先取全局参数 → 没有则去企业资料画像里找 → 都没有就挂人工待办      │
└──────────────────────────────────────────────────────────────────┘
```

**关键交互**：

| 元素 | 行为 |
|------|------|
| `⠿` | 拖拽排序（顺序 = 回退优先级） |
| `kind` 下拉 | 7 类：`global` / `self` / `sibling` / `profile` / `compute` / `ai` / `manual` |
| 第二列 | **随 `kind` 变化**：`global`→参数下拉；`profile`→文档+字段+置信度；`compute`→表达式；`self`→锚点下拉；`ai`/`manual`→无 |
| `onMissing` | `block`（阻断）/ `next`（取下一个，**默认**）/ `todo`（挂待办）/ `empty`（留空） |
| 底部预览 | **实时人话**，让实施人员确认逻辑对不对（这是防错的关键） |

**⛔ 非法组合必须在前端拦住**（`22` 号 §6.1，保存时也要后端复核）：

| 组合 | 为什么不合法 |
|------|-------------|
| `domain(auto)` + 任何 D1 | 域自动值不能写（`PAGE` 交给 Word 算） |
| `table_total` + `manual` | 合计必须能算，人工填合计 = 必然算错 |
| `scalar` + `remove` | 行内标量删除会破坏排版，应改用 `block` |
| `self` 形成环 | 拓扑排序无解 |

### 4.4 ⚠️ 两处表设计冲突（**必须裁决**）

#### 冲突 1：分类 / 作用放**模板表**还是**契约表**？

| 立场 | 出处 | 主张 |
|------|------|------|
| **A** | `21` 号 §4.3 表1 | 放**模板表**（`DocCategory` / `TagsJson` / `DocPurpose` 5 列） |
| **B** | `20` 号 §四 + `19` 号 §二 A 段 | 属**契约**，**不该放模板上**，否则「同一文档的两个模板版本分类不一致」无处仲裁 |

**实连库事实**：`cert_standard_doc_contract` **已建**（48 列），
且 `DocCategory` / `DocPurpose` / `TagsJson` / `DocPurposeSource` / `TagsConfidence` 等列**全都有**；
`StandardFileCode` 是 **UNIQUE** ⇒ **1 标准文档 : 1 契约**。

**⇒ 建议取 B**：模板表**删掉**这 5 列，分类/作用**只在契约表**。

**理由**：分类/作用是**文档的属性**，不是**模板的属性**。模板可能有多个历史版本（换版归档），
而「这份文档是记录类还是手册类」不随模板版本变。两个地方存 = **必然不一致**（`33` 号 §7.1 的教训）。

⇒ **裁决 Q-2**

#### 冲突 2：全文填写提示词存**模板行**还是**独立表**？

| 立场 | 出处 | 主张 |
|------|------|------|
| **A** | `21` 号 §4.3 表1 | `cert_doc_template.FillPrompt longtext`（**内嵌**） |
| **B** | `23` 号 §5.2 | `cert_doc_template.FillPromptCode` + **独立表** `cert_doc_fill_prompt` |

**⇒ 建议取 B**（独立表），三条理由：
1. **要跨模板复用** —— 「标准文档通用填写」一套规则应服务多份模板，内嵌就必须复制 N 份
2. **要版本留痕** —— `cert_doc_fill_prompt.Version` + `IsDefault` 是 `23` 号刻意设计的
3. **`Model`/`Temperature`/`MaxTokens`/`OutputSchema` 需要独立承载** —— 内嵌会让模板表膨胀

⇒ **裁决 Q-3**

| POST | `/api/DocFillRule/fill-prompt/save` | 保存全文规则（新版本） | `Version+1`，旧版保留 |
| POST | `/api/DocFillRule/fill-prompt/try` | 试跑 | 一次 LLM，返回 `{FieldCode:value}` + token/费用 |
| GET | `/api/DocFillRule/contract?fileCode=` | 文档契约（**只读**） | Tab3 数据源 |
| POST | `/api/DocFillRule/validate` | 三色校验 | 红黄牌 |
| POST | `/api/DocFillRule/publish` | 发布 | 有红牌 ⇒ 拒绝（**后端也判**，防绕过） |

**★ 接口返回契约（⛔ 不得偏离）**：
- 信封 **camelCase**，`success` 是**唯一判据**；业务失败 **恒 HTTP 200**
- `data` **camelCase** ⇒ DTO 必须**逐字段** `[JsonPropertyName]`（否则前端读 `undefined` 且**零报错**）
- 写操作**一律走 `expectOk`**（否则静默失败甚至假成功提示）
- 前端 `savePrompt` 类请求体 **必须 PascalCase**（后端 `PromptSaveRequest` 无 `[JsonPropertyName]`）

## 六、两条规则的详细设计（★★ 本设计的核心）

> 这两条规则**不是本文发明的**，是 `22` 号（层 1）与 `23` 号（层 2）的既有设计。
> 本节只做**「在页面上怎么落」**的落地说明。

### 6.1 层 1 · 字段填写规则 = 三元组（你说的「字段提取规则」）

**一个填写单元 = `(D1 取值来源, D2 写入方式, D3 承载形态)` 三元组。**

> ⛔ **不要压成一个枚举**。「页眉里的企业名称」同时是 *替换型* + *参数型* + *页眉形态*，
> 归到任何一类都会丢信息（`22` 号 §〇）。

#### D1 取值来源（7 类，判据 = 「值最初从哪来」）

| 码 | 名称 | 值从哪来 | 典型例子 | 失败行为 | 频率 |
|----|------|---------|---------|---------|------|
| `global` | 全局参数 | 认证项目上下文（企业/阶段/标准/机构） | 企业名称、统一社会信用代码、标准号 | 必填缺失 → **阻断** | ★★★ |
| `self` | 本文档内引用 | 同一模板的另一个锚点 | 封面写企业名 → 页眉引用它 | 引用目标未填 → 阻断（**须防环**） | ★★ |
| `sibling` | 同批文档取值 | 同企业同阶段另一份标准文档 | 「管理评审报告」引用「内审报告」的日期 | 目标未完成 → 降级下一源 | ★（**一期不做**） |
| `profile` | 企业资料画像 | 企业上传散乱资料的画像结果 | 从「营业执照」取注册号 | 未命中 → 降级下一源 | ★★★ |
| `compute` | 计算 / 统计 | 对锚点集合做运算 | 表格行数合计、日期差 | 依赖缺失 → 留空并告警 | ★★ |
| `ai` | AI 生成 | LLM 依上下文生成 | 大段描述、审核结论 | 低置信 → 降级人工 | ★★★ |
| `manual` | 人工录入 | **必须人填** | 签字日期、现场观察结论 | 未填 → 挂**待办**，不阻断出文档 | ★★★ |

#### D2 写入方式（4 类）

| 码 | 名称 | 语义 | 需原值 | 典型场景 |
|----|------|------|--------|---------|
| `replace` | 替换 | 锚点处**已有内容**，替换掉它 | ✅ | 页眉、模板里已写示例值的大段描述 |
| `overwrite` | 重写 | 锚点处**为空**，直接写入 | ❌ | 空白书签位置、空单元格 |
| `append` | 追加 | 保留原内容，在锚点后追加 | ⚠️ | 「备注：」后追加条款编号 |
| `remove` | 删除 | 该内容**不适用**，整块移除 | ✅ | 企业无某项资质 → 删掉对应整段 |

> ★ `replace` 的**真正价值不是省事，是可审计**：它必须落一份原值快照（`OriginalText`），
> 才能支撑「原值 → 新值」差异展示、人工改过的值不被覆盖、回滚（`22` 号 §4.1）。

#### D3 承载形态（5 类）

| 码 | 名称 | 定位手段 | 例子 |
|----|------|---------|------|
| `scalar` | 标量 | 行内 Token `{{FieldCode}}` | 单元格、行内字段 |
| `block` | 段落块 | Word 书签 | 大段描述、体系覆盖范围 |
| `table` | 表格区域 | Excel 区域 + `total_token`；Word 表格书签 | 受审核部门清单、不符合项表 |
| `table_total` | 表格合计 | 表格区域的合计行 | 行数、金额、人数合计 |
| `domain` | 域 | Word 页眉/页脚 + 域代码 | 页眉企业名、页脚「第 X 页 共 Y 页」 |

#### 合法组合（`22` 号 §六，**可直接当实现清单**）

| # | 场景 | D3 | D1 | D2 |
|---|------|----|----|----|
| 1 | 封面「企业名称」 | `scalar` | `global(ENT_NAME)` | `replace` |
| 2 | 页眉「企业名称」 | `domain` | `self(→封面锚点)` | `replace` |
| 3 | 正文「认证范围」 | `block` | `global(ENT_CERT_SCOPE)` | `replace` |
| 4 | 正文「体系覆盖过程描述」 | `block` | `ai` | `overwrite` |
| 5 | 表格「受审核部门清单」 | `table` | `profile(部门表)` | `overwrite` |
| 6 | 表格「人数合计」 | `table_total` | `compute(SUM_ROWS)` | `overwrite` |
| 7 | 「统一社会信用代码」 | `scalar` | `[global, profile, manual]` | `replace` |
| 8 | 「审核结论」 | `block` | `[ai, manual]` | `overwrite` |
| 9 | 「不适用条款段落」 | `block` | `manual(条件)` | `remove` |
| 10 | 页脚「第 X 页 共 Y 页」 | `domain` | `compute(PAGE/NUMPAGES)` | —（不写值） |

> **第 7 行就是「多数据源」的样板** —— 一个锚点、三个源、按序回退、最后兜底人工。

#### ⛔ 一期实现范围（`25` 号纸面实验实测校准）

`22` 号的 `7 × 4 × 5 = 140` 组合，在 **167 份真实文档全量实测**中**一期只用到 3~4 个组合**：

- **D1 只用** `global` / `compute` / `manual`（`ai`/`profile`/`self`/`sibling` 一期无场景）
- **D2 只用** `replace`（+ 少量 `overwrite`）
- **D3 只用** `scalar` / `table` / `table_total`

⇒ **分类保持完整（供二期），但界面默认只展开这三类**，其余折叠在「更多」里。

### 6.2 层 2 · 全文填写规则 = 装配器（你说的「全文提取规则」）

> **一句话**：全文填写规则 = **一个提示词模板 + 一个装配器 + 一次 LLM 调用**。就这三样。
> 它**不是引擎**、**不是画布**、**不是第二套工作流**（`23` 号 §5.4）。

#### 为什么需要层 2（层 1 不够吗？）

| | 层 1 单元级 | 层 2 文档级 |
|---|---|---|
| 表达方式 | **声明式**（属性配置） | **装配式**（组合提示词） |
| 覆盖场景 | 确定性的单点取值 | 需**跨字段推理**、需**从多份文档组织**的内容 |
| 单位成本 | 每个锚点配一次 | **每个模板只配一次** |
| 是否必填 | ⛔ **不是** | ✅ 每模板一条（可留空） |

**★ 关键契约（两层之间的唯一接口）**：

> **没设单元级规则的锚点，其隐式规则 = `SourceKind: ai`，值从「全文填写规则的输出字典」里按 `FieldCode` 取。**

#### 装配器（照抄 `NcPromptAssembler` 的形状）

> ★ `23` 号 §三 的关键发现：**这个模式项目已经做过** —— `NcPromptAssembler` 解决的问题**完全同构**：
> NC 当初是「每条规则重复写一遍判定框架」，现在是「每个模板重复写一遍填写提示词」。

```csharp
/// <summary>★ 文档填写 Prompt 装配器（服务端组装，★ 不依赖引擎改造）</summary>
public class DocFillPromptAssembler
{
    public static (string SystemPrompt, string UserTemplate) BuildFillPrompt(
        DocFillPrompt template,
        IReadOnlyList<AnchorSpec> anchors,              // 决定要填哪些字段/表格
        IReadOnlyDictionary<string, string> globals,    // 全局参数快照（企业×阶段）
        string? profile)                                // 企业资料画像结果（可选）
    {
        var user = template.UserTemplate
            .Replace("{{__FILL__.fields}}",  BuildFieldList(anchors))
            .Replace("{{__FILL__.tables}}",  BuildTableList(anchors))
            .Replace("{{__FILL__.globals}}", BuildGlobalList(globals))
            .Replace("{{__FILL__.profile}}", Safe(profile));

        return (template.SystemPrompt ?? string.Empty, user);
    }

    /// <summary>★ 复用 NC 的漏填检测（同一套正则约定）</summary>
    public static List<string> FindUnresolvedPlaceholders(string? text) => ...;
}
```

#### ★★ 四条铁律（压住复杂度的关键）

| # | 铁律 | 违反后果 |
|---|------|---------|
| **1** | **⛔ 不做分支、不做循环、不做并行** —— 只做「顺序拼装 + 一次 LLM 调用」 | 一旦有分支 ⇒ 你在**重造工作流**，而 `wf_workflow_definition` 已经 **0 行**（此路已废） |
| **2** | **⛔ 不写「怎么填」以外的逻辑** —— 取值逻辑留在层 1 的 `SourceSpec` | 规则里开始出现「如果企业没上传执照则…」⇒ 复杂度失控 |
| **3** | **✅ 输出必须是结构化 JSON**（`{FieldCode: value}`），并按 `FieldCode` 回填 | 自由文本 ⇒ 无法回填 ⇒ 只能人工复制粘贴 |
| **4** | **✅ 复用 `{{__FILL__.*}}` 占位符 + 漏填检测** | 自造一套 ⇒ 与 NC 双轨，维护成本翻倍 |

### 6.3 两层如何协作（填充流程 —— 本页只负责「定义」，流程供 ⑥ 执行期使用）

```
① 加载模板 + 锚点清单（cert_doc_template / _anchor）
② 加载/生成全局参数快照（cert_fill_param_value，企业×阶段）   ← ★ 物化，不实时查
③ 跑全文填写规则（若有 FillPromptCode）
      DocFillPromptAssembler → Prompt → LLM → {FieldCode: 值}   ← ★ 每模板一次
④ 锚点依赖拓扑排序（self 引用 → 有环则拒绝）
⑤ 逐锚点解析 SourceSpec（有序回退）
      · global  → 从 ② 取
      · ai      → 从 ③ 的字典取（★ 这就是"没配单元规则"的锚点的隐式来源）
      · profile → 从企业资料画像取（置信度不足视为未命中）
      · compute → 计算
      · manual  → 先看 ③ 有没有值 → 有就用，没有挂待办
⑥ 按 WriteMode 写回（★ 一次打开 / 一次保存）
⑦ 残留校验：{{XXX}} 残留 + YZH_Mark 残留 → 报"未填充项"
```

> **★ 步骤 ③ 与 ⑤ 的顺序不能颠倒** —— 全文规则是**批量供给**，单元级是**逐点解析**。先供给，再解析。

### 7.1 七步闭环（`20` 号 §3.3 的落地版）

```
① 左树选标准文档「风险管理报告」
② [下载标准文档] → 下载 /…/4记录文件/风险管理报告.doc        ← 复用现有端点
③ 本地 Word 打开 → 另存为 .docx
     → 加 {{标签}}（标量）/ 书签 ROW_xxx（表格区）/ 套 YZH_Mark 样式（人工填写区）
```

### 7.2 扫描器（零 LLM）

**手段**：确定性解析（NPOI）
**产物**：锚点清单

| 文件类型 | 扫描目标 | 定位方式 |
|---------|---------|---------|
| Word | 标量 | 段内 `{{FieldCode}}`（**必须先做 W9 字符索引映射**，见 §11） |
| Word | 表格区域 | 书签 `ROW_xxx`（`bookmarkStart`/`bookmarkEnd` 同 id） |
| Word | 页眉/页脚 | `HeaderList` 遍历（**只替换，不新建**） |
| Word | 人工填写区 | `YZH_Mark` 字符样式 |
| Excel | 标量 | 单元格内 `{{FieldCode}}` |
| Excel | 数据区 | 连续矩形 + 样例行（`{{table:items}}` 标记起始行） |
| Excel | 合计 | `{{SUM_ROWS}}` 这类 token（**禁硬坐标**） |

**★ 已实现可复用**：`Office/Word/WordDocumentScanner.cs` / `Excel/ExcelSheetScanner.cs`

（因为它可能已有填过的值 —— `21` 号 §4.3）。

## 十一、风险与已知坑（**照实报出**）

### 11.1 高危（会静默出错）

| # | 坑 | 后果 | 规避 |
|---|----|------|------|
| **R1** | **`{{Token}}` 跨 run（W9）** | Word 把 `{{ENT_NAME}}` 拆成多个 `<w:r>` ⇒ **扫描找得到、写入找不到** | 必须做**字符索引映射法**（`26` 号 §3.4.6 已给出算法）；⛔ **不要合并 run**（会破坏作者刻意的字符级差异） |
| **R2** | `XWPFTable.Rows` 是**缓存列表** | 直接改 `CT_Tbl` ⇒ `trList=3` 但 `Rows.Count=2`，**不报错** | 必须 `table.AddRow(new XWPFTableRow(clone, table), pos)` |
| **R3** | `XWPFTableCell.SetText()` 后同会话读回**空串** | 扫描器误判 | 走段落 API：`cell.Paragraphs[0].Runs[0].SetText(...)` |
| **R4** | 并发写同行 | 互相覆盖，**日志却成功** | **列级写入** `UpdateAsync(entity, cols)`（陷阱 ㉕） |
| **R5** | DTO 漏 `[JsonPropertyName]` | 前端读 `undefined`，**零报错** | 逐字段标注（陷阱 ⑲） |
| **R6** | `PathBuilder` 身份段为空 | 路径拼错、文件散落 | `PathBuilder` 会**抛异常**（已设计），⛔ 不要吞掉 |

### 11.2 中危（影响体验）

| # | 坑 | 说明 |
|---|----|------|
