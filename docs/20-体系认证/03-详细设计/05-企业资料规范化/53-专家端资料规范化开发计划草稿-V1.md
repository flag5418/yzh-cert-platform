# 开发计划草稿：企业资料规范化（专家端）- V1

> 本草稿是「界面行为已定」前提下，关于**后端应该建什么 / 表长什么样 / 接口产什么**的开发推进稿。
> 目的不是写实现，而是把当前已完成的各模块、已定的操作/审核行为、以及尚未落地的规范化链路之间的接口与表结构约定先对齐。
> 编码优先级顺序按「能复用现成实现的先复用 → 缺的接口/表慢慢补」，而不是按文档编号。

## 1. 范围锚点与当前事实

- 本模块在专家端对应菜单/路由意向大致为 `AUDIT_MENU_12` / `/enterprise-normalize`（菜单设计稿里已有占位意向）。
- 当前专家端已有实现至少包括：
  - 企业管理（`/enterprises`）
  - 企业-阶段-标准关联（`/enterprise-stages`）
  - 企业原始资料管理（`/enterprise-original`），含上传/转换/分析/画像雏形
  - 企业全局参数定义（`/enterprise-fill-params`）
  - 任务中心、NC结果、报告结果、资料库、组织与成员、系统设置等
- 后台（Admin）侧已有实现至少包括：
  - 标准文档填写规则（`/business/doc-fill-rule`）相关的模板/契约/锚点/提示词等控制器与实体
  - 标准目录文件/配置/文件夹实体，以及转换/提取链路
  - 企业资料规范化执行器雏形（`EnterpriseDocNormalizationExecutor`）以及适配器注册
  - AI建议表（`cert_doc_ai_suggestion`）、填写日志（`cert_doc_fill_log`）等
- 当前的关键事实是：
  - 标准目录文件行已经是 **YZH-STD-ENT 统一架构**，用 `EnterpriseCode` 区分模板行与企业上传行
  - 启用/禁用字段统一为 `IsValid`，删除统一为软删除（或硬删除的明确例外）
  - 定位/删除/更新/传参走 `Code`，`Id` 不进 WHERE/关联/存在性判定
  - 字符集/排序规则统一为 `utf8mb4` + `utf8mb4_general_ci`

## 2. 已定行为 → 需要哪些后端能力的初步反推

专家端操作/审核行为若已基本固定，那么后端缺的不再是“功能轮廓”，而是：

1. **选哪家企业、哪阶段/标准/文档槽位时，后端能返回一致的规范化上下文**
   - 需要：企业、阶段、标准、标准目录文件槽位、现有原作业状态的一次性或分段查询能力
2. **把原始资料画像翻译成“哪个标准文档槽位由哪些来源支持”**
   - 需要：画像 → 标准文档槽位匹配/候选视图、置信度与依据信息
3. **对每个标准文档槽位，能看到候选来源、AI建议、填写计划、锁定/确认状态**
   - 需要：规范化任务/候选/建议/填写日志/产物状态的读写接口
4. **人工审核能做“确认/改写/重新生成/锁定/跳过”等动作，并且有留痕**
   - 需要：审核动作记录表与接口，以及对Norm执行器任务状态的查询/控制能力
5. **确定产物后，能写回标准目录文件实例侧（企业行）并保留版本/路径/状态**
   - 需要：实例行创建/更新、产物路径登记、状态机更新能力
6. **固定文档/混合文档/可编写文档的处理分支在现有契约/模板/锚点体系中能正确映射**
   - 需要：标准文档契约表、模板/锚点映射、以及Norm执行器对这些元数据的读取一致性

结论：**前端缺的不是“按钮怎么排”，而是上面 1-6 对应的读写契约与状态流转表。**

## 3. 表结构方向（不代替DDL，先列主体与归属）

### 3.1 已有且应复用的表（先锚定）

- `cert_enterprise`：企业档案
- `cert_cert_stage`：认证阶段
- `cert_enterprise_stage`：企业-阶段-标准关联（专家端侧）
- `cert_iso_standard`：ISO标准
- `cert_standard_directory_config`：目录配置（机构/标准/阶段）
- `cert_standard_directory_file`：标准目录文件行（模板行 + 企业上传行共用，`EnterpriseCode`区分）
- `cert_standard_doc_contract`：标准侧文档契约（标签/作用/分类/匹配提示/固定文档分型等）
- `cert_doc_template` / `cert_doc_template_anchor`：填写模板与锚点
- `cert_doc_fill_prompt`：全文提示词（如适用）
- `cert_enterprise_original_file`：企业原始资料文件行
- `cert_enterprise_doc_profile`：原始资料画像（L3）
- `cert_doc_ai_suggestion`：AI建议/候选（已有实体）
- `cert_doc_fill_log`：填写执行日志（已有实体）
- `cert_tag_dict`：标签字典（若规范化需要受控标签）
- `cert_standard_directory_folder`：标准目录文件夹（如需树结构）

### 3.2 若尚未建或尚未约定的 likely 表（草案粒度）

这部分应以“是否真的要单独建表 / 是否复用已有表”为准，草稿里先把候选列出来：

- **规范化任务/批次上下文表**（若队列 payload 自身不够表达专家端可读的任务视图）：
  - 至少应能关联：企业/阶段/标准/目录配置/批次状态/当前完成度/可信度/产物路径摘要
- **规范化候选/匹配决策视图或表**（画像 → 标准文档槽位的对应关系）：
  - 核心字段倾向：候选 Code / 企业 Code / 阶段 Code / 标准 Code / 标准文件 Code(`StandardFileCode`) / 画像 Code / 候选来源文件 / 置信度 / 状态 / 审核结论
- **规范化审核动作留痕表**（确认/改写/重跑/锁定/解锁/跳过等）：
  - 目标是“只追加、可审计”，不鼓励可删改的状态表记流转
- **实例侧填写结果的附加元数据表**（如需记录字段级来源/可信度/人工覆盖，视是否复用`cert_doc_fill_value`或新增决定）：
  - 若能复用已有填写取值账本就复用，否则再建

### 3.3 表设计约束（必须遵守）

- 所有启用/禁用语义一律 `IsValid`，不引入 `Enable`
- 主键/业务键/定位以 `Code` 为准，`Id` 仅作自增标识
- 所有新建表字符集/排序规则显式 `utf8mb4` + `utf8mb4_general_ci`
- 表归属要分清：共享层 / Admin侧 / Auditor侧，尽量不把专家端独占表放到共享层里造成混淆
- 能复用现有契约/画像/建议/日志结构的地方，优先复用，不重复发明同义字段

## 4. 接口方向（待约定候选集）

### 4.1 读取侧（专家端先需要的）

- 规范化上下文加载：企业/阶段/标准/目录配置/标准文件槽位列表及其基础状态
- 标准文档槽位视图：每个槽位的当前实例状态、契约信息、模板/锚点是否存在、固定文档分型
- 画像→候选映射：给定企业/阶段/标准下，哪些画像/原始文件可作为候选来源，附带置信度与依据
- 规范化任务/批次状态查询：运行中/已完成/失败/部分完成的任务视图，含完成度与可信度摘要
- AI建议/人工选定/留痕查询：每个槽位/锚点维度的建议候选与人工决策记录
- 产物下载/预览/版本信息：已生成文档的路径、版本、可访问性

### 4.2 写侧（专家端审核动作）

- 确认/选定候选
- 人工改写值
- 重新生成某文档/某批次
- 锁定/解锁
- 跳过/标记为不适用
- 留痕必须随写操作一起落下，尤其是“人工最终裁决”类动作

### 4.3 接口风格约定（倾向）

- 信封与字段风格尽量跟现有契约保持一致，减少前后端额外翻译
- 枚举值/状态值要有唯一出处，避免多处散落定义
- 成功/失败语义明确区分，业务失败不靠 HTTP 状态码押注
- 返回字段按“专家端实际消费顺序”组织，而不是按数据库列顺便返回

## 5. 复用与隔离的判断

### 5.1 可以/应该复用的部分

- 标准目录文件/配置的读取与实例行写回
- 契约表/模板/锚点/提示词这套“规则侧”元数据结构（若规范化只是消费它们）
- 原始资料转换/分析/画像链路（已有雏形）
- AI建议/填写日志这类留痕结构
- 队列/任务执行器注册方式（若 Norm 任务已有适配器）

### 5.2 要小心隔离的部分

- 专家端独有的规范化任务视图、审核留痕、候选/决策语义，不要强行揉进后台管理侧的规则定义控制器里
- 标准侧“契约定义”与企业侧“规范化执行/审核”语义要分开，避免一个接口同时承担定义与审核
- 若既有 Norm 执行器还很初步，暂时不要让前端接口依赖它内部细节；先把专家端可读的状态视图约定起来

## 6. 当前最可能的阻塞项

按现状看，优先级最高的阻塞通常不在页面长不长，而在于：

1. **标准文档契约/模板/锚点是否已经为规范化提供了足够的元数据**
   - 若契约/模板/锚点还缺，那么规范化页面先打开就是空的或只能展示部分状态
2. **规范化任务/候选/审核留痕是否已有表与接口**
   - 若没有，专家端“看候选/确认/改写/重跑”就没有落脚点
3. **画像 → 标准文档槽位的对应关系是否有明确视图/接口**
   - 这是操作流的核心映射，若模糊，前端容易拍错
4. **菜单/路由/角色是否与本模块约定同步落地**
   - 页面能打开、菜单能点、权限能过，三者要一起对齐
5. **固定文档/混合文档/可编写文档的分支规则是否在契约与 Norm 侧一致**
   - 否则前端显示与后端处理会产生静默偏差

## 7. 建议推进路线（草稿）

1. 先坐下来把**当前已有实现**和**专家端已定行为**逐项对照，确认哪些读写能力已有、哪些确实缺
2. 缺的能力里，先定义**最薄的接口/表约定**，够前端把已定行为串起来即可，不要一次性建成“理想完整版”
   - 尤其是：上下文加载、槽位状态视图、候选/建议视图、审核动作留痕、实例写回
3. 约定定后，菜单/路由/角色/接口一起落地，避免“页面有、路由有、接口缺、权限斜”
4. Norm执行器/契约/模板若还不稳，把它作为后续阶段而非本阶段唯一依赖，先保证专家端操作流有接口可对
5. 固定文档/混合文档分支、完成度/可信度口径、留痕规则这些容易静默错的点，单独列成约定，不要靠口头

## 8. 待用户拍的关键点

- 当前专家端已定行为中，是否已经明确包含“规范化任务/候选/确认/改写/重跑/锁定”这条主流程，还是部分还是雏形
- 规范化上下文里的标准文档槽位，是否默认复用现有的标准目录文件 + 契约 + 模板/锚点体系，还是需要额外的规范化专属元数据
- 候选与审核决策，是直接上视图表/接口，还是先基于画像+建议拼一个轻量视图
- 留痕需求中，哪些是本阶段必选项（例如确认/改写/重跑/锁定），哪些可以延后
- 是否接受先用“最薄接口 + 视图表/留痕表”起步，后续再补充更细的字段与统计口径
