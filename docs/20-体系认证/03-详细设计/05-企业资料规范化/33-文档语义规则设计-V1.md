## 〇、我对本功能的理解（重述，供你校验）

> 这一节是本文档存在的理由 —— 如果这里理解错了，后面全部作废。

### 0.1 问题的形状

| 侧 | 现状 | 规模 |
|----|------|------|
| **标准侧** | 一个标准 + 一个阶段下的**空白标准文档是固定的** | 实测 ISO13485：**167 个** |
| **企业侧** | 企业材料**很乱、不可控**（命名混乱、组织无序、格式各异） | **200 / 300 / 更多** |

要做的事：**拿 N 份乱的企业文档，去填 M 个固定的标准文档**（M≈100~167）。

### 0.2 这两条提示词的真正作用（★ 核心）

它不是"生成一段文字"，而是：

> **把「300 份乱的企业文档」和「100 个固定的标准文档」放进同一个语义坐标系里，
> 使得给定一个标准文档，能快速捞出 5~10 份（或全部接近的）最该读的企业文档去试填。**

坐标系的两个轴：

| 轴 | 角色 | 解决什么 |
|----|------|---------|
| **标签（分组）** | **召回 / 过滤键**（倒排索引） | 把 300 份砍到几十份 —— 解决"太多看不过来" |
| **作用** | **判断依据 + 填写时的取值参考** | 从几十份里挑出 5~10 份 —— 解决"哪份真的能填"，并告诉填写环节"该从里面取什么" |

**用法（你点 2 的原话）**：开始编写一个标准文档时 → **先用该标准文档的标签去过滤企业文档，形成语义清单** → AI 判断 → 筛 5~10 份或全部接近的 → **试填**。效率与准确性同时提升。

### 0.3 为什么这套规则必须两侧同用（你点 2 的关键）

因为**过滤是"两侧做交集"**：

```
标准文档 A 的标签 ──┐
                   ├── 交集 → 候选清单 → AI 精判 → 试填
企业文档 B 的标签 ──┘
```

**两侧必须在同一个坐标系里，交集才成立。** 标准侧用一套标签、企业侧用另一套 → 过滤无从谈起。

> 这正是既有设计 14 号 **D14「多标签体系（受控字典，双侧同规则）」** 的原文：
> 「企业文档标签 = 画像自动打；标准文档标签 = 契约维护（AI 从文件夹路径 + DocPurpose 建议初值，人工确认）。**同字典同规则 → 两侧可比**。」
> 「标签即倒排索引 —— 一个标签直接捞出两侧集合；**标签重叠是真配对的最强先行信号**。」

### 0.4 为什么一定要按标准建（你点 3 的原话）

- **不同标准，对应的标签（文件夹）不一样** —— ISO13485 有「检验作业指导书」，ISO9001 没有；
- **不同标准，文档的作用也不一样** —— 同一份「内审计划」在 13485 和 9001 下的审核关注点不同。

⇒ 标签集合、作用描述，**都是"标准 × 文档"的函数**，必须按标准生成、按标准维护。

### 0.5 什么时候用（你点 4 的两条链）

```
【标准侧 —— 定义填写规则时，一次性】
"标准文档填写规则定义" 时 → 按标准调该提示词 → 得到该标准每个文档的 标签 + 作用
   → 人工干预 → 保存

【企业侧 —— 上传后，自动】
企业上传资料 → 自动调同一套规则 → 每份企业文档的 分组 + 作用
   → 转 markdown / pdf（供后续查阅与提取）
```

### 0.6 页面形态（你点 5）

**左树右表**：左 = 标准树；右 = 两条提示词（标题/分组提示词 + 文档作用提示词），**由元提示词自动生成**；另有「上传文件测试」：上传 → **先转 markdown** → 调 AI 分析得分组与作用 → **自动删除该文件**。

### 0.7 流水线顺序（★ 你已纠正的铁律）

```
拿到文档 → ① 先转 markdown → ② 再按提示词分析出 标签 + 作用
```

⛔ **不是**"先分析标签和作用，再生成 markdown"。

### 0.8 作用必须包含哪几部分（★ 你已纠正）

- **这个文档的核心内容是什么**
- **这个文档包含了哪些信息**

> 只有这样，**语义分析匹配填写的时候才有参考意义** —— 标准文档需要什么信息（需求），企业文档提供什么信息（供给），才能算覆盖度。

### 0.9 ★ 双侧职责与两条流程（V1.2 增补，34 号 §〇/§一）

> **V1.1 最大的叙述缺口：把本模块画成"一条直通流水线"。实际是「双侧 × 双流程」。**

#### （1）双侧职责

| | **后台管理（admin · 9990）—— 定义侧** | **企业/专家端（auditor · 9991）—— 执行侧** |
|---|---|---|
| 别名 | **配置世界** | **数据世界** |
| 本模块在该侧做什么 | 维护 `cert_tag_dict` 标签字典 + 标准文档契约的 `TagsJson`/`DocPurpose`/`InfoItemsJson` | 上传 → ⓪ 策略判定 → 转 MD → 跑**同一套**提示词 → 落画像 → 进候选 |
| 数据主键 | `StandardCode` / 全局无租户 | **必带 `EnterpriseCode`** |
| 菜单 | **`MENU_00210` 文档语义规则**（→ `MENU_00302` 规则定义，OrderNo 250，方案甲） | `MENU_AUD_10` 企业全局参数 / ⑦ 裁决（26 号 ⑤⑥ 分册） |
| 改动影响 | 改一次，**所有企业下一次分析生效** | 只影响本企业本批次 |

> **两侧必须用同一套提示词、同一本字典** —— 这就是 14 号 **D14** 的原文（§0.3），也是 34 号 §一 的第一性切分。

#### （2）两条流程（34 号 §2.3，`03` 号泳道已同步勘误）

```text
 ① 上传 → ② 转 MD → ⓪ AnalyzePolicy → ③ 语义画像 → ④⑤⑥ 召回/精排/冲突 → ⑦ 人工裁决
                                                                        │
                                            ┌───────────────────────────┴──────────────────────┐
                                            │                                                  │
                              DocCategory = fixed / hybrid                          DocCategory = editable
                                            │                                                  │
                               【匹配即终点】短路 ✅                               ⑧ 定向提取（既有规则链）
                               · 匹到那份营业执照 = 完成                                    │
                               · 最多 OCR 抽字段供引用                             ⑨ 契约填充 → docx/xlsx
                               · **不跑 `doc_content`**                                     版本归档 + 审计
                               · 不进 ⑧⑨
```

**⇒ 本模块对两类文档的贡献不同（34 号 §6.5）**：

| | `fixed` 固定文档 | `editable` 可编写文档 |
|---|---|---|
| `AnalyzePolicy` | **`skip`**（指纹接管） | `analyze` |
| `doc_content`（作用提示词） | **不跑** | **跑**（主战场） |
| 本模块贡献 | 仅 `MatchFeature` 编号前缀（L0）+ 标签 | 标签 + 四段作用 + `InfoItems` |

> ⚠️ **`AnalyzePolicy=skip` 的正确语义（V1.2 更正）**：它是 **`fixed`/`editable` 类型分流 + 全局参数已覆盖** 的直接体现（26 号补 6 原文），**成本节省是副产品**。V1.1 曾把它描述成"成本优化"，是理解偏差。

## 二、流水线（对齐 26 号 §3.5，铁律：先 md 后分析）

### 2.1 本模块在 5 段流水线中的位置

```
⓪ 策略判定  AnalyzePolicy = analyze / skip / ignore   ← 26 号 §3.5.3（AI 建议 + 人工确认）
① 落原始文件 → MinIO enterprise-original-source/
② 格式归一   → .doc/.xls → .docx/.xlsx
③ 转 Markdown → MinIO {同路径}/markdown/   ★ 先转
④ ★ 语义分析 → 本模块：产出 分组(标签) + 作用四段 + suggestedPolicy   ★ 后分析
⑤ 落画像     → cert_enterprise_doc_profile
⑥ 进匹配候选 → skip / ignore 不进候选
```

**铁律**

| # | 内容 |
|---|------|
| **L1** | ④ 的输入**只能是 ③ 的 markdown**；⛔ 不读原始文件（26 号约束 A-1） |
| **L2** | ⛔ 顺序不可逆：**先转 markdown，再分析** |
| **L3** | 同一套提示词、同一份输出契约，**标准侧 / 企业侧各跑一次**（D14 双侧同规则） |
| **L4** | 匹配与填充**只读画像 + markdown，永不重读原始文件**（一次提取、多次复用） |

### 2.2 标准侧流水线（对称）

```
选标准 → ① 元提示词按标准生成（2 条提示词 + 标签初值）
       → ② 对该标准 167 个标准文档跑分析（标准文档已有 markdown，见 06 号：cert_standard_directory_file.MarkdownPath）
       → ③ 表格展示 → 人工干预 → 保存（契约表）
```

> ⚠️ 标准侧**已有**「转换 → markdown」链路（`cert_standard_directory_file.MarkdownPath / MarkdownStatus`），
> 26 号明文：「⛔ 不要把两套转换链写成两份代码」—— 企业侧只是**多挂一个语义分析后置步骤**。

### 2.3 测试链（磁盘即弃 · Markdown 落 Redis 复用）★ V1.3 勘误

```
上传任意文件 → 自动转 markdown → 落 Redis(8h) → 调 AI（喂 markdown）→ 返回 分组 + 作用四段 → 删磁盘临时目录
      ↓ 改提示词重测：只回传 cacheKey，**零转换**直接复用
```

- **磁盘即弃**：`DocumentConvertClient.ConvertToMarkdownAsync` finally 删除 `{_workRoot}/{tool}/tmp/{sessionId}`，
  不落 MinIO、不落 DB、不留痕。
- **★ Markdown 不弃（V1.3 勘误，用户裁决 ③）**：V1.2 及更早写的「测试链转完 MD 即弃」是**错的**。
  转换结果以 `{ "fileName", "markdown" }[]` JSON 存进 Redis（前缀 `prompt_md:`，TTL 8h），
  后端 `TestAsync` 回传 `cacheKey`，前端**只传 `cacheKey` 不传 `files`** 即可不重新转换地反复调提示词 ——
  这是「改提示词 → 再分析」迭代闭环的**前置条件**（否则每改一个字都要重新转一遍文件）。
- ⚠️ **与 ② 的区别**：生产链留的是 markdown **文件**（26 号 L2 层 `markdown/` + `pdf/`，供查阅与提取）；
  测试链留的是 **Redis 里的文本**（8h 自动过期）。两者不冲突、不互相覆盖。
- 缓存过期 / 脏数据 → 后端返回「测试缓存已过期或不存在，请重新上传文件（缓存保留 8 小时）」，
  **⛔ 不静默转换**（避免用户以为在测 A、其实后端悄悄跑了 B）。

## 三、语义模型

### 3.1 标签（分组）

**定义**：标签 = 文档的**语义分组**，受控词表，**双侧同字典同规则**（D14）。

**既有 DDL**：`cert_tag_dict`（21 号 §4.3）

| 列 | 说明 |
|----|------|
| `TagCode` | 编码，`PascalCase`（如 `RecordInternalAudit`），`uk_tag_code` |
| `TagName` | 显示名（如 `内审记录`） |
| `TagGroup` | 分组：`文档类型` / `业务域` / `标准条款` |
| `ApplicableSide` | `standard` / `enterprise` / `both` |
| `Sort` / `Status` / `IsValid` | 排序 / 状态 / 有效性（铁律九） |

**种子来源**（14 号 D14）：
1. **标准目录文件夹树**（实测：1质量手册 / 2程序文件 / 3制度文件 / 4记录文件 / 技术类 / 生产类 / 质量类 / 其它 …）
2. **体系域**（质量 / 环境 / 职业健康安全）
3. **ISO 条款业务过程**（文件控制 / 内审 / 管理评审 / 培训 / 设备 / 计量 / 不合格品控制 …）

**三层分类**：形态 × 体系域 × 业务过程；**一文档多标签**。

**★ 关键约束（提示词必须写死）**：
> 「**约束 LLM 只能从字典选**，允许**建议新词 → 进待审核，不直接入库**。」（14 号 D14）

否则 = 26 号 §4.3 警告的「LLM 每次返回不同分类名 ⇒ **不可用**而非不准确」。

**★ 实测支撑（编号前缀是确定性信号）**：

```
XASL-QR-014 年度内审计划.doc        ← QR = 记录
XASL-QR-013 管理评审报告.doc
XASL-QR-027 成品检验记录.xlsx
陪审人员.doc / 风险管理报告.doc      ← 无编号，需 AI 判
```

⇒ **L0 确定性规则先跑**（编号前缀 + 文件夹路径 → 直接得标签，0 次 AI），只对不确定项调 AI。这与 25 号纸面实验「确定性锚点占比 98.6%，能用规则的不用 AI」同一方法论。

**★ 增量 C（按标准裁剪，待裁决 Q1）**：`cert_tag_dict` 是全局字典，但"不同标准标签不一样"。三选一：

| 方案 | 做法 | 影响 |
|------|------|------|
| C1 | 加 `StandardCodes` json 列（`["…"]`，空=全标准通用） | ⚠️ 改既有 DDL |
| C2 | 不改表，靠 `ApplicableSide` + 按标准启用的子集（`Status` 不够表达） | 无法表达"13485 才有检验作业指导书" |
| C3 | 提示词注入 `{{tag_list}}` 时按标准过滤（过滤条件另存配置） | 不改表，但过滤规则散落 |

**我的建议**：**C1**（加一列 json），理由：语义明确、查询用 `JSON_CONTAINS`，且不破坏 `uk_tag_code` 全局唯一。

### 3.2 作用 = 既有三段式 + 新增第四段

**既有（05 号 §2.1，不要改）**：

```text
① 这是什么文档（核心内容）
   ISO9001 质量管理体系的质量手册，覆盖体系范围、职责、过程相互作用。
② 审核关注点
   版本/编制审批齐全、与实际一致、引用标准现行有效。
③ 数据来源口径
   由质量部编制、管理者代表批准；通常 1 年内改版一次。
```

- 100–400 字；`DocPurpose text` 承载；
- ① 供**精排 LLM**；② 供人工理解；③ 供**画像链参照（两侧同口径可直接比对）**。

**★ 本轮新增第四段（增量 B，你的原话）**：

```text
④ 包含信息（要素清单）
   提供：文件编号、版本号、发布日期、编制人、审批人、
        体系范围、职责分工、过程相互作用矩阵 …
   —— 供匹配时算覆盖度，供填写时知道"该取什么"
```

| 段 | 载体 | 给谁读 | 用途 |
|----|------|--------|------|
| ① 是什么 / 核心内容 | `DocPurpose` text | LLM | 语义吻合判断 |
| ② 审核关注点 | `DocPurpose` text | 人工 | 理解 AI 为什么关注这些 |
| ③ 来源口径 | `DocPurpose` text | 画像链 | **两侧同口径可比** |
| ④ **包含信息** | `DocPurpose` text 摘要 + **`InfoItemsJson`** | **匹配 / 填写** | ★ 覆盖度计算 + 取值参考 |

**结论**：`DocPurpose text` 存**四段渲染文本**（人读），`InfoItemsJson json` 存**结构化要素清单**（机器读）。
⛔ 不要把 `DocPurpose` 改成 json —— 破坏 05/06 号既有 text 语义与两侧可比性。

### 3.3 输出 JSON Schema（★ 两条提示词共享的唯一契约）

**对齐 06 号 §4.1，增补 `tags` 与 `infoItems`**（14 号 D14 已预告「画像输出 schema 加 `tags: []`」）：

```json
{
  "tags": [
    { "tagCode": "RecordInternalAudit", "tagName": "内审记录",
      "confidence": 0.92, "reason": "标题含「内审」，编号前缀 XASL-QR" }
  ],
  "purpose": "【是什么】…【审核关注点】…【来源口径】…【包含信息】年度、审核组长、审核范围、审核日期…",
  "infoItems": [
    { "itemName": "年度",       "itemDesc": "所覆盖年度",   "valueType": "number", "isKey": true  },
    { "itemName": "审核组长",    "itemDesc": "本次内审负责人", "valueType": "org",    "isKey": true  },
    { "itemName": "审核日期",    "itemDesc": "计划起止日期",  "valueType": "date",   "isKey": false }
  ],
  "typeGuess": "内审计划",
  "fields":  [ { "name": "文件编号", "key": "wen_jian_bian_hao", "value": "XASL-QR-014", "dataType": "string", "confidence": 0.95, "isKeyField": true } ],
  "tables":  [ { "index": 0, "name": "审核安排", "header": ["日期","部门","审核员"], "rowCount": 8, "columnCount": 3, "confidence": 0.9 } ],
  "suggestedPolicy": "analyze",
  "policyReason": "",
  "confidence": 0.9
}
```

**分组提示词可只出子集**（`tags` + `suggestedPolicy`，不出 `fields`/`tables`）—— 见 §3.4。

**后端校验**（照抄 06 号 §4.1 六条）：截断抢救 → `tags[].tagCode` **必须 ∈ `cert_tag_dict`**（不合法 → 置 `OTHER` 并记 Message，**不整单失败**）→ 分数 clamp `[0,1]` `ROUND(,2)` → `tables` 超 50 行截断 → `fields` 超 100 条截断 → `purpose` 缺失则 `Confidence ≤ 0.5` 标 `[缺作用]`。

### 3.4 两条提示词是否合并（★ 你犹豫的点，三方案对比）

| 方案 | 提示词数 | 输入粒度 | 优点 | 缺点 |
|------|---------|---------|------|------|
| **A 合并 1 条** | 1 | 单份 markdown 全文 | 一次调用、天然一致、页面最简、两侧同规则最纯粹 | 每份都吃全文（贵）；**丢掉文件名/编号/文件夹的确定性信号**（L0 白费）；无法"先便宜粗筛再贵精判" |
| **B 分 2 条**（既有描述） | 2 | **分组 = 文件名+标题清单（批量）**；**作用 = 单份全文** | ① 分组极便宜可批量 ② 分组先跑 → 定 `AnalyzePolicy` → **省掉 skip/ignore 的作用调用**（26 号补 6 收益）③ 编号前缀 L0 规则天然嵌进分组 | 两次调用；可能出现「分组说 A、作用写得像 B」不一致 |
| **C 1 条 + 2 模式** | 1 | `Mode=tag_only`（吃清单）/ `Mode=full`（吃全文） | 一个模板一处维护、输出契约唯一、又保留分档 | 模板里要写两段规则，复杂度高 |

**我的建议**：**B（保持两条）**，理由按权重：

1. **成本差一个量级**：分组吃"文件名清单"（每批约 1K tokens），作用吃"全文"（每份 3~30K）；300 份若都吃全文 = 昂贵。
2. **与 26 号补 6 收益直接挂钩**：分组先跑出 `suggestedPolicy=skip/ignore` → 这些文档**根本不调作用提示词**。
3. **页面形态你已描述为两条**，UI 已按两条设计。
4. **B 的不一致风险有对策**：作用提示词的输出 schema **也含 `tags`**，后端交叉校验 —— 若两者 `tagCode` 不一致 → 标 `[标签冲突]` 并降 `Confidence`，进人工。

> **若你倾向 A（合并）**：页面右表从 2 行变 1 行；输出 schema 不变；成本按 §4.5 分档退回"只对低置信度跑全文"。两种都能实现，差异在成本与页面复杂度，**不影响数据库设计**。

> `DOC_CATEGORY` = **粗分类枚举**（体系文件/记录/资质证照/报告，对应 `DocCategory` 之外的展示维度）；
> `DOC_PURPOSE` = **作用意图枚举**（证明什么）。三者不冲突，但**必须写清谁是召回键** —— 我认为是 `cert_tag_dict`。
