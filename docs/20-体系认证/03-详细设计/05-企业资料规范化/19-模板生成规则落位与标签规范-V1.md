# 模板生成规则 — 落位决策与标签规范

> **版本**：V1 | **日期**：2026-10-02 | **状态**：待裁决（2 条）
> **问题来源**：`/business/doc-extraction-rule` 页面点击「开始分析」时，是否应同时承载「标准文档分类识别 / 作用分析 / 生成规则」？还是独立建菜单？Word/Excel 标签怎么设，后台才能解析出要填的字段与表格？
> **结论一句话**：**你其实在同一条流程里混了三件事。** 其中「分类/作用/字段提取」**应当留在现有页面**（它本来就属于读侧），「生成规则」**必须独立成菜单**（写侧，输入物与手段完全不同）；但**字段/表格定义两侧共用一份**。

## 二、你混在一起的三件事（**本节是核心**）

你说「点击开始分析时，做分类识别 + 作用分析 + 生成规则」——这实际是**三件归属不同的事**：

| # | 事 | 本质 | 输入物 | 手段 | 正确归属 |
|---|----|------|--------|------|----------|
| **A** | 标准文档**分类识别** + **作用分析** | 描述**标准文档自己是谁** | 有数据的标准文档 | LLM 推断 | **契约表**（`cert_standard_doc_contract` 的 `DocCategory` / `DocPurpose`） |
| **B** | **字段/表格定义** | 描述**这份文档有哪些数据位** | 有数据的标准文档 | LLM 推断 + 人工确认 | **字段/表格定义表**（`cert_doc_field_def` / `_table_def`）—— **两侧共用** |
| **C** | **生成规则**（模板锚点） | 描述**值该写到模板的哪个位置** | **带标签的空白模板** | **确定性扫描（零 LLM）** | **模板侧新表**（`cert_doc_template_scan` / `_part`） |

### 为什么 A/B 留在现有页面是对的

A 和 B 的输入物都是「**已经有数据的标准文档**」，手段都是「**LLM 从内容推断**」，都需要**人工确认**（AI 会猜错）。这与现有页面的左树（168 份标准文件）、中栏（文档预览）、右栏（分析 + 验证）**完全匹配**。**A 只是在 B 的基础上多产两个字段（分类、作用），不需要新页面。**

> ⚠️ 但要注意：**A 的产物该落 `契约表`，不是 `提取规则表`**。现在契约表还没建（05 册规划，0 命中），所以要么先建契约表、要么暂存 `cert_doc_extraction_rule` 的 `Remark`。**建议先建契约表**——`DocPurpose` 是匹配精排的必要输入，不能一直挂在规则表上。

### 为什么 C 必须独立

| 冲突点 | 现有页面 | 生成规则 | 后果 |
|--------|----------|----------|------|
| **方向** | 读（取出值） | 写（填入值） | 一个页面两个方向，按钮语义分裂 |
| **输入物** | 左树里的**标准目录文件**（168 个模板行） | **独立上传的模板包** | 模板不在那棵树里，左树无节点可选 |
| **手段** | LLM 推断（不确定，要「验证」） | **确定性扫描**（正则 + 书签 + 区域，零 LLM） | 「开始分析」按钮语义冲突：分析内容？还是扫标签？ |
| **产物** | Prompt + `SampleData` | **锚点清单**（锚点 → FieldCode 映射） | 表结构完全不同 |
| **右栏** | 「提示词与验证」 | **不需要 Prompt**（生成不靠 Prompt） | 页签整块无意义 |
| **作用域键** | 四元组 `(OrgCode, StandardCode, StageCode, StandardFileCode)` | 模板**跨标准复用**（「培训记录表」可被 ISO9001 与 ISO14001 共用） | 键模型冲突 |
| **生命周期** | 随标准目录版本 | 随**模板包版本**（换版 → 重扫 + diff 继承） | 版本模型冲突 |

**结论**：把 C 塞进现有页面，会让一个页面同时承载「两个方向、两种输入物、一个有 LLM 一个零 LLM、两套作用域键」——这是**必然的返工**。

### 为什么字段定义（B）必须共用

- 提取规则说：「我要从企业文档里**抽出** `ENT_NAME`」
- 生成规则说：「我要把 `ENT_NAME` **填进** `{{ENT_NAME}}`」
- **这是同一个 `FieldCode` 的读写两面。**

分开建两套 → 必然出现「抽出来的字段名 ≠ 模板里要填的字段名」，然后要写映射表，然后映射表失配 —— 这正是 05 册 §3.6 画 L5 链要避免的，也是 16 册「**铁律四：`FieldCode` 发布即冻结**」的由来。

## 四、Word 标签怎么设

> **总原则（铁律一）：格式归模板，值归平台。** 模板作者只做两件事：**打字** + **套样式**。不碰代码、不碰公式。

### 4.1 标量（单个值）—— 直接打字 `{{FieldCode}}`

| 场景 | 模板里写成 |
|------|-----------|
| 企业名称 | `企业名称：{{ENT_NAME}}` |
| 统一社会信用代码 | `统一社会信用代码：{{CREDIT_CODE}}` |
| 认证范围 | `认证范围：{{CERT_SCOPE}}` |
| 日期 | `发证日期：{{ISSUE_DATE\|fmt:yyyy-MM-dd}}` |

**必须同时给这段文字套一个字符样式 `YZH_Mark`**（Word：开始 → 样式 → 新建字符样式）。

> **为什么必须有 `YZH_Mark`**：它是**自验收的唯一依据**。填充完成后，扫描器再扫一遍，**任何还带 `YZH_Mark` 的文字 = 没被替换的残留** → 直接报错。没有这个标记，就无法区分「正常文字」和「漏填的 token」。

**修饰符**（写在 `|` 后面，可叠加）：

| 修饰符 | 写法 | 含义 |
|--------|------|------|
| 格式 | `{{BUILD_AREA\|fmt:0.00}}` | 按强类型写入 + 数字格式 |
| 兜底 | `{{FLOOR\|def:—}}` | 值为空时写「—」 |
| 全局参数 | `{{ENT_NAME\|src:global}}` | 走全局参数（如企业名称在所有文档一致） |
| 计算 | `{{=SUM(QTY)}}` | **平台侧求值**，不是 Excel/Word 公式 |
| 页码 | `{{PAGE}}` / `{{NUMPAGES}}` | 写 `fldChar` 三段（唯一允许的域） |

### 4.2 区块（表格重复行）—— 用**书签**包住样板行

**操作步骤（模板作者视角）：**

1. 在模板里做好一张表，**表头 1 行 + 样例数据 1 行**（不要预留 50 行空行）
2. 样例行各单元格打字：`{{TRAIN_DATE}}` / `{{TRAIN_TOPIC}}` / `{{TRAIN_HOURS}}`
3. **选中样例行第一个单元格内的文字** → 插入 → 书签 → 命名 `ROW_培训记录`

**⚠️ 三条硬约束（不遵守必出错）：**

| # | 约束 | 原因 |
|---|------|------|
| ① | **书签落在样板行的第一个单元格内** | 扫描器要**向上取 `<w:tr>` 边界**作为克隆单位；NPOI 克隆的是 `CT_Row`（整行），书签范围未必等于行范围 |
| ② | 书签名全局唯一、PascalCase、≤32 字符、仅字母数字下划线 | Word 书签名有字符与长度限制 |
| ③ | **一个书签，不是两个** | Word 原生是 `w:bookmarkStart w:id=N` … `w:bookmarkEnd w:id=N` **同 id 配对**，范围 = 两者之间 |

> ⛔ 常见错误：把书签理解成「A 处一个、B 处一个」两个标记。**Word 里只有一个书签名**，起止由 start/end 对决定。

### 4.3 页眉页脚

- **三类都要检查**：首页 `first` / 奇偶 `even` / 默认 `default` —— 这是最容易漏配的地方
- 页码用 `{{PAGE}}` / `{{NUMPAGES}}`
- 其他动态值**不要用 Word 域**（域不参与替换）

### 4.4 ⚠️ 必现坑：`{{Token}}` 跨 run

Word 会按**编辑历史**把一段连续文字拆成多个 `<w:r>`。你打 `{{ENT_NAME}}`，实际 XML 可能是：

```xml
<w:r><w:t>{{ENT_</w:t></w:r><w:r><w:t>NAME}}</w:t></w:r>
```

**扫描器和写入器都必须先做 run 归一化**（合并相邻同格式 run）再匹配 token —— poi-tl 的 `RunIterator` 就是干这个的。

> **不归一化，「拿 1 份真实 docx 跑通扫描」这个出口必然不通过。** 这是 P0 级别的必现缺陷，不是边缘情况。

### 4.5 Word 规范可检出项（扫描器红牌）

| # | 规范 |
|---|------|
| W1 | 标量值一律 `{{Token}}` 文本，**不用书签**（书签留给区块） |
| W2 | 重复区必须有书签，且书签在样板行内 |
| W3 | 书签名唯一 / PascalCase / ≤32 / 仅字母数字下划线 |
| W4 | 所有 token 套 `YZH_Mark` |
| W5 | 重复区至少留 1 行样例行 |
| W7 | 页眉页脚三类都要检查 |
| **W9** | **`{{Token}}` 不得跨 run**（扫描器提示模板作者：重新输入该 token） |

## 五、Excel 标签怎么设

### 5.1 标量单元格 —— 单元格里写 `{{FieldCode}}`

- 例：`B3` 写 `{{ENT_NAME}}`
- **数值单元格先在模板里设好 `numFmt`**（格式归模板，平台只写值）

### 5.2 数据区（重复行）—— 圈定**连续矩形** + 样例行

- 数据区必须是**连续矩形**，**不得有空洞**
- **样例行 = 第 1 个含 `{{...}}` 的行**
- 数据区 = 表头 + **1 行样例行**（**不预留空行**）
- 建议用**命名区域**圈定（如 `TRAIN_ROWS`），或按约定给区域地址

### 5.3 区外合计 —— 用 token 声明，**禁硬坐标**

```
A10:F10   表头（固定）
A11:F11   样例数据行（含 {{TRAIN_DATE}} 等）
A12       合计行，含 {{SUM_ROWS}}        ← 只声明「我是合计」，不声明「我在第几行」
```

**为什么必须这样**：Excel 锚点是坐标，**插行即移动**。

```
模板：A10:F60 数据区 + A61 合计行
数据：23 条 → 写 23 行 → 插 22 行 → 数据区变 A10:A33
🔴 A61 没动 → 合计跑到数据区外第 28 行
```

平台按「**数据区末行 + 1**」重定位合计行 → **插多少行都不需要回改任何配置，漂移问题彻底消失**。

### 5.4 Excel 规范可检出项（扫描器红牌）

| # | 规范 | 理由 |
|---|------|------|
| E1 | 数据区必须连续矩形，无空洞 | 空洞破坏偏移计算 |
| E2 | 区外元素（合计/汇总）紧贴数据区下沿，用 token 声明，**禁硬坐标** | 见 5.3 |
| E3 | 样例行 = 第 1 个含 `{{...}}` 的行 | 扫描器识别 |
| E4 | 数值单元格先在模板设好 `numFmt` | 格式归模板 |
| E5 | **不用 Excel 原生公式**（`=` 开头） | 平台不消费，且 NPOI 不更新引用 |
| E6 | **数据区禁合并单元格**（只允许表头与标签区） | 合并区破坏偏移 |
| E7 | 隐藏 sheet / 隐藏行不参与数据区 | 易漏 |
| **E8** | **数据区不预留空行**；扩行一律 `ShiftRows` 插入；数据区下方内容**随 ShiftRows 下移，禁止删除** | 否则「清理第 N~M 行残留」会**误删合计下方的签字栏/说明** |

## 六、后台怎么解析（扫描器流程，**零 LLM**）

> **这是与现有「开始分析」最大的区别**：生成规则的扫描**不用 AI**。模板自己声明了要填什么，扫描器只是把它读出来。

```
模板文件（docx / xlsx）
 │
 ├─ ① 解析结构        NPOI 读：段落 / run / 表格 / 书签 / 单元格 / 命名区域
 ├─ ② run 归一化      合并相邻同格式 run（★ W9，不做则 ③ 会漏）
 ├─ ③ 扫标量锚点      正则 {{...}} → [{FieldCode, 修饰符, 位置(段/表/单元格)}]
 ├─ ④ 扫区块锚点      Word: 读书签 → 向上取 <w:tr> 得样板行边界
 │                   Excel: 读区域 + 第 1 个含 token 的行 = 样例行
 ├─ ⑤ 校验标记覆盖    读 YZH_Mark 样式 → 哪些 token 没套样式
 ├─ ⑥ 页眉页脚遍历    first / even / default 三类
 ├─ ⑦ 与字段定义比对
 │     锚点有、定义无  → 🔴 红牌「未定义 Token」→ 阻断发布
 │     定义有、锚点无  → 🟡 黄牌「字段无处落笔」→ 进清单
 │     FieldCode 大小写/拼写不一致 → 🔴 红牌
 └─ ⑧ 落库
       cert_doc_template_scan   扫描快照（SourceSha256 免重扫）
       cert_doc_template_part   锚点清单（一行一个锚点）
```

### 6.1 产物是「锚点清单」，不是「字段清单」

| | 谁提供 | 例子 |
|---|--------|------|
| **字段清单** | **契约侧**（`cert_doc_field_def`） | `ENT_NAME`、`CREDIT_CODE`、`CERT_SCOPE` |
| **锚点清单** | **模板侧**（扫描产出） | `{{ENT_NAME}}` 在段落 12；`ROW_培训记录` 在表 3 第 1 行 |

**两者必须双向一致** —— 这就是「校验」要报的红牌/黄牌。

### 6.2 一个重要副产品：**模板即「完成度」的分母**

因为模板显式声明了「要填哪些锚点」，所以：

```
完成度 = 已填锚点数 / 模板锚点总数（扣掉 na 项）
```

**分母不用猜、不用 AI 估** —— 模板一改，分母自动跟着变。这比 05 册 `§九` 里讨论的「分母是字段定义数还是锚点数」要干净得多：**就是锚点数**。
