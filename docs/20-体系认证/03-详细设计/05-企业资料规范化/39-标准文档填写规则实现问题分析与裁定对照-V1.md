## 二、分层模型：理解全部问题的钥匙

项目已有抽象是**三层**，全部 11 条主张都能映射进来，混淆点多发生在「把取值与写入合称 Skill」：

```
层 2  全局填写规则（语义描述 + 值字典）
      │  输入：锚点清单 + 全局参数 + 企业画像
      │  AI 分析 → 产出【值字典】{ AnchorCode: value, ValueType, Confidence }
      │  ⛔ AI 到此为止 —— 不打开文件、不碰 NPOI、不知道是 Word 还是 Excel
      ↓
层 1  写入执行（NPOI，确定性）
      │  定位 → 写值 → 保留样式 → 自验收
      ↓  ⛔ 不做任何语义判断（不猜值、不补值、不改值）
      文件真正被填上
```

**载体裁定（三句话）**：

- **取值** → 不做 Skill，做 `IValueResolver` + 特征注册（22 号 §十三）
- **写入** → 是 Skill 原语（26 号 §3.4.6）
- **文档级提示词装配** → 可以 Skill 化（23 号 §3.3）

> 23 号原文：「⇒ **22 号 §十三说的『填充取值不做成 Skill』与这里不冲突**：`build_nc_prompt` 是文档级、每模板一次、要调 LLM 的重操作 —— 命中 22 号 §13.6 判据（低频 · 重 · 需留痕）。**层 2 可以 Skill 化，层 1 不行。**」

## 三、专题一：doc→docx / xls→xlsx 的保真方案

### 3.1 硬事实（先说清边界）

- **没有任何方案能 100% 不丢样式。** Apache POI 官方立场：二进制格式转 OOXML 超出文档对象模型解析器的能力范围，需要完整布局引擎。
- **NPOI 的 HWPF 对 `.doc` 只读**（且上游 POI 已弃用），**它不是转换器**。
- 因此转换必须依赖外部引擎——这属于「引擎能力」而非「库能力」，不要在 NPOI 里找解法。

### 3.2 三档方案对比

| 方案 | 保真度 | 成本 | 限制 | 适用性 |
|---|---|---|---|---|
| **LibreOffice headless** | 元数据 ≈92% | 免费 LGPLv3 | 需容器/进程 | **当前方案，选得对** |
| MS Word COM Automation | 近 100%（VBA/OLE 完整） | 需 Office 授权 | 仅 Windows + 桌面会话，Docker 服务端不可用 | 不适用本项目部署 |
| Aspose.Words / Cells | >99%，中文 GBK 自动探测 | 商业（约 $1,199/开发者起） | 无技术限制 | 预算充足时的兜底 |

### 3.3 关键补强：转换后校验（必做）

既然 92%≠100%，就必须让损失**可检测**。项目已有锚点扫描器，直接复用即可，无需新建设施：

1. **转换前**：扫描源文件锚点集合 **A**
2. **转换后**：扫描目标文件锚点集合 **B**
3. **判定**：`A ⊄ B`（有锚点丢失）→ 告警或拒收，转人工复核
4. **登记**：把校验结果写入转换记录，作为可追溯凭据

这是唯一能把「不丢样式」从愿望变成工程指标的办法。

### 3.4 转换的两个已知坑

| 坑 | 说明 |
|---|---|
| soffice 退出码 0 但无产物 | 必须独立校验输出文件是否存在，不能只看退出码 |
| 带密码 / 宏 / 表单保护的 doc | 直接转换失败，需前置检测并给出明确提示 |

### 3.5 `.xls` 的补充事实

NPOI 的 HSSF **能读也能写** `.xls`（与 Word 侧「只能读不能写」不同），因此理论上存在第二条路径：HSSF 读 + XSSF 写。但**样式需手工映射、极易丢失**，仍推荐统一走 LibreOffice。此条仅作备案，不推荐实施。

### 3.6 转换时机：建议修正为「上传/入库时」

| 方案 | 问题 |
|---|---|
| **下载时转** ✗ | 填写期面对的仍是 `.doc`，NPOI 写不了；每次下载重复转换；库内状态与产物不一致 |
| 上传侧直接拒绝 ✗ | 用户被迫手工另存，体验差（21 号 Q-3 原裁定） |
| **上传时自动转 + 校验 + 扫锚点 + 落库** ✓ | 转一次，之后全链路统一 docx/xlsx |

**存量处理**：若指的是存量 168 份标准文档中的 `.doc`/`.xls`，做法应为**一次性批转 + 校验 + 落库**，而不是挂在下载链路上。

## 五、专题三：Skill 分类的裁定

### 5.1 操作类 ✅ 成立（26 号 §3.4.6 已定义并落地）

| SkillCode | 作用 | NPOI 落点 |
|---|---|---|
| `doc_cell_write` | 写标量单元格 | Word `XWPFTableCell` / Excel `ICell` |
| `doc_replace` | 段内片段替换 | Word `XWPFParagraph` 的 `XWPFRun` 集合 |
| `doc_table_write` | 表格插行 + 填充 | Word `XWPFTable`+`CTRow` / Excel `ISheet.ShiftRows` |
| `doc_domain` | 写域代码 | Word `fldChar` 三段式 |
| `doc_save` | 落盘 + 自验收 | `XWPFDocument.Write` / `XSSFWorkbook.Write` |
| `doc_convert` | `.doc`/`.xls` → 新格式 | 复用 `OfficeConvertService` |

### 5.2 内容类 ✗ 已被 22 号 §十三否决

**否决理由（原文立论）**：

1. **粒度差一个数量级**：一份模板 42 个锚点 × 平均 2 个来源 ≈ **84 个节点 + 上百条连线**，而画布（`WorkflowDesigner.vue`）的舒适区是**十几个节点**。「用画布表达『字段级取值』是量级错配。」
2. **项目已走过这条路并改了回来**：
   - `get_field` / `get_table` 已从 Skill 体系移除，理由「数据源节点，行为与功能性节点不一致」
   - `LlmExtractSkill` 列入废弃清单，理由「臆想的 AI 提取 Skill，信息提取走独立流程」
   - 22 号原话：「⇒ **你的提议在方向上回到了 2026-09-12 之前的状态。**」
3. **正确载体已给出**：

```csharp
public interface IValueResolver
{
    string Kind { get; }  // global / self / sibling / profile / compute / ai / manual
    Task<ResolveResult> ResolveAsync(ResolveContext ctx, SourceSpecEntry src, CancellationToken ct);
}

[ValueResolver("global", Name = "全局参数")]
public sealed class GlobalParamResolver : IValueResolver { /* 读 cert_fill_param_value */ }
```

> 「**注册**：DI 扫描 + 特性，登记即用；**扩展**：新增来源 = 加一个类 + 一个特性，⛔ 不改填充引擎；**区别**：它是填充引擎内部的策略，不是用户可见的画布节点。」

### 5.3 「字典」这一类不成立

22 号 §2.2 原文：「否掉的理由：`cert_application.CertType` 已经是**项目上下文的一部分** ⇒ 归 `global` 即可。把『值是枚举』当成『来源类别』是**把值域混进了来源维度**。」

⇒ 不新增第 8 类来源。

### 5.4 「AI 字段 / AI 表格」的正确定位

它们不是两个独立 Skill，而是 **`D1.ai` 来源 × `D3` 形态（`scalar` / `table`）**的两种组合。

### 5.5 取值来源 7 类（D1，判据：只看「值最初从哪里来」）

| 码 | 名称 | 值从哪来 | 失败行为 |
|---|---|---|---|
| `global` | 全局参数 | 认证项目上下文（企业/阶段/标准/机构） | 必填缺失 → 阻断填充 |
| `self` | 本文档内引用 | 同一模板的另一锚点 | 引用目标未填 → 阻断（须防环） |
| `sibling` | 同批文档取值 | 同企业同阶段另一份标准文档的已填结果 | 目标未完成 → 降级下一源 |
| `profile` | 企业资料画像 | 企业上传资料的画像提取结果 | 未命中 → 降级下一源 |
| `compute` | 计算/统计 | 对锚点集合做运算 | 依赖缺失 → 留空并告警 |
| `ai` | AI 生成 | LLM 依上下文生成 | 失败/低置信 → 降级到人工 |
| `manual` | 人工录入 | 必须人填 | 未填 → 挂待办，不阻断出文档 |


样板：**统一社会信用代码** = `scalar` + `[global, profile, manual]` + `replace`——一个锚点、三个源、按序回退、最后兜底人工。

## 六、专题四：坐标 vs 锚点

### 6.1 必须拆成两层看

- **写入期**：确实需要坐标，`ICell` 写入本质即 row/col。✅ 成立
- **配置期**：⛔ 绝不能让人工在属性里配置坐标。

### 6.2 19 号 E2 铁律与算例（原文）

```
A10:F10   表头（固定）
A11:F11   样例数据行（含 {{TRAIN_DATE}} 等）
A12       合计行，含 {{SUM_ROWS}}   ← 只声明「我是合计」，不声明「我在第几行」
```

> **为什么必须这样**：Excel 锚点是坐标，**插行即移动**。
> ```
> 模板：A10:F60 数据区 + A61 合计行
> 数据：23 条 → 写 23 行 → 插 22 行 → 数据区变 A10:A33
> 🔴 A61 没动 → 合计跑到数据区外第 28 行
> ```
> 平台按「**数据区末行 + 1**」重定位合计行 → 插多少行都不需要回改任何配置。

### 6.3 正确姿势

1. **锚点（`{{}}` / 书签 / token）负责定位** —— 稳定，改版可重扫
2. **坐标是扫描产物** —— 扫描器从锚点位置算出 row/col，存入 ScanResult
3. **写入期用坐标执行**
4. **人工配置里不出现坐标**

**「得不到坐标」这个担心不成立**：NPOI 遍历 `Sheet.Row.Cell` 天然带 `RowIndex`/`ColumnIndex`，一次遍历全部获得，无需人工填写。

### 6.4 一个易错的细节

Excel 存在**两套列标**：字母（A/B/C，用户可见）与 0-based 索引（0/1/2，NPOI 接口）。**存储统一用 0-based，展示用字母**，两者必须有明确且唯一的转换点，不可混用。

### 11.3 必须补齐的 4 个接口点

**接口 1：markdown 视图 ↔ 锚点坐标的映射（最高优先级）**

markdown 是给 AI 看的，锚点坐标是给 NPOI 写的，两者是**两套视图**。

- 若 markdown 生成时抹掉锚点标记 → AI 给出的值无法回填到具体 run / cell → 流水线断在第五段。
- 要求：markdown 生成时**保留锚点 token**（`{{ANCHOR_CODE}}` 原样保留），或在库中维护 `anchor_code ↔ 文档位置` 映射表。
- 这条不成立，前面四段做得再好也落不了地。

**接口 2：漏斗判定标准要可复现**

- 分类过滤依据什么？（文件类型 / 目录归属 / 标准条款号 / 关键词？）
- 语义过滤的阈值如何确定？
- 要求：判定规则须落库且可追溯，不能每跑一次得出不同结果——否则同一份资料两次填充结果不一致，审计上不可接受。

**接口 3：召回片段数 ≠ 锚点数**

- 一份模板可能有 40+ 锚点，语义召回只有 2~5 处片段，差额锚点由谁供给？
- 明确分工：`ai` 只负责「需要从资料中理解生成」的少数锚点；其余走 `global`（项目上下文）/ `profile`（画像）/ `manual`（人工）。
- 这个分工要写进模板锚点配置，避免误以为 AI 能全包。
- **这也反过来印证了 §11.1 的效率账**：正因为 AI 只碰少数锚点，合并调用才划算。

**接口 4：批量写入的边界**

- 「一次打开」的粒度 = 一份文档一次，还是一批文档一次？
- 建议：**一份文档一次写入会话**（同一份文档的所有锚点合并在一次 open / write / save 内完成），批次级只做循环调度。
- 值字典完整性校验通过后，才允许打开文件。

### 11.4 效率账

- **合并调用优于拆分**：N 个锚点拆 N 次调用 → N 次往返；合并为 1 次 → 上下文变长，但**过滤后总 token 更小**（只剩 2~5 处片段），成本与延迟双降。
- **markdown 落库复用**：转换一次、多次使用，不重复转；与第三章「上传 / 入库时转换」的建议一致。

### 11.5 一处待确认

markdown 转换范围是「全量文档统一转」还是「只转入选的 5~10 份」？

- **全量转**：库内视图统一，但转换成本前置
- **按需转**：节省成本，但同一文档可能被多次转换，需缓存规避

建议：**入库时全量转 + 落库缓存**（转一次，永久复用）。
