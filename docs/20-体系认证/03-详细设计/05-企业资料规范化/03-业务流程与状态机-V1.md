## 1. 端到端泳道流程

```text
企业/审核员        系统（L1-L2）           AI（L3）              匹配引擎（L4）         人工（L4）           输出（L5）
──────────       ─────────────         ─────────            ──────────────        ──────────         ─────────
 ① 上传资料  ──►  落 MinIO              │                      │                    │                  │
                 PathBuilder.           │                      │                    │                  │
                 EnterpriseFile()       │                      │                    │                  │
                 写 file 表             │                      │                    │                  │
                 入 file_convert 队列 ──►│                      │                    │                  │
                 ② anydoc→MD           │                      │                    │                  │
                 libreoffice→PDF        │                      │                    │                  │
                 回写 MarkdownPath ─────┼──────────────────────►│                    │                  │
                                        │ ③ 入 ent_doc_profile  │                    │                  │
                                        │   队列：指纹识别 ──────►│                    │                  │
                                        │   (零LLM) 未命中 ──────┼─► LLM 画像提取      │                  │
                                        │   产出 profile/       │  (作用/字段/表格)    │                  │
                                        │   field/table ────────┼────────────────────►│                  │
                                        │                      │ ④ 召回（零/低LLM）   │                  │
                                        │                      │ ⑤ 精排 Top-K 打分   │                  │
                                        │                      │ ⑥ 冲突检测         │                  │
                                        │                      │ 生成候选+可信度 ─────┼──► ⑦ 人工裁决页    │
                                        │                      │                    │   选来源/否决/     │
                                        │                      │                    │   改换/手工指定   │
                                        │                      │◄─ 裁决落 decision ───┼──                │
                                        │                      │ 回填 file.          │                  │
                                        │◄─ 入定向提取 ──────────┼─ StandardFileCode   │                  │
                                        │  (既有规则链)          │                    │                  │
                                        │  cert_extraction_     │                    │                  │
                                        │  result 落库 ─────────┼──────────────────────────────────────►│
                                        │                      │                    │   ⑧ 契约驱动填充  │
                                        │                      │                    │   实例状态推进    │
                                        │                      │                    │   版本归档+审计 ◄─┘
```

### 1.1 分步说明

| 步 | 动作 | 执行者 | 关键点 |
|----|------|--------|--------|
| ① | 上传资料（支持文件夹结构） | 企业/审核员 → 系统 | 四段式 `upload-init/file-v2/confirm/cancel`；OSS 路径唯一由 `PathBuilder.EnterpriseFile()` 生成；`FileHash` 去重（重复标 `IsDuplicate` 但仍入库，不阻断） |
| ② | 格式转换 | `file_convert` 队列（已有） | 双产物：`PreviewPdfPath`（预览）+ `MarkdownPath`（**画像与匹配的唯一输入**）；失败分类 `Unsupported/Timeout/NotProduced/InvalidInput`（OCR 不单独作为失败分类，anydoc 链统一处理图片/PDF） |
| ③ | 画像提取 | `ent_doc_profile` 队列（**新增**） | 先指纹（零 LLM），未命中固定文档才走 LLM；无 Markdown 的走 `skipped`（PDF 图片型待 OCR，P3） |
| ④⑤⑥ | 召回、精排、冲突检测 | `ent_doc_match` 队列（**新增**） | 三阶段算法见 04 分册；只对 `ProfileStatus=completed` 的文件跑 |
| ⑦ | 人工裁决 | 审核员/管理员 | 页面见 09 分册；每个标准文档视角列出候选与证据；动作落 `cert_doc_match_decision`（只追加） |
| ⑧ | 定向提取 + 填充 | 服务编排 | 裁决确认后触发既有规则链（Phase3 §4.3），产出 `cert_extraction_result`；填充按契约生成标准文档实例，状态推进 |

### 1.2 各步之间的解耦约定

1. **②失败不阻断①**：文件上传成功即算接入成功，转换失败有独立状态与重试入口（既有 `RetryFailedConversionsAsync` 模式）。
2. **③可独立重跑**：重跑产生新 `ProfileVersion` 行，不动裁决数据。
3. **④⑤⑥可独立重算**：重算 UPDATE 候选（`uk_file_std`），已 `confirmed` 的候选不被覆盖（见 04 分册 §9.2）。
4. **⑦是唯一改归属的动作**：AI 永不写 `cert_standard_directory_file.StandardFileCode`；只有 `DecisionService` 能写（高置信自动动作也必须写一条 `IsAuto=1` 的 decision 记录，见 §3 触发点）。
5. **⑧依赖⑦**：未裁决（或未达自动阈值）不进入填充。

## 2. 四条状态机

### 2.1 企业文件（企业行，落在 `cert_standard_directory_file`）

> **⚠️ 2026-09-30 勘误（表名 R-07）**：本册原稿的 `cert_enterprise_file` 表**不建**（D11 统一表），企业文件行 = `cert_standard_directory_file` 中 `EnterpriseCode` = 真实企业 Code 的行。下文凡写 `cert_enterprise_file` 之处均按此换算。

```text
                    ┌────────── upload-confirm ──────────┐
                    ▼                                    │
                 uploaded ──入队──► converting ──成功──► profiled(待画像)
                    │                  │ 失败                │
                    │                  ▼                     │ 入队 ent_doc_profile
                    │               convert_failed ──重试──► converting
                    │                  │ 放弃                 ▼
                    │                  ▼                  profiling
                    │              (仍可人工指定匹配)          │ 成功
                    │                                        ▼
                    │                                    matched ──裁决──► confirmed
                    │                                        │ 失败              │
                    │                                        ▼                  ▼
                    │                                    profile_failed     synthesized
                    │                                        │ 重跑              │ 导出
                    │                                        ▼                  ▼
                    └──◄───────────── 替换文件(新版本) ──── pending ◄────── archived
```

**字段映射**（`ProfileState` / `MatchState` 双列）：

| 阶段 | `ProfileState` | `MatchState` |
|------|----------------|--------------|
| 刚上传 | `none` | `none` |
| 转换中 | `none` | `none` |
| 转换完成待画像 | `pending` | `none` |
| 画像中 | `processing` | `none` |
| 画像完成 | `completed` | `recalling`→`scored`（由匹配服务推进） |
| 画像失败 | `failed` | `none` |
| 待人工 | `completed` | `pending_review` |
| 裁决通过 | `completed` | `confirmed` |
| 裁决否决 | `completed` | `rejected` |
| 替换文件 | 重置为 `none`，`MatchState` 重置 `none`（**触发新一轮全流程**，旧 version 行保留） | |

**规则**：
- 转换期间沿用既有约定 `IsValid=0`，终态回 `IsValid=1`（`OfficeConvertService.cs:401-408` 同款）；
- 替换/新版本必须把画像与匹配状态归零——旧画像对应旧内容，直接复用会产生「新文件配旧画像」的静默错误。

### 2.2 画像 `cert_ent_doc_profile.ProfileStatus`

```text
pending ─► processing ─┬─► completed（有字段/表格/作用）
   ▲                   ├─► skipped（无 Markdown：图片型 PDF / 转换失败）
   │                   └─► failed（LLM 超时/JSON 解析失败/内容超长截断）
   └── 重跑（新 ProfileVersion 行，IsLatest 切换）
```

**规则**：
- `skipped` ≠ `failed`：前者是**能力边界**（等 OCR，P3），后者是**异常**（可重试）；
- 重跑**新建行**而非 UPDATE（`uk_file_latest` + `IsLatest` 位），旧版本留存对比；
- 单个字段提取失败不导致整体 `failed`（`ExtractionResult` 现有同款策略：低置信度标待复核，不阻断提交）。

### 2.3 匹配候选 `cert_doc_match_candidate.Status`

```text
pending（召回产生） ─精排─► scored ──►
                              ├─ confidence ≥ auto   → recommended（系统推荐，可自动确认）
                              ├─ review ≥ conf ≥ auto → pending_review（进人工队列）
                              └─ conf < review        → 不生成/置 rejected（低分不打扰人工）
                                         │
                 人工/自动裁决 ────────────┤
                              ├─ accept  → confirmed
                              ├─ reject  → rejected
                              ├─ replace → superseded（同 StandardFileCode 的旧 confirmed 候选）
                              └─ 重算    → 仅 pending/scored/recommended 可被重算覆盖
```

**规则**（关键保护）：
- `confirmed` 候选**永不被自动重算覆盖**——重算范围限定 `Status IN ('pending','scored','recommended')`；
- 同一 `StandardFileCode` 下最多 1 条 `confirmed`（应用层校验，用 `idx_target` 查询 + 裁决事务保证，不加 DB 唯一约束以保留历史 `superseded` 行）；
- `ScoreStage='human'` 的候选（人工直接指定，无 AI 依据）`Confidence` 存 NULL，`EvidenceJson` 存 `[{"type":"manual"}]`。

### 2.4 标准文档实例 `cert_standard_directory_file.InstanceState`

```text
empty ──部分字段就位──► partially_filled ──必填项齐──► filled ──人工复核──► reviewed ──导出──► exported
  │                            │                          │                    │
  └── 裁决解除/来源变更 ◄────────┴────── 回退（来源失效） ◄───┴── 实例版本归档（PathBuilder.Archive）
```

**规则**：
- `filled` 判定 = 契约中 `IsRequired=true` 的字段/表格全部有值（`cert_extraction_result` 按 `StandardFileCode` 聚合）；
- 来源文件被替换或裁决 `unlink` → 依赖它的实例**回退**到 `partially_filled`，并在实例变更记录中登记原因；
- 每次状态推进写审计（07 分册）；`InstanceState` 由服务聚合回写，不单独建表。

## 3. 触发点矩阵

> **勘误（2026-09-30，R-10）**：本表 T3 原为「画像完成后累积批次自动入队」，已被 `14` 号 **D21（匹配手动触发为主）** 推翻 —— 控制权交给人（点「开始匹配」或圈范围）；自动触发降为 **P4 可选开关**；附带消除原 T3「累积凑批无超时兜底、最后一批永不触发」的缺口。
>
> **主路径**：`T1 → T2 →（人工点「开始匹配」/ 圈范围）→ T7/T3 → T4 → T5`。

| # | 触发事件 | 后续动作 | 执行方式 | 幂等键 |
|---|----------|----------|----------|--------|
| T1 | `upload-confirm` 成功 | 建 `file_convert` 队列（已有逻辑） | 队列 | `uk_source(upload_task, taskId)` |
| T2 | `file_convert` 任务完成且 `MarkdownStatus=completed` | 建 `ent_doc_profile` 队列 | 队列 | `uk_source(ent_doc_profile, fileCode+ver)` |
| T3 | 画像 `completed` | **默认不自动触发匹配**（D21 手动为主）：审核员点「开始匹配」或圈范围触发，统一口径为「**文件夹 × 文件夹**」（D13）。P4 可选开关：累积批次后自动入队 | 手动 → 队列 | `uk_source(ent_doc_match, batchCode)` |
| T4 | 匹配批次完成 | 生成待人工清单（`pending_review`），通知（可复用 `CertQueueNotifier`） | 服务 | — |
| T5 | 人工 `accept/replace/manual` | ① 写 decision ② 回填 `file.StandardFileCode` ③ 置候选 `confirmed/superseded` ④ 触发定向提取 ⑤ 聚合 `MatchState`/`InstanceState` | **同步事务**（单文件量级） | `GetByCode` 分流 |
| T6 | 自动确认（`confidence ≥ auto` 且无冲突） | 同 T5，但 decision 记 `IsAuto=1, Trigger=auto_rule` | 服务内联或轻队列 | 同上 |
| T7 | 用户圈范围定向匹配（**主交互**，第五节 / D13） | 只对该范围重跑召回+精排；Payload 带 `ScopeFolderCode + ScopeFileCodes` | 手动 → 队列 | `uk_source(manual_scope, scopeCode)` |
| T8 | 重跑画像 | 新 `ProfileVersion` + 失效其候选（`Status→pending`，**confirmed 除外**） | 队列 | `uk_source(ent_doc_profile, fileCode+ver)` |
| T9 | 重跑匹配 | 同 T8 对候选的处理 | 队列 | `uk_source(ent_doc_match, batchCode)` |
| T10 | 文件替换/删除 | 状态归零 + 旧实例回退 + decision 追加 `unlink` 记录 | 同步事务 | 文件 Code |

**T5 的事务边界**（必须原子，避免「裁决了但没回填」）：

```text
BEGIN;
  INSERT decision (只追加);
  -- 企业行守卫：WHERE 必须同时带 EnterpriseCode（防误改模板行），见 15 号 T-06
  UPDATE cert_standard_directory_file SET StandardFileCode = ?, MatchState='confirmed'
    WHERE Code = ? AND EnterpriseCode = ?;
  UPDATE candidate SET Status='confirmed' WHERE Code = ?;
  UPDATE candidate SET Status='superseded' WHERE StandardFileCode=? AND Status='confirmed' AND Code<>?;  -- replace 场景
  UPDATE cert_standard_directory_file SET MatchState='…' WHERE Code = ?;  -- 聚合
COMMIT;
-- 定向提取（LLM，秒级~分钟级）在事务外，入队执行
```

## 4. 队列编排

### 4.1 新增两个 TaskType

| TaskType | 中文名（`CertQueueNotifier` 映射） | Payload | 执行器类 |
|----------|-----------------------------------|---------|----------|
| `ent_doc_profile` | 企业文档画像 | `{ FileCode, ProfileVersion, MarkdownPath, Force }` | `EntDocProfileTaskExecutor` |
| `ent_doc_match` | 企业文档匹配 | `{ BatchCode, EnterpriseCode, StandardCode, StageCode, ScopeFileCodes?, ScopeFolderCode? }` | `EntDocMatchTaskExecutor` |

**注册模式**（照抄既有，`CertPlatformAdminServiceExtensions.cs:54-61`）：

```csharp
services.AddSingleton<EntDocProfileTaskExecutor>();
services.AddSingleton<EntDocMatchTaskExecutor>();
services.AddSingleton<IYzhTaskExecutor>(sp => sp.GetRequiredService<EntDocProfileTaskExecutor>());
services.AddSingleton<IYzhTaskExecutor>(sp => sp.GetRequiredService<EntDocMatchTaskExecutor>());
```

执行器必须单例、自开 `IServiceScope`（`OfficeConvertTaskExecutor.cs:13,44` 注释同款约束）。

### 4.2 提交队列的请求结构

```csharp
var req = new QueueManager.CreateQueueRequest
{
    QueueType   = "ent_doc_profile",
    QueueName   = $"文档画像 - {files.Count}个文件",
    ScopeKey    = $"ent_norm|{enterpriseCode}|{standardCode}|{stageCode}",  // 同作用域同时只跑一个
    SourceType  = "profile_batch",
    SourceId    = batchCode,                       // uk_source 防重复入队
    ResourceLocks = new List<QueueManager.ResourceLockItem>
    {
        new() { ResourceTable = "cert_standard_directory_file", ResourceCode = file.Code, ResourceName = file.FileName }
    },
    Tasks = files.Select(f => new QueueManager.TaskItem {
        TaskType = "ent_doc_profile",
        Payload  = JsonSerializer.Serialize(new EntProfilePayload { FileCode = f.Code, ... }),
        TaskId   = batchCode
    }).ToList()
};
var (ok, error, queueCode, _) = await _queueManager.CreateQueueAsync(req);
if (!ok) return Fail(error);   // "有正在执行的任务队列（…），请等待完成后再操作"
```

- `ResourceTable` 用企业文件表名：资源锁粒度 = 单文件，避免同一文件被画像/匹配并发写；
- `ScopeKey` 保证同一企业+标准+阶段的同类型作业串行，跨标准并行。

### 4.3 状态回写与列白名单（**必须遵守**）

2026-09-26 实测事故：双链并发 + `UpdateAsync(实体)` 全列写回 → `MarkdownPath` 被覆盖为 NULL 且零报错。本模块同样存在「画像链 / 匹配链 / 转换链」多链并发写 `cert_standard_directory_file`（企业行），故：

| 链 | 允许写入的列 |
|----|--------------|
| `ConvertChain`（转换链，已有约定迁移过来） | `PreviewPdfPath, MarkdownPath, ConvertStatus, MarkdownStatus, ConvertMessage, UpdateTime, UpdateBy` |
| `ProfileChain`（画像链） | `ProfileState, DocCategoryDetected, UpdateTime, UpdateBy` |
| `MatchChain`（匹配链） | `MatchState, StandardFileCode, UpdateTime, UpdateBy` |
| `DecisionChain`（裁决，同步事务） | `StandardFileCode, MatchState, UpdateTime, UpdateBy` |

实现方式与 `OfficeConvertService.SavePdfChainAsync` 一致：`_db.UpdateAsync(entity, 列名数组)` 指定列更新，**禁止**裸 `UpdateAsync(entity)`。该白名单表必须写进服务类头注释（决策留痕风格对照 `OfficeConvertService.cs:33-44`）。

### 4.4 重试与失败分类

复用 `QueueManager` 既有机制，本模块只需在执行器返回值里正确表达：

| 场景 | 返回 | 框架行为 |
|------|------|----------|
| LLM 超时/网络抖动 | `Success=false, Retryable=true` | 指数退避 `5*3^n ≤300s` + 抖动，至 `MaxRetryCount` |
| JSON 解析失败 | `Retryable=true`（一次），二次仍失败 `Retryable=false` | 与 `TryRepairTruncatedJson` 抢救配合 |
| Markdown 缺失 | `Retryable=false, Message="无Markdown产物"` | 任务 `failed`，画像置 `skipped`，等转换重试 |
| 契约不存在 | `Retryable=false` | 跳过该标准文档，不重试 |
| 权限/不存在类永久错误 | 命中 `ClassifyError` 词表（`"不存在","已被修改","不支持"…`） | 自动判永久失败 |

**框架缺口提示**：`IYzhTaskExecutor.OnTaskStateChangedAsync` 与 `IYzhQueueNotifier.NotifyAsync` 目前是死接口（`src/yzh-core` 零调用点）。本模块的业务状态回写**必须在 `ExecuteAsync` 内自行完成**，不得依赖这两个钩子（若届时框架已接通，可迁移——登记框架改动清单）。

## 5. 定向匹配（用户第四步）

用户诉求：「针对一个文档，用户可以指定某些企业文档或文件夹进行让 ai 自动匹配」。

### 5.1 三种定向范围

| 范围 | 入参 | 说明 |
|------|------|------|
| 单个企业文档 | `fileCodes: []` | 对指定文件重跑画像（如需）+ 全量召回精排 |
| 企业文件夹（含子树） | `folderCode` | 展开子树文件集合后同上 |
| 当前标准文档的企业侧候选 | `standardFileCode` | 反向：只看「谁最像这份标准文档」，跑该目标的召回 |

### 5.2 流程

```text
用户圈选范围 → POST /match/scope-run（同步校验权限+建批次）
   → 校验：范围内文件 ProfileState（未画像的先入 ent_doc_profile 队列，串联）
   → 建 ent_doc_match 队列（ScopeFileCodes 写入 Payload）
   → 完成后前端轮询/通知 → 进入裁决页该范围的待办
```

**边界约束**：
- 定向范围**不跳过**指纹与召回阶段，只跳过「全量」——保证结果与批量跑可比（同算法、同批次排序基准）；
- 定向范围不降低阈值，不自动确认（人工发起 ≠ 自动放行）；
- 权限：按 `EnterpriseCode` 数据权限过滤，跨企业圈选直接拒绝。

## 6. 异常流与降级

| 异常 | 表现 | 处理 | 用户可见 |
|------|------|------|----------|
| 转换失败（需 OCR） | `MarkdownStatus=failed, ConvertMessage` 含 OCR 类原因 | 不入画像队列；标记待 OCR（P3） | 文件列表「需 OCR」徽标 + 人工指定通道仍可用 |
| LLM 服务不可用 | 画像/精排批量失败 | 队列重试 → 永久失败；**指纹链与人工通道不受影响** | 队列失败横幅 + 重试按钮 |
| 无匹配候选 | 该文件召回为空 | `MatchState` 保持 `scored` 之前的 `none`，进「无归属」清单 | 人工可手工指定（`Action=manual`） |
| 全部候选低于复核线 | 精排后无 ≥ review 分 | 不打扰人工，进「低置信」折叠区 | 可展开强制人工判断 |
| 多候选冲突 | 见 04 分册 §6 | `IsConflicted=1` + 强制人工 | 裁决页冲突高亮，禁自动确认 |
| 契约缺失 | 标准文档无契约行 | 该标准文档不参与匹配（召回源为空） | 标准目录页「未配置契约」提示 |
| 批量超大（>500 文件） | 单队列过长 | 按文件夹分批，每批独立 `batchCode` | 进度按批展示 |
| 并发写覆盖 | 多链写同一 file 行 | §4.3 列白名单 | （静默，无感） |
| 队列被取消 | 作业中止 | `UploadQueueCancelHandler` 同款：把中间态字段回置终态并写原因 | 「队列已取消」状态与原因 |

**降级总原则**（承接前置稿有效部分）：**AI 全线不可用时，系统退化为「规则识别 + 人工全量裁决」，业务不中断**——这是固定文档指纹链与人工手工指定通道必须独立存在的理由。
