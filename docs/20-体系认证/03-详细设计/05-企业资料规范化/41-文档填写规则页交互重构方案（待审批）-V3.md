# 41 · 文档填写规则页交互重构方案（待审批）· V3

> **修订历史**
> - **R1（V1 → V2 → V3）**：类型优先 → 锚点卡片化 → 一级功能导航 + 状态标记 + 左树过滤。
> - **R2**：用户第四轮反馈修正 **4 处** ——
>   ① 一级菜单**移进第 3 栏顶部**（原横跨全页顶部，位置错）；

>   ③ **保存按钮固定居底**，随时可存；
>   ④ **未保存改动自动提醒**。
> - **R3**：用户第五轮反馈修正 **3 处** ——

>   ⑦ **全文填写规则重构** = 三组可点击**书签**（① 锚点 ② 企业参数 ③ 填写方法）+ 光标处插入 ⇒
>      即使**没有任何 AI 填入项**，也能阐述「怎么筛选企业材料」「哪些单元格怎么写」。
> - **R4**：用户第六轮反馈修正 **1 处** ——
>   ⑧ **说明外移**：页内只留**事实与操作**（状态 / 缺失项 / 按钮 / 清单），
>      把**解释与背景**收进菜单区右上角的 **`!` 浮层**（四个功能的「作用 / 做法」一屏看完）；
>      同时清理装饰性图标与长段落。⇒ §13
> - **R5（本文当前版本）**：用户第七轮反馈修正 **1 处** + 1 条实施约束 ——
>   ⑨ **全文规则改上下结构**：上 = **素材区**（锚点 / 全局参数 / 填写方法，各占一行），
>      下 = **提示词编辑区**（占满剩余高度）。⛔ 不再左右分栏（第 3 栏 610px 分两栏后编辑区只剩 ~380px，
>      而提示词是长句、最需要宽度）。⇒ §8.5.6
>   ⑩ **实施时按项目前端风格**（令牌 + 兜底 / Element Plus / 样板页 / 守卫 + 构建）⇒ **§15**

## 0. 一句话结论

**整体成立，R3 的 3 处修正已全部采纳。** R2 第 ② 条（保存 ≠ 完成）牵出的**架构判断**（§0.2）
仍是全案最重要的结论；R3 第 ⑦ 条（全文规则）则把「填写规则」从**AI 生成口径**扩成
**人机共读的填写方法** —— 这是本轮最大增量。

### 0.1 R2 修正的 4 处

| # | 用户原话 | 归因 | 修正 |
|---|---|---|---|
| 1 | 「顶部的一级菜单位置错误了，应该在 3 栏页面的第三栏」 | 上一版把 5 个功能按钮横跨**整个页面顶部**（压在第 1/2/3 栏之上），层级错位 —— 它是**第 3 栏的菜单**，不是页面级的 | 菜单移进**第 3 栏顶部**；顶行只留「当前文档是谁 + 全局未保存提醒」 |
| 2 | 「用户随时可以保存……保存的时候需要判断该文档所有信息全部完成后，再更改该文档设置为已完成」 | 现在只有「有/无契约行」二元，**保存了就当成配好了** | **三态状态机**：`未设置规则` / `正在设置` / `已完成设置`，**完成度实时算**（§2） |
| 3 | 「保存按钮应该固定居底部」 | 保存按钮在页面顶部操作条里，与编辑区离得远 | 第 3 栏**底部固定保存条**，任何时候都能点（§4.1） |
| 4 | 「如果有信息没有保存应该自动提醒操作者」 | 切换文档/功能会**静默丢弃**未保存的改动 | 切换前**弹确认** + 左树**橙点** + 顶行**全局计数**（§4.2） |

### 0.2 ★★ 架构判断：完成度是「算出来的」，不是「存出来的」

`cert_standard_doc_contract.Status` 这一列**已经存在**（`varchar(20)`，默认 `draft`），
看起来正好可以拿来存三态。**但建议不要。**

| | 落库 `Status` | **实时计算**（推荐） |
|---|---|---|
| 谁负责回退 | ❌ **没有人** —— 删锚点、换空白模板、解绑提示词都会让文档从「已完成」退回「正在设置」，但**这些操作分散在 4 个端点**，没有一处会去改 `Status` | ✅ 自动 —— 状态由原子字段推导，**永远和事实一致** |
| 后果 | 状态**必然漂移** ⇒ 左树筛选出的「已完成」里有跑不通的文档 ⇒ 用户不再信任筛选 | 无 |
| 代价 | 每次读要算 | 每次读要算 —— 但**所需原子字段全都已有**，是**纯内存计算，零额外查询** |
| 新增列 | 需要（或复用 `Status`，与它的 `draft` 语义打架） | **零** |

**做法**：后端在 `directory-tree` 的节点 `Extra` 里下发 **`setupStatus`**（`none`/`draft`/`done`）
与 **`missingItems`**（缺失项文本数组），前端**只展示、不计算**。
口径**唯一在后端**，前端与后端不可能漂移。

> ⚠️ 反例说明为什么必须这样：用户手动把某个锚点的「未配来源」配好 ⇒ 文档该变「已完成」；
> 但若状态是落库的，得靠「保存锚点」这个动作顺手去更新契约行 ——
> 而锚点保存走的是 `DocTemplateAnchor/save-batch`，**它根本不知道契约表的存在**。

### 0.3 三个状态的判据（唯一口径）

| 状态 | 判据 |
|---|---|
| **未设置规则** | 无 `cert_standard_doc_contract` 行 |
| **正在设置** | 有契约行，但**必需项**没全过 |
| **已完成设置** | 有契约行，且**必需项**全过 |

**必需项**（决定状态，也是「测试验证」的通过条件 —— **两处同源**）：

| 类型 | 必需项 |
|---|---|
| 通用 | ① AI 语义分析完成（标签 + 作用）　② 文档类型已确认 |
| `editable` 追加 | ③ 锚点已扫描，且**无「未配来源」锚点** |
| `fixed` 追加 | ③ 标签非空　④ 文档作用非空　<span>（⛔ **不要求指纹** —— 否则 PDF 会永远完不成）</span> |

**建议项**（**不影响状态**，只在保存条给一个黄标）：
全文规则已挂接、填写规则与说明非空、`fixed` 的指纹规则（未实现）。

> ★ 为什么「全文规则」不算必需：设计上**不挂接也能跑**（运行期只按锚点逐格填），
> 把它列为必需会让一批文档卡在「正在设置」而用户根本不想配。

### 0.4 R3 修正的 3 处

| # | 用户原话 | 归因 | 修正 |
|---|---|---|---|
| 5 | 「由于第三栏空间比较小，顶部的一类菜单，可以考虑九宫格模式，因为不能为了控制第三栏的空间，让常用菜单被遮挡」 | 第 3 栏只有 **610px**：横向 5 项 ≈ 550px 已贴边，**再加功能就溢出**；纵向省宽但吃高度 | 菜单改**九宫格（2 列）** —— **宽高都省**，4~6 项都一眼看全（§3.1） |
| 6 | 「文档的类型应该是第一级菜单，这个菜单可以和语义分析在一起，因为无论哪种文档，语义分析都还是必须要进行设置的，文档类型只需要设置一个类型没必要单独设置一页」 | 「语义分析」与「类型设置」被拆成两个平级菜单，但**前者是任何文档的必经步骤**，**后者只是点一下卡片** | 合并为第一项 **「识别与类型」**（页内两步引导：① 分析原始文件 → ② 确认类型）⇒ 菜单 **5 → 4 项**（§3.2） |
| 7 | 「全文填写规则，即使没有任何 ai 填入项，也可以阐述该文档如何筛选企业的材料，如何描述哪些单元格如何填写……首先有几个固定内容：1 所有的锚点、2 企业的相关参数、3 填写方法，这些内容类似书签，可以点击形成 `[xxx锚点]`」 | 现有「全文规则」只有**挂接/解绑提示词**一个开关，**没有任何编辑能力** —— 想写也无处下笔 | 重构为**书签 + 编辑器**：左侧三组可点素材（① 锚点 ② 企业参数 ③ 填写方法）⇒ 点一下**插入到光标处** ⇒ 拼出完整填写方法（§8.5） |

> ★ 由第 7 条牵出一个**定位修正**：全文规则**不再只服务于「AI 生成」**。
> 它是**人机共读的填写方法** —— 人看「这格要什么材料、怎么筛」，机器拿它做生成口径。
> ⇒ 因此 **`fixed` 文档也必须能写全文规则**（R2 曾把它禁用，R3 解禁，见 §7.1）。

```
├────────────────────────┬──────────────────────────┬──────────────────────────────────────────────┤
```

> 菜单形态**三选一**（原型右上角可实时切换对比）：**九宫格（默认 · 推荐）** / 横向 / 纵向。

**五条硬规则**：

| # | 规则 | 解决什么 |
|---|---|---|
| **R1** | 顶行只放**页面级**信息：当前文档 + 全局未保存提醒 + 类型闸门 | 层级错位 |
| **R2** | **一级功能菜单 = 第 3 栏的菜单**，与第 3 栏内容是同一层级 | 位置错 |
| **R3** | **第 3 栏底部固定保存条**，任何时候可保存 | 保存够不着 |
| **R4** | 功能禁用**不静默** —— 置灰 + 悬停给原因 | 反馈缺失 |
| **R5** | **菜单必须全部可见** —— 九宫格让「常用项永不被遮挡」 | 为省空间牺牲可达性 |

## 2. 三态状态机（R2 新增）

```
        ┌──────────────┐   首次保存（哪怕只填一项）
        │ 未设置规则    │ ────────────────────────────┐
        │ (无契约行)    │                             ▼
        └──────────────┘                   ┌──────────────────┐
                                           │   正在设置        │
                   必需项被破坏             │ (有行，必需项未全过)│
        ┌──────────────────────────────────┤                  │
        │                                  └────────┬─────────┘
        │                                           │ 必需项全过
        │                                           ▼
        │                                  ┌──────────────────┐
        └──────────────────────────────────│  已完成设置       │
                    必需项被破坏            │ (有行，必需项全过) │
                                           └──────────────────┘
```

**关键**：状态**自动前进也自动回退**。
- 前进：补齐最后一项必需项 ⇒ **下一次读**就是「已完成」
- 回退：删锚点 / 换类型 / 清空作用 ⇒ **下一次读**就退回「正在设置」

> ⛔ **没有「标记为完成」按钮** —— 完成是**事实的推论**，不是用户的声明。

### 2.1 与「测试验证」的关系

**必需项清单 = 「测试验证」的通过条件 = 「已完成设置」的判据**，三处同源。

| 概念 | 含义 | 用途 |
|---|---|---|
| 必需项 | 4 项（或 3 项）检查 | 唯一的**中间表示** |
| 已完成设置 | 必需项全过 | 左树筛选、保存条状态标签 |
| 可发布 | 必需项全过 **且** 已通过校验 | `publish` 端点的前置 |

⇒ **实现上只写一份 `missingItems()`**，三处都调它。⛔ 不要写三份判据（必然漂移）。

## 3. 一级功能菜单（第 3 栏顶部）

### 3.1 菜单形态：三选一（D6）

第 3 栏固定 **610px** 宽 —— 这是全部取舍的前提。

| 形态 | 布局 | 优点 | 代价 |
|---|---|---|---|
| **九宫格**（★ 默认 · 推荐） | 2 列网格，每格 = `图标 + 名称` + 右侧徽标 | **宽高都省**；4~6 项都**一眼看全**；**加功能不挤爆**；常用项**永不被遮挡** | 比横向多占 ~24px 纵向 |
| 横向 | 顶部一排，两行式（上行图标+名称、下行徽标） | 最省纵向 | 5 项 × ~110px = 550px，**已贴边**；**再加一个功能就溢出**（要么换行要么横向滚动 ⇒ 遮挡） |
| 纵向 | 左侧竖排，一行式 | 徽标**对齐成一列**，扫读最顺 | 占 ~44px 纵向；**挤占内容区** |

> **推荐九宫格**。它同时解决了横向的「加功能就溢出」和纵向的「吃掉内容高度」——
> 而且用户原话说得很准：**「不能为了控制第三栏的空间，让常用菜单被遮挡」**。
> 4 项时是 2×2，未来加到 6 项是 2×3，**都不用改布局**。

### 3.2 菜单项：5 → 4 项（★ R3 合并）

| # | 菜单 | 合并说明 |
|---|---|---|
| 1 | **✦ 识别与类型** | **= 原「语义分析」+「类型设置」合并**。理由：① **语义分析是任何文档的必经步骤**（含 PDF / 图片），它是「第一件事」；② 而**类型只是一个值**，点一下卡片即可，**不值得单独占一页**。页内做成两步引导：`① 分析原始文件 → ② 确认文档类型` |
| 2 | **⚓ 锚点设置** | 不变（仅 `editable`） |
| 3 | **ƒ 全文规则** | 不变（★ R3 对 `fixed` **解禁**，见 §7.1） |
| 4 | **✓ 测试验证** | 不变 |

### 3.3 状态标记口径（唯一入口 `computeNav()`）

| 功能 | 适用 | 徽标口径 | 禁用条件 |
|---|---|---|---|
| **✦ 识别与类型** | 全部文档 | `分析中`(w) / `未分析`(w) / **`待确认类型`**(w) / `已分析 · 可编辑`(s) / `已分析 · 固定`(s) | 永不 |
| **⚓ 锚点设置** | 仅 `editable` | `未扫描`(w) / `N 个`(s) / `N 个 · M 未配`(**d**) | `fixed` ⇒ 禁用 |
| **ƒ 全文规则** | **全部文档**（R3 解禁） | `已挂接`(s) / `未挂接`(w) | **永不** |
| **✓ 测试验证** | 全部文档 | `待分析`(i) / `未验证`(w) / `N 张红牌`(**d**) / `已通过`(s) | 未分析 ⇒ 禁用 |

> ★ 徽标是**一屏内的状态总览**：用户扫一眼 4 个徽标就知道「这份文档还差什么」，不用逐个点开。

## 4. 保存与未保存提醒（R2 新增）

### 4.1 固定底部保存条

```
┌────────────────────────────────────────────────────────────────────┐
│ ●正在设置   ▓▓▓▓▓░░░ 3/4  缺：锚点来源   [建议 2 项]   ●未保存 [保存] │
└────────────────────────────────────────────────────────────────────┘
```

| 元素 | 说明 |
|---|---|
| 状态标签 | 三态之一（`未设置规则` / `正在设置` / `已完成设置`），**只读** |
| 进度 | `已完成必需项 / 必需项总数`（2、3 或 4） |
| 缺失项 | 直接列出，如「缺：锚点来源」；全过时显示「必需项已全部完成」 |
| 建议项 | 黄标 + 悬停展开（**不影响状态**） |
| 未保存标记 | `● 未保存`（有 dirty 时出现，保存按钮同时变主色） |
| **保存** | **任何时候可点**。保存 ≠ 完成 —— 保存后状态可能仍是「正在设置」 |

**保存后的反馈**（必须明确，否则用户不知道保存到底改变了什么）：
- 仍有缺失 ⇒ `已保存 · 当前状态「正在设置」（还缺：锚点来源）`
- 全过 ⇒ `已保存 · 该文档状态已更新为「已完成设置」`

### 4.2 未保存提醒（三处）

| # | 位置 | 行为 |
|---|---|---|
| 1 | **切换文档 / 切换功能时** | 弹确认：`取消` / `丢弃改动` / **`保存并继续`**。⛔ **绝不静默丢弃** |
| 2 | **左树节点** | 有未保存改动的文档打**橙点**；侧栏底部计数 `● N 未保存` |
| 3 | **顶行** | `⚠ N 份文档有未保存改动`（可点击跳到第一份未保存的） |

> ⚠️ **实现注意（原型里已踩）**：编辑框用 `onblur` 写回 state 并标 dirty，
> 但**不能整页重渲染** —— 否则「点保存按钮」会先触发 blur → 重渲染 → **按钮元素被替换 → click 丢失**。
> ⇒ blur 只做**局部刷新**（保存条 / 左树 / 顶行），整页重渲染只在切换功能/文档时做。

### 4.3 「保存」到底保存了什么

保存 = 把**当前功能的编辑内容**写入后端，**不影响其他功能已保存的内容**。
- `语义分析` 页保存 ⇒ 写 `TagsJson` / `DocPurpose` / `FillHint`（人工改的标 `manual`，批量重跑不覆盖）
- `类型设置` 页保存 ⇒ 写 `DocCategory`（**同时同步 `cert_standard_directory_file.DocCategory` 权威列**）
- `锚点设置` 页保存 ⇒ 走 `save-batch` 写锚点行
- 每处保存后，后端**回传最新的 `setupStatus` + `missingItems`** ⇒ 保存条与左树立即刷新

## 6. 类型推导规则（沿用 R1）

```
.pdf .jpg .jpeg .png .bmp .tif .tiff .gif .webp  ⇒ 预选 fixed
.doc .docx .xls .xlsx .ppt .pptx .txt            ⇒ 预选 editable
其他                                              ⇒ 无预选
```

- **只是预选**，用户可改；**预选 ≠ 已确认**（未确认时闸门画虚线框 + 顶行提示）
- **AI 分析结果可覆盖**（PDF 版的《内审计划》⇒ 提示改回可编辑）
- ⛔ **不改 DB 默认值**（`DocCategory` 默认保持 `editable`；预选在推导层做）
- ⚠️ **实测：668 份标准文档 `FileType` 全是 doc 567 / xls 44 / docx 36 / xlsx 20 / txt 1 —— ⛔ 0 份 PDF/图片**
  ⇒ 这条规则**目前无数据可作用**，是为未来准备的

## 7. `fixed` 文档的一期口径（沿用 R1，R3 修正）

| 项 | `fixed` 一期要求 | 说明 |
|---|---|---|
| 文档类型 | ✅ 必须确认 | 闸门 |
| AI 语义分析（标签 + 作用） | ✅ **必须**（计入必需项） | 用户明确要求 |
| 填写规则与说明 | 🟡 建议 | **不影响状态** |
| 指纹规则 | ⛔ **不要求** | 二期实现；做成独立能力、可后补 |
| 空白模板 / 锚点 | ⛔ 不适用 | 直接禁用 |
| **全文规则** | ✅ **可用（★ R3 解禁）** | 见 §7.2 |

**理由**：`fixed` 文档的**一期目标 = 「能被匹配」**（企业传营业执照 ⇒ 系统认出是哪一格），
**不是「能被生成」**。若把指纹列为必需，一批 PDF 会**永远停在「正在设置」**。

### 7.1 ★ R3 修正：`fixed` 的全文规则**不再禁用**

R2 曾把「全文规则」对 `fixed` 一并禁用，**这是错的**。用户第五轮原话：

> 「全文填写规则，即使没有任何 ai 填入项，也可以阐述该文档**如何筛选企业的材料**，
> 如何描述哪些单元格如何填写。」

⇒ 全文规则的**定位被扩展**了：

| 类型 | 全文规则在这里是什么 |
|---|---|
| `editable` | ① 给机器的**生成口径**（整篇怎么组织、口吻怎么写）＋ ② 给人的**填写方法** |
| `fixed` | **给人的「上传要求 / 筛选口径」** —— 这一格要什么样的材料、怎么判断合格、不合格怎么办 |

⇒ 因此菜单里 **`ƒ 全文规则` 对两种类型都可用**（仅 `⚓ 锚点设置` 仍只对 `editable` 可用）。
`fixed` 的全文规则**仍是建议项**（不影响「已完成设置」），但**建议项文案改为「未写上传要求」**，
因为对 `fixed` 而言它恰恰是最有价值的一条。

## 8. AI 语义分析落地（沿用 R1）

**缺口**：`StandardDocContractController.Analyze` 的 `Semantic` 段是**源码硬编码** `Status="not_wired"`
—— 不是「缺提示词」，是**压根没接线**。

**路径**（已实证）：

```
Analyze(fileCode)
  ├─ 读 cert_standard_directory_file.MarkdownPath → MinIO 下载 → Markdown 全文
  ├─ PromptWorkbenchService.AnalyzeForQueueAsync(Types.Group,   standardCode, [(name, md)], ref) → tags
  ├─ PromptWorkbenchService.AnalyzeForQueueAsync(Types.Content, standardCode, [(name, md)], ref) → purpose / infoItems / fillHint
  └─ upsert cert_standard_doc_contract（IsManualCorrected=1 ⇒ ⛔ 不覆盖）
```

| 实证事实 | 值 |
|---|---|
| `AnalyzeForQueueAsync` 可见性 | **`public`**（`PromptWorkbenchService.cs:565`）⇒ 可同步调用，无需进队列 |
| 提示词 | `doc_group` / `doc_content` 各 1 版，均绑 `846dec4b-…`（9001） |
| `MarkdownPath` 覆盖 | 668 行中 **179 行 completed** |
| 单文件成本 | **2 次 LLM ≈ 15~25s** ⇒ 前端 loading + **axios 超时 ≥120s**；批量走队列 |

**三态口径**：`ok` / `blocked`（无 Markdown、该标准无提示词）/ `failed`（LLM 报错）。
⛔ `blocked` **不是** `failed`，要给「先去转换 / 先配提示词」的人话引导。

**分析对象 = 原始文件**（`MarkdownPath`），⛔ **不读空白模板**。

> ★ R2 关联：**AI 分析结果在保存前不落库** ⇒ 分析完成后保存条亮「未保存」，
> 用户点保存才写入，**保存后状态按 §0.3 重算**（很可能仍是「正在设置」，因为锚点还没配）。

## 8.5 全文填写规则（★ R3 新增 · 本轮最大增量）

### 8.5.1 定位：**人机共读的填写方法**

```
┌─ 人读 ────────────────────────────────────────────────┐
│  这份文档要什么样的企业材料？怎么筛？哪些格怎么填？    │  ← 即使没有任何 AI 填入项，也有价值
└───────────────────────────────────────────────────────┘
┌─ 机器读 ──────────────────────────────────────────────┐
│  整篇怎么组织、口吻怎么写、按什么顺序生成              │  ← 有 AI 填入项时，这是生成口径
└───────────────────────────────────────────────────────┘
```

⇒ 同一份文本，**两种读者**。所以它**不是**「有 AI 项才需要配的东西」，
而是**每一份标准文档都值得写**的东西。

### 8.5.2 三组「书签」（用户指定，固定内容）

| # | 组 | 内容来源 | 点击插入什么 |
|---|---|---|---|
| ① | **锚点** | **本模板扫出来的全部锚点**（`cert_doc_template_anchor`） | 锚点原文 token，如 `{{ENT_NAME}}`、`{{table:审核安排}}`、`{{ai:quality_policy}}` |
| ② | **企业参数** | 全局参数（`cert_fill_param_def`）+ 企业资料字段表达式 | `{{ENT_NAME}}`、`{{STD_NO}}`；表达式 `{{enterprise.Name}}` |
| ③ | **填写方法** | **内置片段库**（一期静态，二期可维护 —— D9） | 写法约定文本，如「日期一律用 YYYY-MM-DD」「序号从 1 起连续编号」 |

> ★ 三组的**排序即使用顺序**：先引用锚点（这一格要什么）⇒ 再引用参数（值从哪来）⇒
> 最后写方法（怎么写）。用户原话「首先有几个固定内容」正是这个顺序。

> ⚠️ **第 ① 组的语义已由 `42` 号裁定（D13）**：插入 `{{ENT_NAME}}` = **「给 ENT_NAME 这条锚点补一句说明」**，
> **⛔ 不是「声明这个锚点存在」** —— 锚点清单由引擎在 `{{__FILL__.anchors}}` 处**自动注入**，
> 提示词**不承担「列清单」职责**。
> ⇒ 页面**不做**「锚点是否被引用」的必填校验；**已引用清单保留**（帮人回顾）；
> **未知 token 标红**（§8.5.3 约束 3）**恰好成为两条通路的一致性检查器** —— 提示词手写了锚点表里没有的 token，立即可见。
> 详见 `42-填写通路职责边界与AI节点裁定-V1.md`。

### 8.5.3 交互：**素材 + 光标插入**（★ R5 改上下结构）

```
┌ 全文填写规则 ────────────────────────────────────────────────────────┐
│ [已挂接]                                     [新建][挂接已有][解绑]   │
│ ┌ 素材（上）───────────────────────────────────────────────────────┐ │
│ │ ⚓ 锚点       5  [{{ENT_NAME}}] [{{文件控制程序}}] [{{table:审核安排}}] →│
│ │ ▤ 企业参数   7  [企业名称] [统一社会信用代码] [法定代表人] →        │ │
│ │ ✎ 填写方法   6  [日期格式] [金额单位] [序号规则] [签字要求] →       │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│ ┌ 提示词（下 · 占满剩余高度）──────────────────────────────────────┐ │
│ │ 按年度内审方案逐条填写，每行一个受审部门。                        │ │
│ │ 企业名称：{{ENT_NAME}}                                           │ │
│ │ 审核日期：{{AUDIT_DATE}}                                         │ │
│ │                                                                  │ │
│ │ 填写方法：                                                       │ │
│ │ - 日期一律用 YYYY-MM-DD（如 2026-03-11）。                       │ │
│ │ - 序号从 1 起连续编号，不得留空行。                              │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│ 已引用 2 个： {{ENT_NAME}} {{AUDIT_DATE}}                            │
└──────────────────────────────────────────────────────────────────────┘
     ↑ 点素材 ⇒ 插入到光标处
```

**三条实现约束**（原型里已按此写，实施时必须照做）：

| # | 约束 | 原因 |
|---|---|---|
| 1 | **插入的是引擎原文 token**（`{{ENT_NAME}}`），⛔ 不是可读标记（D8） | 填充引擎**零改动**即可识别；用可读标记就要多一层解析，且解析失败是静默的 |
| 2 | 插入 / 输入后**只局部刷新**（保存条 + 左树 + 顶行），⛔ **绝不整页重渲染** | 整页重渲染会**丢焦点**（用户接着打不了字）、**丢点击**（见 §4.2 注） |
| 3 | 编辑区下方**实时列出「已引用」清单**，未知 token **标红** | token 是**拼字符串**，最容易打错；标红能把「引擎取不到值 ⇒ 静默留空」提前暴露 |

### 8.5.4 落库

| 项 | 做法 |
|---|---|
| 存哪 | `cert_doc_fill_prompt`（**已有表**）。一期**只暴露一个编辑区** ⇒ 落到 `UserTemplate` |
| `SystemPrompt` | 一期用系统默认（角色设定），页面**不暴露**；二期需要再放出来 |

### 8.5.5 引擎侧：**零改动**

书签插入的就是 `{{...}}` 原文，而 `{{...}}` 本来就是这个系统的锚点语法
（见 `Shared/Fill/AnchorClassifier.cs`：`ai:` → block、`table:` → table、`@PAGE` → domain(auto)、

### 8.5.6 布局：**上素材 / 下编辑**（★ R5）

**问题**：R4 版本把「素材区」放左侧、「提示词编辑区」放右侧（**左右分栏**）。
第 3 栏总共只有 **610px** —— 素材区固定 210px 后，**编辑区只剩约 380px**。
而**提示词是长句，最需要宽度的地方反而最窄**。用户原话：

> 「全文填写规格，我们应该分为上下结构，一块区域专门设计提示词需要的锚点，全局参数，及填写方法这些，
> 下方才是我们的提示词，因为我们 3 栏，留给我们设置的空间有限。」

**做法**：改**上下结构**（`.pmpage { display:flex; flex-direction:column }`）。

| 区 | 内容 | 高度 |
|---|---|---|
| **上 · 素材区**（`.pm-mats`） | **三行**，每组一行：**⚓ 锚点** / **▤ 企业参数** / **✎ 填写方法**；每行 = 组名 + 条数 + chip 列表 | **固定 ~104px** |
| **下 · 编辑区**（`.pm-ed`） | `textarea`（`flex:1` 占满剩余高度）+ 下方「已引用」清单 | **占满剩余**（`min-height:150px`） |

**三个好处**：

| # | 好处 | 说明 |
|---|---|---|
| 1 | 编辑区宽度 **~380px → 610px** | 一行能写更多字，长句不必频繁换行 |
| 2 | 素材区高度**固定** ⇒ 编辑区**不跳动** | 条目增减（锚点 5 个 vs 12 个）**不改变布局** |
| 3 | 上下顺序 = **使用顺序** | 先看素材 → 再写提示词；左右分栏反而是「先左后右」的横向扫读 |

> ★ **素材区必须用「横向滚动」而不是「换行」**：换行会让高度**随条目数变化**
> （锚点 5 个 vs 12 个 = 高度差一倍），而上下结构里**素材区一变高，编辑区就被挤下去**。
> ⇒ `.pmrow .pmb { flex:1; min-width:0; overflow-x:auto }`，**每行高度恒定**。

> ⚠️ 与 §13「说明外移」的关系：全文规则页**不放 `.hint` 提示行** ——
> 页面只剩「挂接状态 + 素材区 + 编辑区 + 已引用清单」，**全是事实与操作**（符合 §13.2）。
> 素材区里「该模板还没有扫到锚点」这类**空状态文案**是**事实**，保留。

## 15. 按项目前端风格实施（★ R5 · 用户第七轮要求）

> 用户原话：「真正完成的时候，**请按我们项目风格进行设置**」。

**前提**：本方案里的 HTML 原型**只是交互规格**（布局、字段、状态、点击后的行为），
**⛔ 不是样式规范**。原型为了自包含，用了 `#fbfcfe` / `11px` / `<button class="btn pri">` 这类**硬编码**写法；
真正写页面时**一律换成项目既有组件与令牌**。

### 15.1 原型 ↔ 项目实现 对照表

| 原型里写的 | 项目里必须写成 | 依据 |
|---|---|---|
| `<button class="btn pri">保存</button>` | `<el-button type="primary">保存</el-button>`（**必须显式 `type`**） | 法条 **S04**（`type` 只三档，见 S03） |
| `<div class="tag s">已挂接</div>` | `<YzhStatusBadge>` | 法条 **S08** |
| 空态文案 `<span class="tiny muted">（空）</span>` | `<YzhEmptyState>` | 法条 **S05** |
| 未保存确认（切换文档/功能前） | `confirmOrFalse()`（**⛔ 不手写 `ElMessageBox`**） | 法条 **S06** |
| 任何弹层（挂接已有 / 新建提示词 / 帮助浮层可选） | `YzhDialog` / `YzhFormDialog` | 法条 **S07** |
| 图标 `⚓ ƒ ✦ ✓` | `@element-plus/icons-vue`（⛔ 禁 `.bi`、⛔ 禁 emoji 当图标） | 法条 **S09** |
