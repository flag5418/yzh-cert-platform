# 41 · 文档填写规则页交互重构方案（待审批）· V2

> **V2 相对 V1 的变化**：用户 2026-10-04 第二轮反馈把问题从「右栏页签怎么排」升级为
> **「整页布局怎么重排」**，并追加了一条**能力缺口**（AI 分析不产出标签与作用）。
> V1 的结论（类型优先 + 锚点卡片化）**仍然成立且被保留**，但承载方式从
> 「右栏加个选择器」改为 **「四阶段状态机」**。
>
> **配套可点原型**：`原型/41-文档填写规则页-布局重构原型-V1.html`（浏览器直接打开）

## 0. 一句话结论

**整体成立，且 V1 的方案不够彻底。**

用户的判断链是自洽的：
1. 「类型高于一切」⇒ 类型**不是**右栏里的一个控件，而是**整页的分叉闸门**；
2. 「元素全部堆叠、没有主次」⇒ 现在**任何时刻页面上都同时存在 7 个操作按钮 + 4 个页签 + 1 条引导**，
   用户无法判断「现在该干什么」；
3. 「AI 分析不产出标签和作用」⇒ 这是**能力缺口**，不是交互问题 —— 必须先补上，否则「识别」这一步是空的。

**结论**：本页要重做成 **「① 识别 → ② 备模板 → ③ 配规则 → ④ 校验发布」的四阶段状态机**，
任何时刻只显示当前阶段该做的事；`fixed` 类型直接砍掉 ②③ 的主体。

**要裁决 4 条**（§7）：D1 阶段能否自由跳转 / D2 卡片展开态 / D3「填写说明」落库方式 / D4 提示词是否扩展共享模板。

## 1. 问题归因

| 用户原话 | 真实归因 | 性质 |
|---|---|---|
| 「AI 分析不能生成该文档的标签和文档作用」 | `StandardDocContractController.Analyze` 的 `Semantic` 段**恒返回** `Status="not_wired"`（源码硬编码）。真正能产出标签/作用的执行器 `EnterpriseOriginalAnalyzeExecutor` 只对**企业原始资料**开放，标准侧未接线 | **能力缺口**（非交互问题） |
| 「分析的是原始文件，不受空白文档的影响」 | 现有 `Analyze` 里：字段提取走 `DocExtractionRuleService.AIAnalyzeAsync`（读 `DocContent` 快照），锚点扫描走**空白模板**。**语义分析压根没接** ⇒ 「分析对象是谁」这件事从未定义过。本次必须**显式定义**：语义分析读**原始文件**的 `MarkdownPath` | **语义未定义** |
| 「文档类型高于一切，固定文档很多 tab 都不需要填」 | 类型现在藏在第 3 个页签「文档契约」里，且**类型未定时 4 个页签就已全部渲染** ⇒ 用户看到 4 个不知道该点哪个。V1 只把选择器提到右栏顶部 —— **不够**，`fixed` 时页签虽变少，但操作条、引导条、统计条**照旧全在** | **闸门位置错误** |
| 「整个页面元素全部堆叠，没有主次，没有清理的逻辑」 | 现页面同一屏内有：7 个操作按钮 / 1 条三步引导 / 中栏预览 / 4 个页签 / 锚点统计条 / 4 个筛选 / 表格 / 侧边栏。**没有任何机制让「已完成的步骤消失」** ⇒ 每一步的认知负担都是全量 | **缺少状态机** |
| 「点击锚点、设置规则、必填好像没有效果」 | ① 「必填」是侧边栏里的开关，**必须滚到底点保存**才生效；② 列表是表格，改完只有一个小徽标变；③ 侧边栏 580px **盖住中栏预览** | **反馈缺失 + 布局冲突** |
| 「还不如把锚点改成卡片模式」 | 表格一行 ~40px 塞不下「状态徽标 + 来源摘要 + 操作按钮」 | **呈现形式** |

**一句话**：本页缺的**不是功能**，而是**一个能表达「我现在在哪一步、这一步该干什么、干完这步什么会消失」的骨架**。

## 2. 方案总览

### 2.1 布局：四阶段状态机（V2 新增，是本轮核心）

**现状**（一屏全量）：
```
┌ 操作条：[下载][上传][扫描] │ [分析][校验][发布]  ●草稿 ●可编辑 ┐
├ 引导条：① ② ③ 三步引导（永远都在）──────────────────────────┤
├ 中栏预览 ─────┬ 右栏 [锚点|全文|契约|校验] 4 个平级页签 ────────┤
│               │ 统计条 / 筛选 / 表格 / 点行弹侧边栏            │
└───────────────┴──────────────────────────────────────────────┘
```

**改为**：
```
┌ 身份条（常驻）：📄 陪审人员.doc  │  类型闸门 [可编辑|固定]  │  ①识别─②备模板─③配规则─④校验 ┐
├ 阶段任务条（只显示当前阶段的 1~3 个主按钮）──────────────────────────────────────────────┤
├ 中栏预览（随阶段切换「原始文档 ↔ 空白模板」）┬ 右栏：当前阶段的**唯一面板** ────────────────┤
└──────────────────────────────────────────────┴──────────────────────────────────────────┘
```

**四条硬规则**（这就是「主次」和「清理逻辑」）：

| # | 规则 | 解决什么 |
|---|---|---|
| **R1** | **身份条常驻**：文件名 + 类型闸门 + 阶段进度点。用户永远知道「我是谁 / 我是什么类型 / 我在第几步」 | 迷路 |
| **R2** | **阶段任务条只放当前阶段的按钮**。同一时刻**最多 3 个可点按钮**（现为 7 个） | 按钮堆叠 |
| **R3** | **右栏只显示当前阶段的面板**，不再是 4 个平级页签。做完的阶段**从右栏消失**，只留进度点 | 无清理逻辑 |
| **R4** | **阶段未就绪 ⇒ 进度点置灰且点击给明确原因**（不静默失败） | 反馈缺失 |

**阶段与前置条件**：

| 阶段 | 前置 | editable | fixed |
|---|---|---|---|
| ① 识别 | 选中文件 | ✅ | ✅ |
| ② 备模板 | ① 完成 且 类型=editable | ✅ | ⛔ **不出现** |
| ③ 配规则 | ② 完成（有空白模板） | 锚点规则 + 全文规则 | ⛔ **不出现** |
| ③′ 指纹规则 | ① 完成 且 类型=fixed | ⛔ | ✅（编辑器未实现，占位） |
| ④ 校验发布 | ③/③′ 完成 | ✅ | ✅ |

> ★ 注意：**`fixed` 的阶段序列是「① → ③′ → ④」，三步**。
> 这正是用户要的「固定文档很多 tab 都不需要填写了」——
> 不是「页签变少」，而是**这些阶段整体不存在**。

### 2.2 类型优先：从「控件」升级为「闸门」

**V1 的做法**（右栏顶部加选择器）**不够**。V2 改为：

- 类型闸门放在 **身份条右侧**，**任何阶段都可见、随时可改**；
- 切换类型 ⇒ **立即落库**（复用 `StandardDocContract/save`）**并重建阶段序列**：
  - `editable → fixed`：清空已上传模板与锚点（内存态，库内不动），跳到 ③′；
  - `fixed → editable`：跳回 ②；
- **类型未定时**，闸门显示 `⚠ 类型未定` 黄标，且 ②③ 的进度点置灰。

> ⛔ 与 V1 一致的坚持：**「文档契约」页签改名「文档信息」** —— 分类已经上移到身份条，
> 名字不改会让人以为分类还在里面。

### 2.3 AI 语义分析补齐（V2 新增，对应用户第 1 条）

**分析对象**：该标准文档的**原始文件**（`cert_standard_directory_file.MarkdownPath`）。
**⛔ 不读空白模板** —— 空白模板是「我们要求企业怎么填」，
而语义分析要回答的是「**这份文档本来是什么**」，用于**匹配企业提供的不可控文档**。

**产出四样**（前三样落库，第四样只做建议）：

| # | 产出 | 落库列 | 用途 |
|---|---|---|---|
| 1 | **分类标签** | `TagsJson`（值必须 ∈ `cert_tag_dict.TagCode`） | 与企业文档的标签做粗筛 |
| 2 | **文档作用**（四段式） | `DocPurpose` | 语义匹配的主力特征 |
| 3 | **填写规则与说明**（新增） | `FillHint`（**新增列**，见 §4.3） | 给企业看「该填什么、怎么填」，用于**不可控文档的语义匹配 + 填报引导** |
| 4 | **文档类型建议** | 不落库，回前端 | 驱动 §2.2 的类型闸门 |

**技术路径**（⛔ 不新写 LLM 逻辑）：

```
StandardDocContractController.Analyze(fileCode)
  ├─ 读 fileRow.MarkdownPath ──→ MinIO 下载 → Markdown 全文
  ├─ PromptWorkbenchService.AnalyzeForQueueAsync(Types.Group,   standardCode, [(fileName, md)], ref)  → tags
  ├─ PromptWorkbenchService.AnalyzeForQueueAsync(Types.Content, standardCode, [(fileName, md)], ref)  → purpose / infoItems / fields / tables / fillHint
  └─ upsert cert_standard_doc_contract（人工改过的 IsManualCorrected=1 ⇒ ⛔ 不覆盖）
```

**为什么可行（已实证，非推测）**：

| 事实 | 实测值 | 含义 |
|---|---|---|
| `AnalyzeForQueueAsync` 可见性 | `public`（`PromptWorkbenchService.cs:565`） | 可从 Admin 控制器**同步调用**，无需进队列 |
| `doc_group` / `doc_content` 提示词 | 各 1 版，均绑 `846dec4b-…`（9001） | 9001 可直接跑通 |
| `cert_standard_directory_file.MarkdownPath` | 668 行中 **179 行已完成** | 179 份可立刻分析，其余需先转 Markdown |
| `cert_standard_doc_contract` | **0 行**（本页承担读写） | 无历史包袱 |

**⚠️ 已知边界（⛔ 不假装已实现）**：
1. 单文件同步调用 = **2 次 LLM**（doc_group 1 份 + doc_content 1 份），约 15~25s ⇒ 前端必须 loading，
   且 axios 超时要放到 ≥120s；**批量分析应走队列**（复用 `EnterpriseOriginalQueue` 模式），本页只做单文件。
2. 其余标准（如 `475da4fe-…`）**没有提示词** ⇒ 分析会明确报「未找到生效的 doc_content 提示词」，⛔ 不静默返回空。
3. `MarkdownStatus ≠ completed` 时**不报错**，返回 `Status="blocked"` + 明确引导「需先转 Markdown」。

### 2.4 锚点卡片化（沿用 V1，已被用户认可）

**改为卡片列表**，每张卡固定三行 + 操作行：

```
┌──────────────────────────────────────────────────┐
│ {{ENT_NAME}}                          ⚠ 未配来源 │  ← 标题：锚点原文（mono）+ 状态徽标
│ 类型 标量 · 位置 正文 · 字段 ENT_NAME            │  ← 元信息行
│ 来源 全局参数 ENT_NAME → 落空留空                │  ← 来源摘要行（前端现算）
│ ──────────────────────────────────────────────── │
│ [⚙ 配置规则]        [必填 ⚪]        [删除]      │  ← 操作行
└──────────────────────────────────────────────────┘
```

**状态徽标**（互斥，优先级从高到低）：
1. `孤儿`（`IsOrphan`）—— 黄，换版后消失的锚点
2. `未配来源` —— 红，运行期必然留空（**唯一红牌来源，阻断发布**）
3. `必填` —— 蓝，已勾选必填
4. `已配` —— 绿，来源链完整

**★ 关键修复**：「必填」改为**就地开关，拨动即存**（乐观更新 + toast），
不再需要「进侧边栏 → 滚到底 → 点保存」。
侧边栏（`AnchorSidePanel`）**收窄 580px → 420px**，只覆盖右栏，**中栏预览保持可见**。

**保留现有能力**（⛔ 不删）：统计条（自动/人工/计算/未配/孤儿）、4 个快速筛选、来源链编辑器。

## 4. AI 语义分析落地方案（后端）

### 4.1 改 `StandardDocContractController.Analyze`

把 `Semantic = new { Status = "not_wired" }` 换成真实实现，**返回结构保持向后兼容**
（前端 `onAnalyze` 已读 `data.Field` / `data.Scan`，本次只新增 `data.Semantic` 的真实内容）：

```csharp
Semantic = new {
    Status    = "ok" | "blocked" | "failed",
    Message   = "...",                 // blocked 时给人话引导
    Tags      = new[] { "内审记录", … },
    DocPurpose = "…四段式…",
    FillHint   = "…填写规则与说明…",
    SuggestCategory = "editable",      // ★ 类型建议
    Confidence = 0.92m,
    ModelName  = "qwen-plus",
    DurationMs = 8421,
}
```

### 4.2 三个 `Status` 的口径（⛔ 不要混）

| Status | 触发 | 前端动作 |
|---|---|---|
| `ok` | 两次 LLM 都成功 | 回填标签 / 作用 / 填写说明 + 给类型建议 |
| `blocked` | `MarkdownPath` 为空 / `MarkdownStatus≠completed` / 该标准无提示词 | 显示**明确原因** + 下一步（「先去转换」/「先配提示词」），⛔ 不是失败 |
| `failed` | LLM 报错 / 输出不合规 | 显示错误原文 + 「可手工填写」出口 |

### 4.3 新增列「填写规则与说明」（需裁决 D3）

`cert_standard_doc_contract` **没有**承载「填写规则与说明」的列。三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 新增 3 列：`FillHint` TEXT / `FillHintSource` varchar(10) / `FillHintConfidence` decimal(3,2) | DDL + 实体 + `detail`/`save` 各加一段；与 `DocPurpose` 三件套**同构**，语义最清晰 |
| B | 新增 1 列 `FillHint` TEXT，来源复用 `AnalyzeStatus` | 省 2 列，但「AI 还是人工」分不出来，批量重跑会覆盖人工内容 |
| C | 复用已有 `Remark` varchar(500) | ⛔ 不推荐：500 字装不下（实测说明文本 200~400 字，易截断），且 `Remark` 语义是通用备注 |

> ⚠️ 另有发现：实体 `StandardDocContract` 里声明了 `MatchPrompt` / `SynthesisPrompt` 两列，
> **全项目零引用**（死列）。本次**不动**，但建议在后续清理时删掉，避免下一个人误以为有匹配提示词机制。

### 4.4 提示词侧：`fillHint` 从哪来（需裁决 D4）

`doc_content` 的 `OutputSchemaJson`（`PromptWorkbenchService.cs:112`）目前不含 `fillHint`。
而 `doc_content` 是**标准侧与企业侧共用**的提示词类型（`EnterpriseOriginalAnalyzeExecutor` 也用 `Types.Content`）。

| 选项 | 做法 | 影响 |
|---|---|---|
| **A（推荐）** | 在共享 schema 里**追加可选字段** `fillHint`；企业侧解析器不读它（`ExtractContentHints` 已按字段名逐个取，忽略新字段零成本） | 改 1 处 schema + 9001 的提示词模板追加一段；两侧都受益 |
| B | 新建提示词类型 `doc_fill_hint`（仅标准侧） | 隔离干净，但多一套提示词要维护 + 多一个作用域要绑 |

> ⚠️ 无论选哪个，**提示词模板本身要改**（`wf_prompt_template` 里 9001 那行）——
> 这属于**配置**不是代码，改完需在提示词工作台里点「生效」。

## 8. 同批缺陷（已修，2026-10-04）

| # | 缺陷 | 根因 | 修法 |
|---|---|---|---|
| 1 | tab 页签贴边无 padding | EP 有 `.el-tabs--top … .el-tabs__item:nth-child(2){padding-left:0}`（特异性 **0,4,0**）**强制抹掉首尾页签内边距**，上一轮又把 `nav-wrap` padding 归零 | `nav-wrap` 补 12px + item padding 加 `!important` 压过 EP |
| 2 | 重传模板后锚点「重复」 | `UpsertTemplateAsync` 只重置 `PublishStatus/ScanStatus/ViolationJson`，**旧锚点一条不删** ⇒ 新旧并存 | 换版（`SourceSha256` 变化）时 `InvalidateAnchorsAsync()` **软删全部旧锚点**，由重扫按 `uk_tpl_anchor` 逐条**复活并保留人工配置** |
| 3 | 保存契约报 `Invalid JSON text: "The document is empty."` | 标签为空时前端提交**空串**，而 `TagsJson` 是 MySQL `json` 列（INSERT 阶段抛错，整条失败） | 前端改发 `'[]'`；后端加 `ToJsonArray` / `ToJsonObject` **第二道闸** |

> ⚠️ 缺陷 2 的修复**只改后续行为**：用户库里已存在的那条孤儿锚点 `{{ENT_NAME}}`
> （带全局参数配置）**未被删除**，等用户裁决。

## 9. 验收口径

**布局（本轮核心）**
- [ ] 选中文件后，一屏内**可点的主按钮 ≤ 3 个**，且**全部属于当前阶段**
- [ ] 身份条任何时刻可见：文件名 / 类型闸门 / 阶段进度点
- [ ] 完成 ① 识别后，② 成为当前阶段，**① 的内容从右栏消失**（只在进度点留 ✓）
- [ ] 类型未定时，②③ 的进度点置灰，点击给出**明确原因**（不是静默无反应）

**类型闸门**
- [ ] 切到「固定格式」⇒ 阶段序列**立刻变为 ①→③′→④**（②③ 整体消失），且刷新后保持
- [ ] 切回「可编辑文档」⇒ 回到 ② 备模板

**AI 分析**
- [ ] 点「AI 分析原始文件」⇒ 产出**标签 / 作用 / 填写说明 / 类型建议**四样
- [ ] 分析对象是**原始文件**：把空白模板换成完全不同的内容，重跑分析结果**不变**
- [ ] 该标准没有提示词时，返回 `blocked` + 人话原因（⛔ 不是 `failed`，⛔ 不是空结果）
- [ ] 人工改过（`IsManualCorrected=1`）的字段，重跑分析**不被覆盖**

**锚点卡片**
- [ ] 每张卡都能看到状态徽标与操作按钮，**不需要点开任何东西**
- [ ] 拨动「必填」⇒ **无需点保存**，toast + 徽标立即变，刷新后仍为必填
- [ ] 「配置规则」打开侧边栏（420px）后，**中栏预览仍然可见**
- [ ] 重传空白模板 ⇒ 旧锚点消失，扫描后列表**只含新模板里的 token**

> 依「**三过滤器**」：F1 消除已知风险 → F2 产生复利 → F3 在关键路径（登录→建档→上传→提取→NC→报告）。

| 5 | ③ 锚点卡片 | 用户最痛的一条，但依赖骨架 |
| 6 | ② 备模板面板 | 最薄，最后做 |
