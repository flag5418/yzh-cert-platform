## 1. 总体结构：三阶段 + 仲裁

```text
            企业文档画像集合 P (N)                标准文档契约集合 C (M)
                    │                                   │
                    └──────────────┬────────────────────┘
                                   ▼
        ┌─────────────────────────────────────────────────────────┐
        │ S1 指纹识别（fingerprint）  规则/正则/关键字段组合 · 0 次 LLM │
        │   命中 → Confidence=0.95±, Status=recommended, 直通 S4     │
        │   未命中 → 进入 S2                                       │
        └───────────────────────────┬─────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────┐
        │ S2 召回（recall）· 0~低 LLM · 产出每企业文档 Top-K 候选      │
        │   多路并行：文件名 / 类别 / 关键词倒排 / 标题语义(可选向量)   │
        │   合并去重 → 每个企业文档保留 Top-K(K=10)  → 写候选 Status=pending │
        └───────────────────────────┬─────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────┐
        │ S3 精排（rank）· LLM · 对 Top-K 候选逐对打分                │
        │   输入：企业画像(作用+字段+表格摘要) × 契约(作用+字段/表格定义) │
        │   输出：五维分数 + Confidence + 理由 + 证据(JSON Schema 固定) │
        │   写候选 Status=scored/ScoreStage=ranked                 │
        └───────────────────────────┬─────────────────────────────┘
                                    ▼
        ┌─────────────────────────────────────────────────────────┐
        │ S4 仲裁（arbitrate）· 纯规则 · 阈值分流 + 冲突检测            │
        │   自动推荐 / 待人工 / 低置信折叠 / 冲突强制人工               │
        └─────────────────────────────────────────────────────────┘
```

**为什么不是「逐个标准文档对每个企业文档做 AI 语义匹配」（用户原设想）**：

| 维度 | 全量两两 LLM | 本方案 |
|------|--------------|--------|
| LLM 调用次数（N=100, M=60） | 6000 | 指纹≈100 次规则 + 召回 0 次 + 精排 ≤ 100×10/批 ≈ 100–300 次 |
| 结果可比性 | 每次调用独立，分数无共同基准 | 同批次内统一批式 prompt，可横比排序 |
| 可解释性 | 单次判断，无分维度 | 五维分数 + 证据链落库 |
| 失败影响 | 一个失败丢一对 | 单候选失败可重试，不丢全局 |
| 可控成本 | 不可控 | 按 M（配置的契约数）计上限 |

## 2. 阶段一：固定文档指纹识别

### 2.1 为什么固定文档必须先走规则

- 国家固定格式文档（营业执照、许可证、资质证书）**格式恒定、字段恒定**，LLM 是昂贵且引入不确定性的绕路；
- 指纹可给出**确定性高分**（0.95+），直接支撑自动确认，减少人工队列；
- LLM 不可用时，指纹链仍能完成固定文档的全部匹配（降级底线）。

### 2.2 指纹规则结构（存 `cert_standard_doc_contract.FingerprintJson`）

```json
{
  "version": 1,
  "fileNames": ["营业执照", "工商营业执照", "统一社会信用代码"],
  "fileNameRegex": ["营业执照.*(正本|副本|电子)?"],
  "keyFields": [
    { "name": "统一社会信用代码", "pattern": "91[0-9A-Z]{16}", "required": true, "weight": 0.5 },
    { "name": "经营范围",       "pattern": "经营范围",       "required": false, "weight": 0.2 },
    { "name": "法定代表人",     "pattern": "法定代表人|负责人", "required": false, "weight": 0.2 }
  ],
  "headerMarkers": ["中华人民共和国", "市场监督管理局"],
  "minScore": 0.8,
  "maxCandidates": 1
}
```

### 2.3 打分算法

```text
FingerprintScore = 0.4 × FileNameHit + 0.4 × KeyFieldHit + 0.2 × HeaderHit

其中：
  FileNameHit   = Σ(命中的 fileNames/regex) / 1   → 封顶 1.0；命中即强信号
  KeyFieldHit   = Σ(required 命中 ? weight : 命中×weight) / Σweight
                  任一 required 未命中 → 整体降级为「弱指纹」（score ≤ 0.6）
  HeaderHit     = 命中 headerMarkers / 总数
```

- `Score ≥ minScore`（默认 0.8）→ **指纹成立**：写候选 `RecallSource=fingerprint`、`RuleStrength=1.0`、`Confidence = max(0.95, FingerprintScore+0.1)`（封顶 0.99）、`ScoreStage=ranked`（跳过 S3）；
- `maxCandidates=1`：固定文档**一目标一属**，同分多中时取最高分并标冲突（§6）；
- 未命中 → 进 S2，但 `RuleStrength` 保留为 0（不惩罚）。

### 2.4 输入数据

指纹比对基于：① 文件名 ② `cert_ent_doc_profile_field`（`IsKeyField=1` 的字段，来自画像）③ Markdown 前 2000 字符。
因此**指纹也在画像阶段执行**（画像服务内先跑指纹，`DetectSource=fingerprint` 时可跳过 LLM），写入 `FingerprintResultJson` 供 S1 直接消费。

### 2.5 固定文档清单（P6 决策点）

首批建议（须用户圈定）：营业执照、统一社会信用代码证、生产许可证、各类资质证书、法人身份证明、体系证书（若有）。
每份固定文档的指纹规则由**管理员在契约页维护**，系统不内置硬编码规则。

## 3. 阶段二：候选召回

### 3.1 多路召回（每路独立打分，加权合并）

| 路 | 数据源 | 分数计算 | 权重 |
|----|--------|----------|------|
| R1 文件名路 | `cert_enterprise_file.FileName` vs 契约 `FileNamePattern` + `DocName` | 编辑距离相似度（归一 0–1） | 0.35 |
| R2 类别路 | 画像 `DocTypeGuess` vs 契约 `DocName`/`DocPurpose` 类别词 | 字符串包含 + 同义词表 | 0.25 |
| R3 关键词倒排路 | 画像 `FieldKeywords`/字段 `FieldName` 命中契约字段定义（`cert_doc_field_def.FieldName`）+ 契约 `Keywords` | `命中数 / min(契约字段数, 20)` | 0.25 |
| R4 语义路（可选，P2） | 画像 `DocPurpose` 向量 vs 契约 `DocPurpose` 向量 | cosine | 0.15 |
| R5 指纹弱命中路 | 指纹分数在 `[0.5, minScore)` | 直接用 `FingerprintScore` | 0.30（**取代** R1–R3 的合成，即部分命中） |

```text
RecallScore = Σ(路权重 × 路分)   （未启用的路权重按比例归一化）
```

### 3.2 召回策略

1. **按企业文档取 Top-K**（K=`ent_norm_recall_topk`，默认 10）：每个企业文档产出至多 K 条候选；
2. **硬性下限**：`RecallScore ≥ 0.15` 才入候选表（否则该文档进「无归属」清单）；
3. **标准文档视角补漏**：反向做一次「每个标准文档取 Top-K 企业文档」，并入候选集合——保证冷门标准文档不会因为企业文档侧竞争激烈而漏召；
4. **必需项保障**：`IsRequired=true` 的标准文档，若两路都无候选，至少以 `RecallSource=category` 弱候选进入（分数如实，不注水），确保人工能看见「这份必需文档没找到对应资料」。

### 3.3 R4 向量路的启用条件（P2）

- 依赖 embedding 能力（`LlmInvokeService` 现只拼纯字符串 content，**需扩展**多模态/embedding 端点）；
- 或引入本地向量库（部署复杂度上升）；
- **建议**：MVP 关闭 R4（权重归一化到 R1–R3），以 `DocTypeGuess` + 关键词倒排先跑通闭环；二期用**真实误配样本**评估 R4 增益后再决定。

## 4. 阶段三：LLM 精排

### 4.1 调用组织（批式，控制成本与一致性）

```text
对每个「标准文档契约 c」：
    取该契约下全部候选企业文档画像（≤ K' 条，默认 20）
    一次 LLM 调用：输入 c 的契约 + 数个企业文档画像，输出每条的评分
    → 拆解写回各候选
```

- 按**契约侧分组**批式调用：契约是相对稳定的「问题」，一组企业画像是「选项」，同一 prompt 内横比，**消除单对调用的分数漂移**；
- 单批超过 20 条画像时切片，每片独立调用，片内可比、片间用共享锚定样例（见 §9.3）。

### 4.2 输入构造

```text
【标准文档契约】
名称：ISO9001-质量手册
作用：…（契约 DocPurpose）
必需字段：文件编号 / 版本号 / 编制日期 / 审批人 / 适用标准 …（cert_doc_field_def 列表）
必需表格：文件修订记录表（表头：版本/日期/修订内容/审批）…（cert_doc_table_def 列表）
匹配提示词：…（契约 MatchPrompt，若配置）

【候选企业文档画像】（共 n 条）
候选1：文件名=质量手册-QM-2026-v2.docx
  作用：…（DocPurpose）
  字段：文件编号=QM-2026、版本号=v2、编制日期=2026-03-01、审批人=张三 …
  表格：文件修订记录（表头：版本/日期/修订说明/审批，3行）
候选2：…

【任务】逐候选评判与标准文档的对应程度，输出 JSON。
```

### 4.3 输出契约（固定 JSON Schema）

```json
{
  "results": [
    {
      "fileCode": "a1b2…",
      "standardFileCode": "c3d4…",
      "semantic": 0.92,
      "fieldMatch": 0.88,
      "tableMatch": 0.90,
      "periodConsistency": 1.0,
      "reason": "内容为质量手册，字段与表格定义高度对应，版本与编制日期齐全",
      "missingFields": ["适用标准"],
      "evidence": [
        { "type": "field", "profileFieldName": "文件编号", "contractFieldCode": "DOC_NO", "profileValue": "QM-2026", "hit": true },
        { "type": "table", "profileTableName": "文件修订记录", "contractTableCode": "T_REV", "hit": true },
        { "type": "purpose", "summary": "手册类文件，覆盖职责与体系范围" }
      ],
      "recommend": "accept"
    }
  ]
}
```

**约束**（写进 prompt 与后处理）：
- 分数必须 `0–1`，两位小数；缺项填 `null`（落库 NULL，不许编造 0）；
- `evidence` 至少 1 条，且 `type=field` 的 `contractFieldCode` 必须存在于该契约的字段定义中（**后端校验，防止 LLM 幻觉出不存在的字段**）；
- 后端 `TryRepairTruncatedJson` 抢救 → 解析 → 校验 → 逐字段 clamp 到 `[0,1]` → 落库；校验失败的候选降级为 `RecallScore` 直接作为 `Confidence`，`ScoreStage` 保持 `recall` 并标 `ProfileMessage` 记因。

### 4.4 LLM 不可用时的精排退化

`Confidence = RecallScore`，`ScoreStage='recall'`，`Status='scored'`——**流程不中断**，只是精度下降，全部候选进入人工队列（阈值在退化模式下收紧为「一律人工」）。

## 5. 可信度模型

### 5.1 五维分量

| 分量 | 含义 | 来源 | 值域 |
|------|------|------|------|
| `SemanticScore` 语义 | 文档作用与目标文档作用的吻合 | S3 LLM `semantic` | 0–1 |
| `FieldMatchRatio` 字段 | 画像字段命中契约必需字段的比例 | 画像字段 × 契约 `cert_doc_field_def`，LLM 复核 | 0–1 |
| `TableMatchRatio` 表格 | 画像表格结构命中契约表格定义的比例 | 画像表格 × 契约 `cert_doc_table_def` | 0–1 |
| `RuleStrength` 规则 | 指纹/文件名强匹配强度 | S1 指纹分或文件名相似度 | 0–1 |
| `PeriodConsistency` 时效 | 文档期间与阶段期间/彼此是否矛盾（如 2019 年的手册配 2026 年阶段） | 画像字段日期 vs 阶段时间 | 0/0.5/1 |

### 5.2 综合公式（分类型加权）

```text
【可编辑文档 editable】
Confidence = 0.35 × Semantic
           + 0.30 × FieldMatch
           + 0.20 × TableMatch
           + 0.10 × RuleStrength
           + 0.05 × Period

【固定文档 fixed】
Confidence = 0.45 × RuleStrength          ← 指纹主导
           + 0.30 × Semantic
           + 0.15 × FieldMatch
           + 0.10 × Period
           （TableMatch 不参与：固定扫描件通常无标准表格定义）

【人工指定 manual】
Confidence = NULL（不参与自动化分流，EvidenceJson = [{"type":"manual"}]）
```

**实现约束**：
- 公式参数放 `cert_sys_config`（`ent_norm_w_semantic` 等），**不硬编码**，便于调参与 A/B；
- 落库前 `ROUND(x, 2)`，类型 `decimal(3,2)`（D8）；
- 任一必需维缺失（NULL）时：该维按 0 计且在 `Reasons` 追加 `"[缺X维]"`，**并在 `IsAuto` 判定上直接降级为人工**（缺维不自动放行）。

### 5.3 与既有可信度口径的关系

| 体系 | 值域 | 位置 |
|------|------|------|
| 定向提取字段可信度 | `decimal(3,2)` NULL | `cert_extraction_result.Confidence`（已有） |
| 画像字段/表格可信度 | `decimal(3,2)` NULL | `cert_ent_doc_profile_field/_table.Confidence`（本模块） |
| 匹配综合可信度 | `decimal(3,2)` NOT NULL | `cert_doc_match_candidate.Confidence`（本模块） |
| 报告溯源可信度 | `decimal(3,2)` NULL | `rpt_report_section_source`（已有，实体待补） |

四者**同值域同类型**，前端可信度徽标组件（标绿/标黄/标红）可复用同一套阈值渲染逻辑（`审核端…V2.2.md` §869「低于阈值标黄」策略）。

## 6. 冲突检测与仲裁

### 6.1 四类冲突

| 类型 | `ConflictType` | 判定 | 裁决要求 |
|------|----------------|------|----------|
| **一源多目标**（一份企业文档很像多个标准文档） | `multi_target` | 同一 `FileCode` 下 ≥2 条候选 `Confidence ≥ auto−0.05` | 强制人工选唯一归属（固定文档尤甚） |
| **一标多源**（多个企业文档争同一标准文档） | `multi_source` | 同一 `StandardFileCode` 下 ≥2 条 `confirmed` 候选竞争 | 强制人工定主来源；其余 `reject` 或作补充来源 |
| **字段覆盖不足** | `low_field_coverage` | `Confidence ≥ auto` 但 `FieldMatchRatio < 0.5` | 分数高但字段对不上 = 可疑，强制人工 |
| **期间矛盾** | `period_mismatch` | `PeriodConsistency ≤ 0.5` 且其余分高 | 强制人工（旧版文件冒充现行文件的典型风险） |

### 6.2 仲裁规则

```text
对每条候选：
  isConflict = 命中上表任一 → IsConflicted=1 + ConflictType
  autoConfirmable = (Confidence ≥ auto) AND NOT isConflict AND 五维无缺失
  needReview      = (review ≤ Confidence < auto) OR isConflict
  reject          = Confidence < review
```

**任何 `IsConflicted=1` 的候选禁止自动确认**（`T6` 自动确认路径需检查该位）。

### 6.3 冲突在裁决页的呈现（人工判断依据）

按用户要求「多个文件可能匹配标准文档 → 形成人工判断依据」，裁决页以**标准文档为主轴**展示：

```text
目标：ISO9001-质量手册（必需）        当前：未匹配
┌──────────────────────────────────────────────────────────────┐
│ 候选A  质量手册-QM-2026-v2.docx   92%  [推荐]                  │
│   字段命中 8/9（缺：适用标准） 表格命中 1/1  期间 2026 ✓         │
│   理由：…                        [采纳] [否决] [改用其他]       │
├──────────────────────────────────────────────────────────────┤
│ 候选B  QM手册(旧版2023).docx      71%  [期间矛盾 ⚠]            │
│   字段命中 7/9 表格命中 1/1  期间 2023 ✗（阶段为2026）          │
│   理由：…                        [采纳] [否决]                 │
├──────────────────────────────────────────────────────────────┤
│ 无候选？[手工指定企业文档/文件夹]                               │
└──────────────────────────────────────────────────────────────┘
```

## 7. 阈值分流与自动化策略

### 7.1 三档分流（P1 待拍板，此处给默认建议）

| 区间（默认） | 动作 | 系统行为 | 人工负担 |
|--------------|------|----------|----------|
| `Confidence ≥ 0.85` 且无冲突、五维齐全 | **自动推荐** | 写候选 `recommended`；可选（`ent_norm_enabled` 子开关）直接 `T6` 自动确认并记 `IsAuto=1` | 抽检 |
| `0.50 ≤ Confidence < 0.85` | **待人工** | `pending_review`，进裁决队列 | 必须处理 |
| `Confidence < 0.50` | **不打扰** | 候选保留但不进队列，折叠于「低置信」区 | 按需查看 |
| 任意 `IsConflicted=1` | **强制人工** | 覆盖上面三档 | 必须处理 |

> 用户原话「可信度大于 50% 进入字段/表格内容匹配」→ 对应：**≥0.50 才做字段/表格对齐试填**（试填产出 = 待确认实例，非终稿）；「多个文件可能匹配 → 人工判断依据」→ 对应 §6 冲突矩阵。

### 7.2 自动化的三层开关

| 层级 | 配置 | 语义 |
|------|------|------|
| L1 总闸 | `ent_norm_enabled=0` | 停全部自动匹配，人工手工指定照常 |
| L2 自动确认 | `ent_norm_auto_confirm=0/1` | 只评分不落归属（默认建议 **0**：首期全部人工确认，积累判例后再开） |
| L3 定向提取 | `ent_norm_auto_extract=0/1` | 裁决后是否自动触发定向提取（建议 1，LLM 可用时） |

**首期建议**：`auto_confirm=0`——先用真实数据观察分数分布与人工否决率，再放开自动确认，避免「错误自动归属」污染 `cert_extraction_result`（那是 NC/报告的数据源，错了会传导）。

## 8. 批处理、成本与性能

### 8.1 调用量估算（N=100 企业文件，M=60 契约）

| 阶段 | LLM 调用 | 说明 |
|------|----------|------|
| 画像 | ≤100 次（固定文档命中指纹的可省） | 每文件 1 次，输入 ~4K token |
| 精排 | ≈ 有候选的契约数 × 批片数，约 60–150 次 | 每批 10–20 候选，输出 ~1.5K token |
| **合计** | **≈160–250 次/百文件** | 对比全量两两 6000 次，**降低约 96%** |

### 8.2 计费与观测

- 每次调用写 `cert_ai_usage_log`：`BusinessType='ent_profile' / 'ent_match'`，沿用现有 `CostUsd/DurationMs/Success` 字段；
- 费用监控页（`AIUsageController`）按 `BusinessType` 过滤即可看到本模块开销，**无需新建费用体系**；
- 单企业单批次设 `ent_norm_max_calls` 上限（默认 500），超限截断并提示分批。

### 8.3 性能预算

| 环节 | 目标（100 文件） | 手段 |
|------|------------------|------|
| 转换 | 已有队列，~10–20 min | 复用 |
| 画像 | ≤ 30 min | 画像队列并发度 3（LLM 限速） |
| 召回 | < 10 s | 纯内存倒排 + SQL |
| 精排 | ≤ 20 min | 批式 + 并发 3 |
| 裁决 | 人工时长 | 每标准文档 ≤ 30 s（候选 ≤3 条时） |

## 9. 重算稳定性与结果漂移控制

### 9.1 问题

LLM 打分天然有随机性（temperature）。若每次重算都全量重排，已确认的归属可能被「新分数」挑战，制造无意义的变更噪声。

### 9.2 规则

1. **重算范围**：只重算 `Status IN ('pending','scored','recommended')`；`confirmed/rejected/superseded` 不动；
2. **新增候选**：重算时新出现的、分数高于已 `confirmed` 者且差值 > 0.10 → **不自动替换**，标 `IsConflicted` + `ConflictType=multi_source` 提示人工（「出现了更强候选」）；
3. **temperature=0**（`cert_sys_config.ai_temperature` 本链路建议 0）+ 固定 prompt 版本 → 同输入近似同输出；
4. **批次落 `RankBatchCode`**：任何展示都标明「第 N 批结果」，避免跨批混比。

### 9.3 批间锚定

批式切片时，每片 prompt 注入 2 条**系统级锚定样例**（固定画像+固定期望分数），后处理校验锚定样例误差 > 0.15 时告警——用于发现模型/prompt 变更导致的整体分数漂移。

## 10. 评测与验收指标

### 10.1 离线评测集（P5 决策点：ISO9001 + 1 家真实企业 30–50 份资料）

人工预先标注「企业文档 → 标准文档」的**金标准**，跑全链路后对比：

| 指标 | 定义 | 建议达标线 |
|------|------|------------|
| 召回率 Recall@K | 金标准配对出现在 Top-K 候选中的比例 | ≥ 0.90 |
| 精确率 Precision@1 | 第 1 名候选即正确配对的比例 | ≥ 0.70 |
| 自动档准确率 | `Confidence ≥ auto` 的候选中人工认可的比例 | ≥ 0.95（**关键安全指标**） |
| 漏配率 | 金标准配对完全未被召回的比例 | ≤ 0.05 |
| 人工采纳率 | 进入人工队列的候选被采纳的比例 | ≥ 0.60（衡量是否过度打扰） |

### 10.2 过程指标（上线后持续观测）

- 单文件画像 P95 耗时、精排批次 P95 耗时；
- LLM 失败率与 JSON 解析失败率；
- 人工否决率按 `DocCategory` 分布（固定 vs 可编辑）；
- 每 100 文件的 AI 成本（`cert_ai_usage_log` 汇总）。

### 10.3 验收口径

1. 评测集跑通全流程，`Recall@10 ≥ 0.90`、自动档准确率 ≥ 0.95（若首期 `auto_confirm=0`，自动档以「推荐且人工抽样认可」计）；
2. 断网/LLM 下线演练：指纹链 + 人工指定通道可完成全部固定文档归属；
3. 重算演练：重算后已确认归属零变化，新强候选只产生冲突提示；
4. 全部 AI 产出可在页面点开证据并跳转到源文件位置（`PositionInfo` 可解析）。
