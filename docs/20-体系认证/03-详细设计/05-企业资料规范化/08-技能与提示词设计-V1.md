## 1. 与 Skill 体系的边界（D4 落地）

| 判据 | 工作流 Skill（`wf_skill`） | 本模块能力单元 |
|------|---------------------------|----------------|
| 触发方式 | 工作流节点编排、人工在 Skill 页调用 | **事件驱动**（上传完成/裁决完成）+ 队列 |
| 编排归属 | 由流程定义决定何时跑 | 由本模块状态机决定（03 分册） |
| 典型 | 报告生成、证书生成、人工节点 AI 助手 | 画像、召回、精排、裁决回写 |
| 结果形态 | 交互式/文档产出，进工作流上下文 | 结构化数据落 `cert_*` 表 |

**结论**：本模块**全部能力单元不注册为 `wf_skill`**，实现为独立 Service + `yzh_queue` 任务（承接 `document_extract` 被移出 Skill 的同理判定——「确定性数据管线 ≠ 人机交互能力」）。

| | 注册进 Skill 体系 | 本模块 |
|---|---|---|
| 谁能触发 | Skill 页/流程节点 | 队列、API、状态机 |
| 需要 SkillCategory | 是 | 否（TaskType 字典即可） |
| 例外 | **契约页「AI 辅助生成 DocPurpose」**（§3.5）可复用「AI 节点」的对话式能力 | 唯一允许的 Skill 交集 |

|---|----------|------|------|------|----------|

| C2 | 指纹预判 | `EntDocProfileService.FingerprintAsync`（新） | 文件名 + Markdown 头 + 契约指纹集 | `FingerprintResultJson` | 画像内 P1 |

| C5 | LLM 精排 | `MatchRankService` + `ent_doc_match` 任务（新） | 候选批次 + 两侧摘要 | 五维分数 + 证据 | 召回后（T5） |

## 3. 提示词分层与模板

### 3.1 四层提示词 + L5 元生成层（V1.1 增补：2026-10-02 已落地）

| 层 | 名称 | 字段/存放 | 消费单元 | 模板要点 |
|----|------|-----------|----------|----------|
| L1 | 画像提示词 | `wf_prompt_template`（`Code=ent_profile`） | C3 | 输入 Markdown（截断）→ 输出 06 §4.1 固定 JSON；含三段式作用归纳要求 |
| L2 | 匹配精排提示词 | `wf_prompt_template`（`Code=ent_match_rank`）+ 契约 `MatchPrompt` 追加 | C5 | 输入契约 + N 个画像 → 04 §4.3 固定 JSON；含证据校验约束 |
| L3 | 段落合成提示词 | 契约 `SynthesisPrompt`（+ 规则 `Prompt` 上下文） | C8 内段落字段 | 「按目标文档的章节组织，引用源位置」 |
| L4 | 辅助生成提示词 | `wf_prompt_template`（`Code=ent_contract_assist`） | C10 | 「按三段式写 DocPurpose，100–400 字」 |
| **L5** | **元生成层（提示词的提示词）** | `wf_prompt_template`（`Code=prompt_generator`，`PromptType=prompt_generator`，`StandardCode=NULL`） | **提示词工作台**「AI 生成 / AI 优化」按钮 | **双模式**：`{{work_mode}}=generate` 从零生成 / `optimize` 优化现有正文；输出 `doc_group`（批量 `items[]` 子集）或 `doc_content`（单对象全字段）**二选一**；正文里占位符**只写名字不写花括号**（避免被单趟渲染提前吃掉） |

> 单元格/表格提示词（`CellPrompt/TablePrompt`）不是独立层，是 **L2/L3 的注入片段**——随字段/表格定义进 prompt（05 §2.3）。

> ★ **L5 与 L1~L4 的区别**：L1~L4 产出**业务结果**（画像 / 打分 / 段落），L5 产出**提示词正文本身**。
> 因此 L5 的验收口径不是「业务字段对不对」，而是 33 号 §3.3 的**输出契约 + 保存闸门**：
> 生成稿必须先跑通一次真实文件分析（`validation.valid=true`）才允许落库。
> L5 走与 L1~L4 **同一个** `cert_ai_usage_log.BusinessType='ent_profile'` 计费口径。

### 3.2 模板结构（遵循 AI 提示词规则设计：三段式）

```text
【角色与任务】你是认证平台的文档画像提取器……
【规则】1. 只输出 JSON，禁止解释 2. 分数 0-1 两位小数，缺项 null 不得编造
        3. position 必须来自原文 4. 表格超50行只保留前50行…
【输入】{{markdown_content}}（占位符渲染由 PromptRenderer 承担）
【输出契约】{ …JSON Schema… }
```

- **占位符**统一走 `wf_prompt_template` + `Services/Workflow/PromptRenderer`（复用不改）；
- **输出 JSON Schema 内嵌在模板里**——schema 改 = 模板改 = 有版本可回滚，不允许代码里硬编码半套模板。

### 3.3 模板版本与代码的契约耦合

| 组件 | 耦合点 | 保护 |
|------|--------|------|
| L1/L2 模板 | 后端解析器期望的 JSON 字段名（purpose/fields/…；semantic/fieldMatch/…） | 模板保存时**跑一次校验调用**（照抄规则设计器「提示词生成与验证」机制），解析失败不允许保存 |
| 契约 `MatchPrompt` | 同上（追加段） | 同上，契约页「测试匹配」按钮 |
| `SynthesisPrompt` | 字段名 = `FieldCode`（D：LabelTag=FieldCode） | 同上 |

### 3.4 模板正文示例（L2 精排，节选）

```text
【角色与任务】你是 ISO 认证资料的匹配评审员。给定 1 个「标准文档契约」和 N 个「候选企业文档画像」，
逐候选判定对应程度并打分。

【规则】
1. 只输出 {"results":[...]}，禁止任何解释文字。
2. semantic/fieldMatch/tableMatch/periodConsistency 取值 0-1，两位小数；无从判断填 null。
3. evidence 至少 1 条；type=field 时 contractFieldCode 必须出现在契约字段定义中，否则该条无效。
4. 一份企业文档若明显是另一类文档，直接给低分并写明理由，不要强行匹配。
5. 期间（年份）与阶段不符时 periodConsistency ≤ 0.5。

【契约】{{contract_doc_name}} / 作用：{{contract_purpose}} / 字段定义：{{contract_fields}} / 表格定义：{{contract_tables}}
{{contract_match_prompt}}   ← 契约级 MatchPrompt 注入点

【候选画像】{{candidate_profiles}}

【输出契约】{ "results": [ { "fileCode":"", "standardFileCode":"", "semantic":0.0,
  "fieldMatch":0.0, "tableMatch":0.0, "periodConsistency":0.0, "reason":"", "missingFields":[],
  "evidence":[{"type":"field|table|purpose","...":"..."}], "recommend":"accept|review|reject" } ] }
```

## 4. 提示词管理与演进

| 治理项 | 约定 |
|--------|------|
| 存放 | L1/L2/L4 → `wf_prompt_template`（有版本/启停能力）；契约级 → 契约表字段（随契约） |
| 修改入口 | 模板管理页（既有）+ 契约页；**不改代码即可调提示词** |
| 变更影响 | 改 L1/L2 → 建议批量重跑画像/精排（06 §6「按模板版本过滤」），重跑受 04 §9 稳定性规则保护 |
| 调优数据源 | `cert_ai_usage_log.BusinessType` + 04 §10 评测集（Recall@K、自动档准确率） |
| 回滚 | 模板启用/停用切换；结果侧用 `RankBatchCode` 标批次，不跨批混比 |
| 禁止 | 在 C# 字符串里拼提示词正文（除极短固定约束句）；把 JSON Schema 拆一半在代码一半在模板 |

## 5. LLM 通道与配置约定

| 项 | 约定 | 依据 |
|----|------|------|
| 通道 | 复用 `DocExtraction/LlmInvokeService`（OpenAI 兼容直连、六键配置、`json_object`、截断抢救、180s 超时） | 不新建通道 |
| temperature | 画像/精排固定 0（`cert_sys_config.ai_temperature` 或链路覆盖） | 04 §9.2 |
| 超时/重试 | 任务级重试照抄转换队列参数；单任务失败不拖垮队列 | 03 §7 |
| 计费 | `cert_ai_usage_log.BusinessType ∈ {ent_profile, ent_match}` | 06 §7.2 |
| 模型选择 | 画像/精排用当前默认对话模型；**OCR/视觉**待 P3 | P3 |
| 上限 | 单企业 `ent_norm_max_calls`（默认 500） | 04 §8 |

## 6. 禁止事项

| ⛔ 禁止 | ✅ 正确做法 |
|---------|------------|
| 把 C2–C7 注册为 `wf_skill` | 独立 Service + 队列（D4） |
| 代码里硬编码提示词正文/schema | `wf_prompt_template` + 模板校验保存 |
| 各能力单元各开一套 LLM 配置/计费 | 统一 `LlmInvokeService` + `BusinessType` |
| 提示词改动不跑评测直接全量重跑 | 先评测集回归（04 §10）再批量 |
| 用 `Id`/文件名当能力单元的输入键 | 一律 `Code`（`FileCode/StandardFileCode/ProfileCode`） |
