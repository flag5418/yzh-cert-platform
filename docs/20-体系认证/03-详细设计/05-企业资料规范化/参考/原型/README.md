## 五、核心机制（4 个）

### ① 匹配歧义

```text
后端返回：MatchState='ambiguous' · CandidateCount=4 · Top1Score=0.94 · Threshold=0.90
```

| 状态 | 界面 | 需人工 |
|------|------|:---:|
| `auto_matched` | 绿「已自动匹配」，可复核 | 否 |
| **`ambiguous`** | 黄告警 + 候选列表 + 必须指定 | **是** |
| `no_match` | 红「无可匹配文件」+ 引导上传 | 是 |
| `warn` | 已匹配但有告警（如许可证有效期） | 建议 |

> ⚠️ **待你拍板**：法人身份证是选**正面**、**反面**、还是**一对**？
> 数据模型上一个槽位只能放一个文件。要支持一对，需槽位拆成 `法人身份证_正面` / `_反面`，或允许一个槽位关联多个原始文件。
> 原型按「二选一」做（反面 62% 的判定依据是「同名前缀推断」）。

### ② 编辑三缓冲

```text
改值 / 换来源 / 锁锚点
   ↓  只写 S.edits[docCode][ref] = { from, val, srcKind, pinned }
   ↓  ★ 不动 S.docs、不动后端
点「更新文档」
   ↓  回写 S.docs + 重算完成度 + 写日志 + 同步到企业资料库
```

**四条不覆盖规则**：① 已锁定文档整份跳过 ② 锁定锚点保留 ③ 人工值默认保留 ④ 示例数据必须清空（原型未演示，依赖后台标记）

### ③ 队列粒度

| 层 | 形态 |
|---|---|
| 批次 | 顶部队列条：进度 + 计数 + 明细 + 取消 |
| 任务（原子=单文件） | 明细抽屉：状态 / 耗时 / **人话失败原因** / 单条重试 |
| 可恢复 | 批量重试失败项 · 取消后已完成产物保留 |

### ④ 输入 / 输出分离

```text
企业原始资料（输入，只读）              企业资料库目录（输出）
enterprise-original-source/             enterprise-documents/
→ 只出现在候选选择器 + 「企业资料管理」菜单   ← 「更新文档」同步到这里
```

**「同步到企业的文件夹」= 更新资料库目录的文件指针 + 产物落 `enterprise-documents/`。**
原始资料目录**只读不改**（它是证据链）。

## 六、队列的过渡方案

| 步 | 后端 | 前端 | 工作量 |
|:--:|------|------|:-----:|
| **P0 桩** | `POST /normalize/run` **同步**跑编排器，不入队，返回真实结果 | 无感（返回结构逐字相同） | 0.5 人天 |
| **P1 真队列** | 改为建批次 + N 个任务；新增 `GET /normalize/batch/{QueueCode}` | 加轮询（**仅此一处**） | 3 人天 |

**桩只做 3 件事**：① 校验入参 ② 写一条 `cert_doc_normalize_action`（审计不断）③ 同步执行、返回真实产物与完成度。

> ⚠️ **⛔ 桩不能伪造数据**。返回 `Completion=100%` 而 `cert_doc_fill_value` 一行没有，就和 25 号「`Confidence` 95 行全 NULL」同类 —— 界面看着对、数据是空的。正确做法：**只是不入队，其余全真**。
>
> **保留的接口**：`POST /normalize/plan`（干跑预览，纯读 DB 零副作用，P0 就该做，是「一键规范化」的前置）+ 列表/明细查询。
