## 三、原型里刻意演示的 4 个关键机制

### ① 匹配歧义（Ambiguity）—— 你提的核心问题

**后台返回形态**（原型在抽屉里用等宽字示意了字段名）：

```
MatchState = 'ambiguous'        ← 不是 auto_matched
CandidateCount = 4              ← 「有几个待匹配项」
Top1Score = 0.94
Candidates[] = [
  { FileCode, FileName, Score, MatchField, MatchedBy, Evidence, Fields[] }
]
```

| 状态 | 界面表现 | 是否需要人工 |
|------|---------|:---:|
| `auto_matched`（Top1 唯一且分高） | 绿色「已自动匹配」+ 仍可查阅 | 否（可复核） |
| **`ambiguous`**（≥2 个候选） | ★ 黄色告警 + 候选列表 + **必须人工指定** | **是** |
| `no_match` | 红色「企业原始资料里没有可匹配的文件」+ 引导去上传 | 是（或标记「企业暂无」） |
| `warn` | 已自动匹配但有告警（如许可证有效期） | 建议复核 |

> ⚠️ **一个判定问题需要你拍板**：`张明远_身份证反面.jpg` 匹配度 62%，
> 它其实是「法人身份证的**反面**」—— 是不是应该自动选「正面+反面」**一对**，而不是二选一？
> ⇒ 原型暂按「二选一」演示（`MatchedBy` 里写了「同名前缀推断」）。这是个业务口径问题。

### ② 三层编辑缓冲 —— 「点更新文档才真正执行」

```text
用户改单元格
   ↓  只写 S.edits[docCode][cellRef] = { from, val, srcKind, pinned }
   ↓  ★ 不动 S.docs、不动后端
点「更新文档」
   ↓  才把 S.edits 回写进 S.docs，并重算 Completion / FilledCount / Status
   ↓  写 cert_doc_normalize_action（审计留痕）
   ↓  ★ 真实系统里：调 NPOI 写入 docx → 上传 MinIO enterprise-documents/ → 回写资料库目录
```

**四条不覆盖规则**（抽屉底部两个勾选框对应前两条）：

| # | 规则 | 原型对应 |
|---|------|---------|
| ① | 已锁定 🔒 的文档整份跳过 | 重新生成时 toast 提示「跳过已锁定 N 个」 |
| ② | 钉住 📌 的单元格保留 | 每行「钉住」复选框 + 底部「保留钉住值」 |
| ③ | 人工改过的值默认保留 | 底部「重写时保留人工填写值（推荐）」，默认勾选 |
| ④ | 示例数据必须清空 | ⚠️ 原型未演示（依赖后台标记 `SampleData`，见 `41-01` §一·5） |

### ③ 队列粒度 —— 一个文件 = 一个任务

| 层 | 演示形态 |
|---|---|
| 批次（范围） | 顶部队列条：进度条 + 进行中/完成/失败计数 + 「明细」「取消」 |
| 任务（文件） | 明细抽屉：10 行，每行 = 文档 / 类型 / 状态 / 耗时 / **人话失败原因** |
| 可重试 | 「↻ 重试失败项」批量 + 行内「重试」单条 |
| 可取消 | 「取消」后进行中转 `skipped`，**已完成产物保留** |

> ⚠️ 失败原因写的都是**人话**，不是异常堆栈（26 号 S-8）：
> `模板未上传（后台「标准文档填写规则」尚未配置此模板）` / `企业原始资料中无可匹配文件`

### ④ 输入 / 输出分离 —— 回应「两个目录」的困惑

```text
企业原始资料（输入，只读）          企业资料库目录（输出，可编辑）
enterprise-original-source/         enterprise-documents/
cert_enterprise_original_file       cert_standard_directory_file 企业行
        │                                    ▲
        │  ←「从企业资料重新筛选」下拉         │  ←「更新文档」同步到这里
        │  ← 候选列表（证件类）              │
        └──── 底部只读表格列出 + 标注「已被引用为」
```

**「同步到企业的文件夹」= 更新 `cert_standard_directory_file` 企业行的文件指针 + 产物字节落 `enterprise-documents/`。**
原始资料目录**只读不改** —— 它是证据链，改了就没有审计价值了。

## 四、队列的过渡方案（你提的「先写个接口直接返回成功」）

**建议分两步走，两步之间前端零改动**：

| 步 | 后端 | 前端 | 工作量 |
|:--:|------|------|:-----:|
| **P0 桩** | `POST /normalize/run` **同步**跑一遍编排器，直接返回结果；**不入队** | 完全不知道有桩 —— 返回结构与真实现**逐字相同** | 0.5 人天 |
| **P1 真队列** | `POST /normalize/run` 改为建批次 + N 个任务；新增 `GET /normalize/batch/{QueueCode}` 轮询 | 加轮询逻辑（**仅此一处**） | 3 人天 |

**桩端点必须做的事只有 3 件**（这才是「严谨」与「糊弄」的分界）：

1. **校验入参**（范围合法 / 模板存在 / 不是只读文档）
2. **写一条 `cert_doc_normalize_action`**（`ActionType='batch_run'`）—— 审计链不断
3. **同步执行编排器**，返回真实产物 + 真实完成度（⛔ **不要**返回写死的假数据）

> ⚠️ **⛔ 桩不能伪造数据**。如果 `run` 返回 `Completion=100%` 而 `cert_doc_fill_value` 一行没有，
> 那就和 25 号发现的「`Confidence` 95 行全为 NULL」是同一类病 —— **界面看起来对，数据是空的**。
> 正确做法：**桩只是「不入队」，其余全真**。

**保留的接口**（与队列无关，永久需要）：
- `POST /normalize/plan` —— **干跑预览**（展开范围 + 各类跳过计数 + 警告）。⛔ 纯读 DB，零副作用 ⇒ P0 就该做，且是「一键规范化」按钮的前置。
- `GET /normalize/list` / `values` / `value/{code}` —— 列表与单元格明细

## 七、需要你确认的 3 个业务口径

| # | 问题 | 为什么原型里只能猜 |
|---|------|----------------|
| **Q1** | ★ **「法人身份证」应该选正面、反面、还是一对？** | 数据模型上「一个标准文档槽位」只能放一个文件。若要一对，需要把槽位拆成两个（`法人身份证_正面` / `_反面`），或允许「一个槽位关联多个原始文件」 |
| **Q2** | 匹配度多少算「可自动匹配」？ | 原型暂定 ≥0.90 自动、0.60~0.90 告警、<0.60 需人工。25 号实测 `profile` 类占比 0%，所以这个阈值一期几乎只在证件类生效 |
| **Q3** | 「企业暂无此件」要不要做成正式动作？ | 做了要写缺口清单（`InstanceState='partial'`），后续审核阶段要看「企业缺哪些材料」；不做则该槽位永远空白 |
