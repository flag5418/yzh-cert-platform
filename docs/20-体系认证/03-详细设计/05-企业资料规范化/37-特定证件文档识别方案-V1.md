# 特定证件文档识别方案 — 联网调研（V1）

> **版本**：V1 | **日期**：2026-10-03 | **状态**：调研结论，供 36 号 §十 L7 决策
> **触发**：用户 2026-10-03 —— 「不建议提取的文件可能是营业执照、身份证等特定证书或证件信息，这一块我需要你联网有无比较好的 AI 或开源项目能分析特定功能的文档」

---

## 〇、结论先行

**当前不需要引入任何方案**，就能解决 80% 的问题：

| 现状能力 | 覆盖 |
|---|---|
| **格式层预判**（已落地，`IsNotSuggestedByFormat`） | 图片类（jpg/png/gif/bmp/webp/tif）直接判「不建议提取」—— 企业上传的图片几乎全是证照扫描件 |
| **AI 建议 + 人工确认**（已落地） | PDF/Word 由 LLM 读正文后建议 skip/ignore，人工确认 |
| **「不设标签/作用」的 UI 规则**（已落地） | 命中上述任一 ⇒ 标签列/作用列显示「—」，**无编辑入口** |

**剩下 20%（真 PDF 格式的营业执照/资质证书）需要下面三个方向之一**，按落地成本排序：

| 方案 | 成本 | 准确度 | 说明 |
|---|---|---|---|
| **① PaddleOCR / PP-StructureV3**（推荐先试） | 低 | 中高 | 中文 OCR 事实标准，CPU 可跑，可 Docker 化；我们已有 `yzh-libreoffice` / `yzh-anydoc` 容器，加一个 `yzh-paddleocr` 顺理成章 |
| **② VLM 文档解析（MinerU / dots.ocr）** | 中 | 高 | 直接 PDF/图片 → Markdown，自带版面理解；MinerU 有 Docker 镜像，与我们现有 anydoc 容器模式同构 |
| **③ 专用证件模型** | 高 | 很高 | 见 §四，通用性差，只做「证件」这一件事 |

---

## 一、⭐ 首选：PaddleOCR / PP-StructureV3

- **仓库**：`PaddlePaddle/PaddleOCR`（GitHub 20k+ stars，中文 OCR 事实标准）
- **能力**：中文印刷体/手写体 OCR + 版面分析（标题/正文/表格/印章区域）+ 印章检测
- **对本项目的价值**：
  - 解决「图片类文件（jpg/png）无法提取任何内容」—— 现在它们只能预览、连 OCR 都没有
  - 印章检测对**体系认证**特别有用：营业执照/资质证书上的公章可作为「证件真伪」的辅助信号
  - CPU 可跑，不需要 GPU；我们已用 Docker 跑 anydoc / LibreOffice，加一个 `yzh-paddleocr` 容器是同款模式
- **落地形态**：`IOcrProvider` 已有接口（`DefaultOcrProvider` 目前是空实现）⇒ **直接换实现即可，不动调用方**
- **成本**：镜像约 2–3 GB，首次启动拉模型；单张证件图 <1s

## 二、VLM 文档解析（MinerU / dots.ocr）

| 项目 | 特点 |
|---|---|
| **`opendatalab/MinerU`**（GitHub 社区大量封装） | PDF/图片/Office → 结构化 Markdown，自带公式/表格识别，中文效果好；有官方 Docker 镜像 |
| **`studio-dots-ai/dots.ocr`** | 「单 VLM 做多语言文档版面解析」，输入图片/PDF → Markdown + bbox；社区已有多个 Docker/Client 封装（`ThinkParse`、`dots-ocr-client`、`Super-OCRs-Demo`） |
| **`wzdavid/ThinkParse`** | 基于 MinerU + Celery + Docker 的**企业级异步队列服务** —— 与我们现有 `yzh_queue` 架构思路一致，可作参照 |

**对本项目的价值**：把现在「anydoc → Markdown」这一环升级为「版面感知」解析，对**表格类文件**（内审记录、合格证、检测报告）的字段提取质量提升最大。

**成本**：VLM 推理要 GPU（或量化 CPU，慢）；比 PaddleOCR 重。

## 三、文档分类（LayoutLM 系列）

| 项目 | 适用 |
|---|---|
| **`microsoft/LayoutLMv3` / `LayoutXLM`** | 版面 + 文本多模态，文档分类/预训练；`yongzhuo/layoutlmv3-layoutxlm-chinese` 是中文适配版 |
| **`lucky-verma/Document-Classification-using-LayoutLM`** | 参考实现（HuggingFace Transformers，RVL-CDIP 数据集） |
| **`huridocs/pdf-document-layout-analysis`** | Docker 服务，做 PDF 版面分段与元素分类（文本/标题/图片/表格） |

**对本项目的价值**：如果我们要把「体系文件」分得更细（而不是靠 LLM 自由判断），LayoutLMv3 分类是**可训练、可解释、便宜**的方案。

**但**：需要标注数据。我们现在 27 个标签是人工定义 + LLM 填的，**没有训练集** ⇒ 短期不划算。

## 四、专用证件识别（暂不推荐，但列出）

| 方向 | 说明 |
|---|---|
| 规则 + OCR | 身份证/营业执照的字段位置**高度固定**（国标 GB/T 2260 / GA 469），用「模板区域 + 正则」比 ML 更准更可控 |
| 专用 SDK | 百度 / 阿里云 /腾讯云 OCR 都提供「身份证识别 / 营业执照识别」API，**准确率 98%+**，按量计费 |

⭐ **我的建议**：如果目标只是「知道这是不是证件 + 抽出证号/有效期/企业名」，
**先用现成云 OCR API + 正则**，比自建模型快 10 倍、准确率高。
自建模型（方案③）只在「数据不能出内网」或「调用量极大到成本反超」时才划算。

## 五、建议的落地顺序

```
阶段 1（本次已做，零成本）
  格式层预判（图片类不参与提取）+ UI 不给标签/作用入口
        ↓
阶段 2（低成本，建议下一个迭代）
  接入 PaddleOCR → 填进 IOcrProvider
  效果：jpg/png 证照能 OCR 出文字 → 「不建议提取」从「格式瞎猜」升级为「OCR 内容判定」
        ↓
阶段 3（按需）
  把「不限格式」升级为「不限文件夹」：分析目标从文件夹下钻到单份文件
        ↓
阶段 4（可选，量大才做）
  MinerU / dots.ocr 替换 anydoc，版面解析质量提升
```

## 六、⚠️ 一个必须记下的架构结论

**证件不该塞进通用标签池。**

理由：标签池（`cert_tag_dict`，27 个 / 4 组）是**召回键**，用于「体系文件 ↔ 资料匹配」。
把「营业执照」放进去，会让所有匹配逻辑开始考虑「这份材料是不是证件」——而证件应该是
**独立的一类资料**，走**自己的字段**：

```
证书类型（营业执照 / 资质证书 / 许可证 / 身份证 / 授权书 …）
证书编号
发证机关
有效期（起 / 止）
企业名称（证件上的，与主档企业名做一致性校验）
```

⇒ 若采纳，建议新增 `cert_enterprise_credential` 表（独立于原始资料表与画像表），
   `cert_enterprise_original_file` 加一个 `CredentialKind` 列指向它。
   **不要**复用 `TagsJson`。

## 七、附：调研中看到的实际风险

| 风险 | 说明 |
|---|---|
| **VLM 不能当唯一裁判** | 社区反复反馈：VLM 对「这是不是营业执照」这类判断**会给出流畅但错误的答案**。它适合「抽文字」，不适合「做分类决策」。分类仍应由规则/专用模型/人工兜底。 |
| **版面解析 ≠ 语义理解** | 拿到 Markdown 只是第一步。我们现有的 `doc_group`/`doc_content` 提示词是按「无版面信息」设计的，接入版面后**提示词需要重写**，否则拿到的信息对不上。 |
| **Docker 体积** | PaddleOCR 镜像 ~3GB、MinerU ~5GB+模型。当前 `yzh-mysql/redis/minio/libreoffice/anydoc` 已占不少磁盘，接入前要评估部署机容量。 |
