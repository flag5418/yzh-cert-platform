## 〇、一句话结论

**整套机制是合理的，且已具备可执行条件；但它此前被描述成「一条直通流水线」，实际是「双侧 × 双流程」的结构，漏掉的三块拼图是：分侧职责、固定文档短路、标准核心字段的前置过滤作用。**

| 你的三点补充 | 判定 | 一句话理由 |
|---|---|---|
| 应按**后台管理功能**与**企业端实现**分开分析 | ✅ **成立，且是第一性切分** | 定义（配置世界）与执行（数据世界）是两套菜单、两套表、两套权限；混谈会把 `cert_fill_param_def` 与 `_value` 当成一张表 |
| 没讲**标准核心字段**与**企业全局参数**的作用 | ✅ **成立，且比我原判断更重要** | 它们不只是填充侧第 1 级优先级 —— 它是 `AnalyzePolicy` **⓪策略判定的输入源**，是语义分析的**第一道闸** |
| 标准文档分**固定**与**需编写**两类 | ✅ **成立，是流程级分叉** | 05 号 §3 已三分（`fixed`/`hybrid`/`editable`），`DocCategory` 直接决定 04 号 §5.2 用哪套加权公式；固定文档**匹配即终点**，不进填充 |

**修正后的一句话结构**：

> **后台定义侧**用「标准核心字段 + 文档语义规则 + 文档提取规则 + 文档生成规则」四套规则定义世界；**企业执行侧**用「⓪策略判定 → 语义分析 → 匹配 → 裁决 → 分叉」跑数据；其中**固定文档在裁决后短路**，**可编写文档才进入提取与填充**。

## 一、双侧职责矩阵：后台定义侧 vs 企业执行侧

### 1.1 为什么这是第一性切分

| | **后台管理（admin · 9990）** | **企业/专家端（auditor · 9991）** |
|---|---|---|
| 别名 | **配置世界** / 定义侧 | **数据世界** / 执行侧 |
| 回答的问题 | 应该有什么文档？每个字段从哪来？按什么规则分析？怎么写进文档？ | 我有哪些资料？对应哪份标准？值填多少？谁确认的？ |
| 产出物 | 字典、契约、规则、提示词、模板（**可版本化、可复用、跨企业共享**） | 画像、候选、裁决、实例（**一次性、可追溯、带 EnterpriseCode**） |
| 数据主键特征 | 多为 `StandardCode` 或全局无租户 | **必带 `EnterpriseCode`**（数据权限边界） |
| 改动影响 | 改一次，所有企业下一次分析生效 | 只影响本企业本批次 |

### 1.2 菜单与表的对照

## 二、标准文档三分类与流程分叉

### 2.1 三分类（05 号 §3 权威，本文不新造）

| `DocCategory` | 判据 | 匹配策略 | 填充策略 | 典型 |
|---|---|---|---|---|
| **`fixed` 固定文档** | 国家/机构规定格式，字段位置固定，通常为扫描件 | **S1 指纹主导**，语义权重≈0 | OCR 按固定字段位提取，或人工录入 | 营业执照、生产许可、资质证书、法人身份证 |
| **`hybrid`** | 主体固定但有自由段 | 指纹定「是不是这类」，精排定「是哪一份/够不够格」 | 两法并用 | 体系认证证书、含自填页的备案表 |
| **`editable` 可编写文档** | 自由编写，内容需重新产出 | R1–R4 多路召回 + LLM 精排 | **契约驱动填充**，生成 docx/xlsx | 质量手册、程序文件、记录表单 |

> **硬约束（05 号 §3）**：`DocCategory` **直接决定 04 号 §5.2 用哪套加权公式，不得留空**（默认 `editable`）。
> **现状**：`DocCategory` 列 **❌ 未加**（`00` 号 §三）⇒ **匹配引擎当前无分支可选，跑不起来。**

### 2.2 用户原话的精确含义

> 「固定文档**不需要重新编写**，直接匹配企业最适合的，比如营业执照、生产许可」

翻译成流程语：**固定文档的「匹配」就是终点** —— 匹到企业那份营业执照，任务完成；**不进入 ⑧定向提取、⑨契约填充**（除非要把它里面的字段抽出来供别处引用，那是 OCR 提取，不是契约填充）。

### 2.3 流程分叉（`03` 号 §1 泳道的勘误）

```text
 ① 上传 → ② 转 MD → ⓪ 策略判定 → ③ 语义画像 → ④⑤⑥ 召回/精排/冲突 → ⑦ 人工裁决
                                                                      │
                                              ┌───────────────────────┴───────────────────────┐
                                              │                                               │
                                   DocCategory=fixed / hybrid                      DocCategory=editable
                                              │                                               │
                                  【匹配即终点】短路 ✅                              ⑧ 定向提取（既有规则链）
                                  · 匹到那份营业执照 = 完成                                     │
                                  · 最多 OCR 抽字段供引用                              ⑨ 契约填充 → docx/xlsx
                                  · 不跑 L2 作用提示词                                          │
                                  · 不进 ⑧⑨                                                    版本归档 + 审计
```

**必须补的两处**：

| # | 补什么 | 落在哪 |
|---|---|---|
| 1 | 泳道图加 **fixed 短路分支** | `03` 号 §1 §1.1 |
| 2 | 状态机加一条 **`fixed → matched(终态)`** 转移，不设 `filling` | `03` 号 §2.4 `InstanceState` |
| 3 | `DocCategory` 列 DDL | `02` 号 §4.1（与 6 列一起，见 §七） |

**不补的后果**：营业执照被拿去跑契约填充 → **白烧 LLM + 产出垃圾实例**，且会在裁决页制造大量"看起来填了但没意义"的行。

### 2.4 `AnalyzePolicy` 与 `DocCategory` 的关系（必须写清先后）

| 字段 | 判定时机 | 回答 | 作用域 |
|---|---|---|---|
| **`AnalyzePolicy`**（26 号 补 6） | **⓪ 上传后、语义分析前** | **要不要分析这份文件？** | **文件级**（`analyze`/`skip`/`ignore`） |
| **`DocCategory`**（05 号 §3） | **③ 语义分析产出**（fixed 可由 L0 指纹先判） | 这份文档属于哪类？ | **标准文档契约侧** + 企业画像侧 |

**判定顺序（建议）**：

```text
⓪ AnalyzePolicy（先判，省掉不该跑的）
   ├─ ignore  → 完全无关，仅 L0 存档，不进任何清单
   ├─ skip    → 两类：① 固定文档（指纹接管，不需 LLM 读全文判作用）
   │            ② 值已在全局参数里定义（cert_fill_param_value 直取，不需从文档提取）
   └─ analyze → 继续 ③ 语义分析 → 产出 DocCategory + 标签 + 作用
```

> ⚠️ **R-8 铁律（26 号）**：`AnalyzePolicy` 是**用途级**不是文件级 —— L0 存档**永不忽略**，`skip` 的文件**仍在证据清单里**。

## 三、标准核心字段 / 企业全局参数的三重作用

此前分析只认到「作用 1」，**作用 2、3 是本轮新增的关键连接**。

### 作用 1｜填充侧：27 号六级优先级的**第 1 级（最高）**

| 项 | 内容 |
|---|---|
| 定义 | 平台统一维护的企业主数据/公共配置自动填充，**不可覆盖** |
| 数据来源 | 企业主数据（名称/统一代码/Logo/法人）、体系配置（标准/版本）、系统固定参数 |
| 实例 | 所有文件的页眉页脚企业名称与 Logo、文件编号、检验依据、适用标准编号与版本 |
| 载体 | 后台 `cert_fill_param_def` → 企业 `cert_fill_param_value`（**Specificity 多级继承算法**，31 号 §一） |
| 实现状态 | ✅ 表已建、接口已实现（`api/Cert/FillParamDef` + `api/Auditor/FillParamValue` + `api/Auditor/DocumentFill`，2026-10-02）；种子 17 通用 + 3 作用域示例 |

### 作用 2｜语义侧：**`AnalyzePolicy` ⓪策略判定的输入源** ★ 本轮新增

26 号 §3.5.3 **补 6** 原文：

> 企业上传的资料里**有些文档没有任何作用（营业执照、无关文档）**、**有些已经在全局参数里定义了** ⇒ 增加忽略状态，**减少分析过程**

`skip` 的两大理由，恰好对应「固定文档」与「全局参数」两件事：

| `skip` 理由 | 由谁接管 | 为什么可以不分析 |
|---|---|---|
| ① 是固定文档（营业执照 / 生产许可） | **S1 指纹规则**（`MatchFeature` 编号前缀 + OCR 关键字段） | 作用自明，无需 LLM 读全文去判断"这是什么" |
| ② 值已在全局参数里定义 | **`cert_fill_param_value`** | 值直接从参数表取，无需从文档里提取 |

> **★★ 由此得出的核心命题**：
> **⓪策略判定的本质 = 用「标准核心字段（全局参数）+ 固定文档指纹」两条已有能力，把不该走语义分析的文档提前拦掉。**
> 它是整条流水线的**第一道闸**，不是可选的成本优化。

### 作用 3｜边界作用：**它圈定了语义分析真正服务的范围**

见 §四 —— 六级优先级里**只有 2 级需要语义**，而「标准核心字段」正是把另外几级不需要语义的部分**显式指认出来**的那一级。

## 四、六级填写优先级 × 语义分析参与矩阵

**左列 = 27 号 §一 权威优先级（冲突时从高到低取值）**；右两列 = 本文新增的判定。

| # | 27 号层级 | 定义 | 需要「文档是什么/作用是什么」吗 | 33 号参与吗 |
|---|---|---|---|---|
| **1** | **全局参数自动替换**（最高） | 主数据/公共配置自动填充，不可覆盖 | ❌ 参数表直取 → **`skip`** | ❌ 被它过滤 |
| **2** | **关联文档自动提取** | 从已提交/已审批的关联文档提取，数据同源 | ✅ **必须先知道"这是哪份文档"** | ✅ **主战场** |
| **3** | **规则推断自动填充** | 确定性业务规则推导（审核人日、条款映射、下次截止日） | ❌ 确定性计算 | ❌ |
| **4** | **字典枚举选择** | 从受控字典选固定枚举，不允许自定义 | ❌ 选枚举 | ❌ |
| **5** | **AI 辅助生成**（较低） | LLM 结合企业信息生成描述性长文本 | ✅ **必须知道"作用是什么"才能生成对味的内容** | ✅ **第二战场** |
| **6** | **人工录入**（兜底） | 原始记录、客观证据 | ❌ 人填 | ❌ |

### 关键推论

1. **语义分析（33 号）不是全流程，它是层 2 + 层 5 的使能器。**
2. **层 1（标准核心字段 / 企业全局参数）是语义分析的前置过滤器**，不是它的并列项。
3. **22 号 ★ 实测校准**：167 份真实文档全量实测，一期 D1 取值来源**只用到 `global` / `compute` / `manual`**（`ai` / `profile` / `self` / `sibling` 一期无场景）。
   ⇒ 一期真正需要语义的是 **层 2（关联文档提取，需匹配）+ 层 5（AI 生成，需作用）**，其余靠参数、规则、人工即可闭环。
4. **27 号层 2「关联文档自动提取」的典型实例里，第一条就是固定文档**：
   > 「认证范围表的经营范围直接提取自**最新营业执照附件**」

   ⇒ 固定文档**既要被匹配到（层 2），又不需被重新编写** —— 这正是 §2.3 短路分支的业务依据：**匹配它们是为了"引用"，不是为了"生成"。**

## 五、三套「字典」的边界

三者都叫"字典"，但正交不冲突。**不写清必然有人拿错当召回键。**

| 名字 | 是什么 | 粒度 | 载体 | 谁消费 | 权威 |
|---|---|---|---|---|---|
| **标准核心字段** | 参数**定义**（企业名称 / 统一社会信用代码 / Logo / 法人…） | **参数级** | `cert_fill_param_def` | 27 号**层 1** 全局替换 | 31 号 |
| **企业全局参数** | 上者的**企业侧取值**（含 Specificity 继承） | 参数 × 企业 × 标准 × 阶段 | `cert_fill_param_value` | 同上 | 31 号 |
| **`DOC_CATEGORY` / `DOC_PURPOSE`** | 语义分析的**输出受控值**（分类枚举 / 作用意图枚举） | **枚举值级** | 字典表 | LLM 返回值**校验**（越界 ⇒ 记 warning 不落库） | 26 号 §4.3 |
| **`cert_tag_dict`** | 文档**标签实体**（带 `MatchFeature`、`StandardCodes`、`MatchFeature`…） | **文档级** | 🆕 自有实体 | **04 号 R2/R3 召回键** | 14 号 D14 / 33 号 |

**分工结论（33 号 Q6 的正式答案）**：

> - **召回键 = `cert_tag_dict`**（文档级实体，可带前缀规则、可按标准裁剪、可倒排）
> - `DOC_CATEGORY` = **粗分类枚举**（体系文件 / 记录 / 资质证照 / 报告）
> - `DOC_PURPOSE` = **作用意图枚举**（证明组织架构 / 证明内审已实施 / 证明管理评审）
> - `fill_param_def/value` = **参数**，与文档分类**完全无关**，但它是 `skip` 的判定输入之一

**冷启动顺序铁律**（26 号 §4.3）：**必须先定字典、再写提示词** —— 否则 LLM 返回不同分类名 ⇒ 是**不可用**而非不准确。

## 六、文档语义规则（33 号）的定位

### 6.1 一句话定位

> **文档语义规则 = 后台定义侧的「语义坐标系定义器」。它不属于填充链（27 号六级的任何一级），它属于匹配链（04 号五路召回）的供给侧；与标准核心字段 / 企业全局参数是两条平行线 —— 后者管「值从哪来」，前者管「文档是什么」。**

### 6.2 它解决的原始问题

> **M 个固定标准文档（实测 167）← 填 ← N 份乱的企业文档（200~300）。**
> 两条提示词的作用 = **把两堆东西放进同一个语义坐标系**，使「给定一个标准文档，能快速捞出 5~10 份最该读的企业文档去试填」。

| 轴 | 角色 | 解决什么 | 下游 |
|---|---|---|---|
| **标签** | **召回 / 过滤键**（倒排索引） | 300 份 → 几十份 | 04 号 R2 类别路、R3 关键词倒排 |
| **作用** | **判断依据 + 填写时的取值参考** | 几十份 → 5~10 份，并告诉填写环节取什么 | 04 号 R4 语义路；27 号层 5 AI 生成 |

**为什么两侧同规则**：过滤是两侧**做交集**，坐标系必须同一个 —— 这正是 14 号 **D14**「双侧同规则，同字典同规则 ⇒ 两侧可比」的原文。
**为什么按标准**：标签集合与作用都是「**标准 × 文档**」的函数（13485 有检验作业指导书，9001 没有）。

### 6.3 与核心模块组的关系表

| 核心模块 | 侧 | 与文档语义规则的关系 |
|---|---|---|
| 标准核心字段 `fill-param-def` | 后台 | **平行**（参数 vs 文档类别）；但它是语义分析的**过滤器**（作用 2） |
| 企业全局参数 `fill-param-value` | 企业 | 同上 |
| 标准文档契约（167 模板） | 后台 | **★ 落点**：`TagsJson` / `DocPurpose` / `InfoItemsJson` 写入此处 |
| 文档提取规则 | 后台 | **并列**：契约管"有什么"，提取规则管"怎么取值" |
| 文档生成规则（锚点） | 后台 | **下游**：仅 `editable` 用，33 号不碰 |
| 空白模板 + 锚点 | 后台 | 同上 |
| 企业语义画像 | 企业 | **★ 落点（企业侧）** |
| 匹配召回 R2/R3/R4 | 企业 | **★ 33 号是其词表与语义原料供给者** |
| 指纹 S1（`fixed`） | 企业 | `MatchFeature` 编号前缀 = 其 **L0 版本** |
| 六级填充规则 Resolver | 企业 | 仅层 5 间接相关 |

### 6.4 对 04 号五路召回的供给关系（最实的定位）

04 号 §3.1 五路权重与 33 号的供给：

| 路 | 权重 | 数据源 | **33 号供给什么** |
|---|---|---|---|
| **R1 文件名路** | 0.35 | `FileName` vs `FileNamePattern` | — （无需 33 号） |
| **R2 类别路** | 0.25 | 画像 `DocTypeGuess` vs 契约 `DocName`/`DocPurpose` 类别词 | **`cert_tag_dict` 标签** |
| **R3 关键词倒排路** | 0.25 | 画像字段关键词命中契约字段定义 + `Keywords` | **`InfoItemsJson` 结构化要素** |
| **R4 语义路**（P2） | 0.15 | 画像 `DocPurpose` 向量 vs 契约 `DocPurpose` 向量 cosine | **两侧 `DocPurpose` 同源** |
| **R5 指纹弱命中** / S1 | 0.30 | `FingerprintScore` | **`MatchFeature` 编号前缀（L0）** |

> **★ 结论：五路中四路的原料由文档语义规则供给。** 这就是它在匹配链里的分量 —— 它不是一个"锦上添花的 AI 功能"，而是**召回引擎的词表供给侧**。

### 6.5 `fixed` 与 `editable` 对本模块的差异化要求

| | `fixed` 固定文档 | `editable` 可编写文档 |
|---|---|---|
| `AnalyzePolicy` | **`skip`**（指纹接管，不跑 L2 作用） | `analyze` |
| 33 号 L2 作用提示词 | **不跑** | **跑**（主战场） |
| 33 号贡献 | 仅 `MatchFeature` 编号前缀（L0 指纹）+ 标签 | 标签 + 四段作用 + `InfoItems` |
| 成本含义 | 167 份里固定文档占比若 10% → 直接省 10% 的 L2 调用 | 主要成本区 |

> **⚠️ 对 33 号原稿的修正**：V1.1 把 `AnalyzePolicy=skip` 描述成**成本优化**，这是**理解偏差** —— 它是 **`fixed`/`editable` 类型分流的直接体现**，成本是副产品。回写见附录 B。
