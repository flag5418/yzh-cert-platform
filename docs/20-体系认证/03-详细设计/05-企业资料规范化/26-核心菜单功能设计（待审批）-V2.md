## 二、统一页面范式（左树右表）

### 2.1 左树组件：**不新写，按「树用途」二选一**

> ★ **2026-10-02 实施修订（R4）**：V1~R3 写的是「统一用 `CertBizTree`」。开工实测后发现
> **两棵树的用途不同**，硬统一会让两边都变形 —— 改为**按用途选组件**：

| 树用途 | 组件 | 用在哪 | 为什么 |
|--------|------|--------|--------|
| **标准目录域树**（机构→标准→阶段→**目录→文件**；有懒加载 / 转换徽标 / 规则状态） | `CertBizTree`（`cert-share/src/components/`） | ② 提取规则 · ③ 生成规则 · ⑤ 上传 · ⑥ 规范化 | 自带 `useFileTree` 懒加载 + 徽标 + 规则状态筛选，正好是文件树的全部需求 |
| **作用域树**（只有 机构/企业 → 标准 → 阶段 三层，**无文件**） | `YzhTreeTableLayout` + `YzhTree`（yzh-core 官方外壳） | ① 后台全局参数 · ④ 企业全局参数 | 不需要文件懒加载；且要与 `TreeTableLogic` 内核配合（`shouldApplyTreeFilter` / `onPrepareAdd` 等钩子），样板 `report-rule` 已验证 |

**为什么 ①④ 不用 `CertBizTree`**（三条硬理由，实测得出）：

1. **它不支持外部数据源** —— 内部固定 `useFileTree()`（根 = 机构）。④ 的根是**企业**，直接用不了；
   若为此给它加 `treeData` prop，等于把它从「文件树组件」改成「通用树组件」，反而破坏它在 ②③⑤⑥ 的既有语义。
2. **会多拉无用请求** —— 它的阶段节点展开会拉 `stage-files/{directoryCode}`（文件夹 + 文件 + 规则状态），
   而作用域树根本不需要文件。
3. **与内核不搭** —— `TreeTableLogic` 的树过滤（`shouldApplyTreeFilter` / `relatedValue` / `buildFilters`）
   与新增注入（`onPrepareAdd`）都要挂在 `YzhTreeTableLayout` 上；① 的右表还要覆写 `dataLoader`
   走 `effective` 端点（见 §3.1）。

`CertBizTree` 的能力清单（②③⑤⑥ 仍用它）：

| 能力 | 现状 |
|------|------|
| 节点类型 | `organization` / `standard` / `stage` / `folder` / `file` —— 覆盖文件树的全部层级 |

### 2.2 六棵树的层级

|------|-------------------|---------------|--------|

##### 分层铁律（**写死，⛔ 不得违反**）

```text
层 2  全局填写规则（语义描述）
         │  AI 分析：读「填写框的语义描述 + 上下文素材」
         ↓  产出【值字典】{ AnchorCode: value, ValueType, Confidence }
         │  ⛔ AI 到此为止 —— 不打开文件、不碰 NPOI、不知道是 Word 还是 Excel
         ↓
层 1  写入 Skill（NPOI 实现）
         │  确定性执行：定位 → 写值 → 保留样式 → 自验收
         ↓  ⛔ 不做任何语义判断（不猜值、不补值、不改值）
       Word / Excel 单元格真正被填上
```

**为什么必须这样分**（不是洁癖，是三条硬理由）：
1. **可重放**：同一值字典重跑必得同一文件（`DocumentFillEngine` 已经为这个目标做成了纯函数）
2. **可审计**：出问题能定位是「值错了（层 2）」还是「写错了（层 1）」—— 混在一起无法归因
3. **可换库**：NPOI 换成 OpenXML SDK / Aspose 时，**只换层 1，层 2 零改动**

| 4 | `doc.CreateHeader()` 后 **`HeaderList.Count` 仍 0**（本会话不可见，重开才可见） | `HeaderList` 本会话**不刷新** | ⚠️ **本轮已不适用**（规格 3/4：**不新建页眉页脚** ⇒ `EnsureHeadersFooters` 已删）。**保留记录**：若将来真要新建，必须**显式并入待处理集合 + 传给扫描器** |

**另一条同类陷阱（W9 的姊妹坑）**：一个 `<w:r>` 内可有**多个 `<w:t>`** ⇒ `run.Text` **丢字**、`run.SetText()` **残留旧内容**。解法：`WordRunText.Get/Set` 覆盖**全部** `<w:t>`，且**永不触碰 `<w:rPr>`**（样式天然保留）。

###### ★★ 依赖决策：NPOI **刻意锁 2.7.2**（Apache-2.0），⛔ 不要顺手升 2.8.x

###### 契约口径（**写死，层 2 必须遵守**）

- **值字典**：`FillValue { AnchorCode, Kind, Text, Number, Date, Bool, NumberFormat, FieldInstruction, Confidence, Source }`
- ★ **类型必须由层 2 显式给出** —— `SetCellValue(string)` vs `(double)` 传错重载**不报错但结果错**。

### 3.5 ⑤ 专家端 · 企业资料上传（新建）

**目标**：企业把**原始资料**（标准无关）传上来，形成「企业 × 阶段」的原始资料库，并**在上传时就把资料变成结构化信息（画像）**。

> **与你原话的对应**：「我们企业的资料，需要在 minio 中得到一个新的企业 `Enterprise_Original_source`，结构是**企业的 code，阶段 code**，企业资料」

> ⚠️ **V2 重要修正**：本菜单**不只是上传** —— 它是**整条 5 段流水线的宿主**（见下）。
> 用户补充第 2 点明确：「上传企业或替换企业的资料其实是一个**非常复杂的过程**」。**本菜单的工作量远超「一个上传页」**，故已独立成册（`29` 号）。

#### 左树

```
● G4测试企业甲
   ● 复审                        ← 叶子 = 「企业×阶段」的原始资料
   ● 初审
● 测试企业b
      ● 复审
```

#### 右区

- 原始资料清单表：`文件名` / `大小` / `格式` / `上传时间` / `转换状态` / ★ **分析策略** / ★ **策略原因** / `操作`
- 工具栏：`[上传资料]`（**四段式上传**，已存在）/ `[批量替换]` / `[删除]` / ★ `[批量设置分析策略]`
- 列：`转换状态` 复用 `CertConvertBadge`；★ `分析策略` 是**可编辑下拉**（`分析` / `跳过分析` / `忽略`），`策略原因` 只在 `skip`/`ignore` 时显示，`PolicySource='ai'` 的行加「待确认」角标
- ★ **上传完成后弹出「本次上传 N 份，系统建议跳过分析 M 份」确认条**（补 6 的交互落点）—— 让用户**一次确认**，而不是逐行点

#### ★★ 上传 = 一条流水线（**补 2 的核心，V1 漏了这一步**）

> 用户原话：「上传企业或替换企业的资料其实是一个非常复杂的过程，涉及到**上传企业资料后，自动进行语义分析，分析他的分类，分析他文件的作用，自动生成 markdown 文件**，并需要考虑如何进行存储，我们**用标准文件进行匹配、计算填充的时候，其实并不是去读取原始文件，是从上传后提取的信息中进行匹配的**」

**上传不是「存文件」，是「把文件变成结构化信息」。** 5 段流水线：

```text
⓪ ★ 策略判定       → AnalyzePolicy = analyze / skip / ignore   ← 补 6，见 §3.5.3
   │                  （ignore ⇒ 到此为止，仅存档；skip ⇒ 只做 ①②，跳到 ⑥）
   ↓
① 落原始文件       → MinIO enterprise-original-source/{Ent}/{Stage}/…
   ↓ 入队 yzh_queue_task（TaskType = enterprise_doc_ingest）
② 格式归一         → .doc/.xls → .docx/.xlsx（复用 OfficeConvertService）
   ↓
③ 转 Markdown      → 落 {同路径}/markdown/xxx.md（复用现有转换链，⛔ 不另写）
   ↓
④ ★ 语义分析       → 产出「分类」+「作用」+「摘要」+「可服务的标准/阶段」
   ↓                + ★「建议策略 suggestedPolicy」（补 6）
   ↓                （LLM + 受控字典；结果可人工修正）
⑤ 落画像           → cert_enterprise_doc_profile（见 §四 新表）
   ↓
⑥ 进匹配候选       → skip / ignore 的文件**不进**候选集（补 6 的直接收益）
```

**★ 关键架构约束（决定系统形状）**：

| # | 约束 | 后果 |
|---|------|------|
| **A-1** | **匹配与填充的输入 = 画像 + markdown，⛔ 不重读原始文件** | 原始文件只在「上传/替换」时读一次 ⇒ 生成侧性能与原始格式解耦 |
| **A-2** | ④ 语义分析**必须在上传时完成并落库**，不能推迟到规范化时 | 规范化时做 LLM 调用 ⇒ 不可重放、不可批量、不可审计 |
| **A-3** | 画像的「分类/作用」是**推荐值**，允许人工修正；修正后**必须留痕** | 见 §九 质量基线 |
| **A-4** | 原始文件**替换** ⇒ 画像必须**失效重算**（不是增量更新） | 否则「同一文件名的旧画像」会污染新一轮生成 |

> ⚠️ **与「标准文档」侧的对称性**：标准文档侧已经有「转换 → markdown」链路（`cert_standard_directory_file.MarkdownPath / MarkdownStatus`）。
> 企业侧要做的是**同构 + 多一段语义分析**。⛔ **不要把两套转换链写成两份代码** —— 应抽同一份「转换 + 解析」服务，企业侧多挂一个「语义分析」后置步骤。

#### 存储三层（补 2 的「需要考虑如何进行存储」）

| 层 | 存什么 | 存在哪 | 谁读它 |
|----|--------|--------|--------|
| **L1 原始** | 企业上传的原文件（不可变，替换 = 新版本） | MinIO `enterprise-original-source/…` | 仅下载/预览 |
| **L2 派生** | markdown + 转 pdf（可重算） | MinIO 同路径 `markdown/`、`pdf/` | 生成侧读 markdown |
| **L3 结构** | 画像（分类/作用/摘要）+ 字段/表格提取结果 | **MySQL**（`cert_enterprise_doc_profile` 等） | ★ 匹配 / 填充 / 规范化**只读这一层** |

> **为什么 L3 必须在 MySQL 而不是 MinIO**：匹配与填充需要**按字段检索、排序、打分**（`DispatchMatcher`），文件系统做不了。
> 这也是「不读原始文件」的落地方式 —— 生成侧连 markdown 都可能不读，只读 L3 的结构化字段。

#### ★★ 3.5.3 忽略状态（**补 6**）—— 先分清「忽略什么」

> 用户原话：「针对企业上传的资料，**有一些文档是没有任何作用的**，我们也可以增加**忽略状态**，因为有些企业提供的比如**营业执照、企业的无关文档**等，**有些已经在我们全局参数定义了**，有些是**根本无关的文档**，这样，我们**分析的时候，可以减少分析过程**」

**★ 第一个必须纠正的认知**：用户把三类文档混成了一句，但它们的处理**完全不同**。

| 用户说的 | 实际是什么 | 该不该忽略 | 为什么 |
|---------|-----------|-----------|--------|
| **营业执照** | 内容（统一社会信用代码/名称/地址）**已在全局参数里** | ⛔ **不能整体忽略** | 营业执照是**必备审核证据** —— 忽略它 ⇒ 证据清单里少了法定要件。**要忽略的是「从它提取数据」，不是「处理这个文件」** |
| **已被参数覆盖的文档** | 数据来源冗余 | ✅ **跳过分析/提取** | 参数已有 ⇒ 再提取一遍是纯浪费（LLM 调用 + markdown 转换） |
| **根本无关的文档**（企业随手传的） | 与本次认证无关 | ✅ **跳过分析，且不进匹配候选** | 否则它会污染匹配召回（出现在候选里但永远匹配不上） |

⇒ **结论：忽略的粒度必须是「用途级」，不是「文件级」。**

**三层区分（本文写死，⛔ 后续不得压平）**：

| 层 | 问题 | 能不能忽略 |
|----|------|-----------|
| **L0 存档** | 文件还在不在？ | ⛔ **永不忽略**（证据链完整性，审计要看「企业当时交了什么」） |
| **L1 证据** | 审核时要不要看？ | ⛔ **默认不忽略**；仅 `irrelevant` 可移出证据清单，且**必须留痕** |
| **L2 数据来源** | 要不要从它提取数据？ | ✅ **这一层才是「忽略状态」的作用域** |

**新增列（加在 `cert_enterprise_original_file`）**：

| 列 | 类型 | 语义 |
|----|------|------|
| `AnalyzePolicy` | `varchar(20) NOT NULL DEFAULT 'analyze'` | `analyze` 全流程 / `skip` 只存档+作证据（**不分析、不提取、不进匹配候选**）/ `ignore` 完全无关（**不进任何清单**，仅 L0 存档） |
| `PolicyReason` | `varchar(30)` | `covered_by_params`（已被全局参数覆盖）/ `irrelevant`（与本企业认证无关）/ `duplicate`（重复上传）/ `manual`（人工指定） |
| `PolicySource` | `varchar(10)` | `ai`（系统建议）/ `manual`（人工确认/改写）—— 与 §3.4 的 `*Source` 同一模式 |
| `PolicyDecidedBy` / `PolicyDecidedTime` | `varchar(50)` / `datetime` | 留痕（§九 审计 A-1 同类要求） |

**★ 谁决定**（与 A-3「推荐值 + 人工可改」一致）：
- **AI 给建议**（在语义分析时顺带产出 `suggestedPolicy` + `reason`）
- **人工确认**（上传页表格里一列下拉，可批量改）
- ⛔ **不允许纯自动静默忽略** —— 「企业交了一份必备证据却被系统静默扔掉」是**审核事故**，不是效率优化

**★ 收益量化（回答「减少分析过程」到底省多少）**：

| 省掉的环节 | 对 `skip` | 对 `ignore` |
|-----------|----------|------------|
| markdown 转换（anydoc 容器，秒级） | ✅ 省 | ✅ 省 |
| **LLM 语义分析调用（贵）** | ✅ 省 | ✅ 省 |
| 字段/表格提取（② 的规则链） | ✅ 省 | ✅ 省 |
| 匹配候选集大小 | ✅ 缩小 | ✅ 缩小 |
| 存档 + 证据清单 | 保留 | 仅存档 |

> ⚠️ **判定「已被全局参数覆盖」需要一个能力**：把「文档类型」映射到「它本该提供的参数集合」。
> 例：`营业执照` → 提供 `credit_code` / `company_name` / `legal_person` / `company_address`；
> 若这 4 个参数**在 `cert_fill_param_value` 里都已有值** ⇒ 建议 `skip` + `covered_by_params`。
> ⇒ 这是一张**「文档类型 → 参数集」映射**（可先硬编码在字典里，后续再做智能推断）—— **Q-O**。

```
         ● 4 记录文件              ← 点它 = 该目录**全量生成**
            ▸ 风险管理报告         ← 点它 = **单文件生成**
              🔒 已锁定            ← 锁定徽标
            ▸ 内审计划
              ⚪ 未生成
```

#### ★★ 粒度模型（**补 1 的核心，V1 想错了**）

> 用户原话：「企业按整体的所有的标准化，还是按一个标准，或一个标准下的目录，或一个文件进行规范化**都是可以的**，我们的**核心是单个文件的规范化**，**一个文件的规范化是一个队列**，不同的范围是**队列的范围不一样**」

**V1 的错误**：写「点阶段 = 全量生成」，暗示**一个范围 = 一个大任务**。
**V2 的正确模型**：

```text
┌─ 范围（用户点的树节点）────────────────────────────┐
│  整体 / 标准 / 阶段 / 目录 / 单个文件              │
│  ↓ 展开成文件清单（后端 normalize/plan 计算）        │
│  yzh_queue  ← 一个范围 = 一个「批次」，只做统计与进度  │
│    ├── yzh_queue_task  ← 一个文件 = 一个任务（原子）  │
│    ├── yzh_queue_task  ← 一个文件 = 一个任务         │
│    └── yzh_queue_task  ← 一个文件 = 一个任务         │
└────────────────────────────────────────────────┘
```

| 概念 | 落在哪 | 说明 |
|------|--------|------|
| **原子单位 = 单文件** | `yzh_queue_task`（`Payload` = 单文件标识） | **恒为单文件**，与范围无关 |
| **范围** | `yzh_queue`（批次，含 `TotalCount` / `CompletedCount` / `FailedCount` / `Progress`） | 点「整体」= 批次含全部文件；点「一个文件」= 批次含 1 个任务 |
| **「点阶段自动生成」** | 前端把阶段节点**展开成文件清单** → 批量入队 | ⛔ 不是后端一个大事务 |

**★ 这个模型白拿的 4 个好处**（正是「严谨程序」的要求，见 §九）：

| # | 好处 | 机制 |
|---|------|------|
| 1 | **部分失败可重试** | 失败的是**单个 task**，重试不重跑已成功的文件（V1 的「一个大任务」会全量重跑） |
| 2 | **并发安全** | 每个 task 只写自己的行 ⇒ 天然符合陷阱 **㉕**（并发写同行须列级 `UpdateAsync`）；配合 `yzh_queue_resource_lock` 防同文件双写 |
| 3 | **进度真实** | `CompletedCount / TotalCount` 是**文件数**，不是「步骤数」，用户看到的进度与实际一致 |
| 4 | **可取消** | 取消批次 = 把未开始的 task 置 `Cancelled`，已完成的产物**保留** |

> ⚠️ **与「专家任务」的区别**：`cert_expert_task_queue` 是**专家审核任务**（业务实体）；`yzh_queue` 是**执行队列**（技术设施）。
> 本处用 **`yzh_queue`**（技术队列），⛔ 不要往 `cert_expert_*` 里塞。

#### 右区（选中节点后）

- **范围预览**（干跑，不写任何数据）：
  > 「本次将生成 **12** 个文件：新增 8 / 重新生成 2 / **跳过 2**（已锁定）。按 `[开始生成]` 入队。」
- 生成结果表：`文件名` / `标准编号` / `来源画像` / `状态` / `锁定` / `操作`
  - `来源画像` = 指向 L3 画像（**不是原始文件**，见 §3.5 A-1）
- 操作：`[开始生成]` / `[重新生成]`（仅未锁定项）/ `[锁定]` / `[解锁]` / `[取消批次]`
- 进度：复用 `yzh_queue` 批次进度（**框架层已完整，⛔ 勿新建**）

| **Q-J** | **队列粒度术语对齐**：你说「一个文件的规范化是**一个队列**」，但工程上「批次 vs 任务」需要分开 | **A**：**文件 = `yzh_queue_task`（任务）**，**范围 = `yzh_queue`（批次）** | **B**：一个文件也建一个独立 `yzh_queue` 批次，范围 = 多个批次 | 选 B 会产生大量「只有 1 个任务」的批次，且「点阶段生成」无法整体取消 / 无法统一看进度 |

| **Q-L** | **画像的人工修正是否触发下游重算** | **A**：只**留痕** + 提示「已有 N 个产物基于旧画像」，由用户决定是否重生成 | **B**：自动把受影响产物标记为「待重算」并入队 | A 安全可控；B 会「改一个字，全库重跑」 |
| **Q-M** | **企业资料字段/表格提取结果表**（`cert_enterprise_doc_field_value`）本轮建不建 | **A**：**延后**。本轮匹配只用「分类 + 作用 + 关键词」 | **B**：本轮建，匹配可用字段级打分（更准） | A 少一张表、少一套提取链路；B 匹配精度更高但依赖 ② 的提取规则已配好 |
| **Q-N** | **⑤⑥ 独立成册的拆分粒度** | **A**：`29-企业资料上传详细设计` + `30-企业资料规范化详细设计` 两册 | **B**：合成一册 `29-企业资料管理详细设计` | 两册各约 800~1200 行（补 4 说「大量表结构与功能点」）；合成一册会超过单册可读上限 |

> **Q-J 特别说明**（术语容易混）：
> ```text
> 你说的「一个文件的规范化是一个队列」
>   → 工程落地 = 一个文件 = 一个【任务】（yzh_queue_task），可独立重试 / 独立并发 / 独立计进度
> 你说的「不同的范围是队列的范围不一样」
>   → 工程落地 = 范围 = 一个【批次】（yzh_queue），负责统计 Total/Completed/Failed
> ```
> 两者**都是「队列」这个概念**，只是一个在批次层、一个在任务层。**若选 B**，则「点阶段生成 12 个文件」= 建 12 个批次，`yzh_queue` 表会迅速膨胀且列表页无意义。

## 九、★ 质量基线（**补 5：不要 demo，要严谨的程序**）

> 用户原话：「我之前提出的需要给机构和专家看到我们程序的设计，**并不是做 demo**，我需要**实实际际的功能开发，严谨的程序设计**，哪怕我们最终生成的东西是个理想化的，但程序的**规范性、合理性、稳定性**都是必须要考虑的」

**本节不是原则声明，是可验收项。** 每一条都要在实现时能被检查。

### 9.1 规范性（规范 = 不依赖个人记忆）

| # | 要求 | 判据 |
|---|------|------|
| N-1 | 一切路径经 `PathBuilder`，⛔ 禁手工拼串 | `grep` 不到 `"/standard-directory/" +` 之类的拼接 |
| N-2 | 一切新库进白名单 `DocumentLibraryPath.Prefixes` | 新库的 `download`/`preview` 实测通过（漏加会静默失败） |
| N-3 | DB 列 = C# 属性 = TS 字段，PascalCase 逐字一致 | 新增表跑一次列名对照 |
| N-4 | 禁 `Enable` 列，启用唯一字段 `IsValid` | 新表 DDL 无 `Enable` |
| N-5 | 唯一键不含 `IsDeleted`，建前查重**含已删**并**复活** | 删了再建同名 ⇒ 不报 1062 |

### 9.2 合理性（合理 = 与业务语义对齐，不是「能跑就行」）

| # | 要求 | 判据 |
|---|------|------|
| R-1 | **三层语义分开**：层 1「写在哪」（锚点）/ 层 2「值从哪来」（字段定义）/ 层 3「怎么写」（格式） | 三张表各司其职，⛔ 不合并 |
| R-2 | **读写共用一份定义**（`cert_doc_field_def`），⛔ 不造第二套 | 生成侧与提取侧引用同一 `FieldCode` |
| R-3 | **生成输入 = 画像，不是原始文件**（A-1） | 生成服务的依赖里**没有**「读原始文件」的调用 |
| R-4 | **语义分析输出必须落受控字典**（`DOC_CATEGORY`/`DOC_PURPOSE`） | LLM 返回的分类名 ∈ 字典值集；越界 ⇒ 记 warning 不落库 |
| R-5 | 参数作用域遵循**最具体优先**（`PickMostSpecific`），通用可被标准/阶段覆写 | 实测：食品版 `quality_objective` 覆写通用版 ✓ |
| R-6 | 「完成度」等指标**只有一套口径** | `total=0` ⇒ 后端 `0.0`、前端 `0`（V1 曾出现 100% vs 0% 两套，已修） |

### 9.3 稳定性（稳定 = 失败可解释、可重试、不脏写）

| # | 要求 | 判据 |
|---|------|------|
| S-1 | **幂等**：同一「企业+标准+阶段+文件」重复入队 ⇒ 识别为「重新生成」而非新增 | 连点两次 `[开始生成]`，产物不重复、版本不虚增 |
| S-2 | **任务级重试**：失败的是单文件任务，重试不重跑已成功项 | `yzh_queue_task.RetryCount` / `NextRetryAt` 生效 |
| S-3 | **并发不脏写**：并发写同一行必须列级 `UpdateAsync(entity, cols)`（陷阱 **㉕**） | 两链并发跑，字段不被清成 NULL |
| S-4 | **后台取数用 `GetOneIgnoreValidAsync`**（陷阱 **㉖**） | 执行器能找到「自己正在处理的」文件 |
| S-5 | **软删/启用过滤**：属性必须声明在实体自身（陷阱 **㉚**） | 过滤实测生效 |
| S-6 | **锁定优先**：已锁定项在任何生成路径下**都不被覆盖** | 锁一个文件 → 全量生成 → 该文件 `UpdateTime` 不变 |
| S-7 | **可取消**：取消批次 ⇒ 未开始任务置 `Cancelled`，已完成产物保留 | 取消后批次状态为 `Cancelled` 且产物可下载 |
| S-8 | **失败可解释**：`ErrorMessage` 必须是人能看懂的原因（不是堆栈） | 队列详情页显示「模板未上传」「画像缺失」等具体原因 |

| A-2 | 锁定/解锁 ⇒ 记 `LockedBy` / `LockedTime`（解锁也留痕） |
| A-3 | 产物 ⇒ 记 `SourceProfileCode`（哪份画像）+ 生成时间 + 生成批次 |
| A-4 | 上传替换 ⇒ 走 `cert_enterprise_file_version`（版本 + `Reason`）+ `cert_enterprise_file_op_log` |
| **A-5** | ★ **忽略/恢复必须留痕**（补 6）：`PolicyDecidedBy` / `PolicyDecidedTime` / `PolicySource`（`ai` 建议 or `manual` 确认）；**恢复**同样留痕 |
