## 一、ACM 在中国医疗审核市场的地位

### 1.1 机构身份确认

通过调研确认，用户朋友所在机构实名信息：

| 项目 | 详情 |
|------|------|
| 中文全称 | 艾西姆认证（上海）有限公司 |
| 英文简称 | ACM (CHINA) LIMITED |
| 注册地 | 上海 |
| 批准号 | CNCA-RF-2016-67 |
| 企业性质 | 中外合资（英国 ACM International + 海南博钲投资） |
| 分支机构 | **全国 20 家分公司** |
| 累计认证企业 | **超 10,000 家** |

### 1.2 ACM 行业地位

**中等偏上规模，定位清晰**。在 ISO 13485 医疗器械认证领域具备以下特征：

| 维度 | 评价 | 说明 |
|------|------|------|
| 总体规模 | 中型偏大 | 10000+ 认证企业，20 家分公司，但年审核项目数不及 SGS/TÜV |
| 医疗领域 | 有竞争力 | ISO 13485 是其核心业务线之一 |
| 差异化优势 | 中外合资身份 | 兼具国际认可（UKAS）+ 国内合规（CNCA），出口型企业偏好 |
| 行业荣誉 | 多项"首家" | 首家取得 IPMS 认证的外资机构、第三家取得服务认证的外资机构（继 SGS、ITS 后） |
| 苏州布局 | 必有分支 | 苏州是长三角医疗器械重镇，20 家分公司中必然覆盖 |

**结论**：ACM 不是体量最大的，但资质齐全、覆盖面广，是非常理想的**第一个客户**——规模足够验证产品价值，又不至于像 SGS 那样流程僵化难以撬动。

### 1.3 分支与推广路径

ACM 全国 20 家分公司意味着：一旦苏州分公司验证成功，内部推广到上海总部及其他 19 家分公司的路径是**天然存在的**。这是从审核机构端切入的最大优势——内部渠道比外部销售高效得多。

**推广节奏建议**：

```
第一阶段（0-3月）    第二阶段（3-9月）       第三阶段（9-18月）
苏州分公司试点    →   上海总部+长三角分公司   →   全国20家分公司全覆盖
（朋友内部推广）      （总部认可后推广）         （形成机构标准工具）
                                                            ↓
                                               第四阶段（18月+）
                                               适配其他认证机构模板
                                               （SGS/CQC/华测等）
```

## 二、规则引擎体系架构

### 2.1 总体设计原则

所有校验逻辑应拆分为**独立引擎**，各引擎之间通过统一的数据总线通信，便于单独开发、测试、扩展。

```
                          ┌──────────────────┐
                          │   审核数据总线     │
                          │  (统一数据结构)    │
                          └──────┬───────────┘
           ┌─────────┬─────────┬─┴─────────┬─────────┬─────────┐
           ▼         ▼         ▼           ▼         ▼         ▼
      ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
      │ 文件    │ │ 日期    │ │ 人员    │ │ 条款    │ │ 数值    │ │ 报告    │
      │ 完整性  │ │ 逻辑    │ │ 一致性  │ │ 符合性  │ │ 指标    │ │ 生成    │
      │ 引擎    │ │ 引擎    │ │ 引擎    │ │ 引擎    │ │ 引擎    │ │ 引擎    │
      └────────┘ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
```

### 2.2 各引擎详细设计

#### 引擎一：文件完整性引擎

**职责**：校验企业提交文件与实际需求的匹配度。

**核心规则**（可扩展）：

| 规则 ID | 规则描述 | 触发条件 | 输出 |
|---------|---------|---------|------|
| FILE-001 | 应提交文件清单 vs 实际提交文件列表 | 审核项目创建时 | 缺失文件清单 |
| FILE-002 | 文件编号格式校验 | 文件入库时 | 格式异常文件 |
| FILE-003 | 文件版本号 vs 手册引用版本号 | 文件入库时 | 版本不一致警告 |
| FILE-004 | 空文件/占位文件检测 | 文件入库时 | 疑似占位文件 |
| FILE-005 | 引用文件追溯（A文件引用B文件，B是否存在） | 全量扫描 | 断链清单 |
| FILE-006 | 文件最后修改时间 vs 审核时间合理性 | 文件入库时 | 时间异常文件 |

**扩展机制**：通过配置文件定义"应提交文件清单"，不同机构/标准可加载不同清单模板。

```yaml
# 示例：ISO 13485 Stage 1 应提交文件清单模板
standard: ISO 13485:2016
stage: Stage1
required_documents:
  - category: "管理手册"
    items:
      - pattern: "质量手册|管理手册"
        required: true
        description: "包含范围、删减说明、过程描述"
  - category: "程序文件"
    items:
      - pattern: "文件控制程序|QP-01"
        required: true
      - pattern: "记录控制程序|QP-02"
        required: true
      # ... 22个标准程序文件
  - category: "记录表单"
    items:
      - pattern: "内审.*记录|内部审核.*报告"
        required: true
        min_period_months: 12
      - pattern: "管理评审.*记录|管理评审.*报告"
        required: true
        min_count: 1
```

---

#### 引擎二：日期逻辑引擎

**职责**：校验所有日期字段的逻辑一致性。

**核心规则**（可扩展，当前 12 条）：

| 规则 ID | 校验逻辑 | 严重度 | 说明 |
|---------|---------|--------|------|
| DATE-001 | 批准日期 ≤ 生效日期 | 🔴 高 | 文件未经批准不得生效 |
| DATE-002 | 培训日期 ≤ 考核日期 | 🔴 高 | 先培训后考核 |
| DATE-003 | 内审日期 < 管理评审日期 | 🔴 高 | 先内审后管理评审 |
| DATE-004 | 管理评审间隔 ≤ 12 个月 | 🟡 中 | ISO 13485 要求 |
| DATE-005 | 设备校准有效期 > 审核日期 | 🔴 高 | 校准过期不可用 |
| DATE-006 | 入职日期 ≤ 培训日期 | 🟢 低 | 入职后培训 |
| DATE-007 | NC 关闭日期 ≥ NC 开具日期 | 🔴 高 | 不可能提前关闭 |
| DATE-008 | 体系运行时间 ≥ 3 个月 | 🔴 高 | Stage 1 前提条件 |
| DATE-009 | 供应商评价日期 < 采购日期 | 🟡 中 | 先评价后采购 |
| DATE-010 | 设计阶段日期有序性 | 🟡 中 | 输入→输出→评审→验证→确认 |
| DATE-011 | 管理评审日期 > 上次管理评审日期 | 🟡 中 | 时间单向性 |
| DATE-012 | 人员资格证书有效期 > 审核日期 | 🔴 高 | 证书过期 |

**扩展机制**：规则以 JSON/YAML 配置，支持动态新增，无需改代码。

```json
{
  "rule_id": "DATE-013",
  "name": "合同签订日期 vs 审核申请日期",
  "field_a": "contract_date",
  "field_b": "application_date",
  "operator": "lt",
  "severity": "medium",
  "message_template": "合同签订日期({a})应早于审核申请日期({b})"
}
```

#### 引擎三：人员一致性引擎

**职责**：校验所有涉及人员的记录与企业人员主数据的匹配。

**核心规则**（可扩展，当前 8 条）：

| 规则 ID | 校验逻辑 | 严重度 |
|---------|---------|--------|
| PERSON-001 | 培训记录参训人员 ∈ 员工名册 | 🟡 中 |
| PERSON-002 | 内审员不审核自己所在部门 | 🔴 高 |
| PERSON-003 | 管理者代表在组织架构中明确任命 | 🔴 高 |
| PERSON-004 | 特殊过程操作人员持有效资格证书 | 🔴 高 |
| PERSON-005 | 检验人员 ≠ 生产人员（职责分离） | 🟡 中 |
| PERSON-006 | 管理评审参与人覆盖管理层+管代+部门负责人 | 🟢 低 |
| PERSON-007 | 文件审批人在授权签署人清单中 | 🟡 中 |
| PERSON-008 | 供应商评价人 ≠ 同一供应商联系人 | 🟢 低 |

**人名匹配处理**：支持模糊匹配（"张三" vs "张 三" vs "Zhang San"）、同音字容错、简称匹配（"王总"→"王建国"需人工确认）。

---

#### 引擎四：条款符合性引擎

**职责**：将审核证据与 ISO 13485 标准条款自动匹配，判定符合性。

**核心逻辑**：

```
审核证据 → NLP语义解析 → 提取关键词/实体 → 规则库匹配 → 关联条款 → 输出判定建议
```

| 证据示例 | 自动匹配条款 | 判定依据 |
|---------|------------|---------|
| "内审于2026.05.15-16开展，覆盖全部部门" | 8.2.4 内部审核 | 关键字"内审"+"日期"+"覆盖范围" |
| "顾客满意度调查得分96.5分" | 8.2.1 反馈 | 关键字"满意度"+数值 |
| "发现3项不符合，已全部整改关闭" | 8.5.2 纠正措施 | 关键字"不符合"+"整改"+"关闭" |
| "培训记录显示焊接操作工张某证书有效期至2025.12" | 6.2 人力资源 + 7.5 特殊过程 | 关键字"培训"+"证书"+"有效期"+"操作工" |

---

#### 引擎五：数值指标引擎

**职责**：提取质量目标和实际达成值，自动对比。

| 规则 ID | 校验逻辑 | 严重度 |
|---------|---------|--------|
| METRIC-001 | 质量目标必须量化（不能纯定性） | 🟡 中 |
| METRIC-002 | 实际值 vs 目标值对比 | 🔴 高 |
| METRIC-003 | 统计周期与报告周期一致 | 🟡 中 |
| METRIC-004 | 设备数量 vs 设备清单一致 | 🟡 中 |
| METRIC-005 | 培训学时 ≥ 法规最低要求 | 🟡 中 |

---

#### 引擎六：报告生成引擎

**职责**：将审核数据 + 校验结果 → 按机构模板 → 生成最终报告。

**架构**：

```
审核数据（JSON）  +  模板（Word/HTML）  →  报告（PDF/Word）
     ↓                      ↓                      ↓
 统一数据结构          Jinja2/docxtpl           自动填充
 企业信息              ACM 模板                  页码、目录
 审核证据              SGS 模板                  双栏排版
 NC 记录              CQC 模板                  签章位置
 审核结论              自定义模板                双语输出
```

**模板体系**：

```
templates/
├── acm/
│   ├── stage1_audit_record.docx      # Stage 1 审核记录模板
│   ├── stage2_audit_record.docx      # Stage 2 审核记录模板
│   ├── nc_report.docx                # 不符合项报告模板
│   └── audit_conclusion.docx         # 审核结论模板
├── sgs/                              # 后续扩展
├── cqc/                              # 后续扩展
└── custom/                           # 机构自定义上传
```

**重点**：模板用 Word 的 Jinja2 标签（如 `{{ enterprise.name }}`、`{% for clause in audit.clauses %}`），审核员只需上传一次模板，后续全部自动填充。

---

### 2.3 引擎调度与编排

所有引擎通过**审核流水线（Audit Pipeline）**统一调度：

```
审核项目创建
    │
    ▼
[阶段1: 文件接收] → 文件完整性引擎 → 缺失清单 → 通知企业补交
    │
    ▼
[阶段2: 数据提取] → OCR/NLP → 结构化数据池
    │
    ▼
[阶段3: 预审校验] → 日期引擎 + 人员引擎 + 数值引擎 → 预审报告（审核员用）
    │
    ▼
[阶段4: 条款审核] → 条款符合性引擎 → 审核记录草稿
    │
    ▼
[阶段5: 报告输出] → 报告生成引擎 → 正式审核报告
```

每个引擎独立运行，可单独启用/禁用，新引擎通过注册机制接入流水线。

## 三、移动端深度分析

### 3.1 审核员的移动端需求场景

审核员的工作场景天然是移动的：

| 场景 | 移动端需求 | 频率 |
|------|-----------|------|
| 现场审核 | 在车间/仓库/实验室现场录入审核证据 | 每天 6-8 小时 |
| 拍照取证 | 拍摄设备铭牌、校准标签、生产记录、现场环境 | 每次审核 50-200 张照片 |
| 离线工作 | 部分生产区域无网络（洁净车间、屏蔽室） | 每次审核 2-4 小时 |
| 语音记录 | 现场口述审核发现，解放双手 | 高频 |
| 查看标准条款 | 现场实时查阅 ISO 13485 条款原文 | 每次审核 20-50 次 |
| 标记不符合项 | 现场即时标记 NC，拍照+描述+条款 | 每次审核 3-10 项 |
| 查看历史记录 | 查阅该企业上次审核的问题点和整改情况 | 每次审核 5-10 次 |

### 3.2 移动端核心功能设计

**MVP 阶段（必须有的）**：

| 功能 | 描述 | 优先级 |
|------|------|--------|
| 审核项目列表 | 查看分配给自己的审核任务，离线缓存项目数据 | P0 |
| 条款对照录入 | 按标准条款逐条录入审核证据，支持拍照/语音/文字 | P0 |
| 拍照取证 | 拍照自动关联到当前条款，自动添加水印（时间+GPS+条款号） | P0 |
| 离线模式 | 无网环境下正常使用，恢复网络后自动同步 | P0 |
| NC 快速标记 | 一键标记不符合项，自动生成编号，拍照+描述 | P0 |
| 报告预览 | 实时查看当前审核进度和已生成的报告内容 | P1 |
| 电子签名 | 审核员和企业代表现场签名确认 | P1 |

**V1.0 阶段**：

| 功能 | 描述 |
|------|------|
| 语音转文字 | 口述审核发现，AI 自动转文字并归类到条款 |
| AR 辅助 | 拍摄设备铭牌，AR 叠加显示校准状态、上次审核问题 |
| 实时协作 | 多审核员同时审核不同部门，数据实时合并 |
| 智能提醒 | 根据审核进度，提醒哪些条款还未覆盖 |

### 3.3 移动端开发价值判断

**结论：必须做，而且这是差异化竞争的关键。** 理由：

1. **竞品覆盖不全**：智审100 的移动端体验一般，iAuditor 移动端好但 AI 能力弱。做出"AI 辅助的移动审核工具"是差异化点
2. **审核员核心场景**：审核员 70% 的工作时间在现场，移动端不好用 = 产品不好用
3. **数据采集入口**：移动端是数据采集的核心入口，拍照/语音/文字都在移动端发生，质量直接影响后端 AI 效果
4. **降低使用门槛**：审核员大多是年纪较大的行业专家，操作越简单越好，移动端拍照即录入比 PC 端打字门槛低得多

**技术实现建议**：uni-app（一套代码编译 iOS + Android + H5），降低开发成本。

## 四、任务队列与通知系统

### 4.1 需要队列的场景

| 场景 | 耗时 | 是否需要队列 |
|------|------|------------|
| OCR 文字识别（单张图片） | 1-3 秒 | 同步即可 |
| OCR 文字识别（50 张图片批量） | 30-90 秒 | ✅ 需要队列 |
| NLP 语义分析（单条证据） | 1-2 秒 | 同步即可 |
| PDF/Word 报告生成 | 5-15 秒 | 看报告复杂度 |
| 全量文件校验（100+ 文件） | 10-60 秒 | ✅ 需要队列 |
| 知识库向量化（企业档案入库） | 30-300 秒 | ✅ 需要队列 |
| 大模型分析（长篇审核记录） | 10-30 秒 | ✅ 需要队列 |

### 4.2 队列系统设计

```
                    ┌─────────────────┐
    用户操作        │   任务队列       │    Worker 池
       │            │  (Redis/RabbitMQ)│       │
       ▼            │                  │       ▼
  ┌─────────┐       │  ┌────────────┐  │  ┌──────────┐
  │ API 服务 │──────▶│  │ OCR 队列    │──▶│ OCR Worker│
  └─────────┘       │  ├────────────┤  │  ├──────────┤
       │            │  │ NLP 队列    │──▶│ NLP Worker│
       ▼            │  ├────────────┤  │  ├──────────┤
  ┌─────────┐       │  │ 报告队列    │──▶│ 报告Worker│
  │ WebSocket│◀─────│  ├────────────┤  │  ├──────────┤
  │ 推送服务 │       │  │ 校验队列    │──▶│ 校验Worker│
  └─────────┘       │  └────────────┘  │  └──────────┘
                    └─────────────────┘
```

**MVP 阶段简化方案**：用 Redis 做轻量级队列（通过 `LPUSH/BRPOP`），Worker 用 Python Celery 或直接多进程。不需要 RabbitMQ/Kafka 这种重型 MQ，3-5 人团队用 Redis 足够。

### 4.3 通知系统

| 通知类型 | 触发场景 | 通知方式 |
|---------|---------|---------|
| 任务完成通知 | OCR/NLP/报告生成完成 | Web 端 Toast + 移动端推送 |
| 校验结果通知 | 文件校验发现缺失 | WebSocket 实时推送 |
| 审核进度通知 | 条款覆盖率达到阈值 | 审核员面板实时更新 |
| 企业端通知 | 审核员要求企业补交材料 | 短信/微信/邮件 |
| 报告生成通知 | 报告生成完成，可下载 | 下载按钮高亮 + 推送 |

**MVP 阶段**：WebSocket（实时）+ 邮件（异步）足够。不需要独立的推送服务。

### 4.4 资源消耗估算

| 操作 | CPU | 内存 | 单次耗时 | 日均调用量估算 |
|------|-----|------|---------|--------------|
| OCR（百度 API） | 低（云端） | - | 1-2s | 200-500 次 |
| NLP 语义分析 | 中 | 2GB | 1-3s | 100-300 次 |
| 报告生成 | 低 | 500MB | 5-15s | 20-50 次 |
| 全量文件校验 | 中 | 1GB | 30-60s | 10-20 次 |
| 知识库向量化 | 高 | 4GB | 60-300s | 1-5 次 |

**服务器建议（MVP 阶段）**：阿里云 4 核 16G + 100G SSD，月费约 500-800 元，完全够用。AI 重度计算（OCR/NLP）先走第三方 API，降低自建 GPU 成本。

## 五、企业知识库系统

### 5.1 必要性分析

**结论：必须建。这是产品的核心数据壁垒。**

原因：

| 维度 | 说明 |
|------|------|
| 审核连续性 | 同一企业每年审核，上次的问题点、NC 记录、整改情况是本次审核的重要参考 |
| 规则自进化 | 积累的审核数据越多，规则引擎越精准，AI 模型越强 |
| 客户粘性 | 企业历年数据在系统中，迁移成本极高，客户流失率低 |
| 增值服务 | 基于历史数据提供趋势分析、风险预警、合规健康度评分等增值服务 |
| 竞品壁垒 | 先发者积累的数据越多，后来者越难追赶 |

### 5.4 存储量估算

| 数据类型 | 单企业单次审核 | 说明 |
|---------|--------------|------|
| 原始文件（PDF/Word/图片） | 50-200 MB | 管理手册、程序文件、记录表单 |
| 审核证据照片 | 50-300 MB | 现场拍照 50-200 张，每张 1-3MB |
| 审核报告（PDF） | 1-5 MB | 生成的审核报告 |
| 结构化数据（JSON） | 1-5 MB | 审核记录、NC、校验结果 |
| 向量数据 | 5-20 MB | 全文向量化索引 |
| **单次合计** | **100-500 MB** | |

**规模化估算**：

| 企业数量 | 年数 | 总存储（中位数） | 存储方案 |
|---------|------|----------------|---------|
| 10 家 | 1 年 | ~3 GB | 服务器本地磁盘 |
| 100 家 | 3 年 | ~90 GB | 阿里云 OSS |
| 500 家 | 5 年 | ~750 GB | OSS + 冷热分层 |
| 2000 家 | 5 年 | ~3 TB | OSS 标准存储 |

MVP 阶段（朋友内部 10-20 家企业）存储压力很小，服务器本地磁盘即可。

### 5.5 知识库的应用场景

| 场景 | 实现方式 | 价值 |
|------|---------|------|
| 审核前准备 | 自动加载企业历年 NC 记录，审核员提前了解问题点 | 提效 30% |
| 审核中参考 | 审核员拍照铭牌，AI 自动显示该设备上次校准信息 | 省去翻找时间 |
| NC 趋势分析 | 按条款/部门/年份分析 NC 趋势，发现系统性问题 | 增值服务 |
| 合规健康度评分 | 基于历史数据给企业打分，量化合规水平 | 差异化功能 |
| 同行对比 | 匿名化后对比同类型企业的审核数据，发现行业共性 | 增值报告 |
| AI 培训 | 用历史 NC 数据训练模型，提升自动判定准确率 | 长期壁垒 |

### 5.6 技术选型

| 层 | 方案 | 说明 |
|----|------|------|
| 结构化存储 | PostgreSQL | 企业信息、审核记录、NC、校验结果 |
| 文件存储 | 本地磁盘 → 阿里云 OSS | MVP 本地 → 规模化后上云 |
| 向量数据库 | ChromaDB（轻量）→ Milvus | MVP 用 ChromaDB 嵌入 Python 进程，零运维 |
| 知识图谱 | Neo4j（后期） | MVP 不做，V2.0 引入关联分析 |
| RAG 检索 | LangChain + ChromaDB | 审核员自然语言查询历史记录 |

**MVP 简化**：所有数据存在 PostgreSQL + 本地文件系统，向量化用 ChromaDB（pip install 即可），不需要独立部署任何额外服务。

## 六、MVP 技术栈总结

| 层 | MVP 方案 | 升级方案（规模化后） |
|----|---------|-------------------|
| 前端 Web | Vue 3 + Element Plus | — |
| 移动端 | uni-app（iOS/Android/H5） | — |
| 后端 | Python FastAPI | 加 Node.js 微服务拆分 |
| 数据库 | PostgreSQL + Redis | 读写分离 |
| 任务队列 | Redis + Celery | RabbitMQ |
| OCR | 百度智能云 API | 私有化 PaddleOCR |

| 向量检索 | ChromaDB | Milvus |
| 文件存储 | 本地磁盘 | 阿里云 OSS |
| 部署 | 单机 Docker | K8s 集群 |
| 监控 | — | Prometheus + Grafana |

**核心原则**：MVP 阶段所有组件都选**可单机部署、零运维、免费开源**的方案，全力聚焦业务逻辑开发。
