## 一、功能概述

### 1.1 两个核心功能

| 功能 | 页面 | 用户角色 | 一句话描述 |
|------|------|---------|-----------|
| **NC检查规则管理** | `/CertPlatform/WorkflowRules/Rules` | 管理员 | 按机构→标准→阶段→条款维度维护 NC 检查项，每项绑定一个可执行工作流 |
| **工作流可视化设计** | `/CertPlatform/WorkflowDesigner/Designer/:code` | 管理员 | 用 LogicFlow 画布拖拽 Skill 节点，配置 inputs/outputs/branches，发布为可执行 DAG |

### 1.2 核心业务逻辑（必读）

```
工作流定义（wf_workflow_definition）        ←  先创建（草稿），独立存在
       │  workflow_code（版本化，发布态可被引用）
       ▼
NC检查规则（cert_validation_rule）          ←  后绑定，引用工作流最新发布版本
       │  审核员点击"执行审核"
       ▼
WorkflowEngine.RunAsync(workflowConfig, context)
       │  context = { BusinessType, BusinessId, EnterpriseCode, PhaseCode, OrgCode, StandardCode }
       ├── get_field[label_tag]   → 查 B-08（enterprise_code + phase_code + label_tag 过滤）
       ├── compare / date_diff    → 确定性计算（自研解释器）
       ├── llm_judge              → AI 语义判断（confidence + 人工复核兜底）
       ├── create_nc              → 写 B-07 不符合项
       └── （可选）审批节点        → ApproverResolver 解析审批人 → 生成待办
```

**关键设计决策（V2 与 V1 的差异）**：
- 工作流定义是**独立版本化实体**：同 `workflow_code` 支持多版本行，规则绑定"最新发布版本"，历史版本可回滚
- 规则页的"工作流"列是**只读引用**（显示 workflow_name + 版本号），操作入口是"在设计器中编辑"
- `enterprise_code`/`phase_code` 是**运行时注入**（来自审核任务上下文），设计器不配置
- **工作流保存与规则保存彻底分离**：设计器保存走 `api/workflow-definition`（草稿/发布），规则绑定走 `api/validation-rule`（V1 中二者混用是缺陷，V2 修正）

## 二、业务背景与目标

### 2.1 当前问题（V2 核验结论）

1. **工作流定义无法版本化管理**：`WorkflowDefinitionService.SaveAsync` 按 Id 覆盖式保存，无 draft/published 状态、无版本递增、无回滚能力；规则绑定后修改工作流会静默影响线上规则
2. **DAG 引擎缺失**：全仓仅 `DocExtractionRuleService.AI.cs` 与 `Program.cs` 出现 WorkflowEngine/SkillExecutor 字样，无实际执行器；设计的 DAG 无法运行
3. **测试沙箱悬空**：前端 Designer.vue 已有"测试"按钮并调用 `api/validation-rule/test`，但后端无此接口（404）；无测试企业数据，`get_field` 永远"未找到"
4. **设计器保存接口混用**：Designer.vue 保存时复用 `api/validation-rule`（ruleCode 生成逻辑与 workflow-definition 混用），工作流定义与规则实体语义混淆
5. **F-02 标签选择器缺失**：`wf_field_label_mapping` 表已建（v2.1.sql 1398 行）但无种子数据、无 tree 接口，`get_field`/`get_table` 节点无法可视化配置数据源
6. **F-04 缺 status 字段**：节点级执行状态无法落库，违反留痕设计初衷（选型文档 §4.3/TODO:P0）
7. **审批人解析空白**：审核任务产生 NC 后，审批流如何流转、审批人如何解析无设计（VOL 自带审批流与自研 DAG 的关系未澄清）
8. **规则无版本与测试**：`ValidationRuleService.CopyAsync` 可复制规则，但规则本身无版本管理、无"复制后测试通过再发布"的流程

### 2.2 目标

1. 工作流定义支持**版本化发布**：draft → published → archived 状态机，版本递增、历史保留、规则绑定发布版本
2. 实现**自研轻量 DAG 执行引擎**（YZH.Core/Workflow），支撑提取/校验/报告三引擎共用
3. 提供**规则测试沙箱**：测试企业数据 + `POST /api/workflow-definition/test` + `POST /api/validation-rule/test`，返回节点级执行日志
4. 设计器**保存/发布分离**：保存草稿走 workflow-definition，规则绑定走 validation-rule，删除接口混用
5. 补齐 **F-02 标签树**：种子数据生成 + `/api/wf-field-label/tree` + NodePropertyForm 树形选择器
6. F-04 补 **status 字段**并接入引擎日志写入
7. 设计**审批人解析器**：审批节点运行时按机构/角色/任务上下文解析审批人并生成待办
8. 规则支持**版本与灰度**：复制→测试→发布生效，发布前不影响线上

## 四、业务规则

### 4.1 工作流定义规则

| 规则 | 说明 |
|------|------|
| R1 | 工作流类型：`extraction`（提取）/ `validation`（校验）/ `report`（报告），由 workflow_type 约束 |
| R2 | **版本化**：同 `workflow_code` 允许多版本行，version 从 1 递增；唯一约束 `(workflow_code, version)` |
| R3 | 工作流状态机：`draft`（草稿）→ `published`（已发布）→ `archived`（已归档）；仅 published 可被规则绑定；archived 不可再被新规则绑定 |
| R4 | 发布动作：将当前 draft 行的 workflow_config 固化为新版本行（version+1，status=published），原 published 行自动转历史（可回滚为 draft） |
| R5 | 规则引用的是 workflow_code + 版本号（快照语义：绑定后不受新发布影响，除非规则侧显式升级） |
| R6 | `IsActive=true` 且 status=published 的工作流才可被规则下拉选择 |
| R7 | 删除限制：有规则引用（含历史版本）时拒绝物理删除；支持软删除（enable=false）与归档 |

### 4.2 NC 检查规则规则

| 规则 | 说明 |
|------|------|
| R8 | 一条规则必须绑定一个已发布工作流（workflow_code 非空，且 status=published） |
| R9 | 规则按 机构→标准→阶段→条款 四级维度组织（org_code/standard_code/phase_code/clause_code） |
| R10 | 同一 机构+标准+阶段+条款 组合下不允许重复规则编码（uk_rule_code + 业务校验） |
| R11 | 复制规则：workflow_code 自动复制为新草稿，需单独编辑并测试后发布 |
| R12 | 规则删除前检查是否有审核任务（cert_audit_task 或 NC 记录）引用该规则，有则拒绝或标记停用 |
| R13 | 规则启停（toggle-active）：停用后新审核任务不再调度该规则；进行中任务不受影响 |

### 4.3 规则版本与测试规则

| 规则 | 说明 |
|------|------|
| R14 | 规则同样采用版本化：`cert_validation_rule` 主行 + `cert_validation_rule_version` 历史快照（rule_json + workflow 引用 + 生效范围） |
| R15 | 规则发布流程：新建/复制 → 草稿 → 测试（沙箱）→ 发布（生成新版本行）→ 生效；未测试通过不得发布 |
| R16 | 测试运行注入测试企业 `enterprise_code='YZH-STD-ENT'`（或用户指定企业），不产生真实 NC/审批副作用（测试标记 `is_test=true`） |
| R17 | 测试结果以节点级日志返回（nodeResults），节点失败不中断整体返回（hasError=true） |

### 4.4 工作流设计器规则

| 规则 | 说明 |
|------|------|
| R18 | 节点按四类划分：输入（get_field/get_table/get_file_list/get_nc_list）、确定性计算（compare/date_diff/set_contains/count/check_not_empty）、AI（llm_judge/llm_generate）、输出（create_nc/assemble_text/save_result/save_section）；另有**审批节点**（approval，V2 新增） |
| R19 | 连线合法性实时校验：上游 `output_schema` 的 `sourceHandle` 端口必须存在于下游 `input_schema` 的 `targetHandle`，类型兼容；非法连线在画布上直接拦截 |
| R20 | DAG 必须无环（拓扑排序失败即提示，保存/发布前置校验） |
| R21 | 保存/发布前必须通过结构校验：DAG 合法 + Skill 存在且启用（F-01 is_active + 注册表存在）+ 末端含输出节点（create_nc/save_result/save_section）或显式 output_config |
| R22 | 条件分支边（branches）仅允许出现在判断类节点（compare/llm_judge 等有布尔/枚举输出的节点）之后；每条分支边必须声明 `condition` |
| R23 | 同一节点输入端口不可重复连接多条数据流（一对一）；输出端口可扇出（一对多） |
| R24 | 设计器保存草稿不校验版本冲突；发布时若线上已被规则绑定，提示"将产生新版本，已绑定规则不受影响" |

### 4.5 审批人解析规则（V2 新增）

| 规则 | 说明 |
|------|------|
| R25 | 审批节点（approval）配置 `approver_rule`：`task_assignee`（任务指定人）/ `role`（按角色）/ `org_auditor`（机构默认审核员）/ `expression`（表达式：角色+机构+标准组合）；多配置时按优先级取首个命中 |
| R26 | 解析优先级：审核任务显式指定审批人 > 规则/流程配置的审批人表达式 > 机构默认审核员 > 角色兜底（系统管理员） |
| R27 | 审批人解析结果为 userId 列表，生成待办（cert_approval_task）；审批动作：通过/驳回（驳回附原因，可退回指定节点） |
| R28 | 审批节点不改变 DAG 主数据流：主链路继续执行（如先创建 NC 再审批），审批结果写回 F-04 日志与审批任务表 |

#### F-04 wf_workflow_execution_log（执行日志）

| 用途 | 工作流实例执行留痕：实例级 + 节点级 |

| 关键字段 | `workflow_code`、`workflow_version`、`business_type`、`business_id`、`node_id`、`skill_code`、`input_data`（JSON）、`output_data`（JSON）、`error_msg`、`duration_ms`、`started_at`、`completed_at`、**`status`（V2 新增：pending/running/success/failed/skipped）** |

| 现状 | 表已建但无 status 字段、无写入方 |
| 外键 | `workflow_code → wf_workflow_definition(workflow_code)` |

## 七、数据流 / 时序

### 7.1 规则绑定工作流（配置期）

```
管理员 → 工作流定义页：保存草稿 → 发布（version+1, published）
      → 规则页：新建/编辑规则 → 选择已发布工作流（下拉只列 published）→ 保存规则草稿
      → 规则测试沙箱：POST /api/validation-rule/test（引擎执行，返回 nodeResults）
      → 测试通过 → POST /api/validation-rule/publish → 规则生效（生成版本行）
```

### 7.2 工作流发布时序

```
Designer.vue
  └─ 点击[发布]
      ├─ 前端：compileToWorkflowConfig（剔除 UI 字段，生成发布态 JSON）
      ├─ 前端：结构校验（环检测 + Skill 存在 + 末端输出）
      ├─ POST /api/workflow-definition/publish
      │     ├─ WorkflowDefinitionService.ValidateAsync（拓扑排序 + 端口契约校验）
      │     ├─ 事务：旧 published 行保留（历史）；新增 version+1 published 行
      │     └─ 返回新版本号
      └─ UI：显示版本历史，规则绑定仍指向旧版本（快照语义）
```

### 7.3 审核执行时序（引擎运行）

```
审核员触发"执行审核"（audit task）
  └─ 加载规则集（org+standard+phase 匹配、is_active=true）
      ├─ 逐条：取规则绑定的 workflow_code + workflow_version
      ├─ 加载发布态 workflow_config
      ├─ WorkflowEngine.RunAsync(config, context)
      │     ├─ 1. TopoSort（Kahn，检测环 → 失败中止）
      │     ├─ 2. 构建节点执行计划（含 branches 条件边）
      │     ├─ 3. 逐节点：ResolveInputs（{{nX.port}} 替换）→ ISkillRegistry 取执行器 → ExecuteAsync
      │     ├─ 4. 每节点结果写 F-04 日志（status/duration/input/output/error）
      │     ├─ 5. 条件分支：判断节点按 branches condition 决定后继
      │     └─ 6. 汇总 WorkflowRunResult（success/failed/skipped）
      ├─ 输出节点 create_nc → 写 B-07 不符合项（is_test=false）
      ├─ 审批节点 → ApproverResolver.ResolveAsync(context, approverRule)
      │     ├─ 优先级：任务指定人 → 表达式 → 机构审核员 → 角色兜底
      │     └─ 生成 cert_approval_task（pending）→ 审批人待办
      └─ 整条规则执行结果回写规则执行记录
```

### 7.4 审批时序

```
审批人 → 待办列表 → 打开审批任务
  ├─ 通过：status=approved → 业务回调（如 NC 确认/关闭）
  └─ 驳回：status=rejected（comment 必填）→ 业务回调（NC 退回/重新生成）
       └─ 可选：按配置退回指定 DAG 节点重新执行（[TODO:P2]）
```

## 八、边界与异常处理

### 8.1 数据缺失行为

| 场景 | 行为 |
|------|------|
| 测试运行 B-08 无数据 | `get_field` 返回"未找到"，nodeResults 该节点 failed；提示"请先通过 DocExtractionRule 保存提取规则或注入测试企业数据" |
| 规则列表左侧树无规则 | 树仍从参考表加载机构/标准/阶段，规则数为 0 |
| F-02 无种子数据 | 标签树接口返回空；设计器提示"标签映射未初始化，请执行种子生成任务" |
| 新建规则时无已发布工作流 | 下拉为空并提示"请先创建工作流并发布" |

### 8.2 删除与版本限制

- 工作流：仅 draft 可删除；published 需先归档；有规则引用（任意版本）拒绝物理删除
- 规则：仅 draft/archived 可删除；有审核任务/NC 引用时拒绝或标记停用
- 规则版本与工作流版本为**快照关系**：规则发布时固化 workflow_version，工作流后续发布不自动影响已发布规则

### 8.3 并发与事务

- 工作流发布使用数据库事务：校验 + 新增版本行原子提交；并发发布同 code 时依赖 `uk_wf_code_version` 唯一约束，冲突返回 409 重试
- 规则发布同样依赖 `uk_rule_ver` 保证版本唯一
- 引擎执行日志写入失败不阻断主流程（try-catch，降级为内存日志 + 告警）

### 8.4 引擎异常

| 异常 | 处理 |
|------|------|
| 拓扑排序失败（环） | 配置期已拦截；运行期兜底：中止并返回 422 |
| Skill 执行器缺失 | 节点 failed，error=`Skill {code} 未注册`；继续执行其他节点 |
| AI 节点超时 | 按 Skill endpoint_config 超时配置（默认 60s）；超时按 failed 处理，可配置重试 1 次 |
| 输出节点写库失败 | 记录 error + 回滚该节点副作用（无补偿时标记 [TODO:P1]） |

### 8.5 审批解析失败

- 所有解析规则均未命中：回退系统管理员角色；仍失败则该审批节点 failed，审批任务不生成，错误写入 F-04

### 8.6 测试隔离

- 测试运行（is_test=true）不产生真实 NC、不生成审批任务、不触发外部副作用（写 B-07 前检查 context.IsTest）
