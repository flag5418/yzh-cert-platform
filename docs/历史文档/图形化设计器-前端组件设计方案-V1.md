## 〇、背景与驱动因素

### 0.1 用户提出的核心要求

| # | 要求 | 原文摘要 |
|---|------|---------|
| 1 | **不操作数据库** | "我们在布局的时候，是不能去操作数据库的" |
| 2 | **同一节点可多次放置** | "我们可能同一个节点，需要多次放置到画布中，每个放置到画布上的节点，必须有一个固定的编号" |
| 3 | **前端建立合理的数据结构** | "我们必须要在前端建立合理的结构，存储当前节点、节点配置、连线等相关所有信息" |
| 4 | **保存前可调用解释器验证** | "后续我们在没进行保存前，需要调用解释器，通过真实数据进行验证" |
| 5 | **详细操作日志** | "我需要非常详细的操作日志，我进行节点操作，或节点画布操作的时候，这些必要的方法现在就得有，否则没办法触发前端数据的缓存和变更" |
| 6 | **项目级复用组件** | "这个工作流引擎，后续我们的报告配置也需要使用，应该形成一个项目级的组件，进行复用" |
| 7 | **合理代码拆分** | "该组件估计逻辑非常复杂，应该合理的代码进行规划，该组件应该是一个文件夹，对当前组件进行合理的拆分，不能将所有逻辑全部在一个页面完成" |
| 8 | **节点命名、连线结构等必要信息需要保存** | "我们不用着急一次性的先解决所有的问题，但节点命名、连线结构等必要信息需要保存" |

### 0.2 当前实现的问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | 所有逻辑堆在 `NCConfig/index.vue`（624 行） | 树管理、画布初始化、节点增删改、保存、布局全在一个文件，无法复用 |
| 2 | 节点 ID 用 `n${Date.now()}` | 不可预测、不可读、不便于调试和端口引用 |
| 3 | 无前端状态管理 | 每次操作直接读写 LogicFlow 的 `getGraphData()`，没有独立的响应式状态层，无法在保存前做试运行 |
| 4 | 连线无端口信息 | 用户连线后 `edge.properties` 为空对象，`sourceHandle`/`targetHandle` 全是 undefined，解释器无法知道数据流方向 |
| 5 | 缺少边事件监听 | 只监听了 `edge:click`（且只是清空选中），没有 `edge:add`/`edge:delete` 事件，连线创建/删除无法被感知 |
| 6 | 操作日志完全缺失 | 没有 `console.log`，没有操作历史，无法追踪"做了什么" |
| 7 | `WorkflowDesigner.vue` 是死代码 | 使用 LogicFlow 1.x API（`Diagram`/`HtmlPlugin`/`behavior`/`require`），NCConfig 已绕过它直接用 LogicFlow 2.x |
| 8 | `NodePropertyForm` 变量引用语法不一致 | placeholder 显示 `{{n1.fieldValue}}`（双大括号），V4 §5.5 要求 `n1.fieldValue`（无大括号） |
| 9 | 无法复用 | NCConfig 的画布+节点库+属性面板代码无法被 ReportDefinition 复用 |

### 0.3 V4 设计文档的约束

| # | V4 约束 | 本设计如何遵守 |
|---|--------|--------------|
| 1 | JSON 键名统一 camelCase（§5.5） | 所有前端状态和导出 JSON 使用 camelCase |
| 2 | 边模型：`{ source, target, sourceHandle?, targetHandle? }`（§5.5） | 前端 Edge 结构对齐 |
| 3 | 节点 inputs 端口语义：`nX.portName` 引用上游，`ctx.field` 引用上下文（§5.5 缺陷 G） | NodePropertyForm 引用语法对齐 |
| 4 | 画布布局不入 JSON，重新打开自动布局（§7.2 / §0.2 #6） | `exportConfig()` 不含布局；`exportLayout()` 独立导出（保留但可选） |
| 5 | 保存前必须运行验证（§7.2） | `WorkflowDesigner` emit `run` 事件，由页面调后端试运行 API |
| 6 | 保存 = 更新业务行内联 JSON（§7.2） | `emit('save', config, layout)` → 页面 POST 到业务 API |
| 7 | 图形化界面复用 LogicFlow/compiler.js 资产（§7.2） | 保留 compiler.js，重构为 composable 调用 |

## 一、组件定位与复用策略

### 1.1 定位

`WorkflowDesigner` 是**项目级前端组件**，不是框架级组件（不进 `yzh/`），而是认证业务域组件（进 `components/workflow-designer/`）。

定位边界：
- **组件负责**：画布渲染、节点增删改、连线增删改、端口管理、操作日志、自动布局、状态管理、JSON 编译/反编译
- **组件不负责**：左栏业务树（NC 规则树 / 报告章节树）、后端 API 调用、业务校验逻辑
- **页面负责**：左栏树、选中规则/章节后加载已有配置、保存时调后端 API、试运行时调后端 run API

### 1.2 复用场景

| 场景 | 页面 | 左栏（页面自建） | 中右栏（复用组件） | workflowType |
|------|------|----------------|-------------------|-------------|
| NC 规则配置 | `NCConfig/index.vue` | 机构→标准→阶段→NC检查项 | WorkflowDesigner | `validation` |
| 报告内容配置 | `ReportDefinition.vue` | 机构→标准→阶段→报告章节 | WorkflowDesigner | `report` |

### 1.3 页面与组件的交互契约

## 四、Composable 详细设计

### 4.1 useWorkflowState.js — 核心状态管理

**职责**：前端唯一的状态真相源（single source of truth），所有节点/边的增删改查都经过这里。

```js
export function useWorkflowState() {
  // ===== 响应式状态 =====
  const nodes = reactive(new Map())       // Map<nodeId, WorkflowNode>
  const edges = reactive(new Map())       // Map<edgeId, WorkflowEdge>
  const selectedNodeId = ref(null)
  const selectedEdgeId = ref(null)
  const isDirty = ref(false)
  const nodeCounter = ref(0)
  const edgeCounter = ref(0)

  // ===== 节点操作 =====
  function addNode(node) { ... }          // 写入 nodes Map + markDirty + log
  function deleteNode(nodeId) { ... }      // 删除节点 + 关联边 + markDirty + log
  function updateNode(nodeId, partial) { ... }  // 部分更新 + markDirty + log
  function getNode(nodeId) { ... }        // 读取
  function moveNode(nodeId, x, y) { ... } // 更新坐标（不 markDirty，布局不入 JSON）

  // ===== 边操作 =====
  function addEdge(edge) { ... }          // 写入 edges Map + markDirty + log
  function deleteEdge(edgeId) { ... }     // 删除 + markDirty + log
  function updateEdge(edgeId, partial) { ... } // 更新端口 + markDirty + log
  function getEdge(edgeId) { ... }

  // ===== 选中 =====
  function selectNode(nodeId) { ... }     // selectedNodeId = nodeId, selectedEdgeId = null + log
  function selectEdge(edgeId) { ... }    // selectedEdgeId = edgeId, selectedNodeId = null + log
  function deselect() { ... }             // 清空选中 + log

  // ===== 批量操作 =====
  function clearAll() { ... }             // 清空 nodes + edges + 重置编号器 + log
  function loadFromConfig(config, layout) { ... }  // 从 JSON 反编译加载 + 重置编号器 + log

  // ===== 导出 =====
  function exportConfig(workflowType) { ... }  // 编译为 workflow_config JSON
  function exportLayout() { ... }             // 导出布局 JSON

  // ===== 查询 =====
  function getStats() { ... }              // { nodeCount, edgeCount, isDirty }
  function getSelectedNode() { ... }      // 当前选中的节点对象
  function getSelectedEdge() { ... }      // 当前选中的边对象
  function getNextNodeId() { ... }         // n${nodeCounter + 1}（不递增）
  function getNextEdgeId() { ... }         // e${edgeCounter + 1}（不递增）

  // ===== 脏标记 =====
  function markDirty() { isDirty.value = true }
  function markClean() { isDirty.value = false }

  return { /* all of the above */ }
}
```

**节点编号规则**：
- 首次放置：`n1`、`n2`、`n3`...（`++nodeCounter`）
- 删除 `n2` 后再加新节点：继续 `n4`（不复用已删除编号，避免引用混乱）
- 从 JSON 加载时：`nodeCounter` 重置为已有节点编号中的最大序号（如已有 `n1/n3/n5`，则 `nodeCounter = 5`，下一个新节点是 `n6`）
- 边编号同理：`e1`、`e2`、`e3`...

### 4.2 useLogicFlow.js — LogicFlow 实例 + 事件

**职责**：封装 LogicFlow 2.x 的实例管理和事件监听，将 LogicFlow 的画布操作转换为 useWorkflowState 的状态变更。

```js
export function useLogicFlow(state, nodeFactory, edgeManager, log) {
  const lf = shallowRef(null)
  const canvasRef = ref(null)

  // ===== 初始化/销毁 =====
  function init(canvasEl, options) { ... }    // new LogicFlow + bindEvents
  function destroy() { ... }                   // clearData + 释放引用

  // ===== 渲染 =====
  function render(graphData) { ... }           // lf.render()
  function getGraphData() { ... }             // lf.getGraphData()
  function clearCanvas() { ... }              // lf.render({ nodes: [], edges: [] })

  function bindEvents() {
    lf.value.on('node:click', ({ data }) => {
      state.selectNode(data.id)
    })

    lf.value.on('edge:click', ({ data }) => {
      state.selectEdge(data.id)
    })

    lf.value.on('blank:click', () => {
      state.deselect()
    })

    // 节点拖拽移动
    lf.value.on('node:drop', ({ data }) => {
      state.moveNode(data.id, data.x, data.y)
      // 注意：移动不 markDirty（布局不入 JSON），但记录操作日志
    })

    // 连线创建（拦截）
    lf.value.on('edge:add', ({ data }) => {
      // LogicFlow 创建边后，写入前端状态
      // 如果端点尚未配置，边会标记为"待配置端口"
      const edge = edgeManager.createEdge(
        data.sourceNodeId,
        data.targetNodeId,
        data.properties?.sourceHandle,
        data.properties?.targetHandle
      )
      // 同步更新 LogicFlow 上的边 ID 为我们的编号 e1/e2...
      // 并触发右侧 EdgePropertyForm
    })

    // 连线删除
    lf.value.on('edge:delete', ({ data }) => {
      state.deleteEdge(data.id)
    })

    // 节点删除（连带边）
    lf.value.on('node:delete', ({ data }) => {
      state.deleteNode(data.id)
    })
  }

  // ===== 坐标转换 =====
  function clientToCanvas(clientX, clientY) { ... }  // getPointByClient 封装

  // ===== 画布操作 =====
  function addNodeToCanvas(nodeData) { ... }  // lf.addNode()
  function deleteNodeFromCanvas(nodeId) { ... } // lf.deleteNode()
  function updateNodeText(nodeId, text) { ... }  // lf.updateText()
  function updateNodeProperties(nodeId, props) { ... }  // lf.setProperties()
  function focusNode(nodeId) { ... }          // 定位到节点

```

**关键设计：LogicFlow 事件 → 状态同步**

LogicFlow 的 `edge:add` 事件触发时，边已经画到画布上了。我们的处理是：
1. 从事件中拿到 `sourceNodeId` / `targetNodeId`
2. 调 `edgeManager.createEdge()` 在前端状态中创建边记录（编号 `e1`）
3. 用 `lf.setProperties(edgeId, { edgeId: 'e1' })` 把我们的编号写回 LogicFlow 的边 properties 中
4. 如果是 logic 节点的边，自动设置 `sourceHandle` 为 `success` / `failure`
5. 如果是普通 skill 节点的边，`sourceHandle` / `targetHandle` 留空，标记 `portConfigured: false`
6. 右侧面板自动切换为 `EdgePropertyForm`，引导用户选择端口

### 4.3 useNodeFactory.js — 节点创建

export function useNodeFactory(state, skills) {

    }
  }

  function defaultNodeData(item) {
    // start / end / logic 的默认数据
    if (item.nodeType === 'start') { ... }
    if (item.nodeType === 'end') { ... }
    if (item.nodeType === 'logic') { ... }
    // skill 的默认数据：从 skills 元数据生成 inputs 默认值
    const meta = skills.value.find(s => s.skillCode === item.skillCode)
    const inputs = {}
    for (const input of meta?.inputs || []) {
      if (input.defaultValue) inputs[input.inputName] = input.defaultValue
    }
    return { nodeType: 'skill', title: ..., skillCode: ..., inputs, ... }
  }

  function lfTypeOf(nodeType) { ... }    // start/end → circle, logic → diamond, skill → rect
  function styleOf(nodeType, skillCode, category) { ... }  // 配色（从 compiler.js 迁移）

  // 从 JSON 加载时重置编号器
  function resetCounterFromNodes(nodeIds) {
    const maxNum = nodeIds
      .map(id => parseInt(id.replace('n', ''), 10))
      .filter(n => !isNaN(n))
      .reduce((max, n) => Math.max(max, n), 0)
    state.nodeCounter = maxNum
  }

### 4.4 useEdgeManager.js — 连线管理

**职责**：边的创建、编号、端口管理、校验、样式。

```js
export function useEdgeManager(state, skills) {

  function nextEdgeId() {
    return `e${++state.edgeCounter}`
  }

  function createEdge(sourceId, targetId, sourceHandle, targetHandle) {
    const edgeId = nextEdgeId()

    // 校验
    const validation = validateEdge(sourceId, targetId)
    if (!validation.valid) {
      return { error: validation.message }
    }

    // 判断是否为逻辑分支
    const sourceNode = state.getNode(sourceId)
    const isLogicBranch = sourceNode?.nodeType === 'logic'

    // 如果是 logic 节点，自动分配 success/failure
    let finalSourceHandle = sourceHandle
    if (isLogicBranch && !finalSourceHandle) {
      // 查看该 source 已有多少边，第一条 success，第二条 failure
      const existingEdges = [...state.edges.values()].filter(e => e.source === sourceId)
      finalSourceHandle = existingEdges.length === 0 ? 'success' : 'failure'
    }

    const edge = {
      edgeId,
      source: sourceId,
      target: targetId,
      sourceHandle: finalSourceHandle || '',
      targetHandle: targetHandle || '',
      label: getEdgeLabel(isLogicBranch, finalSourceHandle),
      style: getEdgeStyle(isLogicBranch, finalSourceHandle),
      _meta: {
        isLogicBranch,
        portConfigured: !!(finalSourceHandle && targetHandle)
      }
    }

    state.addEdge(edge)
    return { edge }
  }

  function validateEdge(sourceId, targetId) {
    // 1. 禁止自连
    if (sourceId === targetId) return { valid: false, message: '禁止连接到自身' }
    // 2. 禁止重复（相同 source+target+sourceHandle 组合）
    const exists = [...state.edges.values()].some(e =>
      e.source === sourceId && e.target === targetId &&
      e.sourceHandle === (sourceHandle || '')
    )
    if (exists) return { valid: false, message: '该连线已存在' }
    // 3. logic 节点最多 2 条出边（success + failure）
    const sourceNode = state.getNode(sourceId)
    if (sourceNode?.nodeType === 'logic') {
      const outEdges = [...state.edges.values()].filter(e => e.source === sourceId)
      if (outEdges.length >= 2) return { valid: false, message: '逻辑判断节点最多 2 条出边' }
    }
    return { valid: true }
  }

  function updateEdgePort(edgeId, sourceHandle, targetHandle) {
    state.updateEdge(edgeId, { sourceHandle, targetHandle })
    // 更新边样式和标签
  }

  function availableOutputPorts(nodeId) {
    const node = state.getNode(nodeId)
    if (!node) return []
    // start 节点无输出端口概念，但可以有出边
    if (node.nodeType === 'start') return [{ name: 'start', type: 'signal' }]
    // logic 节点：success / failure
    if (node.nodeType === 'logic') return [
      { name: 'success', type: 'boolean', label: '成功' },
      { name: 'failure', type: 'boolean', label: '失败' }
    ]
    // skill 节点：从 Skill 元数据 outputs 声明
    const meta = skills.value.find(s => s.skillCode === node.skillCode)
    return meta?.outputs || Object.keys(node.outputs || {}).map(k => ({ name: k, type: node.outputs[k] }))
  }

  function availableInputPorts(nodeId) {
    const node = state.getNode(nodeId)
    if (!node) return []
    // end 节点无输入端口概念
    if (node.nodeType === 'end') return [{ name: 'end', type: 'signal' }]
    // skill 节点：从 Skill 元数据 inputs 声明
    const meta = skills.value.find(s => s.skillCode === node.skillCode)
    return meta?.inputs || Object.keys(node.inputs || {}).map(k => ({ name: k }))
  }

  function getEdgeLabel(isLogicBranch, sourceHandle) { ... }
  function getEdgeStyle(isLogicBranch, sourceHandle) { ... }

  return { createEdge, validateEdge, updateEdgePort,
           availableOutputPorts, availableInputPorts,
           getEdgeLabel, getEdgeStyle }
}
```

    logs.value.push({
      seq: ++seq,
      timestamp: Date.now(),
      action,
      target,
      details
    })
    // console 输出（带颜色区分）
    const colors = {
      add_node: '#67C23A', delete_node: '#F56C6C', update_node: '#E6A23C',

      load_workflow: '#409EFF'
    }
    console.log(
      `%c[WF-Log #${seq}] ${action} → ${target || '(canvas)'}`,
      `color: ${colors[action] || '#303133'}; font-weight: bold;`,
      details
    )
  }

  function getLog() { return logs.value }
  function clearLog() { logs.value = []; seq = 0 }

      `[${new Date(l.timestamp).toLocaleTimeString()}] #${l.seq} ${l.action} → ${l.target || '(canvas)'}`

  }

  return { log, getLog, clearLog, formatLog }
}

## 八、连线端口交互设计

### 8.1 当前问题

当前实现中，用户连线后：
1. `edge.properties` 为空对象 `{}`
2. `sourceHandle` / `targetHandle` 均为 `undefined`
3. 解释器无法知道数据从源节点的哪个输出端口流到目标节点的哪个输入端口

### 8.2 设计方案：先连线，后选端口（方案 C）

**流程**：

```
1. 用户从节点 A 的右侧锚点拖拽到节点 B 的左侧锚点
   → LogicFlow 自动创建边
   → edge:add 事件触发

2. useLogicFlow 拦截 edge:add：
   → edgeManager.createEdge(A.id, B.id, null, null)
   → 边创建后 sourceHandle=null, targetHandle=null
   → 边标记 _meta.portConfigured = false
   → 边样式改为 EDGE_STYLES.pending（橙色虚线，提示"待配置"）
   → 自动选中该边 → 右侧面板切换为 EdgePropertyForm

3. 用户在 EdgePropertyForm 中：
   → 选择"源端口"（下拉列表来自 availableOutputPorts(A.id)）
   → 选择"目标端口"（下拉列表来自 availableInputPorts(B.id)）
   → 每次选择触发 handleEdgeUpdate → state.updateEdge + lf.updateEdgeProperties

4. 两端端口都选完后：
   → 边样式恢复正常（EDGE_STYLES.normal）
   → _meta.portConfigured = true
```

### 8.3 逻辑判断节点特殊处理

逻辑判断（logic）节点的出边端口自动分配：
- 第 1 条出边 → `sourceHandle = 'success'`（绿色实线）
- 第 2 条出边 → `sourceHandle = 'failure'`（红色实线）
- 不允许第 3 条出边（`validateEdge` 拦截）

### 8.4 端口列表来源

| 节点类型 | 输出端口 | 输入端口 |
|---------|---------|---------|
| `start` | `[{ name: 'start', type: 'signal' }]` | 无 |
| `end` | 无 | `[{ name: 'end', type: 'signal' }]` |
| `logic` | `[{ name: 'success', label: '成功' }, { name: 'failure', label: '失败' }]` | 从 Skill 元数据 |
| `skill` | 从 Skill 元数据 `outputs` 声明 | 从 Skill 元数据 `inputs` 声明 |

## 九、操作日志详细设计

### 9.1 为什么需要操作日志

用户原话："我需要非常详细的操作日志，我进行节点操作，或节点画布操作的时候，这些必要的方法现在就得有，否则没办法触发前端数据的缓存和变更。"

操作日志的核心价值：
1. **调试**：开发阶段追踪状态变更链路，快速定位"为什么数据不对"
2. **状态追踪**：确认每个操作都正确触发了前端状态更新
3. **用户行为分析**：后续可扩展为操作历史（undo/redo 基础）
4. **保存前审查**：保存前检查是否有未完成的操作（如边端口未配置）

### 9.2 日志触发点

| 操作 | 触发位置 | action | log details |
|------|---------|--------|-------------|
| 从面板添加节点 | SkillPanel → click/dragend | `add_node` | `{ nodeType, skillCode?, x, y }` |
| 选中节点 | LF → node:click | `select_node` | `{}` |
| 选中边 | LF → edge:click | `select_edge` | `{}` |
| 取消选中 | LF → blank:click | `deselect` | `{}` |
| 移动节点 | LF → node:drop | `move_node` | `{ fromX, fromY, toX, toY }` |
| 删除节点（键盘 Delete） | LF → node:delete | `delete_node` | `{ title, connectedEdges: [...] }` |
| 删除边（键盘 Delete） | LF → edge:delete | `delete_edge` | `{ source, target, sourceHandle, targetHandle }` |
| 创建连线 | LF → edge:add | `add_edge` | `{ source, target }` |

| 修改节点 inputs | PropertyForm → update | `update_node` | `{ field: 'inputs.<key>', old, new }` |

## 十三、风险与对策

| # | 风险 | 影响 | 对策 |
|---|------|------|------|
| 1 | LogicFlow 2.x `edge:add` 事件可能在某些场景不触发 | 连线无法被前端状态感知 | 监听 `connection` 事件作为备选 |
| 2 | `reactive(Map)` 在 Vue 3 中的响应式追踪可能有边界 case | 某些批量操作后 UI 不更新 | 使用 `shallowReactive` + 手动触发 `triggerRef` |
| 3 | Skill 元数据未就绪时创建节点，inputs/outputs 为空 | 节点端口下拉列表为空 | SkillPanel 在 skills 加载完成前禁用拖拽 |
| 4 | 画布在 keep-alive 切换后 DOM 引用失效 | `parentNode null` 错误 | onUnmounted 中正确销毁 LogicFlow 实例 |
| 5 | 大量节点（50+）时性能下降 | 画布卡顿 | LogicFlow 自身支持虚拟渲染；限制单工作流节点数 |

## 十四、与 V4 设计文档的差异说明

| # | V4 原文 | 本设计 | 差异原因 |

## 十六、总结

本设计方案的核心设计决策：

1. **组件化**：WorkflowDesigner 作为项目级复用组件，3 栏布局（节点库 + 画布 + 属性面板）
2. **状态管理**：useWorkflowState 作为唯一状态真相源，LogicFlow 仅负责渲染和事件
3. **编号体系**：节点 `n1/n2/n3...`，边 `e1/e2/e3...`，删除不复用，加载时重置为最大值
4. **连线端口**：先连线后选端口（方案 C），逻辑节点自动分配 success/failure
5. **操作日志**：13 种 action 类型，Console 带颜色输出，结构化存储可扩展
6. **数据分离**：config JSON（业务）与 layout JSON（布局）独立导出
7. **代码拆分**：12 个文件，逻辑层 5 个 composable + 视图层 4 个组件 + 2 个支撑文件
8. **页面解耦**：组件不碰数据库，不碰业务树，只管画布和状态；页面负责树和 API

- D3: 左栏是否进组件
- D4: 操作日志用途`
