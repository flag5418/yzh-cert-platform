# 多租户体系认证平台——组织与权限架构设计（V2）

> **版本**：V2.0 | **日期**：2026-09-08 | **状态**：修订版
>
> **修订说明**：基于 V1.0 讨论，采用更简洁的设计思路——**统一组织树 + 扩展附件表**，避免两层组织带来的复杂性。
>
> **核心决策**：
> 1. 组织模型保持简单：一棵树 + 普通人员表 + attach 扩展表
> 2. 树结构预初始化：系统管理员组 → 体系认证机构 → 虚拟机构
> 3. 业务复杂性后置：具体权限控制在业务控制器中实现
> 4. 与现有 TreeTable 架构完全兼容

---

## 一、设计思路对比

### 1.1 V1 方案（已废弃）

```
两层组织模型：
├─ 真实组织：认证机构（CB）
└─ 虚拟组织：CB 下的审核团队（独立树结构）

问题：
- 两套树结构，维护复杂
- 人员需要在两张关联表中维护
- 权限逻辑分散在两处
```

### 1.2 V2 方案（采用）

```
统一组织树模型：
├─ 🏢 系统管理组（预初始化根节点）
│   ├─ 👥 系统管理员组
│   ├─ 👥 维护人员组
│   └─ 👥 审核人员组
│
├─ 🏭 体系认证机构（真实机构，可多组织）
│   ├─ 🏢 ACM认证有限公司
│   │   ├─ 👤 机构管理员
│   │   └─ 📁 虚拟机构-A
│   │       ├─ 👤 审核组长
│   │       ├─ 👤 审核员
│   │       └─ 👤 企业用户
│   └─ 📁 虚拟机构-B
│       └─ ...
│
└─ 🌐 虚拟机构（审核员注册形成的组织）
    └─ （已挂载到对应认证机构下）
```

**核心原则**：
- **组织树是普通的左树右表**：用现有 `TreeTableControllerBase<T, V>` 实现
- **人员是普通用户表**：在 `sys_user` 基础上新增 `user_type` 字段
- **特殊信息用 attach 表**：不污染主表，按需扩展
- **业务权限后置**：体系认证相关的权限控制在业务控制器中实现

```sql
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,

    name        VARCHAR(100) NOT NULL COMMENT '部门名称',
    parent_code VARCHAR(36) COMMENT '父部门编码',

    sort_order  INT DEFAULT 0,
    enable      TINYINT(1) DEFAULT 1,
    remark      TEXT,
    create_id   INT,
    creator     VARCHAR(50),
    create_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    modify_id   INT,
    modifier    VARCHAR(50),
    modify_date DATETIME,
    delete_id   INT,
    deleter     VARCHAR(50),
    delete_time DATETIME,
    FOREIGN KEY (parent_code) REFERENCES org_department(code),
    INDEX idx_org_parent (parent_code),
    INDEX idx_org_type (dept_type)
```

### 4.1 角色定义

| 角色 | user_type | login_portal | 数据范围 | 核心权限 |
|------|-----------|--------------|---------|---------|
| 系统管理员 | super_admin | admin | 全局 | 全部 |
| 维护人员 | maintainer | admin | 按配置范围 | 编辑配置草稿 |
| CB管理员 | auditor | cb | 本CB所有数据 | 虚拟机构管理、任务分配 |
| 审核组长 | team_lead | auditor | 本虚拟机构 | 人员管理、任务建议 |

| 企业用户 | enterprise_user | enterprise | 本企业 | 查看进度、提交整改 |

### 5.1 组织管理页面（左树右表）

**后端控制器**：

```csharp
[Route("api/org")]
public class OrgController : TreeTableControllerBase<OrgDepartment, SysUser>
{
    public OrgController(
        EntityService<OrgDepartment> treeService,
        EntityService<SysUser> userService,
        IUserContext userContext) : base(treeService, userService, userContext)
    {
        TreeConfig = new TreeConfig
        {
            CodeField = "Code",
            NameField = "Name",
            ParentCodeField = "ParentCode",
            RelateField = "dept_code",
            RootParentCode = null,
            Lazy = true,
            AllowEdit = true,
            AllowDelete = true,
            AllowRename = true,
            NoSelectionBehavior = "empty"
        };
    }
    
    // 重写：自动注入数据权限
    protected override List<FilterItem> OnBuildingQuery(RequestCondition[]? conditions)
    {
        var user = _userContext.GetCurrent();
        var filters = base.OnBuildingQuery(conditions);
        
        // 非超级管理员只能看本CB的数据
        if (user.UserType != "super_admin" && !string.IsNullOrEmpty(user.CertOrgCode))
        {
            // 获取本CB下的所有部门编码
            var deptCodes = GetDepartmentsUnderCBOrg(user.CertOrgCode);
            filters.Add(new FilterItem 
            { 
                Field = "code", 
                Value = string.Join(",", deptCodes), 
                Operator = "in" 
            });
        }
        
        return filters;
    }
    
    // 辅助方法：获取CB下的所有部门编码
    private List<string> GetDepartmentsUnderCBOrg(string cbCode)
    {
        // 递归查询所有子部门
        var result = new List<string>();
        var cbDept = _treeEntity.FirstOrDefault(d => d.Code == cbCode);
        if (cbDept != null)
        {
            result.Add(cbDept.Code);
            result.AddRange(GetAllChildrenCodes(cbDept.Code));
        }
        return result;
    }
}
```

## 六、业务控制器权限设计

### 6.1 权限中间件（通用）

```csharp
// 通用权限中间件：检查用户是否有访问该API的权限
public class PermissionMiddleware
{
    public async Task<bool> HasPermissionAsync(UserContext user, string apiPath)
    {
        // 1. SuperAdmin 拥有所有权限
        if (user.UserType == "super_admin") return true;
        
        // 2. 根据 API 路径解析所需权限
        var requiredPermission = ResolvePermission(apiPath);
        
        // 3. 检查用户角色权限
        if (!user.HasRolePermission(requiredPermission)) return false;
        
        // 4. 检查数据权限（由业务控制器实现）
        return true;
    }
}
```

#### 6.2.2 配置管理权限

```csharp
[Route("api/config")]
public class ConfigController : YzhControllerBase<ConfigEntity>
{
    public ConfigController(
        EntityService<ConfigEntity> service,
        IUserContext userContext) : base(service, userContext) { }
    
    // 编辑配置
    [HttpPost("edit")]
    public async Task<IActionResult> EditConfig([FromBody] ConfigEditRequest request)
    {
        var user = _userContext.GetCurrent();
        
        // 权限检查：只有维护人员和 CB管理员 可以编辑
        if (user.UserType != "maintainer" && user.UserType != "auditor")
            return Forbid();
        
        // 配置权限检查：维护人员只能编辑有权限范围的配置
        if (user.UserType == "maintainer")
        {
            if (!await HasConfigPermissionAsync(user, request.CbCode, request.StandardCode, request.PhaseCode))
                return Forbid();
        }
        
        // 数据权限：只能编辑草稿状态
        var config = await _service.FindAsync(request.Id);
        if (config?.Status != "draft")
            return BadRequest("只能编辑草稿状态的配置");
        
        // 业务逻辑...
        return Ok();
    }
    
    // 辅助方法：检查配置权限
    private async Task<bool> HasConfigPermissionAsync(UserContext user, string cbCode, string standardCode, string phaseCode)
    {
        var perms = await _configPermissionService.GetPermissionsAsync(user.Code);
        return perms.Any(p => 
            p.CbCode == cbCode && 
            (p.StandardCode == null || p.StandardCode == standardCode) &&
            (p.PhaseCode == null || p.PhaseCode == phaseCode) &&
            p.PermissionType != "readonly");
    }
}
```

## 八、关键设计决策

### 8.1 为什么用 attach 表而不是在主表加字段？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **主表加字段** | 查询简单，无需 JOIN | 字段膨胀，不相关字段混在一起 |
| **attach 表** ✅ | 主表保持简洁，扩展信息按需查询 | 需要 JOIN 查询 |

**决策**：采用 attach 表，因为：
1. 不同角色（审核员/企业用户/维护人员）的扩展信息完全不同
2. 避免主表字段过多导致维护困难
3. 与现有 `sys_user` 表兼容性好

### 8.2 为什么统一组织树而不是两层树？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **两层树** | 真实/虚拟分离清晰 | 维护复杂，关联困难 |
| **统一树** ✅ | 简单直观，符合用户认知 | 需要 dept_type 区分类型 |

**决策**：采用统一树，因为：
1. 用户习惯一棵树管理所有组织
2. 前端实现简单，符合现有 TreeTable 架构
3. 通过 `dept_type` 字段区分不同类型，逻辑清晰

### 8.3 为什么业务权限在控制器层实现？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **框架层统一处理** | 代码简洁 | 复杂业务权限难以表达 |
| **控制器层实现** ✅ | 灵活，可表达复杂业务逻辑 | 代码稍多 |

**决策**：采用控制器层实现，因为：
1. 体系认证业务权限复杂（CB隔离、虚拟机构隔离、配置范围隔离）
2. 框架层中间件适合处理通用权限（登录、角色）
3. 业务控制器可以访问完整的业务上下文

## 九、待确认问题

1. **虚拟机构是否支持多层级？** （本设计支持 parent_code 自引用，但需确认业务需求）
