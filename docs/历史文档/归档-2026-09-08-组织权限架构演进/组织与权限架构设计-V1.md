# 多租户体系认证平台——组织与权限架构设计（V1）

> **版本**：V1.0 | **日期**：2026-09-08 | **状态**：草案，待评审
>
> **前置文档**：
> - 左树右表统一架构设计-V1.md（已有统一 TreeTable 架构）
> - 数据库表设计-V2.md（已有域 A/E 基础表结构）
> - 总体设计-V3.md（企业中心模型）
>
> **核心问题**：
> 1. 体系认证机构具有特殊属性，与普通部门不同
> 2. 存在 3-4 类租户（系统管理员、审核人员、企业、体系认证机构管理人员）
> 3. 配置数据（标准/阶段/规则）需要细粒度权限管控
> 4. 审核人员按机构注册，形成虚拟组织架构
> 5. 不同角色有不同的登录界面、首页、菜单

---

## 一、问题诊断：为什么传统 TreeTable 不够用？

### 1.1 传统组织管理的假设

```
传统方案：
┌─────────────────────────────────────┐
│  一棵树 = 组织架构                   │
│  ├─ 公司                             │
│  │   ├─ 部门A                         │
│  │   └─ 部门B                         │
│  └─ 扁平权限：角色+用户               │
└─────────────────────────────────────┘
```

### 1.2 当前系统的需求复杂性

| 复杂性维度 | 说明 |
|-----------|------|
| **多租户隔离** | 不同 CB 机构的数据严格隔离 |
| **虚拟机构** | 审核员注册在 CB 下，形成虚拟组织，可自建企业用户子组织 |
| **配置权限** | 标准/阶段/规则配置需要按 CB+标准+阶段 三维隔离，且区分"已上线/草稿" |
| **多端多入口** | 系统管理端 / CB管理端 / 审核员端 / 企业端 |
| **审批角色** | 审核组长（每个虚拟机构只有一个）|

### 1.3 关键洞察

**不是"一个组织树"的问题，而是"两层组织"的问题**：
1. **真实组织**：认证机构（CB）—— 机构本身，具有认证资质
2. **虚拟组织**：CB 下的审核团队 —— 由 CB 管理员创建，内部可分层（组长/审核员/企业用户）

这两层组织用同一棵树表达是不合理的。

## 二、核心概念定义

### 2.1 实体定义

| 概念 | 定义 | 对应现有表 |
|------|------|-----------|
| **认证机构（CB）** | 经 CNAS 认可、有资格颁发证书的第三方机构 | `cert_certification_body` |
| **虚拟机构（VirtualOrg）** | CB 下为审核工作划分的虚拟组织单元，可建立企业用户 | 新增表 |
| **审核组长（TeamLead）** | 每个虚拟机构中唯一的组长角色 | 新增字段/表 |
| **审核员（Auditor）** | 在 CB 下注册、可执行审核任务的人员 | `sys_user`（现有）+ 关联 |
| **企业用户（EnterpriseUser）** | 企业端登录账号，隶属于某个虚拟机构 | 新增表 |
| **配置维护员（ConfigMaintainer）** | 仅能维护特定配置（不分配任务）的辅助角色 | 新增角色 |
| **系统管理员（SuperAdmin）** | 平台级超级管理员，可见所有数据 | `sys_user`（现有）|

## 三、数据库设计

### 3.1 新增表清单

#### 新增表 V-01：VirtualOrg（虚拟机构）

```sql
CREATE TABLE vrt_virtual_org (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    code        VARCHAR(36) NOT NULL UNIQUE COMMENT '全局唯一编码（GUID）',
    
    cb_code     VARCHAR(36) NOT NULL COMMENT '所属认证机构编码 → cert_certification_body.code',
    cb_name     VARCHAR(200) COMMENT '冗余机构名称（便于展示）',
    
    name        VARCHAR(100) NOT NULL COMMENT '虚拟机构名称',
    short_name  VARCHAR(50) COMMENT '简称',
    
    parent_code VARCHAR(36) COMMENT '父虚拟机构编码（支持多层级虚拟组织，NULL=根级）',
    
    org_type    ENUM('audit_team', 'enterprise_user_group') DEFAULT 'audit_team' COMMENT '组织类型',
    
    lead_user_code VARCHAR(36) COMMENT '审核组长用户编码 → sys_user.code（每个虚拟机构只能有1个组长）',
    
    status      ENUM('active', 'inactive', 'archived') DEFAULT 'active' COMMENT '状态',
    
    remark      TEXT COMMENT '备注',
    
    create_id   INT COMMENT '创建人ID → sys_user.id',
    creator     VARCHAR(50) COMMENT '创建人姓名',
    create_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    modify_id   INT,
    modifier    VARCHAR(50),
    modify_date DATETIME,
    delete_id   INT,
    deleter     VARCHAR(50),
    delete_time DATETIME,
    
    FOREIGN KEY (cb_code)     REFERENCES cert_certification_body(code),
    FOREIGN KEY (lead_user_code) REFERENCES sys_user(code),
    INDEX idx_vrt_cb (cb_code),
    INDEX idx_vrt_parent (parent_code),
    INDEX idx_vrt_status (status)
) COMMENT '虚拟机构表';
```

#### 新增表 V-02：VirtualOrgUser（虚拟机构人员）

```sql
CREATE TABLE vrt_virtual_org_user (

    status          ENUM('active', 'inactive') DEFAULT 'active',
    
    create_id       INT,
    creator         VARCHAR(50),
    create_date     DATETIME DEFAULT CURRENT_TIMESTAMP,
    modify_id       INT,
    modifier        VARCHAR(50),
    modify_date     DATETIME,
```

#### 新增表 C-07：ConfigPermission（配置权限）

> **解决核心需求**：一个配置维护员只能管理特定 CB + 标准 + 阶段的配置

```sql
CREATE TABLE cfg_config_permission (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
    code            VARCHAR(36) NOT NULL UNIQUE,
    
    -- 权限绑定
    user_code       VARCHAR(36) NOT NULL COMMENT '被授权用户 → sys_user.code',
    
    -- 权限范围（三维隔离）
    cb_code         VARCHAR(36) NOT NULL COMMENT '认证机构编码',
    standard_code   VARCHAR(50) NOT NULL COMMENT '标准编码，NULL=全部标准',
    phase_code      VARCHAR(20) NOT NULL COMMENT '阶段编码，NULL=全部阶段',
    
    -- 权限类型
    permission_type ENUM('readonly', 'draft_edit', 'full_edit') NOT NULL DEFAULT 'draft_edit' COMMENT '权限级别',
    -- readonly：只能查看
    -- draft_edit：只能编辑草稿状态配置
    -- full_edit：可编辑所有配置（仅限CB管理员）
    
    -- 授权来源
    granted_by      VARCHAR(36) NOT NULL COMMENT '授权人 → sys_user.code',
    grant_reason    TEXT COMMENT '授权原因',
    
    -- 生效范围
    effective_from  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    effective_to    DATETIME COMMENT 'NULL=永不过期',
    
    status          ENUM('active', 'expired', 'revoked') DEFAULT 'active',
    
    create_date     DATETIME DEFAULT CURRENT_TIMESTAMP,
    modify_date     DATETIME,
    
    FOREIGN KEY (user_code)   REFERENCES sys_user(code),
    FOREIGN KEY (cb_code)     REFERENCES cert_certification_body(code),
    FOREIGN KEY (granted_by)  REFERENCES sys_user(code),
    
    INDEX idx_ccp_user (user_code),
    INDEX idx_ccp_cb (cb_code),
    INDEX idx_ccp_range (cb_code, standard_code, phase_code)
) COMMENT '配置权限表';
```

#### 新增表 V-03：EnterpriseUser（企业用户）

```sql
CREATE TABLE ent_enterprise_user (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT,
```

## 四、权限模型设计

### 4.1 权限维度矩阵

| 权限类型 | SuperAdmin | CBAdmin | TeamLead | Auditor | ConfigMaintainer | EnterpriseUser |
|---------|:----------:|:-------:|:--------:|:-------:|:----------------:|:--------------:|
| 查看本CB所有数据 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ |
| 创建/编辑本CB配置 | ✅ | ✅ | ❌ | ❌ | 按范围 | ❌ |
| 管理本CB人员 | ✅ | ✅ | 本虚拟机构 | 无 | 无 | ❌ |
| 分配审核任务 | ✅ | ✅ | 可建议 | ❌ | ❌ | ❌ |
| 执行审核任务 | ❌ | 可执行 | 可执行 | ✅ | ❌ | ❌ |
| 查看本企业数据 | N/A | 可配置 | 可配置 | 可配置 | 按范围 | 本企业 |
| 提交整改证据 | N/A | ❌ | ❌ | ❌ | ❌ | ✅ |
| 创建新企业 | ✅ | ✅ | 可创建 | ❌ | ❌ | ❌ |

## 六、组织树设计（前端 TreeTable）

### 6.1 架构决策

**问题**：用户提到"左边是机构，右边是人员"的 TreeTable 页面。
**决策**：这个页面应该有两种形态：

| 形态 | 用途 | 左树 | 右表 |
|------|------|------|------|
| 形态A：虚拟机构管理 | CB管理员使用 | 虚拟机构树 | 该虚拟机构下的人员列表 |
| 形态B：人员管理 | 系统管理员/CB管理员使用 | 真实CB机构树 | 该CB下所有人员 |

### 6.2 形态A：虚拟机构+人员（CB管理员使用）

```
左树（虚拟机构树）：
├─ 🏢 CB名称（只读，作为根节点展示）
│   ├─ 📁 虚拟机构A
│   │   └─ 📁 虚拟机构A-1（子机构，可选）
│   ├─ 📁 虚拟机构B
│   └─ 📁 虚拟机构C
│
右表（人员列表）：
┌──────────┬──────────┬──────────┬──────────┬────────┐
│ 姓名     │ 角色     │ 资格证号 │ 专业领域 │ 状态   │
├──────────┼──────────┼──────────┼──────────┼────────┤
│ 张三     │ 审核组长 │ A12345   │ QMS      │ 启用   │
│ 李四     │ 审核员   │ A12346   │ QMS/EMS  │ 启用   │
│ 王五     │ 企业用户 │ —        │ —        │ 启用   │
└──────────┴──────────┴──────────┴──────────┴────────┘
```

**后端 API**：
```
GET  /api/virtual-org/tree/root        → 加载虚拟机构根节点
GET  /api/virtual-org/tree/children    → 懒加载子节点
```

### 9.1 权限检查逻辑（伪代码）

```csharp
// 伪代码，实际实现需根据 YZH.Core 框架调整

public class PermissionMiddleware
{
    public async Task<bool> CheckAsync(UserContext user, string apiPath, string action)
    {
        // 1. SuperAdmin 拥有所有权限
        if (user.UserType == "super_admin") return true;
        
        // 2. 检查 API 路径对应的权限标识
        var requiredPermission = ResolvePermission(apiPath, action);
        
        // 3. 检查用户角色是否有该权限
        if (user.HasRole(requiredPermission.RoleType)) return true;
        
        // 4. 检查数据权限（Data Scope）
        if (!await CheckDataScopeAsync(user, requiredPermission)) 
            return false;
        
        // 5. 检查配置权限（如果是配置相关API）
        if (apiPath.Contains("/config/") || apiPath.Contains("/rule/"))
        {
            if (!await CheckConfigPermissionAsync(user, apiPath))
                return false;
        }
        
        return true;
    }
    
    // 数据权限检查
    private async Task<bool> CheckDataScopeAsync(UserContext user, Permission required)
    {
        switch (user.UserType)
        {
            case "cb_admin":
                // 只能访问本CB的数据
                return await IsDataInCBOwner(user.CbCode, required.TargetCbCode);
            
            case "team_lead":
                // 只能访问本虚拟机构的数据
                return await IsDataInVirtualOrg(user.VirtualOrgCode, required.TargetVirtualOrgCode);
            
            case "auditor":
                // 只能访问被分配任务的数据
                return await HasAssignedTask(user.UserId, required.TargetTaskId);
            
            case "enterprise_user":
                // 只能访问本企业的数据
                return await IsDataInEnterprise(user.EnterpriseCode, required.TargetEnterpriseCode);
            
            default:
                return false;
        }
    }
}
```

### 9.2 查询时自动注入数据权限

```csharp
// 后端 Base Controller 自动注入数据权限过滤条件
protected override List<FilterItem> OnBuildingQuery(RequestCondition[]? conditions)
{
    var userContext = _userContext.GetCurrent();
    
    // 根据用户类型自动添加数据权限过滤
    var dataScopeFilter = ResolveDataScopeFilter(userContext);
    
    if (dataScopeFilter != null)
    {
        conditions = conditions ?? Array.Empty<RequestCondition>();
        // 注入权限过滤条件
        var filteredConditions = conditions.Concat(new[] { dataScopeFilter }).ToArray();
        return base.OnBuildingQuery(filteredConditions);
    }
    
    return base.OnBuildingQuery(conditions);
}

// 数据权限过滤规则
private RequestCondition? ResolveDataScopeFilter(UserContext user)
{
    switch (user.UserType)
    {
        case "cb_admin":
            return new RequestCondition { Field = "cb_code", Value = user.CbCode, Operator = "eq" };
        
        case "team_lead":
            return new RequestCondition { Field = "virtual_org_code", Value = user.VirtualOrgCode, Operator = "eq" };
        
        case "auditor":
            return new RequestCondition { Field = "auditor_id", Value = user.UserId.ToString(), Operator = "eq" };
        
        case "enterprise_user":
            return new RequestCondition { Field = "enterprise_code", Value = user.EnterpriseCode, Operator = "eq" };
        
        default:
            return null; // SuperAdmin 无过滤
    }
}
```

```csharp
// Redis 缓存权限数据
public class PermissionCacheService
{
    private const string KEY_PREFIX = "yzh:permission:";
    private const int CACHE_TTL_MINUTES = 30;
    
    // 缓存用户权限
    public async Task CacheUserPermissionsAsync(string userCode, UserPermissions perms)
    {
        var key = $"{KEY_PREFIX}user:{userCode}";
        await _redis.SetAsync(key, perms, TimeSpan.FromMinutes(CACHE_TTL_MINUTES));
    }

    public async Task<UserPermissions?> GetCachedPermissionsAsync(string userCode)
    {
        var key = $"{KEY_PREFIX}user:{userCode}";
        return await _redis.GetAsync<UserPermissions>(key);
    }
}
```

## 十三、关键决策记录（ADR）

| 编号 | 决策 | 理由 | 日期 |
|------|------|------|------|
| ADR-008 | **分离真实组织与虚拟组织** | 认证机构（CB）是法定实体，虚拟机构是管理工具，两者性质不同，不应混为一谈 | 2026-09-08 |
| ADR-009 | **虚拟机构使用独立树结构** | 虚拟机构有自身层级（可子机构），与CB机构树分离，避免混淆 | 2026-09-08 |
| ADR-010 | **配置权限使用三维隔离（CB+标准+阶段）** | 配置数据复杂度最高，需要最细粒度隔离，三维是最小可用维度 | 2026-09-08 |
| ADR-011 | **审核组长每个虚拟机构只能有1个** | 业务规则约束：审核组长是审批节点，多组长会导致审批链混乱 | 2026-09-08 |
| ADR-012 | **登录接口统一，根据 user_type 返回不同上下文** | 减少前端登录复杂度，后端统一鉴权，前端根据上下文决定路由 | 2026-09-08 |
