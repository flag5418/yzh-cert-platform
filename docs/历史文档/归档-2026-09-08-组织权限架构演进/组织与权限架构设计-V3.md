# 多租户体系认证平台——组织与权限架构设计（V3）

> **版本**：V3.0 | **日期**：2026-09-08 | **状态**：修订版
>
> **修订说明**：基于 V2.0 讨论，引入核心设计原则——**机构类型即角色类型，attach 视图即权限基础**。
>
> **核心洞察**：
> 1. 机构类型（dept_type）与用户角色（user_type）一一对应
> 2. 每个 attach 表对应一类特定的机构/人员类型
> 3. attach 视图成为权限管理的数据基础
> 4. 统一组织树 + 分类 attach 视图 = 清晰且可扩展的架构

---

## 一、核心设计原则

### 1.1 设计铁律

```
机构类型 = 角色类型 = Attach 视图类型

一个机构的 dept_type 决定了：
  1. 该机构下用户的默认 user_type
  2. 该机构对应的 attach 表结构
  3. 该机构具备的权限范围
  4. 该机构用户在系统中的行为模式
```

### 1.2 类型对应关系

| 机构类型（dept_type） | 用户角色（user_type） | Attach 表 | 权限特征 | 登录入口 |
|---------------------|---------------------|-----------|---------|---------|
| `system_admin` | `super_admin` | `org_system_attach` | 全局访问 | admin |
| `system_maintainer` | `maintainer` | `org_maintainer_attach` | 配置编辑（按范围） | admin |
| `cert_org` | `cb_admin` | `org_cert_org_attach` | 本CB所有数据 | cb |
| `virtual_org` | `team_lead` | `org_virtual_org_attach` | 本虚拟机构 | auditor |
| `audit_team` | `auditor` | `org_auditor_attach` | 被分配任务 | auditor |
| `enterprise_group` | `enterprise_user` | `org_enterprise_attach` | 本企业数据 | enterprise |

### 1.3 设计优势

```
┌─────────────────────────────────────────────────────────────────────┐
│                        统一且可扩展的架构                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. 类型驱动：新增机构类型 = 新增角色类型 = 新增 attach 表            │
│                                                                     │
│  2. 视图统一：每个 attach 表可形成视图，作为权限查询的基础            │
│                                                                     │
│  3. 权限清晰：角色权限由机构类型隐式决定，无需额外维护                │
│                                                                     │
│  4. 扩展简单：新增业务场景只需新增 dept_type + attach 表            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 二、数据库设计（按类型分离）

### 2.1 组织树主表（统一）

```sql
CREATE TABLE org_department (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,

    remark      TEXT,
    
    -- 审计字段

    modify_id   INT,
    modifier    VARCHAR(50),
    modify_date DATETIME,
    delete_id   INT,

    delete_time DATETIME,
    
    FOREIGN KEY (parent_code) REFERENCES org_department(code),

    INDEX idx_org_enable (enable)
```

## 三、Attach 视图设计（权限管理核心）

### 3.1 视图设计原则

```
每个 attach 表对应一个视图，视图是权限管理的数据基础：
  1. 视图封装了该类型机构/人员的所有属性
  2. 视图支持权限查询（哪些人可以访问哪些数据）
  3. 视图支持统计和分析（人员分布、权限范围等）
```

### 3.2 核心视图定义

#### 3.2.1 系统管理员视图

```sql
CREATE OR REPLACE VIEW v_sys_admin AS
SELECT 
    u.id,
    u.code AS user_code,
    u.user_name,
    u.user_type,
    d.code AS dept_code,
    d.name AS dept_name,
    sa.data_scope,
    sa.permitted_cbs,
    u.login_portal,
    u.create_date,
    u.modify_date
FROM sys_user u
JOIN org_department d ON u.dept_code = d.code
JOIN org_system_attach sa ON d.code = sa.code
WHERE d.dept_type = 'system_admin' AND u.enable = 1;
```

## 四、权限管理模型

### 4.1 权限层次结构

```
┌─────────────────────────────────────────────────────────────────────┐
│                        权限层次结构                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Level 1: 框架层权限（通用）                                          │
│  ├── 登录认证（JWT）                                                  │
│  ├── 基础角色权限（super_admin / cb_admin / auditor 等）              │
│  └── 数据隔离（CB隔离、虚拟机构隔离）                                  │
│                                                                     │
│  Level 2: 业务层权限（按 attach 视图）                                │
│  ├── 系统管理员：全局权限（v_sys_admin 视图）                         │
│  ├── 维护人员：配置权限范围（v_sys_maintainer 视图）                   │
│  ├── CB管理员：本CB所有数据（v_cert_org 视图）                         │
│  ├── 审核组长：本虚拟机构数据（v_virtual_org 视图）                    │
│  ├── 审核员：被分配任务数据（v_auditor 视图）                          │
│  └── 企业用户：本企业数据（v_enterprise_user 视图）                    │
│                                                                     │
│  Level 3: 接口层权限（API 细粒度）                                    │
│  ├── 接口访问权限（哪些API可以调用）                                  │
│  ├── 接口操作权限（增删改查权限）                                     │
│  └── 接口数据权限（能操作哪些数据记录）                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 权限检查逻辑

```csharp
// 权限中间件：三层检查
public class PermissionMiddleware
{
    public async Task<PermissionResult> CheckAsync(UserContext user, string apiPath, string action)
    {
        // Level 1: 框架层检查
        if (!await CheckFrameworkPermissionAsync(user, apiPath))
            return PermissionResult.Forbidden("框架权限不足");
        
        // Level 2: 业务层检查（基于 attach 视图）
        if (!await CheckBusinessPermissionAsync(user, apiPath, action))
            return PermissionResult.Forbidden("业务权限不足");
        
        // Level 3: 接口层检查
        if (!await CheckApiPermissionAsync(user, apiPath, action))
            return PermissionResult.Forbidden("接口权限不足");
        
        return PermissionResult.Allowed();
    }
    
    // Level 2: 业务层权限检查（核心）
    private async Task<bool> CheckBusinessPermissionAsync(UserContext user, string apiPath, string action)
    {
        // 根据用户所在机构类型，检查对应的 attach 视图权限
        var dept = await _deptService.GetByCodeAsync(user.DeptCode);
        
        return dept?.DeptType switch
        {
            "system_admin" => await CheckSystemAdminPermissionAsync(user, apiPath, action),
            "system_maintainer" => await CheckMaintainerPermissionAsync(user, apiPath, action),
            "cert_org" => await CheckCertOrgPermissionAsync(user, apiPath, action),
            "virtual_org" => await CheckVirtualOrgPermissionAsync(user, apiPath, action),
            "audit_team" => await CheckAuditorPermissionAsync(user, apiPath, action),
            "enterprise_group" => await CheckEnterpriseUserPermissionAsync(user, apiPath, action),
            _ => false
        };
    }
}
```

### 4.3 数据权限注入（自动过滤）

```csharp
// 后端 Base Controller 自动注入数据权限过滤
protected override List<FilterItem> OnBuildingQuery(RequestCondition[]? conditions)
{
    var user = _userContext.GetCurrent();
    var filters = base.OnBuildingQuery(conditions);
    
    // 根据用户机构类型自动注入数据权限过滤
    var dataScopeFilter = ResolveDataScopeFilter(user);
    if (dataScopeFilter != null)
    {
        filters.Add(dataScopeFilter);
    }
    
    return filters;
}

private RequestCondition? ResolveDataScopeFilter(UserContext user)
{
    // 查询 attach 视图获取权限范围
    var attachData = await GetAttachDataAsync(user.DeptCode);
    
    return attachData?.DeptType switch
    {
        "system_admin" => null, // 全局访问，无过滤
        "system_maintainer" => new RequestCondition 
        { 
            Field = "code", 
            Value = attachData.PermittedCbs, 
            Operator = "in" 
        },
        "cert_org" => new RequestCondition 
        {
```

## 八、关键设计优势

### 8.1 类型驱动架构

```
新增业务场景 = 新增 dept_type + 新增 attach 表 + 新增视图

示例：未来需要新增"外部专家"角色
  1. 新增 dept_type = 'external_expert'
  2. 创建 org_external_expert_attach 表
  3. 创建 v_external_expert 视图
  4. 在 sys_user.user_type 枚举中新增 'external_expert'
  5. 完成！
```

### 8.2 权限管理清晰

```
1. 每个 attach 视图对应一类权限
2. 权限查询统一通过视图进行
3. 权限变更只需修改 attach 表数据
4. 权限审计可通过视图历史记录追踪
```

### 8.3 与现有架构兼容

```
1. 完全兼容现有 TreeTable 架构
2. 无需修改现有 sys_user 表结构（仅新增字段）
3. attach 表采用标准基类（BaseEntity）
4. 视图可作为现有查询的替代方案
```

## 九、待确认问题

1. **虚拟机构是否支持多层级？** （本设计支持 parent_code 自引用，但需确认业务需求）
2. **审核员是否可以属于多个虚拟机构？** （本设计 sys_user 只关联一个 dept_code，如需多归属需调整）
3. **企业用户是否只能隶属于一个虚拟机构？** （本设计 org_enterprise_attach 关联单个 enterprise_code）
4. **预初始化树结构是否固定？** （本设计系统管理组固定，CB机构和虚拟机构动态创建）
5. **attach 表是否需要软删除？** （本设计通过 org_department.enable 控制，attach 表级联删除）
