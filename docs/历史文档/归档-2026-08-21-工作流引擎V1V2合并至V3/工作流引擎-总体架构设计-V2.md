## 0.5 业务背景与核心约束

> 本章回答：**引擎为什么存在、必须满足哪些业务刚性约束**。后续所有设计（任务建模、存储、执行、证据链）均需能兑现本节承诺，否则视为不满足需求。本节是用户明确要求写入文档的业务背景，也是所有设计决策的出发点。

### 0.5.1 业务模型（机构 + 标准 + 阶段）

系统面向**体系认证审核**：一个认证机构（CB）下，一个标准（如 ISO 9001）、一个审核阶段（初审/一监/二监）构成一个**业务配置单元**。在该单元内：

- 存在**一套完整的 NC 检查项**（多项，每项一个 `workflow_config`），用于企业资料上传后的自动/人工审核
- 存在**一套需要生成的报告**（按章节组织，每章一个 `workflow_config`），用于审核完成后组装输出

```
机构 + 标准 + 阶段（业务配置单元）
  ├── NC 检查项集合（N 项，每项一个 workflow_config）→ 审核中发现不符合项
  └── 报告模板 + 章节集合（M 章，每章一个 workflow_config）→ 审核完成后组装报告
```

### 0.5.2 两种触发方式

| 触发 | 场景 | 说明 |
|---|---|---|
| 自动 NC 检查 | 企业资料上传完成后 | 按 机构+标准+阶段 定位该单元全部启用检查项，自动批量执行 NC 检查 |
| 一键生成报告 | 审核员/客户申请 | 基于该单元已完成审核数据，逐章节生成报告内容 |

### 0.5.3 业务可变性与数据可靠性（核心约束）

| 约束 | 业务含义 | 对引擎的硬性要求 |
|---|---|---|
| 文档频繁更换 | 企业文档在审查中可能反复替换版本 | 每次执行必须绑定**文件版本基线**；历史执行结果不因文档更新而失效，形成版本结果链 |
| NC 结果可修改 | 自动审核结果可被人工调整，且修改需**完整保存流程** | 结果（audit_finding）版本化 + 修改审计（谁/何时/改了什么/原因）；引擎重跑不得静默覆盖人工修订 |
| NC 可追踪 | 每项 NC 可查**审计来源、错误原因** | 节点输出携带 provenance：来源文件版本、条款、上游节点；每步决策可回溯 |
| 报告可审计 | 每份报告可还原"什么流程产出、每步如何执行、如何得到最终结果" | 报告章节内容 ↔ 执行任务/任务项/节点/来源 的完整追溯链 |
| 证据链可信 | 工作流**不允许客户直接修改**，但必须提供完整证据链 | 客户可查看执行全链路与出处；引擎配置仅机构管理员可改；支持导出审计附录 |

> **一句话总结**：业务要求 **"配置可复用、执行可追溯、结果可修订、证据链完整"**——这正是本引擎设计的出发点，也是 §4 三层任务模型与 §5.4 证据链设计的直接依据。

## 1. 设计目标与核心理念

### 1.1 设计目标

把审核领域的**NC 检查**与**报告生成**，从"写死在代码里的业务逻辑"升级为**可编排、可测试、可审计的配置化流程**：

- **可编排**：审核规则（取字段 → AI 判断 → 分支 → 组装结论）在画布上配置，引擎按配置执行
- **可测试**：配置期可在画布上试运行，验证逻辑后再落地
- **可审计**：每次执行的全过程（每个节点的输入输出、分支决策、token 消耗）可回溯

### 1.2 五个核心理念

这五条是驱动引擎所有模块的**设计原理**，后续任何子功能设计若与它们冲突，以它们为准。

**理念一：配置即流程（Configuration as Process）**
审核逻辑 = `workflow_config` JSON。引擎是一个**通用解释器**，不关心具体业务，只按配置执行节点。业务能力（取字段、AI 判断、表格操作）通过 **Skill 注册表** 注入，新增业务能力 = 注册新 Skill，不改引擎核心。

**理念二：任务统一建模（Unified Task Model）**
NC 检查、报告生成、测试试运行，本质都是"**一次工作流执行**"，统一建模为 `ExecutionTask`（一条 `wf_execution_task` 记录）。三者区别只在于：
- `task_type`（NC_CHECK / REPORT_GENERATE / TEST）
- 数据边界（真实企业 / 固定测试企业 YZH-STD-ENT）
- 产出目标（写 audit_finding / 写 section.content / 不写业务终态）

**它们共用同一套执行内核、同一套节点记录、同一套队列**。这是保证"测试跑通 = 正式能跑"的根本前提——绝不能为测试单独建一套执行逻辑。

**理念三：路径驱动执行（Path-Driven Execution）**
一个完整配置可能包含**多条拓扑线路**（如分支的两个走向）。引擎的执行原则：

1. 一次推进**一条线路**：从 start 出发，按边逐个执行节点
2. 遇到分支（logic）节点：执行条件判断 → 结果决定走哪条子线路 → **未选中的线路整体标记为 skipped（跳过）**，不执行、不阻塞
3. **节点结果落库复用**：每个节点执行后，输出按 `task_code + node_id` 落库；后续线路执行时，**已执行过的节点不重复执行**，直接从库中读取结果；只跑当前线路尚未涉及的新节点
4. 一条线路走完（到达 end 或被分支跳过）→ 若还有其他未终结线路则继续推进
5. 所有线路均终结 → 工作流 completed；任一线路失败且不可容忍 → 工作流 failed

**理念四：确定性分离（Determinism Separation）**
节点按是否确定性分类，决定"能否复用执行结果"：

| 节点类型 | 是否确定性 | 输入相同能否复用结果 |
|---|---|---|
| docField / docTable / 文档写入 | 是 | 可安全复用 |
| logic（条件判断）| 是 | 可复用 |
| skill（业务功能）| 视实现，默认按确定性处理 | 复用前确认无副作用 |
| ai_node（LLM 生成）| **否**（同输入可能不同输出）| **默认重跑**，复用需显式配置 |

**理念五：可观测与可审计（Observability & Auditability）**
每个节点执行记录（输入/输出/耗时/token/是否复用）+ 每条分支决策 + 任务级日志全部落库。它们既支撑前端调试面板，也支撑断点续跑（基于已有记录跳过已完成节点），更支撑合规审计。

## 2. 引擎总体架构

### 2.1 分层架构总览

引擎按"**接入层 → 核心层 → 执行层 → 存储层**"四层组织，每层职责单一、向下依赖：

```
┌───────────────────────────────────────────────────────────────────────────┐
│ 接入层  API / SignalR / 画布触发                                            │
│         POST /api/workflow/run | enqueue | task/{code}/cancel 等            │
└────────────────────────────────┬──────────────────────────────────────────┘
                                 ▼
┌───────────────────────────────────────────────────────────────────────────┐
│ 核心层  任务管理器（ExecutionTaskManager）                                   │
│         · 唯一入口：创建 / 查询 / 取消执行任务                               │
│         · 统一任务建模（§4）——NC / 报告 / 测试都从这里进                    │
└────────────────────────────────┬──────────────────────────────────────────┘
                                 ▼
┌───────────────────────────────────────────────────────────────────────────┐
│ 执行层  路径驱动执行（§3 核心执行模型）                                      │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐           │
│  │ 路径分析器   │→│ DAG 解释器  │→│ 节点执行器   │→│ 上下文管理器│           │
│  │ Topology   │  │ Workflow   │  │ Node       │  │ Workflow   │           │
│  │ Analyzer   │  │ Interpreter│  │ Executor   │  │ Context Mgr│           │
│  └────────────┘  └────────────┘  └────────────┘  └────────────┘           │
│        ↑                ↑                ↑                ↑                │
│  ┌────────────┐  ┌───────────────────────────────────────────────────┐    │
│  │ 队列集成器   │  │ 存储层                                            │    │
│  │ Queue      │  │ wf_execution_task / wf_node_output /              │    │
│  │ Integrator │  │ wf_execution_log                                  │    │
│  └────────────┘  └───────────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────────────────────┘
```

**分层原则**：
- 接入层不写业务逻辑，只做参数校验与协议转换
- 核心层管"任务生命周期"，不直接操作节点
- 执行层管"节点怎么跑、下一步跑谁"，不感知业务
- 存储层管"数据怎么写、怎么查"，不感知执行

### 2.2 六大核心模块与运行机制

每个模块必须明确"**它驱动什么**"——这是模块存在的原因，也是子功能设计的上游：

| 模块 | 驱动什么（运行机制一句话） | 关键接口 |
|---|---|---|
| **任务管理器** | 驱动"任务生命周期"：把一次执行请求变成有状态、可追踪、可取消的任务 | `IExecutionTaskManager` |
| **路径分析器** | 驱动"静态校验"：拓扑排序、环检测、路径枚举，只在创建/校验时用，**不参与运行时调度** | `ITopologyAnalyzer` |
| **DAG 解释器** | 驱动"路径推进"：按理念三逐线路执行节点、复用记录、路由分支，是运行时的心脏 | `IWorkflowInterpreter` |
| **节点执行器** | 驱动"单个节点怎么执行"：解析输入 → 调 Skill/AI → 落输出 → 写日志 | `IYzhTaskExecutor` / `IAiNodeExecutor` |
| **上下文管理器** | 驱动"数据边界"：区分 TEST/正式的数据源、产出目标、环境注入 | `EnvironmentContext` |
| **队列集成器** | 驱动"异步调度"：把节点推进变成队列任务，获得超时/重试/并发/断点能力 | `IQueueDrivenExecutor` |

> 重要区分：**路径分析器（静态）与 DAG 解释器（运行时）职责分离**。静态只做校验与可达性分析；运行时按"执行当前节点 → 读输出 → 按条件/边路由 → 取下一节点"的遍历式模型推进，绝不用静态拓扑序直接"全量执行所有节点"。

### 2.3 模块接口定义

```csharp
namespace YZH.Core.Workflow
{
    /// <summary>入口：创建执行任务（TEST / NC_CHECK / REPORT_GENERATE），统一任务模型唯一入口</summary>
    public interface IExecutionTaskManager
    {
        /// <summary>创建执行任务（支持幂等：同幂等键重复请求返回已有任务）</summary>
        Task<ExecutionTask> CreateAsync(CreateTaskRequest req);
        /// <summary>查询任务状态</summary>
        Task<ExecutionTask> GetByCodeAsync(string taskCode);
        /// <summary>取消任务（级联：已入队节点跳过、执行中节点中断、已落库输出保留）</summary>
        Task<bool> CancelAsync(string taskCode, string reason);
    }

    /// <summary>静态拓扑分析：只做校验与路径枚举，不参与运行时调度</summary>
    public interface ITopologyAnalyzer
    {
        IReadOnlyList<string> TopoSort(WorkflowConfig config);
        bool HasCycles(WorkflowConfig config, out List<string> cycle);
        IReadOnlyList<PathSegment> GetAllPaths(WorkflowConfig config);
    }

    /// <summary>运行时解释器：按路径驱动模型推进节点执行</summary>
    public interface IWorkflowInterpreter
    {
        Task<WorkflowRunResult> RunAsync(string config, ExecutionTask task, CancellationToken ct);
        /// <summary>返回"下一可执行节点集"：同步/异步共用同一套路由核心（§3.3）</summary>
        IReadOnlyList<NodeRef> ResolveNextNodes(WorkflowConfig config, string currentNodeId, IDictionary<string, object> currentOutput);
    }

    /// <summary>队列驱动（异步路径）：节点级入队，解耦执行卡与结果获取</summary>
    public interface IQueueDrivenExecutor
    {
        Task<string> EnqueueAsync(ExecutionTask task);
        Task<TaskExecuteResult> ExecuteTaskAsync(YzhQueueTask queueTask);
    }

    /// <summary>AI 节点专用执行器：封装 LLM 调用、提示词组装、token 统计</summary>
    public interface IAiNodeExecutor
    {
        Task<AiNodeResult> ExecuteAsync(AiNodeContext ctx);
    }

    /// <summary>节点输出存储：执行记录的核心载体，支撑结果复用与断点续跑</summary>
    public interface INodeOutputStore
    {
        Task SaveOutputAsync(string taskCode, string nodeId, string portName, object value);
        Task<T> GetOutputAsync<T>(string taskCode, string nodeId, string portName);
        Task<IDictionary<string, object>> GetAllOutputsAsync(string taskCode, string nodeId);
    }

    /// <summary>执行日志查询：按任务聚合、节点回溯、TRACE 序列</summary>
    public interface IExecutionLogQuery
    {
        Task<IReadOnlyList<ExecutionLogEntry>> GetByTaskAsync(string taskCode);
        Task<IReadOnlyList<ExecutionLogEntry>> GetByNodeAsync(string taskCode, string nodeId);
        Task<ExecutionTrace> GetTraceAsync(string taskCode);
    }

    /// <summary>SignalR 推送：实时执行事件</summary>
    public interface IWorkflowNotifier
    {
        Task NotifyNodeStarted(string taskCode, string nodeId);
        Task NotifyNodeCompleted(string taskCode, string nodeId, bool success, object output);
        Task NotifyTaskCompleted(string taskCode, bool success, object result);
    }
}
```

## 3. 核心执行模型

> **本章是整个引擎最核心的内容**。后续所有执行类子功能设计（节点执行器、队列调度、断点续跑、日志存储）都以本章为总纲。

### 3.1 执行模型总纲：路径驱动 + 结果复用

引擎运行时采用**遍历式解释执行**，核心规则（对应 §1.2 理念三）：

```
执行器 = 一个循环，推进当前线路：

  while (还有未终结线路) {
      取当前线路的下一个节点 N；
      
      if (N 已执行过且满足复用条件) {
          从 wf_node_output 读取结果 → 直接使用（不重跑）;
      } else {
          执行 N；
          if (N 是 logic 分支节点) {
              记录分支决策（走了哪条路、跳过了哪些线路）；
              未选中线路 → 全部标记 skipped；
          }
          落库 wf_node_output + 写执行日志 + 推送 SignalR；
      }
      
      if (N 到达 end 或 N 所在线路被标记结束) {
          标记当前线路终结；
          切换/继续下一条未终结线路；
      }
  }
  所有线路终结 → 汇聚输出 → 更新任务状态；
```

**关键定义**：

1. **线路（Path）**：从 start 出发、按边可达 end 的一条节点序列。配置可含多条线路（分支多走向）。
2. **结果复用**：节点执行后输出落库 `wf_node_output`（按 `task_code + node_id` 唯一）。再次遇到同一节点时，若**满足复用条件**则读库复用。复用条件（对应理念四）：
   - 确定性节点（docField/docTable/logic）：`task_code + node_id` 已有记录 → 直接复用
   - AI 节点：**默认不复用、重跑**；仅当节点配置显式开启 `reuse_if_same_input` 且输入指纹一致时才复用（用于测试调试）
   - 复用发生时，在执行日志记录 `is_reused=true` 标记，保证可审计
3. **分支决策落库**：logic 节点判定结果（选中哪条、跳过哪些线路）必须写入执行记录，否则无法回溯"为什么走这条路"，也无法支撑断点续跑。
4. **结束判定**：所有线路均终结（到达 end 或被跳过）→ 任务 completed。任一线路执行中出现不可重试错误 → 任务 failed（具体见 §6.3）。
5. **运行时防护**：除静态环检测外，运行时设置最大节点执行次数上限（如 500），防止逻辑缺陷导致死循环；单节点设最大耗时上限（见 §6.4）。

### 3.2 执行生命周期（路径推进视角）

```
 REQ: POST /api/workflow/run  或  /api/workflow/enqueue
 ─────────────────────────────────────────────────────────────
 [1] ExecutionTaskManager.CreateAsync()
     · 创建 wf_execution_task（status=queued）
     · 锁定 config_snapshot（防止执行期间配置变更）
     · 返回 taskCode / queueCode
 ─────────────────────────────────────────────────────────────
 [2] 同步路径（TEST 小图）                   异步路径（正式/大图）
     IWorkflowInterpreter.RunAsync()    →    IQueueDrivenExecutor.EnqueueAsync()
     直接按 §3.1 模型推进，返回结果            生成队列任务，逐节点驱动（§6）
 ─────────────────────────────────────────────────────────────
 [3] 每个节点执行时，固定五步（顺序不可变）：
     ① NotifyNodeStarted            // SignalR 推送开始
     ② 判断复用 → 读库 or 执行        // §3.1 规则
     ③ SaveOutput(wf_node_output)    // 落输出（复用则跳过）
     ④ WriteLog(wf_execution_log)    // 写日志（含分支决策、is_reused、token）
     ⑤ NotifyNodeCompleted           // SignalR 推送完成
 ─────────────────────────────────────────────────────────────
 [4] 汇聚：所有线路终结
     · 更新 task.result_summary（end 输出）
     · 更新 task.task_status = completed / failed
     · NotifyTaskCompleted
 ─────────────────────────────────────────────────────────────
 RES: {taskCode, status, result} + SignalR 节点级事件 + wf_node_output 可查
```

### 3.3 统一路由核心（同步/异步共用）

> 同步与异步**必须共用同一套"下一节点路由"逻辑**，否则会出现"测试跑通、正式走不同路径"的不一致。

```csharp
/// <summary>
/// 统一路由核心：给定当前节点与运行时输出，返回下一可执行节点集。
/// 同步（RunAsync 循环内）与异步（WorkflowNodeExecutor 内）都调用它。
/// </summary>
public IReadOnlyList<NodeRef> ResolveNextNodes(config, currentNodeId, currentOutput)
{
    // 1. 取当前节点的出边
    var edges = config.Edges.Where(e => e.From == currentNodeId);
    if (当前节点是 logic)
    {
        // 2. 分支：按运行时布尔输出选择出边
        var passed = (bool)currentOutput["result"];
        return edges.Where(e => e.Handle == (passed ? "true" : "false"))
                    .Select(e => new NodeRef(e.To)).ToList();
    }
    // 3. 无条件直连边：返回下一节点（扇出则返回多个，并行场景用）
    return edges.Select(e => new NodeRef(e.To)).ToList();
}
```

**配套规则**：
- `TopoSort` 只用于创建/校验时（环检测、可达性、路径枚举），**绝不用于运行时调度**
- logic 节点的未选中出边 → 对应子线路整体标记 skipped
- 扇出（一个节点多个无条件出边）：V1 串行处理（按序推进），V2 可扩展同层并行（见 §12 决策）

### 3.4 节点类型与执行器映射

| nodeType | 执行器 | 输出端口 | 确定性 | 执行后副作用 |
|---|---|---|---|---|
| `start` | 引擎内置 | 声明的工作流输入 | 是 | 无（注入上下文） |
| `skill` | `SkillExecutor.ExecuteAsync()`（反射）| 按 wf_skill_output 定义 | 视 Skill 实现 | 写 wf_node_output |
| `ai_node` | `AiNodeExecutor.ExecuteAsync()` | content / json / confidence | 否 | 写 wf_node_output + token 统计 |
| `logic` | 引擎内置（条件求值）| result(boolean) | 是 | 仅决定路由（决策落库） |
| `loop` | v1: AI 提示词整包执行（与 ai_node 边界见 §12 决策）| results(json) | 否 | 写 wf_node_output |
| `docField` / `docTable` | 引擎内置（查 B-08/B-09）| 字段值/表格数据 | 是 | 读数据后写 wf_node_output |
| `end` | 汇聚输出 | 无（终态写 result_summary）| 是 | 更新任务状态 |

## 4. 任务体系统一建模

### 4.0 三层任务模型（任务 → 任务项 → 节点）⭐ 业务核心

> **背景**（§0.5）：一次"自动 NC 检查" = 一个配置单元内 **N 个检查项**同时执行；一份报告 = **M 个章节**分别生成。若沿用"任务 → 节点"两层，只能表达"一次任务跑一个 config"，无法承载"一次触发跑一套 item"，且不同 item 的节点 id 会互相冲突。因此任务体系统一建模为**三层**：

```
wf_execution_task             一次业务触发 = 一个任务（如"企业A 初审 NC 全量检查"/"企业A 一审报告生成"）
  └── wf_execution_task_item   item = 一个检查项 / 一个报告章节，各携带一份 config 快照
        └── wf_node_output / wf_execution_log   节点执行记录（按 task_code + item_code + node_id 隔离）
```

| 层 | 实体 | 含义 | 粒度 |
|---|---|---|---|
| 任务 | wf_execution_task | 一次触发的业务聚合（状态机/看门狗/幂等/取消的载体）| 一次点击 / 一次自动触发 |
| 任务项 | wf_execution_task_item | 一个 NC 检查项或一个报告章节（各含独立 workflow_config 快照）| 一个 rule / 一个 section |
| 节点记录 | wf_node_output / wf_execution_log | 单个节点的输入/输出/日志/决策 | 一次节点执行 |

**三层关键规则**：
1. 任务负责"业务聚合与生命周期"（所有 item 的终态汇聚成任务结果）；item 负责"单 config 执行"；节点记录负责"证据链原子单元"
2. **节点记录唯一键必须含 item_code**：`(task_code, item_code, node_id, port_name)`，防止不同 item（不同 config 中同名节点 id，如 `n1`/`judge`）相互污染
3. item 之间**默认并行**（同属一次触发、互不依赖）；单 item 内节点按路径驱动串行
4. 失败传播：某 item 失败 → 默认仅该 item 置 failed，其余 item 继续；是否级联失败整个任务由触发配置决定（§12 决策 9）
5. 取消级联：取消任务 → 级联取消所有未终结 item；已落库节点记录保留
6. 断点续跑粒度 = **item 级**：失败/取消的 item 从断点继续，未受影响的 item 不重跑

### 4.1 统一任务项模型（item 层）

所有执行（TEST / NC_CHECK / REPORT_GENERATE）在 item 层共用同一套执行内核，用字段区分：

| 维度 | TEST | NC_CHECK | REPORT_GENERATE |
|---|---|---|---|
| item_type | TEST | NC_CHECK | REPORT_GENERATE |
| config 来源 | 画布当前编辑态 JSON | wf_check_rule.rule_config 快照 | rpt_report_section.workflow_config 快照 |
| 数据边界 | enterprise_code = "YZH-STD-ENT"（固定测试企业）| 真实 enterprise_code | 真实 enterprise_code |
| 数据读写 | 只读（查询 B-08/B-09）| 只读 + 写 NC 结果 | 只读 + 写 section.content |
| 产出目标（OutputTarget）| None（不写业务终态）| AuditFinding | SectionContent |
| 保留策略 | 可定期清理 | 永久（审计）| 永久（审计）|

> **关键约束**：TEST 与正式任务**共用同一套执行代码**。测试"跑通 = 正式能跑"，差异只体现在数据边界与产出目标，由 `EnvironmentContext`（§4.3）控制，绝不出现第二套执行路径。

### 4.2 任务状态机

队列驱动下，任务存在多个中间态，必须用状态机表达（区分"正在跑"与"卡死"）：

```
                        ┌──────────┐
                        │  queued   │  创建成功，待入队/已入队
                        └─────┬────┘
                              │ 入队消费
                              ▼
                        ┌──────────┐   ──→ 失败(不可重试) ──→ ┌────────┐
   CancelAsync ──→     │ executing │                         │ failed  │
                        └─────┬────┘   ←── 失败(可重试) ───┘ └────────┘
                              │ 重试入队（计数+1）
                              ▼
                        ┌──────────┐
                        │ retrying  │
                        └─────┬────┘
                              │ 重试成功
                              ▼
                        ┌──────────┐
                        │ executing │
                        └─────┬────┘
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
     ┌────────┐        ┌────────────┐      ┌────────────┐
     │completed│       │  cancelled  │     │  failed     │
     └────────┘        └────────────┘      └────────────┘
```

状态取值：`queued | executing | retrying | completed | failed | cancelled`

**配套规则**：
- **看门狗**：任务创建后若超过阈值（如 30 分钟）仍处于 `queued/executing` 且无活跃节点执行事件 → 判定卡死，置 `failed` 并告警（防"节点落库完成→下一节点入队"之间崩溃导致的永久 running）
- **断点续跑**：任务失败/取消后重跑时，扫描 `wf_node_output` 已有记录，跳过已完成节点，从断点继续（机制见 §6.3）
- **入队幂等**：`CreateAsync` 支持幂等键（`rule_code + file_code + trigger_id` 维度），重复请求返回已有 taskCode，防止双击/重连重复触发

### 4.3 任务上下文 EnvironmentContext

上下文对象树（各子功能设计需遵循）：

```
ExecutionTask (wf_execution_task 记录)
  └── WorkflowContext        // 通用执行上下文（节点输入解析、输出引用）
        └── EnvironmentContext   // 环境/数据边界（TEST vs 正式）
              ├── IsTestMode: bool          // TEST=true
              ├── EnterpriseCode: string    // 数据边界（TEST=YZH-STD-ENT）
              ├── PhaseCode: string         // 审核阶段（数据源定位 B-08/B-09）
              └── OutputTarget: enum        // None / AuditFinding / SectionContent
```

```csharp
public class EnvironmentContext
{
    public bool IsTestMode { get; set; }
    public string EnterpriseCode { get; set; }
    public string PhaseCode { get; set; }
    public OutputTarget OutputTarget { get; set; }
}

public enum OutputTarget
{
    None,           // TEST：绝不写业务终态
    AuditFinding,   // NC_CHECK：写 audit_finding / 更新 NC 状态
    SectionContent  // REPORT_GENERATE：更新 section.content
}
```

**隔离铁律**：`OutputTarget=None`（TEST）时，任何节点**不得**写入 audit_finding / section.content / NC 状态等业务终态；只允许写 `wf_node_output`（调试展示）与执行日志。

### 5.1.1 任务项表 wf_execution_task_item（三层模型新增）

> **定位**：一次任务内的"一个检查项 / 一个报告章节"执行单元。每个 item 携带**独立 config 快照**，是路径驱动执行与结果复用的实际载体（§4.0）。

**item 与 task 的关系**：
- 一次任务创建时，按 机构+标准+阶段 找到该单元全部启用 item（NC 检查项 / 报告章节），为每个 item 生成一条 `wf_execution_task_item` 记录
- 自动 NC 检查：任务创建后，为每个启用检查项生成 item，item 间并行执行
- 一键生成报告：为每个报告章节生成 item，item 间并行执行（章节间无依赖时）
- 任务终态 = 所有 item 终态的汇聚（全部 completed → completed；任一不可容忍 failed → failed）

**存储约束**：
- `text_value` 与 `json_value` **二选一**互斥：小尺寸（< 64KB）→ text_value；结构化/大尺寸 → json_value
- `json_value` 大小上限 1MB；超限内容转存文件/对象存储，仅存引用
- 节点多端口输出：`SaveOutputsAsync` **批量写**（一节点全部端口一次事务提交）

### 5.4 证据链与审计设计（Provenance & Audit Trail）⭐ 业务核心

> **背景**（§0.5）：NC 与报告都必须**可审计、可追踪、证据链完整**，才能让客户信服系统数据可靠。本节定义"从最终结果一路追溯回来源"的机制。

#### 5.4.1 证据链四要素

| 要素 | 载体 | 说明 |
|---|---|---|
| **执行链** | wf_execution_task + wf_execution_task_item + wf_execution_log（TRACE）| 什么流程产出：任务 → item → 节点事件序列，含分支决策、is_reused、耗时、token |
| **结果链** | wf_node_output（含 provenance 字段）| 每步如何执行：节点输入/输出/来源（文件版本/文档/条款）|
| **版本链** | item.input_baseline + source_file_version | 基于哪个版本基线：企业文档版本集 + 配置快照，历史执行不因文档更换失效 |
| **修订链** | audit_finding 版本记录（见 5.4.3）| 结果如何被修改：人工修订的完整历史（谁/何时/改什么/原因）|

#### 5.4.2 追溯方向（双向可查）

```
最终结果（NC 结论 / 报告章节内容）
   ↑ 来源追溯（点击某段/某项 → 向上钻取）
   wf_node_output（生成该结果的 AI/技能节点输出，含来源文件版本、条款）
   ↑
   wf_execution_task_item（该 item 的 config 快照 + 输入基线）
   ↑
   wf_execution_task（一次触发的业务聚合 + 触发人 + 触发时间）
   ↑
   业务终态（audit_finding / section.content，带 provenance 关联）
```

反向（结果变更追踪）：业务终态被人工修改 → 修订链记录 → 关联回原自动执行任务，形成"自动结果 → 人工修订"闭环。

#### 5.4.3 NC 结果修订链（audit_finding 版本化）

用户约束：**NC 审核结果可修改，且完整保存流程**。设计原则：

- 自动执行只**新增/生成** audit_finding 的初始结论（来源 = 自动任务），不直接覆盖
- 人工修改走**独立修订记录**（谁/何时/改前值/改后值/修改原因），业务表保留最终值 + 关联修订历史
- **重跑保护**：item 重跑（断点续跑/重新检查）时，若目标 audit_finding 已存在人工修订，自动结果**不得静默覆盖**——默认跳过或生成"待确认"的新候选，由审核员决定采纳/丢弃（§12 决策 10）
- 前端展示：每项 NC = 自动审核结果 + 审计来源 + 错误原因 + [修改] 入口，修改即写修订链

#### 5.4.4 报告内容出处（section.content provenance）

用户约束：**每份报告可审计"什么流程产出、每步如何执行、得到最终结果"**。

- 报告章节内容生成后，记录该章节内容 ↔ 生成它的 item（task + item_code）映射，存于业务表（如 `rpt_report_section` 增加 `last_generate_task_item_code`）
- 前端"报告审计"视图：点击报告某段 → 展示该章节的执行 TRACE（节点序列、输入来源文件版本、token）
- 报告导出时可选附加**审计附录**：执行摘要 + 每章节生成链 + 版本基线清单（供客户留档）

#### 5.4.5 权限边界（客户可看不可改）

用户约束：**工作流不能让客户轻易修改，但需完整证据链确保可信**。

| 角色 | 引擎配置 | 执行触发 | 执行/证据链查看 | 结果修改 |
|---|---|---|---|---|
| 机构管理员 | 可编辑（画布）| 可触发 | 全部可见 | 可（需原因，写修订链）|
| 审核员 | 只读 | 可触发 | 全部可见 | 可（需原因，写修订链）|
| 客户 | 不可见 | 不可 | 可查看证据链（执行链+出处）| 不可直接改（可提交修改申请）|

> 证据链查看对客户开放，是"数据可靠可信"的商业承诺；引擎配置与执行控制对客户关闭，保证流程不被客户篡改。

## 6. 队列驱动执行

### 6.1 设计动机

| 问题 | 同步执行 | 队列驱动 |
|---|---|---|
| 超时控制 | HTTP 超时（60s），长工作流易卡死 | 队列任务租约，自然超时回收 |
| 失败重试 | 手动/全量 | 单节点级重试（Retryable 分类）|
| 并发控制 | 无 | 信号量（SemaphoreSlim）限制背压 |
| 中断恢复 | 不支持 | 节点输出落库，断点续跑 |
| 进度感知 | 无 | SignalR 实时推送节点状态 |
| 日志聚合 | workflow_instance_id 虚关联 | taskCode 强关联 |

### 6.2 队列与引擎的协作模型

                   │         yzh_queue 表             │

### 6.3 节点级执行流程（WorkflowNodeExecutor）

```csharp
public class WorkflowNodeExecutor : IYzhTaskExecutor
{
    public string TaskType => "WF_NODE_EXEC";

    public async Task<TaskExecuteResult> ExecuteTaskAsync(YzhQueueTask queueTask)
    {
        var payload = JsonSerializer.Deserialize<NodeExecPayload>(queueTask.Payload);
        var task = await taskMgr.GetByCodeAsync(payload.TaskCode);
        var node = task.Config.FindNode(payload.NodeId);

        // ① 复用判定（§3.1）：确定性节点已有记录 → 读库，不重跑
        if (await outputStore.HasOutputAsync(task.Code, node.NodeId) && IsReusable(node))
        {
            var outputs = await outputStore.GetAllOutputsAsync(task.Code, node.NodeId);
            await logWriter.WriteAsync(task.Code, node.NodeId, 
                new { reused = true, outputs });
            await notifier.NotifyNodeCompleted(task.Code, node.NodeId, true, outputs);
            return BuildNext(queueTask, task, node, outputs);
        }

        // ② 解析输入（从 wf_node_output 读上游）
        var inputs = await outputStore.ResolveInputsAsync(task.Code, node.Inputs, task.WorkflowInputs);

        // ③ 执行节点（AI / Skill / 内置）
        var result = node.NodeType == "ai_node"
            ? await aiExecutor.ExecuteAsync(new AiNodeContext(inputs, task, node))
            : await skillExecutor.ExecuteSkill(node.SkillCode, new SkillContext(inputs, task.Code, node.NodeId));

        // ④ 落输出 + 写日志（含 token、分支决策）+ 推送
        await outputStore.SaveOutputsAsync(task.Code, node.NodeId, result.Outputs);
        await logWriter.WriteAsync(task.Code, node.NodeId, result);
        await notifier.NotifyNodeCompleted(task.Code, node.NodeId, result.Success, result.Outputs);

        return BuildNext(queueTask, task, node, result.Outputs);
    }

    /// <summary>统一路由核心：同步/异步共用（§3.3），返回下一节点集</summary>
    private TaskExecuteResult BuildNext(...)
    {
        var nextNodes = interpreter.ResolveNextNodes(task.Config, node.NodeId, outputs);
        if (nextNodes.Count == 0)
            return new TaskExecuteResult { IsCompleted = true, NextTaskType = "WF_END" };
        // 线路终结但还有其他未终结线路 → 继续推进（由解释器维护线路推进状态）
        return new TaskExecuteResult
        {
            IsCompleted = false,
            NextTaskType = "WF_NODE_EXEC",
            NextPayload = JsonSerializer.Serialize(new NodeExecPayload
            {
                TaskCode = task.Code,
                NodeIds = nextNodes.Select(n => n.NodeId).ToList()
            })
        };
    }
}
```

**可靠性机制（必须实现）**：
- **任务级看门狗**（§4.2）：任务长时间无节点完成事件 → 置 failed + 告警，防永久 running
- **断点续跑**：启动/重跑时扫描 `task_status in (failed,cancelled)` 的任务，根据 `wf_node_output` 已有记录跳过已完成节点，从断点继续
- **入队幂等**：同一节点任务重复入队时，以 `uk_task_node_port` 唯一键兜底，避免重复执行
- **失败分类**：基础设施/瞬态错误（LLM 超时、网络）→ 可重试；业务/配置错误（Skill 参数非法、校验失败）→ 不可重试，直接置失败

### 6.4 与现有 YzhQueueManager 对接

**现有能力复用**（`YzhQueueManager` / `YzhQueueTask`）：

| 现有机制 | 引擎使用方式 |
|---|---|
| 资源锁（resource_lock） | wf_execution_task 行级锁 + 并发队列隔离 |
| Semaphore 并发控制 | 限制同时执行的 NC 检查/报告数（workflow_execute 单独并发额度，避免拖垮 file_convert 等短任务）|
| 租约 + 超时回收 | 长时间未完成的节点任务自动释放 |
| 指数退避重试 | AI 节点调用失败重试（默认 3 次，退避 1s→2s→5s）|
| 取消 / 整队重跑 | 用户取消工作流执行（级联见 §4.2）|

> 澄清：TEST 模式**不是"不落任何库"**，而是"不写业务终态"。节点级执行记录照常落库，这样才能在画布上回查每次试运行的节点输入输出。
