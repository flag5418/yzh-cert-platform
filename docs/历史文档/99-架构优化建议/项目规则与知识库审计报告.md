### 2.2 建设原则 vs 实际实现问题（高优先级）

#### 问题 4: 实体基类使用不一致

**建设原则** (来自 `YZH-建设原则-V1.md` §2.4):
> `YZHBaseEntity` 仅提供最基础的审计字段，其他能力通过特性按需组合

**实际实现**:
```csharp
// 大部分实体继承 YZHBaseEntity ✅
public class CertificationBody : YZHBaseEntity { }
public class CertStage : YZHBaseEntity { }
public class ISOStandard : YZHBaseEntity { }

// 关联表继承 BaseEntity ❌
public class CertOrgStandard : BaseEntity { }  // 缺少审计字段
public class CertOrgStage : BaseEntity { }     // 缺少审计字段

// 配置表继承 BaseEntity ✅（符合"简单配置实体不需要完整审计"原则）
public class YzhPageConfig : BaseEntity { }
public class YzhFieldConfig : BaseEntity { }
```

**分析**:
- 关联表 `CertOrgStandard` 和 `CertOrgStage` 继承 `BaseEntity` 而非 `YZHBaseEntity`
- 这导致关联表缺少 `CreateID`、`Creator`、`CreateDate` 等审计字段
- 违反"所有实体应继承 YZHBaseEntity"的隐含约定

**建议**:
1. **方案 A（推荐）**: 为关联表创建轻量级审计基类
   ```csharp
   public class AuditBaseEntity : BaseEntity
   {
       public int? CreateID { get; set; }
       public string Creator { get; set; }
       public DateTime? CreateDate { get; set; }
       // ... 仅包含必要的审计字段
   }
   ```

2. **方案 B**: 修改关联表继承 `YZHBaseEntity`
   - 优点：统一性更好
   - 缺点：关联表不需要完整的审计字段（如 DeleteID、Deleter 等）

#### 问题 5: Service 层绕过

**建设原则** (来自 `YZH-建设原则-V1.md` §2.1):
> 通过特性声明"做什么"，而非在业务代码中写"怎么做"

**实际实现**:
```csharp
// OrgLinkController 直接操作 DbContext ❌
public class OrgLinkController : ApiBaseController<object>
{
    private readonly VOLContext _db;
    
    public IActionResult SyncOrgStandards([FromBody] SyncLinkRequest request)
    {
        var existingStdIds = _db.Set<CertOrgStandard>()...;  // 直接操作
        // ...
    }
}

// CertStageService 正确继承 ServiceBase ✅
public class CertStageService : ServiceBase<CertStage, ICertStageRepository>
{
    public override PageGridData<CertStage> GetPageData(PageDataOptions options)
    {
        // 使用 repository 操作
    }
}
```

**分析**:
- `OrgLinkController` 直接操作 `_db`，绕过了 Service 层
- 这导致无法使用 Service 层的权限检查、审计日志、缓存等功能
- 违反分层架构原则

**建议**: 已实施（Phase 4 已创建 `IOrgLinkService` 和 `OrgLinkService`）

#### 问题 8: 全局异常处理违反原则

**建设原则** (来自 `YZH-建设原则-V1.md` §2.3):
> 框架层面统一捕获和处理异常，上层业务代码禁止使用 try-catch 做业务判断

**实际实现**:
```csharp
// OrgLinkController.cs 中使用 try-catch ❌
try {
    // 业务逻辑
} catch (Exception ex) {
    Console.WriteLine($"[OrgLink.SyncStd] 异常: {ex}");
    return JsonNormal(new WebResponseContent().Error($"同步失败: {ex.Message}"));
}
```

**建议**: 
- 移除 Controller 中的 try-catch
- 让全局异常过滤器处理异常
- 只在 `OrgLinkService` 中使用 try-catch（如果确实需要）
