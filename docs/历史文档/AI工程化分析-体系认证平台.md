## 一、什么是AI工程化？（通俗解释）

### 1.1 传统软件开发 vs AI工程化

```
传统软件开发：
  你写代码 → 代码按照你写的逻辑运行 → 输出确定的结果
  
  特点：
  - 结果是确定的（同样的输入 → 同样的输出）
  - 测试容易写（预期结果固定）
  - 出bug好排查（堆栈跟踪明确）
  
示例：
  function add(a, b) { return a + b; }
  add(1, 2) 永远返回 3，不会突然返回 4

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

AI工程化（LLM应用）：
  你写Prompt/配置 → 调用AI模型 → AI"理解"你的意图 → 输出"智能"结果
  
  特点：
  - 结果是不确定的（同样的输入可能输出略有不同）
  - 测试难写（没有唯一正确答案）
  - 出bug难排查（是Prompt问题？数据问题？还是模型问题？）
  
示例：
  Prompt: "将这段口语转换为规范的审核NC描述"
  输入: "检验记录好像没签名"
  输出1: "成品检验记录存在未签署情况..."
  输出2: "在生产过程中发现检验记录缺少签字..."
  
  两个都对！但哪个更好？这需要评估。
```

### 1.2 为什么需要"AI工程化"？

```
❌ "调个API就行了"的误区：

   很多人以为：
     调用DeepSeek API → 得到结果 → 完事
   
   实际上生产环境会遇到：
     ✗ API调用失败怎么办？
     ✗ 返回结果质量不稳定怎么办？
     ✗ 用户输入包含敏感信息怎么办？
     ✗ 响应太慢用户体验差怎么办？
     ✗ 成本超支怎么办？
     ✗ 模型更新后行为变了怎么办？
     ✗ 如何知道AI是否在"胡说八道"？

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ AI工程化的正确定义：

   AI工程化 = 让AI能力在真实业务中
             稳定、可控、可观测、可优化地运行
   
   包含7个层次：
     L1 数据层      → 准备好"喂"给AI的数据
     L2 嵌入层      → 让计算机"理解"语义
     L3 检索层      → 找到最相关的知识
     L4 提示层      → 设计好"指令"
     L5 模型层      → 选择和调用AI模型
     L6 编排层      → 组合多个AI步骤
     L7 观测层      → 监控和评估效果
```

### 1.3 一个类比帮助理解

```
把AI系统想象成一家"智能餐厅"：

L1 数据层    = 食材仓库（菜谱、食材清单）
L2 嵌入层    = 食材分类系统（蔬菜/肉类/调料分类标签）
L3 检索层    = 配菜系统（根据客人需求找食材）
L4 提示层    = 菜谱卡片（告诉厨师怎么做这道菜）
L5 模型层    = 厨师（真正做菜的人）
L6 编排层    = 后厨流程（切菜→炒菜→摆盘的协作流程）
L7 观测层    = 顾客反馈+菜品质检（好不好吃？为什么？）

AI工程化的目标：
  确保每次端出来的菜都好吃（质量稳定）
  即使换了个厨师（换模型）味道也差不多（一致性）
  能根据顾客反馈改进菜谱（持续优化）
  知道哪道菜成本高、哪道菜耗时久（可观测）
```

### 3.2 各层职责详解

#### L1 数据层（Data Layer）

**职责**：存储和管理所有AI相关的数据

```
数据类型：
  
1. 结构化数据（PostgreSQL）
   ├─ 企业档案信息
   ├─ 审核任务数据
   ├─ NC记录
   ├─ 检查表填写结果
   └─ 用户操作日志
   
2. 非结构化/半结构化数据（MinIO对象存储）
   ├─ 上传的原始文件（PDF/图片/Word/Excel）
   ├─ OCR识别后的文本
   ├─ 语音录音文件
   ├─ AI生成的报告草稿
   └─ 企业上传的体系文件
   
3. 向量数据（向量数据库）
   ├─ ISO标准条款的嵌入向量
   ├─ 历史NC描述的嵌入向量
   ├─ 审核报告段落的嵌入向量
   └─ 企业文档的嵌入向量
   
4. Prompt训练数据（JSON/数据库）
   ├─ 优质的输入输出样本对
   ├─ 用户修正后的AI输出（作为新训练数据）
   └─ 不同场景的Prompt模板
```

#### L2 嵌入层（Embedding Layer）

**职责**：将文本转换为计算机能理解的向量表示

```
什么是嵌入（Embedding）？

  文本: "检验记录缺少签名"
       ↓ 通过嵌入模型
  向量: [0.12, -0.34, 0.56, 0.78, -0.23, ...]  （1536维或768维数字）
       
  为什么需要？
  - 计算机不"理解"文字，只理解数字
  - 语义相近的文字 → 向量距离近
  - 支持快速相似度搜索
  
  示例：
    "检验记录未签名"     → 向量A
    "检验单缺少签字人"   → 向量B  （与A距离很近，因为意思相近）
    "今天天气真好"       → 向量C  （与A距离很远，因为无关）
    
您的项目需要的嵌入能力：
  
  1. 标准条款嵌入
     - ISO 9001所有条款 → 嵌入向量
     - 用途：当审核员描述问题时，自动找到最相关的条款
     
  2. NC描述嵌入
     - 历史NC → 嵌入向量
     - 用途：发现类似的NC，辅助审核员判断
     
  3. 企业文档嵌入
     - 企业上传的文件 → 分块 → 嵌入向量
     - 用途：RAG检索，回答企业相关问题
```

#### L3 检索层（Retrieval Layer）

**职责**：从大量数据中快速找到最相关信息

```
检索方式对比：

1. 关键词搜索（传统）
   SQL: WHERE description LIKE '%检验%'
   ❌ 问题：找不到"检测""检查"等同义词
   
2. 向量语义搜索（AI工程化）
   Query: "产品出厂前没有做检验"
   → 转为向量 → 在向量空间中找最近的邻居
   ✅ 能找到："成品放行前缺少检验记录"（虽然用词不同但意思相近）
   
3. 混合搜索（推荐）
   关键词搜索 + 向量搜索 → 结果融合排序
   ✅ 兼顾精确匹配和语义理解
   
您的项目需要的检索能力：
  
  场景1：标准条款推荐
    输入: 审核员正在查看"生产车间"
    检索: 找到ISO 9001中关于"生产和服务提供"的条款
    
  场景2：历史NC查找
    输入: 新发现的问题描述
    检索: 找到历史上类似的NC（看看别人怎么写的）
    
  场景3：企业文档检索（RAG）
    输入: "这个企业的质量目标是什么？"
    检索: 从企业上传的质量手册中找到相关段落
```

#### L4 提示层（Prompt Layer）

**职责**：设计和管理工作交给AI的"指令"

```
什么是Prompt Engineering（提示工程）？

  好的Prompt:
    ```
    你是一位资深ISO 9001审核员，有15年审核经验。
    
    请将以下口语化的审核发现，转换为规范的不符合项(NC)描述。
    
    要求：
    1. 使用专业审核术语
    2. 明确指出不符合的具体事实
    3. 引用可能相关的ISO 9001:2015条款号
    4. 区分客观事实和主观推断
    
    审核活动类型：现场巡视
    审核部门：生产部
    发现时间：2026-08-15 14:30
    
    原始记录：{user_input}
    
    请直接输出NC描述，不要其他解释。
    ```
    
  不好的Prompt:
    ```
    把这段话改成正式的：{user_input}
    ```

Prompt管理的复杂性：
  
  1. 版本管理
     - Prompt v1.0 效果不好 → 修改为 v1.1
     - 需要能回滚、对比不同版本的效果
     
  2. 变量插值
     - Prompt中有动态部分（如{user_input}、{activity_type}）
     - 需要安全的变量替换机制
     
  3. A/B测试
     - 同时运行两个版本的Prompt
     - 统计哪个版本的用户满意度更高
     
  4. 场景化
     - 报告生成用一套Prompt
     - NC描述用另一套Prompt
     - 问答系统又用一套Prompt
```

#### L5 模型层（Model Layer）

**职责**：选择和管理AI模型

```
模型选择策略：

1. 主力模型（付费API）
   ├─ DeepSeek-V3 / DeepSeek-Coder
   │   ├─ 优势：中文能力强、价格便宜、支持长上下文
   │   └─ 适用：报告生成、NC描述增强、通用问答
   │
   ├─ 通义千问（Qwen-Max）
   │   ├─ 优势：阿里生态、国内访问快
   │   └─ 适用：备选方案
   │
   └─ Claude 3.5 Sonnet（如果需要英文/复杂推理）
       ├─ 优势：长文本处理能力强
       └─ 适用：长报告生成（Phase 2考虑）

2. 专用模型（按需调用）
   ├─ OCR模型（腾讯云/百度云）
   │   └─ 用于证件识别、表格识别
   │
   ├─ STT模型（讯飞/阿里云）
   │   └─ 用于语音转文字
   │
   └─ 嵌入模型（OpenAI / 本地部署）
       └─ 用于文本向量化

3. Fallback机制
   主力模型失败 → 自动切换备用模型
   例：DeepSeek超时 → 尝试通义千问 → 都失败 → 返回错误提示

模型路由器设计：
  
  Input: 任务类型 + 优先级 + 预算限制
  ↓
  Router: 选择最优模型
  ↓
  Output: API调用 + 结果返回
  
  路由规则示例：
    IF task == "report_generation" AND budget_ok:
        USE deepseek-v3 (temperature=0.7)
    ELIF task == "ocr_business_license":
        USE tencent-cloud-ocr (model=general)
    ELIF task == "embedding":
        USE bge-large-zh (local)
    ELSE:
        USE qwen-max (fallback)
```

#### L6 编排层（Orchestration Layer）

**职责**：组合多个AI步骤，形成完整的业务流程

```
编排模式对比：

1. 简单链式（Sequential）
   用户上传文件 → OCR提取文字 → LLM分析 → 生成报告
   适合：轻量路径
   
2. 条件分支（Conditional）
   IF OCR置信度 < 80%:
       请求人工确认
   ELSE:
       自动进入下一步
   适合：关键数据的OCR
   
3. 并行执行（Parallel）
   ├── 任务A：OCR识别营业执照
   ├── 任务B：OCR识别组织机构代码证
   └── 任务C：OCR识别ISO证书
   → 合并结果
   适合：批量证件识别
   
4. 循环迭代（Loop/Refinement）
   LLM生成初版报告
   → 用户修改
   → LLM根据修改重新生成
   → 直到用户满意
   适合：报告编写（PC端场景）
   
5. Agent模式（自主决策）⭐ Phase 2-3
   AI Agent自主决定：
   - 需要调用哪些工具（OCR/搜索/数据库查询）
   - 是否需要人工介入
   - 当前的最佳下一步行动

您的项目需要的编排场景：

  场景1：轻量路径（一键生成报告）
  ┌─────────────────────────────────────────────┐
  │ Start                                         │
  │   ↓                                          │
  │ [上传文件]                                    │
  │   ↓                                          │
  │ [并行] ─┬─ OCR通用文字                      │
  │         ├─ OCR表格识别                      │
  │         └─ OCR证件结构化                    │
  │   ↓                                          │
  │ [合并结果]                                   │
  │   ↓                                          │
  │ [LLM: 分析资料完整度]                        │

#### L7 观测与评估层（Observability & Evaluation）

**职责**：监控AI系统的表现，持续改进

```
需要观测的指标：

1. 技术指标（系统健康度）
   ├─ API调用成功率（目标 >99%）
   ├─ 平均响应时间（目标 <3秒）
   ├─ P95/P99延迟（了解尾部性能）
   ├─ 错误率（按错误类型分类）
   └─ Token消耗量（成本控制）

2. 质量指标（AI输出质量）
   ├─ OCR准确率（字符级/字段级）
   ├─ STT字错误率（WER）
   ├─ LLM输出满意度（用户评分/采纳率）
   ├─ 幻觉率（Hallucination Rate，AI编造信息的比例）
   └─ 格式合规率（输出是否符合预期格式）

3. 业务指标（实际价值）
   ├─ AI功能使用率（多少用户用了AI功能）
   ├─ 用户编辑率（AI输出后用户修改的比例）
   ├─ 时间节省（使用AI前后对比）
   └─ 成本效益（AI带来的效率提升 vs API费用）

评估方法：

1. 自动化评估（适合回归测试）
   ├─ 使用"金标准"数据集（已知正确答案的数据）
   ├─ 对比AI输出与金标准的差异
   └─ 例：100条已知NC描述 → AI增强 → 对比人工写的版本

2. AI-as-Judge（AI评估AI）
   ├─ 用更强的模型（如GPT-4）来评估弱模型的输出
   ├─ 设定评估维度和打分标准
   └─ 成本较低，可大规模运行

3. 人工评估（最准确但成本高）
   ├─ 邀请审核员专家对AI输出打分
   ├─ 适用于重要场景（如报告生成）
   └─ 建议每月抽样评估一次

用户反馈闭环：

  用户使用AI功能
    ↓
  系统记录：原始输入 + AI输出 + 用户是否修改 + 修改了什么
    ↓
  分析：用户最常修改什么？（提示Prompt改进方向）
         哪类输入效果最好？（积累优质样本）
         哪类输入效果差？（需要特殊处理）
    ↓
  持续改进：更新Prompt / 调整模型参数 / 积累训练数据
```

       ]
       
     - name: "ocr_service"

       fallback: [
         {provider: "baidu_cloud", model: "general_ocr"}
       ]
       
     - name: "stt_service"
       condition: {task_type: "stt"}
       primary: {provider: "xunfei", model: "realtime_asr"}
       fallback: [
         {provider: "alibaba_cloud", model: "paraformer-v2"}
       ]
       
     - name: "embedding"
       condition: {task_type: "embedding"}
       primary: {provider: "local", model: "bge-large-zh"}
       fallback: []  # 嵌入通常不需要远程fallback

3. 成本控制
   features:
     - 每月预算上限（按机构设置）
     - 单次调用Token限制
     - 超预算时的降级策略（使用更便宜的模型 or 暂停非必要AI功能）

   implementation:
     - 每次API调用前检查剩余预算
     - 记录每次调用的Token数和费用
     - 按日/周/月聚合统计
     - 超限时返回友好提示而非报错

4. 重试机制
   policy:
     - 最大重试次数：2次
     - 重试间隔：指数退避（1s → 2s → 4s）
     - 可重试错误：超时、限流(429)、服务暂时不可用(503)

## 附录：AI工程化术语速查表

| 术语 | 英文 | 通俗解释 | 您的项目中的对应 |
|------|------|---------|------------------|
| **嵌入** | Embedding | 文本→向量，让计算机理解语义 | L2层：将标准条款转为向量 |
| **RAG** | Retrieval-Augmented Generation | 先检索相关知识，再让AI基于知识回答 | 用企业文档辅助回答问题 |
| **Prompt Engineering** | 提示工程 | 设计给AI的"指令"，让它输出更好的结果 | L4层：报告生成的Prompt模板 |
| **Few-Shot Learning** | 少样本学习 | 在Prompt中给几个示例，AI照着做 | Prompt中附带优秀NC范例 |
| **Temperature** | 温度参数 | 控制AI输出的随机性（0=确定性，1=创造性） | 报告生成用0.5，事实提取用0.2 |
| **Token** | 词元 | AI计费的基本单位（中文约1.5字=1Token） | 成本控制的核算单位 |
| **Context Window** | 上下文窗口 | AI一次能处理的文本长度限制 | DeepSeek支持64K+，足够长 |
| **Fine-tuning** | 微调 | 在预训练模型基础上，用私有数据继续训练 | Phase 3：用历史审核数据微调 |
| **Hallucination** | 幻觉 | AI编造不存在的信息（"一本正经胡说八道"） | 需要检测和避免 |
| **Vector Database** | 向量数据库 | 专门存储和检索向量的数据库 | 存储标准条款和企业文档的向量 |
| **Chunking** | 分块 | 将长文档切成小块，便于嵌入和检索 | 质量手册按章节分块 |
| **Reranking** | 重排序 | 对检索结果重新排序，提高精度 | 先检索20条→重排序→取Top5 |
| **Orchestration** | 编排 | 组织多个AI步骤形成完整流程 | 轻量路径的OCR→分析→报告流程 |
| **Agent** | 智能体 | 能自主决定调用什么工具的AI系统 | Phase 3：自主决定下一步做什么 |
| **A/B Testing** | A/B测试 | 同时运行两个版本，比较效果 | 测试不同Prompt版本的效果 |
| **Observability** | 可观测性 | 监控系统内部状态，了解发生了什么 | 监控AI调用的成功率和质量 |
| **Fallback** | 降级/备选 | 主方案失败时自动切换备用方案 | DeepSeek挂了→切换通义千问 |
| **Rate Limiting** | 速率限制 | 控制API调用频率，避免超限或超支 | 控制每用户每天最多调用几次 |
| **Guardrails** | 护栏 | 防止AI输出有害/不当内容的机制 | 防止AI输出敏感信息 |

```

### 核心建议

1. **不要被AI工程化的复杂性吓到** —— Phase 0只需要做好接口抽象和Prompt模板
2. **先让一个场景跑通** —— 推荐"AI增强语音转文字"或"轻量路径"作为第一个AI场景
3. **Prompt是核心资产** —— 花时间打磨Prompt比换模型更重要
4. **数据是长期护城河** —— 从第一天就开始收集用户反馈和AI输出数据
5. **成本意识要有** —— 设置预算上限，避免意外超支
