# yzh-core 架构改进意见书

- 版本：v1.0
- 日期：2026-09-06
- 评审对象：`src/yzh-core`（Stand / DataBase / Api / Web 四工程）
- 对照基线：`/Volumes/Expand/wangqingquan/Downloads/LANDrop/YZH架构`（多年运行老架构）
- 评审基准：以设计者的核心理念为准绳，而非以"通用框架应该长什么样"为准

---

## 一、评审基准（设计者核心理念确认）

本次评审以以下理念作为判定"是否问题"的标尺，避免误伤合理设计：

1. **yzh.core 是"与项目无关"的通用底座**：用户/权限/菜单/角色/组织结构等是所有项目都需要的公共基建，内置框架是合理方向（参照 ABP/Vol 成熟实践），不算业务耦合。
2. **双关键字（Id + Code）是实体核心**：Id 面向存储（GUID 主键，规避自增 id 跨环境迁移错乱），Code 面向业务关联（改名/改结构不影响既有关联）。**一切跨表关联应以 Code 为锚**。
3. **业务工程仅是临时挂接宿主**：用于编译联调的集成宿主，物理上必须与框架核心分离，框架库工程本身保持 0 业务引用。
4. **原子核心能力 + 泛型基类控制器**：单表基类控制器（完整生命周期 + 可扩展 + 继承即用）是区别于 Vol 的核心设计，后续扩展主从表等基类控制器。
5. **实体缓存自适应**：通过基类特性配置自动完成缓存，提高运行效率。
6. 老架构（dynamic + 自增 xh + code 主键 + 单例 Chloe）已被本架构（强类型泛型 + EF Core + GUID）**继承性升级**，改进方向正确。

## 二、分级改进意见

### P0 — 正确性阻断项（建议优先修复）

#### P0-1 底座 Sys_User 背老表结构 + int 关联，违反双关键字理念

- **位置**：`YZH.Core.Api/Models/Users/Sys_User.cs`
- **问题**：
  - `RoleId` 为 int，关联老 Sys_Role 自增主键——不是用 Code/GUID 关联；
  - 以 `new int? CreateId / new DateTime? CreateDate / new string? Creator / new int? ModifyId / new DateTime? ModifyDate / new string? Modifier` 覆盖基类审计字段，列名沿用 Vol 老库 snake_case；
  - 底座实体是"新壳装老心"，新项目复用即被拉回 int 关联与老列名体系，跨环境迁移仍会踩 id 不一致陷阱。
- **改进**：
  - 审计列删除全部 `new` 覆盖，统一走 BaseEntity 的 `CreateTime/CreateBy/UpdateTime/UpdateBy/DeleteTime/DeleteBy`；
  - 角色关联改 `RoleCode`（string）或 GUID `RoleId`，与 Sys_Role 的 Code 对应；
  - snake_case 物理列名交由 EF `HasColumnName` 或统一约定映射，不在实体层造列。

#### P0-2 DeleteBatch 在事务提交后执行 int.Parse(GUID)，必抛异常

- **位置**：`YZH.Core.Api/Services/EntityService.cs` ~L349
- **代码**：`_auditLogger.LogBatchDelete<T>(idList.ConvertAll(x => int.Parse(x)), ctx);`
- **问题**：新版 Id 为 GUID 字符串，`int.Parse` 必然抛 `FormatException`；且该行位于事务提交之后、缓存失效之前——数据已删、接口报 500、缓存未清。属老架构（int xh）升级漏改。
- **改进**：
  - 审计日志接口改为接收 string id 列表（`IEnumerable<string>` / `IReadOnlyList<string>`）；
  - 调整顺序为：事务提交 → 清缓存 → 记录审计 → 返回成功，任何一步失败都要有兜底（缓存清理不得因审计异常而跳过）。

#### P0-3 泛型基类构造函数内调用虚方法（OnRegisterDicts）

- **位置**：`YZH.Core.Api/Controllers/SingleTableController.cs` 构造函数
- **问题**：子类构造函数体尚未执行完即触发虚方法，若子类覆写依赖自身字段（如 `_db`/服务字段），必 NRE 或拿空数据。
- **改进**：构造函数只做依赖注入；`OnRegisterDicts()` 改为首次访问时的惰性初始化（Lazy / 状态位 / 由中间件或首个请求触发），或文档明确约定"覆写不得依赖自身构造完成的字段"并加代码注释警示。

#### P0-4 密码可逆存储 + 固定 Key/IV

- **位置**：`YZH.Core.Stand/Helpers/PasswordHelper.cs`
- **问题**：AES 可逆加密存储密码，Key 固定截 16 字符、IV 固定 `0x00~0x0F`、无盐；数据库泄露即全部口令可还原。作为 Vol 老数据兼容层可保留，但**新底座与后续项目不得再用于新密码**。
- **改进**：
  - 新写密码一律 PBKDF2（Rfc2898DeriveBytes）/ BCrypt / Argon2 加盐哈希；
  - 老数据提供一次性迁移任务：登录成功时用 VerifyAes 校验通过后改写为哈希并标记已迁移；
  - 明确 `PasswordHelper.AesEncrypt` 标 `[Obsolete]` 或在注释中限定"仅老数据兼容"。

#### P0-5 宿主硬编码密钥/口令，连接串含高危选项

- **位置**：`YZH.Core.Web/Program.cs`、`YZH.Core.Web/appsettings.json`
- **问题**：
  - 数据库口令 `Yzh123456.`、JWT SecretKey `AA36...`、PasswordSecret `C5AB...` 明文入库并带代码 fallback；
  - 连接串含 `AllowLoadLocalInfile=true`（MySQL 可读客户端本地文件的高危项）、`sslmode=none`。
- **改进**：
  - 密钥口令全部移入环境变量 / 用户机密（`dotnet user-secrets`）/ 密钥管理服务；
  - 代码删除明文兜底，缺失即启动失败（fail-fast）；
  - 连接串删除 `AllowLoadLocalInfile`，生产开启 SSL。

#### P0-6 软删除只打标、查询不拦截

- **位置**：`YZH.Core.DataBase/BaseRepository.cs`（全文件无 IsDeleted 过滤）
- **问题**：EntityService 软删置 IsDeleted 后，GetPage/GetList/Count/GetById 仍能查到"已删"记录。
- **改进**：在 DbContext 层为继承 BaseEntity 的实体统一配置 EF Core 全局查询过滤器（`HasQueryFilter(e => !e.IsDeleted)`），一次配置全局兜底；硬删实体（标注 `YZHDeleteStrategy(Hard)`）不套用该过滤器。仓储层删除手工过滤逻辑依赖。

### P1 — 架构收敛与重要改进

#### P1-1 双轨用户体系收敛（老实体 vs 新底座）

- **位置**：Web 宿主 6 控制器（Auth/Sys_User/ISOClause/Menu/SysDictionary/SysMenu）全部手写 `ControllerBase`，无一继承 `SingleTableController`；`YZH.Core.Api/Models/Users/Sys_User`（GUID）与老 YZH.Entity Sys_User（int）并存。
- **问题**：新基类控制器没有任何真实消费方，框架能力空转、验证闭环缺失；平台实际跑的是老套实现。
- **改进**：选 1~2 个真实业务/底座控制器（推荐 Sys_User + 一个业务单表）改为继承 `SingleTableController`，作为首批验证用例，让"继承即用"被真实接口检验后再铺开。

#### P1-2 三套控制器基类收敛

- **位置**：`BaseController` / `PageBaseController` / `SingleTableController`
- **问题**：功能逐步演进造成堆积，新项目易继承错对象。
- **改进**：确立 SingleTableController 为唯一单表基类；其余标注 `[Obsolete]` 并给迁移提示；迁移期结束后删除。

#### P1-3 事务双实现 + saveChanges 语义冲突

- **位置**：`WorkUnit` 与 `BaseRepository.ExecuteInTransaction`；`EntityService.Insert/Update` 默认 `saveChanges: true`
- **问题**：WorkUnit 约定回调内 saveChanges:false、外层统一提交；但 EntityService 单条写默认 true 会提前提交；两套并存使事务边界不可预期。
- **改进**：明确唯一事务模型（建议保留仓储级 `ExecuteInTransaction`，WriteUnit 语义收敛为文档化约定）；设计主从表基类时，提供"组合写单元"接口，保证多表写同事务、钩子按 SaveContext 三阶段触发；单条写保持自提交、批量写统一入事务并**统一在事务外清缓存**。

#### P1-4 审计链路统一

- **位置**：BaseRepository（只填时间）/ EntityService（填人 + 时间）/ 底座 Sys_User（new 一套 snake_case 审计列）
- **问题**：直用仓储丢审计人；实体可 new 覆盖审计字段造成双写混乱。
- **改进**：审计填充收敛到 EntityService/保存管道统一完成，仓储不碰审计；实体禁止覆盖基类审计列（可加 Analyzer/约定约束）；`RowVersion` 若保留乐观锁需配置 `IsConcurrencyToken`，否则字段空转。

#### P1-5 缓存链路补齐

- **位置**：`YZH.Core.Api/Services/CacheManager.cs`、`EntityService.cs`、`YZH.Core.Stand/Attributes/CacheEntityHelper.cs`
- **问题**：
  - `CacheEntityHelper` 注释"默认启用缓存"，实际无特性时 `Enabled=false`，注释与行为矛盾；
  - 批量写路径（InsertBatch/UpdateBatch/DeleteBatch 软删）绕过 EntityService 清理逻辑，仅靠末尾 `InvalidateEntity` 兜底，中途异常即残留；
  - GetOrAdd 无防击穿/防穿透处理（可后续优化）。
- **改进**：修正注释；批量写统一在事务成功后调 `InvalidateEntity<T>`；删除/写操作以 try-finally 保证清缓存不被审计异常中断；高并发场景补充单飞（single-flight）或信号量防击穿。

#### P1-6 控制器默认授权缺失

- **位置**：`SingleTableController`、Web 各控制器均未见 `[Authorize]` 类级标注
- **问题**：鉴权完全依赖宿主手动配置，任何一个新控制器漏配即匿名可访问。
- **改进**：框架基类类级默认 `[Authorize]`；登录/健康检查等公开接口用 `[AllowAnonymous]` 显式放行；宿主 Program 保留全局鉴权策略作为第二道闸。

#### P1-7 JWT 体系与 GUID 底座对齐 + 刷新机制

- **位置**：`YZH.Core.Stand/Helpers/JwtHelper.cs`（`GenerateToken(int userId, int? roleId)`、默认 30 天）
- **问题**：subject/角色仍按 int 设计，与 GUID 底座矛盾；无刷新令牌；单角色不够支撑菜单/数据权限。
- **改进**：subject 传 GUID 用户 Id；角色改 claim 列表（`ClaimTypes.Role` 多次添加）；引入 refresh token 或缩短有效期 + 滑动续期；将 userId/roleId 类型切换列入底座改造联动清单。

#### P1-8 反射行操作接口收紧

- **位置**：`SingleTableController.ExecuteAction`
- **问题**：按前端 methodName 反射调用，靠 Config 字符串白名单隐式放行；若 Config 可被篡改或方法名疏漏，存在越权执行风险。
- **改进**：改为显式 `[Action(name)]` 特性注册（方法级声明），反射仅针对带特性方法；白名单来源从 Config 解耦为特性元数据；鉴权下沉到方法级。

#### P1-9 宿主引用与 Program.cs 自举

- **位置**：`YZH.Core.Web.csproj`（挂 Vol 三工程 + certplatform-api 四工程）、`Program.cs`（手写接线，`YzhWebBuilder.UseYzhCore/UseYzhPipeline/UseYzhDatabase` 未调用）
- **问题**：临时挂接写进正式 csproj 长期留在主分支；框架自身接线扩展闲置，宿主未成为框架能力示范。
- **改进**：业务挂接整体移入 `samples/` 或独立解决方案；宿主 Program.cs 改为调用 YzhWebBuilder 一行接线（配好即用），业务差异配置走 appsettings + 扩展点；从宿主角度验证框架"拿来即用"。

### P2 — 整洁与完善

#### P2-1 结果/请求模型收敛

- ApiResponse / IOperationResult / OperationResult / RepoResult / TxResult → 收敛为 1 套响应 + 1 套仓储结果；
- PageRequest / PageRequestModel / VolPageRequest / PageRequestBody 统一；**PageRequest 等模型类不要内嵌在 SingleTableController.cs 文件中**，移入 Stand/Models 或独立 Models 文件。

#### P2-2 GridConfig 三处并存收敛

- Stand `GridConfig.GetGridConfig<T>`、Api `GridConfigController`（读 XML）、`GridConfigLoader.FromXml` → 收敛为 ConfigLoader 单一加载链路 + 缓存；JSON（sys_user_list.json）与 XML 两套来源选一或定义统一适配。

#### P2-3 时间与注释一致性

- 时间基准：已统一 UtcNow（BaseRepository/EntityService），继续遵守并写入编码约定；
- `UserContext.cs` 存在重复 `using System.Security.Claims;`，清理；
- CacheEntityHelper / 各类注释与默认值对齐（P1-5 已列）。

#### P2-4 IP 审计防伪造

- `UserContext.ClientIp` 信任 X-Real-IP/X-Forwarded-For：明确仅在部署可信代理（Nginx/网关）时生效，提供配置开关；否则回退 RemoteIpAddress。

#### P2-5 空目录与示例填充

- `YZH.Core.Api/Controllers/Examples/` 为空目录：要么提供真实示例（推荐：一个完整单表控制器示例 + 注释中的伪代码落成真实可编译代码），要么删除占位。
