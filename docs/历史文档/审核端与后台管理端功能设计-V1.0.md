# 体系认证平台 —— 审核端 & 后台管理端 功能设计

> **版本**：V1.0 | **日期**：2026-07-28
>
> **定位**：本文档仅描述「审核端」和「后台管理端」两个 PC Web 端的功能点设计与 UI 建议。
>
> **前提确认**（用户已确认）：
> - 技术栈：.NET Core + Vue 3 + MySQL + MinIO
> - 不做移动端，纯 PC Web 端
> - AI 工作流采用开源方案（Dify / n8n），不自研引擎
> - 核心模型：以企业为中心

---

## 一、整体架构概览

### 1.1 两端划分

| 端 | 用户 | 定位 | 核心职责 |
|----|------|------|---------|
| **审核端** | 审核员 / 认证机构人员 | 业务操作前台 | 企业管理 → 阶段规划 → 执行审计/报告任务 |
| **后台管理端** | 系统管理员 | 配置与运维 | 规则配置、模板管理、标准库维护、字典管理、系统参数 |

### 1.2 核心业务模型

```
企业 (Enterprise)
  ├── 基本信息（名称、联系人、认证范围）
  ├── 文件目录（企业上传的资料，支持版本历史）
  ├── 阶段列表（初审S1 → 初审S2 → 一监 → 二监 → ...）
  │   └── 每个阶段下：
  │       ├── 🔍 审计任务（可新建多个）
  │       │   └── 状态：排队中 → 执行中 → 完成
  │       └── 📄 报告任务（可新建多个）
  │           └── 状态：排队中 → 执行中 → 完成
  └── 归档状态：待执行 / 已归档（可取档重新激活）
```

**关键交互**：

| 操作 | 说明 |
|------|------|
| 上传文件 | 支持拖拽上传、批量上传；自动计算 SHA-256；识别 MIME 类型 |
| 新建文件夹 | 在当前目录下创建子文件夹 |
| 版本历史 | 点击文件可查看所有历史版本，对比差异，回滚到某版本 |
| 预览 | PDF/图片/Word 在线预览（无需下载） |
| 标签 | 可给文件打标签（如"QMS手册"、"程序文件"），便于筛选 |

#### 2.2.6 NC 管理页

**功能目标**：NC 全生命周期管理与整改跟踪。

**UI 建议**：列表 + 详情抽屉/弹窗模式。

**NC 列表字段**：

| 字段 | 说明 |
|------|------|
| NC 编号 | 自动生成，如 NC-2026-001 |
| 严重度 | 🔴 Major / 🟡 Minor / 🔵 Observation |
| 关联条款 | 如 7.2.1 能力 |
| 描述 | 不符合事实描述（来自审计任务）|
| 状态 | 开启 → 整改中 → 待验证 → 已关闭 |
| 到期日 | 整改截止日期 |
| 负责人 | 企业对接人 |

**NC 详情包含**：
- NC 基本信息
- 关联证据列表
- 整改记录时间线（含版本追溯）
- 审核员验证操作（通过/退回）

### 4.2 核心 AI 场景设计

#### 场景 1：OCR 智能录入

```
触发: 用户上传文件（PDF/图片/照片）
  │
  ▼
[Dify 工作流]
  ├─ Step 1: 文件类型识别（是证件？表格？文档？）
  ├─ Step 2: 调用 OCR API 提取文字
  ├─ Step 3: 结构化解析（按模板提取关键字段）
  └─ Step 4: 返回结构化数据 → 自动填入对应字段

示例:
  上传: 营业执照照片
  输出: { 企业名称: "XX公司", 统一信用代码: "91xxx", 法人: "张三", ... }
```

#### 场景 2：报告一键生成

```
触发: 用户在报告页点击 "AI 生成"
  │
  ▼
[Dify 工作流]
  ├─ Step 1: 收集审计数据（检查表结果 + NC 列表 + 证据摘要）
  ├─ Step 2: 选择对应的 Prompt 模板
  ├─ Step 3: 构造 Prompt（注入审计数据作为上下文）
  ├─ Step 4: 调用 LLM（DeepSeek / 开源模型）
  ├─ Step 5: 后处理（格式化为报告结构）
  └─ Step 6: 返回报告初稿 → 展示在编辑器中

注意: AI 生成的是"初稿"，审核员必须复核确认后才算正式报告。
```

#### 场景 3：NC 智能辅助

```
触发: 审核员开具 NC 时
  │
  ▼
[Dify 工作流]
  ├─ Step 1: 接收 NC 草案（条款 + 事实描述）
  ├─ Step 2: LLM 增强（规范化表述、补充标准引用建议）
  ├─ Step 3: 严重度建议（基于历史数据和条款重要性）
  └─ Step 4: 返回增强后的 NC 文本供审核员参考采纳
```

### 4.3 开源工作流集成要点

| 维度 | 说明 |
|------|------|
| **选型** | Dify（可视化编排强）或 n8n（自动化流程强），Phase 1 先跑通 Dify |
| **集成方式** | .NET Core 通过 HTTP API 调用 Dify/n8n 的工作流接口 |
| **Prompt 管理** | Prompt 模板存储在数据库，通过 API 注入到工作流 |
| **降级策略** | AI 服务不可用时，系统仍可正常运行（手动填写），只是缺少智能辅助 |
| **成本可见** | 每次 AI 调用记录 Token 消耗和费用，后台可查看统计 |

## 六、我的理解确认

以上是我对您当前设计的理解，核心要点如下：

### ✅ 我理解的审核端核心逻辑

1. **企业是一切的中心** — 进入系统先看到企业列表，不是任务列表
2. **企业有生命周期** — 通过"阶段"表达（初审→监督→再认证），不是一次性的
3. **审计和报告是两类独立的任务** — 都挂在阶段下面，各自有排队→执行→完成的流程
4. **文件目录是企业级资产** — 不是属于某个任务的，企业可以随时更新，有版本历史
5. **归档是企业维度的** — 一个企业的所有阶段都完成了才算归档，取档后可以继续新的审核周期

### ✅ 我理解的 AI 设计思路

1. **不自研 AI 引擎** — 用 Dify/n8n 这类开源平台做编排
2. **AI 是辅助而非替代** — 审核员始终是决策者，AI 帮忙做提取、生成、增强
3. **核心价值链** — 资料上传 → OCR 提取 → 规则校验 → AI 分析 → 报告生成
4. **规则即资产** — File Checklist 是核心竞争力，要做成可配置的平台化能力

### ❓ 需要与您确认的点

1. **审核端的左侧导航** — 您倾向于顶部 Tab 切换还是左侧固定菜单？
2. **审计任务的"排队"机制** — 是自动排队还是手动触发执行？
3. **企业端的上传权限** — 企业可以上传任意目录的文件，还是只能上传指定目录？
4. **报告生成后是否需要审批流程** — 还是直接生成即可？
