## 二、与总体设计-V3 的关系

### 2.1 总体设计中的 FileRepository

总体设计 V3.0 定义了 `FileRepository` 作为核心证据库：

```sql
CREATE TABLE file_repositories (
    id CHAR(36) PRIMARY KEY,
    enterprise_id CHAR(36) NOT NULL,
    parent_id CHAR(36),          -- 父节点（NULL 表示根目录）
    name VARCHAR(200) NOT NULL,
    type ENUM('folder', 'file') NOT NULL,
    file_path VARCHAR(500),      -- MinIO 路径（type=file 时）
    file_size BIGINT,
    file_hash VARCHAR(64),
    mime_type VARCHAR(100),
    current_version INT DEFAULT 1,
    uploaded_by ENUM('auditor', 'enterprise'),
    tags JSON,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);
```

### 2.2 当前实现 vs 总体设计

| 维度 | 总体设计 V3.0 | 当前实现 | 差异分析 |
|------|--------------|---------|---------|
| 核心实体 | `FileRepository` | `EnterpriseDocument` + `EnterpriseFile` | **当前更细化** |
| 三维管理 | 企业维度 | 机构-标准-阶段维度 | **当前更精准** |
| 文件类型 | 统一字段 | 分离表结构 | **当前更清晰** |
| 编码规则 | 未定义 | 已定义完整编码体系 | **当前更规范** |

### 2.3 建议：对齐总体设计

**方案 A：保持当前实现（推荐）**
- 当前实现已在 V3.0 基础上做了细化
- `EnterpriseDocument` 对应 `FileRepository` 的 folder 类型
- `EnterpriseFile` 对应 `FileRepository` 的 file 类型
- 建议：在文档中明确这种对应关系

**方案 B：统一到 FileRepository**
- 将 `EnterpriseDocument` 和 `EnterpriseFile` 合并为 `FileRepository`
- 通过 `type` 字段区分文件夹和文件
- 优点：与总体设计完全一致
- 缺点：需要重构现有代码

**建议采用方案 A**，在文档中说明映射关系。

### 5.2 编码生成服务

```csharp
public class CodeGeneratorService : ICodeGeneratorService
{
    // 企业编码：EB-{日期}-{6位随机}
    public string GenerateEnterpriseCode()
    {
        var date = DateTime.Now.ToString("yyyyMMdd");
        var random = new Random().Next(100000, 999999);
        return $"EB-{date}-{random}";
    }

    // 文件夹编码：FD-{父编码}-{3位序号}
    public string GenerateFolderCode(string parentCode, int sequence)
    {
        return $"FD-{parentCode}-{sequence:D3}";
    }

    // 文件编码：FL-{FolderCode}-{文件名哈希}-{版本}
    public string GenerateFileCode(string folderCode, string fileName, int version)
    {
        var hash = ComputeFileNameHash(fileName);
        return $"FL-{folderCode}-{hash}-v{version}";
    }

    // 版本编码：VR-{FileCode}-{3位版本号}
    public string GenerateVersionCode(string fileCode, int versionNumber)
    {
        return $"VR-{fileCode}-v{versionNumber:D3}";
    }

    // 企业文档根编码：ED-{EnterpriseCode}-{Scope}-{ParentCode|ROOT}
    public string GenerateEnterpriseDocCode(string enterpriseCode, string scope, string parentCode)
    {
        var parent = string.IsNullOrEmpty(parentCode) ? "ROOT" : parentCode;
        return $"ED-{enterpriseCode}-{scope}-{parent}";
    }

    private string ComputeFileNameHash(string fileName)
    {
        // 取文件名前6位字符的哈希，确保唯一性
        var bytes = Encoding.UTF8.GetBytes(fileName);
        var hash = MD5.HashData(bytes);
        return Convert.ToBase64String(hash).Substring(0, 6).Replace('/', 'X');
    }
}
```

```

  → 允许同名，各自独立管理
```

### 6.3 前端拖拽处理代码

```javascript
// 拖拽处理
function handleDrop(event) {
  event.preventDefault()
  const items = event.dataTransfer.items
  const entries = []
  
  for (let i = 0; i < items.length; i++) {
    const entry = items[i].webkitGetAsEntry()
    entries.push(entry)
  }
  
  // 递归读取文件夹结构
  readEntries(entries).then(structure => {
    // 显示预览确认
    showDropPreview(structure)
  })
}

// 递归读取文件夹
async function readEntries(entries) {
  const result = { folders: [], files: [] }
  
  for (const entry of entries) {
    if (entry.isFile) {
      const file = await new Promise(resolve => entry.file(resolve))
      result.files.push({
        name: entry.name,
        size: file.size,
        type: file.type,
        path: entry.fullPath,
        lastModified: file.lastModified
      })
    } else if (entry.isDirectory) {
      const dirReader = entry.createReader()
      const children = await new Promise(resolve => 
        dirReader.readEntries(resolve)
      )
      const childStructure = await readEntries(children)
      result.folders.push({
        name: entry.name,
        path: entry.fullPath,
        ...childStructure
      })
    }
  }
  
  return result
}
```

## 七、与 NC 整改、报告生成的文件区别

### 7.1 三类文件的对比

| 维度 | 企业档案上传 | NC 整改上传 | 报告生成上传 |
|------|------------|------------|-------------|
| **来源** | 企业基础资料 / 阶段资料 | 企业提交整改证据 | 系统自动生成 |
| **位置** | EnterpriseDocument 树下 | NC 整改记录关联 | 报告任务输出 |
| **管理方式** | 树形目录管理 | NC 关联管理 | 任务关联管理 |
| **预览** | 完整树形浏览 | 列表浏览 | 列表浏览 |
| **权限** | 审核员 + 企业 | 仅企业提交 | 仅审核员 |
| **版本历史** | 支持 | 支持 | 不支持 |
| **提取规则** | 可配置 | 不适用 | 不适用 |
| **校验规则** | 可配置 | 简单校验 | 不适用 |

### 7.2 文件存储路径设计

## 十、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 文件夹树深度过大 | 查询性能下降 | 使用 PathCode 路径编码 + 缓存 |
| 大文件上传超时 | 用户体验差 | 设置合理的超时时间 + 进度条 |
| MinIO 存储不足 | 业务中断 | 配额管理 + 自动清理策略 |
| 并发上传冲突 | 数据不一致 | 乐观锁 + 版本号控制 |
| 编码冲突 | 数据错误 | 唯一索引 + 重试机制 |
