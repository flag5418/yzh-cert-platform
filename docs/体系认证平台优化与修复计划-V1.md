## 第 3 章 优化建议

> 本章只给方案，排期见第 4 章。

### 3.1 数据库字段不规范（DB-1 ~ DB-7）

#### 建议 1（DB-1，最高优先）：把 `all_tables_ddl.sql` 从"手工维护的基线"改为"从 live 库自动导出的产物"

**问题本质**：`all_tables_ddl.sql` 被当作"真源"人工维护，实际是快照。手工维护 96 表 × 2396 列的快照，注定过期——已过期 63 表。

**方案（三步，缺一不可）**：

| 步 | 动作 | 说明 |
|---|---|---|
| 1a | **立即重新导出**，并把生成命令写进文件头注释 | 用 `mysqldump --no-data --skip-comments --skip-add-drop-table` 导出，**排除** `z_deprecated_*`；文件头写明"⚠️ 本文件由 `scripts/db/dump-schema.sh` 生成，**禁止手工编辑**；修改表结构必须走 `scripts/db/` 迁移" |
| 1b | **新建 `scripts/db/dump-schema.sh`** | 唯一出口。带 `--check` 模式：重新导出到临时文件与库内文件 diff，不一致则非零退出（供 CI 用） |
| 1c | **建立"基线快照 vs 迁移历史"双文档** | `all_tables_ddl.sql` = 当前状态（自动生成）；`scripts/db/CHANGELOG.md` = 变更历史（人工写，但有固定模板） |

**配套铁律（写入 `项目全局规则.md`）**：
> 建表 / 改表 **只能**通过 `scripts/db/YYYYMMDD_<语义>_V<N>.sql` 迁移完成；`all_tables_ddl.sql` 是**只读导出产物**，任何手工编辑视为回潮，由守卫拦截。

**验收**：`bash scripts/db/dump-schema.sh --check` 返回 0；新库按 `all_tables_ddl.sql` + `CHANGELOG.md` 顺序执行后表集合 = live 表集合。

#### 建议 2（DB-2）：列宽统一到"按语义的固定档位"，并让 `BaseEntity` 标注与 DB 一致

**问题本质**：宽度不是"统一成一样"，而是"**同一语义必须同一档**"。当前 `Code` 有 4 档、`CreateBy` 有 5 档（含 1 个 `65535`，显然是误建）。

**方案：定档位表，然后收敛**

| 语义 | 建议档位 | 依据 |
|---|---|---|
| `Code`（业务键，GUID/雪花） | **36** | live 已有 68/95 表用 36，是事实标准；`BaseEntity` 自动生成逻辑已按 36 设计 |
| `*By`（审计人 Code） | **64** | 与 `BaseEntity.Code` 声明对齐；`50` 装不下 64 位 Code |
| `TaskStatus` / `ExecStatus` / `NodeType` 等枚举 | 20 / 30 | 保持现状，仅登记 |
| `PhaseCode` | **36** | `cert_phase_definition` 的 20 属遗留（其枚举是 `S1/S2/Surv1` 短码，但列名叫 `PhaseCode` 会与全局语义混淆）→ 建议**改名 `StageCode`** 或统一 36 |

**关键动作：把 `BaseEntity` 的 `[StringLength]` 标注改为与 DB 一致（Code: 64→36）**——当前标注是错的，会误导所有新代码生成 64 位 Code 写入 36 位列（MySQL 严格模式直接报错，非严格模式静默截断）。这是"实体标注自证清白、DB 不是"铁律的活案例。

**执行方式**：**只改宽度、不改列名**（避免与已完成的 snake→Pascal 收口冲突）。用 `ALTER TABLE ... MODIFY` 逐表，只放宽不收窄（收窄需先验证存量数据长度）。

**验收**：`verify_naming.sql` 新增"列宽一致性"检查，`Code` 全部 36、`*By` 全部 64，0 违规。
