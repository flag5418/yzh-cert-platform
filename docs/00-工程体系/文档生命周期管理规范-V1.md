# 文档生命周期管理规范

> **定位**：定义项目中每一份文档的三种状态及其流转规则。解决"文档太多不知道哪些该维护、哪些该归档"的核心痛点。
>
> **核心原则**：一份文档在"被需要"之前，保持萌芽态即可。不要提前完善。

---

## 一、三级生命周期

```
萌芽态 (Seed)              成熟态 (Mature)              归档态 (Archived)
─────────────              ───────────────              ────────────────
- 快速记录想法              - 深度完善细节                - 已完成历史使命
- 允许模糊                  - 对齐宪法                    - 不再修改
- 允许矛盾                  - 标注依赖关系                - 移入 历史文档/
- 允许不完整                - 补充遗漏                    - 保留索引引用
- 文件名无版本号            - 文件名含版本号

      │                          │                          │
      │   时机到了                 │   功能已交付               │
      │   ──────────→            │   ──────────→            │
      │   准备开发此模块时         │   或设计已被推翻           │
      │                          │                          │
      └──────────────────────────┴──────────────────────────┘
```

---

## 二、状态判定标准

### 2.1 萌芽态判定

符合以下**任意一条**即为萌芽态：

- [ ] 内容是"一闪而过的想法"，没有经过反复推敲
- [ ] 没有与其他文档交叉校验矛盾
- [ ] 缺少量化数据（QPS/数据量/成本估算）
- [ ] 未对齐宪法（如使用的技术栈名称不一致）
- [ ] 缺少具体实现细节（只有方向，没有步骤）
- [ ] 文件名无版本号

### 2.2 成熟态判定

以下条件**全部满足**即为成熟态：

- [ ] 内容经过至少一轮推敲和补充
- [ ] 已与相关文档交叉校验，无矛盾
- [ ] 核心结论有量化数据支撑
- [ ] 已对齐宪法（技术栈、命名、禁止项）
- [ ] 包含足够的实现细节，可直接指导开发
- [ ] 文档头包含版本号、日期、状态

### 2.3 归档态判定

符合以下**任意一条**即可归档：

- [ ] 对应的功能已开发完成，文档完成使命
- [ ] 设计已被后续文档推翻或吸收
- [ ] 调研结果已过时（技术栈变更/市场变化）
- [ ] 文档内容已被拆分为多份新文档

## 三、流转触发条件

| 流转 | 触发条件 | 操作 |
|------|---------|------|
| 萌芽 → 成熟 | 准备开发该模块 | 打开文档，补充细节，对齐宪法，标注依赖 |
| 成熟 → 归档 | 功能交付上线 | 移入 历史文档/，在 DOCUMENTATION_INDEX 中标记 |
| 任意 → 删除 | 确认无用 | 物理删除（不移入回收站） |
| 多份 → 合并 | 内容重叠严重 | 合并为新文档，旧文档归档 |
| 成熟 → 萌芽 | 设计被推翻（罕见） | 降级，注明原因 |

```markdown
（自由格式，不需要结构化）
```


## 五、文档存放目录规范

```
docs/
├── README.md                ← 全库唯一入口：导航与阅读指引
├── 00-工程体系/              ← 宪法级：管文档本身、管协作、管 AI（规范、术语、人设、建设原则）
├── 10-YZH架构/               ← ★ YZH 架构唯一入口：框架设计原理与规范（总纲/后端/前端/数据契约/权限/代码结构/流程/常见错误）
├── 20-体系认证/              ← 业务体系：总体设计、数据库设计、详细设计、延展规划、业务知识库、实施方案
├── 30-项目规则/              ← 强制规范 + 按需知识：编码规范、AI 协作规范、知识库
├── 40-实施/                  ← 过程记录："当时做了什么、遇到什么问题"
├── 50-任务/                  ← 行动路线：待办任务清单与实施计划
└── 90-归档/                  ← 归档态文档统一存放（只进不出，不参与日常检索）
```

> 说明：`项目全局规则.md`（文档体系最高宪法）位于**仓库根目录**，不在 `docs/` 内；`docs/` 根目录仅保留 `README.md` 一个文件。

### 5.1 各目录归属判定标准

| 目录 | 定位 | 存放什么 | 禁止放什么 |
|------|------|---------|-----------|
| `docs/` 根目录 | 无存储职能 | 仅允许 `README.md` 一个文件 | 禁止平铺任何其他文档 |
| `00-工程体系/` | 宪法级 | 文档管理规范、AI 协作偏好、术语表、YZH 建设原则 | 系统功能设计、技术选型 |
| `10-YZH架构/` | 框架设计原理 | 架构总纲、后端/前端设计、数据契约、权限体系、代码结构、开发流程、常见错误、框架治理类文档 | 业务模块设计（放 20-） |
| `20-体系认证/` | 业务体系 | 总体设计、数据库设计、详细设计、延展规划、业务知识库、实施方案 | 框架设计原理（放 10-）、过程记录（放 40-） |
| `30-项目规则/` | 强制约束与按需知识 | 编码规范、AI 协作规范、功能开发过程规范、知识库（边界/模板/踩坑/速查） | 框架设计原理（放 10-）、业务功能设计（放 20-） |
| `40-实施/` | 过程记录 | 阶段性实施报告、问题追踪（"过去实际是什么样"） | 目标态设计（放 10-/20-）、待办计划（放 50-） |
| `50-任务/` | 行动路线 | 待办任务清单、实施计划、排期（"接下来要做什么"） | 已交付的过程记录（放 40-） |
| `90-归档/` | 归档态 | 已过时/被替代/旧版本备份（只进不出） | 活跃文档 |

### 5.2 新文档归类决策流程

```
新文档产生
    ↓
① 判性质：规范/框架设计/业务设计/过程记录/待办任务/延展/归档？
    ↓
② 选目录：对照 §5.1，只允许进入一个归属目录；拿不准走 §5.4
    ↓
③ 按规范命名：成熟态 `<主题>-V<版本>.md`，萌芽态 `<主题>.md`；编号子目录先查 README 再续号。**本项目强制约定**：成熟态版本号从 V1 起用 `-V1` 后缀（如 `术语表-V1.md`），禁止 `-V1.0` / `-V1.0.0` 或省略版本号；同一文档升版按 `-V2`、`-V3` 递增
    ↓
④ 落盘后：更新该目录 README → 更新 00-工程体系/README.md（全项目文档导航）
```

### 5.3 移动 / 归档同步机制

任何文档发生**移动、归档、重命名、升版、删除**时，必须同步执行：

1. 更新源目录 README（移除条目）
2. 更新目标目录 README（新增条目）
3. 更新 `00-工程体系/README.md`（全项目文档导航）
4. 检查引用该文档的其他文档，修正路径 / 名称引用

### 5.4 拿不准放哪时（处理办法）

1. 先读 `项目全局规则.md` §2.4 与相关目录 README；
2. 仍不确定 → 对照文档实际内容判断性质；
3. 判断为"业务功能设计类"的歧义文档 → 默认放 `20-体系认证/03-详细设计/` 对应模块目录（拿不准先放 `03-平台基础/` 并标注待归组）；判断为"框架设计类"的歧义文档 → 默认放 `10-YZH架构/`；
4. 仍无法判定 → **必须询问用户**，不得擅自创建新目录或跨目录存放。

> 红线：禁止在 docs/ 根目录平铺文档；禁止 AI 自行臆造新目录或新编号；禁止归档/移动后不同步 README 与 INDEX。

## 六、操作规则

### 6.1 状态变更

- 变更文档状态时，必须同时更新文档头的状态字段
- 归档操作需在 00-工程体系/README.md 全项目文档导航中同步更新

### 6.2 文档审查

- 不设定期审查——没用。文档不会自己变，代码会
- 改代码时如果发现相关文档过时，顺手更新。不强求，但提倡

### 6.3 归档操作

- 物理移动到 `历史文档/`，不要在 Git 中删除（保留历史——过期文档是思想碰撞的结果，有保留价值）
- 归档文件名保持原名，不加日期后缀
- 历史文档/ 不分文件夹，扁平存放
- 归档后必须同步 `00-工程体系/README.md`（文档清单 + 全项目导航 + 清理记录）

### 6.4 脚本迁移规范

- 新脚本统一存放至 `scripts/`，按用途分子目录（backend / db / frontend / storage / generate / tools，见 scripts/README.md）
- 禁止在仓库根目录或 docs/ 内新增散落脚本；存量散落脚本按用途迁移归位
- `docker/` 内脚本与 compose.yml 强绑定，保持原地不迁移
- 一次性脚本（如 test_ai_*）用完即删，删除时在权威文档变更记录（00-工程体系/README.md 清理记录）中注明

## 七、常见问题

**Q：我写了一份萌芽态文档，但后来发现方向性错了，怎么处理？**
A：直接删除。萌芽态文档没有保留价值，别不舍得删。

**Q：一份成熟态文档引用了另一份萌芽态文档，可以吗？**
A：可以，但存在风险。被引用的萌芽态文档在它自己成熟之前，引用的结论可能是错的。建议标注"依赖XXX（萌芽态，待验证）"。

**Q：00-工程体系/README.md（全项目文档导航）应该多久更新一次？**
A：每次新建/归档文档时更新。建议在 commit 前检查一次导航是否同步。

**Q：是否每个模块都要有对应文档？**
A：不。先有代码还是先有文档，取决于复杂度。简单 CRUD 模块不需要文档——代码本身就是文档。复杂业务逻辑（如 NC 状态机、证书签发流程）必须有成熟态文档。
