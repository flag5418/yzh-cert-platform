## 二、角色定义

### 2.1 主程（项目主导者）

| 维度 | 界定 |
|------|------|
| 核心职责 | 架构决策、技术选型、规则制定、AI 工程体系搭建与维护 |
| 产出物 | 项目宪法、知识库、Skills、CRUD 模块、前端页面、数据库迁移 |
| 代码审查 | 审查攻坚者的所有代码产出 |
| 决策权 | 拥有所有技术决策的最终裁量权 |
| 边界 | 不期望主程深入每个技术细节——那不是他的工作，是攻坚者的工作 |

### 2.2 攻坚者（技术专家）

| 维度 | 界定 |
|------|------|
| 核心职责 | 攻克技术难点、深度设计讨论、领域知识补充、主程代码逻辑审查 |
| 产出物 | 核心算法、引擎集成、技术验证报告、设计建议文档 |
| 代码审查 | 审查主程的核心逻辑（非 CRUD） |
| 决策权 | 在攻克的技术领域内拥有设计建议权，最终决策归主程 |
| 边界 | **不负责** CRUD 编写、页面搬砖、规范对齐——这些由主程 + AI 完成 |

### 2.3 不做什么

攻坚者不需要做的事，以及为什么：

| 不需要做的事 | 原因 |
|-------------|------|
| 学习 AI 工程体系 | 规则是机器执行的，不是人学的 |
| 理解全部宪法条目 | 接口约定代替规则对齐 |
| 写 CRUD / 表单页面 | AI 比人更快，主程比攻坚者更熟 |
| 遵守命名规范到每个字符 | 自动化检查会拦住，拦住再改 |

## 三、接口约定（代替规则对齐）

**核心思想**：不要求攻坚者理解宪法，只要求遵守接口约定。

### 3.1 Service 层接口

```csharp
// 主程定义接口（写在 contracts/ 目录）
public interface IAuditPlanService
{
    Task<ApiResult<AuditPlanDto>> CreateAsync(CreateAuditPlanDto dto);
    Task<ApiResult<AuditPlanDto>> UpdateAsync(string code, UpdateAuditPlanDto dto);
    Task<ApiResult<PagedResult<AuditPlanDto>>> QueryAsync(AuditPlanQueryDto query);
}

// 攻坚者只需要知道：
// 1. 输入类型（Dto）
// 2. 输出类型（ApiResult<T>）
// 3. 异常不用自己 catch——全局中间件统一处理
// 4. 返回 null 等于抛异常，不要返回 null
```

### 3.2 前端组件接口

```typescript
// 主程定义 Props
interface AuditPlanFormProps {
  engagementCode: string;  // 必传
  planCode?: string;        // 编辑时传，新建不传
  onSuccess?: (plan: AuditPlanDto) => void;
}

// 攻坚者只需要知道：
// 1. 组件名、Props 类型
// 2. 不做全局状态管理——数据通过 Props 进出
// 3. 用 Design Tokens 中定义的颜色和间距
```

### 3.3 接口约定 vs 规则体系的互补

```
接口约定（契约层）：
  → "你写的 Service 返回 ApiResult<T> 就行"
  → 攻坚者不需要理解为什么不直接返回 T

规则体系（宪法层）：
  → 自动化检查拦下不符合约定的代码
  → 拦住之后告诉攻坚者具体错在哪一行
```

## 四、冲突解决协议

```
当主程的设计决策与攻坚者的建议冲突时：

步骤 1：攻坚者提出理由
  → 必须有数据支撑（性能测试/业务场景/历史经验）
  → 不接受"我觉得这样更好"

步骤 2：主程做出决策
  → 15 分钟内做出（不追求完美决策，追求决策速度）
  → 决策即最终

步骤 3：记录决策
  → 写入 docs/00-工程体系/ADR/ 目录
  → 格式：ADR-{编号}-{标题}.md
  → 包含：背景、选项对比、决策、后果

原则：不追求共识，追求决策速度和可追溯性。
      一个月后忘了为什么这样设计，翻 ADR 就能想起来。
```

## 五、代码审查分工

| 审查对象 | 审查人 | 审查重点 |
|---------|--------|---------|
| 主程的 CRUD 代码 | AI（自动化检查）+ 攻坚者（逻辑抽查） | 自动化：命名/格式/安全；攻坚者：事务边界/N+1 查询 |
| 主程的核心逻辑 | 攻坚者 | 业务逻辑正确性、边界条件、性能风险 |
| 攻坚者的代码 | 主程 | 接口约定对齐、安全、是否引入禁止依赖 |
| AI 生成的代码 | 主程 | 宪法对齐、业务合理性、是否有幻觉 |

## 七、常见问题

**Q：攻坚者写的代码风格不一致怎么办？**
A：自动化检查拦住。拦不住的才由主程手动指出。不要为风格问题开长会。

**Q：攻坚者想引入新的 NuGet 包？**
A：走宪法变更流程。先在宪法白名单中添加，再使用。禁止"先用再说"。

**Q：主程忙不过来，攻坚者是否可以写 CRUD？**
A：如果攻坚者愿意且主程认为时间紧迫，可以。但主程需要明确指定模板（给一份已完成的 CRUD 作为参照），且产出代码必须走自动化检查。

**Q：这个模型会不会让攻坚者觉得不被尊重？**
A：恰恰相反。攻坚者不做搬砖，只做最有价值的事——攻克难点、挑战设计、补充领域知识。这才是对专家的尊重。
