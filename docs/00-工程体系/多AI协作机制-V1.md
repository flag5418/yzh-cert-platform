# 多 AI 协作机制

> **版本**：V1.0 | **日期**：2026-07-31 | **状态**：成熟态
>
> **定位**：确保不同 AI（Claude/GPT-4/Gemini/Copilot 等）在同一项目中产生一致行为的标准化机制。

---

## 一、核心问题

不同 AI 的行为差异：
- **输出风格**：Claude 倾向详细解释，GPT-4 倾向直接给代码，Gemini 倾向先分析再给方案
- **规则遵从**：有的 AI 会跳过加载步骤直接开始写代码
- **边界感知**：有的 AI 会为了"功能完整"而突破硬边界
- **上下文记忆**：长对话中有的 AI 会丢失早期约束

本机制的目标：**让任何 AI 在任何一次对话中，都能产出符合项目约束的代码。**

---

## 二、AI 行为规范（机器可解析）

### 2.1 对话启动协议

```
AI 在收到用户第一条消息时，必须按顺序执行：

Step 1: 加载项目全局规则
  → 读取 项目全局规则.md（仓库根目录）
  → 确认当前版本号

Step 2: 判断需求类型
  → 代码需求 → 加载 vol-skill.md 的 §12.Z
  → 架构需求 → 加载 20-架构决策/README.md
  → 文档需求 → 加载对应文件夹的 README.md

Step 3: 确认边界
  → 读取 60-AI工程设计/YZH-知识库/03-边界与约束.md
  → 确认哪些文件不可修改

Step 4: 开始执行
```

### 2.2 代码生成契约

AI 在生成任何代码前，必须确认：

| 检查项 | 确认方式 |
|--------|---------|
| 目标文件夹的 README 已查阅 | 读取了对应的 README.md |
| 需求对应的 §12 章节已定位 | 在输出中引用了 §12.X.Y |
| YZH 组件的代码就绪度已确认 | 检查了 02-YZH增量清单.md 的状态标记 |
| 03-边界约束未被违反 | 未修改 9 个 Vol 源码文件 |
| 输出格式符合用户偏好 | 直接给文件路径 + 代码块，无长篇解释 |

### 2.3 输出格式规范

| 场景 | 允许格式 | 禁止格式 |
|------|---------|---------|
| 代码生成 | `文件路径` + 完整代码块 | 解释性文字 > 3 行 |
| 方案选择 | 表格对比 + 结论 | 段落式分析 |
| 错误处理 | 错误原因 + 修复方案 | "让我来帮您..." |
| 文档更新 | diff 格式或完整替换内容 | "建议修改..." |
| 需求确认 | 1-2 个关键问题 | "让我先了解一下您的需求..." |
