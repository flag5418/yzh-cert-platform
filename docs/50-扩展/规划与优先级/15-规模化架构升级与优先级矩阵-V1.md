# 体系认证审核平台——规模化架构升级与优先级矩阵 V2

> 编写日期：2026-07-27
> 版本：V2
> 背景：用户明确规模为 200+ 审核员，参考住房监测平台成熟 .NET Core 架构设计，重新评估全部功能点的优先级与人天。

---

## 一、规模变化的核心影响分析

### 1.1 规模对比

| 维度 | V1 假设（MVP） | V2 实际 |
|------|---------------|---------|
| 审核员数 | 3-5 人（单团队） | 200+ 人 |
| 并发用户 | 个位数 | 50-100 并发 |
| 数据量 | 年审核报告数百份 | 年报告数千份，文件 TB 级 |
| 组织复杂度 | 单一团队 | 多分公司/多部门/多层审批链 |
| 部署模式 | 单机单进程 | 至少需要应用服务器 + 数据库分离 |

### 1.2 架构升级映射表

以下是在 V1 基础上因 200+ 人规模必须调整的决策：

| V1 决策 | V1 理由 | V2 重新判断 | 依据 |
|---------|---------|------------|------|
| 砍掉 Redis | 单机够用 | **必须恢复**（P0） | 200+ 人的 Session/缓存/分布式锁，内存缓存撑不住 |
| 砍掉消息队列 | 同步即可 | **升级为 P1** | 审核通知/报告生成/批量任务需要异步削峰 |
| 6 引擎合并为 1 内核 | 减少复杂度 | **保留合并，但内核需支持水平扩展** | 逻辑层合并没错，但需要无状态设计 |
| 砍掉数据分析大屏 | 非 MVP | **降级为 P2** | 200+ 人机构管理需要可视化 | 
| 部署：单机 | 最快上线 | **升级：Nginx + 双实例 + DB 分离** | 住房平台经验：Docker Compose 起步 |
| 规则 28→15 条 | 简洁优先 | **恢复至约 20 条，逐步扩** | 更多审核员 = 更多审核类型覆盖 |
| ZeroTier 简化 | 成本最低 | **前期可延续，后期切换 VPN 专线** | 200 人机构通常已有内网/VPN |

### 1.3 住房监测平台可复用的架构资产

| 住房平台经验 | 审核平台复用 |
|------------|------------|
| VOL 框架 + 代码生成器 | 用户/角色/菜单/字典/日志 → 约 **15 人天直接省掉** |
| 雪花 ID + Code GUID 双主键 | 审核报告跨系统唯一编号 |
| Partial Service/Controller 模式 | 自定义业务不受框架升级影响 |
| EF LINQ + repository 标准数据访问 | 统一数据层，新人好上手 |
| Redis + SignalR 实时通知 | 审核任务推送、审批通知 |
| Quartz 定时任务 | 监督审核到期提醒、证书到期提醒 |
| Docker Compose 部署 | 开箱即用，政务云/自建服务器均兼容 |
| 数据库表命名规范 (`biz_` / `sys_`) | 直接沿用，省去命名争论 |
| 软删除 + 审计字段（BaseEntity） | 框架自带，满足追溯需求 |

## 二、框架选型：采用 VOL (Vue.NetCore)

### 2.1 最终推荐

基于住房监测平台的深入实践验证，采用 **VOL (Vue.NetCore)** 作为基础框架。

| 维度 | 详情 |
|------|------|
| 后端 | .NET 8 + EF Core + SqlSugar + Dapper |
| 前端 | Vue3 + Element Plus |
| 移动端 | Uniapp（iOS/Android/H5/微信小程序） |
| ORM | EF Core 为主，SqlSugar/Dapper 按需 |
| 认证 | JWT + SignalR 实时 |
| 任务调度 | Quartz.NET |
| 缓存 | Redis 7 |
| 部署 | Docker Compose |

### 2.2 框架自带能力（直接复用，0 人天）

| 能力 | 审核平台对应场景 |
|------|----------------|
| 用户管理 | 审核员账号管理（200+ 人） |
| 角色管理 | 审核员/组长/技术专家/管理员 |
| 部门管理 | 分公司/审核组组织架构 |
| 菜单管理 | 动态权限菜单 |
| 字典管理 | 审核类型/标准条款/NC 分类 |
| 日志管理 | 操作审计/异常日志（CNAS 必需） |
| 数据权限 | 按分公司/审核组隔离数据 |
| API 权限 | 接口级权限控制 |
| 代码生成器 | 快速生成 CRUD 页面，节省大量重复开发 |
| 导入导出 | 报告 Excel 导出 |
| 消息推送（SignalR） | 实时通知审核员 |
| 文件管理 | 审核附件上传下载 |
| Uniapp 移动端 | 审核员现场 APP |

### 5.2 数据库设计策略（借鉴住房平台）

| 策略 | 住房平台做法 | 审核平台采用 |
|------|------------|------------|
| 主键 | 雪花 ID + Code GUID 双主键 | 直接沿用 |
| 表前缀 | `sys_`（系统）/ `biz_`（业务） | 直接沿用 |
| 审计字段 | BaseEntity（CreateTime/Creator/ModifyTime/Modifier/IsDeleted） | 直接沿用 |
| 框架表 | sys_user/sys_role/sys_menu/sys_dict 等直接复用 | 省掉 10+ 张表设计 |
| 数据权限 | 按行政区划隔离 | 改为按分公司/审核组隔离 |
| 软删除 | IsDeleted 标记 | 满足审计"不可删除"要求 |

### 5.3 关键设计决策

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 框架 | VOL (Vue.NetCore) | 住房平台已验证，.NET 生态最成熟的后台框架 |
| 多实例 | Nginx + 至少 2 个应用实例 | 200+ 人的高可用基线 |
| 缓存 | Redis 集群（主从） | 缓存 Session + 字典 + 分布式锁 |
| 消息队列 | RabbitMQ | 报告生成（耗时长）/批量通知/数据导出 |
| 对象存储 | MinIO | 审核附件海量小文件，S3 兼容 |
