## 一、功能概述

### 1.1 核心定位

本功能解决"审核规则如何定义、报告内容如何生成"的**配置化**问题，核心资产是一个**自研工作流解释引擎**（非图形化编排平台）：

| 能力 | 说明 | 归属 |
|------|------|------|
| NC 规则定义 | 一个机构+标准+阶段下的多条必须检查的 NC 项；每条 NC 记录内置一条工作流配置（JSON） | 基础配置层 |
| 报告内容定义 | 一个机构+标准+阶段一份报告；报告主表+明细表，每条明细（章节）内置一条工作流配置（JSON） | 基础配置层 |
| Skill 体系 | 全局顶层抽象：后台方法型（类路径+函数名+参数+返回）/ API 型（地址+方法+参数+返回），解释器反射或 API 调用执行 | 执行层 |
| 工作流解释引擎 | 读取挂接在工作流配置层 JSON，按 DAG 语义调度 Skill，完成 NC 判定与报告章节生成 | 执行层 |

### 1.2 核心业务逻辑（必读）

```
基础配置层（页面先行）                         工作流配置层（JSON 即配置）
─────────────────────                        ─────────────────────────
cert_validation_rule（NC 规则）  ──rule_json──▶  工作流配置 JSON（一对一）
cert_report_template（报告模板）──section_config─▶ 章节级 workflow_config（内嵌）
rpt_report_section（报告明细）  ──workflow_config─▶ 工作流配置 JSON（一对一）
       │
       ▼
执行层（后续解释器）
WorkflowEngine.RunAsync(workflowConfigJson, context)
       ├── 拓扑排序 → 逐节点执行（反射调用后台方法 Skill / HttpClient 调用 API Skill）
       ├── get_field[label_tag / field_code] → 读取内容提取结果（复用 cert_doc_field_def）
       ├── compare / llm_judge / assemble … → 判定与组装
       └── 写 wf_workflow_execution_log 节点日志
```

**关键设计决策（V3 与 V1/V2 的根本差异）**：

1. **配置不独立成表**：工作流配置 JSON 直接内联存储在业务行上（`cert_validation_rule.rule_json`、`rpt_report_section.workflow_config`），**废弃** `wf_workflow_definition` 作为配置存储载体的定位。
2. **一对一无多版本**：一个规则 / 一条内容**有且只有一个**工作流配置。不搞多版本、不搞发布态、不搞客户间配置漂移，稳定兼容历史与几百上千客户的一致性。
3. **Skill 顶层抽象**：Skill 有基类、多个输入项、特定输出项；分**后台方法型**（类完整路径+函数名+参数+返回）与 **API 型**（地址+请求方法+参数+返回）两类，解释器统一通过反射 / API 调用执行。
4. **数据来源复用内容提取规则**：节点数据来源复用已建立的 `cert_doc_extraction_rule / cert_doc_field_def / cert_doc_table_def`（`field_code` / `table_code` 为引用键），后台抽象好数据供前端选择，**不单独建表**。
5. **基础配置页先行、图形化设计器必做但按阶段实施**：基础配置页（NC 规则定义页、报告内容配置页、工作流配置页 JSON 编辑 + 校验）先行落地；**图形化工作流设计器是必做项**，只是放在前期准备（数据契约、有限 Skill 集、基础配置页）整理好之后再实施，与解释器开发同步开展，不是"不设计"也不是"无限期后置"。
6. **Skill 有限集起步 + 解释器同步迭代**：Skill **不必一次性建全**，先选定少数几个特定 Skill 支撑工作流配置，即可启动图形化工作流引擎开发，解释器同步开展——用有限 Skill 验证工作流配置与解释执行是否可靠，验证通过后再逐步扩展 Skill 集；解释器与 Skill 必须有全局框架性设计、顶层抽象，**不得为单个特殊业务改解释器**。本轮工作流解释器与执行部分**不做具体设计**（仅定框架原则与边界，见第八章）。

### 2.2 分层原则

| 原则 | 内容 |
|------|------|
| 配置与执行分离 | 配置层只产生 JSON；执行层只消费 JSON。解释器不感知页面、不感知业务表 |
| 一对一定位 | 配置挂接在业务行上，由业务行唯一键（org+standard+phase+clause / report+section）保证唯一 |
| 抽象防特化 | 一切能力以 Skill 形态注册进 SkillRegistry；解释器只按 Schema 调度，禁止为单个 Skill/业务写分支 |
| 复用优先 | 数据来源复用内容提取规则体系（field_code/table_code），不重复建标签映射表 |
| 演进路径 | 基础配置层（数据契约） → 有限 Skill 集 + 解释器框架 → 图形化设计器（双界面）+ 解释器同步 → 日志/测试 → Skill 集扩展 |

### 2.3 边界声明

- **审批流不在本功能范围**：Vol 框架自带 `VOL.Core/WorkFlow` 是 OA 审批流引擎，与自定义 DAG 工作流是两套体系，审批节点 / 审批人解析不属于本功能，另行设计，互不混用。**审批/人工复核完全划出**本模块（归审核员端开发），标准程序只按程序逻辑自动走（澄清 9）。
- **校验逻辑强一致**：同一标准程序下的校验逻辑**不允许按客户差异化**；客户可调整判定结果，但属审核员端行为并保留修改记录，不在本模块设计内（澄清 1）。
- **历史追溯归审核员端**：历史审核记录/任务日志的追溯与查询在审核员端实现，与本功能设计无关；本模块仅保留**排障级**节点执行日志（wf_workflow_execution_log），不做业务级配置快照/追溯设计（澄清 2）。
- **不做多机构复制/共享**：本阶段聚焦**单机构单标准**跑通，不做多机构配置复制/共享；"基础配置+机构覆盖"两层概念删除（过度设计）（澄清 7/12）。
- **测试与正式系统严格分离**：保存必须校验、无草稿/发布状态机；测试环境全局检验通过后导出正式系统（澄清 11）。
- **图形化设计器必做但按阶段实施**：现有 `workflow-designer` 前端模块（LogicFlow）保留代码并作为图形化阶段的输入；图形化设计器是**必做交付物**，但启动时机放在前期准备（数据契约、有限 Skill 集、基础配置页）完成之后，与解释器开发同步推进，不作为 P0/P1 交付物。
- **解释器本轮不做具体设计**：工作流解释器与执行部分（调度实现、反射/API 调用实现等）用户已有思路，本轮**仅定框架原则与边界**（见第八章），具体实现细节待基础打牢后再详细讨论，本稿不展开。
- **AI 能力不特化**：LLM 判定等以通用 Skill（`llm_extract` / `llm_judge`）注册，提示词模板属于 Skill 配置数据，解释器不做业务语义解析。

| V2 方向 | 问题 | V3 处理 |

### 3.3 目标

1. 建立**全局框架性**的工作流配置规范（JSON 结构、校验规则、挂接语义），一规则一配置、一明细一配置，稳定兼容历史。
2. 建立 **Skill 顶层抽象**：基类 + 后台方法型/API 型两类描述结构，注册、校验、反射/API 执行统一，持续扩展不特化。
3. 完成 **NC 规则定义页、报告内容配置页、工作流配置页**三个基础配置页面（JSON 编辑 + 校验 + 试运行），作为配置落地基座。

6. 明确 **解释器框架设计原则与边界**：调度语义、执行方式、日志与测试边界、扩展机制；本轮**不做解释器与执行的具体设计**（用户已有思路，待基础打牢后详细讨论），本稿仅定框架基线。

## 四、业务规则

### 4.1 工作流配置挂接规则（一对一定位）

- 一条 **NC 规则**（cert_validation_rule 一行） ↔ 一条工作流配置（`rule_json`），规则行唯一键（org_code + standard_code + phase_code + clause_code + rule_code）即配置唯一键。
- 一条 **报告明细**（rpt_report_section 一行） ↔ 一条工作流配置（`workflow_config`），明细行唯一键（report_code + clause_code + section_name）即配置唯一键。
- 报告模板（cert_report_template）的 `section_config` 内每个章节内嵌 `workflow_config`，报告生成实例化为报告明细行时逐条复制。
- **禁止**通过外键引用独立配置表；**禁止**为同一规则/明细保留多个配置版本。
- 配置变更 = 行内 JSON 整体替换，业务行 `ModifyDate/Modifier` 即审计记录；**历史审核记录/任务日志的追溯由审核员端实现**，本模块不做业务级配置快照/日志追溯设计（澄清 2，见 §〇）。

### 4.2 NC 规则规则

- NC 规则按 机构 → 标准 → 阶段 → 条款（clause）维度组织，同一机构+标准+阶段下可有**多条** NC 项（不同条款/不同规则）。
- **校验逻辑强一致**：同一标准程序下的校验逻辑对同一 NC 项不允许按客户差异化；客户可调整判定结果，但由审核员端记录修改痕迹，本模块不做客户级覆盖（澄清 1）。
- 每条 NC 记录必含：`RuleCode`（全局唯一）、`RuleName`、`SeverityIfViolated`（major / minor / observation）、`NcDescriptionTemplate`、`RuleJson`（工作流配置）。
- `RuleJson` 允许为空（未配置）；**保存时必须通过校验**（§5.4），校验不通过**禁止保存**，不存在"草稿/停用"态（澄清 11）；执行前必须为已配置且校验通过的启用状态（`IsActive=true`）。
- 审核执行时：解释器加载 `RuleJson` → 执行 → 产出判定结果（是否违规 + 违规描述，由 NcDescriptionTemplate 与工作流输出组装）。

### 4.3 报告定义规则

- 一个 机构+标准+阶段 对应**一份**报告：`cert_report_template` 定义空白报告模板（`TemplateFilePath` 为 MinIO 空白文档 OSS 路径），`rpt_report_task` 生成报告任务，`rpt_audit_report` 为主表（一份），`rpt_report_section` 为明细（多条章节）。
- 每条明细（章节）绑定一条工作流配置（`workflow_config`），解释器执行后产出 `SectionContent`（章节填充内容），`rpt_report_section_source` 记录内容溯源。
- 概述 / 结论等不映射条款的章节（clause_code 为空）同样可以绑定工作流（如"汇总各章节判定结果"），或为静态模板内容（workflow_config 为空时直接使用模板内容）。
- 报告状态机：draft（生成中）→ finalized（定稿）；明细逐条执行完成前报告保持 draft。

### 4.4 Skill 规则（全局顶层抽象）

- Skill 是工作流节点的**唯一执行单元**，有基类、多个输入项、特定输出项。
- Skill 分两类：
  - **后台方法型**：描述 = 类完整路径 + 函数名 + 参数定义 + 返回结果；解释器通过**反射**调用。
  - **API 型**：描述 = 地址 + 请求方法 + 参数 + 返回结果；解释器通过 **HttpClient/API 调用**执行。
- Skill 必须有 Schema（InputSchema/OutputSchema），解释器与配置校验均只依赖 Schema，不感知实现细节。
- 新增能力以"注册新 Skill"方式扩展，**禁止修改解释器核心**；Skill 内不得引用具体业务表硬编码（数据经上下文 Inputs 传入）。
- 现有 6 个内置 Skill（document_extract / llm_extract / get_field / get_table / compare / date_diff / assemble）作为**基座 Skill**，统一纳入 SkillRegistry 注册管理。
- **有限集起步策略（V3.1/V3.2）**：Skill **不必一次性建全**。第一批仅落地少数几个能支撑工作流配置的特定 Skill（候选：`get_field` / `get_table` / `compare` / `assemble`，按需加 `document_extract` / `llm_extract`），即可启动图形化工作流引擎开发，解释器同步开展——用有限 Skill 验证工作流配置与解释执行是否可靠（配置校验 → 解释执行 → 结果正确性闭环）。验证通过后再按业务需求逐步扩展 Skill 集；**禁止**以"Skill 没建全"为由阻塞图形化设计器与引擎开发。
- **顶层设计稳定优先（澄清 3）**：核心是**顶层设计保证配置 JSON 与解释器稳定**——Skill Schema、workflow_config JSON 规范、校验规则一旦确立即作为契约冻结；后续新增 Skill **只维护反射/API 描述信息**（wf_skill 行 + 对应类/接口实现 + EndpointConfig），不修改解释器核心、不改变配置 JSON 规范。
- **API 型鉴权存环境变量（澄清 10）**：API 型 Skill 的鉴权信息（API Key/Token 等）**不落库**，从环境变量读取（约定 `SKILL_API_KEY_<SkillCode>`），EndpointConfig 仅存引用键，见 §5.6/§8.2。

### 4.5 数据来源规则

- 工作流节点数据来源复用内容提取规则体系：`cert_doc_extraction_rule`（文档级）、`cert_doc_field_def`（字段级，`field_code` 为引用键）、`cert_doc_table_def`（表格级，`table_code` 为引用键）。
- 后台抽象"数据源选择器"（按标准/文档/字段/表格维度出树），供配置页面选择；**不新建**字段标签映射表。
- 节点入参 `label_tag / field_code / table_code / file_code` 为运行时数据源定位键，解释器统一注入上下文。
- **提取时序（澄清 4/8，定调）**：
  - **标准文档侧**：制定内容提取规则（cert_doc_extraction_rule + field_def/table_def）时，**自动完成标准文档内容存储**（按规则提取并落库）；
  - **企业资料侧**：审核员上传企业资料后，**队列按提取规则自动提取**并落库（ent_extraction_result / ent_table_extraction_result）；
  - 工作流节点（get_field/get_table）**直接引用已提取落库的数据**，不在工作流内重复提取；`document_extract` 仅用于标准侧内容就绪或特殊场景，不作为常规执行路径。

```
        │  报告生成实例化
        ▼
rpt_report_task（D-01，报告任务）  ──template_code──▶  cert_report_template
        ▼
rpt_audit_report（D-02，报告主表）  report_task_code / report_number(uk) / file_path / status(draft|finalized)
        ▼ 1 : N
rpt_report_section（D-03，报告明细）
  ├─ report_code → rpt_audit_report
  ├─ clause_code → cert_iso_clause（可空）
  ├─ section_name / sort_order
  ├─ **workflow_config（json，V3 新增）**      每条明细一条工作流配置
  ├─ section_content                           解释器执行后填充
  └─ workflow_code（废弃，不再引用独立配置表）
        ▼ 1 : N
rpt_report_section_source（D-04，内容溯源）
  ├─ source_type：extraction / finding / nc / compliance / manual / template
  └─ source_code / source_summary
```

- 空白报告 OSS 路径：`template_file_path`（MinIO），报告成品：`rpt_audit_report.file_path`（MinIO）。

### 5.4 工作流配置校验规则（配置期）

| # | 校验项 | 规则 |
|---|--------|------|
| 1 | JSON 结构 | 可反序列化为 workflow_config；必含 version/workflowType/nodes/edges |
| 2 | 节点 Skill | nodes[].skill_code 必须存在于 wf_skill 且 IsActive=1 |
| 3 | 输入 Schema | 每个节点的 inputs 引用必须匹配该 Skill InputSchema（必填项齐全、类型正确） |
| 4 | 端口引用 | edges 的 source/target 必须引用存在的 node_id；sourceHandle/targetHandle 必须匹配上游 outputs / 下游 inputs 端口 |
| 5 | DAG 无环 | 拓扑排序可完成；存在环则校验失败 |
| 6 | 数据源引用 | 引用 field_code / table_code 的输入必须存在于 cert_doc_field_def / cert_doc_table_def |
| 7 | 输出完整性 | output_config 引用的端口必须存在于对应节点 outputs |
| 8 | 一对一 | 同一业务行只允许一条配置（行内字段天然保证） |

### 5.5 workflow_config JSON 规范（工作流配置层）

```json
{
  "version": 1,
  "workflowType": "validation",
  "nodes": [
    {
      "nodeId": "n1",
      "skillCode": "get_field",
      "config": { "label_tag": "[ISO9001_企业基础资料_营业执照_企业名称]" },
      "inputs": { "label_tag": "ctx.extraction.label_tag" },
      "outputs": { "field_value": "string", "confidence": "number" }
    },
    {
      "nodeId": "n2",
      "skillCode": "compare",
      "config": { "operator": ">=", "threshold": 60 },
      "inputs": { "value": "n1.field_value" },
      "outputs": { "result": "boolean" }
    }
  ],
  "edges": [
    { "source": "n1", "target": "n2", "sourceHandle": "field_value", "targetHandle": "value" }
  ],
  "outputConfig": { "is_violated": "n2.result" }
}
```

字段语义：

| 字段 | 说明 |
|------|------|
| version | 固定 1（协议版本，非业务版本；结构升级时递增，解释器按版本兼容） |
| workflowType | extraction / validation / report（与业务场景对应，解释器仅作日志与校验提示） |
| nodes[].nodeId | 节点唯一标识（画布/JSON 内唯一） |
| nodes[].skillCode | 引用 wf_skill.SkillCode |
| nodes[].config | Skill 静态参数（Skill Schema 定义的常量入参） |
| nodes[].inputs | 端口语义：`{ 输入端口名: 数据来源 }`；数据来源为 `ctx.*`（上下文注入）或 `nX.端口名`（上游节点输出） |
| nodes[].outputs | 端口语义：`{ 输出端口名: 类型 }`；Skill 运行时按 OutputSchema 产出 |
| edges[].source/target/sourceHandle/targetHandle | 端口级连线（与前端 compiler.js 输出一致） |
| outputConfig | 工作流整体输出映射，供上层（NC 判定 / 报告章节）消费 |

**挂接**：
- NC 规则：`cert_validation_rule.rule_json` = 上述 JSON（workflowType 通常为 validation）。
- 报告明细：`rpt_report_section.workflow_config` = 上述 JSON（workflowType 通常为 report / extraction）。
- 报告模板章节：`cert_report_template.section_config[]` 内嵌 `workflow_config` 字段（与明细行结构一致）。

### 5.6 Skill 描述结构（顶层抽象）

wf_skill 表统一承载两类 Skill，`SkillType` 归并为两大体系 + 基座类别：

| SkillType（大类） | 子类枚举（兼容历史） | EndpointConfig 结构 | 执行方式 |
|------------------|--------------------|--------------------|---------|
| method（后台方法型） | ocr / word_extract / excel_extract / pdf_extract / llm_judge / calculate / compare / assemble / llm_generate | `{ "classPath": "YZH.Core.Skills.CompareSkill", "method": "ExecuteAsync", "params": [...], "returnType": "object" }` | 反射调用 |
| api（API 型） | api | `{ "url": "https://…", "httpMethod": "POST", "params": [...], "returnType": "object", "timeoutMs": 30000 }` | HttpClient 调用 |

> **鉴权信息（澄清 10）**：API 型 Skill 的 API Key/Token 等**不落库、不入 EndpointConfig**，统一从环境变量读取（约定 `SKILL_API_KEY_<SkillCode>`）；EndpointConfig 仅描述调用协议，不含任何敏感凭据。

**后台方法型描述结构**：

```json
{
  "classPath": "YZH.Core.Skills.CompareSkill",
  "method": "ExecuteAsync",
  "params": [
    { "name": "value", "type": "object", "required": true, "from": "input.value" },
    { "name": "operator", "type": "string", "required": true, "from": "config.operator" }
  ],
  "returnType": "SkillResult"
}
```

**API 型描述结构**：

```json
{
  "url": "https://ai.internal/api/v1/judge",
  "httpMethod": "POST",
  "headers": { "Content-Type": "application/json" },
  "params": [
    { "name": "document", "type": "string", "from": "input.document_content" },
    { "name": "prompt", "type": "string", "from": "config.prompt" }
  ],
  "returnType": "object",
  "timeoutMs": 30000
}
```

**Skill 基类设计（解释器侧契约）**：

```csharp
public interface ISkillNode
{
    string SkillCode { get; }
    Task<SkillResult> ExecuteAsync(SkillContext context, CancellationToken ct = default);
}
// SkillContext: Inputs / Config / WorkflowInstanceId / NodeId / Logger / BusinessContext
// SkillResult : Success / Outputs(端口字典) / Confidence / Error / DurationMs / TokenUsage
```

- `SkillRegistry` 负责注册与解析：method 型注册为强类型 ISkillNode 实例（DI），或按 classPath 反射懒加载；api 型注册为通用 `ApiCallSkill`（读取 EndpointConfig 执行）。
- 校验：注册时校验 classPath 可解析、method 存在、params 与 InputSchema 一致。

### 5.7 执行日志（wf_workflow_execution_log）边界

| 字段 | 说明 |
|------|------|
| biz_type | rule / report_section（V3 新增，日志挂接业务行） |
| biz_code | rule_code / section_code（V3 新增） |
| workflow_instance_id / workflow_code | 实例与配置来源标识 |
| node_id / skill_code | 节点级日志 |
| inputs / outputs / error / duration_ms / token_usage | 执行快照 |
| execution_status | 成功/失败/超时 |

- 日志只写不删；按 biz_type+biz_code 提供查询接口（**排障与测试入口**）。
- **边界（澄清 2）**：执行日志仅用于**排障级**定位（节点输入/输出/异常/耗时），**不做业务级历史追溯**；历史审核记录、任务日志的追溯与查询由审核员端实现，与本模块无关（见 §〇）。

### 7.3 NC 规则配置界面

- 左侧树：`机构 → 标准 → 阶段 → NC 检查项`（源自 cert_validation_rule 行，按 org/standard/phase/clause 组织）。
- 点选 NC 项 → 右侧画布加载该行 `rule_json` 的工作流（未配置则空画布 + 提示"未配置，可拖拽创建"）。
- 画布能力：节点面板（当前可用 Skill = 有限集）、拖拽节点、节点属性编辑（Skill 静态参数 config / 输入输出端口）、连线（端口级 sourceHandle/targetHandle）、删除节点/边。
- **布局不入 JSON（澄清 13）**：画布坐标/视图等 UI 布局信息**不写入** workflow_config JSON（JSON 仅逻辑结构：节点/边/端口）；节点可随时删除重拖，不影响配置语义。
- 数据源面板：按 `标准 → 文档 → 字段/表格` 出树（data-source-tree，源自 cert_doc_field_def / cert_doc_table_def），拖拽 `field_code / table_code` 生成 `get_field / get_table` 节点（自动绑定 label_tag/field_code）。
- 工具栏：「校验」「运行」「保存」；右上角展示配置状态（未配置/已配置(校验通过)/非法）。
- **保存必须校验（澄清 11）**：保存前必须「运行」验证——点击运行 → 携带业务上下文调 `/workflow-config/run` → 展示各节点输出与最终 outputConfig → 结果正确后点保存 → 校验（§5.4）通过后写回 `cert_validation_rule.rule_json`；**校验不通过禁止保存**，无草稿态。

### 7.4 认证体系报告配置界面

- 左侧树：`机构 → 标准 → 阶段 → 报告章节`（报告模板章节 / 已生成报告任务的 rpt_report_section 明细行）。
- 点选章节 → 右侧画布加载该章节 `workflow_config`。
- 画布能力与 NC 界面一致（同一套画布组件，按业务场景参数化）。
- 保存即回写：模板章节模式写 `cert_report_template.section_config[].workflow_config`；报告明细模式写 `rpt_report_section.workflow_config`。
- 章节内容支持静态模板（workflow_config 为空时直接用模板内容），画布显示"未配置"状态。

### 7.5 画布交互流程与数据流

```
审核员 → 打开图形化配置界面（NC / 报告）
  → 左侧树点选 NC 检查项 / 报告章节
  → 右侧画布加载现有 workflow_config（或空画布）
  → 从节点面板拖拽 Skill 节点 → 从数据源面板拖入字段/表格引用
  → 连线（sourceHandle → targetHandle，端口级）
  → 配置节点属性（Skill config 静态参数）
  → 点「校验」：走 §5.4 全量校验（Skill 存在/Schema 匹配/DAG 无环/数据源存在）
  → 点「运行」：调 /workflow-config/run（携带业务上下文）→ 工作流引擎解释执行
        ├── get_field/get_table 节点读内容提取结果（复用 cert_doc_field_def/table_def）
        ├── compare/assemble 等节点完成判定与组装
        └── 返回 outputConfig + 节点执行明细（含日志）
  → 审核员确认结果正确 → 点「保存」→ 回写业务行内联 JSON
        ├── NC 界面：cert_validation_rule.rule_json
        └── 报告界面：cert_report_template.section_config[].workflow_config / rpt_report_section.workflow_config
  → 保存成功后该行配置状态置"已配置（校验通过）"，可启用
```

- **运行与保存分离**：运行是临时执行（不落业务行），保存才回写 JSON；运行结果仅作配置验证依据，不作为正式审核结果。
- **运行时数据来源（澄清 4/8）**：数据已前置提取落库——标准文档侧在制定提取规则时自动存储；企业资料侧由审核员上传后队列自动提取；运行阶段 get_field/get_table 直接读已提取数据；未上传文件时可注入模拟数据（测试模式）。
- **画布与 JSON 等价**：画布内容与 `workflow_config` JSON 一一对应（compiler.js 端口语义），任一方向变更可互转，保证图形化与 JSON 编辑等价（P2 后 JSON 编辑器保留为"源码视图"）；**画布布局信息不入 JSON**（澄清 13）。

### 7.6 后续执行链路（自动执行）

- **数据链路（澄清 4/8，定调）**：
  - 标准文档侧：制定内容提取规则（cert_doc_extraction_rule + field_def/table_def）时**自动完成标准文档内容存储**；
  - 企业资料侧：审核员上传企业资料后，**队列按提取规则自动提取**并落库（ent_extraction_result / ent_table_extraction_result）；
  - 上层业务按已保存流程（规则/明细行 JSON）调解释器自动执行 → 得到 NC 判定 / 章节内容结果。
- 本界面不负责正式执行；正式执行由上层业务在审核执行/报告生成时触发（见 §9.3）。

## 八、解释器框架设计原则

> **本章边界（V3.1）**：工作流解释器与执行部分**本轮不做具体设计**——用户已有思路，待基础打牢（数据契约、有限 Skill 集、图形化配置界面）后再详细讨论。本章**仅保留框架原则与边界**（调度语义、执行方式、日志与测试边界、扩展机制），不展开实现细节；后续详细设计在独立章节/文档展开。

### 8.1 调度语义

- 输入：workflow_config JSON（§5.5）+ WorkflowContext（BusinessType/BusinessId/OrgCode/StandardCode/PhaseCode/EnterpriseCode 等运行时注入）。
- 执行：反序列化 → 校验（同 §5.4）→ 拓扑排序（DAG，含 Branches 展开）→ 逐节点执行 → 按边传递端口值 → 输出 outputConfig 映射。
- 分支：节点支持条件分支（MatchCondition），分支结构在 JSON 中显式声明（branches[].from/condition/then），不引入隐式副作用。
- 幂等与重试：节点执行失败记录日志并中止（可由上层选择重跑）；Skill 内部不做业务级补偿，补偿逻辑归上层业务。

### 8.2 反射 / API 执行

- **后台方法型**：SkillRegistry 解析 EndpointConfig.classPath → 反射实例化（优先取 DI 注册实例）→ 绑定 params（来自 inputs/config）→ 调用 method → 返回 SkillResult。
- **API 型**：SkillRegistry 解析 EndpointConfig.url/httpMethod → 组装请求（headers/params）→ HttpClient 调用 → 按 returnType 解析响应 → 包装为 SkillResult。
- **鉴权（澄清 10）**：API 型 Skill 的鉴权信息**存环境变量、不落库**（约定 `SKILL_API_KEY_<SkillCode>`），HttpClient 组装请求时从环境变量读取注入头/参数；EndpointConfig 不含敏感凭据。
- 统一收敛为 `ISkillNode` 契约，解释器不区分两类差异（差异封装在 Skill 宿主内）。

### 8.3 日志与测试边界

- 日志：节点级执行快照写入 `wf_workflow_execution_log`（§5.7），只写不删；**日志仅用于排障级定位**，业务级历史追溯由审核员端实现（澄清 2）。
- 测试：解释器提供 `/workflow-config/run` 单次执行入口 + 测试数据注入（上下文可指定模拟数据源），**测试沙箱 UI 后置**；先保证引擎行为稳定，再建设沙箱界面。
- **测试与正式系统严格分离（澄清 11）**：测试环境全局校验 OK 后导出正式系统；不允许在正式系统直接调试或保存未经验证的配置。
- 边界：解释器不负责业务规则判定结果的落库（NC 写入、报告章节写入由上层服务基于 outputConfig 完成），保持引擎通用。

### 8.4 扩展机制（防特化）

- 新能力 = 新 Skill：实现 ISkillNode（或注册 API 型配置）→ 登记 wf_skill → 前端数据源面板自动可用。
- 解释器核心（调度/拓扑/端口传递/日志）禁止因单个业务需求修改；业务差异一律表达为 Skill 参数（config）与 workflow_config 结构。
- Skill 评审红线：Skill 不得硬编码业务表主键、不得绕过 SkillContext 直连数据库、不得依赖执行顺序以外的隐式状态。

## 九、数据流 / 时序

### 9.1 配置期（NC 规则）

```
审核员 → NC 规则定义页
  → 选择 机构/标准/阶段/条款 → 填规则字段
  → 工作流配置区编辑 rule_json → 校验（validate）→ 试运行（run）
  → 保存（cert_validation_rule 行，rule_json 落库）→ 启用
  ── 图形化阶段（P2）：改走 NC 规则配置界面，左侧树选 NC 检查项 → 画布拖拽/连线 → 运行验证 → 保存回写 rule_json（与上述 JSON 编辑等价，流程见 §7.5）
```

### 9.2 配置期（报告模板）

```
审核员 → 报告内容配置页
  → 选择 机构/标准/阶段 → 上传空白报告（MinIO）→ 定义模板信息
  → 逐章节配置 section_name/clause/sort_order/workflow_config → 校验 → 保存
  → 生成报告任务时：模板 section_config 实例化 → rpt_report_section 明细行（复制 workflow_config）
  ── 图形化阶段（P2）：改走认证体系报告配置界面，左侧树选报告章节 → 画布拖拽/连线 → 运行验证 → 保存回写 section_config[].workflow_config / rpt_report_section.workflow_config（流程见 §7.5）
```

### 9.3 执行期（解释器运行）

```
上层业务（审核执行/报告生成）
  → 取 cert_validation_rule.rule_json 或 rpt_report_section.workflow_config
  → WorkflowEngine.RunAsync(json, context)
       → 拓扑排序 → 逐节点执行（get_field 读提取结果 / llm_extract 调 LLM / compare 判定…）
       → 写节点日志（wf_workflow_execution_log）
       → 返回 outputConfig
  → 上层消费：NC 判定 → 写不符合项；章节内容 → 写 rpt_report_section.section_content + source 溯源
```

> **边界（澄清 5/6/15）**：NC 判定结果**写入哪些表**、报告章节内容**回写 section_content 的时机**、以及 WorkflowContext 字段集与注入边界，均在**实现工作流引擎和解释器时再讨论**，本稿不展开具体设计（见 §〇 0.3）。

## 十、边界与异常处理

| 场景 | 处理 |
|------|------|
| rule_json / workflow_config 为空 | 视为"未配置"，禁止启用/执行，页面提示先配置 |
| 配置校验失败 | 保存被拒并返回错误明细（定位到节点/边/端口） |
| 引用的 Skill 被停用/删除 | 校验失败，禁止保存与执行 |
| 引用的 field_code/table_code 不存在 | 校验失败，提示重新选择数据源 |
| 执行中途节点失败 | 记录日志、中止执行、返回失败节点与错误信息；上层可重试 |
| LLM 输出异常/超时 | Skill 内重试 1 次（现有 LlmExtractSkill 逻辑），仍失败按节点失败处理 |
| 并发执行同一规则/明细 | 以 workflow_instance_id 隔离日志；写业务结果由上层加锁/事务控制 |
| 删除约束 | 有执行日志的规则/明细禁止删除；被模板引用的模板禁止删除 |
