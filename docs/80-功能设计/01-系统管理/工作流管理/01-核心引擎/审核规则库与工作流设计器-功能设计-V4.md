## 一、功能概述

### 1.1 核心定位

本功能解决"审核规则如何定义、报告内容如何生成"的**配置化**问题，核心资产是一个**自研工作流解释引擎**：

| 能力 | 说明 | 归属 |
|------|------|------|
| NC 规则定义 | 一个机构+标准+阶段下的多条必须检查的 NC 项；每条 NC 记录内置一条工作流配置（JSON） | 基础配置层 |
| 报告内容定义 | 一个机构+标准+阶段一份报告；报告主表+明细表，每条明细（章节）内置一条工作流配置（JSON） | 基础配置层 |
| Skill 体系 | 全局顶层抽象：**功能性 Skill**（数据获取/AI 提取/输出写入）与**逻辑性 Skill**（比较/计算/组装），解释器反射或 API 调用执行 | 执行层 |
| 工作流解释引擎 | 读取挂接在工作流配置层 JSON，按 DAG 语义调度 Skill，完成 NC 判定与报告章节生成 | 执行层 |

### 1.2 核心业务逻辑

```
基础配置层（页面先行）                         工作流配置层（JSON 即配置）
─────────────────────                        ─────────────────────────
cert_validation_rule（NC 规则）  ──rule_json──▶  工作流配置 JSON（一对一）
cert_report_template（报告模板）──section_config─▶ 章节级 workflow_config（内嵌）
rpt_report_section（报告明细）  ──workflow_config─▶ 工作流配置 JSON（一对一）
       │
       ▼
执行层（后续解释器）
WorkflowEngine.RunAsync(workflowConfigJson, context)
       ├── 拓扑排序 → 逐节点执行（反射调用后台方法 Skill / HttpClient 调用 API Skill）
       ├── get_field[label_tag / field_code] → 读取内容提取结果（复用 cert_doc_field_def）
       ├── compare / llm_judge / assemble … → 判定与组装
       └── 写 wf_workflow_execution_log 节点日志
```

**关键设计决策**：

1. **配置不独立成表**：工作流配置 JSON 直接内联存储在业务行上（`cert_validation_rule.rule_json`、`rpt_report_section.workflow_config`），废弃 `wf_workflow_definition` 作为配置存储载体的定位。
2. **一对一无多版本**：一个规则 / 一条内容有且只有一个工作流配置。
3. **Skill 分两类**：**功能性 Skill**（读数据库/API 调用/文件提取，有副作用）与**逻辑性 Skill**（纯计算/比较/组装，无副作用），解释器统一通过 `ISkillNode` 契约调度。
4. **数据来源复用内容提取规则**：节点数据来源复用 `cert_doc_field_def / cert_doc_table_def`（`field_code` / `table_code` 为引用键）。
5. **验证数据已就绪（缺陷 C 补充）**：规则保存时，AI 提取的标准文档真实数据已落库到 B-08/B-09（挂在 YZH-STD-ENT 虚拟企业下）。工作流配置期试运行注入 `enterprise_code='YZH-STD-ENT'` 即可取到真实数据，不存在"无数据可运行"的死循环。
6. **基础配置页先行、图形化设计器必做但按阶段实施**。
7. **JSON 键名统一 camelCase**（缺陷 A/G 修复）：所有 workflow_config JSON 的键名使用 camelCase，与前端 compiler.js 输出一致；后端 `[JsonPropertyName]` 特性同步改为 camelCase。

```

                                │ 配置期校验（Schema 契约）
                                ▼
┌──────────────────────────────────────────────────────────────────┐

                                │ 配置期校验（Schema 契约）
                                ▼
┌──────────────────────────────────────────────────────────────────┐
│ ② 工作流配置层（JSON 即配置）                                      │
│   · workflow_config JSON 规范：version/workflowType/nodes/edges    │
│   · 键名统一 camelCase（缺陷 A 修复）                              │
│   · 校验：节点 Skill 存在、输入输出 Schema 匹配、DAG 无环、         │
│          数据源引用（field_code/table_code）存在                    │
│   · 挂接：cert_validation_rule.rule_json（一对一）                 │
│           rpt_report_section.workflow_config（一对一）             │
└──────────────────────────────────────────────────────────────────┘
                                │ RunAsync(json, context)
                                ▼
┌──────────────────────────────────────────────────────────────────┐
│ ③ 执行层（独立工作流解释引擎）                                     │

│       - 功能性 Skill：get_field / get_table / document_extract /   │
│         llm_extract（读数据库/API 调用，有副作用）                 │
│       - 逻辑性 Skill：compare / date_diff / assemble               │
│         （纯计算/比较/组装，无副作用）                              │
│       - 起步策略：先启用少数特定 Skill（有限集）支撑配置与验证，     │
│         可靠性验证通过后再扩展（本轮仅定框架原则，不做实现设计）     │
│   · 日志：wf_workflow_execution_log（节点级）                      │
│   · 测试：解释器级测试沙箱（下一阶段，先有引擎再测）                 │
└──────────────────────────────────────────────────────────────────┘
```

### 2.2 分层原则

| 原则 | 内容 |
|------|------|
| 配置与执行分离 | 配置层只产生 JSON；执行层只消费 JSON |
| 一对一定位 | 配置挂接在业务行上，由业务行唯一键保证唯一 |
| 抽象防特化 | 一切能力以 Skill 形态注册进 SkillRegistry；解释器只按 Schema 调度 |
| 复用优先 | 数据来源复用内容提取规则体系（field_code/table_code） |
| 演进路径 | 基础配置层（数据契约） → 有限 Skill 集 + 解释器框架 → 图形化设计器 + 解释器同步 → 日志/测试 → Skill 集扩展 |

### 2.3 边界声明

- **审批流不在本功能范围**：Vol 框架自带 `VOL.Core/WorkFlow` 是 OA 审批流引擎，与自定义 DAG 工作流是两套体系，互不混用。
- **校验逻辑强一致**：同一标准程序下的校验逻辑不允许按客户差异化。
- **历史追溯归审核员端**：本模块仅保留排障级节点执行日志。
- **不做多机构复制/共享**。
- **测试与正式系统严格分离**。
- **图形化设计器必做但按阶段实施**。
- **解释器本轮不做具体设计**。
- **废弃表全部废除（缺陷 I）**：`wf_workflow_definition` 停止使用，`wf_field_label_mapping`（F-02）不建，相关 Service/Controller 标记废弃，详见 §14。

## 四、业务规则

### 4.1 工作流配置挂接规则（一对一定位）

- 一条 NC 规则（cert_validation_rule 一行） ↔ 一条工作流配置（`rule_json`）。
- 一条报告明细（rpt_report_section 一行） ↔ 一条工作流配置（`workflow_config`）。
- 报告模板（cert_report_template）的 `section_config` 内每个章节内嵌 `workflow_config`。
- 禁止通过外键引用独立配置表；禁止为同一规则/明细保留多个配置版本。
- 配置变更 = 行内 JSON 整体替换，业务行 `ModifyDate/Modifier` 即审计记录。

### 4.2 NC 规则规则

- NC 规则按 机构 → 标准 → 阶段 → 条款（clause）维度组织。
- 校验逻辑强一致：同一标准程序下的校验逻辑不允许按客户差异化。
- 每条 NC 记录必含：`RuleCode`（全局唯一）、`RuleName`、`SeverityIfViolated`、`NcDescriptionTemplate`、`RuleJson`（工作流配置）。
- `RuleJson` 允许为空（未配置）；保存时必须通过校验（§5.4），校验不通过禁止保存。
- 审核执行时：解释器加载 `RuleJson` → 执行 → 产出判定结果。

### 4.3 报告定义规则

- 一个机构+标准+阶段对应一份报告。
- 每条明细（章节）绑定一条工作流配置（`workflow_config`），解释器执行后产出 `SectionContent`。
- 概述 / 结论等不映射条款的章节同样可以绑定工作流，或为静态模板内容。

### 4.4 Skill 规则（全局顶层抽象 — 缺陷 E 完善）

> **V4 关键修订**：将 Skill 明确分为两大类——**功能性 Skill**（有副作用）与**逻辑性 Skill**（无副作用），对应工作流引擎选型文档 §8.1 的"输入/AI/输出"与"确定性计算"四类。

#### 4.4.1 Skill 分类定义

| 大类 | 说明 | 特征 | 示例 Skill | 执行方式 |
|------|------|------|-----------|---------|
| **功能性 Skill** | 读数据库 / 调 API / 文件提取 / 写入结果，**有副作用** | 依赖外部资源（DB 连接、HTTP 客户端、文件系统），执行可能改变外部状态 | `get_field` / `get_table`（读 B-08/B-09）、`document_extract`（文件提取）、`llm_extract`（调 LLM API） | DI 注册的 ISkillNode 实例 |
| **逻辑性 Skill** | 纯计算 / 比较 / 组装，**无副作用** | 不依赖外部资源，输入确定 → 输出确定，可缓存可并行 | `compare` / `date_diff`（日期比较）、`assemble`（文本拼接） | DI 注册的 ISkillNode 实例 |

#### 4.4.2 分类设计意义

| 维度 | 功能性 Skill | 逻辑性 Skill |
|------|-------------|-------------|
| 副作用 | 有（读 DB/API/文件） | 无 |
| 可缓存 | 否（数据可能变化） | 是（相同输入→相同输出） |
| 可并行 | 谨慎（需考虑资源竞争） | 是 |
| 配置期校验 | 校验数据源引用存在 | 校验输入端口 Schema 匹配 |
| 测试注入 | 需 mock 数据 / YZH-STD-ENT 验证数据 | 纯函数测试 |
| 解释器重试 | 谨慎（可能重复写入） | 安全（幂等） |

#### 4.4.3 Skill 规则

- Skill 是工作流节点的唯一执行单元，有基类、多个输入项、特定输出项。
- Skill 必须有 Schema（InputSchema/OutputSchema），解释器与配置校验均只依赖 Schema。
- 新增能力以"注册新 Skill"方式扩展，禁止修改解释器核心。
- Skill 内不得引用具体业务表硬编码（数据经上下文 Inputs 传入）。
- **有限集起步策略**：先落地少数特定 Skill 支撑工作流配置（候选：`get_field` / `get_table` / `compare` / `assemble`，按需加 `document_extract` / `llm_extract`），验证通过后再扩展。
- **顶层设计稳定优先**：Skill Schema、workflow_config JSON 规范、校验规则一旦确立即作为契约冻结。
- **API 型鉴权存环境变量**：`SKILL_API_KEY_<SkillCode>` 环境变量，不落库。

#### 4.4.4 Skill 与 wf_skill 表的关系（缺陷 F 完善）

当前 `wf_skill` 表结构保留（SkillCode/SkillType/InputSchema/OutputSchema/EndpointConfig/IsActive），不做独立管理表设计。原因：
1. 当前 Skill 体系不完善（OCR 未接入，第三方图片文字提取能力缺失）。
2. 现有 6 个 Skill 均为硬编码后台方法，无 API 型。
3. Skill 管理表设计需在 Skill 体系成熟后再进行。
4. 当前阶段先补齐 `wf_skill` 的 CRUD 接口（§6.4），使基础配置页可管理 Skill 元数据。

### 4.5 数据来源规则

- 工作流节点数据来源复用内容提取规则体系：`cert_doc_field_def`（`field_code` 为引用键）、`cert_doc_table_def`（`table_code` 为引用键）。
- 节点入参 `label_tag` / `field_code` / `table_code` / `file_code` 为运行时数据源定位键。

#### 4.5.1 提取时序（V3 定调，已实施）

- **标准文档侧**：制定内容提取规则时，**自动完成标准文档内容存储**（按规则提取并落库到 B-08/B-09，挂在 YZH-STD-ENT 虚拟企业下）。
- **企业资料侧**：审核员上传企业资料后，**队列按提取规则自动提取**并落库。
- 工作流节点（get_field/get_table）直接引用已提取落库的数据。

#### 4.5.2 验证数据机制（缺陷 C 补充 — 已实施）

> **关键澄清**：文档内容提取功能设计阶段的大规模改动，正是为工作流验证做数据准备。具体机制见 `YZH特殊企业-工作流验证数据设计-V1.md` 和 `提取结果落库-功能设计-V1.md`（均已实施）。

**数据链路**：

```
管理员在 DocExtractionRule 页面操作：
  AI 分析 → 生成 Prompt → 验证 Prompt → 保存规则
       │
       ▼
SaveExtractionRuleAsync（单事务，已实现）
  ├── 1~4. 保存规则定义（cert_doc_extraction_rule + field_def + table_def）
  └── 5. 【已实现】SyncExtractionResultToB08B09Async
        ├── 物理删除 B-08/B-09 WHERE enterprise_code='YZH-STD-ENT' AND file_code=@file
        ├── 字段 → ent_extraction_result（每字段一条，label_tag=field_code）
        └── 表格 → ent_table_extraction_result（每表格一条）
       ▼
工作流配置期试运行（注入 enterprise_code='YZH-STD-ENT'）：
  get_field[label_tag] → SELECT extracted_value FROM ent_extraction_result
                       WHERE enterprise_code='YZH-STD-ENT' AND label_tag=@tag
                       → ✅ 返回标准目录文件的提取值（真实数据，非 mock）
```

**结论**：保存 NC 规则时，工作流配置期"试运行"不需要 mock 数据——只要该标准下已有提取规则并保存过（规则保存即落 B-08/B-09 数据），注入 `enterprise_code='YZH-STD-ENT'` 即可取到真实提取数据。不存在"要保存必须运行，要运行需要数据，但没有数据"的死循环。

#### 5.8.4 引擎输入解析升级

**Before（当前）**：`ResolveTemplate` 使用 `{{n1.output}}` 双大括号模板语法。

**After（目标）**：解析 `n1.portName` 端口引用（无大括号），直接在 `ResolveInputs` 中处理：
```csharp
private static object ResolveInputValue(object val, Dictionary<string, IDictionary<string, object>> outputs, IDictionary<string, object> workflowInputs)
{
    var str = val?.ToString() ?? string.Empty;
    // 1. ctx.* 引用上下文
    if (str.StartsWith("ctx."))
    {
        var key = str.Substring(4);
        return workflowInputs.TryGetValue(key, out var v) ? v : string.Empty;
    }
    // 2. nX.portName 引用上游节点输出
    if (str.StartsWith("n") && str.Contains("."))
    {
        var parts = str.Split('.', 2);
        if (outputs.TryGetValue(parts[0], out var nodeOut))
            return nodeOut.TryGetValue(parts[1], out var v) ? v : string.Empty;
        return string.Empty;
    }
    // 3. 直接值
    return val;
}
```

```csharp
{
    [JsonPropertyName("from")]
    public string From { get; set; } = string.Empty;
    [JsonPropertyName("condition")]
    public BranchCondition? Condition { get; set; }
    [JsonPropertyName("then")]
    public List<WorkflowNode> Then { get; set; } = new();
}

public class BranchCondition
{
    [JsonPropertyName("field")]
    public string Field { get; set; } = string.Empty;
    [JsonPropertyName("op")]
    public BranchOp Op { get; set; }
    [JsonPropertyName("value")]
    public object? Value { get; set; }
}

public enum BranchOp
{
    Truthy, Equals, NotEquals, Gt, Gte, Lt, Lte
}
```

**JSON 示例**：
```json
{
  "from": "n1",
  "condition": { "field": "result", "op": "equals", "value": true },
  "then": [{ "nodeId": "n2", "skillCode": "assemble", ... }]
}
```

#### 5.8.6 WorkflowEngine 反序列化升级

**Before（当前）**：使用 `JsonNamingPolicy.CamelCase` + `[JsonPropertyName("snake_case")]` 冲突。

**After（目标）**：所有 `[JsonPropertyName]` 改为 camelCase 后，反序列化器不再需要 CamelCase 策略：
```csharp
// Before
var opts = new JsonSerializerOptions { PropertyNamingPolicy = JsonNamingPolicy.CamelCase };
// After: 不需要 NamingPolicy，JsonPropertyName 直接匹配
var opts = new JsonSerializerOptions { };
opts.Converters.Add(new BranchOpConverter());
```

## 八、解释器框架设计原则

> 本章边界：工作流解释器与执行部分本轮不做具体设计。仅保留框架原则与边界。

### 8.1 调度语义

- 输入：workflow_config JSON + WorkflowContext。
- 执行：反序列化 → 校验 → 拓扑排序（DAG，含 Branches 展开）→ 逐节点执行 → 按边传递端口值 → 输出 outputConfig。
- 分支：节点支持条件分支，分支结构在 JSON 中显式声明。
- 幂等与重试：节点执行失败记录日志并中止；Skill 内部不做业务级补偿。

### 8.2 反射 / API 执行

- **后台方法型**：SkillRegistry 解析 EndpointConfig.classPath → DI 优先，反射兜底 → 绑定 params → 调用 method → 返回 SkillResult。
- **API 型**：SkillRegistry 解析 EndpointConfig.url/httpMethod → HttpClient 调用 → 包装为 SkillResult。
- **鉴权**：API 型 Skill 鉴权信息存环境变量。
- **DI vs 反射双路径（缺陷 J 保留）**：内置 Skill 走 DI（编译时已知），动态新增 Skill 走反射（运行时加载）。后续按具体实现深入分析。

### 8.3 日志与测试边界

- 日志：节点级执行快照写入 wf_workflow_execution_log，只写不删，仅排障用。
- 测试：解释器提供 `/workflow-config/run` 单次执行入口 + 测试数据注入（`enterpriseCode='YZH-STD-ENT'`）。
- 测试/正式分离：测试环境全局校验 OK 后导出正式系统。

### 8.4 扩展机制（防特化）

- 新能力 = 新 Skill：实现 ISkillNode → 登记 wf_skill → 前端面板自动可用。
- 解释器核心禁止因单个业务需求修改。
- Skill 评审红线：不得硬编码业务表主键、不得绕过 SkillContext 直连数据库、不得依赖隐式状态。

## 十、边界与异常处理

| 场景 | 处理 |
|------|------|
| rule_json / workflow_config 为空 | 视为"未配置"，禁止启用/执行 |
| 配置校验失败 | 保存被拒并返回错误明细（定位到节点/边/端口） |
| 引用的 Skill 被停用/删除 | 校验失败 |
| 引用的 field_code/table_code 不存在 | 校验失败 |
| 执行中途节点失败 | 记录日志、中止执行、返回失败信息 |
| LLM 输出异常/超时 | Skill 内重试 1 次，仍失败按节点失败处理 |
| 并发执行同一规则/明细 | 以 workflow_instance_id 隔离日志 |
| 删除约束 | 有执行日志的规则/明细禁止删除 |
| 重新打开已保存的工作流 | 自动布局（dagre LR），布局不入 JSON |
