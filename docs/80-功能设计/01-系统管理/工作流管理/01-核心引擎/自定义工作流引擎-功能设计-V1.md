## 一、功能概述

### 1.1 是什么

管理员（维护人员）在画布上**拖拽节点、连线编排**审核核验流程（NC 判定、报告章节生成），保存为 `workflow_config` JSON；运行时由**确定性解释器按图遍历自动执行**，产出可审计的执行轨迹（TRACE）与最终结果；**AI（LLM）作为特殊节点**承载复杂逻辑（语义判断、循环、文本组织）。

**一句话架构**：画布产出的是"流程说明"（workflow_config JSON + Skill 元数据），**解释器是唯一执行主体**——它按规则从开始跑到结束，把所有节点串起来执行并产出结果；AI 只是解释器调用的一个普通节点；提示词只是解释器组装出来给 AI 的输入。

### 1.2 与 n8n / 扣子的对应关系

| 能力 | n8n | 扣子 | 本系统 | 说明 |
|------|-----|------|--------|------|
| 画布 | LogicFlow | 自研画布 | **LogicFlow（复用现有资产）** | 通用 skillNode，元数据驱动 |
| 执行引擎 | Execution Engine | 工作流引擎 | **自研确定性解释器（本稿核心，§三）** | 唯一执行主体 |
| 节点执行 | execute() | 节点输入输出 | **SkillExecutor（反射调用静态方法）** | **只有 method 形态**（反射执行）；LLM/引擎内置为特殊节点硬编码 |
| 参数引用 | 表达式 `{{ $json.x }}` | 引用节点输出 | **命名参数 + 引用模板** | 字面量 / 单引用 / 模板拼接；**引用不依赖连线** |
| AI 节点 | AI Agent | 大模型节点 | **ai_node（弱约束）** | 提示词承载语义判断/文本生成 |
| 逻辑判断 | IF | 选择器 | **logic（双分支 + 多条件）** | conditions[] + and/or；success/failure 锚点，两分支必连 |
| 循环 | Loop Over Items | 循环节点 | **loop（统一端口，v1 提示词驱动）** | 引擎 for-each 为 P2+ 增强 |
| 开始/结束 | Start/End | 开始/结束 | **start / end（多入边汇聚）** | end 输出独立解析 |
| 轨迹调试 | 节点输入输出展示 | 画布实时调试 | **单步调试（断点执行）+ TRACE** | 每步看真实输入输出，可调参重跑 |
| 独立测试 | — | 节点试运行 | **run-node / 不连线手动录入** | 未连线节点单独验证 |

### 1.3 三层执行架构

```
第 1 层  确定性遍历引擎（解释器 WorkflowEngine）—— 程序自动运行（核心，§三）
         解析 → 校验 → 依赖排序（边∪命名引用）→ 按序灌数据/执行/传递 → end 汇聚输出
第 2 层  轨迹序列化（TraceFormatter + MermaidRenderer）—— 让 AI 看懂
         每节点真实输入/输出/状态 → TRACE 协议；工作流 → Mermaid 流程图
第 3 层  AI 语义分析（PromptAssembler + AiAnalyzer）—— 产出最终结果
         Mermaid + glossary + TRACE + 判定要求 → LLM → 最终判定
```

**边界（设计定稿）**：第 2/3 层都是**解释器执行完成之后的产物/消费方**——AI 不决定执行顺序，执行顺序由解释器按依赖图确定性完成；AI 分析的是执行结果。

### 1.4 节点模型（6 种，统一端口口径）

**统一端口口径**：所有节点（表注册 Skill 与引擎内置特殊节点）共用同一套端口契约——输入端口 / 输出端口 = `name + type + prompt`；内置节点在代码中按相同结构声明，表注册节点在表中定义；引用语法统一 `nX.portName`。**前后端口口径一致，解释器/校验器/画布无需区分节点来源。**

| nodeType | 类别 | 端口 | 说明 |
|----------|------|------|------|
| start | 引擎内置 | 仅输出 | 声明工作流输入（enterpriseCode/phaseCode/fileCode 等），引擎注入 |
| **skill** | 表注册 | 强约束（output_strict=1） | 确定性能力：数据获取（get_field/get_table）、计算（compare/assemble）、文档/AI 提取——**只有 method 型**（反射执行，第三方 API 调用封装在方法内部） |
| **ai_node** | 表注册 | 弱约束（output_strict=0） | 提示词组织输入 → LLM → 通用输出 content/json/confidence；承载语义判断/文本生成 |
| **logic** | 引擎内置 | 固定端口 | **判断节点**：conditions[]（8 操作符 + and/or 组合）→ 输出 `result`(boolean) 数据端口 + **success/failure 双路由锚点**，两分支必连（校验强制） |
| **loop** | 引擎内置 | 固定端口 | 输入 `collection`；输出 `results`(json)。**v1 实现 = 提示词驱动**（collection 整包 + "逐项核验…输出数组" → LLM 一次调用）；引擎 for-each 为可选增强（P2+） |
| **end** | 引擎内置 | 仅输入 | **多分支汇聚**：outputConfig 每引用独立解析（ref+default），未执行分支取默认值不失败；**提前终止是合法执行路径** |

### 1.5 功能范围

| 能力 | 说明 |
|------|------|
| 画布编排 | LogicFlow 通用 skillNode + 动态输入表单 + 布局保存/恢复（layout_json）；**拖入节点必须命名**（自动生成 nodeId + 可编辑 title） |
| 节点元数据管理 | 4 表 CRUD（主表/输入模板/输出契约/反射），全部前台页面维护——**为解释器执行提供元数据**（wf_skill_api 表保留不删但不再使用） |
| 节点注册 | **只有 method 型**：内置 method（DI 容器注册）/ 自定义 method（反射，wf_skill_reflection 驱动，DI 优先实例化） |
| **确定性执行** | 解释器：依赖排序（**边 ∪ 命名引用**）+ 命名参数解析 + 节点执行 + end 汇聚输出 |
| **不连线独立测试** | 校验不强制全图连通；未连线节点运行时可手动录入输入，单独验证 |
| **单步调试** | 断点执行（stopAt）+ 每步展示真实输入/输出 + 参数调整重跑——底座 P0 |
| AI 能力 | ai_node（弱约束）+ 第 3 层 AI 语义分析 |
| 可审计可解释 | TRACE（真实数据）+ Mermaid（结构）+ glossary（名词解释） |
| 系统参数 | `$sys.<路径>` 运行时解析（环境变量→系统配置），密钥不落库 |

## 二、业务背景与目标

### 2.1 为什么自研（选型结论）

| 选项 | 结论 | 理由 |
|------|------|------|
| 直接引入 n8n | ❌ 否决 | Node.js 栈与 .NET 体系割裂；数据模型与业务表（cert_*/ent_*/rpt_*）强绑定难定制；部署运维重；用户自身评估"嵌入难度很大" |
| 引入扣子 | ❌ 否决 | 云平台依赖、数据在外部、无法集成本地 B-08/B-09 与审核业务 |
| **开源工作流思路自研** | ✅ 采纳 | LogicFlow 画布 + 自研轻量解释器，**概念对标 n8n/扣子，深度集成现有体系**；灵活、可控、可持续扩展 |

### 2.2 目标

1. 画布编排 → `workflow_config` JSON（布局独立列、Mermaid 可生成、glossary 提示词）。
2. **确定性解释器自动执行**：程序按规则从开始跑到结束，不依赖 AI 决策执行顺序。
3. **自定义节点 = 登记即用**：新增 Skill 只插表（反射/api），不改代码、不改前端。
4. **复杂逻辑由 ai_node 提示词承载**：语义判断、文本组织；循环由 loop 节点（提示词驱动）承载。
5. **逻辑判断节点**：8 基础操作符 + 多条件 and/or 组合，success/failure 双分支必连，失败常为提前终止。
6. **命名引用不依赖连线**：拖入节点即命名，`nX.port` 按名引用，支持节点运算。
7. **不连线独立测试**：未连线节点手动录入输入即可单独验证。
8. **单步调试**：断点执行，每步分析节点真实输入/输出，针对异常调整后重跑。
9. **AI 可理解**：Mermaid 流程图 + TRACE 真实数据 + glossary → 最终语义判定。
10. **数据链路先行**：真实参数触发 skill 拿到真实结果（阶段 0）。
11. **底座完整，节点渐进**：端口契约/引用解析/校验/执行/轨迹/调试第一版完整；业务节点后续按需补充。

### 2.3 设计原则（贯穿全文）

1. **解释器是核心（最高原则）**：解释器 = 简单确定性遍历引擎，是唯一执行主体；节点/Skill/表结构/画布全部是为解释器执行做准备的输入。**底座完整，节点渐进**——底座能力第一版必须完整（引擎成败决定系统成败），业务节点可后续按需补充。
2. **解释器极简**：只做"按图遍历、灌数据、执行、传递、汇聚"，不承载业务逻辑。
3. **复杂逻辑下沉节点**：节点（尤其 ai_node 提示词）是复杂逻辑唯一载体。
4. **契约分级**：强约束（确定性 skill 输出强校验）/ 弱约束（ai_node 输出由提示词定义）。
5. **引用即依赖**：边与命名引用共同决定执行序（依赖图 = 边 ∪ 引用），不连线也能引用与测试。
6. **一切可解释**：TRACE + Mermaid + glossary 三件套，AI 与人皆可读；每步调试可见真实输入输出。
7. **密钥不落库**：第三方凭证经 `$sys.` 运行时解析。

## 三、解释器核心设计（本体系核心）

> 本章是整个体系的中心。解释器是**唯一执行主体**：它读取 `workflow_config` JSON 与 Skill 元数据，按确定性规则从开始遍历到结束，灌数据、执行节点、传递结果、汇聚输出。**所有 Skill、节点、表结构、画布设计，最终目的都是为解释器执行准备输入**（§3.14 详述关系）。

### 3.1 原理与定位

**原理（一句话）**：把画布上保存的"流程说明"（workflow_config：节点、连线、命名参数、判断条件）当作**程序**，解释器就是这台程序唯一的**执行引擎**——按依赖顺序一个节点一个节点地跑，跑到 end 输出最终结果。程序自动运行，不生成复杂结构让 AI 来读懂，也**不需要 AI 决定执行顺序**。

**三条定稿边界**：

| 边界 | 说明 |
|------|------|
| 解释器 = 唯一执行主体 | 布局、连线、参数注入、分支、循环（提示词形态）、汇聚全部程序化执行 |
| AI 是普通节点 | ~~llm_extract~~ / ai_node 等 AI 能力是 DAG 中的普通节点，解释器执行到它时调用 LLM，结果照常进端口。**注：llm_extract 已废弃，信息提取走独立流程** |
| 提示词是解释器组装的输入 | skill_prompt / output_prompt / glossary 由解释器在执行到 AI 节点时组装成 prompt 传给 LLM——**AI 消费的是解释器喂给它的东西，不反向驱动解释器** |

### 3.2 输入契约

```
WorkflowEngine.RunAsync(workflow_config JSON, WorkflowContext, options?)
```

| 输入 | 内容 | 来源 |
|------|------|------|
| workflow_config JSON | nodes / edges / glossary / outputConfig（§5.7） | 画布保存（rule_json / workflow_config 业务列） |
| **WorkflowContext.Inputs** | enterpriseCode / standardCode / phaseCode / fileCode 等工作流输入 | 上层业务（NC 判定、报告生成）传入；start 节点注入 |
| BusinessType / BusinessCode | 业务类型与业务编码（NC 检查项 / 报告章节） | 上层业务 |
| LogStore | 执行日志写入器（wf_workflow_execution_log） | 框架 |
| options | `{ stopAt: nodeId }`（单步调试断点，§3.11）| 调试会话 |

### 3.3 输出契约

```
WorkflowRunResult {
  Success: bool,
  NodeOutputs: { nodeId → { portName → value } },   // 每节点输出端口字典（第 2 层引用来源）
  OutputConfig: { name → value },                    // 最终结果（§3.9）
  FailedNodeId, Error, DurationMs, PromptTokens,     // 失败定位/耗时/token 统计
  Trace: TRACE 序列, Mermaid: 流程图                   // 第 2 层产物（§3.12 协议）
}
```

上层业务直接消费 `OutputConfig`（写 audit_nonconformity / section_content）与 `Trace`（可审计、可人工复核）。

### 3.4 执行流水线（八步，确定性）

```
WorkflowEngine.RunAsync(json, context, options?)
 ① 解析     camelCase 反序列化（nodes/edges/glossary/outputConfig）
 ② 校验     九项（§3.16）：结构/Skill 存在/端口匹配/引用可解析/无环/数据源/输出完整/一对一/logic 双分支完整
            —— 未连线节点允许存在（独立测试），但引用端口必须可解析（连线/手动注入/默认值）
 ③ 建依赖图  边 ∪ 命名引用：扫描每个节点 inputs/conditions/outputConfig 中的 nX.port / {{nX.port}}
            → 被引用但未连线的节点自动进入依赖序（先于引用者执行）
 ④ 拓扑排序  Kahn 算法：start 最前、end 最后；依赖图成环 → 报错拦截
 ⑤ 遍历执行  按依赖序逐节点：
            灌数据（ResolveInputs，§3.6）→ 执行（节点分派，§3.5）→ 输出端口映射（§3.7）→ 写 TRACE
 ⑥ 分支路由  logic 节点按 result 走 success / failure 锚点边；未连线分支 = 提前终止（§3.8）
 ⑦ end 汇聚  outputConfig 每引用独立解析（ref + default）（§3.9）
 ⑧ 输出      WorkflowRunResult（含 OutputConfig + TRACE + Mermaid）
```

**执行范围**：start 可达（边 ∪ 引用）∪ outputConfig 引用链上的节点；孤岛节点（无引用、无连线）在工作流运行时跳过（日志 noted），在独立测试/调试模式下可单独执行。

### 3.5 节点执行分派（6 种 nodeType）

解释器执行到某节点时，按 nodeType 分派到对应执行逻辑：

| nodeType | 执行逻辑 | 产物 |
|----------|---------|------|
| start | 把 WorkflowContext.Inputs 注入其输出端口（enterpriseCode 等），供下游 `start.xxx` 引用 | 输出端口字典 |
| skill | ① ResolveInputs 灌数据（§3.6）② `SkillRegistry.Get(skillCode)`（§3.14）③ 构造 `SkillContext{Inputs, Config, NodeId, BusinessContext, Logger}` ④ `ExecuteAsync` ⑤ 输出映射 + 强约束类型校验（§3.7）⑥ 写日志 | 输出端口字典 |
| ai_node | 同 skill；**执行前由 PromptAssembler 组装 prompt**（当前输入 JSON + skill_prompt + output_prompt + glossary）→ 调 LLM → 输出 content/json/confidence（弱约束放行） | 输出端口字典 |
| logic | 逐条求值 conditions[]（8 操作符 + and/or 组合）→ result(boolean) 写入数据端口；按 result 决定路由（§3.8） | result + 路由决策 |
| loop | 解析 collection（上游输出，json 数组）→ v1 整包交 LLM（提示词驱动"逐项核验…输出数组"）→ results；P2+ 引擎 for-each（§3.10） | results(json) |
| end | 收集上游输入端口值，按 outputConfig 解析（§3.9） | OutputConfig |

### 3.6 参数注入：ResolveInputs（"灌数据"的核心机制）

每个节点执行前，解释器把该节点 `inputs` / `conditions` 中的**命名参数**逐项替换为真实值，**按序取第一个命中的来源**：

| 优先级 | 值形态 | 示例 | 说明 |
|--------|--------|------|------|
| ① | 常量（字面量固定值） | `"operator": ">="`、报告固定文案 `"不符合条款要求"` | 直接输入，不解析——报告/NC 输出的固定内容即常量 |
| ② | 变量（单引用） | `"value": "n1.fieldValue"` | 从 NodeOutputs 按名取上游输出（**不依赖连线**）/ `ctx.xxx` 上下文 |
| ③ | 模板拼接（常量+变量混合） | `"prompt": "条款{{ctx.clauseCode}} 分值是{{n2.fieldValue}}"` | 双大括号内多引用，整体替换 |
| ④ | 系统参数 | `"threshold": "$sys.audit.minScore"` | SysConfigResolver：环境变量 → 系统配置（§4.5） |
| 兜底 | 默认值 | 输入模板 default_value | 未引用时取默认值；`is_required=1` 且解析为空 → 校验期拦截 |

**值来源三分类（用户定调）**：参数值按来源分三类——**常量**（固定值直接输入，如报告/NC 的固定文案、拼接模板固定文本）/ **变量**（节点输出 `nX.port`、上下文 `ctx.xxx`）/ **系统参数**（`$sys.xxx`）。模板拼接 = 常量与变量混合。**递归解析**：数组/对象元素内的 `{{}}` 引用同样解析（如 assemble 的 parts 数组可混入常量与 `{{nX.port}}` 按序拼接，见 §4.4）。

**节点必须命名**：拖入画布自动生成唯一 nodeId（可编辑 title），`nX.portName` 按名字解析，**与是否连线无关**（§2.3 原则 5）。

### 3.7 数据传递与端口映射

- **传递**：每节点执行结果写入 `NodeOutputs[nodeId][portName]`；下游引用（`nX.port` / `{{nX.port}}`）按名字从该字典读取，天然支持"不连线引用"与"一个节点输出被多处引用"。
- **映射**：skill 的 ExecuteAsync 返回 `SkillResult`（结构统一：字段 + PromptTokens/CompletionTokens 统计），解释器按输出契约映射到端口：
  - 强约束（output_strict=1）：按 wf_skill_output 逐端口校验类型（5 种），不匹配报错；
  - 弱约束（output_strict=0）：content/json/confidence 放行，结构由提示词定义。
- **类型统一**：`string / number / date / boolean / json`（复杂结构一律 json）。

### 3.8 logic 双分支与提前终止

```
logic 节点执行：
  ① 逐条求值 conditions[]（每条 valueA op valueB，支持引用/字面量）
  ② 按 conditionLogic（and=全部满足 / or=任一满足）组合 → result(boolean)
  ③ result 写入数据端口 result（下游可 nX.result 引用，不依赖连线）
  ④ 路由决策：result=true → 走 success 锚点出边；result=false → 走 failure 锚点出边
  ⑤ 未连线的分支 = 隐式提前终止：记录 terminated，end 用 default 解析（合法路径，非异常）
```

- 双分支完整性由校验第九项强制（§3.16）：success / failure 各至少一条出边。
- **提前终止不是异常**：失败分支直连 end 是最常见形态（如"数量不达标 → 直接判定违规"），outputConfig 对未执行节点取 default（§3.9）。

### 3.9 end 汇聚与 outputConfig 解析（"得到想要的结果"）

```
end 节点执行（多入边自然汇聚，不建 join 节点）：
  对 outputConfig 中每个引用独立解析：
    { "ref": "n4.json.qualified", "default": true }
      → 节点 n4 执行过：取实际值 n4.json.qualified
      → 节点 n4 未执行（分支未走/提前终止）：取 default；无 default → null + TRACE 标记"未执行"
  整体不因某分支未走而失败
```

- 多分支到 end："条件不满足直接提前终止"与"所有条件满足汇聚到结束"均成立。
- **不同分支可产出不同的最终结果**：失败走 default、成功走真实节点值。

### 3.10 loop 执行

| 实现 | 说明 |
|------|------|
| **v1（提示词驱动，落定）** | 解析 collection（上游输出数组）→ 整包交给 LLM：提示词"逐项核验…输出 JSON 数组" → results。循环的执行是程序化的（解释器调用），逐项语义判断由 LLM 完成；空数组按提示词返回 []，不报错 |
| P2+ 增强（可选） | 引擎 for-each：仅当循环体需要**逐项执行确定性 skill**（如每项单独查 B-08 字段）时启用；需子图执行能力，留待后续 |

### 3.11 单步调试（底座 P0）

维护人员在画布上**用真实数据单步执行工作流**，逐步分析每个节点的输入与输出，针对异常调整参数后重跑——保证工作流行为正确、审核结果稳定的核心手段。

```
调试期（维护人员）：
  workflow → 调试模式（step by step）
    step 1: start + n1 执行 → 面板展示 n1「解析后的输入 + 真实输出」（含 TRACE）
    step 2: n2 执行 → 展示输入/输出
    ...
  每步可做三件事：
    ① 看  该节点解析后的输入（灌数据结果）+ 真实输出（异常定位）
    ② 改  修改该节点 inputs/config（如调 prompt、换阈值、改操作符）→ 从该节点重跑后续
    ③ 注  未连线节点手动注入输入，单独验证
```

| 能力 | 实现 |
|------|------|
| **断点执行** | `RunAsync(json, ctx, { stopAt: nodeId })`——执行到指定节点暂停，返回中间状态（已执行节点输出 + 待执行队列）；带状态续跑 = 单步 |
| **参数调整重跑** | 暂停时改节点参数 → 从该节点重新计算后续（后续节点输出失效重算），或仅重跑该节点 |
| 节点独立运行 | run-node：manualInputs 覆盖输入解析，单节点执行（不依赖连线） |
| 接口 | `/api/workflow-config/debug/step`（一步 + 状态）；复用 `/api/skill/execute`（单 skill）与 run-node |
| 状态隔离 | workflow_instance_id 隔离并发调试会话（含已执行节点输出/待执行队列） |

### 3.12 TRACE 与日志

- **每节点执行后写日志**：`wf_workflow_execution_log`（workflow_instance_id / biz_type / biz_code / node_id / skill_code / inputs / outputs / status / duration），`workflow_instance_id` 隔离并发。
- **TRACE 序列**（第 2 层协议，符号包裹真实数据，执行时逐节点追加）：

```
【工作流】<mermaid 图>
【节点:n1:get_field:success】
  输入: {"fieldCode":"HR_STAFF_COUNT","enterpriseCode":"YZH-STD-ENT"}
  输出: {"fieldValue":"25","confidence":0.98}
【节点:n2:logic:success】条件: n1.fieldValue(25) gte 1 → true → 走 success 分支
【节点:n4:ai_node:success】标题: 资源充分性判定
  输出: {"json":{"qualified":true,"reason":"25人>=1人"},"confidence":0.9}
【终止:failure 分支未连线】n2 failure → end（提前终止，isViolated 取 default=true）
【结束:outputConfig】{"isViolated":{"ref":"n4.json.qualified","value":true},"evidence":{"ref":"n1.fieldValue","value":"25"}}
```

### 3.13 失败处理与重试

| 场景 | 处理 |
|------|------|
| skill/api 节点失败 | SkillResult 失败 → 节点失败中止，返回 FailedNodeId + Error |
| ai_node 调用失败/超时 | 重试 1 次（超时 30s 可配），仍失败 → 节点失败中止 |
| 分支未命中 / 循环空数组 | 记录 skipped，不报错，继续其余路径 |
| 提前终止（failure 未连线） | terminated 记录，end 用 default 解析，不整体失败 |
| 引用环 / 结构非法 | 校验期拦截，不进入执行 |

### 3.14 解释器与 Skill 的关系（核心关系阐述）

**总原则：所有 Skill（及其中介——节点、表、画布）都是为解释器执行做准备的。解释器不认识业务，它只做一件事：按流程把 Skill 串起来跑。** 具体分五层：

```
① 元数据层（准备）      wf_skill 5 表：描述每个 Skill 的输入表单/输出契约/反射信息/API 信息
                        → 画布据此生成节点、表单；校验器据此校验；解释器据此映射输出
② 注册层（加载）        SkillRegistry：按 skill_code 找到可执行实例（DI 内置 / 反射 / api 包装器 / ai_node）
                        → 解释器执行节点时通过 Get(skillCode) 拿到它
③ 调用层（执行）        解释器构造 SkillContext{Inputs(已灌数据), Config, NodeId, BusinessContext, Logger}
                        → 调 ExecuteAsync → 拿 SkillResult → 按输出契约映射到端口
④ 提示词层（组装）      skill_prompt / output_prompt / glossary 是解释器执行到 AI 节点时组装的输入
                        → 供 LLM 理解该 Skill 怎么用、结果怎么读、整体流程是什么
⑤ 校验层（约束）        output_strict 分级：强约束 Skill 输出严格校验；ai_node 弱约束放行
                        → 解释器执行结果可信、可预测
```

| 关系点 | 说明 |
|--------|------|
| **Skill 是解释器的执行单元** | 解释器按图遍历，每个 skill 节点 = 一次 SkillRegistry.Get + ExecuteAsync 调用；新增 Skill 只插表（登记即用），解释器零改动 |
| **表结构服务执行** | wf_skill_input 生成画布表单（让维护人员填对参数）、wf_skill_output 定义输出映射与校验、reflection/api 定义如何实例化——三者都是解释器执行前的"准备" |
| **提示词是执行期的组装物** | glossary（工作流级）、skill_prompt（Skill 级）、output_prompt（输出级）不驱动解释器，只在解释器执行到 AI 节点 / 第 3 层分析时被组装成 prompt |
| **内置特殊节点不落表** | start/logic/loop/end 是解释器原生能力（代码内置），端口口径与表注册 Skill 统一（§1.4），解释器无需区分来源 |
| **契约分级保执行可信** | 强约束 Skill 的输出在解释器内强校验（类型/端口），弱约束 ai_node 放行（结构由提示词定义，靠 TRACE 实际结果验证）——解释器既保证确定性部分的准确，又给 AI 部分留出自由度 |

### 3.15 与第 2/3 层的关系（时序）

```
第 1 层（解释器执行完成）  →  产出 OutputConfig + NodeOutputs + TRACE + Mermaid
第 2 层（序列化产物）       →  TRACE（真实数据）/ Mermaid（结构）——解释器执行过程的"留痕"
第 3 层（AI 语义分析）      →  消费第 1/2 层产物 + glossary + 判定要求 → 最终判定（NC/报告内容）
```

第 2/3 层都在解释器之后发生，不反向影响执行顺序。

### 3.16 工作流校验（九项）

> V4 §5.4 八项 + 第九项；由解释器在校验步（§3.4 ②）执行，保存与运行共用。

| # | 校验项 | 说明 |
|---|--------|------|
| 1 | 结构合法 | JSON 可解析，nodes/edges 结构完整 |
| 2 | 节点 Skill 存在 | skillCode 已登记且 is_active=1 |
| 3 | 端口 Schema 匹配 | 按 output_strict 分级校验（强约束严格 / 弱约束放行） |
| 4 | 端口引用可解析 | `nX.port` 目标存在（连线或命名引用）；未连线节点允许存在（独立测试），但引用端口必须可解析（连线/手动注入/默认值） |
| 5 | 无环 | 依赖图（边 ∪ 引用）拓扑排序不失败 |
| 6 | 数据源存在 | 数据源引用（field_ref/table_ref）有效 |
| 7 | 输出完整 | outputConfig 引用的端口存在 |
| 8 | 一对一 | 节点端口唯一性 |
| 9 | **logic 双分支完整性** | logic 节点 success/failure 锚点各至少一条出边（悬空分支 → 保存失败） |

## 四、节点体系（为解释器执行准备的输入）

> 本章定义解释器要执行的对象：节点分类、六种节点、输出契约、参数体系、注册链路。**全部内容服务于 §三 解释器的执行**。

### 4.1 节点分类与统一端口口径

| 类别 | 成员 | 定义位置 | 说明 |
|------|------|---------|------|
| **特殊节点**（7 种） | start / end / logic / ai / loop / docField / docTable | **前后端硬编码**，不落 wf_skill 表 | 前后端固定约定，前端硬编码面板/渲染/交互，后端硬编码执行逻辑 |
| **功能节点**（表注册 Skill） | ~~get_field~~/~~get_table~~/document_extract/compare/assemble（可扩展） | wf_skill 4 表（主表/输入/输出/反射） | **只有 method 型**（反射执行）；前端通用表单渲染（wf_skill_input 驱动），后端反射执行（wf_skill_reflection 驱动）。**注：get_field/get_table 已移除，改为前端特殊节点** |

**统一端口口径**：所有节点端口 = `name + type + prompt`；特殊节点在代码中按相同结构声明，功能节点在表中定义；引用语法统一 `nX.portName`——解释器、校验器、画布无需区分节点来源。

**关键约定**：特殊节点的 `classCode` 是固定编码（start/end/logic/ai/loop/docField/docTable），前端硬编码面板和渲染，后端硬编码执行逻辑。功能节点完全由 `wf_skill` 表注册驱动，新增功能节点不改引擎。

### 4.3 标准输出端口约定（V1.3 新增）

> **设计原则**：所有功能性 Skill 的输出统一为标准结构，下游节点统一引用 `nX.success` 判断是否成功，`nX.result` 取结果。新增 Skill 不需要考虑标准输出，只关注业务输出。

**标准输出端口（所有功能节点自动包含）**：

| 端口名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `success` | boolean | 是 | 是否执行成功 |
| `error` | string | 否 | 失败时的错误信息（成功时为空字符串） |
| `result` | json | 是 | 执行结果（业务数据，包含 Skill 自定义的所有输出端口） |

**实现方式**（V1.4）：`SkillExecutor.ExecuteAsync` 统一包装标准输出（反射调用静态方法）：
- 执行成功：`{ success: true, error: "", result: { ...原始输出 }, ...原始输出（平铺到顶层供兼容引用） }`
- 执行失败：`{ success: false, error: "错误信息", result: {} }`

**静态方法只需**：
1. 用 `[SkillParam]` 特性声明参数描述 + 绑定模式（BindMode / EnumSource）
2. 方法参数即为输入端口（反射自动分析 name/type/required/default/bindMode/enumSource）
3. 返回 `SkillResult.Ok(outputs)` 或 `SkillResult.Fail(error)`——标准端口由 SkillExecutor 自动包装

**已有 Skill 改造对照**（V1.4，仅 3 个，get_field/get_table/llm_extract 已移除）：

| Skill | 业务自定义输出（SkillResult.Ok 字典内容） | 标准端口（自动） |
|---|---|---|
| ~~get_field~~ | ~~已移除，改为前端特殊节点~~ | — |
| ~~get_table~~ | ~~已移除，改为前端特殊节点~~ | — |
| compare | compare_result | success/error/result |
| assemble | assembled_text | success/error/result |
| document_extract | sections/tables/full_text/source_type/file_name/effective_path/is_converted_version | success/error/result |
| ~~llm_extract~~ | ~~已废弃~~ | — |

#### 4.2.2 ai_node（弱约束，对标扣子"大模型节点"）

```json
{ "nodeId": "n4", "title": "资源充分性判定", "skillCode": "ai_node",
  "config": { "prompt": "依据输入的人员名单 {{input.collection}} 判断资源是否充分，输出 JSON：{\"qualified\":bool,\"reason\":string}", "jsonMode": true },
  "inputs": { "collection": "n1.rows" },
  "outputs": { "content": "string", "json": "json", "confidence": "number" } }
```

| 要素 | 设计 |
|------|------|
| 输入 | 动态命名参数（画布节点声明，引用上游/上下文/手动值）；不走静态输入表 |

| 输出 | 弱约束通用端口 content/json/confidence；结构由提示词定义 |

#### 4.2.3 logic（多条件 + 双分支）

```json
{ "nodeId": "n3", "nodeType": "logic", "title": "数量且类型判断",
  "conditions": [
    { "valueA": "n1.fieldValue", "operator": "gte", "valueB": 1 },
    { "valueA": "ctx.hazardType", "operator": "eq", "valueB": "危险化学品" }
  ],
  "conditionLogic": "and",
  "outputs": { "result": "boolean" } }
```

| 要素 | 设计 |
|------|------|
| 操作符集 | `gt / gte / lt / lte / eq / neq / contains / not_contains`（8 种，可扩展）。比较语义：数值强转、日期按日期、contains 支持字符串子串与数组成员、eq/neq 宽松比较 |
| 多条件组合 | conditions[] + `conditionLogic`(and/or)，单层组合（对标 n8n IF）；嵌套分组（(A or B) and C）列为扩展点，不进 v1 |
| 条件引用 | 每条 condition 的 valueA/valueB 支持字面量 / `nX.port` 引用 / 模板（与 §3.6 一致） |
| 输出 | 数据端口 `result`(boolean)（下游可 `nX.result` 引用，不依赖连线） |
| 路由 | **两个源锚点**：`success`（满足）/ `failure`（不满足），连线从哪个锚点引出就走哪个分支；**双分支必连（校验第九项）** |
| 提前终止 | 未连线的分支 = 隐式提前终止（terminated），end 用 default 解析（合法路径，非异常）——执行语义见 §3.8 |

#### 4.2.4 start / end

```
start：仅输出端口，声明工作流输入（enterpriseCode/standardCode/phaseCode/fileCode）→ 引擎注入
end：  仅输入端口，多分支汇聚；outputConfig 每引用独立解析（ref + default）——执行语义见 §3.9
```

#### 4.2.5 loop（统一端口，v1 提示词驱动）

```
输入 collection（上游输出数组）；输出 results(json)——执行语义见 §3.10
```

### 4.3 输出契约：强 / 弱分级

| 级别 | 适用 | 定义 | 校验 | 下游引用 |
|------|------|------|------|---------|
| **强约束**（output_strict=1） | 确定性 skill：get_field/get_table/compare/assemble/document_extract/llm_extract | `wf_skill_output` 严格定义端口 + 5 类型 | 保存/运行强校验（解释器内） | 安全：`nX.port` 类型确定 |
| **弱约束**（output_strict=0） | ai_node / loop | 固定通用端口 content(string)/json(json)/confidence(number)（loop: results(json)），**具体结构由提示词定义** | 放行任意输入、通用输出 | 引用 `nX.json`，具体字段靠 TRACE 实际结果 / 人工 / AI 理解 |

输出类型统一 5 种：`string / number / date / boolean / json`（复杂结构一律 json）。

### 4.4 参数体系：命名 + 引用模板（对标 n8n/扣子）

每个节点 `inputs` 是**命名参数集合**（节点保存时在画布上确定，可增删），值支持三种形态（常量 / 变量 / 模板拼接，解析规则见 §3.6）：

| 值形态 | 示例 | 说明 |
|--------|------|------|
| **常量**（固定值） | `"operator": ">="`、`"fixedText": "该企业不符合"` | 直接输入，不解析——报告/NC 输出中的固定文案即常量 |
| **变量**（单引用） | `"value": "n1.fieldValue"` | 引用节点输出（**不依赖连线**）/ `ctx.xxx` 上下文 / `$sys.xxx` 系统参数 |
| 模板拼接（常量+变量混合） | `"prompt": "条款{{ctx.clauseCode}} 分值是{{n2.fieldValue}}"` | 双大括号内多引用，整体替换；数组/对象内同样递归解析 |

**assemble（字符串拼接，用户定调）**：parts 数组支持**任意数量**元素，常量与变量**按顺序混合**拼接成符合要求的字符串（如报告引言固定文案 + 变量值 + 结尾固定文案）；元素为字符串/数字/布尔/引用均可，`joiner` 指定连接符（可空=直接拼接）。这是报告章节与 NC 描述生成的核心手段。

**节点必须命名**：拖入画布自动生成唯一 nodeId（可编辑 title），`nX.portName` 按名引用，**与是否连线无关**。

### 4.5 系统参数解析（`$sys.`）

- 语法：`$sys.<路径>`（如 `$sys.SKILL_API_KEY_LLM` 环境变量 / `$sys.llm.apiKey` 系统配置点分路径）
- 解析器：`ISysConfigResolver`，顺序：环境变量 → 系统配置 → null（报明确错误）
- 使用位置：api url / headers / auth_config（**密钥不落库**）/ 输入默认值

### 4.6 注册与执行链路

| 路径 | 适用 | 注册 | 执行 |
|------|------|------|------|
| 内置 method | 平台自带（6 个） | YZHModule DI 注册（现状保留） | ISkillNode 实例 |
| 自定义 method | 项目内新增 C# Skill | wf_skill_reflection 登记 class_path，运行期反射加载（**默认路径**，DI 容器实例化） | 反射调用 ExecuteAsync |
| api | 外部 HTTP 服务 | wf_skill_api 登记（url/鉴权/参数映射/响应解析） | HttpApiSkillNode 包装器 |
| **ai_node** | LLM 能力 | wf_skill 登记（output_strict=0） | AiNodeSkill（提示词 → LLM） |
| **内置特殊节点** | start / logic / loop / end | 代码内置，**不落表** | 解释器直接执行（端口口径与表注册一致） |

**登记即用**：表内登记 + 注册成功（is_active=1）才算可用；新增 Skill 不改代码、不改前端——解释器零改动（§3.14）。

## 七、数据流 / 时序

### 7.1 设计期（维护人员）


### 7.2 执行期（解释器第 1 层确定性遍历）

```

  → 解析 → 校验（九项）→ 建依赖图（边 ∪ 命名引用）→ 拓扑排序

  → end 汇聚解析 outputConfig（ref+default）｜ 提前终止（failure 分支未连线 → terminated）
  → 返回 WorkflowRunResult（OutputConfig + TRACE + Mermaid）→ 上层消费
```

### 7.3 调试期（单步调试，底座 P0）

```
选中工作流 → 调试模式
  step 1: start + n1 → 展示 n1 输入/输出（TRACE）→ 继续

```

```

  → 消费：写 audit_nonconformity / section_content
```
