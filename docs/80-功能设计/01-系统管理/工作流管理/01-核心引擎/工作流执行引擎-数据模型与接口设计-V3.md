## 一、数据全景：三类信息

工作流配置保存到数据库时，拆分为 **3 类独立信息**：

```
cert_validation_rule
  ├── rule_json      → 节点配置 + 拓扑关系（执行引擎读取）
  ├── layout_json    → 画布布局（仅 UI 恢复用，执行引擎不读）
  └── rule_name 等   → 业务字段
```

| # | 信息类别 | 存储字段 | 执行引擎是否读取 | 说明 |
|---|---------|---------|----------------|------|
| 1 | **节点配置** | `rule_json` 内的 `nodes[]` | ✅ 读取 | 每个节点的类型、名称、配置、输入绑定、端口声明 |
| 2 | **拓扑关系** | `rule_json` 内的 `edges[]` | ✅ 读取 | 节点间的连线关系、branch 的 success/failure 分支 |
| 3 | **画布布局** | `layout_json` | ❌ 不读取 | 节点坐标，仅用于画布恢复显示 |

## 二、节点配置（Node Config）

### 2.1 单个节点的数据结构

```json
{
  "nodeId": "docField_n1",
  "nodeType": "docField",
  "title": "营业执照",
  "skillCode": "",
  "config": {
    "docType": "standard",
    "ruleCode": "b9938691...",
    "fieldCode": "HR_COUNT",
    "fieldName": "企业人员数量"
  },
  "inputs": {},
  "inputPorts": [],
  "outputPorts": [
    { "name": "fieldValue", "type": "string", "display": "visible" }
  ]
}
```

### 2.2 节点字段定义

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `nodeId` | string | ✅ | 唯一标识，格式 `{classCode}_n{序号}`，如 `start_n1`、`docField_n2` |
| `nodeType` | string | ✅ | 节点类型：`start` / `end` / `branch` / `docField` / `docTable` / `ai_node` / `skill` |
| `title` | string | ✅ | 用户自定义名称（画布显示名），全流程唯一 |
| `skillCode` | string | ⬚ | 功能节点的 Skill 编码（如 `compare`、`assemble`），非功能节点为空 |
| `config` | object | ✅ | 节点特有配置（按 nodeType 不同结构不同，见 2.3） |
| `inputs` | object | ✅ | 输入参数绑定（portName → 值，见 2.4） |
| `inputPorts` | array | ✅ | 输入端口声明（定义有哪些输入端口、bindMode） |
| `outputPorts` | array | ✅ | 输出端口声明（定义有哪些输出端口、数据类型） |

### 2.3 各节点类型的 config 结构

#### start 节点
```json
{}
```
> 无配置。运行时引擎自动注入上下文参数（enterpriseCode、phaseCode、standardCode、fileCode）。

#### end 节点
```json
{
  "successField": "result",
  "errorField": "error"
}
```
> end 节点输出统一结构：`{ success: bool, error: string|null, result: any }`，作为 NC 最终结果写入。

#### branch 节点
```json
{}
```
> 无配置。branch 不含比较逻辑，只消费上游 compare 节点输出的 bool 结果进行分流。

#### docField 节点
```json
{
  "docType": "standard",
  "ruleCode": "b9938691...",
  "fieldCode": "HR_COUNT",
  "fieldName": "企业人员数量"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `docType` | enum | `standard`（标准文档，配置期验证）/ `enterprise`（企业文档，运行期提取） |
| `ruleCode` | string | 标准文档提取规则编码（关联 `cert_doc_extraction_rule.Code`） |
| `fieldCode` | string | 字段编码（关联 `cert_doc_field_def.FieldCode`） |
| `fieldName` | string | 字段显示名（冗余，面板展示用） |

#### docTable 节点
```json
{
  "docType": "standard",
  "ruleCode": "b9938691...",
  "tableCode": "ORG_STAFF_TABLE",
  "tableName": "人员花名册"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `docType` | enum | 同 docField |
| `ruleCode` | string | 标准文档提取规则编码 |
| `tableCode` | string | 表格编码（关联 `cert_doc_table_def.TableCode`） |
| `tableName` | string | 表格显示名（冗余） |

#### ⏳ ai_node 节点（V3 暂不实现）

> **TODO**：AI 节点极其复杂，需要前后端完整的匹配约束规则。AI 节点可以调用当前工作流中已执行节点的方法，引用其执行结果，但需要定义：
> - AI 提示词中 `{{nodeId.portName}}` 引用格式
> - AI 可调用的功能节点白名单
> - AI 输出结果的标准化格式
>
> **当前策略**：先跑通普通节点流程，AI 节点作为后续 TODO 单独实现。

#### skill 功能节点（如 compare）
```json
{
  "operator": "gte",
  "threshold": "10"
}
```
> config 结构由 Skill 的 `inputPorts` 定义决定，不同 Skill 不同。

### 2.4 输入参数绑定（inputs）

`inputs` 是一个 map，key 是端口名，value 是绑定值。

```json
{
  "actual": "get_field_n1",
  "expected": "constant:10",
  "operator": "gte"
}
```

**值的两种格式**：

| 格式 | 含义 | 解析规则 |
|------|------|---------|
| `"源节点ID"`（如 `"get_field_n1"`） | 引用上游节点输出 | 执行时从缓存或 `wf_node_execution.output_json` 读取 |
| `"constant:值"`（如 `"constant:10"`） | 常量 | 截取 `constant:` 后面的部分，直接使用 |

**解析伪代码**：
```
function resolveInput(value, upstreamOutputs):
    if value starts with "constant:":
        return value.substring("constant:".length)
    else:
        // value 是源节点 ID
        return upstreamOutputs[value]  // 该节点的完整输出
```

### 2.5 端口声明（inputPorts / outputPorts）

```json
{
  "name": "actual",
  "label": "比较值A",
  "type": "string",
  "bindMode": "Link",
  "required": true,
  "maxIn": 1,
  "display": "visible"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | 端口名称（inputs 的 key） |
| `label` | string | 显示名称 |
| `type` | string | 数据类型：`string` / `number` / `boolean` / `json` / `signal` |
| `bindMode` | enum | `Link`（仅连线）/ `LinkOrConstant`（可连线可输入）/ `Enum`（字典选择） |
| `required` | boolean | 是否必填 |
| `maxIn` | number | 最大入边数（默认 1，end 节点的 result 端口 = 999） |
| `display` | enum | `visible`（面板显示）/ `hidden`（面板隐藏） |
| `role` | enum | `data`（数据端口）/ `anchor`（控制流锚点，如 branch 的 success/failure） |
| `enumSource` | string | 字典来源（仅 Enum 模式） |
| `defaultValue` | any | 默认值 |

## 三、拓扑关系（Topology）

### 3.1 单条边的数据结构

```json
{
  "source": "compare_n1",
  "target": "branch_n1",
  "sourceHandle": null,
  "targetHandle": "condition"
}
```

### 3.2 边字段定义

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `source` | string | ✅ | 源节点 ID |
| `target` | string | ✅ | 目标节点 ID |
| `sourceHandle` | string | ⬚ | 源输出端口。branch 节点区分 `success` / `failure`，其他节点为 `null` |
| `targetHandle` | string | ⬚ | 目标输入端口名（如 `condition`、`result`），无特定端口时为 `null` |

### 3.3 拓扑规则

1. **每个节点至少有一条入边**（start 节点除外）
2. **每个节点至少有一条出边**（end 节点除外）
3. **branch 节点必须有 2 条出边**：一条 `sourceHandle=success`，一条 `sourceHandle=failure`
4. **无环**：不允许出现循环引用
5. **可达**：所有节点必须从 start 可达

### 3.4 路径枚举算法

```
function enumeratePaths(nodes, edges):
    paths = []
    startNode = find(n => n.nodeType == "start")
    dfs(startNode, [], paths)
    return paths

function dfs(currentNode, currentPath, paths):
    currentPath.append(currentNode)
    
    if currentNode.nodeType == "end":
        paths.append(currentPath.copy())
        return
    
    outEdges = edges.filter(e => e.source == currentNode.id)
    
    if currentNode.nodeType == "branch":
        // branch 必须有 success 和 failure 两条出边
        successEdge = outEdges.find(e => e.sourceHandle == "success")
        failureEdge = outEdges.find(e => e.sourceHandle == "failure")
        dfs(successEdge.target, currentPath, paths)
        dfs(failureEdge.target, currentPath, paths)
    else:
        // 普通节点：走唯一出边
        for edge in outEdges:
            dfs(edge.target, currentPath, paths)
```

## 四、执行模型（Execution Model）

### 4.1 核心执行规则

#### 原则 1：路径间可并行，路径内节点阻塞

```
NC 检查项 1: [start] → [docField] → [compare] → [branch] → [end_pass]
NC 检查项 2: [start] → [docField] → [assemble] → [end]          ← 与项1并行
NC 检查项 3: [start] → [docField] → [compare] → [branch] → [end_pass] ← 与项1、2并行
```

- **路径间**（不同 NC 检查项之间）：可以并行执行，系统参数 `wf.max_parallel_items` 控制并发数
- **路径内**（同一 NC 检查项的不同路径）：**节点阻塞**，一个节点完成后再执行下一个
- **同一路径**：严格串行，`[node1] → [node2] → [node3]`

#### 原则 2：节点失败 = 当前路径终止，继续下一路径

```
路径1: [start] → [docField_A] → [compare] → [branch] → [end_pass]  ✅ 完成
路径2: [start] → [docField_B] → [compare] → 💥 失败                 ❌ 路径终止
路径3: [start] → [docField_C] → [assemble] → [end]                  ✅ 继续执行
```

- 节点执行异常 → 当前路径**立即终止**（不重试、不继续后续节点）
- 已执行的节点结果保留（`wf_node_execution` 中有记录）
- 其他路径**不受影响**，正常继续执行

#### 原则 3：NC 结果在所有路径终结后写入

- 所有路径都到达 end 节点（或因失败终止） → 工作流完成
- **如果所有路径都失败**：NC 结果标记为"失败"，注明失败原因
- **如果有任何路径成功**：NC 结果标记为"通过"
- **如果所有路径都走完了但没有有效结果**：那是流程配置设计不合理，不是执行引擎问题

### 4.2 执行流程图

### 4.3 跨路径复用规则

```
已执行过的节点不重复执行：
- 同一个 task_code + item_code + node_id → 只执行一次
- 后续路径遇到同一节点 → 从 wf_node_execution.output_json 读取结果
- 这是路径驱动的核心优势：branch 分叉后，公共节点不需要重跑
```

## 五、docField / docTable 文件来源解析

### 5.1 文件来源的核心逻辑

**两种场景的文件来源**：

| 场景 | docType | 文件来源 | 说明 |
|------|---------|---------|------|
| **节点测试** | `standard` | 标准文档 | 从 `cert_doc_extraction_rule` 关联的标准文档获取 |
| **正式执行** | `enterprise` | 企业文档 | 通过任务主表 → 企业编码 → 企业文档 + 标准目录匹配 |

### 5.2 标准文档模式（节点测试 / 配置验证）

```
docType = "standard"

解析链路：
1. 从 node.config.ruleCode → cert_doc_extraction_rule（提取规则）
2. 从 rule.standardFileCode → 标准文档文件路径
3. 从 node.config.fieldCode → cert_doc_field_def（字段定义）
4. 从 rule.sample_data 或 doc_content → 提取字段值

数据来源：
- cert_doc_extraction_rule（提取规则，含 ruleCode、标准文件编码、skill类型）
- cert_doc_field_def（字段定义，含 fieldCode、xpath/cellRef 等）
- sample_data（规则的示例数据，配置期验证用）
```

### 5.3 企业文档模式（正式执行）

```
docType = "enterprise"

解析链路：
1. 从 task.enterpriseCode → 企业编码
2. 从 task.phaseCode → 阶段编码
3. 通过企业 + 阶段 → ent_enterprise_file（企业上传的文档列表）
4. 通过标准目录结构匹配 → 找到对应的文档（standard_file_code 匹配）
5. 从匹配到的文档 → 提取字段/表格值

数据来源：
- wf_execution_task（任务主表，含 enterpriseCode、phaseCode、standardCode）
- ent_enterprise_file（企业文档，含 standardFileCode 与标准目录的映射）
- cert_doc_extraction_rule（提取规则，含字段的 xpath/cellRef 定义）
```

### 5.4 docField 执行逻辑

```
function executeDocField(node, task):
    config = node.config
    
    if config.docType == "standard":
        // 标准文档模式：直接从 sample_data 读取
        rule = queryCertDocExtractionRule(config.ruleCode)
        field = queryCertDocFieldDef(config.ruleCode, config.fieldCode)
        value = extractFromSampleData(rule.sampleData, field.Xpath)
        return { fieldValue: value, confidence: 1.0, source: "sample_data" }
    
    else if config.docType == "enterprise":
        // 企业文档模式：通过任务找到企业文档，再提取
        file = matchEnterpriseFile(task.enterpriseCode, task.phaseCode, config.ruleCode)
        if file == null:
            return { fieldValue: null, confidence: 0, error: "未找到对应企业文档" }
        field = queryCertDocFieldDef(config.ruleCode, config.fieldCode)
        value = extractFromFile(file.FilePath, field.Xpath)
        return { fieldValue: value, confidence: file.Confidence, source: "enterprise_doc" }
```

### 5.5 docTable 执行逻辑

```
function executeDocTable(node, task):
    // 与 docField 类似，区别在于提取的是表格而非字段
    config = node.config
    
    if config.docType == "standard":
        rule = queryCertDocExtractionRule(config.ruleCode)
        table = queryCertDocTableDef(config.ruleCode, config.tableCode)
        rows = extractTableFromSampleData(rule.sampleData, table.CellRef)
        return { rows: rows, confidence: 1.0, source: "sample_data" }
    
    else if config.docType == "enterprise":
        file = matchEnterpriseFile(task.enterpriseCode, task.phaseCode, config.ruleCode)
        table = queryCertDocTableDef(config.ruleCode, config.tableCode)
        rows = extractTableFromFile(file.FilePath, table.CellRef)
        return { rows: rows, confidence: file.Confidence, source: "enterprise_doc" }
```

  "nodePositions": {

## 八、详细日志输出规范

> **V3 新增**：日志是执行过程的完整记录，既是调试工具，也是未来持久化的数据源。

### 8.1 日志设计原则

1. **每个关键步骤必须有日志**：任务创建、缓存预热、节点执行、路径决策、结果聚合
2. **日志格式统一**：便于解析和持久化
3. **日志级别分明**：INFO（正常流程）、WARN（异常但可恢复）、ERROR（失败）
4. **日志可追溯**：每条日志包含 taskCode + itemCode + nodeId，便于定位

### 8.2 日志输出时机与内容

#### 8.2.1 任务生命周期日志

| 时机 | 级别 | 日志内容 | 示例 |
|------|------|---------|------|
| 任务创建 | INFO | `[TASK_CREATE] taskCode={code}, taskType={type}, ruleCode={rule}, enterprise={ent}` | `[TASK_CREATE] taskCode=abc123, taskType=TEST, ruleCode=VR-001, enterprise=YZH-STD-ENT` |
| 缓存预热开始 | INFO | `[CACHE_WARMUP_START] taskCode={code}, nodeCount={n}` | `[CACHE_WARMUP_START] taskCode=abc123, nodeCount=6` |
| 缓存预热完成 | INFO | `[CACHE_WARMUP_DONE] taskCode={code}, cachedKeys={n}, durationMs={ms}` | `[CACHE_WARMUP_DONE] taskCode=abc123, cachedKeys=4, durationMs=2300` |
| 任务开始执行 | INFO | `[TASK_START] taskCode={code}, itemCount={n}` | `[TASK_START] taskCode=abc123, itemCount=1` |
| 任务执行完成 | INFO | `[TASK_DONE] taskCode={code}, status={status}, durationMs={ms}` | `[TASK_DONE] taskCode=abc123, status=completed, durationMs=5600` |
| 缓存清理 | INFO | `[CACHE_CLEANUP] taskCode={code}, cleanedKeys={n}` | `[CACHE_CLEANUP] taskCode=abc123, cleanedKeys=4` |

#### 8.2.2 Item 执行日志

| 时机 | 级别 | 日志内容 | 示例 |
|------|------|---------|------|
| Item 开始 | INFO | `[ITEM_START] taskCode={tc}, itemCode={ic}, ruleCode={rule}` | `[ITEM_START] taskCode=abc123, itemCode=def456, ruleCode=VR-001` |
| 路径枚举 | INFO | `[PATH_ENUM] taskCode={tc}, itemCode={ic}, pathCount={n}` | `[PATH_ENUM] taskCode=abc123, itemCode=def456, pathCount=2` |
| 路径执行开始 | INFO | `[PATH_START] taskCode={tc}, itemCode={ic}, pathIndex={i}, nodeCount={n}` | `[PATH_START] taskCode=abc123, itemCode=def456, pathIndex=0, nodeCount=5` |
| 路径执行完成 | INFO | `[PATH_DONE] taskCode={tc}, itemCode={ic}, pathIndex={i}, status={status}` | `[PATH_DONE] taskCode=abc123, itemCode=def456, pathIndex=0, status=completed` |
| 路径执行失败 | WARN | `[PATH_FAIL] taskCode={tc}, itemCode={ic}, pathIndex={i}, failedAt={nodeId}, error={msg}` | `[PATH_FAIL] taskCode=abc123, itemCode=def456, pathIndex=1, failedAt=compare_n3, error=Value cannot be null` |
| Item 完成 | INFO | `[ITEM_DONE] taskCode={tc}, itemCode={ic}, isSuccess={bool}, durationMs={ms}` | `[ITEM_DONE] taskCode=abc123, itemCode=def456, isSuccess=true, durationMs=3200` |

#### 8.2.3 节点执行日志（核心）

| 时机 | 级别 | 日志内容 | 示例 |
|------|------|---------|------|
| 节点开始 | INFO | `[NODE_START] taskCode={tc}, itemCode={ic}, nodeId={id}, nodeType={type}, title={title}` | `[NODE_START] taskCode=abc123, itemCode=def456, nodeId=docField_n2, nodeType=docField, title=营业执照` |
| 节点输入解析 | INFO | `[NODE_INPUTS] taskCode={tc}, itemCode={ic}, nodeId={id}, inputs={json}` | `[NODE_INPUTS] taskCode=abc123, itemCode=def456, nodeId=compare_n3, inputs={"value_a":"docField_n2","value_b":"constant:10"}` |
| 节点执行中 | INFO | `[NODE_EXEC] taskCode={tc}, itemCode={ic}, nodeId={id}, action={action}` | `[NODE_EXEC] taskCode=abc123, itemCode=def456, nodeId=docField_n2, action=querying_standard_doc` |
| 节点输出 | INFO | `[NODE_OUTPUT] taskCode={tc}, itemCode={ic}, nodeId={id}, output={json}, durationMs={ms}` | `[NODE_OUTPUT] taskCode=abc123, itemCode=def456, nodeId=docField_n2, output={"fieldValue":"91110000XXXX","confidence":1.0}, durationMs=150` |
| 节点成功 | INFO | `[NODE_DONE] taskCode={tc}, itemCode={ic}, nodeId={id}, status=completed, durationMs={ms}` | `[NODE_DONE] taskCode=abc123, itemCode=def456, nodeId=docField_n2, status=completed, durationMs=150` |
| 节点失败 | ERROR | `[NODE_FAIL] taskCode={tc}, itemCode={ic}, nodeId={id}, error={msg}, durationMs={ms}` | `[NODE_FAIL] taskCode=abc123, itemCode=def456, nodeId=compare_n3, error=Value cannot be null, durationMs=50` |
| 节点复用 | INFO | `[NODE_REUSE] taskCode={tc}, itemCode={ic}, nodeId={id}, reusedFrom={existingNodeId}` | `[NODE_REUSE] taskCode=abc123, itemCode=def456, nodeId=start_n1, reusedFrom=start_n1` |

#### 8.2.4 节点类型特定日志

| 节点类型 | 日志内容 | 示例 |

| **start** | `[START_INJECT] enterpriseCode={ent}, phaseCode={phase}, standardCode={std}` | `[START_INJECT] enterpriseCode=YZH-STD-ENT, phaseCode=S1, standardCode=ISO9001` |

## 九、任务级缓存方案

### 9.1 缓存生命周期

```
任务开始（CreateTaskAsync）
  │
  ├── 1. 锁定 config_snapshot（从 rule_json）
  ├── 2. 解析 nodes → 识别需要哪些文档数据
  │      ├── docField 节点 → 需要 ruleCode + fieldCode
  │      ├── docTable 节点 → 需要 ruleCode + tableCode
  │      └── skill 节点 → 需要 skillCode
  │
  ├── 3. 批量预热缓存
  │      ├── 标准文档字段：wf:task:{taskCode}:doc:field:{ruleCode}:{fieldCode}
  │      ├── 标准文档表格：wf:task:{taskCode}:doc:table:{ruleCode}:{tableCode}
  │      ├── 企业文档字段：wf:task:{taskCode}:ent:field:{enterpriseCode}:{ruleCode}:{fieldCode}
  │      ├── 企业文档表格：wf:task:{taskCode}:ent:table:{enterpriseCode}:{ruleCode}:{tableCode}
  │      └── Skill 配置：wf:task:{taskCode}:skill:{skillCode}
  │
  └── 4. 缓存就绪，开始执行
          │
          ├── 并行执行 N 个 item
          │     └── 每个 item 的节点执行时，直接读缓存
          │
          └── 所有 item 完成
                │
                └── 清理缓存：DEL wf:task:{taskCode}:*
```

### 9.2 缓存键设计

```
wf:task:{taskCode}:doc:field:{ruleCode}:{fieldCode}  → 标准文档字段值
wf:task:{taskCode}:doc:table:{ruleCode}:{tableCode}  → 标准文档表格数据
wf:task:{taskCode}:ent:field:{entCode}:{ruleCode}:{fieldCode}  → 企业文档字段值
wf:task:{taskCode}:ent:table:{entCode}:{ruleCode}:{tableCode}  → 企业文档表格数据
wf:task:{taskCode}:skill:{skillCode}  → Skill 配置
```

### 9.3 优势

1. **无失效问题**：任务结束直接 `DEL wf:task:{taskCode}:*`，不需要在每个写入点触发清除
2. **数据一致性**：任务开始时快照，执行过程中数据不变
3. **实现简单**：只需要在 `CreateTaskAsync` 和 `TaskComplete` 两处处理
4. **并行安全**：多个 item 读同一缓存键，无竞争

### 9.4 性能对比

| 场景 | 无缓存 | 任务级缓存 |
|------|--------|-----------|
| 单次工作流（5 节点） | 5 次 DB | 0 次（全命中） |
| 10 个检查项并行 | 50 次 DB | 0 次 |
| 同一文档多字段 | N 次查同一规则 | 1 次预热 + 0 次执行时查询 |
| 任务开始开销 | 0 | 批量加载（约 2-5 秒） |
| 任务结束清理 | 0 | DEL 缓存键（约 0.1 秒） |

## 十、后端执行引擎解析规则

### 10.1 解析流程

```
输入：rule_json 字符串
输出：可执行的工作流模型

步骤：
1. JSON 反序列化 → 得到 nodes[] + edges[]
2. 构建邻接表：adj[nodeId] = [outEdge...]（按 sourceHandle 排序）
3. 构建入边表：inEdges[nodeId] = [inEdge...]
4. 找到 start 节点（nodeType == "start"）
5. 枚举所有路径（DFS，branch 按 success/failure 分叉）
6. 返回：{ startNode, paths, adjacency, nodeMap }
```

### 10.2 节点执行规则

```
function executeNode(node, task, upstreamOutputs):
    switch node.nodeType:
        case "start":
            // 注入上下文参数
            return { enterpriseCode, phaseCode, standardCode, fileCode }
        
        case "docField":
            // 按 docType 解析文件来源（见第五章）
            // standard → 从缓存或 sample_data 读取
            // enterprise → 从缓存或企业文档读取
            return { fieldValue, confidence, source }
        
        case "docTable":
            // 同 docField，读取表格数据
            return { rows, confidence, source }
        
        case "skill":
            // 解析 inputs（resolveInput）
            // 反射调用 SkillExecutor.ExecuteAsync()
            return { success, error, result }
        
        case "ai_node":
            // ⏳ V3 暂不实现
            throw new NotImplementedException("AI 节点将在后续版本实现")
        
        case "branch":
            // 读取 condition 输入的 bool 值
            // bool == true → 走 success 出边
            // bool == false → 走 failure 出边
            return { decision: "success" | "failure" }
        
        case "end":
            // 汇聚上游结果，输出标准格式
            return {
                success: true,
                error: null,
                result: upstreamOutput
            }
```

### 10.3 节点失败处理

```
function executeNodeWithFailureHandling(node, task, upstreamOutputs):
    try:
        result = executeNode(node, task, upstreamOutputs)
        // 写入 wf_node_execution（status = completed）
        saveNodeExecution(task.code, item.code, node.nodeId, "completed", result)
        return { success: true, output: result }
    
    catch (Exception ex):
        // 节点执行失败 → 当前路径终止
        saveNodeExecution(task.code, item.code, node.nodeId, "failed", { error: ex.Message })
        
        // ⚠️ 关键：不抛异常，返回失败标志
        return { success: false, error: ex.Message }
```

### 10.4 路径执行（串行阻塞）

```
function executePath(path, task, item, sharedOutputs):
    for node in path:
        // 检查是否已执行过（跨路径复用）
        existing = queryNodeExecution(task.code, item.code, node.nodeId)
        if existing != null && existing.status == "completed":
            sharedOutputs[node.nodeId] = existing.output
            continue
        
        // 解析输入参数
        upstreamOutputs = resolveInputs(node.inputs, sharedOutputs)
        
        // 执行节点（阻塞）
        result = executeNodeWithFailureHandling(node, task, upstreamOutputs)
        
        if !result.success:
            return { pathStatus: "failed", failedAt: node.nodeId, error: result.error }
        
        sharedOutputs[node.nodeId] = result.output
    
    return { pathStatus: "completed", output: sharedOutputs[path.last] }
```

### 10.5 工作流执行（所有路径终结后写入 NC 结果）

```
function runWorkflow(task, items):
    for each item in items (并行，受 max_parallel_items 控制):
        config = deserialize(item.config_snapshot)
        paths = enumeratePaths(config.nodes, config.edges)
        
        sharedOutputs = {}
        pathResults = []
        
        for path in paths:
            result = executePath(path, task, item, sharedOutputs)
            pathResults.append(result)
        
        ncResult = aggregateNcResult(pathResults)
        saveItemResult(task.code, item.code, ncResult)

function aggregateNcResult(pathResults):
    successPaths = pathResults.filter(r => r.pathStatus == "completed" && r.output.endNodeType == "通过")
    failedPaths = pathResults.filter(r => r.pathStatus == "failed")
    
    if successPaths.length > 0:
        return { success: true, error: null, result: successPaths[0].output }
    else if failedPaths.length > 0:
        return { success: false, error: failedPaths.map(f => f.error).join("; "), result: null }
    else:
        return { success: false, error: "所有路径均无有效结果，工作流配置可能不合理", result: null }
```

### 路径 1：配置验证（前端传 JSON）

6. 返回每个节点的执行结果
7. 清理缓存
```

### 路径 2：正式执行（后端读 rule_json）

```
审核员点击「开始审核」→ POST /api/workflow/run

后端处理：

## 十二、NC 结果（wf_item_result）结构

### 12.1 统一结果格式

```json
{
  "success": true,
  "error": null,
  "result": {
    "decision": "pass",
    "confidence": 0.95,
    "evidence": "人员数量 12 ≥ 10"
  }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `success` | boolean | 该路径/节点是否成功执行 |
| `error` | string | 失败原因（成功时为 null） |
| `result` | any | 具体结果值（bool / string / json 等） |

### 12.2 NC 最终结果写入时机

```
写入时机：所有路径终结后（成功或失败）
写入内容：
  - auto_result.success → 是否通过
  - auto_result.error → 失败原因（所有失败路径的原因汇总）
  - auto_result.result → 最终结果值（来自成功路径的 end 节点输出）
  - auto_result.executedPaths → 执行了哪些路径
  - auto_result.failedAt → 哪个节点失败（如有）
  - item.is_success → 业务成功标志（true/false）
```

## 十三、数据库表关系

```
cert_validation_rule（已有，配置定义）
  ├── rule_code + rule_json → 工作流拓扑 + 节点属性
  └── 被 wf_execution_task.config_snapshot 引用

wf_execution_task（新增，一次执行）
  ├── config_snapshot → 从 rule_json 锁定的快照
  ├── cache_keys → 预热的缓存键列表
  └── 1:N → wf_execution_task_item（每个检查项）
              ├── rule_code → 关联配置定义
              ├── is_success → 业务成功标志
              ├── cache_keys → 预热的缓存键列表
              └── 1:N → wf_node_execution（每个节点的执行状态）
                          ├── node_id + exec_status → 跨路径复用的核心
                          └── output_json → 节点输出

wf_item_result（后续加，企业维度的 NC 结果）
  └── 通过 task_code + rule_code 关联到执行记录
      └── auto_result / manual_result → 支持人工修改
```
