# 工作流节点定义与属性抽象 V1

> 创建日期：2026-08-20  
> 状态：设计定稿（V1.2，2026-08-20 修订）  
> 关联文件：`specialNodes.js` / `SkillPanel.vue` / `NodePropertyForm.vue` / `index.vue` / `compiler.js`
>
> V1.2 变更：docField/docTable 增加 docType（standard/enterprise）双态设计 + 配置期验证；AI 节点提示词编辑器增加「可用功能/可用数据」选择器 + 引用插入 + 标准输出包装；AI 节点可引用其他节点结果组织到 Skill 方法中。
>
> V1.1：移除 loop 节点（复杂循环由 AI 节点提示词解决）；AI 提示词规则独立成稿；end 语义收敛（汇聚上游唯一节点输出，不配置结论）；底层引用统一节点 id、界面显示中文别名。

## 一、设计目标

1. **统一元数据源**：所有节点定义集中在 `specialNodes.js`，消除 SkillPanel / NodePropertyForm / compiler 各持一份的混乱
2. **属性面板抽象**：基于端口 `bindMode` 三分法统一渲染，不再每种节点一个 `v-if` 硬编码
3. **连线即拓扑**：连线不仅传递数据，还定义从 start 到 end 的完整拓扑路径；一个流程图可能有多条拓扑线路，这是流程执行和测试的依据
4. **严格定义边界**：每种节点明确输入/输出/可改名/可测试/单例，不严格定义后续开发必然混乱

## 二、节点分类

### 2.1 特殊节点（前端硬编码，不落 wf_skill 表）

| classCode | className | 说明 |
|-----------|-----------|------|
| `start` | 开始 | 工作流起点，运行时自动注入上下文参数 |
| `end` | 结束 | 工作流终点，汇聚上游结果 |
| `branch` | 条件分支 | 根据 bool 输入分流到 success/failure 两条路径 |
| `ai_node` | AI 节点 | 调用 LLM 执行提示词，输出结果自动传递下游 |
| `docField` | 文档字段 | 从文档中提取指定字段 |
| `docTable` | 文档表格 | 从文档中提取指定表格 |

> loop 已移除：复杂循环/集合处理由 AI 节点固定提示词规则解决（见《AI提示词规则-功能设计-V1.md》）。

### 2.2 功能节点（后端 Skill 表注册，前端动态加载）

> 功能性 skill 只完成参数固定、功能固定的原子功能；复杂循环、复杂逻辑判断、比对、组装等复杂逻辑统一由 AI 节点提示词承担，功能节点不做复杂编排。

| skillCode | 名称 | 输入 | 输出 |
|-----------|------|------|------|
| `compare` | 值比较 | value_a(LinkOrConstant) + value_b(LinkOrConstant) + operator(Enum) | compare_result(bool) |
| `get_field` | 获取字段 | 按后端定义 | 按后端定义 |
| `get_table` | 获取表格 | 按后端定义 | 按后端定义 |
| `llm_extract` | LLM提取 | 按后端定义 | 按后端定义 |
| `assemble` | 组装结果 | 按后端定义 | 按后端定义 |

> 功能节点的 `inputPorts`/`outputPorts`/`bindMode` 由后端 `[SkillParam]` 特性声明，前端从 `api/skill/query-nodes` 获取。

## 四、每种节点的精确定义

### 4.1 开始节点（start）

| 属性 | 值 | 说明 |
|------|------|------|
| 输入端口 | 无 | — |
| 输出端口 | 1 个 start 信号端口 | 运行时注入上下文参数不变（enterpriseCode/phaseCode/standardCode/fileCode） |
| 可改名 | 否 | 固定名称"开始" |
| 可测试 | 否 | — |
| 单例 | 是 | 画布中仅允许一个 |
| 面板内容 | 类型标签 + 帮助说明 | "工作流起点，运行时自动注入上下文参数" |
| 操作 | 删除 | — |

> **设计决策**：开始节点不从节点库拖拽，而是在画布为空时自动放置；用户不可删除（或删除后自动重建）。节点库面板中移除开始节点拖拽项。start 只绑定一个开始：全图唯一、不可删除、输出信号口作为拓扑起点。

### 4.2 结束节点（end）

| 属性 | 值 | 说明 |
|------|------|------|
| 输入端口 | 1 个 `result`（Link, maxIn=999） | 汇聚上游路径结果 |
| 输出端口 | 无 | end 自身不配置结论，上游节点输出即最终结果 |
| 可改名 | 是 | 多分支场景可命名"合格结束""不合格结束"等 |
| 可测试 | 否 | — |
| 单例 | 否 | 可有多个结束节点 |
| 面板内容 | 名称（只读） + 输入端口（下拉选择来源节点） | 无结论配置 |
| 操作 | 删除 | — |

> **设计决策**：end 汇聚上游唯一节点的输出作为最终结果，end 自身不配置结论；可多 end（每个 end 的上游节点输出即该 end 的最终结果）；执行到任意 end 输出该 end 上游节点结果并结束。面板内容"名称（只读）+ 输入端口（下拉选择来源节点）"（无结论配置）。

### 4.3 条件分支节点（branch）

| 属性 | 值 | 说明 |
|------|------|------|
| 输入端口 | 1 个 `condition`（Link, bool 型） | 必须连接输出 bool 型的上游节点（如 compare） |
| 输出端口 | 2 个锚点：`success`（条件为真）、`failure`（条件为假） | 控制流锚点，非数据端口 |
| 可改名 | 是 | — |
| 可测试 | 否 | 分支节点本身不执行逻辑，只是路由 |
| 单例 | 否 | — |
| 面板内容 | 名称（只读） + 输入端口（下拉选择来源节点） | **无条件编辑器** |
| 操作 | 删除 | — |

> **关键设计决策**：branch 节点不包含任何条件比较逻辑。条件比较由 `compare` 功能节点完成，branch 只消费 compare 输出的 bool 结果进行分流。这实现了"比较逻辑"与"控制流路由"的职责分离。
>
> **V1.1 补充**：branch 与图形化设计器-V2 的 logic 统一为分支路由节点：不内嵌条件逻辑，条件由上游 compare（简单比较）或 AI 节点（复杂判断）产生 bool 输出。

### 4.4 比较节点（compare） — 功能节点

| 属性 | 值 | 说明 |
|------|------|------|
| 输入端口 | 3 个：`value_a`(LinkOrConstant) + `value_b`(LinkOrConstant) + `operator`(Enum) | 仅简单两值比较（>, >=, <, <=, ==, !=），由后端 CompareSkill 定义 |
| 输出端口 | 1 个：`compare_result`(bool) | 下游 branch 节点消费 |
| 可改名 | 是 | — |
| 可测试 | 是 | — |
| 单例 | 否 | — |
| 面板内容 | 名称（只读） + 3 个输入端口 + 输出端口（只读） | operator 是 Enum 模式，从后台获取字典 |
| 操作 | 测试 + 删除 | — |

> compare 节点从 `api/skill/query-nodes` 动态加载，不是特殊节点。前端通过 `bindMode` 统一渲染其 3 个输入端口。compare 仅做简单两值比较；多条件/复杂判断请使用 AI 节点提示词（见《AI提示词规则-功能设计-V1.md》）。

**可用功能 / 可用数据选择器规则**：

| 选择器 | 包含节点 | 排除节点 | 插入格式 |
|--------|---------|---------|----------|
| 可用功能 | skill (compare/assemble等) + docField + docTable + branch | start / end / ai_node | `{{节点别名}}` → 编译为 `{{nodeId.result}}` |
| 可用数据 | 所有节点的输出端口（含 ai_node） | start / end | `{{节点别名.portName}}` → 编译为 `{{nodeId.portName}}` |

> **设计意图**：AI 节点可以引用其他节点的功能结果（如 compare 的布尔判断）和数据结果（如 docField 的字段值），将这些结果组织到 Skill 方法中，实现更灵活的编排。例如：AI 节点引用 compare 的结果 + docField 的字段值 → 生成综合判定文本。

| 来源 | 编辑器内插入格式 | 编译后（落库） | 示例 |

| 节点功能结果 | `{{节点别名}}` | `{{nodeId.result}}` | `{{值比较}}` → `{{compare_n1.result}}` |
| 节点指定端口 | `{{节点别名.portName}}` | `{{nodeId.portName}}` | `{{人员数量.fieldValue}}` → `{{docField_n1.fieldValue}}` |
| 上下文 | `{{ctx.field}}` | `{{ctx.field}}` | `{{ctx.enterpriseCode}}` |

| 可改名 | 是 | — |

**config 结构（V1.2）**：

```json
{
  "docType": "standard",
  "ruleCode": "b9938691...",
  "fieldCode": "HR_STAFF_COUNT",
  "fieldName": "企业人员数量"
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `docType` | enum: `standard` / `enterprise` | 文档类型：standard=标准文档（配置期），enterprise=企业文档（运行期） |
| `ruleCode` | string | 标准文档提取规则编码（关联 cert_doc_extraction_rule.Code） |
| `fieldCode` | string | 字段编码（关联 cert_doc_field_def.FieldCode） |
| `fieldName` | string | 字段显示名（冗余，用于面板展示） |

**双态设计（标准 vs 企业）**：

| 场景 | docType | 数据来源 | 说明 |
|------|---------|---------|------|
| **配置期验证** | `standard` | 标准文档的 `sample_data` 或重新提取 | 选标准文档 + 字段 → 测试 → 展示标准文档中的字段值 |
| **运行期执行** | `enterprise` | 企业上传文档 | 用标准规则的 prompt + 字段定义对企业文档执行提取 |

**配置期验证流程**：
1. 用户在面板选择标准文档（从 `api/DocExtractionRule/configured-rules` 加载）
2. 选择该文档的某个字段（从 `api/DocExtractionRule/{ruleCode}/fields-tables` 加载）
3. 点击「测试」按钮
4. 后端读取该规则的 `sample_data`（已缓存的标准文档提取结果）
5. 返回字段值，前端展示在测试结果面板

**运行期执行流程**（后续实现）：
1. 企业上传文件 → 匹配标准规则（通过 `standard_file_code` 匹配）
2. 用标准规则的 prompt + 字段定义对企业文档执行提取
3. 返回提取结果

**后端 API**：

```
POST /api/DocExtractionRule/test-field
Request:  { ruleCode, fieldCode, docType: "standard" }
Response: { status, data: { fieldValue, confidence, sampleData } }
```

## 五、端口绑定模式（bindMode）三分法

> **统一说明**：底层引用一律存储节点 id（如 get_field_n1），界面下拉/显示一律使用中文别名；连线绑定与文本引用均基于 id，序列化保持 id，仅展示层映射中文。

### 5.1 Link（仅连线）

- **含义**：该端口只能通过画布连线绑定上游节点输出
- **面板渲染**：`el-select` 下拉，options = 画布上所有其他节点
- **交互**：
  - 选中来源节点 → 自动创建 LogicFlow 边
  - 已有连线 → 下拉显示来源节点名称
  - 切换来源 → 删旧边 + 创新边
  - 画布删边 → 下拉清空为"请选择"

### 5.2 LinkOrConstant（可连线可输入）

- **含义**：该端口可通过连线引用上游节点输出，也可直接输入常量/模板
- **面板渲染**：`el-select`（选择节点） + 编辑按钮（切换为文本输入）
- **交互**：
  - 默认下拉模式：选中节点 = 连线引用（同 Link）
  - 点击编辑按钮 → 切换为 `el-input` 文本输入 + 返回按钮
  - 文本模式可输入常量或模板（如 `{{n1.fieldValue}}`、`60`、`2026-01-01`）
  - 已有连线时下拉自动显示来源节点

### 5.3 Enum（仅字典选择）

- **含义**：该端口只能从预定义的字典项中选择
- **面板渲染**：`el-select` 下拉
- **数据来源**：根据 `enumSource` 调用后台 API 获取字典项
  - `compare_operator` → 操作符列表（>, >=, <, <=, ==, !=）
  - 其他 → 通用字典 API

## 七、拓扑线路

### 7.1 定义

连线定义了从 `start` 到 `end` 的完整执行路径。一个流程图可能有多条拓扑线路：

```
start → compare → branch(success) → end1
                         ↓
                    branch(failure) → ai_node → end2
```

上图有 2 条拓扑线路：
1. `start → compare → branch(success) → end1`
2. `start → compare → branch(failure) → ai_node → end2`

### 7.2 用途

- **流程执行**：引擎按拓扑线路顺序执行节点
- **流程测试**：可选择某条线路进行单线路测试
- **校验**：确保每条线路都从 start 到达 end

### 7.3 提取算法

```
1. 从 start 节点出发
2. 沿边遍历到下一个节点
3. 遇到 branch 节点时，分别沿 success/failure 边各走一条
4. 遇到 end 节点时，一条线路完成
5. 回溯处理其他分支
6. 汇总所有从 start 到 end 的线路
```

### 7.4 API 设计

```js
// compiler.js 新增
export function extractTopologicalPaths(graphData) {
  // 返回：[{ nodes: [nodeId...], edges: [edgeId...], label: 'success' }]
}
```

### 7.5 死循环防护规则

1. 结束节点不能反连开始节点；
2. 一个完整流程至少有一个开始和一个结束节点；
3. 后续如引入循环能力，须提供循环次数上限退出机制（人为校验 + 引擎兜底）。

## 八、连线与面板的同步机制

### 8.1 数据流

```
画布连线操作                     属性面板状态
─────────────                   ──────────
edge:add (手动连线)     ──→     selectedNode.inputs[portName] = 上游节点 id（code）
edge:delete (手动删边)  ──→     selectedNode.inputs[portName] = ''
edge:delete (删来源节点) ──→     selectedNode.inputs[portName] = ''

面板下拉选择节点                画布边操作
───────────────                ─────────
emit('link-node', {            创建/删除 LogicFlow 边
  portName,
  sourceNodeId
})                             edge:add / edge:delete
```

> 注：inputs 中存储的是上游节点 id（code），显示时映射为中文别名。

### 8.2 实现要点

1. `index.vue` 监听 `edge:add` / `edge:delete`，同步更新 `selectedNode.inputs`
2. `NodePropertyForm.vue` 新增 `emit('link-node', { portName, sourceNodeId })`
3. `index.vue` 接收 `link-node` 事件后，创建或更新 LogicFlow 边
4. 删除节点时，自动清理所有关联的边和面板端口值
