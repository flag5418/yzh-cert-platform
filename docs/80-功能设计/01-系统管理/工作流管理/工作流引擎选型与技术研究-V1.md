## 一、背景与目标

### 1.1 背景

- 标准目录（配置数据层）已完成设计：`StandardDirectoryConfig / StandardDirectoryFolder / StandardDirectoryFile` 三表及后端 Service、前端页面已落地（域 A 配置体系）。
- 「自定义工作流」是平台核心能力，用于串联**提取数据 → 校验 → 生成报告**三个自动化环节，但**当前只有想法**：
  - 无工作流运行时（引擎 / Skill 执行器 / 节点注册 / 执行日志）；
  - 无可视化配置工具；
  - 域 F 四表仅有实体类，无服务实现。
- 本阶段为**技术研究阶段**：完成框架现状盘点、前端设计器选型、双态 JSON 模型定案、后端解释器接口设计、落地路线规划，产出正式研究结论。

### 1.2 目标

1. 明确 Vol 自带工作流组件的边界，回答"能否直接复用"；
2. 完成前端设计器开源选型（本阶段核心决策），确定改造与隔离策略；
3. 定案「设计器 JSON ↔ 可执行 JSON」双态模型与 `workflow_config` 结构；
4. 设计后端轻量 DAG 解释器的接口与最小实现；
5. 输出四阶段落地路线，供后续实施立项。

### 1.3 技术研究结论速览

| # | 结论 | 状态 |
|---|------|:---:|
| 1 | Vol 自带工作流是**审批流**（人到人），与自定义工作流**数据加工流水线**（数据到数据）是两类问题，**不可直接复用引擎**；可复用其配置驱动 / 留痕 / 可视化编辑三种范式 | [DONE] |
| 2 | 审批流继续服务审核任务分配、NC 整改闭环、报告审核发布，与 DAG 引擎**并行共存** | [DONE] |
| 3 | 前端不自研图形界面排版，选 **LogicFlow**（MVP）改造，封装为独立模块 `workflow-designer`，只暴露导入/导出 JSON 接口；维护断档时可平替 Vue Flow | [DONE]（PoC 验证前生效） |
| 4 | 设计器 JSON（草稿态）与可执行 JSON `workflow_config`（发布态）**分离**，发布态剔除 UI 字段存入 F-03 | [DONE] |
| 5 | 后端自研轻量 DAG 解释器（读 JSON、排顺序、调 Skill、传数据、记日志），不引入重量级开源引擎 | [DONE] |
| 6 | 节点按输入 / 确定性计算 / AI / 输出四类划分；Skill 即节点执行器注册表，靠 input/output schema 在配置期拦截错误编排 | [DONE] |
| 7 | 落地分四阶段：基础闭环 → AI 节点 → 可视化配置工具 → 规模化 | [PLAN] |

## 二、框架现状：Vol 自带审批工作流盘点

### 2.1 组件全景（均已有完整实现）

| 层 | 组件 | 位置 | 职责 |
|----|------|------|------|
| 数据实体 | `Sys_WorkFlow` | `src/server/Vue.NetCore/VOL.Entity/DomainModels/flow/` | 流程头：存 `NodeConfig` / `LineConfig` JSON，绑定业务表（WorkTable / WorkTableKey） |
| 数据实体 | `Sys_WorkFlowStep` | 同上 | 审批节点：StepType / StepValue / Filters / NextStepIds，节点执行者是人（审批人） |
| 数据实体 | `Sys_WorkFlowTable` | 同上 | 流程与业务表关联配置 |
| 数据实体 | `Sys_WorkFlowTableStep` | 同上 | 业务表节点步骤配置 |
| 数据实体 | `Sys_WorkFlowTableAuditLog` | 同上 | 审批留痕日志 |
| 后端引擎 | `WorkFlowManager` | `src/server/Vue.NetCore/VOL.Core/WorkFlow/` | 审批流转：`AddProcese / Audit / Rewrite`，基于业务表 `AuditStatus` 状态机驱动，按角色/部门/用户三路路由审批人 |
| 后端容器 | `WorkFlowContainer` | 同上 | 启动时从 `Sys_WorkFlow` 加载流程配置到内存；`Use<T>()` 注册业务表；把 `Sys_WorkFlowStep.Filters` 反序列化为 `FieldFilter` 并编译为 `Expression`（数据过滤）；按实体匹配流程配置 |
| 前端设计器 | `workflow.vue / panel.vue / node.vue / node_menu.vue` | `src/admin/src/components/workflow/` | 拖拽式流程编辑（jsPlumb 连线），节点菜单仅 start / end / node 三类 |
| 前端页面 | `WorkFlowGridHeader.vue` | `src/admin/src/views/sys/flow/Sys_WorkFlow/` | 流程编辑弹窗，读写 `NodeConfig` + `LineConfig` |

### 2.2 能力边界与限制

Vol 自带工作流为**线性审批流**：

- 模型：`A → B → C` 顺序通过，每一步由人工审批（通过 / 驳回）；
- 路由：按角色 / 部门 / 用户分发审批人，状态由 `AuditStatus` 驱动；
- 数据过滤：节点通过 `Filters` 表达式限定可见业务数据。

**不支持**：

| 能力 | 说明 |
|------|------|
| 并行分支 | 多个节点同时执行（split / join） |
| 条件路由 | 按节点输出条件选择后续分支 |
| 子流程 | 流程嵌套 / 复用 |
| 回调 / 延迟节点 | 异步回调、定时触发、等待事件 |
| 任意 DAG 拓扑 | 仅线性链，无环校验、无拓扑调度 |

### 2.3 结论：审批流与数据加工流水线是两类问题

| 维度 | Vol 审批流 | 自定义工作流（数据流水线） |
|------|-----------|--------------------------|
| 驱动模式 | 状态机（AuditStatus 流转） | DAG（拓扑序执行） |
| 节点执行者 | 人（审批人） | 程序（Skill 执行器） |
| 节点产物 | 审批意见 / 状态迁移 | 数据（字段 / 判定 / 文本） |
| 数据来源 | 业务表 + Filters 过滤 | 提取结果（B-08/B-09）+ 上游节点输出 |

- **不可直接复用引擎**：领域错配，且改造 Vol 源码违反项目宪法「禁止直接修改 Vol 框架源码」。
- **可复用三种范式**：
  1. **配置驱动**：流程 JSON 存库、引擎读配置执行（对齐 F-03 设计）；
  2. **执行留痕**：Vol 靠 `Sys_WorkFlowStep` 记录，YZH 对应 F-04 节点级日志；
  3. **可视化编辑**：拖拽节点 + 连线 + 属性表单的交互形态，可参考其交互范式重做（不直接复用其节点模型）。
- **并行共存**：审批流继续服务审核任务分配、NC 整改闭环、报告审核发布；自定义 DAG 引擎专司数据加工，两者互不干扰。

## 三、设计愿景：三大引擎共用一套工作流体系

| 引擎 | 数据链路 | 节点特性 | 同步/异步 |
|------|---------|---------|-----------|
| 提取引擎 | 文件 → 字段（文件上传 → 预审 → Skill 提取 → B-08/B-09） | Skill 节点 | 异步（队列） |
| 校验引擎 | 规则 → NC（读取 B-08/B-09 → 校验工作流 → B-07 → 自动 NC C-03） | Skill 节点 | 同步 |
| 报告生成引擎 | 数据 → 章节文本（读取审核结果 → 报告工作流 → D-03/D-04） | Skill 节点 | 同步/异步可选 |

三大引擎共用：

- `F-03 WorkflowDefinition`：工作流 DAG JSON（`workflow_config`）；
- `F-04 WorkflowExecutionLog`：节点级执行日志（输入/输出/状态/耗时），是建立审核员信任的关键基础设施；
- `F-01 Skill`：节点能力库（注册表）。

> 核心工作原理原文：「提取、校验、报告三个引擎共用一套工作流体系，通过 DAG 编排 Skill 节点」——本文所有设计均以此为准。

## 五、前端设计器选型（本阶段核心结论）

### 5.1 选型原则

1. **不自研图形界面排版**：前端图形界面选用支持 Vue 的开源工作流组件并改造（引入自定义节点、自定义数据），编排产物为特定 JSON 结构，后端针对该 JSON 开发解释器执行；
2. 必须支持 **Vue 3**（技术栈锁定 Vue 3.4+ + Element Plus）；
3. 自定义节点能力优先（Skill 节点面板、节点属性表单）；
4. 导出 JSON 可控（与 `workflow_config` 结构对齐，或经编译层转换）。

### 5.2 候选方案对比

| 方案 | 许可证 | 维护活跃度 | 开箱即用度 | Vue 支持 | 自定义能力 | 主要风险 |
|------|--------|-----------|-----------|----------|-----------|---------|
| **LogicFlow**（滴滴开源） | Apache-2.0 | 最后活跃提交约 2025-05，社区有维护放缓反馈 | **高**：节点面板/拖拽连线/属性表单流程编排开箱即用度高 | Vue 2/3 | 自定义节点、插件机制、注册自定义方法 | 维护断档风险 |
| **Vue Flow**（@vue-flow/core） | MIT | **活跃维护** | 中：需自建节点面板、连线校验、属性表单 | Vue 3 | **节点即 Vue 组件，最灵活** | 编辑器骨架需自建较多 |
| **AntV X6** | MIT | 持续更新 | 中：偏图形引擎，流程编排能力需自行搭建 | 框架无关（Vue 可用） | 定制能力强但工作量大 | 定制成本高，非流程开箱方案 |

### 5.3 结论与封装隔离策略

> **决策**：MVP 首选 **LogicFlow**；必须做封装隔离；维护断档时可平替 **Vue Flow**。

- **独立模块 `workflow-designer`**：设计器全部逻辑收敛为一个独立前端模块，对外**只暴露「导入 JSON / 导出 JSON」两个接口**，不向业务页面泄漏 LogicFlow 内部 API；
- **平替路径**：因封装隔离，若 LogicFlow 社区维护彻底停滞，可基于同一模块契约替换为 Vue Flow，业务页面与后端零改动；
- **交互范式**：参考 Vol workflow 组件（节点面板拖拽 → 画布连线 → 右侧属性表单），但节点模型改为 Skill 节点（skillCode + inputs + outputs），不复用其 start/end/node 审批模型。

```
src/admin/src/
└── components/
    └── workflow-designer/          ← 独立模块 [PLAN]
        ├── WorkflowDesigner.vue    ← 画布容器（内部使用 LogicFlow）
        ├── SkillPanel.vue          ← Skill 节点面板（读 F-01）
        ├── NodePropertyForm.vue    ← 节点属性表单（inputs/outputs 配置）
        ├── export.js               ← 导出 JSON（编译为 workflow_config）
        ├── import.js               ← 导入 JSON（设计器 JSON 或 workflow_config）
        └── schema-check.js         ← 连线/数据流校验（基于 F-01 schema）
```

### 5.4 PoC 验证要求（实施前置条件）

> 设计器选型正式定案前，必须先完成 PoC 验证两条链路 [TODO:P0]：

## 六、关键设计：设计器 JSON 与可执行 JSON 分离

### 6.1 双态 JSON 模型

| 态 | 存储位置 | 内容 | 说明 |
|----|---------|------|------|
| **草稿态**（设计器 JSON） | 设计器草稿存储（前端本地/草稿表，待定） | 含坐标（x/y）、样式、画布布局等 **UI 字段** | 用于继续编辑，不可执行 |
| **发布态**（workflow_config） | `F-03 WorkflowDefinition.workflow_config` | **剔除 UI 字段**，只保留可执行语义 | 后端解释器唯一消费对象 |

**编译动作**：设计器点击「发布」→ `export.js` 将设计器 JSON 编译为 `workflow_config`（丢弃坐标/样式）→ 校验通过 → 写入 F-03（新版本）→ 记录 `version` 递增。

### 6.2 workflow_config 结构（发布态）

```json
{
  "version": 1,
  "workflowType": "validation",
  "nodes": [
    {
      "nodeId": "n1",
      "skillCode": "get_field",
      "config": {},
      "inputs": { "labelTag": "[ISO9001_一监_管理评审记录_评审日期]" },
      "outputs": { "value": "string" }
    },
    {
      "nodeId": "n2",
      "skillCode": "get_field",
      "config": {},
      "inputs": { "labelTag": "[ISO9001_一监_阶段审核日期]" },
      "outputs": { "value": "string" }
    },
    {
      "nodeId": "n3",
      "skillCode": "date_diff",
      "config": { "unit": "month" },
      "inputs": { "dateA": "{{n1.value}}", "dateB": "{{n2.value}}" },
      "outputs": { "diff": "number" }
    },
    {
      "nodeId": "n4",
      "skillCode": "compare",
      "config": { "operator": ">", "threshold": 12 },
      "inputs": { "value": "{{n3.diff}}" },
      "outputs": { "isViolation": "boolean" }
    }
  ],
  "edges": [
    { "source": "n1", "target": "n3", "sourceHandle": "value", "targetHandle": "dateA" },
    { "source": "n2", "target": "n3", "sourceHandle": "value", "targetHandle": "dateB" },
    { "source": "n3", "target": "n4", "sourceHandle": "diff", "targetHandle": "value" }
  ]
}
```

字段语义：

| 字段 | 说明 |
|------|------|
| `version` | 工作流版本号（与 F-03.version 一致） |
| `workflowType` | `extraction` / `validation` / `report` |
| `nodes[].nodeId` | 节点唯一标识（DAG 内唯一） |
| `nodes[].skillCode` | 引用 F-01 Skill 编码 |
| `nodes[].config` | Skill 静态参数（与 inputs 分离） |
| `nodes[].inputs` | 节点入参：直接值 或 `{{nX.port}}` 模板引用上游输出 |
| `nodes[].outputs` | 节点出参声明：`端口名 → 类型`（多输出端口，替代单值 output） |
| `edges[].source/target` | 边两端节点 ID |
| `edges[].sourceHandle/targetHandle` | **端口语义**：sourceHandle = 上游输出端口名，targetHandle = 下游输入参数名 |

### 6.3 端口语义与数据流解析一致性（关键改造点）

- 边携带端口名后，解释器**按端口名匹配**：`sourceHandle` 决定取上游哪个输出，`targetHandle` 决定写入下游哪个入参，无需猜测；
- 端口名必须与 Skill 的 `output_schema` / `input_schema` 字段名**完全一致**——这是配置期连线校验（§8.3）与运行期数据流解析的契约；
- 设计器导出时**必须保留端口名**（LogicFlow 自定义边/节点需显式配置 handle），PoC 链路二专门验证此点。

> 与 `数据库表设计-V2.md` §F-03 示例的差异（须在实施前同步更新该文档 [TODO:P0]）：`output` 单值 → `outputs` 多端口字典；`edges from/to` → `source/target + sourceHandle/targetHandle`；节点字段 `node_id/skill_code` → `nodeId/skillCode`（JSON 键名统一为 camelCase，与实体序列化约定一致）。

## 七、后端解释器设计（自研轻量 DAG 引擎）

### 7.1 职责边界

> **决策**：不引入 Elsa Workflows / Workflow Core 等重量级开源引擎，自研轻量 DAG 解释器。理由：域 F 的 `workflow_config` 已设计完毕可 1:1 消费；三引擎核心诉求是"确定性地按拓扑序执行 Skill 并留痕"，非长流程暂停恢复；避免 schema 适配层与新持久化模型侵入 YZH 模块。

引擎**职责仅五件事**：

1. 读 JSON（解析 `workflow_config`）；
2. 排顺序（DAG 拓扑排序，含环检测）；
3. 调 Skill（按 skillCode 路由到 `ISkillRegistry` 中的执行器）；
4. 传数据（按边端口语义拼接上游输出 → 下游入参）；
5. 记日志（每个节点输入/输出/状态/耗时写 F-04）。

### 7.2 接口签名

| 接口/类 | 方法 | 参数 | 返回值 | 职责 |
|---------|------|------|--------|------|
| `ISkillNode` | `ExecuteAsync` | `SkillContext context, CancellationToken ct = default` | `Task<SkillResult>` | Skill 执行器统一契约 |
| `SkillContext` | — | — | — | 节点执行上下文：Inputs / WorkflowInstanceId / NodeId / Logger |
| `SkillResult` | — | — | — | 执行结果：Success / Outputs / Error / Confidence / DurationMs |
| `ISkillRegistry` | `Get` | `string skillCode` | `ISkillNode` | 按编码取执行器 |
| `ISkillRegistry` | `RegisterAsync` | `ISkillNode skill` | `Task` | 注册执行器（启动时扫描） |
| `WorkflowEngine` | `RunAsync` | `string workflowConfigJson, WorkflowContext context` | `Task<WorkflowRunResult>` | 解释器入口：拓扑排序 + 调度 + 日志 |

### 7.3 最小可用代码示例

```csharp
// YZH.Core/Workflow/ISkillNode.cs
namespace YZH.Core.Workflow;

public interface ISkillNode
{
    string SkillCode { get; }
    Task<SkillResult> ExecuteAsync(SkillContext context, CancellationToken ct = default);
}

// YZH.Core/Workflow/SkillContext.cs
public class SkillContext
{
    public IDictionary<string, object> Inputs { get; set; }      // 已解析的入参（含 {{nX.port}} 求值结果）
    public string WorkflowInstanceId { get; set; }               // 本次执行实例 ID（对应 F-04 批次）
    public string NodeId { get; set; }                           // 当前节点 ID
    public ILogger Logger { get; set; }                          // 节点级日志写入器
}

// YZH.Core/Workflow/SkillResult.cs
public class SkillResult
{
    public bool Success { get; set; }
    public IDictionary<string, object> Outputs { get; set; }     // 端口名 → 值（与 output_schema 对齐）
    public string Error { get; set; }
    public double? Confidence { get; set; }                      // AI 节点可信度 0.00-1.00
    public long DurationMs { get; set; }
}

// YZH.Core/Workflow/ISkillRegistry.cs
public interface ISkillRegistry
{
    ISkillNode Get(string skillCode);                            // 不存在返回 null，由引擎报未知 Skill
    Task RegisterAsync(ISkillNode skill);                        // 注册；重复注册覆盖
}

// YZH.Core/Workflow/WorkflowEngine.cs
public class WorkflowEngine
{
    private readonly ISkillRegistry _registry;
    public WorkflowEngine(ISkillRegistry registry) => _registry = registry;

    public async Task<WorkflowRunResult> RunAsync(string workflowConfigJson, WorkflowContext context)
    {
        var wf = JsonConvert.DeserializeObject<WorkflowConfig>(workflowConfigJson);
        var order = TopoSort(wf.Nodes, wf.Edges);                // Kahn 拓扑排序，检测环则抛异常
        var outputs = new Dictionary<string, IDictionary<string, object>>();

        foreach (var nodeId in order)
        {
            var node = wf.Nodes.First(n => n.NodeId == nodeId);
            var skill = _registry.Get(node.SkillCode);
            if (skill == null) throw new UnknownSkillException(node.SkillCode);

            var inputs = ResolveInputs(node, outputs);           // {{nX.port}} 模板求值
            var ctx = new SkillContext
            {
                Inputs = inputs,
                WorkflowInstanceId = context.WorkflowInstanceId,
                NodeId = node.NodeId,
                Logger = context.Logger
            };
            var sw = Stopwatch.StartNew();
            var result = await skill.ExecuteAsync(ctx);
            sw.Stop();
            result.DurationMs = sw.ElapsedMilliseconds;

            await context.LogWriter.WriteAsync(node, ctx, result); // 写 F-04（输入/输出/状态/耗时）
            if (!result.Success) throw new SkillExecutionException(node.NodeId, result.Error);

            outputs[node.NodeId] = result.Outputs;
        }
        return new WorkflowRunResult { Success = true, NodeOutputs = outputs };
    }
}
```

> 说明：以上为**最小可用骨架**；`TopoSort / ResolveInputs / WorkflowRunResult` 为示意，实施时补全定义。确定性节点与 AI 节点实现同一 `ISkillNode` 接口，引擎对调用方无差别，通过 `skill_type` 在配置期标注是否需人工复核。

### 7.4 依赖与放置

- **放置位置**：`src/server/Vue.NetCore/YZH.Core/Workflow/`（YZH 独立模块，不进入 VOL.Core / VOL.Builder 生成代码）；
- **依赖**：`YZHBaseEntity` 所在程序集（F-01/F-03/F-04 实体）；Newtonsoft.Json 或 System.Text.Json；
- **约束**：不修改 Vol 源码；实体可继续放 `VOL.Entity/CertPlatform/Wf/`（现有模式）。

## 八、节点四类划分与 Skill 注册表

### 8.1 节点四类

| 类别 | 示例 skill_code | 说明 | 同步/异步 |
|------|----------------|------|-----------|
| **输入** | `get_field` / `get_table` / `get_file_list` / `get_nc_list` | 从 B-08/B-09/C-03 等已存数据读取 | 同步 |
| **确定性计算** | `compare` / `date_diff` / `set_contains` / `count` / `check_not_empty` | 纯逻辑、快、免费，走自研解释器 | 同步 |
| **AI** | `llm_judge` / `llm_generate` | 结构化输出 + confidence + 低可信度人工复核兜底 | 同步/异步 |
| **输出** | `create_nc` / `assemble_text` / `save_result` / `save_section` | 写 B-07、自动 NC C-03、报告段落 D-03 | 同步（副作用） |

> 典型组合（对齐核心工作原理 §4.2）：文件存在性 `get_file_list → check_not_empty`；日期有效性 `get_field×2 → date_diff → compare`；语义判断 `get_field×2 → llm_judge`。

### 8.2 Skill 即节点执行器注册表

```
F-01 Skill（配置数据）                  YZH.Core/Workflow/Skills（执行实现）
├─ skill_code: get_field               ├─ InputSkills/（get_field/get_file_list...）
├─ skill_type: calculate               ├─ ComputeSkills/（compare/date_diff...）
├─ input_schema / output_schema        ├─ AiSkills/（llm_judge/llm_generate...）
├─ endpoint_config（API/函数名）       ├─ OutputSkills/（create_nc/assemble_text...）
└─ is_active                           └─ 启动时 RegisterAsync 扫描注册进 ISkillRegistry
```

- **关系**：自定义节点 = 工作流 DAG 中引用 `skillCode` 的一个节点实例；Skill = 节点执行器注册表条目。**一个 Skill 可被多个工作流节点复用**（跨标准、跨阶段）；
- **注册**：应用启动时扫描 `YZH.Core/Workflow/Skills` 下实现了 `ISkillNode` 的类型，`RegisterAsync` 注入 `ISkillRegistry`；与 F-01 表配置交叉校验（表启用 + 执行器存在才可编排）[TODO:P0]。

### 8.3 连线与数据流校验（配置期拦截，而非运行期报错）

- `F-01.input_schema / output_schema` 是唯一契约来源；
- 设计器连线时实时校验：上游 `output_schema` 中是否存在 `sourceHandle` 端口、类型是否匹配下游 `input_schema` 的 `targetHandle` 入参；
- 配置期校验还包括：DAG 无环、`{{nX.port}}` 引用存在、输出端口类型兼容、末端节点存在 `output_config`（副作用）或输出节点；
- 非法连线在**配置 UI 上直接拦截**（错误提示 + 禁止连线），保证发布态 `workflow_config` 语义合法。

### 9.2 JSON 字段方言适配（关键改造点）

- 项目实际数据库为 **SQL Server / MySQL**（非 PostgreSQL），**不存在原生 `jsonb` 类型**；
- 策略：JSON 字段使用 `nvarchar(max)`（SQL Server）/ `text`（MySQL）+ **应用层序列化**（System.Text.Json / Newtonsoft.Json）；
- 适用字段：`F-03.workflow_config`、`F-04.input_data / output_data`、`StandardDirectoryFile.ExtractionRules` 等全部 JSON 语义字段；
- 约束：不使用数据库侧 JSON 函数/索引；JSON 的读写、校验、投影全部在应用层完成，保证两库迁移零方言差异。
