## 三、代码核查发现（关键问题）

### 3.1 LabelTag 赋值不一致（严重）→ 用户决定改名

**问题**：同一个 `field_code` 在标准文档落库和企业文件落库时，`label_tag` 格式不同。

| 落库场景 | 代码位置 | LabelTag 赋值 | 示例 |
|---------|---------|--------------|------|
| 标准文档提取保存 | `DocExtractionRuleService.cs` L537 | `LabelTag = kv.Key`（= field_code） | `"EnterpriseName"` |
| 企业文件自动提取 | `ExtractionResultService.cs` L66 | `LabelTag = $"{ruleCode}.{field.Key}"` | `"RULE001.EnterpriseName"` |

**用户决策**：方案 C — `label_tag` → `field_name` 改名，彻底整改。存储字段中文名（展示用），查询改用 `field_code`。

**执行状态**：已完成（2026-08-16）

|---|------|------|------|
| 1 | `DB/mysql/phase9_label_tag_to_field_name.sql` | DDL：`ent_extraction_result.label_tag` → `field_name`；`cert_extraction_field` 删除 `label_tag`；数据清洗 | 已执行 |

### 3.2 GetFieldSkill 缺 enterprise_code 过滤（严重）

**问题**：`GetFieldSkill.cs` L20-28 查询时未按 `enterprise_code` 过滤：

```csharp
// 当前代码（有缺陷）
var labelTag = context.Inputs.TryGetValue("label_tag", out var lt) ? lt?.ToString() : string.Empty;
var query = _db.Set<ExtractionResult>().Where(x => x.LabelTag == labelTag);
// 没有 .Where(x => x.EnterpriseCode == enterpriseCode)
```

**影响**：
- 多个企业的同名字段会查到最新的那条（`OrderByDescending(ExtractedAt)`），数据混淆
- 配置期注入 `enterprise_code='YZH-STD-ENT'` 时，Skill 根本不接收也不按此过滤

**修复建议**：`GetFieldSkill` 增加 `enterprise_code` 入参，查询时加 `.Where(x => x.EnterpriseCode == enterpriseCode)`。入参来源：工作流上下文 `context.Inputs["enterprise_code"]` 或 `context.WorkflowContext.EnterpriseCode`。

### 3.3 GetTableSkill 为占位代码（中等）

**问题**：`GetTableSkill.cs` L26 查询逻辑明显是占位代码：

```csharp
// 当前代码（占位）
var query = _db.Set<TableExtractionResult>().Where(x => x.ExtractedJson != null);
// 没有 .Where(x => x.TableCode == tableCode) 过滤
```

**影响**：工作流 `get_table` 节点无法正确查到指定表格数据。

**修复建议**：
- `TableExtractionResult` 实体新增 `table_code` 列（当前无此列，只有 `table_index`）
- 查询按 `table_code + enterprise_code + file_code` 过滤

### 3.4 后端工作流模型落后于前端（阻塞）→ 根因：数据库设计规范未约束 JSON 命名

**问题**：前端 `compiler.js` 已输出 camelCase + 端口语义 JSON，但后端三个 Model 类还在用 snake_case `[JsonPropertyName]`。

**根因分析**：数据库表设计 V2（§八 F-03 WorkflowDefinition）的 `workflow_config` JSON 示例中使用 `node_id`/`skill_code`/`output`/`from`/`to` 等 snake_case 键名，这是设计文档级别的规范偏离——设计文档本身就没有约束 JSON 键名必须 camelCase。

**用户反馈**："我们有数据库设计文档，为什么到现在还有这种问题，说明我们项目的全局规则还是没有约束数据库设计的规范。"

**整改建议**：

1. **数据库设计文档 V2 修订**：域 F 的 `workflow_config` JSON 示例全部改为 camelCase；F-02 `wf_field_label_mapping` 标记废弃（V4 已定调不建）
2. **全局规则补充**：在 `项目全局规则.md` 中增加一条："所有 JSON 字段（数据库 JSON 列、API 请求/响应体、前后端传输契约）统一使用 camelCase 命名，与前端 JS/TS 惯例一致。C# 实体的 `[JsonPropertyName]` 特性必须写 camelCase。"
3. **后端模型对齐**：升级 `WorkflowNode/Edge/Config` 三个 Model 类 + WorkflowEngine

### 3.5 企业文件 AI 提取未完善（已知 TODO）

**问题**：`EnterpriseFileService.cs` L250 `CallAIForExtractionAsync` 返回空结果。

**影响**：企业文件上传后自动提取流程虽然走通，但实际不产生提取数据。

**建议**：不阻塞当前阶段，标记为已知 TODO，后续补齐。

5. **第六阶段 Skill 修复 + 详细设计**：用户要求单独开文档详细设计 Skill 开发规范。修复 GetFieldSkill/GetTableSkill 的查询逻辑。

6. **每阶段交付标准**：前后端同步实现 → 独立菜单可用 → 测试数据录入 → 验证通过 → 进入下一阶段。

## 八、对用户问题的逐条回答

### 8.1 "workflow_config 这个字段是用来存储工作流配置生成的json结构吗"

**是的**。`workflow_config` 列存储的是图形化设计器（LogicFlow 画布）通过 `compiler.js` 编译后输出的 workflow_config JSON 结构，包含 `version`/`workflowType`/`nodes`/`edges`/`branches`/`outputConfig` 等字段。它是工作流引擎的输入——解释器读取这个 JSON，按 DAG 语义调度 Skill 执行。

在 V4 设计中：
- `cert_validation_rule.rule_json` — NC 规则的工作流配置（一对一）
- `rpt_report_section.workflow_config` — 报告章节的工作流配置（一对一）
- `cert_report_template.section_config` — 报告模板的章节定义（每章节内嵌 `workflowConfig`）

### 8.2 "我们有数据库设计文档，为什么到现在还有这种问题"

根因是**数据库设计文档的 `workflow_config` JSON 示例本身就用了 snake_case**（`node_id`/`skill_code`/`output`/`from`/`to`），没有约束 JSON 键名必须 camelCase。后续开发时前端按 JS 惯例用了 camelCase，后端按数据库文档示例用了 snake_case，导致不一致。

整改建议：
1. 数据库设计 V2 修订域 F 的 JSON 示例
2. `项目全局规则.md` 补充："所有 JSON 字段统一 camelCase"

### 8.3 "labeltag 修改为 fieldname 这种好理解的更好"

见 §3.1 的三个方案。推荐方案 B（废弃 `label_tag`，查询改用 `field_code`），但待用户确认。

### 8.4 "Skill 需要单独开一个自定义节点及自研 skill 开发的文档来进行详细设计"

已规划，见 §七 文档体系中的 `05-Skill体系/` 目录。第一阶段先创建 `Skill开发规范-V1.md`。

### 8.5 "该引擎开发必须有个完整的计划，先从基础开始搭建"

见 §五 调整后的开发计划。八个阶段从数据库整改 → 基础骨架（NC+报告）→ 模型对齐 → 图形化 → Skill → JSON+校验 → 解释器，循序渐进，每阶段前后端同步实现、独立菜单、可独立验证。
