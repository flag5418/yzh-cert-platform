# 文件转换队列化设计方案 V1

> **版本**：V1.0 | **日期**：2026-08-11 | **状态**：待评估
>
> **背景**：当前文件上传后采用 `ConvertHostedService` 串行异步转换，用户无进度反馈，多用户并发上传无隔离控制。

---

## 一、问题分析

### 1.1 当前架构的痛点

| 问题 | 影响 | 严重度 |
|------|------|--------|
| 串行转换，3-5秒/文件 | 87个文件需7分钟+ | 高 |
| 无进度反馈 | 用户不知道何时能预览 | 高 |
| 无并发控制 | 多用户同时上传，资源争抢 | 高 |
| 无任务取消 | 转换失败只能等待重试 | 中 |
| 无死信队列 | 失败任务丢失上下文 | 中 |
| UploadConfirm 异步触发转换 | 调用方不知道转换结果 | 高 |

### 1.2 未来需求

- 几十个审核员同时上传文件
- 大文件（50MB+）分片上传
- 转换失败需要重试和人工干预
- 管理员需要查看全局转换队列状态

---

## 二、目标架构

```
用户上传 → UploadPreInit → UploadFileWithTask → UploadConfirm
                                                        │
                                          ┌─────────────┴─────────────┐
                                          │  转换队列管理器 (新增)      │
                                          │  ┌──────────────────────┐  │
                                          │  │ 任务入队 + 优先级     │  │
                                          │  │ 并发控制 (SemaphoreSlim)│  │
                                          │  │ 进度追踪 + SignalR    │  │
                                          │  │ 失败重试 + 死信队列    │  │
                                          │  └──────────────────────┘  │
                                          └─────────────┬─────────────┘
                                                        │
                          ┌─────────────────────────────┼─────────────────────┐
                          │                             │                     │
                    并行 Worker 1                并行 Worker 2          并行 Worker N
                    LibreOffice                  LibreOffice            LibreOffice
                    (Docker 容器)                (Docker 容器)          (Docker 容器)
```

### 3.2 后端：转换队列管理器

#### 3.2.1 新增 `ConvertQueueManager` 服务

```
职责：
1. 任务入队：接收 UploadConfirm 的转换请求，批量入队
2. 并发控制：SemaphoreSlim 限制同时运行的 LibreOffice 进程数
3. 任务分发：从队列取出任务，分配给 Worker
4. 进度推送：通过 SignalR 实时推送进度到前端
5. 失败处理：自动重试（最多3次），超过后移入死信
6. 超时检测：定期扫描 locked_at 超过 5 分钟的任务，释放锁
```

#### 3.2.2 改造 `UploadConfirm` 方法

```csharp
// 伪代码
public async Task<WebResponseContent> UploadConfirm(string taskId)
{
    // 1. 激活文件（现有逻辑）
    
    // 2. 筛选需要转换的文件
    var filesToConvert = filesToActivate
        .Where(f => IsOldOfficeFormat(f.FileName))
        .ToList();
    
    // 3. 批量入队（不等待完成）
    foreach (var file in filesToConvert)
    {
        await _queueManager.EnqueueAsync(new ConvertTask
        {
            FileCode = file.FileCode,
            SourcePath = file.StoragePath,
            ConvertType = GetConvertType(file.FileName),
            TaskId = taskId,
            UserId = UserContext.Current.UserId,
            OrgCode = orgCode,
            Priority = 0
        });
    }
    
    // 4. 立即返回（不阻塞）
    return new WebResponseContent().OK(
        $"上传完成，{filesToConvert.Count} 个文件正在转换",
        new { 
            convertCount = filesToConvert.Count,
            taskId = taskId,
            // 前端可以用这个 taskId 查询进度
            trackUrl = $"/api/standard-directory/convert/progress?taskId={taskId}"
        }
    );
}
```

#### 3.2.3 新增进度查询 API

```
GET /api/standard-directory/convert/progress?taskId=xxx
  → 返回该批次的转换进度

GET /api/standard-directory/convert/queue-status
  → 返回全局队列状态（管理员用）

POST /api/standard-directory/convert/cancel?taskId=xxx
  → 取消指定批次的未处理任务
```

#### 3.3.2 推送时机

| 事件 | 推送内容 |
|------|---------|
| 任务入队 | `{ taskId, status: "queued", total: N }` |
| 开始转换 | `{ taskId, fileCode, status: "converting", progress: 0 }` |
| 转换完成 | `{ taskId, fileCode, status: "completed", progress: 100 }` |
| 转换失败 | `{ taskId, fileCode, status: "failed", error: "..." }` |
| 批次完成 | `{ taskId, status: "batch_completed", success: N, failed: M }` |

### 3.4 前端改造

#### 3.4.1 上传确认流程

```
用户点击"确认上传"
  │
  ├─ POST /upload-confirm → 返回 taskId + convertCount
  │
  ├─ 如果 convertCount > 0：
  │   ├─ 显示进度面板："正在转换 3/85 个文件..."
  │   ├─ 连接 SignalR Hub，订阅 taskId
  │   ├─ 实时更新进度条
  │   └─ 收到 batch_completed → 显示通知 "转换完成" + 关闭面板
  │
  └─ 如果 convertCount == 0：
      └─ 直接关闭上传弹窗
```

#### 3.4.2 进度面板组件

```
┌─────────────────────────────────────────┐
│ 📄 文档转换进度                          │
│                                         │
│ ████████████░░░░░░░░░░░░  45% (38/85)  │
│                                         │
│ ✅ 已完成：38                            │
│ ⏳ 等待中：46                            │
│ ❌ 失败：1                               │
│                                         │
│ 当前：XASL-QP-001 文件控制程序.doc       │
│                                         │
│ [取消队列]  [最小化]                     │
└─────────────────────────────────────────┘
```

#### 3.4.3 离开页面后回来

- 前端存储 taskId 到 Pinia/localStorage
- 回到页面时检查是否有未完成的 taskId
- 调用 `GET /convert/progress?taskId=xxx` 恢复进度
- 重新连接 SignalR 继续接收通知

### 3.5 并发控制与隔离

#### 3.5.1 用户级隔离

- 每个用户同时只能有一个活跃的上传任务
- `UploadPreInit` 时检查：如果用户有未完成的上传任务 → 拒绝或提示

#### 3.5.2 机构级隔离

- 队列任务带 `org_code`
- Worker 按机构分组处理（避免一个机构的任务占满所有 Worker）

#### 3.5.3 全局并发控制

```csharp
// 在 ConvertQueueManager 中
private static SemaphoreSlim _workerSemaphore;
private static int _maxConcurrent = 3; // 从数据库配置读取

// Worker 获取任务前
await _workerSemaphore.WaitAsync();
try {
    var job = await GetNextPendingJobAsync();
    await ExecuteConvertAsync(job);
}
finally {
    _workerSemaphore.Release();
}
```

### 3.6 失败处理与死信队列

```
任务失败流程：
  1. 首次失败 → status="pending", retry_count++
  2. 重试3次仍失败 → status="dead_letter"
  3. 管理员可在死信队列页面查看失败原因
  4. 管理员可手动重试或跳过
```

## 五、技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 实时通知 | SignalR | 项目已启用 SignalR（main.js 中 signalR:true） |
| 并发控制 | SemaphoreSlim | 轻量级，进程内即可 |
| 任务存储 | MySQL 现有表 | 不引入新中间件 |
| 进度查询 | REST API + SignalR | 离开页面后可恢复 |
| 配置管理 | 数据库 cert_convert_queue_state | 可动态调整 |

### 未引入 Redis 队列的理由
- 当前单机部署，进程内 SemaphoreSlim 足够
- 后续如需多机部署，可平滑迁移到 Redis Stream/RabbitMQ
- 避免引入新中间件增加复杂度

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| LibreOffice 进程崩溃 | Worker 捕获异常，标记任务失败，自动重试 |
| 大量并发导致内存溢出 | SemaphoreSlim 限制并发数（默认3） |
| 用户关闭浏览器后任务继续 | 后端独立运行，不依赖前端连接 |
| 数据库连接耗尽 | 每个 Worker 用独立 DbContext scope |
| SignalR 连接断开 | 前端自动重连 + 轮询兜底 |

3. **取消策略**：取消队列时，正在处理中的文件是等完成还是强制终止？

5. **前端交互**：进度面板是模态弹窗还是可最小化的侧边栏？
