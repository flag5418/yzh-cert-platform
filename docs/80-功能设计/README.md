# 80-功能设计

> **作用**：每个已确认功能的设计文档集中处。**文档先行**——先写清楚业务逻辑、涉及表、接口、实施计划，再实施；实施后保持文档与代码一致，供后续迭代维护直接参考（不靠代码反推逻辑）。
>
> **维护原则**：
> 1. 一个功能一个文档，命名 `{功能名}-功能设计-V{N}.md`（如 `提取结果落库-功能设计-V1.md`）；
> 2. 进入实施前必须完成本目录设计文档（评审通过），**文档未完成不得实施**；
> 3. 实施后若逻辑变化，**必须同步更新本文档**（状态头注明修订日期）；
> 4. 功能完成后文档留在本目录（它是该功能的权威说明），不归档；
> 5. `70-当前执行` 中**已完成的功能**，结论归纳进本目录对应功能设计文档（正文+清单更新），避免执行文档与功能文档重复。

---

## ⚠️ 严格规范（必须遵守，不允许按各自理解编写）

1. **章节固定**：每个功能设计文档必须按下方模板的章节顺序与标题编写，**不得增删章节**（新增内容放"八、边界与异常处理"后追加编号章节，并在文末"章节变更记录"登记）。
2. **TODO 执行计划必填**：模板"十、TODO 执行计划"是**硬性章节**，任何功能文档都必须包含；每项任务必须标注状态 `[ ] 未开始 / [~] 进行中 / [x] 已完成` + 完成日期，让读者一眼看清"该功能是否已实施、还欠缺什么"。
3. **状态机**：文头 `状态` 取值唯一：`设计稿 → 评审中 → 实施中 → 已实施 → 已废弃`，与 TODO 计划联动（TODO 全部 `[x]` 才可标 `已实施`）。
4. **表设计必含约束**："五、数据设计"每张表必须列出：用途、关键字段、索引、**唯一约束**（DB 层硬保障，不依赖逻辑控制）。
5. **接口必含错误处理**："六、接口设计"每个接口必须写：方法、路径、请求/响应结构、失败场景与错误返回。
6. **命名规范**：表名 `cert_`/`ent_`/`wf_` 前缀、字段 snake_case、接口 `/api/模块/动作`、常量全大写。
7. **关联文档必写**：文头"关联文档"必须列出前置/相关文档（含 70-当前执行 中来源文档），不允许无来源设计。
8. **版本管理**：修改非新增 → 同版本内修订并在头部注明；设计变更 → 升版本号（V1→V2），旧版本内容保留在历史文档。

## 文档模板（必须按此结构编写）

```markdown
# {功能名} - 功能设计

> 版本：V1.0 | 状态：设计稿/评审中/实施中/已实施/已废弃 | 创建日期：YYYY-MM-DD | 最近修订：YYYY-MM-DD
> 关联文档：{前置设计/来源文档，如 YZH特殊企业-工作流验证数据设计-V1.md §4}

## 一、功能概述
（一句话：功能做什么、为谁服务、处于什么链路）

## 二、业务背景与目标
（为什么需要、解决什么问题、后续依赖什么——业务逻辑的来龙去脉写清楚）

## 三、前置条件
（依赖的已存在数据/表/企业记录，如 YZH-STD-ENT；实施顺序上必须先完成什么）

## 四、业务规则
（核心业务逻辑，逐条编号：状态机、规则、优先级、幂等性、删除/插入策略）

## 五、数据设计
### 5.1 涉及表
（每张表：用途、关键字段含义、索引）
### 5.2 表约束（DB 层兜底）
（唯一键/外键/检查约束——逻辑控制是软保障，表约束是硬保障，必须给出 DDL）

## 六、接口设计
（每个接口：方法、路径、请求/响应结构、错误处理；DTO 变更）

## 七、数据流 / 时序
（ASCII 时序图或 mermaid）

## 八、边界与异常处理
（失败场景、并发、重复提交、数据缺失、唯一键冲突等）

## 九、测试要点
（端到端验证清单：前置数据 → 操作 → 断言）

## 十、TODO 执行计划
（硬性章节。每项：[ ] 未开始 / [~] 进行中 / [x] 已完成(日期)）

| # | 任务 | 状态 | 说明 |
|---|------|------|------|
| 1 | SQL：xxx | [ ] | ... |
| 2 | 常量/实体 | [ ] | ... |
| ... | ... | ... | ... |

> 状态 = TODO 全部完成才可标"已实施"。

## 十一、章节变更记录
| 日期 | 版本 | 变更内容 |
|------|------|----------|
```
