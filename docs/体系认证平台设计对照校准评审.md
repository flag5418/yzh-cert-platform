## 第 0 章 校准方法与依据清单

### 0.1 方法

1. **先取设计现状**：三目录下各分册的 README 与「评估/实测/裁决」类分册（15/17/18/21/24/25/26）是三目录内部已经完成的自评与裁决载体，优先采信其结论；再以核心设计分册（02/03/04/22/23/34、专家任务设计 02/03/04、企业资料管理 09）核对细节。
2. **再逐条对照**：以补充评审 v1.1 的**建议条目**为骨架（约 40 条可判定项），逐条给出四类判定。
3. **判定口径**（不设「部分通过」的模糊态，凡跨类一律拆条）：

| 判定 | 含义 |
|---|---|
| ✅ 已被设计覆盖 | 三目录现有设计已明确给出对应机制（含「已裁决」） |
| ⭐ 设计优于建议 | 现有设计比原建议更具体、更完备或换用了更好的实现路径 |
| ⚠️ 需修正 / 撤回 | 原建议与现有设计或用户裁决冲突，需改写甚至撤回 |
| ❌ 仍是缺口 | 三目录未给出对应设计（含「能力演示 ≠ 功能完备」的明确自认缺口） |

### 0.2 基准的读法（重要）

三目录本身**不是一份成品设计**，而是「已定稿待编码 + 已落地首批能力 + 待裁决清单」并存的混合体。对照时必须区分三种状态，否则会误判：

| 状态 | 表现 | 对照时的处理 |
|---|---|---|
| **已裁决** | 文档标注「D…已裁决」「用户裁决原文」 | 视为**不可违背的现状**，建议与它冲突就要改建议 |
| **已定稿待编码** | 标注「设计已定稿，待编码」 | 视为**设计已覆盖**，但需注明「尚未实现」 |
| **已自评推翻/待重写** | 标注「⚠️ 本文为 V1（已被 12 号部分推翻），待 V2 重写」 | 视为**设计在建**，不能作为覆盖依据 |

> 典型：`专家任务设计/03-详细设计-NC检查-V1.md`、`04-详细设计-报告生成-V1.md` 均被 `12 号` 部分推翻（V1 状态机含 `approved` 已删、结论统一表已拆 4 张），**事实依据以 `17-实测基线-V1.md` 为准，业务裁决以 `12 号` 为准**。这两点必须写进任何后续文档，否则会引到已废弃口径。

### 2.1 企业资料规范化（`docs/20-体系认证/03-详细设计/05-企业资料规范化`）

#### 2.1.1 模块命题与边界（原文依据：README §一、§三）

- **核心命题原文**：「标准目录（`cert_standard_directory_file`）定义了『应该有什么文档、每个单元格该填什么』；企业资料库产生『实际有什么文档、实际填了什么』。本模块是连接两者的**匹配与填充引擎**，其枢纽字段 = `StandardFileCode`。」
- **模块边界（用户澄清口径）**：本册 = **企业资料规范化**（散乱资料 → 匹配/裁决/填充成标准格式文档，**下一步**）；**企业资料管理**（企业已备好的标准格式材料 → 采集/提取 → 喂 NC 规则与报告规则 → 自动出 NC 检查报告和认证报告，**本期**）已独立成册。
- **范围裁定**：本册**不进 10/15 关键路径**（关键路径 = `登录→建档→分配标准/阶段→上传→提取→NC→报告`）；模板线**可冻结、可停**。

#### 2.1.2 数据模型（原文依据：README §4.1 决策登记、§3.3 既有裁决）

| 类别 | 要点 |
|---|---|
| 统一表架构 | **YZH-STD-ENT**：标准侧与企业侧共用 `cert_standard_directory_file`，以 `EnterpriseCode` 列区分（D11）；模板行 = `YzhVirtualEnterprise.Code`（`'YZH-STD-ENT'`），**⛔ 禁 NULL** |
| 表前缀 | 一律 `cert_`，不复活已删除的 `ent_*`（D1）；**企业表统一 `cert_enterprise`**，所有 `EnterpriseCode` 外键指向它 |
| 主键口径 | 复合编码 `FileCode/FolderCode/DirectoryCode` 已删除，**本行 `Code`(GUID) 即业务键**；`Id` 不进 WHERE/关联（「双关键字准则 A」） |
| 阶段口径 | `PhaseCode → StageCode`，阶段权威 = `cert_cert_stage`；`cert_phase_definition` 是孤儿模型，不引用 |
| 启用字段 | `Enable` 零容忍，**唯一启用字段 = `IsValid`** |
| 字符集 | `utf8mb4` + 显式 `COLLATE=utf8mb4_general_ci` |
| 字段对齐 | `LabelTag = FieldCode`（**不采用** `[ISO9001_..._企业名称]` 长标签方案） |
| 可信度 | 统一 `decimal(3,2)`，值域 0.00–1.00，可空（空 = AI 未给 / 人工录入，D8） |
| 新建表 | 契约/模板侧：`cert_doc_template` / `cert_doc_template_anchor` / `cert_tag_dict`（21 号）；全局参数：`cert_fill_param_def` / `cert_fill_param_value`（22 号 §七，**已实现**）；核心菜单侧共 **8 张新表**（26 号） |

> ⚠️ **实测提醒（原文依据：`00-实现现状对照表-V1`）**：本册 `02`/`13`/`16` 描述的表结构与接口，**除 06 册线外均为未实施设计（0 命中）**。对照「已落地」时必须先查 `00-实现现状对照表-V1.md`。

#### 2.1.3 流程链路（原文依据：README §二·五、`34-核心模块定位与端到端流程-V1`）

- **双侧职责**：后台定义侧（管理员/实施：分类、作用、生成规则）+ 企业执行侧（上传、填值、规范化）。
- **标准文档三分类**：`fixed` / `hybrid` / `editable`。
- **文档级六级优先级**：仅**层 2（文档级规则）+ 层 5（企业覆盖）需要语义判断**，其余为机械执行。
- **填充引擎（已实现）**：锚点语法统一 `{{...}}`，**由 token 内容决定归属**；Resolver 按 `Order` 升序链式执行 `AiGenerate(10) → HeaderFooter(20) → Replace(30) → GlobalParam(100 兜底)`；`GlobalParamResolver` 用 `IsClaimedByOthers` **主动拒收**前三类 token。
- **★ 引擎必须纯函数**（原文）：「`DocumentFillEngine` 不读 DB / 不读时钟 / 不引 `YZH.Core.DataBase` ⇒ 同一输入必得同一输出，167 份文档批量填充**可重跑**。」
- **★ 取值决策唯一实现** = `ParamValueResolver`（`auto` 恒实时取档案且不落值表 / `both` 无企业值时自动带出档案作初值可改 / `manual` 回落 `DefaultValue`）——「⛔ 两个控制器**不得各写一份**」。
- **已实现 4 项能力**：全局参数 / 替换 / 页眉页脚 / AI 生成（**本期不直连模型**，只产出可投喂模型的提示词）。实测：35 锚点 / 4 能力全命中 / 有证据摘要。
- **填充预览**：`DocumentFillController.preview`。

#### 2.1.4 规则模型（原文依据：`22`/`23` 号、README §4.4）

- **填写单元属性 = 3 个正交维度**（**不是 4 种分类**）：

| 维度 | 取值 |
|---|---|
| D1 取值来源 | `global` / `self` / `sibling` / `profile` / `compute` / `ai` / `manual`（**有序列表** + `combine`=`firstHit`/`concat`/`template`，默认 `firstHit`） |
| D2 写入方式 | `replace` / `overwrite` / `append` / `remove`（默认 `overwrite`） |
| D3 承载形态 | `scalar` / `block` / `table` / `table_total` / `domain` |

- `onMissing` 默认 `next`（有序回退链）；**⛔ 不加 `dict` 类**（枚举值域 ≠ 来源维度）。
- **全局填写规则 = 服务端装配器**（★ 照抄 `NcPromptAssembler`，**⛔ 不做工作流**）；全局参数按「标准 × 阶段」裁剪（枚举式 `StandardScope` / `StageScope`）。
- **⛔ 填充取值不做成 Skill**（22 号 §十三「实现载体裁定」）。
- **重传合并三条硬约束**：①覆盖 = 文件 + 扫描结果，保留 = 分类/作用/提示词，锚点 **diff**（新增→插入，消失→`IsOrphan=1` **不删**）；`SourceSha256` 相同 → 跳过整个重扫；②「自动带出」必须有落库标记 `TagsSource`/`DocPurposeSource`/`FillPromptSource`（`ai`/`manual`/`carried`），`manual` 的值**连重新分析都不覆盖**；③**上传侧拒绝非 `docx`/`xlsx`**（⛔ 不自动转换，会自动转会破坏锚点）。

### 2.2 专家任务设计（`docs/40-实施/专家任务设计`）

#### 2.2.1 数据模型（原文依据：`02-详细设计-任务与队列-V1` §1.3、`12 号` 拆分口径）

- **任务项表已从 1 张拆为 4 张**（12 号）：`cert_expert_nc_item`（实体）/ `cert_expert_nc_result`（结果轮次）、`cert_expert_report_section_item` / `cert_expert_report_result`；「任务包含哪些项」**⛔ 不再有独立表**，通过结果表 `TaskCode` 反查；日志 = `cert_expert_task_log`（`TaskItemCode` → 结果行 `Code`）。
- **三层状态列**：`ExecStatus` + `ReviewStatus` + `LifecycleStatus`；**⛔ 没有 `TaskStatus` 单列，⛔ 没有 `approved`**。
- **锁用生成列**：`ActiveLockKey` 由 `LifecycleStatus + ExecStatus` 自动维护，**⛔ 不显式赋值**，撞 `uk_active_lock`（MySQL 1062）→ 转 `BIZ_LOCKED`。
- **实体层跨任务长期存在**：`cert_expert_nc_item` 「跨任务存在（11 号实测同一检查项跑过 15 轮）」⇒ **⛔ 不能重建**（重建会丢 `CurrentResultCode` / `LastAuditedTime` ⇒ `D30「沿用」当场失效`）。
- `TaskSource ∈ NEW | REDO | PATCH`（D25）；`ScopeType ∈ FULL | PARTIAL`（D02：1 任务 → N 标准子任务，1 子任务 = 1 队列）。

#### 2.2.2 流程链路（原文依据：`02` 号 §1.1、§1.2、§六）

- **前置校验链顺序不可调换**：①租户解析（`WorkspaceContextService.Resolve()`，**禁止从 body 取**）→ ②业务锁检查（**分类型串行锁**，`TaskType` 进锁键；用户 2026-09-30 裁决，**推翻 D15 / D28**）→ ③企业-阶段-标准三元组校验（`STANDARD_NOT_ASSIGNED`）→ ④局部任务单标准校验（D03，`CROSS_STANDARD_NOT_ALLOWED`）→ ⑤阶段有效性（`STAGE_INVALID`）→ ⑥事务写入。
- `OrgCode` **同名不同义**：规则/章节侧 = **认证机构 CbCode**；任务表侧 = **专家工作区**（02 号 §9 口径对照表）。
- 已知阻塞：`cert_validation_rule.PhaseCode` 现库还存业务码 `'03'` ⇒ 直查必 0 行 ⇒ **依赖 22 号 §1.1「阶段编码口径统一」（唯一真阻塞，0.5 人天）**。

#### 2.2.3 规则模型（原文依据：`18-NC结论判定体系-V1`、`21-架构判断-V1`、`17-实测基线-V1`）

- **单节点多维度替代多路径**；四节点体系：`nc判断(ai_node)` + **规则引擎（权威）** + `nc结论(ai_node)` + `nc_validate`（校验）。
- **结论四态语义**：`conform` / `nonconform` / `na` / **`unverifiable`**；配置表 `cert_conclusion_rule` 落标。
- **结论三模式**：`RULE_ONLY` / `AI_ASSISTED` / `EXPERT_MANUAL`。
- 6 个 Skill 已注册、**106 单测全过**；`B3(B1)` 已修、`B4` 溯源字段 V1.4 已修。
- **★ DAG 权威在 `cert_validation_rule.RuleJson`**（21 号修正了「`wf_workflow_definition`=0 行」的原严重阻碍判断）。

#### 2.2.4 接口与关键约定（原文依据：`03` 号 §2.2、§2.3；`04` 号）

- **结果归一化（AI 不确定性在此收口）**：AI 输出必须符合**约定的 JSON 契约**（写进 Prompt 模板）；解析失败 **≠ 判定为符合** ⇒ `AiNcResult.NeedsManual`：`AutoStatus=failed`、`Conformity=null`（**不预填**）、`ReviewStatus=pending`（阻塞认可校验 → 强制专家介入）、界面黄色提示 + 展示 `rawOutput`。原文理由：「这是认证审核系统，『AI 解析失败 → 静默通过』是**最危险的失败模式**。宁可阻塞也不能伪造结论。」

## 第 4 章 需要修正或撤回的判断

以下 7 条为**因现有设计/裁决而必须改写**的建议。逐条给出「原判断 → 为什么错 → 校准后判断」。

### 4.1 撤回「报告家族先做 NCR 与检查表」的形态假设（C2.4-1）

- **原判断**：报告要分家族（NCR / 审核报告 / 内部记录），建议先做 NCR 与检查表，再做审核报告全文。
- **为什么错**：用户已明确裁决「**我现在不想做报表系统了，报告的主表我也不需要了**」「只导 Excel 才是 excel」。报告的产物是**章节列表 + 逐章节认可/修改**，不是报告文件；`D34` 进一步删掉了报告主表。
- **校准后**：报告产物 = 按标准分节的章节列表（`ItemType='report_section'`），导出时一个标准一个 Sheet；NCR 在本系统中等价于「NC 检查项 + 导出」，**不另建单条文书文件模型**。

### 4.2 修正「审核结论保守三档」（C2.4-4）

- **原判断**：审核结论保持推荐 / 有条件推荐 / 不推荐三档，AI 只做素材组织。
- **为什么错**：「推荐 / 不推荐」属**认证决定**，而补充评审 §0.3 已引用用户口径「不做完整体系认证流程（…认证决定…）」；且实现侧落地的是 **NC 结论三模式**（`RULE_ONLY`/`AI_ASSISTED`/`EXPERT_MANUAL`）与结论定级。
- **校准后**：保留「AI 素材组织 + 专家定结论 + 留痕」的原则；把三档取值改为「NC 结论的定级」，认证决定类结论**不在本期范围**。

### 4.3 修正「标准包版本号 / 建版本表」（C3.2-2、C5.2-7、C4-3、C6-4）

- **原判断**：标准包要素含「版本号」，版本化后「某次审核用了哪个版本」可追溯。
- **为什么错**：`21 Q-3` 明确「覆盖前 `PathBuilder.Archive()`（**不建版本表**）」，且设计以满足用户「不引入版本号」为前提；追溯改用**快照**（规则快照、`SectionTemplateContent`、`ExtractVersionStamp`）。
- **校准后**：追溯路线改为「**三层快照 + 文件归档**」，不新增版本表。**保留一个真问题**：跨文档/跨批次比对时是否需要「规则集级版本标识」（快照只保证单条可追溯，不保证可比较），此项建议列为待裁决。

### 4.4 修正「严禁硬编码进 Skill」的措辞（C2.2-4）

- **原判断**：模板配置属标准包，严禁硬编码进 Skill。
- **为什么错**：本设计的 Skill 语义与建议不同——`22` 号 §十三明确「**⛔ 填充取值不做成 Skill**」，`23` 号 §〇.五专门回答「填写 Skill 是否合理」，`16` 号 V2 另有「12 个 Skill」，`26` 号 §3.4.6 给出「写入侧 Skill 含 NPOI 实现规格」。即：**配置在表、Skill 作载体**，二者不冲突。
- **校准后**：表述改为「配置**入表**（`cert_doc_template` / `cert_doc_template_anchor` / `cert_tag_dict`）；Skill 仅作执行载体，取值决策逻辑**不进 Skill**」。

### 4.5 修正「文件化信息四级分类」的维度定位（C2.1-1）

- **原判断**：分类体系按四级（手册/程序/作业指导/记录）落地，支持四层可配置。
- **为什么错**：现有设计的分类是另一维度（标准文档 `fixed`/`hybrid`/`editable`），且该维度的落地列（`DocCategory`）**尚未加、构成 B1 阻断**。把两者混为一谈会导致需求错位。
- **校准后**：明确两者是**独立并存的两个维度**（内容层级 vs 模板可编辑性）；四级层级模型应作为**尚未建模项**单列，且其优先级需在 `B1` 阻断解除后确定。

### 4.6 修正「E-1 无兜底收口」的定级表述（C0.2-1、C5.1-2）

- **原判断**：引擎无兜底收口，任务会停留 `executing`。
- **为什么错**：兜底**在设计与台账层面已被识别**，问题落在实现：`26` 号列出 4 个 P0（含「失败吞成 `completed`」「租约仅启动回收致队列停摆」），并给出 5.5 人天修复顺序。
