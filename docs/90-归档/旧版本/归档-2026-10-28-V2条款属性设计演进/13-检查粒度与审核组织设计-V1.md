## 一、检查粒度：数据说了什么

### 1.1 先看我们自己的条款树

`cert_iso_clause` 现有 **273 条 / 4 标准**：

| 标准 | 一级 | 二级 | 三级 | 叶子（真正可检查单元） | 最深层级 |
|---|:--:|:--:|:--:|:--:|:--:|
| GB/T 19001-2016 质量 | 10 | 28 | 40 | **60** | 三级 |
| GB/T 24001-2016 环境 | 10 | 22 | 16 | **35** | 三级 |
| GB/T 45001-2020 职业健康安全 | 10 | 23 | 26 | **43** | 三级 |
| ISO 13485 医疗器械 | 8 | 23 | 57 | **70** | **四级**（`7.5.9.1`/`6.1.2.1`/`8.1.4.1`） |

**第一个发现**：`13485` 有四级编号，`19001/24001/45001` 最深三级。
⇒ **"最深层级"是标准自带的，不是我们定的**；粒度规则必须**按标准**存，不能全局写死一个"取三级"。

**第二个发现（重要）**：我们的 19001 树里，**`6.2` 和 `9.2` 本身就是二级叶子** —— 没有建 `6.2.1/6.2.2/9.2.1/9.2.2`。
而脱敏版那家机构用的正是 `6.2`、`9.2`（不是 `6.2.1`）。
⇒ **我们已有的条款树，粒度上已经和持证机构一致了。** 这是意外的好消息。

### 1.2 「按最小的小数点一位」这句话要修正

你的直觉方向对，但实测不是"机械取最深"。看 19001 的 11 个「有子条款的二级分支」：

| 二级分支 | 子条款数 | 该机构实际用哪层 | 判定 |
|---|:--:|---|:--:|
| 5.1 领导作用和承诺 | 2 | 用 `5.1` | **合并** |
| 5.2 方针 | 2 | 用 `5.2` | **合并** |
| **7.1 资源** | 6 | 用 `7.1.1`~`7.1.6` | **拆开** |
| ↳ 7.1.5 监视和测量资源 | 2 | 用 `7.1.5`（不再分 7.1.5.1/2） | **合并** |
| 7.5 成文信息 | 3 | 用 `7.5` | **合并** |
| 8.2 产品和服务的要求 | 4 | 用 `8.2` | **合并** |
| 8.3 设计和开发 | 6 | 用 `8.3` | **合并** |
| 8.4 外部提供 | 3 | 用 `8.4` | **合并** |
| **8.5 生产和服务提供** | 6 | 用 `8.5.1`~`8.5.6` | **拆开** |
| **9.1 监视测量分析评价** | 3 | 用 `9.1.1`/`9.1.2`/`9.1.3` | **拆开** |
| 9.3 管理评审 | 3 | 用 `9.3` | **合并** |

**同一个分支里两层并存**：`7.1` 拆到三级，但 `7.1.5` 内部又合回二级。
⇒ 所以规则不是"取最深一级"，而是：**每个分支独立决定停在哪一层，判据是"这一层能不能用一份证据问完"。**

- `7.1` 必须拆：人员 / 设施 / 环境 / 测量资源 / 知识 —— **5 类不同资源，5 份不同证据**
- `7.1.5` 不必拆：`7.1.5.1` 总则 + `7.1.5.2` 测量溯源 —— **一份「设备台账 + 校准报告」就覆盖**
- `8.5` 必须拆：受控条件 / 标识 / 防护 / 交付后 / 变更 / 放行 —— **6 个不同控制点**
- `9.3` 不必拆：管理评审的输入输出 —— **一次评审会议记录全覆盖**

**统计结果：40 个三级条款里，25 个（62.5%）被合并回二级，只有 15 个（37.5%）按三级逐条查。**

### 1.3 由此得出的粒度规则（可落库）

| 层级 | 规则 | 存哪 |
|---|---|---|
| **默认** | 检查到「标准自身的最深编号」= 现有条款树的**叶子** | 不需要字段，树天然表达 |
| **例外** | 某分支可**合并到父节点**检查 | 项目级 `cert_check_item` 一行挂多个 `ClauseCode` |
| **禁止** | 跨二级分支合并（如 `8.5`+`8.6` 合并） | 校验规则，实测无此做法 |

> ★ **关键：默认不需要"合并规则表"。** 我们原来的 `MergeGroupCode`（07 号）想多了 —— 默认就是按树叶子，合并是**例外**，记在实例上即可。

## 二、合并/拆分：不是随意的，有可计算判据

### 2.1 先分清两种"合并"（这是最容易混的一点）

| 类型 | 含义 | 表现 | 影响 | 何时决定 |
|---|---|---|---|---|
| **定义级合并** | 几个条款合并成**一个检查项** | 表格里只出现一个编号（如 `6.2` 覆盖 6.2.1/6.2.2） | 改变**检查项清单**和**工时** | **计划阶段** |
| **记录级合并** | 几个检查项**共用一段审核记录** | 4 个 `过程要求` 行 + 1 段连续文字（P47 的 4.1~4.4） | 只影响**写法**，不影响清单 | **记录阶段** |

脱敏版里两种都存在：
- 定义级：`6.2`、`9.3`、`8.4`（表格里没有子编号）
- 记录级：P47 一页写 `4.1 / 4.2 / 4.3 / 4.4` 四行，但只有一段记录

⇒ **必须分开建模**，否则"检查项数量"和"证据条数"会算错。

### 2.2 判据是可算的

你说"由审核员自己定义"——从**现象**看对，但从**规律**看不对。上面 11 个分支的取舍，全部落在一条判据上：

> **这组子条款要求的材料，是不是同一份？**
> 是 ⇒ 合并；否 ⇒ 拆开。

这条判据我们**已经有数据支撑**：11 号核定的 20 个属性里有 `Artifacts`（要哪些材料）。
⇒ **两两算 `Artifacts` 的 Jaccard 相似度，高于阈值就给"建议合并"，低于就"建议拆开"。**

举例（19001）：

| 分支 | 材料集合（简化） | 相似度 | 建议 |
|---|---|:--:|---|
| 9.3.1 / 9.3.2 / 9.3.3 | 都指向「管理评审记录」 | 高 | 合并 |
| 7.1.3 / 7.1.4 / 7.1.5 | 设施台账 / 环境监测 / 校准报告 | 低 | 拆开 |
| 8.5.2 / 8.5.3 | 标识记录 / 防护措施记录 | 中 | 拆开 |

⇒ **我们不是"猜审核员怎么想"，而是"用材料重合度给出建议"，审核员可采纳可推翻。** 这比让人凭经验重新发明要稳。

### 2.3 归属：四级，各管一段

| 级 | 管什么 | 表 |
|---|---|---|
| **标准级** | 粒度**默认值**（= 树叶子）；`Artifacts`（算相似度的原料） | `cert_iso_clause` + `cert_iso_clause_artifact` |
| **机构级** | 合并**习惯**（这家机构固定把哪几组合并）；跨标准同号合并（`QES` 前缀） | `cert_org_merge_pref`（新） |
| **项目级** | 本次**实际**合并结果（可覆盖机构习惯） | `cert_check_item` 挂多 `ClauseCode` |
| **审核员级** | 记录级合并（一段话覆盖几条） | `cert_check_evidence` 挂多 `item` |

> ★ 你原来的判断"由审核员定义"是对的，但要落到**项目级 + 记录级**，不能落到标准级 —— 否则同一条款在不同项目里粒度不同，条款库就废了。

## 三、审核计划 / 入场计划：为什么必须升级为一级对象

### 3.1 计划是三个对象的交汇点

```
条款（查什么） × 部门（查谁） × 审核员（谁去查）  =  检查项实例
```

三者任缺一个，计划都排不出来：

- 只有条款 ⇒ 不知道去哪查（脱敏版里 `8.4` 只去采购部，`8.5` 只去生产部）
- 只有部门 ⇒ 不知道查什么（财务部只查 `5.3`+`6.2` 两条）
- 没有审核员 ⇒ 不知道谁负责（脱敏版每页页脚都签人）

### 3.2 合并/拆分必须在计划阶段定死

理由很实际：**它决定工时**。以 19001 为例（叶子 60 个）：

| 口径 | 检查项数 | 算法 |
|---|:--:|---|
| 按树叶子逐条（不合并） | **60** | 40 个三级 + 20 个二级叶子 |
| 按实测合并（8 组合并） | **43** | 60 − 25（被合并的三级）+ 8（合并后的二级） |
| **差额** | **17** | — |

差 **17 个检查项**，乘以部门（7 个）就是 **119 条记录的工作量差**。
⇒ 计划阶段不定粒度，排期就是错的。

### 3.3 入场计划 = 疑点清单，不是"时间表"

沿用 03 号已定的四类疑点（问 / 看 / 测 / 沟通），落到 13 号只是**加两个维度**：
- 每条疑点必须挂 **部门**（谁回答）
- 每条疑点必须挂 **审核员**（谁去问）

## 四、审核组织：组 → 成员 → 分工

### 4.1 实证：组是显式的

脱敏版文件名本身就带组：`二阶段-行政部AC组`、`管理层B组`、`行政部B组`。
A 公司主表里，同一企业内按部门换人：

|---|---|
| 采购部 | 李强、吴迪、王芳 |
| 生产部 | 杨帆、黄敏、高翔 |
| 领导层 | 张伟、黄敏、王芳 |
| 销售部 | 李强、吴迪、王芳 |

⇒ 两个特征：
1. **同一企业分多组**（AC 组 / B 组），各组覆盖不同部门
2. **组内有分工**（3 人一组，共享 2~3 个部门）

### 4.2 模型

```
cert_audit_team        审核组（项目级）   ProjectCode + TeamCode + TeamName + LeaderUserCode
```

> ★ 你说的"每个企业可能都由不同的人组织"⇒ **组是项目级（专家端），绝不能做成机构级固定**。机构级（后台）只能存"**可用人员池 + 资质**"（现有菜单：平台管理 → 机构-人员管理 `/system/organization`），**不能存"组"**。

## 五、企业部门：为什么它是第一维度

## 六、机构证据风格：按机构配提示词

### 6.1 实证：两家机构差得很多

| | 中安质环（`ZAZH—SHH/JL 006.2019`） | 科斯亚（人工样本） |
|---|---|---|
| 形态 | **三列表格**（过程要求 / 检查清单 / 审核记录） | 三种：**证据清单** / **证据对照表** / **现场版报告** |
| 不符合标记 | 只有 `N`，**无分级** | 无固定标记，用文字 |
| 条款覆盖声明 | 靠页眉印条款清单 | 靠"条款原文"整段引用 |
| 否定表述 | 「未见…」（现场观察） | 「记录文件中未见，需补充XX」 |
| 抽样明细 | 报告编号 / 证书编号 / 日期 / 签字 | 路径 + 文件名 + 证据说明 |

⇒ **同一个条款、同一批证据，两家机构产出物完全不同。** 这就是你说的"必须按机构配提示词"。

### 6.2 载体已经存在，不用新造

`wf_prompt_template` 已有：`OrgCode` + `PromptCode` + `PromptType` + `StandardCode` + `Template` + `ModelName` + `Version` + `IsActive` + `LastTestResult`。

⇒ **机构级 + 标准级 + 版本化 + 可试跑**，四件套齐了。只需：
1. `PromptType` 增枚举值（如 `audit_evidence` / `audit_nc_draft` / `audit_plan`）
2. `OrgCode` 填机构，`StandardCode` 填标准

### 6.3 还需要补一张表：证据风格

提示词只解决"怎么写"，还缺"写成什么形状"。需要 `cert_org_evidence_style`：

| 字段 | 说明 | 例 |
|---|---|---|
| `OrgCode` | 机构 | — |
| `OutputForm` | 输出形态 | `table3col` / `checklist` / `report` |
| `RequiredElements` | 必填要素（JSON 数组） | `["文件名","文件编号","抽样值","日期","签字人"]` |
| `WordingRules` | 措辞规则（JSON） | `{"否定表述":"记录文件中未见，需补充XX","禁止":"不得虚构数据"}` |
| `SeverityMode` | 分级模式 | `none`（中安质环）/ `two`（国标）/ `four` |
| `PromptCode` | 关联提示词 | → `wf_prompt_template.PromptCode` |
| `SampleRef` | 样例文件 | 脱敏版路径 |

### 6.4 和 02 号「配置层无机构」矛盾吗？

**不矛盾。** 02 号那条铁律的原话是「**标准条款不与机构关联**」—— 防止同一条款在不同机构有不同定义。
`cert_org_evidence_style` 挂的是**输出形态**，不是**条款定义**；机构差异只影响"怎么写"，不影响"查什么"。

> 一句话划界：**条款、属性、粒度默认值 = 无机构；证据形态、提示词、合并习惯 = 有机构。**

## 十、坑（放最后）

1. **`cert_iso_standard.CbCode` 全为 `NULL`** —— 4 个标准的标准号字段都是空的，标准号只存在于 `StandardName` 文本里。做"按标准号匹配"时会全部匹配不上。
2. **`13485` 有四级条款**（`7.5.9.1` 等）—— 任何"取三级"的硬编码都会漏掉它。粒度必须按标准配置。
3. **合并会让"检查项数量"对不上"条款数量"** —— 报表里必须区分「条款数 / 检查项数 / 证据条数」三个口径，否则永远对不平。
4. **`cert_iso_clause_bak_20261026` 存在** —— 说明条款表今天被动过（备份表）。重建条款树前要先确认这份备份的用途，别覆盖掉。
