## 零、先撤回我上一条的一个错误建议

我在 01 号评审时提过「严重度下沉到**分项级**」。**作废。**

理由就是你的第 1 条：**a/b/c 不会被单独拆成检查项**。既然分项不是独立实体，就没有"分项级严重度"这个落点。

**修正为：严重度 / 取样深度下沉到「材料级」**。而且 7.1.5 那个例子本来就证明了这一点：

| 缺什么 | 落点 | 该判几级 |
|---|---|---|
| 缺《设备台账》 | 材料（artifact） | 严重 |
| 缺"设备校准状态标识" | 材料（artifact，类型=标识） | 一般 |

两件事的差别，本质是**两份材料的差别**，不是两个分项的差别。所以材料级就够了，不需要引入第三层。**设计反而更简单了。**

## 一、检查单元的粒度：a/b/c 不拆，条款可合并

### 1.1 三层粒度重新定义

| 层 | 是不是独立一行 | 干什么 | 谁来决定 |
|---|:--:|---|---|
| **条款** | ✅ 是 | 检查单元的基础；NC 挂在这一层 | 标准（GB/T） |
| **分项要求 a/b/c** | ❌ **否** | 只是**引用片段**，用来把 NC 写准 | 标准（GB/T） |
| **材料（产物）** | ✅ 是 | **判定粒度的真正落点**（严重度、取样深度） | 标准 + AI 提取 |

### 1.2 那"到底是哪一点不符合"怎么表达？

这是"不拆分"和"能写出 c)"之间的矛盾。解法：

> **`RequirementItems` 是「引用字典」，不是「判定单元」。**

- 判定：按**整条条款 + 逐份材料**做，产出"符合 / 不符合 / 未取证"
- 措辞：不符合时，从 `RequirementItems` 里挑出对应的 key，NC 写成 `8.5.1 c) 未提供监视和测量记录`
- 一行 NC 只挂**一条条款**，但可以**引用其中若干个分项**

所以 `RequirementItems` 不产生独立行、不独立判定、不独立严重度 —— 它只是让 NC 从"8.5.1 不符合"升级成"8.5.1 c) 不符合"。

> **为什么这条重要**：如果分项也拆成行，条款数会从 273 涨到 800+，检查计划会爆炸，而且审核员现场根本不会按 a/b/c 逐条打勾 —— 那是"填表"，不是"审核"。

### 1.3 合并：条款 → 检查项

> ⚠️ **V1.2 更正（见 [13 号](./13-检查粒度与审核组织设计-V1.md) §二）**：本节原设计「标准级存建议合并组 `MergeGroupCode`」**已被实测推翻**。
> 中安质环 79 页报告显示：**默认按条款树叶子逐条查，合并是例外**（19001 的 40 个三级条款中只有 25 个被合并回二级），且**同一分支内两层并存**（`7.1` 拆到三级、`7.1.5` 又合回二级）。
> ⇒ **`MergeGroupCode` 降级为 P2 可选**，真正生效的合并记在**项目级 `cert_check_item`** 上。本节下表保留作历史记录，实施以 13 号为准。
> 另：原举例 `MG-MEASURE = 7.1.5 + 7.1.6` **是错的** —— `7.1.6` 是「组织的知识」，与测量无关；正确应为 `7.1.5.1 + 7.1.5.2`（总则 + 测量溯源）合回 `7.1.5`。

你说"条款之间可以相互合并"。这件事必须**分两级**放，否则会和"标准不与机构关联"打架：

| 层 | 存什么 | 例子 |
|---|---|---|
| **标准级** | **建议**合并组（可空）`MergeGroupCode` | ~~`MG-MEASURE` = 7.1.5 + 7.1.6~~ → 正确：`7.1.5.1 + 7.1.5.2` 合回 `7.1.5` |
| **机构级** | **实际**合并规则（有 `OrgCode`） | A 机构把 4.4+8.1 合并成一项；B 机构不合并 |

**铁律**：
- 标准级的合并组只是**建议**，不是强制。空 = 不建议合并。
- 真正生效的合并发生在**机构级**（不同机构的审核方案不同）。
- **合并只影响"一次查几条"，不影响"缺了算谁的"** —— 开 NC 时仍以**主条款**开单，成员条款在证据描述里列明。

> ★ 还要再分一层：**定义级合并**（合成一个检查项）vs **记录级合并**（几项共用一段记录）。详见 13 号 §2.1。

### 1.4 合并后的 NC 归属规则

```
检查项 = 主条款 7.1.5 + 成员 7.1.6
   ↓ 取证发现"校准证书无法溯源到国家标准"
NC 主条款 = 7.1.6（这条才是"溯源"的要求）
证据描述  = 7.1.5 台账 + 7.1.6 溯源要求，一并说明
```

判定"主条款是谁"的规则：**哪条条款的分项要求被违反，主条款就是哪条**。所以合并组里**每条条款必须保留自己的 `RequirementItems`**，不能合并成一份。

### 1.5 业界印证（详见 08 号）

| 我们的概念 | 业界对应 |
|---|---|
| 标准级条款目录 | OSCAL `catalog` |
| **机构级合并/裁剪** | **OSCAL `profile`**（从 catalog 选择+裁剪，产出 baseline） |
| 跨标准去重合并 | UCF `Intelligent Controls`（15,000 控制 ↔ 4,100 法规） |

**OSCAL 的做法直接印证了"合并归机构级"**：catalog 是标准原文，profile 才是"这家机构/这个项目怎么用"。我们没有发明新东西。

## 二、过程维度：条款管哪个过程、涉及哪些部门

### 2.1 三个概念必须先分开（混在一起就永远做不对）

| 概念 | 属于谁 | 能不能枚举 | 例子 |
|---|---|:--:|---|
| **过程域** | **标准级** | ✅ 能（10 个左右） | 监视和测量资源管理 |
| **企业过程** | **企业级** | ❌ 不能（ISO 9001 不规定过程清单） | 该企业叫"计量管理" |
| **部门** | **企业级** | ❌ 不能（各企业组织架构不同） | 品质部 / 计量室 |

> **关键判断**：ISO 9001 §4.4 只要求企业"确定所需过程"，**从不规定过程清单**。所以"过程"本身是企业级资产。但条款**约束的职能域**是标准级的 —— 7.1.5 永远管"测量资源"，不管企业管它叫计量还是仪校。

### 2.2 为什么部门不能进标准级（一句话）

> **同一个过程，在不同企业归不同部门。**

小企业：计量归品质部。大企业：计量归设备部或独立计量室。把"7.1.5 → 品质部"写进标准级，等于给所有企业硬套一家企业的组织架构 —— 这正是 V1 犯过的错（把机构配方写进标准侧）。

**所以"条款 → 部门"这条边必须经过企业级映射：**

```
标准级：7.1.5 ──→ 过程域「监视和测量资源管理」
                          ↓  （企业级映射，每家一套）
企业级：过程域「监视和测量资源管理」──→ 该企业的「品质部」+「计量室」
```

### 2.3 过程域枚举（建议 10 个）

| # | 过程域 | 覆盖条款（GB/T 19001） | 典型主责部门（仅举例，**不进库**） |
|:--:|---|---|---|
| 1 | 领导与战略 | 5.1 / 5.2 / 5.3 | 总经理 / 管理者代表 |
| 2 | 策划与风险 | 6.1 / 6.2 / 6.3 | 管理者代表 / 体系办 |
| 3 | 支持-人力资源 | 7.1.2 / 7.2 / 7.3 | 人力资源部 |
| 4 | 支持-基础设施与环境 | 7.1.3 / 7.1.4 | 设备部 / 行政部 |
| 5 | 支持-监视测量资源 | 7.1.5 / 7.1.6 | 品质部 / 计量室 |
| 6 | 支持-知识与成文信息 | 7.1.6 / 7.5 | 体系办 / 文控 |
| 7 | 运行-设计与开发 | 8.3 | 技术部 / 研发部 |
| 8 | 运行-采购与外部供方 | 8.4 | 采购部 / 供应商管理 |
| 9 | 运行-生产与服务提供 | 8.1 / 8.2 / 8.5 / 8.6 | 生产部 / 销售部 |
| 10 | 绩效评价与改进 | 8.7 / 9.1 / 9.2 / 9.3 / 10.1 / 10.2 / 10.3 | 品质部 / 体系办 |

> ⚠️ **这不是部门清单，是过程域清单**。表里"典型主责部门"一列**只用于帮你审阅时理解**，不写进数据库。写进库的只有前两列。

### 2.4 一个条款管多个过程域怎么办

**允许一对多**（如 8.5 生产与服务提供同时落在"运行-生产"和"绩效评价"）。但必须指定**一个主过程域**：

- 主过程域 → 决定这条款**默认归哪个部门查**（检查计划的第一轮分组依据）
- 次过程域 → 只用于"证据可能在哪还能找到"

存储：`ProcessAreas`（逗号串）+ `PrimaryProcessArea`（单值）。

### 2.5 部门数据从哪来（现实约束，必须承认）

**当前仓库里没有部门表**（这是 D28 阻塞项）。三条可能来源：

| 来源 | 可靠性 | 成本 |
|---|:--:|---|
| 企业档案里的部门字段 | 高（企业自己填的） | 低 |
| 从文档编制/受控部门反推 | 中（文件上有编制部门） | 中 |
| 审核员现场确认 | 最高 | 高（要人干） |

**建议**：先建映射表结构，数据走「AI 建议 → 审核员确认」，与 §2.3 的过程域映射分开存。**不要在上传时让企业选部门**（13 个部门 = 13 个入口，必放弃）。

## 三、阶段维度：不同阶段对同一条款要求不同

### 3.1 先把两个"阶段问题"分清（最容易混的地方）

你的第 3 条和 V1 遗留的"阶段能推"是**两个不同问题**：

| 问题 | 由谁回答 | 能不能推 |
|---|---|:--:|
| 这条证据**什么时候能拿到** | `EvidenceKinds` | ✅ **能推**（文件→一阶段；记录/现场/人→二阶段） |
| 这个阶段**要不要查**这条款、查到什么程度 | `StageApplicability` | ❌ **不能推，必须配** |

**为什么不冲突**：`EvidenceKinds` 只回答"证据的物理属性"，它推不出"一阶段该不该查 7.3 意识"。一阶段要看"文件有没有写"，但 7.3 本来就没有文件要求 —— 这个结论只能显式配置。

> **所以旧铁律「阶段能推」需要收窄为**：「**证据收集时点**能推；**阶段覆盖范围**不能推」。

### 3.2 阶段不只影响"查什么"，还影响"能不能开单"

查现有 `cert_cert_stage` 表，6 个审核类阶段的性质差异很大：

| 阶段码 | 名称 | 覆盖条款 | 查什么证据 | 判到什么程度 | **能否开正式 NC** |
|:--:|---|---|---|---|:--:|
| **S1** | 第一阶段审核 | 有文件要求的条款 + **9.2/9.3 强制** | 只查**文件** | 有没有 / 全不全 | ❌ **只出「发现/关注事项」** |
| **S2** | 第二阶段审核 | 全部适用条款 | 记录 / 现场 / 人 | 对不对 / 时间 / 一致 / 可追溯 | ✅ 出 NC |
| **SV** | 监督审核 | **抽样 + 周期内全覆盖** | 全类型 | 同 S2 + 变更/改进/事故 | ✅ 出 NC |
| **RC** | 再认证审核 | 全部适用条款，重心**整体有效性** | 全类型 | 有效性 / 适宜性 / 改进 | ✅ 出 NC |
| **SA** | 特殊审核 | 触发范围内 | 按触发原因 | 按触发原因 | ✅ 出 NC |
| **TT** | 转机构审核 | 按剩余有效期折算 | 全类型 | 同 S2 | ✅ 出 NC |

> **★ S1 不能开正式 NC** —— 依据 CNCA-QMS-01:2025 **§5.6.2.3** 原文：「包括所识别的**需引起关注的、在第二阶段可能被判定为**不符合的问题」。也就是说一阶段只标记「潜在不符合」，判定权在二阶段。数据库 `cert_cert_stage.S1` 的描述与此一致。

> ⚠️ **SV 的强制重点：原文是 9 项，不是 4 项。** 现有 `cert_cert_stage.SV` 描述只列了「上次 NC 验证 / 内审 / 管理评审 / 投诉」，漏了 5 项：持续改进进展、持续的运作控制、**任何变更**、**证书与标志使用**、**质量事故**。依据 §5.7.3（全文见 09 号 §4.1）⇒ 需修正该表描述文字。

### 3.3 一阶段的"不查"有默认推导规则

```
若 EvidenceKinds ∩ {doc} = ∅  ⇒  该条款在 S1 默认「不查」
```

> ⚠️ **必须配一张「例外清单」**：CNCA-QMS-01:2025 §5.6.2.1 第 (5) 项**明文要求**一阶段确认「已实施了内部审核和管理评审」⇒ **9.2 内部审核 / 9.3 管理评审 在一阶段强制必查**。
> 但这两条的**主要证据是记录（record）不是文件（doc）**，按上面的默认推导会被误判成"不查"。
> ⇒ 所以推导规则**不能单独生效**，必须有例外清单覆盖（并记录覆盖理由）。依据见 09 号 §2.3。
典型：7.3 意识（证据形态=人，无文件要求）⇒ S1 不查，S2 查。

但**允许人工覆盖**：有些条款虽无成文信息要求，一阶段仍要确认"制度上有没有规定"。覆盖后记入 `Note` 说明原因。

### 3.4 存储：新增子表 `cert_iso_clause_stage`

一条条款 × 6 个审核阶段 = 最多 6 行（**稀疏：只填有差异的**，空 = 继承条款级默认）。

| 列 | 说明 |
|---|---|
| `ClauseCode` | 条款 Code |
| `StageCode` | S1 / S2 / SV / RC / SA / TT（引用 `cert_cert_stage.StageCode`） |
| `StageApplicability` | **必查** / **可抽** / **不查** |
| `EvidenceKinds` | 该阶段查哪几类证据（留空 = 继承条款级） |
| `CheckModes` | 该阶段用哪几种判定（留空 = 继承条款级） |
| `CanIssueNc` | 该阶段能否开正式 NC（S1 默认 0） |
| `Note` | 为什么这样配 |

### 3.5 阶段归属哪一级

| 内容 | 归属 | 理由 |
|---|:--:|---|
| 阶段清单（S1/S2/SV/RC/SA/TT） | **标准级** | ISO/IEC 17021-1 强制，所有机构共同遵守 |
| 条款 × 阶段 的覆盖要求 | **标准级** | 同上（一阶段审文件、二阶段审实施是通则） |
| **抽样比例 / 人日 / 审核组配置** | **机构级** | 各机构审核方案不同，且受 IAF MD5 等约束 |

> **铁律**：阶段是标准级的，**抽样是机构级的**。`StageApplicability` 只标「必查/可抽/不查」，**不标具体抽几条**；具体抽样比例由机构在审核方案里定（并受 IAF MD5 等约束）。

> ⚠️ **V1.1 更正**：本表原写「S1 约 30% 适用条款」，**该说法已撤回**。经核对 CNCA-QMS-01:2025 原文全文，「30%」只出现在 §5.4.3.4 的**多场所抽样**（监督审核抽不少于 30% 的**场所**），与条款覆盖率无关。国标对一阶段的规定是**7 项内容清单**，没有任何比例数字。
> **阶段要求的全部国标依据见 [09 号](./09-阶段检查要求的国标依据-V1.md)**（含原文逐条摘录，可对照 PDF 核对）。
