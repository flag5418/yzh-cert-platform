# 文档匹配设计：语义匹配与可信度（V1）

> 2026-10-26 ｜ V2 设计文档 10
> 起因：用户指出「**企业并不是按标准原样提供文档名称的，我们只是要根据条款的要求，找到符合条款的文档**」+「**很多东西还是需要语义分析的**」+「**找到的信息还有一个可信度的概念**」。
> 本文回答三个问题：① 为什么不能按名字匹配 ② 那按什么匹配 ③ 匹配结果怎么表达"有多可信"。

---

## 一、先看实证：企业文件名里根本没有条款号

取自本项目真实案例 `docs/90-归档/案例资料/科斯亚质量体系文件`（常州科斯亚自动化科技有限公司）：

| 真实目录 / 文件名 | 它其实对应哪条款 | 名字里有条款号吗 |
|---|---|:--:|
| `04-记录文件/03监视和测量设备控制记录--（企业填写并提供校准报告）` | **7.1.5 监视和测量资源** | ❌ |
| `04-记录文件/21产品和服务的放行控制记录--企业提供实际表单，如果没有按模板做几份` | **8.6 产品和服务的放行** | ❌ |
| `04-记录文件/17生产和服务提供控制记录--生产记录需提供实际或企业填写` | **8.5.1 生产和服务提供的控制** | ❌ |
| `04-记录文件/23内部审核记录--打印后签到表培训手签` | **9.2 内部审核** | ❌ |
| `04-记录文件/05基础设施及过程环境控制记录--填写设备名称` | **7.1.3 基础设施** | ❌ |
| 文件编号 `KSY-QMS-P-17-01` / `KSY-QMS-WI-09` | 程序/作业指导书的**内部序号** | ❌ |

**三条硬事实**：

1. **文件名里没有任何条款号** —— 一个都没有。
2. **名字是"控制记录"这种职能化表述**，不是标准用语（标准说"监视和测量资源"，企业写"监视和测量设备控制记录"）。
3. **名字后面还挂着一串操作说明**（`--（企业填写并提供校准报告）`），这是给企业看的填报要求，不是文档语义。

> **结论**：`DocPattern`（文件名关键字）**不能做主匹配键**，只能做最弱兜底。V1 时期把它当主键，方向就错了。

## 二、那按什么匹配：三级，主次分明

```
                ┌─────────────────────────────────────────┐
   条款侧        │  Intent（作用）+ MatchAnchors（语义锚点） │
                │  Artifacts（要什么材料）+ Fields（要哪些栏目）│
                └───────────────────┬─────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  L1 语义匹配（主）            L2 结构匹配（辅）            L3 名称兜底（最弱）
  读文档**正文内容**            读文档**实际栏目**            读**文件名/编号**
  判"这段内容在讲什么"          判"这份表有没有这几栏"        判"名字里有没有关键词"
  权重 0.6                    权重 0.3                    权重 0.1
```

### 2.1 L1 语义匹配（主，权重 0.6）

**做法**：把「条款的 `Intent` + `MatchAnchors`」与「文档正文的切片」做语义相似度。

**为什么必须读正文**：`03监视和测量设备控制记录` 这个目录名，只能告诉你"这是设备相关记录"；但里面的《校准证书管理与预警台账》才是 7.1.5 的真正证据 —— **语义在内容里，不在名字里**。

**关键设计**：条款侧需要一个**语义锚点集合** `MatchAnchors`，因为单靠 `Intent`（一句话 ≤60 字）语义密度不够。锚点包含：

| 锚点类型 | 例（7.1.5） |
|---|---|
| 核心概念 | 测量设备 · 校准 · 检定 · 溯源 · 有效期 |
| 企业常见叫法 | 计量器具 · 仪校 · 内校 · 外校 · 台帐 |
| 典型文档名 | 设备台账 · 校准证书 · 校准计划 |
| 典型栏目名 | 设备编号 · 校准日期 · 有效期至 · 校准机构 |
| 反例（易混淆） | 生产设备台账（属 7.1.3，不是 7.1.5） |

> ⚠️ **「反例锚点」是必须的**。`设备台账` 和 `生产设备台账` 长得几乎一样，但一个归 7.1.5、一个归 7.1.3。没有反例锚点，语义匹配必然混淆。

### 2.2 L2 结构匹配（辅，权重 0.3）

**做法**：条款要求的材料栏目（`Fields`）↔ 文档实际的表头栏目。

**为什么有效**：栏目是**最难伪装**的特征。一份表如果真有"校准日期 / 有效期至 / 校准机构"三栏，它大概率就是校准台账 —— 比文件名可靠得多。

**限制**：只对有表格结构的文档有效（Excel / Word 表格 / PDF 表格）。纯文字制度文件没有栏目，L2 权重归 0，全部压给 L1。

### 2.3 L3 名称兜底（最弱，权重 0.1）

`DocPattern` 保留，但**降级**：只在 L1+L2 都弱的时候提供一点点信号，且**永远不能单独把一份文档关联到条款**。

## 三、可信度：不是单一分数，是"可解释的多因子"

### 3.1 为什么不能只给一个 0.87

审核员看到"可信度 0.87"没法判断该不该采信。必须能回答：**为什么是 0.87？哪一项命中了？哪一项没命中？**

所以匹配结果必须存**因子分解 + 理由**：

| 因子 | 权重 | 说明 |
|---|:--:|---|
| `SemanticScore` | 0.45 | L1 语义相似度（0~1） |
| `AnchorHitRate` | 0.20 | 语义锚点命中率（命中数 / 该条款锚点总数） |
| `FieldHitRate` | 0.20 | 栏目命中率（命中栏目 / 条款要求栏目） |
| `NameHitRate` | 0.10 | 文件名/编号关键词命中 |
| `TypeMatch` | 0.05 | 文档类型是否匹配（程序↔程序、记录↔记录） |

**再乘两个惩罚项**：

| 惩罚 | 条件 | 效果 |
|---|---|---|
| 反例命中惩罚 | 命中了该条款的「反例锚点」 | × 0.5，并标红提示 |
| 多条款争用惩罚 | 同一文档同时高匹配 ≥3 条款 | × 0.8，提示"这份文档可能覆盖多条，需人工拆分" |

### 3.2 三档结论（决定后续动作，这是关键）

| 可信度 | 档位 | 系统动作 |
|:--:|---|---|
| **≥ 0.85** | **确定** | 可自动关联，但**仍需在报告里标"经语义匹配"** |
| **0.60 ~ 0.85** | **可能** | **必须人工确认**，进"待确认队列" |
| **< 0.60** | **弱** | **不进候选**，但保留在日志里供排查 |

> **铁律**：**任何匹配结果都不等于"证据成立"**。匹配只回答"这份文档可能在讲这件事"，不回答"这件事做到了"。后者必须靠 `CheckModes` 判定。

### 3.3 「未匹配」和「未取证」要分开

| 状态 | 含义 | 后果 |
|---|---|---|
| `no_candidate` | 没有任何文档达到 0.60 | 进「疑似缺失」清单，**不是 NC** |
| `pending_review` | 有候选但未确认 | 进待确认队列 |
| `matched` | 已确认关联 | 进入判定环节 |
| `rejected` | 人工判定不相关 | 记入反例库，**反过来训练锚点** |

> ★ **`no_candidate` 绝不能直接开 NC。** 依据 CNCA-QMS-01:2025 §5.11.3：审核报告必须含「说明审核基于对可获得信息的抽样过程的免责声明」。**没找到 ≠ 没有。**

## 四、一个条款可能有多种合规实现（对应你说的"每个企业管理不一样"）

### 4.1 问题

同一条款，不同企业的合规做法不同。举两个真实例子：

| 条款 | 实现方式 A | 实现方式 B | 实现方式 C |
|---|---|---|---|
| **7.1.5 测量溯源** | 全部**外校**（送第三方计量机构） | 部分**内校**（自建计量室 + 标准器溯源） | 免校（仅作指示用，不用于合格判定） |
| **8.5.1 f) 特殊过程确认** | **五要素确认**（人机料法环） | **工艺验证**（连续三批合格） | 委托**外部机构确认** |
| **9.2 内部审核** | 集中式年度内审 | 滚动式（每月一个部门） | 集团统一组织 + 分公司互审 |

**如果系统只认一种做法，另外两种都会被误判成"不符合"** —— 这是最危险的错误方向（冤枉企业）。

### 4.2 设计：`ImplementationVariants`（可接受的实现变体）

条款属性新增一项：

```json
{
  "variants": [
    {
      "key": "external_calibration",
      "name": "全部外校",
      "requiredArtifacts": ["校准证书"],
      "requiredAnchors": ["校准机构", "溯源"],
      "applicableWhen": {"has_internal_lab": false}
    },
    {
      "key": "internal_calibration",
      "name": "部分内校",
      "requiredArtifacts": ["标准器溯源证书", "内校规程", "内校记录"],
      "requiredAnchors": ["标准器", "内校规程"],
      "applicableWhen": {"has_internal_lab": true}
    }
  ],
  "exhaustive": false
}
```

**两条铁律**：

1. **`exhaustive: false` 是默认值** —— 变体清单是"已知的常见做法"，**不是穷举**。企业用了清单外的做法，只能判"未识别实现方式，需人工确认"，**不能判不符合**。
2. **判定顺序**：先问"企业用了哪种变体" → 再按该变体的要求判 → **不能用 A 变体的要求去判 B 变体**。

> 这条设计直接来自你的话：「条款是一个指导性的，但每个企业的管理可能不太一样」。**国标说的是"应达到什么状态"，不是"必须用哪种方法"。**

## 五、数据落点

### 5.1 条款属性新增（3 项，并入 11 号核实表）

| 属性 | 说明 |
|---|---|
| `MatchAnchors` | 语义锚点集合（含反例锚点） |
| `ImplementationVariants` | 可接受的实现变体 |
| `SourceRef` | 该属性在标准原文的出处（页码/条款段落），供追溯 |

### 5.2 匹配结果表（新表，项目级）

```
cert_clause_evidence_match
  条款 Code × 文档 Code
  SemanticScore / AnchorHitRate / FieldHitRate / NameHitRate / TypeMatch
  PenaltyJson（反例命中 / 多条款争用）
  Confidence（最终加权分）
  MatchLevel（certain / probable / weak）
  Status（no_candidate / pending_review / matched / rejected）
  ReasonText（人可读的理由，进报告）
  VariantKey（用了哪种实现变体）
  ConfirmedBy / ConfirmedTime（人工确认留痕）
```

**关键点**：

- 这是 **M:N** 表（一条款多文档，一文档多条款）。8.5.1 一个条款在科斯亚案例里就关联了 **20+ 份文档**。
- 每行都要有 `ReasonText` —— 报告的"证据描述"直接从这里长出来，不能事后凭空写。

### 5.3 与已有表的边界

| 表 | 管什么 | 不管什么 |
|---|---|---|
| `cert_iso_clause_artifact` | 条款**应该**要哪些材料（应然） | 企业**实际**提供了什么 |
| **`cert_clause_evidence_match`** | **实际文档 ↔ 条款的匹配关系**（实然对上应然） | 判定结论 |
| `cert_extraction_result` | 文档里**抽出了什么内容**（既有表） | 匹配与判定 |

## 六、目标输出长什么样（用真实样本校准）

科斯亚案例里，同一条款 8.5.1 有三种成熟输出形态，**这就是我们要自动生成的东西**：

| 样本 | 形态 | 用在哪一步 |
|---|---|---|
| `8.5.1条款证据清单.md` | 逐条证据清单（a-1/a-2…，每条一个文件+路径+说明） | **准备阶段**：期望集 |
| `8.5.1条款审核证据.md` | 证据对照表（a~h × 证据描述 × 文件路径），带"直接/间接/缺失"判定 | **文件审核**：一阶段 |
| `8.5.1条款审核证据_现场版.md` | 现场审核报告风格（抽样覆盖产品/关键工序/作业依据），未见处写"记录文件中未见，需补充XX" | **现场审核**：二阶段 |

**三个样本共同证明了三件事**：

1. **整条 8.5.1 是一次审核、一份输出** —— a~h 不拆成 8 个检查项（印证 07 号 §1.2）
2. **每条证据都要落到具体文件 + 具体栏目/数值**（如"二次元 设备编号20240701127，证书LX168-263076730，有效期至2027-05-14"）
3. **"未见"的写法是"记录文件中未见，需补充XX"，不是"不符合"** —— 现场版原文如此
