# 业界条款模型对标（V1）

> 2026-10-26 ｜ V2 设计文档 08
> 问题：**有没有现成的条款模型可以直接用？**
> 结论先行，证据在后。所有引用均标注来源，未验证的一律标注「行业口径」。

---

## 一、结论（先看这三句）

1. **不存在**可直接使用的「ISO 管理体系标准条款模型」—— 没有任何开源/商业产品把 GB/T 19001 / 14001 / 45001 的条款做成结构化数据 + 判定规则。
2. **但有三个现成模型可以拆着用**：**OSCAL**（借结构）、**SCF**（借属性集）、**VDA 6.3**（借过程维度 + 降级规则）。
3. 我们要做的不是"发明"，是**拼装 + 补最后一段**：把这三者的长处拼起来，落在 ISO/IEC 17021 的审核流程上。**唯一真正的空档是「证据 → 判定」这一段**（与 39 号市场分析的结论一致）。

---

## 二、逐个分析

### 2.1 OSCAL（NIST）★ 结构上最接近，但领域不对

**是什么**：Open Security Controls Assessment Language，NIST 主导的**机器可读合规模型**，提供 XML / JSON / YAML 三种格式。
（来源：<https://pages.nist.gov/OSCAL/>）

**四层结构**（这是最值得抄的部分）：

| OSCAL 层 | 装什么 | 对应我们的 |
|---|---|---|
| `catalog` | 控制项目录：id / title / **params** / **parts** / related-controls / refs | **标准级条款属性**（02–05 号） |
| `profile` | 从 catalog **选择 + 裁剪**，产出 baseline | **机构级合并/裁剪规则**（07 号 §1.3） |
| `assessment-plan` | reviewed-controls / assessment-subject / assets / **tasks** | **准备阶段 + 入场计划**（03 号） |
| `assessment-results` | findings / observations / POA&M | **检查报告 + NC** |

**`control` 内部的 `parts` 分解**（直接印证我们的"分项要求"设计）：

| OSCAL part | 含义 | 对应我们的 |
|---|---|---|
| `statement` | 要求陈述（可含 a/b/c 子项） | `RequirementItems` |
| `guidance` | 实施指南 | — |
| `objective` | 控制目标 | `Intent` |
| `assessment-method` | 规定的评估动作 | `CheckModes` |

**`assessment-plan` 的两个字段最值得借**：

- `assessment-subject` = **locations / components / inventory-items / users**
  ⇒ 这正是我们缺的「**部门 / 场所 / 人员**」维度（你第 2 条要的东西，OSCAL 已经抽象好了）
- `task` = 里程碑 + **assessment-actions**（具体动作清单）
  ⇒ 这就是「**入场计划**」：什么时间、去哪、做什么

**评估方法三分类**（NIST SP 800-53A）：**Examine（查）/ Interview（问）/ Test（测）**
⇒ 与 03 号的疑点四分类高度一致（`request`/`observe`/`interview`/`verify` 可映射为 Examine/Test/Interview/Examine）。

**⚠️ 关键限制**：NIST 自己在文档里写明 ——

> "The OSCAL catalog model was designed to represent security and privacy controls; however, **it may be possible to apply OSCAL to other applications related to safety, health, or other purposes. These other applications have not been explored so far.**"
> （来源：<https://pages.nist.gov/OSCAL/learn/concepts/layer/control/catalog/>）

**翻译**：OSCAL **从未**被用于 ISO 管理体系标准。所以：**借结构，不借内容，不要指望能直接用。**

### 2.2 SCF（Secure Controls Framework）★ 属性集上最接近

**是什么**：免费元框架（meta-framework），**1,500+ 控制项、34 个域**，映射到 **200+** 法规/框架/标准。
（来源：<https://securecontrolsframework.com/>；GitHub README 写 "100+"，官方站点写 "200+"，**口径不一**）

**它带的元数据，几乎就是我们属性字典的翻版**：

| SCF 元数据 | 对应我们的字段 | 说明 |
|---|---|---|
| **Control questions** | `QuestionHint` | 每个控制项自带"该问什么" |
| **Control weighting** | `Severity` | 权重 ⇒ 缺失严重度 |
| Maturity model criteria（基于 SSE-CMM） | — | 我们暂不需要（不做成熟度评级） |
| Associated risks & threats | — | 安全域特有 |
| **RASCI matrix** | **过程域 → 部门** | 责任分工矩阵 ⇒ 你第 2 条要的"涉及哪些部门" |
| **Cadence**（执行频次） | **阶段要求** | 多久查一次 ⇒ 你第 3 条要的"阶段" |

**⚠️ 限制**：
- 领域是**网络安全/隐私**，不是质量管理体系
- **闭源**：官方只发 Excel + 商业 API，不提供可编程的完整模型
- **没有"审核流程"层** —— 它只到"控制项 + 证据要求"，没有检查计划/入场计划/报告

**可借的**：属性清单的**完备性校验**（拿它的字段表对照我们有没有漏项）；`Control questions` / `weighting` / `RASCI` / `cadence` 四个概念。

---

### 2.3 UCF（Unified Compliance Framework）★ 「条款合并」的成熟商业实践

**是什么**：20 年积累，**15,000+ Intelligent Controls**，映射到 **4,100+ authority documents**，主打**跨标准调和（harmonization）与去重**。
（来源：<https://www.unifiedcompliance.com/>、<https://mapper.unifiedcompliance.com/>）

**核心能力正好是你说"条款可以相互合并"**：它把不同法规里"其实是同一件事"的要求，归并成一个 Intelligent Control，再反向映射回各自条款号。这就是 **M:N 合并 + 可回溯到原文**。

**⚠️ 限制**：闭源商业产品，无条款原文、无判定规则、无中国国标覆盖。

**可借的**：**合并后必须能反向定位到原文条款**这条铁律（对应 07 号 §1.4 的"主条款 + 成员条款"设计）。

---

### 2.4 VDA 6.3 ★ 唯一「过程维度 + 条款 + 判定规则」齐全的现成模型

**是什么**：德国汽车工业联合会（VDA）的过程审核标准，第四版 2023 年发布。**它本身就是一份"条款 + 检查表 + 评分规则"的完整体系**。

| 特征 | 内容 | 对应我们的 |
|---|---|---|
| **过程维度** | P1 潜在供应商分析 + **P2 项目管理 / P3 产品开发 / P4 供应商管理 / P5 生产 / P6 客户关怀 / P7 服务** | 07 号 §2.3 的**过程域**（它做得比我们细，且是行业共识） |
| **条款级提问** | 每个过程下若干编号提问（如 `P6 6.1.2`） | 条款 + `RequirementItems` |
| **量化打分** | 每个提问 **0 / 4 / 6 / 8 / 10** 分 | 我们的"符合/不符合"是二值，**它是五值** —— 更细，但需要更多现场判断 |
| **降级规则** | 个别关键提问得 0 分 ⇒ **整体评级下调** | 我们的 `Severity` 升级规则 |
| **检查表含「受审部门」列** | 每个提问标注由哪个部门接受审核 | 07 号 §2 的「条款 → 部门」 |

**⚠️ 限制**：汽车行业专用（不覆盖 9001/14001/45001 全条款）；载体是 Word/Excel/PDF，**非结构化**。

**可借的 3 条**：
1. **过程清单是可以行业标准化的** —— 我们不必自己发明 10 个过程域，可参考 VDA 的切法
2. **降级规则**（关键项 0 分 ⇒ 整体降级）比"逐项判严重度"更接近审核员的真实思维
3. **检查表必须标"受审部门"** —— 这条直接支持你第 2 条

### 2.5 ISO/IEC 17021-1 / CNCA 认证规则 / IAF MD ★ 流程权威，但没有数据模型

| 来源 | 提供什么 | 缺什么 |
|---|---|---|
| ISO/IEC 17021-1 | 两阶段审核强制（§9.3.1.2 / §9.3.1.3）、NC 分级、审核时间 | **无条款级模型** |
| CNCA 管理体系认证规则 | 一阶段可不在现场、二阶段必须在现场、监督要求 | **无条款级模型** |
| IAF MD5 | 审核人日计算 | **无条款级模型** |

**这三者是我们"阶段维度"的权威依据**（07 号 §3 全部引用它们），但它们只规定**流程**，不规定**数据结构**。⇒ 这部分必须自己做。

## 四、所以我们的做法：拼装，不发明

| 我们的模块 | 从哪借 | 借什么 | 必须自己做的 |
|---|---|---|---|
| 条款属性主表 | **SCF** | 字段清单完备性（questions / weighting / cadence / RASCI） | GB/T 条款的**中文语义**提取（AI 流水线） |
| 分层架构 | **OSCAL** | catalog → profile → plan → results 四层 | 把 profile 换成"机构级合并规则" |
| 分项要求 | **OSCAL** | `parts.statement` 的 a/b/c 结构 | 中文条款的 a/b/c 切分 |
| 过程维度 | **VDA 6.3** | P1–P7 的过程切法 | 10 个过程域的中文枚举 + 企业级部门映射 |
| 阶段维度 | **17021 + 现有 `cert_cert_stage`** | S1/S2/SV/RC/SA/TT 六码 | (条款 × 阶段) 矩阵的实际填充 |
| 判定规则 | **VDA 6.3** | 降级规则思路 | **证据 → 判定**（★ 唯一空档，认证行业 0 成品） |
| 证据模型 | **OSCAL** | `assessment-subject` + Examine/Interview/Test | 录音/照片/现场笔记的采集与关联 |

### 4.1 现在就能借的 5 条（低成本高收益）

1. **`assessment-subject` 的四个维度**（locations / components / inventory-items / users）⇒ 直接用于我们缺的"部门/场所/人员"，不用自己设计
2. **Examine / Interview / Test 三分法** ⇒ 校验我们的疑点四分类有没有漏（结论：没有，但 `request` 本质是 Examine 的前置动作，可考虑合并）
3. **`profile` 概念** ⇒ 印证"合并规则归机构级"是对的，不是我们瞎定的
4. **VDA 的降级规则** ⇒ 比"逐项判严重度"更贴近审核员真实判断，建议在机构级加一层
5. **SCF 的 `Control questions`** ⇒ 印证 `QuestionHint` 该有，但**最终问法归机构提示词**

### 4.2 不要借的 3 条（会带偏）

1. **不要用 OSCAL 的 XML/JSON 格式直接存** —— 它太重（一个 control 的 JSON 上百行），我们只需要它的**概念分层**，不需要它的**序列化格式**
2. **不要抄 SCF 的成熟度模型** —— 我们不做成熟度评级（V1 已明确"定位=辅助系统，ISO shall 不适用"）
3. **不要抄 VDA 的五档打分** —— 0/4/6/8/10 需要审核员现场量化判断，我们的定位是"辅助"，二值（符合/不符合/未取证）足够

---

## 五、一句话回答你的问题

> **有现成的"条款模型"，但没有现成的"ISO 体系认证条款模型"。**
> 结构抄 OSCAL，属性抄 SCF，过程维度抄 VDA 6.3，阶段维度用现有的 `cert_cert_stage`。
> **真正没人做的是「证据 → 判定」这一段** —— 这也正是 39 号市场分析里"认证行业 0 成品"的同一个结论。
