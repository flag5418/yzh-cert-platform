## 一、功能概述

本文档解决"一个企业同时进行多个 ISO 标准认证"（行业术语：**结合审核 / combined audit**）在本系统的支持问题，分两层：

| 层 | 内容 | 优先级 |
|---|---|---|
| 基础层（方案 A） | 多标准并行：企业挂 1..N 个标准，各标准独立推进阶段、独立 NC 检查、独立报告 | P1（MVP 必须） |
| 增强层（方案 B） | 结合审核编排：一次检查任务覆盖多标准的通用条款（HLS 同构条款只跑一次、结论分发到各标准），显著降低三体系审核员的重复劳动 | P2（种子客户验证后） |

**核心结论（重评估确认）**：现有数据模型 `ent_enterprise_phase(enterprise_code, standard_code, phase_code)` 三元组唯一已天然支持多标准，**无需推翻任何核心表**；需要修正的是 OSS 路径语义、企业-标准显式绑定缺失、以及 V1 历史文档中"企业绑定单一标准/单活跃阶段"的错误表述（已在新主文档中修正）。

## 二、业务背景与目标

### 2.1 行业事实（联网核实，2026-09-01）

1. **结合审核是规范定义的主流场景**：GB/T 19011-2021（等同 ISO 19011:2018）术语——"一个组织中两个或两个以上管理体系一起接受审核"即构成结合审核；GB/T 27021.1（认证机构要求）明确"确定审核时间时，应考虑是否为结合审核"。
2. **三体系 = 中国制造业刚需**：ISO 9001（质量）+ ISO 14001（环境）+ ISO 45001（职业健康安全）并行人审极常见（招投标硬性要求）；三标准共享 HLS 高层结构（第 4~10 章框架一致：组织环境/领导/策划/支持/运行/绩效评价/改进），通用条款可合并审核。
3. **证书/报告/NC 独立**：即使结合审核，**每张证书独立、每份报告独立、NC 按标准+条款独立记录**——这是本系统"报告按标准独立生成"设计的行业依据。
4. **结合审核的动机是省人日**：认证机构一次进场、一个审核组覆盖三标准，人日数打折；同理，对审核员而言三体系的通用条款（如 9.2 内部审核、9.3 管理评审）逐标准重复检查是最大的重复劳动——这正是本产品"减轻审核员负担"定位下的价值高点。

### 2.2 现状核实结论（逐层检查，2026-09-01）

| 层 | 检查点 | 结论 |
|---|---|---|
| 数据模型 | `ent_enterprise_phase` 唯一键 `(enterprise, standard, phase)` | ✅ 天然支持多标准 |
| NC 规则 | `cert_validation_rule` 按 `(标准, 阶段, 条款, 工作流)` | ✅ 每标准独立规则集 |
| 报告 | `cert_report_template` 按 `(机构, 标准, 阶段)`；`rpt_report_task` 挂 phase | ✅ 每标准独立报告 |
| NC 记录 | `audit_nonconformity` 挂 task→phase→standard | ✅ NC 天然带标准归属 |
| OSS 路径 | `/enterprise-documents/{EntCode}/{OrgCode}/{StandardCode}/{PhaseCode}/...` | ⚠️ 残留问题 R1：企业基础资料（营业执照/组织架构图等与标准无关的文件）无处安放 |
| 目录实例 | `ent_enterprise_document.scope`(enterprise/stage) 已预留 | ⚠️ 残留问题 R2：scope=enterprise 的目录在 OSS 路径上没有对应落点（路径强制含 StandardCode+PhaseCode），设计与路径脱节 |
| 企业-标准绑定 | 无显式关联表，靠 phase 记录隐式推导 | ⚠️ 残留问题 R3：新建企业多标准交互缺少干净落点；企业卡片聚合需 group by |
| 任务编排 | 一次任务只能挂一个 phase（一个标准） | ⚠️ 残留问题 R4：结合审核能力空白（方案 B 解决） |

### 2.3 目标

1. P1：企业建档多标准、并行推进、独立报告的完整闭环，语义干净无歧义；
2. P2：三体系一次检查，通用条款只执行一次工作流，结论自动分发三标准，检查成本从 3× 降至约 1.3×；
3. 全程不改核心表结构（`ent_enterprise_phase` 等不动），改造收敛在存储路径规则、一张显式绑定表、任务编排层。

## 四、业务规则

### 4.1 多标准并行规则（方案 A，P1）

| 规则 | 说明 |
|---|---|
| 企业-标准 1..N | 企业建档时可选多个标准（机构可用标准集内多选）；建后可追加/移除（有阶段记录的标准不可直接移除，需先处理其阶段） |
| 阶段独立推进 | 每个标准下独立创建/推进/归档阶段；不同标准可同时各有进行中阶段（无单活跃约束） |
| 资料两层 | 企业基础资料（scope=enterprise，跨标准共享一份）+ 阶段资料（scope=stage，标准+阶段隔离）；行业惯例：营业执照等基础资料三体系共用 |
| 检查/报告独立 | NC 检查任务、报告任务按标准独立发起；NC 带标准归属；报告每标准一份 |
| 展示上下文 | 涉及标准的页面（任务详情、条款树、报告、资料）必须显式携带 standardCode；企业详情页按标准分组展示阶段 |

### 4.2 结合审核规则（方案 B，P2）

| 规则 | 说明 |
|---|---|
| 任务组 | 一次"结合检查"创建 1 个任务组（task group），内含 N 个标准的子任务（每标准一个 audit_task，phase 对齐） |
| 通用条款只跑一次 | 任务组内，条款映射表中标记为 HLS 同构的条款组（如 9001:9.2 ↔ 14001:9.2 ↔ 45001:9.2）只执行一次工作流（以主标准规则为准，默认 9001） |
| 结论分发 | 通用条款的工作流结论按映射分发写入各标准的检查结果（`ent_file_compliance_check` 按标准+条款各落一条，共享 execution 引用） |
| 标准特有条款 | 映射表中无映射的条款（如 14001 的 8.1.2 环境因素）各标准独立执行 |
| 报告独立不变 | 报告仍按标准各出一份；通用条款结论复用注入 |
| 降级兼容 | 未配置映射的标准组合 = 退化为逐标准独立检查（方案 A 行为），不阻断 |

## 五、数据设计

### 5.1 方案 A 新增/改造

**5.1.1 `ent_enterprise_standard`（企业-标准显式绑定表，新增）**

```sql
CREATE TABLE `ent_enterprise_standard` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `code` varchar(36) NOT NULL COMMENT '编码(GUID)',
  `enterprise_code` varchar(36) NOT NULL COMMENT '关联企业 code',
  `standard_code` varchar(36) NOT NULL COMMENT '关联标准 code',
  `status` varchar(20) NOT NULL DEFAULT 'active' COMMENT 'active/archived',
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '绑定时间',
  `create_id` int NOT NULL COMMENT '创建审核员ID',
  `creator` varchar(50) DEFAULT NULL,
  `create_date` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `modify_id` int DEFAULT NULL,
  `modifier` varchar(50) DEFAULT NULL,
  `modify_date` datetime DEFAULT NULL,
  `enable` tinyint(1) NOT NULL DEFAULT '1',
  `status_ext` varchar(50) NOT NULL DEFAULT 'active',
  `remark` varchar(500) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_code` (`code`),
  UNIQUE KEY `uk_ent_std` (`enterprise_code`, `standard_code`),
  KEY `idx_enterprise_code` (`enterprise_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='企业-标准绑定(显式)';
```

> 用途：新建企业多标准落点、企业卡片/工作台聚合直读；`ent_enterprise_phase` 继续三元组（冗余 standard_code 便于查询，绑定表与 phase 表由 Service 层保持一致）。

**5.1.2 OSS 路径规则改造（R1/R2 修复）**

```
现状（问题）：
/enterprise-documents/{EntCode}/{OrgCode}/{StandardCode}/{PhaseCode}/{Folder}/{File}
                                            ↑ 企业基础资料被迫塞进某个标准

改造后：
/enterprise-documents/{EntCode}/_base/{Folder}/{FileName}                          ← 企业基础资料层(scope=enterprise)
/enterprise-documents/{EntCode}/{OrgCode}/{StandardCode}/{PhaseCode}/{Folder}/{File} ← 阶段资料层(scope=stage，不变)
```

| 规则 | 说明 |
|---|---|
| `_base` 保留字 | 文件夹命名空间中的保留字，企业短编码（ENT-2026-0001 等）不会与其冲突；路径生成器中硬编码 |
| 基础资料唯一 | 同一企业全标准共用一份基础资料；替换走版本链（ent_file_version），三标准即时共享新版本 |
| 存量迁移 | 当前数据量≈0；上线时执行一次性脚本：scope=enterprise 的存量文件挪入 `_base` 路径并更新 storage_path |
| 阶段资料层不动 | 现有路径规则、转换产物 `.converted/` 规则完全不变 |

**5.1.3 `ent_enterprise_document` 语义对齐（R2 收口，无 DDL）**

| scope | OSS 落点 | phase_code |
|---|---|---|
| enterprise | `_base` 层 | 恒为 NULL |
| stage | 标准+阶段层 | 必填 |

Service 层写入校验：scope=enterprise 时忽略 standard/phase 维度；上传基础资料时目录树取机构配置的企业基础资料模板。

### 5.2 方案 B 新增（P2）

**5.2.1 `cert_clause_mapping`（跨标准通用条款映射表）**

```sql
CREATE TABLE `cert_clause_mapping` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `code` varchar(36) NOT NULL COMMENT '编码(GUID)',
  `group_code` varchar(36) NOT NULL COMMENT '映射组编码(一组同构条款共享)',
  `standard_code` varchar(36) NOT NULL COMMENT '标准 code',
  `clause_code` varchar(36) NOT NULL COMMENT '条款 code(cert_iso_clause.code)',
  `mapping_type` varchar(20) NOT NULL DEFAULT 'hls' COMMENT 'hls=HLS同构(通用)/unique=标准特有',
  `is_primary` tinyint(1) NOT NULL DEFAULT '0' COMMENT '组内主条款(工作流执行基准,默认9001侧)',
  `create_id` int DEFAULT NULL,
  `creator` varchar(50) DEFAULT NULL,
  `create_date` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `modify_id` int DEFAULT NULL,
  `modifier` varchar(50) DEFAULT NULL,
  `modify_date` datetime DEFAULT NULL,
  `enable` tinyint(1) NOT NULL DEFAULT '1',
  `status` varchar(50) NOT NULL DEFAULT 'active',
  `remark` varchar(500) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_code` (`code`),
  UNIQUE KEY `uk_group_std_clause` (`group_code`, `standard_code`, `clause_code`),
  KEY `idx_clause` (`clause_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='跨标准条款映射(结合审核)';
```

> 示例：group_code=G-9.2 内含三条：9001/9.2(is_primary=1)、14001/9.2、45001/9.2，均 mapping_type=hls。配置来源：行业顾问提供 HLS 对照表 → 管理端维护界面录入。

**5.2.2 `audit_task` 增列（任务组）**

```sql
ALTER TABLE `audit_task`
  ADD COLUMN `task_group_code` varchar(36) DEFAULT NULL COMMENT '结合审核任务组编码(组内各标准子任务共享;NULL=独立任务)' AFTER `audit_scope`,
  ADD KEY `idx_task_group` (`task_group_code`);
```

**5.2.3 检查结果分发关联**

`ent_file_compliance_check` 增列：

```sql
ALTER TABLE `ent_file_compliance_check`
  ADD COLUMN `mapping_group_code` varchar(36) DEFAULT NULL COMMENT '通用条款映射组(结论分发标记;NULL=独立检查)' AFTER `rule_code`,
  ADD COLUMN `shared_execution_code` varchar(36) DEFAULT NULL COMMENT '共享的执行记录引用(同组各标准结果指向同一次执行)' AFTER `mapping_group_code`;
```

### 5.3 表约束汇总

| 表 | 唯一约束（硬保障） |
|---|---|
| ent_enterprise_standard | `uk_ent_std(enterprise_code, standard_code)` |

## 七、数据流 / 时序

### 7.1 方案 A：多标准建档与并行推进

```
新建企业(standards=[9001,14001,45001])
  → ent_enterprise
  → ent_enterprise_standard ×3（uk_ent_std 兜底防重）
  → ent_enterprise_phase ×3（各标准首个阶段，三元组唯一）
  → 基础资料目录实例化(scope=enterprise → OSS _base 层)
  → 各标准独立推进：独立 NC 检查任务 / 独立报告任务
```

### 7.2 方案 B：结合检查执行（一次执行，分发落库）

```
createCombined(enterprise, phase, standards=[9001,14001,45001])
  → task_group_code=G001
  → audit_task ×3（G001 组内，各标准一个子任务）
  → 解析检查范围：
      通用条款组 G-9.2（三标准同构）→ 主条款(9001:9.2)执行一次工作流
      标准特有条款（如 14001:8.1.2）→ 各自独立执行
  → 通用条款完成 → 结论分发：
      ent_file_compliance_check ×3（每标准+条款一条）
      共享 shared_execution_code=G001 的同一次执行记录（审计入口唯一、结论三份）
  → 各子任务完成 → 待复核（复核界面按标准分组展示，通用条款复核一次即同步三标准）
  → 报告：每标准独立生成，通用条款结论复用注入
```

## 八、边界与异常处理

| 场景 | 处理 |
|---|---|
| 未配置条款映射的标准组合 | createCombined 降级：仅对已配置映射的条款合并执行，其余独立；完全无映射 = 拒绝创建并提示走普通任务 |
| 映射组缺主条款 | 配置校验拦截（管理端保存时强制每组恰一条 is_primary=1） |
| 组内某标准阶段归档 | createCombined 原子拒绝，列出冲突标准 |
| 通用条款复核修正 | 修正一次同步组内三标准的落库记录（同一映射组联动），修订留痕记录联动范围 |
| 基础资料版本替换 | `_base` 层文件替换 → 版本链 +1，全标准共享；进行中的检查任务按 file_hash 判定是否需要增量重跑 |
| OSS `_base` 与企业短编码冲突 | ENT-2026-XXXX 命名规则与 `_base` 保留字无交集；路径生成器单测覆盖 |
| 存量数据迁移失败 | 迁移脚本幂等（按 storage_path 前缀判断已迁移），失败项清单输出人工处理 |
| standardCodes 含重复 | 去重 + 提示 |
