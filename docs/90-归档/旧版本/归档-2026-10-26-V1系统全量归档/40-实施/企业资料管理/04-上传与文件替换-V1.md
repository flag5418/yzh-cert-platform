## 一、四段式上传（企业侧沿用，参数化到企业库）

### Step 0：选阶段（前置，需求 1 硬约束）

- 前端必须选中**企业 → 阶段**；未选阶段所有上传入口 `disabled`。
- 选中阶段后：解析机构 + 阶段 GUID → 对每个关联标准 `ensure` 企业行（见 02 §四）→ 拉页面主数据。

### Step 1：`POST upload-init`（生成清单 + 预建行 + 算路径）

**请求**（`UploadManifestRequest`）
```json
{
  "DirectoryCode": "企业 config.Code（GUID）",     // 决策⑦ 起 = config.Code
  "OrgCode": "机构 Code",
  "StandardCode": "标准 GUID",
  "PhaseCode": "阶段 GUID",                        // 兼容字段名，语义 = StageCode
  "Folders": [{ "Path": "4记录文件/技术类" }],      // 相对配置根的路径（/ 分隔）
  "Files":   [{ "RelativePath": "4记录文件/技术类/XASL-TR-001 ….doc",
                "FileName": "XASL-TR-001 ….doc", "FileSize": 12345, "MimeType": "application/msword" }]
}
```

**服务行为（`UploadInitAsync`）**

| 步 | 动作 | DB 影响 |
|---|---|---|
| 1 | 定位 config：先按 `Code` 查；再回退 `OrgCode+StandardCode+StageCode`（⚠️ 修订后必须带 OrgCode，缺机构回退会跨机构误命中 ⇒ **禁用**） | — |
| 2 | **队列互斥**：`GetQueueLockErrorAsync(configCode)`（同目录有运行中队列 ⇒ 直接拒绝） | 读 `yzh_queue_resource_lock` |
| 3 | 生成 `TaskId = Guid("N")` | 插 `cert_upload_task`（`Status=initialized`, `ConfigCode`, `TotalFiles`, `TotalSize`, `ExpireTime`） |
| 4 | 处理 `Folders`：按深度排序 → 校验名 → 同 `FullPath` **复用**（`Mode=reuse`）或新建（`IsValid=0` 草稿 + `TaskId`） | 写 `cert_standard_directory_folder` |
| 5 | 处理 `Files`：按 `FullPath` 复用或**预建文件行**（`IsValid=0`、`UploadStatus=pending`、`TaskId`），并**计算并返回 `StoragePath`** | 写 `cert_standard_directory_file` |
| 6 | 返回 `UploadManifestResponse { TaskId, DirectoryCode, TotalFiles, TotalSize, Folders[Enhanced…], Files[EnhancedFileItem{FileCode, StoragePath, ParentFolderCode, Mode}] }` | — |

> **关键契约**：`StoragePath` 在 **Step1 就算好并下发**；Step2 只带 `TaskId + FileCode`，后端从 DB 读路径（防前端伪造路径）。

### Step 2：`POST upload-file-v2`（逐文件传字节）

- 表单：`File`（IFormFile）+ `TaskId` + `FileCode`（`[FromForm]`）
- 服务：`UploadFileAsync(stream, length, fileCode, taskId)` → 按 Step1 记录的 `StoragePath` 调 `IObjectStorage.UploadAsync`
- 前端：`useDirectoryApi.uploadFile()` 用 **裸 `fetch` + `Authorization: Bearer {token}`**（FormData 场景），逐个文件串行，前 500 个文件上限、单文件 50 MB（`YzhFolderUpload` 参数）
- 失败：单文件失败不整体中断，Step3 前由前端统计/可重试

### Step 3：`POST upload-confirm`（激活 + 入队）

| 动作 | 细节 |
|---|---|
| 激活文件行 | `IsValid 0→1`、`UploadStatus` `uploaded→active`、清 `TaskId` |
| 可转换文件额外置双 pending | `UploadStatus='uploaded'`、`ConvertStatus='pending'`、`MarkdownStatus='pending'`、清 `TaskId` |
| 激活文件夹行 | `IsValid 0→1`、清 `TaskId`（⚠️ 查询必须 `includeDisabled: true`，否则草稿文件夹永远查不到 → 目录列表全空） |
| 建转换队列 | `QueueType="file_convert"`、`ScopeKey=config.Code`、`SourceType="upload_task"`、`SourceId=taskId`、资源锁 `RESOURCE_DIR(configCode)`、`Tasks=BuildConvertTasks(...)` → 返回 `convertQueueCode` |
| 任务收尾 | `cert_upload_task.Status='completed'`、`UpdateTime=now` |

### Step 4：`POST upload-cancel`（回滚）

- 取消关联运行中队列（`SourceType='upload_task' AND SourceId=taskId AND Status ∉ (completed,failed,cancelled)`）
- 删除已上传 MinIO 对象（按 `TaskId` 找文件行）
- 删除/回滚预建行（文件行删除；文件夹行回滚 `IsValid`）
- 返回 `{ deleted, restored }`

## 二、状态机（唯一权威）

```
                     ┌─────────────── cert_upload_task.Status ───────────────┐
                     initialized ──(Step3)──> completed
                          └──(Step4)──> (回滚：行删除/对象清理/队列取消)

文件行（cert_standard_directory_file）：
  UploadStatus : pending ──(Step1 预建)──> pending
                 ──(Step2 传字节)──> uploading/uploaded
                 ──(Step3 确认)──> active（不需转换） / uploaded + ConvertStatus=pending（需转换）
                 ──(替换)──> pending/uploading → uploaded
  IsValid      : 0（草稿，页面不可见） ──(Step3)──> 1（可见）
  ConvertStatus: NULL ──> pending ──> converting ──> completed / failed（+ConvertMessage/ConvertDate）
  MarkdownStatus: none ──> pending ──> converting ──> completed / failed / unsupported（+MarkdownMessage/Date）
```

| 组合 | 页面呈现（01 §5.1） |
|---|---|
| `StoragePath` 空 | 缺失 |
| `UploadStatus ∈ (pending, uploading)` | 上传中 |
| `UploadStatus=uploaded` 且 `ConvertStatus ∈ (null,'')` | 已上传 |
| `ConvertStatus ∈ (pending, converting)` 或 `MarkdownStatus ∈ (pending, converting)` | 转换中 |
| `ConvertStatus=completed` | **已就绪**（下游 NC/报告可读） |
| `ConvertStatus=failed` | 转换失败（红，可重试） |
| `MarkdownStatus=failed/unsupported` | 提取失败（橙，**不阻塞就位**） |

## 三、双队列转换（`file_convert`，**零改动复用**）

### 3.1 入队载荷（每个文件 **2 个任务**）

```
BuildConvertPayloads(f) =>
  { Code = f.Code, FileName = f.FileName, SourcePath = f.StoragePath, ConvertType = "office2pdf" }   // 预览链
  { Code = f.Code, FileName = f.FileName, SourcePath = f.StoragePath, ConvertType = "anydoc2md" }    // 提取链
```

`TaskItem { TaskType = "file_convert", Payload = Json(payload), TaskId = <上传任务号或 config.Code> }`

| 设计点 | 理由（源码注释原文要点） |
|---|---|
| **两条独立任务而非一个双产物任务** | ① 失败语义隔离（扫描件能出 PDF 预览、转不了 Markdown —— 合成一个任务整体判失败，用户以为"预览也没好"）；② 可独立重试；③ `ConvertStatus` 与 `MarkdownStatus` 互不干扰 |
| 入队点**不算** `TargetPath` | 产物路径由执行器用 `PathBuilder.Product` 从源路径派生；旧实现在入队点调 `GenerateConvertedStoragePath("","","","",name)` 空参 ⇒ 产物全落 `/standard-directory/.converted/{名}` 互相覆盖（**实测已丢数据**） |
| 判据放宽（`NeedsConversion`） | 只排除"无 `StoragePath`"和"被忽略的系统文件"（`.DS_Store`/`Thumbs.db`/`desktop.ini`）；旧实现只认 `FileType==doc||xls` ⇒ **docx/xlsx/ppt/pptx/pdf 从不入队**（这正是"上传后不转换"的根因） |

### 3.2 执行与回写

`OfficeConvertTaskExecutor`（`TaskType="file_convert"`，**单例**，内部 `CreateScope()` 取 Scoped `OfficeConvertService`）

| ConvertType | 动作 | 产物列 |
|---|---|---|
| `office2pdf` / `doc2pdf` / `xls2pdf` / `docx2pdf` … | LibreOffice 容器 → PDF；**PDF 原样透传**（`PreviewPdfPath = StoragePath`） | `PreviewPdfPath`、`ConvertStatus`、`ConvertMessage`、`ConvertDate` |
| `anydoc2md` / `doc2md` / `pdf2md` / … | anydoc 容器 → Markdown；退出码 3（需 OCR）→ `IOcrProvider`；不支持类型 → `unsupported` | `MarkdownPath`、`MarkdownStatus`、`MarkdownMessage`、`MarkdownDate` |
| `doc2docx` / `xls2xlsx` | 中间产物（兼容存量） | `ConvertedStoragePath` |
| 空 | 自动双产物（PDF + MD，任一失败不阻塞另一个） | 上述全部 |

> **企业库自动兼容**：产物路径由**源路径派生**，源是企业库路径 ⇒ 产物落企业库同层级；执行器按 `FileCode` 查表（企业行同样命中）。
> ⚠️ **企业侧入队必须用 `TaskType="file_convert"`**（现原型写的是 `"convert"` ⇒ 执行器不认 ⇒ 任务永不执行，见 07 B2/B3）。

### 3.3 替换时的产物作废与缓存清理

`InvalidateProductsAsync(file)`：删除旧 `PreviewPdfPath`（**若 `== StoragePath` 则跳过，防删源文件**）、`MarkdownPath`、`ConvertedStoragePath`，并复位 `ConvertStatus='pending'` / `MarkdownStatus='pending'` / 清 `ConvertMessage`/`MarkdownMessage`。
`ClearDocContentCacheAsync(fileCode)`：只清 `cert_doc_extraction_rule.DocContent`（**正文缓存**），**不动规则本身**（字段/表格定义是人工资产；连规则一起清 = 每次替换都要重配）。

> 必要性：不清理 ⇒ 替换后若命中旧 `MarkdownPath`，会读到**替换前的内容**且状态仍显示 `completed`（**静默错误**）。

## 四、多标准分发算法（需求 3 的核心）

**入口**：顶部「所有标准上传」（多标准）。**产出**：`DispatchPlan`（**纯计算，不落库**，人工确认后才执行）。

```
输入：
  Files      = [{ RelPath, FileName }]                    // 一次选择的上传项
  Scope      = (EnterpriseCode, StageCode, Standards[])   // 该阶段关联的全部标准
处理：
  For each 标准 s ∈ Standards:
      T(s) = 模板(s) 的 文件夹树 + 文件定义集
      For each f ∈ Files:
          hit = Match(f, T(s))          // M0→M3 顺序，命中即停
          if hit: rows.Add({ s, hit.FolderPath, hit.TemplateFileCode, f, hit.Level, hit.Confidence })
仅当 rows 为空时才进入 unmatched（未归属）
输出：DispatchPlan { Rows[], Unmatched[], Conflicts[], CrossStandard[] }
```

### 4.1 匹配层级

| 层 | 判据 | 是否需人工确认 |
|---|---|---|
| **M0** | **文件夹路径强匹配**：`f.RelPath` 的目录段 == 模板文件夹 `FullPath`（归一后），且末段文件名命中 M1/M2 | 否 |
| **M1** | **文件名精确**（归一后相等）**且扩展名族兼容**（见下方「扩展名族门」） | 否 |
| **M2** | **文件名主词包含**（模板名去扩展名后的中文主词出现在上传名中）**且扩展名族兼容** | 否 |
| **M3** | **文件夹一层分类 + 扩展名族** | ✅ 标黄，需确认 |

> **★ 扩展名族门（2026-10-08，A 方案，B14）**：M0/M1/M2 此前**完全剥掉扩展名**只比主词 —— 模板要 `制度.doc`、
> 企业传 `制度.pdf`（甚至 `制度.xlsx`）同名也会被判「已匹配」，槽位 `StoragePath` 落库 ⇒ 页面显示「已就位」，
> 格式不符被静默吞掉。修正后：命中主词后必须再过 `DispatchMatcher.ExtCompatible`（任一侧无扩展名放行，
> 否则 `NormalizeExt` 相等）；不兼容 ⇒ **不给命中**，文件落未归属并标 `ext_mismatch`，槽位保持「缺失」。
> 同族（`doc↔docx`、`xls↔xlsx`、`ppt↔pptx`、`jpg↔jpeg`）仍然放行。兜底：`upload/init` 槽位模式同样校验
> （防绕过 `upload/plan` 直调）；唯一人工出口是未归属区的「指派到标准+文件夹」。

### 4.2 归一化函数（集中一处，配单测）

| 规则 | 例 |
|---|---|
| 去编码前缀（`^[A-Za-z]{2,6}[-_][A-Za-z]{1,4}[-_]\d{1,4}\s*`） | `XASL-TR-001 年度验证计划.doc` → `年度验证计划` |
| 去括号注释（`（…）`/`(…)`，含"可根据企业实际修改"） | `4记录文件` / `3制度文件（可根据企业实际修改）` → 同名 |
| 去序号前缀（`^\d+`） | `1质量手册` → `质量手册` |
| 去空格/全半角/下划线/连字符差异 | `XASL_QM` ≡ `XASL-QM` |
| 扩展名族归一 | `doc≡docx`、`xls≡xlsx`、`ppt≡pptx`、`jpg≡jpeg` |
| 大小写不敏感 | `营业执照.PDF` ≡ `营业执照.pdf` |

### 4.3 结果分类

| 类别 | 处理（默认值，见 README D4/D5/D8） |
|---|---|
| **命中行** | 逐标准展示：`上传文件 → 目标文件夹 → 目标标准文件`；可逐行取消 |
| **跨标准命中**（同文件命中多标准） | 提示"将各存一份（共 N 份）" ⇒ 产出 N 行、N 个对象（满足"3 个标准都传 3 份"） |
| **冲突**（同标准内多文件命中同一目标） | 弹「全部上传 / 只取一份」 |
| **未归属** | 单列展示 + `[指派到标准]` `[指派文件夹]` `[忽略]`；**不指派则不入库、不上传**（⛔ 禁止把它塞进所有标准 —— 需求 3 硬约束）。`Reason` ∈ `no_standard` / `no_match` / `ambiguous` / `ext_mismatch`（文件名命中槽位但扩展名不同族，见 §4.1 扩展名族门） |
| **模板外文件** | 视为未归属（D8） |

### 4.4 执行（确认后）

```
For each 标准 s 分组:
    1. ensure 企业行（02 §四）
    2. Step1 upload-init（Folders = 命中行涉及的文件夹全路径；Files = 命中行）
    3. Step2 逐文件上传（StoragePath 已由 Step1 下发）
    4. Step3 upload-confirm（激活 + 该标准一个 file_convert 队列）
未归属：忽略（不产生任何调用）
```

> 单标准上传（入口 A/B）= 上述流程的**单标准子集**，跳过跨标准汇总，直接展示该标准的匹配预览。

## 五、文件替换（归档 + 版本）

### 5.1 两套现有实现对照

| 维度 | 标准侧（`StandardDirectoryService.ReplaceFileAsync`，已跑通） | 企业侧（`EnterpriseFileService.ReplaceFileAsync`，原型） |
|---|---|---|
| 路径策略 | **沿用原路径覆盖**（`StoragePath` 不变 ⇒ 预览/提取引用不变） | 归档旧件 → **新路径重算**（`PathBuilder.EnterpriseFile(...)`） |
| 归档 | ❌ 无（标准侧「纯覆盖」语义） | ✅ `PathBuilder.Archive(path, n)` + `RenameAsync` |
| 版本表 | ❌ 不写 | ✅ 写 `cert_enterprise_file_version` |
| 产物作废 | ✅ `InvalidateProductsAsync` + `ClearDocContentCacheAsync` | ❌ 未做（**静默读旧内容**风险） |
| 重新入队 | ✅ `file_convert` 双任务（`SourceType='file_replace'`） | ❌ 未做（`ConvertStatus` 只置 pending，**不入队 ⇒ 永不转换**） |
| 锁检查 | ✅ `GetFileLockErrorAsync`（队列运行中禁止替换） | ❌ 未做 |
| 文件名回传 | 后端同时写 `Description` ⇒ 前端必须回传原值（否则**清空备注**） | — |

### 5.2 目标实现（企业侧，P4）

```
POST files/{fileCode}/replace   （multipart：File + 可选 Reason）
1. 权限 + 归属校验：file.EnterpriseCode == 当前企业；file.IsValid=1
2. 锁检查：GetFileLockErrorAsync(fileCode)（该文件在运行中队列里 ⇒ 拒绝）
3. 校验：新文件扩展名需与 FileType 兼容（不兼容 ⇒ 拒绝或提示改 FileType）
4. 归档旧件（仅当 StoragePath 非空）：
     n = MAX(VersionNumber)+1（同 FileCode）
     archivePath = PathBuilder.Archive(file.StoragePath, n)      // …/_archive/原名.v{n}
     复制/移动对象到 archivePath
     Insert cert_enterprise_file_version { Code=GUID, FileCode, EnterpriseCode,
        VersionNumber=n, FileName=原文件名, StoragePath=archivePath, FileSize=原大小,
        Reason='用户上传新文件覆盖' }
5. 覆盖上传新件：同一 StoragePath（沿用原路径，保持外部引用稳定）
6. 复位状态：FileSize=新大小、UploadStatus='uploaded'、
     ConvertStatus='pending'、MarkdownStatus='pending'、
     PreviewPdfPath/MarkdownPath/ConvertedStoragePath 清空（+ 删旧产物对象，跳过 ==StoragePath 者）
7. 重新入队：file_convert（office2pdf + anydoc2md），ResourceLocks = [RESOURCE_DIR(configCode), RESOURCE_FILE(fileCode)]
8. 审计：UpdateBy/UpdateTime；返回 queueCode
```

**关键约束**

| # | 约束 |
|---|---|
| R1 | **不能删源文件**：PDF/图片走透传时 `PreviewPdfPath == StoragePath`，作废产物必须跳过它（否则替换后原文件消失） |
| R2 | **必须入队**：否则 `ConvertStatus='pending'` 永远不前进（原型缺陷） |
| R3 | **必须归档**：企业资料是"只追加版本"语义（旧件物理保留在 `_archive/`，DB 只记元数据） |
| R4 | 归档失败 **不阻塞替换**（记 warning，替换继续），但 `cert_enterprise_file_version` 需与实际对象一致（失败则不写行或标 `Reason` 含失败标记） |
| R5 | 队列创建失败 **不阻塞替换**：返回 `(ok=true, err=null, queueCode=null)`，日志告警（禁止 `(true, 非空err)` 形态） |

### 5.3 版本查看

- UI：文件行 `[版本]` → 抽屉列出 `VersionNumber desc`（版本号/文件名/大小/归档时间/原因 + `[下载]`）
- 下载走通用下载端点（按 `cert_enterprise_file_version.StoragePath`），**同样受白名单校验**

## 六、删除

| 场景 | 行为 |
|---|---|
| 删单个文件 | 归属校验 → 删对象（`StoragePath` + 产物，跳过 `==StoragePath`）→ `IsValid=0`、`IsDeleted=1`、`DeleteTime=now`（**软删**，保留 `cert_enterprise_file_version`） |
| 删整个标准目录（企业×标准×阶段） | 二次确认 → `DeletePrefixAsync('/enterprise-documents/{Ent}/{Std}/{Stage}')` → 企业 config + 文件行软删（`IsValid=0`） |
| 删企业 | 仅下架档案，**不动对象**（对象保留供审计）—— 需产品确认 |
| 恢复 | `IsValid=1`（复用软删行；因 `uk_*` 不含 `IsDeleted`，**禁止**再插同键行） |

> ⛔ **不得**用 `DeletePrefixAsync` 删单文件（前缀粒度会误伤同目录其它文件）。

## 七、队列与资源锁（互斥与取消）

| 项 | 约定 |
|---|---|
| 队列类型 | `QueueType = "file_convert"`（唯一） |
| `ScopeKey` | = **该标准的企业 config.Code**（同标准目录一次只允许一个运行队列） |
| `SourceType` | `upload_task`（四段式）/ `file_replace`（替换）/ `enterprise_upload`（原型写法，**建议统一为前两者**） |
| `SourceId` | `TaskId`（上传）/ `FileCode`（替换） |
| 资源锁 | `RESOURCE_DIR = "cert_standard_directory"`（目录级，`ResourceCode=configCode`）+ `RESOURCE_FILE = "cert_standard_directory_file"`（文件级，`ResourceCode=fileCode`） |
| 互斥检查 | Step1 前置 `GetQueueLockErrorAsync(configCode)`；替换前置 `GetFileLockErrorAsync(fileCode)` ⇒ 命中即拒绝并给出队列号 |
| 取消 | `CancelConvertAsync(queueCode)` → `QueueManager.CancelQueueAsync`；DB 无 `IsValid` 过滤问题（`yzh_queue` 实体特殊处理） |
| 取消后的文件状态 | 队列取消 ⇒ 未完成文件 `IsValid=1`、`ConvertStatus='failed'`、`ConvertMessage='队列已取消'`（`UploadQueueCancelHandler` 已实现，判断条件为 `QueueType='file_convert' AND SourceType='upload_task'`） |
| 前端轮询 | `GET active-queue?directoryCode={configCode}` 5s 轮询（`FindRunningQueueByScopeKeyAsync`），显示进度/完成数/取消入口；`isBusy` 期间禁用写入类操作 |

> ⚠️ `UploadQueueCancelHandler` 的 `SourceType` 判据只覆盖 `upload_task` ⇒ **企业侧替换队列（`file_replace`）取消时不会回写文件状态** ⇒ 若采用 `file_replace`，需同步扩展该判据（P4）。
