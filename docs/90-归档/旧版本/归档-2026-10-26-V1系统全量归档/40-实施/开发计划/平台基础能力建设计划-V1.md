## 〇、结论

这四件事不该由业务端各写一遍，应按「**抽象进框架层、实现按渠道插拔、业务只发消息**」的原则收口。现状是**一条都没有**：

| 能力 | 现状 | 结论 |
|---|---|---|
| 站内消息 | ✅ 已有：`cert_message` 表（94 行）+ `IYzhMessagePusher`（SignalR，按 `UserCode` 路由）+ 消息中心页面 | 作为「通知中台」的第一个通道接入即可 |
| 邮件 | ❌ 全仓 0 处 SMTP/MailKit；`Sys_User.Email` 17 人中 10 人有值，但从未被使用 | P1，最容易落地 |
| 短信 | ❌ 全仓 0 处短信代码；**`Sys_User` 连手机号列都没有**（全库仅 `Email`） | P2，前置 = 加手机号列 + 短信资质报备 |
| 微信登录 | ❌ 无任何 `OpenId`/`UnionId`/OAuth 代码；无 `sys_user_oauth` 表 | P3，需先定接入形态 |
| 支付 | ❌ 无订单/对账/回调代码 | P4，**条件启动**（收费模式未定前不写码） |

工期：P0–P3 ≈ **6.0d**；P4 另计 3–5d/渠道。

## 一、归属原则（先定层，再写码）

| 能力 | 契约（`YZH.Core.Stand`） | 实现 | DI 注册 | 业务侧 |
|---|---|---|---|---|
| 通知渠道（站内/短信/邮件） | `IYzhNotificationSender` + `IYzhSmsProvider` / `IYzhEmailProvider` | `YZH.Core.Api/Services/Notify/*` | `YZH.Core.Web/Extensions/NotificationServiceExtensions` | 只调 `SendAsync`，不碰渠道 SDK |
| 微信身份 | `IExternalIdentityProvider` | `YZH.Core.Api/Services/Auth/WeChatIdentityProvider` | 同上 | `AuthController` 复用现有 JWT 签发 |
| 支付 | `IPaymentProvider`（只含下单/验签/退款原语） | `CertPlatform.Shared/Payment/Providers/*` | `AddCertPlatformSharedServices` | 订单、状态机、对账在业务层 |

**三条硬边界**（与 `IYzhMessagePusher` 的既有口径一致）：

1. **框架只负责「送出去」**：存哪张表、文案怎么写由业务决定；框架不引业务实体。
2. **目标标识一律用 `UserCode`**（`Sys_User.Code`），与 `CreateBy` / `cert_message.UserCode` / `yzh_queue.CreateBy` / SignalR 分组同键 —— 写登录名会**静默**进空分组。
3. **密钥只走配置/环境变量**：`appsettings.json`（已 gitignore）或 `SMS__AccessKeySecret` 形式；缺失即**启动失败**，⛔ 代码内不写任何 AppSecret / SMTP 密码 / 商户私钥。

## 二、统一设计：一个通知中台，四个通道

```text
业务侧（任务分派 / 报告完成 / 验证码 / 专家邀请）
   └→ IYzhNotificationSender.SendAsync(NotificationMessage)
        ├ 模板解析（sys_notification_template：Code→Body/ProviderTemplateId）
        ├ 幂等去重（BizType+BizCode+Channel+Recipient，窗口 10 分钟）
        ├ 频率控制（Redis：验证码 60s / 手机号日上限）
        ├ 落日志（sys_notification_log：状态 / provider id / 错误码，PII 掩码）
        └ 分发
            ├ InApp  → cert_message + IYzhMessagePusher（SignalR，立即）
            ├ Email  → IYzhEmailProvider（同步 10s 超时，失败入 yzh_queue 重试）
            ├ Sms    → IYzhSmsProvider（验证码类同步，通知类入队）
            └ WeChat → 预留（模板消息/订阅消息，本期不实现）
```

**为什么复用 `yzh_queue` 而不新建队列**：它已有 `RetryCount` / `MaxRetryCount` / `BackoffSeconds` / `ErrorType`（retryable｜permanent）与 Worker 回收（`QueueManager:327-394`），通知重试直接用这套语义，避免第二套重试机制。

**统一数据模型**

```csharp
public sealed record NotificationMessage
{
    public NotificationChannel Channel { get; init; }        // InApp / Sms / Email
    public string? UserCode { get; init; }                   // 首选：按用户取联系方式
    public string? Recipient { get; init; }                  // 备选：显式手机号/邮箱（需已授权场景）
    public string TemplateCode { get; init; } = "";
    public IReadOnlyDictionary<string, string> Data { get; init; } = ...;
    public string? Subject { get; init; }                    // 邮件用
    public IReadOnlyList<NotificationAttachment>? Attachments { get; init; } // 邮件用（对象键，不落本地盘）
    public string? BizType { get; init; }                    // 幂等/追溯：如 TaskAssign
    public string? BizCode { get; init; }
}
```

## 三、分期

### P0 — 通知中台骨架（1.5d）

1. 契约：`IYzhNotificationSender`、`NotificationMessage`、`NotificationResult`、`NotificationChannel`。
2. `NotificationService`：模板解析 → 去重 → 频控 → 落 `sys_notification_log` → 分发。
3. 把现有站内消息改为走 InApp 通道（**行为不变**：仍落 `cert_message` + SignalR 推送，`MessageController` 只读接口不动）。
4. 新表：`sys_notification_template`、`sys_notification_log`（列见 §四）。
5. 管理页（可延后到 P1）：模板 CRUD，照抄 `pages/system/user/` 样板，标 `ControllerName = 'System/NotificationTemplate'`。

**验收**：同一 `BizCode` 在 10 分钟内重复调用 → 只产生 1 条站内信 + 1 条日志；日志含渠道、状态、耗时；PII 掩码（`138****1234`）。

### P1 — 邮件（1d）

1. `SmtpEmailProvider`（MailKit）：`Smtp:Host/Port/UseSsl/UserName/Password/From/FromName`；启动自检（连不上**不阻断启动**，但健康检查标红）。
2. 模板：标题/正文支持 `{{占位符}}`，**严格模式**（缺值报错，不允许把 `{{x}}` 原样发出去）。
3. 附件：从 `IObjectStorage` 流式读取（对象键，不落临时盘），复用存储计划的 `OpenReadAsync`。
4. 场景：专家邀请、任务分派通知、密码重置、报告/NC 附件。
5. 运维清单：发信域名 SPF / DKIM、独立子域（如 `mail.`）、退信地址。

**验收**：10 MB PDF 附件发送成功；错误密码时 `sys_notification_log` 记 `AUTH_FAILED` 且不外泄密码；失败重试 3 次后标记 `dead`。

### P2 — 短信（1.5d）

1. **前置数据**：`sys_user` 增 `Phone varchar(20)`（全库当前没有手机号列），迁移脚本 + 唯一性策略（`Phone + IsDeleted`，注意 MySQL 多 NULL 允许）。
2. `AliyunSmsProvider`（Dysmsapi，RPC 签名）为默认；`ISmsProvider` 预留腾讯云实现。
3. 模板：`sys_notification_template.ProviderTemplateId` 存**已报备**的模板 ID；签名存 `Sms:SignName`。
4. 场景：登录验证码（可选）、改密、绑定手机、任务提醒。
5. 频控：同号 60s / 次、10 次/日；验证码 5 分钟有效、错误 5 次锁定 15 分钟（Redis）。

**验收**：60s 内二次请求被拒且提示不含内部细节；模板 ID 未配置时启动自检报错；日志中手机号一律掩码。

### P3 — 微信登录（2d）

1. **形态先定**（决策 D1）：PC 后台推荐**开放平台扫码登录**（`qrconnect`）；若后续做移动端/公众号，再加 `snsapi_userinfo`；小程序走 `code2session`。
2. 新表 `sys_user_oauth`：`Code / UserCode / Provider / OpenId / UnionId / NickName / AvatarUrl / BindTime / LastLoginTime`，唯一索引 `(Provider, OpenId)`。
3. 流程：`state`（Redis，5 分钟、一次性）→ `code` 换 token → 拉 userinfo → 查绑定
   - 已绑定 → 复用 `JwtHelper` 签发，与账号密码登录同一套 claim；
   - 未绑定 → **不自动注册**，跳「登录后绑定」（认证平台主体可信，自动注册会绕过审核）；绑定需密码或短信二次验证。
4. 头像外链**转存对象存储**（微信头像 URL 会过期，直接入库会在几个月后全站裂图）。
5. 解绑后立即失效：`sys_user_oauth.IsValid=0`，登录时校验。

**验收**：`state` 重放/过期被拒；同一 `OpenId` 不能绑两个账号；解绑后微信登录返回明确业务错误；登录成功页能拿到与账密登录等价的 JWT。

### P4 — 支付（3–5d / 渠道，条件启动）

**启动前置**（缺一不做）：收费模式与开票/退款规则已定；商户号/应用已备案；财务确认对账口径。

1. 表：`cert_payment_order`（`Code` 即 `OutTradeNo`、`AmountFen int`、`Channel`、`Status`、`TransactionId`、`PaidTime`）、`cert_payment_notify_log`、`cert_payment_refund`。
2. 微信支付 V3（平台证书/公钥模式）+ 支付宝（RSA2），实现 `IPaymentProvider`。
3. 回调：**验签 → 验金额 → 幂等（`OutTradeNo` 唯一）→ 状态机推进**，四步缺一不可；回调原文先落 `cert_payment_notify_log` 再处理。
4. 对账：每日拉账单比对，差异进运维视图；**不对账不上线**。

**验收**：同一回调重放 3 次只入账 1 次；金额与订单不符 → 拒绝 + 告警；退款重复请求幂等；账单差异报告可导出。

## 四、数据模型（新表 / 新列）

| 对象 | 关键列 | 铁律合规点 |
|---|---|---|
| `sys_notification_template` | `Code`(业务键)、`Channel`、`ProviderTemplateId`、`Title`、`Body`、`IsValid`、`Sort` | 无 `Enable`；`Code` 定位；软删 `IsDeleted` |
| `sys_notification_log` | `Code`、`Channel`、`TemplateCode`、`UserCode`、`RecipientMasked`、`BizType`、`BizCode`、`Status`、`ProviderMessageId`、`ErrorCode`、`RetryCount`、`SendTime` | `CreateBy`=UserCode；时间 `DateTime.Now` |
| `sys_user_oauth` | `Code`、`UserCode`、`Provider`、`OpenId`、`UnionId`、`NickName`、`AvatarUrl`、`BindTime`、`LastLoginTime`、`IsValid` | 唯一 `(Provider, OpenId)`；`UserCode` 外键语义 |
| `sys_user.Phone`（新列） | `varchar(20) NULL` | 与 `Email` 同风格；索引按需 |
| `cert_payment_order` | `Code`、`BizType`、`BizCode`、`AmountFen`、`Channel`、`Status`、`TransactionId`、`PaidTime` | 金额存**分**（int），不存 decimal 浮点；`Code` = `OutTradeNo` |

建表统一 `COLLATE=utf8mb4_general_ci`；脚本进 `scripts/db/`，命名 `yyyyMMdd_xxx_V1.sql`。

## 五、安全与合规

| # | 事项 | 要求 |
|---|---|---|
| 1 | 密钥 | 只走配置/环境变量；启动缺失即失败；⛔ 不入库、不入仓、不进日志 |
| 2 | PII | 手机号/邮箱在日志、列表、导出中一律掩码；表列可评评估加密（本期先掩码） |
| 3 | 验证码 | 一次性、5 分钟、错误计数、同号频控；验证码**不落日志** |
| 4 | 微信绑定 | `state` 防 CSRF、一次性；绑定/解绑需二次验证；不自动注册 |
| 5 | 支付 | 回调验签 + 金额校验 + 幂等 + 对账；私钥仅服务器持有；回调日志保留 ≥180 天 |
| 6 | 邮件 | 发信域名 SPF/DKIM；退订/频率；附件不含敏感信息（按业务模板控制） |
| 7 | 短信资质 | 签名与模板需企业资质报备（1–3 工作日），**提前启动**，否则代码就绪也发不出 |
