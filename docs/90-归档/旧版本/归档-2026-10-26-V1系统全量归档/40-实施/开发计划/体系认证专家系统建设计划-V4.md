## 第一篇 产品定义

### 1.1 我们做的是什么

> **一个面向审核专家的收费服务平台。** 专家因为我们的服务能解决他的核心痛点而**自愿付费**。

| 维度 | 定义 |
|---|---|
| 产品形态 | SaaS，**注册制** |
| 付费主体 | 审核专家个人（不是认证机构） |
| 付费动因 | 服务解决核心痛点 → 自愿付费 |
| 核心卖点 | **一键 NC** ＋ **一键自动出报告** |
| 交付方式 | 注册 → 立即可用，无需审批、无需后台开通 |

### 1.2 为什么必须"注册 + 选机构"（产品逻辑，不是技术选择）

我们**不可能一次性建成所有标准、所有规则、所有报表系统**。这些能力是**逐个机构、逐个标准**积累起来的，目前只存在于后台配置里。

因此产品设计只能是：

```
专家注册
  └─ 选择一个认证机构（该机构在后台已配置好能力）
      └─ 继承该机构的：
          ├─ 标准集（cert_org_standard）
          ├─ 阶段集（cert_org_stage）
          ├─ NC 检查规则（cert_validation_rule，按 标准+阶段+条款+工作流 DAG）
          ├─ 报告模板与章节（cert_report_template + 章节配置）
          └─ 文档提取规则 / Prompt / 技能
              ↓
         专家在这个"能力边界"内干活：
         建企业 → 分配标准/阶段 → 传文档 → 【一键 NC】→【一键报告】
```

**这就是"只能选后台已定义机构"的真正原因**：选机构 = 选择一套**已经建好的能力**。没建好的机构，选了也没用。

### 1.3 注册约束（硬约束）

| 约束 | 含义 |
|---|---|
| **一次注册只针对一个机构** | 一个账号绑定一个 `CbCode`，能力边界随之确定 |
| 一个机构下可有**多个注册人** | 每人一个独立工作区（VirtualOrg），互不可见 |
| 机构不可切换 | 换机构 = 重新注册（避免能力边界混淆） |

### 1.4 本期边界

> **目前只专注专家系统这一个领域。** 机构版是未来的事（见第二篇）。

## 第二篇 产品族战略与 `cert-share` 分层纪律

### 2.1 两条产品线

| | **专家版（本期）** | **机构版（未来）** |
|---|---|---|
| 主体 | 专家个人 | 体系认证机构 |
| 代码位置 | `cert-auditor` | 新建（如 `cert-org`） |
| 数据库 | `yzh_cert_platform` | **另建一套库**（机构级组织/派单/权限模型不同） |
| 业务逻辑 | 个人空间、自助建企业 | 机构组织架构、统一派单、机构级企业池 |
| 核心能力 | 一键 NC / 一键报告 | **同一套核心** ← 复用点 |

### 2.2 `cert-share` 的战略定位

> 做机构版时，**数据库要重来、业务逻辑要调整**，但**最核心的部分不该重写**。
> `cert-share` 就是把这部分**抽象出来的容器** —— 让两条产品线共用同一套核心，快速并行开发。

```
              ┌─────────────────────────────────────────┐
              │           cert-share（共用核心）          │
              │  API 契约 · 认证 · 业务组件 · 组合式函数   │
              │  ★ 两产品线都依赖，改动需双向兼容          │
              └───────────┬─────────────────┬───────────┘
                          │                 │
          ┌───────────────▼──────┐   ┌──────▼──────────────────┐
          │  cert-auditor（专家版）│   │  cert-org（机构版，未来） │
          │  工作区/注册/收费/配额  │   │  组织架构/派单/机构企业池  │
          └───────────────────────┘   └─────────────────────────┘
                          │                 │
          ┌───────────────▼──────┐   ┌──────▼──────────────────┐
          │   yzh_cert_platform   │   │      另建一套库           │
          └───────────────────────┘   └─────────────────────────┘
```

### 2.3 ★ 分层纪律（判定标准）

**唯一判定问题**：

> **「明天做机构版，这个能力还需要吗？」**
> 需要 → 放 `cert-share`；不需要 → 放 `cert-auditor`。

| 归属 | 内容 | 理由 |
|---|---|---|
| **`cert-share`**（共用核心） | • API 层（认证、企业、标准、阶段、文档、NC、报告、工作流调用）<br>• 数据契约与类型（`types/cert.ts`）<br>• 业务组件（企业选择器、条款树、NC 结果列表、报告编辑器、文档上传）<br>• 组合式函数（轮询、队列监控、文件树、目录 API）<br>• 工具函数（格式化、下载、状态转换） | 两产品线的**核心业务一致** |
| **`cert-auditor`**（专家版专属） | • 注册与工作区（VirtualOrg）<br>• 成员管理<br>• 收费、配额、计费<br>• 页面布局、路由、专家端菜单 | 个人 SaaS 特有 |
| **`cert-org`**（机构版专属，未来） | • 机构组织架构<br>• 统一派单<br>• 机构级企业池与共享 | 机构特有 |

**⚠️ 纪律红线**：
1. 新增**业务能力**（如"报告导出"、"NC 复核"）→ **必须先进 `cert-share`**，专家版与未来机构版同时获得
2. 只有**确认机构版不需要**的东西才写进 `cert-auditor`
3. `cert-share` 的改动必须**同时兼容** admin / auditor（未来 org）三方，禁止为某一端加破坏性参数
4. 禁止在 `cert-auditor` 里复制一份 `cert-share` 已有的实现

## 第四篇 架构设计

### 4.1 三层模型

```
① 认证机构域（后台维护，只读消费）
   cert_certification_body（7 条 active）
   ├─ 作用一：决定工作区可用能力（标准/阶段/规则/报告模板）
   └─ 作用二：作为权限预配的锚点

② 工作区域（= 虚拟机构，注册时自动创建）★ 数据隔离边界
   Sys_Organization（OrgType='VirtualOrg'，OrgName = "姓名（登录名）"）
   ├─ 管理员（注册人，ROLE_AUDIT_CLIENT_ADMIN，默认全权限）
   ├─ 审核员 / 审核组长（工作区内可添加）
   └─ 企业用户（工作区内可添加）

③ 业务数据域（全部以工作区 Code 为隔离键）
   ent_enterprise / ent_enterprise_phase / ent_enterprise_file
   audit_task / wf_execution_task
```

**组织树形态**（推荐方案，D5/D6）：

```
ORG_ROOT_002「认证机构」(CertBody 根)
└─ 5833c904…「河北雄安尚龙认证有限公司」(CertBody)
    ├─ 张三（zhangsan）  (VirtualOrg)  ← 张三注册
    │   ├─ 管理员 / 审核员 / 审核组长（前端按角色合成）
    │   └─ 企业用户
    └─ 李四（lisi）      (VirtualOrg)  ← 李四注册
```

### 4.2 ★ 企业档案「非唯一」——必须改约束

**需求**：同一真实企业可出现在多个工作区（初审张三、复审李四）。

**现状（`SHOW CREATE TABLE ent_enterprise`）**：

```sql
UNIQUE KEY `uk_enterprise_no` (`EnterpriseNo`)    -- ⛔ 全局唯一
UNIQUE KEY `uk_credit_code`   (`CreditCode`)      -- ⛔ 全局唯一
```

→ 李四建第二份档案会**报重复键失败**。**核心场景跑不通。**

**迁移（`scripts/db/`）**：

```sql
ALTER TABLE `ent_enterprise`
  DROP INDEX `uk_enterprise_no`,
  DROP INDEX `uk_credit_code`,
  ADD UNIQUE KEY `uk_org_ent_no` (`OrgCode`, `EnterpriseNo`),
  ADD UNIQUE KEY `uk_org_credit` (`OrgCode`, `CreditCode`);
```

| 场景 | 结果 |
|---|---|
| 张三工作区建"企业A"（credit=X） | ✅ |
| 李四工作区建"企业A"（credit=X） | ✅ 允许 |
| 张三工作区再建一份（credit=X） | ❌ 拦截（工作区内不重复） |

> ⚠️ 这**推翻了审核员端功能设计-V1 §2.2 决策 D1** 中"全局唯一约束维持不变"的表述——该表述与其自身"同一企业换审核员=新建独立档案"**自相矛盾**，需回写修订（D8）。

### 4.3 ★ 权限机制：后台预配 → 注册只绑角色 → 自动继承

```
【后台一次性预配】Sys_Menu（auditor 菜单）+ Sys_RoleMenu + sys_api + sys_role_api
        ↓
【注册只做一步】Sys_RoleUser（用户 → ROLE_AUDIT_CLIENT_ADMIN）
        ↓
【登录后自动继承】菜单树 = Sys_RoleMenu ⋈ Sys_Menu；接口通行 = PermissionFilter 查 sys_role_api
```

**实测覆盖度**：

| 项 | 现状 | 缺口 |
|---|---|---|
| `sys_api` | 397 条 | — |
| `sys_role_api`（该角色） | **87 条，全为 `Foundation/*` 只读配置类** | ❌ 业务接口 0 条 |
| `Sys_RoleMenu`（该角色） | **0 条** | ❌ 菜单权限完全未配 |
| `Sys_Menu` | 26 条全管理端 | ❌ 无 auditor 菜单 |

> 那 87 个 `Foundation/*` 恰好是"专家只读消费后台配置"所需能力（读标准、条款、机构、阶段、目录模板），**可直接复用**。

**⚠️ 维护铁律**：

```
ApiCode = SHA256("{HTTP方法}|{控制器名}|{动作名小写}")     // 源码 ApiScanner.cs:326-331，已实测验证
```

| 变更 | ApiCode | 后果 |
|---|---|---|
| 改**路由前缀** | 不变 | ✅ 安全 |
| 改**控制器名**或**动作名** | **变** | ⛔ 角色-接口关联**静默断裂**，必须重跑 ApiSync 并重关联 |
| 新增接口 | 新增 | 需补 `sys_role_api`，否则非超管 **403** |

### 4.4 注册流程（★ 阶段 1 交付）

### 4.6 数据模型

**新增：`cert_auditor_org`（工作区 Attach 表）**

```sql
CREATE TABLE `cert_auditor_org` (
  `Id`             bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `Code`           varchar(50)  NOT NULL COMMENT '工作区编码 = Sys_Organization.Code',
  `CbCode`         varchar(50)  NOT NULL COMMENT '挂靠认证机构 Code = cert_certification_body.Code',
  `OrgName`        varchar(200) NOT NULL COMMENT '工作区名称（= 姓名（登录名））',
  `OwnerUserCode`  varchar(50)  NOT NULL COMMENT '所有者（注册人）UserCode',
  `MaxUsers`       int          NOT NULL DEFAULT 5   COMMENT '成员上限（继承机构配额）',
  `MaxEnterprises` int          NOT NULL DEFAULT 50  COMMENT '企业上限（继承机构配额）',
  `ExpireDate`     datetime     DEFAULT NULL COMMENT '到期时间（继承机构）',
  `Status`         varchar(20)  NOT NULL DEFAULT 'active' COMMENT 'active / frozen / closed',
  `Remark`         varchar(500) DEFAULT NULL,
  `IsValid`        tinyint(1)   NOT NULL DEFAULT 1,
  `IsDeleted`      tinyint(1)   NOT NULL DEFAULT 0,
  `CreateBy`       varchar(50)  DEFAULT NULL,
  `CreateTime`     datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `UpdateBy`       varchar(50)  DEFAULT NULL,
  `UpdateTime`     datetime     DEFAULT NULL,
  `DeleteBy`       varchar(50)  DEFAULT NULL,
  `DeleteTime`     datetime     DEFAULT NULL,
  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_code` (`Code`),
  KEY `idx_cb_code` (`CbCode`),
  KEY `idx_owner` (`OwnerUserCode`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='审核员工作区（虚拟机构）';
```
