## 2. 直接回答：为什么两个页面的文件"对不上"

### 2.1 我按你给的参数实调了两个端点（可复现）

```
GET /api/Admin/Workflow/StandardDirectory/stage-files/b27945be5e1b44f28bcf8fc19852d92d
  → success=true，共 23 个文件
      3制度文件（可根据企业实际修改）  1 个（受控文件清单-三阶.xls）
      检验作业指导书                   7 个
      制度文件                        15 个
GET /api/Admin/Workflow/StandardDirectory/folders/4c9e5101d9d741e8b4193613bb83a012/files
  → 就是上面「制度文件」那 15 个，逐条一致（Code/Id 全同）
```

DB 复算同口径：`cert_standard_directory_file WHERE ConfigCode=b27945be… GROUP BY FolderCode`  
→ `4c9e5101… = 15`、`781b4dc6… = 7`、`233bc384… = 1`；`IsValid=0` 的文件 **0 行**；根级孤儿文件 **0 行**。

**结论：这两个入口的数据本身不矛盾，只是"切片"不同**：

- `doc-extraction-rule` 渲染的是**整个阶段的树**（一次 23 个，横向铺到 3 个文件夹）；
- `directory-manager` 渲染的是**你当前所在的那一层**（进到「制度文件」就只有这 15 个，回到根就只剩 1 个文件夹 + 根级文件）。

### 2.2 另外两个"看起来像 bug 但其实正常"的点

1. `active-queue` 返回 `data: null` ⇒ 队列端点，无运行中队列时本就无 `data`。
2. 该 ConfigCode 下有 **2 个 `IsValid=0` 的文件夹**（`33`、`33344`）。它们**在两个页面的树里都不显示**（都过滤 `IsValid==1`），  
   所以不会造成差异；但如果哪天有页面用 `includeDisabled: true` 渲染，就会立刻"多出两个文件夹"。

### 2.3 什么情况下**真的会**看出两批文件（这些才是要修的）

| 触发条件                                                                                    | 现象                                      | 为什么                                                        |
| --------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------- |
| 文件挂在**保留段目录**（`pdf` / `markdown` / `editable` / `_template` / `_preview` / `_archive`）下 | 树里看不到，`folders/{该目录}/files` 却列得出来       | `stage-files` 剔除保留段；`GetFilesAsync` **不剔除**                |
| 文件夹的 `ParentCode` 指向**已禁用/不存在的父**（断链）                                                   | 树里整棵子树消失，但 `folders-flat` / `files` 仍能查 | `stage-files` 只从"根可达"的文件夹开始递归                              |
| 文件 `IsValid=0` 但有对象（`StoragePath != ''`）                                                | 专家端**显示**、后台**不显示**                     | auditor 判据带 `\|\| StoragePath != ''`；admin 只认 `IsValid==1` |
| 文件 `FolderCode` 指向**别的 ConfigCode** 的文件夹（历史脏数据）                                         | `folders/{code}/files` 会把它带出来           | 该查询**缺 `ConfigCode` 过滤**                                   |
| 根级文件 `IsDeleted=0` 但 `IsValid=0`                                                        | `root-files` 显示、`stage-files` 不显示       | 视图不过滤 `IsValid`                                            |

> 想确认你当时具体看到的是哪一类，跑这一条即可（把 `b27945be…` 换成你当时的 ConfigCode）：
>
> ```sql
> SELECT FolderCode, IsValid, IsDeleted, COUNT(*) c
> FROM cert_standard_directory_file
> WHERE ConfigCode='b27945be5e1b44f28bcf8fc19852d92d'
> GROUP BY FolderCode, IsValid, IsDeleted;
> ```
>
> 再对照 `v_standard_directory_root_files`（不过滤 `IsValid`）。

### 2.4 工作流层已经「实锤」的 3 处不一致（可执行复现）

| 现象                                                | 复现                                                                                                                                                              | 后果                                                                                                        |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **两个判空 skill 对同一个值给出相反结论**                        | 字段值 = `"-"`：<br />`is_empty.Judge("-")` → `result=false`（**非空**）<br />`EmptyJudge.IsBlankText("-")` → `true` ⇒ `is_field_empty` → `state=is_empty`（**空**）       | 规则作者用哪个判空节点，结论不同；`branch` 分流走错边。`EmptyJudgeTests` 已断言 `-`/`N/A`/`待填写` 是空，但 `IsEmptySkill.Judge` **无任何测试** |
| **两条「取数→判空」链路行为不同**                               | `docField → is_empty`：`NodeExecutor:470` 刻意把占位符输出成 `null` ⇒ 判空正确<br />`get_field → is_empty`：`GetFieldSkill` 命中时透出 `ExtractedValue` **原值**（可能 `-`）⇒ 判空**误判为非空** | 同一条规则，换成 skill 版节点就「没检出问题」，**且全程不报错**                                                                     |
| **`is_std_file_missing` 用 `FileSize > 0` 判「已上传」** | `FileSize` 是 `long?`（可空）。真上传但 `FileSize` 未回填的行 ⇒ 判「必需文件缺失」                                                                                                      | **产生假 NC 不符合项**。权威口径其实是 `IsValid==1 ∧ StoragePath != ''`（`EnterpriseFileService.IsLive:1111`）             |


> 这三处正是「错误后非常难发现」的典型：**没有异常、没有日志、没有红字，只是结论悄悄不同。**
