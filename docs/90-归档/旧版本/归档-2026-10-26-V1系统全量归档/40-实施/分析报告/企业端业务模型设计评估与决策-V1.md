> 结论来源：联网核实的体系认证规范（ISO 9001 §7.5、CNAS-CC01 一体化审核应用、NC 分级三分法）
> + 对 `yzh_cert_platform` 13 张设计相关表的实测列结构。

## 一、已核实的业务规范（4 条硬事实）

### 1.1 认证流程（通用体系认证）

```
体系建立 → 试运行（≥3 个月，须有内审 + 管理评审记录）→ 认证申请
  → 一阶段审核（文件审核：查体系文件齐套性）
  → 二阶段审核（现场审核）
  → 不符合项整改 → 认证决定 → 发证
  → 监督审核（每年 1 次）→ 再认证（3 年周期）
```

**对本设计的含义**：「一阶段审核 = 文件齐套性检查」正是用户第 2 点描述的能力，**业务位置正确**。

### 1.2 文件四层级（ISO 9001 §7.5 文件化信息）

| 层级 | 内容 |
|---|---|
| 一级 | 质量手册 |
| 二级 | 程序文件（**8 个强制程序**：文件控制 / 记录控制 / 内部审核 / 不合格品控制 / 纠正措施 / 风险评估 / 外部提供控制 / 客户沟通） |
| 三级 | 作业指导书 |
| 四级 | 记录与表单 |

**强制必查记录**：内审、管理评审、不合格品处理、纠正措施。

**对本设计的含义**：单标准下四层级是**固定的**；多标准下是**各标准四层级的并集去重**。
→ 「缺失文档分析」的判据来源 = **要求侧（标准+阶段）展开后的清单**，不是人工列表。

### 1.3 NC 分级（三分法）

| 等级 | 判据 |
|---|---|
| 严重不符合 major | 系统性失效 / 区域性失效 / 明知故犯 / 同一部门多条同款 / 多部门同款 / 严重质量问题未解决 |
| 一般不符合 minor | 个别、孤立、偶发、易关闭 |
| 观察项 observation | 有苗头未构成不符合 / 已构成但极轻微 / 可能不符合但无客观证据 |

**★ 关键：体系审核按「是否系统性」分级，不按「后果严重性」分级。**

**对本设计的含义**：`Severity` 是**判定规则的产物**，不是人工填的 → 输入是 `条款 + 证据 + 频次`。
现有 `audit_nonconformity` 的 `SourceType(enum auto_rule|manual)` + `RuleCode` + `ClauseCode` 已能承载，**但缺 StandardCode**（见 §三.2）。

### 1.4 多标准一体化（IMS）

- 各标准共用 **HLS 高阶结构**（相同章节框架 / 管理原则 / 过程方法）→ 可融合为一个体系
- **审核时间起始值 = 各标准单独审核时间之和，最大可减少 20%**
- **审核组须覆盖所有标准要求**
- ★★ **审核报告需追溯每个发现至对应标准，并评估不符合项对其他标准的影响**
- 证书模式：**「一次审核、多张证书」与「一次审核、一张证书」两种都存在**，趋势向一张整合证书过渡，长期并存

## 二、对提案四点的裁定

### 2.1 第 1 点「认证阶段管理（左企业 / 右 阶段+标准 树表）」→ **方向对，但提案自相矛盾**

- 「一个企业在一个认证阶段可同时针对多个标准做统一认证」→ **符合 IMS 事实，正确**。
- ⚠️ 但右侧是「阶段 + 标准的树表」→ 若树里仍挂「标准」层，等于把标准当作**用户操作维度**；
  而第 4 点又说「标准这一栏被取消」→ **第 1 点与第 4 点冲突**。

**裁定**：树**只到阶段**。标准作为**阶段节点上的信息条**（如「覆盖标准：ISO 9001 / ISO 14001」）
和**表格里的列/标签**，**不作为树的层级**。

### 2.2 第 2 点「企业文档管理」→ **方向对，但数据模型上有一处必须现在决定**

- 「上传后针对该阶段下所有标准格式文档进行校验」→ 正确，即 IMS 的**文件齐套性检查**。
- 「按文档提取规则电子化归档」→ 正确，对应一阶段审核的文件审核。
- ★ **最大的数据模型问题**：现有 `cert_standard_directory_folder` / `cert_standard_directory_file`
  是**「要求定义」与「上传实例」混在同一张表**：

  | 类别 | 现有列 |
  |---|---|
  | 要求定义 | `FilePattern` `IsRequired` `MaxFileSizeMB` `ExtractionEnabled` `ExtractionRules` `PreCheckRequired` `ComplianceRequired` `FolderName` `Depth` `SortOrder` |
  | 上传实例 | `TaskId` `UploadStatus` `StoragePath` `FullPath` `ConvertStatus` `ConvertMessage` `ConvertDate` `PreviewPdfPath` `MarkdownPath` `MarkdownStatus` `MarkdownDate` `FileName` `FileSize` |

  **一张表既当模板又当实例 → 多企业复用时必然互相污染。**

**裁定：拆成两组表。**
- **要求侧**（按 `标准 + 阶段` 定义，全企业共用）：目录文件夹 / 文件要求 / 提取规则
- **实例侧**（按 `企业 + 阶段` 落库）：企业文档目录 / 企业文档 / 上传记录
- 实例侧**不挂 StandardCode**，只挂 `EnterpriseCode + PhaseCode`；
  但**每个文件条目保留「来源标准」**（IMS 要求可追溯），该值**来自要求侧的展开结果**。

### 2.3 第 3 点「任务管理（左 企业+阶段 / 右 任务列表）」→ **正确，与 IMS 事实一致**

- 「不再区分标准」→ 正确。IMS 就是「一次审核」，任务按 `企业 + 阶段` 建。
- ★ **但：任务不区分标准 ≠ 结果不区分标准。** IMS 明文要求「报告需追溯每个发现至对应标准」。

**裁定**：`audit_task` 保持无 `StandardCode`（粒度正确）；
`audit_nonconformity` **必须能反查标准** → 见 §四 Q2。

### 2.4 第 4 点「为什么取消标准这一栏」→ **理由成立，但要精确表述**

| 用户原话 | 裁定 |
|---|---|
| 「多标准认证时，需上传的资料不用再挂接到标准下」 | ✅ **成立**（IMS 融合为一个体系，文件是体系的文件） |
| 「NC 检查任务和报告任务也不区分标准」 | ⚠️ **任务粒度成立，结果粒度不成立** |

**★ 精确表述：标准从「用户操作维度」降级为「系统内部维度」。**

- **用户侧**：`企业 → 阶段`（唯一操作单位）
- **系统侧**：标准仍然存在，作用在三处
  1. **文件要求展开的来源**
  2. **NC / 发现的归属**（可追溯，IMS 强制）
  3. **报告章节与证书数量**

## 三、DB 实测出的硬约束（决定能不能开工）

核对了 13 张设计相关表的真实列结构，得到三条：

### 3.1 需求侧全部按 `(StandardCode, PhaseCode)` 建键 —— **保留标准是对的**

`cert_validation_rule` / `cert_report_template` / `cert_standard_phase_config` /
`cert_standard_directory_config` / `cert_file_requirement` —— 全部带 `StandardCode` + `PhaseCode`。

### 3.2 执行侧全部**没有** `StandardCode` —— **「无标准」也对，但要补「可追溯」**

| 表 | 关键列 | 是否缺标准归属 |
|---|---|---|
| `audit_task` | `OrgCode` `PhaseCode` `TaskNumber` `AuditorId` | 粒度正确，**不需要** |
| `audit_nonconformity` | `TaskCode` `ClauseCode` `RuleCode` `Severity` `SourceType` | ⚠️ **需要**（见 §四 Q2） |
| `audit_checklist_item` | `TaskCode` `ClauseCode` `Conformity` | 可经 `ClauseCode` 推 |
| `audit_project` | `ApplicationCode` `CurrentPhase` | 无企业维度 ⚠️ |

### 3.3 `cert_application` 装不下多标准 —— **结构性缺口**

`cert_application` 有 `StandardCode`（**单值**）+ `EnterpriseCode` → **多标准申请装不下**。
若「一个企业一个阶段多标准」成立，`cert_application` 要么改成一对多，要么被 `(企业, 阶段)` 取代。

## 五、现在做什么 / 什么延后 / 为什么

### 现在做（本周，每项 <1 天且产生复利）

1. **把「企业 + 阶段」落成一张关联表**（暂名 `cert_enterprise_stage`）
   - 字段：`EnterpriseCode + PhaseCode + 覆盖标准(JSON) + 状态`
   - 理由：这是第 1/2/3 三个页面**共用的左侧树数据源**，没有它三个页面都起不来
   - 覆盖标准来源：从 `cert_org_standard`（机构配了哪些标准）× 该企业所选 → **第一期手工勾选，不自动推导**
2. **拆 `cert_standard_directory_folder` / `_file`**：要求侧 vs 实例侧
   - 理由：**0 行时拆 = 改 DDL；有数据后拆 = 数据迁移**，成本差 10 倍
3. **给 `audit_nonconformity` 加 `StandardCode`**（可空）
   - 理由：加列是 5 分钟的事；等报告生成时才发现就是返工

### 延后

| 项 | 为什么延后 |
|---|---|
| `cert_application` 重构 | 本期链路用不到（0 行） |
| 一体化审核时间自动计算（-20% 算法） | 不产生任何界面价值 |
| 多标准文件的「并集去重」智能合并 | 第一期手工勾选覆盖标准即可 |
| 证书自动生成 | 先出一张整合证书 |
| 多标准「不符合项对其他标准的影响」评估 | 规则库为空，无规则可评估 |

### 为什么这么排

- 三个页面**共用同一个左侧树**（企业 + 阶段）→ 这张表不落地，三个页面都得造临时数据
  → **违反用户「不要为跑通验证临时造数据」的原则**
- 拆表和加列**都是 0 行时的操作**，成本最低；一旦有业务数据，成本翻 10 倍
- **报告生成是 10/15 必达**，NC 的标准归属直接卡在它前面

# 第二轮：五个关键问题的逐条答复（2026-09-25）

## 八、第一问：一个企业在一个阶段下能否多标准认证？

**能。** 这在规范里叫 **一体化审核（整合管理体系的认证审核）**。

> 定义：「一个客户已将两个或两个以上管理体系标准要求的应用**整合在一个单一的管理体系中**，并按照一个以上标准接受审核。」
> —— GB/T 27021.1-2017 / ISO 9001:2015 标准解读

**5 个前提条件**（缺一不可）：

1. **企业侧**：多标准的应用必须已**整合在一个单一管理体系**中，**不是三个体系的简单相加**
2. **机构侧**：认证机构须在 **审核方案策划 / 审核组能力评估 / 管理体系有效性评价** 三方面采取**整合视角**
3. **审核组**：须**覆盖所有标准要求**（"三项全能"一体化审核员）
4. **审核时间**：起始值 = 各标准单独审核时间之和，**最大可减少 20%**
5. **标准间兼容性**：需共享 HLS 高阶结构 → 9001/14001/45001 是经典组合；27001/27017/27018 亦可

**证书模式**：**「一次审核、多张证书」与「一次审核、一张证书」两种都存在**，趋势向一张整合证书过渡，**长期并存**。

### ⚠️ 但必须先澄清一件事：你的「阶段」有两个不同概念，库里状态不一样

| 概念 | 表 | 现状 | 含义 |
|---|---|---|---|
| **认证阶段** | `cert_cert_stage` | **1 行**：`jd01 / 初审 / process` | 初审 / 监督审核 / 再认证 |
| **审核阶段** | `cert_phase_definition` | **0 行（空表）** | 一阶段审核 / 二阶段审核 |

**你说「一个企业在一个阶段下」= 认证阶段（初审）**。
但 `cert_org_stage`（机构-阶段关联）只有 1 行且 **`StandardCode` 为 NULL** → **"机构-阶段"到底要不要绑标准，当时就没定**。

**→ 这个歧义必须先裁决，否则 `cert_enterprise_stage` 不知道该挂哪个「阶段」。**

## 九、第二问：多标准一份报告，内容怎么定义？

### 9.1 核心答案：**报告是「一次审核」的记载，不是「一个标准」的记载**

规范（CCAA 审核概论 / GB/T 19011 体系）规定的审核报告固定内容项，**逐项对多标准的处理**：

| 报告内容项 | 多标准时怎么写 |
|---|---|
| 审核目标 | 不变 |
| **审核范围**（组织单元、职能、过程、活动） | 不变 —— **与标准无关** |
| 审核委托方 | 不变 |
| 审核组和受审核方参与人员 | 不变（但审核组须覆盖所有标准能力） |
| 审核活动的日期和地点 | 不变 |
| **★ 审核准则** | **这一栏写多个标准**：ISO 9001:2015、ISO 14001:2015、ISO 45001:2018 |
| **★ 审核发现和相关证据** | **每条发现标注它涉及哪个/哪些标准的哪条条款** |
| **★ 审核结论** | **按标准分别给结论**（9001 推荐 / 14001 推荐 / 45001 不推荐） |
| 关于对审核准则遵守程度的陈述 | 同上，按标准分述 |

可选/引用项：审核计划、审核过程综述、未覆盖到的区域、未解决的分歧意见、改进机会、良好实践、后续行动计划、保密声明、分发清单。

### 9.2 ★★ 最重要的结论：这不是两种方案，是**同一批数据的两个视图**

```
一次审核  →  一套原始数据（发现 / 证据 / NC / 检查表）
                    │
        ┌───────────┴───────────┐
   按「标准」组织            按「一次审核」组织
        │                        │
   每个标准一份              一份一体化审核报告
   「标准符合性报告」        （审核准则写多个标准）
```

**→ 所以你说的「多标准生成多个报告」和「多标准生成一个报告」不冲突。系统只存一份原始数据，报告模板决定怎么切。**

**架构含义**：`cert_report_template` 现在按 `(StandardCode, PhaseCode)` 建键 —— **要加一个「报告类型 / 切分维度」字段**，而**不是建两套数据**。
- 类型 1：标准符合性报告（切分维度 = 标准）
- 类型 2：一体化审核报告（切分维度 = 一次审核，准则多值）

### 9.3 前置条件（不做这个，报告一定出不来）

`audit_nonconformity` / `audit_checklist_item` **必须能反查标准**（IMS 明文要求「报告需追溯每个发现至对应标准」）。
现有两表都**没有 `StandardCode`** → 见第一轮 §四 问题 B。

## 十、第三问：按阶段管理一套企业资料，合理吗？

### 10.1 **合理。** 但你说的「资料不符合认证要求需要重新替换」是**两种完全不同的业务**

规范把「审核后续活动」明确分为：**受审核方纠正/纠正措施/改进措施的确定与实施 → 实施情况的报告 → 审核委托方的评审与验证**。

**验证方式三分（规范原文）**：

| 验证方式 | 适用 | 系统含义 |
|---|---|---|
| **现场验证** | **严重不符合**（major） | 需**重新安排现场审核** |
| **书面验证** | **一般不符合**（minor） | 就是**企业重新提交资料** → 你说的"重新替换" |
| **随后审核时验证** | 影响极其轻微 / 需较长时间 | 挂到下次审核 |

### 10.2 ★ 必须区分两个"替换"场景

| | **场景 1：文件预审不符合** | **场景 2：审核不符合项整改** |
|---|---|---|
| 业务位置 | **一阶段审核**（文件齐套性/内容检查） | **二阶段审核后**（NC 整改） |
| 触发 | 文件缺失 / 格式不符 / 内容不达标 | NC 单 |
| 企业动作 | **替换文件** | 提交**纠正措施 + 证据** |
| 验证人 | 文件预审（可自动 + 人工） | **审核员**（现场/书面） |
| 留痕要求 | 版本替换记录 | NC 关闭闭环（`audit_rectification`） |
| 对应表 | 实例侧文档表（需加版本） | `audit_nonconformity` + `audit_rectification` |

**→ 如果只做一个"替换"按钮，会把两者混在一起**：文件预审的替换是**覆盖**，NC 整改的提交是**闭环证据**（不能覆盖，是追加）。

### 10.3 实例侧文档表必须补的字段

- **版本**：`Version` / `IsCurrent`（当前有效版本唯一）—— 现在是**完全覆盖式**，无版本
- **替换留痕**：`ReplacedBy` / `ReplaceReason` —— 认证审核是**证据链**，不能覆盖丢失
- **校验状态**：`CheckStatus` / `CheckResult`（齐套性 / 内容符合性）
- **整改关联**：`RectificationCode`（若因 NC 替换）

**规范对纠正措施验证的 6 个关注点**（可作为校验规则）：原因分析是否准确 / 措施计划是否切实可行 / 是否按规定时间实施 / 自我验证是否有效 / 是否引起文件更改 / 能否防止同类不符合再次发生。

## 十一、第四问：任务体系的建立，是否合理？

**合理，但必须分两类，不能塞一张表。**

| 类别 | 本质 | 特征 | 现有表 |
|---|---|---|---|
| **A. 审核任务** | **业务对象**（人做的） | 有审核员、有排期、有现场、有审核范围 | `audit_task` |
| **B. 异步作业** | **系统作业**（机器做的） | 有队列、有进度、有耗时、有失败重试 | `cert_upload_task` |

`cert_upload_task` 是 B 类（`TotalFiles`/`SuccessCount`/`Status`/`ExpireTime`）；`audit_task` 是 A 类。

### 11.1 A 类（`audit_task`）要补的

- **`TaskType`**：现有表**没有任务类型字段** → 无法区分 文件预审 / 现场审核 / 监督审核 / 再认证 / 整改验证
- 现状：`OrgCode` + `PhaseCode` + `TaskNumber` + `AuditorId` + `PlannedDate` + `AuditScope`，**无 `StandardCode`（正确）**

### 11.2 B 类要补的

你提的「**NC 检查任务**」和「**生成报告任务**」**都是 B 类**，不是审核任务 —— 它们是"点了按钮后机器跑"的异步作业。
→ 需要一张作业表（或复用 `cert_upload_task` 的模式），字段：`JobType` / `RefCode` / `Status` / `Progress` / `StartedAt` / `FinishedAt` / `Error`

**→ 结论：`audit_task` 保留并补 `TaskType`；NC 检查/报告生成不要塞进 `audit_task`。**

### 12.2 ★★★ 最硬的一条：`cert_iso_clause` 标准条款库是空的 —— 这一条卡死两条链

- **实测**：ISO 9001 在库里只有 **1 行**「`2025-01 前言`」，其余 10 行全是 `AUTOTEST-*` 测试垃圾。**真实的 ISO 9001:2015 条款树（4~10 章含子条款）根本不在库里。**
- **而条款是所有下游配置的挂载点**：
  - `cert_validation_rule.ClauseCode` → NC 规则挂条款
  - `audit_checklist_item.ClauseCode` → 检查表挂条款
  - `cert_report_template.SectionConfig` → 报告章节挂条款
  - `cert_standard_phase_config.RequiredClauses` → 必查条款挂条款
- **后果**：**条款库空 → NC 规则无法落位 → 检查表无法生成 → 报告章节无法落位** → 专家端的 **NC 链 + 报告链全部悬空**。
- **这就是「即使我们尽力去完善专家系统，也没有后台能力支撑」的最硬证据。**
- **好消息**：录入工具**已经做完了**（后台 `ISO 标准管理` 页）→ **只需录数据，不需写代码**。

### 12.3 三处真实错位（需补正）

| # | 错位 | 证据 | 补正 |
|---|---|---|---|
| **1** | 后台把「机构-标准-阶段」当**业务主线**，但它是**授权** | `cert_org_stage` 仅 1 行且 `StandardCode` **NULL** → 语义当时就没定 | 明确：`cert_org_standard` = 机构**获授权可做的标准**；`cert_org_stage` = 机构**获授权可做的认证阶段**（**不绑标准**，`StandardCode` 废弃）；企业级"覆盖标准" = `cert_org_standard` ∩ 企业所选 |
| **2** | `cert_standard_directory_*` 把**要求**和**实例**混表 | 同表既有 `FilePattern/IsRequired/ExtractionRules`，又有 `TaskId/UploadStatus/StoragePath/MarkdownPath` | 拆要求侧 / 实例侧（第一轮 §2.2） |
| **3** | 后台**没有「规则版本化」** | `cert_validation_rule` 有 `IsActive` 但**无 Version**；`cert_report_template` 有 `IsDefault` 但**无 Version** | 规则表加 `Version` + `EffectiveDate`，或建 `cert_rule_snapshot`。**否则改了规则，去年的报告就重算不出来 —— 违反体系认证可追溯性硬要求** |

### 12.4 一处空缺：后台完全没有「认证业务流」

缺：认证申请/受理、审核立项、审核组/审核员资质、审核计划、检查表、不符合项、整改验证、认证决定、证书、监督审核。

⚠️ **但这不一定是"后台的错"** —— **取决于"专家端是谁的系统"**：

- **若专家端 = 认证机构的完整作业系统** → 这些**应该在专家端**，后台**不补**（补了就是两套业务系统打架）
- **若专家端 = 只是专家的个人工作台**（专家被派活后干活）→ 后台（或别处）**必须有**

**→ 这是第五问的真正前置：你需要先回答「专家端到底是谁的系统」。**

### 12.5 补正优先级

| 序 | 补正项 | 为什么这个序 |
|---|---|---|
| **1** | **录 ISO 9001:2015 真实条款树** | **不可由代码替代**，卡死 NC + 报告两条链 |
| **2** | 明确 `cert_org_stage` 语义 | 1 行数据，改语义即可；不定则企业级"覆盖标准"无合法来源 |
| **3** | 拆 `cert_standard_directory_*` | 0 行时拆 = 改 DDL |
| **4** | 规则加版本 | 越晚加越贵 |
| **5** | 回答「专家端是谁的系统」 | 决定是否补业务流 |
