## 〇、一句话结论（V2 · 四条裁决全部落地）

> **① `run` 拒绝时结构化带回 `ParamGaps`** ⇒ 改后端 1 处（`Fail` 携带 data）。
> **② ⛔ 不建视图 ⇒ 抽通用 Service**（查询 + 补录收口）—— **这个选择比视图更对症**：
> 真正重复的不是「标准名翻译」（一行字典查询即可），而是**「取定义 × 取值 × 决策 × 分组」这段逻辑

> **③ 弹窗 = 缺口优先 + 全量可编辑**（必填 + 选填 + **已填可改**；选填可留空继续；⛔ 拦截判据仍只认必填，见 §1.3）。
> **④ 全链路关联 / 定位 / 传参只用 `Code`**（⛔ 无 `Id`）—— 已逐条核对（见 §1.4）。
>
> ⇒ 交付形态：**1 个通用 Service**（`IFillParamService`，落 `Auditor`）+ **1 个通用组件**（`FillParamForm`，落 `cert-share`）
> + **1 处后端小改**（`run` 带回 `ParamGaps`）+ **3 处前端接线**（DTO / 预览卡 / 弹窗）。

## 一、V2 四条裁决

### 裁决一览

| # | 议题 | V1 建议 | **用户裁决（2026-10-14）** | 本文处置 |
|---|---|---|---|---|
| **D-4-1** | `run` 拒绝是否带回 `ParamGaps` | A 结构化带回 | **✅ 采纳 A**：「带回 `ParamGaps`」 | §1.1 |
| **D-4-2** | 参数视图范围 | A 只做 `v_cert_fill_param_def` | **⛔ 不建视图**；改「**查询和补录都需要一个通用的 service 而不是 controller，需要复用的时候可以直接通过 service 获取**」 | §1.2 + §二 |
| **D-4-3** | 弹窗显示范围 | A 只显示必填缺项 | **✅ 采纳 B**：「做选填吧」 | §1.3 |
| **架构** | 关联关键字 | —（V1 未单列） | 「**我们 yzh 架构的规则所有的关联，关键字只有 code，按这个规则统一设计**」 | §1.4 |

### 1.1 D-4-1 采纳 A：`run` 拒绝时带回 `ParamGaps`

**现状**（实测）：`EnterpriseNormalizeController.Run` 在缺参时 `Fail` 的载荷是**纯字符串**
（`ApiResponse<object>.Fail("存在尚未填写的必填全局参数，请先到…：" + gapLines)`，`:1144-1146`）
⇒ 前端只能拿到一句话，**拿不到结构化清单**，弹窗没有数据可渲染。

**改造**（1 处）：

```csharp
// EnterpriseNormalizeController.Run —— 缺参分支（:1134-1147）
return Ok(ApiResponse<object>.Fail(
    "存在尚未填写的必填全局参数，请先到「企业资料参数」补齐后再执行：" + string.Join("；", gapLines),
    new { ParamGaps = plan.ParamGaps, MissingRequired = plan.MissingRequired }));
```

> ⚠️ **实施前必查**：`ApiResponse<T>.Fail` 是否已有**带 data 的重载**。
> 若没有 ⇒ 用既有等价写法（如 `Fail` 后 `SetData(...)`，或改为返回 `Ok(new ApiResponse<object> { Success = false, Err = msg, Data = new {...} })`）。
> ★ **信封铁律不变**：`success=false` + `err` 非空 + `message` 为空 ⇒ 仍是**业务拒绝**，⛔ 不是「`Ok` + 把解释塞 `data.message`」。

**为什么选 A（而不是前端先调 `plan`）**：

| 理由 | 说明 |
|---|---|
| **与既有设计一致** | `plan` / `run` **共用同一份算法**（`BuildPlanAsync`，`:1064-1065` 注释：「干跑说『3 个会跑』就是承诺」）⇒ `run` 的返回值就是权威 |
| **消灭新缺口** | 选 B（前端先调 `plan`）会引入「plan 与 run 结果不一致」的窗口（页面停留期间模板可能被取消发布、参数可能被改） |
| **省一次请求** | 弹窗直接吃 `run` 的返回值 |

### 1.2 D-4-2 裁决：⛔ 不建视图 → 抽通用 Service

**用户原话**：

> 「**不建立视图**，但就类似我们之前建立 share 的统一规则一样，**查询和补录都需要一个通用的 service 而不是 controller**，
> **需要复用的时候，可以直接通过 service 获取**」

**裁决落地**：

| 项 | V1 设计 | V2 处置 |
|---|---|---|
| `v_cert_fill_param_def`（视图） | 建（翻译标准名 / 族名） | ⛔ **作废**（不建） |
| 标准名翻译 | 靠视图 JOIN | 改走 **`ICoreResourceQuery.GetStandardsByCodesAsync`**（`CoreResourceQuery.cs:375`，**已存在，零新增**） |
| 「取定义 × 取值 × 决策 × 分组」逻辑 | 仍散在两个 Controller | ✅ **收口到通用 Service** |
| 补录（写 `cert_fill_param_value`） | 散在 `FillParamValueController.Save` | ✅ **收口到同一 Service** |

⇒ **「类似 share 的统一规则」= 项目 1.B「核心资源检索统一」的同一手段**：
把「谁都要做一遍的取数」收口到一个共享入口，⛔ 不在各 Controller 里各写一份。
（既有先例：`ICoreResourceQuery`、`FillParamValueProvider`。）

### 1.3 D-4-3 采纳 B：弹窗 = **缺口优先 + 全量可编辑**

**用户原话**：「做选填吧」＋（V2.1 补充）「可以，可以针对**已经填写的内容，进行修改**」。

**落地**：弹窗 ⛔ **不是「只补空缺」**，而是一个**完整的参数编辑抽屉**：

| 呈现 | 内容 |
|---|---|
| **未填项** | **置顶 + 高亮**（它们是阻断入队的原因，用户第一眼要看到） |
| **选填** | 显示（可折叠），可留空 |
| **已填项** | **显示当前值，可查看并修改**（★ V2.1 补充） |

> ★ **必须澄清的一条边界（✅ 用户 2026-10-14 已确认）**：
> **「显示范围」≠「拦截判据」。**
>
> | | 范围 | 依据 |
> |---|---|---|
> | **弹窗显示** | 必填 + 选填 + **已填（可改）** | 用户裁决（D-4-3 + V2.1 补充） |
> | **`run` 拦截** | **只认必填**（`IsRequired=true`） | 既有设计（`:1130-1133`：「只拦必填，选填缺失放行（照旧 partial + 待办归因），⛔ 不把整批卡死」） |
>
> ⇒ **弹窗里选填可以留空，主按钮仍可「补齐并继续」**（✅ 已确认）。
> 若把选填也纳入拦截 ⇒ **推翻「选填缺失不阻断」这条既有裁决**，且用户会被强迫填一堆非必要项。

> ★ **「已填可改」的实现要点（★ 零后端改动）**：
> `save` 端点的 **upsert 语义天然支持修改** —— 按 `(EnterpriseCode, StandardCode, StageCode, ParamCode)`
> 查重（**含已删**，命中则复活），命中即 `Update`（`FillParamValueController.cs:471-493`）。
> ⇒ 前端只需把**改动过的项**放进 `Items` 即可，⛔ 无需新端点。
>
> ⚠️ **一处例外（⛔ 不是缺陷）**：`MergedParamItem.Editable === false` 的项（`MaintainMode='auto'`）
> **仍不可改** —— 它的语义是「**永远等于企业档案**」，即使传了值也会被 `Save` 忽略并进 `ignoredAuto`
> （`:459-464`）。弹窗里**不显示**这类项，避免「改了不生效还不报错」。

### 1.4 架构铁律：所有关联 / 定位 / 传参**只用 `Code`**

**用户原话**：「我们 yzh 架构的规则**所有的关联，关键字只有 code**，按这个规则统一设计」。

**依据**：`AGENTS.md` ④「双关键字准则 A（Id/Code）」——
`Id` **永不**进 WHERE / 关联 / `Id>0`·`Id==0` 的 add·update 分流 / 存在性判定；
定位 / 删除 / 更新 / 前后端传参**只用 `Code`**。
（`OrderBy(Id)` 与 `new` 实体 `Id=0`/`null` 允许。）

**本设计逐条核对**：

| 环节 | 用什么 | 合规 |
|---|---|---|
| Service 入参 | `WorkspaceCode` / `EnterpriseCode` / `StandardCode` / `StageCode` / `ParamCode` | ✅ 全 `Code` |
| 取定义谓词 | `OrgCode == '' && (StandardCode == '' \|\| == sc)` | ✅ `Code` |
| 取值谓词 | `EnterpriseCode` + `StandardCode` + `StageCode` + `ParamCode` | ✅ `Code`（= 唯一键 `uk_ent_std_stage_param` 四列） |
| 补录 upsert 查重 | 同上四列（**含已删**，命中则复活） | ✅ `Code` |
| 标准名翻译 | `GetStandardsByCodesAsync(codes)` → `ToDictionary(s => s.Code)` | ✅ `Code` |
| 前端树节点 | `node.Code` / `node.Extra.StandardCode` | ✅ `Code` |
| 弹窗定位 | `EnterpriseCode` + `StandardCode` | ✅ `Code` |
| **⛔ 禁止出现** | `Id` 进 WHERE / 关联 / 前后端传参 | — |

> ⚠️ **一处需保留但**不违反**准则**：`Save` 的 `defMap` tie-break 用了 `.ThenBy(d => d.Id)`（`:436`）——
> **排序用 `Id` 是准则明确允许的**（「`OrderBy(Id)` 允许」），⛔ 不是违规、⛔ 不要「顺手改掉」。

## 二、通用 Service 设计（替代视图）

### 2.1 为什么「不建视图」是对的（★ 证据）

V1 论证过视图的**三个障碍**（通配谓词无法静态化 / 业务判定不可进视图 / 分组聚合不可进视图）。
V2 补一条**更本质的**：**视图只能解决「翻译」，而真正重复的是「逻辑」**。

**实测重复证据** —— 同一件事（取定义 × 取值 × 按标准分组）**已经写了两遍**：

| 入口 | 位置 | 做了什么 |
|---|---|---|
| `FillParamValueController.MergeList` | `:271-345` | 取定义 → `PickMostSpecific` → 取值 → 逐条 `Resolve` → **按 `GroupName` 分组** → 算完成度 |
| `EnterpriseNormalizeController.BuildParamGapsAsync` | `:414-492` | 取定义 → 取值 → **按标准分组** → 算差集 → **手工翻译标准名**（`:424-429` 查 `ISOStandard` + `GroupBy` + `ToDictionary`） |
| `FillParamValueController.Save` | `:430-525` | 取定义 → 建 `defMap`（**又一遍** `Specificity` 排序去重）→ upsert |

⇒ 三处各自实现了「取定义 + 特异性去重」，其中**标准名翻译**还被单独重写了一遍。
⇒ **收口到 Service 的收益**：三处共用一份实现，⛔ 不可能给出不同结论。

> ★ 结论：**用户选 Service 而非视图，比 V1 的建议更对症**。
> 视图（若建）只消除「标准名翻译」这一小段；Service 消除**全部重复逻辑**，
> 且顺带把「补录」也收口 —— 这正是用户说的「查询和补录都需要一个通用的 service」。

### 2.2 ★ 分层约束：Service **必须落 `Auditor`**（不可放 `Shared`）

这是本设计的**硬约束**，⛔ 不是偏好：

| 事实 | 后果 |
|---|---|
| `FillParamValue` 实体在 **`CertPlatform.Auditor/Entities/Cert/`**（R17 裁决：Shared 实体须两端都用；实测 Admin=0 / Auditor=12） | Service 要读写该表 ⇒ **只能在 Auditor** |
| `Shared` ⛔ **不能引 `Auditor`**（`Auditor → Shared` 单向，反向成环；**A-R2 零容忍**） | 若 Service 放 Shared 并要操作 `FillParamValue` ⇒ **直接违反 A-R2** |
| 若把 `FillParamValue` 上移 `Shared/Entities/` 换取 Shared 落位 | 违反 **R17**（Shared 实体必须两端都用）⇒ 换来一个新的守卫违规 |

⇒ **落位**：`CertPlatform.Auditor/Services/Ent/FillParamService.cs`
（与 `DocumentFillOrchestrator` 同目录；`Services/Ent/` 是专家端业务服务层）

**Service 依赖**（全部已存在，⛔ 零新增底层能力）：

```
IFillParamService
  ├─ IDbOrm                          （读写 cert_fill_param_value / 查企业档案）
  ├─ ICoreResourceQuery              （★ 取参数定义 + 翻译标准名 —— 复用 Shared 收口）
  └─ （纯函数）ParamValueResolver / FillParamValueProvider.BuildValue（决策，⛔ 不重写）
```

> ★ **`Shared` 侧零改动**：`GetFillParamDefsAsync`（`:505`）与 `GetStandardsByCodesAsync`（`:375`）**都已存在**，
> Service 只是**调用方**。这正是用户说的「复用的时候可以直接通过 service 获取」。

### 2.3 Service 契约（`IFillParamService`）

```csharp
namespace CertPlatform.Auditor.Services.Ent;

/// <summary>
/// ★ 企业资料参数通用服务 —— 「查询 + 补录」的唯一入口。
///
/// <para><b>为什么要它</b>：同一件事（取定义 × 取值 × 决策 × 分组）此前在
/// FillParamValueController.MergeList / Save 与 EnterpriseNormalizeController.BuildParamGapsAsync
/// 各写了一遍 ⇒ 收口到本服务，⛔ 不允许再在 Controller 里各写一份。</para>
///
/// <para><b>★ 铁律</b>：全部入参 / 谓词 / 关联只用 Code（AGENTS.md ④ 双关键字准则 A），⛔ 无 Id。</para>
///
/// <para><b>落位约束</b>：必须在 Auditor —— 本服务读写 FillParamValue（Auditor 独占实体），
/// 而 Shared ⛔ 不能引 Auditor（A-R2）。</para>
/// </summary>
public interface IFillParamService
{
    /// <summary>① 合并清单（纯读）—— 「后台定义 × 企业已填值」按 GroupName 分组 + 完成度。</summary>
    Task<FillParamListResult> GetMergedListAsync(FillParamScope scope, CancellationToken ct = default);

    /// <summary>
    /// ② 缺参清单（纯读）—— 按「涉及标准」算缺失项，供规范化入队前预检 + 补参弹窗。
    /// <paramref name="includeOptional"/>=false 时只算必填（= run 的拦截口径）。
    /// </summary>
    Task<List<FillParamGapGroup>> GetGapListAsync(
        FillParamScope scope, IEnumerable<string> standardCodes,
        bool includeOptional, CancellationToken ct = default);

    /// <summary>③ 批量补录（写）—— 只落 manual / both；auto 项忽略并回报。</summary>
    Task<FillParamSaveResult> SaveAsync(
        FillParamScope scope, IReadOnlyList<FillParamSaveItem> items,
        string userCode, CancellationToken ct = default);
}

/// <summary>作用域（★ 全 Code，⛔ 无 Id）</summary>
public sealed record FillParamScope(
    string WorkspaceCode, string EnterpriseCode,
    string StandardCode, string StageCode);
```

### 2.4 三个方法详设

#### ① `GetMergedListAsync`（= 现 `MergeList` 下沉）

| 步骤 | 实现 | 来源 |
|---|---|---|
| 1. 取定义 | `_core.GetFillParamDefsAsync(scope.StandardCode, scope.StageCode)` | `CoreResourceQuery:505`（复用） |
| 2. 特异性去重 | `ParamValueResolver.PickMostSpecific(defs)` | `Shared/Fill/`（纯函数，复用） |
| 3. 取值 | `Queryable<FillParamValue>`，谓词 = `EnterpriseCode + ParamCode ∈ 定义集` | `IDbOrm` |
| 4. 逐条决策 | `ParamValueResolver.Resolve(def, entInfo, row.Value, row.Source, row.IsManualEdited)` | 纯函数（复用） |
| 5. 分组 + 完成度 | `GroupBy(GroupName)` + `Count` | **Service 内**（业务判定，⛔ 不进视图） |
| 6. 标准名翻译 | `_core.GetStandardsByCodesAsync(codes)` → `ToDictionary(s => s.Code, s => s.StandardName)` | `CoreResourceQuery:375`（★ 替代视图） |

#### ② `GetGapListAsync`（= 现 `BuildParamGapsAsync` 下沉 + 扩展选填）

```
入参：scope + standardCodes（涉及的标准）+ includeOptional
口径：对每个标准 S，取「(S 或通配) × 阶段(通配或 stage)」下 IsRequired[+选填] 的定义全集
     减去「该企业已填且非空」的值 ⇒ 缺失集合
出参：List<FillParamGapGroup> { StandardCode, StandardName, Items[{ ParamCode, ParamName, GroupName, ValueType, IsRequired }] }
```

> ★ **`includeOptional` 的两个调用口径**（同一方法，两个开关）：
> - `false` ⇒ **`run` 的拦截口径**（只算必填）—— 语义与现 `BuildParamGapsAsync` **完全一致**（行为不变）
> - `true` ⇒ **补参弹窗的口径**（必填 + 选填，D-4-3）
>
> ⚠️ **标准名翻译**改走 `GetStandardsByCodesAsync` ⇒ **消除** `:424-429` 那段手工 `GroupBy` 建字典。

#### ③ `SaveAsync`（= 现 `Save` 下沉）

```
1. 企业存在性 + 归属校验（Code 定位；企业必须属于当前工作区）
2. 定义全集 + defMap（Specificity 排序去重）
3. ⛔ 未定义编码 ⇒ 报错（不静默丢弃）
4. 事务内逐项 upsert：
   · auto 项 ⇒ 忽略 + 记 ignoredAuto
   · 查重键 = (EnterpriseCode, StandardCode, StageCode, ParamCode) —— ★ 含已删，命中则「复活」
   · 命中 ⇒ Update（ParamValue / ValueSource='manual' / IsManualEdited=true / 清软删）
   · 未命中 ⇒ Insert（Code = Guid，OrgCode = 工作区 Code）
5. 返回 { savedCount, ignoredAuto, message }
```

> ★ **唯一键 `uk_ent_std_stage_param` 四列全是 `Code`** ⇒ 天然符合「关联只用 `Code`」。

### 2.5 复用点：三个 Controller 变薄

**落位**：`cert-share/src/components/fill-param/FillParamForm.vue`（⛔ 不放页面目录，否则只能被一页用）。

```
props:
  groups: MergedGroup[]          // 数据源（merge-list 的 Groups）
  mode?: 'page' | 'dialog'       // 页面模式（全量）/ 弹窗模式（缺口优先 + 全量可编辑）
  showOptional?: boolean         // 弹窗模式是否显示选填（★ D-4-3 = true）
  showFilled?: boolean           // 弹窗模式是否显示已填项（★ V2.1 = true，可修改）
  saving?: boolean

emits:
  change(items: { ParamCode, ParamValue }[])   // 只带**改动过**的项（新增 + 修改）
  save()                                        // 父层决定时机（页面=保存 / 弹窗=补齐并继续）
```

**两种模式的差异**：

| | 页面模式 | 弹窗模式 |
|---|---|---|
| 显示范围 | 全部参数（按 `GroupName` 分组） | **未填项置顶高亮** + 选填折叠 + **已填项可查看修改**（★ V2.1） |

| 完成度 | 显示 | 显示「将补 N 项 / 共缺 M 项」 |
| 只读项（`Editable=false`） | 显示 + 「去企业管理修改」 | ⛔ 不显示（弹窗里改不了，避免误导） |
| `change` 事件 | 改动项（含清空） | 改动项（含清空）—— **已填项改成新值同样计入** |

> ★ **「已填可改」零后端改动**：`save` 的 upsert 语义天然支持（见 §1.3 的实现要点）。
> ⛔ **唯一例外**：`Editable=false`（`MaintainMode='auto'`）的项不可改，弹窗不显示它们。

**⛔ 三条硬约束（复用 `KeyInfoFillDrawer` 已验证的契约）**：

1. **纯表单** —— ⛔ 不发任何请求；落库与入队全由页面 `logic` 编排（`KeyInfoFillDrawer.vue:25-28`）。
2. **每次打开重置编辑态** —— ⛔ 不残留上次输入（`KeyInfoFillDrawer.vue:108-120`）。
3. **文案指向具体下一步** —— ⛔ 不写「参数缺失」这类笼统话。

### 3.4 「分区显示」的落地（D-3 显示层要求）

│    └─ 二级：按 GroupName（基础信息 / 体系信息 / …）
