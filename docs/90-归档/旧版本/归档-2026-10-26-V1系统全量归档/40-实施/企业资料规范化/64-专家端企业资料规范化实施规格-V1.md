## 1 定位与权威关系

### 1.1 一句话

**专家端把企业上传的原始资料，收敛成「标准文档实例」的链路**：分流 → 入队 → 单文件编排（取模板 / 读画像 / 取值 / 落笔 / 自验收 / 清示例 / 回写）→ 单元格级取值账本 → 人工干预 → 打包下载。

**AI 只产候选与建议值，最终落笔与裁决必须人工**；冲突候选禁止自动确认。

### 一、数据库变更

#### 1.1 ★ 新表 ①：`cert_doc_fill_value` —— 单元格级取值账本

**为什么必须有**（`41-00` §二·缺口 2）：

| 现状 | 问题 |
|------|------|
| `FillValue.Confidence` | 构造 `OfficeFillHit` 时**被丢弃**（`OfficeFillModels.cs:246`） |
| `cert_doc_fill_log` | **聚合表**（JSON 汇总），⛔ 无「一行一锚点」 |
| `cert_doc_ai_suggestion` | **只管 AI 建议**；而 25 号实测 **98.6% 的锚点是确定性来源**（编号 444 / 日期 472 / 人名 315 / 公司名 22）⇒ **98.6% 的取值没有账本** |
| 「查看数据来源 / 改数据来源 / 全部重写」 | **无表可支撑** |

⇒ 这张表是**用户 2026-10-04 那句核心需求的物理载体**：
> 「每个文档有完成率和可信度的显示，可以针对任何单元格查看填写的数据来源，或更改数据来源或全部重写」

```sql

  `CreateTime`        datetime      NOT NULL              COMMENT '创建时间',

  `OrgCode`           varchar(36)   NOT NULL DEFAULT ''   COMMENT '认证机构Code（冗余，便于按机构查）',

  `AnchorCode`        varchar(36)   NOT NULL              COMMENT '★锚点 → cert_doc_template_anchor.Code',
```

#### 1.1.1 ★ V1.1 补充①：固定文档的取值**也落这张表**

V1.1 原设计只考虑「可编辑文档的锚点取值」。但定稿后 **固定文档（营业执照 / 身份证 / 许可证）同样是一次「取值」**：

| 项 | 可编辑文档 | ★ 固定文档 |
|----|-----------|-----------|
| `AnchorCode` | `cert_doc_template_anchor.Code` | ★ 标准文档 Code（固定文档无空白模板 ⇒ 无锚点行） |
| `SourceKind` | `global`/`profile`/`compute`/`ai`/`manual` | ★ 固定为 **`profile`**（值来自企业上传原件） |
| `SourceDetailJson` | `{paramCode, profileCode, originalFileCode, fieldPath}` | ★ `{originalFileCode, fileCode, candidateCount, topScore, matchedBy}` |
| `Confidence` | 按 `41-01` §三·2 计算 | ★ **= 候选的 `Score`**（指纹/关键字段比对得分） |
| `FillStatus` | `filled`/`pending` | ★ `filled`（已选定）/`pending`（待人工指定） |
| `ValueText` | 抽取的字段值 | ★ 抽取的字段值（`Fields[][]` 序列化） |

> ⚠️ **候选清单 ⛔ 不落库**（重要决策）：

### 二、★ 完成率口径（26 号未定义，本节定义）

#### 2.1 唯一定义

```text
完成率 = 已写入锚点数 / 有效锚点总数
       = (FillAnchorCount − FillPendingCount) / FillAnchorCount
       = FillCompletion（物化在 cert_standard_directory_file）
```

| 项 | 规则 | 依据 |
|----|------|------|
| **分母** | `cert_doc_template_anchor` 中 `AnchorType ∈ (scalar, block, table, table_total, domain)` 且 `IsOrphan = 0` 的**行数** | 21 号 §6.2「模板即完成度的分母 —— 分母不用猜、不用 AI 估，模板一改分母自动跟着变，**就是锚点数**」 |
| 排除 | `IsOrphan = 1`（模板重传后消失的锚点） | 它已无落笔位置，算进分母会让完成率永远上不去 |
| **分子** | `cert_doc_fill_value` 中 `FillStatus = 'filled'` 的行数 | `kept_as_is` 与 `pending` 都不算「已写入」 |
| **`Total = 0`** | ⛔ 记 **0.0000**，⛔ **不是 1.0000** | `FillReport.Completion` 注释 + `OfficeFillReport.Completion` 注释 + 26 号 R-6「V1 曾出现 100% vs 0% 两套，已修」 |
| **区域填充** | ⛔ **不计入分母**（`OfficeFillRegionHit` 注释：「数据有几行就是几行，混在一起会让完成度失真」） | 同上 |
| **锁定的文件** | 完成率**照常显示**，但 UI 加 🔒 徽标 + tooltip「已锁定，重新生成时跳过」 | 26 号 S-6 |

#### 2.2 三处口径必须一致（同一份数据，三个地方算出同一个数）

| # | 位置 | 现状 | 本册要求 |
|---|------|------|---------|
| 1 | `FillReport.Completion`（E1 文本引擎） | ✅ 已是 `Total == 0 ? 0.0 : Resolved / Total` | ⛔ 不改 |
| 2 | `OfficeFillReport.Completion`（E2 文件写入） | ✅ 已是 `Total == 0 ? 0.0 : Resolved / Total` | ⛔ 不改 |
| 3 | 企业端 `liveCompletion`（`FillParamValueController`） | ✅ 29.41% 实测一致 | ⛔ 不改 |
| 4 | **本册列表页聚合** | 🆕 | ⚠️ **读 `cert_standard_directory_file.FillCompletion`（物化列），⛔ 不实时聚合** |

> **为什么第 4 条要物化**：一份文档 1271 个锚点、668 份文档 ⇒ 实时聚合 = 每行一次 `COUNT(*)`，列表页直接卡死。
> 物化时机 = 编排器第 ⑦ 步（`41-03` §一），⛔ 不在查询时算。

#### 2.3 三个层级的完成率（页面要显示三种，不能只一种）

| 层级 | 字段 | 口径 | 界面位置 |
|------|------|------|---------|
| **单锚点** | — | `filled` / `pending` | 单元格抽屉 |
| **单文档** | `cert_standard_directory_file.FillCompletion` | 上面的定义 | ★ 列表页「完成率」列（左树节点徽标同源） |
| **单范围**（目录/阶段/标准/企业） | 🆕 `GET /normalize/plan` 返回 | 该范围内 `Σ已写入 / Σ分母` | 范围预览条 |

> ⚠️ **范围级完成率的分母必须重新数，不能把子文档的 `FillCompletion` 求平均** ——
> 一份 3 锚点的文档和一份 500 锚点的文档，平均它们的完成率是错的。**必须先求和再相除。**

### 三、★ 可信度口径（26 号未定义，本节定义）

#### 3.1 ⚠️ 先说清「两套可信度不是同一套」

| # | 体系 | 值域 | 落表 | 算法 | 本册是否用 |
|---|------|------|------|------|-----------|
| **①** | **定向提取字段可信度** | `decimal(3,2)` NULL | `cert_extraction_result.Confidence` | 04 号 §5 | ⛔ 间接（经画像 `FieldsJson`） |
| **②** | **画像置信度** | `decimal(3,2)` NULL | `cert_enterprise_doc_profile.Confidence` / `TagsConfidence` / `DocPurposeConfidence` | 33 号 `doc_content` 给分 | ✅ 作为 `profile` 来源的输入 |
| **③** | **匹配综合可信度** | `decimal(3,2)` | `cert_doc_match_candidate.Confidence`（**该表 0 行，未建**） | **04 号 §5.2 五维加权** | ⛔ **本册不用** |
| **④** | ★ **单元格级取值可信度** | `decimal(3,2)` | ★ **`cert_doc_fill_value.Confidence`** | **本节定义** | ✅ **本册主体** |

> **为什么 ③ 不能拿来用**：它是「这份企业资料**是不是**这份标准文档」的分数（五维：语义 0.35 + 字段 0.30 + 表格 0.20 + 规则 0.10 + 时效 0.05），
> 回答的是**文档级归属**问题。
> 用户要的是「**这个单元格的值可不可信**」—— 这是**取值链**问题，粒度差两个数量级。
> ⇒ **混用会导致「文档匹配 92% 但某个单元格是错的」无法表达。**

#### 3.2 ★ 单元格级可信度定义（本册新增口径）

```text
Confidence = f(SourceKind, 来源自身的 Confidence, 是否人工确认)
```

| `SourceKind` | 公式 | 25 号实测占比 | `ConfidenceReason` 示例 |
|--------------|------|-------------|----------------------|
| `global`（全局参数） | **1.00** | 35.0%（编号 444）+ 37.1%（日期 472）≈ **72%** | 留空（确定性） |
| `compute`（计算/统计） | **1.00** | 派生清单表（4 文件占 36%） | 留空 |
| `replace`（企业属性直取） | **1.00** | 1.7%（公司名 22）+ 部分人名 | 留空 |
| `manual`（人工录入） | **1.00** | 认证日期等（一期 `F-11`） | 留空 |
| `self`（本文档内引用） | **1.00** | 一期不用（`F-13`） | 留空 |
| `profile`（企业资料画像取值） | **`SourceConfidence`**（画像 `FieldsJson[].confidence`） | ★ **0%**（25 号实测：⑤ 类一期占比 0%） | 「取自企业上传资料《内审计划》，AI 抽取，未人工确认」 |
| `ai`（AI 生成） | **`SourceConfidence` × 0.9** | ≤5 处（0.1%） | 「来源为 AI 建议，未人工确认」 |

**三条硬规则**：

| # | 规则 | 理由 |
|---|------|------|
| **R-C1** | ⛔ **`Confidence` 恒 `NOT NULL`**（与 `cert_extraction_result.Confidence` 的可空口径**相反**） | 可空 = 「不知道」；但「从全局参数取值」这件事**本身就是确定的**，留空会让 72% 的行显示「未知」，界面没法用 |
| **R-C2** | `SourceKind = 'profile'` / `'ai'` 时，`SourceDetailJson` **必须**含 `profileCode` 或 `suggestionCode`；否则 `Confidence` 强制打 **0.50** | 说不出来源的 AI 值 = 不可信，降级 |
| **R-C3** | 人工确认后（`IsOverridden = 1`），`Confidence` **强制置 1.00** | 人看过的东西就是可信的；⛔ 不保留模型原分（那会让人误以为还有风险） |

#### 3.3 ★ 文件级可信度（列表页显示的那个）

```text
FillConfidence = Σ(Confidence_i) / N
```

⚠️ **三条防坑**（都是会被写错的）：

| # | 坑 | 正解 |
|---|-----|------|
| 1 | 把「已人工确认」和「AI 给分」一起平均 | ⛔ **可以一起平均**（人工已置 1.00，抬高均值是正确的 —— 人工确认过就是可信） |
| 2 | 把 `pending` 行（无值）算进分母 | ⛔ **不算**。只对 `FillStatus = 'filled'` 的行求均值。`pending` 的影响体现在**完成率**上，不体现在可信度上 |
| 3 | 用「文档级匹配置信度 ③」当文件级可信度 | ⛔ **两码事**（见 §三·1） |

**展示口径（三档配色，与 `04` 号阈值刻意不同）**：

| 区间 | 徽标 | 文案 | 建议动作 |
|------|------|------|---------|
| `≥ 0.95` | 🟢 绿 | 高可信 | 无需干预 |
| `0.70 ~ 0.95` | 🟡 黄 | 部分待确认 | 点开看黄/红单元格 |
| `< 0.70` | 🔴 红 | 需人工复核 | **列表页可按此筛选** |
| `FillConfidence = 1.00` 且 `FillCompletion = 0` | ⚪ 灰 | 无可填项 | 「该文档不含可填锚点，纯复制即可」（25 号：**42.5% 的文件属于此类**） |

> ⚠️ **阈值为什么不跟 `04` 号一样**（`04` 号是 `≥0.85 / 0.50–0.85 / <0.50`）：
> 因为 ④ 的分母里 **72% 是确定性来源恒 1.00**，若用 0.85 阈值，**几乎所有文档都是绿的**，界面失去筛选意义。
> ⇒ ④ 的阈值必须**更高**（0.95）才能把「少数 AI/画像来源」标出来。
> 这三个阈值落 `cert_sys_config`（`ent_fill_conf_high` / `ent_fill_conf_mid`），⛔ 不硬编码。

### 四、★ 匹配歧义机制（本轮最重要的新增）

#### 4.1 问题陈述

> 用户原话：「标准文档中需要一个法人的身份证，但我们企业上传了多份身份证，电脑可能没办法精准匹配那一张是法人的，但从企业资料中找到了 3 个身份证，这就要求我们从待选项中重新选择」

**为什么自动识别必然失败**：

| 判据 | 对身份证的效果 |
|------|--------------|
| 文件名匹配 | `张明远_身份证正面.jpg` / `李建国_身份证正面.jpg` —— **都叫「身份证正面」**，无法区分 |
| 文档内关键字段 | 正面有姓名可与营业执照法定代表人比对（94%）；**反面没有姓名字段**（62%，只能靠文件名推断） |
| 分类标签 | 全部命中「身份证明」—— **无区分度** |

⇒ 结论：**同名/同类文件必须人工指定**，系统只负责「把候选找齐 + 排出优先级 + 给出判定依据」。

#### 4.2 后端返回契约（★ 新增端点的一部分）

```text
MatchState  : auto_matched | ambiguous | no_match | warn | confirmed
Top1Score   : decimal(3,2)
Threshold   : 0.90（落 cert_sys_config，⛔ 不硬编码）
Candidates[]: [
  {
    FileCode      : 原始资料 Code → cert_enterprise_original_file.Code
    FileName      : 原始文件名
    FileType      : PDF / JPG / DOCX / XLSX …
    Size          : 字节数
    Pages         : 页数（影像件为 1）
    Score         : decimal(3,2)   匹配度
    MatchField    : 命中了哪个字段（如「姓名 + 公民身份号码」）
    MatchedBy     : 判定依据（人话，如「与营业执照『法定代表人 张明远』姓名一致」）
    Evidence      : 证据原文片段（含高亮标记 <em>…</em>）
    Fields[]      : 抽取出的字段值 [[字段名, 值], …]
  }
]
```

| `MatchState` | 触发条件 | 界面表现 | 需人工 |
|-------------|---------|---------|:---:|
| `auto_matched` | Top1 ≥ 0.90 且无同分候选 | 绿「已自动匹配」，可复核 | 否 |
| **`ambiguous`** | ≥2 个候选（无论分差） | ★ 黄色告警 + 候选列表 + **必须指定** | **是** |
| `no_match` | 候选数 = 0 | 红「无可匹配文件」+ 引导去上传 | 是 |
| `warn` | Top1 ≥ 0.90 但有告警（如证件有效期） | 已匹配 + 橙色告警条 | 建议 |
| `confirmed` | 人工已指定并确认 | 绿「已就位」+ 🔒 | — |

```text
│ 住址        │ 陕西省西安市雁塔区科技路 xx 号                 │
│ 公民身份号码 │ 6101**********2317                            │
├────────────────────────────────────────────────────────────┤
│ [🔍 预览原件]  [企业暂无此件]                                │
└────────────────────────────────────────────────────────────┘
```

> ★ **「判定依据」必须人话**，⛔ 不能只给分数 —— 只给百分比不给依据是盲选（26 号 §3.6 精神）。

#### 4.4 ★ 落点（数据）

| 数据 | 落库 | 说明 |
|------|------|------|
| 选定结果 | `cert_doc_fill_value`（`AnchorCode` = 固定文档的标准文档 Code） | `SourceKind='profile'` · `SourceDetailJson.originalFileCode` · `SourceDetailJson.fileCode` · `Confidence` = 候选 Score |
| 候选清单 | ⛔ **不落库**（实时算） | ⚠️ 候选会随原始资料上传而变，落库就过期了 |
| 动作留痕 | `cert_doc_normalize_action`（`ActionType='lock'` / `ScopeType='file'`） | 记选定/取消/企业暂无 |

> ⚠️ **候选不落库**是重要决策：企业重新上传资料后候选集就变了，落库的候选是**假信息**。
> 只有**人工选定结果**落库（因为那是决定，不是候选）。

#### 4.5 「企业暂无此件」

| 项 | 值 |
|----|-----|
| 动作 | 标记该标准文档在当前企业/阶段**暂无** |
| 落库 | `cert_standard_directory_file.InstanceState = 'partial'` + `Remark` |
| 界面 | 状态列显示「企业暂无」，**不锁定**（后续补传后可继续） |
| 作用 | 审核阶段能看到「该企业缺哪些材料」（`file-check` 缺口清单的来源） |

### 五、★ 固定文档 vs 可编辑文档：两条完全不同的闭环

#### 5.1 分流判据（`cert_standard_doc_contract.DocCategory`）

| `DocCategory` | 闭环 | 平台生成内容？ |
|--------------|------|:---:|
| `fixed` | 上传 → 自动识别（歧义则人工指定）→ 接收 → 固定 | ⛔ **不生成** |
| `platform_generated` | 按目录自动派生 | ✅ 纯规则，⛔ 不走 LLM |
| `editable` | 模板 → 自动填充 → 逐格干预 → 更新文档 → 同步 | ✅ 生成 |

#### 5.2 固定文档闭环（5 步）

```text
① 一键规范化（范围）
      ↓ 每个固定文档 = 一个队列任务
② 自动识别 → 返回 MatchState + Candidates
      ├ auto_matched → 自动就位
      ├ ambiguous    → ⚠️ 进「待人工匹配」清单（不阻塞其他文档）
      ├ no_match     → 标「未就位」，等人工上传
      └ warn         → 就位 + 告警
③ 人工从候选指定（抽屉）
      ↓ 点「确认并更新文档」
④ 固定：IsLocked = 1 + 写 cert_doc_normalize_action
⑤ 同步到企业资料库（该槽位指向选定原件的 PDF）
```

> ★ **关键**：步骤 ② 的 `ambiguous` **不阻塞整批**。其他文档照常完成，只有这一个停在「待人工匹配」。

#### 5.3 可编辑文档闭环（7 步）

```text
① 一键规范化 → 每个文档 = 一个队列任务
② 读模板字节（走 EditableSegment 归一产物）
③ 层 2 全文填写规则 → 层 1 逐锚点解析 SourceSpec
④ NPOI 落笔（区域 → 正文 → 表格 → 页眉）
⑤ 自验收 VerifyMarks() → Verified=false 则判 partial
⑥ ★ 生成后即可预览 PDF（= 企业资料库里那个文件）
⑦ 逐格干预 → 点「更新文档」→ 重跑 ④~⑥ → 同步
```

### 六、★ 三页签职责边界（★ 定稿）

| 页签 | 内容 | ⛔ 不含 |
|------|------|--------|
| **文档预览（PDF）** | ★ **只有 PDF**：分页 · 缩放 · 下载 · 重新上传原件 · 跳转按钮 | ⛔ 不含任何表格、字段列表、填入值 |
| **锚点明细** | 逐格编辑：改值 · 从企业资料重新筛选 · 锁定锚点 · 待办清单 | ⛔ 不含完整取值账本（那是审计页） |
| **审计** | 四段（见 §6.3） | ⛔ 不含编辑输入框（编辑去锚点明细） |

#### 6.1 为什么预览页不能放表格

| 放表格的问题 | 后果 |
|-------------|------|
| 用户同时看 PDF 和表格，两处信息**不一致的窗口** | 改完表格忘了更新，PDF 还是旧的 |
| 表格占一半屏，PDF 被挤到看不清 | 预览失去意义 |
| 「预览」的心智是「看成品」，混入「编辑源」 | 职责混乱 |

⇒ **预览 = 只读成品**；**锚点明细 = 编辑源**；**审计 = 追溯**。三者互不越界。

#### 6.2 锚点三操作

| 操作 | 按钮 | 行为 | 落库 |
|------|------|------|------|
| **查** | `查` | 弹出来源卡：当前值 · 来源实体 · 证据原文 · 可信度 · 可点预览原始资料 | 只读 |
| **编** | `编` | 就地编辑输入框 / 从企业资料候选下拉筛选 | 写 `S.edits`（暂存） |
| **🔒** | `🔒` | 锁定/解锁该锚点（重写时保留） | `IsPinned` + `cert_doc_normalize_action` |

> **「查」返回时回到来源页签**（记录 `S.srcFromTab`），⛔ 不能固定回「锚点明细」—— 因为「查」现在也能从审计页进入。

#### 6.3 审计页四段

| 段 | 内容 | 数据源 |
|----|------|--------|
| ① **本次待提交改动** | 原值 → 新值 + 撤销按钮；空时提示「当前没有未提交的改动」 | `S.edits`（内存暂存） |
| ② **锚点状态概览** | 锚点总数 / 已填 / 待填写 / 已锁定 / 人工改动 | `cert_doc_template_anchor` + `cert_doc_fill_value` |
| ③ **已填入内容** | 只读速览表：位置 · 字段 · 值 · 来源 · 可信度 · `查`/`编`/`🔒` | `cert_doc_fill_value` |
| ④ **历史留痕** | 时间线：时间 · 操作人 · 动作 · 范围 · 对象/理由 | `cert_doc_normalize_action` |

> ★ **为什么叫「审计」而不是「改动清单」**：
> 「改动清单」回答「我刚才改了什么」（限本次会话、可撤销）；
> 「审计」回答「这个文档**从谁到谁**经历了什么」（跨会话、**只追加不可删改**，26 号 A-7）。
> **审核场景问的是后者。**

> ★ **段② 为什么必要**：「锚点总数 / 已填 / 待填写」是完成度的分子分母，
> 专家常问「为什么是 88%」—— 段② 直接给出 `17/19`，⛔ 不用自己反推。

### 七、★ 编辑三缓冲（「更新文档」到底更新什么）

#### 7.1 三个阶段

```text
【阶段1 · 暂存】用户改值 / 换来源 / 锁定锚点
   ↓ 只写内存 S.edits[docCode][ref] = { from, val, srcKind, pinned, srcChanged }
   ↓ ★ 不动 cert_doc_fill_value、不动后端、不动文件
   ↓ 界面表现：审计页段①出现「本次待提交改动」，底部按钮变「更新文档」可点

【阶段2 · 落笔】用户点「更新文档」
   ↓ ① 重跑编排器 ④~⑥（NPOI 落笔 + 自验收 + 上传 MinIO）
   ↓ ② 回写 cert_doc_fill_value（全来源，含本次改动）
   ↓ ③ 回写 cert_doc_fill_log
   ↓ ④ 回写 cert_standard_directory_file（NormalizedPath / Fill* 4 列）
   ↓ ⑤ 写 cert_doc_normalize_action（ActionType='rewrite'）
   ↓ ⑥ ★ 同步到企业资料库目录（该槽位指向新产物）

【阶段3 · 丢弃】用户关闭抽屉
   ↓ S.edits 清空，★ 数据库零变化
```

> ★ **为什么必须三缓冲**：
> 专家逐格核对 19 个锚点，中途发现第 3 格填错需要参考第 15 格的写法 —— 若改一格就落一次盘，
> 效率极低且中途关闭会留下半成品。**一次性提交**是唯一合理形态。

#### 7.2 四条不覆盖规则（「重新生成」时）

| # | 规则 | 判据 | 界面反馈 |
|---|------|------|---------|
| ① | **锁定的文件整份跳过** | `IsLocked = 1` | 预览条「跳过 2（已锁定 🔒）」 |
| ② | **锁定的锚点保留** | `cert_doc_fill_value.IsPinned = 1` | 预览条「其中 5 个锚点已锁定，将保留」 |
| ③ | **人工改过的值默认保留** | `IsOverridden = 1` | 弹窗默认勾选「保留人工填写值（推荐）」 |
| ④ | **示例数据必须清空** | `cert_doc_template_anchor.SampleData = 1` | ⛔ **不可跳过**（25 号 Q-5 合规铁律） |

> ⚠️ **规则③ 默认必须是「保留」**。若默认覆盖，专家辛苦核对的 3 格会在下次全量规范化时被冲掉 —— 最伤信任的设计。

### 八、队列与「先返回成功」的过渡

#### 8.1 粒度模型（沿用 26 号 §3.6 Q-J 方案 A）

```text
一个范围 = 一个批次（yzh_queue）—— 只做统计与进度
  ├── 一个文件 = 一个任务（yzh_queue_task）—— 原子，可独立重试
  ├── 一个文件 = 一个任务
  └── ...
```

| 层 | 界面 |
|----|------|
| 批次 | 顶部队列条：进度条 + `进行中 n · 完成 n · 失败 n` + 明细 + 取消 |
| 任务 | 明细抽屉：文档 · 类型 · 状态 · 耗时 · **人话失败原因** · 单条重试 |

> ⚠️ **失败原因必须是人话**，⛔ 不是堆栈（26 号 S-8）：
> `模板未上传（后台「标准文档填写规则」尚未配置此模板）` / `企业原始资料中无可匹配文件` / `无此参数`

#### 8.2 ★ P0 桩 → P1 真队列（用户提的「先写个接口直接返回成功」）

| 步 | 后端 | 前端 | 工作量 |
|:--:|------|------|:-----:|
| **P0 桩** | `POST /normalize/run` **同步**执行编排器，**不入队**，返回真实结果 | **完全无感**（返回结构与真实现逐字相同） | 0.5 人天 |
| **P1 真队列** | 改为建批次 + N 个任务；新增 `GET /normalize/batch/{QueueCode}` | 加轮询（**仅此一处**） | 3 人天 |

**桩端点必须做的 3 件事**（这才是「严谨」与「糊弄」的分界）：

1. **校验入参**（范围合法 / 模板存在 / 不是只读文档）
2. **写一条 `cert_doc_normalize_action`**（`ActionType='batch_run'`）—— 审计链不断
3. **同步执行编排器**，返回**真实产物 + 真实完成度**

> ⛔ **桩不能伪造数据**。返回 `Completion=100%` 而 `cert_doc_fill_value` 一行没有，
> 就和 25 号发现的「`Confidence` 95 行全为 NULL」同类 —— **界面看着对、数据是空的**。
> 正确做法：**只是「不入队」，其余全真**。

**永久保留的接口**（与队列无关）：
- `POST /normalize/plan` —— **干跑预览**（展开范围 + 各类跳过计数 + 警告）。⛔ 纯读 DB 零副作用 ⇒ **P0 就该做**，且是「一键规范化」按钮的前置。
- `GET /normalize/list` / `values` / `value/{code}` —— 列表与明细

### 九、★ 原型自检结论（4 个已修的真实缺陷）

> 这 4 个缺陷都是**原型阶段靠自检脚本跑出来的**，若留到实现阶段成本会高一个量级。

| # | 缺陷 | 症状 | 根因 | 修法 |
|---|------|------|------|------|
| 1 | `render()` 漏调 `renderTree()` | **左树整棵空白**，展开折叠无反应 | 函数写了但无人调用 | 补调用 |
| 2 | `renderSubMenu()` 清空 `.main` 的 `innerHTML` | 切到「规范化日志」再切回，**左树与右区所有节点从 DOM 消失** | 清空 innerHTML 会移除节点 | 改为 `style.display` 隐藏 |
| 3 | `switchMenu()` 绕过 `render()` | 切菜单时右区未隐藏 | 直接调 `showDrawer()` | 统一先跑 `render()` |
| 4 | `$()` 取 `innerHTML` 注入的元素 | 改值/重写抛错，「更新文档」失效 | `$()` 只查静态存在的 id | 改用 `querySelector` |

> ★ **教训**：自检脚本的 DOM 桩**必须严格**（`getElementById` 找不到就返回 `null`），
> 宽松桩（找不到就造一个元素）会把这一整类缺陷挡在门外。
> ⇒ 已把 `smoke.js` 改成严格模式，并加一条「运行期每次 `getElementById` 都必须命中真实节点」的断言。

### 十、★ 4 个待拍板的业务口径

| # | 问题 | 原型的处理 | 影响 |

#### 11.1 ★ 「同步到企业的文件夹」的准确语义

用户的困惑点在此，明确三条：

| 目录 | 库前缀 | 谁写 | 本页关系 |
|------|--------|------|---------|
| **企业原始资料目录** | `enterprise-original-source/` | 菜单 ⑤「企业原始资料管理」 | ⛔ **只读**（它是**证据链**，改了就没有审计价值） |

⇒ **「同步到企业的文件夹」= 更新 `cert_standard_directory_file` 企业行的文件指针 + 产物字节落 `enterprise-documents/`。**
⇒ ⛔ **不是**「把产物写回原始资料目录」。

### 5.3 分流：入队之前的三段式


> ⚠️ 我此前把「editable 生成」当成默认路径、把分流写在填充链里，**位置错了**。
> **分流不在填充链里，它在「范围展开」的那一刻**——它决定**哪些文件根本不该进队列**。

#### 2.1 判据链（顺序不可颠倒）

```text
① 这份文档是 fixed 还是 editable？      ← cert_standard_doc_contract.DocCategory（②判断，可人工覆盖）
      ├─ fixed ② 是否可替代？            ← .FixedDocSubtype（standard_provided / enterprise_provided）
      └─ editable ③ 三个前置齐不齐？      ← 模板已发布？锚点数 > 0？（有 ai 节点则还有：汇聚规则存在？）
```

#### 2.2 分流矩阵（**四种去向**，不是一个"全量入队"）

| 类型 | 可替代性 | 进队列？ | 任务性质 | 干跑计数 |
|------|---------|:------:|---------|---------|
| fixed | **`standard_provided`**（非可替代） | ⛔ **不进** | 只做**存在性校验 + 归位**（它本来就该存在） | 不进 `TotalCount` |
| fixed | **`enterprise_provided`**（可替代） | ✅ 进（轻任务） | **匹配 + 归位**（⛔ 不生成）；`ambiguous` 挂待办、**不阻塞批次** | 待人工匹配 |
| editable | —（不适用） | ✅ 进 | **生成** | — |
| editable · 无模板 / 未发布 | — | ⛔ **跳过** | — | `SkippedNoTemplateCount` |
| editable · 锚点 = 0 | — | ⛔ **跳过**（纯复制即可） | — | `SkippedNoAnchorCount` |
| 任意 · 已锁定 | — | ⛔ **跳过** | — | `SkippedLockedCount` |

#### 2.3 为什么必须在入队前

1. **`SkippedNoTemplateCount` / `SkippedNoAnchorCount` 就是分流的产物**——不先在展开阶段分流，这两个数根本算不出来。
2. **"非可替代的 fixed 文档"进队列 = 凭空造一个永远成功的空任务**，污染进度与统计。
3. **干跑 `plan` 必须纯读零副作用** ⇒ 它是 P0 就该做的、且是「一键规范化」的**强制前置**（⛔ 不能跳过直接入队）。

#### 2.4 ★ 标准文档范围的确定（**规则驱动**：167 → 2）

> 用户口径（2026-10-06）：「我们标准文档可能有 100 个文件，但我们**设置规则的文档可能只有 20 个**，那么一个标准下，我们的标准文档是 20 个。**格式，以我们定义的空白文档为准。**」

**先在「标准」这一层收敛，再谈文档**。一个范围内到底有几个「标准文档」，由**后台「标准文档填写规则」**（菜单 `MENU_00218`）声明 ——
⛔ **不是标准目录里有多少文件就算多少**。

```text
① 定标准：范围命中的【标准集合】
     企业级 / 阶段级 → 经 cert_enterprise_stage 推导（★ 可多个，见 §13.7）
     标准 / 文件夹 / 文件级 → 用户直接选中
② 取该【标准 × 阶段】在标准目录下的【全部槽位】
     cert_standard_directory_file WHERE EnterpriseCode='YZH-STD-ENT'
③ ★ 收敛到【配了填写规则的槽位】= 真正进队列的
     有 cert_doc_template 行（StandardFileCode UNIQUE ⇒ 与槽位 1:1）
④ 每份文档「是 fixed 还是 editable / 可否替代」由后台规则声明（§2.1 判据链）
⑤ 格式：⛔ 不是企业上传的原件，而是【空白模板】cert_doc_template.StoragePath
```

| 层 | 数量（实测 2026-10-06） | 事实源 |
|----|:---:|--------|
| 标准目录里该标准 × 阶段的槽位 | **167** | `cert_standard_directory_file`（`EnterpriseCode='YZH-STD-ENT'`） |
| ★ 配了填写规则的（= **真正进队列**的） | **2** | `cert_doc_template`（`StandardFileCode` UNIQUE） |
| 已发布模板（`PublishStatus='published'`） | **0**（2 份均 `scanned`） | 同上 ⇒ 当前**全部会跳过**（`SkippedNoTemplateCount`） |

> ⇒ **队列规模由规则决定，不由目录决定。** 后台没配规则的槽位**不进队列**（它没有被填充的定义），
> 也**不计入完成率分母**（分母 = 有模板的有效锚点数，见 `54` §5.3）。
> ⇒ 所以「一键规范化」的 `TotalCount` **几乎总是远小于**目录里的文件数 —— 这是**正确的**，不是漏算。

### 5.4 队列：两层结构 + 五级范围


#### 3.1 两层（工程口径，避免术语混）

```text
一个【范围】= 一个批次 yzh_queue          ← 只做统计与进度，本身不干活
  ├── 一个【文件】= 一个任务 yzh_queue_task   ← ★ 原子，可独立重试
  ├── 一个文件 = 一个任务
  └── …
```

> 用户口径：「一个文件的规范化是一个队列」→ 工程落地 = **一个文件 = 一个任务**。
> 用户口径：「不同的范围是队列的范围不一样」→ 工程落地 = **范围 = 一个批次**。

#### 3.2 五级范围（★ 2026-10-06 口径修正：**「文件夹」回来了**）

> `ScopeType ∈ {enterprise, stage, standard, folder, file}`；五个层级⛔ 不互相替代。
> ★ **执行队列时排除两类**：`IsLocked=1` 的文件（L2）与 `IsPinned=1` 的锚点（L3）——见 §18.6 / §18.7。

### 5.8 MinIO 三库与 `PathBuilder`

#### 13.1 三库定义（权威源 = `CertPlatform.Shared/Entities/Dir/DocumentLibrary.cs`）

| 库 | 前缀 | 路径形态 | 输入/输出 | 谁写 |
|----|------|---------|:--------:|------|
| **标准目录库** | `standard-directory` | `/standard-directory/{OrgCode}/{StandardCode}/{StageCode}/{FolderPath}/…` | — | 后台（标准目录管理） |
| **企业资料库** | `enterprise-documents` | `/enterprise-documents/{Ent}/{StandardCode}/{StageCode}/{FolderPath}/{FileName}` | **输出** | ★ **本模块** |
| **企业原始资料库** | `enterprise-original-source` | `/enterprise-original-source/{Ent}/{StageCode}/{FolderPath}/{FileName}` | **输入** | 菜单 ⑤ |

#### 13.2 为什么必须分三个库（原文理由，⛔ 不可合并）

```text
① 标准目录库 ≠ 企业侧：一侧是「机构配的标准模板与清单」，一侧是「某企业的实际文件」
② 企业资料库 vs 企业原始资料库 = 输出 vs 输入：
     原始资料按【阶段】组织 —— 企业上传时就是【按阶段】交的，文件本身【不带标准】
        （标准归属由「企业阶段定义」推导，桥 = cert_enterprise_stage，见 §13.7）
     资料库按【阶段 × 标准 × 槽位】组织 —— 因为产物已经归位到标准目录结构
   ⇒ 混库的后果：重新规范化时分不清「哪些是原始、哪些是产物」
③ 原始资料库 = 证据链 ⇒ 【只读不改】（改了就没有审计价值）
```

#### 13.3 ★ MinIO 语义（一个容易误判的点）

> **MinIO/S3 是扁平 key 存储**，控制台按 `/` 分组**显示**成目录。
> ⇒ 「库」只是 **key 的前缀段**；**「建库 / 建文件夹」不需要任何 API 调用**，路径在代码里算好即可。

#### 13.4 路径唯一构造器 = `PathBuilder`（⛔ 禁止手拼）

| 方法 | 产出 |
|------|------|
| `StandardFile(org, std, stage, folderPath, name)` | 标准目录源文件 |
| `TemplateFile(...)` | `/standard-directory/{Org}/{Std}/{Stage}/{Folder}/**_template**/{name}`（空白模板，与源文件**同层级**并列） |
| `EnterpriseFile(ent, std, stage, folderPath, name)` | ★ **本模块产物** |
| `EnterpriseOriginalSource(ent, stage, folderPath, name)` | 原始资料 |
| `Product(storagePath, kind, ext)` | 派生产物：`kind ∈ { pdf, markdown, editable }` |
| `Archive(storagePath, version)` | `…/_archive/{name}.v{n}` |

**五个保留段**（⛔ 文件夹名/文件名不得使用）：`pdf` · `markdown` · `editable` · `_template` · `_archive`

**三段各自的作用（一次说清，这是最常混的）**：

| 段 | 指什么 | 谁生成 | 本模块关系 |
|----|--------|--------|-----------|
| `editable` | **格式归一产物**：`.doc` → `.docx`、`.xls` → `.xlsx`（实测已回填 **167** 份） | 后台归一链 | ★ **喂 NPOI 的字节来源**（`.doc` 连读都读不了） |
| `pdf` | 源文件的**预览 PDF**（实测 185 行在用） | 转换链 | ⛔ **别挤占**（试填 PDF 必须另用 `_preview/`，见 `52` §12.3） |
| `markdown` | 源文件的 **Markdown**（喂 LLM 的正文原料） | 转换链 | ★ AI 节点依赖文档组的素材 |
#### 13.7 ★ 三库的语义链路（用户口径校正，2026-10-06）

> 用户口径：「我们企业上传的材料是**按阶段**进行上传的，**我们企业阶段定义的时候，关联了标准**。」

**这是本册此前没说透的一环**：原始资料**自身不带标准**，但**企业阶段定义带了标准** —— 桥就是 `cert_enterprise_stage`。

| 事实 | 实测 |
|------|------|
| `cert_enterprise_original_file` 的定位列 | `EnterpriseCode` + `StageCode` + `RelFolderPath` —— **无 `StandardCode`** ✅ |
| `cert_enterprise_stage` 三列 | `EnterpriseCode` + `StageCode` + **`StandardCode`**（价值 = 作用域桥） |
| 一个（企业 × 阶段）可关联**几个**标准 | **可多个** —— 实测多组 (企业, 阶段) 各关联 **2 个**标准 |
| 现存行 | **8 行**（其中 `TEST-ENT-0001` 1 行 `active`，其余多组各 2 个标准） |

⇒ **「按阶段上传」+「阶段 → 标准」= 原始资料到标准的唯一推导路径**。⛔ 不要试图从文件本身猜标准。

**完整语义链路（三库各占一段）**：

```text
【输入 · 原始资料库】 /enterprise-original-source/{Ent}/{Stage}/…      ← 阶段级，标准无关
        │
        │  ★ 桥：cert_enterprise_stage(EnterpriseCode, StageCode, StandardCode)
        ▼
【规则 · 后台】 标准目录（standard-directory）该标准 × 阶段的槽位
        │   └ 按「标准文档填写规则」收敛到【配了规则的文档】（167 → 2，§2.4）
        ▼
【输出 · 企业资料库】 /enterprise-documents/{Ent}/{Std}/{Stage}/{Folder}/{FileName}
        └ 导出 = 生成好的标准文档（按标准文档与目录归位）
```

**三库各一句话（因果链，⛔ 方向不可逆）**：

| 库 | 一句话 | 角色 |
|----|--------|------|
| 标准目录 | 「**机构**认为这个标准 × 阶段应该有哪些文档、该长什么样」 | 定义**要什么 + 格式（空白模板）** |
| 企业原始资料 | 「**企业**按阶段交上来的散乱材料」 | 规范化**取值的数据源**（只读证据链） |
| 企业资料库 | 「规范化**跑出来的结果**，按标准文档 × 目录归位」 | **导出物** |

⇒ ⛔ 企业资料库**永不作输入**（否则「重新规范化」分不清原始与产物，§13.2）。
⇒ ⚠️ **实测异常**：企业资料库**已有 18 行**（§13.6），而 `cert_enterprise_original_file` = **0**
⇒ 这 18 行**不可能经本链路产生** ⇒ 开工前必须查明来历，否则干跑 `NewCount`/`RegenCount` 建立在错误前提上。

### 5.9 溯源：存指针，不存副本


#### 15.1 ★ 核心原则：**存指针，不存副本**

原始文档**永不复制第二份**。所有溯源都存**指向**（`Code` / 路径 / 证据片段），否则数据膨胀且必然出现「两份不一致」。

#### 15.2 文件级：一次填充用了哪些原始文档

| 落点 | 列 | 内容 |
|------|----|------|
| `cert_doc_fill_log` | **`RetrievedDocCodes`**（**已有列** ✅） | 本次生成参考过的**全部原始件 Code**（json 数组） |
| `cert_doc_fill_log` | `SkillTrace`（**已有列** ✅） | 逐锚点取值路径轨迹 |
| 宿主 `cert_standard_directory_file` | `SourceProfileCode` | 本次产物用的画像 Code（可多值，逗号分隔，最多 3 个） |
| 宿主 | `SourceOriginalPath` | 对应原始文件路径（**冗余展示用**，⚠️ ⛔ 生成过程**绝不读它**） |

#### 15.3 ★ 字段级：某个单元格的值从哪来（枢纽）

**一行一锚点**，落 `cert_doc_fill_value`：

| 列 | 内容 |

### 5.10 三种「锁」+ 忽略策略

#### 18.1 三种锁的对照

| # | 名称 | 载体 | 层 | 作用 | 谁设 |
|:--:|------|------|----|------|------|
| **L1** | **规则锁定** `IsLocked` | `cert_doc_template_anchor` | **后台·配置层** | 锚点规则**就此冻结**，⛔ 不可再修改配置 | 实施人员（后台） |
| **L2** | **文件锁定** `IsLocked`/`LockedBy`/`LockedTime` | `cert_standard_directory_file` | **专家端·业务层** | 产物已确认，**任何生成路径不得覆盖** | 审核专家 |
| **L3** | **锚点钉住** `IsPinned` | `cert_doc_fill_value` | **专家端·取值层** | 「全部重写」时**跳过本行** | 审核专家 |

> ⛔ **不是文件锁！** L2 是**业务确认**：解锁**不删文件**，只是允许被覆盖，且**必留痕**。
> ⛔ **L1 与 L2 正交**：L1 管「规则能不能改」，L2 管「产物能不能盖」——两者互不代管。

#### 18.2 L1 规则锁定的逻辑控制（已实施，`52` §11.4）

| 判断点 | 行为 |
|--------|------|
| `save-batch` / `UpdateCore` | 提交项命中已锁定锚点且**配置列有实质变化** ⇒ **整批拒绝** + 点名「哪条锚点 / 哪些列」 |
| `clear` | **跳过**锁定行，返回 `SkippedLocked`（⛔ 不静默少删） |
| `scan` 重扫 | 锁定锚点的**配置自动保留**（换版也只更新扫描列） |
| `lock` 动作本身 | **不设前置**（未配来源、孤儿也允许锁，只进 `Warnings`） |
| ⛔ 设计要点 | `IsLocked` **不进** `BatchUpdatableColumns`（否则前端漏传 `isLocked` 会**静默解锁**）；`ConfigDiff` 与落库**共用同一份列清单** |

#### 18.3 L2 文件锁定的逻辑控制（本模块待实施）

| 判断点 | 行为 |
|--------|------|
| **编排器第 ⓪ 步**（锁检查在**最前**） | `IsLocked=1` ⇒ `SkippedCount++` **直接返回**，⛔ 不进 ①②③④ |
| 干跑 `plan` | 计入 `SkippedLockedCount`，UI 文案「跳过 2（已锁定 🔒）」 |
| `run` 批次 | 锁定项**不进任务队列**（连任务都不建） |
| 解锁 | `POST unlock`，**`Reason` 必填**；留痕 `ActionType='unlock'`（**多次解锁 = 多行**） |
| ★ 验收判据 | 「**锁一个文件 → 全量生成 → 该文件 `UpdateTime` 不变**」 |
| 边界 | 锁定项**完成率照常显示** + 🔒 徽标 + tooltip |

#### 18.4 ★ L3 锚点钉住的逻辑控制

**与 `IsOverridden` 的区别（务必分清）**：

| 列 | 语义 | 类别 |
|----|------|------|
| `IsOverridden` | 「值或来源**被人工改过**」 | **事实**（发生过什么） |
| `IsPinned` | 「**重写时不要动它**」 | **指令**（以后怎么办） |
| 可否同时为 1 | ✅ 可以（「人工改了值，并要求以后保留」） | — |

| 判断点 | 行为 |
|--------|------|
| 「全部重写」 | 命中 `IsPinned=1` ⇒ **跳过本行**（五条不覆盖规则之二） |
| 依赖失效处理 | 钉住的行 **⛔ 不清空**（人工确认过 ⇒ 优先） |
| 落库时机 | 点「**更新文档**」时（暂存阶段只写内存） |
| 留痕 | `ActionType='pin'` / `'unpin'` + `AnchorCode` |
| 界面 | 锚点行 🔒 按钮；审计页段②「已锁定锚点」计数 |
| ★ 原型对应 | 审核表的 **「勾选 = 顶住」**：☐ 未勾 ⇒ 资料更新会**清空**它；☑ + 确定性来源 ⇒ **自动顶住**；☑ + 企业资料/AI ⇒ **你认可了**（人工顶住）。空值行勾选框**禁用** |
