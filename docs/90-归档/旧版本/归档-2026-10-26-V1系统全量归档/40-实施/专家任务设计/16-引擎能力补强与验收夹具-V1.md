## 一、五条引擎能力（N1-N5）

### N1 ★ 规则版本化

**问题**：`cert_validation_rule` 无 `Version` 列，`RuleJson` 里内联 DAG 且**被就地改写**。后果：
- 无法回答「这条结论是哪版规则跑的」
- 无法 A/B 对比（改判据 → 重跑 → 比对）
- 配置面是一次性的

**方案**：

```sql
-- cert_validation_rule 加两列
ALTER TABLE cert_validation_rule
  ADD COLUMN `RuleVersion`    int NOT NULL DEFAULT 1 COMMENT '★规则版本号（每次改判据/改DAG递增）',
  ADD COLUMN `RuleContextHash` varchar(64) COLLATE utf8mb4_general_ci DEFAULT NULL
    COMMENT '★DAG 内容指纹（SHA256 前 64 位），用于识别「同版本不同内容」的异常',
  ADD KEY `idx_version` (`Code`, `RuleVersion`);
```

**版本化策略（3 选 1，本期选 ②）**：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 原地递增 | 改 `RuleJson` 时 `RuleVersion+1` | ⚠️ 旧版内容丢了，无法复现 |
| ② **★ 版本行表** | 规则主表存 `RuleVersion`；改判据时**新增** `cert_validation_rule_version` 历史行 | 完整可复现，多 1 张表 |
| ③ 复用工作流版本 | `RuleJson` 只存 `wf_workflow_definition.Version` 引用 | DAG 部分有版本，判据部分仍无 |

**② 的表**：

```sql
CREATE TABLE cert_validation_rule_version (
  Id bigint NOT NULL AUTO_INCREMENT,
  Code varchar(36) NOT NULL COMMENT '版本行编码',
  OrgCode varchar(50) NOT NULL,
  RuleCode varchar(36) NOT NULL COMMENT '★对应 cert_validation_rule.Code（外键）',
  RuleVersion int NOT NULL COMMENT '版本号（1,2,3…）',
  RuleJson text COMMENT '★该版本的 DAG 快照',
  NcDescriptionTemplate text,
  SeverityIfViolated varchar(20),
  JudgeMode varchar(20),
  RuleContextHash varchar(64) COMMENT 'DAG 指纹',
  ChangeBy varchar(50), ChangeByName varchar(100), ChangeTime datetime,
  ChangeReason varchar(500) COMMENT '★改判据的理由（专家填写）',
  IsValid int NOT NULL DEFAULT 1, IsDeleted tinyint(1) NOT NULL DEFAULT 0,
  CreateTime datetime DEFAULT CURRENT_TIMESTAMP, UpdateTime datetime,
  Sort int DEFAULT 0, Remark varchar(500),
  PRIMARY KEY (Id), UNIQUE KEY uk_code (Code),
  UNIQUE KEY uk_rule_version (RuleCode, RuleVersion),
  KEY idx_rule (RuleCode, IsValid, RuleVersion)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  COMMENT='NC检查规则版本历史';
```

**任务项落库时快照版本**：

```
cert_expert_nc_result 增两列：
  RuleVersion      int          -- ★执行时读到的 RuleVersion
  RuleContextHash  varchar(64)  -- ★DAG 指纹（判重「同版本不同内容」）
```

### N2 ★ 字段/表格槽位字典

**问题**：`fieldCode` / `tableCode` 在规则侧与提取侧**各写各的自由文本**。平台交给专家自助配置后：
- 拼错编码 → 永远判缺，或永远判不缺
- **没有任何一处会报错**

**方案**：新增槽位字典表，规则编辑器与提取规则**都从字典选，不允许自由输入**。

```sql
CREATE TABLE cert_extract_field_slot (
  Id bigint NOT NULL AUTO_INCREMENT,
  Code varchar(36) NOT NULL COMMENT '★槽位编码（规则与提取共用的唯一键）',
  OrgCode varchar(50) NOT NULL,
  SlotType varchar(20) NOT NULL COMMENT '★field | table',
  SlotName varchar(200) NOT NULL COMMENT '槽位名（界面显示）',
  -- 归属：挂在哪套标准文件要求下
  StandardCode varchar(36) NOT NULL,
  StageCode    varchar(36) NOT NULL,
  StandardFileCode varchar(200) DEFAULT NULL COMMENT '★应来自哪个标准文件（cert_standard_file.Code）',
  FileTypeCode varchar(36) DEFAULT NULL COMMENT '文件类型（手册/程序/记录…）',
  -- 类型与结构
  ValueType    varchar(20) DEFAULT 'text' COMMENT 'text | number | date | bool | json | table',
  Unit         varchar(50) DEFAULT NULL COMMENT '单位（如 mm / % / 天）',
  TableColumnDefs json DEFAULT NULL COMMENT '★表格槽位的列定义 [{Key,Name,Type}]',
  -- 校验
  IsRequired   tinyint(1) NOT NULL DEFAULT 1 COMMENT '★是否必填（完备性检查依据）',
  ValidationRule json DEFAULT NULL COMMENT '校验规则（正则/范围/枚举）',
  Sort int DEFAULT 0, Remark varchar(500),
  CreateBy varchar(50), CreateTime datetime DEFAULT CURRENT_TIMESTAMP,
  UpdateBy varchar(50), UpdateTime datetime,
  IsValid int NOT NULL DEFAULT 1, IsDeleted tinyint(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (Id), UNIQUE KEY uk_code (Code),
  UNIQUE KEY uk_slot (OrgCode, StandardCode, StageCode, StandardFileCode, SlotType, SlotName),
  KEY idx_scope (OrgCode, StandardCode, StageCode, IsValid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  COMMENT='★提取槽位字典（规则与提取的共用编码入口）';
```

**接入点**：

| 位置 | 改造 |
|---|---|
| `cert_doc_extraction_rule` 的字段定义 | `FieldCode` 改为从 `cert_extract_field_slot` 下拉选择 |
| `rpt_report_section.WorkflowConfig` 的 `docfield` 节点 | `fieldCode` 改为下拉选择（**不是自由输入**） |
| 完备性检查 | 按 `cert_extract_field_slot.IsRequired` 判定是否算缺口 |
| 提交前校验 | 端点校验 `fieldCode` 在字典中存在，否则 400 `SLOT_NOT_IN_DICT` |

> **收益**：专家拼错编码在**保存时就报错**，不是等到跑不出结果才发现。

### N5 ★ 执行幂等与轮次

**问题**：`wf_execution_task_item` **无幂等键**。重跑 / 租约到期 / 路径复用分支重试 → **重复调 LLM、重复插 NC**。

**方案**：

```sql
-- ① 引擎层幂等键（★ 注意与业务轮次区分）
ALTER TABLE wf_execution_task_item
  ADD COLUMN `Attempt` int NOT NULL DEFAULT 1 COMMENT '★引擎内重试次数（幂等键组成）',
  ADD COLUMN `IdempotencyKey` varchar(64) NOT NULL DEFAULT '' COMMENT '★幂等键 = SHA256(TaskCode|ItemCode|Attempt)',
  ADD UNIQUE KEY `uk_idem` (`IdempotencyKey`),
  ADD COLUMN `Committed` tinyint(1) NOT NULL DEFAULT 0 COMMENT '★是否已原子提交（0=暂存，1=已提交）';
```

> ⚠️ **关键区分**（我原设计混淆了）：
> | 概念 | 归属 | 含义 |
> |---|---|---|
> | `Attempt` | **引擎层** | 同一次执行内重试第几次（防重复调 LLM） |
> | `RoundNo` | **业务层**（`cert_expert_nc_result.RoundNo`） | 跨任务的业务轮次（历史累积） |
>
> 二者**独立编号，不共用**。幂等键里用 `Attempt`，不用 `RoundNo`。

**② 原子提交**：

```csharp
// 结果先落暂存（Committed=0），全部节点成功后原子提交（Committed=1）
// 中途失败 → 暂存行作废，不产生半成品结果
await _wfService.CommitOrDiscardAsync(taskCode, success: allNodesOk);
```

**③ 重跑只追加轮次**：

```
重跑某条规则：
  ① 引擎层：Attempt+1，IdempotencyKey 重算 → 不与历史冲突
  ② 业务层：cert_expert_nc_result 新增 RoundNo=n+1 的行
  ③ ⛔ 旧轮次永不修改（审计要求）
```

## 二、引擎资产与本设计的分工（消除重复造轮子）

| 能力 | ★ 用引擎（`wf_*`） | 用本设计（`cert_expert_*`） |
|---|---|---|
| 节点级执行留痕 | ✅ `wf_node_execution` | ⛔ 不建 |
| 分支路径追踪 | ✅ `wf_path_execution` | ⛔ 不建 |
| AI prompt/输出/token | ✅ `wf_node_execution` | ⛔ 不建 |
| **文件/字段级数据溯源** | ✅ `SourceFileCode`/`SourceFieldName`/`SourceVersion` | ⛔ **不用建**（D08 说的追溯，引擎免费给） |
| 幂等与重试 | ✅ `wf_execution_task_item.Attempt` | ⛔ 不建 |
| **专家认可/修改记录** | ⛔ 引擎不管 | ✅ `cert_expert_task_log` |
| **业务轮次累积** | ⛔ 引擎不管 | ✅ `cert_expert_nc_result.RoundNo` |
| **跳过原因分类** | ⛔ 引擎不管 | ✅ `SkipCategory` |
| **补录清单** | ⛔ 引擎不管 | ✅ `cert_expert_task_data_gap` |
| **存续状态（归档/作废/取消）** | ⛔ 引擎不管 | ✅ `LifecycleStatus` |

> ⛔ **`cert_expert_task_log` 的动作枚举修订**：
> | 动作 | 处置 |
> |---|---|
> | `AUTO_GENERATE` | ⛔ **删除**（原始输出在 `wf_node_execution.OutputJson`） |
> | `AUTO_FAIL` | ⛔ **删除**（失败节点在 `wf_path_execution.FailedAtNodeId`） |
> | `ACKNOWLEDGE` / `MODIFY` | ✅ 保留（专家动作，引擎不管） |

### 3.3 夹具的验收判据（一次跑完的 checklist）

```
□ C1  docfield 节点 SourceFileCode 正确，OutputJson 等于夹具文件里的值
□ C2  wf_path_execution.NodeIds 序列 = 预期 DAG 拓扑序
□ C3  doctable 节点取到表格行数与预期一致
□ C4  AiPrompt 非空 / token 双向 > 0 / 结论值在枚举内
□ C5  data_gap: pending → filled，且对应 item 不再 skipped
□ C6  坏节点 → permanent failed；同任务其他项正常完成；任务到 pending_review
□ C7  2 个标准 2 个队列都 completed
□ C8  导出 Excel：Sheet 数 = 标准数；含「未检查清单」段
□ C9  ReusedCount > 0；LLM 调用次数 < 节点数（证明复用生效）
□ C10 RuleVersion 1→2；RoundNo 1→2；旧轮次未被修改（校验 RuleContextHash 变化）
```

> **回归用法**：任何改动 `WorkflowInterpreter` / `NodeExecutor` / `AiNodeExecutor` / `EnterpriseExtractionResultStore` 之后，**跑一遍 C1-C10**，10 项全绿才算没破坏。
