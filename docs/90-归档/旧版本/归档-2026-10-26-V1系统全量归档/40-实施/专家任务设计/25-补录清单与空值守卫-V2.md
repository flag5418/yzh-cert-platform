## 二、核心机制：`R \ H` 差集

### 2.1 三段定义

```
R（需求集）= ∪ { 本次任务内 itemCode 的 DAG 里所有 docfield / doctable 节点 }
H（已有集）= 企业在 (OrgCode, StandardCode, StageCode) 范围内、
             按 RuleCode 收窄后的有效值（人工优先）
G（缺口）  = R \ H
```

### 2.2 ★ `R` 必须按 `itemCodes` 局部收集（性能与可用性前提）

**⛔ 禁止按标准全量收集规则**。一次局部 NC 检查（5 条规则）只应产出这 5 条规则引用的字段缺口；若是 40 条规则的标准全量，清单会膨胀到数百行，无法使用。

这正是「本次是局部 NC 或局部报告章节」的业务诉求：**只需要通过 NC 检查项 / 章节检查项分析出需要哪些信息**。

依赖收集伪码（对齐 `NodeExecutor.cs:93-102` 的实测节点类型）：

```csharp
IReadOnlyList<DataDependency> CollectDependencies(string taskType, IReadOnlyList<string> itemCodes)
{
    // ① 取 DAG 文本（★ 两表列名不同）
    //    NC_CHECK       → cert_validation_rule.RuleJson
    //    REPORT_GENERATE → cert_report_section.WorkflowConfig
    // ② WorkflowConfigParser.Parse
    // ③ 遍历节点，★ 节点类型必须 ToLowerInvariant()（DB 实测是 "docField" 驼峰）
    foreach (var node in dag.Nodes)
    {
        switch (node.NodeType?.ToLowerInvariant())
        {
            case "docfield":
                deps.Add(new DataDependency(
                    GapType:   "field",
                    RuleCode:  GetConfig(node, "ruleCode"),      // ★ J4：RuleCode 是主键
                    FieldCode: GetConfig(node, "fieldCode"),
                    NodeId:    node.NodeId));
                break;

            case "doctable":
                deps.Add(new DataDependency(
                    GapType:   "table",
                    RuleCode:  GetConfig(node, "ruleCode"),
                    TableCode: GetConfig(node, "tableCode"),
                    NodeId:    node.NodeId));
                break;

            case "start": case "end": case "branch":
            case "skill":  case "ai_node":
                break;   // 不产生数据依赖

            default:
                // ★ 未知节点类型不静默跳过，登记 GapType="unknown" 待人工确认
                deps.Add(new DataDependency(GapType: "unknown", NodeId: node.NodeId,
                    Remark: $"未识别的节点类型 {node.NodeType}"));
                break;
        }
    }
    return deps;
}
```

> ⚠️ **`ruleCode` 是 `R` 的主键成分**。`NodeExecutor.ExecuteDocFieldAsync` 本来就用 `config.ruleCode` 查库，依赖收集与执行侧同源，不会分叉（05 号未定义 `RuleCode`，此处补齐）。

### 2.3 ★ `H` 的取值口径（J4 · 唯一口径）

```sql
-- 字段级
SELECT * FROM cert_extraction_result
 WHERE OrgCode      = @enterpriseCode
   AND RuleCode     = @ruleCode            -- ★ J4：规则级收窄，取代 FileCode
   AND FieldCode    = @fieldCode
   AND IsValid      = 1
   AND IsDeleted    = 0
 ORDER BY (ValueSource = 'manual') DESC,  -- ★ 人工值优先
          VersionNumber DESC
 LIMIT 1;

-- 表格级
SELECT * FROM cert_table_extraction_result
 WHERE OrgCode   = @enterpriseCode
   AND RuleCode  = @ruleCode
   AND TableCode = @tableCode
   AND IsValid   = 1
 ORDER BY (ValueSource = 'manual') DESC,
          VersionNumber DESC, TableIndex DESC
 LIMIT 1;
```

**为什么按 `RuleCode` 而不是 `FileCode`**：

| 维度 | `FileCode` | ★ `RuleCode` |
|---|---|---|
| 补录行有值吗 | ❌ 企业未上传该文件 ⇒ 无值（J3 已否决虚拟文件） | ✅ 恒有 |
| 1:1 保证 | ❌ 一个企业可有多个文件 | ✅ `uk_rule_scope` 唯一索引强制 |
| 同名 `FieldCode` 串扰 | ⚠️ 跨文件可能同名 | ✅ 规则级天然隔离 |
| 覆盖文件的清理键 | ❌ 补录行的 `FileCode` 是"凑"出来的 | ✅ 同一把钥匙 |

### 2.4 ★ 判空：复用既有 Skill 原语，⛔ 不写第三份

仓库已有三态判定原语，**质量优于 05 号 §2.4 的伪代码**：

| 组件 | 位置 | 能力 |
|---|---|---|
| `wf_skill.is_field_empty` | `ExistenceJudgeSkills.cs:129` | 三态 `has_value` / `is_empty` / `not_found` |
| `wf_skill.is_table_empty` | `ExistenceJudgeSkills.cs:230` | 三态 + `row_count` / `column_count` |
| `EmptyJudge.IsBlankText` | `ExistenceJudgeSkills.cs:78` | 识别 `-` `——` `/` `N/A` `无` `暂无` `待填写` `待补充` `待上传`、纯符号、正则 `^(待\|需要\|请)\S{0,6}(填写\|补充\|上传\|提供)` |

**⭐ 这同时修掉 B3**：`IsBlankText` 的占位符识别让 `[{"item":"","value":""}]` 这类"伪非空"能被判为缺。

> **铁律**：守卫（`NodeExecutor`）与清单生成（`GapDetector`）**必须调用同一个 `ExtractionDataResolver`**，⛔ 禁止各写一份判空。否则会出现「清单说齐了、执行说缺了」。

### 3.3 覆盖文件时按 `RuleCode` 清理（J4）

```csharp
/// <summary>★ 按规则归档（J4：1 文件 = 1 RuleCode，uk_rule_scope 保证唯一）</summary>
public async Task<int> InvalidateByRuleAsync(string enterpriseCode, string ruleCode, int? upToVersion = null)
{
    var now = DateTime.Now;
    var f = _db.Client.Updateable<ExtractionResult>()
        .SetColumns(x => new ExtractionResult { IsValid = 0, UpdateTime = now })
        .Where(x => x.EnterpriseCode == enterpriseCode && x.RuleCode == ruleCode && x.IsValid == 1);
    var t = _db.Client.Updateable<TableExtractionResult>()
        .SetColumns(x => new TableExtractionResult { IsValid = 0, UpdateTime = now })
        .Where(x => x.EnterpriseCode == enterpriseCode && x.RuleCode == ruleCode && x.IsValid == 1);
    if (upToVersion.HasValue)
    {
        f = f.Where(x => x.VersionNumber <= upToVersion.Value);
        t = t.Where(x => x.VersionNumber <= upToVersion.Value);
    }
    return await f.ExecuteCommandAsync() + await t.ExecuteCommandAsync();
}
```

**软归档 vs 物理删**：本文按 **软归档（`IsValid=0`）** 设计，与既有 `EnterpriseExtractionResultStore` 铁律「行数永不减少」一致。人工值被归档时记 `ChangeAction='archive'` 到 `cert_extraction_change_log`。

## 四、`cert_expert_task_data_gap` 粒度修正（J1）

### 4.1 记录粒度：`FieldCode × SourceItemCode` → `FieldCode`

| 项 | 05 号 / 现行 DDL | ★ 本文（J1） |
|---|---|---|
| 记录粒度 | 1 条 = 1 个（字段 × 依赖它的规则） | **1 条 = 1 个待补字段/表格** |
| `GapKey` 生成列 | `CONCAT(GapType,'|',FieldCode,'|',TableCode,'|',SourceItemCode)` | `CONCAT(GapType,'|',RuleCode,'|',IFNULL(FieldCode,'-'),'|',IFNULL(TableCode,'-'))` |
| 唯一键 | `uk_gap(TaskCode, GapKey)` | **不变**（唯一键本身够用） |
| 「影响 N 条规则」 | 落库（多条 gap 聚合） | **前端按 DAG 实时反查** |

**为什么降粒度**：落 `SourceItemCode` 就必须维护「规则改了 → 同步 gap 表」的耦合；规则是业务配置、变动频繁，gap 是任务快照，两者生命周期不一致 ⇒ 必然漂移。改为实时反查后，规则一改前端立刻正确。

### 4.2 「不分文档」的具体含义

| 项 | 处理 |
|---|---|
| 清单**形态** | 两张扁平表：**字段清单** + **表格清单**。⛔ 不按文档分组、不做文档树 |
| `StandardFileCode` | 保留为**只读提示列**（「此字段本应来自哪个标准文件」），**不作为分组键、不作为存储键** |
| `ExpectedFileName` | 同上，提示用 |
| 补录路径 | 按 `RuleCode + FieldCode/TableCode` 定位（§3.1），**与文件无关** |

### 6.2 ★ 提交执行：软提示，不阻断

**⛔ 取消 05 号 §2.3 的 `409 DATA_GAP_UNRESOLVED` 硬阻断。** 理由（J1 语义）：补录清单是**信息**，不是**门禁**；客户可以忽略（用户原话）。改为：

```
POST /api/Auditor/ExpertTask/{code}/submit
  → 正常入队，响应附加：
     { gapCount: n, warning: "有 {n} 项数据未补录，依赖它们的检查项执行时会自动失败" }
```

**真正的门禁在执行期**（§六 6.3）。

### 6.3 ★ 执行期空值守卫：自动失败

`docfield` / `doctable` 节点取不到可用值 ⇒ **抛 `WorkflowDataMissingException` ⇒ 该任务项自动失败**，错误文案「缺失必要数据：字段「X」…请先补录」。

**⛔ 阻塞项**：`NodeExecutor.cs:118` 的 `catch (Exception ex)` 会把异常吞成字符串，`DataKind`/`DataCode`/`Reason`/`StandardFileCode` 七个属性全丢。必须先放行：

```csharp
catch (WorkflowDataMissingException)
{
    throw;                       // ★ 语义异常必须穿透，供上层分类
}
catch (Exception ex)
{
    …现有吞异常逻辑…
}
```

⚠️ 因此 `WorkflowInterpreter`（`catch` 数 = 0）需在 `ExecuteItemAsync` 外层或 `WfExecutionTaskService.cs:137` 处接住，落成 `cert_expert_task_data_gap` 一行（`GapStatus='pending'`）**并把该任务项标记为 `failed`**。

**失败分类码**（无它则正反信号无法在 UI 区分）：

| `ErrorCode` | 含义 | UI |
|---|---|---|
| `DATA_MISSING` | 引用的字段/表格为空 | 红 · 去补录 |
| `SYSTEM_ERROR` | 取数异常 / 配置错误 | 灰 · 报 bug |

> **为什么必须先分分类**：B1 未修时「故意造的缺」和「口径错配造成的缺」报的是同一句话，夹具等于没有信号。分类码是夹具有效性的前提。

| 7 | `ExpertItemExecutors` 的 `HandleDataMissingAsync` 走**实时补登**而非只标 `failed` | 兜底：规则可能中途被改、或补录后数据又被重新提取冲掉。靠 `uk_gap(TaskCode, GapKey)` 幂等 |
