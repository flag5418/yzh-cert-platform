## 一、提取状态机修正（用户第 C 轮裁决）

### 1.1 问题

旧实现只有 **3 态**（`none` / `completed` / `skipped`），且 `EnterpriseExtractStatus.Normalize` 把 `failed` **抹成 `none`**。

后果：执行器报了失败，但 DB 存的是 `none`，前端显示「未提取」—— **用户以为根本没跑，实际跑了但失败了**。

### 1.2 用户裁决

> 「1、提取失败，是有提取规则，但执行的时候，失败了，可能是文档内容和标准目录结构完全不同，或者该文档不能解析等，2、重跑，3、加入重试，4、优化界面」

**最终口径**（经后续澄清确认）：

| 场景 | DB 状态 | 页面显示 | 说明 |
|---|---|---|---|
| 无可用规则 | `skipped` | **未配置** | 不算失败，忽略 |
| 有规则 + 文档不能识别（转不出 markdown） | `failed` | **提取失败** | 失败原因 = **解析失败** |
| 有规则 + 有正文但执行失败（AI 返回空 / 不匹配） | `failed` | **提取失败** | 可重试 |
| 执行成功 | `completed` | **已提取** | — |
| 尚未提取 | `none` | **未提取** | — |
| 队列中 | — | **提取中** | 由资源锁判定，非 DB 态 |

### 1.3 实施

#### 后端

- **`CertPlatform.Shared/DocExtraction/EnterpriseExtractStatus.cs`**：3 态 → **4 态**。`Normalize` 原样保留 `failed`；`ForDisplay` 同步。
- **`CertPlatform.Auditor/Services/Ent/EnterpriseFileService.cs`**：
  - `ExtractStateRule.Of` **改为直接读后端 `rawExtractStatus`**（不再依赖 `ruleMap` 命中）⇒ 输出 5 态；`lockedFiles` 仍优先判 `queued`。
  - DTO `StandardDirectoryFileView` 补 `ExtractMessage`（页面 tooltip 用）。
- **`CertPlatform.Auditor/Services/Ent/EnterpriseExtractTaskExecutor.cs`**：
  - 解析失败分支细化：`MarkdownStatus='unsupported'`（格式不支持）/ `'failed'`（转换失败）/ `'none'`（尚未转换）。
  - `unsupported` / `failed` ⇒ `retryable: false`（重传文件，不是重试）。
  - 取 `MarkdownMessage`（转换器原始报错，截断 120 字）优先显示。
  - **真实 bug 修复**：留痕判断 `st is "completed" or "none" or "skipped"` **漏了 `"failed"`** ⇒ 已补。

#### 前端

- `cert-share/src/api/ent/enterprise-file.ts`：
  - `FileSlot` 补 `ExtractMessage`。
  - `SLOT_STATUS_TEXT.markdownFailed` 文案 `'提取失败'` → **`'缺 Markdown'`**（与新的提取状态列撞名，已消歧）。
- `cert-auditor/src/pages/resources/components/StandardFolderTree.vue`：
  - `EXTRACT_STATE_TEXT` 加第 5 态 `failed: { text:'提取失败', type:'danger' }`。
  - 新增 `extractTip(row)` 按状态给专家看得懂的 tooltip。
  - 操作列 `failed` 时按钮显示**红色「重试」**（复用 `emit('extract')`）。
- `cert-auditor/src/pages/resources/logic.ts`：`handleTriggerExtract` 按 `ExtractState==='failed'` 区分「已重新提交提取」/「提取已入队」。
- `cert-auditor/src/pages/resources/index.vue`：4 处提示文案精简（常驻橙条 / 空 Tab / M0–M3 弹窗 / 未归属说明）。

### 1.4 重跑历史 `none` 槽位

- 脚本 `scripts/db/fix/rerun-extract-none-20260930.py`（新建）：真入队（`yzh_queue` + `yzh_queue_task` + `yzh_queue_resource_lock`），不硬改状态。
- **关键教训 1**：`docker exec` 必须带 `-i`。缺它 ⇒ stdin 不转发 ⇒ 容器内 mysql 空跑、`exit 0`、无 stderr ⇒ **脚本报成功但 DB 一行没写**。已加「写入回查校验」兜住。
- **关键教训 2**：`cert_standard_directory_file` 同时承载两个域：
  - `EnterpriseCode='YZH-STD-ENT'` = **标准目录模板行**（路径 `/standard-directory/…`，**168 行，不做企业提取**）。
  - `EnterpriseCode=<真实企业 Code>` = **企业资料槽位行**（路径 `/enterprise-documents/…`）。
  - 初版脚本未排除模板域 ⇒ 候选算成 173 个；加 `EnterpriseCode <> 'YZH-STD-ENT'` ⇒ **真实候选 11 个**。
- 结果：11 个队列全部 `completed`，11 个槽位 `none` → `skipped`；**企业域 `none` 清零**。

## 二、工作流空值守卫与取数口径修正

### 2.1 问题

旧实现（`NodeExecutor.cs:342`）：

```csharp
var field = (await _db.GetOneAsync<ExtractionResult>(x =>
    x.FieldCode == fieldCode && x.EnterpriseCode == enterpriseCode)).Data;
if (field == null) throw new InvalidOperationException("未找到提取字段...");
```

**三个致命缺陷**（05 号 §2.2 已记录但**未编码修复**）：

| 缺陷 | 后果 |
|---|---|
| 无 `IsValid=1` 过滤 | 读到归档旧版本（文件替换后旧行还在 `IsValid=0`）⇒ **拿旧文件数据算新结论** |
| 无 `StandardCode`/`StageCode` | 多标准 / 多阶段互相串 |
| 记录存在但值为空 ⇒ 返回 `""` | **流程照常跑完，结论却是错的**（用户原话：「虽然不影响流程的执行，但对结果有非常严重的影响」） |

**实测**：`2ac77e26`（附录三 程序文件清单.doc）的 `ExtractedValue` 实际为空 ⇒ 但流程给它喂进 NC 检查 ⇒ AI 对着空值给出随机结论。

### 2.2 实施

#### ① 新建 `WorkflowDataMissingException`

- 路径：`src/certplatform-api/CertPlatform.Shared/Exceptions/WorkflowDataMissingException.cs`
- 语义：这不是系统故障、也不是「不符合」，而是 **无法判定**。因此工作流必须**自动失败**，⛔ 不得产出看似正常的结论。
- 属性：`DataKind`（field/table）、`DataCode`、`Reason`（not_found/is_empty）、作用域信息。
- 上层用法：未来 `catch (WorkflowDataMissingException ex)` 即可按码生成 `cert_expert_task_data_gap`。

#### ② `ExecuteDocFieldAsync`

```csharp
// 新增：从上下文取 StandardCode / StageCode（上下文键是 phaseCode → DB 列是 StageCode）
var standardCode = contextParams?.GetValueOrDefault("standardCode")?.ToString() ?? "";
var stageCode    = contextParams?.GetValueOrDefault("phaseCode")?.ToString() ?? "";

// 取数口径修正：粗取后内存精过滤（05 号 §2.2 唯一口径）
var candidates = (await _db.GetListAsync<ExtractionResult>(x =>
    x.FieldCode == fieldCode && x.EnterpriseCode == enterpriseCode)).Data ?? new();
var field = candidates
    .Where(x => x.IsValid == 1 && !x.IsDeleted)
    .Where(x => string.IsNullOrEmpty(standardCode) || x.StandardCode == standardCode)
    .Where(x => string.IsNullOrEmpty(stageCode)    || x.StageCode    == stageCode)
    .OrderByDescending(x => x.VersionNumber)
    .FirstOrDefault();

// 空值守卫：无记录
if (field == null)
    throw new WorkflowDataMissingException("field", fieldCode, "not_found",
        "缺失必要数据：字段「…」没有提取记录，无法执行判定，请先补录…");

// 空值守卫：有记录但值为空（旧实现这里返回 "" ⇒ 流程跑完 ⇒ 结论错）
if (string.IsNullOrWhiteSpace(field.ExtractedValue))
    throw new WorkflowDataMissingException("field", fieldCode, "is_empty",
        "缺失必要数据：字段「…」的提取值为空，无法执行判定，请先补录",
        standardFileCode: field.StandardFileCode, ...);
```

#### ③ `ExecuteDocTableAsync`

- 取数口径：同 docField —— `IsValid=1` + `StandardCode` + `StageCode`（注：表格实体无 `IsDeleted`）。
- 空值守卫：`table == null` ⇒ `not_found`；`rows.Count == 0` ⇒ `is_empty`。
- `OrderByDescending(x => x.VersionNumber).ThenByDescending(x => x.TableIndex)`（支持同名多表格取最新）。

#### 向后兼容

- `standardCode` / `stageCode` 为空时 → 不过滤，不影响现有测试。
- `GetOneAsync` 改为 `GetListAsync` + 内存过滤 → 单个企业单个字段的结果行通常 ≤5，性能影响可忽略。

## 四、待编码项与优先级建议

按**杠杆率**（对 10/15 死线的贡献 / 工作量）排序：

| 优先级 | 项 | 工作量 | 前置条件 |
|---|---|---|---|
| **P0** | `WorkflowInterpreter` 捕获 `WorkflowDataMissingException` ⇒ 写 `cert_expert_task_data_gap` | 0.5d | 无（异常类型已建） |
| **P0** | 专家任务创建时生成补录清单（`IsManual=1` 的字段/表格 vs 企业已采集信息比对） | 1d | 无 |
| **P1** | `cert_extraction_change_log` 表 + 实体 | 0.5d | 无 |
| **P1** | 补录端点（`fill` / `batch-fill` / `skip`） | 1d | 需 `change_log` 表 |
| **P2** | 前端缺口/补录页 | 1–2d | 需后端端点 |
| **P2** | `cert_table_extraction_result` 补 `IsManualEdited` + `ValueSource` | 0.5d | 无 |

**关键约束**：`cert_doc_extraction_rule` **全库仅 1 条规则**（覆盖率 ≈ 0.6%）。⇒ 现在做缺口生成，跑出来的**补录清单基本是空的**。

**建议**：
1. **先提规则覆盖率**（业务配置，非开发工作）—— 规则不上去，先把补录链路做出来也是空转。
2. 与此同时做 **P0 两项**（异常捕获 + 清单生成），规则配上去后清单立刻有内容。
3. **前端补录 UI 延后**—— 对着空数据做界面，产出不可验证。
