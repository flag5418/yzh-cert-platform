## 一、你的判断对在哪：为什么"一个流程难生成几种结果"

这不是工程能力问题，是 **LLM 的固有特性 + 编排的耦合代价**。四个根因：

| # | 根因 | 具体表现 |
|---|---|---|
| 1 | **输出格式不稳定** | 要求一次输出 N 个章节的 JSON（嵌套 2 层、含数组）⇒ 嵌套越深越容易截断/漏字段。1 个章节的输出 schema 是扁平的，10 个章节就要 3 层嵌套 |
| 2 | **上下文注意力分散** | 一条 prompt 里塞 5 个章节的素材 ⇒ 模型会把章节 A 的素材写进章节 B（样本里"地址两个省"就是人干这事的翻版） |
| 3 | **失败无法定位** | 一个节点失败 ⇒ 整条流程失败 ⇒ **不知道是哪个章节出的问题**。重跑也只能整条重跑 |
| 4 | **输出是一坨** | 拿到一个长文本，无法回答"章节 3 单独跑出来是什么" ⇒ **无法独立测试** |

**"一个章节一个 LLM" 同时解决这四条**：

| 问题 | 分章后 |
|---|---|
| 输出格式 | 每个章节 schema 扁平（`{title, items[], confidence}`） |
| 注意力 | 上下文只含这一章节的素材 |
| 失败定位 | 章节级状态，失败的是哪一个一目了然 |
| 可测性 | **给一段文本就能单独跑一个章节** |

> ★ 这是分治（divide and conquer）的经典收益。你说"这种比较好实现"，**对，而且不是"比较好"，是"唯一能测的"**——因为整条跑的时候，你没法知道某一段输出到底是谁产生的。

## 二、★ 关键发现：三种执行单元的入口**系统里都已经有了**

你说的"每一项可以针对一个工作流，或是一个节点，或一段固定文本" —— 这三种能力**不需要新建**：

| 执行单元 | 现成入口 | 位置 | 返回类型 |
|---|---|---|---|
| **一个工作流** | `CreateAndRunAsync(request, ct)` | `WfExecutionTaskService.cs:158` | `TaskExecutionResponse` |
| **一个节点** | `RunSingleNodeAsync(request, ct)` | `WfExecutionTaskService.NodeScope.cs:112` | `NodeScopeRunOutcome` |
| **一个 AI 节点** | `RunAiNodeAsync(...)` | 同文件 `:249` | `NodeScopeRunOutcome` |
| **一段固定文本** | 不需要引擎 | 直接构造 | — |

而且 `RunSingleNodeAsync` 的实现**正是你要的"独立测试"语义**：

```csharp
// WfExecutionTaskService.NodeScope.cs:112-139（节选）
public async Task<NodeScopeRunOutcome> RunSingleNodeAsync(NodeTestRequest request, CancellationToken ct = default)
{
    var nodeConfig = new WorkflowNodeConfig { NodeId = ..., NodeType = ..., Config = ..., Inputs = ... };
    var parsed = BuildSyntheticWorkflow(new[] { nodeConfig });   // ★ 单节点合成一条伪路径
    var cacheKeys = await BeginRunAsync(...);                    // 落库（可回溯）
    var result = await _nodeExecutor.ExecuteAsync(nodeConfig, taskCode, itemCode,
        new Dictionary<string, object>(),   // ★ 无上游（独立执行）
        contextParams, ct);
    ...
}
```

注释里写明了两件对我们极其有利的事：

> 「**伪路径设计**：单节点测试的 PathResults 只有一条路径…因此前端 `ExecutionResultPanel` 无需为「节点测试」写分支判断。」
> 「**不走 WorkflowConfigParser.Parse**：单节点测试前端只传目标节点…走解析器会被拓扑校验挡掉。」

⇒ **"一项独立执行 + 独立输出 + 独立落库 + 前端无分支"这套语义，已经是现成能力。** 我们要做的只是**在检查表业务里调用它**。

## 三、执行单元模型

### 3.1 三种类型

```csharp
public enum ExecUnitType
{
    StaticText,   // 固定文本，零 LLM
    SingleNode,   // 单节点（含 ai_node），1 次调用
    Workflow      // 多节点 DAG，N 次调用
}
```

### 3.2 选择依据（给配置人员的一句话判据）

| 场景 | 用哪个 | 判据 |
|---|---|---|
| 证据是**固定表述/不适用/说明性文字** | `StaticText` | 不需要从企业文档取任何东西 |
| 需要**从文档里抽一段** | `SingleNode` | 一次抽取就够，不需要判"文件在不在" |
| 需要**先判存在再抽取再校验** | `Workflow` | 有前置判断或多步串联 |

> ⚠️ **`StaticText` 的合规红线**：它**只能用于非证据内容**（提示语、过渡句、"不适用"结论）。⛔ **不能用它写证据正文** —— 那就是编造，违反 31 号「无出处不得输出」。这条必须写进配置校验（保存时检查：`StaticText` 且 `IsEvidence=true` ⇒ 拒绝）。

### 3.3 配置示例（真实条款 4.2.4 拆 2 章节）

## 四、统一输出契约（这是调度器能统一的前提）

三种执行单元内部差异很大，但**输出必须同构**：

```csharp
// CertPlatform.Shared/Checklist/BlockResult.cs
public sealed class BlockResult
{
    public string BlockTitle { get; init; } = "";
    public int Seq { get; init; }

    /// <summary>明细条目（StaticText 时为 1 条；Workflow 时可能 N 条）</summary>
    public List<EvidenceItem> Items { get; init; } = new();

    /// <summary>组合文本（纯函数拼好，导出直接用）</summary>
    public string RawText { get; init; } = "";

    /// <summary>完备性（31 号 L3）</summary>
    public CompletenessLevel Completeness { get; init; } = CompletenessLevel.Unverifiable;

    /// <summary>出处（可验证性硬门槛）</summary>
    public string? SourceFileCode { get; init; }
    public string? LocationValue { get; init; }

    public decimal? Confidence { get; init; }

    /// <summary>失败原因（成功时为空）</summary>
    public string? ErrorCode { get; init; }
    public string? ErrorMessage { get; init; }

    public static BlockResult Fail(int seq, string title, string code, string msg) => new()
    {
        Seq = seq, BlockTitle = title, ErrorCode = code, ErrorMessage = msg,
        Completeness = CompletenessLevel.Insufficient
    };
}

public sealed class EvidenceItem
{
    public int Seq { get; init; }
    public string Text { get; init; } = "";
    /// <summary>在原文中的起止位置（前端高亮用）</summary>
    public int[]? Span { get; init; }
}
```

> ★ **统一契约是整个设计的枢纽**：调度器只看 `BlockResult`，不需要知道章节内部是 1 个节点还是 5 个节点。这就是"每一项独立输出"的实现基础。

### 5.3 为什么执行单元配置存 JSON 而不是拆表

`NodeConfigJson` / `ParamsJson` 是**异构结构**（单节点配置 vs 模板参数完全不同形状），拆表会导致大量 NULL 列。JSON 列在这里是正确选择——**但章节本身必须独立表**（D14），因为要按 `BlockTitle` 聚合。

### 6.2 三个实现

```csharp
// ── ① StaticText：零成本，直接构造 ──
public sealed class StaticTextBlockExecutor : IBlockExecutor
{
    public ExecUnitType SupportedType => ExecUnitType.StaticText;

    public Task<BlockResult> ExecuteAsync(BlockConfig cfg, BlockContext ctx, CancellationToken ct)
    {
        // ⛔ 合规闸：证据类章节禁止用固定文本（防编造）
        if (cfg.IsEvidence)
            return Task.FromResult(BlockResult.Fail(cfg.Seq, cfg.BlockTitle,
                "CONFIG_ERROR", "证据类章节不允许使用固定文本（无出处）"));

        return Task.FromResult(new BlockResult
        {
            Seq = cfg.Seq, BlockTitle = cfg.BlockTitle,
            Items = new List<EvidenceItem> { new() { Seq = 1, Text = cfg.StaticText } },
            RawText = cfg.StaticText,
            Completeness = CompletenessLevel.Complete,
            Confidence = 1.0m
        });
    }
}

// ── ② SingleNode：直接复用现有 RunSingleNodeAsync / RunAiNodeAsync ──
public sealed class SingleNodeBlockExecutor : IBlockExecutor
{
    private readonly WfExecutionTaskService _wf;
    public ExecUnitType SupportedType => ExecUnitType.SingleNode;

    public async Task<BlockResult> ExecuteAsync(BlockConfig cfg, BlockContext ctx, CancellationToken ct)
    {
        var node = JsonSerializer.Deserialize<WorkflowNodeConfig>(cfg.NodeConfigJson!)!;

        // ★ 复用现成入口（TestScope=NODE / AI_NODE），不重写引擎
        var req = new NodeTestRequest
        {
            NodeId = node.NodeId, NodeType = node.NodeType, Title = node.Title,
            SkillCode = node.SkillCode, Config = node.Config,
            Inputs = node.Inputs, InputTypes = node.InputTypes,
            InputPorts = node.InputPorts, OutputPorts = node.OutputPorts,
            EnterpriseCode = ctx.EnterpriseCode, PhaseCode = ctx.StageCode,
            StandardCode = ctx.StandardCode
        };

        var outcome = node.NodeType == "ai_node"
            ? await _wf.RunAiNodeAsync(req, ct)
            : await _wf.RunSingleNodeAsync(req, ct);

        // ── Adapter：异构输出 → 统一 BlockResult ──
        return ToBlockResult(cfg, outcome);
    }
}

// ── ③ Workflow：走 CreateAndRunAsync（完整 DAG）──
public sealed class WorkflowBlockExecutor : IBlockExecutor
{
    private readonly WfExecutionTaskService _wf;
    private readonly ITemplateInstantiator _tpl;   // 模板参数注入（编排层，不改引擎）

    public ExecUnitType SupportedType => ExecUnitType.Workflow;

    public async Task<BlockResult> ExecuteAsync(BlockConfig cfg, BlockContext ctx, CancellationToken ct)
    {
        // ① 模板实例化：读模板 JSON → 参数替换 → 得到完整 ruleJson
        var ruleJson = _tpl.Instantiate(cfg.TemplateRef!, cfg.ParamsJson);

        // ② 跑完整工作流（现有入口）
        var resp = await _wf.CreateAndRunAsync(new TaskExecutionRequest
        {
            RuleJson = ruleJson,
            EnterpriseCode = ctx.EnterpriseCode,
            PhaseCode = ctx.StageCode,
            StandardCode = ctx.StandardCode
        }, ct);

        return ToBlockResult(cfg, resp);
    }
}
```

> ★ **注意三个实现都没有新造执行引擎** —— 全部复用 `WfExecutionTaskService` 的三个入口。新增的只有**Adapter（转 BlockResult）** 和 **TemplateInstantiator（参数注入）**。

### 6.3 调度器（章节扇出）

```csharp
// CertPlatform.Auditor/Services/Checklist/ChecklistItemRunner.cs
public sealed class ChecklistItemRunner
{
    private readonly IEnumerable<IBlockExecutor> _executors;
    private readonly SemaphoreSlim _blockSem;   // ★ 章节级并发闸（D11 = 3）

    public ChecklistItemRunner(IEnumerable<IBlockExecutor> executors, IOptions<ChecklistOptions> opt)
    {
        _executors = executors;
        _blockSem = new SemaphoreSlim(opt.Value.BlockConcurrency, opt.Value.BlockConcurrency);
    }

    public async Task<IReadOnlyList<BlockResult>> RunItemAsync(
        IReadOnlyList<BlockConfig> blocks, BlockContext ctx, CancellationToken ct)
    {
        var tasks = blocks.Select(async b =>
        {
            await _blockSem.WaitAsync(ct);
            try
            {
                var exec = _executors.First(e => e.SupportedType == b.ExecUnitType);
                var r = await exec.ExecuteAsync(b, ctx, ct);
                await PersistAsync(b, r, ct);   // ★ 章节级先落库（33 号 §7.3）
                return r;
            }
            catch (OperationCanceledException) { throw; }
            catch (Exception ex)
            {
                var r = BlockResult.Fail(b.Seq, b.BlockTitle, "EXEC_FAILED", ex.Message);
                await PersistAsync(b, r, ct);   // 失败也落库，便于定位
                return r;
            }
            finally { _blockSem.Release(); }
        });

        return await Task.WhenAll(tasks);
    }
}
```

**关键点三条**：

1. `Task.WhenAll` + `SemaphoreSlim` ⇒ 并发受控（不是无限扇出）
2. **每个章节独立 try/catch** ⇒ 一个失败不影响其他（`Task.WhenAll` 不会因单个异常中断，因为我们内部已 catch）
3. **章节级结果先落库，再返回** ⇒ 汇总失败不用重跑

### 6.4 汇总（纯函数为主）

```csharp
// CertPlatform.Shared/Checklist/EvidenceComposer.cs  ← 纯函数层（G-4）
public static class EvidenceComposer
{
    public static string Compose(IEnumerable<BlockResult> blocks)
    {
        var sb = new StringBuilder();
        foreach (var b in blocks.OrderBy(x => x.Seq))
        {
            if (!string.IsNullOrEmpty(b.BlockTitle)) sb.AppendLine($"{b.BlockTitle}：");
            var i = 0;
            foreach (var it in b.Items)
                sb.AppendLine($"{++i}、{it.Text}");
        }
        return sb.ToString().TrimEnd();
    }
}
```

> ⛔ **不要用 LLM 拼接**（33 号 §5.1）：LLM 会顺手润色，而证据必须保持原文。

## 七、单测策略（"独立测试"的落地）

这是本设计最大的工程收益：**三种执行单元可以完全独立测，不需要跑整个任务**。

| 执行单元 | 测法 | 夹具 | 断言 |
|---|---|---|---|
| `StaticText` | 纯内存 | `BlockConfig{StaticText="..."}` | 输出 `RawText` 等于原文；`IsEvidence=1` 时返回 `CONFIG_ERROR` |
| `SingleNode` | Mock `WfExecutionTaskService` | 给定 `NodeTestRequest` | Adapter 正确转出 `BlockResult`；`NodeScopeRunOutcome` 的失败态映射到 `ErrorCode` |
| `Workflow` | Mock `CreateAndRunAsync` + 真实 `TemplateInstantiator` | 模板 JSON + 参数 | 实例化后的 ruleJson 含替换值；输出被正确转出 |
| **调度器** | Mock 三个 executor | 5 个章节，其中 1 个抛异常 | 其余 4 个成功；失败的那个 `ErrorCode=EXEC_FAILED`；**并发不超过上限** |
| **Composer** | 纯函数 | blocks 列表 | 拼接格式与样本一致（`标题：` + `1、…`） |

**★ 关键**：`SingleNode` 和 `Workflow` 的测试**不需要真实 LLM**（Mock 服务层），所以可以进 CI，跑得快。这是"可独立测试"的真实价值——**不是"能手动点一下测试"，是"能进单测"**。

## 八、端到端例子（4.2.4 配 2 章节）

### C2 · 模板参数注入在哪层？ ✅ **必须编排层（引擎不支持）**

实测：`NodeExecutor.cs:426` 注释里的 `{{常量节点标题.result}}` 是 **AI 节点提示词内的模板引用**，由 `ResolveTemplateRefs` 解析，**引用的是上游节点的运行期输出**。

⇒ **`config` 里的 `{{}}` 不是"配置期常量注入"**，而是"运行期上游引用"。两者语义不同，不能混用。

**结论**：`TemplateInstantiator` 必须在**编排层**做，且用 **JSON 路径替换**（不是字符串替换）：

```csharp
// CertPlatform.Auditor/Services/Checklist/TemplateInstantiator.cs
public string Instantiate(string templateRef, string? paramsJson)
{
    var tpl = _templateStore.Get(templateRef);            // 模板 JSON 字符串
    if (string.IsNullOrEmpty(paramsJson)) return tpl;

    var root = JsonNode.Parse(tpl)!.AsObject();
    var prm  = JsonNode.Parse(paramsJson)!.AsObject();

    // 按约定路径替换：节点 config 里的 "$param.xxx" → 实际值
    foreach (var node in root["nodes"]!.AsArray())
    {
        var cfg = node!["config"]?.AsObject();
        if (cfg == null) continue;
        foreach (var kv in cfg.ToList())
            if (kv.Value is JsonValue v && v.TryGetValue<string>(out var s) && s.StartsWith("$param."))
                cfg[kv.Key] = prm[s["$param.".Length..]]?.DeepClone();
    }
    return root.ToJsonString();
}
```

> ★ **为什么用 `$param.` 前缀而不是 `{{}}`**：避开与引擎既有 `{{}}` 语义冲突，配置人员一眼能分清"这是配置期注入"还是"这是运行期引用"。
