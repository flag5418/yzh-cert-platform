## 一、系统定位与边界

### 1.1 定位

**CertExpert（专家平台）任务子系统**是「体系认证审核」的执行环节。管理员/实施人员在后台配置**规则**（NC 检查规则 / 报告章节规则），专家在企业资料齐备后发起**任务**，系统自动执行并产出**结果**，专家**逐条认可或修改**，最后**导出 Excel**。

一句话：**配置层（管理端）→ 执行层（专家端任务）→ 产物（Excel）**。

### 1.2 明确的非目标（本期不做）

| 不做 | 理由 |
|---|---|
| docx / pdf 报告生成 | D14：这是工具系统，不是报表系统。固定格式 Excel 即可 |
| 客户定制报表格式 | D09：同上 |
| 字段级/文件级证据追溯下钻 | D08：归后台工作流设计（规则侧）实现。规则引擎已有 `RuleContext` 快照可查 |
| 双人复核（制单≠审核） | D21：注册人即管理员，全权限 |
| 任务追加检查项/章节 | D20：进入 `running` 后不可变更范围，避免中途改范围污染结果 |
| 整改跟踪（NC 开具后的整改闭环） | `audit_rectification` 表已存在但属另一功能域，本期只做到 NC 记录生成 |
| 改代码标识符（`CertPlatform.*` → `CertExpert.*`） | D18：影响面过大（命名空间/目录/构建/路由/文档），另开任务 |

### 1.3 角色

| 角色 | 载体 | 权限 |
|---|---|---|
| 专家 | `cert_auditor_profile` + `Sys_User`（工作区内） | 建任务、跑队列、补录、认可/修改、批准、导出。**注册即管理员，全权限**（D21） |
| 管理员 / 实施人员 | `CertPlatform.Admin` | 配置 NC 规则、报告章节、工作流 DAG、Prompt 模板、文档提取规则 |

> 多租户隔离唯一入口：`WorkspaceContextService.Resolve()`（`CertPlatform.Auditor/Services/`）。所有专家端端点**必须**先解析工作区上下文，任务表的 `OrgCode` 一律取自该上下文，**禁止**从请求参数取。

### 2.2 为什么 NC 检查项与报告章节可以合表

用户原始描述的第 5 条：

> 「所有的队列执行完成后，专家可以手动进行批准，哪些自动检查的结果是 ok 的，也可以手动修改」
> 「nc 检查报告和报告内容可以导出」

以及最终裁决 D14：

> 「执行完成应该是按每个标准，每个章节的列表，和 nc 检查项一样，用户可以审批是否接受，也可以修改报告内容」

**判断依据**：两类对象的生命周期完全一致 ——

| 阶段 | NC 检查项 | 报告章节 |
|---|---|---|
| 来源 | `cert_validation_rule`（规则 Code） | `cert_report_section`（章节 Code） |
| 执行 | 工作流 DAG 跑一遍 | 工作流 DAG 跑一遍 |
| 自动产出 | 结论 + 严重度 + 说明 | 章节正文 |
| 专家动作 | 认可 / 改结论 / 改严重度 / 改说明 | 认可 / 改正文 |
| 留痕 | 必需 | 必需 |
| 导出 | Excel 一行 | Excel 一行/一段 |
| 缺数据 | 跳过不显示 | 跳过不显示 |

**唯一差异是 3 个标量列**：

| 差异点 | 列名 | NC 检查项 | 报告章节 |
|---|---|---|---|
| 判定结果 | `Conformity` | `conform`/`nonconform`/`observation`/`na` | 恒为 `null`（章节不判定合规） |
| 严重度 | `Severity` | `major`/`minor`/`observation` | 恒为 `null` |
| 结果正文 | `ContentText` | 说明文字（可空） | **章节正文（核心产物）** |

因此设计成**统一表 `cert_expert_task_item`**，这 3 列在不同 `ItemType` 下留空。这样做带来的收益：

1. 认可 / 修改 / 日志 / 导出 / 列表混排 —— **只写一遍逻辑**
2. 任务级统计（总数/待认可/已认可/已修改/跳过）—— **一条 SQL 聚合**
3. 批准前置校验（「所有结果必须被认可」，D12）—— **一次校验覆盖两类**
4. 未来加第三类结果（如「不符合项跟踪」）—— **零表结构改动**

### 2.3 三层「Code」辨析（极易出错，务必分清）

| 层级 | 键 | 取值 | 举例 |
|---|---|---|---|
| 任务层 | `cert_expert_task.Code` | GUID | `a1b2c3...` |
| 子任务层 | `cert_expert_task_standard.Code` | GUID | `d4e5f6...` |
| 规则层 | `ItemCode` | `cert_validation_rule.Code` 或 `cert_report_section.Code` | `7f8a9b...` |

> ⛔ `ItemCode` 存的是**规则表的主业务键**，不是 `RuleCode`（`NC-{StandardCode}-{seq:D3}`）也不是条款号。关联回规则时用 `ItemCode`，展示时读规则的 `RuleName`。

### 3.2 关键顺序约束（★ 两条，D31 后从三条变两条）

| # | 规则 | 强制点 | 违反后果 |
|---|---|---|---|
| **O1** | ★ **数据源锁**：`(企业, 阶段)` 上存在 `ExecStatus ∉ {completed,failed}` 且 `LifecycleStatus='active'` 的任务 → **禁止企业文件上传/替换/删除/恢复/手动提取** | 文件操作端点前（`CertEnterpriseFileController` + `trigger-extract` 需接同一把锁） | 中途换文件 → 已跑结果与新文件不一致 |
| **O2** | **软阻塞**：未补录且未跳过的 gap 存在 → 拒绝 `submit` | `POST /{code}/submit` 事务内重跑完备性检查 | 缺数据跑出来的结论是假的 |

> ⛔ **O1 不再拦「新建任务」**（D28 修正，评审 P0-26）。两个任务读同样的提取结果，不污染。
> ⛔ **O3「认可强制 → 拒绝 approve」已作废**（D31）。因为**没有 approve 动作**了。认可强制性改为**结果菜单归档时**校验。

**★ 僵尸任务例外**（13 号 E5-6）：进程 crash 导致 `ExecStatus` 卡在 `running` → 锁永不释放。加定时 Job：扫 `ExecStatus ∈ {pending_run, running}` 且 `UpdateTime` 超 2 小时 → 置 `failed` + 告警（阈值依据：单项含 LLM 调用实测上限约 10 分钟，2 小时是 12 倍余量）。

## 四、状态机（★ V2 已按 D27/D31 重写为三层）

> ⛔ **原 V1 的单列 `TaskStatus`（含 `approved`）已作废**。评审 P0-29 指出的四个冲突（D31/D28/D32/D33）在此修正。
> ⛔ **不存在「批准」动作**。任务系统只管执行与生死；认可/修改/归档在**结果菜单**。

### 4.1 ★ 三层状态分离（D27）

三个状态**正交**，各管各的，互不替代：

```
┌────────────────────────────────────────────────────────────┐
│ 第 3 层 · 存续状态  LifecycleStatus        【任务系统】     │
│   active | archived | cancelled | voided                    │
│   —— 管"这次执行还算不算数"                                 │
│   归档：完美结束，本次执行封存                              │
│   取消：因故无效（企业资料不符合等）                         │
│   作废：结果不被认可                                        │
│   ★ 全部为终态后自动解除业务锁（见 §三 O1）                 │
├────────────────────────────────────────────────────────────┤
│ 第 2 层 · 结果状态  ReviewStatus          【结果菜单】     │
│   not_started | pending_review | reviewed | frozen          │
│   —— 管"专家看过了吗"                                       │
│   ★ 不再有 approved（D31）                                  │
├────────────────────────────────────────────────────────────┤
│ 第 1 层 · 执行状态  ExecStatus            【机器】         │
│   draft | pending_run | running | completed | failed        │
│   —— 管"机器跑完了吗"                                       │
└────────────────────────────────────────────────────────────┘
```

**存储方式**（06 号 §2.1）：

| 层 | 列 | 类型 |
|---|---|---|
| 执行 | `ExecStatus` | varchar(20) |
| 结果 | `ReviewStatus` | varchar(20) |
| 存续 | `LifecycleStatus` | varchar(20) DEFAULT 'active' |

> ⛔ **不再有** `TaskStatus` / `SubStatus` / `ApproveBy` / `ApproveName` / `ApproveTime` / `ApproveRemark` 六列。

### 4.2 执行状态机（`ExecStatus`，机器管，不可逆）

```
 draft ──提交──▶ pending_run ──worker领取──▶ running ──全部队列终态──▶ completed
   │                  │                          │                        │
   │                  │                          └──全部失败──▶ failed    │
   │                  │                                                    │
   └──作废──▶ archived / cancelled / voided  ◀──归档──────────────────────┘
```

| 状态 | 含义 | 可执行 |
|---|---|---|
| `draft` | 已创建，未提交 | 补录、跳过 gap、提交、归档/作废/取消 |
| `pending_run` | 已入队，等 worker 领取 | 看进度、取消 |
| `running` | 至少一个队列在跑 | 看进度、取消 |
| `completed` | 全部队列结束（★ 含部分失败，失败项已转 skipped） | 看结果、归档/作废 |
| `failed` | 队列全部失败 | 重新提交、重试单项 |
| `archived` | 归档终态 | 只读 |
| `cancelled` | 取消终态 | 只读 |
| `voided` | 作废终态 | 只读 |

**流转白名单**（集中定义，防散落）：

```csharp
private static readonly HashSet<(string, string)> AllowedExec = new()
{
    ("draft", "pending_run"), ("draft", "archived"), ("draft", "cancelled"), ("draft", "voided"),
    ("pending_run", "running"), ("pending_run", "cancelled"), ("pending_run", "voided"),
    ("running", "completed"), ("running", "failed"),
    ("running", "cancelled"), ("running", "voided"),
    ("completed", "archived"), ("completed", "voided"), ("completed", "cancelled"),
    ("completed", "pending_run"),      // ★ rerun：重新执行
    ("failed", "pending_run"),         // ★ 重新提交
};
```

### 4.3 结果状态机（`ReviewStatus`，专家管）

```
                    ┌──────────────────────────────────┐
                    │                                  │
  队列执行完成       ▼                                  │
  ────────────▶ pending_review                          │
                    │                                  │
      ┌─────────────┼─────────────┐                   │
      ▼             ▼             ▼                   │
 acknowledged   modified      skipped                 │
  已认可         已修改        已跳过                  │
                    │                                   │
                    └───────────────────────────────────┘
                                │ 归档
                                ▼
                             frozen
                          （不可再改）
```

| 状态 | 含义 | 谁改 | 可否继续修改 |
|---|---|---|---|
| `not_started` | 队列还在跑，结果未出 | 机器 | — |
| `pending_review` | 结果已出，专家未处理 | — | ✅ |
| `acknowledged` | 专家认可了自动结果 | 专家 | ✅（可再改，转 modified） |
| `modified` | 专家改了结果（★ 修改即认可，D11） | 专家 | ✅ |
| `skipped` | 数据不足/规则禁用/人工模式/执行失败 | 机器 | ✅（补录后可重跑） |
| `frozen` | 归档后冻结 | 归档动作 | ⛔ |

> ⛔ **没有 `approved`**。`pending_review` 不阻塞任何任务级操作（12 号 §3.5）。

### 4.4 数据缺口状态机（`cert_expert_task_data_gap.GapStatus`）

```
  完备性检查产出
        │
        ▼
   ┌─────────┐   专家补录    ┌─────────┐
   │ pending │─────────────▶│ filled  │
   └────┬────┘              └─────────┘
        │
        │ 专家跳过（整体 or 单条）
        ▼
   ┌─────────┐
   │ skipped │ 终态（可反悔：补录后转 filled）
   └─────────┘

  补录后文件被替换 → 相关 gap 重置为 pending
```

### 4.5 ★ "任务完成"的唯一定义

> ⚠️ 12 号 §3.2 与 §3.5 曾给出两个不同定义（评审 P1-17），此处收敛为**一个**：

| 说法 | 定义 | 用途 |
|---|---|---|
| **★ 任务完成** | `ExecStatus='completed'` **且** `LifecycleStatus ∈ {active, archived}` | 对外表述、业务锁判定 |
| 排队列结束 | `ExecStatus ∈ {completed, failed}` | 进度条 100% |

> 「全部结果已认可」是**检查项级别的状态**，不是一个任务状态 —— 任务可能部分认可部分没认可，任务本身照样"完成"。

### 4.6 业务锁的三层判据（★ D28 修正）

```
锁条件（唯一）：(OrgCode, EnterpriseCode, StageCode) 上存在任一任务满足
               ExecStatus ∈ {draft, gap_detected, pending_run, running, pending_review}
               ★ 即：ExecStatus NOT IN ('completed','failed')
               ★ 且 LifecycleStatus = 'active'（★ 归档/作废/取消后立即解锁）

锁范围（★ 只锁数据源写操作，【不拦新建任务】，D28）：
  ✅ 锁：企业文件上传 / 替换 / 删除 / 恢复 / 手动触发提取
  ⛔ 不锁：新建任务、认可、修改、导出、归档
```

> ⛔ **原 V1 的 O1「有活任务就禁建任务」已作废**（评审 P0-26）。理由：两个任务读同样的提取结果（没变），结果一致，不污染。
> ⚠️ **僵尸任务例外**（13 号 E5-6）：进程 crash 导致任务卡在 `running`，锁永不释放 → 加定时 Job 扫描 `ExecStatus ∈ {pending_run,running}` 且 `UpdateTime` 超 2 小时 → 置 `failed` + 告警。

## 六、设计原则（本期遵守）

| # | 原则 | 具体含义 |
|---|---|---|
| P1 | **单一真相源** | 任务结果只存 `cert_expert_task_item`。`wf_execution_task_item` 是过程留痕（引擎视角），`cert_expert_task_item` 是业务结论（专家视角）。两者通过 `RuleCode` 关联，不互为副本 |
| P2 | **规则不脏** | 任务**绝不回写** `cert_validation_rule` / `cert_report_section`。补录只写 `cert_extraction_result` / `cert_table_extraction_result`（企业域数据）。规则是全企业共享的配置，被单企业任务污染是灾难 |
| P3 | **不物理删** | 所有表用 `IsDeleted`；`cert_extraction_result.IsValid` 复用为「1=当前版本，0=归档旧版本」（企业域版本链，见 10 号分册 02 号 V-P1）。不 DROP 任何历史数据 |
| P4 | **缺数据即显式跳过，绝不静默** | 与其产出空结果让人误以为「检查通过」，不如显式标记「数据不足未检查」（D05） |
| P5 | **一切人工动作留痕** | 补录、认可、修改三类动作全部落日志表（05 号）。日志只追加，永不更新 |
| P6 | **软阻塞优于硬拦截** | D04：允许专家跳过。系统提示但不强制，业务节奏由专家掌控 |
| P7 | **口径唯一** | 阶段统一用 `cert_cert_stage.Code`；启用标志统一 `IsValid`；队列 ScopeKey = 子任务 Code（不复用 `yzh_queue` 的双口径，见 09 号 D20） |
| P8 | **三层同构** | 后端 Controller / 前端 api / 前端 pages 三层同名同路径（`docs/30-项目规则/前后端代码结构统一规则-V1.md`） |

## 七、验收标准（本期完成的样子）

一句话验收：**专家选企业+阶段 → 系统告知缺 3 个字段 → 专家补录 2 个、跳过 1 个 → 提交 → 队列跑出 5 条结果（4 条正常 + 1 条跳过）→ 专家改 1 条认可 4 条 → 批准 → 导出 Excel 5 个 Sheet（按标准分）→ 每条结果都能查到谁在什么时候改了什么**。
