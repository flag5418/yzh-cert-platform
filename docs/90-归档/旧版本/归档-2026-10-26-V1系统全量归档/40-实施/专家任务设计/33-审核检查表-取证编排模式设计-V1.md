## 一、结论速览

| # | 你的设想 | 结论 | 关键依据 |
|---|---|---|---|
| 1 | 「配置期先结构化定义：一段提示词 or 章节结构」 | ✅ **完全可行，且必须这么做** | 32 号实测：58.5% 是纯段落（单提示词够），26% 长证据需章节结构 ⇒ **两种模式都是刚需，不是二选一** |
| 2 | 「每个章节关联到工作流中定义流程执行方法」 | ⚠️ **方向对，但会配置爆炸** | 250 条 × 2 章节 = **500 个章节**。若每章节绑一个 DAG ⇒ **500 个流程要维护**。应绑「**取证方法类型**」（4 种）⇒ **4 个模板 DAG + 500 行参数** |
| 3 | 「一次性执行多个 AI 流程」 | ⚠️ **撞了已有设计决策** | `ExpertTaskQueueRunner.cs:21-23` 明写「**同一队列内串行**…保证不会并发打爆 LLM 配额」⇒ 并行粒度必须放在**队列项内部（章节级）**，不能放队列项之间 |
| 4 | 「无论多少章节结果，最后统一到一个 LLM」 | ⚠️ **要拆成 4 种汇总，只有 2 种该用 LLM** | 文本拼接 = 纯函数；要素校验 = 纯函数 + LLM；只有**一致性校验**和**综合判定**是 LLM，且**输入必须是章节摘要，不是全文** |
| 5 | （隐含）汇总输出一个整条结论 | ⛔ **会抵消 32 号的价值** | 32 号刚把 NC 从"笼统"做到"精确到章节"；汇总若压平成"整条不符合"，又回去了 |

**一句话**：这个思路**架构上是对的**（就是标准的 Map-Reduce / Orchestrator-Workers），但要改 3 处 —— **章节绑方法不绑流程**、**汇总拆 4 种**、**并行放队列项内部**。

## 二、你这个设想在架构上叫什么

这是经典的 **Map-Reduce over LLM**（也叫 Orchestrator-Workers 模式）：

```
                    ┌─────────────────────────┐
                    │  配置期（声明式）        │
                    │  检查项 → 模式 → 章节    │
                    └───────────┬─────────────┘
                                ↓
                    ┌─────────────────────────┐
                    │  Map（扇出）             │
                    │  章节1 → 流程 → 结果1    │
                    │  章节2 → 流程 → 结果2    │  ← 并发
                    │  …                       │
                    │  章节N → 流程 → 结果N    │
                    └───────────┬─────────────┘
                                ↓
                    ┌─────────────────────────┐
                    │  Reduce（汇总）          │
                    │  拼接 / 校验 / 判定      │
                    └─────────────────────────┘
```

**为什么这个模式适合本场景**：

| 特征 | 本场景 | 适配性 |
|---|---|---|
| 任务是**可分解**的 | 一条检查项的证据天然分 N 个方面 | ✅ |
| 子任务**互不依赖** | 章节 A 的取证不依赖章节 B | ✅ |
| 子任务**可并行** | LLM 调用是 IO 密集 | ✅ |
| 汇总需要**全局视角** | 章节间矛盾检测、整体判定 | ✅ |
| 结果要**可定位** | NC 要指向具体章节 | ✅（只要汇总不压平） |

> ★ 这类模式在长文档处理里是标准做法。**你不是在发明新架构，是在用一个成熟模式** —— 这是好事，说明思路对。

## 三、配置期：两种模式（都对，都要）

### 3.1 模式定义

| 模式 | 适用 | 32 号实测依据 | 配置内容 |
|---|---|---|---|
| **`single_prompt`** | 短证据（<500 字） | **58.5% 是纯段落**，一句话说完 | 1 段提示词 + 要素清单 |
| **`block_structured`** | 长证据（≥500 字） | **26% 行 / 75% 字数 / 95% 天然有结构** | N 个章节，每章节 1 段提示词 + 方法 + 要素 |

> ★ **关键**：两种模式**不是二选一的产品决策，而是按证据复杂度自动分流的工程必然**。如果只做 `block_structured`，58.5% 的短证据会被硬拆成"1 章节 1 明细"（32 号 §3.4 已论证是纯噪音）。

### 3.2 配置结构（一个检查项的完整声明）

```json
{
  "itemCode": "CHK-9001-4.2.4",
  "clauseCode": "…",
  "collectMode": "block_structured",
  "blockThreshold": 500,
  "singlePrompt": null,
  "blocks": [
    {
      "seq": 1,
      "blockTitle": "文件审批要求",
      "evidenceMethod": "document",
      "promptTemplate": "从企业文档中找出《文件控制程序》对文件审批的规定，摘录：审批人、审批环节、审批记录形式。",
      "evidenceElements": ["approver", "approvalStep", "recordForm"],
      "required": true
    },
    {
      "seq": 2,
      "blockTitle": "文件发放范围",
      "evidenceMethod": "record",
      "promptTemplate": "抽查最近 3 次文件发放记录，摘录：发放部门、发放份数、签收人、日期。",
      "evidenceElements": ["dept", "copies", "receiver", "date"],
      "sampleRule": "recent_3",
      "required": true
    }
  ]
}
```

> ★ 注意 `evidenceMethod` —— 这就是 §四 的核心：**章节绑的是"方法"，不是"流程实例"**。

## 四、★ 第一处要改：章节绑「取证方法」，不绑「工作流」

### 4.1 配置爆炸的算术

| 方案 | 配置对象 | 数量 | 维护成本 |
|---|---|---|---|
| **你的原设想**（章节 → 工作流） | 每个章节一个 DAG | 250 条 × 平均 2 章节 = **500 个 DAG** | ⛔ 不可维护：改一个通用逻辑（如"必须带出处"）要改 500 处 |
| **建议**（章节 → 方法类型） | 4 个模板 DAG + 章节参数 | **4 个 DAG + 500 行参数** | ✅ 改通用逻辑只改 4 处 |

### 4.2 为什么"4 个模板"够（31 号已论证）

31 号 §3.3 已把取证方法穷举成 4 类，覆盖样本 62/76 行：

| 方法 | 模板 DAG | 覆盖 | 差异点在哪 |
|---|---|---|---|
| `document` | T1 文件查阅 | 26 行 | 只差**提示词**和**要素清单** |
| `record` | T2 记录抽查 | 12 行 | 只差提示词 + 抽样规则 |
| `observe` | T3 现场观察 | 19 行 | 只差观察提纲 |
| `interview` | T4 访谈 | 5 行 | 只差访谈提纲 |

> ★ **同一个方法下，所有条款的流程骨架完全一样**（取数 → 判存在 → 抽取 → 校验 → 组装）。差异只在**提示词文本**和**要素清单**。把这两样做成参数注入模板，就不需要 500 个 DAG。

### 4.3 模板 DAG 怎么参数化

```json
{
  "templateId": "T1_document",
  "nodes": [
    { "nodeId": "n1", "nodeType": "start" },
    { "nodeId": "n2", "nodeType": "doctable",
      "config": { "tableCode": "{{block.sourceTable}}" } },        // ← 章节参数注入
    { "nodeId": "n3", "nodeType": "skill", "skillCode": "is_std_file_missing",
      "config": { "standardFileCode": "{{block.standardFileCode}}" } },
    { "nodeId": "n4", "nodeType": "ai_node",
      "config": { "prompt": "{{block.promptTemplate}}",             // ← 章节参数注入
                  "outputSchema": "{{block.outputSchema}}" } },
    { "nodeId": "n5", "nodeType": "skill", "skillCode": "evidence_sufficiency",
      "config": { "elements": "{{block.evidenceElements}}" } },     // ← 章节参数注入
    { "nodeId": "n6", "nodeType": "end" }
  ]
}
```

> ⚠️ **需要确认**：现有 `NodeExecutor` 是否支持 `{{}}` 占位符在 `config` 里做参数注入。从 `DocumentFillOrchestrator` 的锚点机制看，`{{}}` 是**文档填充**用的，DAG 的 `config` 未必支持。
>
> **如果不支持**：在**编排层做模板实例化**（读模板 JSON → 字符串替换 → 反序列化成 DAG 跑），不改引擎。这是更安全的做法（引擎零改动）。

## 五、★ 第二处要改：汇总不是"一个 LLM"，是 4 种汇总

### 5.1 四种汇总的分解

你说"无论有多少章节结果，最后统一到一个 LLM 中执行"。拆开看，这一步其实有 **4 件不同的事**：

| # | 汇总类型 | 做什么 | **该用什么** | 输入 |
|---|---|---|---|---|
| 1 | **文本拼接** | 把 N 个章节拼成完整证据（导出用） | ⛔ **纯函数**（`EvidenceComposer`） | 章节全部明细 |
| 2 | **要素校验** | 整体要素命中率（31 号 L3） | **纯函数 + 可选 LLM** | 章节明细 |
| 3 | **一致性校验** | 章节之间有没有矛盾 | ✅ **LLM**（独立 skill） | **章节摘要**（非全文） |
| 4 | **综合判定** | 整条检查项最终结论 | ✅ **LLM**（可选，见 §九） | **块判定结果**（非原文） |

> ★ **只有第 3、4 项该用 LLM。第 1 项用 LLM 是错的** —— 拼接是确定性的，LLM 拼会把原文改写掉（违反 31 号「`RawSnippet` AI 不得改写」）。

### 5.2 为什么"全文塞进一次 LLM"不可行（4 个硬理由）

| # | 问题 | 具体后果 |
|---|---|---|
| 1 | **上下文爆炸** | H8.1.2 一条就 3,286 字 / 25 章节。若 10 个检查项一起汇总 ⇒ **3 万字以上**，接近甚至超出窗口 |
| 2 | **注意力稀释**（lost in the middle） | 超长上下文中，中间部分信息被忽略 ⇒ **漏掉中间章节的矛盾**，而这恰恰是最容易出问题的地方 |
| 3 | **定位丢失** | 一次调用输出"整条不符合" ⇒ **32 号刚解决的"NC 说不清哪里不符"又回来了** |
| 4 | **成本线性增长** | 输入 token 随章节数线性增长；而"摘要"是常数级（25 章节 × 50 字 = 1,250 字） |

### 5.3 正确的汇总输入：结构化摘要

```json
{
  "itemCode": "CHK-45001-8.1.2",
  "blocks": [
    { "seq": 1, "title": "运行控制措施",   "conformity": "conform",     "summary": "配备灭火器/消防箱，照明空调完好，培训到位", "confidence": 0.92 },
    { "seq": 2, "title": "应急准备与响应", "conformity": "nonconform",  "summary": "应急预案未覆盖有限空间作业场景",           "confidence": 0.88 },
    { "seq": 3, "title": "承包商管理",     "conformity": "observation", "summary": "承包商进场教育记录缺失 1 次",              "confidence": 0.71 }
  ]
}
```

**汇总 LLM 的职责 = 在摘要层面找矛盾 + 给整条结论**，需要细节时**按 `seq` 回查**（不是预先塞全文）。

> ★ 这个设计的额外好处：**汇总的 token 量与章节数几乎无关**（每个章节摘要 30-60 字），25 章节也只有 1,500 字左右。

## 六、★ 第三处要改：汇总必须保留章节级结构

### 6.1 32 号的价值不能被抵消

32 号刚建立的结论（§九）：

| | 整条判定 | 分块判定 |
|---|---|---|
| NC 描述 | 「运行控制存在不符合」 | 「在**『应急准备与响应』方面**不符合」 |
| 企业知道改哪吗 | ❌ | ✅ |

**如果汇总输出只有一个 `overall: nonconform`，章节级判定结果就被压平了** ⇒ 前面所有分块工作白做。

### 6.2 正确的汇总输出

```json
{
  "overall": "nonconform",                    // 整条结论（用于列表页）
  "blocks": [                                  // ★ 章节级结构必须保留
    { "seq": 1, "conformity": "conform" },
    { "seq": 2, "conformity": "nonconform", "ncCandidate": true, "reason": "应急预案未覆盖有限空间作业" },
    { "seq": 3, "conformity": "observation" }
  ],
  "crossBlockIssues": [                        // ★ 一致性校验产出（这是 LLM 汇总的独有价值）
    { "type": "contradiction", "between": [2, 5], "detail": "章节2 称已覆盖全部高风险作业，章节5 列出有限空间作业未编入预案" }
  ]
}
```

> ★ `crossBlockIssues` 才是"统一到一个 LLM"**真正的价值** —— 章节间的矛盾**只能在汇总层发现**（单个章节内部看不出来）。这与 31 号 §4.4 的「② 一致性判定线」是同一件事，只是粒度从"跨检查项"细化到"跨章节"。

## 七、执行期：扇出 / 汇总的编排

### 7.1 时序

```
队列项领取（一个检查项）
   ↓
读 cert_check_item → collectMode
   ├─ single_prompt ──→ 1 次 LLM → 1 个 block
   └─ block_structured
         ↓
       fan-out（章节并发，上限 C）
         ├─ 章节1 → T1 模板 DAG → {title, items, confidence}
         ├─ 章节2 → T2 模板 DAG → {…}
         └─ 章节N → …
         ↓
       fan-in
         ├─ 纯函数 Compose        → EvidenceText 快照
         ├─ 纯函数 ElementCheck   → 要素命中率
         └─ LLM（可选）CrossBlock → crossBlockIssues
   ↓
写 cert_check_evidence / _block / result.EvidenceText
   ↓
队列项完成
```

### 7.2 ★ 并发粒度：必须放队列项内部（这是硬约束）

`ExpertTaskQueueRunner.cs:21-23` 原文：

> 「**同一队列内串行**：领取条件要求「该队列当前无 running 项」。这保证同一标准下的检查项按 `Seq` 顺序执行，**不会并发打爆 LLM 配额**，也让日志顺序与业务顺序一致（可读）。」

且 `MaxConcurrent = 3`（`:31`）。

⇒ **不能把并行放在检查项之间**（会打破这个刻意设计）。正确落点：

| 层 | 并发策略 | 现值 | 建议 |
|---|---|---|---|
| **队列级**（标准子任务之间） | `MaxConcurrent` | **3** | **保持 3 不变** |
| **队列项级**（检查项之间） | 串行 | 串行 | **保持串行**（现有设计） |
| **★ 队列项内部**（章节之间） | **新增扇出** | 无 | **上限 3**（可配） |

**最大并发 = 3 × 3 = 9 个 LLM 调用**（现状是 3）。如果仍偏高，加一层**全局 LLM 闸**（单例 `SemaphoreSlim(8)`，所有 LLM 调用都过闸）。

> ★ **这是本方案最容易出错的地方**：如果按"一次性执行所有 AI 流程"字面实现（25 章节全并发 × 3 个队列 = 75 个调用），**必然 429**（我们上一轮就遇到过限流）。

### 7.3 部分失败处理

| 情况 | 处理 |
|---|---|
| 某章节 LLM 超时 | 该 block 标 `insufficient`，**不阻塞其他章节** |
| 某章节抽不到证据 | 该 block 标 `insufficient` + 归因（企业没交 / 提取没配） |
| 全部章节失败 | 整条检查项落 `not_checked`，进重试队列 |
| 汇总 LLM 失败 | **不影响章节级结果**（已落库），只缺 `crossBlockIssues` ⇒ 可单独重跑汇总 |

> ★ **关键设计**：**章节级结果先落库，再做汇总**。这样汇总失败不用重跑 25 个章节（省钱 + 省时）。

### 7.4 状态机（章节级）

```
pending → running → done
                 └→ failed → retry(N) → done / dead
                 └→ insufficient（业务性缺证据，不重试）
```

> ⚠️ 需要**章节级状态列**（`cert_check_evidence_block.BlockStatus`），32 号的 DDL 里没有。这是本方案要补的一列。

## 八、现有引擎能不能支撑

| 需要的能力 | 现有 | 结论 |
|---|---|---|
| 单个流程编排 | `NodeExecutor` 串行 DAG（7 类节点） | ✅ 够 |
| DAG 存配置 | `cert_validation_rule.RuleJson` / `cert_check_item.RuleJson` | ✅ 够 |
| 队列并发控制 | `ExpertTaskQueueRunner.MaxConcurrent = 3` | ✅ 够（队列级） |
| **章节级扇出** | 无 | ❌ **需新增**（编排层，不改引擎） |
| **模板参数注入** | 未知（`config` 是否支持 `{{}}`） | ⚠️ 需确认；不支持则在编排层实例化 |
| **全局 LLM 闸** | 无 | ⚠️ 建议新增（防 429） |
| **章节级状态** | 无 | ❌ 需加列 |

**⇒ 不需要改 `NodeExecutor`。** 新增的都在编排层（`ChecklistExecutor`）+ 1 个全局闸 + 1 个状态列。这与 32 号 §八「循环放编排层」的结论一致。

## 九、什么时候"统一到一个 LLM"真的是对的

有一个场景确实需要：

**章节级判定有歧义时，让汇总 LLM 做最终裁决。**

```
触发条件：存在 2 个以上 block 的判定置信度 < 0.6
输入：这些 block 的【判定结果 + 原文】（只传争议块，不传全部）
输出：修正后的 block 判定 + 整条结论
```

> ★ 这就是 31 号 §7.1「分级诊断」的延伸：**先便宜地全判 → 只对可疑的贵判**。汇总 LLM 只在"可疑"时才启用，不是每次都跑。

**所以你的设想要微调为**：

```
❌ 「无论多少章节结果，最后统一到一个 LLM」
✅ 「章节级先各判 → 汇总层做矛盾检测（摘要级）→ 仅争议块回传原文做终裁」
```

## 十、待裁决

### D11 · 章节级并发上限定多少？

**白话**：一个检查项有 25 个章节，同时跑几个？
- 全跑 ⇒ 25 个 LLM 并发，乘以队列 3 = 75 ⇒ **必然 429**
- 跑太少 ⇒ 慢，25 章节 × 单次 30 秒 / 3 并发 ≈ 4 分钟

**建议**：章节并发 **3**（总并发 9）+ **全局 LLM 闸 8**。实测调优后再改。

### D12 · 模板参数注入在哪一层做？

**白话**：章节的提示词怎么"填"进模板 DAG？

### D13 · 汇总 LLM 每次都跑，还是只在有歧义时跑？

**白话**：矛盾检测要不要每次都做？
