## 一、结论速览（先看这 10 条）

| # | 问题 | 结论 |
|---|---|---|
| ① | 市面上有没有「排班计划」？ | ✅ **有，而且做透了**。国内三家老牌 ERP + 新一代 AI 产品均已实现，**且监管强制** |
| ② | 市面上有没有「证据收集」？ | ✅ **有，但形态不同**。国际 CBMS 做到「逐条挂证据 + 离线 + 复用上次证据」；国内 ERP 的「证据」= 卷宗附件上传 |
| ③ | 有没有**一家把两半接上**？ | ❌ **没找到**。计划层成熟、证据层成熟，但「证据 → 判定」这段是空的 |
| ④ | 最危险的对手是谁 | ★★★ **辰泽智擎**（`chenze-ai.com`）。「智擎·计」审核计划智能编制**已公测**，「智擎·审」明确写**按部门拆分检查表** —— 与 36 号设计**几乎同构** |
| ⑤ | 老牌厂商做到什么程度 | 数通国软：**审核日历 / 日历排期 / 审核员专业匹配 / 自动生成上报表 / 人日计算 / 批量下卷回传 / 电子签章 / 在线阅卷** |
| ⑥ | 国际厂商的 AI 态度 | ★ **Zertic 明确拒绝 AI 做计划决定**（"Accelerate, don't decide"），AI 生成审核计划**仅 PoC** |
| ⑦ | 「AI 自动判 NC」有人做吗 | ❌ **全网未找到成品**。这是空档，也是最难的一段 |
| ⑧ | 我们的功能 1（规范化）还有溢价吗 | ⚠️ **没有**。ISOPilot 已把它商品化到 **¥990/年** |
| ★⑨ | **能不能自动形成证据链？** | ❌ **认证行业无成品**；✅ **财务审计已跑通**（DataSnipper / Blast Audit：OCR 抽取 → 自动匹配底稿 → 每条结论**可追溯到源**）。⇒ **技术已验证，行业未落地** |
| ★⑩ | **能不能通过证据链自动生成 NC？** | ❌ **无成品**。⚠️ 六家都宣称「自动生成不符合项」，**只有 IACheck（检测报告）是真判定**，认证行业全是「**人工记录 → 自动成文**」。详见 §十五 |

**一句话**：**排班计划和证据收集都不是蓝海，都有人做；真正没人做的是「证据 → 判定」。**

**第二句话（回答核心问题）**：**「自动证据链」和「自动 NC」在认证行业是 0 个成品，但在财务审计和检测报告两个同构领域已经跑通** ⇒ **不是技术空白，是行业空白**。技术风险可控，真正的风险在**准确率 + 责任边界**。
⇒ 战略含义：**计划层是入场券（必须做、且必须能对接监管上报），判定层是护城河（唯一值得重投入的地方）。**
⇒ ★ 落地含义：**三条判定线里先做「完备性」**（证据有没有），它规则可判、容错高、不需要开 NC，绕开责任问题。符合性判定后置。

|---|---|---|

| **L5 通用巡检/内审** | SafetyCulture(iAuditor) · Nimonik · 易审核(LPA) | **移动端拍照证据、离线、海量模板、AI 报告** | **不是认证机构业务**（无条款体系、无 CCAA 人员库、无上报） |

## 四、L2 深挖：辰泽智擎（最危险的对手）

### 4.1 它的定位

官网原文：

> 「面向认证机构、审核员与优秀企业的数智化质量管理生态平台。**智擎·计（审核计划智能编制）已公测**，智擎·审/卓/练持续建设中。」

四大引擎：**计（计划）· 审（检查表）· 卓（企业诊断）· 练（培训）**。

⚠️ **路线图和我们高度重叠**：它做计划 + 检查表 + 企业诊断，我们做计划 + 检查表 + NC/报告。

### 4.2 「智擎·计」实测到的功能细节（逐项摘录）

**① 输入侧：被认证组织信息**

| 字段 | 说明 |
|---|---|
| 认证类型 | **各体系可不同**（如 Q 再认证 / E 初审二阶 / S 监督+变更）。选项：初审一阶、初审二阶、再认证、监督、监督+变更、扩项、缩小、其他 |
| 体系类型 | 多选组合（QE / QES / ES），**五体系 Q/E/S/En/Ec** |
| 组织类型 | 单一组织 / 总部分公司（主从） |
| 产品范围 | 一类产品 → 行业大类 → **专业小类代码**（如变压器 → 大类 19 → 小类 19.09.01） |
| **承接条款** | 本次计划负责的条款范围，**留空 = 审全部**；颗粒度规则：三位条款细化到三位（6.1.1/6.1.2），两位保持两位（6.3） |

**② 审核组侧**

- 角色标记：组长 / 组员 / 正式 / 实习 / 有组长资格 / 无组长资格
- 可审体系 + 可审大类 + **专业小类（每个标风险等级 低/中/高）**
- 专业代码**可多选**，「不选 = 该体系无专业」

**③ 排期方式（★ 和我们设想的不同）**

> 页面**没有按日期自动排班日历**。排期核心 = **日期区间 + 审核天数 + 总人日** 三者联动校验。
> 校验规则原文：「**总人日 > 审核员数 × 审核天数 即预警**」

⇒ **重要修正**：所谓「排班」在认证行业**不是「谁周几去哪」的日历排班**，而是**「人日预算 vs 条款/部门分配」的均衡问题**。日历只是展示。

**④ 部门构成（★ 直接印证 36 号部门维度）**

- **通用职能部门 10 类**：总经理、综合部、采购部、市场部、财务部、设备部、物流部、销售部、员工代表、食堂
- **专业部门 6 类**：
  - 设计研发类（设计部、研发部、设计院）
  - 工艺策划类（工艺部、工程部）
  - 生产作业类（生产部、车间、施工现场、项目部）
  - 质量检验类（质量部、质检部、试验室）
  - 运维服务类（运行维护现场、售后服务部、客服部）
  - E/S 专业（安环部）· En 专业（公用工程部）
- 支持「暂不定分类（待确认）」+ 5 类自定义 + **合并部门**（并入/移除）

**⑤ 条款分工（★ 每个部门预置典型条款）**

示例（Q 体系）：
| 部门类别 | 预置条款 |
|---|---|
| 设计研发类 | 5.3、6.2、7.1.2、7.4、7.5、8.1、8.3、10.2 |
| 工艺策划类 | 5.3、6.1.2、6.2、6.3、7.1.6、7.4、8.1、8.5.1、8.5.6、9.1.1、10.3 |
| 生产作业类 | 5.3、6.2、6.3、7.1.3、7.1.4、7.4、8.5、8.6、8.7 |
| 质量检验类 | 5.3、6.1、6.2、7.1.5、7.4、8.5.2、8.6、8.7、9.1.1、9.1.3、10.2、10.3 |

⇒ **这正是 36 号 §3.6「条款 × 部门」的落地形态**：**部门预置条款库 + 可拖动调整**。

**⑥ 智能分工规则（★ 最值得借鉴，原文摘录）**

> 「① **专业匹配** —— 专业部门优先分给有专业注册的审核员，无专业审核员时**不静默错配**，交由合规校验预警；
> ② **负载平衡** —— 任务自动向已分配部门数少的审核员倾斜，避免集中于个别人；
> ③ **非专业部门向全组开放**，无专业注册的审核员同样承担通用职能条款；
> 分配后可手动改任意审核员审任意部门/条款，复杂任务可多人同审。
> **实习审核员不能独立承担审核任务，须与正式审核员配对**；**组长须具备组长资格**（S4 自动校验）。」

⇒ 「**不静默错配**」这个设计思路值得直接抄 —— 与我们「参数缺失要分清锅的归属」是同一种哲学：**宁可报警，不可猜**。

**⑦ 合规校验（4 类）**

| 校验 | 内容 |
|---|---|
| (a) 部门分配 | 逐部门检查是否有审核员承担 |
| (b) 条款覆盖 | 「承接条款集合」vs「各部门已分派条款并集」是否 100% |
| (c) 体系覆盖 | 实测输出：「✓ Q 体系（再认证）：应覆盖条款已全部覆盖（**76 项**）」 |
| (S4) 组长资格 / 人日 | 组长须有资格；人日不得超载 |

实测输出示例：**「自动冲突检测结果：预警 6 项，通过 1 项」**。

**⑧ 输出**

- 审核计划预览 + 导出（带现场审核日期）
- **E/S 条款输出方式可选**：**合并输出**（同条款号合一行，标识 ES）/ **拆分输出**（E、S 各一行）
- 「生成检查表」公测期未开放 → 引导至「智擎·审」

⇒ ★ **「合并输出 / 拆分输出」正好对应我们在 36 号 §3.7 发现的 `E&H8.2` 多标准合并行**。它把这个做成了**用户可选开关**，而不是固定一种。

### 4.3 「智擎·审」实测到的功能细节

| 项 | 内容 |
|---|---|
| 输入 | 行业小类代码 · **认证体系 Q/E/S/En/Ec** · 组织名称/认证范围/人数（仅抬头） |
| 分工 | 部门 → 条款 → 审核员，三列联动；「**按体系常用部门预填**」一键带出 |
| 组装 | **三段式检查表自动组装（过程 / 骨架 / 增量）** |
| 体系切换 | **五体系条款列自动切换** |
| ★ 拆分 | **「生成总表」/「生成总表 + 按部门拆分」** 两个按钮 |
| 导出 | 打印 / PDF / Excel / Word |
| 定位 | 「确保审核过程**真实、完整、可追溯**」 |

⚠️ **公开页未提及**：证据抽取、证据判定、NC 自动生成、报告生成。**「真实、完整、可追溯」是它对检查表的承诺，不是对证据的承诺。**

### 4.4 它的技术底座（一条有意思的线索）

页面反复出现「**飞书记录模型自动生成项**」「所属审核项目 / 所属审核任务 / 审核员 字段由接口自动填充」⇒ **它建在飞书多维表格之上**，不是自研数据库。

⇒ **含义**：
- 优势：上线快、协作好、零代码改字段
- 劣势：**大表 JOIN、多表关联、复杂统计会撞飞书上限**；证据链这种「一条证据挂 N 个检查项 + 时间戳定位」的关系型查询，飞书表格不是好载体

**这是我们真正的技术差异点**（不是功能差异）。

### 5.2 关键判断

**① 「证据收集」在这个层级的真实形态 = 卷宗附件**

「批量下卷 / 回传 / 在线阅卷 / 图片附件」—— 证据是**审核员把 Word/Excel 卷宗传上来，评审员在线看**。

⇒ **不是结构化证据**：没有「一条证据 = 某个条款 + 某份文件 + 某段原文 + 某个时间戳」的模型。**这正是我们的机会**。

**② 「自动生成上报表」已经是标配**

⇒ 印证了 §六 的结论：**CNCA 上报是硬需求，不做就等于让机构手工录两遍**。

**③ 「专业匹配分数」「自动问题清单」**

说明老牌厂商也在往「半自动」走，但停在**打分和建议**，没到**判定**。

## 六、L3 深挖：国际 CBMS（Zertic / CABflo）

### 6.1 Zertic 的三阶段产品结构（值得抄的产品化思路）

| 阶段 | 定位 | 模块 |
|---|---|---|
| **Phase 1 CONTROL** | 连通的工作流 | CRM · Quotation · **Audit Program** · **Planning** · **Audit Execution** · **NC Management** · Certification · Client Portal · Competence Mgt · API |
| **Phase 2 OPTIMIZE** | 数字化与自动化 | Calculator · **Digital Audit** · Digital Certificates · Time writing · Invoicing |
| **Phase 3 PROPEL** | 数据驱动 | Business Rule Engine · AI Insights · **AI Audit Assistant** |

⇒ **启示**：它把「AI」放在第三阶段，**前两阶段先卖工作流**。这是 to-B 的正确卖法 —— 客户先为「不乱」付费，再为「更快」付费。

### 6.2 Audit Execution 的证据收集细节（★ 最值得学的一段）

原文关键点：

| 能力 | 原文/说明 |
|---|---|
| **一个数字表单装全部** | 「plan, checklist, and review in a single view, scored as you go」 |
| ★ **离线工作** | 「capture evidence on-site **without connectivity**，数据回来自动同步」 |
| ★ **证据就地挂载** | 「capture evidence **directly where it belongs**」—— 证据挂在检查项上，不是挂在文件夹里 |
| ★ **NC 就地升起** | 「flag a clause and it enters the NC workflow **automatically, no re-entry**」 |
| ★★ **逐字段复用上次证据** | 「Per field a **sync button** will populate the evidence if nothing has changed」 |
| 合规约束 | 「To comply with the accreditation rules, the auditor **needs to press sync per field** so data is synced **after the auditor's consent**」 |
| 表单配置 | 「per standard and **version-controlled**，从 **Excel / LibreOffice / XML** 上传配置，含权重、条件问题、答案选项、校验」 |
| 客户参与 | 「clients can answer portal-flagged questions or **upload evidence directly**」 |
| 一键出文件 | 「audit plan, **end-of-audit letter**, and report generated straight from the form」 |
| 历史沿用 | 「Depending on the audit phase, the auditor can select a **previous audit as a basis** for transferring data」 |
| Word 兼容 | 「local standard approach」—— 管流程用 Zertic，审现场用 Word，卷宗挂到任务上 |

**★★ 最重要的一条**：「**逐字段同步按钮 + 审核员主动确认**」

这解决了我们 36 号没解决的一个问题：**第二轮审核怎么复用第一轮证据**。

它的答案是：**不自动复用，让审核员逐字段点「同步」**。理由是认可规则要求「审核员必须确认证据仍然有效」。

⇒ **这直接回答了我们的 D23/D24 争议**：不是「AI 自动沿用」，是「AI 提示可沿用 + 人逐条确认」。

### 6.3 Zertic 对 AI 的立场（★ 行业共识，也是我们的护城河）

原文摘录：

> 「Accreditation has **no room for a confident wrong answer**」（认可没有「自信的错误答案」的容身之地）
>
> 「AI should **accelerate** your people where mistakes can be fixed. Firm **rules** should govern decisions like **competence-based planning**, where they can't.」
>
> 「**Some tools attempt to let a model decide who audits what, and when. In an accredited environment, that is the wrong place to hand over judgement.**」
> （有些工具试图让模型决定谁审什么、什么时候审。在受认可的环境里，这是**交错了判断权**。）
>
> 「Competence, scope, rotation, location, and impartiality are **pass-or-fail requirements, not preferences to optimize**.」
>
> 「Does Zertic offer AI features today? The foundation is built, and the AI is taking shape. Business Rule Engine and DataCube already run in production, with **proof-of-concepts underway for AI-driven BI and AI-generated Audit Plans**.」
>
> 「Will Zertic planning be based on AI? **No, and that's deliberate.**」

⇒ ★★★ **它明确点名批评「让 AI 决定排班」这条路**，而这正是辰泽智擎「智能分工」在做的事。

**这对我们是一个重要信号**：
- 国际主流（受 UKAS/ANAB 认可压力）**不敢**让 AI 定排班
- 国内（CNCA 监管，但机构竞争激烈）**敢**，因为能省人力
- ⇒ **我们的「AI 出建议 + 人确认」正好踩在中间**，两边都能接受

- **公开页未见 AI 相关描述**（比 Zertic 更保守）

## 八、L6：监管强制层（★ 最容易被忽略的硬约束）

### 8.1 审核计划必须上报，字段是定死的

依据：市监认证（司）函〔2021〕102 号 + 《认证认可业务信息统一上报平台》模板。

**审核计划上报 15 个字段（完整）**：

| # | 字段 | 要求 |
|---|---|---|
| 1 | 审核计划编号 | **必填**，机构内唯一 |
| 2 | 被审核组织名称 | 必填 |
| 3 | 统一社会信用代码 | 选填（18 位） |
| 4 | 被审核组织联系人 | 必填 |
| 5 | 被审核组织联系方式 | 必填，多值全角分号分隔 |
| 6 | 审核地址行政区划 | 必填，按《地区行政区划代码》 |
| 7 | 审核地址 | 必填，**需含详细行政区划名称** |
| 8 | 认证项目分类代码 | 必填，体系认证**必须 5 位** |
| 9 | 认证审核阶段代码 | 必填，可多值（同项目全角逗号 / 不同项目全角分号） |
| 10 | **审核方式** | 必填，**FS01 现场 / FS02 远程 / FS03 结合**，与阶段代码一一对应 |
| 11 | 计划开始时间 | 必填，`YYYY-MM-DD HH:00:00` |
| 12 | 计划结束时间 | 必填 |
| 13 | **审核员证件号码、姓名、角色代码** | 必填，**组长在第一位**，成员间全角分号，三值间全角逗号 |
| 14 | 审核技术专家 | 选填 |
| 15 | 备注 | 选填（**不参加全部审核的成员必须在此说明**） |

**审核计划编号规则**（建议）：
- 内资：`R` + 机构顺序号（第 2 位预留扩展默认 0 + 批准号后三位）+ 分支机构代码（2 位）
- 外资：`RF` + ……

**平台侧校验（不通过不予入库）**：
- 审核员证件号、姓名**必须与 CCAA 人员库匹配**
- **资质有效期 > 计划开始日期**
- **审核员必须在上报机构执业**

### 8.2 现场签到监管（微信「认证到」小程序）

依据：国认监〔2021〕3 号。

| 规则 | 内容 |
|---|---|
| 数据来源 | 机构在统一上报平台报计划 → 签到系统**自动提取**生成任务，**无需另报** |
| 签到时点 | **首次会议开始签一次、末次会议结束签一次** |
| 时间窗 | 首签最晚 = 首次会议开始后 **2 小时**（可早于开始，限当天）；末签最晚 = 末次会议结束后 2 小时 |
| 地点 | 任何地点可签，系统记录位置；**偏差 > 5 公里** 提示异常 |
| 照片 | **必须上传首末次会议照片**（1-3 张，含全体成员）；未参加者可传「其他照片」证明到场 |
| 三项异常规则 | ① 未签到 ② 地点偏差 > 5km ③ 未上传照片 |
| 多场所 | 分开上报 ⇒ 每个场所单独签到；报为一条 ⇒ 审核地址用**全角分号**分隔，可在任一地址签到 |
| 涉密单位 | 无法签到/拍照 ⇒ 事后填异常说明 |

### 8.3 这一层的三条设计含义

1. ★★ **「审核计划」不是内部文档，是监管数据** ⇒ 我们的 `cert_audit_session` 必须能**聚合导出成这 15 个字段**，否则机构要手工再录一遍，产品价值打对折
2. ★ **「首末次会议」是法定节点** ⇒ 36 号的「场次」模型里，**首末次会议必须是一等公民**（不能只是普通场次），因为照片、签到、录音告知都挂在这两个点上
3. ★ **「多场所用全角分号」这种细节说明监管数据是文本拼接** ⇒ 我们的结构化模型要能降维成它的格式（而不是反过来）

## 十、对我们的 7 条直接结论

### 结论 1 · 「排班计划」是入场券，不是差异化

三家老牌 ERP 做了十年以上，辰泽已做到「智能编制 + 合规校验」。**这一层拼不过功能广度，只能拼「接得上」**。

⇒ 必须做到：**能一键导出 CNCA 15 字段上报格式**。这是唯一能立刻说服机构用你的点（省一次手工录入）。

### 结论 2 · 「按部门拆分检查表」已被辰泽做了

36 号花了一整章论证「检查项 = 条款 × 部门」，方向**是对的**（辰泽独立走到了同一结论，是交叉验证）。但**它已经不是独占优势**。

⇒ 部门维度仍要做（不做就错），但**不能当卖点讲**。

### 结论 3 · ★★★ 真正的空档是「证据 → 判定」

全网没有找到任何产品做「AI 从企业认证资料/原始资料自动抽取证据 → 三条判定线 → 自动出 NC」。

- 国内老牌：证据 = 卷宗附件，靠人看
- 辰泽：停在检查表组装
- Zertic：**明确拒绝**让 AI 做判定
- ISOPilot：只写文件，不判

⇒ **这是我们唯一值得重投入的地方**，也是 35/36 号文档的价值所在。

### 结论 4 · Zertic 的「逐字段同步确认」直接回答我们的 D23/D24

我们纠结「第二轮怎么复用第一轮证据」。Zertic 的答案：**不自动复用，让审核员逐字段点同步**，理由是认可规则要求「审核员确认证据仍有效」。

⇒ **落进设计**：`cert_check_evidence` 加 `ReusedFromCode` + `ReuseConfirmedBy`，复用必须有人签字。

### 结论 5 · 「AI 出建议 + 人确认」正好踩在国际/国内的中间地带

- 国际：不敢让 AI 定排班（认可压力）
- 国内：敢（省人力）
- 我们：AI 出建议 + 审核员确认

⇒ **这个定位两边都能接受，且与我们已有的 `DeptConfirmedBy` / `RawSnippet 不得改写` 口径一致**。不要为了「更智能」把确认环节去掉。

### 结论 6 · 功能 1（规范化）不能单独卖

ISOPilot 已经 ¥990/年。⇒ 规范化必须**绑在「证据/NC」上卖**，作为「让证据可被 AI 读」的前置步骤，而不是独立产品。

### 结论 7 · 我们的技术差异点在「关系型」，不在「功能」

辰泽建在**飞书多维表格**上（页面反复出现「飞书记录模型自动生成字段」）。它的优势是上线快；劣势是**大表 JOIN、多表关联、复杂统计会撞上限**。

而证据链的本质是**多对多关系查询**：
- 一条证据 → N 个检查项（跨部门引用）
- 一个场次 → N 个部门 → N 个条款
- 一份文件 → N 段证据 → N 个时间戳

⇒ **这是我们能用「关系型数据库 + 工作流引擎」做出它做不出的东西的地方**。不要在「表格好不好用」上跟它比。

## 十五、★★★ 专项核查：「自动证据链」与「自动生成 NC」到底有没有人做到

> 本节是用户 2026-10-20 追问后的**定向核查**（排班和录音都不是重点，重点是这两件事）。
> 结论：**这两件事在认证行业都没有成品；但同构领域已经有跑通的产品。**

### 15.1 一句话结论

| 能力 | 认证行业 | 同构领域 | 判断 |
|---|---|---|---|
| **自动形成证据链**（从企业资料抽证据 → 挂到检查项 → 可追溯） | ❌ **无成品** | ✅ **财务审计有**（DataSnipper / Blast Audit） | **技术已验证，行业未落地** |
| **通过证据链自动生成 NC** | ❌ **无成品** | 🟡 **检测报告有**（IACheck，但是数值判定）；财务审计**不做**（判定留给人） | **真空白** |

### 15.2 ★ 别被「自动生成不符合项」这句话骗了 —— 六家的真实机制

这是本次核查最重要的一张表。**六家都说自己「生成不符合项」，但只有一家是真的在判定。**

| 产品 | 宣称 | 真实机制 | 是「判定」吗 |
|---|---|---|---|
| **世通 AI 认证工作平台**（企业侧） | 「对于发现的不符合项，系统会**自动生成不符合项报告**，并关联对应的体系文件条款，明确整改要求和期限」 | **审核人员在平台实时记录问题** → 系统套模板成文 + 自动派整改任务 + 跟踪 | ❌ **人工记录 → 自动成文**，判定是人做的 |
| **KIRINISO 智辅助手**（企业侧，五洲联合检验认证） | 「输出：内审实施计划、内审检查表、**不符合项报告**、内审报告」 | 企业上传旧手册/程序文件 → AI 按 2026 版条款结构**改写与生成** | ❌ **是「生成文档」，不是「判定」** |
| **辰泽智擎**（机构侧） | 「检查表自动组装」 | 条款 + 部门 → 组装检查表并导出 | ❌ 无证据、无判定 |
| **数通国软**（机构侧） | 「**自动问题清单**」 | 评审员在线阅卷时标注 → 汇总成清单 | ❌ **人工标注后汇总** |
| **Zertic**（机构侧） | 「NC 就地升起，no re-entry」 | 审核员 **flag 一个条款** → 自动进 NC 工作流 | ❌ **人工 flag** |
| ★ **IACheck**（软秦科技，TIC 检测报告） | 「AI 审核，出问题清单，**误差压至 0.5% 以下**」 | **大模型深度萃取 → 结构化 → 百项质检规则库判定** | ✅ **真判定**（但对象是**检测报告**，不是体系证据） |
| ★ **DataSnipper / Blast Audit**（财务审计） | 「AI 抽取证据、自动匹配到工作底稿、**可追溯到源**」 | 文档 OCR → 匹配底稿 → 每条结论**可回溯到源**；**professionals retain control over judgment** | 🟡 **抽证据 ✅，判定留给人** |

**⇒ 一句话**：**「自动生成不符合项」这句话，在整个认证/TIC 行业里，只有检测报告领域（IACheck）是真的在判定；认证审核领域全是「人工记录后自动成文」。**

### 15.3 为什么认证行业没人做（三个真实原因，不是技术不行）

| # | 原因 | 说明 |
|---|---|---|
| ① | **责任** | NC 是法律文件，开错了机构要担责。Zertic 原话：「**no room for a confident wrong answer**」 |
| ② | **证据形态** | 检测报告是**结构化数值**（一个限值 vs 一个结果）⇒ 可规则判定；体系证据是**散落的叙述**（一份记录说明一件事）⇒ 要先结构化才能判 |
| ③ | **准则性质** | 检测报告有「限值」；体系条款是 "shall determine / shall ensure" —— **没有数值边界** ⇒ 只能判「有没有」，很难判「对不对」 |

⇒ **所以真正的技术难点不是「AI 能不能读文档」，是「把叙述性证据结构化到可判定的程度」。**

### 15.4 但技术可行 —— 三个已经跑通的范式

**范式 A · IACheck（检测报告，最接近我们要做的）**

原文关键表述：
> 「没有从规则入手，而是把重点放在**数据处理的起点**，通过大模型能力对报告内容进行**深度萃取**，让原本分散的信息被重新组织成**结构化数据**，这一步虽然不直接体现为审核结果，却**决定了后续所有判断的可靠性**。」
>
> 「IACheck 2.0 通过构建**百项质检规则库**，将这些分散的判断经验转化为**可执行的规则逻辑**……使『AI 报告审核』从经验驱动逐步转向**规则与数据共同驱动**。」

⇒ **三条可直接抄的经验**：
1. **先萃取、再判定**，萃取质量决定判定可靠性（对应我们 32 号分块 + 35 号证据模型）
2. **判定靠规则库，不靠纯大模型**（对应我们 31 号的「三条判定线」应该落成规则，而不是一个 prompt）
3. **把「误差 <0.5%」当核心卖点** ⇒ **准确率必须可测**，否则没人信

**范式 B · DataSnipper / Blast Audit（财务审计，证据链形态）**

- DataSnipper：「AI agents take on work across the full audit lifecycle… while **every output remains traceable to source** and **professionals retain control over judgment and sign-off**」
- Blast Audit：「Extract data from PDFs with OCR, **match documents to workpapers automatically**, and query evidence with AI」+「**Every cell linked to a snip keeps its anchor, source and history**」

⇒ **两条铁律**：
1. **每条结论必须可回溯到源**（文件 + 原文 + 位置）—— 这正是我们 `RawSnippet 不得改写` 的外部印证
2. **判断权留给人**（professionals retain control）—— 与我们「AI 建议 + 人确认」完全同口径

**范式 C · CNAS 官方期刊（行业背书，2024-09）**

《中国认证认可》刊文《人工智能大模型在认可评定审核中的应用探讨》（靳冬、孙晓辰），核心表述：

> 「AI 大模型可以精准地**提取评审报告等材料中的关键要素和要点**……帮助审核人员快速聚焦重点内容，减少无关信息干扰，**准确地发现报告中的潜在问题、异常情况和逻辑漏洞**，还可以结合风险识别分析结果为审核者提供**智能化的辅助决策功能**，提供关于评定结论的建议，降低误判和漏判的风险。」

> 「由于复杂的标准规范体系、专业技术能力要求，**仅依靠大模型短期内难以完全替代人类专家的经验和判断**，需要……探寻更为合理的**人机协作模式**。」

⇒ **两条含义**：
1. **行业权威（CNAS 体系内期刊）认为「AI 发现不符合/逻辑漏洞」是可行的、值得做的**
2. 但明确是「**辅助决策 + 人机协作**」，不是「AI 判定」

⚠️ 注意层次差别：这篇文章讲的是**认可评定**（CNAS 审认证机构），不是**认证审核**（认证机构审企业）。**层次更高一层，但判定逻辑同构。**

### 15.5 ★ 对我们「三条判定线」的重新评估（重要）

36 号定的三条判定线，**自动化的难度完全不同**：

| 判定线 | 内容 | 能自动吗 | 难度 | 建议 |
|---|---|---|---|---|
| **① 完备性** | 证据 vs 应有要素（有没有） | ✅ **能** | 低 | ★ **P1 先做这个**，规则可判、容错高、不涉责任 |
| **② 一致性** | 证据 vs 证据（矛盾不矛盾） | 🟡 **半自动** | 中 | 需先结构化（数值/日期/主体），P2 |
| **③ 符合性** | 证据 vs 准则（对不对） | ⚠️ **最难** | 高 | 准则无边界，只能做「明显缺失」的初筛，P3 |

**⇒ 结论：先做完备性。** 理由：

- 完备性**有确定答案**（要素清单在，缺就是缺），不依赖模型判断力
- 完备性**错了代价低**（提示「可能缺审批人」，审核员一看就知道真假）
- 完备性**恰好是行业最痛**（36 号实测：资料缺口占绝大多数，且「资料缺口非 NC」）
- 完备性**不需要开 NC**（只出「缺口清单」），绕开了责任问题

⇒ **这是唯一能立刻做准、且立刻有用的一段。** 符合性判定可以后置，不要一上来就做。

### 15.6 四条工程结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | **不要用纯大模型判定，要「规则 + 大模型」双引擎** | IACheck 的百项规则库；CNAS 文章「规则和标准」 |
| 2 | **先萃取、再判定，萃取质量决定一切** | IACheck 原文「决定了后续所有判断的可靠性」 |
| 3 | **每条 NC 必须能回溯到源**（文件 + 原文 + 位置） | DataSnipper「traceable to source」· Blast「keeps its anchor, source and history」· 我们 `RawSnippet 不得改写` |
| 4 | **准确率必须可测、可展示** | IACheck 把「<0.5% 误差」当卖点 ⇒ 我们也要有准确率基线（建议：人工标注 200 条做金标准） |

### 15.7 所以机会到底有多大

| 维度 | 判断 |
|---|---|
| 认证审核领域做「自动证据链 + 自动 NC」 | **0 个成品**（本次全网核查未找到） |
| 同构领域是否已跑通 | ✅ **是**（检测报告 IACheck、财务审计 DataSnipper） |
| 技术风险 | **可控**（范式已验证，不是从零探索） |
| 真正的风险 | ⚠️ **准确率 + 责任边界**，不是技术可行性 |
| ⇒ 定性 | **不是技术空白，是行业空白** |

⇒ **这句话可以直接对外讲**：「财务审计和检测报告都已经有 AI 抽取证据的产品，认证审核还没有。」
