# 58 号《条款属性模型与文档匹配设计》评审与补充建议（V1）

> 2026-10-26 ｜ 评审对象：[58-条款属性模型与文档匹配设计-V1.md](58-条款属性模型与文档匹配设计-V1.md)
> 取证方式：MySQL 容器实测 `information_schema` + 源码 + 今日条款树/正文入库结果
> 结论先行：**方向成立，模型未成立**。58 的"为什么"（把检查单四列数字化）是对的；但实体设计混了标准侧与机构侧、与三张既有表职责重叠、阶段开关的取值口径与全库不一致。按现稿直接建表，会得到**第四套并行的条款配置**，且改一处不生效、不报错。

---

## 一、设计意图还原：58 为什么这样设计

58 不是"给标准条款加注释"，而是**把审核员手里那张检查单数字化**。这个起点决定了全部结构：

| 58 的设计选择 | 真实动机 | 出处 |
|---|---|---|
| 属性不是"条款释义"，而是 `RequiredDocs` / `RequiredFields` / `EvidencePoints` | 检查单第 3 列「Audit Evidence 审核证据」要能自动预填 | 58 §一 核心发现 |
| `MissingRule` / `SeverityDefault` / `NcDescriptionTemplate` | 检查单第 4 列「NC/OFI」要能自动出结论草案 | 58 §一 |
| `ChecklistQuestion` | 检查单第 2 列「Requirements 要求」是**提问句**，不是标准原文 | 58 §一、§三 |
| 标准侧一张表装全部（含 `ProcessCode`/`DeptCodes`） | 想让"一次建成、全机构复用"，减少重复录入 | 58 §2.2 表注释「公共知识一次建成」 |
| 12 类属性收敛成 JSON 列 | 单人开发、属性还会长，先不锁死列结构 | 58 §5.2「不要一次加 12 个独立列」 |
| 「确定性优先、LLM 兜底」 | 编号规则（`KSY-QMS-P-17-01`→8.5）是可解析的，不该交给概率模型 | 58 §四 关键点 1、3 |
| 先填核心 20 条再铺全量 | 属性填错比不填更贵，先小步验证 | 58 §5.2 |

**一句话**：58 的隐含假设是「**条款属性 = 检查项的生成模板**」。这个假设本身成立，且与 50 号 §二 的判断一致——问题出在"生成模板"里的机构配方被塞进了标准侧的表。

---

## 二、成立的部分（不要推翻）

1. **方向对**：条款属性是审核自动化的本体，不是附属配置。没有它，"文档来了该找什么"无从谈起。
2. **三个待答问题（有没有文档／字段全不全／缺了算不算 NC）切分准确**，正好对应 证据要求／字段校验／NC 规则 三组属性。
3. **"字段级校验是核心价值"判断正确**：这是与通用 AI 的结构差——通用 AI 能读 PDF，但不知道"特殊岗位名单必须有资格领域和证书编号"。
4. **P0→P3 的排序方向与 50 号 §五 入手顺序一致**（属性 schema 排第 3，前面先做证据池与规则卡片）。

## 三、必须先解决的 5 处冲突（P0，不定不能建表）

### 3.1 机构配方字段进了标准侧表，而新表没有 `OrgCode`

58 §2.2 的实体里同时装了：

- 标准侧（公共知识）：`ShallLevel`、`Applicability`、`RequiredDocsJson`、`EvidencePointsJson`、`DefaultLevel`…
- 机构侧（每家不同）：`ProcessCode`、`DeptCodesJson`、`MergeGroupJson`、`ChecklistQuestion`

但整张表**没有 `OrgCode` 列**。这与 50 号 §一 第 4 条裁决直接冲突：

> 「合并/拆分属于**检查项（机构侧）**，不属于条款属性（标准侧）」—— 50 号原文

**实测对照**（同一批表里的既有做法）：

| 表 | 归属列 | 说明 |
|---|---|---|
| `cert_expert_nc_item` | `OrgCode varchar(50) NOT NULL` | 机构隔离 |
| `cert_validation_rule` | `OrgCode varchar(50) NULL` | 空 = 平台级 |
| `cert_iso_clause` | `OrgCode varchar(50) NULL` | 空 = 平台标准级 |
| **58 的 `cert_iso_clause_attr`** | **无** | ⚠️ 无法隔离 |

**后果**：A 机构把 7.3 的 `DeptCodes` 改成「研发部」，B 机构跟着变；要绕开只能"每机构复制一份属性"，70 条 × N 机构的数据爆炸，且标准换版时无法批量更新。

**建议**：按 50 号裁决拆两张表（见 §五）。

### 3.2 与 `cert_validation_rule` 职责重叠

`cert_validation_rule` 实测列（已存在、已有数据）：

```
OrgCode · StandardCode · PhaseCode · ClauseCode · RuleCode · RuleName
SeverityIfViolated enum('major','minor','observation')
JudgeMode · RuleJson(longtext) · LayoutJson · NcDescriptionTemplate(text)
```

对照 58 的字段：

| 58 字段 | `cert_validation_rule` 已有 | 结论 |
|---|---|---|
| `SeverityDefault` | `SeverityIfViolated` | **重复** |
| `NcDescriptionTemplate` | `NcDescriptionTemplate` | **重复（同名）** |
| `MissingRuleJson` | `RuleJson` | 语义重叠 |
| （未提）| `JudgeMode` | 58 缺，但判定必须有 |
| （未提）| `PhaseCode` | 58 用 `StageSwitch` 替代 → 见 3.4 |

**必须先回答的问题**：条款属性（条款固有）与校验规则（机构/项目配置）的边界在哪？58 的答案是"属性里也放一份默认严重度"，那 `cert_validation_rule` 就是覆盖层——**这成立，但必须写明"58 是默认值，规则是覆盖值，求值顺序 = 规则 > 属性"**，否则两处都改、谁生效无人知道，且不报错。

### 3.3 与 `cert_standard_phase_config` 重复（58 未提及）

实测该表已建（当前 0 行）：

```
cert_standard_phase_config
  OrgCode · StandardCode · PhaseCode · RequiredClauses(json) · RequiredFiles(json)
```

这就是「某标准在某阶段要查哪些条款、要收哪些文件」——**正是 58 的 `StageSwitch` + `RequiredDocs` 想表达的东西**，而且它带 `OrgCode`，归属模型是对的。

58 另起一套 `StageSwitch`（逗号串）⇒ 两处都能配"二阶段查什么"，必然分叉。

**建议**：阶段开关以 `cert_standard_phase_config` 为准，条款属性表**不再存** `StageSwitch`；若确需"条款级默认阶段"，改为 `DefaultStagesJson` 并注明"被 phase_config 覆盖"。

### 3.4 `StageSwitch` 用中文名，与全库阶段码不一致

58 写的是 `"二阶段,监督,再认证"`。全库阶段码实测（`cert_cert_stage`）：

| StageCode | 名称 |
|---|---|
| `S1` | 第一阶段审核 |
| `S2` | 第二阶段审核 |
| `SV` | 监督审核 |
| `RC` | 再认证审核 |

**项目铁律：关联一律用 Code**。存中文名 ⇒ 改名即静默失效（不会报错，只会"配了不生效"）。

⚠️ 另外还有一个既有债务：阶段字段**两套命名并存** —— `PhaseCode`（5 张表：`cert_validation_rule`/`cert_report_section`/`cert_standard_phase_config`/`cert_conclusion_rule`/`wf_execution_task`）与 `StageCode`（30+ 张表）。58 若要新增字段，**必须选 `StageCode`**（多数派 + 新表口径），并在文档里写明"不跟随 PhaseCode 旧命名"。

### 3.5 58 §一 的现状诊断已过期

58 第 15 行写：`Description`「存原文/摘要（**已裁决全部置 NULL**）」。

**2026-10-26 上午已改判并执行**：四标准 273 条条款中 **208 条已回填国标完整正文（53,827 字）**，脚本 `scripts/db/20261026_gbt_standard_clause_text_V1.sql`。

这直接影响 58 的可行性判断——因为**条款正文正是属性提取的输入**（AI 从原文提 `ShallLevel`/`EvidencePoints`，专家校对）。原文回填不是可选项，是前置条件，且已完成。58 应把这一行改为"已完成前置"。

## 四、模型结构性问题（P1）

### 4.1 `RequiredFields` 放错层（影响最大）

58 把「记录必须有的字段」挂在**条款**上：

```json
"RequiredFields": ["设计输入", "设计输出", "设计验证", "设计确认", "设计更改"]
```

但**字段是"产物/表单"的属性，不是"条款"的属性**。同一条款 7.3，A 企业用《设计开发控制程序》+ 附表 1~5，B 企业用《设计输入清单》《验证报告》各自独立。挂在条款上会退化成一张巨大的字段清单，判不出"**哪份文件缺哪个字段**"——而后者才是能写进 NC 的结论。

50 号 §二 写得是对的：`required_artifacts[]`（产物）+ 每份产物有 `artifact_fields[]`（表单 schema 引用）。58 把这两层压成了一层。

**建议**：拆两级（见 §五 表 B / 表 C）。这也是 58 自己 P2 说的"最难填的"——难正是因为放错了层。

### 4.2 `DocPattern` 通配符是弱标识，而"编号规则"根本没建模

58 §四 说"编号规则匹配是确定性逻辑，`KSY-QMS-P-17-01` → 8.5 是一等映射"，但**规则本身没有落点**：存在哪张表、谁维护、段位语义怎么解析、企业换了一套编号体系怎么办？

而 `DocPattern: ["*设计开发*", "*设计*"]` 依赖文件名——实测案例里文件名恰恰不规范（`KSY-QMS-P-17-01`、`XASL-QP-001`、`XASL-QM`）。

**建议**：新增「企业文件编号规则」配置（企业级）：

```
EnterpriseCode · PatternRegex · SegmentSemantics(Json) · ClauseMapRule(Json) · Priority
```

`DocPattern` 降级为**兜底**（编号解析失败时才用），并标注 `confidence=low`。

### 4.3 `ApplicabilityRule` 的求值上下文未定义

```json
"ApplicabilityRule": "{\"exclude_if\": [\"no_design_activity\"]}"
```

`no_design_activity` 从哪来？谁判定？什么时候判定？判错了怎么办？

现有系统里"企业有没有设计活动"这类事实在**企业画像**（`cert_enterprise_doc_profile` 等）与档案字段里，不在条款侧。

**建议**：明确三段——
① 事实来源 = 企业画像字段（列出字段名）；
② 判定时机 = 建档/预审时一次性求值，结果落 `cert_expert_check_item.ApplicabilityOverride`；
③ 判错兜底 = 专家可手工覆盖，覆盖动作留痕（谁改、何时、理由）。

### 4.4 JSON 一刀切与"按属性检索"冲突

58 §5.1 建议"12 类收敛为 3-4 个 JSON 列"。但引擎的真实用法是**按属性筛选**：

- "哪些条款要求程序文件？" → `RequiredDocs` 含"程序文件"
- "二阶段要查哪些条款？" → 阶段过滤
- "哪些条款默认 major？" → 排序/风险权重
- "哪些条款适用性=按产品？" → 生成检查单时裁剪

JSON 列无法建索引，全表扫 + 应用层过滤，70 条尚可、上千条（多标准）就慢。

**建议**：**高频过滤维度用独立列，低频结构用 JSON**——

| 独立列（可索引） | JSON 列 |
|---|---|
| `ShallLevel`、`Applicability`、`DefaultLevel`、`SamplingDepth`、`SeverityDefault`、`DefaultStagesJson`（或走 phase_config） | `RequiredDocsJson`、`EvidencePointsJson`、`VerificationMethodsJson`、`ApplicabilityRuleJson` |

这与 58「不要一次加 12 个独立列」并不矛盾：**6 个标量 + 4 个 JSON**，仍是"不锁死结构"。

### 4.5 `MergeGroup` / `ChecklistQuestion` 方向错误

- `MergeGroup: ["7.3.1"…"7.3.10"]` —— 7.3 本身就是父节点，它的子条款天然成组，此字段冗余；而"**哪些条款可以合并成一次检查**"是检查项/检查单的编排属性（50 号已裁决）。
- `ChecklistQuestion` —— 检查单是**机构资产**，同一标准不同机构问法不同（ACM 与国内机构模板差异已在 47 号记录）。放标准侧 ⇒ 全平台被一家机构的问法锁死。

两者都应移到机构侧检查项表。

## 五、建议的表结构（四表分工，替代 58 §2.2 的单表）

| 表 | 归属 | 职责 | 关键列 |
|---|---|---|---|
| **A. `cert_iso_clause`**（既有，不动） | 平台级 | 条款骨架 + **原文** | `Code` `StandardCode` `ParentCode` `ClauseNumber` `Title` `Description`(原文,已回填) `Sort` |
| **B. `cert_iso_clause_attr`**（新建） | 平台级（`OrgCode` 恒空，防误用可保留列） | 条款固有属性（标准侧） | `ClauseCode`(UK) `ShallLevel` `Applicability` `ApplicabilityRuleJson` `DefaultLevel` `SamplingDepth` `SeverityDefault` `MissingRuleJson` `EvidencePointsJson` `VerificationMethodsJson` `NcDescriptionTemplate` `AiConfidence` `AiSource` `ReviewStatus` |
| **C. `cert_iso_clause_artifact`**（新建） | 平台级 | 条款 → 应有产物（一级） | `ClauseCode` `ArtifactName` `ArtifactType`(程序/记录/报告/计划) `DocPatternJson` `FormSchemaCode`(→D) `IsMandatory` `LLevel` `Sort` |
| **D. `cert_doc_form_schema`**（新建） | 平台级 | 产物 → 必备字段（二级，可复用可版本化） | `Code` `SchemaName` `FieldsJson`([{key,label,required,type,rule}]) `Version` |
| **E. `cert_expert_check_item`**（后续，机构侧） | `OrgCode` 隔离 | 机构配方 | `OrgCode` `ClauseCodesJson`(M:N) `StandardCodesJson` `StageCodesJson` `ProcessCode` `DeptCodesJson` `MergeGroupJson` `QuestionOverride` `SeverityOverride` `ApplicabilityOverride` |

> 表 D 是 58 缺的那一层，也是"字段级校验"真正落地的地方：**校验对象是"某份文件是否符合某个 form schema"，不是"条款字段清单"**。

**58 的 12 类属性按此归位**：

| 58 属性 | 归位 |
|---|---|
| `ShallLevel` `Applicability` `ApplicabilityRule` `DefaultLevel` `SamplingDepth` `SeverityDefault` `MissingRule` `NcDescriptionTemplate` `EvidencePoints` `VerificationMethods` | 表 B |
| `RequiredDocs` `DocPatterns` | 表 C（拆成"产物行"） |
| `RequiredFields` | 表 D |
| `ProcessCode` `DeptCodes` `MergeGroup` `ChecklistQuestion` | 表 E（机构侧） |
| `StageSwitch` | 以 `cert_standard_phase_config` 为准，表 B 不存 |
| `AiConfidence` `AiSource` `ReviewStatus` | 表 B（另加 `ReviewBy`/`ReviewTime`，`BaseEntity` 的 `UpdateBy` 不等于"审核通过"） |

## 六、落地路径（替代 58 §5.1 的 P0-P3）

58 的 P0「扩 `cert_iso_clause` 加 `AttributesJson` 大字段」建议**不要做**——把属性写进条款主表会让"标准换版时重建条款树"变成高危操作（今日重建 13485 条款树时，若属性在主表内，会一并丢失）。

建议改为：

| 步 | 内容 | 出口判据 | 量级 |
|---|---|---|---|
| **S0** | 定边界：写一页四表分工（§五），**先不建表** | 四表职责无重叠、无缺列 | 0.5 天 |
| **S1** | **单条款端到端**：选 4.2.4 或 7.3，用科斯亚真实文件跑通 编号解析 → 文档匹配 → 字段校验 → 疑点 → 人工确认 | 能对 1 条条款产出 1 条可复核疑点 | 1 天 |
| **S2** | 按 S1 暴露的缺项定 DDL，只建**用到的列** | S1 的链路不改代码即可配第 2 条条款 | 0.5 天 |
| **S3** | 属性填充**按证据强度排序**，不按条款号：先填"案例里有真实文件可对照"的条款 | 每条属性都能指到一份真实文件 | 分批 |
| **S4** | 表单 schema（表 D）从案例文件逐份提，做成**可复用模板**，不是一次性文本 | 同一 schema 能被 ≥2 个条款引用 | 分批 |

> 与 50 号 §五 的顺序一致：证据池 → 规则卡片 → 属性 schema。58 若先铺 70 条属性再验证，返工成本最高。

## 七、指标修订（替代 58 §5.3）

58 的「映射准确率 ≥80%（编号匹配）」口径不成立——**编号匹配是确定性逻辑，应 100%；<100% 说明规则写错了，不是"准确率不够"**。建议改为分层指标：

| 指标 | 定义 | 目标 | 为什么 |
|---|---|---|---|
| **编号规则覆盖率** | 能被编号规则解析的文件 / 全部文件 | ≥ 85% | 剩余 15% 走语义兜底（低置信度） |
| **文档匹配精确率** | 人工抽检 30 条，匹配正确的比例 | ≥ 90% | 误匹配会让专家白读，比漏匹配更伤信任 |
| **字段校验假阴性率** | 判"缺失"但实际存在的比例 | **≤ 2%** | ⚠️ 说企业缺证据却没缺 ⇒ 直接冤枉企业，是产品红线 |
| **字段校验假阳性率** | 判"存在"但实际缺失 | ≤ 15% | 漏判由人工兜底，可容忍度更高 |
| **人工确认率** | 低置信度结果占比 | ≤ 20% | 同 58 |
| **误报率（按规则聚类）** | 驳回数 / 命中数 | 逐版下降 | 51 号 §四 反馈环的度量 |

## 九、一句话结论

**58 想清楚"为什么"，但没想清楚"放哪里"。** 把机构配方从标准侧剥出去、把字段从条款层下沉到表单层、阶段开关复用既有表、属性主表独立于条款主表——这四刀切完，58 就是一个可以直接施工的模型；不切，它会变成第四套并行配置。
