## 一、两类补录/日志的边界

| 维度 | 补录日志 | 认可/修改日志 |
|---|---|---|
| 记什么 | **人工改了提取结果的值** | **专家认可/修改了任务项结果** |
| 表 | `cert_extraction_change_log` | `cert_expert_task_log` |
| 对象 | 字段值 / 表格值（数据源层） | 检查项结论 / 章节正文（结果层） |
| 触发端点 | `PUT /api/ExpertTaskDataGap/{gapCode}/fill` | `POST /api/ExpertTaskItem/{code}/acknowledge` · `/modify` |
| 生命周期 | 跨任务（值改了所有任务都受益） | 任务内（任务批准后冻结） |
| 回答的问题 | 「这个数据哪来的、谁改的」 | 「这个结论谁认可的、改了什么」 |

> **两者不可合并**：对象层级不同（数据源 vs 结论），生命周期不同，追溯路径不同。合并会导致查询时无法按层级过滤。

## 二、数据缺口检测

### 2.1 ★ 提取结果的 `OrgCode` 存的是企业 Code

这是一个极易踩的坑，必须先说清。

```csharp
// certplatform-api/CertPlatform.Shared/Entities/Doc/ExtractionResult.cs:20-23
/// <summary>标准企业标识（多租户隔离，映射到 DB OrgCode 列）</summary>
[Required, StringLength(36)]
[SugarColumn(ColumnName = "OrgCode")]
public string EnterpriseCode { get; set; }
```

**结论**：`cert_extraction_result.OrgCode` 列里存的是**企业 Code**，不是认证机构 Code，也不是专家工作区 Code。

> 背景：该表原名 `ent_extraction_result`（企业域），`OrgCode` 语义随 `ent_` → `cert_` 改名时被保留（见 `fix-restore-extraction-result-2026-09-25.sql`）。改名时列语义未变，导致 `OrgCode` 名字与内容不符。
>
> ⛔ **不改列名**（会破坏 10 号分册的所有查询），但**必须在实体注释里加醒目警告**，并在本文档固化。
>
> ★ **2026-09-29 用户裁决：选方案乙**（保留 `OrgCode` 列名，视作「机构/归属代码」）。
> - 完整三域规范（认证机构 / 专家工作区 / 企业）见 [02 号 §9.1](02-详细设计-任务与队列-V1.md) 与 [14 号 N8](14-表命名规范-V1.md)
> - **实测证据**：该列实际有 3 种值 —— `42833c3d3fe2...`(15 行，某企业) / `TEST-ENT-0001`(7 行，测试) / ★ `YZH-STD-ENT`(1 行，模板数据)
> - ⛔ `YZH-STD-ENT` 一律用 `YzhVirtualEnterprise.Code` 引用，**禁写字面量**（`YzhVirtualEnterprise.cs:8` 已明令）
> - ⚠️ **S2.5 收口 `docField` 时必须显式分叉**（模板数据 vs 企业数据读法不同），否则会读串

### 2.2 读取契约（唯一口径）

> ⚠️ **2026-09-29 实测修正（B6）**：`NodeExecutor.ExecuteDocFieldAsync` 的现存取数口径**有缺陷**，本设计必须绕开。

**现存代码的真实口径**（`NodeExecutor.cs:~330`）：

```csharp
// ⛔ 缺陷 1：没有 StandardCode / StageCode 过滤（★ 列名是 StageCode，见 17 号 E-2）
// ⛔ 缺陷 2：没有 IsValid = 1 过滤 → 会读到归档的旧版本
// ⛔ 缺陷 3：没有 FileCode 过滤     → 企业有多份文件时取到哪份不确定
var field = (await _db.GetOneAsync<ExtractionResult>(x =>
    x.FieldCode == fieldCode && x.EnterpriseCode == enterpriseCode)).Data;
```

> 注：`GetFieldSkill.cs:63` 里有 `byFile = fields.Where(x => x.FileCode == file_code)` 的二次筛选，但那是 `skill` 节点的路径，**`docfield` 节点没有**。两条路径口径不一致。

**本设计的正确口径**：

```sql
SELECT *
FROM cert_extraction_result
WHERE OrgCode        = @enterpriseCode     -- ★ 存的是企业 Code（见 §2.1）
  AND StandardCode   = @standardCode       -- ★ 必须（NodeExecutor 缺此项）
  AND ★ StageCode    = @stageCode          -- ★ 必须（NodeExecutor 缺此项）
  -- ★★ 实测：cert_extraction_result 无 PhaseCode 列，是 StageCode（17 号 E-2）
  AND IsValid        = 1                   -- ★ 必须（NodeExecutor 缺此项 → 会读到归档旧版本）
  AND IsDeleted      = 0
ORDER BY FieldCode;
```

**三个修复项的必要性**：

| 缺失项 | 后果 |
|---|---|
| `StandardCode` | 多标准认证时，ISO9001 的规则会读到 ISO14001 的提取值 |
| `StageCode` | 同企业不同阶段的提取结果串（★ 实测列名，17 号 E-2） |
| `IsValid = 1` | ★ **最严重**：文件替换后旧版本被 `InvalidateActiveAsync` 归档（`IsValid=0`），但 `GetOneAsync` 仍可能取到它 → **拿旧文件的数据算出新结论** |
| `FileCode` | 同企业多份文件（质量手册 / 程序文件 / 作业指导书）各含同名字段时取到哪份不确定 |

**实现方式**：

```csharp
/// <summary>
/// 读取某企业某标准某阶段的【当前有效】提取结果。
/// ★ 唯一口径：NC 检查 / 报告生成 / 完备性检查都必须调这个方法。
/// ⛔ 禁止调用 NodeExecutor 的 docfield/doctable 节点取数（口径有缺陷，见 §2.2）
///    —— 本模块自己取数后注入 context.ExtractionData。
/// </summary>
public async Task<IReadOnlyList<ExtractionResult>> GetActiveAsync(
    string enterpriseCode, string standardCode, string stageCode);
```

> **执行时如何绕过 NodeExecutor 的缺陷**：`WorkflowInterpreter.RunAsync` 的 `context` 中预置 `ExtractionData`
> （= `GetActiveAsync` 的结果），并让 `docfield` 节点**改从 `context.ExtractionData` 读**而非查库。
> 这是对 `NodeExecutor` 的一处框架层改造（`src/yzh-core` 之外的业务层，允许改，见 AGENTS.md 第 11 条）。
> 若不改 `NodeExecutor`，则**必须**在 S0 阶段一并修（列入阻塞项 A5）。

### 2.3 接口签名与字段级

```csharp

public async Task<IReadOnlyList<ExtractionResult>> GetActiveByScopeAsync(
    string enterpriseCode, string? standardCode, string? stageCode);

/// <summary>★ 表格级同样必须走唯一口径（原设计遗漏，评审 P1-24）</summary>
public async Task<IReadOnlyList<TableExtractionResult>> GetActiveTablesByScopeAsync(
    string enterpriseCode, string? standardCode, string? stageCode);
```

> ⚠️ **两个方法都不存在，需新增**。`EnterpriseExtractionResultStore.cs:99` 的现存签名是 `GetActiveAsync(enterpriseCode, fileCode, versionNumber)`（★ **按文件**），服务于企业资料管理的替换/恢复流程。
>
> ⛔ **不改现有签名**（会破坏替换/恢复链），**新增 `ByScope` 重载**。
>
> ★ 命名带 `ByScope` 而非同名重载，是为了在编译期就能区分两种语义（按文件 vs 按标准+阶段）—— 这正是 09 号 H11「ScopeKey 双口径」教训的延伸。

**SQL 实现**：

```sql
SELECT *
FROM cert_extraction_result
WHERE OrgCode        = @enterpriseCode     -- ★ 存的是企业 Code
  AND IsValid        = 1                   -- ★ 1=当前版本，0=归档旧版本
  AND IsDeleted      = 0
  AND (@standardCode IS NULL OR StandardCode = @standardCode)
  AND (@stageCode    IS NULL OR ★ StageCode  = @stageCode)
ORDER BY FieldCode;
```

**为什么这三个条件缺一不可**：

| 条件 | 缺失后果 |
|---|---|
| `OrgCode = 企业Code` | **跨企业数据串**（最严重） |
| `IsValid = 1` | 读到文件旧版本的提取结果 —— 专家替换过文件后，跑出来的是旧数据结论 |
| `IsDeleted = 0` | 读到已软删的提取结果 |

> ⚠️ `GetExtractionResultAsync` 现存缺陷（10 号分册 S2 提到）：「补 `VersionNumber` 过滤」。`GetActiveAsync` 必须正确实现 `IsValid=1` 语义，不能只按 `VersionNumber` 取最大。

> ⚠️ 表格表**缺 `IsManualEdited` 与 `ValueSource`**（字段级表有），本期补齐（见 [06 号 §4.3](06-数据库设计-V1.md)）。不对称会导致表格补录不留痕。

> ⚠️ 表格表**无唯一约束**（09 号分册 H13）。企业可能有多份文件各含一张同名字段表。取数策略见 [10 号 Q4](10-待裁决问题-V1.md)（默认：规则节点配 `FileCode` 精确指定）。

### 2.4 缺口的判定

```csharp
bool IsFieldMissing(ExtractionResult? r)
    => r == null || string.IsNullOrWhiteSpace(r.ExtractedValue);

bool IsTableMissing(TableExtractionResult? r)
{
    if (r == null) return true;
    if (string.IsNullOrWhiteSpace(r.ExtractedJson)) return true;
    // JSON 解析后判断是否空表
    var rows = JsonSerializer.Deserialize<JsonElement>(r.ExtractedJson);
    if (rows.ValueKind != JsonValueKind.Array) return true;
    return rows.GetArrayLength() == 0;
}
```

> **空字符串 = 缺**：`ExtractedValue = ""` 说明字段提取了但没内容，与"字段根本没提取"在业务上等价 —— 都是"这条规则跑不了"。

### 2.5 多规则共享同一字段 → 多条 gap

```
规则 A（8.4 文件控制）  ──依赖──▶ FieldCode=F001（文件编号规则）
规则 B（7.5 成文信息）  ──依赖──▶ FieldCode=F001
规则 C（7.1 总要求）   ──依赖──▶ FieldCode=F002（组织架构）

若 F001 缺失：
  → 2 条 gap 记录（SourceItemCode 分别为 规则A.Code、规则B.Code）
  → 但补录时只需填 1 次值（按 FieldCode 去重）
  → 界面展示聚合为：1 个字段缺失，影响 2 条规则
```

**`cert_expert_task_data_gap` 记录粒度**：`FieldCode` × `SourceItemCode`（规则级）。
**界面展示粒度**：`FieldCode`（字段级），带「影响 N 条规则」标注。
**补录粒度**：`FieldCode`（一次填全部关联 gap 变 `filled`）。

## 三、补录清单数据结构

`cert_expert_task_data_gap` 一行 = 一个「字段/表格 × 依赖它的规则」：

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) | 业务键 |
| `OrgCode` | varchar(50) | 专家工作区（租户） |
| `TaskCode` | varchar(36) | 所属任务 |
| `SubTaskCode` | varchar(36) | 所属标准子任务 |
| `StandardCode` / `StageCode` / `EnterpriseCode` | varchar(36) | 冗余，便于按标准查 |
| `GapType` | varchar(20) | `field` / `table` |
| `GapLabel` | varchar(200) | 展示名（字段名或表格名） |
| ★ `RuleCode` | varchar(36) | **25 号补**：规则 Code。J4「1 文件 = 1 规则」⇒ 取数与清理的主键成分 |
| `FieldCode` | varchar(36) | 字段级才有 |
| `TableCode` | varchar(200) | 表格级才有 |
| `StandardFileCode` | varchar(200) | 该数据应来自哪个标准文件。★ **仅作只读提示列**，25 号 J1「不分文档」⇒ 不作分组键、不作存储键 |
| `SourceItemType` | varchar(20) | `nc_check` / `report_section` |
| `SourceItemCode` | varchar(36) | 依赖它的规则/章节 Code。★ **不再进 `GapKey`**（记录粒度已降为 `FieldCode`） |
| `SourceItemName` | varchar(200) | 冗余名称 |
| `ClauseCode` | varchar(36) | 规则关联的条款 |
| `GapStatus` | varchar(20) | `pending` / `filled` / `skipped` |
| `FilledValue` | text | 补录的值（快照） |
| `FilledBy` / `FilledByName` / `FilledTime` | | 补录人 |
| `SkipBy` / `SkipByName` / `SkipTime` / `SkipReason` | | 跳过信息 |
| `CreateTime` / `UpdateTime` / `IsValid` | | |

> `FilledValue` 存快照的理由：补录的值会写进 `cert_extraction_result`，若该值后来又被改了（重新提取覆盖 / 按 `RuleCode` 归档），此记录仍能还原"任务创建时补的是什么"。

> ★ **25 号 J1 修正 `GapKey` 生成列**：
> ```
> 原：CONCAT(GapType,'|',FieldCode,'|',TableCode,'|',SourceItemCode)   -- 规则级，N 条规则 ⇒ N 条 gap
> 新：CONCAT(GapType,'|',RuleCode,'|',IFNULL(FieldCode,'-'),'|',IFNULL(TableCode,'-'))   -- 字段级，1 条 = 1 个待补项
> ```
> 「影响 N 条规则」改由**前端按 DAG 实时反查**展示。理由：规则是业务配置、变动频繁，gap 是任务快照，落库 `SourceItemCode` 会导致两者漂移。

## 四、人工补录（D06：不新建补录表）

### 4.1 补录 = 编辑提取结果

用户裁决 D06 原文：

> 「我们有企业文档，自动提取出来的字段和表格数据结构表，我们最好针对这两个表增加日志，如果是通过内容提取规则形成的数据，值的类型是**系统自动计算**，如果是**手动修改的**，则填写**人工录入**，并记录日志，一个字段，一个表格，可以反复由人员进行更改」

**结论**：补录不落独立表，**直接写 `cert_extraction_result` / `cert_table_extraction_result`**，并：
1. 把 `ValueSource` 从 `auto` 改为 `manual`
2. `IsManualEdited` 置 1
3. 记一条 `cert_extraction_change_log`

### 4.2 补录端点逻辑

```
PUT /api/ExpertTaskDataGap/{gapCode}/fill
  Body: { Value: string, Remark? }

  事务：
  ① 校验 gap 存在且 GapStatus='pending'
  ② 按 GapType 分流：

     字段级：
     a. 取 StandardFileCode（应归属的标准文件）
     b. 在 cert_extraction_result 中找 (OrgCode=企业, FileCode=该文件, FieldCode)
        找到 → UPDATE（改值）；找不到 → INSERT（新建一行提取结果）
     c. ★ 必须归档旧版本（用 `InvalidateActiveAsync`，★ 17 号实测：**没有** `ArchiveAsync`）
        若该文件已有当前版本行 → 置 IsValid=0，再插入 IsValid=1 的新行
        → 这样其他任务若引用了旧版本，不会被静默改掉
     d. 更新：ExtractedValue / ValueSource='manual' / IsManualEdited=1 / ModifyBy / ModifyTime
     e. 若 Confidence 原本是 AI 给的 → 置 NULL（人工录入无 AI 置信度）

     表格级：
     a. 同上，Value 是 JSON 字符串
     b. cert_table_extraction_result 目前【无 FileCode 唯一约束】，
        查找条件：OrgCode + TableCode + IsValid=1
        → ⚠️ 需先补唯一键（见 06 号 §4.3），否则可能命中多行

  ③ 记 cert_extraction_change_log（见 §5）
  ④ 把【所有 FieldCode/TableCode 相同】的 pending gap → GapStatus='filled'
     ★ 不是只填这一条：一个字段被 3 条规则依赖时，一次补录解决 3 条 gap
  ⑤ 回写 cert_expert_task.GapCount（-受影响条数）
```

### 4.3 批量补录

```
POST /api/ExpertTaskDataGap/batch-fill
  Body: { Items: [{ GapCode, Value }[]], Remark? }

  逐条执行 §4.2 的逻辑，单事务。
  失败策略：整体回滚（避免部分成功导致数据不一致）。
  上限：单次 200 条。
```

### 4.4 跳过

```
POST /api/ExpertTask/{code}/skip-all-gaps
  → 该任务下所有 GapStatus='pending' → 'skipped'

POST /api/ExpertTaskDataGap/{gapCode}/skip
  Body: { Reason? }
  → 单条 → 'skipped'
```

**跳过后能否反悔**：可以。专家可再次点 [去补录] 补录，跳过的 gap 会转 `filled`，对应任务项可 [重新执行]（02 号 §5）。

### 4.5 补录后的重新执行

```
补录成功 → 界面提示「已补录 N 项，涉及 M 条检查项，是否重新执行？」
  → POST /api/ExpertTask/{code}/rerun  { ItemCodes: [受影响的 M 条], ResetReview: true }
```

> **只重跑受影响的项**，不重跑全部。避免浪费 LLM 配额（一个任务 40 条，全跑一次可能几十分钟）。

## 五、补录日志（`cert_extraction_change_log`）

### 5.1 日志表设计

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) | 业务键 |
| `OrgCode` | varchar(50) | ★ 专家工作区（补录人所属） |
| `ResultType` | varchar(20) | `field` / `table` |
| `ResultCode` | varchar(36) | `cert_extraction_result.Code` 或 `cert_table_extraction_result.Code` |
| `EnterpriseCode` | varchar(36) | 冗余（注意：提取结果的 OrgCode 列存的是这个值） |
| `StandardCode` / `StageCode` / `StandardFileCode` / `FileCode` | varchar | 冗余，便于按维度查 |
| `FieldCode` / `TableCode` | varchar | 冗余 |
| `FieldLabel` | varchar(200) | 展示名快照 |
| `ChangeAction` | varchar(20) | `manual_edit` / `restore_auto` / `archive` |
| `OldValue` | text | 旧值（截断至 60000 字符，MySQL TEXT 上限 65535） |
| `NewValue` | text | 新值 |
| `OldValueSource` | varchar(20) | `auto` / `manual` / `null`（原先不存在该行） |
| `NewValueSource` | varchar(20) | `manual` / `auto` |
| `OperatorCode` | varchar(50) | 操作人 |
| `OperatorName` | varchar(100) | 操作人姓名（冗余，防用户改名后追溯断裂） |
| `OperateTime` | datetime | |
| `TaskCode` | varchar(36) | ★ 哪个任务触发的补录（可空，手动改提取结果时为空） |
| `Remark` | varchar(500) | |
| `CreateTime` / `IsValid` | | |

### 5.2 「一个字段可反复修改」的表达

```
时间线（同一 FieldCode=F001）：
  2026-09-20 10:00  auto      "3年"        ← AI 自动提取
  2026-09-25 14:30  manual    "5年"        ← 专家 A 补录
  2026-09-26 09:15  manual    "5年"        ← 专家 B 改（值相同也要记，因为是显式动作）
  2026-09-28 16:20  manual    "3年"        ← 专家 A 改回
  2026-09-29 10:00  auto      "3年"        ← 重新提取，覆盖了人工值
```

**5 条日志记录，完整还原**。`cert_extraction_result` 当前行只存最后一条（`"3年"`，`ValueSource='auto'`）。

> **「值相同也要记」的理由**：专家 B 打开了编辑框、确认、保存，这是一次有意的确认动作。审计上"他看过并认可了这个值"和"没人看过"是两回事。日志只追加，永不修改。

### 5.3 `restore_auto` 的场景

专家手工改完后，文件被替换触发重新提取 → 新值覆盖了人工值。这是**系统行为导致的人工值丢失**，必须留痕：

```
ChangeAction = 'archive'，OldValue = "5年"（人工值），NewValue = "3年"（新提取值）
```

同时弹窗提示专家：「您之前对『文件编号规则』的人工补录值已被新的自动提取覆盖，是否需要重新补录？」

## 六、认可/修改日志（`cert_expert_task_log`）

### 6.1 日志表设计

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) | 业务键 |
| `OrgCode` | varchar(50) | 租户 |
| `TaskCode` / `SubTaskCode` | varchar(36) | 冗余，便于按任务查 |
| `TaskItemCode` | varchar(36) | 任务项 |
| `ItemType` | varchar(20) | `nc_check` / `report_section` |
| `StandardCode` | varchar(36) | 冗余 |
| `LogAction` | varchar(20) | 见 §6.2 |
| `FieldName` | varchar(50) | 改的哪个字段（`ACKNOWLEDGE` 时为 null） |
| `FieldLabel` | varchar(100) | 字段中文名 |
| `OldValue` | text | 旧值 |
| `NewValue` | text | 新值 |
| `OldValueText` | longtext | 长文本旧值（章节正文用） |
| `NewValueText` | longtext | 长文本新值 |
| `BeforeStatus` | varchar(20) | 改前 `ReviewStatus` |
| `AfterStatus` | varchar(20) | 改后 |
| `IsAutoResult` | tinyint(1) | 该条操作针对的是否自动生成的结果 |
| `OperatorCode` | varchar(50) | |
| `OperatorName` | varchar(100) | 冗余 |
| `OperateTime` | datetime | |
| `Remark` | varchar(500) | |
| `ClientIp` | varchar(50) | 可选，见 10 号 Q9 |
| `CreateTime` / `IsValid` | | |

### 6.2 四种动作

| `LogAction` | 何时写 | 写几条 |
|---|---|---|
| `ACKNOWLEDGE` | 专家点 [认可]，结果未改动 | 1 条（不带 diff） |
| `MODIFY` | 专家点 [保存并认可] / [恢复为 AI 原文] | ★ 改几个字段写几条（逐字段 diff） |
| `AUTO_GENERATE` | 队列执行产出自动结果 | 1 条（记录自动结果摘要，便于与专家结果对比） |
| `AUTO_FAIL` | 队列执行失败 | 1 条（记录错误摘要） |
| `SKIP` | 任务项被标记跳过 | 1 条（记录 `SkipCategory` + `SkipReason`） |

> `AUTO_GENERATE` 让日志成为**完整时间线**：自动生成 → 专家改 → 再改 → 认可，一眼看清。代价是每项多 1 行日志（40 项 = 40 行，可接受）。

### 6.3 逐字段 diff 的示例

专家把 NC 结论从 `conform` 改成 `nonconform`，严重度从 null 改成 `major`：

```
cert_expert_task_log:
  ① LogAction=MODIFY, FieldName=Conformity,  OldValue=conform,  NewValue=nonconform,
     BeforeStatus=acknowledged, AfterStatus=modified
  ② LogAction=MODIFY, FieldName=Severity,    OldValue=(空),     NewValue=major,
     BeforeStatus=modified,     AfterStatus=modified
```

前端 diff 展示：把 ① ② 合成一条"此条结果有 2 处修改"，展开看逐字段。

> **报告章节正文**的 diff 特殊：正文可能上千字符，存两列 `OldValueText` / `NewValueText`（`longtext`）。前端不全文展示，只显示"行数从 X 变 Y" + 前 3 行差异，需要时展开全文。

### 6.4 任务级日志

`cert_expert_task_log` 记任务整体动作（`CREATE` / `SUBMIT` / `APPROVE` / `CANCEL` / `RERUN` / `SKIP_ALL_GAPS` / `EXPORT`）。字段少，但审计时需要知道"任务是什么时候被批准的"。

> 是否需要独立表：可以并入 `cert_expert_task_log`（`TaskItemCode=NULL` 表示任务级）。**本期采用合并方案**，不建第五张日志表。

## 八、日志的不可变性

> **铁律：日志表只允许 `INSERT` 和 `SELECT`，代码中禁止出现 `UPDATE` / `DELETE`。**

| 表 | 允许操作 | 理由 |
|---|---|---|
| `cert_expert_task_log` | INSERT / SELECT | 审计凭据。改了就失去意义 |
| `cert_extraction_change_log` | INSERT / SELECT | 同上 |
| `cert_expert_task_data_gap` | INSERT / UPDATE | ★ 例外：gap 的状态流转（pending→filled/skipped）是业务状态，不是审计日志 |

**代码级保障**（建议）：
```csharp
// 在这两个实体上加只读标记，或用 SqlSugar 的全局过滤器拦截
// 最简做法：在 Repository 层不提供 Update/Delete 方法，并在 code review 检查项里列出
```

**软删除怎么办**：`IsValid` 字段存在但**不使用**。日志不删。需要"作废"某条日志时，用 `ChangeAction` 新增一条反向记录（`revoke`），而不是改原记录。
