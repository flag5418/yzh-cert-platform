# 程序架构收敛：五层模型与条款属性 Schema（V1）

> 2026-10-23 ｜ 回应用户五条架构理解 ｜ 前置：47（战略收敛）· 48（试跑报告）· 49（疑点 POC）
> 结论先行：用户五条理解全部成立；本稿做逐条校准、补齐三个缺口、定稿 schema 与入手顺序。

## 一、五条理解的校准

| # | 用户理解 | 裁决 | 校准要点 |
|---|---|---|---|
| 1 | 企业文档采集时自动分析对应条款＋内容（markdown/语义/pdf） | ✅ 成立，但须分层 | ① 映射**确定性优先**：企业编号规则（`KSY-QMS-P-17-01`→8.5）、表单命名先解析，语义分析兜底；② 解析深度须到**表单字段级**（特殊岗位名单的"资格领域/证书编号"字段在不在，是声称-证据规则的输入，散文级 markdown 不够）；③ 扫描件（校准台账、GBT 42061）OCR 是前置工序；④ 映射结果落库为资产（条款↔文档映射表），AI 建议＋人工确认 |
| 2 | 条款要设计一系列规则/标签（强制性/适用范围/约定材料/材料字段/检查方法/验证程度） | ✅ 成立，这是标准模型的本体 | 见 §二 schema。须补 6 个属性：阶段开关、适用性判定规则、L 层来源、法规挂接、默认严重度＋判定模式、合并/拆分提示 |
| 3 | 通用引擎分预审（入场前）与审核证据生成，强约束执行 | ✅ 成立 | "强约束"的准确含义：规则=结构化条件（触发/输入/输出/严重度），**执行期无 LLM**——LLM 只在预处理（实例抽取）与后渲染（措辞）；两模式共用引擎、不同管线（预审输入=全量文档＋历史，输出=疑点清单＋入场计划；审核输入=文档＋现场采集，输出=双栏预填件＋NC 候选） |
| 4 | 条款可合并/须拆分/不同企业可查条款不同/专家组织编辑/三体系合并计划 | ✅ 成立，一处关键精确 | 合并/拆分属于**检查项（机构侧）**，不属于条款属性（标准侧）——ACM 实证：同标准一阶段主题式（风险管理过程涵盖 4.1.5/7.1 家族）、二阶段逐条 1:1；"不同企业可查不同"要分两回事：① **适用性**（7.3 按产品裁，且"理由成不成立"本身是检查项）② **阶段开关**。专家编辑的是机构配方，条款是公共知识（标准驱动、机构调味） |
| 5 | 入场＋现场证据收集也要做；先做认证准备阶段（独立产品）＋二阶段认证（真实产品）两块 | ✅ 成立，与既定路线一致 | 认证准备阶段=企业侧迎审准备/自检（引擎"预审模式"的消费者，兼获客楔子＋数据地基）；二阶段=主产品（引擎"审核模式"＋现场采集端 L1 入口）。**现场采集不可整体后移**——它是二阶段 L1 证据的唯一来源，v1 至少给结构化槽位表单 |

## 二、条款属性 Schema（标准侧，每条一款，公共知识一次建成）

| 字段 | 说明 | 实证来源 |
|---|---|---|
| clause_code / standard_code | 条款号＋标准 | 13485 条款树（GBT OCR 后建） |
| text_original_zh/en | 中英双语原文 | ACM QR-04-72 Requirements 列即原文 |
| shall_level | shall / should / may | 标准文本解析 |
| applicability | 通用 / 按产品 / 按规模 / 按过程 | 7.3 设计开发按产品（ACM 留行标注实证） |
| required_artifacts[] | 企业必须产物（程序/计划/记录/报告）＋表单 schema 引用 | 48 号试跑：编号规则可自动解析 |
| artifact_fields[] | 每份材料必须具备的字段 | 特殊岗位名单 8 字段实证 |
| evidence_points[] | 证据收集要点 | ACM 证据列实证 |
| verification_method / depth | 文件评审/现场观察/访谈/抽样＋深度 | 真实报告：当日抽样＋现场观察＋访谈 |
| stage_switch[] | 一阶段/二阶段/监督/再认证 各阶段是否查、粒度 | QR-04-70 vs 72 实证 |
| l_level_source | L1 现场/L2 记录/L3 模板——哪些层可满足本条款 | 48 号 §6.3 |
| judge_mode / severity_default | 四态判定＋默认严重度 | 复用现有 ValidationRule |
| regulation_refs[] | 法规挂接（新 GMP 128 条等） | 法规层=0 缺口的修补通道 |
| merge_split_hints | 合并/拆分提示（机构配方起点，非强制） | 一阶段主题式实证 |

**检查项 Schema（机构侧，OrgCode 隔离）**：check_item_code · org_code · clause_refs[]（主条款＋关联条款，M:N）· standard_codes[]（M:N，三体系合并）· stage_codes[] · process_code · dept_applicability · applicability_override（按企业裁）· merge_group · requirements_text_override · nc_template。现有 `cert_expert_task` 已支持多标准，`cert_expert_nc_item` 单 StandardCode 是待补缺口。

## 三、引擎规则 Schema（确定性层，无 LLM）

```
rule_id · rule_type(引用完整性/日期指纹/账实diff/声称-证据/覆盖/雷同)
trigger_condition（结构化条件） · inputs（数据引用：文档树/证据池/台账）
output_template（疑点条目结构） · severity_default
applies_to（预审/审核/自检） · version（留痕用）
```

POC 的 10 条疑点即前 10 张规则卡片的原料（49 号文档）。

## 四、用户 synthesis 未覆盖的三个缺口（必须补）

1. **证据池显式化**：用户的第 1、2 点之间缺一个中间artifact——实例级证据（四要素事实＋来源锚点＋L 层＋模板态/记录态）。它是摄入层与引擎层之间的**脊柱**，schema 是第一优先产出；
2. **合规外壳**：两阶段间隔 ≥5 日/≤6 个月、一阶段到场两条例外、计划提前 3 日报送 15 字段、180 天人日台账、监督时钟——纯规则引擎、无 LLM、构成先行件卖点；
3. **留痕与审计档案**：每条疑点/判定/签字须带 rule_id＋数据行＋规则版本＋时间戳——这是"留痕判据"的落地，也是进认证档案的前提。

## 五、入手顺序（单人开发者，按杠杆率）

1. 证据池 schema＋双栏数据契约（一周）；
2. 10 条疑点 → 结构化规则卡片（第一行真代码，反推 schema 缺项）；
3. 条款属性 schema＋13485 ~70 条填充（标准模型）；
4. 合规外壳（先行件卖点）；
5. 现场采集槽位表单（L1 入口）；
6. 提示词工程最后做，作为渲染层配置资源。
