# 54 号桌面化技术架构评审（V1）

> 2026-10-23 ｜ 评审对象：`54-桌面化技术架构Docker组件本地等价物-V1.md`
> 关联：`53-审核员侧商业化模式选型买断制Exe-V1.md`、`52-定价与商业化落地-V1.md`
> 结论：**方向成立，施工图未成立**。核心判断（桌面是新产品、不做 docker 重打包、云只做授权/规则/统计）正确；但有 **5 项 P0 阻断**，修正前不能按 54 的工时排期。

## 一、总裁决

| 维度 | 判断 | 说明 |
|---|---|---|
| 产品方向 | **成立** | 审核员现场/弱网/保密场景适合本地程序；买断制 + BYOK 与 53 号一致 |
| 组件映射 | **大体成立，1 处硬错** | MySQL→SQLite 应走 **SqlSugar**，不是 EF Core；文档转换不是 Pandoc 单二进制可等价 |
| 云地分离 | **方向成立，边界要写死** | 授权/规则/统计可上云；业务数据“零上传”与 AI BYOK/云代理冲突，必须分层表述 |
| 安全 | **不足** | 53 号的“手机连同一 Wi-Fi 采集”在 54 中缺少鉴权/绑定/防火墙设计 |
| 商业可交付 | **不足** | 缺代码签名、自动更新、备份恢复、许可合规；这些不是“以后再说” |
| 工作量 | **偏乐观** | 54 的 6 步是“技术骨架”，不是“可卖 v1”；需先做 6 个 spike |
| 总体 | **B+ 方向 / C 施工图** | 先修 P0，再谈排期；不要直接进入全量开发 |

## 二、P0 阻断项（修正前不得排期）

### P0-1 ORM 写错：项目是 SqlSugar，不是 EF Core

- **54 原文**：`MySQL 8.0 → SQLite（EF Core 换 provider）`（54 号 §一）。
- **事实**：
  - `src/yzh-core/YZH.Core.DataBase/YZH.Core.DataBase.csproj:13-14` 明确 **SqlSugarCore 5.1.4.167 是唯一 ORM**；
  - `src/yzh-core/YZH.Core.DataBase/MultiDatabase/DbContextFactory.cs:74-78` 已支持 `"SQLITE" => DbType.Sqlite`；
  - 全仓未发现 `Microsoft.EntityFrameworkCore` / `UseSqlite` / `UseMySql`。
- **影响**：按 54 排期会错误地引入 EF Core 数据层，和现有 `IDbOrm` / `SqlSugarDbOrm` / 实体特性 / 审计填充脱节，返工面大。
- **修正**：改为 **SqlSugar SQLite provider**；新增 `CertPlatform.Desktop` 时复用 `IDbOrm` 抽象；**先做 SQLite 兼容性 spike**，不要先写 EF migrations。
- **必须审计**：`SqlSugarDbOrm.cs` 中反引号 SQL、`ViewName` 视图路由、分页排序、`DateTime`/`decimal`/`Guid` 映射；SQLite 虽兼容反引号，但函数/类型/排序规则与 MySQL 不同。

### P0-2 文档转换不等价：Pandoc 不能替代 anydoc 全链路

- **54 原文**：`anydoc（node）→ Pandoc 单二进制（~30MB）或 .NET 原生解析`；`docx/xlsx→md 质量足够`；`PDF→文本走 pdftotext 同类方案`（54 号 §一）。
- **事实**：
  - 现有 `DocumentConvertClient` 的 anydoc 链支持 **doc/docx/xls/xlsx/pdf/csv/pptx 等 14 种格式**，且 `.doc/.xls` 可直转（`CertPlatform.Shared/DocExtraction/DocumentConvertClient.cs:12-14,47-53`）；
  - 现有预览链是 **LibreOffice headless → PDF**（同文件 `:66-73,86-99`）；
  - 现有 OCR 前置是 **poppler `pdfinfo`/`pdftoppm` 逐页渲染**（同文件 `:120-161`），再交视觉模型；
  - **Pandoc 不能读 xlsx/xls/doc/ppt/pptx/pdf**；`docx→md` 可以，`xlsx→md` 不成立；PDF 文本抽取也不是 Pandoc 的职责。
- **影响**：54 把“anydoc 14 格式”压缩成“Pandoc 单二进制”，会低估格式兼容、OCR、表格/版面、旧 Office 格式的工作量；上线后表现为“某些客户文件转不出来”，且不报错或报错不可读。
- **修正**：先做 **格式支持矩阵**，再定工具链：
  - `.doc/.xls/.ppt` → LibreOffice 转 OpenXML/PDF；
  - `.docx` → Pandoc 或 LibreOffice；
  - `.xlsx` → 专门解析（OpenXML/ExcelDataReader/LibreOffice→csv），**不要写 Pandoc**；
  - `.pdf` 文本层 → Poppler `pdftotext -layout` 或 PDF 解析库；
  - 扫描 PDF/图片 → `pdftoppm` + 本地 OCR/视觉模型；
  - 保留“失败分类”（NeedsOcr/Unsupported/Timeout/NotProduced），不要退化成一句“转换失败”。
- **验收**：用真实样例做回归集：`.doc` 中文质量手册、`.xls` 台账、`.xlsx` 多 sheet、`.pptx`、文本 PDF、扫描 PDF、手机照片、超长中文路径。

### P0-3 “全功能离线”与 AI/零上传自相矛盾

- **54 原文**：图中写“本地 exe（全功能离线）”（54 号 §二）；同时写“AI 调用：BYOK 直连 或 云端代理”（同图）；又说“业务数据零上传”（54 号 §二、§五）。
- **事实**：
  - BYOK 直连意味着文档/提示词会发给模型厂商；云端代理意味着会经过你的服务器；
  - 53 号已明确“规则在云端、匿名统计回传、AI 费用用户自理”（53 号 §二）；
  - 现有 OCR 是 **视觉模型**（`VisionOcrProvider`），不是本地 Tesseract；扫描件 OCR 会走 AI。
- **影响**：对客户承诺“数据永不离开本机”时，一旦用了 AI/云 OCR 就是虚假承诺；这是商业信任和法律风险，不是文案问题。
- **修正**：把能力分三层写清楚：
  | 层 | 能力 | 网络 | 数据去向 |
  |---|---|---|---|
  | L0 核心 | 检查单、证据池、疑点裁定、导出 | 可离线 | 仅本机 |
  | L1 规则 | 规则包下载/离线 zip 导入 | 可离线 | 仅规则元数据 |
  | L2 AI | 疑点生成、视觉 OCR、文档抽取 | 需网络 | 用户 BYOK 直连厂商，或显式同意走云代理 |
- 文案改为“**核心流程离线可用；AI 功能需网络，数据去向由用户选择**”；不要笼统写“全功能离线/零上传”。

### P0-4 手机采集的本地 Web 服务缺少安全设计

- **53 原文**：`exe 内置本地 Web 服务，手机连同一 Wi-Fi 访问 localhost 页面采集`（53 号 §三）。
- **54 现状**：只画了 `UI(SPA) + API(Kestrel)`，没有写手机访问、绑定地址、鉴权、防火墙、会话、文件权限。
- **风险**：Kestrel 若绑 `0.0.0.0`，同网段任何人可访问客户证据；目录遍历/未授权下载/CSRF/恶意文件上传都可能发生；客户现场 Wi-Fi 不可信。
- **修正**：
  - 默认只绑 `127.0.0.1`；开启手机采集时才绑定局域网，并显式提示 Windows 防火墙；
  - 一次性配对码/二维码 + 短期会话 token；会话超时自动失效；
  - 只允许上传到指定项目目录；文件名消毒、大小/类型白名单、路径穿越防护；
  - 不提供目录列表；下载走签名 URL/一次性 token；
  - 可选 HTTPS（自签证书）或至少局域网 token；
  - 采集端与桌面端并发写 SQLite 时用 WAL + busy timeout + 重试。
- **验收**：同网段第二台设备无 token 访问应 401/403；退出采集模式后端口关闭；日志不记录证据内容。

### P0-5 商业交付缺失：签名、更新、备份、许可

54 把“安装器（Inno Setup）”作为第 5 步，但可卖的 Windows 桌面产品还缺四件事：

| 项 | 为什么是 P0 | 最低要求 |
|---|---|---|
| 代码签名 | 未签名 exe 会被 SmartScreen/杀软拦截，客户不敢装 | OV/EV 证书 + 时间戳；安装器和主程序都签 |
| 自动更新 | 规则包可手动，但主程序不能靠用户手动下载 | 应用更新通道 + 增量/回滚；规则包与应用版本分离 |
| 备份/恢复 | SQLite/证据文件是本机唯一副本，崩溃即丢 | 自动备份、导出/导入、WAL checkpoint、恢复向导 |
| 许可合规 | Pandoc/Poppler 是 GPL，LibreOffice 是 MPL/LGPL，字体有授权 | 法务复核；随包许可证/来源声明；不把 GPL 工具链接进专有代码 |

> 代码签名/更新对“内部试点”可降为 P1，但对“对外卖 exe”是 P0；54 没有区分“试点版”和“可售版”。

## 三、P1 重要修正

### 3.1 SQLite 不是“换个 provider”就完事

- 开启 `PRAGMA journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout`；处理桌面端 + 手机端并发写。
- 明确 `DateTime`/`decimal`/`Guid`/`bool` 的存储与读回口径；SQLite 的 `decimal` 精度和 `DateTime.Kind` 容易与 MySQL 行为不同。
- 中文排序/大小写：SQLite 默认 `NOCASE` 只对 ASCII 有效；不要假设与 MySQL `utf8mb4_general_ci` 一致。
- 全文检索：如要做“证据搜索”，SQLite FTS5 默认分词对中文不友好；需 trigram/外部分词，或先不做全文。
- 迁移：SQLite 对 `ALTER COLUMN` 支持弱，升级要用“新表 + 复制 + 重命名”；不要假设 EF/SqlSugar migrations 能无痛跨版本。
- 审计 `SqlSugarDbOrm` 的 raw SQL：反引号、`AS` 视图、分页、`OrderBy` 字符串；SQLite 能跑不代表语义一致。
- 不要移植 60+ 表；桌面只建自己的表，但**实体仍要遵守项目铁律**（PascalCase、`Code` 业务键、`IsValid`、审计字段）。

### 3.2 数据目录：`%APPDATA%` 不适合放大量证据

- `%APPDATA%` 可能被漫游/同步，几 GB 的 PDF/照片会拖垮登录/同步，甚至损坏 SQLite。
- 建议：
  - 配置/许可证：`%APPDATA%\<产品>\config`；
  - 数据库/证据/缓存：`%LOCALAPPDATA%\<产品>\data`；
  - 用户可改数据目录（企业受控环境/大容量盘）。
- 处理 Windows 长路径、中文/空格、OneDrive 重定向、只读目录、磁盘满。

### 3.3 Redis → `IMemoryCache` 要核对接口

- 现有平台用 `StackExchange.Redis` / `IDistributedCache`（见 `CertPlatform.Admin.csproj:18`、`CertPlatformAdminServiceExtensions.cs:63`）。
- 54 说换 `IMemoryCache`，但若复用代码依赖 `IDistributedCache`，需要适配器；不能直接替换类型。
- 单用户进程内缓存可行；但要设计缓存失效、规则包更新后的清空、提示词/Markdown 缓存落盘大小上限。

### 3.4 MinIO → 本地文件不是“换个目录”

- 复用 `IObjectStorage` 抽象，新增 local provider；不要在每个业务类里直接 `File.WriteAllBytes`。
- 需要：原子写（临时文件 + rename）、内容去重/哈希、路径消毒、文件锁、配额、清理孤儿、备份。
- 预览/下载 URL 在本地没有 MinIO 预签名；改用本地 token/短路径，不要暴露绝对路径。
- 证据照片/PDF 可能很大；需要缩略图/分页预览策略，避免一次性读入内存。

### 3.5 LibreOffice 便携版

- 体积需实测（350MB 只是量级；便携版 + CJK 字体可能更大）；安装包分“完整/精简”两档是合理方向。
- 进程隔离：每次转换独立 `-env:UserInstallation`，超时 kill，临时目录清理；禁用宏/外部链接。
- 字体：只捆绑可再分发字体（如 Noto/思源，OFL）；不要打包 Windows 系统字体。
- 版本固定，升级要回归 `.doc/.xls` 中文排版；不要依赖用户机器已装 Office。

### 3.6 OCR：54 把“本地 OCR”写得太轻

- 现有 OCR 是视觉模型（`VisionOcrProvider`），依赖 AI 配置；不是本地 Tesseract。
- 本地 OCR 方案（Tesseract `chi_sim` / `Windows.Media.Ocr`）对扫描件、表格、手写、低分辨率照片的质量要实测；`Windows.Media.Ocr` 还依赖系统语言包。
- 扫描 PDF 要逐页渲染（Poppler `pdftoppm`），不是 `soffice --convert-to png`（现有代码注释已实测只能出首页）。
- 建议做 OCR 基准集：校准台账、检验记录、供应商报告、营业执照、扫描 PDF、手机照片；比较“本地 OCR vs 视觉模型”的准确率/成本/隐私。

### 3.7 AI/BYOK 的密钥与数据

- API Key 用 Windows DPAPI 加密存储；不要明文写配置文件/日志。
- 区分“直连 BYOK”和“云端代理”：代理必须显式同意、可关闭、不记录正文；否则“零上传”不成立。
- 模型厂商可能保留数据；产品文档要写清数据去向，不能只写“本地”。
- 失败/超时/限流要有降级：不阻塞核心离线流程。

### 3.8 规则包同步

- 规则包要有：`schemaVersion`、`minAppVersion`、内容签名、发布时间、变更说明。
- 应用前验签；原子替换；失败回滚上一版；离线 zip 同格式。
- 规则包只放数据/提示词/规则，不放可执行代码；如必须放脚本，需沙箱/白名单。
- 规则包与应用版本解耦，但要做兼容性检查；否则老客户端拿到新规则会静默错判。

### 3.9 激活与授权

- 机器码用稳定硬件特征哈希，不采集可识别个人信息；换机/重装要自助解绑。
- 离线激活文件/宽限期要设计；53 说“不做纯离线”，但现场可能长时间无网，需明确“首次激活联网 + N 天离线宽限”。
- 授权撤销、过期、时钟回拨要处理；但不要过度反盗版导致客户无法工作。
- 激活服务只做授权，不接触业务数据；独立部署，不复用全量平台 API。

### 3.10 安装器与运行形态

- 明确：默认浏览器打开 localhost，还是 WebView2 壳？后者要带 Evergreen Runtime，安装包/兼容性都变。
- 单实例锁、端口冲突、动态端口、开机自启、托盘、退出时是否停止 Kestrel。
- 每用户安装（无需管理员）优先；机器级安装要写 ProgramData/注册表，权限更复杂。
- 卸载是否保留数据；升级是否迁移数据库；回滚是否兼容旧库。
- 安装包体积、下载/更新带宽、杀软误报、企业软件白名单都要测。

### 3.11 复用层不是“纯函数”就能直接拿

- 54 说复用 `Shared/Fill`、`Shared/Office` 纯函数；但要先做**可移植性审计**：
  - 是否依赖 `IDbOrm` / `IUserContext` / `ILogger` / `IConfiguration` / ASP.NET；
  - `DocumentConvertClient` 依赖 `docker` 命令和挂载目录，不是纯函数；
  - `VisionOcrProvider` 在 `CertPlatform.Admin`，依赖 `IDbOrm` + `LlmInvokeService`，不能直接搬；
  - `FileConvertCore` 含 PDF 渲染/OCR 分支，需替换为本地进程调用。
- 建议画一张“复用矩阵”：直接复用 / 适配后复用 / 重写 / 不复用；不要用“Shared 纯函数”一句话带过。

### 3.12 测试与支持

- 干净 Windows 10/11 虚拟机：无 Office、无 .NET、无 Node、无管理员权限、离线安装。
- 中文/空格/长路径、OneDrive 重定向、多显示器/DPI、低配机器、杀软开启。
- 升级/卸载/回滚/数据库迁移；断电/崩溃后的恢复。
- 本机日志 + 可选崩溃上报（不含业务数据）；客户支持要能远程诊断但不拉走证据。
- 许可合规测试：安装包内许可证、第三方 notices、GPL 源码获取方式。

## 四、逐组件复核表

| 54 组件 | 54 结论 | 评审结论 | 修正/工作量 |
|---|---|---|---|
| MySQL → SQLite | EF Core 换 provider，中 | **硬错**：项目是 SqlSugar；SQLite 已支持但需兼容性审计 | 改为 SqlSugar；加 2–3 天 spike；中 |
| Redis → IMemoryCache | 低 | 方向可行；需核对 `IDistributedCache` 依赖 | 加适配器/缓存失效；低 |
| MinIO → 本地目录 | 低 | 方向可行；但原子写/备份/安全/URL 未写 | 中，不是低 |

| anydoc → Pandoc | 中 | **不等价**：Pandoc 不支持 xlsx/doc/xls/ppt/pdf；需 LibreOffice + Poppler + OCR | 高，先做格式矩阵 |
| API self-contained | 低 | 可行；需签名/单实例/端口/更新 | 低-中 |
| Vue 内嵌 wwwroot | 低 | 可行；需明确浏览器/WebView2、鉴权、端口 | 低-中 |
| OCR（54 隐藏工作量） | Tesseract/Windows OCR | 现有是视觉模型；本地 OCR 质量/多页/表格未验证 | 高/未知，先基准 |
| 云轻服务 | 复用现有 API 新端点组 | 方向可行；但应独立最小服务，不复用全量平台 | 中 |
| 规则包 | 版本+签名+增量 | 方向对；缺 schema/应用版本/回滚/离线细节 | 中 |
| 激活 | 机器码绑定 | 方向对；缺离线宽限/自助解绑/撤销/隐私 | 中 |

## 五、建议的 Spike（先验证，不先写全量）

| Spike | 目标 | 时间盒 | 通过标准 |
|---|---|---|---|
| S1 SQLite/SqlSugar | 桌面子集 CRUD、迁移、备份、并发 | 2–3 天 | 10 张表 CRUD + 升级 + 备份恢复通过；无 MySQL 专有 SQL 阻断 |
| S2 文档格式矩阵 | 真实样例 10 类格式转换 | 3–5 天 | `.doc/.xls/.xlsx/.pptx/文本 PDF/扫描 PDF/图片` 全部有明确结果与失败分类 |
| S3 本地 OCR | 扫描件/照片/表格准确率与成本 | 2–3 天 | 关键字段准确率可接受；明确“本地 OCR vs 视觉模型”边界 |
| S4 打包/签名/更新 | 干净 Windows 安装、升级、回滚 | 3–5 天 | 无 Office/.NET 环境可装；SmartScreen/杀软可接受；更新/回滚成功 |
| S5 手机采集安全 | 局域网配对、鉴权、退出 | 2–3 天 | 无 token 拒绝；退出后端口关闭；路径穿越/大文件测试通过 |
| S6 激活/规则包 | 激活、离线宽限、规则签名/回滚 | 3–5 天 | 换机/离线/回滚/篡改测试通过 |

> 54 的“6 步骨架”是可行的，但**至少还要 4–6 周工程化**（不含业务规则/内容），才能到“可卖 v1”。不要用“6 步”直接对外承诺工期。

## 七、验收清单（Go/No-Go）

- [ ] SQLite/SqlSugar：建库、CRUD、升级、备份、恢复、并发写通过。
- [ ] 格式矩阵：10 类真实文件全部有明确结果；失败分类可读。
- [ ] OCR：扫描 PDF/照片的关键字段准确率达标；成本/隐私边界清楚。
- [ ] 安装：干净 Win10/11、无 Office/.NET、非管理员、离线安装通过。
- [ ] 签名/更新：SmartScreen/杀软可接受；升级/回滚成功。
- [ ] 手机采集：无 token 拒绝；退出关闭；路径穿越/大文件测试通过。
- [ ] 激活：离线宽限、换机解绑、撤销/篡改处理通过。
- [ ] 数据：日志/上报不含业务内容；备份/导出/删除可验证。
- [ ] 许可：Pandoc/Poppler/LibreOffice/字体 notices 与合规方案确认。
- [ ] 复用：Shared 依赖审计完成；无 Admin/Auditor 业务层被拖入桌面。

## 八、结论

54 号是**方向正确的架构判断**，不是**可直接施工的详细设计**。它最有价值的三句话是：

1. 桌面产品是新产品，不是 docker 的重新打包；
2. 逐组件换本地等价物，复用纯函数层；
3. 不移植权限/多租户/队列/三端分离。

但必须先把 **ORM（SqlSugar 不是 EF Core）、文档转换（Pandoc 不是 anydoc）、离线/零上传口径、手机采集安全、商业交付（签名/更新/备份/许可）** 五项 P0 修掉，再谈工时。建议按本文 §五 先做 6 个 spike（至少先做 S1/S2/S4/S5），通过后再进入“可卖 v1”排期。
