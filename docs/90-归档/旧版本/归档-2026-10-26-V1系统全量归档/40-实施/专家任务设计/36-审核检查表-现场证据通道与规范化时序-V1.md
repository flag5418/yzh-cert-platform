## 一、结论速览

| # | 问题 | 结论 |
|---|---|---|
| ① | 录音/拍照能不能进现有链路 | ⛔ **不能**。上传白名单**无音频**；企业资料是**槽位制**（扩展名必须匹配模板）；`file_convert` 只认 Office/PDF；全仓 ASR **零命中** |
| ② | 现场证据的前提条件 | ★ **审核计划 + 场次**。系统里**完全没有这一层**（全仓 `审核计划\|日程\|场次\|AuditPlan\|Schedule` 零命中） |
| ③ | 录音的核心难点 | ⚠️ **不是转写，是「按条款切分」**。一段 1 小时会议跨 20 个条款，1 万字转写稿要分给 20 个检查项 |
| ④ | 方言怎么办 | ★ **真正的解法不是 ASR，是审核员现场复述确认**（不依赖技术进步） |
| ⑤ | 规范化在哪个环节 | **认证申请之前**（①建立体系）。⚠️ 但**不在「NC 前/后」这个坐标系里**——中间隔着「运行 3 个月 + 申请 + 一阶段」 |
| ⑥ | 一阶段审什么 | **审规范化产物**（文件写得对不对）⇒ 它是**审核对象**，不是证据 |
| ⑦ | 二阶段审什么 | **取证**（记录 + 现场 + 访谈），查「实然」 |
| ⑧ | 第二轮/第三轮要不要重新规范化 | **不要**。判据不是轮次，是「**这份文件有没有正式发布**」 |
| ⑨ | 现状最大缺口 | `confirmed` 状态**定义了但从未写入**；**没有「产物 → 回传」的关联列** |
| ⑩ | **检查项的单位是什么** | ★★ **不是「条款」，是「条款 × 部门」**。样本 76 行只对应 **59 个唯一条款** —— **17 行是同一过程在不同部门重复问**（`E6.1.2` 环境因素问了 **4 次**） |
| ⑪ | 一张检查表装几个标准 | **3 个**。条款号带前缀 `Q`/`E`/`H` = ISO 9001 / 14001 / 45001；**10/76 行是多标准合并行**（`E&H8.2`、`QE10.2`、`Q5.2.1/2 E&H5.2`） |
| ⑫ | **部门能不能当第一轮过滤** | ✅ **能，但过滤键是「场次」不是「部门」**。表5 与表7 部门组**完全相同**、条款**完全不同** ⇒ 同一部门组要开多场 |
| ⑬ | 原始资料要不要分部门 | ✅ **要**，但**分的是「归属部门」不是「上传目录」** —— 让企业上传时选部门 = 把内部负担转嫁给用户（违反用户视角铁律），见 §3.8 |

**一句话**：现场证据要补的是**三层**——计划层（场次）、采集层（录音/照片/文字）、落库层（`cert_check_evidence`）。录音可以后置，但**计划层不能后置**，因为它是「按条款切分」的先验约束。

**第二句话（本轮新增）**：**检查项的主键不是条款号**。同一条款在不同部门是**不同的检查项**（因为要查的东西不同），所以「条款 × 部门」才是检查项的最小单位 —— 这是部门维度的**根本理由**，不是设计偏好。

## 二、为什么现场证据装不进现有链路（技术实证）

### 2.1 上传白名单无音频

`upload-file-policy.json`（全平台单一事实源，2026-10-14）：

```json
"document": [".doc", ".docx", ".xls", ".xlsx", ".ppt", ".pptx", ".rtf", ".odt", ".ods", ".odp", ".txt", ".md", ".csv"],
"image":    [".jpg", ".jpeg", ".png", ".gif", ".bmp", ".webp"],
"pdf":      [".pdf"],
"archive":  [".zip", ".rar", ".7z", ".tar", ".gz"],
"never":    [".exe", ".dll", ".so", ...]
```

**无 `audio` 段**（mp3 / m4a / wav / aac 全无）。

✅ 好消息：`$comment` 明写「加/减后缀只改本文件，然后跑 `node scripts/generate/upload-policy.mjs` 重新生成两端清单段」⇒ **加音频 = 改一个 json + 跑一个脚本**。

⚠️ 但**不要**直接加进 `document` 段 —— 见 §2.2。

### 2.2 企业资料是槽位制，扩展名必须匹配模板

`EnterpriseFileService.cs:736-737`：

```csharp
var want = Path.GetExtension(slot.FileName);
return ($"「{item.FileName}」扩展名与槽位「{slot.FileName}」不兼容（模板要求 {want}），请上传 {want} 或同族格式", null);
```

**每个槽位有指定的文件名/格式**（如「质量手册.docx」）。录音/照片**没有对应槽位**，塞进去必然被挡。

⇒ **现场证据必须走独立通道**，不能寄生在企业资料体系里。

### 2.3 `file_convert` 只认 Office/PDF

`OfficeConvertService.cs:108-118` 支持的转换类型：

```
doc2pdf / xls2pdf / office2pdf / docx2pdf / xlsx2pdf / ppt2pdf / pptx2pdf
anydoc2md / doc2md / docx2md / xls2md / xlsx2md / pdf2md / office2md
doc2docx / xls2xlsx
```

**无音频分支**。全仓 `ASR` / `语音` / `转写` / `whisper` / `audio` —— **零命中**。

### 2.4 专家端只有企业侧上传入口

| 控制器 | 用途 | 归属 |
|---|---|---|
| `EnterpriseOriginalController` | 企业原始资料（`/enterprise-original`） | **企业侧** |
| `EnterpriseFileController` | 企业认证资料（槽位） | **企业侧** |
| — | **审核员现场证据** | ❌ **无** |

`cert_expert_nc_result` 只有 `EvidenceRef` / `ContentText` 两个文本字段（`ExpertResultController.cs:891` 是全仓唯一 `EvidenceRef` 写入点）。

## 三、审核计划层与部门维度：现场证据的前提（系统完全缺失）

### 3.1 标准依据

| 条款 | 要求 |
|---|---|
| ISO 19011 **§6.3.2** | **编制审核计划** |
| ISO 19011 **§6.4.2** | **与受审核方沟通**（计划、日程、参与方） |

⇒ **「计划要告知客户」不是管理偏好，是标准动作。**

### 3.2 现状：这一层不存在

全仓 `审核计划|审核日程|场次|AuditPlan|Schedule` —— **零命中**。

`CertExpertTask` 只有：`TaskType` / `ScopeType`(`FULL`) / `TaskSource`(`NEW`) / `ScopeSnapshot`(JSON) / `AuditEventCode` / `AuditEventName`。
**没有**：计划日期、参与单位、议题、地点、场次。

**现在的模型是**：`任务（要检查什么）→ 队列项（逐条跑）→ 结果`
**缺中间那一环**：什么时候、跟谁、讨论什么。

### 3.3 有了计划层，能解决三个目前解决不了的问题

**① 按条款切分从「全量猜」变成「范围内选」**（最关键）

| | 没有场次 | 有场次 |
|---|---|---|
| 输入 | 1 小时录音 / 1 万字 / 20 个候选条款 | 1 小时录音 / **只在这场的 3 个条款里归集** |
| 准确率 | 注意力稀释，容易串到别的条款 | 候选集缩小 6 倍，判定更稳 |
| 成本 | 20 次判断 | 3 次判断 |

**这一条直接决定录音能不能用** —— 切不准，录音就只能当附件存着。

**② 责任主体明确**

没有参与单位 ⇒ NC 只能写「存在不符合」；有参与单位 ⇒ 能写「**安全部**在应急准备方面不符合」。

企业整改要知道找谁，这直接决定 NC 能不能用。

**③ 「漏审」变得可算**

计划应覆盖全部条款。**计划里有、实际没执行 = 漏审**，是审核质量的硬指标。

### 3.4 样本实测：「过程/区域」不是部门（修正上一版说法）

⚠️ **上一版本文写「按审核场次/受审部门组织」，不准确**。实测样本 12 张表（6 块头 + 6 明细交替），块头「Process Area / 过程/区域」列实际填的是：

| 块 | 过程/区域（原文） | 负责人（原文） | 明细行数 |
|---|---|---|---|
| 1 | `GM/MR` | 总经理：张庆捷 / 员工代表：葛文红 / 职业健康监视人员：孟建波 | 33 |
| 3 | `行政财务、安环运行` | 行政人资部：杨青 / 环保部：李晓燕 / 安全部：潘健平 / 财务部：陈香英 | 15 |
| 5 | `生产部、质量管理部、设备部、研发部` | 孟建波、姜丽华、张志新、吴建飞 | 9 |
| 7 | `生产部、质量管理部、设备部、研发部` | 孟建波、姜丽华、张志新、吴建飞 | 10 |
| 9 | `采购过程、销售过程` | 营销部：黄欣 / 物资部：何小常 | 7 |
| 11 | `采购过程、销售过程` | 营销部：黄欣 / 物资部：何小常 | 2 |
| | | **合计** | **76** |

**三条结论，全部与直觉相反：**

**① 这一列混了三种东西**

| 类型 | 例子 | 说明 |
|---|---|---|
| **角色/岗位** | `GM/MR` | 不是部门，是「最高管理者 / 管理者代表」两个**角色** |
| **过程组** | `行政财务、安环运行`、`采购过程、销售过程` | 不是部门，是**业务过程**（一个过程跨多部门） |
| **部门组** | `生产部、质量管理部、设备部、研发部` | 是部门，但**一个块 4 个部门** |

⇒ ⛔ **不能把这一列直接当 `DepartmentCode` 存**。它是「审核单元」的名字，粒度大于部门。

**② 「一个块」≠「一个部门」，是 M:N**

- 块 3 含 **4 个部门**；块 5/7 含 **4 个部门**；块 9/11 含 **2 个部门**
- 反过来，一个部门也可能出现在多个块：`安全部`/`环保部` 在块 3；`生产部` 在块 5 和 7

⇒ **块 ↔ 部门 必须走关联表**，不能放单列。

**③ 同一个部门组可以开多场 —— 这是「过滤键不是部门」的铁证**

块 5 与块 7 的「过程/区域」和「负责人」**一字不差**，但条款完全不同：

| 块 | 条款 |
|---|---|
| 5 | `7.1.3/7.1.4` `7.1.5.1` `7.1.5.2` + 环境/安全 4 条 |
| 7 | `Q8.1` `Q8.3` `Q8.5.1~8.5.6` `Q8.6` `Q8.7`（全是产品实现） |

⇒ **同样是「生产部+质量部+设备部+研发部」，要开两场会**：一场看基础设施/环境（7.1），一场看产品实现（8.5）。

⇒ ★★ **切分场次的真实维度是「部门 × 过程」，不是「部门」**。只按部门切，块 5 和块 7 会合并成一场，那 19 行证据就全部混在一起、无法定位。

> 这也说明：**「区域 ≠ 场次」在样本里是字面成立的** —— 区域（过程/区域）出现 4 个不同值，场次有 6 个。**4 ≠ 6**。

### 3.5 建议的最小计划模型

```sql
cert_audit_session   -- 审核场次（一次会议/一个受审单元）
    Code, TaskCode, EnterpriseCode, StageCode
    SessionName        -- 「安全部访谈」「车间现场走查」
    ProcessAreaName    -- ★ 原文保留样本的「过程/区域」列（GM/MR、采购过程、销售过程…）
    PlannedDate        -- 计划日期
    ActualStartTime    -- 实际开始（录音起点对齐）
    ActualEndTime
    Location           -- 地点
    PlannedClausesJson -- ★ 计划覆盖的条款 Code 列表（切分的先验约束）
    NoticeSentTime     -- ★ 计划告知企业的时间（合规留痕）
    NoticeConfirmedBy  -- 企业确认人
    RecordConsent      -- ★ 是否同意录音（合规）
    Status             -- planned / in_progress / done / cancelled
```

**关键列是 `PlannedClausesJson`** —— 它把「按条款切分」从开放式猜测变成**封闭集合内选择**。

⚠️ 但按 35 号 D14 的教训：**如果将来要按条款聚合统计，JSON 列查不了**。建议同时建关联表 `cert_audit_session_clause`（SessionCode + ClauseCode + Sort），JSON 只作快照。

**⛔ 不要用 `ParticipantsJson` 存部门。** 部门要能反查（「这个部门今年被审了几次」「这场的录音在哪」），JSON 查不了。改成两张关联表：

```sql
cert_audit_session_dept   -- ★ 场次 ↔ 部门（M:N，样本块3含4个部门）
    Code, SessionCode, DeptCode, Sort
    LeadPersonName       -- 该部门在这场会的接待人（样本「行政人资部：杨青」）
    IsPrimary            -- 是否主场（多部门块里谁是主角）

cert_audit_session_clause -- ★ 场次 ↔ 条款（M:N，切分先验）
    Code, SessionCode, ClauseCode, StandardCode, Sort
```

**为什么部门必须独立成表，不能塞 JSON**：样本块 3 一个块 4 个部门、块 5/7 一个部门组两场 —— 只有关联表才能同时回答「某部门参与哪几场」和「某场覆盖哪几个部门」。

### 3.6 ★★★ 部门维度的真正理由：检查项的单位不是条款

这是本轮最重要的实测发现。

**样本 76 行，去掉跨块重复后只剩 59 个唯一条款** —— 也就是说 **17 行（22%）是同一个条款被问了不止一次**：

| 条款 | 出现次数 | 出现在哪些块 |
|---|---|---|
| `E6.1.2`（环境因素） | **4** | GM/MR · 行政财务安环 · 生产质量设备研发 · 采购销售 |
| `H6.1.2.1`（危险源辨识） | **3** | 行政财务安环 · 生产质量设备研发 · 采购销售 |
| `E8.1`（运行策划与控制） | **3** | 同上 |
| `H8.1.1`（运行策划与控制） | **3** | 同上 |
| `H8.1.2`（运行策划与控制） | **3** | 同上 |
| `E&H8.2`（应急准备与响应） | **2** | 行政财务安环 · 生产质量设备研发 |

**为什么重复？因为这些条款是「每个部门都有一份」的跨部门过程：**

- `E6.1.2` 环境因素 → 每个部门都有自己的环境因素清单（财务部的废纸 vs 生产部的废液）
- `H6.1.2.1` 危险源 → 每个部门都有自己的危险源（仓库的叉车 vs 实验室的化学品）
- `8.1` 运行策划 → 每个部门都有自己的作业指导书
- `8.2` 应急准备 → 每个部门都有自己的应急预案（火灾、泄漏、触电不一样）

⇒ ★★★ **同一条款在不同部门，问的东西完全不同、证据完全不同、结论也完全不同。**

**所以：**

| 错误模型 | 正确模型 |
|---|---|
| 检查项 = 条款（59 条） | 检查项 = **条款 × 部门**（76 条+） |
| `E6.1.2` 一条，证据一份 | `E6.1.2` **四条**，财务部一份、生产部一份、采购部一份、管理层一份 |
| 按条款过滤证据 | 按**条款 + 部门**过滤证据 |

**⛔ 如果按条款建检查项，后果是**：
1. 76 行塌成 59 行，**丢失 17 行的部门归属**
2. `E6.1.2` 的 4 份证据会被塞进同一条检查项 → **AI 分不清哪份是财务部的** → 判定必然出错
3. NC 只能写「环境因素识别不充分」，**写不出「财务部环境因素识别不充分」** → 企业不知道找谁整改

⇒ **部门维度不是「优化」，是「检查项能不能成立」的前提。**

### 3.7 一张检查表装 3 个标准 —— 多标准是现状不是未来

条款号带前缀，这是样本里最容易被忽略的信息：

| 前缀 | 标准 | 样本条款例 |
|---|---|---|
| `Q` | ISO 9001 质量 | `Q4.4` `Q5.1` `Q6.3` `Q7.1.2` `Q8.5.1` `Q9.1.3` |
| `E` | ISO 14001 环境 | `E4.4` `E6.1.2` `E6.1.3` `E8.1` |
| `H` | ISO 45001 职业健康安全 | `H4.4` `H5.4` `H6.1.2` `H8.1.1` |
| **无前缀** | **三标准共有** | `4.1` `4.2` `4.3` `5.3` `6.2.1/2` `9.1.1` `9.2` `10.1` `10.3` `7.2` `7.3` `7.4` |

**关键：10/76 行是「一行覆盖多标准」**

| 原文 | 含义 |
|---|---|
| `EH5.1` | 环境 + 职业健康安全 的 5.1（领导作用与承诺）同一条 |
| `Q 5.2.1/2 E & H 5.2` | 三个标准的 5.2（方针）**合成一行** |
| `E& H 6.1.4` | 环境 + 安全 的 6.1.4（措施策划）一行 |
| `Q 7.1.1 E & H 7.1` | 三个标准的 7.1（资源）一行 |
| `Q 9.3.1/2/3 E & H 9.3` | 三个标准的 9.3（管理评审）一行 |
| `QE10.2` | 质量 + 环境 的 10.2（不符合与纠正措施）一行 |
| `E&H8.2` ×2 | 环境 + 安全 的 8.2（应急准备）一行 |

⇒ ★ **「多标准合并执行」不是我们发明的优化，是审核员的实际做法**（用户第 7 轮提的猜想，样本直接印证）。

**这修正了 31/32 号的一个隐含假设**：证据是「一个检查项 → 一份证据」。实际上：

```
一个检查项（条款 5.2 方针）
  ├─ Q5.2.1/2  → 质量方针证据
  ├─ E5.2      → 环境方针证据
  └─ H5.2      → 安全方针证据
  三个标准的证据可能在同一份文件里（一份方针文件三合一）
```

⇒ **检查项 ↔ 标准 也是 M:N**，需要 `cert_check_item_standard` 关联表，或至少在检查项上存 `StandardCodesJson` + 明确的 `ClauseCode` 原文（保留 `E&H8.2` 这种写法）。

⚠️ **但不要试图解析 `Q 5.2.1/2 E & H 5.2` 这种字符串** —— 它是人写的，格式不统一（`Q 5.2.1/2` 有空格、`QE10.2` 没空格、`E& H 6.1.4` 有空格）。**保留原文 + 人工/AI 结构化两个字段并存**：`ClauseCodeRaw`（原文，只显示）+ `ClauseCode`（结构化，只查询）。

### 3.8 企业上传原始资料要不要分部门

**结论：要分，但分的是「归属部门」，不是「上传目录」。**

**为什么不能按部门建上传目录**（用户视角铁律）：

| 问题 | 后果 |
|---|---|
| 企业上传时不知道归哪个部门 | 「这个培训记录是人事部还是生产部的？」→ 卡住 |
| 一份文件跨多部门 | 质量手册、程序文件是**全公司**的，不是某部门的 |
| 部门调整/改名 | 历史目录全乱 |
| 上传量 | 样本企业 13 个部门/角色 ⇒ 上传页要 13 个入口，企业直接放弃 |

⇒ **上传时不分部门，上传后补部门**：

```
① 企业按「阶段 + 资料类型」上传（保持现状，零负担）
      ↓
② 系统/AI 建议部门（从文件名、内容、目录推断）
      ↓
③ 审核员批量确认（一场会只看这一场的，一次确认几十份）
```

**为什么必须有部门字段**（三条硬理由）：

| 理由 | 说明 |
|---|---|
| **过滤** | 审核员开「安全部」这场会，只想看安全部的资料，不想在 500 份里翻 |
| **交叉验证** | 「财务部说没做环境因素识别」vs「财务部交的环境因素清单」→ 矛盾 = NC |
| **责任归属** | NC 要写「哪个部门不符合」，没有部门字段只能写「企业不符合」 |

**建议字段**（`cert_enterprise_original_file` 增列）：

```sql
DeptCode          -- 归属部门（空 = 全公司级，如质量手册）
DeptSource        -- ai_suggest / auditor / enterprise  ← 来源留痕，AI 猜的要能追责
DeptConfirmedBy   -- 审核员确认人（AI 建议未确认的不能用于判定）
```

⚠️ **`DeptSource` 不是可选项**：AI 从文件名猜部门会错（「安全培训记录」可能是人事部组织的）。**未经确认的部门归属不能作为 NC 依据** —— 同 35 号「AI 辅助描述待确认」的口径。

### 3.9 检查项 / NC / 报告章节，哪些挂部门

**逐个回答（用户的三个对象）：**

| 对象 | 挂部门？ | 粒度 | 理由 |
|---|---|---|---|
| **检查项** | ✅ **必须挂** | **多选**（一个检查项可能查多个部门） | §3.6 —— 同条款不同部门是不同检查项。样本 `E6.1.2` 4 份 |
| **NC 项** | ✅ **继承，不独立填** | 从检查项带过来，可改 | NC 从检查项产生，部门应自动带出；审核员可修正（因为根因可能在别的部门） |
| **报告章节** | ❌ **不挂** | — | 章节是**标准条款的骨架**（4.1/5.1/8.5…），不是部门骨架。报告要按条款写，不是按部门写 |

**报告章节为什么不能挂部门**（容易搞错）：

报告的结构是标准规定的（ISO 17021-1 要求报告按审核准则组织）。如果按部门组织章节：
- 同一部门出现在 3 个章节 → 报告重复
- 部门改名 → 历史报告结构变
- 客户拿到的报告「不像认证报告」→ 直接影响可用性

✅ **正确做法**：章节挂条款（现有 `ReportSection.ClauseCode` 已有），部门信息在**章节内容里体现**（「安全部在应急准备方面…」），不在结构里体现。

**NC 报告要部门，但通过 NC 表带，不通过章节带。**

### 3.10 ★ 「部门做第一轮过滤」到底合不合理

**分两问，答案相反：**

| 过滤什么 | 合理？ | 原因 |
|---|---|---|
| **过滤检查项**（这场会该问哪些项） | ✅ **完全合理，必须做** | 场次已声明 `PlannedClauses` + 部门 ⇒ 候选集从「全部 76 项」缩到「这场 9~15 项」 |
| **过滤证据**（这场会只看这些证据） | ⚠️ **部分合理，会漏** | 跨部门证据会漏（见下） |
| **过滤原始资料** | ✅ **合理**（用 `DeptCode`） | 安全部的资料就是安全部看 |

**「过滤证据」为什么会漏 —— 三种跨部门证据：**

| 类型 | 例子 | 如果按部门过滤 |
|---|---|---|
| **管理层证据** | 管理评审记录、方针、目标 | ❌ 全公司级，`DeptCode` 为空 ⇒ 任何部门过滤都查不到 |
| **跨部门流程证据** | 合同评审（销售+生产+质量三方签字） | ⚠️ 挂在销售部，但生产部也要看 |
| **上游输出** | 采购部的进货检验记录 → 生产部要用 | ⚠️ 归属采购部，生产部这场也要读 |

⇒ ★ **过滤规则必须是「部门过滤 + 空部门兜底 + 显式跨部门引用」三条并集**：

```
候选证据 = ① DeptCode = 本场部门
         ∪ ② DeptCode IS NULL（全公司级）
         ∪ ③ 检查项上显式声明的跨部门引用
```

⛔ **只做 ① = 必然漏管理层证据**，而管理层证据恰恰是 59% 现场证据里最重要的一块。

**★★ 但更重要的修正：第一轮过滤的键不是「部门」，是「场次」**

理由（§3.4 实测）：块 5 与块 7 部门组完全相同，条款完全不同。

| 过滤键 | 效果 |
|---|---|
| 按部门过滤 | 生产部这场会拿到 19 项（块5 的 9 项 + 块7 的 10 项），混在一起 |
| **按场次过滤** | 块5 这场只拿 9 项，块7 这场只拿 10 项，**各归各位** |

⇒ **正确的过滤链是三层，不是一层：**

```
任务（76 项）
   ↓ 按场次过滤
场次（9~15 项）        ← ★ 第一轮过滤在这里
   ↓ 按部门过滤（含空部门兜底 + 跨部门引用）
本场候选检查项
   ↓ 按条款归集
证据
```

⇒ **「部门」是场次的属性，不是过滤的入口。** 用户提的「部门做第一轮过滤」方向对，但**入口要放在场次上**，部门是第二层。

### 3.11 计划怎么接进现有工作流（不改引擎）

用户问「每个计划有什么结论（录音、照片、文档），怎么组合到我们的流程中」。

**答案：计划不进 DAG，计划进「上下文」。**

现有 35 号已定「一个检查项 = 一个工作流」（复用 `ReportSection` 的 4 列）。计划层的作用**不是新增节点**，而是给已有节点**换数据源范围**：

```
计划层（场次）
   │  ① 提供 ScopeSnapshot：本场覆盖的条款 + 部门
   ↓
任务创建（CertExpertTask.ScopeSnapshot 里加 sessionCode）
   │  ② 队列项按场次分组（一个场次一个批次）
   ↓
检查项工作流（现有 10 个节点，⛔ 不改）
   │  ③ 节点读证据时带 sessionCode 过滤
   ↓
证据池（cert_check_evidence）
   │  ④ 每条证据带 sessionCode + deptCode + 载体类型
   ↓
NC 判定 / 报告
```

**四个接口点（都是加列，不加节点）：**

| # | 位置 | 加什么 | 为什么 |
|---|---|---|---|
| ① | `CertExpertTask.ScopeSnapshot` | `sessionCodes: []` | 一个任务可跑多场次，⛔ 不塞完整计划（D26） |
| ② | 队列项 | `SessionCode` 列 | 一个场次一个批次，失败可单独重跑 |
| ③ | 节点上下文 | `SessionScope { DeptCodes, ClauseCodes }` | 节点读证据时自动带上，**不用改节点签名** |
| ④ | `cert_check_evidence` | `SessionCode` / `DeptCode` / `CarrierType`（text/photo/audio/file） | 一条证据能回答「哪场会、哪个部门、什么载体」 |

**关键设计：`CarrierType` 而不是新建三张证据表。**

录音、照片、文字最终都是「一段可引用的证据」，差别只在：
- 位置表达：文字用 `span`、录音用 `timestamp`、照片用 `区域框`
- 能否被 AI 判定：文字 ✅、照片 ⚠️辅助、录音 ⚠️需人工确认

⇒ **一张表 + `CarrierType` + `LocationType`/`LocationValue`**（`span` / `timestamp` / `bbox`），⛔ 不要为三种载体建三张表（会产生三套判定逻辑、三套统计口径）。

**「组合到流程」的正确理解**：

| 错误理解 | 正确理解 |
|---|---|
| 计划是一个流程节点，跑完产出证据 | 计划是**执行前的范围声明**，不产出证据 |
| 一个场次跑一个工作流 | 一个场次**约束**该批检查项工作流的输入范围 |
| 录音/照片/文档各走一条链路 | 三条链路**汇入同一张证据表**，靠 `CarrierType` 区分 |

## 四、现场证据的三种载体

| 载体 | 优势 | 处理方式 | P1 做不做 |
|---|---|---|---|
| **文字**（审核员手记） | 零技术依赖、直接可用 | 文本框录入 | ✅ **做** |
| **照片** | 直观、可核验 | 上传 + 人工写观察结论 | ✅ **做**（AI 只辅助描述） |
| **录音** | 信息量最大、审核员不用边问边记 | ASR 转写 + 人工确认 | ⚠️ **P2**（P1 只存不转） |

### 4.1 为什么录音可以后置

- 录音叠了**三个难点**：方言准确率 + 按条款切分 + 人工确认
- 而**审核员现在就是用文字记的**（样本 76 行全是文字证据）
- 录音是「更好」，不是「必需」

**P1 折中方案**：录音**只存不转**——上传后当附件挂在证据上，审核员自己写要点。这样审核报告里有录音可查（审计要求），但不依赖 ASR。

### 4.2 照片的边界

| 项 | 做法 |
|---|---|
| 元数据 | **必填**：拍摄时间 / 地点 / 观察对象（人工填，照片本身不带） |
| AI 能做什么 | ⚠️ **只能做辅助描述**（「图中可见灭火器压力表指针在绿区」） |
| AI **不能**做什么 | ❌ **不能作为判定依据** |
| 为什么 | ISO 19011 要求证据「可验证」—— AI 看图描述是二次加工，不是原始观察 |

**照片必须人工写观察结论**，AI 描述只能作为辅助（帮审核员省打字时间），且标注「AI 辅助描述，待确认」。

## 五、录音转文字的设计

### 5.1 链路（四段，中间必须有人工确认）

```
① 审核员上传录音（mp3/m4a，关联到某个「场次」）
      ↓
② ASR 转写 → 转写稿 Markdown（带时间戳 + 说话人分离）
      ↓
③ ★ 审核员确认/编辑转写稿（专业术语、方言、人名必错）
      ↓
④ 按「问答对」切分 → 在 PlannedClauses 范围内归集 → 成为证据
```

**第 ③ 步不能省**：
- 体系认证术语密集（「管理评审」「不符合项」「风险机遇」），ASR 必错
- 企业名、人名、文件编号错一个，证据就不可用
- ISO 19011 §3.9 要求「可验证」—— 转写错的内容无法验证

**状态机**：转写稿 `draft` → 审核员确认 → `confirmed` → 才能进证据库。

### 5.2 新增队列任务 `audio_transcribe`（复用现有机制）

| 任务 | 执行器 | 位置 |
|---|---|---|
| `file_convert` | `OfficeConvertTaskExecutor` | `CertPlatform.Admin/Services/StandardDirectory/` |
| `doc_extract` | `EnterpriseExtractTaskExecutor` | `CertPlatform.Auditor/Services/Ent/` |
| **`audio_transcribe`** | **`AudioTranscribeTaskExecutor`（新）** | `CertPlatform.Auditor/Services/Expert/` |

实现 `IYzhTaskExecutor`，`TaskType => "audio_transcribe"`，并在 `CertQueueNotifier.cs:34-35` 的中文名映射加「录音转写」。

**不新建队列引擎** —— 与 35 号「不新造引擎」原则一致。

### 5.3 按条款切分：三种方案

| 方案 | 做法 | 评价 |
|---|---|---|
| A 全自动 | LLM 读全文 + 条款清单 → 输出归属 | ⚠️ 20 条款 × 1 万字，注意力稀释，容易漏 |
| **B 两段式** | 先切问答对 → 再逐对判归属 | ✅ **推荐**，准确率高，成本可控 |
| C 人工指定 | 上传时标注「这段是问 8.1 的」 | ⚠️ 负担重，但最准 |

**推荐 B + C 混合**：场次声明 `PlannedClauses`（缩小范围）→ 系统逐对判归属（在范围内选）。

### 5.4 位置用**时间戳**，不是字符偏移

35 号 §八 说位置用 `span` + `quote`。**录音是例外**：

| 证据类型 | 位置表达 | 为什么 |
|---|---|---|
| 文档 | `span`（字符区间）+ `quote` | 可精确定位到原文 |
| **录音** | **`[00:12:35 - 00:14:20]`** + 转写片段 | **审核员要回听原音核对**，时间戳是录音的天然坐标 |

⇒ `LocationType` 需要三个值：`page` / `span` / **`timestamp`**。

⚠️ **必须提前定** —— 按 `span` 存录音位置，审核员拿到「第 3421 字」没法回听。

### 5.5 方言：真正的解法不是 ASR

用户指出的现实约束：**没办法约定参与人员只能说标准普通话**（车间工人、地方企业管理层）。

四条应对，前三条是常规：

1. 支持方言的 ASR 模型
2. **人工校对必须**（非可选，合规红线）
3. **不追求全文准确，只追求关键要素准确** —— 证据只需要「谁说了什么关键内容」，不需要逐字稿

**第 4 条才是关键，且不依赖技术进步：**

> 审核员听到方言回答后，**用普通话复述一遍**：「您是说 XXX，对吗？」

这样录音里就有普通话版本，转写自然准确。而且**复述确认本身就是审核员防误解的基本功**。

系统能做的是：**访谈提纲里除问题外，附一句「复述确认话术」**，让审核员照着念。

### 5.6 数据结构：录音不需要新模型

完美契合 32 号的「evidence → block → items」三层：

```
cert_check_evidence（一条 = 一个来源文件的一次取证）
    SourceFileCode = 音频文件 Code
    LocationType   = "timestamp"
    ↓ 1:N
cert_check_evidence_block（一个 = 一个语义方面 = 一个问答对）
    Title = "关于应急准备与响应的问答"
    ↓ Items
    [{ seq, text, timestamp: "00:12:35", speaker: "审核员" },
     { seq, text, timestamp: "00:12:58", speaker: "安全部经理" }]
```

**一条录音被 N 个检查项引用**（多条 evidence 指向同一音频）—— 这正是 32 号「evidence 层承载出处、block 层承载语义」的设计意图。

## 六、规范化在认证流程中的位置

### 6.1 联网核实的标准流程（ISO 17021-1 / 《质量管理体系认证规则》4.3.3）

| 阶段 | 干什么 | 数据源 |
|---|---|---|
| **① 建立体系** | 企业自行或**聘请咨询公司**建立（手册/程序/记录表） | 企业资料（散乱） |
| **② 运行 ≥3 个月** | 产生运行记录 + 内审 ≥1 次 + 管理评审 ≥1 次 | 产生记录 |
| **③ 申请认证** | 合同评审 → 受理 | — |
| **④ 一阶段审核（文件审核）** | 核查体系文件**是否符合标准框架**、确认内审/管理评审已实施 | **规范化产物 = 审核对象** |
| **⑤ 二阶段审核（现场审核）** | 验证**实际运行有效性**：访谈、观察、查阅记录 | **记录 + 现场 + 访谈 = 取证** |
| **⑥ NC 判定** | 证据 vs 准则 | 证据链 |
| **⑦ 认证报告** | 综合判断 | 判定结果 |
| **⑧ 监督（每年 9-12 个月）/ 再认证（3 年）** | 抽样 / 全面 | 记录 + 现场 |

**一阶段与二阶段间隔：最少 5 天、最长 6 个月**（留给一阶段问题整改）。

### 6.2 ★ 规范化的位置不在「NC 前/后」这个坐标系里

「规范化在 NC 检查之前」这句话对，但**容易误解成「紧接着」**。实际中间隔着：**运行 3 个月 → 申请 → 一阶段审核**。

### 6.3 ★★ 关键区分：一阶段审产物，二阶段才取证

| | 审什么 | 规范化产物的角色 |
|---|---|---|
| 一阶段（文件审核） | 文件**写得对不对** | **审核对象** |
| 二阶段（现场审核） | 实际**做得对不对** | **不是证据** |

**更本质的理由（应然 vs 实然）**：

| | 是什么 | 来源 |
|---|---|---|
| **应然** | 规定**应该**怎么做 | 制度文件、程序文件、作业指导书 |
| **实然** | 实际**怎么**做的 | 运行记录、现场观察、访谈 |

**审核 = 比对应然和实然**（ISO 19011 §3.10）。

⇒ **规范化产物属于「应然」一侧**（它规定要怎么做）。拿它当二阶段证据，等于**用「规定」证明「执行」**，逻辑不成立。
⇒ **这是 59% 的行需要现场证据的根本原因**：现场证据不是补充，是**另一半**。

### 6.4 第二轮/第三轮：判据不是轮次

| 审核类型 | 要不要重新规范化 | 为什么 |
|---|---|---|
| 初次认证 | **要** | 体系文件从无到有 |
| 监督审核（第 2、3 年） | **不要** | 文件已建立，只需修订 |
| 再认证（第 4 年） | **不要** | 同上，全面审但不重建 |

监督审核的重点明确包含「**体系文件的现行有效性**」（标准换版、法规更新后是否修订）⇒ 说明文件是**持续存在**的。

**⇒ 此时「标准文档」与「企业认证资料」合二为一。**

**真正的判据**：

> **这份文件有没有正式发布？**
> 有（盖章 / 版本号 / 生效日期 / 受控编号）→ **直接可作证据，不需规范化**
> 没有（零散制度、旧版、无签批）→ **需要规范化**

判据是「**是否正式发布**」，不是「**是不是系统生成的**」，也不是「**第几轮**」。

### 6.5 现状缺口：`confirmed` 从未写入

`InstanceState` 状态机（`StandardDirectoryFile.cs:142`）：`none / pending / filling / filled / confirmed / archived`。

实际写入（`DocumentFillOrchestrator.cs`）：

```csharp
:612  instanceRow.InstanceState = "filled";
:776  instanceRow.InstanceState = "archived";
:863  instanceRow.InstanceState = "archived";
```

`confirmed` 只在 `EnterpriseOriginalService.cs:236` 有常量定义，**全仓无写入点**。

**⇒ 系统区分不了「系统草稿」和「企业已发布的正式文件」。** 而这正是 §6.4 的判据。

**需要补**：
- 写入 `confirmed`（企业确认发布时）
- 企业行加 `SourceInstanceCode`（指向它来自哪个规范化产物实例）⇒ 追溯「这份文件是系统生成后企业盖章的」

### 6.6 合规边界（机构不能既咨询又认证）

联网核实原文：

> 「发证认证机构**不可以为本机构辅导过的企业**开展认证审核发证工作…同一家机构既帮企业搭建体系文件，又安排自己审核员审核发证，属于**不合规操作，证书存在后期被监管撤销风险**。」
>
> 「**咨询认证一条龙服务是国家明令禁止的**。」

| 做法 | 判断 |
|---|---|
| 机构用系统**帮企业写文件** | ❌ **踩红线** |
| 机构用系统**审咨询公司交的材料** | ✅ **完全合规，且是刚需** |

⇒ **规范化的角色应从「生成文件」改为「检查文件」**（详见 §七）。

## 七、数据源总表（回答「数据源错则流程全错」）

### 7.1 三源模型

| # | 源 | 表 | 性质 | 现状 |
|---|---|---|---|---|
| ① | **企业认证资料** | `cert_standard_directory_file` 企业行 | **应然**（按标准整理） | ✅ 工作流可读 |
| ② | **企业原始资料** | `cert_enterprise_original_file` | **实然的一半**（未整理的真实记录） | ⚠️ **有数据，工作流读不到** |
| ③ | **审核员现场证据** | **无表**（需新建） | **实然的另一半** | ❌ **连数据都没有** |

### 7.2 按阶段看：每阶段读哪个源

| 阶段 | 主源 | 辅助源 | 规范化产物的角色 |
|---|---|---|---|
| 一阶段（文件审核） | ① 认证资料 | ③ 现场（首末次会议） | **审核对象** |
| 二阶段（现场审核） | ① + ③ | ② 原始资料（交叉验证） | **不读** |
| NC 判定 | 证据链（①+②+③） | — | **不读** |
| 认证报告 | 判定结果 | 证据链 | **不读** |

### 7.3 三源交叉的判定关系

| 比什么 | 判什么 | 对应 31 号的线 |
|---|---|---|
| ① vs ② | **一致性**：认证资料说的是不是真的 | ② 一致性判定线 |
| ① vs ③ | **符合性**：实际做的符不符合规定 | ③ 符合性判定线 |
| ② vs ③ | **印证**：原始记录和现场说法对不对上 | ② 一致性判定线 |

⚠️ **没有 ② 就判不了一致性** —— 而这恰恰是最能抓到造假的一条线。

### D26 · 计划与任务的关系

### D27 · 录音的告知与保存

### D31 · 「场次」还是「部门」做第一轮过滤

## 九、坑

1. **⛔ 不要把音频加进 `document` 白名单段**。企业资料是槽位制，扩展名要匹配模板（`EnterpriseFileService.cs:736`），音频塞进去必然被挡。走独立通道。
2. **⛔ 不要用 `span` 存录音位置**。审核员要回听，必须是时间戳（`LocationType='timestamp'`）。
3. **⛔ 不要把「计划」塞进 `ScopeSnapshot` JSON**。一个任务多份计划，JSON 存了就没法按场次聚合。
4. **⛔ 不要让 ASR 转写稿直接进证据库**。方言 + 术语必错，必须人工确认。
5. **⛔ 不要让 AI 描述照片当判定依据**。ISO 19011 要求证据可验证，AI 看图是二次加工。
6. **⛔ 别把「区域」改名成「场次」**。两者是 1:N 关系，不是同一个东西。
7. **⚠️ 59% 这个数会被反复挑战**。口径是「含」不是「主类型」，用「主类型」算只有 32%，但那是低估。
8. **⚠️ 规范化产物在一阶段是审核对象**，不是证据。混了会导致「用规定证明执行」的逻辑错误。
9. **⚠️ `confirmed` 状态从未写入**。想判断「企业是否已发布」必须先补这个状态。
10. **⛔ 不要把「过程/区域」列直接当 `DepartmentCode`**。它混了角色（`GM/MR`）、过程组（`采购过程、销售过程`）、部门组（4 个部门），粒度大于部门。用 `ProcessAreaName` 原样存。
11. **⛔ 不要用「部门」做第一轮过滤入口**。块 5 与块 7 部门组一字不差、条款完全不同（7.1 vs 8.5）⇒ 按部门过滤会把两场会合并。**入口是场次**。
12. **⛔ 不要按条款建检查项**。76 行 → 59 条款，丢 17 行部门归属；`E6.1.2` 的 4 份证据会塞进一条，AI 分不清哪份是哪个部门的。
13. **⛔ 不要只按「部门相等」过滤证据**。必须 `部门 = 本场 ∪ 部门为空（全公司级）∪ 显式跨部门引用`，否则**管理层证据永远查不到**（方针、管理评审、目标是全公司级，没有 `DeptCode`）。
14. **⛔ 不要正则解析条款号原文**。`Q 5.2.1/2 E & H 5.2` / `QE10.2` / `E& H 6.1.4` 三种空格习惯 ⇒ 原文只显示，结构化另存。
15. **⛔ 不要让企业在注册/上传时选部门**。样本企业 13 个部门/角色 ⇒ 上传页要 13 个入口，企业直接放弃。**上传后 AI 建议 + 审核员批量确认**（`DeptSource` 留痕，未确认不能作 NC 依据）。
