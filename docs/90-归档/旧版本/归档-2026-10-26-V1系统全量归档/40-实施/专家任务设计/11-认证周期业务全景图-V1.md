| 项 | 值 |
|---|---|
| 企业 | XX 有限公司（`cert_enterprise.Code = E001`） |
| 标准 | ISO 9001:2015（`StandardCode = ISO9001`） |
| 认证机构 | 河北雄安尚龙认证有限公司 |
| 专家 | 张专家（本期唯一操作人，D21 不区分角色） |
| 检查项总数 | 该标准该阶段 40 条 NC 规则 / 6 个报告章节 |

**3 年周期内的审核事件序列**（ISO 9001:2015 标准流程）：

```
第 0 年
  6月  ★ S1 第一阶段审核（文件审核）        ┐ 初次认证，不在任务系统内流转
  9月  ★ S2 第二阶段审核（现场审核）        ┘
     11月  CD 认证决定 / CE 颁发证书（3年有效期）

第 1 年  6月  ★ SV-1 监督审核
第 2 年  6月  ★ SV-2 监督审核
第 3 年  6月  ★ SV-3 监督审核
第 3 年  9月  ★ RC 再认证（= S1+S2 合并，完整审核）
            → 新周期开始
```

**关键业务事实**：

| 事实 | 出处 | 对设计的影响 |
|---|---|---|
| 监督审核**可缩小范围**（不必覆盖全部条款） | ISO 17021 / CNCA 认证实施规则 | SV 阶段**局部任务是主场景**，不是例外 |
| 监督审核**必须覆盖**：上次所有不符合项的验证 + 内审 + 管理评审 + 投诉 + 上次遗留 | 认证实施规则 | SV 范围虽小但**有强约束**，不能随便勾 |
| 审核发现须经**审核组长复核**方为有效 | ISO 19011 §7.2 | 同一次审核至少有 **2 轮执行**（初稿 + 复核） |
| 报告章节跨事件**大量重复**（「审核概述」6 次事件 80% 相同） | 业务常识 | 必须支持章节沿用 |

## 二、一次审核事件内部：为什么是 2 轮

### 2.1 ISO 19011 的两层结构

```
审核组长（Lead Auditor）           审核员（Auditor）
├─ 策划审核                        ├─ 实施审核
├─ 主持审核监督 ★                   ├─ 记录发现
├─ 复核审核发现 ★                   ├─ 编制审核草稿 ★
└─ 批准审核报告 ★                   └─ 提交草稿
      ↑                                    ↓
      └────── 复核：认可 / 退回修改 ────────┘
```

### 2.2 映射到任务系统

| ISO 概念 | 任务系统 | 专家（管理员）扮演 |
|---|---|---|
| 审核员编制草稿 | 任务第 1 轮执行 → 结果待认可 | 张专家（自动结果已出） |
| 审核组长复核 | 任务第 2 轮「继续执行」 | 张专家（逐条认可/修改） |
| 批准报告 | 任务批准（`approve`） | 张专家 |

> ⛔ **本期不建模"审核组长"这个角色**（D21）。但 `CreateBy` / `ReviewBy` / `ModifyBy` 字段必须落全，将来引入角色时历史数据自动可用，**零迁移**。

### 2.3 第 2 轮的关键特性：**局部 + 沿用**

组长复核时不会把 40 条全看一遍。他只看：
- 初稿判为 `nonconform` 的（有争议要核对）
- 初稿 AI 置信度低 `< 0.5` 的
- 初稿 `failed` 的
- 随机抽查若干条

**其余项直接沿用第 1 轮结果**。这直接对应你的原话：

> 「让用户选择需要保留的结果……只保留文件更改过的」

**3 年累计：约 24 个任务 / 企业 / 标准**。

**关键观察**：
1. **同一个事件内 2 轮**（初稿 + 复核）
2. **SV 事件的全局任务是例外**（通常只有局部）
3. **报告任务大量是"继续"模式**（沿用上次的章节）
4. 任务数是可接受的（24 个 / 3 年 / 企业 / 标准）

### 3.2 「继续」vs「新建」的界面差异

| | 继续（TSK-…-0002） | 新建（TSK-…-0005） |
|---|---|---|
| 入口 | 从任务详情页点 [复核本任务] | 从任务列表点 [创建任务] |
| 范围预设 | **自动勾选**：初稿的 nonconform + 低置信度 + failed | 全部未勾选（或按范围类型） |
| 沿用项 | 未勾选的项**自动沿用上一轮**，界面上灰显且标注"沿用第 N 轮" | 无沿用（`FULL` 全部重算） |
| 任务名 | `TSK-…-0001 · 复核` | `TSK-…-0005 · 第二阶段审核` |
| 结束后 | 组长认可 → `approved`（**该事件定稿**） | 仍是 `pending_review`（等下一次的复核任务） |

> ⚠️ **注意**：`approved` 的语义在两种模式下不同 —— 继续任务的 `approved` = **该审核事件定稿**；新建任务的 `approved` = **这一轮已认可**。这是需要消歧的地方，见 §六结论 3。

**当前有效结果 = 轮次 9**（最新）。
**历史 = 9 轮**（其中 2 轮是"沿用"无新轮次）。

### 4.3 这个例子暴露的 4 个设计需求

| # | 需求 | 原因 |
|---|---|---|
| **N1** | 检查项是**独立实体**，跨任务跨事件长期存在 | 15 轮结果挂在同一个实体上，才有"这企业反复在这条款出问题" |
| **N2** | 结果是**多轮次**，不是单值 | 专家要看历史（轮次 3 判不符合 → 轮次 6 改回符合） |
| **N3** | 需要标记**"当前有效轮次"** | 列表默认显示最新，不能让专家在 15 轮里找 |
| **N4** | "沿用"要**留痕但不产生新轮次** | 轮次 7/8 是"沿用轮次 6"，不是新结果。若也产生轮次，3 年后轮次会膨胀到 30+ 且噪声大 |

> ⛔ **N4 是关键决策点**：沿用行为**不产生新结果轮次**，只在任务上记录"本次沿用了哪些项"。轮次表只在"真正重新计算"时增长。

## 五、报告章节的生命周期

### 5.1 章节：2「审核准则」

| 轮次 | 时间 | 来源事件 | ContentText（节选） | 沿用关系 |
|---|---|---|---|---|
| 1 | 第0年8月 | S1 | 审核依据：GB/T 19001-2016/ISO 9001:2015…（全文展开） | 全新生成 |
| 2 | 第0年8月 | S1 复核 | （同上，专家微调措辞） | 局部修订 |
| 3 | 第0年10月 | S2 | **完全沿用轮次 2** | ★ 整段沿用，无新轮次 |
| 4 | 第1年7月 | SV-1 | **完全沿用轮次 2** | ★ 整段沿用 |
| … | | | | |
| 9 | 第3年 | RC | 沿用轮次 2 | |

> **报告章节的沿用率极高**。「审核准则」在 3 年 6 次事件中**内容完全不变**（依据的标准没变），只有「审核目的」「审核日期」「审核组」会变。
>
> 这意味着：**如果每次都让 AI 重新生成 + 专家重写，报告工作会产生大量无意义劳动**。沿用机制是必须有的。

### 5.2 章节：1「审核概述」

这个章节**变化多**（目的/日期/审核组每次不同），沿用率低。

| 轮次 | 来源事件 | 变化点 | 处理 |
|---|---|---|---|
| 1 | S1 | 目的="第一次审核" | 全新生成 |
| 3 | S2 | 目的="第二次审核"，范围相同 | **继承上轮 → 专家只改目的字段** |
| 4 | SV-1 | 目的="第1次监督审核" | 继承上轮 → 改目的 |
| … | | | |

> ⚠️ **"继承上轮"和"完全沿用"是两种不同的沿用**：
> - **完全沿用**：内容一个字不改 → 不产生新轮次
> - **继承初值**：以上轮为起点，但本次会改 → 产生新轮次
>
> 这与你上一轮说的「让用户选择需要保留的结果」是同一件事的两种粒度。

## 六、结论：做 / 不做认证周期模型

### 6.1 三个方案

| | 方案 A：周期+事件 | 方案 B：只做任务+轮次 | 方案 C：任务+轮次，预留字段 |
|---|---|---|---|
| 新增表 | `cert_cycle` `cert_event` +2 | 无 | 无（结果表加 `EventCode` 可空列） |
| 表总数 | **12 张** | **8 张** | 8 张 |
| 任务归属 | 挂 `EventCode` | 挂 `TaskCode` | 挂 `TaskCode`，预留 `EventCode` |
| 轮次归属 | `EventCode` + `TaskCode` | `TaskCode` | `TaskCode` + 可空 `EventCode` |
| 任务列表分组 | 可按周期分组 | 按时间排序 | 按时间排序 |
| "第几次监督审核" | 显式（`EventType=SV, EventSeq=1/2/3`） | 靠时间 + 任务名推断 | 靠时间 + 任务名推断 |
| 证书到期提醒 | ✅ 可做 | ❌ | ❌ |
| 跨周期对比 | ✅ 天然支持 | ⚠️ 需按时间区间硬编码 | ⚠️ 同 B |
| 额外工作量 | **+2.5 人天**（2 表 + 周期管理页面 + 事件生成逻辑） | 0 | +0.2 人天 |
| 未来补做的成本 | — | 需迁移历史数据（加列 + 回填） | 低（字段已在） |

### 6.2 一次 3 年周期的数据量（方案 B 的实测估算）

| 实体 | 3 年/企业/标准 | 100 家企业 × 3 标准 = 300 组 |
|---|---|---|
| 任务 | 24 | 7,200 |
| 标准子任务 | 36 | 10,800 |
| 检查项实体 | 40 | **12,000**（40 × 300） |
| 结果轮次 | 约 40 × 9 = 360 | **108,000** |
| 日志 | 约 700 | 210,000 |
| 报告章节实体 | 6 | 1,800 |
| 章节轮次 | 约 20 | 6,000 |

**5 年（500 组）：结果轮次约 18 万行。** 无分表必要。

> ⛔ **注意「检查项实体」这一行**：不管做不做周期模型，**这一层都必须建**。因为用户的核心需求「同一个阶段只有一套执行结果，多个历史结果」要求结果挂在检查项实体上，而不是挂在任务上。

### 6.3 我的建议

**方案 C（本期不做周期，但预留 `EventCode` 字段）**，理由：

| 理由 | 说明 |
|---|---|
| 周期模型是**管理功能**，不是执行功能 | 专家日常只需要"查结果、改结果、导出"。证书到期提醒是管理层需求 |
| 3 年周期时间跨度长 | 系统上线时存量企业大多在周期中段，周期起点难以准确回填 |
| 任务数不爆炸（24/3年/企业/标准） | 任务列表靠时间排序 + 阶段筛选够用 |
| 字段预留成本极低（0.2 人天） | 将来要做，直接用预留字段，无需迁移 |
| **但检查项实体 + 结果轮次必须本期做** | 这是"一套执行结果 + 多个历史"的载体，是你需求的技术必然 |

⚠️ **但这需要你确认一个业务判断**：你们是否需要在系统里**管理认证周期**（知道证书什么时候到期、该安排第几次监督审核）？如果需要，方案 A；如果不需要，方案 C。

## 七、待你确认的业务问题

| # | 问题 | 为什么必须先定 |
|---|---|---|
| **B1** | 系统是否需要**管理认证周期**（证书有效期、到期提醒、第几次监督）？ | 决定方案 A 还是 C |
| **B2** | 「继续（复核）」和「新建」是**两种任务模式**，还是同一种任务的两种范围？ | 决定任务表是否要 `TaskMode` 字段 |
| **B3** | 沿用行为**不产生新轮次**（只留任务级痕迹），对吗？ | 决定结果轮次表的增长速度（3 年 9 轮 vs 15 轮） |
| **B4** | 任务 `approved` 有两种含义（事件定稿 vs 本轮认可），要区分吗？ | 决定是否加 `TaskKind` 或 `FinalizeType` 字段 |
| **B5** | 同一事件内，「审核员初稿」和「组长复核」是两个任务，还是一个任务的两轮？ | 决定任务数量（24 vs 12）和页面结构 |
| **B6** | SV 阶段的检查范围，是否需要**系统预置推荐**（上次不符合项 + 内审 + 管理评审 + 投诉）？ | 决定是否要做"范围推荐"功能 |
