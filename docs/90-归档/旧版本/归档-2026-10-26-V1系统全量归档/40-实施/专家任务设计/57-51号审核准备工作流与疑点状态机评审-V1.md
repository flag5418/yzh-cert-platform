# 51 号审核准备工作流与疑点状态机评审（V1）

> 2026-10-23 ｜ 评审对象：`51-审核准备工作流与疑点状态机-V1.md`
> 关联：`47-二阶段检查单工作台V1设计输入与战略收敛-V1.md`、`48-851条款人肉试跑证据归位报告-V1.md`、`49-851疑点清单与入场计划POC-V1.md`、`50-程序架构收敛五层模型与条款属性Schema-V1.md`
> 结论：**工作流方向成立，状态机尚未成立**。七步主循环是对的，但当前“状态机”把状态、解决方式、验证层级、结论混在一张图里；且“AI 补全证据链”与 48/49/40 号已确立的证据红线冲突。修正前不宜按此直接写代码。

## 一、总裁决

| 维度 | 判断 | 说明 |
|---|---|---|
| 七步工作流 | **成立** | 拿资料→AI 疑点→人工过滤→分流→入场计划→远程核实→现场采集→结论→复核，确实是主产品核心循环 |
| 疑点作为独立实体 | **成立且关键** | 补上“检查项→NC”的候选态；比直接生成 NC 更符合审核认知 |
| 人工过滤/结构化驳回 | **成立** | 驳回理由是规则调优数据；但“删一半”不能当设计指标 |
| 远程 vs 现场分级 | **成立** | 文件类可远程关闭；实施类只能部分排除；这是本稿最有价值的红线 |
| 外发脱敏 | **方向对，但不够** | 只脱敏不够；还需审批、最小化、中性话术、留痕、禁止 NC 方向/规则编号外泄 |
| 状态机 | **未成立** | 状态、渠道、验证层级、结论四类信息混用；缺迁移表、守卫、终态、重开、并发/幂等 |
| AI 角色 | **表述冲突** | 50 号说执行期无 LLM；51 号说“AI 跑 100 疑点”“AI 补全证据链”；需明确规则引擎 vs LLM 的边界与 provenance |
| 入场计划 | **偏薄** | “不按部门排”过于绝对；缺条款/过程/部门/场所/班次覆盖矩阵与 CNCA 15 字段等合规要求 |
| 数据模型 | **不足** | 只有实体名，没有字段、关系、状态历史、证据多对多、与现有检查项/NC/任务表的映射 |
| 总体 | **A- 业务方向 / C+ 可施工性** | 先改状态机与证据措辞，再做 10 条疑点的纵向切片；不要先铺平台 |

## 二、做对了什么（应保留）

1. **疑点是候选态，不是 NC**：`AI候选 → 保留/驳回 → 证据 → 结论 → NC` 的认知顺序正确；直接“AI 出 NC”既不可信也不合规。
2. **人工过滤是产品的一部分，不是补丁**：批量操作、结构化驳回理由、规则级驳回，符合审核员真实工作方式。
3. **远程核实与现场采集分级**：文件类可远程关闭，实施类必须现场或追加访问；这条应升级为硬规则，不是建议。
4. **外发脱敏**：内部疑点清单 vs 可外发询问事项的区分非常关键；这是公正性/保密性的底线。
5. **专家新增疑点是一等公民**：资深专家的判断不能被降级成备注；同结构、同状态机、同留痕是对的。
6. **反馈环**：保留/驳回/确认/升级都是规则调优信号；规则版本化 + 历史结论 immutable 的方向正确。
7. **审核准备层阶段无关**：二阶段主产品与企业侧迎审准备可复用预审模式；这个分层是对的（但“一阶段=准备度审核”的表述要修正）。

## 三、P0：修正前不应直接施工

### P0-1 状态机不是状态机：四类信息被压成一条线

51 号 §二 的图（`51:22-27`）同时表达了：

- **状态**：AI候选、保留、已排除、部分排除、未决、转入现场、已关闭；
- **解决方式**：问询、观察、远程、现场；
- **验证层级**：远程核实、现场采集；
- **结论**：结论草案、不符合、NC；
- **动作**：裁定、升级 NC。

这会导致状态爆炸、迁移不可判定、UI 无法表达、审计留痕不完整。例如：

- “保留(问询)”不是状态，是 `status=retained` + `channel=inquiry`；
- “部分排除”不是终态，必须还有 `onsite_pending`；
- “转入现场”不是状态，是 `verification=onsite` 的路由结果；
- “结论草案”不是状态，是 `conclusion=draft` 的产物；
- “升级 NC”不是状态，是副作用（创建 `cert_expert_nc_item`），疑点仍需保留关联。

**修正**：拆成四个正交维度 + 一张迁移表。

| 维度 | 取值（建议） | 说明 |
|---|---|---|
| `Status` | `candidate` / `retained` / `remote_pending` / `remote_partial` / `onsite_pending` / `evidence_ready` / `draft_conclusion` / `confirmed` / `closed` / `rejected` / `deferred` | 只表达“流程走到哪” |
| `Channel` | `inquiry` / `observation` / `remote` / `onsite` / `document` | 只表达“用什么方式解决” |
| `VerificationLevel` | `L1_onsite` / `L2_record` / `L3_template` / `remote_document` | 只表达“证据可信度/验证方式” |
| `Conclusion` | `none` / `conformity` / `nonconformity` / `observation` / `ofi` / `not_applicable` / `insufficient_evidence` | 只表达“判定结果” |
| `NcCode` | 可空 | 确认不符合后关联 NC；不是状态 |

**必须有的守卫**：

- `rejected` 必须填理由；软删可重开；
- `closed` 必须有证据或“无法获取”的书面理由；
- `nonconformity` 必须人工确认，AI 不得直接落；
- 实施类疑点 `VerificationLevel=remote_document` 时，**禁止**直接 `closed`，只能 `remote_partial → onsite_pending`；
- `NcCode` 创建必须幂等（同一疑点重复升级不产生多条 NC）；
- 每次迁移写 `doubt_transition`（操作人/时间/从/到/理由/证据引用/规则版本）。

### P0-2 “AI 补全证据链”与证据红线冲突

51 号 §一 第 7 步写“AI 补全＋结论＋复核”，并说“证据归位→结论草案→人工确认→写入检查单证据列”（`51:17`）。但 48/49 号已明确：

- 四要素事实（时间/地点/人物/数值）**只能来自现场采集，不得生成**（48 号 §6.3/§6.5）；
- 文档侧与现场侧**禁止合并成一段“完整证据文本”**（49 号 §三）；
- AI 只能从证据池取数，取不到即留槽（49 号 §三）。

**问题**：`补全` 是危险词。若 AI 把缺失的证据“补”出来，就是编造记录；若只是把已有证据归位/摘要/提示缺口，则不应叫“补全”。

**修正**：改为 **“AI 归位/摘要/缺口提示 + 结论建议”**：

- 证据只从 `L1/L2/L3` 证据池取；每条带来源锚点、采集人、时间、层级；
- L3（模板/咨询交付 artifact）不得作为判定依据，只能标疑点；
- AI 输出是“建议者档”，保留 `ai_suggestion` 与 `human_final` 双份，便于审计；
- 缺口只能是“未获取/待现场确认”，不能自动生成四要素；
- 结论段永远人工落定；AI 不签字、不负责。

### P0-3 “AI 跑 100 疑点”与 50 号“执行期无 LLM”不一致

50 号 §一 第 3 条明确：规则=结构化条件，**执行期无 LLM**；LLM 只在预处理（实例抽取）与后渲染（措辞）。51 号却写“AI 跑一遍出 100 疑点”“AI 补全证据链”。

**需要明确**：这里的“AI”到底是：

- A. 规则引擎（确定性）+ 文档抽取（LLM）→ 疑点；
- B. LLM 直接读文档生成疑点；
- C. 混合：规则优先，LLM 只做候选提示。

三者法律/可解释性/成本/稳定性完全不同。

**修正**：

- 疑点加 `Source`：`rule` / `llm` / `human`；
- `rule` 必须有 `RuleCode + RuleVersion + DataRef`；`llm` 必须有 `Model + PromptVersion + EvidenceRef + Confidence`；
- 不允许 LLM 伪造 `rule_id`；LLM 候选必须人工确认后才能进入“保留”；
- 规则执行与 LLM 渲染分层，别把“执行期无 LLM”写成“全流程无 AI”；
- 若走混合，先跑规则，LLM 只对规则无法覆盖的语义/一致性做补充，避免 100 条噪声。

### P0-4 微信远程核实：脱敏不够，缺审批/证据链/角色

51 号 §三 红线 1 说“疑点清单外发必须脱敏”，方向对，但仍不够：

- **谁批准外发**：审核组长/项目负责人审批；不能由单个专家直接发给企业；
- **发给谁**：企业指定联系人；不能发群、不能转发；
- **发什么**：只发“请提供 X 记录/请确认 Y 过程”的中性问句；禁止规则编号、NC 方向、风险分、内部批注、其他企业信息；
- **怎么留痕**：外发内容、时间、接收人、审批人、企业回复、证据文件；截图需哈希/时间/采集人；
- **证据效力**：微信截图可编辑，不能单独作为关闭依据；需原始文件/记录 + 审核员核验；
- **实施类**：远程只能部分排除，必须转现场或追加访问；
- **个人信息**：聊天记录含员工信息时，需最小化/同意/留存期限；避免个人微信长期保存客户资料。

**建议**：产品内置“询问事项”通道（企业上传/回复），微信只作为通知渠道；不要把微信聊天记录直接当证据池。

### P0-5 入场计划：不能只说“不按部门排”

51 号 §一 第 4 步写“按疑点排动线（不按部门排）”（`51:14`），49 号 POC 也写“按疑点分布排，不按部门排”。这句话作为“优先疑点”是对的，作为“审核计划原则”是危险的：

- 二阶段审核必须覆盖审核范围/条款/过程/部门/场所/班次；只按疑点排会漏覆盖；
- 审核计划是合规文件，不只是动线；CNCA 15 字段、两阶段窗口、提前 3 日报送、人日/监督时钟都要有（49/50 已列）；
- “人日扣减”不是随便扣，需有依据/审批；不能把合规外壳写成固定公式；
- 现场动线可按地点/过程聚合，但覆盖矩阵必须先成立。

**修正**：

1. 先建 **覆盖矩阵**：条款 × 过程 × 部门 × 场所 × 班次 × 审核方法；
2. 再按“地点/过程”排动线，把疑点作为 slot 内的优先项；
3. 计划生成后做 **覆盖校验**（未覆盖条款/部门/班次告警）；
4. 合规外壳独立成“规则包”，按标准/方案/机构配置，不硬编码；
5. 明确“疑点驱动”是排序策略，不是覆盖策略。

## 四、P1：重要但可并行修正

### 4.1 数据模型：先把“疑点”接到现有表上

51 号只说 `cert_expert_doubt_item` 位于检查项与 NC 之间（`51:29`），但没有字段/关系。至少要先回答：

| 问题 | 建议 |
|---|---|
| 疑点属于谁 | `OrgCode` + `EnterpriseCode` + `StageCode` + `SessionCode`（可空）+ `StandardCode`；不要只挂任务 |
| 疑点挂哪 | `CheckItemCode`（可空，手工疑点可无）+ `ClauseCode` + `ProcessCode` + `DeptCode` |
| 证据关系 | 疑点 ↔ 证据 **多对多**；证据可服务多个疑点；允许未绑定证据 |
| NC 关系 | 疑点 0..1 NC；NC 可由多条疑点合并；保留 `DoubtCode` 关联 |
| 状态历史 | 独立 `cert_expert_doubt_transition`，不要只写当前状态列 |
| 去重 | `DedupeKey`（规则+条款+数据引用）防 AI 重跑重复；人工可合并/拆分 |
| 业务键 | `Code` 唯一；遵守项目 `Code` 规则，不用 `Id` 做业务定位 |
| 来源 | `Source`（rule/llm/human）+ `RuleCode/RuleVersion` 或 `Model/PromptVersion` |
| 审计 | `CreateBy/UpdateBy/DeleteBy` 用用户 Code；软删 + 理由 |
| 结论 | `Conclusion` + `Severity` + `NcCode` + `ConfirmedBy/ConfirmedTime` |
| 外发 | `OutboundStatus` + `OutboundApprovedBy` + `OutboundContentHash` |

> 先画 ER 图再接现有 `cert_check_item` / `cert_check_result` / `cert_expert_nc_item` / `cert_expert_task`；不要让“疑点”变成第二套任务系统。

### 4.2 角色与权限

至少区分：

- **审核组长**：批准外发、批准计划、确认 NC、关闭疑点；
- **审核员**：采集证据、提出/修改疑点、起草结论；
- **技术专家**：提供技术意见，不独立签字/不单独关闭；
- **复核人**：独立复核（如机构要求）；
- **企业联系人**：只能看“询问事项”，不能看内部疑点清单/规则/风险分；
- **企业端用户**：独立租户，不能看到认证机构租户的疑点。

51 号目前统一叫“专家”，会掩盖权限差异。

### 4.3 “一阶段”表述要修正

51 号 §五 说“一阶段审核是另一项活动（准备度审核）”（`51:47`）。更准确：

- 一阶段是 **审核阶段**（ISO 17021-1），目的是确定是否准备好进入二阶段，包含文件评审、范围/资源/内审/管理评审等；不是“准备度审核”这么轻；
- 51 的七步是 **审核准备**，阶段无关；它可服务于二阶段，也可服务于企业迎审准备；
- v1 只做二阶段产品没问题，但不要把“审核准备”叫成“一阶段”；
- 企业侧迎审准备是独立产品/租户，注意咨询与认证的隔离（41 号）。

### 4.4 反馈环：别把客户数据直接拿去训练

51 号 §四 说“每个项目做完，规则精度上一档”。方向对，但要加：

- 只回传 **匿名元数据/命中统计**，不上传审核内容（53 号已有此原则）；
- 规则调优与模型微调分开；不把客户文档发给模型厂商做训练；
- 规则版本、提示词版本、模型版本都要留；历史结论 immutable；
- 需要 holdout/盲测，避免“专家个人偏好”污染规则；
- 规则级驳回要防“一键全删”误杀：批量操作需预览、抽样、撤销、审计。

### 4.5 指标：不要用“删一半”当目标

“AI 出 100，人工删 20/一半”只是用户描述，不是产品指标。建议追踪：

- 疑点采纳率（保留/生成）；
- 误报率（按规则/条款）；
- 每条疑点人工处理时间；
- 从资料到入场计划的时长；
- 现场证据采集时长；
- 疑点→NC 转化率；
- 漏报（事后审核发现但系统未提示）；
- 专家修改率（AI 建议 vs 人工最终）。

没有这些，无法证明“AI 净增量”，也无法决定 100 条是否太多。

### 4.6 UI 细节

- 批量驳回：按规则分组可以，但要有“样本预览 + 数量 + 撤销 + 二次确认”；不要一键全删；
- 疑点卡：显示来源/规则版本/证据锚点/置信度/建议解决方式/潜在 NC 方向；内部可见，外发隐藏；
- 证据：支持多对多、未绑定证据、拍照即挂、离线草稿、冲突提示；
- 计划：一键生成后必须做覆盖校验，不能只拖拽；
- 审计：每次操作可追溯；AI 建议与人工最终双栏/diff。

## 五、建议的状态迁移表（最小版）

| From | 事件 | To | 守卫 |
|---|---|---|---|
| candidate | 保留/问询 | retained | 人工确认；填 channel |
| candidate | 保留/观察 | retained | 人工确认；填 channel |
| candidate | 驳回 | rejected | 必填理由；软删 |
| retained | 发起远程 | remote_pending | 组长批准外发；内容脱敏 |
| remote_pending | 文件类排除 | closed | 有证据/书面说明 |
| remote_pending | 部分排除（实施类） | remote_partial | 必须转现场 |
| remote_pending | 未决 | onsite_pending | 记录原因 |
| remote_partial | 转现场 | onsite_pending | 不允许直接关闭 |
| retained | 直接现场 | onsite_pending | 观察类/实施类 |
| onsite_pending | 证据齐 | evidence_ready | 证据带 L1/L2 锚点 |
| evidence_ready | AI 起草 | draft_conclusion | AI 建议档；不落最终 |
| draft_conclusion | 人工确认符合 | confirmed | 人工签字 |
| draft_conclusion | 人工确认不符合 | confirmed | 人工签字；可升级 NC |
| confirmed | 关闭 | closed | NC 已建/无需 NC |
| rejected/closed | 重开 | retained | 理由 + 权限 |

> 这张表只是最小版；实现前要补并发（两人同时操作）、幂等（重复提交）、权限（谁能做）、通知（外发/待现场）和审计字段。

## 六、与 47/48/49/50 的一致性

| 文档 | 51 号应对齐的点 | 当前问题 |
|---|---|---|
| 47 | AI 只读文档（应然），现场（实然）由人录入；双栏预填 | 51 的“AI 补全”容易被读成生成现场证据 |
| 48 | L1/L2/L3 证据分级；L3 不得作判定依据；四要素只能采集 | 51 只写“L1 证据入池”，未写 L3 禁用/证据层级 |
| 49 | 双栏预填；禁止合成完整证据文本；入场计划=准备包⊕合规外壳 | 51 的入场计划缺合规外壳细节；仍写“不按部门排” |
| 50 | 执行期无 LLM；规则结构化；合规外壳五件套 | 51 的“AI 100 疑点/AI 补全”与“执行期无 LLM”冲突，需明确 |

**结论**：51 号应作为 47–50 的“工作流层”，不是另起一套。所有术语/证据层级/合规规则回到 47–50 的定义。

## 七、建议的最小纵向切片

不要先做完整状态机平台；先做一条能证明价值的切片：

1. **单条款/单企业/10 条疑点**（49 号已有 POC 语料）；
2. 疑点表 + 证据多对多 + 状态迁移 + 审计；
3. 人工保留/驳回/新增；
4. 生成“询问事项”脱敏版（不生成入场计划全文）；
5. 现场采集 1 个疑点的照片+文字；
6. AI 归位/摘要/结论建议（不补全）；
7. 人工确认 1 条符合/1 条不符合，升级 1 条 NC；
8. 导出检查单证据列 + 审计留痕。

通过标准：10 条疑点全流程可追溯；无一条四要素由 AI 生成；远程外发有审批/脱敏；现场证据可挂接；NC 人工确认。

## 八、结论

51 号的**业务方向是对的**，而且抓住了现有模型缺的“候选态”。但它现在更像“工作流宣言”，还不是“状态机设计”：

- 状态、渠道、验证层级、结论必须拆开；
- “AI 补全证据链”必须改成“AI 归位/摘要/缺口提示”；
- “AI 100 疑点”必须明确规则引擎 vs LLM，并带 provenance；
- 微信外发必须有审批、脱敏、留痕、证据效力规则；
- 入场计划必须先覆盖、再排动线，合规外壳不能省；
- 数据模型必须先接现有检查项/NC/任务表，不要造第二套。

**建议**：先把 51 修成 V2（状态迁移表 + 数据模型 + 角色矩阵 + 证据红线 + 入场计划覆盖矩阵），再用 49 号的 10 条疑点做纵向切片。通过切片再谈平台化。
