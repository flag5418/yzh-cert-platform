## 二、数据源：**两张表 + 三个角色**（核心澄清）

> ⚠️ **2026-10-19 重大修正（用户指出）**：本节初版把「企业认证资料」误称为「企业原始资料」。**两者在系统里是两张不同的表**，用途完全不同。以下为修正后版本。

### 2.0 ★★ 先分清：企业认证资料 ≠ 企业原始资料

`EnterpriseOriginalService` 类注释（`:22-38`）自带一张对照表，是唯一权威口径：

| 维度 | **企业原始资料** | **企业认证资料**（资料库） |
|---|---|---|
| 主表 | `cert_enterprise_original_file` | `cert_standard_directory_file`（企业行） |
| 组织轴 | 企业 → **阶段**（无标准） | 企业 → 阶段 → **标准 → 槽位** |
| MinIO 库 | `enterprise-original-source/…` | `enterprise-documents/…` |
| **输入性质** | 企业交上来的**散乱资料**（还没对标准） | 企业**已按标准备好**的材料 |
| 谁在用 | 企业资料规范化（画像 / 填充素材） | **NC 检查 / 报告**（工作流节点） |

**代码实证**：`grep -rn "OriginalFile" CertPlatform.Admin/Services/Workflow/` ⇒ **零命中**。

> ⇒ **工作流引擎完全不认识「企业原始资料」表。** NC 与报告读的 `docmarkdown` / `docfield` / `doctable`，全部落在 `cert_standard_directory_file` 的企业行上，即**企业认证资料**。

### 2.1 `cert_standard_directory_file` 同一张表里的三个角色

靠 `EnterpriseCode` 是否为空 + 有无产物路径区分：

| 角色 | 判定 | 含义 | 是证据源吗 |
|---|---|---|---|
| **模板行**（标准文档槽位） | `EnterpriseCode` 为空 | 配置层：规定「这个标准要交哪些文件」 | ❌ 不是（只是槽位定义） |
| **企业行**（= **企业认证资料**） | `EnterpriseCode` 非空 | 企业**按槽位备好**的文件 + 转换产物 | ✅ **是**（`MarkdownPath` / `PreviewPdfPath`） |
| **规范化产物** | 企业行 + `NormalizedPdfPath` 非空 | `DocumentFillOrchestrator` 生成的成品 | ❌ **不是**（见 §2.3） |

### 2.1b ★★★ 证据源的完整三源模型（本版新增，最重要）

| # | 源 | 表 | 性质 | 现状 |
|---|---|---|---|---|
| ① | **企业认证资料** | `cert_standard_directory_file` 企业行 | **应然**（按标准整理） | ✅ 工作流可读 |
| ② | **企业原始资料** | `cert_enterprise_original_file` | **实然的一半**（未整理的真实记录） | ⚠️ **有数据，但工作流读不到** |
| ③ | **审核员现场证据** | **无表** | **实然的另一半**（观察 / 访谈 / 照片） | ❌ **连数据都没有** |

**为什么 ② 必须能读**（业务理由，不是技术洁癖）：

| | 企业认证资料 ① | 企业原始资料 ② |
|---|---|---|
| 性质 | 按标准整理过 | 未经整理 |
| 可信度 | 可能被美化 | 更接近真实 |
| 审核用途 | 看「**应该**怎么做」 | 验证「**实际**是不是这样做」 |

> 审核员查原始记录，**就是因为认证资料可能造假**。系统只给 ①，等于让审核员失去交叉验证手段。
> 而且 31 号 §4.4 的「**一致性判定线**」（证据 vs 证据）**没有第二个源就判不了** —— ② 正是这条线的必需品。

**好消息：② 的技术条件已完全具备**（`EnterpriseOriginalFile.cs`）：

```csharp

public string? PreviewPdfPath { get; set; }      // :91  PDF 产物
```

**只差一个工作流节点**（见 §6.6）。而且 `EssentialSummary` 正好解决 §八 提的「全文 token 爆炸」—— 先用精要筛，需要细节再读全文。

代码依据（`StandardDirectoryFile.cs`）：

### 2.2 代码实证：`docmarkdown` 的真实取数路径

`NodeExecutor.cs:703-766` 的 `ExecuteDocMarkdownAsync` 是取证链路的关键节点，它的行为是**双模式**：

```
配置期：node.GetConfigString("StandardFileCode")   ← 存的是【模板行】Code
   ↓
运行期：enterpriseCode 非空？
   ├─ 是 → FindEnterpriseDirectoryFileByTemplateAsync(enterpriseCode, standardFileCode)
   │        ⇒ 反查【企业行】，读 fileRow.MarkdownPath
   └─ 否 → GetDirectoryFileByCodeAsync(standardFileCode)   ← 配置期样例数据路径
   ↓
读 MinIO 上的 Markdown 全文
```

注释原文（`:693-695`）：

> 「**双模式**（与 docField 同款）：配置期存的是**模板行**的 Code（`StandardFileCode`）；运行期 `enterpriseCode` 非空时按「企业 + 模板 Code」**反查企业上传行（取企业文档全文）**，为空时取模板行本身（样例数据路径）。」

**所以「标准文档」在系统里是「槽位定义」，真正的内容来源是企业行。** 配置期选的是槽位，运行期落到企业上传的文件。

### 2.3 NC 链路完全不读规范化产物（grep 实证）

对 `NormalizedPdfPath` / `EditableStoragePath` 全仓检索，命中全部在 **Admin 端**的转换与契约链路：

| 命中位置 | 用途 |
|---|---|
| `OfficeConvertService.cs` | 归一产物路径回写 |
| `DocTemplateController.cs` | 模板填写引擎读可编辑字节 |
| `StandardDocContractController.cs` | 契约预览 |
| `StandardDirectoryService.cs` | 删除时清理产物 |

**Auditor 侧（NC / 专家任务）零命中。**

再看 NC 判定 Prompt 的装配口（`BuildNcPromptSkill.cs:41`）：

```csharp
/// <param name="dataMaterial">★ 企业材料（由 get_field / get_table / is_* 节点的输出拼装）</param>
```

而 `get_field` 读的是 `cert_extraction_result`（`GetFieldSkill.cs:66-67`），其 `FileCode` 指向**企业实际上传文件**。

**结论**：NC 检查的数据源 = **企业认证资料**（`cert_standard_directory_file` 企业行，经 `file_convert` 转出的 Markdown / 提取的字段表格），**不是**规范化标准文档，**也还不是**企业原始资料（`cert_enterprise_original_file`，工作流读不到，见 §6.6）。

### 2.4 为什么必须这样（不是巧合）

规范化产物是 `DocumentFillOrchestrator` **用企业资料 + AI 生成**的。如果拿它当证据源：

> 用系统生成的文档，证明系统自己的判定 —— **循环论证**。

ISO 19011 §3.9 要求审核证据「与审核准则相关且**可验证**」。可验证 = 能追溯到**企业的客观记录**。规范化产物已经是加工结果，追溯链断在生成环节。

⚠️ 但有一个**灰色地带**要明确：规范化产物里**有一部分是企业填的**（`cert_fill_param_value`）。这部分算「**企业声明**」，不算「**客观证据**」——除非能回溯到原始文件。建议：**检查表不采信规范化产物中的任何内容**，需要时回原始文件取。

## 三、证据源的真实分布（样本实测 76 行）

### 3.1 数据

统计口径：76 个明细行 / 50,166 字（已排除表头行）。**一行可命中多类来源标记**。

| 来源标记 | 命中行数 | 占比 | 典型句式（样本原文） |
|---|---|---|---|
| **制度文件** | 51 | 67% | 「查见“公司内外部因素分析表”，编制：行政人资部，10/12/2025」 |
| **记录表单** | 51 | 67% | 「见“安全生产隐患整改复查意见书”，编号：【2026】WH 16号」 |
| **现场观察** | 28 | 37% | 「现场确认和实际相符」「现场查看，灭火器有效」 |
| **访谈沟通** | 32 | 42% | 「与最高管理者张庆捷**面谈沟通**，经其介绍…」「经与总经理张总**沟通获知**」 |
| **外部第三方** | 5 | 7% | 「查询国家药品监督管理局药品审评中心**官网（CDE平台）**」 |

### 3.2 聚合结论（决定性）

| 口径 | 行数 | 占比 |
|---|---|---|
| **纯企业资料**（制度/记录，无现场无访谈） | 27 | **36%** |
| **含审核员采集**（现场 或 访谈） | 45 | **59%** |
| **多源**（≥2 类来源） | 57 | **75%** |
| 平均每行来源标记数 | **2.20** | — |

**三条推论**：

1. **单源模型不成立** —— 75% 的证据天然多源。你「多节点取数 → 汇总」的设想不是可选项，是**唯一符合实际的结构**。
2. **审核员现场通道是真缺口，且影响 59% 的行** —— 我此前按「主类型」分类得出 32%，**低估了近一倍**。原因是「主类型」把「文件+访谈」混成的行归到了文件类，而这类行**访谈部分是取不到的**。
3. **证据句式高度模板化** —— 「查见“X”」「与 X 沟通获知」「现场确认」这三类句式覆盖绝大多数行。**这意味着来源标注可以规则化抽取**（正则 + LLM 校验），不需要靠人工逐项判断。

### 3.3 证据句式的三段结构

样本里一条典型证据长这样（4.1 条款，371 字）：

```
① 文件依据：查见"公司内外部因素分析表"，编制：行政人资部，10/12/2025
② 访谈确认：经与总经理张总沟通获知，识别的外部因素有…（列举）
③ 结论：    识别充分，符合要求
```

**这三段来自三个不同的源**。系统要做的正是：**分段取数 → 分段标注来源 → 拼成一条完整证据**。

## 四、证据源的 5 类 + 两个正交维度

### 4.1 `EvidenceOrigin`（谁产生的）—— ★ 新增

| 值 | 含义 | 能否自动取 | 样本占比 |
|---|---|---|---|
| `enterprise` | 企业提供的**认证资料**（`cert_standard_directory_file` 企业行） | ✅ 能（`docmarkdown` / `docfield` / `doctable`） | 67% |
| `enterprise_original` | 企业**原始资料**（`cert_enterprise_original_file`） | ⚠️ **暂不能**（缺 `docoriginal` 节点，§6.6） | 待测 |
| `auditor` | 审核员现场采集（观察 / 访谈 / 照片） | ❌ **不能**，必须人工录入 | 59%（含） |
| `external` | 外部可核验数据（官网 / 公示系统 / 证书查询） | ⚠️ 半自动（联网查 + 人工确认） | 7% |
| `system` | 系统自身计算（一致性比对结果、统计值） | ✅ 能（纯函数） | 派生 |

### 4.2 `EvidenceMethod`（怎么取）—— 31 号的 4 值必须改成**多值**

31 号 §3.2 定义 `EvidenceMethod` 单值（`document` / `record` / `observe` / `interview`）。**实测证明单值不够**：

| 单值假设 | 实测反驳 |
|---|---|
| 一条检查项对应一种取证方法 | 75% 的行 ≥2 类来源 |
| 按方法选模板即可 | 同一行需要「文件取数 + 访谈填空」两条并行支路 |

**修正**：`EvidenceMethods`（JSON 数组，多值）。一条检查项声明它需要哪几种方法，工作流按声明挂对应节点。

### 4.3 两个维度的关系（正交）

```
EvidenceOrigin = 谁产生的   （enterprise / auditor / external / system）
EvidenceMethod = 怎么取     （document / record / observe / interview / query）

对应关系（不是 1:1）：
  enterprise → document / record        （可自动）
  auditor    → observe / interview      （必须人工）
  external   → query                    （半自动）
  system     → compute                  （纯函数）
```

⚠️ **不要合并成一个枚举**。原因：同一 `Origin=enterprise` 下，`document`（查制度）和 `record`（查台账）的取证流程不同；同一 `Method=observe` 可能来自 `auditor`（现场看）也可能来自 `enterprise`（企业提供的现场照片）。

## 五、数据源如何定（不需要每项人工排查）

### 5.1 三层定位，只有中间一层需要人

```
第 1 层：条款性质推导（自动，覆盖 ~70%）
   9.2 内审 → 必然 record
   8.1 运行控制 → 必然 observe + document
   7.5 成文信息 → 必然 document + record
   ↓
第 2 层：AI 建议 + 人工确认一次（配置期，一次性）
   AI 读条款 + 样本证据句式 → 建议 { methods: [...], origins: [...] }
   审核员勾选确认 → 固化到 cert_check_item
   ↓
第 3 层：运行期按配置执行（不判断）
   读 cert_check_item.EvidenceMethods → 挂对应节点
```

**关键**：第 2 层是**一次性**的，不是每次跑都排查。250 条检查项配一遍，之后所有企业复用。

### 5.2 为什么不需要「AI 自动判断具体是哪个文件」

「需要哪类来源」和「具体哪份文件」是两件事：

| 问题 | 由谁决定 | 依据 |
|---|---|---|
| 这条需要制度还是记录？ | 条款性质 + 配置 | `cert_check_item.EvidenceMethods` |
| 具体看哪份制度？ | **目录映射** | `cert_standard_directory_file` 模板行（配置期已建） |

`docmarkdown` 节点配置的 `StandardFileCode` 就是「具体哪份」。**这是配置，不是 AI 猜**。AI 猜错一次，整条证据就错，且无法发现。

### 5.3 现场证据通道（★ 真实缺口，必须新建）

**现状**：专家端只有两个上传入口，且都是**企业侧**：

| 控制器 | 用途 |
|---|---|
| `EnterpriseOriginalController` | 企业原始资料（`/enterprise-original`） |
| `EnterpriseFileController` | 企业文件 |

**没有「审核员上传现场照片 / 录入观察记录」的通道。** 而 `cert_expert_nc_result` 只有 `EvidenceRef` / `ContentText` 两个文本字段（`ExpertResultController.cs:891` 是全仓唯一 `EvidenceRef` 写入点）。

**需要新建**：

| 项 | 内容 |
|---|---|
| 表 | 复用 `cert_check_evidence`（32 号），加 `EvidenceOrigin='auditor'` |
| 附件 | 照片存 MinIO，路径落 `cert_check_evidence.AttachmentPath`（新增列，多附件走 JSON 数组） |
| 录入界面 | 检查表页面内「现场证据」录入区（照片 + 观察描述 + 访谈对象/时间） |
| 与 AI 的关系 | **AI 不生成现场证据**，只在人工录入后做「完备性校验」（要素是否齐：时间/对象/地点/观察内容） |

⚠️ **这条不影响主体设计**：现场证据本来就是 `JudgeMode=manual`，系统只需提供**录入 + 存储 + 引用**能力，不需要自动化。而 `cert_check_evidence` 表结构已经能承载（加 2 列即可）。

## 六、一个工作流实现证据链（可行，且必须）

### 6.1 现有节点已经够用

`NodeExecutor.cs:124-131` 的节点清单，取证所需全部具备：

| 节点 | 作用 | 取证场景 |
|---|---|---|
| `docmarkdown` | 文档全文（Markdown） | ★ 主取数节点，制度/记录全文 |
| `docfield` | 字段值 | 定向取值（如「文件编号」「生效日期」） |
| `doctable` | 表格数据 | 记录表单的行 |

| `is_std_file_missing` | 文件四态 | L1 完备性 |

## 七、章节表达：`blocks` 数组 vs N 个 `ai_node`

你说「一个章节执行一个 llm」。这里需要一次澄清，因为它影响 DAG 复杂度：

| 方案 | DAG 节点数（25 章节） | 风险 |
|---|---|---|
| N 个 `ai_node`（每章节一个） | 取数 3 + AI 25 + 汇总 1 = **29** | 画布难维护；25 次串行调用；章节间一致性无法在一次调用内保证 |
| **1 个 `ai_node` 输出 `blocks[]` 数组** | 取数 3 + AI 1 + 校验 1 = **5** | 长证据（3,286 字）单次输出可能截断 |

**32 号已论证过这一点**：`{blocks:[{title, items:[]}]}` 是**一次 LLM 输出两层结构**，拆两次调用必然漂移。

**建议的判定规则**：

```
证据长度 < 500 字     → 1 个 ai_node（本来只有 1 个 block）
500 ~ 3000 字         → 1 个 ai_node 输出 blocks[]（32 号实测 95% 有结构）
> 3000 字             → 拆 2-3 个 ai_node，按原文的一级标题切分（人工配置切分点）
```

**关键区别**（你担心的「一个流程生成不了几种结果」）：

| | 会不会难 |
|---|---|
| ❌ 一个流程生成「证据 + 判定 + 描述」**三种不同格式**的结果 | 会，格式异构 |
| ✅ 一个流程生成「一个 `blocks` 数组」**一种格式**的结果 | 不会，格式统一 |

**「几种结果」的问题，用「一个数组结果」解决，不是用「多个节点」解决。**

## 八、位置定位：`span` + `quote`（不依赖 Markdown 标题）

证据必须带出处（ISO 19011 §3.9 可验证性）。但**位置怎么表达**有一个坑：

| 方式 | 问题 |
|---|---|
| 页码 | ❌ PDF 页码因转换器/字体不同而漂移，不可复现 |
| Markdown 标题路径 | ⚠️ 依赖转换器是否保留 `#` 层级（**未验证**，全仓无解析代码） |
| **字符偏移 `span` + 原文 `quote`** | ✅ **不依赖任何转换器行为**，可精确复现 |

**建议**：`span`（起止字符偏移）+ `quote`（原文片段，AI 不得改写）为**必选**；`headingPath` 为**可选增强**（有就填，没有不影响）。

`docmarkdown` 的输出已带三个溯源字段（`NodeExecutor.cs:786-789`）：

```csharp
["sourceFileCode"]  = fileRow?.StandardFileCode ?? fileRow?.Code,
["sourceVersion"]   = fileRow?.VersionNumber ?? 0,
["fileName"]        = fileRow?.FileName ?? ""
```

**缺的只有「位置」**。所以：`docmarkdown` 节点输出 + `ai_node` 输出的 `span`/`quote` = 完整出处四要素（文件 + 版本 + 位置 + 原文）。

## 十、坑

1. **⛔ 不要用规范化产物当证据源**。它是系统生成的，用来自证 = 循环论证，审计上站不住。需要时回原始文件取。
2. **⛔ 不要把「标准文档」和「规范化产物」混说**。前者是槽位（模板行），后者是产物（`NormalizedPdfPath`）。两者在同一个表里，靠 `EnterpriseCode` + 产物列区分——说错一个字，设计就偏。
3. **`docmarkdown` 取全文，长文件有 token 风险**。一份程序文件可能 2 万字。P1 先用全文，P2 需要加「按标题路径取节」节点（现有无此节点）。
4. **`docmarkdown` 只能指定一个模板行**。无法表达「最近 3 份内审报告」这类动态取数。P1 固定文件，P2 需扩展。
5. **59% 的行含现场证据，这个数字会被反复挑战**。统计口径是「含」不是「主类型」。用「主类型」算是 32%，但那是**低估**——因为「文件+访谈」混成的行，访谈部分取不到。
6. **现场证据不是「AI 自动获取」的对象**。审核员访谈和观察是 ISO 19011 规定的审核方法（§6.4.7），不是数据源缺陷。AI 能做的是「生成访谈提纲 + 校验记录要素完整」。
7. **⛔ 别把 `EvidenceOrigin` 和 `EvidenceMethod` 合并**。两个维度正交，合并会丢掉「企业提供的现场照片」这类交叉情况。
8. **`JudgeMode=manual` 不等于「不用配工作流」**。manual 章节也需要工作流——用来「整理人工录入的内容」和「做完备性校验」，只是不自动判定。
