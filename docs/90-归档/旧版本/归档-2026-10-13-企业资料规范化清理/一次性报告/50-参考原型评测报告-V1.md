## 二、✅ 值得继承的 8 条（好设计）

| # | 做法 | 为什么好 |
|:--:|---|---|
| 1 | **竖向顺序有逻辑**：定位（面包屑）→ 操作（功能菜单）→ 内容（表格）→ 问题（底部）→ 规则（页脚） | 眼睛从上到下走一遍就够，不用来回找 |
| 2 | **状态是「算出来的」** | `docState()` 注释原话：「⛔ 状态是「算出来的」不是「存出来的」」⇒ 与 `49-V3/V4` 的 P2' **完全一致** |
| 3 | **「只报需要人动手的」** | `diagnose()` 注释原话：「只报「需要人动手」的，**不做统计、不做告警、不拦截**」⇒ **这正是你第 15 轮说的「程序不阻断、只如实告知」** |
| 4 | **依赖失效分级**（不一刀切） | `DEP_KILL` = `profile`/`ai` ⇒ 清空；`DEP_KEEP` = `global`/`compute`/`replace` ⇒ 保留；`DEP_REVIEW` = `manual` ⇒ 保留+标待复核。**比「全部重来」扎实得多** |
| 5 | **输入/输出分离** | 原始资料只读（证据链），产物落 `enterprise-documents/` ⇒ 与 `49-V4` §五 的产物来源一致 |
| 6 | **有自检脚本**（3 个，47 步交互） | ★ **方法论级优点**。README §四 记录：靠 `smoke.js` 跑出 2 个真 bug（`enrich()` 就地改 MOCK / `openQueue` 传错参数） |
| 7 | **表格纪律** | `table-layout:fixed` + `white-space:nowrap` + `text-overflow:ellipsis`；备注列单行 + `title` 看全文 |
| 8 | **顶住 = 勾选框**（v7 去掉「编」按钮） | 判断对：值本来就是输入框，再给个「编」是**多余动作** |

### P1 · 设计问题

| # | 问题 | 说明 |
|:--:|---|---|
| **P1-4** | **「完成度」与「状态」并列会误读** | `docState()` 注释自己说「⚠️ 因此「完成度 100% 但没锁定」仍然是「待审」」⇒ 两个指标并排，用户会以为 100% = 通过。**建议**：完成度降为详情内的参考信息，列表主列只留状态 |

## 四、★★★ 最重要的发现：它把**后台职责全部硬编码**了

你说「这里暴露了很多我们在实际应用中，**后台应该考虑的问题**」—— 我把这些硬编码逐条列出来，**它们就是后台必须配出来的东西**：

| 原型里的硬编码 | 位置 | 后台必须提供 |
|---|---|---|
| `SRC_KIND` = global / replace / compute / profile / manual / pending | `data.js:9-16` | **数据源枚举**（= 22 号 D1 七类，一期 5 类） |
| `DEP_KILL` / `DEP_KEEP` / `DEP_REVIEW` | `app.js:204-206` | **依赖策略**（哪些来源依赖企业文件）⇒ 后台要能配 |
| `DOC_STATE` 三态（locked / empty / review） | `data.js:25-29` | **状态判据**（= `49-V4` §九） |
| `CandidateCount` / `Top1Score` / `Threshold` | `data.js` | **匹配阈值**（= 契约表 `AutoConfirmThreshold` / `ReviewThreshold`） |
| `cands`（候选池 + 命中字段 + 证据） | `data.js` | **`MatchPrompt` / `FingerprintJson`** |
| `e.Cells[].Kind`（每个锚点的来源） | `data.js` | **`SourceSpec`**（锚点数据源配置） |
| `f.promptBound`（全文规则是否挂接） | `app.js:688` | **`cert_doc_fill_prompt`**（全局填写规则） |
| `f.tags` / `f.purpose` | `app.js:676-677` | **`TagsJson` / `DocPurpose`**（语义分析产物） |
| `r.Cat` = fixed / editable / platform_generated | `data.js` | **`DocCategory` + `FixedDocSubtype`** |

> ### ★ 结论
> **原型把「后台要配什么」全部写成了常量** ⇒ 读者**看不出**这些值是从哪来的、谁配的、配错了会怎样。
> **这就是「后台问题被隐形」的根因。**
> ⇒ 重做时的关键改进：**每个值都要能点开看「这条规则来自后台哪个配置」**。
