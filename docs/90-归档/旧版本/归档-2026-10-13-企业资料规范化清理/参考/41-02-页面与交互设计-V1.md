## 二、左树：五级 + 徽标

### 2.1 ★ 层级结构（V1.1 定稿 —— 阶段在标准之上）

```text
● G4测试企业甲                        ← enterprise   cert_enterprise
   ● 初审                             ← stage        cert_cert_stage
     ● ISO 9001:2015                  ← standard     cert_enterprise_stage 绑定的标准
       ● 0 基础资料                   ← folder       后台标准文档目录结构
         ▸ 营业执照                   ← file         cert_standard_directory_file
           🔒 已锁定
         ▸ 法人身份证                 ← file
           ⚠ 4 候选
   ● 复审                             ← stage
     ● ISO 9001:2015                  ← standard     ★ 同一阶段可挂多个标准
       ● 4 记录文件
         ▸ 风险管理报告               ◉ 88%
         ▸ 年度内审计划               ◉ 100%
     ● ISO 14001:2015                 ← standard     ★ 第二个标准
       ● 4 记录文件
         ▸ 环境因素识别表
```

> ★★ **为什么阶段在标准之上**（V1 写反了）：
> 企业的「阶段定义」（`cert_enterprise_stage`，三元组 `EnterpriseCode × StageCode × StandardCode`）**已经绑定了标准**。
> 且不同阶段对同一标准的要求可能不同（如初审与复审的清单差异）⇒ 阶段必须是上层维度。

> ★★ **同一阶段可挂多个标准** —— 原型实测演示了 `复审` 下同时有 `ISO 9001:2015` 与 `ISO 14001:2015`。
> ⛔ 树**不能假设「一个阶段一个标准」**。

**五种节点与点击语义**：

| 节点 | `Type` | 点击 = 规范化范围 | 后端 `ScopeType` |
|------|--------|------------------|-----------------|
| 企业 | `enterprise` | 该企业**全部阶段全部标准** | `enterprise` |
| **阶段** | `stage` | 该阶段**全部标准** | `stage` |
| **标准** | `standard` | 该标准**全部文件夹** | `standard` |
| 文件夹 | `folder` | 该文件夹（含子文件夹） | `folder` |
| 文档 | `file` | ★ **单文件** | `file` |

> ⚠️ **「标准」是循环的维度，不是「上传」维度** —— 26 号 §2.2 原文：
> 「企业上传的原始资料是**标准无关**的。标准是**规范化阶段**才引入的维度 —— 这正是你说的『按每个标准循环企业的资料』。」

### 2.1.1 ★ 节点键构造（照抄 `resources/logic.ts` 实测坑）

```typescript
const entKey    = (code: string) => `E:${code}`;
const stageKey  = (ent: string, st: string) => `S:${ent}:${st}`;   // ★ 必须带企业前缀
const stdKey    = (ent: string, st: string, sd: string) => `SD:${ent}:${st}:${sd}`;
const folderKey = (code: string) => `FO:${code}`;
const fileKey   = (code: string) => `FI:${code}`;
```

> ⛔ **阶段键只用 `S:{阶段Code}` 会撞键** —— 实测 `G4测试企业甲` 与 `测试企业b` **都关联了「复审」阶段**
> ⇒ `el-tree` 的 `node-key` 失去唯一性，`setCurrentKey` 会把高亮打到别的企业的节点上（`resources/logic.ts` 逐字警告）。

## 三、右区：逐层收敛（★ V1.1 定稿）

### 3.0 ★ 视图随层级切换（V1.1 新增）

| 选中层级 | 视图 | 理由 |
|---------|------|------|
| 企业 / 阶段 | 文档清单表（平铺） | 该范围文档不多，直接看 |
| **标准** | ★ **文件夹卡片墙** → 点进去看清单 | 一次可能几十个文件，先看目录结构再逐个进，避免一上来铺满屏 |
| 文件夹 / 文件 | 文档清单表 | 已收敛 |

**文件夹卡片墙**每张卡显示：文件夹名 · 文件数 · 完成进度条 · `完成 x/y` · `固定 n` · `待匹配 n`。

### 3.0.1 上下文操作条（随层级变化）

| 选中 | 按钮 |
|------|------|
| 企业 / 阶段 / 标准 | 一键规范化 · 打包下载 · 重新生成勾选 |
| **文件夹** | ★ **规范化此文件夹** · 打包下载 · 锁定/解锁勾选 |
| **文件** | 打开详情 · 规范化 · 下载 PDF · 锁定/解锁 |

> **不变式**：点任何层级，**操作条第一项永远是「对该范围执行规范化」**，范围语义由选中节点决定。

### 3.5 ★ 统计区（★ V1.1：置于表格**下方**）

|------|------|--------|
| 已就位 | 锁定 + 完成度 100% 的文档数 | — |

## 四、★ 一键规范化：三级粒度 + 干跑预览

### 4.1 粒度模型（26 号 §3.6 原文，正确且已按 Q-J 方案 A 落地）

```text
┌─ 范围（用户点的树节点）────────────────────────────┐
│  企业 / 标准 / 阶段 / 目录 / 单个文件              │
│  ↓ 展开成文件清单（后端 normalize/plan 计算）       │
│  yzh_queue  ← 一个范围 = 一个「批次」，只做统计与进度 │
│    ├── yzh_queue_task  ← 一个文件 = 一个任务（原子） │
│    ├── yzh_queue_task  ← 一个文件 = 一个任务        │
│    └── yzh_queue_task  ← 一个文件 = 一个任务        │
└────────────────────────────────────────────────────┘
```

> **Q-J 特别说明**（26 号原文，避免术语混）：
> ```
> 用户说的「一个文件的规范化是一个队列」
>   → 工程落地 = 一个文件 = 一个【任务】（yzh_queue_task）
> 用户说的「不同的范围是队列的范围不一样」
>   → 工程落地 = 范围 = 一个【批次】（yzh_queue）
> ```

### 4.2 ★ 干跑预览（范围卡片）是**强制前置**，⛔ 不能跳过

点「一键规范化」**不立即入队**，而是先调 `POST /normalize/plan` 拿一份**纯统计**结果：

| 显示项 | 后端字段 | 判定规则 |
|--------|---------|---------|
| 本次将规范化 N 个文档 | `TotalCount` | 展开后的文件清单长度 |
| · 新增 M | `NewCount` | `NormalizedPath` 为空 |
| · 重新生成 K | `RegenCount` | `NormalizedPath` 非空 且 `IsLocked = 0` |
| · **跳过 S（已锁定 🔒）** | `SkippedLockedCount` | `IsLocked = 1`（**26 号 S-6**） |
| · 跳过 T（无模板） | `SkippedNoTemplateCount` | 无 `cert_doc_template` 行 或 `PublishStatus ≠ 'published'` |
| · 跳过 U（无锚点） | `SkippedNoAnchorCount` | 锚点数 = 0（**25 号：42.5% 的文件属此类，UI 要说清「纯复制即可」**） |
| 范围完成率预览 | `ScopeCompletionPreview` | `Σ已写入 / Σ分母`（⛔ **不能平均子文档的完成率**，见 `41-01` §二·3） |
| 预计耗时 | `EstimateSeconds` | `TotalCount × ~15s` |
| ⚠ 警告清单 | `Warnings[]` | 如「3 个文档尚未上传空白模板」「2 个文档锚点全为示例数据」 |

> **为什么必须干跑**：26 号 S-8「失败可解释」+ S-1「幂等：连点两次 `[开始生成]`，产物不重复、版本不虚增」。
> 干跑是幂等的**前置验证** —— 用户在入队前就能看到「会跳过什么、为什么跳过」。

### 4.3 按钮态机（防重复提交）

```text
未生成 ──[一键规范化]──► 范围卡片(预览) ──[开始规范化]──► 入队中(按钮禁用+转圈)
   ▲                                                        │
   │                                                        ▼
   └──────────── 已生成 ◄── 批次完成 ◄── yzh_queue 进度 ◄───┘

已生成 ──[↻重新生成]──► 范围卡片 ──[开始]──► …（跳过已锁定项）
已锁定 ──[🔒锁定]──► 锁定态 ──[🔓解锁]──► 解锁态（写 cert_doc_normalize_action）
```

> ⚠️ **`[↻ 重新生成]` 与 `[▶ 一键规范化]` 是两个按钮，⛔ 不合并**：
> 「一键规范化」= 智能判定新增/跳过；「重新生成」= **强制重跑**（但仍跳过已锁定项 —— 26 号 S-6）。

## 五、★ 匹配歧义（固定文档）与单元格级三大交互

### 5.0 ★★ 匹配歧义机制（V1.1 新增 —— 本轮最重要的补充）

> 用户原话：「标准文档中需要一个法人的身份证，但我们企业上传了多份身份证，电脑可能没办法精准匹配那一张是法人的，但从企业资料中找到了 3 个身份证，这就要求我们从待选项中重新选择」

**为什么自动识别必然失败**：

| 判据 | 对身份证的实际效果 |
|------|------------------|
| 文件名匹配 | `张明远_身份证正面.jpg` / `李建国_身份证正面.jpg` —— **都叫「身份证正面」**，无法区分 |
| 文档内关键字段 | 正面有姓名可比对（94%）；**反面没有姓名字段**（62%，只能靠文件名推断） |
| 分类标签 | 全部命中「身份证明」—— **无区分度** |

⇒ **同名/同类文件必须人工指定**；系统的职责是「把候选找齐 + 排优先级 + 给判定依据」，⛔ **不是替人做决定**。

**后端返回契约**（并入 `tree` / `list` 出参，端点见 `41-03`）：

```text
MatchState  : auto_matched | ambiguous | no_match | warn | confirmed
Top1Score   : decimal(3,2)
Threshold   : 0.90（落 cert_sys_config，⛔ 不硬编码）
Candidates[]: { FileCode, FileName, FileType, Size, Pages,
                Score, MatchField, MatchedBy, Evidence, Fields[][] }
```

| `MatchState` | 触发条件 | 界面 | 需人工 |
|-------------|---------|------|:---:|
| `auto_matched` | Top1 ≥ 0.90 且无同分候选 | 绿「已自动匹配」，可复核 | 否 |
| **`ambiguous`** | ≥2 个候选（无论分差） | ★ 黄告警 + 候选列表 + **必须指定** | **是** |
| `no_match` | 候选数 = 0 | 红「无可匹配文件」+ 引导上传 | 是 |
| `warn` | Top1 ≥ 0.90 但有告警（如证件有效期） | 已匹配 + 橙告警 | 建议 |
| `confirmed` | 人工已指定 | 绿「已就位」+ 🔒 | — |

**⚠️ `ambiguous` 不阻塞整批** —— 同批其他文档照常完成，只有这一个停在「待人工匹配」。

**数据落点**（详见 `41-01`）：

| 数据 | 落库 | 说明 |
|------|------|------|
| 选定结果 | `cert_doc_fill_value`（`SourceKind='profile'` + `SourceDetailJson.originalFileCode`） | 固定文档**也算一次取值** |
| 候选清单 | ⛔ **不落库**（实时算） | ⚠️ 候选随原始资料上传而变，落库即**假信息** |
| 动作留痕 | `cert_doc_normalize_action`（`ActionType='lock'`） | 只追加 |

> ★ **只有「人工选定结果」落库**，因为那是**决定**；候选是**推导**，会过期。

**「企业暂无此件」**：

| 项 | 值 |
|----|-----|
| 落库 | `cert_standard_directory_file.InstanceState = 'partial'` + `Remark` |
| 界面 | 状态列「企业暂无」，⛔ **不锁定**（后续补传可继续） |
| 作用 | 审核阶段能看到「该企业缺哪些材料」 |

### 5.1 交互一：查看数据来源（锚点 `查` 按钮）

**证据链 5 级下钻**（每一级都有兜底，⛔ 任何一级缺失都不报错）：

| 级 | 内容 | 数据来源 | 缺失时 |
|----|------|---------|--------|
| 1 | 当前值 | `cert_doc_fill_value.ValueDisplay` | — |
| 2 | **来源类型** | `SourceKind` + `SourceLabel` | — |
| 3 | **来源实体** | `SourceDetailJson`：`paramCode` / `profileCode` / `originalFileCode` | 显示「来源信息不完整（可信度已降级）」 |

### 5.4 ★ 编辑三缓冲（V1.1 新增：把「改值」和「落笔」彻底分开）


| 包内结构 | `{企业名}/{标准名}/{阶段名}/{目录层级}/{标准文件名}.docx` + 根目录放一个 `填写说明.txt`（列出各文档的完成率/可信度/待办数） |

| 源库 | `enterprise-documents/`（⛔ **不是** `standard-directory/`） |

### 6.2 「自动上传」= 归入标准目录 + 转 PDF

> 用户原话：「并能够**自动上传**或打包下载」。
> ⚠️ **口径澄清**（本册裁定）：本模块的「上传」**不是**把文件传到某个外部系统，
> 而是 **把生成好的产物回填到统一表 `cert_standard_directory_file` 的企业行 + 生成 PDF 预览** ——
> 即 26 号 A-3「产物 ⇒ 记 `SourceProfileCode` + 生成时间 + 生成批次」的落地。

| 子动作 | 落点 | 复用 |
|--------|------|------|
| 写产物路径 | `cert_standard_directory_file.NormalizedPath` | 🆕 |
| 上传到 MinIO | `enterprise-documents/{Ent}/{Std}/{Stage}/…` | `PathBuilder.EnterpriseFile()`（**已启用**） |
| 生成 PDF 预览 | `NormalizedPdfPath` | 复用 `file_convert` 队列（`OfficeConvertTaskExecutor`），⚠️ **不新建转换链** |
| 回写 `InstanceState` | `InstanceState = 'instantiated'` | 已有列（`StandardDirectoryFile.cs:99`） |
| 上传到 NC 报告 | 🔴 **不在本册范围** | NC 侧只读标准目录文件，见 §七·边界 |

> ⚠️ **`[上传到NC ▢]` 复选框**：26 号 §一 明确「**不在本轮**：发证提醒…」，
> 且 NC 规则链的输入是 `cert_extraction_result` 而非 `NormalizedPath`
> ⇒ **本册 ⛔ 不做「上传到 NC」**。线框图里保留该复选框是为了标明「已识别需求，一期不做」，
