# 48 · 锚点数据源与操作参数模型 V1

> **状态**：待审批｜**日期**：2026-10-05｜**承接**：`41`（交互重构 V3）/ `42`（通路职责边界）/ `43`（来源链执行器）/ `22`（填写单元属性模型）
> **本文档要解决的问题**：把用户 2026-10-05 给出的心智模型——**「一个锚点对应两个东西：一个数据源，一个操作」**——固化为可实现的参数模型与页面结构。

---

## 〇、一句话结论

**锚点 = 数据源 × 操作**（两个正交维度）。

- **数据源**（值从哪来）= **全局参数** + **三类 AI** + **人工待办（兜底，非并列）**。
- **操作**（值怎么写回去）= 分类轴是**定位方式**（模板标记 vs 坐标），Word 四类 / Excel 两类，**参数由 `FileKind` 自动分派**。
- **界面** = **配置页面** 与 **测试页面** 分离；测试页一键试填 → 预览填好的文档 → 关闭回到编辑页。

---

## 一、模型

```
              ┌────────── 数据源 · 值从哪来 ──────────┐
              │  全局参数    AI 自动生成   AI 字段   AI 表格  │
              └────────────────────┬───────────────────┘
                              ┌────┴────┐
                              │  锚点    │
                              │{{ENT_NAME}}│
                              └────┬────┘
              ┌────────────────────┴───────────────────┐
              │  操作 · 值怎么写回去（按 word/excel 分派参数）│
              │   替换   单元格赋值   表格生成   页眉替换   │
              └────────────────────────────────────────┘
```

**两个维度互相独立**：同一个「全局参数」数据源，既可以走「替换」也可以走「单元格赋值」；同一个「AI 字段」数据源，在 Word 和 Excel 下的操作参数也不同。

> ⚠️ **`人工待办` 不在「数据源」这一层**（见 §2.4）—— 它不产值。上图未列出它，是刻意的。

## 二、数据源（值从哪来）

### 2.1 全局参数

**最简单的来源**：从全局参数里**选一个字段**即可。

| 项 | 内容 |
|---|---|
| 配置项 | `param_code`（参数编码，下拉选） |
| 取值 | `SrcGlobalParamSkill` 按「标准 / 阶段 / 机构」**取最特异一条**，经 `ParamValueResolver.Resolve` 决策 |
| 零 LLM | ✅ 不调模型，确定性取值 |
| 现状 | ✅ **已实现且参数齐** |

### 2.2 三类 AI —— 统一参数结构

**★★★ 核心结论：三类 AI 共用同一套参数结构，都是 3 个信息。**

| # | 信息 | 形态 | 语义 |
|---|---|---|---|
| ① | **是否带参数** | 开关 + 多选 | 勾选 ⇒ **从全局参数中获取**若干字段，作为 AI 的参考素材 |
| ② | **是否关联文档** | 开关 | 勾选 ⇒ 检索**企业 markdown** 做语义分析 |
| ③ | **提示词** | 文本 / 提示词编码 | 告诉 AI 怎么生成 |

**★ 用户原话（决定 ① ② 的价值）**：

> 「很多 ai 通过**参数的某个字段**，就可以分析出来，**不再需要针对企业的 markdown 进行语义分析了**」

⇒ ①② 是两个**独立**开关，组合出四种模式：

| ① 带参数 | ② 关联文档 | 模式 | 成本 | 典型场景 |
|---|---|---|---|---|
| 否 | 否 | 纯提示词生成 | 最低 | 套话、模板化表述 |
| **有** | **否** | **参数驱动**（★ 用户强调的主力模式） | 低 | 「按经营范围推导认证范围」 |
| 否 | 有 | 纯文档检索 | 高 | 「从企业资料里找证据」 |
| 有 | 有 | 参数 + 文档 | 最高 | 复杂判断 |

> **建议默认值**：② **默认不勾**（用户说「很多 AI 通过参数就能分析出来」），把「关联文档」作为**显式的成本开关**。

**三类 AI 的分工**（⚠️ 命名与边界见 §六 待确认）：

| 类 | 产出 | 素材 | 对应实现 |
|---|---|---|---|
| **AI 自动生成** | 一段内容 | 全局参数参考 + **本段语义**（上下文，自动带） | 近 `src_semantic` |
| **AI 字段** | 一个值 | **某段文字** / 一个全局参数 + 提示词 | 近 `src_ai_field` |
| **AI 表格** | 二维表（多行） | 列定义（模板扫描带出）+ ① ② ③ | `src_ai_table` ✅ |

**三类共有的「自动带入」项**（⛔ 不需要用户配）：

- **本段语义 / 上下文** —— 锚点所在段落原文（⚠️ 现状：**被采集但被丢弃**，见 §五 G3）
- **列定义** —— 表格类专用，由扫描器从模板样板行扫出（`{{col:FieldCode}}`）

### 2.3 「AI 表格」与「签名」

用户表述：「AI 表格，**和签名一样**」。

⇒ 两者应是**并列的独立类型**（不是从字段下拉里选）。⚠️ 「签名」的形态仍未定（见 §六）。

### 2.4 人工待办（兜底项，**不并列**）

| 项 | 内容 |
|---|---|
| 实现 | `src_manual` |
| 产出 | ⛔ **不产值**，只产 `FillTodo{AnchorCode, Hint}` |
| 关键行为 | 返回 **`hit=false`** ⇒ 让 `firstHit` **继续往下找** |
| 落点 | 只有**全部来源落空**时，编排器才把 `Todos` 转成 `OfficeFillReport.Pendings` |

**★ 它的唯一增量价值 = 那句 `Hint` 提示语。**

> 若某锚点**不配任何来源**，结果同样是进 `Pendings`（理由写成「未提供值」）。
> ⇒ 它**不在「数据源」这一层**，正确落位是**来源链最末尾的兜底项**。

**建议**：实现保留（已上线，删是负工作量），但**界面上不把它列成一个数据源选项**。

## 三、操作（值怎么写回去）

### 3.1 分类轴 = 定位方式

**★★ 这是本轮最重要的澄清。** Word 的四类操作，本质区别**不是机制，而是「靠什么找到位置」**：

| 定位方式 | 模板要不要预先标记 | 扫描器能否扫到 |
|---|---|---|
| **模板标记 `{{}}`** | 要 | ✅ 能 ⇒ 页面能自动列出 |
| **坐标（表 / 行 / 列）** | **不要** | ❌ **不能** ⇒ 必须**人工建锚点** |

> 用户第六轮贴的 `table.SetText(0, 2, projectinfo.Id)` 就是**坐标**这一路 ——
> 房产测绘模板的格子固定，**模板里根本没写标记**，所以只能硬编码坐标。

### 3.2 Word 四类

| # | 操作 | 定位方式 | 现状 |
|---|---|---|---|
| 1 | **替换** | 模板标记 `{{}}` | ✅ `WordParagraphFiller`（正文段落 / 表格单元格内 / 页眉，**已解决 token 跨 run**） |
| 2 | **单元格赋值** | 坐标（第几个表 / 第几行 / 第几列） | ❌ **缺**（`OfficeRegionKind` 无 `WordCell`） |
| 3 | **表格生成** | 标记 `{{table:Tag}}` + 克隆补行 | ✅ `WordTableRegionFiller` |
| 4 | **页眉替换** | 页眉段落内的标记 | ✅ 已有 |

**★ 关于第 4 类「页面操作」的定论（用户本轮明确）**：

> 「页面操作，我们**只是针对 word 的页眉进行替换**，因为企业的文档很多带有复杂的页眉，
> 页眉中最重要的替换**企业名称或认证阶段**等信息」

⇒ **「页面操作」= 仅 Word 页眉替换**，⛔ 不包含页脚（`FillLocationKind.Footer` 维持弃用）、不含页码 / 水印 / 页面设置。

⚠️ **页眉的特殊性**：企业文档的页眉常常**很复杂**（表格、logo、多段落），且**页眉里的同名 token 与正文里的会冲突**（`uk_tpl_anchor` 7 列含 `HeaderKind`，但正文/页眉同名 token 只能存一条）。⇒ 这正是 §五 G4 的落地场景。

### 3.3 Excel 两类

| # | 操作 | 定位方式 | 现状 |
|---|---|---|---|
| 1 | **单元格赋值** | 坐标 `Sheet1!B3` | ✅ `ExcelCellWriter` + 扫描天然带坐标 |
| 2 | **表格填充** | 起始行列 + 二维数据 | ✅ `ExcelRegionFiller` |

> ✅ **Excel 侧用户说的两项，现有实现全覆盖** —— 印证了用户「excel 先天好办」的判断。

### 3.4 参数由 `FileKind` 自动分派

用户原话：

> 「系统**自动根据我们的类型是 word 还是 excel**，自动生成对应的参数，
> 但有些参数如果是我们**扫描自动带过来的**，也直接将参数带到我们的操作中，
> **不同的操作方式，对应的不同的参数设置页面**」

⇒ 三条规则：

1. **同一操作，参数面板按 `FileKind` 切换** —— 「单元格赋值」在 Word 下显示「表 / 行 / 列」，在 Excel 下显示「Sheet / Cell」。
2. **扫描带出的参数自动带入** —— `AnchorRef`（`Sheet1!B3` / token）+ **扫描侧的行列号 / 段落号**（⚠️ 现状：Word 扫描器**不算行列**，见 §五 G2）。
3. **操作方式决定参数面板** —— 操作是**判别式**（discriminated union），选哪个显示哪组参数。

> 这是 `FillTableSkill` 已有范式（「**对外统一签名，对内按 `FileKind` 分派**」，`39` §11.3）的推广。

## 四、两个界面

### 4.1 配置页面

**职责**：配「数据源」+「操作」。**不做**实时预览模拟。

```
┌─────────────┬─────────────────────┬──────────────────────┐
│  左树        │   中栏：文档预览      │  右栏：锚点配置       │
│  标准资料清单 │   （空白模板 / 原件）  │  ┌────────────────┐  │
│             │                     │  │ 数据源          │  │
│             │                     │  │ ○全局参数       │  │
│             │                     │  │ ○AI 自动生成    │  │
│             │                     │  │ ○AI 字段        │  │
│             │                     │  │ ○AI 表格        │  │
│             │                     │  ├────────────────┤  │
│             │                     │  │ 操作            │  │
│             │                     │  │ ○替换 ○单元格    │  │
│             │                     │  │ ○表格 ○页眉替换  │  │
│             │                     │  └────────────────┘  │
└─────────────┴─────────────────────┴──────────────────────┘
                          [ 测试 ] ← 进入测试页面
```

### 4.2 测试页面

**职责**：验证配置对不对。用户原话：

> 「将**配置页面和测试页面分开**，在测试页面的时候，可以**一键自动填入信息**，
> 并生成**填写完成的内容后的预览**，**关闭预览，又回到了编辑页面**，
> 这样，操作者就能直观的检查我配置的信息是否有问题了」

**两条判据**（用户明确）：

| # | 判据 | 底座支撑 | 现状 |
|---|---|---|---|
| 1 | **是否还存在 `{{}}` 没有被覆盖到** | `OfficeFillReport.LeftoverTokens` + `Verified` | ✅ **已有** |
| 2 | **我们自己填写的信息，位置是否正确** | `OfficeFillHit.Location`（`正文·第 12 段` / `表格[1] 行 2 列 3` / `Sheet1!B7`） | ✅ **已有**（但 Word 行列号不准，见 G2） |

**试填机制**：

```
合成假 FillContext（随机文字，按锚点 ValueType 生成）
        ↓
装配 OfficeFillRequest（Values + Regions）
        ↓
WordFillWriter.Fill / ExcelFillWriter.Fill   ← ★ 纯内存，天然不落盘
        ↓
OfficeFillReport（Hits / Pendings / Regions / LeftoverTokens）
        ↓
转 PDF 预览 → 操作者肉眼检查 → 关闭 → 回到编辑页
```

**三条硬约束**：

1. ★ **必须 `KeepUnresolvedAsIs = true`** —— 默认 `false` 会把未命中的锚点**直接抹掉**，试填产物就丢了锚点，判据 ① 失效。
2. ★ **随机文字必须「看得出是哪个锚点填的」** —— 建议 `〔锚点键〕+ 随机串`（如 `〔ENT_NAME〕Xk3f9`），纯随机串无法归因。
3. ⚠️ **预览需要一次格式转换**（`.docx` → `.pdf`）—— 存在延迟，需异步或复用产物缓存（`PathBuilder.Product(src, pdf, '.pdf')`）。

**能暴露的错误分三类**：

| 错误 | 信号 | 现状 |
|---|---|---|
| 锚点对不上（模板 token ≠ 规则锚点） | `Pendings[].Reason = "未提供值"` | ✅ 能报 |
| 位置不存在（表格标签写错） | `Regions[].Matched = false` + `Message` | ✅ 能报 |
| **位置越界（行 / 列号超范围）** | —— | ❌ **报不出来**（见 §五 G1） |

### 4.3 交互：关闭预览回到编辑页

⇒ 测试**不是独立路由**，而是**从配置页发起的可返回的浮层**（复用刚建好的 `YzhDrawer`，全屏尺寸）。

### ★ 实施中定下的两条语义（已写进代码注释）

**① 「坐标定位」与「区域填充」的越界语义** —— 这是本轮最重要的设计判断：

| | 定位方式 | 行不足 | 目标不存在 |
|---|---|---|---|
| `WordTable` / `ExcelRange` | 标签 / 起点 + **数据驱动** | **克隆补行**（设计） | 留空 / 新建 |
| **`WordCell`** | **坐标 + 人工指定** | ⛔ **不克隆** | **报 Warning** |

> 若坐标写大了也克隆一行，用户会看到「填成功了」，值却落在**模板里本来没有的行**上 ——
> 打印出来才发现表格多了一行。这类缺陷**在报告里完全看不出来**，
> 正是「试填验证」要消灭的东西。

**② `NumberFormat` 的方言是含糊的，一期不拆字段**：
Excel 侧把它当 **Excel 格式串**喂给 `DataFormat`，Word 侧当 **.NET 格式串**喂给 `ToString`。
两者在常用形态（`#,##0.00` / `yyyy-MM-dd`）上高度重合；遇到 `[$-409]` 这类
Excel 专有写法时**回退到不带格式**，⛔ 不让一个格式串把整份文档的填充炸掉。

### ⏸ 尚未接线：坐标能力还没有「规则 → 区域」的装配路径

`OfficeRegionKind.WordCell` **已可用**，但**没有任何 Skill 产出它** ——
`fill_cell` 产出的是 `Values`（锚点值字典），`fill_table` 产出的是 `WordTable` / `ExcelRange`。
⇒ **D-Z1（人工坐标填在哪）裁决后**，才决定是「给 `fill_cell` 加坐标参数」还是「新增一个区域装配分支」。
**在此之前，坐标能力只能由编排器直接构造 `OfficeFillRegion` 使用。**
