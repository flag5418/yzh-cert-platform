# 认证准备与认证检查 · 业务设计 V3

> 版本：V3.1（2026-11-02 晚 · **含实施回写**）
> 取代：`47-认证准备与认证检查-业务设计-V2.md`
> 本版**改变的是重心，不是推翻 V2 的业务结论**。V2 把「业务流程」讲清了；V3 把「这套系统靠什么产出结果」讲清。
>
> **为什么必须改重心**：V2 花了大量篇幅在角色、权限、菜单、页面版式上，而这些**都不是这个项目的心脏**。心脏是：
> **条款模型 + 文档模型 + 提示词，三者能不能串起来，产出专家认可的检查证据和 NC 疑点。**
> 这件事没做成，权限做得再细也没有意义。
>
> **V3.1 与 V3 的差别**：V3 是「诊断书」，V3.1 是「诊断 + 手术记录」。
> 用户补充了文档模型的真实结构（按条款切片 + 条款号），据此把装配层实现出来并跑通两个分支。
> **初稿有三处判断被实测推翻，已在正文标注「⚠️ 修正」**，不藏着：
> 1. 文档模型的主力不是「文件画像 + 字段抽取」，而是 **`cert_document_extraction`（按条款切片）**；
> 2. 「文件 → 证据自动生成」**不需要建**，切片本身就是原始证据；
> 3. `Artifacts` / `EvidenceChain` 是 **`prompt` 类型**，不是 JSON，⛔ 不能反序列化。

## 〇 · 首要规则（总原则）

> 这一章是本项目一切设计的**最高约束**。后面任何章节与之冲突，以本章为准。

### 0.1 系统是辅助，不是裁判

这套系统**不替审核员做判断**。它做三件事：

1. **不漏**：把条款约定的要求，一条不落地摊到审核员面前
2. **有据**：每条结论都指得回具体条款、具体文件、具体位置
3. **可复核**：系统给的每一条，审核员都能改、能删、能推翻

所以：

- **不做强制约束**。证据不足是**提示**，不是**拦截**；资料缺失是**标注**，不是**阻断**。
- **不做流程卡点**。审核员想跳过、想重跑、想手工改，都允许。
- **不追求自动化替代**。系统跑完，活还是审核员的；系统只是让他快、让他全。

判定标准很简单：**如果一个设计让审核员「做不了他想做的事」，这个设计就是错的。**

### 0.2 本阶段只有一个目标

> **把「条款模型 → 文档模型 → 提示词 → LLM → 检查证据 + NC 疑点」这条链跑通，并让专家认可输出质量。**

这条链是项目存在的理由。它跑通了，系统才有价值；它跑不通，其他一切都是装修。

因此本阶段的验收标准**不是**「功能齐了」，而是：

| 验收项 | 判据 |
|---|---|
| 链路通 | 给一个真实企业 + 一个真实条款，能从空库跑到「有检查证据、有 NC 疑点」落库 |
| 证据可追 | 每条检查证据能点开看到：引用了哪个文件、哪一段、依据哪条条款属性 |
| 专家认可 | 专家看 10 条输出，**至少 8 条认可**（认可 = 结论方向对 + 依据引对了） |
| 可复现 | 同一输入跑两次，**结论完全一致**（理由措辞可变，结论不可变） |
| 可推翻 | 审核员能直接改任何一条，不需要走审批 |

### 0.3 权限与精细化控制：本阶段全部忽略

> 用户原话：「我们是辅助系统，不做强制约束，即使当前的权限控制都是下一步的问题……只有我们推理的检查证据和 NC 疑点能得到专家的认可后，才开始做真正的权限控制，其他的精细化控制都是下一步的问题。」

**本期明确不做**（不是"以后再说"，是**现在明确写下来避免再被讨论**）：

- ❌ 角色权限矩阵（谁能看哪个按钮、哪个字段）
- ❌ 审核组长 / 审核员的字段级权限差异
- ❌ 企业端账号、企业提交证据
- ❌ 多机构隔离、数据行级权限
- ❌ 审批流、签署流、会签
- ❌ 手机端（数据结构留口，功能不做）
- ❌ 报告的版式与导出（二期）
- ❌ 消息通知、待办、站内信

**唯一保留的一条底线**：`OrgCode` 字段继续写、继续按机构过滤查询。这不是权限设计，这是**数据不能串**的基本要求，成本为零，顺手做了。

### 0.4 冲突时的判定优先级

当两条设计意见打架，按这个顺序裁决：

```
① 能不能产出专家认可的检查证据 / NC 疑点？   ← 最高
② 会不会让审核员做不了他想做的事？
③ 会不会让结论不可复现？
④ 实现成本
⑤ 权限、版式、交互美观                      ← 最低
```

任何在 ⑤ 上的争论，**本期直接搁置**。

## 一 · 一句话

> **这套系统不是替审核员做判断，是让审核员不漏判。**

展开一点：

> 审核员拿着一个标准、一家企业、一堆资料，要在有限时间里判断「这家企业符不符合」。
> 难点不是他不会判，是**条款太多记不全、资料太多看不完、部门太多不知道找谁**。
> 系统把条款拆成结构化属性，把资料拆成结构化字段，用提示词把两者对上，
> 让 AI 先说「我看到什么」，再由规则算「这算什么」，最后审核员拍板「是不是这样」。

### 1.1 术语表（先说清词，后面才好讲）

| 词 | 指什么 | 落在哪张表 |
|---|---|---|
| **认证计划** | 一个企业 + 一个标准 + 一段时间的一次认证活动 | `cert_audit_plan` |
| **检查项** | 计划里的一行，含「多条款 + 可空部门」 | `cert_audit_plan_detail` |
| **入场检查项** | 检查项下面的一条具体动作：「去哪、查什么、怎么查」 | `cert_onsite_plan_item`（新建） |
| **条款** | 标准里的一条要求（如 8.3） | `cert_clause` / `cert_clause_attr` |
| **条款属性** | 条款的 9 类结构化拆解 | `cert_clause_attr` |
| **文件画像** | 「这个文件是什么、该关注什么」 | `cert_enterprise_doc_profile` |
| **按条款切片** | 「这个文件在**这条条款**上说了什么」（装配读的就是它） | `cert_document_extraction` |
| **字段抽取** | 「这个文件里那个值是多少」 | `cert_extraction_result` |
| **证据** | 审核员挂上来的原始材料（文件/录音/照片/文字） | `cert_evidence` |
| **检查证据** | 系统推理出来的、带条款依据的结论条目 | `cert_check_result` |
| **NC 疑点** | 系统怀疑不符合、但等审核员确认的条目 | `cert_check_result.NcSuggested` |
| **NC** | 审核员正式签发的不符合项 | `cert_nc` |
| **分析** | 一次 LLM 调用 + 装配 + 落库的完整记录 | `cert_check_analysis` |
| **准备态** | 资料够不够（五态） | `cert_check_result.PrepState` |
| **结论** | 符不符合（四态） | `cert_check_result.Conclusion` |
| **锁定** | 人确认过的，机器不许再动 | `cert_check_item.IsLocked` / `cert_check_result.IsLocked` |

**注意区分三个容易混的词**：

```
证据 (cert_evidence)        审核员给的原始材料
   ↓ AI 推理
检查证据 (cert_check_result) 带条款依据的结论
   ↓ 审核员确认
NC (cert_nc)                正式签发的不符合项
```

**「NC 疑点」不是 NC**。它只是「系统觉得这儿可能有问题」，还没有任何法律效力。

## 二 · 三个模型（资产盘点：谁有货，谁没跑过）

这一章是全文的事实基础。**所有数字都是 2026-11-02 从 `yzh_cert_platform` 库实测的**，不是估计。

### 2.1 模型一：条款模型 `cert_clause_attr` + `cert_clause_attr_def`

**是什么**：把一个标准里每条条款的「文字」拆成 9 类可计算的属性。这是系统的**知识底座**。

**结构：长表，不是宽表。** 一行 = 「某条款上的某个属性」（`ClauseCode` + `AttrCode` + `AttrValue`），
不是「一条款一行的 9 列」。装配时必须**按 `ClauseCode` 分组**成字典。

**有多少**（2026-11-02 实测）：

| 标准 | 行数 | 条款数 | 属性种类 |
|---|---|---|---|
| iso13485 | 603 | 67 | 9 |
| iso14001 | 40 | 5 | 8 |
| iso9001 | 40 | 5 | 8 |
| **合计** | **683** | **77** | 9 |

> ⚠️ 修正：初稿写的「每条款 77 条」是误读。真实口径是 **77 条条款 × 9 类属性 = 683 行**。

**9 类属性及其真实形态**：

| 属性 | `ValueType` | 实测取值 | 平均长度 | 装配时怎么用 |
|---|---|---|---|---|
| `ClauseIntent` | `text` | 自然语言，如「明确组织内质量相关职责与权限的分配、文件化和沟通机制」 | 82 | **直接进提示词**（告诉 AI 这条到底管什么） |
| `Obligation` | `dict` | **全是 `shall`**（77/77） | 5 | 当前零信息量；设计意图是「≠shall 只出观察项」的闸门 |
| `Applicability` | `dict` | `general`(53) / `conditional`(24) | 8 | 进提示词；`na` 只能人给 |
| `ApplicabilityCondition` | `text` | 条件原文 | 22 | conditional 条款才写 |
| `Severity` | `dict` | **`major`(61) / `critical`(16)**，无 `minor` | 6 | 作 `SeverityBaseline` |
| `DocCheckMode` | `dict` | `required`(50) / `optional`(17) | 8 | **决定要不要拿企业资料核对**；`none` 的条款不进资料核对 |
| `Process` | `json` | `["management"]` / `["production","inspection"]` | 25 | **条款 → 部门**的桥（人工确认映射） |
| `Artifacts` | **`prompt`** | 提示词正文 + 预生成结果 | **521** | 进提示词，告诉 AI「该条款要求企业提供哪些资料」 |
| `EvidenceChain` | **`prompt`** | 提示词正文 + 预生成结果 | **523** | 进提示词，告诉 AI「该条款该怎么取证」 |

#### ⚠️ 三个必须知道的实情

**① `Artifacts` / `EvidenceChain` 是 `prompt` 类型，不是 JSON。**

`cert_clause_attr_def.ValueType` 明写 `prompt`，`PromptTypes.cs` 的注释也写明：

> 「⚠️ 输出里的 `Artifacts` / `EvidenceChain` 是**提示词正文**（不是结论），
> 因为这两条属性在 L1 的值类型就是 `prompt`。」

实测值长这样（一条 500+ 字）：

```
只输出 JSON 数组，不要任何解释文字。数组每个 element 包含：Kind、Name、Purpose。
在企业提交的组织架构图、岗位说明书、职责权限分配表…中，
查找是否规定了从事质量相关工作的人员的职责、权限及相互关系…
```

所以：**⛔ 不要试图 `JsonSerializer.Deserialize` 它们**；**⛔ 也不要以为它们没用**。
它们本身就是「针对这条条款的取证指引」，**原样拼进提示词即可** —— 这正是价值所在。

**② `Obligation` 目前 77 条全是 `shall`**，等于没有区分度。设计意图（字典
`clause_obligation` 的 `Remark`）是「判定闸门：≠shall 只出观察项」，但数据没体现出来。
**不影响链路，先记着**。

**③ `Severity` 只有 `major` / `critical`，没有 `minor`。**
所以「一般不符合」的严重度只能由 AI 或审核员给，条款基线给不出来。

#### `Process` 为什么是「条款 → 部门」的桥

`Process` 给的是**过程码**（`management` / `production` / `inspection` / `purchase` / `design` /
`warehouse` / `sales` / `after_sales` / `hr`），**不是部门名**。

用户原话：「由**专家根据条款，还有对企业组织机构的理解，提前定义了过程和部门的对应，这个属于手动操作**。」

所以链路是：`条款 --Process--> 过程码 --专家手工映射--> 企业部门`。中间那一跳**系统不猜**。

⚠️ **`process_domain` 字典未配置**（`Sys_DictionaryList` 里查无此类型），
所以提示词里看到的是 `["management"]` 这样的原始码，不是中文。**不影响链路，先记着**。

### 2.2 模型二：文档模型（三层，**按条款切片的才是主层**）

**是什么**：把企业交上来的资料，从「一堆文件」变成「**按条款可查询的结构**」。

> ⚠️ **V3 初稿在这里写错了一层**。初稿以为「文件级画像 + 字段级抽取」就是全部，
> 于是把「条款 ↔ 文档」的关联当成待建能力。**实际上第三层早就存在，而且就是为这件事建的。**
> 用户 2026-11-02 原话：「每个文档都按标准，按每个条款的适应性提取了每个条款的关键信息和对应条款号」——
> 说的就是 `cert_document_extraction`。

#### ★ 主层 · 按条款切片 `cert_document_extraction`（14 行）

**回答「这个文件在**这条条款**上说了什么」——这是装配真正要读的一层。**

粒度：**文档 × 标准 = 一行**（同一份《质量手册》对 iso9001 与 iso13485 各跑一次）。

| 字段 | 内容 | 为什么关键 |
|---|---|---|
| `FileCode` | → `cert_enterprise_doc.Code` | 指回原文件 |
| `StandardCode` | 标准 **GUID** | **条款号在不同标准里会撞车**（4.1 在 iso9001/iso13485 都有），⛔ 必须按标准隔离 |
| `EnterpriseCode` | 企业 Code（冗余） | 免 join 直接过滤 |
| `ClauseNumbers` | `1,4.1,4.2.2,5.5.1,...` 逗号串 | **匹配键**。查用 `FIND_IN_SET`，⛔ 不能用 `LIKE '%4.1%'`（会误中 4.15） |
| `ContentJson` | `{DocMeta, Clauses[]}` | 见下 |
| `ClauseCount` | 切片条数 | 快速判断产出量 |
| `ExtractStatus` | `done` / `failed` / `skipped` | ⛔ 只取 `done` |
| `IsStale` | 文档被替换后置 1 | 装配时告警「内容可能已过期」 |

`ContentJson` 的结构（实测样本）：

```json
{
  "DocMeta": {"FileName": "01-外部因素识别监视评价总清单.docx", "StandardCode": "iso13485", "Chunks": 1},
  "Clauses": [
    {"ClauseNumber": "4.1", "Title": "总要求",
     "Anchor": "按组织环境与相关方需求期望控制程序执行…",
     "Excerpts": ["按组织环境与相关方需求期望控制程序执行…"],
     "Confidence": 0.85}
  ]
}
```

**`Excerpts` 就是「原始证据」**——原文摘录 + 位置 + 置信度，**不含结论**（实体注释原话：
「★ 铁律：只产『读到什么』，⛔ 不产结论。找不到就交空，⛔ 禁推测」）。

#### 支撑层 · 文件级画像 `cert_enterprise_doc_profile`（178 行）

**回答「这个文件是什么、审核员该关注什么」**。用途是**给人看的**与**做召回/归类**的，
不是逐条款装配的主力（`DocPurpose` 平均 1200 字 × 119 份 = 14 万字，整批塞进提示词不可行）。

| 字段 | 内容示例 | 用途 |
|---|---|---|
| `DocPurpose` | `【是什么】…【审核关注点】…【来源口径】…【包含信息】…` | 审核员看「这文件该关注什么」 |
| `InfoItemsJson` | `[{"isKey":true,"itemName":"...","itemDesc":"..."}]` | 声明文件里有哪些信息项 |
| `TagsJson` | `[{"tagCode":"ManualQuality","tagName":"质量手册","confidence":0.98}]` | 归类、召回 |
| `ProfileStatus` | `completed` | 画像是否已生成 |

#### 辅助层 · 字段级抽取 `cert_extraction_result`（31 行）

**回答「这个文件里，那个具体信息是什么」**（文件编号 / 版号 / 生效日期 / 页码 / 目的 / 范围 / 职责）。

**三层为什么都要**：装配读主层（按条款切片）；画像层给审核员看「这份文件是什么」；
字段层查「版号受不受控」这类**跨条款的文件级属性**。缺主层，AI 只能猜；缺另两层，人看不懂。

#### ⚠️ 覆盖率现状（2026-11-02 实测）

| 项 | 数 |
|---|---|
| 企业文档画像 | 119 份（企业 `26d6dff4…`） |
| 已产出**按条款切片**的文档 | **7 份**（其中 2 份切片为 0） |

**结论**：装配链路已经通了，但**只有 7 份文档喂得进推理**。要让专家认可输出质量，
先把剩下 112 份的「按标准提取条款」跑完 —— 这是数据活，不是代码活。

### 2.3 模型三：提示词（三层，各有分工）

**是什么**：把「条款」和「文档」喂给 LLM 的**装配说明书**。

这三层不是重复，是三个不同的抽象层级：

#### 第一层 · 业务提示词 `wf_prompt_template`（10 条）

平台/标准级，按 `PromptType` 分工：

| `PromptCode` | 名称 | 长度 | 现状 |
|---|---|---|---|
| `audit_prep` | 认证准备 · 资料完备性分析 | 1478 | ✅ **M3 已跑通真实数据** |
| `audit_check` | 认证检查符合性分析 | 398 | ⚠️ 有模板，未跑过真实数据 |
| `evidence_link` | 证据关联度分析 | 315 | ⚠️ 有模板，未接入 |
| `nc_suggest` | NC 不符合项描述生成 | 399 | ⚠️ 有模板，未接入 |
| `clause_attr_v2` | 条款属性预生成 | 7524 | ✅ 已产出 683 行属性 |
| `doc_content_*` | 文档作用提示词 | 5390 | ✅ 已产出 178 行画像 |
| `doc_group_*` | 文档分类提示词 | 5248 | ✅ 已用 |
| `prompt_generator` | 元提示词（生成提示词用） | 4637 | 工具 |

#### 第二层 · 判定提示词 `cert_nc_judge_prompt` + `cert_nc_conclude_prompt`（各 1 条）

这两张表是**独立**的，因为它们的职责根本不同：

| 表 | `PromptCode` | Temperature | MaxTokens | 职责 |
|---|---|---|---|---|
| `cert_nc_judge_prompt` | `nc_judge` | **0.10** | 2000 | **逐维度提取事实**，输出 `dimensions[]` |
| `cert_nc_conclude_prompt` | `nc_conclude` | **0.20** | 500 | **只写一句话理由**，不许改结论 |

`nc_judge` 的 SystemPrompt 已经把护栏写死了：

> 「你只依据材料判断，材料不足时必须如实报告，**严禁推测、严禁编造**、严禁输出判定依据中没有的内容。」

`nc_conclude` 的 UserTemplate 更狠：

> 「【已判定结论】（★由系统确定，不得更改）……★ 不得改变结论等级 ★ 不得添加「依据维度」中未列出的维度」

**这是整个架构最重要的一条设计**：结论由代码算，AI 只负责把代码算出的结论翻译成人话。见 3.6。

### 2.5 三个模型之间的三条人工连接（系统不猜）

三个模型能自动串，但有**三件事系统不许自己判**，必须人给。这三条是「辅助系统」定位的具体体现。

#### 连接一：条款 → 部门（专家手工定义）

用户原话：

> 「我们建立计划的时候，其实是由**专家根据条款，还有对企业组织机构的理解，提前定义了过程和部门的对应，这个属于手动操作**。」

所以：

- `cert_clause_attr.Process` 给了「这条条款属于哪个过程」（如 `["management"]`）
- 但「这个过程对应企业的哪个部门」是**人填的**
- 系统**不做**「根据企业组织架构自动匹配部门」的猜测

**为什么**：部门名千差万别（「总经办」和「综合管理部」可能都是 management 过程）。猜错一次，审核员就要重排一次计划，成本比手工填高得多。

#### 连接二：条款是否适用（专家独立判）

用户原话：

> 「所谓不适用是在认证准备阶段，判断也是**专家独立觉得的，系统不参与判断**。」

所以：

- `Applicability = general`（53 条）/ `conditional`（24 条）只是**提示**
- `na` 这个结论**只能人给**
- AI 输出 `na` 时，界面上要标「AI 建议不适用，待确认」，不能直接生效

**为什么**：不适用判错，等于漏审一条条款。这是认证风险最高的错误类型。

#### 连接三：能不能不去现场（专家判，系统只给事实）

用户原话：

> 「有些检查项是不用去现场就能判断的，比如企业的资料是否齐全，企业的内审材料是否完整，企业是否有失信等。」

系统给**事实**，人给**决定**：

| 系统给 | 人给 |
|---|---|
| `verify_level`（AI 判「这条查文件就行」还是「得去现场」） | 最终是否安排现场 |
| `missing_kinds`（缺什么资料） | 缺的这个资料，能不能远程补 |
| `conflicts`（文档矛盾） | 矛盾要不要现场核 |

**所以 `verify_level` 是「建议」不是「命令」**。审核员可以把 `doc` 改成 `onsite`，也可以把 `onsite` 改成 `remote`，系统不拦。

#### 三条连接的共同点

```
系统：把事实摆清楚（这条属于什么过程、适不适用、需要什么证据、查到什么程度）
人：  做决定（去哪个部门、适不适用、去不去现场）
```

**系统永远只做前半句。**

### 3.2 第一跳：条款 → 检查什么

**输入**：检查项（`cert_audit_plan_detail` 一行，可能挂多条条款）

**动作**：取该检查项下所有条款的 `EvidenceChain`

**输出**：一组「检查动作」

```
条款 8.3 → EvidenceChain:
  {Kind: site,      Action: 看, Target: 危化品仓库警示标识, Sample: 抽查3个区域, Finding: 标识齐全有效}
  {Kind: record,    Action: 查, Target: 危险源识别台账,     Sample: 最近12个月, Finding: 有更新记录}
  {Kind: interview, Action: 问, Target: 仓库管理员,         Sample: 2人,        Finding: 知道应急处置流程}
```

**这一跳的价值**：审核员不用自己想「这条条款该看什么」。系统告诉他了，而且告诉他抽样多少、该发现什么。

**这一跳现在的状态**：✅ **已接通**（2026-11-02）。`CertCheckContextBuilder` 把 `ClauseIntent` /
`EvidenceChain` / `Artifacts` / `Severity` / `Applicability` / `Process` 全部拼进条款块。
⚠️ 但 `EvidenceChain` 的实际值是「提示词 + 预生成结果」的混合文本，不是结构化 JSON —— 原样拼入即可，⛔ 别解析。

### 3.3 第二跳：企业有什么（★ 按条款取，不是按文件取）

**输入**：企业编码 + 标准 GUID + 检查项的条款清单

**动作**：**按条款号**取「企业在这条条款上说了什么」

> ⚠️ **V3 初稿在这里想错了**。初稿写「两条路径必须合流：文件画像 + 字段抽取」，
> 隐含假设是「先按文件找，再找条款」。**实际口径正好相反**：文档早就按条款切好片了。

| 路径 | 来源 | 取什么 | 状态 |
|---|---|---|---|
| **主路径** | `cert_document_extraction` | 按 `ClauseNumbers` 过滤 → `ContentJson.Clauses[]` 里该条款的 `Excerpts` | ✅ 已接入 |
| 辅助 · 文件画像 | `cert_enterprise_doc_profile` | `DocPurpose`（这文件是什么、该关注什么） | 供**人**看；不逐条款装配 |
| 辅助 · 字段抽取 | `cert_extraction_result` | `FieldName` + `ExtractedValue`（版号/生效日期等文件级属性） | 供「文件受不受控」这类判断 |

**为什么主路径是切片而不是画像**：画像 `DocPurpose` 平均 1200 字 × 119 份 = 14 万字，
整批塞进提示词不可行；而切片是**按条款切好的 3–5 段原文**，一个检查项只取 2–4 条，
信息量天然有界。用户原话：**「一个检查项需要的信息是有限的」**。

**这一跳现在的状态**：✅ 已接通。实测一次装配 `doc_hit_count = 1`、`excerpt_count = 1`。
⚠️ **但覆盖率是瓶颈**：119 份文档里只有 7 份产出过切片（见 2.2 末尾）。

### 3.4 第三跳：装配（★ 已实现，2026-11-02）

**代码位置**：`CertPlatform.Auditor/Services/Expert/CertCheckContextBuilder.cs`（新建，约 560 行）

**取数口径**（用户 2026-11-02 确认，这是实现的唯一依据）：

```
检查项（cert_audit_plan_detail）
  └─ Clauses：多个条款 Code（GUID 逗号串）
       ├─ cert_iso_clause          → 条款编号 / 标题 / 原文
       ├─ cert_clause_attr         → 9 类属性（长表按 ClauseCode 分组）
       └─ 条款编号 + 标准 GUID
            └─ cert_document_extraction
                 └─ ContentJson.Clauses[] → 只取该条款的 Excerpts
                      └─ 按条款聚合 → 原始证据
```

**为什么要按条款号过滤，而不是整份文件塞进去**：

一份《管理手册》提取出 29 条切片、1.7 万字，而一个检查项只关心其中 2–4 条。
整份塞进去会让模型在无关条款里找答案 —— 既贵又不准。用户原话：
**「一个检查项需要的信息是有限的」**。

**渲染结构（`RenderClauseBlocks`）**：

```markdown
## 条款清单
本次共 4 条条款，命中企业文档 1 份、摘录 1 条。

### 条款 5.5.1 · 职责和权限

【条款原文】
最高管理者应确保职责和权限得到规定、形成文件并在组织内沟通。…

【条款属性】
- 【管什么】明确组织内质量相关职责与权限的分配、文件化和沟通机制
- 【约束强度】shall
- 【适用性】general
- 【严重度】major
- 【资料核对方式】optional
- 【涉及过程】["management", "hr"]
- 【企业应提供的资料】…（Artifacts 原文）
- 【取证要求】…（EvidenceChain 原文）

【企业文档命中】1 份
· 《质量手册-提取验证.txt》，置信度 0.95
  位置：总经理负责体系运行的资源保障；管理者代表负责…
  摘录：总经理负责体系运行的资源保障；…

### 条款 5.5 · 职责、权限与沟通
【条款属性】（未配置 —— 本条无结构化要求，仅凭条款原文判断）
【企业文档命中】（该条款在企业已提交资料中未提取到对应内容）
```

**三个设计要点**：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 顺序固定 | 正文 → 属性 → 摘录，由程序拼 | 顺序一乱，模型注意力分配就乱 |
| 空也要说话 | 没属性写「未配置」，没命中写「未提取到」 | 模型必须能区分「企业没有」和「我们没给它看」 |
| 裁剪有上限 | 原文 1200 字 / 属性 800 字 / 单摘录 400 字 / 单条款 6 份文档 | 控制 token，且超出必记告警 |

**占位符全表**（`BuildPrompt` 实际替换的）：

| 占位符 | 值 | 分支 |
|---|---|---|
| `{{task_kind}}` | `prep` / `onsite` | 共用 |
| `{{check_item_name}}` | 检查项名称 | 共用 |
| `{{dept_names}}` | 涉及部门 | 共用 |
| `{{clause_blocks}}` | ★ 上面整块（清单 + 命中 + 输出契约） | 共用 |
| `{{previous_results}}` | 上次结论（增量模式） | 共用，V1 留空 |
| `{{onsite_evidence}}` | 现场证据块（访谈转录/照片说明/抽样） | 仅 onsite |
| `{{ClauseInfo}}` / `{{CheckRequirement}}` | → **条款清单**（原文 + 属性） | 旧模板兼容 |
| `{{EvidenceList}}` | → **企业文档命中**（按条款聚合的摘录） | 旧模板兼容 |

> ★ **旧占位符必须映射到新装配结果，不能各拼一份残片**（2026-11-02 踩过）：
> 旧实现里 `{{ClauseInfo}}` 只给「条款编码/序号/部门」，`{{EvidenceList}}` 只列
> `cert_evidence`（实测 **0 行**）。而 DB 里 `audit_check` 正文**只认这三个旧名字**，
> ⇒ onsite 分支永远拿不到条款属性和文档摘录，实测判出「未提供任何支持性证据」。
> 修法：三个旧名字分别指向 `RenderClauseInfo()` / `RenderDocHits()`。

**关键约束**：替换后仍残留 `{{` ⇒ 记错误日志。这是防「模板拼错/没传值，跑下去得到废结论」的护栏。

**装配质量指标**（写进 `cert_check_analysis.ResultSummaryJson`，⛔ 不能只看结论）：

```json
{"attr_hit_count": 27, "doc_hit_count": 1, "excerpt_count": 1,
 "assembly_warnings": ["以下条款在企业文档中未提取到对应内容：5.5,5.5.2,5.5.3"]}
```

`attr_hit_count = 0` ⇒ 条款模型没进装配；`doc_hit_count = 0` ⇒ 文档模型没进装配。
**这两项是「三模型有没有串上」的唯一客观判据。**

### 3.5 第四跳：AI 提取事实（两套输出契约）

#### prep 分支（`audit_prep`）

```json
{
  "prep_state":      "found|partial|missing|unknown|na",
  "summary":         "一句话总结",
  "missing_kinds":   ["缺的资料名称"],
  "conflicts":       ["文档A说X，文档B说Y"],
  "verify_level":    "doc|remote|onsite|test",
  "prep_nc_hint":    "给现场的建议（可为空）",
  "confidence":      0-100
}
```

**提示词里的硬约束（原文）**：

> - 你不能输出 pass / ofi / nc —— 那是现场检查阶段的事，现在还没到现场
> - unknown 绝不等于不符合：不知道就是不知道
> - missing_kinds 只列**资料名称**（如「管理评审记录」），不要写整句
> - conflicts 只列**互相矛盾的具体事实**（「A 文件说 3 人，B 文件说 5 人」）

**`verify_level` 是入场计划的直接输入**——AI 判「这条得去现场」还是「查文件就行」，正好是审核员排计划要的信息。

#### onsite 分支（`audit_check`）

```json
{
  "conclusion":          "conformant|minor_nc|major_nc|observation",
  "summary":             "一句话总结",
  "recommendation":      "建议",
  "confidence":          0-100,
  "nc_suggestion":       "（非符合项时填写）",
  "severity_suggestion": "minor|major"
}
```

⚠️ **注意**：这里是 `conformant/minor_nc/major_nc/observation`，**不是** `pass/ofi/nc/na`。而 `cert_check_result.Conclusion` 字段存的是 `pass/ofi/nc/na`。**两套词表，中间需要一层映射，现在没有。** 见 3.9-断点④。

### 3.6 第五跳：规则算结论（AI 不参与）

**代码**：`NcConclusionV2Calculator.cs`

**为什么必须是代码**（代码注释原文，值得抄进设计原则）：

> 「为什么必须是本地代码而不是 AI：「哪些级别影响结论、几条不过判什么」是专家确定的**决策矩阵** ⇒ 落成配置表，机器执行。让 AI 读提示词做这件事，**同输入两次可能出不同结论，认证审计无法接受**。」

**决策矩阵（7 步，顺序不可颠倒）**：

| 步 | 条件 | 结论 |
|---|---|---|
| 1 | 核心级 fail ≥ `MinorRejectThreshold`(3) | `improvement_required` 待改进后复审 |
| 2 | major/critical fail > 0 | `fail` 不通过 |
| 3 | unverifiable > 0 且策略 = `reject` | `fail` |
| 4 | 核心级 fail ≥ 1 | `pass_with_nc` 通过（带不符合项） |
| 5 | observation fail > `MinorTolerated`(不限) | `pass_with_nc` |
| 6 | unverifiable > 0 且策略 = `cap_basic` | 封顶到 `pass_with_nc` |
| 7 | 其余 | `pass` 通过（推荐认证） |

**安全侧缺省**：judge 漏盖级别 ⇒ **按 `major` 计算**，并计入 `stats.levels_defaulted`。漏配一条 = 按最严处理，不能按「不影响」漏过。

**规则来源**：`cert_conclusion_rule`（当前 1 行，`Code = CR-GENERIC-0001`）

| 字段 | 当前值 | 含义 |
|---|---|---|
| `CoreLevels` | `["major","minor"]` | 哪些级别算核心 |
| `MinorRejectThreshold` | `3` | 核心级 fail 到这个数 ⇒ 复审 |
| `MinorTolerated` | `-1` | 观察项容忍数（-1 不限） |
| `UnverifiedPolicy` | `cap_basic` | 有未验证项 ⇒ 封顶 |
| `ConclusionLabels` | pass/pass_with_nc/improvement_required/fail → 中文 | 结论词 |
| `ConclusionMode` | `AI_ASSISTED` | AI 辅助 |
| `ManualRequired` | `0` | 不强制专家签署 |
| `OverrideAlertThreshold` | `30` | 人工改动超 30% 告警 |
| `JudgePromptCode` | `nc_judge` | 引用判定提示词 |
| `ConcludePromptCode` | `nc_conclude` | 引用理由提示词 |
| `Status` | `draft` | ⚠️ 草稿 |
| `SourceRef` | 「★占位规则：阈值未经认证机构确认，不可用于真实认证结论」 | ⚠️ **阈值是占位的** |

**`RuleSnapshot` 快照**：每次计算把当时用的矩阵参数存进结果，事后可回溯「当时是按什么规则算的」。

### 3.7 第六跳：AI 写理由（不得改结论）

**代码**：`NcPromptAssembler.BuildConcludePrompt()`

**做法**：结论先由 ⑤ 算好，作为 `{{__RULE__.conclusion}}` 注入提示词，AI 只填 `{"reason": "一句话理由"}`。

**三重护栏**：

1. 提示词明写「★由系统确定，不得更改」「★不得改变结论等级」
2. 输出只有 `reason` 一个字段，AI 没有地方塞别的结论
3. `rule_conclusion` 原样回传，供校验 C7 比对

**这是「AI 辅助但不失控」的核心手法**：AI 的自由度被限制在「措辞」这一维，不影响「结论」这一维。

### 3.8 第七跳：审核员复核

**系统给的是「建议」，审核员给的是「最终」**。

落库结构（`cert_check_result`，一行一条款）：

| 字段 | 谁写 | 说明 |
|---|---|---|
| `PrepState` | AI | 准备期五态 |
| `Conclusion` | AI 建议 → 人改 | 四态 `pass/ofi/nc/na` |
| `NcSuggested` | AI | **检查期是否建议开 NC（≠ 已开 NC）** |
| `Severity` | AI / 属性 / 人 | 实际严重度 |
| `SeveritySource` | 系统 | **`attr` / `ai` / `manual` 三源标记** |
| `SeverityBaseline` | 属性 | 条款基线严重度 |
| `Reason` | AI → 人改 | 判定依据摘要（必填） |
| `ConclusionBy` / `ConclusionAt` | 人 | 谁在什么时候拍的板 |
| `ResultStale` / `StaleReason` | 系统 | 计划被编辑后置 1（`clause_change`/`dept_change`） |

**`SeveritySource` 三源设计很关键**：它回答了「这个严重度是条款自带的、AI 判的、还是人定的」。审核员一看就知道要不要重新审。

**「双结论」在字段上的体现**：

- 系统建议 = `NcSuggested` + `Severity`（`SeveritySource = ai`）
- 审核员判断 = `Conclusion` + `ConclusionBy`（`SeveritySource = manual`）

**不保留差异对比**（用户已定）：审核员改了就是改了，系统建议只在 `NcSuggested` 里留个痕迹，不做 diff 页面。

## 四 · 两个分支：准备与检查

### 4.1 数据流方向相反（这是最本质的差异）

```
认证准备：  企业资料 ──→ AI 分析 ──→ 审核员补充证据 ──→ 入场计划
            （先有资料，后补证据，产出是"去哪查什么"）

认证检查：  审核员挂证据 ──→ AI 分析 ──→ 检查证据 + NC 疑点 ──→ 报告
            （先有证据，后做分析，产出是"符不符合"）
```

用户原话：

> 「认证准备是先根据企业资料进行分析，分析后，让审核员补充证据，判断哪些已经符合了，哪些应该检查，如何检查；而我们的认证检查是先让审核员挂接证据信息，有了完整的企业认证资料和审核员的证据才能进行分析。」

**所以两个分支的「装配时机」不同**：

| | 准备 | 检查 |
|---|---|---|
| 首次分析时有什么 | 只有文档模型（按条款切片 + 画像） | 文档模型 + 审核员挂的证据 |
| `{{onsite_evidence}}` | 空 | 有值 |
| 输出 | `prep_state` 五态 + `verify_level` | `conclusion` 四态 + `nc_suggestion` |
| 产出物 | 入场计划 | 认证报告 |

### 4.2 同一个引擎

**关键**：两个分支**共用一个 `CertCheckEngineService`**，靠 `StageKind` 分流提示词和输出契约。

用户原话：

> 「我们认证准备由于实施的方式不一样，挂接证据方式也不一样，但**最终 llm 的执行过程是一样的**。」

所以不要为两个分支写两套引擎。**一个引擎，两个提示词，两套输出契约**。

### 4.3 准备阶段不签 NC

**准备阶段只回答「资料够不够」，不回答「符不符合」**。

- 输出 `prep_nc_hint`（给现场的建议），不是 NC
- 提示词硬约束：「你不能输出 pass / ofi / nc」
- 只有检查阶段才逐条签发 NC

## 五 · 状态词表（四套，绝对不能混）

> 系统里同时存在四套状态词。混用是脏数据的头号来源。**这一章是唯一权威定义。**

### 5.1 准备态 `PrepState`（五态）

用于 `cert_check_result.PrepState`。

| 值 | 中文 | 含义 | 会不会推 NC |
|---|---|---|---|
| `found` | 齐全 | 资料齐全且互不矛盾 | 否 |
| `partial` | 部分 | 有资料但缺关键要素，或文档互相矛盾 | 否（但提示） |
| `missing` | 缺失 | 完全找不到 | 否（但提示） |
| `unknown` | 无法判断 | 资料不足以下判断 | **绝不** |
| `na` | 不适用 | 该条款不适用本企业/本阶段 | 否 |

**`unknown` 的铁律**：`unknown` **绝不等于不符合**。不知道就是不知道。这条写进了提示词的硬约束，也是用户明确要求的「证据缺失是提示不是强制」。

### 5.2 结论态 `Conclusion`（四态）

用于 `cert_check_result.Conclusion`（**人填为最终**）。

| 值 | 中文 | 含义 |
|---|---|---|
| `pass` | 符合 | 满足条款要求 |
| `ofi` | 观察项 | 基本满足，有改进空间（Opportunity for Improvement） |
| `nc` | 不符合 | 不满足 |
| `na` | 不适用 | 该条款不适用 |

### 5.3 维度判定态 `DimensionConformity`（四态）

用于 `nc_judge` 输出的 `dimensions[].conformity`。

| 值 | 中文 | 说明 |
|---|---|---|
| `conform` | 符合 | 材料证明已满足 |
| `nonconform` | 不符合 | 材料证明未满足（必须写清「哪里不符合、差多少」） |
| `na` | 不适用 | 该维度对企业无适用性 |
| `unverifiable` | 无法判断 | 材料缺失或不足 |

**代码里的注释写得很直白**：「★ 四态（★ 不是 bool）」。

### 5.4 严重度（五级 + 三档）

`nc_judge` / `stamp_judge_level` 用的级别：

| 级别 | 含义 | 是否核心 |
|---|---|---|
| `critical` | 极严重（**并入 major 计算**，单独计数展示） | 是 |
| `major` | 严重不符合 | 是 |
| `minor` | 一般不符合 | 是 |
| `observation` | 轻微 / 观察项 | 否（受 `MinorTolerated` 控制） |
| `none` | 显式「不影响最终结论」 | 否 |

`cert_check_result.Severity` 只存两档：`major` / `minor`。

### 5.5 总结论（四档）

`NcConclusionV2Calculator` 输出：

| 代码 | 中文（默认） | 档位 |
|---|---|---|
| `pass` | 通过（推荐认证） | 0（最优） |
| `pass_with_nc` | 通过（带不符合项） | 1 |
| `improvement_required` | 待改进后复审 | 2 |
| `fail` | 不通过 | 3 |

### 5.6 四套词表的映射关系（★ 断点④ 的修复依据）

```
audit_prep 输出          →  cert_check_result.PrepState
  found/partial/missing/unknown/na  →  同名直存（1:1）

audit_check 输出         →  cert_check_result.Conclusion
  conformant    →  pass
  observation   →  ofi
  minor_nc      →  nc   （Severity = minor）
  major_nc      →  nc   （Severity = major）

nc_judge 输出            →  JudgeResult（喂 NcConclusionV2Calculator）
  conform       →  verdict = pass
  nonconform    →  verdict = fail   （level 取 SeverityIfFailed）
  na            →  不参与计算（RollupTo = 0）
  unverifiable  →  verdict = unverifiable

NcConclusionV2Calculator →  cert_conclusion_rule.ConclusionLabels
  pass / pass_with_nc / improvement_required / fail  →  中文结论词
```

**这张映射表要落成代码里的一个静态类，全局唯一，不许各处自己写。**

> ✅ **已落地（2026-11-02）**：`CertPlatform.Auditor/Services/Expert/CertVerdictMapper.cs`。
> 关键方法：`ToConclusion()` / `ToSeverity()` / `SuggestsNc()` / `NormalizePrepState()`。
>
> **两条实测出来的规则**（初稿没写，是跑真数据才发现的）：
>
> 1. **`NcSuggested` 按结论推导，不按 `nc_suggestion` 字段判。**
>    旧 `audit_check` 模板的 JSON 契约里根本没有 `nc_suggestion`，
>    靠字段判会出现「判了 `major_nc` 但 `NcSuggested=false`」的脏数据。
> 2. **`Severity` 模型没给就从结论反推**（`major_nc→major` / `minor_nc→minor`）。
>    理由：`major_nc` 这个词本身已经说明了严重度，让模型再重复输出一次只是多一个不一致的机会。
>
> 落库后 `ResultSummaryJson` 同时保留 `conclusion`（原始 `major_nc`）与
> `conclusion_mapped`（落库 `nc`），排查时不用再猜。

## 六 · 双结论：系统建议 vs 审核员判断

### 6.1 两层，但不保留差异对比

用户已定：

> 「我们有 2 套机制，一个是系统判断的证据，一个是审核员的决定，审核员可以直接修改系统判断的，**不保留差异**。」

所以：

- 系统跑出来的结论存一份（`NcSuggested` + `Severity` when `SeveritySource=ai`）
- 审核员改了直接覆盖 `Conclusion`，记 `ConclusionBy` / `ConclusionAt`
- **不做 diff 页面，不弹「你改了系统的判断」**

### 6.2 但仍要留痕（技术层面）

不是给审核员看的，是给审计和调优看的：

| 留痕点 | 存哪 |
|---|---|
| 系统当时建议什么 | `NcSuggested` |
| 严重度来自哪 | `SeveritySource` = `attr`/`ai`/`manual` |
| 谁改的、什么时候 | `ConclusionBy` / `ConclusionAt` |
| 当时的装配包长什么样 | `cert_check_analysis.InputSnapshotJson` |
| 当时用的哪版提示词 | `PromptCode` / `PromptVersion` |
| 当时用的哪个模型 | `ModelName` |
| 当时的规则参数 | `JudgeConclusionResult.RuleSnapshot` |

**这七项合起来，任何一条结论都能完整回放**。这是「可复现」的落地。

### 6.3 只有审核员能签发 NC

准备阶段不签，检查阶段逐条签。

- `NcSuggested = 1` 只是「建议开」，不等于开了
- 真正开 NC 要写 `cert_nc` 表（当前 0 行）

## 七 · 业务全景（两种使用模式）

### 7.1 模式 A：只用认证检查

```
认证计划 → 审核员按检查项逐个挂证据 → AI 分析 → 检查证据 + NC 疑点 → 复核 → 报告
```

**适用**：企业资料已经很齐，审核员知道自己要查什么，不需要系统帮忙排计划。

**本质**：一个「证据 → 结论」的推理器。

### 7.2 模式 B：认证准备 + 认证检查（完整版）

```
认证计划
   ↓
认证准备（看资料，判资料够不够）
   ↓
入场计划（去哪、查什么、找谁、怎么查）   ← 准备阶段的产物
   ↓
认证检查（按入场计划逐项补证据）
   ↓
AI 分析 → 检查证据 + NC 疑点
   ↓
复核 → 报告
```

**适用**：正常的体系认证项目。审核员要在进现场前，先搞清楚「这家企业缺什么、我要去看什么」。

**本质**：模式 A 前面加了一段「做计划」的工序。

用户原话：

> 「如果认证准备和认证检查结合，就变成了**入场计划的建立，和入场计划的执行，+ 入场计划的补充**（可能通过移动端就完成了证据的补充），再进行推理得到检查证据和 nc 疑点的过程。」

### 7.3 两种模式的技术差异（只有一个）

**唯一的差异：`cert_check_analysis.TaskCode` 是否有值 / 检查项是否挂在入场计划上。**

- 模式 A：检查项直接来自 `cert_audit_plan_detail`
- 模式 B：检查项来自入场计划 `cert_onsite_plan_item`（它本身也是从 `cert_audit_plan_detail` 派生的）

**引擎完全一样**。这就是为什么本期不急着做入场计划的挂接证据——**模式 A 跑通了，模式 B 只是多一层入口**。

### 7.4 本期做哪个

**先做模式 A 的全链路**（因为它是链路本身），入场计划表结构同步建好，但「入场计划 → 证据挂接」的 UI 和手机端**推到后面**。

理由：模式 A 跑不通，模式 B 一定跑不通；模式 A 跑通了，模式 B 是加壳。

## 八 · 认证准备

### 8.1 目标：只判「资料够不够」

**不判符合性**。这是准备阶段唯一的纪律。

用户原话：

> 「我们的认证准备其实是**排除一些非现场调研的信息**，初步让系统根据企业的材料形成初步的原始证据，为审核员制定入场计划（证据收集准备）。」

所以准备阶段的产出是**情报**，不是**判决**：

- ✅ 「这条条款要求管理评审记录，企业给了，但缺签字页」→ `partial`
- ✅ 「这条得去现场看」→ `verify_level = onsite`
- ❌ 「这条不符合」→ **不允许**

### 8.2 七个步骤

| 步 | 动作 | 谁做 | 落到哪 |
|---|---|---|---|
| 1 | 从认证计划派生准备任务 | 系统 | `cert_task`（`StageKind=prep`） |
| 2 | 按检查项取条款清单 | 系统 | `cert_audit_plan_detail.Clauses` |
| 3 | 装配：条款属性 + 文档模型 | 系统 | `InputSnapshotJson` |
| 4 | AI 判 `prep_state` | `audit_prep` | `cert_check_result` |
| 5 | 审核员看结果，补证据 / 改判定 | 审核员 | `cert_evidence` + `Conclusion` |
| 6 | 按 `verify_level` 生成入场检查项 | 系统建议，人确认 | `cert_onsite_plan_item` |
| 7 | 锁定已确认的检查项 | 审核员 | `cert_check_item.IsLocked` |

**第 5 步是准备阶段的核心动作**：AI 说「缺 XX」，审核员可能说「不，XX 在这个文件里，我给你挂上」——这就是「审核员补充证据」。

### 8.3 准备阶段可以改审核员

**这是准备和检查的一个重要差异**。

用户原话：

> 「认证准备中可以定义每个检查项的审核员是谁，而认证检查不能更改审核员信息，而审核员信息是入场计划非常关键的信息。」

| | 准备 | 检查 |
|---|---|---|
| 审核员字段 | **可改** | **只读** |
| 谁定 | 审核组长在准备阶段定 | 继承入场计划 |

**为什么**：入场计划是「谁去哪个部门查什么」的分配表。分配是在准备阶段做的，到检查阶段就是执行，不该再改。

### 8.4 不适用：专家独立判，系统不参与

用户原话：

> 「所谓不适用是在认证准备阶段，判断也是**专家独立觉得的，系统不参与判断**。」

所以：

- `na` 是审核员选的，不是 AI 推的
- AI 可以给 `Applicability` 作为参考（`conditional` 条款），但**不替人决定**
- 人标了 `na`，`RollupTo = 0`，不参与汇总

## 九 · 入场计划

### 9.1 入场检查项：一个检查项 → 多条检查动作

**这是入场计划的核心结构**。

用户原话：

> 「我们在入场准备的时候，还应该多一个列，就是**针对一个检查项，我们应该去检查什么信息，采用什么方式（开会、讨论、现场取证等），这个是多条记录**。」

```
检查项（cert_audit_plan_detail，1 行，挂多条条款）
   ├── 入场检查项 1：去仓库看警示标识，现场取证，抽查 3 个区域
   ├── 入场检查项 2：查危险源台账，查记录，最近 12 个月
   └── 入场检查项 3：问仓库管理员，访谈，2 人
```

**数据来源**：条款的 `EvidenceChain`（见 2.1）。系统可以**预填**，审核员可增删改。

**⚠️ 注意粒度**：入场检查项挂在**检查项**下，不是挂在条款下。因为一个检查项可能含多条条款，而一次现场动作可能同时覆盖多条条款（比如「看仓库标识」可能同时验证 8.3 和 8.5）。

### 9.2 检查方式（预设，审核员选）

用户已定：「讨论方式，由审核员来选择，我们可以预设一些。」

| 预设方式 | 对应 `Kind` | `VerifyLevel` |
|---|---|---|
| 查文件 | `doc` | `doc` |
| 查记录 / 台账 | `record` | `doc` / `remote` |
| 远程核验（视频/截图） | — | `remote` |
| 现场取证（看/拍照） | `site` | `onsite` |
| 访谈 / 开会 / 讨论 | `interview` | `onsite` |
| 抽样测试 | — | `test` |

**预设只是候选，审核员可以自由输入。** 不做强校验。

### 9.3 表 `cert_onsite_plan_item`

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(50) | 业务键 |
| `PlanCode` | varchar(50) | 所属认证计划 |
| `CheckItemCode` | varchar(50) | ★ 所属检查项（`cert_audit_plan_detail.Code`） |
| `SeqNo` | int | 序号 |
| `CheckWhat` | varchar(500) | ★ 检查什么（"危化品仓库警示标识"） |
| `CheckMethod` | varchar(50) | ★ 检查方式（`doc`/`record`/`site`/`interview`/`test`/自定义） |
| `TargetDept` | varchar(200) | 去哪个部门 |
| `ContactCode` / `ContactName` | varchar | 联系人 |
| `AuditorCode` | varchar(50) | ★ 谁去查（准备阶段可改） |
| `SampleRequirement` | varchar(200) | 抽样要求（"抽查 3 个区域"） |
| `ExpectedFinding` | varchar(500) | 应该发现什么 |
| `ClauseCodes` | varchar(500) | 关联条款（多个逗号分隔） |
| `Source` | varchar(20) | `ai`（从 EvidenceChain 预填）/ `manual` |
| `Status` | varchar(20) | `draft` / `confirmed` / `done` |
| `OrgCode` | varchar(50) | 机构 |

**设计要点**：

- `Source` 标记是 AI 预填还是人加的——**AI 预填的要能一眼看出来**，方便审核员快速过一遍
- `Status` 三态，`confirmed` 之后才算定稿
- **定稿后不硬锁**（按总原则），但改会留痕

### 9.4 生成方式

```
Step 1  取检查项的所有条款
Step 2  取每条条款的 EvidenceChain[]
Step 3  按 Kind 映射 CheckMethod，按 Target 填 CheckWhat，按 Sample 填 SampleRequirement
Step 4  Source = ai，Status = draft
Step 5  审核员逐条过：确认 / 改 / 删 / 加
```

**AI 预填的价值**：审核员不用从零想「这条条款该查什么」。他只需要**判断 AI 说得对不对**——判断比创造快得多。

### 9.5 独立执行页面

用户要求：「他可以有个独立的入场计划的页面，针对他能看到的入场计划逐项补充证据。」

**本期只做页面骨架**（列表 + 详情 + 挂证据入口），**不做手机端**。

### 9.6 手机端：数据结构留口，功能不做

用户原话：

> 「更多的是在手机端，打开一个入场计划，进行录音，进行拍照，然后记录一些信息，白天在企业就完成了，我们系统通过手机端，录音转文字，自动归类到每个检查项就完成了证据的收集……（只是这一块比较复杂，我们当前首要是要跑通手动补充证据后，能推理出检查证据，和 nc 疑点）」

**留的口子**（现在就要有，不然以后改不动）：

| 口子 | 字段 | 为什么现在要 |
|---|---|---|
| 按人筛选 | `AuditorCode` | 手机端登录后只看自己的 |
| 证据支持非文本 | `cert_evidence.SourceType` = `file`/`audio`/`photo`/`text` | 录音拍照要能存 |
| 转录文本独立 | `cert_evidence.TranscriptText` | 录音转文字的结果 |
| 位置信息 | `cert_evidence.Location`（可空） | 现场取证要能证明"我去过" |
| 时间戳 | `cert_evidence.CapturedAt` | 现场采集时间 |

**这些字段现在建好，功能不做。** 成本很低，以后省大事。

### 9.7 本期不做

- ❌ 入场计划 → 证据的自动挂接 UI（只做手动）
- ❌ 手机端
- ❌ 录音转文字
- ❌ 自动归类到检查项

### 10.1 两个入口

| 入口 | 场景 | 检查项从哪来 |
|---|---|---|
| 独立使用 | 模式 A | `cert_audit_plan_detail` |
| 从入场计划进来 | 模式 B | `cert_onsite_plan_item` |

### 10.2 五个步骤

| 步 | 动作 | 谁做 |
|---|---|---|
| 1 | 审核员按检查项挂证据 | 审核员 |

### 10.3 证据是提示，不是硬卡

用户原话：

> 「我们缺失证据是提示不是强制。」

所以：

- 证据 0 份 ⇒ **可以分析**，AI 输出 `unverifiable`，界面提示「建议先补证据」
- **不做**「证据 0 份禁止分析」的硬拦截
- **不做**「必须 N 份证据」的校验

V2 原型里那个「证据 0 份不可分析」的灰按钮，**本版明确推翻**。

### 10.4 证据表统一

用户原话：

> 「如果有认证准备，认证准备和认证检查的证据链（审核员提供的），其实都是在一个证据链表中，只是有不同的阶段区分，我们都可以作为核心的原始证据提供给系统进行 llm 分析。」

所以 **`cert_evidence` 一张表**，用 `StageKind` 区分：

| 字段 | 说明 |
|---|---|
| `StageKind` | `prep` / `onsite` |
| `ClauseCode` | 挂哪条条款 |
| `CheckItemCode` | 挂哪个检查项 |
| `SourceType` | `file`/`audio`/`photo`/`text` |
| `SourceName` | 文件名 / 描述 |
| `LlmSummary` | AI 生成的摘要（进提示词用） |
| `TranscriptText` | 转录/全文（截断 500 字进提示词） |
| `CapturedAt` / `Location` | 现场采集信息（手机端留口） |

**两阶段证据同等对待**：装配时不区分来源，只按 `ClauseCode` 分组。

### 10.5 引擎不变

用户原话：

> 「我们认证准备由于实施的方式不一样，挂接证据方式也不一样，但**最终 llm 的执行过程是一样的**。」

所以**不要**为两个分支写两套引擎、两套装配、两套落库。只有：
- 提示词不同（`audit_prep` / `audit_check`）
- 输出契约不同（五态 / 四态）
- `{{onsite_evidence}}` 是否为空

## 十一 · 锁定与重跑

### 11.1 为什么必须能反复执行（业务动机）

用户原话讲得最清楚：

> 「一般企业认证的时候，不是认证必须全部合格，很多时候企业问题都有很多，需要开具 nc，企业会整改，比如企业没有粘贴安全警告，或没有重要设备，缺什么重要信息，企业可以补充后，提供证据，这时候**不用到现场也能重新认证，闭合 nc**，之前已经通过的就必须要锁定。我们推理了一大堆检查证据，审核员好不容易阅读审核完成了，我们如果不锁定，重新跑一遍，就把审核员的工作全部作废了，**是万万不可的**。」

所以反复执行的场景是：

```
检查 → 开 NC → 企业整改 → 补证据 → 重跑 → 闭合 NC
                                    ↑
                            已通过的必须锁住
```

### 11.2 锁的是什么

**锁的是「已经过审核员确认的结论」**，不是锁检查项本身。

| 锁的对象 | 锁什么 | 为什么 |
|---|---|---|
| `cert_check_result` 行 | 该条款的 `Conclusion` + `Reason` | 审核员确认过的，不能被重跑覆盖 |
| 检查项 | `cert_check_item.IsLocked` | 整项都确认完了 |

**粒度是条款级，不是检查项级**——一个检查项里可能 3 条条款通过了、2 条没过，锁的是那 3 条。

### 11.3 锁的三道闸门（已实现，M3）

| 闸门 | 位置 | 作用 |
|---|---|---|
| ① 入队过滤 | `StartTaskAsync` → `GetLockedCodesAsync` | 锁定的检查项不进队列 |
| ② 执行第一行再查 | `CertCheckItemExecutor` 开头 | 排队期间被锁的，跳过 |
| ③ 写入前断言 | `AssertPageEditable*` 四个方法 | 最后一道，防并发 |

**全锁短路**：所有检查项都锁了，直接返回，不建队列。

### 11.4 两把锁方向相反（重要）

| | 页面锁 | 检查项锁 |
|---|---|---|
| 锁谁 | **人**别动 | **机器**别动 |
| 谁开 | 系统（任务运行时自动） | 人（手动解锁） |
| 时长 | 任务运行期间 | 永久，直到人解 |
| 触发 | 入队时加，跑完自动解 | 审核员点「锁定」 |

**页面锁**：任务跑的时候，人不该同时改数据（会打架）。
**检查项锁**：人确认过的，机器不该再动（会作废人的工作）。

### 11.5 重新执行时，锁定的怎么办

用户原话：

> 「重新执行核心查看该检查项是否已经锁定，**如果已经锁定了需要审核员重新勾选认可**。」

所以：

- 默认跳过锁定的
- 审核员可以**主动勾选**「这几项也要重跑」
- 勾选后，锁临时打开，跑完重新锁（或提示重新确认）

### 11.6 自由选择重跑哪些

用户原话：

> 「无论是认证检查也好，还是认证准备也好，我们都可以锁定已经完成的检查项，**可以自由选择哪些检查项进行重新分析**。」

所以入口有两个：

| 入口 | 粒度 | 场景 |
|---|---|---|
| 整批重跑 | 任务级 | 计划大改，全部重来 |
| 勾选重跑 | 检查项级 | 只补了几条证据，只跑这几项 |

### 11.7 与 M3 实现的关系

M3 已实现：

- ✅ 队列接线（`yzh_queue` + `QueueManager`）
- ✅ 汇总回写（`CertTaskAggregator`）
- ✅ 页面锁（4 个写端点 409）
- ✅ 暂停真取消队列

M3 **未实现**：

- ❌ 条款级锁定（现在只有检查项级 `IsLocked`）
- ❌ 勾选重跑
- ❌ `ResultStale` 的自动置位
