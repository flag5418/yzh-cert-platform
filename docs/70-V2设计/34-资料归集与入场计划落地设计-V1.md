## 零、一句话结论与两个计划的分工

**认证计划回答"该查什么"，入场计划回答"哪天、谁、去哪个部门、查什么"。**

| | 认证计划（已落地） | 入场计划（本文新增） |
|---|---|---|
| 本质 | **应审清单**（条款 × 部门全集） | **实审排班**（时段 × 人员 × 部门 × 条款） |
| 是否含时间 | ⛔ 不含日期，只有 `EstMinutes` 预估 | ✅ 含日期/半天/顺序/审核员 |
| 条款清单 | 全集（适用 + 待确认） | 子集（**沟通已解决的剔除**，其余重排） |
| 谁产出 | 由适用性 + 部门矩阵生成 | 由认证计划 + 疑点清单 + 审核组 + 时间预算生成 |
| 可否反写 | ⛔ 不被入场计划改 | ✅ 只读认证计划，自身可反复重排 |
| 与报告 | 提供 `StandardCode/ClauseCodes/DeptCode` 挂载骨架 | 提供"什么时候查的"（报告可写审核日期/班次） |

> **关系裁决**：入场计划**派生**于认证计划（`cert_onsite_plan.PlanCode` 必填指向认证计划），不是并列两套清单。理由：两套清单必然漂移（条款改了入场计划不知道），而派生只维护"状态与排班"。

## 一、目标链路（用户要的四步，顺序不能换）

```
① 企业上传资料 → 已有：cert_enterprise_original_file(237) + cert_extraction_result(31) + cert_table_extraction_result(2)
        ↓  【新增 L2 归集层】
② 按「当前选中的计划」把资料/提取明细挂到 条款(×部门)
        ↓  【新增 L3 判断层】
③ 条款级完备性（found/partial/missing/unknown）→ 缺口清单
        ↓
④ 疑点清单（条款×部门 → 沟通/观察/询问/验证 + 远程/现场 + 严重程度 + 动作 + 时长）
        ↓  【新增 L4 排班层】
⑤ 入场计划：裁掉沟通已解决的 → 按部门重排 → 排到半天/人员 → 预算校验
        ↓  【后置】
⑥ 证据链挂条款（现场取证 → 判定 → 报告）
```

**为什么必须按这个顺序**：④ 的"该现场还是远程"依赖 ③ 的缺口类型；③ 依赖 ② 的"这条款到底有没有资料支撑"；② 依赖①的提取明细。跳过 ②③ 直接做 ⑤，排出来的班次没有依据（回到"凭经验拍时间"）。

## 二、L2 归集层：`cert_plan_doc_index`（条款级证据索引）

### 2.1 为什么是"索引表"而不是给提取结果加列

| 方案 | 问题 |
|---|---|
| A. 给 `cert_extraction_result` 加 `ClauseCode` | 一份资料常服务多个条款（质量手册服务 4.1/4.2/4.3…）；提取结果由**规则**产出，与"哪份计划"无关，加 `PlanCode` 会被计划污染，换计划要重抽 |
| B. 新建索引表（本文） | 提取结果只读复用；一份提取结果可挂 N 个条款；换计划只重建索引，不动提取 |

> **结论**：**B**。`cert_extraction_result` 是"资料说了什么"（事实层，与计划无关）；`cert_plan_doc_index` 是"这条款由谁支撑"（关联层，随计划变）。

### 2.2 表结构

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) PK | GUID 业务键 |
| `PlanCode` | varchar(36) | 认证计划（`cert_audit_plan.Code`） |
| `StandardCode` | varchar(36) | 标准 GUID（与 `cert_iso_clause.StandardCode` 同口径） |
| `ClauseCode` | varchar(36) | 条款（`cert_iso_clause.Code`） |
| `DeptCode` | varchar(50) | **可空**：部门无关的资料（手册/程序）为空；部门专属记录（培训记录/生产记录）填 |
| `StandardFileCode` | varchar(36) | 应然端：`cert_standard_directory_file.Code`（这条款"应该有"的那份资料） |
| `FileCode` | varchar(36) | 实然端：`cert_enterprise_original_file.Code`（企业实际交的那份） |
| `ExtractResultCode` | varchar(36) | **可空**：`cert_extraction_result.Code`（字段级明细，可空 = 资料级命中） |
| `TableResultCode` | varchar(36) | 可空：`cert_table_extraction_result.Code`（表格级明细） |
| `MatchState` | varchar(20) | `found` / `partial` / `missing` / `unknown`（见 §3.2） |
| `MatchSource` | varchar(20) | `directory`（目录项挂条款，人工）/ `artifact`（AI 用 Artifacts 匹配）/ `manual`（人工指定） |
| `Confidence` | decimal(3,2) | 0–1；`manual` 恒 1.00 |
| `Snippet` | text | 命中的原文片段（**只存片段，不存全文**，全文靠 FileCode 回查） |
| `PositionInfo` | json | 位置（页码/段落/表格坐标），下钻用 |
| `Remark` | varchar(500) | |
| `IsValid` / `Sort` / 审计列 | | `CreateBy` = `Sys_User.Code`；`UpdateTime` **可空** |

uk：`(PlanCode, ClauseCode, DeptCode, FileCode, ExtractResultCode)`（允许同条款多资料/多字段）。
索引：`idx_plan_clause(PlanCode, ClauseCode)`、`idx_file(FileCode)`、`idx_state(PlanCode, MatchState)`。

### 2.3 生成逻辑（`DocIndexService.Build(planCode)`）

```
1. 取计划的适用条款集（消费适用性结果；未实现前 = 计划明细里的条款）
2. 对每条款，取 Artifacts（cert_clause_attr 中 AttrCode='Artifacts' 的 prompt 值）
3. 应然端：cert_standard_directory_file 中该标准的目录项（若已配 ClauseCode 映射 → 直接对齐）
4. 实然端：cert_enterprise_original_file 中该企业的文件（按 StandardFileCode / 文件名匹配）
5. 有提取结果 → 逐字段落一行（ExtractResultCode + Snippet + PositionInfo）
   只有资料无字段 → 落一行资料级（ExtractResultCode 为空）
6. 无资料 → 落一行 MatchState=missing / unknown（区分见 §3.2）
7. AI 兜底：用 Artifacts 提示词对"未匹配到条款的资料"做条款匹配 → MatchSource=artifact，Confidence<1 的进人工确认队列
```

**幂等**：按 `PlanCode` 整批重建（先删后插），不做增量 diff（首版简单可靠；重跑成本可控，单企业百级资料）。

## 三、L3 判断层：完备性 + 疑点清单

### 3.1 两条产出，别混

| 产出 | 回答 | 表 |
|---|---|---|
| **完备性/缺口** | 这条款要的东西**有没有** | `cert_plan_doc_index.MatchState` 聚合（不另建表） |
| **疑点清单** | 这条缺口**该怎么解、谁去解、多严重** | `cert_plan_clause_point`（新表） |

> 完备性是"事实状态"，疑点是"行动建议"。两者一对一不成立（一条 `missing` 可能派 2 条疑点：先沟通索取、索取不到再现场观察）。

### 3.2 四态判定（照 29 号 §1.3，补 `found`）

| 状态 | 含义 | 判定依据 | 下游动作 |
|---|---|---|---|
| `found` | 交了，且要素齐 | 目录项 `ExtractionEnabled=1` 的规则全部命中 | 无（可能仍需抽查） |
| `partial` | 交了，缺要素/过期/无审批 | 部分规则命中 / `MaxConfidence` 低 / 有效期已过 | 疑点（verify 或 interview） |
| `missing` | 该有、确实没有 | 应然端有目录项 + 实然端无任何文件 | 疑点（communicate 先索取） |
| `unknown` | **我们没查到**（没上传/没读到/规则没配） | 无目录项 或 `ExtractionEnabled=0` 或提取未跑 | 疑点（communicate），**⛔ 绝不推 NC** |

> ★★ 红线：`unknown` 写成 `missing` = 把"我们没查"变成"企业没有"，这是最贵的一种错（29 号红线 1）。

### 3.3 `cert_plan_clause_point` 疑点清单表

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) PK | |
| `PlanCode` | varchar(36) | 认证计划 |
| `StandardCode` | varchar(36) | 标准 GUID |
| `ClauseCode` | varchar(36) | 条款 |
| `DeptCode` | varchar(50) | **可空**：条款×部门一行（1.33× 的来源） |
| `TargetRole` | varchar(50) | 沟通对象**角色**（⛔ 不写人名，29 号红线 5） |
| `GapType` | varchar(20) | `missing`/`partial`/`unknown`/`inconsistent`（缺口类型，可空=非缺口型疑点） |
| `PointKind` | varchar(20) | `communicate`/`observe`/`interview`/`verify`（疑点四分类，29 号 §1.5） |
| `Mode` | varchar(10) | `remote`/`onsite` |
| `Severity` | varchar(10) | `major`/`minor`/`observation`/空（来源见 §3.4） |
| `SeveritySource` | varchar(20) | `rule`/`ai`/`manual`（**必须标来源**，否则报告说不清严重程度哪来的） |
| `Reason` | text | 依据（指到缺口或矛盾；⛔ 空理由不允许） |
| `Action` | text | 看什么/问什么/抽几份 |
| `Question` | text | 访谈提纲（`interview` 必填） |
| `EstMinutes` | int | 预估时长（喂给入场计划） |
| `Priority` | varchar(10) | `high`/`medium`/`low` |
| `IsMandatory` | tinyint | 法定必查（内审/管评/灭菌确认/投诉与不良事件） |
| `Status` | varchar(20) | `open`/`resolved`/`converted`/`dropped`（`resolved` = 沟通已解决，入场计划据此裁剪） |
| `ResolvedBy`/`ResolvedAt`/`ResolveNote` | | 谁在什么时候怎么解决的（**留痕，不删除**） |
| `IsValid` / `Sort` / 审计列 | | |

uk：`(PlanCode, ClauseCode, DeptCode, PointKind, GapType)`（同格同类型不重复派）。
索引：`idx_plan_dept(PlanCode, DeptCode)`、`idx_status(PlanCode, Status)`。

### 3.4 严重程度来源（⛔ 不许模型自定）

```
① 优先 cert_validation_rule（该条款有判定规则 → SeverityIfViolated）⇒ SeveritySource=rule
② 无规则 → AI 按 Obligation/条款性质给建议 + 置信度 ⇒ SeveritySource=ai，必须人工确认后才可用于报告
③ 人工改 ⇒ SeveritySource=manual
```

> 24 号裁决：「判定只信 `cert_validation_rule`」。所以 `ai` 来源的严重程度**只能用于排优先级**（决定先查谁），⛔ 不能直接写成报告里的 NC 等级。

### 3.5 生成逻辑（`PointService.Build(planCode)`）

```
1. 读 cert_plan_doc_index 聚合 → 每条款的 MatchState（多资料取"最好"状态；任一 found 即 found）
2. 对 missing/unknown → PointKind=communicate, Mode=remote（先索取，成本最低）
3. 对 partial → 视缺什么：
     缺审批/签署/日期 → verify（远程比对）
     缺执行记录/现场状态 → observe（现场）
     缺职责/意识/授权 → interview（现场）
4. 跨文档矛盾（后续 readiness 提示词产出）→ verify + GapType=inconsistent
5. 部门矩阵：条款 Process ∩ 部门 ResponsibleProcesses → 展开成 条款×部门 多行
6. 严重程度：§3.4 三步
7. 时长：机构基准 × 抽样量（首版人工给基准，见 D-T8）
```

| 列 | 类型 | 说明 |

| `EstMinutes` | int | 本格时长 |

> 为什么半天而不是小时：真实排班以半天为单位（上午/下午各一个部门），小时级排班在没有"赶路时间/企业作息"数据时是假精确（30 号 §8.1）。

### 4.3 排班算法（规则版，AI 只做建议）

```
1. 取认证计划全部计划项 + 疑点清单（Status=open）
2. 裁剪：Status=resolved/dropped 的疑点不排（但保留记录，报告可写"经沟通已解决"）
3. 聚合：按 DeptCode 分组 → 同部门疑点合并到同一格（跨标准也合，SessionCode 相同）
4. 排序：IsMandatory 优先 → Severity 高优先 → 同部门连续
5. 落格：按 Days × 2（半天）× 审核员数 铺格子，Σ EstMinutes ≤ Days×BudgetMinutesPerDay
6. 超预算：按"低风险 → 可远程补证 → 可减抽样"顺序提示砍单，砍掉的写 SamplingNote 理由
7. 留白：每半天留 15% 缓冲（赶路/临时追问），不足则显式提示"无缓冲"
```

**出口判据**：每个格能回答"为什么这个部门在这个半天"（`PointCodes` + `ClauseCodes` 可追溯）；Σ时长 ≤ 预算；被裁项 100% 有理由。

### 4.4 与"沟通已解决"的关系（用户重点）

- 沟通解决**不删疑点**，改 `Status=resolved` + `ResolveNote`（如"企业 11-05 补交了灭菌确认报告，已核对通过"）。
- 入场计划生成时自动跳过 `resolved`，但保留在计划里可见（灰显），避免"消失得没人知道为什么少查了一条"。
- 若企业又反悔（补交的不合格），把 `Status` 改回 `open` → 重排即回到排班。

## 五、L5 证据链（后置，只定契约不实现）

`cert_clause_evidence`：`Code, EnterpriseCode, StandardCode, ClauseCode(可空), SlotCode(可空), PointCode(可空), EvidenceType(doc/record/site/interview), Fact(text), Anchor(text，时间/地点/人物/数值至少一项), CollectorCode, CollectedAt, IsValid, 审计列`

- 挂 `ClauseCode` 是主键路径（未来报告按条款聚合）；
- 挂 `SlotCode` 让报告能写"2026-11-11 上午 生产部现场观察到…"；
- 挂 `PointCode` 形成"疑点 → 证据 → 结论"闭环。

> 后置理由：没有 L2–L4 的证据链是空壳（不知道挂哪条条款、哪次现场）。

## 六、现状体检（决定开发顺序的硬事实，2026-10-29 实库核对）

| 项 | 现状 | 影响 |
|---|---|---|
| `cert_enterprise_original_file` | **237 行** ✅ | 实然端有料 |
| `cert_extraction_result` / `_table_` | **31 / 2 行** ⚠️ | 只有少量文档跑过提取；归集会大面积 `unknown` |
| `cert_standard_directory_file` | **93 行，全部 `DocCategory=editable`，全部属 iso13485** ⚠️ | 只能单标准验证；`fixed` 分支无数据 |
| 目录项 → 条款 映射 | **不存在**（目录表无 `ClauseCode`）❌ | **L2 的第一座桥缺失** |
| `cert_clause_attr` | **96 行 / 12 条款**（iso9001:5、iso14001:5、iso13485:2）❌ | `Artifacts` 严重不足 ⇒ 完备性无"应然期望" |
| `cert_validation_rule` | **2 行** ❌ | 严重程度几乎全靠 AI 建议 |
| `cert_enterprise_dept` | **0 行** ❌ | 疑点清单/部门重排的部门维为空 |
| `cert_audit_member` | **0 行** ❌ | 排班无审核员可派 |
| `cert_audit_plan` 存储口径 | 逗号去规范化（`Clauses/Departments/ClauseNumbers`）⚠️ | 按 `ClauseCode` 查会退化成 `LIKE '%code%'`，L2–L4 全靠按条款查 ⇒ **硬坑**（见 D-T7） |

> **结论**：L2–L4 的代码量不大，**卡在输入**。所以 P0 不是写码，是"把三座桥搭起来"。

## 七、开发计划（P0–P5，每阶段有出口判据）

### P0 输入补齐（阻塞，无此不开工）

| 事项 | 做法 | 出口判据 |
|---|---|---|
| P0-1 条款属性全量 | 对目标标准跑 `ClauseAttr/generate`（已有能力），补齐 8 属性 | 目标标准 `Artifacts` 覆盖率 ≥ 80% |
| P0-2 部门建档 | 专家端 `enterprise-dept` 建 ≥3 部门 + 职责（`ResponsibleProcesses` 若未建则先用手工填 `Remark`） | 一企业 ≥3 部门，条款能落至少 1 个部门 |
| P0-3 目录项→条款映射 | 目录表加 `ClauseCode`（主责条款，人工配）+ 允许一对多关联 | ≥30 条目录项有条款映射 |
| P0-4 存储口径收敛裁决 | 见 D-T7：明细是否从逗号改 JSON 数组 | 裁决出结果并落 DDL |

### P1 资料归集（"按计划看资料"）

- 建 `cert_plan_doc_index` + `DocIndexService.Build(planCode)` + 条款证据视图页
- 页面：选计划 → 条款树 → 点条款 → 右表列"支撑资料 + 命中的提取字段 + 原文位置"，可下钻原文件
- **出口**：任一条款能列出支撑它的资料与提取明细；无资料的条款显示四态之一（不是空白）

### P2 完备性（缺口清单）

- 四态判定（§3.2）+ 计划级缺口汇总页（按部门/按标准/按状态筛选）
- **出口**：每个适用条款都有 `found/partial/missing/unknown` 之一，**无空**；`unknown` 不显示为"缺失"字样

### P3 疑点清单

- 建 `cert_plan_clause_point` + `PointService.Build(planCode)` + 疑点页（条款×部门矩阵视图）
- **出口**：每条疑点带 类型/模式/部门/角色/动作/时长/依据；四类都有出现；严重程度 100% 标来源

### P4 入场计划（用户最关心的产出）

- 建 `cert_onsite_plan` + `cert_onsite_slot` + `OnsitePlanService.Build(planCode)` + 排班页（日期×半天×人员甘特/表格）
- **出口**：Σ时长 ≤ 预算；每格可解释；`resolved` 疑点自动不排且灰显可见

### P5 证据链（后置）

- 建 `cert_clause_evidence` + 现场取证页 + 挂 `SlotCode/PointCode`
- **出口**：每条证据有锚点；能回答"这条结论是哪次现场哪个疑点长出来的"

### 依赖关系

```
P0 ──► P1 ──► P2 ──► P3 ──► P4 ──► P5
        └──────────┘
        （P1 的索引是 P2 完备性的唯一数据源，不可跳）
```

## 八、待裁决（每条配白话说明）

| # | 事项 | 白话说明 | 建议 |
|---|---|---|---|
| **D-T1** | 资料→条款怎么建映射 | 现在目录里有 93 份"该交的资料"，但没写它服务哪个条款。要么人工配一遍（准，但慢），要么让 AI 拿条款的"要什么材料"去比对（快，但可能错）。 | **混合**：目录项人工配主责条款（准），AI 只处理人工没配的（`MatchSource=artifact` + 低置信度进人工确认） |
| **D-T2** | 归集落点：索引表 vs 提取结果加列 | 一份质量手册会服务 4.1/4.2/4.3 三个条款，如果直接把条款写到提取结果上，就得复制三份，换计划还得重抽。 | **索引表**（§2.1） |
| **D-T3** | 认证计划与入场计划：派生 vs 并列 | 并列就是两张互不认识的表，条款一改入场计划不知道；派生就是入场计划必须挂在一个认证计划下。 | **派生**（`PlanCode` 必填） |
| **D-T4** | "沟通已解决"怎么表达：改状态 vs 删除 | 删了就没人知道为什么少查一条；改状态能留痕，也能反悔。 | **改状态**（`resolved` + 理由，不删） |
| **D-T5** | 疑点粒度：条款 vs 条款×部门 | 同一条款生产部和质量部都要问，合成一条就分不清派给谁；实测 1.33×。 | **条款×部门** |
| **D-T6** | 严重程度来源 | 严重程度会写进报告，不能由模型随口定。 | **`cert_validation_rule` 优先；无规则 AI 只做排优先级，⛔ 不进报告** |
| **D-T7** | 明细存储口径：逗号 vs JSON | 现在明细是 `"code1,code2"` 字符串，按条款反查只能 `LIKE '%code%'`（慢且会误命中）。L2/P3/P4 全要按条款查。 | **P1 前收敛到 32 号**（`ClauseCodes` JSON 数组 + `ItemKind`），否则后面全返工 |
| **D-T8** | 排班粒度：半天 vs 小时 | 没有赶路时间/企业作息数据时，小时级是假精确。 | **半天 + 序**，P7 再细化 |
| **D-T9** | 时长基准谁给 | `EstMinutes` 决定排得下排不下，首版没有机构基准数据。 | **人工给默认值（30/60/90 分钟三档）**，跑几轮后统计修正 |

## 九、风险与坑（按严重度排）

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| **R1** | 逗号口径（D-T7 不裁） | 按条款反查退化 `LIKE`，命中错、性能差；L2–L4 全部受影响 | **P1 前必须裁** |

## 十、验收（一企业一标准，端到端）

1. 选一个认证计划 → 任一条款能列出"支撑它的资料 + 提取字段 + 原文位置"，可下钻。
2. 每个适用条款都有四态之一，无空白；`unknown` 不被渲染成"缺失"。
3. 每条疑点带类型/模式/部门/角色/动作/时长/依据，且严重程度标了来源。
4. 入场计划：Σ时长 ≤ 预算；每格能解释"为什么这个部门在这个半天"；沟通已解决项不排但可见。
5. 红线零违反：`unknown` 不推 NC；部门名不自造；角色不写人名；`ai` 严重程度不进报告。
