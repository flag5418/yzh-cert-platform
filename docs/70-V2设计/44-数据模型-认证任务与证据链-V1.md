# 数据模型（V2）：认证任务 · 检查项结论 · 证据链

> **上游**：`43 号`（总体设计：检查项 = 计划明细、两方向任务、证据池共享、判定条款级）
> **本文回答一件事**：这些概念怎么落到表上。**不写提示词正文、不写界面。**
>
> **2026-10-30 用户三条定稿**（本文据此重写）：
> ① **计划每年都不一样**（二阶段全条款覆盖 / 后续抽查 / 范围变更）→ 计划不同 ⇒ 任务不同 ⇒ 任务可反复执行、结果可变；
> ② **准备与检查的任务头可以合并**（已采纳）；
> ③ **看准备就看准备的证据与结果，看检查就看检查的** —— 两者不矛盾、**也不该互相覆盖**。

## 零、三条定稿怎么进模型（一句话版）

| 你的结论 | 落到结构上 | 关键差别 |
|---|---|---|
| 计划年年不同、任务可反复 | **结论不挂任务，挂检查项**；任务只是执行记录 | 我上一版把结论挂 `TaskCode`，**错了**，已改 |
| 任务头合并 | `cert_task` + `TaskKind`(`prep`/`onsite`) | 与上一版一致 |
| 准备结果与检查结果不覆盖 | **同一行、两组字段、各有归属**（`PrepState` 组 / `Conclusion` 组）| 靠**字段归属**保证，不靠拆表 |

> **你这个判断是对的**："一个检查项就是证据、疑点、判断"。所以结论行**长在检查项上**——
> 唯一要补的一刀：**一条检查项常含多条条款**（真实报告就是一条款一判定），所以结论行是 **检查项 × 条款**，不是每检查项一行。
> 检查项只有 1 条条款时，效果与"在检查项上加字段"完全一样。

## 一、四层结构

```
① 任务层    cert_task            这次执行（方向 / 计划 / 状态 / 进度）—— 可反复执行
                │ 1:N
② 执行层    cert_task_item       任务 × 检查项（仅执行状态：跑没跑、证据够不够）
                │
③ 结论层    cert_check_result    ★ 检查项 × 条款（准备组 + 检查组字段同行）—— 结论的家
                │
④ 资产层    cert_evidence        证据（挂检查项，CapturedIn 区分谁采的，跨任务复用）
            cert_pq_skill/_task/_result    公共查询（独立模块）
            cert_point           疑点（多条，带 Origin，两方向各自留痕）
            cert_nc              NC 单（有生命周期，人签发）
            cert_analysis        分析记录（追加型，解决"结果为什么变了"）
```

**为什么这样分**：任务会反复（今年跑、明年再跑、补证据再跑），**结果要稳定可查**（打开检查项就看到当前结论），**证据是资产**（一次采到到处可用），**历史靠追加表**（不靠给结果留存多份）。

## 二、表清单（11 张）

> 全表：`Code` 业务键（⛔ 不用 `Id` 关联）、`IsValid`、`IsDeleted`、审计四列、`Sort`、`COLLATE=utf8mb4_general_ci`。
> **不建表**：检查项本身 = `cert_audit_plan_detail` 一行（43 号 D1）。

### 2.1 `cert_task`（任务 —— 合并 + `TaskKind`）

| 字段 | 说明 |
|---|---|
| `Code` / `TaskNo` | 业务键 / 展示号（`P-20261030-01`、`C-20261030-01`，自动）|
| **`TaskKind`** | `prep` 认证准备 / `onsite` 认证检查 |
| `PlanCode` | 所属计划（**不强求唯一**：同一计划可再开一轮，按 `TaskNo` 区分）|
| `EnterpriseCode` / `StageCode` | 快照，便于列表筛选 |
| `AuditType` | 仅 onsite：`initial` / `surveillance` / `recert` / `special`（范围变更）|
| `AuditDateFrom` / `AuditDateTo` / `TeamJson` | 仅 onsite：日期 / 审核组 |
| `Status` | `pending` / `running` / `paused` / `done` / `partial` / `failed` |
| `ItemTotal` / `ItemDone` / `ItemFailed` | 进度（检查项口径）|
| `PromptCode` / `PromptVersion` | 本次用的提示词（**结果可追溯**）|
| `GuardJson` | 启动前校验快照（计划唯一 / 有条款 / 有部门 / 属性覆盖 / 证据源）|
| `Message` | 汇总（⛔ 不许静默跳过）|
| `StartedAt` / `FinishedAt` | |

> **队列**：`QueueStatus` 是映射自 `yzh_queue` 的虚字段，**⛔ 不在本表双写队列内部状态**。

### 2.2 `cert_task_item`（任务 × 检查项 —— 只有执行状态）

| 字段 | 说明 |
|---|---|
| `Code` / `TaskCode` / `CheckItemCode` | **唯一键 `TaskCode + CheckItemCode`**（`CheckItemCode` = `cert_audit_plan_detail.Code`）|
| `Status` | `waiting` / `ready` / `analyzing` / `analyzed` / `reviewed` / `failed` |
| `EvidenceState` | `none` / `partial` / `ready`（**按方向算**：准备看资料证据，检查看现场证据）|
| **`AnalysisState`** | `none` / `done` / `stale`（证据变了就 `stale`）|
| `AnalyzeCount` / `LastAnalyzedAt` | 反复执行计数 |
| `EvidenceCount` | 本方向可见证据条数 |
| **`RunMode`** | `full` / `incremental` / `selective`（重跑模式）|
| **`SkipLocked`** | 0/1。`RunMode=incremental` 时，1 = 跳过 `IsLocked=1` 的结论项（**LLM 节流开关**）|
| **`RerunState`** | `none` / `suggested` / `forced`——证据变更触发的"建议重跑"状态 |
| `RerunReason` | `varchar(500)`——原因列表 JSON：`[{evidence_code, kind, old_md5, new_md5, snippet}]` |
| `RerunTriggeredAt` / `RerunTriggeredBy` | 触发时间 / 来源（`evidence_change` / `doc_reupload` / `manual`）|
| `Message` | 失败原因（必填当 `failed`）|

> ⛔ **不存任何结论字段**（结论在 `cert_check_result`）。⛔ **不复制条款与部门**（读时 join 计划明细）。
> ★ 保留它的唯一理由：**进度与"跑没跑过"是 per (任务, 检查项) 的**，且失败的项没有结论行 —— 靠结论表反推进度会把失败项算成没跑。

### 2.3 ★ `cert_check_result`（检查项 × 条款 —— 结论的家）

| 字段 | 归属 | 说明 |
|---|---|---|
| `Code` / `CheckItemCode` / `ClauseCode` | — | **唯一键 `CheckItemCode + ClauseCode`**；`StandardCode` / `ClauseNumber` 冗余便于展示 |
| **`PrepState`** | **prep** | `found` / `partial` / `missing` / `unknown` / `na` |
| `MissingKindsJson` / `ConflictsJson` | **prep** | 缺的材料 / 跨文档矛盾 |
| `IsMandatory` | **prep** | 是否必须执行（检查可覆盖，写 `IsMandatoryBy`）|
| `VerifyLevel` | **prep** | `doc` / `remote` / `onsite` / `test`（验到什么程度）|
| **`PrepNcHint`** | **prep** | 准备期"建议开 NC 吗"+ 理由（**只是给现场的建议**）|
| **`Conclusion`** | **check** | `pass` / `ofi` / `nc` / `na`（人填为最终）|
| **`NcSuggested`** | **check** | 检查期是否建议开 NC（≠ 已开 NC，见 `cert_nc`）|
| `Severity` / `SeveritySource` | **check** | 实际严重程度 + 来源（`attr` / `ai` / `manual`）|
| `SeverityBaseline` | 条款属性 | 条款基线严重程度（prep 可校正；检查判偏离时以 `Severity` 为准）|
| `Reason` | 共用 | 判定依据摘要（**必填**）|
| `ConclusionBy` / `ConclusionAt` | check | 留痕 |
| `RollupTo` | — | 该行是否参与检查项汇总（`na` 不参与）|
| `ResultStale` / `StaleReason` | — | **计划被编辑后置 1**（条款组/部门变了 ⇒ 结论须重跑）|

> ★ **一行两段，正是你要的"看准备看准备、看检查看检查"**：准备视图只读写 `PrepState` 组，检查视图只读写 `Conclusion` 组。
> **重跑准备不清检查结论，重跑检查不清准备结论**（字段归属见 §五）。

### 2.4 `cert_evidence`（证据 —— 挂检查项，跨任务共享）

| 字段 | 说明 |
|---|---|
| `Code` / `CheckItemCode` / `ClauseCode` | 挂检查项（`ClauseCode` 可空 = 检查项级）|
| **`CapturedIn`** | **`prep` / `onsite` / `manual` / `doc` / `pq`**（谁提供的）|
| `CapturedTaskCode` | 采集它的任务（可空 = 导入/手工）|
| `EvidenceKind` | `doc_slice` / `pq_result` / `lead` / `onsite_media` / `interview` / `sample` / `manual` |
| `SourceCode` / `SourceName` | `FileCode` / `PqResultCode` / 人工自填 |
| `Anchor` / `Snippet` / `Confidence` | 锚点 / 原文 / 置信度 |
| **`ContentMD5`** | 证据内容 MD5（`Snippet` 或 `LlmSummary` 的 MD5），**用于检测证据是否被修改** |
| **`LlmSummary`** | LLM 可消费的标准化文本（OCR 结果 / 转录文本 / 清洗后原文）；**这是实际喂给模型的内容** |
| `TokenEstimate` | `LlmSummary` 的预估 token 数（聚合截断用）|
| `MediaKind` / `DurationSec` / `TranscriptText` | 现场媒体：类型 / 时长 / **转录文本** |
| `AttachmentsJson` | 附件（图片 / PDF 路径数组）|
| `CapturedAt` / `CapturedPlace` / `PresentPersons` | 取证时间 / 地点 / 在场人 |
| `Status` | `collected` / `confirmed` / `dropped`（**dropped 不进分析输入**）|
| **`PrevContentMD5`** | 上一次的内容 MD5（修改检测：与新算的 MD5 比，不同则触发影响分析）|

> **内容变更检测**：`PrevContentMD5` ≠ 新算 MD5 ⇒ 证据内容被修改 → 触发 §2.9 影响分析，关联任务项置 `RerunState=suggested`。
>
> **不覆盖的实现**：证据**只追加不改写**。准备期证据在检查视图里**照常显示**并标 `prep` 来源；现场若推翻，**新增一条 `onsite`** 把旧的置 `dropped`（带理由）—— 两条都在，历史在。
>
> **MD5 与锁定节流的关系**：重跑任务时，先通过 `ContentMD5` 比对找出"证据未变的检查项"；若某检查项所有证据 MD5 都没变**且**结论 `IsLocked=1`，则该检查项**完全跳过 LLM 调用**——这是节约 LLM 消耗的核心机制。

### 2.5 `cert_pq_skill` / `cert_pq_task` / `cert_pq_result`（公共查询，独立）

| 表 | 关键字段 |
|---|---|
| `cert_pq_skill` | `Code` / `SkillName` / `Category` / `AccessMode`(`api`/`web`/`manual`) / `ParamsSchema` / `SummaryTemplate` / `DefaultClauseCodes` / `CacheTtlHours` |
| `cert_pq_task` | `Code` / `SkillCode` / `EnterpriseCode` / `RowTotal` / `RowDone` / **`SourceTaskCode`** / **`SourceTaskKind`**（可空 = 独立使用）/ `Status` |
| `cert_pq_result` | `Code` / `TaskCode` / `RowKey` / `ParamsJson` / `ResultJson` / `Summary` / `Status`(`success`/`empty`/`failed`/`blocked`) / `QueriedAt` / `ExpireAt` |

> 查询结果**不当结论用**，只作线索 ⇒ 经 `cert_evidence`（`EvidenceKind=pq_result`）挂检查项；一条结果可挂多个检查项。

### 2.6 `cert_point`（疑点 —— 多条、带方向、可销账）

| 字段 | 说明 |
|---|---|
| `Code` / `CheckItemCode` / `ClauseCode` / `DeptCode` | 归属（`DeptCode` 可空）|
| **`Origin`** | **`prep` / `onsite` / `pq` / `manual`** —— 两方向各自的疑点都留，**互不清除** |
| `PointKind` | `communicate` / `observe` / `interview` / `verify` |
| `Mode` | `remote` / `onsite` |
| `Reason` / `Action` / `Question` / `TargetRole` / `EstMinutes` / `Priority` | |
| `Fingerprint` | 重跑幂等键（同指纹不重复插入）|
| `Status` | `open` / `resolved` / `dropped` + 理由 + 留痕 |

### 2.7 `cert_nc`（NC 单 —— 独立生命周期）

| 字段 | 说明 |
|---|---|
| `NcNo` | 编号（报告引用）|
| `CheckItemCode` / `ClauseCode` / `ClauseCodes` | 来源（`ClauseCodes` 支持同根因跨条款合并）|
| `Severity` | `major` / `minor` |
| `FactDesc` / `RequirementRef` | 不符合事实 / 违反条款原文 |
| `CorrectiveReq` / `DueDate` / `Responsible` | 整改要求 / 期限 / 责任人 |

| `Origin` | `ai_suggest` / `manual`（系统只建议，**人签发**）|
| `CreatedInTaskCode` | 哪次检查开的（跨年可比较）|
| `CloseEvidenceJson` / `ClosedAt` / `ClosedBy` | 关闭留痕 |

### 2.8 `cert_analysis`（分析记录 —— 追加型）

| 字段 | 说明 |
|---|---|
| `TaskCode` / `TaskItemCode` / `TaskKind` | 哪次执行 |
| **`EvidenceFingerprint`** | 本次输入的证据指纹 = `MD5(GROUP_CONCAT(CONCAT(e.Code, ':', e.ContentMD5, ':', e.Status) ORDER BY e.Code ASC))` |
| `LockedSkippedCount` | 本次跳过的已锁定结论条数（**LLM 节流指标**）|
| `PromptCode` / `PromptVersion` / `ModelName` | |
| `ResultSummaryJson` | 产出摘要（几条疑点 / 几条 NC 建议 / PrepState 分布 / Conclusion 分布）|
| `CreatedAt` | |

> **证据指纹算法**：每条证据取 `Code + ContentMD5 + Status`，按 Code 排序拼接后取 MD5。任一证据内容变化（MD5 变）或状态变（collected→dropped）都会导致指纹变化 ⇒ 触发 stale。
>
> **LockedSkippedCount**：记录本次分析因 `IsLocked=1` 而跳过的结论条数。数值越大说明 LLM 节流效果越明显——这是"锁定节约 LLM 消耗"的可观测指标。
>
> **这是"结果可以改变"的唯一历史入口**：结论行只存当前值，改过几次都在这里。
> 审核员问"上次 5 个疑点这次 3 个为什么" → 对比两条记录的指纹与摘要。

### 2.9 `cert_impact_log`（影响分析日志 —— 证据变更→检查项影响追踪）

| 字段 | 说明 |
|---|---|
| `Code` | 业务键 |
| `TriggerKind` | `doc_reupload` / `evidence_change` / `manual` |
| `TriggerSource` | 触发来源：`FileCode`（文档重传）或 `EvidenceCode`（证据修改）或人工操作 Code |
| `OldMD5` / `NewMD5` | 内容变更前后的 MD5（文档级或证据级，可为空）|
| `AffectedCheckItemCount` | 受影响的检查项数量 |
| `AffectedTaskItemCount` | 受影响的任务项数量 |
| `AffectedItemsJson` | 受影响的项清单（`[{CheckItemCode, TaskItemCode, Action, LockedState}, ...]`）|
| `CreatedBy` / `CreatedAt` | 操作人与时间 |

> **这是"证据变了影响哪些检查项"的审计日志**——每次文档重传或证据修改触发影响分析时写一条。前端"建议重跑 N 个检查项"弹窗的数据来源。

## 三、关系图

```
cert_audit_plan (1) ──< cert_audit_plan_detail (N)      ← 计划明细 = 检查项（唯一身份，属于计划）
                                   │ Code
        ┌──────────────────────────┼───────────────────────────┐
        │                          │                           │
cert_task (1)                      │                   cert_check_result (N)  ★结论的家
  TaskKind prep/onsite             │                     CheckItemCode + ClauseCode
  PlanCode / Status / 进度         │                     PrepState 组 | Conclusion 组
        │ 1:N                      │                           │ IsLocked 🔒
        ▼                          │                           │
cert_task_item (N) ────────────────┘                    cert_evidence (N)
  只有执行状态 + RerunState                              CapturedIn / CapturedTaskCode
  RunMode SkipLocked                                      ContentMD5 / LlmSummary
        │ 1:N                                              PrevContentMD5
        ▼                                                    │
cert_analysis (N)  ← 每次分析一条（指纹 + 跳过计数 + 摘要）  │
                                                      cert_point (N)  Origin=prep/onsite

```

> **`cert_impact_log`** 不在主链上——它是旁路审计证据变更影响范围。每次 MD5 变化时写入，前端据此生成"建议重跑 N 项"提示。

## 四、为什么结论按「检查项 × 条款」而不是每检查项一行

| 证据 | 说明 |
|---|---|
| 真实报告 | 判定列与条款同列：`N 8.3`、`合格 8.5.2` —— **一条款一判定** |
| 检查项定义 | 检查项 = 条款(1..N) × 部门(1..N)，**多条款是常态**（43 号 D1）|
| 你的需求 | 同一检查项里"2 条过、1 条不过"，疑点与 NC 必须落在**那一条**上 |

⇒ 一行 = 一个（检查项, 条款）。单条款检查项时，与"在检查项上加字段"完全等价。

**检查项级汇总不存列**：列表页要显示"这项整体结果"时按规则现算 —— 有 `nc` ⇒ `nc`；否则有 `ofi` ⇒ `ofi`；否则 `na` 多于 `pass` ⇒ `na`；否则 `pass`。人可覆盖（覆盖值放 `cert_task_item` 之外的视图层缓存，**不进结论行**，避免第三处真相）。

## 五、两个方向互不覆盖的三条保证

| # | 保证 | 机制 |
|:--:|---|---|
| **G1** | **字段归属**：prep 只写 prep 组，check 只写 check 组 | `PrepState` / `PrepNcHint` / `MissingKinds` / `Conflicts` / `IsMandatory` / `VerifyLevel` 归 prep；`Conclusion` / `NcSuggested` / `Severity` 归 check。**重跑各自方向只更新自己那组** |
| **G2** | **易撞车字段一律分列** | `PrepNcHint`（准备建议开不开）vs `NcSuggested`（检查判定）；`SeverityBaseline`（条款基线）vs `Severity`（实际判定）|
| **G3** | **证据与疑点只追加** | 证据 `CapturedIn` + `dropped` 而不删；疑点 `Origin` 区分方向、`Fingerprint` 幂等 |
| **G4** | **锁定保护：已确认结论不因重跑被覆盖 + LLM 节流** | `IsLocked=1` 的行，重跑跳过；`cert_analysis.LockedSkippedCount` 计数；审核员可主动解锁 |
| **G5** | **证据链变更→影响追踪→建议重跑** | 证据 `ContentMD5` 变化时触发影响分析，写 `cert_impact_log`，关联任务项置 `RerunState=suggested` 并记录变化原因 |

**影响分析流程**（证据变更触发）：

```
文档重传 / 证据修改
  │
  ├─ 1. 计算新 MD5 → 与 PrevContentMD5 比对
  │   └─ 相同 → 无影响，结束
  │   └─ 不同 → 继续
  │
  ├─ 2. 查找关联：cert_evidence.CheckItemCode → cert_task_item → cert_check_result
  │   └─ 过滤全部已锁定的项（IsLocked=1 且无未锁定条款）→ 跳过（LLM 节流）
  │
  ├─ 3. 更新受影响的 task_item：
  │   ├─ AnalysisState = 'stale'
  │   ├─ RerunState = 'suggested'
  │   ├─ RerunReason = [{evidence_code, kind:'updated', old_md5, new_md5, snippet}]
  │   └─ RerunTriggeredBy = 'doc_reupload' / 'evidence_change'
  │
  ├─ 4. 写 cert_impact_log：
  │   └─ TriggerSource = FileCode / EvidenceCode
  │   └─ OldMD5 / NewMD5（内容对比值）
  │   └─ AffectedItemsJson = [{CheckItemCode, Action, LockedState}]
  │
  └─ 5. 更新 evidence 自身：PrevContentMD5 = 当前 MD5（下次对比基准）
```

**重跑任务判定流程**（含锁定 + MD5 双重检查）：

```
重跑触发（RerunState=suggested 的项 / 手动触发）
  │
  ├─ 确定 RunMode（cert_task_item.RunMode）
  │   ├─ full → 所有 RerunState≠none 的检查项
  │   ├─ incremental（默认）→ 仅 SkipLocked=1 的项
  │   └─ selective → 审核员手动勾选的检查项
  │
  └─ 遍历目标检查项
      ├─ 二次检查：ContentMD5 对比 cert_analysis 上次指纹
      │   └─ 证据 MD5 与上次完全一致 → 跳过（无实际变化）
      │   └─ 有变化 → 继续
      ├─ 所有条款结论 IsLocked=1 → 完全跳过 LLM（节流）
      ├─ 部分条款锁定 → 只重跑未锁定条款
      └─ 全部未锁定 → 全部重跑
  └─ cert_analysis 追加记录（LockedSkippedCount = 节流计数）
```

**视图怎么不同**（你说的第 3 条）：

| 视图 | 读什么 | 写什么 |
|---|---|---|
| **认证准备** | `PrepState` 组 + `CapturedIn∈{prep,doc,pq}` 的证据 + `Origin=prep` 的疑点 | 只写 prep 组 |
| **认证检查** | `Conclusion` 组 + **全部证据（prep 的标来源）+ `Origin` 全部疑点** | 只写 check 组 + 新增 `onsite` 证据 |

> 检查视图**故意显示** prep 证据与 prep 疑点 —— 这是**复用**（43 号 §8.6），不是覆盖。页面用来源标签区分，不隐藏。

## 六、计划年年不同：模型靠什么不串

| 事实 | 后果 | 模型怎么接 |
|---|---|---|
| 二阶段 = **全条款覆盖**；后续 = **抽查**；也可能 **范围变更** | 检查项数量差异极大（全量 88–603 条 vs 抽查 20 条）| **计划 = 审计轮次的快照**：每轮新计划 ⇒ 新明细行 ⇒ **新结论行**。旧计划与旧结论原样留着 = 去年审核记录 |
| 任务可反复执行 | 同一检查项会被跑多次 | `cert_task` 可多行 / 同计划；`cert_task_item` 记执行；`cert_analysis` 记每次；结论行**只存当前值** |
| 抽查要挑"高风险条款" | 需要看上年结果 | 建议计划表补 4 列（见下），据 `AuditYear` + 上年结论/NC 打分选题 |

**计划表建议补 4 列**（`cert_audit_plan`，⛔ 不加结果字段）：

| 列 | 值 | 用途 |
|---|---|---|
| `PlanKind` | `stage1` / `stage2` / `surveillance` / `recert` / `special` | 区分二阶段 / 监督 / 再认证 / 范围变更 |
| `CoverageMode` | `full` / `sample` / `scope_change` | 全量 or 抽查 |
| `AuditYear` | 2026… | 跨年比较与抽查依据 |
| `PreviousPlanCode` | 可空 | 上一年计划（抽查取上年 NC 条款）|

> **不建"年度表"**：年份是计划属性，不是实体。

## 七、易错点（按踩坑代价排）

| # | 坑 | 为什么会错 | 正确 |
|:--:|---|---|---|
| **E1** | 结论挂 `TaskCode` | 任务可反复执行 ⇒ 同一结论出现多行，或重跑丢历史 | **挂检查项（× 条款）**；历史放 `cert_analysis` |
| **E2** | prep 与 check 写同一列（`Severity` / `NcSuggested`）| 后跑的清掉先跑的 ⇒ 你说的"不该覆盖"就破了 | **分列**（G2）|
| **E3** | 一个检查项只留一行结论 | 多条款检查项只能留一条 ⇒ 疑点/NC 落不到具体条款 | 按 `ClauseCode` 拆行 |
| **E4** | 计划编辑不清旧结论 | 条款删了、结论还在 ⇒ 报告里出现幽灵条款 | 明细变更即置 `ResultStale=1`，页面标"计划已变更 · 结果需重跑" |
| **E5** | 把疑点/NC 塞结果表 JSON | 无法筛"未销账疑点"、无法统计 NC 分布 | 独立表（P3）|
| **E6** | 重跑任务未跳过已锁定项 | 审核员手工确认的结论被静默覆盖，且无任何报错——最难查的一类 bug | `RunMode=incremental` 时必须检查 `IsLocked` |

## 八、三条分表判据（可拿去检验以后任何新表）

| # | 判据 | 应用 |
|:--:|---|---|
| **P1** | **"会重复的"与"不会重复的"分开** | 任务会重复 ⇒ `cert_task`；结论不该重复 ⇒ 挂检查项 |
| **P2** | **字段差 > 50% 才分表** | 任务头 14 列只差 4 列 ⇒ **合并 + `TaskKind`**；`PrepState` 组与 `Conclusion` 组同属一结论 ⇒ 同表 |
| **P3** | **一条能有多行的必须独立表** | 疑点、NC、证据、结论（× 条款）|

## 九、落地顺序（先做认证检查方向）

| 步 | 建什么 | 出口判据 |
|:--:|---|---|
| **1** | `cert_task` + `cert_task_item` + `cert_check_result` | 一个任务挂 8 个检查项 × N 条款，进度算得对；`PrepState` 与 `Conclusion` 互不清 |
| **2** | `cert_evidence`（含现场媒体与转录）| 人工证据可挂可传图；`CapturedIn` 正确；`dropped` 不进输入 |
| **3** | `cert_point` + `cert_analysis` | 分析产出疑点；再分析只追加、不覆盖；`Fingerprint` 去重 |
| **4** | `cert_nc` | NC 建议 → 人签发 → 关闭，状态走得通 |
| **5** | `cert_pq_*` | 一条查询结果能挂多个检查项 |

> 先 onsite ⇒ `TaskKind=onsite`；prep 随后接入，**表不改**（合并任务头的直接收益）。
