# 两端职责边界：后台 vs 专家端（V1）

> 2026-10-26 ｜ V2 设计文档 14
> 起因：用户纠正 —— 「**组织、部门不是在后台管理中建立的，是在专家端系统应该维护的；检查单计划、入场计划也是针对专家端的设计；后台建立的是标准、条款、条款属性定义、机构检查证据提示词生成、不同阶段针对条款的检查标准**」。

## 一、边界一句话

> **后台 = 平台方给所有机构准备"弹药"；专家端 = 某个机构拿弹药打自己那场仗。**

```
┌──────────────── 管理端 cert-admin（平台方 / 映智汇）────────────────┐
│  标准 · 条款 · 条款属性 · 阶段检查标准 · 机构关联 · 规则 · 提示词      │
│  ──────────────────────────────────────────────────────────────  │
│  产出：一套"任何机构、任何企业都能用"的通用资产                       │
└──────────────────────────────┬─────────────────────────────────┘
                               │ 被引用（只读）
┌──────────────────────────────▼─────────────────────────────────┐
│  专家端 cert-auditor（机构方 / 审核员工作区）                       │
│  企业 · 部门 · 审核组 · 审核计划 · 检查单 · 入场计划 · 证据 · NC      │
│  ──────────────────────────────────────────────────────────────  │
│  产出：某一家企业的审核底稿与结论                                    │
└────────────────────────────────────────────────────────────────┘
```

**判据（一句话就能判）**：
> 这个东西**换一家企业还用得上**吗？
> 用得上 ⇒ **后台**；只对这家企业成立 ⇒ **专家端**。

- 条款 7.1.5 换企业还用得上 ⇒ 后台
- 「A 公司有 7 个部门」换企业就没意义 ⇒ 专家端
- 「中安质环的证据写成三列表格」换企业还用得上（同机构内）⇒ 后台（机构级）
- 「A 公司采购部由李强审」⇒ 专家端

## 四、同一个维度的两层（最容易搞混的地方）

**同一个概念，在两端各有一层。** 这不是重复，是"定义 vs 实例"。

### 4.1 已有的正确范式：阶段

| 层 | 表 | 端 | 含义 |
|---|---|:--:|---|
| 定义 | `cert_cert_stage` | 后台 | 有哪几个阶段（`S1`/`S2`/`SV`/`RC`…） |
| 机构关联 | `cert_org_stage` | 后台 | 某机构用哪几个阶段 |
| **实例** | `cert_enterprise_stage` | **专家端** | **A 公司现在处于 S2** |

⇒ **阶段已经是对的**，照着这个模式做条款、证据、部门就行。

### 4.2 照抄到另外三组

| 概念 | 后台（定义） | 专家端（实例） |
|---|---|---|
| **阶段 × 条款** | `cert_iso_clause_stage`（该阶段**通用**查什么、能不能开 NC） | `cert_check_item`（A 公司 S2 实际查什么） |
| **条款 × 部门** | `cert_org_clause_dept_template`（该机构**习惯**把哪条放哪个部门） | `cert_enterprise_dept_clause`（A 公司实际归属） |
| **证据** | `cert_org_evidence_style` + 提示词（**写成什么形状**） | `cert_check_evidence`（**这次写了什么**） |

> ★ 一句话：**后台定"规则和形状"，专家端定"这一次的具体值"。**

### 4.3 三处容易放错的东西

| 东西 | 别放错 | 正确位置 | 理由 |
|---|---|---|---|
| 企业部门清单 | ❌ 后台 | ✅ 专家端 | 换企业就变 |
| 审核组 | ❌ 后台 | ✅ 专家端 | 换企业就变（机构级只存人员池） |
| 提示词模板 | ✅ 后台 | ✅ 后台 | 换企业不变（同机构内） |
| 条款合并**习惯** | ⚠️ 后台可存 | ✅ 生效在专家端 | 后台存"这家机构习惯合并哪几组"，专家端可推翻 |
| 某次合并**结果** | ❌ 后台 | ✅ 专家端 | 只在本次项目成立 |

## 六、部门为什么必须在专家端（一个历史教训）

`scripts/db/rebuild_menu_and_drop_department.sql`（2026-09-11）明确写着：

```
-- 菜单重构 + 删除 Sys_Department 表
-- 2. 删除 Sys_Department 表
-- 3. 删除部门管理相关前端文件引用
```

⇒ **V1 曾经有过一张 `Sys_Department`，后来被删了。**

原因不难推断：那张表是**审核机构自己的内部部门**（跟 `Sys_Organization` 配套），而审核业务真正需要的是**受审核企业的部门**。两者名字一样、语义完全不同，混在一起必然出错，所以当时干脆删了。

**这次不能再犯同一个错**：
- 机构内部部门 ⇒ 已经不需要（`Sys_Organization` 够用）
- **企业部门 ⇒ 必须建，且只在专家端**

> ★ 判据：**看到"部门"两个字，先问"谁的部门"**。机构的部门是 HR 概念，企业的部门是审核对象。

## 七、提示词的两段式

你说的「机构检查证据提示词生成」在后台，这个定位要拆成两段才完整：

```
后台（生成段）                          专家端（消费段）
─────────────────────────            ─────────────────────────
cert_org_evidence_style              取：企业画像 + 部门 + 检查项
  OutputForm / RequiredElements         + 已匹配到的证据
  WordingRules / SeverityMode                  ↓
        ↓                              套模板 + 填值
wf_prompt_template                      ↓
  OrgCode + PromptType                产出：审核记录文本
  + StandardCode + Version               ↓
  + Template（含占位符）                人工确认/修改 → 落 cert_check_evidence
```

**边界**：
- 后台**只产模板**，不产任何一条真实证据
- 专家端**只消费**，不修改模板（要改走后台，有版本号）
- `Version` + `LastTestResult` 已有 ⇒ **改模板可追溯、可试跑**

⇒ 这正好回答你 12 号里提的"不同机构证据风格不同"：**风格是后台的配置项，不是专家端的自由发挥。**

## 九、落地顺序（不写码，只排依赖）

```
第一步  后台：条款属性 4 张表 + 菜单          ← 不依赖任何专家端东西，可先做
```

**关键**：前 3 步是后台，**不依赖企业部门**；第 4 步之后才需要。所以"部门阻塞"只阻塞后半段，不影响现在开工。

## 十、坑（放最后）

1. **`/organization` 名字有歧义** —— 专家端的「组织与成员」是**机构内部的人**，不是企业部门。做菜单时建议改名为「**机构成员**」，否则后面一定有人搞混。
2. **`Sys_Department` 已被删除**（2026-09-11）—— 不要以为"表不见了是没建"，是**主动删的**。重建时必须换名字（`cert_enterprise_dept`），不能叫回 `Sys_Department`。
3. **`cert_certification_body` 只有 1 行** —— 多机构场景还没真正跑过。`cert_org_evidence_style` 按机构配置前，得先确认多机构数据怎么进。
4. **提示词菜单现在叫「文档语义规则」** —— 它服务的是"文档填写"，不是"审核证据"。硬塞进去会让语义混乱，**建议新增独立菜单**，不要复用。
