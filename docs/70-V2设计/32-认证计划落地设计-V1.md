## 零、为什么认证计划必须先于准备与报告

用户给定了计划的四个存在理由，缺任一都会让后续环节塌掉：

1. **不同企业认证的标准不一样** → 计划按"企业 × 标准"存在，每个标准独立一份。
2. **不同企业适用的条款不一样** → 计划只能由"适用性裁剪结果"驱动，剔除不适用条款。
3. **企业可能多体系（多标准）** → 一次现场、一个审核组，但结论与报告必须按标准拆分。
4. **需要条款的合并与拆分** → 否则计划项既对不上部门矩阵（漏查），也对不上真实报告（条款×部门=1.33×）。

> 计划的本质是：**把"适用条款集"变成"可执行的检查任务表"，并为后续证据/NC/报告预留标准→条款→部门的挂载骨架。**

## 一、认证计划还有哪些未决问题（问题清单）

> 这一节是设计的核心：先把问题列清，再逐个给解法。

### 问题 1：粒度问题 —— 计划项 ≠ 条款
- 真实报告实测 **条款×部门 = 1.33×**（89 检查项 ÷ 67 条款），同一条款最多被问 10 次（5 部门 × 2 体系）。
- 还有 **6 类无条款号检查项**（资质验证/国抽/申投诉/事故/法规/最高管访谈，见 README 结论 14）。
- **解法**：计划项是 `条款 × 部门（× 方面）`，`ClauseCode` **可空**；用 `ItemKind` 区分 clause 类与 6 类无条款类。

### 问题 2：合并与拆分问题（用户重点强调）
- **拆分**：一条款在企业多个部门负责的过程里都要查 → 必须拆成多项。拆分驱动 = 条款 `Process` × 企业部门 `ResponsibleProcesses` 取交集（部门矩阵）。
- **合并（定义级）**：多个条款若证据/材料重合（如 5.3 职责 + 5.4 沟通都只问"管理者代表"一次），应合成一项以减项减时。**定义级合并改变清单与工时，在计划阶段定**（29 号 §2.4）。
- **记录级合并**：几项共用一段记录写法，只影响记录阶段，**不影响计划**。
- **解法**：计划项用 `ClauseCodes`（JSON 数组）表达"本项覆盖哪些条款"。
  - 合：一项多码（如 `[5.3, 5.4]`），`EstMinutes` 取并集而非相加。
  - 拆：同码出现在多项（不同 `DeptCode`），天然支持。
  - 无需单独的合并组表（保持简单）。

### 问题 3：多体系问题
- 一次现场、一个审核组、N 套条款集合与结论；排程可合并（同一部门一次访完多标准项），但 NC/报告必须按标准拆分（30 号 §8.6）。
- **解法**：**计划按标准一份**（`StandardCode` 必填 GUID）；多标准共享一个 `SessionCode`（排在同一次现场），团队/日期相同；各项通过所属计划带 `StandardCode`，NC/报告按标准聚合。

### 问题 4：适用驱动问题
- 计划只能含 `applicable` 与 `pending` 条款，剔除 `not_applicable`（29 号 §1 / 30 号 §4.1）。`pending` 仍进计划、显眼标记、不阻断。
- **解法**：计划生成服务以"企业 × 标准 × 适用条款清单"为输入；适用性由后续认证准备产出，本期**只消费不生产**。

### 问题 5：时间预算问题
- 现场预算 = 阶段规定天数 × 每天有效工时（扣开场/末次/赶路），硬约束；Σ 任务时长 > 预算必须砍并留理由（30 号 §8.1）。
- **解法**：计划头带 `BudgetDays` / `BudgetMinutesPerDay`；每项带 `EstMinutes`；生成时校验，超限拒绝确认并给出砍单顺序（低风险→可远程补证→抽样可减）。

### 问题 6：部门矩阵问题（拆分引擎）
- 拆分靠"条款 `Process`（受控词表）× 企业部门 `ResponsibleProcesses`"取交集（24 号 §3.6）。
- **解法**：部门与过程归属由"正在创建"的企业部门体系提供，计划只消费 `DeptCode` / `ResponsibleProcesses`，**不建主数据**。

### 问题 7：报告挂载问题
- 报告必须能按 `标准 → 条款 → 部门` 挂 NC，且每条 NC 回指证据锚点。
- **解法**：计划项天然暴露 `StandardCode` / `ClauseCodes` / `DeptCode` / `ItemKind` —— 这四项就是报告挂载的骨架。后续 NC 挂到计划项上，报告按标准聚合即可，无需计划反向感知报告。

## 二、数据模型（设计级，本期不写 DDL）

> 仅 2 张表。严守通用纪律：`StandardCode` 用 GUID 口径；无 `Enable`（用 `IsValid`）；排序列 `Sort`；状态列 `Status`；审计列 `CreateBy/CreateTime/...`（`CreateBy`=`Sys_User.Code`，时间 `DateTime.Now`）；字段 PascalCase；改/查走 `Code` 业务键。

### 2.1 `cert_audit_plan` 计划头

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) PK | GUID 业务键 |
| `EnterpriseCode` | varchar(36) | 企业（消费企业主数据，不建） |
| `StageCode` | varchar(36) | 阶段（cert_cert_stage） |
| `StandardCode` | varchar(36) | **必填 GUID**，每标准一份计划 |
| `SessionCode` | varchar(50) | **可空**，多标准共享同一次现场；单标准可空 |
| `PlanName` | varchar(100) | |
| `TeamCode` | varchar(36) | 审核组（消费创建中的团队，不建） |
| `BudgetDays` | int | 阶段规定天数（硬约束） |
| `BudgetMinutesPerDay` | int | 有效工时 |
| `Status` | varchar(20) | `draft` / `confirmed` |
| `IsValid` / `Sort` / 审计列 | | |

uk：`(EnterpriseCode, StageCode, StandardCode, SessionCode)`。

### 2.2 `cert_audit_plan_item` 检查任务项（计划核心产出）

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) PK | |
| `PlanCode` | varchar(36) | 关联计划头（→ StandardCode） |
| `ClauseCodes` | text(json) | **数组**：本项覆盖的条款码；`ItemKind=clause` 时非空；合并=多码，拆分=同码跨多项 |
| `ItemKind` | varchar(20) | `clause` / `qualification` / `sampling` / `complaint` / `accident` / `regulatory` / `interview`（6 类无条款，ClauseCodes 为空） |
| `DeptCode` | varchar(50) | 检查部门（消费企业部门，不建）；拆分驱动的结果 |
| `TargetRole` | varchar(50) | 沟通/访谈对象角色（不写人名） |
| `ProcessCode` | varchar(50) | 该部门内的过程（受控词表） |
| `PointKind` | varchar(20) | `communicate` / `observe` / `interview` / `verify`（疑点四分类，来自准备检查产出，本期消费） |
| `Mode` | varchar(10) | `remote` / `onsite` |
| `Action` | text | 看什么/问什么/抽几份 |
| `Question` | text | 访谈提纲 |
| `EstMinutes` | int | 预估时长（时间预算用） |
| `AuditorCode` | varchar(36) | 分工（消费团队人员，不建） |
| `Priority` | varchar(10) | `high`/`medium`/`low` |
| `IsMandatory` | tinyint | 法定必查（内审/管评/投诉/灭菌确认等） |
| `SamplingNote` | varchar(200) | 抽样定量（台账抽几台/记录抽几月） |
| `MergeNote` | varchar(200) | 定义级合并理由（哪些条款合、为何合） |
| `Status` / `Sort` / 审计列 | | |

uk：`(PlanCode, Code)`。

> **合并/拆分落点小结**：`ClauseCodes` 数组一处解决双向（合=多项一码；拆=一码多项）；`DeptCode` 承载拆分结果；`MergeNote` 记录合并理由以便复核。

## 三、生成逻辑（计划编排服务，设计级）

```
PlanBuilderService.Build(enterpriseCode, standardCode, stageCode):
  1. 取适用条款集 = cert_clause_applicability(enterprise, standard) 中 applicable + pending
  2. 逐条款 × 部门矩阵（条款.Process ∩ 部门.ResponsibleProcesses）→ 生成拆分项（每部门一项）
  3. 注入 6 类无条款项（qualification/sampling/complaint/accident/regulatory/interview），来自机构/法规定义
  4. 标必查项（IsMandatory）置顶
  5. AI 给"定义级合并建议"（哪些条款可并、并后工时），**人确认**后才合并（写入 ClauseCodes + MergeNote）
  6. 预估时长 = 机构基准 × 抽样量；Σ 校验 ≤ BudgetDays×BudgetMinutesPerDay
  7. 超预算 → 按砍单顺序提示（低风险→可远程→可减抽样），人决定后写 SamplingNote 理由
```

**多标准**：对同一企业同一阶段，循环 standardCode 调一次，多项共享 `SessionCode`；排程时按 `DeptCode` 聚集，跨标准项合并到同一次部门访问。

## 四、与后续环节的接口（只定义契约，不实现）

| 下游 | 计划提供什么 | 挂载方式 |
|---|---|---|
| 认证准备（资料上传/提取/适用性） | 消费其产出的"适用条款集"与"疑点四分类/部门矩阵" | 计划生成以适用性结果 + 部门矩阵为输入 |
| 现场检查/证据 | 计划项清单（去哪个部门、看什么、抽几份） | 证据 `cert_clause_evidence.PlanItemCode` 关联 |
| NC / 判定 | 计划项（标准/条款/部门） | `cert_check_finding.PlanItemCode` 关联 → 报告按标准聚合 |
| 检查报告 | 计划骨架（StandardCode/ClauseCodes/DeptCode/ItemKind） | 报告章节按标准分组，NC 挂到项；**计划不反向感知报告** |

## 五、本期最小可建范围（用于验证模型）

> 用户要求"先解决计划，后续再考虑"。所以本期只做下面三项，且以"能跑出一份任务表"为出口。

1. **建 `cert_audit_plan` + `cert_audit_plan_item` 两张表**（设计见 §二，不实现全量 DDL 之外的表）。
2. **PlanBuilderService（规则版）**：输入"企业 × 标准 × 适用条款 + 部门矩阵"→ 产出拆分任务表 + 必查项 + 预估时长 + 时间预算校验；AI 仅做合并建议，人确认。
3. **专家端计划工作台**：计划头（预算/团队）+ 任务表（`YzhTable`）+ 合并/拆分手动调整 + 时间预算实时校验条。

**验证出口（单标准即可）**：拿一企业一标准，跑出任务表，能解释"为什么这条在现场、那条在远程、归哪个部门"，且总时长 ≤ 预算。
