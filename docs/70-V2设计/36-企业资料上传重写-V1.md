# 企业资料上传重写（V1）

> **一句话结论**：方向成立，而且能一次性砍掉 **一层数据（槽位）+ 一个维度（阶段）+ 一条反推链（机构→标准）**。
> 资料只按「企业」存一层，提取只按「企业 × 标准」存一份 JSON；阶段只活在「计划」里，不碰资料。
>
> **依据**：35 号（L1/L2 提取契约）· 32 号（认证计划）· 24 号（条款属性）
> **前置**：`实施-TODO-认证准备-V1.md` 阶段 1 已完成（iso13485 67 条款 × 9 属性 100%）
> **状态**：**P0 / P1 / P2 / P3 已落地并实测通过**（2026-10-29）；P4–P5 未开工 → 进度见 `实施-TODO-上传重写-V1.md`

## 一、现状：三层数据、两个维度硬绑在一起

### 1.1 现在有三张表在描述「企业有什么文件」

| 表 | 语义 | 键 | 现状行数 |
|---|---|---|---|
| `cert_standard_directory_file`（**企业侧行**） | 「标准目录里的槽位」被企业文件填上了 | 企业×标准×阶段×文件夹×文件名 | 60 |
| `cert_enterprise_original_file` | 企业上传的原始资料 | 企业×**阶段**×文件夹×文件名 | **237** |
| `cert_enterprise_doc_profile` | 文件×标准的画像（标签/作用/字段表格） | 文件×标准×版本（`IsLatest`） | — |

三张表说的是同一件事的三种切法，于是每次上传都要同时维护三份状态。

### 1.2 阶段是硬绑的，而且**实测已经错位**

实测（2026-10-29）：

```
237 份原始资料  →  全部挂在 9777866c… = 第二阶段审核（S2）
唯一 1 张计划   →  挂在     1bc8e72e… = 申请受理（AP），标准 = iso13485 + iso9001
```

**文件的阶段 ≠ 计划的阶段。** 这不是数据脏，而是业务事实：资料是「企业有什么」，阶段是「这次审什么」，两者本来就不是一个维度。硬绑在一起，只能靠人去对齐，一对不齐就全乱。

### 1.3 阶段对资料没有信息量

ISO 17021 的一阶段（文件审）和二阶段（现场审）看的是**同一套体系文件**。企业不会因为进二阶段就换一版质量手册。
⇒ 阶段只能决定「审哪些条款、派谁去、排几天」，决定不了「企业有哪些文件」。

### 1.4 机构是反推来的，不是用户选的

- 前端 `/resources` **一次都没取过机构**（`resources/` 目录内除注释无 `OrgCode`）。
- 机构在后端由「工作区 → `Sys_User.OrgCode` → `OrgPath` 第 2 段 → VirtualOrg」反推（`WorkspaceContextService.cs:158-184`），再据此过滤「机构有哪些标准 / 哪些阶段」（`EnterpriseStageController.cs:264-288`）。
- 用户看到的标准清单其实是「**机构注册过什么**」，不是「**这家企业这次要认证什么**」。

⇒ 这就是要改的根：**从「机构反推」改成「计划直取」**。

### 1.5 现在的提取产物，正是要废弃的那个形态

`cert_enterprise_doc_profile` 存的是「标签集合 / 处理策略 / 一句话作用 / 字段 / 表格」——
这就是用户已经明确否掉的「分组、字段、表格」形态。真正要的是**条款级**：这份文档支撑了哪些条款、条款下有哪些事实、事实的锚点在哪。

## 二、目标：两层数据、一个维度

```
① cert_enterprise_original_file      企业 × 文件            ← 唯一一层，无阶段、无标准
        │  队列（串行）：格式归一 → PDF（预览）+ Markdown（原文）
        ↓
② cert_document_extraction           文件 × 标准 = 一份 JSON  ← 唯一提取产物
        │  ContentJson = { docMeta, clauses:[{clauseNumber, support, facts:[{text,anchor}], why}] }
        ↓
   L2 认证准备（35 号）→ 条款缺口 + 疑点
```

**两条不可动摇的口径**：

1. **资料不随计划变**：计划改部门/条款/阶段，企业资料一行不动。
2. **提取是「文档 × 标准」的函数**：同一份质量手册，对 iso13485 和 iso9001 产出两份不同的 JSON；换阶段不重跑。

### 2.1 阶段去哪了

| 阶段原来管什么 | 改后归谁 |
|---|---|
| 资料归属（存哪个阶段的文件夹） | **取消**——资料属于企业 |
| 决定跑哪些标准 | **计划**（`cert_audit_plan.Standards`，取并集） |
| 决定审哪些条款 | **计划明细**（`cert_audit_plan_detail`，条款×部门） |
| 排班/派谁 | 入场计划（34 号 §四，后置） |

### 2.2 机构去哪了

不再反推。机构 Code 只在两处保留：
- 写入时冗余（`OrgCode` 列），用于**多租户隔离**（防跨工作区串数据）；
- 建目录模板/取提示词时由工作区解析（后端内部，用户无感）。

前端**永远不出现机构选择器**。

## 四、数据模型（**2026-10-29 用户裁定：重建表，重新定义结构**）

### 4.0 ★ 一企业一计划（新规则，先于表结构）

> 用户原话：「我们一个企业有且只有一个计划是有效的，不允许一个企业同时有 2 个计划，可以在计划中限制，如果一个企业新增计划，就自动将之前的计划全部作废，这样我们就找得到标准了。」

**规则**：`cert_audit_plan` 里同一 `EnterpriseCode` 下 **`IsValid=1` 的行最多 1 条**。

| 场景 | 行为 |
|---|---|
| 新增计划（`Code` 为空） | 保存成功后，把该企业**其它**计划的 `IsValid` 置 0（⛔ 不删行、⛔ 不删明细——历史可追溯） |
| 更新计划 | 不动其它计划（本来就不该有第二条有效） |
| 删除/停用当前计划 | 该企业回到「无有效计划」状态，上传仍可用、提取置 `skipped` |
| 前端表现 | 计划列表按企业分组，有效的那条打「当前」标；历史计划折叠 |

**为什么靠代码而不是唯一索引**：MySQL 没有部分唯一索引，`(EnterpriseCode, IsValid)` 唯一会挡掉「多条历史作废计划」。要么加生成列（`IsValid=1 ? EnterpriseCode : NULL`，NULL 不参与唯一），要么代码保证。
⇒ **先代码保证**（`AuditPlanController.Save` 里作废旧计划 + 保存前校验），生成列后置（见 D-7）。

#### ✅ 落地实现（2026-10-29，已实测）

- 作废逻辑在 `AuditPlanController.InvalidateOtherPlansAsync`，由 **`OnAfterAdd` / `OnAfterUpdate`** 触发。
  - ★ **放 after 不放 before**：放 before 时若插入失败（唯一键/DB 异常），旧计划已被作废
    ⇒ 该企业**零有效计划** ⇒ 上传模块随即拿不到标准。必须先插成功再作废旧的。
  - 只对 `IsValid=1 && !IsDeleted` 的其它行动手；`Remark` 追加
    `[yyyy-MM-dd HH:mm 自动作废] 同一企业只允许一个有效计划，已被新计划取代。`（截断 500）
  - ⛔ **只作废、不删行、不删明细**（历史计划与部门×条款关系必须留痕）。
  - ⚠️ ORM **没有全局查询过滤器**（`IsValid` / `IsDeleted` 都要手写谓词）—— 漏写就会把已作废的计划再作废一次。
  - `keepCode` 的比较放**内存**里做：SQL 里 `p.Code != null` 是 NULL 语义（永不成立）。
- `POST save` 响应新增 `invalidatedPlans`（本次自动作废条数，0 = 该企业此前无有效计划）。
- 新增 **`GET api/Auditor/AuditPlan/active?enterpriseCode=`** —— 当前有效计划 + `standardCodes` + `warnings`。
  - 无有效计划 ⇒ `Ok` + `plan=null`（「还没做计划」是正常业务态，不是错误）。
  - 若历史脏数据有 2 条有效 ⇒ 取 `Sort → CreateTime` 最小者，并在 `warnings` 里**如实告知**（⛔ 不静默挑一条）。
- 实测：同企业建第二个计划 ⇒ `invalidatedPlans=1`，旧计划 `IsValid 1→0` + Remark 留痕；验证数据已还原。

## 五、链路与队列

### 5.1 上传（四段式不变，只去掉阶段）

```
POST /api/Auditor/EnterpriseOriginal/plan      { EnterpriseCode, Files[] }        ← 干跑：重复/替换/新增预判，不落库
POST /api/Auditor/EnterpriseOriginal/init      { EnterpriseCode, Files[] }        ← 建批次 + 预建行（UploadStatus=pending）
POST /api/Auditor/EnterpriseOriginal/file      multipart(File, FileCode, TaskId)   ← 逐文件写字节（归档旧版→写新版）
POST /api/Auditor/EnterpriseOriginal/confirm   { TaskId, EnterpriseCode }         ← 激活 + 入队
POST /api/Auditor/EnterpriseOriginal/cancel    { TaskId, EnterpriseCode }         ← 撤草稿行
```

**只改一处语义**：入参 `StageCode` 全部删除；`ScopeKeyOf(ent)`。

### 5.2 队列（保留 `yzh_queue`，任务内串行）

```
一次提交 = 一个队列（QueueType = enterprise_original_file，ScopeKey = {ent}）
  └─ N 个任务（一文件一任务，串行，资源锁 = 文件 Code）
       ├─ 段① 转换：格式归一 → PDF（预览）+ Markdown（原文）   [复用 EnterpriseOriginalIngestExecutor]
       └─ 段② 提取：for each 标准 in 计划标准 ∪：                [新增 ClauseExtractExecutor]
                    L1(文件, 标准) → cert_document_extraction
```

**为什么不在任务内拆成两个队列**：现有 `doc_extract` 的跨队列链式（`OfficeConvertTaskExecutor.TryEnqueueBatchExtractAsync`）有「兄弟任务全终态才入队 + 失败补 Flush」的复杂收尾，是踩过坑的地方。任务内串行状态简单、失败边界清楚，先不引入。

**标准清单快照**：入队时把「计划标准」写进任务载荷（与现在 `ResolveStageStandardCodesAsync` 的做法一致）⇒ 排队期间改计划不影响本次执行。

### 5.3 增量与失效

| 事件 | 动作 |
|---|---|
| 新文件上传 | 该文件 × 每个计划标准，各跑一次 L1 |
| 同 hash 重传 | **跳过**（`SourceSha256` 命中，`VersionNumber` 不变，不调模型） |
| 文件被替换（异 hash） | `VersionNumber+1`；旧提取行 `IsStale=1`；重跑 |
| 计划新增标准 | 该企业全部文件 × 新标准，补跑（`TriggerKind=plan`） |
| 计划删标准 | 提取行不删，标记停用（计划可能又加回来） |
| 条款属性变更 | 不影响 L1（L1 只按条款清单找证据），影响 L2 |

## 六、L1 提取（接 35 号，只补两处）

### 6.1 提示词 `doc_extract_v1`

输入变量（35 号 §4.1 不变）：`{{standard_name}}` / `{{clause_list}}`（只给 `DocCheckMode≠none` 的条款）/ `{{doc_name}}` / `{{doc_markdown}}`

输出契约（35 号 §4.2 不变）：

```json
{
  "docMeta": { "title": "", "docNo": "", "version": "", "effectiveDate": "" },
  "clauses": [
    { "clauseNumber": "4.2.4", "support": "direct|partial|mention",
      "facts": [ { "text": "原文摘录（≤200字，逐字不改写）", "anchor": "章节号或表名" } ],
      "why": "一句话说明这条事实为什么能支撑该条款" }
  ]
}
```

四条硬规则（写进提示词，⛔ 不可省）：
1. **只输出有实质内容的条款**——没有就整条不要出现，⛔ 不许输出空数组占位。
2. **每条 fact 必须带 anchor**——找不到章节号/表名就写 `"anchor": ""` 并在 `why` 里说明，⛔ 不许编。
3. **不判符合性**——⛔ 不写「符合/不符合/充分」，只写「读到了什么」。
4. **条款号逐字取自 `{{clause_list}}`**——⛔ 不许自造编号（文档自身章节号 `6.1` 与标准条款 `6.1` 不是一回事）。

### 6.2 新增的两处（相对 35 号）

1. **标准清单来源**：35 号只写「为每个适用标准触发 L1」，没说标准哪来。本稿定为 **`cert_audit_plan.Standards` 并集**。
2. **企业无计划时的行为**：文件照常上传/转换，提取置 `skipped` + `ExtractMessage='该企业没有认证计划，无法确定要按哪些标准提取'`（⛔ 不静默、不阻塞上传）。

**★ 关键实现决策（踩过的坑，防回退）**

1. **覆盖 `refresh()`**：零行时用 `YzhEmptyState` 占位 ⇒ `YzhTable` 未挂载 ⇒ 基类 `_tableRef?.refresh()` 对 `null` **静默无操作** ⇒ 首屏永远「共 0 份文件」。修法：无 ref 时直接 `await this.dataLoader()`。
2. **上传配对用双指针顺序走**，⛔ 不建 `FileName → File` 字典 —— 同名文件（不同文件夹）会塌缩成一个，静默少传。`row-key` 同理用 `RelFolderPath|FileName`。
3. **`sha256OfFile` 超 64MB 或 `crypto.subtle` 不可用 ⇒ 返回 `''`**（降级为「替换」）。⛔ 不能因为算不出 hash 就中断上传。
4. **锚点定位三级递进** `exact → punctuation → reflow`，这是 §6.3 遗留「锚点标点归一」的消费侧修复。
   `reflow` 级必须 **剥掉** 全部空白（不是折叠成空格）—— 折叠后原文 `程序，\n确保` 与锚点 `程序，确保` 仍差一个空格，永远匹配不上。
   代价：`a b` 与 `ab` 判同一串；锚点是 10–40 字整句，宽松度可接受。
5. **方法名必须避开基类**：`fileColumns` / `docRowActions` / `handleRowAction` / `onRowsSelected`
   （`columns` / `rowActions` / `rowActionButtons` 是基类 getter ⇒ TS2610；`onRowAction` / `onSelectionChange` 是基类实例属性 ⇒ TS2425）。
6. **轮询省流**：5s 只刷 `status-bar`，`signature()`（文件数 + 各状态计数 + 各文件 `ExtractStatus`）变了才 `refresh()` 列表；`document.hidden` 时整轮跳过。

### 9.1 「上传不带标准」的准确含义（用户原话澄清）

> 「我们上传资料的时候，我们的标准也可以不要了，因为我们是在文档按标准的条款自动提取的时候，区分了标准，通过这些补充完善计划」

三层含义，逐条落到实现：

1. **上传入参里没有标准**：`plan/init/file/confirm` 四个端点只收 `EnterpriseCode`（+ 文件）。表 `cert_enterprise_doc` **没有 `StandardCode` 列**。
2. **标准在提取时才出现**：`cert_document_extraction` 的 `StandardCode` 来自「该企业有效计划的 `Standards`」，由提取执行器展开。
3. **提取结果反哺计划**：见 §5.4。

### 9.2 反哺计划（新增，别漏）

提取跑完一轮后，按标准统计「有多少文档真的落到了这个标准的条款」：

| 观察 | 提示（⛔ 只提示，不自动改计划） |
|---|---|
| 某标准 `ClauseCount=0` 的文档占比 > 80% | 「计划里的【ISO 9001】几乎没有文档支撑，是否漏选标准或资料不全？」 |
| 某标准提取出的条款覆盖 < 20% | 「【ISO 9001】仅覆盖 12/60 条款，建议补充资料」 |
| 某文档对**所有**计划标准都 `ClauseCount=0` | 「该文档与计划的任何标准都无关，建议核对是否传错」 |

**为什么只提示不自动改**：计划是审核员的判断（要审哪几个体系），系统不能因为「资料里没找到」就替他把标准删掉——那等于「没查 = 不存在」，正是要避免的错。

## 十、坑（做的时候盯住）

| # | 坑 | 对策 |
|---|---|---|
| 1 | 去 `StageCode` 后，代码里「按规则重算路径」的地方会把老路径算错 | 路径**一律读 DB 的 `StoragePath`**；`PathBuilder` 只用于新上传。老 237 行路径含 `{Stage}` 段，`Product()` 从源路径派生 ⇒ 产物也跟着老路径走，⛔ 不要重算 |
| 2 | `idx_ent_stage_path` 是 4 列联合索引，`RelFolderPath` 512 字节 | 重建时给前缀长度（`RelFolderPath(64)`），否则 3072B 超限建不出来 |
| 3 | `PolicyReason` 是非空 `string` 默认 `''` | 实体别写 `string?`，否则显式插 NULL 报错（已有注释提醒） |
| 4 | DDL 的 `UpdateTime` 写 `NOT NULL` 会让新增炸「必填字段为空」 | 一律 `NULL DEFAULT NULL`（踩过） |
| 5 | 队列 ScopeKey 从 `{ent}@{stage}` 改 `{ent}`，在跑的老队列会失效 | 改之前先清空 `yzh_queue` 里 `enterprise_original_file` 的未完成任务 |
| 6 | 一份文件 × 2 标准 = 2 次 L1；237 文件 = 474 次调用 | 先跑一个企业的子集验证质量，再全量；长文档用 `EssentialSummary` 替代全文（已有能力） |
| 7 | 文档自身章节号（`6.1`）冒充标准条款号 | 提示词硬规则 4：只认 `{{clause_list}}`；L2 侧再做一次白名单校验 |
| 8 | 无计划的企业上传后「提取一直不动」 | 上传时就查计划，无计划立刻提示 + `skipped` 原因，⛔ 不让用户等 |
| 9 | ★ **纯文本文件（`.txt`/`.md`/`.csv`）转 Markdown 必失败，还白烧一次 OCR** | 已在 P1 实测中修掉：`FileConvertCore.ConvertMarkdownInnerAsync` 增「分支 0 纯文本直通」（UTF-8 → GB18030 兜底 → 去 BOM）。⛔ 别删这道短路，否则 `.txt` 会被 anydoc 判 `Unsupported` 再丢去视觉模型 ⇒ 恒 400 `The image format is illegal` |
| 10 | `enterprise-doc` 与 `enterprise-documents` 只差几个字母 | `DocumentLibraryPath.Resolve` 是**首段精确相等**；已有单测 `Resolve_EnterpriseDoc_DoesNotCollideWithEnterpriseDocuments` 当护栏。⛔ 不许改成 `StartsWith` |
| 11 | ORM **没有全局查询过滤器**，`IsValid` / `IsDeleted` 全靠手写谓词 | 每个 `Queryable<T>` 都要显式带 `!x.IsDeleted && x.IsValid == 1`；漏写会把已作废/已删的行当成有效行（本模块踩过） |
| 12 | SqlSugar 对「闭包捕获的集合 `Contains`」翻译不可靠，会**静默返回空集** | 队列明细 / 版本表等场景一律「全取 + 内存过滤」；⛔ 不要相信 `Where(t => codes.Contains(t.X))` |
