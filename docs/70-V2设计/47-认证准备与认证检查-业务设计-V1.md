## 零 · 一句话

**认证准备**回答「哪些条款不用去现场、哪些必须去、去了查什么、怎么查、谁去」；
**认证检查**回答「现场取到的证据，够不够支撑符合性判定，该不该开 NC」。

两者不是「同一个流程跑两遍」，而是**同一份认证任务的前后两段**：准备产出**入场计划**，检查消费入场计划并产出**认证报告**。

## 一 · 业务全景

```
企业申请认证
  │  企业自愿选择要认证的标准（可多体系）
  ↓
认证计划（企业 × 标准 × 阶段）
  │  选定条款范围，按「条款 × 部门」展开成检查项
  ↓
┌──────────────────── 认证准备（入场准备） ────────────────────┐
│                                                              │
│  ① 系统读企业底档：基本情况 / 认证资料 / 组织架构 / 部门职责   │
│  ② 逐条款判适用性：general 通用 / conditional 有条件 / 不适用  │
│  ③ 初判「能不能不去现场」：                                    │
│       · 资料齐全性、内审材料完整性、失信记录 → 非现场可判       │
│       · 涉及过程运行、现场状态、人员能力 → 必须现场             │
│  ④ 形成「初步原始证据」：企业资料里已经能证明的那部分            │
│  ⑤ 审核员补充：要企业补件、电话确认、调阅补充材料               │
│  ⑥ 为每个检查项制定入场动作（多条）：                           │
│       去哪个部门 / 查什么文件 / 问谁 / 抽多少 / 用什么方式       │
│  ⑦ 指定每个检查项的审核员                                      │
│                                                              │
└──────────────────────────┬───────────────────────────────────┘
                           │ 产出
                    ┌──────▼──────┐
                    │  入场计划    │  哪些条款要现场、怎么查、谁去查
                    └──────┬──────┘
                           │ 消费
┌──────────────────────────▼──── 认证检查（现场） ──────────────┐
│                                                              │
│  ① 审核员按入场计划逐条取证（拍照 / 记录查阅 / 访谈 / 抽样）    │
│  ② 系统结合条款元数据 + 企业资料 + 现场证据自动分析            │
│  ③ 形成「检查证据」+ 推论「系统建议结论」+「NC 建议」          │
│  ④ 审核员复核：可完善证据、可改结论、决定是否开 NC              │
│  ⑤ 只有审核员判断的结论才算数，才能签发 NC                     │
│                                                              │
└──────────────────────────┬───────────────────────────────────┘
                           │ 产出
                    ┌──────▼──────┐
                    │  认证报告    │  结论 + NC + 证据链
                    └─────────────┘
```

## 二 · 六个词，先把话说清

| 词 | 定义 | 为什么重要 |
|---|---|---|
| **条款** Clause | 标准里的一条要求，如 `4.1`、`8.5.1` | 自带元数据：适用性、涉及过程、证据链、应提交材料 |
| **检查项** CheckItem | **条款 × 部门** | 真正的工作单元。一个条款可能对应多个部门，一个部门对应多个条款 |
| **入场检查项** OnsiteCheck | 检查项 × 一个具体检查动作 | **多条**。这是本次新增的核心对象，也是入场计划的正文 |
| **审核员** Auditor | 负责某检查项的人 | 准备阶段指定；检查阶段**只读**；是入场计划的关键信息 |
| **系统建议** SystemConclusion | LLM 推论的结论 | 只是建议，**不生效**，必须经审核员复核 |
| **审核员判断** AuditorConclusion | 人确认的结论 | **唯一**能驱动 NC 签发和报告出具的结论 |

### 一个容易被忽略的点

「检查项」不是「计划明细行」。计划明细是**人做选择时的组合**（一次勾了几个条款、几个部门），检查项是**展开后的最小单元**。这两者必须分开，否则「这个检查项归哪个部门」就答不上来。

## 三 · 现状核对

### 3.1 我查了什么

| 对象 | 现状 |
|---|---|
| `cert_iso_standard` | 4 个标准：iso13485 / iso9001 / iso14001 / iso45001 |
| `cert_iso_clause` | 273 条条款 |
| `cert_clause_attr` | **每个条款 77 条属性**，9 类属性，这是最大的隐藏资产 |
| `cert_audit_plan` | 1 份（测试开发企业，iso13485 + iso9001 双标准） |
| `cert_audit_plan_detail` | 一行 = 多个条款 + 可空部门 |
| `cert_task` / `cert_task_item` | 7 个任务 / 十几个任务项，测试数据 |
| `cert_check_analysis` / `cert_check_result` / `cert_check_lock` | 已建，M2/M3 跑通过 |
| `cert_evidence` | **空表** |
| `cert_nc` | **空表** |
| `cert_audit_member` | 审核员档案（姓名/职称/专业/年限/资格证），**是机构级档案，不是任务分配** |

### 3.2 条款属性里已经有的东西（关键）

`cert_clause_attr` 每个条款 9 类属性，正好覆盖你说的「怎么判、怎么查」：

| AttrCode | 含义 | 样例值 | 对我们的用处 |
|---|---|---|---|
| `Applicability` | 适用性 | `general`(53) / `conditional`(24) | **直接支撑条款适用性判定** |
| `ApplicabilityCondition` | 适用条件 | 多为空 | conditional 条款的判定依据 |
| `Process` | 涉及过程 | `["management"]` | **条款 → 部门映射的桥梁** |
| `EvidenceChain` | 取证链 | JSON 数组 `{Kind:site\|record\|interview\|doc, Action, Target, Sample}` | **入场检查项的直接来源** |
| `Artifacts` | 应提交材料 | JSON 数组 `{Kind, FileName, DeviceNo, ValidUntil, Complete}` | 非现场可判定的判断依据 |
| `DocCheckMode` | 文件检查方式 | `required` | 是否属于「资料类」条款 |
| `ClauseIntent` | 条款意图 | 「识别影响…的内外部问题」 | 喂给 LLM 做判定 |
| `Obligation` | 义务强度 | `shall` | 严重度基线 |
| `Severity` | 严重度基线 | — | NC 严重度参考 |

**这意味着入场检查项不需要从零编**，可以从 `EvidenceChain` 派生：

```json
[
  { "Kind": "doc",       "Action": "查组织环境分析报告及更新记录", "Target": "质量手册" },
  { "Kind": "site",      "Action": "现场观察管理层如何获取内外部环境信息", "Target": "管理层办公区" },
  { "Kind": "interview", "Action": "访谈最高管理者关于内外部问题识别过程", "Target": "总经理/EHS负责人" }
]
```

`Kind` 的四个取值 `site / record / interview / doc`，就是你说的「现场取证、查记录、访谈、看文件」；「开会、讨论」可以并入 `interview` 或新增 `meeting`。

### 3.3 三个必须改掉的偏差

#### 偏差一：检查项粒度错了（最严重）

**现状**：`cert_task_item.CheckItemCode` → `cert_audit_plan_detail.Code`，而一行明细是：

```
Code: 5d039736...
Clauses: 680cf5ab...,d20871b4...        ← 2 个条款
Departments: （空）                      ← 没有部门
ClauseNumbers: m 1, m 2
```

**后果**：
- 「这个检查项归哪个部门」答不上来 → 入场计划写不出「去哪个部门查」
- 一个任务项含多个条款，分析结论只能落到 `cert_check_result` 的条款行上，**检查项本身没有业务含义**
- 你说的「不是每个条款都适用于所有部门」完全无法表达

**结论**：必须把检查项独立出来，粒度 = **条款 × 部门**。

#### 偏差二：没有「审核员归属」

`cert_task_item` 有 `Status / EvidenceState / AnalysisState / AnalyzeCount / RerunState` 等一堆执行字段，但**没有 `AuditorCode`**。

`cert_audit_member` 是机构下的审核员档案（谁有资格），不是「这个检查项谁负责」。

#### 偏差三：结论只有一个字段

`cert_check_result.Conclusion` 现在既是系统输出又是最终结论。你要的是**两个**：系统建议的和审核员判断的，且只有后者生效。

## 四 · 核心模型：从条款到检查项

### 4.1 四层结构

```
标准（iso9001）
  └ 条款（4.1）                       ← 自带 9 类属性
       │  × 企业部门（品管部）         ← 通过 Process 属性匹配 + 人工调整
       ↓
     检查项（4.1 × 品管部）            ← 工作单元，有审核员、有状态、可锁定
       │  × 检查动作（多条）           ← 从 EvidenceChain 派生 + 人工增删
       ↓
     入场检查项（查台帐 / 访谈李主任 / 现场看设备）
```

### 4.2 条款 → 部门的映射怎么来

三条路，按优先级：

1. **系统建议**：`cert_clause_attr.Process` 给出过程码（如 `["management"]`），映射到企业的部门类型，给出候选部门
2. **计划已选**：计划明细里人选过的部门组合，作为强约束
3. **人工调整**：审核员在准备阶段增删部门

> `Process` 的取值目前是英文过程码（`management` 等），需要一份「过程码 → 部门类型」的字典。**这是待确认项之一**。

### 4.3 条款适用性

`Applicability` 有两个值：

| 值 | 含义 | 处理 |
|---|---|---|
| `general` | 通用适用 | 所有企业都要查 |
| `conditional` | 有条件适用 | 看 `ApplicabilityCondition`，满足才查 |

检查项需要独立记录**本次判定结果**：

| 判定 | 谁定 | 结果 |
|---|---|---|
| 适用 | 系统建议 + 审核员确认 | 正常走流程 |
| 不适用 | **只能审核员定** | 状态 `na`，不分析、不入场、不进报告正文（但要列在「不适用条款」清单里） |
| 有条件适用 | 系统建议 + 审核员确认 | 需附适用理由 |

> 不适用不能由系统自动判定。认证是法律责任，删条款必须有人签字。

### 4.4 「能不能不去现场」怎么判

这是准备阶段的核心判断，规则如下：

| 条件 | 建议 |
|---|---|
| `DocCheckMode = required` 且 `EvidenceChain` 全部是 `doc`/`record` | **建议免现场**（资料齐全即可判） |
| `EvidenceChain` 含 `site` 或 `interview` | **建议入场** |
| `PrepState = partial/missing` 且有疑点 | **建议入场**（现场核实） |
| `PrepState = found` 且无疑点 | **建议免现场** |

你说的「资料齐全性、内审材料完整性、失信记录」正好落在第一类——它们只看文件，不需要去人。

**但系统只给建议，最终逐条由审核员确认**（你在第二次反馈里明确说了「不强制限制」）。

## 五 · 入场检查项（本次新增的核心）

### 5.1 为什么必须多条

一个检查项（比如 `4.1 × 品管部`）到了现场，不是「看一眼」就完了，可能要：

1. 查《设备台帐》近 12 个月更新记录（记录查阅，抽样 3 份）
2. 访谈品管部李主任，问设备责任人划分（人员访谈）
3. 现场看实验室仪器是否在台帐内（现场观察）
4. 要企业提供《实验室仪器清单》v2（文件调阅）

**四条记录**，方式不同、对象不同、抽样量不同。所以必须是一对多。

### 5.2 入场检查项的字段

表 `cert_onsite_plan_item`：

| 字段 | 类型 | 含义 |
|---|---|---|
| `Code` | varchar(50) | 主键 |
| `PlanCode` | varchar(50) | 所属入场计划 |
| `CheckItemCode` | varchar(50) | 所属检查项 |
| `Seq` | int | 序号 |
| `Method` | varchar(20) | **检查方式**：`site` 现场观察 / `record` 记录查阅 / `interview` 人员访谈 / `doc` 文件调阅 / `meeting` 会议讨论 |
| `TargetType` | varchar(20) | 对象类型：`dept` 部门 / `doc` 文件 / `person` 人员 |
| `TargetCode` | varchar(50) | 对象 Code（部门 Code / 文件 Code / 人员） |
| `TargetName` | varchar(200) | 对象名称（冗余，便于导出） |
| `Action` | varchar(500) | **查什么**（具体动作） |
| `SampleSize` | varchar(50) | 抽样量（如「抽 3 份」「抽 5 台」） |
| `FocusPoints` | text | 重点核查什么（来自疑点） |
| `RequiredDocs` | text | 需企业提前准备的文件 |
| `AuditorCode` | varchar(50) | 这条动作由谁执行 |
| `SourceKind` | varchar(20) | 来源：`system` 系统建议 / `manual` 人工新增 |
| `IsConfirmed` | tinyint(1) | 审核员是否确认过 |
| `Remark` | text | 备注 |

### 5.3 生成方式

```
cert_clause_attr.EvidenceChain (JSON)
        │
        ├─ LLM 结合企业部门结构做适配 ──→ 建议的入场检查项（SourceKind=system）
        │
        └─ 审核员增删改 ────────────────→ 人工项（SourceKind=manual）
                                            ↓
                                     确认后 IsConfirmed=1
                                            ↓
                                     入场计划定稿
```

> 你说了「入场计划如何挂接证据这一块暂时不做」，所以本期入场检查项**只到「怎么查」为止**，不建立「动作 → 证据」的强绑定。现场取证仍然挂在检查项上（`cert_evidence.CheckItemCode`），不强制挂到某个动作。

## 六 · 认证准备：从资料到入场计划

### 6.1 七个步骤

| # | 步骤 | 谁做 | 产出 |
|---|---|---|---|
| 1 | 读企业底档 | 系统 | 企业基本情况 / 认证资料清单 / 组织架构 / 部门职责 |
| 2 | 逐条款判适用性 | 系统建议 + 审核员确认 | 适用 / 不适用 / 有条件适用 |
| 3 | 逐条款初判 | 系统 | `PrepState` + 疑点 + 初步原始证据 |
| 4 | 审核员补充证据 | 审核员 | 补件、电话确认、补充材料 |
| 5 | 判「要不要入场」 | 系统建议 + 审核员确认 | 免现场 / 需入场 |
| 6 | 制定入场动作 | 系统建议 + 审核员编辑 | **入场检查项（多条）** |
| 7 | 指定审核员 | 审核员 | 每个检查项一个负责人 |

### 6.2 PrepState 的五态（保持）

| 值 | 含义 | 是否推 NC |
|---|---|---|
| `found` | 资料齐全，能判定 | 否 |
| `partial` | 部分缺失，需补充 | 否（但推入场） |
| `missing` | 关键资料缺失 | 否（但推入场） |
| `unknown` | 无法判断（LLM 不确定） | **绝不推 NC** |
| `na` | 不适用 | 否 |

> 准备阶段**不判 NC、不签发 NC**。`PrepNcHint` 只是「疑似会成为 NC」的提示，供入场计划参考，不落到 `cert_nc`。

### 6.3 准备阶段的锁定

- 可锁定**已完成**的检查项
- 锁定后：不参与任何重跑、不被分析覆盖、PrepState 冻结
- 解锁：审核员显式操作，留痕（谁、何时、为什么）

## 七 · 认证检查：从证据到 NC

### 7.1 五个步骤

| # | 步骤 | 谁做 | 产出 |
|---|---|---|---|
| 1 | 按入场计划取证 | 审核员 | `cert_evidence`（Kind: 照片/记录/访谈/文件） |
| 2 | 系统分析 | 系统 | 检查证据 + 系统建议结论 + NC 建议 |
| 3 | 审核员复核 | 审核员 | 审核员判断结论（必须四选一） |
| 4 | 决定开 NC | 审核员 | 逐条签发 `cert_nc` |
| 5 | 锁定 | 审核员 | 该检查项定稿 |

### 7.2 证据是提示，不是硬卡

你的原话：「我们缺失证据是提示不是强制」。

所以：

| 证据情况 | 系统行为 |
|---|---|
| 有证据 | 正常分析 |
| **证据为 0** | **仍可分析**，但：① 页面显著提示「该检查项尚无现场证据」② 系统建议结论强制标为 `unknown` 或 `insufficient_evidence` ③ 审核员若要给出结论，必须手填「现场未见相关记录」之类的说明作为证据 |
| 证据与条款不匹配 | 分析时提示，不阻断 |

这条推翻了我在 V2 原型里做的「证据 0 份不可分析」硬卡。**改成软提示**。

### 7.3 NC 只能逐条签发

- 一个检查项最多对应一条 NC（现状 `cert_nc.CheckItemCode` 已如此）
- 签发前必须已有**审核员判断结论 = `nc`**
- 准备阶段不出现任何签发入口

## 八 · 双结论与复核（本次最重要的机制）

### 8.1 两条结论，各管一段

```
LLM 分析
   ↓
SystemConclusion = pass / ofi / nc / na / unknown      ← 系统建议，仅供参考
   ↓
审核员复核（必须）
   ↓
AuditorConclusion = pass / ofi / nc / na               ← 唯一生效结论
   ↓
ReviewStatus = confirmed
   ↓
才允许：签发 NC / 锁定 / 进报告
```

### 8.2 字段设计

`cert_check_result` 改造：

| 字段 | 类型 | 说明 |
|---|---|---|
| `SystemConclusion` | varchar(20) | **新**。LLM 推论结论 |
| `SystemSeverity` | varchar(20) | **新**。LLM 推论严重度 |
| `SystemNcSuggested` | tinyint(1) | **新**。LLM 是否建议开 NC |
| `SystemReason` | text | **新**。LLM 判定理由 |
| `AuditorConclusion` | varchar(20) | **新**。审核员判断结论 |
| `AuditorSeverity` | varchar(20) | **新**。审核员判断严重度 |
| `AuditorReason` | text | 审核员判定依据（原 `Reason` 复用） |
| `AuditorCode` | varchar(50) | **新**。谁判的 |
| `AuditorAt` | datetime | **新**。什么时候判的 |
| `ReviewStatus` | varchar(20) | **新**。`pending` 待复核 / `confirmed` 已确认 / `diverged` 与系统建议不一致 |
| `Conclusion` | varchar(20) | **改造**。改为「生效结论」= `AuditorConclusion`，无则 NULL |

> 保留 `Conclusion` 是为了兼容现有查询（`GetItemsWithResults` 等），但语义收窄为「已确认的最终结论」。

### 8.3 复核界面要暴露的三件事

1. **系统建议是什么**（不能藏，否则审核员没判断依据）
2. **系统为什么这么判**（理由 + 引用证据）
3. **我判的和系统不一样时，必须写理由**（`ReviewStatus=diverged` 时 `AuditorReason` 必填）

### 8.4 与重跑的关系

你说了：「针对认证检查我们所有推论的信息必须有个审核员复核的过程」。

所以：

| 检查项状态 | 能否重跑 |
|---|---|
| 未复核（`ReviewStatus=pending`） | 可以，直接重跑覆盖系统建议 |
| 已确认（`confirmed`）且**未锁定** | 可以，重跑后回到 `pending`，需重新复核 |
| 已锁定 | **必须先解锁**，且要审核员**重新勾选认可** |

## 十 · 锁定与按项重跑

### 10.1 锁定

- **两个阶段都能锁**，锁的是**已完成的检查项**
- 锁定语义：机器不许再改这个检查项的任何结论
- 锁是**检查项级**，不是任务级

### 10.2 重跑：按项选择，不是整批

你的原话：「可以自由选择哪些检查项进行重新分析」。

所以重跑的入口是**勾选检查项**，不是「重新执行整个任务」：

```
勾选 N 个检查项 → 点「重新分析」
        ↓
逐个判断锁定状态
        ├─ 未锁定 → 直接进队列
        └─ 已锁定 → 弹窗：「以下 M 项已锁定，重新分析会覆盖现有结论」
                     □ 我已复核，同意重新分析（必须勾选）
                     ↓
                     解锁 → 进队列
        ↓
队列执行（TaskType = cert_check_prep / cert_check_onsite）
        ↓
新分析行 RunNo+1，旧行 IsCurrent=NULL
        ↓
已确认的检查项回到 pending，需重新复核
```

### 10.3 与现有实现的关系

M3 已经做了「整任务启动 + 锁定项跳过」。这次要改成：

| 现状 | 目标 |
|---|---|
| `StartTaskAsync(taskCode)` 跑整个任务 | `AnalyzeItemsAsync(taskCode, itemCodes[])` 跑选中项 |
| 锁定项**静默跳过** | 锁定项**弹窗要求重新认可**，不静默 |
| 任务级 `Status` 驱动进度 | 保留，但进度按选中项算 |

## 十二 · 状态机

### 12.1 检查项状态（两阶段共用一套，用字段区分阶段）

| 状态 | 含义 | 准备阶段 | 检查阶段 |
|---|---|---|---|
| `waiting` | 待处理 | ✓ | ✓ |
| `running` | 分析中 | ✓ | ✓ |
| `analyzed` | 系统已出建议，**待复核** | ✓ | ✓ |
| `confirmed` | 审核员已确认 | ✓ | ✓ |
| `locked` | 已锁定 | ✓ | ✓ |
| `na` | 不适用 | ✓ | ✓ |
| `failed` | 失败 | ✓ | ✓ |

> 状态存在 `cert_task_item.Status`（每次任务的执行状态），检查项本身的长期状态在 `cert_check_item.Status`。两者不要混。

### 12.2 结论状态

| 层 | 取值 |
|---|---|
| 系统建议 | `pass` / `ofi` / `nc` / `na` / `unknown` / `insufficient_evidence` |
| 审核员判断 | `pass` / `ofi` / `nc` / `na`（**必须四选一，无 unknown**） |
| 复核状态 | `pending` / `confirmed` / `diverged` |

### 12.3 入场计划状态

`draft`（可改）→ `confirmed`（定稿，检查阶段引用）→ `archived`（被新版本替代）
