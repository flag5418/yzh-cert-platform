## 一、用「人」的模型定调（四层对照表）

| 类比                                                                   | 系统里是什么                 | 表                                          | 端         | 量级                 |
| ---------------------------------------------------------------------- | ---------------------------- | ------------------------------------------- | ---------- | -------------------- |
| **属性池**：所有人的所有可能属性（姓名、年龄、学历、执照、宇航员训练） | 属性全集                     | `cert_clause_attr_def`                      | 后台       | **30–50 行，不怕多** |
| **职业定义**：工程师需要学历 + 编程 + 项目经验，**不含宇航员训练**；并注明"学历要验证、编程看项目" | 某条款用哪些属性 + 值 + **这个值固定还是参考** | `cert_clause_attr` | 后台 | 每条款 5–12 行 |
| **具体的人**：张三，28 岁，本科，5 年经验                              | 某企业在这条款上的**实际值** | `cert_enterprise_clause_attr`               | **专家端（暂缓）** | 每企业数百行         |
| **体检报告**：张三这项指标合格/不合格，依据哪张化验单                  | 检查证据 + 预 NC             | `cert_check_evidence` / `cert_check_result` | **专家端（暂缓）** | 每企业数十行         |

> 用户的类比是三层；第 4 层是**执行时的产出**——「形成检查证据，并根据检查证据形成预 NC」。它既不是"要求"也不是"值"，是**判定**，必须单独一层。三层定边界，四层定产出。

### 三个推论（模型的全部约束）

1. **池子大、配置小。** 池子 30–50 条不嫌多，每个"职业"只挑自己那几条。池子小了就会"拿身体部位凑"，属性就不干净——这正如此前一会儿 18 条、一会儿 9 条的根源：**在用"每条款都要有的"标准去限制池子**。
2. **"挑哪几条"不需要额外字段。** 没挑 = 没行 = 稀疏。属性池**不加**"适用条款"列。
3. **"这个值是不是固定的"只能在条款配置时定。** 同一条属性在不同条款下可能固定、也可能参考（`Artifacts` 在 7.1.5.2 是参考、在 7.3 是固定为空）。属性池若自带 `ValueSource`，只能取一个值 ⇒ 必然错。而张三具体叫什么名字，永远不进条款配置 —— 它进企业值表。

### 一条铁律 + 三条边界

> **铁律**：任何一张表，如果它的行既描述「标准要求」又描述「某企业实际」，它就该拆。
> （V1 的 `cert_standard_directory_file` 正是这样的债：同行既有 `IsRequired` 又有 `UploadStatus`。）

| 越界写法                                    | 正确做法                                 |
| ------------------------------------------- | ---------------------------------------- |
| 在 L1 存 `Confidence`/`Source`/`ValueState` | 这些是"值可不可信"，只在 L2 存           |
| 在 L1 存 `ClauseNumber`（人读编号）         | `cert_iso_clause` 已有，join             |
| 在 L2 存"标准要求几条材料"                  | 那是 L1 的事，读 L1 现算，标准换版不失效 |

## 三、总体业务模型：两阶段同链两求值（不变，映射到新表）

```
期望集 = L1 条款配置展开（该有什么：Artifacts 期望 + 各 fixed 属性）
实际集 = L2 企业值（上传/匹配/现场采集）+ L3 证据
缺口   = L2 的 ValueState = missing / partial   ←「有疑问」的机器定义
```

| 段                 | 核心动作                                                                 | 读哪层                       | 写哪层                                        |
| ------------------ | ------------------------------------------------------------------------ | ---------------------------- | --------------------------------------------- |
| **准备**（入场前） | 适用性求值 → 期望集展开 → 语义归纳 → 缺口 → 疑点四分类 → 入场计划 + 预NC | L1（要求）+ 联网查询（信号） | L2（`ValueState`）→ L3（`Status=draft` 预NC） |
| **执行**（入场后） | 证据采集落地 → 双引擎判定 → 确认/推翻预NC → 正式 NC                      | L1 + L2                      | L3（证据 + `Status=confirmed`）               |

**关键不变**：两段推导链完全一致，区别仅在 L2/L3 的完整度。

## 四、数据模型：后台两层（核心章节）+ 企业侧（暂缓）

### 4.1 L0 属性池 `cert_clause_attr_def`（后台，30–50 行）

**回答：世界上有哪些属性、类型是什么、干什么用。**

关键字段：`Code`（业务键）· `AttrName` · `ValueType`（**5 种**：`text`/`dict`/`bool`/`json`/`prompt`）· `DictCode` · `Remark`（作用）· `IsValid`（停用不删）· `Sort`。

⛔ **无 `ValueSource`** —— 在 L1 定（同属性不同条款来源不同，见 §一 推论 3）。
⛔ **无 `PoolLayer`** —— 池子不分层，一个大池子。
⛔ **无 `AttrRole`** —— 作用写在 `Remark` 里，不另设角色列。

- **不设 `AppliesTo`**：挑哪几条 = L1 有没有行（推论 2）。
- JSON 结构**不在表里，在代码里强类型定义**（如 `ArtifactItem`：类型/名称/是否必须/材料级严重度/表单码）。
- 停用属性用 `IsValid=0`，不删除（历史 L1/L2 值不成孤儿）。

**第一批 9 条种子**：

| # | `Code` | 属性名 | `ValueType` | 唯一决定的事 |
|:--:|---|---|---|---|
| 1 | `ClauseIntent` | 条款作用 | `text` | 语义归纳锚点 + NC 理由出处（**给 LLM 做语义分析**） |
| 2 | `Obligation` | 约束强度 | `dict` | **开 NC 的闸门**（应/必须=shall，宜/可/注 不开） |
| 3 | `Applicability` | 适用范围 | `dict` | 要不要查（通用/有条件） |
| 4 | `ApplicabilityCondition` | 适用条件 | `text` | 条件原文（**求值由程序读企业事实做，不存属性**） |
| 5 | `RequirementItems` | 分项要求 | `json` | 逐项判定，NC 精确到 a)/b)；70.7% 条款是分项式（23 号实测） |
| 6 | `EvidenceKinds` | 要求形态 | `json` | **去哪个池子找证据**（doc/record/site/person/system） |
| 7 | `CheckModes` | 检查方式 | `json` | **选引擎的开关**（不产结论，执行信 `cert_validation_rule`） |
| 8 | `Severity` | 影响程度 | `dict` | NC 分级闸门；唯一语法推不出，须法定分级+人判 |
| 9 | `Artifacts` | 要求的企业材料 | `json` | 期望集主体；类型存字典码不存自由文本 |

**扩容方式**：池子变大不改结构，只是 L0 多几行。按需补（7.1.5→校准周期、8.3→设计阶段、8.4→供方评价方式、9.2→内审频次、13485→灭菌方式…），**不预置分层字段、不预置必填集**。

**移出不入池**（23 号 §三之三）：频次/时限 → 阶段域；责任主体 → 过程→部门（`cert_clause_process` 独立小表，D-V6）。

### 4.2 L1 条款配置 `cert_clause_attr`（后台，约 1,300 行）

**回答：这条款要求什么。**

`(StandardCode, ClauseCode, AttrCode)` 唯一键 + **`ValueSource`（`fixed`/`reference`，必填）** + `AttrValue` 单值列（类型由 L0 声明，解析一处收口）+ `FilterCode` 生成列（只对 Obligation/Severity/Applicability 三属性建筛选索引）。

**两种空**：

| 状态 | 表现 | 含义 |
|---|---|---|
| 未配置 | 没有这一行 | 还没提取 |
| 明确无 | 有行值为空 | 提取过，确实不要求（7.3 无任何材料） |

> 「这条款对这家企业不适用」**不在本表** —— 那是企业侧判定，不是标准级配置。
> **不设必填集**：不在代码里规定"7 章条款必须有 8 条属性"。属性挂到条款上约束即可；池子大、配置小，缺哪条补哪条。

### 4.3 L2 企业值 `cert_enterprise_clause_attr`（专家端，**暂缓，字段未定**）

**回答：这家企业实际是什么、可不可信。**

唯一键 `(EnterpriseCode, SessionCode, StandardCode, ClauseCode, AttrCode)`：

- **`SessionCode` 空串 `''` = 企业常驻事实**（如"有没有测量设备"）；非空 = 某次审核场次采集。⚠️ 必须 `NOT NULL DEFAULT ''`，NULL 破坏唯一键。
- **`AttrCode` 只允许 L1 该行 `ValueSource=reference`** —— `fixed` 无企业差异，写进 L2 就是每企业凭空多 7×201 行死数据。
- `ActualValue` 单值列 + `SourceType`（upload/match/onsite/interview/manual）+ `Confidence` + `EvidenceCount`。

**`ValueState` 五态**（比"有没有"细一档）：

| 态        | 含义                               |           可开 NC？            |
| --------- | ---------------------------------- | :----------------------------: |
| `unknown` | 还没查（默认）                     | ❌ **红线：绝不自动推导为 NC** |
| `missing` | 查过了，确实没有                   |       ⚠️ 满足三前置才可        |
| `partial` | 有，但不全/过期                    |       ⚠️ 满足三前置才可        |
| `found`   | 有且完整                           |               ❌               |
| `na`      | 这家企业不适用（程序求值结果）     |               ❌               |

### 4.4 L3 判定（专家端，**暂缓，字段未定**）

**回答：符不符合、开不开 NC。**

- **`cert_check_evidence`**（证据原子）：`ClauseCode` **可空**（6 类无条款检查项）；`AnchorText` 锚点原文（时间·地点·人物·数值四要素定位）；`Finding` **只描述事实不下结论**；来源 `file/record/onsite/interview/extract`。
- **`cert_check_result`**（判定/预NC）：`Verdict`（conform/nc/observation/na/pending）+ `Severity`（仅 nc 强制）+ `RequirementRef`（分项 a)/b)）+ `Reason`（**必须从证据长出**）+ `EvidenceCodes` + `EngineType`（rule/llm/hybrid）+ **`Status`（draft=预NC / confirmed=审核员确认转正）**。

### 4.5 一条真实条款走完四层（7.1.5.2 测量溯源）

| 层  | 内容                                                                                                                                                                                                                                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L0  | 9 条基础 + `CalibrationCycle`（按需补）                                                                                                                                                                                                      |
| L1  | `Obligation=shall`、`Applicability=有条件`、`ApplicabilityCondition=当要求测量溯源时`、`RequirementItems=[a,b,c]`、`EvidenceKinds=[record,site]`、`CheckModes=[全不全,时间]`、`Severity=严重`、`Artifacts=[{设备台账,必须},{校准证书,必须}]` |
| L2  | `ApplicabilityCondition` 求值 → 适用；`Artifacts` 实际 → `partial`（台账 12 台、校准证书缺 3 台）                                                                                                                                            |
| L3  | 证据=台账文件+缺失清单；`Verdict=nc`、`Severity=major`、`RequirementRef=a)`、`Status=draft`（预NC）                                                                                                                                          |

对照 **7.3 意识**：`EvidenceKinds=[person]`、`Artifacts` 明确无 ⇒ L2 不去文件池，转访谈。**硬去文件池搜必然搜不到，然后误判"企业没做"——这就是属性层存在的意义。**

## 五、属性消费地图（按四层重写）

| 属性                                       |  准备·适用性   |         准备·归纳         |                        准备·分派                        | 现场·取证 |                 现场·判定                 |
| ------------------------------------------ | :------------: | :-----------------------: | :-----------------------------------------------------: | :-------: | :---------------------------------------: |
| `ClauseIntent`                             |      辅助      |       ★ **主锚点**        |                                                         |           |                  NC 理由                  |
| `Obligation`                               |                |                           |                                                         |           |      ★ **闸门**（≠shall 只出观察项）      |
| `Applicability` + `ApplicabilityCondition` | ★ 程序求值     |                           |                                                         |           |             ★ 前置（na ⇒ 停）             |
| `RequirementItems`                         |                |                           |                                                         |           |             ★ NC 精确到 a)/b)             |
| `EvidenceKinds`                            |                |  ★ 分流（不去错的池子）   | ★ **渠道**（doc→request/site→observe/person→interview） |  ★ 载体   |                                           |
| `Artifacts`（reference）                    |                | ★ 期望集展开 → 与 L2 比对 |                                                         |           |                                           |
| `CheckModes`                               |                |                           |                                                         |           | ★ 选引擎（结论信 `cert_validation_rule`） |
| `Severity`                                 |                |                           |                                                         |           |        ★ 分级（材料级覆盖条款级）         |

**全生命周期链**：

```
L0 种子 → L1 配置（AI起草→复核→锁定）          【后台，一次/标准】

   → 执行：证据采集(L3) → 双引擎判定 → 预NC确认/推翻(L3 confirmed) → 报告聚合
```

## 六、联网查询公共服务（信号源，不是阻断器）

定位与数据源（工商/事故/监督抽查/行政处罚/投诉/诉讼/环保）同 00 号 §六，不重复。三条原则不变：只查公开数据、查询留痕、**结果只作线索不作 NC 证据**。

**一处法定例外**（20 号 P0-4，待裁决 D-V8）：命中「国家监督抽查不合格」⇒ CNCA 5.9 要求**通报起 30 日内实施特殊审核**——这不是加权信号，是**法定倒计时任务**，疑点分派中单独一类。

联网数据 → A3 求值辅助（存续异常/运行时长不足/处罚记录/转机构期 → 进"待确认"，不阻断入场计划生成）。

## 七、准备阶段自动化（消费四层）

产出物与 00 号 §七一致（企业事实更新 / 适用性判定 / 沟通类疑点 / 检查计划矩阵 / 入场计划 / 预NC候选），链路全部改走四层：

```
① 适用性求值：L1 ApplicabilityCondition × 企业事实(L2 常驻) × 联网信号
② 期望集展开：L1 Artifacts(reference)
③ 语义归纳：ClauseIntent + 文件侧 MatchPrompt（契约跟文件走，属性池不放）
④ 缺口反推：L2 ValueState = missing/partial → 按 EvidenceKinds 分派
   doc/record 缺 → request（待索取清单，微信发企业，不建独立流程）
   site → observe ｜ person → interview ｜ 证据矛盾 → verify
⑤ 入场任务生成：主序=过程域聚集（cert_clause_process × 部门交集），次序=渠道排序
⑥ 预NC：三前置满足 → L3 draft
```

**部门-条款不建硬映射表**：条款侧 `cert_clause_process`（受控过程词表，可解释可回归）× 企业部门职责（LLM 辅助映射、人工确认）取交集；只有对不上的残余交 LLM。机构差异只进提示词模板。

**审核组/人日 = 操作员可控输入**：不建自动分工引擎、不做超载阻断；但 `cert_audit_plan` 需 `ManDayBasis`（人日确定理由，CNCA 10.2 法定记录项，待裁决 D-V8）+ S1/S2 间隔软提示（≥5 日 ≤6 个月，5.6.1）。

## 八、检查逻辑（执行阶段）

### 8.1 NC 三前置（缺一条都不能开）

| 前置         | 读哪               | 判据                   |
| ------------ | ------------------ | ---------------------- |
| **适用**     | 企业侧求值         | `ValueState=na` ⇒ 停   |
| **强制**     | L1 `Obligation`    | ≠shall ⇒ 只出观察项    |
| **证据完备** | L2 `ValueState`    | unknown/partial ⇒ 不开 |

**S1 阶段永远不产正式 NC**（CNCA 5.6.2.3：一阶段只书面告知"潜在不符合"= 预NC 的法定出处）。

### 8.2 双引擎 + 法律红线

判定执行只读 `cert_validation_rule`（细粒度阈值与模板）；`CheckModes` 只选引擎。**禁止纯大模型下判定**：规则定骨架，模型只做框内语义比对；结论含四要素必须有 `AnchorText` 原始锚点。

### 8.3 严重度：材料级优先 + 系统性失效升级（新增，待裁决 D-V8）

- 单点：L3 `Severity` 默认取 L1 条款级，可被 `Artifacts` 元素的材料级覆盖（缺台账 major / 缺标识 minor）。
- **聚合**：CNCA 12.1.7「多项轻微指向同一要求表明系统性失效 ⇒ 严重」——判定引擎 NC 生成前执行「同 ClauseCode 跨部门 minor ≥N ⇒ major 候选，人确认」。当前模型缺此聚合层，须补。

## 九、与既有表/旧模型的边界

### 9.1 00 号旧模型表的处置

| 00 号设计的表                       | 处置                                                                                                     |

## 十、两端职责边界

> 判据不变：**换一家企业还用得上 ⇒ 后台；只对这家企业成立 ⇒ 专家端。**

| 端                         | 内容                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **后台（cert-admin）**     | 标准/条款（已有）· **L0 属性池 + L1 条款配置 + 完备度视图（本次核心）** · 阶段×条款 `cert_iso_clause_stage` · 机构证据提示词 `cert_org_evidence_style` |
| **专家端（cert-auditor）** | 企业建档/部门 · 审核计划三元组（组织+审核组+部门）· 入场任务 · **L2 企业值 + L3 证据/判定** · 报告输出                                                 |

配置层无机构 ≠ 机构无配置：L0/L1 无 `OrgCode`；证据形态/提示词/合并习惯有机构。

## 十二、已确认核心结论（沿用 00 号 §十二，不重开论证）

19 条架构/匹配/对标结论全部沿用（条款唯一原子 / 属性稀疏 / 配置层无机构 / 语义匹配 / 「未见」≠「不符合」 / 条款×部门 1.33× / ClauseCode 可空 / 粒度默认叶子 / 两端判据 / 软约束部门映射 / 信号源不阻断 / 衔接预留……）。**新增三条**：

20. **属性池 + 条款配置两层**：池子大、配置小；挑哪几条=有没有行（§一）
21. **`ValueSource` 只在条款配置、只两档**：`fixed`/`reference`——同属性不同条款来源不同；"求值"是程序逻辑，不做第三档（24 号 §五）
22. **`unknown ≠ missing`**：前者"我们没查"，后者"企业没有"；`unknown` 自动推导 NC 是红线（CNCA 5.11.3 抽样免责）
