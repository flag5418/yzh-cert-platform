## 零、先统一词（读前必看，避免返工）

这套设计最大的风险不是技术，是**同一个词在两处含义不同**。下面 8 组词，混一个就会做错表。

| 词 | 准确含义 | 属于 |
|---|---|---|
| **规则** | 标准要求什么（与哪家企业无关） | 规则侧 |
| **实例** | 这家企业实际是什么 | 企业侧 |
| **定义** | 条款该有哪些属性、值是多少 | 规则侧 |
| **执行** | 拿企业资料去求值、取证、判定 | 企业侧 |
| **固定值** | 标准已经限制死的（必须/应/宜、适用范围、影响程度、检查方式） | 规则侧，企业不能改 |
| **参考值** | 标准级只能写"要什么"，真值必须从企业资料/证据取得 | 规则侧存期望，企业侧存实际 |
| **期望** | 应该有什么（台账、校准证书） | 规则侧 |
| **实际** | 交了什么、齐不齐、过没过期 | 企业侧 |
| **条款** | 国标的一个条文（273 条） | 规则侧 |
| **检查项** | 条款（或条款组合）× 部门 × 审核员，是**执行实例** | 企业侧 |
| **证据** | 支撑判断的事实（文件、记录、现场、访谈） | 企业侧 |
| **NC** | 依据证据下的结论 | 企业侧 |

**一条铁律**：

> 任何一张表，**只能回答一个问题**。既描述"标准要求"又描述"某企业实际"的表，一定拆。
> 这条铁律是三层模型的全部约束来源。

## 一、两条线：规则侧 / 企业侧

```
┌───────────────────────── 规则侧（本文范围）─────────────────────────┐
│ A1 标准 → 条款（已有：4 标准 273 条）                                 │
│ A2 属性池（分层：通用 9 / 条款族专属 / 标准专属）                       │
│ A3 条款配置（每条款选哪些属性 + 固定值 + 参考值期望）                    │
│ A4 标准侧文档要求（这个标准下该有哪些文档、该含什么、作用是什么）          │
│ A5 条款判断提示词（9 属性 + 判断逻辑 → 预 NC 判据）                     │
│ A6 机构证据生成规则（按机构组织取证与证据包，覆盖所有条款）               │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ 交付「契约」，不交付数据
                               ▼
┌───────────────────────── 企业侧（本文不设计）─────────────────────────┐
│ B1 企业档案 / 部门 / 审核组 / 审核计划                                 │
│ B2 企业资料上传（一份文档 × 一个标准 = 一份提取结果）                    │
│ B3 按约定期望做求值（有/无、全/不全、过没过期）                          │
│ B4 入场计划取证（现场 / 记录 / 访谈）                                   │
│ B5 执行 A5 的提示词 + A6 的证据规则 → 预 NC / 正式 NC                   │
│ B6 报告                                                               │
└───────────────────────────────────────────────────────────────────────┘
```

**关键理解**：两条线不是"先做一半再做另一半"，而是**两种不同性质的系统**。

- 规则侧是**知识工程**：把国标翻译成可执行的属性和判据，一次做好，所有企业复用。
- 企业侧是**业务执行**：一家企业一套数据、一套结论。
- 规则侧的输出是**契约**（属性定义、固定值、期望清单、提示词模板、判据），企业侧只能消费，不能反写。

> 所以规则侧的表**没有** `OrgCode`、**没有** `EnterpriseCode`；企业侧的表两者都有。这条分界比任何字段设计都重要。

### 1.1 四个模型 = 两条线上的四个位置

| 模型 | 回答什么问题 | 在哪条线上 | 依据文档 |
|---|---|---|---|
| **条款模型** | 标准要求什么（属性 + 固定值/参考值） | 规则侧 | 本文 + 24 号（字段） |
| **文档模型** | 这个标准该有哪些文档、该含什么、文档里写着什么 | 规则侧定义 / 企业侧提取 | 28 号 V4 |
| **准备检查模型** | 这家企业齐不齐、矛盾不矛盾、疑点该谁去查、怎么排入场 | 企业侧 | 29 号 |
| **体系检查模型** | 现场证据够不够、疑点确认还是推翻、开不开 NC | 企业侧 | 29 号 |

一条链走完是：**条款 → 文档要求 → 企业文档事实 → 准备检查（缺口/疑点/计划/预NC）→ 现场取证 → 判定 → 报告**。

> 四个模型共用五个提示词家族，全部按标准分开（一标准一套）。任何一处把"规则"和"执行"混写，都会在下一环放大成返工。

## 二、三层"人"的模型（这张表定调）

| 类比 | 系统里是什么 | 表 | 量级 |
|---|---|---|---|
| **属性池**：所有人的所有可能属性（姓名、年龄、学历、执照、宇航员训练） | 属性全集，分层存放 | `cert_clause_attr_def` | 30–50 条，不怕多 |
| **职业定义**：工程师需要学历 + 编程 + 项目经验，**不含宇航员训练** | 某条款该有哪些属性 + 哪些是固定值 | `cert_clause_attr` | 每条款 5–12 条 |
| **具体的人**：张三，28 岁，本科，5 年经验 | 某企业在这条款上的实际值 / 证据 | 企业侧表（另立） | 每企业不同 |
| **体检报告**：这项指标合格/不合格，依据哪张化验单 | 证据 + 预 NC | 企业侧表（另立） | 每企业数十条 |

用户原话里的三条推论，就是模型的全部约束：

1. **池子大、配置小**。池子 30–50 条不嫌多，因为每个"职业"只挑自己那几条。池子小了才会"拿身体部位凑"，属性就不干净——这也是之前一会儿 18 条、一会儿 9 条的根因：**在用"每条款都要有的"标准去限制池子**。
2. **"挑哪几条"不需要额外字段**。没挑 = 没行 = 稀疏。属性池**不加**"适用条款"列。
3. **"姓名性别"永远不进条款配置**。条款表回答"工程师该有什么"，企业表回答"张三具体是什么"。两张表一混，就是前面反复出错的根源。

第四层（判定产出）单独说：它既不是"要求"也不是"值"，是**判定**，所以必须有自己的表（企业侧）。

## 三、属性池（L0）：分层，但结构只有一套

### 3.1 分层不是新结构，只是多一列 `AttrLayer`

| 层 | 内容 | 举例 | 何时上 |
|---|---|---|---|
| **通用（12 条）** | 每条条款都该有的，相当于"姓名年龄"；且必须同时覆盖**企业端**与**执行端** | 企业端：分项要求、企业须提供材料；执行端：要求形态、检查方式、检查深度、取证剧本；共有：条款作用、执行标准、适用范围、适用条件、适用过程、影响程度 | 第一批，一次到位 |
| **条款族专属** | 按 4–10 章各自需要 | 8.3 设计开发 → 设计阶段 / 验证方式 / 评审记录；8.4 采购 → 供方评价方式 / 外包类型；7.1.5 → 校准周期 / 溯源等级；9.2 → 内审频次 / 内审员资格 | 试填 9001 时按需补 |
| **标准专属** | 13485 / 45001 特有 | 13485 → 灭菌方式 / 洁净级别 / 法规要求；45001 → 危险源类型 / 防护层级 | 跑 13485 / 45001 时补 |

> 池子变大不改结构，只是 `cert_clause_attr_def` 多几行。三个层共用一个表、一套字段，靠 `AttrLayer` 区分。

### 3.2 通用 12 条：按"端"分三组

**一条条款必须同时回答两个问题**：企业该拿出什么（企业端）、审核员怎么验证（执行端）。只有一端 = 条款未就绪。

| # | `Code` | 属性名 | 端 | 值类型 | 来源 | 唯一决定的事 |
|:--:|---|---|:--:|---|---|---|
| 1 | `ClauseIntent` | 条款作用 | 共有 | `text` | 固定 | 语义归纳锚点 + NC 理由出处 |
| 2 | `Obligation` | 执行标准 | 共有 | `dict` | 固定 | **开 NC 的闸门**（强制/应/宜/可） |
| 3 | `Applicability` | 适用范围 | 共有 | `dict` | 固定 | 要不要查（通用 / 有条件 / 不适用） |
| 4 | `ApplicabilityCondition` | 适用条件 | 共有 | `text` | 固定 | 条件原文，求值由程序读企业事实做 |
| 5 | `Process` | 适用过程 | 共有 | `json` | 固定 | 对应哪些部门（部门矩阵唯一来源） |
| 6 | `Severity` | 影响程度 | 共有 | `dict` | 固定 | 一般 / 严重 / 观察 |
| 7 | `RequirementItems` | 分项要求 | 企业端 | `json` | 固定 | 条款内部判定清单（a)–h)），**不拆检查项**，只用于 NC 措辞与完整性核对 |
| 8 | `Artifacts` | 企业须提供材料 | 企业端 | `json`（结构化清单） | **参考** | 要哪些规则文档 / 内审记录 + 应含要素 |
| 9 | `EvidenceKinds` | 要求形态 | 执行端 | `dict`（多选） | 固定 | 去哪个池子找证据：文件 / 记录 / 现场 / 人 |
| 10 | `CheckModes` | 检查方式 | 执行端 | `dict`（多选） | 固定 | 查哪些维度：有无 / 完整 / 正确 / 时限 / 一致 / 可追溯 |
| 11 | `VerificationLevel` | 检查深度 | 执行端 | `dict` | 固定 | 存在 / 执行（可选：有效） |
| 12 | `EvidenceChain` | 取证剧本 | 执行端 | `text` | 固定 | 看什么、问谁、抽几份、记在哪（**不提前给企业**） |

**为什么是 12 条而不是 9 条**：`Process` 不配，部门矩阵算不出来；`VerificationLevel` 不配，NC 轻重只能靠审核员临场感觉；`EvidenceChain` 不配，现场取证没有剧本。这三件是每天都要用的，不能按条款族挑着配。

**为什么只有第 8 条是参考值**：前 11 条都是标准自己说死的，换哪家企业都一样；只有"要哪些材料"是标准给了期望、真值在企业手里。

> 属性池仍分层（通用 / 条款族专属 / 标准专属），只是"通用"这一层现在有 12 条且带端归属。专属层继续按需补：8.3 设计开发 → 设计阶段 / 验证方式；8.4 采购 → 供方评价方式；13485 → 灭菌方式 / 洁净级别。

### 3.3 "这个职业必须有什么"：必填集放代码，不放表

不建新表。按章号在代码里定必填集，低于这个集在完备度视图里显示红色。

```csharp
// 共有必填：任何条款都必须有
static readonly string[] Common = { "Obligation", "Applicability", "Process", "Severity" };

// 双端门槛：两组各至少 1 条，缺一端 = 未就绪
static readonly string[] EnterpriseSide = { "RequirementItems", "Artifacts" };
static readonly string[] AuditorSide    = { "EvidenceKinds", "CheckModes", "VerificationLevel", "EvidenceChain" };

// 按章追加
static string[] ExtraAttrs(string clauseNumber) => clauseNumber.Split('.')[0] switch {
    "7" or "8" => new[] { "ClauseIntent", "RequirementItems", "Artifacts", "EvidenceKinds", "CheckModes" },
    _          => new[] { "ClauseIntent" }
};
```

**为什么放代码**：必填集是"我们对国标的理解深度"，会随认知变化；放代码可以随版本发布一起回归，放表则会被当成用户可改的配置。

### 3.4 完备度视图：专家一眼看出"吃没吃透"

| 状态 | 含义 | 颜色 |
|---|---|---|
| 已配 | 有值且已复核 | 绿 |
| 不适用 | 这条款本来没这个属性（如 7.3 无适用条件） | 灰 |
| **未配** | 该有但没有 → **没吃透** | 红 |
| 待复核 | AI 起草未确认 | 黄 |

红色一多，就说明这批条款还没标准化完，不能拿去跑业务。这是"专家看一遍就知道我们到底懂不懂"的落地形式。

## 四、条款配置（L1）：这条款要求什么

**唯一键**：`(StandardCode, ClauseCode, AttrCode)`。

**两类值，处理方式不同**：

| 类型 | 存什么 | 谁给 | 缺了会怎样 |
|---|---|---|---|
| **固定值** | 值本身（shall / 通用 / 严重 / [有没有,时间]） | 专家读国标；AI 可起草 | 缺 → **条款未就绪**，禁止进入预检查 |
| **参考值** | 期望（[设备台账, 校准证书]），不是实际 | 专家读国标；企业不能改 | 缺 → 同样**未就绪**；有期望但企业没交 → **企业缺口**（正常业务结果） |

**两种空，含义完全不同**：

| 状态 | 表现 | 含义 |
|---|---|---|
| 未配置 | 没有这一行 | 还没提取 |
| 明确无 | 有行值为空 | 提取过，确实不要求（如 7.3 无任何材料） |

**就绪判定分两层**（这是"能不能用"与"是谁的问题"的唯一判据）：

```
第一层 双端门槛（不满足 = 条款不可用）
  企业端 0 条（RequirementItems / Artifacts 都没有）  → clause_incomplete
  执行端 0 条（EvidenceKinds / CheckModes / VerificationLevel / EvidenceChain 都没有） → clause_incomplete
  共有必填缺任一（Obligation / Applicability / Process / Severity） → clause_incomplete

第二层 值是否齐（过了第一层才看）
  固定值缺任一必填       → clause_incomplete（我们的问题）
  参考值缺期望           → clause_incomplete（我们的问题）
  期望已填、企业无对应   → enterprise_gap（企业的问题，正常结果）
```

> 双端门槛必须在前：只有企业端要求的条款，审核员到了现场没有动作可做；只有执行端要求的条款，企业不知道该交什么。两种都不能进认证计划。

> 没有这套判定，界面上"空"只有一种样子，专家无法判断是模型没吃透还是企业不合规，审核员也无法确定该怪谁。

**适用性不在这张表**：「这条款对这家企业不适用」是企业侧判定，不是标准级配置。

## 五、检查项 = 条款的组合与拆分（本次改动的核心）

### 5.1 为什么要这一层

真实报告里 **89 个检查项 ÷ 67 个唯一条款 = 1.33 倍**；同一分支内既有拆分又有合并（`7.1` 拆到三级、`7.1.5` 又合回二级）。所以：

- 检查项**不等于**条款，也不等于叶子条款；
- 合并/拆分不是随意，而是有可计算判据。

### 5.2 两类合并，必须分开建模

| 类型 | 含义 | 影响 | 何时定 |
|---|---|---|---|
| **定义级合并** | 几个条款合成**一个检查项**（表格里只出现一个编号） | 改变检查项清单和工时 | 计划阶段 |
| **记录级合并** | 几个检查项**共用一段审核记录** | 只影响写法，不影响清单 | 记录阶段 |

不分开，就会永远出现"检查项数、条款数、证据条数"三个口径对不平。

### 5.3 判据：能不能用一份证据问完

```
停在这一层，能用一份证据问完  → 就停在这一层（默认取叶子）
一份证据问不完                 → 继续拆
几条款的要求形态 + 要的材料高度重合 → 可合并（定义级）
```

判据用 `EvidenceKinds` + `Artifacts` 的重合度计算。**这也是这两个属性必须是结构化值、不能是自由文本的原因**——自由文本算不出重合度。

### 5.4 三个口径必须始终分开报

| 口径 | 定义 | 用途 |
|---|---|---|
| 条款数 | 标准里的条文数（273） | 覆盖度、完备度 |
| 检查项数 | 组合/拆分后 × 部门 × 审核员 | 工时、人日、计划 |
| 证据条数 | 实际采集到的证据 | 报告、可追溯 |

### 5.5 落表建议

| 表 | 作用 | 归属 |
|---|---|---|
| `cert_clause_group` | 定义级组合：组码 + 成员条款 + 组合判据 | 规则侧（标准级，无机构） |
| `cert_org_merge_pref` | 机构合并习惯（这家机构固定把哪几组并起来） | 机构级 |
| 检查项实例表 | 条款（组）× 部门 × 审核员 × 场次 | 企业侧（另立） |

> 本文只定"有这一层、判据是什么、表怎么归属"；实例层的字段待企业侧设计时定。

## 六、五个提示词家族（规则侧定义，企业侧执行）

属性只是"零件"，要变成判断，必须组装成提示词。四个模型（条款 / 文档 / 准备 / 检查）最终都落在下面五个家族上。

| 家族 | `PromptType` | 输入 | 输出 | 归属 | 何时执行 |
|---|---|---|---|---|---|
| **① 条款属性预生成** | `clause_attr` | 条款正文 | 9 属性 | 规则侧 | 建库时一次性 |
| **② 文档提取** | `doc_extract` | 一份企业文档 + 该标准的文档要求 | 单文档事实（含候选条款 + 证据强度） | 每标准一份 | 企业侧（上传后） |
| **③ 准备检查** | `readiness` | 全部文档事实 + 内审资料 + 期望 | 齐全性 / 一致性 / 疑点四分类 / 部门矩阵 / 入场计划 / 预NC | 每企业 × 每标准 | 企业侧（入场前） |
| **④ 条款判断** | `clause_judge` | 9 属性 + 文档事实 + 证据 | 判定（含疑点走向） | 每标准一份 | 企业侧（准备与现场各一次） |
| **⑤ 机构证据生成** | `evidence_style` | 条款属性 + 机构风格 | 取证剧本 / 证据包结构 / 记录写法 | 每机构（可再按标准） | 企业侧（排计划时） |

**编排关系**：③ 负责"找疑点、排任务"，对每条可疑条款调 ④（第一次，只有文档）；现场补证后调 ④（第二次，文档 + 现场），产出正式结论。**同一个 ④ 模板，只换证据变量。**

> 家族 ③④⑤ 的完整设计（疑点分类、部门矩阵、入场计划、证据完善、NC 疑点分析）见 `29-认证准备与体系检查模型-V1.md`。

### 6.1 三条红线（五家族都适用）

1. **提示词只产"读到了什么"，不产"合格标准"**。合格标准在 `cert_validation_rule`（阈值、模板）。
2. **找不到就交空，禁止推测**。空 ≠ 没有。
3. **结论必须带锚点**（时间 / 地点 / 人物 / 数值至少一项），否则不可复核。

### 6.2 条款判断提示词的变量契约

| 变量 | 来源 | 说明 |
|---|---|---|
| `standard` | 规则侧 | 标准名 + 版本 |
| `clause` | 规则侧 | 条款号 + 标题 + 正文 |
| `attrs` | 规则侧 | 9 属性（固定值原样注入；参考值注入"期望"） |
| `matchedDocs` | 企业侧 | 该标准视角的文档提取结果 + 可信度 |
| `evidence` | 企业侧 | 现场 / 记录 / 访谈事实（只描述事实） |
| `rules` | 规则侧 | 本次适用的判定规则（维度 + 阈值） |

### 6.3 输出契约（固定，不许自由发挥）

```json
{
  "verdict": "conform | nc | observation | na | pending",
  "severity": "major | minor | null",
  "reason": "必须从证据长出，不得空泛",
  "anchorText": "原文锚点：时间/地点/人物/数值",
  "evidenceRefs": ["证据码"],
  "confidence": 0.0,
  "missingInfo": ["若要下结论还缺什么"]
}
```

> `pending` 是**正常结果**，不是失败。模型不确定时必须给 `pending`，不许凑结论。`unknown ≠ missing` 是红线：没查到不能写成"没有"。

### 6.4 提示词的存放与治理

- 存 `wf_prompt_template`，按 `PromptType` 区分五个家族；`StandardCode` 用标准 GUID，空表示平台兜底。
- 每个标准一份；机构级在证据家族上再叠加一层（带 `OrgCode`）。
- 必须有：版本、发布/停用、测试运行、命中回退告警（用了平台兜底必须显示"该标准尚无专属提示词"）。
- 改提示词 → 相关结果失效重算，不允许新旧混用。

## 七、机构差异只有一个入口

规则侧的表**没有** `OrgCode`。机构差异只出现在三处，且都在"怎么取证/怎么写"，不在"要求什么"：

| 差异 | 载体 |
|---|---|
| 证据组织方式（证据包结构、记录写法、抽样口径） | `cert_org_evidence_style` + `evidence_style` 提示词 |
| 提示词措辞 | 提示词模板的机构级版本 |
| 合并习惯（固定把哪几组合并） | `cert_org_merge_pref` |

> 判据一句话：**换一家机构，条款要求不变、只是取证方式变** ⇒ 机构差异不得进入条款属性表。

---

## 八、与企业侧的分界：交付契约，不共享表

规则侧交给企业侧的只有 6 样东西：

1. 条款清单（标准 × 条款）
2. 属性定义（池 + 层 + 值类型）
3. 条款配置（固定值 + 参考值期望）
4. 标准侧文档要求（该有哪些文档、该含什么、作用）
5. 三个家族的提示词（生效版本）
6. 判定规则（`cert_validation_rule`）

企业侧**不得反写**以上任何一项。企业侧产生的值、证据、NC 一律落在企业侧表。

### 8.1 多标准隔离（一标准一套，不许合并）

- 一个标准 = 一套提示词 + 一套条款配置 + 一套文档要求。
- 企业做 N 个标准 ⇒ **N 份文档提取结果 / N 套值 / N 套 NC / N 份报告**。
- 基础资料（营业执照、组织图、设备清单）只存一份，但**结论不共享**。
- 属性池跨标准共享一份（复制 4 份必然语义漂移）。

### 8.2 `StandardCode` 有三种口径，混了不报错只静默零命中

| 表 | 存什么 | 例 |
|---|---|---|
| `cert_iso_standard.StandardCode` | 短码 | `iso9001` |
| `cert_iso_standard.Code` / `cert_iso_clause.StandardCode` | GUID | `c9d3e1f5-…` |
| `cert_clause_attr.StandardCode` | 当前为短码（技术债，待统一） | `iso9001` |
| `wf_prompt_template.StandardCode` | GUID | `c9d3e1f5-…` |

规则：**与条款同查询（`ClauseCode` 是 GUID）⇒ 用 GUID**；`cert_clause_attr` 是唯一短码表，跨口径处必须显式换算并注释。

## 九、验收标准（规则侧做完怎么算完）

| # | 验收项 | 判据 |
|---|---|---|
| 1 | 属性池 | 通用 12 条（带端归属）+ 专属层 ≥ 30 条；每条有层、端、类型、用途 |
| 2 | 条款配置覆盖 | 273 条条款 × 必填集，红（未配）为 0 |
| 3 | 固定值 | 必填固定值无空；`Obligation`/`Applicability`/`CheckModes`/`Severity` 全部有值 |
| 4 | 参考值 | `Artifacts` 为结构化清单；无期望的条款为 0 |
| 5 | 文档要求 | 每标准的核心文档类型齐全，且有国标依据原文 |
| 6 | 提示词 | 五家族 × 4 标准均有生效版本；平台兜底使用有告警 |
| 7 | 组合/拆分 | 组合组可追溯到条款；三个口径能分别报数 |
| 8 | 回归集 | 真实检查单的「标准×条款」组合全覆盖，改属性后重跑 0 回归 |

> 回归集口径统一为**真实检查报告里的「标准 × 条款」组合**，不要再用"58 / 89 / 273"混着说。

## 十、实施路线（只列规则侧）

```
阶段一（现在）：规则侧，先把标准翻译对
  1  属性池：通用 12 条 + AttrLayer + AttrSide + 专属层样板
  2  条款配置：AI 预生成 → 人工复核 → 完备度视图（红黄绿灰）
  3  条款判断提示词：每标准一份，变量与输出契约固定
  4  标准侧文档要求：国标驱动，先做 9001
  5  机构证据生成规则：先做 1 家机构 + 9001
  6  组合/拆分：定义级组合表 + 判据 + 三个口径报数

阶段二（已出设计，未实现）：企业侧 —— 见 29 号
  企业档案/部门 → 上传与提取（每标准一份）→ 准备检查（缺口/疑点/入场计划/预NC）
  → 现场取证 → 条款判断 → 正式 NC → 报告
```

> 规则侧没做完就做企业侧，等于拿没校准的尺子量东西：所有企业结果都会错，而且错得看不出来。

## 十一、红线清单（违反 = 返工）

1. 规则表出现 `OrgCode` / `EnterpriseCode`。
2. 一行同时描述"标准要求"和"企业实际"。
3. 属性池按"每条款都要有"来限制条数。
4. 把企业实际值写进条款配置。
5. 把 `Artifacts` 写成自由文本（组合判据、缺口判定都会失效）。
6. 用提示词下结论（提示词只描述事实）。
7. `unknown` 被当成 `missing` 自动推 NC。
8. 多标准合并成一份提取结果 / 一份 NC。
9. 检查项数、条款数、证据条数混用一个口径报数。
10. 机构差异写进条款属性表。
