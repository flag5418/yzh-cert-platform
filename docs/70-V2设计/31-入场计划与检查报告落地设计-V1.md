## 一、目标与验证判据

本次不是把 P1–P7 全部做完，而是**用最短路径验证"条款属性驱动"这套模型是否成立**。验证的铰链是**提示词编排（readiness → plan → judge → report）能否产出专家认得出、追得回、拆得开的计划与报告**。

| 验证对象 | 判据（来自 30 号 §十四 / 29 号 §六） |
|---|---|
| **入场计划** | 计划能解释"为什么这条在现场、那条在远程"（疑点四分类驱动），且总时长 ≤ 时间预算（30 号 P4 出口） |
| **检查报告** | 按标准拆分；每条 NC 能回指证据链与锚点；**报告不产生新判断**（30 号 §十） |
| **模型本身** | 漏查率 / 一致率 / 可追溯率可量化；`unknown` 不推 NC；待确认不写不适用（红线） |

**最小验证形态**：一家真实企业 + 一个标准（建议 iso9001），资料上传 → 文档事实 → 画像/部门/适用性 → 疑点分拣 → 入场计划 → 现场检查/证据 → NC → 报告，全程跑通一次。多标准、机构模板、联网 Skill 均后置。

## 三、数据层设计（8 张企业侧表）

> **通用纪律（违反 = 返工，源自 24 号 §0.7 / AGENTS.md 铁律）**：
> - 企业侧**每张表都带 `StandardCode`（GUID 口径，与 `cert_iso_clause` 同）**；⛔ 禁止 `StandardCodes` JSON 列。
> - ⛔ 禁止 `Enable` 列；启用/禁用统一 `IsValid`（tinyint）。
> - 排序列一律 `Sort`（int）；状态列一律 `Status`（string）。
> - 审计列 `CreateBy/CreateTime/UpdateBy/UpdateTime/DeleteBy/DeleteTime/IsDeleted`，其中 `CreateBy/UpdateBy/DeleteBy` **必须等于 `Sys_User.Code`**（铁律六），时间一律 `DateTime.Now`（铁律十）。
> - 字段名 PascalCase 逐字一致（DB 列 = C# 属性 = TS 字段）。
> - 所有新增/更新走 `GetByCode` 分流（`Code` 业务键，绝不靠 `Id` 关联，铁律四）。

## 四、引擎层与提示词编排

### 4.1 六个提示词家族（按标准一份，29 号 §三 扩展）

| 家族 `PromptType` | 输入 | 输出 | 落地表 |
|---|---|---|---|
| `enterprise_fact_build` | 文档事实 + 公开信息 | 画像事实 JSON（§3.1） | `cert_enterprise_fact` |
| `applicability_suggest` | 条款属性（Applicability/Condition/Process）+ 企业画像 | 适用/不适用/待确认 + 依据 | `cert_clause_applicability`（建议，人确认） |
| `readiness` | 文档事实 + 条款属性 + 企业组织 | 齐全性/一致性/疑点四分类/部门矩阵/预NC | `audit_plan_item`(草稿) + `check_finding`(预NC) |
| `plan_build` | 疑点 + 部门矩阵 + 审核组 + 时间预算 | 任务表（远程/现场/部门/时长/分工/必查/风险） | `audit_plan` + `audit_plan_item` |
| `clause_judge` | 条款属性 + 文档事实 + 现场证据 | 判定 + 疑点五走向（两次调用：准备/现场） | `cert_check_finding` |
| `report_assemble` | 检查结论（按标准） | 报告章节 JSON（**不生产新判断**） | `cert_audit_report` + `_item` |

> 编排关系（29 号 §三）：`readiness` 调 `clause_judge`（第一次，仅文档）；现场补证后 `clause_judge`（第二次，文档+现场）→ 确认/推翻/升降级；`report_assemble` 只聚合、不判断。

### 4.2 服务编排（落 `CertPlatform.Admin/Services/Cert/` 或 `Auditor/Services/`）

```
EnterpriseFactService.Build(enterpriseCode, files)   → fact rows（AI 辅助 + 人改）
ApplicabilityService.Suggest(...)                     → 裁剪建议（AI + 人确认）
ReadinessService.Run(standardCode)                   → points + deptMatrix + preNc
PlanBuilderService.Build(planCode)                   → 任务表 + 时间预算校验（Σ时长≤预算，超则砍并记理由）
ClauseJudgeService.Judge(evidenceCode, stage)        → finding（verdict + doubtStatus）
ReportBuilderService.Assemble(standardCode)          → 报告章节（聚合，不判断）
```

**时间预算校验（30 号 §8.1）**：`Σ item.EstMinutes > BudgetDays×BudgetMinutesPerDay` → 拒绝确认，提示砍单顺序（低风险→可远程补证→抽样可减），砍掉的写 `SamplingNote` 理由。

**多标准隔离**：以上服务全部以 `StandardCode(GUID)` 为入参维度，一次现场 N 个标准 = N 次编排、N 份计划/报告。

## 六、端到端时序（一企业一标准，验证模型）

```
上传资料 → M2 文档提取（文档事实）
  → enterprise_fact_build → 画像（性质/产品/工艺/设计职责…）
  → 手工建部门 + ResponsibleProcesses
  → applicability_suggest + 人确认 → 裁剪清单（适用/不适用/待确认）
  → readiness（调 clause_judge 第一次）→ 齐全性/一致性/疑点四分类/部门矩阵/预NC
  → plan_build → 任务表（远程/现场/部门/时长/分工）→ 时间预算校验
  → 现场：evidence 录入（锚点必填）→ clause_judge 第二次 → 确认/推翻/升降级
  → report_assemble → 按标准报告（结论来自检查过程，不新判）
```

## 七、实施序列与验证检查点（最快验证）

| 增量 | 内容 | 验证检查点（出口判据） |
|---|---|---|
| **0 前置** | P1 全量生成目标标准属性；确认 M2 提取契约可达 | `cert_clause_attr` 目标标准 78 条 × 8 属性齐平；文档事实可拉 |
| **1 建表** | §三 8 表 + 实体 + EntityConfig + 控制器（`YzhControllerBase<>`）+ 菜单 | `dotnet build` 0 Error；冒烟 CRUD 通 |
| **2 画像/部门/适用性** | 专家端前 2 页（手动为主 + AI 辅助） | 能建出"一企业一标准"的裁剪清单，待确认项显眼 |
| **3 readiness** | `enterprise_fact_build`+`applicability_suggest`+`readiness` 提示词 + 疑点页 | 拿真实资料跑出疑点四分类清单，专家认不认（29 号验收 1–5） |
| **4 入场计划** | `plan_build` + 计划工作台 + 时间预算校验 | 计划能解释"为什么这条在现场、那条在远程"且总时长 ≤ 预算（30 号 P4） |
| **5 现场/NC** | 证据页 + `clause_judge` + NC 页 | 每条预NC 推进到确认/推翻/待补之一（29 号验收 6）；无锚点结论为 0 |
| **6 报告** | `report_assemble` + 报告预览 | 按标准拆分；一致率/可追溯率可量化（30 号 P6） |

**最快验证 = 增量 0→4**（拿到真实企业的入场计划即证明模型能"分拣 + 排程"）；增量 5–6 补齐"证据→结论→报告"闭环。

1. 一企业一标准：上传资料 → 跑出**入场计划**（任务表含远程/现场/部门/时长/分工，总时长 ≤ 预算）。

3. 红线零违反：`unknown` 不推 NC；待确认不写不适用；部门名不自造；多标准不合并结论；无锚点不出结论。
