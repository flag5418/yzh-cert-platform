## 一、核心设计四句话

> 1. **文档只提一次，多标准视角**：每份企业文档走一遍 LLM，产出通用属性 + 各标准视角的结构化 JSON。
> 2. **标准驱动提取**：提取字段由国家标准（GB/T）驱动定义，不同标准对同一文档有不同的关注点。
> 3. **条款执行 = 供给 + 推理**：供给层自动匹配文档 JSON 中的字段，推理层用固定模板统一处理。
> 4. **LLM 调用线性可控**：200 份文件 = 200 次，80 个检查项 = 80 次，总计 ~360 次，可预算、可执行。

## 二、标准驱动：为什么是核心

### 2.1 现象：不同标准对同一文档关注点不同

```
一份《环境因素识别及评价表》：

  → ISO 14001（环境）：关注"多因子分析法、重要环境因素清单、控制措施"
  → ISO 45001（安全）：关注"危险源辨识、LEC 法、不可接受风险控制"
  → ISO 9001（质量）：基本不引用这份文档
```

```
一份《工序流转卡》：

  → ISO 9001（质量）：关注"工艺参数是否成文、检验点设置、防错充分性"
  → ISO 14001（环境）：可能关注"该工序是否产生环境因素（噪声、废气）"
  → ISO 45001（安全）：可能关注"该工序是否存在危险源（机械伤害、高温）"
```

```
一份《内审记录》：

  → ISO 9001（质量）：关注"内审方案、审核发现、纠正措施闭环"
  → ISO 14001（环境）：关注"环境体系的内审覆盖范围"
  → ISO 45001（安全）：关注"安全体系的内审覆盖范围"
```

### 2.2 规则文档 vs 内审记录——本质不同的两类

```
规则文档（作业指导书、工艺卡、检验规程）→ 提取「写了什么要求」
  · 这些是组织"说"的——规定层面
  · 专属字段：工艺参数、检验标准、工序流程...

内审记录（审核报告、不符合项报告、纠正措施单）→ 提取「执行得怎么样」
  · 这些是做"做"的——执行层面
  · 专属字段：审核日期、不符合项数、审核结论...
```

规则文档回答的是「有没有规定」，内审记录回答的是「规定有没有被执行」。这是两种不同性质的证据，提取字段天然不同。

### 2.3 结论：提取由标准 + 文档分类共同驱动

```
驱动因素 1：文档分类 → 决定文档的基础属性结构（通用 + 分类专属）
驱动因素 2：ISO 标准 → 决定该标准下需要从这个文档提取什么具体信息

最终提取 = 通用属性（共享层）+ 标准视角层（按标准各自投影）
```

## 三、标准 Markdown：提示词的源头

### 3.1 国家标准本身是最好的提示词来源

GB/T 19001、GB/T 24001、GB/T 45001 等国家标准，对每类文档需要写什么有非常明确的定义：

```
GB/T 19001-2016  8.1e)
  "组织应形成文件的信息：
   1) 拟生产的产品或提供的服务的特性
   2) 拟进行的活动的特性
   3) 拟获得的成果"
         ↓ 标准直接定义了
   提取提示词中应包含：
   · 是否描述了产品/服务特性？
   · 是否描述了活动特性？
   · 是否描述了预期成果？
```

不需要人工猜测"该从生产记录里提取什么"——国标已经定义好了。

### 3.2 标准落地为 Markdown 文件

```
步骤 1：将国标中涉及「文档/成文信息/记录」的条文提取出来
     → 按 ISO 标准分册生成 Markdown 文件

步骤 2：Markdown 文件作为提示词的「事实来源」
     → 编写提取提示词时直接引用
     → 或让 AI 分析该 Markdown 文件来自动生成提取要求
     → 复用我们当前系统的提示词分析功能

步骤 3：「文档分类 × ISO 标准」→ 专属提取字段清单
     → 预生成、可配置、可扩展
```

### 3.3 标准 Markdown 的文件结构

```
docs/standard-knowledge/
├── iso9001/
│   ├── 4.理解组织.md
│   ├── 5.领导作用.md
│   ├── 6.策划.md
│   ├── 7.支持.md
│   ├── 8.运行.md              ← 8.1/8.2/8.3/8.4/8.5 等
│   ├── 9.绩效评价.md
│   └── 10.改进.md
├── iso14001/
│   ├── 4.组织环境.md
│   ├── 5.领导作用.md
│   ├── 6.策划.md              ← 含 6.1.2 环境因素、6.1.3 合规义务
│   ├── 7.支持.md
│   ├── 8.运行.md              ← 含 8.1 运行策划和控制、8.2 应急
│   ├── 9.绩效评价.md
│   └── 10.改进.md
├── iso45001/
│   └── ...（结构同 14001）
└── cross-standard/             ← 跨标准的交叉引用说明
    ├── 公因子文档清单.md       ← 哪些文档被多个标准引用
    └── 差异对照表.md           ← 同一文档各标准关注点差异
```

> 这些 Markdown 文件既是提示词的事实来源，也是体系审核知识的资产沉淀。一次投入，多处使用（文档提取提示词生成、条款属性配置、推理模板编写）。

## 四、文档建模：标准驱动的两层提取 → 一份 JSON

### 4.1 三层提取结构

```
一份文档输入 + 企业认证标准列表（如 [iso9001, iso14001, iso45001]）
      │
      ▼
┌─────────────────────────────────┐
│ 第 1 步：通用属性（所有标准共享） │  ← 一次提取，所有标准共用
│ · 文档名称 / 文档编号            │
│ · 过程归属（部门 + 过程）         │
│ · 文档类型（规则/内审/记录/资质…）│
│ · 文档分类（运营/生产/管理/…）    │
│ · 核心内容摘要                   │
│ · Markdown 原文                  │
└─────────────┬───────────────────┘
              │
              ▼
┌─────────────────────────────────┐
│ 第 2 步：标准视角提取             │  ← 每个标准各自关注不同字段
│                                   │
│ ISO 9001 视角：                   │
│   该文档在质量体系中的角色和关注点  │
│                                   │
│ ISO 14001 视角：                  │
│   该文档在环境体系中的角色和关注点  │
│                                   │
│ ISO 45001 视角：                  │
│   该文档在安全体系中的角色和关注点  │
│                                   │
│ （某标准不引用该文档 → null）       │
└─────────────┬───────────────────┘
              │
              ▼
      合并为一份 JSON 输出
```

### 4.2 每份文档的最终 JSON 结构

```json
{
  "docCode": "DOC-2026-001",
  "docName": "环境因素识别及评价表",

  "universal": {
    "processDept": "综合部",
    "processName": "环境因素辨识",
    "docType": "规则文档",
    "docCategory": "监测类",
    "coreContent": "该文档识别了公司办公和生产区域的环境因素...",
    "markdown": "## 1. 办公区域\n- 废纸（一般）\n- 废灯管（有害）..."
  },

  "standardView": {
    "iso9001": null,

    "iso14001": {
      "评价准则": "多因素分析法（时态×状态×类型三维评分）",
      "识别范围": "办公活动 + 生产活动",
      "重要环境因素": "粉尘排放（D=180）、废水排放（D=120）、噪声（D=90）",
      "控制措施": "加装布袋除尘器（粉尘）、污水处理站（废水）",
      "统计指标": "一般环境因素 12 项、重要环境因素 3 项",
      "法规关联": "每一项因素对应了适用的法律法规条款"
    },

    "iso45001": {
      "危险源": "文档中未提及",
      "LEC评分": "文档中未提及",
      "控制方式": "文档中未提及"
    }
  }
}
```

> 关键：ISO 9001 的 `null`、ISO 45001 的「文档中未提及」，都是**显式表达**——绝不留空让你猜。

### 4.3 缺失字段的处理规则

| 场景 | JSON 中的表达 | 含义 |
|---|---|---|
| 文档中有该信息 | 填入实际值 | 正常提取 |
| 文档中明确不存在该信息 | `"文档中未提及"` | 文档说了性质，但没有这项内容 |
| 某标准完全不引用该类文档 | `null` | 该标准与这份文档无关 |
| 文档有提到但信息不完整 | `{"value": "...", "complete": false, "note": "仅提到部分设备"}` | 有但需要补全 |

**绝不允许**：
- ❌ 留空字符串 `""`
- ❌ 不出现该字段（分不清是没提取还是文档没有）
- ❌ 用 `null` 表达"文档中没有"（`null` 保留给"标准不引用"）

## 五、文档分类与标准视角的配置关系

### 5.1 文档分类 → 每类文档在各标准下需要提取的字段

配置表（示例，可扩展）：

| 文档分类 | ISO 9001 视角字段 | ISO 14001 视角字段 | ISO 45001 视角字段 |
|---|---|---|---|
| **生产类** | 工艺参数、检验标准、工序流程、产品特性 | 该工序产生什么环境因素（废气/废水/噪声/固废） | 该工序存在什么危险源（机械/电气/高温/高处） |
| **运营类** | 产品范围、客户要求、交付标准 | 运营活动中涉及的环境因素 | 运营活动中涉及的危险源 |
| **管理类** | 审批层级、发文范围、决议事项 | 环境目标/方案、资源配置 | 安全目标/方案、资源配置 |
| **内审类** | 审核方案、不符合项数、审核结论、纠正措施 | 环境内审覆盖范围 | 安全内审覆盖范围 |
| **资质类** | 营业范围（与认证范围匹配度） | 排污许可、环评批复 | 安全生产许可、特种作业资质 |
| **设备类** | 设备能力、维护保养记录 | 环保设备运行状态、排放监测 | 安全设备/防护装置配置 |
| **设计类** | 设计输入/输出/评审/验证/确认 | 环境友好设计考量 | 安全设计考量（本质安全） |
| **监测类** | 产品检验数据、合格率 | 环境监测数据（废水/废气/噪声达标） | 职业病危害因素监测数据 |

> **配置驱动**：这张表意味着，文档提取提示词是动态生成的——根据文档分类查到它在每个标准下需要提取的字段组合，拼接成完整提示词，一次 LLM 输出全部。

### 5.2 不同标准下的文档提取提示词（示例）

针对同一类「生产类」文档，三个标准的提取提示词不同：

```
ISO 9001 视角的提取要求：
  请提取该文档中与质量管控相关的信息：
  - 工艺参数、检验标准、工序流程
  - 成文信息的充分性（a 分项视角）
  - 防错设计的充分性（g 分项视角）

ISO 14001 视角的提取要求：
  请提取该文档中与环境保护相关的信息：
  - 该过程产生什么环境因素（废气/废水/噪声/固废）
  - 是否有识别、是否有控制措施
  - 是否对应了适用的法规要求

ISO 45001 视角的提取要求：
  请提取该文档中与职业健康安全相关的信息：
  - 该过程存在什么危险源（机械伤害/触电/高处坠落/噪声）
  - LEC 法评分结果、控制方式
  - 不可接受风险是否纳入管控
```

## 六、执行引擎：供给 + 推理

### 6.1 条款执行的两部分

```
┌─────────────────────────────────────────────────────────┐
│                条款执行 = 供给 + 推理                     │
├────────────────────────┬────────────────────────────────┤
│  来源（供给层）         │  推理（推理层）                  │
│                        │                                │
│  · 条款属性 ──────┐    │  固定提示词模板（结构不变）       │
│                ├──→ 喂入 ──→ LLM ──→ 结论             │
│  · 文档 JSON ────┘    │                                │
│  · 审核员证据 ────→   │                                │
└────────────────────────┴────────────────────────────────┘
```

### 6.2 供给层如何读取标准视角

```
条款 14001-6.1.2（环境因素辨识）
    ↓ 条款属性指示
标准 = iso14001 ｜ 需要：监测类 / 生产类文档
    ↓ 属性匹配
文档池中：docCategory=监测类 → 命中《环境因素识别及评价表》
    ↓ 从 JSON 的 standardView 层取
standardView.iso14001 = {
  评价准则: "多因素分析法",
  重要环境因素: "粉尘排放、废水排放、噪声",
  控制措施: "..."
}
    ↓ 自动填入推理模板
```

```
条款 9001-8.5.1（生产和服务提供）
    ↓ 条款属性指示
标准 = iso9001 ｜ 需要：生产类文档
    ↓ 属性匹配
文档池中：docCategory=生产类 → 命中《焊接工序作业指导书》
    ↓ 从 JSON 的 standardView 层取
standardView.iso9001 = {
  工艺参数: "温度280±10℃、压力0.4MPa",
  检验标准: "焊缝外观无气孔、夹渣",
  成文充分性: "工艺要求已量化"
}
    ↓ 自动填入推理模板
```

### 6.3 推理层：固定模板

```markdown
# 条款符合性检查

## 条款基本信息
标准：{{standardCode}}（{{standardName}}）
条款编号：{{clauseCode}}
条款名称：{{clauseName}}
条款作用：{{clauseIntent}}
约束强度：{{obligation}}

## 该条款的检查要求
{{clauseRequirement}}

## 企业已提供的相关资料（{{standardName}} 视角）
{{#each matchedDocs}}
### {{docName}}
分类：{{universal.docCategory}} ｜ 过程：{{universal.processDept}}-{{universal.processName}}
核心内容：{{universal.coreContent}}

{{standardName}} 视角提取字段：
{{standardView.[standardCode]}}

{{/each}}

## 审核员补充证据（认证执行阶段才有）
{{auditorEvidence}}

## 请基于以上完整信息
1. 判断该条款的符合性（符合 / 不符合 / 观察项）
2. 说明判断依据（必须引用原文中的具体内容）
3. 如为不符合，说明不符合的事实和涉及的分项
```

## 七、LLM 调用预算

### 7.1 三阶段调用量

```
阶段一：文档属性提取（一次性）
  200 份文件 × 1 LLM = 200 次
  （每次提取包含通用属性 + 企业涉及的所有标准视角）

阶段二：认证准备（条款级检查）
  80 个检查项 × 1 LLM = 80 次

阶段三：认证执行（加入证据 + NC 预判）
  80 个检查项 × 1 LLM = 80 次

  ──────────────────────────────────
  总计：~360 次 LLM，线性可控
```

> **关键**：即使企业涉及 3 个标准，文档提取也只做 1 次 LLM，在同一个 LLM 调用中覆盖所有标准视角。不是一份文档跑 3 次。

### 7.2 单次 LLM 的提示词结构（文档提取）

```markdown
# 文档属性提取（标准驱动，一次完成）

请分析以下企业文档，提取属性信息。

## 文档内容
{{documentContent}}

## 该企业认证涉及的标准
ISO 9001（质量管理）/ ISO 14001（环境管理）/ ISO 45001（职业健康安全）

## 第一阶段：通用属性（必须提取）
1. 文档名称
2. 过程归属：这份文档涉及哪个部门、哪个过程
3. 文档类型：规则文档 / 内审记录 / 管理评审 / 监测记录 / 资质证书 / 合同文件 / 其他
4. 文档分类：运营 / 生产 / 管理 / 内审 / 资质 / 设备 / 设计 / 监测 / 其他
5. 核心内容摘要：200 字以内
6. Markdown：将文档内容转写为结构化的 Markdown

## 第二阶段：标准视角提取

### 如果文档分类属于"生产类"：
分别从以下三个标准视角提取该文档在该标准下的相关信息。

#### ISO 9001 视角
提取与质量管控相关的信息。
参考标准定义：{{iso9001_标准Markdown_对应章节}}
提取字段：工艺参数、检验标准、工序流程、产品特性、成文信息充分性
```

### 8.2 阶段二/三的详细执行流程

```
对每个检查项（标准 + 条款构成）：
│
├── Step 1: 供给（自动）
│   ├── 读条款属性 → 属于哪个标准、关注哪些过程
│   ├── 读企业文档池 JSON → 按过程 + 分类匹配
│   ├── 从匹配文档的 standardView[standardCode] 中提取该标准视角数据
│   └── 读审核员证据（阶段三才有）
│
├── Step 2: 组装提示词
│   ├── 推理模板（固定不变）
│   ├── 注入变量：条款要求 + 标准视角文档内容 + 证据
│   └── 组装完成 → 一条完整的 LLM 输入
│
└── Step 3: 执行推理
    ├── 一次 LLM 调用 → 输出符合性结论
    └── 结论写入系统（含锚点原文引用）
```

## 九、扩展性分析

### 9.1 新增一份企业文档

```
影响：文档池多一个 JSON（含所有标准视角）
工作量：1 次 LLM（提取）
```

### 9.2 新增一条条款（或检查项）

```
影响：条款属性配置新增一行（L1）
      推理模板不变
工作量：配置 + 1 次 LLM（检查）
```

### 9.3 更换更强的 AI 模型

```
影响：无需改模板或架构
      自包含调用，换模型只改配置
工作量：改配置
```

### 9.4 新增一个 ISO 标准（如 ISO 50001 能源）

```
影响：标准 Markdown 文件新增一组
      配置表新增一列（该标准下各类文档的提取字段）
      文档 JSON 的 standardView 新增一个 key
      文档提取提示词新增一个视角分支
工作量：配置（不需改代码）
```

### 9.5 文档更新（企业换版）

```
影响：重跑该文档（1 次 LLM）→ 新 JSON 覆盖旧 JSON
工作量：1 次 LLM
```

## 十、与四层属性模型的对齐

```
L0 属性池（cert_clause_attr_def）     ← 已完成，本文不动
    ↓
L1 条款配置（cert_clause_attr）        ← 已完成，本文不动
    ↓
文档 JSON（本文新增）                  ← 通用属性 + 标准视角属性
    ↓                                    ↑
    │                              标准 Markdown（起点）
    ↓
L2 企业值（暂缓）                      ← 未来从文档 JSON 自动生成
    ↓
L3 判定（暂缓）                        ← 未来阶段二/三的输出
```

**标准 Markdown 是整个链条的起点**：
- 驱动文档提取字段定义
- 驱动条款属性配置（现有 L0/L1）
- 构成推理模板中"条款要求"部分的事实来源

## 十一、设计原则总结

| # | 原则 | 落地 |
|---|---|---|
| 1 | **文档只提一次，多标准视角** | 通用属性 + standardView 层 |
| 2 | **标准驱动提取** | 提取字段由国标 + 文档分类共同决定 |
| 3 | **缺失显式标注** | 「文档中未提及」/ `null`（标准无关） |
| 4 | **LLM 调用线性可控** | 200 + 80 + 80 = ~360 次 |
| 5 | **一个推理模板** | 结构固定，变量动态填充 |
| 6 | **供给与推理分离** | 供给只负责"拿什么"，推理只负责"怎么判" |
| 7 | **标准 Markdown 作为知识资产** | 一次整理，多处消费 |
| 8 | **证据叠加不改模板** | 阶段二到阶段三只是多一个变量 |
| 9 | **模型可替换** | 自包含调用，换模型只改配置 |
| 10 | **扩展是"加信息"不是"改逻辑"** | 新文档、新条款、新标准、新分类都是增量 |
