| 项 | 结论 |
|---|---|
| **这是什么** | 认证审核的**准备与检查辅助系统**：把国标条款结构化，把企业资料结构化，替审核员完成"找、比、排、起草"，判定与签字留给人 |

## 一、品类：我们在建一个什么品类

### 1.1 它不是这些东西

| 常被误认成 | 为什么不是 |
|---|---|
| QMS 软件（质量管理软件） | 那是给企业管质量体系的工具，我们是给**审核员判体系**的工具 |
| 文档管理系统 | 文档只是输入，我们不解决"存"，只解决"看懂" |
| 认证业务管理系统 | 那管流程（合同/审批/证书），我们管**内容**（条款满不满足） |
| 通用 AI 问答 | 结论无法回溯到条款、不可辩护、不可复现 |
| 咨询机构服务 | 我们不给结论，只给证据与疑点，判断在人 |

### 1.2 它的品类名（建议）

> **认证审核准备与检查辅助系统**（Audit Readiness & Evidence Assistant）

一句话差异：**它是唯一以"条款"为原子、以"证据矩阵"为底座、把"判定"明确留给人的系统。**

### 1.3 为什么"没人做"——三个条件的交集太窄

做这件事需要同时具备三样东西，缺一样就做不成：

| 条件 | 为什么必需 | 我们的状态 |
|---|---|---|
| **条款可结构化** | 否则没有判定依据，只能靠提示词自由发挥 | ✓ 已入库并已铺属性（iso13485 全覆盖） |
| **真实案例可校准** | 否则不知道"专家会怎么判"，模型永远在对空气优化 | ✓ 手上有 8.5.1 三份专家答案 + 完整 79 页报告 + 企业原始资料 |
| **专家闭环** | 否则"准不准"没有裁判 | ✓ 有可配合测试的体系认证专家 |

> ⚠️ **诚实修正一句**：相邻品类（GRC 平台、审计管理软件、合规 gap 分析工具）在海外与金融/IT 合规领域**是存在的**。我们不宣称"全球首创"；准确的表述是——**在中国体系认证这个场景、以"条款属性 + 证据矩阵"这种建模方式，目前没有成熟产品**。这个差别在对外沟通时很重要：夸大首创会被懂行的人一句话问倒，而"场景 + 建模方式"的差异是站得住的。

## 二、市场与商业路径（评估，不是承诺）

### 2.1 用户盘（你提供的数据）

| 群体 | 规模 | 付费逻辑 |
|---|---|---|
| 认证从业者（审核员/技术人员/咨询） | ~15 万 | **单点付费意愿低**——工具是他们的"个人效率器"，公司不报销 |
| 认证机构 | 800+ | 付费意愿高，**但对数据安全极敏感**；决策链长 |
| 企业（受审核方） | 大量 | **付费意愿最强**：怕"不符合"导致拿证延期/丢单，愿意为"提前发现"付钱 |

### 2.2 当前阶段：口碑闭环，不是变现

当前目标不是收入，是**让一个信得过的专家认可，并愿意主动介绍给同行**。

```
你 + 专家朋友（1 人）
   → 在真实项目里用（2–3 次）
   → 他向 2–3 个同行介绍
   → 同行自己试（无你陪同）
   → 其中 1 个愿意在机构内推荐
```

这条链上真正难的只有第 4 步：**"同行自己试"能成功**。前 3 步靠关系，第 4 步只能靠产品。

### 2.3 同行愿意推荐一个工具的五个条件

| # | 条件 | 对设计的约束 |
|:--:|---|---|
| 1 | **省时间且省得明显** | 必须切在最耗时的环节：找资料、比对、起草，而不是"再学一个系统" |
| 2 | **输出能直接用，不丢脸** | 导出的东西能直接贴进他的报告，措辞不能像 AI 写的 |
| 3 | **不占额外时间**（不用录入、不用配置） | 凡需人额外录入的模块一律不做（见 37 号判据） |
| 4 | **能被一句话转述** | 他要在饭桌上跟同行解释"这东西为什么对"。输出必须可解释到一句话：**"它把这条条款该查什么、这份文件能证明什么、还缺什么列出来了"** |
| 5 | **出错时他自己能发现** | 每条结论带锚点，他一眼就知道对不对；看不见源头的结论不敢用第二次 |

> 第 4、5 条最容易被忽略，但它们决定"**会不会被推荐**"，而不是"会不会被试用"。

### 2.4 澄清一个用词：**垂直深度 ≠ 客户定制**

"高度定制化"容易被读成"按客户定制"，准确的意思应是：**高度垂直**——只为体系认证这一个行业做，做到条款级深度。**这与"标准产品"不但不矛盾，反而是标准产品能成立的原因。**

| 概念 | 含义 | 我们的主张 |
|---|---|---|
| **垂直（vertical）** | 只做一个行业、做到条款级深度 | **要**——这是壁垒 |
| **定制（customization）** | 按单个客户改功能、改表结构 | **不要**——会毁掉口碑与数据可比性 |
| **机构风格** | 检查表版式、判定词、措辞 | **要，但只作为"覆盖项"** |

**输出策略（写死）**：

```
默认 = 统一标准输出（所有机构一致）
可选 = 机构风格覆盖（版式 / 判定词 / 措辞，按 ScopeKey 绑定）
```

**为什么"统一输出"是资产而不是限制**：只有输出统一，跨机构的"条款 → 证据 → 判断"对才能横向比较、才能累积成模型。一旦每家机构一套输出，数据就不可比，资产无法形成。

> **验收口径**：新审核员上手 = **用统一输出就能跑**；选机构风格是**可选动作**。零代码、零配置、零你参与。

### 2.5 一个必须提前想清楚的问题：数据权属

机构的第一个法务问题一定是：**"我们把企业资料和报告传给你，你会不会拿去训练/给别家用？"**

这不是话术问题，是产品设计问题。建议提前确立三条，写进产品说明（不是合同）：

1. **不训练**：客户数据不进入任何模型训练；
2. **可删除**：项目结束可一键清除，且提供删除证明；
3. **可私有化**：核心链路支持部署在机构自己的环境（这是 B 端最大的一票）。

> 这三条不给，T2 大概率谈不下来；给了，T2 才可能。

> ⚠️ **熟人试用期的风险反而更高**：没有合同、没有 NDA，靠的是信任。一旦企业资料外流（哪怕无意——日志、备份、示例数据），毁掉的是关系而不是合同。所以试用期就要做到：**示例数据脱敏 · 日志不含原文 · 试用结束可一键清除**。

### 2.6 后期（不在当前阶段）

| 段 | 对象 | 作用 | 备注 |
|:--:|---|---|---|
| T0 工具 | 专家/审核员 | 获客 + **采集专家判定对** | 免费/低价，**就是当前在做的事** |
| T1 企业端 | 受审核企业 | 现金流（付费意愿最强） | 等口碑成立后再谈 |
| T2 机构端 | 认证机构 | 壁垒 | 数据权属（§2.5）是总闸 |

> 顺序不能颠倒——先做 T2 会因为拿不到数据而做不准；但**当前阶段只做 T0**。

### 2.7 交付形态与计费口径（三种形态的真实成本）

| 形态 | 数据在哪 | AI 成本谁承担 | 真实代价 |
|---|---|---|---|
| **SaaS（按月/按次）** | 你方 | 你 → **必须能按次转嫁** | 最低，迭代最快 |
| **内网 / 私有化** | 机构内 | **机构**（自带模型或自带 Key） | 高：license 机制 + 离线模型/API 代理 + 升级包分发 |
| **单机一键部署包** | 客户机器 | 客户 | 中：docker compose 打包即可 |

**三条结论**：

1. **不做桌面版，做"单机一键部署包"**。本系统是 .NET + MySQL + Redis + MinIO 的运行时，打成桌面应用等于自带一个服务器，且每次更新都要重新分发。"桌面版"的真实需求（数据不出门）用单机 docker 包满足，成本低一个量级。
2. **计费必须能转嫁 AI 成本**：订阅含基础额度 + 超量按次；否则重度用户（一家企业 237 份文档）会把订阅吃穿。
3. **从第一天就埋 token 计量**：每次任务记录 `model / input_tokens / output_tokens / 单价 / 成本`。没有这个数据，定价只能拍脑袋（对应风险 A5）。

## 三、模型评估：这套建模新在哪、弱在哪

### 3.1 五个维度的对比

| 维度 | 传统 QMS 软件 | 通用 AI | 咨询顾问 | **本系统** |
|---|---|---|---|---|
| 原子 | 表单/流程 | 无（自由文本） | 人脑 | **条款 × 要求分项 × 检查单元** |
| 判定依据 | 无（只记录） | 模型内部（不可查） | 经验 | **条款属性 + 原文引用** |
| 证据 | 附件 | 无 | 口头 | **证据矩阵（带锚点）** |
| 可追溯 | 有（流程） | **无** | 无 | **有（条款 → 证据 → 疑点）** |
| 可复用 | 配置不复用 | 提示词可复用 | 人不可复用 | **属性资产跨企业复用** |

### 3.2 三个真正"别人做不了"的点

1. **条款属性资产化**：把"这条条款该查什么、缺什么算疑点、多严重"从专家脑里搬到数据里。这是唯一能随企业数增长而边际成本下降的东西。
2. **证据矩阵**：文档与条款的二维命中表，一份数据同时支撑"缺什么 / 草案 / 报告"三件事。
3. **判定与证据分离**：疑点是证据的推论，NC 是否定量的判定。系统只做前者，人做后者——**这个分离是整个产品能落地的前提**。

### 3.3 三个必须承认的弱点（评审结论）

| 弱点 | 影响 | 现在能做什么 |
|---|---|---|
| **条款属性覆盖率不均** | iso13485 全覆盖，iso9001/iso14001 仅 5 条×8 属性 ⇒ 换个标准草案质量断崖 | 对外只承诺"已验证标准"；先把 iso9001 补齐（它是最大市场） |
| **提取覆盖率低**（237 份文件仅 31 条结果） | 演示时证据矩阵是空的 | 草案不依赖资料（37 号决定 4）；先把 8.5.1 的 30 份记录跑满 |
| **"准"没有基线** | 无法判断模型好坏 | 用 8.5.1 三份专家答案做基准，三项度量（§四-4.6） |

## 四、完整总结设计（一页看懂）

### 4.1 一句话架构

> **一个原子（条款）× 一张矩阵（证据）× 两个提示词族（准备 / 检查）× 三类输出（证据 / 疑点 / 交付物），判断永远在人。**

### 4.2 五层结构

```
① 标准层（无机构）   条款 · 属性 · 要求分项 · 适用条件 · 文档要求 · 检查要点
        ↓ 复用
② 企业层（一企业）   部门 · 职能映射 · 资料 · 提取结果 · 适用性结论
        ↓ 落到
③ 任务层（一任务）   草案 · 入场计划 · 现场证据 · 疑点 · NC · 报告
        ↓ 沉淀
④ 证据层（矩阵）     (证据来源, 条款) 稀疏行 —— 贯穿准备与现场
        ↓ 归因
⑤ 反馈层            人工改动 → 调属性 / 调提示词（越用越准的唯一机制）
```

### 4.3 最小表集（8 张，验收到这 8 张就够跑通）

| # | 表 | 作用 | 状态 |
|:--:|---|---|:--:|
| 1 | `cert_iso_clause` | 条款（原子） | 已有 |
| 2 | `cert_clause_attr_def` / `cert_clause_attr` | 属性定义 / 属性值 | 已有 |
| 3 | `cert_clause_applicability` | 适用性判定（三态 + 理由类型） | 待建 |
| 4 | `cert_document_extraction` | 文档提取（宽扫产物） | 已有 |
| 5 | **`cert_evidence`** | **证据矩阵行（本设计的核心）** | **待建** |
| 6 | `cert_audit_plan` / `_detail` | 计划项 = 检查单元（`PlanItemCode` 可空） | 已有（简化版） |
| 7 | **`cert_finding`** | **疑点 / NC（单表双态）** | **待建** |
| 8 | `cert_prompt_template` | 提示词（`PromptCode + ScopeKey + Version`） | 已有 |

### 4.4 两个提示词族

| 族 | 输入（同一装配器） | 输出契约 | 后校验 |
|---|---|---|---|
| **准备（desk）** | 条款原文 + 属性 + 该条款相关文档（分级装配：原文 > 命中段落 > 全文 > 摘要） | 证据候选（带 `docCode + 位置`）+ 缺口 | 缺锚点 ⇒ 降级 `unknown`，不进结论 |
| **检查（onsite）** | 同上 + 现场证据行 | 疑点候选（带依据 + 差距描述） | 无条款依据 ⇒ 丢弃；严重程度必须有来源 |

> ★ **两条铁律**：① "严格"靠 schema + 校验器，不靠提示词里的"请严格"；② 两族共用**同一个装配器**，否则同条款两次跑结论不可比。

### 4.5 主流程六段（与 37 号一致）

认领准备 → 适用性裁剪 → 检查草案 → 入场计划（**本期暂缓**）→ 现场证据（**本期用最简形态**）→ 疑点与交付。

### 4.6 三项度量（唯一能证明"方向对"的东西）

| 度量 | 定义 | 目标 |
|---|---|---|
| **覆盖率** | 有资料支撑的检查项 / 总项 | 升 |
| **命中率** | 命中专家答案项 / 专家答案总项 | 升 |
| **人工改动率** | 被改的草案行 / 总行数 | **降（最重要的健康指标）** |

> 停止/放行条件：专家愿意留下 **≥ 60%**。低于 60% 不铺量。

### 4.7 从今天到验证的七步

1. 补 8.5.1 的属性缺口（缺 `DocCheckMode`）。
2. 灌满 8.5.1 的 30 份记录 → 跑通宽扫，产出 `(文档, 条款)` 命中。
3. 建 `cert_evidence`，把宽扫结果与人工确认写进去。
4. 建 `cert_finding`，疑点按**条款聚合**推理（不是单条证据）。
5. 装配器 + 两套提示词 + 后校验器。
6. 三项度量跑第一遍，记录基线。
7. 专家对照三份答案逐条 diff，改属性 or 改提示词。

## 五、我的担心（风险登记册）

> 分级：**S = 可能让项目死**，**A = 会造成返工**，**B = 会拖慢**。每条给"触发信号"，因为风险只有在能被观察到时才有用。

### S 级

| # | 担心 | 触发信号 | 应对 |
|:--:|---|---|---|
| **S1** | **建议不准，但你说不清哪里不准**。没有度量时，"专家说感觉不太对"会变成反复改提示词的死循环 | 专家指出不了具体条目，只会说"整体不像" | 三项度量 + **逐条 diff**（把系统输出与专家答案并排）；只要能量化，就永远知道下一步改哪里 |
| **S2** | **责任边界被侵蚀**。客户/机构开始把系统输出当结论；出事时系统成为追责对象 | 有人问"你们系统的判定能不能作为依据"；或内部开始用"判定"这个词 | 字段名一律用"建议/疑点"不用"判定"；导出物固定页脚"AI 辅助生成，须人工复核"；不在系统内做签名与审批。<br>★ **与"AI 辅助编程"的关键差异**：代码错误能在 review 阶段拦住、且可回滚；**审核报告一旦签出不可撤回**。所以系统输出只能停在**草稿态**，永远不进入"已提交 / 已签" |
| **S2b** | **"AI 辅助编程"类比的责任不对称**：编程的中间产物（代码）可反复试错，审核的中间产物（记录）会被存档 | 有人把系统生成的措辞当"已确认记录"存档 | 证据行必须带 `State`（candidate / confirmed）；只有人确认过的才能进导出物；导出的每条结论可见"谁确认的" |
| **S3** | **数据保密与权属**。企业资料 + 报告 + NC 全部出机构，法务必问 | 机构 IT/法务介入，要求私有化或不出数据 | 提前确立三条（不训练 / 可删除 / 可私有化）。**这是 T2 能不能谈成的总闸** |
| **S4** | **单点依赖**。这套模型只完整存在于你一个人脑里；专家时间有限，且不可持续占用于测试 | 你休假两周，项目停摆；或专家连续两次无法参与 | 把模型写成**可执行文档**（37 号 + 本文 + 30 号），把专家从"持续参与者"变成"基准提供者"——一次给出 8.5.1 的答案，之后用它回归 |

### A 级

| # | 担心 | 触发信号 | 应对 |
|:--:|---|---|---|
| **A1** | 条款属性覆盖率不均（iso9001/14001 只有 5 条） | 换标准演示时草案质量断崖 | 对外只承诺已验证标准；优先补 iso9001（市场最大） |
| **A2** | 提取覆盖率太低 | 证据矩阵行数远少于文档数 | 草案条款驱动、资料只增强；先把一个条款的资料跑满 |
| **A3** | 多标准合并表达不了（QES 一体化） | 一体化审核客户演示失败 | 检查单元/计划项从第一天支持多条款 + 多部门 |
| **A4** | 疑点太吵，用户直接关掉 | 每条条款都有疑点，专家一眼扫过不看 | 按"可开 NC + 严重程度"分级；默认只显示高风险 |
| **A5** | **成本算不出来** | 不知道"一个企业跑一遍准备"要多少钱 | 现在就测：一份文档宽扫的 token 成本 × 237。**没有这个数，商业模型就是空的** |
| **A6** | 上下文截断静默丢证据 | 专家问"这份文件你怎么没看到"，你答不出 | 分级装配 + 输出回报"用了哪些文档、哪些被摘要化" |

### B 级

| # | 担心 | 触发信号 | 应对 |
|:--:|---|---|---|
| **B1** | 表与文档口径不一致（`StandardCode` 三种口径、疑点四张表、属性 9 vs 12） | 关联查询静默 0 行 | 一次性对齐清单，分三批清理 |

## 六、怎么判断这套系统"成了"（三个客观标志）

| # | 标志 | 为什么是客观的 |
|:--:|---|---|
| 1 | **人工改动率下降**（连续三次任务递减） | 说明模型在学专家的判断，而不是你在改提示词 |
| 2 | **一个真实项目全程用系统完成**（不是演示、不是部分环节） | 说明链路真的通，而不是每段都能跑但接不起来 |
| 3 | **第二个审核员主动要求用** | 自传播信号。第一个用户可能是因为你请他；第二个不是 |

> 这三个都比"功能清单有多长"更能说明问题。

## 七、结论

1. **方向成立**：以条款为原子、证据为底座、判断留给人——这套建模在体系认证场景里是新的，而且三个前提（条款可结构化 / 有真实案例 / 有专家闭环）你都具备。
2. **打法成立，但当前只做第一段**：专家工具（T0）换数据与口碑 → 企业端（T1）换现金 → 机构端（T2）换壁垒。顺序不能颠倒；**当前阶段的目标是"被同行认可"，不是收入**。
3. **真正要防的不是技术，是四件事**：建议不准却无以度量（S1）、责任边界被侵蚀（S2）、数据权属谈不下来（S3）、模型只存在一个人脑里（S4）。
4. **当下唯一该做的**：8.5.1 一条链跑通 + 三项度量有基线。在此之前的任何铺量，都是把错误放大。

> **一句话**：这套系统真正的资产不是代码，是**"条款 → 证据 → 判断"的可复用对**。工具会过时，这份资产不会。
