# 46 · 认证准备与认证检查 —— 执行链路设计（V1）

> **本文定位**：把「入场计划 → 选检查项 → 一个队列 → 两套提示词 → 内容聚合 → LLM 分析 → 疑点 → 锁定 → NC → 报告」这条链路**设计到可以直接照做的程度**。
>
> **本文不含任何代码改动**。所有「建议改哪一行」都是**待评估项**，评审通过后才动手。
>
> **上游依据**：`29 号`（两个模型）· `32 号`（计划落地）· `41 号`（准备闭环）· `42 号`（两阶段同构）· `43 号`（模块契约 · D1）· `44 号`（数据模型 · G1–G5）· `原型-计划启动工作流.html`（V6 定稿）
>
> **状态**：`待评估` — 含 6 个待裁决点（§十六），裁决前不开工。

## 零、一句话

> **一个计划、两套提示词、一个队列；队列里每一项是一个检查项（条款组合 × 部门）；一个检查项在准备、检查两个分支各跑一次分析，每次分析是一个独立容器（证据链 + 结果 + 疑点），两套分支同一套表结构；锁定在检查项上，锁了就跳过；队列跑着时页面只读，跑完才解锁。**
>
> 三条补充口径（本次明确）：
> ① 提示词落 **`wf_prompt_template`**（独立提示词表，后台 `/business/prompt-template` 可视化编辑 + 自测 + 保存闸门），解析走现有 `IPromptWorkbench`；
> ② 准备与检查**分开执行**，将来可结合；因此页面锁与**分析分支**都按 `(计划/检查项, 方向)` 分粒度；
> ③ **队列执行期间页面不可写，队列进终态才允许编辑**；且**已锁定的检查项即使被勾选，队列也一律跳过**（硬约束，不是提示）。

## 一、先对齐 7 个词

这 7 个词在过往文档里被混用过，本文一律按此表：

| 词 | 含义 | 载体 | ⛔ 不是 |
|---|---|---|---|
| **入场计划** | 一个企业、一个阶段、哪些标准 → 查什么 | `cert_audit_plan`（主表） | 不是任务，不记录执行状态 |
| **检查项** | 条款组合（1..N）× 部门（1..N），是**执行与结论的最小单位** | `cert_audit_plan_detail` **一行** | ⛔ 不新建 `cert_check_item` 表（43 号 D1） |
| **入场分析** | ★ **一次分析**：对某个检查项在**某个分支**（准备/检查）跑一遍，产出「该分支的结果 + 该分支的证据链 + 该分支的疑点」 | `cert_check_analysis` **一行**（§4.5） | 不是结论行，也不是任务项 |
| **认证准备** | 用企业现有文档 + 公开查询，判「资料齐不齐、信息全不全」，产疑点 | `cert_task(TaskKind=prep)` + 分析 `StageKind=prep` | 不是「审文件」，**不判符合性** |
| **认证检查** | 用现场证据，判「符不符合」，产结论与 NC 建议 | `cert_task(TaskKind=onsite)` + 分析 `StageKind=onsite` | 不是「再跑一遍准备」 |
| **疑点** | 一条待澄清/待核实的事，带方向（远程/现场）与动作 | `cert_point`（挂分析） | 不是结论，**不是 NC** |
| **入场安排** | 什么时候、谁去、每个检查项花多久 | `cert_onsite_schedule` + `_slot`（§4.4，本期可延后） | 不是入场计划 |

> **关键区分 ①**：用户说的「入场计划 2 个表」= **入场计划（查什么）**；「由认证准备派生入场计划」= 派生 **入场安排（怎么排）**。两者不是一回事，混了会变成「计划自己生自己」（§4.4 详述）。
>
> **关键区分 ②（本次修订）**：**分析 ≠ 结论**。
> 一个检查项会有**多条分析**：准备 1 次 + 检查 1 次（+ 各自的重跑 N 次）。
> 每次分析是**一个独立容器**，装着「那次用的是哪些证据、产出了什么结果、提出了哪些疑点」。
> 看准备分支 = 看 `StageKind=prep` 的那次分析；看检查分支 = 看 `StageKind=onsite` 的那次分析。
> **两套分支用同一套表结构**，靠 `StageKind` 区分 —— 这是本次修订的核心。

## 二、总体链路

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 入场计划（人建 / 或从模板复制）                                    │
│    cert_audit_plan        企业 + 阶段 + 标准[]                       │
│    cert_audit_plan_detail 检查项 = 条款组合 × 部门   ← 这就是检查项   │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ ② 勾选：全选 / 部分选（含跨标准）
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ③ 建任务 cert_task(TaskKind=prep|onsite)                            │
│    + cert_task_item（任务 × 检查项，只存执行状态）                    │
│    + 入队 cert_expert_task_queue（一个队列）                          │
│           cert_expert_task_queue_item（一个检查项 = 一项）            │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ ④ Worker 领取（同队列串行，MaxConcurrent=3）
                               │    ★ 此刻起 page-lock 生效：本页只读
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ⑤ 检查项装配（ContentAggregator）                                    │
│    条款[] → 逐条款：条款正文 + 6 属性 + 该条款命中的文档摘录           │
│                      （FIND_IN_SET 查 cert_document_extraction）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ ⑥ 按 TaskKind 取 wf_prompt_template
                    ┌──────────┴──────────┐
                    ▼                     ▼
      PromptType=audit_prep     PromptType=audit_check
        齐不齐 / 全不全 / 疑点     符不符合 / NC 建议
                    │                     │
                    ▼                     ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ⑦ 落库（★ 一次分析一个容器，分支靠 StageKind 区分）                    │
│    cert_check_analysis   一行 = 检查项 × 分支 × 第 N 次               │
│       StageKind=prep|onsite / IsCurrent / 指纹 / 装配包快照           │
│    cert_check_result     一行 = 分析 × 条款（本分支的结论）            │
│       prep 分支只填：PrepState / MissingKinds / IsMandatory / VerifyLevel│
│       onsite 分支只填：Conclusion / NcSuggested / Severity            │
│    cert_check_analysis_evidence  分析用了哪几条证据（含内容快照）      │
│    cert_evidence         证据资产（CapturedIn 区分 prep / onsite）     │
│    cert_point            疑点（挂分析，Origin 区分来源）               │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ ⑧ 全部项终态 → RefreshCertTaskAsync
                               │    cert_task.Status = done|partial|failed
                               │    ★ 此刻起 page-lock 释放：可以编辑
                               ▼
                               │ ⑨ 审核员在统一视图里改 / 锁（锁在检查项上）
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        派生入场安排       开 NC 卡片        导出认证报告
      （过滤+分组+排班）   （人签发）      （快照冻结）
```

**⑤ 是这条链路的核心**，也是当前**完全缺失**的一环（§七）。没有它，LLM 拿到的是「一堆没归属的证据」，不是「某个条款下企业到底提供了什么」。

**④ → ⑧ 之间是一个只读窗口**：Worker 一开始领取，该 `(计划, 方向)` 的页面就锁住；最后一项收口、任务进终态，才解锁（§5.5）。**这个窗口内的任何写操作都会被后端拒绝**——不是靠前端禁用「看着像锁了」。

**⑦ 是本次修订的重点**：不再是「检查项 × 条款一行、准备段和检查段挤在同一行」，而是**一次分析一行**。这样准备分支和检查分支各有自己的结果、自己的证据链、自己的疑点，互不覆盖，也不需要靠"哪段字段归谁"来约定（§4.5）。

### 4.2 检查项 = 计划明细（不新建表）

**这是全篇最重要的结构决定**，再强调一次：

```
cert_audit_plan_detail.Code  ←── 检查项的唯一身份
        │
        ├── cert_task_item.CheckItemCode        （任务 × 检查项，执行状态）
        ├── cert_check_analysis.CheckItemCode   （★ 检查项 × 分支 × 第 N 次）
        │        ├── cert_check_analysis_evidence.AnalysisCode  （这次用了哪几条证据）
        │        ├── cert_check_result.AnalysisCode             （分析 × 条款，本分支结论）
        │        └── cert_point.AnalysisCode                    （本分支的疑点）
        ├── cert_evidence.CheckItemCode         （证据资产，跨分析复用）
        └── cert_check_lock.CheckItemCode       （★ 检查项锁）
```

**所有下游都挂 `CheckItemCode`（或从它派生），没有一个复制条款/部门快照。** 好处：计划改了条款，全部自动跟着变；代价：读的时候必须 join，且**计划编辑后要给 `cert_check_result` 置 `ResultStale=1`**（44 号 §2.3 已留该字段）。

> **注意 `cert_check_result` 不再直接挂 `CheckItemCode`**，而是通过 `AnalysisCode` 间接挂（`CheckItemCode` 只作冗余列）。
> 这是本次修订的结构性变化：**结论属于"某一次分析"，不属于"这个检查项"**（§4.5）。

### 4.3 检查项七要素 → 数据来源（用户明确要求的展示项）

用户说「每个检查项可以查看对应的条款、关联哪些部门、部门联系人是谁、条款定义的这个检查项是否可以开具 nc、严重程度怎么样、适合哪种方式进行检查、关联的文档具体内容是什么」——**逐项落到字段**：

| # | 界面要素 | 数据来源 | 备注 |
|:--:|---|---|---|
| 1 | **条款**（编号 + 标题 + 正文） | `plan_detail.Clauses` → `cert_iso_clause`（`ClauseNumber` / `Title` / `Content`） | 多条款按 `Sort` 展示 |
| 2 | **关联部门** | `plan_detail.Departments` / `DeptNames` | 快照自计划，⛔ 不猜 |
| 3 | **部门联系人** | 部门表 `ContactsJson`（前端 `parseContacts()` 已做兜底） | ⛔ 展示姓名，但进提示词只给角色 |

### 4.4 派生「入场安排」：新增 2 表（**裁决点 Q2**，本期可延后）

**为什么不能写回 `cert_audit_plan_detail`**：

```
检查项就是 plan_detail
        ↓ 派生时若再往 plan_detail 写
plan_detail 变多 → 下一轮准备的检查项变多 → 又派生 → 又变多
        ↓
计划自我繁殖，永远跑不完
```

所以「派生」的产物必须是**另一层**——排班：

| 表 | 关键字段 |
|---|---|
| `cert_onsite_schedule` | `PlanCode` / `AuditDateFrom` / `AuditDateTo` / `TeamJson`（组长/组员）/ `Status`(draft/confirmed) / `SourceTaskCode`（哪次准备派生的） |
| `cert_onsite_slot` | `ScheduleCode` / `CheckItemCode` / `DeptCode` / `AuditDate` / `HalfDay`(am/pm) / `Seq` / `EstMinutes` / `AssigneeCode` |

**派生算法**（41 号 §六）：

```
① 过滤：PrepState <> 'found' 且 (IsMandatory=1 或 PointCount>0 或 PrepNcHint='yes')
        —— 「资料齐、无疑点」的不进现场，这就是"合格的不占时间"
② 按 DeptCode 分组 → 每组一个"部门块"，块内按 plan_detail.Sort
③ 每块 EstMinutes 求和 → 半天 = 240 分钟 → 建议时段数
④ 人只填：日期 / 上午下午 / 谁去
⑤ 落 schedule + slot（slot 挂 CheckItemCode）
```

> **本期建议先做 §4.4 的 ① ② ③（只读预览：算出「需要现场多少项、多少小时」），④ ⑤ 延后。** 因为现场排班依赖 UI 交互，先把「需要多少时间」算出来，审核员就已经能用它跟企业谈入场日期了。

### 4.5 ★ 入场分析：独立表（**本次修订核心 · 裁决点 Q10**）

#### 4.5.1 为什么必须是独立表

用户原话：「入场的分析是独立的表，因为入场分析包含**原始证据 + 疑点 + 审核员证据**，而且要**区分哪些是认证准备的、哪些是认证检查的**，我们查看对应的分支，看到的是对应的分析结果和证据链，**这两套分支的表结构是统一的**」。

翻译成结构问题，就是三个"装不下"：

| 装不下的东西 | 现有结构为什么不行 |
|---|---|
| **两个分支各一份结果** | `cert_check_result` 唯一键 `(CheckItemCode, ClauseCode)` ⇒ 一个检查项一个条款**只能一行**，准备和检查只能挤同一行（"一行两段"），重跑必然互相覆盖 |
| **每次分析的证据链** | 证据挂 `CheckItemCode`，没有"这次分析用了哪几条"的记录 ⇒ 报告问「这个结论基于哪几条证据」答不出来 |
| **分支级的疑点归属** | `cert_point` 挂 `CheckItemCode`，只能靠 `Origin` 猜是哪次分析产的 ⇒ 同一检查项准备 2 个疑点、检查 3 个疑点，分不清哪批是哪次 |

**一句话**：`cert_check_result` 是"**当前结论**"的家，不是"**一次分析**"的家。用户要的是后者。

#### 4.5.2 四层变五层（新增"分析层"）

```
① 任务层    cert_task              这次执行（方向 / 计划 / 状态）
                │ 1:N
② 执行层    cert_task_item         任务 × 检查项（跑没跑）
                │
③ 分析层    cert_check_analysis    ★ 新增：检查项 × 分支 × 第 N 次
                │                   （一次分析 = 一个容器）
                ├── cert_check_analysis_evidence   这次用了哪几条证据（含内容快照）
                │
④ 结论层    cert_check_result      分析 × 条款（本分支的结论）
                │
⑤ 资产层    cert_evidence          证据（挂检查项，CapturedIn 区分来源，跨分析复用）
            cert_point             疑点（挂分析，Origin 区分来源）
            cert_nc                NC 单（人签发）
            cert_analysis          分析日志（追加型，保留：指纹 + 节流指标）
```

> **为什么保留 `cert_analysis` 日志**：它记的是"跑了多少次、每次指纹是什么、跳过多少"，是**运维指标**。
> 新的 `cert_check_analysis` 记的是"这次分析的内容与产出"，是**业务实体**。
> 两者不合并：一个是计数器，一个是容器。

#### 4.5.3 `cert_check_analysis`（★ 入场分析 · 一次分析一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(50) | 业务键 |
| **`CheckItemCode`** | varchar(50) | 检查项 = `cert_audit_plan_detail.Code` |
| **`StageKind`** | varchar(20) | **分支**：`prep` 认证准备 / `onsite` 认证检查 |
| `EnterpriseCode` / `PlanCode` | varchar(50) | 冗余，免 join |
| `TaskCode` / `TaskItemCode` | varchar(50) | 哪次任务跑的（可空 = 手工发起） |
| **`IsCurrent`** | tinyint NULL | **1 = 当前生效**；历史行置 `NULL`（见下方唯一键技巧） |
| `RunNo` | int | 该 (检查项, 分支) 的第几次分析，从 1 起 |
| `Status` | varchar(20) | `running` / `done` / `failed` / `stale` |
| `PromptType` / `PromptVersion` / `ModelName` | varchar | 用的哪套提示词（`audit_prep` / `audit_check`） |
| **`EvidenceFingerprint`** | varchar(64) | 输入证据指纹（判定"证据变没变"） |
| **`InputSnapshotJson`** | longtext | ★ 装配包快照（条款 + 属性 + 摘录 + 现场证据），**回放用** |
| `ResultSummaryJson` | text | 产出摘要（几条结果 / 几条疑点 / 状态分布） |
| `AnalyzedAt` / `DurationMs` | | |
| `InputTokenCount` / `OutputTokenCount` | int | 成本核算 |
| `ErrorMessage` | text | 失败原因（失败必填） |

**唯一键技巧（⚠️ 容易踩）**：

```sql
UNIQUE KEY uk_current (CheckItemCode, StageKind, IsCurrent)
```

MySQL 唯一索引**允许多个 NULL**，所以：
- 当前行 `IsCurrent = 1` ⇒ `(item, prep, 1)` 唯一，一个分支只有一条当前
- 历史行 `IsCurrent = NULL` ⇒ `(item, prep, NULL)` 可以有无限多条

> ⛔ **不要用 `IsCurrent = 0` 表历史**：那样 `(item, prep, 0)` 只能有一条，重跑两次就插入失败。

#### 4.5.4 `cert_check_result`（结论 · 分析 × 条款）

**只改键，不改字段**（字段已经够用）：

| 变化 | 前 | 后 |
|---|---|---|
| 唯一键 | `uk_checkitem_clause (CheckItemCode, ClauseCode)` | **`uk_analysis_clause (AnalysisCode, ClauseCode)`** |
| 新增列 | — | `AnalysisCode` varchar(50) NOT NULL |
| 新增列 | — | `StageKind` varchar(20)（冗余，便于按分支过滤） |
| 保留 | `CheckItemCode` | 保留（冗余，免 join） |
| 移出 | `IsLocked` / `LockedBy` / `LockedAt` / `LockReason` | **移到 `cert_check_lock`（§10）** |

**字段归属不变（仍是"两段"），但现在是"一行只填一段"**：

| 分支 | 只写这组 | 另一组 |
|---|---|---|
| `prep` | `PrepState` / `MissingKindsJson` / `ConflictsJson` / `IsMandatory` / `VerifyLevel` / `PrepNcHint` | `Conclusion` / `NcSuggested` / `Severity` **必须为 NULL** |
| `onsite` | `Conclusion` / `NcSuggested` / `Severity` / `SeveritySource` | `PrepState` 等 **必须为 NULL** |

> **为什么还留在一张表**：这就是用户说的「两套分支的表结构是统一的」。
> 同一张表 + `StageKind` 区分，比建两张表好在：报告要"按条款列出准备结论和检查结论"时，一次 join 就出来了，不用 UNION。

**写入断言（代码层强制）**：`StageKind=prep` 时若 `Conclusion` 非空 ⇒ 抛错。这样 F3 那种"把 pass 写进 PrepState"的错误，从结构上就写不出来了。

#### 4.5.5 `cert_check_analysis_evidence`（分析 × 证据 · 证据链）

| 字段 | 说明 |
|---|---|
| `Code` / `AnalysisCode` / `EvidenceCode` | 唯一键 `(AnalysisCode, EvidenceCode)` |
| `UsedInPrompt` | 0/1：是否真的喂给了模型（`Status=dropped` 的不喂，但保留关联） |
| **`SnippetSnapshot`** | ★ 分析当时该证据的 `LlmSummary` 快照 |
| **`ContentMD5Snapshot`** | 当时的 MD5（证据后来被改，也能证明"当时用的是这版"） |
| `TokenEstimate` | 该条占多少 token（截断决策留痕） |
| `OrderNo` | 在提示词里的顺序 |

> **为什么必须有快照**：证据是资产，会被修改（`PrevContentMD5` 机制就是干这个的）。
> 报告三个月后要能回答「当时凭什么判的」——只有 `EvidenceCode` 不够，必须存当时的内容。

#### 4.5.6 `cert_point` / `cert_evidence` 的改动

| 表 | 改动 |
|---|---|
| `cert_point` | 加 **`AnalysisCode`**（挂到具体分析）；`Origin` 保留（`prep`/`onsite`/`pq`/`manual`）；幂等键改为 `(AnalysisCode, Fingerprint)` |
| `cert_evidence` | **不改**。仍挂 `CheckItemCode`，`CapturedIn` 就是"哪些是准备采的、哪些是检查采的" |

> **证据为什么不挂分析**：证据是**资产**，一次采到、多次分析复用（准备采的文档切片，检查阶段照样要看）。
> 挂分析会导致重跑时证据被"重新归属"，历史分析链断掉。**用关联表表达"这次用了它"，而不是"它属于这次"。**

#### 4.5.7 一个具体例子（3 条款 × 2 分支 × 准备重跑 1 次）

```
检查项 #03 = 4.2.4 + 4.2.5 + 4.2.6 ｜品质部

cert_check_analysis
  A1  item=#03  prep    第1次  IsCurrent=NULL  done
  A2  item=#03  prep    第2次  IsCurrent=1     done   ← 重跑（改了文档）
  A3  item=#03  onsite  第1次  IsCurrent=1     done

cert_check_result（每分析 3 行，共 9 行）
  A1 × 4.2.4 / 4.2.5 / 4.2.6     ← 历史，PrepState 有值，Conclusion 全 NULL
  A2 × 4.2.4 / 4.2.5 / 4.2.6     ← 当前准备结论
  A3 × 4.2.4 / 4.2.5 / 4.2.6     ← 当前检查结论

界面
  「准备」分支 → 读 A2 的 3 行 → 显示 PrepState 列
  「检查」分支 → 读 A3 的 3 行 → 显示 Conclusion 列
  「历史」     → 读 A1 的 3 行 → 对比"上次 5 个疑点这次 3 个为什么"
```

**两条查询就够（看分支）**：

```sql
-- 看准备分支
SELECT r.* FROM cert_check_result r
JOIN cert_check_analysis a ON a.Code = r.AnalysisCode
WHERE r.CheckItemCode = @item AND a.StageKind = 'prep' AND a.IsCurrent = 1;

-- 看检查分支（证据链一并带出）
SELECT e.*, ae.SnippetSnapshot, ae.UsedInPrompt
FROM cert_check_analysis_evidence ae
JOIN cert_evidence e ON e.Code = ae.EvidenceCode
WHERE ae.AnalysisCode = @currentOnsiteAnalysisCode
ORDER BY ae.OrderNo;
```

#### 4.5.8 迁移脚本要点（表已建，要改）

`scripts/db/20261030_audit_task_check_chain_V1.sql` 已建表。新增迁移脚本做四件事：

| # | 动作 | 风险 |
|:--:|---|---|
| 1 | `cert_check_result` 加 `AnalysisCode` / `StageKind`，删 `uk_checkitem_clause`，加 `uk_analysis_clause` | 存量行 `AnalysisCode` 为空 ⇒ 先补一个"迁移分析"行再改 NOT NULL |
| 2 | 新建 `cert_check_analysis` / `cert_check_analysis_evidence` / `cert_check_lock` | 无 |
| 3 | `cert_check_result` 的 `IsLocked` 等 4 列**降级为镜像**（以 `cert_check_lock` 为准），或直接删 | 存量若有锁定数据要搬 |
| 4 | `cert_point` 加 `AnalysisCode` | 存量按 `CheckItemCode + Origin` 回填 |

> **存量判断**：这批表 2026-10-30 才建，且 `CertCheckEngineService` 只在"自动分析"按钮下写。
> 若库里 `cert_check_result` 行数很少（预期 < 50），**直接清空重来**比写迁移逻辑便宜。**开工前先 count 一次**。

#### 4.5.9 锁定也在这里定（详见 §10）

因为「一个检查项被锁定」是**检查项级**的状态（不是结果行级），它需要自己的位置：

| 表 | 关键字段 |
|---|---|
| `cert_check_lock` | `CheckItemCode` / **`StageKind`**（`prep`/`onsite`/**`all`**）/ `LockedBy` / `LockedAt` / `LockReason` / `LockSource`（`manual`/`auto_nc`） |

唯一键 `(CheckItemCode, StageKind)`。`StageKind='all'` 表示"整项锁死，两个分支都不跑"。

> **为什么不在 `cert_check_result` 上锁**：结果行是"分析 × 条款"，一个检查项 3 条款就有 3 行，锁要锁 3 次；而且重跑产生新分析后，锁就跟着旧行一起变成历史了——**锁必须独立于分析次数**。

## 五、选择与队列

### 5.1 全选 / 部分选

复用 `ExpertTaskService` 已验证的范式：

```csharp
class CertTaskCreateRequest {
    string PlanCode;
    string TaskKind;              // prep | onsite
    string ScopeType;             // full | partial
    List<string>? ItemCodes;      // ScopeType=partial 时必填（plan_detail.Code）
    string RunMode;               // full | incremental | selective
    // ⛔ 无 SkipLocked：锁定项恒跳过，不是开关（§10.1）
}
```

**校验（缺一即拒，⛔ 不许静默跳过）**：

| 校验 | 拒绝条件 | 提示 |
|---|---|---|
| 计划唯一有效 | 同 `PlanCode` 有 `Status=running` 的任务 | 「计划 xxx 有任务在执行中（任务号 P-…）」 |
| 有检查项 | `ItemCodes` 为空且 `ScopeType=partial` | 「未选择任何检查项」 |
| 条款非空 | 选中项 `Clauses` 全空 | 「检查项 #3 没有条款，无法分析」 |
| 部门非空 | 选中项 `Departments` 全空 | 「检查项 #3 没有部门，请先补计划」 |
| 属性覆盖 | 选中项的条款中，`Obligation` 缺失比例 > 0 | **警告不阻断**：「N 个条款未配 Obligation，将无法判断可否开 NC」 |
| 证据源 | `prep` 且该企业 `cert_document_extraction` 有效行为 0 | 「企业尚无已提取文档，准备将全部判 missing」 |
| **锁定项** | 选中项**全部**已锁定（`StageKind IN ('all', taskKind)`） | **不拒绝，但明确告知**：「选中的 8 项均已锁定，本次不会执行任何分析」→ 见 §10.3 |

> **第 5 条只警告不阻断**：属性缺失不该卡住业务，但必须让审核员看见（写进 `cert_task.GuardJson`，界面黄条常驻）。
>
> **第 7 条不是校验是告知**：锁定项不阻断建任务（要留痕"谁在什么时候试图跑过"），但必须在**点「开启」之前**就告诉用户「这 8 项锁了，跑了也白跑」——而不是跑完才发现。

|---|---|
| 勾选已锁项 | **允许勾**（不拦），但行内显示 🔒 + tooltip「已锁定，执行时跳过」 |
| 全选 | 全选包含已锁项，顶部提示「其中 3 项已锁定，实际将执行 5 项」 |
| 点「开启」 | 二次确认框里明确写「将执行 5 项，跳过 3 项（已锁定）」 |

> **为什么不直接禁勾**：审核员可能想"先勾上，回头解锁再跑"。禁勾会逼他改两次操作。
> **为什么必须显示**：不显示就是"勾了 8 项只跑了 5 项，还找不到原因"。

### 5.3 一个队列，逐项独立

用户原话：「选择了多个检查项后执行的是一个队列，这个队列按每个检查项独立运行」。

**这正好就是 `cert_expert_task_queue` 的现成语义**，一行都不用改：

| 用户的话 | 现有实现 |
|---|---|
| 「一个队列」 | `cert_expert_task_queue` 一行（`QueueType='check_item'`，`TaskCode=cert_task.Code`） |
| 「按每个检查项独立运行」 | `cert_expert_task_queue_item` 一个检查项一行（`TaskItemCode=plan_detail.Code`） |
| 「独立」的边界 | `ScopeKey = check:{CheckItemCode}`；单项失败只改该项 `ItemStatus=failed`，**不回滚同批其他项** |
| 进度 | `SELECT ItemStatus, COUNT(*) ... GROUP BY ItemStatus` → 回写 `cert_task.ItemDone/ItemFailed` |

**新增的只有一个执行器**：

```csharp
class ExpertCheckItemExecutor : IExpertItemExecutor
{
    public string ItemType => "check_item";
    // 内部：装配 → 选提示词（按 TaskKind）→ LLM → 落库
}
```

> **为什么是「同队列串行」而不是并发**：`ExpertTaskQueueRunner.ClaimNextAsync` 的 SQL 里带 `NOT EXISTS (... ItemStatus='running')`，同一队列当前有 running 项时不领取下一项。这是**故意的**——避免一次勾 30 个检查项同时打 LLM 配额。`MaxConcurrent=3` 是跨队列上限。

### 5.4 幂等与并发

| 场景 | 处理 |
|---|---|
| 重复点「开始」 | `uk_queue_item(QueueCode, TaskItemCode)` 唯一键 ⇒ 同队列同检查项只入队一次 |
| 同一检查项被两个任务跑 | `ScopeKey=check:{CheckItemCode}` 资源锁 ⇒ 第二个任务该项 `ItemStatus=skipped`，`Message="检查项 #3 正在被任务 C-… 执行"` |
| 执行中文件被重传 | `ExtractVersionStamp` 比对失败 ⇒ 该项 `failed(retryable)`，**不写脏结论**（这是现有引擎已实现的护栏，正好用上） |
| Worker 崩溃 | 租约 10 分钟过期 → `ReapStaleAsync` 回收 → 重试（`MaxRetryCount=3`，指数退避） |

### 5.5 ★ 运行期页面锁：队列跑着，页面不许改

> **用户明确要求**：「我们在执行队列的时候，要现在当前的认证准备或认证检查页面不能进行操作，只有队列完成后，才运行编辑」。

#### 5.5.1 先分清两把锁（⛔ 最容易混的一处）

| | **页面锁（本节）** | **检查项锁（§十）** |
|---|---|---|
| 触发 | 队列 `running` / `queued` | 审核员点「锁定检查项」 |
| 作用范围 | **整页**（该计划 + 该 `TaskKind` 的所有写操作） | **单个检查项**（该检查项该分支的全部结果与证据） |
| 谁释放 | 队列进终态，**自动释放** | 审核员点「解锁」，**手动释放** |
| 防什么 | 队列写库时人也在写 ⇒ 互相覆盖 | 重跑覆盖审核员的判断 |
| 载体 | 无（由 `cert_task.Status` 实时推导，⛔ 不落冗余列） | `cert_check_lock`（`CheckItemCode` + `StageKind` + `LockedBy/At/Reason`） |
| 对队列的影响 | 只影响**人**能不能写 | **让队列跳过该检查项**（§10.2 三道闸门） |

> **两把锁独立，但方向相反**：
> - 页面锁管「**人别动**」——队列在写，人不能写。
> - 检查项锁管「**机器别动**」——人确认过了，队列不能写。
>
> 所以两者不会同时生效于同一对象：队列跑着时页面锁生效（人禁写）；队列跑完后页面锁释放，检查项锁仍生效（机器禁写）。**这正是"人机互斥"的完整闭环。**

#### 5.5.2 锁的粒度与状态机

**粒度 = `(PlanCode, TaskKind)`**。因为认证准备与认证检查**分开执行**：准备跑着，检查页仍可编辑（只是会提示「准备正在跑，你看到的证据可能是旧的」）。将来「结合使用」时把粒度参数化成 `lockScope`，combined 模式一次锁两个 `TaskKind`。

```
                 ┌────────── 无任务 / 任务已终态 ──────────┐
                 │                                        │
                 ▼                                        │
           ┌──────────┐   建任务+入队   ┌──────────┐      │
           │  idle    │ ──────────────▶│ queued   │      │
           │ 可编辑   │                │ 只读     │      │
           └──────────┘                └────┬─────┘      │
                 ▲                          │ Worker 领取 │
                 │                          ▼             │
                 │                    ┌──────────┐        │
                 │                    │ running  │        │
                 │                    │ 只读     │        │
                 │                    └────┬─────┘        │
                 │                          │ 全部项终态  │
                 │      ┌───────────────────┼────────────┘
                 │      ▼                   ▼
                 │  ┌────────┐         ┌──────────┐
                 └──│ done   │         │ partial  │  ← 也算终态，解锁
                    │ 可编辑 │         │ failed   │
                    └────────┘         └──────────┘
                                    （failed 解锁但顶部红条）
```

| `cert_task.Status` | 页面 | 说明 |
|---|---|---|
| `pending` | **只读** | 已建任务、队列未启动 |
| `running` | **只读** | 执行中 |
| `paused` | **只读** | 暂停 ≠ 结束。要编辑必须先「终止任务」（`Status=cancelled`） |
| `done` | 可编辑 | 全部成功 |
| `partial` | 可编辑 | 部分失败（顶部黄条：「3 项失败，可重跑」） |
| `failed` | 可编辑 | 全部失败（顶部红条） |

> **`paused` 必须锁住**：暂停时 Worker 可能正持有某一项的租约，这时改结论必然被覆盖。**唯一出口是终止任务**（把未跑项置 `cancelled`），不是「暂停后就能改」。

#### 5.5.3 后端：一个统一闸门，所有写端点必须过

```csharp
// CertTaskService（或独立 CertPageLockService）
public async Task<Result> AssertEditableAsync(string planCode, string taskKind)
{
    var running = await _db.GetOneAsync<CertTask>(t =>
        t.PlanCode == planCode && t.TaskKind == taskKind && !t.IsDeleted
        && (t.Status == "pending" || t.Status == "running" || t.Status == "paused"));

    if (running.Data == null) return Result.Ok();

    var t = running.Data;
    var pct = t.ItemTotal > 0 ? t.ItemDone * 100 / t.ItemTotal : 0;
    return Result.Fail(
        $"当前{TaskKindName(taskKind)}任务正在执行（{t.TaskNo} · {t.ItemDone}/{t.ItemTotal} · {pct}%），" +
        $"执行期间不可修改。请等待完成，或先终止该任务。");
}
```

**必须调这个闸门的端点**（漏一个就等于没锁）：

| 端点 | 为什么 |
|---|---|
| `save-result` | 改结论 |
| `lock-conclusion` / `unlock-conclusion` | 改锁定状态 |
| 证据新增 / 修改 / 删除 | 改证据（会改指纹） |
| `issue-nc` / `ai-suggest-nc` | 开 NC |
| 计划明细编辑 | 改条款/部门（会触发 `ResultStale`） |
| 重跑（`start`） | 已在跑就别再开一个 |

**HTTP 语义**：返回 **`409 Conflict`**，`code = "PAGE_LOCKED"`，body 带 `taskNo` / `itemDone` / `itemTotal`，前端据此显示进度条而不是干巴巴一句错。

#### 5.5.4 前端：一次查询 + 5 秒轮询 + 自动解锁

```ts

const lock = ref<PageLockState>({ locked: false })

async function refresh(planCode: string, taskKind: 'prep' | 'onsite') {
  const r = await getPageLock(planCode, taskKind)
  lock.value = r
  if (!r.locked) stopPolling()          // ★ 终态即停，别一直打接口

// 页面 onMounted：先查一次；locked 则每 5s 轮询，直到 locked=false

```

| 元素 | 锁定态 |
|---|---|
| 顶部 | 常驻条：`⏳ 认证准备执行中 · 3/8 · 37%` + 进度条 + 「查看队列」链接 |
| 全选/单选 checkbox | `disabled` |
| 「开启准备」「开启检查」按钮 | `disabled` + tooltip「执行中」 |
| 侧边栏所有输入框、锁定/解锁、保存 | `disabled` |
| 行内「补充材料」「开 NC」 | `disabled` |
| 表格本身 | **仍可浏览、仍可展开查看条款与文档**（只读 ≠ 看不见） |
| 解锁瞬间 | 顶部条淡出 + 轻提示「执行完成，现在可以编辑了」 |

> **只读 ≠ 整页遮罩**。审核员在等待期间最想做的事就是**看结果**——跑完的检查项已经能看了。所以只禁写，不禁读。

#### 5.5.5 队列完成判定：`cert_task` 的汇总回写（**当前缺失**）

`ExpertQueueFinalizer` 已有 `RefreshQueueAsync`（队列级）和 `RefreshTaskAsync`（**`CertExpertTask`**，旧的专家任务表）。我们的流程用的是 **`cert_task`**，是**另一张表**，所以要补一个同构的：

```csharp
// 每次队列项收口后调用
public static async Task RefreshCertTaskAsync(IDbOrm db, string taskCode, DateTime now)
{
    var items = await db.GetListAsync<CertTaskItem>(x => x.TaskCode == taskCode && !x.IsDeleted);
    var total  = items.Count;
    var done   = items.Count(i => i.Status == "reviewed" || i.Status == "analyzed");
    var failed = items.Count(i => i.Status == "failed");
    var pending= items.Count(i => i.Status == "waiting" || i.Status == "ready"
                                || i.Status == "analyzing");

    task.ItemTotal = total;
    task.ItemDone = done;
    task.ItemFailed = failed;

    if (pending == 0) {
        task.Status = failed == 0 ? "done" : (done == 0 ? "failed" : "partial");
        task.FinishedAt ??= now;
    }
}
```

> **这是页面锁能自动释放的前提**。没有它，`cert_task.Status` 永远停在 `running`，页面就永远锁死——比不锁更糟。
> 现有 `RefreshTaskAsync` 的逻辑可直接照抄，只换实体与状态常量。

### 6.3 占位符（`wf_prompt_template` 没有占位符注册列）

`wf_prompt_template` **没有占位符注册列**，占位符靠正文约定。所以：

|---|---|
| 在 `AuditPromptTypes`（新建的常量类）里维护占位符常量 | 供代码渲染 + 单测断言「正文里出现未知占位符就失败」 |
| 渲染用 `StringComparison.Ordinal` 替换 | ⛔ 不走文化相关比较，某些区域设置下漏替换且不报错（`DocExtractPromptService` 已踩过） |
| 渲染后**残留 `{{` 即判失败** | 说明正文里的占位符拼错或程序没传值，跑下去只会得到废结论 |

**两套提示词共用的占位符**：

| 占位符 | 内容 |
|---|---|
| `{{task_kind}}` | `prep` / `onsite` |
| `{{check_item_name}}` | 「03 文件控制（4.2.4/4.2.5）｜品质部」 |
| `{{dept_names}}` | 部门名，逗号分隔（⛔ 不带联系人姓名） |

| `{{onsite_evidence}}` | **仅 `audit_check`**：现场证据块（访谈转录 / 照片说明 / 抽样记录） |

> `{{clause_blocks}}` 是**唯一的大块**，其余都是短变量。理由：条款块的结构（正文 → 属性 → 摘录）必须由程序保证顺序与锚点，⛔ 不能交给模型自己拼。

### 6.4 版本留痕与「不做版本管理」的边界

`wf_prompt_template` **有 `Version` 列**，`PromptTemplateView.Version` 也会带出来；但前端 `PromptTemplateDto` 明确**不暴露** `version`（2026-10-02 裁决「提示词不做版本管理」，同时 `modelName` / `maxTokens` / `temperature` 也不暴露，统一走 `cert_sys_config`）。

因此留痕口径：

| 写哪 | 写什么 |
|---|---|
| `cert_task.PromptCode` / `PromptVersion` | `audit_prep` / 解析到的 `Version` 值 |
| `cert_analysis.PromptCode` / `PromptVersion` | 同上（每次分析一行） |

> **已知局限（可接受，不阻塞）**：若后台保存时 `Version` 不自增，则同一版本号可能对应多份正文，回溯精度有限。
> 但**结论是否可解释**不依赖它——`cert_analysis` 同时存了 `EvidenceFingerprint` 和 `ResultSummaryJson`，指纹对得上就能复现输入。**本期不改表、不改保存逻辑**；若将来要精确回溯，再让保存时 `Version++`（1 行代码）。

### 6.5 保存闸门：提示词必须自测过才能保存

`/business/prompt-template` 页已有硬拦（P5）：**没测过 / 测的正文与当前不一致 / 分析输出不合规 ⇒ 禁止保存**，测试结果存 `LastTestResult`。

这对认证准备/检查尤其重要：两套提示词的输出是**结构化 JSON**，格式一错整条链路就废。所以配置流程固定为：

```
① 在页面选类型 audit_prep（或 audit_check）+ 选标准（或「全部标准」= 平台级）
② 填正文 → 上传一份真实企业文档 → 点「测试」
③ 看 jsonOutput 是否含 state / findings / points（或 conclusion / ncSuggested / ncDraft）
④ 合规才允许保存 → 保存后 IsActive=1
⑤ 到专家端重跑该检查项，确认 cert_analysis.PromptVersion 变了、输出跟着变
```

> ⛔ **不许「先保存再慢慢调」**：未自测的正文一旦 `IsActive=1`，队列下一次跑就直接用它，产出的是废结论而不是报错。

  "state": "found | partial | missing | unknown | na",
  "gapSummary": "……必填，一句话说清缺什么/哪里不全……",
  "severity": "critical | major | minor | observation",
  "isMandatory": true,
  "ncHint": "yes | no | uncertain",
  "ncReason": "……",
  "verifyLevel": "doc | remote | onsite | test",
  "missingKinds": ["record", "approval", "signature", "version", "scope"],
  "conflicts": [
    { "theme": "保存期限", "aFile": "A.pdf", "bFile": "B.pdf", "aSays": "5 年", "bSays": "3 年" }
  ],
  "findings": [
    { "clauseNumber": "4.2.4", "clauseState": "found",   "reason": "程序与清单齐全" },
    { "clauseNumber": "4.2.5", "clauseState": "partial", "reason": "未见 12 个月内发放回收记录" }
  ],
  "points": [
    { "clauseNumber": "4.2.5", "kind": "communicate", "mode": "remote",
      "reason": "发放记录可能以电子形式存在，文档中未提及系统名称",

```jsonc

  "reason": "……必填，引用具体证据……",
  "ncSuggested": "yes | no | uncertain",
  "severity": "major | minor | observation",
  "severitySource": "attr | ai | manual",
  "evidenceUsed": ["E-001", "E-003"],
  "findings": [
    { "clauseNumber": "4.2.4", "conclusion": "pass", "reason": "……" }
  ],
  "ncDraft": {                              // 仅 ncSuggested=yes 时产出
    "factDesc": "……客观事实，⛔ 不写原因分析……",
    "requirementRef": "4.2.4 组织应……",
    "severity": "major",
    "correctiveReq": "……",
    "dueDays": 30
  },
  "points": [
    { "clauseNumber": "4.2.5", "kind": "verify", "mode": "onsite",
      "reason": "……", "action": "……", "targetRole": "……", "estMinutes": 20 }
  ]
}
```

**检查阶段的三条硬红线**：

1. **`severity` 不得高于条款基线**（`cert_clause_attr.Severity`）。`Obligation != shall` ⇒ 最高 `observation`。
2. **`conclusion=pass` 时 `ncSuggested` 必须 `no`**，否则判失败。
3. **`ncDraft` 只是草稿**。系统永不自动签发（`cert_nc.Origin=ai_suggest` + `Status=pending_review` 起步）。

### 6.9 校验闸门（不过就判失败，⛔ 不许"尽量修"）

| 校验 | 失败处理 |
|---|---|
| JSON 可解析 + 必填字段齐 | 重试 1 次（温度降 0.2）→ 仍失败 ⇒ `failed` |
| `findings[]` 覆盖**每个** (条款 × 部门) 维度 | 缺哪个就补 `unknown` + `reason="模型未覆盖"`，**并计数**（覆盖率是可观测指标） |
| `state` 与 `ncHint` 不矛盾（`found` 却 `ncHint=yes`） | 判失败 |
| `severity` ≤ 条款基线 | 截到基线，记 `SeveritySource=attr` |
| `points[].clauseNumber` 必须在本检查项条款集内 | 越界的丢弃并计数 |

## 七、内容聚合器（★ 当前完全缺失，是这条链路的心脏）

### 7.1 算法（6 步）

```
输入：checkItemCode（= plan_detail.Code）
输出：CheckItemPackage（§6.2 的输入结构）

① 取检查项
   plan_detail = SELECT * FROM cert_audit_plan_detail WHERE Code=@checkItemCode
   → clauseCodes[]（逗号分隔）、deptCodes[]、planCode

② 拆条款 + 取条款正文与属性（逐条款循环）
   FOR clauseCode IN clauseCodes:
       clause  = cert_iso_clause WHERE Code=@clauseCode
       attrs   = cert_clause_attr WHERE ClauseCode=@clauseCode
                 → Obligation / Severity / Applicability / Artifacts / EvidenceChain / Process

③ 取该条款的文档摘录（★ 关键一步）
   extractions = SELECT * FROM cert_document_extraction
                 WHERE EnterpriseCode=@ent
                   AND StandardCode=@std          -- 条款归属的标准
                   AND FIND_IN_SET(@clauseNumber, ClauseNumbers)   -- ⛔ 禁止 LIKE '%4.2.5%'
                   AND IsStale=0 AND IsDeleted=0 AND ExtractStatus='done'

④ 从 ContentJson 里切出该条款那一段
   FOR e IN extractions:
       ContentJson = JSON.parse(e.ContentJson)      -- { docMeta, clauses[] }
       seg = ContentJson.clauses.find(c => c.clauseNumber == @clauseNumber)
       IF seg == null: continue                     -- 该文档声明适用但没提取到 → 记 missing 线索
       docs.add({ fileCode, fileName, anchor: seg.anchor,
                  snippet: seg.snippet, confidence: seg.confidence,
                  isStale: e.IsStale })

⑤ 落证据（只落 prep 方向）
   FOR d IN docs:
       IF 已存在 (CheckItemCode + ClauseCode + SourceCode + ContentMD5) : skip   -- 幂等
       INSERT cert_evidence {
           CheckItemCode = @checkItemCode, ClauseCode = @clauseCode,
           CapturedIn = 'prep', CapturedTaskCode = @taskCode,
           EvidenceKind = 'doc_slice', SourceCode = d.fileCode, SourceName = d.fileName,
           Anchor = d.anchor, Snippet = d.snippet, Confidence = d.confidence,
           LlmSummary = d.snippet,                    -- 实际喂模型的就是它
           ContentMD5 = MD5(d.snippet),
           TokenEstimate = len(d.snippet)/3,
           Status = 'collected', Origin = 'ai'
       }

⑥ 组装 CheckItemPackage（§6.2），返回
```

### 7.2 一个具体例子

假设检查项 = `4.2.4 + 4.2.5`｜品质部，企业上传了 3 份文档：

| 文档 | `ClauseNumbers` | `ContentJson.clauses[]` 里有 4.2.5 吗 |
|---|---|---|
| 文件控制程序.pdf | `4.2.4,4.2.5` | ✅ 有，anchor=`第 5 节` |
| 文件清单.xlsx | `4.2.4` | — 不命中 |
| 记录管理规范.pdf | `4.2.5,7.5.3` | ✅ 有，anchor=`表格 3` |

聚合结果：

- **4.2.4**：1 条摘录（文件控制程序 第 3 节）
- **4.2.5**：2 条摘录（文件控制程序 第 5 节 + 记录管理规范 表格 3）
- 落 `cert_evidence` 3 行，`CapturedIn=prep`，`EvidenceKind=doc_slice`

> **注意 `FIND_IN_SET` 是必须的**：`ClauseNumbers` 是 `4.2.4,4.2.5` 这种逗号串。用 `LIKE '%4.2%'` 会把 `4.2.4` 和 `4.2.5` 和 `14.2.4` 全捞出来——`cert_document_extraction` 实体注释里已经把这条写成铁律。

### 7.3 落证据的四条规则

| 规则 | 理由 |
|---|---|
| **只追加，不改写** | 现场若推翻准备证据 → 新增一条 `onsite` 把旧置 `dropped`（带理由），两条都在 |
| **`LlmSummary` 才是喂模型的内容** | `Snippet` 是原文（给人看/报告引用），`LlmSummary` 可清洗（OCR 纠错、去页眉页脚） |
| **`ContentMD5` 必填** | 指纹靠它；缺了就没法检测「证据变了」 |
| **幂等键 = `CheckItemCode + ClauseCode + SourceCode + ContentMD5`** | 同一份文档重跑不产生重复证据 |

### 7.4 截断与成本

| 情形 | 处理 |
|---|---|
| 单条款摘录 > 12 条 | 按 `confidence` 降序取 12，余下丢弃并记 `truncated: n` |
| 单检查项装配包 > 24k tokens | 按条款轮流截断（每条款保底 2 条），⛔ 不许整条丢某个条款 |
| 条款数 > 6 | 分两批调用 + 一次综合（共 3 次），上限 8（41 号 Q3） |
| 文档 `isStale=1` | **不进装配包**，该条款记「文档已过期待重提取」→ 影响 `PrepState` 判定为 `unknown` |

**成本估算**：一个检查项平均 2.3 条款 × 平均 4 条摘录 × 约 800 字 ≈ 7.4k 字 ≈ 10k tokens 输入。一次准备 8 检查项 ≈ 80k tokens 输入。**锁定 + 指纹跳过后，二次重跑通常只跑 2–3 项。**

## 八、认证准备：从证据到 `PrepState` + 疑点

### 8.1 五态判定（**程序闸门优先，省 token**）

```
对于每个条款：

  ① Applicability == 'na'                    → PrepState = na      （不调 LLM）
  ② Obligation 缺失 且 零证据                 → PrepState = unknown （不调 LLM，缺属性）
  ③ 有证据 且 全部 isStale                    → PrepState = unknown （不调 LLM，文档过期）
  ④ 零证据 且 Artifacts 非空（企业本该提供）    → PrepState = missing （不调 LLM，程序直接判）
  ⑤ 其余                                      → 调 LLM 判 found/partial/unknown
```

> **④ 是省钱的关键**：企业根本没交文件，不需要问模型。这一步能砍掉准备阶段 30–50% 的调用量。

**五态语义（⛔ 必须严格区分）**：

| 值 | 含义 | 可推 NC 吗 |
|---|---|---|
| `found` | 文档齐、信息全 | ❌ |
| `partial` | 有文档但信息不全（缺签名/缺日期/缺范围） | ✅ 可建议 |
| `missing` | 文档根本不存在 | ✅ 可建议 |
| `unknown` | 文档在，但读不出/看不懂/已过期 | **❌ 绝不推 NC**（29 号红线） |
| `na` | 条款不适用 | ❌ |

### 8.2 检查项汇总（在**本次分析内**汇总）

```
任一 (条款×部门) = missing  → 本次分析 = missing
否则任一 = partial          → 本次分析 = partial
否则任一 = unknown          → 本次分析 = unknown
否则全 found                → 本次分析 = found
```

> **`unknown` 排在 `partial` 之后**：有明确的 `partial` 就不该被「不确定」盖掉。
>
> ⚠️ **汇总结果写进 `cert_check_analysis.ResultSummaryJson`，⛔ 不写回 `cert_audit_plan_detail`**。
> 因为「检查项的当前状态」= 当前分析的汇总，是**推导值**；落一份到计划表必然与多次分析不一致（这正是 F13 那一类错误的翻版）。

### 8.3 疑点四分类（`cert_point.PointKind`）

| 分类 | 什么情况用 | `Mode` 默认 | 举例 |
|---|---|---|---|
| `communicate` **沟通** | 问一句就能清楚，不需要看实物 | **`remote`** ← 微信/邮件/电话可解 | 「文件发放是否走 OA？能否导出近 12 个月记录？」 |
| `interview` **访谈** | 需要当面问、需要追问、需要看对方反应 | `onsite` | 「问品质主管：文件评审多久一次？上次评审结论是什么？」 |
| `observe` **观察** | 必须到现场看实物/看操作 | `onsite` | 「看文件柜是否上锁、作废文件是否单独存放」 |
| `verify` **核验** | 核对记录、抽样、实测 | `remote` 或 `onsite` | 「抽 3 份文件核对版本号与发放记录是否一致」 |

**`remote` 的意义**：用户说「针对这些疑点是否可以通过微信等其他渠道解决一部分的问题」——**`Mode=remote` 就是这批**。它们可以在入场前消解掉，剩下的才是真正的现场工作量。

### 8.4 `PrepNcHint` 与红线

| 项 | 规则 |
|---|---|
| `PrepNcHint` 值域 | `yes` / `no` / `uncertain` |
| 谁能写 `yes` | 仅 `PrepState ∈ {partial, missing}` 且 `Obligation=shall` |
| `unknown` 时 | **强制 `uncertain`**（程序覆盖，不信模型） |
| 措辞 | 「建议现场核实是否构成不符合」，⛔ 不许出现「开具 NC」 |
| 正式 NC | **只能在认证检查阶段由人签发**（29 号红线） |

## 九、认证检查：从现场证据到结论

### 9.1 现场证据类型（`cert_evidence`）

| `EvidenceKind` | 来源 | 关键字段 |
|---|---|---|
| `onsite_media` | 照片/录音/视频 | `MediaKind` / `DurationSec` / `TranscriptText` |
| `interview` | 访谈记录 | `PresentPersons` / `CapturedAt` / `CapturedPlace` |
| `sample` | 抽样记录 | `Snippet`（抽了什么、结果如何） |
| `manual` | 审核员手填 | `Remark` / `AttachmentsJson` |
| `doc_slice` | **复用准备期证据** | `CapturedIn=prep` 照常进装配包 |

> **准备期证据在检查阶段照常显示并参与分析**，标 `prep` 来源。用户说的「系统根据原始企业档案和现场证据，生成检查证据」——就是这两类一起进装配包。

### 9.2 分析差异（相对准备，只有 4 处）

| 维度 | 准备 | 检查 |
|---|---|---|
| 提示词 | `audit_prep` | `audit_check` |
| 证据块 | `clauses[].docs` | `clauses[].docs` **+** `onsiteEvidence[]` |
| 输出主字段 | `state` / `ncHint` / `verifyLevel` | `conclusion` / `ncSuggested` / `ncDraft` |
| 后置 | 派生入场安排 | 开 NC / 导出报告 |

**其余全部相同**——同一张结论表、同一套锁定、同一套指纹、同一个队列。这就是 42 号说的「结构一套，流程两条，提示词两套」。

### 9.3 结论三档 + NC 建议

| `Conclusion` | 含义 | 实测依据（42 号 §一） |
|---|---|---|
| `pass` | 符合 | `合格` 77 / `Y` 70 / `OK` 48 |
| `ofi` | **观察项**（改进机会，不构成不符合） | `OFI1` / `OFI2` / `OFI3` |
| `nc` | 不符合 | `N` |
| `na` | 不适用 | — |

**`ncSuggested=yes` 时前端「开 NC 卡片」按钮才亮**（现在 `issueNc` / `aiSuggestNc` 已定义但前端从未调用——这是 F6 的姊妹问题，§十四 修复清单里有）。

## 十、锁定、跳过、重跑、指纹

### 10.1 锁定的定义（**本次修订**）

用户原话：「一旦一个检查项被锁定了，即使选择了这个检查项，但我们队列执行的时候，也要忽略该检查项」。

**这句话把锁的语义定死了三件事**：

| # | 结论 | 说明 |
|:--:|---|---|
| 1 | 锁在**检查项**上，不在结果行上 | 一个检查项 3 条款只锁 1 次，不是锁 3 行 |
| 2 | 锁是**硬跳过**，不是"提示" | 勾选了也跑不了，⛔ 不是弹窗问「要不要跳过」 |
| 3 | 锁的唯一出口是**解锁** | 没有任何 `RunMode` 能绕过锁（包括 `full`） |

**载体**：`cert_check_lock`（§4.5.9），唯一键 `(CheckItemCode, StageKind)`。

| `StageKind` | 含义 | 用在哪 |
|---|---|---|
| `all` | **整项锁死**，准备和检查两个分支都不跑 | 默认（界面「锁定检查项」） |
| `prep` | 只锁准备分支 | 确认了"资料齐不齐"，但现场还要去 |
| `onsite` | 只锁检查分支 | 最终判定已定，不再重跑检查 |

> **`all` 是默认值**，因为它最符合用户口径（"一个检查项被锁定了"）。
> 分分支锁是**能力**不是默认——给"我确认了准备结论，但现场还没去"这种真实场景留口子。

**锁住的是什么**：不是"禁止查看"，而是**禁止任何队列执行覆盖它**。结果、证据链、疑点、审核员的修改全部冻结。

### 10.2 三道闸门（⛔ 少一道就有漏洞）

只在一个地方判断锁，一定有时间窗漏洞（入队 → 执行之间可能被人锁上）。所以三道都要：

```
① 建任务时（勾选检查项 → 建 cert_task_item）
   SELECT d.Code FROM cert_audit_plan_detail d
   LEFT JOIN cert_check_lock l
          ON l.CheckItemCode = d.Code AND l.IsActive = 1
         AND l.StageKind IN ('all', @taskKind)
   WHERE d.PlanCode = @planCode AND l.Code IS NULL      -- 只要没锁的
   → 锁定的项：仍建 task_item，但 Status='skipped'，Message='已锁定，跳过'
   → 锁定的项：⛔ 不投 cert_expert_task_queue_item

② 执行时（ExpertCheckItemExecutor 第一行）
   if (await IsLockedAsync(checkItemCode, taskKind)) {
       ItemStatus = 'skipped';  Message = '已锁定（执行前被锁），跳过';
       return;                       // ⛔ 不调 LLM、不写结果
   }

③ 写入时（落 cert_check_result 前）
   if (await IsLockedAsync(checkItemCode, taskKind))
       throw new InvalidOperationException("检查项已锁定，拒绝写入");
```

| 闸门 | 防什么 |
|---|---|
| ① 入队 | 白建队列项、白占并发位、白打 LLM 配额 |
| ② 执行 | 入队后、执行前被锁上（时间窗） |
| ③ 写入 | 极端漏判（代码路径绕过前两道） |

### 10.3 全锁的情况：不许空转

```
勾了 8 项，8 项全锁：
  → 任务仍然创建（留痕：谁在什么时候试图跑过）
  → Status = 'done'，ItemTotal=8, ItemDone=0, ItemSkipped=8
  → Message = "选中的 8 个检查项均已锁定，本次未执行任何分析"
  → 界面：绿色提示（不是错误）
```

> ⛔ **不要报错**：勾到已锁定的项是正常误操作，报错会让人以为系统坏了。
> ⛔ **也不要静默**：必须说清"为什么什么都没跑"。

### 10.4 锁与指纹的关系（**本次修订的关键简化**）

**旧设计**：`IsLocked=1` **且** 指纹未变 ⇒ 才跳过（两个条件缺一不可）。

**新设计**：`IsLocked=1` ⇒ **无条件跳过**。指纹不再参与"跳过"判断，改用于**过期告警**：

```
锁定项 + 证据变更（指纹变）⇒ 不重跑，但：
   cert_check_analysis.Status = 'stale'
   cert_task_item.RerunState = 'suggested'
   Message = "证据已变更（3 份文档重传），结论可能过期，建议解锁后重跑"
   界面：该行标橙「证据已变更」
```

**为什么这样更好**：

| 维度 | 旧（锁 + 指纹都满足才跳） | 新（锁就跳，指纹只告警） |
|---|---|---|
| 符合用户口径 | ❌ 用户说"锁了就忽略" | ✅ |
| 人工判断被覆盖风险 | 低 | 低（锁 = 冻结） |
| 审核员是否知情 | ❌ 悄悄跳过，不知道证据变了 | ✅ 明确告警「证据变了，你可能要重跑」 |
| 实现复杂度 | 高（两条件组合 4 种分支） | 低（一个条件） |

> **F10 的定性随之调整**：不是"必须补指纹比对才能跳过"，而是"**跳过时必须比对指纹并告警**"。
> 跳过不需要指纹；"跳过之后要不要提醒审核员"需要。

### 10.5 指纹算法（不变）

```
EvidenceFingerprint = MD5(
    GROUP_CONCAT(CONCAT(e.Code, ':', e.ContentMD5, ':', e.Status) ORDER BY e.Code ASC)
)
```

任一证据「内容变了（MD5 变）」或「状态变了（collected→dropped）」⇒ 指纹变。

**存与比**：存 `cert_check_analysis.EvidenceFingerprint`；比对时取 `IsCurrent=1` 那条 vs 当前重算值。

### 10.6 三种重跑模式（锁定项一律跳过）

| `RunMode` | 行为 | 用在哪 |
|---|---|---|
| `full` | 未锁项**全部重跑**（旧分析置 `IsCurrent=NULL`，新建一条） | 首次 / 想彻底重来 |
| `incremental` | 只跑「未锁 且（没分析过 或 指纹变了）」的项 | **默认**，最省钱 |
| `selective` | 只跑 `ItemCodes` 里指定的项（**仍跳过锁定的**） | 补跑失败项 |

> **三种模式对锁定项的行为完全一致：跳过。** 想跑锁定项，唯一路径是先解锁。
> 所以 `cert_task_item.SkipLocked` **恒为 1**，保留只为兼容旧数据。

### 10.7 解锁

| 项 | 规则 |
|---|---|
| 谁能解 | 锁定人本人，或同机构管理员 |
| 必填 | `UnlockReason`（为什么解锁） |
| 留痕 | `cert_check_lock` 不删行：`IsActive=0` + `UnlockedBy/At/Reason`；另写一条日志 |
| 解锁后 | 恢复"可被队列执行"；界面从「已锁」变「可编辑」 |
| 页面锁期间 | **不许解锁**（队列跑着时解锁 = 允许覆盖，自相矛盾） |

**解锁后不会自动重跑**：要审核员再点一次。⛔ 不许"解锁即重跑"——那等于绕过人的决定。

### 10.8 `ResultStale` 的处理

计划被编辑（条款组或部门变了）⇒ 该检查项所有 `cert_check_result.ResultStale=1` + `StaleReason="计划条款变更"`。

| 项状态 | 处理 |
|---|---|
| 未锁 | 下次 `incremental` 自动重跑 |
| **已锁** | **不重跑**，但标「计划已变更，锁定的结论基于旧条款」——必须让审核员看见 |

## 十一、疑点链路（当前完全断掉）

### 11.1 三段：写 / 读 / 处置

```
① 写（系统）
   audit_prep / audit_check 输出 points[] → 逐条 upsert cert_point
   ★ 挂到本次分析：AnalysisCode = 当前分析 Code
   幂等键：Fingerprint = MD5(AnalysisCode + ClauseCode + PointKind + Action)
          ⇒ 同一次分析内同指纹不重复插入（重试不翻倍）
   Origin = 'prep'（或 'onsite'）
   Status = 'open'

② 读（界面）
   按分支读：WHERE AnalysisCode = 该分支 IsCurrent=1 的那条
   检查项详情里按条款分组展示；统一视图「疑点」列显示 open 条数
   按 Mode 过滤：remote（可远程解决） / onsite（必须现场）

③ 处置（审核员）
   resolve  → Status='resolved'，必填 ResolveReason（怎么解决的）
   drop     → Status='dropped'，必填 ResolveReason（为什么不查了）
   转现场   → 派生入场安排时被选中（§4.4 过滤条件）
```

> **为什么要带 `AnalysisCode`**：同一检查项准备阶段产 2 个疑点、检查阶段产 3 个疑点。
> 不带分析 Code 就只能靠 `Origin` 猜，而 `Origin=manual`（审核员手加）根本分不出属于哪次分析。
> 带上是精确的，且重跑产生新分析时，旧疑点自然跟着旧分析变历史——**不需要"重跑时删旧疑点"这种危险操作**。

**必填校验**：`resolved` / `dropped` 时 `ResolveReason` 为空 ⇒ 拒绝。⛔ 不许静默销账。

### 11.2 远程渠道（**裁决点 Q4**）

用户说「针对这些疑点是否可以通过微信等其他渠道解决一部分的问题」。

**两个方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | 不加字段。`Mode=remote` 即「可远程解决」，解决后写 `ResolveReason` 文本留痕（如「微信沟通，企业提供 OA 导出截图，见证据 E-0031」） | 零成本；渠道信息在文本里，可搜索但不可统计 |
| **B** | 加 `Channel`（`wechat`/`email`/`phone`/`meeting`/`onsite`）+ `ResolvedEvidenceCode`（指向补的证据） | 多 2 列；可统计「远程消解率」 |

> **建议先 A 后 B**：先跑通链路，等有真实数据了再决定要不要统计渠道。因为「远程消解率」这个指标现在还没有业务方要看。

## 十二、派生入场安排（§4.4 的算法，此处给完整伪代码）

```sql
-- ① 过滤：资料齐、无疑点的不进现场（★ 只看「当前准备分析」）
SELECT d.Code, d.DeptNames, d.Clauses,
       SUM(IFNULL(p.EstMinutes, 15)) AS EstTotal,
       COUNT(p.Code)                 AS PointCount
FROM cert_audit_plan_detail d
-- 当前准备分析（IsCurrent=1）；没有准备分析过的项不进派生
JOIN cert_check_analysis a
  ON a.CheckItemCode = d.Code AND a.StageKind = 'prep' AND a.IsCurrent = 1
     AND a.IsDeleted = 0
JOIN cert_check_result r
  ON r.AnalysisCode = a.Code AND r.IsDeleted = 0
LEFT JOIN cert_point p
  ON p.AnalysisCode = a.Code AND p.Status = 'open' AND p.IsDeleted = 0
WHERE d.PlanCode = @planCode AND d.IsDeleted = 0
  AND ( r.PrepState <> 'found'                     -- 资料不齐
        OR r.IsMandatory = 1                        -- 或明确必须做
        OR r.PrepNcHint = 'yes'                     -- 或建议开 NC
        OR p.Code IS NOT NULL )                     -- 或有未消解疑点
GROUP BY d.Code, d.DeptNames, d.Clauses
ORDER BY d.Sort;
```

> **必须 `JOIN` 当前分析，不能直接查 `cert_check_result`**：改键后一个检查项的准备结果散在多次分析里，
> 不限定 `IsCurrent=1` 会把历史分析的疑点也算进现场工作量（重跑 3 次 = 工作量翻 3 倍）。
> 另：**没有准备分析过的检查项不进派生**（`JOIN` 而非 `LEFT JOIN`）——没准备就不知道要不要去现场，先跑准备。

```
② 按 DeptNames 分组 → 部门块
③ 每块 SUM(EstTotal) → 建议时段数 = ceil(总分钟 / 240)
④ 输出只读预览：{ 部门, 检查项数, 疑点数, 预计小时 }
⑤ （延后）人填日期/上午下午/谁去 → 落 cert_onsite_schedule + _slot
```

> **④ 就是本期该交付的最小价值**：审核员在入场前就知道「品质部大概要 3.5 小时、生产部 2 小时」，可以直接跟企业定日期。

### 13.1 NC 卡片

| 步 | 动作 |
|---|---|
| 1 | `audit_check` 输出 `ncDraft` → 界面「建议开 NC」按钮亮起 |

### 13.2 报告导出

**必须快照**（42 号 §4.3）：

```
导出时：
  snapshot = { 检查项[] + 证据摘要[] + NC[] + 结论[] + 汇总统计 }
  INSERT cert_report { SnapshotJson: snapshot, ReportVersion: n, Status: 'draft' }
  → 生成 Word/PDF 只读 SnapshotJson，⛔ 不许 join 实时表
```

**理由**：报告要盖章归档。实时查询 ⇒ 三个月后有人改了某个检查项，已签发的报告内容跟着变，审计上是致命的。

| **D1** | §五「`StartTaskAsync` 投 `yzh_queue`，`SourceId = taskCode`」 | `yzh_queue` 上有 **`uk_source(SourceType, SourceId)` 唯一索引** —— 框架契约是「**一个来源 = 一条队列**」，且 `QueueManager` **没有** `AddTasksAsync` 可以往旧队列追加。而 `cert_task` 是可重跑的 ⇒ 第二次点「开始」必炸：`投递队列失败：队列主表插入失败：数据已存在（唯一约束冲突）` | 已修：`SourceId = attempt<=1 ? taskCode : "{taskCode}#{attempt}"`。**反向查找不靠 `SourceId`，靠 `cert_task.QueueCode`**（每轮覆盖成本轮的）。这是 F1 修复里唯一没预料到的坑 |
| **D2** | §11「汇总回写放 `QueueManager` 终态回调」 | `QueueManager.SafeOnTaskStateChangedAsync` **只在 `failed` / `cancelled` 时**调钩子，**成功时不调** —— 只靠回调汇总，成功跑完永远不会翻 `done`，页面永久锁死 | 已修：**主路径在 `ExecuteAsync` 返回前汇总**（无论成败），`OnTaskStateChangedAsync` 只兜底失败/取消。汇总数据源选 `cert_task_item` 而非 `yzh_queue_task`（后者要等 QueueManager 返回后才更新，会永远差最后一项） |
| **D3** | §10.3「全锁 ⇒ 不建队列、直接 `done`」 | 实际执行顺序必须**先算进度初值再判全锁**，否则全锁分支写 `done` 后又被 `QueueAttempt += 1` 覆盖成 `pending` | 已按「进度初值 → 全锁判定 → 投队列」排序，代码注释里锁死了这个顺序 |
