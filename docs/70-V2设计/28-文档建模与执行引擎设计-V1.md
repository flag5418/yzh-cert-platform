## 一、核心设计三句话

> 1. **文档只提一次**：每份企业文档走一遍 LLM，产出一个包含通用属性 + 分类专属属性的 JSON。
> 2. **条款执行 = 供给 + 推理**：供给层自动匹配文档 JSON 中的字段，推理层用固定模板统一处理。
> 3. **LLM 调用线性可控**：200 份文件 = 200 次，80 个检查项 = 80 次，总计 ~360 次，可预算、可执行。

## 二、文档建模：两层属性提取 → 一份 JSON

### 2.1 为什么不存原文档×条款的展开

27 号文档的实证已验证：87.5% 的文档被多条条款引用，且不同条款读取同一文档的不同字段。如果按「文档×条款」存储提取结果（路径 B），会产生大量冗余且维护困难。

本文选择路径 A 的升级版——**文档只建模一次，条款执行时按需读取**。

### 2.2 两层提取模型

```
一份文档输入
      │
      ▼
┌─────────────────────────────┐
│ 第一次提取：通用属性         │  ← 所有文档都走一遍
│ · 文档名称 / 文档编号        │
│ · 过程归属（部门 + 过程）     │
│ · 文档类型（规则/内审/记录…） │
│ · 文档分类（运营/生产/管理…） │
│ · 核心内容摘要               │
│ · Markdown 原文              │
└─────────────┬───────────────┘
              │
              ▼
     根据通用属性判断文档分类
              │
    ┌─────────┼─────────┬──────────┐
    ▼         ▼         ▼          ▼
┌────────┐┌────────┐┌────────┐┌────────┐
│运营类   ││生产类   ││管理类   ││内审类   │
│专属提取 ││专属提取 ││专属提取 ││专属提取 │
│        ││        ││        ││        │
│产品范围 ││工艺参数 ││审批层级 ││审核日期 │
│客户信息 ││设备编号 ││会议日期 ││审核范围 │
│交付标准 ││检验标准 ││参与岗位 ││不符合项 │
│合同编号 ││工序流程 ││决议事项 ││审核结论 │
└───┬────┘└───┬────┘└───┬────┘└───┬────┘
    │         │         │         │
    └─────────┴─────────┴─────────┘
              │
              ▼
      合并为一份 JSON 输出
```

### 2.3 文档分类与专属属性的配置关系

文档分类与专属字段之间存在**一套配置关系**——不同分类对应不同的专属属性组：

| 文档分类 | 专属属性组（示例） | 体系标准依据 |
|---|---|---|
| 运营类 | 适用产品范围、客户信息、交付标准、合同编号 | 8.2 / 8.4 相关 |
| 生产类 | 工艺参数、设备编号、检验标准、工序流程、工作环境 | 8.5 / 7.1.3 相关 |
| 管理类 | 审批层级、会议日期、参与岗位、决议事项、发文范围 | 5.3 / 9.3 相关 |
| 内审类 | 审核日期、审核范围、审核依据、不符合项数、审核结论 | 9.2 相关 |
| 资质类 | 统一社会信用代码、法定代表人、注册资本、经营范围、有效期 | 4.1 / 7.1.1 相关 |
| 设备类 | 设备编号、型号规格、校准日期、校准机构、有效期 | 7.1.5 / 8.5.1 相关 |
| 设计类 | 设计阶段、设计输入、设计输出、评审结论 | 8.3 相关 |
| 监测类 | 监测项目、监测频次、监测结果、达标情况 | 9.1.1 相关 |

> **配置即 Schema**：每类文档的专属属性组是可配置的。新增一类文档只需在配置表中加一行「分类→字段组」的对应关系，无需改代码。

### 2.4 每份文档的最终 JSON 结构

```json
{
  "docCode": "DOC-2026-001",
  "docName": "焊接工序作业指导书",

  "universal": {
    "processDept": "生产部",
    "processName": "焊接过程",
    "docType": "规则文档",
    "docCategory": "生产类",
    "coreContent": "规定了焊接工序的工艺参数（温度、压力、速度）及检验标准...",
    "markdown": "## 1. 适用范围\n适用于车架焊接工序..."
  },

  "categorySpecific": {
    "工艺参数": "温度：280±10℃；压力：0.4MPa；速度：100mm/s",
    "设备编号": "HJ-001、HJ-002、HJ-003",
    "检验标准": "焊缝外观无气孔、夹渣，强度≥母材80%",
    "工序流程": "备点焊→满焊→去焊渣→自检→专检"
  }
}
```

> **稀疏性**：一份「营业执照」的 JSON 中不会有 `工艺参数`、`设备编号` 等字段；一份「作业指导书」的 JSON 中也不会有 `统一社会信用代码`。各填各的，互不干扰。

## 三、执行引擎：供给 + 推理

### 3.1 条款执行的两部分

```
┌─────────────────────────────────────────────────────────┐
│                条款执行 = 供给 + 推理                     │
├────────────────────────┬────────────────────────────────┤
│  来源（供给层）         │  推理（推理层）                  │
│                        │                                │
│  · 条款属性 ──────┐    │  固定提示词模板（结构不变）       │
│                ├──→ 喂入 ──→ LLM ──→ 结论             │
│  · 文档 JSON ────┘    │                                │
│  · 审核员证据 ────→   │                                │
└────────────────────────┴────────────────────────────────┘
```

### 3.2 供给层：通过属性匹配自动获取

条款执行时，系统根据**条款属性（L1 的 attribute 配置）** 和 **文档的通用属性（过程、类型、分类）** 自动匹配相关文档，从文档的 JSON 中提取对应字段：

```
条款 8.5.1（生产和服务提供）
    ↓ 条款属性指示
需要：生产过程控制类文档
    ↓ 属性匹配
文档池中：processName=焊接过程 AND docCategory=生产类 → 命中《焊接工序作业指导书》
    ↓ 从 JSON 中提取
核心内容："规定了焊接工序的工艺参数及检验标准..."
专属属性：{工艺参数: "...", 设备编号: "...", 检验标准: "..."}
    ↓ 自动填入推理模板
```

### 3.3 推理层：固定模板

提示词模板**只写一次**，内部全部用变量：

```markdown
# 条款符合性检查

## 条款基本信息
条款编号：{{clauseCode}}
条款名称：{{clauseName}}
条款作用：{{clauseIntent}}
约束强度：{{obligation}}

## 该条款的检查要求
{{clauseRequirement}}

## 企业已提供的相关资料（自动匹配）
{{#each matchedDocs}}
### {{docName}}
分类：{{universal.docCategory}} ｜ 过程：{{universal.processDept}}-{{universal.processName}}
核心内容：{{universal.coreContent}}
{{#if categorySpecific}}
相关字段：{{categorySpecific}}
{{/if}}
{{/each}}

## 审核员补充证据（认证执行阶段才有）
{{auditorEvidence}}

## 请基于以上完整信息
1. 判断该条款的符合性（符合 / 不符合 / 观察项）
2. 说明判断依据（必须引用原文中的具体内容）
3. 如为不符合，说明不符合的事实和涉及的分项
```

### 3.4 为什么这样避免"提示词大全"

| 反模式 | 本设计 |
|---|---|
| 为每份文档写一个提示词 | ❌ 200 份文档 = 200 个提示词 → 爆炸 |
| 为每个条款写一个提示词 | ❌ 201 条条款 = 201 个提示词 → 爆炸 |
| 为每份文档×每个条款写一个提示词 | ❌ 200×201 = 40,200 个提示词 → 荒谬 |
| **一个通用推理模板 + 动态填充变量** | ✅ **1 个模板**，变量值动态填充 |

提示词模板是**结构固定、信息动态**的。模板只定义「怎么推理」，具体内容（文档内容、证据、条款要求）全部通过变量注入。

## 四、LLM 调用预算

### 4.1 三阶段调用量

```
阶段一：文档属性提取（一次性）
  200 份文件 × 1 LLM = 200 次

阶段二：认证准备（条款级检查）
  80 个检查项 × 1 LLM = 80 次

阶段三：认证执行（加入证据 + NC 预判）
  80 个检查项 × 1 LLM = 80 次

  ──────────────────────────────────
  总计：~360 次 LLM，线性可控
```

### 4.2 一次 LLM = 一个自包含任务

```
❌ 链式（不可控）
   文档分析 → LLM1 → 分类 → LLM2 → 专属提取 → LLM3 → ...
   一个问题裂变成 N 次，次数不可预测

✅ 单次完整调用（可控）
   提示词 = 通用提取要求 + 分组配置 + 专属字段提取要求
   → 一次 LLM 输出完整 JSON
   可换更强模型保障上下文，不改架构
```

### 4.3 单次 LLM 的提示词结构（文档提取）

```markdown
# 文档属性提取（一次完成两阶段）

请分析以下企业文档，提取属性信息。

## 文档内容
{{documentContent}}

## 第一阶段：通用属性（必须提取）
1. 文档名称
2. 过程归属：这份文档涉及哪个部门、哪个过程（如"生产部-焊接过程"）
3. 文档类型：规则文档 / 内审文档 / 管理评审 / 记录文件 / 资质证书 / 合同文件 / 其他
4. 文档分类：运营 / 生产 / 管理 / 内审 / 资质 / 设备 / 设计 / 监测 / 其他
5. 核心内容摘要：200 字以内，概括这份文档说了什么
6. Markdown：将文档内容转写为结构化的 Markdown

## 第二阶段：分类专属属性（根据第一阶段的分类结果，提取对应字段）

如果分类为「生产类」，额外提取：工艺参数、设备编号、检验标准、工序流程、工作环境
如果分类为「运营类」，额外提取：适用产品范围、客户信息、交付标准、合同编号
如果分类为「管理类」，额外提取：审批层级、会议日期、参与岗位、决议事项、发文范围
如果分类为「内审类」，额外提取：审核日期、审核范围、审核依据、不符合项数、审核结论
如果分类为「资质类」，额外提取：统一社会信用代码、法定代表人、注册资本、经营范围、有效期
如果分类为「设备类」，额外提取：设备编号、型号规格、校准日期、校准机构、有效期
如果分类为「设计类」，额外提取：设计阶段、设计输入、设计输出、评审结论
如果分类为「监测类」，额外提取：监测项目、监测频次、监测结果、达标情况

注：分类与专属字段的对应关系可能随配置扩展。

## 输出格式
以 JSON 输出，结构如下：
{
  "universal": { ... },
  "categorySpecific": { ... }
}
没有值的字段不要输出。
```

## 五、完整端到端流程

### 5.1 数据流总图

```
┌──────────────────────────────────────────────────────────┐
│  阶段一：文档提取                                          │
│                                                          │
│  企业上传文件 → 逐个走 LLM（两阶段提取）→ 文档 JSON 入库    │
│  （200 份 = 200 LLM）                                     │
└────────────────────────┬─────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│  阶段二：认证准备                                          │
│                                                          │
│  80 个检查项逐个执行：                                     │
│  ① 根据条款属性 + 文档标签，自动匹配相关文档                │
│  ② 从文档 JSON 中取出核心内容 + 专属属性                   │
│  ③ 统一推理模板填充变量 → LLM → 符合性结论                │
│  （80 项 = 80 LLM）                                       │
└────────────────────────┬─────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│  阶段三：认证执行                                          │
│                                                          │
│  逻辑基本同阶段二，额外叠加：                               │
│  + 审核员现场证据（survey/site/interview）                 │
│  + NC 预判断（不符合项初步判定）                            │
│  （80 项 = 80 LLM）                                       │
└──────────────────────────────────────────────────────────┘
```

### 5.2 阶段二/三的详细执行流程

```
对每个检查项（条款构成）：
│
├── Step 1: 供给（自动）
│   ├── 读条款属性（L1 配置）→ 该条款需要什么信息、关注哪些过程
│   ├── 读企业文档池（JSON）→ 按过程 + 分类匹配相关文档
│   ├── 从匹配文档中取出：核心内容 + 专属属性字段
│   └── 读审核员证据（阶段三才有）
│
├── Step 2: 组装提示词
│   ├── 推理模板（固定不变）
│   ├── 注入变量：条款要求 + 文档内容 + 证据
│   └── 组装完成 → 一条完整的 LLM 输入
│
└── Step 3: 执行推理
    ├── 一次 LLM 调用 → 输出符合性结论
    └── 结论写入系统（含锚点原文引用）
```

### 5.3 审核员证据的叠加方式

审核员证据不改变推理模板的结构，只是在供给层**多注入一个变量**：

```
认证准备：模板变量 = {条款要求} + {文档内容}
认证执行：模板变量 = {条款要求} + {文档内容} + {审核员证据}
```

模板中预留的 `{{auditorEvidence}}` 变量在认证准备阶段为空，认证执行阶段填入实际证据内容。**模板不变，只有供给变化。**

## 六、扩展性分析

### 6.1 新增一份企业文档

```
影响：文档池多一个 JSON
      已完成的检查项结论不变（文档是一次性提取的，已消费完毕）
      后续检查项自动能匹配到新文档
工作量：1 次 LLM（提取）
```

### 6.2 新增一条条款（或检查项）

```
影响：条款属性配置新增一行（L1）
      供给层的匹配关系新增（条款 → 过程 → 文档类型）
      推理模板不变（已存在，结构固定）
工作量：配置条款属性 + 执行 1 次 LLM（检查）
```

### 6.3 更换更强的 AI 模型

```
影响：不需要改任何模板或架构
      只需要在 LLM 调用层切换模型参数
      因为每个调用都是自包含的（不限定模型能力）
      只要新模型的上下文窗口能容纳组装后的提示词即可
工作量：改配置
```

### 6.4 引入新的文档分类

```
影响：在「分类→专属属性组」配置表中新增一行
      文档提取模板自动感知该分类（模板中有对应的分支）
      无需改代码
工作量：配置
```

### 6.5 文档更新（企业换版）

```
影响：重跑该文档的提取（1 次 LLM）
      新 JSON 覆盖旧 JSON
      后续检查项自动使用新版
工作量：1 次 LLM（仅该文档）
```

## 七、与四层属性模型的对齐

```
L0 属性池（cert_clause_attr_def）     ← 已完成，本文不动
    ↓
L1 条款配置（cert_clause_attr）        ← 已完成，本文不动
    ↓
文档 JSON（本文新增）                  ← 每份文档的通用 + 专属属性
    ↓
L2 企业值（暂缓）                      ← 未来从文档 JSON 自动生成
    ↓
L3 判定（暂缓）                        ← 未来阶段二/三的输出
```

文档 JSON 是连接 L1 条款配置和 L2 企业值的**中间桥梁**：

- L1 说"这条款需要什么信息"
- 文档 JSON 说"这份文档有什么信息"
- 供给层做匹配 → 推理层做判定 → 产出 L3

## 八、为什么这个设计比纯路径 A 更好

纯路径 A 的疑问（27 号文档提出）：

| 疑问 | 本设计的回应 |
|---|---|
| 投影提示词可能丢失条款视角的细节 | 不做投影提示词——条款执行是统一推理模板直接读文档 JSON，不存在"投影"这个中间步骤 |
| 投影需要多次 LLM 调用 | 文档提一次（200 次），条款跑一次（80 次），总计 280 次，没有额外的投影调用 |
| 投影提示词设计负担重 | 没有投影提示词，只有 1 个推理模板 |

> 本设计的本质：**把路径 A 的"按需投影"升级为"属性自动匹配 + 统一推理"**。不是文档端处理多样性，也不是条款端处理多样性，而是中间的供给层做匹配、推理层只做推理。

## 九、设计原则总结

| # | 原则 | 落地 |
|---|---|---|
| 1 | **文档只提一次** | 两阶段提取 → JSON 入库 |
| 2 | **LLM 调用线性可控** | 200 + 80 + 80 = ~360 次 |
| 3 | **一个推理模板** | 结构固定，变量动态填充 |
| 4 | **供给与推理分离** | 供给只负责"拿什么"，推理只负责"怎么判" |
| 5 | **分类专属属性可配置** | 配置表驱动，改配置不改代码 |
| 6 | **证据叠加不改模板** | 阶段二到阶段三只是多一个变量 |
| 7 | **模型可替换** | 自包含调用，换模型只改配置 |
| 8 | **扩展是"加信息"不是"改逻辑"** | 新文档、新条款、新分类都是增量 |
