# 条款标准化整体设计：四层模型

> **版本**：V1 ｜ **日期**：2026-10-28 ｜ **状态**：待裁决（D-M1…D-M10）
>
> **定位**：本文**取代 21 号（字段草案）与 23 号（第一步定义）**，成为「条款 × 属性 × 值」这条主链的唯一设计依据。
> **范围**：从**属性池**到**预 NC** 的完整链路，横跨后台（cert-admin）与专家端（cert-auditor）。
> **不在范围**：审核组、场次排期、报告章节、录音转写 —— 各有独立设计。
>
> **为什么重写**：21/23 号只把「后台两层」写对了，把第 3 层（企业实际值）当作"后续再说"。但第 3 层不是后续，**它是这条链的产出**；不给它独立表，它就会被塞回条款配置表 —— 前面反复出错全部源于此。

---

## 一、用「人」的模型定调（四层，不是三层）

| 类比 | 系统里是什么 | 表 | 端 | 量级 |
|---|---|---|---|---|
| **属性池**：所有人的所有可能属性（姓名、年龄、学历、执照、宇航员训练） | 属性全集 | `cert_clause_attr_def` | 后台 | **30–50 行，不怕多** |
| **职业定义**：工程师需要学历 + 编程 + 项目经验，**不含宇航员训练** | 某条款该有哪些属性 + 固定值 | `cert_clause_attr` | 后台 | 每条款 5–12 行 |
| **具体的人**：张三，28 岁，本科，5 年经验 | 某企业在这条款上的**实际值** | `cert_enterprise_clause_attr` | **专家端** | 每企业数百行 |
| **体检报告**：张三这项指标合格/不合格，依据哪张化验单 | 检查证据 + 预 NC | `cert_check_evidence` / `cert_check_result` | **专家端** | 每企业数十行 |

### 三个推论（模型的全部约束）

1. **池子大、配置小。** 池子 30–50 条不嫌多，因为每个"职业"只挑自己那几条。池子小了反而会想"拿身体部位凑"，属性就不干净 —— 这正是此前一会儿 18 条、一会儿 9 条的原因：**在用"每条款都要有的"标准去限制池子**。
2. **"挑哪几条"不需要额外字段。** 没挑 = 没行 = 稀疏。属性池**不加**"适用条款"之类的列。
3. **实施时补的"姓名性别"永远不进条款配置。** 条款表回答"工程师该有什么"，企业表回答"张三具体是什么"。**这两张表一混，就是前面反复出错的根源。**

> **第 4 层（体检报告）是本文新增的**：用户此前说"形成检查证据，并根据检查证据形成预 NC" —— 它既不是"要求"，也不是"值"，是**判定**，必须单独一层。

## 二、四层各只回答一个问题（划界表）

| 层 | 唯一的问题 | 谁填 | 什么时候 | 绝不回答 |
|---|---|---|---|---|
| **L0 属性池** | 世界上**有哪些**属性、类型是什么、作用是什么 | 平台（映智汇） | 一次 | 哪条款用它 |
| **L1 条款配置** | 这条款**要求什么**（哪些属性 + 固定值） | 专家 / AI 起草 → 复核 | 每标准一次 | 这家企业有没有 |
| **L2 企业值** | 这家企业**实际是什么**、可不可信 | 匹配 / 上传 / 现场 / 人工 | 每企业每次 | 标准要求什么 |
| **L3 判定** | 这条款**符不符合**、开不开 NC | 规则引擎 + 模型 | 每企业每次 | 值从哪来 |

### 一条铁律（拆表判据）

> **任何一张表，如果它的行既描述「标准要求」又描述「某企业实际」，它就该拆。**

对照现有库：`cert_standard_directory_file` 现在正是这样 —— 同一行里既有"标准要这个文件"（`IsRequired`），又有"这家企业传了没"（`UploadStatus`/`MatchState`）。**这是 V1 留下的债，V2 新表一律不许再犯。**

### 三条不许跨层的边界

| 越界写法 | 为什么错 | 正确做法 |
|---|---|---|
| 在 L1 存 `Confidence` / `Source` / `ValueState` | 这些是"值可不可信"，只有 L2 才有 | 放 L2 |
| 在 L1 存 `ClauseNumber` | 人读编号在 `cert_iso_clause` 已有 | join，或计划层带 |
| 在 L2 存"标准要求几条材料" | 那是 L1 的事，且会随标准换版失效 | 读 L1 现算 |

## 三、L0 属性池 `cert_clause_attr_def`

### 3.1 字段（一个属性 = 一行）

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `Code` | varchar(50) | ✅ | 属性码，**业务键**（`Obligation`） |
| `AttrName` | varchar(100) | ✅ | 属性名（约束强度） |
| `ValueType` | varchar(20) | ✅ | 值类型，见 §3.2 |
| `DictCode` | varchar(50) | | 值域字典码；`dict`/`dict_multi` 必填 |
| `ValueSource` | varchar(20) | ✅ | **固定 / 参考 / 求值**，见 §3.3 |
| `AttrRole` | varchar(100) | | 作用角色（多值逗号）：`judge`/`match`/`plan`/`report`/`prompt` |
| `PoolLayer` | varchar(20) | ✅ | 池子分层：`base`/`family`/`standard`，**只表示何时补，不表示适用于哪些条款** |
| `Remark` | varchar(500) | | **这个属性干什么用**（一句话，给人看） |
| `IsValid` | tinyint | ✅ | 是否启用（停用而不删，历史值仍可读） |
| `Sort` | int | ✅ | 展示顺序 |
| + 审计列 | | | `IsDeleted`/`CreateBy`/`CreateTime`/`UpdateBy`/`UpdateTime` |

**业务列只有 5 个**（`AttrName` `ValueType` `DictCode` `ValueSource` `Remark`），其余是治理与分类。

> **为什么不设 `AppliesTo`（适用于哪些条款/章号）**：那是推论 2 的红线。**挑哪几条 = 有没有行**，写在 L1 里。一旦给池子加"适用条款"，就会出现"池子说适用、L1 没配"的双真相。

### 3.2 值类型（10 种）

| `ValueType` | 落库形态 | 例 |
|---|---|---|
| `text` | 单段文本 | `ClauseIntent` |
| `text_multi` | JSON 数组字符串 | `EvidencePoints` |
| `dict` | 单个字典码 | `Obligation = shall` |
| `dict_multi` | JSON 数组（字典码） | `EvidenceKinds = ["record","site"]` |
| `bool` | `"1"`/`"0"` | `IsCritical` |
| `int` | 整数字符串 | `SamplingCount` |
| `date` | `yyyy-MM-dd` | — |
| `json` | JSON 字符串，**结构由代码强类型定** | `RequirementItems` |
| `prompt_filter` | 文本，**召回/过滤用，不产结论** | `MatchHint` |
| `prompt_judge` | 文本，**只允许机构级**（L1 禁用） | — |

> **JSON 的结构不在表里，在代码里。** 例如 `Artifacts` 的元素：
> ```csharp
> public class ArtifactItem {
>     public string ArtifactType { get; set; } = "";  // DICT_ARTIFACT_TYPE
>     public string Name { get; set; } = "";
>     public bool Mandatory { get; set; } = true;
>     public string? Severity { get; set; }            // 空 = 继承条款级
>     public string? FormSchemaCode { get; set; }
> }
> ```
> **材料级严重度不占一行属性** —— 它脱离"哪份材料"无法独立存在，是元素里的字段，不是属性。

### 3.3 `ValueSource` 三档（回答"哪些固定、哪些执行时解决"）

| 档 | 含义 | 谁给 | L1 存什么 | L2 存什么 |
|---|---|---|---|---|
| **`fixed` 固定** | 条款已定，与哪家企业无关 | 专家读国标 | **值本身** | **不存**（无企业差异） |
| **`expected` 参考** | 标准级只能给"期望"，实际从企业取 | 标准级给期望 | **期望**（如要哪类材料） | **实际**（交了几份、过没过期） |
| **`runtime` 求值** | 标准级只给判定条件，结果在专家端算 | 专家给条件 | **条件**（如"有测量设备时才查"） | **求值结果**（适用 / 不适用 + 依据） |

**为什么必须有第三档**：`Applicability=有条件` 是固定值（条款自己写着"当…时"），但"**这家企业适不适用**"要读企业事实才能算。它既不是标准级固定值，也不是企业交的材料，是**求值结果**。只有两档时，这个结果无处安放，只能塞回 L1 —— 于是同一行里既有要求又有实际，正是要拆的那种。

### 3.4 池子分三层（只是实施节奏，不改结构）

| 层 | `PoolLayer` | 内容 | 例 | 何时上 |
|---|---|---|---|---|
| 通用基础 | `base` | 每条款都该有的 9 条 | 约束强度、适用范围、分项要求、要求形态、检查方式、影响程度、条款作用、适用条件、要求的企业材料 | **第一批** |
| 条款族专属 | `family` | 按 4–10 章分化 | 8.3 设计开发 → 设计阶段/验证方式；8.4 采购 → 供方评价方式/外包类型；7.1.5 → 校准周期/溯源等级；9.2 → 内审频次/内审员资格 | 试填 9001 时按需补 |
| 标准专属 | `standard` | 13485 / 45001 特有 | 13485 → 灭菌方式/洁净级别/法规要求；45001 → 危险源类型/防护层级 | 跑 13485/45001 时补 |

> **池子变大不改结构**，只是多几行。这就是它不该写死成 18 或 9 的原因。

### 3.5 第一批 9 条种子（`base`）

| # | `Code` | 属性名 | `ValueType` | `ValueSource` | 作用 |
|:--:|---|---|---|:--:|---|
| 1 | `ClauseIntent` | 条款作用 | `text` | fixed | 文档归纳的语义锚点 |
| 2 | `Obligation` | 约束强度 | `dict`（`DICT_OBLIGATION`） | fixed | **能不能开 NC** 的闸门 |
| 3 | `Applicability` | 适用范围 | `dict`（`DICT_APPLICABILITY`） | fixed | 要不要查 |
| 4 | `ApplicabilityCondition` | 适用条件 | `text` | **runtime** | 求值适用范围的条件 |
| 5 | `RequirementItems` | 分项要求 | `json` | fixed | 逐项判定，NC 精确到 a)/b) |
| 6 | `EvidenceKinds` | 要求形态 | `dict_multi`（`DICT_EVIDENCE_KIND`） | fixed | **去哪个池子找证据** |
| 7 | `CheckModes` | 检查方式 | `dict_multi`（`DICT_CHECK_MODE`） | fixed | 决定用哪组 case |
| 8 | `Severity` | 影响程度 | `dict`（`DICT_SEVERITY`） | fixed | 定级与汇总升级 |
| 9 | `Artifacts` | 要求的企业材料 | `json` | **expected** | 标准级说"要什么"，有没有从企业取 |

> **`Severity` 是唯一语法推不出的**，必须靠法定分级 + 人判断，不能全交给 AI。

## 四、L1 条款配置 `cert_clause_attr`

### 4.1 字段（一条款一属性一值）

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `StandardCode` | varchar(36) | ✅ | 标准 Code |
| `ClauseCode` | varchar(36) | ✅ | 条款 Code（`cert_iso_clause.Code`） |
| `AttrCode` | varchar(50) | ✅ | 属性 Code（`cert_clause_attr_def.Code`） |
| `AttrValue` | text | | **值，就这一个字段** |
| `IsValid` | tinyint | ✅ | 这条配置是否生效 |
| + 审计列 | | | 同 L0 |

**唯一键** `(StandardCode, ClauseCode, AttrCode)`；索引 `(StandardCode, ClauseCode)`。

### 4.2 为什么值只有一个字段

值类型已在 L0 声明过（`Obligation` 是 `dict`，`Artifacts` 是 `json`）。再铺 `ValueCode`/`ValueBool`/`ValueNum`/`ValueJson` 五列 = **把同一个事实写两遍**，且必然打架：改了 L0 的 `ValueType` 忘了迁 L1 数据，两列都留旧值，**谁都不报错**。

读取时按类型解析，一处收口：

```csharp
object? Parse(string valueType, string? raw) => valueType switch {
    "bool"                        => raw is "1" or "true",
    "int"                         => int.TryParse(raw, out var i) ? i : null,
    "date"                        => DateTime.TryParse(raw, out var d) ? d : null,
    "text" or "dict" or "prompt_filter" or "prompt_judge" => raw,
    "text_multi" or "dict_multi" or "json" => raw is null ? null : JsonSerializer.Deserialize<JsonElement>(raw),
    _ => raw
};
```

### 4.3 要按值筛选怎么办

只有三个属性真需要（`Obligation`/`Severity`/`Applicability`，报表与覆盖率要用）。做法是**一个生成列**，不是铺六列：

```sql
ALTER TABLE cert_clause_attr
  ADD COLUMN `FilterCode` VARCHAR(100)
    GENERATED ALWAYS AS (
      CASE WHEN `AttrCode` IN ('Obligation','Severity','Applicability')
           THEN `AttrValue` END) STORED,
  ADD KEY `idx_filter` (`AttrCode`,`FilterCode`);
```

### 4.4 三种空（决定项目会不会烂尾）

| 状态 | 表现 | 含义 | 系统该做什么 |
|---|---|---|---|
| **未配置** | 没有这一行 | 还没提这条属性 | 完备度视图标 **红**；`fixed` 缺 ⇒ 条款**未就绪**，禁止进预检查 |
| **明确无** | 有行，`AttrValue` 为空 | 提取过了，这条款确实不要求（7.3 无任何材料） | 标 **灰**（不适用），正常 |
| **待复核** | 有行有值，`ReviewStatus=draft` | AI 起草未确认 | 标 **黄**，不进业务 |

> **「条款对这家企业不适用」不在这张表。** 那是 L2 的 `runtime` 求值结果（`ValueState=na`），不是标准级的属性值。

### 4.5 量级

9 × 201 = 最多 1,809 行；按稀疏实际约 **1,300 行**（`fixed` 先满填；`expected` 只填期望，实际值在 L2）。

## 五、L2 企业值 `cert_enterprise_clause_attr`（本文重点）

> **这是你强调的「独立的一套表」。** 它不复用 L1，因为 L1 一行代表"标准要求什么"，L2 一行代表"这家企业实际是什么" —— 前者一个标准一份，后者一家企业一份，**生命周期、填写人、可信度语义全都不同**。

### 5.1 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `EnterpriseCode` | varchar(36) | ✅ | 企业 |
| `SessionCode` | varchar(36) | ✅ | **空串 `''` = 企业常驻事实**（如"有没有测量设备"）；有值 = 某次审核场次采集 |
| `StandardCode` | varchar(36) | ✅ | 标准 |
| `ClauseCode` | varchar(36) | ✅ | 条款 |
| `AttrCode` | varchar(50) | ✅ | **只允许 `expected` / `runtime` 类属性**（`fixed` 不进本表） |
| `ActualValue` | text | | 实际值（形态由 L0 的 `ValueType` 决定） |
| `ValueState` | varchar(20) | ✅ | `unknown`/`missing`/`found`/`partial`/`na`，见 §5.2 |
| `SourceType` | varchar(20) | | `upload`/`match`/`onsite`/`interview`/`manual` |
| `Confidence` | decimal(3,2) | | 0.00–1.00；`manual` 恒 1.00 |
| `EvidenceCount` | int | ✅ | 关联证据条数（冗余，列表页不 join） |
| `Remark` | varchar(500) | | 判断说明 |
| + 审计列 | | | 同 L0 |

**唯一键** `(EnterpriseCode, SessionCode, StandardCode, ClauseCode, AttrCode)`；索引 `(EnterpriseCode, SessionCode, StandardCode, ClauseCode)`。

> ⚠️ **`SessionCode` 用空串而非 NULL**：MySQL 唯一键对 NULL 不去重，NULL 会让同一键插入多行。这是必须写进 DDL 注释的坑。

### 5.2 `ValueState` 五态（比"有没有"细一档）

| 态 | 含义 | 会不会开 NC |
|---|---|:--:|
| `unknown` | 还没查（默认） | ❌ |
| `missing` | 查过了，**确实没有** | ⚠️ 满足其他前置才可 |
| `partial` | 有，但不全/过期 | ⚠️ 满足其他前置才可 |
| `found` | 有且完整 | ❌ |
| `na` | **这家企业不适用**（`runtime` 求值结果） | ❌ |

> **`unknown` ≠ `missing`。** 前者是"我们没查"，后者是"企业没有"。CNCA-QMS-01:2025 §5.11.3 要求报告含抽样免责声明 —— **`unknown` 绝不能自动推导为 NC**，这是红线。

### 5.3 为什么不直接把企业值存成"一条款一行 + 若干列"

| 方案 | 问题 |
|---|---|
| `(Enterprise, Clause)` 一行 + 9 列 | 属性池一扩就要 `ALTER TABLE`，池子 30–50 条时变成 50 列稀疏宽表 |
| 复用 L1 表加 `EnterpriseCode` 列 | 同一表里既有标准级行又有企业级行，`WHERE EnterpriseCode IS NULL` 满天飞，**必出错** |
| **本方案：独立 EAV 表** | 加属性不改结构；L1/L2 边界靠表名就分得清 |

## 六、L3 判定：证据与预 NC

### 6.1 检查证据 `cert_check_evidence`（证据链的原子）

| 字段 | 类型 | 说明 |
|---|---|---|
| `EvidenceCode` | varchar(36) | 证据码（主键） |
| `EnterpriseCode` / `SessionCode` | varchar(36) | 归属 |
| `StandardCode` | varchar(36) | 标准 |
| `ClauseCode` | varchar(36) NULL | 条款；**可空**（6 类无条款检查项：资质/抽查/申投诉/事故/法规/访谈） |
| `AttrCode` | varchar(50) NULL | 这条证据服务哪条属性 |
| `SourceType` | varchar(20) | `file`/`record`/`onsite`/`interview`/`extract` |
| `SourceRef` | varchar(200) | 文件 ID / 记录 ID / 访谈对象 |
| `AnchorText` | text | **锚点原文**（四要素定位：时间·地点·人物·数值） |
| `Finding` | text | 观察到什么（只描述事实，不下结论） |
| `Confidence` | decimal(3,2) | 可信度 |
| `CollectedBy` / `CollectedAt` | | 采集人与时间 |

**唯一约束**：`(EnterpriseCode, SessionCode, SourceType, SourceRef, ClauseCode)` —— 同一份文件不能对同一条款重复记两条。

### 6.2 判定结果 `cert_check_result`（预 NC / 结论）

| 字段 | 类型 | 说明 |
|---|---|---|
| `EnterpriseCode` / `SessionCode` / `StandardCode` / `ClauseCode` | | 定位 |
| `Verdict` | varchar(20) | `conform`/`nc`/`observation`/`na`/`pending` |
| `Severity` | varchar(20) | `major`/`minor`/`none`；**只在 `Verdict=nc` 时强制** |
| `RequirementRef` | varchar(50) | 分项引用（`a)`/`b)`），NC 精确到分项 |
| `Reason` | text | 结论理由，**必须从证据长出** |
| `EvidenceCodes` | json | 引用的证据码数组 |
| `EngineType` | varchar(20) | `rule`/`llm`/`hybrid` |
| `Status` | varchar(20) | `draft`（预 NC）/`confirmed`（审核员确认） |

### 6.3 NC 的三个前置（缺一条都不能开）

| 前置 | 读哪 | 判据 |
|---|---|---|
| **适用** | L2 `Applicability` 的 `runtime` 求值 | `ValueState=na` ⇒ 直接停 |
| **强制** | L1 `Obligation` | `≠ shall` ⇒ 只能出观察项，不能开 NC |
| **证据完备** | L2 `ValueState` | `unknown`/`partial` ⇒ 不能开 NC |

### 6.4 法律红线

> **只有「生成没发生过的事实」是红线。**
> 判定结论若含「时间·地点·人物·数值」四要素，**必须有原始证据锚点**，否则不得生成。
> 因此判定必须是 **规则 + 大模型双引擎**：规则定骨架（适用/强制/完备），模型只做语义比对与措辞。**禁止纯大模型下判定。**

## 七、一条真实条款走完四层（7.1.5.2 测量溯源）

| 层 | 内容 |
|---|---|
| **L0** | 池子里有 9 条通用属性 + `CalibrationCycle`（校准周期，`family` 层） |
| **L1** | `Obligation=shall`、`Applicability=有条件`、`ApplicabilityCondition=当要求测量溯源时`、`RequirementItems=[a,b,c]`、`EvidenceKinds=[record,site]`、`CheckModes=[全不全,时间]`、`Severity=严重`、`Artifacts=[{设备台账,必须},{校准证书,必须}]` |
| **L2** | `Applicability` 求值 → `found`（企业有测量设备）；`Artifacts` 实际 → `partial`（台账有 12 台，校准证书缺 3 台） |
| **L3** | 证据：台账文件 + 3 张缺失清单；判定 `Verdict=nc`、`Severity=major`、`RequirementRef=a)`、`Reason` 引用台账与证书缺口；`Status=draft`（预 NC） |

对照 **7.3 意识**：`Artifacts` 为空（不要求成文信息）、`EvidenceKinds=[人]` ⇒ L2 不去文件池，转访谈。**硬去文件池搜必然搜不到，然后误判"企业没做"** —— 这就是属性层存在的意义。

## 九、与既有表的边界（裁决 22 号留下的三个矛盾）

22 号指出库里有**三个平行体系**都在表达"标准要求"，必须裁决，否则新表一定和旧表打架：

### 9.1 「怎么判」：`cert_validation_rule` vs `CheckModes`

| 载体 | 粒度 | 保留？ |
|---|---|:--:|
| `cert_validation_rule`（2 行，`RuleJson`/`JudgeMode`/`SeverityIfViolated`/`NcDescriptionTemplate`） | **细**：具体阈值与模板 | ✅ **判定执行只读它** |
| `CheckModes` 属性 | **粗**：有没有/全不全/对不对/时间/一致/可追溯 | ✅ 保留，但**只用于选引擎与生成任务，不产出结论** |

> **裁决**：不是二选一，是两层。`CheckModes` 说"这条款该用哪组 case"，`cert_validation_rule` 说"这组 case 的具体参数"。**执行时信后者。**

### 9.2 「要哪些文件」：文件体系 vs `Artifacts`

| 载体 | 表达 | 保留？ |
|---|---|:--:|
| `cert_standard_directory_config/_folder/_file`（93 个文件节点） | **具体文件节点**（这套目录清单里是哪一份） | ✅ |
| `Artifacts` 属性 | **材料类型**（这条款要"校准证书"这类东西） | ✅ 保留，但**存字典码 `ArtifactType`，不存自由文本** |

> **裁决**：`Artifacts` = 类型（跨企业复用，用于匹配召回）；目录清单 = 实例（用于生成上传清单）。两者靠 `ArtifactType` 对齐，**不互相抄**。
> **待建关联**：`cert_clause_file`（条款 ↔ 目录文件节点）仍是断点，属独立议题（22 号 D-K2）。

### 9.3 「怎么认出这份文件」：`cert_standard_doc_contract` vs `MatchPrompt`

> **裁决**：匹配契约**跟文件走**（`cert_standard_doc_contract.MatchPrompt`/`Keywords`/阈值）。**属性池不放 `MatchPrompt`。**
> 理由：匹配的对象是文件，不是条款。条款侧只需说"我要这类文件"。

### 9.4 复用与不动

| 表 | 处置 |
|---|---|
| `cert_iso_standard`(5) / `cert_iso_clause`(273) | **不动**，L0/L1 都挂它 |
| `cert_validation_rule` | **不动**，§9.1 定为判定执行唯一来源 |
| `cert_standard_directory_*` / `cert_standard_doc_contract` | **不动**，§9.2/§9.3 定为文件侧唯一来源 |
| `cert_enterprise` / `cert_enterprise_original_file` / `_doc_profile` | **不动**，L2 通过 `EnterpriseCode` 关联 |
| `cert_standard_directory_file` | **一表两义**（要求 + 实例状态），建议分期拆出实例状态表（22 号 D-K4） |

## 十三、坑（全部踩过或差点踩）

1. **`SessionCode` 用 NULL** ⇒ 唯一键不去重，同一键能插多行，值表悄悄变多值。**必须 `NOT NULL DEFAULT ''`**。
2. **给属性池加"适用条款"列** ⇒ 出现"池子说适用、L1 没配"的双真相。**挑哪几条只能靠有没有行。**
3. **`fixed` 类属性也写进 L2** ⇒ 每企业凭空多 7×201 行死数据，且标准换版后与企业值打架。**L2 只收 `expected`/`runtime`。**
4. **把"不适用"当标准级属性值** ⇒ 条款对某企业不适用是**求值结果**，属 L2。写进 L1 就等于把企业事实钉进标准库。
5. **`unknown` 直接开 NC** ⇒ 系统性冤枉企业，法律与商业双重风险。
6. **`CheckModes` 和 `cert_validation_rule` 同时当判定依据** ⇒ 引擎每次要决定信谁，两边都不报错。**只信后者。**
7. **`Artifacts` 存自由文本** ⇒ 与目录清单对不上，匹配召回全靠猜。**存字典码。**
8. **L0 停用属性用删除** ⇒ 历史 L1/L2 值成孤儿。**用 `IsValid=0`。**
