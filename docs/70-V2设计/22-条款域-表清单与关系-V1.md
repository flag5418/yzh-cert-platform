# 条款域：表清单与关系（先定表，再定字段）

> **版本**：V1 ｜ **日期**：2026-10-28 ｜ **状态**：待裁决（D-K1…D-K6）
> **做法**：本文只回答「应该有哪些表、谁连谁、各自管什么」，**不设计字段**。表定了再谈字段。
> **依据**：`yzh_cert_platform` 现有 89 张基表实测（行数为 `information_schema` 估算值）。

---

## 一、一句话结论

现有系统有 7 层，**条款只连上了标准层和判定层，文件层与计划层是断的**：

| 层 | 现状 | 和条款有没有边 |
|---|---|---|
| 标准层 | 有（标准 5 条、条款 273 条、阶段 14 条） | — |
| 条款判定规则 | 有（`cert_validation_rule`，2 行） | ✅ 有 `ClauseCode` |
| **条款语义** | **无**（强制程度、适用范围、证据形态、过程域…无处安放） | ❌ |
| 文件要求 | 有（`cert_file_requirement` 0 行 / `directory_*` 5+5+93 行） | ❌ **全表无 `ClauseCode`** |
| 文件契约（怎么匹配） | 有（`cert_standard_doc_contract` 7 行） | ❌ 只挂 `StandardFileCode` |
| 审核计划 | **无**（只有 `cert_expert_task`，那是任务不是计划） | ❌ |
| 企业实际值 | 半个（散在 `directory_file` 的 `MatchState`/`UploadStatus` 里） | ❌ |

所以之前那套「18 个属性表」的真正问题不是字段多，而是**它想同时补上第三层和第四层，却和已有的第四层（文件体系）没有一条边相连**。两份数据各说各话，必然分叉。

## 三、关系图

```
L1 标准层
  cert_iso_standard ──1:N──> cert_iso_clause ──1:N──> cert_validation_rule   ✅ 已连
        │                          │
        │                          └──── ? ────> 【缺】条款语义
        │
        ├──1:N──> cert_file_requirement          ✗ 无 ClauseCode
        ├──1:N──> cert_standard_doc_contract     ✗ 挂 StandardFileCode
        └──1:N──> cert_standard_directory_config
                        └─1:N─> _folder ─1:N─> _file   ✗ 无 ClauseCode
                                                 │
                                                 └──> cert_standard_doc_contract (ContractCode)

L5 计划层（全缺）
  【缺】cert_audit_plan
            └─1:N─> 【缺】cert_audit_plan_clause ── 引用 cert_iso_clause + 部门 + 审核员
                        └─1:N─> 【缺】cert_audit_plan_task（要采集的证据）

L4/L7 企业实际值
  cert_enterprise ──> cert_enterprise_original_file ──> cert_enterprise_doc_profile（画像/匹配）
  cert_standard_directory_file ──(EnterpriseCode, TaskId)──> 实例状态（MatchState / UploadStatus）
```

**断点只有三处**：条款→语义、条款→文件、标准→计划。补这三处就够，不需要重做任何现有表。

## 四、三个平行体系必须裁决（否则新表一定和旧表打架）

### 4.1 「这条款怎么判」由谁表达？

| 方案 | 载体 | 现状 |
|---|---|---|
| A | `cert_validation_rule`（规则行，`RuleJson` + `JudgeMode`） | **已有**，2 行 |
| B | 条款属性（`CheckModes` / `Criteria` / `Severity`） | 我上一版设计 |

两者都在说"怎么判"。同时存在 ⇒ 判定引擎每次要决定信谁，而两边都不报错。
**建议**：判定规则**只认 `cert_validation_rule`**；属性表里不再放 `CheckModes`/`Criteria`/`Severity`。

### 4.2 「这条款要哪些文件」由谁表达？

| 方案 | 载体 | 现状 |
|---|---|---|
| A | `cert_file_requirement` + `directory_file`（按目录组织） | **已有**，但**不挂条款** |
| B | 条款属性 `Artifacts`（按条款组织） | 我上一版设计 |

**建议**：文件仍然只存在文件体系里（一套文件只能维护一份，挂两处必分叉）；补一条**关联表**把条款和文件连起来。这也是"条款→文件"这个断点的正解，而不是在属性里再抄一份文件清单。

### 4.3 「怎么匹配这份文件」由谁表达？

| 方案 | 载体 | 现状 |
|---|---|---|
| A | `cert_standard_doc_contract.MatchPrompt` / `Keywords` / `FingerprintJson` | **已有**，7 行 |
| B | 条款属性 `MatchPrompt` / `MatchAnchors` / `ImplementationVariants` | 我上一版设计 |

**建议**：匹配契约跟着**文件**走（A）。因为匹配的对象是文件，不是条款。条款侧只需说"我要这类文件"，具体怎么认出它属于哪类，是文件契约的事。

## 五、建议的目标表集

### 新增（4 张）

| 表 | 层 | 职责 | 为什么必须新增 |

## 六、各层只回答一个问题

| 层 | 唯一的问题 | 不回答 |
|---|---|---|
| 标准层 | 标准长什么样 | 任何企业的事 |
| 条款属性 | 这条款**语义上**在要求什么 | 要哪些文件、怎么判 |
| 文件体系 | 标准要**哪些文件**、怎么认出它 | 这条款为什么需要它 |
| 判定规则 | **怎么判**、判错多严重 | 证据在哪 |
| 计划层 | **这次**查哪些、谁查、什么时候 | 企业有没有 |
| 企业值层 | 这家企业**实际**有没有、可不可信 | 标准要求什么 |

> 判据：**任何一张表，如果它的行既描述"标准要求"又描述"某企业实际"，它就该拆。** `cert_standard_directory_file` 现在正是这样。
