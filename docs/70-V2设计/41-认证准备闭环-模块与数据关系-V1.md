## 一、两个层次

| 层次 | 实体 | 是什么 |
|---|---|---|
| **业务层** | **检查项** | **计划的一项** = 条款(1..N) × 部门(1..N)。**部门在编计划时由人定死**，准备阶段不改、不猜 |
| **语义层** | **条款** | 检查项内的输入维度：每个条款各取自己的文档证据与公开查询结果，供模型逐个判、再合判 |

```
检查项（计划明细一行）
   ├─ 条款 × N（每个条款：标准名 + 编号 + 9 属性 + 该条款的文档证据 + 公开查询证据）
   ├─ 部门（来自计划，原样使用）
   ├─ 证据（文档 / 公共查询 / 人工补充 + 附件）
   ├─ 疑点（挂条款，可多条）
   └─ 结论：state / 是否必须执行 / 是否开 NC / 验证程度 / 人员最终判定
```

**关键**：同一条款分给两个部门查 = 计划里两条明细 = **两个检查项**。因为证据链、入场计划都不是一个东西。

## 二、一个检查项怎么跑（5 步，无批次）

| 步 | 动作 | 落点 |
|:--:|---|---|
| ① | 选计划 → 门禁 5 项（计划唯一 / 有条款 / 部门 / 联系人 / 属性覆盖 / 有 L1 产物）| `cert_prep_check.GuardJson` |
| ② | **检查项展开**：计划明细 → 检查项行，**自动编号 + 自动命名** | `cert_prep_check` |
| ③ | **条款维度登记**：`Clauses[]` → N 行（部门组 > 1 时按 条款×部门）| `cert_prep_check_clause` |
| ④ | **证据收集**：按条款 `FIND_IN_SET` 取文档切片；已勾的公共查询结果；人工线索 | `cert_prep_evidence` |
| ⑤ | **闸门 → 一次分析**（一检查项一调用）| 结论回写 `cert_prep_check` + 逐条款片段 + 疑点 |

**没有"批次"怎么跑全量**：检查项状态本身就是队列 —— `SELECT ... WHERE Status='pending'` 逐条跑，进度 = `COUNT(*) GROUP BY Status`。重跑 = 把状态改回 `pending`。**少一层表，少一套状态机。**

## 三、数据模型（4 + 3 张）

> 全表：`Code` varchar(36) 主键（⛔ 不用 Id 关联）、`IsValid`、`IsDeleted`、审计列、`COLLATE=utf8mb4_general_ci`、排序列 `Sort`。

### 3.1 `cert_prep_check`（★ 检查项 = 证据 / 结论 / 入场计划的唯一载体）

**身份与快照**

| 字段 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) | 内部主键（界面不显示） |
| **`CheckNo`** | varchar(10) | **展示序号**，按明细 `Sort` 自动生成，生成后**固化**（口头沟通"第 2 项"不漂） |
| `CheckName` | varchar(300) | **自动只读标题**：`02 文件控制（4.2.4/4.2.5）｜品质部` |
| `MergeNote` | varchar(1000) | 合并说明（**系统自动拼**，进提示词，⛔ 不让人填） |
| `EnterpriseCode` / `PlanCode` / `DetailCode` | varchar | 企业 / 计划 / 计划明细 |
| `ClauseCodes` / `ClauseNumbers` | varchar | 条款快照（可**跨标准**） |
| `DeptCodes` / `DeptNames` | varchar | **部门快照（来自计划，原样用，不猜）** |
| `ClauseTotal` / `ClausePass` | int | 条款数 / 通过数 |

**结果（你列的 8 列）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `State` | varchar(20) | `found` / `partial` / `missing` / `unknown` / `na`（**资料完备性**，不是 NC 结论）|
| `GapSummary` | text | 判定理由（**必填**）|
| **`IsMandatory`** | tinyint | **是否必须执行**（默认：有疑点 或 `Severity=critical` ⇒ 1；可改）|
| **`NcSuggested`** | varchar(20) | **是否需要开 NC**（AI 建议）：`yes` / `no` / `uncertain` + `NcReason` |
| **`Conclusion`** | varchar(20) | **人员最终判定（三档，实测口径）**：`pass` 符合 / **`ofi` 观察项** / **`nc` 不符合** / `na` 不适用（空 = 未审）。⚠️ 不能只有 pass/fail：真实检查记录里 OFI 是独立一档（见 42 号 §一）|
| `ConclusionBy` / `ConclusionAt` | | 谁判的、何时（留痕）|
| **`VerifyLevel`** | varchar(20) | **验证程度**：`doc` 资料核对 / `remote` 远程沟通 / `onsite` 现场 / `test` 实测抽样（AI 建议，可改）|
| `Severity` / `SeveritySource` | varchar | **检查项级统一严重程度**（取条款基线 max，标 `merge`；条款级不存 severity）|
| `MissingKindsJson` / `ConflictsJson` | json | 缺的材料类型 / 跨文档矛盾 |
| `PointCount` | int | 疑点数 |
| `EvidenceCount` | int | 证据条数（文档 + 查询 + 人工）|
| `Remark` | text | **审核员备注** |
| `ManualEvidenceJson` | json | **其他证据**（人工填写：类型 + 说明 + 附件路径数组）|
| `InputHash` / `InputSnapshotJson` | | 装配包指纹 + 快照（回放用）|
| `ModelName` / `PromptVersion` / `AnalyzedAt` / `AnalysisCount` | | 模型与版本、分析次数 |
| `Status` | varchar(20) | `pending` / `collecting` / `analyzing` / `analyzed` / `reviewed` / `stale` |
| **唯一键** | | `(EnterpriseCode, DetailCode)`（未删时唯一）|

### 3.2 `cert_prep_check_clause`（条款维度 · 子表，不是任务）

| 字段 | 说明 |
|---|---|
| `Code` / `CheckCode` / `ClauseCode` / `ClauseNumber` | 唯一键 `CheckCode + ClauseCode + DeptCode` |
| `StandardCode` / `StandardName` | **标准跟着条款走**（一个检查项可跨标准）|
| `DeptCode` / `DeptName` | 可空：部门组 > 1 时按 (条款×部门) 登记 |
| `SliceCount` / `PqCount` / `LeadCount` | 该条款的证据条数 |
| `EvidenceState` | `collecting` / `ready` / `insufficient` |
| **`ClauseState`** | 模型给的逐条款结果 `found`/`partial`/`missing`/`unknown` |
| `ClauseReason` / `MissingKindsJson` | 逐条款理由（解释"为什么 partial"）|

> 「2 个条款通过、1 个不通过」就落在这一张：3 行，`ClauseState` 分别是 found/found/partial ⇒ 检查项 `State=partial`，疑点挂在那一行。

### 3.3 `cert_prep_evidence`（证据 · 挂检查项）

| 字段 | 说明 |
|---|---|
| `Code` / `CheckCode` / `ClauseCode` | 挂检查项 + 溯源条款（可空 = 检查项级/企业级）|
| `DeptCode` | 可空（同条款多部门时必填）|
| `EvidenceKind` | `doc_slice` / `pq_result` / `lead` / **`manual`**（人工补充）|
| `SourceCode` / `SourceName` | `FileCode` / `PqResultCode` / 空 |
| `Anchor` / `Snippet` / `Confidence` | 锚点 / 摘录 / 置信度（人工 = 1）|
| `AttachmentsJson` | **附件路径数组（图片/PDF）** —— 人工证据用 |
| `Remark` | 人工说明 |
| `Status` | `collected` / `confirmed` / `dropped`（**dropped 不进分析输入**）|
| `Origin` | `ai`（切片）/ `pq` / `manual` |

### 3.4 `cert_prep_point`（疑点）

| 字段 | 说明 |
|---|---|
| `Code` / `CheckCode` / `ClauseCode` | 归属检查项 + 条款 |
| `DeptCode` | 检查项部门组 > 1 时必填 |
| `PointKind` | `communicate` 沟通 / `observe` 观察 / `interview` 访谈 / `verify` 核验 |
| `Mode` | `remote` / `onsite` |
| `Reason` / `Action` / `Question` / `TargetRole` / `EstMinutes` / `Priority` | 依据 / 看什么 / 问什么 / 对谁 / 多久 / 优先级 |
| `Origin` | `ai` / `manual` / `pq` |
| `Fingerprint` | `hash(ClauseCode + PointKind + Action)` → 重跑幂等 |
| `Status` | `open` / `resolved` / `dropped` + 理由 + 留痕 |

### 3.5 公共查询三表（独立模块，沿用 §五 的设计）

`cert_pq_skill`（查什么）/ **`cert_pq_task`（一次查询 = 一个任务，可导入多行参数）** / `cert_pq_result`（每行结果）。

**与检查项的关系**：`cert_pq_task.CheckCode` 可空（可独立用）；结果生成 `cert_prep_evidence`（`kind=pq_result`）。

## 四、LLM：一个检查项一次调用

### 4.1 输入

| 块 | 内容 |
|---|---|
| ① 规则 | 只判资料完备性与一致性；五条硬规则 |
| ② 检查项 | `CheckName` / `MergeNote`（系统生成）/ 部门名 / 条款清单 |
| ③ **按条款分组** | 每块：**标准名** + 编号 + 标题 + `ClauseIntent` + `Obligation` + `Artifacts` + `EvidenceChain` + `DocCheckMode` + `Severity` + `Process` + **该条款命中的事实与锚点** + 查询摘要（部门组 > 1 时按 条款×部门 分块）|

### 4.2 输出（对应检查项的结果列）

```json
{
  "state": "found|partial|missing|unknown|na",
  "gapSummary": "……",
  "severity": "major",
  "isMandatory": true,
  "ncSuggested": "yes|no|uncertain",
  "ncReason": "……",
  "verifyLevel": "doc|remote|onsite|test",
  "missingKinds": ["record"],
  "conflicts": [{"theme":"保存期限","aFile":"A.doc","bFile":"B.doc","aSays":"5年","bSays":"3年"}],
  "findings": [
    {"clauseNumber":"4.2.4","deptCode":"…","clauseState":"found","reason":"…"},
    {"clauseNumber":"4.2.5","deptCode":"…","clauseState":"partial","reason":"未见 12 个月内记录实物"}
  ],
  "points": [{"clauseNumber":"4.2.5","kind":"interview","mode":"remote","reason":"…","action":"…","question":"…","targetRole":"文件管理员","estMinutes":20,"priority":"high"}]
}
```

**校验**：`findings[]` 必须覆盖每个 (条款 × 部门) 维度；`severity` 不得高于条款基线；`ncSuggested` 与 `state` 不得矛盾（`found` 却说要开 NC ⇒ 判失败）。

### 4.3 属性分工（与第 3 版一致，删掉"部门"一条）

| 属性 | 进哪 | 用途 |
|---|:--:|---|
| `DocCheckMode` | **程序闸门** | `required`+零证据 ⇒ `insufficient` 不调模型；`none` ⇒ 只出观察/访谈 |
| `Artifacts` | 提示词 + **词表** | 限制 `missingKinds` 取值 |
| `Severity` | 提示词 + **上限** | 输出不得高于基线 |
| `Obligation` | **程序** | ≠`shall` ⇒ 最高 `observation` |
| `Applicability` | **程序** | `conditional` ⇒ 先判适用；`na` ⇒ 不跑 |
| `ApplicabilityCondition` / `ClauseIntent` | 提示词 | 适用条件原文 / 语义对齐 |
| `EvidenceChain` | 提示词 | 疑点动作素材（⛔ 只给审核员）|
| `Process` | **提示词**（降级） | 帮模型理解该条款涉及哪些过程；**不再驱动部门** |

## 五、结果表长什么样（你列的 8 列 → 字段）

| 你说的列 | 字段 | 谁写 |
|---|---|---|
| 检查项 code | `Code` + `CheckNo` + `CheckName` | 系统 |
| **检查证据**（多条款证据集合）| `cert_prep_evidence` 多行（`EvidenceCount` 计总数）| 系统收集 + 人工补 |
| **是否必须执行** | `IsMandatory` | AI 建议 → 人可改 |
| **是否需要开具 NC** | `NcSuggested` + `NcReason` | AI 建议 |
| **验证程度** | `VerifyLevel` | AI 建议 → 人可改 |
| **疑点** | `cert_prep_point` 多行 | AI + 人工 |
| **相关部门** | `DeptCodes/DeptNames` | **来自计划** |
| **其他证据**（人工填）| `ManualEvidenceJson` + evidence(`kind=manual`) + `AttachmentsJson` | **审核员** |
| 备注 | `Remark` | 审核员 |
| **NC / 合格与否（可改）** | `Conclusion` = `pass`/`fail`/`na` | **审核员**（`ConclusionBy/At` 留痕）|

> 注意区分：`NcSuggested` 是**系统建议**，`Conclusion` 是**人的最终判定**。系统永不自动开 NC（26 号红线）。

## 六、入场计划怎么来（一条查询 + 一次分组）

```
① 过滤：Conclusion <> 'pass'  并且 (IsMandatory = 1 或 PointCount > 0 或 NcSuggested = 'yes')
② 按 DeptCodes 分组 → 每个部门一个"部门块"，块内按 CheckNo 排序
③ 每块合计 estMinutes（疑点的预计耗时之和）→ 建议时段数（半天 = 240 分钟）
④ 用户只填：日期 / 上午下午 / 谁去（组长、组员）
⑤ 生成 cert_onsite_plan + _slot（slot 挂 CheckCode）
```

| 项 | 说明 |
|---|---|
| 排除合格 | `Conclusion='pass'` 的不进计划（这就是"合格的不占时间"）|
| 按部门整理 | 部门来自计划快照，天然就是排班维度 |
| 用户填什么 | **只填时间与人**；检查内容、疑点、时长全部来自准备结果 |
| 下来的数据 | 一个检查项的疑点 → 现场做什么（`point.Action`）+ 问谁（`TargetRole`）+ 讲多久（`EstMinutes`）|

> 这正是你要的"完整入场计划"：**准备表一过滤一分组，内容自动成形；人只补时间与人选。**

## 七、零操作原则 + 三个页面

> **审核员只在"不同意"时才动手。**

| # | 原则 |
|:--:|---|
| Z1 | 零输入可启动（选计划 → 开始）|
| Z2 | `CheckNo` / `CheckName` / `MergeNote` 全自动，⛔ 无手填字段 |
| Z3 | 审核页默认只显示 `partial`/`missing`/`unknown` + 有疑点的；`found` 折叠 |
| Z4 | 批量：一击「确认全部 found」、一击「采纳全部疑点」|
| Z5 | 人工只补三样：**其他证据（可传图）/ 备注 / 合格与否** |

**正常路径 3 次点击**：开始 → 批量确认 → 提交审核。

| 页面 | 端 | 主角 |
|---|---|---|
| `/readiness` 认证准备 | auditor | **检查项清单**（`CheckNo` / 名称 / 条款数 / 部门 / 证据进度 / 状态）→ 展开条款与证据；勾公共查询；启动分析 |
| `/readiness-review` 结果审核 | auditor | 检查项结果（§五 那 8 列）→ 补其他证据（可传图）/ 备注 / 判合格与否 |
| `/pq` 公共查询 | auditor | Skill → 建任务 → 导入参数 → 看行结果 |
| `/cert/prompt-center` 提示词中心（admin）| admin | 分类 / 变量校验 / dry-run / 归档 |

## 九、待裁决

| # | 事项 | 建议 |
|:--:|---|---|
| **Q1** | `IsMandatory` 默认值怎么定 | 有疑点 或 `Severity=critical` ⇒ 1；其余 0。AI 可建议改，人可覆盖 |
| **Q2** | `VerifyLevel` 与 `PointKind` 是否重复 | 不重复：`VerifyLevel` 是**检查项整体验到什么程度**（排班用）；`PointKind` 是**单个疑点怎么做**（现场用）|
| **Q3** | 一个检查项条款 > 6 怎么办 | 分两批调用 + 一次综合（共 3 次），上限 8 |
| **Q4** | 公共查询 P0 用 `manual` 还是 `api` | 先 `manual`（人工查、人工录、留痕），`api` 后补 |
| **Q5** | 前置校验（部门/联系人）放哪 | `ClauseCodes` 空、`DetailCode` 空的企业级检查项，同表同状态机 |
