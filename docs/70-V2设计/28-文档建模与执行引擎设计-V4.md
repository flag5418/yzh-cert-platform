# 文档建模与提示词资产（V4）

> **版本**：V4 ｜ **日期**：2026-10-28 ｜ **状态**：待裁决
>
> **定位（改了三版才定准）**：本文写的是**规则侧**——国标定义了哪些文档、文档该含什么、作用是什么，以及**文档模型**的提取契约。**不写企业侧**（企业上传、提取执行、取证、NC）。企业侧的"准备检查 / 体系检查"两个模型见 [`29-认证准备与体系检查模型-V1.md`](./29-认证准备与体系检查模型-V1.md)。
>
> **四个模型的位置**：条款模型（25 号）· **文档模型（本文）** · 准备检查模型（29 号）· 体系检查模型（29 号）。
>
> **V1–V3 错在哪（三句话）**：
> 1. 把**企业侧执行**写成了规则侧设计：整篇在讲"200 份文件怎么跑 LLM"，那是执行，不是规则。
> 2. V2 把多个标准合并成一份 `standardView`，违背"一个标准一套"。
> 3. V3 方向改对了（每标准独立），但仍留在企业侧，且另开两张表，与既有实现重复。
>
> **与 25 号的关系**：25 号定层、定界、定红线；本文定**文档规则**和**文档提取契约**。冲突时以 25 号为准。

## 零、一句话说清本文范围

```
规则侧（本文）：
  国标条文  →  文档要求（该有哪些文档、该含什么、作用、服务哪些条款）
            →  每标准一套文档提取提示词（规则资产，供企业侧调用）
            →  文档提取契约（单文档事实 + 候选条款 + 证据强度）

企业侧（见 29 号）：
  企业上传 → 跑提取 → 准备检查（齐全性/一致性/疑点/部门/入场计划/预NC）
          → 现场取证 → 条款判断 → 正式 NC → 报告
```

**五个提示词家族的分工**：`clause_attr`（条款属性预生成，25 号）· `doc_extract`（本文）· `readiness`（准备检查，29 号）· `clause_judge`（条款判断，29 号）· `evidence_style`（机构证据，29 号）。

**为什么要先有"文档要求"这一层**：没有它，企业侧只能"看到什么算什么"，永远回答不了"这份文档该有什么、缺了什么"。国标已经把这件事写清楚了，我们要做的是把它翻成受控字段。

## 一、国标里的文档：三类，性质不同

| 类别 | 例 | 国标怎么表述 | 提取时问什么 |
|---|---|---|---|
| **规则性文档** | 质量手册、程序文件、作业指导书、工艺卡、检验规程 | "组织应建立/保持…形成文件的信息" | 写了什么要求（规定层面） |
| **内审文档** | 内审方案、内审报告、不符合项报告、纠正措施单、管理评审记录 | "应策划并实施…保留成文信息" | 执行得怎么样（执行层面） |
| **记录** | 培训记录、设备台账、校准证书、检验记录、供方评价记录 | "应保留…作为证据" | 有没有、全不全、过没过期 |

> 三类混在一起提取，字段必然互相污染：规则性文档要"要素齐不齐"，记录要"数据全不全、时间覆盖够不够"。所以**文档要求按类别分别定义**。

## 二、标准侧文档要求（本文核心表）

### 2.1 这张表回答什么

**这个标准下，应该有哪些文档；每份文档该含什么；它的作用是什么；它服务哪些条款。**

它**不回答**"这家企业交了没有"——那是企业侧。

### 2.2 字段

| 字段 | 说明 | 例 |
|---|---|---|
| `Code` | 业务键 | `REQ-9001-8.3-01` |
| `StandardCode` | 标准 GUID（与条款同口径） | `c9d3e1f5-…` |
| `StageCode` | 阶段（可空 = 全阶段通用） | 一阶段 / 二阶段 |
| `DocTypeCode` | 受控文档类型：手册 / 程序文件 / 制度 / 计划 / 记录 / 报告 / 证书 / 台账 | 程序文件 |
| `DocName` | 文档名（标准级叫法，不是企业文件名） | 设计开发控制程序 |
| `DocPurpose` | **作用**（这份文档在体系里干什么） | 规定设计输入/输出/评审/验证/确认的控制要求 |
| `RequiredElements` | **应含要素**（结构化清单，受控要素码 + 中文名） | 设计输入清单、评审记录、验证方式、确认方式、变更控制 |
| `ServesClauses` | 服务哪些条款号（可多个） | `["8.3.2","8.3.3","8.3.4","8.3.5"]` |
| `IsMandatory` | 是否强制（国标"应"=强制，"宜"=非强制） | true |
| `BasisText` | 国标依据原文（一句，可核对） | "8.3.2 组织应确定…设计输入…" |
| `MatchHint` | 语义匹配提示：别名/常见叫法（**不靠文件名**） | 设计开发程序、设计控制程序、APQP |
| `ExtractPromptType` | 用哪套提取提示词（按标准） | `doc_extract` |
| `Sort` / `IsValid` | 排序 / 停用不删 | |

### 2.3 例子：7.1.5.2 测量溯源

| 项 | 值 |
|---|---|
| 文档要求 1 | 计量器具台账（`记录`，强制） |
| 应含要素 | 设备编号、名称、型号、校准日期、校准机构、有效期 |
| 作用 | 证明在用的测量设备可追溯 |
| 服务条款 | 7.1.5.2 |
| 国标依据 | "当要求测量溯源时…应…保留成文信息作为证据" |

> 这份"要求"是**标准级**的：所有企业都应具备。企业台账里是 12 台还是 100 台、过期与否，是企业侧的事。

### 2.4 与机构资料清单的关系（三层，不许混）

| 层 | 内容 | 有无机构 | 现有载体 |
|---|---|---|---|
| **标准要求（本文）** | 该标准下应有哪些文档、该含什么 | 无 | 新表 |
| **机构资料清单** | 这家机构按标准×阶段整理出的具体文件清单（含模板、编号） | 有 | 现有资料清单与提取规则 |
| **企业上传** | 这家企业实际交了什么 | 有企业 | 企业侧（另立） |

**关系**：标准要求是"抽象"，机构资料清单是"实例化"，企业上传是"执行"。所以：
- 标准要求表**没有** `OrgCode`；
- 机构资料清单可以有，且它才是"168 份文件"那种粒度；
- 两层通过 `DocTypeCode` + `ServesClauses` 对齐，**不互抄**。

> 这也是 V3 那个"一标准一份提示词"和既有"一文件模板一份提示词"看起来冲突的原因：它们不在同一层。本文说的是抽象层，既有的是实例层。

## 三、每标准一套文档提取提示词

### 3.1 为什么按标准分开

- 术语按标准分册：`成文信息` 集中在 9001，`记录` 集中在 13485，24001/45001 多说"文件"。
- 义务动词分布不同：`必须` 只在 45001/24001，9001 一次不用。
- 条款粒度不同：13485 有四级条款，9001 只到三级。
- 换版只换一本：9001 换版时另外几个标准的配置与结果不动。

反面教训：以前用一条平台级提示词跑 4 个标准，结果是 `约束强度` 恒等于"应"、`过程` 恒等于"管理"——连没有义务动词的"1 范围"也判成"应"。根因就是一条提示词要同时覆盖四本书，只能给最通用的答案。

### 3.2 提示词里放什么

| 变量 | 来源 | 说明 |
|---|---|---|
| `standard` | 规则侧 | 标准名 + 版本 + 术语表（该标准专用） |
| `docRequirement` | 规则侧 | 本次命中的文档要求（类型 / 应含要素 / 作用 / 服务条款） |
| `documentMarkdown` | 企业侧 | 文档转写后的 Markdown 全文 |
| `priorContext` | 企业侧（可选） | 同企业同类文档的已知信息，用于判定"是否重复/是否补充" |

### 3.3 输出契约（固定）

> 这一版以 13485 的通用提取提示词为基准改写，并按"通用字段 + 条款级关键信息"两层重组。
> 原提示词是"一条提示词跑全部条款 + 全部字段"，实际会漏项与截断，因此改为**两跳**：
> **第一跳**提通用字段与候选条款；**第二跳**只对候选条款补条款级关键信息。

```json
{
  "docMeta": {
    "docCode": "XASL-QM",
    "docName": "医疗器械质量手册",
    "docCategory": "质量手册",
    "docKind": "rule | internal_audit | record",
    "version": "A/0",
    "effectiveDate": "2025-03-01",
    "approvalStatus": "approved | unsigned | unknown",
    "isControlled": true,
    "processDept": "质量部",
    "deptSource": "enterprise | inferred",
    "sourceFileCode": "FILE-0001",
    "summary": "200 字以内：目的、核心流程、关键控制点、法规符合性"
  },
  "entities": {
    "keyPersons":  [{ "name": "…", "role": "批准人", "clauseNumber": "4.2.2" }],
    "keyDates":    [{ "date": "2025-03-01", "event": "实施日期", "clauseNumber": "4.2.4" }],
    "keyProducts": [{ "product": "…", "specification": "…", "clauseNumber": "4.2.3" }],
    "keyMeasures": [{ "measure": "灭菌确认", "frequency": "每年", "clauseNumber": "7.5.7" }]
  },
  "tables": [
    { "title": "计量器具台账",
      "rows": [{ "设备编号": "…", "校准日期": "2025-01-10", "有效期至": "2026-01-09" }],
      "anchor": "第 3 章 表 3-1" }
  ],
  "clauseFacts": [
    { "clauseNumber": "7.5.7",
      "related": true,
      "evidenceLevel": "direct | indirect | mention_only",
      "keyFacts": { "灭菌方式": "环氧乙烷", "再确认频次": "每年" },
      "evidence": "文档第 5 章规定灭菌确认每年一次…",
      "anchor": "第 5 章 §5.6",
      "confidence": 0.86 }
  ],
  "coverage": {
    "checked": ["4.1", "4.2.1", "7.5.7"],
    "notRelated": ["7.3", "7.5.9.2"]
  },
  "extraction": { "promptCode": "…", "promptVersion": 3, "model": "…", "confidence": 0.82 }
}
```

**两层字段，用途不同**：

| 层 | 字段 | 用途 |
|---|---|---|
| **通用字段** | `docMeta` + `entities` + `tables` | 快速找回原始文档、判断文档身份与有效性（4.2.4）、跨文档比对 |
| **条款级关键信息** | `clauseFacts[].keyFacts` | 组装证据链：某条款在这份文档里具体写了什么 |

> `clauseFacts` 取代原 `clauseLinks`：`keyFacts` 是该条款专属的键值对，由条款的 `RequirementItems` / `Artifacts` 决定要提什么；`evidence` 是原文证据，`anchor` 是位置。三者合起来才能构成证据链的一环。

**五条结构规则**：

| 规则 | 原因 |
|---|---|
| 只输出命中的条款（`clauseFacts`），未命中放 `coverage.notRelated` | 逼模型填满 40+ 条款就是逼它编证据 |
| 每条证据带 `anchor` | 报告与 NC 必须能引原文，无锚点不可复核 |
| `evidenceLevel` 分三级 | "写了"≠"能作为证据"，下游据此决定是否还要现场验证 |
| `docMeta` 必须有编号/类别/版本/受控/审批/来源文件 | 前两项用于找回原文档，后四项是 4.2.4 的判据 |
| `tables.rows` 用对象数组 | 扁平 `keyValues` 与 `keyFields` 对不上，下游无法消费 |

**状态只有三种，不许留空**：

| 状态 | 含义 |
|---|---|
| `found` | 有，且完整 |
| `partial` | 有，但不全（缺要素 / 过期 / 无审批） |
| `not_mentioned` | 文档里没有这一项（明确不存在，不是"没看清"） |

> 这三种状态是"缺口"能不能算出来的前提。留空或写"文档中未提及"混在值里，下游无法区分"不存在"和"漏提"。

### 3.4 对通用提取提示词的 12 处修正

通用提示词方向是对的（通用字段 + 条款专项），但有 12 处会让下游返工：

| # | 问题 | 后果 | 修正 |
|---|---|---|---|
| 1 | 一条提示词要求输出全部 40+ 条款的 `extractedInfo` | 输出超长、必漏项、字段漂移 | 改两跳：先出候选条款，再逐条补专项 |
| 2 | `applicable` 含义是"文档涉及该条款" | 与条款配置的"适用范围"同名不同意，会被误读成"该条款对企业不适用" | 改名 `related` |
| 3 | 不相关条款也出现，值为空 | 模型为凑结构编内容 | 只出现命中项 + `coverage.notRelated` |
| 4 | 缺证据强度 | 文档写了就当符合 | 加 `evidenceLevel`（direct / indirect / mention_only） |
| 5 | 缺版本、受控状态、审批状态 | 无法判 4.2.4 | 加 `docMeta.version / isControlled / approvalStatus` |
| 6 | `processDept` 由模型自由生成 | 同一部门出现"生产部/制造部/车间"三种写法，矩阵算错 | 由企业档案给候选，模型只选 + 标 `deptSource` |
| 7 | `keyDates` 只有日期，没有时间要求 | 无法判"每年一次"是否过期 | 每条日期带 `clauseNumber`，与条款的时限要求比对 |
| 8 | `tableData.keyValues` 是扁平数组 | 与 `keyFields` 无法对齐 | 改 `rows` 对象数组 |
| 9 | 全篇无锚点 | 报告写不出，NC 不可复核 | 每条证据带 `anchor`（章节/表名/页码） |
| 10 | `未明确` 与 `""` 混用 | 下游分不清"没提"与"提取失败" | 统一三态枚举，不用字符串哨兵 |
| 11 | 条款号当字符串 | 不同标准四级/三级不一致，静默零命中 | 存 `clauseNumber` 人读号 + 关联条款 `ClauseCode` |
| 12 | 单文档内部判断"够不够" | 判断标准应由条款配置与判定规则给 | 提示词只给事实，比对归准备检查模型 |

### 3.5 一条硬约束

**提示词只描述读到了什么，不判合格与否。** "要素齐不齐"由准备检查模型拿 `RequiredElements` 比对，不由提示词下结论。理由：判断标准会随法规和机构变，不能让模型自己定。

### 3.6 存放与版本

- 存 `wf_prompt_template`，`PromptType = doc_extract`，`StandardCode` 用标准 GUID。
- 每标准一份；没有专属版本时回退平台版，但**必须显式告警**（"该标准尚无专属提示词"），不许静默降级。
- 支持上传测试文档试跑；改提示词后，已提取结果按规则失效重算，不许新旧混用。

## 四、条款判断与机构证据：已移入 29 号

这两个提示词家族（`clause_judge` / `evidence_style`）属于**企业侧执行**，其完整设计（组织结构、输出契约、与判定规则的分工、机构证据包）已写在 [`29-认证准备与体系检查模型-V1.md`](./29-认证准备与体系检查模型-V1.md) 的 §一 / §二。

本文只保留一条与文档模型相关的约束：

> **文档提取的产出只能作为判断的输入，不能直接当结论。** 文档说"有台账"，`evidenceLevel` 是 `direct` 还是不相关，都要由准备检查模型比对后再交给条款判断；提词本身不下"符合/不符合"。

## 五、只定义，不执行（本文与企业侧的边界）

本文只管"规则长什么样"。下面三件事属于企业侧，本文只定契约：

1. **一企业 N 体系 = N 份提取结果**：同一份文档，9001 / 14001 / 45001 各跑一次，各存一份，各供各自条款消费。基础资料只存一份，但结论不共享。
2. **求值**：拿 `RequiredElements` 与提取出的 `elements` 比对，得出"有/无/不全/过期"。
3. **判定与 NC**：跑条款判断提示词 + 判定规则，得出预 NC；一阶段永远只出预 NC。

> 换句话说：本文定义"考卷和评分标准"，企业侧才是"考试和阅卷"。混在一起写，就会出现 V1–V3 那种"规则文档里写 200 份文件怎么跑"的错位。

## 七、落地顺序与验收

```
1  标准侧文档要求：先做 9001 的 8 章 + 7 章（覆盖规则性文档 / 内审文档 / 记录三类）
2  每标准一套提取提示词：9001 先行，用真实企业资料试跑，看 elements 状态是否可判
3  条款判断提示词：先跑 20 条高频条款（7.1.5.2 / 8.3 / 8.4 / 8.5.1 / 9.2 …）
4  机构证据生成：先做 1 家机构 + 9001，覆盖全部条款
5  其余标准按需补（14001 / 45001 / 13485）
```

验收（每条都要能拿真实资料验证）：

| # | 验收项 | 判据 |
|---|---|---|
| 1 | 文档要求覆盖率 | 9001 的 7/8 章条款，每条都能指到至少一份文档要求或明确"本条款不要成文信息" |
| 2 | 依据可核对 | 每条文档要求都有国标原文出处 |
| 3 | 提取可判 | 真实企业文档跑出来，`found/partial/not_mentioned` 三态都有值，无空 |
| 4 | 判断可回归 | 20 条高频条款的人工结论与提示词结论一致率达标，不一致的能说清原因 |
| 5 | 多标准隔离 | 同一文档在 3 个标准下产出 3 份结果，字段不串 |
