# 整体设计方案：以条款为核心的认证准备与检查辅助系统（V1）

> **版本**：V1 | **日期**：2026-10-29 | **状态**：待裁决（战略层）
> **本文是什么**：战略层的**整体设计与方向论证**。回答"这套系统为什么这么建、骨架对不对、责任在哪、先做什么"。
> **本文不是什么**：不写字段细则（见 32/34/35/36）、不写页面（见 33）、不写提示词全文（见 35/28）。
> **定位一句话**：**我们不是认证系统，是审核员的辅助系统。** 所有判定由人做，我们只解决"费精力、费时间"的部分。

## 一、产品定位：做什么、不做什么、责任在哪

### 1.1 一句话定义

> **把 ISO 条款变成结构化数据，把企业资料变成条款级证据，替审核员完成"找、比、排、起草"四件耗时的事，判断和签字留给人。**

### 1.2 与"认证业务管理系统"的根本区别

市面上的体系认证软件基本是"业务管理"——管合同、管流程、管审批、管证书。这条路上我们做不过他们，也不该做。

| 维度 | 认证业务管理系统 | **本系统** |
|---|---|---|
| 管的是什么 | **流程**（谁在什么状态该做什么） | **内容**（条款要求什么、企业提供了什么、差在哪） |
| 核心能力 | 表单 + 审批流 + 归档 | **条款结构化 + 资料结构化 + 语义比对** |
| 用户价值 | 合规留痕、进度可视 | **少花时间、少漏检、少返工** |
| 用不用的后果 | 不用就违规 | **不用只是慢一点**（← 这是辅助系统的关键特征） |
| 失败方式 | 流程卡住 | **建议不准**（人一眼看穿，绕过即可，不停机） |

> 最后两行是这套设计最重要的安全感来源：**我们的失败模式是"建议不准"，不是"业务卡死"**。所以敢把 AI 放进来，也敢让人一键忽略。

### 1.3 责任边界三条（写进产品，不是写进合同）

| # | 原则 | 落地表现 |
|:--:|---|---|
| R1 | **不替人判定** | 系统输出"疑点/建议"，永远不输出"不符合"。NC 由审核员开具，签名是人 |
| R2 | **不阻断** | 任何一步都能跳过、手工填、直接导出。系统从不"必须先完成 A 才能做 B" |
| R3 | **交付即脱管** | 导出的检查表/计划/证据包是审核员的文件。系统不追踪后续修改，也不为已交付内容负责 |

> R3 不是免责话术，是**设计要求**：因此系统里不建"报告审批状态机"、不做"版本冻结"、不做"提交后锁定"。这些都会把辅助系统变成管理系统，而管理系统一旦卡住就没人用了。

### 1.4 为什么"辅助"不是妥协，而是唯一可行解

这一条要论证清楚，否则每次讨论都会被"能不能自动判 NC"带偏。

| 论据 | 内容 |
|---|---|
| **① 责任不可转移** | 认证决定是认证机构的法定行为（CNCA-QMS-01:2025 §5.7、§5.8）。系统若"判定"，等于把机构的法律责任挂到一个无法出庭的软件上 ⇒ 机构法务直接否 |
| **② 输入本质不完整** | 体系审核是**抽样**，报告必须含"抽样过程的免责声明"（§5.11.3(18)）。系统永远只看到一部分证据 ⇒ 任何"判定"都是越权 |
| **③ 判断的辩护成本** | 案例里"f（再确认未勾选）判**部分满足**"这种程度判断，需要的不是结论，是**可辩护的理由**。模型给结论容易，给可辩护理由难；而人给理由只要 30 秒 |
| **④ 人的边际价值在判断** | 审核员的时间分布（按案例反推）：找资料/比对/整理 ≈ 60–70%，判断 ≈ 20%，写报告 ≈ 10–20%。系统吃前 70%，比抢后 30% 更值、更安全 |

**结论**：系统的价值上限 = 把 70% 的机械工作压缩掉；**不是**替人做那 20% 的判断。所有设计选择按这条检验。

## 二、方向论证：为什么必须是"以条款为核心"

### 2.1 四条被否掉的路线（以及它们各自的死因）

| 路线 | 做法 | 死因（有实证） |
|---|---|---|
| **A 文档中心** | 以"文档规范化"为核心，把企业文件按模板改造 | V1 实际走的路线，已冻结。死因：企业文件无法被规范（每家企业组织方式不同），且**规范完之后仍然不知道条款满足没满足** |
| **B 流程中心** | 以任务/审批流为核心，配置检查步骤 | V1 的第二死因：配置量随企业数线性增长，配置永远补不完；且审核员现场会绕过流程 |
| **C 报告模板中心** | 以"生成报告"为核心，模板填空 | 死因：报告是产物不是过程。模板填空只能生成"看起来对"的文字，证据链是空的，专家一眼看穿 |
| **D 纯 AI 问答** | 不做模型，直接把资料丢给大模型问"有没有问题" | 死因：① 结论无法回溯到条款要求（不可辩护）；② 无事实验证，幻觉不可控；③ 每次问结果不同，无法交付一致的产物 |

**共同点**：四条路线都缺一个"稳定的、可枚举的、有权威原文的、可挂属性的"锚点。这个锚点就是条款。

### 2.2 条款作为原子的五个必要条件（逐条验证）

| 条件 | 是否满足 | 依据 |
|---|:--:|---|
| **稳定**（换版可控） | ✓ | 国标换版是外部事件，条款树换一版重跑；属性是资产不随树变（README 结论 2） |
| **可枚举**（能穷尽） | ✓ | 4 标准 273 条已入库，iso13485 67 条已全覆盖 9 属性 |
| **有权威原文**（可辩护） | ✓ | 国标正文 208 条 53,827 字已入库；引用可回到原文 |
| **可挂属性**（能承载判定依据） | ✓ | `cert_clause_attr_def` + `cert_clause_attr`（EAV）已落地 |
| **对齐真实工作对象** | ✓ | 见 §2.3，四份真实材料的共同键 |

### 2.3 真实材料的共同骨架（这是本方案最硬的证据）

取自 `docs/90-归档/案例资料/`：

| 材料 | 结构事实 | 说明什么 |
|---|---|---|
| [8.5.1条款证据清单.md](../../90-归档/案例资料/科斯亚质量体系文件/8.5.1条款证据清单.md) | 1 个条款 → **a~h 8 个分项** → 30+ 份记录文件；文件名里**一个条款号都没有** | 条款 → 分项 → 证据文件 是真实结构；匹配必须靠语义，不能靠文件名 |
| [8.5.1条款审核证据.md](../../90-归档/案例资料/科斯亚质量体系文件/8.5.1条款审核证据.md) | 对照表 + 结论；**f、g 判"部分满足"** | `partial` 是日常态，不是理论态 ⇒ 判定必须是多值 |
| [8.5.1条款审核证据_现场版.md](../../90-归档/案例资料/科斯亚质量体系文件/8.5.1条款审核证据_现场版.md) | **8 个现场问询维度**：抽样产品 / 关键工序 / 作业依据 / 人员能力 / 设备状态 / 监视测量 / 抽样证据 / 需确认过程 | 一个条款的"现场要问什么"是可以枚举的 ⇒ 可结构化、可预生成 |
| 江门药用辅料审核检查报告（6 张表） | **75 个检查项**；表名即检查单元（GM-MR / 行政财务+安环 / 生产部 / 质量部 / 设备部 / 研发部 / 采购+销售） | 真实粒度 = **条款 × 检查单元**；检查单元常是**多部门合并** |
| 同上 | 条款列大量跨标准合并：`Q 5.2.1/2 E & H 5.2`、`Q 9.3.1/2/3 E & H 9.3`、`Q7.1.1 E & H 7.1` | QES 一体化审核是常态；"每标准一份计划"表达不了真实合并 |
| 同上 | **同部门同表内同条款出现两次**（`4.1×2`、`4.2×2`、`Q5.2×2`、`H6.1.2×2`） | 拆分的驱动是**要求分项**，不只是部门 |
| 脱敏版 vs 原始报告对比 | 3 列 + `N` 标记 / 4 列 + `Major·Minor·OFI` / 企业内审 5 列 + `合格·OK` | **版式与判定词随机构/层次变** ⇒ 交付物层有机构差异 |

**一句话**：四份材料的工作对象完全一致——**条款 × 要求 × 检查单元 × 证据 × 判定**。我们只要把这五个东西的数据结构做对，就与他们的习惯对齐，落地阻力最小。

## 三、总体模型

### 3.1 一个原子，三个坐标

```
判定单元 = 条款(ClauseCode) × 要求分项(RequirementItem，可空) × 检查单元(CheckUnit)
```

| ⚠️ 与 README 结论 7 的差异 | 说明 |
|---|---|
| README 结论 7：`a/b/c 不拆成检查项`，判定落到"材料级" | **案例 4 显示真实报告在同部门同条款下按分项拆了项**（4.1 拆"背景"与"许可资质"；6.1.2 拆"识别"与"风险评估"） |
| **本文修订** | 分项**不升格为独立检查项**（清单行数仍按条款×单元），但**判定与 NC 必须能落到分项**。即：**行是条款级，判定是分项级** |

这样两个目标同时满足：清单长度可控（与审核员习惯一致），判定可精确（"f 缺再确认、g 缺防错"能分开写）。

### 3.2 三层数据 + 归属判据

| 层 | 内容 | 换企业能否复用 | 例子 |
|---|---|:--:|---|
| **标准层** | 条款 / 属性 / 适用性条件 / 检查要点 / 要求分项 / 文档要求 | ✓ 全复用 | `cert_iso_clause`、`cert_clause_attr` |
| **企业层** | 部门 / 职能映射 / 资料 / 提取结果 / 适用性结论 | △ 同企业复用 | `cert_enterprise_dept`、`cert_document_extraction` |
| **任务层** | 检查草案 / 入场计划 / 证据 / 疑点 / NC / 报告 | ✗ 一次性 | `cert_audit_plan`、`cert_evidence`、`cert_finding` |

**归属判据（沿用 README 结论 19）**：*这个东西换一家企业还用得上吗？* 用得上 = 标准层/后台；只对这家成立 = 任务层/专家端。

### 3.3 四条数据链

```
① 标准链（一次投入，全企业复用）
   条款 → 属性 → 适用条件 → 检查要点 → 要求分项 → 文档要求

② 企业链（一企业一次）
   资料 → 提取（条款候选 + 锚点 + 证据强度） → 覆盖度/缺口

③ 任务链（一任务一次）
   草案 → 人工修订 → 入场计划 → 证据采集 → 疑点 → NC → 交付物

④ 反馈链（越用越准的唯一机制）
   人工改动（增/删/改/合并） → 归因 → 调属性 or 调提示词
```

> **④ 是本设计新增的一条**，也是回答"模型和提示词有瑕疵怎么办"的唯一工程化答案：瑕疵不靠猜，靠**审核员改了什么**来定位。所以草案的每一处人工改动必须留痕（`Origin` + `ChangeReason`），这不是审计要求，是**调优数据源**。

### 3.4 证据矩阵：一个矩阵，两个时间点（全系统的统一底座）

整套系统其实只有**一张二维矩阵**：轴一 = 条款，轴二 = 证据来源。

```
                条款（ClauseCode，可多值）
              ┌────────────────────────────────┐
 计划项 /       │  证据（cert_evidence）            │
 企业文档       │  · 来源：企业文档 / 访谈 / 观察 / 照片 / 录音 │
              │  · 锚点：文件+位置，或 录音+时段+人   │
              │  · 采集：desk（准备） / onsite（现场）│
              └────────────────────────────────┘
```

**同一张矩阵，两个时间点填**：

| 时间点 | 怎么填 | 产出 |
|---|---|---|
| **准备（desk）** | 每份企业文档 × 本标准全部条款 → 命中 / 部分 / 不命中 + 关键信息 + 原文锚点 | "哪份文件支撑哪条条款" |
| **现场（onsite）** | 每个计划项 × 其条款 → 访谈 / 观察 / 照片 / 录音 / 现场记录 | "这条条款现场问到了什么" |

**这张矩阵同时是三件事的底座**（这才是它值钱的地方）：

| 用途 | 怎么从矩阵得到 |
|---|---|
| **缺口分析** | 某条款在此矩阵里零命中 ⇒ 要索取什么、要现场问什么 |
| **草案增强** | 某检查项在矩阵里已有 N 条命中 ⇒ 标"已找到资料"，审核员直接读 |
| **证据链 / 报告** | 某条款的全部命中行按时间排序 ⇒ 就是报告段落的原料，不需要二次拼接 |

> ★ **关键结论**："文档匹配"与"现场证据"**不是两套模型**，而是同一张矩阵的两个填充方向。因此 §五-决定 1（证据单表）不是风格选择，而是这张矩阵能成立的**必要条件**。

### 3.5 五条不变量（违反即数据不可信）

| # | 不变量 | 为什么 |
|:--:|---|---|
| I1 | **每条证据必须有锚点**：文件 Code + 位置，或 采集方式 + 时间 + 人 | 无锚点的证据在报告里写不进去，等于没有 |
| I2 | **每个疑点必须有依据**：条款要求 + 证据 + 差距 | 无依据的疑点会被审核员全部删掉，删多了就不用了 |
| I3 | **"不符合"只能指向条款未满足，不能是"资料没找到"** | 「未见 ≠ 不符合」（README 结论 12），否则会批量误开 NC |
| I4 | **每次判定必须记人与时间** | 责任在人，系统只提供过程 |
| I5 | **草案的任何人工改动必须留痕** | 反馈链的输入 + 报告"偏离计划"的依据 |

## 四、主流程：从接单到交付

### 4.1 全景

| 段 | 阶段 | 输入 | 系统做什么 | 人做什么 | 产物 |
|:--:|---|---|---|---|---|
| ① | **认领与准备** | 企业档案、标准、阶段 | 拉条款清单 + 已有资料清单；按标准/阶段过滤 | 用 AI/官网/电话了解企业（**外部完成**），决定查哪些、问什么 | 条款工作集 |
| ② | **适用性与裁剪** | 条款工作集 | 按属性给出"适用/不适用/待确认"建议 + 理由 | 确认/推翻，写理由 | 适用性结论 |
| ③ | **检查草案** | 适用条款 + 组织架构 + 已有资料 | 生成"条款 × 检查单元"草案：检查要点、要什么证据、问谁、远程还是现场 | 增删改、合并、标注已沟通 | 草案（可导出） |
| ④ | **入场计划** | 草案 | 按部门/单元/半天排班 + 分工 | 调顺序、补组员、定日期 | 入场计划（可打印可确认） |
| ⑤ | **现场证据** | 入场计划 | 手机端采集（录音/照片/记录），自动挂到计划项 | 问、看、拍、记 | 证据（带锚点） |
| ⑥ | **结论与交付** | 证据 | 按机构风格提示词组织证据、推论疑点、起草段落 | 判 NC、定严重程度、签字 | 检查表 / NC 清单 / 报告初稿 |

### 4.2 ① 认领与准备（含"企业研究由人完成"的定位）

**这里必须讲清楚一件事**（已按实际工作方式修正）：**企业研究不做成系统模块。**

| 项 | 结论 |
|---|---|
| 人怎么了解企业 | 问 AI、查官网、看公开信息、给联系人打半小时电话——**半小时足够判断哪些条款不适用、哪些能合并** |
| 系统要不要建模"企业画像" | **不要**。散落信息不会有人愿意录入，做了也没人填，最后是一张空表 |
| 系统承接什么 | **只承接结论**：① 条款适用性判定 ② 检查单元合并 ③ 需要索取哪些资料。三样都用一键写入，不需要先说清"为什么" |
| 系统提供什么 | 一份**带适用性建议的条款清单**（哪些大概率不适用、常见不适用理由），让人在研究时对照，减少"漏想" |

> 判据：**凡是需要人额外录入才能成立的模块，一律不做**。这条与 §1.3 的 R2（不阻断）同源。

### 4.3 ② 适用性与裁剪

三态 + 理由类型（理由分类见 §五-决定 3）：

```
条款 × 检查单元 → applicable | not_applicable(reason) | pending
```

裁剪的三个目的：① 减少无效检查项（企业无此业务）② 避免误开 NC（标准允许不适用）③ 报告"不适用"有据可查。

### 4.4 ③ 检查草案（用户最关心的一段）

**生成输入**（按重要性排序）：

| 优先级 | 输入 | 必需? |
|:--:|---|:--:|
| 1 | 条款属性（检查要点、要什么证据、怎么查、能否开 NC、严重程度、适用阶段） | **必需** |
| 2 | 适用性结论 | **必需** |
| 3 | 企业部门/职能映射（用于生成检查单元） | 必需（可默认按标准过程域推） |
| 4 | 已有资料与提取结果 | 可选（**只做增强，不做前置**） |

> ⚠️ 第 4 条是产品级判断：当前提取只跑通 31/237 份文件。若草案依赖资料，第一次演示就是空表。**草案必须"有条款就能出"，资料到了只标"已找到/缺失"**。

**提取必须两段式（这是成本分水岭）**：

| 段 | 输入 | 调用粒度 | 237 份文档的调用次数 | 产出 |
|:--:|---|---|:--:|---|
| **宽扫** | 一份文档 markdown + 本标准的**全部条款清单** | **一份文档一次调用** | ~237 | 候选条款 + 置信度（"这份文档大概能对上哪些条款"） |
| **深提取** | 过阈值的候选条款 + 该文档 markdown | 一份文档 × 若干候选条款 | 仅命中部分 | 逐条款：是否满足 / 可提取哪些关键信息 / 原文锚点 |

> ⛔ **不能做成"每份文档 × 每条条款各调一次"**：237 × 273 ＝ **6.4 万次**，同一份文档会被重复塞进上下文几十次，成本与耗时都不可接受。宽扫一次把文档读透，深提取只跑命中的那一小块，量级差 1–2 个数量级。
> 这也顺带回答了"条款编号怎么串起来"：宽扫的输出本身就是 `(文档, 条款)` 对，直接落 §3.4 的矩阵。

**草案行的内容**（每题一行或一条卡片）：

```
条款 / 要求分项 / 检查单元（部门组）/ 检查要点 / 需要什么证据 /
执行方式：远程可判 | 必须现场 | 已通过沟通解决 / 预判风险（可开 NC 吗、多严重）/
当前状态：已找到资料（N 份）| 部分 | 未找到
```

**人工修订的四个动作**（也是反馈链的四个信号）：

| 动作 | 含义 | 归因到哪里 |
|---|---|---|
| 删掉 | 生成多了 | 属性过宽 / 适用性判断错 |
| 新增 | 生成漏了 | 属性缺失 / 要求分项没拆 |
| 合并 | 粒度太细 | 合并规则（README 结论 16：停在哪层能一份证据问完） |
| 改要点 | 措辞不对 | 提示词 / 属性表述 |

### 4.5 ④ 入场计划

- **不是另建一套清单**，是草案的排班视图（34 号 D-T3 已定）；
- 必须**可打印、可确认**（法规要求现场前提交企业确认）；
- 补的字段：日期/场所/组员与任务/目的与准则（法定要素，见 §七-不做 5 的反面）；
- 与"认证计划"的分工不变：**认证计划回答"该查什么"，入场计划回答"哪天谁去哪个单元查什么"**。

**计划项的字段（按你的描述，不需要新增表）**：

```
条款编号（多个）         ← 一个计划项可对应多条条款（合并检查）
沟通部门（多个）         ← 检查单元 = 多条款 × 多部门
审核员（执行人）/ 是否组长
主要内容（检查要点）
执行方式：desk | onsite
证据：录音（可转文字）/ 照片 / 现场记录 / 文档引用  ← 全部落 cert_evidence，带 ClauseCode
预判：可开 NC 吗 / 严重程度
来源：auto（草案生成）| manual（人工新增）/ 改动理由
```

> 你说的"多条款 + 多部门 + 审核员 + 主要内容 + 证据"**就是检查单元本身**。所以不必新增 `CheckUnit` 实体 —— **计划项即检查单元**；`cert_audit_plan_detail` 现有结构（`Clauses` / `Departments` 多值）已能承载，只缺 `执行方式`、`预判`、`来源留痕` 三类列。

### 4.6 ⑤ 现场证据

- 采集媒介：录音 / 拍照 / 手记 / 表格填写；
- 每条证据自动挂 `PlanItemCode`，带 `CollectMode=onsite`；
- 与准备阶段证据**同一张表**（见 §五-决定 1），只是 `SourceKind` 与 `CollectMode` 不同；
- 一旦落库即可被疑点推论复用，**现场不用二次录入**。

> 这一段是整套系统"别人做不到"的地方：多数工具停在"生成检查表"，我们能一路接到"证据 + 疑点"，因为证据与计划项是同一个键。

### 4.7 ⑥ 结论与交付

- 按机构风格提示词（通用版 + 机构覆盖版）把证据组织成段落；
- 推论疑点：`证据 + 条款要求 → 差距 → 疑点(未判)`；
- 审核员判：符合 / 观察 / 轻微 / 严重 / 不适用，写理由；
- 导出：检查表（Excel/Word）、NC 清单、报告初稿。

## 五、四个骨架决定（现在定，以后改不动）

### 决定 1：证据只有一张表

企业提供的文件 与 审核员现场采集 是**同一种东西的不同来源**，必须同表。

```
cert_evidence
  Code, PlanItemCode(可空), ClauseCode, RequirementItemCode
  SourceKind    -- enterprise_doc | interview | observation | photo | record | public_info
  SourceRef     -- 文件 Code / 录音路径 / 页码 / 表格行
  Excerpt       -- 原文片段（带锚点）
  CollectedAt, CollectorCode, CollectMode   -- desk | onsite
  State         -- candidate | confirmed | rejected
```

**为什么必须**：疑点推论本质是"在同一套证据上推理"。若分两套表（`cert_doc_extract_*` 与现场证据表），到 §4.7 就要二次拼接，且永远拼不干净；报告的证据链也就无法自动生成。

**这张表就是 §3.4 的矩阵**：`ClauseCode` 是横轴，`PlanItemCode + SourceKind + CollectMode` 是纵轴。你描述的"文档按全部条款过一遍"与"计划项的录音/照片/记录"，只是往同一张表的两侧写行。

### 决定 2：疑点与 NC 是一张表的两个状态

"推论出疑点，帮助判断是否开 NC"这句话本身已给出答案：**疑点是未断定的 NC**。

```
cert_finding
  Code, PlanItemCode, ClauseCode, RequirementItemCode
  State      -- draft | questioning | confirmed | closed
  Verdict    -- null(未判) | conform | observation | minor | major | na
  Basis      -- 条款要求 + 差距描述
  EvidenceRefs, OpenedBy, ClosedBy, ClosedAt
```

现状问题：`cert_check_finding` / `cert_plan_clause_point` / `cert_clause_point` / `cert_clause_gap` 四张表字段互不兼容，**谁都写不进去、谁都读不全**。合表是骨架第二件必做。

### 决定 3：不适用是"判定 + 理由"，不是删除

| 类型 | 情形 | 报告怎么写 | 依据 |
|---|---|---|---|
| `BusinessNotFound` | 企业无此业务（如无设计开发 → 8.3） | 未开展…活动，不适用 | 事实 |
| `StandardExclusion` | 标准明确允许不适用 | 按 x.x.x 不适用，理由：… | ISO 13485:2016 §4.2.2（允许 6.4.1 / 7.3 / 7.5.2 / 7.5.4 四条不适用，须记录理由） |
| `OutOfScope` | 不在认证范围内 | 不纳入本次范围 | ISO 9001 §4.3、ISO 14001 §4.3（9001:2015 起已无"删减"条款，只能通过范围） |
| `Merged` | 已合并到其他检查项 | — | README 结论 16 |

⛔ 禁止用软删除表达"不适用"。因为报告里"不适用"必须**有人、有理由、有依据**，否则现场核查直接判不符合。

### 决定 4：草案以条款驱动，资料只做增强

见 §4.4 的四级输入表。一句话：**有条款就能出草案；资料缺失只标状态，不减项。**

## 六、怎么证明方向是对的（不靠感觉，靠度量）

### 6.1 黄金案例：ISO 13485 / 8.5.1

手上有专家标准答案（三份 8.5.1 文件）。把它做成回归基准：

| 回归项 | 专家答案 | 系统应输出 | 通过线 |
|---|---|---|---|
| 分项识别 | a~h 8 个分项 | ≥ 6 个对得上 | 75% |
| 建议索取材料 | 30+ 份记录 | 命中 ≥ 20 份 | 60% |
| 现场问询点 | 现场版 8 维度 | ≥ 6 个对上 | 75% |
| 疑点 | f、g 判"部分满足" | 至少识别出 g 缺记录 | 命中 1 条 |

> 这条比任何设计评审都有效：**模型或提示词一改就跑一遍，看离专家有多远**。有度量才有迭代方向。

### 6.2 三个度量（长期跟踪）

| 度量 | 定义 | 目标方向 |
|---|---|---|
| **覆盖率** | 草案里有资料支撑的检查项 / 总项 | 升 |
| **命中率** | 专家答案里被系统命中的项 / 专家答案总项 | 升 |
| **人工改动率** | 被审核员增删改的草案行 / 总行数 | **降** |

第三个是最重要的健康指标：它同时是提示词调优的唯一信号。

### 6.3 验收口径

**一个企业 × 一个标准 × 一条链跑通**（资料 → 草案 → 入场计划 → 证据 → 疑点 → 导出），再横向铺。理由：骨架对不对只能靠"一条走通"证明；横向铺量只会把错误放大。

### 6.4 验证阶段明确暂缓的模块（以及为什么可以暂缓）

目标：**有限时间内跑通业务、验证模型与提示词**，专家认可后再补成商业版。所以下列模块**本阶段不做**：

| 暂缓项 | 为什么可以暂缓 | 一旦要做，代价是什么 |
|---|---|---|
| **入场计划（排班层）** | 它解决的是"谁哪天去哪个部门"，**不提高 AI 判断质量**；专家是否认可只取决于两件事：证据找得准不准、疑点提得对不对 | 纯增量：只需把证据按 `PlanItemCode` 分组 |
| **手机端证据采集** | 录音/拍照/手记是复杂工程（权限、上传、转写、断网），但它**不改变数据结构** | 纯增量，只需增加 `SourceKind` 取值 |
| **交付物格式（机构模板）** | 验证阶段用最丑的导出（CSV/Markdown）就够，只要**内容**对 | 纯增量 + 配置，但它是**商业版的第一道门**（见下） |

> ★ **保护性设计（唯一现在必须做的）**：为了让上面三项都是"纯增量"而不是"回填迁移"，证据表必须满足两条：
> 1. **`PlanItemCode` 可空** —— 没有入场计划时证据也能独立存在；
> 2. **证据行按 `(证据来源, 条款)` 稀疏拆行** —— 一份文档支撑 5 条条款就是 5 行，共享同一个文件引用。
>
> 这样后补入场计划只是"按 `PlanItemCode` 分组展示"，补手机端只是"多一个 `SourceKind`"，**不需要动已有数据**。
>
> ⚠️ 但同时记录一条商业版输入：验证时专家抱怨的**格式问题**（表格不像他们的表、导出是 CSV）不是噪音，那是商业版的开工清单。

### 6.5 验证阶段的最小闭环（不做入场计划时的替代路径）

```
选 1 条款（8.5.1）
  → 装配：条款 markdown + 索引 + 该条款相关文档内容（后台聚合）
  → 准备提示词（严格输出契约） → { 证据候选 + 缺口 }
  → 人工确认（这一步就是"专家认可度"的度量点）
  → 检查提示词（同输入装配）     → { 疑点候选 + 依据 }
  → 与专家答案对比（§6.1 的四项度量）
```

**停止条件**：专家愿意留下 **≥ 60%** 的证据候选与疑点 → 模型可用，再谈铺量与商业版。低于 60% 不铺量，因为铺得越多，返工越大。

## 七、明确不做的事（以及理由）

| # | 不做 | 理由 |
|:--:|---|---|
| 1 | **企业画像/资料画像模块** | 人会靠 AI、官网、半小时电话了解企业，不会把散落信息录进系统。做了是一张空表（详见 §4.2） |
| 2 | **流程审批 / 任务催办 / 状态机** | V1 的死因。审核员现场不会被系统驱动，只会被自己的进度驱动 |
| 3 | **自动开 NC** | 责任不可转移（§1.4①）。系统只到"疑点"，判定留人 |
| 4 | **自造时间预算** | 时间估算若靠模型累加，永远对不上真实人日。计划只留日期与法定要素；人日核对用外部依据（见 §九-风险 2） |
| 5 | **按机构复制整套配置** | 机构差异只体现在**交付物层**（检查表版式、判定词、提示词风格），不复制条款与属性 |
| 6 | **为历史建议负责** | R3：交付即脱管。系统不追踪已导出文件的后续修改 |
| 7 | **不做"报告审批"** | 报告是机构自己的事，我们只出初稿 |

## 十、风险（按真实概率排）

| # | 风险 | 表现 | 对策 |
|:--:|---|---|---|
| 1 | **草案生成"看着对但没用"** | 审核员全部删掉重写 | 用人工改动率度量；先只做 8.5.1 一条到"审核员愿意留 60% 以上" |
| 2 | **审核员年度人日溢出** | 排了人，结果该审核员当年已超 **180 天**上限（2026-01-01 新规），只能换人重排 | **最小做法（不做排产引擎）**：① `审核员年度人日余额`视图（由已完成计划自动累计：180 − 已用）② 入场计划分工时**提示**超限，**不阻断**（R2）③ 组内多人时给出"谁还有余量"。注意 180 ÷ 250 工作日 ⇒ 余量年末必然吃紧，**一季度就要看余额**，不能等到 Q4 |
| 3 | **多标准合并表达不了** | QES 一体化的行被拆成三份 | 检查单元 + 条款组从第一天就支持多标准 |
| 4 | **提取覆盖率太低，草案空** | 237 份文件只出 31 条提取 | 草案不依赖资料（决定 4）；提取只做增强 |
| 5 | **疑点太吵** | 每条条款都出疑点，人就不看了 | 按"可开 NC 与否 + 严重程度"分级排序；默认只显示高风险 |
| 6 | **责任边界被模糊** | 用户开始把系统结论当结论用 | 界面固定"建议"字样；导出物带"AI 辅助生成，需人工复核"页脚 |

## 十一、一句话总结

> 以条款为原子、以证据为血脉、以人为最终判断者。
> 我们不改变认证业务的责任结构，只是把审核员最耗时的 70% 工作（找、比、排、起草）交给人机协作完成。
> **方向正确的判据不是"模型多聪明"，而是"审核员愿意留下多少"**——这也决定了我们的开发顺序：先把一条 8.5.1 做到有人愿意用，再谈全量。
