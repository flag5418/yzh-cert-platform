## 二、三处文档矛盾（必须先裁决，否则实施必返工）

### 矛盾 1：`DocCheckMode` 到底在不在属性池

| 出处 | 说法 |
|---|---|
| 24 号 §3.4 | 种子 8 条，**无** `DocCheckMode` |
| `实施-TODO-认证准备-V1` §1.1 | 已加属性行 `DocCheckMode`（`ValueType=dict`，`Sort=85`）；实测值域 `required×50 / optional×17 / none×0` |
| 39 号 M2 / 48 号 | 说 9 条属性 |
| 实库 | **8 行，无 `DocCheckMode`** |

**裁决**：`DocCheckMode` **必须有**。理由：它是"这条款要不要去查资料"的开关。缺了它，装配只能对所有条款查资料——既贵又不准，且无法回答"这条款材料侧够不够"。
**值域**：`required` / `optional` / `none`（字典码 `cla_clause_doc_check`，需新建）。

> 顺带记录一个实测异常：`实施-TODO` 记的分布是 `required 50 / optional 17 / none 0`——**`none` 为零**，说明生成时没有一条判成"不需要资料"。这本身可疑（纯现场类条款、纯访谈类条款应当有 `none`）。重灌时把它列为校验项。

### 矛盾 2：`RequirementItems` 删了，但文档提取还要用它

| 出处 | 说法 |
|---|---|
| 24 号 §3.4 | **删除** `RequirementItems`，理由："实测找不到对应到 a/b/c 的检查证据" |
| 28 号 §3.3 | `clauseFacts[].keyFacts` "由条款的 `RequirementItems` / `Artifacts` 决定要提什么" |
| 20 号评估报告 R-1 | 建议**保留**，用途从"NC 引用字典"改为"**检查内容字典 + NC 措辞素材**" |

**裁决**：24 号删得对（不要国标原文的 a/b/c 分项），但**删过头了**。28 号需要的是"这条款要验哪几个点"，那是**可验证要素**，不是 a/b/c。

**新增 `CheckElements`（可验证要素）**，明确与 a/b/c 的区别：

| | 国标 a/b/c 分项 | 可验证要素 |
|---|---|---|
| 来源 | 条文原文结构 | 从条文拆出的可独立验证的点 |
| 粒度 | 1 条款 1–5 项 | 1 条款 3–7 项（可跨 a/b/c） |
| 例子 | 7.5.2 a) 标识和说明；b) 格式和载体；c) 评审和批准 | E1 唯一标识 / E2 日期作者 / E3 载体可识别 / E4 发布前评审 / E5 授权批准 / E6 发放回收 / E7 作废处理 |
| 用途 | 引用位置 | **判定单位 + 措辞锚点 + 提取目标** |

> 这一条修完，28 号的 `keyFacts` 才有定义来源，"缺哪个要素"才可计算，报告才能写出"未见批准记录"这种程度的句子。

### 矛盾 3：提示词存哪张表

| 出处 | 说法 |
|---|---|
| 28 号 §3.6 | `wf_prompt_template`，`PromptType = doc_extract` |
| 39 号 D6 | ⛔ 不读 `wf_prompt_template` |
| 48 号 §12.1 | `cert_prompt_template` 7 行、`wf_prompt_template` 10 行（两表并存） |
| 实库 | 两表都在，都是 0 行 |

**裁决**：**一张表 `cert_prompt_template`**，`wf_prompt_template` 停用（V1 遗留，只读兼容，不写入）。
**理由**：两表并存时，"今天改了哪张"永远说不清，且 39 号已明令不读 wf 表。28 号 §3.6 作废。

## 三、属性池重设计（8 → 11 条）

### 3.1 定稿清单

| # | `Code` | 属性名 | `ValueType` | 唯一问题（这条属性只回答这一件事） | 状态 |
|:--:|---|---|---|---|---|
| 1 | `ClauseIntent` | 条款作用 | `text` | 这条款到底在管什么 | 保留 |
| 2 | `Obligation` | 约束强度 | `dict` | 是"应"还是"宜/可/注"（能不能开 NC 的闸门） | 保留 |
| 3 | `Applicability` | 适用性 | `dict` | 通用，还是有条件 | 保留 |
| 4 | `ApplicabilityCondition` | 适用条件 | `text` | 有条件的触发条件原文 | 保留 |
| 5 | `Process` | 过程域 | `json` | 这条款管哪些过程（与部门取交集） | 保留 |
| 6 | `DocCheckMode` | 文档核对方式 | `dict` | 要不要查资料、查到什么程度 | **补回** |
| 7 | `Artifacts` | 企业应备资料 | `json` | 企业侧该有什么（清单化） | **改造** |
| 8 | `EvidenceChain` | 取证剧本 | `json` | 审核员侧怎么查（看什么/问谁/抽几份） | **改造** |
| 9 | `CheckElements` | 可验证要素 | `json` | 拆成哪几个可独立验证的点 | **新增** |
| 10 | `RecordRetention` | 记录时效要求 | `json` | 频次 / 保留期 / 覆盖期 | **新增** |
| 11 | `SamplingHint` | 抽样建议 | `json` | 最少样本数 / 抽样维度 | **新增** |
| 12 | `Severity` | 严重度基线 | `dict` | 不满足时的默认级别 | 保留 |

> 12 条，不是 11——`Severity` 必须留（它是 NC 级别的唯一基线，且 48 号实测"模型没给就从结论反推"说明它现在无处可依）。

### 3.2 两条改造（`Artifacts` / `EvidenceChain`）——把提示词从属性值里搬出去

**现状问题**（48 号自述）：这两个属性的值是一段 500+ 字提示词，"只能原样拼入提示词"，实测"整份塞进去既贵又不准"。

**裁决**：**属性值只存"生成用的提示词引用 + 产出结构"，不存提示词正文。**

```json
// Artifacts 的值（结构化，不是一段话）
{
  "promptCode": "attr_artifacts_qms",
  "promptVersion": 3,
  "expect": "ArtifactHit[]",
  "artifactKinds": ["procedure", "record", "list"]
}
```

提示词正文进 `cert_prompt_template`（按标准各一份），属性只留引用。这样：

- 改提示词不动属性值（不会 683 行全失效）
- 属性可被程序校验（`expect` 与代码强类型对上）
- 装配时按需取，不再拼几百字自由文本

> 24 号 §3.3 说"`prompt` 类型内部仍要求输出结构化 JSON"——方向是对的，但落地方式错了：结构化的是**产出**，不是**值**。

### 3.3 三条新增的结构定义

**`CheckElements`**

```json
[
  {
    "elementCode": "E4",
    "text": "发布前经过评审",
    "judgeLevel": "B",
    "evidenceKinds": ["review_record", "signature"],
    "factKeys": ["reviewDate", "reviewer"],
    "requiredFor": ["QMS-7.5.2"],
    "wordingFound": "查见《{docName}》的评审记录，评审人：{reviewer}，日期：{reviewDate}",
    "wordingMissing": "未见《{docName}》发布前的评审记录"
  }
]
```

**`RecordRetention`**

```json
{ "frequency": "annual", "periodFrom": "2026-01", "periodTo": "2026-12",
  "retainYears": 3, "basisText": "9.2.1 组织应按照策划的时间间隔进行内部审核" }
```

> `frequency` 是"时效不符合"的唯一依据（记录覆盖期 < 要求周期 → 时效不符合）。当前属性池完全没有这一项，这是一处实质缺口。

**`SamplingHint`**

```json
{ "min": 3, "max": 10, "dims": ["部门", "班次", "项目"], "basisText": "抽样应覆盖不同班次" }
```

> 没有它，"同一条款两个审核员抽 3 份和 10 份得出不同结论"就永远无法收敛——这是"可复现"的硬前提。

### 3.4 属性池的四条纪律（沿用 24 号，保留）

1. 池子大、配置小：不设"适用条款"列，没行 = 没配。
2. 不设 `ValueSource` 在池子层（只在条款配置层）。
3. 不设"必填集"（不在代码里规定 7 章必须有哪几条）。
4. 值类型只有 5 种（`text/dict/bool/json/prompt`），多值一律 `json`。

**新增第五条**：

5. **可机器生成的属性 vs 必须人定的属性，必须在定义里标注**。

| 类别 | 属性 | 生成方式 |
|---|---|---|
| 语法可推 | `Obligation`、`Applicability`、`Process` | 规则 + 模型，可全自动 |
| 语义可生 | `ClauseIntent`、`CheckElements`、`RecordRetention`、`SamplingHint` | 模型生成 + 抽检 |
| 结构可生 | `DocCheckMode`、`Artifacts`、`EvidenceChain` | 模型生成 + 强类型校验 |
| **必须人定** | `Severity` | 专家配置，模型不得自定 |

> 加一个 `GenMode` 字段（`rule` / `model` / `manual`），让流水线知道哪些能自动跑、哪些必须停下来等人。

## 四、条款挂接（L1 条款配置）重设计

### 4.1 表结构：沿用 24 号，加两列

| 列 | 说明 | 为什么加 |
|---|---|---|
| `GenBatch` | 生成批次号 | 重跑时能整体回滚/对比，不会新旧混用 |
| `PromptVersion` | 生成时用的提示词版本 | 可复现：同一批值能追到是哪版提示词产的 |

> 24 号明确不加 `ReviewStatus`——这一条保留（那是企业侧的概念）。但 `GenBatch` 不是审核状态，是**数据血缘**，必须加。

### 4.2 生成策略：按标准分支，分两跳

**第一跳（结构层）**：只产 `Obligation` / `Applicability` / `Process` / `DocCheckMode`
- 失败模式：值域错（"必须"写成 shall）、漏项
- 校验：值域白名单 + 分布检查

**第二跳（语义层）**：产 `ClauseIntent` / `CheckElements` / `Artifacts` / `EvidenceChain` / `RecordRetention` / `SamplingHint`
- 失败模式：要素拆不出、编证据、动词映射错
- 校验：结构强类型 + 抽检

**为什么分两跳**：24 号 §3 自己记了反面教训——"一条提示词跑 4 个标准，结果是 `约束强度` 恒等于应、`过程` 恒等于管理"。结构层和语义层的失败模式完全不同，混在一次调用里，出了问题分不清是哪层。

**每标准一份提示词**（`qms` / `ems` / `ohsms` / `mdqms`），不允许一条跑四本。

### 4.3 三道校验闸门（这是"评估后再实施"的落地）

| 闸门 | 规则 | 不过怎么办 |
|---|---|---|
| G1 值域 | `dict` 属性的值必须在字典内；`json` 必须能反序列化成强类型 | 该行作废，进失败清单 |
| G2 分布 | `Obligation` 必须出现 ≥3 种取值（全 shall 直接判失败）；`DocCheckMode` 的 `none` 不得为 0；`Process` 不得恒等于 `management` | 整批重跑，不落库 |
| G3 抽检 | 每标准随机抽 20 条款，人工比对 6 条核心属性，一致率 ≥90% | 不达标不准进下一步 |

> G2 是从这次事故里长出来的：上次 683 行属性里 `Obligation` 77/77 全是 shall，等于这条属性报废，但没人发现——因为没有分布校验。

### 4.4 覆盖率报表（每次重灌必须出）

按 `标准 × 属性` 统计：

| 指标 | 阈值 |
|---|---|
| 条款覆盖率（有值的条款 / 总条款） | ≥90% |
| 缺失清单（哪个条款缺哪条属性） | 必须导出 |
| 空值 vs 未配置 | 分开统计（24 号 §4.4 的"两种空"） |

## 五、文档提取重设计

### 5.1 保留 28 号的部分（这些设计是对的）

| 设计 | 保留理由 |
|---|---|
| 文档分三类（规则性 / 内审 / 记录） | 三类要提的东西不同，混在一起字段必污染 |
| 两跳提取（先候选条款，再补条款级信息） | 一次跑 40+ 条款必漏项 |
| 三态 `found/partial/not_mentioned` | "不存在"与"没看清"必须分开 |
| 每条证据带 `anchor` | 报告与 NC 必须能引原文 |
| `evidenceLevel` 三级（direct/indirect/mention_only） | "写了"≠"能当证据" |
| 只输出命中条款 + `coverage.notRelated` | 逼模型填满就是逼它编 |
| 提示词只给事实、不下结论 | 判定归规则 |

### 5.2 修订四处

**修订 1：`keyFacts` 的来源改为 `CheckElements`（见 §2 矛盾 2）。**
提取时逐要素回答：这份文档有没有覆盖 E1–E7、覆盖到哪、原文在哪。输出：

```json
"clauseFacts": [{
  "clauseCode": "QMS-7.5.2",
  "elements": [
    { "elementCode": "E1", "state": "found", "facts": {"docNo": "XXKJ-QESM-2025"}, "anchor": "封面" },
    { "elementCode": "E4", "state": "not_mentioned", "facts": {}, "anchor": "" }
  ],
  "evidenceLevel": "direct"
}]
```

> 这个改动让"缺哪个要素"直接可算，不再需要模型在 `keyFacts` 里自由发挥。

**修订 2：提示词表名终裁为 `cert_prompt_template`（见 §2 矛盾 3）。**

**修订 3：增加"文档类型识别规则"，放在提取之前。**
手册 / 程序 / 指导书 / 记录 / 报告 / 台账，先分类再提取。判据优先级：

```
① 目录结构（如 04-记录文件/、02-程序文件/）
② 文件名关键词（程序、规定、办法、制度、指导书、台账、记录、报告、计划）
③ 内容首屏特征（"1 目的 2 范围 3 职责"= 程序；表头+数据行 = 记录）
④ 以上都不确定 → other，交人工
```

> 这一步不做，"三类文档分别提取"就是空话——因为系统不知道该用哪套契约。

**修订 4：表格抽取按 `DocType` 定义"关键表模板"。**

真实资料里最有价值的证据都在表格里（劳动合同、培训签到、设备台账、供方评价）。现在 `tables.rows` 结构每次不同，下游没法消费。做法：

| 文档类型 | 关键表 | 必抽列 |
|---|---|---|
| 记录-培训 | 培训签到表 | 时间、项目、讲师、参加人、考核结果 |
| 记录-合同 | 劳动合同 | 甲方、乙方、起止日、岗位、签署 |
| 记录-设备 | 计量器具台账 | 设备编号、名称、校准日期、证书号、有效期 |
| 记录-采购 | 供方评价表 | 供方名称、评价日期、评价结论、批准人 |

**这张表是"抽样句"能不能自动生成的关键**——没有固定列名，"抽3份、日期、签署"就抽不出来。

### 5.3 新增两项产出（当前完全没有）

**产出 1：条款覆盖率**
哪些条款被至少一份文档覆盖、哪些一份都没有。这是"未见"的**正当来源**，也是报告覆盖声明的依据。

**产出 2：文档级部门归属**
`docMeta.processDept` 必须与企业部门表对齐（同一部门不许三种写法），否则"部门 × 条款"矩阵算不出来。做法：先由企业档案给候选部门清单，模型只选 + 标 `deptSource = enterprise|inferred`。

## 六、字段级映射表（三层之间的唯一契约）

> 这是整套设计里最缺的一张表。没有它，装配时只能靠猜。

| 层 | 字段 | 来源 | 去向 | 用途 |
|---|---|---|---|---|
| L1 属性 | `CheckElements[].elementCode` | 条款配置 | 提取请求 | 决定每份文档要回答哪几个要素 |
| L1 属性 | `CheckElements[].factKeys` | 条款配置 | 提取契约 | 决定要抽哪些事实字段 |
| L1 属性 | `CheckElements[].judgeLevel` | 条款配置 | 判定 | A 机械可判 / B 半机械 / C 专业 |
| L1 属性 | `RecordRetention.frequency/period` | 条款配置 | 覆盖声明 | 时效判定 |
| L1 属性 | `SamplingHint.min/dims` | 条款配置 | 抽样句 | 样本数下限 |
| L1 属性 | `Artifacts.artifactKinds` | 条款配置 | 提取检索 | 该找哪类材料 |
| L1 属性 | `Obligation` / `Severity` | 条款配置 | 判定 | 能否开 NC / 默认级别 |
| L2 提取 | `clauseFacts[].elements[].state` | 文档提取 | 齐备度 | found/partial/not_mentioned |
| L2 提取 | `elements[].facts` | 文档提取 | 句式槽位 | 编号/版本/日期/签署 |
| L2 提取 | `elements[].anchor` | 文档提取 | `SourceRef` | 可追溯 |
| L2 提取 | `tables[].rows` | 文档提取 | 抽样句 | 样本明细 |
| L3 生成 | 齐备度三态 | 代码计算 | 结论候选 | complete→conform 候选 |
| L3 生成 | 覆盖声明 | 代码统计 | 报告第 18 项 | 抽样免责 |

**一句话**：L1 定"要什么"，L2 答"有没有"，L3 写"是什么"。三者之间只通过本表交互，任何一边私自多传字段都算破坏契约。

## 七、评估方案（过关才实施）

### 7.1 设计评估（本文档层面，一天内可完成）

| # | 检查项 | 通过标准 |
|:--:|---|---|
