## 零 · 一句话

> **这套系统不是替审核员做判断，是让审核员不漏判。**

认证准备：把**条款要求、企业资料、部门联系人**三样东西对齐，告诉审核员「哪些能不去现场、哪些必须去、去了查什么、找谁查」，产出**入场计划**。
认证检查：审核员按计划取证，系统结合条款分析证据，**推论** NC，由审核员确认。

**准备阶段不做 NC 判断，只有检查阶段才做。**

## 零之二 · 入场计划是强连接器

这是本轮最重要的结构认知：

```
认证准备 ──产出──→ 入场计划 ──被消费──→ 认证检查
                      │
                      └─ 独立的页面：组长看全部，审核员看「我的」
                         逐项补证据（桌面端 / 手机端）
```

| 情形 | 认证检查的形态 |
|---|---|
| **有入场计划**（准备派生过） | 与入场计划**强挂钩**。独立的入场计划页面，审核员对着自己名下的检查项逐项补证据 |
| **无入场计划**（准备跳过） | 走模式 A：从认证计划展开的检查项列表，逐项补证据 |

**手机端是主战场**：审核员白天在企业，打开入场计划 → 录音 → 拍照 → 记录信息，当场完成证据收集。系统后续把录音转文字、自动归类到检查项。

> 本期先把「手动补证据 → 推理出检查证据 + NC 疑点」跑通。手机端与自动归类是下一步，但证据表要预留 `SourceType` 和 `RawTranscript` 字段，避免以后改表。

## 一 · 业务定位：这套系统到底在帮谁

你说的核心作用，拆成三条能力：

| # | 能力 | 解决什么问题 |
|---|---|---|
| **1** | 条款结构化 + 文档结构化 | 审核员对条款不熟、容易遗漏，导致检查失误 |
| **2** | 企业资料与条款的**匹配情况**分析 | 审核员不知道企业现在缺什么、该往哪个方向查 |
| **3** | 条款 ↔ 部门 ↔ 联系人 的对应信息 | 审核员不知道怎么和哪些部门制定审核计划、找谁谈 |

这三条决定了设计的取舍：

- **不做**：系统自动判适用性、自动映射部门、自动定检查方式 —— 这些是专家的专业判断，系统不该插手
- **要做**：把信息**组织好、摆到审核员面前**，让他做判断更快、更准、不漏

## 二 · 业务全景

### 2.1 两种使用模式

**模式 A：只做认证检查**（认证检查可独立使用）

```
认证计划 → 审核员按检查项逐个补充检查证据 → 系统分析 → 检查证据 + 推理 NC
```

**模式 B：认证准备 + 认证检查**（完整流程）

```
认证计划
   ↓
认证准备 → 入场计划建立
   ↓
入场计划执行（现场取证）
   ↓
入场计划补充（可能通过移动端完成证据补充）  ← 下一步
   ↓
系统推理 → 检查证据 + NC 疑点
```

> **模式 A 必须能独立跑通**，不能强依赖认证准备。这是设计约束。

### 2.2 完整链路

```
企业申请认证（自愿选择标准，可多体系）
  ↓
认证计划（企业 × 标准 × 阶段）
  │  专家在建计划时：
  │   · 选条款范围
  │   · 手工指定每个条款对应哪些部门 ← 靠专家对条款和企业组织机构的理解决定
  ↓
┌──────────── 认证准备（入场准备）────────────┐
│  目的：为证据收集做准备，不判 NC             │
│                                             │
│  ① 系统读企业底档 + 条款结构化信息            │
│  ② 系统告知：企业资料与条款的匹配情况         │
│  ③ 专家独立判定：条款适用 / 不适用            │
│  ④ 专家独立判定：哪些不用去现场               │
│  ⑤ 专家制定入场动作（多条）+ 选检查方式       │
│  ⑥ 审核组长分配：每个检查项归哪个审核员       │
│  ⑦ 锁定已完成的检查项                        │
└─────────────────────┬───────────────────────┘
                      │ 产出
               ┌──────▼──────┐
               │  入场计划    │
               └──────┬──────┘
┌─────────────────────▼───────────────────────┐
│  认证检查（现场执行）                        │
│                                             │
│  ① 审核员按入场计划取证（照片/记录/访谈/文件） │
│  ② 证据进统一证据链（阶段=onsite）            │
│  ③ 系统分析：企业资料 + 全部证据 + 条款属性    │
│  ④ 产出：检查证据 + 系统建议结论 + NC 建议     │
│  ⑤ 审核员确认或直接改结论                     │
│  ⑥ 逐条签发 NC                               │
│  ⑦ 锁定                                      │
└─────────────────────┬───────────────────────┘
                      │ 产出
               ┌──────▼──────┐
               │  认证报告    │
               └─────────────┘
                      │
                      ↓ 企业整改 → 补充证据 → 重跑（不用到现场）→ 闭合 NC
                    （循环，见第十二章）
```

## 三 · 七个词

| 词 | 定义 | 谁定 |
|---|---|---|
| **条款** Clause | 标准里的一条要求，如 `4.1` | 标准本身，带 9 类属性 |
| **检查项** CheckItem | **条款 × 部门** | 建计划时专家定义，准备阶段可调 |
| **入场检查项** OnsiteCheck | 检查项 × 一个检查动作，**多条** | 专家制定，系统给建议但不强制 |
| **审核组长** LeadAuditor | 定计划、定入场计划、分配检查项 | 计划级角色 |
| **审核员** Auditor | 执行自己负责的检查项，取证、确认结论 | 检查项级，一人一项 |
| **系统建议** SystemConclusion | LLM 推论的结论，仅供参考 | 系统 |
| **审核员判断** AuditorConclusion | 覆盖系统建议的最终结论 | 审核员 |

### 4.1 已有资产

| 对象 | 现状 |
|---|---|
| `cert_iso_standard` | 4 个标准：iso13485 / iso9001 / iso14001 / iso45001 |
| `cert_iso_clause` | 273 条条款 |
| `cert_clause_attr` | **每条款 77 条属性，9 类**（见 4.2） |
| `cert_audit_plan` | 1 份（测试开发企业，iso13485 + iso9001 双标准） |
| `cert_audit_plan_detail` | 一行 = 多条款 + 可空部门 |
| `cert_task` / `cert_task_item` | 测试数据，7 任务 / 十几项 |
| `cert_check_analysis` / `cert_check_result` / `cert_check_lock` | 已建，M2/M3 跑通过 |
| `cert_evidence` | **空表** |
| `cert_nc` | **空表** |
| `cert_audit_member` | 审核员档案（姓名/职称/专业/年限/资格证） |

### 4.2 条款属性（9 类）

| AttrCode | 含义 | 样例 | 用途 |
|---|---|---|---|
| `Applicability` | 适用性 | `general`(53) / `conditional`(24) | 供专家判定的**参考**，不是系统判定依据 |
| `ApplicabilityCondition` | 适用条件 | 多为空 | 同上 |
| `Process` | 涉及过程 | `["management"]` | 供专家建计划时参考 |
| `EvidenceChain` | 取证链 | JSON `{Kind:site\|record\|interview\|doc, Action, Target, Sample}` | **入场动作的建议来源** |
| `Artifacts` | 应提交材料 | JSON `{Kind, FileName, DeviceNo, ValidUntil, Complete}` | 判「资料匹配情况」的依据 |
| `DocCheckMode` | 文件检查方式 | `required` | 判「能不能不去现场」的参考 |
| `ClauseIntent` | 条款意图 | 「识别影响…的内外部问题」 | LLM 判定输入 |
| `Obligation` | 义务强度 | `shall` | 严重度基线 |
| `Severity` | 严重度基线 | — | NC 严重度参考 |

> **重要边界**：这些属性是**给人和 LLM 看的参考材料**，不是系统的自动判定规则。
> `Applicability` 只用来在界面上提示「这条通常是有条件适用的」，最终判定由专家下。

### 4.3 三个必须改的结构偏差

#### 偏差一：检查项粒度（最严重）

`cert_task_item.CheckItemCode` → `cert_audit_plan_detail.Code`，而明细一行是：

```
Clauses: 680cf5ab...,d20871b4...   ← 2 个条款
Departments: （空）                 ← 没有部门
```

⇒ 「这个检查项归哪个部门」无法回答 ⇒ 入场计划写不出「去哪个部门查」。
⇒ 必须独立成 `cert_check_item`，粒度 **条款 × 部门**。

#### 偏差二：没有审核员归属

`cert_task_item` 有 `Status / EvidenceState / AnalysisState / AnalyzeCount / RerunState` 等执行字段，**没有 `AuditorCode`**。
`cert_audit_member` 是机构档案（谁有资格），不是「这个检查项谁负责」。

#### 偏差三：结论只有一个字段

`cert_check_result.Conclusion` 既是系统输出又是最终结论，无法表达「系统判断」和「审核员决定」两层。

## 五 · 核心模型

### 5.1 四层结构

```
标准（iso9001）
  └ 条款（4.1）                        ← 9 类属性
       │  × 企业部门（品管部）
       │    ↑ 建计划时专家手动指定（靠对条款 + 组织架构的理解）
       ↓
     检查项（4.1 × 品管部）             ← 工作单元：有审核员、有状态、可锁定
       │  × 检查动作（多条）
       │    ↑ 系统按 EvidenceChain 给建议，专家增删
       ↓
     入场检查项（查台帐 / 访谈李主任 / 现场看设备）
```

### 5.2 条款 × 部门：人工定义，系统不猜

**建计划时**，专家勾选条款后，为每条条款指定涉及部门：

| 条款 | 涉及部门（专家指定） |
|---|---|
| 4.1 组织环境 | 总经办、品管部 |
| 7.1.5 监视测量资源 | 品管部、技术部 |
| 8.5.1 生产控制 | 生产部、技术部 |

依据：专家对条款的理解 + 企业的组织机构图 + 部门职责。
系统在这一步只做两件事：**展示条款属性供参考**、**展示企业部门树**。**不做自动映射。**

### 5.3 条款适用性：专家独立判定

| 判定 | 谁定 | 结果 |
|---|---|---|
| 适用 | **专家** | 正常走流程 |
| 不适用 | **专家** | 状态 `na`，不分析、不入场、报告里列在「不适用条款」清单 |
| 有条件适用 | **专家** | 需附理由 |

**系统完全不参与判定**，只在界面上把 `Applicability` 和 `ApplicabilityCondition` 摆出来供参考。

> 判定发生在**认证准备阶段**。检查阶段不改适用性。

### 5.4 「能不能不去现场」：专家判定，系统只给事实

系统能做的是**摆事实**：

| 事实 | 呈现 |
|---|---|
| 企业资料齐全 / 缺失 | `PrepState` = found / partial / missing |
| 条款要求哪些材料（`Artifacts`） | 逐条列出「应有 vs 实有」 |
| 条款的取证动作含 `site` / `interview` | 标出「此条款涉及现场或访谈」 |

系统**不做的是**给出「建议免现场 / 建议入场」的结论。

专家看完事实后自己定，填 `EnterOnsite = yes / no`。

> 你说的「资料齐全性、内审材料完整性、失信记录」——这些条款的 `EvidenceChain` 全是 `doc`/`record`，事实摆出来专家自然知道不用去。

## 六 · 角色与权限

### 6.1 两个角色

| 角色 | 职责 | 作用范围 |
|---|---|---|
| **审核组长** LeadAuditor | 建计划、定入场计划、**分配检查项给审核员** | 整个认证计划 |
| **审核员** Auditor | 执行自己负责的检查项：取证、确认结论、签发 NC | 自己名下的检查项 |

> 一个企业检查一般 **2-3 人**。A 审核员查 A 部门，B 审核员查 B 部门。

### 6.2 组长是项目角色，不是人的属性

`/audit-member`（专家组设置）是**人员档案**：姓名、职称、专业、工作年限、资格证号。**这里不该有「职位」字段**，因为：

> 今天可能是张三当组长，明天另一个企业又是李四当组长。组长不是固定的。

所以：

| 概念 | 存在哪 | 说明 |
|---|---|---|
| 这个人有没有审核员资格 | `cert_audit_member` | 机构级档案，跨项目复用 |
| 这个人在**这个项目**是不是组长 | `cert_audit_plan.LeadAuditorCode` | **项目级**，随项目走 |

**同一个人在不同项目里角色可以不同**：A 项目是组长，B 项目是普通审核员。

⇒ 权限判断不能写成「这个人是不是组长」，必须写成「**在计划 X 里，我是不是组长**」。即权限是 `(PlanCode, UserCode)` 的函数，不是人的属性。

> 如果以后需要记录「这个项目组有哪几个人参与」，再加 `cert_audit_plan_member`（计划 × 人 × 项目内角色）。本期用「计划上的组长 + 检查项上的执行人」两个字段就够，因为分工已经在检查项粒度上表达了。

### 6.3 权限矩阵

| 操作 | 审核组长 | 审核员 | 说明 |
|---|---|---|---|
| 建/改计划 | ✓ | ✗ | |
| 定条款 × 部门 | ✓ | ✗ | |
| 判适用性 | ✓ | ✗ | 准备阶段 |
| 制定入场动作 | ✓ | ✗ | |
| **分配检查项审核员** | **✓** | ✗ | 准备阶段可改 |
| 看入场计划（全部） | ✓ | ✗ | |
| **看入场计划（我的）** | ✓ | **✓** | **手机端按登录人筛** |
| 现场取证 | ✓ | ✓ | 只对自己名下 |
| 确认结论 / 改系统判断 | ✓ | ✓ | 只对自己名下 |
| 签发 NC | ✓ | ✓ | 只对自己名下 |
| 锁定 | ✓ | ✓ | 只对自己名下 |
| **检查阶段改审核员** | **✗** | **✗** | 要改回准备阶段改 |
| **检查阶段改入场动作** | **✗** | **✗** | 同上 |

### 6.4 审核员字段

`cert_check_item` 上单值：

| 字段 | 说明 |
|---|---|
| `AuditorCode` | 执行审核员（一人） |
| `AuditorName` | 冗余，便于导出与手机端显示 |
| `AuditorAssignedAt` / `AuditorAssignedBy` | 分配时间与分配人（组长） |

计划级另加 `cert_audit_plan.LeadAuditorCode`（审核组长）。

> 单人是有意为之：手机端登录后要能直接筛出「我的入场计划」，多人会让这个筛选失去意义。

## 七 · 认证准备

### 7.1 目标（不是判 NC）

> 「入场准备就是为了方便审核员为证据收集做准备，这里不是做判断 NC 的。」

准备的产出是**信息组织 + 入场计划**，不是结论。

### 7.2 七个步骤

| # | 步骤 | 谁做 | 产出 |
|---|---|---|---|
| 1 | 读企业底档 | 系统 | 企业基本情况 / 认证资料清单 / 组织架构 / 部门职责 |
| 2 | 条款要求结构化 | 系统 | 每条条款：要求什么、要什么材料、证据链是什么 |
| 3 | **资料与条款匹配分析** | 系统 | 逐条：应有 vs 实有，缺什么，`PrepState` + 疑点 |
| 4 | **判适用性** | 专家 | 适用 / 不适用 / 有条件适用 |
| 5 | **判是否入场** | 专家 | 免现场 / 需入场 |
| 6 | **制定入场动作** | 专家（系统给建议） | 入场检查项（多条），检查方式由专家选 |
| 7 | **分配审核员** | 审核组长 | 每个检查项一个执行人 |

### 7.3 PrepState 五态

| 值 | 含义 | 是否推 NC |
|---|---|---|
| `found` | 资料齐全 | 否 |
| `partial` | 部分缺失 | 否 |
| `missing` | 关键缺失 | 否 |
| `unknown` | 无法判断 | **绝不推 NC** |
| `na` | 不适用 | 否 |

准备阶段**没有任何 NC 相关动作**。`PrepNcHint` 只是给入场计划看的「这里可能会成为问题」，不进 `cert_nc`。

## 八 · 入场计划

### 8.1 入场检查项（多条）

一个检查项（如 `4.1 × 品管部`）到了现场可能要：

1. 查《设备台帐》近 12 个月更新记录（记录查阅，抽 3 份）
2. 访谈李主任，问设备责任人划分（人员访谈）
3. 现场看实验室仪器是否在台帐内（现场观察）
4. 要企业提供《实验室仪器清单》v2（文件调阅）

**四条记录，方式不同、对象不同、抽样量不同。**

### 8.2 检查方式（预设，审核员选）

| 值 | 显示名 |
|---|---|
| `site` | 现场观察 |
| `record` | 记录查阅 |
| `interview` | 人员访谈 |
| `meeting` | 会议讨论 |
| `doc` | 文件调阅 |
| `sample` | 抽样验证 |
| `other` | 其他（手填） |

> 预设清单可配置（`Sys_DictionaryList`）。审核员自由选，系统**不推荐**。
> 「开会 / 讨论」独立成 `meeting`，因为导出后是给人看的，和一对一访谈有区别。

### 8.3 表 `cert_onsite_plan_item`

| 字段 | 类型 | 含义 |
|---|---|---|
| `Code` | varchar(50) | 主键 |
| `PlanCode` | varchar(50) | 入场计划 |
| `CheckItemCode` | varchar(50) | 检查项 |
| `Seq` | int | 序号 |
| `Method` | varchar(20) | 检查方式（见 8.2） |
| `MethodOther` | varchar(100) | `other` 时的说明 |
| `TargetType` | varchar(20) | `dept` / `doc` / `person` |
| `TargetCode` / `TargetName` | | 对象 |
| `Action` | varchar(500) | **查什么**（具体动作） |
| `SampleSize` | varchar(50) | 抽样量 |
| `FocusPoints` | text | 重点核查（来自疑点） |
| `RequiredDocs` | text | 需企业提前准备 |

| `SourceKind` | varchar(20) | `system` 系统建议 / `manual` 人工新增 |
| `IsConfirmed` | tinyint(1) | 组长是否确认 |
| `Remark` | text | |

### 8.4 生成方式

```
cert_clause_attr.EvidenceChain (JSON)
        ↓ 系统给出建议动作（SourceKind=system）
        ↓ 专家增删改（SourceKind=manual）
        ↓ 组长逐条确认 IsConfirmed=1
        ↓
      入场计划定稿
```

### 8.5 定稿后不能改

| 阶段 | 能否改 |
|---|---|
| 认证准备（draft） | ✓ 可改 |
| 认证检查（confirmed） | **✗ 完全不能改** |

> 要改就回认证准备阶段改。理由：计划是审核组长定的，检查是审核员执行的，执行阶段改计划等于绕开组长。

### 8.6 按人筛选（手机端关键）

入场计划列表必须支持：

| 视图 | 谁能看 |
|---|---|
| 全部检查项 | 组长 |
| **我的检查项**（`AuditorCode = 当前登录人`） | 所有人（默认视图） |

手机端登录后直接看到「我要查什么」，这是单人审核员设计的目的。

### 8.7 独立的入场计划执行页面

入场计划定稿后，它本身就是一个**可独立打开的页面**，不是认证检查里的一个标签页：

```
入场计划列表（组长看全部 / 审核员默认「我的」）
  └ 入场计划详情（一份计划 = 一个企业的这次入场）
       ├ 概览：企业 / 阶段 / 标准 / 审核组长 / 检查项数 / 需入场数 / 进度
       ├ 我的检查项（审核员视角，按 AuditorCode 过滤）
       │    └ 检查项 4.1 × 品管部
       │         ├ 入场动作 1：查设备台帐（记录查阅）      [补证据]
       │         ├ 入场动作 2：访谈李主任（人员访谈）      [补证据]
       │         └ 入场动作 3：现场看实验室仪器（现场观察） [补证据]
       └ 检查项状态：待取证 / 已取证待分析 / 已分析待确认 / 已确认 / 已锁定
```

关键点：

| 点 | 说明 |
|---|---|
| **逐项补证据** | 对着入场动作补，补完该动作标「已取证」 |
| **不强绑** | 证据仍挂在**检查项**上（`cert_evidence.CheckItemCode`），不强制挂到某个动作。动作只是引导 |
| **随时可看进度** | 组长看全员进度，审核员看自己的 |
| **手机端同一套数据** | 桌面和手机是同一份入场计划，不是两套 |

### 8.8 手机端形态（下一步，但数据结构要留口）

审核员的真实场景：

```
白天在企业
  ↓ 打开手机上的入场计划
  ↓ 对着检查项：录音 / 拍照 / 记几笔
  ↓ 当场完成证据收集
  ↓ 晚上回酒店点「分析」
```

系统要做的自动化：

| 能力 | 说明 |
|---|---|
| 录音转文字 | 现场访谈录音 → 文本 |
| **自动归类到检查项** | 根据内容把录音片段归到对应的检查项（甚至对应的入场动作） |
| 拍照归类 | 按当前打开的检查项自动打标 |

**本期不做**，但证据表要预留：

| 字段 | 用途 |
|---|---|
| `SourceType` | `manual` 手填 / `voice` 录音 / `photo` 拍照 / `import` 导入 |
| `RawTranscript` | 录音转出的原始文本（未归类时先存这里） |
| `MediaKind` / `AttachmentsJson` | 已有，复用 |

> 这样以后接语音，不用改表结构，只需要加一个「归类」服务。

### 8.9 本期不做

- 入场动作 ↔ 证据的**强绑定**（证据仍挂检查项，动作只做引导）
- 移动端实现、录音转文字、自动归类
- 入场计划的版本对比（`Version` 字段先留着）

## 九 · 认证检查

### 9.1 两个入口

| 模式 | 起点 | 页面形态 | 流程 |
|---|---|---|---|
| **A 独立** | 认证计划 | 检查项列表（计划展开的全部项） | 逐项补证据 → 分析 → NC |
| **B 强挂钩** | **入场计划** | **独立的入场计划页面**，按 `AuditorCode` 只看我的 | 逐项补证据 → 分析 → NC |

判据很简单：**这个计划派生过入场计划吗？**

- 派生过 → 认证检查与入场计划**强挂钩**，检查的工作面就是入场计划页面，不再另起一个检查项列表
- 没派生过 → 走模式 A，直接按检查项列表干活

两种模式**最终 LLM 执行过程完全一样**，只是证据来源和入口不同。这也是为什么引擎不用改。

### 9.2 五个步骤

| # | 步骤 | 谁做 | 产出 |
|---|---|---|---|
| 1 | 按入场计划取证 | 审核员 | `cert_evidence`（`CapturedIn=onsite`） |
| 2 | 系统分析 | 系统 | 检查证据 + 系统建议结论 + NC 建议 |
| 3 | **审核员确认或改结论** | 审核员 | 最终结论（直接覆盖，不留差异） |
| 4 | 逐条签发 NC | 审核员 | `cert_nc` |
| 5 | 锁定 | 审核员 | 该检查项定稿 |

### 9.3 证据是提示，不是硬卡

| 证据情况 | 系统行为 |
|---|---|
| 有证据 | 正常分析 |
| **证据为 0** | **仍可分析**。① 页面提示「尚无现场证据」② 系统建议标 `insufficient_evidence` ③ 审核员要下结论必须手填说明 |
| 证据与条款不匹配 | 分析时提示，不阻断 |

### 11.1 一张表，阶段区分

> 「认证准备和认证检查的证据链（审核员提供的），其实都是在一个证据链表中，只是有不同的阶段区分，我们都可以作为核心的原始证据提供给系统进行 LLM 分析。」

|---|---|
| `CheckItemCode` | 挂在哪个检查项 |
| `CapturedIn` | **`prep` / `onsite`** —— 唯一的阶段区分 |
| `CapturedTaskCode` | 哪次任务采的 |
| `EvidenceKind` | 文件 / 照片 / 访谈记录 / 抽样 / 手填说明 |

### 11.2 两阶段证据同等对待

LLM 分析时**不区分来源**，全部塞进 prompt：

```
企业原始资料（企业上传）
  + 准备阶段补充的证据（CapturedIn=prep）
  + 检查阶段采集的证据（CapturedIn=onsite）
  + 条款属性（ClauseIntent / Artifacts / EvidenceChain / Severity）
  → 一次分析
```

> 这解释了为什么「认证准备挂证据方式不一样，但 LLM 执行过程一样」—— 因为引擎只认证据，不认它是哪个阶段采的。

### 11.3 引擎不变

现有 `CertCheckEngineService.AnalyzeCheckItemAsync` 的设计（`StageKind` 区分分支、同一套 prompt 骨架、同一套落库逻辑）**保持**。只需在证据收集环节把两阶段证据都取出来。

## 十二 · 锁定与整改闭环

### 12.1 锁定的业务动机（这次才讲清）

> 「我们推理了一大堆检查证据，审核员好不容易阅读审核完成了，我们如果不锁定，重新跑一遍，就把审核员的工作全部作废了，是万万不可的。」

锁定保护的是**审核员已经付出的阅读与判断**，不是技术上的防覆盖。

### 12.2 为什么必须能反复执行

企业认证不是必须全部合格。典型场景：

```
检查 → 开 NC（如：未粘贴安全警告 / 缺关键设备 / 缺重要信息）
  ↓
企业整改
  ↓
企业补充证据（拍照、提供新文件）
  ↓
重跑该检查项（不用到现场）
  ↓
新结论 pass → 闭合 NC
```

所以**重跑是常态**，不是异常。但重跑只能动「需要闭合 NC 的那几项」，**已通过并锁定的项绝不能动**。

### 12.3 补证据的是审核员，不是企业

企业线下把整改材料交给审核员（邮件 / 微信 / 现场递交），**审核员录进系统**：

```
企业整改完成 → 线下把材料给审核员
  ↓
审核员在系统里补证据（CapturedIn=onsite，EvidenceKind=整改材料）
  ↓
NC 置 pending_review → 重跑该检查项 → 复核
  ↓
通过 → NC 置 closed（或 rejected 退回）
```

**系统不需要企业端账号。** 审核员能独立解决的事，不牵涉企业。

### 12.4 锁定规则

| 规则 | 说明 |
|---|---|
| 锁的粒度 | **检查项级**，不是任务级 |
| 谁能锁 | 该检查项的审核员 / 组长 |
| 锁定后 | 不参与任何重跑、不被分析覆盖、结论冻结 |
| 解锁 | 显式操作，留痕（谁、何时、为什么） |
| 两阶段都能锁 | 准备阶段锁 = 资料判定定稿；检查阶段锁 = 结论定稿 |

### 12.5 按项重跑（不是整批）

```
勾选 N 个检查项 → 点「重新分析」
        ↓
逐个判断锁定状态
        ├─ 未锁定 → 直接进队列
        └─ 已锁定 → 弹窗：「以下 M 项已锁定，重新分析会覆盖现有结论」
                     □ 我已复核，同意重新分析（必须勾选）
                     ↓ 解锁 → 进队列
        ↓
队列执行（TaskType = cert_check_prep / cert_check_onsite）
        ↓
新分析行 RunNo+1，旧行 IsCurrent=NULL
        ↓
该检查项结论清空，需审核员重新确认
```

### 12.6 与现有实现的关系

| 现状（M3 已做） | 目标 |
|---|---|
| `StartTaskAsync(taskCode)` 跑整个任务 | `AnalyzeItemsAsync(taskCode, itemCodes[])` 跑选中项 |
| 锁定项**静默跳过** | 锁定项**弹窗要求重新认可**，不静默 |
| 任务级 `Status` 驱动进度 | 保留，但进度按选中项算 |

## 十四 · 状态机

### 14.1 检查项状态（`cert_check_item.Status`，长期状态）

| 状态 | 含义 |
|---|---|
| `waiting` | 待处理 |
| `running` | 分析中 |
| `analyzed` | 系统已出建议，**待审核员确认** |
| `confirmed` | 审核员已确认 |
| `locked` | 已锁定 |
| `na` | 不适用（专家判定） |
| `failed` | 失败 |

### 14.2 结论状态

| 层 | 取值 |
|---|---|
| 系统建议 | `pass` / `ofi` / `nc` / `na` / `unknown` / `insufficient_evidence` |
| 审核员判断 | `pass` / `ofi` / `nc` / `na`（四选一，无 unknown） |

### 14.3 入场计划状态

`draft`（可改）→ `confirmed`（定稿，检查阶段引用，**不可改**）→ `archived`（被新版替代）

### 14.4 NC 状态（整改闭环）

| 状态 | 含义 |
|---|---|
| `open` | 已签发，待企业整改 |
| `pending_review` | 企业已提交整改证据，待复核 |
| `closed` | 复核通过，闭合 |
| `rejected` | 整改不通过，退回 |

> 重跑该检查项结论转为 `pass` 后，可把对应 NC 置 `closed`。**这是反复执行的主要用途。**

## 十七 · 已确认（前几轮的问题都有答案了）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 审核组长用字段还是成员表？ | **计划上一个字段**（`LeadAuditorCode`）。组长是项目角色，不进人员档案 |
| Q2 | NC 整改闭环要不要企业端？ | **不要**。审核员补证据即可 |
| Q3 | 认证检查独立使用时检查项从哪来？ | 从 `cert_check_item`（计划展开）取全部项 |
| Q4 | 检查项审核员一人还是多人？ | **一人**（手机端按登录人筛入场计划） |
| Q5 | 部门映射要系统自动吗？ | **不要**，专家建计划时手动定 |
| Q6 | 适用性判定系统参与吗？ | **不参与**，专家独立判定 |
| Q7 | 系统建议与审核员判断不一致怎么处理？ | **直接覆盖，不保留差异** |
| Q8 | 检查方式谁定？ | **审核员选**，系统给预设清单 |
| Q9 | 入场计划定稿后能改吗？ | **不能**，回准备阶段改 |
| Q10 | 两阶段证据分表吗？ | **一张表**，靠 `CapturedIn` 区分 |

## 十八 · 还需确认（2 个，都不阻塞开工）

| # | 问题 | 我的建议 |
|---|---|---|
| **Q11** | 入场动作的「已取证」标记，是**动作级**还是**检查项级**？ | 动作级（哪个动作取了证打哪个勾），但**证据仍挂检查项**。这样手机上能看到「还有 2 个动作没做」，又不破坏证据归属 |
| **Q12** | 组长能不能**代审核员操作**（补证据、确认结论）？ | 建议**只读**。组长能看全部进度、能重新分配（在准备阶段），但不能代替审核员签字。因为结论是审核员的责任 |

> 这两个可以边做边定，不影响第一期开工。

## 附录 A · V1 中被推翻的设计（避免以后又绕回去）

| V1 设计 | 为什么错 |
|---|---|
| 系统用 `Process` 属性自动建议部门 | 部门是专家建计划时手动定的，系统不该猜 |
| 系统建议适用性，审核员确认 | 适用性是专家独立判断，系统不参与 |
| `ReviewStatus=diverged` + 理由必填 | 不保留差异，审核员直接覆盖 |
| 检查方式由系统按 `EvidenceChain` 推导 | 方式由审核员选，系统只给预设清单 |
| 入场计划定稿后检查阶段可补说明 | 完全不能改，要改回准备阶段 |
| 准备阶段可推 `PrepNcHint` 并影响 NC | 准备**不判 NC**，只有检查判 |
| 锁定是「防机器覆盖」的技术措施 | 锁定是**保护审核员劳动成果**的业务措施 |
