> **V3.3 变更**：

> 🔴 **"cert_doc_extract_knowledge 这个暂时是多余的"** —— 之前的全局总框架 + 单标准提示词过早设计了运行时的提取结果存储（cert_doc_extract 表）和完整的执行引擎（供给 + 推理），这些都是过早优化。
> - 不同企业面临不同的认证阶段（第一阶段、第二阶段），不同阶段检查的条款不一样
> - 后续的认证准备、认证检查环节的表结构、条款匹配逻辑都没设计出来
> - 提示词拼接逻辑、标准 Markdown → 文档分类字段映射 等都是运行时的细节，现在写死就是过早设计
>
> **三个当前只做**：
> 1. 规则 UI 设计（左树右编辑）
> 2. 规则数据怎么保存（提示词存取）
> 3. 规则测试时上传文档 → 直接显示生成的 JSON（不涉及任何存储）
>
> 等. **提取结果怎么存储（cert_doc_extract）**
> b. **认证准备阶段怎么消费这些结果**
> c. **认证检查阶段怎么匹配文档与条款**
> d. **不同阶段（S1/S2）的不同条款检查规则**

## 二、为什么 Markdown + 提示词要存 DB

### 2.1 问题

提示词编写需要参考标准原文（GB/T 19001-2016 等），不同条款对文档要求不同。如果没有原文，LLM 提取时的 prompt 只能靠猜测字段，质量无法保证。

### 2.2 存什么

| 内容 | 用途 |
|---|---|
| **标准 Markdown**（完整国标原文） | 提示词的事实来源；编写提示词时对照；未来条款匹配时的参考 |
| **提示词文本**（每个标准一份提取提示词） | LLM 文档提取时调用 |

### 2.3 合一表设计

```
cert_doc_extract_rules（文档提取规则表）

| 字段 | 类型 | 说明 |
|---|---|---|
| Id | bigint PK AUTO_INCREMENT | 主键 |
| Code | varchar(50) UNIQUE | 业务键（GUID） |
| StandardCode | varchar(36) NOT NULL | ★ 标准编码（cert_iso_standard.Code GUID） |
| StandardName | varchar(200) NOT NULL | 标准名称（冗余，方便展示） |
| MarkdownContent | mediumtext NULL | 该国标完整 Markdown 全文 |
| PromptContent | mediumtext NULL | 该标准的文档提取提示词 |
| PromptVariables | json NULL | 提示词变量列表（如 ["document_content"]） |
| Version | int DEFAULT 1 | 版本号（每次发布 +1） |
| IsPublished | tinyint(1) DEFAULT 0 | 当前是否发布 |
| Sort | int DEFAULT 0 | 排序号 |
| IsValid | int DEFAULT 1 | 有效标志 |
| Remark | varchar(500) NULL | 备注 |
| CreateBy | varchar(50) NULL | |
| CreateTime | datetime DEFAULT NOW() | |
| UpdateBy | varchar(50) NULL | |
| UpdateTime | datetime NULL | |
| DeleteBy | varchar(50) NULL | |
| DeleteTime | datetime NULL | |
| IsDeleted | tinyint(1) DEFAULT 0 | |
| Status | varchar(50) NULL | |
```

**设计要点**：
- 每标准一行，`StandardCode` 非空（不搞"全局总框架"那套——暂时用不到）
- `MarkdownContent` 和 `PromptContent` 独立存取（Markdown 很大但很少改，Prompt 经常改）
- `Version` + `IsPublished` 支持版本追溯和灰度发布
- 未来加全局总框架只需允许 `StandardCode` 可为空即可，不动结构

**唯一索引**：
- `uk_code` (`Code`) —— 业务键
- `uk_standard` (`StandardCode`) —— 一个标准只能有一条规则（当前简化；未来可扩展为"标准 + 阶段"）

### 2.4 数据行示例

```
| Code | StandardCode | StandardName | MarkdownContent | PromptContent | IsPublished |
|---|---|---|---|---|---|
| RULE-001 | guid-iso9001 | ISO 9001 质量管理 | GB/T 19001 Markdown 全文 | 9001 提取提示词 | 0 |
| RULE-002 | guid-iso14001 | ISO 14001 环境管理 | GB/T 24001 Markdown 全文 | 14001 提取提示词 | 0 |
| RULE-003 | guid-iso45001 | ISO 45001 职业健康安全 | GB/T 45001 Markdown 全文 | 45001 提取提示词 | 0 |
| RULE-004 | guid-iso13485 | ISO 13485 医疗器械 | GB/T 42061 Markdown 全文 | 13485 提取提示词 | 0 |
```

### 3.2 交互流程

```
1. 用户选左侧标准节点
   → 右侧加载该标准的 PromptContent + MarkdownContent
2. 用户编辑 PromptContent
   → [保存] → 暂存（IsPublished 不变）
   → [保存并发布] → Version + 1，IsPublished = 1
3. 用户上传测试文档（.docx/pdf/txt）→ 转 Markdown → 拼接提示词 → LLM 调用
   → 右侧直接显示结果 JSON（不落库）

```

### 4.2 /test API 流程

```
POST /api/DocExtractRule/test
  Body: { ruleCode: "RULE-001", file: <上传文件> }

  1. 根据 ruleCode 查 cert_doc_extract_rules → 取 PromptContent
  2. 上传文件 → 调用现有 AI Vision 服务转 Markdown
  3. 拼接最终 prompt = PromptContent + {{document_content}} = 转换后的 Markdown

```

### 4.3 提取 JSON 输出格式（条款映射为核心字段）

每次 LLM 调用产出的 JSON 必须包含 `clauseCodes` 字段，标识该文档关联的标准条款章节：

```json
{
  "docName": "焊接工序作业指导书",
  "docCategory": "生产类",
  "processDept": "生产部",
  "processName": "焊接工序",
  "coreContent": "规定了焊接工序的工艺参数、检验标准...",
  "clauseCodes": "8.5.1、8.1",
  "specific": {
    "工艺参数": "温度280±10℃、压力0.4MPa",
    "检验标准": "焊缝外观无气孔、夹渣",
    "成文信息充分性": "文档中已明确",
    "防错设计": "文档中未提及"
  }
}
```

#### clauseCodes 字段规范

| 规则 | 说明 | 示例 |
|---|---|---|
| **单条款** | 文档明确对应某一条款 | `"8.5.1"` |
| **多条款** | 用中文顿号（、）或英文逗号（,）分隔 | `"8.5.1、8.1"` 或 `"8.5.1, 8.1"` |
| **无法匹配** | 留空字符串 `""`，不填 null 也不省略字段 | `""` |
| **编号来源** | 必须与 `cert_iso_clause.ClauseNumber` 一致 | `"4.1"` `"5.1.1"` `"8.5.1"` |

#### 为什么条款映射如此重要

```
文档 → clauseCodes = "8.5.1、8.1"
          ↓
  条款 8.5.1（生产和服务提供）执行时 → 自动匹配到此文档
  条款 8.1（运行策划和控制）执行时 → 自动匹配到此文档
          ↓
  审核员检查 8.5.1 时，系统提示："企业已提供《焊接工序作业指导书》，
  该文档规定了工艺参数（温度280±10℃）、检验标准..."
```

**没有 clauseCodes = 文档无法被条款消费 = 提取结果无法进入认证检查流程。**

#### 提示词中如何约束 clauseCodes

每个标准的 PromptContent 必须包含以下指令：

```markdown
## 条款映射（必填）
分析文档内容，判断该文档适用于本标准哪些条款章节。
- 输出字段名：clauseCodes
- 多个条款用顿号（、）分隔
- 无法确定对应条款时输出空字符串 ""
- 条款编号参考：[此处列出该标准的核心条款号]
```

## 五、标准 Markdown：来源与清洗

### 5.1 已有素材

| 标准 | 源文件 | 大小 | 质量 |
|---|---|---|---|
| GB/T 19001-2016 | `temp/gbt_extract/gbt19001_ocr3.txt` | 62KB | ✅ OCR 已校对 |
| GB/T 24001-2016 | `temp/gbt_extract/gbt24001.txt` | 85KB | ✅ 原生文本 |
| GB/T 45001-2020 | `temp/gbt_extract/gbt45001.txt` | 122KB | ✅ 原生文本 |
| GB/T 42061-2022 | `temp/gbt_extract/gbt42061_ocr3.txt` | 79KB | ✅ OCR 已校对 |

### 5.2 清洗规则

1. 去除 `===PAGE N===` 标记
2. 合并为连续 Markdown 文档
3. 保留官方章节编号（"1 范围" "4 组织环境" "4.1 …"）
4. OCR 污点已校正处保留，新增可疑处标 `[待校对]`
5. 头部加 YAML front matter（标准号、名称、发布日期）

### 5.3 验证

- [ ] 章节覆盖完整（如 ISO 9001 应含第 1–10 章）
- [ ] 关键条款号存在（4.1/5.1/6.1/7.1/8.1/8.5.1 等）
- [ ] Markdown 与 `cert_iso_clause.ClauseNumber` 交叉验证覆盖率 > 95%
