## 零、标准是第一维（多标准隔离 · 最上位约束）

> **2026-10-28 用户指正**：「针对一个标准一个提示词的设计还是没有体现在文档中，因为不确定最终企业选择几个标准进行认证，企业文档的结果，也应该只针对一个标准，如果有 3 标准认证，就有 3 个结果。」
> 此前全文只有「`StandardCode` 是唯一键的一部分」这种字段级表述，**没有把「标准」立成贯穿全链的第一维** ⇒ 补此节。

### 0.1 一句话

**标准不是标签，是结果的容器。** 企业选 N 个标准做认证 ⇒ **N 条互不相干的链路**，每条各有自己的提示词、条款配置、企业实际值、证据、NC、报告。⛔ 任何环节都不许把多个标准合并成一份结果。

### 0.2 链路：每一环都带标准

```
标准 iso9001（cert_iso_standard.StandardCode = 短码）
  └─ 条款树 cert_iso_clause.StandardCode          ← 条款天生属于某一个标准（存 GUID）
      └─ L1 条款配置 cert_clause_attr              ← uk(StandardCode, ClauseCode, AttrCode)
          └─ 预生成提示词 wf_prompt_template        ← ★ 每标准一份（StandardCode 非空）
              └─ L2 企业实际值（专家端）             ← uk(Enterprise, Session, StandardCode, Clause, Attr)
                  └─ L3 证据 / 判定 / NC             ← 每标准一套
                      └─ 企业文档结果                 ← ★ 每标准一份文档
```

### 0.3 四层归属：什么共享、什么按标准复制

| 对象 | 跨标准共享？ | 判据与理由 |
|---|:--:|---|
| **L0 属性池** `cert_clause_attr_def` | ✅ **共享**（8 行，只有一份） | `Obligation` 在 4 个标准里是**同一个概念**（约束强度）。复制 4 份 ⇒ 改一处要改四处，且四份的语义会漂移 |
| **L1 条款配置** `cert_clause_attr` | ❌ 按标准独立 | 条款本身按标准独立；同号条款要求不同（`8.5.1` 在 9001 是「生产和服务提供的控制」，在 13485 还叠加医疗器械特殊要求） |
| **预生成提示词** `wf_prompt_template` | ❌ **按标准一份** | 见 §0.4 |
| **L2 企业实际值** | ❌ 按标准独立 | 唯一键含 `StandardCode`（25 号 §4.3） |
| **L3 证据 / 判定 / NC** | ❌ 按标准独立 | 一张 NC 只能引用一个标准的条款；合并 ⇒ 报告无法按标准拆分 |
| **企业文档结果**（规范化产物） | ❌ **每标准一份** | 见 §0.5 |
| **企业基础资料**（营业执照/组织图/设备清单） | ✅ **只存一份** | 不因标准变化；但**只共享原始资料，不共享结论** |

> **判据（一句话）**：**换一个标准，这个东西还成立吗？** 成立 ⇒ 共享；不成立 ⇒ 按标准复制。
> 这与 §二「拆表判据」（是否同时描述「标准要求」与「某企业实际」）是两条正交的判据，都要过。

### 0.4 为什么「一个标准一份提示词」

不是洁癖，是四条硬理由，每条都有实测依据（§十二 附录）：

1. **术语按标准分册。** `成文信息` 29 条**全在 9001**；`记录` 44 条**全在 13485**；24001/45001 用 `文件`。一条提示词写「识别成文信息」，在 13485 上会漏掉全部 44 条记录要求 —— **且不报错**。
2. **义务动词分布不同。** `必须` 19 条**只在 45001(13) / 24001(6)**，9001 和 13485 一次不用。提示词只举 `应` 的例子，模型在 45001 上会把「必须」当普通陈述。
3. **条款粒度不同。** 13485 有四级条款（`7.5.5 灭菌`、`7.5.6 污染控制`），9001 只到三级。提示词里「一条款 = 一个检查项」的示例，在 13485 上会诱导模型把两个特殊过程合成一条。
4. **换版只换一本。** 9001:2015 → 2026 换版时，只需新写一份 `iso9001` 提示词 + 重跑该标准；另外 3 个标准的配置与结果**完全不动**。共用一条提示词则「改一处 = 全库重跑」。

**反面实证（本项目自己踩的）**：v1/v2 用**一条平台级提示词**跑 4 个标准，实测 `Obligation` 恒 `shall`（连「1 范围」这种没有义务动词的条款也是）、`Process` 恒 `management`（连 7.1.5.2 计量条款也是）。根因就是「一条提示词要同时覆盖四本书，只能给最通用的答案」。

**机制（已实现）**：`PromptWorkbenchService.ResolveActiveAsync(type, standardCode)` 按 **标准级 → 平台级** 回退。

| 层级 | `wf_prompt_template.StandardCode` | 命名 | 用途 |
|---|---|---|---|
| 标准级 | **标准 GUID**（非空） | `clause_attr_iso9001_v1` | 正式生产：该标准专属判据与示例 |
| 平台级 | `NULL` | `clause_attr_v2` | **只作新标准试跑 / 兜底**，⛔ 不作为长期生产 |

> ⚠️ **回退必须可见**：用了平台兜底时，生成结果里必须标明「本标准尚无专属提示词」（`PromptScope=platform`）。⛔ 不许静默降级 —— 否则用户以为跑的是本标准提示词，4 个标准跑出同一种味道还以为是模型问题。

### 0.5 企业选 3 个标准 = 3 份结果

**白话**：企业拿三张证书 = 三个认证项目。审核员按标准分开判定、分开开 NC、分开出报告 —— 这是发证规则决定的，不是我们想不想合的问题。

| 如果合并 | 后果 |
|---|---|
| 一份《质量手册》同时声明符合 9001 + 13485 | 审核时无法把某段文字对应到某一个标准 ⇒ 一条证据同时"证明"两件事 ⇒ 判定不可复核 |
| 一张 NC 挂两个标准的条款 | 报告按标准拆分时归属不明；整改验证也不知道该验哪一本 |
| 企业值表只存一份 + `StandardCodes` JSON 列 | 9001 要求「有」、13485 要求「全」时，**一个 `ValueState` 装不下两种结论** |

**但「3 份结果」≠「3 倍工作量」**，必须分清三件事：

| 层次 | 处理 | 说明 |
|---|---|---|
| **基础资料**（营业执照 / 组织机构图 / 厂区平面图 / 人员名册 / 设备清单） | **读一次、存一份**，3 个标准都引用 | 不因标准变化，重复上传是纯粹的负担 |
| **标准结果文档**（质量手册 / 程序文件 / 内审与管理评审记录） | **每标准一份**，⛔ 不复制第 1 份的「结论」 | 内容 80% 相似，但条款号、术语、要求出处不同 |
| **审核场次** | **可以合并**（一体化审核：一次现场、一个审核组） | 但 `cert_check_result` / `cert_check_evidence` 仍按 `StandardCode` 分行 ⇒ **一次审核，三份结论** |

### 0.6 ⚠️ `StandardCode` 三种口径（最易踩，且不报错）

同一个列名，在不同表里含义不同。⛔ 拿短码去匹配 GUID **不会报错，只会静默零命中**。

| 表 · 列 | 存什么 | 例 |
|---|---|---|
| `cert_iso_standard.StandardCode` | **短码** | `iso9001` |
| `cert_iso_standard.Code` | GUID | `c9d3e1f5-2a68-4b7c-8e04-5a1b7f3d9c62` |
| `cert_iso_clause.StandardCode` | **GUID**（= 标准 `Code`） | `c9d3e1f5-…` |
| `cert_clause_attr.StandardCode` | **短码** | `iso9001` |
| `wf_prompt_template.StandardCode` | **GUID**（= 标准 `Code`） | `c9d3e1f5-…` |
| 企业侧表（待建） | **GUID** | 与 `cert_iso_clause` 同口径 |

**规则三条**：

1. **与 `cert_iso_clause` 同查询出现（`ClauseCode` 是 GUID）⇒ 一律用 GUID。** 企业侧所有表都属此类。
2. `cert_clause_attr` 是**唯一存短码**的表 —— 因为它的入口是「标准 → 条款」树，树节点 `Code` 就是短码；跨口径处**必须显式换算**（`ClauseAttrController` 第 273 行已做），代码注释要写明「⛔ 不能直接传短码」。
3. `wf_prompt_template` 传参**必须用 GUID** —— 已修：`ClauseAttrGenerateService` 原传 `null`（永远只取平台级），现传 `standard.Code`。

> 待裁决 **D-N12**：`cert_clause_attr.StandardCode` 是否统一为 GUID（与 `cert_iso_clause` 同口径）。当前短码口径已闭环，改 GUID 属技术债清理，需同步改前端树与生成入参。

### 0.7 五条红线

1. ⛔ **企业侧任何表的唯一键不含 `StandardCode`** ⇒ 多标准企业必然串数据，且串了查不出来。
2. ⛔ **用 `StandardCodes` JSON 列代替按标准分行** ⇒ 一个 `ValueState` / 一个 `Verdict` 装不下多个标准的结论。
3. ⛔ **一份文档结果声明符合多个标准** ⇒ 审核无法拆分判定。
4. ⛔ **平台级提示词长期顶替标准级而不告警** ⇒ 4 个标准跑出同一种味道，质量退化无人发现。
5. ⛔ **把 L0 属性池按标准复制成 4 份** ⇒ 语义漂移 + 改一处漏三处。

## 一、两层（人的模型）

| 类比 | 系统里是什么 | 表 | 量级 |
|---|---|---|---|
| **属性池**：所有人的所有可能属性（姓名、年龄、学历、执照、宇航员训练） | 属性全集 | `cert_clause_attr_def` | **30–50 行，不怕多** |
| **职业定义**：工程师需要学历 + 编程 + 项目经验，**不含宇航员训练**；并注明"学历要验证、编程看项目" | 某条款用哪些属性 + 值 + **这个值固定还是参考** | `cert_clause_attr` | 每条款 5–12 行 |

### 三个推论

1. **池子大、配置小。** 池子 30–50 条不嫌多，因为每个条款只挑自己那几条。池子小了反而会想"拿身体部位凑"，属性就不干净。
2. **"挑哪几条"不需要额外字段。** 没挑 = 没行 = 稀疏。属性池**不加**"适用条款"之类的列。
3. **"这个值是不是固定的"只能在条款配置时定。** 同一条属性在不同条款下可能固定、也可能参考（§六 有两个反例）。属性池若自带 `ValueSource`，就只能取一个值 —— 必然错。

## 二、两层各回答一个问题

| 层 | 唯一的问题 | 绝不回答 |
|---|---|---|
| **L0 属性池** | 世界上**有哪些**属性、值类型是什么、干什么用 | 哪条款用它 · 它是不是固定值 |
| **L1 条款配置** | 这条款**用哪些**属性、值是什么、**这个值固定还是参考** | 这家企业实际是什么 |

> **拆表判据**：任何一张表，如果它的行既描述「标准要求」又描述「某企业实际」，它就该拆。本文两张表都在"要求"侧，企业侧是下一步。

## 三、L0 属性池 `cert_clause_attr_def`

### 3.1 字段（一个属性 = 一行）

| 字段 | 类型 | 必填 | 说明 |
|---|---|:--:|---|
| `Code` | varchar(50) | ✅ | 属性码，**业务键**（`Obligation`） |
| `AttrName` | varchar(100) | ✅ | 属性名（约束强度） |
| `ValueType` | varchar(20) | ✅ | 值类型，5 种，见 §3.2 |
| `DictCode` | varchar(50) | | 值域字典码；`dict` 必填 |
| `Remark` | varchar(500) | | **这个属性干什么用**（一句话，给人看） |
| `IsValid` | tinyint | ✅ | 是否启用（停用而不删） |
| `Sort` | int | ✅ | 展示顺序 |
| + 审计列 | | | `IsDeleted`/`CreateBy`/`CreateTime`/`UpdateBy`/`UpdateTime` |

**业务列只有 4 个**：`AttrName` / `ValueType` / `DictCode` / `Remark`。

⛔ **不设 `ValueSource`** —— 见 §六。
⛔ **不设 `PoolLayer`** —— 池子不分层，一个大池子。
⛔ **不设 `AppliesTo`** —— 挑哪几条 = 有没有行。
⛔ **不设"必填集"** —— 不在代码里规定"7 章条款必须有这 8 条属性"。

### 3.2 值类型只有 5 种

| `ValueType` | 落库形态 | 例 |
|---|---|---|
| `text` | 一段文字 | 条款作用、适用条件 |
| `dict` | 单个字典码（值域来自 `DictCode`） | 约束强度 = `shall` |
| `bool` | `"1"` / `"0"` | 是否需要现场核实 |
| `json` | JSON 字符串，**结构由代码强类型定** | 过程（受控词表多选）等**纯结构化**值 |
| `prompt` | 一段提示词文本 | **企业资料提取、证据链取证**（见 §3.3）；内部仍要求 LLM 输出结构化 JSON |

**为什么没有 `int` / `date`**：认证判定里没有"拿一个数字比大小""拿一个日期比早晚"这种动作。条款要求的是"有没有、全不全、对不对"，不是数值比较。真有需要时再加，不预先臆想。

**为什么没有 `text_multi` / `dict_multi`**：多值就是 JSON 数组，`json` 一种装得下。多一种类型 = 多一处解析分支、多一处出错点。

### 3.3 `prompt` 类型：属性值本身就是提示词

这是本设计里**最重要的一种值类型**。理由：

- 条款要求是自然语言，写成固定 JSON 清单必然丢信息。
- 企业真实资料的文件名五花八门（`04-记录文件/03监视和测量设备控制记录`），固定清单认不出来。
- 同一条款不同企业的资料组织方式不同 —— **只有语义提取能覆盖**。

所以 `Artifacts` / `EvidenceChain` 这类"要从企业资料 / 证据链里认出什么"的属性，**值就是一段可执行的提示词**。

#### 三条铁律

1. **提示词内部必须要求输出结构化 JSON** —— 灵活性在前端（怎么找），结构在后端（存什么）。
2. **提示词只产"读到了什么"，不产结论** —— 结论归判定（`cert_validation_rule` + 双引擎）。
3. **找不到就输出空，禁止推测** —— 这是「未见 ≠ 不符合」在提示词层的落地。

#### 提示词可以引用联网 Skill

值里可用 `{{skill:国家监督抽查}}` 占位，运行时注入该 Skill 的查询结果（详见 26 号）：

> 参考【国家监督抽查】结果：若该企业近 3 年有不合格记录，**必须**核查整改闭环（整改报告、验证记录）。
> {{skill:国家监督抽查}}

> 这样专家端的一部分证据就能**直接来源于公共服务**，而不必全靠企业自述。

### 3.4 第一批种子（8 条）

| # | `Code` | 属性名 | `ValueType` | 作用 |
|:--:|---|---|---|---|
| 1 | `ClauseIntent` | **条款作用** | `text` | **给 LLM 做语义分析的锚点**（这条款到底在要求什么） |
| 2 | `Obligation` | 约束强度 | `dict`（`DICT_OBLIGATION`） | 能不能开 NC 的闸门 |
| 3 | `Applicability` | 适用范围 | `dict`（`DICT_APPLICABILITY`） | 通用 / 有条件 |
| 4 | `ApplicabilityCondition` | 适用条件 | `text` | 条件原文（求值由程序读企业事实做） |
| 5 | `Process` | **过程** | `json`（受控词表多选） | **这条款管哪些过程**（生产/销售/设计/采购/检验/计量/仓储/售后/人力/管理）→ 与部门取交集，见 §3.6 |
| 6 | `Artifacts` | **企业应提供的资料** | **`prompt`** | **① 企业侧**：从企业资料里认出该条款要的规范性文档/内审资料/记录，见 §3.5 |
| 7 | `EvidenceChain` | **证据链要求** | **`prompt`** | **② 审核员侧**：从证据链里抽取该条款的取证结果，见 §3.5 |
| 8 | `Severity` | 影响程度 | `dict`（`DICT_SEVERITY`） | 严重 / 一般 / 观察项 / 不算 |

> `Severity` 是唯一**语法推不出**的，必须靠法定分级 + 人判断。
> `prompt` 类型暂不预置种子 —— 用到哪个条款再配，避免凭空造提示词。

**这一版删掉的 3 条（都有明确理由，不是嫌多）**：

| 删掉 | 理由 |
|---|---|
| `RequirementItems`（分项要求 a/b/c） | 实测**找不到对应到 a/b/c 的检查证据** —— 真实检查报告里检查项就是整条款，不拆到分项。硬拆只会逼着人编细分 |
| `EvidenceKinds`（要求形态 doc/record/site/person） | 抽象层级不对，用户无法理解。它的作用被 **`Artifacts`（要什么）+ `EvidenceChain`（怎么查）** 两部分完整吸收 |
| `CheckModes`（检查方式） | "怎么判"是**判定规则**（`cert_validation_rule`），不是条款语义。放属性里会与规则表双真相（§7.1） |

### 3.5 ★ 任何一个条款 = 两份要求（这一节是属性池的骨架）

标准对同一个条款说了两件事，**给两拨人看**：

| 部分 | 给谁看 | 属性 | 产出什么 | 能不能公开 |
|---|---|---|---|---|
| **① 企业侧要求** | 企业 | `Artifacts` | "你要准备什么"清单：规范性文档、内审资料、记录 | ✅ 可以，企业本来就该知道 |
| **② 审核员侧要求** | 审核员 | `EvidenceChain` | "你怎么验"：看什么、问谁、抽几份 | ⚠️ **取证剧本，不提前给企业** |

**为什么必须分成两条属性，而不是一条**：

- 合成一条 ⇒ 企业照审核员的取证剧本去准备 ⇒ **审核失效**（企业知道只查 5 份，就只做 5 份）。
- 分成两条 ⇒ 企业只知道"要有什么"，不知道"会怎么抽"；审核员拿着取证剧本进场，才验得出真伪。

这也解释了 12 号 的实测：真实报告里 **89 个检查项**（审核员侧）与企业的**资料目录清单**（企业侧）是两套东西，从来没合并过。

#### `Artifacts`（企业侧）= 一段提取提示词

以 7.1.5.2 测量溯源为例，`Artifacts` 的值是：

> 从企业提交的资料中，识别与**测量设备**相关的台账与校准证书。
> 台账需含：设备编号、名称、校准日期、校准机构。
> 证书需含：设备编号、校准机构、有效期。
> 输出 JSON：`[{"kind":"台账|证书","fileName":"","deviceNo":"","validUntil":"","complete":true}]`
> 找不到就输出 `[]`，**不要推测**。

固定清单认不出 `04-记录文件/03监视和测量设备控制记录.pdf` 这种文件名，提示词能。

#### `EvidenceChain`（审核员侧）= 一段取证提示词

同一个条款：

> 请按三步取证：
> 1. **现场**：查看在用测量设备上是否有校准状态标识，记录设备编号与标识状态
> 2. **记录**：从校准证书中抽 5 台，抽取设备编号、校准日期、有效期，核对是否超期
> 3. **访谈**：询问设备管理员校准计划的编制依据、超期处理流程
> 输出 JSON：`[{"kind":"site|record|interview","action":"","target":"","sample":"","finding":""}]`
> **只描述观察到的事实，不下"符合/不符合"结论。**

#### 两者的输出结构（代码强类型，不在表里）

```csharp
public class ArtifactHit {          // Artifacts 的输出
    public string Kind { get; set; } = "";        // 台账/证书/程序文件/记录
    public string FileName { get; set; } = "";
    public string? DeviceNo { get; set; }
    public string? ValidUntil { get; set; }
    public bool Complete { get; set; }
}

public class EvidenceStep {         // EvidenceChain 的输出
    public string Kind { get; set; } = "";        // site/record/interview/doc
    public string Action { get; set; } = "";
    public string? Target { get; set; }
    public string? Sample { get; set; }
    public string? Finding { get; set; }          // 只记事实
}
```

> `EvidenceChain` **只描述"怎么取证、看到什么"，不描述"合格标准"** —— 合格标准归 `cert_validation_rule`。
> `Artifacts` **只描述"企业该有什么、找到的是不是它"**，不描述"够不够"。

### 3.6 `Process` 怎么落到企业部门（三步，中间靠受控词表）

条款**不是对所有部门都查**：7.1.5.2 只在管计量/设备的部门查，8.4 只在有采购的部门查，售后条款跟生产车间无关。

```
① 条款声明它管哪些过程      L1 `Process`（受控词表：生产/销售/设计/采购/检验/计量/仓储/售后/人力/管理）
② 企业部门声明它负责哪些过程  企业侧（专家端，暂缓）—— 按部门名称+职责映射，人工确认
③ 两边取交集               → "部门 × 条款"矩阵 → 入场计划
```

**关键：用受控过程词表做连接，LLM 只处理对不上的残余。**

| 做法 | 后果 |
|---|---|
| 两边都打过程码，取交集 | 可解释、可复核、可回归，零模型调用 |
| 直接拿「条款作用」自由文本去对部门名 | 每家新企业都要重跑；今天匹配上、明天改提示词就变；结果无法复核 |

> **归属**：① 是标准级（后台，本文范围）；② 是企业侧（专家端，暂缓）。所以本文只做前半段 —— 先把"这条款管哪些过程"配准，等企业侧就绪后取交集即可。

### 4.1 字段（一条款一属性一值）

| `AttrValue` | text | | **值，就这一个字段** |
| `IsValid` | tinyint | ✅ | 这条配置是否生效 |
| + 审计列 | | | 同 L0 |

**唯一键** `(StandardCode, ClauseCode, AttrCode)`；索引 `(StandardCode, ClauseCode)`、`(StandardCode, ValueSource)`。

⛔ **无 `ReviewStatus`** —— 用户指正：不知道是什么，删掉。
⛔ **无 `ClauseNumber`** —— `cert_iso_clause` 已有，显示时 join。
⛔ **无 `Confidence` / `Source` / `ValueState`** —— 那是企业侧（下一步）的事。

### 4.2 为什么值只有一个字段

值类型已在 L0 声明过（`Obligation` 是 `dict`，`Artifacts` 是 `prompt`）。再铺 `ValueCode`/`ValueBool`/`ValueJson` 多列 = **把同一个事实写两遍**，且必然打架：改了 L0 的 `ValueType` 忘了迁 L1 数据，两列都留旧值，**谁都不报错**。

读取时按类型解析，一处收口：

```csharp
object? Parse(string valueType, string? raw) => valueType switch {
    "bool"   => raw is "1" or "true",
    "dict"   => raw,
    "text"   => raw,
    "prompt" => raw,
    "json"   => raw is null ? null : JsonSerializer.Deserialize<JsonElement>(raw),
    _        => raw
};
```

### 4.3 要按值筛选怎么办

只有三个属性真需要（`Obligation` / `Severity` / `Applicability`，报表与覆盖率要用）。做法是**一个生成列**，不是铺多列：

```sql
ALTER TABLE cert_clause_attr
  ADD COLUMN `FilterCode` VARCHAR(100)
    GENERATED ALWAYS AS (
      CASE WHEN `AttrCode` IN ('Obligation','Severity','Applicability')
           THEN `AttrValue` END) STORED,
  ADD KEY `idx_filter` (`AttrCode`,`FilterCode`);
```

### 4.4 两种空（不是三种）

| 状态 | 表现 | 含义 |
|---|---|---|
| **未配置** | 没有这一行 | 还没提这条属性 |
| **明确无** | 有行，`AttrValue` 为空 | 提取过了，这条款确实不要求（7.3 无任何材料） |

> 原来的"待复核"随 `ReviewStatus` 一起删掉（用户指正 5）。
> "条款对这家企业不适用"也不在这张表 —— 那是企业侧判定，不是标准级配置。

### 4.5 量级

9 × 201 ≈ 最多 1,809 行；按稀疏实际约 **1,300 行**。

## 五、`ValueSource` 两档（只在条款配置上有）

| 档 | 含义 | L1 存什么 | 谁补 |
|---|---|---|---|
| **`fixed` 固定** | 条款已定，与哪家企业无关 | **值本身** | 专家读国标 |
| **`reference` 参考** | 条款只给"期望"，实际从企业取 | **期望**（要哪类材料） | 企业资料 + 专家证据链 |

### 为什么没有第三档「求值」

用户指正：**"求值"不是一个属性值的来源，是我们自己要写的复杂逻辑。**

- 适用性判断要读企业事实（有没有测量设备、有没有外包过程）+ 写代码求值，**不是一个字段能承载的**。
- 哪怕 `reference` 也一样：不可能"看到企业某一句话、看到一个文件名"就搞定。真实的认证判定都是规则 + 材料 + 人的判断叠出来的。
- 所以只保留两档，把"求值"交回程序，不塞进数据模型。

### `reference` 的值从哪来（两条合法路径）

| 路径 | 谁产 | 典型 |
|---|---|---|
| **企业资料** | 企业上传 + 匹配 | 校准证书、设备台账、内审记录 |
| **专家证据链** | 审核员现场/访谈采集 | 现场看标识、访谈班组长、抽记录 |

> 这两条路径属于**企业端**，本文不展开（§八）。

## 六、为什么 `ValueSource` 必须在条款配置上（用户指正 1 的正面论证）

同一条属性，不同条款，来源不同 —— 这是常态，不是例外：

| 属性 | 条款 | 条款级 `ValueSource` | 理由 |
|---|---|:--:|---|
| `Artifacts` | 7.1.5.2 测量溯源 | `reference` | 要企业交台账与校准证书 |
| `Artifacts` | 7.3 意识 | **`fixed`（值为空）** | 条款不要求成文信息，**明确无**，不是"待采集" |
| `Applicability` | 4.1 理解组织环境 | `fixed` = 通用 | 无条件限定 |
| `Applicability` | 7.1.5.2 | `fixed` = 有条件 | 原文"当要求测量溯源时"，这是条款自带的固定判断 |
| `Severity` | 5.1.1 总则 | `fixed` = 严重 | 法定分级 |

**如果 `ValueSource` 挂在属性池**（`Artifacts` 默认 `reference`），系统会向 7.3 的企业索要材料 → 拿不到 → 误判"企业没做"。这正是"硬去文件池搜必然搜不到"的机制性根因。

**"这条款适不适用"由程序算，不存属性**：

```
读 Applicability=有条件
  → 读 ApplicabilityCondition 原文
  → 程序按该条件去查企业事实（有没有测量设备）
  → 得出 适用 / 不适用
```

这个结果属于企业侧，不写回 L1。

## 七、与既有表的边界（裁决 22 号留下的三个矛盾）

22 号 指出库里有**三个平行体系**都在表达"标准要求"，必须裁决：

### 7.1 「怎么判」：`cert_validation_rule` 唯一

| 载体 | 处置 |
|---|---|
| `cert_validation_rule`（2 行，`RuleJson`/`JudgeMode`/`SeverityIfViolated`/`NcDescriptionTemplate`） | ✅ **判定执行只读它** |
| ~~属性 `CheckModes`~~ | ❌ **删掉** —— "有没有 / 全不全 / 对不对"是**判定规则**，不是条款语义 |

> 原设计想用属性 `CheckModes` 表达判定维度，但那与 `cert_validation_rule` 是同一件事的两种说法。同时存在 ⇒ 引擎每次要决定信谁，两边都不报错。

### 7.2 「要哪些文件」：文件体系 vs `Artifacts`

| 载体 | 表达 | 保留？ |
|---|---|:--:|
| `cert_standard_directory_config/_folder/_file`（93 个文件节点） | **具体文件节点** | ✅ |
| `Artifacts` 属性 | **企业侧要求类型**（这条款要"校准证书"这类东西） | ✅ 值=提示词，但**输出里的 `Kind` 必须落字典码 `ArtifactType`，不得回自由文本** |

> `Artifacts` = 类型（跨企业复用，用于匹配召回）；目录清单 = 实例（用于生成上传清单）。两者靠 `ArtifactType` 对齐，**不互相抄**。
> ⚠️ **V2.2 后的边界**：值改成提示词，不等于"输出随便写"。提示词的自由度只体现在**怎么找**，`ArtifactHit.Kind` 仍是受控码 —— 否则下游按类型聚合、材料级严重度、报告归类全部失效（这是 D-N8 与 D-N11 的交界处，别只批一半）。

### 7.3 「怎么认出这份文件」：`cert_standard_doc_contract` vs `MatchPrompt`

> **匹配契约跟文件走**（`cert_standard_doc_contract.MatchPrompt`/`Keywords`/阈值）。属性池⛔ **不放 `MatchPrompt`**。
> 理由：匹配的对象是文件，不是条款。

### 7.4 复用与不动

| 表 | 处置 |
|---|---|
| `cert_iso_standard`(5) / `cert_iso_clause`(273) | **不动**，L0/L1 都挂它 |
| `cert_validation_rule` | **不动**，§7.1 定为判定执行唯一来源 |
| `cert_standard_directory_*` / `cert_standard_doc_contract` | **不动**，§7.2/§7.3 定为文件侧唯一来源 |
| `cert_standard_directory_file` | **一表两义**（要求 + 实例状态），建议分期拆出实例状态表（22 号 D-K4） |

| **D-N8** | `Artifacts` 存字典码 `ArtifactType`？ | 是（§7.2） |
| **D-N12** | `cert_clause_attr.StandardCode` 统一为 **GUID**（与 `cert_iso_clause` 同口径）？ | **建议是** —— 现状短码能跑（`ClauseAttrController` 已显式换算），但「同名列两种口径」是长期债；改需同步改前端树节点与生成入参（§0.6） |

## 十一、坑

1. **给属性池加 `ValueSource`** ⇒ 同一条属性在不同条款下来源不同（§六 的 `Artifacts`），池子只能取一个值，必然错。
2. **给属性池加 `AppliesTo` / 必填集** ⇒ 出现"池子说适用、条款配置没配"的双真相；也会逼着人"拿身体部位凑属性"。
3. **加 `int` / `date` 类型** ⇒ 认证没有数值/日期比较的判定动作，加了就要维护一条永远走不到的分支。
4. **把"求值"做成属性或第三档** ⇒ 适用性判断要读企业事实 + 写代码，不是字段能承载的；做成属性只会变成"填个值假装算过了"。
5. **企业侧字段回流**（`Confidence`/`Source`/`ValueState` 写进 L1）⇒ 一张表同时描述"标准要求"和"企业实际"，判断"要求 vs 实际"时无法区分。这是 V1 留下的债（`cert_standard_directory_file`），不许再犯。
6. **`AttrValue` 铺多列**（`ValueBool`/`ValueJson`/…）⇒ 同一事实写两遍，改类型时两边打架且不报错。
7. **把 `Artifacts` 和 `EvidenceChain` 合成一条** ⇒ 企业能看到审核员怎么抽、抽几份，然后只做那几份 ⇒ **审核失效**。这两条必须分开存（§3.5）。
8. **把 `Process` 做成独立表** ⇒ 又回到"属性 + 关系表"两套，L1 每次查询都要 join，且"属性说管生产、关系表没配"就是双真相。**它就是一条属性。**
9. **硬拆 a)/b)/c) 分项** ⇒ 实测找不到对应到分项的检查证据，拆出来的细分全靠编，反而降低可信度。真实检查项就是整条款。
10. **一条提示词打四个标准** ⇒ 术语/义务动词/粒度三处全错，且**不报错**：`成文信息` 在 13485 上认不出 44 条记录要求、`必须` 在 45001 上被当普通陈述。必须一标准一份（§0.4）。
11. **拿短码去匹配 GUID**（或反之）⇒ **静默零命中**，不抛异常、不报错。`cert_iso_clause` / `wf_prompt_template` 存 GUID，`cert_iso_standard` / `cert_clause_attr` 存短码（§0.6）。
12. **企业侧表按「一份结果」设计**（唯一键不含 `StandardCode`，或用 `StandardCodes` JSON 列）⇒ 多标准企业数据互串，且因为不报错，要等出报告时才发现（§0.7）。

## 十二、附录：国标条文的语法成分（208 条叶子实测）

> **迁移说明（2026-10-28）**：原 23 号 §二 已归档，其**唯一仍有价值的实测结论**迁到此处 —— 因为属性池之所以能"穷举"，依据就是这张表。⛔ 不要再引 23 号。
> **实测口径**：4 本标准共 273 条条款，其中叶子 208 条（`iso13485` 70 / `iso9001` 60 / `iso14001` 35 / `iso45001` 43）。

国标不是散文，是规范语体。它的每个"要不要做、做什么、怎么算做到"都由固定语法承载：

| 语法标记 | 命中条款 | 占比 | 它说明什么 |
|---|:--:|:--:|---|
| **应**（shall） | 201 | 96.6% | 强约束 |
| **必须**（shall 的另一种写法） | **19** | 9.1% | 强约束，**只出现在 45001(13) / 24001(6)** |
| **宜**（should） | 26 | 12.5% | 弱约束 |
| **可**（may） | 72 | 34.6% | 允许 |
| **注**（note） | 53 | 25.5% | 说明，不产生要求 |
| **当…时 / 适用时 / 必要时** | 71 | 34.1% | **有条件限定** |
| **a) b) c) 列举** | **147** | **70.7%** | 分项要求 |
| 成文信息 | 29 | 13.9% | 文件化要求（**全部在 9001**） |
| 记录 | 47 | 22.6% | 记录要求（**44 条在 13485**） |
| 程序 / 文件 | 95 | 45.7% | 文件化要求（13485/45001 的词） |
| 确定 / 建立 / 实施 / 保持 | 153 | 73.6% | 动作类型 → 判定方式 |
| 监视 / 测量 / 评审 / 评价 | 96 | 46.2% | 判定方式 |
| 定期 / 时间间隔 / 每年 / 至少 | 18 | 8.7% | **时间合规要求** |
| 最高管理者 | 24 | 11.5% | 责任主体 |
| 人员 / 能力 / 意识 / 知晓 | 77 | 37.0% | 人证型要求 |
| 供方 / 外部提供 | 25 | 12.0% | 外部对象 |

### 三个必须知道的发现

**① 70.7% 的条款是"分项式"的。** 近乎所有条款都写成 `a) … b) … c) …`。但**这不等于要拆成 a/b/c 检查项** —— 实测拿不到对应到分项的检查证据（真实检查项就是整条款），所以本模型**不建 `RequirementItems`**，见 §3.4。

**② `必须` 是 shall，但只在两本标准里出现。** 45001 用 13 次、24001 用 6 次，9001 和 13485 一次不用。**只正则 `应` 会把 19 条条款误判成"说明类"**。

**③ 术语按标准分册，词表不能共用。** `成文信息` 29 条全在 9001；`记录` 44 条全在 13485；24001/45001 用 `文件`。一套正则打四本书，必然在这本命中、在那本漏光，而且**不报错**。

### 不产生要求的条款

7 条叶子没有任何 `应/必须`：`1 范围`、`2 规范性引用文件`、`3 术语和定义`（各标准的第 1–3 章）。它们是说明章节，**不该配属性**。
**配置范围 = 208 − 7 = 201 条。**
