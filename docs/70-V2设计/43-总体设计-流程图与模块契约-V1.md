# 总体设计（V1）：流程图 · 模块契约 · 自洽校验

> **这份文档回答四个问题**：系统由哪些模块组成 · 每个模块干什么 · 模块之间传什么 · 这套模型自洽吗。
> **⛔ 本文不写表结构、不写字段、不写提示词正文**。模型定稿后，每个模块另开专题（`41/42` 是专题，等本文定稿再回填）。
> **评审用法**：先看图 → 再看模块 I/O 表 → 最后看 §五 自洽校验与 §六 待挑战清单。**图与 I/O 表对不上，就是设计有问题**。

---

## 零、一句话

> **企业交资料 → 系统按条款读懂 → 按"检查项"逐项判断准备好了没有 → 人去现场验证 → 出报告。**
> 全系统的原子是**条款**（国标编号），执行单位是**检查项**（条款组 × 部门组，在编计划时定死）。

**图上看三件事**
1. **F2 是分水岭**：它之前都是"企业有什么"，它之后都是"该查什么"。检查项在这里产生，**后面没有任何模块能自己组合条款与部门**。
2. **F6 是收口点**：切片、查询、人工三类证据在这里汇合；**没有 F6，F7 没有内容可排**。
3. **F8 与 F6 同构**：同一个检查项、同一批表，只是证据来源从"系统收"换成"人现场补"，提示词从"完备性"换成"符合性"。
4. **F6 与 F7 是可选环节**（见 §八）：图上的箭头是"可以这样走"，不是"必须这样走"。可以从 F2 直接跳到「补证据 → 分析 → 判定」。

## 二、模块清单（15 个）

### 2.1 知识层 K（平台级 · 无企业）

| 模块 | 作用 | 输入 | 输出 | 消费者 |
|---|---|---|---|---|
| **K1 标准与条款** | 登记国标，维护条款树与正文 | 国标原文 | 标准 + 条款（编号/标题/父级）| K3、F2、F4 |
| **K2 属性池** | 定义"条款可以有哪些维度"（9 条）| 人工维护 | 属性定义（含取值要求）| K3、F4（渲染提示词）|
| **K3 条款配置** | 给某条款挂属性值（条款 × 属性）| K1 条款 + K2 属性 + AI 预生成 | 属性值（材料清单/证据剧本/严重程度/资料要求…）| F4、F6、F8 |
| **K4 提示词模板** | 提示词唯一来源，按代码分作用域 | 人工维护 | 提示词正文 | F4、F6、F8、F9 |

> **K 层的规矩**：⛔ 不知道任何企业。一旦 K 层出现 `EnterpriseCode`，模型就坏了。

### 2.2 业务主链 F（企业级 · 按流程）

| 模块 | 作用 | 输入 | 输出 | 消费者 |
|---|---|---|---|---|
| **F1 企业与组织** | 企业档案、部门树、部门人员、审核组、阶段 | 人工录入 | 企业身份 + 部门清单 + 人员 | F2、F3、F5、F6、F7 |
| **F2 认证计划** | 一企业一有效计划：企业 × 阶段 × 标准；**明细 = 检查项** | F1 | **检查项清单（条款组 × 部门组）** | F6、F7、F8 |
| **F3 企业资料** | 上传 → 转换（PDF/Markdown）→ 版本；**不带阶段、不带标准** | F1 + 文件 | 文件 + Markdown + 指纹 | F4、F5 |
| **F4 文档条款化（L1）** | 一份文档 × 一个标准 → 该文档提到哪些条款、原文是什么、在第几页 | F3 + K1/K3/K4 | **条款切片（事实 + 锚点）** | F6、F8 |
| **F5 公共查询** | 一次查询一个任务，可多行参数（如 20 人）；可独立/嵌入 | F1 + 查询定义 | 查询结论（含"未查/无记录/失败"三态）| F6、F8、独立查看 |
| **F6 认证准备**（可选）| 按检查项汇证据 → LLM 判完备性 → 缺口/疑点/必不必须/验证程度 | F2 + F4 + F5 + K3 + K4 + 人工 | **检查项结论 + 疑点 + 预计时长** | F7、F8、报表 |
| **F7 入场计划**（可选）| 滤掉合格 → 按部门分组 → 人填时间与人 | F6 + F1 | 排班（日期/时段/人 × 检查项）| F8 |
| **F8 认证检查** | 现场按检查项补证据 → LLM 判符合性 → 预 NC | F7 + F4 + F5 + 现场证据 | **判定（符合/观察/不符）+ NC 建议** | F9、F6（回填）|
| **F9 检查报告** | 汇总 + 冻结成快照 → 签发 | F8 | **报告（不可变快照）** | 交付/归档 |

### 2.3 支撑 S（横切）

| 模块 | 作用 | 输入 | 输出 | 消费者 |
|---|---|---|---|---|
| **S1 AI 执行** | 模型调用、队列执行、用量与失败重试 | 任务（类型 + 作用域）| 结果回写 + 用量 | F4、F6、F8、F9 |
| **S2 平台与权限** | 用户/角色/菜单/接口/字典/日志/机构 | 人工配置 | 登录态、菜单、权限、字典 | 全部 |

## 三、关键建模决定（评审就评这 10 条）

| # | 决定 | 理由 | 推翻它的代价 |
|:--:|---|---|---|
| **D1** | **检查项 = 计划明细**，不另建表 | 计划页面本来就在编"条款组 × 部门组"（勾条款树 + 勾部门树 = 一项）；再建一张就是重复建模 + 两份数据会不一致 | 低（还没建）|
| **D2** | 证据**挂检查项**，条款只是维度 | 一条款分给两个部门 = 两个检查项，证据链与入场计划都不是一回事 | 高（证据归属全错）|
| **D3** | 一检查项 = 一任务 = 一队列项 | 失败单条重跑、进度按状态统计、**不需要批次表** | 低 |
| **D4** | 资料**不带阶段**（阶段只活在计划里）| 237 份文件实测全挂同一阶段，企业资料本身与阶段无关；硬绑必错位 | 高（要迁数据）|
| **D5** | 标准**跟条款走**，检查项可跨标准 | 整合审核时同一条款号出现多标准，按批次分标准会切碎检查项 | 中 |
| **D6** | 部门**来自计划**，准备阶段不推断 | 部门是检查项身份的一部分；推断必错，且已有人工定好的地方 | 中 |
| **D7** | 两阶段**同构**（一套结构、两套提示词）| F6 与 F8 都是"检查项 × 证据 → 判定"，只差证据来源与判断标准 | 中 |
| **D8** | **NC 独立于检查项** | 一个检查项可开多张 NC；同根因的两部门问题可合并一张；NC 有整改→验证→关闭生命周期 | 中 |
| **D9** | 报告**快照冻结** | 报告要盖章归档，实时查询会让"已签发的报告自己变" | 低（加一张表）|
| **D10** | V1 一律**不碰** | V2 并行跑，V1 稳定后再清；混改后出问题无法回滚 | 高 |
| **D11** | **流程非强制**：F6 认证准备、F7 入场计划都是**可选步骤**，可从计划直接到“补证据 + 分析 + 判定” | 真实使用中没人能被强制走完五步；且我们需要一条**最短路径**快速验证模型与提示词 | 高（菜单与状态机全部受影响）|
| **D12** | **菜单按“操作粒度”拆，不按“阶段”拆**：单点操作进**检查项工作台**，批量操作才是准备/检查两个菜单 | 阶段菜单会逼人“必须经过准备”；工作台则天然允许跳过——准备不在就不显示准备结果 | 中 |
| **D13** | **判定落在条款级，检查项级只是汇总** | 真实检查报告就是“一条款一判定”（`N 8.3`）| 高 |
| **D14** | **任务只记执行记录，不承载检查项与证据**（两个方向共享证据池）| 检查项 = 计划明细、证据挂检查项 ⇒ 派生任务不需复制任何数据 | 中 |

## 四、模块契约（输入输出的硬约束）

| 契约 | 内容 | 违反后果 |
|---|---|---|
| **C1** | K 层 ⛔ 出现任何 `EnterpriseCode` | 条款知识被企业污染，无法跨企业复用 |
| **C2** | 只有 F2 能产生检查项；F6/F7/F8 ⛔ 自行组合条款与部门 | 检查项身份分裂，入场计划对不上 |
| **C3** | F6/F8 ⛔ 直接读 F3 的原始文件，只读 F4 的切片 | 装配逻辑分裂两处，页面依据与喂给模型的不一致 |
| **C4** | F7 ⛔ 决定"查什么"，只决定"何时谁去" | 入场计划变成第二套条款清单 |
| **C5** | F9 ⛔ 实时 join F8，只读快照 | 已签发报告会变 |
| **C6** | 系统 ⛔ 自动开 NC / 自动判不合格，只出建议 | 责任边界破了（辅助系统不担责）|
| **C7** | 判定必须三档：符合 / **观察项** / 不符合 | 现实检查记录就是三档，缺一档会逼人塞备注 |
| **C8** | 端不互引：Admin ⛔ 引 Auditor，共用只经 Shared | 两端无法独立部署 |

## 五、自洽校验（这套模型能不能闭环）

> **自洽的定义**：每个输出都有消费者；每个输入都有生产者；依赖图无环；没有"两处真相"。

### 5.1 每个输出都有消费者

| 输出 | 消费者 | 有没有孤儿？ |
|---|---|:--:|
| K1 条款 | K3、F2、F4 | ✅ |
| K2 属性定义 | K3、F4 | ✅ |
| K3 属性值 | F4、F6、F8 | ✅ |
| K4 提示词 | F4、F6、F8、F9 | ✅ |
| F1 企业与部门 | F2、F3、F5、F6、F7 | ✅ |
| F2 检查项 | F6、F7、F8 | ✅ |
| F3 文件/Markdown | F4、F5 | ✅ |
| F4 条款切片 | F6、F8 | ✅ |
| F5 查询结论 | F6、F8（+独立查看）| ✅ |
| F6 结论 + 疑点 | F7、F8、报表 | ✅ |
| F7 排班 | F8 | ✅ |
| F8 判定 + NC | F9 | ✅ |
| F9 报告 | 交付 | ✅ |

### 5.2 每个输入都有生产者

| 模块 | 输入 | 生产者 | 缺口？ |
|---|---|---|:--:|
| F4 | Markdown | F3 | ✅ |
| F4 | 条款清单 | K1 | ✅ |
| F4 | 提示词 | K4 | ✅ |
| F6 | 切片 | F4 | ✅ |
| F6 | 查询结论 | F5 | ✅ |

| F9 | 判定 + NC | F8 | ✅ |

### 5.3 依赖图无环

```
K1→K3→F4←F3←F1→F2→F6←F5←F1
                    F6→F7→F8→F9
                    F8→F6（回填疑点，⚠️ 见下）
```
- 主链 **无环**；
- **唯一的反向边**：F8 把现场发现回填给 F6（补充疑点）。**允许但必须单向且留痕**——检查阶段的发现不得改写准备阶段的结论，只能"追加证据 + 追加疑点"。

### 5.4 有没有"两处真相"（最容易出错的地方）

| 概念 | 唯一真相 | 副本（只读/快照）| 校验 |
|---|---|---|---|
| 检查项身份（条款组×部门组）| **F2 计划明细** | F6/F8 读时 join | ⛔ 不许在 F6 复制一份可编辑的条款部门 |
| 条款属性 | **K3** | 提示词渲染时读取 | ⛔ 不许在提示词正文里写死属性值 |
| 提示词正文 | **K4** | 无（每次读）| ⛔ 不许有第二张提示词表 |
| NC | **D8 独立表** | 报告快照里存一份 | 已签发报告不得随 NC 变化 |
| 判定 | **F8**（现场）| 报告快照 | 准备阶段的 `判定建议` 不是判定 |

> ★ 上面 5 行是本设计最容易出问题的地方。**它们同时也是 41/42 两版被推翻的原因**（我曾把检查项复制成快照、把部门做成本表推断、把判定塞进检查项字段）。

## 六、待挑战清单（请多 AI / 多人就这 6 条开火）

| # | 问题 | 我的倾向 | 需要什么证据才能定 |

| **② 边界评审** | 每模块"做什么 / ⛔ 不做什么"一页 | 任意两人对"这条需求归谁"答案一致 |
| **③ 单模块专题** | 一次只做 1 个（先 F4 或 F6）| 输入输出与本图一致；表结构在该专题里定 |
| **④ 多任务并行** | 按专题拆给多个 AI | 每个专题只改自己模块，契约 C1–C8 不被破 |

> **⛔ 现在不要做的**：定表结构、写提示词正文、建菜单。**模型一旦改，这些都要重做。**

## 八、流程非强制：三条路径与菜单拆分（D11 / D12）

> **核心问题**：不能要求每个审核员都走“准备 → 入场计划 → 检查”。他们可以拿到计划就直接补证据、让 AI 出疑点与 NC。
> **但底座不变**：不管是哪条路，落的都是同一套数据 —— **检查项 + 证据 + 判定 + 疑点**。**流程是可选的组织方式，不是数据的先决条件。**

### 8.1 三条合法路径（同一底座）

```
路径 A · 全流程（完整辅助）
  计划 → 资料+提取 → 准备（完备性）→ 入场计划 → 检查（符合性）→ 报告

路径 B · 最短闭环（快速验证模型与提示词）★
  计划 → 补/取证据 → 分析（符合性）→ 疑点 + 预 NC → 报告草稿
         （跳过资料提取、跳过准备、跳进入场计划）

路径 C · 半程（常见：先准备后直接出报告，不做现场排班）
  计划 → 资料+提取 → 准备 → （跳过入场）→ 补充证据 → 分析 → 报告
```

**三条路都成立的前提**：

| 前提 | 含义 |
|---|---|
| 证据可来自任意源 | 文档切片 / 公共查询 / 人工补（可传图）/ 现场 |
| 分析可任选一种或两种都跑 | `完备性`（缺不缺资料）与 `符合性`（做没做到）**互不依赖** |
| 判定不依赖前提 | 人随时可以填“符合/观察/不符合” |
| 报告只要求有判定 | 不要求入场计划存在 |

### 8.2 菜单拆分原则（回答“怎么拆”）

| # | 原则 | 反例（会把人逼进单行道）|
|:--:|---|---|
| M1 | **按操作粒度拆**：单点 → 工作台；批量 → 专题菜单 | “准备任务”“检查任务”各做一套详情页 |
| M2 | **一个菜单只做一件事**，且能**单独使用** | “认证检查”里同时管排班、补证、判定、报告 |
| M3 | **只有一个事实工作台**：检查项工作台，所有入口最终落到它 | 准备页能改判定，检查页也能改，两处不一致 |
| M4 | **可选步骤跳过后不留空洞** | 没跑准备就在页面上显示一堆空白“准备结果” |
| M5 | **菜单不表达顺序**，顺序靠数据就绪度提示 | 用灰色未启用菜单暗示“你得先做上一步” |

### 8.3 三菜单模型（用户定稿 2026-10-30）

> **用户口径**：一个**认证任务**可以开**认证准备**任务，也可以开**认证检查**任务；不同任务对应不同界面；
> 在认证检查里针对该任务挂证据链 → 下一步认证分析 → **分析后可以返回补证据 → 再分析**。

```
               ┌───────────────────────┐
               │ ① 认证任务             │  任务列表（企业 × 计划 × 审核类型）
               │ 一个任务下可开两个通道： │
               └───────┬───────┬───────┘
                       │       │
             ┌─────────▼──┐  ┌─▼────────────┐
             │ ② 认证准备  │  │ ③ 认证检查    │   同一批检查项，两套界面 + 两套提示词
             │ （可选）    │  │ （可单独开）  │
             │ 系统收证据  │  │ 人现场补证据  │
             │ 完备性分析  │  │ 符合性分析    │
             └────────────┘  └──────┬───────┘
                                    │
                          挂证据 ⇄ 分析（可反复）
```

| 菜单 | 干什么 | 能否单独用 | 为什么需要它 |
|---|---|:--:|---|
> 🔁 **2026-10-30 定稿修正（用户）**：**不建“认证任务”菜单** —— **计划即入口**，计划完成后从计划行派生两个**独立任务方向**，**少一个菜单**。

```
  ✅ 认证计划（唯一入口）
        │ 计划完成后 → 派生（二选一或两个都开）
        ├──────────────▶ 【认证准备任务】方向
        └──────────────▶ 【认证检查任务】方向   ← 当前优先实现
```

| 菜单 | 干什么 | 与计划的关系 |
|---|---|---|
| **认证计划** | 编检查项（条款组 × 部门组）| **唯一入口**；未完成不得开任务 |
| **认证准备** | 列表 + 批量跑**完备性** | 由计划派生；可不建 |
| **认证检查** | 列表 + 挂现场证据链 → 跑**符合性** → 预 NC | 由计划派生；**可单独开**；启动时判断是否复用已有证据 |

**两个方向共用一个检查项与一份证据池**（见 §8.7）——“派生两个任务”而不是“两套数据”。

**检查项详情不单独做菜单**，而是两个方向里点进去的**同一个工作台页**（条款/部门/属性 + 证据 + 分析 + 判定 + 疑点 + NC）。菜单只有 3 个，工作台只有 1 个（满足 M3）。

**采集与输出不属这 3 个菜单**（而是各自独立、可从任务内跳转）：企业资料 / 公共查询 / 入场计划 / 检查报告。

### 8.4 这样能解决“非强制”，但三处必须定死

| # | 必须定死的事 | 为什么 | 我的建议 |
|:--:|---|---|---|
| **A** | **"认证任务"与"认证计划"是什么关系** | ~~现在已有计划（企业 × 阶段 × 标准），再加任务会重复或层级混乱~~ | ✅ **已定稿（44 号 §2.1）**：`cert_task` 是独立表 + `TaskKind`。**任务通过 `PlanCode` 指向计划**，计划是入口，任务由计划派生。同一企业多次审核 = 同计划下多个任务（`TaskNo` 区分）。~~原"先不新增任务实体"已推翻。~~ |
| **B** | 准备/检查是**两张表还是一张表** | 两套表 = 两倍代码；而“跳过准备直接检查”时要复制数据 | **一张子任务表 + `TaskKind`(prep/onsite)**；菜单只是筛选 + 换提示词 |
| **C** | “补证据 → 再分析”怎么不丢历史 | 审核员会问“上次 5 个疑点，这次 3 个，为什么” | 每次分析写一条**分析记录**（证据指纹 + 提示词版本 + 产出摘要），在新证据后标上次结果 `stale`；**疑点保留不删**，只标来源批次 |

> ★ **A 已定稿**：`cert_task` 是独立表（44 号 §2.1），**任务通过 `PlanCode` 指向计划**。计划是入口，任务由计划派生。~~原"先不新增任务实体"已推翻~~——任务表已建，菜单"认证计划"是入口，派生"认证准备"和"认证检查"两个方向。

### 8.5 衔接机制（回答“怎么接”）

**唯一衔接物 = 检查项 `Code`（即计划明细 `Code`）**。不靠“上一阶段完成”判定，靠**三个就绪度**：

| 就绪度 | 取值 | 谁推进 | 页面怎么用 |
|---|---|---|---|
| **证据就绪** | `none` / `partial` / `ready` | 证据增删（任意来源）| `ready` 才建议跑分析 |
| **分析就绪** | `none` / `done` / `stale` | 跑过任一分析；证据变化后置 `stale` | `stale` 显“结果可能过期” |
| **判定就绪** | 空 / `pass` / `ofi` / `nc` / `na` | 人填写 | 非空才进入场计划/报告集合 |

**事件流（无阶段状态机）**：

```
证据新增/删除 ──▶ 分析就绪 = stale（若有旧结果）
      │
      ├─ ★ MD5 变化检测（44 号 G5）
      │   ├─ PrevContentMD5 ≠ 新 MD5 → 证据内容被修改
      │   │   ├─ 触发影响分析，写 cert_impact_log
      │   │   ├─ 关联任务项 RerunState = 'suggested'（含变化明细）
      │   │   └─ 全部锁定项 → 跳过（LLM 节流）
      │   └─ MD5 未变 → 无操作
      │
      ▼
跑分析（完备性或符合性，任选）──▶ 产出：疑点 / NC 建议 / 判定建议 ──▶ 分析就绪 = done
      │
      ├─ ★ 锁定检查（44 号 G4）
      │   ├─ IsLocked=1 的结论行 → 不覆写，保留原人填结论
      │   └─ cert_analysis.LockedSkippedCount 计数（LLM 节流指标）
      │
      ▼
人填判定 ──▶ 判定就绪非空 ──▶ ① 进入场计划过滤器 ② 进报告集合
```

**把“跳过”变成正常路径的文案**（M4）：
- 未跑完备性分析 ⇒ 工作台显示：`未做资料完备性分析 · 可直接补证据后跑符合性分析`
- 未建入场计划 ⇒ 报告页显示：`未排班（不影响报告生成）`
- ⛔ 不显示空白表格、不弹“请先完成上一步”。

### 8.6 ★ 两方向共享证据池（派生任务不用复制证据）

> **关键结论**：因为 **检查项 = 计划明细**，而**证据挂检查项**，所以**两个方向的证据天然同一个池**。
> “认证检查引用认证准备的证据”**不需要引用表、不需要复制、不需要迁移** —— 它本来就在那里。

```
              计划明细 = 检查项（唯一身份）
                     │
        ┌────────────┴────────────┐
        │                         │
   准备任务                      检查任务
  （完备性分析）                 （符合性分析）
        │                         │
        └────────┬────────────────┘
                 ▼
        证据池（挂检查项，共享）
   doc_slice / pq_result / lead / onsite
```

**唯一需要区分的是“这条证据是哪个阶段采的”**：`cert_evidence.CapturedIn` = `prep` / `onsite` / `manual` / `doc` / `pq`（表与字段定稿见 44 号）。

**启动认证检查时的判断规则**（用户口径：启动时再判断）：

| 情形 | 处理 |
|---|---|
| 已有准备任务且证据非空 | 直接进入检查；工作台顶部提示“已复用 N 条准备期证据”，**不弹窗、不要求确认** |
| 已有准备任务但证据为空 | 正常进入；提示“未找到可复用证据” |
| 无准备任务 | 正常进入；提示“未做资料完备性分析 · 可直接补证据后跑符合性分析” |
| 准备期证据在入现场后被推翻 | **不删**，改 `Status=dropped` + 理由；现场新证据 `CapturedIn=onsite` |

**两个方向的任务只记“执行记录”，不改检查项身份**：

| 表 | 内容 |
|---|---|
| `cert_task` | 任务头（合并 + `TaskKind`=`prep`/`onsite`）：`PlanCode` + 状态 + 进度 + 提示词版本（理由见 44 号 §四 P2 判据）|
| `cert_task_item` | **任务 × 检查项**：执行状态 + `RerunState`（建议重跑）+ `RunMode`（含锁定节流）|
| `cert_analysis` | **分析记录**：`TaskItemCode` + 证据指纹（含 ContentMD5） + `LockedSkippedCount`（LLM 节流指标） + 产出摘要 |
| `cert_impact_log` | **影响分析日志**：文档重传 / 证据修改 → MD5 变化 → 影响哪些检查项 |

> 三张都是**追加型记录**，不承载条款/部门/证据本身 ⇒ 加任务不会产生"两份检查项"。

### 8.7 判定粒度：条款级（已用真实报告定下）

**证据**：`审核检查报告汇总.xlsx` 的判定列与条款同列（`Clause | Requirements | Audit Evidence | NC/OFI`），例如 `N 8.3`、`合格 8.5.2` ⇒ **真实业务就是“一条款一判定”**。

| 层 | 判定 | 说明 |
|---|---|---|
| **条款层（权威）** | `cert_check_result.Conclusion` = `pass`/`ofi`/`nc`/`na`（`CheckItemCode + ClauseCode`）| 人在这里填；NC 引到这一层 |
| **检查项层（汇总）** | 现算，不落列 | 按优先级自动汇总：有 `nc` ⇒ `nc`；否则有 `ofi` ⇒ `ofi`；否则 `na` 多于 `pass` ⇒ `na`；否则 `pass`。**人可覆盖** |

> ★ 同一行还有 `PrepState`（准备期四态 `found`/`partial`/`missing`/`unknown`），**准备与检查结论同行并存、字段各有归属** —— 这就是“看准备看准备、看检查看检查，且互不覆盖”（44 号 §五 G1–G3）。
> ★ **结论行不带 `TaskCode`**（用户 2026-10-30 定稿：任务可反复执行）—— 结论属于**检查项**，历史靠 `cert_analysis` 追加。

**这条决定了检查方向的最小实现**：列表要按条款展开，进度按条款统计，NC 必须引条款。

### 8.8 最短闭环（用于快速验证模型与提示词）

**路径 B 的可执行版本（建议作为第一个可跑版本）**：

| 步 | 操作 | 依赖 |
|:--:|---|---|
| 1 | 建计划（8 个检查项）| 已有 |
| 2 | 工作台点「取证据」= 文档切片 + 公共查询（有什么用什么）| F3/F4/F5 有啥用啥 |
| 3 | 点「跑分析」选 **符合性**（或两种都跑）| 证据非空即可，**不要求 ready** |
| 4 | 看疑点 + 预 NC 建议 | —— |
| 5 | 填判定 → 出报告草稿 | —— |

> **这条路径只需要：计划 + 工作台 + 两个提示词 + 报告模板。**
> 它不依赖入场计划、不依赖准备菜单、甚至不依赖文档提取（可全靠人工证据）。
> ⇒ **模型与提示词能不能用，一周内就能知道；不被五步流程拖死。**
