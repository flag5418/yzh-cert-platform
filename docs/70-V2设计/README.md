## 一、V2 与 V1 的本质区别

| 维度 | V1 | **V2** |
|---|---|---|
| **核心** | 工作流引擎 + 文档规范化 | **标准条款及其属性** |
| **能力** | 人工配置规则 | **属性推导**（属性 → 匹配 → 判定 → NC） |

| **模型** | 以文档/任务为中心 | **以条款为唯一原子；一切都是条款的函数** |

## 四、六条已确认的核心结论（不再重开论证）

1. **条款是唯一原子**；检查项 = 条款（实例可多，定义唯一）
2. **属性是资产，条款树是消耗品** —— 标准换版靠流水线重跑，不靠人工维护
3. **属性必须稀疏** —— 不是每条填满，很多条款只约束 1–2 个维度
4. **配置层无机构**；机构差异只进提示词与组合/拆分规则；**提示词只消费属性，不生产属性**
5. **归属是匹配的结果，不是上传时的输入** —— 这是"缺口发现"能自动化的唯一原因
6. **准备逻辑只需 6 个属性**：条款作用 / 适用范围 / 适用条件 / 要哪些材料 / 取证要点 / 证据形态

### 2026-10-26 追加的三条（用户四条补充的结论）

7. **a/b/c 不拆成检查项** —— `分项要求` 只是 NC 措辞的**引用字典**；判定粒度落在**材料级**（缺台账 major vs 缺标识 minor）
8. **过程域在标准级，部门在企业级** —— 「过程域 → 部门」必须经企业级映射；部门**绝不**进标准库（V1 犯过这个错）
9. **阶段是标准级，抽样是机构级** —— 且 **S1 不能开正式 NC**（`cert_cert_stage` 已写明"仅出发现/关注事项"），判定引擎必须按阶段切换输出类型

### 2026-10-26 第二轮追加的三条

10. **文档匹配必须靠语义，不能靠文件名** —— 实证：真实企业文件名/编号里**一个条款号都没有**（`04-记录文件/03监视和测量设备控制记录` → 7.1.5）；匹配结果必须带**可解释的可信度**
11. **只引用一手国标原文** —— 「一阶段覆盖 30%」已因引用二手资料而撤回；`依据/` 目录下的原文才可引用
12. **「未见」≠「不符合」** —— CNCA-QMS-01:2025 §5.11.3 要求报告含「抽样过程的免责声明」；未匹配/未取证**绝不能**自动推导为 NC

来源：[02](./02-条款核心架构与属性抽象-V1.md) · [03](./03-两阶段审核流程-V1.md) · [04](./04-条款属性字典-技术版-V1.md) · [05](./05-条款属性存储设计-V1.md) · [07](./07-条款属性模型补充-合并·过程·阶段-V1.md) · [09](./09-阶段检查要求的国标依据-V1.md) · [10](./10-文档匹配设计-语义匹配与可信度-V1.md)

### 2026-10-26 第三轮追加的三条（对标真实检查报告）

13. **条款×部门 = 1.33×** —— 中安质环 A 公司 79 页报告：**89 个检查项实例 ÷ 67 个唯一条款 = 1.33×**（与 36 号 76 行样本的 1.29× 互相验证）；同一条款最多被问 **10 次**（`5.3`/`6.2` 在 5 部门 × 2 体系全部出现）⇒ **按条款建项必丢部门归属**
14. **检查项不只有条款** —— 真实报告存在 **6 类无条款号的检查项**（资质验证 / 国家监督抽查 / 申投诉 / 安全环保事故 / 法规执行 / 最高管理者访谈）⇒ `ClauseCode` **必须可空**，另设 `ItemKind`
15. **「不适用」在实践中从不记录** —— 79 页全文 `不适用` **0 次**、`观察项` **0 次**、`建议项` **0 次**，NC 只有 **N 一种标记**（无分级）⇒ 我们保留分级，但**默认不填**；同时必须补 `na + NaReason` / `skipped + SkipReason` / `none_found` / `closed_history` 四态，否则报告无法自证覆盖

来源：[12](./12-与机构实际检查报告对标-V1.md)

### 2026-10-26 第四轮追加的三条（粒度 · 组织 · 证据风格）

16. **粒度默认 = 条款树叶子，合并是例外** —— 实测 19001 的 40 个三级条款中 **25 个（62.5%）被审核员合并回二级**，且同一分支内两层并存（`7.1` 拆到三级、`7.1.5` 又合回二级）⇒ 规则不是"机械取最深"，而是「**停在这一层能不能用一份证据问完**」；判据可用 `Artifacts` 重合度计算，**不需要标准级预置合并组**
17. **合并要分两级** —— **定义级合并**（几条款合成一个检查项，改变清单与工时，计划阶段定）vs **记录级合并**（几项共用一段记录，只影响写法，记录阶段定）；两者必须分开建模，否则"检查项数"与"证据条数"永远对不平
18. **配置层无机构 ≠ 机构无配置** —— 条款/属性/粒度默认值**无机构**；证据形态/提示词/合并习惯**有机构**；载体已存在（`cert_certification_body` + `wf_prompt_template` 带 `OrgCode`/`Version`），只需补 `cert_org_evidence_style`

来源：[13](./13-检查粒度与审核组织设计-V1.md)

### 2026-10-26 第五轮追加（两端边界，最上位的一条）

19. **★ 判据：这个东西换一家企业还用得上吗？** —— 用得上 ⇒ **后台**（标准 / 条款 / 条款属性 / 阶段检查标准 / 机构证据提示词）；只对这家企业成立 ⇒ **专家端**（企业部门 / 审核组 / 审核计划 / 检查单 / 入场计划 / 证据 / NC）。
    实证：`Sys_Menu.Tag` = `admin` **33 项** / `auditor` **15 项**；专家端 `organization` 是**机构内部成员**不是企业部门；`Sys_Department` 已于 2026-09-11 **主动删除**（那是机构内部部门，语义不同）。
    **同一维度两层**（照抄已正确的「阶段」范式）：`cert_cert_stage`(后台定义) → `cert_org_stage`(后台机构关联) → `cert_enterprise_stage`(**专家端实例**)。

来源：[14](./14-两端职责边界-V1.md)

## 五、实施路线摘要

> 完整路线图见 [00-总体设计-V1.md](./00-总体设计-V1.md) §十一。

```
第一步  后台：条款属性 4 表（补 D34 三列）+ 菜单         ← 不依赖专家端，可立即开工
第二步  后台：阶段×条款（cert_iso_clause_stage，已建）
第三步  后台：机构证据提示词（cert_org_evidence_style + 新菜单）
第四步  专家端：企业部门（cert_enterprise_dept）          ← D28，后面全依赖它
第五步  专家端：审核组→计划→场次→检查项→结果/证据→匹配
第六步  联网查询公共服务上线
第七步  准备阶段自动化（入场计划+预NC）
第八步  检查逻辑双引擎上线
```

**关键**：前 3 步是后台，不依赖企业部门，**现在就可以开工**。
