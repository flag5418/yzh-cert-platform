# 反推评估：认证检查能否直接复用认证准备的结构（V1）

> **方法**：不从头设计检查阶段，而是**从"检查报告 + 预 NC"倒推**，看认证准备那 4 张表够不够。
> **结论**：**结构成立（约 85%），但"完全不用换"要改成两句话——结构只加 4 处，命名必须现在改。**
> **依据**：`41 号`（准备结构）· `34 号 §四`（入场计划）· **案例真检查记录实测**（§一）

---

## 零、结论先给

| 判断 | 结论 |
|---|---|
| 检查项作为两阶段共用单位 | ✅ **成立**（入场计划已经按 `CheckCode` 排班）|
| 条款维度承载判定 | ✅ **成立**（真实检查记录就是"条款 / 要求 / 审核证据 / 判定"四列）|
| 证据表承载现场证据 | ⚠️ **能，但缺结构化字段**（录音时长、转录文本、取证时间地点）|
| 结论字段承载 NC | ⛔ **不成立**——一个检查项可开 2 张 NC，一张 NC 可跨检查项 |
| 实时查询直接出报告 | ⛔ **不成立**——报告必须快照冻结 |
| 表名 `cert_prep_*` | ⛔ **现在必须改**（检查阶段复用，"prep"名不副实；建表后改名要迁移）|

---

## 一、反推第一步：真实检查记录长什么样（实测）

`docs/90-归档/案例资料/审核检查报告汇总.xlsx`（21 个工作表）的实际列结构：

```
| Clause 条款 | Requirements 要求 | Audit Evidence 审核证据 | NC/OFI 判定 |
```

判定列的**实际取值分布**（全表统计）：

| 取值 | 次数 | 含义 |
|---|:--:|---|
| `合格` | 77 | 符合 |
| `Y` | 70 | 符合（另一家机构的写法）|
| `OK` | 48 | 符合（第三种写法）|
| `OFI1` / `OFI2` / `OFI3` | 各 1 | **观察项**（编号）|
| `N` | 1 | 不符合 |

**两个硬事实**：
1. **真实检查表只有 4 列** ⇒ 我的 `check_clause`(条款) + `evidence`(审核证据) + `Conclusion`(判定) 一一对应 ⇒ **结构成立**；
2. **判定是三档**：符合 / **观察项(OFI)** / 不符合 ⇒ 我原来只有 `pass`/`fail`/`na`，**缺 OFI 这一档**。丢了它会逼审核员把观察项塞进备注——这正是要把结构定准的地方。

## 二、反推第二步：检查报告要什么（要素清单）

| # | 报告要素 | 现有结构能否承载 |
|:--:|---|---|
| 1 | 报告编号 / 审核类型（初次·监督·再认证）/ 审核日期 | ❌ 无（`cert_report` 表）|
| 2 | 审核范围、依据标准、审核组名单 | ⚠️ 部分（计划 + 人员表可拼）|
| 3 | 各部门检查记录（条款→证据→判定）| ✅ **完全够**（§一 已证）|
| 4 | 不符合项汇总（编号 / 事实 / 条款 / 严重程度 / 整改要求 / 期限）| ❌ **缺**（NC 是独立实体，§四-1）|
| 5 | 观察项汇总 | ⚠️ 需要 OFI 档位 + 疑点/观察的列表 |
| 6 | 首次/末次会议记录、审核人日 | ❌ 无（可放报告 JSON，不必建表）|
| 7 | 结论（推荐 / 有条件推荐 / 不推荐）| ❌ 无 |
| 8 | 报告一旦签发**不可变** | ❌ 实时查询会"报告自己改了" ⇒ **必须快照** |

> **一句话**：**报告正文的 80% 能从现有结构拼出来（第 3 行），但"报告壳 + NC 汇总 + 冻结"三样缺。**

## 三、两阶段同构：差异只有四条

同一批表，两个阶段跑不同的提示词、由不同的人补证据、后置动作不同：

| 维度 | 认证**准备** | 认证**检查** |
|---|---|---|
| **证据来源** | 文档切片 + **公共服务查询**（系统收）| **审核员入场后补填**（录音/照片/现场记录/访谈）+ 复用准备期证据 |
| **谁补证据** | 系统 → 审核员**后补**少量 | **审核员本人**（现场）|
| **闸门** | 证据齐 → 跑 LLM | 现场证据齐 → 跑 LLM |
| **提示词** | `prep_analyze`：完备性 + 缺口 + 疑点 + 必不必须 + 验证程度 | `onsite_analyze`：**符合性 + 预 NC**（事实 / 条款依据 / 严重程度 / 整改要求）**两套完全不同** |
| **LLM 后** | 审核员决定**如何安排入场**（过滤合格 → 按部门分组 → 填时间）| 证据齐后**多一步**：生成**检查报告** + **预 NC** |
| **产出** | 入场计划 | 检查报告 + NC 单 |

**这条对照表就是"两阶段同构"的全部内容**——结构一套，流程两条，提示词两套。你感觉"逻辑顺畅"，是因为**检查项这个单位在两个阶段都是"一件事"**。

## 四、必须补的 4 处（不改这 4 处，第 5 处就是往 Remark 塞字符串）

### 4.1 `cert_nc`（NC 单 · 新表）★ 最关键

**为什么不能塞进 `Conclusion`**：

| 场景 | 用 `Conclusion='fail'` 会怎样 |
|---|---|
| 一个检查项（含 4.2.4 + 4.2.5）两条款各违反 | 只能记一个"不合格"，**开不出两张 NC** |
| 同一条款在品质部、生产部都发现同类问题 | 两个检查项各一张 NC，但**客户要求合并成一张**（同一根因）⇒ 无法合并 |
| 整改与验证 | NC 有生命周期：开具 → 整改 → 验证 → 关闭（或升级为暂停）⇒ 需要一个可追踪状态，不是检查项的一个字段 |

| 字段 | 说明 |
|---|---|
| `NcNo` | NC 编号（报告引用）|
| `CheckCode` / `ClauseCode` | 来源检查项 + 条款（**多对多**：用 `cert_nc_link` 或 `CheckCodes` 逗号 + 主 `CheckCode`）|
| `FactDesc` | 不符合事实（客观描述，⛔ 不写原因分析）|
| `RequirementRef` | 违反的条款原文（引用，不改写）|
| `Severity` | `major` 严重 / `minor` 一般（⛔ 不用 critical，那是条款属性口径）|
| `CorrectiveReq` / `DueDate` / `Responsible` | 整改要求 / 期限 / 责任人 |
| `Status` | `issued` / `rectifying` / `verifying` / `closed` / `escalated` |
| `CloseEvidenceJson` / `ClosedAt` / `ClosedBy` | 关闭证据与留痕 |
| `Origin` | `ai_suggest`（预 NC）/ `manual` ⇒ **系统只建议，人签发** |

### 4.2 现场证据要结构化（扩 `cert_check_evidence`）

`EvidenceKind` 增加 `onsite_media`（录音/照片/视频）、`interview`（访谈记录）、`sample`（抽样记录）。

新增字段：

| 字段 | 为什么 |
|---|---|
| `MediaKind` | `audio` / `photo` / `video` / `note` / `sample` |
| `DurationSec` | 录音时长（排班复盘、成本核算）|
| `TranscriptText` | **录音转文字**（不给转录，LLM 无法用现场语音）|
| `CapturedAt` / `CapturedPlace` | 取证时间地点（飞检溯源）|
| `PresentPersons` | 在场人（⛔ 记录姓名，但报告里按角色表述）|

> 塞 `AttachmentsJson` 的后果：按类型统计做不了、"转录后喂 LLM"做不了、报告引用做不了。

### 4.3 报告必须快照（`cert_report` · 新表）

| 字段 | 说明 |
|---|---|
| `ReportNo` / `ReportType` | 编号 / 初次·监督·再认证 |
| `EnterpriseCode` / `PlanCode` | |
| `SnapshotJson` | **全量快照**（检查项 + 证据摘要 + NC + 结论），签发后只读 |
| `ReportVersion` | 版本（重签 = 新版本，旧版留档）|
| `Status` | `draft` / `issued` / `archived` |
| `IssuedBy` / `IssuedAt` / `SignedFileJson` | 签发人 / 时间 / 签章文件 |

**为什么必须快照**：报告要盖章归档。实时查询 ⇒ 三个月后有人改了某个检查项，**已签发的报告内容跟着变**，这在审计上是致命的。

### 4.4 判定档位要三档（改 `Conclusion` 值域）

| 值 | 含义 | 实测依据 |
|---|---|---|
| `pass` | 符合 | `合格` 77 / `Y` 70 / `OK` 48 |
| **`ofi`** | **观察项** | `OFI1` / `OFI2` / `OFI3` |
| `nc` | 不符合 | `N` |
| `na` | 不适用 | — |

## 五、命名裁决：`cert_prep_*` → `cert_check_*`（现在改，零成本）

检查阶段复用同一批表，叫 `prep` 就名不副实——将来每个新人都要问一次"检查阶段为什么用 prep 表"。

| 现在（41 号） | 建议 | 理由 |
|---|---|---|
| `cert_prep_check` | **`cert_check_item`** | 两阶段都叫"检查项" |
| `cert_prep_check_clause` | **`cert_check_item_clause`** | |
| `cert_prep_evidence` | **`cert_check_evidence`** | |
| `cert_prep_point` | **`cert_check_point`** | |
| — | 新增 **`StageKind`**（`prep` / `onsite`）| 区分阶段 |
| — | 新增 **`PrepStatus` / `OnsiteStatus`** 两个状态字段 | ⛔ 一个 Status 混两阶段会出错 |

> **现在改是零成本**（表还没建）；建完再改就要迁移 + 改 4 份文档 + 改所有引用。
> 与铁律零不冲突：这些都是 V2 新表，改的是自己的名字。

## 六、不换结构的边界（什么时候必须拆）

| 触发条件 | 拆法 |
|---|---|
| `cert_check_item` 超过约 **45 列** | 现场组拆 `cert_check_item_onsite`（1:1 扩展表）|
| 一个检查项要**多个审核员各自独立记录** | 拆 `cert_check_record`（一人一行，挂 `CheckCode`）|
| 报告要素继续膨胀（会议记录/审核人日/多机构模板）| 只进 `SnapshotJson`，⛔ 不建表 |

**目前都不触发**：一个检查项一个审核员、字段约 40 列。

## 七、风险

| # | 风险 | 盯法 |
|:--:|---|---|
| R1 | 同表两用 ⇒ 审核员看到 20 个不该看的空字段 | 页面/`EntityConfig` **按 `StageKind` 分组显隐**，不是一张大表单 |
| R2 | 直接查询出报告 | 一律走 `cert_report.SnapshotJson`，⛔ 不许报告页直接 join 实时表 |
| R3 | 预 NC 被当成正式 NC | `cert_nc.Origin=ai_suggest` 且 `Status` 从 `pending_review` 起，**人签发才 `issued`** |
| R4 | 两阶段状态互踩 | `PrepStatus` 与 `OnsiteStatus` 分开；⛔ 不复用一个 `Status` |
| R5 | 同一检查项被并发跑两次 | 队列 `ScopeKey = check:{CheckCode}` 做互斥（复用 yzh_queue）|

## 八、队列模型（你说的"一个检查项一个任务"，落地就是这样）

| 项 | 做法 |
|---|---|
| 任务单位 | **一个检查项 = 一个任务 = 一个队列项** |
| 驱动 | 复用 `yzh_queue`：`TaskType` = `prep_collect` / `prep_analyze` / `onsite_analyze` / `report_generate` |
| 锁 | `ScopeKey = check:{CheckCode}`（同一检查项不并发）|
| 进度 | `SELECT Status, COUNT(*) FROM cert_check_item GROUP BY Status`（**不需要批次表**）|
| 失败 | 单条改回 `pending` 重跑；⛔ 不回滚同批其他项 |
