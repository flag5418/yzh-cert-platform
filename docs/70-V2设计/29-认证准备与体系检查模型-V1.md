# 认证准备与体系检查模型（V1）

> **版本**：V1 ｜ **日期**：2026-10-28 ｜ **状态**：待裁决
>
> **定位**：规则侧已有"条款模型"（属性池 + 条款配置）和"文档模型"（文档要求 + 提取契约）。本文补**两个企业侧模型**：
> - **准备检查模型**：企业资料交上来之后，判断齐不齐、矛盾不矛盾、每个疑点该怎么解（远程补交还是现场取证）；
> - **体系检查模型**：审核员进场后，拿现场证据把疑点变成结论（确认 / 推翻 / 升级 / 降级）。
>
> **这一层存在的理由**：文档只是"企业说它做了什么"，不等于"它做到了"。准备阶段负责**发现缺口**，现场阶段负责**验证缺口**。两者共用一套判断提示词，输入不同。

---

## 零、四个模型与五个提示词，一张图

```
【规则侧】标准怎么要求
  M1 条款模型     属性池 → 条款配置（固定值 / 参考值期望）
                  └─ P1 条款属性预生成（clause_attr）
  M2 文档模型     这个标准该有哪些文档、该含什么
                  └─ P2 文档提取（doc_extract）→ 单文档事实

【企业侧】这家企业实际怎么样
  M3 准备检查模型  资料齐全性 → 跨文档一致性 → 疑点四分类 → 部门/沟通对象 → 预NC（现场任务建议交计划）
                  ├─ P3 准备检查（readiness，编排调用 P4）
                  └─ P4 条款判断（clause_judge，第一次调用：只有文档）
  M4 体系检查模型  现场证据入库 → 证据完善 → 疑点确认/推翻 → 正式NC
                  ├─ P4 条款判断（clause_judge，第二次调用：文档 + 现场）
                  └─ P5 机构证据生成（evidence_style：证据包 / 记录写法 / 抽样）

落地形态：规则侧是"知识资产"，企业侧是"数据 + 结论"；两边只通过契约连接。
```

**五个提示词家族，不是五个模型**：M1 用 P1；M2 用 P2；M3 用 P3（内部调 P4）；M4 用 P4 + P5。提示词全部存提示词工作台，按 `PromptType` 区分，按标准一份。

> **本文与 30 号的分工**：全系统总图（三类主体、认证准备、认证计划、审核组、企业部门、10 步主线）见 [`30-系统总体架构设计-V1.md`](./30-系统总体架构设计-V1.md) §六 / §七 / §八。
> 本文只讲**两个检查模型**本身（齐全性、一致性、疑点、证据、判定）；计划怎么生成、组织怎么建模，不在这里重复。

## 一、准备检查模型（M3）

> **前置不在本文**：企业研究（性质 / 产品 / 工艺 / 组织 / 职能 / 范围 / 删减）与**条款适用性裁剪**（适用 / 不适用 / 待确认）在 30 号 §七完成。本文从"画像已建、适用条款已定"开始。
> 没有前置，齐全性就会拿 273 条去比，把不适用的条款全算成"企业缺失"。

### 1.1 输入

| 输入 | 来源 | 说明 |
|---|---|---|
| 企业资料提取结果 | M2 / P2 | 每份文档 × 该标准一份，含 `clauseFacts`（条款级关键信息） |
| 内审资料 | 企业提交 | 内审方案 / 检查表 / 不符合项报告 / 纠正措施 —— **既是证据，也是疑点来源** |
| 条款配置 | M1 | 固定值 + 参考值期望（要哪些材料） |
| 文档要求 | M2 | 该标准该有哪些文档、该含哪些要素 |
| 企业组织 | 企业档案 | 部门列表 + 职责（过程 → 部门的映射基础） |
| 机构风格 | P5 / 机构配置 | 证据包结构、抽样口径、记录写法 |
| 阶段 | 审核计划 | 一阶段只出预NC，不出正式NC |

### 1.2 五步，顺序不能乱

```
① 齐全性：期望（标准侧的文档要求 + 条款的材料期望） × 实际（企业交了什么）
② 一致性：手册 / 程序 / 记录 三层是否自洽；同类文档之间是否矛盾
③ 疑点分类：每个缺口或矛盾，判定由谁去查（沟通 / 观察 / 询问 / 验证）
④ 部门与对象：按过程 → 部门取交集，给出沟通对象（角色，不是人名）
⑤ 预NC：满足三前置（适用 / 强制 / 证据完备）的才出预NC
```

> 入场计划不在这里排。它属于 30 号 §八：先按"能不能远程解决"分拣，再在阶段锁死的时间预算内排任务。本文只负责"找出疑点、说清每个疑点该怎么解"。

### 1.3 齐全性：三种"没有"，含义不同

| 状态 | 含义 | 处置 |
|---|---|---|
| `missing` | 国标要求有、企业确实没交 | 企业缺口（可开NC的必要条件之一） |
| `partial` | 有，但缺要素 / 过期 / 无审批 | 疑点，需现场核对或补交 |
| `unknown` | 我们没查到（没上传、没读到） | **绝不推NC**，先转"沟通"去索取 |

> 这三态是准备阶段最重要的产出。把 `unknown` 写成 `missing`，就是从"我们没查"变成"企业没有"，直接造成错判——这是最贵的一种错。

### 1.4 一致性：跨文档比对（单文档提取发现不了）

真实 NC 大量来自"三层不一致"：

| 类型 | 例 | 判据 |
|---|---|---|
| 纵向不一致 | 质量手册说"灭菌按 7.5.7 确认"，程序文件没有确认章节 | 要求存在、下游缺失 |
| 横向不一致 | 程序规定"每批灭菌"，记录显示"每周一次" | 规定 vs 执行频率不符 |
| 要素不一致 | 台账 12 台设备，校准证书只有 9 份 | 数量/编号/有效期对不上 |
| 版本不一致 | 作业指导书在用版本 A，受控清单登记 B | 版本与受控状态不符 |

> 一致性判断归 M3，不归 M2。M2 只看单份文档内部，看不到文档之间。

### 1.5 疑点四分类（准备阶段的核心产出）

| 类型 | 判据 | 谁去做 | 产出 |
|---|---|---|---|
| **沟通** `communicate` | 资料缺失但企业能补交 / 能书面说明 | 认证前，通过企业联系人 | 待索取清单（发企业，不建独立流程） |
| **现场观察** `observe` | 只能眼见为实：标识、状态、环境、设备、现场执行 | 审核员现场 | 观察任务（看什么、在哪看、抽几份） |
| **询问** `interview` | 需要人回答：职责、意识、授权、培训效果、决策依据 | 审核员现场 | 访谈提纲（问谁、问什么） |
| **验证** `verify` | 两处信息矛盾，必须交叉核对 | 现场或远程 | 核对清单（A 说法 vs B 说法） |

**四分类不是标签，是任务派发**：分类错了，要么白跑现场，要么该看的没看。

### 1.6 部门与沟通对象

```
条款声明它管哪些过程（Process，受控词表）
        ×
企业部门声明自己负责哪些过程（部门职责，人工确认）
        ↓
部门 × 条款矩阵
        ↓
每格给出：本部门要准备什么 / 会被问什么 / 需要谁在场
```

- 部门名一律用企业档案里的规范名（生产部 / 质量部 / 灭菌车间），不许模型自造（"制造部""车间"会被当成不同部门）。
- 沟通对象写**角色**不写人名：管理者代表、生产负责人、灭菌工序操作员、检验员、内审组长。
- 对不上的残余（部门没声明职责）才交模型判断，并标"待人工确认"。

### 1.7 交给计划的输入（排期不在这里做）

准备阶段的产出，最后喂给 30 号 §八 的排期：

| 交给计划的东西 | 说明 |
|---|---|
| 现场类疑点 | 观察 / 询问 / 验证 三类，每条带部门、对象、优先级 |
| 每条疑点的取证动作 | 看什么、问什么、抽几份 |
| 部门 × 条款矩阵 | 每个部门要查哪些条款、多少任务 |
| 必查项 | 法定必查（灭菌确认、内审、管理评审、投诉与不良事件） |
| 抽样建议 | 台账抽几台、记录抽几个月、批次抽几个 |
| 风险提示 | 系统性风险（同类缺口 ≥N 处、跨部门同条款） |

> 天/半天、先后顺序、人员分工由计划阶段按时间预算决定，不在准备阶段拍。

### 1.8 预NC：三前置，缺一不可

| 前置 | 读哪 | 判据 |
|---|---|---|
| 适用 | 条款配置 + 企业事实 | 不适用 ⇒ 停 |
| 强制 | 约束强度 | 非"必须/应" ⇒ 最多观察项 |
| 证据完备 | 文档 + 现场 | 只有文档、无现场验证 ⇒ 只能 `draft` |

**S1 永远不出正式 NC**：一阶段只书面告知"潜在不符合"。

### 1.9 准备检查的输出契约

```json
{
  "completeness": [
    { "requirement": "灭菌确认报告", "clauseNumber": "7.5.7",
      "state": "missing | partial | unknown", "gapReason": "…", "expectedBy": "标准文档要求" }
  ],
  "consistency": [
    { "theme": "灭菌频次", "clauses": ["7.5.7"],
      "conflict": "程序写每批，记录显示每周一次", "severity": "major | minor" }
  ],
  "points": [
    { "kind": "communicate | observe | interview | verify",
      "mode": "remote | onsite",
      "clauseNumber": "7.5.7", "action": "抽查 3 批灭菌记录与再确认报告",
      "question": "…",
      "targetDept": "灭菌车间", "targetRole": "灭菌操作员",
      "priority": "high | medium | low", "why": "依据哪条缺口/矛盾",
      "estMinutes": 45 }
  ],
  "deptMatrix": [
    { "dept": "灭菌车间", "clauses": ["7.5.5", "7.5.6", "7.5.7"],
      "tasks": 6, "focus": "过程确认与灭菌记录" }
  ],
  "preNc": [
    { "clauseNumber": "7.5.7", "verdict": "nc | observation | pending",
      "severity": "major | minor | null", "reason": "…",
      "anchor": "记录显示灭菌日期…", "evidenceRefs": ["…"], "confidence": 0.0 }
  ]
}
```

> `preNc` 与 `points` 必须能互相追溯：每条预NC都要说明"还差哪一步验证"，否则现场不知道去补什么。

## 二、体系检查模型（M4）

### 2.1 输入

| 输入 | 来源 |
|---|---|
| 检查项（条款 / 条款组 × 部门 × 审核员） | 认证计划 |
| 准备阶段的疑点与预NC | M3 |
| 已匹配的文档事实 | M2 |
| 现场新证据（观察 / 访谈 / 记录 / 抽样） | 审核员录入 |
| 判定规则（维度 + 阈值） | 规则侧 |

### 2.2 证据完善：四问

| 问 | 不够时会怎样 | 动作 |
|---|---|---|
| **够不够** | 只有一个部门/一个批次 → 不能证明系统性 | 补抽 / 补部门 |
| **新不新** | 证据日期早于最近一次变更 → 不成立 | 要最近一期 |
| **一致不一致** | 现场说法与记录矛盾 | 转"验证" |
| **可否复核** | 没有锚点（时间/地点/人物/数值）→ 报告写不出来 | 补锚点 |

### 2.3 NC 疑点分析：五种走向

| 走向 | 触发 | 结果 |
|---|---|---|
| `confirmed` | 证据闭合，满足三前置 | 正式 NC（S2） |
| `refuted` | 现场证明资料缺失但有等效控制 | 关闭，记录理由 |
| `downgrade` | 约束强度非"应"，或仅单点 | 观察项 |
| `upgrade` | 同条款跨部门 minor ≥ N，指向系统性失效 | major 候选（人确认） |
| `pending` | 证据不足 / 需补充 | 留待补充，不得默认 NC |
| `uncovered` | 时间/资料不足，本轮没查 | 显式标注，不默认符合 |

> `pending` 必须写清"还缺什么"，否则会被当成"忘了判"。

### 2.4 输出契约

基础字段与 25 号 §6.3 的 `clause_judge` 契约一致（`verdict` / `severity` / `reason` / `anchor` / `evidenceRefs` / `confidence` / `missingInfo`），现场阶段增加疑点走向：

```json
{
  "clauseNumber": "7.5.7",
  "verdict": "conform | nc | observation | na | pending",
  "severity": "major | minor | null",
  "reason": "必须从证据长出",
  "anchor": "时间/地点/人物/数值 至少一项",
  "evidenceRefs": ["证据码"],
  "doubt": {
    "status": "confirmed | refuted | downgrade | upgrade | pending",
    "before": "准备阶段的疑点原文",
    "after": "现场看到的事实",
    "changedBy": "哪条证据改变了判断",
    "needMore": ["还缺什么"]
  },
  "systemic": { "sameClauseDepts": ["生产部", "灭菌车间"], "count": 2, "candidate": "major" }
}
```

### 2.5 机构证据生成（P5）在 M4 里的位置

P5 不管"该判什么"，只管"这家机构怎么组织这次取证与记录"：

- 证据包分册 / 命名 / 必备项；
- 记录写法（机构模板）；
- 抽样口径（抽几份、怎么选）；
- 覆盖要求（每个条款至少一条证据）。

所以 M4 的产出 = P4 的判断 + P5 的组织形式。两者不互相替代。

## 三、五个提示词家族（总表）

| 家族 | `PromptType` | 归属 | 输入 | 输出 | 调用时机 |
|---|---|---|---|---|---|
| 条款属性预生成 | `clause_attr` | 规则侧 | 条款正文 | 9 属性 | 建库时，一次性 |
| 文档提取 | `doc_extract` | 规则侧定义 / 企业侧执行 | 文档 Markdown + 文档要求 | 单文档事实（含 clauseLinks） | 上传后，每文档 × 每标准 |
| 准备检查 | `readiness` | 企业侧 | 全部文档事实 + 内审 + 期望 | 齐全性 / 一致性 / 疑点 / 部门 / 预NC | 入场前 |
| 条款判断 | `clause_judge` | 企业侧 | 条款属性 + 文档事实 + 证据 | 判定（含疑点走向） | 准备与现场各一次 |
| 机构证据生成 | `evidence_style` | 机构侧 | 条款属性 + 机构风格 | 取证剧本 / 证据包结构 | 排计划时 |

**编排关系**：`readiness` 负责"找疑点、排任务"，它对每条可疑条款调用 `clause_judge`（第一次）；现场补证后再调用 `clause_judge`（第二次），产出正式结论。两次调用同一模板、同一输出契约，只有 `evidence` 变量不同。

## 四、端到端时序（一企业三标准）

```
上传资料
  → P2 文档提取：每份文档 × 3 个标准 = 3 份结果（事实互不共享）
  → M3 准备检查（逐标准）：
       齐全性 → 一致性 → 疑点四分类 → 部门矩阵 → 预NC
       （内审资料同时作为证据与疑点来源）
  → P5 机构证据生成：把疑点排成取证剧本 + 证据包结构
  → 现场（一次审核，三个标准各自的结论）
       P4 clause_judge 第二次：文档 + 现场证据 → 确认/推翻/升降级
  → 报告（按标准拆分，基础资料共享，结论不共享）
```

**关键**：一次现场、一个审核组、三份结论。审核场次可以合并，结论不能合并。

## 五、红线（违反 = 返工）

1. `unknown` 当 `missing` 推 NC —— 把"没查到"变成"企业没有"。
2. 准备阶段直接出正式 NC（S1 只能预NC）。
3. 疑点不分类就排现场 —— 白跑或漏查。
4. 部门名由模型自造 —— 同部门被拆成两个，矩阵算错。
5. 沟通对象写人名不写角色 —— 人员变动即失效。
6. 一致性判断下放到单文档提取 —— 看不到文档之间。
7. 证据无锚点 —— 报告写不出来，NC 不可复核。
8. 同条款跨部门的多处轻微不聚合 —— 系统性失效被漏掉。
9. 一次现场出一份混合多标准的结论 —— 报告无法按标准拆分。
10. 用 `clause_judge` 判"合格标准" —— 阈值与模板归判定规则表。

## 六、验收（能拿真实资料验证）

| # | 验收项 | 判据 |
|---|---|---|
| 1 | 齐全性 | 期望清单里的每一项，都能给出 `found/partial/missing/unknown` 之一，无空 |
| 2 | 一致性 | 手册/程序/记录三层比对能产出矛盾清单，且每条能指到两份文档 |
| 3 | 疑点分类 | 每条疑点都有类型、对象、优先级、依据；四类都出现过分派 |
| 4 | 部门矩阵 | 每个条款至少落一个部门；部门名与企业档案完全一致 |
| 5 | 疑点可解 | 每条疑点都写明"远程补交 / 现场观察 / 现场询问 / 交叉验证"之一，且带部门与对象 |
| 6 | 现场判定 | 每条预NC都能被现场证据推进到"确认/推翻/待补"之一 |
| 7 | 可追溯 | 每条结论能回指证据 + 锚点；无锚点结论为 0 |
| 8 | 多标准 | 同一现场产出三份独立结论，字段不串 |
