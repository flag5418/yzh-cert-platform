# 标准条款属性字典与两逻辑主线（V1）

> 2026-10-26 ｜ 回应用户「第一步就是确定标准的属性」｜ 全流程主线定稿  
> 前置：[60-条款核心架构](60-条款核心架构与属性抽象设计方向-V1.md) · [61-两阶段流程](61-两阶段审核流程与条款四要素驱动-V1.md) · [62-辰泽拆解](62-辰泽智擎审核计划方案分析与借鉴-V1.md)  
> 结论先行：**属性是第一件事，而且必须是「稀疏」的** —— 很多条款只约束 1~2 个维度，填满反而是错的。按这个前提，属性只需 **5 组 16 项**；机构差异**不进属性**，只进**提示词**与**组合/拆分规则**。另有一条战略校准：**条款树是消耗品，属性是资产**。

## 一、全流程主线（先看这条，其余都是它的展开）

```
【标准级 · 唯一】
  标准条款 + 条款属性（5 组 16 项，稀疏填充，AI 生成 + 专家维护）
        │
        │  ← 机构提示词（按机构不同，作用于全部条款）
        │  ← 组合 / 拆分规则（机构级编排）
        ▼
【项目级 · 每家企业一次】
  ① 体系认证准备逻辑
       检查计划（检查项 = 条款 × 部门，可组合可拆分）
         → 缺口（期望集 − 已知集）
         → 疑点（按渠道分派）
         → 入场计划（什么时间 · 哪个部门参与 · 调研什么信息 · 补哪段证据链）
        ▼
  ② 体系认证检查逻辑
       证据链（文档 + 内审记录 + 现场：录音/照片/现场记录）
         → 逐项判定（分项要求级）
         → NC 候选
        ▼
  ③ 检查报告
```

**两个逻辑的分界**：准备逻辑回答「**该有什么、缺什么、去问谁**」；检查逻辑回答「**有的东西对不对、不对算几级**」。共用同一套属性，不共用同一套流程。

## 二、先纠一个概念：检查项 = 条款

你这次说「之前我不理解什么是检查项，现在理解就是条款」——这个纠正是对的，而且它解决了一个长期含混：

| 说法                       | 正解                                |
| ------------------------ | --------------------------------- |
| 检查项是**另一个东西**（比条款更细的新实体） | ❌ 错。检查项的**本质就是条款**                |
| 检查项 = 条款 × 部门            | ⚠️ 只对了一半 —— 那是**实例**，不是定义         |
| **检查项 = 条款**             | ✅ 对。条款是定义，检查项是它在某部门/某场次上的**落地实例** |

所以正确的表述是：

> **条款**是标准级的定义（无 `OrgCode`）；**检查项**是条款在「某企业 × 某部门 × 某场次」上的实例（有归属）。**实例可以有多个，定义只有一个。**

这直接决定了三件事：

1. 属性只挂在**条款**上，不挂在检查项上 —— 检查项只是引用条款
2. 「组合/拆分」是**检查计划生成时的编排动作**，不改变条款本身
3. 同一条款在不同部门查，**属性相同、证据不同** —— 差别只在证据，不在要求

## 三、属性字典（5 组 16 项）

> 标注：**必填** = 每条条款都要有；**可选** = 有才填（稀疏）。

### A 组 · 标识与意图（让机器知道"这条款管什么"）

| #      | 属性                            | 类型        | 必填     | 含义                | 谁消费                          |
| ------ | ----------------------------- | --------- | ------ | ----------------- | ---------------------------- |
| A1     | `StandardCode` + `ClauseCode` | 字符串       | **必填** | 标准 + 条款号（已有）      | 全部                           |
| A2     | `Title`                       | 字符串       | **必填** | 标题（已有）            | 展示                           |
| A3     | `Text`                        | 长文本       | **必填** | 国标原文（已有，208 条已回填） | 属性提取的输入                      |
| **A4** | **`Intent`** 作用               | 一句话 ≤60 字 | **必填** | 这条款要达成什么、管什么      | ★ **文档匹配主键** · 适用性推理 · NC 理由 |
| A5     | `RelatedClauses`              | 条款号数组     | 可选     | 弱关联（证据可复用，不合并检查项） | 证据复用                         |

**`Intent` 为什么必填**：企业文件不会写条款号，只会体现条款的作用。没有它，匹配只能靠文件名通配符。

### B 组 · 约束力（让机器知道"缺了算不算问题、要不要查"）

| #      | 属性                       | 类型  | 必填                     | 取值                                                                    | 谁消费                     |
| ------ | ------------------------ | --- | ---------------------- | --------------------------------------------------------------------- | ----------------------- |
| **B1** | `Obligation`             | 枚举  | **必填**                 | `shall` 应 · `should` 宜 · `may` 可 · `note` 注/指南                        | ★ NC 前置（只有 shall 能开 NC） |
| **B2** | `Applicability`          | 枚举  | **必填**                 | `universal` 通用 · `conditional` 有条件 · `scope` 按认证范围 · `na_by_org` 机构可裁 | ★ 要不要查                  |
| B3     | `ApplicabilityCondition` | 表达式 | 可选（B2=conditional 时必填） | 引用企业事实字段，如 `has_design_activity = true`                               | 适用性求值                   |

> ⚠️ **`Obligation` 必须规则优先**：国标里「应/宜/可/注」是语言标记，正则先抽，LLM 只补"无情态动词但实为要求"的句子。LLM 最易把「注」当 `shall`，而这一维错了后面全错。

### C 组 · 要求内容（让机器知道"要什么"）

| #      | 属性                   | 类型                                     | 必填 | 含义                                             | 谁消费                  |
| ------ | -------------------- | -------------------------------------- | -- | ---------------------------------------------- | -------------------- |
| **C1** | `RequirementItems[]` | `[{key:'a', text, mandatory}]`         | 可选 | 条款的**分项要求**（a/b/c…）                            | ★ **NC 定位到 a/b/c 级** |
| **C2** | `Artifacts[]`        | `[{name, type, mandatory}]`            | 可选 | 应有产物。`type`：程序 / 记录 / 报告 / 计划 / 清单 / 标识 / 现场状态 | ★ 展开期望集              |
| C3     | `Fields[]`           | `[{key, label, required, type, rule}]` | 可选 | 关键字段 —— **挂在产物上，不挂条款**                         | 字段级校验                |
| C4     | `EvidencePoints[]`   | 文本数组                                   | 可选 | 取证要点（检查单第 3 列）                                 | 生成检查项                |

**`RequirementItems` 是本轮新增，也是之前漏的**：一条款常含 a)~f) 多个子要求，NC 必须指到子项 —— 「8.5.1 c) 未提供监视测量记录」比「8.5.1 不符合」有用得多。国标里这种列举极普遍，没有它 NC 描述永远停在条款级。

### D 组 · 检查方式（让机器知道"怎么查"）

| #      | 属性             | 类型                     | 必填 | 取值                                                                                                                 | 谁消费               |
| ------ | -------------- | ---------------------- | -- | ------------------------------------------------------------------------------------------------------------------ | ----------------- |
| **D1** | `EvidenceKind` | 枚举（可多值）                | 可选 | `doc` · `record` · `field` · `site` · `person` · `system`                                                          | ★ 去哪个池子找 · 疑点渠道分派 |
| **D2** | `JudgeMode`    | 枚举（可多值）                | 可选 | `existence` 有无 · `completeness` 字段全 · `content` 内容符合 · `timeliness` 时间合规 · `consistency` 跨件一致 · `traceability` 可追溯 | ★ 选哪个引擎           |
| D3     | `Criteria[]`   | `[{type, expr, desc}]` | 可选 | 判据参数，如 `{type:'interval', max_months:12}`                                                                          | 判定参数              |
| D4     | `Depth`        | 枚举                     | 可选 | `single` · `sample` · `all` · `census`                                                                             | 查几份               |
| D5     | `Severity`     | 枚举                     | 可选 | `major` · `minor` · `observation` · `none`                                                                         | 出问题算几级            |
| D6     | `Question`     | 字符串                    | 可选 | 提问句（检查单第 2 列，由要求改写）                                                                                                | 生成检查单             |

### E 组 · 治理（让机器知道"这条属性可信吗"）

| #  | 属性                        | 类型       | 含义                                            |
| -- | ------------------------- | -------- | --------------------------------------------- |
| E1 | `Source`                  | 枚举       | `ai` / `expert` / `case`（从真实检查单反推）/ `import`  |
| E2 | `Confidence`              | 0~1      | AI 自评置信度                                      |
| E3 | `ReviewStatus`            | 枚举       | `draft` → `validated` → `reviewed` → `locked` |
| E4 | `ReviewBy` / `ReviewTime` | 字符串 / 时间 | **人工审核留痕**（`UpdateBy` ≠ 审核通过）                 |

## 四、★ 稀疏原则：三种「空」必须区分

你说「不是每个条款都一定有所有的属性，有些条款只限制其中 1~2 个」——这不是缺陷，是**常态**。所以模型必须支持稀疏，而且要区分三种"空"：

| 状态        | 存储                          | 含义              | 下一步            |
| --------- | --------------------------- | --------------- | -------------- |
| **未设置**   | `null`                      | 还没提取            | **待办**（进覆盖率清单） |
| **明确不要求** | `[]` / `none`               | 提过了，这条款确实不约束这一维 | 已完成            |
| **不适用**   | `Applicability = na_by_org` | 整条不适用           | 已完成            |

**为什么必须区分**：如果 `null` 和 `[]` 都当"空"，覆盖率永远算不清，而且会反复重提已确认的条款 —— 这是属性维护最常见的烂尾原因。

**稀疏到什么程度算正常**？三个真实例子：

| 条款            | 实际约束                                                          | 说明                                            |
| ------------- | ------------------------------------------------------------- | --------------------------------------------- |
| **7.3 意识**    | 只有 `Obligation` + `EvidenceKind=person` + `JudgeMode=content` | **无强制产物**（`Artifacts=[]`）。这就是"只约束 1~2 个属性"的典型 |
| **8.3 设计和开发** | 全维度                                                           | 条件型 + 6 个分项要求 + 多产物，属最重的一类                    |
| **9.2 内部审核**  | 全维度 + `consistency`                                           | 复合型，且要求跨件一致（计划 vs 报告 vs 整改）                   |

> **结论：不要用「填满 16 项」当目标。** 用「该条款约束的维度都填了」当目标 —— 而"该填哪些"由 `Obligation` + `Intent` 决定，不由模板决定。

## 五、属性 × 两个逻辑 用途矩阵

| 属性                    |    ① 准备逻辑    |    ② 检查逻辑   |
| --------------------- | :----------: | :---------: |
| A4 `Intent`           |    ★ 匹配主键    |   ★ NC 理由   |
| B1 `Obligation`       |   ○ 过滤 note  | ★ **NC 前置** |
| B2 `Applicability`    |  ★ **要不要查**  |     ★ 前置    |
| B3 `Condition`        |     ★ 求值     |             |
| C1 `RequirementItems` |    ○ 生成检查项   |  ★ **判定粒度** |
| C2 `Artifacts`        |  ★ **展开期望集** |    ○ 校验对象   |
| C3 `Fields`           |    ○ 期望集细化   |    ★ 字段校验   |
| C4 `EvidencePoints`   |    ★ 生成检查项   |    ★ 取证指引   |
| D1 `EvidenceKind`     | ★ **疑点渠道分派** |    ★ 载体选择   |
| D2 `JudgeMode`        |              |  ★ **引擎选择** |
| D3 `Criteria`         |              |    ★ 判据参数   |
| D4 `Depth`            |    ○ 计划工作量   |    ★ 抽样量    |
| D5 `Severity`         |              |     ★ 分级    |
| D6 `Question`         |     ★ 检查单    |    ★ 现场提问   |

**读法**：准备逻辑只重度依赖 **6 个**（`Intent` / `Applicability` / `Condition` / `Artifacts` / `EvidencePoints` / `EvidenceKind`），检查逻辑重度依赖另外 **6 个**（`Obligation` / `RequirementItems` / `Fields` / `JudgeMode` / `Criteria` / `Severity`）。

> **这就是分批填充的顺序**：先把准备逻辑那 6 个填到可用，准备逻辑就能跑；检查逻辑的 6 个随后补。不必等 16 个齐了才开工。

## 六、机构差异放哪：提示词是「消费者」，不是「生产者」

你说「按不同机构，可以有不同的提示词（针对所有条款）」。这句话必须钉死一个方向，否则属性会分叉：

| 层       | 谁定       | 内容                                           | 有 `OrgCode` 吗 |
| ------- | -------- | -------------------------------------------- | ------------- |
| **标准级** | 标准本身     | 条款 + **属性**                                  | ❌ 无           |
| **机构级** | 每家机构     | **提示词**（渲染检查单/问法/NC 措辞）· **组合/拆分规则** · 严重度加严 | ✅ 有           |
| **项目级** | 每家企业这次审核 | 检查计划实例 · 入场计划 · 证据链 · 报告                     | ✅ 有           |

> **提示词只消费属性，不生产属性。** 如果机构提示词能生成/改写属性，那"标准属性唯一"立刻破功 —— 同一份标准在不同机构下会长出不同的要求，这正好回到你反对的那件事。

若机构确需加严（比如某机构要求 8.3 必须看 3 份），走**机构级覆盖层**单独存（`SeverityOverride` / `DepthOverride`），求值顺序 **覆盖 > 属性默认**，且覆盖留痕、不回流标准属性。

### 组合 / 拆分 = 检查计划的编排动作

| 动作     | 场景                 | 效果                  |
| ------ | ------------------ | ------------------- |
| **组合** | 一阶段主题式审核；同部门同类条款   | 多个条款 → 一个检查项，共用一次取证 |
| **拆分** | 二阶段逐条；一条款涉及多部门/多场次 | 一个条款 → 多个检查项，分别取证   |

两者都是**机构级规则 + 项目级确认**，不改变条款属性。这也解释了 50 号那句「合并/拆分属检查项，不属条款属性」——现在可以说得更准：**组合/拆分是编排，编排作用在实例上**。

## 七、入场计划与报告的落点（补全你说的全流程）

**入场计划**（准备逻辑的终点）四个要素，全部可由属性 + 疑点推出：

| 要素         | 来自                                                      |
| ---------- | ------------------------------------------------------- |
| **什么时间**   | 疑点数量 × `Depth` 抽样量 → 估算工作量 → 排场次                        |
| **哪个部门参与** | 检查项的部门归属（来自企业文档编制/受控部门）                                 |
| **调研什么信息** | 疑点按渠道分派：`observe` 看什么 / `interview` 问谁 / `verify` 核对哪两份 |
| **补哪段证据链** | 未命中的 `Artifacts` 逐条列出                                   |

**检查报告**（检查逻辑的终点）：`RequirementItems` 给判定粒度，`JudgeMode` 给判法，`Severity` 给分级，`Intent` 给"为什么不符合"的理由句 —— 四者拼起来就是一条可复核的 NC。

## 八、生成与维护：条款树是消耗品，属性是资产

你这句话是对的：**标准每年可能变，所以条款树不是护城河**。据此调整两件事：

### 8.1 补 8 个节点 → 降级为「修解析器」，不手工补

62 号查出的 8 个缺失节点（`6.1.1/6.1.2/6.2.1/6.2.2/8.7.1/8.7.2/9.2.1/9.2.2`）根因不是数据错，是**解析器漏了「无标题编号段」**。

- ❌ 手工补 8 条 ⇒ 下次换版又要人工核一遍
- ✅ **修解析器规则（有编号即建节点）⇒ 重跑即得**，换版时同样一条命令

**结论：这不该是"补数据"任务，是"修流水线"任务。** 优先级降到与属性生成流水线一起做。

### 8.2 同一条流水线产出「条款树 + 属性」

```
标准 PDF
  → ① 解析：条款树（编号/标题/正文）        ← 修 §8.1 的解析器规则
  → ② 抽取：Obligation（正则，规则优先）
  → ③ 抽取：Intent / RequirementItems / Artifacts / EvidenceKind（LLM）
  → ④ 自检：必填项齐否 / 枚举合法 / 交叉一致
  → ⑤ 人工复核 → locked
```

这样"标准每年变化"就从**维护负担**变成**重跑一次**。这才是可持续的。

### 8.3 验收口径：不用"完整度"，用「检查单反推命中率」

因为属性是稀疏的，"填了 68%"没有意义。可验证的口径只有一个：

> 拿真实检查单（邝敏威那份，58 个「标准 × 条款」引用组合）反推：**属性展开后能否命中它实际用到的证据**。当前命中 57/58（`Q 6.1.2` 因节点缺失未命中，修解析器后应变 58/58）。

**属性任何改动都必须重跑这个回归集**，否则"改一条、悄悄改坏一片"永远发现不了。

## 十、一句话结论

**属性是资产，条款树是消耗品；属性要稀疏，机构差异要隔离。**

准备逻辑靠 6 个属性就能跑，检查逻辑靠另外 6 个 —— 所以第一步不是"把 16 个填满"，是**先把准备逻辑那 6 个填到可用**，跑通一条端到端，再补另一半。
