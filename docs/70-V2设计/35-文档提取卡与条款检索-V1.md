# 认证准备：文档提取 + 疑点自动生成 落地设计（V2）

> **版本**：V2 ｜ **日期**：2026-10-29 ｜ **状态**：待审批 ｜ **V2 取代 V1（含 V1.1 / V1.2 两次修正）**
> **本文只回答一件事**：企业资料上传之后，到"入场计划"之前，**疑点是怎么自动长出来的**。入场计划（34 号 §四）在这一步验收后再启动。
> **用户口径（唯一依据）**：
> 1. 提取按 **企业 × 标准** 跑；一份文档一份完整 JSON；**文档不变则提取结果不变**（计划/部门/条款调整都不触发重跑）。
> 2. 提取 JSON 里带 **本文档适用该标准的哪些条款**；条款按编号**一查就定位**到文档内容 —— 这是普通数据查询，不是模型工作。
> 3. 条款侧**收集齐该条款的相关信息后，再做一次判断/推理**（L2），产出疑点。
> 4. **GB/T 条款可以定义"是否需要检查企业资料"** —— 不需要的条款不进资料核对，疑点直接走现场。
> **上游**：27 号（条款无关提取）· 29 号 §一（齐全性/一致性/疑点四分类）· 24 号（属性池）· 30 号（总图）

## 零、先论证"这套设计能不能跑通业务"

| 业务问题 | 本设计怎么答 | 能不能通 |
|---|---|---|
| 企业交了几百份文档，怎么知道够不够？ | 每份文档提取时自报"我支撑哪些条款 + 该条款的事实与锚点" | ✅ 一次提取，长期复用 |
| 换计划 / 改部门 / 加条款，要重算吗？ | **不重算**。结果键 = `企业 + 标准 + 条款`，与计划无关 | ✅ |
| 条款多、文档多，会不会上下文爆？ | 筛选靠 SQL 查 `ClauseNumbers`；每个条款只取命中的那几份切片 | ✅ 单条款约 4k tokens |
| 哪些条款根本不用看资料？ | 新增属性 `DocCheckMode`，`none` 的条款跳过资料核对 | ✅ 省一半工作量 |
| 疑点从哪来？ | 一次 `readiness` 推理：够不够 / 矛不矛盾 / 该谁怎么查 | ✅ |
| 结论可信吗？ | 每条结论必须带锚点（页码/表号/日期/编号）；`unknown` 不推 NC | ✅ 可复核 |

> **结论：能通。** 唯一的前置是"条款属性要齐"（尤其 `Artifacts` 与新增的 `DocCheckMode`），否则提取侧不知道要找什么。

## 一、链路（四步，每步一个明确产物）

```
① 上传完成（文档转 Markdown 成功）
        ↓  增量触发（只跑新/变更文档）
② L1 文档提取   一份文档 × 一个标准 → 一份 JSON（含 clauses 切片）
        ↓  SQL：按条款号取切片（普通查询，无模型）
③ L2 认证准备   一个条款 + 该条款的全部切片 → 一次推理 → 缺口 + 疑点
        ↓
④ 疑点清单     按计划/条款/部门查看 → 喂给入场计划
```

**两个关键点**：
- ② 是"每份文档一次"；③ 是"每个条款一次"。**文档侧不做第二次模型调用。**
- ③ 的输入完全由 SQL 拼出来，模型只负责判断，不负责找。

## 二、条款属性新增一条：`DocCheckMode`（决定要不要查资料）

### 2.1 为什么是三态而不是布尔

"完全不需要资料"的条款极少（ISO 13485 大量要求"成文信息"）；更常见的是"资料只是辅助，主要靠现场"。所以：

| 值 | 含义 | 对链路的动作 |
|---|---|---|
| `required` | 该条款**必须**以文档证据为主（文件控制、记录控制、内审、管理评审、确认记录、投诉记录…） | 进资料核对；`unknown/missing` 即疑点 |
| `optional` | 文档可作辅助，但**现场才是主证据**（职责权限、人力资源、工作环境、生产控制…） | 进资料核对，但判定偏宽；疑点默认 `onsite` |
| `none` | 纯现场/纯访谈，**资料核对无意义**（如 4.1 总要求的承诺类内容） | **跳过 ③**，直接生成现场任务 |

### 2.2 落点

- 属性池 `cert_clause_attr_def` 加第 9 条：`AttrCode='DocCheckMode'`，`ValueType=dict`，`AttrSide=both`
- 条款配置 `cert_clause_attr` 存值
- 值域 `required/optional/none`，默认 `optional`（⛔ 不默认 `required`：宁可少查，不可把"没查"当"企业没有"）

### 2.3 带来的收益（这是用户这条建议的核心价值）

1. **L1 的条款清单变短**：只把 `required + optional` 的条款给模型（`none` 的条款不需要从文档里找证据）→ 提示词更短、漏判更少。
2. **L2 的条款数减少**：`none` 的条款不跑资料核对，直接进现场任务 → 省调用、省时间。
3. **疑点质量提升**：`optional` 条款的疑点默认 `onsite`，不会把"资料里没写"错判成缺口。

## 四、L1 文档提取提示词（`doc_extract`）

### 4.1 输入变量

| 变量 | 来源 | 说明 |
|---|---|---|
| `{{document_content}}` | 文档 Markdown 全文 | |
| `{{standard_name}}` | 标准名 | |
| `{{clause_list}}` | `ICoreResourceQuery.GetClausesAsync` | **只给 `DocCheckMode ≠ none` 的条款**（编号 + 标题 + Artifacts 一句话） |
| `{{extract_contract}}` | 系统注入 | 输出契约（下面 §4.2），逐字给出，⛔ 不靠模型猜 |

### 4.2 输出契约（一份完整 JSON）

```json
{
  "docMeta": {
    "docType": "manual|procedure|record|report|form|ledger|certificate|list|other",
    "title": "文件名称",
    "docNo": "XASL-QD-018",
    "version": "A/0",
    "effectiveDate": "2026-02-05",
    "dept": "生产部"
  },
  "clauses": [
    {
      "clauseNumber": "4.2.5",
      "support": "direct|partial|context",
      "facts": [
        { "text": "记录保存期限为 5 年", "anchor": "第3页 表2 第4行" }
      ],
      "why": "本文件第 3 页规定了记录保存期限，直接对应记录控制要求"
    }
  ]
}
```

**四条硬规则（写进提示词）**：
1. 只输出**有实质内容**的条款（`support=context` 的泛泛提及不要凑数），上限 20 条
2. 每条事实**必须带锚点**（页码/表号/日期/编号至少一项），无锚点的事实不写
3. ⛔ 不判断符合性、不下结论、不编造；没读到就不写
4. `clauseNumber` 必须**逐字**取自 `{{clause_list}}`，⛔ 不许自造编号

### 4.3 缓存与失效

| 情况 | 动作 |
|---|---|
| 同一 `FileCode + StandardCode`，`SourceSha256` 未变 | **直接复用**，不调模型 |
| 文档被替换（新 `FileCode` 或 `Sha256` 变化） | 重跑该文档；旧行 `IsValid=0` |
| 文档被删除 | 提取行 `IsValid=0`，相关条款进"待重跑"队列 |
| 提示词升级 | **不自动重跑**；标记 `PromptVersion` 不一致，人工决定 |

## 五、L2 认证准备提示词（`readiness`）

> 这是用户要的"通用提示词"：**一套模板跑所有条款、所有标准**，条款差异全部来自变量。

### 5.1 输入变量

| 变量 | 来源 | 说明 |
|---|---|---|
| `{{standard_name}}` / `{{clause_number}}` / `{{clause_title}}` | 条款表 | |
| `{{clause_intent}}` | `cert_clause_attr.ClauseIntent` | 条款意图 |
| `{{obligation}}` | `Obligation` | 约束强度（shall/should/note） |
| `{{artifacts}}` | `Artifacts`（prompt 型） | 该条款需要哪些成文信息 |
| `{{evidence_chain}}` | `EvidenceChain`（prompt 型） | 审核员取证剧本（**只给审核员，不给企业**） |
| `{{doc_check_mode}}` | `DocCheckMode` | required/optional/none |
| `{{severity}}` | `Severity` | 违规严重程度基线 |
| `{{doc_slices}}` | **SQL 拼装** | 该条款命中的全部切片：`[文件A] 事实（锚点）…` |

### 5.2 输出契约（单 JSON 对象）

```json
{
  "clauseNumber": "4.2.5",
  "state": "found|partial|missing|unknown",
  "hits": [{"fileName": "XASL-QD-018.doc", "anchor": "第3页 表2", "snippet": "记录保存期限为5年"}],
  "missingKinds": ["record"],
  "gapReason": "有记录清单，但未见最近 12 个月的记录实物",
  "conflicts": [
    {"theme": "保存期限", "aFile": "A.doc", "bFile": "B.doc",
     "aSays": "5年", "bSays": "3年", "severity": "major"}
  ],
  "doubt": {
    "kind": "communicate|observe|interview|verify",
    "mode": "remote|onsite",
    "severity": "major|minor|observation",
    "severitySource": "rule|ai",
    "reason": "……",
    "action": "……",
    "question": "……",
    "targetRole": "记录管理员",
    "estMinutes": 30,
    "priority": "high|medium|low"
  }
}
```

### 5.3 判定规则（写进提示词，7 条）

| # | 规则 |
|---|---|
| R1 | 只判**资料完备性与一致性**，⛔ 不判"做得对不对"（符合性留现场） |
| R2 | 无锚点的事实**不算命中**（必须能回指页码/表号/日期/编号） |
| R3 | `{{doc_slices}}` 为空 ⇒ `state=unknown`（我们没查到），**⛔ 不得写 missing** |
| R4 | 有内容但缺关键要素 ⇒ `partial`，并列出 `missingKinds` |
| R5 | 两份文档说法不一致 ⇒ `conflicts` 必填，`aSays/bSays` **原文引用** |
| R6 | `doc_check_mode=none` ⇒ 不判资料，`doubt.kind` 只能是 `observe`/`interview`，`mode=onsite` |
| R7 | 不确定 ⇒ `unknown`，⛔ 不推测、不补全 |

### 5.4 成本

- 每条款一次调用；单条款输入约 **4k tokens**（条款属性 1k + 切片 3k）
- 88 条款全量 ≈ **88 次**；`DocCheckMode=none` 的条款跳过，实际更少

## 六、触发流程（"上传后怎么开始自动生成疑点"）

```
① 上传 → 文件转换 → MarkdownStatus=completed
        ↓
② 为每个"适用标准"触发 L1（增量）
   命中缓存（SourceSha256 未变）→ 跳过
        ↓
③ 取本次 L1 产出的 ClauseNumbers 并集
        ↓
④ 建 cert_readiness_run（ScopeClauses = ③ 的并集；首次=全量 required+optional）
        ↓
⑤ 逐条款：SQL 拼 doc_slices → readiness → 落 gap + point
        ↓
⑥ 更新批次进度；页面按计划/条款/部门查看疑点
```

**增量规则（三条，够用）**：

| 事件 | 范围 |
|---|---|
| 新文档上传 | 该文档的 `ClauseNumbers`（通常 3–8 条） |
| 文档被替换/删除 | 该文档涉及的条款 + 原文档涉及的条款（取并集） |
| 条款属性更新 | 该条款 1 条 |

> 首次全量、之后增量 ⇒ 日常几乎不产生成本。

## 七、实施顺序（V0 验证 → V1 全量）

### V0 最小验证（省 token，先证明链路）

| 项 | 范围 |
|---|---|
| 标准 | iso13485（88 条款） |
| 条款 | **8 条**：`4.1`、`4.2.1`（已有属性，对照组）+ `4.2.4` 文件控制、`4.2.5` 记录控制、`5.6` 管理评审、`8.2.4` 内部审核、`6.4.1` 工作环境、`7.5.1` 生产和服务提供的控制 |
| 属性 | 只给后 6 条生成（`DocCheckMode` + 其余 8 属性） |
| 文档 | **12 份**（手册 1 + 程序 4 + 记录 4 + 台账 1 + 证书 2） |
| 调用量 | ≈ 8（属性）+ 12（L1）+ 8（L2）= **28 次** |

**出口判据（3 个数字）**：
1. L1 平均每份输出 **3–8 个条款**（>20 说明乱铺）
2. 事实带锚点比例 **> 80%**
3. 任一条款 `doc_slices` 能拼出 **≥2 份不同文档**的记载

### V1 全量（V0 达标后）

1. iso13485 88 条属性全量生成（含 `DocCheckMode`）
2. 237 份文档全量 L1
3. 88 条款 L2 → 缺口 + 疑点
4. 页面：条款树 + 缺口/疑点明细（可下钻原文件）
