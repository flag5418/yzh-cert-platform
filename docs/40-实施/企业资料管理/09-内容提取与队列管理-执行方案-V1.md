| # | 原文要点 | 拆解 |
|---|---|---|

## 三、目标架构

### 3.1 链路（五段，R1/R5）

```
① 上传确认 (upload/confirm)
      ↓ 入队 file_convert（ScopeKey=目录 ConfigCode，互斥：目录级）
② 转换执行器 OfficeConvertTaskExecutor → PreviewPdfPath / MarkdownPath（MarkdownStatus）
      ↓ 入队 doc_extract（ScopeKey=EnterpriseCode，互斥：企业级）★本次改造点
③ 提取执行器 EnterpriseExtractTaskExecutor
      · 规则解析：StandardFileCode = 槽位.StandardFileCode ?? 槽位.Code
      · 无规则 → skipped（不是 failed）
      · LLM：TestFieldWithMarkdownAsync
      ↓
④ 落库 B-08/B-09 企业域（VersionNumber = 槽位当前版本；旧版本行 IsValid=0 归档）
      ↓
⑤ 就位状态回写 StandardDirectoryFile.ExtractStatus / ExtractMessage / MaxConfidence
      ↓ 供下游读取（唯一口径：FileCode + IsValid=1 + 版本）
   NC 检查 / 报告生成
```

### 3.2 提取状态机（`cert_standard_directory_file.ExtractStatus`）

| 值 | 含义 | 进入条件 | 页面表现 |
|---|---|---|---|
| `none` | 未提取 | 初始 / 替换 / 恢复 / 删除回滚 | 灰 tag「未提取」 |
| `pending` | 已入队 | `extract/*` 成功建队列 | 蓝 tag「排队中」 |
| `processing` | 执行中 | 执行器读 Markdown 前 | 蓝 tag「提取中」（转圈） |
| `completed` | 已提取 | 至少写成功 1 个字段或 1 张表 | 绿 tag「已提取 N 字段 M 表格」 |
| `skipped` | **无规则跳过**（新增） | 该槽位无提取规则 | 灰 tag「无规则」+ 配置出口 |
| `failed` | 失败 | LLM/存储异常，或提取结果为空 | 红 tag + 原因 + 「重试」 |

> 前置条件（不满足不出现在可提取清单）：`IsValid=1` 且 `MarkdownStatus='completed'` 且 `ExtractionEnabled=1`。

### 3.3 队列模型（R5/R6 的关键设计）

| 场景 | 队列数 | ScopeKey | 资源锁 | 理由 |
|---|---|---|---|---|
| 自动（转换完成） | 1 文件 = 1 队列 | `EnterpriseCode` | `RESOURCE_FILE` × 该文件 | 保持现状 |
| 单文档手动提取 | 1 文件 = 1 队列 | `EnterpriseCode` | `RESOURCE_FILE` × 该文件 | 保持现状（`trigger-extract`） |
| **按标准 / 按阶段批量** | **1 队列 = N 任务** | `EnterpriseCode` | `RESOURCE_FILE` × N 文件 | ⚠️ 见下 |

**为什么批量必须是「1 队列 N 任务」而不是 N 个队列**：`QueueHostedService` 每秒 `GetNextPendingTaskAsync` 且 `_ = Task.Run(...)`（**不 await**）⇒ 任务实际**并发**执行；若按文件各建一个队列，会在一秒内同时发起 N 个 LLM 调用（现有 3 并发已触发过 qwen 400）。单队列 + 显式并发闸门（`SemaphoreSlim`，默认 2）才能控住配额与内存。

**互斥口径**：同一企业同时只允许 1 个 `doc_extract` 队列运行（`FindRunningQueueByScopeKeyAsync(EnterpriseCode)`）；命中即拒并回队列号，文案「该企业已有提取队列 Q-xxx 运行中」。

## 四、功能分解（WP1–WP9）

> 每项给出：目标 / 改动文件 / 契约 / 验收 / 风险。文件路径均为仓库相对路径。

### WP1 — 提取范围与规则解析（R1/R3 前置）

- **目标**：明确定义「哪些槽位需要提取、为什么不需要」，并把判断收口到**一个**服务，前后端共用同一结论。
- **改动**：
  - 新增 `CertPlatform.Shared/DocExtraction/ExtractionScopeResolver.cs`
    - `ResolveAsync(enterpriseCode, stageCode, standardCode?) → List<ExtractScopeItem>`
    - 每项：`{ FileCode, FileName, StandardCode, StageCode, MarkdownReady, RuleCode?, ExtractionEnabled, ExtractStatus, Extractable, SkipReason }`
  - `EnterpriseFileService` 的 `TriggerExtractAsync` 改为调用本解析器（消除「只校验 ConvertStatus」的漏判）
- **可提取判定（单一权威）**：`IsValid=1` ∧ `MarkdownStatus='completed'` ∧（`ExtractionEnabled=1` ∨ 人工显式勾选）∧ `规则存在`
- **验收**：SQL 断言 —— 按上口径算出的可提取数 = `extract/plan` 返回的 `Extractable` 数（同源，不得各算一遍）。
- **风险**：`ExtractionEnabled` 历史行多为 NULL/0（326 行）⇒ 默认可提取集合会很小；须以 D13 决策定「是否允许绕过开关」。

### WP2 — 自动链补齐与失败可诊断（R1/R5）

- **目标**：上传 → 转换 → 提取全自动、幂等、失败可重试，且每个失败都有**人话原因**。
- **改动**：
  - `OfficeConvertTaskExecutor.EnqueueEnterpriseExtractAsync`：`SourceId` 唯一化沿用；补 `OrgCode`；失败时把原因写回槽位 `ExtractMessage`
  - `EnterpriseExtractTaskExecutor`：
    - 新增 `skipped` 分支（无规则 → `ExtractStatus='skipped'`，不再记 `failed`）
    - 并发闸门（静态 `SemaphoreSlim(2)`）+ Markdown 长度护栏（超限截断/分块，见 WP8）
    - 错误分类：`retryable`（网络/超时/5xx）vs `permanent`（400 InvalidParameter、无 Markdown、无规则）
    - `MaxConfidence` 真实回填（当前恒 `null`）
  - 转换失败 → 槽位 `ExtractStatus` 保持 `none`，`ExtractMessage="等待转换完成"`
- **验收**：E2E —— 上传 → 队列链自动产出 `MarkdownPath` → 自动产生 `doc_extract` 队列 → 槽位终态 ∈ {`completed`,`skipped`,`failed`}；`failed` 必有非空 `ExtractMessage`。
- **风险**：转换链 12 个 `retryable` 失败说明转换服务本身不稳；提取方案不修转换，但要**在页面暴露前置失败**。

### WP3 — 批量提取入口（R3）

- **目标**：三种粒度都能发起提取，且**先预览后执行**（与上传四段式同风格）。
- **新增端点**（`EnterpriseFileController`）：

| 端点 | 入参 | 出参 |
|---|---|---|
| `POST extract/plan` | `{ enterpriseCode, stageCode, standardCode?, fileCodes? }` | `{ Extractable, AlreadyDone, NoRule, NotConverted, Disabled, Rows[] }` |
| `POST extract/batch` | 同上 + `{ includeDisabled?: bool }` | `{ QueueCode, TaskCount, Rejected[] }` |
| `POST extract/retry` | `{ enterpriseCode, fileCodes[] }` | 同上（强制重跑，忽略 `completed`） |
| `POST extract/progress` | `{ enterpriseCode, queueCode? }` | `{ QueueCode, Status, Total, Completed, Failed, Pending, Rows[{FileCode,Status,Message}] }` |

- **服务**：`EnterpriseFileService.ExtractPlanAsync / ExtractBatchAsync / ExtractProgressAsync`
- **队列**：1 队列 N 任务；`QueueName="企业资料提取（按阶段/标准）－{名称} {N} 个文件"`；`SourceType="enterprise_batch"`
- **验收**：`extract/plan` 调用前后 DB 行数/对象数不变（干跑）；`extract/batch` 只建 **1** 个队列、任务数 = `Extractable`；重复点击被互斥拒绝。
- **风险**：一次 N=50 会让企业队列长时间占用 ⇒ 提供「取消队列」与进度条（`queue/cancel` 已存在）。

### WP4 — 替换 / 删除 / 恢复 的提取数据清理（R2，本方案核心）

- **目标**：**任何让文件内容失效的动作，都必须让该文件的提取结果同步失效**；恢复旧版本时旧版本的提取结果要回来。
- **新增服务**：`CertPlatform.Shared/DocExtraction/EnterpriseExtractionResultStore.cs`
  - `ArchiveAsync(enterpriseCode, fileCode, versionNumber?)` — 归档（`IsValid=0`，**不物理删**，保留审计链）
  - `PurgeAsync(enterpriseCode, fileCode, versionNumber?)` — **硬删**（仅用于"该文件被彻底移除且不保留版本"的场景）
  - `RehydrateVersionAsync(enterpriseCode, fileCode, versionNumber)` — 恢复版本时把该版本行反归档（`IsValid=1`），其余版本归档
  - `GetActiveAsync(enterpriseCode, fileCode, versionNumber?)` — **唯一下游读取口径**（`IsValid=1`）
- **接线点（逐条对齐现有代码行）**：

| 动作 | 当前位置 | 现状 | 改后 |
|---|---|---|---|
| 替换 `ReplaceFileAsync` | `EnterpriseFileService.cs:1015-1140` | 仅 `VersionNumber+1`、`ExtractStatus='none'`，**B-08/B-09 原样留 `IsValid=1`**（**缺陷**） | 归档本文件全部旧版本提取行 + `ExtractStatus='none'` + 转换完成后自动重提取 |
| 删除 `DeleteFileAsync` | `EnterpriseFileService.cs:1165-1198` | 完全不动提取结果（**缺陷**） | `ArchiveAsync`（版本恢复依赖，故不硬删） |
| 恢复 `RestoreFileAsync` | `EnterpriseFileService.cs:1200-1290` | 仅重置转换/提取状态（**缺陷**） | 目标版本已有提取行 ⇒ `RehydrateVersionAsync`；无 ⇒ 重入队提取 |
| 转换重跑（重传同版本） | `upload/confirm` / convert 链 | 不清理 | 转换前 `ArchiveAsync(该版本)`，转换后重提取 |
- **验收**（R2 的验收断言，必须逐条 E2E）：
  1. 上传 → 提取成功（B-08 有 `IsValid=1` 行）→ 替换文件（v2）→ **断言 B-08 不再有 `FileCode+IsValid=1` 的 v1 行**；
  2. 删除文件 → 断言下游读取口径返回空；
  3. 恢复到 v1 → 断言 v1 的字段值原样回来（`IsValid=1` 且 `VersionNumber=v1`）；
  4. 全程 `cert_extraction_result` **行数不减**（审计链不丢，只翻转 `IsValid`）。
- **风险**：`RehydrateVersionAsync` 是**新增语义**，需与 `cert_enterprise_file_version`（版本表）口径对齐；若旧版本从未提取过，恢复后必须重提取（不能空手）。

### WP5 — 结果模型补强（R1/R4 的可信基础）

- **目标**：下游读到的字段值「唯一、可判版本、可判来源」。
- **DB 变更（详见 §五）**：加唯一索引、补 `StageCode/StandardCode` 冗余一致性、`IsValid/IsDeleted` 默认值。
- **写入侧**：`SaveEnterpriseExtractionResultsAsync`
  - 归档条件补 `VersionNumber <> 本次`（避免误归档同版本重试行以外的数据）；**同版本重跑先归档同版本旧行**
  - 逐行 `Confidence`／`PositionInfo` 落库（现全 `null`）
  - 写前按 `(OrgCode, FileCode, FieldCode, VersionNumber)` 去重（配合唯一索引兜底）
- **读取侧**：`GetExtractionResultAsync` 支持 `versionNumber` 参数；默认取槽位当前版本
- **验收**：`select OrgCode,FileCode,FieldCode,VersionNumber,count(*) … having count(*)>1 and IsValid=1` 返回 **0 行**。
- **风险**：加唯一索引前必须先清历史重复行（WP9）。

### WP6 — 队列管理后端（R6/R7）

- **目标**：专家端能看**自己企业域**的队列、看详情、重试失败、取消运行中；**绝不能看到别家**。
- **新增**：`CertPlatform.Auditor/Controllers/AuditorQueueMonitorController.cs`（路由 `/api/Auditor/QueueMonitor/*`，基类同现有 Auditor 控制器）
  - 端点：`list` / `detail` / `status` / `cancel` / `retry` / `task/retry`
  - **企业隔离（必做）**：`list` 先算「本工作区可访问的企业 Code 集合」→ 换算成允许的 `ScopeKey` 集合（现状 `ScopeKey` 有 ConfigCode 与 EnterpriseCode 两套口径，故需**双口径**匹配：`ScopeKey ∈ 企业集合 ∪ 该企业的目录 ConfigCode 集合`）
