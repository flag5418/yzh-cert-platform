## §1 业务模型

### 1.1 规则侧（标准文档域）

| # | 表述 | 落实 |
|---|---|---|
| R1 | 一个文档对应一套提示词 | 一条规则 = 提示词 + 字段定义 + 表格定义 |
| R2 | 不是所有文档都有规则 | **没规则是常态** ⇒ 该文件不提取（`skipped`），不报错、不重试、不占队列失败 |
| R3 | 规则可追溯到 机构→标准→阶段→文档 | 唯一键 = **四元组** `(OrgCode, StandardCode, StageCode, StandardFileCode)` |

### 1.2 企业侧（企业资料域）

| # | 表述 | 落实 |
|---|---|---|
| R4 | 企业信息 → 机构；文件信息 → 标准/阶段/文档 | `cert_enterprise.OrgCode` + 槽位行的 `StandardCode`/`StageCode`/`StandardFileCode` |
| R5 | 找到规则就提取，没有就不提取 | 查不到 ⇒ `skipped` |
| R6 | 按后台规则的字段/表格结构存储 | 结构由规则自带，企业侧不自定义 |
| R7 | 唯一差异：`org-std-ent` vs 真实企业 code | **同一套实现、同一套规则、同一套结构**，只有落库 `OrgCode` 不同 |
| R8 | 替换后已提取数据应该清除 | 清除 = 置 `IsValid=0`（见 R10） |

### 1.3 两个标志位的正交语义

| 标志 | 含义 | 业务后果 |
|---|---|---|
| **`IsValid = 0`** | 「**现在**无效」 | **后续一律忽略**。规则无效 ⇒ 全部企业该文档判「无规则」；提取结果无效 ⇒ 下游读不到 |
| **`IsDeleted = 1`** | 「已**删除**」（软删） | 行仍在，**操作日志保留**；所有默认查询都看不到 |

两者不矛盾、各管一件事。ORM 侧天然如此（`SqlSugarDbOrm`）：

| 取数方式 | 过滤 `IsDeleted` | 过滤 `IsValid` |
|---|---|---|
| `GetListAsync(includeDisabled: false)` | ✅ | ✅ |
| `GetListAsync(includeDisabled: true)` | ✅ | ❌ |
| `GetOneIgnoreValidAsync` | ✅ | ❌ |

⇒ **「清除提取结果」= 置 `IsValid=0`**：下游立即读不到（这就是清除），行留库供审计与版本回看。与本模块 E3「移除不删对象」口径一致。

### 1.4 触发方式

| # | 表述 | 落实 |
|---|---|---|
| R9 | **上传时带参数：是否自动提取内容** | `upload/init` 与 `replace` 增加 `AutoExtract: bool`，默认 `true` |
| R10 | 企业频繁更换文件，换文件也要自动提取 | 替换同样走自动链（`file_replace` → 转换完成 → 自动提取） |
| R11 | 状态 3 个：已提取 / 未提取 / 无规则 | 见 §五 状态机 |
| R12 | 常规是上传时自动；拆开手动入口只是为了测试 | 手动入口（整批 / 只提更新的文件）保留为**补跑与测试**，不是主路径 |

## §2 现状差距

### 差距 1 规则表没有机构 Code，且唯一键是单列

```
cert_doc_extraction_rule 的列：Id, Code, FileCode, StandardFileCode, StandardCode,
                              StageCode, Skill, Prompt, DocIsValid, …      ← 无 OrgCode
唯一键：uk_standard_file_code (StandardFileCode)                            ← 全局唯一
```

**为什么阻断**：模板文档按 `(机构, 标准, 阶段)` 分组，**同一标准同一阶段在不同机构下是不同的文档 Code**：

| OrgCode（机构） | 标准 | 阶段 | 模板 config | 文档数 |
|---|---|---|---|---|
| `906e8b2a…` 雄安尚龙 | 9001 | 复审 | `3881ecae…` | **167** |
| `1579641b…` 测试认证机构 | 9001 | 复审 | `34cbb75f…` | 0 |
| `906e8b2a…` 雄安尚龙 | 9001 | 初审 | `f45744e3…` | 0 |
| `1579641b…` 测试认证机构 | 9001 | 初审 | `cf6f1034…` | 1 |

⇒ 机构 A 的「质量手册」与机构 B 的「质量手册」是两个不同 `Code`；单列唯一 ⇒ 一条规则只能挂一个机构，你要的「按机构追溯」做不到。

### 差距 2 自动提取链路已跑通，但**没有上传参数**

`OfficeConvertTaskExecutor.cs:50` 转换成功后自动 `EnqueueEnterpriseExtractAsync` —— 链路已存在（实测 `doc_extract` 12 completed / 3 failed）。缺的是：
- `upload/init` 无 `AutoExtract` 参数，无法按次决定
- 替换走 `file_replace` 队列也会自动提取（行为正确，但无显式参数、无文档说明）

### 差距 3 替换/移除不清除提取结果 + 读取口径不过滤版本

| 位置 | 现状 |
|---|---|
| `ReplaceFileAsync` | 只 `ExtractStatus='none'`，**B-08/B-09 一行未动** |
| `DeleteFileAsync` | 只 `IsValid=0`，提取结果原样留存 |
| `GetExtractionResultAsync` | 过滤 `IsValid=1` 但**不过滤 `VersionNumber`** |

⇒ 替换后下游（NC/报告）**直接读到旧版本**字段值。实测 B-08 已有 8 行跨 v1/v2/v3，7 行归档行。

### 差距 4 提取结果唯一键设计错误

09 §五① 的 `uk(…, VersionNumber, IsValid)`：实测 `(TEST-ENT-0001, TESTENT-12711e0c, certificateNo, v1)` 已有 **2 行 `IsValid=0`** ⇒ DDL 直接报错；且含 `IsValid` 的唯一键会**禁止合法的重提取历史**。修正见 §七②。

## §3 追溯链：规则表是唯一锚点（★ 本方案的核心设计）

```
                    ┌──────────────────────────────────────────────┐
                    │  cert_doc_extraction_rule   ★ 唯一锚点        │
                    │  ┌────────┬────────────┬──────────┬────────┐  │
                    │  │ OrgCode│StandardCode│StageCode │Standard│  │
                    │  │  机构  │   标准     │  阶段    │FileCode│  │
                    │  │ ★新增  │            │          │ 文档   │  │
                    │  ├────────┴────────────┴──────────┴────────┤  │
                    │  │ Code(=RuleCode) │ Prompt │ Status      │  │
                    │  └───────┬──────────────────────┬──────────┘  │
                    └──────────┼──────────────────────┼─────────────┘
                               │                      │
              ┌────────────────┘                      └───────────────┐
              │ 1 : N（按 RuleCode 回溯，定义表无需冗余 OrgCode）        │
              ▼                                                      ▼
   ┌────────────────────────┐                        ┌──────────────────────────┐
   │ cert_doc_field_def     │                        │ cert_doc_table_def      │
   │ RuleCode               │                        │ RuleCode                │
   │ Code / FieldCode       │                        │ Code / TableCode        │
   │ FieldName / DataType   │                        │ TableName               │
   └───────────┬────────────┘                        └───────────┬──────────────┘
               │                                                  │ 1 : N
               │                                                  ▼
               │                                    ┌──────────────────────────┐
               │                                    │ cert_doc_table_field_def │
               │                                    │ TableCode                │
               │                                    │ ColumnCode / DataType    │
               │                                    └──────────────────────────┘
               │
               │  ★ 定义结构完全由规则决定 ⇒ 企业侧沿用，不自定义
               ▼
   企业资料提取时按 RuleCode 取定义 → 拼 Prompt → 调 LLM → 落 B-08 / B-09
```

**为什么不在定义表冗余 `OrgCode`**：
1. 定义结构**完全由规则决定**，企业侧不自定义 ⇒ 冗余列没有写入方，也就没有一致性维护成本与漂移风险。
2. 需要「按机构查定义」时，走 `rule JOIN def ON def.RuleCode = rule.Code` 即可，实测定义表最大 1 行、后续个位数，join 无性能问题。
3. 少改 3 张表 = 少 3 份迁移与回滚风险。

**查规则的唯一入口**（所有调用方共用，禁止各处自己写 WHERE）：

```csharp
Task<DocExtractionRule?> GetRuleByScopeAsync(
    string orgCode, string standardCode, string stageCode, string standardFileCode);
// WHERE OrgCode=@orgCode AND StandardCode=@standardCode
//   AND StageCode=@stageCode AND StandardFileCode=@standardFileCode
//   AND IsValid=1
```

**改四元组的影响面**（实测已全部定位）：

| # | 位置 | 现状 | 改后 |
|---|---|---|---|
| 1 | `DocExtractionRuleService.cs:118` | `GetOneAsync(x => x.StandardFileCode == request.FileCode)` | 传四元组 |
| 2 | `DocExtractionRuleService.cs:373-374` `GetRuleByStandardFileCodeAsync` | 单列 | 改名 `GetRuleByScopeAsync` + 四元组 |
| 3 | `DocExtractionRuleService.AI.cs:570` | 单列 | 四元组 |
| 4 | `DocExtractionRuleService.AI.cs:884`（提取主路径） | `GetOneAsync(x => x.StandardFileCode == standardFileCode)` | 四元组 |
| 5 | `DocExtractionRuleService.AI.cs:1322-1328` `LoadRuleDefsAsync` | 先按 `standardFileCode` 反查 `ruleCode` | 直接传 `ruleCode`（少一次查询） |
| 6 | `DocExtractionRuleController.cs:105` `GetRuleDetail(standardFileCode)` | 路由参数单值 | 四元组（query 或 body） |
| 7 | `DocExtractionRuleController.cs:123` `DeleteRule(standardFileCode)` | 路由参数单值 | 同上 |
| 8 | `cert-share/api/workflow/doc-extraction-rule.ts:91,111` | `getRuleDetail(standardFileCode)` / `deleteRule(...)` | 同步改签名 |

> `GetFieldsAndTables(ruleCode)`（`:114`）本来就是按 `ruleCode` ⇒ **不用改**。

```
        │ 未提取 · 无规则      N1 → 灰、不可选   │
        │ 未提取 · 可提取      N2 → 勾选执行     │
        │ 已提取              N3 → 默认不勾     │
        │ 未转换（无 Markdown）N4 → 灰，先转     │
        └────────────────────────────────────────┘
                      │ 用户确认
                      ▼
        POST extract/batch → 1 个队列 + N 个任务（并发闸门 2）
        POST extract/retry → 指定 fileCodes 强制重跑
                      ▼
        POST extract/progress（前端 5s 轮询）
```

> **为什么批量必须「1 队列 N 任务」**：`QueueHostedService.cs:62` 是 `_ = Task.Run(...)` **不 await**，每秒一轮 ⇒ N 个队列会在一秒内并发发起 N 次 LLM 调用（qwen 400 已实测发生）。

## §8 决策清单（**全部按默认执行**；有异议的条目单独指出即可）

| # | 决策点 | 默认执行 | 理由 |
