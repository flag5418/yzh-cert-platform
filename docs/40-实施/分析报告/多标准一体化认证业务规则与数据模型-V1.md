# 多标准一体化认证业务规则与数据模型-V1

> **本文是「业务规则澄清」，不是设计文档。** 目的是把多标准认证这件事说到没有歧义。
> 依据：Annex SL（HLS）高层架构、GB/T 27021.1-2017、CCAA 审核概论、ISO 9001:2015 / 14001:2015 / 45001:2018 条款对照。

---

## 〇、一句话结论

> **★ 你的困惑有一个共同根源：把「整合」理解成了「去重」。**
>
> **整合不是「删掉重复项」，而是「一行、多列标注」。**
>
> - 检查表：**一个检查项一行**，标注它覆盖哪些标准的哪些条款
> - NC 台账：**一张 NC 单**，标注涉及的体系类别和条款号
> - 报告：**一份报告**，章节骨架共用，内容按标准分列
>
> 所以「排重」的正确动作**不是删除，是合并成一行 + 保留多标准映射**。
> 而**这个映射关系是「业务知识」，不是代码能算出来的** → **必须由专家在后台手工建「条款映射表」**。

# 第一部分：后台 5 点假设的逐条裁定

## 一、假设 1：「每个机构可认证的标准固定，每个标准下应评审的阶段也固定」

**前半句 ✅ 对。后半句 ⚠️ 错——阶段不随标准变。**

| | 裁定 |
|---|---|
| 「每个机构可认证的标准固定」 | ✅ **对** → `cert_org_standard`（机构-标准授权） |
| 「每个标准下应评审的阶段固定」 | ⚠️ **不对**。**阶段是通用的**（初审 / 监督审核 / 再认证），**不随标准变化** |

**证据**：`cert_org_stage` 表设计上允许 `StandardCode`，但**实际数据里是 NULL** —— 说明当初也没想清楚要不要绑。**这个 NULL 其实是对的。**

**正确模型**：

```
机构 ──1:N──> 可做标准（cert_org_standard）      ← 独立
机构 ──1:N──> 可做认证阶段（cert_org_stage）      ← 独立，不绑标准
        两者交叉 = 该机构可承接的「标准 × 阶段」组合
```

**→ 补正**：正式宣布 `cert_org_stage.StandardCode` **废弃**（不绑标准）。

---

## 二、假设 2：「标准目录按 一个机构 一个标准 一个阶段 下，针对企业的文档结构内容固定」

**⚠️ 要去掉「一个机构」。**

| 项 | 裁定 |
|---|---|
| 按「标准 + 阶段」定义目录 | ✅ **对** |
| 按「机构」定义目录 | ⚠️ **不该有机构维度** —— ISO 9001 初审要什么文件，**对所有机构都一样**（标准是国际标准，不是机构标准） |

**★ 有意思的是：你库里的表结构其实是对的** ——
`cert_standard_directory_config` 的键是 `DirectoryCode + StandardCode + PhaseCode + RootFolderName`，**没有 `OrgCode`**。**是假设写偏了，不是表建错了。**

**但现实折中**：不同机构确实有自己的目录习惯 → **两层设计**
1. **平台级默认目录**（按标准+阶段，映智汇维护）
2. **机构级覆盖**（机构可增删改）

**⚠️ 同时必须修的老问题**：`cert_standard_directory_folder/_file` 现在**既存"要求"又存"企业上传实例"**（同表有 `FilePattern/IsRequired/ExtractionRules` 又有 `TaskId/UploadStatus/StoragePath/MarkdownPath`）→ **必须拆要求侧 / 实例侧**（第三轮提出）。

---

## 三、假设 3：「内容提取规则：一个标准目录，按每个文档提取字段、表格」

**✅ 对，但要改一个挂载点：提取规则应挂在「文档类型」上，不是挂在「标准」上。**

| 项 | 裁定 |
|---|---|
| 按文档提取字段/表格 | ✅ **对** |
| 提取规则挂「标准」 | ⚠️ **应挂「文档类型」** |

**理由**：同一份「营业执照」，在 9001 和 14001 下**要提取的字段完全一样**（统一社会信用代码、法人、经营范围…）。
→ 若按标准挂，同一份文件会被提取两次，且结果可能不一致。
→ **正确：一个文档类型一套提取规则；多标准要求同一文档时，提取一次、结果共用。**

**现状**：`cert_doc_extraction_rule` + `cert_doc_field_def` + `cert_doc_table_def` + `cert_doc_table_field_def` **四张表全 0 行**。

---

## 四、假设 4：「NC 规则：一个机构 一个标准 一个阶段，审核内容固定，可从标准内容通过自定义流程引擎生成 NC 检查内容」

**✅ 基本对。同样去掉「一个机构」，并补一个「整合映射」层。**

| 项 | 裁定 |
|---|---|
| 按「标准 + 阶段」定义 NC 规则 | ✅ **对**（去掉机构维度） |
| 「从标准内容通过流程引擎生成 NC 检查内容」 | ✅ **对**，但**前置条件是条款库要有内容**（现在几乎为空，见 §九） |
| 「多标准 NC 很多项重复，要排重吗」 | ★ **要，但不是"删除"，是"合并 + 多标准标注"** → 见 §七 |

**★ 关键补充**：多标准的 NC 规则之间**需要一张「整合映射表」**（条款级），这张表**后台现在没有** → 见 §八。

---

## 五、假设 5：「认证报告：一个机构 一个标准 一个阶段，报告内容固定，每条内容可通过自定义流程定义」

**✅ 对。同样去掉机构维度，并补「报告模式」概念。**

| 项 | 裁定 |
|---|---|
| 按「标准 + 阶段」定义报告模板 | ✅ **对** |
| 每条报告内容可通过流程定义 | ✅ **对** |
| 「多标准一个报告」如何合并 | ★ **不是"合并去重"，是"用 HLS 骨架的模板 + 多标准填充"** → 见 §七.4 |

**→ 需要新增一个维度**：`cert_report_template` 加「**报告模式**」字段：
- 模式 A：**标准符合性报告**（一份报告 = 一个标准）
- 模式 B：**一体化审核报告**（一份报告 = 一次审核，准则多值）

# 第二部分：企业端 4 点的逐条答复

## 六、问题 1：企业处于什么阶段？认证阶段 / 评审阶段，本质上还有什么区别？

### 6.1 ★ 你其实混了**三个**不同的「阶段」概念

| # | 概念 | 时间尺度 | 内容 | 决定什么 | 归属 |
|---|---|---|---|---|---|
| **①** | **认证阶段**<br>certification cycle stage | **年**（3 年一周期） | 初审 → 监督审核（第1年）→ 监督审核（第2年）→ 再认证（第3年） | **证书的有效性**（发证/保持/换证） | 认证机构 |
| **②** | **审核阶段**<br>audit stage | **天**（一次审核内部） | **一阶段审核**（文件审核）→ **二阶段审核**（现场审核） | **本次审核怎么走** | 认证机构 |
| **③** | **体系准备阶段** | **月**（≥3 个月试运行） | 体系建立 → 试运行 → 内审 → 管理评审 | **能不能申请认证** | **企业自己 / 咨询方** |

### 6.2 三者的**本质区别**与关系

```
① 认证阶段（年）
    └── 一次审核
            ├── ② 审核阶段：一阶段审核（文件审核）  ← 查齐套性，可远程
            └── ② 审核阶段：二阶段审核（现场审核）  ← 查执行，必须现场

③ 体系准备阶段 —— 在 ① 之前，企业（或咨询方）自己做，不属于认证机构的审核
```

**★ 本质区别**：
- **① 认证阶段 = 证书生命周期的时间轴** —— 回答「这是第几次审核」
- **② 审核阶段 = 一次审核内部的两步法** —— 回答「这次审核分几步走」
- **③ 体系准备阶段 = 企业的备考期** —— 回答「企业准备好了没有」

### 6.3 ★ 对你设计的影响（重要）

你原话提到「企业 → **咨询（中介准备材料）** → 体系认证」→ **这说明你的系统可能要覆盖 ③ 体系准备阶段**。
如果是，那么「企业 + 阶段」里的**阶段应该是一个更上层的「企业认证生命周期」**，而不是认证机构内部的审核阶段。

**建议的落法**：
- `cert_enterprise_stage` 挂 **① 认证阶段**（初审/监督/再认证）
- ③ 体系准备阶段如果要做，**单独一层**（如 `Prep` 阶段），不要和 ① 混
- ② 审核阶段**只在审核任务内部出现**，不进企业的左侧树

**库现状**：
| 表 | 现状 |
|---|---|
| `cert_cert_stage`（① 认证阶段） | **1 行**：`jd01 / 初审 / process` → **缺 监督审核、再认证** |
| `cert_phase_definition`（② 审核阶段） | **0 行（空表）** |
| ③ 体系准备阶段 | **无表** |

## 七、问题 2/3/4 的统一答案：多标准到底怎么处理？

> **这三个问题（文档完整性检查、NC 排重、报告合并）本质是同一个问题：多标准之间怎么「对应」。**
> **答案只有一个：建「映射表」，用「一行多项标注」，不用「删除去重」。**

### 7.1 ★★ 基础事实：HLS 高阶结构（Annex SL）

**ISO 9001 / 14001 / 45001 都基于 Annex SL，第 4~10 章骨架完全一致：**

| 章 | 名称 | 三标准是否一致 |
|---|---|---|
| **4** | 组织环境 | ✅ 骨架一致 |
| **5** | 领导作用 | ✅ 骨架一致 |
| **6** | 策划 | ⚠️ **展开不同**（6.1 内容差异最大） |
| **7** | 支持 | ✅ 骨架一致 |
| **8** | 运行 | ⚠️ **完全不同**（各标准专属） |
| **9** | 绩效评价 | ✅ 骨架一致 |
| **10** | 改进 | ✅ 骨架一致 |

**★★ 但「骨架一致 ≠ 内容可互换」。** 同样一个条款号，**审核意图完全不同**：

| 条款 | ISO 9001 审什么 | ISO 14001 审什么 | ISO 45001 审什么 |
|---|---|---|---|
| **4.1** | 内外部因素对**质量目标**的影响 | **环境条件**与利益相关方 | 工作人员及相关方的**安全诉求** |
| **5.1** | **质量方针**与顾客要求 | **环境方针**与合规承诺 | **OHS 方针**与协商参与 |
| **6.1** | **过程风险、产品风险** | **环境因素、合规义务** | **危险源、OHS 风险** |
| **8.1** | 生产和服务提供控制 | 环境运行控制 | 运行控制与变更管理 |
| **9.1** | 产品检验、过程能力 | 环境监测、合规评价 | 职业健康监测、绩效 |
| **10.2** | 不合格品、顾客投诉 | 环境事件、违规 | 事故、事件、职业病 |

**→ 所以「按条款号自动去重」是错的**（6.1 在三个标准下审的东西完全不同）。
**→ 但「同一审核对象、同一份证据」的检查确实可以只做一次。**

### 7.2 ★★★ 正确的排重单位：不是「条款」，是「审核对象 / 过程 / 证据」

**规范实践（整合审核三种模式）**：

| 模式 | 做法 | 适用 |
|---|---|---|
| 一 | **以 9001 为主干，14001/45001 挂靠** | 质量体系成熟、EHS 刚起步 |
| **二** | **三体系并行，按条款逐条合并** | ✅ **推荐起步**（条款对应关系清晰，易上手） |
| 三 | **按过程整合**（条款打散到采购/生产/设备/人力等过程） | 流程导向强的组织 |

**模式二的具体做法 = 建一张「条款映射表」**：把三套标准的 **条款号 / 审核要点 / 证据类型 / 责任部门** 列在一起。

**★ 排重的真正判据（三条，按可靠性排序）**：

| # | 判据 | 可靠性 | 能否自动 |
|---|---|---|---|
| 1 | **同一份证据**（都查「文件控制程序」这一份文件） | 最高 | ❌ 需人工 |
| 2 | **同一审核对象/过程**（都查「内审」这个活动） | 高 | ❌ 需人工 |
| 3 | **条款号相同**（都是 7.5） | 中（**可能内容不同**） | ⚠️ 可自动**建议**，需人工确认 |

**→ 结论：自动建议（按条款号）+ 人工确认（按证据/对象）。⛔ 不要全自动。**

### 7.3 ★★ 三条统一原则（这是本文最重要的一段）

> **原则一：能合则合，合的是「检查动作」，不是「条款」。**
> 一个检查项覆盖多个标准的多个条款 → **执行一次，结果回填到所有覆盖的条款上**。
>
> **原则二：合不了就分，绝不强行合并。**
> 证据不互认的典型场景（规范明确警告）：
> - ❌ 9001 的「**顾客满意**调查」≠ 45001 的「**工作人员参与**」（对象不同：顾客 vs 员工）
> - ❌ 14001 的「**合规义务**」≠ 9001 的「**法律法规要求**」（合并可以，但清单必须**分列标注适用体系**）
> - ❌ 45001 的「**危险源辨识**」只做现场作业 → 漏办公室/实验室/外包人员
>
> **原则三：保留差异标签，不要为了整齐而抹平。**
> 规范原文建议：**「不符合报告的不符合事实里，同时标注涉及的体系类别和条款号」**（如「ISO 45001 8.1 运行控制」）；
> **「用同一份不符合与纠正措施台账，加一列体系类别」** —— **整合但保留差异**。

### 7.4 逐项回答你的三个具体问题

#### （1）文档完整性检查怎么做？

**答：在「要求侧」展开并集去重，不在「上传侧」去重。**

```
企业在阶段内勾选覆盖标准（9001 + 14001）
        ↓
系统展开要求清单：
    (9001, 初审) 的目录/文件要求  ∪  (14001, 初审) 的目录/文件要求
        ↓
★ 去重判据 = 「文档类型」（不是标准）
    同一份「营业执照」被两个标准要求 → 只算 1 个槽位
        ↓
企业看到的是一份【合并后的要求清单】，每个条目后面标注 [9001, 14001]
        ↓
上传 → 按槽位匹配 → 缺失的槽位 = 缺失文档
```

**★ 关键点**：
- 企业**不"遵循某个标准的规则"**，而是**被合并后的规则校验一次**
- **每个槽位保留「来源标准」列表**（因为报告要追溯，IMS 强制）
- 「完整性」= 槽位覆盖率；「内容符合性」= 提取结果 vs 规则要求

**你的原话**「如果不勾选标准，没办法针对企业资料的完整度进行筛选，也不能直接对应到后端的标准文档提取规则」→ **完全正确，所以必须先勾标准。** 但勾完之后，**系统要把多标准的要求合并成一份清单**，而不是让企业面对两份清单。

#### （2）资料内容提取怎么做？

**答：按「文档类型」提取一次，多标准共用结果。**

```
企业上传「营业执照」
        ↓
匹配到槽位（文档类型 = 营业执照）
        ↓
★ 按【文档类型】取一套提取规则（不按标准）
        ↓
提取字段：统一社会信用代码 / 法定代表人 / 经营范围 …
        ↓
提取结果挂在该槽位上 → 被 9001 和 14001 的检查项共用
```

**★ 关键点**：
- **提取规则挂「文档类型」**（`cert_doc_extraction_rule` 应关联文档类型，不关联 StandardCode）
- 同一份文件**只提取一次** → 避免两个标准提取结果不一致
- **现状**：四张提取规则表**全 0 行** → 这是和条款库并列的第二个硬空缺

#### （3）NC 检查：多标准重复项要不要排重？执行一次可以吗？

**答：要排重；可以执行一次，但要「一次执行、多标准回填」。**

```
后台：专家按标准录 NC 规则（保持现状）
        ↓
后台：★ 建「整合映射表」—— 标注哪些规则是同一个检查动作
        ↓
执行：同组的规则 → 只跑一次
        ↓
结果：一次检查结果 → 回填到所有覆盖标准的条款上
        ↓
NC 单：一张单，标注涉及的体系类别 + 条款号（如「9001 7.5 / 14001 7.5」）
```

**★ 落地建议**：给 `cert_validation_rule` 加一个 **`IntegrationKey`（整合键）** 字段：
- 同 `IntegrationKey` 的多标准规则 = **一次检查**
- **未填的 = 各自独立跑**（默认安全，不影响单标准场景）
- 不改专家录入习惯（还是按标准录），只多填一个**可选**字段

**★ 为什么不做全自动**：6.1 在三个标准下审的东西**完全不同** → 按条款号自动合并会**漏项**（规范明确警告：「把三者当成同一张表来审，必然漏项」）。

#### （4）报告：多报告 vs 一个报告，一个报告如何去重？

**答：报告不是"合并去重"出来的，是「模板 + 数据填充」出来的。**

**⛔ 先排除一个错误做法**：不要做「自动判断章节内容是否重复」——
① 语义判断靠代码不可靠 ② **审核报告是有法律效力的文件，不能自动去重**。

**✅ 正确做法**：

| 报告模式 | 实现方式 |
|---|---|
| **模式 A：多报告**（每标准一份） | 模板按 `(标准, 阶段)` 定义；**同一批数据，按标准切分** → 每份只填该标准的条款 |
| **模式 B：一份报告**（一体化审核报告） | 模板**按 HLS 骨架定义章节**（4 组织环境 / 5 领导 / 6 策划 / 7 支持 / 8 运行 / 9 绩效 / 10 改进）；每个章节的**条款槽位填多个标准的条款** |

**★ 核心认知：报告是「视图」，不是「数据」。**

```
一次审核 → 一套原始数据（检查项结果 / 发现 / NC / 证据）
                ├─ 按【标准】切 → 模式 A：N 份标准符合性报告
                └─ 按【一次审核】切 → 模式 B：1 份一体化审核报告
```

**→ 所以「去重」发生在模板设计阶段（人工配置章节槽位），不发生在生成阶段（自动）。**
**→ 数据只存一份，报告模板决定怎么切。⛔ 不要建两套数据。**

**规范依据**：审核报告的固定内容项里，**「审核准则」本身就是可多值的字段**（写多个标准）；**「审核发现和相关证据」每条标注涉及哪些标准的哪条条款**；**「审核结论」按标准分别给**。
→ **「多标准一份报告」在规范上是天然的**，不是硬凑出来的。

## 八、★ 后台缺的核心资产：一张「条款映射表」

**这是本次分析最关键的结论。**

你的后台有：标准库、目录、提取规则、NC 规则、报告模板 —— **每个都按标准分开建**。
但**没有一张表回答「9001 的 7.5 和 14001 的 7.5 是什么关系」**。

| 缺的资产 | 作用 | 影响的环节 |
|---|---|---|
| **① 条款映射表**<br>（标准A条款 ↔ 标准B条款 ↔ 整合组） | 决定哪些检查项可以合并 | NC 排重、检查表生成、报告章节合并 |
| **② 文档类型映射表**<br>（同一份文件被哪些标准要求） | 决定哪些文件要求可以合并 | 文档完整性检查、提取规则复用 |
| **③ 报告章节槽位配置**<br>（HLS 章节 → 多标准条款列表） | 决定一份报告怎么组织 | 一体化审核报告 |

**★ 这三张表都是「业务知识」，不是「代码能算出来的」→ 必须由专家录入。**
**→ 这解释了为什么「完善专家系统也没用」：后台缺的不是功能，是知识。**
