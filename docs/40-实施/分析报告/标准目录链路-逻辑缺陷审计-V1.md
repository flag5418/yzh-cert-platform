# 标准目录链路 · 逻辑缺陷审计 V1

> 2026-09-26｜**审计对象**：标准目录 / 上传 / 转换 / 导出 这条链路的控制器与服务层
> **方法**：逐行读源码 + 逐条查数据库与视图定义 + 与「新写的专家端代码」对比
> **结论**：**你的担心是对的，而且比想象中更集中** —— 隐患不是零散的 bug，是**三个根因**长出来的。
> 建议在 P1 重构中**一并修掉 6 条 P0**，因为 P2 清库后正好是一个干净起点。

## 0. 一句话结论

> **这条链路是整个项目里唯一「没按新架构写」的孤岛** —— 控制器继承裸 `ControllerBase`、
> 服务层用 `IsValid` 一个字段表达 4 种业务状态、所有查询都缺租户维度。
> 对比之下，新写的专家端（`EnterpriseController` / `EnterpriseStageController`）**同类问题一条都没有**。
> 所以这不是"架构不行"，是**这块代码没被架构约束到**。

## 2. 根因（三条，全部 P0 级）

### 根因 A ★★★ `IsValid` 一个字段承担 **4 种**互不相容的语义

`StandardDirectoryFile.IsValid` 同时是：

| 语义 | 写入点 | 证据 |
|---|---|---|
| ① 启用 / 禁用（行按钮） | 管理页手工切换 | `isRowEnabled` 约定 |
| ② **上传草稿**（还没传完） | `UploadInitAsync` 建记录 | `:700`（文件夹）、`:791`（文件） |
| ③ **转换中 / 转换失败被隐藏** | `RetryFailedConversionsAsync` 置 0；PDF 链完成置 1 | `:2102`、`OfficeConvertService.cs:406` |
| ④ **已删除** | `DeleteFileAsync`、`DeleteFolderRecursiveAsync`、`DeleteConfigAsync` | `:435`、`:348`/`:360`、`:193` |

**后果**（都是"看起来正常但是错的"）：

1. **删除与转换中不可区分** —— 目录页默认过滤 `IsValid=1`，所以「正在转换的文件」和「已被删除的文件」在界面上**表现完全一样：都不显示**。
2. **失败文件凭空消失** —— `RetryFailedConversionsAsync` 把失败文件置 `IsValid=0` 来"藏起来"，用户看到的是**文件没了**（代码自己的注释 `:2173` 承认了这一点）。
3. **行按钮语义错乱** —— 「启用/禁用」开关对草稿文件夹、转换中文件都成立，点一下就能把"转换中"改成"启用"。
4. **`ISoftDelete.IsDeleted` 从未被写过** —— 你上一轮定的"软删除"**在现状里根本没有生效**，`IsDeleted` 列一直是 0。现在所谓的"软删除"是靠业务代码到处手写 `IsValid = 0` 硬凑的。

> **这是 P1 的第一优先级。** 不先把状态语义分开，后面加 `OrgCode`、改路径、做归档都会继续踩在同一个坑上。

### 根因 B ★★★ 没有租户维度的显式落库

全链路只按客户端传来的 `directoryCode` 过滤，**从不校验这个目录属于谁**。见 P0-3。

### 根因 C ★★ 失败路径没有统一出口

服务层大量"记日志继续"或"返回 `ok=true` 带 error"，控制器再把 error 丢掉。见 P1-9 / P1-10 / P1-11 / P1-17 / P1-18。

## 3. P0 缺陷（会导致数据丢失 / 越权 / 进程崩溃）

### P0-1 ★★★ 每次上传都会**物理删除**同目录下别人正在转换的文件

- **证据**：`StandardDirectoryService.cs:1275-1295`，由 `:649` 在 `UploadInitAsync` 中调用
  ```csharp
  var orphanFiles = await _db.Client.Queryable<StandardDirectoryFile>()
      .Where(x => x.DirectoryCode == directoryCode && x.IsValid == 0 && x.TaskId != taskId)
      .ToListAsync();
  foreach (var f in orphanFiles)
      await _db.Client.Deleteable(f).ExecuteCommandAsync();   // ← 物理删除
  ```
- **触发**：同一目录下发起第二次上传即可（不需要任何异常操作）。
- **后果**：`IsValid=0` 恰恰是「转换中」和「重试失败被隐藏」的状态 ⇒ 第二次上传会把**第一次上传的全部文件从库里物理删除**；它们的 MinIO 对象随即变成孤儿（此处**不做存储清理**）。同名文件夹、以及 `Status != "completed"` 的**他人上传任务记录**也一并被物理删除。
- **修复**：删除"跨任务清理"这个设计。改为三重判据：`TaskId != 当前` **且** `CreateTime` 超过过期窗口 **且** 无活跃队列/资源锁 **且** 无 MinIO 对象。且只清理 `UploadStatus IN ('pending','replacing')` 的，绝不碰 `ConvertStatus='pending'` 的。

### P0-2 ★★★ 导出 ZIP 存在路径穿越与 Zip Slip

- **证据**：`:1620-1632`
  ```csharp
  var entryPath = string.IsNullOrEmpty(folderPath) ? file.FileName : $"{folderPath}/{file.FileName}";
  var localPath = Path.Combine(tempDir, entryPath.Replace('/', Path.DirectorySeparatorChar));
  ...
  using var fileStream = File.Create(localPath);
  ```
  `folderPath` 由 `FolderName` 拼成（`GetFolderPath`，`:1684-1696`），而 `FolderName` **来自客户端且从不做任何清洗**（`CreateFolderAsync:260` 直接用、`UpdateFolderAsync:305` 直接用、`UploadInitAsync:682` 直接取清单路径末段）。
- **触发**：把文件夹命名为 `..`（或含 `../`）。
- **后果**：① `Path.Combine(tempDir, "../…")` 逃出临时目录 ⇒ **任意路径写文件**（服务端）。② `archive.CreateEntryFromFile(filePath, entryName)` 把 `../` 写进 zip 条目名 ⇒ **Zip Slip**，解压方（用户本机）被写入任意路径。
- **修复**：`FolderName`/`FileName` 入库前强制清洗（禁 `/`、`\`、`..`、控制字符，见 `PathBuilder` 的保留段与穿越校验）；导出时对 `localPath` 做 `Path.GetFullPath` 前缀校验（必须仍在 `tempDir` 内），条目名同样校验。

### P0-3 ★★★ 全链路无租户隔离（水平越权）

- **证据**：控制器全部端点只接收 `directoryCode`/`folderCode`/`fileCode`/`storagePath`，服务层全部查询形如 `x => x.DirectoryCode == directoryCode && x.IsValid == 1`，**从不叠加"该目录属于当前工作区"**：
  - `GetConfigsAsync:160-163` → 返回**全部工作区**的目录配置
  - `GetConfigAsync:165-168` / `GetFolderTreeAsync:207-219` / `GetFilesByDirectoryAsync:1513-1517` / `GetStageFileTreeAsync:1337`
  - `DownloadFileAsync:445-459` ← `storagePath` 由客户端给，只校验"前缀是已知文档库"（`:166`）⇒ **可下载任意工作区任意文件**
  - `ExportAsZipAsync:1585-1664` ← 同理，可打包任意工作区的目录
  - `GetFilesAsync:377-386` ← 传 `null` 时返回 **全库所有文件**
  - `UploadInitAsync:623-639` ← 目录配置不存在时**按客户端输入自动创建**，无归属、无权限校验
- **对比**：`EnterpriseController` 用 `WorkspaceContextService` 取工作区，并把 `OrgCode = 当前工作区` **强制叠加进过滤器**（`:170-175`），还在 `:242`、`:509` 做归属校验。
- **修复**：① `cert_standard_directory_config` 增加 `OrgCode` 列（P1 本来就要加）；② 服务层所有入口先解析工作区，再叠加 `OrgCode` 过滤；③ `Download`/`Export` 先按 `StoragePath` 反查文件行并校验归属，**不允许仅凭路径前缀放行**。

### P0-4 ★★ 控制器是裸 `ControllerBase`，零权限声明

- **证据**：`StandardDirectoryController.cs:18` `public class StandardDirectoryController : ControllerBase`；全文件 **0 处** `[RequirePermission]`、**0 处** `ApiCode` 登记。它是项目里 10 个裸控制器之一（承载 90/96 端点）。
- **后果**：任何能通过登录的账号（含企业端用户）都能调用全部端点 —— 结合 P0-3 就是**跨租户读写**。且因动作名未纳入 ApiSync，角色-接口关联表里没有它，**权限体系对这块完全失效**。
- **修复**：改为继承 `YzhControllerBase<>`（或至少补 `[RequirePermission]` + 纳入 ApiSync）。⚠️ 改控制器名/动作名会让 `ApiCode` 变化，需重跑 ApiSync 并重关联。

### P0-5 ★★ `UpdateConfig` 可按 `Code` 劫持任意目录配置（IDOR + 全字段覆盖）

- **证据**：控制器 `:72-78` 只强制了 `config.DirectoryCode = directoryCode`，**没有强制 `config.Code`**；
  服务 `:180-187` 把客户端实体直接交给 `UpdateAsync(config)`；
  而框架 `SqlSugarDbOrm.BuildUpdateLocator`（`:276-281`）**只用 `Code` 定位**、且单参 `UpdateAsync` 写**全部 `BcFlag` 列**。
- **触发**：请求体里带上另一个配置的 `Code`。
- **后果**：路由里的 `directoryCode` 完全失效，目标行由请求体决定 ⇒ **可改写任意工作区、任意目录的配置**（含 `IsValid`，等于远程删除）。`CreateConfigAsync:170-178` 因为服务端强制重写 `Code` 反而安全 —— **两处不对称，是"漏改"而非"设计"**。
- **修复**：服务层禁止把客户端实体直接入库。统一改为「先按业务键查 existing → 只从白名单字段拷贝 → 更新 existing」。

### P0-6 ★★ 环状 `ParentCode` 会让 4 处树遍历失控

- **证据**（全部无 visited 保护）：
  | 位置 | 形态 | 后果 |
  |---|---|---|
  | `GetChildFolders:230-238` | 递归 | 无限递归 → 内存耗尽 |
  | `DeleteFolderRecursiveAsync:328-368` | 递归 | **StackOverflow → 进程崩溃** |
  | `AddChildFolderCodes:1674-1682` | 递归 | 无限递归 → 内存耗尽 |
  | `GetFolderPath:1684-1696` | `while (current = folder.ParentCode)` | **死循环 → 请求线程永久挂住** |
- **触发**：`A.ParentCode = B` 且 `B.ParentCode = A`。当前无环，但**没有任何约束阻止它**（无 FK、无环检测、`UpdateFolderAsync` 也不校验 ParentCode）。
- **修复**：① 加 visited 集合；② 加深度上限（如 20 层）；③ 新增/改文件夹时校验 `ParentCode` 不构成环；④ DB 层加 FK 或触发器（可选）。

## 4. P1 缺陷（语义错误 / 静默失败）

### P1-7 ★★★ 根因 A 的直接后果：删除用 `IsValid` 而非 `IsDeleted`

- 见 §2 根因 A。**修复**：`IsValid` 只留「启用/禁用」；删除一律走 `ISoftDelete`（`IsDeleted` + `DeleteTime` + `DeleteBy`）；转换中/草稿的可见性改用 `UploadStatus` / `ConvertStatus` 表达，不再借用 `IsValid`。

### P1-8 ★★ 删目录不级联，且目录查询不校验配置是否有效

- **证据**：`DeleteConfigAsync:189-198` 只把配置置 `IsValid=0`；而 `GetFolderTreeAsync:207`、`GetFilesByDirectoryAsync:1513`、`GetStageFileTreeAsync:1337` **只按 `DirectoryCode` 过滤，不检查配置**。
- **后果**：删掉的目录仍然**完整可见、可上传、可删除文件**。
- **修复**：级联软删（文件夹 + 文件 + 队列取消），或所有目录级查询先校验配置 `IsValid=1`。**建议两者都做**。

### P1-9 ★★ 建配置失败仍返回 success

- **证据**：服务 `:170-178` 返回 `(await _db.InsertAsync(config)).Data`（失败时为 `null`）；控制器 `:65-70` 无条件 `Ok(ApiResponse.Ok(data: result))`。
- **触发**：`DirectoryCode` 与已有记录撞 `uk_directory_code` → 1062。
- **后果**：前端收到"创建成功"，`data` 为 `null`。
- **修复**：服务改返回 `(ok, error, data)`；控制器按 `ok` 分支。

### P1-10 ★★ 队列创建失败时仍返回成功，且错误串被控制器丢弃

- **证据**：
  - `ReplaceFileAsync:979-982` → `return (true, $"替换成功，但转换队列创建失败：{qerr}", null);`
  - `UploadConfirmAsync:1073-1085` → 队列失败时 `convertQueueCode` 保持 `null`，**仍 `return (true, null, null)`**
  - 控制器 `:224-225` / `:203-204` → `ok ? Ok(data: new { convertQueueCode }) : Fail(error)` ⇒ **error 永远不被使用**
- **后果**：用户看到"替换成功/上传成功"，但**没有任何转换任务被创建**；文件停在 `ConvertStatus="pending"`，界面上长期显示"转换中"。错误信息被静默吞掉。
- **修复**：`ok=false` + error；或引入三态 `(ok, warning, error)` 并在前端展示 warning。

### P1-11 ★★ 替换文件时先作废产物、后建队列 ⇒ 建队列失败则产物永久丢失

- **证据**：`ReplaceFileAsync:944-982` 先 `InvalidateProductsAsync(file)`（清 `PreviewPdfPath`/`MarkdownPath`/`ConvertedStoragePath`）与 `ClearDocContentCacheAsync`，**之后**才创建队列；队列失败直接返回。
- **后果**：文件既没了预览/提取产物，也没有新任务去重建 ⇒ **预览与提取双双失效**，且用户只看到"替换成功"。
- **修复**：顺序反转（先建队列成功，再作废产物），或失败时回滚产物字段。

### P1-12 ★★ 「根级文件」接口用错了视图，返回的是全目录文件

- **证据**：`GetRootFilesAsync:391-404` 用的是 `UploadTaskDetailView`（`v_upload_task_detail`，按 **`TaskId`** 关联），而**专为此功能存在的** `v_standard_directory_root_files`（按 `FolderCode` 为空/不存在过滤）与实体 `StandardDirectoryRootFileView` **从未被使用**（全仓 0 处引用）。
- **后果**：接口文档说"目录根级别的文件"，实际返回**该目录下所有任务的所有文件**（含子文件夹、含草稿 `IsValid=0`），并且只回填 6 个字段（`FileCode`/`FileName`/`DirectoryCode`/`UploadStatus`/`StoragePath`），**`Code`、`Id`、`FolderCode`、转换状态全为 null**。
- **后果叠加**：列表里的草稿行点「删除」→ `DeleteFileAsync:430` 带 `IsValid == 1` 过滤 → 报"文件不存在"（**界面有行、操作说没有**）。
- **修复**：改用 `v_standard_directory_root_files`（视图已就绪，零成本）。

### P1-13 ★★ 重命名文件夹/文件后，`FullPath` 与 MinIO 对象名不跟着变

- **证据**：`UpdateFolderAsync:296-309` 只写 `FolderName`；`UpdateFileAsync:409-420` 只写 `FileName`/`Description`。**都不重算 `FullPath`，也不重命名 MinIO 对象**。而路径计算依赖 `FolderName`（`GetFolderPath:1684`）与 `FullPath`（`BuildFolderFullPathAsync:1262`）。
- **后果**：① `FullPath`（**判重键**，`UploadInitAsync:662-664` 用它查重）与实际不一致 ⇒ 重命名后再上传同名文件会被当成**新文件**，产生重复行；② `StoragePath` 仍指向旧对象名 ⇒ 与"路径身份段取 `Code`"的 V4 规范脱节。
- **修复**：这是 V4 §1.4 已识别的风险 4。P1 落地时必须同时实现「改名 → 重算 FullPath + 批量重命名对象（源+pdf+markdown）」或**禁止改名**（只能删了重建）。**建议后者**（单人开发，成本最低、语义最干净）。

### P1-14 ★★ 全实体写回（陷阱 ㉑）遍布，共 14 处

- **位置**：`:183`、`:195`、`:307`、`:351`、`:363`、`:418`、`:438`、`:757`、`:899`、`:1049`、`:1083`、`:1144`、`:2107`、`:2292`
- **后果**：这些位置都是「先读实体 → 改 1-2 个字段 → `UpdateAsync(实体)` 写**所有列**」。而 PDF 链与 Markdown 链**并发写同一行**（`:OfficeConvertService`）⇒ 后完成者用内存快照覆盖先完成者。这正是陷阱 ㉕ 实测过的现象（`MarkdownPath` 被清成 NULL，**日志却打印成功**）。
- **修复**：全部改为列级写入 `UpdateAsync(entity, nameof(X), ...)`。已在 `:891`、`:937`、`:1028`、`:1038`、`:1915` 等处用对的写法，**说明规范已知，只是没贯彻**。

### P1-15 ★ 删文件先删 MinIO 再改 DB ⇒ DB 失败则不可逆

- **证据**：`DeleteFileAsync:434-438`（先 `DeleteFileFromStorageAsync`，后 `UpdateAsync`）。`DeleteFolderRecursiveAsync:347-351` 同。
- **后果**：DB 更新失败 ⇒ 对象已没了，行仍 `IsValid=1` ⇒ 用户看到文件、点下载得到"文件不存在"。
- **修复**：先写 DB 状态（`IsDeleted=1` + `UploadStatus='deleting'`），再删对象，最后确认；或至少失败时把行标为异常态。

### P1-16 ★★ 「取消上传」无法还原被替换的文件内容

- **证据**：`UploadInitAsync:751-756` 替换分支把 `existingFile.StoragePath` **改成新路径**（`OldStoragePath` 只放进响应 DTO，**从未落库**）；`UploadCancelAsync:1130-1147` 删除 `file.StoragePath` 指向的对象后把行置回 `IsValid=1`，**但不恢复 `StoragePath`**。
- **后果**：用户"取消上传"后，文件行指向一个**已被删除的对象**；且因为同名文件路径相同，旧内容在上传时就被覆盖了 ⇒ **原内容永久丢失**，"取消"实际上是"破坏"。
- **修复**：正是 V4 §5.2 归档机制要解决的。P1 落地「替换前先归档旧对象到 `_archive`」后，取消即可从归档恢复。

### P1-17 ★ 下载失败一律报"文件不存在"

- **证据**：`DownloadFileAsync:445-459` 用 `catch (Exception ex) { log; return null; }`，控制器 `:170-171` 统一转成 `Fail("文件不存在")`。
- **后果**：MinIO 不可达、桶权限错误、对象损坏、网络超时 —— 全部显示为"文件不存在"，**排查方向被引向错误的地方**。
- **修复**：区分"对象不存在"（`IObjectStorage.ExistsAsync`）与"其他异常"，后者返回真实原因。

### P1-18 ★ 导出 ZIP 失败时写入假占位文件

- **证据**：`:1644-1648` `catch { await File.WriteAllTextAsync(localPath, $"[文件未找到] 原始路径: {objectName}\n错误: {ex.Message}"); }`
- **后果**：用户拿到一个"看起来正常"的 ZIP，里面混着伪装成真实文件的错误文本；若后续用这个 ZIP 做归档/交付，**错误被固化进产物**。
- **附带**：`:1627-1629` 当 `StoragePath` 为空时回退拼一个**旧格式**路径（`{StandardCode}/{PhaseCode}/{FolderCode}/{FileName}`），必然下载失败 ⇒ 必然产生占位文件。
- **修复**：失败即整体失败（返回 `success=false` + 失败清单）；或显式产出 `_FAILED.txt` 清单文件并在响应里标注，**不得混入同名占位**。

### P1-19 ★ 上传计数非原子 + 全实体写回 + 无幂等

- **证据**：`UploadFileAsync:894-900` 先 `taskToUpdate.SuccessCount++` 再 `UpdateAsync(taskToUpdate)`（全列）。
- **后果**：同一任务并发上传多个文件 ⇒ **丢更新**；同一 `fileCode` 重复上传 ⇒ 计数重复自增（无幂等判据）。
- **修复**：改 `UPDATE ... SET SuccessCount = SuccessCount + 1` 的原子自增；或由 `UploadConfirmAsync` 直接按文件状态统计（去掉这个计数器）。

### P1-20 ★ `UploadConfirmAsync` 对同一批文件双写，最终状态与注释不符

- **证据**：`:1023-1029` 先把 `UploadStatus="active"`、`TaskId=null`；`:1032-1039` 又把同一批可转换文件写成 `UploadStatus="uploaded"`、`ConvertStatus="pending"`。注释 `:1022` 说"全部文件激活：UploadStatus→active"，**实际可转换文件最终是 `uploaded`**。
- **后果**：两轮写库（2×N 次 UPDATE）；状态与设计文档/前端预期不一致。
- **修复**：合并为一次写入，明确"可转换文件的终态是 `uploaded` + `ConvertStatus=pending`"，并同步修正注释与前端判据。

### P1-21 ★ 文件夹序号按 `Depth` 取，且靠 `Split('|')` 反解复合码

- **证据**：`GetMaxSequenceAsync:1243-1260` —— 过滤条件只有 `DirectoryCode + Depth`（**不含 `ParentCode`**），再 `f.FolderCode.Split('|')` 取末段解析序号。
- **后果**：① 同层不同父的文件夹共享序号空间，序号语义混乱；② 与 `UploadInitAsync:658-689` 的 `seqCounter`（**跨深度全局递增**）是**两套不同算法** ⇒ 两条创建路径产生的序号规则不一致；③ 依赖 `|` 结构（陷阱 ㉗），P1 删复合码时必然重写。
- **修复**：P1 一并重写为「按 `ParentCode` 取 `MAX(SortOrder)`」，不再解析编码。

### P1-22 ★ 唯一冲突时静默改序号重试最多 100 次

- **证据**：`CreateFolderAsync:274-290` `catch (DuplicateKeyError) { FolderCode = Generate(..., maxSeq + attempt + 2); continue; }`
- **后果**：本该是 `S002` 的文件夹可能被静默写成 `S103`；掩盖了真正的并发/脏数据问题。`IsDuplicateKeyError:1322-1327` 靠**匹配异常消息文本**判断（`"1062"` / `"Duplicate entry"`），脆弱。
- **修复**：改为在事务内 `SELECT MAX + INSERT`，或直接改用 `Code`（P1 已删除 `FolderCode`，此问题自然消失）。

## 5. P2 缺陷（死代码 / 可维护性）

### P2-23 ★★★ `DbOrmExtensions.cs` 整个文件是**未被调用**的、会生成非法 SQL 的重复实现

- **证据**：
  - 三个方法 `BulkUpdateByConditionAsync` / `PhysicalDeleteByConditionAsync` / `QueryWithInAsync` 在全仓**零调用点**（grep 只命中自身定义）。
  - 框架 `IDbOrm` **已有同名方法**（`IDbOrm.cs:70,73`，参数化、正确实现）⇒ **API 分叉**。
  - `BuildWhereClause:75-85` 把 `Expression.ToString()` 字符串替换成 SQL：`&&` 在表达式树里是 **`AndAlso`** 节点，`.Replace(" && ", " AND ")` **永不命中** ⇒ 复合条件会生成含 `AndAlso` 的**非法 SQL**；单条件才碰巧能用。
  - `BuildSetClause:45-54` 生成 `SET \`Prop\`=@Prop` 但**从不绑定参数** ⇒ 执行必失败。
  - `:80` `.Replace(".IsDeleted", ".IsDeleted")` —— **空操作**，未完成的代码。
- **风险**：今天无害（无人调用），但它**长得像可用的 API**，迟早有人用。且它与框架同名，会让人误以为框架实现不可靠。
- **修复**：**整文件删除**。

### P2-24 `UploadFileAsync:879-886` 空 `if` 体

```csharp
if (isReplaceMode && !string.IsNullOrEmpty(file.Remark)) {
    var marker = $"[upload-replace:{taskId}]";
    if ((file.Remark ?? "").Contains(marker)) {
        // 从 remark 中提取旧路径（简化处理：不做旧路径删除，由 confirm 统一处理）
    }
}
```
废弃逻辑残留，且注释承诺的"由 confirm 统一处理"**在 confirm 里并不存在**。删除。

### P2-25 `v_upload_task_detail` 视图缺 `IsValid` 过滤，且是 `left join` 会产生 NULL 行

- 视图定义：`left join ... on t.TaskId = f.TaskId and f.IsDeleted = 0` —— **不筛 `IsValid`**，任务无文件时产生 `FileCode` 为 NULL 的行。
- 调用方 `GetRootFilesAsync` / `UploadCancelAsync` / `GetUploadStatusAsync` 各自手工兜底（`!string.IsNullOrEmpty(v.FileCode)`、`FileIsDeleted == false`），**兜底逻辑分散且不一致**。
- **修复**：视图本身把过滤条件写全（`IsDeleted=0` + 明确是否要 `IsValid`），调用方不再重复判断。

### P2-26 复合编码的反解点

`ParseDirectoryCode:244-254`、`GetMaxSequenceAsync:1251-1257` 都在 `Split('|')` 反解 `SDC-`/`FD-` 结构。P1 删除复合编码时**必须同时删这两处**，否则会留下"解析永远返回 null"的静默降级（`ParseDirectoryCode` 返回 `(null,null)` 时 `UploadInitAsync:616-621` 静默跳过，不报错）。

## 6. 为什么专家端没有这些问题（对比基线）

| 维度 | 标准目录链路 | 专家端（新写） |
