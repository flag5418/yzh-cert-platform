## 第 0 章 三点澄清的采纳与定级修订

### 0.1 关于 YZH.Core.Web：由「结构性缺陷」改判为「边界表达问题」

**采纳结论**：撤销 v1.0 中 A-1 的「结构性缺陷」定级，改判为 **P2（命名与边界表达）**。项目主导者明确该工程是刻意设计的**组合启动器**（组装入口），且核心框架工程未被业务代码污染——这与实测结果一致：反向引用业务工程只发生在 `YZH.Core.Web`，`YZH.Core.Api / DataBase / Stand` 的引用关系中不含任何 `CertPlatform.*`。

**但有三点实质关切保留**：

| 序 | 关切 | 建议 |
|---|---|---|
| 1 | **命名误导**：`YZH.Core.*` 命名空间下唯一一个携带业务引用的工程，会让后来者（包括 AI 协作者）误读「框架仓与业务无关」这条红线 | 改名为 `CertPlatform.Host`（或 `Yzh.Host`），让「框架 = 类库、宿主 = 组合根」在命名上一眼可辨 |
| 2 | **红线缺少可执行校验**：「核心框架不依赖业务」目前靠人记，未落成规则 | 加一条守卫：`YZH.Core.Api / DataBase / Stand` 的 `ProjectReference` 中不得出现任何 `CertPlatform.*`；宿主允许引用业务，但需显式登记为组合根 |
| 3 | **组合根职责未显式化**：既然它是启动器，就应只做装配（DI 注册、控制器程序集扫描、中间件、配置），不承载业务逻辑 | 建议把 `Program.cs`（225 行）中的 auth / CORS / Swagger 等装配段拆成扩展方法，保持组合根「一眼可读」 |

**仍然成立的独立问题**：v1.0 的 A-2（`CertPlatform.Auditor` → `CertPlatform.Admin` 横向依赖）与「启动器设计」无关，属业务域之间的真实耦合，仍建议按阶段 2 处理。审核端是对外交付一侧，与内部管理端编译期绑定过高，会限制后续授权与交付形态。

**连带降级**：A-3（空壳工程被宿主引用）在「宿主统一装配所有端」的解释下属合理预留，降为轻微项；仅建议为 `CertPlatform.Enterprise` 与 `Shared/WorkflowEngine` 各加一份说明文件，标注「计划中，暂未实现」，避免目录噪音被误读为半成品。

### 0.2 评价基准修订：从「产品级交付」切换到「MVP 分阶段基准」

v1.0 第 1.3 节的九维度评分隐含「产品级交付」基准，对当前阶段不完全公平。项目主导者已明确：这是面向体系认证三大核心功能的**快速原型验证**，目标是先把想法变成可论证的软件功能。据此修订评价基准：

| 阶段 | 目标 | 合格线 |
|---|---|---|
| A. 想法 → 功能（当前） | 三个核心功能可演示、可复现 | 功能闭环 + 单次结果可信 |
| B. 少量数据验证 | 稳定性与结果质量可度量 | 有标注数据集 + 有指标 |
| C. 单标准配置突破 | 与专家论证后至少一个标准达标 | 一个标准包端到端跑通且规则集被专家认可 |
| D. 合格系统 | 可交付、可审计、可维护 | 合规留痕 + 版本可追溯 + 可部署 |

**在此基准下，v1.0 下列问题在阶段 A/B 属「合理取舍」，不构成缺陷**：无 CI、无应用容器化、空壳工程与占位目录、数据不完整与规则不充分、编译告警未清零、前端测试少、95 表命名不统一、迁移命名多风格并存。这些统一移入「阶段化待办」，不再计入当前阶段的欠账。

**需要反向调高优先级的两项**：

- **E-1（无兜底收口）**：马上要进入「用少量数据验证稳定性」阶段，僵尸任务会直接污染验证结论。
- **E-4（无幂等键）**：验证阶段的典型动作是反复重跑，无幂等意味着每跑一次就产生一批脏数据，验证结果不可信。

**修订后的阶段 A 判断**：按 MVP 基准，当前完成度约 **4.0 / 5**——核心功能骨架已成型、工程自觉性（构建零错误、166 用例全通过、20 条前端守卫、498 篇文档）显著高于同类单人项目；主要欠账集中在「结果可度量」与「运行态保障」两项，恰好是进入阶段 B 前必须补的。

### 0.3 关于功能范围

项目主导者明确：不做完整体系认证流程（受理、合同评审、审核方案、认证决定、证书、监督），只做四件事——**审核员工作台、NC 自动检测、报告自动生成、企业文档规范化与自动填写**。这是**正确的收口**：完整流程是「过程管理」，产品化程度已高且与个人优势无关；而审核作业的智能增强是行业内尚未被充分产品化的空白区。v1.0 中一切与「流程完整性」相关的建议，在本文件中均按此范围裁剪。

## 第 1 章 体系认证专家视角：先厘清你做的到底是什么

### 1.1 定位

你描述的四件事，本质是**「审核员的智能工作台」**，不是「认证机构业务管理系统」。这个定位差别决定了很多设计取舍：

- 认证机构的业务管理系统（受理、合同评审、审核方案策划、认证决定、证书、监督）你不做——正确，那是流程管理。
- 你的价值在**审核作业的智能增强**：把审核员最耗时的三件事（读一堆散乱文件、判不符合、写报告）自动化。这条路在行业里属于尚未被充分产品化的空白区，创新性判断成立。

### 1.2 一个必须先接受的专业事实

**完整的 NC 判定依赖现场审核手段**：面谈、现场观察、记录抽样、跨部门追踪。任何纯文档/数据驱动的系统，都只能覆盖其中「文件审查（desk review）」与「体系文件符合性」这一部分。

因此建议：

1. 把能力域明确表述为**「不符合线索识别 / 差距检测（Gap Detection）」**，而不是「NC 判定」。你们代码里 `GapDetector` 的命名，比「NC 自动检测」更专业、更安全。
2. 对客户与专家沟通时，主张「**AI 给线索与依据，审核员下结论**」。这在 **ISO/IEC 17021-1**（认证机构要求）与 **ISO 19011:2018**（管理体系审核指南）的框架下是站得住的：不符合判定与认证决定属于有资格人员的职责，工具只能是辅助。
3. 这不是文字游戏，它直接决定三件事：输出形态（必须带「依据 + 置信度 + 待确认」标记）、留痕设计（谁在何时确认了什么）、责任边界（AI 不签署、不负责）。

## 第 2 章 四个核心功能的专家意见

### 2.1 模块一：企业文档规范化（数据入口）

**业务本质**：把企业给的「一堆格式各异、命名随意、层级混乱」的文件，整理成符合体系认证逻辑、可按条款检索的标准结构。这是整条链路的**燃料入口**——入口质量决定后面三件事的上限。

**专家意见**：

1. **分类体系按「文件化信息层级」落地**（行业通行心智模型，便于与专家对话）：
   - 一级：手册（方针目标、体系范围、过程交互）
   - 二级：程序文件 / 管理制度（对应标准的成文信息要求）
   - 三级：作业指导书、规范、表单模板
   - 四级：记录（含外来文件，如法规、客户要求）

   需要准确认识：**ISO 9001:2015 起标准已不再强制要求「质量手册」**，但绝大多数企业与审核实务仍沿用该四级结构。因此系统应**支持四层可配置**，而不是把结构写死。

2. **主索引用标准条款结构，不用企业组织架构**：条款维度（4 组织环境 / 5 领导作用 / 6 策划 / 7 支持 / 8 运行 / 9 绩效评价 / 10 改进）必须成为主检索入口，因为后续 NC 检测与报告引用都依赖它；企业自有的组织架构无法跨企业复用，只能做副索引。

3. **三段式而非一步到位**：`识别（文件类型 + 主题）→ 映射（条款 + 层级）→ 归一（命名 / 格式 / 元数据）`，每段之间输出「待人工确认清单」。**分类错误的代价是后续 NC 检测全盘偏移**，黑箱输出风险过高。

4. **命名规范要可枚举、可校验**（如 `层级编码-条款号-文件名称-版本-生效日期`），并做成可执行校验（沿用你已有的 guards 思路）。这样「规范化」才有验收标准，而不是主观判断。

5. **超长文档要分段与条款对齐**：手册动辄数万字，不做分段与条款锚定，后续按条款检索必然失败。建议每个文件产出结构化元数据：`文件ID / 类型 / 层级 / 主责条款 / 涉及条款列表 / 版本 / 生效日期 / 修订记录`。

6. **版本有效性判断是一等公民**：企业文件里常混有受控与非受控、作废版本。入口必须标注「现行有效 / 作废 / 非受控」，否则报告会引用作废文件——这在认证审核里是硬伤。

### 2.2 模块二：自动填写

**业务本质**：把已结构化的数据，按模板要求填进表单、记录、检查表。

**专家意见**：

1. **严格界定边界**：自动填写只做「模板 + 结构化数据」的填充；自由文本（审核结论、不符合描述）只出草稿建议，必须经审核员编辑确认。既保住价值，又把风险压到最低。
2. **字段分三类，策略不同**：
   - 强确定性字段（企业名称、标准编号、日期、部门）→ 直接填
   - 派生字段（如「是否建立内审程序」由文件映射结果推导）→ 填 + 标注来源
   - 判断性字段（有效性、适宜性结论）→ 只出建议，强制人工确认
3. **每个填入值都带字段级来源引用**（来自哪个文件、哪一条）。这是认证机构做记录审查时最先问的问题，也是你区别于通用生成式工具的核心竞争力。
4. **模板必须配置化**：不同标准、不同认证机构、不同规模企业的表单模板都不同，应作为「标准包」的一部分，严禁硬编码进 Skill。

### 2.3 模块三：NC 自动检测（核心中的核心）

**业务本质**：给定「企业客观证据（文件 / 记录）」与「审核准则（标准条款 + 企业自身文件 + 适用法规）」，找出证据与准则之间的偏离，给出分级与依据。

**专家意见（按重要性排序）**：

1. **判定三元组必须结构化沉淀**。任何一条线索都应落成：

   ```
   客观证据（原文引用 + 文件ID + 位置）
   ｜ 不符合准则（标准条款号 / 体系文件条款号 / 法规条款）
   ｜ 判定（符合 / 疑似不符合 / 一般不符合 / 严重不符合 / 观察项 OFI）
   ```

   这是整个系统最有价值的资产：它同时是检测输出、报告素材、复核对象、以及后续规则优化的数据。若当前只是「输出一段结论文本」，建议尽早改为三元组落库。

2. **分级规则要显式、可配置、可引用**：
   - **严重不符合（Major）**：体系性 / 区域性失效，或会导致体系无法实现预期结果的重大问题（如无内审、管理评审缺失、关键过程完全失控）。
   - **一般不符合（Minor）**：孤立、偶发、未构成体系性失效的偏离。
   - **观察项 / 改进机会（OFI）**：尚未构成不符合但存在风险。

   不同认证机构对分级尺度的把握存在差异，因此分级规则应当**作为标准包的可配置项**，输出时附「依据条款 + 判定理由」。

3. **小样本下的规则策略**：你提到规则不充分，这完全正常。建议「**最小可判定规则集 + 高频条款优先**」：
   - 优先覆盖审核中不符合最集中的领域：文件与记录控制、内部审核、管理评审、纠正措施、外部提供过程与供方控制、人员能力与培训、监视测量资源（含校准）、不合格输出控制。
   - 每条规则要素：`准则条款 → 所需证据类型 → 判定条件 → 默认分级 → 证据不充分时的降级策略`。
   - **「证据不足就说不确定」必须设计成一等公民**。宁可漏报，不可误报——误报在专家论证会上会直接摧毁可信度。

4. **可解释性**：每条判定固定四段输出：`事实（原文证据）→ 准则（条款原文）→ 差距分析（为什么不符合）→ 建议分级与整改方向`。这正是审核员写不符合报告的思维结构，也是最容易被专家接受的形态。

5. **防幻觉的工程约束**：LLM 参与的判定必须有「引用约束」——结论必须能引用到具体输入的某个片段，无法引用则降级为「无法判定」。这类约束应在**引擎层（节点级校验）**实现，而不是只写在提示词里。

6. **术语一致性**：全文统一「不符合 / 观察项」口径，避免与「缺陷 / 问题 / 异常」混用。跟专家沟通时，术语一致性很吃细节。

### 2.4 模块四：报告自动生成

**专家意见**：

1. **先分清报告家族，不要混为一谈**：
   - **不符合报告（NCR）**：单条不符合的结构化文书，含事实、准则、分级、受审核方确认、整改与验证。
   - **审核报告**：审核目的、范围、准则、时间、审核组、过程摘要、发现汇总、不符合汇总、结论与建议。
   - **内部记录**：审核计划、检查表、会议记录。

   建议**先做 NCR 与检查表**（结构化程度最高、最容易做对），再做审核报告全文。

2. **模板与内容分离**：报告模板（版式、章节、固定话术）属「标准包配置」，内容由三元组数据 + 汇总逻辑生成。不要把模板写进代码。

3. **结论必须可回溯**：报告中每一句结论都能跳到对应证据与条款。这既是质量保证，也符合审核记录须保留并可追溯的通行要求。

4. **审核结论保持保守三档**：推荐认证 / 有条件推荐（整改后验证）/ 不推荐。AI 只做**素材组织**，结论由审核员选择，且系统记录「谁在何时做出该结论」。

5. **从「格式正确」升级到「内容自洽」**：Office 写入已有测试覆盖是好的基础；建议追加生成后自检——必填字段完整性、条款引用是否存在、数字前后一致性。

### 2.5 模块五（承载者）：审核员模块

1. **审核员侧与内部管理侧应逐步解耦**（对应 v1.0 的 A-2）。审核员是外部用户（认证机构雇员或合作审核员），工作台一旦与管理端编译期绑定，后续授权与交付形态都会被限制。
2. **权限按「审核任务上下文」授权**：审核员只能看到自己任务范围内的受审核方资料。受审核方资料属商业秘密，这条属**保密底线**，当前若未做，应视为重要风险。
3. **AI 建议的每个动作都要留痕**（确认 / 修改 / 驳回：谁、何时、改了什么）。这既是责任界定，也是你后续优化规则最宝贵的数据来源。

### 2.6 四个模块的数据流（建议的目标形态）

```
企业原始文档 ──[规范化]──► 结构化文件库（条款索引 + 元数据）
                                  │
                                  ▼
                         [条款级证据抽取] ──► 证据池
                                                  │
   标准包（条款库 + 规则 + 分级 + 模板） ──► [差距检测] ──► 判定三元组（分级 / 依据 / 置信度）
                                                  │
                                                  ▼
                                    [审核员确认 / 修改（留痕）]
                                                  │
                                                  ▼
                                    [报告生成] ──► NCR / 检查表 / 审核报告
```

关键点：**规范化是入口、三元组是中枢、报告是出口**。中枢一旦结构化，入口与出口都可以替换升级而不伤主体。

## 第 3 章 给「突破一个标准」的建议

### 3.1 首选标准：ISO 9001

理由：

1. **通用性最强**：企业基数最大，专家与资料最易获取，论证成本最低。
2. **结构可迁移**：ISO 9001:2015 采用高阶结构（Annex SL，条款 4–10），与 ISO 14001:2015、ISO 45001:2018 等同构。把 ISO 9001 的「条款—证据—规则—报告」链条做成标准包后，向其他标准迁移时主要替换行业特定要求，主体框架可复用。
3. **规则稳定**：审核实务中不符合最集中的条款相对稳定（文件 / 记录控制、内审、管理评审、纠正措施、外部供方、人员能力等），适合用小规模规则集做出可验证效果。

补充：若目标客户以信息安全为主，则 ISO 27001 优先级上升。但要注意其**附录 A 是 93 项控制、4 个主题（组织 / 人员 / 物理 / 技术）**，规则库需按「控制项」组织而非按「章节条款」组织——**标准包的数据模型必须能同时容纳这两种结构**，这是选型时要提前确认的。

### 3.2 把「标准包」设计成一等配置单元

这正好契合你已有的「机构 + 标准 + 阶段 = 业务配置单元」模型。建议一个标准包至少包含：

`条款树 ｜ 条款要求原文与解读 ｜ 证据类型清单 ｜ 判定规则集 ｜ 分级默认值 ｜ 检查表模板 ｜ 报告模板 ｜ 术语表 ｜ 版本号`

三个好处：

- 换标准只换包；
- 规则可独立评审（专家可以只审规则集，不必理解代码）；
- 版本化后「某次审核用了哪个版本的规则」可追溯——这在论证与后续复核阶段极其重要。

### 3.3 带什么去论证

建议准备四份材料：

| 材料 | 内容 | 作用 |
|---|---|---|
| 可复现 demo | 同一份输入、同一版本配置，跑出同一结果 | 可复现性是专家信任的第一关 |
| 样例三元组 | 20–50 条「证据—准则—判定」，其中**必须包含若干反例**（明确不该判不符合的情形） | 让专家检验判定逻辑，而非只看成功的例子 |
| 边界与不确定性清单 | 主动列出「我做不到什么」（现场审核类发现、需行业专业知识的分级、证据不足的处理） | 比隐藏短板可信得多 |
| 度量数据 | 漏报率 / 误报率（哪怕样本很小）、单份文档处理耗时、单次审核 AI 成本 | 让论证从「感觉」变成「数据」 |

## 第 6 章 风险与底线

| 风险 | 说明 | 建议 |
|---|---|---|
| 误判责任 | AI 给出的不符合若被直接采信并写入报告，责任归属不清 | 一切判定必须经审核员确认，系统留痕；对外表述统一为「辅助工具」 |
| 保密义务 | 企业文件含商业秘密与个人信息 | 审核员按任务隔离访问、存储加密、访问审计；演示一律使用脱敏数据 |
| 规则过拟合 | 用少量数据反复调规则，换一家企业就失效 | 保留「留出集」（不参与调参的样本）；记录规则变更历史 |
| 标准版本变化 | 标准换版会导致条款号与要求变化 | 标准包版本化，条款树与规则集绑定版本 |
| 输出被当成品 | 报告草稿被直接使用 | 草稿带「待审核」标记；导出前强制人工确认 |
| 术语不统一 | 与专家沟通时口径不一致 | 建一份术语表（不符合 / 观察项 / 准则 / 客观证据 / 文件化信息……），全系统统一 |
