# 三大核心模块业务全链路重建


> 📅 生成日期：2026-10-02


---


## 第 1 章 总览：三个模块在同一条链上的位置与共用底座

### 1.1 平台只做三件事，三件事共用一套坐标系

这个平台的产品定位很窄：**它是审核员的智能工作台，不是一套发证系统**。审核员工台、NC 自动检测、报告自动生成、企业资料规范化与自动填写，四个功能覆盖的就是审核员日常最高频、最费时的动作（出处：V4 建设计划；评审结论）。发证流程、证书管理、收费管理等不在范围内。

支撑这三个模块的组织轴只有一条：**企业 × 标准 × 阶段**。系统里几乎所有的能力、参数、任务、规则都挂在这条三维作用域上，理解这条轴是理解全链路的前提。

| 轴 | 业务含义 | 为什么必须独立成轴 |
|---|---|---|
| 企业 | 认证主体 | 不同企业的资料、参数、结论彼此隔离，且是专家端列表的第一层展开 |
| 标准 | 认证依据（如质量、环境等各体系标准） | 一家企业可以同时认证多个标准，每个标准下的条例、模板、结论完全不同 |
| 阶段 | 认证所处环节（初次、监督、再认证等） | 同一标准在不同阶段要看的条款、要生成的章节不一样；资料也按阶段分批提交 |

这条坐标系不是文档里的抽象说法，它直接决定了几条硬业务规则：

- **同一企业、同一阶段、同一类型的任务，只允许存在一个未结束的任务**（出处：40·实施 12 号 D36）——避免专家重复发起、结论互相覆盖；
- **企业资料按「企业 × 阶段」管理，与标准无关**；而**参数按「企业 × 标准 × 阶段」维护**，与标准强相关（出处：05 册 26 号）——这个差异是本报告第 4 章的关键。

### 1.2 三层角色：一层定义，一层提供，一层消费

三个模块都可以按同一套三层结构来读，这也是本报告后续三章的统一切法：

| 层 | 谁 | 在系统里实际做什么 | 主要落点 |
|---|---|---|---|
| **后台定义侧** | 平台管理员、实施顾问 | 定义标准与阶段、NC 判定规则、报告模板与章节、企业参数定义、文档提取规则、文档生成规则 —— 即**定义「能力」** | 管理端配置类菜单 |
| **企业侧** | 企业（当前由专家在专家端代为操作） | 提供原始资料、补齐企业自身参数 —— 即**提供「事实」** | 专家端「资料库」、企业参数页 |
| **专家端应用侧** | 审核员 | 发起任务、审阅 AI 给出的线索、认可或修改、导出交付 —— 即**消费能力并下结论** | 专家端 6 个菜单 |

三者是**串行依赖**关系：定义侧没配好，专家端点了也没结果；企业资料没到位，AI 判不出、也生成不出。**任何一个环节缺失，链路都不成立**——这是后文反复出现的判断依据。

有一点必须点明，否则容易误读链路：**当前版本没有企业独立登录端**。企业资料的上传、企业参数的补齐，实质上都由专家在专家端完成；面向企业的协同系统与独立企业用户账号属于阶段 6 的规划（出处：专家端菜单册 §3.6）。这是现阶段的现实约束，不是设计遗漏。

专家端的整体结构也反过来印证了这个分工——专家端 1 个分组「专家系统」下挂 6 个子菜单（系统一览、企业管理、任务中心、资料库、组织与成员、系统设置），**全部是只读查看或任务操作，没有任何"定义能力"的入口**；所有定义动作都在后台（出处：专家端菜单与系统一览设计）。

### 1.3 贯穿三个模块的四条运转规则

这四条规则不属于某一个模块，而是三个模块共用的运行机制，后文会反复引用：

1. **任务管生死，结果管认定**。任务系统只负责创建、提交、归档、作废、取消这一条生命周期；而"认可 / 修改 / 导出"这类实质结论动作全部在**结果**侧完成。与之配套的是**状态三层分离**：执行态（系统跑到哪一步）、审核态（专家认不认可）、生命周期态（任务开不开启）各管一摊，互不干扰（出处：40·实施 12 号）。
2. **任务有三种来源**：NEW（首次做）、REDO（标准或规则变了要重做）、PATCH（只补做受影响的局部）。这解释了一个常见疑问——为什么同一个企业会反复出现同类型的任务。
3. **AI 给线索，人下结论**。每个模块在"出结论/出产物"之前都设了人工确认点，系统绝不直接替专家拍板（出处：评审结论）。
4. **规则用快照，历史不改写**。NC 检查与报告生成在任务发起的那一刻对规则/模板做快照；标准包**不建版本表**，靠三层快照加归档来追溯（出处：设计对照校准评审）。业务含义是：事后修改规则，不会污染历史上已出的结论。

此外还有一条所有模块共用的兜底原则：**AI 不可用时退化为「规则 + 人工」，不允许链路断掉**（出处：05 册 03 号）。这一点在三个模块的执行链里都有具体落点。

### 1.4 三模块阅读地图

| 模块 | 一句话定位 | 核心产物 | 链路特征 | 当前状态（详见第 5 章） |
|---|---|---|---|---|
| NC 自动检测 | 按标准条款逐条判定符合性 | 逐条款结论清单（四态 + 严重度） | 中：规则定义 → 资料基础 → 逐条判定 → 人工确认 | 设计与数据就位，代码未写 |
| 报告自动生成 | 按模板逐章节生成报告内容 | **章节列表**（非 Word 报告） | 中：模板定义 → 逐章节生成 → 逐章节认可 → 导出 | 设计与模板就位，代码未写 |
| 企业资料规范化与自动填写 | 把一堆原始文件变成结构化信息，再驱动生成产物 | 结构化画像 + 提取结果 + 填好的产物 | 长：上传 → 转 markdown → 画像 → 匹配 → 裁决 → 提取填充 | 底座有实物，表与页面最不齐 |

三个模块并非彼此独立：**模块 ③ 产出的"结构化信息"是模块 ① 判定的数据基础，也是模块 ② 成文的事实来源**。这条隐性依赖是判断先做哪个模块的核心依据，会在第 5 章展开。

## 第 2 章：NC 自动检测 —— 从后台规则定义到专家端一条条结论

### 2.1 模块定位与结论形态

NC 检查要回答的业务问题只有一个：**这家企业在这个标准下，每一条条款到底符不符合**。系统的做法是逐条款判定，而不是给一个总分。

判定结论有四种基本形态：符合、不符合、观察项、不适用。除这四态之外还有一个特殊态——**数据不足**（难以判定）。这个态的存在是本模块最重要的业务设计之一：当企业资料不足以支撑判断时，系统**不会硬猜一个结论**，而是把该条标为"数据不足"，悬置等待补资料（出处：03 号《详细设计-NC 检查》；40·实施 12 号）。这与"AI 给线索、人下结论"的产品原则是一致的。

不符合的条款还会带**严重度分级**，用于专家后续判断问题的性质与整改要求（出处：03 号）。

### 2.2 后台定义侧：把"怎么判"变成系统能执行的能力

| 项 | 内容 |
|---|---|
| 触发条件 | 引入新标准；某标准的条款判定要求调整；严重度分级规则调整 |
| 操作角色 | 平台管理员、实施顾问 |
| 输入 | 标准条款清单与逐条判定要求、严重度分级口径 |
| 系统动作 | 维护 NC 检查规则（按机构与标准维度组织）、维护严重度分级、设定判定模式 |
| 输出 | 一套可被专家端调用的规则集 |
| 人工确认点 | 规则发布前由实施人员审定，不做自动生效 |
| 界面位置 | 管理端规则配置类菜单（业务管理分组） |
| 文档出处 | 03 号；现状数据见专家端菜单册 §4.3 |

这一层的关键在于**规则是"按机构 + 按标准"组织的**，而不是一份全局通用规则。这直接带来了后文提到的机构关联键问题——只要机构这条线没打通，专家端就查不到该机构配了哪些规则。规则数据当前已有 4 条实际配置（出处：专家端菜单册 §4.3 能力数据）。

### 2.3 企业侧：资料齐备度就是判定的输入条件

| 项 | 内容 |
|---|---|
| 触发条件 | 企业被纳入某标准、某阶段 |
| 操作角色 | 企业提供资料（当前经专家端录入） |
| 输入 | 体系文件、运行记录、申请书等原始材料 |
| 系统动作 | 资料入库并归入「企业 × 阶段」，形成可供系统读取的资料集合 |
| 输出 | 可供判定的证据基础 |
| 人工确认点 | 资料确认与归类 |
| 界面位置 | 专家端「资料库」；任务详情·资料管理 Tab |
| 文档出处 | 40·实施 12 号；专家端菜单册 §3.2.1 |

企业侧在这一模块里**不是被动方**。企业资料的齐备程度直接决定 NC 能不能判——这就是系统里"缺数据预检"这个动作的业务含义：预检不过关，后面判定出的"数据不足"不是系统的失败，而是对现实的如实反映。

### 2.4 专家端应用侧：一条任务是怎么跑完的

专家端发起一次 NC 检查，系统内部按以下顺序执行（出处：03 号）：

| 步骤 | 谁在做 | 输入 | 系统/人的动作 | 输出 |
|---|---|---|---|---|
| 1 发起任务 | 专家 | 企业 × 标准 × 阶段 | 创建 NC 检查任务 | 一个未结束的检查任务（同企业同阶段同类型唯一） |
| 2 规则快照 | 系统 | 该机构该标准当前规则 | 把规则冻结为本次任务的快照 | 本次任务专属的判定依据 |
| 3 缺数据预检 | 系统 | 企业已入库资料 | 逐条款检查资料是否足够支撑判定 | 可判条款清单 + 数据不足条款清单 |
| 4 逐条判定 | 系统 | 规则快照 + 资料 | 按判定模式执行判定工作流，AI 给出四态结论与严重度 | 逐条款候选结论 |
| 5 结果归一化 | 系统 | 判定输出 | AI 失败或输出异常时转为人工处理 | 不出现"任务卡死" |
| 6 结论落库 | 系统 | 归一化后的结论 | 写入 NC 结果 | 可展示的结论数据集 |
| 7 人工确认 | 专家 | 系统给出的逐条结论 | 逐条认可或修改 | 最终结论 |

**人工确认点是这条链的终点，也是业务上最重要的一环**。系统给的是"线索与依据"，专家才是有权下结论的人；专家的修改会同步回该条 NC 的后续生命周期（出处：03 号）。

界面上，这条链的入口是专家端「任务中心」下的 NC 检查；任务发起后在任务详情页内操作，结论确认落在**检查结论 Tab**（任务详情共六个 Tab：企业信息 / 资料管理 / 执行情况 / 检查结论 / 报告 / 标准条款）（出处：专家端菜单与系统一览设计）。此外还有独立的"NC 检查记录"结果视图，用于跨任务查看与导出，采用左树右表结构（企业 → 阶段 → 任务三级），"看结果"和"干活"在界面上是分开的（出处：40·实施 12 号）。

### 2.5 三个容易被忽略的设计点

- **数据不足（待补资料）是合法结论**。它不是错误态，而是把"证据不足"这一现实显式记录下来，避免 AI 硬判带来的假结论。
- **规则快照保证历史不可改写**。专家半年前出的结论，不会因为今天改了规则而变了口径。
- **规则变更后的处理方式是重做而非改史**。任务来源里的 REDO 就是为此存在的——规则变了，新发起一次任务，旧结论原样保留。

需要提醒的一处口径冲突：**"观察项"与"数据不足"在枚举层面的归属尚未收敛**（设计对照校准评审指出该冲突）。这是业务上必须先裁决的事项，因为它决定专家端看到的是四个选项还是五个、以及"数据不足"是否算一种正式的符合性结论。此项列入第 5 章待裁决清单。

## 第 3 章：报告自动生成 —— 从章节模板到专家逐章节认可

### 3.1 先纠正一个最容易误解的点：产物不是 Word 报告

这是本模块最需要先说清的business事实：**系统不生成 docx 报告文件**。它产出的是**一份章节列表**——按报告模板拆好的章节，每章一段系统生成的正文，由专家逐章节认可或修改，最后整体导出为 Excel（每个标准一个工作表）（出处：04 号《详细设计-报告生成》；40·实施 12 号 D14；设计对照校准评审）。

这个选择是刻意的。原因在于报告的价值在于"内容对不对"，而不在于"排版好不好看"：审核员真正需要的是逐章节确认内容，排版和成稿是后续环节的事。之前把产物理解为"报告家族 + 先做 NCR"是一种误读，已被明确撤回（出处：设计对照校准评审）。

因此本模块的业务产物应该这样理解：

| 层级 | 是什么 | 谁在维护 |
|---|---|---|
| 配置层 | 报告模板与章节配置：某标准下的报告由哪些章节组成、每章节怎么生成 | 后台（管理员/实施） |
| 实体层 | 某次任务实际使用的章节清单（发起时的快照） | 系统自动生成 |
| 结果层 | 每个章节最终被专家认可的内容 | 系统生成 + 专家确认 |

### 3.2 后台定义侧：模板与章节是"生成能力"的载体

| 项 | 内容 |
|---|---|
| 触发条件 | 新标准接入；报告结构或表述要求调整 |
| 操作角色 | 平台管理员、实施顾问 |
| 输入 | 报告结构要求、每章节的内容口径 |
| 系统动作 | 维护报告模板，并为每个标准配置章节清单；对需要自动生成的章节，指定其对应的生成流程 |
| 输出 | 一套可被专家端调用的报告章节配置 |
| 人工确认点 | 模板与章节配置发布前人工审定 |
| 界面位置 | 管理端报告模板/章节配置类菜单 |
| 文档出处 | 04 号；现状数据见专家端菜单册 §4.3 |

现状：报告模板已有 2 条实际配置（出处：专家端菜单册 §4.3 能力数据）。

### 3.3 企业侧：资料与参数决定"哪些章节能成文"

| 项 | 内容 |
|---|---|
| 触发条件 | 企业进入某标准某阶段，需要出报告 |
| 操作角色 | 企业提供资料与参数（当前经专家端录入/补齐） |
| 输入 | 已入库的企业资料、企业参数 |
| 系统动作 | 作为章节生成的素材来源；参与缺数据预检 |
| 输出 | 支撑各章节成文的事实基础 |
| 人工确认点 | 资料与参数确认 |
| 界面位置 | 专家端「资料库」、企业参数页 |
| 文档出处 | 04 号；05 册 26 号 |

关键业务含义：**报告不是"有模板就能生成"，而是"资料到哪一步，章节就生成到哪一步"**。哪几个章节的数据没到位，系统在预检阶段就能识别出来，而不是等生成完才发现满篇空话。

### 3.4 专家端应用侧：一条报告任务是怎么跑完的

| 步骤 | 谁在做 | 输入 | 系统/人的动作 | 输出 |
|---|---|---|---|---|
| 1 发起任务 | 专家 | 企业 × 标准 × 阶段 | 创建报告生成任务 | 一个未结束的报告任务 |
| 2 章节快照 | 系统 | 该标准的报告章节配置 | 冻结为本次任务的章节清单 | 本次任务专属的章节结构 |
| 3 缺数据预检 | 系统 | 企业资料与参数 | 逐章节检查素材是否齐备 | 可生成章节 + 缺口章节清单 |
| 4 逐章节生成 | 系统 | 章节配置 + 素材 | 按章节执行生成；若某章节未配置生成流程，则降级为按模板示例产出 | 逐章节草稿正文 |
| 5 结果归一化 | 系统 | 生成输出 | 异常时转人工处理，链路不断 | 可展示的章节草稿 |
| 6 人工确认 | 专家 | 逐章节草稿 | 逐章节认可或修改 | 最终章节内容 |
| 7 交付导出 | 专家 | 已认可的章节 | 导出为 Excel | 交付文件（每标准一个工作表） |

这里有两个需要特别说明的设计：

- **降级生成**：如果某个章节在后台没有配置对应的生成流程，系统不会报错中断，而是用模板里的示例内容作为占位产出（出处：04 号）。这让报告链路在配置不完整时依然可跑，但同时也意味着**产出的质量取决于后台配置的完整度**。
- **多标准分节**：当一次任务覆盖多个标准时，报告按标准分节组织；导出时每个标准独立成一个工作表（出处：04 号）。

人工确认同样是逐章节进行的，粒度比 NC 检查（逐条款）更粗，但性质一致——系统给草稿，专家定稿。

界面上，入口是专家端「任务中心」下的报告生成，操作落在任务详情页的**报告 Tab**；独立的"系统认证报告"结果视图承担跨任务的查看与导出，同样采用左树右表（企业 → 阶段 → 任务）结构（出处：专家端菜单与系统一览设计；40·实施 12 号）。

### 3.5 本模块当前最需要拍板的两件事

1. **产物形态是否最终确认**。当前设计明确"不做 docx、导出 Excel"。若业务方仍期待拿到一份可直接交付的成稿文档，就需要补一个后续环节（排版成稿），这属于范围决策，不属于技术实现。
2. **版本号口径**。设计对照校准评审中已识别出报告相关的版本号表述需要统一修正（出处：设计对照校准评审），否则后续实现会出现同一概念多种叫法。

## 第 4 章：企业资料规范化与自动填写 —— 从一堆原始文件到一份填好的产物

### 4.1 模块定位：原始文件不是主数据，结构化信息才是

这是三个模块里链路最长、也最容易被误读的一个。它做的不是"文件管理"，而是一条**信息提炼管道**：

> 企业交上来的是**一堆格式各异的原始文件**；系统要把它变成**可以直接被程序使用的结构化信息**；最后用这份结构化信息，去**自动填出**企业还需要提交的标准文档。

理解这句话，就能理解本模块为什么有那么多中间步骤——每多一层加工，都是为了让"原始文件"变得可计算。反过来也成立：**这层结构化信息（文档画像 + 文本内容 + 提取结果）是本模块的主数据**，原始文件只是来源（出处：05 册 34 号《核心模块定位与端到端流程》）。

### 4.2 后台定义侧：四类定义决定这条管道能跑多深

| 定义项 | 定义什么 | 谁维护 | 当前状态 | 出处 |
|---|---|---|---|---|
| 体系认证全局参数定义 | 在某「机构 × 标准 × 阶段」下有哪些企业参数、参数编码与名称、取值来源、由谁维护 | 平台管理员/实施 | **已实施**：已改造为左树右表，取值接口实测通过 | 26 号（R4 已实施） |
| 标准核心字段 | 标准层面的核心字段清单 | 平台管理员/实施 | 已有 | 34 号 |
| 文档提取规则 | 针对某类标准文档，要提取哪些字段与表格、如何生成提取指令 | 平台管理员/实施 | 已有基础，待完善；提取能力本身尚在重新设计 | 26 号；28 号（提取 Skill，设计中） |
| 文档生成规则定义 | 生成产物用哪些模板与锚点、填写语义怎么定 | 平台管理员/实施 | **未建**（新建菜单，编码待定） | 26 号 |

这里有一条容易被忽略但很关键的因果：**标准核心字段是"分析策略"的前置条件**（出处：05 册 34 号）。业务含义是——后台没定义清楚这个标准的核心字段，系统就无从判断一份文件到底该重点处理还是可以略过，整条管道的入口闸门就打不开。

### 4.3 企业侧：资料进来的那条链（上传 → 转 markdown → 分析策略 → 画像）

企业资料上传后的流水线是四步，顺序不能颠倒（出处：05 册 03 号《业务流程与状态机》）：

| 步骤 | 系统做什么 | 产出 | 人工确认点 |
|---|---|---|---|
| ① 上传 | 接收原始文件，落入「企业 × 阶段」的资料范围 | 待处理文件 | 上传范围由人指定 |
| ② 转 markdown | 把各种格式的文档统一转成可读的文本形态 | 文件的文本内容 | 无（自动） |
| ⓪ 分析策略判定 | 判断这份文件要不要做深度处理 —— 三种处置：正常分析 / 跳过 / 忽略 | 该文件的处理策略 | **AI 给建议，人工确认** |
| ③ 文档画像 | 给文件打上"这是什么文件、起什么作用"的画像 | 文档画像记录 | 可人工修正 |

三个必须讲清的业务细节：

1. **原子任务是单个文件**。一个文件就是一个队列任务；而"范围"（整体 / 按标准 / 按目录 / 按文件）只决定队列里装哪些文件（出处：26 号）。这样设计的好处是单个文件失败不会拖垮整批。
2. **"忽略"是一种合法处置**。企业交上来的资料里必然有大量与认证无关的文件，系统允许把它们标记为忽略或跳过，避免后续无谓的算力与人工消耗（出处：26 号）。
3. **这一步是"资料入库"的真正终点**。走完这四步，文件才真正具备了被后续匹配和填充使用的前提。

### 4.4 专家端应用侧：产物出去的那条链

专家端在本模块承担两段工作，分属两个不同菜单：

**第一段：企业参数补齐（企业 × 标准 × 阶段）**

系统把后台定义的参数清单与该企业已有信息自动关联，形成一个"还差哪些参数"的待完善清单，由企业（当前经专家）逐项补齐（出处：26 号）。这一步必须在生成之前完成，否则产物里会出现大量空白项。

**第二段：企业资料规范化与自动填写（企业 × 标准 × 阶段 × 目录 × 文档）**

这是本模块的主流程，按以下顺序推进（出处：05 册 03 号）：

| 步骤 | 谁在做 | 做什么 | 产出 |
|---|---|---|---|
| 启动处理 | 专家 | 在指定范围内启动规范化流程 | 一条处理队列 |
| 召回 → 精排 → 冲突识别 | 系统 | 把企业已有资料与目标文档的要求做匹配，排出候选并识别出互相矛盾的候选 | 带候选与冲突的匹配结果 |
| 人工裁决 | 专家 | 对存在冲突或不确定的匹配做出选择 | 确定的匹配关系 |
| **分叉处理** | 系统 | **按文档类型走不同路径**（见下） | 短路结果 或 提取填充结果 |
| 提取与填充 | 系统 | 对需要生成的文档，抽取所需数据并填入模板 | 生成产物 |
| 落笔写盘 | 系统 | 把填写结果写入目标文件 | 可下载的成品文件 |

**分叉是本模块最核心的业务规则**——不同文档的处理深度完全不同：

- **固定类文档（fixed）：短路**。这类文档内容完全固定、不需要企业信息参与，匹配到即结束，**不进入填充环节**。在泳道图上表现为"走到匹配就到终点"（出处：05 册 34 号阻断项 B4 指出当前泳道图缺这条短路分支，需要补画）。
- **混合类文档（hybrid）：短路**。主体固定、少量内容需替换，处理方式上同样不进入完整填充流程。
- **可编辑类文档（editable）：进入提取 + 填充**。这才是真正"自动填写"的部分——从企业已有资料中提取所需值，填入模板生成成品（出处：05 册 34 号；03 号）。

填充环节有两条工程上的铁律，业务表现上就是"系统不会乱写文件"（出处：26 号）：

- **归一：AI 只负责产出值**。即输出一份"锚点 → 值"的对应关系，不直接操作文件；
- **落笔：由专用写入能力把值填到文件的具体位置**。这种职责分离保证了即使 AI 输出异常，也不会破坏文件结构。

另外一条贯穿规则：**匹配与填充只读取已经解析好的结果，不回读原始文件**（出处：26 号）。这既是性能考虑，也是准确性考虑——一次解析、多次使用，避免不同环节对同一份原件得出不同理解。

### 4.5 现状：底座比想象中扎实，业务链路比想象中薄弱

这个模块有个反差很大的特征——**技术底座是三模块里最成熟的，但业务链路是三模块里最不齐的**：

已经有的实物：

- 资料提取链路底座已经存在，且跑过真实数据（12 份完成 / 3 份失败）（出处：企业资料管理现状）；
- 填充引擎以纯函数形式已实现四项能力（出处：34 号）；
- 纸面实验：167 份文档的确定性锚点识别率达到 98.6%（出处：34 号）——这是三个模块中唯一有实测准确率数据的环节；
- 后台参数页与企业参数页已改造为左树右表并实测通过（出处：26 号 R4）；
- 文件写入能力已封装完成，15 个源文件、4 组测试、148 项测试全部通过（出处：26 号 R5）。

还没有的：

- 核心业务表尚未建成、关键字段缺失、种子数据为零（出处：34 号阻断项 B1–B4）；
- 上传与规范化两个页面尚未建设（出处：26 号）；
- 上传之后的提取能力正在重新设计（28 号），生成侧因此暂时没有稳定输入；
- 整份菜单功能设计仍处于**待审批**状态（出处：26 号文档状态），并且遗留了若干需要业务方拍板的问题项。

**结论**：这个模块不是"做不出来"，而是"还没被允许全面开工"。它同时是三个模块中工作量最大、依赖最多的一环，具体判断见第 5 章。

### 5.4 依赖的先后顺序（本文建议）

上述依赖不是并列关系，存在明确的先后约束。按"不解决就会导致其他工作白做"的标准排序：

1. **先打通 D-1、D-2**——这两项是所有页面的地基，且属于"静默失败"型问题，越晚发现代价越大。它们工作量小、收益立竿见影。
2. **再处理 D-3**（建表、补字段、种子数据）——这是三个模块共同的落地前提，没有它，任何编码都只能停在纸面。
3. **同步启动模块 ③ 的提取能力设计**——它是长周期项，且是模块 ① 的判定输入、模块 ② 的事实来源。它启动得越晚，整条数据主轴成形越晚。
4. **D-4、D-5、D-6 属口径收敛**，应在 ①② 开始编码前完成，成本低但能避免大面积返工。
5. **模块 ①② 可在第 1、2 步完成后并行开工**——它们链路短、依赖少，是三个模块中最快能见到成效的部分。
6. **模块 ③ 的上传页与规范化页放在最后**——它是全链条上依赖最多、工作量最大的一段，且 26 号尚待批准。

需要说明：以上顺序为本文基于依赖关系给出的建议，非源文档既有结论。

### 5.5 业务视角的可执行性判断

**设计的合理之处**

- **边界克制**。产品只做三件事，不贪大求全，排除了证书管理、收费等与核心价值无关的范围，这是这类系统最常见也最致命的膨胀点。
