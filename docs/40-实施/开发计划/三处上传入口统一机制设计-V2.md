## 零、一页结论

**后端早就统一了** —— 不是"三处类似"，是**同一套代码**，连数据表都共用。
**真正分裂的是前端**，且形态是「**底座建好了、页面没接入**」：共享组件、共享状态字典、**实时进度通道**都已存在，三个页面各写各的。

⇒ 本设计**不是"从零抽一套通用机制"**，而是两件事：
1. **把已有底座接到三个页面上**（接入类工作，风险低）
2. **补齐确实不存在的机制件**（**文件操作机制族** + 队列横幅）

| 层 | 现状 | 要不要动 |
|---|---|---|
| 后端 · 路径规则 | `PathBuilder` 三处**全接**（三个前缀，同一套规则 + 同一套产物段 `pdf/`·`markdown/`·`editable/`） | ⛔ 不动 |
| 后端 · 上传契约 | `UploadFilePolicy` + `upload-file-policy.json` = 唯一事实源，前端常量由脚本生成 | ⛔ 不动 |
| 后端 · 转换能力 | `IFileConvertCore` = **唯一内核**，三处**全部委托** | ⛔ 不动 |
| 后端 · 语义释义 | `LlmInvokeService` 唯一；入口服务 2 个 → **收敛为 1 个**（裁决① 已定案） | ✅ 收敛（唯一后端改动） |
| 后端 · 队列 | `QueueManager` 唯一框架（按 `TaskType` 分派） | ⛔ 不动 |
| 后端 · 实时推送 | `IYzhMessagePusher` → `YzhMessageHub`（`/api/yzh-msg`）**已通**；`CertQueueNotifier` 已在推队列进度 | ⛔ 不动（前端接入即可） |
| 后端 · 数据 | 标准文档 + 企业资料库**同一张表**（靠 `EnterpriseCode` 区分）；原始资料独立表 | ⛔ 不动 |
| 前端 · 上传组件 | `YzhFolderUpload` 已有，**2/3 处用**（企业资料库用裸 `el-upload`） | ✅ 接入 |
| 前端 · 状态字典 | `utils/convertStatus.ts` 已有（含双链合并 `mergeConvertStatus`），**1/4 处用** | ✅ 接入 |
| 前端 · **文件操作机制族** | ❌ **不存在**，上传/替换/下载/打包四处各写各的（含 2 组「同名不同参」） | ✅ **新建** |

| 前端 · 队列横幅 | ❌ 无共享件，**2 处复制**（第 2 份注释自认"照抄"） | ✅ **新建** |
| 前端 · 文件夹树 | ❌ **2 份**（252 / 396 行，后者自认"照抄"前者） | ✅ **合并** |

**一句话回答用户**：能抽，但抽的不是"页面"，是"**机制 + 展示件**"；后端不用抽（已经是了），前端是"接回去 + 补齐"。

## 一、问题陈述

### 1.1 用户原话

> 「我们有 3 个地方文件上传，标准文档管理、企业资料库、企业原始资料，其实这 3 个大类，界面，后台的转 pdf 转 markdown 还有释义，包括队列基本都是类似的，我觉得整体的页面，特别是队列，上传相关的也是类似的，分析是否可以写一套通用的机制进行复用」

**V2 追加（2026-10-16）**：

> 「比如文件上传，文件替换，文件下载，文件打包等这些可以统一」—— 复用范围由「上传」扩展为**文件操作机制族**。

### 1.2 拆成两个问题（这两个问题的答案**相反**）

| # | 问题 | 答案 |
|---|---|---|
| Q1 | **后台**的转 PDF / 转 MD / 释义 / 队列，是否重复？ | ⛔ **不重复** —— 已是同一套实现（§2.2 逐条举证） |
| Q2 | **前端**的页面 / 上传 / 替换 / 下载 / 打包 / 队列展示，是否重复？ | ✅ **重复严重** —— 但根因不是"没人抽"，而是"抽了没接"（§2.4 ~ §2.6） |

⚠️ 这个区分很重要：如果把 Q1 也当成"要抽"的，就会去重构一套**已经统一、且踩过坑**的后端链路（`IFileConvertCore` 上有并发列白名单、回填裁剪、产物作废等一堆血泪约定，见 `skill yzh-add-convert-chain`），**纯属自伤**。

## 三、★ 复用边界（能抽什么、不能抽什么）

### 3.1 ✅ 可复用 —— 「机制」

| 可抽项 | 为什么能抽 |
|---|---|
| **上传管线编排**（校验分区 → [可选 plan] → init → file → confirm → 进度） | 三处的**协议骨架**同形（`init/file/confirm`），差异只在端点名、入参、以及**是否有 `plan`**（见 §3.4） |
| **★ 替换机制**（选文件 → 覆盖上传 → 回填 → 进队列） | 两套 `replaceFile` 名字相同、动作一致，只是参数与端点不同 ⇒ 差异收敛为参数 |
| **★ 下载机制**（取 Blob → 命名 → 触发保存） | 保存逻辑已有 3 份等价实现 ⇒ 天然可合一；**取数端点**各页注入 |
| **★ 打包机制**（范围选择 → 请求 ZIP → 保存） | `packageNormalize` 已是现成范式，机制可抽；**范围口径**各页注入 |
| **文件校验与分区**（`partitionUploadable`：接受 / 系统噪声 / 拒收） | `upload-file-policy.ts` 已是唯一事实源，逻辑本就共用 |
| **进度获取**（轮询 或 推送） | 三处都在做同一件事（5s 轮询），差异只是"查哪个端点"；实时通道已通（§2.5） |
| **队列横幅展示**（进度条 + 文案 + 计数） | 纯展示，无业务语义 |
| **文件夹树**（递归 + 计数汇总 + 每节点文件表） | 两份已经是同一结构，只是数据类型不同 |
| **状态文案与徽标** | 字典已存在（`convertStatus.ts`），只需接入 |

### 3.2 ⛔ 不可复用 —— 「业务语义」

| 不可抽项 | 为什么不能抽 |
|---|---|
| **列定义** | 标准文档：名称/大小/状态/修改时间/操作；资料库：`FileName/Status/ExtractState/VersionNumber`；原始资料：`FileName/ExtractState/VersionNumber`（**无标准列**） |
| **状态机** | 标准文档 = `ConvertStatus`；资料库 = `SlotStatus`（live/missing/removed）；原始资料 = `ConvertStatus` + `AnalyzeStatus` + `AnalyzePolicy` |
| **版本语义** | 标准文档模板行**恒 v1**；资料库有 `cert_enterprise_file_version`；原始资料是 `Sha256` 幂等 + 独立版本表 |
| **归属与分组** | 标准文档有 `StandardCode/StageCode`；资料库按标准分 Tab；原始资料表**无标准列**（标准在画像表） |
| **操作按钮集** | 三处的可用操作不同（补产物 / 替换 / 提取信息 / 钉住取值 …） |
| **★ 下载的口径** | 裸 `storagePath` / `fileCode` / 模板路径、是否带 `enterpriseCode`，各不相同 ⇒ **只抽「Blob→保存」，不抽取数** |
| **★ 打包的范围与产物** | 「打哪些、打谁」（已规范化产物 / 原件 / 按阶段）是业务口径；且**打包导出 ≠ 压缩包上传**（见 §3.3 注） |

### 3.3 ⛔ 明确不做：「一个配置驱动的万能上传页」

三处业务语义确实不同（§3.2）。强行合并会造出一个满是 `if (kind === 'standard') … else if (kind === 'library') …` 的页面 —— 那只是把三份代码塞进一个文件，**可读性更差、改一处怕碰三处**。

**原则**：抽「**怎么做**」（管线、替换、下载、打包、进度、展示），不抽「**做什么**」（列、状态机、操作、口径）。
这与项目既有判据一致 —— 「**整合 ≠ 去重**」。

> ⚠️ **打包的双向性（必须区分）**：本设计抽的是**打包导出**（服务端产 ZIP → 下载）。而「上传压缩包自动解压」是**另一件事** —— `upload-file-policy.ts:84-87` 明令 `archive` 类别**默认不允许**，注释写明「要支持应新增**解压任务**，而不是放宽白名单」。⛔ 二者不得合并。

### 3.4 ★ 协议形状纠正（V2 新增）

V1 §3.1 断言「三处都是 `plan/init/file/confirm` 四段」—— **错误**。实测：

| 页 | 端点序列 | 谁是「匹配预览」 |
|---|---|---|
| 标准文档管理 | `upload-init` → `upload-file-v2` → `upload-confirm`（**无 plan**） | 无（本地 `partitionUploadable` 直接分区） |
| 企业资料库 | `upload/plan` → `upload/init` → `upload/file` → `upload/confirm` | `plan` 走 `DispatchMatcher` M0–M3 |
| 企业原始资料 | `upload/plan` → `upload/init` → `upload/file` → `upload/confirm` | 同上 |

⇒ 可复用管线的正确形状是「**`init → file* → confirm` + `plan` 可选**」，且「本地校验分区」与「服务端 plan」是**两个独立步骤**。⛔ 设计时不得把 `plan` 当必备环节（否则标准目录无处安放）。

## 四、设计方案

### 4.1 分层

```
L3 业务层（各页自留，⛔ 不抽）
   ├─ 列定义 · 状态机映射 · Tab/树结构 · 操作按钮 · 下载/打包口径
   └─ 只消费 L2 的件，不重复实现机制

L2 展示层（cert-share/src/components/ 共享件）
   ├─ YzhQueueBanner.vue     ← 新建（替代 2 份复制）
   ├─ YzhFolderTree.vue      ← 合并（替代 2 份 ~300 行）
   └─ 状态文案/徽标           ← 复用已有 convertStatus.ts + CertConvertBadge.vue

L1 机制层（cert-share/src/composables/）
   ├─ useFileOps.ts（族）    ← 新建（替代 上传/替换/下载/打包 四处各写）
   └─ useUploadProgress.ts   ← 收口轮询 + 改接 SignalR（/api/yzh-msg）
```

### 4.2 L1 — 文件操作机制族（新建，替代四处各写）

**职责**：把「怎么操作文件」编成一套可注入端点的管线；**端点、口径、业务子集由调用方注入**。

```
useFileOps({
  acceptCategories,            // 复用 upload-file-policy 的类别（含业务子集）
  upload:  { init, file, confirm, plan? },   // plan 可选（§3.4）
  replace: { run },            // 各页注入自己的 replaceFile（2 套签名差异收敛到此）
  download:{ fetchBlob },      // 各页注入取数端点；保存统一
  package: { run },            // 各页注入打包口径；保存统一
  progress,                    // 见 4.3
})
→ { accepted, noise, rejected, stage, progress, error, start(), cancel(), replace(), download(), pack() }
```

**收益**：三/四处各删约 120 行编排 + 约 70 行轮询 ⇒ 净减 **约 500+ 行**，且「上传后必须轮询」「噪声文件静默剔除」「下载必走 Blob」「保存用统一命名」这类**约定只写一次**。

⚠️ 设计要点（都是本项目踩过的坑）：
- **`accept` 必须由 `buildAcceptAttribute()` 生成**，⛔ 页面不许再硬编码后缀串（`upload-file-policy.ts:153` 注释已明令）
- **系统噪声静默剔除、不阻塞**（`.DS_Store` 等；曾因"一个不合规就整体中止"导致整文件夹传不上去）
- **`plan` 必须可选**（§3.4），标准目录不传
- **`download.fetchBlob` 必走鉴权 Blob**，⛔ 禁裸链接（`useDirectoryApi.ts:128-131` 注释已明令）
- 先**消同名**：`downloadBlob`（utils vs enterprise-file）、`replaceFile`（useDirectoryApi vs enterprise-file）两处同名不同参，**合并时以签名区分或改名**，避免 import 歧义

### 4.3 L1 — 进度获取（**收口轮询 + 启用 SignalR**，裁决 ② 已定案）

- **兜底**：把三处 `setInterval` 5s 轮询收口为一个 composable（替代 `directory:338` / `resources/logic.ts:557` / `enterprise-original/logic.ts:197`）。
- **实时**：订阅**已通**的 `/api/yzh-msg`（`YzhMessageHub`），消费 `CertQueueNotifier` 已推的 `QueueProgress`，用于**提速**；轮询仍在，作**掉线/丢消息兜底**。
- ⛔ **不接** `/api/yzh-upload`：`UploadProgressHub` 无生产者（§2.5），接了会"永远没有进度且不报错"。
- ⚠️ 现有 `useUploadProgress.ts` 连的正是坏 Hub ⇒ 要么**改接 `/api/yzh-msg`**，要么**标注弃用**，不得原样接入。

### 4.4 L2 — 两个共享件

| 件 | 替代 | 要点 |
|---|---|---|
| `YzhQueueBanner.vue` | `directory:970` + `enterprise-original:229` 两份复制 | 入参 = `{ active, label, progress, done, total }`；⛔ 不查队列、不含业务判断（纯展示） |

### 4.5 L3 — 各页保留（清单见 §3.2）

三处**必须各自保留**：列定义、状态机映射、Tab/树结构、操作按钮集、**下载/打包口径**。改造后各页只做"配置 + 插槽"，不再实现机制。

### 4.6 与既有 V3 计划的关系（**不推翻，是它的"前端下半场"**）
