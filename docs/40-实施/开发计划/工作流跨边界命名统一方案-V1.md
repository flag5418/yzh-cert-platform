## 一、判定口径（沿用 §16.9，不改）

> 一个键是否受铁律七约束，**看它有没有 DB 列**。

| 情形 | 判定 |
|------|------|
| 有 DB 列 | DB 列名 = C# 属性名 = TS 字段名，**逐字 PascalCase** |
| 无 DB 列（纯信封 / 纯 payload / 纯展示 DTO / 动态字典 / **落库 JSON payload**） | 走**例外清单**（E1–E7），且须在代码注释标注「已登记例外」 |

工作流 `rule_json` / `LayoutJson` **不是实体字段**（各自只是 `cert_validation_rule` 等表的**一个 `text` 列的内容**），已在 **E2** 登记为 camelCase 例外。

**因此本方案不是「消灭违规」，而是「从一个合法例外（E2）迁移到另一套更统一的写法」**——动机是可维护性（删归一化层、消除大小写敏感读），不是合规。这一点必须在拍板前说清：**不做 O2 也是合法的**（守法成本 = 0）。

### 2.3 归类结论

- **必须改**：A（写法统一）+ B（消除大小写敏感读）+ E（删归一化层）+ **C（2026-10-17 裁定：强制 PascalCase）**。
- **不能改**：F（会牵动画布）。
- **不必改**：D（E3）/ 内部灰区（E8）。
- **纯内部常量改名零收益**：不跨端、不落库、不影响可读性 ⇒ ⛔ **不要顺手改**。

## 四、执行顺序与前置依赖（★ 待拍板）

「**呈现层落 DB**」（把 `specialNodes.ts` 的**显示名 / 说明 / 分组**等呈现元数据搬到 DB）与 O2 共享同一批文件（`specialNodes.ts` / `NodePropertyForm.vue`）。

| 视角 | 结论 |
|------|------|
| **先 O2 后呈现层落 DB** | 现在动手 = **存量数据为 0**（最便宜）；但 `specialNodes.ts` 会在两次改造中被**触碰两次**，付两次回归成本 |
| **先呈现层落 DB 后 O2**（上轮建议） | 节点 schema 字段来源收缩（显示名/说明/分组落 DB、且**届时须 PascalCase**）⇒ 要改的键面更小、契约测试更好写；但届时 `rule_json` 可能已有存量 ⇒ 迁移成本上升 |

**★ D1 决议（2026-10-16 用户拍板）：先做 O2（现在）**。理由：`rule_json`/`LayoutJson` 存量**全为 NULL**（唯一「零迁移」窗口），且「呈现层落 DB」在仓库中无任何计划文档（全仓 grep 未命中）⇒ 不应让 O2 被无限期阻塞。代价：`specialNodes.ts` 日后会被「呈现层落 DB」再触碰一次。

> ⚠️ 上轮分析已明确：若不做呈现层落 DB，则 **E8 灰区长期保留**（合法）。二者不互为硬前置，只是「一起做省一次回归」。

## 六、边界契约测试设计（P2）

**问题**：跨语言（TS 写 / C# 读）无法在单个测试里端到端跑。**解法**：两侧各锁一半，用**同一份夹具 JSON**。

| 侧 | 测试 | 断言 |
|----|------|------|
| 前端 | `serializer.test.ts`（新增） | `serialize()` 产出的每个节点/边/`config` 键名 = 期望 PascalCase 白名单 |
| 后端 | `WorkflowConfigContractTests.cs`（新增） | 对**每类节点**喂代表 `rule_json`（PascalCase），**解析 → 执行**，断言关键 `config` 键**非空**（负向：故意写错大小写 → 断言读不到，证明测试不是恒绿） |
| 夹具 | `fixtures/node-<type>.json` | 前端序列化产物 = 后端测试输入，**同一份**（防两侧漂移） |

范式文件：`CertPlatform.Admin.Tests/Workflow/WorkflowConfigParserPortTests.cs`（5 例）+ `specialNodes.test.ts`（负向对照）。
