### 2.2 ★★ 3 个悬空外键 + 1 个孤儿实体（**会阻断"提取"链路**）

**这是本轮顺带发现的真实缺陷**，不是我的推断 —— 实测证据：

```
=== 悬空外键（引用了不存在的表）===
ent_extraction_result        fk_extres_field      → cert_extraction_field   ❌ 表不存在
ent_extraction_result        fk_extres_rule       → cert_extraction_rule    ❌ 表不存在
ent_table_extraction_result  fk_tableext_rule     → cert_extraction_rule    ❌ 表不存在
```

**根因**：这两张配置表**已被改名**，但引用它们的外键**没有跟着改**：

| 旧名（FK 仍指向） | 新名（实际存在） | 证据 |
|---|---|---|
| `cert_extraction_rule` | **`cert_doc_extraction_rule`** | `DocExtractionRule.cs:16` → `[SugarTable("cert_doc_extraction_rule")]`（表存在，注释「文档提取规则主表」） |
| `cert_extraction_field` | **`cert_doc_field_def`** | `DocFieldDef.cs:13` → `[SugarTable("cert_doc_field_def")]`（表存在，注释「文档字段定义表」） |

**同时发现的孤儿实体**：

```
src/certplatform-api/CertPlatform.Shared/Entities/Cert/ExtractionRule.cs:13
  [SugarTable("cert_extraction_rule")]     ← ★ 表不存在，孤儿实体
```

`ExtractionRule.cs` 是改名前的旧实体，**已被 `DocExtractionRule.cs` 取代但没删** → 任何走它的代码都会运行时报「表不存在」。

**影响（★ 在关键路径上）**：

| 影响 | 说明 |
|---|---|
| **INSERT 会失败** | 带悬空 FK 的表，写入时 MySQL 无法校验父表 → `ERROR 1452` / 表级错误 |
| **命中关键路径** | 关键路径是 `登录→工作台→建档→分配标准/阶段→上传→**提取**→NC→报告`；`ent_extraction_result` 正是"提取结果"的落点 |
| **为什么现在没暴露** | 3 张表**全 0 行**，且提取功能尚未实现 → **典型的"等实现时才炸"** |

**修法（3 条 ALTER，约 10 分钟）**：

```sql
-- ============================================================
-- 修复悬空外键：指向改名后的实际表  (2026-09-25)
-- 前置：已备份 ent_extraction_result / ent_table_extraction_result
-- 映射依据：DocExtractionRule.cs → cert_doc_extraction_rule
--           DocFieldDef.cs      → cert_doc_field_def
-- ============================================================
USE `yzh_cert_platform`;

ALTER TABLE `ent_extraction_result`
  DROP FOREIGN KEY `fk_extres_field`,
  DROP FOREIGN KEY `fk_extres_rule`,
  ADD CONSTRAINT `fk_extres_field` FOREIGN KEY (`FieldCode`) REFERENCES `cert_doc_field_def`      (`Code`),
  ADD CONSTRAINT `fk_extres_rule`  FOREIGN KEY (`RuleCode`)  REFERENCES `cert_doc_extraction_rule`(`Code`);

ALTER TABLE `ent_table_extraction_result`
  DROP FOREIGN KEY `fk_tableext_rule`,
  ADD CONSTRAINT `fk_tableext_rule` FOREIGN KEY (`RuleCode`) REFERENCES `cert_doc_extraction_rule`(`Code`);

-- 验证：全库悬空外键应为 0 行
SELECT rc.TABLE_NAME, rc.CONSTRAINT_NAME, rc.REFERENCED_TABLE_NAME
FROM information_schema.REFERENTIAL_CONSTRAINTS rc
LEFT JOIN information_schema.TABLES t
  ON t.TABLE_SCHEMA = rc.CONSTRAINT_SCHEMA AND t.TABLE_NAME = rc.REFERENCED_TABLE_NAME
WHERE rc.CONSTRAINT_SCHEMA = 'yzh_cert_platform' AND t.TABLE_NAME IS NULL;
```

> ⚠️ **映射需你确认**（已列为待确认项 ③）：我按「旧名 → 新名」的字面推断 `cert_extraction_field` → `cert_doc_field_def`。若实际不是这个对应关系，请指出。
> ⚠️ **孤儿实体 `ExtractionRule.cs`**：建议**删除**（表已不存在，且已有 `DocExtractionRule.cs` 取代）。但它属"零引用≠死代码"的判死范畴 → 按三问核查后处置（§4.3 末）。

### 3.1 ★ 完善工作区挂靠机构编码（**已确认 W1**）

**定位**（逐层剥开，第 2 轮已实测）：

```
wzm (Sys_User).OrgCode = 7c3cfbdf…（「管理员」分组）      ← ✅ 正确，不动
  └─ 工作区 66bbf572….OrgCode = 'CB001'                  ← ★★ 断在这里
       语义：所属体系认证机构的 CbCode（AuditorRegisterService.cs:187）
       现状：cert_certification_body 里只有 'cs001' → CB001 是孤儿
```

**根因时间线**：09-23 注册时机构 `CbCode='CB001'` 存在 → 09-24 重建库后机构表被重新 seed，只剩 `906e8b2a…/cs001/测试机构` → `CB001` 成孤儿。工作区节点 `Remark` 自证意图：「所属认证机构：河北雄安尚龙认证有限公司（5833c904…）」。

**修法（W1）**：把机构 `906e8b2a…` 补成正式机构，**`Code` 保持不变**。

> ★ **为什么 `Code` 不能改**：机构关联键有**两条不同的链** —— 工作区用 **`CbCode`**；而 `cert_org_standard` / `cert_org_stage` 用 **`Code`**（实测其 `OrgCode='906e8b2a…'`）。改 `Code` 会打断标准/阶段关联。

```sql

-- 完善专家工作区的挂靠机构编码  (2026-09-25 · 已确认)
-- 前置：已备份 cert_certification_body / sys_organization
-- 原理：工作区 OrgCode = 机构的 CbCode（AuditorRegisterService.cs:187）
--       → 把机构 CbCode 补成工作区已写入的 'CB001'
-- ★ 只改 Name/ShortName/CbCode，【不改 Code】（否则断 cert_org_standard/stage 关联）
-- ============================================================
USE `yzh_cert_platform`;

UPDATE `cert_certification_body`
SET `Name`       = '河北雄安尚龙认证有限公司',
    `ShortName`  = '尚龙认证',
    `CbCode`     = 'CB001',
    `UpdateBy`   = 'manual_fix_20260925',
    `UpdateTime` = NOW()
WHERE `Code` = '906e8b2a962c4062b21144af4cc4abc0';

-- 验证 ①：工作区 → 机构，挂靠链已通
SELECT o.Code AS WsCode, o.OrgName AS WsName, o.OrgCode AS WsOrgCode,
       cb.Code AS CertBodyCode, cb.CbCode, cb.Name AS CertBodyName
FROM `sys_organization` o
LEFT JOIN `cert_certification_body` cb ON cb.CbCode = o.OrgCode AND cb.IsDeleted = 0
WHERE o.Code = '66bbf57219d74e21bf164b7e42380c19';
-- 期望：WsOrgCode='CB001'，CertBodyName='河北雄安尚龙认证有限公司'

UNION ALL
SELECT 'cert_org_stage',          COUNT(*)     FROM `cert_org_stage`    WHERE `OrgCode` = '906e8b2a962c4062b21144af4cc4abc0';
```

### 3.2 ★ 企业节点**就地改造**「企业用户」（修订：改，不删）

**规则**（V4 的"删除 + 新建"作废）：

> 建档时，若当前工作区下存在**名为「企业用户」且尚未绑定企业**的占位节点 → **就地改造它**（不删除、不新建）；否则新建节点。

**"尚未绑定"的判定**：`OrgType = 'Dept' AND OrgName = '企业用户'`
（一旦改造过，`OrgType` 会变成 `Enterprise`，不会被二次命中）

```sql

-- ============================================================
-- ① 查找可复用的占位节点
SELECT `Code` FROM `sys_organization`
WHERE `ParentCode` = '<工作区Code>'
  AND `OrgType` = 'Dept' AND `OrgName` = '企业用户' AND `IsDeleted` = 0
```
