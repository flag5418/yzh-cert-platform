## 一、现实思路

### 1.1 你的文书系统 4 点 vs 现有表（逐点对照，全部实测）

| 你的设想 | 现有支撑（已核实） | 缺口 |
|---|---|---|
| **① 需要编辑的内容** —— 每个文件的「作用 + 填写规则」，规则从 Word/Excel **每一个单元格、或一个区域**定义 | `cert_doc_extraction_rule`（**`Skill`** / **`Prompt`** / `SampleData` / `DocContent`）｜`cert_doc_field_def`（`FieldCode` / `DataType` / `Description` / **`IsManual`** / **`IsAiRecommended`**）｜`cert_doc_table_def` + `cert_doc_table_field_def`（表格 / 列定义） | ⚠️ **规则侧没有「区域坐标」字段**（结果侧 `PositionInfo(json)` 有，规则侧没有）→ 「一个区域」这个粒度**无处安放** |
| **② 固定内容** —— 营业执照 / 生产许可 / 证书；用**名称 + 格式 + 提取内容**相互比对得**可信度** | `cert_standard_directory_file`（`FilePattern` / `FileType` / `IsRequired` / `MaxFileSizeMB`）｜`cert_doc_extraction_rule`.**`DocIsValid`** + **`VerifyMessage`**｜`cert_extraction_result.Confidence` | ⚠️ **「比对规则」没有可执行的载体** —— 现在只能写成 `VerifyMessage` 文本，**机器读不了** |
| **③ 文档自动生成** —— 分步：提取 → 每文档/一组文档对应一个文件夹 → 依次试填得匹配度 → 相近时人工干预 → 出**评估报告 + 人工干预清单** | `cert_extraction_result`.**`VersionNumber`**（试填轮次）+ **`Confidence`**（匹配度）+ **`IsManualEdited`**（人工干预）+ `PositionInfo`（溯源）｜`rpt_report_section_source.SourceType`（多来源） | ⚠️⚠️ **「生成结果表」不存在**（生成的文档存哪）｜⚠️ **「试填作业表」不存在**（谁跑、跑几轮、每个槽位匹配到哪些候选） |
| **④ 预审** —— 企业端/咨询公司做资料预审（逻辑同专家端 NC 检查） | `cert_validation_rule`（`RuleJson` / `LayoutJson` / `SeverityIfViolated` / `NcDescriptionTemplate`）｜`cert_validation_rule_source`（规则 ← 文件来源） | ⚠️ **缺 `JudgeMode`**（判定方式：自动 / 人工 / 半自动）—— 你上轮明确要的「哪些人工、哪些自动」正是缺这个字段 |

**结论：4 点全部成立，且都不需要推翻现有设计。** 要补的是 **4 个载体 + 1 个字段**：

| 序 | 要补 | 服务哪一点 | 什么时候做 |
|---|---|---|---|
| 1 | `cert_validation_rule.JudgeMode` | ④ | 死线后（不挡链路） |
| 2 | 规则侧「区域坐标」字段（`CellRange` / `PositionRule`） | ① | 死线后（第一期按字段级够用） |
| 3 | 「比对规则」可执行载体 | ② | 死线后（第一期靠 `FilePattern` + 名称匹配） |
| 4 | 「试填作业表」 | ③ | **目标 3 开工时** |
| 5 | 「生成结果表」 | ③ | **目标 3 开工时** |

### 1.2 三条不能走偏的认知（复述，防走偏）

1. **目标 1、2 是「判断」（封闭），目标 3 是「生成」（开放）** —— 判断有唯一答案、准确率**可自动统计**、天花板 = 规则完备度；生成**无唯一答案**、准确率**不能自动统计**、天花板 = 素材质量 + 模型能力。⛔ **不能把目标 3 当「第 3 个检查项」做。**
2. **「先天准确性」只适用目标 1、2** —— 目标 3 生成的内容**不在规则里**，规则只能约束「应包含什么」，不能约束「具体怎么写」。
3. **结果可修改 / 导出 / 二次加工（原话「并不是系统控制死的」）** —— 这处设计**绕过了「整合」难题**，是你**能砍掉整合而不损商业价值**的根本原因。

### 1.3 关于「做成桌面端应用」

**方向赞成，但现在不做。**

- **桌面端解决的是**：本地文件夹批量读写 + 大文件不出内网。
- **这三件事里只有目标 3 需要** → 现在做桌面端 = **为 1/3 的功能引入第二套构建 / 发布 / 升级链路**，单人维护成本翻倍。
- **现在怎么做**：Web 上传 + 服务端处理（`yzh-anydoc` / `yzh-libreoffice` 容器**已在跑**格式转换）。
- **★ 关键澄清**：你说的「每一个文档或一组文档，应该对应用户的一个文件夹」——**Web 端也能实现**，不需要桌面端：
  - 让用户**上传一个 zip**，或**多选文件夹**（`<input type="file" webkitdirectory>`）
  - 服务端解压后**按文件夹分组**，每个文件夹 = 一个「文档组」→ 试填的输入单位
  - 这正好对上你「每个文档/一组文档 → 一个文件夹」的语义
- **转桌面端的判据（不到不动）**：① 单企业资料包 > 500MB ② 客户明确要求资料**不出内网** ③ 需要**读本地文件夹自动批量入库**（无人工上传环节）。

## 三、详细计划

### 3.1 企业-阶段关联

**目标**：回答「这个企业现在在哪个认证阶段、覆盖哪些标准」，并成为三个页面左侧树的**唯一数据源**。

#### 3.1.1 表：`cert_enterprise_stage`（新建）

| 列 | 类型 | 说明 |
|---|---|---|
| `Id` | bigint | 主键（**不做业务定位** —— 准则 A） |
| `Code` | varchar(64) | **业务键**（准则 A） |
| `OrgCode` | varchar(64) | 工作区（专家端租户边界） |
| `EnterpriseCode` | varchar(64) | ← `cert_enterprise.Code` |
| `PhaseCode` | varchar(64) | ← `cert_cert_stage.Code`（**认证阶段**，不是审核阶段） |
| `StandardCodes` | json | 覆盖标准，如 `["iso9001-2015","iso14001-2015"]` —— **第一期手工勾选** |
| `StageStatus` | varchar(20) | `preparing` / `auditing` / `completed` / `archived` |
| `StartDate` / `EndDate` | date | 阶段起止 |
| `IsValid` | int | **启禁唯一契约（铁律九，禁 `Enable`）** |
| `Status` / `Sort` / `Remark` / 审计字段 / `IsDeleted` | | 与 `cert_*` 同族一致 |

**★ 为什么 `StandardCodes` 用 JSON 而不是子表**
- 先例：`cert_standard_phase_config.RequiredClauses(json)` / `RequiredFiles(json)`。
- 单人开发第一期，「勾选」即全部语义。
- **代价**：按标准反查企业要 `JSON_CONTAINS`（MySQL 8 支持，但**索引差**）。
- **若后期需要「按标准统计企业数」** → 再拆 `cert_enterprise_stage_standard` 子表。**现在不拆。**（见 §6 确认项 ①）

**★ 为什么不用 `cert_application`**
它是「申请单」，`StandardCode` 是**单值** → **装不下多标准**；且带 `CbCode` / `CertType` / `SubmitTime` 等**机构侧**语义 → **企业端不碰它**（机构端才用）。

**★ 为什么不用 `cert_org_stage`**
那是「**机构** × 阶段」（机构能提供哪些阶段），`StandardCode` 可为 NULL 是**对的**；企业端要的是「**企业** × 阶段 × 标准」，**两者不同层**。

#### 3.1.2 后端

- 位置：`src/certplatform-api/CertPlatform.Auditor/`
- 实体：`Shared/Entities/Cert/EnterpriseStage.cs`（`BaseEntity, ISoftDelete, IIsValid`）
- 控制器：`Controllers/EnterpriseStageController.cs` → **必须继承 `YzhControllerBase<EnterpriseStage>`**（新业务强制，⛔ 不学那 10 个裸 `ControllerBase`）
- 端点全部由基类提供：`GET config`｜`POST filter`｜`POST add`｜`POST update`｜`POST delete`｜`POST toggle-valid`
- **无需覆写 `AddCore`**（单表写入；⚠️ 基类 `AddCore/UpdateCore/DeleteCore` **都不是事务**）
- EntityConfig：`Assets/EntityConfigs/EnterpriseStage.json` —— ⚠️ **文件名必须 = 实体类型名**（陷阱②），且 **`Program.cs` 的 `BusinessEntityConfigPaths` 已含 Auditor**（陷阱⑨）
- ⚠️ `SearchFields[].ControlType` 用 **`input` / `select`**，**不是** `TextBox` / `ComboBox`（陷阱⑭）
- 路由：`/api/Auditor/EnterpriseStage/*`

#### 3.1.3 前端

- 位置：`src/certplatform-web/cert/cert-auditor/src/pages/enterprise-stages/`
- **照抄 `yzh.vue.core/src/pages/system/user/`**（单表 CRUD **唯一模板**，67 行、零手写 CRUD）
- `logic.ts` → `class ... extends SingleTableCore<EnterpriseStage>`（⛔ **不是 `CrudPageLogic<V>`，该类不存在**）
- **若 `SearchFields` > 2 个必须显式传 `:search-max-fields`**（陷阱⑮）

- 菜单：补 `sys_menu` 一行（`Tag='auditor'`）+ `sys_role_api` 授权 `ROLE_AUDIT_CLIENT_ADMIN` → **动菜单后必跑 `sync_menu_urls.sh`**（R12）

#### 3.1.4 工作量

建表 SQL 30min｜实体 20min｜EntityConfig 40min｜控制器 20min｜页 60min｜菜单 + `sys_api` 同步 40min → **约 3.5h**

#### 3.1.5 验收（浏览器实测，照 `yzh-frontend-e2e`）

5. 探针数据**结束即清**（认知③）

### 3.2 企业资料管理

> **三个里最难的，也是关键路径上「上传 → 提取」的落点。**

#### 3.2.1 ★ 核心问题（必须先解决）

现状（已实测）：

- `cert_standard_directory_file` = **要求表**，但塞了 **13 个实例侧列**：`TaskId` / `UploadStatus` / `StoragePath` / `FullPath` / `ConvertedStoragePath` / `ConvertStatus` / `ConvertMessage` / `ConvertDate` / `PreviewPdfPath` / `MarkdownPath` / `MarkdownStatus` / `MarkdownMessage` / `MarkdownDate`
- **一个要求只有 1 行** → **再传一次就把上次覆盖了**
- `cert_upload_task` 只有 `DirectoryCode`，**没有 `EnterpriseCode` / `PhaseCode`**
- 但 `cert_extraction_result` **已经**同时有 `FileCode`（实例）+ `StandardFileCode`（要求）+ `PhaseCode` + `VersionNumber`
  → **设计意图本来就是「要求表 + 实例表」两张表，实例表没建**（实例列被临时塞进要求表）

#### 3.2.2 方案对比

| 方案 | 做法 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **A** 新建 `cert_enterprise_document` | 实例侧独立成表，要求表**保持不动** | 干净；语义清晰；**不动已有页面** | 要改上传落点；要求表 13 个实例列变遗留 | **✅ 推荐** |
| B 拆 `cert_standard_directory_file` → `_requirement` + `_instance` | 彻底拆分 | 最彻底 | **破坏 `business/directory-manager` 页 + `StandardDirectoryService`** → 回归面大 | 不推荐（现在） |
| C 给要求表补 `EnterpriseCode` / `PhaseCode` | 继续混表 | 改动最小 | **混表更严重**：一个要求 N 个企业 = N 行要求，要求被企业数据污染 | ⛔ **不可** |

#### 3.2.3 A 方案表设计：`cert_enterprise_document`（新建）

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(64) | 业务键 |
| `OrgCode` | varchar(64) | 工作区 |
| `EnterpriseCode` | varchar(64) | ← `cert_enterprise.Code` |
| `EnterpriseStageCode` | varchar(64) | ← `cert_enterprise_stage.Code`（**归属到「企业-阶段」**） |
| `PhaseCode` | varchar(64) | 冗余，便于查询 |
| `StandardFileCode` | varchar(150) | ← `cert_standard_directory_file.Code`（**要求槽位**；NULL = 未匹配 / 多余文件） |
| `FileName` / `FileType` / `FileSize` | | 文件元信息 |
| `StoragePath` / `FullPath` | | MinIO 路径 |
| `SourceType` | varchar(20) | `upload`（用户上传）/ `generated`（**目标 3 生成**）/ `fixed`（固定内容：营业执照等） |
| `DocStatus` | varchar(20) | `pending`（未匹配）/ `matched`（已匹配槽位）/ `unmatched`（多余）/ `verified`（已核验）/ `rejected`（**不合格，待替换**） |
| `MatchConfidence` | decimal(3,2) | 与槽位的**匹配度**（目标 3 试填用） |
| `MatchCandidates` | json | 试填时匹配到的**候选槽位**（相近时人工决策的依据） |
| `Version` | int | **替换即 +1**（你第 3 轮明确要的「资料不符合要求可重新替换」） |
| `IsCurrent` | tinyint(1) | 只有 1 行为 `1`（**历史版本留档不删**） |
| `ReplaceReason` | varchar(500) | 替换原因（人工填 / 预审不合格原因） |
| `ConvertStatus` / `ConvertMessage` / `ConvertDate` | | 格式转换（沿用现有语义） |
| `PreviewPdfPath` / `MarkdownPath` / `MarkdownStatus` / `MarkdownDate` | | 转换产物 |
| `ExtractStatus` | varchar(20) | 提取状态 |
| `IsValid` / `IsDeleted` / 审计字段 | | 同族 |

**★ 为什么用 `IsCurrent` 而不是物理覆盖**
报告有**法律效力** + 目标 3 要出「评估报告 + 人工干预清单」→ **必须能回答「当时用的是哪一版」**。这正是 `cert_extraction_result.VersionNumber` 存在的意义。

#### 3.2.4 上传与匹配流程（7 步）

1. 用户选「企业 + 阶段」→ 左侧树定位
2. 系统按 `cert_enterprise_stage.StandardCodes` 展开**要求清单**：
   - 对每个标准取 `cert_standard_directory_config`（`StandardCode` + `PhaseCode`）→ `_folder` → `_file`
   - **合并并集**，**排重判据 = 文档类型**（**不是**文件名、**不是**路径）
   - 每条标注**来源标准**（`["iso9001-2015","iso14001-2015"]`）
   - ★ 这一步就是多标准的「**一行、多列标注**」—— **不是删重复项**
3. 用户上传（**支持 zip / 多选文件夹 `webkitdirectory`** → 服务端按文件夹分组，见 §1.3）
4. 服务端按 **文件名 + 格式 + 提取内容** 匹配槽位 → 写 `cert_enterprise_document`：
   - 匹配上 → `DocStatus='matched'`，填 `StandardFileCode`
   - 匹配不上 → `DocStatus='unmatched'` → **进「人工干预清单」**
   - 匹配度相近（多候选）→ 填 `MatchCandidates` → **进「人工干预清单」**
5. **缺失槽位** = 要求有、但无任何实例匹配 → **「缺失文档清单」**
6. **预审**：跑 `cert_validation_rule`（`PreCheckRequired` / `ComplianceRequired`）→ 不合格的置 `DocStatus='rejected'` + `ReplaceReason`
7. 用户替换 → 新 `Version`，旧版 `IsCurrent=0`

#### 3.2.5 ★ 三个输出清单（你第 7 轮明确要的）

| # | 清单 | 内容 |
|---|---|---|
| ① | **缺失文档清单** | 要求 vs 实例**差集**（按标准分别列出） |
| ② | **人工干预清单** | `unmatched` + 匹配度相近 + `rejected` 三类合并 |
| ③ | **评估报告** | 齐套率 / 匹配率 / 不合格数 / 待人工数（**每项带 AI 置信度**，人工补充点单独标注） |

#### 3.2.6 前端

- 位置：`src/certplatform-web/cert/cert-auditor/src/pages/enterprise-documents/`
- 左侧树 = 企业 → 阶段（`cert_enterprise_stage`）｜右侧 = 资料列表（`YzhTable` + 上传工具栏）
- ★ **左树右表照抄 `foundation/iso-standard/` 的 `logic.ts` 的 `dataLoader` 骨架** —— ⛔ **`index.vue` 不要抄**（样板页自己手写了 11 个 CRUD handler，**是坏榜样**）

#### 3.2.7 工作量
