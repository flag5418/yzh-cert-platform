# 43 · 来源链执行器设计（待审批）· V1

## 〇、一句话结论

> **设计不是「缺失」，而是「三份互相冲突」。**
>
> 我把全仓翻了一遍：来源链的**契约形状**有 **3 份写法**，**互相不兼容**，而且**实现侧全部停在最老的那一份**。
> ⇒ **执行器的第一件事不是写代码，是裁定形状**（本文 §二）。
>
> 裁定之后，执行器本身**很小**（约 400 行 + 30 条单测），因为它只做四件事：
> **读 `SourceSpec` → 逐条调 Skill → 按 `combine` 组合 → 交 `FillSession`**。
> 真正的工作量在**兼容层**与**校验**上。

## 一、先纠一个前提：不是「缺失」，是「三份冲突」

### 1.1 三份设计的对照（全部有出处，逐字）

| # | 出处 | `sources[]` 的形状 | 谁消费 | 状态 |
|---|---|---|---|---|
| **① 老形状（枚举 `kind`）** | `22` 号 §三 | `{ "kind": "global", "ref": "ENT_NAME", "onMissing": "next" }` | `22` 号 §十三.5 的 `IValueResolver`（**⛔ 该接口全仓不存在**） | 🟡 **实现侧全用这个** |

## 二、★ 裁定建议 **D-S1**：采用「SkillCode 引用 + 参数字典」

### 2.1 新契约（正例，可直接录入）

```jsonc
{
  "combine": "firstHit",          // firstHit | concat | template
  "separator": "、",              // 仅 concat 用；缺省 "、"
  "expr": "{{1}}（{{2}}）",       // 仅 template 用；占位符语法见 §五
  "sources": [                    // ★ 有序 = 回退优先级
    { "skill": "src_global_param", "params": { "param_code": "ENT_NAME" },                    "onMissing": "next" },
    { "skill": "src_ai_field",     "params": { "instruction": "企业全称，须与营业执照一致" },  "onMissing": "next" },
    { "skill": "src_manual",       "params": { "hint": "请填写企业名称" },                    "onMissing": "todo" }
  ]
}
```

**字段说明**：

| 字段 | 必填 | 说明 |
|---|---|---|
| `combine` | ✅ | `firstHit`（默认）/ `concat` / `template` |
| `separator` | 仅 `concat` | 缺省 `、` |
| `expr` | 仅 `template` | 小模板；**`combine='template'` 且 `expr` 空 ⇒ 校验红牌 `E4`**（`42` 号 §5 缺陷 ②） |
| `sources[].skill` | ✅ | **`wf_skill.SkillCode`**（如 `src_ai_field`）<br>⚠️ ⛔ **不是 `wf_skill.Code`** —— 那一列是**行业务码**（如 `SK_SRC_AI_FIELD`），实测 18 行里**两列值全部不同**（见 §附 ③） |
| `sources[].params` | — | **该 Skill 的业务入参字典**，键名 = `[SkillParam]` 参数名（**由反射驱动，⛔ 前端不硬编码**） |
| `sources[].onMissing` | — | `next`（默认）/ `todo` / `block` / `empty` |

> ### ⚠️★ 命名陷阱：`wf_skill.Code` ≠ `wf_skill.SkillCode`（**实测，⛔ 别猜**）
>
> | 列 | 实测值（`src_ai_field` 那行） | 语义 |
> |---|---|---|
> | `wf_skill.Code` | `SK_SRC_AI_FIELD` | **行业务码**（`SK_*` 前缀，供 `Sys_DictionaryList` / 日志 / 关联用） |
> | `wf_skill.SkillCode` | **`src_ai_field`** | ★ **真正的技能编码** —— `SourceSpecEntry.skill` 要的就是它 |
> | `wf_skill.CategoryCode` | `doc_src_scalar` | 类别（`doc_src_scalar` / `doc_src_table` / `doc_fill`） |
> | `wf_skill.SideEffect` | `0` | 0 = 内容类（产值，⛔ 不碰文件）；1 = 操作类（装配，由编排器统一落盘） |
> | `wf_skill_reflection.SkillCode` | `src_ai_field` | 与 `wf_skill.SkillCode` 同值 ⇒ **JOIN 键** |
>
> **⇒ 症状（若不注意）**：`WHERE s.Code LIKE 'src_%'` ⇒ **返回 0 行、不报错**，
> 然后执行器报「找不到 Skill `src_ai_field`」——**指错方向**，让人去查注册 SQL 而不是查列名。
> 这是本项目 `REFERENCE.md §二十` 反复总结的**静默失败**类（同类第 N 次）。
>
> **⇒ 连带影响**：§2.4 ① 里前端「从后端拉 Skill 列表」也必须**取 `SkillCode`**，
> 且**过滤 `CategoryCode IN ('doc_src_scalar','doc_src_table')`**（⛔ 不能把 `fill_cell` 列进「数据来源」下拉）。

### 2.2 ★ 兼容层（老形状 → 新形状的映射，**必须实现**）

**为什么必须有**：库里 3 行老数据 + `sourceSpec.ts` 存量代码 ⇒ 不做兼容层 = **页面配的东西立刻失效**（静默）。

**`kind` → `skill` 映射表**（照抄 `38` 号 §5.2 + `39` 号 §2.2 的收敛结论）：

| 旧 `kind` | 新 `skill` | `ref` → `params` 的换算 |
|---|---|---|
| `global` | `src_global_param` | `{ param_code: ref }` |
| `profile` | **`src_ai_field`** | `{ instruction: ref ?? field }` ⚠️ `38` 号原写 `src_from_profile`，`39` 号 §2.2 已收敛到 `src_ai_field` |
| `self` | **`src_global_param`** | `{ param_code: ref }`（`39` 号 §2.2：同表不同参数） |
| `sibling` | **`src_global_param`** | 同上 |
| `ai` | **按 `AnchorType` 分派**（见下） | — |
| `manual` | `src_manual` | `{ hint: ref }` |
| `compute` | ⛔ **一期不做**（`Q-24`） | 命中 ⇒ **`Fail("compute 来源一期未实现")`**（⛔ 不静默跳过） |
| `dict` / `src_dict_pick` | ⛔ **二期**（`src_dict` 未实现） | 同上 |

**`kind='ai'` 的分派规则（★ 这是 `kind` 枚举表达不了的部分，也是升级的根本理由）**：

| `cert_doc_template_anchor.AnchorType` | 分派到 | 自动注入的 `params` |
|---|---|---|
| `table` | `src_ai_table` | `{ table_tag: AnchorRef 去前缀, columns_json: 锚点表 ColumnsJson }` |
| `block`（= `{{ai:xxx}}`） | **`src_ai_field`**（默认） | `{ instruction: 见 §4.3 第 ③ 步 }` |
| `scalar` / `domain` | `src_ai_field` | 同上 |

> ⚠️ **`src_semantic` 不在自动分派里**：它需要 `source_text`（**模板里的标准原文**），
> 而 `ref` 表达不了「去哪取原文」。⇒ **只在 `SourceSpec` 里显式写 `"skill": "src_semantic"` 时才用**（**D-S2**）。

### 2.3 为什么必须升级到 `skill`（3 条理由，第 1 条是决定性的）

| # | 理由 | 证据 |
|---|---|---|
| **①** | **`kind` 枚举表达不了已上线的 3 个 AI Skill** | `ai` 一个枚举值要覆盖 `src_semantic` / `src_ai_field` / `src_ai_table` 三个语义完全不同的 Skill（一个改写原文、一个从文档找值、一个出表格）⇒ 只能靠「猜 `AnchorType` + 猜有没有原文」，**猜错就是静默填错** |
| **②** | **前端参数表单会退化成硬编码** | `38` 号 §5.3 要的是「**参数 UI 由反射驱动**」：读 `SkillExecutor.Analyze` 的 `InputPorts` 自动生成表单。若参数名写死在前端（`ref` / `field` / `minConfidence` 三个固定槽），**新来源上线就要改前端** |
| **③** | **`kind` 的语义边界已经烂了** | 实测 `SOURCES_KINDS` 里 `implemented` 标记 **`ai: false` 已经过时**（3 个 AI Skill 已上线）；`compute: true` 但**后端无任何 `compute` 实现**。⇒ 枚举本身就是一处「文档说 A、实现是 B」 |

### 2.4 连带影响（4 处，**升级不是改一个文件**）

| # | 文件 | 改动 |
|---|---|---|
| ① | `cert-admin/.../doc-fill-rule/components/sourceSpec.ts` | `SourceSpecEntry` 改 `{ skill, params, onMissing }`；`SOURCE_KINDS` 改为**从后端 `wf_skill` 拉**（按 `CategoryCode` 过滤 `doc_src_*`）；`implemented` 由 `wf_skill_reflection.Status` 决定 |
| ② | 库里 3 行老数据 | **不迁移**（兼容层兜住）。⚠️ 若用户要求「库要干净」，再写一次性迁移脚本（`kind` 列保留只读，照 `38` 号 §5.2） |
| ③ | 校验端点 `DocTemplateAnchorController.Validate` | 加 **E4 红牌**（`template` + `expr` 空）+ **E5 红牌**（`skill` 不在 `wf_skill` 里 / `Status≠active`）+ **E6 黄牌**（`concat` 来源 < 2） |
| ④ | 页面侧边栏「来源链」编辑器 | 每条来源从「选 `kind` 下拉」改为「选 Skill 下拉 + 反射生成的参数表单」 |

## 三、★★ 边界：后台配「规则」，企业由「任务」注入

> **用户 2026-10-04 逐字裁定**：
> 「这里只是规则，没办法确定是哪个企业，哪个企业是我们在**专家端，选择企业的阶段的原始资料进行任务**才能搞定的，
>  所以，我们**后台设置的是规则，而不是具体哪个企业**」

### 3.1 两层职责（实测对齐）

| 层 | 载体 | 作用域字段 | 有企业吗 |
|---|---|---|---|
| **后台 = 规则** | `cert_doc_template_anchor`（`SourceSpec`/`ValueType`/`Required`）+ `cert_doc_fill_prompt` + `cert_doc_template` | 只有 `StandardCode` / 阶段码 / 文档类型 | ⛔ **没有 `EnterpriseCode`** |
| **专家端 = 任务** | `cert_expert_task`（+ `_task_standard` / `_queue` / `_queue_item`） | **`OrgCode` + `EnterpriseCode` + `StageCode` + `StandardCodes[]` + `TaskType`** | ✅ **有** |

实测 `cert_expert_task` 现有 2 行（都是 `NC_CHECK`，企业 `42833c3d…`，阶段 `29c1bcc3…`）。

### 3.2 对执行器的 4 条硬约束

| # | 约束 | 违反后果 |
|---|---|---|
| **①** | **`SourceSpec` 里 ⛔ 不得出现 `EnterpriseCode` / 具体文件 Code** | 规则绑死企业 ⇒ 换企业就要重配 |
| **②** | 执行器的**入参里必须有 `EnterpriseCode` / `StageCode` / `StandardCode`**，且**由调用方（任务）给**，⛔ 不从 `SourceSpec` 读 | 同上 |
| **③** | `enterprise_docs`（AI 来源的输入）**必须由外部注入**，执行器 ⛔ 不自己查企业文档 | 执行器会变成「既编排又取数」的巨型类 |
| **④** | 执行器**不认识 `cert_expert_task`**（不 JOIN、不读表） | 编排器 ↔ 任务系统耦合，单测要建全套任务数据 |

> **⇒ 执行器是「纯部件」**：输入 = `(锚点行集合, 作用域, enterprise_docs, session)`，输出 = `(值字典, 待办, 轨迹)`。
> **它不读 DB、不调 HTTP、不碰文件** ⇒ 可以完全用假数据单测（本文 §七 的验收标准）。

### 3.3 ⚠️ 顺带发现：`ItemType` 需要新增

`ExpertTaskConst.ItemType` 现只有 **`NcCheck`** / **`ReportSection`** ⇒ 文档填写要进任务队列，
**需要新增一个 `ItemType`**（如 `DocFill`）。**本轮不实现**，登记为 **D-S4**。

## 四、执行器设计

### 4.1 位置与命名

| 项 | 值 | 理由 |
|---|---|---|
| **类名** | `SourceChainExecutor` | ⛔ 不叫 `IValueResolver`（`22` 号 §十三.5 的名字，已被推翻）；⛔ 不叫 `DocumentFillOrchestrator`（那是**整条链**，执行器只是它的第 ④ 步） |
| **位置** | `CertPlatform.Admin/Services/Workflow/Skills/Fill/Chain/SourceChainExecutor.cs` | 与它要调的 Skill 同根；`Admin` 才有 `SkillExecutor` |
| **配套** | `.../Chain/SourceSpecParser.cs`（解析 + 兼容层）、`.../Chain/SourceCombine.cs`（组合算法） | 三个文件各管一件事，**均可独立单测** |

### 4.2 接口（照抄可编译）

```csharp
namespace CertPlatform.Admin.Services.Workflow.Skills.Fill.Chain
{
    /// <summary>
    /// 来源链执行器 —— 读 <c>cert_doc_template_anchor.SourceSpec</c>，逐条调 Skill，按 <c>combine</c> 组合。
    ///
    /// <para><b>★ 它是纯部件</b>：不读 DB（锚点行由调用方给）、不调 HTTP、不碰文件。
    /// 唯一的外部依赖是 <see cref="SkillExecutor"/>（执行 Skill 本身）。</para>
    ///
    /// <para><b>★ 边界（用户 2026-10-04 裁定）</b>：本类只认「规则」，⛔ 不认识企业与任务；
    /// <c>EnterpriseCode</c> / <c>StageCode</c> / <c>StandardCode</c> / <c>EnterpriseDocs</c>
    /// 全部由 <see cref="SourceChainContext"/> 从外部注入。</para>
    /// </summary>
    public sealed class SourceChainExecutor
    {
        public SourceChainExecutor(SkillExecutor executor);

        /// <summary>执行一个锚点的来源链。</summary>
        public Task<ChainOutcome> ExecuteAsync(
            SourceChainContext ctx, DocTemplateAnchor anchor, CancellationToken ct = default);

        /// <summary>批量执行（一个模板的全部锚点）。★ 与单锚点走同一条代码路径。</summary>
        public Task<ChainBatchOutcome> ExecuteAllAsync(
            SourceChainContext ctx, IReadOnlyList<DocTemplateAnchor> anchors, CancellationToken ct = default);
    }

    /// <summary>执行上下文 —— ★ 作用域由调用方注入，⛔ 不从 SourceSpec 读</summary>
    public sealed class SourceChainContext
    {
        /// <summary>★ 运行期作用域（来自 cert_expert_task；后台试跑时可留空）</summary>
        public string? OrgCode { get; set; }
        public string? EnterpriseCode { get; set; }
        public string? StageCode { get; set; }
        public string? StandardCode { get; set; }

        /// <summary>★ AI 来源的文档输入（由 IEnterpriseDocRetriever 产出；空 ⇒ AI 来源跳过并记 pending）</summary>
        public string? EnterpriseDocs { get; set; }

        /// <summary>企业档案快照（src_global_param 的 auto/both 自动带出用）</summary>
        public SharedFill.EnterpriseInfo? Enterprise { get; set; }

        /// <summary>提示词编码（透传给 AI Skill；空 ⇒ 用内置默认模板）</summary>
        public string? PromptCode { get; set; }

        /// <summary>★ 填充会话（放真对象实例 ⇒ SkillExecutor.ConvertValue 原样透传）</summary>
        public FillSession? Session { get; set; }
    }

    /// <summary>单锚点执行结果</summary>
    public sealed class ChainOutcome
    {
        public string AnchorCode { get; set; } = string.Empty;

        /// <summary>取到的值（null = 未取到）</summary>
        public FillValue? Value { get; set; }

        /// <summary>表格锚点的值（与 Value 互斥）</summary>
        public TablePayload? Table { get; set; }

        /// <summary>★ 命中的来源 Skill 编码（审计 + FillValue.Source 用）</summary>
        public string? HitSkill { get; set; }

        /// <summary>尝试过的来源（顺序 + 每条的结果）—— 写入 cert_doc_fill_log.SkillTrace</summary>
        public List<ChainAttempt> Attempts { get; set; } = new();

        /// <summary>待办（onMissing=todo 或 src_manual 命中时产出）</summary>
        public FillTodo? Todo { get; set; }

        /// <summary>是否被阻断（onMissing=block）</summary>
        public bool Blocked { get; set; }

        /// <summary>阻断/失败原因（人话）</summary>
        public string? Error { get; set; }
    }

    /// <summary>一次来源尝试的记录</summary>
    public sealed class ChainAttempt
    {
        public int Index { get; set; }
        public string Skill { get; set; } = string.Empty;
        /// <summary>hit | miss | error | skipped | blocked</summary>
        public string Result { get; set; } = string.Empty;
        /// <summary>人话原因（miss/error 时给）</summary>
        public string? Message { get; set; }
    }
}
```

### 4.3 ★ 单锚点算法（7 步，顺序不可颠倒）

```text
① 解析 SourceSpec（SourceSpecParser.Parse）
   ├ 空 / 解析失败 ⇒ 返回 ChainOutcome{ Error="未配置取值来源" }，⛔ 不抛异常
   └ 老形状 ⇒ 兼容层换算成 (skill, params)（§2.2）

② 预检（★ 全部在调 LLM 之前，避免白烧 token）
   ├ combine='template' 且 expr 空 ⇒ Error（= 校验 E4 的运行期兜底）
   ├ combine='concat' 且 sources.Count < 2 ⇒ 降级为 firstHit 并记 Attempts（= 黄牌 E6）
   └ sources 为空 ⇒ Error="未配置取值来源"

③ 组装每条来源的 params（★ 三层合并，后者覆盖前者）
   ├ 层 1 通用：anchor_code = 锚点键；value_kind = anchor.ValueType；number_format = anchor.NumberFormat
   ├ 层 2 锚点表注入（★ 用户不用在 params 里重复写）：
   │     table 锚点 ⇒ table_tag = AnchorRef 去 "table:" 前缀；columns_json = anchor.ColumnsJson
   │     instruction 缺 ⇒ 回落 anchor.Remark（⚠️ 二期改为「从模板上下文提取」，见 D-S3）
   └ 层 3 SourceSpecEntry.params（人工显式写的，优先级最高）
   ⛔ 任何一条来源都不得覆盖 anchor_code（否则值会被写到别的锚点上）

④ ★ 逐条尝试（顺序 = 回退优先级）
   for (i, src) in sources:
     ├ 前置跳过（★ 不调 Skill，直接记 skipped）
     │    src.skill 需要 enterprise_docs 但 ctx.EnterpriseDocs 为空 ⇒ skipped("无企业文档输入")
     │    src.skill 需要 enterprise_code 但 ctx.EnterpriseCode 为空 ⇒ skipped("无企业作用域")
     ├ 解析 ClassPath：wf_skill s JOIN wf_skill_reflection r ON r.SkillCode = s.SkillCode
     │    ★ 判据 = s.SkillCode = src.skill（⚠️ 两侧都是 SkillCode 列，⛔ 不是 wf_skill.Code）
     │    ★ 由 CertSkillRegistry 缓存（⛔ 不每次查库）；Status≠'active' ⇒ 记 error
     ├ 调 SkillExecutor.ExecuteAsync(classPath, methodName, new SkillContext{ Inputs = params })
     ├ ★ 判据是 Outputs["success"]（⛔ SkillResult.Success 恒 true，不是判据）
     ├ 命中判据（★ 按 Skill 类别区分，见 4.4）
     │    hit=true 且 Outputs["value"] is FillValue  ⇒ 命中（标量）
     │    hit=true 且 Outputs["table"] is TablePayload ⇒ 命中（表格）
     │    hit=false（src_manual）⇒ **未命中**，但记 Todo
     ├ 命中 ⇒ 跳出循环（firstHit / concat 例外，见 4.4）
     └ 未命中 ⇒ 按 src.onMissing 处理（4.5）

⑤ 组合（SourceCombine，见 4.4）

⑥ 类型与格式收口
   ├ 标量：FillValueFactory.FromRaw(anchorCode, raw, anchor.ValueType, anchor.NumberFormat)
   │    ⚠️ 若 Skill 已返回 FillValue 实例 ⇒ 透传（FromRaw 内部已处理）
   │    ★ 返回 null ⇒ Error（⛔ 不静默降级成文本）
   └ 表格：列一律用**输入的** columns_json，⛔ 不用 AI 返回里的列（39 号 §8.3）

⑦ 落会话（★ 认领归 fill_cell，见 4.6）
   └ 只回填 FillValue.Source = $"来源链 · {HitSkill}"（人话 + 编码），⛔ 不写 session.Request.Values
```

### 4.4 ★ `combine` 三种算法（含边界）

| `combine` | 算法 | 边界与陷阱 |
|---|---|---|
| **`firstHit`** | 按顺序取**第一个命中**，取到即停 | ⚠️ **`src_manual` 恒 `hit=false`** ⇒ 必须继续往下找（`39` 号 §5.3：若改成 `true`，链会在人工待办处提前终止，**报告里看不出异常**）。⇒ **`manual` 应放链尾**（校验加黄牌提示） |
| **`concat`** | **所有**来源都尝试，把命中的值用 `separator` 拼起来 | ⚠️ 来源 < 2 时**没有拼接语义** ⇒ 降级 `firstHit` + 记 Attempts。⚠️ 命中的值为空串算**未命中**（⛔ 不产生「、」连缀） |
| **`template`** | 所有来源都尝试，把命中的值填进 `expr` 的占位符 | ⚠️ `expr` 空 ⇒ Error（E4）。占位符语法见 §五。⚠️ 未命中的占位符 ⇒ **保留占位符原文 + 记 pending**（⛔ 不静默变空串 —— 否则「模板套用」失效看不出来） |

**表格锚点的组合**：`combine` 对表格锚点**无意义**（表格只有一个来源）⇒ 校验加黄牌，执行期按 `firstHit` 处理。

### 4.5 `onMissing` 语义表（4 值，与 `sourceSpec.ts` / `22` 号 §八 一致）

| 值 | 行为 | 落到哪 |
|---|---|---|
| `next`（默认） | 跳过本来源，继续下一条 | `Attempts` |
| `todo` | **记待办，继续填其他锚点** | `FillSession.Todos` → `OfficeFillReport.Pendings` |
| `block` | **直接报错，整份文档不生成** | `ChainOutcome.Blocked = true` ⇒ 编排器中止该文件 |
| `empty` | 留空，**不告警** | 什么都不做 |

> ⚠️ **`block` 是唯一会「中断整份文档」的值** ⇒ 校验应把 `block` 标为**高风险**（页面提示「该锚点取不到值时，整份文档不会生成」）。
> ⚠️ **全部来源落空且无 `todo`** ⇒ 按 `anchor.Required` 决定：`Required=1` ⇒ 记 pending（**必须展示**，`39` 号 §14 不变量 3）；`Required=0` ⇒ 留空。

### 4.6 与 `FillSession` 的协同（★ 认领归谁 —— 这是最容易做错的一处）

**现状（实测）**：`FillCellSkill` 里做认领：

```csharp
if (!session.TryClaim(kv.Key, SkillCode, out var conflict))   // SkillCode = "fill_cell"
    return Task.FromResult(SkillResult.Fail($"锚点 {kv.Key} 已被「{conflict}」赋值（⛔ 不覆盖…）"));
```

⇒ **`AnchorOwners` 里记的是 `fill_cell`，不是产出值的来源 Skill** ⇒ `FillSession` 注释里写的
「用途二：审计（这一格的值是谁写的）」**实际拿不到**。

**本设计的选择**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A** | 执行器先 `TryClaim(anchorCode, hitSkill)`，`fill_cell` 放宽为「owner 已是来源 Skill ⇒ 允许」 | 审计真实，但要改 `fill_cell`（已实现、已测） |
| **B ✅（建议）** | **执行器 ⛔ 不认领**；`fill_cell` 保持现状；**审计走 `FillValue.Source` + `cert_doc_fill_value.SourceSkill`（`41-01` 的账本表）** | **零改动**；审计粒度更细（逐锚点一行，含置信度） |

⇒ **本设计取 B**。执行器只负责把 `HitSkill` 写进 `FillValue.Source`，并在 `ChainOutcome.Attempts` 里留全量轨迹。

### 4.7 错误语义（⛔ 不静默降级 —— 这是本项目的头号缺陷类型）

| 场景 | 行为 | ⛔ 绝不这样做 |
|---|---|---|
| `SourceSpec` 空 / 解析失败 | `Error="未配置取值来源"` | 静默当 `firstHit` 空链 |
| `skill` 不在 `wf_skill` / `Status≠active` | `Attempts` 记 `error`，按 `onMissing` 走 | 静默跳过（用户配了个不存在的 Skill，页面必须能查出来） |
| Skill 抛异常 | 捕获 ⇒ `Attempts` 记 `error` + 原因 | 让异常冒泡（一份文档坏掉不该中断整批） |
| 值类型不符（`ValueType=number` 但值是 `ABC`） | `Error`（`FillValueFactory.FromRaw` 返 null） | 降级成文本 ⇒ Excel 数字变文本 |
| `compute` / `src_dict` 来源 | `Error="一期未实现"` | 静默返回空（= `42` 号 §5 缺陷 ②③ 同类） |
| `enterprise_docs` 为空但来源是 AI | `skipped("无企业文档输入")` + 按 `onMissing` 走 | 拿空文档去调 LLM（**白烧 token 且返回空**） |
| 表格 `columns_json` 解析不出列 | `Error` | 让 AI 自己定列 ⇒ **整列数据静默消失**（`39` 号 §8.3） |

## 五、★★ **D15** 裁定：`template` 的占位符语法

**问题**（`42` 号 §5 缺陷 ③）：`22` 号 §三 的例子写 `{{Name}}（{{CreditCode}}）`，
但来源的 `ref` 是 `ENT_NAME` / `company_name` —— **既不是下标也不是 ref**，运行期**无法解析**。

**三个选项**：

| 选项 | 写法 | 优点 | 缺点 |
|---|---|---|---|
| **A** | `{{1}}` / `{{2}}`（**按来源下标**） | 来源增删不影响模板；实现 5 行 | 可读性差（看不出第 1 个是什么） |
| **B** | `{{ref}}` / `{{skill:param}}`（按 ref） | 可读 | `ref` **不唯一**（同一 Skill 可能被引用两次；`src_ai_field` 的 `ref` 可能是 `instruction`）⇒ **歧义** |
| **C** | 两者都收（先试下标，再试 ref） | 兼容 | **两套口径**（本项目反复出现的缺陷类型） |

**★ 建议：A**（`{{1}}` 按来源下标），理由：
1. **`ref` 不唯一**（`src_ai_field` 无 `ref`，靠 `instruction`）⇒ B 会歧义；
2. **来源增删不影响模板**（把 `{{1}}` 换成 `{{ref}}` 后，删掉第 1 个来源会让模板静默失效）；
3. **校验可以做**：`expr` 里的 `{{n}}` 若 `n > sources.Count` ⇒ **红牌**（页面直接看得见）。

⇒ 落地：`expr` 的占位符 = **`{{1}}` ~ `{{N}}`**；`{{0}}` / 越界 / 非法占位符 ⇒ 保留原文 + 记 pending。
