# 企业资料规范化 — 标准文档契约模型

> **版本**：V1 | **日期**：2026-09-27 | **状态**：草案（P6 固定文档清单待拍板）

## 1. 契约在架构中的位置

```text
                    问题侧（本册）                        答案侧
  ┌──────────────────────────────────────┐   ┌─────────────────────────────┐
  │ cert_standard_doc_contract           │   │ cert_ent_doc_profile* 画像   │
  │   要素1 名称（镜像 DocName）           │   │   DocPurpose / 字段 / 表格    │
  │   要素2 作用（DocPurpose）            │◄──┤   （企业文档实际有什么）        │
  │   要素3 单元格（复用 cert_doc_field_def）│   └─────────────────────────────┘
  │   要素4 表格（复用 cert_doc_table_def） │   ← 匹配引擎（04 分册）做两侧比对
  │   要素5 提示词（Match/Synthesis/提取）  │
  └──────────────┬───────────────────────┘
                 │ RuleCode / CellPrompt / TablePrompt
                 ▼
  ┌──────────────────────────────────────┐
  │ cert_extraction_result 定向提取结果    │  ← 要素3/4/5b 在此被消费（填充）
  └──────────────────────────────────────┘
```

- **契约只描述标准文档**，不描述企业文档；企业侧的一切在画像（06 分册）。
- **一文件一契约**：`uk_standard_file_code`，契约不独立创建，必须挂在 `cert_standard_directory_file` 上。
- 契约的 `ConfigCode/StandardCode/StageCode/DocName` 全部是**冗余镜像**（从宿主同步），用于匹配阶段免 JOIN 过滤与排序；**权威永远在宿主表**。

## 2. 五要素逐项建模

| # | 要素 | 载体 | 归属 | 读取方 | 写入方 |
|---|------|------|------|--------|--------|
| 1 | 文档名称 | `DocName`（镜像）；权威 = 宿主 `FileName` + `FilePattern` | 契约表 | 召回 R1（文件名路）、精排 prompt | 宿主变更时同步 |
| 2 | 文档作用 | `DocPurpose`（text） | 契约表 | 画像参照、精排 prompt、语义召回 R4 | **人工编写**（可 AI 辅助生成初稿） |
| 3 | 单元格定义 | `cert_doc_field_def`：`FieldName/FieldCode/DataType/Description` + **新增 `CellPrompt`** | 既有子表（按 `RuleCode` 挂） | 精排（字段命中比对）、定向提取、人工填写指引 | 规则设计器 + 契约页扩展 |
| 4 | 表格定义 | `cert_doc_table_def`：`TableName/TableCode/Description` + **新增 `TablePrompt`** + 子表列 | 既有子表 | 精排（表头比对）、定向提取 | 同上 |
| 5 | AI 提示词 | 三层拆分（见下） | 契约表 + 规则表 | 各层独立 | 人工/AI 辅助 |

### 2.1 要素 2：`DocPurpose` 写什么（给编写者的规范）

三段式，缺一不可：

```text
① 这是什么文档：ISO9001 质量管理体系的质量手册，覆盖体系范围、职责、过程相互作用。
② 审核关注点：版本/编制审批齐全、与实际一致、引用标准现行有效。
③ 数据来源口径：由质量部编制、管理者代表批准；通常 1 年内改版一次。
```

- `①` 供**精排 LLM** 判断语义吻合；`②` 供人工理解「为什么 AI 会关注这些字段」；`③` 供**画像链**参照（企业文档画像的 `DocPurpose` 用同样口径写，两侧可直接比对）。
- 长度建议 100–400 字；空值时精排降级为纯字段匹配（04 分册 §5.2 会标 `[缺X维]` 并强制人工）。

### 2.2 要素 5：提示词三层拆分

| 层 | 字段 | 消费场景 | 时机 | 可空策略 |
|----|------|----------|------|----------|
| 5a 匹配 | `MatchPrompt` | S3 精排判断「企业文档 vs 本文档」 | 一次性（每对候选） | 空 → 用全局默认模板 |
| 5b 填充 | `SynthesisPrompt` | 不可直接结构化的**段落类**字段如何组织撰写 | 裁决后定向提取 | 空 → 段落字段跳过，只填结构化字段 |
| 5c 提取 | `DocExtractionRule.Prompt`（**已有**） | 从 Markdown 中抽取字段/表格 | 定向提取 | 空 → 规则页生成（已有能力） |

**为什么不合并**：三者输入不同（5a 输入=两侧摘要；5b 输入=Markdown+字段定义；5c 输入=Markdown+规则），合并会导致提示词互相污染、无法独立调优。`08-技能与提示词设计-V1.md` 给出各层模板。

### 2.3 单元格/表格提示词（要素 3/4 的新增列）

```sql
-- 02 分册 §6，随契约页实施
ALTER TABLE `cert_doc_field_def` ADD COLUMN `CellPrompt` text ... AFTER `Description`;
ALTER TABLE `cert_doc_table_def` ADD COLUMN `TablePrompt` text ... AFTER `Description`;
```

- `CellPrompt` 写**取值口径**：单位、枚举、取数位置（表头/落款/页眉）、示例（`合格 ✗ / 符合 ✓`）。
- `TablePrompt` 写**表结构规则**：表头别名（「修订记录=改版履历」）、合并单元格处理、必填列、空行丢弃。
- 必须与定义**同表同行**（02 §6 已述理由：跨表 JOIN 破坏 `BuildAnalysisPromptAsync` 结构）。

## 3. 固定 vs 可编辑分类体系

| `DocCategory` | 判据 | 匹配策略 | 填充策略 | 典型 |
|---------------|------|----------|----------|------|
| `fixed` | **国家/机构规定格式**，字段位置固定、通常为扫描件 | S1 指纹主导（04 §2），`Confidence=0.45×RuleStrength+…` | OCR 后按固定字段位提取，或人工录入 | 营业执照、许可证、资质证书 |
| `editable` | **企业自编文档**，格式自由、内容结构多样 | S2+S3 召回精排主导（语义+字段+表格） | 结构化字段直填 + 段落走 `SynthesisPrompt` | 质量手册、程序文件、作业指导书、记录表单 |
| `hybrid` | 主体固定但有自由段（如带封面的证书扫描+自填页） | 指纹定「是不是这类」，精排定「是哪一份/够不够格」 | 两法并用 | 体系认证证书、含自填内容的备案表 |

**判定规则**：
- 首批分类**由人工在契约页圈定**（P6 清单），系统不自动判定；
- `DocCategory=fixed` 必须配 `FingerprintJson`（校验：保存时缺指纹 → 警告但不拦截）；
- `DocCategory` 直接决定 04 分册 §5.2 用哪套加权公式，**不得留空**（默认 `editable`）。

`DocRole`（与 `DocCategory` 正交）：

| 值 | 含义 | 对匹配的影响 |
|----|------|--------------|
| `required` | 该阶段必需 | 召回为空 → 生成「缺失必需项」告警（04 §3.2 R5） |
| `optional` | 建议提供 | 无候选不告警 |
| `reference` | 参考资料 | 只入候选池，不进必需项校验 |
| `attachment` | 附属材料 | 随主文档，不独立匹配 |

> `DocRole` 与宿主 `IsRequired` 的关系：宿主 `IsRequired` 是**目录级**必需标记（上传预检用），契约 `DocRole` 是**匹配级**角色（细分 optional/reference/attachment）。初始值从宿主 `IsRequired` 同步（`IsRequired=1 → required`，否则 `optional`）。

## 4. 与既有表的关系与同步规则

| 关系 | 键 | 方向 | 规则 |
|------|----|------|------|
| 契约 ↔ 标准文件 | `StandardFileCode` → `cert_standard_directory_file.Code` | 宿主**主**、契约**从** | 一文件一契约；宿主删除 → 契约软删（`IsDeleted`） |
| 契约 ↔ 目录配置/标准/阶段 | 冗余 `ConfigCode/StandardCode/StageCode` | 单向同步 | 宿主或 `cert_iso_standard` 变更时**批量刷新**（见 §4.1） |
| 契约 ↔ 提取规则 | `RuleCode` → `cert_doc_extraction_rule.Code` | 弱关联 | **可空**：无规则 = 该标准文档还没有字段/表格定义（要素 3/4 未配置）；有规则 = `GetByCode` 读出 `DocFieldDef/DocTableDef` 消费 |
| 契约 ↔ 标准文件（反向） | 宿主 `ContractCode`（02 §4.1 新增） | 冗余直查 | 契约创建/删除时回写，供标准目录页免 JOIN 显示契约状态 |
| 要素 3/4 ↔ 提取规则 | `DocFieldDef.RuleCode` | 规则侧 | 与既有完全一致，不改 |

### 4.1 同步时机（谁改谁刷）

| 变更事件 | 刷什么 | 实现点 |
|----------|--------|--------|
| 标准文件改名 `FileName` | 契约 `DocName` | 契约页保存前读宿主；或 `StandardDirectoryService` 更新钩子 |
| 目录配置/标准/阶段迁移 | 冗余三列 | 契约维护页「一键刷新」按钮（低频，不做强一致） |
| 契约 `Status→active` | 宿主 `ContractCode` | 契约保存事务内回写 |
| 提取规则删除 | 契约 `RuleCode` 置 NULL + 提示要素 3/4 失效 | 规则删除钩子 |

> **不做跨表触发器**：全项目无 DB 触发器惯例，一致性由服务层保存路径保证（与 `FullPath/StoragePath` 分离的判重逻辑同思路）。

## 5. 契约生命周期与状态机

```text
  ┌────────┐  保存(要素2+分类就绪)  ┌────────┐  人工发布    ┌────────┐
  │ draft  │ ───────────────────► │ review │ ──────────► │ active │
  │  草稿  │ ◄─────────────────── │ 待发布 │ ◄────────── │  生效  │
  └────────┘      退回编辑         └────────┘   停用/撤回   └────────┘
       │                                  ▲                  │
       │ 从规则批量种子（自动生成）          │                  │ 宿主归档/标准换版
       ▼                                  │                  ▼
  （自动生成的契约带 Remark='seed'，        │              ┌──────────┐
    必须人工补 DocPurpose 才能到 review）    └──────────────│ archived │
                                                          │  归档    │
                                                          └──────────┘
```

| 状态 | 能做什么 | 匹配引擎行为 |
|------|----------|--------------|
| `draft` | 编辑全部要素 | **不参与**匹配（不被召回） |
| `review` | 编辑 + 预览指纹/提示词 | 不参与匹配 |
| `active` | 正常使用 | 参与召回与精排，可产候选 |
| `archived` | 只读 | 已产生的候选保留，不再新增召回 |

- **`active` 前置校验**（保存时自动跑，不通过给警告清单）：① `DocPurpose` 非空 ② `fixed` 必须有 `FingerprintJson` ③ `RuleCode` 有值时 `CellPrompt` 覆盖率 ≥ 50%（要素 3 提示词过半字段已填）。
- 无强制拦截的项只出黄牌警告——契约页首期以可用性优先，严格度随使用迭代。

## 6. 种子生成与维护

### 6.1 从既有提取规则批量生成（`02` §8.1 脚本 4）

```text
输入：所有 cert_doc_extraction_rule（按 StandardFileCode 分组）
输出：cert_standard_doc_contract 初值

映射：
  StandardFileCode  = 规则.StandardFileCode（无此值的规则 → 跳过并出清单）
  RuleCode          = 规则.Code
  DocName           = 宿主.FileName
  ConfigCode/StandardCode/StageCode/DocRole = 从宿主/IsRequired 派生
  DocCategory       = 'editable'（默认；固定文档由人工在清单上改，见 P6）
  DocPurpose        = NULL  ← 必须人工补（种子无法编造业务语义）
  Status            = 'draft'，Remark = 'seed:{日期}'
  FingerprintJson   = NULL（仅 fixed 类人工配置）
```

- **种子只建骨架，不编造语义**：`DocPurpose/MatchPrompt/FingerprintJson` 一律空，靠人工补——AI 生成的"作用说明"若与实际不符会污染精排，宁缺毋滥。
- 种子脚本**幂等**：`INSERT ... SELECT ... WHERE NOT EXISTS (同 StandardFileCode)`。

### 6.2 无规则的标准文件

标准目录里 `ExtractionEnabled=1` 但无提取规则的文件 → 仍建契约（骨架），`RuleCode=NULL`，契约页显示「要素 3/4 未配置」并给两个出口：① 跳转规则设计器新建规则 ② 先只做要素 1/2/5a（纯语义匹配，不给字段分）。

### 6.3 日常维护

| 场景 | 操作 |
|------|------|
| 新标准上线 | 目录配置发布 → 跑种子脚本 → 人工补 DocPurpose → active |
| 标准换版 | 新版标准建新配置 → 新契约；旧契约 `archived`，候选保留（`MatchState` 不回退） |
| 召回总漏 | 先看 `Keywords`（人工维护，04 R3 路），再看 `DocPurpose` 是否写了同义表达 |
| 指纹误判 | 调 `FingerprintJson.minScore` 或删 `fileNames` 词条，勿改阈值全局值 |

## 7. 固定文档清单（P6）

**用户圈定前的建议首批**（默认 `DocCategory=fixed`，各配指纹规则）：

| 文档 | 关键指纹字段 | 备注 |
|------|--------------|------|
| 营业执照 | 统一社会信用代码（`91[0-9A-Z]{16}`）、法定代表人、经营范围 | 正本/副本/电子版同规则 |
| 生产/经营许可证 | 许可编号、有效期、发证机关 | 按行业可能多份 |
| 资质证书 | 证书编号、资质等级、有效期 | |
| 法人/负责人身份证明 | 姓名、身份证号 | 注意脱敏 |
| 体系认证证书（已获证） | 证书编号、认证机构、有效期 | 与本平台认证结果区分 |

清单产出后写入 10 分册验收范围；**每份指纹规则由管理员在契约页维护，代码不硬编码规则**（04 §2.5）。

## 8. 使用规范与禁止事项

| ✅ 必须 | ⛔ 禁止 |
|---------|---------|
| 契约一律经宿主文件创建（一文件一契约） | 独立建契约、契约脱离 `StandardFileCode` 存活 |
| 定位/更新用 `StandardFileCode`（业务键） | 用 `Id` 定位契约（准则 A） |
| 冗余列变更走 §4.1 同步点 | 手工 UPDATE 冗余列 |
| `CellPrompt/TablePrompt` 与定义同表维护 | 把提示词拼进契约 `Remark`/`Keywords` |
| 阈值优先读契约级，空则全局 `cert_sys_config` | 每个文档写死阈值进代码 |
| `DocCategory` 决定匹配公式分支 | 匹配代码里对固定文档写死 if-else 清单 |

**与既有铁律的交汇**：契约表已满足 `IsValid`（禁 `Enable`）、`utf8mb4_general_ci` 显式、`Code` 为业务键、PascalCase 三处一致——02 分册 §8.2 验证 SQL 覆盖，实施后必跑。
