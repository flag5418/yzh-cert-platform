## 一、问题陈述

### 1.1 用户提问

1. 固定文档缺一个关键属性：**是否依赖企业文档**（该文档必须存在，且自动属于企业标准文档，不需要企业单独提供）。
2. 「文档角色」的 4 个选项（必须提供 / 可选提供 / 参考资料 / 附件）在**企业资料规范化**里到底起什么作用。

### 1.2 实测结论：关于「文档必要性 / 依赖性」的 4 个字段，全部死或半死

| # | 字段                            | 位置                             | 运行期消费                   | 判定  |
| - | ----------------------------- | ------------------------------ | ----------------------- | --- |
| 1 | `IsRequired`（bool，默认 `true`）  | `cert_standard_directory_file` | **零消费**                 | 死字段 |
| 2 | `DocRole`（4 值）                | `cert_standard_doc_contract`   | 仅被拼进「生成提示词」文本           | 半死  |
| 3 | `FixedDocSubtype`（2 值）        | `cert_standard_doc_contract`   | **零消费**                 | 死字段 |
| 4 | `Replaceable`（bool，默认 `true`） | `cert_standard_directory_file` | 仅被编排器**读**，无写入入口 ⇒ 恒为默认 | 半死  |

实测方法（可复算）：

```bash
# ① DocRole 在真实规范化链路（Auditor）零引用 —— 应返回 No files found
grep -rn "DocRole" src/certplatform-api/CertPlatform.Auditor/

# ② Replaceable 全项目仅 2 处引用（实体定义 + 编排器读取），无写入点
grep -rn "Replaceable" --include=*.cs --include=*.ts --include=*.vue src/

# ③ IsRequired 在 Shared + Auditor 仅 1 处（实体定义），无消费
grep -rn "IsRequired" src/certplatform-api/CertPlatform.Shared/Entities/Dir/
```

### 1.3 危害（为什么必须处理）

**这是典型的「写了没人看」类缺陷**：配置界面一切正常、不报错、不抛异常，只是**运行结果与配置无关**。具体表现为：

- 用户把一份固定文档配成「标准自带」，运行期照旧走「文件匹配」分支去找企业文件 ⇒ 找不到 ⇒ 判 `unmatched`，用户不知道是自己配错了还是企业没交。
- 用户把一份文档配成「参考资料」，运行期毫无区别 —— 它照样计入完成度、照样报缺口。
- 编排器读的是 `file.Replaceable`，页面上写的是 `contract.FixedDocSubtype` —— **两列永不同步**，第三对分叉列。

## 二、概念澄清（「设计混乱」的根因）

### 2.1 ★ `DocCategory` **不是**分组标签 —— 二者是同一次分析的三套正交产出

上传企业资料后跑的那次语义分析（`doc_group` + `doc_content` 两跳），一次吐出**三套互相正交**的东西：

| 概念           | 列                              | 取值                              | 答什么问题            |
| ------------ | ------------------------------ | ------------------------------- | ---------------- |
| **文档分类**     | `DocCategory`                  | `fixed` / `editable` / `hybrid` | 这份文档**要不要被重新编写** |
| **分组标签**     | `TagsJson`                     | 受控字典 `cert_tag_dict.TagCode`    | 属于哪个**业务类别**     |
| **作用 / 信息项** | `DocPurpose` / `InfoItemsJson` | 文本 / JSON                       | 干什么用、包含什么        |

> ⛔ 三者**不是一回事**，只是同一次分析同时产出。把它们混为一谈是本轮混乱的主要来源。  
> `EnterpriseDocProfile.DocCategory` 的实体注释已明确写着：「画像结论，与标签/受控字典是**三套正交概念**」。

### 2.2 `DocCategory` 出现在**三张表**

| # | 位置                                         | 角色      | 谁是权威                                        |
| - | ------------------------------------------ | ------- | ------------------------------------------- |
| 1 | `cert_standard_directory_file.DocCategory` | 标准侧     | ★ **权威列** —— 编排器分流读它                        |
| 2 | `cert_standard_doc_contract.DocCategory`   | 标准侧     | 镜像 —— `Save` 时同批写两处（**同步代码已存在且正确**）         |
| 3 | `cert_enterprise_doc_profile.DocCategory`  | **企业侧** | AI 对「企业上传的那份资料」的分类结论 —— **另一个维度**，⛔ 不要与前两个混 |

### 2.3 `FixedDocSubtype` 存的是什么

固定文档的「**内容从哪来**」：`standard_provided`（标准自带，不向企业索取）/ `enterprise_provided`（企业提供，要匹配依据）。**仅当 `DocCategory=fixed` 时有意义**。目前零消费。

## 三、定稿语义模型

### 3.1 两个**互相独立**的维度（用户 2026-10-16 确认 2×2 成立）

|           | 依赖企业文档     | 不依赖企业文档                      |
| --------- | ---------- | ---------------------------- |
| **必要文档**  | 企业必须交（最常见） | ★ **标准自带，但必须存在**（导航页 / 固定描述） |
| **非必要文档** | 企业可以交，不交也行 | 基本无意义                        |

★ 用户描述的那一格 = **必要 + 不依赖企业文档**：该文档必须存在、自动属于企业标准文档体系，但不需要企业单独提供。

### 3.2 用户裁决记录（2026-10-16）

| # | 裁决                                                                                               |
| - | ------------------------------------------------------------------------------------------------ |
| 1 | 「是否依赖企业文档」**=** 「是否可替换」，同一件事。业务依据：标准文档里有些是**导航页 / 固定描述**，不需要企业提供。                                |
| 2 | 「文档角色」改为「**文档约束**」，只留 2 值：**必要文档 / 非必要文档**。补充语义：非必要文档若程序生成不出来，**可以忽略**。                          |
| 3 | 作用域纠正：只有**后台自动规范化真跑起来**才能算，且只算「**哪些文档生成了、哪些未生成**」⇒ 粒度 = **文档级**、性质 = **事后统计**（⛔ 不是事前约束、⛔ 不是锚点级）。 |
| 4 | 不依赖企业文档的槽位：**不出现**在「企业提供清单」中，由后台**根据规则自动生成并存入数据库**。                                              |
| 5 | 文档级统计：**沿用之前的设计**（= `64` 号 §3.3 已定稿的六项口径，见 §6.3）。                                                |

### 4.2 保留（目录表两列）

| 列                                          | 承载概念         | UI 措辞    | 取值                              |
| ------------------------------------------ | ------------ | -------- | ------------------------------- |
| `cert_standard_directory_file.IsRequired`  | **文档约束**     | 文档约束     | `true` = 必要文档 / `false` = 非必要文档 |
| `cert_standard_directory_file.Replaceable` | **是否依赖企业文档** | 是否依赖企业文档 | `true` = 依赖 / `false` = 不依赖     |

**★ 两列都只在标准行上配置**（判据：`EnterpriseCode` 为空 ⇒ 标准行；归属模型 V2）。

### 4.3 命名裁定

**建议不改列名，只改注释 + UI 措辞**。理由：

1. `IsRequired` 与「必要 / 非必要」**逐字一致**，无需改。
2. `Replaceable` 与「是否依赖企业文档」是**同一件事的两种表述**（不依赖企业文档 ⇒ 不能被企业文件替代），语义等价，⛔ 不是错误命名。
3. 改名需要 DDL 迁移 + 实体 + 编排器 + 全部 SQL 脚本同步，收益低而风险实在。

⇒ 处置：**保留列名**，在实体注释里显式写明「业务口径 = 是否依赖企业文档，⛔ 不要按『文件可替换』理解」。

> ⚠️ **待裁决项 ①**：若用户坚持列名与业务口径逐字一致，则 `Replaceable` → `DependsOnEnterprise`（只有 2 处引用，成本可控）。

### 4.4 ★ 重要修正：`Replaceable` 的适用范围

实体注释现写「**仅 `DocCategory='fixed'` 时有意义**」—— **这条要改**。

用户场景中的「导航页 / 固定描述」在 `DocCategory` 上很可能是 `editable`（有模板、要走填充链），但**内容不依赖企业资料**。

⇒ 新口径：**「是否依赖企业文档」适用于全部文档**，与 `DocCategory` 正交。

## 六、运行期消费点清单

### 6.1 编排器四路分流（`DocumentFillOrchestrator.FillOneAsync`）

现状（`DocumentFillOrchestrator.cs:154`）只按 `DocCategory` 二分。**改为按两个维度四分**：

| 是否依赖企业文档 | DocCategory | 路径                | 现状                                              |
| -------- | ----------- | ----------------- | ----------------------------------------------- |
| 依赖       | `fixed`     | ② 文件匹配（读画像匹配结论）   | ✅ 已实现                                           |
| 依赖       | `editable`  | 七步填充链（取企业资料）      | ✅ 已实现                                           |
| **不依赖**  | `fixed`     | ① 快归档（标准原件归档）     | ⚠️ **空壳**（`RunFixedArchiveAsync` 是「如实记录版」，不搬文件） |
| **不依赖**  | `editable`  | 七步填充链，**但不读企业资料** | ❌ **未实现**                                       |

### 6.2 「不依赖企业文档」⇒ 自动生成并入库（用户裁决 4）

**语义**：该文档不出现在「企业需提供清单」中，由后台按规则自动生成、存入数据库。

**落地口径**：

- **`fixed` + 不依赖**：沿用路径①，补全归档搬运 —— 把标准目录行上的原件（`stdFile.StoragePath`）按企业标准资料结构复制到企业区，并建企业实例行（`InstanceState='archived'`）。
  - ⚠️ 若该槽位**无实体文件**（纯导航页），则只建实例行、不搬文件，状态记 `archived`。
- **`editable` + 不依赖**：走七步填充链，但**画像输入置空**，取值来源只允许 `src_semantic`（AI 语义改写标准原文 —— 该 Skill 已存在，见 `phase14_doc_fill_ai_skills.sql`：`'按企业实际情况改写标准原文（不依赖企业文档）。'`）/ `global` / `manual`。
  - ⛔ 校验：该文档的锚点若配了「企业资料」类来源 ⇒ 配置期给**警告**（不阻断），运行期该锚点记待办。

**「忽略」的落地**（用户裁决 2）：

- 编排器遇到 **非必要文档**（`IsRequired=false`）生成失败 ⇒ 状态记 `skipped_optional`，⛔ **不判失败、不进失败统计**。
- 与既有的 `skipped_locked` / `skipped_no_template` 并列（同一模式）。

### 6.3 文档级统计（用户裁决 5 —— 沿用 `64` 号 §3.3）

**沿用现有六项口径，不新建表、不新建统计实体**：

| 指标    | 口径（`64` §3.3 原文）                 | 本轮变化         |
| ----- | -------------------------------- | ------------ |
| 已就位   | 锁定 + 完成度 100% 的文档数               | —            |
| 部分完成  | `0 < 完成度 < 1` 的文档数（副标题：共缺 N 个锚点） | —            |
| 未生成   | `完成度 = 0`（副标题：需先执行规范化）           | ★ **拆两档**，见下 |
| 待人工匹配 | `MatchState='ambiguous'` 的固定文档数  | —            |
| 低可信文档 | 存在 `Confidence < 70%` 锚点的文档数     | —            |
| 已锁定   | `IsLocked = 1`（不参与重新生成）          | —            |

**★ 本轮唯一变化 ——「未生成」按文档约束拆两档**：

| 档           | 判据                           | 呈现              |
| ----------- | ---------------------------- | --------------- |
| **未生成（必要）** | 完成度 = 0 **且** `IsRequired=1` | 计入**缺口**，红色，需处理 |
| 未生成（非必要）    | 完成度 = 0 **且** `IsRequired=0` | 灰色淡化，**不计缺口**   |

**统计落点**：直接查企业实例行（`cert_standard_directory_file`，按 `EnterpriseCode` 非空过滤）× 标准行（`IsRequired` / `Replaceable`），⛔ 不新增统计表。

**分母口径**：范围 = 该企业 × 该标准/阶段下 **`cert_doc_template` 已发布** 的文档（= 规范化范围，`60` §六之补三）。

## 七、迁移脚本

### 7.1 ★ 必须先跑：`FixedDocSubtype` → `Replaceable` 值迁移

页面上的「是否可替换」此前**确实可写**（`Save` 端点已接），故契约表**可能有真实数据**，迁移前先核对：

```sql
-- ① 核对：有多少契约配过 FixedDocSubtype（非默认值）
SELECT c.FixedDocSubtype, COUNT(*) AS Cnt
FROM cert_standard_doc_contract c
WHERE c.IsDeleted = 0
GROUP BY c.FixedDocSubtype;
```

```sql
-- ② 迁移（幂等）：只更新【标准行】（EnterpriseCode 为空），企业实例行不覆盖
UPDATE cert_standard_directory_file f
JOIN cert_standard_doc_contract c ON c.StandardFileCode = f.Code AND c.IsDeleted = 0
SET f.Replaceable = (c.FixedDocSubtype = 'enterprise_provided')
WHERE f.EnterpriseCode = ''
  AND f.IsDeleted = 0
  AND c.FixedDocSubtype IN ('standard_provided', 'enterprise_provided');
```

> ⚠️ **幂等性**：脚本可重复执行；已迁移行再跑一次结果不变（按值重算，非增量）。
