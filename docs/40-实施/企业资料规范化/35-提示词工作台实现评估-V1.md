### 1.1 评分

## 第 3 章 P1 · `suggestedPolicy` 语义冲突（🔴 上生产链前必修）

### 3.1 冲突事实

**同一个枚举值 `skip`，设计与实现指的是两件完全不同的事。**

| | `skip` 的含义 | 判定依据 | 后果 |
|---|---|---|---|
| **设计文档**<br>33 号 §0.9 / §五 / 26 号 补6 | **`DocCategory = fixed`**（营业执照、生产许可等固定文档）→ **「匹配即终点」短路** | 类型分流 + 全局参数已覆盖 | **不跑 `doc_content`** + **不进 ⑧定向提取 / ⑨契约填充** |
| **当前实现**<br>`doc_group` 种子提示词 §五 | **「编号前缀+标题已能定标签，不必再读全文」** → 省一次 LLM 调用 | 标签 confidence ≥ 0.9 | 只是"不再读全文精判" |

实测输出直接命中了这个分歧：

```
XASL-QR-014-年度内审计划.docx
  → suggestedPolicy = skip
  → policyReason    = 编号前缀与标题双重确定，符合 L0 规则
```

**而"年度内审计划"按 05 号 §3 是典型的 `editable` 文档，必须走 ⑧→⑨。**

### 3.2 为什么这是"重犯"，不是"新问题"

33 号 §0.9 有一处明确的自我警告（原文）：

> ⚠️ **`AnalyzePolicy=skip` 的正确语义（V1.2 更正）**：它是 **`fixed`/`editable` 类型分流 + 全局参数已覆盖** 的直接体现（26 号 补 6 原文），**成本节省是副产品**。V1.1 曾把它描述成"成本优化"，是理解偏差。

**设计文档 V1.2 已经把这个坑填了，但种子提示词（V1.3/D.2-3 重写时）又按 V1.1 的口径写了回去。** 这是典型的"文档已勘误、代码未同步"——也再次印证 V2 优化计划第 3 章的判断：**本项目最大的成本不是缺能力，是文档与实现不同步。**

### 3.3 危害（当前被"生产链未接入"掩盖）

已实测确认：`grep -rn "SuggestedPolicy|AnalyzePolicy"` 在 `PromptWorkbenchService` 之外**零命中** ⇒ 企业侧生产链（26 号 §3.5 ④）尚未消费该字段。

所以现在**不会出事**。但一旦 P1 期接入企业侧分析入队（33 号 §九 P1-③「F4 企业侧分析入队 + `AnalyzePolicy` 联动」），后果是：

```
一份 editable 的《年度内审计划》
  → 提示词判 skip（因为有编号前缀）
  → 生产链按"fixed 短路"处理
  → 不跑作用提示词、不进契约填充
  → ★ 这份资料永远不会出现在标准文档的候选清单里
  → 且没有任何报错（因为"逻辑正常执行"）
```

**静默丢失业务数据，且 669 份标准文档全部 `DocCategory=editable` 的情况下会系统性发生。**

### 3.4 建议方案（二选一，倾向 A）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | **拆成两个字段**：`tagConfidence` 已在 `tags[].confidence` 里有了；把"要不要读全文"从 `suggestedPolicy` 里拿出来，独立成 `needFullRead: bool`（或直接复用现有 `confidence`）。`suggestedPolicy` **只保留设计语义**：`skip`（=fixed，指纹接管）/ `analyze` / `ignore` | 两种语义彻底解耦；提示词不再需要"猜"该给哪个 | 需改种子提示词 §五 + `OutputSchemaJson` + `SemanticResult.vue` 渲染 + 契约表列 |
| B | 保留单字段，但**改种子提示词的定义**：`skip` 只在"该文档命中固定文档指纹清单"时给；编号前缀只能影响 `confidence` 与 `reason` | 改动面小（只改提示词 + 一处说明） | "指纹接管"依赖 34 号 **N4（P6 固定文档清单）尚未裁决**（33 号 §十 明确标注 🔴 未裁决）⇒ 现在改会引入对未决清单的依赖 |

> **建议 A + 先按 B 止血**：短期（B 的口径）改种子提示词，避免误导；P1 期接入生产链时（A）再彻底拆开。理由：`N4` 未裁决前，`skip` 的设计语义缺少可判定的具体条件，B 方案无法真正执行。

## 第 4 章 P2 · 功能缺口（标准侧闭环未合拢）

### 4.1 缺口 1：F3 标准侧批量分析 + 人工干预 —— 完全未实现

| 项 | 实测 |
|---|---|
| `DocSemanticController` | **0 个文件**（设计 §八规划 3 端点） |
| `cert_standard_doc_contract` | **0 行**（表已建、45 列齐、实体已建） |
| 页面入口 | 无。设计 §7.2 的 **Tab2「标准文档语义」**（167 行表格 + 右侧抽屉改标签/作用四段/infoItems）不存在 |
| 生产链 | 无（26 号 §3.5 ④ 未接） |

**后果**：工作台能"调提示词"，但**调出来的结果无处可去**。设计 P0 的交付定义是"**F1/F2/F5/F6 + 2 张表，标准侧闭环**"——实际达成的只有 F1/F2/F5，闭环的最后一跳（结果落 `cert_standard_doc_contract`）缺失。

**这是本模块当前最大的功能缺口**，且它是 P1 期（企业侧自动分析）的**前置**：没有标准侧契约，就没有"标准文档需要什么"，企业侧画像算不出覆盖度。

### 4.2 缺口 2：F6 标签清单维护 —— 无任何 UI 入口

| 项 | 实测 |
|---|---|
| `TagDictController` | **0 个文件**（设计 §八规划 7 端点） |
| 页面入口 | 无。设计 §7.2 **Tab3「标签清单」**（增删改/排序/启停/导入文件夹树/按标准重新生成/新词待审核）不存在 |
| 现状 | 27 个标签只能改 SQL |

**为什么这个缺口比看起来严重**：`{{tag_list}}` 是整个模块的**核心约束**——§3.3 后端校验第 ① 条（`tagCode` 必须 ∈ `cert_tag_dict`，越界强制回退 `OTHER`）完全依赖它。而 §3.1 明确：

> 「**约束 LLM 只能从字典选**，允许**建议新词 → 进待审核，不直接入库**。」

**"新词进待审核"这条链路完全没有载体**：LLM 判为 `OTHER` 后，`policyReason` 里会写"需全文确认"，但没有任何机制把"这个反复 OTHER 的模式"反哺成新标签。实测中 `陪审人员.docx` 正是这种情况——它被判 `analyze`（正确），但"无编号前缀的审核类文档"这个模式**没有地方沉淀成新标签**。

**这是 33 号 §10 引用 14 号 D14 的核心机制，目前只实现了"约束"，没实现"反馈"。**

### 4.3 缺口 3：F4 企业侧自动分析 —— 属 P1 期，**不算缺口**

33 号 §九已把 F4 排在 P1。但需注意：F4 依赖 §3.1 的 P6 固定文档清单（34 号 **N4，🔴 仍未裁决**）。**N4 不裁决，F4 的 `skip` 分支无法实现正确语义**——这与第 3 章的结论互相印证。

### 4.4 缺口 4：设计 §7.2 的 4 Tab 结构未采用

设计 §7.2 规划的是「左树 + 右 4 Tab（提示词 / 标准文档语义 / 标签清单 / 测试记录）」，实现是「**左树 + 中编辑 + 右测试**」三栏（V1.5 界面去教学化的产物）。

**这个改动本身是对的**（三栏更适合"边写边试"，且符合 E1「本页用户 = 系统维护人员」）。但副作用是：**F3 与 F6 原本要落的两个 Tab 没有位置了**，且决策时没有同步记录"那这两个功能放哪"。

> 建议：不要恢复 Tab。**把 F3/F6 作为独立的页面入口**（如 `基础资料` 或 `规则定义` 下各一个菜单），理由是它们的用户与工作流和"调提示词"不同——F3 是"批量跑 167 份 + 人工校对"（批量任务型），F6 是"维护字典"（表单型）。挤进三栏工作台会破坏 V1.5 刚定下的界面定性。
