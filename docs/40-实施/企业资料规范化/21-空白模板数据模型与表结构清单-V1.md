## 一、格式统一：能力已存在，零成本

### 1.1 实测发现

| 项 | 实测 |
|----|------|
| 标准文档老格式占比 | `.doc` 143 + `.xls` 11 = **154 / 168 = 91.7%** |
| `ConvertStatus` | **168/168 = `completed`** |
| `ConvertedStoragePath` | **168/168 全为空** ⚠️ |
| `MarkdownPath` + `PreviewPdfPath` | 167/168 有值 |

**为什么 `completed` 但中间产物为空**：默认的 `ConvertAutoAsync` **只做 PDF + Markdown 两条链**，不做中间格式（`OfficeConvertService.cs:116-119`）。

### 1.2 但能力确实存在 ✅

| 能力 | 位置 |
|------|------|
| `.doc`→`.docx` / `.xls`→`.xlsx` 转换 | `DocumentConvertClient.ConvertToFormatAsync()`（`:64`）——「中间产物链：doc→docx / xls→xlsx」 |
| 队列分支 | `OfficeConvertService.ConvertAsync()` 的 `"doc2docx" or "xls2xlsx"` 分支（`:104-105`） |
| 产物落点 | `ConvertToOfficeIntermediateAsync()` → 回写 `ConvertedStoragePath`（`:151`） |

**所以你的第 2 条是「把已有能力接上」，不是「新建能力」。**

### 1.3 落地方式（建议）

| 方式 | 做法 | 评价 |
|------|------|------|
| **A. 批量预转换（推荐）** | 一次性把 168 个标准文档入队 `doc2docx`/`xls2xlsx`，产物落 `ConvertedStoragePath` | 模板制作是**集中进行**的，一次转完最省事 |
| B. 按需转换 | 点「下载标准文档」时，若 `ConvertedStoragePath` 为空 → 入队 + 提示「转换中，请稍候刷新」 | 省一次批量，但用户体验断点 |

### 1.4 ⚠️ 必须提示用户：转换有损

`.doc` → `.docx` 由 LibreOffice 转换，**排版可能与原件有差异**（分页、字体替换、表格边框）。

**下载时 UI 必须提示**：
> 「该文件由 `.doc` 自动转换而来，排版可能与原件有差异，**请核对后再作为模板底稿**。」

### 1.5 ⛔ 上传侧**不要**自动转换

上传模板时校验扩展名，非 `docx`/`xlsx` → **拒绝**，并提示「请用下载的 `.docx` 底稿制作」。

**理由**：模板的格式是**精确的**（锚点位置、样式名都依赖它）。自动转换会破坏锚点 → 扫描器报一堆假红牌。**下载侧统一是「给你一个能编辑的底稿」，上传侧统一是「拒绝不统一的输入」** —— 方向相反，不能混。

## 二、不引入版本号：可以，但覆盖规则要写死

### 2.1 判定

✅ **成立**。单人开发 + 模板数量可控，先不做版本历史是对的（`16` 册那套 `TemplateVersion` + `IsLatest` + `uk_file_version` 可以整体删掉）。

### 2.2 但「覆盖」必须明确三条规则

| 规则 | 内容 | 理由 |
|------|------|------|
| **① 覆盖什么** | `StoragePath` / `FileName` / `FileKind` / `SourceSha256` / 全部扫描结果列 | 文件换了，这些必须跟着换 |
| **② 保留什么** | `TagsJson` / `DocCategory` / `DocPurpose` / `FillPrompt` **及其 `*Source` 标记** | **这正是你第 3/4/5 条要的「自动带出」** |
| **③ 锚点怎么处理** | 重扫后与旧锚点 **diff**：<br>· 新增锚点 → 插入（无值，待处理）<br>· 消失锚点 → `IsOrphan=1`，**⛔ 不删** | 消失的锚点可能**已有填过的值**，直接删就丢了 |

**⚠️ 补一条捷径**：上传时若 `SourceSha256` 与库里**相同** → **整个重扫跳过**，直接返回「文件未变化」。省一次扫描，也避免无意义地把人工确认的锚点重置。

### 2.3 建议加一个「零成本兜底」

你说不要版本号 —— 那就**不在数据库里做版本**，但在**文件层面留一份归档**：

```
覆盖前：PathBuilder.Archive("/…/_template/风险管理报告.docx", n)
     → /…/_template/_archive/风险管理报告.docx.v{n}
```

- **复用已有方法**（`PathBuilder.Archive()`），零新增代码
- **零表结构成本**（不建版本表、不加版本列）
- 收益：模板被改坏时，**还能从 MinIO 找回上一版**

> 这是我唯一想在你「不引入版本号」上坚持的一点 —— 因为模板是**人工精调**的产物，误覆盖的代价远高于一次归档调用。

## 三、「自动带出」必须落库标记 ⚠️ 本节是最容易漏的

你的第 3/4 条是：「重新上传了文件，发现该字段有值，**不是直接覆盖，应该是自动带出**」「重新点击分析的时候，如果有值，则自动带出，**不是重新执行语义分析**」。

**行为定义清楚了，但落库还缺一个东西**：**UI 怎么知道「这个值是刚 AI 生成的」还是「这是上次留下的」？**

### 3.1 建议：每个可带出字段配一个 `*Source`

| 列 | 取值 | 语义 |
|----|------|------|
| `TagsSource` | `ai` / `manual` / `carried` | 标签从哪来 |
| `DocPurposeSource` | `ai` / `manual` / `carried` | 文档作用从哪来 |
| `FillPromptSource` | `ai` / `manual` / `carried` | 提示词从哪来 |

- `ai` = 本次 AI 新生成
- `manual` = 人工改过（**最高优先级，永不自动覆盖**）
- `carried` = 本次未重跑，沿用已有值

### 3.2 分析端点的行为（写死）

```
点击「分析」：
  for 每个可带出项（Tags / DocPurpose / FillPrompt）:
      if 已有值且 Source ∈ {manual, carried}:
          → 直接返回已有值，标记 Source=carried        ← 不调 AI
      else:
          → 调 AI 生成，标记 Source=ai
  → 扫描锚点（这部分永远重跑，因为文件可能变了）
```

**关键**：`manual` 的值**连「重新分析」按钮都不该覆盖** —— 那是人工精调的结果。要改只能人工再改。

### 3.3 UI 表现

| 标记 | 展示 |
|------|------|
| `ai` | 徽标「AI 生成」+ 可编辑 |
| `manual` | 徽标「人工设置」+ 可编辑 + 🔒「重新分析不会覆盖」 |
| `carried` | 徽标「沿用已有」+ 可编辑 |

## 四、完整表结构清单

### 4.1 总览：**新建 3 张表**

| # | 表 | 类型 | 职责 |
|---|----|------|------|
| 1 | `cert_doc_template` | 🆕 | **模板主表**：文件 + 分类 + 作用 + 填写提示词 + 扫描结果（**合并了原 `cert_doc_template_scan`**） |
| 2 | `cert_doc_template_anchor` | 🆕 | **锚点清单**：标量 / 表格 / 合计 / 页眉页脚（**合并了你的「字段表」+「表格表」**） |
| 3 | `cert_tag_dict` | 🆕 | **标签字典**（受控词表，供多标签校验） |

**复用（只读，不改）**：

| 表 | 用途 |
|----|------|
| `cert_standard_directory_file` | 模板宿主；`StoragePath` = 下载源；`ConvertedStoragePath` = 统一格式源 |
| `cert_doc_field_def` | 读侧字段定义（与锚点按 `FieldCode` 对齐） |
| `cert_doc_table_def` + `cert_doc_table_field_def` | 读侧表格定义 |

### 4.2 为什么「字段表」和「表格表」建议合并成一张

你的第 6 条要分两张表。**建议合并为 `cert_doc_template_anchor`，用 `AnchorType` 区分**：

| 理由 | 说明 |
|------|------|
| **扫描器是同一个循环** | 解析 Word/Excel 结构时，标量、表格、合计、页眉页脚是**一次遍历同时产出**的；分表要拆成两轮写 |
| **「合计」「页眉页脚」无处安放** | 它们**既不是字段也不是表格**。分两张表时，`{{SUM_ROWS}}` 和 `{{PAGE}}` 只能硬塞进其中一张，语义别扭 |
| **唯一键天然统一** | `uk(TemplateCode, AnchorType, AnchorKind, SheetName, SectionIndex, HeaderKind, AnchorRef)` 是一把钥匙管全部 |
| **UI 上照样分两块** | 页面上按 `AnchorType` 分组渲染 —— **你看到的就是「字段」和「表格」两个 Tab**，心智模型不变 |

> 换句话说：**数据库一张表，界面两块内容**。你想要的体验保留，数据不分裂。

## 六、8 条更完善的建议

### 6.1 ★ 提示词要**结构化**，不要存一坨纯文本

你定「一个模板一个完整提示词」是对的（省 AI 调用、能做跨字段校验）。但**别让维护人员手写 50 个字段名** —— 字段名一改，提示词就失效。

**建议**：`FillPrompt` 存「**模板正文 + 变量占位**」，渲染时由系统从锚点表自动注入：

```
FillPrompt 正文（维护人员只写「怎么填」的语义）：
────────────────────────────────────
你是体系认证文档填写助手。请根据下列企业资料，为《风险管理报告》生成字段值。

【需要填写的字段】
{{FIELD_LIST}}
────────────────────────────────────

渲染时自动展开为（从 cert_doc_template_anchor 生成）：
────────────────────────────────────
【需要填写的字段】
- ENT_NAME（企业名称，string）：填写营业执照上的完整名称
- CERT_SCOPE（认证范围，string）
- RISK_LEVEL（风险等级，string）：高/中/低
────────────────────────────────────
```

**收益**：改字段不用改提示词；提示词长度可控；维护人员的心智负担大幅下降。

> ⛔ **勘误（2026-10-02，见 `22` 号 §9.1）**：占位符**必须写成 `{{FIELD_LIST}}`，不能写 `{{#FIELD_LIST}}`**。
> 依据：`PromptRenderer.Placeholder` 正则 = `\{\{([\w\u4e00-\u9fff][\w\u4e00-\u9fff.]*)\}\}`（`CertPlatform.Admin/Services/Workflow/PromptRenderer.cs:16-17`），字符类为 `\w` + 中文 + `.`，**不含 `#`** ⇒ 带 `#` 的占位符**永远不会被替换**，且因为 `Render` 未命中时**保留原文**，它会**静默地以 `{{#FIELD_LIST}}` 原样留在提示词里**（不报错、结果看起来正常但是错的）。

### 6.2 ★ 「带出」必须落库标记（见 §三）

`TagsSource` / `DocPurposeSource` / `FillPromptSource` 三个列。**没有它们，UI 无法区分「AI 刚生成」和「上次留下的」**，你的第 3/4 条行为就只做了一半。

### 6.3 ★ 重传的合并规则要写死（见 §二.2）

覆盖什么 / 保留什么 / 锚点 diff 怎么处理。**尤其是「消失的锚点不能删」** —— 它可能已有填过的值。

### 6.4 `FieldCode` 发布即冻结（铁律四）

模板重传时，**字段名不能改**（`ENT_NAME` 不能改成 `ENTERPRISE_NAME`）。因为：
- 锚点按 `FieldCode` 绑定
- 读侧 `cert_doc_field_def` 按 `FieldCode` 对齐
- 改名 → 读侧对不上 → 全链静默失效

**扫描器要校验**：锚点里的 `FieldCode` 必须 ∈ 该标准文档的字段定义（不在 → 红牌）。

### 6.5 ★「无字段无表格」的判定口径要精确

不要用「扫描结果为空」判定。**正确口径**：

```
需人工录入的锚点数 = COUNT(AnchorType IN ('scalar','table')) WHERE IsOrphan=0
若 = 0  →  报错「该模板未识别到任何可填字段或表格」
```

**为什么排除 `table_total` 和 `domain`**：`{{SUM_ROWS}}` 是平台算的，`{{PAGE}}` 是页码 —— **都不需要人工录入**。一个只含页眉页脚页码的模板，不该被判为「有效模板」。

**报错文案建议**：
> 「该模板未识别到任何可填字段或表格。请确认：① 标签是否用 `{{FieldCode}}` 格式；② 是否套了 `YZH_Mark` 样式；③ 是否需要更换空白文档。」

### 6.6 ★ 标签必须受控，禁止自由文本

`TagsJson` 的每个值必须 ∈ `cert_tag_dict.TagCode`。**否则标签漂移 → 召回退化**（`14` 册 §10 已登记该风险）。

UI 用**多选下拉**（从字典取），不是自由输入框。新增标签走「提交 → 待审核 → 入字典」流程。

### 6.7 ★ `DocCategory` 与 `TagsJson` 是两个维度，建议都留

| 列 | 基数 | 用途 |
|----|------|------|
| `DocCategory` | **单值**（fixed/editable/hybrid） | 决定**填充策略** —— 固定文档（营业执照类）走「替换」，可编辑文档走「生成」 |
| `TagsJson` | **多值** | 供**检索 / 召回** |

**如果只留多标签**，「这个文档该用哪种填充策略」这个信息就丢了 —— 后面匹配引擎没法分流。

### 6.8 下载体验要处理「转换中」这个中间态

若采用**按需转换**（方案 B）：点「下载标准文档」→ `ConvertedStoragePath` 为空 → 入队 → **前端显示「转换中…」并轮询** → 完成后自动开始下载。

⛔ 不要让用户点一下、等 3 秒、然后超时。LibreOffice 冷启动可能 2–5 秒。
