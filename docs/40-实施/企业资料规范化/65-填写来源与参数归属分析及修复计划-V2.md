## 一、四个问题，逐条回答

### Q1 「通用参数我觉得可以保留」—— 成立，且是必需的

**结论：保留，而且它是「跨标准共用字段」的唯一合法落点，删不掉。**

| 判据 | 证据 |
|---|---|
| 运行期解析就是靠它兜底 | `CoreResourceQuery.GetFillParamDefsAsync`（`CoreResourceQuery.cs:505-537`）谓词 = `OrgCode=="" && (StandardCode=="" \|\| StandardCode==sc)` —— **空串即「对所有标准生效」** |
| 现状 8 条参数全在通用 | 实测 `cert_fill_param_def` 8 行 **`StandardCode` 全为空串**（文件编号前缀 / 持有资质证书 / 主要产品 / 企业荣誉 / 质量方针 / 质量目标 / 企业概况 / 上次审核遗留问题） |
| 没有它必然重复定义 | 企业全称、统一社会信用代码这类字段在 ISO9001 与 ISO13485 都要用 ⇒ 不通用就得每个标准各建一条 |

⚠️ **但有一条必须澄清的口径**（否则会被误判为缺陷）：
「通用参数」与「企业基本信息」**不是一回事，两者并存不是重复**：

| | 通用参数（`StandardCode=''`） | 企业基本信息（`enterprise.*`） |
|---|---|---|
| 存储 | `cert_fill_param_def` + 企业填的 `cert_fill_param_value` | 直接读 `cert_enterprise` 列 |
| 引擎能力 | `global`（Order 100，**企业可覆盖**） | `replace`（Order 30，**只读**，企业改档案即改文档） |
| 配置入口 | 后台「企业资料参数」页可增删 | **前端硬编码 16 项**，不可增删 |
| 典型用例 | 文件编号前缀、质量方针 | 企业全称、统一社会信用代码 |

⇒ 判据（写模板时照此选，来自 `ReplaceResolver.cs:22-25`）：
**「这个位置允不允许企业填一个和档案不同的值？」允许 → 通用参数；不允许 → 企业基本信息。**

### Q2 参数该挂在「族」上还是「具体标准」上？

**结论（推荐）：主挂载点 = 具体标准；族 = 只读导航节点（点击看该族下所有标准的参数合集），⛔ 不引入族级存储与三层解析。**

#### 2.1 现状（实测）

| 层 | 是否可挂参数 | 证据 |
|---|---|---|
| 通用参数 | ✅ 可（`StandardCode=''`） | `FillParamDefController.OnBeforeAdd`（`:129-134`）只归一 `OrgCode`/`StageCode`，**放行 `StandardCode`** |
| 体系（`iso_category` 字典） | ⛔ 不可（virtual） | `logic.ts:70-75` `isSelectableNode` 判 `NodeType==='virtual'` ⇒ 不可点 |
| **族（`cert_standard_family`）** | ⛔ **不可（virtual）** | 同上；`loadConfig` 里 `MaxLevel:3`、族为 virtual |
| 标准（`cert_iso_standard` 叶子） | ✅ 可（`StandardCode=ISO GUID`） | `onPrepareAdd`（`logic.ts:200-202`）注入选中节点 Code |

⇒ **现状就是「只能挂 通用 或 标准」**，族点不动（点了只展开/折叠）。这与你观察到的现象一致。

#### 2.2 三个方案

| 方案 | 做法 | 好处 | 代价 | 风险 |
|---|---|---|---|---|
| **A（推荐）族 = 导航** | 存储仍只有两级（通用 / 标准）。族节点改为**可点击的只读聚合视图**（列出该族下所有标准的参数）；在族节点上点「新增参数」时，**先要求选一个具体标准**（或弹窗多选后批量下发到各标准） | 运行期解析**零改动**（仍是 2 层）；用户获得族的分组便利；语义诚实 | 纯前端 + 1 个只读端点 | 低 |
| **B 加 `FamilyCode` 列 + 三层解析** | `cert_fill_param_def` 加 `FamilyCode`；解析优先级 标准 > 族 > 通用；`PickMostSpecific` 加一层 | 族内共性参数只配一次 | ⚠️ **5 处联动**：① 实体/表加列 ② `uk_org_std_stage_param` 唯一键加列 ③ `GetFillParamDefsAsync` 谓词加 OR ④ `ParamValueResolver.PickMostSpecific` 加优先级 ⑤ 前端 `kindOfRef`/卡片分组 | **高**：同 `ParamCode` 在族与标准各有一条时优先级需额外裁决；任一处漏改 = **配了不生效且两边不报错** |
| **C 把「通用」升级为「族」** | 用族取代通用 | —— | ⛔ 语义错（跨族字段无处放，如企业全称） | 高 |

#### 2.3 为什么推荐 A（判据）

1. **运行期的标准维度是唯一的**。参数最终是否生效，由「模板属于哪个标准」（`cert_doc_template.StandardCode` → `FillRequest.StandardCode`）决定，**族不进运行期**。把族塞进解析链 = 引入一个运行期不需要的维度。
2. **A 的「族内共性」用「批量下发」解决，不用「继承」解决**。你真正要的是「一次配、族内全生效」这个**操作效率**，而不是「族是参数的所有者」这个**数据语义**。批量下发满足前者，且不污染后者。
3. **B 的收益/风险比不划算**。族内共性参数的真实规模（ISO9000 族目前只有 1 个标准 `iso13485`；`cert_standard_family` 活跃 2 行）**撑不起 5 处联动改造**。
4. **符合项目铁律「规则必须正确，不用 UI 选项绕过程序缺陷」**（`61` §R-3）：B 一旦落地，就必须同时定义「族与标准同码时谁赢」，否则又是一层「想当然」。

#### 2.4 顺带要修的现状瑕疵

- 族/体系节点**当前完全点不动**（`isSelectableNode` 返回 false），用户点它会得到「无反应」——这本身就是体验问题。按方案 A，族节点应变成**可点（只读聚合）**。
- 左树层级 `MaxLevel:3`（`logic.ts:139`）与「体系 → 族 → 标准」三层一致，无需改。

### Q4 ★ 四类信息在「文档填写规则」里如何引用（核心）

#### 4.1 先给全景（设计 ↔ 实现 对照）

> 「文档填写规则」的配置形态 = **一个锚点 = 一个来源**（`61` §R-1/S-3 用户裁定）。
> 一个来源 = `{ kind, ref, ... }`，写在 `cert_doc_template_anchor.SourceSpec`。
> 前端把 kind 归并成 **6 张卡片**（`sourceSpec.ts:61-96`），其中「全局参数」卡片下再分 **4 组**。

| 你要引用的信息 | 配置入口（UI） | 存储 `kind` / `ref` | 运行期解析器 | 状态 |
|---|---|---|---|---|
| **全局参数**（跨标准） | 全局参数 卡片 → 组③「后台定义的全局参数」 | `global` / `ParamCode` | `GlobalParamResolver`(Order 100) ← `FillParamValueProvider` | ✅ **通**（实测 7 条可用） |
| **不同标准的参数** | 全局参数 卡片 → 组④「标准对应的参数」 | `global` / `ParamCode`（定义行带 `StandardCode`） | 同上，谓词 `StandardCode=="" \|\| == sc` | ⚠️ **半通**（见 G-B） |
| **企业基本信息** | 全局参数 卡片 → 组①「企业基本信息」（16 项） | `replace` / `enterprise.<Attr>` | `ReplaceResolver`(Order 30) ← `EnterpriseInfo` | ✅ **通**（16 项） |
| **机构 / 系统变量** | 全局参数 卡片 → 组②（12 项） | `replace` / `org.*` `system.*` | 同上 | ✅ 通 |
| **文档信息** | 文档信息 卡片（6 项） | `headerFooter` / `@doc_no` … | `HeaderFooterResolver`(Order 20) | ⚠️ `@doc_no`/`@version` **无来源**（刻意留空） |
| **企业标准条款** | **⛔ 无入口** | **⛔ 无 kind** | **⛔ 无解析器** | ⛔ **完全缺失 —— 但 V2 已关闭**（G-A，取证见 §4.2） |
| **企业资料原文（画像）** | ⛔ 前端已删（`61` §R-2） | `profile`（后端仍认） | 编排器 `ResolveFromProfile`（读 `FieldsJson`） | ⚠️ **后端有、前端无**（G-C） |
| **AI 生成** | AI 语义生成 / AI 字段 / AI 表格（3 张卡片） | `ai_semantic` / `ai_field` / `ai_table` | 编排器 `ResolveAiAnchorsAsync` + `AiFillPromptBuilder` | ⚠️ 见 G-C |
| **人工填写** | 人工填写 卡片 | `manual` | `SourceResolver.TryResolveManualAsync`（查 `cert_doc_ai_suggestion`） | ⚠️ **语义与文案不符**（`61` P1-1） |

#### 4.3 缺口 G-B：**配置期「标准对应的参数」不按当前模板的标准过滤**（静默失效）

**事实链**：
1. 前端取参数清单：`listFillParamDefs()` → `POST /api/Admin/Cert/FillParamDef/filter`，
   **`Filters` 里只有可选的 `ParamCode like`，没有 `StandardCode`**（`doc-fill-rule.ts:602-610`）。
2. 前端分组：`AnchorSidePanel.vue:216/220` 只按「**有没有** `standardCode`」分成 组③ / 组④，
   **不按当前模板的 `StandardCode` 过滤**。
3. 运行期解析：`GetFillParamDefsAsync(sc, stc)` 谓词 = `StandardCode=="" || StandardCode==sc`
   ⇒ 一个 `StandardCode=ISO9001` 的参数，在 **ISO13485 模板**里**取不到**。
4. 取不到时归因（`GlobalParamResolver.cs:49`）报的是
   「参数「x」尚未完善，请到「企业全局参数定义」填写」——
   **指错方向**：真正的问题是「这条参数不属于本模板的标准」，不是「企业没填」。

**症状**：实施人员在配 ISO13485 模板时，能从 组④ 里选到只对 ISO9001 生效的参数 → 保存成功 → 运行期恒 pending。

**修复**：
- 前端：组④ 增加**当前模板标准**的过滤（模板标准可从 `doc-fill-rule` 页当前模板上下文取）；
  或后端在 `/filter` 支持 `StandardCode` 入参，前端传模板标准。
- 后端：`GlobalParamResolver` 的失败原因区分「**参数不属于当前标准**」与「**企业未填**」两种
  （新增一条归因分支，⛔ 不合并成一句话）。

#### 4.4 缺口 G-C：**AI 来源拿不到「结构化」企业信息**

**事实链**：
1. AI 锚点的「依赖企业资料」开关（`DependsOnEnterprise`）在 `BuildAiInstructionAsync`（`:1828-1830`）里
   **只做一件事**：当 `false` 时追加一句「本项不依赖企业资料…」。
   **`true` 时并不额外注入任何结构化企业字段**。
2. 企业信息的实际注入点 = `EnterpriseDocs`（`:1340`），内容是**企业文档画像的 markdown 原文**
   （由 `cert_enterprise_doc_profile` → `MarkdownPath` 拼成，`:1273-1276`）。
3. ⇒ **若企业没有画像（`cert_enterprise_doc_profile` 无行），AI 拿到的企业信息 = 空**；
   且 AI 提示词里**无法引用 `{{enterprise.Name}}` 这类结构化字段**（提示词只能引用「参数」，
   见 `AiFillPromptBuilder.RenderParamRefs`，而参数走的是 `cert_fill_param_value`）。

**症状**：企业还没上传资料 / 画像未跑时，配了「依赖企业资料」的 AI 锚点会生成**脱离企业实际**的内容，
且**不报错**（模型会自己编）。

**修复**：
- AI 提示词上下文里补入**企业结构化快照**（复用 `EnterpriseInfo`，键名如 `enterprise.Name` / `enterprise.CertScope`），
  与 `EnterpriseDocs` 并列；并在「依赖企业资料 = true 但两者皆空」时**显式降级为待办**（⛔ 不让模型裸编）。
- 前端 AI 卡片 ② 段补一句可读的说明（当前只说「是否依赖企业资料」，用户不知道「依赖」具体依赖什么）。

#### 4.5 顺带缺口 G-E：**企业属性清单有两份副本，无同步机制**

| 副本 | 位置 | 条数 |
|---|---|---|
| 后端 | `ReplaceResolver.EnterpriseAttrLabels`（`ReplaceResolver.cs:113-131`） | 16 |
| 前端 | `sourceSpec.ts` `ENTERPRISE_ATTRS`（`:118-135`） | 16 |

`ReplaceResolver.cs:109` 的注释声称「全项目唯一口径：`FillParamDefController.EnterpriseAttrs`」——
**该端点已于 2026-10-06 删除**（`fill-param-def.ts:19-20`），**注释已过时**。

⇒ 加一个企业字段要改 **2 处**（后端 + 前端），漏一处 = 「选得到但取不到」或「取得到但选不了」。
建议：新增一个只读端点下发属性清单（后端为唯一源），或至少在两端加**守卫断言**（条数 + 键名一致）。
