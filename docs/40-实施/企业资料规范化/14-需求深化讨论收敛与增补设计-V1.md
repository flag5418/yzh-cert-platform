## 2. 路线裁决（本报告最重要结论）

### 2.1 架构哲学：YZH-STD-ENT 统一表设计

**`YZH-STD-ENT` 是故意设计的架构标识符，不是临时妥协方案。**

```
┌─────────────────────────────────────────────────────────────┐
│  统一表结构设计哲学                                          │
│                                                             │
│  cert_standard_directory_file                              │
│    ├── EnterpriseCode = 'YZH-STD-ENT' → 标准侧            │
│    │       （后台配置、提取规则、契约定义）                     │
│    └── EnterpriseCode = 真实企业 Code           → 企业侧    │
│              （实际上传的文件、画像、匹配结果）                  │
│                                                             │
│  同一张表 = 同一套字段 = 同一套CRUD逻辑                       │
│  唯一区别：EnterpriseCode 列的值                             │
└─────────────────────────────────────────────────────────────┘
```

**设计收益**：

| 维度 | YZH-STD-ENT 统一表 | 独立表方案（B路线） |
|------|-------------------|---------------------|
| 代码复用 | ✅ 一套Controller/Service | ❌ 两套平行逻辑 |
| 数据一致性 | ✅ 天然同构 | ⚠️ 需维护双表同步 |
| 查询简化 | ✅ `WHERE EnterpriseCode = 'YZH-STD-ENT'`（**禁 NULL 后不再需要 `IS NULL` 分支**） | ⚠️ 需JOIN或视图 |
| 扩展成本 | 低（加列） | 高（建新表+映射） |
| 匹配引擎挂载 | 直接过滤EnterpriseCode | 需建视图或额外FK |

**相关决策佐证**：
- 工作流引擎的 `get_field`/`get_table` Skill 使用 `YZH-STD-ENT` 作为测试数据锚点
- NC 检查规则配置使用 `YZH-STD-ENT` 存储标准侧规则定义
- 报告模板配置同理

这一架构模式已在系统中多处应用，13号分册的实现是正确的方向。

### 2.2 裁决结论

**裁决（登记为 README D11）：维持 A 路线——YZH-STD-ENT 统一表架构，不新建独立企业文件表。13 号已实施功能继续有效，仅需修正少量代码规范问题。**

## 3. 产品定位与商业约束

| 定位 | 对设计的约束 |
|------|--------------|
| **面向企业收费的核心功能**；价值 = 替代企业/咨询公司的人力与时间成本 | 质量优先于成本；`ent_norm_max_calls` 类上限在本地模型部署后可放开 |
| **通用性工具产品**，非针对单一标准定制 | 所有定制通过配置表（契约、标签字典、全局参数）实现，代码零硬编码特定标准 |

| 定价依据 | 验收指标补业务口径（D23）：自动归位率、单份裁决耗时、替代率 |
| 模型策略 | API 优先（六键配置），本地模型（LLM/embedding）作为部署选项，切配置即可——架构模型无关 |

## 5. 增补设计清单（D12–D28）

### D12 匹配双模式（simple / deep）

| 模式 | 流水线切点 | LLM | 定位 |
|------|-----------|-----|------|
| `simple` | 指纹 + 召回（标签倒排为主信号，辅以文件名/markdown 摘要相似度） | 0 次 | 引流/快速预览 |
| `deep` | simple + LLM 精排 + 证据链 + 五维分 | 每契约 1 次批式 | **默认**，收费档 |

- 触发接口加 `Mode` 参数（默认 `deep`）；simple 产出 = 召回分直接作 `Confidence`、`ScoreStage='recall'`、全部进人工队列（复用 04 §4.4 既有退化路径，零新增逻辑）。

### D13 文件夹 × 文件夹 = 主交互轴

- **入口**：标准目录树选文件夹（含子树）× 企业侧范围（分组/文件夹/全部）→ 建匹配队列（Payload 带 `ScopeFolderCode + ScopeFileCodes`）；
- **过程**：该文件夹下每个标准文档走完整三阶段；**精排 prompt 注入文件夹主题上下文**（文件夹名 + 同级文档清单摘要）——同文件夹内文档天然相似，跨文件夹区分靠主题；
- **产出**：文件夹维度清单（每个标准文档一行：候选/无候选/已确认），逐文档裁决 → 试填 → 文件夹进度（`InstanceState` 聚合到文件夹，纯 UI 汇总不建表）；
- **全局自动规范化 = 同一逻辑递归到根文件夹**（按子文件夹逐个填充），非独立流程。

### D14 多标签体系（受控字典，双侧同规则）

- **字典**：新薄表 `cert_tag_dict`（TagName / Category / Sort / IsValid），**受控词表**。种子来源 = 标准目录文件夹树（质量手册/程序文件/制度文件/记录文件…）+ 体系域（质量/环境/职业健康安全）+ ISO 条款业务过程（文件控制/内审/管理评审/培训/设备/计量/不合格品控制…）。三层分类（形态 × 体系域 × 业务过程），一文档多标签。
- **生成规则**：标签生成提示词 = 按体系认证业务规范编写的资产（存 `wf_prompt_template`），**约束 LLM 只能从字典选**，允许建议新词 → 进待审核，不直接入库。
- **双侧同规则**：企业文档标签 = 画像自动打（输出 schema 加 `tags: []`）；标准文档标签 = 契约维护（AI 从文件夹路径 + DocPurpose 建议初值，人工确认）。**同字典同规则 → 两侧可比**。
- **召回**：标签集合交集/Jaccard 作为独立召回路（标签即倒排索引——一个标签直接捞出两侧集合，"快速定位、天然降低筛选范围"）。**标签重叠是真配对的最强先行信号，直接压低召回漏配率（§6 对冲①）**。
- **与分组的关系（D15）**：分组 = 高频标签聚类的物化，共享同一字典。

### D15 企业资料预分组（薄层）

- 新表 `cert_ent_doc_group`（Code / EnterpriseCode / GroupName / TypeTag / 统计）+ `cert_standard_directory_file.GroupCode`；支持人工改名/合并/拆分；
- 聚类起步用规则（类别词 + 标签/关键词 Jaccard），deep 可选 embedding 聚类；
- 价值链：企业资料现状一览（咨询价值，收费点）→ 组↔标准文件夹粗对齐建议（人工确认后组内文档级匹配，N×M 缩到 n×m）→ 分组一键转文件夹整理建议；
- 边界：分组永远是建议，不自动改企业文件夹结构。

### D16 填充策略四值（契约新增 `FillStrategy`）

| FillStrategy | 适用标准文档 | 匹配信号 | 数据源 | 填充动作 |
|--------------|--------------|----------|--------|----------|
| `replace` 关键信息替换 | 申请书/承诺书/授权书/合同等文书类 | **不参与企业文档匹配**（平台模板直接生成）；企业自传版本走指纹 | 企业主数据（`cert_enterprise`：名称/地址/法人/信用代码）+ 固定文档画像字段（营业执照等提取值）+ 人工输入 | 模板占位符（`{{FieldCode}}`/书签，定义=契约字段）批量替换，NPOI 落盘 |
| `extract` 抽取填充 | 记录表单类 | 标签 + 字段/表格命中 | `cert_extraction_result`（AI 原值 + 人工覆盖合并视图） | 字段/表格值写入模板（现有主路径） |
| `derive` 差距分析 | 制度/模板衍生类（企业拿模板改的） | **结构同源检测**：标题树比对 + 段落相似度 | 企业文档本身即 90% 正确底稿 | diff 出差异清单（缺章节/多章节/关键段改动）→ 人工逐项采纳 → NPOI 保留样式落修改 |
| `synthesize` AI 组织撰写 | 段落综合类 | 语义 | LLM | 按 `SynthesisPrompt` 组织撰写（既有设计） |

- 契约页下拉配置，管线按策略走分支，**禁止代码里写死类型清单**（对齐 05 分册既有禁令）；
- **replace 的数据源闭环**：固定文档链（营业执照→统一社会信用代码/法人/经营范围）提取的企业基础信息，回流为 replace 类文档的替换值来源——固定文档做一次，全套文书受益。

### D17 向量召回升级 + 批次工作集

- R4（embedding 召回）从"二期评估"升为 **P2 期内可配置开关，本地模型部署后默认开**；
- **不上向量数据库**：匹配按企业作用域隔离，一家企业 100 文件 × 约 50 章节块 ≈ 5000 向量 × 1024 维 ≈ 20MB——embedding 存 MySQL（JSON/BLOB 列），任务内内存余弦扫描即可；
- **批次工作集**（取代"长期缓存"）：匹配任务开始时一条 `SELECT … WHERE IsLatest=1` 全量载入画像（含标签、精排就绪摘要），任务结束释放；每次批次取最新，天然无失效问题。工作集放**精排就绪摘要**（作用 + 类别 + 标签 + 关键字段 + 表头），拼 prompt 零转换。

### D18 NPOI 实例生成服务（L5 补全）

### D24 审核页面交互模型（新增）

> **核心定位**：所有自动化产出最终都要经过审核员之手。审核后台不是"编辑文档内容"的文本编辑器，而是"完成度 + 可信度 + 可调数据源"的**可信度漏斗**。

**两颗核心指标**：

| 指标 | 公式 | 渲染 | 设计意图 |
|------|------|------|----------|
| **完成度** `CompletionRatio` | `已填写字段数 / 契约字段总数`（`COUNT(FilledValue IS NOT NULL) / COUNT(cert_doc_field_def)`） | 顶部进度条（百分比 + 分数如 `17/23`） | 让审核员一眼知道"这块文档还有多少没填" |
| **景信度** `ConfidenceRatio` | `AVG(字段Confidence)` 未填写字段 Confidence=0 计入平均 | 顶部彩色徽标（绿≥0.85 / 黄 0.5–0.85 / 红<0.5） | 让审核员判断"能直接采纳 vs 需要逐字段核查" |

```csharp
// 两颗指标的计算
public class AuditPageMetrics {
    // 完成度：0.0 ~ 1.0
    public decimal CompletionRatio =>
        (decimal)Fields.Count(f => f.FilledValue != null) / Fields.Count;

    // 景信度：0.0 ~ 1.0，未填字段按 0 计
    public decimal ConfidenceRatio =>
        Fields.Average(f => f.FieldConfidence ?? 0m);
}
```

### D25 文档四型填充矩阵精化（新增）

> D16 已定义 FillStrategy 四值。本轮用户进一步确认了四类必须按规则区分，并揭示了 **DocCategory=fixed 内部的两类不同填充动作**。

**FillStrategy 四值精确定义**：

| FillStrategy | 用户称谓 | 适用文档 | 数据源 | 平台动作 | 审核页面上呈现 |
|---|---|---|---|---|---|
| `replace` **只替换关键字** | 企业主数据驱动的合同/申请书 | 申请书/承诺书/授权书/合同等文书类（**不参与企业文档匹配**——平台模板直接生成；企业自传版本走指纹） | ① 企业主数据（名称/地址/法人/信用代码）② 固定文档 OCR 回流值（营业执照提取的统一社会信用代码等）③ 手动输入 | 模板占位符（`{{FieldCode}}`/书签，定义 = 契约字段定义中的 FieldCode）批量替换，NPOI 落盘 | 蓝底高亮字段 = 自动替换；点击可改**替换来源**（主数据/固定文档/手动） |
| `extract` **从企业文档提取** | 记录表单类（支持多文档聚合） | 培训记录/设备台账/内审计划等**结构化字段密集型文档** | `cert_extraction_result`（AI 原值 + 人工覆盖合并视图） | 按字段抽取规则从企业文档 Markdown 抽取；多文档时按 AggregateRule 选择最优 | 紫底字段 = 抽取的；点击可看**候选文档列表 + 候选抽取值** |
| `synthesize` **描述性撰写** | 需要根据企业具体情况描述的段落/文档 | 质量方针/企业介绍/过程描述等**自由描述性内容** | LLM 按 SynthesisPrompt 生成（可调参数：文档体裁/详细程度/侧重点） | 按 SynthesisPrompt 组织撰写 | 橙底字段 = AI 撰写；点击可**修改提示词重新生成** |
| `derive` **差距分析** | 企业拿了模板改的制度/文件 | 企业从体系咨询公司买的模板改编的制度类文件 | 企业文档本身即 90% 正确底稿 | diff 出差异清单（缺章节/多章节/关键段改动）→ 人工逐项采纳 → NPOI 保留样式落修改 | 绿底 = 与原模板一致；红底 = 企业增删改 |

**DocCategory=fixed 的二级拆分（用户揭示的关键差异）**：

在 D16 / 05 分册 §3 中 `DocCategory=fixed` 涵盖所有固定格式文档。用户在 R7 指出：这两类在**填充动作**上完全不同，需要在审核页面区分呈现。

| FixedDocSubtype | 典型文档 | 平台动作 | 审核页面呈现 |
|---|---|---|---|
| `enterprise_provided` 企业提交原件 | 营业执照、许可证、资质证书、法人身份证明、体系证书 | OCR → 抽取字段值 → 回流为 `replace` 类文档的数据源（固定文档做一次，全套文书受益） | 原件缩略图 + OCR 识别文本 + 字段值表格（可编辑）；**不可穿透替换原文** |
| `platform_generated` 平台自动生成 | 标准目录索引表（自动从标准目录层级结构生成）、空白记录表单模板（自动从字段/表格定义生成）、法规清单 | 从标准目录元数据 / 契约定义直接生成（**完全不走 LLM**，纯规则驱动） | 展示为"系统已生成——无需企业填写"，提供 [重新生成] 按钮 |

**合同表增加字段**：`cert_standard_doc_contract.FixedDocSubtype` enum(`enterprise_provided`,`platform_generated`)，NOT NULL DEFAULT `enterprise_provided`。

**多文档聚合提取（extract 的增强）**：

现有 D16 表格中 extract 定义为"从 `cert_extraction_result` 抽取"。用户确认实际场景中经常需要**从多份企业文档取同一字段的不同维度值**（例如：企业名称从营业执照取、法人从章程取、地址从租赁合同取）。

`cert_doc_field_def` 新增 `AggregateRule` 字段（text/JSON）：

```json
{
  "mode": "priority",
  "description": "优先级：取最高可信度的值",
  "sources": [
    { "fileType": "营业执照",    "fieldName": "企业名称", "priority": 1, "expectedConfidence": 0.99 },
    { "fileType": "组织章程",    "fieldName": "公司名称", "priority": 2, "expectedConfidence": 0.70 },
    { "fileType": "高新技术企业证书", "fieldName": "企业名称", "priority": 3, "expectedConfidence": 0.85 }
  ],
  "selection": "highest_confidence",
  "fallback": "manual"
}
```

三种模式：

| mode | 语义 | 适用场景 |
|------|------|----------|
| `priority` | 按优先级取第一个命中的值 | 有明确偏好顺序（营业执照 > 其他） |
| `concat` | 多值拼接（用分隔符） | 多个值都需保留（如"多企业名称汇总"） |
| `max_confidence` | 取所有候选中 Confidence 最高的值 | 不确定哪份文件最准，让系统自动判断 |

**结合完成度/可信度的效果**：

- 当 extract 字段的 AggregateRule 有多个 source，且只有一个 source 解析成功 → 完成度=1但 Confidence 显著低于 multi-source-parsed 的字段（因为"只有一份文件佐证"）
- 审核员点开这样的字段 → 看到 candidate 面板里其他 source 标"未命中"，自然理解需要再补一份来源佐证

**缺口分析（Gap Analysis，"完成度"的低值信号）**：

CompletionRatio < 1.0 直接对应"体系文档位置未被覆盖"的情况。在审核页面上：

- 未填写的字段（FieldConfidence=0）标红，旁边显示"缺数据来源"
- 审核员有两种处理：① 手动录入 ② 触发"自动补录"——后台尝试从已上传但未匹配的企业文档中，按字段关键词做补抽
- 全局视图：文件夹级 CompletionRatio 排序 → 审核员优先处理最低完成度的文件夹（即缺口最大的地方）

**与 NC 检测的关系（D22 延续）**：

- CompletionRatio = 1.0 → 可以跑 NC（但 NC 可能发现内容错误）
- CompletionRatio < 1.0 → 直接跑 NC 没意义（字段缺失 NC 也检不出逻辑问题）
- 因此 NC 入口前置校验：该标准文档 CompletionRatio 必须 = 1.0，否则引导审核员先补字段

### D27 行业条款知识库（新增，P4 前瞻性）

**工作流**：

```text
新标准上线
  → 数据维护员选择标准 → 系统种子：
      从公开 ISO 条款解读资料 + 专家知识库 +
      同体系历史企业匹配数据中抽取高频条款-文档关联
  → 管理员审核 + 补充（每条款 ≤ 5 分钟）

  精排时：Confidence < auto 的候选，表中存在同 ClauseNum → 
          加 0.05 的行业知识加成（仅辅助，不决定）

```

**注意**：此功能不影响 MVP（种子脚本 + 契约手动配置可满足 P1–P3），排 P4 实施。建表即加（与 D19 预留列同原则，0 成本）。

### D28 全局参数体系（新增）

> **问题来源**：部分规范化字段（企业名称、法人、统一社会信用代码、文档编号等）需要在**所有标准文档间共享一致**。这些值可能来自企业文档 OCR 提取、也可能是 OCR 无法获取的项目元数据（如本次认证项目编号、统一的文档编号流水号）。**全局参数**提供了跨文档的企业主数据统一入口，一次填写、全套文书引用。

**两层数据结构**：

```
定义层：cert_global_param_def（全局参数定义模板，按 StandardCode 维度）
    ↓ 实例化
实例层：cert_global_param_instance（每次"企业×标准×阶段"任务的具体值）
```

**定义表 `cert_global_param_def`（管理后台维护）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `Code` | varchar(50) | 业务键 |
| `StandardCode` | varchar(50) | 关联 ISO 标准（ISO 9001 通用 / ISO 13485 专用） |
| `ParamCode` | varchar(50) | 参数编码（如 ENT_NAME / ENT_LEGAL_PERSON / ENT_CREDIT_CODE / DOC_SERIAL_NO） |
| `ParamName` | varchar(100) | 参数显示名（如"企业名称"） |
| `ParamType` | varchar(20) | text / number / date / enum |
| `DefaultValue` | varchar(500) | 默认值（可空） |
| `ValidationRule` | varchar(200) | 校验规则（如 credit_code = 18 位） |
| `IsRequired` | tinyint | 是否必填（0/1） |
| `Description` | varchar(500) | 填写说明（引导审核员填写） |
| `Sort` | int | 排序号 |
| `IsValid` | int | 启用标志 |

**实例表 `cert_global_param_instance`**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `Code` | varchar(50) | 业务键 |
| `EnterpriseCode` | varchar(50) | 关联企业 |
| `StandardCode` | varchar(50) | 关联 ISO 标准 |
| `StageCode` | varchar(50) | 关联认证阶段（可为空 = 跨阶段通用） |
| `ParamCode` | varchar(50) | 关联参数定义 |
| `ParamValue` | text | 用户填写的实际值 |
| `SourceType` | varchar(30) | 来源：`manual` / `ocr_extract` / `master_data` |
| `FillTime` | datetime | 填写时间 |
| `FillBy` | varchar(50) | 填写人 Code |

**数据填充时机**：

```
场景 A：OCR 已提取 → ParamValue 预填（SourceType=ocr_extract）
         审核员在审核页面确认/修改后 → SourceType 改为 manual

场景 B：无 OCR 来源（如文档编号）→ 审核员在"任务启动"弹窗中手动录入
         → 进入实例表（SourceType=manual）

场景 C：从企业主数据表（cert_enterprise）同步 → SourceType=master_data
```

**与 FillStrategy 的整合**：

| FillStrategy | 如何使用全局参数 |
|---|---|
| `replace` | **直接引用**：模板占位符 `{{ENT_NAME}}` → 查 `cert_global_param_instance WHERE ParamCode='ENT_NAME'` → 替换。这是全局参数最主要的消费场景 |
| `extract` | 作为**补充候选源**：字段 `AggregateRule` 可声明 `sourceType=global_param`，当 OCR 抽取失败时回退到全局参数值 |
| `synthesize` | 作为**上下文注入**：SynthesisPrompt 中注入全局参数作为 LLM 撰写基础信息 |
| `derive` | 一般无关（derive 消费的是企业文档本身） |

**审核页面的全局参数入口**：

```
规范化任务启动
  → 系统检查 cert_global_param_instance 是否有空值必填参数
  → 若有 → 弹出"请补充以下企业信息"面板（可在 30 秒内完成）
  → 用户填写 → 写入实例表
  → 后续 replace 类文档全部自动引用这些值

审核页面顶部
  → 新增 [全局参数] 按钮 → 侧边面板展示所有参数当前值
  → 审核员可直接修改（如统一更正企业名称格式）
  → 修改后触发所有引用该参数的文档重新填充（后台队列批量）
```

**与现有固定文档链的关系**：

D16 已定义"固定文档（营业执照→统一社会信用代码/法人/经营范围）提取的企业基础信息，回流为 replace 类文档的替换值来源"。全局参数体系是这个闭环的**正式存储与维护层**：

```
现状：固定文档 → 抽取值 → 直接写入字段（无中间存储）
D28：固定文档 → 抽取值 → 写入 cert_global_param_instance（SourceType=ocr_extract）
     → 所有 replace 字段统一从实例表读取
     → 审核员可在全局参数面板统一修改 → 触发所有引用文档重填充
     → 避免"改了一个文档的名、另一个文档漏改"的不一致问题
```

**排期建议**：
- **P0**：建两张表（定义表 + 实例表）；种子 10–15 个通用参数（企业名称/法人/信用代码/地址/联系电话/传真/邮编/成立日期/注册资本/文档编号前缀…）
- **P1**：13 号平移 + anydoc 链验证时，将固定文档抽取的全局类字段写回实例表
- **P3**：审核页面的全局参数面板 + 统一修改触发重填充

**工作量估算**：定义表种子 + 建表 + 基础 CRUD 约 **+1–2 天**（纳入 P0/P1，非独立大块）。

## 6. 设计依据：为什么不采用两两全量对比

**两两的两种形态及各自的问题：**

**形态 A（一次比一对，N×M 次）**——致命问题是**分数没有统一尺子**。每次调用只看一对，LLM 给的是孤立印象分（同一对今天 0.82、明天 0.74 是固有随机性）；文档甲得 0.80、乙得 0.78，无法确认是否同一把尺子。裁决页要排 a/b/c，**排序的前提是分数可比**。类比：100 个选手分散在 100 个考场、100 个考官各自关起门打分，最后排总名次——名次无意义。

**形态 B（每契约一次调用、100 个画像全喂，M 次）**——方向已对（同调用内横比 = 同一评委同一场比赛），剩下的问题是**名单太长**：输入约 4 万 token 的名单，模型对中部条目系统性看漏（lost in the middle）；输出 100 条评分 JSON 极易截断。

**三阶段 = 形态 B + 先把名单从 100 缩到 ≤20。** 召回不判断"像不像"，只排除"明显不可能"（营业执照不会是质量手册的候选），用标签/关键词/文件名零成本完成；精排在舒适区长度的名单内统一打分横比——尺子统一、看得全、输出不截断。

**召回先行的风险（漏配）与四层对冲**：① 多标签重叠（D14，最强对冲——内容相关即有共同标签）；② 反向召回（每个标准文档主动捞企业侧 Top-K）；③ 必需文档无候选强制进人工视野；④ `Recall@10 ≥ 0.90` 验收指标持续盯漏配率。

**结论**：三阶段不是省钱的妥协。token 免费、上了本地模型，仍然需要"同一个评委、同一场比赛"和"评委看得完的名单"——这是排序可信度的质量问题，不是成本问题。

## 10. 风险登记更新

| 风险 | 对策 |
|------|------|
| 标签字典维护懈怠 → 标签漂移、召回退化 | 新词必须走待审核；字典变更纳入契约页校验；定期用"标签覆盖率"报表巡检 |

| 审核员频繁替换数据来源导致队列压力 | change-source 接口设每文档每分钟 ≤ 3 次限流；后端异步队列 + 结果推 UI WebSocket；失败保留原值不丢 |

| 任务启动弹窗参数过多导致审核员疲劳 | 通用参数 10-15 个精简到必须的 5-8 个（名称/法人/信用代码/地址+阶段相关项）；其余提供"稍后填写"延后到审核页 |
