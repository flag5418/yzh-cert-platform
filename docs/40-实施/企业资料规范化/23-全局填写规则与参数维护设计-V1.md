## 〇.五、直答：「建立填写 Skill」这个思路是否合理

> 2026-10-02 用户反馈「**我还是没有完全理解**」。所以这里用最直白的方式重答一次，**不绕弯**。

### 答案：**思路对，载体错。一半合理，一半不合理。**

| 你的想法 | 判定 | 一句话理由 |
|----------|------|-----------|
| ① 把「取值来源」抽象成**独立、可插拔的实现单元** | ✅ **合理，必须做** | 这就是策略模式，开闭原则 |
| ② 新增来源 = **加一个单元 + 补它的参数** | ✅ **合理** | 不改调用方 |
| ③ 这个单元叫 **"Skill"** | ⛔ **不合理** | 在本项目里，**Skill ≠ 可复用代码**，Skill = **工作流画布上的一个节点类型** |
| ④ 来源单元之间可以**组合 / 编排** | ⚠️ **一期不做** | 一编排就是第二套工作流（而那条路 `wf_workflow_definition` 已 0 行） |

### 为什么 ③ 不合理：Skill 有**三条硬绑定**

| # | 硬绑定 | 出处 |
|---|--------|------|
| 1 | **必须登记在数据库** `wf_skill_reflection`（`ClassPath` + `MethodName`），不登记就调不到 | `Skill清单-V1.md` §1.1「登记即用」 |
| 2 | **每个参数必须声明绑定模式** `Link`（必须连上游节点）/ `LinkOrConstant` / `Enum`（选字典） | `Skills/SkillAttributes.cs:49-59` |
| 3 | **前端会把它渲染成画布上的方块** | `SkillPanel` / `specialNodes.ts` |

⇒ **「一个来源一个 Skill」= 「一个来源一个画布方块」。**

### 一句话判据

> **Skill 是给"人要在画布上摆、要连线"的东西用的。填充取值，没有人会在画布上摆。**

### 那正确的东西叫什么：**Resolver（解析器）**

```csharp
public interface IValueResolver
{
    string Kind { get; }                                   // "global" / "ai" / "profile" ...
    Task<ResolveResult> ResolveAsync(ResolveContext ctx, SourceSpecEntry src, CancellationToken ct);
}

[ValueResolver("global", Name = "全局参数")]
public sealed class GlobalParamResolver : IValueResolver { /* 读 cert_fill_param_value */ }
```

### 两者对比（**这是理解的关键**）

| | **Skill**（画布节点） | **Resolver**（解析器） |
|---|---|---|
| 注册方式 | 数据库 `wf_skill_reflection` 登记 | DI 扫描 + 特性 |
| 参数 | 每个参数声明 `BindMode` | 普通方法参数 |
| 前端 | **渲染成画布方块** | **前端根本不知道它存在** |
| 谁调用 | **工作流引擎** | **填充引擎** |
| 适合什么 | 人要在画布上摆的东西 | 引擎内部的策略 |
| 新增一个要动几处 | 类 + 数据库登记 + 画布绑定声明 | **只加一个类 + 一个特性** |

⇒ **功能上一模一样**（都是"可插拔的取值实现"），**差别只在"要不要在画布上摆"。**

### 所以你的 Skill 直觉**没错**，只是**放错了层**

用 `22` §13.6 的判据（①低频 ②重 ③需人工编排 ④需留痕，**≥3 条命中才做 Skill**）：

| 场景 | 命中数 | 该用什么 |
|------|--------|---------|
| **填充取值**（层 1 单元级） | **0 / 4** | ✅ **Resolver** |
| **全局填写规则**（层 2 文档级） | **3~4 / 4**（低频·重·调 LLM·需留痕） | ✅ **可以做成 Skill**（`build_nc_prompt` 就是先例） |
| **模板扫描 / 分类识别 / 生成提示词**（定义期） | **4 / 4** | ✅ **Skill** |

⇒ **一句话收口**：
> **「简单取值」用 Resolver；「一次重活」用 Skill。** 你把简单取值当重活做了。

## 二、★ 你的核心补充成立：**两层规则**

```
层 2 · 文档级（编排）  ── 全局填写规则（本篇）
        │  引字段 + 引 Skill + 组合提示词  →  一次产出 {FieldCode: 值}

```

**为什么必须分两层：**

| | 层 1 单元级 | 层 2 文档级 |
|---|---|---|
| 表达方式 | **声明式**（属性配置） | **装配式**（组合提示词） |
| 覆盖场景 | 确定性的单点取值 | 需要**跨字段推理**、需要**从多份文档组织**的内容 |
| 单位成本 | 每个锚点配一次 | **每个模板只配一次** |
| 是否必填 | ⛔ **不是**（你说的对） | ✅ 每模板一条（可留空） |

**你说的「每个填写单元不是一定要设置填写规则」是对的** —— 但**必须补一条隐式规则**，否则值回不来：

## 四、全局参数：按你的定义**重做**

### 4.1 你说的「不是我们系统的全局参数」，我理解是这个意思

| | 我上一版设计的（`22` §七） | 你现在要的 |
|---|---|---|
| 来源 | **全部从已有表自动取**（`cert_enterprise` 等） | **用户在界面上人工维护** |
| 载体 | 物化快照表（用户看不见） | **要一个新菜单，用户能填能改** |
| 粒度 | 企业 × 阶段 × 标准 | **企业 × 阶段** |
| 性质 | 系统内部机制 | **平台常用固定信息字典** |

⇒ **两者不冲突，是两层。** 需要合并成一张表 + 一个 `MaintainMode` 开关。

### 4.2 两层参数

| 层 | 名称 | 谁产生值 | 例子 |
|----|------|---------|------|
| **A** | **自动映射层** | 从已有表实时映射后**物化** | 企业名称、统一社会信用代码、法定代表人、注册地址、认证范围、机构名称、CNAS 编号、标准名称、阶段名称 |
| **B** | **人工维护层** | 用户在**新菜单**里填 | 认证日期、证书编号、审核组长、审核组成员、现场审核日期、覆盖场所数、体系覆盖人数 |

**`MaintainMode` 三值**：

| 值 | 行为 | 界面表现 |
|----|------|---------|
| `auto` | 只从源表取，⛔ 不可改 | 只读展示 |
| `manual` | 只能人工填 | 可编辑 |
| `both` | 自动取初值，**允许人工覆盖** | 可编辑，有「恢复自动值」按钮 |

**⛔ 铁律**：`both` 型参数一旦被人工改过，`ValueSource = manual`，此后**连重新同步源表都不覆盖**（与 `21`/`22` 号的 `*Source` 规则一致）。

### 4.3 表结构（对 `22` §7.4 的增补）

```sql
-- 参数定义表：增补 MaintainMode
ALTER TABLE `cert_fill_param_def`
  ADD COLUMN `MaintainMode`  varchar(20) NOT NULL DEFAULT 'auto'
      COMMENT 'auto=只读源表 / manual=仅人工 / both=自动初值+可覆盖',
  ADD COLUMN `GroupName`     varchar(50) DEFAULT NULL
      COMMENT '界面分组（企业信息 / 认证信息 / 审核信息）',
  ADD COLUMN `ShowInMenu`    tinyint(1)  NOT NULL DEFAULT 1
      COMMENT '是否在维护菜单显示（⛔ 0 = 内部参数，用户不可见）';

-- 参数值表：增补人工维护痕迹（22 §7.4 已有 ValueSource，此处明确语义）
ALTER TABLE `cert_fill_param_value`
  MODIFY COLUMN `ValueSource` varchar(20) NOT NULL DEFAULT 'auto'
      COMMENT 'auto=自动映射 / manual=人工改过（⛔ 永不自动覆盖） / fallback=源缺失降级';
```

### 4.4 维护入口

- **主入口**：新菜单「企业认证信息」→ 选企业 → 按**阶段**分组展示参数 → 编辑
- **副入口**（建议同时提供）：审核员端 · **企业管理 · 企业详情** 内嵌同一组件（省一次"先选企业"）
- ⚠️ 与 `22` §7.4 的 `SourceExpr` 配合：`SourceExpr IS NULL` 且 `MaintainMode = manual` ⇒ **菜单里必须填**，否则填充时静默留空

> ⚠️ **实测提醒**：「认证日期」当前**无数据源**（`22` §7.3），所以它必然是 `manual` 型。这类"看起来该自动、实际只能人工"的参数，**必须在定义表里显式标出来**，否则维护人员会以为是 bug。

### 4.5 ★★ 参数必须按「标准 × 阶段」裁剪（**2026-10-02 用户补充**）

> **用户原话**：「一个标准下，不同阶段是不是能提取的全局参数是不一样的，有些信息只能在某个阶段才填写，**并不是所有标准都适用一套全局参数**，这个决定了我们体系认证全局参数的定义规则。」

**判定：✅ 完全成立，而且这是参数设计的**定义级约束**，不是细节。**

#### 4.5.1 为什么成立（业务事实）

以 ISO9001 认证流程为例，参数是**随阶段产生的**，不是一开始就齐的：

| 阶段 | 该阶段才有的参数 |
|------|-----------------|
| 申请 | 申请编号、申请日期、申请范围 |
| 合同评审 | 合同编号、签订日期、合同金额 |
| 方案策划 | 审核方案、审核范围、审核人日 |
| 一阶段审核 | 一阶段审核日期、一阶段审核员 |
| 二阶段审核 | 二阶段审核日期、**审核组长**、审核组成员 |
| 整改 | 不符合项数量、关闭日期 |
| 认证决定 | 认证决定日期、**证书编号**、证书有效期 |
| 监督 | 监督审核日期、监督结论 |
| 再认证 | 再认证日期 |

⇒ 在**一阶段**填文档时，「证书编号」**取不到值** —— 但这**不是缺失**，是**还没到**。

⇒ **⛔ 必须新增一个失败语义**（`22` §八 的 `onMissing` 不够用）：

| 语义 | 码 | 行为 |
|------|----|------|
| **未到阶段** | `notYet` | **留空，静默跳过，⛔ 不算缺失、⛔ 不告警、⛔ 不挂待办** |
| 已到阶段但源缺失 | `missing` | 按 `onMissing` 处理（`block`/`next`/`todo`/`empty`） |

⇒ **把「未到阶段」当成「缺失」，会产生大量假告警** —— 这是本设计最容易踩的一个坑。

#### 4.5.2 ★ 落点：项目已有现成的「标准 × 阶段」锚点

| 表 | 作用 | 实测 |
|----|------|------|
| `cert_standard_directory_config` | **机构 × 企业 × 标准(GUID) × 阶段(GUID) → 目录根** | 列齐全 |
| `cert_standard_directory_file.ConfigCode` | 每份标准文档 → 指向上面那行 | ✅ |

⇒ **填充某份文档时，「标准 × 阶段」上下文是现成的**：`file.ConfigCode` → `config.StandardCode` + `config.StageCode`。
⇒ **不需要新造维度，也不需要让用户手选阶段。**

#### 4.5.3 ⛔ 但有一个前提没满足：**阶段没有序号**

实测 `cert_cert_stage`（**只有 3 行**）：

| StageCode | StageName | Category | SortOrder |
|-----------|-----------|----------|-----------|
| `jd01` | 初审 | process | **0** |
| `jd02` | 预审 | process | **0** |
| `03` | 复审 | process | **0** |

- ⚠️ 列注释写的是「如 `AP/CR/SP/S1/S2/CD/CE/SV/RC`」「排序号 1~9」—— **注释与数据不符**
- ⛔ **`SortOrder` 全为 0 ⇒ 无法做"阶段先后"比较**

⇒ **直接后果**：`StageFrom` / `StageTo`（阶段区间，"某阶段之后才可用"）**做不了**。

#### 4.5.4 ✅ 因此：一期用**枚举式**，不用区间式

在 `cert_fill_param_def` 上增补两列（**不建范围表**）：

```sql
ALTER TABLE `cert_fill_param_def`
  ADD COLUMN `StandardScope` json DEFAULT NULL
      COMMENT '适用标准 Code 数组，NULL/空=全部标准适用',
  ADD COLUMN `StageScope`    json DEFAULT NULL
      COMMENT '适用阶段 Code 数组（cert_cert_stage.Code），NULL/空=全部阶段适用';
```

**取值规则**：

```
可用参数 = 参数池
         ∩ (StandardScope 为空 或 含 当前 StandardCode)
         ∩ (StageScope   为空 或 含 当前 StageCode)
```

**为什么用枚举而非区间**：

| 方案 | 依赖 | 一期可行？ |
|------|------|-----------|
| `StageFrom` / `StageTo`（区间） | `cert_cert_stage.SortOrder` 有序 | ⛔ **不可行**（全 0） |
| `StageScope`（枚举数组） | 只要 `StageCode` 有值 | ✅ **可行** |

⇒ **保留扩展口**：等阶段清单正经维护、`SortOrder` 补上 1~9 后，再加区间列（**届时是加法，不是改造**）。

### 4.6 ★★ 企业基础信息 vs 全局参数：**不重复**（2026-10-02 用户提出）

> **用户原话**：「我们企业的基础信息其实和全局参数很多信息是重复的，如何解决……我还是没有更好的思路」

**根因**：`22` §7.4 的 `cert_fill_param_value` **多存了一份自动值** ⇒ 和 `cert_enterprise` 撞车。

**✅ 解法：按 `MaintainMode` 分流，参数表只存「人工覆盖」**

| 参数类型 | 值存在哪 | 参数表里有行吗 |
|----------|---------|---------------|
| `auto`（企业名称、信用代码、地址…） | **只在源表** | ⛔ **没有行** |
| `manual`（认证日期、证书编号…） | **只在参数表** | ✅ 有行 |
| `both`（自动初值 + 可覆盖） | 没被改 → 只在源表；**被改过** → 参数表 | ✅ **只在被改过时** |

**★ 语义约定**：

> **`cert_fill_param_value` 里"没有行" = "用源表的自动值"；"有行" = "用户覆盖了它"。**

⇒ 自动值**根本不进这张表** ⇒ **重复消失**。

**物化快照改落在「填充结果」**（不是参数表）：填充时读源表 + 读覆盖值 → 合成运行期字典 → 填充后把**本次用到的每个值**写入填充结果表（含 `ValueSource` 与取值时间）。

⇒ 三处职责彻底分开：

| 位置 | 职责 | 会不会变 |
|------|------|---------|
| `cert_enterprise` 等源表 | **唯一权威** | 企业改名就变 |
| `cert_fill_param_value` | **只存人工覆盖** | 用户改才变 |
| 填充结果表 | **本次用了什么值的证据** | ⛔ **永不改变**（审计依据） |

**⛔ 配套铁律**：参数菜单里 `MaintainMode = auto` 的参数**只读展示 + 跳转企业管理**，⛔ **不提供编辑**（否则又变两处可写）。
> 与 `20` 号 Q-3「源语义只读 + 跳转」同一原则：**同一语义只能有一处可写。**

> 📎 **完整论证见** [`24-生产可行性与准确性提升路径-V1.md`](./24-生产可行性与准确性提升路径-V1.md) §一。

### 5.3 装配器接口（照抄 `NcPromptAssembler` 的形状）

```csharp
/// <summary>★ 文档填写 Prompt 装配器（服务端组装，★ 不依赖引擎改造）</summary>
public class DocFillPromptAssembler
{
    /// <param name="template">cert_doc_fill_prompt 取出的模板</param>
    /// <param name="anchors">本模板锚点清单（决定要填哪些字段/表格）</param>
    /// <param name="globals">全局参数快照（企业×阶段）</param>
    /// <param name="profile">企业资料画像结果（可选）</param>
    public static (string SystemPrompt, string UserTemplate) BuildFillPrompt(
        DocFillPrompt template,
        IReadOnlyList<AnchorSpec> anchors,
        IReadOnlyDictionary<string, string> globals,
        string? profile)
    {
        var user = template.UserTemplate
            .Replace("{{__FILL__.fields}}",  BuildFieldList(anchors))     // 要填的标量字段
            .Replace("{{__FILL__.tables}}",  BuildTableList(anchors))     // 要填的表格区域
            .Replace("{{__FILL__.globals}}", BuildGlobalList(globals))    // 已确定的全局参数
            .Replace("{{__FILL__.profile}}", Safe(profile));              // 企业资料画像

        return (template.SystemPrompt ?? string.Empty, user);
    }

    /// <summary>★ 复用 NC 的漏填检测（同一套正则约定）</summary>
    public static List<string> FindUnresolvedPlaceholders(string? text) => ...;
}
```

### 5.4 ★★ 四条铁律（**这是压住复杂度的关键**）

你说「全局填写规则可能会比较复杂」—— **复杂度可以压住，前提是守住这 4 条：**

| # | 铁律 | 违反后果 |
|---|------|---------|
| **1** | **⛔ 不做分支、不做循环、不做并行** —— 全局规则只做「**顺序拼装 + 一次 LLM 调用**」 | 一旦有分支 ⇒ 你就在**重造工作流**，而工作流这条路 `wf_workflow_definition` 已经 0 行 |
| **2** | **⛔ 不写"怎么填"以外的逻辑** —— 取值逻辑留在层 1 的 `SourceSpec` | 规则里开始出现"如果企业没上传执照则…" ⇒ 复杂度失控 |
| **3** | **✅ 输出必须是结构化 JSON**（`{FieldCode: value}`），并**按 `FieldCode` 回填** | 自由文本 ⇒ 无法回填 ⇒ 只能人工复制粘贴 |
| **4** | **✅ 复用 `{{__FILL__.*}}` 占位符 + 漏填检测** | 自造一套 ⇒ 与 NC 双轨，维护成本翻倍 |

> **一句话**：全局填写规则 = **一个提示词模板 + 一个装配器 + 一次 LLM 调用**。就这三样。
> 它**不是引擎**，**不是画布**，**不是第二套工作流**。

### 5.5 「引 Skill」怎么落

你说的「引入我们的 Skill 来组合我们的提示词规则」—— 落在**装配器的输入侧**，而不是规则内部：

```
全局参数快照 ─┐
企业资料画像 ─┤
锚点清单    ─┼→ DocFillPromptAssembler → 一条完整 Prompt → LLM → {FieldCode: 值}
上游 Skill  ─┘   （如 get_field / get_table / is_* 的输出，与 NC 一致）
```

⇒ **Skill 提供"素材"，装配器负责"拼装"，LLM 负责"生成"。** 三者职责不重叠。
⇒ ⚠️ 但**一期不要做 Skill 编排**（会退化成工作流）。**先只接"全局参数 + 锚点清单"两个输入**，跑通再扩。

## 六、两层如何协作（填充流程）

```
① 加载模板 + 锚点清单（cert_doc_template / _anchor）
② 加载/生成全局参数快照（cert_fill_param_value，企业×阶段）   ← ★ 物化，不实时查
③ 跑全局填写规则（若有 FillPromptCode）
      DocFillPromptAssembler → Prompt → LLM → {FieldCode: 值}   ← ★ 每模板一次
④ 锚点依赖拓扑排序（self 引用 → 有环则拒绝）
⑤ 逐锚点解析 SourceSpec（有序回退）
      · global  → 从 ② 取
      · ai      → 从 ③ 的字典取（★ 这就是"没配单元规则"的锚点的隐式来源）
      · profile → 从企业资料画像取（置信度不足视为未命中）
      · compute → 计算
      · manual  → 先看 ③ 有没有值 → 有就用，没有挂待办
⑥ 按 WriteMode 写回（★ 一次打开 / 一次保存）
⑦ 残留校验：{{XXX}} 残留 + YZH_Mark 残留 → 报"未填充项"
```

**★ 步骤 ③ 与 ⑤ 的顺序不能颠倒** —— 全局规则是**批量供给**，单元级是**逐点解析**。先供给，再解析。

**★ 二次填充（重传/重跑）的规则**：

| 情况 | 行为 |
|------|------|
| `ValueSource = manual` 的锚点 | ⛔ **跳过，不覆盖** |
| `SourceSha256` 未变 | ⛔ **整轮跳过** |
| 锚点 `IsOrphan = 1` | 保留其已填值，不参与本轮 |

## 七、⚠️ 页眉页脚：你说「不存在不同格式造成 Skill 不适用」——**这条要修正**

你的判断**方向对**（页眉页脚是我们定义的，格式可控），**但结论过头了**。

**格式问题不是消失了，是从"排版"转移到了"域代码 + 分节"：**

| 坑 | 说明 | 后果 |
|----|------|------|
| **Word 域代码** | 页眉里的 `{ PAGE }` / `{ NUMPAGES }` / `{ DATE }` 是 **field code**，不是普通文本 | ⛔ **整段 setText 会抹掉域代码**，页码变死数字 |
| **首页不同 / 奇偶页不同** | `HeaderKind` = `default` / `first` / `even` | 同一份文档**最多 3 套页眉**，锚点必须带 `HeaderKind` |
| **分节** | `SectionIndex` —— 不同 section 可以有不同页眉 | 锚点必须带 `SectionIndex` |
| **跨 run 拆分（W9）** | Word 会把 `{{ENT_NAME}}` 拆成多个 `<w:r>` | 扫描器与写入器**都要做 run 归一化** |

⇒ **页眉页脚不是"最安全"的形态，而是"坑最集中"的形态。** 建议**一期只做 `domain(text)` 类型**（写企业名称等），`domain(auto)`（`PAGE`/`NUMPAGES`）**只登记不写值**（`22` §5.2 已定）。
