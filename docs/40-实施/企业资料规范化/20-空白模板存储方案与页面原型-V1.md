# 空白模板 — 存储方案与后台页面原型

> **版本**：V1 | **日期**：2026-10-02 | **状态**：待裁决（3 条）
> **本轮输入**：用户补充——「空白文档的路径和标准文档都在**同一个目录**，方便设置时下载标准文档、上传定义好的空白文档，两个文档所处的**文件夹是一样的**」
> **结论一句话**：**「同目录」这个诉求是对的，而且实测数据支持它；但「同名 + `|blank` 后缀 + 覆盖」必须换掉**——168 份标准文档里 **154 份是老格式 `.doc`/`.xls`**，你下载改完必然存成 `.docx`/`.xlsx`，**「同名」这个前提在数据上就不成立**。

---

## 〇、结论速览

| 你的想法 | 判定 | 处置 |
|----------|------|------|
| 空白模板与标准文档**放同一个文件夹** | ✅ **采纳** | 用 `_template/` **子目录**（与项目已有 `pdf/`、`markdown/` 产物段**同模式**） |
| 上传时**自动加 `\|blank` 后缀**区分 | ⛔ **换掉** | `\|` 是 Windows 非法字符；且用文件名承载语义违反项目纪律 |
| 同名**自动更名并覆盖**空白模板 | ⛔ **换掉** | ① 实测 `.doc`→`.docx` 文件名必变，同名不成立；② 与已定设计冲突（`TemplateVersion`+`IsLatest`）；③ 模板换版要保留历史 |
| 页面里**下载标准文档 → 改 → 上传** | ✅ **采纳** | 这是正确的操作闭环 |
| 打开模板**点分析** → 分类看字段/表格 | ✅ **采纳** | 即「锚点扫描」，**零 LLM**（与现有「开始分析」本质不同） |
| 针对字段/表格**定义填写语义** | ⚠️ **需拆分** | 拆成「值从哪来」（→字段定义，共用）与「怎么写」（→锚点，模板独有），**否则会造出第二套字段定义** |
| 把**分类/作用**也生成在模板上 | ⛔ **不建议** | 分类/作用属**契约**（标准文档的属性）；模板可有多个版本，放模板上会互相打架 |

## 一、数据实测（决定了方案必须怎么改）

### 1.1 标准文档的真实格式分布

| `FileType` | 数量 | 占比 |
|------------|------|------|
| **`.doc`**（老格式） | **143** | 85.1% |
| `.xls`（老格式） | 11 | 6.5% |
| `.docx` | 8 | 4.8% |
| `.xlsx` | 5 | 3.0% |
| `.txt` | 1 | 0.6% |
| **合计** | **168** | |

> **154 / 168 = 91.7% 是老格式**。

**推论（这条直接否定了「同名覆盖」）**：
1. 你下载的是 `风险管理报告.doc`
2. 本地用 Word 打开 → **另存为 `.docx`** → 加 `{{}}` 标签、书签、`YZH_Mark` 样式
3. 上传的是 `风险管理报告.docx`

**文件名和扩展名都变了。**「同名 + 后缀」这套从第一步就走不通。

**但反过来看，这恰好支持你的「同目录」直觉**：下载与上传在同一个文件夹，操作闭环最短。

### 1.2 可下载性

168 个模板行 **100% 有 `StoragePath`** → **全部可下载** ✅。

### 1.3 实测路径样例（暴露一个历史问题）

```
/standard-directory/906e8b2a962c4062b21144af4cc4abc0/846dec4b-c534-4983-94e6-8cf04982b7d9/29c1bcc3a18942e1865b2497a0262504/CS河北雄安尚龙医疗科技有限公司13485体系材料/4记录文件/风险管理报告.doc
                    ↑ 机构段：GUID 的 - 被删掉了（历史 CleanCode bug）        ↑ 标准段：- 保留了
```

**注意机构段**：`906e8b2a962c4062b21144af4cc4abc0` —— **`-` 被删了**；而标准段 `846dec4b-c534-…` 保留了。
这正是 `PathBuilder` 头注释里写的那个历史 bug（`CleanCode` 删 `-` ⇒ 路径段与 DB 值**不可逆不一致**）。

> **对本方案的影响**：新建模板路径**必须走 `PathBuilder`**（`⛔ 除本类外任何地方不得手工拼接存储路径`），且**身份段取 `Code` 原文、不 CleanCode**。否则新老数据会出现两套格式，重演「1182 个对象只有 177 个被引用」的局面。

### 1.4 与已定设计的冲突（决定性）

`16-模板标注与Skill流程化方案-V2` §9.1 已定义 `cert_doc_template_scan`：

| 列 | 已定语义 |
|----|----------|
| `StandardFileCode` | 模板宿主 → `cert_standard_directory_file.Code`（`YZH-STD-ENT` 侧） |
| `TemplateVersion` | **模板版本（换模板递增）** |
| `IsLatest` | 是否最新版本 |
| `FileKind` | `docx` / `xlsx` |
| `SourcePath` | **本次扫描所用模板存储路径** |
| `SourceSha256` | 模板指纹：**同 sha 不重扫** |
| `uk_file_version` | `(StandardFileCode, TemplateVersion)` |

**已定设计明确是「新增版本行 + 翻转 `IsLatest`」，不是覆盖。** 你要的「自动更名并覆盖」会：
- 废掉 `TemplateVersion` / `IsLatest` / `uk_file_version` 三个已定对象
- **丢失模板历史** —— 而模板恰恰最需要历史：换版后要「重扫 + 差异继承」（`16` §11），旧版留着才能 diff
- 让 `SourceSha256` 的「同 sha 不重扫」优化失效（覆盖后 sha 变了，但业务上其实没变）

## 二、存储方案（采纳「同目录」，换掉「同名后缀」）

### 2.1 目录结构

```
/standard-directory/{OrgCode}/{StandardCode}/{StageCode}/{FolderPath}/
    ├── 风险管理报告.doc              ← 标准文档（有内容，企业参照 + 你下载的底稿）
    ├── 4记录文件/…
    ├── pdf/                          ← 已有：预览产物
    ├── markdown/                     ← 已有：提取产物
    └── _template/                    ← ★ 新增：空白模板
          ├── 风险管理报告.docx        ← 当前版本（带 {{}} 标签 + 书签 + YZH_Mark）
          └── _archive/
                └── 风险管理报告.docx.v1   ← 换版归档（复用现有 Archive()）
```

**为什么用 `_template/` 子目录而不是「同名 + 后缀」：**

| 理由 | 说明 |
|------|------|
| **与项目已有先例同模式** | `pdf/`、`markdown/` 就是「源文件同级 + 产物类型段」——`_template/` 是**第 4 个同类段**，一致性最好 |
| **不撞唯一键** | `uk_cfg_fullpath(ConfigCode, FullPath)` 按 `FullPath` 判重；子目录让 `FullPath` 天然不同 |
| **人工浏览清晰** | MinIO 控制台按 `/` 分组显示，一眼能分出「标准文档」和「模板」 |
| **`|` 是非法字符** | Windows 文件名禁用 `\ / : * ? " < > |`；`PathBuilder.Sanitize` **只去 `/` 和 `\`**，`|` 会原样进路径 → URL 编码后难排查，下载到 Windows 会出问题 |
| **不靠文件名承载语义** | 文件名是**展示物**，语义应由**字段**承载（项目纪律） |

### 2.2 需要改动的三处基础设施（都很小）

| # | 位置 | 改动 |
|---|------|------|
| ① | `PathBuilder.cs` | 新增 `TemplateFile(orgCode, standardCode, stageCode, folderPath, fileName)` —— 内部复用 `StandardFile()` 再插 `_template` 段 |
| ② | `PathBuilder.ReservedSegments` | 加 `_template`（与 `pdf`/`markdown`/`_archive` 并列，防止业务文件夹撞名） |
| ③ | `PathBuilder` | 加 `IsTemplatePath(path)`（对标已有的 `IsProductPath` / `IsArchivePath`），供清理与列举时区分 |

**✅ 不需要改的**（这是「同目录」方案的最大好处）：
- `DocumentLibrary` 枚举 —— 路径仍在 `standard-directory/` 下，`Resolve()` 照样返回 `StandardDirectory`
- 白名单校验 `IsAllowedStoragePath()` —— 不变
- 格式转换链（`OfficeConvertService` / `file_convert` 队列）—— **零改动**，它按路径处理，不关心归属表
- 预览链 / Markdown 链 —— 零改动

> 归档**直接复用**已有的 `PathBuilder.Archive()`：
> `Archive("/…/4记录文件/_template/风险管理报告.docx", 1)` → `/…/4记录文件/_template/_archive/风险管理报告.docx.v1` ✅

### 2.3 数据模型

**新建 `cert_doc_template`（模板主表）** —— 模板的「上传 / 替换 / 发布」是独立动作，必须有地方记；否则「上传了但没扫描」这个中间态无处安放。

```sql
CREATE TABLE `cert_doc_template` (
  `Id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `Code` varchar(36) NOT NULL COMMENT '业务键GUID',
  `CreateTime` datetime NOT NULL COMMENT '上传时间',
  `CreateBy` varchar(64) DEFAULT NULL,
  `UpdateTime` datetime DEFAULT NULL,
  `UpdateBy` varchar(64) DEFAULT NULL,
  `StandardFileCode` varchar(36) NOT NULL COMMENT '宿主标准文档 → cert_standard_directory_file.Code',
  `OrgCode` varchar(36) NOT NULL DEFAULT '' COMMENT '冗余：机构',
  `StandardCode` varchar(36) NOT NULL DEFAULT '' COMMENT '冗余：标准',
  `StageCode` varchar(36) NOT NULL DEFAULT '' COMMENT '冗余：阶段',
  `TemplateVersion` int NOT NULL DEFAULT '1' COMMENT '模板版本（换版递增，不覆盖）',
  `IsLatest` bit(1) NOT NULL DEFAULT b'1' COMMENT '是否最新版本',
  `FileKind` varchar(10) NOT NULL COMMENT 'docx / xlsx',
  `FileName` varchar(500) NOT NULL COMMENT '上传时原始文件名（.doc 改存 .docx 后）',
  `StoragePath` varchar(512) NOT NULL COMMENT '模板存储路径（PathBuilder.TemplateFile 产出）',
  `SourceSha256` varchar(64) DEFAULT NULL COMMENT '模板指纹：同 sha 不重扫',
  `PublishStatus` varchar(20) NOT NULL DEFAULT 'draft'
      COMMENT 'draft=已上传未扫描 / scanned=已扫描待处理 / ready=校验通过待发布 / published=已发布 / archived=已归档',
  `Remark` varchar(500) DEFAULT NULL,
  `IsDeleted` tinyint(1) NOT NULL DEFAULT '0',
  `DeleteBy` varchar(64) DEFAULT NULL,
  `DeleteTime` datetime DEFAULT NULL,
  `IsValid` int NOT NULL DEFAULT '1',
  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_code` (`Code`),
  UNIQUE KEY `uk_file_version` (`StandardFileCode`,`TemplateVersion`),
  KEY `idx_file_latest` (`StandardFileCode`,`IsLatest`),
  KEY `idx_sha` (`SourceSha256`),
  KEY `idx_publish` (`PublishStatus`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='标准文档空白模板（模板包）';
```

**对 `16` 册 §9.1 的一处修订**：`cert_doc_template_scan` 的 `StandardFileCode` + `TemplateVersion` → 改为 **`TemplateCode`**（→ `cert_doc_template.Code`），扫描结果挂模板行而非标准文件行。
> `16` 册这 4 张表**尚未建**（实连库 0 命中），改动成本 **0**。

**⛔ 不往 `cert_standard_directory_file` 加行** —— 理由：这行会被目录树、企业侧列表、`IsRequired`/`FilePattern`/统计口径全部扫到，漏一处过滤就出静默 bug（`06` 册 B1「模板查询恒空」是同类教训）。**模板独立表，目录树天然干净。**

## 四、⚠️ 一处必须拆开的语义（否则会造出第二套字段定义）

你说「针对字段和表格，定义**如何填写的语义**」。这里实际有**两层**，必须分开落表：

| 层 | 问题 | 例子 | 归属 |
|----|------|------|------|
| **层 1：写在哪** | 这个锚点对应哪个字段 | `{{ENT_NAME}}` → `ENT_NAME` | **锚点**（`cert_doc_template_part.FieldCode`）—— **扫描器自动得到，不需要 AI** |
| **层 2：值从哪来** | 这个字段的值来自哪里 | `ENT_NAME` 来自**全局参数**；`TRAIN_TOPIC` 来自**企业文档提取**；`SUM_ROWS` 是**计算** | **字段定义**（`cert_doc_field_def`）—— **读写两侧共用** |
| **层 3：怎么写** | 写入格式、空值兜底 | `fmt:0.00` / `def:—` | **锚点**（`TokenModifiersJson` / `DefaultText`）—— 模板独有 |

### 关键建议

> **右栏的「来源语义」应当是「只读展示 + 一键跳转到字段定义编辑」，不是在这里重新定义。**

理由：提取规则说「我要从企业文档**抽出** `ENT_NAME`」，生成规则说「我要把 `ENT_NAME` **填进** `{{ENT_NAME}}`」——**这是同一个 `FieldCode` 的读写两面**。如果在模板页再定义一遍「来源」，就会出现两套字段定义，然后要写映射，然后映射失配。

**AI 的正确介入点**：只在**首次扫描完成后给一次「来源建议初稿」**（例如「`ENT_NAME` 建议走全局参数，因为它在 6 个模板里都出现」），人工可改。**层 1 的绑定不需要 AI** —— 扫描器读 `{{}}` 里的名字就是 `FieldCode`，AI 介入只会猜错。

### 同理：分类 / 作用不该生成在模板上

- **分类（`DocCategory`）/ 作用（`DocPurpose`）是标准文档的属性**，属**契约**（`cert_standard_doc_contract`）
- 一个标准文档 → **一个契约**，但可以有**多个模板**（Word 版 + Excel 版 + 多个版本）
- 放模板上 ⇒ 同一标准文档的两个模板版本「分类不一致」，无处仲裁

**模板页只读展示**（从契约带出来），编辑入口在契约页。

```text
         └ 出口：三件事有实测结论，再动手写扫描器

第 3 步  扫描服务 + 锚点表 + 校验（红黄牌）
第 4 步  页面（三栏 + 操作条 + 锚点清单 + 校验结果）
第 5 步  填充执行器（NPOI 落笔）—— 属 16 册 P1，本册不做
```

> **与 10/15 死线的关系**：第 1 步很小（半天到一天），但**建议排在 10/15 之后**——它不服务「登录→建档→上传→提取→报告」这条关键路径。
