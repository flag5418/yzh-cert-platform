## 1. 需求本质与精确化

### 1.1 用户原始诉求

> 把企业散乱的资料，整理成体系认证标准目录中的标准文档格式。

原始思路四步：

1. 按**固定文档**（营业执照、许可证等国家固定格式扫描件）先识别分类，剩下的交 AI 组织编辑；
2. 对剩余文档一次性做**字段提取、表格提取、功能作用提取**；
3. 针对每个标准文档，用 AI 与企业文档做语义匹配，生成**可信度列表**，大于 50% 的做字段/表格内容匹配，成功则自动填写，多文件命中则形成人工判断依据；
4. **人工干预**决定标准文档 ↔ 企业文档的对应关系，再据此自动填充；并允许用户指定某些企业文档或文件夹做定向匹配。

### 1.2 精确化的功能定义

本模块 = **标准文档实例化引擎**，由三个子问题构成：

| 子问题 | 输入 | 输出 | 承载分册 |
|--------|------|------|----------|
| **Q1 识别**：这份企业文档是什么？ | 单个企业文件（含 Markdown 产物） | 文档画像：类别（固定/可编辑）、作用、字段、表格、指纹 | 06、04-§2 |
| **Q2 匹配**：它对应哪份标准文档？ | 文档画像集合 + 标准文档契约集合 | 候选列表 + 可信度 + 证据 | 04 |
| **Q3 填充**：如何生成标准文档实例？ | 裁决后的字段/表格值 + 契约定义 | 标准文档实例（docx/xlsx），带溯源 | 05、07 |

三个子问题必须**解耦**：识别可独立重跑、匹配可独立重算、填充可独立重做；任何一步的人工修正都不得被后续自动重跑覆盖。

### 1.3 价值

- 企业侧：资料收集从「按模板整理后上传」变为「随意上传，系统归位」；
- 平台侧：产出的字段/表格值直接喂给 NC 检查、报告生成（Phase3 §4.4 数据消费）；
- 合规侧：每一条填入标准文档的数据都可回溯到「哪个企业文件、哪个位置、谁确认的」。

## 5. 核心枢纽与两条提取链

### 5.1 枢纽字段 `StandardFileCode`

Phase3 已确立（`Phase3-标准文件code枢纽改造设计-V1.md`）：

> 标准文件定义了「应该提取什么」，企业文件产生了「实际提取了什么」，`standard_file_code` 让两者通过同一个 code 关联。

本模块的三处用法：

| 用法 | 字段位置 | 语义 |
|------|----------|------|
| 匹配目标 | `cert_doc_match_candidate.StandardFileCode` | 这个候选指向哪份标准文档 |
| 裁决回填 | `cert_standard_directory_file.StandardFileCode`（**企业行**上） | 人工确认后，企业文件被钉到该标准文档（**同一标准内一对一；跨标准可一对多**，见 15 号 R-15） |
| 消费桥接 | `cert_extraction_result.StandardFileCode`（已有） | 填充时按此取字段定义与提取结果 |

⚠️ 注意：Phase3 写的是 `→ cert_file_requirement.code`，但 2026-09-26 重建后规则键已指向 `cert_standard_directory_file.Code`（`DocExtractionRule.StandardFileCode` 实测口径）。**本模块统一以 `cert_standard_directory_file.Code` 为准**，Phase3 §2.3 的 `cert_file_requirement` 行需随本模块实施时一并勘误。

### 5.2 两条提取链的分离（决策 D3）

| | **画像链（新增）** | **定向链（已有）** |
|---|---|---|
| 触发 | 企业文件上传/转换完成即触发，**一次性** | 匹配裁决完成后，或规则配置试运行 |
| 规则 | **无规则**——对文档内容做开放式理解 | 有规则——`cert_doc_extraction_rule` 按 `StandardFileCode` 取 |
| 产出 | `cert_ent_doc_profile`（作用/类别/指纹）+ 字段/表格（**存储形态待 Q-01**） | `cert_extraction_result` / `cert_table_extraction_result` |
| 目的 | 回答「这是什么文档」→ 服务**匹配** | 回答「该标准字段值是多少」→ 服务**填充** |
| 可信度 | 画像级 + 字段级 | 字段级（已有 `Confidence`） |
| 是否覆盖裁决 | 可重跑（画像是事实描述） | **不得覆盖**人工裁决与人工修正值 |

**为什么必须分离**：定向链按标准契约提取，若拿它当画像用，等于要求「先知道匹配结果才能画像」，因果倒置；而画像链若复用 `cert_extraction_result`，会污染 NC/报告的数据源。两者表物理隔离，正是为守住 `Phase3 §1.3` 的「企业保存的字段和表格数据是真正的数据核心」。

## 6. 关键设计决策详解

### D1 — 表前缀 `cert_`，不复活 `ent_`

2026-09-25 裁决已 DROP 全部 9 张 `ent_*` 并明确「等真要做这些功能时再讨论表结构」。本模块即该讨论。选 `cert_` 而非 `ent_` 的理由：
- `cert_` 是业务域现行前缀（`cert_enterprise`、`cert_extraction_result` 已迁入）；
- `数据库表设计-V2.md` §域B 仍写 `ent_` 前缀，属**文档滞后**，本模块实施时该文档需同步勘误（登记于 11 号分册）。

### D2 — 枢纽 = `cert_standard_directory_file.Code`

理由：标准目录 2026-09-26 重建后，`cert_standard_directory_file` 是「机构×标准×阶段」下文档清单的唯一实体，且 `ExtractionEnabled/ExtractionRules/FilePattern` 等属性全在此表。契约挂它，匹配、规则、填充三者天然同键。

### D4 — 匹配不走工作流 Skill

`Skill清单-V1.md` §1.2 已有同理先例：`document_extract` 因「文档提取走独立子系统（DocExtractionRuleService），有自己的 Service/Controller/页面，不经过 Skill 体系」被移出。匹配引擎具备完全相同的特征（多阶段、长耗时、需队列、需独立页面），故：
- 实现为 `Services/EntNorm/` 下的独立 Service 组 + 2 个队列 TaskType；
- **不**在画布上暴露为 Skill 节点；
- 但工作流 `ai_node` 可通过既有数据源节点**读取**匹配结果（与 `get_field`/`get_table` 的消费方式一致）。

### D7 — 三阶段匹配而非全量两两 LLM

设企业文档 N=100、标准文档 M=60：
- 全量两两：6000 次 LLM 调用，按 qwen-turbo 计费与 180s 超时不可接受，且两次调用结果不可比对（无全局排序基准）；
- 三阶段：指纹阶段零 LLM；召回阶段零/低 LLM；精排阶段仅对 `Top-K`(K≤10) 候选打分，且**一次调用对一个标准文档评分全部相关企业文档**（批式），实际调用量 ≈ M×(有候选的标准文档数)，可控制在百次量级。
详见 04 分册 §2。

### D9 — 自动化的天花板是「候选」，不是「结论」

`confidence ≥ 阈值` 只允许进入「字段/表格对齐试填」，生成的是**待确认的标准文档实例**；实例转为「已确认」必须有人工动作。这是认证业务的合规底线，也是 `审核端与后台管理端功能设计-V2.2.md` 全篇「可信度 + 溯源 + 人工最终裁决」原则的延续。
