## 六、专题评审一：标准模板设计

> 2026-09-30 用户追问「后台标准模板的设计是否认可」。本节只评**已定骨架的技术正确性**。
> **判定**：✅ **认可骨架**，但有 2 处必修（1 处必现缺陷 + 1 处模型错误），5 处改进。

### 6.1 认可的（不要改）

- 「格式归模板、值归平台」+ 按 `DataType` 写强类型值 —— 正确，且顺带消掉公式/重算/样式三类风险。
- 锚点分层（标量 Token / 区块书签 / Excel 区域 + `total_token` / 域独立）—— 与 poi-tl、docxtemplater 的成熟分层同构。
- 唯一写入者不变量 → 阶段 B 无序化、无屏障 —— 推导成立（`sum` 在阶段 A 已算完）。
- 一种模板语言两种渲染器 + `.doc/.xls` 用转换归一 —— 比"两种模板语言"省得多。
- `total_token` 相对推导解决 Excel 插行漂移 —— **本设计里最有价值的原创点之一**。
- `SourceSha256` 免重扫、`fill_plan.ScanCode` 绑定模板版本 —— 模板换版可追溯。

### T-01｜`{{Token}}` 跨 run 拆分 —— 必现缺陷，P0 就会撞 ⛔ 最高

Word 会把一段连续文本按编辑历史拆成多个 `<w:r>`（例如 `{{ENT_NAME}}` 实际可能是 `{{ENT_` + `NAME}}` 多段）。**`{{...}}` 语法在真实模板上必然遇到跨 run**，`16` 号全文未提处理策略。

- **建议**：① 扫描器前置 **run 归一化**（合并相邻同格式 run 后再匹配 token，poi-tl `RunIterator` 同款）；② 规范新增可检出项 **W9「Token 不得跨 run」**（保存模板时红牌）；③ **写入时同样需要跨 run 合并替换**，不只是扫描。
- **影响**：不修则 P0 出口"拿 1 份真实 docx 跑通扫描"大概率不通过。

### T-02｜书签模型写错了：Word 书签是「一个书签 + start/end 配对」⛔ 高

`16` §3.1 写「书签 Bookmark **A→B**」，§9.2 给了 `AnchorRef` + `BookmarkEnd` 两个字段 —— 这是**两个书签**的模型。Word 原生机制是 `w:bookmarkStart w:id=N` … `w:bookmarkEnd w:id=N` **配对同一个 id**，范围即两者之间。

- **建议**：`cert_doc_template_part` 去掉 `BookmarkEnd`（或改存 `BookmarkId`）；范围由该书签的 start/end 决定。
- **配套（更重要）**：**书签应放在样板行的首个单元格内，扫描器向上取 `<w:tr>` 边界**作为克隆单位 —— NPOI 克隆的是 `CT_Row`，书签范围未必等于行范围。这条必须写进规范（W2 补充），否则扫描器与克隆器对"重复区"理解不一致。

### T-03｜Excel「清理模板原第 12~60 行残留」与 E2 自相矛盾，且会误删 ⚠️ 中高

`16` §4.3 执行步骤 4 是「清理模板原第 12~60 行残留」，但 E2 又要求「区外元素（合计/汇总）**紧贴**数据区下沿」。若合计行下方还有签字栏/说明，ShiftRows 会下移它们，而「清理残留」会误删。

- **建议**：① 模板**不预留空行**（数据区 = 表头 + 1 样例行），靠 ShiftRows 插入；② 数据区下方内容一律「随 ShiftRows 下移」，禁止删除；③ 写成可检出项 **E8**。

### T-04｜合并单元格 + 行克隆缺降级路径 ⚠️ 中高

`16` §15 隐患 #12 自认「未评估」。真风险：`gridSpan` / `vMerge` / `tcW` 在行克隆时需手工处理。

- **建议**：① P1 前的技术验证 spike 应成为 P1 的**入口条件**而非并行项；② 预置降级路径 —— 若克隆不可靠，退回「**按模板样式重建整块表格**」（牺牲保真换确定性）；③ 模板规范限制「数据区禁合并」（E6 已有，方向一致）。
- **理由**：审核员现场 Excel 台账大量使用「部门名称合并单元格」，这是主流形态，不是边缘场景。

### T-05｜缺一条铁律：`FieldCode` 一经发布不得改名 ⭐ 建议采纳

`16` §11 承诺「书签名稳定则换模板配置零改动」，但**没有约束 `FieldCode` 的稳定性**。契约、字段定义、`AggregateRule`、`FillTarget`、占位符全部按 `FieldCode` 对齐；换模板时把 `ENT_NAME` 改成 `ENTERPRISE_NAME` → 整套流程配置静默失效。

- **建议**：新增**铁律四** —— `FieldCode` 是稳定语义键，**发布即冻结**；模板换版只能改锚点，不得改 `FieldCode`；需改名 = 新字段 + 迁移脚本。并加扫描器校验（锚点引用的 `FieldCode` 必须 ∈ 契约字段定义）。

### T-06｜统一表架构的必然代价：模板行必须写保护 ⭐ 建议采纳

D11 统一表下模板行与企业行同表。任何走企业侧上下文的写路径若条件不全，就能改到模板行 —— 影响**全部企业**。

- **建议**：① Service 层硬校验：`EnterpriseCode == YzhVirtualEnterprise.Code` 的行**拒绝**企业侧上下文写入；② 模板发布独立权限点；③ 并发编辑加乐观锁（`UpdateTime` 比对）；④ 加守卫或验证 SQL 巡检「模板行被企业上下文改动」。

### T-07｜把「模板包」定义为一等交付物 ⭐ 建议采纳

`16` §4 提到「模板包 + 维护团队」，但没定义模板包形态。

- **建议**：模板包 = 模板文件（docx/xlsx）+ 锚点清单 + 字段定义 + 规范校验报告，**可导入导出、可 diff、可回滚**。顺带解决：换版原子性、咨询团队交付物、离线评审、模板规范培训材料载体。

## 七、专题评审二：企业文档自动匹配

> **判定**：✅ **认可骨架**，但有 3 处逻辑缺陷 + 1 处遗漏终态。

### 7.1 认可的（不要改）

- 三阶段的**真正理由**是"同一评委、同一场比赛 + 评委看得完的名单"，不是省钱 —— 比成本论扎实得多（`14` §6）。
- 指纹先行、LLM 兜底；**指纹在画像阶段只算一次、匹配阶段复用**（`06` §5）。
- 按**契约侧批式**调用 + `temperature=0` + `RankBatchCode` 批次隔离 + 批间锚定样例 —— 漂移控制三件套齐全，罕见。
- `confirmed` 永不被重算覆盖，重算只覆盖 `pending/scored/recommended`。
- 标签作为独立倒排召回路（D14）—— 最强的先行信号之一。
- 四类冲突矩阵把「高分但字段对不上」（`low_field_coverage`）单列 —— 嗅觉准。

### M-01｜`multi_target` 判定依赖 `auto − 0.05`，漏掉最危险的双高分 ⛔ 高

`04` §6.1 判据：同一 `FileCode` 下 ≥2 条候选 `Confidence ≥ auto − 0.05`。当 auto=0.85 时，0.92 与 0.94 **都 ≥ auto**，公式判定"不冲突" —— 而这恰恰是最典型的"一份文件同时很像营业执照和许可证"。

- **建议**：改为 **`Top1 − Top2 ≤ margin`（建议 0.10–0.15）即判 `multi_target`**，与 auto 阈值解耦。冲突是"两者接近"，不是"两者都低"。

### M-02｜「进精排的集合」与「进人工视野的集合」必须分开 ⭐ 建议采纳

`04` §3.2 同时用 Top-K=10、`RecallScore ≥ 0.15`、必需项强塞弱候选三条约束，导致 0.16 的弱候选也**进精排批式 prompt**，污染"名单内横比"的校准基准。

- **建议**：双集合 —— ① **精排集合**：`RecallScore ≥ recall_rank_min`（建议 0.35）；② **人工视野集合**：`≥ 0.15` 或必需项保障的弱候选。弱候选只进人工视野，**不消耗 LLM**。

### M-03｜`fixed` 文档的可信度权重给错了 ⚠️ 中

`04` §5.2 fixed 公式：`0.45×Rule + 0.30×Semantic + 0.15×Field + 0.10×Period`。固定扫描件的"语义"来自 OCR 文本，**噪声最大**；而「统一社会信用代码/法人/许可编号」精确命中的 `Field` 才是**最强且最客观**的信号。

- **建议**：`0.45×Rule + 0.35×Field + 0.20×Period + 0.00~0.05×Semantic`。
- **理由**：同时提升 `Period` —— 固定文档最常见的错配是"旧版营业执照 / 过期许可证"，Period 只占 0.10 压不住。

### M-04｜`DocTypeGuess` 作召回路 R2 有循环依赖风险 ⚠️ 中

`DocTypeGuess` 由画像 LLM 产出；用它召回候选 = "用 LLM 的猜测决定 LLM 能看什么"。类别猜错即**漏召**，S3 精排无法挽回（没进名单）。

- **建议**：① R2 权重下调（0.25 → 0.20）；② **R3（字段名倒排）升为第一信号（0.35）** —— 企业文档里实际出现的字段名（营业执照必有"统一社会信用代码"）不受 LLM 表述影响，是最客观的路；③ 建议权重：R1 文件名 0.30 / R3 字段倒排 0.35 / R2 类别 0.20 / R4 向量 0.15。

### M-05｜精排前加「灰区预筛」可再降一半调用，且不损准确率 ⭐ 建议采纳

`14` §6 已承认批式名单会长（输入约 4 万 token，有 `lost in the middle` 风险），当前所有候选都送 LLM。

- **建议**：先用**零成本规则组合分**（`RuleStrength` + 字段命中率 + 标签 Jaccard）预筛，只把落在 **0.30–0.90 灰区**的候选送 LLM；`> 0.90`（几乎确定）与 `< 0.30`（无关）跳过。
- **收益**：调用量再降约 40–50%；同时把批大小从 20 降到 8–10，缓解名单过长。

### M-06｜缺少「拒识」终态 —— 最容易在真实数据上炸 ⛔ 高

整条链隐含假设"每份企业文档都能找到归属"。真实企业 30–50 份资料里，**发票、合同附件、无关扫描件占比不低**，它们会走完召回→精排→进人工队列，制造大量噪声。

- **建议**：把"归不进去"设为**第一类合法结论**：① `Confidence < review` → 直接置 `unmatched`（**不进**人工队列，可随时捞回）；② 新增人工动作 `mark_irrelevant`（与 `reject` 区分：`reject` = 这份不对换别的，`irrelevant` = 这份不是认证材料）；③ 缺口表达统一到"缺口清单"（与 D22「缺失 = 资料不全」合流）。

### M-07｜「必需项保障」塞弱候选，应改为记缺口 ⭐ 建议采纳

`04` §3.2.4 以 `RecallSource=category` 塞入弱候选"确保人工能看见"，结果是裁决页出现为凑数而存在的候选行，审核员要逐条 `reject`；而 `07` §2.2-4 已有另一条路径「标记为企业暂无 → `MatchState=partial`」。

- **建议**：**统一到缺口清单** —— 必需项零候选时**不生成候选行**，只在标准文件上记 `MatchState=missing` 并进缺口清单。人工在同一处处理"缺失"与"归属"，避免两套入口。

### M-08｜`simple` 与 `deep` 的分数写进同一列会破坏「分数可比」⚠️ 中

`14` D12 让 simple 模式"召回分直接作 `Confidence`"。但召回分（多路加权）与精排五维分**不同源**，用户切模式时同一对文档分数会跳变。

- **建议**：simple 模式**不写 `Confidence`**，写 `ScoreStage='recall_only'` + `Confidence=NULL`，页面显式标"未深度分析"。守住"一列一个语义"。

### M-09｜重算提示的 magic number 需加绝对门槛 ⚠️ 低中

`04` §9.2 规则 2：新候选比 confirmed 高 > 0.10 即提示冲突。若 confirmed 只有 0.40（人工指认），新候选 0.55 也会触发提示，无意义。

- **建议**：加绝对门槛 —— 新候选 **≥ auto** 且高 ≥ 0.10 才提示。

### M-10｜评测指标补两类 ⭐ 建议采纳

`04` §10 已有 Recall@K / Precision@1 / 自动档准确率 / 漏配率 / 人工采纳率。缺：

- **拒识精确率**：被标 `unmatched` 的是否真的无关（对应 M-06）；
- **单份文档平均裁决动作数**：衡量"过度打扰"的操作层面指标（比采纳率更贴近审核员体感）。

## 九、需求补充评审：完成度 / 可信度 / 审批交互

> 评审 2026-09-30 用户补充设计，登记为 **D39–D41**（续 `14` D12–D28、`16` D29–D38）。

### 9.1 需求原文登记

| # | 用户原话要点 | 落点 |
|---|--------------|------|
| N1 | 执行自动规范化/填充后，**按每个文档**生成两个指标 | 文档级指标 |
| N2 | **完成度** = 文档定义的输入项有多少个，我们填充了多少个 | D39 |
| N3 | **可信度** = 每个填写信息都有一个可信度，文档可信度 = 所有可信度合计 ÷ **总的填写数量** | D40 |
| N4 | 单项可信度规则：**确定只有一个文件/一个数据源 → 100%**；**来源有 2 个文档 → 随机选一个填写 → 50%** | D40 |
| N5 | 用户审批时，**点击任意一个填写信息** → 可改数据来源，或直接修改当前单元格的信息 | D41 |

**与既有设计的关系**：N1/N2 ≈ `14` D24 `CompletionRatio`；N5 ≈ `14` D24 `ChangeFieldSourceEvent` + `14` D26 候选面板 + `07` §4 `FieldOverrideJson`。**N3/N4 是新增语义，与既有设计存在三处冲突**（见 9.3）。

### 9.2 完成度（D39）

#### 9.2.1 既有定义（需修正）

`14` D24：`CompletionRatio = 已填写字段数 / 契约字段总数`。
`16` §9.3：`cert_doc_fill_plan` 有 `ExpectedFieldCount / FilledFieldCount / UnfilledFieldCount`。

#### 9.2.2 四个必须定死的口径

| # | 问题 | 备选 | 建议 |
|---|------|------|------|
| C-a | **分母是谁** | ① `cert_doc_field_def` 行数 ② 模板锚点数 ③ 仅 `Required=1` 的锚点 | **②**：谁要落笔谁才计入；一字段多锚点各计 1；定义里没有锚点的字段不会虚增分母 |
| C-b | **表格怎么计** | ① 整体计 1 项 ② 按行计 ③ 按"列 × 至少一行"计 | **①**：表格行数动态（`16` §4.3 插行），按行计会让完成度随数据量抖动 |
| C-c | **N/A 与阶段相关项** | 计入分母 / 扣除 | **扣除**：`DocRole=optional/reference/attachment` 与"本阶段不适用"应可标 `na` 并从分母扣除，否则完成度永远封顶不到 100% |
| C-d | **失败项** | 计入分子 / 扣除 / 单列 | **单列** `FailedFieldCount`，不进分子也不扣分母（保留"还差"语义） |

#### 9.2.3 建议定义

```text
完成度 CompletionRatio = (已填项 + 已确认项) / (预期项 − 不适用项)

  预期项 = 模板锚点数（cert_doc_template_part，一字段多锚点各计 1）
  已填   = fill_item.ItemState ∈ {filled, verified} 且值非空
  不适用 = fill_item.ItemState = 'na'
  失败   = fill_item.ItemState = 'failed' → 单独展示 FailedFieldCount
  表格   = 整体计 1 项
```

展示：顶部进度条 + 分数（如 `17/23`）+ 独立徽标显示 `na` 与 `failed` 数量。多来源聚合（`14` D25）**不重复计数**，按 `FieldCode` / 锚点去重。

### 9.3 可信度（D40）— 本节是重点

#### 9.3.1 先厘清：册内已有**三个**同名不同义的「可信度」

| 概念 | 语义 | 既有字段 |
|------|------|----------|
| ① 匹配可信度 | 企业文档 ↔ 标准文档**配不配** | `cert_doc_match_candidate.Confidence`（`04` §5.2 五维加权） |
| ② 值可信度 | 这个值**抽得准不准** | `cert_extraction_result.Confidence`（既有） |
| ③ **来源唯一性** | 这个值**来自几个来源** ← **用户本次要的** | **不存在** |

用户 N3/N4 描述的是 **③**，但用的是"可信度"这个词。**若直接复用 `Confidence` 字段，会打破 `04` §5.3「四体系同值域同类型 + 语义唯一」的口径**，违反本项目"字段名语义唯一 / PascalCase 三处一致"的纪律。

**结论：必须新增字段名，不能复用 `Confidence`。**

#### 9.3.2 N4 的 `1/N` 规则：四处问题

| # | 问题 | 说明 |
|---|------|------|
| ① | **"随机选一个"不可复现** | 同输入两次运行可能给出不同值，与 `04` §9「temperature=0 + 固定 prompt + 锚定样例」的漂移控制目标**直接相反**；且与 `14` D25 已定义的确定性解法（`AggregateRule`：`priority`/`concat`/`max_confidence`，首期默认 `priority`="营业执照优先"）**正面冲突** |
| ② | **丢弃源质量** | 0.99 的营业执照与 0.30 的手写说明，在 `1/N` 下都算 50% |
| ③ | **不区分"同值一致"与"不同值冲突"** | 两个来源都写"XX公司"（多源互证，**应更可信**）与写"XX公司 / YY公司"（真冲突，**必须人工**），在 `1/N` 下同为 50% —— 这是 `1/N` 丢失的最大信号 |
| ④ | **与冲突矩阵脱节** | `04` §6 的四类冲突（含 `multi_source`）已承担"多来源"判定职责，`1/N` 若独立成体系会与它并存 |

#### 9.3.3 建议：保留你的直觉，拆成两个正交指标再合成

```text
字段综合可信度 FieldConfidence（decimal(3,2)，0.00–1.00）
  = ValueConfidence × CertaintyFactor

  ValueConfidence（值可信度）
    = 最终选用来源自身的提取/生成可信度（cert_extraction_result / fill_item.Confidence）
    人工覆盖 → NULL（页面标"人工"，按 07 §9 不计分）

  CertaintyFactor（来源确定性系数）
    N = 1                    → 1.00   （唯一来源，无歧义 —— 你的规则）
    N ≥ 2 且各源取值一致      → 1.00   （多源互证 → 不惩罚）
    N ≥ 2 且各源取值冲突      → 0.50   （保留"两个来源降半"直觉，同时强制人工）
    N 个来源、无一致/冲突判定 → 0.5 + 0.5/N （N=1→1.00、N=2→0.75、N=3→0.67）

文档可信度 ConfidenceRatio = Σ(FieldConfidence) / 已填项数
  · 分子只含已填项；人工覆盖项（NULL）按 1.00 计入分子并计入分母
  · 未填项**不计入**分母 —— 缺口由"完成度"表达（← 修正 14 号 D24）
```

**worked example（供拍板用）**

| 场景 | N | 各源取值 | 各源值可信度 | N4 原规则 | 建议 |
|------|---|----------|--------------|-----------|------|
| 唯一来源，抽得准 | 1 | — | 0.95 | 100% | **95%** |
| 唯一来源，抽得勉强 | 1 | — | 0.55 | 100%（**高估**）① | **55%** |
| 两源，取值**一致** | 2 | 同 | 0.95 / 0.80 | 50%（**低估**）② | **95%** |
| 两源，取值**冲突** | 2 | A / B | 0.95 / 0.30 | 50% | **47.5% + 强制人工** |
| 人工填写 | — | — | NULL | 未定义 | **NULL（标"人工"）** |

> ① 你的规则假设"唯一来源 = 正确"，但提取本身可能不准 —— 100% 会掩盖这一点。
> ② 多来源**互证**恰恰是最可信的情形，给 50% 会系统性地**惩罚高质量数据**。

#### 9.3.4 与 `14` D24 的分母冲突（必须拍板）⛔

| 出处 | 口径 |
|------|------|
| `14` D24（现有） | `ConfidenceRatio = AVG(字段Confidence)`，**未填写字段 Confidence = 0 计入平均**（代码 `f.FieldConfidence ?? 0m`） |
| 用户 N3（本轮） | 分母 = **总的填写数量**（即未填不计） |

**两者相反。** 建议采纳**用户口径**（未填不计入分母）—— 否则可信度会被完成度拖垮，两个指标语义重叠；缺口应只由"完成度"表达。

同时建议明确：**人工填写的项**计入分母、按 1.00 计入分子，否则会出现"机器填得越多、平均越低"的逆向激励。

#### 9.3.5 与 `07` 号禁止事项的关系

`07` §9 已定：「AI 分数低就人工补个 0.9 → ⛔」「人工不改 `Confidence`」。因此：

- 用户改**值** → 该字段 `FieldConfidence = NULL`（人工信号），**不得**由前端传一个"人工打的 0.9"；
- 用户改**来源** → 按新来源重算（回到公式），**旧值保留**（`FieldOverrideJson` 原值/覆盖值分离）。

### 9.4 审批交互（D41）

#### 9.4.1 与既有设计对齐情况：✅ 同构，无需新建模型

| 用户 N5 | 既有设计 | 结论 |
|---------|----------|------|
| 点击任一填写信息 | `14` D26 字段图谱 + 候选面板 | 一致 |
| 改数据来源 | `14` D24 `ChangeFieldSourceEvent` / `FieldSourceChanged` | 一致 |
| 直接修改当前单元格 | `14` D24 `DocContentChanged` + `07` §4 `FieldOverrideJson` | 一致（但见 9.4.2 ①） |

#### 9.4.2 三处必须澄清

**①「修改当前单元格」改的是数据，不是产物** ⛔ 易误解

`16` 铁律一已定分层：**取值层（AI/规则）产出值 → 落笔层（NPOI）产出文件**。用户说"直接修改当前单元格的信息"极易被理解为**直接编辑生成的 Word/Excel**。必须澄清：

> 改的是 `fill_item` 的数据层；**产物是重生成的**。否则产物与数据不同源，审计断链、下次重跑覆盖人工修改。

**② 表格的"单元格"粒度未定义** ⚠️

`16` §3.1 的表格锚点是**区域**（`Sheet1!A11:F11`）整体写入，`fill_item` 是"每个锚点一行"。所以"改表格里的某一个单元格"目前**无处落点**。需在 `fill_item` 支持子行/子列定位（或表格值以结构化形式存 + 行内列锚点）。

**③ 改来源后的连锁反应** ⚠️

需定：是否只重算该字段（建议是，`14` D24 流程 2 已如此）；是否触发级联（`14` §9 #10 全局参数级联只影响 `replace` 类文档）；是否限流（`14` §10 风险登记给了"每文档每分钟 ≤ 3 次"）。

### 9.5 数据落点建议

现在"字段级填充事实"有三处候选：`cert_extraction_result`（既有）、`FieldOverrideJson`（14 D24 / 07 §4）、`cert_doc_fill_item`（16 §9.4）。

| 表 | 建议定位 |
|----|----------|
| `cert_doc_fill_item` | **唯一「字段级填充事实表」**（含 `ItemState` / `SourceType` / `Confidence` / `IsOverridden` / 值三形态）；**完成度与可信度都从它聚合** |
| `cert_extraction_result` | 退回「定向提取的原始产出」，**不参与页面指标**，仅作提取链自身的记录与溯源 |
| `FieldOverrideJson` | 保留为 `decision` 上的**审计快照**（谁在何时改了什么），不作为查询源 |

需在 `fill_item` 增列（或明确写入既有列）：`SourceCount`（N，int）、`SourceCertainty`（`decimal(3,2)`）、`ValueConfidence`（`decimal(3,2)`）、`SourceAgreement`（0/0.5/1）。

## 二、全局方向合理性（✅ 认可，不要动）

1. **命题清晰、目标单一**：「企业散乱资料 → 标准目录中的标准文档」。输入/处理/输出三句话可复述，符合「先有全局方向」的要求。
2. **三条链物理分离（转换链 / 画像链 / 定向链，D3）**：画像链服务匹配、定向链服务填充，互不写对方的表——这是本设计最关键的**解耦决策**，避免了「先有匹配结果才能画像」的因果倒置。
3. **三阶段匹配（D7）**：指纹（零 LLM）→ 召回（零/低 LLM）→ 精排（Top-K、批式）。理由不是省钱，而是「同一评委、同一场比赛」的**可比性**——属架构级论证。
4. **人工裁决底线（D9）**：AI 只产候选、最终归属必须人工；`IsConflicted=1` 禁自动确认。符合认证合规。
5. **降级底线**：LLM 全线不可用时退化为「规则识别 + 人工全量裁决」，业务不中断。
6. **五层依赖单向**：L1（接入）→ L2（加工前置）→ L3（认知）→ L4（匹配决策）→ L5（填充输出），无环，符合分层原则。

**判定**：全局方向**不需要重新论证**。下面全部是**同一方向内的完整性缺口**。

## 三、端到端流程闭环审查（泳道级）

`03` §1 的泳道画的是**理想全链**（上传→转换→画像→召回→精排→裁决→定向提取→填充）。逐路径检查「有没有出口」：

| 路径 | 是否有出口 | 判定 |
|------|-----------|------|
| 正常链（有高分候选 → 裁决 accept → 填充） | ✅ 有 | 闭环 |
| 转换失败 | ✅ 有（`convert_failed`，可重试/放弃，仍可人工指定） | 闭环 |
| 画像失败 | ✅ 有（`profile_failed`，可重跑） | 闭环 |
| 画像跳过（无 Markdown / 图片型 PDF） | ✅ 有（`skipped`，等 OCR） | 闭环 |
| 裁决 reject | ✅ 有（候选 `rejected`） | 闭环 |
| **召回为空 / 全部低于复核线** | ⚠️ **仅 `03` §6 异常表一行文字**（「进无归属清单」），**未进四条状态机、未进泳道、无可操作终态** | ⛔ **缺口 G-01** |
| 契约缺失 | ✅ 有（该标准文档不参与匹配） | 闭环 |
| 文件替换/删除 | ✅ 有（状态归零 + 回退） | 闭环 |

**结论**：泳道在**最坏情况**（一份企业文档谁都不匹配、也不该匹配任何标准文档）没有建模出口。详见 `G-01`。
