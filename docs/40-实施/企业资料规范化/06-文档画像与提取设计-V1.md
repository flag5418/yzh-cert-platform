## 1. 两条提取链的边界（D3 落地）

| | 画像链（本册） | 定向链（既有，`DocExtractionRuleService`） |
|---|---|---|
| 目标 | 「这**是**什么文档」 | 「这文档里**按定义**填了什么值」 |
| 输入 | 企业文档 Markdown | 企业文档 Markdown + 规则（字段/表格定义） |
| 规则 | **无规则**，通用地归纳 | 按 `StandardFileCode` 取 `DocExtractionRule` |
| 触发 | 上传转换完成 / 手动重跑 | 裁决确认归属后（T7，03 分册） |
| 写入 | `cert_ent_doc_profile*` | `cert_extraction_result*` |
| 次数 | 每份文件 **1 次**（版本内） | 每份文件×其契约字段数（分批） |
| 服务 | 匹配（04 分册） | 填充（标准文档实例） |

**硬边界**：
- ⛔ 画像链**禁止**读写 `cert_extraction_result`；定向链**禁止**写 `cert_ent_doc_profile`。
- ⛔ 画像**不产出** `StandardFileCode` 判断（`DocTypeGuess` 只是类别词，不是归属——守 D9）。
- ✅ 两链共享：转换产物（Markdown）、`LlmInvokeService` 通道、`cert_ai_usage_log` 计费（`BusinessType` 区分）、位置溯源 `PositionInfo`。

## 2. 画像的前置依赖：转换产物

```text
企业文件上传（03 分册 T2）
   └─ 复用文件转换队列（OfficeConvertService → anydoc → Markdown，libreoffice → PDF）
        ├─ MarkdownPath 有值 → 画像可跑
        └─ MarkdownPath 无值（转换失败/不支持格式）
             → ProfileStatus='skipped'，ProfileMessage='无Markdown产物'
             → 只跑 §5 指纹预判（文件名级），文件名也识别不出 → 进「人工指定」通道
```

- **画像的唯一内容输入 = Markdown**（承接 `docs/50-任务/开发计划/文档提取规则-移植实施计划-V1.md` D-6：预览转 PDF、提取转 Markdown，Markdown 直接作 LLM 上下文）。
- 图片/PDF 扫描件无 Markdown → 触发 P3 决策点：OCR 打通前，这类文件在画像链只能走「文件名指纹 + 人工指定」，**在 10 分册 MVP 范围中明示该限制**。
- `SourceMarkdownPath` 记录本次画像输入快照路径，供复现与对比。

## 3. 画像流水线

```text
┌─ T1 触发 ────────────────────────────────────────────────┐
│ 上传转换完成（T2 后置） / 裁决页「重新画像」 / 批量重跑        │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌─ P0 队列 ────────────────────────────────────────────────┐
│ TaskType = ent_doc_profile（03 分册 §4.2）               │
│ 消费端：EntDocProfileTaskExecutor（新，照抄 OfficeConvert 模板）│
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌─ P1 指纹预判（0 次 LLM，见 §5）────────────────────────────┐
│ 遍历 active 的 fixed 契约 FingerprintJson                │
│  ├─ 命中 minScore → DetectSource='fingerprint'           │
│  │   DocCategory='fixed'，DocPurpose/字段= 指纹已知项，    │
│  │   仍跑一次轻量 LLM 归纳作用（可关，ent_norm_profile_llm）│
│  └─ 未命中 → DetectSource='ai'，进入 P2                  │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌─ P2 LLM 画像（1 次调用）─────────────────────────────────┐
│ 输入 = Markdown（截断策略见 §4.3）+ 固定画像 prompt        │
│ 输出 = 严格 JSON：purpose / typeGuess / fields / tables   │
│ 解析 → TryRepairTruncatedJson → 字段校验 → clamp 分数     │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌─ P3 落库（只追加 + 指定列更新）────────────────────────────┐
│ INSERT 新 ProfileVersion 行（IsLatest=1，旧行 IsLatest=0） │
│ 批插 field / table 子行（PositionInfo 逐条带源位置）       │
│ 主表更新仅指定列：ProfileStatus/ProfileMessage/           │
│   ProfileVersion/DocPurpose/DocTypeGuess/FieldKeywords/  │
│   Counts/Confidence/ModelName/Tokens/SourceMarkdownPath  │
│ ⛔ 禁止 UpdateAsync(entity) 全列覆盖                       │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌─ P4 回写文件侧 + 通知 ───────────────────────────────────┐
│ cert_standard_directory_file.MatchState 保持（匹配另跑）  │
│ IYzhQueueNotifier.NotifyAsync 仅前端进度                  │
│ 业务状态已在 ExecuteAsync 内写完（死接口不承载业务）         │
└──────────────────────────────────────────────────────────┘
```

### 3.1 触发点与幂等

| 触发 | 幂等键 | 行为 |
|------|--------|------|
| 上传转换完成 | `FileCode` 已有 `IsLatest=1` 且 `ProfileStatus='completed'` 且 Markdown 未变 | **跳过**（防重复烧钱） |
| 人工「重新画像」 | 无条件 | 新 `ProfileVersion+1` |
| 标准/契约变更引发的批量重画像 | —— **不存在**：画像不依赖契约（无规则），标准侧变化不影响画像 |
| 重传文件（新版本） | `FileCode` | 重跑，版本+1 |

### 3.2 字段/表格子行的处理

> **⚠️ 本节描述的「子表」形态待 `Q-01` 裁决**（见 `15-全册评估报告-V1.md` §十二）。若裁决为 JSON 内嵌，则「重新 INSERT 子行 / JOIN 子行」改为「整行新版本 `FieldsJson`/`TablesJson`」；下述三条原则（只追加、按 `IsLatest` 取、`FieldKey` 归一化）**两种形态都适用**。

- 子行随新版本**重新 INSERT**，旧版本子行物理保留（`ProfileCode` 区分）——与主表同一「只追加」哲学；
- 查询永远带 `IsLatest=1` 的主表行再 JOIN 子行；
- `FieldKey` 归一化键（拼音/英文）用于**跨文档对齐**（召回 R3 与精排字段比对都按它），生成规则：中文字段名 → pinyin 小写去空格，稳定可复算。

## 4. 画像提示词与输出契约

### 4.1 输出 JSON Schema（固定）

```json
{
  "purpose": "该文档的作用归纳，200-500字，口径与契约 DocPurpose 对齐（是什么/审核关注点/来源口径）",
  "typeGuess": "质量手册",
  "fields": [
    {
      "name": "文件编号", "key": "wen_jian_bian_hao", "value": "QM-2026",
      "dataType": "string",
      "position": { "page": 1, "line": 3, "section": "封面" },
      "confidence": 0.95, "isKeyField": true
    }
  ],
  "tables": [
    {
      "index": 0, "name": "文件修订记录",
      "header": ["版本", "日期", "修订内容", "审批"],
      "rows": [["v2", "2026-03-01", "换版", "张三"]],
      "rowCount": 3, "columnCount": 4,
      "position": { "page": 12, "section": "附件1" },
      "confidence": 0.9
    }
  ],
  "confidence": 0.9
}
```

**后端校验**（与 04 §4.3 同套路）：
1. `TryRepairTruncatedJson` 抢救截断 → 反序列化；
2. `fields[].position` 必须可解析（解析失败置 NULL 并记 `ProfileMessage`，**不整单失败**）；
3. 分数 clamp 到 `[0,1]`，`ROUND(,2)`；
4. `tables` 超 50 行 → `rows` 截断至 50 行，`rowCount` 保留真实值，`ProfileMessage += '表格截断'`；
5. `fields` 超 100 条 → 截断（画像只是匹配摘要，不是全量抽取）；
6. `purpose` 缺失 → `Confidence` 不高于 0.5 并标 `[缺作用]`。

### 4.2 与契约 `DocPurpose` 的口径对齐

画像 prompt 内嵌一句固定要求：**「作用归纳按『是什么 / 审核关注点 / 来源口径』三段式」**——与 05 分册 §2.1 契约侧规范同构，使精排比对两侧文本时结构可比。这比"让 LLM 自由发挥再语义比对"稳定得多。

### 4.3 输入截断策略

| 文档规模 | 策略 | 理由 |
|----------|------|------|
| ≤ 30K 字符 | 全文入 prompt | 通常手册类 1–5 万字符 |
| > 30K 字符 | 取「封面/目录/前 10 章节标题 + 每章首段」+ 末尾 10% | 画像只需结构与作用，不需全文 |
| 多表格文档 | 表头全取 + 每表前 5 行 | 表格结构是匹配主信号 |

截断参数放 `cert_sys_config`（`ent_norm_profile_max_chars=30000`），可调。

## 5. 指纹预判（DetectSource=fingerprint）

- 复用 04 分册 §2 的 `FingerprintJson`，但此处**只用于打标签，不产候选**（归属判断属匹配阶段）：
  - 命中 → `DocCategory` 画像结论记 `fixed`、`FingerprintResultJson` 存明细（`{"matched":true,"rules":["fileName:营业执照"],"score":0.92}`）、`DetectSource='fingerprint'`；
  - 明细落库后，S1 匹配阶段直接读它，**指纹只算一次**（画像阶段算，匹配阶段复用）。
- `DetectSource='manual'`：人工在文件上直接指定「这是营业执照」时，画像行由人工建（`DocPurpose` 人工写），不跑 LLM。
- `mixed`：文件名指纹命中 + LLM 补充作用归纳（默认路径）。

## 6. 画像版本与重跑

| 概念 | 规则 |
|------|------|
| 版本 | `ProfileVersion` 从 1 递增；新版本行 `IsLatest=1`，旧行置 0（同一事务） |
| 何时重跑 | ① 人工点击 ② 文件重传 ③ prompt 模板升级（管理员批量触发，按 `ModelName+模板版本` 过滤） |
| 旧版本用途 | 对比画像差异、审计「为什么当时匹配是那个结论」 |
| 匹配引用 | 候选表记 `ProfileCode`（02 §3.8），**画像重跑不自动改候选**——按 04 分册 §9 重算规则另行触发 |

## 7. 失败、降级与成本

### 7.1 失败分类与出口

| 失败 | `ProfileStatus` | `ProfileMessage` | 后续 |
|------|-----------------|------------------|------|
| 无 Markdown 产物 | `skipped` | `无Markdown产物` | 指纹/人工通道 |
| LLM 超时/5xx | `failed` | `LLM调用失败:{err}` | 队列重试（照抄转换队列的重试参数） |
| JSON 解析失败（抢救后仍败） | `failed` | `JSON解析失败:{片段}` | 重试 1 次 → 仍败转人工 |
| 低置信（purpose 缺失等） | `completed` | `[缺作用]` | 照常参与，但 04 §5.2 强制人工 |
| 队列单企业超 `ent_norm_max_calls` | `failed` | `超过单企业调用上限` | 人工分批触发 |

### 7.2 成本与计费

- 每次画像调用写 `cert_ai_usage_log`：`BusinessType='ent_profile'`（匹配为 `'ent_match'`），复用现有 `CostUsd/DurationMs/Success`；
- 主表冗余 `PromptTokens/CompletionTokens/ModelName` 用于单文件对账，明细在日志表；
- 费用监控页按 `BusinessType` 过滤即可，**不新建费用体系**（01 分册衔接矩阵）。

### 7.3 并发与限速

- 画像队列消费并发度默认 3（`ent_norm_profile_concurrency`），与精排队列共用 LLM 配额时由 `LlmInvokeService` 侧的超时/重试策略兜底；
- 批量重跑（如模板升级）必须**分企业分批**触发，避免单次脚本打爆配额。

## 8. 与定向提取链的协同

```text
画像（本册）──► 匹配候选 ──► 人工裁决确认归属（T6）
                                 │
                                 ▼
                     T7 触发定向提取链（既有 DocExtractionRuleService）
                     输入 = 同一份 Markdown + 该标准文件的规则（要素3/4）
                     输出 = cert_extraction_result（带 CellPrompt/TablePrompt 指引）
                                 │
                                 ▼
                     待确认实例 → 字段级人工确认（07 分册）
```

- **同一 Markdown，两种读法**：画像读「全貌」，定向读「按定义取值」。转换产物只做一次，两链共享路径。
- 定向链的规则来源 = 契约 `RuleCode`（05 分册 §4）；契约无规则 → T7 跳过并提示「要素 3/4 未配置」。
- 双链都必须在**裁决确认之后**才允许定向链开跑——未确认归属的文档跑定向提取 = 给错误目标填值（守 D9）。

## 9. 禁止事项

| ⛔ 禁止 | ✅ 正确做法 |
|---------|------------|
| 画像阶段写 `cert_extraction_result` | 画像只写 `cert_ent_doc_profile*` |
| 用 `UpdateAsync(entity)` 全列回写主表 | 指定列更新（P3 列白名单，防 `MarkdownPath` 覆盖事故） |
| 画像里预判 `StandardFileCode` | 只给 `DocTypeGuess` 类别词 |
| 每次匹配都重新画像 | 画像一次、版本化、匹配复用 |
| 无规则时让 LLM「顺便」按想象的字段抽取 | 无规则 = 只做画像（要素 1/2/5a），要素 3/4 留白 |
| 手拼 OSS 路径读 Markdown | `PathBuilder` / 库表已存的 `SourceMarkdownPath` |
| `Enable` 字段 | `IsValid`（铁律九） |
