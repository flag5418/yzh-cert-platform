# 企业资料全生命周期与语义画像深度设计-V1.md

> **状态**：**工程级深度设计 —— 待审批**
> **目标**：详述企业原始资料从上传到转化为“可消费画像”的全管线逻辑，确保数据的规范性与稳定性。

---

## 一、 资料处理流水线 (Data Pipeline)

资料上传不再是简单的文件写入，而是触发一系列原子任务的编排。

### 1.1 生命周期阶段
1.  **Ingest (上传)**：文件存入 `enterprise-original-source` 库。
2.  **Scan (扫描)**：检测文件格式、大小，计算 SHA256 防止重复处理。
3.  **Convert (转换)**：进入 `yzh_queue` 执行 Office -> PDF/Markdown 转换。
4.  **Analyze (语义分析)**：
    - **画像识别**：LLM 识别文档的 `Category` (分类) 和 `Purpose` (作用)。
    - **画像打标**：将分析结果写入 `cert_enterprise_doc_profile` 表。
5.  **Index (索引)**：将提取出的标量和表格存入 `cert_enterprise_extracted_data`。

---

## 二、 语义画像与存储策略

### 2.1 存储分层
- **L0 原始层 (MinIO)**：`enterprise-original-source/{Ent}/{Stage}/{File}`，永久保存，不可修改。
- **L1 转换层 (MinIO)**：`.pdf`（预览用）和 `.md`（AI 消费用）。
- **L2 结构层 (DB)**：
  - `cert_enterprise_doc_profile`：文档元数据、画像标签。
  - `cert_enterprise_extracted_data`：**核心层**。存储提取出的所有原子信息。

### 2.2 画像表结构设计
```sql
CREATE TABLE `cert_enterprise_doc_profile` (
  `Id` bigint NOT NULL AUTO_INCREMENT,
  `FileCode` varchar(36) NOT NULL COMMENT '对应 cert_enterprise_file.Code',
  `EnterpriseCode` varchar(36) NOT NULL,
  `DocCategory` varchar(50) COMMENT '手册|程序|记录|证明',
  `DocPurpose` varchar(200) COMMENT '文档用途描述',
  `Confidence` decimal(3,2) COMMENT '分析置信度',
  `SemanticHash` varchar(64) COMMENT '内容指纹',
  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_file` (`FileCode`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

---

## 三、 提取数据消费模式

**匹配引擎不再读取原始文件**，其执行逻辑如下：
1.  **获取上下文**：从 `cert_enterprise_doc_profile` 筛选出符合 `DocCategory` 和 `DocPurpose` 的候选文件。
2.  **提取数据**：从 `cert_enterprise_extracted_data` 中按 `FieldName` 获取已提取的值。
3.  **动态补充**：如果画像中缺失某字段，按需触发单次 `Skill` 实时提取并回填画像。

---

## 四、 稳定性保障：幂等与重试
- **MD5/SHA256 校验**：上传同内容文件时，直接复用已有的画像数据，避免重复消耗 AI 费用。
- **任务隔离**：语义分析任务在 `yzh_queue` 中拥有独立的优先级，确保不会阻塞正常的预览转换。
