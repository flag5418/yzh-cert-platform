## 〇、一句话结论

**你列的不是「4 种分类」，是 3 个正交维度上的取值。**

| 你的原话 | 实际属于哪个维度 |
|----------|------------------|
| 「有值，只需要进行替换」 | **D2 写入方式**（`replace`）+ 隐含 **D3 形态** |
| 「需要完全重写」 | **D2 写入方式**（`overwrite`） |
| 「从多个其他数据源来获取」 | **D1 取值来源**（多源列表） |
| 「全局参数」（企业名称/营业执照/认证日期） | **D1 取值来源**（`global`） |
| 「页眉、页脚」「大段的描述」「表格」 | **D3 承载形态**（`domain` / `block` / `table`） |

⇒ **一个填写单元 = `(D1 取值来源, D2 写入方式, D3 承载形态)` 三元组。**

- 分类数**不是 4 种**，而是 `7 × 4 × 5 = 140` 种组合，其中**合法且有用的大约 26 种**。
- 把三个维度压成一个枚举（例如"替换型 / 重写型 / 多源型 / 参数型"）**必然失败** —— 因为「页眉里的企业名称」同时是 *替换型* + *参数型* + *页眉形态*，归到哪一类都会丢信息。

**★★★ 第二条结论（比第一条重要）：`取值来源` 必须是「有序列表」，不是单值。**

你说「该字段的填写需要从多个其他数据源来获取」—— 这句话**只有做成列表才成立**：

```json
[
  { "kind": "global",  "ref": "ENT_CREDIT_CODE", "onMissing": "next" },
  { "kind": "profile", "ref": "营业执照", "field": "统一社会信用代码", "onMissing": "next" },
  { "kind": "manual",  "onMissing": "todo" }
]
```

含义：**先取全局参数 → 没有则去企业资料画像里找 → 都没有就挂人工待办**。

这才是「多数据源」的正确表达。如果做成单值枚举，你就只能在「全局参数」和「人工录入」里二选一，回退能力直接丢失。

## 一、先钉事实：读侧**已经有这个分类的雏形**

设计写侧之前先看清读侧 —— 避免重复发明。

| 表 | 列 | 现有注释 | 对应本模型的 |
|----|----|---------|-------------|
| `cert_doc_field_def` | `IsManual` | 是否需手动补充：0-否 1-是 | **D1 = `manual`** |
| `cert_doc_field_def` | `IsAiRecommended` | 是否AI推荐字段(1=是,0=手动添加) | **D1 = `ai`** |

## 二、维度 D1 — 取值来源（7 类）

> **判据统一**：只看「**值最初从哪里来**」，不看怎么写、不看写在哪。

| 码 | 名称 | 值从哪来 | 典型例子 | 失败行为 | 频率 |
|----|------|---------|---------|---------|------|
| `global` | **全局参数** | 认证项目上下文（企业 / 阶段 / 标准 / 机构），**一次取值，全文档可用** | 企业名称、统一社会信用代码、认证标准号、机构名称、法定代表人 | 必填缺失 → **阻断填充** | ★★★ 最高 |
| `self` | **本文档内引用** | 同一模板的**另一个锚点** | 封面写了企业名称 → 页眉引用它；表格合计行引用明细 | 引用目标未填 → 阻断（**须防环**） | ★★ |
| `sibling` | **同批文档取值** | 同企业同阶段下**另一份标准文档**的已填结果 | 「管理评审报告」引用「内审报告」的审核日期 | 目标文档未完成 → 降级到下一源 | ★ 低频 |
| `profile` | **企业资料画像** | 企业上传的**散乱资料**的画像提取结果 | 从「公司简介.pdf」取成立日期；从「营业执照.jpg」取注册号 | 未命中 → 降级到下一源 | ★★★ |
| `compute` | **计算 / 统计** | 对锚点集合做运算 | 表格行数合计、字段计数、日期差、金额汇总 | 依赖缺失 → 留空并告警 | ★★ |
| `ai` | **AI 生成** | LLM 依上下文生成 | 大段描述、体系覆盖范围叙述、审核结论 | 失败/低置信 → **降级到人工** | ★★★ |
| `manual` | **人工录入** | **必须人填**，无自动来源 | 审核员签字日期、现场观察结论、专家判定 | 未填 → 挂**待办**，不阻断出文档 | ★★★ |

### 2.1 每类的实现要点

**`global`（全局参数）**
- 值来自**已有表**，不需要用户录入：`cert_enterprise` / `cert_certification_body` / `cert_iso_standard` / `cert_cert_stage`
- ⚠️ **必须物化快照**，不能每次实时查 —— 理由见 §七
- 建议做成**参数字典**（`ParamCode` → 取值表达式），模板侧只写 `ParamCode`

**`self`（本文档内引用）**
- 这是**依赖图**的边：`页眉锚点 → 封面锚点`
- ⇒ 填充前必须**拓扑排序**；发现环 → **报错拒绝保存模板**（不能运行时才发现）
- 与 `global` 的区别：`self` 的值依赖**另一处填得好不好**，`global` 不依赖任何人

**`sibling`（同批文档取值）**
- 依赖的是**另一份文档的填充结果** ⇒ 引入**文档间排序**（DAG 跨文件）
- ⚠️ **低频，建议二期**。一期用 `global` + `profile` + `manual` 就能覆盖 95% 场景
- ⛔ 不要为一期实现跨文档依赖调度 —— 复杂度远超收益

**`profile`（企业资料画像）**
- 值来自**画像链**（`06` 册的产物）—— 这正是本册「规范化」的核心命题
- 引用方式 = `(来源文档名 or 文档类型, 字段名)`，**不是** `FieldCode`（画像没有规则，就没有 FieldCode）
- ⚠️ 画像结果是**带置信度**的 ⇒ 低于阈值**视为未命中**，继续回退

**`compute`**
- Excel 侧：直接用**原生公式**（`=SUM(...)`），比后端算更稳、用户可改
- Word 侧：`{{SUM_ROWS}}` 这类由后端算完再写值
- ⛔ 不要把 Excel 的公式改写成后端计算 —— 会丢掉「用户打开文件能看见公式」这个体验

**`ai`**
- 提示词 = `21` 号定义的**每模板一条 `FillPrompt`**（不是每字段一条）
- 输出必须**结构化 + 逐字段**，便于按锚点回填
- ⚠️ AI 的输出**永远当作候选**，不能直接覆盖人工值（见 §四 `manual` 优先级）

**`manual`**
- 这是**唯一不能自动完成**的一类 ⇒ 它决定了「一键填充」的真实完成度上限
- 必须在界面上**显式统计**：「本模板 42 个锚点：31 自动 / 9 人工 / 2 计算」

### 2.2 被否掉的第 8 类：`dict`（受控词表）

考虑过把「认证类型 QMS/EMS」这类做成独立的 `dict` 类。

**否掉的理由**：`cert_application.CertType` 已经是**项目上下文的一部分** ⇒ 归 `global` 即可。把「值是枚举」当成「来源类别」是**把值域混进了来源维度**。

> 若将来真出现「与项目无关的平台级词表」（如行业分类 GB/T 4754），再加 `dict` 类，**现在不加**。

## 三、「从多个数据源获取」有两种语义 —— 必须拆开

你说「从多个其他数据源来获取」，这句话**天然有歧义**，两种语义的代码完全不同：

| 语义 | 码 | 含义 | 例子 |
|------|----|------|------|
| **回退链** | `firstHit` | 按顺序取**第一个非空**，取到即停 | 信用代码：全局参数 → 画像 → 人工 |
| **拼接** | `concat` | 多个源**拼成一句**，全部都要 | 「XX 公司（统一社会信用代码 91…）」 |
| **模板套用** | `template` | 用**小模板**组合多个源 | `{{Name}}（{{CreditCode}}）成立于 {{FoundDate}}` |

⇒ **`SourceSpec` = 有序数组 + 一个 `CombineMode`**：

```jsonc
{
  "combine": "firstHit",        // firstHit | concat | template
  "separator": "、",            // 仅 concat 用
  "expr": "{{Name}}（{{CreditCode}}）",  // 仅 template 用
  "sources": [ /* 有序 */ ]
}
```

**默认值**：`combine = "firstHit"`（覆盖 90% 场景）。

## 四、维度 D2 — 写入方式（4 类）

| 码 | 名称 | 语义 | 是否需要原值 | 典型场景 |
|----|------|------|-------------|---------|
| `replace` | **替换** | 锚点处**已有内容**，替换掉它 | ✅ 需要 | 页眉/页脚、模板里已写示例值的大段描述、表格内已有占位行 |
| `overwrite` | **重写** | 锚点处**为空**（书签/空区域），直接写入 | ❌ 不需要 | 空白书签位置、空单元格 |
| `append` | **追加** | 保留原内容，在锚点后**追加** | ⚠️ 部分 | 「备注：」后追加条款编号 |
| `remove` | **删除** | 该内容**不适用**，整块移除 | ✅ 需要 | 企业无某项资质 → 删掉模板里对应整段 |

### 4.1 `replace` 与 `overwrite` 的真正区别

代码上两者都是「在锚点位置 setText」，**但运营上完全不同**：

| | `replace` | `overwrite` |
|---|-----------|-------------|
| 有原值快照 | ✅ | ❌ |
| 支持「原值 → 新值」差异展示 | ✅ | ❌ |
| 支持「人工改过的值不被覆盖」 | ✅ | ❌（无历史可比） |
| 支持回滚 | ✅ | ❌ |

⇒ **`replace` 的锚点必须落一份原值**（`OriginalText`）。这是你想要的「有值只需替换」的**真正价值** —— 不是省事，是**可审计**。

### 4.2 ⚠️ `replace` 的头号坑：**Word 域代码**

页眉/页脚里的 `{ PAGE }` / `{ NUMPAGES }` 是 **field code**，不是普通文本。

- ⛔ **绝不能用「整段 setText」的方式替换页眉** —— 会把域代码一起抹掉，页码变死数字
- ✅ 只能**定位到具体 run** 做替换，域代码原样保留
- 这是 `W` 系列规范里最容易踩的一条（`16` 册 `W4` 附近）

### 4.3 ⚠️ `replace` 的第二个坑：**跨 run 拆分（W9）**

Word 会把 `{{ENT_NAME}}` 拆成多个 `<w:r>` run（拼写检查、格式变化都会触发）。

⇒ **扫描器与写入器都必须先做 run 归一化**，否则「扫描时找得到、写入时找不到」。
⇒ 已有先例可参照：poi-tl 的 `RunIterator` 等价物。

### 4.4 `remove` 需要「条件」

`remove` 不能无条件执行，必须挂一个**条件**：

```json
{ "writeMode": "remove", "condition": { "kind": "manual", "ref": "HAS_QUALIFICATION", "op": "==", "value": "否" } }
```

⇒ 锚点表需要 `ConditionJson` 列（见 §八）。

## 五、维度 D3 — 承载形态（5 类）

| 码 | 名称 | 定位手段 | 例子 |
|----|------|---------|------|
| `scalar` | **标量** | 行内 Token `{{FieldCode}}` | 单元格、行内字段 |
| `block` | **段落块** | Word 书签（单个，`bookmarkStart`/`bookmarkEnd` 同 id） | 大段描述、体系覆盖范围 |
| `table` | **表格区域** | Excel 区域 + `total_token`；Word 表格书签 | 受审核部门清单、不符合项表 |
| `table_total` | **表格合计** | 表格区域的合计行 | 行数、金额、人数合计 |
| `domain` | **域** | Word 页眉/页脚 + 域代码 | 页眉企业名、页脚「第 X 页 共 Y 页」 |

> ⚠️ **对 `21` 号的修订**：`21` 号的 `AnchorType` 只有 `scalar`/`table`/`table_total`/`domain`，**缺 `block`**。
> 你这次提到的「大段的描述」正是 `block`。**必须补上**，否则大段描述只能挤进 `scalar`，语义丢失。

### 5.1 `block` 与 `scalar` 的分界

判据不是「字多字少」，而是**是否需要整块替换**：

- 值写进去后**不破坏段落结构**（无换行、无编号）→ `scalar`
- 值可能**多段落 / 带换行 / 需要整体替换** → `block`

### 5.2 `domain` 的特殊性

`domain` 锚点有**两种值**，必须区分：

| 子类 | 例子 | 是否写值 |
|------|------|---------|
| **域-文本** | 页眉里的企业名称 | ✅ 写值（但**不能碰域代码**） |
| **域-自动** | `PAGE` / `NUMPAGES` / `DATE` | ⛔ **不写值**，交给 Word 自己算 |

⇒ `domain` 锚点需要 `DomainKind` 列（`text` / `auto`）。`auto` 类**只登记、不填充**（但计入"已处理"）。

## 六、组合矩阵（合法组合）

不是 140 种组合都合法。下表是**实际会出现的 10 种**，可直接当**实现清单**：

| # | 场景 | D3 形态 | D1 来源 | D2 写入 |
|---|------|---------|---------|---------|
| 1 | 封面「企业名称」 | `scalar` | `global(ENT_NAME)` | `replace` |
| 2 | 页眉「企业名称」 | `domain` | `self(→封面锚点)` | `replace` |
| 3 | 正文「认证范围」 | `block` | `global(ENT_CERT_SCOPE)` | `replace` |
| 4 | 正文「体系覆盖过程描述」 | `block` | `ai` | `overwrite` |
| 5 | 表格「受审核部门清单」 | `table` | `profile(部门表)` | `overwrite` |
| 6 | 表格「人数合计」 | `table_total` | `compute(SUM_ROWS)` | `overwrite` |
| 7 | 「统一社会信用代码」 | `scalar` | `[global, profile, manual]` | `replace` |
| 8 | 「审核结论」 | `block` | `[ai, manual]` | `overwrite` |
| 9 | 「不适用条款段落」 | `block` | `manual(条件)` | `remove` |
| 10 | 页脚「第 X 页 共 Y 页」 | `domain` | `compute(PAGE/NUMPAGES)` | —（不写值） |

**第 7 行是「多数据源」的样板** —— 一个锚点、三个源、按序回退、最后兜底人工。**这就是你说的那个场景。**

### 6.1 非法组合（必须在保存时拦住）

| 组合 | 为什么不合法 |
|------|-------------|
| `domain(auto)` + 任何 `D1` | 域自动值不能写 |
| `table_total` + `manual` | 合计必须能算，人工填合计 = 必然算错 |
| `scalar` + `remove` | 行内标量删除会破坏排版，应改用 `block` |
| `self` 形成环 | 拓扑排序无解 |

## 七、全局参数：新表 + **必须物化**

### 7.1 为什么必须物化（不能实时查）

| 方案 | 行为 | 后果 |
|------|------|------|
| **动态**（每次填充实时查 `cert_enterprise`） | 企业改名后 → **历史报告里的名字跟着变** | ⛔ **审计不可接受**：报告出具时的企业名称必须冻结 |
| **物化**（填充时快照） | 值写入后不再变 | ✅ 可审计、可复现 |

⇒ **定案：物化。** 快照时机 = **填充任务开始时**（不是项目创建时 —— 那时企业信息可能还没录完）。

> ⚠️ **修订（2026-10-02，见 `24` 号 §一）**：**快照的位置变了** ——
> - 原来：快照落在 `cert_fill_param_value` ⇒ ⛔ **与企业基础信息重复**
> - 现在：`cert_fill_param_value` **只存人工覆盖值**；自动值**实时读源表**，快照落在**填充结果表**
> - ⇒ 见 §7.4 的表注释与 `23` §4.6

> 这与 `21` 号「不引入版本号」不冲突：物化的是**参数值**，不是**模板文件**。

### 7.3 ⛔ 实测发现：**「认证日期」当前无数据源**

查遍全库，与"认证/审核日期"相关的只有两处：

| 位置 | 含义 | 问题 |
|------|------|------|
| `cert_application.SubmitTime/AcceptTime/CompleteTime` | 提交/受理/完成时间 | ⚠️ `cert_application` **0 行**，且语义是"申请"不是"认证" |
| `audit_task.PlannedDate` | **计划**审核日期 | ⚠️ 是"计划"不是"实际"，且 `audit_task` 属旧表 |

⇒ **「认证日期」目前取不到。** 三个选项：

- **A** 一期先**降级为 `manual`**（人工录入），等真有数据源再改回 `global` —— **推荐**
- **B** 从 `cert_enterprise_stage` 补日期列（但该表是**关联表**，加日期是**职责扩张**）
- **C** 从 `cert_application` 取（但该表 0 行，等于没实现）

> ⚠️ 这类「参数清单里写了、但数据源不存在」的项，**必须在参数字典里显式标记 `SourceExpr = null`**，否则填充时会**静默填空**。

## 八、锚点属性表（对 `21` 号的增补 DDL）

`21` 号的 `cert_doc_template_anchor` 只有 `ValueType varchar(20) DEFAULT 'auto'` —— **不足以表达本模型**。增补列：

```sql
ALTER TABLE `cert_doc_template_anchor`
  -- ① D1 取值来源（有序列表 + 组合方式）
  ADD COLUMN `SourceSpec`      json         DEFAULT NULL COMMENT '取值来源规格：{combine,separator,expr,sources[]}；sources 有序',
  ADD COLUMN `SourceSummary`   varchar(500) DEFAULT NULL COMMENT '来源摘要（列表展示用，由 SourceSpec 生成）',
  -- ② D2 写入方式
  ADD COLUMN `WriteMode`       varchar(20)  NOT NULL DEFAULT 'overwrite' COMMENT 'replace/overwrite/append/remove',
  ADD COLUMN `OriginalText`    text         DEFAULT NULL COMMENT '原值快照（仅 replace/remove 需要，支撑差异与回滚）',
  ADD COLUMN `ConditionJson`   json         DEFAULT NULL COMMENT '写入条件（仅 remove 必填）',
  -- ③ D3 承载形态补充
  ADD COLUMN `DomainKind`      varchar(20)  DEFAULT NULL COMMENT '域子类：text=写值 / auto=交给Word算（PAGE/NUMPAGES）',
  -- ④ 值类型（原 ValueType 语义收窄）
  ADD COLUMN `ValueType`       varchar(20)  NOT NULL DEFAULT 'text' COMMENT '值类型：text/number/date/bool/enum（⛔ 不再是"来源"）';
```

**同时修订 `AnchorType` 的取值域**：

```
scalar | block | table | table_total | domain
```

（原缺 `block`）

**`SourceSpec` 结构示例**（第 7 行场景）：

```json
{
  "combine": "firstHit",
  "sources": [
    { "kind": "global",  "ref": "ENT_CREDIT_CODE", "onMissing": "next" },
    { "kind": "profile", "ref": "营业执照", "field": "统一社会信用代码", "minConfidence": 0.85, "onMissing": "next" },
    { "kind": "manual",  "onMissing": "todo" }
  ]
}
```

**`onMissing` 取值**：

| 值 | 行为 |
|----|------|
| `block` | 阻断填充，报错（用于 `IsRequired`） |
| `next` | 跳过，取下一个源（**默认**） |
| `todo` | 挂人工待办，继续填其他锚点 |
| `empty` | 留空，不告警 |

## 十三、实现载体裁定：**填充取值不做成 Skill**（附与既有裁决的对照）

> **问题来源（2026-10-02 用户）**：「将所有的填写规则定义成一对 Skill —— 替换的、AI 自动生成的、参数中获取的；未来有更复杂的来源就加 Skill、补参数。这样是否合理？」

### 13.1 合理的内核：**策略模式 + 开闭原则**

这个直觉**本身是对的**：

- 一个来源 = 一个实现类
- 每个实现有自己的参数（`ParamCode` / 锚点位置 / 提示词）
- 新来源 = 加实现 + 加参数，**不改调用方**

⇒ **「可扩展」这个诉求成立，必须满足。** 分歧只在**载体**。

### 13.2 ⛔ 但项目**已经走过这条路径，并且改了方向**

| 你的提议 | 项目里的对应物 | 项目裁决（出处） |
|----------|---------------|-----------------|
| 「从参数中获取」→ Skill | `get_field` / `get_table`（`Skills/GetFieldSkill.cs`、`GetTableSkill.cs`） | **已从 Skill 体系移除**，理由：「**数据源节点，行为与功能性节点不一致**，改为**前端硬编码特殊节点**」（`Skill清单-V1.md` §6.2） |
| 「AI 自动生成」→ Skill | `LlmExtractSkill`（`Skills/LlmExtractSkill.cs`，实现已废弃的 `ISkillNode`） | 废弃清单：「**臆想的 AI 提取 Skill**，信息提取走独立流程，不依赖 AI」（`Skill清单-V1.md` §1.2） |
| 「替换」→ Skill | ❌ 无对应 | 写入方式**不是取值**，不应节点化（见 13.4） |
| 文档提取 → Skill | `document_extract` | 「文档提取走**独立子系统**（`DocExtractionRuleService`），不经过 Skill 体系」 |

**前端已经落地的替代形态**（`specialNodes.ts:264-314`）：

```
docField  文档字段   inputPorts: []   → fieldValue / confidence / is_manual_edited
docTable  文档表格   inputPorts: []   → rows / confidence
```

⇒ **「从参数中获取」这件事，项目已经用「特殊节点」实现过了，不是 Skill。**
⇒ 你的提议在方向上**回到了 2026-09-12 之前的状态**。

### 13.3 为什么不匹配：**粒度差一个数量级**

Skill / 特殊节点是**画布节点**，参数绑定三模式（`SkillAttributes.cs:49-59`）：

| 模式 | 含义 |
|------|------|
| `Link` | 参数值**必须来自上游节点连线** |
| `LinkOrConstant` | 可连线，也可在画布上**手输常量** |
| `Enum` | 从**字典**加载下拉选项 |

⇒ 若「一个来源 = 一个节点」，那么「这个字段从哪取」就变成**画布上的一条连线**：

```
一份模板 42 个锚点 × 平均 2 个来源 ≈ 84 个节点 + 上百条连线
```

而画布（`WorkflowDesigner.vue`）的舒适区是**十几个节点**的业务流程。**用画布表达"字段级取值"是量级错配。**

### 13.4 ★ 三个维度里，**只有 D1 能节点化**

| 维度 | 能否节点化 | 原因 |
|------|-----------|------|
| **D1 取值来源** | ✅ 可以 | 有独立实现、有参数、可扩展 —— **但用 Resolver 更轻**（见 13.5） |
| **D2 写入方式** | ⛔ **不能** | `replace`/`overwrite`/`append`/`remove` 共享同一套 IO：**打开文档 → 定位锚点 → 改 run → 保存**。拆成节点 ⇒ **同一文件被打开 N 次** ⇒ 直接撞项目已有教训 **`㉕`（队列锁不参与调度 + 全实体写回 ⇒ 同文件两链并发互相覆盖）** |
| **D3 承载形态** | ⛔ **不能** | 形态是**定位手段**，属于「锚点解析器」，不是「值来源」 |

### 13.5 ✅ 正确载体：`IValueResolver` + 注册表（**不进画布**）

```csharp
public interface IValueResolver
{
    string Kind { get; }                                  // global / self / profile / compute / ai / manual
    Task<ResolveResult> ResolveAsync(ResolveContext ctx, SourceSpecEntry src, CancellationToken ct);
}

[ValueResolver("global", Name = "全局参数")]
public sealed class GlobalParamResolver : IValueResolver { /* 读 cert_fill_param_value */ }
```

- **注册**：DI 扫描 + 特性，**登记即用**
- **扩展**：新增来源 = **加一个类 + 一个特性**，⛔ **不改填充引擎**
- **区别**：它是**填充引擎内部的策略**，**不是用户可见的画布节点** —— 这正是它与 Skill 的本质差别

> ✅ 开闭原则**已经满足**，且比 Skill 轻一个数量级。**不需要为了"可扩展"付出画布的复杂度。**

### 13.6 ★ 反过来看：**该画布化的是「定义期」，不是「填充期」**

| 阶段 | 特征 | 载体 |
|------|------|------|
| **定义期**（扫描模板 / 分类识别 / 语义分析 / 生成提示词） | 低频（维护人员手动触发）、重（秒级、调 LLM）、需要人工编排与审核、要留痕 | ✅ **画布 / Skill**（`16` 册的 12 个 Skill 构想应放这里） |
| **填充期**（取值 → 写回 → 残留校验） | 高频（每份文档一次）、轻（毫秒级、确定性）、无人工编排 | ✅ **引擎 + Resolver** |

⇒ **你的提议是在「填充期」用 Skill，而 Skill 的价值在「定义期」。方向正好相反。**

**可复用的判据 —— 一个操作该不该做成画布节点 / Skill？**

| 条件 | 命中？ |
|------|--------|
| ① 低频（人手动触发，一天几次） | 填充：❌ 高频 |
| ② 重（秒级，可能调 LLM） | 填充：❌ 毫秒级 |
| ③ 需要人工编排顺序 / 分支 | 填充：❌ 顺序由拓扑排序算 |
| ④ 有副作用需要留痕 | 填充：❌ 结果落在 fill_item |

**⇒ 填充取值 4 条全不命中；定义期 4 条全命中。三条以上命中才做节点。**
