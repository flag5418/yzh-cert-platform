## 〇、执行摘要

### 一句话结论

> **用户的担心是对的，而且不是「将来会重复」—— 是「已经重复了」（V2 又新增 2 处实证：D6 / D7）。**
> 重复的**唯一机制**：**`CertPlatform.Admin` 看不见 `CertPlatform.Auditor` 的任何类型**（C2），于是「两端都要用的东西」只剩两条路 —— **让对端预取（加胶水层）** 或 **自己手抄一遍（复制实现）**。
> ⇒ 所以「放哪里」的真问题**不是「能不能放 `Shared`」（V2 已确认：能），而是「放进去之后，是不是真的只剩一份实现」**。
> ⇒ `55` 批次 B 的**方向是对的**（把共用能力收敛到 `Shared`），但**对象选错了**：它想下沉的 `Skills/Fill/*` 绑死了 Admin 的 `SkillExecutor` / `SkillResult` 基础设施，**搬不动**；而**真正该下沉的是「查 DB + 组装 `FillValue`」那一段共同内核**（§6.1 批次 B″）。

### 1.4 `Shared` 的能力边界（**V2 重定义** —— 用户裁定 + 实测）

**用户裁定**：`Shared` 可以引 `DataBase`、可以引 `Stand`、**也可以有 Controller**。

**实测（全部本机验证）**：

| # | 事实 | 证据 | 结论 |

| 1 | `Shared → DataBase` **不构成环** | `YZH.Core.DataBase.csproj:22` 只引 `Stand`；`YZH.Core.Stand.csproj` **零 `<ProjectReference>`**（叶子）⇒ 加边后是 `Shared → DataBase → Stand`，无回边 | ✅ **技术可行** |
| 2 | `Shared → Api` 同样无环 | `YZH.Core.Api.csproj:18-19` 引 `DataBase` + `Stand` | ✅ 若需要控制器基类也可加 |
| 3 | `Shared.csproj` **已有** ASP.NET Core 引用 | `CertPlatform.Shared.csproj:13` `<FrameworkReference Include="Microsoft.AspNetCore.App" />` | ✅ `ControllerBase` / `ApiController` 等类型**今天就能用**，**连 csproj 都不用改** |
| 4 | `Shared` 已预留完整分层目录 | 实测 `Shared/{Controllers,Services,IServices,Repositories,IRepositories,WorkflowEngine,Data}` **全部存在且全空** | ✅ 「Shared 是完整共享层」= **原始设计意图**，只是从未启用 |
| 5 | ⚠️ **但 `Shared` 的 Controller 目前会被静默忽略** | `Program.cs:150-155` 的 `AddApplicationPart` **只注册 Admin 的 4 个 + Auditor 的 1 个程序集**，**没有 `Shared`**；`MapControllers()` 只发现已注册的 ApplicationPart | ⛔ **往 `Shared/Controllers/` 加 Controller = 路由 404 且零启动错误** |
| 6 | ⚠️ 而且这个 404 **会被 `sys_api` 掩盖** | `ApiScanner.LoadAllAssemblies()`（`YZH.Core.Api/Services/ApiScanner.cs:390-398`）会加载 bin 下**所有** `CertPlatform*` DLL 并扫描 `ControllerBase` 派生类 ⇒ **接口管理页能看到、能授权** | ⛔ **「配置了不生效」的典型形态**：权限页显示已配置，调用 404 |
| 7 | ⚠️ `Shared` 在宿主挂了 `extern alias` | `YZH.Core.Web.csproj:32` `<ProjectReference ... Aliases="CertPlatform,SharedEntities" />` | ⛔ `Program.cs` 里**不能直接 `typeof(CertPlatform.Shared.Controllers.X)`**，必须先 `extern alias CertPlatform;`（否则**编译不过** —— 这个是硬错误，不是静默的） |
| 8 | `EntityConfig` 路径清单里**没有 `Shared`** | `Program.cs:61-62` 只有 `Admin/Assets/EntityConfigs` + `Auditor/Assets/EntityConfigs` | ⚠️ 实体上移 `Shared` 后，`EntityConfig` JSON **仍须留在某个端的 `Assets/`**（`Shared` 无 `Assets/` 目录） |

> **⇒ 在 `Shared` 放 Controller 的完整清单（缺一即静默失效）**：
> ① `Program.cs` 顶部加 `extern alias CertPlatform;`（**编译期硬要求**）
> ② `.AddApplicationPart(...)` 加 `Shared` 程序集（**运行期硬要求**；因 alias 不能直接 `typeof`，须 `extern alias` 后 `typeof`，或 `Assembly.Load("CertPlatform.Shared")`）
> ③ 若涉及实体：`EntityConfig` JSON 放到某个**已被登记**的 `Assets/EntityConfigs/`
> ④ 跑一次 `ApiSync`（新接口才会进 `sys_api`）

> **⇒ V2 的落点判据因此变为**：**「能不能放 `Shared`」不再是问题**；问题是
> **A. 放进去是不是真的只剩一份实现**（去重收益）
> **B. 放进去会不会破坏「纯函数可单测」这类有价值属性**（可测性成本）
> 两条都过 ⇒ 放 `Shared`；只过 A 不过 B ⇒ **拆成「纯函数内核（Shared）+ 薄查库适配器（端）」**。

## 二、判据：怎么判一个东西该放哪

### 2.1 三条判据（可机械执行；⚠️ P1 在 V2 已重写）

| 判据 | 问题 | 结论 |
|:--:|------|------|
| **P1** | 这段代码**需要查库**（用 `IDbOrm` / `EntityService` / `SqlSugar`）吗？ | ✅ 需要 ⇒ **V2：可以进 `Shared`**（C1 已放宽）—— 但**必须再判两件事**：① 进 `Shared` 后**是否真的只剩一份实现**（否则白搬）② 它**是否破坏了「纯函数」属性** ⇒ 若破坏 ⇒ **拆成「纯函数内核（`Shared`）+ 薄查库适配器（端）」** |
| **P2** | 这个实体**有没有 ≥2 个端需要读它**（含**将来**的 `Enterprise`）？ | ✅ 有 ⇒ **进 `Shared/Entities/`**；⛔ 只有一个端 ⇒ **留该端** |
| **P3** | 它是不是**纯函数 / 纯模型**（不碰 DB、不碰 HTTP、不碰文件）？ | ✅ 是 ⇒ **进 `Shared`**（可单测、可重放） |

### 2.2 ⚠️ 一条方法论警告：**不能用「现有引用数」判落点**

这是本册最容易踩的坑，也是 `55` 号判断失准的根因之一。

| 事实 | 后果 |
|------|------|
| Auditor 的 19 个实体，在 Admin 侧引用数 **恒为 0** | 因为 **C2 让 Admin 物理上看不见它们** —— 不是「Admin 不需要」，是「Admin 想用也用不了」 |
| 所以：**「Auditor 实体只有 Auditor 在用」这句话是恒真的废话** | 用它来论证「所以该留在 Auditor」= **循环论证** |

⇒ **必须按 P2 的「设计意图」判**：翻 `55` / `54` / `36` 号，问「**这里设计上要求谁来读这个数据**」，而不是「现在谁在读」。

**本册正是这么做的**：§四 D2 发现 Admin 的执行器**需要**企业原始资料（`55` 要求「画像召回」），但它读不到 `cert_enterprise_original_file`，于是**错读了另一张表** —— 这就是 P2 判据的价值。

### 2.3 判据落地为「一个算法」

```
对一个实体 X：
  1. 列出【设计上需要读 X 的消费者】，标注各自所在项目（Admin / Auditor / Enterprise）
  2. 若消费者集合 ∩ {Admin, Enterprise} ≠ ∅   →  X 必须在 Shared        （因 C2 / C4）
  3. 若消费者集合 ⊆ {Auditor}                  →  X 可留 Auditor
  4. 再看 X 的语义：领域实体（企业/文档/标准）倾向 Shared；端工作台实体（专家任务）倾向该端

对一个能力（服务 / 逻辑）Y：
  5. 列出【设计上需要 Y 的消费者】。若 ≥2 个端 ⇒ Y 的目标落点是 Shared（V2：允许查库）
  6. 拆 Y：【不碰 DB 的内核】与【碰 DB 的读取/组装】分开
     - 内核（纯函数）→ 必须进 Shared（可单测、可重放）
     - 查库部分   → 也进 Shared/Services/，但必须是【薄适配器】（只做「查 + 组装」，不含业务判断）
  7. 若 Y 绑死了某个端的私有基础设施（如 Admin 的 SkillExecutor / SkillResult / CertSkillRegistry）
     ⇒ ⛔ 不要整体搬；只搬【能脱离该基础设施的那一层】（见 §6.1 批次 B″）
```

### D2 · 企业原始资料：**执行器读错表**（⛔ 2026-10-06 用户裁决改判：**不是重复设计**）

> ⛔ **改判说明（2026-10-06 用户裁决）**：本节原标题为「**两套表模型并存，且读方 ≠ 写方**」，并被归入「**重复设计**」。**该定性已作废。**

**⇒ 读方（Admin 执行器）读的是「**成品文档表**」，而设计上它应读「**原始资料表**」⇒ 把成品当原始资料喂给填充引擎。**

**这会怎么爆炸**：
1. `55` §4.2 要求执行器「**按画像召回**」⇒ 必须读 `cert_enterprise_doc_profile`（其输入是 `cert_enterprise_original_file`）
