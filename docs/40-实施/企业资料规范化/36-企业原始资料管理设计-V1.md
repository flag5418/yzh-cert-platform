## 〇、一句话定位

> 企业把**散乱原始资料**（标准无关）传上来 → 系统**自动转 PDF/Markdown** → **自动调用 33 号的提示词做语义分析** → 用户**查看 / 忽略 / 人工改标签与语义**，产出 L3 画像供后续匹配与填充只读。

### 1.1 版本管理语义（D7/D8 展开，与企业资料库逐条对齐）

| 场景 | 判定 | `VersionNumber` | MinIO 动作 | `cert_enterprise_original_file_version` | 画像 |
|---|---|---|---|---|---|
| **首次上传** | 无行 | `1` | `Upload(StoragePath, 字节)` | 不写 | `ProfileVersion=1` |
| **同名同 hash 重传** | `Sha256` 逐字相等 | **不变** | 字节覆盖（内容本已相同） | 不写 | **不变**（幂等，不浪费 LLM） |
| **同名不同 hash 重传**（= 替换） | `Sha256` 不同 | `+1` | ①`Rename(旧 → _archive/{名}.v{n})` ②`Upload(原 StoragePath, 新字节)` | **追加一行**（记 `StoragePath`=归档路径 / `FileSize` / `Sha256` / `Reason`） | `ProfileVersion+1`，旧版 `IsLatest=0` |
| **删除** | — | 不变 | 源 + `pdf/` + `markdown/` + 全部 `_archive/` 一并移除 | 一并软删 | 保留（`IsLatest` 不动，审计可查） |

> ⚠️ **归档路径不入库为主行 `StoragePath`**：主行恒指**当前活跃版**的原始路径（与 `EnterpriseFileService.cs:1181-1182` 同口径），归档路径只存版本表。这样预览 / 下载 / 分析链的路径**永不失效**。
> ⚠️ **二次归档必须抛异常**：`PathBuilder.Archive` 对已含 `_archive` 段的入参直接抛（`PathBuilder.cs:150-151`），状态机出错时必须响，不能静默。

## 三、数据模型

### 3.1 表① 🆕 `cert_enterprise_original_file`（26 号 §4.1⑤ 补全）

> **职责**：L1 层的 DB 侧登记 —— **文件生命周期**（上传/替换/转换/分析/策略）。
> ⛔ **不与画像合表**：换一次文件 ⇒ 本表 `VersionNumber+1`、画像 `ProfileVersion+1` **失效重算**（26 号 A-4）；合表会导致「版本与语义混在一起，无法判断画像是否过期」。

```sql
SET NAMES utf8mb4 COLLATE utf8mb4_general_ci;

CREATE TABLE `cert_enterprise_original_file` (
  `Id`               bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `Code`             varchar(36)  NOT NULL                COMMENT '业务键GUID',
  `CreateTime`       datetime     NOT NULL                COMMENT '创建时间',
  `CreateBy`         varchar(64)  DEFAULT NULL            COMMENT '创建人Code',
  `UpdateTime`       datetime     DEFAULT NULL            COMMENT '更新时间',
  `UpdateBy`         varchar(64)  DEFAULT NULL            COMMENT '更新人Code',

  -- ── 身份段（P13：NOT NULL DEFAULT ''，⛔ 禁 NULL）──
  `EnterpriseCode`   varchar(36)  NOT NULL DEFAULT ''     COMMENT '★企业Code → cert_enterprise.Code',
  `StageCode`        varchar(36)  NOT NULL DEFAULT ''     COMMENT '★阶段Code → cert_cert_stage.Code（第 3 级）',
  `OrgCode`          varchar(36)  NOT NULL DEFAULT ''     COMMENT '机构Code（冗余，P13）',

  -- ── 批次（upload/cancel 定位草稿行，见 §3.3）──
  `UploadTaskCode`   varchar(36)  NOT NULL DEFAULT ''     COMMENT '当前激活上传批次 → cert_enterprise_original_upload_task.Code；空=不属任何批次',

  -- ── 文件 ──
  `RelFolderPath`    varchar(512) NOT NULL DEFAULT ''     COMMENT '相对 {Ent}/{Stage}/ 的文件夹路径，/ 分隔，空串=根。⛔ 不入唯一索引（3072B 上限）',
  `FileName`         varchar(300) NOT NULL DEFAULT ''     COMMENT '文件原名（含扩展名）',
  `FileType`         varchar(20)  NOT NULL DEFAULT ''     COMMENT '扩展名（小写，含点，如 .docx）',
  `FileSize`         bigint       NOT NULL DEFAULT 0      COMMENT '字节数',
  `Sha256`           varchar(64)  NOT NULL DEFAULT ''     COMMENT '★当前版内容指纹 —— D7 变更判定唯一依据（hash 不变=同一文件=幂等）',
  `StoragePath`      varchar(512) NOT NULL DEFAULT ''     COMMENT '★MinIO 源路径（恒指当前活跃版 ⇒ 外部引用永不失效）',
  `VersionNumber`    int          NOT NULL DEFAULT 1      COMMENT '★替换递增；旧字节走 PathBuilder.Archive（_archive/{名}.v{n}）',

  -- ── 转换（枚举对齐 cert-share/src/utils/convertStatus.ts:11-18，⛔ 不得写 converted）──
  `ConvertStatus`    varchar(20)  NOT NULL DEFAULT 'none' COMMENT 'none/pending/converting/completed/failed/unsupported',
  `ConvertMessage`   varchar(1024) DEFAULT NULL           COMMENT '失败原因',
  `PreviewPdfPath`   varchar(512) DEFAULT NULL            COMMENT 'PDF 产物（PathBuilder.Product 派生）',
  `MarkdownPath`     varchar(512) DEFAULT NULL            COMMENT '★Markdown 产物（语义分析输入）',
  `MarkdownStatus`   varchar(20)  NOT NULL DEFAULT 'none' COMMENT 'none/pending/converting/completed/failed/unsupported',
  `MarkdownMessage`  varchar(1024) DEFAULT NULL,
  `ConvertDate`      datetime     DEFAULT NULL            COMMENT '双产物完成时间',

  -- ── 分析 ──
  `AnalyzeStatus`    varchar(20)  NOT NULL DEFAULT 'pending' COMMENT 'pending/analyzing/analyzed/failed/skipped',
  `AnalyzeMessage`   varchar(1024) DEFAULT NULL           COMMENT '失败原因 / 跳过原因',
  `AnalyzeTime`      datetime     DEFAULT NULL            COMMENT '最近分析完成时间',

  -- ── 分析策略（26 号 §3.5.3 补 6）──
  `AnalyzePolicy`    varchar(20)  NOT NULL DEFAULT 'analyze' COMMENT 'analyze/skip/ignore —— L2 数据来源层，⛔ 非文件级删除',
  `PolicyReason`     varchar(30)  DEFAULT NULL            COMMENT 'covered_by_params/irrelevant/duplicate/manual',
  `PolicySource`     varchar(10)  DEFAULT NULL            COMMENT 'ai（建议）/ manual（人工确认）',
  `PolicyDecidedBy`  varchar(64)  DEFAULT NULL            COMMENT '留痕',
  `PolicyDecidedTime` datetime    DEFAULT NULL            COMMENT '留痕',

  `Remark`           varchar(500) DEFAULT NULL,
  `IsDeleted`        tinyint(1)   NOT NULL DEFAULT 0      COMMENT '软删除',
  `DeleteBy`         varchar(64)  DEFAULT NULL,
  `DeleteTime`       datetime     DEFAULT NULL,
  `IsValid`          int          NOT NULL DEFAULT 1      COMMENT '★1有效0无效（铁律九，禁 Enable）',

  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_code` (`Code`),
  -- ⛔ 曾经尝试 uk_ent_stage_path(EnterpriseCode,StageCode,RelFolderPath,FileName)
  --    = (36+36+512+300)×4 = 3536 B > InnoDB DYNAMIC 行格式上限 3072 B
  --    MySQL 8.0.46 实跑：ERROR 1071 Specified key was too long
  --    ⇒ 定位改走下面这条普通索引 + 应用层 Sha256 判重（D7）
  KEY `idx_ent_stage_path` (`EnterpriseCode`,`StageCode`,`RelFolderPath`(191),`FileName`(120)),
  KEY `idx_ent_stage` (`EnterpriseCode`,`StageCode`),
  KEY `idx_sha256` (`Sha256`),
  KEY `idx_upload_task` (`UploadTaskCode`),
  KEY `idx_analyze_status` (`AnalyzeStatus`),
  KEY `idx_policy` (`AnalyzePolicy`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='企业原始资料索引（L1 文件生命周期 + 当前活跃版 + 分析策略）';
```

**设计要点**

| # | 要点 | 说明 |
|---|------|------|
| 1 | **唯一键只有 `Code`**（D9） | 与铁律四、基座其余 40+ 表一致。⛔ 任何定位/删除/更新传 `Code` |
| 2 | **⛔ 不建 `(Ent,Stage,Path,FileName)` 唯一键**（D7） | 4 列联合索引 3536 B > 3072 B 上限，实跑 `ERROR 1071`。本仓已有同类教训：`20260926_standard_directory_rebuild_V1.sql` 把 `FullPath` 从 1024 收窄到 500 正是注释里写的「唯一索引长度上限」 |
| 3 | **判重 = 应用层两段式** | ①`idx_ent_stage_path` 前缀索引收窄命中候选（`RelFolderPath(191)`+`FileName(120)` 前缀足以区分，真同路径必然命中）→ ②逐行比 `Sha256` 逐字相等则幂等跳过，不等则走替换（D8） |
| 4 | **同名不同文件 = 同一行 `VersionNumber+1`**，旧字节 `PathBuilder.Archive` 走 `_archive/{名}.v{n}` | 与 `enterprise-documents` **零新逻辑同构**（对照 `EnterpriseFileService.cs:1179-1246`） |
| 5 | **不建 `IngestStatus`** | 总进度由 `ConvertStatus` + `AnalyzeStatus` 推导；多一列就多一个可能不同步的状态源 |
| 6 | **不建 `Enable`** | 铁律九，启用唯一字段 = `IsValid` |
| 7 | **策略列是 L2 不是 L0/L1** | 见 §3.5 三层区分 |
| 8 | **身份段禁 NULL** | 定位索引含 `EnterpriseCode`/`StageCode`，NULL 会让索引与判重同时失效，静默产生重复行 |
| 9 | **初始状态一律 `none`** | 草稿行尚未入队，用 `none` 而非 `pending`（与既有 `cert_standard_directory_file.markdown_status` 一致，且 `none` 已在 `convertStatus.ts` 字典内） |

### 3.3 表③ 🆕 `cert_enterprise_original_upload_task`（批次表，`upload/cancel` 定位草稿行）

> **为什么必须有**：§5.1 的五段式上传要求 `upload/cancel` 能「撤草稿行」，但表① ⛔ 不能拿批次号当唯一键（否则一批 N 个文件互相覆盖一个 `TaskId`），必须另立批次表。
> **对标物**：`cert_upload_task` + `EnterpriseFileService.GetDraftRowAsync(fileCode, taskId)`（`:2030`）—— 本表是它在原始资料域的对等物。

```sql
CREATE TABLE IF NOT EXISTS `cert_enterprise_original_upload_task` (
  `Id`             bigint       NOT NULL AUTO_INCREMENT COMMENT '主键ID（⛔零语义）',
  `Code`           varchar(36)  NOT NULL                COMMENT '★批次业务键 GUID（= TaskId，唯一键）',
  `CreateTime`     datetime     NOT NULL,
  `CreateBy`       varchar(64)  DEFAULT NULL,
  `UpdateTime`     datetime     DEFAULT NULL,
  `UpdateBy`       varchar(64)  DEFAULT NULL,

  `EnterpriseCode` varchar(36)  NOT NULL DEFAULT ''     COMMENT '★企业Code',
  `StageCode`      varchar(36)  NOT NULL DEFAULT ''     COMMENT '★阶段Code',

  `TotalFiles`     int          NOT NULL DEFAULT 0      COMMENT '计划份数',
```

**最终设计（三次踩坑收敛出的结论）**

```
上传 confirm
  └─ 建 ingest 队列（N 个任务，逐文件转换）
       └─ 每个任务转换成功 → 调 EnsureAnalyzeQueuedAsync(批次号)
            ├─ 幂等检查：本批次已有 analyze 队列 ⇒ 跳过
            ├─ 全批到达终态？否 ⇒ 跳过（等下一个任务）
            ├─ 至少一份有 Markdown？否 ⇒ 跳过
            └─ 是 ⇒ 建**一个** analyze 队列（带整批 FileCodes）
                 └─ doc_group 一次扫整批 + doc_content 逐份 ⇒ 画像 upsert
```
实测：ingest **1** 个 + analyze **1** 个队列，`doc_group` **恰好 1 次/批**，`doc_content` 每份 1 次。

**其余 3 处同源缺陷（一并修）**：`YzhQueue` 有**两个**码（`Code` GUID 业务键 / `QueueCode` `Q-2026...`）⇒ 队列明细用错码导致任务列表恒空；SqlSugar 的闭包 `List.Contains` 翻译不可靠（**本模块第 3 次**静默返回空集，已全部改内存过滤）；`guards R17` 未排除注释 ⇒ 把「注释里提到某实体」误判成分层倒退。

**实测抓出并修掉的 4 个真实缺陷**

| # | 缺陷 | 症状 | 修法 |
|---|------|------|------|
| **B1** | `init` 把前端声称的 sha 写进 `Sha256` | **首传被误判「幂等跳过」⇒ 文件永远传不上去** | `Sha256` 语义收紧为「**已落库字节**的指纹」，`init` 一律留空；`upload/file` 的幂等复核加「已存 Sha256 非空」前置条件 |
| **B2** | `stage-tree` 用 `stageCodes.Contains(x.StageCode)` | 左树**永远只有企业没有阶段**（静默空树） | `CertStage` 有两个 Code 语义：`Code`（GUID 业务键）与 `StageCode`（slug `jd01/03`）；关联表存的是 `Code` ⇒ 改比 `x.Code`。★ 与 AGENTS.md ③「字段名逐字一致」同类错误的另一个变种 |
| **B3** | 多标准时按「字典序最小」取作用域 | 选中**没绑提示词**的标准 ⇒ 分析报「未找到生效的 doc_content」 | `ResolveScopesAsync` 返回**候选列表**（关联先后）· `PickScopeAsync` 逐个回退到第一个能解析到提示词的 |
| **B4** | `upload/file` 直接比 multipart 的 filename | 客户端传**本地全路径**时误判「改名」拒绝 | 先 `Path.GetFileName` 取末段再比 |

另把 14 处 `GetListAsync` 改为 `_db.Client.Queryable` 显式查询 —— SqlSugar 对「谓词里闭包捕获的 `List<string>.Contains`」翻译不可靠（实测静默返回空集，不报错、日志无痕）。
