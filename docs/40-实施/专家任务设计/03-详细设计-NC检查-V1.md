## 一、业务语义

### 1.1 NC 检查是什么

对一家企业的某个认证阶段，依据该阶段**关联标准**的条款要求，检查企业的体系文件与记录是否满足要求，产出三类结果：

| 判定 | 含义 | 后果 |
|---|---|---|
| `conform` 符合 | 企业满足该条款要求 | 记录留痕，不产生 NC |
| `nonconform` 不符合 | 企业不满足该条款要求 | **生成 NC 记录**（`cert_nc`） |
| `observation` 观察项 | 未构成不符合，但有改进空间 | 记录留痕，可生成观察项 NC（严重度=observation） |
| `na` 不适用 | 该条款对本企业不适用 | 记录留痕，需专家手工判定 |

### 1.2 NC 记录四要素（`ISO体系认证NC与报告标准约束-V1.md:38-48`）

| 要素 | 映射到 `cert_nc` | 来源 |
|---|---|---|
| 审核准则 | `RequirementRef` | `cert_iso_clause` 条款原文（`clause_content`） |
| 不符合描述 | `Description` | 工作流 AI 判定产出 + 模板 `NcDescriptionTemplate` |
| 客观证据 | `EvidenceRef` | 提取结果引用（D08：本期只存引用，不做字段级下钻 UI） |
| 严重度 | `Severity` | `cert_validation_rule.SeverityIfViolated` 预设 + 专家可改 |

### 1.3 符合项也留记录（D13）

**为什么符合项必须落库**：

| 收益 | 说明 |
|---|---|
| 可证明检了什么 | 认证审核的基本要求：能说清"审核了哪些条款、依据什么" |
| 防止漏检 | 若只存不符合项，条款表有 69 条但只跑出 5 个 NC，无法区分"检查后符合"和"根本没检查" |
| 支持导出 | Excel 报告需要全量检查结论，不只是问题清单 |
| 支持重跑对比 | 重新执行时可对比前后差异 |

**落哪张表**：`audit_checklist_item`（**已存在但无实体**，`all_tables_ddl.sql:23-62`）。该表已有 `Conformity enum('pending','conform','nonconform','observation','na')` 字段定义，语义完全匹配。

> **决策：符合项落 `audit_checklist_item`（条款级）还是 `cert_expert_nc_result`（规则级）？**
>
> 两者粒度不同：`audit_checklist_item.ClauseCode` 是**条款级**（一个条款可能有多条 NC 规则），`cert_expert_nc_result.ItemCode` 是**规则级**。
>
> **方案：`cert_expert_nc_result` 是唯一结果表**（已按 D11 统一），`audit_checklist_item` **不启用**。理由：
> 1. 统一表是 D11 的核心收益，拆两张表会破坏认可/日志/导出的一致性
> 2. `audit_checklist_item` 没有 `StandardCode` —— 多标准阶段下**无法区分是哪条标准**的检查项，而多标准认证正是本系统的核心场景
> 3. `audit_checklist_item.TaskCode` FK 指向已废弃的 `audit_task`
>
> → **`audit_checklist_item` 标记废弃**，与 `audit_task` 一并处理（见 [README §5.3](README.md)）。`Conformity` 枚举值移植到 `cert_expert_nc_result.Conformity`。

## 二、执行链路

### 2.1 数据流

```
cert_expert_task_queue_item.Payload
  {
    "TaskItemCode": "...",
    "ItemType": "nc_check",
    "RuleCode": "<cert_validation_rule.Code>",     ← 注意是 Code 不是 RuleCode
    "WorkflowCode": "<wf_workflow_definition.Code>",
    "EnterpriseCode": "...", "StandardCode": "...", "StageCode": "...",
    "ExtractVersionStamp": "20260929-1430"        ← ★ 文件版本戳，见 §2.3
  }
        │
        ▼
① 读取规则快照（执行开始时取一次，避免规则中途被改导致结果与配置不符）
   SELECT vr.Code, vr.RuleCode, vr.RuleName, vr.RuleNameEn, vr.SeverityIfViolated,
          vr.JudgeMode, vr.NcDescriptionTemplate, vr.RuleJson, vr.WorkflowCode,
          c.Code AS ClauseCode, c.ClauseNumber, c.ClauseTitle, c.ClauseContent
   FROM cert_validation_rule vr
   LEFT JOIN cert_iso_clause c ON c.Code = vr.ClauseCode
   WHERE vr.Code = @ruleCode AND vr.IsValid = 1
        │
        ▼
② 缺数据预检（02 号 §2.4）
   有未解决 gap → MarkSkipped(data_gap / data_gap_skipped)，结束本项
        │
        ▼
③ 判 JudgeMode
   'manual' → MarkSkipped(manual_mode)，结束本项
   'auto' / 'semi' → 继续
        │
        ▼
④ 跑 WorkflowInterpreter.RunAsync(dag, context)
   context.ExtractionData ← EnterpriseExtractionResultStore.GetActiveAsync(
                                 EnterpriseCode, StandardCode, StageCode)
        │
        ▼
⑤ 结果归一化（★ 关键：AI 输出的不确定性必须在这里收口）
        │
        ▼
⑥ 写 cert_expert_nc_result + （若 nonconform）INSERT cert_nc
```

### 2.2 结果归一化（⑤）

AI 节点输出的是自由文本/JSON，必须归一化成 `audit_checklist_item` 语义的三个标量。**归一化失败的处理不能是"静默取默认值"** —— 那会产出假结论。

```csharp
async Task<AiNcResult> NormalizeAsync(string aiOutput, NcRuleSnapshot rule)
{
    // ① 尝试解析为结构化 JSON
    //    约定的输出契约（★ 写进 Prompt 模板，不是让 AI 自由发挥）：
    //    {
    //      "conformity": "conform|nonconform|observation|na",
    //      "severity":   "major|minor|observation",   // 仅 nonconform/observation 时需要
    //      "description": "不符合事实描述（客观、可核查）",
    //      "evidence":    "客观证据引用（文件+字段）",
    //      "requirement": "违反的标准要求原文",
    //      "confidence":  0.0-1.0
    //    }
    if (!TryParseAiNcResult(aiOutput, out var parsed))
    {
        // ★ 解析失败 ≠ 判定为符合！
        //   置为「需人工判定」，让专家自己填，而不是编一个结论
        return AiNcResult.NeedsManual(aiOutput);
    }

    // ② 枚举白名单校验（AI 可能吐出 "符合"/"CONFORM"/"不适用" 等变体）
    parsed.conformity = NormalizeConformity(parsed.conformity);
    if (parsed.conformity == null)
        return AiNcResult.NeedsManual(aiOutput, "AI 输出的判定值不在枚举范围");

    // ③ nonconform/observation 必须有 severity
    if (parsed.conformity is "nonconform" or "observation")
    {
        parsed.severity = NormalizeSeverity(parsed.severity)
                          ?? rule.SeverityIfViolated      // 回落到规则预设
                          ?? "observation";                // 再回落到最轻
        if (string.IsNullOrWhiteSpace(parsed.description))
            return AiNcResult.NeedsManual(aiOutput, "AI 未给出不符合描述");
    }

    // ④ 专家可改：AI 的 severity 只是建议
    //    → cert_expert_nc_result.Severity 初值 = AI 结果；改不改由专家决定
    return parsed;
}
```

**`NeedsManual` 的落库**：

| 字段 | 值 |
|---|---|
| `AutoStatus` | `failed` |
| `AutoResult` | `{ "rawOutput": "...", "reason": "AI 输出无法解析为结构化结论" }` |
| `Conformity` | `null`（**不预填**，等专家填） |
| `ReviewStatus` | `pending`（阻塞 O3 认可校验 → 强制专家介入） |
| 界面呈现 | 黄色提示「AI 未能给出结构化结论，请人工判定」，并显示 `AutoResult.rawOutput` 供参考 |

> **为什么不自动判成 `conform`**：这是认证审核系统，"AI 解析失败 → 静默通过"是最危险的失败模式。宁可阻塞也不能伪造结论。

### 2.3 文件版本戳（`ExtractVersionStamp`）

**问题**：任务执行期间（可能 10 分钟），企业文件被替换 → 提取结果归档旧版本、生成新版本（10 号分册 S2 的 `InvalidateActiveAsync`）→ 但业务锁 O1 应该在文件操作时拦截。

**双保险**：锁是第一道防线，但锁是**查询式**的（存在即锁），存在极短竞态窗口（检查通过 → 换文件 → 继续上传）。因此加第二道：

```csharp
// 入队时记录提取结果的版本戳
stamp = $"{MaxVersionOf(enterpriseCode, standardCode, stageCode)}-{CountOfActiveRows(...)}";

// 执行时比对
var current = ComputeStamp(...);
if (current != payload.ExtractVersionStamp)
{
    // 数据源在排队期间变了 → 该项结果不可信
    await MarkFailedAsync(taskItem.Code, new {
        ErrorType    = "permanent",
        ErrorMessage = "企业文件在任务执行期间发生变更，请重新执行该检查项",
    });
    return;
}
```

### 2.4 结论到 DB 的映射

```sql
-- NC 检查结果写入 cert_expert_nc_result
UPDATE cert_expert_nc_result
SET
  -- 自动结果
  AutoStatus      = 'ok',            -- ok | ng | skipped | failed
  AutoResult      = @autoResultJson, -- 完整 AI 输出痕迹（含 rawOutput / confidence）
  AutoSeverity    = @aiSeverity,
  AutoDescription = @aiDescription,  -- 便于对比"专家改成了什么"
  AutoEvaluatedAt = NOW(),
  -- 最终结果（自动执行后未经专家动，先落 AI 建议值）
  Conformity      = @aiConformity,
  Severity        = @aiSeverity,
  ContentText     = @aiDescription,
  -- 认可状态：仍是待认可
  ReviewStatus    = 'pending',
  UpdateTime      = NOW()
WHERE Code = @taskItemCode AND ReviewStatus = 'pending';
```

> `AutoDescription` 与 `ContentText` 都存是**有意的冗余**：专家改 `ContentText` 后，`AutoDescription` 保留原 AI 输出，日志里记 diff。否则"改了什么"只能靠日志反推。

## 四、严重度（`Severity`）

### 4.1 三级定义（`ISO体系认证NC与报告标准约束-V1.md:28-36`）

| 值 | 含义 | 判定标准 |
|---|---|---|
| `major` 严重 | 体系性失效 | 某过程完全缺失/无文件/多个要求同时不满足，可能导致认证不能通过 |
| `minor` 一般 | 局部不符 | 某过程存在但执行不到位，不影响体系整体运行 |
| `observation` 观察 | 改进建议 | 未构成不符合，但有优化空间 |

### 4.2 严重度的三级来源（优先级从高到低）

```
① 专家手工指定（cert_expert_nc_result.Severity，改过则 IsModified=1，日志记 diff）
        ↑
② AI 判定输出（AutoSeverity）
        ↑
③ 规则预设（cert_validation_rule.SeverityIfViolated）
        ↑
④ 默认 observation（最轻，不冤枉企业）
```

> **为什么默认落 `observation` 而非 `major`**：§2.2 已说明，AI 解析失败时不预填结论。严重度同理 —— 没有依据时取最轻值，专家有权上调。

### 4.3 `SeverityIfViolated` 的填充

现状：`ValidationRule.json` 的配置页**不填**此字段（由引擎动态决定）。本设计保持这个约定：它作为**兜底预设**，由实施人员在后台配置时可选填写。

## 五、NC 记录（`cert_nc`）的生命周期

### 5.1 自动生成

```
当 cert_expert_nc_result 的最终 Conformity ∈ {nonconform, observation} 时：

INSERT INTO cert_nc (
  Code, OrgCode, TaskCode, ClauseCode, NcNumber, Severity,
  Description, RequirementRef, EvidenceRef,
  SourceType,          -- 'auto_rule'  ← 表定义已有此枚举
  SourceCheckCode,     -- ★ 改指 cert_expert_nc_result.Code（原 FK 指向已删除的 ent_file_compliance_check）
  RuleCode,            -- cert_validation_rule.Code
  Status,              -- 'open'
  OpenedBy, OpenedAt,  -- 专家 Code / NOW()
  IsValid, IsDeleted
)
```

**`SourceType` 的两种值**（表定义已有 `enum('auto_rule','manual')`）：

| 值 | 何时产生 |
|---|---|
| `auto_rule` | 工作流自动判定为 `nonconform`/`observation`，专家**未修改**就认可 |
| `manual` | 专家手工把结论改成 `nonconform`，或手工新建 |

> **`SourceType` 是审计的关键**：`auto_rule` + `IsModified=0` = 纯机器结论；`auto_rule` + `IsModified=1` = 机器建议 + 人工修正；`manual` = 纯人工。导出与追溯时这三类的可信度完全不同。

### 5.2 NC 编号

```
格式：NC-{TaskNumber去前缀}-{标准Code}-{序号:D2}
示例：NC-20260929-0001-ISO9001-01

★ 唯一键：uk_nc_number (NcNumber)  ← 表定义已有
★ 不用 Id 参与任何查询（铁律九）
```

### 5.3 专家修改结论时，NC 记录如何同步

这是最容易出错的地方。**`Conformity` 改动 → NC 记录的存亡随之变化**：

```
专家 modify Conformity：

原值            新值              cert_nc 动作
────────────────────────────────────────────────────────────
nonconform    → conform          软删（IsDeleted=1）★ 撤销了这条 NC
observation   → conform          软删
conform       → nonconform       ★ 新建（SourceType='manual'）
conform       → observation      ★ 新建（SourceType='manual'）
na            → nonconform       ★ 新建（SourceType='manual'）
nonconform    → observation      改 Severity 为 observation（不删不建）
nonconform(major) → nonconform(minor)  改 Severity
conform       → conform          无 NC 变化（只改说明文字）
```

**为什么不物理删 NC**：审核过程中结论可能反复改（先判不符合，看完证据改成符合；又发现新证据改回不符合）。软删 + 每次都记 `cert_expert_task_log` 能完整还原过程。`cert_nc` 表已有 `IsDeleted` 字段。

**同步实现**：

```csharp
async Task SyncNcAsync(string taskItemCode, string oldConformity,
                       string newConformity, string oldSeverity, string newSeverity,
                       NcRuleSnapshot rule, UserInfo user)
{
    var existing = _ncRepo.GetByTaskItemCode(taskItemCode);   // 通过 SourceCheckCode

    bool needNc = newConformity is "nonconform" or "observation";
    bool hadNc  = existing != null && !existing.IsDeleted;

    if (!needNc && hadNc)
    {
        // 撤销
        _ncRepo.SoftDelete(existing.Code, user.Code);
        _ncLogRepo.Write(existing.Code, "CANCEL", user);
    }
    else if (needNc && !hadNc)
    {
        // 新建
        _ncRepo.Insert(BuildNc(taskItemCode, newConformity, newSeverity, rule, user));
    }
    else if (needNc && hadNc)
    {
        // 更新
        if (existing.Severity != newSeverity)
            _ncRepo.UpdateSeverity(existing.Code, newSeverity, user);

        // ★ 还要更新 SourceType
        //   专家改过 → 'manual'（哪怕原来是 auto_rule）
        if (existing.SourceType == "auto_rule" && taskItem.IsModified)
            _ncRepo.UpdateSourceType(existing.Code, "manual", user);
    }
}
```

### 5.4 NC 记录只在本期做到"开具"

| 阶段 | 表 | 本期 |
|---|---|---|
| 发现 → 记录 | `cert_nc` | ✅ 本期实现 |
| 整改 | `audit_rectification` | ❌ 另一功能域 |
| 跟踪验证 | `audit_rectification` | ❌ |
| 关闭 / 升级 | `ClosedAt` 字段 | ❌ |

> 本期导出的 NC 检查报告 Excel 包含"不符合项明细"Sheet，但**不含整改跟踪列**。这是有意的功能边界，见 09 号分期计划 S6。

## 六、`JudgeMode` 三值的处理

`cert_validation_rule.JudgeMode`（`fix-add-judge-mode-2026-09-25.sql` 加列，default `'auto'`）：

| 值 | 含义 | 本期处理 |
|---|---|---|
| `auto` | 全自动 | 正常工作流 → AI 判定 → 专家认可 |
| `semi` | 半自动 | **等同 `auto`**，但界面高亮提示"AI 结论仅供参考，请重点复核" |
| `manual` | 纯人工 | `MarkSkipped(manual_mode)`，界面单独分区，允许专家手工录入结论 |

> **`semi` 的差异化处理**：不改执行逻辑，只改界面强调。这样避免为 `semi` 引入第二套执行路径（一套逻辑三种值已经足够）。

**`manual` 模式在界面上的位置**（08 号 §4.4）：

```
任务项列表
├── 已自动判定区（AutoStatus ∈ ok/ng）
│   └── 每条：结论 + 严重度 + 说明 + [认可] [修改]
├── 缺数据跳过区（SkipCategory = data_gap / data_gap_skipped）
│   └── 只显示「缺乏必要数据」，不显示结果
├── 人工检查区（SkipCategory = manual_mode）★ 专家在这里填结论
│   └── 每条：条款 + 规则名 + [填写结论] → 填完转 modified
└── 执行失败区（SkipCategory = exec_failed）
    └── 显示错误摘要 + [重试该项]
```

## 七、跳过语义的 NC 侧表现

D05 要求"缺数据的规则自动不执行，并告知缺乏必要数据，不显示结果"。落到 NC 工作台：

| 展示维度 | 内容 |
|---|---|
| 结果区 | **空白**（不显示 `AutoResult`、不显示 `Conformity`、不显示 AI 的任何输出） |
| 状态标签 | 灰色「数据不足，未检查」 |
| 提示文案 | `SkipReason` 全文，如"该规则缺乏必要数据：缺少 质量手册、程序文件" |
| 操作按钮 | [去补录]（跳补录清单页）· [重新执行该项]（补录后） |
| 导出 Excel | 计入"检查项总数"，但结论列写「数据不足，未检查」，**不算作符合** |

> **Excel 导出的关键约定**：「数据不足，未检查」**绝不能被统计成"符合数"**。导出文件的汇总行必须分四类：符合 / 不符合 / 观察 / 未检查。混成三类会直接导致审核结论失真。

## 八、Excel 导出的 NC 部分

### 8.1 Sheet 划分（D09：一个标准一个 Sheet）

| Sheet 名 | 内容 | 行数级 |
|---|---|---|
| `{标准Code}` | 该标准下**全部**检查项结论表 | 20-40 行 |
| `汇总` | 跨标准统计 | 汇总行 |

> 单标准阶段时 Sheet 名为 `ISO9001` + `汇总` 两个。

### 8.2 检查项 Sheet 列定义

| 列 | 来源 | 宽度 | 备注 |
|---|---|---|---|
| 序号 | `Sort` | 6 | |
| 条款号 | `ClauseNumber` | 10 | 如 `8.4` |
| 条款标题 | `ClauseTitle` | 30 | |
| 规则编号 | `RuleCode` | 18 | `NC-ISO9001-001` |
| 规则名称 | `RuleName` | 30 | |
| 审核方式 | `JudgeMode` 映射 | 10 | 自动/半自动/人工 |
| 判定结论 | `Conformity` 映射 | 12 | **符合/不符合/观察项/不适用/数据不足，未检查** |
| 严重度 | `Severity` 映射 | 10 | 严重/一般/观察项/— |
| 不符合描述 | `ContentText` | 50（自动换行） | |
| 证据引用 | `cert_nc.EvidenceRef` | 30 | |
| 结论来源 | `SourceType` + `IsModified` | 12 | **自动规则/自动规则（已修改）/人工录入** |
| 审核专家 | `ReviewByName` | 12 | |
| 认可时间 | `ReviewTime` | 18 | `yyyy-MM-dd HH:mm` |

**样式约定**：
- 表头：加粗 + 灰底 + 冻结首行 + 自动筛选
- 判定结论列：不符合=红字、观察项=橙字、数据不足=灰字+斜体
- 列宽自适应上限 50
