## 一、你的 3 部分设计 —— 整体判断：✅ 成立

### 1.1 架构本质：这是「执行实例」与「业务实体」分离

```
【任务系统】          一次执行 = 一个容器（企业 + 阶段 + 类型）
   │  写：创建 / 提交 / 看进度 / 归档·作废·取消
   ▼
【检查项实体】        长期存在，跨任务、跨年度   ← ★ 这是全设计最关键的一层
   └─【结果轮次】     每次执行产生一轮（可 N 轮）
   ▼
【NC 检查记录】【系统认证报告】   读：看结论 / 认可 / 修改 / 导出
```

**为什么这个分离是对的**（这是整套设计最大的亮点，不是细节）：

| 若不分 | 会怎样 |
|---|---|
| 把"检查项"当成"任务的一次性记录" | **无法表达"沿用"** —— 而 11 号 §4 的实测数据显示：**同一个检查项跑过 15 轮**。监督审核没查的条款不能说"这次也查了"（D30），必须有"实体 + 多轮"才能表达 |

→ **这不是"多加了一张表"，而是"能不能表达真实业务"的分水岭。** 你这一步做对了。

## 四、你问的第 1 点：部门配置到底多繁琐？

### 4.1 直接回答：**不需要"每个 NC 检查项 × 每个企业"配一遍**

**你担心的那个笛卡尔积配置，在设计上是存在的，但在落地方式上是不需要的。** 正确做法是**三层，各配一次**：

| 层 | 配什么 | 配几次 | 举例 |
|---|---|---|---|
| **① 规则层**（后台，全局） | 每条规则 → 责任部门 | **一次**（所有企业通用） | "8.4 外部提供" → **采购部** |
| **② 企业层** | 该企业有哪些部门 | **每企业一次**（5-10 行） | XX公司：管理层 / 采购部 / 生产部 / 品质部 |
| **③ 结果层** | 自动带出 + 对不上时改一次 | **不需要主动配** | 规则带出"采购部"；若该企业没这个部门名 → 落"待确认"，专家认可时改 → **回写②** |

```
后台配规则 → 8.4 → 采购部        ← 配 1 次
                              ↓
新企业建档 → 配 5-10 行部门清单    ← 配 1 次
                              ↓
跑 NC 检查 → 自动带出"采购部"      ← 不配
            名字对不上 → 待确认，专家改 1 次
```

> ★ **关键**：**"每个检查项归属哪个部门"是在规则层配的（全局一次），不是在结果层配的。**
> 所以 **每家企业你只需要维护一份部门清单（5-10 行）**，不是"检查项 × 企业"。
