### 2.2 ★★★ P0-2 17 号「实测基线」含误诊 —— 且是全册的头号阻塞项

**17 号 §二 E-1 声称**（原话）：

> 「`SqlSugarDbOrm` 的 `IsValidCondition<T>()` 自动追加 `WHERE IsValid=1` → **这两条规则永远查不出来**」
> 「修复 SQL：`UPDATE cert_validation_rule SET IsValid = 1 WHERE IsValid IS NULL;`」

**10 号 §一 B1** 据此升级为「**阻塞编码**」第 1 项；**13 号 E0-0a** 据此列为「★★★ 基线纠正」。

#### ❌ 实测复核：不成立

**证据 1 —— ORM 的守卫条件**（`YZH.Core.DataBase/Implementations/SqlSugarDbOrm.cs`）：

```csharp
// :494-505
private static bool IsDeclaredOnType<T>(string propertyName) where T : class, new()
{
    var prop = typeof(T).GetProperty(propertyName);
    if (prop == null) return false;
    ...
    // 检查 DeclaringType：是否在当前类型自身声明（而非 BaseEntity）
    return prop.DeclaringType == typeof(T);      // ★ 关键
}

// :525-528
private static Expression<Func<T, bool>> IsValidCondition<T>() where T : class, new()
{
    if (!IsDeclaredOnType<T>(nameof(IIsValid.IsValid)))
        return _ => true;                        // ★ 实体没声明 → 恒真 → 不过滤
    ...
}
```

**证据 2 —— 实体确实没声明**（`CertPlatform.Shared/Entities/Cert/ValidationRule.cs`）：

```csharp
[SugarTable("cert_validation_rule")]
public class ValidationRule : BaseEntity        // ← 没有 IIsValid，也没有 IsDeleted
{
    public bool IsActive { get; set; } = true;   // :86  ★ 只有 IsActive
}
```

**证据 3 —— 代码自己写明了**（`ValidationRuleController.cs:210` 注释原文）：

> 「按 Code 置 IsActive（ValidationRule 用 bool IsActive 做启用开关，**实体无 IsValid 字段**）」

**结论**：`IsDeclaredOnType<ValidationRule>("IsValid")` → `GetProperty` 返回 null → `false` → `IsValidCondition` 返回 `_ => true` → **查询不带 `IsValid=1`**。这两条规则**今天完全查得出来**，`IsValid IS NULL` 当前**无害**。

> 讽刺的是：**17 号 §4.1 自己引用了 `:523-535` 的守卫注释**（「仅当实体声明了 `IsValid` 属性时才生效」），却没把它套到 `ValidationRule` 上。**证据在文档里，结论却错了。**

#### ✅ 正确处理（结论相同，理由与顺序不同）

| 项 | 17 号 的说法 | 实际情况 |
|---|---|---|
| 现在的危害 | 规则被永久屏蔽 | **无危害**（不过滤） |
| 真正的危害 | —— | ★ **反向的**：一旦按 E1-2 让 `ValidationRule` 实现 `IIsValid`，过滤**当场生效**，那 2 行 `NULL` 立刻「消失」→ **同一张表，改代码前能看见、改代码后看不见，且无任何报错** |
| 因此 | E0-0a 先做 | ✅ **顺序对**（数据先回填，再改实体），但**理由要改** |

> ⚠️ **连带风险（比原问题更严重）**：如果**只回填数据、不实现 `IIsValid`**（或反之），系统会长期处于「DB 有 `IsValid` 列但 ORM 不读」的状态 —— 这正好命中你已在 `REFERENCE.md §二十㉚` 登记的陷阱：**「软删/启用过滤只在『属性声明在实体自身』时生效 ⇒ 上提到 `BaseEntity` ⇒ 全库过滤静默失效」**。
>
> **本册 11 张新表的固定列模板若把 `IsValid` 放在 `BaseEntity`，同样会静默失效。** 13 号 E2-1 只验了「列存在」，**没验「过滤生效」**。

**建议新增一条验收**（成本 5 分钟）：

```bash
# 断言：实体自身声明 IsValid 的，查询真的带上了过滤
# 做法：把某行 IsValid 置 0，用该实体的列表接口查，必须查不到
```

### 2.4 ★★★ P0-4 12 号对「任务完成」给了两个定义

| 出处 | 定义 |
|---|---|
| 12 号 §3.2 | 完成 = `ExecStatus=completed` **且** `ReviewStatus=reviewed` **且** `LifecycleStatus ∈ {active, archived}` |
| 12 号 §3.5 | 完成 = `ExecStatus=completed` **且** `LifecycleStatus ∈ {active, archived}`（**去掉了 `ReviewStatus`**） |
| README **D12** | 「**所有结果必须经专家手动认可**，必须有认可记录。**无认可 = 任务不可批准**」 |

**冲突实质**：跑完但专家没认可的任务，**算不算「完成」**？

- 按 §3.2 → 不算 → 业务锁继续生效 → 该企业该阶段**不能做下一件事**
- 按 §3.5 → 算 → 业务锁释放 → 但 D12 又说「必须有认可记录」

**且 §3.5 的理由本身可疑**：「全部已认可」是检查项级别的状态，任务可能部分认可部分没认可，任务本身照样"完成" —— 这与 D12「所有结果必须经专家手动认可」在**同一册内**互相抵消。

**建议裁决**：任务**执行完成**（机器语义）与**任务结束**（业务语义）分开命名，业务锁认「任务结束」。否则「跑完了没人看」的任务会永久占锁。
