## 零之二、★ 定位澄清（2026-09-30 用户补充）与结论重定性

### 澄清内容（用户原话）

> 「1、所有的 nc 其实对应企业的部门的是吧，我们自动检查出来的 nc 应该告知哪个部门？
> 2、**我们的结论不是正式报告**，我们的系统现在的目标是**辅助系统**，是通过规则设置，通过流程，自动将企业的资料按 nc 规则、报告规则，形成**自动判断的结果**，**并不能替代正式报告**。」

### 这个定位**印证**了什么（不是削弱，是加强）

| # | 结论 | 为什么被加强 |
|---|---|---|
| **1** | ★★★ **部门维度是硬需求，而且比我原来判断的更硬** | 你自己问了「自动检查出来的 NC **应该告知哪个部门**」—— 说明你要的是**系统主动给出部门**，不是留个空列让人填。辅助系统的产出物就是给审核员用的判断结果，审核员拿到一条 NC 的第一动作是"这条该找谁核实/派给谁"。**没有部门，这条结论就是半成品** |
| **2** | ★★★ **`JudgeMode` 必须按「审核方法」划分** | 你的原话限定了系统的能力边界：「自动将**企业的资料**按规则形成自动判断结果」。**只能对"企业的资料"自动判断** → 即**只有「查阅文件/记录」这一类审核方法可自动化**。现场观察、访谈**永远不在这个系统里**（没有数据源）。这正好证明 `JudgeMode` 的语义应该是**审核方法**，而不是"自动化程度" |
| **3** | ★★ **观察项必须与 NC 分开** | 辅助系统输出给审核员，必须让他一眼分清"这是不符合（要整改）"还是"这只是改进建议"。混在一起会误导审核员对问题量级的判断 |

### 这个定位**降级**了什么（我原来的部分结论作废）

| 原编号 | 原结论 | 重定性 |
|---|---|---|
| §2.6 `EvidenceRef` 证据栏为空 | 判为「**违反 ISO 17021-1 §9.4.4.2 的合规缺口**」 | ⬇️ **不再是合规问题**（导出物不是正式报告，§9.4.4.2 的 shall 不适用）。**但理由要换成「可用性」**：辅助系统的核心价值就是让审核员**快速核对 AI 判得对不对**。证据栏为空 → 审核员要自己去翻文件 → **辅助价值大打折扣**。**建议仍然做**（0.2 人天，数据已在引擎里） |
| §2.8 报告章节无「必备章节」约束 | 判为「**违反 ISO 17021-1 §9.4.6 的 shall**」 | ⬇️ **从"合规强制"降为"业务建议"**。但仍有理由做：若缺「审核结论」章节，**辅助判断就失去了落点**（判断完了没地方形成结论）。建议降级为**软提示**（缺必备章节时告警），不做硬拦截 |
| §2.9 `degraded` 章节导出无标记 | 判为「**审核事故风险**」 | ⬇️ **风险等级下调**（不会交付给客户）。但**保留建议**：混入"审核发现应包含……"这类示例文字会**误导审核员本人**，导出时仍应标记 |
| §5.3-3 审核员署名 / 审核组 / 报告分发 | 判为「**需要明确边界**」 | ✅ **边界已明确**：导出物 = **内部工作底稿/判断结果**，非正式报告 → **这些都不需要**。⛔ 不再是缺陷 |

### ⚠️ 但定位澄清带来 **2 个新要求**（原报告未覆盖）

| # | 新要求 | 理由 | 成本 |
|---|---|---|---|
| **N-1** | ★★ **把定位写进文档与界面**（免责边界） | 现在菜单叫「**系统认证报告**」（12 号 D23/D31），措辞暗示它是报告。**必须显式声明这是"辅助判断结果"，不替代正式审核报告** —— 否则用户/客户会误当正式报告使用，责任不清。建议：菜单名改「**报告章节要点**」或「**报告草稿**」；导出 Excel 首页加一行声明 | 0.1 人天 |
| **N-2** | ★★★ **「一键看证据」是辅助系统的核心体验，不是"本期不做"** | 辅助系统的价值公式 = **AI 说 A，审核员 3 秒内能验证**。若做不到，就是"AI 说 A，审核员去翻文件" → 审核员不会用。而 D08 明确写「字段级追溯不是本期重点」。**这两者冲突，需要重新裁决** | 见下 |

**关于 N-2 的成本权衡**（供裁决）：

| 方案 | 做法 | 成本 | 效果 |
|---|---|---|---|

## 一、先肯定：对得上的部分（不要动）

评审要公允。以下设计**与 ISO 要求逐条对得上**，是这套文档最有价值的部分：

| # | 设计 | ISO 依据 | 判定 |
|---|---|---|---|
| 1 | **NC 四要素**（`RequirementRef` 准则 / `Description` 描述 / `EvidenceRef` 证据 / `Severity` 严重度） | ISO 17021-1 §9.4.4.2「每个 NC 记录**必须**包含」 | ✅ **完全对应** |
| 2 | **严重度三级** `major`/`minor`/`observation` | ISO 17021-1 §9.4.4.2（major/minor）+ 行业实践（observation） | ✅ 且**诚实标注了**「标准文本只明确区分 major 和 minor」 |
| 3 | **符合项也落库**（D13） | 认证审核要求"能说清审核了哪些条款、依据什么" | ✅ 理由写得比标准还清楚：「69 条只跑出 5 个 NC，无法区分'检查后符合'和'根本没检查'」 |
| 4 | **报告七要素**（目标/范围/准则/日期地点/组员/发现/结论） | ISO 17021-1 §9.4.6 | ✅ 章节可配置 → 可承载全部 7 项 |
| 5 | **NC 生命周期只做"开具"** | §9.4.4.2→§9.6 完整链是"发现→记录→整改→验证→关闭" | ✅ 明确划边界（整改归另一功能域），**没有假装做全** |
| 6 | **`JudgeMode` 承认"不是所有条款都能自动判"** | ISO 19011 审核方法：查阅文件 / 现场观察 / 访谈 / 抽样 | ✅ 方向对（细节见 §2.2） |
| 7 | **AI 解析失败不预填结论**（`NeedsManual` + `Conformity=null`） | 审核结论不可伪造 | ✅ **这是全册最正确的判断**：「宁可阻塞也不能伪造结论」 |
| 8 | **「数据不足，未检查」不统计为符合** | 报告结论不得失真 | ✅ 且规定汇总必须分**四类**而非三类 |
| 9 | **严重度默认落最轻（`observation`）而非 `major`** | 不冤枉企业 | ✅ 方向正确 |
| 10 | **审核发现版本戳**（`ExtractVersionStamp`） | 证据必须对应审核时点的状态 | ✅ 业务上是"证据固定"，思路对 |

**技术设计层面的合理判断**（也一并肯定）：

- **NC 与报告结构对称**（都是「配置层 → 实体层 → 结果层」）：这是**正确的抽象**，认可/修改/日志/导出只写一遍
- **状态三层分离**（执行/结果/存续）：正交、清晰，比单列状态机强得多
- **软阻塞**（可跳过补录，缺数据的规则不执行而非报错）：符合"审核是人的判断"这一本质
- **`wf_node_execution` 已有 AI 可回溯字段**（`AiPrompt`/`OutputJson`/`SourceFileCode`）→ 不重复造表：**这是真正的省工时发现**
- **幂等键与业务轮次分离**（`Attempt` vs `RoundNo`）：概念干净

## 二、业务符合性：对不上的 9 处

### 2.1 ★★★ 最严重：整个模型缺「受审核部门 / 过程」维度

#### 真实体系审核是怎么组织的

ISO 19011 §6.3「编制审核计划」的核心产物是 **受审核部门/职能 × 审核准则（条款）× 时间** 的矩阵：

```
审核计划（片段）
┌────────────┬──────────────────────────┬──────────┐
│ 受审核部门  │ 对应条款                  │ 审核方法  │
├────────────┼──────────────────────────┼──────────┤
│ 管理层      │ 4.1 4.2 5.1 5.2 5.3 9.3  │ 访谈      │
│ 采购部      │ 8.4                      │ 查文件+访谈│
│ 生产部      │ 8.1 8.5 8.6 8.7          │ 现场观察  │
│ 品质部      │ 9.1 9.2 10.1 10.2        │ 查记录    │
└────────────┴──────────────────────────┴──────────┘
```

**NC 记录在实务中必须能回答「在哪个部门、哪个过程发现的」** —— 因为：
1. 整改要派到具体部门（`DueDate` + 责任人）
2. 报告要按部门呈现"审核发现"
3. 要能核对"计划要审的部门都审了没"
4. 同一份文件在两个部门执行不一致 → 是两条不同的 NC

#### 这套设计里有什么

**没有。全 19 篇、全库，零覆盖。** 实测证据：

```sql
-- NC 表字段（★ 无任何部门/过程列）
TaskCode ClauseCode NcNumber Severity Description RequirementRef EvidenceRef
SourceType SourceCheckCode RuleCode DueDate OpenedBy OpenedAt ClosedAt ...
--                                                                  ↑ 只有"什么时候开、什么时候关"

-- 全库找"部门/过程"主数据表
SELECT TABLE_NAME FROM information_schema.TABLES
WHERE TABLE_SCHEMA='yzh_cert_platform'
  AND (TABLE_NAME LIKE '%dept%' OR TABLE_NAME LIKE '%process%'
       OR TABLE_NAME LIKE '%organ%' OR TABLE_NAME LIKE '%scope%');
-- → 只有 Sys_Organization（系统组织架构，不是受审核企业的部门）

-- 条款表：纯条款树，无"该条款通常审哪个部门"
StandardCode ParentCode ClauseNumber Title Description SortOrder
```

**文档侧**：全文检索「受审核部门 / 受审核过程 / 部门 / 审核方法 / 现场观察 / 访谈 / 抽样」，全 19 篇仅 3 处命中，**且都不是这个意思**：

| 位置 | 原文 | 实际含义 |
|---|---|---|
| 10 号:145 | 「ISO 条款『**过程方法**』一条规则查出 3 个问题」 | 指 ISO 9001 §4.4 这个**条款**，不是"按过程审核" |
| 11 号:42 | 「S2 第二阶段审核（**现场审核**）」 | 时间轴上的事件名，无审核方法建模 |
| 09 号:397 | 「3 个标准子任务可并行（**观察**队列状态）」 | 观察 = watch，不是"现场观察" |

#### 为什么这是「地基」级而不是「加功能」级

因为**它决定表结构**，而表结构**还没建**（`cert_expert_*` 实测 0 张）：

| 已设计的表 | 若现在不补，后面要改什么 |
|---|---|
| `cert_validation_rule` | 规则要能绑定「该规则在哪个过程验证」→ 加 `ProcessCode` |
| `cert_expert_nc_result` | NC 结论要记录过程 → 加 `ProcessCode` / `ProcessName` |
| `cert_expert_report_section_item` | "审核发现"章节要按过程分组 → 加分组维度 |
| 任务创建向导 | 从「选企业+阶段」变成「选企业+阶段+**审核计划范围**」 |
| 左树右表（D32） | 树上多一层「过程」；右表多一列「受审核部门」 |
| Excel 导出 | NC 清单多一列「受审核部门/过程」（**实务必备列**） |

> ⚠️ **这 6 处全部是「建完再改 = 全量返工」的位置**。按 13 号自己的铁律 X1「地基不净不开工」，**它必须排在 S1 之前**。

#### ★ 直接回答：「是不是所有 NC 都对应一个部门？自动查出的 NC 怎么告知部门？」

**答案：是的，绝大多数能对应 —— 但不是"一个部门"，而是「部门 + 过程」两个维度，且有 3 类例外。**

**① 为什么是「部门 + 过程」两个维度（不是只要部门）**

两者**不是一回事**：

| | 受审核部门 | 过程 |
|---|---|---|
| 是什么 | 审核计划里列的**组织单元** | 失效的**业务过程** |
| 例子 | 采购部 / 品质部 / 生产部 | 8.4 外部提供的过程、产品和服务 |
| 关系 | **一对多**：生产部负责 8.1 / 8.5 / 8.7 多个过程 | **多对一**：8.4 涉及采购部 + 品质部 + 技术部 |

ISO 9001 第 4-10 章**本身就是过程**（4 组织环境 / 5 领导作用 / 6 策划 / 7 支持 / 8 运行 / 9 绩效评价 / 10 改进）→ **每个条款都能归到一个"主责过程"**。

**② 3 类例外（必须诚实处理，不能硬塞部门）**

| 例外 | 条款 | 归属 |
|---|---|---|
| **管理层级** | 4.1 理解组织环境 · 4.2 相关方 · 5.1 领导作用 · 5.2 方针 · 5.3 职责权限 · 9.3 管理评审 | **最高管理者 / 管理层**（不是一个部门） |
| **跨部门** | 7.5 成文信息 · 8.4 外部提供 · 9.2 内审 · 10.2 纠正措施 | 需**主责 + 相关**多部门（建议主责必填、相关可多选） |
| **企业规模差异** | 同一条款 | 小企业一个部门兼多职 → **同一条款在不同企业对应不同部门** → **映射必须分两层，不能全局写死** |

**③ 自动查出的 NC 如何"告知部门"—— 四步机制（这才是可落地的答案）**

```
标准条款 (ClauseCode)
    ↓ 【第①层 · 全局业务知识】条款 → 典型过程       ← 专家/实施人员建表，一次性
典型过程 (Process)
    ↓ 【第②层 · 企业级】过程 → 责任部门             ← 按企业组织架构配，每企业一次
责任部门 (Department)
```

| 步 | 机制 | 什么时候生效 | 成本 |
|---|---|---|---|
| **1** | ★ **规则侧直接绑定**：`cert_validation_rule.ProcessCode`（+ `DepartmentCode`）。**专家配规则时就选好"这条规则在哪个过程/部门验证"** | **最准**（专家按过程配的规则，天然带部门）→ 优先级最高 | 加 2 列 |
| **2** | ★ **全局兜底映射**：`cert_iso_clause_process`（条款 → 典型过程）。规则没绑时自动带出 | 覆盖"忘了绑"的规则 | 1 张表 |
| **3** | ★ **标"待确认"而非留空**：前两步都没命中 → `ProcessCode = null` 但**标记 `NeedProcessConfirm=1`**，专家**认可该条时必须指定**，不允许留空 | 保证**导出永远没有空部门列** | 1 列 |
| **4** | ★★ **反哺学习**：专家手工指定的结果**回写第 2 步的映射表** → 下次同类条款自动带出 | **专家只教一次**，系统越用越准，**且不依赖 AI 猜** | 0 人天（逻辑） |

> ★ **第 4 步是这套设计的关键**：它让"部门映射"这个**业务知识**由专家**在使用中沉淀**，而不是要求实施人员一开始就把所有条款→部门配全。这与你「规则库本期只做框架、真实规则由实施人员 + 专家共同配置」（D22）的定位一致。

> ⛔ **绝不能靠 AI 从企业文件里推部门**：文件里不会写"这条不符合该归采购部"。AI 只能判"文件内容是否符合条款"，**归属是组织知识**。

#### 最小闭合方案（**V1.2 已改为采纳用户方案**，见 [20 号 §8.2](20-端到端链路评审-V1.md)）

### 2.2 ⬇️ 「人工/自动」—— **★ 本节 V1.2 已修正：收回"错位"表述**

> ⚠️ **V1.2 修正（2026-09-30 用户第 4 轮澄清）**：
> 用户原话：「我在 NC 检查项中，**其实也增加了人工判断和自动判断** —— 有些依据**人工现场核实、勘察**，
> 有些通过**企业材料结合 ISO 标准规则通过流程配置**；**我们自动 NC 其实是第二部分**」
>
> **核对实测后，本节的"错位"判断不成立**：① `JudgeMode` 列**确实存在**（实测 `varchar(20) NOT NULL DEFAULT 'auto'`）；
> ② 03 号 §六**确实**定义了 `manual` 档（`MarkSkipped(manual_mode)` + 界面"人工检查区"）；
> ③ **用户的二分法本质就是 ISO 19011 的审核方法二分** —— 人工 = 现场观察/访谈/勘察，自动 = 查阅文件/记录。
> → **不是"分错类"，是本节误读了用户的分类依据。⛔ 收回"错位"一词。**
>
> **真正的缺口在 `manual` 档内部**（详见 [20 号 §8.1](20-端到端链路评审-V1.md)）：
> `manual_mode` 一个标签下混了两类本质不同的东西 ——
> **M1 现场类**（审核方法本身如此，系统永远无数据源 → 人工录入正确）/ **M2 待处理类**（`no_rule`/`rule_disabled`/`NeedsManual` → 是缺陷，应催办而非让专家手工填）。
> → **修正后的建议：`manual_mode` 拆成 `manual_onsite` / `manual_pending`（0.2 人天，必做）；
> `JudgeMode` 值域改名降为"可选"（0.1 人天）。**
> → **§5.1 第 2 项由「必须补 0.3」下调为「应该补 0.3」。**

#### 设计现状（保留原分析，供对照）

`cert_validation_rule.JudgeMode` 三值（03 号 §6）：

| 值 | 设计里的含义 | 本期处理 |
|---|---|---|
| `auto` | 全自动 | 正常工作流 |
| `semi` | 半自动 | ★ **「等同 `auto`」，只改界面高亮** |
| `manual` | 纯人工 | `MarkSkipped`，专家手工填 |

#### 业务上的问题

**① `semi` 是假值。** 设计自己承认「不改执行逻辑，只改界面强调」。业务上"半自动"不是一种审核方法，也不产生任何行为差异 —— 它是为了凑三值而设的。

**② 真正的分界线是「审核方法」，设计里没有这个概念。** ISO 19011 的四类审核方法：

| 审核方法 | 能否自动化 | 为什么 |
|---|---|---|
| **查阅文件/记录** | ✅ **可以** | 数据来自提取结果（`cert_extraction_result`） |
| **现场观察** | ❌ 永远不能 | 无数据源 —— 系统里没有"现场" |
| **访谈** | ❌ 永远不能 | 无数据源 |
| **抽样验证** | ⚠️ 部分 | 需人工确定样本 |

→ **`JudgeMode` 的正确语义应该是「审核方法」**，而不是"自动化程度"。因为：

1. **它决定报告怎么写**。ISO 19011 §6.6 要求报告包含「审核活动概要（**时间、方法**）」。现在系统无法回答"本次审核用了哪些方法"。
2. **它决定缺数据时的行为**。现场观察类规则**天然没有提取结果**，不该被报成「数据不足」去让专家补录 —— 那是**审核方法本身如此**，不是数据缺失。设计现在把它们混在同一个 `data_gap` 里。
3. **它决定专家工作台的分区**。03 号 §6 已把界面分成「人工检查区」，但分区依据是 `SkipCategory=manual_mode`，没有"该条款需现场审核"的提示。

#### 建议

| 改动 | 内容 |
|---|---|
| `JudgeMode` 值域改为 **审核方法** | `doc_review`（查阅文件，可自动）/ `onsite`（现场观察）/ `interview`（访谈）/ `sampling`（抽样） |
| 自动执行条件 | 只有 `doc_review` 走工作流；其余三种**不产生 gap**，直接进「人工检查区」 |
| 报告侧 | 汇总 Sheet 增加「审核方法分布」；章节正文可用 `审核方法` 变量 |
| 与 03 号 §6 的界面分区对齐 | 「人工检查区」按方法再分组：现场观察 / 访谈 / 抽样 |

> ⚠️ 现库中 2 条规则的 `JudgeMode` 都是 `'auto'`（实测），**迁移成本≈0**。

### 2.3 ★★ 观察项被塞进 NC 表 → 语义矛盾 + 导出清单混装

**设计现状**（03 号 §1.1 + §5.1）：

| 结论 | 动作 |
|---|---|
| `nonconform` | INSERT `cert_nc` |
| **`observation`** | ★ **也 INSERT `cert_nc`**（`Severity='observation'`） |

1. **观察项不是 NC。** ISO 17021-1 的 NC 只有 major/minor 两类；业务知识库自己也写明「observation 是**行业实践中常见的第三类**」，即**它不是标准定义的 NC**。

**建议**（三选一，按成本排序）：

| 方案 | 做法 | 成本 |
|---|---|---|
| **甲（推荐）** | `cert_nc.Severity` 收敛为 `major`/`minor`；观察项落**同一张表但加 `RecordType` 列**（`nc`/`observation`），导出时分两个 Sheet | 0.2 人天 |
| 乙 | 观察项独立成表 `cert_expert_observation` | 0.5 人天 |
| 丙 | 不动表结构，只在导出层分列 | 0.1 人天（**治标**，数据层仍混） |

### 2.4 ★★ 「不适用(na)」缺判定依据 —— 没有「认证范围 / 删减声明」模型

**设计现状**：`na`（不适用）由 **AI 或专家**在审核时判定（03 号 §1.1「需专家手工判定」、§2.2 归一化里 AI 可输出 `na`）。

**业务问题**：条款是否适用，**不是审核时判的**，而是**认证委托阶段就确定的**：

- ISO 9001 §4.3 要求确定**体系范围**；§7.5（成文信息）要求说明**适用性**（即哪些条款删减、理由）
- 认证机构在**受理阶段**就要确认认证范围与删减，审核时**依据已确认的范围**判断
- 后果：设计里 `na` 无依据 → **同一企业不同任务的 `na` 判定会不一致**（上次判 na，这次判 conform）

**实测：库里没有这个模型。**

```sql
-- cert_enterprise 只有一个自由文本，无结构化删减声明
CertScope  认证范围描述     ← 就这一个
```

**建议**：
- `cert_enterprise` 加 `ExcludedClauses`（JSON 或关联表：条款 Code + 删减理由）
- 任务创建时**自动预置** `na` 集合（来自认证范围），专家只能在预置范围内调整
- 报告"审核准则"章节自动带出「本报告未涉及以下条款及其理由」

成本约 0.3 人天，**收益是"结论可复现"**。

### 2.5 ★★ 多标准整合审核被切成 3 次独立审核

**设计现状**（04 号 §4.1）：

> 「任务下有 N 个标准子任务……**章节不跨标准合并**」
> 「同一阶段关联 3 个标准 → 3 套独立章节，各自成区」

**业务问题**：真实的多标准是**一次整合审核（integrated audit）** —— 审核员**同一份文件、同一个部门、同一段访谈**同时覆盖 9001/14001/45001。设计把它呈现为**三次独立审核**：

| 维度 | 数据层（设计） | 呈现层（设计） | 真实业务 |
|---|---|---|---|
| 标准 | 一行一标准 ✅ | **3 个 Sheet / 3 个折叠区** ⚠️ | **1 次审核，1 份报告** |
| 同一客观事实 | 生成 N 条记录 ✅ | **N 条 NC** ❌ | 通常合并为 **1 条 NC 映射多个条款** |

**两个具体后果**：

1. **专家要在 3 个 Sheet 之间来回对照**，而他做的是**一次**审核 —— 交互成本翻 3 倍。
2. **NC 会重复**。同一个事实（如"内审未覆盖 45001 条款"）同时违反 9001 §9.2 与 45001 §9.2 → 生成 **2 条 NC**；实务上应**合并为 1 条 NC 映射 2 个标准条款**（或至少明确标注为同一发现的重复）。
   而 `cert_nc.ClauseCode` 是**单值**（实测 `ClauseCode varchar(36) NOT NULL` 单列）→ **无法表达"一条 NC 对应多标准多条款"**。

**建议**（⚠️ **用户已裁决「能砍整合而不损商业价值」→ 本节整体降为延后项，见 §5.3-1**）：

| 项 | 改动 | 成本 | 优先级 |
|---|---|---|---|
| NC 支持多条款 | 新增关联表 `cert_nc_clause`（`NcCode` + `StandardCode` + `ClauseCode`），保留主 `ClauseCode` 作为"主准则" | 0.4 人天 | **延后** |
| 呈现层提供"整合视图" | 左树右表增加「跨标准合并」开关：同一条款号（如 §9.2）在多个标准下的结论并列显示 | 0.5 人天 | **延后** |
| 导出 | 增加「整合审核报告」Sheet（按条款号聚合，多标准列并列） | 0.3 人天 | **延后** |

> ⚠️ **接受的代价（记录在案）**：`cert_nc.ClauseCode` 保持单值 → **多标准认证下，同一客观事实会生成 N 条 NC**（如"内审未覆盖"同时违反 9001 §9.2 与 45001 §9.2 → 2 条）。这是**已知且接受**的取舍，不再重复讨论。

### 2.6 ★★ 缺「审核发现」与「不符合项」的层次区分 + `EvidenceRef` 只有引用

**业务定义**（ISO 19011 §3.10 / §3.11）：

```
审核证据  →  与审核准则比较  →  审核发现  →  汇总  →  审核结论
                                   │
                                   ├─ 符合的发现
                                   └─ 不符合的发现  =  NC
```

**设计现状**：`cert_expert_nc_result.Conformity ∈ {conform, nonconform, observation, na}` —— 把**审核发现**和**不符合项**压在一个字段。这本身可接受（简化），但带来一个问题：

**`EvidenceRef` 只是"引用"**（D08：本期不做字段级下钻 UI）→ **导出的 NC 清单里"客观证据"栏会是空的或只有文件名**。

> ⚠️ **定性已按定位澄清调整**（§零之二）：这**不再是合规问题** —— 导出物是内部判断结果，ISO 17021-1 §9.4.4.2 的 shall 不适用于它。
>
> **但它仍是"辅助系统能不能用"的核心问题**：辅助系统的价值 = **AI 说 A，审核员 3 秒内能验证**。证据栏为空 → 审核员要自己去翻文件 → **系统退化成"AI 说了个结论，我还得自己查"**，审核员不会用。

**建议**：
- `EvidenceRef` 在导出/展示时**自动填充为可读证据描述**：`{文件名} · {字段名} = {值}`（数据已在 `wf_node_execution.SourceFileCode/SourceFieldName` 里，**免费**）
- 成本约 0.2 人天（只做摘要拼接，不做下钻 UI）—— 见 §零之二 N-2 的方案甲

### 2.7 ★ 阶段主数据只有 3 行，且 **D26 与 D30 互相拆台**

**实测**：`cert_cert_stage` 只有 **3 行**（初审 / 预审 / 复审），而真实认证周期是：

```
初次认证：S1 第一阶段审核 + S2 第二阶段审核
监督审核：SV1 第一次监督 + SV2 第二次监督（每年一次）
再认证：  RC 再认证审核
特殊审核：扩项 / 变更 / 投诉触发
```

**两个后果**：

| # | 后果 |
|---|---|
| 1 | **无法区分"第一次监督"和"第二次监督"**。任务只能挂在 `(企业, 阶段)` 上，同一"监督审核"阶段下两次任务混在一起 |
| 2 | ★ **D26 与 D30 直接冲突**：D26 说「认证周期本期不做」，但 D30 说「**沿用项保留上次检查时间** —— 监督审核没查的条款不能说'这次也查了'，**该字段是审计凭据**」。**"这次"和"上次"的区分，恰恰需要周期/事件维度** |

设计预留了 `AuditEventCode` / `AuditEventName`（可空，0.2 人天），但**没有说明这两个字段由谁填、值域是什么** → 按 13 号自己的标准（「没等级的规则 = 愿望」），**这两个字段会变成永远为空的占位列**。

**建议**：
- 要么**补阶段主数据到 6-7 行**（S1/S2/SV1/SV2/RC/特殊），并在任务向导里选"本次是第几次监督"
- 要么**明确写清** `AuditEventCode` 的填充时机与值域，否则**删掉这两个字段**（避免"看起来有追溯、实际是空的"）

成本 0.2-0.3 人天。**这是 D30 能否成立的前提**。

| 界面 | 黄色 Alert 提示 |
| 导出 | 「与普通章节同等对待导出，**不加特殊标记**（专家已确认过）」 |

**降级后的风险**：模板示例正文是「**审核发现应包含：不符合项描述、涉及条款、证据。**」这类**写作指导文字**。专家漏看黄色提示直接导出后，自己回头看 Excel 时**无法分辨哪段是 AI 生成、哪段是模板示例** → 可能把示例当判断结果使用。

**建议**（成本 0.2 人天，可延后）：导出的 `degraded` 章节正文前加 `【本节内容来自模板示例，请核实】`，或导出汇总页列出「哪些章节来自模板示例」。

## 三、设计合理性：需要修正的 4 处

### 3.1 ★ `TaskSource` 是技术语义，且有两个选项做同一件事

**设计现状**（12 号 §2.2）：

| | `ScopeType=FULL` | `ScopeType=PARTIAL` |
|---|---|---|
| `TaskSource=REDO` | 全阶段重跑 | 重跑大部分，留几项沿用 |
| `TaskSource=PATCH` | ★ **「语义重复，等价 FULL+REDO」** | 最常用 |

设计**自己承认** `REDO+FULL` 与 `PATCH+FULL` 等价，并写「**前端应在选择时提示这一点**」。

> ⚠️ **需要靠 UI 提示来消解的设计缺陷，就是设计缺陷。** 而且向导第 2 步的文案是「重新执行（整体再跑一遍）/ 局部更新（只补跑部分）」—— 这是**技术动作**，专家（审核员）脑子里想的是**业务原因**（"上次 3 个条款证据不足，这次补上"）。

**建议**：
- **取消 `TaskSource`**，只保留 `ScopeType`（FULL/PARTIAL）
- 增加**业务化的"本次审核原因"**枚举：`首次审核` / `补充证据` / `整改验证` / `文件变更后重跑` / `监督审核到期`
- 这个枚举**直接用于向导文案、任务列表筛选、报告"审核目的"章节**

成本 0.2 人天（改枚举 + 向导文案），**收益是向导从"技术选择题"变成"业务选择题"**。

### 3.2 ★ 「上次不符合未关闭」的预勾选**无法实现**（依赖明确不做的功能）

12 号 §2.3 的 `PATCH` 预勾选策略：

> 「★ 预勾选『**上次有新文件的**』『**上次不符合未关闭的**』」

但：
- **"上次不符合未关闭"** 需要整改跟踪的关闭状态 → `audit_rectification` **明确不做**（03 号 §5.4、10 号 N6）
- **"上次有新文件"** 需要文件版本与任务的关联 → 设计里只有 `ExtractVersionStamp`（运行时戳），**没有"任务 → 文件版本"的关联**

→ **这两个预勾选条件都落不了地**，向导第 3 步会退化成"全勾/全不勾"。

**建议**：改成**可实现的判据**：`上次结论为 nonconform 的项` + `上次被判"数据不足"的项`（这两个都只依赖结果表）。成本 0.1 人天。

### 3.3 ⚠️ 「认可范围」在左树右表里语义含糊

12 号 §八 D32 的树是 **企业 → 阶段 → 标准 → 任务** 四级（12 号 §1.5 写"三级"，D32 写"企业→阶段→标准→任务"，**两处不一致**），并说：

> 「⚠️ **选中"任务"节点 ≠ 认可范围**。它只是'这次执行了哪些'的只读视图。」

**业务问题**：专家**最自然的动作**就是"选中任务 A → 全部认可"。设计却要求他"先选中任务节点看范围，再用右表顶部的 `[认可本次执行的 N 项]` 按钮" —— **树的选中态与操作范围解耦**，这是反直觉的。

**建议**：树节点选中 = 右表过滤范围 = 批量操作范围，三者统一；"只读投影"的性质用**表头文案**表达（如"本次执行了 12 项（只读）"）而不是靠解耦交互。

### 3.4 ⚠️ `audit_nonconformity.OpenedBy` 是 `bigint` —— 违反项目自己的双关键字准则 A

**实测**：

```sql
OpenedBy  bigint  NOT NULL     -- ★ 存用户 Id
```

项目铁律（AGENTS.md 准则 A）：「`Id` **永不**进 WHERE / 关联 / 前后端传参」。而这张表的 `OpenedBy` 是 `bigint`（用户自增 Id），其余表都用 `varchar Code`。

→ 建 NC 时无法从 `IUserContext` 直接取（那是 `Code`），需要一次 Id↔Code 转换，**且转换漏了不报错**（写入 0 或错的人）。

成本 0.1 人天（改 `varchar(36)` 存 `Code`）。**建议在 D34/E5-3 改造这张表时一并处理。**

## 四、可操作性评估

### 4.1 能跑通吗 —— **能**

链路完整、无断点：

```
选企业+阶段 → 完备性检查（报缺口）→ 补录/跳过 → 提交
   → 按标准拆队列 → 逐项跑工作流 → 落结果（含 skipped/failed/degraded）
   → 结果菜单左树右表 → 认可/修改（留日志）→ 导出 Excel
```

**三个可操作性亮点**：

| # | 亮点 | 为什么好 |
|---|---|---|
| 1 | **软阻塞**（可跳过补录） | 审核场景下"先出一部分结论"是常态，硬拦会卡死流程 |
| 2 | **AI 解析失败 → 强制专家介入** | 不伪造结论，且给了 `rawOutput` 供参考 |
| 3 | **「数据不足，未检查」独立成类** | 保证导出统计不失真 —— 这是最容易被做错的地方 |

### 4.2 可操作性的 3 个真实障碍

| # | 障碍 | 影响 | 处置 |
|---|---|---|---|
| **1** | ★★★ **缺部门/过程维度** | 结论**无法用于整改派单**、报告**无法按部门呈现**、审核计划**无法核对覆盖** | **S1 前补 0.8 人天**（§2.1） |
| **2** | ★★ **专家实际工作流是"按部门审"，系统是"按条款审"** | 专家在系统里要**自己把条款归到部门**，或在系统外维护部门视角 → **系统变成"录入工具"而不是"工作台"** | 同上，靠 `ProcessCode` 解决 |
| **3** | ★ **10/15 前做不完** | 全册 ≈ 42.6 人天 vs 11 个工作日 | 见 §5 砍法 |

### 4.3 按「今天可操作」的最小闭环（建议）

```
① 补地基（约 2.5 人天）
   · IsValid 回填 + 实现 IIsValid（同批）
   · 阶段码迁移 '03' → GUID
   · GetActiveByScope* 两个重载
   · ★ 部门/过程维度：cert_audit_process + 3 处 ProcessCode（0.8）

② D34 收尾（0.5 人天）
   · 删 ReportTemplate 死实体 + 前端 + 修铁律七

③ 最小链路跑通（不做 11 张表，先跑 1 条规则）
   · 用 WorkflowTestController 放开 TaskType 跑 1 条 NC 规则
   · 落 1 条结果 → 专家认可 → 导出 1 个 Sheet
   → 证明"登录→建档→上传→看到提取结果→报告生成"可达
```

> **不做 11 张新表也能验证 10/15 的必达目标**（登录→建档→上传→看到提取结果→报告生成）。11 张表是"任务系统"，属于**争取**项，不是必达项。
