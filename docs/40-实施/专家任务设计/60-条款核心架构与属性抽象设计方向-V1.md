# 条款核心架构与属性抽象：设计方向（V1）

> 2026-10-26 ｜ 回应用户「以条款为核心重新设计」的定位陈述
> 前置：50（五层模型 / 属性 Schema）· 58（12 类属性）· 59（58 评审）· 38（证据与 NC 同粒度）
> 结论先行：**方向成立，而且比 58 更彻底。** 58 把条款属性当「检查项的生成模板」，你要的是「**条款是唯一原子，其余全部是它的函数**」。这一句差异决定三件事：属性表只有一个归属（标准级）、机构差异退出配置层、阶段/归属/判定从属性推导而非配置。

---

## 一、先把你的话翻译成四条原则

| 你的原话 | 提炼 | 后果 |
|---|---|---|
| 「以条款为核心」 | **P1 条款是唯一原子**：文档归属、阶段、判定规则、NC 全部是条款属性的**函数**，不是独立配置 | 不允许再存在第二套以「文档」或「任务」为中心的主数据 |
| 「标准条款不应该和机构关联，因为不同机构都必须遵循该标准」 | **P2 配置层无机构**：条款属性表**没有 `OrgCode`**；机构差异只允许出现在执行层（检查项实例、结论覆盖） | 推翻 59 的 D1「拆标准侧/机构侧两张表」，改为**只建标准侧一张，机构侧配置表不建** |
| 「抽象成特定的几个属性，未来文档归属/阶段/判定规则都可以通过条款分析」 | **P3 属性是控制位，不是分类**：每一维只决定一件下游行为，任两维不重叠 | 属性数量要少到能穷举，多到能推导 |
| 「LLM 自动生成 + 后台可维护可修改」 | **P4 属性是知识资产**：AI 起草 → 规则自检 → 专家复核 → 锁定；每条可溯源、可回归验证 | 属性质量成为产品护城河，且必须可度量，不能靠"填了就行" |

再加一条你没明说、但整件事绕不开的：

> **P5 归属是匹配的结果，不是上传时的输入。**

现在的做法是「文档进来 → 人标它属于哪个条款」；你要的是「条款先声明期望 → 匹配器把文档挂上去」。**这是整套设计里唯一真正新的东西**，也是「找不到相关内容就是有疑问」能自动化的唯一原因。

## 二、为什么 P5 是关键（这是全部论证的核心）

现状（文档驱动）有一个结构性盲点：**你只看得见「有的」，永远看不见「该有没有的」。**

- 一份文档上传 → 找它像哪个条款 → 挂上 → 结束
- 没上传的那份文档，系统里**根本不存在这个对象**，因此不会产生任何疑问

条款驱动（期望驱动）把这件事反过来：

```
期望集 = 条款属性展开（该有什么）
实际集 = 企业上传 + 现场采集（有什么）
缺口   = 期望集 − 实际集        ← 这就是「有疑问」的机器定义
```

所以「找不到企业相关内容可能是有疑问」不是一句判断，而是**一次集合减法**。前提是期望集必须由条款生成 —— 这就是为什么属性抽象是前置条件，不是加分项。

顺带回答一个必然会被问的问题：**为什么不能直接让 AI 读全部文档然后说「这条款符不符合」？**

因为那样得到的结论不可复核、不可定位、不可反驳。审核要的是这样一句话：

> 「你缺 X；X 的定义来自标准第 N 条（原文在此）；你的文件池里没有；匹配过程在此。」

这条链每一步都要能指到具体对象。纯 LLM 判定给不出这条链，只能给出一个无法追溯的结论 —— 而无法追溯的结论进不了认证档案（38 号 §留痕）。

## 三、属性抽象：6 个正交维度（第一层）

设计要求：**每一维只决定一件事，且任两维语义不重叠**。这不是分类学，是**控制位**。

| # | 维度 | 取值 | **唯一决定的事** |
|---|---|---|---|
| **A1** | `EvidenceKind` 证据形态 | `doc` 体系/程序文件 · `record` 运行记录 · `field` 记录内字段 · `site` 现场状态 · `person` 人员能力资质 · `system` 系统数据/截图 | **去哪个池子找** |
| **A2** | `Obligation` 强制程度 | `shall` 应 · `should` 宜 · `may` 可 · `note` 注/指南 | **缺了算不算问题** |
| **A3** | `Applicability` 适用性 | `universal` 通用 · `conditional` 有条件 · `scope` 按认证范围 · `na_by_org` 机构可裁 | **这条要不要查** |
| **A4** | `JudgeMode` 判定方式 | `existence` 有无 · `completeness` 字段全不全 · `content` 内容符合 · `timeliness` 时间合规 · `consistency` 跨件一致 · `traceability` 可追溯 | **用哪个引擎判** |
| **A5** | `Severity` 缺失严重度 | `major` · `minor` · `observation` · `none` | **出了问题算几级** |
| **A6** | `Depth` 取样深度 | `single` 一份即可 · `sample` 抽查 N 份 · `all` 全覆盖 · `census` 普查 | **查几份** |

### 正交性自检（任取两条，改一条不应引起另一条变化）

- `Obligation=note` 与 `Severity=major` 语义矛盾 ⇒ **A2 优先级最高，`note` 直接短路 A5**：注不产生 NC，无论严重度配什么
- `Applicability=conditional` 时，A4/A5/A6 **不求值**（不适用就不判）
- 求值顺序固定：**A3 → A2 → A1 → A4 / A5 / A6**
- `JudgeMode=existence` 时 `Depth` 才真正起作用；`content` 判定天然需要样本，二者不冲突

### 为什么正好是 6 个，不是 12 个也不是 3 个

58 的 12 类里有 6 类其实是这 6 维的**同义词或组合**：

| 58 的属性 | 实际是 |
|---|---|
| `ShallLevel` | = A2 |
| `Applicability` + `ApplicabilityRule` | = A3（Rule 是 A3 的参数，不是新维度） |
| `DefaultLevel` + `SeverityDefault` | = A5（两个词一个意思，58 自己重复了） |
| `VerificationMethods` | = A1 + A4 |
| `SamplingDepth` | = A6 |
| `StageSwitch` | = A1 的函数（见 §五） |

剩下的 6 类不是"属性"，是**内容** —— 见 §四。把内容塞进属性，是 58 混层的另一半原因。

## 四、第二层：内容属性（AI 生成，非枚举）

6 维是控制位，回答「怎么查」；内容属性回答「查什么」。两者必须分开，因为用途完全不同：**枚举可索引、可筛选、可调度；内容只能渲染、匹配、比对。**

| 内容属性 | 形态 | 生成方式 | 用途 |
|---|---|---|---|
| **`Intent`** 条款作用 | 一句话：这条款管什么、要达成什么 | LLM 提炼 + 专家改 | **语义匹配的主键**（见下） |
| `Artifacts[]` | `[{name, type, mandatory, typical_owner}]` | LLM 从条款原文提 | **展开期望集**（P5 的"期望"） |
| `Fields[]` | **挂在产物上，不挂条款** | 从案例真实文件反推 | 字段级校验 |
| `Criteria[]` | `[{type, expr, desc}]`，如 `{type:'interval', max_months:12}` | LLM 起草 + 专家改 | A4 的判据参数 |
| `EvidencePoints[]` | 取证要点（检查单第 3 列） | LLM 起草 | 生成检查项 |
| `Question` | 提问句（检查单第 2 列） | LLM 把要求改写成问句 | 生成检查单 |
| `RelatedClauses[]` | 弱关联条款 | LLM + 专家 | 证据复用（不是合并检查项） |

### `Intent`（条款作用）是匹配的主键 —— 原稿漏项，此处补记

这一项的地位不是"多一个描述字段"，而是**唯一能把企业文档和条款连起来的东西**：

- 企业文件**不会写条款号**。`KSY-QMS-P-17-01`、`XASL-QP-001` 这些名字里没有"7.1.5"。
- 但文件名的语义、目录结构、正文主题会和**条款的作用**对上：7.1.5 的作用是「保证测量结果可信」⇒《计量器具管理规定》《监视测量设备控制程序》都对得上。
- 所以匹配顺序必须是：**先按 `Intent` 找候选 → 再按 `Artifacts` 校验 → 最后按 `Fields` 判完整性**。`DocPattern` 通配符只是兜底。

`Intent` 还有两个用途，都不是"顺带"：

1. **适用性推理依据**：7.3 的作用是「控制设计过程」⇒ 企业无设计活动 ⇒ 不适用。A3 的 `conditional` 条件就是从 `Intent` 推出来的，不是另配的。
2. **NC 描述的"为什么不符合"**：NC 不能只写"缺 X"，要写"该条款要求保证 X 可信，而你的证据无法证明"——后半句就来自 `Intent`。**没有 `Intent`，NC 只能写"缺东西"，写不出"为什么这是问题"。**

### 一条关键修正（继承 59 §4.1，但理由要说得更硬）

`Fields` 必须挂在**产物**上，不能挂条款。原因不是"结构整洁"，是**结论的可写性**：

- 挂条款 ⇒ 只能说「7.3 缺设计输出字段」——这句话审核员写不进 NC，因为**没有主语**（缺在哪份文件里？）
- 挂产物 ⇒ 能说「你的《设计输入清单》缺『设计输出』栏」——这才是可开单的结论

同一条款 7.3，A 企业用《设计开发控制程序》+ 附表 1~5，B 企业用《设计输入清单》《验证报告》各自独立。挂在条款上必然退化成一张巨大的字段清单，**永远答不出"哪份文件缺哪个字段"**。

## 五、把「阶段 / 归属 / 判定」变成函数（这就是你要的效果）

```
条款（原文 + A1..A6 + 内容属性）
  │
  ├─① 适用性求值   A3 × 企业画像        ──→  该企业应查条款集
  │
  ├─② 产物展开     Artifacts            ──→  期望证据集（该有什么）
  │
  ├─③ 匹配         定位线索 × 文档池     ──→  证据单元（条款 × 文件 × 位置）
  │
  ├─④ 判定         A4 + Criteria        ──→  符合 / 不符 / 缺失 / 部分满足
  │
  └─⑤ 归集         A5 + 证据链          ──→  疑点 → NC 草案
```

### 三个「配置项」消失了，变成函数

| 原来要配的 | 现在等于 | 为什么可以推 |
|---|---|---|
| **阶段开关**（58 `StageSwitch` / 50 `stage_switch`） | `f(A1)`：`doc` → 一阶段（S1）；`record`/`site`/`person` → 二阶段（S2） | 一阶段审「有没有建立」（文件），二阶段审「有没有执行」（记录/现场/人员）。**这是标准本身的语义，不该每家机构配一遍** |
| **文档归属** | `f(Artifacts × 定位线索)` 的匹配结果 | 见 P5 |
| **判定规则** | `f(A4 + A5 + Criteria)` | 确定性模式由 A4 直接选引擎；严重度默认取 A5；参数取 Criteria |

### 但有三件事**不能**从条款推导，必须留在执行层

这一条是防止重蹈 58 病根的关键：

| 不能推导的 | 为什么 | 放哪 |
|---|---|---|
| **审核类型**（初审 / 监督 / 再认证） | 由上次 NC、体系变更、证书周期决定，与条款语义无关 | 项目 / 任务属性 |
| **部门** | 标准不会说"由品质部负责"，这是企业组织决定的 | 从**企业文档自身属性**（编制/受控部门）长出，或建档期一次性确认 |
| **场次 / 区域** | 由排班与现场组织决定 | 审核计划 |

**一句话记住这条边界：**

> **「阶段」能推，「审核类型」不能推；「归属」能推，「部门」不能推。**

把这两组混为一谈，就是 58 把 `DeptCodes` / `ProcessCode` 塞进标准侧表的根本原因 —— 它不是"放错了表"，是**把不能推的东西当成了能推的**。

### 与证据链的接口

你提到的「证据链收集成功后 → 形成检查证据 → 生成可能质疑的 NC」，对应 38 号已裁决的口径：**证据与 NC 同粒度、不同用途**。所以 §五 第 ⑤ 步不是"再造一套 NC 逻辑"，而是把已有证据单元按 A5 归集后**投影成 NC 草案**，再走人工确认（51 号的疑点状态机）。条款属性在这里的作用只有一个：**给每个证据单元一个"该不该有问题"的默认判据**，让草案有初值，而不是从零猜。

## 六、「一套标准」怎么治理（P4 落地）

属性是资产 ⇒ 必须有生命周期和验收口径，否则会变成"填了 70 条、没人敢改、改坏也不知道"。

### 生命周期

`draft`（AI 起草）→ `validated`（规则自检通过）→ `reviewed`（专家确认）→ `locked`（换版才动）

### 三条硬规则

**1. `Obligation` 必须规则优先，LLM 只补不改。**

国标里「应 / 宜 / 可 / 注」是**语言标记**，先正则抽；LLM 只处理"没有情态动词但实为要求"的句子（如 OCR 把"组织应确定"识别成"组织确定"）。

> **LLM 最容易犯、代价最大的错，就是把「注」当 `shall`。** 这一维错了后面全错 —— 把提示当要求，等于凭空冤枉企业。今日实测：19001 的 78 条里大量条款带「注」，若不区分，假 NC 会成片出现。

**2. 属性必须可回归验证。**

回归集 = 真实检查单（`Documents except for the above parts(4)-邝敏威.docx`）：**58 个「标准 × 条款」引用组合**。属性展开后应能命中其中 **57 个**（唯一未命中 `Q 6.1.2` 是 GB/T 19001 无 6.1.x 标题，已知且已记录）。

**属性任何改动都必须重跑这个回归集** —— 否则"改一条属性、悄悄改坏一片"永远发现不了。这是唯一能把属性质量从主观变客观的机制。

**3. 覆盖率必须可视化到格子。**

`条款数 × 6 维` 的完整度矩阵，**未填的格子就是工作清单**。不要用"完成度 68%"糊过去 —— 要能点进去看到"哪一条缺哪一维"。

### 换版迁移（提前想，别到时候救火）

条款号会漂（GB/T 19001-2016 → 2026 版）。属性按 **`(标准族, 条款号)` + 语义指纹（标题 + 关键短语向量）双键**对齐：

- 号变语义同 ⇒ 迁移属性
- 号同语义变 ⇒ 标 `stale` 待重审
- **只按号对齐是错的** —— 会把旧判据挂到新要求上，而且不报错

## 七、六个会出事的地方

| # | 风险 | 处置 |
|---|---|---|
| 1 | **一份文件覆盖多个条款**（质量手册覆盖 20 条） | 证据单元细到 `条款 × 文件 × 位置(页/表/行)`，否则"命中"退化成一个布尔值，说不出"第 3 页有、第 7 页没有" |
| 2 | **一份记录只满足某条款的一个字段**（设计输入清单只对 7.3.3 的一个栏） | 匹配必须**多对多**且允许 `partial`（部分满足），否则会产生大量假缺失 |
| 3 | **65 条父条款无正文**（今日实测：273 条中 65 条为空，全是父条款无引导段） | 这些条款属性只能**从子条款归纳**，标 `derived_from=children`，**禁止 LLM 凭空补**（否则等于编造要求） |
| 4 | **企业自创证据无处安放**（有标准没要求但真实有效的文件） | 保留**未归属池**，人工可挂载；反复挂到同一条款 ⇒ 提示"该条款 `Artifacts` 可能漏项"，形成**属性反哺**。这是属性越用越准的唯一机制 |
| 5 | **LLM 生成属性系统性偏严**（倾向把"宜"当"应"） | 首次上线**100% 人工复核**，稳定后降到抽检；偏严比偏松更危险，因为偏严会冤枉企业 |
| 6 | **纯条款驱动会漏条款之间的关联**（8.5.1 与 7.1.3 的基础设施、8.4 与 7.4.1 的供方，证据是同一份） | 需要 `RelatedClauses[]`（弱关联），用于**证据复用**，不用于合并检查项 |

## 八、与既有表的关系：这次重构「不新建什么」

| 既有对象 | 处置 | 理由 |
|---|---|---|
| `cert_iso_clause` | **不动**（骨架 + 原文，已回填 208 条 / 53,827 字） | 属性独立成表，重建条款树不丢属性 |
| **条款属性表** | **唯一新建**：标准级、**无 `OrgCode`** | P2 |
| 产物表 + 表单 schema 表 | 新建（二级，`Fields` 的落点） | §四 |
| `cert_validation_rule` | **降级**为"机构加严覆盖层"，只存与属性默认值**不同**的部分 | 未来大部分行可由属性生成 ⇒ 该表应**缩小**而不是扩张 |
| `cert_standard_phase_config` | 保留，但 `RequiredClauses` 改为**由属性推导后缓存**，不再手填 | §五 阶段 = f(A1) |
| `cert_expert_check_item` / `cert_nc_item` | 执行层，**照旧** | P2：机构差异只在这里 |

**净新增 = 1 张属性表 + 1 张产物表 + 1 张表单 schema 表。** 比 58 的方案少 1 张（机构侧配置表），且让 58 想建的那套消失。

### 那要不要推倒重来？

**不要。** 这次不是重写系统，是**给主数据换一颗心**：

- **变的**：谁来决定"该有什么"（从人工配置 → 条款属性推导）
- **不变的**：条款树、文件转换链路、提取链路、证据池、疑点状态机、报告生成、权限与归属模型

换句话说：**换的是"配置的来源"，不是"执行的方式"**。执行层一行不用动，这也正是 38 号已经裁决过的分层（证据与 NC 同粒度、依赖是 DAG 不是链）能直接复用的原因。

| **C2** | 「阶段 = f(EvidenceKind)」是否接受？接受则 `StageSwitch` 与 `phase_config.RequiredClauses` 都退化为缓存 | **接受。** 这是删掉两处并行配置的唯一机会，错过就永久三套 |
| **C3** | 机构侧那层配置（59 的 E 表）本期**不建**，机构差异只在执行层覆盖 | **不建。** 建了就会有人往里塞东西，P2 立刻破 |

## 十、一句话结论

**58 想清楚"为什么"，59 想清楚"放哪里"，这一版想清楚"谁说了算"。**

答案是：**条款说了算。** 机构不参与配置，只参与执行；文档不决定归属，只被匹配；阶段不是开关，是证据形态的函数。
