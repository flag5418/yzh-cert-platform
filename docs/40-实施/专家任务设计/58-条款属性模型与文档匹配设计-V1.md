# 条款属性模型与文档匹配设计（V1）

> 2026-10-26 ｜ 基于邝敏威检查单 + GB/T 42061 条款树
> 前置：46（可建模性）、50（五层模型）、51（疑点状态机）、68（定位决策）

## 一、问题背景

### 现状诊断

当前 `cert_iso_clause` 只有骨架：

| 现有字段 | 能做什么 | 不能做什么 |
|---|---|---|
| `ClauseNumber` + `Title` | 树形展示条款编号 | 无法判断"这条要求什么" |
| `Description` | 存原文/摘要（已裁决全部置 NULL） | — |
| `StandardCode` / `ParentCode` | 关联标准、构建树 | — |
| `Sort` | 排序 | — |

**结论**：当前条款 = 目录索引，不是审核规则。企业文档来了，系统不知道"该去哪找什么、找什么字段、找不到算什么性质"。

### 核心发现

从邝敏威检查单（`Documents except for the above parts(4)-邝敏威.docx`）提炼的结构：

```
Clause条款  |  Requirements要求  |  Audit Evidence审核证据  |  NC/OFI
```

每一行都是：
- **条款编号**（如 `4.1`、`7.3`）
- **审核提问**（"组织如何确定内外部因素..."）
- **证据要求**（"查见...记录，编制人...日期..."）
- **判定结果**（NC/OFI/符合）

**产品机会**：把这套结构数字化，让系统能自动回答：
1. 企业有没有这份文档？
2. 文档里有没有必须有的字段？
3. 找不到/找不全算不算NC？

## 二、条款属性模型

### 2.1 属性分类（12类）

| 类别 | 字段 | 说明 | 示例 |
|---|---|---|---|
| **元数据** | `ShallLevel` | 强制程度 | shall / should / may |
| | `Applicability` | 适用范围 | 通用 / 按产品 / 按过程 |
| | `StageSwitch` | 阶段开关 | 二阶段,监督,再认证 |
| **证据要求** | `RequiredDocs[]` | 要求的文档类型 | ["程序文件", "记录", "报告"] |
| | `DocPatterns[]` | 文档命名匹配规则 | ["*设计开发*", "*设计*"] |
| | `RequiredFields[]` | 记录必须有的字段 | ["设计输入", "验证记录", "确认记录"] |
| | `EvidencePoints[]` | 证据收集要点 | [{"point":"...", "method":"文件评审"}] |
| **验证方式** | `VerificationMethods[]` | 如何验证 | ["文件评审", "访谈", "现场观察"] |
| | `DefaultLevel` | 默认证据层级 | L1 / L2 / L3 |
| | `SamplingDepth` | 抽样深度 | full / sampling |
| **NC规则** | `SeverityDefault` | 默认严重度 | major / minor / observation |
| | `MissingRule` | 缺失判定规则 | {"no_doc": "major_nc"} |
| | `NcDescriptionTemplate` | NC描述模板 | "未发现{clause}的{field}证据" |
| **机构配方** | `ProcessCode` | 关联过程编码 | design_dev |
| | `DeptCodes[]` | 涉及部门 | ["研发部", "质量部"] |
| | `MergeGroup` | 可合并检查的条款组 | ["7.3.1", "7.3.2"] |
| | `ChecklistQuestion` | 检查单提问原文 | "是否建立了设计开发控制程序？" |

### 2.2 完整实体设计（C#）

```csharp
/// <summary>
/// 条款属性 — 标准侧，每条一款，公共知识一次建成
/// </summary>
[SugarTable("cert_iso_clause_attr")]
public class ISOClauseAttribute : BaseEntity, ISoftDelete, IIsValid
{
    // ──── 关联 ────
    [StringLength(36)]
    public string ClauseCode { get; set; } = string.Empty;

    // ──── 元数据 ────
    [StringLength(20)]
    public string? ShallLevel { get; set; }

    [StringLength(50)]
    public string? Applicability { get; set; }

    public string? ApplicabilityRuleJson { get; set; }

    [StringLength(200)]
    public string? StageSwitch { get; set; }

    public string? ExclusionConditionsJson { get; set; }

    // ──── 证据要求 ────
    public string? RequiredDocsJson { get; set; }
    public string? DocPatternsJson { get; set; }
    public string? RequiredFieldsJson { get; set; }
    public string? EvidencePointsJson { get; set; }

    // ──── 验证方式 ────
    public string? VerificationMethodsJson { get; set; }
    [StringLength(10)]
    public string? DefaultLevel { get; set; }
    [StringLength(20)]
    public string? SamplingDepth { get; set; }

    // ──── NC规则 ────
    [StringLength(20)]
    public string? SeverityDefault { get; set; }
    public string? MissingRuleJson { get; set; }
    [StringLength(500)]
    public string? NcDescriptionTemplate { get; set; }

    // ──── 机构配方 ────
    [StringLength(50)]
    public string? ProcessCode { get; set; }
    public string? DeptCodesJson { get; set; }
    public string? MergeGroupJson { get; set; }
    [StringLength(500)]
    public string? ChecklistQuestion { get; set; }

    // ──── AI辅助 ────
    [StringLength(20)]
    public string? AiConfidence { get; set; }
    [StringLength(50)]
    public string? AiSource { get; set; }
    [StringLength(20)]
    public string? ReviewStatus { get; set; }
}
```

## 四、企业文档自动匹配链路

```
企业上传文档
    ↓
OCR / 解析（markdown + 字段级提取）
    ↓
① 编号规则匹配（确定性）
   KSY-QMS-P-17-01 → 8.5.1（从命名规则解析）
    ↓
② 条款属性匹配（基于属性）
   DocPattern "*设计开发*" → 匹配 Clause 7.3
   RequiredFields ["设计输入", "设计输出"] → 检查文档是否有这些字段
    ↓
③ 字段级校验（结构化比对）
   特殊岗位名单 → 检查8个字段是否在
    ↓
④ 生成映射结果
   ClauseDocMapping: clause_code, file_code, match_type, confidence, is_applicable
    ↓
⑤ 疑点引擎
   找不到证据 → cert_expert_doubt_item（51号状态机）
    ↓
⑥ 证据链组装
   证据归位 → 检查单预填件（双栏）
```

### 关键点

1. **编号规则匹配是确定性逻辑**，不依赖LLM（科斯亚 `KSY-QMS-P-17-01` → 8.5 是一等映射）
2. **字段级校验是核心价值**：特殊岗位名单的8个字段在不在，决定了"声称-证据"规则能否触发
3. **LLM只做兜底**：编号匹配失败的，用语义分析，但标记 `confidence=low`，人工确认

## 五、实施建议

### 5.1 优先级

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | 扩 `cert_iso_clause` 表 | 加 `AttributesJson` 大字段（JSON列），把12类属性收敛为3-4个JSON列 |
| P1 | 填13485的~70条属性 | 从GB/T 42061逐条提取，专家校对 |
| P2 | 做字段级schema | `RequiredFields[]`是最难填的，需要从案例文件逐份提取 |
| P3 | 验证 | 拿科斯亚/尚龙资料跑一遍，看映射准确率 |

### 5.2 不要做的事

- ❌ 不要一次加12个独立列 → 改用JSON列，后续可演进
- ❌ 不要试图自动填充全部属性 → 先填核心20条（7.3/7.4/7.5/8.2/8.3/4.2/6.2/6.3/6.4），其余逐步补
- ❌ 不要依赖LLM做编号映射 → 编号规则是确定性逻辑，LLM只做语义兜底

### 5.3 验证标准

- 映射准确率 ≥ 80%（编号匹配）
- 字段级校验准确率 ≥ 70%（字段存在性）
- 人工确认率 ≤ 20%（低置信度结果才需人工）
