## 一、产品定位（★ 本篇最重要的一节）

### 1.1 核心主张：用流程化替代人工复核机制

| 维度 | 传统体系认证审核 | 本系统（CertExpert） |
|---|---|---|
| 数据来源 | 审核员**人工填写**检查表 | **企业文档真实内容**流程化提取 |
| 数据可信度 | 不可信 → **必须**人工复核兜底 | 流程保证**先天的准确性和追溯性** |
| 复核机制 | 审核组长**逐条人工复核** | 流程化设计，**复核环节可被信任替代** |
| 审核组机制 | 需要审核员 + 审核组长 + 更高权限 | **不需要**（前期不分角色） |
| 交付 | 纸质/Word 报告 | 流程化结果 + Excel |

**推论（推翻 11 号 §2.2）**：

| 11 号原设计 | 作废原因 |
|---|---|
| 一次审核事件 2 轮执行（审核员初稿 + 审核组长复核） | 复核是人工审核时代的产物。本系统用流程化保证准确性，**不需要第二层人工复核** |
| 「继续/复核」任务模式 | 同上。**取消该模式** |
| 审核员 / 审核组长角色权限 | 前期不区分（D21）。后续「把菜单分配给审核组长」是**独立迭代** |
| **任务系统内的认可/修改/批准/导出** | **D31**：这些动作属于结果菜单，任务系统只管执行与生死 |

> ⛔ **但"专家认可"环节保留**。理由：承认"系统算得对"不等于"任务完成"。专家认可 = 专家确认结果符合实际，**这是交付承诺，也是审计要求**（用户原话：「所有的结果，需要专家手动认可，必须有认可记录」）。

### 1.2 三个核心功能（不是全平台）

```
① 审核员 NC 检查        ② 审核员报告         ③ 企业资料规范化
        ↓                      ↓                     ↓
   3 个独立菜单            （与①同一套机制）      （上游：数据来源）
```

⛔ **明确不是**：认证项目全生命周期平台、证书管理、机构管理、收费、审核员排班、监督评价。

**理由（用户原话）**：

> 「初衷就是为了解决审核员的 nc 检查和报告 2 个核心问题，和企业资料的规范化问题，用 3 个核心功能来形成服务或产品，**迅速占领市场，形成产值**」

**3 菜单 + 不做的事**：

| 菜单 | 回答的问题 | 频率 |
|---|---|---|
| **任务系统** | "我要做一次检查/出一次报告，现在什么状态？" | 低频（触发） |
| **NC 检查记录** | "这个企业这个阶段的每条 NC 检查项，现在结论是什么？能改吗？能导出吗？" | **高频（日常）** |
| **系统认证报告** | "报告的每个章节现在是什么内容？能改吗？能导出吗？" | **高频（日常）** |

> 用户原话：「nc 检查，报告 2 个菜单分配给审核组长都是后面的事情，**我们前期是完成功能和逻辑设计即可**」

### 1.3 认证周期模型：本期不做

| 项 | 决策 |
|---|---|
| 认证周期（`cert_cycle`） | ❌ **不做** |
| 审核事件（`cert_event`，S1/S2/SV/RC） | ❌ **不做** |
| 预留字段 | ✅ `cert_expert_task.AuditEventCode`（可空）+ `cert_expert_task.AuditEventName`（可空）。**0.2 人天** |
| 未来补做成本 | 低（字段已在，不需迁移） |

**理由**：

| 理由 | 说明 |
|---|---|
| 周期是管理功能，非执行功能 | 专家日常只需"查结果、改结果、导出"。证书到期提醒是管理层需求 |
| 3 年时间跨度 | 系统上线时存量企业多在周期中段，周期起点难准确回填 |
| 不影响核心逻辑 | 周期只影响**列表分组和筛选**，不影响执行、认可、导出 |
| 用户定位 | 「复审我们可以先不设计」 |

> ⚠️ **但"一个阶段下有多个任务"必须支持**（1.5 节）。这与"不做周期模型"不冲突 —— 前者是执行层，后者是管理层。

### 1.4 ★ 三个菜单的职责边界（D31-D33）

> **这是本次设计的核心边界，编码时不得越界。**

| 菜单 | 只做这些 | ⛔ 绝不做这些 |
|---|---|---|
| **任务系统** | 创建任务 · 提交执行 · 看进度 · 看任务包含哪些项 · **归档** · **作废** · **取消** · 取消/重试失败项 · 看补录清单 | ⛔ 认可 ⛔ 修改结果 ⛔ 批准 ⛔ 导出 |
| **NC 检查记录** | 看结论 · **认可** · **修改** · 看历史轮次 · **导出** · 归档/作废/取消（针对结果） | ⛔ 创建任务 ⛔ 触发执行 |
| **系统认证报告** | 看章节内容 · **认可** · **修改** · 沿用上轮 · **导出** · 归档/作废/取消（针对结果） | ⛔ 创建任务 ⛔ 触发执行 |

**为什么这么切**：

| 理由 | 说明 |
|---|---|
| 任务系统是**执行管理** | 它的产出是"一批结果"，但**专家的判断动作不在这**。专家不该为了改一条结论先找到那个任务 |
| 结果菜单是**日常工作台** | 专家 90% 的操作在这里：查、改、认可、导出 |
| 任务只管**生死** | 归档/作废/取消是对"这次执行"的管理，不涉及内容判断 |

**关键推论：**

| 推论 | 影响 |
|---|---|
| ⛔ 任务系统**没有** [认可] [修改] [批准] [导出] 按钮 | UI 简化一半 |
| ⛔ 任务系统**没有** `approved` 状态 | 状态三层进一步简化（见 §3.5） |
| ✅ 任务完成后**自动**成为结果记录中的一轮 | 专家在结果菜单里看到的是"已生效 / 待认可"的混合列表 |
| ✅ 归档/作废/取消在**两个地方都能操作** | 任务菜单管"这次执行"，结果菜单管"这个检查项当前的结论来源" |

### 1.5 结果菜单 = 左树右表（D32）★ 2026-09-30 层级已裁决

**不是单表列表**，而是「**企业 → 阶段 → 任务**」**三级**树形导航 + 右侧结论表。

**用户裁决原文（2026-09-30）**：

> 「这个是我们设计 **nc 检查结果、体系认证报告结论**中设计需要的，**左侧是企业 + 阶段 + 任务，右侧是结果**。如果是 nc 就是 nc 检查的列表，如果是报告就是报告章节的列表，**审核员可以勾选进行审批，或直接修改，整体列表可以导出**」
>
> 「（追加）**点「阶段」节点不显示结果，必须选到任务**」

| # | 规则 | 说明 |
|---|---|---|
| 1 | **树恒为 3 级**：企业 → 阶段 → 任务 | ⛔ **「标准」不进树** |
| 2 | **两个菜单各有一棵自己的树**，按 `TaskType` 过滤 | NC 菜单只显示 `NC_CHECK` 任务；报告菜单只显示 `REPORT_GENERATE` 任务 |
| 3 | **「标准」落到右表的列 + 顶部筛选** | 一个任务跨 N 标准是常态（`ScopeType=FULL`），用列区分而非树分组 |
| 4 | **只有「任务」节点出结果** | 点企业 / 阶段节点 → 右表**空**（不发请求） |
| 5 | **右表操作**（两菜单一致） | 勾选**批量审批** · 单个**直接修改** · **整体列表导出** · 看历史轮次 |
| 6 | 树上「任务」节点 = 该次执行的**只读投影**（D33 不变） | 右表 = 该 `TaskCode` 的结果行（`cert_expert_nc_result` / `cert_expert_report_result`） |

> ⚠️ **本节推翻了 §八 D32 的「四级树」草图**（原草图是「企业 → 阶段 → 标准 → 任务」，且**把标准放在任务之上**，与数据模型「任务在标准之上」相反）。
> **裁决：以本节为准，3 级。**

理由：

| 理由 | 说明 |
|---|---|
| 层级天然存在 | 结论总是属于「某企业 某阶段 某次任务」，**三级层次是事实** |
| 大数据量 | 一个企业 3 年 × 3 标准 × 6 阶段 → 几十次任务、数千条结论。扁平列表没法用 |
| 与规则库页一致 | 管理端 `nc-config` / `report-rule` 已是左树右表（`useFileTree` 3 层），专家端沿用同一交互，**降低理解成本** |
| 任务系统与结果菜单的桥梁 | 树上的"任务"节点就是任务系统的**只读投影** —— 点任务看该次执行了哪些项 |

### 2.1 三种来源

用户原话：

> 「新建任务的时候，是从已有任务中，**重新执行（整体）**，还是**局部更新（局部）**，还是**开启全新任务**，都是**任务平台的引导**来实现的」

| 来源 | `TaskSource` | 业务含义 | 沿用未跑项 | 结果轮次 |
|---|---|---|---|---|
| **全新任务** | `NEW` | 该企业该阶段该标准**第一次**做 | 无（规则库全部视为"未检查"） | 各检查项第 1 轮 |
| **整体重执行** | `REDO` | 同阶段重跑一遍（如企业换了全套文件） | 无 | 每项**新轮次** |
| **局部更新** | `PATCH` | 只补跑部分（如新增文件、整改验证） | ✅ **沿用** | 仅勾选项产生新轮次 |

> ⛔ **注意 11 号的「继续/复核」模式已作废**。这里的三种来源都是"要做一次新的检查"，不是"复核上一轮"。

### 2.2 三种来源 × 全局/局部 的组合

`TaskSource` 和 `ScopeType`（`FULL`/`PARTIAL`）**正交**：

| | `ScopeType=FULL` | `ScopeType=PARTIAL` |
|---|---|---|
| `TaskSource=NEW` | 首次全局检查 | 首次只查部分（其余标记"未检查"） |
| `TaskSource=REDO` | 全阶段重跑 | 重跑大部分，留几项沿用 |
| `TaskSource=PATCH` | （语义重复，等价 FULL+REDO） | **最常用**：补跑/整改验证 |

> ⚠️ `REDO` + `FULL` 和 `REDO` + `PATCH` 的区别：前者全部重算，后者留几项沿用。
> ⚠️ `PATCH` + `FULL` 在语义上等同于 `REDO` + `FULL`（都是全部重算，只是"起点"不同）。**前端应在选择时提示这一点**，避免专家困惑。

### 2.3 任务平台引导流程（用户强调的重点）

> 「都是**任务平台的引导**来实现的」

这意味着**不是专家自己懂这些概念，而是系统在引导他做选择**。向导设计：

```
第 1 步：选企业 + 阶段
         ↓  系统立即告知：该企业该阶段已有 N 个任务，当前生效结果是第 M 轮
第 2 步：选任务来源
         ┌────────────────────────────────────────────────┐
         │ 这是该企业该阶段的首个任务？                   │
         │  ○ 开启全新任务                               │
         │                                                │
         │ 已有任务，要再跑一次？                         │
         │  ● 重新执行（整体再跑一遍）                    │
         │  ○ 局部更新（只补跑部分）                     │
         │                                                │
         │  [看看有哪些选项] ← 悬停解释每个选项的后果      │
         └────────────────────────────────────────────────┘
         ↓  系统根据来源自动预设第 3 步的范围
第 3 步：选范围
         · NEW  + FULL  → 预勾选全部规则/章节
         · NEW  + PARTIAL → 不预勾选，专家选
         · REDO + FULL  → 预勾选全部
         · REDO + PARTIAL → 预勾选全部，专家取消不需要的
         · PATCH        → ★ 预勾选「上次有新文件的」「上次不符合未关闭的」
                          专家在此基础上增减
第 4 步：确认 → 创建
```

**向导里的"系统告知"是关键设计**。例如：

```
┌─ 第 1 步 · 选择企业与阶段 ──────────────────────────┐
│                                                       │
│  企业    [XX有限公司                        ▼]         │
│  阶段    [第二阶段审核 ▼]                              │
│                                                       │
│  ── 该企业该阶段的现状 ──────────────────────────     │
│  ISO 9001:2015 阶段：第二阶段审核                      │
│  · 已有任务 3 个（1 个已归档 / 2 个已取消）            │
│  · 当前生效检查项：40 条（均来自 2025-09 的任务）      │
│  · 历史结果轮次：平均 3.2 轮 / 检查项                  │
│  · 建议：若本次为企业换文件后的复核，选择「重新执行」   │
│                                                       │
│  [创建新任务]   [从已有任务出发]                        │
└───────────────────────────────────────────────────────┘
```

**"从已有任务出发"的交互**：

```
┌─ 从已有任务出发 ──────────────────────────────────┐
│                                                      │
│  选择基准任务                                         │
│  ┌──────────────────────────────────────────────┐  │
│  │ TSK-20250915-0003  XX公司 局部更新(5项)       │  │
│  │   已归档  创建于 2025-09-15  张专家           │  │
│  ├──────────────────────────────────────────────┤  │
│  │ TSK-20250610-0001  XX公司 全新任务(全量)     │  │
│  │   已作废  创建于 2025-06-10  张专家           │  │
│  └──────────────────────────────────────────────┘  │
│                                                      │
│  选择出发方式                                         │
│  ○ 重新执行（整体）：以该任务的范围为基准，全部重跑   │
│  ● 局部更新（局部）：在【当前生效结果】基础上补跑     │
│                                                      │
│  下一步将展示：本次可选项 40 条（已生效 40 / 未检查 0）│
└──────────────────────────────────────────────────────┘
```

> ⚠️ **注意"局部更新"的基准是【当前生效结果】，不是"基准任务的历史结果"**。因为中间可能又跑过其他任务。这与用户原话一致：「局部更新……不影响已经计算过的结果」。

### 2.4 局部更新的"已生效"语义

```
XX公司 / ISO9001 / 第二阶段审核

检查项总数 40   ·   已生效 40   ·   未检查 0

上次检查时间分布：
  2025-09  第二阶段审核（全局）    40 项   ← 当前生效
  2024-06  第一次监督审核（局部）   18 项   ← 已被 2025-09 覆盖
```

**局部更新时**：

```
☑ 8.1 运行策划        （建议勾选：上次不符合已关闭需验证）
☑ 7.5 成文信息        （建议勾选：企业新增了程序文件）
☐ 4.1 体系边界        （沿用 2025-09 结论：符合，审核时间保持 2025-09）
☐ 5.1 领导作用        （沿用 2025-09 结论：符合，审核时间保持 2025-09）
...
```

> ⛔ **沿用项的"上次检查时间"保持原值**（用户裁决）。理由：监督审核没查的条款不能说"这次也查了"。这个时间字段是审计凭据。

## 三、状态三层分离（★ 状态问题"后定"的解法）

### 3.1 为什么拆三层

用户裁决：

> 「归档，是本次任务完美结束，结果可信，未来不再修改；取消：该任务由于某些原因（企业资料不符合），等任务无效；**作废：针对该结果不被认可**。这些都是**状态管理和状态控制的问题**，我们可以根据体系认证的业务，明确出来，**或先完成业务逻辑最好再设计**」

**三层正交，各管各的**：

```
┌─────────────────────────────────────────────────────────┐
│ 第 3 层 · 存续状态  LifecycleStatus                       │
│   active | archived | cancelled | voided                   │
│   —— 管"这个任务还算不算数"                               │
│   —— 人工控制，可逆                                       │
│   归档：完美结束，结果可信（=approved 的终态）              │
│   取消：因故无效（企业资料不符合）                          │
│   作废：结果不被认可（专家改完了，这轮不算）                 │
├─────────────────────────────────────────────────────────┤
│ 第 2 层 · 结果状态  ReviewStatus                          │
│   not_started | pending_review | reviewed | frozen          │
│   —— 管"结果专家看过了吗"                                 │
│   —— 本期实现                                             │
├─────────────────────────────────────────────────────────┤
│ 第 1 层 · 执行状态  ExecStatus                            │
│   draft | pending_run | running | completed | failed        │
│   —— 管"机器跑完了吗"                                     │
│   —— 本期实现，机器管，不可逆                              │
└─────────────────────────────────────────────────────────┘
```

### 3.2 三层的对应关系与"完成"的定义

| 三层组合 | 业务含义 | 是否产生生效结果 |
|---|---|---|
| `completed` + `not_started` + `active` | 跑完了，专家还没看 | ⭐**是**（但未认可，不可导出定稿） |
| `completed` + `reviewed` + `active` | 跑完了，专家认可了 | ⭐**是** |
| `completed` + `reviewed` + `archived` | 归档：完美结束 | ⭐**是**（且冻结） |
| `completed` + `reviewed` + `voided` | 作废：结果不被认可 | ❌ 否（回退到上一轮） |
| `completed` + `*` + `cancelled` | 取消：任务无效 | ❌ 否（结果作废） |
| `cancelled` + `*` + `cancelled` | 执行中取消 | ❌ 否 |
| `failed` + `*` + `cancelled` | 执行失败 | ❌ 否 |

**"完成"的唯一定义**（本系统对外表述）★ 2026-09-30 统一（原 §3.2 与 §3.5 各写一套，**已消解**）：

> **任务"已结束" = `ExecStatus = completed`**（执行跑完）
> **或** `LifecycleStatus ∈ {archived, cancelled, voided}`（已归档 / 已取消 / 已作废）
>
> ⇒ **"未结束" = `LifecycleStatus='active'` 且 `ExecStatus <> 'completed'`**
>
> ⛔ **不看 `ReviewStatus`** —— 「全部已认可」是**检查项级别的状态**，不是任务状态。任务可能部分认可、部分没认可，任务本身照样"已结束"（D31 裁决，见 §3.5）。
> ★ **业务锁只认这个定义**（用户 2026-09-30 二选一裁决：**"执行跑完即解锁"**）→ 完整实现见 `02 号 §六`。

### 3.3 "一个阶段可有几个有效任务"（用户提问）★ 2026-09-30 已裁决

> **原答案（V1，已作废）**：「允许同阶段多 `active` 任务，业务锁**不锁**能否建第二个任务」

**用户裁决原文（2026-09-30）**：

> 「关于任务的控制，如果**企业 阶段 分类（nc 还是报告）**，还未结束，不允许开启新的任务，**我不允许同一个阶段下，一个 nc 任务还没完成，又开启另一个 nc 任务**」

**⇒ 新规则：同「企业 + 阶段 + `TaskType`」**只允许一个未结束任务**。**

| 情况 | 是否允许 | 说明 |
|---|---|---|
| 同企业同阶段，**一个 NC 任务未结束** → 再建 NC 任务 | ❌ **拒绝** `BIZ_LOCKED` | ★ 新规则 |
| 同企业同阶段，**一个 NC 任务未结束** → 建**报告**任务 | ✅ **允许** | ★ 分类型（**推翻 D15**） |
| 同企业同阶段，NC 任务 `completed`（未归档）→ 再建 NC 任务 | ✅ 允许 | ★ "执行跑完即解锁"（用户裁决） |
| 同企业同阶段，NC 任务 `failed` → 再建 NC 任务 | ❌ 拒绝 | `failed` 也算未结束，**必须显式取消**才能解锁 |
| 同企业同阶段，NC 任务 `archived`/`cancelled`/`voided` | ✅ 允许 | 已结束，不占锁 |

**两处推翻**：

| 被推翻 | 原文 | 新规则 |
|---|---|---|
| **D15** | 「**不分任务类型**：NC 未结束 → 报告也不能建」 | **分类型**，NC / 报告互不阻塞 |
| **D28** | 「**允许**同阶段多 `active` 任务」 | **同类型只允许一个未结束任务** |

> ★ **完整实现（锁定义 / 两把锁 / 生成列 + 唯一索引并发兜底 / C# 代码 / 前端配合）→ `02 号 §六 业务锁`**。
> ★ **对向导的影响**：第 1 步选完企业+阶段后立刻校验，被占用则**禁用「下一步」**并显示占用任务。
> ⛔ **不存在"技术上不安全"的问题**（原 V1 说"允许多 active 技术上安全"）—— 现在**业务上就不允许**，不需要再论证技术安全性。

### 3.4 状态控制矩阵（后定，先记录）

| 动作 | 允许的前置状态 | 副作用 |
|---|---|---|
| 归档 | `completed` + `reviewed` + `active` | 结果冻结，不可再改 |
| 取消 | 任意非终态 | 结果作废，当前生效回退到上一轮 |
| 作废 | `completed` + `reviewed` + `active` | 同取消，但语义是"结果不被认可" |
| 恢复 | `archived`/`cancelled`/`voided` → `active` | 恢复生效结果（若未被更新轮次覆盖） |
| 删除 | 仅 `cancelled` + 从未产生结果 | 软删 |

> ⚠️ **"回退到上一轮"是状态管理的难点**。作废一个任务后，它产生的轮次不能物理删（审计要求），但不能再是"当前生效"。方案：
> - 检查项实体的 `CurrentResultCode` 指向作废任务的轮次 → 需重新指向「上一个 `active/archived` 任务的轮次」
> - 实现：查该检查项的轮次列表，按 `TaskCode` 的 `LifecycleStatus` 过滤掉 `cancelled/voided`，取时间最新的
> - **待后定**（属于状态管理范畴）

> ★ 用户裁决的右表三件操作：**勾选批量审批 · 单个直接修改 · 整体列表导出**。
