## 二、P0：4 个新断点（25 号未记载）

### P0-1 ★ 机器不出结论，界面却显示「符合」——**语义造假**

| 环节 | 事实 | 证据 |
|---|---|---|
| 引擎侧 | `AutoStatus` 由 **关键词嗅探** 得出：`text.Contains("不符合" / "不满足" / "nonconform" / "\"ng\"")` ⇒ `ng`，否则 `ok` | `ExpertItemExecutors.cs:248-273` |
| 引擎侧注释 | 自己写明「⚠️ 只做执行是否成功的判定 + **轻量关键词识别**」「**最终是否符合由专家确认**（`Conformity` 机器不写）」「isNg **仅作提示，非结论**」 | 同上 `:243-246`、`:265` |
| 前端 | `AUTO_STATUS_MAP = { ok: '符合', ng: '不符合', … }`，且 `ok` 打 **绿色 success 标签**，列头叫「自动结果」 | `cert-share/src/constants/expert-task.ts:85-101` |

**实测截图证据**（`/nc-results` → TSK-20260930-0001）：

```
复审规则01   轮次1   自动结果=符合(绿)   结论=不符合(红)   严重度=一般不符合   结论来源=人工修改
```

同一行左边说「符合」右边说「不符合」。**专家读到的是"系统判了符合，被人改成了不符合"，而事实是系统根本没判。**

**后果分级**：
- 产品价值主张（README 核心判断：「自动算出一个结果 → 专家认可或改」）**未兑现** —— 机器只产出"执行成功/失败"，不产出结论；
- 每条 NC 的结论 100% 由专家手填 → 「一键 NC 检查」退化成「一键跑一遍并列出待填项」；
- 导出物（见 P1-1）会把这句假话带出去。

**修法（两阶段）**：

| 阶段 | 内容 | 工作量 |
|---|---|---|
| **止血** | 文案改口径：`ok→'执行成功·待判定'`、`ng→'疑似不符合'`，标签降为 `info/warning`；列头「自动结果」→「执行情况」 | 0.2d |
| **兑现** | 让 AI 出**结构化结论**：`llm_extract`/`ai_node` 输出 `{conformity, severity, evidence, confidence}`，`MapNcResult` 只读该结构，⛔ 删关键词嗅探；`Conformity` 由机器写、专家改 | 1d（含规则模板约定） |

> ⚠️ 阶段二与 25 号 §7.1「Skill 自动生成缺失信息」是**同一类业务裁决**（AI 输出能否直接采信驱动 NC 结论），需你先定口径再动代码。

### P0-2 ★ 执行失败被吞成「已完成」→ 提前解锁 + 无法重试

```
引擎返回 resp.IsSuccess=false
  → MapNcResult 返回 AutoStatus=failed
  → ExecuteAsync 仍 return { Success = true }          ← 断点在此
  → FinalizeAsync: outcome.Success ⇒ ItemStatus='completed'
  → RefreshTaskAsync: failed==0 ⇒ task.ExecStatus='completed'
  → D36 业务锁提前释放；CanRetry=false ⇒ 「重试失败项」按钮永不出现
  → 而 retry-failed 只重置 ItemStatus='failed' 的项 ⇒ 这类失败在机制上不可重试
```

| 证据 | 位置 |
|---|---|
| `return new ItemExecOutcome { Success = true, Message = "工作流执行失败（已记录原因，可重试）" }` | `ExpertItemExecutors.cs:231-239` |
| 成功即置 `completed` | `ExpertTaskQueueRunner.cs:273-280` |
| `failed==0` 即判任务 `completed` | `ExpertTaskQueueRunner.cs:465-482` |
| 重试只认 `ItemStatus='failed'` | `ExpertTaskService.cs:1244` |

**矛盾点**：提示语写「可重试」，机制上不可重试。报告侧同构（`autoStatus=failed` 但 `IsSkipped` 不含 failed，`ExpertItemExecutors.cs:524-529`）。

**修法**：`autoStatus==failed` ⇒ `Success=false, Retryable=true`；终态失败落 `ItemStatus='failed'`，让 P0-4 的取消出口有对象可取消。**0.3d**

### P0-3 ★ 租约只在进程启动时回收一次，执行期无续期 → 整条队列永久停摆

| 事实 | 证据 |
|---|---|
| `ReapStaleAsync` **全仓唯一调用点**在 `ExecuteAsync` 启动处，主循环无周期回收 | `ExpertTaskQueueRunner.cs:56`（对照主循环 `:65-86`） |
| 领取条件含「该队列当前无 `running` 项」（同队列串行） | `:109-111` |
| 抢占 UPDATE 设 `LockedUntil = now + 10min`，但执行期**无续期** | `:117-127` |
| 先抢占置 `running`，再在 `Task.Run` 内 `await _sem.WaitAsync`（并发闸 3） | `:69-72` |

**后果链**：worker 崩溃 / 单次执行 >10min ⇒ 该项永远 `running` ⇒ `NOT EXISTS running` 让**整条队列再不发任何项** ⇒ 任务永不 completed ⇒ **业务锁永不释放**。队列数 >3 时更糟：已抢占的项在闸外排队等信号量，10 分钟租约白白烧掉。

**修法**：① 主循环每轮（或每 30s）跑一次 `ReapStaleAsync` ② 执行期心跳续租（`LockedUntil` 每 60s 更新）③ 把 `_sem.WaitAsync` 提到抢占**之前**。框架层 `QueueManager` 已有 ①② 的成熟实现，可对照移植。**0.5d**

### P0-4 ★ 没有取消 / 归档 / 作废端点 → `failed` 任务死锁，无出口

`ExpertTaskController` 实测**只有 10 个端点**：

```
lock-check · candidates · create · detail · logs · gaps · submit · queue/start · queue/pause · retry-failed
```

| 设计明确要求 | 状态 |
|---|---|
| 21 号 §2.3：「`failed` 也算未结束，**必须显式取消才能解锁** —— 这是刻意的：强制专家处理失败任务」 | ❌ 取消端点不存在 |
| 23 号 §2.3：按钮可用性三层推导，「取消在任何未归档状态可用」「`completed` 才可归档」 | ❌ 详情页只有「查看结果」 |
| README D31：任务系统职责含 **归档 · 作废 · 取消** | ❌ 三个都没有 |

**当前未暴露纯属运气**：库里 2 个任务都是 `completed`。而 **25 号 §6.3 的设计目标恰恰是「缺数据 ⇒ 任务项自动失败」** —— 一旦按 25 号开工，`failed` 任务会立刻出现，届时该企业该阶段该分类**永久锁死**。

⇒ **P0-4 是 25 号实施的前置依赖，不是可延后的收尾项。** 修法：`cancel`（`LifecycleStatus='active'→'cancelled'`，解锁）+ `archive`（`completed` 后归档），详情页补两个按钮 + 状态推导。**0.5d**
