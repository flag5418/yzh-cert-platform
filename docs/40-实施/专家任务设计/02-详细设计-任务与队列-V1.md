## 一、任务创建

### 1.1 前置校验链（顺序不可调换）

```
POST /api/ExpertTask
  │
  ├─① 租户解析   WorkspaceContextService.Resolve()
  │              → OrgCode（禁止从 body 取）
  │
  ├─② 业务锁检查 O1   ★ 见 §6
  │   SELECT 1 FROM tsk_task
  │   WHERE EnterpriseCode=? AND StageCode=? AND OrgCode=?
  │     AND TaskStatus NOT IN ('approved','cancelled','failed')
  │   LIMIT 1
  │   命中 → 409 { code:'BIZ_LOCKED', message:'该企业在该阶段存在进行中的任务，请先完成' }
  │
  ├─③ 企业-阶段-标准三元组校验
  │   读 cert_enterprise_stage（EnterpriseCode + StageCode + StandardCode）
  │   · ScopeType=FULL     → 用该三元组里 IsValid=1 的全部 StandardCode
  │   · ScopeType=PARTIAL  → 用 SelectedItemCodes 里的 StandardCode 去反查
  │   校验：body 里的每个 StandardCode 必须在该企业该阶段的已分配标准内
  │   失败 → 400 { code:'STANDARD_NOT_ASSIGNED' }
  │
  ├─④ 局部任务单标准校验 D03
  │   SelectedItemCodes 反查出的 StandardCode 去重后 size > 1
  │   → 400 { code:'CROSS_STANDARD_NOT_ALLOWED',
  │            message:'局部任务一次只能提交一个标准下的检查项/章节' }
  │
  ├─⑤ 阶段有效性
  │   cert_cert_stage.Code 存在且 IsValid=1
  │   失败 → 400 { code:'STAGE_INVALID' }
  │
  └─⑥ 事务写入（见 §1.3）
```

### 1.2 范围解析算法

```csharp
// 输入
//   TaskType   : NC_CHECK | REPORT_GENERATE
//   ScopeType  : FULL | PARTIAL
//   StandardCodes : FULL 时 = 企业该阶段全部已分配标准；PARTIAL 时 = 从勾选项反查
//   SelectedItemCodes : PARTIAL 时的勾选 Code 列表（规则 Code 或章节 Code）
//
// 输出：List<(StandardCode, List<ItemCode>, ItemType)>

IEnumerable<(string Std, List<string> Items)> ResolveScope(
    string taskType, string scopeType, string enterpriseCode, string stageCode,
    List<string> standardCodes, List<string> selectedItemCodes)
{
    // ① 确定候选规则集合
    //    NC_CHECK      → cert_validation_rule  where IsValid=1
    //                              AND OrgCode=? AND StandardCode IN(...) AND PhaseCode=?
    //    REPORT_GENERATE → rpt_report_section   where IsValid=1
    //                              AND OrgCode=? AND StandardCode IN(...) AND PhaseCode=?
    //
    // ★ OrgCode 这里用【认证机构 CbCode】，不是专家工作区 OrgCode！
    //   规则是企业无关的全局配置，归认证机构所有。
    //   而任务表的 OrgCode 是【专家工作区】。两者同名不同义 → 见 §9 口径表。

    var candidates = LoadActiveRules(taskType, standardCodes, stageCode);

    // ② FULL：全取
    if (scopeType == "FULL")
        return candidates.GroupBy(r => r.StandardCode)
                         .Select(g => (g.Key, g.Select(x => x.Code).ToList()));

    // ③ PARTIAL：按 Code 精确取，且校验每项的 StandardCode 落在请求的标准内
    var picked = candidates.Where(r => selectedItemCodes.Contains(r.Code)).ToList();

    if (picked.Count != selectedItemCodes.Distinct().Count())
        throw new BizException("PARTIAL_ITEM_NOT_FOUND",
            "勾选项中包含无效或不属于该企业该阶段的检查项/章节");

    return picked.GroupBy(r => r.StandardCode)
                 .Select(g => (g.Key, g.Select(x => x.Code).ToList()));
}
```

> **PARTIAL 的一个隐含约束（D03 的实现细节）**：因为返回结果按 `StandardCode` 分组，若勾选项跨了 2 个标准，会产出 2 个子任务 —— 这在数据上可行，但用户明确要求「每次只能提交一个标准下的队列」。因此**在 §1.1 步骤 ④ 提前拦截**，不进入分组逻辑。

### 1.3 创建事务

```sql
BEGIN;

-- ① 任务头
INSERT INTO tsk_task (
  Code, OrgCode, TaskNumber, TaskType, ScopeType,
  EnterpriseCode, EnterpriseName,
  StageCode, StageName, StandardCodes, StandardNames, StandardCount,
  TaskStatus, TotalItemCount, PendingCount, GapCount,
  CreateBy, CreateName, CreateTime, IsValid
) VALUES (
  @Code, @OrgCode, @TaskNumber, @TaskType, @ScopeType,
  @EnterpriseCode, @EnterpriseName,
  @StageCode, @StageName, @StandardCodesJson, @StandardNamesJson, @StandardCount,
  'draft', 0, 0, 0,
  @CreateBy, @CreateName, NOW(), 1
);
-- StandardCodes 存 JSON 数组，字段名用复数避免与单值混淆
-- ★ 之所以冗余存 StandardCodes/StandardNames：任务列表要显示「ISO9001+ISO14001+ISO45001」
--   不必每次 JOIN；标准后续改名也不影响历史任务的显示。

-- ② 标准子任务（D02：1 任务 → N 子任务）
INSERT INTO tsk_task_standard (Code, TaskCode, StandardCode, StandardName, SubStatus, ...)
VALUES (@SubCode, @TaskCode, @StdCode, @StdName, 'draft', ...);

-- ③ 任务项（核心）
INSERT INTO tsk_task_item (
  Code, OrgCode, TaskCode, SubTaskCode, EnterpriseCode, StageCode, StandardCode,
  ItemType, ItemCode, ItemName, ItemNameEn, ClauseCode, ClauseNumber, ClauseTitle,
  WorkflowCode, SeverityDefault, JudgeMode,
  AutoStatus, ReviewStatus, ReviewStatus,  -- 'none' / 'pending'
  Sort, CreateBy, CreateTime, IsValid
) VALUES ...;  -- 每个子任务每项一行

-- ④ 队列（每个子任务 1 个）
INSERT INTO tsk_task_queue (Code, OrgCode, TaskCode, SubTaskCode, StandardCode, QueueType, ScopeKey, Status, TotalCount, ...)
VALUES (@QueueCode, ..., 'pending', @ItemCount, ...);

-- ⑤ 队列项
INSERT INTO tsk_task_queue_item (Code, QueueCode, TaskItemCode, ItemType, ItemCode, Seq, Status, MaxRetryCount, ...)
VALUES ...;

-- ⑥ 回写任务头计数
UPDATE tsk_task SET TotalItemCount=@n, PendingCount=@n WHERE Code=@TaskCode;

COMMIT;
```

**事务边界说明**：步骤 ③ 一次插 N 行（N = 该企业该阶段该类型的全部规则数，实测 ISO9001 一个阶段约 20-40 条，可接受）。若未来单任务超 500 项，改为分批 `INSERT ... SELECT` 或批处理（见 10 号 Q5）。

## 二、完备性检查（D04 / D05 的落地）

### 2.1 依赖收集

完备性检查的核心是回答一个问题：**这个企业这个阶段跑这些规则，缺哪些数据？**

答案需要**反向解析规则的工作流 DAG**，把 DAG 里所有"取数节点"引用的字段/表格抽出来。

```csharp
IReadOnlyList<DataDependency> CollectDependencies(
    string taskType, IReadOnlyList<string> itemCodes)
{
    // ① 查规则
    //    NC_CHECK       → cert_validation_rule.RuleJson（工作流 DAG JSON）
    //    REPORT_GENERATE → rpt_report_section.WorkflowConfig（或 WorkflowJson）
    //    ★ 两者字段名不同！详见 §9 字段映射表
    //
    // ② 用 WorkflowConfigParser 解析 DAG
    var dag = WorkflowConfigParser.Parse(rule.WorkflowJson);
    //
    // ③ 遍历节点，按节点类型抽依赖
    foreach (var node in dag.Nodes)
    {
        switch (node.Type)
        {
            case "docField":   // 取字段
                deps.Add(new DataDependency(
                    GapType:    "field",
                    FieldCode:  node.Config.FieldCode,
                    FieldName:  node.Config.FieldName,
                    StandardFileCode: node.Config.StandardFileCode));
                break;

            case "docTable":   // 取表格
                deps.Add(new DataDependency(
                    GapType:    "table",
                    TableCode:  node.Config.TableCode,
                    TableName:  node.Config.TableName,
                    StandardFileCode: node.Config.StandardFileCode));
                break;

            // ⚠️ 以下节点不产生数据依赖，但会产生「执行前置条件」
            case "aiJudge":    // AI 判定：依赖上游节点的输出，不是直接取数
            case "aiGenerate":
            case "condition":
            case "start":
            case "end":
                break;

            default:
                // ★ 未知节点类型 → 不能默认"无依赖"，必须保守处理
                //   记 warning 并跳过该节点，避免漏报缺口
                _logger.LogWarning("未知工作流节点类型 {Type}，完备性检查跳过该节点", node.Type);
                break;
        }
    }
    return deps;
}
```

> **为什么要拆到「规则 × 依赖」粒度**：因为跳过是**按规则**跳过的（D05「该流程缺乏必要数据」—— 流程 = 规则）。如果只算出"缺 3 个字段"，无法回答"哪几条规则因此不能跑"。所以 `tsk_task_data_gap` 必须同时记 `SourceItemCode`（哪条规则依赖它）。

### 2.2 缺口判定

```csharp
IReadOnlyList<DataGap> DetectGaps(DataDependency[] deps, ScopeContext ctx)
{
    var gaps = new List<DataGap>();

    // 一次性把该企业该阶段该标准的全部提取结果捞进来，避免 N+1
    // ★ 过滤条件是本设计的核心，务必与 05 号 §2 完全一致
    var fieldResults = _extractResultStore
        .GetActiveAsync(ctx.EnterpriseCode, ctx.StandardCode, ctx.StageCode)
        .ToDictionary(r => r.FieldCode);      // 一个 FieldCode 一行

    var tableResults = _extractResultStore
        .GetActiveTablesAsync(ctx.EnterpriseCode, ctx.StandardCode, ctx.StageCode)
        .ToDictionary(r => r.TableCode);

    foreach (var dep in deps)
    {
        bool missing;
        if (dep.GapType == "field")
            missing = !fieldResults.TryGetValue(dep.FieldCode, out var fr)
                      || string.IsNullOrWhiteSpace(fr.ExtractedValue);
            // ★ 空字符串也算缺：字段在但值是空 = 没提取到实质内容
        else
            missing = !tableResults.TryGetValue(dep.TableCode, out var tr)
                      || IsEmptyTable(tr.ExtractedJson);
            // 表格判定：JSON 解析后 rows 长度为 0，或内容为 "[]"

        if (missing)
            gaps.Add(new DataGap { /* ... dep ... */ GapStatus = "pending" });
    }
    return gaps;
}
```

**去重规则**：同一个 `FieldCode` 可能被 3 条规则引用 → 产生 3 条 gap 记录（因为 `SourceItemCode` 不同）。补录时**按 `FieldCode` 一次补齐所有引用它的 gap**（见 05 号 §4.2）。导出/展示时按 `FieldCode` 聚合显示为"1 个字段被 3 条规则依赖"。

### 2.3 提交时的二次校验（O2）

```
POST /api/ExpertTask/{code}/submit
  │
  ├─① 状态校验：TaskStatus ∈ {draft, gap_detected}，否则 409
  │
  ├─② 重跑完备性检查
  │   为什么重跑：补录后数据变了（可能补录时发现还有别的缺口）
  │
  ├─③ 判定阻断条件（O2）
  │   SELECT COUNT(*) FROM tsk_task_data_gap
  │   WHERE TaskCode=? AND GapStatus='pending' AND IsValid=1
  │
  │   > 0 → 409 {
  │        code: 'DATA_GAP_UNRESOLVED',
  │        message: '还有 {n} 项数据未补录也未跳过，请先补录或点击"跳过全部"',
  │        data: { gapCount: n, gaps: [ ...前 10 条摘要... ] }
  │      }
  │   ★ 这是【软阻塞】：专家点"跳过全部"后 gap 变 skipped，校验即通过（D04）
  │
  ├─④ 预置 skipped 标记
  │   对每条 gap 仍为 pending 的规则，先把对应 tsk_task_item 标记为待跳过
  │   （实际 AutoStatus 由队列执行时落，此处只做统计预填）
  │
  ├─⑤ 派发队列
  │   UPDATE tsk_task_queue SET Status='pending' WHERE TaskCode=? AND Status='draft'
  │   UPDATE tsk_task SET TaskStatus='pending_run' WHERE Code=?
  │
  └─⑥ 返回 { taskCode, queueCount }
```

### 2.4 跳过语义的三种触发

| 触发方式 | 端点 | 影响范围 | GapStatus |
|---|---|---|---|
| 一键跳过全部 | `POST /{code}/skip-all-gaps` | 该任务全部 `pending` gap | → `skipped` |
| 跳过单条 | `POST /api/ExpertTaskDataGap/{gapCode}/skip` | 该条 gap | → `skipped` |
| 补录后自动消失 | `PUT /api/ExpertTaskDataGap/{gapCode}/fill` | 该 FieldCode 下**所有** pending gap | → `filled` |

**执行时如何知道该跳过**（队列 worker 内）：

```csharp
// 在跑某条任务项之前，先查该规则是否有关联的未补录缺口
var blockingGaps = await _gapRepo.GetUnresolvedAsync(taskItem.Code);
if (blockingGaps.Count > 0 && !hasSkipAllFlag(taskItem.Code))
{
    // D05：自动不执行 + 告知缺乏必要数据 + 不显示结果
    await _taskItemRepo.MarkSkippedAsync(taskItem.Code, new
    {
        AutoStatus   = "skipped",
        SkipCategory = "data_gap",
        SkipReason   = $"该规则缺乏必要数据：缺少 {string.Join("、", blockingGaps.Select(g => g.GapLabel))}",
        ReviewStatus = "skipped",       // ★ 终态，不阻塞 O3 认可校验
        AutoResult   = null,            // ★ 不产出结果 → 界面"不显示结果"
    });
    return;
}
```

> **`hasSkipAllFlag` 的意义**：如果专家点过"跳过全部"，gap 是 `skipped` 状态，`GetUnresolvedAsync`（只查 `pending`）自然返回空，worker 就会尝试执行 —— 这是错的。必须额外检查：**该规则关联的 gap 里是否存在 `skipped` 状态的**。有则直接跳过（理由改为"专家选择跳过"）。详见 03 号 §7 与 04 号 §5。

### 2.5 五种跳过原因（`SkipCategory`）

`skipped` 不是单一原因，导出与界面要区分，否则专家看不懂"为什么这条没有结果"。

| `SkipCategory` | 触发条件 | `SkipReason` 示例 | 可否补录后重跑 |
|---|---|---|---|
| `data_gap` | 关联的 `docField`/`docTable` 节点数据缺失且 gap 为 `pending` | 该规则缺乏必要数据：缺少 质量手册、程序文件 | **可以**（补录后重跑该 item） |
| `data_gap_skipped` | 关联的 gap 被专家显式跳过 | 专家选择跳过（缺乏必要数据未补录） | 可以（改主意可补录） |
| `no_rule` | `ItemCode` 指向的规则已被删除或 `IsValid=0` | 规则已失效 | 否 |
| `rule_disabled` | 规则 `IsValid=0`（创建任务后被禁用） | 规则已被禁用 | 否 |
| `manual_mode` | 规则 `JudgeMode='manual'`（不由 AI 判定，需纯人工填） | 该规则为人工检查模式，不支持自动执行 | 否，但专家可**直接手工录入结论** |
| `exec_failed` | 工作流执行抛异常且重试耗尽 | 执行失败：{异常摘要} | 可重跑 |

> `manual_mode` 的设计要点：这类规则本就不该自动跑，但**不能因为"不自动跑"就完全不出现** —— 专家仍需对该条款做检查并给出结论。因此这类 item 的 `ReviewStatus` 直接置 `skipped`（不阻塞批准），同时**在工作台中单独分区展示**，允许专家手工录入结论，录入后转为 `modified`。

## 三、队列设计

### 3.1 为什么不用 `yzh_queue`

| 理由 | 详情 |
|---|---|
| **跨租户泄露（H12）** | `QueueMonitorController.cs:25-26` 的 `GetQueueListAsync` **无租户过滤参数**，任何登录用户可看全部队列。专家端直接复用 = 企业数据泄露 |
| **ScopeKey 双口径** | 实测 `file_convert` 用 `ConfigCode`（目录编码）、`doc_extract` 用 `EnterpriseCode`（企业编码）—— 同一列两种语义，无法写正确的互斥查询 |
| **业务混杂** | 文档转换/提取是 IO 密集型，NC/报告是 LLM 密集型（单任务可能 30s-5min）。混在一张表里优先级调度失效 |
| **锁粒度冲突** | 现有按 `EnterpriseCode` 互斥。本设计按 `SubTaskCode` 互斥（同一企业不同标准可并行） |
| **表结构不匹配** | `yzh_queue` 无 `SubTaskCode`/`StandardCode` 概念；`ScopeKey` 是 varchar(100) 单值，表达不了 N 个标准 |

### 3.2 表职责

| 表 | 职责 | 粒度 |
|---|---|---|
| `tsk_task_queue` | 队列头：进度、状态、失败重试统计 | 1 子任务 = 1 队列 |
| `tsk_task_queue_item` | 队列项：单条待执行的任务项 | 1 任务项 = 1 队列项 |

> **为什么不用「1 任务 = 1 队列」**：多标准阶段下，同一标准内的检查项有强数据依赖（同标准文件共享），跨标准则完全独立。按标准切队列既能并行，又能保证同标准内的顺序执行。

### 3.3 执行编排

```
tsk_task_queue_queue_scanner（后台服务，每 2 秒轮询）
  │
  ├─ 取可领取的队列
  │   SELECT Code FROM tsk_task_queue
  │   WHERE Status='pending' AND IsValid=1
  │     AND (LockedUntil IS NULL OR LockUntil < NOW())
  │   ORDER BY Priority DESC, CreateTime ASC
  │   LIMIT {并发上限}
  │
  ├─ 乐观锁抢占
  │   UPDATE tsk_task_queue
  │   SET Status='running', LockCode=@workerId, LockedUntil=DATE_ADD(NOW(), INTERVAL 10 MINUTE)
  │   WHERE Code=@code AND Status='pending'        ← 条件更新，0 行受影响=被别人抢了
  │   受影响行数 = 0 → 跳过这条
  │
  ├─ 置子任务与任务状态
  │   tsk_task_standard.SubStatus = 'running'
  │   tsk_task.TaskStatus = 'running'（若任一子任务 running）
  │
  ├─ 逐项执行（串行，保证同标准内顺序）
  │   while (还有 pending 队列项)
  │   {
  │     ├─ ① 缺数据预检（§2.4）→ 命中则 MarkSkipped，continue
  │     ├─ ② 缺队列项预检（§3.4）→ 命中则 MarkSkipped，continue
  │     ├─ ③ 置队列项 running（带 LockCode，租约 10 分钟）
  │     ├─ ④ 释放队列租约（下一轮再领），避免长任务占死队列
  │     │      ★ 这是关键：AI 节点可能跑 5 分钟，租约必须 > 单项超时
  │     ├─ ⑤ 执行 WorkflowInterpreter
  │     ├─ ⑥ 结果落库：
  │     │     NC_CHECK       → 写 Conformity/Severity/ContentText
  │     │                       nonconform → 同时 INSERT audit_nonconformity
  │     │     REPORT_GENERATE → 写 ContentText
  │     │     异常           → 置 exec_failed，按 ErrorType 决定是否重试
  │     └─ ⑦ 置队列项 completed/failed
  │   }
  │
  └─ 队列收尾
     ├─ 全部项终态（completed/failed/skipped）→
     │    Status = 有 failed ? 'failed' : 'completed'
     ├─ 回写 tsk_task_standard 计数（DoneCount/AckedCount/SkippedCount）
     └─ 若全部子任务终态 → tsk_task.TaskStatus = 'pending_review'
                          （★ 有失败也算结束 —— 失败项已 MarkSkipped，不阻塞专家）
```

**并发控制三层**：

| 层 | 机制 | 值 |
|---|---|---|
| 队列级 | `SELECT ... FOR UPDATE` + 条件 UPDATE 抢占 | 全局并发上限 `MaxWorkerCount`（配置项，默认 **2**） |
| 队列项级 | `LockedUntil` 租约 | 10 分钟（> 单项 LLM 超时上限） |
| 任务项级 | `tsk_task_item` 的 `ReviewStatus` 乐观更新 | `WHERE ReviewStatus='pending'` 防止重复执行 |

> **为什么并发上限是 2 而非更高**：`QueueHostedService` 当前实现是每秒 `Task.Run()` 不 await（09 号分册 H14 隐患），实际并发不可控。本设计**不复用**该实现，改为受控的 `Channel<T>` + 固定 worker 数，避免打爆 LLM 配额和数据库连接池。详见 09 号 R-04。

### 3.4 队列项缺失兜底

| 情形 | 处理 |
|---|---|
| 队列项 `TaskItemCode` 对应的 `tsk_task_item` 已软删 | 队列项置 `failed`，`ErrorType=permanent`，`ErrorMessage='任务项已删除'` |
| 规则 `cert_validation_rule.IsValid=0` | `MarkSkipped(rule_disabled)` |
| `WorkflowCode` 为空 | `MarkSkipped(no_rule)`` + `ErrorMessage='规则未配置工作流'` |
| `JudgeMode='manual'` | `MarkSkipped(manual_mode)` |
| `RuleJson` 解析失败 | 队列项置 `failed`，`ErrorType=permanent`（这是配置错误，重试无用） |
| LLM 超时 / 429 | `ErrorType=retryable`，`RetryCount+1`，退避 `min(2^RetryCount * 30s, 10min)` |
| 数据库连接失败 | `ErrorType=retryable` |

### 3.5 任务结束判定

```
任务结束 = 所有 tsk_task_standard.SubStatus ∈ {completed, failed, cancelled}
       且 所有 tsk_task_queue.Status ∈ {completed, failed, cancelled}
       → tsk_task.TaskStatus = 'pending_review'
```

**为什么允许带 failed 结束**：专家的工作台会把失败项以 `skipped(执行失败)` 呈现，专家可以选择手工补录结论后认可。若强制重试到成功，专家会卡死在某个 LLM 超时上。

## 四、认可与批准

### 4.1 认可（ACKNOWLEDGE）

```
POST /api/ExpertTaskItem/{code}/acknowledge
  Body: { Remark?: string }

  事务：
  ① UPDATE tsk_task_item
       SET ReviewStatus='acknowledged', ReviewBy=@user, ReviewByName=@name,
           ReviewTime=NOW(), UpdateTime=NOW()
     WHERE Code=@code AND ReviewStatus='pending' AND IsValid=1
     受影响 0 行 → 409 ALREADY_REVIEWED（已被别人改过，或已跳过）
  ② INSERT tsk_task_item_log (Action='ACKNOWLEDGE', ...)
  ③ 回写 tsk_task_standard.AckedCount（增量）
  ④ 回写 tsk_task.PendingCount（-1）
```

### 4.2 修改即认可（MODIFY，D11）

```
POST /api/ExpertTaskItem/{code}/modify
  Body: { Conformity?, Severity?, ContentText?, Remark? }

  事务：
  ① 读当前值（旧值快照）
  ② UPDATE tsk_task_item
       SET <被改字段> = @new,
           ReviewStatus='modified',      ← ★ 一次操作同时完成修改与认可
           IsModified=1,
           ReviewBy=@user, ReviewByName=@name, ReviewTime=NOW()
     WHERE Code=@code AND ReviewStatus IN ('pending','acknowledged')
     ★ 允许从 acknowledged 再改：专家认可后又改主意，也算修改
  ③ INSERT tsk_task_item_log (Action='MODIFY', FieldName, OldValue, NewValue, ...)
     ★ 改几个字段就插几条日志（逐字段 diff，便于前端高亮变化处）
  ④ ★ 同步 NC 记录
     若该项 Conformity 改动了：
       原 nonconform 且新值 != nonconform → audit_nonconformity 置 IsDeleted=1（撤销）
       原 != nonconform 且新值 == nonconform → INSERT 新 NC
       两者都是 nonconform 但 Severity 变了 → UPDATE audit_nonconformity.Severity
     详见 03 号 §5.3
  ⑤ 回写计数
```

> **为什么允许从 `acknowledged` 再改**：专家可能在对照原始文件时发现认可错了。禁止会导致"先乱点认可再改"的绕路，不如直接允许，并用日志记录 `原状态`。

### 4.3 批量认可

```
POST /api/ExpertTaskItem/batch-acknowledge
  Body: { TaskCode, SubTaskCode?, ItemCodes[], Remark? }

  事务（单事务，≤ 500 条）：
  批量 UPDATE ... WHERE Code IN (...) AND ReviewStatus='pending'
  批量 INSERT log
  批量回写计数（用 SQL 聚合，不用循环）
```

### 4.4 批准（O3 强制）

```
POST /api/ExpertTask/{code}/approve
  Body: { Remark? }

  事务：
  ① 状态校验：TaskStatus='pending_review'，否则 409
  ② ★ 认可完整性校验（O3）
     SELECT
       SUM(ReviewStatus='pending')    AS pendingCnt,
       SUM(AutoStatus='failed')      AS failedCnt
     FROM tsk_task_item WHERE TaskCode=? AND IsValid=1

     pendingCnt > 0 → 409 {
       code: 'REVIEW_INCOMPLETE',
       message: '还有 {pendingCnt} 条结果未认可',
       data: { pendingCodes: [ ...最多 20 条 Code...] }   ← 前端可直接跳转定位
     }
     ★ skipped 状态不计入（§2.4 已解释：它是确定性终态）
  ③ 可选告警（不阻断）：
     failedCnt > 0 → 记 warning 日志，提示"有 {n} 条因执行失败被跳过"
  ④ UPDATE tsk_task SET TaskStatus='approved', ApproveBy, ApproveName, ApproveTime=NOW()
  ⑤ UPDATE tsk_task_standard SET SubStatus='approved' WHERE TaskCode=?
  ⑥ INSERT tsk_task_log (Action='APPROVE')  —— 任务级动作日志
  ⑦ ★ 释放业务锁（见 §6.3）
```

### 4.5 批准后

| 允许 | 禁止 |
|---|---|
| 导出 Excel（定稿态，带批准人/时间水印） | 修改任何任务项（`ReviewStatus` 校验全链路拦死） |
| 查看日志与追溯 | 重新提交 |
| 查看关联的 NC 记录 | 删除任务 |

> **「批准后冻结」是本设计的关键约束**：否则 Excel 导出内容与批准时不一致，审计链断裂。实现上所有 item 写操作端点第一行就校验所属任务 `TaskStatus='approved'` → 409 `TASK_FROZEN`。

## 五、重新执行

允许「重新执行」的场景：文件替换后、或专家改主意想重新生成。

```
POST /api/ExpertTask/{code}/rerun
  Body: { ItemCodes[], ResetReview: bool }

  前置：
  ① TaskStatus ∈ {pending_review, failed}，approved 不可重跑
  ② 业务锁检查（本任务自己不算冲突）
  ③ ItemCodes 必须是本任务内的；★ 不允许追加新项（D20）

  事务：
  ① 目标 item 的 ReviewStatus/IsModified/审核人 → 清空
  ② audit_nonconformity 关联项 → 软删（避免 NC 重复）
  ③ 置回 pending，创建新队列项
  ④ TaskStatus → 'pending_run'
```

> **为什么 `ResetReview` 是显式参数**：默认重跑会清空专家的认可，这在多标准任务里可能误伤其他标准的成果。显式参数让专家明确表达意图。

## 六、业务锁（O1，D15）

### 6.1 锁的定义

```
锁标识：LockKey = $"{OrgCode}|{EnterpriseCode}|{StageCode}"
锁条件：tsk_task 存在 TaskStatus NOT IN ('approved','cancelled','failed')
        的记录（OrgCode + EnterpriseCode + StageCode 三者全等）
```

**不分任务类型**（D15）：NC 任务未结束 → 报告任务也不能建。好处是天然保证「先 NC 后报告」。

### 6.2 锁的范围（★ 比任务本身更广）

| 被锁操作 | 位置 | 加锁方式 |
|---|---|---|
| 新建任务 | `ExpertTaskController.Create` | §1.1 步骤 ② |
| 企业文件上传 | `CertEnterpriseFileController` 上传端点 | 同一服务方法 |
| 企业文件替换 | `CertEnterpriseFileController` 替换端点 | 同一服务方法 |
| 企业文件删除 | `CertEnterpriseFileController` 删除端点 | 同一服务方法 |
| 文档提取（手动触发） | `trigger-extract` 端点 | 同一服务方法 |

> **为什么文件操作也要锁**：任务执行时会把提取结果读进 `tsk_task_item`。若专家中途替换了企业文件，提取结果变了（10 号分册 S2 的 `EnterpriseExtractionResultStore` 会 `ArchiveAsync` 归档旧版本），但已跑完的 item 结果不会自动更新 → **结论与数据源不一致**。用户原话：「因为这样会影响结果，我们在执行企业文件管理的时候，也要做限制」。

### 6.3 锁的实现

```csharp
public class ExpertTaskBizLockService
{
    public void EnsureUnlocked(string enterpriseCode, string stageCode)
    {
        var active = _taskRepo.Query()
            .Where(t => t.OrgCode == _workspace.OrgCode
                     && t.EnterpriseCode == enterpriseCode
                     && t.StageCode == stageCode
                     && t.TaskStatus != "approved"
                     && t.TaskStatus != "cancelled"
                     && t.TaskStatus != "failed"
                     && t.IsValid == 1
                     && t.IsDeleted == false)
            .First();

        if (active != null)
            throw new BizException("BIZ_LOCKED",
                $"该企业在该阶段存在进行中的任务【{active.TaskNumber}】，请先完成后再操作");
    }
}
```

**锁的自动释放**：任务进入 `approved` / `cancelled` / `failed` 时自动解除（因为查询条件是"存在非终态任务"，无需显式解锁动作）。**但要注意**：`failed` 也算终态并解锁 —— 见 10 号 Q1（是否允许 `failed` 状态的任务继续占用锁）。

**锁查询性能**：`tsk_task` 上建索引
```sql
KEY `idx_bizlock` (`OrgCode`, `EnterpriseCode`, `StageCode`, `TaskStatus`, `IsValid`)
```
锁检查在每次文件操作时触发，**必须走索引**，不能全表扫。

### 6.4 前端配合

- 任务列表页：被锁的企业+阶段组合显示 🔒 图标 + hover 提示占用中的任务编号
- 企业资料管理页（`pages/resources/index.vue`）：上传/替换/删除按钮置灰 + tooltip「该企业该阶段有进行中的任务」
- 创建向导第 1 步：选完企业+阶段立刻调 `GET /api/ExpertTask/creatable-context` 校验，禁用「下一步」

## 七、异常与重试汇总

| 异常 | 位置 | 分类 | 处理 |
|---|---|---|---|
| LLM 超时 / 429 / 5xx | 队列项执行 | retryable | 退避重试，最多 `MaxRetryCount=3` |
| 数据库连接失败 | 任意写 | retryable | 队列项重试 |
| `RuleJson` 解析失败 | 完备性检查 / 执行 | permanent | 标记失败 + 告警（配置错误，重试无用） |
| `WorkflowCode` 为空 | 执行前置 | — | `MarkSkipped(no_rule)` |
| 规则失效 | 执行前置 | — | `MarkSkipped(rule_disabled)` |
| `JudgeMode='manual'` | 执行前置 | — | `MarkSkipped(manual_mode)` |
| 数据缺失 | 执行前置 | — | `MarkSkipped(data_gap / data_gap_skipped)` |
| 企业文件版本变化 | 执行前置 | — | 检测到 `VersionNumber` 与入队时不一致 → 置 `permanent`，提示需重新执行 |
| 任务已被批准 | 任何写操作 | — | 409 `TASK_FROZEN` |
| 任务被并发修改（乐观锁） | 认可/修改 | — | 409 `CONCURRENT_MODIFIED`，前端刷新 |

## 八、与 `wf_execution_task` 的关系

两套任务并存，**职责不同**：

| | `wf_execution_task` | `tsk_task` |
|---|---|---|
| 视角 | **引擎视角**：一次 DAG 执行的留痕 | **业务视角**：专家发起的一次审核任务 |
| 粒度 | 1 规则 = 1 任务 | 1 企业+阶段+类型 = 1 任务 |
| 状态语义 | 执行中/成功/失败 | 业务全流程（含认可、批准） |
| 谁写入 | `WfExecutionTaskService.BeginRunAsync` | `ExpertTaskService` |
| 前端是否可见 | 仅执行历史抽屉（`ExecutionHistoryDrawer.vue`） | **任务列表主数据源** |

**关联方式**：`tsk_task_queue_item.Payload.WorkflowExecutionTaskCode` ← 执行时回填。任务项 → 队列项 → 执行任务，形成完整链路，可从专家端一路下钻到引擎执行细节。

> **不合并的理由**：执行任务的粒度（每规则一条）与业务任务的粒度（每企业阶段一条）差 1-2 个数量级。强行合并会让任务列表被 40 条执行记录淹没。
