## 一、先说结论（不粉饰）

> **架子成立，产品未成立；机遇真实，窗口有限。**
>
> **下一步不是「再写多少功能」，而是「证明有人愿意为它付钱」。**

### 1.1 客观评分

| 维度 | 评分（10） | 说明 |
|---|---|---|
| 架构与设计 | **7** | AI 原生、可追溯、多端同构，方向对 |
| AI 能力 | **7** | 证据链 / NC / 报告链路有想法，但未在真实项目跑透 |
| 可追溯性 | **8** | 相对传统软件的真优势 |
| **内容（DAG / 规则 / 模板）** | **2** | **几乎空白；只覆盖 1 个标准，且未端到端验证** |
| 产品完整度 | **3** | 权限、日志、导入导出、异常、备份、SLA 未经历真实客户 |
| 交付可复制性 | **2** | 每来一个客户是否还要专家驻场？未验证 |
| 信任与案例 | **1** | 没有 reference customer |
| 获客能力 | **2** | 三条线都想做，等于三条线都没打透 |
| 单位经济 | **5** | 理论成立，实测未知 |

**综合判断**：**原型期，不是可售期。**
这不是否定设计，而是区分「潜力」和「可售」。

### 1.2 三个判断

| # | 判断 | 含义 |
|---|---|---|
| 1 | **设计有差异化，但差异化尚未变成「可感知的价值」** | 客户不会为「架构好」付钱，只会为「省时间 / 少出错 / 过审」付钱 |
| 2 | **真正的短板是内容、交付、信任，不是代码** | DAG 空白不是「功能没做完」，是「产品没有米」 |
| 3 | **当前最大风险不是竞争，是「做完了没人买」** | 传统软件不会因为功能少而立刻死，你会因为没收入而先死 |

## 二、你现在的真实位置：站在断层上

### 2.1 左边是「做出来」，右边是「卖出去」

```
做出来（已完成）                 卖出去（未开始）
搭架子 · 跑通链路 · 有设计   →   有客户 · 有案例 · 有收入 · 可复制
        ↑
   你现在在这里
```

**仓促搭架子不是错。** 没有骨架，连验证都无从谈起。
**错的是**：用「继续加功能」来缓解「没人买」的焦虑。

### 2.2 焦虑的真实来源

| 你以为的焦虑 | 真实的焦虑 |
|---|---|
| 「功能还不够多」 | **「我没有证据证明有人要」** |
| 「DAG 还没填完」 | **「填完之后，谁付钱？」** |
| 「别人会不会抄」 | **「我能不能先活到别人来抄」** |

**解决焦虑的唯一方式，是拿到证据**：一个真实客户、一个可量化结果、一笔真实付款。
**不是**再写一个模块。

### 2.3 想挣钱不丢人，仓促也不丢人

- 想挣钱是合理的，不需要为「商业化」感到羞耻。
- 仓促是资源约束下的必然，不是能力问题。
- **真正危险的是**：把「仓促做出来的架子」当成「已经成立的产品」，然后按「平台」的节奏烧钱。

> **先活下来，再谈平台。** 这不是降低野心，是保护野心。

## 三、传统软件为什么能活（他们卖的不是功能）

| 你以为客户买的是 | 客户实际买的是 |
|---|---|
| 功能多、AI 强 | **「出了事有人兜」**：合同、发票、SLA、驻场支持 |
| 界面先进 | **「审核员 / 机构已经熟悉」**：培训成本低、换人成本低 |
| 自动化 | **「流程能跑完」**：合同→派单→审核→报告→证书→归档 |
| 技术架构 | **「采购合规」**：软著、等保、案例、公司资质 |
| 价格低 | **「不用我做决定」**：同行都在用，选它不会被追责 |

### 3.1 他们的护城河（按强度排序）

1. **切换成本**（数据、流程、习惯都在里面）
2. **关系与案例**（同行背书）
3. **实施与培训**（卖的是「人 + 软件」）
4. **采购合规**（能进供应商名录）
5. **功能「够用」**（80% 流程能跑，剩下 20% 靠人）

### 3.2 你的机会在哪

| 他们不做的「脏活 / 深水区」 | 你能做的差异化 |
|---|---|
| 证据链自动归集与追溯 | AI 提取 + 逐字段溯源 |
| NC 判定的一致性 | 规则 + 证据 + 可复核 |
| 报告与证据的对应关系 | DAG 编排 + 章节引用 |
| 企业资料的「体检」而非「代写」 | 一致性检查 + 缺口提示 |
| 多端数据隔离与合规 | 时点隔离 + 审计留痕 |

> **但注意**：你必须先补齐「80% 的表桩能力」，客户才会让你进场做那 20%。

## 四、优势与短板（哪些是潜力，哪些是当下）

| 项 | 性质 | 是否可持续 | 是否致命 |
|---|---|---|---|
| AI 原生架构 | 优势 | 中（会被追赶） | 否 |
| 可追溯 / 可审计 | **强优势** | 高（需要时间积累） | 否 |
| 多端同构 | 优势 | 中 | 否（但会分散资源） |
| 专家规则库 | **核心资产** | 高（人 + 内容） | 目前**空** |
| 成本结构（一人 / 小团队） | 优势 | 中 | 否 |
| **内容空白** | **短板** | — | **是** |
| **无真实案例** | **短板** | — | **是** |
| **交付未验证** | **短板** | — | **是** |
| 产品卫生（权限/日志/备份/SLA） | 短板 | — | 进入机构市场时**是** |
| 获客能力 | 短板 | — | **是** |

### 4.1 一句话

> **优势是「潜力」，短板是「当下」。**
> 投资人 / 客户只为「当下能解决的问题」付钱，不为「未来的潜力」付钱。

## 五、生死线（Go / No-Go）

> **以下阈值是建议值，可按你的现金流和跑道调整。**
> **原则：先定死线，再开始跑；否则会不断给自己找理由。**

| # | 验证项 | 绿灯（继续） | 黄灯（调整） | 红灯（停 / 转） |
|---|---|---|---|---|
| 1 | **内容可复制** | 1 个标准端到端 **≤10 人日** | 10–20 人日 | **>20 人日** |
| 2 | **价值可感知** | 节省时间 **≥30%** 或错误率下降 **≥30%** | 15–30% | **<15%** |
| 3 | **付费验证** | 90 天内 **≥3 个付费客户**（或 1 个付费机构试点） | 1–2 个 | **0 个** |
| 4 | **支持可规模化** | **≤2 小时/客户/周** | 2–5 小时 | **>5 小时** |
| 5 | **复用性** | 第 2 个客户配置工时 **≤第 1 个的 30%** | 30–60% | **>60%** |
| 6 | **现金流** | 12 个月跑道，或服务收入覆盖成本 | 6–12 个月 | **<6 个月** |

### 5.1 判定规则

| 结果 | 动作 |
|---|---|
| **4 项以上绿灯** | 继续，进入「复制」阶段 |
| **3 项绿灯 + 2 项黄灯** | 收缩到一个场景，再验证 6 周 |
| **2 项以上红灯** | **停止加功能**，转服务 / 转定位 / 转客户 |
| **第 1 项红灯** | **产品模式不成立**（内容是核心），必须换交付方式或换标准 |

> **第 1 项是根**：如果配置一个标准要 20 人日以上，你就不是 SaaS，是项目制外包。

## 六、6 周验证计划（暂停新功能）

> **铁律：这 6 周不新增业务模块，只做「内容 + 客户 + 证据」。**
> 新需求先记入 backlog，验证结束后再排。

| 周 | 目标 | 关键动作 | 交付物 |
|---|---|---|---|
| **W1** | 选楔子 + 摸需求 | 选 1 个标准、1 类客户；访谈 10 人（审核员/企业/咨询公司）；记录「现在怎么做、花多久、最痛哪一步」 | 《访谈记录 + 痛点排序》 |
| **W2** | 内容工厂设计 | 定义「一个标准包」的组成：条款 / 模板 / NC / 章节 / 提取规则；设计配置流程与校验器 | 《标准包配置手册 V0》 |
| **W3** | 端到端配完 1 个标准 | 从 141 条款到 8 章节全部配完；记录每个模块工时；内部 dry run | **1 个可演示的标准包 + 工时表** |
| **W4** | 3 个真实试点 | 2 个审核员 / 1 家企业（或反之）；真实项目使用；记录前后耗时、漏项、返工 | 《试点记录表》×3 |
| **W5** | 分析与修复 | 找 Top 3 阻塞点；修复；做一次定价测试（哪怕 99 元） | 《阻塞清单 + 修复记录》 |
| **W6** | 决策 | 对照生死线打分；写案例；决定 Go / Pivot / Stop | **《Go-NoGo 决策 memo》+ 1 个案例** |

### 6.1 6 周后必须拿到的 5 样东西

1. **1 个配好的标准包**（能演示、能交付）
2. **3 份真实试点记录**（含前后耗时）
3. **1 个可量化的 ROI 数字**（省多少小时 / 少多少错）
4. **1 个付费意向或真实付款**
5. **1 份 Go / No-Go 决策 memo**

> **没有这 5 样，不要进入「开发更多功能」阶段。**

### 6.2 如果 3 周配不完：先做「最小可验证切片」（MVS）

全量标准包（141 条款 / 32 模板 / 64 NC / 8 章节）可能超过 3 周。**不要因此推迟验证**，改做一条**纵向切片**：

| 切片 | 内容 | 目的 |
|---|---|---|
| 1 个过程域 | 例如「文件控制」或「不合格品控制」 | 跑通条款→模板→NC→报告 |
| 3 份模板 | 该过程域最常用的 3 份 | 验证生成/检查链路 |
| 10 个 NC 项 | 该过程域的高频不符合 | 验证判定一致性 |
| 1 个报告章节 | 对应章节 | 验证证据引用 |
| 1 条提取规则 | 对应文档 | 验证溯源 |

**判定**：

- 切片能跑通 ⇒ 记录「全量估算工时」，再决定是否扩展。
- 切片都跑不通 ⇒ **不是内容问题，是产品链路问题**，优先修链路。
- **不要**用「全量没配完」作为「不能验证」的理由。

### 6.3 每周复盘 3 问（防止跑偏）

1. 这周有没有拿到**新证据**（客户原话 / 数据 / 付款意向）？
2. 这周有没有**新增功能**？如果有，为什么不是先验证？
3. 下周的动作，能不能让「第一个付费客户」更近一步？

> 三问里有两问答不上来，下周只做一件事：**去见客户**。

## 七、三种路径，先选一个跑

| 路径 | 客户 | 优点 | 风险 | 建议 |
|---|---|---|---|---|
| **A. 审核员工具**（证据→NC→报告） | 审核员个人 / 小机构 | 需求主动、决策链短、可量化省时 | 个人付费意愿低、客单价低 | ✅ **首选** |
| **B. 企业文档体检**（一致性检查） | 企业 | 市场大、对标咨询费 | 获客慢、要教育、不能生成运行记录 | 🟡 第二 |
| **C. 机构平台** | 认证机构 | 客单价高、稳定 | 采购慢、要求高、无案例打不进 | ⛔ 暂缓 |
| **D. 咨询服务 + 工具** | 企业 / 咨询公司 | 现金流快、能积累规则 | 容易变成定制项目、不可规模化 | 🟡 过渡 |

### 7.1 推荐路径：A → B → C

```
A 审核员工具（1 个标准 / 3 个试点 / 1 个案例）
  ↓ 拿到证据与口碑
B 企业文档体检（通过咨询公司/协会渠道）
  ↓ 拿到企业侧数据与需求
C 机构平台（有案例后再谈）
```

### 7.2 「服务先行」可以，但必须有累积

如果你需要现金流，可以接**付费试点 / 轻咨询**，但设三条规矩：

| # | 规矩 | 目的 |
|---|---|---|
| 1 | 每个项目必须产出**可复用的规则/模板** | 不能只换钱，不积累 |
| 2 | 定制部分**不超过 30%** | 防止变成外包 |
| 3 | 报价按「标准包 + 人日」拆开 | 让客户和你都清楚：软件值多少、人值多少 |

> **服务是桥，不是终点。** 桥的那头必须是「可复制的产品」。

## 八、失败预演（Pre-mortem）

> 假设 12 个月后产品死了，最可能的死因是什么？先写下来，再逐条防。

| # | 死因 | 早期信号 | 预防动作 |
|---|---|---|---|
| 1 | **内容永远填不满** | 配第 1 个标准就超过 20 人日 | 先做配置工具与校验器；只选 1 个标准 |
| 2 | **没有第一个敢用的客户** | 访谈都说「不错」，但没人愿意试点 | 找关系最近的 3 个人；免费试点换案例 |
| 3 | **支持成本吃掉收入** | 每周支持 >5 小时/客户 | 做自助文档 / 视频 / FAQ；限制定制 |
| 4 | **免费用户不转化** | 试用很多，付费 0 | 从第一天收费；免费只给 7 天 |
| 5 | **咨询公司渠道反目** | 他们觉得你抢客户 | 明确「工具」定位；做白标；不绕过渠道 |
| 6 | **法律 / 数据事件** | 客户要求删数据 / 出事故 | 按 40 号做加密、留存、DPA、审计日志 |
| 7 | **创始人精力耗尽** | 同时做三条线、每天救火 | 只留一个楔子；每周复盘一次 |

### 8.1 最危险的死因（我的判断）

> **不是 1，也不是 2，是 7。**
>
> 一人 / 小团队最容易死于「同时想做三件事」。
> 你的设计越完整，越容易高估自己的交付能力。

**对策**：6 周内只允许一个目标——**「让 1 个标准包跑通 3 个真实试点」**。其他全部搁置。

## 九、只有你能定的五个决策

> 这些不是法律 / 技术问题，是**资源与取舍**问题。文档只给选项，不替你决定。

| # | 决策 | 选项 | 取舍 | 截止 |
|---|---|---|---|---|
| 1 | **第一个标准** | ISO 9001 / ISO 13485 / 其他 | 9001 市场大、竞争多；13485 窄、你有数据 | W1 结束 |
| 2 | **第一个买家** | 审核员 / 企业 / 咨询公司 | 审核员快、企业大、咨询公司有预算但冲突 | W1 结束 |
| 3 | **收费模式** | 订阅 / 按次 / 标准包 / 服务费 | 订阅稳、按次易试、服务费快但不可规模化 | W4 结束 |
| 4 | **是否接受定制** | 接受 / 拒绝 / 有限接受 | 现金流 vs 产品化 | W1 结束 |
| 5 | **时间与现金跑道** | 6 / 12 / 18 个月 | 决定你能试错几次 | 立即 |

### 9.1 如果只能给一个建议

> **选「审核员 + 1 个标准 + 按次/订阅」先跑。**
>
> 理由：决策链最短、反馈最快、最容易量化「省几小时」，也最容易拿到第一个案例。
> 企业端和机构端，等你有案例后再谈。

## 十、给创始人的三句话

> **1. 仓促不是错，继续仓促才是错。**
> 你已经把架子搭起来了，这比 90% 只停留在想法的人强。现在缺的不是能力，是**验证**。
>
> **2. 你不需要证明产品伟大，只需要证明有人愿意为它付钱。**
> 一个愿意付 99 元的真实客户，比十个说「不错」的朋友更有价值。
>
> **3. 先活下来，再谈平台。**
> 现金流、案例、口碑，是平台的入场券；没有这三样，「平台」只是负担。

### 10.1 本周就能做的三件事（不要再等「准备好」）

| # | 动作 | 完成标准 |
|---|---|---|
| 1 | 列出 10 个能联系到的审核员 / 企业 / 咨询顾问，约 5 个访谈 | 日历上有 5 个时间 |
| 2 | 选定 1 个标准 + 1 个过程域，做 MVS 切片 | 能跑通「条款→模板→NC→报告」一条线 |
| 3 | 把本文档发给 1 个你信任、且敢说真话的人 | 拿到 3 条反对意见 |

> **不要用「再准备一下」推迟第一次客户接触。**
> 你现在最缺的不是准备，是**真实反馈**。

## 附录 A：访谈提纲（10 问）

> 对象：审核员 / 企业体系负责人 / 咨询顾问
> 原则：不问「你觉得这个功能好不好」，只问「你上次实际怎么做、花了多久」。

1. 你最近一次完整做（审核 / 体系文件 / 咨询项目）是什么时候？
2. 从开始到结束，一共花了多少小时？哪一步最花时间？
3. 这一步现在用什么工具？（Word / Excel / 微信 / 纸质 / 其他软件）
4. 有没有出过错 / 返工 / 被批评？最严重的一次是什么？
5. 如果有一个工具能帮你省 30% 时间，你愿意试吗？

9. 如果明天就要用，你最希望它先解决哪一个问题？
10. 你认识的人里，谁也有同样的问题？能不能介绍一个？

## 十一、按当前资源修订的路线图（本地环境 + 熟人试点 + 2–3 个月）

> 这一节是按你的真实约束写的：**没有域名 / 没有服务器 / 本地环境 / 靠朋友介绍 / 2–3 个月准备期**。
> 不是「标准创业模板」，是「你现在能执行的版本」。

### 11.1 先分清两个「定位」

| 定位 | 状态 | 说明 |
|---|---|---|
| **产品定位** | ✅ **已定** | AI 辅助工具，不是认证机构、不是咨询机构（见 41 号） |
| **商业定位（第一个付费场景）** | ❌ **未定** | 审核员 / 企业 / 咨询公司 / 机构，**四选一先跑** |

> 你现在的困惑不是「产品定位没想好」，是「**第一个付费场景没选好**」。
> 这两件事不要混：前者已经解决，后者是接下来 2 周要解决的。

### 11.2 四个阶段（每阶段有通过条件）

| 阶段 | 时间 | 目标 | 交付物 | 通过条件 |
|---|---|---|---|---|
| **P0 专家验证** | 第 1–2 周 | 验证设计、选定标准、锁定试点 | 专家反馈 memo + 标准选择 + 试点清单 | ≥3 位专家认可；≥1 位愿意共建；≥1 个真实项目 |
| **P1 内容与 MVS** | 第 3–8 周 | 用真实资料跑通一条纵向切片 | 1 个标准包（或 MVS）+ 工时表 + 演示 | 切片跑通；全量估算 ≤20 人日 |
| **P2 熟人试点** | 第 9–12 周 | 2–5 人真实使用 | 试点记录 ×3–5 + ROI 数字 + 案例草稿 | ≥2 人第二次使用；≥1 个付费意向 |
| **P3 商业化准备** | 第 13 周起 | 按信号补基础设施 | 域名/服务器/OSS/支付/协议 | 有付费客户或明确合同 |

> **关键**：P0 不写代码，P1 不接新需求，P2 不做上架，P3 才碰支付。
> 每个阶段没通过，**不要进入下一阶段**。

### 11.3 基础设施：按信号买，不按日期买

| 项 | 触发信号 | 现在怎么做 |
|---|---|---|
| **域名** | 需要对外演示、企业邮箱、正式报价 | 可暂缓；先用本地 + 微信/邮件 |
| **服务器** | 试点用户不在同一局域网，或数据不能放你电脑 | 先用**轻量云 / 内网穿透 + 强认证**；⛔ 不要把本地机器直接暴露公网 |
| **OSS** | 文件量超出本地容量，或需要远程上传/断点续传 | 先用**本地 MinIO**；P2 再评估 |
| **支付** | 第一个付费客户明确要求线上支付 | 先用**合同 + 对公/转账 + 手工开票**；不要先接支付 |
| **手机 App** | 试点明确说「没有手机现场采集就没法用」 | 先用**手机浏览器 H5** 顶住；Flutter 推迟到 P3 之后 |
| **等保 / ISO 27001** | 机构合同明确要求 | 先不做；有机构单再启动 |
| **软著 / 商标** | 现在就可以做，成本低 | 软著 P0、商标 P0；不与服务器绑定 |

> **原则：基础设施是「被客户逼出来的」，不是「提前准备好的」。**
> 但**数据安全不是**：即使是熟人试点，也要有访问控制、备份、脱敏、删除机制。

### 11.4 熟人试点的 6 条规矩（比技术更重要）

| # | 规矩 | 原因 |
|---|---|---|
| 1 | **朋友的资料 ≠ 朋友有权授权** | 资料可能属于其公司/客户；必须拿**企业书面授权**，或做**匿名化/样例化** |
| 2 | **免费也要签试点协议** | 范围、数据用途、保密、反馈义务、期限、终止条件 |
| 3 | **用真实项目 + 真实 deadline** | Demo 数据测不出痛点；真实截止日期才会暴露问题 |
| 4 | **只记录行为，不收集夸奖** | 前后耗时、是否第二次用、是否愿意付 99 元；「不错」不算证据 |
| 5 | **每个朋友推荐 1 个非朋友** | 避免熟人回音室；非朋友的反馈更接近市场 |
| 6 | **数据隔离** | 审核员朋友和企业朋友的数据**不能互通**；从第一天就按租户隔离 |

> **第 1 条最容易被忽略，也最容易出事。** 朋友的「帮忙」不等于企业的「授权」。

### 11.5 给朋友的「一页纸」（降低他们的风险感）

朋友不敢用，通常不是不信你，是**怕三件事**：数据出事、用了被绑定、不知道怎么商业化。给他们一页纸：

| 模块 | 内容 |
|---|---|
| 我们做什么 | 认证审核辅助分析 / 文档体检；**不出认证结论、不代写运行记录** |
| 这次请你做什么 | 30 分钟反馈 + 1 个真实项目试用；不要求你改变现有流程 |
| 数据怎么处理 | 本地/国内模型；脱敏；不对外；试用结束可删除；签协议 |
| 现在怎么收费 | 试点期免费或象征性收费 |
| 以后怎么收费 | 一句话：审核员订阅 / 企业年费 / 机构服务包（三选一先验证） |
| 你能得到什么 | 省时间、少返工、提前发现问题；可优先影响产品方向 |

> 这张纸的作用：**让朋友看到「商业化路径」**，而不是「帮你测一个不知道能不能卖的东西」。

### 11.6 机构合作：按「服务包」卖，不按「平台」卖

| 服务包 | 内容 | 计价 | 备注 |
|---|---|---|---|
| **诊断** | 现状评估、差距清单、1 个标准的选择建议 | 按人日 | 轻量，建立信任 |
| **配置** | 1 个标准包 + 1 个流程 + 规则校验 | 按标准包 | 必须沉淀为可复用资产 |
| **试点** | 1 个真实项目陪跑（2–4 周） | 按项目 | 记录工时与效果 |
| **交付** | 规则包 + 报告 + 培训 | 打包 | 明确「软件配置服务」，不做体系咨询、不出认证结论 |

> **目的**：用服务收入养活验证期，同时把每个项目变成**可复用的规则/模板**。
> **红线**：定制部分不超过 30%；否则你就是外包公司，不是产品公司。

### 11.7 硬检查点（到点就决策，不拖）

| 时间 | 检查 | 不通过怎么办 |
|---|---|---|
| **第 8 周** | 有没有 1 位专家愿意共建？有没有 1 个真实项目？ | 没有 ⇒ 换标准 / 换人群 / 停 |
| **第 12 周** | 2–5 个试点里，有没有人**第二次使用**？有没有付费意向？ | 没有 ⇒ 收缩到一个场景，再跑 4 周 |
| **第 16 周** | 有没有 1 个付费客户或机构服务包合同？ | 没有 ⇒ 转服务 / 转定位，不再加功能 |
| **第 24 周** | 能否把第 2 个客户配置工时压到第 1 个的 30%？ | 不能 ⇒ 不是 SaaS，按项目制管理 |

### 11.8 一句话

> **2–3 个月不是「延迟商业化」，是「用最低成本买确定性」。**
> **确定性只能从客户那里买，不能从代码里长出来。**

## 十二、第二曲线与退路：能力复用与垂直选择

> 本节回答两个问题：① 这套能力是不是只能做体系认证？② 如果认证这条路走不顺，退路是什么、按什么顺序退？

### 12.1 你真正可复用的能力（不是「认证软件」）

| 能力 | 认证里的用途 | 其他行业的对应需求 |
|---|---|---|
| 异构文档解析 / 结构化 | 企业资料、记录、报告 | 申报材料、技术文件、合同 |
| **规则校验**（完整性/一致性/交叉引用） | NC、条款覆盖、证据链 | 合规检查、形式审查、逻辑校验 |
| **模板化文档组装 + 溯源** | 体系文件、报告章节 | 注册资料、申报书、验收资料 |
| 人工复核 + 审计留痕 | 审核员确认 | 审批、评审、签发 |
| DAG 编排 | 证据 → NC → 报告 | 多步骤申报 / 审查流程 |
| 多角色 / 多租户 | 审核员 / 企业 / 机构 | 服务机构 / 客户 / 监管方 |

**一句话**：你做的是「**受监管文档的自动组装与规则校验**」。这个能力是横向的，但**产品必须纵向卖**。

### 12.2 概念澄清：认证 / 认可 / CMA

| 概念 | 审谁 | 谁来做 | 依据 | 输出 |
|---|---|---|---|---|
| **认证**（Certification） | 产品 / 服务 / **管理体系** | **认证机构**（CB） | ISO/IEC 17021、17065 | 认证证书 |
| **认可**（Accreditation） | **机构的能力** | **CNAS** | ISO/IEC 17011 | 认可证书 + 范围 |
| **资质认定**（CMA） | **检验检测机构** | 市场监管部门 | 资质认定办法 + RB/T 214 | CMA 证书 + 能力范围 |

**核心区别**：

- **体系认证审「管理」；CNAS/CMA 审「技术能力」。**
- 体系证书上的 CNAS 标志 = **认证机构**被认可；检测报告上的 CNAS 标志 = **实验室**被认可。
- **CMA 不是认证，也不是认可**，是行政许可性质的「资质认定」。

**为什么体系认证资料里总出现 CNAS/CMA**：同属合格评定生态；CNAS 同时认可认证机构和实验室；咨询师业务重叠；实验室常同时建 ISO 9001 + ISO/IEC 17025 + CMA；标志相似但含义不同。

### 12.3 适用行业的判据

判据：**强监管 + 文档密集 + 模板化 + 证据链 + 人工复核 + 周期性**。

| 行业 / 场景 | 匹配度 | 付费意愿 | 主要障碍 | 建议 |
|---|---|---|---|---|
| **实验室 CNAS / CMA 认可** | ★★★★★ | 中高 | 市场较小、专家集中 | ✅ 最佳邻近行业 |
| **医疗器械注册（NMPA）** | ★★★★☆ | 高 | 责任大、需强领域专家 | ✅ 高价值备选 |
| **安全生产标准化 / 双重预防** | ★★★★☆ | 中 | 价格敏感、偏服务 | ✅ 适合服务包 |
| **政府项目申报 / 高新 / 专精特新** | ★★★★☆ | 高 | 规则年年变、不能「包过」 | ✅ 现金流备选 |
| 环评 / 排污许可 | ★★★☆☆ | 中 | 有技术模型，不只是文档 | 🟡 后期 |
| 招投标文件 | ★★★☆☆ | 中低 | 价格战、造假风险 | ⛔ 不推荐 |
| ESG / 碳核查 / 碳足迹 | ★★★☆☆ | 中 | 标准演化快、计算重 | 🟡 观察 |
| 数据合规 / 等保测评 | ★★★☆☆ | 中 | 咨询属性重 | 🟡 可选 |
| 金融信贷 / 医疗病历 | ★★☆☆☆ | 高 | 合规 / 数据门槛极高 | ⛔ 不是退路 |

### 12.4 复用率与真实成本

| 资产 | 可复用比例 | 说明 |
|---|---|---|
| 引擎（解析 / 规则 / 模板 / 溯源 / 编排） | **70–80%** | 真正的期权 |
| 前端框架 / 多租户 / 权限 | **60–70%** | 需改领域字段 |
| 领域包（条款 / 模板 / NC / 章节 / 提示词） | **10–20%** | 几乎要重做 |
| 专家网络 / 渠道 / 信任 | **0%** | 要重新挣 |

**进入新垂直的真实成本**：

- 有领域专家 + 现成客户：**2–4 个月**做出窄 MVP。
- 没有专家、只靠代码：**不要进**，会做出一堆「看起来对、专家不认」的东西。

> **代码是门票，不是生意。** 新行业愿不愿意买，取决于「谁给你介绍前 3 个客户」，不取决于复用了多少行代码。

### 12.5 三条退路（按成本从低到高）

#### 退路 1：同一批客户，换一个标准（最便宜）

- 从 ISO 9001 / 13485 扩到 **14001 / 45001 / 27001 / 22000**。
- 客户、渠道、专家、话术都不变，只加「标准包」。
- 成本：**1–2 个月 / 标准**（内容为主）。
- **这是真正的第二曲线，不是换行业。**

#### 退路 2：邻近行业（2–4 个月）

- 实验室 CNAS/CMA、安全生产标准化、政府项目申报、医疗器械注册。
- 复用引擎，重做领域包，借现有专家进入。
- 关键不是代码，是**找到那个行业的 1 位共建专家 + 3 个试点客户**。

#### 退路 3：通用文档工具 / API（最差，不推荐）

- 「什么文档都能填、什么规则都能配」。
- 会直接撞上大模型厂商和通用 Agent，**没有领域壁垒，价格战**。

### 12.6 先诊断失败模式，再决定是否换行业

| 失败原因 | 换行业有用吗 | 正确动作 |
|---|---|---|
| 内容填不满、专家不认 | ❌ 没用 | 先补内容，别换行业 |
| 没有客户 / 没有渠道 | ❌ 没用 | 先换获客，别换行业 |
| 交付太重、每家都要驻场 | ✅ 有用 | 换标准化程度更高的场景 |
| 单价太低、养不活 | ✅ 有用 | 换高价值场景（医械注册 / CNAS） |
| 产品太宽、三端都做 | ❌ 没用 | 收缩，不是换行业 |
| 合规 / 责任压力太大 | 🟡 部分有用 | 换低责任场景，或纯工具定位 |

> **换行业只能解决「场景不匹配」，解决不了「没客户」和「没内容」。**

### 12.7 医疗器械分叉：13485 / NMPA / CNAS/CMA

| 路径 | 审什么 | 客户 | 付费 | 复用度 | 关键能力 | 建议 |
|---|---|---|---|---|---|---|
| **ISO 13485** | 质量管理体系 | 医疗器械制造商 | 高 | **高** | 设计开发、风险、CAPA、追溯、供应商、无菌/IVD | 朋友是 13485 专家 ⇒ **先做这条** |
| **NMPA 注册** | 产品上市许可 | 医疗器械制造商 | **更高** | 中 | 产品技术要求、研究资料、临床评价、说明书 | 朋友是 RA 专家 ⇒ 做「注册资料一致性检查」，**不代写/不保证** |
| **CNAS / CMA** | 实验室技术能力 | 实验室 / 检验检测机构 | 中高 | 中 | 方法验证、不确定度、能力验证、原始记录、设备校准 | 另一条线；除非朋友是实验室专家，否则**后置** |

**先问朋友三个问题**：

1. 你最熟的是 **ISO 13485 体系**，还是 **NMPA 注册（RA）**？
2. 你手上有没有 **3 家制造商**愿意试用？
3. 你愿意做**规则共建 / 审校**吗？每周能投入多少时间？

**建议**：

- **13485** → 先做体系垂直；复用度最高，但定位是「辅助检查」，不能生成运行记录。
- **NMPA** → 做「注册资料体检」，价值更高；必须由 RA 专家背书，不能承诺过审。
- **CNAS/CMA** → 不要和 13485 混为一谈；它是技术能力认可，领域包要重做。
- **不要同时做三条**；先选一条，跑通再扩。

> **13485 这条线的完整验证与 6 个月计划，见 [43-ACM分析与ISO13485小众软件规划](43-ACM分析与ISO13485小众软件规划-V1.md)**：V4 已按“新发证数不是核心指标”修订，改看 **审计事件 / 专家座位 / 单项目工作量**；并明确 **企业端 = 事实文档 + 预 NC**（从原始资料提取事实、逐句绑定出处、缺证据标缺口），与专家端 **同引擎、两个前台**，不是转行。含 ACM 事实底稿、3 条款 MVP、极简产品要求、定价与止损线。

### 12.8 架构期权：引擎与领域包分离

```
Engine（稳定）
  ├─ 解析 / 提取
  ├─ 规则执行
  ├─ 模板渲染
  ├─ 溯源 / 审计
  └─ DAG 编排
        ↑
Domain Pack（可替换）
  ├─ 标准条款库
  ├─ 文档模板
  ├─ 校验规则
  ├─ 提示词
  ├─ 样例与测试夹具
  └─ 领域术语
```

**原则**：

- 不要现在重构成「通用平台」；只在改动时**渐进抽出**。
- 认证相关的条款、模板、提示词，**不要继续泄漏进核心**。
- 每个领域包都能独立测试；换标准 / 换行业时，引擎不改。

### 12.9 启动第二曲线的触发条件

| 时间 | 信号 | 动作 |
|---|---|---|
| 第 8 周 | 没有 1 位专家愿意共建 | 换标准 / 换人群；不是换行业 |
| 第 12 周 | 没有人第二次使用 | 收缩到一个场景，再跑 4 周 |
| 第 16 周 | 没有付费客户 / 机构合同 | 先诊断失败模式：内容、渠道、交付、单价 |
| 第 16 周 | 诊断结论是「场景不匹配」 | 启动**退路 1**（同客户多标准）或**退路 2**（邻近行业） |
| 第 24 周 | 第 2 个客户配置工时 > 第 1 个的 30% | 按项目制管理，不按 SaaS 扩张 |

### 12.10 一句话

> **代码让你有 2–3 次机会，不是无限次。**
> **下一次选行业，不要看「代码能复用多少」，要看「谁能给你介绍 3 个客户」。**
