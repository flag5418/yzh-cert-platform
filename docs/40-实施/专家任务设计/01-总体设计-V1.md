## 一、系统定位与边界

### 1.1 定位

**CertExpert（专家平台）任务子系统**是「体系认证审核」的执行环节。管理员/实施人员在后台配置**规则**（NC 检查规则 / 报告章节规则），专家在企业资料齐备后发起**任务**，系统自动执行并产出**结果**，专家**逐条认可或修改**，最后**导出 Excel**。

一句话：**配置层（管理端）→ 执行层（专家端任务）→ 产物（Excel）**。

### 1.2 明确的非目标（本期不做）

| 不做 | 理由 |
|---|---|
| docx / pdf 报告生成 | D14：这是工具系统，不是报表系统。固定格式 Excel 即可 |
| 客户定制报表格式 | D09：同上 |
| 字段级/文件级证据追溯下钻 | D08：归后台工作流设计（规则侧）实现。规则引擎已有 `RuleContext` 快照可查 |
| 双人复核（制单≠审核） | D21：注册人即管理员，全权限 |
| 任务追加检查项/章节 | D20：进入 `running` 后不可变更范围，避免中途改范围污染结果 |
| 整改跟踪（NC 开具后的整改闭环） | `audit_rectification` 表已存在但属另一功能域，本期只做到 NC 记录生成 |
| 改代码标识符（`CertPlatform.*` → `CertExpert.*`） | D18：影响面过大（命名空间/目录/构建/路由/文档），另开任务 |

### 1.3 角色

| 角色 | 载体 | 权限 |
|---|---|---|
| 专家 | `cert_auditor_profile` + `Sys_User`（工作区内） | 建任务、跑队列、补录、认可/修改、批准、导出。**注册即管理员，全权限**（D21） |
| 管理员 / 实施人员 | `CertPlatform.Admin` | 配置 NC 规则、报告章节、工作流 DAG、Prompt 模板、文档提取规则 |

> 多租户隔离唯一入口：`WorkspaceContextService.Resolve()`（`CertPlatform.Auditor/Services/`）。所有专家端端点**必须**先解析工作区上下文，任务表的 `OrgCode` 一律取自该上下文，**禁止**从请求参数取。

### 2.2 为什么 NC 检查项与报告章节可以合表

用户原始描述的第 5 条：

> 「所有的队列执行完成后，专家可以手动进行批准，哪些自动检查的结果是 ok 的，也可以手动修改」
> 「nc 检查报告和报告内容可以导出」

以及最终裁决 D14：

> 「执行完成应该是按每个标准，每个章节的列表，和 nc 检查项一样，用户可以审批是否接受，也可以修改报告内容」

**判断依据**：两类对象的生命周期完全一致 ——

| 阶段 | NC 检查项 | 报告章节 |
|---|---|---|
| 来源 | `cert_validation_rule`（规则 Code） | `rpt_report_section`（章节 Code） |
| 执行 | 工作流 DAG 跑一遍 | 工作流 DAG 跑一遍 |
| 自动产出 | 结论 + 严重度 + 说明 | 章节正文 |
| 专家动作 | 认可 / 改结论 / 改严重度 / 改说明 | 认可 / 改正文 |
| 留痕 | 必需 | 必需 |
| 导出 | Excel 一行 | Excel 一行/一段 |
| 缺数据 | 跳过不显示 | 跳过不显示 |

**唯一差异是 3 个标量列**：

| 差异点 | 列名 | NC 检查项 | 报告章节 |
|---|---|---|---|
| 判定结果 | `Conformity` | `conform`/`nonconform`/`observation`/`na` | 恒为 `null`（章节不判定合规） |
| 严重度 | `Severity` | `major`/`minor`/`observation` | 恒为 `null` |
| 结果正文 | `ContentText` | 说明文字（可空） | **章节正文（核心产物）** |

因此设计成**统一表 `tsk_task_item`**，这 3 列在不同 `ItemType` 下留空。这样做带来的收益：

1. 认可 / 修改 / 日志 / 导出 / 列表混排 —— **只写一遍逻辑**
2. 任务级统计（总数/待认可/已认可/已修改/跳过）—— **一条 SQL 聚合**
3. 批准前置校验（「所有结果必须被认可」，D12）—— **一次校验覆盖两类**
4. 未来加第三类结果（如「不符合项跟踪」）—— **零表结构改动**

### 2.3 三层「Code」辨析（极易出错，务必分清）

| 层级 | 键 | 取值 | 举例 |
|---|---|---|---|
| 任务层 | `tsk_task.Code` | GUID | `a1b2c3...` |
| 子任务层 | `tsk_task_standard.Code` | GUID | `d4e5f6...` |
| 规则层 | `ItemCode` | `cert_validation_rule.Code` 或 `rpt_report_section.Code` | `7f8a9b...` |

> ⛔ `ItemCode` 存的是**规则表的主业务键**，不是 `RuleCode`（`NC-{StandardCode}-{seq:D3}`）也不是条款号。关联回规则时用 `ItemCode`，展示时读规则的 `RuleName`。

### 3.2 关键顺序约束（三条硬规则）

| # | 规则 | 强制点 | 违反后果 |
|---|---|---|---|
| **O1** | **业务锁**：`(企业, 阶段)` 上存在任一非终态任务 → 禁止新建任务、禁止企业文件上传/替换/删除 | 建任务前 + 文件操作前（`CertEnterpriseFileController` 需接同一把锁） | 中途换文件 → 已跑的队列结果与新文件不一致，结论失真 |
| **O2** | **软阻塞**：未补录且未跳过的 gap 存在 → 拒绝 `submit` | `POST /{code}/submit` 事务内重跑完备性检查 | 缺数据跑出来的结论是假的 |
| **O3** | **认可强制**：任一 item 的 `ReviewStatus=pending` → 拒绝 `approve` | `POST /{code}/approve` | 未复核的结果被当成定论，追溯链断裂 |

> O1 的锁**不分任务类型**（D15）—— NC 任务未结束就不能建报告任务。这天然保证了「先 NC 检查、后出报告」的业务顺序，专家无需人工记住次序。

## 四、状态机

### 4.1 任务状态机（`tsk_task.TaskStatus`）

```
                    ┌─────────────────────────────────────────┐
                    │                                         │
  创建              ▼        完备性检查        提交           │ 批准
 ──────▶ draft ──────────▶ gap_detected ──────▶ pending_run   │
                    │            │                  │           │
                    │            │                  ▼           │
                    │            │              running         │
                    │            │                  │           │
                    │            │    全部队列结束   │           │
                    │            │    （有失败也算） │           │
                    │            │                  ▼           │
                    │            └────────────▶ pending_review ──┼──▶ approved
                    │                              │            │        （终态）
                    │        重新补录后再次提交     │            │
                    │        （可无限次）           ▼            ▼
                    │                          running     approved
                    │                                         （终态）
                    │
                    └────── 任意非终态状态 ──▶ cancelled（专家作废）
```

| 状态 | 含义 | 可执行操作 |
|---|---|---|
| `draft` | 已创建，未提交 | 补录、跳过 gap、提交、作废 |
| `gap_detected` | 已跑完备性检查，产出补录清单 | 补录、跳过 gap、重新检查、提交、作废 |
| `pending_run` | 已入队，等待 worker 领取 | 查看进度、作废 |
| `running` | 至少一个队列在跑 | 查看进度、作废 |
| `pending_review` | 全部队列结束（含失败），结果待认可 | 认可、修改、批准、**导出（草稿态）**、作废 |
| `approved` | 全部结果已认可，任务定稿 | **导出（定稿）**、查看日志 |
| `cancelled` | 专家作废 | 只读 |
| `failed` | 队列全部失败且无可用结果 | 重新提交（重试） |

> `gap_detected` 是**软状态**而非阻断状态：专家可以完全不补录、直接 `submit`，此时所有相关 item 会走 `skipped`（D05）。因此 `submit` 时若无任何 gap 处于 `pending` 也放行。

### 4.2 任务项状态机（`tsk_task_item.ReviewStatus`）

```
                        ┌──────────────────────────────────────┐
                        │                                      │
  队列执行              ▼                                      │
 ───────────▶  ┌─────────────────┐                            │
               │   pending       │  （待认可）                 │
               │  ReviewStatus   │                            │
               └────┬───────┬────┘                            │
                    │       │                                 │
      专家点「认可」 │       │ 专家点「保存修改」               │
      (D12 强制)    │       │ (★修改即认可 D11)               │
                    │       │                                 │
                    ▼       ▼                                 │
            ┌──────────┐  ┌──────────┐                        │
            │acknowledged│ │ modified │ ─────────────────────┘
            │  已认可   │  │ 已修改   │
            └──────────┘  └──────────┘

  独立分支（队列执行时直接落）：
            ┌──────────┐
            │ skipped  │  数据不足 / 规则禁用 / 无规则 / 人工模式 / 执行失败
            │  已跳过  │  ★不显示结果内容，只显示「缺乏必要数据」
            └──────────┘
```

**`skipped` 为什么不算「未认可」**：D05 明确「该流程缺乏必要数据，该流程就自动不执行，并告知这条规则缺乏必要数据，不显示结果」。它是一个**确定性的终态**，不是「还没看」。因此 O3 认可校验放行 `skipped`。

**`pending` 是唯一的阻塞态**。任务下只要有一个 `pending` 的 item，`approve` 就拒绝。

### 4.3 数据缺口状态机（`tsk_task_data_gap.GapStatus`）

```
  完备性检查产出
        │
        ▼
   ┌─────────┐   专家补录    ┌─────────┐
   │ pending │─────────────▶│ filled  │
   └────┬────┘              └─────────┘
        │
        │ 专家跳过（整体 or 单条）
        ▼
   ┌─────────┐
   │ skipped │  终态
   └─────────┘

  补录后文件被替换 → 该 gap 重置为 pending（见 05 号 §6）
```

       ★ 不产出 AutoResult，不生成 NC 记录

## 六、设计原则（本期遵守）

| # | 原则 | 具体含义 |
|---|---|---|
| P1 | **单一真相源** | 任务结果只存 `tsk_task_item`。`wf_execution_task_item` 是过程留痕（引擎视角），`tsk_task_item` 是业务结论（专家视角）。两者通过 `RuleCode` 关联，不互为副本 |
| P2 | **规则不脏** | 任务**绝不回写** `cert_validation_rule` / `rpt_report_section`。补录只写 `cert_extraction_result` / `cert_table_extraction_result`（企业域数据）。规则是全企业共享的配置，被单企业任务污染是灾难 |
| P3 | **不物理删** | 所有表用 `IsDeleted`；`cert_extraction_result.IsValid` 复用为「1=当前版本，0=归档旧版本」（企业域版本链，见 10 号分册 02 号 V-P1）。不 DROP 任何历史数据 |
| P4 | **缺数据即显式跳过，绝不静默** | 与其产出空结果让人误以为「检查通过」，不如显式标记「数据不足未检查」（D05） |
| P5 | **一切人工动作留痕** | 补录、认可、修改三类动作全部落日志表（05 号）。日志只追加，永不更新 |
| P6 | **软阻塞优于硬拦截** | D04：允许专家跳过。系统提示但不强制，业务节奏由专家掌控 |
| P7 | **口径唯一** | 阶段统一用 `cert_cert_stage.Code`；启用标志统一 `IsValid`；队列 ScopeKey = 子任务 Code（不复用 `yzh_queue` 的双口径，见 09 号 D20） |
| P8 | **三层同构** | 后端 Controller / 前端 api / 前端 pages 三层同名同路径（`docs/30-项目规则/前后端代码结构统一规则-V1.md`） |

## 七、验收标准（本期完成的样子）

一句话验收：**专家选企业+阶段 → 系统告知缺 3 个字段 → 专家补录 2 个、跳过 1 个 → 提交 → 队列跑出 5 条结果（4 条正常 + 1 条跳过）→ 专家改 1 条认可 4 条 → 批准 → 导出 Excel 5 个 Sheet（按标准分）→ 每条结果都能查到谁在什么时候改了什么**。

详细验收清单见 [09-实施计划-V1.md](09-实施计划-V1.md) §四。
