# 18 NC 检查结论判定体系（Skill 与节点设计）

> 目的：把「NC 检查的结论必须符合体系认证，而不是不受控的自由输出」这一诉求，**落成可实施、可配置、可审计的技术设计**。
> 状态：**设计已定稿，待实现**
> 依据：引擎实测（`WorkflowInterpreter` / `NodeExecutor` / `AiNodeExecutor` / `SkillExecutor` / `CertSkillRegistry`）

---

## 一、要解决的三个问题

| # | 问题 | 后果 |
|---|---|---|
| **P1** | 工作流有**多路径**（`WorkflowConfigParser.EnumeratePaths` DFS 枚举），但执行端 `AggregateNcResult` **只取第一条成功路径**（`WorkflowInterpreter.cs:237-241`） | ★ 多维度的检查结果被丢弃，结论失真 |
| **P2** | AI 输出是自由文本/自由 JSON，**不受控** | ★ 同一批结果两次跑出不同结论；可能输出「良好/优秀」等非标准词 |
| **P3** | 认证结论（完全符合/基本符合/不符合）的**判定规则是行业标准**，不是产品自定义 | ⛔ 不能写死在代码里；也不能猜 |

**本篇的解法**：

```
P1 → 用「ai_node 单节点多维度」替代「多路径」：一次 AI 调用判所有维度，无路径竞争
P2 → 规则引擎算结论（权威） + AI 只写说明（可读） + 后端枚举/依据校验（兜底）
P3 → 判定规则全部落配置表（cert_conclusion_rule），标准确认后只改配置
```

---

## 二、★ 关键设计决策：为什么用「单节点多维度」而不是「多路径」

### 2.1 两种范式的对比

| | 范式 A：多路径 + 汇聚 Skill | ★ 范式 B：单节点多维度（采纳） |
|---|---|---|
| 画布 | N 条路径 + 1 个汇聚节点 | **1 个 `nc判断` 节点** |
| LLM 调用 | N 次（每路径一次） | ★ **1 次** |
| 增删维度 | 改工作流图 | ★ 改规则配置 `dimensions` |
| 维度间关联判断 | ❌ 做不到 | ★ **能**（"审批与发放同时缺失 → 体系性问题 → 升级为严重"） |
| 结果完整性 | ★ 有 bug（只取第一条） | ✅ 单次输出完整列表 |

**决定性理由**：**维度之间的关联判断**是认证审核的核心业务能力。

> 例：维度1「文件审批记录」不符合 + 维度2「文件发放记录」不符合
> - 孤立看：2 个一般不符合
> - 关联看：★ **文件控制过程整体失效** → 升级为**严重不符合**
>
> 这个判断只有单节点方案能做（多路径方案里两条路径互不可见）。

### 2.2 引擎能力核实（全部实测）

| 能力 | 依据 | 结论 |
|---|---|---|
| 一个 `ai_node` 能引用**任意多个**上游节点输出 | `AiNodeExecutor.cs:148` `ResolveTemplateRefs(template, sharedOutputs, paramPool)`，模板写 `{{节点名.端口}}` | ✅ 可行 |
| 表格数据能进 Prompt | `NodeExecutor.ExecuteDocTableAsync` 返回 `{ rows, rowCount, confidence, source }` | ✅ 可行 |
| 字段数据能进 Prompt | `ExecuteDocFieldAsync` 返回 `{ fieldValue, confidence, source }` | ✅ 可行 |
| 证据可自动带出 | `wf_node_execution.SourceFileCode` / `SourceFieldName` / `SourceVersion`（17 号 §三） | ✅ 免费 |
| Skill 能否接收集合参数 | ❌ `SkillExecutor.cs:252-269` `ConvertValue` 只支持标量；`context.Inputs` 是 `Dictionary<string,object>`，一个 key 一个值 | ⛔ **不行，故汇聚必须用 `ai_node`** |

### 3.2 `nc判断` 节点（ai_node · Code: `nc_judge`）

**职责**：把「企业文档事实」+「维度要求」→ 变成「结构化的维度判定列表」

**输入契约**：

| 占位符 | 来源 | 必需 |
|---|---|---|
| `{{任一docfield节点.fieldValue}}` | 画布连线 | 至少一个 |
| `{{任一doctable节点.rows}}` | 画布连线 | 可选 |
| `{{__RULE__.dimensions}}` | ★ 规则表的维度清单（系统自动注入） | ★ 是 |
| `{{__RULE__.clause}}` | 条款号+标题+内容（系统自动注入） | ★ 是 |

> ★ `__RULE__` 前缀是**保留占位符**，由后端在执行前从 `cert_validation_rule` 读取并注入 `paramPool`。这样实施人员改维度清单不用动工作流图。

**输出契约**（严格 JSON）：

```json
{
  "dimensions": [
    {
      "no": 1,
      "name": "文件审批记录完整性",
      "conformity": "nonconform",
      "desc": "3 份审批记录缺少审批人签字，且未记录审批日期",
      "evidence": "审批台账.xlsx 第 5、9、14 行",
      "confidence": 0.91
    },
    {
      "no": 2,
      "name": "审批流程规定性",
      "conformity": "conform",
      "desc": "文件控制程序第 2 节规定了审批流程与授权要求",
      "evidence": "文件控制程序.pdf 第 2 节",
      "confidence": 0.95
    },
    {
      "no": 3,
      "name": "文件变更控制",
      "conformity": "unverifiable",
      "desc": "企业未提供文件变更记录，无法判断",
      "evidence": "",
      "confidence": 0.0
    }
  ]
}
```

**★ 四态语义**（不是 bool）：

| 值 | 含义 | 说明 |
|---|---|---|
| `conform` | 符合 | 维度要求已满足 |
| `nonconform` | 不符合 | 有客观证据表明未满足 |
| `na` | 不适用 | 该维度对企业不适用（如无出口产品则无"出口文件控制"） |
| `unverifiable` | **无法判断** | ★ 材料不足 / 证据缺失 |

> ⛔ **`unverifiable` ≠ `nonconform`**。认证审核中这是基本要求：不能说"没查到"就是"不符合"，也不能说"没查到"就算"符合"。

**Prompt 模板**（存 `cert_nc_judge_prompt` 表，版本化）：

```
你是体系认证审核员。请根据以下材料，对照审核维度逐项判断。

【审核标准】{{__RULE__.clause}}
【条款原文】{{__RULE__.clauseContent}}

【检查维度清单】
{{__RULE__.dimensions}}

【企业提供的客观材料】
{{__DATA__}}

【判定要求】
1. ★ 只依据上述材料判断，材料不足时一律标 unverifiable，禁止推测
2. 每个维度必须给出 evidence（文件名+位置）；unverifiable 时 evidence 留空
3. ★ 四态严格区分：
   - conform      符合
   - nonconform   不符合（必须指出具体哪里不符合、差多少）
   - na           不适用（该维度对企业无适用性）
   - unverifiable 材料不足无法判断
4. 维度之间可以关联判断：若两个以上维度同时 nonconform，且属于同一过程，
   在 desc 中注明「该过程整体失效」，供上层升级严重度

【输出格式】严格输出 JSON，不要任何解释文字：
{"dimensions":[{"no":1,"name":"...","conformity":"...","desc":"...","evidence":"...","confidence":0.0}]}
```

### 3.3 ★ 规则引擎（纯代码 · 非 AI · 权威）

**这是整个设计的核心**：结论由代码算，不由 AI 判。

```csharp
public class NcConclusionCalculator
{
    /// <summary>
    /// ★ 权威结论计算。AI 不得参与此项判定。
    /// 规则来源：cert_conclusion_rule（可配置，标准确认后只改配置）
    /// </summary>
    public ConclusionResult Calculate(
        IReadOnlyList<DimensionResult> dimensions,
        ConclusionRule rule)
    {
        // ① 统计
        var nonconform = dimensions.Where(d => d.Conformity == "nonconform").ToList();
        var unverifiable = dimensions.Where(d => d.Conformity == "unverifiable").ToList();
        var na           = dimensions.Where(d => d.Conformity == "na").ToList();

        // ② ★ 严重不符合判定（顺序不可颠倒：先严重，后一般）
        bool hasMajor = nonconform.Any(d => d.Severity == "major")
                     || (rule.CrossProcessEnabled
                         && HasCrossProcessFailure(nonconform, rule));   // ★ 跨过程失效升级

        if (hasMajor)
            return New(rule.LevelReject, nonconform, unverifiable, "major");

        // ③ 一般不符合累计
        if (nonconform.Count >= rule.MinorRejectThreshold)
            return New(rule.LevelReject, nonconform, unverifiable, "minor");

        if (nonconform.Count >= rule.MinorToBasicThreshold)
            return New(rule.LevelBasic, nonconform, unverifiable, "minor");

        // ④ ★ 未检查项封顶（存在无法判断的维度，不能给"完全符合"）
        if (unverifiable.Count > 0)
            return New(CapLevel(rule, unverifiable), nonconform, unverifiable, null);

        return New(rule.LevelFull, nonconform, unverifiable, null);
    }
}
```

**★ 跨过程失效升级**（范式 B 独有能力）：

```csharp
/// <summary>
/// 同一过程下有 ≥ N 个维度不符合 → 判定为「该过程整体失效」→ 升级为严重不符合。
/// 例：7.5 成文信息下，「审批记录」+「发放记录」同时缺失
///     → 不是 2 个一般不符合，而是「文件控制过程整体失效」→ 严重不符合
/// </summary>
private bool HasCrossProcessFailure(
    IReadOnlyList<DimensionResult> nonconform, ConclusionRule rule)
{
    return nonconform
        .Where(d => !string.IsNullOrEmpty(d.ProcessCode))
        .GroupBy(d => d.ProcessCode)
        .Any(g => g.Count() >= rule.CrossProcessThreshold);
}
```

> `ProcessCode`（过程代号）由维度配置携带，如 `P-7.5-成文信息`。**无过程代号的维度不参与升级判定**。

### 3.4 `nc结论` 节点（ai_node · Code: `nc_conclude`）

**职责**：★ **只写理由，不判结论**。

| 输入 | 来源 | 说明 |
|---|---|---|
| `{{__RULE__.conclusion}}` | ★ 规则引擎算出的**权威结论** | 系统注入 |
| `{{__RULE__.basis}}` | 依据维度编号 | 系统注入 |
| `{{__RULE__.unverified}}` | 未检查维度 | 系统注入 |
| `{{__NODE__.dimensions}}` | `nc判断` 的输出 | 画布连线 |

**输出**：

```json
{
  "reason": "文件审批与发放两个维度均不符合，文件控制过程整体失效；文件变更维度因缺记录未检查。",
  "suggestedFix": null
}
```

**Prompt 模板**：

```
你是体系认证审核报告撰写人。请根据已判定的审核结果，写一句话说明结论理由。

【已判定结论】（★已由系统确定，不得更改）
结论等级：{{__RULE__.conclusion}}
依据维度：{{__RULE__.basis}}
未检查项：{{__RULE__.unverified}}

【各维度明细】
{{__NODE__.dimensions}}

【要求】
1. ★ 不得改变结论等级
2. ★ 不得添加未在"依据维度"中列出的维度
3. 一句话，不超过 60 字，须包含"哪里不符合 + 什么程度"
4. 若存在未检查项，须在理由中体现
5. 严格输出 JSON：{"reason":"..."}
```

### 3.5 ★ 输出校验器（后端，非 AI · 兜底）

| # | 校验 | 不通过时 |
|---|---|---|
| C1 | `nc判断` 输出的 `dimensions` 数组存在且非空 | ❌ 节点 `failed` |
| C2 | 维度 `no` 集合 ⊇ 规则表配置的维度编号 | ❌ 判 `failed`（防漏判） |
| C3 | `conformity` ∈ 四态枚举 | ❌ 该维度置 `unverifiable` + 告警 |
| C4 | `nonconform` 的 `desc` 非空 | ⚠️ 允许空但标记 warning |
| C5 | `evidence` 中的文件在 `wf_node_execution.SourceFileCode` 中存在 | ⚠️ 标记 `evidence_unverified`（防幻觉，但不阻断） |
| C6 | ★ `nc结论` 的 `reason` 里若出现「依据维度」以外的维度号 | ⚠️ 剥离 + 告警 |
| C7 | ★ 规则引擎结论 vs AI 若产出结论 | ★ **以规则为准**（AI 的仅记录，不采纳） |

> **C5 的价值**：`wf_node_execution.SourceFileCode` 是引擎自动记录的真实来源（17 号 §三实测）。AI 说的证据如果引擎没记录到，就是幻觉 —— 这是一个**零成本的交叉验证**。

## 五、结论规则配置表（★ 标准确认后只改这里）

```sql
-- ============================================================
-- Table: cert_conclusion_rule（认证结论判定规则）
-- 说明：★ 行业标准要求，规则全部落配置，标准确认后只改配置不改代码
-- ============================================================
CREATE TABLE cert_conclusion_rule (
  Id              bigint      NOT NULL AUTO_INCREMENT,
  Code            varchar(36) COLLATE utf8mb4_general_ci NOT NULL COMMENT '业务键',
  OrgCode         varchar(50) COLLATE utf8mb4_general_ci NOT NULL COMMENT '认证机构编码',
  StandardCode    varchar(36) COLLATE utf8mb4_general_ci NOT NULL COMMENT '标准编码（★全部标准的通用规则可共用一行 StandardCode=''）',
  PhaseCode       varchar(36) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '阶段（NULL=全阶段）',

  LevelFull       varchar(30) COLLATE utf8mb4_general_ci NOT NULL DEFAULT '完全符合' COMMENT '最高档结论词',
  LevelBasic      varchar(30) COLLATE utf8mb4_general_ci NOT NULL DEFAULT '基本符合' COMMENT '中间档结论词',
  LevelReject     varchar(30) COLLATE utf8mb4_general_ci NOT NULL DEFAULT '不符合'   COMMENT '最低档结论词',
  ConclusionOrder json        DEFAULT NULL COMMENT '★结论档位顺序（数组，供枚举校验与降级判断）',

  MinorToBasicThreshold  int NOT NULL DEFAULT 3 COMMENT '★一般不符合 ≥ N → 基本符合',
  MinorRejectThreshold   int NOT NULL DEFAULT 5 COMMENT '★一般不符合 ≥ N → 不符合',

  CrossProcessEnabled    tinyint(1) NOT NULL DEFAULT 1 COMMENT '★是否启用跨过程失效升级',
  CrossProcessThreshold  int NOT NULL DEFAULT 2 COMMENT '★同过程 ≥ N 个维度不符合 → 升级为严重',

  UnverifiedPolicy      varchar(30) COLLATE utf8mb4_general_ci NOT NULL DEFAULT 'cap_basic'
                        COMMENT '存在未检查项时的处理：cap_basic=最高只能到中间档 | reject=直接判不符合 | ignore=不处理',

  JudgePromptCode   varchar(100) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT 'nc判断 的 Prompt 模板编码',
  ConcludePromptCode varchar(100) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT 'nc结论 的 Prompt 模板编码',

  SourceRef         varchar(500) COLLATE utf8mb4_general_ci DEFAULT NULL
                    COMMENT '★规则来源（标准号+条款号+版本），供审计追溯',
  IsValid           int NOT NULL DEFAULT 1,
  IsDeleted         tinyint(1) NOT NULL DEFAULT 0,
  CreateBy varchar(50), CreateTime datetime DEFAULT CURRENT_TIMESTAMP,
  UpdateBy varchar(50), UpdateTime datetime,
  DeleteBy varchar(50), DeleteTime datetime,
  Status varchar(50), Sort int DEFAULT 0, Remark varchar(500),
  PRIMARY KEY (Id), UNIQUE KEY uk_code (Code),
  KEY idx_scope (OrgCode, StandardCode, PhaseCode, IsValid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  COMMENT='★认证结论判定规则（行业标准，全部可配置）';
```

> ⚠️ **`SourceRef` 是审计关键**：记录"这条规则依据哪份标准的哪个版本"。标准换版时，改配置 + 填 `SourceRef`，历史结论可回溯。

### 5.1 ⚠️ 待确认的默认值（★ 不能猜）

表中默认值 `3` / `5` / `2` **是占位，不是标准**。必须由你们与认证机构确认后填写。

| 参数 | 含义 | 现状 |
|---|---|---|
| `MinorToBasicThreshold` | 几个一般不符合 = 基本符合 | ⛔ **待确认** |
| `MinorRejectThreshold` | 几个一般不符合 = 不符合 | ⛔ **待确认** |
| `CrossProcessThreshold` | 同过程几个维度失效 = 严重不符合 | ⛔ **待确认** |
| `UnverifiedPolicy` | 有未检查项怎么办 | ⛔ **待确认** |

## 九、★ 结论生成的三种模式（规则即专家论证产物）

### 9.1 核心认知：规则不是"待实验的草稿"，而是"已论证的资产"

本系统的 NC 规则是**一条一条配置出来的，配置全程专家参与**：

```
① 专家定义维度（7.5 拆成 审批记录/流程规定/变更控制 三个维度）
     ↓
② 专家逐维度论证判定标准（"抽 5 份全有签字且有日期 → conform"）
     ↓
③ 专家用真实企业数据试跑，验证判定标准是否可执行
     ↓
④ 论证稳定 → 发布规则（cert_validation_rule.RuleVersion + 1）
```

**这意味着**：

| 认知 | 推论 |
|---|---|
| 规则是专家**已经论证过**的 | ⛔ 不需要每次运行都"再论证一次" |
| 判定标准（`JudgeCriteria`）是专家写的 | ✅ `nc_judge` 的 Prompt 主要是**格式约束**，不是"教 AI 怎么判定" |
| 规则稳定后才发布 | ✅ 已发布的规则可以直接信任其自动判定结果 |
| ⛔ **专家配置一条规则的成本很高**（写判定标准 + 试跑 + 论证） | ★ 这正是要自动化的部分 |

### 9.2 三种模式

| 模式 | 含义 | 专家参与度 | 适用 |
|---|---|---|---|
| **`RULE_ONLY`** | ★ **只按规则表算，不调 AI** | 零 | ✅ 规则已充分论证、判定逻辑可枚举时 |
| **`AI_ASSISTED`** | ★ **规则算结论 + AI 写理由**（辅助） | 审理由 | 结论可枚举，但理由需要语言表达 |
| **`EXPERT_MANUAL`** | 专家逐条人工判定 | 全程 | 新型不符合模式、规则未覆盖的探索期 |

> ⛔ **不要"全 AI 判结论"**：规则配置已由专家论证完毕，AI 重新判定会引入漂移且不可复现。AI 的定位是**辅助**（把结构化结果翻译成人话），不是**决策者**。

### 9.3 ★ 关于"提示词"的关键澄清

用户原话：

> 「哪怕 nc 结论全部由专家根据每一条路径手动判断都是可以的，但我们有个专门设计的提示词……是一个辅助，最终应该可以替代专家人工配置，因为专家人工配置，我们需要手动编写很多的提示词」

**这里要区分两种提示词**：

| 类型 | 谁写 | 内容 | 是否会随规则数增长 |
|---|---|---|---|
| **① 判定标准** | ★ **专家逐条写** | "抽 5 份全有签字 → conform" | ★ **会**（每条规则一份） |
| **② 判定框架** | ★ **我们写一次，全局复用** | "按四态输出 / 证据引用规范 / 维度关联提示" | ⛔ **不会**（所有规则共用一份） |

**因此"专家配置成本高"的解法不是让 AI 替代判定，而是**：

| 成本来源 | 解法 | 效果 |
|---|---|---|
| 每条规则要写判定标准 | 无法省（这是专家的专业判断） | ❌ 不可替代 |
| 每条规则要写 Prompt 格式约束 | ★ **抽成全局 `nc_judge` 框架 Prompt** | ✅ **省掉** |
| 每条规则要试跑论证 | ★ 走 `WorkflowTestController` 一键试跑 | ✅ 省掉手工 |
| 每条规则要人工判一遍所有维度 | ★ **`RULE_ONLY` / `AI_ASSISTED` 自动化** | ✅ **这是最大收益** |

**结论**：18 号 §3.2 的 `nc_judge` Prompt 模板应当是**一份全局复用的判定框架**，专家只填 `dimensions` 里的 `JudgeCriteria`，不写 Prompt。

### 9.4 模式切换的时机

```
规则新建         → EXPERT_MANUAL（专家边配边验）
规则首次发布     → AI_ASSISTED（AI 出理由，专家核对理由）
规则论证 2-3 次后 → RULE_ONLY（全自动，专家只看结果）
```

**降级保护**：若 `RULE_ONLY` 模式下发现某规则的结论被专家改动率 > 30%，建议告警提示"该规则可能需要重新论证"。

### 9.5 开关配置

```sql
-- cert_conclusion_rule 增列
ConclusionMode varchar(20) NOT NULL DEFAULT 'AI_ASSISTED'
  COMMENT '★结论生成模式：RULE_ONLY=仅规则 | AI_ASSISTED=规则+AI理由 | EXPERT_MANUAL=专家全人工',
ManualRequired bit NOT NULL DEFAULT 0
  COMMENT '★专家是否必须签署（RULE_ONLY 且论证充分时可为 0 → 专家不卡审核流程）',
OverrideAlertThreshold int NOT NULL DEFAULT 30
  COMMENT '★结论改动率告警阈值（%），超阈值提示规则需重新论证'
```

> ⚠️ **`ManualRequired=0` 的风险**：专家不卡流程 = 结论直接生效。需在报告上标注"本结论由系统自动判定，未经人工签署"。
