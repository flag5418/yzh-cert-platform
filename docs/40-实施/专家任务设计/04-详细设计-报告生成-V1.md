## 一、关键决策回顾（D14）

用户裁决原文：

> 「只有导出才是excel，否则执行完成应该是**按每个标准，每个章节的列表**，和 nc 检查项一样，用户可以审批是否接受，也可以修改报告内容」

由此确定 4 条设计原则：

| # | 原则 | 影响 |
|---|---|---|
| 1 | **不生成 docx、不落 `rpt_audit_report`** | 报告的产物是**章节列表**（`tsk_task_item`，`ItemType='report_section'`），不是报告文件 |
| 2 | **章节不合并，按标准分节** | 同一阶段关联 3 个标准 → 3 套独立章节，各自成区 |
| 3 | **专家逐章节认可/修改** | 与 NC 检查项完全一致的交互 |
| 4 | **导出才出 Excel，一个标准一个 Sheet** | 每个标准一个 Sheet，章节按 `SortOrder` 纵向排列 |

> **与 NC 检查的结构对称性**：见 [01 号 §2.2](01-总体设计-V1.md)。本章只讲差异，相同部分（认可、修改、日志、跳过、队列）不重复。

## 二、报告章节的元数据解析

### 2.1 ★ 三个必须注意的口径问题

#### 问题 1：`rpt_report_section` 没有 `StandardCode` 列

```sql
-- 现状（all_tables_ddl.sql:1643-1675）
CREATE TABLE `rpt_report_section` (
  `Code`         varchar(36)  NOT NULL,
  `ReportCode`   varchar(36)  NOT NULL,   -- ★ 存的是 ReportTemplate.Code，不是 rpt_audit_report.Code
  `SectionName`  varchar(200),
  `SectionNameEn` varchar(200),
  `SectionContent` text,                  -- ★ 列名是 SectionContent，不是 Content
  `SortOrder`    int,
  `IsActive`     tinyint(1),              -- ★ 违反铁律九，本期改 IsValid
  `WorkflowCode` varchar(36),
  `WorkflowConfig` text,                  -- ★ 工作流 DAG 在这里（规则是在 RuleJson）
  `LayoutJson`   text,
  `SectionJson`  text,
  `ClauseCode`   varchar(36),
  `OrgCode`      varchar(50),
  ...
);
```

**结论**：章节的标准必须 **JOIN `cert_report_template`** 才能拿到：

```sql
SELECT
  s.Code           AS SectionCode,
  s.SectionName,
  s.SectionNameEn,
  s.SectionContent,          -- ★ 模板里的示例正文
  s.SortOrder,
  s.ClauseCode,
  s.WorkflowCode,
  s.WorkflowConfig,          -- ★ DAG 在这里
  t.Code           AS TemplateCode,
  t.TemplateName,
  t.StandardCode   AS StandardCode,      -- ★ 从模板拿
  t.PhaseCode      AS TemplatePhaseCode
FROM rpt_report_section s
INNER JOIN cert_report_template t ON t.Code = s.ReportCode
WHERE t.OrgCode = @cbOrgCode            -- ★ 认证机构，不是专家工作区
  AND t.StandardCode IN (@standardCodes)
  AND t.PhaseCode  = @stageCode
  AND t.IsValid = 1
  AND t.IsDeleted = 0
  AND s.IsValid = 1                      -- ★ 本期新增（原为 IsActive）
  AND s.IsDeleted = 0
ORDER BY t.StandardCode, s.SortOrder;
```

> ⚠️ `rpt_report_section.ReportCode` 的 DDL 声明是 `FK → rpt_audit_report(Code)`，但代码（`ReportDefinitionController.cs:168,215`）实际存 `ReportTemplate.Code`。**这是存量语义错位**。本期不改表结构（改列名影响面大），但在 DDL 注释和本文档中明确标注「实际语义 = 模板 Code」，并在新增索引中体现。

#### 问题 2：章节的工作流 JSON 字段名与规则不同

| 对象 | DAG 所在列 |
|---|---|
| NC 规则 | `cert_validation_rule.RuleJson` |
| 报告章节 | `rpt_report_section.WorkflowConfig` |

> 编码时极易写错。统一封装：`LoadDag(TaskItem item)` 内部按 `ItemType` 分派。

#### 问题 3：`cert_report_template` 可能有多个（`IsDefault`）

一个 `(机构, 标准, 阶段)` 下可以有多个模板。范围解析时**只取 `IsDefault=1` 的那个**；若没有默认模板，取 `Sort` 最小的一个并记 warning。

```csharp
var template = templates.OrderByDescending(t => t.IsDefault)
                        .ThenBy(t => t.Sort)
                        .FirstOrDefault();
if (template == null) { /* 该标准无可用模板 → 该标准无章节可跑 */ }
if (template.IsDefault != 1)
    _logger.LogWarning("标准 {Std} 阶段 {Phase} 无默认报告模板，回落到 Sort 最小的 {Name}",
                       std, phase, template.TemplateName);
```

| `tsk_task_item` 字段 | 来源 | 说明 |

### 3.1 报告章节的 AI 输出契约

```json
{
  "content": "章节正文（纯文本，含换行）",
  "confidence": 0.0-1.0,
  "usedFields": [
    { "fieldCode": "...", "fieldName": "受审核方名称", "value": "XX有限公司" }
  ]
}
```

**归一化规则**：

| 情形 | 处理 |
|---|---|
| 正常返回 | `ContentText` = 归一化后的正文（去首尾空白、统一换行符为 `\n`） |
| `content` 为空字符串 | 视为**生成失败** → `AutoStatus='failed'`，`ReviewStatus='pending'`，专家手工写 |
| JSON 解析失败 | 同上，`AutoResult.rawOutput` 保留原文供专家参考 |
| `confidence < 0.5` | 正常落库，但界面黄色高亮提示"AI 生成置信度低，请重点复核" |

> **与 NC 侧的关键差异**：NC 侧解析失败是"结论未定"（阻塞）；报告侧解析失败是"正文空"（**不阻塞**，专家手写即可）。因为报告章节本质是**文本产出**，人工补写是天然合理的动作；NC 结论则涉及合规判定，必须更慎重。

### 3.2 正文的存储格式（D19）

| 决策 | 内容 |
|---|---|
| 存储 | **纯文本**（`longtext`），换行用 `\n` |
| 不用 | 富文本 HTML 标签、Markdown 标记 |
| 前端展示 | **HTML 渲染**（用户指定） |
| 渲染方式 | 转义后 `\n` → `<br>`，容器 `white-space: pre-wrap` |
| 导出 | Excel 单元格直接写原文，换行用 `\n`（Excel 自动换行） |

**安全要求（必须执行）**：

```vue
<!-- 正确：先转义，再把换行转 <br> -->
<div class="section-content" v-html="renderedContent"></div>
```

```ts
// composables/useSectionRender.ts
export function useSectionRender() {
  function render(raw: string | null | undefined): string {
    if (!raw) return ''
    return escapeHtml(raw).replace(/\r\n|\r|\n/g, '<br>')
  }
  return { render }
}

// escapeHtml 必须自己实现（不能用 v-text，因为要保留换行）
function escapeHtml(s: string): string {
  return s
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;')
}
```

> ⛔ **绝不能**把 AI 产出的正文直接 `v-html` 而不转义。AI 输出是不可信输入，直接渲染会导致存储型 XSS。虽然本期后端是内网系统，但这是必须写进代码规范的硬要求（`docs/10-YZH架构/08-常见错误与修复.md` 应补一条）。

### 3.3 专家编辑正文的交互

```
┌─ 章节：审核发现 ──────────────────── 标准：ISO9001 ──┐
│                                                     │
│  【AI 生成内容】                                    │
│  ┌─────────────────────────────────────────────┐    │
│  │ 审核过程中发现 2 项不符合，详见 NC 清单。      │    │
│  │                                              │    │
│  │ 1. 文件控制程序缺失版本标识                    │    │
│  │ 2. 记录保存期限未规定                        │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  【章节模板示例】（只读参考）                        │
│  ┌─────────────────────────────────────────────┐    │
│  │ 审核发现应包含：不符合项描述、涉及条款、证据。 │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  【专家编辑】                                        │
│  ┌─────────────────────────────────────────────┐    │
│  │ textarea（自动增高，Ctrl+Enter 保存）         │    │
│  │                                              │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │

└─────────────────────────────────────────────────────┘
```

| 按钮 | 行为 |
|---|---|
| **保存并认可** | `POST /api/ExpertTaskItem/{code}/modify`，`ContentText` = 编辑后内容 → `ReviewStatus='modified'`（D11 修改即认可） |
| **恢复为 AI 原文** | 把 `ContentText` 重置为 `AutoResult.content`，**仍记一次 MODIFY 日志**（因为这是一次有意的改动） |
| **查看修改历史** | 打开日志抽屉，显示该章节的 MODIFY 记录及逐次 diff |

> **「恢复为 AI 原文」也要记日志**：它改变了 `ContentText`，审计链不能有洞。

## 四、多标准分节（D14 第 2 条）

### 4.1 组织方式

任务下有 N 个标准子任务，每个子任务下是该标准的章节。**章节不跨标准合并**：

```
任务 TSK-20260929-0001（REPORT_GENERATE，企业 XX，阶段 S1，标准 3 个）
├── 标准子任务 A（ISO9001）  → 章节 1,2,3,4,5,6
├── 标准子任务 B（ISO14001） → 章节 1,2,3,4
└── 标准子任务 C（ISO45001） → 章节 1,2,3
```

**为什么不合并且同名章节**（比如三个标准都有"审核发现"）：认证报告要求"针对每个标准分别描述审核过程与发现"，合并会丢失标准的区分度，专家也无法对"这段是针对哪个标准写的"产生歧义。

### 4.2 工作台的分组展示

```vue
<!-- 08 号 §5 的核心结构 -->
<el-collapse v-model="activeSections">
  <el-collapse-item v-for="std in groupedByStandard" :name="std.code">
    <template #title>
      <StandardBadge :code="std.code" :name="std.name" />
      <span class="ml-2 text-sm text-gray-500">
        {{ std.ackedCount }}/{{ std.totalCount }} 已认可
      </span>
      <el-tag v-if="std.skippedCount > 0" type="info" size="small">
        {{ std.skippedCount }} 条跳过
      </el-tag>

  </el-collapse-item>

```

**章节项的展示元素**：

| 元素 | 内容 |
|---|---|
| 章节标题 | `SectionName`（+ `SectionNameEn` 小字） |
| 对应条款 | `ClauseNumber ClauseTitle`（可空则不显示） |
| 状态徽标 | 待认可（橙）/ 已认可（绿）/ 已修改（蓝）/ 数据不足（灰） |
| AI 正文区 | 折叠默认收起，点开可见 |
| 专家编辑区 | textarea |
| 置信度提示 | `confidence < 0.5` 时黄色提示条 |

## 五、跳过语义

与 NC 侧完全同构（02 号 §2.4），此处只列报告侧的差异：

| 场景 | 报告侧表现 |
|---|---|
| 缺数据跳过 | 该章节不生成正文，界面显示「数据不足，未生成内容」+ 缺什么 |
| 模板缺失 | 若某标准无 `cert_report_template`，该标准**不生成子任务**，任务创建时直接排除并在响应中告知 |
| 章节 `IsValid=0` | `MarkSkipped(rule_disabled)` |
| `WorkflowCode` 为空 | `MarkSkipped(no_rule)` —— 但报告章节**可以退化为"用模板示例正文"** |

> **最后一条的设计权衡**：章节的 `WorkflowConfig` 为空时，是否直接用 `SectionContent`（模板示例正文）作为初值？
>
> - **支持**（本设计采用）：报告章节有"模板示例"可作为起点，专家在此基础上改，比空白强得多。且能让系统在规则未配齐时也有可用的产出
> - 反对：模板示例可能是"标准写法示例"而非"本次实际内容"，直接用可能误导
>
> **折中落地**：`WorkflowCode` 为空时 → `AutoStatus='degraded'`（新增状态），`ContentText` = 模板示例正文，`AutoResult` 里标 `{ "degraded": true, "reason": "章节未配置生成工作流，以下内容为章节模板示例，请专家核实修改" }`，界面黄色提示「本章节未配置自动生成，内容来自模板示例」。`ReviewStatus='pending'` 强制专家过目。

> `degraded` 是**新增的第 6 种 `AutoStatus`**，取值域：`ok` / `ng` / `skipped` / `failed` / `degraded` / `none`。
> `degraded` 专用于报告章节，NC 侧不会产生（NC 侧缺 DAG 就是 `no_rule` 跳过）。

## 六、Excel 导出的报告部分（D09）

### 6.1 Sheet 划分

| Sheet 名 | 内容 |
|---|---|
| `{标准Code}` | 该标准下全部章节，按 `SortOrder` 纵向排列 |
| `汇总` | 跨标准统计 + 任务信息 + 章节清单索引 |

### 6.2 章节 Sheet 格式

两种排版，取决于专家偏好（提供导出选项，默认 A）：

**方案 A：纵向分段（默认）**

```
┌──────────────────────────────────────┐
│ 1  审核发现                            │  ← 章节标题行（加粗、灰底）
│    审核过程中发现 2 项不符合，…        │  ← 章节正文（自动换行）
│                                        │
│ 2  审核结论                            │
│    依据 ISO 9001:2015，…              │
│                                        │
│ 3  认证建议                            │
│    建议通过认证，附条件关闭 2 项 NC。   │
└──────────────────────────────────────┘
```

**方案 B：表格化**

| 列 | 内容 |
|---|---|
| 章节号 | `SortOrder` |
| 章节标题 | `SectionName` |
| 对应条款 | `ClauseNumber` |
| 正文 | `ContentText`（自动换行，行高自适应） |
| 状态 | 待认可/已认可/已修改/数据不足 |

### 6.3 汇总 Sheet

| 区块 | 内容 |
|---|---|
| 任务信息 | 任务编号、企业名称、阶段、标准列表、创建时间、批准人、批准时间 |
| 章节统计 | 总章节数 / 已认可 / 已修改 / 数据不足未生成 |
| 标准清单 | 每个标准一行：标准名 / 章节数 / 已认可 / 未认可 / 数据不足 |
| 章节索引 | 全部章节的清单（标准、章节号、标题、对应条款、状态） |

### 6.4 导出水印

| 字段 | 值 |
|---|---|
| 生成时间 | 导出时刻 |
| 任务编号 | `TaskNumber` |
| 任务状态 | `draft`（草稿）/ `approved`（定稿） |
| 批准人 / 批准时间 | 仅 `approved` 态有值 |
| 专家 | 各章节的 `ReviewByName`（在明细行里） |

> **草稿导出允许但必须标水印**：专家可能需要中途给领导看。Excel 里第一行加 `【草稿·未经批准】` 红色大字，防止草稿被当成定论使用。

### 6.5 NPOI 实现要点

```csharp
// 一个标准一个 Sheet
foreach (var std in task.StandardCodes)
{
    var sheet = wb.CreateSheet(std);            // Sheet 名 = 标准 Code，长度 ≤ 31
    var items = itemsByStandard[std];
    int rowIdx = 0;

    if (task.TaskStatus != "approved")
    {
        // 草稿水印（合并单元格 + 红色大字）
        var wmRow = sheet.CreateRow(0);
        var wmCell = wmRow.CreateCell(0);
        wmCell.SetCellValue("【草稿·未经批准】");
        wmCell.CellStyle = draftWatermarkStyle;
        sheet.AddMergedRegion(new CellRangeAddress(0, 0, 0, 8));
        rowIdx = 2;
    }

    foreach (var item in items)
    {
        if (item.AutoStatus == "skipped")
        {
            // ★ 数据不足：计入总章节数，但不输出正文
            var r = sheet.CreateRow(rowIdx++);
            r.CreateCell(0).SetCellValue($"{item.Sort}. {item.ItemName}");
            r.CreateCell(2).SetCellValue($"【数据不足，未生成内容】{item.SkipReason}");
            continue;
        }

        var titleRow = sheet.CreateRow(rowIdx++);
        var tc = titleRow.CreateCell(0);
        tc.SetCellValue($"{item.Sort}. {item.ItemName}");
        tc.CellStyle = sectionTitleStyle;

        var bodyRow = sheet.CreateRow(rowIdx++);
        var bc = bodyRow.CreateCell(0);
        bc.SetCellValue(item.ContentText);
        bc.CellStyle = bodyStyle;                 // WrapText = true, Vertical = Top
        sheet.AddMergedRegion(new CellRangeAddress(rowIdx - 1, rowIdx - 1, 0, 8));
        rowIdx++;                                 // 空行分隔
    }

    sheet.SetColumnWidth(0, 60 * 256);            // 单位 1/256 字符宽
}
```

**关键点**：
| 点 | 要求 |
|---|---|
| Sheet 名长度 | Excel 限制 31 字符，`StandardCode` 是 GUID 需处理（建议用 `StandardCode` 前 8 位或标准简称） |
| 换行 | `CellStyle.WrapText = true` + `VerticalAlignment = Top`；行高需 `sheet.Row(rowIdx).Height = -1`（自适应） |
| 长文本 | Excel 单元格上限 32767 字符。超长章节正文需截断并加提示 |
| 中文 | NPOI 需 `workbook.Setting.SetShrinkToFit` / 字体设为 `宋体` 或 `微软雅黑` |
| 内存 | 用 `NPOI.XSSF` 流式写（`XSSFWorkbook(Stream)`），避免大报告 OOM |

## 七、与 NC 检查侧的差异总表

| 维度 | NC 检查 | 报告生成 |
|---|---|---|
| `ItemType` | `nc_check` | `report_section` |
| 元数据源表 | `cert_validation_rule` | `rpt_report_section` + JOIN `cert_report_template` |
| DAG 字段 | `RuleJson` | `WorkflowConfig` |
| `StandardCode` 来源 | 规则表自带 | ⚠️ 必须 JOIN 模板取 |
| `ClauseCode` | 必填（NOT NULL） | 可空（概述/结论章节不映射） |
| 规则编号 | `RuleCode`（`NC-xxx-001`） | 无（用 `SortOrder`） |
| `Conformity` | ✅ 有值 | `null` |
| `Severity` | ✅ 有值 | `null` |
| `ContentText` | 说明文字（可空） | ★ 章节正文（核心产物） |
| AI 节点类型 | `aiJudge`（判定） | `aiGenerate`（生成） |
| 输出解析失败 | 阻塞（`ReviewStatus=pending`） | 不阻塞（专家可手写） |
| 缺 DAG | `MarkSkipped(no_rule)` | `degraded` + 用模板示例 |
| 额外产出 | `audit_nonconformity` 记录 | 无 |
| Excel 行结构 | 每项一行（表格） | 每章节一段（分段或表格） |
| Sheet 划分 | 一个标准一个 Sheet | 一个标准一个 Sheet（相同） |
