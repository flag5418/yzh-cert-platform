## 一、关键决策回顾（D14）

用户裁决原文：

> 「只有导出才是excel，否则执行完成应该是**按每个标准，每个章节的列表**，和 nc 检查项一样，用户可以审批是否接受，也可以修改报告内容」

由此确定 4 条设计原则：

| # | 原则 | 影响 |
|---|---|---|
| 1 | **不生成 docx、不落 `rpt_audit_report`** | 报告的产物是**章节列表**（`cert_expert_report_result`，`ItemType='report_section'`），不是报告文件 |
| 2 | **章节不合并，按标准分节** | 同一阶段关联 3 个标准 → 3 套独立章节，各自成区 |
| 3 | **专家逐章节认可/修改** | 与 NC 检查项完全一致的交互 |
| 4 | **导出才出 Excel，一个标准一个 Sheet** | 每个标准一个 Sheet，章节按 `SortOrder` 纵向排列 |

> **与 NC 检查的结构对称性**：见 [01 号 §2.2](01-总体设计-V1.md)。本章只讲差异，相同部分（认可、修改、日志、跳过、队列）不重复。

## 二、报告章节的元数据解析

### 2.1 ★★ 章节配置层的结构（2026-09-29 D34 修正：删除报告主表）

> **本节已整体重写。** 原设计是「`cert_report_template`（主表）+ `cert_report_section`（章节）」两层，**现已删除主表**，章节直接承载归属维度。

#### 2.1.1 为什么删掉主表

用户裁决：

> 「针对报告的内容定义，首先定义了一个报告的主表，定义了报告的空模板，然后针对报告才设计了章节。**我现在不想做报表系统了，报告的主表我也不需要了**」

**与 NC 规则的对齐**（删掉后完全对称）：

```
删前：  cert_validation_rule        cert_report_template + cert_report_section
        (规则，自带 OrgCode/         (模板) + (章节，★标准/阶段要 JOIN 模板取)
         StandardCode/PhaseCode)                 ↑ ★多一层容器

删后：  cert_validation_rule        cert_report_section
        (规则)                      (章节，自带 OrgCode/StandardCode/PhaseCode)
        ────────────── 完全对称 ──────────────
```

#### 2.1.2 顺带解决的 3 个现存问题

| 问题 | 删前 | 删后 |
|---|---|---|
| 章节表无 `StandardCode` | 每次查章节都要 JOIN 模板（原 §2.1 问题 1） | **直接读** |
| `ReportCode` 语义错位 | DDL 声明 FK→`rpt_audit_report`，实际存 `Template.Code`（阻塞项 B3） | **列直接删除**，错位消失 |
| 启用标志不一致 | 模板 `IsValid` / 章节 `IsActive` | **统一 `IsValid`**（与 E1-3 合并） |

#### 2.1.3 章节的归属维度（D34）

**章节定义 = 全局配置**（认证机构 + 标准 + 阶段），**所有企业共享一套**。

```
配置层（全局）              实体层（企业级）           结果层（企业级 · 多轮）
cert_report_section    →    biz_report_section    →   biz_report_result
  OrgCode=认证机构           EnterpriseCode           RoundNo / ContentText
  StandardCode              StandardCode             ReviewStatus
  PhaseCode                 StageCode
  SectionName  ← 空白模板      SectionName
  SectionContent ← 示例正文
  WorkflowCode ← 生成规则
```

| 层 | 谁维护 | 粒度 | 例子 |
|---|---|---|---|
| **配置层** `cert_report_section` | 管理员 / 实施人员 | (认证机构, 标准, 阶段) | ISO9001 第二阶段的"审核准则"章节怎么写 |
| **实体层** `biz_report_section` | 系统自动派生 | (企业, 阶段, 标准) | XX公司第二轮的"审核准则"章节这个对象 |
| **结果层** `biz_report_result` | 专家（认可/修改） | (实体, 轮次) | 该章节第 3 轮的实际内容 |

> **为什么是"全局配置"**：按 §5.1 的沿用率分析 ——「审核准则」在 3 年 6 次事件中**内容完全不变**。这说明它是**标准的空白模板**，不是企业数据。企业数据在 `biz_report_result`。
>
> ⛔ **不是"企业级章节"**：若章节定义是企业级的，章节表要加 `EnterpriseCode`，多企业后章节数暴涨，且与 NC 规则（全企业共用的配置）完全不对称。

#### 2.1.4 章节查询（删掉 JOIN）

```sql
SELECT
  s.Code           AS SectionCode,
  s.SectionName,
  s.SectionNameEn,
  s.SectionContent,          -- ★ 模板示例正文
  s.SortOrder,
  s.ClauseCode,
  s.WorkflowCode,
  s.WorkflowConfig,          -- ★ DAG 在这里（规则的 DAG 在 RuleJson，字段名不同）
  s.ClauseCode,              -- 可空（概述/结论章节不映射条款）
  cs.ClauseNumber,           -- ★ 现在只需 LEFT JOIN 条款表（为了显示条款号）
  cs.ClauseTitle
FROM cert_report_section s
LEFT JOIN cert_iso_clause cs ON cs.Code = s.ClauseCode
WHERE s.OrgCode      = @certBodyCode       -- ★ 认证机构 CbCode（不是专家工作区）
  AND s.StandardCode IN (@standardCodes)
  AND s.PhaseCode    = @stageCode
  AND s.IsValid      = 1
  AND s.IsDeleted    = 0
ORDER BY s.StandardCode, s.SortOrder;
```

> ⚠️ **`OrgCode` 语义**：配置层的 `OrgCode` = **认证机构 Code**（`cert_certification_body.Code`），因为规则/章节是企业无关的全局配置，归认证机构所有。
> ⛔ **与 `cert_expert_task.OrgCode`（专家工作区）不同** —— 见 [02 号 §9 口径对照表](02-详细设计-任务与队列-V1.md)。

### 2.1.5 ★ 章节 → 任务项的字段映射

| `biz_report_section` 字段 | 来源 | 说明 |
|---|---|---|
| `Code` | 系统生成 | 实体业务键 |
| `EnterpriseCode` | 任务上下文 | 企业 |
| `StageCode` / `StandardCode` | 章节配置 | |
| `SectionCode` | `cert_report_section.Code` | ★ 指向配置层 |
| `SectionName` / `SectionNameEn` | 章节配置 | 快照 |
| `SectionTemplateContent` | `cert_report_section.SectionContent` | ★ 模板示例正文快照（只读参考） |
| `ClauseCode` / `ClauseNumber` | 章节配置 | 可空 |
| `WorkflowCode` | 章节配置 | |

> `SectionTemplateContent` 是**冗余快照**：把配置层的示例正文快照到实体上，专家编辑时能对照"标准写法"与"本次实际写法"。配置层后续改动不影响历史任务显示。

### 2.1.6 失去的能力（已确认可接受）

| 失去 | 原因 |
|---|---|
| 一套阶段多套模板（`IsDefault` 选默认） | D14 已定"只导 Excel 不做 docx"，模板的唯一价值就是 docx 载体 |
| docx 模板文件（`TemplateFilePath`） | 同上，字段本身失去意义 |
| 章节顺序的整体编排（`SectionConfig` json） | 章节有 `SortOrder`，够用 |
| 模板级启停 | 替代方案：按 `(OrgCode, StandardCode, PhaseCode)` 批量改 `IsValid` |

## 三、执行链路

> ⚠️ **章节的 DAG 字段名与 NC 规则不同**（极易写错）：规则的 DAG 在 `cert_validation_rule.RuleJson`，章节的 DAG 在 `cert_report_section.WorkflowConfig`。
> 统一封装：`LoadDag(itemType, configJson)` 内部按 `ItemType` 分派。

```
cert_expert_task_queue_item.Payload
  {
    "TaskItemCode": "...",
    "ItemType": "report_section",
    "EntityCode": "<biz_report_section.Code>",   ← ★ 企业级实体（12 号拆分后的实体层）
    "SectionCode": "<cert_report_section.Code>",  ← 配置层章节
    "WorkflowCode": "...",                        ← 从章节配置快照而来
    "EnterpriseCode": "...", "StandardCode": "...", "StageCode": "...",
    "ExtractVersionStamp": "..."
  }
        │
        ▼
① 读取章节配置快照（防中途改动；★ 删掉主表后无需 JOIN）
   SELECT Code, SectionName, SectionNameEn, SectionContent, SortOrder,
          ClauseCode, WorkflowCode, WorkflowConfig, StandardCode, PhaseCode
   FROM cert_report_section
   WHERE Code = @sectionCode AND IsValid = 1 AND IsDeleted = 0
        │
        ▼
② 缺数据预检（同 02 号 §2.4，完全同一套逻辑）
   有未解决 gap → MarkSkipped(data_gap / data_gap_skipped)
        │
        ▼
③ 判定 WorkflowCode 为空
   → ★ AutoStatus='degraded'（不是 no_rule 跳过）
     ContentText = SectionContent（模板示例）
     见 §5 降级语义
        │
        ▼
④ 跑 WorkflowInterpreter（★ TaskType='REPORT_GENERATE'）
   ★ 关键差异：NC 是「判定」，报告是「生成文本」
     → 两者在 NodeExecutor 里是【同一个 ai_node 节点类型】
     → 靠节点配置 + Prompt 内容区分判定 / 生成（见 10 号 C3）
        │
        ▼
⑤ 提取结果版本戳比对（同 03 号 §2.3）
        │
        ▼
⑥ 归一化：AI 输出的长文本 → ContentText
```

### 3.1 报告章节的 AI 输出契约

```json
{
  "content": "章节正文（纯文本，含换行）",
  "confidence": 0.0-1.0,
  "usedFields": [
    { "fieldCode": "...", "fieldName": "受审核方名称", "value": "XX有限公司" }
  ]
}
```

**归一化规则**：

| 情形 | 处理 |
|---|---|
| 正常返回 | `ContentText` = 归一化后的正文（去首尾空白、统一换行符为 `\n`） |
| `content` 为空字符串 | 视为**生成失败** → `AutoStatus='failed'`，`ReviewStatus='pending_review'`，专家手工写 |
| JSON 解析失败 | 同上，`AutoResult.rawOutput` 保留原文供专家参考 |
| `confidence < 0.5` | 正常落库，但界面黄色高亮提示"AI 生成置信度低，请重点复核" |

> **与 NC 侧的关键差异**：NC 侧解析失败是"结论未定"（阻塞）；报告侧解析失败是"正文空"（**不阻塞**，专家手写即可）。因为报告章节本质是**文本产出**，人工补写是天然合理的动作；NC 结论则涉及合规判定，必须更慎重。

### 3.2 正文的存储格式（D19）

| 决策 | 内容 |
|---|---|
| 存储 | **纯文本**（`longtext`），换行用 `\n` |
| 不用 | 富文本 HTML 标签、Markdown 标记 |
| 前端展示 | **HTML 渲染**（用户指定） |
| 渲染方式 | 转义后 `\n` → `<br>`，容器 `white-space: pre-wrap` |
| 导出 | Excel 单元格直接写原文，换行用 `\n`（Excel 自动换行） |

**安全要求（必须执行）**：

```vue
<!-- 正确：先转义，再把换行转 <br> -->
<div class="section-content" v-html="renderedContent"></div>
```

```ts
// composables/useSectionRender.ts
export function useSectionRender() {
  function render(raw: string | null | undefined): string {
    if (!raw) return ''
    return escapeHtml(raw).replace(/\r\n|\r|\n/g, '<br>')
  }
  return { render }
}

// escapeHtml 必须自己实现（不能用 v-text，因为要保留换行）
function escapeHtml(s: string): string {
  return s
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;')
}
```

> ⛔ **绝不能**把 AI 产出的正文直接 `v-html` 而不转义。AI 输出是不可信输入，直接渲染会导致存储型 XSS。虽然本期后端是内网系统，但这是必须写进代码规范的硬要求（`docs/10-YZH架构/08-常见错误与修复.md` 应补一条）。

### 3.3 专家编辑正文的交互

```
┌─ 章节：审核发现 ──────────────────── 标准：ISO9001 ──┐
│                                                     │
│  【AI 生成内容】                                    │
│  ┌─────────────────────────────────────────────┐    │
│  │ 审核过程中发现 2 项不符合，详见 NC 清单。      │    │
│  │                                              │    │
│  │ 1. 文件控制程序缺失版本标识                    │    │
│  │ 2. 记录保存期限未规定                        │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  【章节模板示例】（只读参考）                        │
│  ┌─────────────────────────────────────────────┐    │
│  │ 审核发现应包含：不符合项描述、涉及条款、证据。 │    │
│  └─────────────────────────────────────────────┘    │
│                                                     │
│  【专家编辑】                                        │
│  ┌─────────────────────────────────────────────┐    │
│  │ textarea（自动增高，Ctrl+Enter 保存）         │    │
│  │                                              │    │
│  └─────────────────────────────────────────────┘    │
```

| 按钮 | 行为 |
|---|---|
| **保存并认可** | `POST /api/ExpertTaskItem/{code}/modify`，`ContentText` = 编辑后内容 → `ReviewStatus='modified'`（D11 修改即认可） |

> **「恢复为 AI 原文」也要记日志**：它改变了 `ContentText`，审计链不能有洞。

## 四、多标准分节（D14 第 2 条）

### 4.1 组织方式

任务下有 N 个标准子任务，每个子任务下是该标准的章节。**章节不跨标准合并**：

```
任务 TSK-20260929-0001（REPORT_GENERATE，企业 XX，阶段 S1，标准 3 个）
├── 标准子任务 A（ISO9001）  → 章节 1,2,3,4,5,6
├── 标准子任务 B（ISO14001） → 章节 1,2,3,4
└── 标准子任务 C（ISO45001） → 章节 1,2,3
```

**为什么不合并且同名章节**（比如三个标准都有"审核发现"）：认证报告要求"针对每个标准分别描述审核过程与发现"，合并会丢失标准的区分度，专家也无法对"这段是针对哪个标准写的"产生歧义。

### 4.2 工作台的分组展示

```vue
<!-- 08 号 §5 的核心结构 -->
<el-collapse v-model="activeSections">
  <el-collapse-item v-for="std in groupedByStandard" :name="std.code">
    <template #title>
      <StandardBadge :code="std.code" :name="std.name" />
      <span class="ml-2 text-sm text-gray-500">
        {{ std.ackedCount }}/{{ std.totalCount }} 已认可
      </span>
      <el-tag v-if="std.skippedCount > 0" type="info" size="small">
        {{ std.skippedCount }} 条跳过
      </el-tag>
    </template>

    <SectionItemList :items="std.items" />
  </el-collapse-item>

```

**章节项的展示元素**：

| 元素 | 内容 |
|---|---|
| 章节标题 | `SectionName`（+ `SectionNameEn` 小字） |
| 对应条款 | `ClauseNumber ClauseTitle`（可空则不显示） |
| 状态徽标 | 待认可（橙）/ 已认可（绿）/ 已修改（蓝）/ 数据不足（灰） |
| AI 正文区 | 折叠默认收起，点开可见 |
| 专家编辑区 | textarea |
| 置信度提示 | `confidence < 0.5` 时黄色提示条 |

## 五、跳过语义

与 NC 侧完全同构（02 号 §2.4），此处只列报告侧的差异：

| 场景 | 报告侧表现 |
|---|---|
| 缺数据跳过 | 该章节不生成正文，界面显示「数据不足，未生成内容」+ 缺什么 |
| 章节配置缺失 | 若某标准该阶段**一条章节配置都没有**，该标准**不生成子任务**，任务创建时直接排除并在响应中告知（`NO_SECTION_CONFIG`） |
| 章节 `IsValid=0` | `MarkSkipped(rule_disabled)` |
| `WorkflowCode` 为空 | `MarkSkipped(no_rule)` —— 但报告章节**可以退化为"用模板示例正文"** |

> **最后一条的设计权衡**：章节的 `WorkflowConfig` 为空时，是否直接用 `SectionContent`（模板示例正文）作为初值？
>
> - **支持**（本设计采用）：报告章节有"模板示例"可作为起点，专家在此基础上改，比空白强得多。且能让系统在规则未配齐时也有可用的产出
> - 反对：模板示例可能是"标准写法示例"而非"本次实际内容"，直接用可能误导
>
> **折中落地**：`WorkflowCode` 为空时 → `AutoStatus='degraded'`（新增状态），`ContentText` = 模板示例正文，`AutoResult` 里标 `{ "degraded": true, "reason": "章节未配置生成工作流，以下内容为章节模板示例，请专家核实修改" }`，界面黄色提示「本章节未配置自动生成，内容来自模板示例」。`ReviewStatus='pending_review'` 强制专家过目。

> `degraded` 是**新增的第 6 种 `AutoStatus`**，取值域：`ok` / `ng` / `skipped` / `failed` / `degraded` / `none`。
> `degraded` 专用于报告章节，NC 侧不会产生（NC 侧缺 DAG 就是 `no_rule` 跳过）。

### 5.1 ★ 为什么 `degraded` 是「结果级」而非「任务级」（2026-09-29 评审 R3 澄清）

评审建议「补充 `TaskSource=degraded` 或独立降级队列路径」。**本设计不采纳，理由如下**：

| 维度 | 降级是**结果级**（本设计） | 降级是**任务级**（评审建议） |
|---|---|---|
| 触发条件 | **个别**章节的 `WorkflowCode` 为空 | 整份报告的模板/规则都没配 |
| 实际发生频率 | ★ **常见**（章节 6 个，配了 5 个很平常） | 罕见（模板都没配，任务根本不该建） |
| 粒度 | `cert_expert_nc_result.AutoStatus`（单章节） | `cert_expert_task.TaskSource`（整任务） |
| 队列 | 正常队列，该章节走简化分支 | 需要独立的降级队列 |
| 结果 | 5 个正常生成 + 1 个模板示例，专家过目 | 全部用模板示例 |

**关键判断**：报告模板有 6-8 个章节，实施人员漏配某一个的 `WorkflowCode` 是**常态**。若因此要降级整个任务，工作台会频繁进入"非正常路径"，代码分支翻倍。

```
 报告任务（正常执行）
   ├─ 章节1 审核概述   WorkflowCode 有 → ai_node 生成     AutoStatus=ok
   ├─ 章节2 审核准则   WorkflowCode 有 → ai_node 生成     AutoStatus=ok
   ├─ 章节3 审核发现   WorkflowCode 有 → ai_node 生成     AutoStatus=ok
   ├─ 章节4 审核结论   WorkflowCode 有 → ai_node 生成     AutoStatus=ok
   ├─ 章节5 认证建议   WorkflowCode 有 → ai_node 生成     AutoStatus=ok
   └─ 章节6 附件清单   ★ WorkflowCode 空 → 用模板示例    AutoStatus=degraded
                                                    ↑ 单章节降级，任务照常完成
```

⛔ **不引入 `TaskSource=degraded`、不引入独立降级队列**。若报告模板整体未配置，`TaskSource=NEW` 时范围解析阶段就会排除该标准（12 号 §2.1 已述），根本不会建出空任务。

### 5.2 降级章节的完整处理链

| 环节 | 行为 |
|---|---|
| 完备性检查 | ⛔ **跳过**降级章节（它不依赖提取数据，不产生 gap） |
| 队列执行 | 走 `degraded` 分支：不做 LLM 调用，`ContentText` = `SectionTemplateContent` |
| `AutoResult` | `{ "degraded": true, "reason": "章节未配置生成工作流，以下内容为章节模板示例，请专家核实修改" }` |
| `ReviewStatus` | `pending_review`（强制专家过目；⛔ **无批准动作**，归档时才校验是否全部处理完） |
| 界面 | 黄色 Alert「本章节未配置自动生成，内容来自模板示例，请专家核实修改」 |
| 导出 | 与普通章节同等对待导出，**不加特殊标记**（专家已确认过） |

## 六、Excel 导出的报告部分（D09）

### 6.1 Sheet 划分

| Sheet 名 | 内容 |
|---|---|
| `{标准Code}` | 该标准下全部章节，按 `SortOrder` 纵向排列 |
| `汇总` | 跨标准统计 + 任务信息 + 章节清单索引 |

### 6.2 章节 Sheet 格式

两种排版，取决于专家偏好（提供导出选项，默认 A）：

**方案 A：纵向分段（默认）**

```
┌──────────────────────────────────────┐
│ 1  审核发现                            │  ← 章节标题行（加粗、灰底）
│    审核过程中发现 2 项不符合，…        │  ← 章节正文（自动换行）
│                                        │
│ 2  审核结论                            │
│    依据 ISO 9001:2015，…              │
│                                        │
│ 3  认证建议                            │
│    建议通过认证，附条件关闭 2 项 NC。   │
└──────────────────────────────────────┘
```

**方案 B：表格化**

| 列 | 内容 |
|---|---|
| 章节号 | `SortOrder` |
| 章节标题 | `SectionName` |
| 对应条款 | `ClauseNumber` |
| 正文 | `ContentText`（自动换行，行高自适应） |
| 状态 | 待认可/已认可/已修改/数据不足 |

### 6.3 汇总 Sheet

| 区块 | 内容 |
|---|---|
| 任务信息 | 任务编号、企业名称、阶段、标准列表、创建时间、批准人、批准时间 |
| 章节统计 | 总章节数 / 已认可 / 已修改 / 数据不足未生成 |
| 标准清单 | 每个标准一行：标准名 / 章节数 / 已认可 / 未认可 / 数据不足 |
| 章节索引 | 全部章节的清单（标准、章节号、标题、对应条款、状态） |

### 6.4 导出水印

| 字段 | 值 |
|---|---|
| 生成时间 | 导出时刻 |
| 任务编号 | `TaskNumber` |
| 任务状态 | `draft`（草稿）/ `approved`（定稿） |
| 批准人 / 批准时间 | 仅 `approved` 态有值 |
| 专家 | 各章节的 `ReviewByName`（在明细行里） |

> **草稿导出允许但必须标水印**：专家可能需要中途给领导看。Excel 里第一行加 `【草稿·未经批准】` 红色大字，防止草稿被当成定论使用。

### 6.5 NPOI 实现要点

```csharp
// 一个标准一个 Sheet
foreach (var std in task.StandardCodes)
{
    var sheet = wb.CreateSheet(std);            // Sheet 名 = 标准 Code，长度 ≤ 31
    var items = itemsByStandard[std];
    int rowIdx = 0;

    if (task.TaskStatus != "approved")
    {
        // 草稿水印（合并单元格 + 红色大字）
        var wmRow = sheet.CreateRow(0);
        var wmCell = wmRow.CreateCell(0);
        wmCell.SetCellValue("【草稿·未经批准】");
        wmCell.CellStyle = draftWatermarkStyle;
        sheet.AddMergedRegion(new CellRangeAddress(0, 0, 0, 8));
        rowIdx = 2;
    }

    foreach (var item in items)
    {
        if (item.AutoStatus == "skipped")
        {
            // ★ 数据不足：计入总章节数，但不输出正文
            var r = sheet.CreateRow(rowIdx++);
            r.CreateCell(0).SetCellValue($"{item.Sort}. {item.ItemName}");
            r.CreateCell(2).SetCellValue($"【数据不足，未生成内容】{item.SkipReason}");
            continue;
        }

        var titleRow = sheet.CreateRow(rowIdx++);
        var tc = titleRow.CreateCell(0);
        tc.SetCellValue($"{item.Sort}. {item.ItemName}");
        tc.CellStyle = sectionTitleStyle;

        var bodyRow = sheet.CreateRow(rowIdx++);
        var bc = bodyRow.CreateCell(0);
        bc.SetCellValue(item.ContentText);
        bc.CellStyle = bodyStyle;                 // WrapText = true, Vertical = Top
        sheet.AddMergedRegion(new CellRangeAddress(rowIdx - 1, rowIdx - 1, 0, 8));
        rowIdx++;                                 // 空行分隔
    }

    sheet.SetColumnWidth(0, 60 * 256);            // 单位 1/256 字符宽
}
```

**关键点**：
| 点 | 要求 |
|---|---|
| Sheet 名长度 | Excel 限制 31 字符，`StandardCode` 是 GUID 需处理（建议用 `StandardCode` 前 8 位或标准简称） |
| 换行 | `CellStyle.WrapText = true` + `VerticalAlignment = Top`；行高需 `sheet.Row(rowIdx).Height = -1`（自适应） |
| 长文本 | Excel 单元格上限 32767 字符。超长章节正文需截断并加提示 |
| 中文 | NPOI 需 `workbook.Setting.SetShrinkToFit` / 字体设为 `宋体` 或 `微软雅黑` |
| 内存 | 用 `NPOI.XSSF` 流式写（`XSSFWorkbook(Stream)`），避免大报告 OOM |

## 七、与 NC 检查侧的差异总表

| 维度 | NC 检查 | 报告生成 |
|---|---|---|
| `ItemType` | `nc_check` | `report_section` |
| 元数据源表 | `cert_validation_rule` | ★ `cert_report_section`（D34 后自带标准/阶段，无需 JOIN） |
| DAG 字段 | `RuleJson` | `WorkflowConfig` |
| `StandardCode` 来源 | 规则表自带 | ⚠️ 必须 JOIN 模板取 |
| `ClauseCode` | 必填（NOT NULL） | 可空（概述/结论章节不映射） |
| 规则编号 | `RuleCode`（`NC-xxx-001`） | 无（用 `SortOrder`） |
| `Conformity` | ✅ 有值 | `null` |
| `Severity` | ✅ 有值 | `null` |
| `ContentText` | 说明文字（可空） | ★ 章节正文（核心产物） |
| AI 节点类型 | `ai_node`（判定） | `ai_node`（生成） |
| 输出解析失败 | 阻塞（`ReviewStatus=pending`） | 不阻塞（专家可手写） |
| 缺 DAG | `MarkSkipped(no_rule)` | `degraded` + 用模板示例 |
| 额外产出 | `cert_nc` 记录 | 无 |
| Excel 行结构 | 每项一行（表格） | 每章节一段（分段或表格） |
| Sheet 划分 | 一个标准一个 Sheet | 一个标准一个 Sheet（相同） |
