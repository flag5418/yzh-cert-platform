## 零、强制铁律（DDL 写之前必读）

| 铁律 | 要求 |
|---|---|
| **七 · 列名三处一致** | DB 列名 = C# 属性名 = TS 字段名，**PascalCase 逐字一致** |
| **八 · 字符集** | 建表**必须显式** `COLLATE=utf8mb4_general_ci`；⛔ 只写 `DEFAULT CHARSET=utf8mb4`（不带 COLLATE）会落到 `utf8mb4_0900_ai_ci`，不是库默认值 |
| **九 · Enable 零容忍** | 启用/禁用唯一字段 = `IsValid`（int，0/1）。⛔ 数据库中不允许任何表存在 `Enable`/`enable` 列 |
| **九 · 验证 SQL** | 用 `CONVERT(COLUMN_NAME USING utf8mb4) COLLATE utf8mb4_bin` 做大小写检查，否则 `NOT REGEXP '^[A-Z]'` **永远返回 0 行**（假阴性） |
| **准则 A · Id/Code** | `Id` **永不**进 WHERE / 关联 / `Id>0` 分流。定位删除更新传参**只用 `Code`** |
| **十 · SQL 外置** | 脚本放 `scripts/db/`，`.sh` 只做编排，不内嵌 SQL |

**每张表的固定列**（与项目现有表一致）：


### ★ 为什么 8 张新表的 `OrgCode` 都是 `NOT NULL`（2026-09-29 评审 R2 修正）

**评审指出**：`cert_expert_task_queue.OrgCode` 写成了 `DEFAULT NULL`，租户隔离键不应可空。**核查后发现 8 张表全都有这个问题，已批量修正。**

**为什么 `NOT NULL` 是必须的**（SQL 三值逻辑陷阱）：

```sql
-- 若 OrgCode 可为 NULL：
SELECT * FROM cert_expert_task_queue WHERE OrgCode = 'WS001';
--  ⛔ OrgCode IS NULL 的行【查不出来】！
--     原因：NULL = 'WS001' 的结果是 NULL（不是 true），WHERE 只保留 true

-- 后果：这批"没有租户归属"的行对任何工作区都不可见 → 成为隐形数据
--      专家会困惑："我建的队列呢？"
--      排查成本极高，因为 WHERE 有条件、SQL 不报错

-- 若 OrgCode NOT NULL：
--  ⛔ 问题在建表/插入时就暴露（列约束 / 应用层强制赋值）
--  ✅ 每行都必然属于某个租户，WHERE OrgCode = @OrgCode 永远完整
```

**配套要求**：

| 要求 | 说明 |
|---|---|
| 应用层强制赋值 | 所有 Repository 的 `Insert` 必须从 `WorkspaceContextService.Resolve().OrgCode` 取，⛔ 禁止从 DTO 传入 |
| 唯一键/索引首列 | 所有涉及租户隔离的索引，`OrgCode` 必须在**前导位**（如 `idx_org_list (OrgCode, QueueStatus, CreateTime)`） |
| 验证 SQL | 见 §7.1 ⑥ |

> ⚠️ **注意**：本项目**存量表**的 `OrgCode` 大多是 `DEFAULT NULL`（沿用历史约定）。新表从严，存量表不动（改动面大且无必要 —— 存量表 `OrgCode` 实际都有值）。

### ★ `IsValid` 的存在性（2026-09-29 评审 R1 澄清）

评审报告称 `cert_expert_task` 缺 `IsValid`。**核查：8 张新表全部已有 `IsValid int NOT NULL DEFAULT 1`**（固定列模板，见上）。此处补充说明其用途，避免再次误读：

| 场景 | 用哪个标志 |
|---|---|
| 软删除（行不再使用，但保留） | `IsDeleted tinyint` |
| **有效/无效（行仍存在，但业务上不生效）** | **`IsValid int`** ← 铁律九指定 |
| 归档 / 作废 / 取消（12 号 D27 存续状态） | ⚠️ **用 `LifecycleStatus` 列**，⛔ 不是 `IsValid` |

> **三者的区别**（易混淆）：
> - `IsValid=0` = "这条数据无效"（配置层面的失效，如规则被停用）
> - `IsDeleted=1` = "这条数据删了"（软删）
> - `LifecycleStatus='archived'/'voided'/'cancelled'` = "这次执行结束了/作废了"（12 号 D27 存续状态，**不影响 `IsValid`**）
>
> 三者正交，不可互相替代。

## 二、新建表 DDL

### 2.1 `cert_expert_task` — 任务头

```sql
-- ============================================================
-- Table: cert_expert_task（专家任务头）
-- 说明：NC 检查 与 报告生成 共用一张表，用 TaskType 区分（D01）
--       用 ScopeType 区分全局/局部（D01）
--       1 个任务按标准自动拆 N 个子任务（D02）
-- ============================================================
USE `yzh_cert_platform`;
SET NAMES utf8mb4 COLLATE utf8mb4_general_ci;

CREATE TABLE `cert_expert_task` (
  `Id`               bigint      NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `Code`             varchar(36) COLLATE utf8mb4_general_ci NOT NULL COMMENT '全局唯一编码（GUID，业务键）',
  `OrgCode`          varchar(50) COLLATE utf8mb4_general_ci NOT NULL COMMENT '★专家工作区编码（租户隔离键，★非认证机构，★禁止为 NULL）',
  `CreateBy`         varchar(50) COLLATE utf8mb4_general_ci DEFAULT NULL,
  `CreateName`       varchar(100) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '创建人姓名（冗余，防改名后追溯断裂）',
  `CreateTime`       datetime     DEFAULT CURRENT_TIMESTAMP,
  `UpdateBy`         varchar(50) COLLATE utf8mb4_general_ci DEFAULT NULL,
  `UpdateTime`       datetime     DEFAULT NULL,
  `DeleteBy`         varchar(50) COLLATE utf8mb4_general_ci DEFAULT NULL,
  `DeleteTime`       datetime     DEFAULT NULL,
  `Status`           varchar(50) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '业务状态（保留）',
  `Sort`             int          DEFAULT 0   COMMENT '排序号',
  `Remark`           varchar(500) COLLATE utf8mb4_general_ci DEFAULT NULL,
  `IsDeleted`        tinyint(1)   NOT NULL DEFAULT 0,
  `IsValid`          int          NOT NULL DEFAULT 1 COMMENT '有效标志（1=有效，0=无效）',

  `TaskName`     varchar(200) COLLATE utf8mb4_general_ci NOT NULL COMMENT '★任务名称（★D29 专家自定义必填，如「XX公司2026第一次监督审核」）',
  `TaskNumber`       varchar(50) COLLATE utf8mb4_general_ci NOT NULL COMMENT '任务编号 TSK-yyyyMMdd-NNNN（系统生成，仅展示，不作关联键）',
  `TaskType`         varchar(20) COLLATE utf8mb4_general_ci NOT NULL COMMENT '任务类型：NC_CHECK | REPORT_GENERATE',
  `ScopeType`        varchar(20) COLLATE utf8mb4_general_ci NOT NULL COMMENT '范围类型：FULL=全局 | PARTIAL=局部',
  `TaskSource`   varchar(20) COLLATE utf8mb4_general_ci NOT NULL DEFAULT 'NEW'
                     COMMENT '★任务来源（D25）：NEW=全新 | REDO=整体重执行 | PATCH=局部更新',
  `ScopeSnapshot`    json         DEFAULT NULL COMMENT '范围快照（勾选/沿用/排除的 Code 数组），FULL 时为 NULL',

  `EnterpriseCode`   varchar(36) COLLATE utf8mb4_general_ci NOT NULL COMMENT '企业编码（cert_enterprise.Code）',
  `EnterpriseName`   varchar(200) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '企业名称（冗余快照）',

  `StageCode`        varchar(36) COLLATE utf8mb4_general_ci NOT NULL COMMENT '阶段编码（★cert_cert_stage.Code，不是 StageCode 业务码）',
  `StageName`        varchar(100) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '阶段名称（冗余快照）',

  `StandardCodes`    json         DEFAULT NULL COMMENT '涉及标准 Code 数组（冗余，列表页免 JOIN）',
  `StandardNames`    json         DEFAULT NULL COMMENT '涉及标准名称数组',
  `StandardCount`    int          DEFAULT 0   COMMENT '涉及标准数',

  -- ★★★ 三层状态（01 号 §4.1 / D27），⛔ 原有单一 TaskStatus 与 approved 已删除
  `ExecStatus`       varchar(20) COLLATE utf8mb4_general_ci NOT NULL DEFAULT 'draft'
                     COMMENT '★第1层 执行状态（机器管，不可逆）：draft | pending_run | running | completed | failed',
  `ReviewStatus`     varchar(20) COLLATE utf8mb4_general_ci NOT NULL DEFAULT 'not_started'
                     COMMENT '★第2层 结果状态（专家管）：not_started | pending_review | reviewed | modified | skipped | frozen',
  `LifecycleStatus`  varchar(20) COLLATE utf8mb4_general_ci NOT NULL DEFAULT 'active'
                     COMMENT '★第3层 存续状态（管理控制）：active | archived | cancelled | voided',
  `AuditEventCode`   varchar(36) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '★预留：认证周期审核事件（D26 本期不建表，仅留字段）',
  `AuditEventName`   varchar(100) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '★预留：事件名（如 SV-1 第一次监督审核）',

  `TotalItemCount`   int          DEFAULT 0   COMMENT '本轮涉及的任务项总数',
  `AckedCount`       int          DEFAULT 0   COMMENT '已认可数（reviewed）',
  `ModifiedCount`    int          DEFAULT 0   COMMENT '已修改数（modified）',
  `SkippedCount`     int          DEFAULT 0   COMMENT '已跳过数（skipped）',
  `PendingCount`     int          DEFAULT 0   COMMENT '待认可数（pending_review）',
  `FailedCount`      int          DEFAULT 0   COMMENT '执行失败数',
  `GapCount`         int          DEFAULT 0   COMMENT '未处理数据缺口数（★submit 前必须为 0）',
  `Progress`         decimal(5,2) DEFAULT 0.00 COMMENT '执行进度 %（队列执行进度，非认可进度）',

  `SkipAllGaps`      tinyint(1)   NOT NULL DEFAULT 0 COMMENT '专家是否点了「跳过全部补录」',
  `SkipAllGapsTime`  datetime     DEFAULT NULL,

  `SubmitTime`       datetime     DEFAULT NULL COMMENT '提交执行时间',
  `FinishTime`       datetime     DEFAULT NULL COMMENT '全部队列结束时间',

  -- ★★★ 业务锁键（D36 · 2026-09-30 用户裁决）—— 生成列，⛔ 不显式赋值
  `ActiveLockKey`  varchar(200) COLLATE utf8mb4_general_ci
                     GENERATED ALWAYS AS (
                       IF(`LifecycleStatus` = 'active' AND `ExecStatus` <> 'completed',
                          CONCAT_WS('|', `OrgCode`, `EnterpriseCode`, `StageCode`, `TaskType`),
                          NULL)
                     ) STORED
                     COMMENT '★业务锁键（锁键=Org|Ent|Stage|TaskType；已结束=NULL）。MySQL 唯一索引允许多个 NULL',

  PRIMARY KEY (`Id`),
  UNIQUE KEY `uk_code`          (`Code`),
  UNIQUE KEY `uk_org_tasknum`   (`OrgCode`, `TaskNumber`),
  -- ★ D36 业务锁并发兜底：同「企业+阶段+类型」只允许一个未结束任务
  --   并发下第二个 INSERT 撞此键 → MySQL 1062 → 转 BIZ_LOCKED
  UNIQUE KEY `uk_active_lock`   (`ActiveLockKey`),
  -- ★ 已按 D36 调整：加 TaskType（等值列在前），ExecStatus 是范围列放最后
  KEY `idx_bizlock`             (`OrgCode`, `EnterpriseCode`, `StageCode`, `TaskType`, `LifecycleStatus`, `ExecStatus`, `IsDeleted`),
  KEY `idx_ent_list`            (`OrgCode`, `EnterpriseCode`, `CreateTime`),
  KEY `idx_status_list`         (`OrgCode`, `ExecStatus`, `CreateTime`),
  KEY `idx_type_list`           (`OrgCode`, `TaskType`, `CreateTime`),
  KEY `idx_stage_code`          (`StageCode`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  COMMENT='专家任务（NC检查/报告生成）';
```

> **`idx_bizlock` 是业务锁专用索引**（02 号 §6.5）。锁检查在每次建任务 / 文件操作时触发，**必须走索引不能全表扫**。字段顺序按等值列在前、范围列（`ExecStatus <>`）在后设计。
>
> **`ActiveLockKey` + `uk_active_lock` 是并发兜底**（02 号 §6.4）：应用层 `SELECT` 与 `INSERT` 之间有竞态窗口，靠这个唯一索引兜住。★ MySQL 唯一索引允许多个 `NULL` ⇒ 已结束的任务不互相冲突。
> ⚠️ **生成列是 `STORED`**，插入/更新时由 MySQL 计算，**应用层 ⛔ 不要给它赋值**（会报错）。
>
> ★★ **实体映射（铁律七：DB 列名 = C# 属性名 = TS 字段名）** —— `ActiveLockKey` 必须在 `CertExpertTask` 实体上声明，但**排除写入**：
>
> ```csharp
> /// <summary>★业务锁键（D36）—— DB 生成列，应用层只读，⛔ 不参与 INSERT/UPDATE</summary>
> [SugarColumn(IsOnlyIgnoreInsert = true, IsOnlyIgnoreUpdate = true)]
> public string? ActiveLockKey { get; set; }
> ```
>
> ⛔ **若漏了这个特性**：SqlSugar 会把 `ActiveLockKey` 放进 INSERT 列表 → MySQL 报 **`ERROR 3105: The value specified for generated column ... is not allowed`** → 创建任务**恒失败**。
> ⛔ **也不要图省事不加这个属性**：那样前端 `Task` 对象拿不到锁键（虽然当前用不上），且违反铁律七的"三处一致"。
>
> ★ **生成列在 `INSERT` 时无需赋值**；任务状态变化（`ExecStatus` → `completed`，或 `LifecycleStatus` 变化）时 **MySQL 自动重算 ⇒ 锁自动释放**。

### 2.3 ★ 结果域（4 张表）— ★★ V2 已拆分（12 号 D11）

> ⚠️ **原 V1 是 1 张统一表 `cert_expert_task_item`（NC 检查项 + 报告章节合表）**。
> 12 号裁决：拆为「**实体层**（长期对象）+ **结果层**（多轮）」，NC 与报告各一组。
> 理由：同一企业该阶段的检查项跨任务存在，历史结论要累积多轮（3 年约 9 轮）。

```
配置层（全局，企业无关）        实体层（企业级，长期）        结果层（企业级，多轮）
cert_validation_rule    →  cert_expert_nc_item          →  cert_expert_nc_result
cert_report_section     →  cert_expert_report_section_item → cert_expert_report_result
  （管理员维护）                （系统按范围自动派生）           （专家认可/修改）
```

**四张表的职责**：

| 表 | 一行代表 | 关键字段 | 谁写 |
|---|---|---|---|
| `cert_expert_nc_item` | 「XX企业/复审阶段/ISO9001/文件控制」**这个检查项** | `Code` `EnterpriseCode` `StageCode` `StandardCode` `RuleCode` `CurrentResultCode` `LastAuditedTime` | 系统（建任务时派生） |
| `cert_expert_nc_result` | 该检查项的**第 N 轮结论** | `Code` `ItemCode` `RoundNo` `TaskCode` `Conformity` `Severity` `ReviewStatus` | 队列（执行）+ 专家（认可/改） |
| `cert_expert_report_section_item` | 「XX企业/复审阶段/ISO9001/审核概述」**这个章节** | 同上 + `SectionCode` `SectionTemplateContent` | 系统 |
| `cert_expert_report_result` | 该章节的**第 N 轮正文** | `Code` `ItemCode` `RoundNo` `TaskCode` `ContentText` `ReviewStatus` | 队列 + 专家 |

#### 2.3.5 ★ 轮次与「沿用」的语义

| 概念 | 归属 | 含义 |
|---|---|---|
| `RoundNo` | **业务层**（本节两表） | 跨任务的业务轮次。3 年约 9 轮/检查项 |

**沿用的三种情况**：

| 情况 | 结果表行为 | 实体表行为 |
|---|---|---|
| 局部任务**未勾选**该项 | ⛔ 不产生新行 | `CurrentResultCode` 不变；★ `LastAuditedTime` **不变**（D30） |
| 专家点「沿用上轮」 | ⛔ 不产生新行，`InheritFromCode` 记录来源 | 不变 |
| 重新执行该项 | ✅ 新增 `RoundNo+1` 的行 | `CurrentResultCode` 指向新行；`LastAuditedTime` 更新 |

#### GapKey 取值修正（★ 2026-09-30 用户裁决 J1）

| | 原（05 号 §2.5） | ★ 现（25 号） |
|---|---|---|
| 记录粒度 | 1 条 = 1 个（字段 × 依赖它的规则） | **1 条 = 1 个待补字段/表格** |
| 生成列 | `GapType\|FieldCode\|TableCode\|SourceItemCode` | `GapType\|**RuleCode**\|FieldCode\|TableCode` |
| 「影响 N 条规则」 | 落库（多条 gap 聚合） | **前端按 DAG 实时反查**，不落库 |

**为什么去掉 `SourceItemCode`**：规则是业务配置、变动频繁；gap 是任务快照、创建后不变。两者生命周期不一致 ⇒ 落库 `SourceItemCode` 必然漂移（规则改了，gap 还指向旧规则）。改为实时反查后，规则一改前端立刻正确。

**为什么加 `RuleCode`**：J4「1 文件 = 1 规则」（`uk_rule_scope` 唯一索引强制）⇒ 取数与清理的主键成分。同名 `FieldCode` 跨规则串扰也顺带消解。

> ⚠️ **本表已建（实测存在、0 行）**。改 `GapKey` 生成列需 `ALTER TABLE ... DROP INDEX uk_gap, DROP COLUMN GapKey, ADD COLUMN ... , ADD UNIQUE KEY uk_gap ...`，**在首次产生 gap 之前做即可（当前 0 行，零迁移成本）**。

> **为什么必须用生成列**：
>
> | 写法 | MySQL 8.0 行为 |
> |---|---|
> | ⛔ `UNIQUE KEY (TaskCode, GapType, IFNULL(FieldCode,''), ...)` | **语法错误** —— 索引列不允许函数表达式，建表直接失败 |
> | ⛔ `UNIQUE KEY (TaskCode, FieldCode, TableCode)` | 能建，但 **NULL 不参与去重**（`NULL != NULL`）→ 多行 NULL 同时通过，起不到作用 |
> | ✅ `GapKey` 生成列 + `UNIQUE (TaskCode, GapKey)` | ★ 正确。`IFNULL(...,'-')` 在生成列内合法，且 `'-'` 是普通字符串，参与唯一性判定 |
>
> ⚠️ **占位符用 `'-'` 而非 `''`**：空字符串在 `utf8mb4_general_ci` 下的比较行为需实测（见 13 号 E5-7），`'-'` 更明确且不会与真实值（槽位编码不以 `-` 开头）冲突。
>
> **实测验证 SQL**（建表后必跑）：
> ```sql

### 7.2 功能验证

```sql
-- ① 业务锁能命中（O1）
-- ★ D28 修正后的锁条件：执行未结束 且 未归档/作废/取消
SELECT Code, TaskNumber, TaskType, ExecStatus, LifecycleStatus, CreateTime
FROM cert_expert_task
WHERE OrgCode = '{工作区Code}'
  AND EnterpriseCode = '{企业Code}'
  AND StageCode = '{阶段Code}'
  AND ExecStatus    NOT IN ('completed','failed')
  AND LifecycleStatus = 'active'
  AND IsValid = 1 AND IsDeleted = 0;
-- 建一个 running 任务 → 期望 1 行
-- ⛔ 注意：此处【不】校验 TaskType，锁不分任务类型（D15）
-- ⚠️ 僵尸任务由 E5-6 定时 Job 兜底（ExecStatus 卡 running 超 2h → 置 failed）

-- ② 认可状态分布（★ 归档时校验，不是在批准时）
SELECT
  SUM(ReviewStatus='pending_review') AS PendingCnt,
  SUM(ReviewStatus='reviewed')      AS AckedCnt,
  SUM(ReviewStatus='modified')      AS ModifiedCnt,
  SUM(ReviewStatus='skipped')       AS SkippedCnt
FROM cert_expert_nc_result
WHERE TaskCode = '{任务Code}' AND IsValid = 1 AND IsDeleted = 0;
-- PendingCnt 供专家参考（结果菜单顶部提示），★不阻断任务级操作（D31）

-- ③ 缺口阻断校验（O2 ★ 唯一还在阻断的操作）
SELECT COUNT(*) AS UnresolvedGap
FROM cert_expert_task_data_gap
WHERE TaskCode = '{任务Code}' AND GapStatus = 'pending' AND IsValid = 1;
-- 必须为 0 才能 submit

-- ③-2 ★ 检查项实体复用验证（D11）
SELECT COUNT(*) AS ItemCnt, SUM(CurrentResultCode IS NULL) AS NeverChecked
FROM cert_expert_nc_item
WHERE EnterpriseCode='{企业}' AND StageCode='{阶段}' AND StandardCode='{标准}'
  AND IsValid=1 AND IsDeleted=0;
-- ItemCnt = 该范围内规则数；NeverChecked = 从未检查过的项

-- ④ 提取结果读取正确性（GetActiveAsync 口径，05 号 §2.2）
SELECT FieldCode, ExtractedValue, ValueSource, IsManualEdited, VersionNumber
FROM cert_extraction_result
WHERE OrgCode = '{企业Code}'          -- ★ 存的是企业 Code
  AND IsValid = 1 AND IsDeleted = 0
  AND StandardCode = '{标准Code}'
  AND PhaseCode = '{阶段Code}';
-- 验证：手动置 IsValid=0 一行 → 应查不到

-- ⑤ 补录日志完整
SELECT ResultType, FieldCode, ChangeAction, OldValueSource, NewValueSource,
       OperatorName, OperateTime
FROM cert_extraction_change_log
WHERE EnterpriseCode = '{企业Code}'
ORDER BY OperateTime DESC;
-- 验证：同一 FieldCode 反复修改应有 N 条记录

-- ⑥ ★ 归档/作废后冻结（D31：无 approved，判据是 LifecycleStatus）
SELECT Code, TaskName, TaskNumber, ExecStatus, LifecycleStatus
FROM cert_expert_task WHERE Code = '{任务Code}';
-- LifecycleStatus IN ('archived','voided','cancelled') 后
--   写端点应返回 409 TASK_FROZEN；已冻结的结果 ReviewStatus='frozen'
```
