## 一、总体结论

**不可直接开工。** 三类必须先解决的问题，按阻塞度排序：

| # | 结论 | 影响 |
|---|---|---|
| 1 | **数据模型存在两套并存且互斥的设计**：README/01-08 是「统一 `cert_expert_task_item`」旧模型，12/13 是「4 张 `biz_*` 结果表 + 三层状态」新模型。08 号内部已自相矛盾（第 970 行用 `biz_report_result`，第 1073 行用 `cert_expert_task_item`） | 建表、建实体、建页面全部返工 |
| 2 | **06 号迁移 SQL 有 6 处会直接执行失败**（1060 / 1091 / 1054 / 1452 / 1064），且 §4.1 的 `UPDATE ... INNER JOIN cert_phase_definition` 对空表更新 0 行 —— 静默无效 | S0「阻塞修复」实际修不动，后面全空转 |
| 3 | **规则域 `OrgCode` 口径在设计中是错的**：02 §1.1 ① 用专家工作区 `OrgCode` 去查 `cert_validation_rule.OrgCode`（该列存认证机构 `CbCode`）→ 候选规则恒为空 → 任务创建永远 0 项 | 整条链路跑不出任何结果 |

**需要纠正的基线误判**：05 §2.2 / 09 §3.2 把「`NodeExecutor` 无 `IsValid=1` 过滤」列为「★最严重缺陷」，实测**不成立** —— `SqlSugarDbOrm.GetOneAsync` 自动追加 `IsValid=1`（`SqlSugarDbOrm.cs:37-54`、`IsValidCondition<T>()` `:525-535`），且 `ExtractionResult.cs:74-77` 已声明 `IsValid`。真实缺陷只剩「无 `StandardCode`」「无 `FileCode`/`StageCode`」两项。基线事实错，S0 工时与验收标准都会定偏。
