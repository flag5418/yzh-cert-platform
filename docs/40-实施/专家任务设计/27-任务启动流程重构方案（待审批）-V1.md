## 一、整体判断

**不成立。**

用户逐字：

> 「这个任务的启动很奇怪……任务队列还有一个启动，填写的信息不是中文，全是字段的英文和看不懂的编号，我们的启动，如果发现缺失关键信息，应该是主动弹窗，将需要录入的信息，形成表单，让客户进行填写，队列如果因为某些问题不能启动，不是任务暂停，而是任务失败，而且应该是补全相关信息才开始真正的任务，而不是开启任务后，再让人去页面找，发现还有资料没有填写，这些操作都是反人直觉的，我作为开发者都很难理解，更不用说让审核员他们来理解如何执行」

这 6 条不是 6 个 bug，而是**同一处设计错位**：

> 系统把「跑之前必须备齐资料」这件**它自己该负责的事**，
> 拆成「提交 → 到详情页 → 再点启动 → 去第 4 个 Tab 找缺什么」四步，**推给了审核员**。

违背 `MEMORY.md §2` 的用户视角铁律：

> 设计要**同时**考虑「程序逻辑底层」与「**用户操作意愿**」—— 用户**不需要理解系统为什么这么做**，⛔ **不能把系统内部准备工作的负担转嫁给用户**。

**唯一正确的收口方向**：把「提交 + 启动」合并成**一个动作**，并把这个动作的**前置校验**做实 —— 缺资料就**不启动**，改成**弹窗表单当场补**，补齐后自动开跑。

## 二、逐条定性（含实测证据）

### F1 · 创建任务后返回列表，列表不刷新

**根因（已定位，前端）**：`cert-auditor/src/layouts/AuditorLayout.vue:55`

```html
<keep-alive>
  <component :is="Component" />
</keep-alive>
```

`<keep-alive>` **没有 `include`** ⇒ **所有页面永久缓存**；返回 `/tasks` 时组件被**复用**，`onMounted` **不再触发**，而内核 `yzh.vue.core` 全目录 grep `onActivated` = **0 命中** ⇒ 永远用旧数据。

**同一根因的另外两个症状（用户尚未报，但必踩）**：

| # | 症状 | 原因 |
|---|------|------|
| ② | 第二次进 `/tasks/create`，向导**还留着上次填的内容**和「创建成功」面板 | `create.vue` 的 `onMounted`（行 481）只跑一次 |
| ③ | 从列表点开**第二个任务**的详情，显示的还是**第一个任务**的数据 | `detail.vue` 的 `onMounted`（行 125）只跑一次；`taskCode` 变了但没人重新 `loadDetail()` |

⇒ **修法应落在布局层（keep-alive 策略），⛔ 不是逐页打补丁** —— 逐页打补丁会漏掉 ②③。

### F2 · 两个「启动」入口，语义重叠

**事实**：不是「重复按钮」，是**语义重叠**：

| 位置 | 真实按钮名 | 调用的接口 | 效果 |
|------|-----------|-----------|------|
| 列表行 | **提交执行** | `POST /submit` | 生成队列，`QueueStatus = pending` |
| 详情 Tab2 行 | **启动** | `POST /queue/{code}/start` | `pending → running` |

设计原意是「提交与启动拆开，允许分批跑」（`detail.vue:7` 注释）。

**问题**：这个**高级能力被摆在了主路径上**。审核员的心智是「我要跑这个任务」，不是「我要先物化实体层范围再启动队列」。

### F3 · 补录界面全是英文和编号

**两层根因，且已拿到真实数据。**

实测 `cert_expert_task_data_gap` 唯一那条缺口：

```
GapLabel         = appendix_three_program_file_list   ← 英文 snake_case
FieldCode        = appendix_three_program_file_list
RuleCode         = c8c0e278-aea9-42d5-9890-174911ae5412  ← GUID，用户说的「看不懂的编号」
ExpectedFileName = 附录三 程序文件清单.doc
GapStatus        = pending
```

**① 代码层**（可修）：

- `GapDetector.cs:412` —— `GapLabel` 兜底 = `d.FieldCode ?? ""` / `d.TableCode ?? ""`
- `GapDetector.cs:317` —— **table 型压根不赋 label** ⇒ **表格缺口永远是英文码**
- `detail.vue:323 / 332` —— 界面还**显式加了两列**「字段编码 / 表格编码」
- `detail.vue:374` —— 表格型补录要求用户**手填 JSON 数组**（`[{"列名":"值"}]`）

**② 数据层（更根本，⛔ 只改代码没用）**：

中文名的**唯一来源**是 `cert_doc_field_def.FieldName` / `cert_doc_table_def.TableName`。实测：

| 表 | 行数 | 内容 |
|----|------|------|
| `cert_doc_field_def` | **1** | 只有 `证书编号 / certificateNo` —— **`appendix_three_program_file_list` 根本没登记** |
| `cert_doc_table_def` | 6 | `TableName` = `table1` … `table6`（**本身就是英文**） |
| `cert_doc_table_field_def` | 23 | 列定义（可用） |

⇒ **这条实测缺口，即使把代码改完，仍然显示英文**。

**③ 配置层**：规则 `c8c0e278-…` 的 DAG 里，取数节点的 `title` 是泛化的「文档字段」，`config.fieldCode = appendix_three_program_file_list`；而该规则 `cert_doc_extraction_rule.SampleData` 里实际定义的是 `table_1.file_name / file_number` ⇒ **工作流节点引用的字段码与规则实际定义的字段不一致**（配置未同步）。

### F5 · 队列不能跑时应该是「失败」不是「暂停」—— **实测比用户描述的更严重**

**证据链**：

1. `ExpertTaskService.cs:1238` `StartQueueAsync` —— **完全没有缺口门禁**，直接 `q.QueueStatus = Running`（行 1253）。
2. 缺数据的任务项在 `ExpertItemExecutors.cs:221-231` 被标 **`skipped`**（`IsSkipped = true`）。注释写明设计意图：
   > `⛔ 不标 failed —— 缺数据不是专家的错，标 failed 会让失败数虚高、误导排查方向`
3. `ExpertTaskQueueRunner.cs:356-369` `RefreshQueueAsync`：

```csharp
if (pending > 0 || running > 0) { /* 保持原状态 */ }
else if (failed > 0) { q.QueueStatus = Failed; }
else { q.QueueStatus = Completed; }   // ← 全 skipped 时走这里
```

**⇒ 全部项都因缺数据被跳过时，`failed = 0` ⇒ 队列被置为 `Completed`。**

> **队列显示「已完成」，但里面全是「数据不足，未检查」。**
> 报告看起来跑完了，实际有检查项**根本没做** —— 而且**完全静默**。

这比用户说的「暂停」危险得多。

**注**：`PauseQueueAsync`（行 1297）确实是 `running → pending`，语义**没问题**（暂停就是人主动操作）。**问题不在「暂停」，在于缺数据根本不该进 `running`** —— 门禁要放在启动**之前**。

## 三、建议方案

### 一句话

> 把「提交执行 + 到详情逐个启动」合并为列表上的**一个「启动任务」**，前置校验；
> 缺数据就**不启动**，改为**弹窗表单当场补**，补齐后**自动开跑**。

### 目标流程

```
创建任务 → 点「启动任务」 → 前置校验（GapDetector 实时重算）
                              ├─ 无缺口 → 提交 + 启动全部队列 → 开跑
                              └─ 有缺口 → ⛔ 不启动，返回 Fail + 缺口清单
                                          → 弹窗表单（全中文）当场填
                                          → 批量补录成功 → 自动继续启动
```

### 关键设计点

1. **入口收敛**：列表行按钮「提交执行」→ **「启动任务」**，一次点击 = 提交 + 启动全部队列。
2. **门禁语义**：缺口存在时，`POST /submit`（或新端点）返回 **`Fail`**
   —— `success:false` + `err` 非空 + `message:""`（信封判据），**⛔ 不是「`Ok` + 提示塞 `data.message`」**（= 假成功）。
   返回体 `data` 里带**待补录清单（含中文名）**供前端直接渲染表单。
3. **弹窗表单**：一行一个待补项，**中文标签** = `<字段中文名>（来自 <文件名>）`；字段型 = 单行输入；表格型 = **逐列输入的小表格**（⛔ 不让用户写 JSON）。
4. **F5 语义**：门禁前置后，「先开任务再发现缺资料」的场景**不再存在** ⇒ 用户批评的「暂停」自然消失。
   执行期**兜底**仍保留（数据被删/换版）：`ExpertItemExecutors` 分支 3.5 已实时补登缺口。
   ⚠️ **但队列终态 `Completed` 的问题必须单独修**（见 §五 坑 1）。
5. **F1 修法**：在布局层收敛 `keep-alive` 策略，一并修掉向导页/详情页的缓存残留（§二 F1 的症状 ②③）。

### 裁 1 · 列表那个按钮叫什么、点一下做多少？

| 选项 | 内容 |
|------|------|
| **A（推荐）** | 改名 **「启动任务」**，一次点击 = 提交 + 启动全部队列；缺数据 ⇒ 弹窗补齐后自动继续 |

| 选项 | 内容 |
|------|------|
| **A（推荐）** | 允许，但降为**次要按钮 + 二次确认**（明说后果：相关检查项将标「数据不足，未检查」，**不计入符合数**） |

> B = 不填完就别想跑。最严格，但如果客户手上**真的没有**这份资料，任务会**永远卡住**。

## 五、动手的坑（按风险排序）

1. **★ 队列终态 `Completed` 的静默假完成**（`ExpertTaskQueueRunner.cs:360-369`）
   全部项 `skipped` 时队列被置 `Completed`。门禁前置后触发概率下降，但**不归零**（执行期兜底路径仍会跳过）。
   建议：队列终态增加「**有跳过项**」的显式区分（`RefreshQueueAsync` 判 `skipped > 0 && failed == 0` ⇒ 不置 `Completed`，或另立状态），⛔ 但这会动 `Queue` 枚举 ⇒ **需单独裁决**。
2. **合并「提交 + 启动」会跳过 `pending_run` 这一跳** —— 若以后要保留「只提交不启动」的分批能力，必须在详情页**留一条独立路径**，否则能力丢失。
3. **改 `Assets/EntityConfigs/*.json` 后必须重建 + 重启后端**（`EntityConfigLoader` 走 `IMemoryCache`，滑动 30 min / 绝对 2 h）⇒ 否则**静默不生效**。判据 = `GET /api/Auditor/ExpertTask/config`。
4. **中文字典的跨工程读取**：`cert_doc_field_def` / `cert_doc_table_def` 在 `CertPlatform.Shared`，`Auditor` 可引（无环）；⛔ 但 `Shared` 不能引 `Auditor`。
5. **表格型补录的列定义**来源 = `cert_doc_table_field_def`（实测 23 行，可用）—— 从「手填 JSON」升级为「可编辑小表格」的数据基础已具备。
6. **前端守卫（新页面必须 0 违规）**：弹窗必须用 `YzhDrawer`（**S07** 禁裸 `el-dialog`/`el-drawer`）；每个 `<el-button>` 必须显式 `type`（**S04**）；状态徽标用 `YzhStatusBadge`（**S08** 禁裸 `<el-tag>`）；样式走 `var(--yzh-*, 兜底)`（**R18** 禁裸 hex / 裸 px）。
7. **字段归属**：填写/提取提示词与字段中文名的补录，归**「提示词 / 规则配置」模块**，⛔ **不在 `doc-fill-rule` 页**（与既有归属裁定一致）。
