# 23 · 条款章节分类与文档召回的匹配·精炼·合并全链路设计

> **本文定位**：把用户 2026-11-26 提出的「先按大章节归类、条款三级结构 + 四要素释义、文档四分类且按大类与部门归属、条款与文档靠自定义大章节枚举对齐、两阶段过滤后组合发现再精炼、条款合并分两类」这套判断，落成**可实施的字段级设计**。
> **本文不做的事**：不改写用户结论、不推翻 05/15/16/17/19/20 已裁定的口径。凡与既有文档不一致处，一律进 §13 差异对照表并标为「沿用 / 修订 / 冲突待裁定」，**不自行改口径**。
> **一句话结论**：把「条款号对号」这条不可靠链路，换成「**大章节枚举（1 个键）→ 部门（n 个键）→ 释义语义（LLM 判定）**」的三段漏斗；条款侧与文档侧各只加**一组可过滤枚举 + 一组可读释义**，中间用两阶段过滤收敛到 ~10 → ~6 份，后段用「发现组合（不筛不判）」+「释义精炼（只重组不新增事实）」+「两类合并」收口。

## 零、一页结论（先看这 11 条）

1. **大类判定以语义为主，章号只作辅助特征（K3 裁定）**。Annex SL 三标准（`iso9001` / `iso14001` / `iso45001`）的条款号首段数字（4–10）与大章节一一对应，可作为**高置信辅助特征**（族内对应率 100%），但**不作唯一依据**——单看条款、不研究大标题难以判断大类（零-C P1），故判定顺序为「释义/条款语义 → PDCA 属性与章号特征 → `CD_UNKNOWN` 不猜」；非 Annex SL 标准（如 `iso13485`）走属性池 `Role` + 释义语义。这与 15 号「绝不按章号推 `Role`」不矛盾：禁的是**由章号推 `Role`**，此处推的只是 `ChapterDomain` 这一结构枚举，且仅作特征参与判定。
2. **大章节枚举 = 7 值 + 1 个未知值**：`CD_ENV 环境 / CD_LEAD 领导 / CD_DECIDE 决策 / CD_SUPPORT 支持 / CD_RUN 实施 / CD_ASSESS 评估 / CD_IMPROVE 改进 / CD_UNKNOWN`。用户的 7 个词与 GB/T 19001 第 4–10 章**数量与顺序完全对齐**，因此它可以直接承载「条款 ⇄ 文档」的对齐键。
3. **条款结构 = 三级展示 + 叶子成记录**。`4` / `4.1` / `4.1.1` 三级负责「树」，「一条结构记录」= **叶子条款**；`7.1.5.1` 这类四段号属真实存在的叶子，保留原号、树上折叠挂到最近三级节点（与 16 号、19 号一直在用的 `7.1.5.1` 检查项粒度兼容）。见 §3.1 与 §13.2-K2。
4. **释义 = 四要素，不是一个长文本**：`ClausePurpose`（条款作用，够 LLM 理解「做什么/需要什么/达到什么目的」）+ `EvidenceChain`（怎么找证据链，有序步骤）+ `EvidenceCheck`（找到的证据怎么检查，判据表）+ `ClauseScope`（范围：哪些环境/部门/过程）。四者分列四个 `AttrCode` 存，不合成一个巨型 JSON。
5. **文档侧 = 四分类 + 两维归属 + 一个抽象**：`Genre4`（质量手册 / 过程 / 作业指导 / 记录）+ `ChapterDomains[]`（可多值）+ `DeptCodes[]`（可多值）+ `Abstract`（精简抽象）。四分类与 17 号 8 个 `DocType` 是**投影关系**，不是替换关系。
6. **对齐键只有一组，不是条款号**：条款侧 `ChapterDomain`（1 值）⟷ 文档侧 `ChapterDomains[]`（n 值）交集非空；再加条款 `ClauseScope.depts ∩ 文档 DeptCodes` 与 19 号 `Role` 体裁白名单。**条款号不参与对齐**（沿用 16 号 §一四条硬伤）。
7. **两阶段过滤的规模是设计出来的，不是碰出来的**：Stage1 硬过滤目标中位 ~10 份（区间 3–40），Stage2 LLM 判定目标 ~6 份（区间 3–8）。Stage1 有 5 级显式降级阶梯（L0–L4），每一级都必须记账，**禁止静默兜底**（对 17 号「零兜底」的边界说明见 §13.2-K5）。
8. **后段三段不许互相越权**：Stage3「组合发现」只做组装、**不筛不判**（命中文档一份一条发现）；Stage4「释义精炼」只做重组压缩、**不得新增事实**（用「数字/编号/日期必须是输入子串」做幻觉校验）；合并只在两处发生——**跨标准在精炼之前合并释义**、**同标准在精炼之后按条款分段**。
9. **本设计的新增面很小**：条款侧加 5 个 `AttrCode`（`ChapterDomain` + 四要素）+ 1 个版本号；文档侧加 6 个 `DocProfileJson` 字段；运行时只加 1 个「两阶段过滤器」+ 5 个提示词契约 + 1 张合并缓存表（新建·待评审）。**不新建业务主表、不改既有提示词的既有职责。**
10. **动因不是「做不到」，而是「不划算」**：三体系企业下 1 份文档要按 3 个国标全跑一遍，token 与判定次数成倍、口径还不一致；V4 改用**指纹 + 特征逻辑**（`ChapterDomain` + `Genre4` + `DeptCodes` + 编号等可回引的结构特征）一次定形，跨标准只在释义层合并。理由三条见零-A。
11. **内核稳定、外壳可变**：内核 = 大章节枚举（`ChapterDomain`）+ 文档类型枚举（`Genre4`）+ 释义四要素的结构；外壳 = 具体标准的条款、条款号、标准间映射。**标准切换或更新只动外壳，Stage1–Stage4 算法与阈值不动**。分层与变更影响矩阵见零-B。

### 零-A · 设计动因：以指纹 + 特征逻辑取代条款匹配

> 本节记录用户 2026-11-26 第二轮补充确认的**动因**，是后文所有取舍的根因；原文逐字收录见「附录 A-2」。

V4 不再以「条款文本 ⇄ 文档条款号 / 条款原文」的匹配为主链路，而是以**指纹**（可回引的结构特征，沿用 17 号 `Fingerprints[].Key` 的「每条判断必须回引证据」口径）**+ 特征逻辑**（大章节枚举、文档类型枚举、部门、编号等结构化特征）来完成判定与对齐。用户给出的三条理由：

| # | 用户理由（原语义） | 对本设计的约束 |
|:--:|---|---|
| R1 | 三体系企业下，**1 个文档要按 3 个国标全部跑一遍**，浪费 token、效率低，**且条款匹配不精准** | 对齐键从「条款号/条款文本」换成「`ChapterDomain` 1 值 ⟷ `ChapterDomains[]` n 值」（§5）；**一份文档只画像一次、多标准复用**；跨标准差异收敛到释义层合并（§11.1 Type A），不重复判同一份文档 |
| R2 | **很多文档没必要按国标彻底跑一遍**，例如记录文档只能记录「是哪个部门、干了什么」 | 按 `Genre4` 分支的提取契约（§4.6）：记录类只做 `sampling` + 表格逐行改造，不套国标条款语义；手册/过程/作业指导各走各的引用口径 |
| R3 | 该方式**灵活**：无论标准如何切换或更新，核心都是我们归纳的**大章节枚举 + 文档类型枚举**，未来只需完善枚举，**核心算法不变** | 内核/外壳分层（零-B）；新增或换版标准不触碰 Stage1–Stage4 与阈值，只补枚举与释义 |

> 与旧路的关键差别：旧路把「标准」放在算法中心（新增一个标准 ≈ 新增一条判定链路）；V4 把「**枚举**」放在算法中心（新增一个标准 = 补枚举 + 补释义，链路不动）。这也是 §13.2 K1/K4「枚举即内核」裁定的直接依据。

### 零-B · 稳定内核与可变外壳：分层与变更影响矩阵

| 层 | 内容 | 变更频率 | 谁维护 | 是否影响 Stage1–Stage4 |
|:--:|---|---|---|---|
| **内核（稳定）** | ① 大章节枚举 `ChapterDomain`（7 值 + `CD_UNKNOWN`）；② 文档类型枚举 `Genre4`（手册 / 过程 / 作业指导 / 记录）；③ 释义四要素的**结构**（`ClausePurpose` / `EvidenceChain` / `EvidenceCheck` / `ClauseScope`）；④ 三键对齐与「两阶段漏斗 + 两处合并」的链路形状 | 低（只在归纳出新维度时增改） | 本设计 | **不变** |
| **外壳（可变）** | ① 具体标准的条款清单与条款号；② `ClauseText` 原文；③ 标准间同号映射与差异说明；④ 17 号 `DocType` 8 类投影、19 号 `Role` 白名单；⑤ 部门映射主数据 | 高（换版、增标准、组织调整） | 标准/主数据维护 | **不变** |

**变更影响矩阵**（回答「改什么要动哪一层、要不要重跑算法」）：

| 变更类型 | 需动的层 | 需动的实现面 | Stage1–Stage4 算法 | 阈值 / 判定口径 | 存量数据动作 |
|---|---|---|---|---|---|
| 增删 `ChapterDomain` 或 `Genre4` 取值 | 内核 | 枚举定义 + 提示词 vocab + 前端筛选器 + 画像回填脚本 | 不变 | 不变 | 新增值需增量回填（存量 `CD_UNKNOWN` 重判） |
| 改释义口径（四要素字段结构或写法） | 内核（结构微调，链路不变） | `clause_digest_gen` 提示词 + 质量抽检口径 | 不变 | 不变 | 按 `DigestRev` 增量重生成 |
| 换版 / 新增标准 / 多体系叠加 | 外壳 | 标准条款导入 + 释义批量生成 + Type A 合并缓存失效 | 不变 | 不变 | 新增标准行；**同一文档不重跑画像** |
| 改部门映射主数据 | 外壳 | 部门映射表 | 不变 | 不变 | `DeptCodes[]` 重算 |
| 改「大类 → 文档类型」白名单 | 内核（判据） | 19 号 `Role` 白名单扩展字段 | 不变 | C3 条件写法不变 | 无 |

> 判据：**内核改 = 可能引发全量回填与提示词重跑；外壳改 = 只引发增量数据动作**。两者都不触碰 Stage1–Stage4 的算法形状与阈值，这正是 R3「核心算法不变」的落点。

### 零-C · 认知前提：大类不能靠条款号猜，释义必须逐条写清作用

本节把用户反复强调的三点认知前提写成设计约束，避免后续实现把「归约」误当成「释义的替代品」。

| # | 认知前提 | 设计约束 | 落点 |
|:--:|---|---|---|
| P1 | **单看某条款、不研究大标题，难以判断它属于哪个大类**；国标每章严格按 **PDCA** 顺序编排，章节与条款**亦可带有该相关属性** | 大类判定以**语义**为主，PDCA 属性与章号只作**辅助特征**，不作硬推依据（不按章号硬推，见 §13.2 K3 裁定） | §2.1 的 PDCA 列、§2.3 判定优先级链 |
| P2 | **同一大章节下不同条款作用不同**（总则、方针、职责权限…），有的要求「**必须有什么**」，有的要求「**需要检查什么**」 | 释义**必须逐条写清作用**，不能只写一句概括：`ClausePurpose` 回答「做什么/需要什么/达到什么目的」，`EvidenceCheck` 回答「找到后怎么验」 | §3.2 四要素；`ClausePurpose` 三问必含 |
| P3 | 文档侧同构：**记录文档天然与「范围」「领导作用」相关**，因此**先定义每份文档属于哪一类大章节**，再按体裁走独立提取规则（手册 / 过程 / 记录 / 作业指导各有各的抽法） | `ChapterDomains[]` 判定**先于**提取契约执行；大类错了后续提取再精细也白做 | §4.3 判定规则、§4.6 四套提取契约 |

> **关键界定（防止实现走偏）**：**「按大类归约」不是替代释义，而是释义的检索前置键**。大类只负责把「条款 ⇄ 文档」的搜索空间从全库收敛到 ~10 份（Stage1），此后是否相关、证据够不够，仍由**逐条释义**在 Stage2/Stage4 判定。任何「用大类判定代替条款释义」或「用释义反推大类枚举」的做法都不成立。

## 二、条款一级归类：大章节枚举（`ChapterDomain`）

### 2.1 枚举定义（7 值 + 1 未知）

| Code | 中文名 | GB/T 19001 章 | `Role` | PDCA | 这一大类在问什么（一句话） |
|:--:|---|:--:|:--:|:--:|---|
| `CD_ENV` | 环境 | 4 组织环境 | r1 | P | 你识别了什么（内外部因素、相关方、体系范围与过程） |
| `CD_LEAD` | 领导 | 5 领导作用 | r2 | P | 谁承诺、谁负责（方针、职责权限、沟通） |

> **枚举采用用户命名的理由**：用户的 7 个词（环境 / 领导 / 决策 / 支持 / 实施 / 评估 / 改进）在**数量与顺序**上与 GB/T 19001 第 4–10 章一一对应，可作为稳定的对齐全集。既有 `Role`（r1–r7）与之中文名不同（组织环境 / 领导作用 / 策划 / 支持 / 运行 / 绩效评价 / 改进），语义完全同构 —— 因此 §2.2 用一张**恒等映射表**把两者挂住，不新增第二个体系。
> 「决策」与「策划」、「实施」与「运行」、「评估」与「绩效评价」是**同义换称**，对外只用用户口径，对内只存 `Role`。这不是两套枚举，是一套枚举的两种语言。

#### 2.1.1 章节原型定义（★ 一等资产：名称 + 作用 + 释义 + 典型证据）

> **本节是 2026-11-26 用户概念纠正的落点。** `ChapterDomain` **不是** 9001 的具体章节、**也不是**任何标准的条款号，而是**跨全部国标（9001 / 14001 / 45001 / 13485 …）提炼出的更抽象原型**。它有自己的「名称 + 作用 + 释义」，与条款释义**同构**（同样写清「干什么 / 需要什么 / 达到什么目的」）。
>
> **归类方法**：靠「**章节释义 ⟷ 文档/条款精简释义**」的**语义推理**得到，⛔ **不看文档里有没有显式章号或标题**（这是原文关键词法的失效根因，见 §4.3）。
>
> **可增量扩展**：标准新增领域（如 13485 的设计开发 / 法规要求 / 灭菌 / 植入）时，先在**本表**加或调原型，再回填条款与文档，**Stage1–Stage4 算法与阈值不动**。

| Code | 名称 | 作用（这一层在整个体系里干什么） | 释义（判据，供语义推理） | 典型证据 |
|:--:|---|---|---|---|

### 2.2 与既有属性/枚举的映射（唯一事实源）

| `ChapterDomain` | `Role`（15 号） | 16 号 `ClauseCategory`（6 类） | 19 号章号 | 映射性质 |
|:--:|:--:|:--:|:--:|---|
| `CD_ENV` | r1 | **框架**（仅 4、4.4、4.4.1、4.4.2）/ **策划**（4.1–4.3） | 4 | 一对多：需按条款号二级拆分【待裁定 K1】 |
| `CD_LEAD` | r2 | 承诺 | 5 | 一对一 |
| `CD_DECIDE` | r3 | 策划 | 6 | 一对一 |
| `CD_SUPPORT` | r4 | 支持 | 7 | 一对一 |
| `CD_RUN` | r5 | 运行 | 8 | 一对一 |
| `CD_ASSESS` | r6 | **改进**（与 r7 合并） | 9 | 二对一：16 号把 9/10 合并【待裁定 K1】 |
| `CD_IMPROVE` | r7 | 改进 | 10 | 一对一 |

**结论**：`ChapterDomain` 与 `Role` 是**一一对应主干 + 1 处细分**（4 章内部 4.1–4.3 与 4.4 的差别），与 16 号 `ClauseCategory` 是**7 类 vs 6 类**的粒度差。落库口径：

- `ChapterDomain` **必须**是独立属性（`AttrCode='ChapterDomain'`），因为它要参与 SQL 过滤；
- `Role` **保留不动**，继续负责「体裁白名单 + 默认提取方式」（15 号 / 19 号已落地）；
- `ClauseCategory` 的现有职责是「这个条款要不要追加 RM7 语义补召回」（16 号 §三.b），与 `ChapterDomain` 职责正交，**保留但不再扩用**，冲突处理见 §13.2-K1。

### 2.3 判定规则（优先级链，确定性优先）

```
ResolveChapterDomain(clause, standardCode):
 (1) 若 cert_clause_attr 已存在 ChapterDomain 且 ChapterDomainSource='manual'
     -> 直接返回（人工裁定优先，任何自动规则不得覆盖）
 (2) 若 standardCode ∈ {iso9001, iso14001, iso45001}      （Annex SL 族）
     -> n = ClauseCode 首段整数
     -> n ∈ [4,10] 则按 §2.1 表返回 CD_*
     -> n ∉ [4,10] 则落 (3)（不猜）
 (3) 读属性池 Role（r1..r7）-> §2.2 映射表 则返回 CD_*
 (4) Role 缺失 -> 一次性 LLM 打标（输入仅 ClauseText，输出单值 + ≤60 字理由），
     落 ChapterDomainSource='llm'，进 5% 人工抽检队列
 (5) 仍失败 -> CD_UNKNOWN，进人工确认队列，Stage1 记账必须出现
```

**K3 裁定口径（2026-11-26，用户）对本优先级链的约束**：上述 (2) 在 Annex SL 族内的章号规则，性质是**高置信特征快路径**，不是「唯一依据」。因此：

| 情形 | 处理 |
|---|---|
| 章号特征与释义/条款语义**一致** | 直接返回，`ChapterDomainSource='annex_sl'`（快路径，不额外消耗模型） |
| 章号特征与释义/条款语义**冲突** | **以语义为准**，落 `ChapterDomainSource='semantic_conflict'`，强制进人工抽检队列，并出冲突清单（不允许静默采用任一值） |
| 条款语义显式给出 PDCA 阶段属性且与章号不符 | 同上按语义处理；PDCA 属性仅作辅助特征参与判定 |
| 非 Annex SL 族 | 不走章号特征，按 (3)(4) 走 `Role` + 释义语义 |

> 即：**大类判定按语义与 PDCA 属性，不按章号硬推**（见 §13.2-K3、§13.3）。这一调整不改变 Stage1 的过滤键与阈值，只改变「章号特征与语义冲突时谁胜出」的口径。

**三条硬规则**

| # | 规则 | 为什么 |
|:--:|---|---|
| H1 | **禁止用文件名 / 文档标题 / 关键词反推条款大类** | 17 号已实测「靠文件名猜」= 分类失效的根因，同一错误不许在条款侧重演 |
| H2 | **禁止跨标准族用章号硬推** | `iso13485` 沿用旧 8 章体系、无第 9/10 章，章号与大类不同源（15 号已核实的校正结论） |
| H3 | `CD_UNKNOWN` **不得静默丢弃**，也不得默认归到 `CD_RUN` | 静默归并会制造「看起来覆盖率 100%、实际错类」的假象；必须作为**可观测缺口**暴露 |

### 2.4 归类覆盖率与验收

| 项 | 判据 |
|---|---|
| Annex SL 三标准 | `ChapterDomain` 覆盖率必须 = 100%（确定性映射，无理由低于 100%） |
| 非 Annex SL（首批外） | `CD_UNKNOWN` 允许存在，但必须出清单；首批验证不含 `iso13485`（沿用 15 号「暂缓」口径） |
| 人工抽检 | 每标准随机 10 条，与专家判断一致率 ≥ 95% |
| 冲突检测 | 同一 `ClauseCode` 在 3 个标准下 `ChapterDomain` 冲突数必须 = 0（16 号 P1 实测口径） |

## 三、条款结构与条款释义

### 3.1 三级结构规则

| 层级 | 号码形态 | 例 | 是否独立结构记录 | 是否参与大类归属 | 说明 |
|:--:|:--:|---|:--:|:--:|---|
| L1 | `N` | `4` | 否（容器） | 是 | 大类归属的唯一来源 |
| L2 | `N.M` | `4.1` | 否（容器） | 继承 L1 | 分组节点 |
| L3 | `N.M.K` | `4.1.1` | **是** | 继承 | 常规叶子 |
| L4+ | `N.M.K.J` | `7.1.5.1` | **是**（视为最末层） | 继承 | 树上折叠挂到最近 L3 节点下 |

**规则表述（与用户口径的对应）**

1. 用户口径「4 / 4.1 / 4.1.1 三级，不再细分」→ 落为**树只展示三级**；
2. 用户口径「以最末层作为一条结构记录」→ 落为**记录集合 = 叶子集合**，容器节点（L1/L2）不产生记录，只承上启下；
3. 现实中存在 `7.1.5.1` 这类四段号叶子，且**现有检查项就按 `7.1.5.1` 挂证据**（15 号 §四.2 示例、16 号 §一「粒度错位」均以此号为单位）。因此四段号不得被折叠成记录，只能折叠成**展示层级**。

**数据结构（字段级）**

| 字段 | 落点 | 说明 |
|---|---|---|
| `ClauseCode` | 条款树主键组成 | 真实条款号，四段号原样保留 |
| `StandardCode` | 条款树主键组成 | 标准短码；⚠️ 与 `cert_iso_clause` 的 `StandardCode`（GUID 口径）跨口径，必须显式换算（§15-C9） |
| `ParentCode` | 由号码前缀推导 | `4.1.1` → `4.1`；`7.1.5.1` → `7.1.5` |
| `Depth` | 由号码段数推导 | 1 / 2 / 3 / 4 |
| `IsLeaf` | 由条款树推导 | 无子节点即叶子 |
| `IsDigestRecord` | 本设计新增派生位 | `= IsLeaf`；只有它为 true 的条款才有四要素释义 |
| `ChapterDomain` | `cert_clause_attr`，`AttrCode='ChapterDomain'` | 见 §2 |
| `ClauseText` | `cert_clause_attr`，`AttrCode='ClauseText'`（16 号已定，JSON `{Title,Body,Items,Notes}`） | 语义匹配与释义生成的原文源 |
| `DigestRev` | `cert_clause_attr`，`AttrCode='DigestRev'`（整数） | 释义版本；释义重生成即 +1，用于缓存失效【待确认命名】 |

> **容器节点是否需要释义**：不需要。用户口径「每条释义」指每条**结构记录**，即叶子。容器节点的语义由子条款释义的并集近似，**不额外生成**（否则同一段文字被写 3 遍，且 Stage2 会把它喂给 LLM 造成重复）。

### 3.2 释义四要素：逐项定义

用户口径的四项，落为四个字段。每一项都必须**可被机器消费**，否则它只是「给 LLM 的提示词」而不是模型资产（05 号「模型才是资产」的判据）。

#### (1) `ClausePurpose` 条款作用

| 项 | 规定 |
|---|---|
| 定义 | 用审核员语言讲清该条款**要企业做到什么、需要哪些前提输入、达到什么目的**，使一个不具备体系知识的 LLM 能据此判断「某份文档是否与它有关」 |
| 必含三问 | (a) 这条要求企业**做什么动作**；(b) 做之前**需要什么**（准则/清单/授权/资源）；(c) 做到什么程度算**达到目的** |
| 长度 | 120–400 字 |
| 反抄袭约束 | 与 `ClauseText.Body` 的字符 3-gram 重合率 ≤ 0.40（超过即判「抄原文」，重生成） |
| 禁用 | 禁「应满足相关要求」「按标准执行」这类空话；禁出现「本系统」「提示词」「召回」等内部词 |

#### (2) `EvidenceChain` 证据链怎么找

| 项 | 规定 |
|---|---|
| 定义 | **有序步骤**，表达「要证明这条，需要按什么顺序、去找哪一类文档的哪一类信息」 |
| 元素字段 | `seq`（序号，1 起）、`action`（动作，动词短语 ≤20 字）、`targetGenre`（`Genre4` 之一）、`targetChapterDomain`（`CD_*`，可空=继承条款）、`targetDept`（部门词表内的值，可空=不限）、`expectForm`（`basis` 制度依据 / `execution` 执行证据 / `conclusion` 结论证据）、`minCount`（最少份数，默认 1） |
| 约束 | 步数 ≥ 2 且 ≤ 6；必须**至少 1 步** `expectForm` 为 `basis` 或 `execution`；`targetDept` 只能取部门词表值（词表外 = 0 容忍） |
| 示例（8.4.1 外部提供） | ① 找《采购控制程序》看准则是否存在（basis, process, 采购部）→ ② 找合格供方名录看是否经批准（execution）→ ③ 找供方评审/再评价记录看是否有业绩（execution）→ ④ 找进货检验记录看结果是否被使用（conclusion） |

#### (3) `EvidenceCheck` 找到的证据怎么检查

| 项 | 规定 |
|---|---|
| 定义 | 拿到证据后的**可判定清单**，回答「看到这份东西，凭什么说它够/不够」 |
| 元素字段 | `checkId`（`C01`…）、`target`（检查对象，如「名录批准人」）、`criterion`（判据，一句话）、`passCondition`（通过条件，须可量化）、`sampling`（抽样口径，如「近 3 个月 3 份」）、`onFail`（不通过时处置：`doubt` 进疑点 / `note` 仅记录） |
| 约束 | 条数 1–8；`passCondition` 不得写成「符合要求」（必须可对照）；`onFail` 默认 `doubt`（对齐 20 号「否定信息只进 `DoubtsJson`，不进正文」） |
| 与 05 号可判定度的关系 | `EvidenceCheck` 是实现 05 号 A/B/C 分级的载体：A 级条款的 `passCondition` 必须结构可判（存在/日期/签署/数量）；C 级条款允许只写「提供材料 + `onFail=note`」 |

#### (4) `ClauseScope` 范围

| 项 | 规定 |
|---|---|
| 定义 | 该条款**检查到哪些对象**上：哪些环境（组织环境 / 场所）、哪些部门、哪些过程 |
| 元素字段 | `depts[]`（部门词表 Code）、`processes[]`（过程码，沿用 19 号 `Process` 归一口径）、`sites[]`（场所，可空）、`environments[]`（环境维度，可空）、`exclusions[]`（明确不适用范围，可空）、`notes`（≤80 字） |
| 约束 | `depts` 与 `processes` 至少一个非空；`depts` 每项必须在部门词表内 |
| 【待确认】 | 用户口径「针对哪些环境/部门」中的「**环境**」，本设计按两种可能同时保留字段：`sites`（物理场所/车间/仓库）与 `environments`（内外部环境因素）；语义归属需用户一句话确认（见 §13.2 补充项） |

### 3.3 释义的存储方案（为什么是多个 `AttrCode` 而不是 1 个大 JSON）

| `AttrCode` | 值形态 | 大小量级 | 主要消费者 |
|---|---|---|:--|
| `ChapterDomain` | 枚举单值 | 8 字符 | **Stage1 SQL 过滤** |
| `ClausePurpose` | 纯文本 | 120–400 字 | Stage2 判定、Stage4 精炼 |
| `EvidenceChain` | JSON 数组 | 4–6 元素 | Stage2 判定（体裁/部门期望）、Stage3 提示 |
| `EvidenceCheck` | JSON 数组 | 1–8 元素 | Stage4 精炼（决定说什么/不说什么） |
| `ClauseScope` | JSON 对象 | 小 | **Stage1 部门过滤**、Stage2 范围校验 |
| `ClauseText` | JSON（16 号已定） | 中 | Stage2 语义、释义生成输入 |
| `DigestRev` | 整数 | 1–3 位 | 缓存失效 |

**为什么不合并成 `ClauseDigest` 一个 JSON 字段**（4 条理由，均可被既有实践印证）：

1. **过滤只读枚举**：Stage1 是纯 SQL，若 `ChapterDomain` 埋在 JSON 里，就必须 `JSON_EXTRACT` 或全表拉到内存 —— 与 22 号 `R-07`（索引与热查询不匹配）同类隐患，不能再自造一个。
2. **可单独重生成**：`ClausePurpose` 改文案不该导致 `EvidenceCheck` 也重跑（省 LLM）。
3. **可单独比对**：释义质量抽检、版本 diff 需要按要素比对，混在一起只能整段人工读。
4. **同构既有做法**：16 号已把 `ClauseText` 做成 JSON 单属性、`RecallRoutes` 做成 JSON 单属性 —— 说明本项目既有约定就是「过滤维度单列，内容维度 JSON」，本设计只是沿用。

> 唯一键口径沿用 `cert_clause_attr`：`(StandardCode, ClauseCode, AttrCode)`。⚠️ 16 号写作 `(StandardCode, ClauseNumber, AttrCode)`，两处字段名不一致，以现场库表为准（§15-C10）。

### 3.4 释义生成：提示词契约 `clause_digest_gen`

**用途**：为一条叶子条款生成四要素释义。一条一次，**离线批量**（配置期），不在运行期调用。

**输入槽位**

**契约条款（写进提示词正文，逐条可校验）**

1. 只输出 JSON，不输出解释、前后缀、Markdown 围栏。
2. `chapter_domain` **必须原样回填**输入值，不得自行改判；改判需求走 §2.3-(5)。
3. `purpose` 不得整段复制 `clause_text`（3-gram 重合率 ≤ 0.40）。
4. `evidence_chain` ≥ 2 步，每步 `target_genre` 必须取自 `{{genre_vocab}}`，`target_dept` 必须取自 `{{dept_vocab}}`（词表外一律置空，**禁止造部门**）。
5. `evidence_check` ≥ 1 条，`pass_condition` 必须可对照（禁「符合要求」这类）。
6. `scope.depts` 优先取 `{{dept_vocab}}` 中的实际部门；若条款本身不限部门，允许为空但 `processes` 必须非空。
7. 禁用词（命中即判失败重生成）：`置信度`、`召回`、`提示词`、`模型`、`AI`、`系统`、`未提供`、`无法判断`。
8. 数值一致性：`seq` 从 1 连续递增；`check_id` 形如 `C01`。

### 3.5 释义质量阈值

| 判据 | 阈值 | 不达标处置 |
|---|---|---|
| 叶子条款释义覆盖率 | ≥ 95%（`DigestRev` 存在且 `purpose` 非空） | 缺口清单进 P0 交付物，不得进入 P2 |
| `purpose` 长度 | 120–400 字 | 重生成 1 次 → 仍不达标标 `degraded` |
| `purpose` 抄原文率 | ≤ 0.40 | 重生成 1 次 |
| `evidence_chain` 步数 | 2–6 | 重生成 1 次 |
| `evidence_check` 条数 | 1–8 且 `pass_condition` 全部可对照 | 重生成 1 次 |
| 部门词表外命中 | 0 处 | 直接判失败 |
| 禁用词命中 | 0 处 | 直接判失败 |
| 人工抽检（每标准 10 条） | 四要素「可直接使用」≥ 80% | 该标准释义整体返工 |

### 4.3 `ChapterDomains[]` 判定规则（★ 2026-11-26 修订：改为「释义语义推理」）

> **方法纠正（本节为关键修订）**：原文用「目录标题关键词命中」判定 `ChapterDomains` —— 这正是用户指出的**失效根因**（记录类无显式章节标题 ⇒ 推不出 CD ⇒ 被 Stage1 滤掉，实测 `9.2.1` 内审 `B=0` = 漏召）。**改为**：① 先对每份文档生成**精简释义 `Abstract`（§4.5）**；② 把该释义与 **§2.1.1 的章节原型释义**做**语义推理**；③ 输出命中的 `ChapterDomains[]`（≤3）。⛔ **不看文档里有没有显式章号 / 标题**。

| 优先级 | 信号 | 规则 | `ChapterDomainsSource` |
|:--:|---|---|---|
| (1) | 人工裁定 | `IsManualCorrected=1` 或存在人工 `ChapterDomains` → 直接用（任何自动规则不得覆盖） | `manual` |
| (2) | **释义语义推理（主路径）** | `Abstract.OneLiner + ScopeLine + KeyObjects + SectionLabels` × §2.1.1 章节释义 → LLM 输出 `CD_*` 集合 + 每项 ≤60 字理由 | `semantic` |
| (3) | 目录标题关键词（**降级为辅助特征**） | 仅当 (2) 不可用（无 `Abstract`）时启用；命中即得，**不做模糊推断** | `toc` |
| (4) | 文档唯一体裁 | `manual` 类且未命中 → 全集 7 值（手册覆盖全部章节） | `inherit` |
| (5) | 均未命中 | **空集合**（不猜），进人工队列；该文档不参与 Stage1 的 C1 条件（见 §7.5-L2） | 空 |

**四条硬规则**

| # | 规则 | 为什么 |
|:--:|---|---|
| D1 | **`ChapterDomains` 与 `DocType`/`Genre4` 解耦** | 现有 `DocType` 错分严重（实测肉眼可辨 ≥15 份：「XX 控制程序」被判 `audit_profile`、「管理制度/规范」被判 `record_profile`、「内审检查表」被判 `manual_chapter`）。若 CD 从 DocType 投影 ⇒ **继承错误**。CD **只由释义推理得到**，二者独立；`Genre4` 另行从修正后的分类投影（用 `IsManualCorrected` 兜底） |
| D2 | 每条 CD **必须能回指** `Abstract` 的一个 `KeyObject` / `SectionLabel` | 沿用 17 号「必须回引证据」，避免纯猜 |
| D3 | 记录类**必须能判**（内审记录⇒`CD_ASSESS`、培训记录⇒`CD_SUPPORT`、检验报告⇒`CD_RUN`） | 记录不属于「领导/方针」；判不出 = 第 1 层失效，Stage1 全废 |

### 4.4 `DeptCodes[]` 判定规则（★ 2026-11-26 修订：**只用一种方式 = 语义推理到宽泛职能枚举**）

> **为什么废弃原文的「三路投票」**：原文用「文件名关键词 / `OwnerDept` / 表头字段」三路**拼分**（权重 1/2/1，得分 ≥2 入集）。多信号拼分 = **多方式**，任一信号错都会拉低或拉高总分 ⇒ **误判**。而部门是 Stage1 的**第一层筛选**，误判直接漏召或炸召回。故**只保留一种方式**。

**唯一判定方式（条款侧与文档侧同源、同一套枚举）**：

```

  ├─ x = 条款：释义 = ClausePurpose + ClauseScope（§3.2）
  └─ x = 文档：释义 = Abstract.OneLiner + ScopeLine + KeyObjects（§4.5）
```

- **归一（企业实际部门 ↔ 抽象职能）按固定优先级取来源**（仍是一种方式，只是分优先级降级）：

| ③（降级） | `cert_enterprise_dept.DeptDuty` 语义推理 | 语义 | 前两者皆缺，必须记账 |

### 4.5 `Abstract` 文档级精简抽象

用户口径「每份文档有精简抽象的作用」—— 落为一个必须先存在的对象，因为 Stage2 是拿它去和条款释义比语义的：**没有抽象，Stage2 就只能全文比对，等于把 4 万字手册再喂一遍**（14 号已实测超时）。

| 字段 | 类型 | 规定 |
|---|---|---|
| `OneLiner` | string | ≤ 80 字，一句话说清「这份文档是什么、规定/证明了什么」 |
| `ScopeLine` | string | ≤ 60 字，适用对象/范围 |
| `DocNature` | enum | `规定` / `执行` / `结论`（对应 05 号三职能） |
| `KeyObjects[]` | string[] | ≤ 8 项，关键对象（如「供应商」「校准证书」「内审报告」） |
| `ClauseRefs[]` | string[] | ≤ 10 项，文内自述的条款号（**仅记录，不用于对齐**） |
| `VersionInfo` | object | `DocCode` / `Version` / `Issuer` / `Approver` / `EffectiveDate`，可空（来自 `Metadata`） |
| `SectionLabels[]` | string[] | ≤ 12 项，章节标题，供 Stage2 定位 |

**为什么 `ClauseRefs` 只记录不对齐**：16 号 §一已实测「条款号幻觉」与「粒度错位」，17 号又把 `PrimaryClauses/Chapters` 由「必须」降为「有则记」。本设计继承该结论：条款号是**检索的辅助线索**，不是**对齐的依据**。

### 4.7 文档抽象生成提示词契约 `doc_abs_gen`

| 项 | 规定 |
|---|---|
| 触发 | 文档画像重建时（`doc-profile/rebuild-all` 同批），或指纹变更时 |
| 输入 | 文件名 + 目录 + `Fingerprints[]` + `Toc` 标题（≤12）+ 各节 `Summary`（≤120 字/节，≤8 节）+ `Metadata` |
| 输出 | §4.2 的 ★ 六字段（`Genre4` / `ChapterDomains[]` / `ChapterDomainsSource` / `DeptCodes[]` / `DeptSource` / `Abstract`）+ `AbstractStatus` |
| 约束 1 | `Genre4` 必须与 `DocType` 投影一致；不一致时**以 `DocType` 为准**并把模型值记入 `ClassReason`（防模型擅自改分类） |
| 约束 2 | `ChapterDomains` 每项必须回引一个 `Sections[].Label` 或指纹 Key，否则丢弃该项 |
| 约束 3 | `DeptCodes` 只能取部门词表值；`DEPT_UNKNOWN` 由代码补，不由模型写 |
| 约束 4 | `OneLiner` ≤ 80 字；禁「未提供/无法识别/不确定」式表述；判不出 → `AbstractStatus=degraded` + 空 `ChapterDomains` |
| 失败处置 | 非法 JSON → 修 JSON 重试 1 次 → 仍失败 → `AbstractStatus=missing`，该文档进 Stage1 时只按体裁参与（L2 降级） |

## 五、条款与文档的对齐：唯一对齐键

### 5.1 对齐键就是 `ChapterDomain`（三键组合）

```
条款 ──(1) ChapterDomain（1 值） ──∩── 文档 ChapterDomains[]（n 值）
     ──(2) ClauseScope.depts（n 值） ──∩── 文档 DeptCodes[]（n 值）
     ──(3) Role -> 体裁白名单（19 号 §三表） ──∈── 文档 ExtractionMode / Genre4
```

| 键 | 侧 A（条款） | 侧 B（文档） | 匹配语义 | 判定 |
|:--:|---|---|---|---|
| K-A 大类 | `ChapterDomain` | `ChapterDomains[]` | 交集非空 | **必要条件**（Stage1-C1） |
| K-B 部门 | `ClauseScope.depts[]` | `DeptCodes[]` | 交集非空；条款 `depts` 空则恒真 | 必要条件（Stage1-C2，可降级） |
| K-C 体裁 | `Role` → 白名单 | `ExtractionMode` | 命中白名单 | 必要条件（Stage1-C3，可降级） |

### 5.2 为什么对齐键不是条款号

| 硬伤（16 号 §一实测） | 若用条款号对齐的后果 | 用大类对齐的效果 |
|---|---|---|
| 记录类文档 `PrimaryClauses` 全空（37 份） | 记录类**完全不可达** | 记录靠大类 + 部门可达（记录也有 `CD_*` 归属） |
| 条款号幻觉（`6.1.3` / `7.5.4` 等不存在号） | 幻觉号永远匹配不上 | 大类是 7 值枚举，不可能幻觉到「不存在的类」 |
| 粒度错位（文档写 `6.2`、检查项是 `6.2.1`） | 需父子匹配补丁，仍有漏 | 大类粗到不怕粒度差 |
| 多标准重复提取（97 文档 × 3 标准） | 一份文档要按标准各猜一次条款号 | 大类是**标准无关**的（7 值跨标准同构），一次归属多标准复用 |

> 这与用户口径一致：「先不按 4.1.1 具体号，先归纳所属大类」。**大类是粗筛，语义是精筛** —— 粗筛用确定性键，精筛用释义（Stage2）。条款号只保留为 `Abstract.ClauseRefs` 的参考线索。

### 5.3 连接矩阵（条款大类 × 文档四分类）

> √ = 正常连接；△ = 弱连接（仅当 `EvidenceChain` 显式要求时才连）；× = 不连（Stage1-C3 直接排除）。

| 条款大类 \ 文档 `Genre4` | 质量手册 `manual` | 过程 `process` | 作业指导 `wi` | 记录 `record` |
|:--:|:--:|:--:|:--:|:--:|
| `CD_ENV` 环境 | √ | △ | × | √（因素清单/相关方清单） |
| `CD_LEAD` 领导 | √（方针/职责） | △ | × | △（任命书/职责矩阵） |
| `CD_DECIDE` 决策 | √ | △ | × | √（风险表/目标统计） |
| `CD_SUPPORT` 支持 | √ | √ | △ | √（台账/校准/培训） |
| `CD_RUN` 实施 | √ | √ | √ | √（运行记录） |
| `CD_ASSESS` 评估 | △ | △ | × | √（内审/管评/满意度） |
| `CD_IMPROVE` 改进 | △ | △ | × | √（NC/纠正措施） |

> 本矩阵是 Stage1-C3 的**可读表达**；**唯一事实源仍是 19 号 §三的 `Role → 体裁白名单`**（本表与之一致，不新增第二份判据）。

## 七、Stage1：大章节 + 部门 硬过滤

### 7.1 输入

| 输入项 | 来源 | 必填 |
|---|---|:--:|
| `enterpriseCode` | 检查项上下文 | 是 |
| `standardCode` | 检查项上下文 | 是 |
| `clauseCode` | 检查项 | 是 |
| `chapterDomain` | `cert_clause_attr.ChapterDomain` | 是（缺失即 `CD_UNKNOWN` → 跳过 Stage1） |
| `scopeDepts[]` | `ClauseScope.depts` | 否（空 = 不限部门） |
| `role` | `cert_clause_attr.Role` | 是（用于体裁白名单） |
| `allowDegrade` | 调用方开关，默认 true | 否 |

### 7.2 条件表达式（唯一判据，只允许一处实现）

```
C1  doc.ChapterDomains ∩ {clause.chapterDomain} ≠ ∅
C2  clause.scopeDepts = ∅  OR  (doc.DeptCodes ∩ clause.scopeDepts) ≠ ∅
    └ DEPT_UNKNOWN 不参与交集（视为空集）
C3  doc.ExtractionMode ∈ RoleWhitelist(clause.role)        // 19 号 §三表
C4  doc.ClassSource ≠ 'unclassified' AND doc.DocType ≠ 'none'
    AND doc.AbstractStatus ∈ {ok, degraded}
C5  doc.IsDeleted = 0 AND doc 提取产物存在（ExtractStatus 成功）

WHERE C1 AND C2 AND C3 AND C4 AND C5
```

> **判据唯一性**：本条件只能有**一份**实现（19 号 §一「同一判据出现在第二处 = 散乱根源」，守卫 A-R6）。现状 `CertTaskService` 与 `CertCheckContextBuilder` 两份实现必须收敛到此处，两端只做投影（沿用 19 号改造 1）。

```json
{

  "chapter_domain": "CD_RUN",
  "filter": "C1∧C2∧C3∧C4∧C5",
  "hit_count": 11,
  "degraded_level": 0,
  "degraded_reason": "",
  "candidates": [
    {
      "doc_id": "…",
      "doc_name": "采购控制程序",
      "genre4": "process",
      "extraction_mode": "process_profile",
      "chapter_domains": ["CD_RUN"],
      "dept_codes": ["PUR", "QA"],

      "match_keys": { "chapter": true, "dept": true, "genre": true },
```

### 7.4 阈值与规模控制

| 判据 | 阈值 | 依据 |
|---|:--:|---|
| 候选下限 `minCandidates` | 3 | 少于 3 份不足以支撑一条证据（19 号报告句式「抽查 N 份」的下限） |
| 候选中位目标 | ~10 | 用户口径「先得约 10 份候选」 |
| 候选上限 `maxCandidates` | 40 | 上限由 Stage2 token 预算反推（10 份 ≈ 1200 token，40 份 ≈ 4800 token，超出则 Stage2 分批） |
| 超出上限处置 | 按 `match_keys` 命中数降序 → `Genre4` 优先级（`process` > `manual` > `wi` > `record`）→ 摘要长度降序 截断 | 保证制度依据类不被记录类挤掉 |

> `maxCandidates=40` 与 `minCandidates=3` 均为**初值**【待确认】，需 P1 阶段用金标准 20 条款实测后定稿。

### 7.5 降级阶梯（L0–L4，必须逐级记账）

| 级别 | 触发条件 | 动作 | 标记 | 是否上屏 |
|:--:|---|---|---|:--:|
| **L0** | 五条件原样命中，候选 ∈ [3,40] | 正常进入 Stage2 | `degradedLevel=0` | 是 |
| **L1** | L0 命中 < 3 且 `scopeDepts` 非空 | **去掉 C2**（不按部门限）重跑 | `degradedLevel=1, reason=DEPT_FILTER_OFF` | 是（附原因） |
| **L2** | L1 仍 < 3 且存在 `ChapterDomains` 为空的文档 | **C1 改为「交集非空 OR 文档大类为空」**（空集文档按「未归属」放行，不判错） | `degradedLevel=2, reason=CHAPTER_EMPTY_PASS` | 是 |
| **L3** | L2 仍 < 3 | **去掉 C1 与 C2，只留 C3 体裁白名单** | `degradedLevel=3, reason=GENRE_ONLY` | 是（黄色提示） |
| **L4** | L3 仍 < 3 | **去掉 C3**，全库按 `Abstract.OneLiner` 与条款 `ClausePurpose` 的 BM25 取 top10（复用 16 号 RM7 的打分内核） | `degradedLevel=4, reason=FULLTEXT_FALLBACK` | 是（红色提示 + 需人工确认） |

**降级不是兜底，是显式失败路径**，三条约束：

1. **必须记账**：每级 `degradedLevel` 与 `reason` 写进 `InputSnapshotJson.recall.stage1`，前端按级别着色（L3 黄 / L4 红）。
2. **不得静默**：L3/L4 结果必须让审核员看到「本次按体裁/全文兜回来的」，避免「看起来召回了、其实是降级的」（22 号 `R-03` 的教训）。
3. **`CD_UNKNOWN` 不进 L1–L4**：它是数据缺口，降级也救不了，只出清单。

### 7.6 记账字段（`InputSnapshotJson.recall.stage1`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `filter` | string | 实际生效的条件表达式（如 `C1∧C3∧C4∧C5`） |
| `hitCount` | int | 命中数 |
| `degradedLevel` | int | 0–4 |
| `reason` | string | 降级原因码 |
| `candidates[].docId` / `docName` / `genre4` | — | 候选清单 |
| `matchKeys` | object | `{chapter, dept, genre}` 三键命中布尔，便于回答「它为什么被找来」 |
| `dropped[].docId` / `reason` | — | 被排除文档及首个失败条件（`C1_MISS` / `C2_MISS` / `C3_MISS` / `C4_UNCLASSIFIED` / `C5_NO_EXTRACT`） |

## 八、Stage2：条款释义 × 文档释义 的 LLM 筛选

### 8.1 输入裁剪（token 预算）

| 侧 | 内容 | 单份预算 | 总预算 |
|---|---|:--:|:--:|
| 条款侧 | `ClausePurpose`（全文）+ `EvidenceChain`（压缩为一行一步）+ `EvidenceCheck`（只留 `target` + `criterion`）+ `ClauseScope` | — | ≤ 900 token |
| 文档侧 | 每份：`doc_name` + `genre4` + `chapter_domains` + `abstract.one_liner` + `key_objects`（≤5）+ `section_labels`（≤3） | ≤ 120 token | ≤ 1200 token（10 份） |
| 系统侧 | 提示词正文 + 输出 schema | — | ≤ 800 token |

> **裁剪原则**：Stage2 **不喂章节原文**。它判的是「这份文档是否与这个条款有关」，只需要抽象层；原文留给 Stage3（按节锚段取，零额外成本）。这条与 14 号「绝不整篇喂 LLM」一致。
> 超过 20 份候选时，按 §7.4 截断规则分批调用，批间串行（Stage2 是判定，不可并行去重）。

### 8.2 提示词契约 `clause_doc_screen`

| 项 | 规定 |
|---|---|
| 角色 | 「体系审核资料筛选员」 |
| 任务 | 对每份候选文档判断：是否为该条款的取证对象；若命中，属于哪种证据角色 |
| 必须 | **逐份**给 `verdict`；每份必须有 `score`（0–1，两位小数）；每份必须有 `reason`（≤40 字，须引用该文档 `one_liner` 或 `section_label` 的措辞） |
| 禁止 | 禁输出「无法判断/不明确/需要更多信息」（信息不足判 `weak` 并在 `reason` 写**缺什么**）；禁编造文档内容（只能引用给定字段）；禁输出系统内部词（置信度/召回/提示词/模型）；禁改变 `doc_id` |
| 判定尺度（写进提示词） | `hit`：能直接支撑这条款的取证（制度依据/执行痕迹/结论）；`weak`：部分相关但需配合其它文档，或只覆盖条款一部分；`miss`：体裁或内容与条款无关（如同一体系但不同过程） |
| 输出 | 纯 JSON，无围栏、无解释 |
| 温度 | `temperature=0`，一次给全，**不允许逐份多轮问** |

### 8.3 输出 JSON Schema

```json
{
  "clause_code": "8.4.1",
  "chapter_domain": "CD_RUN",
  "decisions": [
    {
      "doc_id": "d_001",
      "doc_name": "采购控制程序",
      "verdict": "hit",
      "score": 0.91,
      "reason": "抽象写明规定供方选择评价再评价准则，与条款取证要求一致",
      "matched_sections": ["工作程序"],
      "as_evidence_role": "basis"
    }
  ],
  "selected": ["d_001"],
  "insufficient": false,
  "notes": "（≤60字，说明整体判断或缺口）"
}
```

字段约束

| 字段 | 约束 |
|---|---|
| `decisions` 条数 | 必须 = 输入候选数（**不允许漏判**，漏判即非法输出） |
| `verdict` | `hit` / `weak` / `miss` 三值 |
| `score` | 0.00–1.00；须与 `verdict` 一致（不一致时以 `score` 为准，并记 `inconsistent=true`） |
| `as_evidence_role` | `basis` / `execution` / `conclusion`（对齐 05 号的证据角色） |
| `matched_sections` | 必须取自输入 `section_labels`；不得自造 |
| `selected` | 必须 ⊆ `hit` 集合 |
| `insufficient` | 命中不足阈值时置 true（见 §8.4） |

### 8.4 判定标准与阈值

| 判据 | 阈值 | 处置 |
|---|:--:|---|
| `hit` 分数门 | `score ≥ 0.65` | 入 `selected` |
| `weak` 区间 | `0.40 ≤ score < 0.65` | 备选，仅在 `hit` 不足时补 |
| `miss` 区间 | `score < 0.40` | 排除，但保留在 `decisions`（可审计） |
| 保留上限 `maxKeep` | 8 | `hit > 8` → 按 `score` 降序截断，且**强制保证** `basis` 至少 1 份、`execution` 至少 1 份（体裁多样性） |
| 最少需求 `minNeed` | 3 | `hit < 3` → 用 `weak` 按 `score` 补到 3 |
| 目标值 | ~6 | 用户口径「约剩 6 份」 |
| 补足后仍 < 3 | — | 置 `insufficient=true`，**不虚增**：`selected` 保留实际命中，Stage3 按实际份数生成，Stage4 标注「证据份数不足」并要求 `conclusion=pending` |
| `basis` 缺失（全部非 basis） | — | 允许，但 Stage4 必须把「制度依据缺位」写进 `DoubtsJson`（不进正文，对齐 20 号） |

> 三个阈值（0.65 / 0.40 / 3–8）为**初值**【待确认】，P2 阶段用金标准集调参。判定口径不变：**拿不准就判 weak，不许判 hit 也不许说「无法判断」**。

### 8.5 失败处理（不含静默兜底）

| 失败场景 | 处置 | 记账 |
|---|---|---|
| 输出非 JSON / JSON 非法 | 只重产出 JSON（同一输入，重试 1 次） | `stage2.retry=1` |
| 重试仍失败 | **降级为「Stage1 候选全 hit」**（`score=0.50`）：Stage1 已含大类/部门/体裁三重对齐，全收比丢空更安全 | `degraded=true, reason=SCREEN_LLM_FAIL` |
| `decisions` 条数 ≠ 候选数 | 缺判的文档按 `weak(0.45)` 补齐并标 `autoFilled=true` | `stage2.autoFilled=n` |
| `selected` ⊄ `hit` | 以 `selected` 为准，差额记 `inconsistent=true` | — |
| LLM 超时（> 90s） | 同「重试仍失败」 | `reason=SCREEN_TIMEOUT` |

### 8.6 记账字段（`InputSnapshotJson.recall.stage2`）

| 字段 | 说明 |
|---|---|
| `selected[].docId` / `score` / `verdict` / `asEvidenceRole` / `reason` | 判定结果 |
| `weak[]` / `miss[]` | 未入选但也记原因（回答「为什么这份没进来」） |
| `insufficient` | 是否份数不足 |
| `inconsistent` / `autoFilled` | 一致性异常计数 |
| `promptRev` | 提示词版本号（提示词会改，必须留痕） |

## 九、Stage3：命中文档生成证据，直接组合成发现

### 9.1 证据角色（沿用 19 号三族）

| 角色 | 来源体裁 | 句式骨架（19 号 §六） | 必填要素 |
|---|---|---|---|
| `basis` 制度依据 | `manual` / `process` / `wi` | 公司依据《X》（编号/版次/三签/发布日期）规定了… | 名称 + 编号 + 版次 + 批准 + 日期 + 条款/章节 |
| `execution` 执行证据 | `record` | 查见《Z》，共 N 条，其中抽 M 条（编号/日期/对象/签字/结论）… | 记录名 + 数量 + 抽样明细 + 期间 |
| `conclusion` 结论证据 | `record`（报告/评价类） | 查见《W》，结论为… | 结论值 + 日期 + 批准人 |

> 用户口径「将命中文档生成证据直接组合成发现」——`Discover` 就是「一份文档对应的一条发现」，它是 `basis` / `execution` / `conclusion` 的容器，**不是压缩后的句子**。

### 9.2 分体裁取数（Stage3 的输入已存在，不重复抽）

| 体裁 | 取什么 | 是否调模型 |
|---|---|:--:|
| `manual` | `Sections[]` 中与条款大类相关的节：`Label` + `Summary` + `CharStart/CharEnd` 锚段（原文回取） | 否（离线已有） |
| `process` / `wi` | `doc_code` / `version` / `issuer` / `approver` / `effective_date` / `purpose_one_line` / `clause_refs` | 否（`Metadata` 已有） |
| `record` | `sampling` + `records[]`（逐条：`row_no` / `fields` / `signers` / `zero_event`） | 否（离线已有） |

> **结论：Stage3 默认 0 模型调用。** 只有当某份文档的离线产物缺关键要素（如 `record` 缺 `sampling`）时，才对该文档单独调一次补抽（上限 2 次/条款，超限则该 `Discover` 标 `partial=true`）。这正是 14 号「离线预处理、运行期只取」的落点。

### 9.3 `Discover` 结构（字段级）

| 字段 | 类型 | 说明 |
|---|---|---|
| `discoverId` | string | `D1`…`Dn`，按 `evidenceRole` 排序后编号 |
| `clauseCode` | string | 所属条款（合并场景下可为多值） |
| `docId` / `docName` / `docCode` | string | 文档标识（`docCode` 可空） |
| `genre4` | enum | 四分类 |
| `evidenceRole` | enum | `basis` / `execution` / `conclusion` |
| `sectionAnchor` | object | `{label, charStart, charEnd}`（`manual` 必填；`record` 用 `rowNo`） |
| `facts` | object | 按体裁的可读事实（见 §9.2） |
| `factsText` | string | 由 `facts` 模板化渲染的事实陈述（≤150 字，**不含结论、不含评价**） |
| `deptScope` | string[] | 该文档覆盖部门 |
| `sourceType` | string | 固定 `企业`（05 号 §4.3：标准原文不得入槽） |
| `partial` | bool | 离线产物缺要素时为 true |
| `internalScore` | number | 仅落快照，**严禁上屏**（20 号禁系统痕迹） |

### 9.4 组合规则（关键：不做二次筛选）

1. **一份命中文档 → 一条 `Discover`**，条数 = `selected` 数（~6）。不得因「内容看起来重复」丢弃某条 —— 丢不丢是 Stage4 的职责（且 Stage4 必须写明 `dropped` 原因）。
2. **排序**：`basis` → `execution` → `conclusion`；同角色内按 `stage2.score` 降序。
3. **去重**：只做**物理去重**（同一 `docId` 因父子条款重复入选 → 合成一条，`clauseCode` 记多值）；**不做语义去重**。
4. **不跨文档合并事实**：一条 `Discover` 只陈述一份文档里的事实。跨文档的综合是 Stage4 的事。
5. **证据不足照实**：`selected` < 3 时照实组装（不补假文档），并把份数写进 `factsText` 前缀（「查见《X》等 2 份资料」）。

### 9.5 补抽提示词契约 `discovery_patch`（仅 partial 场景）

| 项 | 规定 |
|---|---|
| 触发 | 离线产物缺要素且该文档已被 Stage2 选为 `hit` |
| 输入 | 条款 `ClausePurpose` + 该文档指定章节锚段原文（≤1200 字）或指定表格片段 |
| 输出 | `{"doc_id","missing_field":"sampling|doc_code|approver|…","value":"…","evidence_span":"原文片段≤80字","confidence":"high|low"}` |
| 约束 | `value` 必须能在 `evidence_span` 中找到依据；找不到 → `confidence=low` 且 `value` 置空；禁止推断未出现的信息 |
| 失败 | `confidence=low` → 该 `Discover.partial=true` 保留，不阻塞 Stage4 |

## 十、Stage4：条款释义 × 全部发现 的 LLM 精炼

### 10.1 输入

| 侧 | 内容 | 预算 |
|---|---|:--:|
| 条款侧 | `ClausePurpose`（全文）+ `EvidenceCheck`（全部，用于决定说什么）+ `ClauseScope`（用于限定范围表述） | ≤ 1000 token |
| 发现侧 | 每条 `Discover`：`discoverId` + `evidenceRole` + `docName` + `docCode` + `factsText` + 抽样摘要 | ≤ 150 token/条，≤ 6 条 |
| 规则侧 | 20 号禁令清单 + 字数区间 + 符合项逻辑 | ≤ 300 token |

### 10.2 提示词契约 `clause_evidence_refine`

| 项 | 规定 |
|---|---|
| 角色 | 「体系审核员（写结论）」 |
| 任务 | 依据条款释义与已给发现，写出**该条款一段**审核证据 |
| 必须 | ① 200–500 字；② 符合项逻辑（先依据后执行再结论）；③ 每个事实必须能追溯到某个 `discoverId`（写进 `used_doc_ids`）；④ 未使用的发现必须给 `reason` |
| 禁止（20 号已定，逐条继承） | 禁置信度/召回/定位片段/章节候选/模型评分等**系统痕迹**；禁「未发现/未提供/缺乏/无法证实」等**否定表述进正文**（只进 `DoubtsJson`）；禁英文字段名（须中文化）；禁编造日期/编号/人员；禁写「疑点/不确定」 |
| 追溯校验 | 正文中出现的**数字、编号、日期**必须是输入 `Discover` 文本的子串（见 §12.1 幻觉率判据） |
| 输出 | 纯 JSON |

### 10.3 输出 JSON Schema

```json
{
  "clause_code": "8.4.1",
  "final_evidence": "（200-500字，符合项逻辑）",
  "conclusion": "conform",
  "used_doc_ids": ["D1", "D2", "D3"],
  "dropped": [{ "doc_id": "D6", "reason": "与条款取证无直接关系" }],
  "word_count": 356,
  "doubts": ["合格供方名录未见批准人签署"]
}
```

| 字段 | 约束 |
|---|---|
| `final_evidence` | 200–500 字（按 `CHAR_LENGTH`，与 20 号实测 `ReasonLen` 同口径） |
| `conclusion` | `conform` / `noconform` / `pending`（`pending` 仅在 `stage2.insufficient=true` 或 `EvidenceCheck` 命中 `doubt` 时） |
| `used_doc_ids` | 必须 ⊆ 输入 `Discover` 的 `discoverId` 集合 |
| `dropped` | 输入中未使用的必须全部列出并给 `reason`（≤20 字） |
| `word_count` | 自报字数；与实测差 > 30 字判 `miscount` |
| `doubts` | 否定信息/缺口，落 `cert_check_result.DoubtsJson`（20 号 `SanitizeDoubtText` 保留「未标注/缺失」） |

### 10.4 精炼 ≠ 重写（三条硬边界）

| 边界 | 判据 | 违反处置 |
|---|---|---|
| 不得新增事实 | 正文中的数字/编号/日期子串命中率 ≥ 90% | < 90% 判 `hallucination_suspect` → 重生成 1 次 → 仍低则回退为 `Discover.factsText` 直接拼接（不精炼） |
| 不得改变结论方向 | 若 `EvidenceCheck.onFail=doubt` 项命中，`conclusion` 不得为 `conform` | 强制改写为 `pending` + 该句进 `doubts` |
| 不得越过范围 | 不得出现 `ClauseScope.exclusions` 中的对象 | 命中即重生成 |

### 10.5 精炼失败链路

```
LLM 输出非法 -> 修 JSON 重试 1 次
     -> 仍非法 -> 走模板装配：按 basis / execution / conclusion 三段用 19 号 §六模板拼一段（禁评价词）-> 标 degraded
final_evidence 为空（20 号 RemoveAbsenceSentences 清空）-> 重生成 1 次
     -> 仍空 -> 回填首条 basis 的 factsText + 标注「（证据待补充）」-> 落 evidence_empty 事件
```

## 十一、条款合并（两类，位置不同）

### 11.1 Type A：跨标准同条款 → 先合并释义，再做统一语义分析

**触发**：同一 `ClauseCode`（如 `8.4.1`）在 2 个及以上启用标准（`iso9001` / `iso14001` / `iso45001`）中同时存在。

**位置：Stage2 之前**（这一点与既有实现不同，见 §13.2-K6）。

```
iso9001:8.4.1 Digest A \
iso14001:8.4.1 Digest B  --> MergedDigest(8.4.1) --> Stage2 --> Stage3 --> Stage4 --> 一段文字
iso45001:8.4.1 Digest C /
```

**合并的三个必做动作**（用户口径「对多条款释义合并后做统一语义分析，得到合并解释」）

| 动作 | 具体做法 | 理由 |
|---|---|---|
| (1) 释义合并 | 四要素逐项求并集：`Purpose` 取三者要点归并（去重同义句）；`EvidenceChain` 按 `seq` 重排、同 `(action,targetGenre,targetDept)` 合成一步；`EvidenceCheck` 按 `target` 归并（同对象保留更严 `passCondition`）；`ClauseScope` 求并集（`depts`/`processes`/`sites`） | 三个标准对同一号的要求高度重叠，分列会让 Stage2 把同一文档重复判 3 次 |
| (2) 统一语义分析 | 用 `clause_digest_merge` 提示词让 LLM 输出**一段**合并解释（`MergedPurpose` 150–450 字）+ **一张**合并检查表 + 一句「三标准差异点」（若存在实质差异，如 14001 的 8.4.1 强调外包过程的环境因素） | 这就是用户说的「合并解释」 |
| (3) 差异标注 | `Divergence[]`：`{clauseCode, standardCodes[], aspect, detail}` —— 只标注**实质差异**（要求不同/范围不同），标「表述差异」不算 | 审核员必须知道「这条在三个体系里要求是否一致」 |

**`MergedDigest` 结构**

| 字段 | 类型 | 说明 |
|---|---|---|
| `MergeKey` | string | `M:{ClauseCode}:{sorted standardCodes}`，如 `M:8.4.1:iso14001+iso9001` |
| `ClauseCode` | string | 条款号 |
| `StandardCodes[]` | string[] | 参与合并的标准 |
| `MergedPurpose` | string | 合并解释（150–450 字） |
| `MergedChain[]` | array | 合并后证据链（结构同 `EvidenceChain`） |
| `MergedCheck[]` | array | 合并后检查表（同 `EvidenceCheck`，取严） |
| `MergedScope` | object | 并集范围 |
| `Divergence[]` | array | 实质差异清单 |
| `SourceRev` | object | `{standardCode: DigestRev}`，任一源 `DigestRev` 变化即失效重算 |
| `PromptRev` | string | 提示词版本 |
| `Status` | enum | `ok` / `degraded`（LLM 失败时用「并集拼接」降级，不做语义归并） |

**存储**：新建 `cert_clause_digest_merge`（**新建·待评审**），唯一键 `(MergeKey)`，缓存策略见 §11.4。若评审不通过，退化为运行时内存合并（每次都会多调 1 次 LLM）。

**提示词契约 `clause_digest_merge`**

| 项 | 规定 |
|---|---|
| 输入 | 各标准的 `ClausePurpose` + `EvidenceChain` + `EvidenceCheck` + `ClauseScope`（各 ≤ 900 token） |
| 输出 | `{"merged_purpose","merged_chain[]","merged_check[]","merged_scope","divergence[]"}` |
| 硬约束 | `merged_purpose` 不得遗漏任一标准的**独有要求**（须在 `divergence` 或正文出现）；`merged_check` 同 `target` 取更严条件（可判定条件的交集优先）；不得出现标准号与条款号错配 |
| 上限 | 3 个标准合并；>3 时按「9001 为基准 + 逐个增量合并」串行 |

### 11.2 Type B：同标准多条款合并 → 一个条款一段文字

**触发**：一次检查任务覆盖同标准多个条款（如 4.1 + 4.2 + 4.3），需汇总为一段。

**位置：Stage4 之后**（每个条款已各自有 `final_evidence`，只做**段落拼接**，不重写）。

```
8.5.1 -> final_evidence_1 (2xx字)
8.5.2 -> final_evidence_2 (2xx字)   -->  拼接：一段/条款，段首带条款号
8.5.3 -> final_evidence_3 (2xx字)
```

**规则**

| # | 规则 |
|:--:|---|
| B1 | **一个条款一段文字**，段首统一 `{ClauseCode} {ClauseTitle}：`；段间不写过渡语（禁「综上所述」「此外」） |
| B2 | 不跨段合并事实（`8.5.1` 的记录不得出现在 `8.5.2` 段） |
| B3 | 段序 = 条款号自然序（`4.1 < 4.10 < 4.2` 按数字段比较，禁用字符串排序） |
| B4 | 父条款（`4` / `4.1`）非叶子**不单独成段**；其内容由子条款段落体现（对齐 20 号「父子归最细号」） |
| B5 | 全段共享的**制度依据**允许在首段完整写一次，后续段写「依据同前《X》」——仅此一种跨段引用 |
| B6 | 合并后做一次**全局去重**：完全相同的事实句（≥20 字完全相同）只保留首次出现（这是唯一允许的自动删句，且必须记账 `dedupCount`） |

### 11.3 两类合并的差异对照

| 维度 | Type A 跨标准同条款 | Type B 同标准多条款 |
|---|---|---|
| 位置 | **Stage2 之前**（合并释义再检索） | **Stage4 之后**（合并已写好的段落） |
| 合并对象 | 释义（`Digest`） | 正文（`final_evidence`） |
| 是否调 LLM | 是（`clause_digest_merge`，配置期可预生成） | 否（纯拼接，不做改写） |
| 输出形态 | 一段合并解释 + 一张合并检查表 | N 段，一段一条款 |
| 缓存 | 必须缓存（`MergedDigest`），源 rev 变则失效 | 不缓存（随任务生成） |
| 丧失信息的风险 | 合并会淡化标准差异 → 必须出 `Divergence[]` | 拼接不会丢信息 → 只需要去重记账 |
| 典型错法 | 把三个标准的要求写成一段「通用话术」，导致 14001 的合规性评价被漏掉 | 把多个条款写成一段，审核员无法按条款回填结论 |

### 11.4 缓存与失效

| 缓存对象 | Key | 失效条件 |
|---|---|---|
| `MergedDigest` | `MergeKey` | ①任一源 `DigestRev` 变化；②`PromptRev` 变化；③标准启用集合变化；④超过 30 天（防上游数据被手改未改 rev） |
| 释义 `Digest` | `(StandardCode, ClauseCode, AttrCode)` | `ClauseText` 变化 / 人工编辑 |

### 12.2 兜底与降级矩阵（一眼看清「坏了会怎样」）

| 环节 | 失败形态 | 兜底动作 | 标记 | 是否阻断 |
|:--:|---|---|---|:--:|
| 大类判定 | `CD_UNKNOWN` | 不进 Stage1，出清单 | `unclassifiedDomain` | 否（该条款记 `pending`） |
| 释义生成 | 四要素缺失 | 用 `ClauseText` 原文 + 通用链（「查制度 → 查记录」）构造 minimum digest | `digest=minimal` | 否 |
| 文档画像 | `unclassified` / `none` | 不进候选池 | — | 否 |
| 文档抽象 | `missing` / `degraded` | 只按体裁参与（L2） | `AbstractStatus` | 否 |
| Stage1 | 候选 < 3 | L1→L4 阶梯 | `degradedLevel` | 否（L4 需人工确认） |
| Stage2 | 非法 JSON / 超时 | 候选全 hit（0.50） | `SCREEN_LLM_FAIL` | 否 |
| Stage2 | 命中 < 3 | 不虚增，`insufficient=true` | 同上 | 否（Stage4 → `pending`） |
| Stage3 | 产物缺要素 | 补抽 ≤2 次 → `partial=true` | `partial` | 否 |
| Stage4 | 非法 JSON | 模板装配三段式 | `refine=template` | 否 |
| Stage4 | 幻觉率高 | 回退 `factsText` 拼接 | `refine=raw` | 否 |
| Stage4 | 清洗后为空 | 首条 `basis` 的 `factsText` + 「（证据待补充）」 | `evidence_empty` 事件 | 否 |
| 合并 | LLM 失败 | 并集拼接（不做语义归并）+ `Status=degraded` | `MERGE_DEGRADED` | 否 |

> **总则**：任何一级都**不允许把失败伪装成成功**。每个兜底动作都必须留一个可观测标记，前端与报告都能回答「这条证据是怎么来的、哪一级降过级」。

### 12.3 必须上屏 / 必须不上屏

| 必须上屏 | 必须不上屏 |

| 证据份数、文档名、编号、日期 | 「召回」「提示词」「模型」「token」 |
| 疑点（`doubts`，独立区域） | 「未发现 XX」（正文内，只可进疑点区） |
| `Divergence` 差异点 | `doc_id` / `charStart-charEnd` |

## 十三、与既有文档的口径关系

### 13.1 逐项差异对照表

> 判定列三值：**沿用**（本设计与之一致）/ **修订**（本设计明确改了它，且给出理由）/ **冲突待裁定**（两者不能同时成立，需用户裁决）。

### 16.3 审核计划 = 部门归一最高权威来源（★ 2026-11-26 决定性，零猜测）

> **用户原话**：「审核计划是审核员制定的，他们其实已经将条款和部门信息制定好了，我们直接拿来用就可以了，不用猜，因为先制定计划，再开始检查。」
> 本节把这句话落成字段级接入口径。

**A. 为什么它是最权威（业务时序决定）**

审核的**业务时序 = 先制定计划 → 再逐条检查**。制定计划时，审核员已按**标准条款**逐条勾选**受审核部门**（谁负责这条、要去哪个部门查）。因此「条款 ↔ 部门」这层映射在**检查开始之前就已被人工确认**，是**确定性事实**，不是需要模型推理的未知量。**能拿到计划就绝不猜。**

**B. 数据源实测（`cert_audit_plan` + `cert_audit_plan_detail`）**

| 表 | 实测 | 说明 |
|---|---|---|
| `cert_audit_plan` | **3 行**（1 `closed` + 2 `active`），均属企业 `7f9c7fa3…`、标准 `iso9001` | 计划头：`EnterpriseCode` / `Standards`(→`cert_iso_standard.Code`) / `AuditYear` / `Status` |
| `cert_audit_plan_detail` | **70 行**，**100% 有 `ClauseNumbers` + 100% 有 `DeptNames` + 100% 有 `Departments`** | 计划明细：**一行 = 一组条款 ↔ 一组部门** |

明细列语义（实测确认）：

| 列 | 语义 | 实测样例 |
|---|---|---|
| `PlanCode` | 所属计划（`cert_audit_plan.Code`） | `35658996e78c…` |
| `ClauseNumbers` | **条款编号**（逗号分隔） | `4.1` / `5.3` / `7.1.5.1` / `4.4.1,4.4.2` |
| `Departments` | 部门 **Code**（逗号分隔，指向 `cert_enterprise_dept.Code`） | `c670f7dca389…,e58000248c12…` |
| `DeptNames` | 部门 **名**（逗号分隔，人可读、**干净**） | `管理层` / `管理层,综合部` / `品质部` |
| `ClauseRefsJson` | 条款引用明细（JSON） | — |
| `OwnerCode` / `OwnerName` | 该细则责任人 | — |

实测 `DeptNames` 全部取值仅 **6 个、零脏值**：`管理层 / 综合部 / 生产部 / 品质部 / 销售部 / 采购部`。**与 `cert_enterprise_dept` 的脏值（流程名「生成过程/校验过程」、同义并存「管理层/总经理/管理者代表」）形成鲜明对比** —— 审核员填的是「受审核组织单元」，天然规范。

> ⚠️ **数据质量小瑕疵（不阻塞）**：70 行中 **7 行** `ClauseNumbers` 带 `e ` 前缀（如 `e 4.1,e 4`），疑似历史导入残留。接入时对 `ClauseNumbers` 做**规范清洗**（去 `^e\s+` 前缀）即可，**不影响「条款 ↔ 部门」的确定性**。

**C. 接入口径（Stage1 第 2 层直接用，不推理）**

```
第 2 层部门过滤（审核场景）：
  plan   = cert_audit_plan WHERE EnterpriseCode=<企业> AND Standards=<标准Code> AND Status='active'
  detail = cert_audit_plan_detail WHERE PlanCode=plan.Code            // 70 行量级，一次取回
  // ① 建「条款号 → 部门名集合」倒排（先清洗 e 前缀）
  clause2depts = GroupBy(detail, d => 拆分(d.ClauseNumbers)) → 合并(d.DeptNames)
  // ② 条款侧部门范围直接读它，无需语义推理
  for 条款 C in 本次检查范围:
      C.DeptScope = clause2depts[C.ClauseNumber]                     // 命中即用
      若未命中 → 回退 ② 质量手册职能分配表 → ③ DeptDuty 语义（记账）
```

**关键点**：

- **条款侧**（标准条款该由哪个部门负责）与**文档侧**（某份文档属于哪个部门）**共用同一份 `clause2depts`** ⇒ 两侧口径天然一致，**不可能错配**。
- `DeptNames` 已是**企业真实部门名**，**跳过「抽象职能 `FN_*` → 企业部门」的归一推理** —— 这正是用户要的「不用猜」。
- 只有该企业该标准**无审核计划**时，才降级到 ②/③，并**记账**（哪条条款、为何降级）。

**D. 降级链（同一方式的分级，非并行投票）**

| 优先级 | 来源 | 性质 | 触发 |
|:--:|---|---|---|
| ① | `cert_audit_plan_detail`（审核员已填） | **确定性、零模型** | 审核场景默认（先定计划再检查） |
| ② | 质量手册「0.6 职能分配表」 | 确定性 | 无审核计划（如预审 / 首次接触） |
| ③ | `cert_enterprise_dept.DeptDuty` 语义推理 | 语义 | 前两者皆缺，**必须记账** |

> 与 §4.4 优先级表一致。① 是**常态**（只要有审核计划就一定走它），②③ 是**例外路径**。

**E. 对顾虑 W4 / W5 的消解**

- **W4（部门归一源缺失）**：实测 `cert_audit_plan_detail` **70 行 100% 覆盖「条款 ↔ 部门」**，且审核流程**必然先有计划** ⇒ 归一源在审核场景**不缺失**。质量手册职能分配表降为**次选**，不再是唯一依赖。
- **W5（职能 vs 部门实例跨企业泛化）**：审核计划里的 `DeptNames` **就是本企业真实部门**，直接消灭「`FN_*` → 企业部门」这一步跨企业泛化 —— 泛化风险仅存在于**无计划的例外路径**。
