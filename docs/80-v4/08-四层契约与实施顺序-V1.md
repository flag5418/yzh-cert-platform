# 08 · 四层契约与实施顺序

> **2026-11-23 修订**：本文 §二（补 3 条）、§四（结论算 nc/ofi/pass）、§六 D1（OwnerDept 35%）、§九（6 周 5 条款）**已被 `09-对接属性与召回路线-V1.md` 修订**。

> 本文回答四个问题，每个都只答一件事：
> ① 属性池 / 文档模型 / 审核发现 / 审核证据生成，各自**回答什么、存什么、存多细、谁消费、不许存什么**；
> ② 现在**实测坏在哪**（带数据，不是感觉）；
> ③ 先分析文档还是先人工测试（答案是：**都不是**）；
> ④ 单人 6 周怎么排，每道门的判据与止损条件。

## 零、一句话结论

四层不是四个模块，是**同一条判据逐层收窄**：

```
L1 这条条款要求什么      → 标准级，跨企业恒定，已 100% 覆盖（240 叶子 × 9 属性）
L2 这家企业有什么        → 企业级，缺"地址"和"权威映射"
L3 这份文档证明了什么    → 计划级，表是空的（0 行）
L4 报告里写哪一句        → 报告级，不存在
```

**现在的瓶颈不在 L1，在 L2 的"地址"（anchor）和 L1 的"期望清单"（EvidenceKinds）。**
L3 / L4 不是写不出来，是**没有可判的东西**：56 个检查项里 50 个从没跑过，跑过的 6 个输入里只有手册。

## 一、四层契约总表

| 层 | 唯一问题 | 载体 | 粒度（唯一键） | 生命周期 | 消费点 | 严禁存 |
|:--:|---|---|---|---|---|---|
| **L1** 属性池 | 这条条款**要求什么** | `cert_clause_attr_def` + `cert_clause_attr` | (标准, 条款号, 属性码) | 改标准才变 | 装配器、缺口计算、抽样 | 企业名、文档名、结论、疑点 |
| **L2** 文档模型 | 这份文档**是什么、有什么** | `cert_document_extraction.ContentJson` + `cert_enterprise_doc.MarkdownPath` | (文档, 块) | 企业资料变才变 | 召回、L3 输入 | 结论、符合性、条款判定 |
| **L3** 审核发现 | 这份文档**证明了什么、缺什么** | `cert_evidence`（`EvidenceKind=doc_fact`）+ `cert_point` | (检查项, 条款, 文档, 块, 抽样号) | 每次分析重算 | L4 装配、审核员复核 | 报告句式、章节顺序 |
| **L4** 审核证据 | 这次审核**能写进报告的是哪句** | `cert_report_clause_map` + 模板 | (报告, 条款, 句序) | 每次出报告重写 | 报告导出 | 新事实（只能引用 L3） |

### 1.1 为什么必须分四层：稳定性不同

| 层 | 换机构 | 换标准 | 换企业 | 换计划 |
|---|:--:|:--:|:--:|:--:|
| L1 | 不变 | **重灌** | 不变 | 不变 |
| L2 | 不变 | 不变 | **重抽** | 不变 |
| L3 | 不变 | 不变 | 不变 | **重算** |
| L4 | **换模板** | 不变 | 不变 | 重写 |

这张表就是分层的理由：**四层的失效条件完全不同，混在一起必然互相拖累**。
现在 `CertCheckResult` 一行里同时存了 `Reason`（L3 事实）、`AiConclusion`（L3 判断）、`DoubtsJson`（L3 疑点），三者失效条件不同却共用一行 —— 这是 58/58 那个现象的结构性原因（见 §四）。

### 1.2 层间只允许一种数据流

```
L1 ──(条款号 + 期望清单)──→ 召回 ──→ L2 ──(块 + 锚点 + 表行)──→ L3 ──(证据行 id)──→ L4
                                      ↑                              │
                                      └──── 缺口反查（缺哪类）────────┘
```

**L4 不许直接读 L2。** 一旦允许，模型就会绕过"证据行"直接抄原文，可溯源性立刻失效（07 号 §12 记的"手册证据变成标准条文"就是这么来的）。

## 二、L1 属性池：**不用重灌，只补 3 条**

### 2.1 实测（2026-11-23）

| 事实 | 数值 | 结论 |
|---|---|---|
| 条款总数 | 846 行 | 含章/节节点 |
| 叶子条款 | 240（9001:68 / 13485:75 / 14001:49 / 45001:48） | 与后台树显示一致 |
| 属性定义 | 11 条（9 描述 + Artifacts/EvidenceChain 各 3 行遗留） | 9 条是主力 |
| 有效属性值 | 2160 行 = **240 × 9** | 四标准叶子 **100% 覆盖** |
| 被软删的行 | 208 对（2026-11-14 清理） | 历史重复，不是缺口 |
| `EvidenceContract` | **0 行** | 定义了从没用过 |

**所以"重灌 846 条款"是伪需求。** 池子已经满了，问题在别处。

### 2.2 三个判断（都基于上表）

**判断一：`EvidenceForm` 是"取证动作"，不是"取证对象"，这是召回失明的直接原因。**

实测分布：`cite` 167 / `sample` 55 / `interview` 12 / `site` 6。

7.1.3（基础设施）的 `EvidenceForm = site`，含义是"去现场看"。但召回引擎需要知道的是"**看什么**"——设备台账、维护保养记录、维修记录。属性给不出，于是召回只能靠 `PrimaryClauses`，而 37 份记录里只有 1 份有这个字段。

> 一句话：**属性池回答"怎么查"，没回答"查哪份"，而召回需要的是后者。**

**判断二：`EvidenceFamily` / `Role` 有字典、能用，但太粗。**

字典实测存在且完整：`f1` 制度族 / `f2` 执行族 / `f1f2` 混合族；`r1` 情境 … `r7` 改进。
它们能回答"这条款该看制度还是看执行"（有用），但回答不了"看哪一份"（不够）。

**判断三：真正缺的是"期望清单"，缺了它，疑点只能是空话。**

现在疑点的实际长相（7.1.5.1 真实输出）：

> 「程序文件缺失：《01管理手册QMS.doc》提及《监视和测量设备控制程序》但未提供该程序文件本身」

这句话**没有说缺的是哪一份、编号是什么、应该由谁提供**。因为系统根本不知道 7.1.5.1 应该有哪些文件。没有期望，就只能说"缺证据"。

### 2.3 只补 3 条（不是 12 条）

| 属性码 | 值类型 | 回答什么 | 为什么非它不可 |
|---|---|---|---|
| `EvidenceKinds` | json | 这条款**应有**哪几类材料（受控词表 + 名称关键词） | **缺口与疑点的唯一来源**。没有它，"缺证据"永远泛泛 |
| `SamplingHint` | json | 最少抽几份 / 按什么维度抽（部门/期间/类型） | 报告里"抽3份"这句话的判据 |
| `JudgeLevel` | dict | A 结构可判 / B 关系可判 / C 价值判断 | 决定这条款**要不要进自动分析**（C 级直接跳过，省 25% 成本与误判） |

三条都是**静态判据**（跨企业逐字相同），符合属性池的定位，不违反 2026-11-10 的收敛裁决。

`EvidenceKinds` 的值形如：

```json
{ "kinds": ["ledger","certificate","record","maintenance"],
  "nameHints": ["检测设备台账","校准证书","期间核查","维护保养"] }
```

`kinds` 走字典（`dict_evidence_kind`，约 10 个码：manual/procedure/instruction/ledger/certificate/record/report/list/plan/policy），`nameHints` 只做匹配提示，不做判定。

### 2.4 回填成本（可算）

- 240 叶子 × 3 属性 = **720 行**
- 现有 `ClauseAttrGenerateService` 实测 5 并发、单条约 2.6s ⇒ 720 行 ≈ **6–8 分钟**
- 人工抽检 24 条（10%），每条约 1 分钟 ⇒ **半小时**
- **不需要改表结构**（`cert_clause_attr` 已经是 (标准, 条款, 属性码) 三元组）

## 三、L2 文档模型：三个"零模型"修法

### 3.1 实测

| 事实 | 数值 | 含义 |
|---|---|---|
| 提取记录 | 99 份（97 done / 2 skipped） | 98 个不同文件名（手册重复 1 份） |
| 有 `ModeOutput` | 88 份（11 份旧格式，只有 `Clauses[]`） | 两代格式并存 |
| 有 `PrimaryClauses` | 45 份 | 条款轴召回可用 |
| 有 `SupportClauses` | 29 份 | — |
| 有 `Clauses[]` 切片 | **13 份** | 装配真正能用的只有 13 份 |
| 37 份记录中有 `PrimaryClauses` | **1 份** | 记录几乎全在条款轴外 |
| `OwnerDept` 与**所属条款的受审部门**无交集 | 7.1.3（生产部,品质部）× 设备台账（设备管理部）= 0；9.1.2（销售部）× 顾客满意度调查表（品质部）= 0 | 部门名在企业树里存在，但与该条款的受审部门对不上 |
| `MarkdownPath` 非空 | **99/99** | **锚点可以回填，不需要重抽** |

最后一行是本文最重要的一条技术事实：**转换后的 Markdown 全都还在**。所以"锚点"不是一个需要重跑模型的工程，是一次字符串搜索。

### 3.2 修法一：锚点回填（1 天，零模型）

现状的"定位"是假的：

> 定位片段：7.1.5.1 总则 建立、实施并保持……　**未核验原文，待核实**

它不是地址，是一段摘要。地址必须是可计算的：

```json
{ "DocCode": "…", "BlockId": "b_0042",
  "CharStart": 18422, "CharEnd": 18610,
  "HeadingPath": ["7.1.5.1 总则"],
  "Verify": "exact" }   // exact | fuzzy | failed
```

做法：拿 `Snippet` 在 `MarkdownPath` 的全文里做 `IndexOf`，命中即写偏移，未命中标 `failed`。
**验收口径**：99 份文档的现有 Excerpts 中，`Verify=exact` 的比例 ≥ 95%。这是纯离线校验，可反复跑。

### 3.3 修法二：用企业自己的《记录清单》替掉模型的猜测（2 天，零模型）

科斯亚的 `04-记录文件/11文件化信息控制记录/07记录清单.docx` 是一张 53 行的表：

| 记录编号 | 记录名称 | 保存期限 |
|---|---|---|
| KSY-QMS-P-01-01 | 外部因素识别监视评价总清单 | 3年 |
| KSY-QMS-P-05-01 | 设备台账 | 3年 |
| KSY-QMS-P-05-02 | 设备日常维护保养记录 | 3年 |
| KSY-QMS-P-09-01 | 年度培训计划表 | 3年 |

这张表一次修掉三个缺陷：

| 缺陷 | 现状 | 用记录清单后 |
|---|---|---|
| 记录无条款映射 | 1/37 | **编号前缀 `P-05` → 程序文件 05 → 该程序覆盖的条款**，确定性推导 |
| `OwnerDept` 错 35% | 模型猜 | 程序文件的"职责"章节 + 手册职能分配表，**企业自己写的** |
| 无保存期限 | 空 | 表里就有（3年），直接进 `RecordRetention` |

关键点：**`P-xx` 不是我们发明的规则，是企业编号体系本来的结构。** 记录编号 `KSY-QMS-P-05-02` 的含义就是"第 05 号程序文件的第 02 号记录"。

这条规律对三家案例企业都成立，但**写法各不相同**，所以必须是配置而不是写死正则：

| 企业 | 程序文件 | 其下的记录 |
|---|---|---|
| 科斯亚 | `KSY-QMS-P-05` | `KSY-QMS-P-05-02` |
| 双尼 | 目录 `11 与顾客有关的过程` | `11-4客户满意度分析报告` |
| 尚龙 | 待核（13485 体系，编号另成一套） | — |

⇒ 落成一张 `doc_number_rule`（企业 + 正则 + 程序分组 + 记录分组），三家各一行。**没有这行配置就退回人工**，⛔ 不要用一条正则硬套所有企业。

**这是整个 V4 里性价比最高的一件事**：2 天，零模型调用，一次修三个缺陷，而且产出的是**权威数据**而不是模型猜测。

### 3.4 修法三：部门对齐（半天，零模型）

`cert_enterprise_dept` 有 14 行（科斯亚的真实部门树）。抽取输出的 `OwnerDept` 是自由文本，产生"设备管理部"这种企业里不存在的部门。

改法：模型只能**从给定候选里选**，不能自由生成。

```json
{ "OwnerDeptCode": "…", "OwnerDeptName": "生产部",
  "DeptSource": "enterprise" }   // enterprise | inferred
```

`inferred` 的进人工复核队列，`enterprise` 的直接用。
**验收**：`DeptSource=enterprise` 的比例 ≥ 80%；`inferred` 里错的不超过 20%。

### 3.5 检索三轴（替代现在的"条款轴独木桥"）

```
条款轴   PrimaryClauses 命中            → 制度类（手册/程序/指导书）
过程轴   ProcessArea ∈ 条款的 Process   → 执行类（记录/台账/报告）
部门轴   OwnerDept ∈ 检查项的部门        → 收窄
```

三轴取并集，再按 (体裁, 部门, 期间) 去重排序，配额：制度类 ≤ 3 份、执行类 ≤ 6 份。
**这是 03 号 D1 的正式化**，但补了一条 03 号没写的：**没有 `EvidenceKinds` 就无法算缺口**，所以 L1 必须先补（见 §二）。

## 四、L3 审核发现：拆成两段，结论由代码算

### 4.1 实测（这是全文最硬的一条）

| 事实 | 数值 |
|---|---|
| `cert_check_result` | 72 行 |
| `AiConclusion = ofi` | **58** |
| `AiConclusion = pass` | 16 |
| `AiConclusion = NULL` | 3 |
| 有 `DoubtsJson` 的行 | **58** |
| **有疑点的行 ∩ ofi 行** | **58（完全重合，1:1）** |

**"有疑点"和"判观察项"是同一个事件。** 这不是模型不会判，是代码把它们焊死了。

同时：`cert_evidence` 0 行、`cert_point` 0 行、`cert_check_analysis_evidence` 0 行。
**"审核发现"这一层在库里根本不存在** —— 只有一段自由文本 `Reason` 和一个 JSON 字符串 `DoubtsJson`。

### 4.2 两段式：Finding 与 Doubt 分开

| | Finding（证据行） | Doubt（疑点） |
|---|---|---|
| 回答 | 这份文档**写着什么** | **期望的**和**实际的**差在哪 |
| 有无判断 | **无**（纯事实） | 有（差异） |
| 粒度 | (检查项, 条款, 文档, 块, 抽样号) | (检查项, 条款, 疑点类型, 期望种类) |
| 来源 | L2 的块/表行 | L1 的 `EvidenceKinds` − L3 的 Findings |
| 为空意味着 | 没查到（本身是疑点） | 没问题（正常，占 80–90%） |

**Finding 契约（字段级）**

```
EvidenceItem {
  CheckItemCode, ClauseNumber,
  DocCode, BlockId, Anchor{start,end},
  Role: basis | execution | conclusion | site,   // 决定进 L4 的哪一句
  SampleNo,                                       // 0=整体，1..N=抽第几份
  Claim,                                          // 一句话事实，不含"符合/不符合"
  Fields: [{name, value, isBlank}],               // 表行字段；空值也是事实
  Period: {from, to}
}
```

**Doubt 契约**

```
Doubt {
  CheckItemCode, ClauseNumber,
  Type: missing_expected | inconsistent | expired | unverified,
  Expect: {kind, nameHint},        // 来自 L1 EvidenceKinds
  Found:  {docCode?, blockId?},    // 实际命中的是什么（可空）
  Level: critical|major|minor,     // 来自 L1 Severity，⛔ 不由模型定
  NeedsOnsite: bool
}
```

### 4.3 断掉 `doubts ⇒ ofi`（约 30 行代码）

结论由代码算，模型只出 Finding 和 Doubt：

```
if 存在 Level=critical 且 !NeedsOnsite        → nc(critical)
elif 存在 Type=missing_expected 且 Obligation=shall → nc(minor) 或 ofi（按机构阈值）
elif 存在 Type=inconsistent                    → ofi
elif 只剩 NeedsOnsite=true 的疑点              → pass + 待核事项（⛔ 不翻 ofi）
else                                           → pass
```

**关键一行是 `NeedsOnsite`**：现场才能核实的事，不该在资料评审阶段变成观察项。
现在 58 条疑点里大量是"未进行面谈""未观察现场活动"—— 这类疑点**永远无法在资料阶段消除**，所以每条条款必然 ofi。这是 58/58 的第二个成因。

两个成因必须一起修：
- 成因一（主因）：输入只有手册 ⇒ 每条都"缺实施证据"。修法在 §三。
- 成因二（次因）：`NeedsOnsite` 也翻 ofi ⇒ 即使输入修好，仍会 100% ofi。修法在本节。

### 4.4 疑点必须指向一个具体的东西

对比：

| 现在（泛泛） | 改后（具体） |
|---|---|
| 程序文件缺失 | 缺《监视和测量设备控制程序》(KSY-QMS-P-03)，应覆盖 a) 适用性 b) 维护 |
| 实施证据缺失 | 缺 `ledger` 类：检测设备台账；缺 `certificate` 类：校准/检定证书 |
| 现场活动未验证 | 待核（现场）：观察品质部在用检测设备的校准标识与有效期 |

差别不在措辞，在**能不能被核对**。左边专家没法用（不知道到底缺什么），右边专家可以直接去要。

### 4.5 载体决策：`cert_evidence` 扩语义，不新开表

| 方案 | 利 | 弊 |
|---|---|---|
| 新表 `cert_finding` | 语义干净 | L4 要在同一句里引用文档事实与现场证据 ⇒ 两次 join；`cert_check_analysis_evidence` 要改指向 |
| **扩 `cert_evidence`（选它）** | 已有 `Anchor`/`Snippet`/`ClauseNumber`/`CheckItemCode`/`ContentMD5`/`LlmSummary`/`Status`；0 行，改语义零迁移 | 需修订 48 号 §3.9 ③ 的表述 |

修订后的口径：`cert_evidence.EvidenceKind` 取 `doc_fact`（自动，文档事实行）/ `manual`（人工补充）/ `interview` / `sample` / `onsite_media`。
**同表不同 kind**，而不是"文档切片不进证据表"。理由：L4 的"每句必须挂证据 id"校验只能对一张表做。

## 五、L4 审核证据生成：90% 装配，10% 润色

### 5.1 真实报告只有四类句子（05 号 §4.1 已验证）

| 角色 | 句式 | 来源 Finding 的 `Role` |
|---|---|---|
| ① 制度依据 | 查见《X》（编号），规定了…… | `basis` |
| ② 执行证据 | 抽查 N 份《Y》，其中…… | `execution` |
| ③ 结论证据 | 查见《Z》，结论为…… | `conclusion` |
| ④ 现场证据 | 现场查见……（见照片 N） | `site` |

**没有第五类。** 这是从三份真实报告 + 一份 80 页底稿里数出来的，不是设计出来的。

### 5.2 空白率是特性，不是缺陷

科斯亚 31 页报告：32 个条款段、约 3.7 万字证据、仅 5 处"符合要求"+2 处"基本符合要求"、**0 处"符合 ISO 第 X 条"**。

脱敏版《行政部B组》更直接：11 个条款标题里，`7.1.2` 和 `7.1.6` **只有标题，没有任何内容**。

> 所以 L4 对 80–90% 的条款，**正确输出是空**。
> 把"没内容"当失败，就会逼模型编 —— 这是 V3 全线 ofi 的另一面。

### 5.3 装配契约（防编造的唯一手段）

```
ReportSentence {
  ClauseNumber,
  Role,                     // basis|execution|conclusion|site
  Text,                     // 渲染后的一句
  EvidenceIds: [ ... ],     // ⛔ 至少 1 个，为空则该句丢弃
  TemplateCode, TemplateVersion,
  RenderedBy: template | llm_polish
}
```

三条硬校验（代码，非提示词）：
1. `EvidenceIds` 为空 ⇒ 丢弃该句（不是报错，是静默丢）；
2. `Text` 里的每个专有名词（书名号内、编号、日期、数字）必须能在所挂 EvidenceItem 的 `Claim`/`Fields` 里找到原文 ⇒ 否则丢弃；
3. `Role=basis` 的 `DocCode` 必须是企业文档，⛔ 不能是标准原文（拦 07 号 §12 的"引标准条文"错）。

**模型的唯一职责**：把 3 个 Finding 连成一句通顺的话。它不改数字、不加结论、不换主语。

## 七、实施顺序：既不"继续分析文档"，也不"直接人工测试"

你问的三选一，答案是第三件事：**先建金标准集**。

### 7.1 为什么"继续分析文档"不收敛

已经读了 3 家企业、300+ 份文件、4 份报告（含 1 份 80 页底稿）。再读第 4 家，边际收益趋零 —— 因为缺的不是样本，是**尺子**。

分析的产出如果不落成"断言"（这一条款，期望的证据是哪几行），下次改代码时它不能复用，等于白读。

### 7.2 为什么"直接人工测试"判不出对错

现在打开系统点"分析"，跑出来的东西**没有期望值可比**。你只能说"感觉不对"，说不出"少了第 3 行"。
而且同一检查项跑两次结果会变（温度、召回顺序），没有固定输入就没有可重复的测试。

### 7.3 金标准 = 把"文档与报告的关系"固化成可执行的断言

一份金标准文件，每条款四段：

