# 09 · 对接属性与召回路线

> 08 号回答了"四层各存什么"，本文回答**层与层之间靠什么连**。
> 结论先给：四层的内部契约基本没问题，**断在连接键上**。而且断点有确凿反例（§零）。

## 零、一个反例，足以定优先级

系统对 **7.1.5.1** 的实际输出（`cert_check_result`，2026-11-21）：

> 未采集到《监视和测量设备控制程序》文件、**监视和测量设备台账、校准/检定证书**、期间核查记录、维护保养记录、设备使用前适用性确认记录等支撑性成文信息

而库里实际有（`cert_document_extraction`）：

| 项 | 值 |
|---|---|
| 文件 | `校准证书管理与预警台账(3).pdf` |
| 抽取状态 | done |
| 记录 | 设备校准状态跟踪表 |
| 行数 | **19 行** |
| 字段 | 序号 / 仪器设备名称 / 设备编号 / **校准证书编号** / **校准日期** / **有效期至** / 剩余天数 / 状态 |
| 首行 | 二次元 · 20240701127 · LX168-263076730 · 2026-05-15 · 2027-05-14 · 正常 |
| 部门 | 品质部（= 7.1.5.1 的受审部门，交集非空） |
| PDCA | 执行 |

**证书在库里，19 条，编号日期有效期齐全；模型说"未采集到校准证书"。**

这一条把优先级钉死了：**问题不在抽取质量，不在提示词，在"没接上"。**
所以第一件事不是重抽、不是换模型，是**把已有的 19 行接进 7.1.5.1**。

## 一、四条补充意见的落点

| # | 你的意见 | 采纳后的改动 | 落在 |
|:--:|---|---|---|

## 二、修正一：默认符合，`AiConclusion` 应当**删除**

### 2.1 口径

```
默认：所有检查项 = 符合
证据：全部来自企业文档的事实行（EvidenceItem）
例外：只有"应有未见"和"前后矛盾"两种，且都叫"待核"，不叫"不符合"
NC：只能由专家签发（现在的工作台第 3 步已经是这样）
```

这个口径下，**系统不产出"结论"**，所以 `AiConclusion` 这个字段没有存在的理由。

### 2.2 为什么是删，不是修

| 方案 | 结果 |
|---|---|
| 修映射（把 ofi 拆成 nc/ofi/pass） | 仍要求模型对每条条款表态 ⇒ 仍会 58/58 |
| 加阈值、加规则后处理 | 治标：模型先给一个错判断，再用规则纠正，两套逻辑打架 |
| **删掉，只留事实** | 模型不再有"表态"的机会，58/58 从结构上不可能发生 |

现在 `cert_check_result` 72 行里 58 行 ofi，不是模型判错，是**它被要求判，而它只有手册可看**。

### 2.3 `CertCheckResult` 一行的拆法（字段级）

| 现字段 | 处置 | 去处 |
|---|---|---|
| `Reason`（自由文本） | 降级为**渲染结果**，不独立存判断 | 由 `EvidenceIds` 渲染；无证据则必须为空 |
| `AiConclusion` | **删** | 换 `DerivedState`（代码算）+ `DerivationJson`（命中哪条规则） |
| `DoubtsJson` | **拆表** | `cert_point`，每条疑点一行（Type / Expect / Found / Level） |
| `PrepState` | 保留 | 仍是流程状态（未分析/已分析/已锁定） |
| `Conclusion` | 保留 | 人工判定，默认空 = 符合 |
| — | 新增 | `EvidenceIdsJson`（本次判定引用了哪几行证据） |

`DerivedState` 只有 4 个值：

| 值 | 条件 | 界面表现 |
|---|---|---|
| `default_conform` | 无缺口 | "符合"（默认，不需要人点） |
| `gap_required` | 应有未见，且 `Obligation=shall` | "待核"（黄） |
| `gap_optional` | 应有未见，且 `Obligation≠shall` | "提示"（灰） |
| `not_applicable` | `Applicability=conditional` 且条件不成立 | "不适用" |

> 注意：**没有 `nc` 这个值**。NC 是专家签发的实体，不是系统算出来的状态。

### 2.4 界面上的连带改动（三处，都不大）

| 位置 | 现在 | 改成 |
|---|---|---|
| 工作台"判定结论"列 | 待判定 / 观察项 / 建议 | `DerivedState` 四值：符合（默认）/ 待核 / 提示 / 不适用 |
| 详情抽屉"疑点分析（N 条）" | 系统疑点，来自 `DoubtsJson` | **缺口清单**，每条带"应有 / 实有 / 差在哪"三列 |
| 详情抽屉"审核证据（判定依据）" | 一段自由文本 `Reason` | **证据行表格**（19 行 × 字段），每行可跳原文锚点 |

第三处是关键：把"一段话"变成"一张表"，专家才有可能核对。这也是"默认符合"能成立的前提 —— 符合不需要理由，但**需要证据**。

## 三、对接层：条款侧 × 文档侧

### 3.1 四层契约缺的是什么

08 号定义了每层"存什么"，但没定义**层与层靠哪个字段对上**。缺了这张表，装配时只能靠猜 —— 这就是"召回的几条路"没有真正接通的原因。

**连接键（Join Key）不是属性，是契约**：条款侧和文档侧必须用**同一个键名、同一套码值**，否则永远对不上。

### 3.2 六个连接键

| 键 | 名称 | 条款侧 | 文档侧 | 用途 |
|:--:|---|---|---|---|
| **K1** | 条款号 | `ClauseNumber` | `PrimaryClauses[]` | 手册/程序 → 条款 |
| **K2** | 过程 | `Process[]`（码） | `ProcessArea`（需归一） | 记录 → 条款 |
| **K3** | 部门 | 计划明细 `DeptNames` | `OwnerDept`（需对齐） | 收窄 |
| **K4** | 编号 | `EvidenceKinds.nameHints` | `DocNo`（**缺**） | 记录 → 程序 → 条款 |
| **K5** | 期间 | 检查项的审核期间 | `CoveragePeriod`（68/99 空） | 时效判定 |
| **K6** | 作用 | `EvidenceForm` / 报告角色 | `DocFunction`（**缺**，现为 8 个自造值） | 选句式 |

### 3.3 条款侧：`RecallRoutes` 由现有属性**推导**，不新增生成

你说"条款上要有明确标识，说明这条款适合用什么方式找证据"。这条不需要再跑 720 行 AI —— 现有三个属性已经蕴含了答案：

```
EvidenceFamily = f1  (制度族，145 条)   → 路线 clause
EvidenceFamily = f2  (执行族，29 条)    → 路线 process + dept
EvidenceFamily = f1f2(混合族，66 条)    → 路线 clause + process
EvidenceForm  = site                    → 追加路线 site
Role          = r5   (运行，55 条)      → 追加路线 docno
```

145 + 29 + 66 = 240，与叶子条款数一致，**推导是完备的**。

`RecallRoutes` 落成 `cert_clause_attr` 的第 10 条属性（json 数组），一次 SQL 就能算完：

```sql
INSERT INTO cert_clause_attr (...)
SELECT StandardCode, ClauseNumber, 'RecallRoutes',
       JSON_ARRAYAGG(...)   -- 按上面五条规则拼
FROM cert_clause_attr WHERE AttrCode='EvidenceFamily' GROUP BY ...
```

**成本：一条 SQL，0 次模型调用。**

### 3.4 文档侧：6 个键里 4 个已有，2 个缺

| 键 | 字段 | 实测 | 缺什么 |
|:--:|---|---|---|
| K1 | `PrimaryClauses` | 45/99 有（记录仅 1/37） | 记录类的条款号（靠 K4 推导，不靠模型） |
| K2 | `ProcessArea` | 82/99 有值，但只有 **9 个自由文本**（行政人事 22 / 检验过程 14 / 生产过程 13 / GM/MR 11 / 销售过程 9 / 仓储/设备 8 / 采购过程 5 / 未标注 1 / 空 16） | **归一化到 `Process` 的码**（8 个值，一张映射表） |
| K3 | `OwnerDept` | 有值 | 与检查项部门**求交集**，交集为空就不召回（见 §3.7） |
| K4 | `DocNo` | **无** | 从文档头正则抽 `KSY-QMS-P-05-02` |
| K5 | `CoveragePeriod` | **仅 12/99 有真实日期**；68 份是空对象 `{Start:'',End:''}`；19 份无 ModeOutput | 记录类的期间；台账类改用**行内日期**（校准日期/有效期），比文档级更准 |
| K6 | `DocFunction` | 现为 `ReportRole` 7 个自造值 + `DocUse` 6 个值（两套重复） | 归并为 4 个值（见 §四） |

> K2 的映射表只有 8 行，是**纯配置**。做一次，四标准通用。

### 3.5 五条召回路线（路线 × 键）

| 路线 | 判据 | 用哪些键 | 适用体裁 | 现在可用度 |
|:--:|---|---|---|---|
| **R1 条款号** | 文档写了条款号 | K1 | 手册 / 程序 / 指导书 | 45/99 |
| **R2 过程** | 条款过程 ∩ 文档过程 | K2 | 记录 / 台账 / 报告 | 需归一（8 行映射） |
| **R3 部门** | 检查项部门 ∩ 文档部门 | K3 | 记录 | 需交集判定 |
| **R4 编号** | 记录编号 → 程序 → 条款 | K4 + 记录清单 | 记录 | 需抽 DocNo |
| **R5 现场** | 必须现场看 | — | 人工 | 不做 |

**取并集，再按 (体裁, 部门, 期间) 去重排序**，配额：制度类 ≤3 份、执行类 ≤6 份。

### 3.6 空召回必须**可见**

这是整套设计里最容易漏的一条：路线没命中时，现在的行为是**静默返回空**，然后模型说"未提供"。

改法：每条路线独立记账，进 `InputSnapshotJson`：

```json
{ "R1": { "hit": 3, "miss": 0 },
  "R2": { "hit": 0, "miss": 1, "reason": "ProcessArea='仓储/设备' 未映射到码" },
  "R3": { "hit": 0, "miss": 1, "reason": "设备管理部 ∉ {生产部,品质部}" },
  "R4": { "hit": 2, "miss": 0 } }
```

**有了这张账，"缺证据"就能区分成三种**：数据没有（真缺）/ 有但没接上（映射问题）/ 接了但模型没用（提示词问题）。现在这三种混成一句"未提供"，无法定位。

### 3.7 反例复盘：7.1.5.1 为什么断，7.1.3 为什么也断

| 条款 | 检查项部门 | 文档 | 文档部门 | 交集 | 结果 |
|---|---|---|---|:--:|---|
| 7.1.5.1 | 品质部 | 校准证书台账 | 品质部 | 有 | 本该召回，实际没召回 ⇒ 断在 R2/R4 未接 |
| 7.2 | 综合部 | 培训记录 | 综合部 | 有 | 同上 |
| **7.1.3** | 生产部, 品质部 | 设备台账 | **设备管理部** | **空** | **即使接通也召不回** ⇒ 需部门映射 |
| **9.1.2** | 销售部 | 顾客满意度调查表 | **品质部** | **空** | 同上 |

两种断法必须分开治：

- **接线断**（7.1.5.1 / 7.2）：数据齐、部门对，只是没进装配 ⇒ 改 `CertCheckContextBuilder`，1–2 天。
- **语义断**（7.1.3 / 9.1.2）：文档部门 ≠ 受审部门，但业务上就是该看这份 ⇒ 需要**部门映射表**（企业部门 → 受审部门，多对一），而不是改模型。

> 部门映射表是企业级配置（`cert_enterprise_dept` 加一列 `AuditDeptName`），14 行，一次配完。
> 这一步不做，R3 路线永远有一半条款召不回。

## 四、文档侧的"作用"：只有 4 种

### 4.1 现在有三套词表，互不对应

| 字段 | 值 | 个数 |
|---|---|---|
| `DocType` | document_control / procedure / policy / work_instruction / record / context_list / audit_record | 7 |
| `DocUse` | evidence / requirement / policy / audit_record / document_control / context_evidence | 6 |
| `ReportRole` | evidence_source / supporting_requirement / management_requirement / audit_evidence / documented_information_evidence / operation_basis / context_analysis_evidence | **7** |

三套都在描述"这份文档干什么用"，但没有一套等于报告的四类句子。

### 4.2 归并成 `DocFunction`（4 值，与报告角色 1:1）

| `DocFunction` | 含义 | 体裁 | 报告角色 |
|---|---|---|---|
| `basis` | 规定了什么 | 手册 / 程序 / 指导书 / 方针 | ① 制度依据 |
| `execution` | 做过的痕迹 | 记录 / 台账 / 签到 / 检验单 | ② 执行证据 |
| `conclusion` | 得出的结论 | 报告 / 评价 / 统计 / 分析 | ③ 结论证据 |
| `context` | 背景与识别 | 相关方清单 / 风险清单 / 环境因素 | 不进正文，进覆盖声明 |

归并规则可代码化（08 号 §3.3 的三信号法）：有具体数据 + 有签署 + 有覆盖期，命中 ≥2 → `execution`；全无 → `basis`。

### 4.3 "这份记录证明什么"是 L3 的事，不是文档的事

你说文档上要有"作用"。这里必须切一刀，否则会过度建模：

| 层级 | "作用"的含义 | 存在哪 |
|---|---|---|
| 文档级 | 它是**规定**还是**痕迹**还是**结论** | `DocFunction`，4 个值，一份文档一个 |
| 证据级 | 这一行**证明了哪一条要求** | `EvidenceItem.Claim` + 挂的条款号，一行一个 |

《培训记录》的文档级作用是 `execution`；它证明"7.2 能力"这件事，是那 33 行证据各自挂到条款上才算的。
**把"证明什么"塞进文档级字段，会退化成一份文档只能服务一个条款。**

## 五、PDCA 与语言套路

### 5.1 已经抽到了，只是没归一

`ModeOutput.PdcaPhase` 实测：执行 60 / 绩效 6 / 策划 5 / 改进、绩效 4 / 执行、改进 2 / 执行、绩效 2 / 执行、策划 1 / 策划、绩效 1 / 综合 1 / 未判定 1 / NULL 16。

**83/99 有值**，但是中文自由文本，且有 6 种组合值。归一成 4 位掩码即可（`P` / `D` / `C` / `A`，可多选）。

### 5.2 条款侧：`PdcaStage`

240 条款各标一个（`P` / `D` / `C` / `A`，主阶段）。可由 `Role` 推导，再人工校正 20 条：

| `Role` | 含义 | 默认 PDCA |
|---|---|:--:|
| r1 情境 | 组织环境 / 相关方 / 范围 | P |
| r2 领导 | 方针 / 职责 / 承诺 | P |
| r3 策划 | 风险 / 目标 / 变更 | P |
| r4 支持 | 资源 / 人员 / 知识 / 文件 | D |
| r5 运行 | 设计 / 采购 / 生产 / 交付 | D |
| r6 绩效 | 监视 / 内审 / 管评 | C |
| r7 改进 | 不合格 / 纠正 / 持续改进 | A |

### 5.3 (PDCA × 角色) → 句式矩阵

这就是你说的"不同场景下的语言套路"。真实报告的句子可以完全按这个矩阵生成：

| 条款 PDCA | 主角色 | 句式骨架 | 真实例 |
|:--:|---|---|---|
| **P** | basis | 查见《X》（编号/版本），规定了…… | 查见《人力资源控制程序》，规定了各岗位任职要求 |
| **P** | basis + execution | 经查，……已策划并形成文件；抽 N 份…… | 查见《2025-2026培训计划》，经批准后实施 |
| **D** | execution | 抽查 N 份《Y》，其中…… | 抽 3 次培训（2025.9.16 / 2026.3.25 / 2026.7.10），均有签到与效果评价 |
| **D** | execution（台账） | 查见《Y》，共 N 条，……齐全 | 查见《设备校准状态跟踪表》19 台，证书编号、校准日期、有效期齐全 |
| **C** | conclusion | 查见《Z》，结论为…… / 统计……，达标 | 查见《目标统计表》，2025.9-2026.6 考核均达标 |
| **A** | execution + conclusion | 针对……开具《NC》，已整改并验证 | 针对……，已制定纠正措施并验证有效 |

**四类角色 × 四个阶段 = 16 格，实际用到的约 8 格。** 8 个模板就是 L4 的全部资产，不是"让模型自由写"。

### 5.4 一句话记住分工

```
PDCA 决定"这段话该说什么"（P 说规定，D 说执行，C 说结论，A 说改进）
角色 决定"这句话从哪来"（basis 从程序，execution 从记录，conclusion 从报告）
模型 只负责把 2–3 个事实连成一句通顺的话
```

## 六、第一种文档：单表台账（校准证书台账）

### 6.1 为什么是它

| 候选 | 抽取质量 | 部门交集 | 期间 | 结论 |
|---|---|:--:|---|---|
| **校准证书台账（PDF）** | **19 行 × 8 字段，完全对齐** | 有（品质部） | 行内有日期 | **选它** |
| 设备台账（xlsx） | 19 行 × 6 字段，对齐 | **空**（设备管理部） | 无 | 次选（要先修部门映射） |
| 培训记录（docx） | 33 行 × **13 字段混了两张表** | 有（综合部） | 有 | 第三种（要先修多表拆分） |
| 程序文件 | 好 | — | — | 已在跑，不算新胜利 |

三条理由：

1. **抽取已经是对的**（19 行 × 8 字段），不需要碰模型，验证的是"接线"而不是"抽取"；
2. **每行自带证书编号 + 校准日期 + 有效期 + 状态**，正好是 7.1.5.1 要求的全部要素，不需要期间字段；
3. **有确凿的反例**（§零）：模型说"未采集到校准证书"，而它就躺在库里 —— 跑通它，等于把这个反例翻过来。

### 6.2 "跑通"的定义（五条，可验收）

## 九、今天做什么

不是写代码，是**跑一条 SQL 验证反例**：

```sql
-- 7.1.5.1 的受审部门 vs 校准证书台账的部门（已实测，返回「有交集 = 1」）
SELECT d.ClauseNumbers AS 检查项条款, d.DeptNames AS 检查项部门,
       x.OwnerDept AS 文档部门,
       (d.DeptNames LIKE CONCAT('%', x.OwnerDept, '%')) AS 有交集
FROM cert_audit_plan_detail d
JOIN (SELECT JSON_UNQUOTE(JSON_EXTRACT(ContentJson,'$.ModeOutput.OwnerDept')) OwnerDept
      FROM cert_document_extraction
      WHERE JSON_UNQUOTE(JSON_EXTRACT(ContentJson,'$.DocMeta.FileName')) LIKE '校准证书%') x
WHERE d.ClauseNumbers = '7.1.5.1' AND d.IsDeleted = 0;
```

把两处一起换，会看到 `有交集 = 0` —— 这就是"语义断"的那两条：

| 条款 | 文件名过滤 | 检查项部门 | 文档部门 | 交集 |
|---|---|---|---|:--:|
| 7.1.3 | `01设备台账%` | 生产部,品质部 | 设备管理部 | **0** |
| 9.1.2 | `01顾客满意度调查表%` | 销售部 | 品质部 | **0** |

交集非空 ⇒ 证明"数据在、部门对、就是没接上"，P1 的可行性成立。
交集为空 ⇒ 先配部门映射，再谈接线。
