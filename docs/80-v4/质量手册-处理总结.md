## 一、目标与设计口径（已固化）

- 体系认证平台从"录入系统"改造为**规则驱动**的证据链工具：先「认证发现」找事实与疑点，再「证据组织生成」精简成 400–500 字证据。
- 证据 **80–90% 来自企业文档**；现场发现/面谈当前不做、全部忽略。
- 单 ACM 机构、**ACM 三份报告第 4–5 章做唯一裁判**。
- 质量手册是**特例**：每家企业都准备、4–5 万字、章节复杂，必须单独优化。
- 质量手册是"**纲领**"：审核员靠它定位"每个检查项该读什么文档、哪个部门负责、何时发布"。所以应读章节/负责部门/前置事实**从手册解析**，不写死在提示词里。
- 工作方式：**大胆尝试、小心求证、直接调接口验证**，不空谈。

## 二、手册提取（时间 / 截断问题）

### 问题
- 手册 66578 字节，早期 `doc_clause_extract` 分 2 段，第 1 段（15000 字符，覆盖 0.x–5.x 密集章节）撞 **8192 token 输出上限被截断**，只救回 35 条，`4.4.2` 缺失。

### 修复
- `ClauseExtractExecutor` 改为**按 Markdown 标题切块**（`SplitByHeadings`/`SplitOversized`）。
- 关键参数：`ChunkChars=2800`、`MaxChunks=16`、`MaxConcurrentExtractCalls=8`、`Parallel.ForEachAsync`(8 并发)+顺序合并。

### 结果
- 11 块、8 路并发，总耗时约 **1 分 45 秒～2 分 24 秒**。
- **67 条条款**、`4.4.2` 已出现、无截断。

### 结论 / 遗留
- 提取已稳定可用，但 **"1 分钟内"未完全达成**；主要冗余是每块重复喂条款 Markdown 与条款清单。
- 提取链仍**硬编码 `MaxTokens=8192`**（未用 `ai_max_tokens=32768`）。

## 三、数据清洗（先定位、后清洗）

- 结论：**必须先清洗再入库**，下游证据发现/生成会直接逐字复用与定位，不再二次加工。
- 关键顺序：**定位用原文 → 清洗放在定位之后**。
  - 第一次在 `ReadClauses` 读模型输出时就清洗，导致 `LocateUnique` 逐字匹配失败（原文 `**a)**` 被洗成 `a)` 后定位不到）。
  - 最终改为：先拿原文做定位，再统一 `CleanText` 后写 `ContentJson`，`Start/End` 仍指向原文位置。
- `CleanText`：去 `▲△`、`|`、`**`、反引号、`<br>`、压缩连续空白、去零宽字符、逐行 trim 去空行。实测残留符号为 0。

## 五、事实证据提取属性 `EvidenceSources`

用户设计："每个条款一个事实证据提取属性 + 一个条款通用提取属性，没有事实属性就用通用属性"。

- 由 `ManualIndexParser.BuildEvidenceSources` **确定性派生**：应读章节（TocMapping 反查 + 前置事实章节）、负责部门（职能分配表）、命中的前置事实类型。
- 无映射时 `IsFallback=true` → 走条款通用提取。
- **父子粒度回退**：叶子条款 `4.4.1`/`5.2.1` 回退到 `4.4`/`5.2`，用 `BestPrefixKey`（最长前缀匹配）。
- `ClauseFactMap`：`4.1/4.2→公司简介`、`5.2→方针目标`、`5.3→部门职责`；`FactKeywordMap` 反查章节号。
- 实测：67 条 EvidenceSources，fallback 仅 `1`、`3` 两条。

## 七、证据发现 + 证据组织 两段式管线（已接线手册纲领）

代码位置：`CertCheckEngineService.RunTwoStageAsync` + `CertCheckContextBuilder`。

两段式：`clause_evidence_findings`（审核发现）→ `audit_check_evidence`（证据生成）。

本轮接线：
1. `CertCheckContextBuilder` 从 `ContentJson` 读出 `ManualIndex` + `EvidenceSources`，挂到每条条款（应读章节/负责部门/前置事实原文）。
2. 发现提示词喂入 `{{chapter_profile}}`（去哪找+谁负责）与 `{{doc_facts}}`（公司简介/方针目标/部门职责原文 + 手册封面 ManualMeta）。
3. 第一段输出的 `EvidenceFindings / Doubts / EvidenceAssembly` **拆成三段**分别喂给第二段（不再整包塞 JSON）。
4. 阶段映射（用户口径）：
   - **认证准备 = 认证发现**（无入场计划时，展示找到的事实 + 疑点）——⚠️ **尚未接线**，当前 prep 页仍是旧单段 `prep_state`。
   - **认证检查 = 证据组织生成**；直接操作认证检查时两步一起跑（`analyze-item StageKind=onsite`）。

## 八、证据编写原则（`audit_check_evidence` 提示词 v1.2）

用户口径：**证据正文纯正面、默认符合；疑点全部剥离单独给审核员参考；文件引用必须带全元数据**。

- 证据正文只写已确认的正面事实，禁止"未提供/未见/无签字/缺少/未体现/但…"等否定或存疑表述（一律进 `doubts`）。
- **文件引用必须带全元数据**：`《文件名》编号（版本，编制/审核/批准，日期）`，例：`《岗位职责和权限》KSY-QMS-WI-01（A/0，体系编写小组编制，潘明海批准，2026.6.10）`。
- 字数硬上限：每条条款证据 ≤ 200 字、整体 ≤ 500 字。
- 同类文件合并、不复述原文/方针全文、禁止把"【部门职责】"标注编造成文件名。
- 有 filled 记录写编号/日期/批号/签字/字段值；空白模板只写"建立了记录"，不写"已有效执行"。
