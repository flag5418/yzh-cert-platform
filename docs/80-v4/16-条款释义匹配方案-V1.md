## 一、要解决的问题（为什么不能"靠条款号"）

| 硬伤 | 证据 | 根因 |
|---|---|---|
| 记录类文档**完全不可达** | 全库 record 37 份，`PrimaryClauses/SupportClauses/Chapters` 三字段全空 ⇒ 条款召回召不回任何记录 | 记录文档没有条款号 |
| **条款号幻觉** | 出现 ISO9001 不存在的 `6.1.3`/`7.5.4`/`7.5.5`/`5.4.4` | 模型硬凑条款号 |
| **粒度错位** | 文档声明 `6.2`/`7.1.5`/`7.5.3`，检查项是 `6.2.1`/`7.1.5.1`/`7.5.3.1` ⇒ 匹配规则（等于或后代）判不中 | 模型给的粒度偏粗 |
| **多标准重复提取** | `cert_document_extraction` 按 `StandardCode` 存 ContentJson：97 文档 × 3 标准 = 291 次 LLM | 条款号是标准相关的，只能按标准各跑一遍 |

**结论**：条款号是"模型在提取期猜出来的标准相关产物"，本身不可靠且贵。改为**匹配期用条款释义反查**，可同时消除以上四点。

## 二、释义的三段与归位（核心修订）

用户口径：**释义 = 3 段**——① 条款的解释、② 条款需要什么证据、③ 条款如何找到证据；三段**落点不同**：

| 段 | 含义 | 落点 | 现状 |
|---|---|---|---|
| **① 条款解释** | 标准条款正文（GB/T 19001 原文） | `cert_clause_attr` 新增 `AttrCode='ClauseText'`；源 = `cert_iso_clause.Description`；**值为 JSON**（见 二.b） | **新建** |
| **② 需要什么证据** | 该条要求"哪一类证据"（族/形态） | **复用** `EvidenceFamily`(f1/f2/f1f2) + `EvidenceForm`(cite/sample/site/interview)；如需"清单式需求"再补 `EvidenceNeed`（提示词，可选） | 已有枚举 |
| **③ 如何找证据** | 从**哪条轴 / 什么键 / 什么体裁**找 | `RecallRoutes`（RM 轴 + 键 + **体裁白名单 = 文档画像**），由 `RecallPathResolver` 生成 | 15 号已设计 |

**三条判据（本次采纳）**：

1. **释义只承载 ①**。②③是条款的"取证规则"，本就属属性池，**不进释义**——避免把"怎么找"混进"是什么"。
2. **② 基本含在条款内容里**：条款正文已说清"要什么证据"，故 ② 以**枚举**归纳（现有 `EvidenceFamily/EvidenceForm` 即此），不另写长文；若个别条款需强调，再补一句 `EvidenceNeed` 提示词。
3. **③ 必须与"文档画像"对应**：找法不是凭空，而是「按什么画像去找这份文档」。画像 = 标准无关的 `{体裁(ExtractionMode), 过程域(ProcessArea), 记录名, 主题词}`；`RecallRoutes.DocTypes` 正是画像里的**体裁**维度。**换标准时画像不变、找法不变**。

> **权威源**：`cert_iso_clause.Description`（text，GB/T 19001 条款正文，质量高）。
> **与 `ClauseIntent` 的分工**：`ClauseIntent` = 意图摘要（≤72 字）；`ClauseText` = 完整正文（含 a/b/c 与注）。语义匹配用 `ClauseText`（词面覆盖更全），`ClauseIntent` 保留作提示用。
> **生成脚本**：`scripts/db/fix/2026xxxx_clause_attr_add_clausetext_V1.sql`（从 `cert_iso_clause` 灌入，幂等）。

### 二.b `ClauseText` 的 JSON 结构（采纳"释义结构可以是 json"）

`ClauseText.AttrValue` 存 JSON，便于承载条款的多段原文；BM25 语料 = 各字段拼接。

```json
{
  "Title": "6.1.2 组织应策划…",
  "Body":  "确定需要应对的风险和机遇…",
  "Items": ["a) …", "b) …"],
  "Notes": ["注：…"]
}
```

字段可空；后续新增字段不影响匹配（匹配取 `Title+Body+Items+Notes` 的连接）。

## 三、语义匹配 = 第 7 种召回方式 RM7（由**条款分类**驱动，非开关）

15 号的 `RM1–RM6` 是**确定性轴**（靠条款号 / 过程 / 部门 / 编号等**明确键**召回）。语义匹配是**第 7 种（RM7）**：

- **RM7 语义轴**：无确定性键可用时，用条款 `ClauseText` 与**文档画像**的 BM25 相似度反查。
- **启用方式 = 给条款加分类，而非给条款一个开关**（采纳）：属性 `ClauseCategory`（条款**作用类型**，**可扩展**）——取值与判据见 **三.a**，优先级与可审计见 **三.b**。

### 三.a `ClauseCategory` = 条款作用类型（横向归纳所得，标准无关）

对 9001 / 14001 / 45001 **全部 138 个条款号**做横向比对归纳，得 **6 类作用类型**；**跨三标准分类冲突 = 0 个**（2026-11-24 实测）⇒ 它只由条款号域决定，**标准无关**。

| `ClauseCategory` | 判据（条款号域） | iso9001 条数 | 证据落点 | 需 RM7 |
|---|---|:--:|---|:--:|
| **框架** | 章级（`4`…`10`）+ `4.4`/`4.4.1`/`4.4.2` | 10 | 手册 / 体系文件整体 | 否（RM1） |
| **承诺** | `5.1` / `5.2` / `5.3` / `5.4`（方针 / 承诺 / 协商） | 7 | 方针文本 + 访谈 | 否（RM6） |
| **策划** | `4.1` / `4.2` / `4.3` / `6.x` | 10 | 环境分析表 / 相关方清单 / 风险机遇评估表 / 目标台账 | **是** |
| **支持** | `7.x` | 18 | 程序文件（记号）+ 培训 / 校准 / 沟通记录 | **是** |
| **运行** | `8.x` | 30 | 运行记录 + 现场 | **是** |
| **改进** | `9.x` / `10.x` | 16 | 监测报告 / 内审报告 / 评审记录 / NC 台账 | **是** |

> **与 15 号 `Role`(r1–r7) 的关系**：本表与 `Role` **高度重合**（r1=4 章 / r2=5 章 / r3=6 章 / … / r7=10 章），仅两处更细：① **4 章拆为「框架(4.4)/策划(4.1–4.3)」**；② **9、10 章合并为「改进」**。
> ⇒ **实现时不另造属性**：`ClauseCategory` 由 `Role` + 条款号二级规则派生（或把 `Role` 细化为 r1a/r1b、把 r6/r7 合并）。
> **可扩展**：后续发现新文档类型 ⇒ 加一个取值 + 一行"是否需 RM7"映射，**召回代码不动**。
> **与 `EvidenceFamily` 的关系**：保留**两个独立属性**（2026-11-24 用户裁定）——`ClauseCategory` 决定"**要不要 RM7**"，`EvidenceFamily`(f1/f2) 决定"**要什么证据**"，职责正交。
> 与 15 号 §三"只此 6 种"的冲突已记入 §八 修订点：**6 种确定性轴 + RM7 语义轴**。

### 三.b RM7 的优先级与可审计

- **RM1–RM6 恒优先**；RM7 仅作**补召回**，命中结果标注 `source=RM7` 可审计。
- 分档：`ClauseCategory ∈ {策划, 支持, 运行, 改进}` ⇒ 追加 RM7；`{框架, 承诺}` ⇒ 不追加。

## 四、RM7 的打分内核（BM25，自实现，无外部依赖）

**为何自实现**：项目无 Lucene/向量能力；语料仅约 68 条款/标准 × 中文正文，规模极小；自实现 BM25 约 100 行，可解释、可单测。

1. **建索引**（启动或首次加载，缓存 `IReadOnlyDictionary<string, ClauseDoc>`）
   - 每条条款 → 词袋：`Title + ClauseText`。
   - 中文切词：**字符 2-gram**（免词典、对中文稳）；英数 → 按 `[A-Za-z0-9]+` 切词并小写。记录 `df`（文档频次）、`docLen`。
2. **查询串** = 文档的**标准无关画像**：`DocMeta.FileName` + `ModeOutput.ProcessArea` + `Records[].RecordName` + 主题词（`Chips`/摘要）。
3. **打分**：对候选条款算 BM25（k1=1.2, b=0.75）→ 取 `topK`（建议 8）。
4. **结构先验消歧**（消融"相邻子条款释义高度重叠"的糊）：把 15 号的纵向信息当**过滤/加权**，而非硬删：
   - 体裁白名单：`docMode` 与条款 `Role` 对应体裁不符 ⇒ 降权（不是删除，避免 6/7 章误杀）；
   - 章号范围：优先与文档 `ProcessArea` 同过程的条款；
   - 过程轴：`Process` 属性命中 ⇒ 加权。
5. **产出**：`条款 → 证据挂靠`（带 `score` + `命中词`，可展示、可审计）。

## 五、与现状的接缝

- 匹配器新增 `ClauseTextMatcher`（放 `CertPlatform.Shared/Domain/Clauses/`，与 `RecallPathResolver` 同域）；作为 **RM7 唯一入口**，端内不另写 `Queryable`（守 A-R6 "同一 WHERE 第二处即违规"）。
- `RecallPathResolver` **增补"是否追加 RM7"逻辑**（读 §三 开关），RM1–RM6 判定不变。
- 15 号白名单**由"硬过滤"降为"降权/排序"**——这是 6/7 章误杀的根治。
- 文档提取提示词改造（P3）：去掉对 `PrimaryClauses` 的强依赖，改输出**标准无关画像** ⇒ **一次提取多标准复用**（省 2/3 LLM）。
