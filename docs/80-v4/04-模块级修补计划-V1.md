## 三、M2 文档抽取（要修的三个点）

- **核心功能**：把 Markdown 按文档类型抽取成结构化事实（`cert_document_extraction.ContentJson`）。
- **现有实现**：`DocExtractPromptService` 读 `cert_prompt_template`；`EnterpriseDocExtractionRouter` 按文件名分类走不同模式（`record_profile` / `process_profile` / `policy_profile` / `audit` / `index` 等）；`RecordQualityGuard` + `ModeOutputProjector` 做读时校正。
- **现状**：⚠️ 质量本身不差——《01供应商评审表》抽出了 `RowCount=1`、六项评审、4 人签署（采购部胥加娟/生产部黄勇/品质部张红红/总经理潘明海），`Warnings` 还记了"模型报 4 行、按有数据的行重算为 1"。
- **问题**：
  1. **两套产物结构**：新模式写 `ModeOutput`（`Clauses: []`），旧模式写 `Clauses[]`（无 `ModeOutput`）。消费侧只认其中一套，导致"好数据被丢、坏数据被留"。
  2. **86/99 无条款归属**：`ClauseNumbers` 空、`ClauseCount=0`。这对记录类是设计决定，但**没有替代锚点**（`ProcessArea` 有空值）。
  3. **ProcessArea 存在空值**：《01信息联络单》的 `ModeOutput` 整个为 null。
- **修补方式**（改 3 处）：
  1. `DocumentExtractionService` 落库前加**产物完整性闸门**：`ModeOutput` 缺失 → 重跑；`DocType=record` 且 `ProcessArea` 为空 → 重跑；两次仍空 → 标 `ExtractStatus=partial` 并记 `ExtractMessage`。
  2. `ModeOutput` 作为**唯一产物**，`Clauses[]` 只保留为兼容层（读取时若 `ModeOutput` 存在则忽略 `Clauses`）。统一由 `ModeOutputProjector.ForProjection` 出口。
  3. 记录类**不补条款**（保持 97 号 §10.7 的裁决），但必须补 `ProcessArea` + `OwnerDept` —— 这两个字段是过程轴召回的唯一依据。
- **验收**：99 份里 `ProcessArea` 非空 ≥ 95%；`ModeOutput` 缺失 = 0；同一份文档重抽两次 `RowCount` 一致。

## 四、M3 文档画像（从 0 到 1）

- **核心功能**：给每份文档一个"用途画像"（规定类/执行类/结论类、覆盖期、责任部门、报告角色），供召回与装配使用。
- **现有实现**：`EnterpriseDocProfileBuilder` 存在，表 `cert_enterprise_doc_profile` 存在。
- **现状**：❌ **表 0 行**——画像从来没被写回。
- **问题**：召回只能靠抽取产物里的字段硬拼，没有统一画像可查；装配时也不知道某份文档该进报告哪一节。
- **修补方式**：
  1. `EnterpriseDocProfileBuilder` 增加"从 `ModeOutput` 投影画像"的分支，写 `cert_enterprise_doc_profile`（字段：`FileCode / DocType / DocClass / ProcessArea / OwnerDept / CoverageStart / CoverageEnd / ReportRole / RowCount / SignoffCount`）。
  2. 抽取完成后自动触发（`EnterpriseExtractTaskExecutor` 末尾钩子），并提供一次性补数脚本。
- **验收**：99 行画像；任取一份记录类文档，能被不读 `ContentJson` 直接答出"它是执行类、采购过程、采购部、覆盖 2026.6"。

## 五、M4 条款库与属性池（补两个洞）

- **核心功能**：条款树 + 每条条款的属性（义务/过程/证据形式/角色/严重度），是召回与判定的依据。
- **现有实现**：`cert_iso_clause`(846 条)、`cert_clause_attr`(4038 行)、`cert_clause_attr_def`(12 个属性定义)。
- **问题**：
  1. 属性缺 `DocCheckMode`（94 号 P0 已记）——召回时无法判断"这条款该查哪类文档"。
  2. GB/T 45001 的 8.x 只有 8/8.2 两条，**8.4 采购缺失**，导致采购类文档在该标准下无法按条款召回。
- **修补方式**：
  1. 补 `DocCheckMode` 属性（取值：`doc_only / record_only / doc_and_record / onsite`），按条款逐条配置；
  2. 补 45001 的 8.4 条款行（复用 19001 的 8.4 结构，改语义）；
  3. 属性配置页加"覆盖率"统计（哪些条款还没配 `Process`）。
- **验收**：4 个标准的 8.4 均可召回；`Process` 属性覆盖 ≥ 95% 的叶子条款。

## 八、M7 召回/上下文装配（最优先修，1 天）

- **核心功能**：把"检查项 + 条款 + 部门"变成"给模型看的文档切片"。这是唯一决定输入的地方。
- **现有实现**：`CertCheckContextBuilder.BuildAsync`（引擎调它，`CertCheckEngineService:280`）；另有 `CertTaskService.ProjectDocSlices`（计划详情页用，含 `ProcessAreaRecall` 四轴）。
- **现状**：❌ 四个缺陷叠加：
  1. `ParseModeOutputSlices` 读 `PrimaryClauses`，**空则整份丢弃** → 86 份记录类消失；
  2. `wantedNumbers.Contains` 精确匹配，**7.1.5 不命中 7.1.5.1** → 程序也丢；
  3. 旧结构文档（只有 `Clauses`）反而能进 → 奖励坏数据；
  4. **两条链路并存**：97 号的四轴召回只接在 `ProjectDocSlices`，引擎这条路一行没接。
- **修补方式**（改一个文件的三处 + 复用一个现成类）：
  1. **条款轴保留**：`PrimaryClauses` 有值 → 原逻辑；
  2. **新增过程轴分支**：`DocType=record` 时，用 `ProcessArea`（"采购过程"）匹配检查项条款的 `Process` 属性（`purchase`），命中即产生切片，`ClauseCode=null`、`Anchor="过程召回"`；
  3. **父条款归一**：匹配前把 `7.1.5` 展开成"命中所有 `7.1.5.x`"，`8.1` 同理；
  4. 配额：规定类 ≤3 份、执行类 ≤6 份、结论类 ≤2 份，按 `RowCount` 降序、期间新优先；
  5. 直接复用 `ProcessAreaRecall.ParseKeys/KeywordsFor/Matches`（已实现、已有 13 个单测），**不要另写一套**。
- **验收**：8.4.1 输入含《01供应商评审表》；7.1.5.1 输入不再是 1 份；四跑不再全部 ofi。

## 九、M8 分析引擎（拆三段，3 天）

- **核心功能**：一次检查项分析 = 取上下文 → 渲染提示词 → 调模型 → 解析 → 落库。
- **现有实现**：`CertCheckEngineService.AnalyzeCheckItemAsync`，已分 L2/L2.5/L3/L4/L5/L6/L7/L8 八步，结构清楚。
- **现状**：⚠️ 八步都在，但 **L6 只调一次模型**，一次产出 `conclusion + summary + audit_evidence + clause_evidence + doubts + nc_suggestion + severity + nc_draft` 六样。
- **问题**：
  1. 结构逼模型"先定结论再配证据"（数据实验：补一份记录后疑点从 2 条归零）；
  2. 输出含 `nc_draft`，与 95 号 R-C（"不符合"出现 0 次）冲突；
  3. 证据句违反 R-A（实测四次都写"未提供/未见"）。
- **修补方式**：
  1. 把 L6 拆成三段调用：`fact → doubt → evidence`，中间产物落表（见 M9/M10）；
  2. 新增 `EvidencePipeline` 编排器（放 `CertPlatform.Auditor/Services/Expert`），负责串联三段并保证"第二段只读第一段的表，不重读文档"；
  3. 删除 `nc_draft` / `severity_suggestion` 字段，`conclusion` 改为"审核员手填，系统只给 blank"（R-C）。
- **验收**：一次分析产生三张表各 ≥1 行；输出中"未提供"出现 0 次；`nc_draft` 字段不存在。

## 十、M9 证据（4 天，从"人工挂附件"改成"从文档生成条目"）

- **核心功能**：证据条目 = 一条可定位、可核对的事实。
- **现有实现**：`CertEvidenceService` 只有人工 CRUD（`AddAsync/UpdateAsync/DeleteAsync`）；引擎里 `WriteEvidenceLinksAsync` 写的是**快照**（这次用了哪条人工证据），上游 `cert_evidence` 0 行 → 循环 0 次 → `cert_check_analysis_evidence` 也是 0 行。
- **现状**：❌ 证据不是系统的产物，是"人上传 → 模型读 → 存快照"。
- **问题**：无法追溯（点不到原文）、无法装配（没有字段可映射槽位）、无法统计（证据来源类型分布）。
- **修补方式**：
  1. **新建表** `cert_evidence_item`，字段见 `02-V4总体方案` §3.1（13 个字段，含 `Anchor/Excerpt/FieldName/FieldValue/IsBlank/RecalledBy`）；
  2. **新建服务** `EvidenceItemProjector`：读 `cert_document_extraction.ContentJson`，走 `ModeOutputProjector.ForProjection` 归一后，把 `Records[].Samples[]` 逐行投影成 `EvidenceItem`；`Signoff[]` 合成一条；
  3. **Anchor 唯一性校验**：复用 `DocumentSourceLocator.LocateUnique`，定位不到的行降级为 `Confidence=0` 并标 `AnchorUnverified`，不进证据句；
  4. 保留 `cert_evidence` 作为"现场证据（照片/录音）"的容器，与 `cert_evidence_item` 分表、不混用。
- **验收**：跑 8.4.1 后 `cert_evidence_item` ≥ 5 行；抽取 4 行签署；Anchor 唯一命中率 ≥ 95%。

## 十一、M10 疑点与缺口（3 天，规则优先）

- **核心功能**：指出"哪里对不上、哪里为空、哪里可疑"，但不下结论。
- **现有实现**：`GapDetector`（补录清单，`R\H` 差集）、`GapFillService`、`GapLabelResolver`；疑点落在 `DoubtsJson`，由模型生成。
- **现状**：⚠️ 缺口检测有，但**疑点全交给模型**——实测看到记录就归零。
- **修补方式**：
  1. 新增 `DoubtRuleEngine`，10 条规则（记录为空 / 关键字段空 / 跨文档对不上 / 日期集中 / 签署缺人 / 覆盖期不齐 / 名录过少 / 结论无数据支撑 / 程序引用记录但记录未填 / 模板雷同）；
  2. 规则输入 = `cert_evidence_item` + `cert_clause_attr` + 条款要求，**不调模型**；
  3. 模型只负责把 `rule_id + 命中数据` 翻成审核员语言（`ev_doubt_rule`）；
  4. 疑点落表 `cert_doubt`（`CheckItemCode / RuleId / Point / Detail / SeverityHint / EvidenceItemIds`）。
- **验收**：供应商评审表报出"名录仅 1 家""四部门同日签署"；疑点精确率 ≥ 70%（专家认可/报出）。

## 十二、M11 结论与判定（1 天，收敛词表）

- **现有实现**：`CertVerdictMapper` 已是"全局唯一出口"，注释自己写明系统里存在四套词表（`PrepState` / `Conclusion` / `NcSuggestion` / `Severity`）。
- **问题**：值域不一致，同一状态在不同页面显示不同词。
- **修补方式**：以 `CertVerdictMapper` 为准，反向清理写入端的枚举；`conclusion` 只允许 `pass / ofi / blank`（`nc` 由审核员现场判定，系统不产生）。
- **验收**：全库 `Conclusion` 取值只有 3 个；`nc_suggestion` 字段清零。

## 十六、依赖顺序（不能乱）

```
M7 召回 ──┐
          ├→ M9 证据条目 ──→ M10 疑点规则 ──→ M8 三段编排 ──→ M12 装配
M2 抽取 ──┤                        ↑
M3 画像 ──┘                        │
                          M13 提示词 ─┘
M4 条款 ──→ M7（过程轴要用 Process 属性）
M14 校验 ──→ 跟着 M9 一起上（落库前拦截）
```

**硬依赖三条**：
