# 26 · 当前召回与证据质量实测-V1

> 用途：把「5 个问题」的答案固化成可复现的实测记录，并回答一个更尖锐的问题——**「两步筛选没落地」是不是当前最严重的问题**。
> 关系：`25` 是「全量评价」，本文是**召回与证据链的专项实测**，只补数据与因果，不重复 23/24 的设计论证。
> 数据时点：2026-11-27。库 `yzh_cert_platform`，基线 `RunNo=1`（56 检查项，全部 `onsite`）。
> 样本：提取 97 份 / 条款属性 650 条（65×10）/ 存活条款 320 条 / 分析 56 条（另 6 条对抗实验）/ 结果 62 行。

## 零、先回答「两步筛选是不是最严重的问题」

### 0.1 一句话

> **不是最严重的那一个，但它是「召回侧」最严重的那一个。**
> 放到「报告能不能用」这个总目标下，**唯一 P0 是「证据正文引用了没读过的文档」**；两步筛选缺失排 P1，但它解释了 51.8% 的检查项为什么召回 ≥10 份。

### 0.2 严重度排序（按「对最终报告可信度的杀伤」）

| 级 | 问题 | 硬数据 | 为什么排这个位置 |
|:--:|---|---|---|
| **P0** | 证据正文引用「不在摘录里」的文档 | 硬下限 **42/265 = 15.8%**（17/56 项）；代理估计 **112/267 = 41.9%**（41/56 项） | 报告会写出「《X》规定……」而系统从未读过《X》。**这是伪造证据，不是召回不准** |
| **P1** | 无「用途精准匹配」，过程/部门轴无收敛 | 走 RM2/RM3 的 **30 项平均召回 21.3 份**；不走的 26 项平均 **4.2 份**（5 倍差） | 解释了「虚增」，但不直接产生错误结论 |
| **P1** | **召回计划 7 轴，实际只执行 3 轴** | 51/56 项的 `recall_trace` 写着 RM7，RM7 无实现；RM4/RM5 同样只有计划 | `recall_trace` 让人误判「轴都跑了」；漏召回无法归因 |
| **P1** | 空模板被写成「已建立」正面事实 | 70 份记录类中 **54 份 `Records[].RowCount` 合计 = 0**（record 28/44、audit 26/26） | 结论层已有疑点兜住，伤害在**证据正文** |
| **P1** | 祖先回退缺失 ⇒ 6 条子条款零召回 | 6/56 = **10.7%** | 漏检，但可定位、修复成本 5 行 |
| **P1** | `manual` 误判 1/3 | 3 份 manual 错 2 份（0.8 / 0.9 置信度） | 错分类级联到提取模式 ⇒ 一条链全错 |
| **P2** | 审计链指向了没被使用的提示词 | `cert_check_analysis.PromptCode` = `75ef2454…`（`wf_prompt_template.audit_check`，单段旧提示词），实际跑的是 `cert_prompt_template` 的 `clause_evidence_findings` + `audit_check_evidence`；`Conclusion` 62/62 为 NULL；`DoubtType` 在第二段丢失 | 排查时按 `PromptCode` 找提示词会找错 |

### 0.3 反直觉：召回越窄，编造越多

把 56 项按 `doc_hit` 分桶，统计「正文引用的文档里，有多少份根本不在摘录集内」：

| `doc_hit` | 项数 | 引用份次 | 不在输入快照（代理） | 编造率 |
|---:|---:|---:|---:|---:|
| 0 | 6 | 19 | 19 | **100.0%** |
| 1–4 | 14 | 51 | 43 | **84.3%** |
| 5–9 | 7 | 30 | 10 | 33.3% |
| ≥10 | 29 | 167 | 40 | **24.0%** |
| 合计 | 56 | 267 | 112 | 41.9% |

> 本表用「文件名不在输入快照」作代理（偏宽松，会把「名字在、正文没给」算成没问题）；剔除手册、只按 `doc_hit` 名额算的**硬下限**是 **42/265 = 15.8%**（§3.2）。两者结论方向一致。

单调下降。**这意味着：如果先收紧召回（补 Stage1/Stage2），而不先关掉「目录可被当成正文」这个口子，编造率会从 24% 被推回 84%–100%。**

> 因果方向要说清：是「召回薄 ⇒ 模型拿目录补」，不是「过滤少 ⇒ 编造多」。薄召回可能因为企业确实缺文档（如 5.1.1 领导作用），但**只要目录在，模型就会补**——这才是可控的那一环。

> 这就是本文最重要的排序依据：**两步筛选和引用白名单不是两件并列的事，收紧召回会放大编造。顺序必须是「先关编造，再收紧召回」。**

### 0.4 三条口径更正（对 25 号与本人前次口头结论）

| # | 之前说法 | 实测 | 影响 |
|:--:|---|---|---|
| 1 | 「4 条 `pass`，会降到 1–2 条」 | **基线 56/56 的 `AiConclusion` 全是 `ofi`，0 条 `pass`**。模型原始输出里有 4 条写 `pass`（9.1.2 / 4.3 / 6.1.2 / 7.1.1），但 `ResolveSuggestedConclusion` 因「疑点>0」强制升级为 `ofi` | 结论层**已有**闸门；缺的是**证据正文层**的闸门 |
| 2 | 「`ofi` 是合格」 | `ofi` = 观察项；`verdict.ts` 与提示词均为「部分要求只有制度/空白模板，需现场核实」 | 25 号据此得出的「全合格」不成立 |
| 3 | 「N-1b 召回兜底污染」 | 分析链路不走 `ListByClauseAsync`；run5 的 `doc_hit` 29→28 证明输入确实变了 | 25 号的归因不成立 |

### 0.5 如果只能改一件事

**加「引用白名单」：第二段只允许引用 `doc_excerpts` 里出现过的文件名，`OriginalQuote` 为空的发现不得进证据正文。**

理由：它是唯一**同时**缓解 P0 与 P1 的单点改动——被过召回的文档只要不进正文，就等于没被召回；而没读过的文档再也写不出内容。约 1 小时级改动，不需要动召回算法。

## 一、口径与样本

### 1.1 样本边界

| 项 | 值 | 说明 |
|---|---:|---|
| 基线检查项 | 56 | `RunNo=1`，`StageKind=onsite` |
| 对抗实验 | 6 | `RunNo=2..7`，其中 2 条 `nc` |
| 提取产物 | 97 | 全部 `iso9001`；14001/45001/13485 为 0，**跨标准不可测** |
| 条款属性 | 650 | 65 条 × 10 属性 |
| 存活条款 | 320 | `cert_iso_clause`，0 死副本 |
| 结果行 | 62 | `cert_check_result` |

### 1.2 三个指标的定义（避免各说各话）

| 指标 | 定义 | 来源 | 可信度 |
|---|---|---|---|
| `doc_hit` | 该检查项**有摘录的文档份数**（按 `FileCode` 去重） | `ResultSummaryJson.doc_hit_count` = `CertCheckContext.DocHitCount` | **权威**（代码定义） |
| `cited` | 该检查项 `Reason` 正文里 `《…》` 去重后的文档数 | `cert_check_result.Reason` 正则 | 权威（落库文本） |
| `in_excerpt` | `cited` 中文件名出现在该检查项输入快照里的份数 | `cert_check_analysis.InputSnapshotJson` | **代理**（见 §1.3） |

### 1.3 三个已知局限

1. **两段式的 findings 提示词没有落库**。`InputSnapshotJson` 存的是单段快照（`pipeline` 已是 `two_stage`，但快照字段还是单段的），所以「文件名是否在输入里」只能做代理判断。因此给出**区间**：硬下限 + 代理估计。
2. **手册是例外**。`LoadManualGuidance` 会把手册的 `EvidenceSources` 渲染成 `FactText`（独立于 `doc_hit`），所以**引用《管理手册》不算编造**。所有硬下限计算都已剔除手册。
3. **提示词审计链是断的**。`cert_check_analysis.PromptCode` 指向 `wf_prompt_template.audit_check`（单段旧提示词），而实际执行的是 `cert_prompt_template` 的 `clause_evidence_findings`（6971 字，2026-11-26 10:13，**不在任何 git 脚本里**）+ `audit_check_evidence`。要复现当次输入，只能靠 `InputSnapshotJson` 的代理。

## 二、Q1：检查项的证据能不能顺利找到

### 2.1 分布：89.3% 有召回，但两极分化

| `doc_hit` | 项数 | 占比 | 累计 |
|---:|---:|---:|---:|
| 0 | 6 | 10.7% | 10.7% |
| 1–4 | 14 | 25.0% | 35.7% |
| 5–9 | 7 | 12.5% | 48.2% |
| ≥10 | 29 | 51.8% | 100% |

中位数 **13.5** 份，最大 **39** 份（9.1.3）。50/56 至少 1 份。

### 2.2 6 条零召回：根因是「只做后代回退」

| 条款 | `doc_hit` | 手册实际有的节 |
|---|---:|---|
| 4.4.1 / 4.4.2 | 0 / 0 | 只有 4.4 |
| 5.1.1 / 5.1.2 | 0 / 0 | 只有 5.1 |
| 5.2.1 / 5.2.2 | 0 / 0 | 只有 5.2 |

`CertCheckContextBuilder.ResolveRequestedClause` 的注释写得很清楚：

```csharp
/// <para>与 CertTaskService.IsClauseOrDescendantMatch 口径一致：只做后代回退，不做祖先回退。</para>
```

即：请求 `4.4` 时文档里的 `4.4.1` 能命中；请求 `4.4.1` 时文档里的 `4.4` **不命中**。

这是 `10` 号「父级回退」**没有落到运行时**：探针 `probe_chapter_recall.py` 已加 `ancestry()`，运行时没加。

### 2.3 4.1：不是召回问题，是归属问题

4.1 只召回 **2 份**（手册 + 变更程序），但真实底稿的 4.1 证据是《外部因素清单》《内部因素清单》。

| 文件 | 提取出的 `PrimaryClauses` | `Chapters` |
|---|---|---|
| `01-外部因素识别监视评价总清单.docx` | `["9.2"]` | `["9"]` |
| `02-内部因素识别监视评价总清单.docx` | `["9.2"]` | `["9"]` |
| `03相关方的需求及期望识别及评审表.doc` | `["4.2"]` | `["4"]` |

因素清单因为「监视评价」被挂到 9.2，所以 R1 按 4.1 查不到。**修召回算法救不了它，必须修上游归属或加人工纠正。**

### 2.4 Q1 结论

- **能找得到**：89.3% 有召回；
- **但「找到」≠「对」**：4.1 找到的是依据不是执行，8.5.3 找到的是空模板；
- 6 条零召回是**确定性缺陷**，5 行代码可修；4.1 是**数据缺陷**，修法完全不同。

## 三、Q2：漏条款 / 虚增条款是否明显

### 3.1 虚增：召回 748 份次，正文只用 267 份次

| 条款 | `doc_hit` | 正文引用 | 未引用 | 利用率 |
|---|---:|---:|---:|---:|
| 9.1.3 | 39 | 9 | 30 | 23.1% |
| 9.1.2 | 37 | 5 | 32 | 13.5% |
| 9.3.3 | 31 | 2 | 29 | **6.5%** |
| 9.2.1 | 31 | 9 | 22 | 29.0% |
| 8.5.3 | 29 | 7 | 22 | 24.1% |
| 8.5.2 / 8.5.4 / 8.5.6 | 29 | 5–6 | 23–24 | 17–21% |

全量：**748 → 267，利用率 35.7%**。约 2/3 的召回没有进入最终证据。

### 3.2 更严重：引用不可追溯

**硬下限（剔除手册，且给足 `doc_hit` 名额）**：

| 指标 | 值 |
|---|---:|
| 去重后引用份次 | 265 |
| 引用数 > `doc_hit` 的超出量 | **42（15.8%）** |
| 受影响检查项 | **17 / 56** |

**代理估计（文件名不出现在输入快照里）**：**112 / 267 = 41.9%**，**41 / 56 项**。

区间结论：**至少 1/6、可能接近 2/5 的证据引用指向系统没读过的文档。**

最集中的 6 项：

| 条款 | `doc_hit` | 引用 | 至少多引 |
|---|---:|---:|---:|
| 4.4.2 | 0 | 7 | 6 |
| 6.1.1 | 1 | 6 | 4 |
| 4.4.1 | 0 | 4 | 3 |
| 6.1.2 | 1 | 4 | 3 |
| 6.2.1 | 1 | 5 | 3 |
| 7.1.1 | 1 | 5 | 3 |

### 3.3 机制：`doc_catalog` 泄漏了「体裁 / 过程域 / 责任部门 / 条款」

`CertCheckContextBuilder.BuildDocCatalogText` 把全库文档渲染成目录（上限 12000 字符），每条长这样：

```
《04风险机遇控制程序.doc》｜体裁=process_profile｜过程域=风险与机遇｜责任部门=综合部｜条款=6.1
```

它同时注入了 `clause_evidence_findings` 的 `{{doc_catalog}}`。提示词写了「目录不含正文，不得据此推断」，但**目录里带了「条款=6.1」和「过程域」**——这等于告诉模型「这份文档讲 6.1」，模型很自然地把名字 + 属性扩写成内容。

> 说明：这是**推断**，不是直接观测（findings 提示词未落库）。但 6.1.2 的 4 份被引文档全部只在目录里、不在摘录里，且名字与目录格式一致，是目前唯一能解释「名字对、内容无来源」的机制。

`6.1.2` 是最干净的证据：

| 项 | 值 |
|---|---|
| `doc_hit` | **1** |
| 输入里含「管理手册」 | **0 次** |
| 引用的 4 份文档在输入里 | **0 份** |
| 模型原始结论 | `pass`（被系统改为 `ofi`） |

4 份被引文档是《04销售合同管理制度》《07体系变更策划控制程序》《01质量风险与机遇分析评价表》《01组织环境相关方需求期望控制程序》——输入里一个都没有。

### 3.4 Q2 结论

- **漏是局部的、可定位的**：6 条子条款 + 1 条错挂（4.1）+ 1 条过少（5.3 只 1 份）；
- **虚增是系统性的**：召回端过宽（30 项均值 21.3 份），生成端只用 1/3；
- **最危险的是第三件事**：漏出来的空位被「目录名字」填满，于是「漏」直接转化成「编」。

## 四、Q3：当前是否「大章节 + 部门初过滤 → 用途精准匹配」

### 4.1 答案：没有，而且比「没做两步」更糟——计划 7 轴，只执行 3 轴

```
条款属性（EvidenceFamily / EvidenceForm / Role）
        ↓
RecallPathResolver.Resolve()  → 产出 7 轴「计划」
  RM1 条款 / RM2 过程 / RM3 部门 / RM4 编号 / RM5 现场 / RM6 访谈 / RM7 语义
        ↓
CertCheckContextBuilder 实际执行（取并集，无统一候选池、无用途配对）
  RM1 条款轴   ✓  ContentJson.Clauses[] / ModeOutput.PrimaryClauses ∩ 条款号（只做后代回退）
  RM2 过程轴   ✓  ProcessArea ∩ 条款 Process，记录优先，上限 10
  RM3 部门轴   ✓  OwnerDept ∩ 检查项部门，记录优先，上限 6
  RM4 编号轴   ✗  计划里有，无实现（全仓仅 Resolve 与文案映射）
  RM5 现场轴   ✗  计划里有，无实现（现场证据只进「孤儿」）
  RM6 访谈轴   △  只把 interview 证据挂进条款块，不产生候选文档
  RM7 语义轴   ✗  计划里有，无实现；手册纲领是无条件加载，不是 RM7
        ↓
一次 clause_evidence_findings LLM（6971 字，DB-only）
        ↓
一次 audit_check_evidence LLM（消费 Findings/Doubts）
```

**计划 vs 实际（56 项统计）**：

| 轴 | 计划中出现 | 实际执行 |
|---|---:|---|
| RM1 条款 | 34 | ✓ |
| RM2 过程 | 30 | ✓ |
| RM3 部门 | 22 | ✓ |
| RM7 语义 | **51** | **✗** |
| RM6 访谈 | 4 | △ |
| RM4 编号 | 3 | **✗** |
| RM5 现场 | 2 | **✗** |

**51/56（91%）的检查项，召回计划里写着 RM7，但 RM7 没有实现。** 这解释了为什么 `recall_trace` 看起来「轴都跑了」——它记的是**计划**，不是执行。

| 7 轴召回全部可用 | **只 3 轴可用**，RM4/RM5/RM7 未实现 | 计划与实现脱节 |

### 4.3 三个字段的真实覆盖率

### 4.4 为什么记录类必然过召回：44/44 没有条款号

按体裁拆 `ClauseNumbers` 为空的比例：

| 体裁 | 份数 | 无条款号 | 比例 |
|---|---:|---:|---:|
| `record` | 44 | **44** | **100%** |
| `audit_record` | 26 | 2 | 7.7% |
| `procedure` | 13 | 0 | 0% |
| `context_list` | 4 | 0 | 0% |
| `manual` | 3 | 2 | 66.7% |
| `policy` | 2 | 1 | 50% |

**记录类 44 份全部没有条款号 ⇒ R1 对记录完全失效。** 记录只能靠 RM2（上限 10）和 RM3（上限 6），而这两条轴都是「记录优先」——**记录会先把 10 个名额占满，程序文件反而挤不进去。**

这就是「召回 29 份、正文引用 5 份」的结构性原因：不是模型不想用，是**同一类文档在同一个池子里抢名额**，没有「这份是制度、那份是执行、那份是结论」的区分。

### 4.5 过程/部门轴是过召回发动机（5 倍差）

按 `recall_trace` 的轴组合聚合：

| 轴组合 | 项数 | `doc_hit` 合计 | 均值 |
|---|---:|---:|---:|
| RM2 + RM3 + RM7 | 20 | 499 | **24.9** |
| RM2 + RM3 + RM5 + RM7 | 2 | 50 | **25.0** |
| RM1 + RM2 + RM7 | 8 | 89 | 11.1 |
| RM1 + RM7 | 17 | 102 | 6.0 |
| RM1 + RM4 + RM7 | 3 | 6 | 2.0 |
| RM1（单轴） | 2 | 1 | 0.5 |
| RM1 + RM6 | 3 | 0 | 0.0 |
| RM1 + RM6 + RM7 | 1 | 1 | 1.0 |

汇总：

| 分组 | 项数 | 平均 `doc_hit` |
|---|---:|---:|
| 含 RM2 或 RM3 | **30** | **21.3** |
| 不含 RM2/RM3 | 26 | **4.2** |

**5 倍差。** 过召回不是全局现象，是**过程轴 + 部门轴的专属现象**——而这两条轴恰好就是「没有用途配对」的两条轴。

### 4.6 结论：缺的是第二步，不是第一步

用户直觉「没按理论召回」是对的，但要拆成两句：

| 判断 | 结论 | 依据 |
|---|---|---|
| 召回有没有按理论（7 轴）跑 | **没有** | 计划 7 轴，执行 3 轴；RM7 计划 51 项、实现 0；RM4/RM5 同样为 0 |
| 「大章节初过滤」缺失是不是主因 | **不是** | 70/97 是记录/审核记录，其中 44/44 记录没有标准章节、没有条款号。23 号的 Stage1 对它们**无从下手** |
| 「用途精准匹配」缺失是不是主因 | **是** | 30 项走 RM2/RM3，均值 21.3 份；`DocFunction` 只有 3/97，配对无法执行 |
| 两步筛选是不是全局最严重 | **不是** | 它产生噪音，不产生假证据；假证据来自 `doc_catalog` + 无白名单 |

一句话：**你想的「大章节初过滤」对记录类无效；真正缺的是「用途 + 部门 + 期间」的第二层配对。而第二层的前提是先有 `DocFunction`。**

### 4.7 为什么不能「先上 Stage1」

| 若先做 Stage1 | 后果 |
|---|---|
| 给 44 份记录补 `ChapterDomains` | 记录没有标准章节，只能靠 LLM 猜；猜错 = 硬过滤误杀 |
| 用 `Chapters[]` 反推 | 因素清单已被挂到 9.2，反推会把 4.1 的证据永久锁死 |
| 收紧候选集后再让模型写 | `doc_hit` 从 20 降到 6，编造率按 §0.3 的曲线从 24% 升到 33%–84% |

**Stage1 的前提是分类与归属先可信；现在两者都不可信（manual 1/3、因素清单挂 9.2）。**

## 五、Q4：空记录必须处理

### 5.1 数据比 25 号写的更严重

| 体裁 | 文档数 | `Records[].RowCount` 合计 = 0 | 占比 |
|---|---:|---:|---:|
| `record_profile` | 44 | 28 | 63.6% |
| `audit_profile` | 26 | 26 | **100%** |
| 合计 | 70 | **54** | **77.1%** |

记录类里只有 16 份有真实数据行。

### 5.2 8.5.3：结论对，证据正文错

同一份输出里：

| 位置 | 内容 |
|---|---|
| 证据正文 | 「查阅《01顾客或供方财产登记表.doc》，确认该表单已建立，包含财产类型、数量、状态、责任方等基础字段」 |
| 疑点 | 「《01顾客或供方财产登记表.doc》为模板文件，无实际填写内容」 |
| 结论 | `ofi`（观察项） |

**结论是对的，证据正文把「存在」写成了「运行」。** 一份空模板（1 Record / 0 Rows）被描述成「已建立并包含字段」，读者会以为企业已在登记顾客财产。

### 5.3 代码层缺三样

| # | 缺什么 | 现状 | 后果 |
|:--:|---|---|---|
| 1 | `EvidenceSufficiency`（`filledCount` / `templateCount` / `basisCount`）由代码算 | 没有；靠模型自报 `FillStatus` | 模型说 `filled` 就是 `filled` |
| 2 | 状态闸门：`filledCount=0` ⇒ 不得 `pass` | 结论层有（疑点>0 强制 `ofi`），**证据正文层没有** | 正文可以照写「已建立」 |
| 3 | `DoubtType` 保留 | `ParseDoubts` 只产 `{Point, Detail}`，第二段把 `blank_template` 等类型丢了 | 代码无法区分「空模板」与「缺签字」 |

第 3 条是硬伤：`cert_check_result.DoubtsJson` 实测只有 `Point`/`Detail`，而第一段提示词明确定义了 10 个 `DoubtType`。**类型在第一段产生、在落库时丢失。**

### 5.4 五条处理（按优先级）

| # | 动作 | 落点 | 效果 |
|:--:|---|---|---|
| 1 | 代码算 `filledCount` / `templateCount` / `basisCount` | `CertCheckEngineService` 或 `CertCheckResult` | 不再依赖模型自报 |
| 2 | `filledCount=0` ⇒ 证据正文只能写「建立了《X》（空白，0 行）」 | `audit_check_evidence` 提示词 + 代码校验 | 堵住「空表写成运行」 |
| 3 | 第二段输出补 `type` 字段 | `clause_evidence_findings` + `ParseDoubts` | 类型可落到代码规则 |
| 4 | `recall_trace` 增加「空模板=n」 | `CertCheckContextBuilder` | 「召回 29 份」变成「29 份里 0 份有数据」 |
| 5 | 空模板不计入 `CanFormEvidence=true` | 已有提示词规则，缺代码断言 | 防止「程序 + 空表 = 可形成证据」 |

## 六、Q5：23 号的「指纹 + 特征」能否立住

### 6.1 分层判断

| 能力 | 能否立住 | 依据 |
|---|---|---|
| 粗分类（record / procedure / manual） | **能，但 `manual` 必须先修** | 97/97 有 `DocTypeCode`，仅 1 份 `unclassified` |
| 章节锚点 `Toc` | **能** | 95/97 带 `CharStart/CharEnd`，0 次 LLM |
| 部门归属 | **能（需归一）** | `OwnerDept`/`DeptNames` 95/97 |
| 章节域**硬过滤** | **不能** | `manual` 1/3；程序 Toc 是六段式（1 目的/2 范围/3 权责…），推不出标准章号 |
| 用途过滤 | **现在不能** | `DocFunction` 3/97 |
| 证据可追溯 | **不能** | §3.2 的 15.8%–41.9% |

### 6.2 `manual` 精度 1/3：不是特征不够，是规则不会打架

| 文件 | 分类 | 置信度 | 实际 |
|---|---|---:|---|
| `01管理手册QMS.doc` | manual | 0.9 | 对 |
| `06质量监测分析评价程序.doc` | manual | 0.8 | **错（程序文件）** |
| `05-3内审检查表（管理层）.docx` | manual | 0.9 | **错（内审检查表）** |

`DocFingerprint.Classify` 的规则：

```csharp
var manualHigh = CountHas(fps, "manual.issue_order", "manual.policy_objective", "manual.clause_mapping");
var manualMid  = CountHas(fps, "manual.org_duty", "manual.procedure_index", "manual.std_chapter_span");
if (manualHigh >= 2 || (manualHigh >= 1 && manualMid >= 2))
    return new Classification("manual", ...);
```

- `06程序`：`manualHigh=1`（policy_objective）+ `manualMid=2`（org_duty + procedure_index）⇒ 判 manual，**无视 `procedure.six_section`**；
- `05-3检查表`：`manualHigh=2`（policy_objective + clause_mapping）⇒ 判 manual，**无视 `record.blank_form` + `record.audit_or_review`**。

三个结构性缺陷：**first-match-wins、无负向证据、无竞争分数比较**。

### 6.3 错分类会级联

两份错分文档的 `ExtractionMode` 都被设成 `manual_chapter`，于是用**手册提示词**提取程序和检查表。分类错 → 提取错 → 召回错，一条链全错。**这是「先修 manual」而不是「先加 ChapterDomains」的直接理由。**

### 6.4 `ChapterDomains` 的真实来源

| 文档类 | 可靠来源 | 备注 |
|---|---|---|
| 手册 | `Toc` 章号 | 唯一可靠 |
| 程序 | `PrimaryClauses` / `Chapters` | 不可靠（因素清单 → 9.2） |
| 记录 | **无** | 44/44 无条款号、无标准章节 |
| 审核记录 | `ClauseNumbers` | 24/26 有，可用 |

结论：**`ChapterDomains` 只对手册可靠；对 70/97 的记录类无从推导。** 23 号把它当 Stage1 主键，是把最不可靠的字段放在最前面。

### 6.5 改进方向（收敛为 5 条 P1）

| # | 改进 | 成本 | 收益 |
|:--:|---|---|---|
| 1 | **修 `manual` 判定**：必须命中 `manual.std_chapter_span`，或 manual 分 > procedure/record 分且边际 ≥1；`record.blank_form` 作为负证据 | 小 | manual 精度 1/3 → 目标 ≥0.9 |
| 2 | **`DocFunction` 确定性填充**：manual/policy/procedure/wi → basis；record/audit_record → execution；report → conclusion；context_list → context | 0 LLM | 解锁第二步 |
| 3 | **`DeptCodes` 用 `OwnerDept`/`DeptNames` 归一**，不用自由文本 | 小 | 部门配对可用 |
| 4 | **章节域先确定性、后 LLM**：手册用 `Toc`，审核记录用 `ClauseNumbers`，记录类**不做章节过滤** | 中 | 97 次 LLM 可降到 ~30 次 |
| 5 | **Stage1 只做权重、不做硬过滤**：命中 +2，不命中不淘汰；与 R1 取并集 | 小 | 避免误杀 |

## 七、修复顺序与验收

### 7.1 四批（顺序不可换）

| 批 | 动作 | 工作量 | 为什么在这个位置 |
|:--:|---|---|---|
| **A** | 引用白名单 + 引用必须带 `OriginalQuote` | 0.5 天 | 先关编造；否则后面所有收紧都会放大编造 |
| **B** | 祖先回退（5 行）+ `DoubtType` 落库 + 空模板正文规则 | 0.5 天 | 补确定性缺陷，不依赖分类质量 |
| **C** | 修 `manual` + 填 `DocFunction` + 部门归一 | 1 天 | 第二步的输入先备齐 |

### 7.2 验收指标（改完必须重跑基线）

| 指标 | 当前 | 目标 |
|---|---:|---:|
| 引用不在摘录（硬下限） | 42（15.8%） | **0** |
| 6 条零召回 | 6/56 | **0** |

### 7.3 为什么不能先收紧召回

§0.3 的曲线是硬约束：

```
doc_hit 0    → 编造率 100%
doc_hit 1–4  → 编造率 84.3%
doc_hit 5–9  → 编造率 33.3%
doc_hit ≥10  → 编造率 24.0%
```

召回越少，模型越依赖目录补内容。**在「目录可被当正文」的前提下，收紧召回 = 提高编造率。** 这不是理论推演，是 56 项的实测分布。

## 八、复现

### 8.1 关键 SQL

```sql
-- 基线结论分布（注意：Conclusion 全 NULL，值在 AiConclusion）
SELECT a.RunNo, r.AiConclusion, COUNT(*)
FROM cert_check_result r JOIN cert_check_analysis a ON a.Code = r.AnalysisCode
WHERE r.IsDeleted = 0 AND a.IsDeleted = 0
GROUP BY a.RunNo, r.AiConclusion;

-- 召回 / 摘录 / 利用率
SELECT r.ClauseNumber,
       JSON_EXTRACT(a.ResultSummaryJson, '$.doc_hit_count') doc_hit,
       JSON_EXTRACT(a.ResultSummaryJson, '$.excerpt_count') excerpt,
       r.Reason
FROM cert_check_analysis a JOIN cert_check_result r ON r.AnalysisCode = a.Code
WHERE a.RunNo = 1 AND a.IsDeleted = 0 AND r.IsDeleted = 0;

-- 体裁 × 条款号覆盖
SELECT JSON_UNQUOTE(JSON_EXTRACT(d.DocProfileJson, '$.DocTypeCode')) dt,
       SUM(e.ClauseNumbers IS NULL OR e.ClauseNumbers = '') no_clause,
       COUNT(*) c
FROM cert_document_extraction e
JOIN cert_enterprise_doc d ON d.Code = e.FileCode AND d.IsDeleted = 0
WHERE e.IsDeleted = 0
GROUP BY dt ORDER BY c DESC;

-- 空记录：RowCount 在 ModeOutput.Records[] 里，不是 ModeOutput.RowCount
SELECT dt,
       SUM(CASE WHEN rows_total = 0 THEN 1 ELSE 0 END) empty_rows,
       COUNT(*) c
FROM (
  SELECT d.Code,
         JSON_UNQUOTE(JSON_EXTRACT(d.DocProfileJson, '$.DocTypeCode')) dt,
         COALESCE((SELECT SUM(CAST(jt.rc AS UNSIGNED))
                   FROM JSON_TABLE(e.ContentJson, '$.ModeOutput.Records[*]'
                                   COLUMNS (rc INT PATH '$.RowCount')) jt), 0) rows_total
  FROM cert_document_extraction e
  JOIN cert_enterprise_doc d ON d.Code = e.FileCode AND d.IsDeleted = 0
  WHERE e.IsDeleted = 0
) t
WHERE dt IN ('record', 'audit_record')
GROUP BY dt;
```

### 8.2 脚本

### 8.3 已知局限（必须随结论一起引用）

1. findings 提示词未落库 ⇒ 「不在摘录」只能给区间，不能给精确值；
2. `doc_hit` 是**去重文档数**，不等于摘录条数（`ExcerptCount` 可能更多），所以「引用数 > `doc_hit`」是**保守**判据；
3. 手册引用已剔除，但 `doc_facts` 是否还包含其他文档的元数据未能完全排除 ⇒ 硬下限偏保守；
4. 仅 `iso9001` 有 97 份提取，14001/45001/13485 为 0，**跨标准结论不可外推**；
5. 56 项来自同一企业、同一任务，企业特征（如「记录多为空模板」）可能不具普遍性。
