# 02 · V4 总体方案

> 定位：V4 不是 V3 的补丁，是**换主线**。V3 的主线是"让 AI 写出一篇审核报告"，V4 的主线是"让 AI 为每个检查项交出一张可核对的取证清单"。
> 依据：`01-现状实测与问题定位`（R1–R5 五个根因）+ `60-V3单机版/95` 的 R-A/R-B/R-C/R-D 四条铁律 + `31` 的 U-1/U-4/U-5。

---

## 一、为什么必须换主线

V3 的目标是"生成报告"，而这个目标被三个事实锁死：

1. 报告里 19 项契约中只有第 12 项（逐条款审核发现）需要智能生成，其余 18 项是模板（U-5 已判定）；
2. 第 12 项的质量取决于输入事实，而输入被召回层砍到只剩手册与程序（实测四跑全 ofi）；
3. 专家判断你的产品只要 3 秒（U-4），他看的是"证据是不是真抽查过"，不是文笔。

**推论**：把资源投在"写报告"上，等于用 90% 的力气去做 18 项模板化的工作，而决定成败的第 12 项反而没有事实输入。

---

## 二、产品形态：检查项取证清单（Check Evidence Sheet）

### 2.1 输入 / 输出

| | 内容 |
|---|---|
| 输入 | 一个检查项 = 多条款 + 一个/多个部门 + 企业文档集 + 认证计划 |
| 输出 | 一张取证卡：**找到了哪几份文档 / 每份的关键事实与定位 / 缺哪一类 / 有哪些疑点 / 可直接进报告的句子** |
| 不出 | 整篇报告、不符合项判定、整改建议 |

### 2.2 一张取证卡的字段结构

```
检查项：8.4.1｜采购部
条款：8.4.1（含父条款 8.4）
────────────────────────────
A. 覆盖矩阵（机器算）
   应有：规定类 ✓ 2 份 ｜ 执行类 ✓ 1 份 / 应有 3 份 ｜ 结论类 ✗ 0 份
B. 事实条目（每条可点开定位到原文）
   F1《01供应商评审表》第 1 行｜江阴市金祺达｜2026.6.10｜结论"基本符合"
   F2 签署：采购部胥加娟 / 生产部黄勇 / 品质部张红红 / 总经理潘明海（同为 2026.6.10）
   F3《15外部提供过程产品服务控制程序》KSY-QMS-P-15 A/0｜规定五方面评价
C. 疑点（规则产出，每条带判据）
   D1 合格供方名录仅 1 家供应商（判据：清单类记录行数=1）
   D2 四个部门签署日期完全相同（判据：Signoff 日期去重后=1）
   D3 未见再评价记录（判据：程序要求"定期考核"，未见对应记录）
D. 证据句（模板+槽位产出，可直接进报告）
   "1、查阅《01供应商评审表》（2026.6.10）：对江阴市金祺达的资质、供货能力、
    产品质量、交货、服务六项评审，结论'基本符合'，经采购部、生产部、品质部
    签署，总经理潘明海批准，同意列入合格供方名录。"
```

### 2.3 为什么这个形态能赢

- 专家 3 秒判断的是"事实真假"，这张卡每条都能点开原文，天然可信；
- 绕开机构模板差异（不写整篇报告）；
- 可**按检查项验收、按检查项交付**，不依赖全局跑通；
- 正好是 V3 的第一步（97 号已证明 8.4 能做到 11/12 可进草稿，只是没接线）。

## 三、一颗原子：EvidenceItem

V3 的致命缺陷是"证据"不是对象（`cert_evidence` 0 行）。V4 把证据条目录成表，全链路只认它。

### 3.1 字段定义（表 `cert_evidence_item`）

| 字段 | 类型 | 说明 |
|---|---|---|
| CheckItemCode | varchar(36) | 检查项（计划明细） |
| ClauseCode / ClauseNumber | varchar(36/20) | 条款归属；**召回轴进来的行允许为空** |
| DocCode / DocName | varchar(36/300) | 来源文档 |
| DocType | varchar(20) | 规定类 / 执行类 / 结论类 |
| Anchor | varchar(500) | 定位：章节标题 / 表格行 / 页脚编号（**必须在原文唯一可查**） |
| Excerpt | text | 原文摘录（不改写、不概括） |
| FieldName / FieldValue | varchar(100/500) | 记录类字段（如"结论=基本符合"） |
| IsBlank | tinyint | 该字段原文为空 |
| OwnerDept | varchar(100) | 责任部门 |
| Period | varchar(100) | 覆盖期间（如 2026.6.10） |
| RecalledBy | varchar(20) | 召回轴：`clause` / `process` / `dept` |
| Confidence | decimal(3,2) | 抽取置信度 |
| EvidenceKind | varchar(20) | `doc` / `record_field` / `onsite` |

### 3.2 三条硬约束

1. **Anchor 必须可唯一定位**：定位不到就不入库（对应 V3 的 `DocumentSourceLocator.LocateUnique` 返回 null 的问题）。
2. **一条 EvidenceItem 只挂一个条款**；跨条款的共性事实要复制成多条，不合并。
3. **IsBlank=1 的字段也是证据**（"该栏为空"本身是疑点依据），但不得写成"未提供"。

## 四、三个阶段：谁做什么

V3 是一条提示词三合一。V4 拆成三段，**明确"机器 / 规则 / 模型"的分工**：

| 阶段 | 产出 | 谁做 | 为什么这样分 |
|---|---|---|---|
| ① 事实层 | EvidenceItem 列表 + 覆盖矩阵 | **机器为主**（抽取产物投影）+ 模型只做补充 | 事实必须可核对，不能让模型"回忆" |
| ② 疑点层 | Doubt 列表 + 判据 | **规则为主（≥80%）**，模型只补"非机械可判"的 | 见 §4.2 |
| ③ 证据层 | 证据句 + 槽位填充 | **模板骨架固定 + 模型只写叙述** | 见 §5 |

### 4.1 事实层：不做"生成"，只做"投影"

抽取产物（`ModeOutput`）里已经有 Records / Samples / Signoff / FormFields / Coverage，V4 的工作是**把这些投影成 EvidenceItem**，不是重新读文档让模型总结。

- 记录类：`Records[].Samples[]` → 逐行 EvidenceItem；`Signoff[]` → 一条汇总 EvidenceItem；
- 程序类：`KeyControls / KeySteps` → EvidenceItem（Anchor = 条款位置）；
- 手册类：只写"建立并保持《XX》"，不作为运行证据。

### 4.2 疑点层：90% 由规则算，模型只补剩下的

可机械判定的疑点（**不调模型**，直接算）：

| 疑点类型 | 判据 |
|---|---|
| 记录为空 | `RowCount=0` 或 `Samples` 为空但记录被程序引用 |
| 关键字段空 | 合同/评审/检验类必填字段（结论、日期、签署）为空白 |
| 跨文档对不上 | 程序要求"定期考核"，但无考核记录；标准要求"名录批准"，名录无批准人 |
| 日期集中 | 同一记录集内日期去重后 = 1 |
| 签署缺人 | `Signoff` 人名缺失 / 部门缺失 |
| 覆盖期不齐 | 记录期间未覆盖审核期（如只有 2026.6 一个月） |
| 名录过少 | 清单类 `RowCount < 阈值`（如供应商 < 3 家） |
| 语法性空洞 | "符合要求"类结论无对应评分/数据支撑 |
| 程序引用了记录但记录从未填 | 程序文本含《XX表》引用，且该表 `RowCount=0` |
| 同一模板多处复用 | 多份记录正文相似度 > 阈值 |

**为什么必须规则化**：数据实验证明，模型看到记录就把疑点归零（2 条 → 0 条）。疑点若交给模型，等于把"发现问题"这件事交给最不愿意发现问题的一方。

模型只做一件事：把规则命中翻译成审核员语言的一句话（`point` + `detail`）。

### 4.3 证据层：模板 + 槽位

- 骨架：机构报告的句式（"1、查阅《X》（编号/版本/日期）：……"），**由专家提供，固定**；
- 槽位：`{{doc_name}} {{doc_code}} {{period}} {{row_count}} {{conclusion}} {{signoff}}` 等，全部来自 EvidenceItem；
- 自由文本：只保留"该条款整体叙述"一段，且必须逐句挂 EvidenceItem 编号；
- **不允许模型新增事实**：出现未挂编号的事实即判不合格（机器校验）。

## 五、召回模型：不再让文档自报条款

这是 V4 与 V3 最大的结构差异。

### 5.1 三条召回轴 + 优先级

| 优先级 | 轴 | 适用 | 命中条件 | ClauseCode |
|---|---|---|---|---|
| 1 | 条款轴 | 规定类 | 条款号精确或**父级覆盖**（7.1.5 命中 7.1.5.1） | 有 |
| 2 | 过程轴 | 执行类 | `ProcessArea` ∈ 检查项的条款属性 `过程` 集合（如 8.4.1 → `purchase`） | **空**（Anchor 写"过程召回"） |
| 3 | 部门轴 | 执行类 | `OwnerDept` ∈ 检查项的部门集合，**只加权不硬过滤** | **空**（Anchor 写"部门召回"） |

### 5.2 四个硬约束（沿用 97 号已验证的结论）

1. 过程轴/部门轴**只在条款轴命中不足时启用**（避免噪声）；
2. 召回行 `ClauseCode` 必须为 `null`，机制上不可能串条款；
3. 空文本/空关键词一律不召回；
4. **每个检查项的召回结果设配额**：规定类 ≤ 3 份、执行类 ≤ 6 份、结论类 ≤ 2 份，按"记录行数多、期间新"排序。

### 5.3 覆盖矩阵（新增，机器算）

对一个检查项，先算"应该有哪些"，再看"实际找到哪些"：

```
应有（按条款属性 + 文档类型推导）：
  规定类：程序 ≥1
  执行类：记录 ≥1（采购→评审表/名录/考核表；生产→首件/巡检/放行）
  结论类：内审报告 / 管理评审 / 检验报告 ≥1
实际命中：规定类 2 / 执行类 1 / 结论类 0
缺口：执行类缺"再评价记录"、结论类缺全部
```

**覆盖矩阵是"漏信息"的唯一解药**：它把"该找什么"从"模型猜"变成"机器算"。

## 六、数据契约：一张表、一套枚举

V3 有 4 套 DocType、3 套 RecordState、3 套 Period（94 号 §六）。V4 强制收敛：

| 概念 | 唯一取值 | 权威位置 |
|---|---|---|
| DocType | `规定类 / 执行类 / 结论类` | `cert_doc_field_def`（66 号字段字典） |
| RecordState | `空白 / 部分 / 完整` | 同上 |
| Period | 单字段 `Period`（字符串，如 `2026.6.10` 或 `2026.1-2026.6`） | 同上 |
| 召回轴 | `clause / process / dept` | 本方案 §5.1 |
| 疑点类型 | 10 类（§4.2 表） | `cert_evidence_item.DoubtType` |

**迁移规则**：新字段必须带 `schema_version`；旧产物不迁移则标 `IsStale=1`，不得进入装配。

## 七、提示词：一张表、三阶段、示例驱动

### 7.1 表结构收敛

- 废弃 `wf_prompt_template`（2 条）；
- 全部收敛到 `cert_prompt_template`，`PromptCode` 固定三段：`ev_fact_*` / `ev_doubt_*` / `ev_evidence_*`；
- **状态只有 `active` / `shadow` 两态，且 `active` 必须能被运行时解析到**（加一条自检：`active` 但无人调用即告警）。

### 7.2 每条提示词的结构（示例优先）

按 01 号实测的教训（规则弱于示例），每条提示词固定三段：

```
【角色与任务】一句话
【输入】明确的 JSON 字段（不放自由文本）
【示例】2–3 段真实报告段落（这才是决定输出形态的东西）
【规则】只写"不许做什么"，不超过 10 条
【输出】JSON schema
```

### 7.3 三段提示词的分工

| 提示词 | 输入 | 输出 | 禁止 |
|---|---|---|---|
| `ev_fact_clause` | 条款 + 文档切片 | `{findings:[{doc,anchor,excerpt,field,value,blank}]}` | 禁结论、禁"未提供"、禁跨条款合并 |
| `ev_doubt_rule` | findings + 规则命中 | `{doubts:[{type,point,detail,rule_id}]}` | 禁新事实、禁判 NC |
| `ev_evidence_asm` | findings + doubts + 机构模板 | `{slots:{...}, narrative:"..."}` | 禁新增事实、禁写否定句、禁写"符合要求" |

## 八、装配：报告用槽位，不用自由生成

- `cert_report_clause_map` 驱动：检查项 → 报告章节 → 段落模板；
- 机构差异 = 模板配置（章节顺序、句式、术语），不改代码；
- 第 12 项之外的 18 项全部填槽；
- 换机构 = 换一份模板 + 一次回归，不改系统。

---

## 九、与 V3 的差异一览

| 维度 | V3 | V4 |
|---|---|---|
| 主线 | 生成整篇报告 | 检查项取证清单 |
| 证据 | 不是对象（0 行） | `cert_evidence_item` 一等公民 |
| 召回 | 文档自报条款，记录类全丢 | 三轴（条款/过程/部门）+ 覆盖矩阵 |
| 疑点 | 模型判，看到记录就归零 | 规则算（≥80%） |
| 提示词 | 两张表、三层 shadow、生产跑三合一 | 一张表、三阶段、示例驱动 |
| 输出 | 一份 JSON 六样东西 | 三份契约产物，逐段可校验 |
| 验收 | 看整体报告像不像 | 覆盖完整率 / 定位命中率 / 疑点精确率 / 专家可用率 |

## 十、V4 明确不做

1. 不做机构级流程管理（计划/派员/上报/风险模型）——用户已否决；
2. 不做 NC 自动判定——R-C 已定死；
3. 不做现场手写 OCR——改为"说 / 选 / 拍"三动作；
4. 不做全行业通用模板——一家一家配置；
5. 不碰 VidLang；
6. **不再新写提示词文本，除非同时给出示例与回归结果**。
