# 05 · 条款与文档的分析建模

> 这份文档补的是 04 缺的那块：**条款怎么建模、文档怎么分类、文档和报告是什么关系**。
> 结论先给：这三件东西跟机构无关、跟认证任务无关、不随标准变，是系统的核心资产；代码只是载体。

---

## 一、为什么说"模型才是资产"

一个判据就够：**换个机构、换个标准，模型要不要重做？**

- 换机构（科斯亚 → 双尼）：条款清单变、报告句式变，但"条款要拆成哪几维""文档要分哪几层"不变 → **模型复用**。
- 换标准（19001 → 45001）：条款编号全变，但"每条条款都要判证据形式"不变 → **模型复用**。

代码会过时、提示词会被换掉，只有这两张模型 + 一张映射能沉淀下来。所以：

```
核心资产 = 条款模型 + 文档模型 + 文档↔报告映射
代码     = 模型的读写界面
提示词   = 模型的临时执行器
```

这条判据同时否掉了"提示词是核心"这个判断——提示词是耗材，模型是资产。

## 二、条款模型

### 2.1 条款不是一段文字，是一个六元组

GB/T 的每一条款，都能拆成六个维度：

```
条款 = (主体, 动作, 对象, 条件, 证据形式, 判定口径)
```

以 8.4.1（采购过程）为例：

| 维度 | 取值 |
|---|---|
| 主体 | 采购部（品质部会签） |
| 动作 | 建立 / 实施 / 保持（准则、评价、选择、监视、再评价） |
| 对象 | 外部供方（供应商） |
| 条件 | 按准则、定期（年/批）、变更时 |
| 证据形式 | 规定：采购控制程序；执行：合格供方名录、评审表、业绩记录 |
| 判定口径 | 名录是否经批准 / 评审是否多部门 / 有无业绩记录 / 有无再评价 |

### 2.2 六个维度的可获取性差别很大

这一列是整份文档里最实用的判断：

| 维度 | 怎么得到 | 是否需要模型 |
|---|---|:--:|
| 主体 | 条款原文 + 计划部门列 | 否（查表） |
| 动作 | 动词表映射（建立/保持/评审/批准…） | 否（词表） |
| 对象 | 同上 | 否（词表） |
| 条件 | 频次词归一（定期/每年/必要时 → 枚举） | 否（正则） |
| **证据形式** | 必须人工配置 —— **它是召回的唯一依据** | 否，但**必须配全** |
| 判定口径 | 只能来自专家经验 | 是（人工配） |

一句话：**六维里四维可规则化，一维靠配置，一维靠经验。**现在的系统卡在"证据形式"这一维配得不全，所以召回全瞎。

### 2.3 可判定度分级：A / B / C

这条直接回答"我能不能吃透 GB/T"。答案是——**不需要吃透，只需要给每条条款标一个等级**。

| 级别 | 定义 | 典型条款 | 系统能力 | 覆盖率预期 |
|:--:|---|---|---|:--:|
| **A 结构可判** | 存在性、批准、日期、版本、覆盖期、数量、字段完整 | 4.2.3 文件控制、7.1.5 监视测量资源、8.4.1 采购 | 规则引擎 100% 判定，机器出结论 | ≈ 40% |
| **B 关系可判** | 跨文档一致、覆盖充分性、频次符合、抽样代表性 | 8.4.1 名录 vs 评审表是否一致、9.2 内审覆盖部门 | 规则 + 阈值，输出"高度疑似" | ≈ 35% |
| **C 价值判断** | 有效性、适宜性、风险识别是否到位 | 5.1 领导作用、6.1 风险应对有效性、9.3 管理评审充分性 | **系统不判，只提供材料** | ≈ 25% |

**这是整个产品最重要的一次取舍。**它把"我不懂 GB/T"从致命问题降级为可管理问题：C 级条款你不懂，是因为你不做它；A/B 级条款你只需要懂"结构长什么样"，而这个东西查表就有。

同时它解决了专家的问题：专家最擅长的恰恰是 C 级判断，而 C 级我们不做——**所以不需要说服专家接受 AI 下结论，AI 只在他做判断之前把材料摆齐。**

### 2.4 现有 12 个属性定义 vs 六元组

`cert_clause_attr_def` 有 12 个定义、`cert_clause_attr` 有 4038 行值。需要做一次对齐（实际 12 个名字要现场核对，此处只给方法）：

1. 把 12 个属性逐个归到六元组的某一维；
2. 六维里没有对应属性的维度 → 标注"缺失"（大概率是"条件"和"判定口径"）；
3. 六元组之外的属性 → 标注"冗余"，考虑合并；
4. 为每条条款补一个 **`JudgeLevel`（A/B/C）** 属性——**这是要新增的第 13 个属性，也是最有用的一个。**

## 三、文档模型

### 3.1 一个 DocType 字段扛了三件事，所以必然乱

"这份文档是什么"其实是三个独立问题的答案：

| 问题 | 维度 | 决定什么 |
|---|---|---|
| 怎么抽？ | **体裁（Genre）** | 抽取模式（表单抽行 / 段落抽义务 / 抽结论） |
| 能不能当证据？ | **职能（Function）** | 是"规定"还是"做过的痕迹" |
| 给哪个检查项？ | **归属（Attribution）** | 过程、部门、期间 |

现有代码里 DocType 有 4 套并存，根因就是**想用一个字段同时回答三个问题**。拆开就没事了。

### 3.2 体裁（第一层）

```
手册 / 程序文件 / 指导书（作业指导、工艺、检验规范） / 记录（表单、清单、台账、报告） / 方针目标 / 计划 / 外部文件（标准、法规、客户要求）
```

体裁**必须靠规则匹配**（文件名 + 表头 + 结构特征），不靠模型。因为一份"XX记录表"和一份"XX程序"，文件名和表头差异是稳定的。

### 3.3 职能（第二层）：可规则推导，不需要标注

这是本节最关键的一条：**"规定类 vs 执行类"不用人工标，用三个信号就能判**。

| 信号 | 判据 |
|---|---|
| 有具体数据 | 出现供应商名、人名、数字、日期、批次号 |
| 有签署 | 签名字段非空（`Signoff` 有值） |
| 有覆盖期 | 有起止日期或"第 X 年" |

- 3 个信号命中 ≥ 2 → **执行类**（可当证据用）
- 全部为 0 → **规定类**（只能当依据/引文用）
- 1 个 → **混合类**（模板+少量填写，标 `template_only`，93 号的结论）

实测验证：《01供应商评审表》有供应商名 + 4 人签署 + 2026.6.10 → 命中 3 → 执行类 ✅。这是代码本来就能算出来的，`ModeOutputProjector` 应该做这件事，而不是让模型输出 `DocClass`。

**推论**：文档分类这件事，60% 可以由规则完成，模型只补"体裁识别"和"归属判断"两件。

### 3.4 归属（第三层）：三路投票，不信单点

判断"这份文档属于采购过程"，不要相信模型一次判断，用三路投票：

1. **文件名关键词** —— "供应商/采购/供方/进货"
2. **抽出的 `OwnerDept`** —— 采购部
3. **表头/字段名** —— 有"供应商名称""供货范围"列

三路里有 2 路一致 → 归属成立。规则可实现，而且失败时可解释（能告诉用户"因为文件名和部门都指向采购"）。

### 3.5 文档分类的最终形态

一张规则表（就是 `doc-extract-rule` 页面该配的东西），每行一条规则：

| 字段 | 含义 |
|---|---|
| `RuleCode` | 规则编号 |
| `MatchPattern` | 文件名正则 + 表头必含字段 |
| `Genre` | 体裁 |
| `Function` | 职能（规定/执行/结论） |
| `ProcessArea` | 默认过程归属 |
| `ExtractMode` | 抽取模式（表单/段落/结论/索引） |
| `DefaultReportRole` | 默认报告角色（见 §四） |
| `RequiredFields` | 该体裁必须抽到的字段（缺则判抽取不合格） |

**一份文档进来 → 匹配规则 → 得到（体裁, 职能, 归属, 抽取模式, 报告角色）→ 抽取 → 进证据池。**

这条链是**配置驱动**的，不是提示词驱动的。加一类新文档 = 加一行规则，不写提示词。

## 四、文档 ↔ 报告映射

### 4.1 报告里的句子只有四类

拆开 4 家企业的真实报告，审核证据的句子结构其实高度固定：

| 角色 | 句式 | 例 |
|---|---|---|
| **① 制度依据** | 查见《X》（编号），规定了…… | 查见《采购控制程序》（QP-07），规定了供方选择、评价、再评价的准则 |
| **② 执行证据** | 抽查 N 份《Y》，其中…… | 抽查 3 份《供应商评审表》，3 份均有多部门签署，结论"基本符合" |
| **③ 结论证据** | 查见《Z》，结论为…… | 查见《2026年度供方业绩评价报告》，结论为合格供方 12 家 |
| **④ 现场证据** | 现场查见……（见照片 N） | 现场查见原料区标识完整，待检/合格分区清晰（见照片 3） |

**只有这四类。没有第五类。**

### 4.2 角色由（体裁 + 职能）唯一决定

| 体裁 | 职能 | 报告角色 | 必填字段 |
|---|---|---|---|
| 手册 / 程序 / 指导书 | 规定 | ① 制度依据 | 文档名 / 编号 / 版本 / 企业自述段落 |
| 记录 | 执行 | ② 执行证据 | 数量 / 抽样行 / 关键字段值 / 签署 / 日期 |
| 报告 / 评价 | 结论 | ③ 结论证据 | 结论值 / 日期 / 批准人 |
| — | — | ④ 现场证据 | 照片编号 / 观察点 |

**一个角色 = 一种句式 + 一组必填字段。** 所以报告段落的生成不是"让模型写"，而是：

```
选角色 → 检查必填字段齐不齐 → 齐则填模板 → 缺则标注缺什么
```

**这就是"报告装配"的全部逻辑。**模型只在最后一步"把字段值连成通顺的审核员语言"时介入，介入比例大约 30%。

### 4.3 这个映射能拦住 97 号发现的那个错

97 号 §12 记录过："手册证据变成了标准条文"——即引了 GB/T 原文，不是企业自己写的。

用映射规则拦：① 制度依据 的槽位值，`SourceType` 必须是"企业"，`Excerpt` 必须来自该文档的被引段落。标准原文的 `SourceType=标准` → 直接拒绝入槽。

**这类错不需要改提示词，只需要一个字段校验。**这也是"装配优于生成"的具体兑现。

### 4.4 同一份文档在不同检查项里角色不同

手册在 8.4.1 是 ① 制度依据，在 4.4（文件控制）里可能又是 ② 执行证据（要看它有没有审批签署页）。所以映射必须挂在 (文档, 检查项) 这一对上，不能挂在文档上。

→ 这决定了 `cert_report_clause_map` 必须含 `CheckItemCode`（04 号里已写）。

## 五、为什么提示词正好是两类（回答你第 7 条）

你说"发现 + 组织"两类，这个分法是对的，而且**分界线不是感觉，是有判据的**：

| | 第 1 类：审核发现 | 第 2 类：证据组织 |
|---|---|---|
| 输入 | 原始文档文本 | 结构化字段（EvidenceItem） |
| 输出 | 结构化事实 + 疑点 | 自然语言句子 |
| 本质 | **理解**（非模型不可） | **装配**（模板为主） |
| 模型占比 | 90% | 30% |
| 失败模式 | 漏、串条款 | 编、空话、引错来源 |
| 约束手段 | 契约 + 校验器 | 模板 + 槽位校验 |

**判据一句话：输入是原始文本 → 必须用模型；输入是结构化字段 → 用模板，模型只润色。**

这条判据解释了你一直想不通的那个现象：**为什么"豆包 + 模板"能出可用结果，而你写提示词不行。**

因为豆包那个场景，人实际做的是两件事：
1. 人用豆包做**第 1 类**（问"这份评审表说明了什么"）；
2. 人自己用**模板**做**第 2 类**（把结果填进报告的固定句式）。

两件事都在人的眼前完成，中间有人筛。而你的系统把两件事塞进**一条提示词**，让模型一次做"理解 + 装配"，且中间没有人的判断——于是它只能靠猜，猜出来的就是"未见记录、未提供样本"这种恒定话术。

**所以你说的"漏了一步"，漏的不是一个提示词，是"发现"和"装配"之间那道人的/规则的筛子。**

## 六、从模型反推模块（这也解释了为什么只有 8 个页面）

把模型的生命周期画出来，是"定义 → 填充 → 应用"三段：

```
定义层    iso-clause（条款树）  clause-attr-def（属性定义）  doc-extract-rule（文档分类规则）
            ↓                        ↓                          ↓
填充层    clause-attr（条款属性值）                    enterprise-doc（文档 + 抽取结果）
            ↓                        ↓                          ↓
应用层    audit-plan（选检查项）→ audit-prep（文件评审/发现）→ audit-onsite（现场/证据组织）
```

**8 个页面，正好是这 3×3 的格子里有内容的那些。** 这不是巧合——你凭直觉划出来的 8 个核心，正好是模型的自然结构。

反过来说，不在这个格子里的，都不是核心：

| 残留 | 为什么是残留 |
|---|---|
| `cert_evidence` 手工 CRUD | 证据该由抽取产生，不该人工挂 |
| `cert_report_section`（0 行） | 报告还没到装配阶段，这张表是提前占位 |
| `GapDetector` 独立页面 | 缺口是疑点的一种，应并入 audit-prep |
| `cert_check_result` 多套词表 | 判定口径未收敛，V1 遗留 |
| `cert_prompt_template` 与 `wf_prompt_template` 并存 | 两代实现，必须并表 |

**所以"新建分支 + 彻底删残留"这个决定是对的**，而且删除本身有判据：凡不在 §六 这个格子里的，删。

## 七、这份模型怎么才能被验证（衔接 06）

模型最大的风险不是设计错，是**没人能核对**——专家不懂建模，你也不能闭门自证。

但这套模型有一个好处：**它的每一维都留了可检验的痕迹**。

- 属性抽得出抽不出 → 反向覆盖率矩阵（06 §二）
- 归属对不对 → 跨文档一致性（06 §三）
- 报告角色对不对 → 4 份真实报告反推（06 §四）
- 句式像不像 → 专家做判别不做建模（06 §五）

也就是说，模型不是"信则有"的，它可以被数据打脸。详见 `06-属性与文档模型的自验证方案`。
