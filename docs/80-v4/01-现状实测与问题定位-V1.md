# 01 · V3 现状实测与问题定位

> 实测对象：`src/certplatform-api`（生产代码）+ `yzh_cert_platform`（生产库）+ 科斯亚第二阶段审核计划（56 个检查项）。
> 实测方法：启动全套环境（MySQL 3307 / Redis 6380 / MinIO 9000 / 后端 9992 / admin 9990 / auditor 9991），用 `api/Auditor/CertTask/analyze-item` 对真实检查项逐项跑通，逐层核对输入快照、抽取产物、数据落库。
> 与 94 号的关系：94 号是"读文档 + 读代码"的静态评估（自评 5.0/10）；本篇是"跑真实链路"的动态实测，把 94 号的推断变成了实证。

---

## 一、一页结论

| 结论 | 证据 |
|---|---|
| 当前系统对任何条款都产出同一种结果 | 四跑（8.4.1 / 7.1.5.1 / 8.2.1 / 8.5.1）**全部 `ofi`**，疑点 2–3 条，证据全部是"查阅程序 + 未见记录" |
| 输出恒定不是提示词问题，是**输入恒定** | 记录类文档 86/99 份条款归属为空，被召回层整份丢弃；留下的只有手册与程序 |
| 召回在**系统性奖励旧格式、惩罚新格式** | 新结构文档（含 `ModeOutput`、Records/Samples/Signoff，质量高）因 `PrimaryClauses=[]` 被丢；旧结构文档（只有 `Clauses`、`ModeOutput` 为空、质量低）反而命中 |
| 你写的三层提示词从未生效 | `doc_fact` / `clause_evidence_findings` / `audit_check_evidence` 在 `cert_prompt_template` 中状态全为 **shadow**；检查引擎读的是**另一张表 `wf_prompt_template`** |
| "证据"不是系统的一等对象 | `cert_evidence` 0 行；`EvidenceUsedCount=0`；引擎把拼好的文本直灌模型，一次生成结论+证据+疑点 |
| 现有架构不是三层，是**单层直出** | 一次 prompt 调用 20 秒，同时产出 `conclusion / clause_evidence / doubts / nc_draft` |

**一句话**：V3 的失败不在"提示词写得不够好"，而在**抽取层与召回层之间的契约断裂**——最好的数据被丢掉，最差的数据被留下，模型只能得出"有制度、无执行"这一个结论。

## 二、实测数据

### 2.1 四次实跑（同一企业、同一计划、`LockedMode=override`）

| 条款 | 部门 | 结论 | 疑点 | 命中文档 | 证据形态 |
|---|---|---:|---:|---:|---|
| 8.4.1 | 采购部 | ofi | 2 | 3 | 手册+程序，写"未见《供应商评审表》" |
| 7.1.5.1 | 品质部 | ofi | 3 | **1** | 仅手册，写"未提供台账/校准记录" |
| 8.2.1 | 销售部/采购部 | ofi | 3 | 3 | 手册+程序+信息联络单 |
| 8.5.1 | 生产部/品质部 | ofi | 3 | 5 | 手册+4 份程序，无任何生产记录 |

单次耗时 20–27 秒，模型 `qwen-plus`，输入 9.6K–21.7K 字符，输出 700–1,200 字符。

### 2.2 召回层：三个过滤器叠起来，把执行证据全部排除

抽样 7 份文档，抽取产物对比如下：

| 文档 | DocType | PrimaryClauses | 是否进入检查项输入 |
|---|---|---|---|
| 01供应商评审表.doc | record | `[]` | 丢 |
| 02合格供应商清单.doc | record | `[]` | 丢 |
| 03-首件报告.doc | record | `[]` | 丢 |
| 04制程巡检报告.doc | record | `[]` | 丢 |
| 03监视和测量设备控制程序.doc | procedure | `["7.1.5"]` | 丢（检查项是 7.1.5.1，父子不匹配） |
| 17生产和服务提供控制程序.doc | procedure | `["8.1"]` | 丢（检查项是 8.5.1） |
| **01信息联络单.doc** | **NULL**（旧结构，仅 `Clauses` 5 条） | `["7.4","8.2.1"]` | **留下** |

三个过滤器：

1. **记录类无条款** —— 这是**设计决定**（`ClauseEligible` 只允许手册写条款，97 号 §10.7 撤销条款兜底时的正确选择）。结果是 86/99 份 `ClauseNumbers` 为空、`ClauseCount=0`。
2. **程序类只有粗条款号** —— `CertCheckContextBuilder.ParseModeOutputSlices` 用 `wantedNumbers.Contains` 精确匹配，7.1.5 不会命中 7.1.5.1。
3. **旧格式文档有细条款号** —— 只写了 `Clauses`、没有 `ModeOutput` 的文档，反而能通过老路径命中。

### 2.3 那个"整份丢弃"的代码位置

`CertPlatform.Auditor/Services/Expert/CertCheckContextBuilder.cs`，`ParseModeOutputSlices`：

```
读取 PrimaryClauses + SupportClauses → 与本次检查项条款求交集
交集为空 → return result   ← 整份文档不产生任何切片（86 份记录类在此消失）
```

这不是 bug，是**契约与消费逻辑的直接冲突**：抽取侧按契约不给记录写条款，消费侧却把"有无条款"当作准入条件。

### 2.4 数据实验（可回滚，已恢复）

给《01供应商评审表》临时补 `PrimaryClauses: ["8.4.1"]`，重跑 8.4.1，只多 1 份文档、输入增加 1,080 字符：

| | 补之前 | 补之后 |
|---|---|---|
| 证据句 | "未见《供应商评审表》…未提供任何成文信息样本" | "查阅《01供应商评审表》（江阴市金祺达，2026.6.10）：采购部牵头，生产部、品质部、总经理多部门签署，六项评审，结论'基本符合'，同意列入合格供方名录" |
| 疑点 | 2 条 | **0 条** |
| 结论 | ofi | unknown |

**两个结论**：

1. 召回是瓶颈——一份文档的条款归属，就能让证据从"空话"变成"可核查的事实"；
2. 但疑点随之归零——证明模型是"先定结论、再配证据"，不是"先列发现、再判疑点"。**这正是"缺少发现层"的实体证据。**

## 三、提示词现状：两套表、三条影子

### 3.1 两张提示词表并存

| 表 | 行数 | 谁在读 | 内容 |
|---|---:|---|---|
| `cert_prompt_template` | 19 | `DocExtractPromptService`（抽取层） | 15 条 `doc_extract_*` 生效 + 3 条三层提示词 shadow |
| `wf_prompt_template` | 2 | `IPromptWorkbench.ResolveActiveAsync`（检查层） | `audit_prep`(1,600)、`audit_check`(3,896) |

**检查引擎读的是 `wf_prompt_template`，你写的三层在 `cert_prompt_template`——它根本不读那张表。**

### 3.2 三层提示词的真实状态

| PromptCode | 名称 | 状态 | 体积 |
|---|---|---|---:|
| doc_fact | 文档事实层 v5.3.1 | **shadow** | 2,027 |
| clause_evidence_findings | 条款证据发现层 v5.3 | **shadow** | 12,388 |
| audit_check_evidence | 认证检查证据层 v1 | **shadow** | 3,916 |

`Remark` 与你 95 号的设计完全一致，说明设计是清楚的——**缺的是接线，不是设计**。

### 3.3 生产实际在跑的那一条：3,896 字符，三合一

一次输出六样：

```
{"conclusion","summary","audit_evidence","clause_evidence","recommendation",
 "confidence","nc_suggestion","severity_suggestion","evidence_codes","doubts","nc_draft"}
```

两条与你自己裁决相冲突的地方：

- 95 号 R-C：全链路 `NcCandidate` 字段数 = 0、"不符合"出现次数 = 0；而这条提示词把 `nc_draft` 写成了输出结构的必填项。
- 31 号 U-1：不符合项不是核心、符合项才是；而输出结构迫使模型**先交结论、再配证据**。

它写了"不要写否定句"，实测四次全部写了"未提供/未见"。**规则约束打不过结构约束。**

## 四、五个根因（按影响面排序）

| # | 根因 | 影响面 | 修复量级 |
|---|---|---|---|
| R1 | 召回层按"文档自报条款"准入，记录类 86/99 被丢 | 100% 的执行证据 | 半天（改召回分支） |
| R2 | 程序类粗条款号不匹配叶子条款，父子不认 | 所有 `x.y.z` 类检查项 | 1 小时 |
| R3 | 证据不是一等对象（`cert_evidence` 0 行），三层无中间产物 | 无法追溯、无法装配 | 3–5 天（建表+写入） |
| R4 | 三层提示词 shadow 且读错表，无编排器 | 全部生成质量 | 3–5 天（合并表+接线） |
| R5 | 疑点全靠模型判，看到记录就归零 | 疑点可信度 | 3–5 天（规则化） |

## 五、对 94 号的修正

94 号判断"瓶颈是契约多套并存 + 运行时缺位"，实测确认；但有一处需要修正：

> 94 号认为"继续调提示词边际收益低于副作用"。
> **实测进一步确认：在 R1/R2 修复之前，调提示词的边际收益为零**——因为输入恒定，提示词再怎么写也只能得到"有制度、无执行"。

## 六、复现步骤

1. 启动：`bash docker/start.sh` → `bash scripts/backend/run-backend.sh` → `bash scripts/frontend/start.sh all start`
2. 取登录态：`sys_user` 中 `wzm` 的 `Token`（30 天有效），请求头 `Authorization: Bearer <token>`
3. 取检查项：`POST /api/Auditor/CertTask/plan-checklist`，body 为计划 Code
4. 跑单项：`POST /api/Auditor/CertTask/analyze-item`，body `{"TaskItemCode":"...","LockedMode":"override"}`
5. 看输入：`cert_check_analysis.InputSnapshotJson`（最近一条）——关注"命中企业文档 N 份、摘录 M 条"
6. 看抽取：`cert_document_extraction.ContentJson` 的 `ModeOutput.PrimaryClauses` / `DocType` / `ProcessArea`

数据实验的回滚：把 `ModeOutput.PrimaryClauses` 设为 `JSON_ARRAY()` 即恢复原状。
