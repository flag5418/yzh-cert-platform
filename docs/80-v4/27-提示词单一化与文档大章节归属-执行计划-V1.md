## 五、批 3 ★ 文档大章节语义归属（本次核心）

### 3.1 为什么必须「先判大章节」

用户口径：**大章节与部门是这套机制的前提**；记录/过程类文档**从文档本身看不出属于哪一章**，但**章本身有语义**，所以只能靠语义分析得到归属。

与 26 号实测的关系（两者不矛盾，是互补）：

| 26 号结论 | 本批如何回应 |
|---|---|
| 44/44 记录**没有条款号** ⇒ 靠章号过滤无从下手 | ⇒ 不用章号，用**章节原型语义**做匹配（这正是用户口径） |
| `ChapterDomains` 只对手册（`Toc`）可靠 | ⇒ 拆两档：**确定性档**（手册 `Toc` / 审核记录 `ClauseNumbers`）+ **语义档**（记录 / 程序 / 作业指导） |
| 先上 Stage1 硬过滤会误杀 | ⇒ 本批**只产归属、不过滤**；过滤推迟到批 5，且 Stage1 只做权重 |

### 3.2 两级「章语义」资产

| 侧 | 来源 | 是否需 LLM |
|---|---|---|
| **条款侧 `ChapterDomain`** | 章号确定性映射：4→`CD_ENV`、5→`CD_LEAD`、6→`CD_DECIDE`、7→`CD_SUPPORT`、8→`CD_RUN`、9→`CD_ASSESS`、10→`CD_IMPROVE`（`23` 号 §2.1 枚举） | ❌ 确定性，一条 SQL 回填 |
| **章节原型定义**（一等资产） | `23` 号 §2.1.1：每章「名称 + 作用 + 释义 + 典型证据 + PDCA」，作为**语义匹配锚** | 一次性撰写，之后只维护 |
| **条款释义四要素** | `ClausePurpose` / `EvidenceChain` / `EvidenceCheck` / `ClauseScope`（`23` 号 §3.2） | 依赖批 4 的属性补全 |

### 3.3 判定链路（三级优先级，⛔ 不硬推）

```
每份文档
  ↓
① 确定性档（0 LLM）
   手册            → Toc 章号 → ChapterDomains[]
   审核记录        → ClauseNumbers（24/26 有）→ ChapterDomains[]
   表格记录/过程/作业指导 → 不适用，进 ②
  ↓
② 关键词档（0 LLM，纯字符串包含）
   输入 = 语义骨架（简介 + 目的 + 范围 + 目录标题）+ 文件名
   用 7 章「章节原型关键词」（Strong 权重3 / Normal 权重1）做包含匹配
   ⇒ 命中即落（≤3 章）；来源标记 ChapterDomainsSource='semantic'
  ↓
③ 语义档（LLM 兜底，仅 ①② 均判不出即源='unknown' 时触发）
   输入 = Abstract（语义骨架）+ DocType + 章域原型定义（7 值）
   输出 = { Domains[]（可多值）, Confidence, Reason }
   低置信(<0.4) / 空 ⇒ 保持 CD_UNKNOWN；来源标记 'semantic_llm'
   记录类特别口径：以「表头字段 + 抽样行 + 部门 + 文件名」为主证，⛔ 不用章号
  ↓
④ 落库：cert_enterprise_doc.DocProfileJson（ChapterDomains[] + ChapterDomainsSource）
```
