# 15 · 章作用与召回路径模型

> 本文回答三件事：
> ① 国标"**章的作用**"如何变成可执行的取证规则；
> ② "**召回方式**"如何高度收敛成有限几种（不是每条款一个）；
> ③ 条款如何**自动**挂上召回路径（而不是人工逐条挂）。
>
> 一句话：**章作用（= `Role`）决定"找回什么体裁的文档"；证据族/证据形态决定"从哪个轴去召回"。两条轴一乘，路径自动成。**

---

## 零、五条结论

1. **"章作用"不需要新字段**。属性池里已有的 `Role`（r1–r7）与国标 4–10 章**一一对应**，`Role` 就是"章作用"。国标 0.3.2 已把第 4–10 章切进 PDCA，章号 = 阶段 = 作用，三者同源。

2. **缺的不是数据，是三张映射 + 一次接线**：
   - 映射①：章作用 → 文档类型过滤（找回什么体裁）；
   - 映射②：章作用 → 默认提取方式（怎么提取）；
   - 映射③：证据族/形态 → 召回轴（从哪条轴找）；
   - 接线：把上面三条组合成"条款级召回路径"，并在装配时真正执行。

3. **条款挂载是一条公式，不是 240 次人工**。`RecallPath(条款) = Family→轴 ∥ Form→补充轴 ∥ Role→文档类型过滤`，一条 SQL 可算完 240 条叶子条款。

4. **章只负责"文档类型过滤"，不负责"选轴"**。这是纠正 09/12 号的一个方向性含混：轴由证据族决定，体裁过滤由章作用决定，两者正交。换标准时只重写"章→体裁"这张 7 行表，召回代码与提示词都不动。

5. **证据精准的前置条件是"召回可记账"**。每条路径独立记账（命中/未命中/原因），否则"缺证据"永远是静默空白（09 号 §零的 7.1.5.1 反例）。

## 一、国标"章作用"拆解（依据 GB/T 19001 §0.3.2）

0.3.2 的原话："PDCA 循环能够应用于所有过程，图 2 表明了本标准第 4 章至第 10 章如何构成 PDCA 循环"。**每一章本质是一个固定类型的提问模板**——这才是"本章的作用"。

| 章 | `Role` | PDCA | 这一章在问什么 | 证据形态 | 默认提取方式 | 文档类型过滤（DocType） | 证据行必备要素 |
|:--:|:--:|:--:|---|---|:--:|---|---|
| 4 组织环境 | r1 | P | 你**识别**了什么 | 清单 | E1+E2 | manual / context_list | 清单名 + 编制/批准 + 日期 + 条目数 + 抽中项 |
| 5 领导作用 | r2 | P | 谁**承诺**、谁**负责** | 承诺+访谈 | E1+E4 | manual / policy / document_control | 方针 / 任命书 / 职责矩阵 + 编号 + 批准 |
| 6 策划 | r3 | P | 你**策划**了什么、怎么应对 | 策划输出 | E2 | context_list / record / policy | 风险机遇表 / 目标统计 / 变更记录 |
| 7 支持 | r4 | D | 资源**是否到位且受控** | 资源台账 | E2 | record / work_instruction / document_control | 设备 / 校准 / 培训 / 文件清单 + 编号 + 日期 |
| 8 运行 | r5 | D | 过程**是否按策划执行** | 执行记录 | E2+E3 | procedure / work_instruction / record | 程序/WI + 订单/采购/生产/检验/放行记录 |
| 9 绩效评价 | r6 | C | 你**怎么监视评价** | 评价结论 | E2 | record / audit_record | 内审 / 管评 / 满意度 / 合规性评价 + 结论值 |
| 10 改进 | r7 | A | 不合格**怎么处置、怎么改进** | 处置记录 | E2 | record / audit_record | NC / 纠正措施 / 改进记录 + 验证结论 |

> 该表**跨标准通用**：13485 / 24001 / 45001 / 42061 共用 Annex SL 的 4–10 章，章号与阶段一致，只有个别条款措辞变化。
> `Role` 已在 `cert_clause_attr` 中逐条款填好（实测 13485：r5 运行 30 条 / r4 支持 19 条 / …），**无需新增**。

## 二、抽象模型：三层

```
┌──────────────────────────────────────────────────────────────┐
│ L1 章作用层 ChapterRole（= Role r1–r7，来自国标 4–10 章）      │
│    产出：文档类型过滤 + 默认提取方式 + 证据行要素模板          │
├──────────────────────────────────────────────────────────────┤
│ L2 召回方式层 RecallMethod（6 种，有限、跨标准不变）            │
│    RM1 条款轴 / RM2 过程轴 / RM3 部门轴 / RM4 编号轴           │
│    RM5 现场 / RM6 访谈                                        │
├──────────────────────────────────────────────────────────────┤
│ L3 召回路径层 RecallPath（条款 → N 条路径）                    │
│    每条路径 = 轴(RM) × 键(K) × 文档类型过滤(章) × E × R句式    │
└──────────────────────────────────────────────────────────────┘
```

**L1 从哪来**：章号（条款号首位）→ `Role` → 第一节表。确定性推导，无歧义。
**L2 从哪来**：09 号 §3.5 的 5 条路线 + 访谈，收敛为 6 种方式。
**L3 从哪来**：公式自动生成（§四），落成 `cert_clause_attr` 的 `RecallRoutes` 属性（JSON）。

## 三、L2：召回方式注册表（只此 6 种）

| 方式 | 键 | 判据 | 适用体裁 | 现可用度 |
|:--:|:--:|---|---|---|
| **RM1 条款轴** | K1 条款号 | 文档 `PrimaryClauses[]` ∩ 检查项条款（含祖先/后代） | 手册 / 程序 / 指导书 | 45/99 |
| **RM2 过程轴** | K2 过程 | 条款 `Process[]` ∩ 文档 `ProcessArea`（归一后） | 记录 / 台账 / 报告 | 需 8 行映射 |
| **RM3 部门轴** | K3 部门 | 检查项 `DeptNames` ∩ 文档 `OwnerDept`（经部门映射） | 记录 | 需 14 行映射 |
| **RM4 编号轴** | K4 编号 | 记录编号前缀 → 程序 → 条款 | 记录 | 需抽 `DocNo` |
| **RM5 现场** | — | 必须现场看（标识 / 环境 / 设备状态） | 人工 | 不自动 |
| **RM6 访谈** | — | 承诺类条款（5.1 / 5.2.1） | 两段式 | 使用 E4 |

- **RM2/RM3 是"记录类"的主轴**，不是条款轴的兜底。这与现状相反（现状：条款轴优先、过程轴仅兜底），是本模型要翻转的一条。
- **RM4 只服务 7.5.x 文件控制类**（记录编号→程序→条款），不是通用轴。09 号称它"编号轴"，此处正名为**编号轴（DocNo）**，且**限定体裁为 record / document_control**。

## 四、L3：条款 → 召回路径，自动挂载公式

### 4.1 公式

```
RecallPath(条款) =
  ┌ 轴选择（由证据族 EvidenceFamily 决定）
  │   f1    ⇒ [RM1 条款轴]                         // 制度族：按条款号找制度
  │   f2    ⇒ [RM2 过程轴, RM3 部门轴]              // 执行族：按过程+部门找记录
  │   f1f2  ⇒ [RM1 条款轴, RM2 过程轴]             // 混合族：制度 + 执行
  ├ 补充轴（由证据形态 EvidenceForm 决定）
  │   site      ⇒ 追加 [RM5 现场]
  │   interview ⇒ 追加 [RM6 访谈]
  ├ 体裁过滤（由章作用 Role 决定）—— 给每条轴追加 DocType 白名单
  │   r1⇒manual,context_list  r2⇒manual,policy  r3⇒context_list,record
  │   r4⇒record,work_instruction  r5⇒procedure,work_instruction,record
  │   r6⇒record,audit_record  r7⇒record,audit_record
  └ 提取方式 E 与句式角色 R（由 Family × Form × 章 决定，见 §五）
```

**关键：章只加"体裁白名单"这一层过滤，不改轴。** 换标准只重写 §一末列。

### 4.2 展开示例（用真实条款属性）

| 条款 | Family | Form | Role | 生成路径 |
|:--:|:--:|:--:|:--:|---|
| 4.4 | f1f2 | cite | r1 | 〔RM1 条款轴 · 体裁=manual〕∥〔RM2 过程轴 · 体裁=procedure,work_instruction〕 |
| 4.2 | f1 | cite | r1 | 〔RM1 条款轴 · 体裁=manual〕+〔RM2 过程轴 · 体裁=context_list〕（相关方清单） |
| 5.1 | f1 | interview | r2 | 〔RM1 条款轴 · 体裁=manual〕+〔RM6 访谈〕 |
| 7.1.5.1 | f2 | sample | r4 | 〔RM2 过程轴 metrology · 体裁=record〕+〔RM3 部门轴 · 品质部〕+〔RM4 编号轴〕 |
| 8.5.1 | f1f2 | sample | r5 | 〔RM1 条款轴 · 体裁=procedure〕+〔RM2 过程轴 production · 体裁=record〕 |
| 9.2 | f2 | sample | r6 | 〔RM2 过程轴 management · 体裁=record,audit_record〕（内审报告） |

> 以 7.1.5.1 为例对照 09 号反例：当年"校准证书 19 行在库却报未采集"，正是因为它只走了 RM1 条款轴（记录类 `PrimaryClauses=[]` 必空）。本公式对 f2+sample+r4 会直接生成 RM2(metrology)+RM3(品质部)，**正好命中那份台账**。

### 4.3 落库

`RecallRoutes` 作为 `cert_clause_attr` 新增属性（JSON 数组），一条 SQL 从现有 `EvidenceFamily / EvidenceForm / Role` 推导：

```sql
-- 伪 SQL：按三属性拼 RecallRoutes，0 次模型调用
INSERT INTO cert_clause_attr (StandardCode, ClauseNumber, AttrCode, AttrValue)
SELECT StandardCode, ClauseNumber, 'RecallRoutes',
       JSON_ARRAYAGG(JSON_OBJECT('axis','RMx','docType','...','extract','Ex','role','Ry'))
FROM cert_clause_attr
WHERE AttrCode IN ('EvidenceFamily','EvidenceForm','Role')
GROUP BY StandardCode, ClauseNumber;
```

覆盖 240/240（145 f1 + 29 f2 + 66 f1f2 = 240），与叶子条款数一致。

## 五、L1 × L2 → 提取方式 E × 句式角色 R（接 12 号规则表）

12 号定义"规则 = E（提取方式，5 选 1）× R（句式角色，4 选 1）"。本章把**章作用**接进去，形成完整映射：

| 章 | 默认 E | 默认句式角色 R | 句式骨架 | 真实例（acm 基线） |
|:--:|:--:|---|---|---|
| 4 r1 | E1+E2 | 覆盖声明 | 识别了 N 项…保留有《清单》（编制/批准/日期）…如… | "公司识别了相关方…保留有《相关方的需求和期望清单》，编制：张丹，批准：潘明海，日期：2026-06-10…" |
| 5 r2 | E1+E4 | 制度依据 | 查见《方针/任命》，规定了… | "查见《管理手册》，明确了方针与职责…批准：潘明海" |
| 6 r3 | E2 | 覆盖声明/执行证据 | 查见《风险/目标表》，共 N 项… | "识别出风险…形成《风险与机遇评估分析表》" |
| 7 r4 | E2 | 执行证据 | 查见《台账》，共 N 条，…齐全 | "查见《设备校准状态跟踪表》19 台，证书编号、校准日期、有效期齐全" |
| 8 r5 | E2+E3 | 执行证据 | 抽查 N 份《记录》，其中… | "见《文件化信息控制程序》KSY-QMS-P-11…采用过程方法对…过程进行控制" |
| 9 r6 | E2 | 结论证据 | 查见《评价/统计》，结论为… | "查见《目标统计表》，2025.9–2026.6 考核均达标" |
| 10 r7 | E2 | 执行证据+结论证据 | 针对…已制定《纠正措施》并验证 | "针对…已制定纠正措施并验证有效" |

> 与 09 号 §5.3 的 (PDCA × 角色) 矩阵一致；本表把它与 `Role`/章号、`E`、`R` 三者对齐。
> **实际用到约 8 格模板**，即 L4 的全部资产，不是"让模型自由写"。

## 六、证据生成模型（语义讨论作为规则的一部分）

"找到证据后如何生成证据信息"由**证据族 × 章作用**决定，固化成 3 个模板族：

| 族 | 触发 | 生成模板 | 要素要求 |
|---|---|---|---|
| 制度族 | f1 / f1f2 的 cite 分支 | `公司依据《X》(编号, 版次, 编制/审核/批准, 发布日期) 规定了…；见《Y》(编号)` | 编号 + 版次 + 三签 + 发布日期 + 条款/章节 |
| 记录族 | f2 / f1f2 的 sample 分支 | `查见《Z》，共 N 条，其中抽 1 项（编号…日期…对象…签字…结论…），…齐全` | 记录编号 + 日期 + 期间 + 批次/对象 + 签字 + 结论 |
| 清单族 | 章 4/6 的 E2 | `识别了 N 类…保留有《清单》(编制/批准/日期)，如…` | 清单名 + 编制/批准 + 日期 + 条目数 + 抽中项 |

- 科斯亚 97 份提取产物 `Metadata` 已含 `DocCode / IssuedBy / ApprovedBy / DocVersion / EffectiveDate`（80/97 有），**要素数据在库**，缺的只是按族接进模板。
- 模板**不判断符合性**（结论由代码算，默认符合）；模板只负责把 2–3 个事实连成一句可核对的话。

## 十、为什么这样就"无遗漏 / 无虚增"

- **无遗漏**：每条路径显式挂在条款上；每条路径独立记账；未命中时界面回显"未采集（附原因）"，而非静默空白。
- **无虚增**：路径自带**体裁过滤**。记录类不再被条款轴误判为"空"，也不会被"兜底过程轴"跨体裁误召回——过程轴是记录类的**首选**而且被章钉死为 `record`。
- **可解释**：任一条证据都能回答"它为什么被找来"（走了哪条 RM、命中哪个键、属于哪章体裁）。

## 十一、三个确认点的裁定（2026-11-24 用户裁决）

1. **§一 的"章→体裁/提取方式"表** → **认可**。体裁口径按 **§4.1 统一白名单**（一条条款的全部轴共用同一份 `DocType` 白名单，不按 §4.2 逐轴拆不同体裁）。※ §4.2 示例中"同条款两轴不同体裁"的写法**作废**，仅作示意，不实现。
2. **§九 的命名修订** → **采纳**。规则编号改 `RL1–RL5`（避与路线 `RM1–RM6` 撞号）；条款侧字段名统一为 `RecallRoutes`。
3. **§八 的分期顺序** → 从第 4/5 章起，**认可**。
