# 23 · 指纹特征匹配 · 章节枚举 · 条款释义 · 文档画像 — 两轮召回与条款合并设计（V1）

> **本文定位**：把「条款只按**大章节**归类、文档只按**大章节 + 部门**归类；两轮 LLM（先筛文档、后精炼发现）；最后做条款合并」这条主线，落成可执行的详细设计。
>
> **一句话结论**：**条款与文档不再靠条款号对接，而靠「大章节枚举」这一共同维度对齐**；条款号只在同章节内部作精确定位的兜底，不再作为召回主轴。召回 = **确定性过滤（章节 ∩ 部门）→ 条款释义语义筛选 → 证据组合成发现 → 条款释义精炼成最终证据**。

---

## 零·〇 ★ V4 最大的改变：**不再围绕条款设计，全部是「指纹 + 特征」匹配**

> 这是 V4 相对 V3 的**根本转向**，也是本文所有设计的出发点。（用户 2026-11-26 原话：「这是我 v4 最大的改变，不再围绕条款设计，全部都是指纹和特征匹配」）

| 维度 | V3（旧） | **V4（本设计）** |
|---|---|---|
| **设计中心** | **条款（条款号）** | **指纹与特征** |
| **出发点** | 每条检查项都去"对条款号" | 每个实体先提一组**特征**，靠**特征匹配** |
| **文档提取** | 逐条款对号 ⇒ **3 体系每份跑 3 遍** | 只提**文档自身特征**（标准无关）⇒ **跑 1 遍，多标准复用** |
| **匹配依据** | 条款号相等 / 祖先 / 后代 | **大章节 + 部门 + 语义特征**（⛔ 不用条款号） |
| **失败模式** | 文档不全 / 无条款号 ⇒ 整类漏召回 | 特征在库即可匹配，与"文档是否成套"无关 |

**"特征（Feature）" 的统一定义**：无论**条款**还是**文档**，都先被抽象成一组**可核验的特征**；匹配 = **特征匹配**。

| 实体 | 特征构成 |
|---|---|
| **条款特征** | 大章节（`CH_*`）· 范围/部门 · 释义语义（`Purpose`）· 证据形态（族/形态） |
| **文档特征** | 分类**指纹**（手册/过程/作业指导/记录）· 大章节归属 · 部门归属 · 精简抽象（`Abstract`）· 结构指纹 |

⇒ **条款号从"设计中心"降为"同一标准内部的可选业务键"**（仅供人工定位与合并，**不参与匹配**）。

## 零、三句话总纲（先看这个）

1. **横向对齐维度 = 大章节枚举（标准无关）**。所有 GB/T 体系国标都按 **环境 / 领导 / 决策 / 支持 / 实施 / 评估 / 改进** 七大类编写；条款归一大类，文档也归一大类，**两者在这 7 个枚举值上直接对齐**，⛔ 不用条款号。
2. **条款方**：每个**叶子条款**（最后一层，如 `4.1.1`；不再细分）记录一份**释义** = 作用（详细）+ 如何找证据链 + 找到后如何检查 + 范围（针对哪些部门/环境）。
3. **文档方**：每份文档提炼一份**画像** = 分类（手册/过程/作业指导/记录）+ 归属大章节 + 归属部门（1..N）+ 精简抽象作用；不同分类提取方式不同（手册按章节原文 / 过程·作业指导按引用 / 记录抽查成条）。

## 一、总览：四层 + 两条数据轴

```
┌───────────────────────────────────────────────────────────────────┐
│ L0 标准层   国标（iso9001 / 14001 / 45001 …）                       │
│             ① 每个条款 → 归一大章节枚举（环境…改进）                 │
│             ② 叶子条款 → 一份释义（作用/找证据/检查/范围）          │
├───────────────────────────────────────────────────────────────────┤
│ L1 条款轴   条款 = {条款号(业务键), 标准, 大章节, 释义}              │
│                                     └─ 跨标准同号可合并（§七）      │
├───────────────────────────────────────────────────────────────────┤
│ L2 文档轴   文档 = {分类, 大章节, 部门[], 精简抽象作用, 提取产物}    │
│             提取产物按分类不同：手册=章节原文 / 过程=引用 / 记录=条目 │
├───────────────────────────────────────────────────────────────────┤
│ L3 召回层   两轮：确定性过滤（章节∩部门）→ 条款语义筛选             │
│             产出「发现」→ 条款释义精炼「发现」→ 最终「证据」        │
└───────────────────────────────────────────────────────────────────┘
        L1 与 L2 的**唯一公共键 = 大章节枚举**（+ 部门作为第二过滤维）
```

**两条轴的连接点只有一个：大章节枚举。** 条款号是"标准内部"的坐标，跨标准不可复用；大章节枚举是"所有 GB/T 通用"的坐标，**是唯一可跨标准、跨文档分类对齐的维度**。

## 二、章节枚举（标准无关的七大类）

### 2.1 枚举定义

| 枚举码 | 中文名 | 用户口径 | Annex SL 章 | 现有的 `Role` | PDCA 位 | 这一章在问什么 |
|:--:|---|---|:--:|:--:|:--:|---|
| `CH_ENV` | 环境 | 环境 | 4 | r1 | P | 你**识别**了什么（内外部环境/相关方/体系范围） |
| `CH_LEAD` | 领导 | 领导 | 5 | r2 | P | 谁**承诺**、谁**负责**（方针/职责/协商） |
| `CH_PLAN` | 决策 | 决策（策划） | 6 | r3 | P | 你**策划**了什么、怎么应对（风险机遇/目标/变更） |
| `CH_SUPP` | 支持 | 支持 | 7 | r4 | D | 资源**是否到位且受控**（人/设施/知识/文件） |
| `CH_OPER` | 实施 | 实施（运行） | 8 | r5 | D | 过程**是否按策划执行** |
| `CH_EVAL` | 评估 | 评估（绩效评价） | 9 | r6 | C | 你**怎么监视评价**（监测/内审/管评/合规） |
| `CH_IMPR` | 改进 | 改进 | 10 | r7 | A | 不合格**怎么处置、怎么改进** |

### 2.2 铁律：不"由章号推枚举"，而是**直接读属性池**

> **⚠️ 实测反例（15 号已记）**：`iso13485` 的章号 ≠ 大章节（实测 `4.1.1→r4`、`4.1.2→r3`，与 Annex SL 不同源）。
>
> ⇒ `CH_*` **必须**由条款属性池的 `Role`（r1–r7）映射得到，**⛔ 绝不 `substring(条款号,1,1)` 推**。

- **映射（1:1，确定）**：`r1→CH_ENV`、`r2→CH_LEAD`、`r3→CH_PLAN`、`r4→CH_SUPP`、`r5→CH_OPER`、`r6→CH_EVAL`、`r7→CH_IMPR`。
- **换标准只改这张 7 行表**（+ 逐条款 `Role` 的填充），召回层与提示词都不动。
- `Role` 已在 `cert_clause_attr` 中逐条款填好（15 号实测：13485 运行 30 条 / 支持 19 条 …），**无需新增属性**，只需在代码里加一层 `Role→CH_*` 派生。

### 2.3 与 16 号 `ClauseCategory` 的关系

16 号曾把 6 类 `ClauseCategory`（框架/承诺/策划/支持/运行/改进）由 `Role` 派生。本文**回归用户口径的 7 大类**：

- 16 号把「4 章」拆成「框架(4.4) / 策划(4.1–4.3)」、把「9+10 章」并成「改进」——这是为"要不要 RM7 `ClauseCategory`"服务的，**粒度更粗**。
- 本设计**不与它冲突**：`CH_*` 是**召回对齐维度**（7 类）；16 号的 `ClauseCategory` 若仍需要，可保留为「是否追加 RM7 语义轴」的**派生开关**（`CH_ENV/CH_LEAD` 不追加，其余追加）。**两者职责不同，可并存**。

## 三、条款结构与释义

### 3.1 条款结构：`4` / `4.1` / `4.1.1`，以"最后一层"为释义载体

- 结构最多三层（实测国标不会再细分）。
- **释义只记在"叶子条款"上**（最深层的、不再有子号的那一层）。
- 非叶子条款（如 `4`、`4.1`）**不单独写释义**，由子条款释义归并（§七·2）。
- "叶子"的判定：该标准下**是否存在以它为前缀的下一层号**；无下一层 ⇒ 叶子。

| 情形 | 处理 |
|---|---|
| `4` 有 `4.1` | `4` 非叶子，不写释义 |
| `4.1.1` 无 `4.1.1.x` | `4.1.1` 叶子，写释义 |
| 某标准只有 `4.1`（无 `4.1.x`），且无 `4.1.1` | `4.1` 即叶子，写释义 |

### 3.2 释义四段（用户口径）

释义 = 一个 JSON，含 4 段；**目的**是"让 LLM 完全理解这条到底在干什么"：

| 段 | 字段 | 含义 | 写法要求 |
|:--:|---|---|---|
| ① | `Purpose` **作用** | 这条涵盖什么、需要什么、达到什么目的 | **非常详细**（多句，可含 a/b/c 各分项的解释）；是 LLM 判"文档是否对得上"的主语料 |
| ② | `EvidenceChain` **如何找证据链** | 从哪类文档/哪个过程/哪个部门去找 | 与文档画像的**分类 + 部门**对齐（如"找程序文件 + 该过程记录 + 对应部门台账"） |
| ③ | `CheckPoints` **找到的证据如何检查** | 拿到候选证据后，核验什么 | 核验清单（如"证书是否有编号、是否在有效期、机构是否有资质"） |
| ④ | `Scope` **范围** | 这条针对哪些"环境"（部门）检查 | 部门名列表 / 部门类别（与 `cert_enterprise_dept` 对齐） |

> **①是核心**：它是两轮 LLM 里的**查询语料**（第二轮筛文档、第四轮精炼发现都用它）。
> **④是关键**：它是**第一轮确定性过滤的第二维**（§六·2）。
> **②③** 与 15 号的 `RecallRoutes`（RM 轴）**同源互补**：`RecallRoutes` 是"轴级计划"（机器执行），`EvidenceChain` 是"自然语言找法"（LLM 读）；`CheckPoints` 是**新增的检查段**（15/16 都未单列，此前只隐含在"证据生成模板"里）。

### 3.3 释义的落库

**复用 `cert_clause_attr`**（属性池，键 = `StandardCode + ClauseNumber + AttrCode`），**不新建表**：

| AttrCode | 值 | 来源 |
|---|---|---|
| `ClauseText` | JSON `{Title,Body,Items,Notes}`（条款原文） | `cert_iso_clause.Description`（16 号已设计） |
| `ClauseGloss` **（新增）** | JSON `{Purpose, EvidenceChain, CheckPoints, Scope}` | **LLM 生成一次**（输入 = ClauseText + 标准上下文），落库后**冻结** |
| `Role` | `r1`–`r7`（已有） | 现有属性 |
| `EvidenceFamily` / `EvidenceForm` | （已有） | 现有属性 |
| `RecallRoutes` | JSON（15 号已设计） | 由 Role/Family/Form 推导 |

> `ClauseGloss.Purpose` 与 `ClauseText` **分工**：`ClauseText` = 原文（BM25 语料）；`ClauseGloss.Purpose` = 详解释义（LLM 筛选用）。两者都留，不同用途。

## 四、文档画像（分类 · 大章节 · 部门 · 精简抽象）

### 4.1 文档分类与提取特点（用户口径）

| 分类（`DocClass`） | 对应 17 号 `DocType` | 提取特点（用户原话落地） | 提取产物形态 |
|---|---|---|---|
| **质量手册** | `manual` | **基本按章节原文提取** | 逐章节：标题 + **原文锚段**（`CharStart/CharEnd`）+ 摘要 |
| **过程**（程序文件） | `procedure` | **主要是引用**（引用别的文件/程序号/记录编号） | 逐段：目的/范围/职责/工作程序/相关记录/**引用清单** |
| **作业指导** | `work_instruction` | **主要引用 + 步骤/参数** | 步骤 + 参数 + 判定标准 + **引用的上层文件** |
| **记录** | `record` | **抽查，将表格改造成一条一条的记录** | 表格 → **一条条结构化记录**（字段 + 实例值） |
| （管理制度/规范） | `policy` | 条款式规定 | 第X条 列表 |
| （文件索引/清单） | `index` | 条目列表 | 条目（编号+名称） |
| （组织环境/相关方） | `context_list` | 清单 | 条目清单 |

> **分类判据 = 17 号的"结构指纹"**（颁布令/六段式/条款对照表/表格密度/实例数据…），**零 LLM、零文件名猜测**；判不出 = `unclassified` 待人工确认，⛔ 不猜、不兜底。
> **"每个文档有个精简抽象的作用"** = 下文 §4.3 的 `Abstract`。

### 4.2 文档归「大章节」+「部门」

| 维度 | 字段 | 来源 | 说明 |
|---|---|---|---|
| **归属大章节** | `Chapter`（`CH_*`） | 文档自身的**章节结构** | 不是条款号！由文档内章节标题/内容**语义判定归属哪一类**（手册多章则多值，如 `{CH_ENV, CH_SUPP, CH_OPER}`） |
| **归属部门** | `Depts[]` | 文档 Owner/编制部门/正文出现的部门 | 1..N 个；与 `cert_enterprise_dept` 对齐 |

> **与 17 号的衔接**：17 号 §六 已要求 `ModeOutput` 加 `Sections[]`（`Label/Summary/CharStart/CharEnd`）。**本设计在 `Sections[]` 上再加两个标签**：`Chapter`（该节归属哪一大类）和 `Depts[]`（该节相关部门）——这样**过滤粒度可以从"文档"细化到"节"**。
> **多标准无关**：`Chapter`/`Depts` **与标准无关**，一份文档只判一次，**3 体系复用同一份画像**（§九 的成本根治点）。

### 4.3 精简抽象作用（`Abstract`）

- **定义**：一段**短文本**（< 150 字），概括"这份文档是什么、管什么、归哪类、目的是什么"。
- **来源**：由 `DocProfileJson` 的确定性字段（分类 + 章节 + 部门 + 指纹）**拼装**（零 LLM）或一次 LLM（若需更自然）。
- **用途**：**第二轮 LLM 筛选的"文档侧语料"**（与条款 `Purpose` 对撞）。
- **与 14 号"章节精简"的关系**：14 号的章节 `Summary`（章节级） 细分于 `Abstract`（文档级）；`Abstract` 是文档级、"一句定调"，`Summary` 是章节级、"按节说明"。**两者都留**：先用 `Abstract` 粗筛文档，再用命中章节的 `Summary` 做证据。

### 4.4 文档画像落点（扩 `DocProfileJson`）

```jsonc
// cert_enterprise_doc.DocProfileJson（现有字段基础上扩）
{
  "DocType": "manual",                 // 现有：17 号分类
  "ExtractionMode": "clause_full",     // 现有：路由
  "Fingerprints": [ … ],               // 现有：结构指纹
  "Toc": [ { "Label": "4 组织环境", "CharStart": 100, "CharEnd": 900, "HasContent": true } ], // 现有
  // ↓ 本设计新增
  "Chapter": ["CH_ENV", "CH_SUPP"],    // 文档归属大章节（多值）
  "Depts":   ["品质部", "综合部"],      // 文档归属部门（多值）
  "Abstract": "本文为质量手册，规定了公司质量管理体系的范围、方针、组织职责与过程接口…", // 精简抽象作用
  "Sections": [                        // 17 号 §六 已规划，此处补 Chapter/Depts
    { "Label": "4 组织环境", "Summary": "…", "CharStart": 100, "CharEnd": 900,
      "Chapter": "CH_ENV", "Depts": ["综合部"] }
  ]
}
```

## 五、条款特征 × 文档特征 的匹配（硬特征 → 软特征）

**匹配 = 两组特征做匹配**，⛔ 全程不出现条款号。特征分两层：

| 层 | 特征 | 侧 | 匹配方式 | 轮次 |
|:--:|---|---|---|---|
| **硬特征** | 大章节（`CH_*`） | 条款 · 文档 | 集合相交（确定性、零 LLM） | 第一轮 |
| **硬特征** | 部门（`Dept` / `Scope`） | 条款 · 文档 | 集合相交（确定性、零 LLM） | 第一轮 |
| **软特征** | 释义语义（`Purpose`） | 条款 | BM25 / 语义相似（LLM 或 `ClauseTextMatcher`） | 第二轮 |
| **软特征** | 精简抽象（`Abstract`） | 文档 | 同上 | 第二轮 |

```
条款侧（特征袋）                     文档侧（特征袋）
┌──────────────────────┐           ┌──────────────────────────┐
│ 条款 8.5.1（叶子）    │           │ 《工序流转卡》            │
│ 硬特征：              │           │ 硬特征：                  │
│   大章节 = CH_OPER    ├─ 相交 ───►│   大章节 = CH_OPER        │
│   范围   = 生产部     │           │   部门   = 生产部         │
│ 软特征：              │           │ 软特征：                  │
│   释义 = "过程按策划  ├─ 语义 ───►│   分类指纹 = 记录         │
│          执行…"       │   匹配     │   抽象 = "工序流转卡，…"  │
└──────────────────────┘           └──────────────────────────┘
        （条款号只作业务键，⛔ 不参与上面任何一个匹配）
```

- **硬特征匹配 = 第一轮粗筛**（大章节 ∩ 部门）→ 把全库降到约 10 份。
- **软特征匹配 = 第二轮精选**（释义语义 × 抽象语义）→ 精选到约 6 份。
- 这就是用户说的「**大的章节（不是条款号）就能对起来**」——**大章节也是"特征"之一**。
- **可扩展**：新增一类特征（如"过程域 `ProcessArea`"）只需在对应侧加一个特征字段 + 一条匹配规则，**匹配代码骨架不动**。

## 六、两轮召回 → 发现 → 精炼（核心流程）

### 6.1 流程总图

```
① 定条款：取待检查条款（叶子）
      │  读：Chapter、Scope(部门)、ClauseGloss.Purpose
      ▼
② 第一轮 · 硬特征匹配（大章节 ∩ 部门，零 LLM）
      过滤条件 = 文档.Chapter ∩ 条款.Chapter  ∥  文档.Depts ∩ 条款.Scope
      结果 ≈ 10 份「可能符合的文档」
      ▼
③ 第二轮 · 软特征匹配（条款释义 `Purpose` × 文档抽象 `Abstract`，LLM 轻量）
      输入 = 条款释义(Purpose) × 10 份文档的精简抽象(Abstract)
      输出 ≈ 6 份「确实符合」的文档（其余剔除并记账）
      ▼
④ 取证据 + 直接组合
      对 6 份文档 → 按分类取证据（手册取章节原文/记录取条目/过程取引用）
      → 直接组合 = 一条「发现」(Finding)
      ▼
⑤ 第三轮 · 条款释义精炼（LLM · 收口）
      输入 = 条款释义(Purpose + CheckPoints) × 本条所有「发现」
      输出 = 「最终证据」（审核员可直接用的结论，200–500 字/条）
```

### 6.2 第一轮 · 硬特征匹配（章节 ∩ 部门，零 LLM）— 从"全库"降到"约 10 份"

- **输入**：条款 `Chapter` + `Scope`(部门列表)。
- **规则**：
  - `文档.Chapter ∩ 条款.Chapter ≠ ∅` **或** `文档.Depts ∩ 条款.Scope ≠ ∅`；
  - 二者是**并集**（任命中即入候选），保证"手册类（无部门）"与"记录类（无明确章节）"都能进。
- **产物**：候选文档集 + **每份的命中原因**（命中哪个章节 / 哪个部门），可审计。
- **与 15/16 号的关系**：这一轮 = 15 号的 **RM1–RM6 确定性轴的统一入口**的"最外层"。15 号的轴是"用哪把钥匙开"，本轮的 `Chapter/Dept` 是"先划定钥匙的搜索范围"。**RM 轴在候选集内继续用**（如记录类在候选内按 `ProcessArea` 命具体记录）。
- **降规模效果（用户口径）**：全库近百份 → 约 10 份。

### 6.3 第二轮 · 软特征匹配（释义 × 抽象，LLM 筛选）

- **为什么需要**：第一轮是**粗筛**（章节/部门是"可能相关"），会带进同名不同实的文档（如"环境"既是 4 章组织环境、又是环保运行）。
- **输入**（一次 LLM 调用）：
  - 条款侧：`ClauseGloss.Purpose` + `EvidenceChain`（这条要什么、从哪找）；
  - 文档侧：每份候选的 `Abstract` + `DocType` + `Chapter`（**只用抽象，不喂正文**）。
- **输出**：保留的文档清单（≈ 6）+ 逐份的**保留/剔除理由**（记账）。
- **产物落点**：`SelectStatus ∈ {kept, dropped}` + `Reason`，供审计与调试（沿用 20 号"可解释"口径）。
- **成本**：输入是"条款释义 + 10 段 ≤150 字摘要"，**不喂正文**，单次轻量。

### 6.4 取证据 + 直接组合 → 「发现」（Finding）

- 对第二轮保留的每份文档，**按分类取证据**（零额外 LLM，用已有提取产物）：

| 文档分类 | 取什么 | 取法 |
|---|---|---|
| 质量手册 | 命中章节的**原文锚段** | 按 `Sections[].CharStart/CharEnd` 切片（0 模型） |
| 过程/作业指导 | 命中的**引用条目**（引用的程序号/记录编号）+ 相关段落 | 读提取产物的引用清单 |
| 记录 | 命中的**结构化条目**（表格行） | 读 `record_profile` 的条目列表 |
| 清单类 | 命中的**条目** | 读 `context_list`/`index` 条目 |

- **"直接组合"** = 把上述命中的证据片段**拼成一条「发现」**（结构：`{条款号, 涉及文档[], 证据片段[], 命中原因}`），**不加判断**（判断留到第四轮）。
- **产物落点**：`clause_evidence_findings`（现有表）的"发现"语义——本设计的"发现"即此表的行。

### 6.5 第三轮 · 条款释义精炼所有发现 → 最终证据

- **输入**（一次 LLM）：条款 `ClauseGloss.Purpose + CheckPoints`（这条到底要看什么、怎么核）+ 本条**所有「发现」**。
- **任务**：把散落在多份文档里的证据片段，**按条款口径收口成 1 条最终证据**：
  - 去掉与条款无关的片段；
  - 补齐条款要求的核查点（`CheckPoints`：如"证书是否在有效期"——若发现里没有该信息，转入**疑点 `Doubts`**，⛔ 不写进结论正文）；
  - 按 20 号规则：**正文 200–500 字、无系统痕迹、无否定表述、全中文**。
- **产物落点**：`audit_check_evidence`（两段式第二段）+ 最终写 `cert_check_result.Reason`。
- **与 20 号的关系**：20 号的 `SanitizeEvidence` / `RemoveAbsenceSentences` / `ResolveEvidenceForClause` **正好是本轮的后置清洗**，**直接复用**。

### 6.6 三轮的分工与"为什么是两轮 LLM"

| 轮次 | LLM | 目的 | 输入规模 | 降规模 |
|:--:|:--:|---|---|---|
| ① 确定性过滤 | 无 | 章节/部门粗筛 | 全库 | 全库 → ~10 |
| ② 条款语义筛选 | **有** | 剔同名不同实 | 条款释义 + 10 摘要 | ~10 → ~6 |
| ③ 释义精炼 | **有** | 组合收口成结论 | 条款释义 + 全部发现 | 发现 → 1 条证据 |

> 用户口径是"两轮 LLM"（②筛选 + ④/⑤精炼），本文与之完全一致；①③（确定性过滤、取证据组合）零 LLM。

## 七、条款合并

### 7.1 跨标准同条款合并（同号不同标准）

**场景**：3 体系下同一条款号（如 `4.1`）在 iso9001 / 14001 / 45001 各有一份释义与证据。

**做法**：
1. **先过滤**：判定这几个同号条款是否"实质同一"（同大类 `CH_*` 即视为可合并；如 `4.1` 在三标准都属 `CH_ENV`）。
2. **合并释义**：把 N 份 `ClauseGloss` 的 `Purpose/EvidenceChain/CheckPoints/Scope` **合成一份合并释义**（求并集 + 去重）。
3. **一并语义分析**：用合并释义对三标准的证据做**一次** LLM 精炼（而非三次），得到**一份"同条款跨标准"的合并解释**。
4. **产物**：`clause_number = "4.1"`（纯号），`standards = [iso9001, iso14001, iso45001]`，`audit_evidence` = 合并结论。

> **"得到 3 个同一条款的合并解释"** = 该条款号在 3 个标准下的三段释义被合并分析后，产出一段统一解释。**由此 3 体系不再各跑一遍**。

### 7.2 同标准多条款合并（父子归并）

**场景**：同标准内 `4`（父）与 `4.1`/`4.1.1`（子）都待检查。

**做法**：
- **归并到最细号**：`4` 的检查归到 `4.1.1`；父条款**不单独产出证据**。
- **一段文字**：每个叶子条款产出**一段**证据（不是多段）。
- 这正是 20 号已实现的"父子条款归并到最细号"。

### 7.3 合并的触发与落点

| 合并类型 | 触发 | 判据 | 落点 |
|---|---|---|---|
| 跨标准同号 | 同一 `ClauseNumber` 出现在 ≥2 标准 | 同 `CH_*`（实质同一） | `audit_check_evidence` 的 `clause_number`（纯号）+ `standards[]` |
| 同标准父子 | 同标准内出现父子号 | 前缀关系 | 归并到最细号，父不产证据 |

> **顺序**：**先合并释义（条款侧）→ 再走 §六 三轮 → 最后合并证据（跨标准）**。即"合并"既是**入口**（释义合并后统一筛文档）也是**出口**（3 标准证据合并成一段）。

## 九、提取层去标准耦合（根治"3 体系 = 每份跑 3 遍"）

### 9.1 病灶

- 现状 `cert_document_extraction` 粒度 = **`FileCode + StandardCode`**（注释明载 2026-10-29 裁定）。
- ⇒ 一份《质量手册》对 iso9001 / 14001 / 45001 **各跑一次**提取 = **3 遍 LLM**。
- 根因：**条款号是标准相关的**，提取期若依赖条款号，就必须按标准各跑一遍。

### 9.2 解法：**提取产物标准无关化**（= 用户"彻底抛弃条款号"的落地）

- **提取产物只描述"文档自身结构"**，与标准无关：
  - 手册 → 章节原文锚段 + 摘要；
  - 过程/作业指导 → 引用清单 + 段落；
  - 记录 → 结构化条目。
- **`PrimaryClauses` / `Chapters` 由"必须"降为"有则记"**（17 号 §六 已规划，16 号 P3 已验证）。
- **标准相关的事，全部下沉到召回层**（§六：条款按 `Chapter` 对齐文档，**不再要求提取期对齐条款号**）。
- **效果**：一份文档**只提取一次**，3 标准复用 ⇒ **省 2/3 LLM**（16 号 P3 实测结论）。

### 9.3 过渡（V2 隔离铁律下的兼容）

- 短期**保留 `(FileCode, StandardCode)` 行**，但**类型化提取（手册/过程/记录）只跑一遍**，仅极少数"条款逐条全文"链路仍按标准。
- 中长期：产物粒度收敛为 `FileCode`，`StandardCode` 仅作"该文档支撑哪些标准"的**标签**（可多值），非提取粒度。

## 十三、为什么这样就"更准、更省、更可解释"

- **更准**：对齐用"大章节"（所有 GB/T 通用），**不再靠模型猜条款号**；释义 `Purpose` 详细到"让 LLM 理解这条干什么"，筛文档有据。
- **更省**：① 提取**一次跑、多标准复用**（省 2/3）；② 第二轮只喂"摘要+释义"（不喂正文）；③ 第一轮零 LLM 把规模从全库降到 ~10。
- **更可解释**：每一层都记账——第一轮记"命中哪个章节/部门"，第二轮记"保留/剔除理由"，第三轮记"取了哪几份文档的哪段"。
- **可扩展**：换标准只改 `Role→CH_*` 7 行表；新增文档分类只加一条指纹规则 + 一条"章节归属"映射，**召回代码不动**。
