# 文档提示词 / 条款提示词 / 认证提示词的职责边界

## 一、先纠正一句话

条款提示词不是“生成最终审核证据”，而是：

> **把企业文档里有什么、原文是什么、可能有什么疑点、应该从哪些文档组合成证据，讲清楚。**

最终审核证据在“体系审核 / 体系准备”里生成，由认证提示词完成。条款提示词只提供事实、原文和疑点，不替审核员下结论。

---

## 二、三层提示词各做什么

| 层 | 输入 | 输出 | 不做什么 |
|---|---|---|---|
| 文档提示词 | 单份企业文档 | `DocFact`：文档分类、核心作用、关键字段、填写状态、样例行、覆盖 | 不判条款符合性，不写审核结论 |
| 条款提示词 | 条款正文 + 章节画像 + 引用条款 + `DocFact` / 文档摘录 | `EvidenceContract`（期望证据） + `EvidenceFindings`（实际发现） + `Doubts`（疑点） + `EvidenceAssembly`（怎么组合成证据） | 不写“符合/不符合”，不写 NC，不生成最终检查项 |
| 认证提示词 | 检查项 + `EvidenceFindings` + `Doubts` + `EvidenceContract` | 最终审核证据 / 检查项 / 报告语言，默认符合，按发现补细节 | 不重新读原始文档，不编造未发现的事实 |

### 2.1 一个关键区分

- **条款提示词**：机构无关。换一家咨询公司、换一家企业，结论仍然成立，因为它只引用文档事实和条款要求。
- **认证提示词**：机构相关。不同机构的话术、默认符合口径、报告模板不同，所以最终审核证据放在这一层生成。

---

## 三、条款提示词的两种运行模式

同一份模板，两个模式，不新增第二份提示词。

| 模式 | 是否有文档 | 输出 |
|---|---|---|
| `contract` | 没有 `DocFact` | 只输出 `ClauseContext / ChapterContext / ReferencedAnalysis / EvidenceContract / ReportHint`；`EvidenceFindings / Doubts / EvidenceAssembly` 为空数组 |
| `findings` | 有 `DocFact` / 文档摘录 | 在契约基础上，输出 `EvidenceFindings / Doubts / EvidenceAssembly` |

这样：

- 条款属性生成阶段不需要企业文档，仍然可以跑；
- 企业文档入库后，同一份提示词进入 `findings` 模式，产出证据发现；
- 不需要为“有文档/没文档”维护两套提示词。

## 四、v5.2 新增的三个结构

### 4.1 `EvidenceFindings`

每条发现必须能回到原文。

| 字段 | 含义 |
|---|---|
| `FindingId` | F1/F2/... |
| `ClauseItemRef` | 对应 a/b/c 或条款要求 |
| `DocClass` | procedure / record / work_instruction / report / list / plan |
| `DocName` | 企业实际文档名，来自 `DocFact`，不许编 |
| `DocLocation` | 文件名 + sheet/行/字段 |
| `FindingType` | `document_exists / record_exists / field_present / field_missing / template_only / report_only / cross_doc_conflict / unreadable / absent` |
| `FillStatus` | 直接取 `DocFact.FillStatus`，不推断 |
| `OriginalQuote` | 原文片段，最多 200 字，必须逐字引用 |
| `WhatItProves` | 这条原文能证明什么，只写事实，不写结论 |
| `RiskLevel` | `high / medium / low` |

### 4.2 `Doubts`

疑点不是 NC，是“审核员应该去看一眼”的地方。

| 字段 | 含义 |
|---|---|
| `DoubtId` | D1/D2/... |
| `DoubtType` | `blank_template / missing_signature / missing_date / inconsistent_person / date_conflict / scope_mismatch / report_only / no_traceability / cross_doc_conflict` |
| `Description` | 疑点是什么，一句话 |
| `RelatedFindings` | 关联 F ID |
| `WhyItMatters` | 为什么值得看 |
| `SuggestedCheck` | 建议审核员查什么，不写“判不符合” |
| `Confidence` | `high / medium / low` |

### 4.3 `EvidenceAssembly`

一条条款的证据往往不是一份文档，而是多份文档组合。

| 字段 | 含义 |
|---|---|
| `AssemblyId` | A1/A2/... |
| `ClauseItemRef` | 对应条款要求 |
| `RequiredDocClasses` | 需要哪些文档类型 |
| `MinDocs` | 最少几份 |
| `CombineRule` | 怎么组合，例如“计划 + 签到 + 检查表 + 不合格报告 + 内审报告” |
| `CanFormEvidence` | `true / partial / false` |
| `Gap` | 缺什么，没有给空串 |

## 五、例子：8.3.2 交付前不合格

### 文档事实

- `QR-020` 不合格品通知及评审处置表：`template_only`
- `QR-021` 让步接收申请表：`template_only`
- `QR-022` 报废申请单：`template_only`
- 报告里有 2026-06-30 黑色车架 100 个、2 件不良、98 件入库

### 条款提示词应输出

- `EvidenceFindings`：
  - F1：`QR-020` 存在，表头字段齐全，`FillStatus=template_only`，原文引用表头字段；
  - F2：`QR-021` 存在，`template_only`；
  - F3：`QR-022` 存在，`template_only`；
  - F4：报告中的批次数据，`FindingType=report_only`，`OriginalQuote` 引用报告原文。
- `Doubts`：
  - D1：三张处置表单均为空白模板，无法证明本次不合格已按 a/b/c 处置；
  - D2：报告有具体批次处置结论，但文档侧无对应已填记录，属于 `report_only`；
  - D3：无返工/返修记录，a 路径无法闭环。
- `EvidenceAssembly`：
  - A1：处置程序 + 三张处置表单 + 返工/返修记录 + 检验记录；当前 `CanFormEvidence=partial`，`Gap=缺已填处置记录、返工/返修记录`。

### 认证提示词再生成最终检查项

默认符合口径可以写：

> 企业编制了《不合格品控制程序》，建立了《不合格品通知及评审处置表》《让步接收申请表》《报废申请单》，表单包含不合格描述、数量、处置方式、批准人员等字段。

但不能写：

> 本次不合格已按返工/返修完成处置。

因为条款提示词已经给出 D1/D2，认证提示词应把“表单已建立”和“本次未填”分开写。

## 六、条款提示词的核心要求

1. **原文优先**：重要字段、结论、日期、人员、批次，能引原文就引原文，不转述。
2. **位置可回查**：每条发现带文档名 + sheet/行/字段。
3. **不推断**：空白模板只写 `template_only`，不写“未执行”；报告数据只写 `report_only`，不回填文档事实。
4. **疑点独立**：疑点不是 NC，不写“违反 XX 条款”。
5. **组合显式**：多文档证据写 `EvidenceAssembly`，不把一份文档当整条证据。
6. **机构无关**：不写机构话术、不写报告模板、不写“建议开 NC”。

---

## 七、效率边界

| 项 | 要求 |
|---|---|
| 条款提示词体积 | 8–10KB，超过就拆到运行时规则 |
| 单次测试 | 2 条并行，通过再扩 5 条 |
| `contract` 模式 | 不读企业文档，只跑条款 |
| `findings` 模式 | 只读已提取的 `DocFact` / 摘录，不重新解析原始文件 |
| 疑点数量 | 每条条款 0–5 个，不为了凑数 |
| 发现数量 | 每条条款 3–12 条，按文档实际内容 |

不追求 100% 召回。结构 100%、原文不编造、疑点可回查、漏项进 `Gap`，就达到可用线。

## 八、和现有系统的关系

| 现有 | 调整 |
|---|---|
| `doc_extract_record_profile` | 保持轻模型，只出 `DocFact`，不加条款判断 |
| `clause_attr_gen` | 改为 v5.2 模板，支持 `contract / findings` 两模式 |
| `CertCheckContextBuilder.RenderDocHits()` | 从“原文摘录”改为“`DocFact` + 关键原文片段”，供 `findings` 模式 |
| `audit_check` | 消费 `EvidenceFindings / Doubts / EvidenceAssembly`，生成最终检查项 |
| `audit_prep` | 消费 `Doubts`，生成补充取证清单 |

## 八点五、v5.2 试跑结果

`8.3.2` 证据发现模式，单条试跑，`JSON_OK`。

- `EvidenceFindings` 4 条：`QR-020 / QR-021 / QR-022` 均为 `template_only`，报告数据为 `report_only`；原文引用可回查。
- `Doubts` 3 条：三张处置表单均为空白模板；报告批次处置未关联原始处置记录；返修未看到再检验衔接。
- `EvidenceAssembly` 2 条：`A1=partial`，只有模板、无实际填写；`A2=false`，让步/报废路径无交叉引用证据。

发现两个需要运行时校验的小问题：

1. `WhatItProves` 会写“字段设计覆盖 a/b/c”，这是轻度推断，认证层可用，但条款层最好只写“表单包含哪些字段”；
2. `Doubt` 会写“未见 QR-024/025”，实际表单存在但为 `template_only`，应写“表单存在、抽样为空”，不能写成“未见”。

这两条不靠加提示词解决，放在 `DoubtValidator` 里做词面校验：出现“未见/没有”时，必须同时检查 `DocFact.FillStatus`，存在即改为“已建立、抽样为空”。

## 九、结论

- 条款提示词：**证据发现层**，负责“文档里有什么、原文是什么、疑点在哪、怎么组合”。
- 认证提示词：**审核证据层**，负责“默认符合的检查项 + 按发现补细节”。
- 文档提示词：**事实层**，只出轻量 `DocFact`，不碰条款。

三层不混，提示词才能短，机构才能换，审核员才能用。
