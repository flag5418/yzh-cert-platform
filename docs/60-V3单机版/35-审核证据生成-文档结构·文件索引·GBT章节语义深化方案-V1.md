## 一、先定三源边界：GBT 是要求源，企业文档是事实源，审核报告只是语言源

这是本方案的第一原则。三源混用，是当前 4.1 写出“条款转述”的根因。

| 源 | 只用来回答 | 绝不用来回答 | 产物 |
|---|---|---|---|
| **GBT 标准** | 这一章要解决什么问题；条款要求什么；什么算证据；什么只是注 | 企业实际做了什么；报告该怎么措辞 | 章节画像、要求点、证据期望 |
| **企业文档** | 企业写了什么、规定什么、记录什么、引用了什么文件 | 标准要求是什么；审核结论是什么 | 章节树、事实单元、文件索引 |
| **真实审核报告** | 审核员怎么分段、怎么起句、用什么动词、结论句怎么写 | 这一条应该查什么；企业事实是什么 | 风格包（按章/按环节，不按条款） |

**一句话**：报告可以学“怎么说”，不能学“查什么”；“查什么”必须回到 GBT 章节结构。

## 二、企业文档结构：先解决“4.1 被拆成 4.1.1–4.1.5 后怎么找全”

### 2.1 问题本质

中国人写体系文件，不是“一条条款一段”，而是：

```
4.1 理解组织及其环境          ← 章标题
  4.1.1 ……                   ← 编号段落
  4.1.2 ……
  4.1.3 ……
  a）……                      ← 无编号分点
  b）……
  4.1.4 ……
  4.1.5 ……
    a ……
    b ……
```

标准条款只有 `4.1`，企业文档却把它拆成 `4.1.1–4.1.5 + a–d`。当前提取按“条款号命中”找行，只找到 4.1.1–4.1.3，后面的编号段落和分点被当成“别的内容”丢掉。

**这不是模型漏写，是文档结构没有先解析。**

### 2.2 四层文档模型

| 层 | 内容 | 谁生成 | 用途 |
|---|---|---|---|
| L0 原文 | MinIO 里的 `.doc/.docx/.pdf` → Markdown | 转换链 | 保真底稿 |
| L1 章节树 | 标题层级 + 字符范围（`SectionMapJson`） | `DocSectionIndex` | 定位“4.1 这一节从哪到哪” |
| L2 段落/编号节点 | `4.1.1`、`a）`、`（1）`、普通段落，按顺序挂到最近标题 | 新增 `SectionTreeBuilder` | 保证子条款和分点不丢 |
| L3 事实单元 | 文件规定/清单项/记录/职责/数值/引用 | 提取模型 + 规则校验 | 供审核证据组织 |

### 2.3 解析规则

1. **标题树**：沿用 `DocSectionIndex` 的 Markdown 标题解析和 `IsLikelyHeading` 过滤（正文误升标题不进目录，但正文仍留在父节范围内）。
2. **编号节点**：在标题范围内按行解析：
   - `4.1.1`、`4.1.2`… → `NumberedNode`，父节点 = 最近的 `4.1` 标题；
   - `a）`、`b）`、`（1）`、`1）` → `ListItemNode`，父节点 = 最近的编号节点或标题；
   - 普通段落 → `ParagraphNode`，继承当前父节点。
3. **章节范围**：`4.1` 的 `CharStart–CharEnd` 覆盖整个子树，不因出现 `4.1.2` 就截断；`4.2` 标题才收口。
4. **标准条款映射**：
   - 优先精确编号（`4.1` 标题存在）；
   - 其次父级折叠（`4.4.1` 没标题 → 归到 `4.4`）；
   - 再次标题语义（“理解组织及其环境”≈4.1）；
   - 最后文档画像（手册/程序/指导书 + 目的段/适用范围）。
5. **非编号文档**（程序文件、作业指导书、记录表单）：不强求条款号，改用 `DocProfile` 的 `DocType + Purpose + Scope + 文件名 + 引用关系` 映射到条款，标记 `mapped_semantic`，不标 `exact`。

### 2.4 建议的 `SectionTreeJson`

```json
{
  "ClauseNo": "4.1",
  "HeadingTitle": "4.1 理解组织及其环境",
  "CharStart": 12345,
  "CharEnd": 14567,
  "Nodes": [
    {"Id":"4.1.1","Type":"numbered","Number":"4.1.1","Text":"公司各级负责人应……"},
    {"Id":"4.1.2","Type":"numbered","Number":"4.1.2","Text":"外部的因素是……"},
    {"Id":"4.1.3","Type":"numbered","Number":"4.1.3","Text":"内部因素是……"},
    {"Id":"4.1.a","Type":"list","Number":"a","ParentId":"4.1","Text":"通过分析市场和行业……"},
    {"Id":"4.1.4","Type":"numbered","Number":"4.1.4","Text":"公司的管理者代表组织……"},
    {"Id":"4.1.5","Type":"numbered","Number":"4.1.5","Text":"确定这些相关因素时……"},
    {"Id":"4.1.5.a","Type":"list","Number":"a","ParentId":"4.1.5","Text":"理解国家在法规、政策……"}
  ]
}
```

### 2.5 提取时的硬动作

**不要再把整本文档切块喂给模型找条款。** 改为：

1. 取 `SectionMapJson` 中 `4.1` 的 `CharStart–CharEnd`；
2. 取该范围内完整小节文本（不是只取 `BodyHead` 300 字）；
3. 连同 `SectionTreeJson` 和标准要求点一起给模型；
4. 模型只做“从这一节里抽事实”，不做“从整本里找 4.1”。

现有代码已经具备 `EnterpriseDocService.ProbeSectionAsync` 的小节探针，但**主提取链 `ClauseExtractExecutor` 还没用**。这是最小、最快的修复点：把主链切到 `DocSectionIndex.ReadRange`，4.1 就能立刻看到 4.1.4/4.1.5。

### 2.6 完整性校验

提取后不能只看 `Confidence`，要做**声明覆盖检查**：

```
Expected = 源小节中识别到的 4.1.1–4.1.5 + a–d 标记
Covered  = SectionTree 中被事实单元引用的节点
Missing  = Expected - Covered
```

- `Missing=[]` 才能标 `complete`；
- 有缺失标 `partial`，并触发一次“补漏”重提；
- 补漏仍缺，写 `Coverage.Missing`，禁止静默 `done`。

## 三、文件索引：上传文件不是本地目录，必须有“文档身份 + 引用图谱”

### 3.1 问题本质

体系文件大量使用引用句：

- “见《质量运行策划控制程序》”
- “按 KSY-QMS-P-14 执行”
- “相关文件：……、……”
- “本手册 8.4 条规定……”
- “记录保存按《记录控制程序》”

但系统里的文件是 MinIO 对象，只有 `FileName` 和 `StoragePath`；没有“文件编号、版本、别名、被谁引用”的索引。模型即使读到引用名，也无法判断：

1. 这份被引用的文件是否已上传；
2. 对应哪个 `FileCode`；
3. 该引用是“要求看这份文件”，还是“只是提了一句”。

### 3.2 文档身份（DocIdentity）

每份上传文件建立：

| 字段 | 来源 | 说明 |
|---|---|---|
| `FileCode` | `cert_enterprise_doc.Code` | 对象存储主键 |
| `FileName` | 上传名 | 原始名称 |
| `DocName` | 封面/首页/标题 | 规范名称，如“质量手册” |
| `DocNo` | 封面/页眉/页脚 | 如 `KSY-QMS-M-01`、`KSY-QMS-P-14` |
| `DocVersion` | 封面/修订页 | 如 `A/0` |
| `EffectiveDate` | 封面/修订页 | 发布日期/实施日期 |
| `DocType` | 文件名/目录/画像 | 手册/程序/指导书/记录/表单 |
| `Aliases` | 封面标题、引用名、简称 | “质量手册”“手册”“QMS 手册” |
| `StandardCodes` | 文档适用标准 | 9001/24001/45001/42061 |
| `ClauseRefs` | 文件名/目的段/手册引用 | 对应条款 |
| `Confidence` | 解析置信度 | 低于阈值进人工确认 |

### 3.3 引用抽取

从每份 Markdown 抽取引用句，模式至少覆盖：

1. `《……》`；
2. `见《……》`、`按《……》执行`、`参照《……》`；
3. `XX-QMS-P-xx`、`XX-QMS-R-xx` 等编号；
4. `相关文件：`、`引用文件：`、`支持文件：` 后面的列表；
5. `本手册 x.x`、`本标准 x.x`；
6. 记录表单编号（`P-14-01`、`R-21-01`）。

每条引用保留：`RawRef`、所在文件、所在章节、前后 100 字上下文、引用类型（要求/参照/记录/说明）。

### 3.4 引用解析顺序

1. **精确匹配**：`FileName` 或 `DocName` 完全相等；
2. **编号匹配**：`DocNo` 完全相等；
3. **别名匹配**：`Aliases` 去空格/去“质量/环境/职业健康”等前缀后相等；
4. **模糊匹配**：文件名 token 重合 + 编辑距离，阈值建议 0.85；
5. **仍未命中**：`reference_gap`，不猜；在详情页显示“被引用但未上传”。

### 3.5 数据模型建议

不新建“文档三表”，只在现有 `cert_enterprise_doc` 上扩展画像，并新增一张引用边表：

```
cert_enterprise_doc（已有）
  + DocProfileJson 扩展：DocName / DocNo / DocVersion / EffectiveDate / DocType / Aliases / StandardCodes / ClauseRefs
  + 或新增 DocIdentityJson 字段，避免破坏旧画像

cert_doc_reference（新增，轻量边表）
  Code
  EnterpriseCode
  FromFileCode
  RawRef
  RefType            // requirement/reference/record/mention
  TargetFileCode     // 解析不到为 null
  ResolveStatus      // exact/no/alias/fuzzy/unresolved
  ContextText
  Sort
  IsDeleted / CreateTime / CreateBy
```

### 3.6 索引怎么用

- **条款→文档**：`ClauseRefs` + 文件名 + 手册“相关文件”小节 + 目的段；
- **文档→条款**：`DocProfile` + `Purpose/Scope` + `ClauseRefs`；
- **文档→文档**：引用图谱 1–2 跳，找“程序引出的记录/表单”；
- **缺口**：`unresolved` 引用进入 `reference_gap`，提示审核员补传；
- **提示词**：把“本条款命中的文档 + 被引用文档 + 未解析引用”一起作为 `doc_index` 注入，而不是只给文件名。

## 四、GBT 章节语义：大标题不是空条款，是“这一章要解决什么”的机器模型

### 4.1 当前错误

之前为了去掉“无正文父级标题”，把 `4`、`5`、`6` 从条款清单中过滤掉。**界面过滤是对的，但上下文不能一起丢。**

- 4 的组织环境、5 的领导作用、6 的策划、7 的支持、8 的运行、9 的绩效评价、10 的改进，正是 PDCA 环节的“章级语义”；
- 它们决定这一章要找什么证据、按什么顺序组织、写到什么深度；
- 没有章级语义，模型只能看 4.1 的几句话，写成“条款转述”。

### 4.2 标准章节画像（StandardChapterProfile）

每个标准 × 每章一条，人工审一次，机器长期用：

| 字段 | 内容 |
|---|---|
| `ChapterNo` | 4/5/6/7/8/9/10 |
| `Title` | 组织环境/领导作用/策划/支持/运行/绩效评价/改进 |
| `StageRole` | 情境/领导/P/D-支持/D-执行/C/A |
| `ChapterQuestion` | 这一章必须回答的核心问题（1 句） |
| `SubClauseDivision` | 子条款怎么分工（4.1 因素、4.2 相关方、4.3 范围、4.4 过程） |
| `EvidenceFocus` | 本章证据重心（手册/方针/目标/记录/现场） |
| `WritingLead` | 本章报告写作重心（陈述/点名/抽样/结论） |
| `CrossClauseLinks` | 与前后章的接口（如 4.1→5.2 方针；6.2→9.3 管评输入） |

9001 的章级画像（先落这一版）：

| 章 | StageRole | ChapterQuestion | EvidenceFocus | WritingLead |
|---|---|---|---|---|
| 4 组织环境 | 情境 | 企业是什么、环境/相关方/范围/过程骨架是什么 | 营业执照、地址、产品、内外因素、相关方清单、过程清单 | 陈述 + 事实列举，不写“符合” |
| 5 领导作用 | 领导 | 谁对体系担总责、承诺什么、方针和职责怎么落 | 手册、方针、任命书、职责权限、管理评审 | 点名责任主体 + 引用方针/职责 |
| 6 策划 | P | 风险机遇怎么定、目标怎么定、变更怎么管 | 风险清单、目标分解、实现计划、变更记录 | 点名制度 + 引用文件 + 目标条目 |
| 7 支持 | D-支持 | 人机料法环和成文信息够不够 | 培训/能力、设备/校准、沟通、文件控制 | 台账归纳 + 抽样明细 |
| 8 运行 | D-执行 | 从顾客要求到放行的过程受控没有 | 合同评审、供方评价、生产记录、放行、不合格 | 过程描述 + 抽样 + 判定 |
| 9 绩效评价 | C | 怎么监视测量、内审、管评，结果说明什么 | 监视数据、内审报告、管评记录 | 结论句 + 日期/要素 |
| 10 改进 | A | 不合格怎么处置、纠正是否有效、改了什么 | 不合格记录、纠正措施、验证记录 | 数量 + 处置 + 验证结论 |

24001/45001 沿用同构，只替换章核心（环境因素/合规义务、危险源/协商参与）；42061 按 33 号文“7/8 章兼环”逐条判，不按章整体归类。

### 4.3 条款要求点（RequirementPoint）

从 GBT 原文解析，不靠报告：

```
RequirementPoint {
  PointId          // 4.1-P1
  ClauseNo         // 4.1
  Text             // 标准原文句
  Subject          // 组织/最高管理者/管理者代表
  Modal            // 应/宜/可/注
  Action           // 确定/监视/评审/建立/保留
  Object           // 内外部因素/记录/方针
  Output           // 清单/记录/报告
  Mandatory        // 注/宜 → false
}
```

4.1 只有两个强制点：

| PointId | 要求 | 类型 |
|---|---|---|
| 4.1-P1 | 确定与其宗旨和战略方向相关、影响预期结果能力的内外部因素 | 文档原生 |
| 4.1-P2 | 对这些因素相关信息进行监视和评审 | 实施/记录型 |

- 标准里的“注 1/2/3”只帮助理解，`Mandatory=false`，不得作为不符合依据；
- 手册 4.1.4 的“管理者代表组织监视评审”只是 **P2 的职责规定**，不等于 **P2 已实施**；
- 真实报告里的“对内部和外部因素进行了监视和评价，并将结果用于经营决策”是 **P2 已实施**，必须来自记录或现场证据。

### 4.4 章节语义怎么进提示词

不要作为“条款”注入，而是作为 `chapter_context`：

```
## 本章要解决什么
第4章 组织环境（情境）：企业处于什么环境、相关方是谁、体系边界和过程骨架是什么。
本章证据重心：营业执照、地址、产品、内外因素、相关方清单、过程清单。
本章写作重心：陈述 + 事实列举；不要写“符合/不符合”。

## 本条款在章内的分工
4.1 理解组织及其环境：确定内外部因素，并监视评审。
```

这样模型知道：**4.1 不是孤立的一句话，它是第 4 章“情境”的输入条款**。它写证据时会找“企业背景/因素清单”，而不是只复述 4.1.1–4.1.3。

### 4.5 父级标题的正确处理

| 场景 | 处理 |
|---|---|
| 计划/检查项条款清单 | 只显示有正文的叶子条款（4.1、4.2…），不显示 4 |
| 提示词上下文 | 保留 4 的章级画像，作为 `chapter_context` |
| 结论/结果行 | 不为 4 生成结论行 |
| 详情页 | 可显示“第4章 组织环境”作为分组标题，不作为可分析条款 |

**结论：父级标题从“条款清单”去掉，但从“上下文”保留。**

## 五、提示词架构：两段式，不在一条提示词里同时“找事实、写证据、下结论”

### 5.1 为什么要拆两段

当前一条提示词同时做四件事：找事实、归并、写证据、下结论。结果：

- 事实没找全也能写出一段“像证据”的话；
- 模型只覆盖它看到的前三条；
- 缺口被一句“符合”掩盖；
- 输出契约有两套，值域冲突。

拆成两段，责任清楚：

| 段 | 输入 | 输出 | 不允许 |
|---|---|---|---|
| **A 事实归集** | 章级画像 + 要求点 + 小节树 + 文件索引 + 现场证据 | `facts[]` + `coverage[]` | 不写结论、不写报告句 |
| **B 证据写作** | A 的 facts/coverage + 章写作重心 + 风格包 | `audit_evidence` + `conclusion` | 不新增事实、不掩盖缺口 |

### 5.2 A 段：事实归集

输出：

```json
{
  "clause": "4.1",
  "chapter": "4 组织环境",
  "facts": [
    {"fact_id":"F1","source_file":"01管理手册QMS.doc","source_node":"4.1.2","fact_type":"list","text":"外部因素包括法律法规、技术、竞争、市场、文化、社会、气候变化、经济","status":"documented"},
    {"fact_id":"F2","source_file":"01管理手册QMS.doc","source_node":"4.1.4","fact_type":"responsibility","text":"管理者代表组织各部门及人员监视和评审内外部因素信息变化","status":"documented"},
```

`status` 值域：

| 值 | 含义 |
|---|---|

| `documented_not_implemented` | 文件有职责/程序，但没有执行记录 |

### 5.3 B 段：证据写作

B 段只做“组织语言”，不做“补事实”。提示词块：

```
{{chapter_profile}}      // 本章要解决什么、证据重心、写作重心
{{requirement_coverage}} // 点级覆盖状态
{{facts}}                // 已核实事实，带来源
{{doc_index}}            // 文件身份 + 引用关系
{{onsite_evidence}}      // 现场证据（可为空）
{{style_pack}}           // 报告语言套路，只学句式/顺序，不学事实
```

写作规则：

1. 主语是企业事实，不是“4.1.1 条款规定……”；
2. 按主题分组，4.1 按“背景→外部→内部→气候变化→监视评审→决策使用”；
3. 只写 `facts` 里的事实；`gaps` 只进 `doubts`；
4. `documented_not_implemented` 只能写“手册规定……”，不能写“已实施”；
5. `onsite_evidence` 为空时，不写人名/面谈/现场观察；
6. 结论按 coverage 推：
   - 关键点 `implemented` 或文档原生 `documented` → pass 候选；
   - 有 `documented_not_implemented` / `onsite_needed` → ofi 候选；
   - 有明确违反事实 → nc；
   - `missing` 不得 pass。

### 5.4 4.1 的目标结果

**仅文档事实**：

> 1、查见《01管理手册QMS.doc》4.1.1—4.1.5：公司各级负责人确定影响战略目标和发展方向实现的内外部因素；识别的外部因素有法律法规、技术、竞争、市场、文化、社会、气候变化、经济等，内部因素有价值观、文化、知识、绩效和成功因素等；手册规定管理者代表组织各部门及人员监视和评审上述因素的变化，并辨识国家政策、相关方理念、员工要求、资源配置等正面和负面要素。

**补现场证据后**：

> 2、与最高管理者潘明海面谈：公司位于……，成立于……，营业执照……，产品为……，厂房面积约 1000㎡；公司识别的外部因素有政治、法律、经济、社会文化、技术、行业竞争、气候变化等，内部因素有企业文化、价值观、知识技术积累、经营绩效、财务、资源、人力、生产运营资源等；对内外因素进行了监视和评价，并将结果用于经营决策。

## 八、风险与边界

1. **章节画像必须人工审一次**：`StageRole/ChapterQuestion/EvidenceFocus` 不能完全让模型生成，否则会变成另一套“报告学习”。建议先做 9001 第4–10章，24001/45001 复用，42061 单独审。
2. **文档结构解析不能追求“全自动”**：标题误升、正文当标题、无编号程序文件，必须允许 `semantic`/`manual` 映射并标置信度。
3. **引用图谱会误配**：同名文件、旧版本、简称，必须保留 `ResolveStatus` 和上下文，低置信度不自动采用。
4. **小节范围有长度上限**：4.1 这类短节可全量；8.x 长节要分块，但分块必须按段落/子标题，不能硬切字符。
5. **报告风格包只学语言**：句式、段落顺序、动词封闭集可以学；证据类型、检查点、结论不能从报告反推。
6. **现场三成不能自动化**：人名、访谈、观察、实际执行记录，必须现场证据；系统只能提示“待确认”。

## 九、一句话总结

**先把企业文档切成“章节树 + 子条款节点”，再把上传文件建成“身份 + 引用图谱”，再把 GBT 建成“章级画像 + 要求点”，最后才让提示词做“事实归集 → 报告式写作”。**

提示词不是第一层，它是最后一层。前三层不做，提示词越写越像报告，事实越不可信。
