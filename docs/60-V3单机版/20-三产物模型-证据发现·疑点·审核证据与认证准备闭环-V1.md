# 三产物模型：证据发现 · 疑点 · 审核证据，与认证准备闭环 V1

> 你提的三个产物方向是对的，而且它把"报告生成"从"一次写作"变成了"一条能被人核查的链路"。本文把三个产物、追溯、认证准备、现场证据回流定成一个闭环，并回答"这个功能该不该加"。

---

## 一、三个产物各自的定义（不能混）

| 产物 | 回答什么问题 | 来源 | 去向 | 审核员能不能改 |
|---|---|---|---|---|
| **证据发现** `Finding` | 文档里**确实写了什么** | 文档提取 | 审核证据的【引用】【事实】槽位 | 可改（改了就锁） |
| **疑点** `Doubt` | 由发现**推论出什么可能缺** | 发现 + 条款要求 + 规则 | 认证准备清单 / 现场核查 | 可标记"已核实/已排除/转不符合" |
| **审核证据** `AuditEvidence` | 按报告语体**怎么写这段话** | 发现 + 疑点状态 + 审核员现场证据 | 报告 | 可改、可锁 |

关键区别：

- **发现是事实陈述，不带判断**。"《采购控制程序》SN/QES-CX-13-2026 规定供方评价由购销部每年进行一次" —— 这是发现。
- **疑点是假设，必须能被推翻**。"2025 年度未见供方评价记录，可能未执行" —— 这是疑点。
- **证据是结论**。"抽查 2025 年供方评价记录 3 份，评价时间分别为…，符合 GB/T 19001-2016 8.4.1" —— 这是证据。

混在一起的后果：模型会把"没找到"直接写成"不符合"，这是审核里最不能犯的错。**分成两层，就能把推论摆在明面上让人判。**

---

## 二、追溯：发现与疑点都必须能点回原文

每条发现/疑点带 `SourceRef`：

| 字段 | 说明 |
|---|---|
| `DocId` | 文档 |
| `Page` / `Para` | 页码、段号（MD 与 PDF 双定位） |
| `Quote` | 原文片段 ≤100 字（用于高亮） |
| `Confidence` | 抽取置信度 |

技术上可行：我们已有 PDF（人看）+ MD（模型读）+ 页码标记，定位链是现成的。

**为什么要加这个功能：**

1. 审核员不会信任一段"没有出处"的话——尤其在他要签字的时候。
2. 疑点被质疑时，能一秒回溯到原文，这是这个工具区别于"让 AI 随便写一段"的核心。
3. 对我们自己也有用：低置信度的发现会被人工点开核对，等于顺手做了标注，回头就是提示词的训练数据。

**结论：加，而且从第一版就加。** 成本很低（提取时顺手存页码与片段），价值很高。

## 三、疑点只从企业资料内部找缺口（不做外部推断）

口径收敛（按你的定义）：**疑点 = 条款要求的东西，资料里没有 / 不完整**。只在企业自己的资料里比对，不推测企业实际怎么运作。

三类，全部可规则化：

| 类型 | 判据 | 例子 |
|---|---|---|
| 有过程无记录 | 条款要求「保持成文信息 / 保留记录」，实际提取到 0 条 | 8.4 要求供方评价记录，全文未找到 |
| 缺文件 | 条款要求的文件（手册/程序/指导书/资质）未在清单中出现 | 6.1.3 要求法规清单，未见该文件 |
| 记录不完整 | 记录存在但关键字段空白 | 入库单无检验结论、校验记录无校验结果/签字 |

判定依据是**条款约束**（属性池里的 `Artifacts` + 条款原文要求的记录物）+ 实际提取结果，做差集。这就是"按条款约束来发现"。

不在本期做：跨部门的覆盖推断（"该部门职责含采购但未见采购记录"）、两处表述矛盾比对。这两类需要跨文档比对，误报率高，等前三类跑稳再说。

疑点状态机：

```
待核查 → 已核实（转不符合） / 已排除（补证据） / 无法确认（保留为观察）
```

只有「待核查」会进入场计划的问题栏；标记后退出，不反复提示。

## 四、认证准备：不用新建，只把疑点灌进入场计划

已确认现状：**认证计划 → 派生入场计划**，但派生是**从检查计划里勾选子集**——很多检查项在远程沟通阶段就已确认，只有一部分需要入场。派生时可勾「是否执行自动分析」，入场计划按检查项组织。

入场准备与入场检查原理相同（都是检查项 + 疑点 + 问题栏），**只在一处验证**，另一处复用同一套数据流。

所以这一块不是新功能，只加一个数据流（先做入场检查，入场准备同构复用）：

```
检查项（多条款×部门×审核人）
   └─ 每个条款：疑点 → 问题栏
入场计划（部门为行，检查项为列/条目）
```

一个检查项挂多个条款时，**逐条款列问题**，不合并成一条模糊问题：

| 检查项 | 条款 | 入场要问的问题 | 要看的东西 |
|---|---|---|---|
| 综合部 / 吕丽荣 | 6.1.2 环境因素 | 重要环境因素清单是否覆盖本次审核范围？ | 环境因素识别评价表、重要环境因素清单 |
| 综合部 / 吕丽荣 | 8.2 应急 | 应急预案演练记录为何缺 2025 年度？ | 应急预案、演练记录、演练照片 |
| 购销部 / 吕丽荣 | 8.4 外部提供 | 供方评价记录未见，是否有其他形式？ | 供方名录、评价表、合格供方清单 |

「能否远程确认」留给审核员勾，不由系统判断。

## 五、闭环：现场证据回流后重算

```
企业资料上传
   ↓ 分析（按标准，与计划解耦）
证据发现 + 疑点
   ↓ 审核员：可选执行"认证准备分析"
现场检查指引（按部门）
   ↓ 审核员：现场补充证据（文字/照片/结论，手动挂接）
审核证据（按报告生成）
   ↓ 审核员：改 / 锁
检查项结论（符合/不符合/观察/不适用）→ NC 卡片 → 报告导出
```

回流规则（按你说的）：

| 情形 | 行为 |
|---|---|
| 检查项已锁 | **不重跑**，现场证据只作留档（锁定在检查项级） |
| 检查项未锁、已挂接现场证据 | 用「企业文档 + 现场证据」一起推论，重算发现/疑点/证据文字；现场证据挂检查项，按语义分到各条款段 |
| 检查项未锁、未挂现场证据 | 只用企业文档生成；疑点保留为"待核查" |
| 只勾选部分检查项 | 只跑勾选的，其余不动 |

**锁定的意义在这里才真正显现**：它不是防覆盖，而是"这段我已经核过了，别再拿模型的话来干扰我"。

## 六、三个产物的数据结构

| 表 | 关键字段 |
|---|---|
| `cert_doc_finding` | `FindingCode`、`DocId`、`Page`、`Quote`、`ProcessDomain`、`ClauseHints`、`Confidence` |
| `cert_clause_doubt` | `DoubtCode`、`ClauseNumber`、`DeptCode`、`Type`、`Text`、`Status`、`SourceFindingCodes` |
| 证据段（18 号） | `ParagraphCode`、`ClauseNumber`、`Text`、`Status`、`FindingCodes`、`DoubtCodes`、`OnsiteEvidenceCodes` |

三段关系：`Finding` 挂在文档上（与条款弱关联），`Doubt` 挂在条款+部门上（强关联），证据段引用两者。

## 七、该不该加：结论

| 功能 | 建议 | 理由 |
|---|---|---|
| 证据发现 + 疑点 | **加，第一版就加** | 它是"可信"的来源；不加，报告就是黑箱 |
| 追溯（页码 + 原文片段） | **加** | 成本低；签字场景必需 |
| 认证准备指引 | **不新建**：已有入场计划，只接疑点当问题栏 | 一期只做数据流，不改流程 |
| 现场证据回流重算 | **加** | 你已经定了流程，缺的只是状态规则（见 §五） |
| 疑点自动转不符合 | **不加** | 判定权留给审核员，且结论挂在检查项（复用认证检查结论字段） |
| 结论编辑 / NC 卡片 / 报告导出 | **后置** | 先把「文字（条款段）」与「判定（检查项）」分开，功能后续接 |
