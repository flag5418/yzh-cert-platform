## 一、结论先行

当前 4.1 与真实报告差在三处，且顺序不能颠倒：

| # | 差距 | 性质 | 直接后果 |
|:--:|---|---|---|
| 1 | **事实没提全**：手册 4.1 有 4.1.1–4.1.5 + a–d，提取结果只有 4.1.1–4.1.3 | 提取链路 | 模型看不到 4.1.4 监视评审、4.1.5 正负面要素，只能写前三条 |
| 2 | **表达没重组**：模型按手册子条款逐条转述（“4.1.1 条款规定……”） | 提示词写法 | 报告是“识别的外部因素有……；内部因素有……”，不是逐条抄手册 |
| 3 | **边界没说清**：哪些必须原样、哪些可以归类合并、哪些只能现场补，提示词没有规则 | 提示词边界 | 模型要么漏，要么把“规定”写成“已实施”，要么把缺口藏进一句“符合” |

**一句话**：4.1 不是提示词“文风”问题，是**事实供给不完整 + 缺少“要求点→事实→主题段”的组织工序**。只改文风，仍会漏 4.1.4/4.1.5。

## 二、4.1 实证诊断

### 2.1 手册原文有什么

`01管理手册QMS.doc` 4.1 实际包含：

| 事实单元 | 内容 | 当前提取 |
|---|---|:--:|
| 4.1.1 | 各级负责人理解顾客/法规，确定影响战略目标的内外部因素和环境、安全状况 | ✅ |
| 4.1.2 | 外部因素：国际/国家/地区/地方法律法规、技术、竞争、市场、文化、社会、气候变化、经济 | ✅ |
| 4.1.3 | 内部因素：价值观、文化、知识、绩效、成功因素 | ✅ |
| a） | 分析市场/行业竞争对手/外部供方，认识行业地位 | ❌ |
| b） | 分析内部能力/技术/管理水平，明确战略目标和发展方向 | ❌ |
| 4.1.4 | 管理者代表组织各部门及人员监视和评审内外部因素信息变化 | ❌ |
| 4.1.5 | 确定因素时辨识正面/负面要素或条件 | ❌ |
| 4.1.5 a–d | 国家法规政策、相关方理念价值观、员工要求、资源配置 | ❌ |

**当前提取只覆盖 3/12 个事实单元**。这就是“没有提取完成”的实锤，不是模型写作偏好。

### 2.2 为什么提取会漏

不是 `Excerpts` 有“最多 3 条”的硬限制，而是提取提示词缺少三条约束：

1. 只要求“逐条摘录原文”，没有要求“一个主条款下的所有子条款/分点必须逐项覆盖”；
2. `Anchor` 只要求一个 10–40 字定位片段，模型给到 4.1.1 就认为这条已完成；
3. 没有输出前自检，也没有提取后校验；漏 4.1.4/4.1.5 仍算 `done`。

### 2.3 当前审核证据为什么是“条款转述”

当前提示词的关键句是：

- “逐条款拆出条款正文里的要求点”；
- “审核证据按条款分开写”；
- “先写查了什么文件/记录，再写看到了什么事实”。

模型于是按**手册子条款编号**逐条写：

> 1、查阅《01管理手册QMS.doc》：4.1.1 条款明确要求……；2、该手册 4.1.2 条款具体列出……；3、该手册 4.1.3 条款具体列出……

这不算错，但不是审核报告写法。真实报告的主语是**企业事实**，不是**手册条款号**：

> 识别的外部因素有政治环境、法律（含标准）、经济、社会文化、技术、行业竞争、气候变化等；识别的内部因素有企业文化、公司价值观、知识技术积累、经营绩效、财务、综合资源、人力、生产运营资源等。

报告把 4.1.2/4.1.3/4.1.5 的事实**按主题归类**了，没有保留手册编号。

### 2.4 还有两个提示词结构问题

1. **属性池仍在进提示词**：`CertCheckContextBuilder.RenderClauseInfo` 仍输出“条款属性线索”（条款意图/义务/适用性/过程/严重度/证据形式等）。这与你“审核员只关心条款内容”的要求冲突，也会把模型注意力拉向属性分类。
2. **两套输出契约并存**：模板正文要求 `pass/ofi/nc/na`，但 `RenderClauseBlocks` 末尾又追加 `conformant/minor_nc/major_nc/observation` 的旧契约。模型可能按旧值域输出，后续解析再映射，属于隐性错误源。

## 三、四个问题的直接回答

### 3.1 找不到的，怎么办

不要用一个“missing”糊过去。按四层处理：

| 情况 | 判定 | 输出位置 | 禁止 |
|---|---|---|---|
| 提取结果里没有该子条款 | `extract_gap` | 提取告警 + 重提 | 不得写成“企业未提供” |
| 企业文档确实没有该内容 | `not_in_doc` | `doubts` | 不得直接判 nc |
| 文档有规定、但没有执行记录 | `ofi_candidate` | `doubts` + `ofi` 建议 | 不得把“规定”写成“已实施” |
| 只能现场确认（访谈/观察） | `onsite_needed` | 现场证据待补 | 不得凭条款推断事实 |
| 条款不适用 | `na` | 结论 + 理由 | 不得用“没找到”代替 N/A |

**检索顺序固定**：条款↔文档对照 → 文档提取摘录 → 记录/台账 → 现场证据。每层都要留检索痕迹，输出 `evidence_gap` 说明“查到哪一层、缺什么”，而不是一句“未见”。

### 3.2 找到了，怎么组织

按“**要求点 → 事实 → 主题段**”三步，不按文档目录/子条款号组织。

| 步 | 做什么 | 4.1 示例 |
|:--:|---|---|
| 1 要求点 | 把标准条款拆成可核对的点 | 4.1 只有两个强制点：①确定内外部因素；②监视和评审 |
| 2 事实 | 把手册/记录/现场事实挂到点上 | 4.1.2 外部因素、4.1.3 内部因素、4.1.4 监视职责、4.1.5 正负面要素 |
| 3 主题段 | 按报告主题合并，不按手册编号 | 组织背景 → 外部因素 → 内部因素 → 气候变化 → 监视评审 → 用于决策 |

4.1 的主题槽位建议固定为：

| 槽位 | 事实来源 | 没有事实时 |
|---|---|---|
| 组织背景 | 企业基础信息/营业执照/现场 | 省略，不编地址/面积 |
| 外部因素 | 手册 4.1.2 + 4.1.5 a | 写手册列出的类别 |
| 内部因素 | 手册 4.1.3 + 4.1.5 c/d | 写手册列出的类别 |
| 气候变化 | 手册 4.1.2/现场 | 省略，不推断“已考虑” |
| 监视评审 | 手册 4.1.4 职责 + 记录/现场 | 只写“规定由管理者代表组织”，不写“已实施” |
| 决策使用 | 管理评审/经营决策记录/现场 | 省略，放 doubts |

**报告式写法示例（仅文档事实，不编访谈）**：

> 1、查见《01管理手册QMS.doc》4.1.1—4.1.5：公司各级负责人确定影响战略目标和发展方向实现的内外部因素；识别的外部因素有法律法规、技术、竞争、市场、文化、社会、气候变化、经济等，内部因素有价值观、文化、知识、绩效和成功因素等；手册规定管理者代表组织各部门及人员监视和评审上述因素的变化，并辨识国家政策、相关方理念、员工要求、资源配置等正面和负面要素。

这段已经比“4.1.1 条款规定……”接近报告，且每个事实都能指回手册。

### 3.3 哪些应该完整提取

**必须完整、逐项保留，不得概括丢失**：

1. 主条款下所有子条款编号及正文（4.1.1–4.1.5）；
2. 所有 a/b/c/d 分点（4.1.5 a–d）；
3. 文件/记录名称、编号、版本、发布日期、编制/审核/批准人；
4. 面谈对象、岗位、部门；
5. 记录期间、样本量、批号、数量、日期；
6. 判定基准中的数值、公差、法规条款号；
7. 原文中明确出现的“应/不应/必须”要求句。

**可以压缩、不必逐字保留**：

1. 重复的解释性铺垫；
2. 目录、页眉页脚、修订记录；
3. 标准条款的“注”（只帮助理解，不作为强制要求）；
4. 同一事实在多份文件中的重复表述（保留最完整的一份，其他记来源）。

### 3.4 哪些应该重新组织和改写

| 允许改写 | 边界 | 4.1 示例 |
|---|---|---|
| 归类合并 | 只能合并原文已有类别，不新增类别 | 法律法规/政策 → 法律（含标准）；文化/社会 → 社会文化 |
| 上位词 | 必须由至少一个原文具体项支撑，括号保留原词 | “政治环境（法律法规、政策）” |
| 主题重排 | 按报告主题，不按手册编号 | 外部因素→内部因素→监视评审 |
| 句式改写 | 用审核报告动词封闭集：查见/见/抽见/现场查见/与X面谈 | “查见《手册》……” |
| 责任主体改写 | 只改表述，不改主体 | “管理者代表组织各部门” |

**绝对不可改写**：

1. 文件编号、版本、日期、人名、部门、样本数；
2. 标准条款原文引用（需要引用时逐字，不改写）；
3. 事实状态：**“规定”不能写成“已实施”**，**“未找到”不能写成“不符合”**；
4. 判定结论：只能从 `pass/ofi/nc/na` 枚举选，不自创；
5. 现场访谈内容：没有现场证据就不写“与潘明海面谈”“现场看到……”。

## 四、提示词优化计划

### P0 · 先修事实供给（1–2 天，优先级最高）

**目标**：4.1 从 3 个事实单元提升到 12 个，先让模型“看得到”。

改动：

1. **提取提示词加“逐项覆盖”硬规则**
   - 一个 `ClauseNumber` 下存在多个子条款（4.1.1–4.1.5）或分点（a–d）时，`Excerpts` 必须逐项覆盖，不得只摘前三条；
   - 输出前自检：“该条款下每个编号/分点是否都有摘录；缺一项则补”；
   - 条目多时可合并相邻短句，但不得丢项；
   - `Anchor` 仍保留一个主锚点，新增可选 `ExcerptItems[{Text, Anchor, SubClause}]`，让每条摘录可回指。

2. **提取后加完整性校验（不能只靠提示词）**
   - 从源 Markdown 的 4.1 小节正则提取 `4.1.x` 与 `a）–d）` 标记；
   - 与 `Excerpts` 覆盖的子项比对；
   - 缺项则记 `Coverage.Missing`，并触发一次“补漏”重试；
   - 仍缺则 `ExtractStatus=partial`，不能标 `done`。

3. **重跑手册提取**
   - 验收：4.1 至少覆盖 4.1.1–4.1.5 + a–d；`Missing=[]`；
   - 当前 `f0475d6f...` 只有 3 条，必须替换，不得沿用。

### P1 · 统一审核证据提示词骨架（2–3 天）

**目标**：只保留一套契约，去掉干扰项，明确工序。

1. **删除属性池**
   - `RenderClauseInfo` 不再输出“条款属性线索”；
   - `RenderClauseBlocks` 只保留：条款正文 → 审核发现（文档原文）。
   - 如后续需要严重度约束，由提示词按条款原文判断，不再依赖 9 类属性。

2. **统一输出契约**
   - 删除 `RenderOutputContract` 里的旧 `conformant/minor_nc/...`；
   - 只保留 `pass/ofi/nc/na`；
   - `clause_blocks` 不再自动追加第二套 JSON schema，避免模型看到两个结论值域。

3. **新增“企业基础信息”块**
   - 字段：企业名称、统一社会信用代码、法定代表人、地址、行业、认证范围；
   - 为空就不写，不得用占位符编造；
   - 用于 4.1 组织背景、4.2 相关方等条款。

4. **把“企业文档命中”改名为“审核发现（企业文档原文，只读）”**
   - 与页面术语一致；
   - 明确“这是事实来源，不是审核证据，不是结论”。

5. **新增“要求点清单”输入**
   - 每条标准条款预拆 1–5 个要求点（4.1：确定因素 / 监视评审）；
   - 每个要求点带 `point_id`、原文句、是否强制（过滤“注”）；
   - 模型必须逐点回答 `covered / missing / onsite_needed`，再合并成段。

### P2 · 加“报告式重组”规则（2 天）

**目标**：从“条款转述”变成“主题段”。

在 `audit_check` 正文增加：

1. **主语规则**：审核证据以企业事实为主语，条款号只做来源标注；
2. **主题优先**：先按主题分组，不按手册子条款编号；
3. **4.1 主题槽位**：组织背景 → 外部因素 → 内部因素 → 气候变化 → 监视评审 → 决策使用；
4. **允许的语义动作**：归类、合并、上位词（须有原文支撑）、句式改写；
5. **禁止动作**：新增事实、把“规定”写成“已实施”、把“未找到”写成“不符合”、写“未进行面谈/未观察到”；
6. **缺口处理**：没找到的要求点只进 `doubts`，不塞进审核证据；
7. **现场问答式**：只有 `onsite_evidence` 有事实时，才允许“与某某面谈……”；否则不写人名。

建议给 4.1 一条 few-shot，但 **few-shot 只用文档事实**，不把报告里的潘明海/营业执照/面积混进去，避免模型学会编造。

### P3 · 验收与回归（2 天）

**测试集**：4.1、4.2、4.3、4.4、5.1、8.6（先文档原生型，再采样型）。

| 指标 | 门槛 |
|---|---|
| 事实覆盖 | 手册 4.1 的 12 个事实单元，审核证据至少覆盖 10 个；缺项必须出现在 doubts 或 coverage |
| 可溯源 | 每个事实能指回文件/记录/现场证据，100% |
| 报告式 | 不出现“4.1.1 条款规定……”作为主语；外部/内部因素按主题归类 |
| 无编造 | 没有现场证据时，不出现人名、地址、面积、营业执照号、监视记录 |
| 契约 | 只有一套 JSON schema，`conclusion` 只在 pass/ofi/nc/na |
| 结论一致 | `pass` 时关键要求点必须 covered；有未覆盖点不得 pass |
| 人工盲评 | 审核员 3 秒判断“可用初稿”的比例 |

## 五、我们能实现到哪一步

| 场景 | 可实现程度 | 说明 |
|---|---|---|
| 4.1 文档部分（因素识别、职责规定、正负面要素） | **80–90%** | 提取补全后，可按报告主题写出“外部因素/内部因素/监视职责” |
| 4.1 完整报告（含潘明海面谈、营业执照、1000㎡、监视评价已实施） | **40–60%（仅文档）→ 90%（补企业基础信息+现场证据）** | 访谈和“已实施”事实不在手册里，系统不能凭空生成 |
| 4.2/4.3/4.4 文档原生型 | **75–85%** | 依赖手册/程序文件的完整提取 |
| 8.x 采样分析型 | **60–70%** | 必须有记录/台账/样本；没有记录只能 ofi/待确认 |
| 全体系整体 | **约七成自动 + 三成现场** | 与 33 号文规律十一致 |

**4.1 的准确说法**：文档部分可以做到“报告式初稿”；报告里的现场访谈和“已实施”结论，必须由现场证据补足。当前系统 `CheckEvidences=0`，所以不能把报告原文直接当成系统应生成的内容。

## 六、建议的下一步

1. **先做 P0**：改提取提示词 + 加覆盖率校验，重跑 `01管理手册QMS.doc`，把 4.1 补到 12 个事实单元。
2. **再做 P1/P2**：删属性池、统一契约、加主题槽位和报告式规则。
3. **用 4.1 做首个对照**：生成段 vs 真实报告逐句 diff，只比较“文档能支撑的部分”；访谈部分单独标注“需现场证据”。
4. **4.1 通过后再扩 4.2/4.3/4.4**，不要直接铺全条款。

**风险**：如果 P0 不做，只改 P1/P2 的写作规则，模型仍然看不到 4.1.4/4.1.5，会继续写出“看起来很像报告、但事实不全”的证据——这比明显的缺失更难发现。
