# 文档画像与章节·部门检索规则 V1

> 结论：**文档提取规则要分两段。上传时只做“文档画像”，不判断检查部门；检查时才用计划里的部门 + 条款章节属性做召回。**
> 条款不是检索主键；主键是 **章节阶段 → 过程 → 部门 → 文档类型**。

---

## 一、先纠正一个关键点

“提示词要考虑计划中定义的部门”是对的，但要分两段：

| 阶段 | 时机 | 是否知道计划部门 | 要做什么 |
|---|---|---|---|
| 上传提取 | 文档上传后立即跑 | **不知道**（计划可能还没建） | 识别文档类型、主章节、主过程、归属部门、作用、提取模式 |
| 检查召回 | 检查项分析时 | **知道**（`DeptNames`） | 用条款章节属性 + 计划部门 + 文档画像召回事实 |

所以：

- **上传时**：抽取 `OwnerDept / SupportDepts`，不依赖计划；
- **检查时**：把 `DeptNames` 注入提示词，按部门过滤；
- 不能在上传时要求“按计划部门提取”，因为那时还没有计划。

## 二、检查项部门现状

当前科斯亚计划 7 条检查项：

| 条款 | 部门 |
|---|---|
| 4.1 | 管理层 |
| 4.2 | 管理层 |
| 4.3 | 管理层 |
| 4.4.1,4.4.2 | 管理层 |
| 5.1.1,5.1.2 | 管理层 |
| 5.2.1,5.2.2 | 管理层 |
| 5.3 | 管理层 |

这说明：

- 4.x/5.x 本来只应召回管理层文档；
- 当前却把财务、考勤、销售、生产指导书都带进来；
- 不是模型不懂，是**召回条件里没有部门**。

## 三、文档画像（上传时）

### 3.1 输出结构

```json
{
  "DocType": "manual|procedure|work_instruction|record|form|index|audit_record|review_record|policy|other",
  "ExtractionMode": "clause_full|process_profile|record_profile|index_only|audit_profile",
  "StageRole": "plan|support|run|check|act|mixed",
  "PrimaryChapter": "4|5|6|7|8|9|10",
  "SecondaryChapters": ["..."],
  "MultiChapterReason": "",
  "PrimaryProcess": "",
  "OwnerDept": "",
  "SupportDepts": [],
  "Purpose": "",
  "Scope": "",
  "ClauseLinks": [
    {"ClauseNumber": "8.5.1", "Relation": "primary|supporting|reference"}
  ],
  "Confidence": 0.0
}
```

### 3.2 文档类型 → 提取模式

| DocType | 典型文档 | ExtractionMode | 是否逐条款 |
|---|---|---|---|
| `manual` | 质量手册 | `clause_full` | **是**，逐条款 + 子条款覆盖 |
| `policy` | 方针、目标文件 | `clause_full` | **是**，但只取 5.2/6.2 |
| `procedure` | 程序文件 | `process_profile` | **否**，取过程/部门/活动/输出记录 |
| `work_instruction` | 作业指导书、操作规程 | `process_profile` | **否**，取工序/岗位/参数/接收准则 |
| `record` / `form` | 检验报告、保养记录、生产日报 | `record_profile` | **否**，取过程/部门/字段/期间/批次/签署 |
| `index` | 封面、目录、文件清单、记录清单、汇编 | `index_only` | **否**，只做索引/引用 |
| `audit_record` | 内审计划、检查表、内审记录 | `audit_profile` | **否**，取审核范围/日期/条款/发现/结论 |
| `review_record` | 管理评审记录 | `audit_profile` | **否**，取评审输入/输出/结论 |
| `other` | 无法判断 | `process_profile` | **否**，低置信度，待人工 |

### 3.3 章节阶段 → 文档作用

| 章节 | StageRole | 本章要解决什么 | 典型文档 | 不应作为主证据 |
|---|---|---|---|---|
| 4 组织环境 | `plan` | 组织处于什么环境、相关方是谁、体系范围、过程有哪些 | 手册、内外部因素清单、相关方清单、范围说明、过程清单 | 生产日报、检验报告、财务/考勤 |
| 5 领导作用 | `plan` | 最高管理者如何领导、承诺、方针、职责 | 手册、方针、目标、组织架构、岗位职责、管理评审 | 作业指导书、生产记录 |
| 6 策划 | `plan` | 风险机遇、质量目标、变更如何策划 | 风险清单、风险程序、目标分解、变更策划 | 检验报告、考勤 |
| 7 支持 | `support` | 资源、能力、意识、沟通、成文信息如何支持 | 培训计划/记录、能力矩阵、设备台账、校准记录、文件控制程序 | 销售合同、生产日报 |
| 8 运行 | `run` | 运行过程如何受控、产品服务如何提供、外部提供如何控制、放行、不合格 | 生产程序、作业指导书、采购程序、检验记录、放行记录、不合格记录 | 财务制度、考勤、内审记录 |
| 9 绩效评价 | `check` | 如何监视测量、内审、管理评审 | 监视测量程序、内审计划/检查表/记录、管理评审、客户满意度 | 作业指导书、生产日报 |
| 10 改进 | `act` | 如何改进、纠正措施 | 不合格/纠正措施程序、改进记录、CAPA | 培训计划、财务制度 |

### 3.4 文档画像的判断规则

**优先级 1：文件名/目录硬规则**

- 含“手册” → `manual`
- 含“程序” → `procedure`
- 含“作业指导书 / 操作规程 / 规范 / 工艺” → `work_instruction`
- 含“记录 / 报告 / 表单 / 检查表 / 清单” → `record` / `form`
- 含“封面 / 目录 / 汇编 / 文件清单 / 记录清单” → `index`
- 含“内审” → `audit_record`
- 含“管理评审” → `review_record`
- 含“方针 / 目标” → `policy`

**优先级 2：正文结构**

- 有“1 目的、2 适用范围、3 职责、4 工作程序、5 相关文件、6 质量记录” → `procedure`
- 有“操作步骤、参数、接收准则、异常处理” → `work_instruction`
- 有“日期、批次、样本、检验项、判定、签名” → `record`
- 有“审核日期、审核员、受审核部门、条款、不符合项” → `audit_record`
- 有“评审输入、评审输出、决定措施” → `review_record`

**优先级 3：章节/过程**

- 文档标题出现“生产和服务提供 / 生产过程 / 工序 / 巡检 / 首件 / 设备 / 特殊过程” → 8 章、run；
- “采购 / 供应商 / 来料” → 8.4、run；
- “内审 / 管理评审 / 客户满意度 / 监视测量” → 9 章、check；
- “不合格 / 纠正措施 / 改进” → 10 章、act；
- “培训 / 能力 / 文件控制 / 记录控制 / 设备 / 校准” → 7 章、support；
- “风险 / 目标 / 变更” → 6 章、plan；
- “方针 / 职责 / 组织架构” → 5 章、plan；
- “环境 / 相关方 / 范围 / 过程” → 4 章、plan。

### 3.5 跨章节处理

- `manual` 允许跨 4–10，`StageRole=mixed`；
- `audit_record` / `review_record` 允许跨多章，但必须标 `audit_profile`，只作二线证据；
- `index` 允许跨多章，但只做索引；
- `procedure` / `work_instruction` / `record` **只允许 1 个主章节**；最多 1 个次章节，且必须写理由；
- 超过 2 个章节 → `MultiChapterSuspect=true`，降低置信度，交人工或二次判定。

## 四、检查时召回（知道计划部门）

### 4.1 输入

```json
{
  "ClauseNumber": "8.5.1",
  "PlanDeptNames": ["生产部"],
  "ClauseRequirement": {
    "Chapter": "8",
    "StageRole": "run",
    "RequiredProcesses": ["生产和服务提供", "设备管理", "过程确认"],
    "RequiredDepts": ["生产部", "品质部"],
    "RequiredDocTypes": ["procedure", "work_instruction", "record"],
    "ExpectedFacts": ["受控条件", "工艺文件", "设备/环境", "人员资格", "过程确认", "防错", "放行/交付"]
  }
}
```

### 4.2 召回顺序

1. **章节匹配**：`ClauseRequirement.Chapter == DocProfile.PrimaryChapter`，或 `ClauseLinks` 有 `primary`；
2. **部门匹配**：`DocProfile.OwnerDept` 或 `SupportDepts` 与 `PlanDeptNames` 有交集；
3. **文档类型匹配**：`DocProfile.DocType` 在 `RequiredDocTypes`；
4. **过程匹配**：`DocProfile.PrimaryProcess` 在 `RequiredProcesses`；
5. **排除**：`index_only`、`audit_profile` 不作为一线事实；`reference` 只作引用；
6. **跨部门**：如果文档 `SupportDepts` 含计划部门，可作为支持证据，但标 `supporting`，不占主证据。

### 4.3 例：8.5.1，计划部门=生产部

召回：

- `17生产和服务提供控制程序`：OwnerDept 生产部，primary；
- `11 IPQC巡线作业指示书`：OwnerDept 品质部，SupportDepts 生产部，supporting；
- `10来料检查作业指示书`：OwnerDept 品质部，supporting；
- `02-1设备日常维护保养记录`：OwnerDept 生产部，primary；
- `特殊过程确认记录`：OwnerDept 生产部，primary；
- `05生产日报表`、`07工序流转卡`：OwnerDept 生产部，primary。

排除：

- `02公司财务管理制度`：OwnerDept 财务，非生产/品质；
- `06考勤管理制度`：OwnerDept 综合部，非 8 章；
- `03销售人员管理制度`：OwnerDept 销售部，非 8 章；
- `00程序文件汇编封面`：index_only。

### 4.4 例：4.1，计划部门=管理层

召回：

- `01管理手册QMS`：OwnerDept 管理层，primary；
- `01-外部因素识别监视评价总清单`：OwnerDept 管理层，primary；
- `02-内部因素识别监视评价总清单`：OwnerDept 管理层，primary；
- `管理评审记录`：OwnerDept 管理层，supporting；
- `01质量风险与机遇分析评价表`：OwnerDept 管理层，supporting（跨 6.1）。

排除：

- `01-年度培训计划表`：OwnerDept 综合部，7 章；
- `04风险机遇控制程序`：OwnerDept 管理层，但 6 章，`ClauseLinks 4.1=reference`，只作引用；
- `07记录清单`：index_only；
- `01组织环境... (1)`：重复副本，去重。

## 五、条款属性要补什么

当前属性池只有 9 类抽象属性，不够。补：

```text
Chapter            4–10
StageRole          plan|support|run|check|act
RequiredProcesses  本条款需要哪些过程
RequiredDepts      本条款需要哪些部门
RequiredDocTypes   本条款需要哪些文档类型
ExpectedFacts      本条款期望看到哪些事实类型
RelatedClauses     相关条款
DepartmentRule     primary/support/cross
```

这不是新增抽象分类，是**条款召回条件**。

### 5.1 七条先做样例

| 条款 | Chapter | StageRole | RequiredProcesses | RequiredDepts | RequiredDocTypes |
|---|---|---|---|---|---|
| 4.1 | 4 | plan | 环境识别、战略、管理评审 | 管理层 | manual, record, review_record |
| 4.2 | 4 | plan | 相关方管理、客户沟通 | 管理层、销售部 | manual, record |
| 4.3 | 4 | plan | 体系范围 | 管理层 | manual |
| 5.1 | 5 | plan | 领导作用 | 管理层 | manual, policy, review_record |
| 6.1 | 6 | plan | 风险机遇 | 管理层、品质部 | procedure, record |
| 7.2 | 7 | support | 人力资源、培训 | 综合部 | procedure, record, work_instruction |
| 8.5.1 | 8 | run | 生产和服务提供、设备、过程确认 | 生产部、品质部 | procedure, work_instruction, record |
| 8.6 | 8 | run | 放行 | 品质部 | procedure, record |
| 9.2 | 9 | check | 内审 | 品质部、管理层 | audit_record |

## 六、改造顺序

### P0 文档画像

1. 新增 `DocProfile` 字段：`DocType / ExtractionMode / StageRole / PrimaryChapter / SecondaryChapters / PrimaryProcess / OwnerDept / SupportDepts / Purpose / Scope / ClauseLinks / Confidence / MultiChapterSuspect`；
2. 先跑 99 份画像，不重跑事实；
3. 产出“画像抽检表”，人工看 10 份：手册、生产程序、IPQC、财务、考勤、封面、内审、管理评审、外部因素清单、记录清单。

### P1 按模式改提取

- `clause_full`：手册/方针，逐条款 + 子条款覆盖；
- `process_profile`：程序/指导书，只出过程画像；
- `record_profile`：记录/表单，只出记录画像；
- `index_only`：封面/清单/汇编，只出索引；
- `audit_profile`：内审/管理评审，只出审核/评审画像。

### P2 检查时按部门召回

- `CertCheckContextBuilder` 增加 `PlanDeptNames`；
- `ProjectDocSlices` / 新的 `DocumentRecallService` 按 `Chapter + Dept + DocType` 召回；
- `AuditFindings` 只接收 `primary/supporting`，`reference` 单独列。

### P3 对照 4.1/8.5.1

- 4.1 计划部门=管理层：只召回手册、因素清单、管理评审；
- 8.5.1 计划部门=生产部：只召回生产程序、作业指导书、设备/特殊过程/生产记录，品质部记录作 supporting；
- 对比真实报告，确认不再出现财务/考勤/销售。

---

## 七、结论

1. **文档画像先于条款提取**：先判断“这是什么文档、属于哪个章节/过程/部门”，再决定要不要逐条款。
2. **只有手册/方针需要逐条款**；程序、指导书、记录、清单都不需要完整条款内容。
3. **检查项部门必须进入召回条件**，否则 4.x/5.x 会继续召回财务、考勤、销售文档。
4. **条款检索顺序**：章节阶段 → 过程 → 部门 → 文档类型 → 事实。
5. **上传时画像不依赖计划，检查时召回才依赖计划部门**；两段不能混。
6. 先做 P0 画像，不重跑 99 份事实；画像稳定后再按模式重跑。
