## 0. 结论先行

1. **3/3 条条款都能形成明确的证据期望**，条款契约这条链路成立。
2. 当前 V2.1 的问题不是“字段不够多”，而是**只有一种扁平的 `Records` 对象**，装不下三种形态：
   - 目录型（`QR-010` 记录清单）
   - 治理证据包（内审 `QR-015/016/017/018/019`）
   - 运行记录（`QR-027/028/037/038` 检验/放行）
3. 最小改动不是加 40 个字段，而是**按对象分型 + 2 个通用字段**：
   - `RecordProfile`：运行记录
   - `RecordCatalog`：目录/清单
   - `RecordSet`：内审/管评等治理包
   - 通用补 `Applicable`、`Coverage`
4. `8.2.6` 出现一个关键反例：**报告引用的实际检验记录不在记录文件夹**，文件夹里只有空白模板和跨产品终检报告。只靠文档提取会误判“缺失”，报告必须作为证据源参与。
5. 不建议继续在扁平结构上加字段；建议先按“三种对象”改提示词，再跑 5 条条款。

**实际证据 `QR-010`：**

- 4 个 sheet：质量类 34、技术类 14、生产类 31、其它 21，合计 100 条。

**匹配结论：`partial`。**

## 5. 三条试点发现

### 5.1 `4.2.5`：目录型不是“多行记录”，是独立对象

`QR-010` 100 条，当前 V2.1 的 `Rows` 最多 30 行，会丢 70 条；`Samples` 只留 3 条，报告只看到 3 条样本。  
更关键的是：目录需要的是**总数、缺项、多项、编号冲突、保存期限字段**，不是“样例行”。

结论：`RecordCatalog` 必须独立，至少包含：

```text
CatalogType        // record_list / file_list / ledger
Count              // 100
Items[]            // 前 10 条即可，不全量塞
Missing[]          // 清单有、文件无
Extra[]            // 文件有、清单无
CodeConflicts[]    // 同号两名/页脚错号
RetentionFields[]  // 保存期限/检索/处置是否存在
```

### 5.2 `8.2.4`：内审不是一张表，是证据包

当前 V2.1 只能输出 `Records 1–3`，装不下“计划 → 签到 → 检查表 → 不合格 → 报告 → 关闭”这条链。  
试点里 `QR-015` 计划、`QR-017` 检查表、`QR-019` 报告三者的审核员名单不一致，扁平结构完全看不到这个缺口。

结论：`RecordSet` 必须独立，至少包含：

```text
SetType            // internal_audit / management_review
Period
Owner
Members[]          // 文档名 + 状态 + 编号
Coverage           // 部门 / 条款 / 过程
Findings[]         // 不符合 / 观察
Closure            // 关闭日期 / 验证人 / 证据
Consistency        // 计划/检查表/报告名单是否一致
```

### 5.3 `8.2.6`：空白模板 ≠ 缺失，跨产品 ≠ 证据，报告可能是唯一证据源

- `QR-027/037/028` 是空白模板：只能证明“表单存在”，不能证明“已检验/已放行”。
- `QR-038` 有内容，但写的是“髓腔锉”，与手动轮椅车不符：必须 `Applicable=false`，否则会被误采信。
- 报告 8.2.6 写了 5 批实际检验记录（日期/型号/数量/检验员），但这些记录不在 `4记录文件`。  
  只靠文件夹提取会得出“缺失”的错误结论；报告必须作为证据源参与匹配。

结论：运行记录必须补两个字段：

```text
Applicable     // 产品/工艺/范围是否适用
Coverage       // 批号/型号/数量/期间/对象覆盖
```

`RecordState` 只回答“有没有实例”，不能替代 `Applicable` 和 `Coverage`。

## 7. 最小改动建议

不建议继续加平面字段。建议按“三种对象”分型，每份文档只填其中一种：

```text
DocBase {
  DocClass        // record / catalog / set / procedure / work_instruction
  Name
  Code
  Process
  AuditArea
  Dept
  Semantic        // 一句话证据角色，可选
}

RecordProfile extends DocBase {
  Applicable
  HasInstance
  ZeroEvent
  Completeness
  Coverage
  Fields[]
  Samples[]
  Warnings[]
}

RecordCatalog extends DocBase {
  CatalogType
  Count
  Items[]          // 前 10 条
  Missing[]
  Extra[]
  CodeConflicts[]
  RetentionFields[]
}

RecordSet extends DocBase {
  SetType
  Period
  Owner
  Members[]
  Coverage
  Findings[]
  Closure
  Consistency
}
```

**为什么这不是“字段更多”：**

- 旧 V2.4：每条记录 46 个字段，全部要填。
- 新结构：每份文档只填 `DocBase` + 一种对象，约 10–13 个字段。
- 目录、内审包各自有专用字段，不再挤进 `Records`。

## 9. 用报告结论对账，不需要你裁决

你不需要决定字段、契约或 NC 分类。报告结论就是现成的 oracle，对账规则如下：

| 情况 | 处理 |
|---|---|
| 报告有明确结论/未开 NC，文件夹事实一致 | 契约验证通过 |
| 报告结论与文件夹事实不一致 | 记 `report_gap`：报告没捕获/没展开，不强行让文档迎合报告 |
| 报告未提但文件夹有 | 记 `unused_evidence`：报告消费不足，契约期望可能过宽 |
| 文件夹没有、报告有实际数据 | 记 `report_only`：报告是证据源，文件夹目录不完整 |

三条对账结果：

| 条款 | 报告结论 | 文件夹匹配 | 对账结论 |
|---|---|---|---|
| `4.2.5` | 未开 NC；称按程序保存留档 | `partial` | 报告结论符合；文件夹证据 partial。差在清单没有保存期限列，属报告未展开，不是企业缺记录 |
| `8.2.4` | 明确“内审实施符合标准要求” | `partial` | 报告结论符合；文件夹 partial。差在计划/检查表/报告审核员名单不一致，属报告未捕获的内部不一致 |
| `8.2.6` | 未开 NC；称所有产品经成品检验合格后入库 | `missing` + `report_only` | 报告结论符合；文件夹 missing。证据在报告里，文件夹只有空白模板，属证据目录不完整 |

所以你只需要做一件事：**测试后确认三类对象的字段是否够读**。  
不需要你写契约卡、不需要你判 NC 分类、不需要你决定“报告和文件夹谁优先”；这些用报告结论 + 文件夹事实对账即可。

## 10. 条款提示词的证据依赖已加强

文档提示词 V2.2 已落库；条款提示词也已从“只产属性”升级为“属性 + 证据契约”：

- 新增属性 `证据契约 / EvidenceContract`（`cert_clause_attr_def.Id=12`，`ValueType=json`）。
- `clause_attr_gen` 已更新（8,396 字节），要求每条条款输出：
  - `EvidenceType`：record / form / report / list / package / procedure
  - `EvidenceName`：1–4 个期望证据名
  - `MustHaveFields`：3–8 个必备字段
  - `Frequency` / `Coverage` / `Signer`
  - `JudgementRules`：符合/部分/缺失/不适用的事实条件
  - `ReportUse`：sample / coverage / counter / conclusion
- 落库脚本：`scripts/db/fix/20261114_clause_evidence_contract_v2.sql`。

> 验证状态：提示词接口与属性池已确认读到 `EvidenceContract`；3 条试点自动生成被现有“标准包含旧条款标识”校验挡住（13485 库内仍有失效重复行），本次未写条款属性。要跑试点，先完成条款切换/去重。

这样条款侧不再只回答“这条款管什么”，而是回答“这条款期望什么证据、证据必须有什么、报告怎么用”。

以 `8.2.6` 为例，条款侧期望的证据契约是：

```json
{
  "EvidenceType": ["record", "form"],
  "EvidenceName": ["过程检验记录", "成品检验记录", "产品放行审核记录"],
  "MustHaveFields": ["产品名称", "规格型号", "生产批号", "数量", "检验项目", "检验结果", "检验员", "日期", "放行人"],
  "Frequency": "每批",
  "Coverage": "全产品/全批次",
  "Signer": ["检验员", "放行人"],
  "JudgementRules": [
    "有已填记录 + 接收准则 + 检验结果 + 放行人 = 符合",
    "缺放行人/日期/检测设备 = 部分",
    "只有空白模板 = 缺失",
    "产品/型号与范围不符 = 不适用"
  ],
  "ReportUse": ["sample", "coverage", "counter"]
}
```

对账时就把这份契约、`QR-027/037/028/038` 的实际事实、报告 8.2.6 的结论三列并排看，不再让你拍板。
