# 条款两族 · 文档两层 · 条款内容灌入 V1

> **修订（2026-11-10，依据你的四点确认）**
> 1. **端边界**：属性池、动作词词典、过程→条款映射表、提示词模板全部属**后台管理端**，是系统核心资产，**不暴露给专家端**；专家端只消费结果。
> 2. **手册按真实审核证据的写法提取**：只取「引用三要素」（文件名 + 章节 + ≤60 字要点），不做全文提取。
> 3. **抽查份数先写死**（默认 3 份），未来再参数化。
> 4. **属性不强制全量**：适用才提取，不适用的标 `N/A`，不硬填（见 §二）。

> 承接 14 号（角色）与 15 号（三者关系），补三块：①条款分两族，②每个条款**属性全提**，③证据生成时**灌入条款内容**并从文档里取事实；④文档结构分两层（通用六字段 + 手册条款数组）。

## 一、条款分两族：制度族 F1 / 执行族 F2

你说的两类，本质是"这条要的是**说法**还是**做法**"。

| 族 | 一句话 | 证据从哪来 | 段落长什么样 | 典型条款 |
|---|---|---|---|---|
| **F1 制度族** | 企业**规定了什么**：方针、职责、制度、过程、资源安排 | 手册、程序文件、制度、职责文件、目标表 | 引用文件 + 概括其规定 + 一句结论 | 4.x 情境、5.x 领导、6.x 策划、7.1–7.5 支持类、8.1 运行策划 |
| **F2 执行族** | 企业**实际做了什么**：执行、检查、处置、改进 | 记录、台账、检验单、内审报告、纠正措施单、现场 | 抽样（时间/编号/数量）+ 结果 + 判定 | 8.2–8.7 运行、9.x 绩效、10.x 改进；13485 的 7.5 生产、8.x |

**注意：族 ≠ 角色，族 ≠ 证据形态。** 三者是三个不同维度：

| 维度 | 回答 | 取值 |
|---|---|---|
| 角色 R1–R7 | 这段**回答什么问题**（功能） | 情境/领导/策划/支持/运行/绩效/改进 |
| 族 F1/F2 | 事实**从哪类来源取** | 制度文档 / 记录实例 |
| 形态 A–F | **怎么落笔** | 原文引用/元数据/条目/字段/结论/现场 |

组合起来就是一个格：`R5 · F2 · D`（运行—执行—记录型）。提示词按格取骨架。

### 1.1 族怎么判：看动作词，不看章号

| 判据（条款原文里的动词） | 归族 |
|---|---|
| 建立、形成文件、保持成文信息、规定、明确、确定、确保、策划、配备、提供 | **F1** |
| 实施、运行、执行、监视、测量、检验、放行、处置、纠正、改进、抽查、记录（作为动作） | **F2** |
| 两类都出现（如"建立并实施"） | **F1 主 + F2 必附实例**（记为 F1F2） |

**为什么不能按章号判（实测负结果）**：按"4/5/6 章→F1，其余→F2"粗分，两份数据是

| 族 | 块 | 引《》 | 引制度文件 | 引记录表单 | 抽样动词 |
|---|---:|---:|---:|---:|---:|
| F1 制度 | 56 | 55% | 41% | 30% | 36% |
| F2 执行 | 45 | 76% | 69% | 36% | 29% |

**方向不稳**：执行族的引用率反而更高（因为运行段大量引用《记录名》），抽样率反而更低。说明**章号不等于族**——QES 的 8.2–8.7 里既有过程规定（F1）也有记录实例（F2），13485 的 7.5 同理。

结论：族必须由**条款原文的动作词**判，判完写进属性 `EvidenceFamily`。这也直接支撑你第 3 点——不灌条款内容，族就判不准。

## 二、属性按适用提取，不适用的标 N/A

属性不追求「条条都填满」。**先判适用，再提取**：不适用的属性一律写 `N/A`，不许硬编一个值凑数——硬填出来的属性会把提示词带偏，比留空更糟。

实测常挂不上的三类：

| 属性 | 常见挂不上的情形 | 处理 |
|---|---|---|
| `ApplicabilityCondition` | 条款本身无「适当时/必要时」限定 | `N/A` |
| `Severity` | 符合类条款、且报告不评严重度 | `N/A`（只在不合格分支用） |
| `MergeHint` | 单标准认证（不涉及同号不同义） | `N/A` |

属性不是「描述」，是**提示词的约束参数**：

| 属性 | 约束提示词里的什么 | 缺了会怎样 |
|---|---|---|
| `ClauseIntent` 意图 | 这段要证明的那件事 | 段落跑题 |
| `Obligation` 义务强度 | 结论强度（应→符合；宜→建议；可→可考虑） | 全部写成"符合"，把"宜"也判死 |
| `Applicability` / `Condition` | 先判适不适用 | 不适用条款被强行生成证据 |
| `Process` 过程域 | 去哪些部门/文档取数 | 取错部门，段落与部门无关 |
| `EvidenceFamily` 族（新） | 取制度文档还是记录实例 | 该抽样的写成引用，或反之 |
| `EvidenceForm` 形态 A–F | 句式族与篇幅 | 手册类写成抽样口吻 |
| `Role` 角色 R1–R7 | 骨架（槽位顺序） | 结构混乱 |
| `Severity` 严重度 | 只用于不符合分支 | 符合段不受影响，可后置 |
| `ClauseText` 条款内容（用时关联） | 灌入原文与检索线索 | 见 §三 |
| `AuditQuestion` 待答问题 | 骨架的槽位清单 | 漏答要点 |
| `MergeHint` 提示（非规则） | 仅提示"勿与某标准同号混写" | 不参与决策 |

**缺省规则**：某一属性确实判不出时，**不许留空**，用同角色同族的众数值兜底，并写 `confidence=low`。留空会让提示词静默退化（表现为段落很短、全是套话），且不报错。

## 三、条款内容灌入：三件套 + 检索线索

这是你第 3 点的核心：写执行类证据时，光有属性不够，必须把**条款内容本身**喂进去，并从里面抽"去哪找什么"。

### 3.1 灌入三件套

| 件 | 内容 | 长度 | 用途 |
|---|---|---|---|
| ① 条款原文 | 该条款正文（不含 a/b/c 细分） | ≤300 字，超出截取首段 + 关键词所在句 | 让模型知道"要求的确切边界" |
| ② 检索线索 | 从原文抽出的：对象名词 / 动作动词 / 限定条件 | 各 3–8 个 | 去 L2 事实条目里匹配 |
| ③ 属性约束 | §二 的 11 条 | — | 定骨架、句式、结论强度 |

### 3.2 线索抽取规则（属于 L3，不进属性）

| 类型 | 抽法 | 例（8.5.1 生产提供） |
|---|---|---|
| 对象名词 | 去掉"组织/应/确保"等后保留的实体名词 | 生产、标识、可追溯性、顾客财产、产品防护 |
| 动作动词 | 原文动词原形 | 实施、控制、标识、保存、放行 |
| 限定条件 | "适当时""必要时""形成文件的程度" | 适当时、必要时、成文信息 |
| 排除词 | 组织、应、应确保、其、该、相关、有关 | — |

**用途**：线索去匹配 L2 事实条目的 `what/who/tag` 字段，命中即进候选集；命中数 < 2 时降级为"按 `Process` 取该类文档的摘要"。

这条路径能把"条款说的事"和"文档里的事"对上，而不是靠模型凭印象联想。

## 四、文档结构分两层

你说的"每个文档至少有基本作用、是否和标准有关、能否提取重要信息、符合什么标准、核心内容，然后手册单独一个条款数组"——就按这个分两层。

### 4.1 第一层：所有文档（6 个字段，一次调用）

| 字段 | 说明 | 示例 |
|---|---|---|
| `basic_purpose` 基本作用 | 一句话 | "规定采购过程的责任分工与供方评价方法" |
| `clause_related` 是否与标准有关 | 布尔 | 小孩作业 → false，直接出局 |
| `extract_need` 是否可提取重要信息 | 布尔（目录相关但提不出内容时为 false） | 空白模板 → false |
| `standards` 符合哪些标准 | 多值（9001/24001/45001/42061） | ["9001","24001"] |
| `core_content` 核心内容 | ≤200 字摘要 + 3–8 条事实条目 | "2026 年向 3 家供方采购水泥，合同期 1 年…" |
| `trace` 出处与置信度 | 页码/锚点 + confidence | P12 / 0.86 |

### 4.2 第二层：仅"体系类文件"（手册/体系汇编），一条款一条

| 字段 | 说明 |
|---|---|
| `clause` | 条款号（来自目录或正文标题） |
| `excerpt` | **引用式摘录**（≤60 字要点）：只保留「规定了什么」，不抄正文 |
| `page` | 页码（供报告脚注与回溯） |

**触发条件**：`doc_category = 手册` 或 `目录中出现的条款号 ≥ 10 条`。满足才建条款数组，否则只做第一层。

**手册的提取口径（重要）**：手册很厚很复杂，但外审时**只做简单引用**——「《XX 手册》第 X 章规定……」。所以条款数组里不存全文、不存长摘录，只存「一句话要点 + 章节号」，供 F1 骨架的【引用】槽位直接用。

**为什么只有手册走数组**：
- 手册天然按条款编排，"条款→内容"是它本来的结构，抽出来几乎不失真；
- 手册是 F1 制度族最主要的证据源，条款数组能直接供 F1 使用，不需要再检索；
- 其他文档（记录/台账/合同）按条款拆会退化成"每文档×每标准×每条款"，200 份 × 3 标准 × 逐条款 = 600 次以上，收益极低。

### 4.3 两层对提示词的供数方式

| 文档类型 | 第一层 | 第二层 | 供 F1（制度族） | 供 F2（执行族） |
|---|:--:|:--:|---|---|
| 质量手册 | 必做 | **必做** | ✅ 直接按条款取 excerpt | 少（手册不写实例） |
| 程序文件/制度 | 必做 | 可选（目录含条款号时） | ✅ 按 core_content | 少 |
| 记录/台账/表单 | 必做 | 不做 | 少 | ✅ 按 core_content 的事实条目 |
| 合同/订单 | 必做 | 不做 | 少 | ✅ 按事实条目（供方/数量/期限） |
| 资质/证书 | 必做 | 不做 | ✅ 供 R1 范围与许可 | 少 |
| 内审/管评报告 | 必做 | 不做 | 少 | ✅ 供 R6 |

## 五、端边界：后台管理端是核心，专家端只消费

| 资产 | 归属 | 专家端能否看到 |
|---|---|---|
| 条款属性池（11 属性 + 动作词词典） | 后台管理端 | 只见结果，不见维护界面 |
| 过程→条款映射表 `process_clause_map` | 后台管理端 | 只见「该条款有哪些文档可查」 |
| 提示词骨架 / 机构风格包 | 后台管理端 | 不暴露 |
| 文档画像与提取结果 | 后台跑队列 | 可见（这是审核员的工作对象） |
| 审核证据建议稿 | 专家端 | 可见、可改、可锁定 |

理由：映射表与骨架一旦暴露，机构会各自改一套，版本立刻失控；而画像与证据稿本来就是审核员天天看的东西。

## 六、两族各自的写作骨架（可直接写进第 3 类提示词）

**F1 制度族骨架（引用 + 概括 + 结论）**

```
【引用】组织《XX 手册》第 N 章 /《XX 程序》第 N 条规定：<摘录 ≤60 字>
【事实】该文件明确了 <对象> 的 <职责/方法/频次/记录要求>
【结论】符合 GB/T XXXXX 第 X.X 条 <要求要点> 的规定。
```

**F2 执行族骨架（抽样 + 结果 + 判定）**

```
【抽样】抽查 <期间> 的 <记录名> 3 份（编号 ___ 至 ___），涉及 <部门/产品/批次>
【结果】记录显示：<时间> 对 <对象> 实施了 <动作>，结果为 <数据/结论>；其中 <N> 份 <缺项/异常>
【判定】符合/基本符合 GB/T XXXXX 第 X.X 条要求（不适用的部分说明理由）。
```

**抽查份数**：本期固定 3 份（写死在骨架里），未来再做成机构参数。

**F1F2 混合（「建立并实施」类）**：先 F1 一段（有制度），再 F2 一段（有实例）。两段共用同一检查项，不拆成两个检查项。

## 七、这套结构下提示词的数量

| 组成 | 数量 | 是否随机构变 |
|---|---:|---|
| 角色 × 族 = 骨架 | 7 × 2 ≈ 12–14（含 F1F2 混合） | 否 |
| 形态变体（同骨架的 2–3 种口吻） | × 2–3 | 否 |
| 机构风格包 | 1 套/机构 | **是** |
| 条款内容灌入 | 动态（每条款不同） | 否 |

即：**骨架 24–42 条（一次性写完，跨标准复用）+ 每家机构 1 个风格包**。换标准不新增骨架，只重跑属性与内容灌入。

## 八、与旧设计的差异

| 项 | 旧（08 号） | 新（本文） |
|---|---|---|
| 文档提取 | 六型逐文档跑，手册也按六型 | **手册走条款数组，其他走 6 字段** |
| 条款分族 | 无（只按章号统计写法） | **F1/F2 按动作词判** |
| 条款内容 | 只在属性里存"意图" | **原文 + 检索线索 + 属性三件套灌入** |
| 调用量 | 200 份 × 3 标准 ≈ 600+ | 200 次画像 + 手册条款数组（每手册 1 次批量）≈ **210–230 次** |
| 属性 | 允许留空 | **全量提取，缺省兜底并标低置信** |
