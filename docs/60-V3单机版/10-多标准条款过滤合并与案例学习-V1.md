# 多标准条款过滤、合并与案例学习：设计 V1

> 回答三件事：①要不要依赖机构的"要求"列；②多标准合并前怎么按标准筛条款；③能不能让模型从大量真实案例里学习并优化提示词。

---

## 一、不依赖"要求"列：用条款骨架，机构列后置

ACM 的表格是四列：`Clause 条款 | Requirements 要求 | Audit Evidence 审核证据 | NC/OFI`。别家机构往往没有"要求"列，只有"检查项/条款 + 审核记录"。

**结论：系统的骨架只认"条款 + 部门 + 事实"，不认机构的"要求"列。**

| 列 | 归谁 | 是否必需 |
|---|---|---|
| Clause 条款 | **数据层**（标准 + 条款号） | 必需，唯一主键的一部分 |
| Requirements 要求 | **风格层**（可选输出） | 非必需；有则复用，无则按条款原文回填 |
| Audit Evidence 审核证据 | 数据层产物 | 必需 |
| NC/OFI | 人工判定 | 必需（但由人填） |

这样带来两个好处：

1. 换机构时表格结构变化不影响数据模型（只是排版不同）；
2. 生成时不需要模型去"理解要求列"——直接用条款原文（`ClauseText`），更通用也更准。

**"要求"列的两种用法**（按机构配置）：

| 机构情况 | 做法 |
|---|---|
| 报告有要求列（ACM） | 复用其 `AuditQuestion`（问句版），直接输出 |
| 报告无要求列 | 只输出条款号 + 证据；或按标准原文回填 |

## 二、多标准合并前，必须先按标准筛条款

### 2.1 问题在哪

三标准同属 Annex SL，条款号大体对齐，但**同号不等于同义**。直接按条款号合并会出三类错误：

| 错法 | 后果 |
|---|---|
| 按号合并所有 4.1 | 三个标准 4.1 都是"理解组织及其环境"，勉强可合，但侧重点被抹平 |
| 按号合并 6.1.2 | 9001=风险和机遇措施、24001=环境因素、45001=危险源辨识 → **彻底串义** |
| 按号合并 8.2 / 9.1.2 | 9001 是"产品和服务要求""顾客满意"，24001/45001 是"应急准备""合规性评价" → **文不对题** |

### 2.2 关系只有三种（QES 4–10 章对齐表）

**A 类 · 同号同义（可合并）**

| 条款 | 9001 | 24001 | 45001 |
|---|---|---|---|
| 4.1 | 理解组织及其环境 | 同 | 同 |
| 4.2 | 理解相关方需求和期望 | 同 | 同 |
| 4.3 | 确定体系范围 | 同 | 同 |
| 4.4 | 体系及其过程 | 同 | 同 |
| 5.1 | 领导作用与承诺 | 同 | 同 |
| 5.2 | 方针 | 环境方针 | 职业健康安全方针（名称不同，结构同） |
| 5.3 | 岗位、职责和权限 | 同 | 同 |
| 6.1.1 | 应对风险机遇·总则 | 同 | 同 |
| 6.2.1 / 6.2.2 | 目标及其实现策划 | 同 | 同 |
| 7.2 / 7.3 | 能力 / 意识 | 同 | 同 |
| 9.2 | 内部审核 | 同 | 同 |
| 9.3 | 管理评审 | 同 | 同 |
| 10.1 | 总则 | 同 | 同 |
| 10.3 | 持续改进 | 同 | 同 |

**B 类 · 同号不同义（禁止按号合并，必须分标准生成）**

| 条款 | 9001 | 24001 | 45001 |
|---|---|---|---|
| **6.1.2** | 应对风险和机遇的策划 | **环境因素** | **危险源辨识及风险和机遇的评价** |
| **8.2** | **产品和服务的要求**（8.2.1 顾客沟通…） | **应急准备和响应** | **应急准备和响应** |
| **9.1.2** | **顾客满意** | **合规性评价** | **合规性评价** |
| 6.1.3 | — | 合规义务 | 法律法规要求和其他要求的确定（近义，可合） |
| 6.1.4 | — | 措施的策划 | 措施的策划（同义） |
| 5.4 | — | — | 工作人员的协商和参与（仅 45001） |
| 8.1.2 / 8.1.3 | — | — | 消除危险源降低风险 / 变更管理（仅 45001） |

**C 类 · 跨号对应（不合并，只做交叉引用）**

| 9001 | 24001 / 45001 | 说明 |
|---|---|---|
| 7.1.5 监视和测量资源（7.1.5.1 总则 / 7.1.5.2 测量溯源） | 9.1.1 监视、测量、分析和评价·总则 | 同内容不同位置，不能按号对齐 |
| 8.4 外部提供的过程、产品和服务 | 24001 8.1 / 45001 8.1.4（8.1.4.1 总则、8.1.4.2 承包方、8.1.4.3 外包） | 采购与外包分散在不同号 |
| 8.5 生产和服务提供 | 24001 8.1 / 45001 8.1.2 + 8.1.3 | 运行控制的三种切法 |
| 8.7 不合格输出的控制 | 10.2 不符合和纠正措施 | 9001 在运行章，环境/职安在改进章 |
| 10.2 不合格与纠正措施 | 45001 10.2 事件、不符合和纠正措施 | 45001 多了"事件" |

> 该表是合并逻辑的唯一依据。C 类里 9001 8.7 与 10.2 的关系尤其要注意：同一件事在两个标准的不同章节，若按号合并会把"不合格输出"和"纠正措施"混成一条。

### 2.3 过滤 + 合并算法

```
输入：已选标准集 S（如 9001+24001+45001）、任务覆盖的条款集 C、部门 D

第一步 按标准筛（这一步就是你说的"过滤"）
  for s in S:
      clauses[s] = 该标准下本次要审的条款集合（按任务计划取，不是全标准）
      去掉该标准不适用的（如 24001 没有 8.3 设计开发）

第二步 按号分组
  for code in union(clauses[s]):
      group[code] = { s: clause for s in S if code in clauses[s] }

第三步 判可合并性（查对齐表）
  if group 内所有条款都属 A 类 → 可合并，标记 merge=by_clause
  if 含 B 类条款            → 不可按号合并，标记 merge=by_standard（分标准各写一段）
  if 只有单一标准命中       → 不涉及合并，直接生成

第四步 生成
  merge=by_clause：一次生成一段，事实取并集，口径取最严，末尾加括注（含环境因素/含危险源）
  merge=by_standard：每个标准各生成一段，不互相引用，避免串义

第五步 部门维度（绝不合并）
  每个 (条款组, 部门) 独立成段，即使同一条款在多部门出现
```

**关键：第三步的对齐表必须是"数据"，不能靠模型判断。** 模型对 6.1.2 这种同号不同义的分辨不可靠，实测它在没有原文时会按标题猜。

### 2.4 落到库里

| 表/字段 | 作用 |
|---|---|
| `ClauseAlign` | `ClauseCode` + `StandardCode` + `AlignType`（A_same / B_diff / C_cross）+ `CrossRefClauses[]` + `Note` |
| `EvidenceUnit` | `UnitCode` + `DeptCode` + `MergeMode`（by_clause / by_standard） |
| `UnitClauseRel` | 单元与（标准, 条款）的多对多关系 |

`ClauseAlign` 是新增表，约 60–80 行（QES 三个标准的 4–10 章），一次性建好，之后只随标准换版维护。

## 三、案例学习：适合，但不是"训练模型"

### 3.1 先说结论

**适合用案例驱动，但不适合微调模型。** 应该做的是"**案例库 + 检索示例 + 回归评分 + 提示词版本化**"。

### 3.2 为什么不做微调

| 原因 | 说明 |
|---|---|
| 数据量不够 | 现有 1,528 句、3 家企业，远低于微调所需规模，只会过拟合这三家企业的写法 |
| 换机构即失效 | 微调学到的是"ACM 的写法"，换一家机构要重训；而机构风格应该做成配置，不是权重 |
| 不可解释、不可回滚 | 输出变差时无法定位是哪句话教坏了模型；提示词可以逐条改、逐版回滚 |
| 迭代太慢 | 微调一轮以天/周计；提示词改一条当天就能回归验证 |

### 3.3 应该怎么做（四步）

**第一步：建案例库**

把 ACM 报告逐句拆成"可复用示例"，一条记录包含：

| 字段 | 例 |
|---|---|
| `ClauseCode` / `StandardCode` | 8.5.1 / 9001 |
| `DeptCode` / `ProcessDomain` | 生产部 / production |
| `EvidenceForm` | D 记录型 |
| `SourceDocTypes` | 生产记录、工艺卡 |
| `SentenceTemplate` | "{部门}按《{文件}》实施{活动}，抽看{数量}份记录，{项目}符合要求" |
| `SlotExamples` | 文件=生产控制程序、活动=首件检验… |
| `FactPoints` | 日期、数量、编号（用于校验"事实是否可溯源"） |
| `Length` / `Tone` | 26 字 / 陈述 |

**第二步：生成时检索示例（few-shot）**

```
按 (ClauseCode, DeptCode, EvidenceForm) 检索 3–5 条最相似示例
→ 注入提示词的"参考写法"区（不是指令区）
→ 明示"只学句式结构，不得复用示例中的企业名、数字、文件名"
```

这解决了"模型不知道 ACM 该怎么写"的问题，且换机构只需换示例库。

**第三步：回归评分（每次改提示词必跑）**

| 指标 | 算法 | 门槛 |
|---|---|---|
| 事实可溯源率 | 生成句里的事实点能否在企业文档中找到 | ≥ 95% |
| 句式合规率 | 是否符合该型的槽位结构 | ≥ 90% |
| 与真实报告相似度 | 与同条款同部门的真实句子做 n-gram 相似度 | 中位数 ≥ 0.55 |
| 编造率 | 出现文档中不存在的事实 | **必须为 0** |

用现有三套资料做固定测试集，改一版跑一遍，四指标不过线不上线。

**第四步：提示词版本化**

| 对象 | 版本化方式 |
|---|---|
| 提示词模板 | 每次改动存新版本号，记录改动点与回归结果 |
| 示例库 | 快照存版本，与提示词版本绑定 |
| 机构风格包 | 单独版本，可整包切换 |

### 3.4 可以再加一层"自动归纳"（人审后入库）

定期用模型对新增报告做归纳：从新句子里提炼"新句式 / 新槽位 / 新结论词"，输出候选清单，**由人确认后**才进示例库和模板库。这样案例越多，模板越准，但不会失控。
