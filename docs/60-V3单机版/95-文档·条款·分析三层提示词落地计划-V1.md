# 95 · 文档 · 条款 · 分析 三层提示词落地计划（V1）

> 本计划按**用户修正后的三层职责**重排，不沿用 89 号"文档 / 条款 / 认证"的旧命名与旧边界。
> 全部结论以实库核对为准（附录 B），不采信文档自述的落地状态。

## 零、与 93 号计划的关系（先看这张表）

| 项 | 93 号计划 | 本计划（95） |
|---|---|---|
| 第三层叫什么 | 认证提示词 / 审核证据提示词（`audit_check_evidence`） | **分析提示词**（`analysis_bundle`），职责 = "聚合 + 分类输出（发现/疑点/证据）+ 按部门组织" |
| 第三层输入 | 检查项 + Findings + Doubts + Assembly | **认证计划（`cert_audit_plan` + 56 项明细）+ 全量 Findings/Doubts + 文档事实 + 现场事实** |
| 第三层输出 | 审核证据 + 结论（含 NC） | **只有三类：审核发现（原样）/ 疑点 / 审核证据（按符合撰写）；⛔ 无 NC**（见 §1.2 铁律 R-C） |
| 谁决定检查项怎么组织 | 未定义（默认沿用计划明细） | **明确：组织权归认证计划，文档层与条款层不得产出检查项** |
| 谁决定条款如何合并、部门如何归属 | 未定义 | **明确：部门归属用计划里的部门组合；分析层一条款一段（R-D），父段合并只在报告装配阶段按 `cert_report_clause_map` 做；两者都不得由模型自创** |
| 文档层是否逐条款 | "只有手册逐条款"（64 号口径） | **只留 手册 / 方针（必要时加程序文件的"引用条款"），其余一律不逐条款** |
| 条款层定位 | 证据发现 + 疑点 + 组合 | 同（不变），但**明确它不是"审核证据"**，只交"可核对的事实 + 疑点 + 取数路径" |
| 推进顺序 | DocFact → Findings → 3 条证据 → 模型路由 → 成本 | 同五步，但**先补 P0 契约与数据源**，再进运行时，最后才做分析层 |

**一句话差异**：93 号把第三层当"写报告的提示词"；本计划把它当**唯一的汇总器**——只有它能拿到认证计划，也只有它能决定"哪个部门、哪几条条款、哪几段证据、疑点合并成几条"。

## 一、起点：审核证据的可得性边界

用户前提（本计划的第一性约束）：**审核证据里有很多信息无法从企业文档获得。**

因此三层的目标不是"从文档推出结论"，而是：

| 要达成 | 靠谁 | 不靠谁 |
|---|---|---|
| 深刻理解条款要求 | 条款属性池（9 属性，2,160 行已就位）+ 条款正文 + 章节画像 | 文档提取（文档不知道条款要什么） |
| 把证据收准 | 条款层给出"该找什么文档、哪一类、什么形态（filled / template_only / 程序）" | 文档层（文档只描述自己是什么） |
| 尽量完整 | 分析层用认证计划做覆盖清单，逐部门逐条款点检缺口 | 单份文档（看不到全局） |
| 事实清楚 | 三层共同：原文优先 + 位置可查 + 不推断 | 任何一层自造事实 |

### 1.1 事实三分（分析层必须区分，且只允许前两类进证据）

| 类别 | 来源 | 能写成什么 | 不能写成什么 |
|---|---|---|---|
| **文档事实** | `cert_doc_fact` + `cert_document_extraction` 原文摘录 + `cert_establish_detail.Anchor` | "查阅《X》（编号/版本/日期）：记载……" | "已有效执行 / 已持续运行"（记录为 `template_only` 时） |
| **现场事实** | `cert_onsite_plan_item` + `cert_evidence`（面谈/观察/抽样） | "与某岗位面谈：……；现场观察：……" | 未发生的事实（当前 `cert_evidence` 实为 0 行） |
| **报告事实**（`report_only`） | 上一轮报告 / 企业自评报告 | "报告汇总为 X，原始记录为 Y，需核实" | 倒推"每份原始记录都存在"；不得回填文档事实 |

### 1.2 四条铁律（2026-11-16 用户口径，**违反即返工**）

> 这四条不是"建议"，是**输出契约与验收判据**。前三条决定"能写什么"，第四条决定"先做什么"。

| # | 铁律 | 具体含义 | 机械判据（可写成守卫） |
|---|---|---|---|
| **R-A** | **只提取当前企业文档的事实** | 文档写了就原样写；文档**没写**就只写"该企业建立了《XXX》记录"，⛔ 不写"未执行 / 未提供 / 缺失"这类评价 | 输出中不得出现"未提供/未执行/未见/没有"等否定判断（`OnsiteTodo` 除外，且必须写成"需现场核实"） |
| **R-B** | **输出只有三类** | ① **审核发现**：文档里有什么（原样、带定位、与机构无关）② **疑点**：记录存在但为空 / 关键字段缺 / 跨文档对不上（只提醒审核员，与机构无关）③ **审核证据**：**按全部符合撰写** | 每条发现必须有 `DocName + 定位`；每条疑点必须有 `DoubtType + 事实依据`；证据段落不得出现"不符合" |
| **R-C** | **不符合项只能由审核员现场确定** | 文档缺失 ⇒ 只进**疑点**；跨文档冲突 ⇒ 只进**疑点**。⛔ 任何层都不得输出 `NC` / `NcCandidate` / 严重程度判定 | 全链路 `NcCandidate` 字段数 = 0；输出中"不符合"出现次数 = 0 |
| **R-D** | **一条款一段** | 分析层按**叶子条款**成段（8.4.1 / 8.4.2 / 8.4.3 各一段）；报告父段合并（8.4.1/2/3 → 8.4）只在**报告装配**阶段按 `cert_report_clause_map` 做，分析层不做 | 分析层 `ClauseEvidence` 条数 = 计划叶子条款数；不出现"并入 8.4" |

**为什么证据要"按全部符合撰写"**：真报告 80–90% 是符合项。文档能证明"建立了什么、记录里有什么"，就足以支撑符合段；把"文档没写"当不符合，等于用抽取器的盲区去判企业不合格——这正是 96 号查出的 F9（森木缺评审表）被无根据推断的机制。

**优先级（R-D 之后的第 5 条）**：先让**发现**与**疑点**事实清楚，再审"证据如何组织"。证据段落先求"可回溯"，不求"写得好"。

## 二、三层职责（修正版，唯一权威）

| 层 | 一句话职责 | 输入 | 输出 | 明确不做 |
|---|---|---|---|---|
| **① 文档提示词** | 说明**这份文档是什么、装了什么、空到什么程度** | 单份文档 Markdown + 文件名 + 目录 | `DocFact`：分类、用途、核心信息、填写状态、样例行、覆盖 | 不判条款符合性；不判"是否满足某条款"；不产出检查项；不做部门归属裁决；⛔ 不写疑点（疑点只在条款层/分析层） |
| **② 条款提示词** | 说明**这条条款要什么证据、企业文档里有什么、疑点在哪、怎么组合** | 条款正文 + 9 属性 + 章节画像 + 允许引用条款 + 相关 `DocFact` + 原文摘录 | `ClauseContext` / `EvidenceContract` / `EvidenceFindings` / `Doubts` / `EvidenceAssembly` / `ReportHint` | 不写"符合/不符合"；⛔ 不写 NC / 严重程度；**不合并条款**（R-D：一条款一段） |
| **③ 分析提示词** | **拿到认证计划，把条款与文档整合成三类输出** | 认证计划 + 部门 + 计划内条款分组 + 该组全部 Findings/Doubts/Assembly + 文档事实清单 + 现场事实 | `AnalysisBundle`：**审核发现**（原样+定位）／**疑点**（归一+建议核实）／**审核证据**（一条款一段、按符合撰写）／覆盖与缺口／待现场核实清单 | 不重读原始文档；不新增事实；不改计划条款分组；不发明部门；⛔ 不产 NC |

### 2.1 为什么必须切成这样（对应三条现实缺口）

| 缺口 | 表现（实库/实测） | 由哪一层补 |
|---|---|---|
| 文档提取规则不知道"检查项怎么组织" | 现网 `doc_clause_extract` 在内审检查表上自造编号，三份分别丢弃 3/4/4 条 | **不是文档层的问题**：检查项由 `cert_audit_plan_detail`（56 项）定义，文档层只提供事实 |
| 条款不知道"条款如何合并、部门如何组织" | `cert_audit_plan_detail.DeptNames` 有 16 种组合（管理层 16、综合部 8、跨 5 部门 2 ……） | **分析层**：按计划的部门组合输出，跨部门事实只详述一次 |
| 单条条款看不到全局 | 8.2.4 审核员名单冲突只在"计划/检查表/报告"三方比对时暴露 | **分析层**：跨条款、跨文档、跨部门比对 |

## 三、层 ① 文档提示词

### 3.1 契约（在 v5.3.1 基础上扩 4 项，其余不动）

现网 shadow `doc_fact` v5.3.1 只有 6 键（2,027 字节）。**缺 4 项导致下游无法路由**：

| 新增/保留 | 字段 | 取值 | 用途 | 缺失后果 |
|---|---|---|---|---|
| 新增 | `StandardRelevant` | `true / false` | 是否进条款层 | 33% 无关文档（财务制度、考勤制度）会进条款链，白烧 token |
| 新增 | `Extractable` | `true / false` | 内容是否可用（只有封面/目录/签收页 ⇒ false） | 空壳文档占用证据位 |
| 新增 | `DocCodeVer` | `{Code, Version, EffectiveDate}` | 报告要写"编号/版本/日期" | 证据段落写不出可核对的标识 |
| 新增 | `PrimaryClauses` | `[]`，≤3 | **仅检索提示**（不是结论） | 条款层无法按条款召回记录类文档 |
| 保留 | `DocClass` | 8 值（见下） | 决定取数路径与写法 | — |
| 保留 | `CoreRole` / `KeyFields` | 自由文本 / 数组 | 报告叙述素材 | — |
| 保留 | `FillStatus` | 6 态 | 决定能不能写"已执行" | — |
| 保留 | `SampleRows` | ≤3 行 | 报告"抽样到了什么" | — |
| 保留 | `Coverage` | `全量/抽样/无实例` | 覆盖度 | — |

### 3.2 `DocClass` 8 类 ↔ 现网 `DocType` 12 类 的映射（必须落成代码常量）

| 现网 DocType | `DocClass` | 取数路径 |
|---|---|---|
| `manual` | `manual` | **逐条款**（唯一需要条款级抽取的纲领文件之一） |
| `policy` | `policy` | **逐条款**（方针，逐条对应承诺） |
| `procedure` | `procedure` | 整份结构化（目的/范围/职责/要点/相关表单），**不逐条款**；仅抽"引用条款" |
| `work_instruction` | `work_instruction` | 整份判据（检验项目/验收标准/抽样判定） |
| `record` / `audit_record` / `review_record` | `record` | 记录事实（状态 + 样例行） |
| `context_list` / `index` / `document_control` | `list` | 清单事实（条目数 + 缺项 + 保留期字段） |
| `other` | `plan`（若内容是计划/方案）否则 `report` | 按内容判 |
| `irrelevant` | 不调用条款层 | — |

> ⚠️ 该映射是**本计划的硬约束**：`DocClass` 是 8 值，不能再扩；12 类的差异在映射表里消化，不回到提示词里加枚举。

### 3.3 逐条款抽取的唯一适用面（收敛，不再对全部文档跑）

| 文档 | 逐条款抽取 | 理由 | 现网实测 |
|---|---|---|---|
| 管理手册 | ✅ | 手册按条款编号组织，是"体系覆盖面"的唯一自述 | 59 条，但 **71 条摘录无法唯一匹配** |
| 方针 | ✅ | 逐条承诺对应 5.2 / 5.3 | — |
| 程序文件 | ⚠️ 只抽"引用条款"字段 | 程序只在报告里被点名证明"有规定"（24/33） | — |
| 记录 / 清单 / 内审检查表 | ❌ | 记录不按条款组织；强抽 ⇒ 自造编号 | 三份内审检查表丢弃 3/4/4 条，2 份产出 0 条 |
| 财务/考勤等无关文档 | ❌ | `StandardRelevant=false` | 2 份被 `ExtractionMode=none` 跳过 |

**结论**：现网 `doc_clause_extract` 跑在 12 份文档上，其中**只有 1 份（手册）该跑**。这是"自造编号"与"0 条款"的根因，不是提示词质量。

### 3.4 检索提示（解决"记录不按条款组织、条款层找不到记录"）

文档层给 `PrimaryClauses ≤3` 只是**提示**，条款层取数走四路，按优先级：

| 路 | 依据 | 适用 |
|---|---|---|
| R1 条款号直连 | `PrimaryClauses` / 手册逐条款锚点 | 手册、方针 |
| R2 过程域 + 部门 | `ProcessArea` + `OwnerDept` ↔ 计划明细的 `DeptNames` | 程序、指导书 |
| R3 文档类型 | `EvidenceItem.DocClass` | 记录、清单（记录类主要靠这条） |
| R4 名称别名 | `DocClassName` 与文件名/表单名匹配 | 表单类（"纠正措施处理单" ↔ `QR-008`） |

> 判定口诀：**R1 命中即可引用；R2/R3/R4 命中只算"候选"，必须给出原文摘录才算证据。**

## 四、层 ② 条款提示词

### 4.1 定位（本次最重要的纠正）

> 条款提示词**不生成最终审核证据**。它的产物是"**可核对的原料**"：这条条款要什么、文档里有什么原文、哪里可疑、几份文档怎么拼。

| 能做 | 不能做 |
|---|---|
| 说清"这条条款需要哪几类文档、什么形态、覆盖几次" | 写"符合/不符合" |
| 引用文档原文（≤200 字，需可回定位） | 写 NC / 严重程度 |
| 列疑点（10 类，可机械校验） | 合并条款、合并部门（分析层的事） |
| 给出证据组合（几份、什么角色、能否成立） | 定义检查项 |

### 4.2 输入 6 项（93 号 §7.1 已列，此处定稿）

| 变量 | 来源 | 现状 |
|---|---|---|
| `clause_number` / `clause_title` / `clause_content` | `cert_iso_clause` | ✅ 就绪 |
| `chapter_profile` | **需新建**：`ChapterProfile`（章节意图 / 章节证据焦点 / 条款在章节中的角色 / 章节缺口） | ❌ 无表、无代码；86 号只给了 5 个样例 |
| `allowed_clause_refs` | 章节内的条款号集合（防自造编号） | ❌ 无运行期实现（`ClauseRefValidator` 不存在） |
| `referenced_clauses` | `cert_iso_clause` 交叉引用解析 | ❌ 无表（`cert_standard_doc_contract` 不等价） |
| `doc_facts` | `cert_doc_fact`（本计划新建） | ❌ 表不存在 |
| `doc_excerpts` | `cert_document_extraction` 原文摘录 + `Anchor` | ✅ 有数据，但 71 条不可唯一匹配 |

### 4.3 输出（v5.3 冻结，7 块，不再改字段）

`ClauseContext` · `ChapterContext` · `ReferencedAnalysis` · `EvidenceContract` · `EvidenceFindings` · `Doubts` · `EvidenceAssembly` · `ReportHint`

- 冻结理由：93 号实测 v5.3 把问题从 55 降到 29、P0 从 15 降到 7、Assembly 过强从 2 降到 0；v5.3.1 反而 Doubt 8→12、P0 7→9，**不替换**。
- 冻结范围：**只冻结构，不冻文本**。允许的唯一改动是补 6 项入参后的占位符措辞适配，不得新增规则段。
- 体积上限：8–10KB（89 号定的），现 12,388B **超 24%** ⇒ 本轮只减不加，把可机械判定的规则移进校验器。

### 4.4 与旧口径的三处硬切割

| 旧口径 | 新口径 | 理由 |
|---|---|---|
| `doubts` 写在文档提取提示词里 | **删除**，疑点只在条款层产出 | 文档层不该知道条款 |
| 条款层输出"检查结论"（81 号 `AuditEvidence.conclusion`） | **删除** | 结论是分析层+审核员的事 |
| `DocRole`（5 值）与 `DocClass`（8 值）并存 | 只留 `DocClass` | 实测两字段重复，模型两边填不一致 |

## 五、层 ③ 分析提示词（本次新增的核心）

### 5.1 为什么必须由它来做

| 现象 | 单看条款层会怎样 | 分析层才有的能力 |
|---|---|---|
| 16 种部门组合（`管理层,综合部,生产部,品质部,销售部,采购部` 等） | 条款层不知道部门，只能按条款输出 | 拿到 `cert_audit_plan_detail`，按计划部门分组 |
| 同一事实被 3 条条款引用（如《供应商业绩考核评估表》同时支撑 8.4.1/8.5.4/9.1.2） | 每条各写一遍，报告重复 | 跨条款去重，首次详述 + 后续"同上" |
| 疑点重复（"未见 QR-024" 在 8.2.4 与 9.2.2 都出现） | 疑点各写各的，现场核实清单重复 | 疑点归一，一条疑点挂多个条款 |
| 条款需合并（父条款 7.5.1 含 a)–e)、7.3 十条并入父块） | 条款层明确"不合并"；分析层也**不合并**（R-D 一条款一段） | 只在**报告装配**阶段按 `cert_report_clause_map` 合并，见 §8.3 |
| 报告要按"部门 → 条款 → 证据"三段式 | 无部门概念 | 直接产出部门级证据块 |

### 5.2 输入（8 块，唯一能拿到计划的层）

| 块 | 内容 | 来源 |

#### 5.3.1 三类输出的写作规则（可直接当提示词条款）

| 类 | 必须这样写 | ⛔ 禁止这样写 |
|---|---|---|
| **审核发现** | "查阅《合格供应商清单》（KSY-QMS-P-15-02，承认日期 2026.6.10，制表/审核 胥加娟，批准 潘明海）：清单载明 1 家供应商——江阴市金祺达金属制品有限公司，主要产品 316L。" | "清单不完整"；"应有 5 家"；"未覆盖全部采购类别"（评价性/推断性） |
| **审核发现**（文档存在但内容为空，**R-A 的固定句式**） | "该企业建立了《进料检验报告》（KSY-QMS-P-21-01）记录。" —— 只陈述"建立了记录"，具体内容进疑点 | "未提供进料检验记录"；"检验未执行"；"记录缺失"（把空内容说成没做事） |
| **疑点** | "《进料检验报告》（KSY-QMS-P-21-01）2 份记录的"材料名称/供应商/规格型号/供销单号"4 栏均为空，记录日期为 2025-03-19、2025-06-23；建议现场核对该期间进料检验与采购单据的对应关系。" | "进料检验记录造假"；"未按程序执行"；"构成不符合 8.4.2" |
| **审核证据** | "组织编制了《外部提供过程产品服务控制程序》（KSY-QMS-P-15，A/0，2026.6.10 实施），明确采购部为归口管理部门、生产部与品质部参与供方评价；抽查《供应商评审表》1 份，评价结论为'基本符合我公司合格供应商的要求'，经总经理批准。" | "完全符合 8.4.1"；"体系运行有效"；"未发现不符合" |

**R-A 的一句话判据**：**"企业没做"与"我们没读到"是两件事**。文档里没有 ⇒ 只能写"建立了记录"（有记录）或"未查见该记录，需现场核实"（无记录），⛔ 不得写成"企业未执行"。

**证据段的"符合"怎么写才不算杜撰**：只允许写"组织建立了 X（编号/版本/日期）+ 抽查到 Y 条记录（内容/结论/签署）+ 与条款要求的对应面"，⛔ 不写"持续有效 / 全部执行 / 无遗漏"这类无法由单份文档支撑的断言。

### 5.4 与现网 `audit_check` 的差别（必须是不同提示词，不能就地改）

现网 `audit_check`（`wf_prompt_template`，3,848 字节，live，已跑 42 次）输入只有 6 个占位符：`task_kind / check_item_name / dept_names / clause_blocks / onsite_evidence / previous_results`。

| 缺什么 | 后果 |
|---|---|
| 没有 `plan_meta` | 不知道这是第二阶段的认证计划、覆盖 5 个过程域 |
| 没有 `item_scope` | 只看单个检查项，无法判断"本部门还漏了哪些条款" |
| 没有 `findings` / `doubts` 结构 | 只能消费"按条款聚合的原文摘录"（`RenderDocHits`），无法区分 filled / template_only |
| 没有跨项聚合 | 42 次分析各自出结论，重复疑点无归一 |
| 没有部门组织 | `dept_names` 只做展示，输出无部门结构 |

**处置**：保留 `audit_check` 作为 V1 现场检查（不删、不改），新增 `analysis_bundle` 作为第三层；并存期两条并行，`analysis_bundle` 通过验收后由开关切换，符合 AGENTS.md §九"V1 不动、新建并存"。

## 八、聚合、去重、部门组织（分析层的三条算法）

### 8.1 去重键（必须写进代码常量，不能靠模型"注意去重"）

| 对象 | 键 | 冲突处理 |
|---|---|---|
| Finding | `ClauseNumber + ClauseItemRef + DocName + DocLocation + FindingType` 的 SHA256 | 保留 `OriginalQuote` 更长者 |
| 同一事实跨条款 | `DocName + DocLocation`（原文指纹） | 首次详述，后续写"同一记录另见 X.X" |
| Doubt | `DoubtType + 归一化描述（去空白/去标点）+ 关联文档名` | 合并 `ClauseNumbers[]`，取最高 `Confidence` |
| 文档 | `FileCode` | 一份文档多条款引用只列一次 |

### 8.2 部门归属（只用计划的部门，不自创）

| 情形 | 规则 | 实库样例 |
|---|---|---|
| 单部门 | 直接归该部门 | 管理层 16 项、综合部 8 项 |
| 多部门 | **以 `DeptNames` 第一项为主责部门**输出详版；其余部门输出"关联版本"（一段摘要 + 指向主责部门） | `管理层,综合部` 3 项 |
| 全部门（5 部门） | 只输出一次（放主责），其余部门在 `OnsiteTodo` 里保留"共同核实" | `管理层,综合部,生产部,品质部,销售部,采购部` 2 项 |
| 计划无此部门 | **拒绝生成**，写 `Gaps` | — |

### 8.3 条款粒度（**分析层一条款一段；父段合并在报告装配阶段做**）

> ★ 2026-11-16 二次修正（用户口径 R-D）：分析层**不做合并**，按叶子条款成段。
> ★ 一次修正（数据依据）：原写"按计划明细 `ClauseRefsJson` 决定合并粒度"，错——计划 56 项，`ClauseNumbers` 全为单值（56/56）⇒ 计划是"1 项 = 1 叶子条款"，推不出父段合并。
> 而真实报告是"父段成段"：科斯亚报告 32 段，计划 56 项中有 **31 条在报告里没有独立段**。这部分差异**不能由文档层/条款层/分析层消化**，只能由报告装配按机构模板消化。

| 层次 | 粒度规则 |
|---|---|
| **分析层（本文档粘性最强的一层）** | **1 个叶子条款 = 1 段证据**（8.4.1 / 8.4.2 / 8.4.3 各一段）。⛔ 不写"并入 8.4"，⛔ 不合并同章节条款 |
| **报告装配阶段**（不在本计划范围，另立文档） | 按 `cert_report_clause_map` 把叶子段映射到报告段：`ReportClauseNo=8.4` 时把 3 段拼成 1 段；`ReportMode` 只在本阶段取值 `direct / merged_into_parent / embedded` |
| 计划有、报告无该段（如 8.6 只在内审段被引用） | 分析层正常出段；装配阶段标 `embedded` 并入被引用段，`Coverage.NoOwnSection += 1` |
| 报告有父段、计划只有子项（4.4/5.1/7.5.3/8.2/8.4/9.2/10.2） | 正常出叶子段；装配阶段聚合。⛔ 不当作缺口、⛔ 不新增计划项 |
| 条款层判 `not_checkable`（标题条款） | 不进证据，只进 `Coverage` |

**推论（写进验收）**：
1. 分析层 `ClauseEvidence` 条数 = 计划叶子条款数（56），**不等于**报告段数（32）。
2. 报告段数 ≠ 计划项数，对账必须先过映射表，⛔ 不能拿"计划项 = 报告段"比覆盖率。
3. 覆盖率的分子是"有证据的叶子条款数"，不是"报告写了多少段"。

| **P4 扩量与切流** | 1 周 | 56 项全量分析 + 成本拆账 + 灰度开关 + 旧链退场条件 | 全量 P0 ≤ 3；单轮成本可归因到 3 层；灰度 5 部门无阻断 |

### 9.1 顺序约束（不可并行）

```
P0（契约/数据源） → P1（文档事实） → P2（条款发现） → P3（分析聚合） → P4（扩量）
                                        ↑
                          校验器必须与 P2 同批上线，不得后补
```

理由：93 号在 P0=7 时就讨论"扩到 10 条"，导致 v5.3.1 反向退化（P0 7→9）。**P0 未清零不得扩量。**

### 9.2 验收口径：75–85% 可用率（2026-11-16 用户裁决）

**目标不是 100%，也不追 100%。** 企业资料本身不全、不规范、现场证据未知——追 100% 只能往提示词里堆特例，
代价是通用性下降、A 类文档的产出被 B 类特例带坏（88 号已证：16KB 仍 40.6% 召回）。所以**用"可用率"验收，不用"完备率"**。

| 项 | 口径 |
|---|---|
| 抽样 | 10 个条款 × 同一家企业整链跑完（文档层 → 条款层 → 分析层） |
| 单条"可用"判据 | 该条款的**审核证据段**可直接放进报告草稿，审核员只需**改字**、不需**补事实** |
| 达标 | 可用 **8/10（80%）** 即达标；**7/10** 为可接受下限；**≥9/10 停手**（抽样偏简单，换更难的条款复验，⛔ 不继续加规则） |
| 不达标 | **≤6/10**：先判"文档有没有"——文档本身没有 ⇒ **不修**（进疑点或"需现场核实"）；抽取丢了 ⇒ 才改提示词或代码 |
| 不计入分母 | ① 报告事实不在文档里（97 号 F2/F4/F8/F12）② 只能现场确认（F13）③ 只能审核员判定（NC，R-C） |

> **分母必须是"文档可支撑的条款"**，⛔ 不是"报告里出现的全部事实"。
> 8.4 实测：报告 13 条事实项中，文档可支撑 7 条，改后 7/7 可写；若用报告全文当分母只有 54%，
> 那 6 条是资料本身没有，加多少提示词都拿不到。

### 9.2.1 提示词字符预算（硬上限，**只准减不准增**）

| 层 | 提示词 | 现字符（2026-11-16） | 上限 | 超限处置 |
|---|---|---|---|---|
| 文档层 | `doc_extract_record_profile` | 7,168 | **8,000** | 先删重复示例；仍超 ⇒ 拆成"记录/清单"两段，不合并塞 |
| 文档层 | 其余 `doc_extract_*` | 1,065–4,660 | **8,000** | 同上 |

FROM cert_prompt_template WHERE IsDeleted=0 ORDER BY chars DESC LIMIT 8;

### 9.2.2 反膨胀 6 条（判断"这条该不该写进提示词"）

1. **能用代码后处理**（路由 / 兜底 / 字段归一）⇒ 不进提示词。例：供应商清单路由、`PrimaryClauses` 兜底。
2. **能用配置表**（部门映射、`cert_report_clause_map`）⇒ 不进提示词。
3. **能用校验器**（缺字段告警、可疑值标记）⇒ 不进提示词。
4. **只服务 1 份文档 / 1 个企业** ⇒ 不进提示词（写进 97 号个例，通用提示词不动）。
5. **会不会让另一类文档变差** ⇒ 先离线 A/B（同一提示词 + 真文档直连模型），**不先落库**。
6. **加了必须删**：每加 1 条规则，至少删 1 条重复示例或冗长枚举；**净增 > 300 字符须在 commit 写明理由**
   （本次 `record_profile` 6,834 → 7,168，+334，同步删 1 条重复示例 —— 属"有理由 + 在 8,000 上限内"的个例，⛔ 不是惯例）。
