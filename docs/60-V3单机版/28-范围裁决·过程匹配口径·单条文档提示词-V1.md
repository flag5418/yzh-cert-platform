# 条款适用范围裁决 · 过程匹配口径 · 单条文档提示词定稿 V1

> 本文回应 2026-11-10 的四个反馈：①条款的「范围」问题；②过程与部门匹配难命中；③`Severity` 不必重跑；④提示词页面的归属与"一条提示词"的形态。
> 结论：属性池只回答"要求什么"，不承担"这条款这次审不审"的裁决；裁决靠企业范围 + 计划 + 条件三处比对。

---

## 一、条款的「范围」：三层裁决，不是属性字段能解决的

你说的现象是准确的：**执行时没有提取"范围"** ⇒ 有些条款只在特定范围下才检查（8.3 设计开发、7.5.2 无菌、7.4 采购外包、多场所抽样），但我们现在一视同仁地跑，等于凭空生成一段"本条款不适用"的证据。

### 1.1 三层信息，缺一不可

| 层 | 存什么 | 存在哪 | 谁来填 | 现状 |
|---|---|---|---|---|
| L1 企业层 | 认证范围（产品/服务类别）、场所清单、员工数、班次 | `cert_enterprise` 扩展字段 | 审核员建档 | 部分有（企业 1 家） |
| L2 计划层 | 本次审核覆盖的标准、删减条款（8.3 不适用等）、多场所抽样方案 | `cert_audit_plan` 新增 `ScopeJson` / `ExcludedClauses` | 审核员定计划时勾 | **表已存在但无这两列** |
| L3 条款层 | `Applicability = general / conditional`、`ApplicabilityCondition` = 触发条件原文 | `cert_clause_attr` | 属性池已生成 | ✅ 208 条已有（39 条 conditional） |

### 1.2 裁决规则（执行前先跑，不产生 LLM 调用）

```
条款 → N/A 判定
① 计划删减清单里有这条 ⇒ N/A（reason=excluded_by_plan）
② 条款 IsApplicability=conditional 且 企业事实不满足条件 ⇒ N/A（reason=condition_not_met）
③ 条款 Process 与计划覆盖的部门/过程无交集 ⇒ N/A（reason=process_not_covered）
④ 其余 ⇒ 进入证据生成
```

- 裁决结果落 `cert_check_result.Conclusion = "na"` + `Reason`（该表已有 `Conclusion` / `Reason` 列，不新建表）。
- **N/A 的条款不调 LLM、不生成审核证据**，报告里该条款不出现（ACM 报告实测：不适用条款整段不写，不是写"不适用"）。
- ②③ 两步需要"企业事实"，而企业事实来自文档 → 所以裁决发生在**文档分析之后、证据生成之前**，且只依赖已落库的 `cert_doc_fact` / 企业范围，不依赖 LLM 打分。

### 1.3 需要补的列（B/C 阶段一并做）

| 表 | 新增列 | 类型 | 用途 |
|---|---|---|---|
| `cert_audit_plan` | `ScopeJson` | TEXT | 本次审核范围快照（产品/场所/班次） |
| `cert_audit_plan` | `ExcludedClauses` | TEXT | 删减/不适用条款号数组 |
| `cert_check_result` | 无（复用 `Conclusion`/`Reason`） | — | 已有 |

## 二、过程与部门的匹配：不靠属性字段，靠下游综合判断

你判断得对：`Process` 给成 `[production, sales, design, purchase, inspection]` 这种宽集合，与部门职责做字面交集几乎必定命中，属性也不能再细化（再细化就是给每条款编部门，等于把咨询顾问脑子搬进字段）。

**处理口径（写进证据提示词，不写进属性）**：

| 环节 | 做法 |
|---|---|
| 属性侧 | `Process` 维持现状（最多 3 个，只给直接作用对象），**不再为提高命中率改字段** |
| 匹配侧 | 证据提示词输入 = 条款意图 + 属性 + 该部门职责摘录（≤120 字）+ 该部门相关事实行；让模型判"这条款的证据该由哪个部门提供、现有事实够不够" |
| 输出侧 | 匹配结果与理由一起输出（`DeptMatch` + `MatchReason`），人工可见可改 |
| 兜底 | 匹配不上 ⇒ 该条款进"待补现场证据"清单，⛔ 不允许模型编造部门 |

**因此本轮不改 `Process` 的取值口径，也不重跑。**

## 三、`Severity`：降级为参考，不重跑

你的口径成立：我们只做证据发现 / 疑点 / 审核证据这三样，**严重程度是审核员判断的事**。

| 处置 | 说明 |
|---|---|
| 不重跑 | 13485 那 61% critical 保留在库里，不再花 3 分钟去修 |
| 不参与裁决 | N/A 裁决与 `Severity` 无关（见 §一） |
| 不参与结论 | 证据生成不引用 `Severity`；`cert_check_result.Severity` 仍由审核员填 |
| 唯一用途 | 列表排序 / 复核时的提示（"这条款历史上多判 major"） |

> 属性池里 `Severity` 保留但标注为 **advisory**；将来若真要做预 NC，再单独校准。

## 四、文档提示词：合并为一条 `doc_analyze`（已落库）

你问得对：一个文档按一个标准，**只有一条提示词**。此前拆成 3 条（语义 / cite / detail）是按"两次调用"设计的，与你现在的口径不一致，已合并。

| PromptCode | 状态 | 字数 | 输入 | 输出 |
|---|---|---:|---|---|
| `doc_analyze` | **启用** | 4068 | 标准 + 文件名 + 过程码表 + 条款清单 + 文档 MD | `Profile` + `CiteEntries` + `Detail` + `Doubts` |
| `doc_semantic` | 停用（保留参考） | 2393 | — | 仅通用属性 |
| `doc_extract_cite` | 停用（保留参考） | 1065 | — | 仅 cite 条目 |
| `doc_extract_detail` | 停用（保留参考） | 1504 | — | 仅 detail 行 |

**一次调用怎么保证"没判能不能用就先提取"不发生**：提示词里写死执行顺序 —— 先判两道闸 → 再定 `DocType/ExcerptStyle` → **只有两闸都过才填提取段**，且 `ExcerptStyle` 决定填 `CiteEntries` 还是 `Detail`，另一段必须留空。这在同一次输出里是可控的（不是靠两次调用）。

**输出契约**（代码按此解析，字段名固定）：

```json
{
  "Profile": { "IsSystemDoc": true, "DocType": "record", "ExcerptStyle": "detail",
               "ProcessDomains": ["inspection"], "ClauseHints": ["8.4.2"],
               "Extractable": true, "DocTitle": "", "DocCode": "", "DocVersion": "",
               "OwnerDept": "", "Period": "", "Confidence": 0.86 },
  "CiteEntries": [],
  "Detail": { "Sheets": [], "Facts": [], "Truncated": false },
  "Doubts": []
}
```

## 五、落地在哪：就用 `/business/doc-extract-rule`，不另开一套

2026-11-10 口径更正（用户裁决）：**不新建 V3 页面、不新建文档三表**，复用已有链路：

| 环节 | 复用对象 | 本次改动 |
|---|---|---|
| 提示词编辑页 | `/business/doc-extract-rule`（左树标准 + 编辑器 + 测试面板） | 把页面读写的 PromptCode 从 `doc_extract`（无人消费）切到 **`doc_clause_extract`**（企业文档上传链路真正在用） |
| 提示词存储 | `cert_prompt_template`（ScopeKey=标准短码，缺省回落平台级） | 写入 V3 单条正文 2893 字（两闸 + 10 类 + 条款摘录 + 疑点） |
| 左树数据源 | `cert_doc_extract_rules`（原为空） | 补 4 个标准节点（iso9001/14001/45001/13485） |
| 上传 → 转 MD → 提取 | Auditor 侧既有：`cert_enterprise_doc`（上传/转换）+ `ClauseExtractExecutor`（按 文档×标准 提取）+ `cert_document_extraction`（产物） | 不改代码，只换提示词内容 |
| 输出契约 | `clauses[{ClauseNumber,Title,Anchor,Excerpts,Confidence}]` | **保持不变**；新增 `profile` / `doubts` 两个键，反序列化忽略未知字段，不破坏链路 |

### 5.1 为什么提示词里能同时放"通用属性"

`ExtractedDoc` 只读 `Clauses`，其余字段被忽略 ⇒ 同一个 JSON 里可以并行输出：

```json
{ "profile": { "IsSystemDoc": true, "Extractable": true, "DocType": "procedure",
               "DocCode": "", "DocTitle": "", "OwnerDept": "", "Period": "",
               "ProcessDomains": ["purchase"], "Confidence": 0.88 },
  "clauses": [ { "ClauseNumber": "8.4", "Title": "采购", "Anchor": "…", "Excerpts": ["…"], "Confidence": 0.9 } ],
  "doubts":  [ { "Type": "no_sign", "Loc": "P3 签批栏", "Message": "无签名无日期" } ] }
```

- 现在：链路只吃 `clauses`，立即可用。
- 以后：`profile` / `doubts` 落 `cert_enterprise_doc` 扩展列或现表，随认证准备/检查消费时再接。
- ⛔ 不再维护第二个"文档分析"提示词副本；`doc_analyze` 已置 `IsValid=0` 留档。

### 5.2 测试入口

页面已有"规则测试"面板（上传 + 运行），但 `runTest()` 目前是 TODO。等 Admin 侧接一个 `POST /prompt/test`（入参：文件 + 标准 → 转 MD → 用当前编辑正文跑一次 → 回 JSON，不落库）即可闭环；转换/调模型能力在 `yzh-anydoc` 容器与既有 LLM 客户端，属后续一步。
