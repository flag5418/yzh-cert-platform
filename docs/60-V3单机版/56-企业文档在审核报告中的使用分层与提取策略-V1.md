# 56-企业文档在审核报告中的使用分层与提取策略-V1

> 状态：诊断 + 17 程序 V5 试跑完成；尚未改运行时。
> 目的：把“报告对不同文档选择性使用”的规律固化成提取模型，避免把所有文档都按同一种深度、同一种结构去提取。
> 关联：`55`（17 在报告中的位置）、`54`（标准 PDCA 投影）、`53`（V3 瘦身）。

## 一、结论

真实报告不是“把企业文档搬进去”，而是按文档作用分四层使用：

| 文档作用 | 典型文档 | 报告用法 | 报告文字占比 |
|---|---|---|---:|
| 框架 | 质量手册 | 条款框架、体系范围、职责引用 | 低 |
| 要求 | 程序文件、方针、目标、制度 | 引用文件名 + 1–2 句摘要；不复制长文 | 中低 |
| 证据 | 记录、表单、检验报告、内审/评审记录 | 抽样，写日期/批次/型号/实测值/人员/结论 | **高** |
| 索引 | 文件清单、记录清单、汇编封面 | 用来定位文件和记录，不作证据 | 极低 |

`17生产和服务提供控制程序` 就是典型“要求层”文档：

- 显式只出现 2 条：7.5.3（文件化信息示例）、8.1（管理要求）；
- 8.5.1–8.7 的报告证据来自生产计划、作业文件、检验记录、不合格记录，不是 17 的原文；
- 17 只需要“引用 + 短摘要 + 证据入口”，不需要 6 个过程 × 21 个活动。

## 二、文档分层与报告深度

新增两个字段，比 `DocType` 更靠近报告：

```json
{
  "DocUse": "framework | requirement | evidence | reference | audit_record",
  "ReportDepth": "verbatim | summary | citation | sample | index",
  "ReportShare": "high | medium | low"
}
```

| DocUse | ReportDepth | 输出什么 | 输出预算 |
|---|---|---|---|
| `framework`（手册） | `summary` / 逐条款另跑 | 章节框架、范围、职责 | 不用于证据 |
| `requirement`（程序/制度） | `summary` | 1 句摘要、3–6 个关键控制、条款/证据入口 | 1–2k 字符 |
| `requirement`（作业指导书） | `citation` | 适用过程/设备、3–8 个关键步骤/参数、记录 | 300–800 字符 |
| `evidence`（记录/表单） | `sample` | 字段、2–3 条样例、日期/批次/人员/结论 | 500–2,000 字符 |
| `audit_record`（内审/评审） | `verbatim` | 审核发现、结论、条款、日期、人员 | 1,000–3,000 字符 |
| `reference`（清单/封面） | `index` | 文件号、文件名、版本、保存部门/期限 | 500–1,500 字符 |

**方针/目标/领导作用**单独按 `verbatim` 处理：承诺、目标、职责、批准/发布日期基本原样保留，不改写。

## 三、报告的实际组织方式

报告按 `Process Area` 分段，再列条款和证据：

```text
Process Area（生产过程、检验过程）
  负责人：生产部/品质部
  7.1.3、7.1.5、8.1、8.5.1–8.5.6、8.6、8.7
```

注意：**同一过程区域不等于同一份程序覆盖全部条款**。`17` 只覆盖 8.1、8.5.1、8.5.4、8.5.5、8.5.6、8.6 的一部分；8.5.2、8.5.3、8.7 由其他程序/记录支撑。因此提取必须同时输出：

- `SupportClauses`：本文件正文实际覆盖的条款；
- `RelatedDocs`：正文“相关文件”列出的其他程序及其对应条款；
- `ReportEvidenceHints`：报告可抽样的记录，标明来源是 `document` 还是 `report`。

### 4.2 仍需代码校验

V5.2 还有一处模型漂移：

- “保留各工序生产操作情况记录”被挂到 **8.5.6**（更改控制），实际应挂 **7.5.2/8.5.1**。

说明只靠提示词不够，必须加确定性 guard：

- 控制语义词表：`记录/填写/保存` → 7.5.2 或 8.5.1；`变更/更改` → 8.5.6；`放行` → 8.6；`不合格` → 8.7；`投诉/交付后/售后` → 8.5.5。
- `ReportClause` 不在 `SupportClauses` 内 → 删除或降级为 `RelatedClause`；
- `EvidenceName` 不在 `DocumentEvidencePointers`/`ReportEvidenceHints` 内 → 删除；
- `SupportClauses` 与 `RelatedDocs` 重叠 → 保留 `SupportClauses`，相关文件改挂其他条款。

## 五、对“报告文字占比”的解释

企业文档数量最多的是二、三阶文件（程序、作业指导书、记录模板），但报告正文不是按数量分配篇幅：

- **程序/作业文件**：数量多，报告里通常只占“引用句 + 1 段摘要”，占比低；
- **记录/表单**：数量多，但报告只抽样 2–5 条，单条写得很细，证据占比高；
- **方针/目标/领导作用**：文件少，但报告接近原文搬运，占比高；
- **内审/管理评审**：文件少，但报告大段引用发现/结论，占比高；
- **清单/索引**：只用于定位，不进入证据正文。

所以提取策略必须是：

> 程序/作业文件“短而准”；记录“少而细”；方针/领导/审核“近原文”；索引“只做导航”。

## 六、落地建议

1. **先改 17 的运行模式**：程序文件不再输出 6 个过程/21 个活动，改为 `ReportProjection`：1 句摘要 + 3–6 个 KeyControls + SupportClauses + RelatedDocs + EvidenceHints；目标 ≤2k 字符、≤20 秒。
2. **作业指导书另做 `citation` 模式**：1 个过程 + 3–8 个步骤/参数 + 记录，不再输出 42 个活动。
3. **记录保持 `sample` 模式**：字段可以全，但样例最多 3 条；日期/批次/人员/结论必须来自原文。
4. **方针/领导/审核保持 `verbatim`**：不改写承诺、目标、发现、结论。
5. **索引保持 `index`**：只输出文件号/文件名/版本/保存期限。
6. **手册继续逐条款**：不用 `ReportProjection` 替代。
