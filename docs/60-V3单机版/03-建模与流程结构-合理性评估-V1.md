# 建模、流程与结构：合理性评估 V1

> 本文回答四个问题：①“一条提示词灌全部条款”是否可行、要不要 80 次调用 ②你的“文档两层结构”是否成立 ③证据组织放在第三步是否对 ④流程与结构设计是否合理。
> 全文自包含。所有数字为估算口径，用于判断量级，不是承诺。

## 一、问题 1：一条提示词灌进全部条款，还是每条跑一次

### 1.1 先看硬约束

| 方案 | 输出体量（80 条款 × 12 属性） | 结果 |
|---|---|---|
| 1 次全灌 | 约 2 万 token 输出 | **必然截断**。多数模型单次输出上限 4k–8k token，第 30 条之后为空，且**不报错** |
| 80 次逐条 | 每次约 1k token 输出 | 可靠，但每次都要重复带“标准术语表 + 12 条属性定义”，约 2k token × 80 = 16 万 token 全是重复开销 |
| 分批 | 每批 5–20 条 | 输出可控，重复开销摊薄 |

**结论：不是“1 次”，也不是“80 次”。**

### 1.2 正确做法：先分层，再定批量

十二个属性的答案长度差一个数量级，所以批量不能一刀切：

| 层 | 属性 | 每批条款数 | 每标准批数 | 单批输出 |
|---|---|---|---|---|
| 结构层 | 约束强度 / 适用性 / 过程域 / 文档核对方式 | 15–20 条 | 4–5 批 | 约 1–1.5k 字 |
| 语义层 | 条款作用 / 可验证要素 / 应备资料 / 取证剧本 / 时效 / 抽样 | 5–6 条 | 14–16 批 | 约 3–4k 字 |

**合计约 20 次/标准**。四个标准约 80 次。串行按每次 6 秒算约 8 分钟，可并行则 3 分钟内。

### 1.3 为什么结构层能大批量

“应/宜/可/注”“通用/有条件”“管哪些过程”“要不要查资料”——这些是**词法特征**，答案极短，模型不需要长推理，20 条一批不降质。

语义层相反：一条条款要拆 3–7 个要素、写两套措辞，输出长，5 条一批已是上限。

### 1.4 标准频繁换版、标准数量多，怎么不返工

这是设计里最容易踩的坑，要靠三条机制，而不是靠“提示词写得宽容”：

**机制一：模板共享，值独立**

- 生成**规则与模板**可以跨标准复用（Annex SL 高阶结构里 4–10 章位置相同）。
- **属性值绝不跨标准复用**。典型反例：环境管理体系与环境/职业健康安全体系都有 6.1.2，但一个是“环境因素”，一个是“危险源辨识”。复用值 = 两本标准全错，且不报错。

**机制二：按“标准 + 版本”分区，不按“标准”分区**

- 条款表、提示词、属性值都带标准版本号。
- 某本标准换版时，只重跑这一本、这一版；其他标准一行不动。
- 旧版本行保留（停用不删），用于“换版差异对比”——这本身是卖给审核员的一个附加价值：新版多了什么、改了什么。

**机制三：模板层与差异层分离**

新增一本标准时：
1. 先套模板（结构层 4 个属性按句式规则直接推，不用模型）
2. 再只对“差异条款”跑语义层（增补条款、术语替换条款、加严条款）
3. 全量语义层只在该标准首次引入时跑一次

> 按经验，一本新标准真正需要模型的条款约为全量的 40%–60%，其余可由模板 + 映射得到。

### 1.5 分批必须配套的三件事

| 配套 | 为什么 |
|---|---|
| 每批落库即提交 | 一批失败不拖累其他批；重跑从断点开始 |
| 每批带“条款清单回执” | 输出里必须回显这一批的条款号，缺了哪个立即发现，而不是等到下游报空 |
| 输出尾部要求“结束标记” | 模型截断时结束标记缺失，可判定为不完整，自动重跑该批 |

> 第三条是纯工程手段，能把“静默截断”变成“显式失败”。这一条不做，前面所有分批设计都是纸上的。

## 二、问题 2：你的“文档两层结构”是否成立

### 2.1 判定：整体成立，四处要改

| 你的设计 | 判定 | 说明 |
|---|---|---|
| ① 先判“是否与条款有关”，无关的直接排除 | **方向对，做法要改** | 排除是不可逆的：判错了这份文件永久失踪，而且下游只会表现为“这条款没证据”，不会报错。应改为“标记相关度”，低相关仍保留但降权 |
| ② 分类为 手册/过程/指导书/记录 | **对，但要扩** | 至少补：报告、台账、证书、计划。台账与记录混在一起，抽样句就抽不出来 |
| ③ 所属过程 / 主要相关部门 | **对，但必须受控** | 部门名必须来自该企业的部门清单（受控词表），否则“生产部/制造部/车间”三种写法同时存在，部门矩阵算错 |
| ④ 文档作用（概括） | **对，但只作检索线索** | 概括必然丢信息，不能当证据。证据只能是原文片段 + 位置 |
| ⑤ markdown 原文 | **对，但必须同时存位置映射** | 这是最容易被忽略的一点，见 2.3 |

### 2.2 必须先改的一点：不要“每文档 × 每条款”全跑

你的原始设想是每个文档过一遍全部条款，3 个标准就跑 3 遍。按 60 份文档、80 条款算：

```
朴素做法： 60 × 80 = 4,800 次/标准 × 3 标准 = 14,400 次
```

这个量级不可行——不是钱的问题，是**失败率和不可控**：几千次调用里必然有几十次返回垃圾，且无法定位。

**改为两级召回：**

```
第一级（每份文档 1 次）：文档画像 → 分类 / 相关度 / 作用 / 部门 / 涉及哪些条款（候选 8–15 个）
第二级（只用规则，零模型）：按条款术语表 + 关键词，校验并收缩候选（80 → 8–15）
第三级（仅候选条款，5 条/批）：要素级提取
```

**量级对比：**

| 做法 | 调用数（60 文档 / 1 标准） |
|---|---|
| 朴素全跑 | 4,800 |
| 两级召回 | 60 画像 + 约 40 相关文档 × 2 批 ≈ **140** |
| 三标准（差异条款约 70%） | 60 + 40 × 2 × 2.7 ≈ **280** |

> 差 30 倍以上。而且第二级的规则召回**可解释、可复核**：命中了哪几个关键词、为什么收进候选，全都能打印出来；模型只处理规则对不上的残余。

### 2.3 markdown 转换必须保留位置映射

转成 markdown 后，页码没了、章节层级也被压平。如果不额外存映射：

- 报告里的“出处”只能写“某文件”，写不到第几页第几节
- 不符合项无法引原文，复核人一查就对不上

**做法**：转换时同步产出 `位置表`：

```
{ 原文页码: 3, 章节: "3.2 文件控制", markdown 起止行: [120, 168] }
```

证据定位到 markdown 行号 → 反查页码/章节。这一步不做，后面所有“带出处的句子”都是假的。

### 2.4 三个标准是否要跑三遍

| 层 | 是否要按标准跑 3 遍 | 理由 |
|---|---|---|
| 文档画像（分类/作用/部门） | **不用，1 遍** | 与标准无关，只与文件本身有关。术语差异不影响“这是不是一份程序文件” |
| 候选召回 | **不用，1 遍后按标准过滤** | 候选按条款号建，直接按标准拆开 |
| 要素级提取 | **要，但只对差异条款** | 同号不同义必须分别提，不许复用 |

**结论：3 个标准约等于 1.7 遍，不是 3 遍。**

## 三、问题 3：证据组织放在第三步，对不对

### 3.1 顺序对，但补三个东西

你的顺序：文档结构 → 条款属性 → 证据组织。这个顺序是对的（证据组织必须在有“要素级事实”之后）。

缺的三件：

| 缺 | 为什么必须有 |
|---|---|
| 组织单位是“部门 × 条款组”，不是单条款 | 真实报告一行压 5 个条款号；按单条款生成会把一段话拆成五段碎话 |
| 三态与覆盖声明 | “有/不全/没有”决定能不能写“符合”；覆盖声明是报告免责条款的唯一依据 |
| 结论候选由规则算、人确认 | 系统不判定，但必须给候选，否则审核员要从零想 |

### 3.2 七种句式不是七个模板，是“段内顺序”

真实记录的顺序是固定的：

```
定位句（部门/负责人/日期）
  → 依据句（执行哪个程序）
  → 查见句（文件元数据：编号/版本/发布日/编制/审核/批准）
  → 抽样句（抽几份，每份关键字段）
  → 结论句（经查…）
```

现场句是插入项，不符合句是另开卡片（不混在段内）。这个顺序不能打乱——打乱了审核员一眼就看出来不是人写的。

### 3.3 合并一段时的三条拼装规则

一组条款合成一段，必须有规则，否则会出现“同一份文件被引用五遍”：

1. 条款按编号升序排列
2. 同一份文件只在首次出现时写全元数据，后续引“同上”
3. 每段句子数设上限（建议 8–12 句），超了就拆段

## 四、问题 4：流程与结构是否合理

### 4.1 流程：八个阶段

| 阶段 | 做什么 | 用模型 | 幂等键 | 失败处理 |
|---|---|:--:|---|---|
| S0 资料入库 | 扫描、算哈希、识别类型、排除无关 | 否（规则） | 文件 MD5 | 单文件失败不阻塞 |
| S1 文档画像 | 分类 / 相关度 / 作用 / 部门 / 候选条款 | 是（1 次/文件） | MD5 + 提示词版本 | 单文件重试，最多 3 次 |
| S2 候选收缩 | 规则 + 条款术语表 | 否 | 同上 | 可随时重跑，零成本 |
| S3 要素提取 | 按标准，仅候选，5 条/批 | 是 | MD5 + 条款版本 + 提示词版本 | 批次级重跑 |
| S4 证据归集 | 按（部门 × 条款 × 要素）建索引 | 否 | 由 S3 派生 | 可全量重算 |
| S5 计划装配 | 部门 × 条款组 → 生成单元 | 否 | 计划版本 | — |
| S6 句式生成 | 模板填槽 + 结论候选 + 覆盖声明 | 否（可选润色） | 生成单元 + 证据快照 | 单段重生成 |
| S7 报告导出 | 三份文档 + 快照冻结 | 否 | 快照版本 | — |

**关键判定：S1、S3 是唯一两次花钱的地方，其余全部是确定性计算。** 这是整个结构设计的第一原则：**把模型调用压缩到两个阶段，且都能缓存。**

### 4.2 结构设计：五个必须

**① 知识库与项目库物理分离**

- 知识库（标准侧）：条款、属性定义、属性值、提示词、文档要求。只读，按版本重灌。
- 项目库（企业侧）：文档、提取结果、证据、记录、报告。增量，按项目隔离。

混在一起（同一批表带 `EnterpriseCode` 判断归属）是典型事故源：一次重灌知识库会把项目数据一起洗掉。

**② 必须存“原始模型输出”**

每个提取结果同时存三份：原始 JSON 文本、解析后字段、派生状态。

原因很实在：解析逻辑改了（比如加一个字段、改一个枚举），如果没存原文，就得重新花钱跑模型。这是最容易后悔的一处设计。

**③ 全链路幂等 + 缓存**

每个计算单元带 `(单元键, 输入哈希)`，命中缓存直接取。输入哈希至少包含：文件 MD5 + 条款版本 + 提示词版本。

效果：改一句措辞模板，不会触发全量重跑；只有真正变了的输入才重算。

**④ 批次级断点**

每个阶段有批次记录（批号、范围、状态、耗时、失败清单）。中断后从"未完成批次"继续，而不是从头再来。

**⑤ 版本与失效显式化**

提示词版本、条款版本、标准版本三者任一变化 → 相关结果标脏（不删），重算时覆盖，旧值留档。

⛔ 禁止"静默降级"：某标准没有专属提示词时用通用版，必须在结果里打标记并告警。否则出问题时完全无法解释。

### 4.3 存储形态建议

| 对象 | 形态 | 理由 |
|---|---|---|
| 条款、属性值、提示词 | 数据库表 | 需要按条款/属性查询、需要版本对比 |
| 文档原文 markdown | 文件（按项目目录） | 体积大，不查全文就不必进库 |
| 位置映射表 | 文件（JSON，与 markdown 同目录） | 与原文强绑定 |
| 提取原始输出 | 文件（按文档/标准/批次归档） | 便于排查，不进库不拖慢查询 |
| 解析后字段、证据 | 数据库表 | 需要按部门/条款/要素检索 |
| 报告快照 | 数据库 + 导出 docx | 快照要能回溯任意历史版本 |

## 五、需要你拍板的四个决策

| # | 决策 | 选项 | 影响 | 建议 |
|:--:|---|---|---|---|
| 1 | 结构层是否允许大批量（20 条/批） | 是 / 否 | 调用数减半 | 是，但要带“条款清单回执” |
| 2 | 无关文档是“排除”还是“降权保留” | 排除 / 降权 | 判错的代价 | 降权保留，只在生成阶段不取用 |

## 六、一句话总结

**建模上你的两层结构是对的，只需把“每文档 × 每条款”改成“先画像、再规则召回、最后只跑候选”；流程上把钱花在两个阶段（画像 + 要素提取），其余全部确定性计算；结构上把知识库和项目库分开、把原始输出留住、把每个单元做成幂等可重算。**
