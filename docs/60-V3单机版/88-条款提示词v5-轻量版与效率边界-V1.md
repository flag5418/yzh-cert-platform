# 条款提示词 v5.1：轻量版与效率边界

## 一、先回答两个问题

### 1. 时间为什么长

不是模型慢，是流程长：

- v4 → v4.1 → v4.2，连续三轮；
- 每轮 5 条条款，串行调用；
- 每条都重新读 DB、重新拼 prompt、重新写文件；
- 为了压住个别条款，反复加规则、反复重跑。

v5.1 改成：

| 项 | v4.2 | v5.1 |
|---|---:|---:|
| 提示词体积 | 14,772 字节 | **7,678 字节** |
| 行数 | 273 行 | **169 行** |
| 单轮测试条数 | 5 条串行 | **2 条并行** |
| 单轮耗时 | 约 2–3 分钟 | **约 30–40 秒** |
| 迭代次数 | 3 轮 | **1 轮** |

以后只做“2 条冒烟 + 通过再扩 5 条”，不再每改一个字就全量重跑。

### 2. 报告内容文档里没有，不是提示词的错

前面已经确认：报告里很多证据是审核员单独收集、补充、拍照、截图、访谈形成的，企业文档里本来就没有。

所以：

- 提示词只负责“从企业文档能抓到什么”；
- 报告里的内容只做 `report_only` 对账，⛔ 不回填文档事实；
- 抓不到就进 `Gaps`，交给审核员；
- 不要求提示词把报告里的证据“补”出来。

---

## 二、准确率边界

不按代码的 90% 正确率要求提示词。分三层：

| 层级 | 指标 | 目标 |
|---|---|---|
| 结构 | JSON 可解析、范围正确、文档字段齐全 | **100%** |
| 文档事实 | 不编造企业文件名、不把空白模板写成已执行、不把报告数据写成文档事实 | **≥95%** |
| 证据召回 | 条款明示要求尽量覆盖，允许漏项进 `Gaps` | **60–80% 可接受** |

核心不是 100% 召回，而是：

1. 不编造；
2. 不遗漏条款明示的关键证据；
3. 能识别风险；
4. 能按文档类型组织；
5. 漏掉的能明确标 `Gaps`，审核员知道去哪补。

## 三、v5.1 的五个结构

v5.1 只保留五块，不再为 8.2.4 / 8.2.6 / 8.3.2 / 7.6 写特例：

1. `ClauseContext`：范围、是否可检查、检查方式、边界、a/b/c/d 分项；
2. `ChapterContext`：章节意图、章节核心证据、本条在整章的作用；
3. `ReferencedAnalysis`：正文“见 X.X”的引用条款，带条件进来，不另开检查项；
4. `EvidenceContract`：文档类型、覆盖层级、提取深度、轻模型 key、文档边界、字段、频次、覆盖；
5. `ReportHint`：报告用法提示，不依赖用户合并。

### 3.1 文档类型只用一张表

| 条款语言 | DocClass | EvidenceRole | ExtractionDepth | DocProfileKey |
|---|---|---|---|---|
| 建立/形成文件/规定职责 | procedure | establishment | structured | procedure_v1 |
| 实施/执行/保留记录 | record | implementation | fact_profile | record_v1 |
| 依据/接收准则/检验规程 | work_instruction | criteria | criteria | work_instruction_v1 |
| 手册/方针/范围 | manual / policy | establishment | citation_only | manual_v1 / policy_v1 |
| 计划/方案 | plan | support | structured | plan_v1 |
| 清单/台账 | list | support | structured | list_v1 |
| 报告/结论 | report | support | fact_profile | report_v1 |

### 3.2 术语映射只保留 5 条

| 条款术语 | 证据命名 |
|---|---|
| 消除已发现的不合格 | 返工/返修记录 |
| 防止原预期使用或应用 | 报废/隔离/转用记录 |
| 授权让步使用、放行或接收 | 让步接收审批记录 |
| 审核记录/审核和审核结果的记录 | 签到表/首末次会议记录 |
| 审核员的选择/客观公正 | 审核员能力/授权/任命记录 |

这 5 条是通用语言映射，不是单个条款特例。

## 四、v5.1 冒烟结果

2 条并行，**2/2 JSON_OK**，总耗时约 35 秒。

### 4.1 `8.2.4` 内部审核

证据 7 项：

1. 内部审核程序（procedure / structured）
2. 年度内部审核方案（plan / structured）
3. 单次内部审核检查表（work_instruction / criteria）
4. 内部审核首末次会议记录（record / fact_profile）
5. 内部审核不合格报告（record / fact_profile）
6. 内部审核报告（report / fact_profile）
7. 审核员能力与授权记录（list / structured）

评价：

- 比 v4.2 少 1 项（少了独立的签到表，把签到并入首末次会议记录）；
- 仍覆盖“程序、计划、检查表、会议/签到、不合格报告、内审报告、审核员能力”七件套；
- 多文档组合出内审结论的路径还在。

### 4.2 `8.3.2` 交付前不合格

证据 6 项：

1. 返工/返修记录（record / fact_profile）
2. 报废/隔离/转用记录（record / fact_profile）
3. 让步接收审批记录（record / fact_profile）
4. 不合格品处置程序（procedure / structured）
5. 让步接收授权人员清单（list / structured）
6. 交付前检验规程（work_instruction / criteria）

评价：

- a/b/c 三条路径已拆开；
- 比 v5 多了返工/返修、报废/隔离；
- 仍没有进货/过程/成品三张不合格检验记录，这属于 `Dependencies.support`，不继续写进提示词。

## 五、以后不再做的事

| 不再做 | 替代方案 |
|---|---|
| 为单个条款加特例规则 | 通用术语映射 + 运行时 `DocumentExpectationMap` |
| 为压住条款号幻觉反复改提示词 | 运行时 `ClauseRefValidator`，白名单外直接标 `ClauseRefViolation` |
| 报告有什么，就要求文档提取什么 | 报告数据只作 `report_only`，不回填文档事实 |
| 每改一版都跑 5 条串行 | 2 条并行冒烟，通过再扩 5 条 |
| 追求 90%+ 证据召回 | 结构 100%、事实 ≥95%、召回 60–80%，漏项进 `Gaps` |
| 提示词越长越安心 | 7–8KB 为上限，超过就拆到运行时规则 |

## 六、下一步只做三件

1. **`ClauseRefValidator`**：正则抽 `Boundary / ClauseRoleInChapter / Influence` 里的条款号，与 `AllowedClauseRefs` 比对，越界标 `ClauseRefViolation`；
2. **`DocumentExpectationMap`**：把“接收准则→work_instruction”“检测设备→support”“不合格→record”做成运行期映射，补 8.2.6/8.3.2 的漏项；
3. **`ReportMap`**：把 7.3/7.5 的合并父块做成配置，不让用户手工合并。

这三件都在运行时做，不再增加提示词体积。
