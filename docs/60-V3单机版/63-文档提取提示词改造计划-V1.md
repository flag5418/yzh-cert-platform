# 63-文档提取提示词改造计划-V1

> 状态：已完成（提示词落库 + 7 类真实文档试跑）
> 日期：2026-11-13
> 目标：把现有类型提示词统一到一套“报告可用的事实契约”，不再按条款全文硬灌，也不再让每类文档输出同一种深度。

## 一、问题

现有提示词已经按类型分了 `process_profile`、`record_profile`、`work_instruction_citation`、`policy_profile`、`context_list`、`document_control`、`index_only`、`audit_profile`，但存在四个不一致：

1. 字段名不一致：过程用 `DocRole/Processes`，指导书用 `DocUse/KeySteps`，记录用 `Records`，索引只有 `IndexEntries`；
2. 缺少统一报告字段：多数没有 `ProcessArea`、`ReportDepth`、`SupportDepts`；
3. 条款范围不统一：有的输出 `PrimaryClauses/SupportClauses`，有的只输出 `ClauseLinks`，后者已被代码清掉；
4. 深度不统一：程序文件仍可能输出 2–6 个过程、几十个活动，和报告“引用+短摘要”的实际用法不符。

## 二、改造原则

| 原则 | 做法 |
|---|---|
| 按报告用法定深度 | 程序/制度=summary；指导书=citation；记录=sample；方针/领导/审核=verbatim；索引=index；文件控制=metadata+catalog |
| 统一公共字段 | 所有类型都输出 `DocUse / ReportRole / ReportDepth / ProcessArea / OwnerDept / SupportDepts / PrimaryClauses / SupportClauses / ReportUse` |
| 条款只到叶子 | 父条款没有描述的，拆到有描述的子条款；不把整章条款塞进提示词 |
| 部门只认真实部门 | 只写报告受审六部门或文档明确写出的部门；不写“各部门/相关部门” |
| PDCA 代码算 | 模型不写 `PdcaPhase`；代码按 `PrimaryClauses/SupportClauses` 计算 |
| 不做审核结论 | 不写符合/不符合/充分/缺失/建议；只写文档事实和报告可用摘要 |
| 不引标准全文 | 提取提示词不塞 GB/T 全文；条款范围由画像、报告过程域和条款清单约束 |

## 三、输出公共契约

```json
{
  "DocUse": "requirement | evidence | audit_record | reference | context_evidence | policy | document_control | irrelevant",
  "ReportRole": "supporting_requirement | operation_basis | evidence_source | audit_evidence | index | context_analysis | management_requirement | documented_information_evidence | none",
  "ReportDepth": "summary | citation | sample | table_sample | metadata+catalog | verbatim | index",
  "ProcessArea": "GM/MR | 行政人事 | 生产过程、检验过程 | 销售过程 | 采购过程、销售过程 | 未标注",
  "OwnerDept": "真实部门或未标注",
  "SupportDepts": ["真实部门"],
  "PrimaryClauses": ["叶子条款号"],
  "SupportClauses": ["叶子条款号"],
  "ReportUse": "报告可用说明；不写报告已引用"
}
```

## 四、分类型输出预算

| 模式 | 提示词 | 输出重点 | 预算 |
|---|---|---|---|
| `process_profile` | Id=9 | 1 句摘要 + 3–6 KeyControls + 条款范围 + 相关文件 + 记录入口 | ≤2k 字符 |
| `record_profile` | Id=10 | 记录名/部门/字段/期间/批次/1–3 条样例/签署 | ≤2k 字符 |
| `index_only` | Id=11 | 文件号/文件名/版本/关系；不产出事实 | ≤1k 字符 |
| `audit_profile` | Id=12 | 审核/评审事实、发现、原文结论、覆盖部门 | ≤3k 字符 |
| `document_control` | Id=13 | 元数据 + 目录摘要 + 7.5.2/7.5.3 | ≤2k 字符 |
| `work_instruction_citation` | Id=14 | 1 句摘要 + 3–8 步骤 + 记录指针 | ≤1k 字符 |
| `context_list` | Id=15 | 因素/相关方条目 1–12 + 字段 + 总数 | ≤1.5k 字符 |
| `policy_profile` | Id=16 | 目的/范围/责任/3–8 关键规则 + 记录 | ≤1.5k 字符 |

## 五、实施步骤

1. 建 SQL：`scripts/db/fix/20261113_doc_extract_prompt_unify_V1.sql`；
2. 更新 Id=9/10/11/12/13/14/15/16 八个模板；
3. 不改 `DocExtractGuard` 的删除逻辑，但补齐新字段的 PDCA/部门计算；
4. 选四份真实文档试跑：17 程序、10 指导书、01 外部因素、07 记录清单；
5. 检查：输出 JSON 合法、字段齐全、部门在真实部门内、条款为叶子、无审核结论、无 `ReportPresence`。

## 六、验收

- 四份文档都输出公共字段；
- `17` 不再输出 2–6 个过程和几十个活动，改为短投影；
- `10` 保持 3–8 步；
- `01` 保持 4.1 证据，不挂 7.5.3；
- `07` 保持 7.5.2/7.5.3 文件控制；
- `DocPdcaClassifier` 能为四份文档算出 `PdcaPhase` 和 `DeptNames`；
- 总耗时不超过原同文档的 1.2 倍。

## 七、不做

- 不把 GB/T 全文再塞进提示词；
- 不新增文档三表；
- 不把“条款合并规则”写进系统规则；
- 不让模型判断报告是否引用。
