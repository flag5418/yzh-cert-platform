# 94 · 文档提取与条款证据提示词体系评估（V1）

> 评估对象：`docs/60-V3单机版/` 编号 60–93 的全部设计、试跑与提示词全文（34 篇 md + 25 份 json + 7 份 txt，共 1.58 MB）。

**三句话结论**

1. 60–93 已经把"文档事实层 / 条款证据发现层 / 审核证据层"这条主线论证清楚，v5.3 是当前最优基线，v5.3.1 不应替换。
2. 真正的瓶颈已经不是提示词文本，而是**契约多套并存 + 运行时缺位**：shadow 三条提示词在库里、生产代码里没有对应服务，旧链产物 22 行仍是旧结构且 `IsStale=0`。
3. 继续调提示词的边际收益已低于副作用；下一阶段应冻结文本，按 §十 的顺序补数据源、运行时、校验器，并先做 3 条端到端。

## 八、五个模式性判断（进一步分析）

1. **改进来自"改输入结构"，不是"加规则"。**
   v3.2 加到 16,072 字节，召回仍 13/32（40.6%）；v4.2 提升到 26/32（81%）靠的是新增 `chapter_profile`/`allowed_clause_refs`/`referenced_clauses` 三个输入；v5.x 把体积砍到 7,678 又把问题从 55 降到 29，靠的是删规则 + 校验器。下一步若继续在文本里加条款特例，方向与实证相反（88 号也已写明这条边界）。

2. **单轮最优 ≠ 可用。** 6/10 条款重跑数量变化、8.6 的 finding 集合重合 2/7，说明"模型每次都换一批疑点"。真正需要锁的是结构与门禁，不是某一次的漂亮结果。评估任何新版本，应至少两轮同输入 + 一致性指标。

3. **技术债的主因是"重命名没有迁移"。** DocRole→DocClass、DocType 10→12→四层→8、RecordState 3→5→6→3，每次都留下旧数据；本次实测 22 行旧 schema 且 `IsStale=0`，就是这种模式的直接产物。

4. **两套链路并存的时间越长，退场成本越高。** 现网 95 行产物按旧契约写入，V3 一旦上线，同一文档会在两套结构里各有结论；而"哪套算数"没有定义。建议在 V3 第一条端到端通过时，同时写下旧链退场条件与时间点。

5. **验收标准不缺，缺的是排期约束。** 92 §八 的六项指标写得很专业，但 93 号仍然在 P0=7 的状态下讨论"扩到 10 条"。正确顺序是 P0 清零 → 两轮一致 → 扩量。

## 九、与上一轮"文档条款提取"提示词评估的衔接

被评估的那份提示词就是现网 `doc_clause_extract`（5,601 字节，单行转义）。结合 60–93 可得到更准确的处置意见：

| 上轮判断 | 60–93 给出的补充 | 修正后的结论 |
|---|---|---|
| `profile` 门禁与分段调用冲突 | 64 号确实主张"文档级门禁先判"，但落点在 `doc_profile`（整篇一次、10,603 字节、live） | 门禁本身没错，**位置错了**；不要再往逐条款提示词里塞第三套 |
| 字段与既有契约冲突 | 63/64/65/66 本身已有 3–4 套 DocType/Extractable 口径 | 冲突不是这份提示词引入的，而是体系性欠账；不应由它承担修复 |
| Anchor 10–40 字与 `LocateUnique` 互斥 | 现网手册已实测 71 条摘录无法唯一匹配 | 这是**在跑的**缺陷，优先级高于任何提示词改写 |
| doubts 与"禁符合性"矛盾 | V3 的 `Doubts` 已收敛为 10 个可机械校验的类型，且配套校验器 | 旧提示词的 `doubts` 应删除，疑点交给 V3 条款层 |

**处置建议**：`doc_clause_extract` **冻结，不再演进**。过渡期只做两件低风险修复：① 用真实换行重写；② 配齐 `DocCheckMode`（或同步删除代码里对它的假设）。其职责最终由 `doc_fact`（事实）+ `clause_evidence_findings`（条款）替代。
