# 64-文档通用属性与按类型提取规则-V1

## 一、问题定位（先说清“为什么还在逐条款”）

不是提示词里没写“按类型”，而是执行链上仍有三处会把文档拉回旧链：

| 位置 | 原行为 | 后果 |
|---|---|---|
| `ClauseExtractExecutor` | 在判断 `IsModePrompt` 之前先 `ResolveClausesAsync`，条款数为 0 就直接跳过 | 过程/指导/记录类本不需要条款，却被整份丢弃；或被迫走旧链 |
| `EnterpriseDocExtractionRouter.FromDocType` | 英文 `procedure` 被映射为 `work_instruction_citation` | 程序文件被当成作业指导书，输出结构不对 |
| `EnterpriseDocExtractionRouter` 默认分支 | 无法识别时回退 `legacy` | 21 份旧画像文档继续逐条款提取，手册 59 条、岗位职责 9 条、考勤 8 条都被灌条款 |

已修正：
- 模式分支前不再解析条款；`ResolveClausesAsync` 只在 `clause_full/legacy` 分支执行。
- `procedure → process_profile`，`work_instruction → work_instruction_citation`。
- 无法识别时回退 `none`，不再回退 `legacy`；逐条款只保留给手册。
- 文件名“作业指导/操作规程/指导书”统一为 `work_instruction_citation`。

> 注意：21 份旧画像文档的 `ContentJson.Clauses` 仍是旧产物；代码修正只影响下一次重提取，历史数据必须重提才会变。

## 二、通用关键属性（所有文档必须先落这一层）

通用属性是“文档级门禁”，不依赖标准全文，不按条款数展开。所有类型共用同一组字段名，写在 `ContentJson.ModeOutput` 根节点，并回写 `cert_enterprise_doc.DocProfileJson`。

| 字段 | 必填 | 类型 | 取值/说明 | 用途 |
|---|---|---|---|---|
| `DocTitle` | 是 | string | 文档标题，取封面/首页/页眉，不取文件名拼音 | 报告引用、同名文档区分 |
| `DocType` | 是 | enum | `manual / procedure / work_instruction / policy / record / audit_record / review_record / context_list / document_control / index / other / irrelevant` | 决定提取模式与报告深度 |
| `StandardRelevant` | 是 | bool | 是否与当前 GB/T 标准相关 | false 时不进入检查上下文 |
| `Extractable` | 是 | bool | 是否有可提取内容（扫描件、纯图片、空表为 false） | false 时只留元数据，不调用深层提取 |
| `ExtractReason` | 是 | string | ≤40 字，说明相关/可提取/不相关的原因 | 人工复核、排查误判 |
| `ProcessArea` | 是 | enum | `GM/MR`、`行政人事`、`销售过程`、`采购过程`、`生产过程`、`检验过程`、`仓储/设备`、`未标注`；必须按文档实际归属选一个 | 按过程域过滤证据；大章节必须落 |
| `OwnerDept` | 是 | string | 必须来自企业真实部门；报告受审六部门：管理层、销售部、生产部、采购部、综合部、品质部 | 按部门过滤；没有则填“未标注”并进 Warnings |
| `SupportDepts` | 否 | array | 实际参与部门；只写原文出现的真实部门 | 跨部门过程、接口证据 |
| `DeptSource` | 否 | string | `封面/审批栏/职责章节/正文责任描述/文件名` | 解释部门来源，便于复核 |
| `DocUse` | 是 | enum | `framework / requirement / operation / evidence / policy / audit_record / reference / context / document_control / irrelevant` | 文档在报告中的使用方式 |
| `ReportRole` | 是 | enum | `framework / supporting_requirement / operation_basis / evidence_source / management_requirement / audit_evidence / index / context_evidence / document_control_evidence / none` | 报告角色 |
| `ReportDepth` | 是 | enum | `framework / verbatim / summary / citation / sample / table_sample / metadata / index / none` | 报告写多深 |
| `ReportUse` | 是 | string | ≤100 字，一句话说明“报告拿它证明什么/怎么用” | 最终提示词的直接输入 |
| `PrimaryClauses` | 是 | array | 只写叶子条款；非手册 1–3 条，手册可多条 | 主归属条款 |
| `SupportClauses` | 否 | array | 只写正文确实覆盖的支撑条款；非手册 0–6 条 | 支撑条款 |
| `ClauseBasis` | 否 | string | 条款来自“正文明确条款号/职责映射/过程推断” | 防止模型乱挂条款 |
| `ReportSummary` | 是 | string | ≤100 字；手册可 1–2 句，其他 1 句 | 检查上下文的第一层摘要 |
| `Confidence` | 是 | number | 0–1 | 低置信度进入人工复核 |
| `Warnings` | 否 | array | 缺失部门、类型不确定、扫描件、表格无表头等 | 前端提示与重提依据 |

### 2.1 必填校验顺序

1. `DocType` 必须命中枚举；不命中 → 直接拒收，不让模型“猜”。
2. `StandardRelevant=false` → 保留 `DocType/Extractable/ExtractReason`，其余不再要求，检查上下文不引用。
3. `Extractable=false` → 只保留元数据、`ReportUse`、`Warnings`，不进入条款映射。
4. `ProcessArea` / `OwnerDept` / `DocUse` / `ReportRole` / `ReportDepth` 任一为空 → 输出 `Warnings`，该文档不得进入检查上下文。
5. `PrimaryClauses` 必须是叶子条款；父条款（4.4、5.1、5.2、6.1、6.2、7.1.5、7.5.3、8.2、8.4、8.7、9.2、10.2）不得作为 primary。
6. `ReportUse` 不能写“见全文/详见文档/按标准要求”，必须写报告具体怎么用。

## 三、按类型提取规则（具体实现）

### 3.1 总表

| DocType | 提取模式 | 是否逐条款 | 报告深度 | 必须产出 | 明确禁止 |
|---|---|---|---|---|---|
| `manual` | `clause_full` | 是，唯一允许逐条款的类型 | `framework` / `verbatim` | 章节框架、条款覆盖、方针目标、职责、删减说明 | 把手册全文复制进检查上下文 |
| `procedure` | `process_profile` | 否 | `summary` / `citation` | 1 句摘要、3–6 个关键控制点、1–3 主条款、记录指针 | `Processes/Activities/Inputs/Responsibilities` 全展开；把提到的所有条款都写 primary |
| `work_instruction` | `work_instruction_citation` | 否 | `citation` | 名称、用途、3–8 关键步骤/参数、验收准则、记录 | 复制完整作业步骤；按过程链展开 |
| `policy` | `policy_profile` | 否 | `summary` / `verbatim` | 目的/范围、发布/生效、责任部门、3–8 条关键规则、相关记录 | 当文件控制证据；逐条款转述 |
| `record` | `record_profile` | 否 | `sample` / `table_sample` | 1–3 条抽样、字段、日期/批次/人员/结论、关联过程/条款 | 整张表搬运；把空表当已执行证据 |
| `audit_record` | `audit_profile` | 否 | `verbatim` | 审核/评审类型、日期、审核员、范围、3–8 条发现、结论、NC | 替代 8.5.1 一线记录；判断体系符合性 |
| `review_record` | `audit_profile` | 否 | `verbatim` | 评审输入/输出、参会人、结论、改进项 | 当成普通会议记录 |
| `context_list` | `context_list` | 否 | `table_sample` | 3–12 条因素/相关方、影响、监视方式、评价、责任部门 | 当 7.5.3 文件控制证据 |
| `document_control` | `document_control` | 否 | `metadata` | 编制/审核/批准、版本、生效日期、分发/回收、目录数量、前 N 条 | 逐条输出长清单 |
| `index` | `index_only` | 否 | `index` | 文件名、编号、版本、目录结构 | 产出事实、进入审核发现主表 |
| `other` | `none` | 否 | `none` | 类型、标题、原因 | 逐条款 |
| `irrelevant` | `none` | 否 | `none` | 不调用 LLM，直接跳过 | 任何提取 |

### 3.2 手册 `manual`

- **唯一逐条款类型**。输入标准条款 Markdown，按叶子条款输出 `ClauseNumber / Title / RequirementSummary / OrganizationEvidence / CoverageStatus`。
- `ReportDepth=framework`；报告主要用它确定章节框架、方针目标、职责、删减说明。
- 手册中的“方针/目标/职责”可抽 `PolicyStatements / Objectives / Responsibilities`，供 5.2/5.3/6.2 直接引用。
- 不要求每条款都长；无内容条款标 `not_applicable` 或 `not_described`，不硬编。

### 3.3 程序 `procedure`

输出结构：
```json
{
  "DocType": "procedure",
  "DocTitle": "生产和服务提供控制程序",
  "StandardRelevant": true,
  "Extractable": true,
  "ProcessArea": "生产过程",
  "OwnerDept": "生产部",
  "SupportDepts": ["品质部"],
  "DocUse": "requirement",
  "ReportRole": "supporting_requirement",
  "ReportDepth": "summary",
  "ReportSummary": "规定生产计划、工序控制、标识追溯和不合格处置要求，由生产部执行。",
  "PrimaryClauses": ["8.1"],
  "SupportClauses": ["8.5.1", "8.5.4", "8.5.6"],
  "KeyControls": [
    {"Control": "生产计划审批后下达，按工序组织生产", "Clause": "8.1", "Record": "生产计划"},
    {"Control": "关键工序按作业指导书操作并保留记录", "Clause": "8.5.1", "Record": "工序生产记录"}
  ],
  "EvidencePointers": ["生产计划", "工序生产记录", "产品标识卡"],
  "RelatedDocs": [{"DocName": "外部提供过程产品服务控制程序", "RelatedClause": "8.4"}],
  "ReportUse": "作为 8.1 管理要求引用；现场再抽生产计划和工序记录验证执行。"
}
```
硬规则：
- `KeyControls` 3–6 条，每条只写一个控制点，≤60 字。
- `PrimaryClauses` 1–3 条；`SupportClauses` 0–6 条；不得把正文提到的所有条款都写 primary。
- 不输出 `Processes / Activities / Purpose / Scope / Inputs / Responsibilities / Equipment / Parameters / AcceptanceCriteria / OutputRecords / ClauseLinks`。
- 不写符合/不符合/充分/缺失/建议。

### 3.4 作业指导书 `work_instruction`

输出：`DocTitle / ProcessArea / OwnerDept / ApplicableProcess / KeySteps[3–8] / Parameters / AcceptanceCriteria / Records / PrimaryClauses[0–2] / ReportUse`。
- 报告只引用名称和关键步骤，不复制全文。
- `KeySteps` 每条 ≤50 字；参数只保留会影响符合性的数值/范围。
- 找不到验收准则写空数组，不推断。

### 3.5 制度 `policy`

输出：`DocTitle / Issuer / EffectiveDate / OwnerDept / Scope / KeyRules[3–8] / RelatedRecords / PrimaryClauses[0–2] / ReportUse`。
- 报告用它是“企业已建立管理规则”的证据，不是文件控制证据。
- `KeyRules` 只写可审核的规则，不写口号。
- 方针/目标归 `policy`，`ReportDepth=verbatim` 时可保留原句，但不逐条款。

### 3.6 记录 `record`

输出：`DocTitle / FormCode / OwnerDept / ProcessArea / SampleRows[1–3] / Fields / LinkedProcess / PrimaryClauses[0–2] / ReportUse`。
- `SampleRows` 必须包含日期、批次/单号、填写人/确认人、结论；没有就写 `Warnings`。
- 一张空表只能证明“表单已建立”，不能证明“已执行”；`ReportUse` 必须区分。
- 不整张表搬运；最多 3 行抽样。

### 3.7 内审/管理评审 `audit_record / review_record`

输出：`AuditType / AuditDate / Auditors / Scope / Findings[3–8] / Conclusions / NcItems / PrimaryClauses`。
- 内审 `PrimaryClauses` 9.2；管理评审 9.3.1。
- 报告可近原文引用发现，但不替代一线过程记录。
- 不判断体系符合性，只提取活动事实。

### 3.8 组织环境/相关方 `context_list`

输出：`Entries[3–12]`，每条含 `Factor / Type(外部/内部/相关方) / Impact / MonitorMethod / ReviewMethod / OwnerDept / Source`。
- `PrimaryClauses` 4.1；相关方需求和期望可加 4.2。
- 报告用表格抽样，不逐条全文搬运。

### 3.9 文件控制 `document_control`

输出：`DocTitle / DocKind / PreparedBy / ReviewedBy / ApprovedBy / Version / EffectiveDate / Distribution / CatalogCount / CatalogSample[前 10–20 条] / PrimaryClauses`。
- `PrimaryClauses` 7.5.2 / 7.5.3。
- 报告证明“文件已建立、已受控、谁批准、何时发布、包含哪些文件”；不逐条输出长清单。

### 3.10 索引 `index`

输出：`DocTitle / IndexType / Entries[文件名/编号/版本] / PrimaryClauses=[]`。
- `ReportRole=index`，不产出事实，不进入审核发现主表。

## 四、代码实现映射

### 4.1 路由

`EnterpriseDocExtractionRouter`：
- 明确模式优先：`DocProfileJson.ExtractionMode` → `DocType` → 文件名 → `none`。
- `clause_full` 仅 `manual` 或显式 `ExtractionMode=clause_full`。
- `procedure` → `process_profile`；`work_instruction` → `work_instruction_citation`；`policy/方针/目标` → `policy_profile`。
- 未知 → `none`，不再 `legacy`。

### 4.2 执行器

`ClauseExtractExecutor`：
1. 读取 Markdown、标准、缓存。
2. 先算 `extractionMode`。
3. `none` → 跳过。
4. `IsModePrompt` → 直接 `ExecuteModePromptAsync`，**不解析条款**。
5. 只有 `clause_full/legacy` 才 `ResolveClausesAsync`、分块、逐条款。
6. 模式产物写 `ModeOutput`，`Clauses=[]`；`MergeModeOutputProfileAsync` 回写 `DocType/ProcessArea/OwnerDept/DocUse/ReportRole/ReportDepth`。

### 4.3 提示词

现有 Id=9–16 的 8 个提示词统一加“通用属性块”，放在 JSON 第一层：
```json
{
  "DocType": "procedure",
  "DocTitle": "…",
  "StandardRelevant": true,
  "Extractable": true,
  "ExtractReason": "…",
  "ProcessArea": "生产过程",
  "OwnerDept": "生产部",
  "SupportDepts": ["品质部"],
  "DeptSource": "职责章节",
  "DocUse": "requirement",
  "ReportRole": "supporting_requirement",
  "ReportDepth": "summary",
  "ReportUse": "…",
  "PrimaryClauses": ["8.1"],
  "SupportClauses": ["8.5.1"],
  "ReportSummary": "…",
  "Confidence": 0.86,
  "Warnings": []
}
```
随后才是该类型的专属字段。**类型专属字段不得覆盖通用字段**。

新增 `doc_gate`（Id=17，可选）：只对 `Doc Profile` 无法判断类型的文档调用，输入文件名、目录、Markdown 前 4k 字和标题列表，输出 `DocType/StandardRelevant/Extractable/ProcessArea/OwnerDept/DocUse/ReportRole/ReportDepth`；不让它读标准全文。

### 4.4 校验

`DocExtractGuard`：
- 校验 `DocType` 枚举、必填字段、部门来源。
- `StandardRelevant=false` 或 `Extractable=false`：保留元数据，`ReportRole=none`。
- `PrimaryClauses` 父条款过滤；非手册 primary >3 条降为 support。
- `ProcessArea` 不在枚举 → `未标注` + Warnings。
- `OwnerDept` 不在真实部门 → 保留原文 + Warnings，不静默改成“各部门”。

### 4.5 检查上下文

`CertCheckContextBuilder`：
- 先按 `ProcessArea` + `OwnerDept` 过滤，再按条款匹配。
- `Clauses` 为空时使用 `ModeOutput`：`ReportSummary + ReportUse + KeyControls/KeySteps/SampleRows/Entries`。
- 手册仍走 `Clauses`；其他类型不再要求 `Clauses`。
- 报告提示词只接收“通用属性 + 类型摘要 + 3–6 条关键点”，不接收长文档全文。
