> 已按真实库表核对：**大部分能力已有表**，本文件明确"用哪张表、哪个字段、还缺什么"，不做重复造表。

## 零、一页总览

```
① 条款层（与机构无关，一次建好，长期不变）
   cert_iso_standard  ──┬── cert_iso_clause（条款原文/标题）
   cert_standard_card  │        │
                       │        ├── cert_clause_attr（属性值，按标准实例化）
                       │        └── cert_clause_align（跨标准对齐 A/B/C）
                       └── cert_prompt_template（CLAUSE_PROFILE_V1）

② 文档层（与机构无关，上传即跑）
   cert_enterprise_doc → 转换 → cert_enterprise_doc_profile（画像/分类）
                                → cert_document_extraction（按型提取）
                                → cert_doc_fact（事实条目，扁平化）

③ 任务层（由审核计划驱动）
   cert_audit_plan_detail（部门×条款×审核员）
        → cert_task_item（检查项 CheckItemCode）
        → cert_task（一次勾选 = 一个任务）+ cert_expert_task_queue（队列）

④ 生成层（机构风格在此分叉）
   cert_prompt_template(EVIDENCE_*_V1, ScopeKey=OrgCode)  ← 机构差异唯一落点
        → 事实条目 + 条款属性 + 案例示例 → LLM → cert_evidence + cert_check_result

⑤ 控制层（防覆盖）
   cert_check_analysis（指纹/快照/IsCurrent）
   cert_check_lock（锁定）
   cert_task_item（EvidenceState / SkipLocked / RunMode）
```

一句话概括规则：**条款与文档两层永远与机构无关；机构差异只在生成层；锁定与指纹保证"人工改过的不会被覆盖"。**

## 一、属性池设计

### 1.1 两层结构（沿用现有表，不新建）

| 层 | 表 | 含义 | 现状 |
|---|---|---|---|
| 定义层 | `cert_clause_attr_def` | 属性有哪些、什么类型、取值域 | 已有 8 条 |
| 实例层 | `cert_clause_attr` | 某标准某条款该属性的值 | 已有表，0 行 |
| 标准口径卡 | `cert_iso_standard.Description` | 每标准一份：目的/术语/义务动词/侧重点 | 复用现有列 |

**唯一键**：`cert_clause_attr` = (`StandardCode`, `ClauseCode`, `AttrCode`)；`AttrCode` 指向 `cert_clause_attr_def.Code`。

### 1.2 定义层：8 条已有 + 3 条要补

| AttrCode | 属性名 | 类型 | 值域 | 现状 |
|---|---|---|---|---|
| `ClauseIntent` | 条款作用 | text | — | 已有 |
| `Obligation` | 约束强度 | dict | clause_obligation | 已有 |
| `Applicability` | 适用性 | dict | clause_applicability | 已有 |
| `ApplicabilityCondition` | 适用条件 | text | — | 已有 |
| `Process` | 过程域 | json | process_domain | 已有 |
| `Artifacts` | 企业应提供的资料 | prompt | — | 已有 |
| `EvidenceChain` | 证据链要求 | prompt | — | 已有 |
| `Severity` | 严重度 | dict | clause_severity | 已有 |
| **`EvidenceForm`** | **证据形态（A–F）** | dict | evidence_form | **要补，Sort=90** |
| **`MergeMode`** | **合并方式** | dict | merge_mode | **要补，Sort=100** |
| **`DocCheckMode`** | **文档核对方式** | dict | doc_check_mode | **要补，Sort=85** |

补 3 个字典：`evidence_form`（A 文件/B 制度/C 台账/D 记录/E 结论/F 现场）、`merge_mode`（by_clause / by_standard / standalone）、`doc_check_mode`（required / optional / none）。

### 1.3 条款原文和"要求列"为什么不做成属性

09 号曾把 `ClauseText` 列进属性，这里纠正：

| 内容 | 归属 | 理由 |
|---|---|---|
| 条款原文 | **条款本体**（`cert_iso_clause`） | 一条条款只有一份原文，做成 attr 会变成 320 行冗余 |
| a/b/c 分项 | 条款本体 | 同上 |
| 机构问句版（要求列） | **风格层**（`cert_prompt_template` / 机构包） | 同一句 4.1，ACM 写"列举组织如何确定…吗？"，别家写法不同 |

`cert_iso_clause` 现有 `Title`、`Description`，但 `Description` 不是完整原文。**建议新增列 `ClauseText` text + `ClauseItems` json**；若不愿改表，则新建 `cert_iso_clause_text`（1:1）。

### 1.4 值怎么来（生成规则）

| 属性 | 生成方式 |
|---|---|
| `ClauseIntent` | 模型：看条款原文写一句"这条要求组织做什么" |
| `Obligation` | **规则**：正则统计"必须/应/宜/可"，取最高频且与分项一致（不用模型） |
| `Applicability` / `Condition` | 模型 + 规则校验（"适用时/如果/当"→ conditional） |
| `Process` | 模型给候选 → **必须落进 process_domain 字典**，否则丢弃 |
| `Artifacts` / `EvidenceChain` | 模型生成（长文本，作为提示词片段） |
| `Severity` | 模型给基线 → 人工可改 |
| `EvidenceForm` | **规则优先**：由章号 + 义务动词 + Artifacts 类型推断，模型兜底 |
| `MergeMode` | **规则**：查 `cert_clause_align` 的 A/B/C 决定 |
| `DocCheckMode` | 人工登记为主（现场类条款给 none） |

关键原则：**能用规则算的绝不调模型**（Obligation、MergeMode、EvidenceForm），否则 320 次调用里一半是浪费。

## 二、条款挂接关系

### 2.1 挂接的四个键

| 关系 | 表 | 键 |
|---|---|---|
| 标准 → 条款 | `cert_iso_clause` | `StandardCode` + `ClauseNumber`（`ClauseCode` 为代理键） |
| 条款 → 属性 | `cert_clause_attr` | `StandardCode` + `ClauseCode` + `AttrCode` |
| 条款 ↔ 条款（跨标准） | **`cert_clause_align`（新表）** | `StandardCode` + `ClauseCode` + `AlignType` |
| 条款 → 过程域 | `cert_clause_attr.Process` | 多值 json |

**铁律：所有业务主键都是"标准 + 条款"，不用条款号单键。** 因为 6.1.2 在 9001/24001/45001 是三个不同东西。

### 2.2 `cert_clause_align`（新表，约 60–80 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `StandardCode` / `ClauseCode` | varchar | 本条 |
| `AlignType` | varchar(8) | `A_same` 同义 / `B_diff` 不同义 / `C_cross` 跨号对应 |
| `PeerStandardCode` / `PeerClauseCode` | varchar | 对应方（C 类必填） |
| `MergeAllowed` | int | 1/0，是否允许按号合并 |
| `Note` | varchar | 差异说明，如"本条为环境因素，非危险源" |

内容按 10 号的对齐表灌入，典型行：

| 条款 | AlignType | MergeAllowed | Note |
|---|---|---|---|
| 6.1.2 | B_diff | 0 | 9001 风险机遇 / 24001 环境因素 / 45001 危险源 |
| 8.2 | B_diff | 0 | 9001 产品服务要求 / 24001+45001 应急准备 |
| 9.1.2 | B_diff | 0 | 9001 顾客满意 / 24001+45001 合规性评价 |
| 4.1 / 4.2 / 9.2 / 9.3 | A_same | 1 | 三标准同义，可合并加括注 |
| 7.1.5 ↔ 9.1.1 | C_cross | 0 | 9001 监视测量资源对应 24001/45001 的 9.1.1 |

### 2.3 挂接后的三道校验（灌完必跑）

| 校验 | 判据 | 不通过怎么办 |
|---|---|---|
| 同号不同义 | `B_diff` 条款的 `ClauseIntent` 与对标准相似度 <0.8 | 打回重生成 |
| 义务动词 | `Obligation` 与条款原文统计一致 | 以原文为准，覆盖模型值 |
| 分布校验 | 每标准 80 条全部有 11 个属性，空值率 <5% | 列出缺失清单重跑 |

## 三、条款提示词（与机构完全无关）

### 3.1 落点

| 项 | 值 |
|---|---|
| 表 | `cert_prompt_template` |
| `PromptCode` | `CLAUSE_PROFILE_V1` |
| `ScopeKey` | `GLOBAL`（跨机构共用，不受机构影响） |
| `Template` | 见 3.2 |
| `Placeholders` | `{std_card}` `{std_code}` `{std_name}` `{clause_number}` `{clause_title}` `{clause_text}` `{clause_items}` `{peer_hint}` |

### 3.2 提示词模板（一条通吃四标准，逐条执行）

```
你是体系认证条款分析助手。给你一个标准及其条款原文，请输出该条款的结构化属性。
只输出 JSON，不要解释。所有判断必须能在条款原文中找到依据。

【标准身份】{std_code} {std_name}
【标准口径卡】
{std_card}
（口径卡含：本标准目的、义务动词习惯、术语替换、与其他标准同号条款的差异提醒）

【条款】{clause_number} {clause_title}
【条款原文】
{clause_text}
【分项】
{clause_items}
【同号差异提示】{peer_hint}
（如："本条在 24001 中为'环境因素'，在 45001 中为'危险源辨识'，勿混用"）

【逐项要求】
1. ClauseIntent：一句话说清"这条要求组织做什么"，不超过 30 字。
2. Obligation：从原文判断约束强度，取 shall/should/may/note 之一。
3. Applicability：general（无条件适用）或 conditional（有条件适用）。
4. ApplicabilityCondition：仅 conditional 时填写条件（引用原文表述）。
5. Process：从下列固定值域中选 1–3 个，不得自造：
   management/design/purchase/production/inspection/metrology/warehouse/
   sales/after_sales/hr/env_safety/other
6. Artifacts：企业应提供哪些资料来证明符合，逐条列（≤6 条，写成资料名）。
7. EvidenceChain：审核员应按什么顺序取证（观察→查文件→抽样→访谈），写成 3–5 步。
8. Severity：critical / major / minor（本条出不符合时通常的严重度基线）。
9. EvidenceForm：本条证据在报告里是什么形态，取 A/B/C/D/E/F 之一：
   A 文件型（手册原文引用） B 制度型（程序点名+概括） C 台账型（清单条目归纳）
   D 记录型（表单抽样看明细） E 结论型（管评/内审结论+日期） F 现场型（人工录入）
10. DocCheckMode：required（必须有文档证据）/ optional（有则更好）/ none（纯现场或纯访谈）

【硬规则】
- Artifacts 只能写"资料类别名"，不得编造具体文件名。
- 不得引用其他条款的内容；本条没写的不补。
- 若条款原文含"适用时/如果/当"，Applicability 必须为 conditional。
- 输出 JSON，字段名严格用上面的英文名。
```

### 3.3 输出契约（直接映射到 `cert_clause_attr` 行）

```json
{
  "ClauseIntent": "", "Obligation": "", "Applicability": "",
  "ApplicabilityCondition": "", "Process": [], "Artifacts": [],
  "EvidenceChain": [], "Severity": "", "EvidenceForm": "", "DocCheckMode": "",
  "confidence": 0.0, "basis": "原文中支撑判断的关键句"
}
```

### 3.4 调用量与成本

| 项 | 数量 |
|---|---|
| 条款数 | 4 标准约 320 条 |
| 每条一次调用 | 320 次（一次性，之后只在标准换版时重跑） |
| 单次 token | 输入约 1.5k（口径卡 300 字 + 原文 ≤600 字 + 指令）/ 输出约 400 |
| 合计 | 约 48 万输入 token、13 万输出 token |

比"一个标准灌一次 2 万 token"稳得多——后者必截断且不报错。

### 3.5 条款属性挂接队列

复用 `cert_expert_task_queue` + `cert_expert_task_queue_item`：

| 字段 | 值 |
|---|---|
| `QueueType` | `CLAUSE_ATTR` |
| `ScopeKey` | `{StandardCode}` |
| `TotalCount` | 该标准条款数 |
| `item.ItemType` | `CLAUSE` |
| `item.ItemCode` | `ClauseCode` |
| `item.Payload` | `{"standardCode":"","clauseCode":"","clauseNumber":""}` |
| `item.ExtractVersionStamp` | `sha256(clauseText + stdCard + promptVersion)` |

**幂等**：跑之前比对 `ExtractVersionStamp`，相同则 `ItemStatus=Skipped`，不重复调模型。

**单条重跑**：后台页面按条款号手动触发，只入队 1 个 item。

### 4.4 分类提示词 + 六型提取提示词

**直接采用 08 号全文**（分类 1 条 + A 手册 7 处 + B 零模型 + C 零模型 + D 七类字段 + E 结论 + F 现场），此处不重复贴。要点：

| 型 | 提示词 | 调用 |
|---|---|---|
| 分类 | 1 条（JSON 输出 8 字段） | 每份 1 次（1.2k token） |
| A 手册 | 1 条（7 项定位） | 每份 1 次 |
| B 程序/三阶 | **无**（正则 + 动词映射表） | 0 |
| C 清单 | **无**（表格/行解析） | 0（列头不明时 1 次） |
| D 记录 | 1 条（字段清单 + 原文 evidence） | 仅规则失败时 |
| E 结论 | 1 条（结论句/日期/依据/要素） | 每份 1 次 |
| F 现场 | **无**（人工登记） | 0 |

### 4.5 空表/扫描件必须先判（否则报告会编）

| 条件 | 判定 | 处理 |
|---|---|---|
| 字 < 60 且无图 | 空白模板 | 只写"已建立表单"，不进抽取句 |
| 字 < 200 且有图 | 扫描件 | OCR，失败转人工 |
| 单元格非空率 < 20% | 空白模板 | 同上 |

### 4.6 文档提取队列

| 字段 | 值 |
|---|---|
| `QueueType` | `DOC_PROFILE` / `DOC_EXTRACT`（两个队列，画像完再提取） |
| `item.ItemType` | `FILE` |
| `item.ItemCode` | `cert_enterprise_doc.Code` |
| `item.Payload` | `{"fileCode":"","sha256":"","docCategory":"","standardCodes":[]}` |
| `item.ExtractVersionStamp` | `sha256(markdownSha + promptCode + promptVersion)` |

**幂等**：源文件没变（`SourceSha256` 相同）且提示词版本没变 → 跳过。

## 五、审核计划 → 检查项 → 证据生成队列

### 5.1 检查项从哪来（现有表已经支持）

`cert_audit_plan_detail` 现有字段：`PlanCode`、`Clauses`、`Departments`、`DeptNames`、`ClauseNumbers`、`OwnerCode`、`OwnerName`。

**一行 = 一个检查项 =（部门 × 条款 × 审核员）**，展开生成 `cert_task_item`（`CheckItemCode`）。

这意味着：**"同一条款在多部门分别出证据"天然支持**，不需要给 `cert_evidence` 加 `DeptCode`——部门通过 `CheckItemCode → cert_audit_plan_detail.Departments` 反查即可。

> 前提：审核计划编排时把"条款×部门"拆成多行（而不是一行多个部门）。若保留一行多部门，则需在生成时按部门拆成多个虚拟检查项。**建议前者**，实现最简。

### 5.2 任务与队列

| 概念 | 表 | 说明 |
|---|---|---|
| 一次"全部生成" | `cert_task`（`TaskKind=EVIDENCE_GEN`，`QueueCode`，`ItemTotal/Done/Failed/Skipped`） | 一个任务对应一次勾选批量 |
| 单个检查项生成 | 不入 `cert_task`，直接调生成服务 | 或入单 item 任务，二选一 |
| 队列 | `cert_expert_task_queue`（`QueueType=EVIDENCE_GEN`） | 支持暂停/续跑/重试 |
| 队列项 | `_queue_item`（`ItemType=CHECK_ITEM`，`ItemCode=CheckItemCode`） | 每项独立状态 |

`cert_task_item` 现有 `RunMode`、`SkipLocked`、`EvidenceState`、`AnalysisState`、`AnalyzeCount`，正好承载"单跑/全跑/跳过锁定"。

### 5.3 单个检查项的生成八步

```
1 取检查项：CheckItemCode → plan_detail（部门、条款、审核员、阶段）
2 取条款侧：该条款的 11 个属性 + ClauseText（多标准时按 cert_clause_align 决定合并/分段）
3 取事实侧：cert_doc_fact 按 (EnterpriseCode, ProcessDomain/DeptHint, ClauseHints) 检索
             + cert_document_extraction 里该 FileCode 的元信息（文件名/编号/版本）
             + 空白/扫描件标记（决定能不能写"抽看"）
4 选骨架：按 EvidenceForm（A–F）取对应句式模板（属于生成层，不含机构信息）
5 选机构风格：按任务所属机构取 EVIDENCE_*_V1 风格包（句式/结论词/要求列/合并策略）
6 取案例示例：按 (ClauseCode, DeptCode, EvidenceForm) 检索 3–5 条 ACM 真实句，作 few-shot
7 调模型：输出证据文本 + 使用的事实清单 + 缺口清单
8 校验与落库：
   - 事实溯源：句子里的事实点必须能在 cert_doc_fact 找到（找不到即判编造，重试或降级）
   - 写 cert_evidence（每条事实一条证据，ContentMD5 记指纹）
   - 写 cert_check_result（PrepState/Conclusion 初值）
   - 写 cert_check_analysis（指纹、输入快照、token、耗时）
```

### 5.4 输入快照（用于比对与复现）

`cert_check_analysis.InputSnapshotJson` 存：

```json
{"clauseCodes":["8.5.1"],"standardCodes":["9001"],"dept":"PROD",
 "factCodes":["F001","F017","F033"],"docCodes":["DOC012","DOC045"],
 "promptCode":"EVIDENCE_ACM_V1","promptVersion":"3",
 "styleOrg":"ACM","mergeMode":"by_clause","exampleCodes":["EX221","EX305"]}
```

这份快照就是"这次生成用了什么"的唯一证据，排查与回滚都靠它。

## 六、机构差异：只在生成层，做多套方案

### 6.1 分层原则

| 层 | 是否含机构信息 |
|---|---|
| 属性池 / 条款提示词（`CLAUSE_PROFILE_V1`） | **不含** |
| 文档分类与提取（`DOC_PROFILE_V1` / `DOC_EXTRACT_*`） | **不含** |
| 认证证据提示词（`EVIDENCE_*`） | **含，一套机构一个方案** |

### 6.2 机构风格包（`cert_prompt_template`，`ScopeKey=OrgCode`）

| 组成 | 内容 |
|---|---|
| `PromptCode` | `EVIDENCE_ACM_V1`（机构缩写 + 版本） |
| 句式模板 | 按 EvidenceForm × 章号给出，如 D 型 8 章："抽看 N 份{资料}，{明细}，{结论}" |
| 结论词表 | 符合/有效/适宜/正常运行/未发现不符合（机构偏好固定） |
| 要求列策略 | `use_question`（用机构问句）/ `use_clause_text`（用国标原文）/ `none`（不输出） |
| 合并策略 | `by_clause`（跨标准同号合成一段，科斯亚）/ `by_standard`（分标准分段，双尼部分页） |
| 段落顺序与标题 | 4→10 章顺序、每章是否加小标题、字号层级 |
| 字数上限 | 单段 ≤120 字（ACM 实测中位 26 字，长段 ≤120） |

### 6.3 多方案并存

- 同一机构可有多个方案（不同审核类型：初次/监督/再认证，或换版过渡）；
- 任务创建时选定 `PromptCode + PromptVersion`，写入 `cert_task`；
- 切换方案**不影响已生成的证据**，但会让指纹变化 → 标 `ResultStale`，提示"方案已切换，是否重跑"。

## 七、锁定与重跑（核心防覆盖）

### 7.1 三级状态（现有字段就够）

| 级别 | 存储 | 含义 |
|---|---|---|
| 证据状态 | `cert_task_item.EvidenceState` | 无 / 已收集 / 已失效 |
| 分析状态 | `cert_task_item.AnalysisState` | 未跑 / 已跑 / 失败 / 跳过 |
| 锁定 | `cert_check_lock.IsActive`（按 `CheckItemCode`） | 锁定后不允许覆盖 |

### 7.2 指纹的构成（决定"要不要重跑"）

```
EvidenceFingerprint = sha256(
    sorted(cert_evidence.ContentMD5 of 该检查项)
  + promptCode + promptVersion
  + sha256(InputSnapshotJson 里的事实/文档/示例清单)
)
```

存 `cert_check_analysis.EvidenceFingerprint`。**指纹相同 = 结果可复用，不重跑。**

### 7.3 规则矩阵（勾选 × 锁定 × 指纹）

| 场景 | 锁定 | 指纹变化 | 行为 |
|---|---|---|---|
| 首次生成 | 否 | — | 正常生成 |
| 再次勾选，什么都没变 | 否 | 否 | **跳过**，沿用旧结果（`ItemStatus=Skipped`，原因 `no_change`） |
| 再次勾选，新增了文档 | 否 | 是 | 重新生成，写 `RunNo+1`，旧分析 `IsCurrent=0` |
| 审核员改过证据并锁定 | **是** | 无关 | **跳过**，`SkipLocked` 生效，原因 `locked`，页面提示"已锁定，未覆盖" |
| 锁定但证据有新增 | 是 | 是 | **不覆盖**，只标 `ResultStale=1` + `StaleReason`，页面提示"有 N 条新证据，建议解锁重跑" |
| 主动重跑单条 | 是 | — | 需先解锁（`IsActive=0` 再 `LockedBy` 记录），或勾选"强制覆盖" |
| 解锁后勾选 | 否 | 是 | 重新生成，覆盖证据，保留 `cert_check_analysis` 历史（`IsCurrent=0`） |

一句话：**锁定优先于一切；指纹只决定"没锁定时要不要重跑"。**

### 7.4 人工修改 → 自动锁定

| 触发 | 行为 |
|---|---|
| 审核员在页面编辑证据文本 | 写 `cert_evidence.IsManualCorrected=1`（`cert_enterprise_doc_profile` 同名字段为同一模式）+ 自动插入 `cert_check_lock`（`LockSource=manual_edit`，`LockReason`=修改类型） |
| 审核员只改结论（符合/不符合） | 锁 `cert_check_result`（同一锁表，`LockSource=conclusion_edit`） |
| 审核员显式"锁定本条" | `LockSource=manual_lock` |
| 审核员显式解锁 | `IsActive=0`，`UnlockedBy/UnlockedAt` 留痕 |

锁**不删历史**：`cert_check_analysis` 保留历次 `RunNo`，可回溯"改之前模型写的是什么"。

### 7.5 生成前的守卫（防止覆盖的唯一实现点）

```
if lock.IsActive and not forceOverwrite:
     item.ItemStatus = Skipped; item.Payload.reason = "locked"
     if fingerprintChanged: check_result.ResultStale = 1
     return   ← 绝不写 cert_evidence / 绝不改 Conclusion
```

这条守卫必须放在**服务层最前面**，不能放在提示词里，也不能靠页面控制。

## 八、状态机

### 8.1 队列项

```
Pending → Processing → Completed
                     ↘ Failed → (RetryCount<Max) Pending
                              → (超限) FailedFinal
                    ↘ Skipped（no_change / locked / not_applicable）
```

### 8.2 检查项

| `EvidenceState` | 含义 | 转移 |
|---|---|---|
| `empty` | 无证据 | 生成成功 → `ready` |
| `ready` | 已生成 | 证据变更 → `stale` |
| `stale` | 已失效 | 重跑 → `ready` |

| `AnalysisState` | 含义 |
|---|---|
| `none` | 未跑 |
| `done` | 已跑且指纹有效 |
| `failed` | 跑失败 |
| `skipped` | 跳过（锁定/无变化） |

### 8.3 结论

`cert_check_result.Conclusion`（人工）与 `AiConclusion`（模型）分离；`AiConclusion` 永不覆盖 `Conclusion`。`SeveritySource` 记录严重度是人定还是模型基线。

### 10.1 已有、可直接用

### 10.2 缺的（本设计要补）

| # | 缺口 | 建议 |
|---|---|---|
| 1 | `cert_clause_attr_def` 只有 8 条，缺 `EvidenceForm`/`MergeMode`/`DocCheckMode` | 补 3 条 + 3 个字典 |
| 2 | 条款无完整原文 | `cert_iso_clause` 加 `ClauseText` text、`ClauseItems` json（或新建 1:1 表） |
| 3 | 无跨标准对齐关系 | 新建 `cert_clause_align`（60–80 行） |
| 4 | 提取结果只有大 JSON，无法按条款/部门检索 | 新建 `cert_doc_fact`（扁平事实表） |
| 5 | 机构风格包无结构化字段 | `cert_prompt_template.Template` 存 JSON schema 化风格包（见 6.2） |
| 6 | `cert_check_result` 无 `TaskCode` | 可由 `AnalysisCode → cert_check_analysis.TaskCode` 反查，暂不加列 |
| 7 | `cert_evidence` 无 `DeptCode` | 由 `CheckItemCode → plan_detail.Departments` 反查，暂不加列 |

**结论：真正要新建的只有 2 张表（`cert_clause_align`、`cert_doc_fact`）+ 1 个字段（`ClauseText`）+ 3 条属性定义。** 其余全部复用。

## 十一、分期

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 补 3 条属性 + 条款原文 + 对齐表；跑 320 条条款属性 | 每标准 80 条全属性、空值 <5%、同号不同义校验通过 |

| P3 | 机构风格包 + 锁定 + 指纹 + 重跑守卫 | 改一条 → 锁定 → 再勾选不覆盖；新增文档 → 指纹变 → 未锁项重跑 |
