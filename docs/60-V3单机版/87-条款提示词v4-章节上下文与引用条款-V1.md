# 条款提示词 v4.2：章节上下文、条款范围与引用条款

## 一、结论

你提的四点，v4.2 已全部落进提示词结构，不再靠“用户先合并条款”：

| 你的要求 | v4.2 的处理 |
|---|---|
| 1. 不指望用户合并；引用条款要带进来一起分析 | 新增 `ReferencedAnalysis`；正文每个“见 X.X”必须解析，引用条款正文随输入传入；引用只作条件/规则，不单独开检查项 |
| 2. 条款紧紧围绕文档 | 每个 `EvidenceItem` 增加 `DocClass / DocScope / ExtractionDepth / DocProfileKey / DocBoundary`，证据必须落到文档类型和提取深度 |
| 3. 条款范围必须清晰 | 新增 `ClauseContext`：`ScopeType / IsCheckable / CheckMode / Boundary / ClauseItems`；大标题不检查，a/b/c/d 只进 `ClauseItems` |
| 4. 每条条款归属大章节 | 输出最顶部新增 `ChapterContext`：章节意图、章节核心证据、本条款在整章的作用、章节缺口 |

试跑结果：5 条条款 **5/5 JSON_OK**，全部输出 `ClauseContext + ChapterContext + ReferencedAnalysis + EvidenceContract + ReportHint`。

提示词全文：`87-条款提示词v4.2-全文-V1.txt`（273 行 / 14,772 字节）。

## 二、v4.2 的五个硬结构

### 2.1 `ClauseContext`：先定范围，再谈证据

```json
{
  "ClauseNumber": "8.2.4",
  "ScopeType": "clause",
  "IsCheckable": true,
  "CheckMode": "single",
  "Boundary": "本条款管内部审核的策划、实施、记录与结果处置；不管过程监视、产品检验、不合格品处置的具体执行。",
  "ParentClause": "8.2",
  "ClauseItems": [
    {"ItemCode": "a", "ItemType": "requirement", "Text": "体系符合策划安排、标准要求、法规要求"},
    {"ItemCode": "b", "ItemType": "requirement", "Text": "体系得到有效实施和保持"}
  ]
}
```

规则：

- `4 / 5 / 6 / 7 / 8` 是 `chapter`，`4.2 / 7.3 / 7.5 / 8.2` 是 `section`，`8.2.4` 是 `clause`，正文 `a) b) c)` 是 `item`。
- 有子条款的标题：`IsCheckable=false`，只出 `SectionProfile`，不出 `EvidenceContract`。
- `a/b/c/d` 一律进 `ClauseItems`，⛔ 不新开条款行。
- `Boundary` 必须写“管什么、不管什么”。

### 2.2 `ChapterContext`：每条条款顶部先写整章

```json
{
  "ChapterCode": "8",
  "ChapterTitle": "测量、分析和改进",
  "ChapterIntent": "验证体系与产品是否符合要求，处置不合格，分析数据并持续改进",
  "ChapterEvidenceFocus": ["内审包", "产品检验与放行记录", "不合格品处置记录", "数据分析记录", "纠正预防措施记录"],
  "ClauseRoleInChapter": "8.2.4 是体系层面的监视证据，与 8.2.5 过程监视、8.2.6 产品监视构成三层监视结构",
  "ChapterGap": ["审核员能力/任命", "内审结果与管理评审的衔接"]
}
```

规则：

- `ClauseRoleInChapter` 必须结合整章，不许只写“本条很重要”。
- 章节核心证据来自 `ChapterProfile`，不是模型凭记忆生成。
- `ChapterGap` 只写本条相对整章缺什么，最多 2 条。

### 2.3 `ReferencedAnalysis`：引用条款带进来，但不另开检查项

```json
[
  {
    "ClauseNumber": "4.2.5",
    "Title": "记录控制",
    "RelationType": "record_rule",
    "Influence": "为审核记录补充标识、贮存、保护、检索、保存期限和处置规则；保存期从放行之日起不少于 2 年",
    "AppliedTo": ["a", "b"],
    "ReferenceStatus": "full",
    "MissingAction": ""
  }
]
```

规则：

- 正文每个“见 X.X”都必须出现在 `ReferencedAnalysis`。
- 引用条款只作当前条款的条件/规则，⛔ 不单独开检查项。
- 引用正文为空：`ReferenceStatus=missing`，⛔ 不许用“标准惯例”补。
- `ReferencedAnalysis` 与 `EvidenceContract` 分开，避免把 4.2.5 变成 8.2.4 的检查项。

### 2.4 `EvidenceContract`：证据必须落到文档类型

每个 `EvidenceItem` 新增 5 个文档字段：

| 字段 | 作用 | 示例 |
|---|---|---|
| `DocClass` | 文档大类 | `procedure / work_instruction / record / report / list / plan / manual / policy` |
| `DocScope` | 文档覆盖层级 | `system / process / product / batch / event` |
| `ExtractionDepth` | 提取深度 | `citation_only / structured / criteria / fact_profile` |
| `DocProfileKey` | 用哪套轻模型 | `manual_v1 / policy_v1 / procedure_v1 / work_instruction_v1 / record_v1 / report_v1 / list_v1 / plan_v1` |
| `DocBoundary` | 这类文档管什么、不管什么 | “该程序须规定审核方案策划、审核员选择、记录和报告职责；不覆盖单次检查表内容” |

同时保留：`Name / NameAliases / Required / Condition / ExpectedFields / Frequency / Coverage / ReportUse / ClauseItemRefs`。

这样条款侧不只是说“要什么记录”，而是说“这是什么文档、读多深、用什么模型、边界在哪”。

### 2.5 `ReportHint`：报告用法只做提示，不依赖用户合并

```json
{
  "ReportMode": "direct",
  "ReportParent": "",
  "ReportReason": "本条款是独立可检查的叶子条款",
  "ReportUse": ["establishment", "sample", "coverage"]
}
```

规则：

- 标题/范围/术语：`not_checkable`；
- 4.2.5 这类记录规则：`supporting_only`；
- 叶子条款默认 `direct`；
- 输入没有给报告映射：`unknown`，⛔ 不许自己编“合并到某条”。

## 四、仍存在的问题

### 4.1 条款号仍会被模型自行补

v4.2 已加两条硬规则：

- `Boundary` 禁止出现任何 `X.X` 条款号；
- `ClauseRoleInChapter` 只能引用 `AllowedClauseRefs`。

但实测 `7.5.1` 的 `Boundary` 仍写“不含采购过程（属7.4）、设计转换活动（属7.3.8）……”；`8.2.4` 仍写“属7.1/7.2/7.5等过程能力要求”。

结论：**光靠提示词压不住，必须在运行时加校验器**：

- 用正则抽出 `Boundary / ClauseRoleInChapter / Influence` 里的所有条款号；
- 与 `AllowedClauseRefs` 比对；
- 不在白名单的条款号直接标 `ClauseRefViolation`，不进入契约；
- 或更简单：`Boundary` 只允许业务语言，运行时不接受任何 `X.X`。

### 4.2 `8.2.6` 证据召回仍不足

v4.2 已拆出过程检验记录和成品检验记录，但仍缺：

- 过程检验规程 / 成品检验规程（`criteria` 文档）；
- 检测设备使用记录（`support`）；
- 第三方检验报告（仅法规/产品要求触发时）。

原因：条款正文只写“形成文件的安排和形成文件的程序”“适当时记录应识别检测设备”，没有直接写“检验规程”“检测设备台账”。模型没有把“接收准则”映射到 `work_instruction`，也没有把“检测设备识别”映射到 `support`。

### 4.3 `8.3.2` 缺检验类记录

v4.2 已把 a/b/c 路径拆开，但缺：

- 进货不合格检验记录；
- 过程不合格检验记录；
- 成品不合格检验记录。

原因：8.3.2 只写“处置不合格品”，不写“不合格在哪发现”。这三类记录来自 8.3.1 总则、7.4.3 采购产品验证、8.2.6 产品监视，但不是 8.3.2 的显式引用。  
处理方式：在 `Dependencies` 里加 `support` 角色，不跨成 `evidence_rule`，也不要求用户合并。

### 4.4 `ReportHint` 仍是单条直出

5 条都输出 `ReportMode=direct`。真实报告里 `7.3` 是 10 条合 1 个父块、`7.5.1` 并入 `7.5`。这不是提示词能单独解决的，仍需要 `ReportMap` 配置：

- `direct`
- `merged_parent`
- `merged_into_parent`
- `supporting_only`
- `not_checkable`

提示词只负责给 `ReportReason`，最终映射由配置决定。

### 4.5 `DocProfileKey` 从 4 个扩到 8 个

v4.2 把 `DocProfileKey` 扩为：

`manual_v1 / policy_v1 / procedure_v1 / work_instruction_v1 / record_v1 / report_v1 / list_v1 / plan_v1`

这比原来的 4 个多 4 个。需要你确认：是正式扩成 8 个，还是强行归并到 `procedure_v1 / record_v1`。我建议扩成 8 个，因为 `plan / report / list` 的轻模型和 `record` 不同，强行归并会再次出现“文档可以复杂，提示词必须简单”的反面。
