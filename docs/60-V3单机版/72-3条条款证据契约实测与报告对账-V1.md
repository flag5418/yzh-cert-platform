## 2. `4.2.5`：契约内部自相矛盾

模型输出：

```json
{
  "ClauseIntent": "组织应建立并保持程序，以控制记录的标识、收集、索引、存取、存档、维护、检索、保存期限和处置。",
  "Obligation": "shall",
  "Applicability": "general",
  "Process": ["management","inspection","production","purchase","warehouse","after_sales"],
  "Severity": "major",
  "EvidenceForm": "cite",
  "EvidenceFamily": "f1",
  "Role": "r4",
  "EvidenceContract": {
    "EvidenceType": ["procedure","list","record"],
    "EvidenceName": ["记录控制程序","记录清单","记录保存期限表"],
    "MustHaveFields": ["记录名称","标识方式","保存期限","存档方式","处置方法","责任部门","检索方法"],
    "Frequency": "未明确",
    "Coverage": "全条款",
    "Signer": ["管理者代表","文件控制负责人"],
    "JudgementRules": [
      "有成文程序 + 明确标识/保存期限/处置要求 = 符合",
      "缺保存期限或处置规定 = 部分",
      "无程序或仅标题无内容 = 缺失",
      "未覆盖委托方/顾客提供记录的保密性要求 = 不符合"
    ],
    "ReportUse": ["sample","coverage"]
  }
 }
}
```

报告事实：

- 企业建立了《记录控制程序》，规定标识、贮存、安全与完整性、检索、保存期限、处置。
- 保存期限：产品交付后 10 年；设计开发记录不少于最后一批产品生产后 10 年；其他 5 年。
- 报告引用 `OR-007/016/012` 作为“已按要求保存留档”示例。
- `QR-010` 记录清单只有名称、编号、版本、生效日期、编制部门；**没有保存期限/检索/处置列**。

对账：

- 契约的 `JudgementRules` 写“有成文程序 + 明确要求 = 符合”，报告正好用程序 + 保存期限证明，所以 **条款层结论应是 `exact`**。
- 但 `EvidenceName` 同时要求“记录清单”，`MustHaveFields` 又要求“保存期限/存档/处置/检索”，会让人误以为清单必须含这些列。**同一份契约里，程序要求和清单要求没有分开**。
- 因此 `QR-010` 的缺列应记 `report_gap`（报告没展开清单字段），不是 `C5` 企业缺证据。
- `EvidenceFamily=f1` 也偏窄：报告同时用了程序（f1）和实际保存记录（f2），应为 `f1f2`。

**这条不是模型不会判，是 `EvidenceContract` 把多个证据对象压成一个 `EvidenceName[] + MustHaveFields[]`，字段不知道属于谁。**

## 3. `8.2.4`：契约漏了报告真正用的三份证据

模型输出要点：

```json
{
  "ClauseIntent": "组织按策划的时间间隔进行内部审核以确定质量管理体系是否符合要求并得到有效实施和保持。",
  "Process": ["management"],
  "Severity": "major",
  "EvidenceForm": "cite",
  "EvidenceFamily": "f1f2",
  "Role": "r6",
  "EvidenceContract": {
    "EvidenceType": ["procedure","record","report"],
    "EvidenceName": ["内部审核程序","年度内部审核计划","内部审核报告","内部审核检查表"],
    "MustHaveFields": ["审核准则","审核范围","审核时间间隔","审核方法","审核员姓名及独立性声明","受审核区域","不合格项描述","纠正措施要求","验证结果"],
    "Frequency": "每事件",
    "Coverage": "全条款",
    "Signer": ["审核组长","管理者代表","受审核区域负责人"],
    "JudgementRules": [
      "有已发布程序+年度计划+每次审核的检查表+报告+纠正措施跟踪记录 = 符合",
      "缺审核员独立性声明/未覆盖全部过程/无纠正措施验证 = 部分",
      "仅有空白模板或无任何审核活动证据 = 缺失",
      "无内审安排且无合理暂停说明 = 不适用"
    ],
    "ReportUse": ["coverage","counter"]
  }
 }
}
```

报告事实：

- 报告明确写“组织的内审实施符合标准要求”。
- 证据段引用《内部审核计划》《内部审核检查表》《内审不合格报告》《内部质量审核报告》。
- 还写“查见内审签到表，总经理/管代和各部门负责人均参予”。
- 内审组：组长尚月永，组员王倩；报告称“内审组成员未审核本部门工作”。
- 实际 `QR-015` 计划只写组员王倩；`QR-017` 检查表出现董晶晶审生产部；`QR-019` 报告未提董晶晶。

对账：

- 契约 `EvidenceName` 只有 4 份，**漏了 `内审不合格报告`、`签到表`、`纠正措施验证记录`**，而报告恰好用了这三类证据。
- `MustHaveFields` 里的“审核员姓名及独立性声明”过强：标准要求“审核员不应审核自己的工作”，报告用“培训 + 任命 + 未审本部门”证明，不一定要一份“独立性声明”。这条应改成“审核员名单 + 分工/部门回避记录”。
- `ReportUse` 缺 `conclusion`：报告 8.2.4 有明确结论“符合标准要求”，契约只给了 `coverage/counter`。
- 文档事实与报告结论冲突：报告说名单/独立性没问题，但计划/检查表/报告名单不一致。应记 `report_gap`，不是直接判企业不符合。

**这条是 `EvidenceName` 覆盖不足 + 个别字段过强，不是报告不会写。**

模型输出要点：

```json
{
  "ClauseIntent": "对产品特性进行监视和测量以验证产品要求已得到满足",
  "Applicability": "conditional",
  "ApplicabilityCondition": "对于植入性医疗器械",
  "Process": ["inspection","production"],
  "Severity": "critical",
  "EvidenceForm": "sample",
  "EvidenceFamily": "f2",
  "Role": "r5",
  "EvidenceContract": {
    "EvidenceType": ["record"],
    "EvidenceName": ["成品检验记录","产品放行审核记录","植入性医疗器械检验人员身份记录"],
    "MustHaveFields": ["产品名称","规格型号","生产批号","检验项目","检验结果","接收准则","检验员","放行人","日期","检测设备（适当时）","检验人员身份（植入性医疗器械）"],
    "Frequency": "每批",
    "Coverage": "全产品/全批次",
    "Signer": ["检验员","放行人"],
    "JudgementRules": [
      "有已填记录 + 接收准则 + 检验结果 + 放行人 + 日期 = 符合",
      "缺放行人/日期/检测设备（适当时）/检验人员身份（植入性医疗器械） = 部分",
      "只有空白模板或无记录 = 缺失",
      "未覆盖所有批次或植入性医疗器械未单独标识检验人员身份 = 不适用"
    ],
    "ReportUse": ["sample","coverage","counter"]
  }
 }
}
```

报告事实：

- 企业手动轮椅车生产和销售，**不涉及植入性医疗器械**。
- 报告引用《过程检验记录》：2026-05-08、2026-06-15 两批，型号、工序、操作者、检验员齐全。
- 报告引用《成品检验记录》：2026-06-23、2026-05-15、2026-07-09 三批，型号、数量、检验项目、结果、检验员齐全。
- 报告结论“所有产品经过成品检验合格后入库”。
- 文件夹 `QR-027/037` 是空白模板，`QR-028` 是空白放行模板，`QR-038` 是跨产品“髓腔锉”。
- 报告没有明确写“产品放行审核记录”的实际批次；只写检验合格后入库。

对账：

- **`Applicability=conditional` 判错**：条款主句是通用要求；“对于植入性医疗器械”只是最后一段的条件子要求。企业不涉及植入器械，不应把整条判为条件适用。
- `EvidenceName` 漏了 `过程检验记录`，而报告 8.2.6 第一组证据就是过程检验。
- `EvidenceName` 把 `植入性医疗器械检验人员身份记录` 当成通用证据，实际不适用；应标为条件证据，不是必须项。
- `产品放行审核记录` 在契约中是必须项，但报告没有引用实际放行记录；文件夹只有空白模板。这可能是 `C5`（企业没有放行记录）或 `C1`（契约把“放行记录”当成必然证据，标准只要求“记录有权放行产品的人员身份”）。
- `ReportUse` 缺 `conclusion`：报告有“所有产品经成品检验合格后入库”的结论。

**这条同时暴露两个问题：条件子句被抬成整条适用性；证据对象没有“必选/条件”标记。**

## 5. 五个可复用的偏差

| 编号 | 偏差 | 影响 | 归属 |
|---|---|---|---|
| D1 | `EvidenceName[]` 与 `MustHaveFields[]` 是全局数组，字段不知道属于哪份证据 | 4.2.5 程序 vs 清单混在一起；8.2.4 计划/报告/检查表混在一起 | C4 契约结构不清 |
| D2 | 条件子句被抬成整条 `Applicability=conditional` | 8.2.6 企业不涉及植入器械，却整条判条件适用 | C1 契约期望过宽 |
| D3 | `EvidenceName` 漏报告实际用的证据 | 8.2.4 漏不合格报告/签到表；8.2.6 漏过程检验记录 | C2 契约覆盖不足 |
| D4 | `ReportUse` 漏 `conclusion` | 8.2.4/8.2.6 报告都有明确结论，契约未标 | C4 报告用法规则不清 |
| D5 | 个别字段过强/过窄 | 8.2.4“独立性声明”；4.2.5 `f1` 漏执行证据 | C1/C3 契约过严或过窄 |

> C1 契约期望过宽；C2 文档画像缺字段；C3 文档画像字段冗余；C4 匹配规则不清；C5 企业确实缺证据。

## 6. 需要你决定的事（4 件）

### 决定 1：`EvidenceContract` 要不要从“全局数组”改成“按证据对象分组”

- **A. 保持现状**：`EvidenceName[] + MustHaveFields[]` 全局数组。简单，但程序/清单/报告/检查表的字段会混在一起，4.2.5 已经出现自相矛盾。
- **B. 改成 `EvidenceItems[]`（推荐）**：一份证据一个对象，每个对象有 `Type/Name/MustHaveFields/Frequency/Signer/Required`；`JudgementRules/ReportUse` 留在契约层。顶层字段不增加，只多一层嵌套。
- **C. 先不改**：3 条手工修，等 5 条试点后再决定。

### 决定 2：`8.2.6` 的“植入性医疗器械”怎么处理

- **A. 整条 `general`，把植入器械要求作为 `EvidenceItems` 里的 `Required=false` 条件项（推荐）**。
- **B. 保留 `conditional`，企业不适用时整条标 `not_applicable`**。但这会把通用产品监视也排除，风险大。
- **C. 拆成两条契约**：通用 8.2.6 + 植入器械补充要求。实现重，暂不建议。

### 决定 3：`8.2.4` 的“审核员独立性”按什么证据判

- **A. 按标准判“审核员不应审核自己的工作”**：证据 = 审核员名单 + 分工/部门回避记录；不要求单独的“独立性声明”（推荐）。
- **B. 保留“独立性声明”**：要求企业提供单独声明，报告没有就判 `partial`。
- **C. 只记 warning**：名单不一致只进 `Warnings`，不影响条款结论。报告本身已判“符合”。

### 决定 4：`8.2.6` 的“产品放行记录”算不算必须证据

- **A. 算必须**：标准要求记录“有权放行产品的人员身份”，没有放行记录就判 `partial`；文件夹 `QR-028` 空白是证据缺口。
- **B. 不算必须**：成品检验记录里有检验员/日期，报告也写“检验合格后入库”，可视为放行证据；`QR-028` 空白只记 `report_gap`（推荐，和报告结论一致）。
- **C. 拆成两个匹配等级**：成品检验 `exact`，放行记录 `report_only`，整体 `partial`，但不判不符合。

## 7. 我的建议

先做 **决定 1-B + 决定 2-A + 决定 3-A + 决定 4-B**。理由：

- 1-B 只多一层 `EvidenceItems[]`，解决 4.2.5/8.2.4 的字段归属问题，不增加顶层字段数量。
- 2-A 把条件子句降为条件证据，避免 8.2.6 整条误判。
- 3-A 按标准原文判，不要求企业造“独立性声明”。
- 4-B 与报告结论一致，不把“没有单独放行表”直接判成企业缺失。

这四条定完后，再改 `clause_attr_gen` 和 `EvidenceContract` schema，然后重跑 3 条；结果应该能从现在的“3 条都有偏差”收敛到“1 条 exact、2 条 partial + report_gap”。

## 8. 追加结论：`4.2.5` 不是独立检查项，证据是“包”不是“份”

用户的补充判断成立，而且比之前的“1-B”更进一步：

### 8.1 条款要分三种角色，不能都当检查项

| 角色 | 含义 | 例子 | 系统处理 |
|---|---|---|---|
| `check_item` | 有独立过程要求，审核员会单独判符合/不符合 | `8.2.4` 内审、`8.2.6` 产品监视测量 | 单独生成契约、单独出结论 |
| `evidence_rule` | 规定“记录怎么留、怎么标识、怎么保存”，被其他条款引用 | `4.2.5` 记录控制 | 不单独开检查项；作为其他条款证据包的约束规则 |
| `support` | 术语、范围、引用性条款，不单独判 | `3` 术语、`4.2.4` 文件控制的部分内容 | 只做上下文，不生成检查结论 |

`4.2.5` 在报告里没有单独 NC，也不是因为企业“没问题”，而是它被 `8.2.4` / `8.2.6` 的证据引用掉了。只有出现系统性记录失控（如全部记录无标识、无保存期限、无法检索）时，才升级为 `4.2.5` 的 `cross_clause_finding`。所以：

- `4.2.5` 的 `EvidenceContract` 应该输出“记录控制规则”，不是“去检查一份记录清单”。
- `QR-010` 缺保存期限列，应记在 `4.2.5` 的 `report_gap`，不单独判 `4.2.5` 不符合。
- `8.2.4` / `8.2.6` 的证据包在匹配时，继承 `4.2.5` 的 `标识/保存/检索/处置` 约束。

### 8.2 `8.2.4` 的证据包（报告是组合出来的）

报告 8.2.4 的结论“组织的内审实施符合标准要求”，不是从一份文档读出来的，而是以下成员组合：

| 成员 | 作用 | 报告对应 |
|---|---|---|
| 内审程序 | 频次、职责、报告要求 | “每年一次、审核组选择、内审报告编制” |
| 内审计划 `QR-015` | 时间、范围、准则、审核组 | 2026.05.15-16，组长尚月永，组员王倩 |
| 签到表 `QR-016` | 参与人、首末次会议 | 总经理/管代/各部门负责人参加 |
| 检查表 `QR-017` | 条款覆盖、部门分工、现场发现 | 生产部检查表覆盖 6.3/6.4/7.1/7.3/7.5.1/7.5.2… |
| 不合格报告 `QR-018` | 不合格事实、原因、纠正、验证 | 7.5.8 标识，一般，2026.05.17 关闭，尚月永验证 |
| 内审报告 `QR-019` | 整体结论、NC 汇总、分发 | 1 项一般不符合，未出现严重不合格；结论“基本符合” |
| 审核员能力/任命/分工 | 公正性、能力 | 培训、任命、未审本部门 |

关键点：`QR-018` 本身能读到“7.5.8 标识不合格、一般、已关闭”；但“本次内审只有 1 项不合格、无严重不合格、结论基本符合”必须靠 `QR-019`，而“生产部由董晶晶审、计划只写王倩”必须靠 `QR-015 + QR-017` 组合。**单文档提取只能读到一张表，读不到“本次内审的结论”。**

### 8.3 `8.2.6` 的证据包（跨批次、跨阶段）

### 8.4 对 `EvidenceContract` 的最终要求

不是 `EvidenceName[]`，而是：

```json
{
  "EvidenceBundle": {
    "BundleType": "record_set",
    "Members": [
      {
        "Role": "plan",
        "Type": "record",
        "Name": "内部审核计划",
        "MustHaveFields": ["审核时间","审核范围","审核准则","审核组","受审核部门"],
        "Required": true,
        "Condition": ""
      },
      {
        "Role": "finding",
        "Type": "record",
        "Name": "内审不合格报告",
        "MustHaveFields": ["不合格描述","条款号","不合格类别","原因分析","纠正措施","验证结果"],
        "Required": true,
        "Condition": ""
      }
    ],
    "SynthesisRules": [
      "计划+签到表+检查表+不合格报告+内审报告 → 本次内审结论",
      "不合格报告的数量与内审报告中的 NC 汇总必须一致",
      "审核员名单在计划/检查表/报告三处必须一致，否则记 consistency_gap"
    ]
  },
  "JudgementRules": [],
  "ReportUse": ["coverage","conclusion","counter"]
}
```

这样 `4.2.5` 只提供 `RecordRule`，`8.2.4`/`8.2.6` 各自定义 `EvidenceBundle`，报告侧按 `SynthesisRules` 组合成结论。**条款不再是“查什么表”，而是“这类要求需要哪一组证据、这组证据怎么合成为一个结论”。**
