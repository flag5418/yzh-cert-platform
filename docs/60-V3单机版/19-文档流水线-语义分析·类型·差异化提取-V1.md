# 文档流水线：语义分析 → 类型判定 → 差异化提取 V1

> 前提已定：属性池、文档结构提取规则**与机构无关，平台一套**；只有证据生成规则按机构。本文把"文档从上传到可被条款调用"的全过程定死，并明确哪些资产属平台、哪些属机构。

---

## 一、五步流水线

```
① 上传
   └─ 转 PDF（原件留档，审核员看这个）
   └─ 转 Markdown（模型读这个）
② 语义分析（每文档 1 次）
   └─ 这一步只回答"这是什么文档、能不能用"，不做提取
③ 类型判定 → 挂通用结构（第一层 6 字段）
④ 差异化提取（按类型决定提多少、怎么提）
⑤ 入库 → 等条款来调用
```

两条硬规则：

- **PDF 与 MD 都要留**。PDF 给人看、给报告做附件；MD 给模型读。两者不互相替代。
- **② 与 ④ 是两次不同的模型调用**，不能合并。合并的后果是"没判断能不能用就开始提内容"，会把目录、合同、无关文件也提成"证据"。

---

## 一之二、语义分析按"文档 × 标准"切分，不节 token（按你的口径修正）

一次调用的单位不是"一个文档"，而是**一个文档 × 一个标准**。三标准企业、200 份文档 = 600 次判断+提取调用。

理由（你的判断，我认同）：**结论准确优先于 token 成本**。一份 QES 企业的记录本，在 9001 下的过程归属和在 45001 下的归属本来就不同，合成一次调用等于让模型在一个上下文里同时判三条线，边界容易串。

单次调用要一次答完五件事（你列的）：

| 判断 | 输出 |
|---|---|
| 是否符合本标准的体系文件 | `is_system_doc` |
| 能不能提出报告要用的内容 | `extractable` |
| 是哪一类文档 | `doc_type` |
| 属于哪个过程 | `process_domain` + `process_name`（如 采购/内审/培训/应急） |
| 按类型提取内容 | `facts[]` |
| **这份文档自身有没有缺陷** | `doc_doubts[]`（日期过期/字段空/缺签批/编号跳号/数量不足） |

**结构化时顺带判「文档级疑点」**（21 号 §三）：因为此时已经知道该文档对应哪些条款，就地判"过期 / 字段空 / 缺签批 / 编号跳号 / 数量不足"最省——不用等检查项跑，文档一上传就能给企业一张问题清单。

**过程归属必须单独落地**（你第 1 点）：`process_name` 是文档级的强字段，因为"这份记录是采购的还是内审的"直接决定它能不能被 8.4 调用。记录类文档尤其重要——同一本《质量记录汇编》里可能同时有采购、生产、检验三类记录，`process_name` 应落到**行级**（`facts[].process_name`），不是文档级。

## 一之三、计划与文档解耦：计划变了不用重跑分析

你担心"先有计划再上传、计划改了怎么办"。我的建议是**不要绑**：

| 阶段 | 依赖什么 | 计划变了怎么办 |
|---|---|---|
| 文档分析（语义+提取） | **只依赖标准清单**（企业认证范围决定 9001/24001/45001） | **不重跑**，结果一直有效 |
| 证据生成 | 依赖计划（条款×部门×审核员） | 只重跑生成，秒级/段 |

好处：上传时不用等计划，审核员可以先把资料扔进去跑着；计划调整只影响最后一步。

代价：分析阶段不知道"这次只审这几个条款"，会多提一些用不上的内容——但按你的口径，**准确优先，这点浪费可以接受**。

唯一需要计划参与的地方：如果计划里明确"标准删减条款"（如 8.3 不适用），把这个清单当**过滤条件**传给生成阶段，不影响分析。

## 二、② 语义分析输出什么（受约束结构）

不许自由发挥，只输出这一组字段：

| 字段 | 取值 | 作用 |
|---|---|---|
| `is_system_doc` | `是` / `否` | 第一道闸：不是体系文件，后面全部跳过 |
| `doc_type` | 手册 / 程序文件 / 作业指导书 / 记录 / 台账 / 资质证书 / 合同协议 / 法律法规 / 组织架构 / 无关 | 决定提取策略 |
| `process_domain` | 质量 / 环境 / 职安 / 综合 / 不适用 | 决定归到哪条线 |
| `clause_hint` | 条款号数组（可空） | 结合 `process_clause_map` 落定 |
| `extractable` | `是` / `否` | 第二道闸：**与标准有关但提不出报告要用的内容**（如目录、封面、修订记录页） |
| `excerpt_style` | `cite`（引用式）/ `detail`（明细式）/ `none` | 手册程序用 cite，记录台账用 detail |
| `confidence` | 0–1 | 低置信进人工复核队列 |

**两道闸的意义**：

- `is_system_doc = 否` → 直接排除（你说的"小孩作业"那种）。
- `is_system_doc = 是` 但 `extractable = 否` → 保留在资料清单里，**不参与证据生成**。这类是真实存在的一大类：手册目录、文件发放记录页、签字封面——与体系有关，对报告无用。

## 三、③ 类型 → 提取策略（差异化）

| 类型 | `excerpt_style` | 提取内容 | 单文档调用数 |
|---|---|---|---:|
| 质量/环境/职安手册 | `cite` | 条款 → 「章节号 + ≤60 字要点」数组（只对目录条款号 ≥10 的建数组） | 1 |
| 程序文件 | `cite` | 文件名 + 编号 + 目的句 + 覆盖过程（**不抄正文**） | 1 |
| 作业指导书 | `cite` | 文件名 + 适用工序 + 关键控制点（3–5 条） | 1 |
| 记录 / 台账 | `detail` | 按行抽事实：时间、编号、对象、结论、签批 | 1（整本一次） |
| 资质证书 | `detail` | 证书名、编号、有效期、发证机构 | 1 |
| 合同协议 | `detail` | 合同名、相对方、标的、期限、签章 | 1 |
| 法律法规 | `cite` | 法规名、条款号、要点 | 1 |
| 无关 | `none` | 不提 | 0 |

**关键收敛**：记录类**不按条款逐条跑**（这是你提出的优化点，成立）。一本记录本一次调用抽出全部可用行，后续按条款去匹配这些行——因为记录的事实字段是通用的（时间/编号/对象/结论），跑 80 次条款只是把同一批行重复读 80 遍。

估算：200 份文档、3 标准 → **600 次（200×3）**，每次判五件事并直接出提取结果。相比旧方案（600 次语义 + 600 次条款级提取）仍省一半；相比"一文档一次"的合并方案会多，但按你的口径，准确优先。

## 四、平台一套 vs 机构一套

| 资产 | 归属 | 是否随机构变 |
|---|---|---|
| 条款属性池（11 属性） | **平台** | 否 |
| 动作词词典（建立/实施/检验…） | **平台** | 否 |
| 过程→条款映射表 `process_clause_map` | **平台**（机构可覆盖个别行） | 基本否 |
| 过程名清单 `process_domains`（采购/内审/培训…） | **平台** | 否 |
| 文档通用结构（第一层 6 字段） | **平台** | 否 |
| 文档类型 → 提取策略 | **平台** | 否 |
| 证据段落骨架（R1–R7 × F1/F2） | **平台** | 否 |
| **证据生成提示词（含句式、口吻、篇幅、落款）** | **机构** | **是** |
| 报告章节模板 / 排版 | **机构** | 是 |

一句话：**"提什么"是平台的，"怎么写"才是机构的。** 换机构只换最后一层，前面全部复用——这也是当初把提示词收敛成 3 类的目的。

## 五、失败与降级

| 情形 | 处理 |
|---|---|
| PDF 无文本层 | OCR；OCR 质量差（字符 < 500）标 `low_quality`，提取只出摘要不进证据 |
| MD 转换失败 | 退回按 PDF 文本提取，记告警 |
| 语义分析置信度 < 0.6 | 进人工复核队列，不阻塞其他文档 |
| 某文档被判 `无关` 但审核员认为有关 | 提供"手动作答覆盖"入口，覆盖结果记 `manual_override` |
| 提取出的行数 < 3 | 标 `thin`，在证据生成时降级为"仅引用文件名" |

## 六、与前面文档的衔接

- 第一层 6 字段（`basic_purpose` / `clause_related` / `extract_need` / `standards` / `core_content` / `trace`）在 ③ 落定，字段定义见 16 号 §四。
- `clause_hint` 由 ② 的语义 + 17 号的 `process_clause_map` 合成，**数组**。
- ④ 的产出是"事实条目"，被 18 号的证据段按槽位调用。
