# 条款属性池与三种合并：模型设计 V1

> 回答三个问题：①属性池要不要按标准各建一套；②要不要加"条款详细内容"；③跨标准合并、同标准跨条款合并、同条款跨部门合并怎么区分处理。
> 数据来源：06/07 号实证 + 本轮对科斯亚、双尼两套 ACM 报告的行级复核。

---

## 一、属性池要不要按标准一套？——定义一套，值按标准实例化

### 1.1 你的判断是对的：同一条款在不同标准侧重点确实不同

| 现象 | 证据 |
|---|---|
| 同号不同义 | 45001 的 6.1.2 = 危险源辨识；24001 的 6.1.2 = 环境因素；9001 的 6.1.2 = 风险和机遇 |
| 义务动词不同 | 24001/45001 大量用"必须（shall）"，9001 全篇几乎不用"必须"，只用"应" |
| 前言与目的不同 | 9001 讲"满足顾客要求、增强顾客满意"；24001 讲"保护环境、履行合规义务"；45001 讲"防止人身伤害与健康损害"；13485 讲"法规符合性与安全有效" |
| 侧重点不同 | 9001 7.1.5 强调"测量资源满足产品要求"；24001 9.1 强调"环境绩效监测"；45001 9.1 强调"职业健康绩效" |

所以**"一条提示词完全不分标准"是不对的**。但"每个标准各建一套属性池（80×4=320 条）"也不必要——因为属性**结构**完全一样，只有**值**不同。

### 1.2 建议：两层结构

| 层 | 内容 | 数量 | 说明 |
|---|---|---|---|
| **属性定义层** | 12 条属性的名称、类型、值域、抽取规则 | **1 套** | 跨标准不变 |
| **属性实例层** | 每个（标准 + 条款）一行的具体值 | 80 × 4 ≈ 320 行 | 值按标准不同 |
| **标准口径卡** | 每标准 1 份：目的、术语、义务动词、侧重点、常用句式 | **4 份** | 新增，喂给提示词 |

这样：

- 改属性规则只改 1 处（定义层），不用改 320 行；
- 每条条款的属性值独立，能体现"同号不同义"；
- 提示词 = **1 套模板 + 4 份口径卡 + 该条款行**，既不分标准写 4 套模板，也不让模型裸判。

### 1.3 标准口径卡要写什么（每标准 1 份，约 300 字）

```
【标准】GB/T 24001-2016 环境管理体系
【目的】保护环境、履行合规义务、提升环境绩效
【义务动词】必须/应（shall）为主，不得弱化
【术语替换】产品→产品和服务；顾客→相关方；基础设施→设施与设备
【侧重点】环境因素、环境影响、合规义务、生命周期观点、应急准备
【禁用语】不要出现"顾客满意"（这是 9001 口径）
【同号差异提醒】6.1.2 本条指"环境因素"，不是"风险和机遇"，也不是"危险源"
```

这三行（目的 / 义务动词 / 同号差异提醒）是防止模型串标准的关键。

## 二、新增属性："条款详细内容"

**必须加，而且是最高优先级的一条。**

### 2.1 为什么

| 用途 | 说明 |
|---|---|
| 报告"要求"列 | 审核报告每行都有"要求"列，内容就是条款文本（或其问句化版本） |
| 证据生成的依据 | 模型必须看着条款原文写证据，否则会按"条款标题"猜内容 |
| 同号不同义的判别 | 4.1 在两个标准下原文不同，只有原文能区分 |
| 合并时的拼接 | 跨标准合并一段时，要把几条原文拼在一起或取最全的一条 |

### 2.2 但要区分两种文本（实测发现）

ACM 报告"要求"列里其实是**三段内容**：

```
Understanding the organisation and its context        ← 英文条款标题
理解组织及其环境                                        ← 中文条款标题
How the organisation has determined external and       ← 英文问句（审核提问版）
internal issues relevant to the business purpose...?
列举组织如何确定与业务目标和战略方向相关的内外部问题，      ← 中文问句
会影响其实现预期结果的能力吗？
```

所以一个条款有**两份可用文本**：

| 字段 | 内容 | 归属 | 用途 |
|---|---|---|---|
| `ClauseText` | 国标条款原文（含 a) b) c) 分项） | **属性池（标准级）** | 生成证据时的依据、合规判断 |
| `AuditQuestion` | 机构改写后的问句版 | **风格层（机构级）** | 报告"要求"列直接输出 |

机构风格不同的核心差异之一就在 `AuditQuestion`——同一句 4.1，ACM 写成"列举组织如何确定……吗？"，别家可能写成"组织是否识别了内外部因素？"。

### 2.3 存储与注入建议

| 项 | 建议 |
|---|---|
| 字段类型 | `ClauseText` text（长文本，9001 最长条款约 800 字） |
| 分项结构 | 另存 `ClauseItems` json（a/b/c 分项数组），便于"逐项核对" |
| 提示词注入 | **只注入当前条款的原文**，绝不注入全标准（80 条约 2 万 token 会截断且不报错） |
| 长度控制 | 超 600 字的条款，按分项切块，一块一次调用 |

## 三、三种合并必须分开处理（这是最容易做错的地方）

### 3.1 三种合并的性质完全不同

| # | 合并类型 | 例子 | 为什么会合并 | 能不能合并 |
|:--:|---|---|---|---|
| ① | **跨标准·同号** | 9001 4.1 + 24001 4.1 + 45001 4.1 → 一段 | 三标准同属 Annex SL，条款同源，机构用一行覆盖 | **可以**，加括注 |
| ② | **同标准·跨条款** | 4.3 范围 + 4.4 体系过程 → 一段；7.5.2 + 7.5.3 → 一段 | 条款逻辑连续，机构嫌碎 | **有条件可以**，需预定义合并组 |
| ③ | **同标准·同条款·跨部门** | 8.5.1 在生产部写一段、在仓库写一段 | 证据分散在不同部门 | **禁止合并** |

### 3.2 实测结果

| 检验 | 结果 |
|---|---|
| 跨标准同号合并 | 科斯亚 27 行 = 27 个条款号，QES 三标准理论约 90 个条款格 → **合并率约 70%** |
| 同标准跨条款合并 | 行内几乎没有（科斯亚 1/27、双尼 0/32，且那 1 例是解析串行）；说明**合并发生在段落层，不在表格行层** |
| 跨部门 | 科斯亚/双尼以 GM/MR 集中审为主，仅 2 页分部门；脱敏版 A 公司则是**完全按部门组织**（6 部门 80 页），且不出现条款号，用"检查清单项"作骨架 |

结论：**同一批报告里，三种合并的形态都不一样**——说明合并是"机构风格"，不是"标准要求"。

### 3.3 处理规则（建议写成硬规则）

```
规则 1（跨标准同号）：默认合并
  主键 (ClauseCode) 聚合多个 StandardCode 的证据 → 生成一段
  合并时：事实取并集去重；口径取"最严"（必须 > 应 > 宜）；末尾加括注
  例："……（含环境因素与危险源辨识）"

规则 2（同标准跨条款）：默认不合并，只按机构配置的"合并组"合并
  合并组必须人工预定义，形如 {"7.5.2","7.5.3"} → "成文信息"
  禁止模型自动判断"这两条能不能合"，否则会出现把 8.4 和 8.5 合成一段

规则 3（同条款跨部门）：绝对不合并
  证据单元 = (条款, 部门)，一段一个部门
  报告里的信号："生产部……""仓库……""询问采购负责人……"
  合并会直接导致审核员不认（"你抽的是哪个部门的？"）
```

### 3.4 数据模型建议

**证据单元的键 =（企业, 任务, 条款组, 部门）**，而不是"条款"。

| 表/字段 | 说明 |
|---|---|
| `EvidenceUnit` | `UnitCode` / `EnterpriseCode` / `TaskCode` / `DeptCode` / `ProcessDomain` |
| `UnitClauseRel` | `UnitCode` + `StandardCode` + `ClauseCode`（多对多，支持跨标准同号聚合） |
| `MergeGroup` | `GroupCode` + `StandardCode` + `ClauseCodes[]` + `GroupName`（用于规则 2） |
| `MergePolicy` | 机构级参数：`by_clause`（跨标准合并成一段）/ `by_standard`（分标准分段） |
| `CertEvidence` | 加 `UnitCode`（现有只有 `ClauseCode`，无法表达"哪条证据属于哪个部门"） |

现有库的缺口：`cert_check_result` 无 `DeptCode`、无 `TaskCode`；`CertEvidence` 无 `DeptCode`。这两处不补，"同条款跨部门分别出证据"落不了地。

### 3.5 生成顺序（三步，不能颠倒）

```
第一步：按 (标准, 条款, 部门) 生成单条证据
        —— 此时绝不合并不跨标准，保证每条都有明确出处
第二步：按 MergePolicy 合并
        跨标准同号 → 合（规则 1）
        同标准跨条款 → 只合 MergeGroup 里登记的（规则 2）
        同部门不同条款 → 不合
第三步：按机构风格包排版
        段落顺序 4→5→6→7→8→9→10；每条段落套句式模板
```

**关键：先分后合。** 先合并再生成，会造成"同一段里既有 4.1 又有 5.1 的措辞"，事实和口径都串了。

## 四、属性池最终建议（12 + 3 条）

| 属性 | 类型 | 归属 | 说明 |
|---|---|---|---|
| `ClauseIntent` | text | 定义层 | 条款作用（一句话） |
| **`ClauseText`** | text | **标准级** | **新增：条款原文** |
| **`ClauseItems`** | json | **标准级** | **新增：a/b/c 分项** |
| `Obligation` | dict | 标准级 | 约束强度（应/必须/宜/可） |
| `Applicability` | dict | 标准级 | 通用 / 有条件 |
| `ApplicabilityCondition` | text | 标准级 | 有条件时的条件描述 |
| `Process` | json | 标准级 | 过程域 |
| `Artifacts` | prompt | 标准级 | 企业应提供的资料 |
| `EvidenceChain` | prompt | 标准级 | 证据链要求 |
| `Severity` | dict | 标准级 | 不符合严重度 |
| **`EvidenceForm`** | dict | **标准级** | **新增：A 文件/B 制度/C 台账/D 记录/E 结论/F 现场** |
| **`MergeMode`** | dict | **标准级** | **新增：可跨标准合并 / 独立 / 仅括注** |
| `DocCheckMode` | dict | 标准级 | 核对方式（required/optional/none） |
| `SectionRole` | dict | 定义层 | 章节角色（组织/领导/策划/支持/运行/绩效/改进） |

**加 `EvidenceForm` 和 `MergeMode` 这两个属性，就等于把 07 号的分型和本文件的合并规则落进了库**，不用另建表。

## 五、对提示词的最终形态

```
[输入]
  ① 标准口径卡（4 份之一，约 300 字）
  ② 当前条款：ClauseCode + ClauseText（原文，≤600 字）
  ③ 该条款在该部门的已抽事实（事实条目 JSON）
  ④ 骨架（按 EvidenceForm 选 A–F 之一）
  ⑤ 机构风格皮（句式模板 + 结论词表）

[输出]
  单条证据文本 + 使用的事实清单（可回溯）+ 缺口清单
```

一次调用处理"一个条款 × 一个部门"，输出严格不含未给定的事实。
