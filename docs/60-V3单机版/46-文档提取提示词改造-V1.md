# 文档提取提示词改造 V1

> 目标：先改“文档画像 + 按类型提取”，不改最终证据提示词；提取稳定后跑发现/疑点预分析；最后再改证据组织。
> 本文给出**提示词原文骨架**、输入切片规则、输出结构、验收顺序和风险点。
> 实测记录：`doc_profile` 已用 12 份真实企业文档跑 6 轮，见 `48-doc_profile六轮提示词迭代与确定性校验-V1.md`；第 6 版 + 代码侧 `DocProfileGuard` 后 0 残留问题。
> 提取提示词实测：5 条按模式提取提示词已完成 12 个调用试跑，父条路径、`ExtraFacts`、审核 `RecordMark` 结构已修正，见 `49-五条提取提示词样本试跑与结构修正-V1.md`。

---

## 一、先回答：这个实施顺序有没有问题

总体顺序正确：

```text
改提取提示词 → 人工看提示词 → 小样本试跑 → 重跑 99 份 → 预分析发现/疑点 → 最后改证据提示词
```

但要注意 6 个问题：

| 问题 | 说明 | 处理 |
|---|---|---|
| 1. 重新上传不是必须 | 现有 99 份已转换、已提取，Markdown 还在；重传会产生重复文档 | 优先“对现有文档重跑提取”；若必须重传，按 `Sha256` 去重并归档旧提取 |
| 2. 只改提示词不够 | 4.1 只送 4.1.1–4.1.3，提示词再好也提不出 4.1.4/4.1.5 | 同步改输入切片：手册按 `DocSectionIndex.ReadRange` 送完整 4.1 小节 |
| 3. 不能一个提示词通吃 | 手册、程序、记录、清单的输出结构完全不同 | 拆成 `doc_profile` + 5 个提取提示词，按 `ExtractionMode` 路由 |
| 4. 新输出结构要改解析 | 现在 `ContentJson` 只认 `Clauses[]`；新结构如果不加适配，预分析读不到 | 先加 `DocProfile / ProcessFacts / RecordFacts` 解析，再接预分析 |
| 5. 预分析不能复用 `audit_check` | `audit_check` 会直接生成证据和结论，违背“先不改证据提示词” | 新建 `audit_findings` 只出发现+疑点；`audit_check` 冻结不动 |
| 6. 全量重跑前必须先抽检 | 99 份全跑一次成本高，且错误会放大 | 先跑 10 份样本，人工验收后再全量 |

## 二、提示词总路由

```text
每份文档：
  1) doc_profile         → 输出 DocProfile（做什么文档、哪个章节/过程/部门、怎么提取）
  2) 按 ExtractionMode：
       clause_full       → doc_extract_clause_full（手册/方针）
       process_profile   → doc_extract_process_profile（程序/指导书）
       record_profile    → doc_extract_record_profile（记录/表单）
       index_only        → doc_extract_index（封面/清单/汇编）
       audit_profile     → doc_extract_audit（内审/管理评审）
```

只有 `clause_full` 逐条款；其余都不逐条款。

## 三、提示词 1：doc_profile

### 3.1 System

```text
你是企业体系文档画像器。你只判断“这份文档是什么、属于哪个章节/过程/部门、应该怎么提取”，
不提取条款事实，不做符合性判断，不写审核证据。
```

### 3.2 User 输入

```text
文件名：{FileName}
目录：{RelFolderPath}
标题清单：
{Headings}

文档开头 2000 字：
{First2000Chars}
```

### 3.3 输出 JSON

```json
{
  "DocType": "manual|procedure|work_instruction|record|form|index|audit_record|review_record|policy|other",
  "ExtractionMode": "clause_full|process_profile|record_profile|index_only|audit_profile",
  "StageRole": "plan|support|run|check|act|mixed",
  "PrimaryChapter": "4|5|6|7|8|9|10|",
  "SecondaryChapters": [],
  "MultiChapterReason": "",
  "PrimaryProcess": "",
  "OwnerDept": "",
  "SupportDepts": [],
  "DeptSource": "explicit|inferred|unknown",
  "Purpose": "",
  "Scope": "",
  "ClauseLinks": [
    {"ClauseNumber": "8.5.1", "Relation": "primary|supporting|reference"}
  ],
  "Confidence": 0.0,
  "Reason": ""
}
```

### 3.4 硬规则

```text
1. 文件名/目录含“手册”→ manual；含“程序”→ procedure；含“作业指导/操作规程/规范”→ work_instruction；
   含“记录/报告/表单/检查表/清单”→ record；含“封面/目录/汇编/文件清单/记录清单”→ index；
   含“内审”→ audit_record；含“管理评审”→ review_record；含“方针/目标”→ policy。
2. 只有 manual / policy 可以用 clause_full；其余一律不得逐条款。
3. procedure / work_instruction / record 只允许 1 个 PrimaryChapter，最多 1 个 SecondaryChapter；
   超过 2 个章节必须设 MultiChapterReason，Confidence ≤ 0.6。
4. manual / audit_record / review_record / index 可以跨多章；但 audit/review 只能做二线证据。
5. OwnerDept 只能来自：文件封面、页眉页脚、职责章节、审批/签名、目录名。
   找不到就写 ""，DeptSource=unknown；不得猜部门。
6. ClauseLinks 只写文档真正覆盖的条款；只在文中“提到条款号/引用其他文件”的，Relation=reference。
7. 不确定时降 Confidence，不强行分类。
```

### 3.5 章节→阶段

```text
4 → plan（组织环境/相关方/范围/过程）
5 → plan（领导/方针/职责）
6 → plan（风险机遇/目标/变更）
7 → support（资源/能力/意识/沟通/成文信息）
8 → run（运行/生产服务/采购/放行/不合格）
9 → check（监视测量/内审/管理评审）
10 → act（改进/纠正措施）
```

## 四、提示词 2：doc_extract_clause_full（手册/方针）

### 4.1 输入

```text
文档画像：{DocProfile}
标准条款：{ClauseNumber} {ClauseTitle}
标准要求点：{RequirementPoints}
本条款完整小节原文（从 4.1 标题到下一个同级/上级标题）：
{SectionText}
```

**关键**：必须送完整小节，不是只送 `BodyHead` 或 4.1.1–4.1.3 摘录。

### 4.2 输出 JSON

```json
{
  "ClauseNumber": "4.1",
  "Title": "理解组织及其环境",
  "SubClauses": [
    {
      "SubClause": "4.1.1",
      "Text": "原文摘录",
      "Anchor": "10–40 字原文定位片段",
      "FactKind": "requirement|responsibility|result|record|reference|extra"
    }
  ],
  "Coverage": {
    "Declared": 5,
    "Covered": 5,
    "Missing": []
  }
}
```

### 4.3 硬规则

```text
1. 先枚举本条款下所有子条款和 a) b) c) d) 分点，再逐项填；不得只填前几个。
2. 每个子条款/分点必须有独立条目；不得合并 4.1.4、4.1.5 到 4.1.1–4.1.3。
3. 找不到的，不得省略；写进 Coverage.Missing，并注明 missing_reason。
4. Text 必须是原文摘录，不得改写；Anchor 必须是原文连续片段。
5. FactKind：规定=requirement；职责=responsibility；实际结果=result；记录=record；引用=reference；标准外=extra。
6. 手册只证明“规定了什么”，不得写成“已实施”。
```

## 五、提示词 3：doc_extract_process_profile（程序/指导书）

### 5.1 输入

```text
文档画像：{DocProfile}
文档全文或过程小节：
{ProcessText}
```

### 5.2 输出 JSON

```json
{
  "Processes": [
    {
      "ProcessName": "",
      "OwnerDept": "",
      "SupportDepts": [],
      "Purpose": "",
      "Scope": "",
      "Inputs": [],
      "Activities": [
        {"Activity": "", "Responsible": "", "OutputRecord": ""}
      ],
      "Responsibilities": [
        {"Role": "", "Duty": ""}
      ],
      "Controls": [],
      "Equipment": [],
      "Parameters": [],
      "AcceptanceCriteria": [],
      "OutputRecords": [],
      "Interfaces": [],
      "ClauseLinks": [
        {"ClauseNumber": "8.5.1", "Relation": "primary"}
      ]
    }
  ]
}
```

### 5.3 硬规则

```text
1. 不要求输出条款全文，不要求逐条款；只输出过程画像。
2. 每个 Activity 尽量给出 Responsible 和 OutputRecord；没有就留空，不得编造。
3. 程序文件如果覆盖多个子过程，输出多个 Processes。
4. 作业指导书必须输出：工序/岗位、操作步骤、设备、参数、接收准则、输出记录。
5. ClauseLinks 只标主/次/引用，不把提到的所有条款都写成 primary。
```

## 六、提示词 4：doc_extract_record_profile（记录/表单）

### 6.1 输出 JSON

```json
{
  "Records": [
    {
      "RecordName": "",
      "ProcessName": "",
      "OwnerDept": "",
      "FormFields": [],
      "Period": "",
      "Batch": "",
      "Sample": "",
      "Signoff": [],
      "LinkedDoc": "",
      "ClauseLinks": [
        {"ClauseNumber": "8.5.1", "Relation": "supporting"}
      ]
    }
  ]
}
```

### 6.2 硬规则

```text
1. 只读表头、字段、样例行；不得编造记录值。
2. 记录核心是过程、部门、字段、期间、批次/样本、签署、关联文件。
3. 一个文件多张表/多类记录，输出多个 Records。
4. 记录不输出条款原文，不做条款转述。
```

## 九、检查时召回提示词（预分析用，不写证据）

### 9.1 输入

```json
{
  "ClauseNumber": "8.5.1",
  "PlanDeptNames": ["生产部"],
  "ClauseRequirement": {
    "Chapter": "8",
    "StageRole": "run",
    "RequiredProcesses": ["生产和服务提供", "设备管理", "过程确认"],
    "RequiredDepts": ["生产部", "品质部"],
    "RequiredDocTypes": ["procedure", "work_instruction", "record"],
    "ExpectedFacts": ["受控条件", "工艺文件", "设备/环境", "人员资格", "过程确认", "防错", "放行/交付"]
  },
  "DocProfiles": [],
  "Facts": []
}
```

### 9.2 输出

```json
{
  "RecallResult": {
    "SelectedDocs": [
      {"FileCode": "", "FileName": "", "Relation": "primary|supporting", "Reason": ""}
    ],
    "ExcludedDocs": [
      {"FileCode": "", "FileName": "", "Reason": "index_only|dept_mismatch|chapter_mismatch|reference_only|duplicate"}
    ],
    "Findings": [],
    "Doubts": []
  }
}
```

硬规则：

```text
1. 先按 Chapter/StageRole 过滤，再按 PlanDeptNames 过滤，再按 DocType/Process 过滤。
2. index_only、reference 不进入 Findings。
3. audit_record/review_record 只能作 supporting，不能替代一线记录。
4. 同一文件名的重复副本去重。
5. 只输出发现/疑点，不写审核证据、不判结论。
```

## 十、输入切片规则

| 文档类型 | 输入 | 切法 |
|---|---|---|
| 手册 | 单个条款完整小节 | `DocSectionIndex.ReadRange`，从条款标题到下一个同级/上级标题 |
| 程序 | 全文或过程小节 | 按 TOC 小节切，不按 15000 字符盲切 |
| 作业指导书 | 工序/岗位段 | 按标题/表格切 |
| 记录 | 表格区域 | 保留表头 + 样例行，不能只送纯文本 |
| 封面/清单 | 目录/清单区域 | 只送前 2 页或目录 |
| 内审/管理评审 | 审核范围/发现/结论段 | 按章节切 |

## 十一、验收顺序

### S0 提示词评审

先只看提示词，不跑数据。确认：

- 文档类型枚举是否够；
- 部门是否允许 unknown；
- 程序/记录是否真的不逐条款；
- 手册是否强制子条款覆盖。

### S1 10 份样本

选：

1. `01管理手册QMS.doc`（手册）
2. `17生产和服务提供控制程序.doc`（程序）
3. `11 IPQC巡线作业指示书.xlsx`（指导书）
4. `10来料检查作业指示书.xlsx`（指导书）
5. `01-1进料检验报告.doc`（记录）
6. `02公司财务管理制度.doc`（误标样本）
7. `06考勤管理制度.doc`（误标样本）
8. `00程序文件汇编封面.doc`（index）
9. `内审记录.doc`（audit_record）
10. `07记录清单.docx`（index）

验收标准：

- 财务/考勤不再进 8.5.1；
- 封面/记录清单只出 index；
- 程序只出过程画像；
- 手册 4.1 覆盖 4.1.1–4.1.5 + a–d；
- 每份文档 `OwnerDept` 合理。

### S2 全量 99 份

样本通过后再全量；保留旧提取快照，支持回滚。

### S3 预分析发现/疑点

只跑 4.1、8.5.1；不写证据、不判结论。

### S4 最后改证据提示词

发现/疑点稳定后，再改 `audit_check` 的证据组织。

## 十三、结论

1. 你的顺序可行，但**不能只改提示词**：必须同步改输入切片、输出解析、召回条件。
2. **重新上传不是必须**；优先对现有 99 份重跑；若重传，按 SHA256 去重并归档旧提取。
3. **先跑 10 份样本**，不要直接全量。
4. **预分析用独立 `audit_findings`**，不要复用 `audit_check`；证据提示词最后再动。
5. **计划部门只在检查召回阶段使用**；上传画像只抽 `OwnerDept/SupportDepts`。
6. 手册 4.1 的 4.1.4/4.1.5 缺失，必须靠“完整小节输入 + 子条款枚举 + Coverage”三件套解决，单靠提示词解决不了。
