# ACM 审核证据生成：完整设计与实施计划 V1

> 状态：用户已于 2026-11-12 要求开始实施。本文是设计和执行交接记录；各项实际进度以第 9 节为准，不表示已完成代码、提示词、数据库或业务数据变更。
>
> 目标：先以 ACM 三套案例形成可靠的“审核发现、疑点、审核证据”，供审核员核实和使用；其他机构暂不实施，后续仅更换机构编写方案，不重建基础属性、文档提取和通用程序结构。
>
> 技术环境：C#/.NET、SqlSugar、MySQL、Vue；复用现有企业文档、条款属性池、文档提取、检查项分析及锁定链路。

## 1. 范围与现状

### 1.1 本次范围

1. 复核现有九项条款属性定义、生成、保存、使用及其有效性，不默认增加属性或批量重生成。
2. 基于文档类型组织提取：手册、程序及制度、记录与台账、报告、证照及合同、空白表单和其他附属资料。
3. 以标准和条款语义关联企业内容；大手册预先建立内容索引，分析检查项时只取候选原文，不按条款逐次发送整本手册。
4. 分离平台通用的发现与疑点、ACM 证据编写；最终结论由审核员确定。
5. 用科斯亚、双尼、尚龙三套企业资料及 ACM 报告逐项对照后，才确定最终 ACM 提示词。
6. 各阶段保留输入版本、结果、审核和处理记录，支持不同执行者接续。

不在范围：开发其他机构方案、单机版整体迁移、新建独立文档提取页面或文档三表、批量导入企业资料、自动判定严重程度或自动开具不符合项。多标准数据隔离必须保证，但不在本期自动合并同号条款。

### 1.2 已核实的主要断点

| 位置 | 已观察到的事实 | 实施影响 |
|---|---|---|
| `CertCheckContextBuilder.RenderClauseInfo` | 加载了九属性但没有渲染；条款正文上限 1200 字 | 不能假定属性参与分析，长条款可能缺要求点 |
| 同上及 `LoadDocSlicesAsync` | 每条款最多 6 份文件、每份最多 3 段、每段最多 400 字 | 重要原文可能在进入模型前被裁剪 |
| `ClauseExtractExecutor` | 线上按固定分块处理；管理页小节试跑与线上路径不同 | 试跑效果不能直接证明线上效果 |
| 同上 | 当前主要消费 `clauses`；部分分块失败或超限仍可能记为 `done` | 画像、疑点未完整传递；不完整产物可能被复用 |
| `DocumentExtractionService.UpsertAsync` | `ClauseNumbers` 为逗号拼接且最大 500 字符，超过时截断 | 超长映射可能无法被基于此列的查询完整召回 |
| `CertTaskService.LoadDocSliceRowsAsync` | 页面“审核发现”是文档摘录的实时投影，不是逐次分析保存的发现 | 重跑、文档变化后不能依靠它还原当时的发现 |
| `CertCheckEngineService` | `Reason` 优先逐条款证据，否则回退整体证据或摘要；无疑点可建议通过 | 多条款可能重复文本；空疑点不等于充分审核 |
| 现场输出契约 | 模板与 `RenderOutputContract` 存在两套结论值域 | 模型指令冲突；映射兼容不等于上游契约一致 |
| 缓存 | 已保存文件哈希和提示词版本，但跳过条件主要依文件哈希等 | 标准、规则或算法变化时可能复用旧产物 |

科斯亚 4.1.4、4.1.5 在当时已有提取结果中缺失；未逐步复现模型和分块过程，**不能断定唯一根因**。三套案例已做代表性原件对照，**尚未完成全量逐条对照**。

## 2. 决策与取舍

### D1：统一平台基础，机构只配置编写

- 推荐：条款语义、文档画像、候选关联、事实、疑点和来源属于平台；ACM 编写方案仅控制证据组织和语言。
- 备选一：每机构独立复制提取和分析链路。缺点是事实口径易分叉、修改成本高。
- 备选二：一条提示词一次完成全部任务。缺点是难定位漏召回、漏事实和写作问题，也难复用事实。
- 代价：需要约束阶段接口、分别记录提示词与版本；事实或审核员补充变化时须判断重跑范围。

### D2：内容索引 + 多路径候选，不依赖条款号

- 推荐：文档入库后建立有来源的内容单元，再结合条款标题、原文要求点、属性、章节号、文档用途和过程生成候选；逐要求点补充召回。
- 备选一：每检查项发送整本手册。实现简单但重复消耗大、响应慢且长文本易漏。
- 备选二：仅按标准条款号和文档标题精确匹配。便宜但无编号或异名资料会漏。
- 不引入向量数据库作为本期前提；优先复用 MySQL、已有目录索引和 LLM 能力。候选检索能力不足时记录漏召回样本，再决定是否另行审批引入新技术。
- 代价：首次建立索引和关联需要资源；低分候选仍可能有关联，必须有补充检索和人工查看入口。

### D3：复用现有页面及数据，扩展契约

- 文档规则仍使用 `/business/doc-extract-rule` 和每标准一条 `doc_clause_extract`，提示词内按类型分别规定处理；**不再新增三套文档规则页面或文档三表**。
- `cert_enterprise_doc.DocProfileJson` 复用文档级画像和位置索引；`cert_document_extraction.ContentJson` 兼容扩展分类型事实与标准关联，保留旧 `docMeta`、`clauses`。
- `cert_check_result` 拟新增可空 `FindingsJson` 保存“分析 × 条款”的发现快照；沿用 `DoubtsJson`、`Reason`、审核员结论字段。此列是待审批的具体数据库变更，不是已经实施；不能将完整发现塞入可能截断的 `InputSnapshotJson`。
- 代价：需数据库迁移、版本化兼容解析及旧结果回退；大 JSON 的上限和读取成本应在实施前实测，不能默认无限。

## 3. 目标链路及数据边界

```text
标准原文 + 九属性 -> 条款要求点和检索线索
企业原文 -> 类型画像 -> 内容单元及位置 -> 分类型事实
条款要求点 + 单元语义/标题/过程/编号 -> 候选关联 -> 原文回查
检查项 + 关联事实 + 审核员补充 -> 平台：审核发现 + 疑点
发现 + 疑点 + ACM 编写方案 -> 按条款生成审核证据建议
审核员复核、修改、判定、锁定 -> 报告
```

粒度必须同时保存企业、标准及版本、检查项、部门、审核阶段、条款 Code；条款号仅为显示辅助，同号不同标准不可直接合并。文件归属须做企业权限校验；文件内容作为不可信数据，不能执行文档内提示指令。

### 3.1 条款要求点

- 输入：完整标准条款原文及其标准版本、条款 Code、九属性。
- 按自然句及列表提取可核对的要求点，保留与标准原文的对应关系；属性是检索和组织提示，不能覆盖标准原文。
- 正文过长时按完整句、列表项分组处理，再合并去重；不得只截取前 1200 字并视为完整。
- `Process` 用于候选召回和排序；不命中、数据缺失、分类不确定均不自动构成“不适用”。`Severity` 不决定结论。
- 规范化要求点的生成是否持久化及复用方式，在任务 A 的实际样本复核完成后确定；未经复核的模型结果不当作标准原文。

### 3.2 文档类型策略

| 类型 | 处理单元及必须保留 | 与条款关联及编写 |
|---|---|---|
| 手册 | 章节、子节、段落和列表；保存原文位置，章节不可靠时按段落退化 | 标题、编号与语义联合召回；父节与子节均可候选，不能只靠条款号 |
| 程序、制度、规则、指导书 | 文件名、编号、版本、目的、适用范围、职责、过程、关键控制及关联记录 | 根据用途、过程和语义关联；报告一般引用文件并简述相关要求，重要控制可展开 |
| 记录、台账、清单 | 保留表名、表头、单元格、记录行或业务对象及日期、编号、对象、结果、签批；半结构化文本也按对象处理 | 一次形成事实，再依类型、过程和对象关联候选；禁止跨行拼接和编造抽样 |
| 内审、管理评审及其他报告 | 范围、时间、输入、问题、结论、措施和跟踪 | 正面与负面事实并存；报告文本引用时保留其上下文 |
| 证照、合同、校准等 | 主体、编号、范围、签发/有效日期、结果等 | 精确保留，是否有效由适用日期和事实判断 |
| 空白表单、目录、封面、扫描件 | 区分模板、附属资料、已填写资料；OCR 状态和不确定性 | 空白表单可证明模板存在，不证明执行；OCR 不可靠需人工核实 |

同一文件可包含多种内容单元；文件级分类低置信度时保留候选类型与待核状态，不直接丢弃。一次文档索引尽量跨标准复用；标准关联仍以“文件 × 标准”独立留存。

### 3.3 原文与来源

- 文档原文始终保留；模型输出的摘要不能替代原文。事实记录引用 `fileCode`、`sourceSha256`、转换产物版本/哈希、内容单元 ID、原文位置、连续原文锚点及定位状态。
- 偏移统一规定为**原始 Markdown 的 .NET UTF-16 字符索引，起点包含、终点不包含**；计算前不得改变原文换行或空白。转换结果或文件版本变化后原偏移必须失效重建。
- 锚点须回查对应原文：唯一匹配才标记已定位；重复锚点结合位置消歧，缺失或无法验证标为待核。PDF 页码仅在转换链提供可靠映射时显示。
- 表格记录保留表头和原始行/单元位置；跨页、合并单元格及 OCR 不可靠时标待核，不凭模型重组推断单元格关系。
- 资料完整性和候选覆盖单独记录：未找到、未处理、处理失败、内容被截断、已检索但无候选、分类待核，不能混成“企业没有资料”。

## 4. 三项产物与接口

### 4.1 平台：审核发现

每项发现包含 `findingId`、`standardCode`、`clauseCode`、`requirementIds`、`kind`、`text`、`sourceRefs[]`、`verification`。`kind` 至少区分 `document_rule`、`document_record`、`document_conclusion`、`onsite`；`verification` 至少区分资料记载、审核员确认、待核实。

发现可详细引用或概括，但每条关键事实必须关联来源；日期、编号、数值、对象及结果保真。手册规定不能转成已执行事实；自动读取记录不等于审核员已抽样。多个来源支持同一事实时保留全部关联，不仅展示第一份。

### 4.2 平台：疑点

每条疑点包含 `doubtId`、`type`、`point`、`detail`、`requirementIds`、`sourceRefs[]`、`searchScope`、`status`。类型包括资料不足、制度与记录链待核、不同来源冲突、记录内部矛盾、日期/签批待核、转换或定位不可靠。

“有过程文件、未找到记录”必须同时显示已检索企业、标准、文档和处理状态；资料未全部处理时写“当前已处理资料中未找到”，不写“企业无记录”。疑点是核实提示，不自动等于不符合。未输出疑点、输出解析失败和已完整分析且无疑点必须区分。

### 4.3 ACM：审核证据建议

输入为当前检查项的要求点、带来源发现、疑点、审核员提供的现场事实和 ACM 编写方案；输出每条款独立正文及所用 `findingId[]`。建议稿与审核员最终 `Conclusion`、`Severity` 分离。

规则类侧重文件名、编号和关键规定；记录类侧重对象、日期、结果和已确认样本；管理评审类兼顾输入、结论、问题及措施。具体段落顺序和用词必须在三套 ACM 对照完成后确定，不预先声称已有最终模板。

### 4.4 契约、兼容与事务

- 发现和疑点按每个 `standardCode + clauseCode` 输出，不能仅以条款号识别；检查项整体摘要不能回填所有条款的 `Reason`。
- 输出采用版本号 `schemaVersion`；字段缺失、未知枚举、截断、空 JSON、来源不存在均标失败或待核，不能转成空疑点或默认符合。解析与枚举校验由代码负责，提示词只负责描述契约。
- 沿用页面现有 `AuditFindings`、`DoubtsJson`、`Reason` 读取接口：有新版本发现快照时展示快照；历史分析无新字段时回退实时投影，并标识为“当前资料摘录，非当时快照”。
- 当平台发现已成功但 ACM 编写失败时，保留带失败状态的本次运行和发现快照；**不把失败结果设为当前有效结果，不覆盖原有效结果**。全部必需产物验证通过后，在事务内切换 `IsCurrent`，历史仍用 `NULL`。
- 被锁定检查项默认硬跳过；人工已编辑内容不自动覆盖。重跑前和提交前均复查锁及版本；并发中发现用户修改则保留新建议，不覆盖人工结果并提示冲突。

## 5. 提示词与版本方案

| 资产 | 位置 | 责任及变更边界 |
|---|---|---|
| 条款属性生成 | `cert_prompt_template` 的 `clause_attr_gen` | 只生成属性；要求完整九字段、有效值和不确定标识；先试点，不批量覆盖 |
| 文档提取 | 管理页及 `doc_clause_extract` | 每标准一条，按文档类型定义画像、原文与记录提取；页面试跑和线上复用同一策略及契约 |
| 平台发现/疑点 | 基于现有 `audit_check` 链路设计平台分析阶段 | 以事实、来源、要求点和检索范围为输入，输出逐条款发现与疑点；具体注册和配置位置实施前以当前模板工作台为准 |
| ACM 编写 | 现有提示词工作台的机构作用域 | 仅读取发现和审核员事实；具体模板内容以任务 C 的全量对照为依据，先版本化试用，不直接覆盖线上生效模板 |

每次运行记录提示词 Code、版本与内容哈希、模型名和参数、标准版本、源文件及 Markdown 哈希、索引/提取算法版本、输入范围、完成状态、时间与 token。日志不记录密钥，不默认写完整企业敏感原文。

提示词文本中的字面 `\\n` 与真实换行是否会影响发送内容，当前只观察到页面存储表现，须在实施前核实实际请求，不能先认定为故障。

## 6. 运行、缓存及失败恢复

1. 画像指纹：源文件哈希 + Markdown 哈希 + 转换/索引算法版本；变化时仅重建受影响文档画像。
2. 标准关联指纹：画像指纹 + 标准版本及条款内容哈希 + 属性版本 + 提取提示词内容哈希 + 关联算法版本 + 模型版本/参数。全部一致且完整成功才可复用；旧数据缺少指纹视为待重提，不删除旧结果。
3. 分块清单记录单元 ID、输入范围、状态、尝试次数和错误；失败分块可单独重试。未处理或输出截断时，不标记完整 `done`；单标准提取状态与企业文档跨标准聚合状态分别处理。
4. `ClauseNumbers` 不能再作为完整关联的唯一依据：读取 `ContentJson` 中完整映射，或经容量和查询验证后引入兼容索引；不能把截断的 500 字符字段视为全量。实施前记录现有调用方，保持旧接口可用。
5. 模型上下文按要求点和候选分批：预算不足时继续分批处理并合并，或明确返回部分完成；不得静默裁掉剩余事实。每批和最终合并分别校验来源与覆盖状态。
6. 同哈希重复文件只做候选去重建议，不删除文档；不同文件 ID、版本、业务归属和人工选择仍保留。
7. 规则升级不自动批量重跑或导入；仅对审核通过的样本显式发起。发布前备份迁移、配置和旧结果；回退为关闭新链路、恢复旧模板和兼容读取，不删除人工编辑及历史分析。

## 7. 分阶段实施与交接

审批前所有任务均未开始；以下顺序不可颠倒。每项交接至少记录执行者、时间、输入/版本、完成内容、检查结果、未解决事项、下一步和相关变更位置。涉及生产数据、批量重提、替换生效提示词须另行确认，不由执行 AI 自行扩大范围。

### A. 基础复核与基线

- [ ] A1：检查 `cert_clause_attr_def`、`cert_clause_attr`、`ClauseAttrGenerateService.cs` 和现行 `clause_attr_gen`；按九属性列出定义、类型、实际值、生成/写入/消费位置，区分缺失、非法、语义不合适和未知。
- [ ] A2：以 9001 的 4.1、6.2、7.2、9.2、9.3 和 13485 的 4.1.1、5.6.1、7.4.1 为起点，将条款原文与九属性逐项对照，扩展覆盖 F1、F2、F1F2 和 R1–R7；保留错误样例及来源，不批量更新。
- [ ] A3：确认管理页 `doc_clause_extract` 的实际生效作用域、请求文本、变量、试跑与线上分块差异；记录现有输入输出、失败状态、锚点和指纹。
- [ ] A4：冻结一个可回放基线：记录标准/企业/文件版本、当前提示词和模型、原始提取结果、现场页面三个结果及人工锁定状态；不修改业务数据。
