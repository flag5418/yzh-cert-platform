# 条款提示词 v5.2：9001 五条真实文档验证与结论（V1）

> 验证对象：`89-条款提示词v5.2-证据发现与疑点-全文-V1.txt`  
> 验证标准：GB/T 19001-2016  
> 验证方式：真实 `DocFact` + Markdown 原文 → `findings` 模式 → 人工逐条对照原文  
> 结论口径：只验证“证据发现 / 疑点 / 证据组合”，不评价最终审核报告是否符合机构模板。

### 1.2 测试方法

1. 从 `cert_enterprise_doc` 取 18 份 9001 文档的 Markdown 原文；

3. 用 v5.2 `findings` 模式跑 5 条条款，输入 `DocFact + 原文摘录 + 章节约束 + 引用条款`；
4. 人工对照原文，检查四件事：
   - 文档事实是否准确；

   - `WhatItProves` 是否越界；

## 四、错误分类与典型样例

### 4.1 条款条目造码（最严重）

| 条款 | 模型写法 | 实际 |
|---|---|---|
| 8.4.1 | `d)` = 评价/选择/绩效监视/再评价 | 8.4.1 只有 a/b/c；评价要求是未编号段落 |
| 7.1.5.2 | `d)` = 发现设备不符合预期用途时评价以往结果 | 7.1.5.2 只有 a/b/c；最后一段未编号 |
| 8.7.1 | A1 把“隔离/禁用状态标识”标为 `c` | c 是“告知顾客”；b 是“隔离、限制、退货或暂停” |

**影响**：报告按 `a/b/c/d` 组织时会出现“条款里没有 d，但报告写了 d”的硬伤；也会把“告知顾客”和“隔离”混为一谈。

**建议**：`ClauseItemValidator` 只允许 `ClauseItems` 中存在的 `ItemCode`；未编号段落统一用 `main`，禁止模型自造 `d/e/f`。8.4.1、7.1.5.2 的未编号段落必须在 `ClauseContext` 中显式标 `ItemCode="main"`。

### 4.2 `WhatItProves` 越界

典型：

- 8.7.1 `F1`：“字段覆盖 8.7.1 全部处置路径”——实际缺“告知顾客”，且 D2 自己说缺；
- 8.5.1 `F2`：“具备实施监视和测量活动的结构化载体”——只是模板字段；
- 8.5.1 `A2`：“可组合证明 8.5.1(f) 确认要求得到实施”——只有首次确认，没有定期再确认；
- 9.2.2 `F7`：“由审核组长和审核员署名”——打印姓名不是签名。

**建议**：`WhatItProvesValidator` 禁止“全部 / 完整 / 已实施 / 证明有效 / 覆盖所有 / 具备实施条件”等结论词；只允许“本文档显示 / 记录 / 列明 / 包含”这类事实动词。需要条款整体判断时，放到 `EvidenceAssembly`，不放到单条发现。

### 4.3 `FindingType` 误用

| 位置 | 现类型 | 应改为 | 原因 |
|---|---|---|---|
| 7.1.5.2 `F4` | `record_exists` | `cross_doc_conflict` | 设备台账与校准台账编号体系不重叠 |
| 9.2.2 `F9` | `document_exists` | 删除或改为 `record_exists` | 空引用、无具体文档，实质是组合结论 |
| 7.1.5.2 `D4` | `report_only` | `no_traceability` | 程序规定没有现场标识证据，不是报告数据 |
| 9.2.2 `D3` | `date_conflict` | `missing_date` / `no_traceability` | 缺培训记录日期，不是两个日期冲突 |

**建议**：`FindingTypeValidator` 增加语义约束：
- `report_only` 只能用于 `DocClass=report` 或明确“报告数据”；
- `document_exists` 必须有文档级 `OriginalQuote`；
- `record_exists` 不得携带“无法确认/未见/缺失”结论；
- 跨文档编号/名称不一致用 `cross_doc_conflict`。

### 4.4 `Doubts` 误报与类型误用

明确误报 3 条：

1. **8.5.1 D3**：不同负责人签署不同确认要素，是职责分工，不是 `inconsistent_person`；
2. **9.2.2 D2**：计划已写“胥加娟 A、张丹 B”，不是“未说明对应关系”；
3. **8.4.1 D2**：考核起始日与准入日同日，不是 `date_conflict`，只是“初期观察期”弱疑点。

类型/措辞问题 2 条：

- **9.2.2 D1**：计划已含综合部，D1 却说“未覆盖综合部以外”，自相矛盾；真实疑点应是“手册部门清单是否只有 6 个”未核对；
- **7.1.5.2 D4**：程序规定标识，但没有现场贴标证据，应 `no_traceability`，不是 `report_only`。

**建议**：`DoubtValidator` 做四件事：
- `date_conflict` 必须有两个可比较日期且确实冲突；
- `inconsistent_person` 必须是“同一角色/同一职责出现不同人”，不是不同角色分工；
- `missing_date` 只用于“字段存在但空”；
- `report_only` 只用于“信息只在报告里、文档里没有”。

### 4.5 `OriginalQuote` 拼接/空引用

4 条未连续命中：

| 位置 | 情况 | 判断 |
|---|---|---|
| 7.1.5.2 `F3` | 4.7.6 + 4.8.1 + 4.10.1 三段用 `-` 拼接，跳过中间原文 | 拼接，不是原文 |
| 9.2.2 `F7` | 用 `...` 省略跨段内容 | 拼接，不是原文 |
| 9.2.2 `F8` | 把表头和多行数据重组成一段表格 | 重构，不是连续原文 |
| 9.2.2 `F9` | `OriginalQuote` 为空 | 空引用 |

**建议**：`QuoteValidator` 要求 `OriginalQuote` 必须是 `doc_text` 的连续子串（允许空白/表格符号归一化）；禁止 `...`、`……`、多段 `-` 拼接；空引用直接判 `JSON_INVALID`，要求模型重写或拆成多条 finding。

### 4.6 `EvidenceAssembly` 过强

| 位置 | 现判断 | 问题 |
|---|---|---|
| 8.5.1 `A2` | `CanFormEvidence=true` | 只有首次确认，没有定期再确认；应 `partial` |
| 8.5.1 `A2` | `RequiredDocClasses=['report']` | 实际是 `record` |
| 8.7.1 | 只有 1 条组合 | 未形成“程序 + 填写记录”组合 |
| 9.2.2 `A6` | `CanFormEvidence=true`，`Gap` 为空 | 缺内审程序、签到表；至少应 `partial` |

**建议**：`AssemblyValidator`：
- `CanFormEvidence=true` 时 `Gap` 必须为空；
- `Gap` 非空时必须 `partial` 或 `false`；
- 条款含“定期/周期/每年”要求时，只有一次实例不能 `true`；
- `RequiredDocClasses` 必须来自实际 `DocFact.DocClass`，不得把 `record` 写成 `report`。

## 五、结论

### 5.1 可以确认的部分

1. **v5.2 的三层分离方向是对的**：`DocFact` 不判条款、条款提示词只出发现/疑点/组合、认证提示词再生成最终审核证据，这个边界在 5 条真实文档上成立。
2. **文档事实层已经可用**：18/18 份 `DocFact` 结构正确，填写状态（filled / partial / template_only）与原文一致；空模板没有被编造，已填记录的关键值（供应商、316L、2026.6.10、35/35、96/A、19 台校准设备、8.6 NG）都抓到了。
3. **证据发现基本可用**：21 条发现中 20 条事实成立；能区分“记录存在”“模板存在”“字段缺失”“跨文档不对应”，能识别“空白模板不证明执行”“设备台账不是测量设备”“内审 8.6 不合格”这类关键疑点。
4. **证据组合逻辑有价值**：内审“计划+检查表+任命+不合格报告+报告”、校准“台账+程序+设备台账”、供方“评审+清单+绩效”的组合方向正确，能直接给审核员当线索包。
5. **效率可接受**：18 份 `DocFact` + 5 条条款并行跑完，没有出现 v4.2 那种“5 条串行、三轮迭代”的长尾。

### 5.2 不能直接用的部分

1. **条款条目会造码**：8.4.1、7.1.5.2 都自造了 `d)`；8.7.1 把 `c` 当成“隔离”。这会让报告出现“标准里没有的条目”。
2. **`WhatItProves` 会从“文档有什么”滑到“条款已满足”**：8.7.1 “全部处置路径”、8.5.1 “已实施确认”、9.2.2 “署名”都是越界。
3. **疑点有 3 条明确误报**：不同角色分工、A/B 已映射、同日不算冲突；这些会让审核员白跑。
4. **原文引用还不是“引用级”**：连续原文命中 81%，4 条是拼接/空引用；如果报告直接引用，会出现“原文里搜不到这句话”。
5. **证据组合 `true` 过强**：8.5.1 首次确认被当成“已实施”，9.2.2 缺程序/签到仍判 `true`；这会把“部分证据”误报成“完整证据”。

### 5.3 验收判断

| 验收项 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 结构 100% | 5/5 JSON | 5/5 `JSON_OK` | 通过 |
| 文档事实 ≥95% | 18 份 | 18/18 基本准确 | 通过 |
| 证据召回 60%–80% | 证据单元 + 缺口 | 28/37 = 76% | 通过 |
| 疑点准确率 | 未硬性规定，但不能大量误报 | 12–13/17 = 71%–76%，3 条误报 | 未达“可直接用” |
| 原文引用 | 尽量原文 | 17/21 连续命中 = 81% | 未达“引用级” |
| 证据组合 | 不把部分当完整 | 3 条 `true` 中至少 1 条应降级 | 未达“可直接用” |

**总判断：v5.2 有条件通过。**  
作为“审核员线索包 / 认证提示词输入”可用；作为“最终审核证据”还不能直接用。当前差距不在提示词长度，而在**运行时校验**和**少量措辞约束**。

## 六、优化建议（不继续加长提示词）

### 6.1 必须加的 5 个运行时校验器

| 校验器 | 作用 | 触发后的处理 |
|---|---|---|
| `ClauseItemValidator` | 只允许 `ClauseItems` 中存在的 `ItemCode`；未编号段落用 `main` | 非法条目直接置空或标 `invalid_item` |
| `QuoteValidator` | `OriginalQuote` 必须是原文连续子串；禁止 `...`、多段拼接、空引用 | 不通过则要求重写；仍不通过则把该 finding 降为 `unreadable` |
| `WhatItProvesValidator` | 禁止“全部/完整/已实施/证明有效/覆盖所有/具备实施条件” | 改为“本文档显示/记录/列明/包含” |
| `DoubtValidator` | 校验 `date_conflict / inconsistent_person / missing_date / report_only` 的语义前提 | 类型不符则改类型或删除 |
| `AssemblyValidator` | `true` 必须无 `Gap`；含“定期/周期”要求时一次实例不能 `true`；`RequiredDocClasses` 必须来自实际 `DocFact` | 自动降为 `partial` 或 `false` |

### 6.2 提示词只加 5 条短约束

1. “条款条目只从 `ClauseItems` 取；未编号段落用 `main`，不得自造 `d/e/f`。”
2. “`WhatItProves` 只写本文档直接显示的事实，不写条款整体符合/覆盖全部；最多一句。”
3. “`OriginalQuote` 必须是连续原文；跨段请拆成多条 finding，不得用省略号或多段拼接。”
4. “`Doubt` 只写不确定、冲突、缺口；不同角色分工不是 `inconsistent_person`；同日不是 `date_conflict`。”
5. “`CanFormEvidence=true` 只在无 `Gap`、且满足条款频次/覆盖要求时使用；否则用 `partial`。”

> 这 5 条合计约 300–400 字，不会把提示词重新推回 14KB。

### 6.3 文档类型归一

当前 `DocClass` 有 2 处可争议：

- `校准证书管理与预警台账` 判 `record`，但“台账”更接近 `list`；
- `内审记录` 判 `record`，实际是 `plan + record + report` 的合订本。

建议在 `DocFact` 层固定：
- `台账 / 清单 / 名录 / 一览表` → `list`
- `程序 / 控制程序 / 管理规定` → `procedure`
- `记录 / 检查表 / 处理单 / 确认记录` → `record`
- `报告 / 内审报告 / 评审报告` → `report`
- `计划 / 审核计划 / 培训计划` → `plan`

合订本允许 `DocClass=record`，但 `CoreRole` 必须写“合订本：计划+任命+报告+不合格报告”，否则条款提示词会把它当单一记录。

## 七、下一步建议

1. **先不写库**：v5.2 继续留在影子状态，等 5 个校验器落地后再写 `cert_prompt_template`。
2. **先跑认证提示词消费**：用 9.2.2 的 findings/doubts 跑一次 `audit_check`，验证“默认符合 + 记录为空时只写建立了记录”的口径是否能落地；这是三层分离的最后一段。
3. **再扩验证集**：当前 5 条覆盖“已填 / 空模板 / 跨文档 / 组合”四类；下一步加 2 条“纯程序文件条款”（如 7.5.3、8.4.2），验证“无记录、只有程序”时 `contract` 模式是否稳定。
4. **不要追求 90%+ 引用召回**：当前 81% 连续引用 + 19% 拼接/空引用，已经把“哪些能直接引、哪些要重写”暴露清楚；优先修校验器，而不是继续加提示词规则。
