# 条款属性池 V2：章节语义、文档证据与成熟度前提 V1

> 本文修正 35 号文“删属性池”的表述：**删的是 9 类抽象分类属性，不是所有属性。**
> 新属性池 = 章级证据属性 + 条款级证据属性 + 文档/记录级成熟度属性。
> 目标：让每条审核证据都从“企业既定事实”长出来，而不是从审核员两天现场观察或报告话术长出来。
> **手工验证记录见 [38 号文](./38-4.1审核证据提示词对照测试记录-V1.md)**：4.1 已能稳定产出 `documented`/`documented_not_implemented` 与 `ofi`，但手册只有“规定”时不能写成“已实施”。

---

## 一、先修正三个方向

### 1.1 属性池不是“条款分类标签”，是“证据生产参数”

之前 `cert_clause_attr` 的 9 类属性（ClauseIntent / Obligation / Applicability / Process / Severity / EvidenceForm / EvidenceFamily / Role）回答的是“这条是什么性质”，审核员不关心，模型也用不上。

真正需要的是回答：

1. **这一章为什么存在、要解决什么问题**；
2. **这条款在本章分工是什么**；
3. **应从哪些企业文档/记录里找事实**；
4. **找到的事实按什么主题组织**；
5. **哪些要求是文件型、哪些必须看执行记录**；
6. **企业文档是否具备“已执行 3 个月”的前提**。

这些才是属性池的内容。

### 1.2 证据主要从企业文档长出来，现场只做验证

GB/T 19001 第 4–10 章绝大多数要求，是企业“结合自身实际建立并运行”的既定事实：

- 领导如何制定方针、目标；
- 领导识别了哪些风险和机遇；
- 企业如何确定过程、过程顺序、职责、准则；
- 企业如何做合同评审、供方评价、生产控制、放行、不合格处置；
- 企业如何监视测量、内审、管理评审、纠正措施。

这些不是审核员两天现场观察能“看出来”的；它们首先存在于企业的手册、程序、制度、计划、记录、报告、会议纪要里。现场的作用是**验证**这些文档事实是否真实、是否在执行，而不是替代企业生成事实。

### 1.3 方案成立的前提：企业文档是真实且已运行 3 个月以上

必须把前提说清楚：

- 企业文档不是“为审核临时编的”，而是已经生效、被执行、留下记录；
- 体系运行满足认证业务要求的 3 个月以上；
- 文件版本、审批、发放、记录连续、引用关系完整；
- 记录与文件要求一致，不是空白模板或集中补记。

**如果企业文档整体是捏造、胡编乱写的，任何 AI 方案都无效。** AI 只能做“文档事实抽取、一致性检查、证据组织”，不能证明真实性；真实性判断仍是审核员的职责。系统在这种情况下应明确输出“资料真实性无法确认，需现场审核”，而不是硬给一个“符合”结论。

## 二、证据来源总原则：文档为主，现场为辅

按 9001 章节的实际情况，给一个经验比例（不是标准规定，是系统设计参数）：

| 章 | 文档/记录证据占比 | 现场/访谈作用 |
|---|---:|---|
| 4 组织环境 | 85–95% | 监视评审是否实施、最高管理者访谈 |
| 5 领导作用 | 80–90% | 领导承诺、方针理解、职责落地访谈 |
| 6 策划 | 85–95% | 风险/目标是否被使用、变更是否执行 |
| 7 支持 | 85–95% | 现场环境、设备状态、员工意识 |
| 8 运行 | 70–85% | 现场观察、操作见证、抽样、标识/防护 |
| 9 绩效评价 | 90–95% | 内审/管评记录为主，现场验证抽样 |
| 10 改进 | 90–95% | 不合格/纠正措施记录为主，现场验证效果 |

**全体系经验值：约 80% 文档 + 20% 现场。**  
这修正了 35 号文“七成自动 + 三成现场”的粗口径：现场不是三成证据来源，而是验证手段。

### 2.1 典型条款：企业文档里本来就该有什么

| 条款 | 企业文档中的事实 | 现场只验证什么 |
|---|---|---|
| 5.1 领导作用 | 方针、目标、管理评审、资源投入、会议纪要、职责分配 | 领导是否真的理解/推动 |
| 5.2 方针 | 方针文件、发布记录、宣贯记录、目标对应关系 | 员工是否知道 |
| 6.1 风险机遇 | 风险清单、评价准则、措施计划、有效性评价 | 风险是否真的被使用 |
| 6.2 质量目标 | 目标文件、分解表、统计、实现计划 | 目标是否沟通/更新 |
| 4.4 体系过程 | 过程清单、过程关系图、过程准则、绩效指标 | 过程是否按策划运行 |
| 8.1 运行策划 | 质量计划、接收准则、资源计划、变更记录 | 现场是否按准则执行 |
| 8.4 外部供方 | 合格供方名录、评价记录、采购要求、进货检验 | 供方实际表现 |
| 8.5 生产服务 | 作业指导书、工艺记录、首件/巡检、特殊过程确认 | 操作、标识、防护、环境 |
| 8.6 放行 | 检验记录、放行单、授权人签字 | 抽样复核 |
| 9.2 内审 | 内审计划、检查表、不符合报告、内审报告 | 抽样验证 |
| 9.3 管评 | 管评计划、输入材料、会议记录、输出措施 | 措施是否落地 |
| 10.2 纠正措施 | 不合格记录、原因分析、措施、有效性验证 | 现场是否真的改了 |

**结论**：写审核证据时，先问“企业在哪份文件/记录里已经做了这件事”，而不是先问“审核员看到了什么”。

## 三、属性池 V2：三层结构

### 3.1 第一层：章级属性（StandardChapterProfile）

每条标准章节（4–10）都有，父级标题没有正文也可以有属性；它不是检查项，是上下文。

| AttrCode | 含义 | 取值示例 |
|---|---|---|
| `ChapterRole` | 章在 PDCA 中的角色 | context/lead/plan/support/execute/check/improve |
| `ChapterPurpose` | 本章为什么存在、要解决什么 | “确定企业环境、相关方、范围和过程骨架” |
| `ChapterQuestion` | 本章必须回答的核心问题 | “企业是什么、环境/相关方/范围/过程骨架是什么” |
| `EvidenceDirections` | 应从哪些方面找证据 | 营业执照、内外因素清单、相关方清单、过程清单 |
| `WritingPattern` | 本章证据怎么组织 | 陈述+列举 / 点名责任+引用文件 / 过程+抽样 / 结论+日期 |
| `CrossChapterLinks` | 与前后章的接口 | 4.1→6.1→6.2→9.3 |
| `EvidenceSourceRatio` | 文档/现场经验比例 | 85–95% 文档 |
| `ChapterDistortions` | 本章常见失真 | “把章标题当条款”“只写口号” |

### 3.2 第二层：条款级属性（ClauseEvidenceProfile）

每条叶子条款（4.1、4.2、5.1.1…）都有，用于检索、覆盖、写作。

| AttrCode | 含义 | 取值示例 |
|---|---|---|
| `RequirementPoints` | 条款拆成要求点 JSON | 4.1-P1/P2 |
| `ImplementationType` | 文件型/实施型/混合 | document/implementation/mixed |
| `SourcePriority` | 证据来源优先级 | manual > procedure > record > report > interview > observation |
| `EvidenceDirections` | 本条款具体找什么 | 4.1：内外因素清单、监视评审记录 |
| `OrganizationSlots` | 找到事实后按什么主题组织 | 4.1：背景/外部/内部/气候变化/监视评审/决策使用 |
| `EvidenceForms` | 证据形态 | 清单/记录/会议/访谈/观察/抽样 |
| `MaturityRule` | 本条款证据成熟度要求 | 记录覆盖≥3个月；文件生效≥3个月 |
| `CommonDistortions` | 本条款常见失真 | “规定=实施”“未找到=不符合” |
| `CrossClauseLinks` | 与其他条款接口 | 4.1→6.1、9.3 |
| `NaRule` | 不适用条件 | 8.3 不适用必须有理由且不影响能力 |

### 3.3 第三层：文档/记录级属性（DocEvidenceProfile）

每份企业文档、每类记录都要有，用于判断“证据能不能用”。

| AttrCode | 含义 | 取值示例 |
|---|---|---|
| `DocType` | 手册/程序/指导书/记录/表单/报告 | 质量手册 |
| `DocNo` | 文件编号 | KSY-QMS-M-01 |
| `DocVersion` | 版本 | A/0 |
| `EffectiveDate` | 生效日期 | 2026-06-10 |
| `ImplementedMonths` | 已执行月数 | ≥3 |
| `ApprovalStatus` | 编制/审核/批准 | 完整/缺失 |
| `RecordPeriod` | 记录覆盖期间 | 2026-06 至 2026-09 |
| `RecordContinuity` | 记录连续性 | 连续/断档 |
| `ReferenceStatus` | 引用文件解析状态 | resolved/unresolved |
| `ConsistencyStatus` | 跨文件一致性 | consistent/conflict |
| `MaturityStatus` | 成熟度总评 | mature/insufficient_period/inconsistent/authenticity_risk |

## 四、文档成熟度门槛：3 个月是业务前提，不是标准条款

GB/T 19001 没有写“必须运行 3 个月”；3 个月是认证业务对“体系已运行、有足够记录”的实操前提。系统应把它做成**前置门禁**，而不是审核结论。

### 4.1 门禁条件

| 条件 | 判定 |
|---|---|
| 文件生效日期 ≥ 3 个月 | 否则 `insufficient_period` |
| 关键记录覆盖 ≥ 3 个月且连续 | 否则 `insufficient_period` |
| 文件有编制/审核/批准/版本/发放 | 否则 `doc_control_gap` |
| 手册引用的程序/记录存在且版本对应 | 否则 `reference_gap` |
| 文件要求与记录表单字段/频次一致 | 否则 `consistency_gap` |
| 记录有日期/签名/批次/样本，不是空白模板 | 否则 `record_quality_gap` |
| 日期、签名、记录连续性无明显异常 | 否则 `authenticity_risk` |

### 4.2 门禁结果怎么用

| MaturityStatus | 系统行为 |
|---|---|
| `mature` | 允许生成文档型审核证据 |
| `insufficient_period` | 输出“体系运行/记录不足 3 个月，证据不足，待现场或后续审核”，不判 pass |
| `doc_control_gap` / `reference_gap` / `consistency_gap` | 输出具体缺口，进 doubts；不在证据里写“已实施” |
| `authenticity_risk` | 停止生成符合性结论，提示“资料真实性无法确认，需现场审核” |

**关键**：AI 不能证明企业文档真实；只能做完整性、一致性、连续性检查。真实性由审核员判断。如果企业文档整体捏造，方案不成立，系统应如实说“无法确认”，而不是编证据。

## 五、属性怎么驱动证据生产

### 5.1 检索阶段

1. 章级属性给出 `EvidenceDirections`；
2. 条款级属性给出 `SourcePriority` 和 `EvidenceForms`；
3. 文档索引给出 `DocNo/Version/ReferenceStatus`；
4. 先找手册/程序（文件型），再找记录/报告（实施型），最后才排访谈/观察。

### 5.2 事实归集阶段

- 每个事实必须带 `SourceFile / SourceNode / FactType / Status`；
- `Status` 用：`documented / documented_not_implemented / implemented / missing / onsite_needed / na`；
- 文件型要求点可以 `documented`；实施型要求点必须 `implemented` 才能 pass。

### 5.3 写作阶段

- 用条款级 `OrganizationSlots` 组织主题；
- 用章级 `WritingPattern` 决定段落顺序；
- 用 `CommonDistortions` 做自检；
- 用 `MaturityStatus` 决定能不能写“已实施”。

## 六、三个条款的属性示例

### 6.1 4.1 理解组织及其环境

```json
{
  "ClauseNo": "4.1",
  "ChapterNo": "4",
  "ChapterRole": "context",
  "ChapterPurpose": "确定企业环境、相关方、范围和过程骨架",
  "RequirementPoints": [
    {"PointId": "4.1-P1", "Action": "确定", "Object": "内外部因素", "ImplementationType": "document"},
    {"PointId": "4.1-P2", "Action": "监视和评审", "Object": "因素信息", "ImplementationType": "implementation"}
  ],
  "SourcePriority": ["manual", "management_review", "interview"],
  "EvidenceDirections": ["内外因素清单", "相关方清单", "范围说明", "过程清单", "管理评审输入"],
  "OrganizationSlots": ["组织背景", "外部因素", "内部因素", "气候变化", "监视评审", "决策使用"],
  "MaturityRule": "手册生效≥3个月；声称已监视评审时需≥3个月记录/会议",
  "CommonDistortions": ["规定=实施", "未找到=不符合", "只写4.1.1-4.1.3"]
}
```

**结论**：4.1-P1 手册有清单，可 `documented`；4.1-P2 手册只有职责，`documented_not_implemented`，需记录/访谈，不能直接 pass。

### 6.2 5.1 领导作用和承诺

```json
{
  "ClauseNo": "5.1",
  "ChapterNo": "5",
  "ChapterRole": "lead",
  "ChapterPurpose": "确认最高管理者对体系担总责、承诺、方针和职责落地",
  "SourcePriority": ["manual", "policy", "management_review", "meeting_minutes", "interview"],
  "EvidenceDirections": ["方针", "目标", "管理评审", "资源投入", "职责分配", "会议纪要"],
  "OrganizationSlots": ["责任主体", "方针目标", "资源与职责", "改进推动"],
  "CommonDistortions": ["把管理者代表当最高管理者", "只有口号没有资源/评审"]
}
```

**写法**：先写“查见方针/目标/管评/职责文件”，再用访谈验证领导是否理解、是否推动；不能只写“与领导面谈，领导重视”。

### 6.3 6.1 应对风险和机遇

```json
{
  "ClauseNo": "6.1",
  "ChapterNo": "6",
  "ChapterRole": "plan",
  "ChapterPurpose": "把4.1/4.2的输入转成风险机遇、措施和有效性评价",
  "SourcePriority": ["risk_register", "procedure", "management_review", "interview"],
  "EvidenceDirections": ["风险机遇清单", "评价准则", "措施计划", "有效性评价记录"],
  "OrganizationSlots": ["风险识别", "评价准则", "应对措施", "整合实施", "有效性评价"],
  "CommonDistortions": ["风险清单=条款风险", "有措施无评价", "把风险当不合格"]
}
```

**写法**：先查见《风险机遇清单》和措施计划，再写评价记录；访谈只验证“是否真的用风险做决策”。

## 七、与现有系统的落地关系

### 7.1 数据落点

| 数据 | 落点 |
|---|---|
| 章级属性 | `cert_clause_attr` 挂在 `4`–`10` 父级条款上；只做上下文，不做检查项 |
| 条款级属性 | `cert_clause_attr` 挂在叶子条款上；新增 AttrCode |
| 文档身份 | `cert_enterprise_doc` 的 `DocProfileJson` 扩展 |
| 引用关系 | 新增 `cert_doc_reference` 边表 |
| 文档成熟度 | `DocProfileJson` + 分析前门禁 |
| 覆盖状态 | `cert_check_result` / 审核证据 DTO 扩展 |

### 7.2 属性池的展示边界

- **系统内部**：完整属性池参与检索、覆盖、写作；
- **审核员界面**：只展示条款内容、审核发现、审核证据、现场证据、疑点；
- 不把 9 类抽象属性、优先级、槽位直接摊给审核员。

### 7.3 与 35 号文的关系

- 35 号文说“删属性池”：修正为“删 9 类抽象属性展示，重建证据属性池”；
- 35 号文说“70/30”：修正为“约 80% 文档 + 20% 现场验证”；
- 35 号文说“现场补三成”：修正为“现场只验证，不生成企业事实”。

## 八、验收标准

| 验收 | 标准 |
|---|---|
| 章级属性 | 9001 第4–10章每章都有 ChapterRole/Purpose/Question/EvidenceDirections/WritingPattern |
| 条款属性 | 4.1–4.4、5.1–5.3、6.1–6.3 至少先覆盖；每条有 RequirementPoints/SourcePriority/OrganizationSlots/CommonDistortions |
| 文档成熟度 | 4.1 手册能算出 EffectiveDate/ImplementedMonths/RecordPeriod/MaturityStatus |
| 4.1 证据 | 文档事实覆盖 4.1.1–4.1.5 + a–d；无现场证据时 P2 为 `documented_not_implemented`，结论 `ofi`/`onsite_needed` |
| 5.1 证据 | 先写方针/目标/管评/职责，再写访谈验证；不能只写访谈 |
| 6.1 证据 | 先写风险清单/措施/评价，再写访谈验证；不能由审核员观察替代 |
| 真实性 | `authenticity_risk` 时不生成符合性结论，明确提示需现场审核 |

## 九、结论

1. **属性池要保留，但要换定义**：从“条款分类标签”改成“章级 + 条款级 + 文档级证据生产参数”。
2. **证据主要从企业文档长出来**：领导方针、风险识别、过程策划、运行记录、内审管评、纠正措施，都是企业既定事实；现场只验证，不替代。
3. **3 个月是业务前提**：文件生效、记录覆盖、版本审批、引用一致、记录连续，必须先过门禁；不过门禁不判 pass。
4. **AI 不证明真实性**：AI 做抽取、覆盖、组织；真实性由审核员判断。企业文档整体捏造时，系统应停止给结论，而不是编证据。
5. **报告只学语言**：证据来源、要求点、组织方式来自 GBT 属性池和企业文档，不来自报告套路。
