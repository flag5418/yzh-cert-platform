# 审核证据三段式：发现 → 疑点 → 证据 V1

> 后续实测：4.3 / 5.1 / 6.1 的“只跑发现+疑点”结果见 [40 号文](./40-4.3·5.1·6.1发现疑点测试记录-V1.md)。

> 结论：**推荐把“发现 → 疑点 → 证据”作为主线**，比现在“一条提示词同时抽事实、找问题、写证据、下结论”更稳。
> 但“默认所有审核证据都是符合项”要拆成两句话：**证据列始终按符合项写，即使有疑点也写正面事实；结论列单独判断，不默认 pass。**
> 依据：真实报告表头是 `Clause 条款 | Requirements 要求 | Audit Evidence 审核证据 | NC/OFI`，审核证据和 NC/OFI 是两列，证据本身不是结论。

---

## 一、为什么三段式更容易

### 1.1 发现是“有边界的抽取”

审核发现只回答：

> 这条款对应的企业文档里，写了什么？

它不需要判断符合不符合，不需要组织报告语言，不需要猜审核员想听什么。  
可以逐条校验：有没有漏子条款、有没有把“要求”写成“事实”、有没有把其他条款的内容混进来。

### 1.2 疑点是“有对象的比对”

疑点只回答：

> 这些发现，和标准要求比，缺什么、矛盾什么、不可确认什么？

每条疑点必须引用具体 `finding_id`，必须落到一个 `requirement_point`，必须说明需要补什么证据。  
它比“直接写结论”更容易控制，因为疑点有对象、有类型、有边界。

### 1.3 证据是“有输入的写作”

审核证据只拿两样东西：

1. 已核实的发现；
2. 已确认的疑点（只作为“待核实”，不写进证据正文）。

它不再负责“找事实”，也不负责“定性”，只负责把事实按条款语义组织成审核员可读的段落。  
这样语言套路化的风险被隔离在最后一层，前面两层可以独立稳定。

## 二、三段各自的职责

| 阶段 | 回答的问题 | 输入 | 输出 | 不允许做什么 |
|---|---|---|---|---|
| 审核发现 | 文档里写了什么 | 标准条款 + 企业文档原文 | 原子事实、来源、条款映射、覆盖状态 | 不判断符合、不写报告语言、不补外部事实 |
| 疑点 | 发现和标准比，缺什么/矛盾什么 | 发现 + 标准要求点 + 文档成熟度 | 疑点类型、引用发现、需补证据、是否现场 | 不直接下 NC、不把“未找到”当不符合、不自由发挥 |
| 审核证据 | 如何把已获得事实组织成报告段落 | 已冻结发现 + 疑点 + 章级属性 | 分段证据、结论、疑点清单 | 不新增事实、不把疑点写进证据正文、不默认 pass |

## 三、数据结构建议

### 3.1 AuditFinding（审核发现）

```json
{
  "FindingCode": "F4.1-01",
  "CheckItemCode": "c7d4f69b...",
  "StandardNo": "iso9001",
  "ClauseNumber": "4.1",
  "SourceDocCode": "6e6a863b...",
  "SourceDocName": "01管理手册QMS.doc",
  "SourceNode": "4.1.1",
  "SourceText": "公司各级负责人应充分理解顾客和国家法规……",
  "FactText": "公司规定各级负责人应理解顾客和国家法规，并据此确定影响战略目标的内外部因素。",
  "FactKind": "requirement",
  "RequirementPoint": "4.1-P1",
  "Coverage": "covered",
  "Confidence": 0.95
}
```

`FactKind` 至少分四类：

- `requirement`：文件规定“应做什么”；
- `result`：文件写出了“实际确定了什么”；
- `record`：记录证明“已经做了什么”；
- `responsibility`：只规定职责/权限，不等于已执行。

**这是防止“规定=实施”的第一道闸门。**

### 3.2 AuditDoubt（疑点）

```json
{
  "DoubtCode": "D4.1-01",
  "FindingRefs": ["F4.1-06"],
  "RequirementPoint": "4.1-P2",
  "DoubtType": "not_implemented",
  "Question": "手册只规定管理者代表组织监视评审，未说明是否实际开展、频次、输出和结果使用。",
  "Why": "标准4.1-P2要求对因素信息进行监视和评审，属实施型要求；现有发现只有职责。",
  "RequiredEvidence": "监视评审记录/会议纪要/管理评审输入",
  "OnsiteNeeded": true,
  "SeverityCandidate": "observation"
}
```

`DoubtType` 只允许：

- `missing_result`：要求有结果，文档只有要求；
- `not_implemented`：要求实施，文档只有职责/制度；
- `partial_coverage`：子条款/分点漏了；
- `conflict`：两份文件/记录互相矛盾；
- `maturity_gap`：文件/记录不足 3 个月、断档、版本不清；
- `ambiguous_scope`：只限影响“要求是否适用/证据是否有效”的歧义。

### 3.3 AuditEvidence（审核证据）

```json
{
  "EvidenceCode": "E4.1-01",
  "ClauseNumber": "4.1",
  "FindingRefs": ["F4.1-01", "...", "F4.1-11"],
  "DoubtRefs": ["D4.1-01", "D4.1-02"],
  "Body": "组织背景：……\n外部因素：……\n内部因素：……\n气候变化：……\n监视评审：……\n决策使用：……",
  "EvidenceStatus": "provisional",
  "Conclusion": "ofi",
  "ConclusionBasis": "P1 documented；P2 仅职责，未实施"
}
```

**关键约束**：

- `Body` 只写已获得的正面事实；
- `DoubtRefs` 单独关联，不把“未提供/无记录/但无证据”写进 `Body`；
- `Conclusion` 不默认 `pass`；只有 `DoubtRefs` 中无阻断性疑点，才允许 `pass`；
- `EvidenceStatus` 可以是 `provisional`（待现场核实），不是“假证据”。

## 四、4.1 实测：只跑发现和疑点

### 4.1 发现：11 条，全部是 `requirement`

输入：手册 4.1 完整段（4.1.1–4.1.5 + a–d）。  
输出：11 条发现，覆盖：

- 4.1.1 各级负责人确定内外部因素；
- 4.1.2 外部因素类型；
- 4.1.3 内部因素类型；
- 4.1.3-a 分析市场/竞争对手/外部供方，认识行业地位；
- 4.1.3-b 分析内部能力/技术/管理，明确战略目标；
- 4.1.4 管理者代表组织监视评审；
- 4.1.5 辨识正面/负面要素；
- 4.1.5-a 国家法规政策→发展目标；
- 4.1.5-b 相关方理念价值观→相关方关系；
- 4.1.5-c 员工要求→发展战略/承诺；
- 4.1.5-d 资源配置→服务和管理进步。

**结果**：发现层稳定，11/11 覆盖，事实全部可回指原文。  
**但**：11 条全部 `fact_kind=requirement`，没有一条 `result` 或 `record`。  
这说明：手册 4.1 只写了“要求企业做什么”，没有写“企业实际做了什么”。

### 4.2 疑点：4 条，2 条有效、2 条需要抑制

| 疑点 | 类型 | 判断 |
|---|---|---|
| D1：4.1.4 只规定职责，未说明是否实际监视评审 | `not_implemented` | **有效**。标准 P2 是实施型，职责 ≠ 实施 |
| D2：手册只列因素类型，未给出实际确定的具体因素清单/分析结果 | `missing_result` / `ambiguous` | **有效**。P1 要求“确定”，手册只写“应确定” |
| D3：手册列“气候变化”，但标准注2未提气候变化，相关性无说明 | `ambiguous` | **应抑制**。注2只是示例，不是强制清单；标准允许组织自行确定相关因素 |
| D4：“环境、安全状况”不属于 ISO9001 4.1 语境，混淆 QMS 与 EHS | `ambiguous_scope` | **需谨慎**。如果企业是医疗器械组件，环境/安全可能影响 QMS 预期结果；不能凭条款文字直接判“混淆” |

**结论**：发现层已经可用；疑点层需要“疑点规则”约束，否则模型会把标准注的示例当强制清单、把合理的扩展因素当错误。

## 五、疑点规则：只允许“有证据指向的缺口”

### 5.1 必须保留的疑点

- 标准要求“确定/建立/形成文件”，文档只有“应确定/应建立”的口号，没有结果；
- 标准要求“实施/监视/评审/评价”，文档只有职责、制度、流程，没有记录；
- 子条款/分点漏了，或只写标题没有正文；
- 两份文件对同一事实写法冲突（版本、日期、职责、频次）；
- 记录不足 3 个月、断档、无签名/日期/样本；
- 引用文件不存在或版本对不上。

### 5.2 必须抑制的疑点

- “标准注没提这个因素，所以企业不该写”——注是指南，不是强制清单；
- “这个说法可能不严谨，所以有风险”——没有具体事实冲突，不构成疑点；
- “审核员可能不认可”——不是证据问题，是审核员判断；
- “企业可能没做”——没有文档/记录依据，不写；
- “条款号对不上/标题不规范”——只要内容能映射到要求点，不单独开疑点。

### 5.3 疑点输出必须带的字段

- `FindingRefs`：至少一个具体发现；
- `RequirementPoint`：落到 4.1-P1/P2 这种要求点；
- `DoubtType`：六类之一；
- `Question`：要核实什么；
- `RequiredEvidence`：补什么材料能关闭；
- `OnsiteNeeded`：是否必须现场；
- `SeverityCandidate`：只是候选，不是结论。

## 六、证据阶段：证据列始终按符合项写，结论列独立

### 6.1 证据正文只写“已获得事实”

4.1 的 V4 输出已经证明可以做到：

> 组织背景：……  
> 外部因素：法律法规、技术、竞争、市场、文化、社会、气候变化、经济。  
> 内部因素：价值观、文化、知识、绩效、成功因素。  
> 气候变化：作为外部因素之一被明确列出。  
> 监视评审：管理者代表组织各部门及人员对因素信息变化进行监视和评审。  
> 决策使用：用于发展目标、相关方关系、员工要求、资源配置。

这些都是手册里有的内容，没有编人名、面积、营业执照、日期。

### 6.2 证据列永远按符合项写，即使有疑点

- 有疑点时，证据正文仍然只写“已获得的正面事实”，不写“未提供/缺失/不符合”；
- 疑点单独进疑点列，不污染证据列；
- 结论列另行判断：`DoubtRefs` 为空可 `pass`；有 `not_implemented` / `missing_result` / `maturity_gap` → `ofi` 或 `onsite_needed`；有明确事实证明未满足才 `nc`；
- `nc` 不由“未找到”触发，只由“明确事实证明未满足”触发。

**审核证据列 = 符合项叙事；NC/OFI 列 = 结论。**  
这样审核员看到的每一条审核证据都是可进入报告的正面事实，疑点单独提示“还需补什么”，不会把证据写成问题清单。

## 七、分阶段实施：先跑发现和疑点

### P1：只跑审核发现

- 提示词只输出 `findings`；
- 目标：4.1 11/11；4.3、5.1、6.1 子条款全覆盖；
- 验收：无遗漏、无跨条款混入、每条带 `fact_kind`、`requirement_point`；
- 不写疑点、不写证据、不下结论。

### P2：在冻结发现上跑疑点

- 输入：P1 的 findings（不再重新抽事实）；
- 目标：每条疑点引用 finding，类型正确，`RequiredEvidence` 可执行；
- 验收：D3/D4 这类“标准注未提/可能不严谨”的疑点被抑制；D1/D2 保留；
- 不写证据、不下结论。

### P3：在冻结发现+疑点上跑证据

- 输入：P1 findings + P2 doubts + 章级属性 + 风格包；
- 目标：正文只写正面事实；疑点只进 doubts；结论由疑点推导；
- 验收：正文无新增事实、无条款号罗列、无疑点混入；结论与疑点一致。

**P1/P2 稳定前，不调程序；P3 只做手工对照，不进入主链。**

## 八、标准换版时

三段式对标准换版更稳：

1. 新标准发布 → 重新解析标准，生成新的 `RequirementPoint` / `ChapterProfile`；
2. 发现层不变：仍从企业文档抽事实，`FactKind` 不变；
3. 疑点层按新要求点重跑：旧疑点不沿用；
4. 证据层按新章属性重写；
5. 审核报告风格包可保留，但不提供事实/结论。

这样即使审核员不给参考报告，系统也能靠标准约束生成“发现→疑点→证据”，不会自动失败。

---

## 九、结论

1. **三段式是正确主线**：发现和疑点是我们更擅长的结构化工作，证据生成可以后置。
2. **先跑发现和疑点，先不跑证据**：这是当前最稳的验证路径；4.1 已经证明发现 11/11、疑点能定位到具体发现。
3. **疑点要有规则**：只保留“有证据指向的缺口”，抑制“标准注没提/可能不严谨/审核员可能不认可”这类自由发挥。
4. **证据与结论分开**：证据列始终按符合项写，即使有疑点也写正面事实；结论列由疑点决定，不默认 pass。
5. **标准是要求源**：新标准发布时重跑要求点/章属性，不依赖旧报告；企业文档仍是唯一事实源。
