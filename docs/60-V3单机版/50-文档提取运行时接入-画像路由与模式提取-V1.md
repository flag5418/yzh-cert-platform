## 一、本轮改了什么

### 1.1 提示词读取：从“只认 doc_clause_extract”改为“按 PromptCode 取”

`src/certplatform-api/CertPlatform.Auditor/Services/Ent/DocExtractPromptService.cs`

- 新增 5 个提示词代码常量：`doc_extract_clause_full` / `doc_extract_process_profile` / `doc_extract_record_profile` / `doc_extract_index` / `doc_extract_audit`，以及 `doc_profile`。
- 新增 `ResolveByCodeAsync(promptCode, standardShortCode)`：
  - 标准级 `ScopeKey` 优先；
  - 平台级 `ScopeKey=''` 回退；
  - **新提示词缺行直接返回空模板 + `missing`**，⛔ 不再静默退回旧 `doc_clause_extract`；
  - 旧 `doc_clause_extract` 保留代码内兜底。
- 新增 `RenderMode(template, docProfileJson, documentText)`：只替换 `{{doc_profile}}`、`{{document_text}}`。
- 旧 `Render(...)` 保持原样。

### 1.2 文档画像 → 提取模式路由

新增 `src/certplatform-api/CertPlatform.Auditor/Services/Ent/EnterpriseDocExtractionRouter.cs`

判定顺序：
1. `cert_enterprise_doc.DocProfileJson` 里的 `ExtractionMode`（新画像）；
2. 旧画像 `DocType` 中文类型；
3. 文件名兜底。

映射：

| 画像/类型 | 模式 |
|---|---|
| `manual` / 质量手册 / 方针目标 | `clause_full` |
| `procedure` / `work_instruction` / 程序文件 / 作业指导书 | `process_profile` |
| `record` / 记录表单 / 台账 | `record_profile` |
| `audit_record` / `review_record` / 审核记录 / 评审记录 | `audit_profile` |
| `index` / 文件索引 / 封面 / 清单 / 汇编 | `index_only` |
| `other` / 体系文件 | `legacy`（走旧链） |
| `ExtractionMode=none` | `none`（跳过，不调用模型） |

### 1.3 执行器分流

`src/certplatform-api/CertPlatform.Auditor/Services/Ent/ClauseExtractExecutor.cs`

在读完 Markdown、加载标准之后、解析条款清单之前插入分流：

- `none` → 写 `skipped`，消息“画像判定为无标准相关性”。
- `process_profile` / `record_profile` / `index_only` / `audit_profile` → `ExecuteModePromptAsync`：
  - 按模式取提示词；
  - 一次模型调用；
  - 指纹含模式 / 画像 JSON / 模板 / 模型，`Force` 时不复用；
  - 输出原样 JSON 写入 `ContentJson.ModeOutput`；
  - `Clauses=[]`，不再伪造条款切片。
- `clause_full` / `legacy` → 保持旧 `doc_clause_extract` 条款链。

### 1.4 产物契约扩展

`DocumentExtractionService.cs`

`ExtractedDoc` 新增：

```json
{
  "DocMeta": { "...", "ExtractionMode": "process_profile", "PromptCode": "doc_extract_process_profile", "PromptScope": "stored" },
  "ExtractionMode": "process_profile",
  "ModeOutput": { "Processes": [ ... ] },
  "Clauses": []
}
```

- `ModeOutput` 为 `JsonElement`，保留模型原始结构，不做二次改写。
- `PromptCode` / `PromptScope` 落 `DocMeta`，排障时能直接区分新/旧提示词。

### 1.5 确定性清洗

新增 `src/certplatform-api/CertPlatform.Auditor/Services/Ent/DocExtractGuard.cs`

| 模式 | 清洗动作 | 原因 |
|---|---|---|
| `audit_profile` | 递归删除 `Conclusion` / `Conclusions` | 防止“审核发现”被污染成“系统审核结论”；`RecordConclusions` 保留 |
| `process_profile` / `record_profile` | 递归删除 `ClauseLinks` | 实测模型会把生产程序挂到 4.1；条款定位应由 `doc_profile.ClauseLinks` + 章节/部门检索负责 |
| `index_only` | 不动 | 索引条目即事实 |

## 三、当前明确未完成

### 3.1 手册逐条款仍走旧链

`doc_extract_clause_full` 是**逐条款调用**（`{{clause_number}},{{clause_title}},{{requirement_points}},{{section_text}}`），而旧执行器是“一批条款一次调用”。直接接会产生 60 次模型调用，耗时与成本不可接受。

本轮选择：
- 先把 4 类“非逐条款”文档接入新提示词；
- 手册继续旧链，等确定“逐条款是否按父章节批量”或“只跑检查项涉及的条款”后再接。

### 3.2 尚未写回新画像字段

`EnterpriseDocProfileBuilder` 仍只产：
`DocType / Intro / Purpose / Scope / SourceSha256 / VersionNumber / GeneratedAt / Toc`。

新 LLM 画像的 `ExtractionMode / PrimaryChapter / OwnerDept / ClauseLinks / StandardRelevance` 还没有写回 `DocProfileJson`。当前路由只能靠旧中文 `DocType` 派生；这也是 `01管理手册` 仍被判“逐条款”、`04` 部门不一致的根因之一。

### 3.3 过程/记录文档的条款反查会变空

新模式下 `Clauses=[]`，`ClauseNumbers` 为空。旧 `by-clause` 接口按 `Clauses` 匹配，因此：
- 过程/记录/索引/审核文档不再出现在旧“按条款反查文档”的结果里；
- 这不是数据丢失，而是“条款反查”这条旧路径尚未改为读 `ModeOutput` / `doc_profile`。

在预分析接入前，旧 8.5 等条款的证据生成可能看不到这些文档。后续预分析必须改为：
`检查项条款 → 章节/过程/部门 → doc_profile.ModeOutput`。

### 3.4 未跑 99 份全量

本轮只跑 4 份代表文档；99 份尚未整批重跑。建议顺序：
1. 先用 4 类各 2–3 份抽检；
2. 确认 `ModeOutput` 字段稳定；
3. 再点企业资料页「重新分析」整批跑。

## 四、验收口径

本轮可认为“运行时接入第一阶段通过”的标准：

- 4 个模式的 `PromptCode` 分别为对应新代码，不是 `doc_clause_extract`；
- `ContentJson.ExtractionMode` 与路由一致；
- `ContentJson.ModeOutput` 有对应顶层键：`Processes` / `Records` / `IndexEntries` / `AuditProfile`；
- `audit_profile` 无 `Conclusion`；
- `process_profile` / `record_profile` 无 `ClauseLinks`；
- 任务终态 done，0 失败；
- 旧 `doc_clause_extract` 未被破坏，手册仍可跑。

## 五、下一步

1. **决定手册逐条款接入方式**：按父章节批量、只跑检查项涉及条款、或暂时保留旧链。
