# 属性池与文档提取规则影响评估 V1

> 结论：**属性池不用推翻重做，只需补 4 组字段；文档提取规则必须改主链，属于结构性升级；证据生成暂不改。**
> 因此：可以上传全部企业文档，但**不要直接用当前自动提取结果跑 8.5**；先用原始 Markdown 做“按小节切片的发现+疑点”手工验证。

---

## 一、结论表

| 模块 | 是否需要大改 | 判断 | 原因 |
|---|---|---|---|
| 条款属性池 | **否，补字段** | 现有 `RequirementPoints / ImplementationType / SourcePriority / EvidenceForms / MaturityRule` 结构可继续用 | 40 号文暴露的是“缺 RequiredDocs / FactKindExpectation / DoubtPolicy”，不是结构错 |
| 文档提取规则 | **是，结构性升级** | 当前“整篇 15k 分块 + 一条条款一个 Anchor + 平铺 Excerpts”无法保证子条款覆盖 | 4.1 只抽 3/12；8.5 子条款更多，会放大漏项 |
| 发现/疑点数据结构 | **中等改动** | 需要 `FactKind`、`Coverage`、`DoubtType`、`ReferenceGap` | 40 号文已有实测依据 |
| 证据生成 | **暂不改** | 继续手工提示词验证；等发现/疑点稳定后再接 | 证据列始终按符合项写，先不进入主链 |

## 二、属性池：不用大改，补 4 组字段

### 2.1 现有结构可以继续用

37 号文提出的三层属性池仍然成立：

- 章级：`ChapterRole / ChapterPurpose / ChapterQuestion / EvidenceDirections / WritingPattern / CrossChapterLinks / EvidenceSourceRatio / ChapterDistortions`
- 条款级：`RequirementPoints / ImplementationType / SourcePriority / EvidenceDirections / OrganizationSlots / EvidenceForms / MaturityRule / CommonDistortions / CrossClauseLinks / NaRule`
- 文档/记录级：`DocType / DocNo / DocVersion / EffectiveDate / ImplementedMonths / RecordPeriod / RecordContinuity / ReferenceStatus / ConsistencyStatus / MaturityStatus`

这些不需要推翻。40 号文说明的是**字段不够细**，不是模型错。

### 2.2 需要补的 4 组字段

#### ① `RequiredDocs`（本条款需要哪些文档/记录）

例：

- 4.3：质量手册范围声明、营业执照、地址证明、8.3 不适用说明；
- 5.1.1：方针、目标、管理评审、资源投入、会议纪要、授权文件；
- 6.1：风险机遇控制程序、风险机遇清单、措施计划、有效性评价；
- 8.5.1：生产和服务提供控制程序、作业指导书、设备台账、人员资格、首件/巡检记录；
- 8.5.2：标识和追溯程序、批次/序列号、出入库单；
- 8.6：放行程序、进料/首件/巡检/出厂检验报告；
- 8.7：不合格输出程序、不合格品处理单。

这不是新表，只是给 `cert_clause_attr` 增加 `AttrCode='RequiredDocs'` 的 JSON 值。

#### ② `FactKindExpectation`（本条应出现哪些事实类型）

例：

- 4.1：`requirement` 多、`result` 少；只有职责时必须开 `not_implemented`；
- 4.3：`document`（范围声明）、`exclusion`（8.3 不适用）、`result`（产品/地址）；
- 6.1：`document`（程序）、`result`（风险清单）、`record`（有效性评价）；
- 8.5.1：`document`（作业指导书）、`record`（生产记录）、`result`（过程参数/首件结论）。

用途：疑点阶段可以直接判断“本条应有 result，但只有 requirement”，不用模型自由发挥。

#### ③ `DoubtPolicy`（本条允许/禁止哪些疑点）

例：

- 允许：`missing_result / not_implemented / partial_coverage / conflict / maturity_gap / ambiguous_scope / reference_gap`
- 禁止：标准注未提、审核员可能不认可、企业可能没做、条款号不美观
- 特例：5.1.1 手册多写 k 项（职业健康安全），标 `extra`，不纳入本条疑点

#### ④ `ReferenceExpectation`（本条通常引用哪些文件）

例：

- 6.1 引用《风险机遇控制程序》；
- 8.5.1 引用《生产和服务提供控制程序》《IPQC巡线作业指示书》；
- 8.6 引用《产品和服务的放行控制程序》；
- 5.1.2 引用《管理评审控制程序》。

用于 `reference_gap`：引用了但没上传、版本对不上、文件不存在。

### 2.3 属性池使用方式也要改

不是把所有属性都塞给模型。运行时只给：

1. `RequirementPoints`
2. `ImplementationType`
3. `EvidenceDirections`
4. `RequiredDocs`
5. `FactKindExpectation`
6. `MaturityRule`
7. `DoubtPolicy`

`ChapterRole / WritingPattern / CommonDistortions` 可作为内部提示，不直接展示给审核员。

## 三、文档提取规则：需要结构性升级

### 3.1 当前实现的问题

当前 `DocExtractPromptService.FallbackTemplate`：

- 输入是**整篇文档**；
- 每条条款只要求一个 `Anchor` + 平铺 `Excerpts`；
- 没有“子条款/分点逐项覆盖”要求；
- 没有 `SubClause`、没有 `Coverage`、没有输出前自检；
- `ClauseExtractExecutor` 仍按 `15000` 字符分块，`MaxTokens=8192`；
- 4.1 实测只抽 3/12，4.1.4/4.1.5 全丢。

这不是“提示词写得不够好”，是**输入粒度和输出结构都不对**。

### 3.2 必须改的 5 件事

#### ① 主链切到 `DocSectionIndex.ReadRange`

`DocSectionIndex` 已有：

- `Build`：解析 Markdown 标题，生成 `CharStart/CharEnd`；
- `ReadRange(sectionMapJson, clauseNo)`：按条款号读完整小节；
- `CoverageMode=exact/folded/missing`。

当前 `EnterpriseDocService.ProbeSectionAsync` 已经能只送条款小节，但**主提取链没有用**。  
P0 第一件事：`ClauseExtractExecutor` 不再送整篇 15k，而是按条款号取完整小节。

#### ② 输出从 `Excerpts[]` 改成 `ExcerptItems[]`

```json
{
  "ClauseNumber": "4.1",
  "SubClauses": [
    {
      "SubClause": "4.1.4",
      "Text": "公司的管理者代表组织各部门及人员对各种外部和内部因素相关信息的变化进行监视和评审。",
      "Anchor": "管理者代表组织各部门及人员"
    }
  ],
  "Coverage": {
    "Declared": 12,
    "Covered": 12,
    "Missing": []
  }
}
```

`SubClause` 取值：`4.1.1`、`4.1.2`、`4.1.3`、`4.1.3-a`、`4.1.3-b`、`4.1.4`、`4.1.5`、`4.1.5-a`…`4.1.5-d`。

#### ③ 输出前自检：先列子条款，再填内容

提取提示词必须先做一步“枚举”：

1. 从企业文档该小节中识别所有编号节点（`4.1.1`、`a）`、`b）`）；
2. 生成 `Declared` 清单；
3. 逐项填 `Text/Anchor`；
4. 缺一项就写进 `Missing`，不能标 `done`。

这样 4.1 的 4.1.4/4.1.5 不会再被一条 `Anchor` 掩盖。

#### ④ 分块按“条款/小节”，不按“15000 字符”

- 一个条款一个小节，通常 500–3000 字，不会撞 8192 token；
- 8.5 拆成 8.5.1–8.5.6，不把整章 8.5 一次送；
- 长小节再按段落切，但保留 `SubClause` 标签；
- 超过输出上限时返回 `partial`，不能静默截断。

#### ⑤ 文件身份 + 引用索引

当前 `cert_enterprise_doc` 有 `FileName/VersionNumber`，但缺：

- `DocNo`（文件编号，如 `KSY-QMS-M-01`）；
- `DocVersion`（A/0）；
- `EffectiveDate`（生效日期）；
- `DocType`（手册/程序/三阶/记录）；
- `Aliases`（别名）；
- `StandardCodes` / `ClauseRefs`；
- `cert_doc_reference` 边表：`FromFileCode / RawRef / RefType / TargetFileCode / ResolveStatus / ContextText`。

没有这些，6.1 的《风险机遇控制程序》只能报“引用缺失”，不能判断版本对不对。

## 四、全量上传会怎样

### 4.1 可以上传，但分两批

**第一批：8.5 核心组**

- 17 生产和服务提供控制程序
- 11 IPQC巡线作业指示书
- 10 来料检查作业指示书
- 特殊过程/关键过程确认记录
- 设备台账/保养记录/运行环境控制表
- 21 放行控制程序 + 进料/首件/巡检/出厂报告
- 20 标识追溯程序 + 送货/入库/领料/发货单

**第二批：其余程序/三阶/记录**

- 19 顾客财产、22 防护、15 外部提供、16 不合格、07 变更、24 管理评审、13 顾客满意等。

### 4.2 上传后怎么用

- **不要**直接看 `cert_document_extraction` 的 8.5 结果；
- 先用 `EnterpriseDoc/markdown/{fileCode}` 取原文；
- 用 `DocSectionIndex.ReadRange` 或手工切片取 8.5.1/8.5.2/8.6 小节；
- 跑“只出发现+疑点”；
- 等 P0 提取规则改完，再把自动提取接回来。

### 4.3 全量上传的风险

- 文件多、同名的多（如两份《01管理手册QMS.doc》），需要按 `RelFolderPath` 区分；
- 当前提取是“整篇 × 所有条款”，全量上传会产生大量低质量提取和队列压力；
- 没有 `DocNo/Version/EffectiveDate`，后面证据会缺“文件编号/版本/日期”。

## 五、建议顺序

### P0：提取规则升级（先不改证据）

1. `ClauseExtractExecutor` 主链切 `DocSectionIndex.ReadRange`；
2. 提取提示词改 `ExcerptItems + Coverage`；
3. 加覆盖率校验：`Declared/Covered/Missing`，缺项标 `partial`；
4. 8.5 拆成 8.5.1–8.5.6 逐条提取；
5. 加 `DocNo/Version/EffectiveDate` 和 `cert_doc_reference`。

### P1：发现/疑点稳定

- 用 8.5 核心组跑“发现+疑点”；
- 验收：发现不写“没有”；疑点不全发现误判；标准外内容不疑点；引用缺失进 `reference_gap`。

### P2：证据生成

- 只在 P0/P1 稳定后接；
- 证据列始终按符合项写；疑点单独列；结论单独判断。

---

## 六、最终判断

**属性池：不需要大改，补 4 组字段即可。**  
**文档提取规则：需要大改，当前主链的“整篇分块 + 单 Anchor + 平铺 Excerpts”必须换掉。**  
**全量上传：可以，但先上传 8.5 核心组；我用原始 Markdown 做手工验证，不依赖当前自动提取结果。**
