# 收敛与落地：核心链路冻结 + 首轮对照测试方案 V1

> 停止发散。这份文档只回答一件事：**怎么在一周内看到"企业文档 → 审核报告"到底能做到几成**，以及在此之前冻结什么。

---

## 一、先看实库现状（决定从哪一步开始）

| 资产 | 应有 | 实库 | 缺口 |
|---|---:|---:|---|
| 条款（9001） | 78 | 78 | — |
| 条款原文 `Description` | 78 | 60 | **18 条为空（含 8.4）** |
| 条款属性 `cert_clause_attr` | 78×11 | **0** | 全空，需重建 |
| 属性定义 `cert_clause_attr_def` | 11 | 8 | 缺 3（`EvidenceForm`/`MergeMode`/`DocCheckMode`） |
| 文档画像 `cert_enterprise_doc_profile` | ≥100 | **0** | 全空 |
| 证据 `cert_evidence` | >0 | **0** | 全空 |
| 检查结果 `cert_check_result` | >0 | **0** | 全空 |
| 提示词模板 `cert_prompt_template` | 4 类 | **0** | 全空 |
| 审核计划 | 1 | **0** | 无计划，检查项无从产生 |
| 语料 md | 4 国标 + 3 报告 | **齐** | 唯一齐的东西 |

**结论：模型设计再往下画，也画不出结果——因为输入是空的。** 落地第一步不是写代码，是**把 78 条属性重建出来**，再拿一家企业跑通 32 段。

---

## 二、冻结清单（本阶段一律不做）

| 冻结项 | 理由 |
|---|---|
| 企业端（企业自查） | 审核员才是用户；企业端会把范围翻倍 |
| 预 NC 对外开放 | 判定权在人；先证明"证据能写对"再谈预判 |
| 检查项级疑点 | 审核员不看（原文："他们不可能按我们生成的疑点改变工作风格"） |
| 多机构方案 | 只做 ACM；第二家等第一家跑通 |
| NC 卡片 / 报告导出 | 文字对了再谈排版 |
| 移动端 / 现场采集 | 与核心链路无关 |
| 单机版 | 已明确后置 |
| 条款合并规则入库 | 由审核员在计划里定，系统不设限 |

疑点只保留**文档级**（结构化时顺手出，几乎零成本）；检查项级疑点降为"系统分析能力的展示"，不进主链路。

---

## 三、核心链路（只保留四段，不再加环节）

```
① 条款属性池    78 条 × 11 属性        （平台，一次性）
② 文档结构化    每文档×标准 → 事实      （平台）
③ 发现          条款＋事实 → 结构化发现 （平台，按检查项/按条款落）
④ 证据文字      发现＋事实＋ACM方案 → 段落（机构，只这层变）
```

判定、NC、报告排版都在④之后，不属于本阶段。

---

## 四、首轮测试：科斯亚 9001，32 段对 32 段

**为什么选科斯亚**：单标准 9001、条款块 32、列切分可靠（32/32 解析成功）、报告是 ACM 二阶段真实件。

| 步骤 | 动作 | 产出 | 估时 |
|---|---|---|---:|
| S0 | 补 18 条缺失原文（从 `GB-T-19001-2016.md` 抓，人工校） | 78 条原文齐 | 0.5 天 |
| S1 | 78 条属性批量生成并落库 | `cert_clause_attr` 858 行 | 1 天 |
| S2 | 科斯亚文档结构化（先 20 份试，再全量） | 事实条目 + 文档级疑点 | 1 天 |
| S3 | 按 32 条款生成证据文字 | 32 段草稿 | 1 天 |
| S4 | 与真实报告逐段对照 + 人工盲评 | 对照表 + 错误分类 | 0.5 天 |

**验收线（第一轮只看这一条）：**

抽取 20 段做人工盲评（不告诉评者哪段是 AI 写的），**"可直接用 + 小改可用" ≥ 12 段（60%）** 即通过第一轮。低于 60% 不改模型，先看错误分类里哪一类占最大头。

**评估指标：**

| 指标 | 算法 | 目标 |
|---|---|---|
| 条款覆盖 | 生成段数 / 32 | 100% |
| 引用真实率 | 引用到的《文件名》在资料清单中确实存在 | ≥ 90% |
| 可溯源率 | 段内事实带 `DocId+页码` 的比例 | ≥ 80% |
| 抽样达标率 | F2 段含 3 份记录标识 | ≥ 70% |
| 句式贴合 | 句长落在 27–39 字区间的比例 | ≥ 70% |
| 人工可用率 | 盲评 20 段中"可用/小改可用" | **≥ 60%** |

## 五、迭代机制（比指标更重要）

每轮只做一件事：**按错误分类改一处，再跑同一批，看指标动没动。**

| 错误类 | 典型表现 | 改哪里 |
|---|---|---|
| 事实错 | 引用了不存在的记录、张冠李戴 | ② 提取提示词 |
| 空洞 | 只有"符合要求"，没有事实 | ③ 发现提示词 / 属性 `Artifacts` |
| 骨架不符 | 该抽样却写成制度引用 | 属性 `EvidenceFamily` / `Role` |
| 口吻不符 | 不像 ACM 写的 | ④ 机构方案 |

没有"一次改对"，只有"每轮只动一处、指标可比较"。这是唯一能收敛的做法。

## 六、属性重建的样例（先定格式，再批量）

以 8.4 为例（原文缺失，S0 先补）：

| 属性 | 取值（示例） |
|---|---|
| `ClauseIntent` | 控制外部提供的过程、产品和服务，确保其符合要求 |
| `Obligation` | 强（应） |
| `Applicability` | 适用（有采购即适用） |
| `ApplicabilityCondition` | N/A |
| `Process` | 采购、外包、供方管理 |
| `Artifacts` | 供方评价准则、合格供方名录、采购订单、进货检验记录、外包协议 |
| `EvidenceChain` | 先查供方评价与名录 → 再查具体采购/外包实例 → 查进货验证 |
| `Severity` | 严重（供方失控直接影响产品符合性） |
| `EvidenceForm` | 抽样 + 引用 |
| `EvidenceFamily` | F1F2（"建立并实施"） |
| `Role` | R4 支持 |

格式定了，78 条就是同一个模板重复 78 次——这一步不需要再讨论设计。
