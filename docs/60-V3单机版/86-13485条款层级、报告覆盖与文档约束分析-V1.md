# 86-13485 条款层级、报告覆盖与文档约束分析-V1

> 日期：2026-11-15  
> 数据源：`cert_iso_clause` 13485 有效条款 94 条；`77-报告条款与程序制度文件引用映射.json` 报告 56 个条款段落  
> 目的：回答四个问题——条款范围、章节约束、条款合并、文档类型约束

---

## 1. 结论先行

1. **94 条有效条款里，只有 51 条是“有正文的叶子条款”**；19 条是章节/节标题，24 条叶子没有正文。
2. **报告 56 个条款段落里，34 个是“直接条款”，18 个是“有报告但库内无正文”，4 个是“合并父条款”**。
3. **20 条子条款被合并进 4 个父块**：`4.1` 合并 6 条、`5.6` 合并 3 条、`7.3` 合并 10 条、`7.5` 合并 `7.5.1`。
4. **没有一条“有正文的条款”被报告完全遗漏**；所谓“没出现在报告里”，绝大多数是“合并到父条款”或“标题不单独成段”。
5. **真正的问题不是条款太少，而是条款没有“范围/层级/报告映射/文档类型”四层约束**。当前 v3.2 只给了条款正文，AI 无法知道它是标题、叶子、子项，还是已经被合并。

## 3. 四个问题的模型回答

### 3.1 问题一：条款没有“范围约束”

**现状：** v3.2 只把 `clause_number / title / content` 给模型。模型不知道：

- 这是章、节、条款还是子项；
- 有没有子条款；
- 它的边界到哪；
- 正文里的 `a) b) c)` 是条款还是条款内部的分项。

**结果：** 模型会把 `a/b/c/d` 当成独立条款，或者把 `8.2` 这种标题当成检查项。

**新增 `ClauseScope`：**

```json
{
  "ClauseNumber": "8.2.2",
  "ScopeType": "clause",
  "IsCheckable": true,
  "CheckMode": "single",
  "Boundary": "本条只约束投诉处置程序，不约束 8.2.1 反馈、8.2.3 监管报告",
  "ParentClause": "8.2",
  "Children": [],
  "ClauseItems": [
    {"ItemCode": "a", "Text": "接收和记录信息", "IsItem": true},
    {"ItemCode": "b", "Text": "评价信息以确定反馈是否构成投诉", "IsItem": true},
    {"ItemCode": "c", "Text": "调查投诉", "IsItem": true},
    {"ItemCode": "d", "Text": "确定是否需要向适当的监管机构报告信息", "IsItem": true},
    {"ItemCode": "e", "Text": "处置与投诉有关的产品", "IsItem": true},
    {"ItemCode": "f", "Text": "确定是否需要启动纠正或纠正措施", "IsItem": true}
  ]
}
```

**关键规则：**

- `ScopeType`：`chapter` / `section` / `clause` / `item`；
- `IsCheckable`：只有“叶子 + 有正文 + 不是 1/2/3”才是 `true`；
- `CheckMode`：`single`（单条）/ `merged_parent`（父块合并）/ `supporting_only`（4.2.5 这种规则）/ `not_checkable`（标题/术语）；
- `a/b/c/d` 一律进 `ClauseItems[]`，**不新开条款行**；
- 父条款有子条款时，不输出 `EvidenceContract`，只输出 `SectionProfile` 或 `ChapterProfile`。

### 3.2 问题二：忽略了大标题

**现状：** 5 条试点全部是叶子条款，没有一条用到大章节约束。`4.1`、`5.6`、`7.3`、`7.5` 这些父块没有模型。

**新增 `ChapterProfile`：**

```json
{
  "ChapterCode": "8",
  "ChapterTitle": "测量、分析和改进",
  "PDCAPhase": ["C", "A"],
  "ChapterIntent": "验证体系与产品是否符合要求，驱动不合格处置与持续改进",
  "CoreQuestions": [
    "是否建立了反馈/投诉/监管报告渠道",
    "是否按计划实施内审",
    "是否对产品实施监视和测量",
    "是否处置不合格品",
    "是否分析数据并采取纠正/预防措施"
  ],
  "CoreEvidenceSources": [
    "内审包（计划/签到/检查表/不合格报告/报告）",
    "产品检验记录/放行记录",
    "不合格品处置记录",
    "数据分析记录",
    "纠正/预防措施记录"
  ],
  "ClauseGranularity": {
    "single": ["8.2.1", "8.2.2", "8.2.3", "8.2.4", "8.2.5", "8.2.6", "8.3.1", "8.3.2", "8.3.3", "8.3.4", "8.5.1", "8.5.2", "8.5.3"],
    "merged": []
  },
  "ReportStyle": "按条款逐条组织，不按文件组织"
}
```

**每个大章节回答三个问题：**

1. 这一章主要解决什么问题？
2. 核心证据应该从哪些方面收集？
3. 这一章的报告粒度是“逐条”还是“合并父块”？

### 3.3 问题三：不是所有条款都进报告，有些必须合并

**现状：** 报告 56 段，条款 94 条，直接按条款逐条跑会多出 38 条，其中 20 条是合并子条款。

**新增 `ReportHint`：**

```json
{
  "ReportMode": "merged_into_parent",
  "ReportParent": "7.3",
  "MergeGroup": "G3",
  "ReportReason": "报告按 7.3 设计和开发整体描述，不单独展开 7.3.1–7.3.10",
  "ReportUse": ["establishment", "sample", "coverage"]
}
```

**`ReportMode` 五态：**

| 值 | 含义 | 例 |
|---|---|---|
| `direct` | 报告单独一段 | `8.2.4` |
| `merged_into_parent` | 合并进父块 | `7.3.1`–`7.3.10` → `7.3` |
| `merged_parent` | 父块本身是报告段 | `4.1`、`5.6`、`7.3`、`7.5` |
| `supporting_only` | 只作规则/支撑，不单独开检查项 | `4.2.5` |
| `not_checkable` | 标题/范围/术语，不做检查项 | `4`、`5`、`1`、`2`、`3` |

**关键：`ReportHint` 不交给 LLM 猜，应该由“标准-报告映射配置”提供。**

报告是相对稳定的模板；同一标准、同一报告体系，`ReportHint` 是配置，不是每次生成。LLM 只负责在给定 `ReportMode` 下组织证据，不负责判断“这条要不要进报告”。

### 3.4 问题四：条款没有约束文档类型

**现状：** `EvidenceItem` 有 `DocRole`（procedure/record/...），但这是“证据链角色”，不是“文档类型约束”。模型仍可能给出“相关记录”“有关文件”这种空话。

**新增 `DocumentExpectation`，挂在每个 `EvidenceItem` 上：**

```json
{
  "ItemId": "E2",
  "Name": "内部审核计划",
  "DocRole": "record",
  "EvidenceRole": "implementation",
  "DocClass": "plan",
  "DocScope": "event",
  "ExtractionDepth": "fact_profile",
  "DocProfileKey": "record_v1",
  "DocBoundary": "本次内审的范围、准则、时间、审核员、受审核部门",
  "DocAliases": ["内审计划", "年度内审计划", "审核计划"],
  "ExpectedFields": ["审核范围", "审核准则", "审核时间", "审核员", "受审核区域"],
  "Frequency": "每年至少一次",
  "Coverage": "全部门",
  "ReportUse": ["coverage", "counter"]
}
```

**`DocClass` 八类：**

`manual` / `policy` / `procedure` / `work_instruction` / `record` / `report` / `list` / `plan`

**`ExtractionDepth` 四档：**

| 深度 | 适用 | 对应 DocFact |
|---|---|---|
| `citation_only` | 手册/方针 | 手册 4 问 |
| `structured` | 程序/制度 | 程序 6 问 |
| `criteria` | 作业指导/检验规程 | 指导 6 问 |
| `fact_profile` | 记录/表单/报告 | 记录 6 问 |

**`DocProfileKey`：**

`manual_v1` / `procedure_v1` / `work_instruction_v1` / `record_v1`

这样条款侧不只说“要什么证据”，还说“这是什么类型的文档、抽到什么深度、用什么轻模型读”。文档侧只回答 4–6 个问题，不按企业格式写死。

## 5. v3.3 提示词应该怎么改

### 5.1 输入增加“范围与层级”

```text
- 标准：{{standard_name}}
- 条款号：{{clause_number}}
- 条款标题：{{clause_title}}
- 父条款：{{parent_clause}}
- 条款层级：{{clause_level}}（chapter/section/clause）
- 是否有子条款：{{has_children}}
- 子条款：{{children}}
- 条款正文：{{clause_content}}
- 章节画像：{{chapter_profile}}
- 报告映射：{{report_hint}}
```

### 5.2 输出分两种

**叶子条款：**

```json
{
  "ClauseScope": {...},
  "ReportHint": {...},
  "EvidenceContract": {
    "EvidenceItems": [
      {
        "ItemId": "E1",
        "Name": "内部审核程序",
        "DocRole": "procedure",
        "EvidenceRole": "establishment",
        "DocClass": "procedure",
        "DocScope": "system",
        "ExtractionDepth": "structured",
        "DocProfileKey": "procedure_v1",
        "DocBoundary": "审核职责、策划、实施、报告、纠正措施跟踪",
        "ExpectedFields": [...],
        "Frequency": "...",
        "Coverage": "...",
        "ReportUse": [...]
      }
    ],
    "Dependencies": [...],
    "CrossChecks": [...],
    "AuditorRules": [...]
  }
}
```

**父条款/章节：**

```json
{
  "ClauseScope": {
    "ClauseNumber": "7.3",
    "ScopeType": "section",
    "IsCheckable": false,
    "CheckMode": "merged_parent",
    "Children": ["7.3.1", "...", "7.3.10"]
  },
  "SectionProfile": {
    "SectionIntent": "设计和开发全过程控制",
    "CoreEvidenceSources": ["设计开发程序", "设计策划书", "设计输入清单", "设计输出", "评审/验证/确认记录", "设计更改记录", "设计开发文档"],
    "ReportStyle": "合并为一个报告段"
  }
}
```

### 5.3 a/b/c 只做 `ClauseItems`，不做条款

以 `8.2.2` 为例：

- `8.2.2` 是一个 `clause`；
- 正文里的 `a) 接收和记录信息` 到 `f) 确定是否需要启动纠正或纠正措施` 是 `ClauseItems`；
- 每个 `ClauseItem` 下面挂 1–3 个 `EvidenceItems`；
- **不新建 8.2.2.a 这样的条款行**。

以 `8.3.2` 为例：

- `a) 采取措施以消除已发现的不合格` → `ClauseItem a` → 返工/返修记录；
- `b) 采取措施以防止其原预期的使用或应用` → `ClauseItem b` → 报废/隔离/转用记录；
- `c) 授权让步使用、放行或接收` → `ClauseItem c` → 让步接收审批记录；
- 这样 v3.2 的“a/b/c 合并成一个处置记录”会被结构性拆开，而不是靠提示词提醒。

## 6. 数据修复清单

### 6.1 必须补正文的 24 条叶子

优先级最高：

- `4.2.1`–`4.2.5`：文件要求 5 条；
- `5.1`–`5.3`、`5.4.1`–`5.4.2`、`5.5.1`–`5.5.3`、`5.6.1`–`5.6.3`：管理职责 11 条；
- `6.1`–`6.4.2`：资源管理 5 条；
- `1`、`2`、`3`：范围/引用/术语 3 条。

### 6.2 4.2.5 特别处理

`4.2.5` 当前有效行 `Id=878` 的 `Description=0`，另外两行无效。  
在补正文前，`4.2.5` 不能作为 `evidence_rule` 跑提示词，否则模型只能输出空契约。

### 6.3 重复行选择规则

`4.2.5`、`8.2.4`、`8.2.6` 等各 3 行。当前“保留最新 `IsValid=1`”可能选中空正文行。建议：

1. 同一 `ClauseNumber` 有多行时，优先选 `Description` 最长的一行；
2. 其余行标 `IsValid=0`，不删除；
3. 选择结果写入 `cert_iso_clause` 的唯一有效行。

### 6.4 报告映射配置

新增 `cert_clause_report_map`（或 JSON 配置）：

| 字段 | 说明 |
|---|---|
| `StandardCode` | 标准 |
| `ClauseNumber` | 条款号 |
| `ReportMode` | direct / merged_into_parent / merged_parent / supporting_only / not_checkable |
| `ReportParent` | 合并到的父条款 |
| `MergeGroup` | 合并组 |
| `ReportOrder` | 报告顺序 |
| `ReportUse` | establishment/sample/coverage/counter/criteria/combination/support |

这张表由人工按真实报告模板校准，不交给 LLM 猜。
