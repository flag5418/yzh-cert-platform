## 一、条款属性：你的方案成立，我加三道保险

### 1.1 为什么"一条提示词通吃 + 逐条 80 次"是对的

| 理由 | 说明 |
|---|---|
| 输入已含条款原文 | 模型读的是"45001 的 6.1.2 原文"，不是条款号。同号不同义在输入层就消解了，不需要靠"按标准分提示词"来防 |
| 属性池固定 = 输出结构固定 | 提示词的核心是"12 个属性怎么判"，与标准无关。标准只是内容，不是 schema |
| 逐条执行天然支持增量 | 改属性池 / 新增条款 / 换提示词，只需重算受影响的那几条，其余不动。批量方案做不到这一点 |
| 失败隔离 | 一条失败只重跑这一条；批量失败要整批重来，且难定位是哪条坏了 |

**成本换算**（80 条 × 4 标准 = 320 次）：

- 每次输入约 1.8k token（提示词 1.2k + 条款原文 0.6k），输出约 0.8k
- 合计约 80 万 token，串行约 30 分钟，6 并发约 5 分钟
- 这是一次性成本；之后只有"新增条款 / 改属性池 / 改提示词"才增量

**判断：成本可控这一条成立。** 我此前担心的"重复带前缀浪费"，在 320 次的量级上不构成问题——省下来的是 20 分钟，换来的却是重跑范围和失败定位的复杂度。

### 1.2 必须加的三道保险

一条提示词通吃四本标准，风险集中在"模型不知道自己在读哪一本"，所以：

**保险一：输入里显式给标准身份**

```
标准：GB/T 45001-2020 职业健康安全管理体系
条款：6.1.2 危险源辨识及风险和机遇的评价
原文：（条款全文）
```

不给标准名和版本，模型只能靠条款号猜；而 6.1.2 在两本标准下含义完全不同，猜错不报错。

**保险二：提示词内含完整的义务动词映射，不假设某标准只用其中一种**

| 原文用词 | 映射 |
|---|---|
| 应 / 必须 / 应当 | `shall` |
| 宜 / 建议 | `should` |
| 可 / 允许 | `may` |
| 注 / 注： | `note`（不参与判定） |

> "必须"只出现在环境与职业健康安全两本标准，质量管理体系一次不用。提示词若只写"应→shall"，另两本的"必须"就会漏成空值。

**保险三：每标准跑完后做分布校验（这是防"整批退化"的唯一手段）**

| 校验 | 判失败的条件 |
|---|---|
| 约束强度分布 | 某标准下 `shall` 占比超过 95%（说明模型没区分应/宜/可） |
| 过程域分布 | 某标准下"管理"占比超过 70%（说明模型在填默认值） |
| 文档核对方式分布 | "不查资料"为 0（说明模型对纯现场条款也判成要查） |
| 覆盖完整性 | 有值的条款数 / 总条款数 < 90% |

任一条失败 → 整批作废重跑，不落库。**不做这一步，退化是静默的**——上次 683 行属性里约束强度全是"应"，就是没有这一关。

### 1.3 增量重算规则（属性池固定的真正红利）

因为属性池很少变，"什么时候重算"可以写成一张确定性的表：

| 变化 | 重算范围 | 调用数 |
|---|---|---|
| 新增条款 | 只算新条款 | 新增条数 |
| 修改某属性定义（如加一条） | 所有条款，但只跑该属性 | 条款数 × 1 |
| 修改提示词 | 全量 | 条款数 |
| 标准换版 | 该标准该版本全量 | 该标准条款数 |
| 企业侧资料变化 | **不重算**（属性值是标准侧，与企业无关） | 0 |

最后一行是关键：**属性值一旦冻结，就不再因企业变化而重算**。这也是"属性池固定"能带来成本可控的根本原因。

### 1.4 冻结为基线

生成完成后：
1. 人工抽检（每标准 20 条，比对 6 个核心属性，一致率 ≥90%）
2. 抽检通过 → 打基线标记（标准 + 版本 + 批次号）
3. 之后所有生成都用基线，不再实时重算
4. 基线可导出成快照文件，用于换机、比对、回滚

## 二、文档流程：你的"按类型差异化"是对的，而且省得比预估更多

### 2.1 先确认你的判断

| 你的判断 | 判定 | 补充理由 |
|---|---|---|
| 上传时就把每份文档彻底分析完 | **对** | 计划出来后才能立即生成，延迟最低；而且成本差很小（见 2.4） |
| 200 文档 × 3 标准 = 600 次调用，太多 | 对，量级没错 | 但这是"朴素重复"的算法，实际不需要 |
| 记录类、规则类不必按条款逐项过 | **对，且是关键优化** | 记录是"活动证据"，按业务活动归属，不按条款语义 |
| 只有质量手册必须按条款逐项提取 | **对** | 手册本身就是按条款章节写的，逐条款是它唯一的读法 |

### 2.2 四类文档的调用策略

| 文档类型 | 是否按标准重复 | 切分粒度 | 每份调用数 | 输出什么 |
|---|---|:--:|---|
| 质量手册 | **可合并**（一体化手册一次覆盖三标准，输出标标准） | 按章（每章 1–2 次） | 8–12 | 逐条款要素命中 |
| 程序文件 / 制度 | 可合并（三标准同号条款常在同一份文件） | 按条款组（1 次覆盖 5–10 条款） | 2–4 | 条款组要素命中 |
| 作业指导书 / 工艺卡 / 检验规程 | 同上 | 按条款组 | 1–2 | 关键控制点 + 参数 |
| 记录（培训 / 检验 / 校准 / 合同 / 评价） | **不重复** | 整份 | 1 | 事实条目 |
| 台账 / 清单 / 一览表 | **不重复** | 整份 | 1 | 事实条目（含明细行） |
| 内审 / 管评报告 | **不重复** | 整份 | 1–2 | 结论 + 要素命中 |
| 证书 / 资质 / 校准证书 | **不重复** | 整份 | 1 | 有效期 + 范围 + 机构 |

**两条判据，写进代码：**

```
规则 A：这份文件的内容是否随标准变化？
  变（手册/程序/指导书，因为术语与条款结构不同）→ 按标准切，但可合并一体化文件
  不变（记录/台账/证书/报告，因为它是"发生过的事"）→ 只跑一次，全标准共享

规则 B：这份文件是否按条款组织？
  是（手册、按章写的程序）→ 逐条款提取
  否（记录、台账、合同）→ 整份提取，靠"记录类型 → 条款"映射表归位
```

### 2.3 量级重算

设 200 份文档，其中手册 4 份、程序 30 份、记录台账类 166 份：

| 做法 | 调用数 | 说明 |
|---|---|---|
| 朴素（每份 × 3 标准 × 全条款） | 600+ | 你说的 600 次，实际还会更高（因为手册要按条款切） |
| 按类型差异化 | 4×10 + 30×3 + 166×1 = 296 | 手册按章、程序按条款组、记录整份 |
| 再合并一体化文件（约 60% 程序同时覆盖三标准） | 40 + 60 + 166 = **266** | 同一份文件一次产出三标准结果 |

**结论：约从 600 降到 266，减 55%。** 而且减少的全是"重复且无信息增量"的调用，不是砍覆盖。

### 2.4 前置全量 vs 按计划按需

| 方案 | 延迟 | 调用数（200 文档） | 结论 |
|---|---|---|---|
| 上传即全量（你的方案） | 上传后即可见 | 约 266 | 推荐 |
| 计划确定后再按需提 | 计划改一次要重跑 | 约 210（只跑计划覆盖的 60% 条款） | 省 20%，但体验差 |

**差 20% 不值得换延迟。** 而且记录类必须全量（计划再小，记录也要全抽），省不出多少。

## 三、记录形态：不是表格，是"一行一条记录"

### 3.1 你给的真实例子推翻了一个假设

```
1.《散装水泥运输合同》
委托方：…（甲方）   承运方：…（乙方）
水泥  型号：P.O 42.5R
合同期限：2025-12-26 至 2026-12-25（有效期壹年）
约定了交货时间、交货地点等信息，双方盖章签字
```

这段信息在 Word 里**没有表格结构**，就是文字。你们写文档时也是"一行记录生成对应信息"，不是按表格填。

所以：**不能假设证据都在表里，也不能要求模型先识别表格再抽。**

### 3.2 证据形态分三类

| 形态 | 例 | 怎么抽 | 抽成什么 |
|---|---|---|---|
| 真表格 | 设备台账、培训签到、供方名录 | 按行列 | 明细行（每行一组键值） |
| 半结构化文本 | 合同、审批单、评价记录、证书 | 按键值对（甲方/乙方/标的/数量/期限/签署） | 事实条目 |
| 叙述段落 | 手册条款、程序条款 | 按段落 + 锚点 | 片段 + 要素命中 |

### 3.3 统一出口：事实条目（fact row）

不管来源是哪种形态，都归一成同一种结构：

```
{
  记录类型: 采购合同 / 外包合同
  事实: [
    {键: 合同名称,  值: 散装水泥运输合同, 位置: 第1段},
    {键: 甲方,      值: 某某公司,          位置: 第2段},
    {键: 乙方,      值: 某运输公司,        位置: 第2段},
    {键: 标的,      值: 水泥 P.O 42.5R,    位置: 第3段},
    {键: 期限起,    值: 2025-12-26,        位置: 第4段},
    {键: 期限止,    值: 2026-12-25,        位置: 第4段},
    {键: 签署,      值: 双方盖章签字,       位置: 末段}
  ],
  归位条款: [8.4.1, 8.4.3],
  归位部门: [采购部]
}
```

**为什么用"事实条目"而不是表格行**：下游（句式生成）要的是"这条记录里有没有甲方、有没有签署、期限多长"，而不是"第 3 行第 2 列是什么"。表格只是这一种形态的中间产物，不该是统一出口。

### 3.4 合同类必抽字段清单（按记录类型定义，不按表格定义）

| 记录类型 | 必抽字段 | 审核关注点 |
|---|---|---|
| 采购合同 | 合同名称、甲方、乙方、标的、数量、期限起、期限止、签订日期、签署/盖章 | 8.4.1 采购控制：合同是否评审、签署是否齐全、是否在有效期内 |
| 外包合同 | 同上 + 外包过程（运输/仓储/检验…）、外包方资质 | 8.4.1 外包控制：外包过程是否识别、是否评价 |
| 供方评价 | 供方名称、评价日期、评价结论、批准人、合格名录 | 8.4.1 供方选择与评价 |
| 培训记录 | 时间、项目、讲师、参加人、考核结果 | 7.2 能力 / 7.3 意识 |
| 设备台账 | 设备编号、名称、校准日期、证书号、有效期至 | 7.1.5.2 测量溯源 |
| 检验记录 | 日期、批次、项目、结果、检验员 | 8.6 放行 |

> 你的例子直接给出结论：**"公司的外包有：运输"** —— 这是一个必须被单独抽成事实的字段（`外包过程=运输`），因为它决定 8.4 这条款查不查、查什么。表格里没有这一格，但审核必须有这条事实。

### 3.5 生成的句子长什么样

用你给的合同数据，生成句应该是：

> 查见《散装水泥运输合同》，委托方为〔甲方〕，承运方为〔乙方〕，标的为水泥（型号 P.O 42.5R），合同期限 2025 年 12 月 26 日至 2026 年 12 月 25 日，双方盖章签字；另查见《砂石采购合同》，材料为石子 8000 吨、机制沙 5000 吨，签订日期 2026 年 1 月 1 日，双方盖章签字。公司识别的外包过程为运输。

**这一段就是"一行记录"的标准形态**：名称 → 双方 → 标的 → 期限 → 签署，顺序固定。不需要表格，也不需要模型自由发挥。

## 四、报告生成链路：检查项 → 召回 → 聚合 → **压缩** → 生成

### 4.1 你的链路是对的，缺一层

你的设计：

```
检查项（条款 + 部门 + 审核人）
  → 对照找到对应文档
  → 按条款收集所有文档已提取内容
  → LLM 生成审核报告
```

缺的是"聚合"与"生成"之间的**规则压缩层**。原因很具体：

一个部门 8 个条款 × 每条款 5 个要素 × 每要素 2–3 份证据 ≈ 100 条事实。原样喂给模型：

- 输入过长，模型会挑错证据（尤其当同一要素有多份文档时）
- 同一份文件被重复引用五次，生成出来的段落像清单，不像人写的
- 一旦超长被截断，砍掉的往往是后半段条款——静默丢证据

### 4.2 粒度要分两级

| 环节 | 粒度 | 理由 |
|---|---|---|
| 检查项 | 单条款 + 部门 + 审核人 | 便于召回证据、便于逐项勾选与确认 |
| 生成段 | 部门 + 条款组（3–5 条款） | 真实报告一段压多个条款号，按单条款生成会碎成八段 |

中间必须有"条款组"这一层：把同一部门下的相邻条款合并成段，而不是一个条款一段。

### 4.3 聚合键必须是三元组

```
聚合键 = (部门, 条款, 要素)
```

只按条款聚合会错：同一条款在两个部门要的证据不同。只按部门聚合会错：一个部门里 7.5 和 8.4 混成一段。

### 4.4 压缩层的五条规则

| # | 规则 | 目的 |
|:--:|---|---|
| 1 | 同一要素多份证据 → 按"证据强度、日期新旧、完整性"选一条首选，其余进备选 | 避免一段引五份同类文件 |
| 2 | 同一文件只写一次全称，后续引"同上" | 避免重复啰嗦 |
| 3 | 每个要素的原文引用不超过 2 句 | 控长 |
| 4 | 按条款号升序排列，不按文件顺序 | 报告可读性 |
| 5 | 超长时先砍"仅提及"级证据，再砍备选，**绝不砍事实值** | 保证关键事实不丢 |

**输入预算**：每段控制在 6–8k token；超出按"要素优先级"截（有事实值的优先，仅提及的最后）。

### 4.5 结论怎么来

| 环节 | 谁做 |
|---|---|
| 齐备度（有/不全/没有） | 代码算（要素 × 证据三态） |
| 结论候选（符合/基本符合/不符合/待确认） | 代码按规则算（约束强度 + 齐备度 + 时效） |
| 最终结论 | **审核员确认** |
| 覆盖声明（查了哪些文件、抽几份、覆盖期间） | 代码统计 |

## 五、整体流程（含每步产物）

```
① 资料上传
   产物：文件清单 + 哈希 + 类型初判
   用模型：否

② 文档画像（每份 1 次）
   产物：分类 / 相关度 / 作用 / 归属部门 / 服务哪些标准 / 候选条款
   用模型：是
   ← 这一步定"后面要不要按标准重复"

③ 按类型分派提取
   手册：按章 → 逐条款要素
   程序：按条款组
   记录/台账/证书：整份 → 事实条目
   产物：要素命中（有/不全/没有 + 位置锚点）+ 事实条目
   用模型：是（调用数见 §2.3）

④ 证据归集
   产物：以 (部门, 条款, 要素) 为键的证据索引
   用模型：否

⑤ 计划编排 → 检查项（条款 + 部门 + 审核人）
   产物：检查项清单
   用模型：否（专家手工/系统建议后确认）

⑥ 按检查项召回 + 按条款组聚合 + 规则压缩
   产物：每段的证据包（事实 + 引用 + 覆盖统计）
   用模型：否

⑦ 句式生成
   产物：审核记录段（定位/依据/查见/抽样/结论）+ 结论候选
   用模型：可选（只润色措辞，不改事实）

⑧ 报告导出
   产物：记录表 / 报告正文 / 不符合项卡片 + 快照冻结
   用模型：否
```

**花钱的只有 ② 和 ③，其余全是确定性计算。** 这是整个流程设计的第一原则。

## 六、前两版哪些结论作废

| 作废项 | 本文替代 |
|---|---|
| 每标准一套属性提示词 | 一条提示词通吃，输入显式带标准身份 |
| 属性生成分两跳、5–20 条批处理 | 逐条执行（成本可控、增量友好、失败隔离），用分布校验兜底 |
| 文档按"每文档 × 每条款 × 每标准"全跑 | 按文档类型定切分粒度 + 是否按标准重复 |
| 表格是主要证据载体，需固定列模板 | 证据形态三类，统一归一成事实条目；合同走字段清单 |
| 三个标准要跑三遍 | 一部分共享（记录类）、一部分合并（一体化文件） |
| 聚合后直接喂 LLM | 中间必须加规则压缩层 |

## 七、要你确认的三件事

| # | 问题 | 影响 | 我的建议 |
|:--:|---|---|---|
| 1 | 手册是否按"章"切分调用（每章 1–2 次，而不是 80 条款 80 次） | 手册调用数从 80 降到 10 | 是，章内条款一起给，输出逐条款 |
| 2 | 记录类是否完全不按条款跑，只靠"记录类型 → 条款"映射表归位 | 记录调用数从 3×N 降到 N | 是；映射表由专家确认一次，之后固定 |
| 3 | 压缩层由代码做，还是让模型挑证据 | 决定是否可复核 | 必须由代码做，模型只润色措辞 |

## 一句话

**条款属性：一条提示词 + 逐条 + 分布校验 + 冻结基线。文档提取：按类型定策略，记录不按标准重复。报告生成：检查项召回、条款组合并、代码压缩、模板成句、人定结论。**
