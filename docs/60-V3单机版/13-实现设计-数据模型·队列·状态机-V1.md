# 实现设计 V1：数据模型 · 队列 · 状态机

> **修订（依据 14 号，2026-11-10）**
> - `cert_clause_align.MergeAllowed` **只用于提示文案**，不驱动任何自动合并逻辑；合并由审核员在审核计划中决定。
> - 检查项按条款展开的方式保留；一个部门可承担多个过程域，部门不设限。
> - 语料 markdown 已建于 `docs/60-V3单机版/语料md/`，后续分析不再重复解析 PDF。

> 业务语义（有哪些概念、属性怎么定、提取规则怎么随属性变）见《12-模型设计》。两份文档不重复。
>

## 一、落地原则（五条，对应本轮修正）

| # | 原则 | 推论 |
|---|---|---|
| 1 | **条款原文不建实体，用关联** | 复用 `cert_iso_clause.Description` 存原文；用视图拼给证据队列 |
| 2 | **条款不细分 a/b/c** | 不建 `ClauseItems`，一段一条款 |
| 3 | **审核计划按条款拆** | 一行一条款，部门可为空；生成时一条款一段 |
| 4 | **锁定按检查项** | 不做证据级锁，锁表以 `CheckItemCode` 为键 |
| 5 | **生成即建议，重跑由人触发** | 系统永不自动覆盖，指纹只用来"提示" |

## 二、数据落地

### 2.1 属性池（现有表，只补配置）

| 环节 | 表/字段 | 动作 |
|---|---|---|
| 属性定义 | `cert_clause_attr_def` | 补 3 条：`EvidenceForm`(dict/evidence_form)、`MergeMode`(dict/merge_mode)、`DocCheckMode`(dict/doc_check_mode) |
| 属性定义（改） | 同上 | `Artifacts`、`EvidenceChain` 的 `ValueType` 由 `prompt` 改 `text`（只存业务事实） |
| 属性实例 | `cert_clause_attr` | 沿用，唯一键 (`StandardCode`,`ClauseCode`,`AttrCode`) |
| 字典 | `Sys_Dictionary` / `Sys_DictionaryList` | 新增 3 个字典（`DicCode/DicName/DicValue/OrderNo`） |

现有 8 条保留，Sort 10–80；新增 3 条 Sort 85/90/100。

### 2.2 条款对齐（新表，唯一的"关系表"）

`cert_clause_align`

| 字段 | 类型 | 说明 |
|---|---|---|
| `StandardCode` / `ClauseCode` | varchar(50) | 本条 |
| `AlignType` | varchar(10) | `A_same` / `B_diff` / `C_cross` |
| `PeerStandardCode` / `PeerClauseCode` | varchar(50) | 对应方（C 类必填） |
| `MergeAllowed` | int | 1/0 |
| `Note` | varchar(200) | 差异提醒 |

约 60–80 行，一次性灌。

### 2.3 条款原文：用现有列 + 视图（不新增列）

| 载体 | 做法 |
|---|---|
| 存储 | `cert_iso_clause.Description` 存条款原文（现有列，无需改表；不含 a/b/c 拆分） |
| 视图 | 新建 `v_clause_profile`：输出 `StandardCode`、`ClauseCode`、`ClauseNumber`、`Title`、`ClauseText(=Description)`、`AlignType`、`AttrJson`（`cert_clause_attr` 透视成 JSON） |
| 消费方 | 证据生成队列、条款画像页面、报告"要求列"回填 |

**这样属性挂接阶段完全不碰原文，证据阶段一次查询拿全。**

### 2.4 文档事实（新表）

`cert_doc_fact`：把提取结果从大 JSON 拍平成行，供按条款/过程域检索。

| 字段 | 说明 |
|---|---|
| `EnterpriseCode` / `DocCode` / `FileCode` | 来源 |
| `FactType` | policy/objective/scope/dept_duty/process/meta/list_item/record_row/conclusion/cert |
| `RecordType` | 培训/检验/校准/合同/管评/内审/证照（D 型用） |
| `FactKey` / `FactValue` | 键值 |
| `RecordIndex` | 同文件内第几条（抽样用） |
| `ProcessDomain` / `DeptHint` | 检索用 |
| `Locator` / `Snippet` | 章节/页码 + 原文 10–40 字 |
| `ContentMD5` | 指纹与去重 |
| `Confidence` / `ExtractMode` | 质量 |

### 2.5 检查项：按条款拆

| 事实 | 当前状态 | 落地方式 |
|---|---|---|
| 计划一行可能多条款 + 多部门 | `cert_audit_plan_detail` 有 `Clauses`/`Departments` | **生成检查项时按条款展开**：一条款一检查项 |
| 部门可为空 | `Departments` 可空 | 空 → 通用段（管理层/公司级表述） |
| 检查项载体 | `cert_task_item.CheckItemCode` | 每条款一行 |

生成规则（代码侧）：

```
for plan_detail in 计划:
    for clause in plan_detail.Clauses.split():
        建 CheckItem(clause, dept=plan_detail.Departments, owner=plan_detail.OwnerCode)
    # Departments 为空 → dept=null，一段通用
```

**不要求用户改计划录入方式**，单条款+空部门、多条款+多部门都能跑。

### 2.6 缺口汇总（最小新增）

| 类别 | 内容 |
|---|---|
| 新建表 | `cert_clause_align`、`cert_doc_fact`（**2 张**） |
| 新建视图 | `v_clause_profile`（1 个） |
| 改配置 | 属性定义 3 增、2 改类型；3 个字典 |
| **不改表结构** | 不加 `ClauseText`、不加 `DeptCode`、不加 `ClauseItems` |

## 三、四条队列

全部复用 `cert_expert_task_queue` + `_queue_item`（已有 `Payload`、`ExtractVersionStamp`、`NextRetryAt`、`LockedUntil`）。

| 队列 | `QueueType` | item 粒度 | `Payload` 关键字段 |
|---|---|---|---|
| 条款属性 | `CLAUSE_ATTR` | 一条款 | `standardCode`/`clauseCode`/`clauseNumber` |
| 文档画像 | `DOC_PROFILE` | 一文件 | `fileCode`/`fileSha256`/`relPath` |
| 文档提取 | `DOC_EXTRACT` | 一文件 | `fileCode`/`docCategory`/`extractNeed` |
| 证据生成 | `EVIDENCE_GEN` | 一检查项 | `checkItemCode`/`clauseCode`/`dept`/`promptCode`/`promptVersion` |

### 3.1 共性规则

| 规则 | 实现 |
|---|---|
| 幂等 | 比对 `ExtractVersionStamp = sha256(输入签名 + promptCode + promptVersion)`，相同则 `Skipped` |
| 断点续跑 | 依 `ItemStatus` 续；`Failed` 且 `RetryCount < MaxRetryCount` 重排 |
| 退避 | `NextRetryAt` 指数退避（1/2/4 分钟） |
| 限流 | 单企业并发 2–3；模型侧全局并发按 provider 配额 |
| 单条重跑 | 页面按条款号/检查项手动入队 1 个 item |

### 3.2 条款属性队列

- 一个标准一次入队 80 条；
- 入库时按 `AttrCode` 写 `cert_clause_attr`，`ValueSource=ai`；
- 跑完自动执行三道校验（同号不同义、义务动词、分布），不通过的打回重跑。

### 3.3 文档队列（两段式）

```
上传 → DOC_CONVERT（转 Markdown）→ DOC_PROFILE（画像/分类）
     → DOC_EXTRACT（仅 extractNeed=需要提取 的进）→ 写 cert_doc_fact
```

**关键闸门**：`extractNeed ≠ 需要提取` 的文件**不入提取队列**——这就是"目录相关但提不出内容"的拦截点。

### 3.4 证据生成队列

支持三档：单检查项、勾选多个、全部。`cert_task_item.RunMode` 记 `single`/`batch`/`all`。

## 四、证据生成：八步 + 一次视图查询

### 4.1 前置守卫（第一行代码）

```
if lock(checkItem).IsActive and not force:
     item.ItemStatus = Skipped; reason = "locked"
     if 指纹变化: markStaleOnly()      # 只标记，不动内容
     return                            # 永不写证据
```

### 4.2 生成步骤

```
1 取检查项     ← v_check_item_context（条款+部门+owner+阶段）
2 取条款侧     ← v_clause_profile（原 attr JSON + ClauseText + AlignType）
3 取事实侧     ← cert_doc_fact 按 (EnterpriseCode, ProcessDomain, RecordType) 过滤
                + cert_document_extraction 的元信息与 filled 状态
4 选骨架       ← 按 EvidenceForm + 章节角色取骨架编号（代码侧映射表）
5 取风格包     ← cert_prompt_template(PromptCode=EVIDENCE_*, ScopeKey=OrgCode)
6 取示例       ← 案例库按 (ClauseCode, Dept, EvidenceForm) 取 3–5 条
7 调模型       → 建议稿 + 使用的事实清单 + 缺口清单
8 校验落库     → 事实溯源校验 → 写 cert_evidence / cert_check_result / cert_check_analysis
```

`v_check_item_context`（视图）一次输出：`CheckItemCode`、`ClauseCode`、`StandardCode`、`ClauseNumber`、`DeptCode`、`DeptName`、`OwnerCode`、`StageKind`、`EnterpriseCode`、`PlanCode`、`TaskCode`。

### 4.3 事实溯源校验（拦编造）

```
对生成稿做事实点抽取（日期/数值/文件名/编号）
逐个查 cert_doc_fact：
  命中 → 通过
  未命中 → 判为编造
    第一次：带"仅可用下列事实"重试一次
    第二次仍失败：降级为"缺口稿"（写明缺什么），标 NeedManual=1
```

### 4.4 落库字段映射

| 内容 | 表 |
|---|---|
| 证据正文、来源、锚点 | `cert_evidence`（`Snippet`/`Anchor`/`SourceCode`/`ContentMD5`/`CheckItemCode`） |
| 结论初值、缺口 | `cert_check_result`（`PrepState`/`AiConclusion`/`Reason`/`ResultStale`） |
| 指纹、快照、token、耗时 | `cert_check_analysis`（`EvidenceFingerprint`/`InputSnapshotJson`/`RunNo`/`IsCurrent`） |
| 用了哪几条事实 | `cert_check_analysis_evidence`（`SnippetSnapshot`/`ContentMD5Snapshot`） |

## 五、重跑与覆盖：全部由人决定

### 5.1 指纹的用途变了（只提示，不自动跑）

```
EvidenceFingerprint = sha256(sorted(证据 ContentMD5) + promptCode + promptVersion + 快照摘要)
```

用途只有一个：**判断"是否需要提示重跑"**。计算结果写进 `cert_check_result.StaleReason`，页面显示"有 2 条新证据，建议重跑"。

### 5.2 行为矩阵（修正后）

| 场景 | 锁定 | 指纹变化 | 系统行为 |
|---|---|:--:|---|
| 首次生成 | 否 | — | 生成建议稿 |
| 再次勾选，无变化 | 否 | 否 | **跳过**，沿用（`Skipped/no_change`） |
| 再次勾选，有新增文档 | 否 | 是 | **不自动跑**；标 `ResultStale=1`，队列项 `Skipped/suggest_rerun`，页面提示由人点"重跑" |
| 人点"重跑"（未锁） | 否 | 任意 | 执行，`RunNo+1`，旧分析 `IsCurrent=0` |
| 人点"重跑"（已锁） | 是 | 任意 | 需先解锁或显式"强制覆盖"，否则拒绝并提示 |
| 审核员改过并锁定 | 是 | 任意 | **绝不覆盖**，只提示"已锁定" |
| 审核员解锁 | 否 | 是 | 下一次跑才会覆盖 |

一句话：**没有"自动重跑"这条路。系统只做三件事：跑一次、跳过、提示你可以重跑。**

### 5.3 锁定

| 项 | 值 |
|---|---|
| 粒度 | 检查项（`cert_check_lock.CheckItemCode`） |
| 自动锁触发 | 编辑证据文本 / 改结论 / 显式点锁定 |
| `LockSource` | `manual_edit` / `conclusion_edit` / `manual_lock` |
| 解锁 | `IsActive=0`，`UnlockedBy/At` 留痕 |
| 历史 | 锁不删 `cert_check_analysis`，历次 `RunNo` 可回溯 |

## 六、状态机

```
队列项：Pending → Processing → Completed
                            ↘ Skipped(no_change | locked | suggest_rerun | not_applicable)
                            ↘ Failed →（未超限）Pending →（超限）FailedFinal
```

| `cert_task_item.AnalysisState` | 含义 |
|---|---|
| `none` | 未跑 |
| `suggested` | 已产出建议稿（**默认终态**） |
| `stale` | 建议稿存在但有更新，待人工决定 |
| `failed` | 失败 |
| `skipped` | 锁定/无变化/未适用 |

| `cert_task_item.EvidenceState` | 含义 |
|---|---|
| `empty` / `ready` / `stale` | 无证据 / 有建议稿 / 已失效 |

| # | 用户动作 | 系统 | 队列 / 表 |

## 九、分期

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 补 3 属性 + 2 属性改类型 + 3 字典 + 对齐表；跑 320 条条款属性 | 空值 <5%，同号不同义校验通过 |
