# 文档提示词三类改造：语义分析 → 引用式提取 / 明细式提取 V1

> 归属已冻结：**条款属性池、文档结构与提取规则、与机构无关**（平台一套）；**只有证据生成规则按机构**。
> 本文定义平台侧 3 条文档提示词，并把它们的输入、输出、落库字段、与条款属性池的唯一接点写死。
> 三条提示词一次性只处理 **一个文档 × 一个标准**（结论准确优先于 token 成本）。

---

## 一、提示词清单

| # | PromptCode | 名称 | 输入单位 | 输出 | 归属 |
|---|---|---|---|---|---|
| 1 | `doc_semantic` | 文档语义分析 | 文档 × 标准 | 两道闸 + 类型 + 过程 + 条款提示 + 6 字段 + 文档级疑点 | 平台 |
| 2 | `doc_extract_cite` | 引用式提取 | 文档 × 标准（`ExcerptStyle=cite`） | 条目数组：章节号 + ≤60 字要点 | 平台 |
| 3 | `doc_extract_detail` | 明细式提取 | 文档 × 标准（`ExcerptStyle=detail`） | 行级事实数组 + 表头 + 疑点 | 平台 |
| 4 | `evidence_gen`（待建） | 审核发现/审核证据 | 检查项 × 条款 | 证据发现 / 疑点 / 审核证据段落 | **机构** |

**为什么必须两次调用**：语义分析只回答"这是什么、能不能用"；提取才回答"里面有什么事实"。合并的后果是"还没判断能不能用就开始提内容"，目录页、合同页、签字封面都会被提成证据。

---

## 二、`doc_semantic`：契约

### 2.1 输入

| 占位符 | 内容 | 来源 |
|---|---|---|
| `{{standard_name}}` | 标准全名（如 GB/T 19001-2016 质量管理体系 要求） | `cert_iso_standard` |
| `{{doc_name}}` | 文件名（含扩展名） | 上传记录 |
| `{{doc_md}}` | 文档 Markdown 正文（超长按页截断，≥ 12 万字符时分段调用后合并） | anydoc → md |
| `{{process_list}}` | 过程域码表（10 项，带中文名） | `Sys_Dictionary.process_domain` |
| `{{clause_brief}}` | 该标准叶子条款清单（条款号 + 标题，一行一条） | `cert_iso_clause` |

### 2.2 输出字段

| 字段 | 取值 | 落地列 |
|---|---|---|
| `IsSystemDoc` | `true` / `false` | `cert_enterprise_doc_profile.IsSystemDoc` |
| `DocType` | 10 类之一（见 2.3） | `.DocType` |
| `ProcessDomains` | 过程域码数组，可空 | `.ProcessDomains`（JSON） |
| `ClauseHints` | 条款号数组（`["8.4","8.5.1"]`），可空 | `.ClauseHints`（JSON） |
| `Extractable` | `true` / `false` | `.Extractable` |
| `ExcerptStyle` | `cite` / `detail` / `none` | `.ExcerptStyle` |
| `DocTitle` | 文档正式标题 | 6 字段之① |
| `DocCode` | 文件编号（如 `SN/QES-CX-08-2026`） | 6 字段之② |
| `DocVersion` | 版本号（`A/0`、`2026 版`） | 6 字段之③ |
| `OwnerDept` | 归口部门（原文写法） | 6 字段之④ |
| `Period` | 记录覆盖期间（`2025-01~2025-12`；无则空） | 6 字段之⑤ |
| `Confidence` | 0–1 | `.Confidence` |
| `Doubts` | 数组（见 2.4） | `cert_doc_doubt` |

**6 字段只填一次，不做条款级重复**：这是文档的"身份证"，后续所有条款调用共用（K2 槽位 = 事实字段）。

### 2.3 `DocType` 10 类与提取策略

| DocType | 中文 | ExcerptStyle | 典型判据（文件名/内容特征） |
|---|---|---|---|
| `manual` | 手册 | cite | 含"手册""管理手册"，有目录 + 条款号 |
| `procedure` | 程序文件 | cite | 含"程序""控制程序"，编号 `-CX-`，有目的/范围/职责段 |
| `work_instruction` | 作业指导书 | cite | 含"指导书""操作规程""工艺卡"，针对具体工序 |
| `record` | 记录 | detail | 表单编号 + 表头字段 + 行数据 + 签批栏 |
| `ledger` | 台账 | detail | 多行登记表（设备台账、培训台账、合同台账） |
| `certificate` | 资质证书 | detail | 证书名 + 证书编号 + 有效期 + 发证机构 |
| `contract` | 合同协议 | detail | 甲方乙方 + 标的 + 期限 + 签章 |
| `law` | 法律法规 | cite | 法规名 + 条款号 + 发布机构 |
| `org_chart` | 组织架构 | cite | 部门框 + 汇报线 |
| `other` | 其他体系文件 | cite | 是体系文件但归不进上面 9 类 |

`IsSystemDoc=false` ⇒ `DocType=other`、`ExcerptStyle=none`，后面全部跳过（连 Gap 都不打开）。

### 2.4 `Doubts`（文档级疑点，只在文档内部找，不推论外部缺口）

| Type | 判据 |
|---|---|
| `empty_field` | 表头有字段、行内空白（如检验记录"结论"列空） |
| `expired` | 有日期且已超过合理性窗口（记录 >12 个月、证书已过期、培训早于上岗） |
| `no_sign` | 有签批栏但无签名/日期 |
| `missing_seq` | 编号跳号（`QC-001, 002, 004`），或有起无终 |
| `insufficient_count` | 台账/记录条数明显不足（如 12 个月只有 2 条，而文档自称月度） |
| `empty_doc` | 有一类文档但内容只有封面/目录（这一类**直接判 Extractable=false**） |
| `other` | 其他可指认缺陷 |

每条必须带 `Loc`（页码 / 表名 / 行号），否则不许输出 —— 疑点要能追溯到原始文档。

## 三、`doc_extract_cite`（引用式）

适用 `ExcerptStyle=cite`：手册、程序文件、作业指导书、法律法规、组织架构。

**只做"索引 + 要点"，绝不抄正文**（用户口径：手册复杂，外审只需简单引用）。

输出：

```json
{
  "Entries": [
    {
      "ClauseHint": "8.4",
      "Loc": "P12 §8.4 采购",
      "Heading": "8.4 采购",
      "Point": "规定了供方评价、选择、绩效监视与再评价的职责与准则，共 42 字以内的要点",
      "FileRef": "SN/QES-CX-08-2026 采购控制程序"
    }
  ],
  "CoveredProcesses": ["purchase"],
  "Doubts": []
}
```

硬规矩：`Point` ≤ 60 字，是"这条款在这份文件里说了什么"的概括，不是原文摘抄；一份程序文件通常产出 1–8 条，不追求覆盖全部条款。

## 四、`doc_extract_detail`（明细式）

适用 `ExcerptStyle=detail`：记录、台账、证书、合同。

**一次抽整本**（不按条款逐条跑），行级落地过程归属 —— 因为同一本《质量记录汇编》里，采购记录与内审记录的过程不同，决定它能不能被 8.4 / 9.2 调用。

输出：

```json
{
  "Sheets": [
    {
      "Name": "进货检验记录",
      "Loc": "P21 表2",
      "Columns": ["日期","物料名称","批号","检验项目","结论","检验员"],
      "RowsTotal": 12
    }
  ],
  "Facts": [
    {
      "Loc": "P21 表2 第3行",
      "Date": "2025-03-14",
      "RecordNo": "IQC-2025-031",
      "Object": "6061 铝棒",
      "Item": "进货检验",
      "Result": "合格",
      "Signature": "李×",
      "ProcessDomain": "inspection",
      "ClauseHints": ["8.4.2","8.6"],
      "Quote": "≤100 字的原文关键行（可含编号/结论）"
    }
  ],
  "Doubts": []
}
```

硬规矩：
- `Quote` ≤ 100 字，必须能在原文中定位；`Loc` 必须给页码 + 表/行号。
- `Result` 只写原文结论词（合格/不合格/通过/让步接收），⛔ 不许自己判"符合"。
- 行数上限 200 行/文档；超长取前 200 行 + `Truncated=true`，⛔ 不许抽样丢行（宁缺不许编）。
- 空行、合计行、页脚不计入 `Facts`。

## 五、落库结构（两层）

| 层 | 表 | 说明 |
|---|---|---|
| 文档级（6 字段 + 两道闸 + 类型 + 过程 + 条款提示） | `cert_enterprise_doc_profile` | 一行 = 一个文档 × 一个标准；`StandardCode` 参与主键定位 |
| 行级事实 | `cert_doc_fact` | 一行 = 一条事实；带 `ProcessDomain` / `ClauseHints` / `Loc` / `Quote` |
| 疑点 | `cert_doc_doubt` | 一行 = 一条疑点；`Level=doc`，带 `Loc` |

> 行级事实必须落行，不许把整本记录塞进一个 JSON 字段 —— 否则条款调用时无法按过程/条款过滤，等于没写。

---

## 六、与条款属性池的唯一接点

```
L1 条款属性池（9 条，答"要求什么"）     L2 文档（6 字段 + facts，答"有什么事实"）
        └──────────┬──────────────────────────┘
                  唯一接点 = ClauseHints + ProcessDomains
                          ↓
        L3 审核发现/审核证据（按机构，用属性决定段落骨架 R1–R7 × F1/F2）
```

- 属性池**不认识**文档；文档**不认识**属性池。两边只在"条款相关"标记上对齐。
- 因此文档提示词里 ⛔ 不许出现"审核结论""符合性判断""应该开什么 NC"—— 那是 L3 的事。

## 七、调用量与耗时（实测口径）

| 项 | 估算 |
|---|---|
| 语义分析 | 文档数 × 标准数（200 份 × 3 = 600 次） |
| 提取 | 同上（每份只跑一次，按 `ExcerptStyle` 二选一） |
| 单次耗时 | 语义分析 3–6s；提取（记录类，200 行）8–15s |
| 单标准 200 份 | 约 25–40 分钟（串行；LLM 端点并发必 429） |
