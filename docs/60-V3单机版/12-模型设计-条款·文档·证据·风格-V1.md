# 模型设计 V1：条款 · 文档 · 证据 · 风格

> **修订（依据 14 号，2026-11-10）**
> - 提示词由"四类"改为**三类**：①条款属性 ②文档内容（含画像与提取两个子模式）③审核证据（按机构多套）。
> - `MergeMode` **不再作为规则**参与自动决策（合并与否由审核员在计划里定）；属性实际 10 条 + 1 条提示字段。
> - §1.3 的"章节角色"升级为**功能角色 R1–R7**（情境/领导/策划/支持/运行/绩效/改进），章号只用于排版顺序；跨标准按条款内容判角色，详见 14 号 §四。

> 本文件只讲**业务模型**：有哪些概念、每个概念有哪些属性、属性如何决定"该提取什么、该写成什么"。**不讲表结构、不讲队列、不讲代码**——那些在《实现设计》里。
>
> 一条贯穿全篇的铁律：**属性只描述"业务事实与形态"，绝不描述"怎么提取、怎么写"。** 提取与生成的方法是提示词的事，混进属性会让模型无法复用、无法校验。

---

## 零、模型总览

系统只需要四个模型，其余都是它们的组合：

| 模型 | 回答什么问题 | 谁消费 |
|---|---|---|
| **条款模型** | 这条标准要求企业做什么？证据是什么形态？ | 证据生成、条款属性提示词 |
| **文档模型** | 这份资料能不能用？能提供什么事实？ | 文档提取提示词、证据生成 |
| **证据模型** | 一个检查项该写成几段？段落之间能不能合？ | 证据生成、报告排版 |
| **风格模型** | 同一个事实，这家机构该怎么措辞？ | 报告输出 |

三层分离（这是本设计能成立的前提）：

```
模型层  —— 条款/文档/证据/风格的概念与属性     （本文件）
属性层  —— 模型上的具体取值，按标准实例化       （本文件 §1.4、§2.4）
提示词层 —— 拿属性决定"怎么抽、怎么写"          （本文件 §5 + 08 号）
```

**模型与机构无关，风格与机构绑定。** 条款、文档、证据三个模型在所有机构下完全一致，只有风格模型随机构换。

## 一、条款模型

### 1.1 条款本体：三样东西，不细分

| 组成 | 内容 | 说明 |
|---|---|---|
| 编号 | `4.1`、`6.1.2`、`8.5.1` | 主键一半（另一半是标准） |
| 标题 | "理解组织及其环境" | 用于检索与展示 |
| 原文 | 条款正文 | **通过关联获取，不单独建实体** |

**明确不做的：**

- 不把条款原文拆成 a/b/c 分项。条款在证据里始终当作**一个整体**，一段文字；
- 不为条款原文单独建一张表。原文可以在需要时从标准文档关联过来，属性挂接阶段根本用不到原文。

**为什么"挂接阶段用不到原文"是对的**：属性描述的是"这条要求企业做什么"，模型看标题 + 少量原文即可判断；只有**证据生成**时，才需要把原文（以及机构问句版）拿来看，那时按检查项关联即可。

### 1.2 条款分类：证据形态 A–F（挂到属性 `EvidenceForm` 上）

这是整个模型的核心分类，因为它直接决定"报告里这条证据长什么样"。

| 型 | 名称 | 业务含义 | 典型条款 | 主要来源 | 报告形态 | 可自动化 | 需现场 |
|---|---|---|---|---|---|:--:|:--:|
| **A** | 文件型 | 组织用一份纲领性文件承诺怎么做 | 4.1–4.4、5.2、6.2 | 手册 | **原文引用**（不改写） | 高 | 否 |
| **B** | 制度型 | 有一份程序规定了流程 | 7.5、8.4、9.2、9.3 | 程序/三阶 | 点名（文件名+编号）+ 一句概括 | 高 | 否 |
| **C** | 台账型 | 有清单/名录/台账在维护 | 7.1.5、8.4 供方、7.5.3 受控清单 | 清单 | 条目归纳（"共 N 项"或"抽看 N 项"） | 高 | 否 |
| **D** | 记录型 | 有表单在填写，能抽样看明细 | 7.2、8.5、8.6、9.1 | 记录 | **抽样 + 字段明细** | 中 | 否 |
| **E** | 结论型 | 有一份报告给了结论 | 9.2 内审、9.3 管评、9.1.2 合规性评价 | 报告 | 结论句 + 日期 + 要素 | 高 | 否 |
| **F** | 现场型 | 只能到现场看/问/测 | 8.1 现场、5.4 协商参与、7.1 设施 | 无（人工） | 观察/访谈句 | 无 | 是 |

**分型的判据（三条，按顺序判）：**

```
1 有没有"结论句"？有 → E
2 有没有"逐条可数的清单"？有 → C
3 有没有"填写的表单明细"？有 → D
4 有没有"纲领性承诺文件"（方针/目标/范围）？有 → A
5 有没有"规定流程的程序文件"？有 → B
6 都没有、只能现场确认 → F
```

**同一标准内为什么还要分型**：9001 第 8 章里 8.4（合同字段）、8.5（过程参数）、8.6（放行判定）、8.7（不合格数量）四类事实完全不同，用一条提示词写必然串。所以分型不是按章分，而是**按证据形态分**。

### 1.3 章节角色（辅助分类，不单独成属性）

| 角色 | 章 | 对证据的影响 |
|---|---|---|
| 组织 | 4 | 多为 A/B，句子短，事实少 |
| 领导 | 5 | A/E 为主，结论句占比高（实测 27–31%） |
| 策划 | 6 | B 为主，程序引用率最高（33%） |
| 支持 | 7 | C/D 为主，清单与记录 |
| 运行 | 8 | D 为主，句子最长（36 字），字段最密 |
| 绩效 | 9 | E 为主，结论 + 日期 + 要素 |
| 改进 | 10 | D/E 混合，不合格与措施 |

章节角色决定**段落顺序**与**句式偏好**，不决定"抽什么"。

### 1.4 属性池：11 条，每条只答一个业务问题

| # | 属性 | 语义 | 取值 | 回答的业务问题 | **禁止写什么** |
|---|---|---|---|---|---|
| 1 | `ClauseIntent` | 条款作用 | 一句话 ≤30 字 | 这条要求组织做什么 | 禁止写"如何提取得分点" |
| 2 | `Obligation` | 约束强度 | shall / should / may / note | 这是强制的还是建议的 | 禁止写"义务动词正则表" |
| 3 | `Applicability` | 适用性 | general / conditional | 所有企业都要做，还是看情况 | — |
| 4 | `ApplicabilityCondition` | 适用条件 | 原文表述 | 什么情况下才适用 | 禁止写"触发词列表" |
| 5 | `Process` | 过程域 | 固定字典 1–3 项 | 这事归哪些部门管 | 禁止写部门名（要写过程域） |
| 6 | `Artifacts` | 企业应提供的资料 | 资料类别名 ≤6 条 | 要哪些材料才能证明符合 | **禁止写文件名、禁止写抽取字段** |
| 7 | `EvidenceChain` | 取证顺序 | 3–5 步业务动作 | 审核员按什么顺序取证 | **禁止写提示词步骤、禁止写句式** |
| 8 | `Severity` | 严重度基线 | critical / major / minor | 违反这条通常算多严重 | 禁止写判定规则 |
| 9 | `EvidenceForm` | 证据形态 | A–F | 报告里这条长什么样 | 禁止写句式模板 |
| 10 | `MergeMode` | 合并方式 | by_clause / by_standard / standalone | 能不能和别的条款合成一段 | 禁止写合并算法 |
| 11 | `DocCheckMode` | 文档核对方式 | required / optional / none | 必须有文档证据，还是可以只现场 | 禁止写检查清单 |

**对现有设计的修正：** 现在库里 `Artifacts`、`EvidenceChain` 的类型是 `prompt`（存提示词片段）。这违反了上面的铁律，**应改为 `text`**——它们存的是业务事实（"要哪些资料""按什么顺序取证"），措辞由提示词模板负责。否则同一句业务事实会被复制到多个提示词里，改一次要改多处。

### 1.5 跨标准对齐（属性 `MergeMode` 的来源）

条款与条款之间只有三种关系：

| 关系 | 业务含义 | 对证据的影响 |
|---|---|---|
| **同义**（A） | 两个标准同号条款说同一件事 | 可以合成一段，末尾加括注 |
| **不同义**（B） | 同号但说的是不同的事 | **必须分开写**，合了就是文不对题 |
| **跨号对应**（C） | 不同号但内容相关 | 不合并，最多交叉引用 |

典型：6.1.2（B：风险机遇 / 环境因素 / 危险源）、8.2（B：产品服务要求 / 应急准备）、9.1.2（B：顾客满意 / 合规性评价）、7.1.5↔9.1.1（C：监视测量资源）。

**这个判断是模型层的，不是提示词层的**——不能交给模型临场猜，否则 6.1.2 必错。

### 1.6 条款模型的输出

一个条款分析完，产出一份"条款画像"：

```
条款画像 = 编号 + 标题 + （原文，用时关联）+ 11 个属性值
```

这份画像就是所有下游提示词的输入，**不含任何提取方法**。

## 二、文档模型

### 2.1 四个判断（这是文档模型的骨架）

每份文档进来，只判四件事：

| 判断 | 取值 | 业务含义 | 判错的后果 |
|---|---|---|---|
| `relevance` | 体系相关 / 弱相关 / 无关 | 是不是体系资料 | 无关文档进队列，浪费成本 |
| **`clause_related`** | **有关 / 无关** | **这份资料是否可能支撑某个条款** | 把宣传册当证据，报告写空话 |
| **`extract_need`** | **需要提取 / 仅登记 / 不处理** | **是否要读出内容供报告使用** | **强行提取 → 模型编造** |
| `filled` | 已填写 / 空白模板 / 扫描件 | 有没有实际内容 | 空表被写成"抽看 3 份" |

**`clause_related` 与 `extract_need` 是两个不同的判断，这是你提的关键点：**

> 目录可能与体系认证有关（比如"4 记录表单"整个目录都在体系范围内），但具体那份表**对报告提不出任何有用信息**（比如一张只有表头的空白表、一份内部通知、一份与本条款无关的会议签到）。

所以判断链是：

```
relevance（是不是体系资料）
    → clause_related（能不能支撑某条款）
        → extract_need（值不值得读内容）
```

三种组合的处置：

| 组合 | 典型 | 处置 |
|---|---|---|
| 相关 + 有关 + 需提取 | 手册、程序、有数据的记录 | 全流程提取 |
| 相关 + 有关 + 仅登记 | 空白表单、扫描看不清的表 | **只登记存在与表单名称**，不抽内容 |
| 相关 + 无关 + 不处理 | 内部通知、与条款无关的会议材料 | 入档，不进证据池 |
| 无关 | 产品宣传、财务账 | 直接排除，不出现在报告 |

### 2.2 文档七类 × 四个判断

| 类 | 是否体系 | 通常与条款有关 | 通常需提取 | 主要服务哪些条款 |
|---|---|:--:|:--:|---|
| 手册 | 是 | 是 | **是**（只 7 处） | 4、5、6、7 的纲领部分 |
| 程序 | 是 | 是 | **否**（只要元数据） | 7.5、8.x 流程 |
| 三阶（作业指导书/制度） | 是 | 是 | 否（只要元数据） | 8.5 作业方法 |
| 记录 | 是 | 是 | **是**（按类型） | 7.2、8.5、8.6、9.1 |
| 清单/台账 | 是 | 是 | 是（条目） | 7.1.5、8.4、7.5.3 |
| 证照/资质 | 是 | 是 | 是（字段） | 5、7.1、8.4 外包 |
| 空表 / 无关 | — | 否 | **否** | — |

### 2.3 每类"能提供什么 / 报告怎么写 / 用什么方式"

| 类 | 能提供的事实 | 报告里的写法 | 提取方式 |
|---|---|---|---|
| 手册 | 方针、目标、范围、删减、部门职责、关键/特殊/外包过程、元信息 | **原文引用** | 规则定位 7 处 + 模型兜底 |
| 程序 | 文件名、编号、版本、日期、一句概括 | 点名 + 一句概括 | **规则**（正则 + 动词映射） |
| 三阶 | 同上 | 同上 | 规则 |
| 记录 | 按记录类型的字段（培训/检验/校准/合同/管评/内审/证照） | 抽样 + 明细 | 规则优先，模型兜底 |
| 清单 | 条目（名称/编号/版本/状态） | 共 N 项 / 抽看 N 项 | **规则** |
| 证照 | 证号、发证机关、有效期、范围 | 证号 + 有效期 | 规则 + OCR |
| 空表 | 仅表单名称与记录项目 | "已规定记录项目与保存要求" | **不提取** |

### 2.4 文档属性（画像）语义清单

| 属性 | 语义 | 用途 |
|---|---|---|
| 分类 | 七类之一 | 决定提取方式 |
| 用途（一句话） | "明确了采购与供方管理要求" | 直接进报告概括句 |
| 过程域 | 归属部门 | 与条款 `Process` 匹配 |
| 是否与条款有关 | 有关/无关 | 决定进不进证据池 |
| 是否需提取 | 需要/仅登记/不处理 | 决定调不调模型 |
| 填写状态 | 已填/空白/扫描 | 决定能不能写"抽看" |
| 置信度 | 0–1 | 低置信转人工 |

**注意：文档属性里同样不写"怎么抽"**——不写正则、不写字段清单、不写句式。字段清单属于"记录类型 → 字段"的提取规则，归提示词层。

## 三、证据模型

### 3.1 一个条款 = 一段（不细分）

**明确不做：** 不按 a/b/c 分项拆段。一个条款在报告里就是一段文字，分项只在生成时作为"要覆盖的要点"参考，不体现为多个段落。

**理由：** 实测报告里条款行与段落是一对一（科斯亚 27 行 = 27 个条款号，一段一条款）。分项拆段会让报告变成教科书，审核员不认。

### 3.2 检查项 = 条款 × 部门（部门可为空）

| 形态 | 例子 | 报告表现 |
|---|---|---|
| 条款 + 具体部门 | 8.5.1 × 生产部 | 一段，主语是生产部 |
| 条款 + 空部门 | 5.1 × （空） | 一段，主语是"公司/最高管理者"，通用段 |
| 多条款 + 多部门 | 一次计划里勾 6 条 × 4 部门 | 拆成多个检查项，**按条款一段一段写** |

**审核计划不做限制**：既允许"单条款 + 空部门"，也允许"多条款 + 多部门"。系统在生成时**按条款拆分**，一条条款一段，部门作为限定。

### 3.3 一段证据由三样东西组成

| 要素 | 来源 | 例 |
|---|---|---|
| 事实 | 文档事实条目 / 现场记录 | 《培训记录》3 条、日期 2026-03-12 |
| 组织方式 | 条款分类（EvidenceForm）+ 章节角色 | D 型 → "抽看 N 份…明细…判定合格" |
| 结论词 | 风格模型 | "符合要求""有效" |

三者缺一不可：只有事实没有组织方式是流水账；只有组织方式没有事实是空话；没有结论词报告不成立。

### 3.4 合并三规则（模型层判定）

| 情况 | 规则 | 依据 |
|---|---|---|
| 跨标准·同义（A 类） | **可以合**，末尾括注 | 同一件事的三种表述 |
| 跨标准·不同义（B 类） | **必须分** | 6.1.2 三标准各说各的 |
| 同标准·跨条款 | **默认不分**，只按预定义合并组合并 | 条款逻辑相邻但事实不同 |
| 同条款·跨部门 | **绝对不分** | 不同部门的事实不同源 |

判定顺序：先判"是不是 B 类"，再判"同不同部门"，最后才看"要不要按合并组合"。

### 3.5 证据的性质：**建议，不是结论**

| 性质 | 说明 |
|---|---|
| 生成即草稿 | 系统产出的每一段都是"建议稿"，不是最终报告内容 |
| 人可改 | 审核员可改文字、改结论、删段 |
| 改后锁定 | 改过即锁定（按检查项），后续不再被覆盖 |
| 重跑由人决定 | **系统永不自动覆盖**；即使发现文档变了、提示词换版了，也只提示"建议重跑"，由审核员点 |
| 结论权在人 | 符合/不符合、严重度，最终由人确认 |

## 四、风格模型（唯一与机构绑定的模型）

### 4.1 六个维度

| 维度 | 内容 | 例（ACM） |
|---|---|---|
| 句式 | 按 EvidenceForm 与章给出的骨架 | "抽看 3 份成品检验记录，检验项目含外观、尺寸，判定均为合格" |
| 结论词 | 固定词表 | 符合要求 / 有效 / 适宜 / 未发现不符合 |
| 要求列 | 是否输出、用问句还是原文 | 用机构问句版 |
| 合并策略 | 同号是否合段 | 合成一段（by_clause） |
| 段落顺序与层级 | 4→10 顺序、是否加小标题 | 按章顺序，章内连续 |
| 字数 | 单段上限、句长偏好 | ≤120 字，中位 26 字 |

### 4.2 风格只影响"怎么说"，不影响"说什么"

- 同一检查项，换机构 → 事实、条款、部门都不变，只有措辞变；
- 所以风格模型**不回流**到条款/文档/证据模型；
- 风格模型可以有多个方案并存（初次认证/监督/再认证，或换版过渡）。

## 五、属性如何驱动提示词（本文件最重要的部分）

属性本身不写"怎么提取"，但属性**决定**提示词怎么变。这一章把"什么属性 → 影响哪条提示词的哪一段"写死。

### 5.1 四类提示词的分工

| # | 提示词 | 输入 | 输出 | 是否含机构 |
|---|---|---|---|---|
| 1 | 条款画像 | 标准口径卡 + 条款标题 + 少量原文 | 11 个属性 | 否 |
| 2 | 文档画像 | 文件名 + 目录 + 前 1500 字 | 分类/用途/过程域/**条款相关**/**需提取**/填写状态 | 否 |
| 3 | 文档提取 | 文档正文 + 提取模式 | 事实条目（键/值/位置/原文） | 否 |
| 4 | 证据生成 | 条款画像 + 事实条目 + 分类骨架 + 风格包 | 一段建议稿 + 事实清单 + 缺口 | **是** |

**关键：1→2→3 全部与机构无关；只有 4 带风格。**

### 5.2 逐属性 → 提示词消费表

| 属性 | 被哪条提示词消费 | 具体影响什么 |
|---|---|---|
| `ClauseIntent` | 证据生成 | 决定这段的"主题句"往哪写（写"体系范围"还是"职责落实"） |
| `Obligation` | 证据生成 | 决定语气强度：shall → "应…并已实施"；should → "宜…，组织已…"；may → 不写强制措辞 |
| `Applicability` | 证据生成 | general → 直接写；conditional → 先写"适用情况下…"再写事实 |
| `ApplicabilityCondition` | 证据生成 | 作为条件前置句 |
| `Process` | 证据生成 + 审计计划 | 决定取哪些部门的事实；空部门时给通用段 |
| `Artifacts` | 证据生成 | 决定**该去哪类文档里找事实**（不是句子内容，是检索范围） |
| `EvidenceChain` | 证据生成 | 决定段落内部顺序（先观察后查文件再抽样） |
| `Severity` | 证据生成 | 只影响"若判不符合时的措辞"،符合段不体现 |
| `EvidenceForm` | **证据生成（骨架选择）** | 决定用 A–F 哪套句式 |
| `MergeMode` | 证据生成（合并判定） | 决定能否与相邻条款合段 |
| `DocCheckMode` | 证据生成（前置判断） | required 且无文档事实 → 输出"缺口"，不硬写；none → 只允许现场句 |

### 5.3 条款分类 → 提取与写作规则（按型逐条写清）

| 型 | 必须先满足的条件 | 提取动作 | 写作骨架 | 不满足时怎么办 |
|---|---|---|---|---|
| **A** | 有手册且抽到该类事实 | 取方针/范围/职责原文 | "公司编制了《××手册》××编号，明确了……" + 原文引用（可截取不改写） | 手册缺该段 → 降级为 B 型写法 |
| **B** | 有程序且元数据齐全 | 只要文件名/编号/版本/日期 | "组织编制了《××控制程序》××编号，明确了××的控制要求" | 编号缺失 → 只写文件名，并标缺口 |
| **C** | 有清单且条目可读 | 读条目、计数 | "共列入 N 项，现行有效" 或 "抽看其中 N 项：1、…2、…" | 条目不可读 → 只写"建立了××台账" |
| **D** | 有记录且非空表 | 按记录类型抽字段（培训/检验/校准/合同/管评/内审/证照） | "抽看 N 份××记录：1、…（字段明细）…，判定合格" | 空表 → 改 C 型写法"已规定记录项目" |
| **E** | 有结论类报告 | 抽结论句 + 日期 + 依据 + 要素 | "查见《××报告》，××年××月实施，结论为有效" | 无结论句 → 标缺口，转人工 |
| **F** | 无文档依赖 | 不提取 | 观察/访谈句，人工或语音转写 | 无现场记录 → 输出"待现场确认"占位 |

### 5.4 文档属性 → 提取规则（三个属性各管一段）

| 判断 | 取值 | 对应动作 |
|---|---|---|
| `extract_need` | 需要提取 | 走该类的提取提示词 |
| | 仅登记 | **只写"表单名称 + 记录项目 + 保存要求"**，不调模型读内容 |
| | 不处理 | 入档，不进证据池，报告不提 |
| `clause_related` | 有关 | 参与按 `Process` / 条款的检索 |
| | 无关 | 即使 relevance 是"体系相关"，也不参与证据检索 |
| `filled` | 已填写 | 允许"抽看 N 份 + 明细" |
| | 空白模板 | 禁止出现"抽看"，只能写"已建立表单" |
| | 扫描件 | 允许引用证号/日期等显见字段，明细转人工 |

**这三条正是"防止模型编造"的闸门**：实测尚龙 7 份、科斯亚 3 份记录是空表，不闸住就会写出"抽看 3 份，明细如下"。

### 5.5 一条条款走完全程的样子（例：8.5.1 × 生产部）

```
条款画像：ClauseIntent=生产过程受控；Obligation=shall；Process=[production]
          Artifacts=[生产计划, 工艺文件, 首件检验记录, 巡检记录]
          EvidenceForm=D；MergeMode=by_clause；DocCheckMode=required
        ↓
文档检索：按 Process=production + clause_related=有关 找到
          《生产控制程序》(B 元数据)、《首件检验记录》(D 明细)、《工艺卡》(B)
        ↓
事实条目：首件检验 3 批次、巡检 6 次、参数记录（温度/压力/时间）
        ↓
风格包（ACM）：D 型 8 章骨架 + 结论词"符合要求"
        ↓
输出一段建议稿："生产部按《生产控制程序》实施生产过程控制，
抽看 3 批次首件检验记录与 6 次巡检记录，检验项目含外观、尺寸、
性能，结果均判定合格。"
```

整段**没有一个字是凭空造的**：文件、数字、字段都来自事实条目，句式来自骨架，措辞来自风格包。

## 六、模型明确不做的事（边界）

| 不做 | 原因 |
|---|---|
| 不建条款原文实体 | 用时关联即可，属性挂接阶段用不到 |
| 不把条款拆 a/b/c | 报告一段一条款，拆了反而不像报告 |
| 不做证据级锁定 | 报告的核心单位是检查项 |
| 不自动重跑、不自动覆盖 | 生成即建议，是否重跑由审核员判断 |
| 不在属性里写提取规则 | 属性是业务事实，方法归提示词 |
| 不让模型判断跨标准同义/不同义 | 6.1.2 这类必错，必须查对齐关系 |
