# 质量手册提取提示词优化方案 V1

> 结论先行：**质量手册不适合“整本手册 + 整本标准 + 全量条款”的一次性提取。**
> 应改成「清洗 → 章节索引（确定性）→ 按检查项取小节 → 小提示词判定」。
> 不是把提示词写得更长，而是把每次喂给模型的东西换掉。

---

## 一、实测对比（2026-11-11，`01管理手册QMS.doc` × iso9001）

### 1. 手册 Markdown 的真实结构

| 指标 | 实测 |
|---|---|
| 手册 Markdown 总字符 | 27,162 |
| 行数 / 空行 | 1,217 / 407 |
| 封面 + 更改页 + 目录对应表（首个条款标题之前） | 2,150 字符（7.9%） |
| 表格行 | 107 行 |
| `#` 标题总数 | 119 |
| 其中“数字开头”的条款型标题 | 111 |
| 标题文本超过 28 字（正文被误升为标题） | 6 条（如 `2.3 本手册的编号…执行《文件化信息控制程序》。`、`8.5.1.1 公司应在受控条件下…`） |
| 真正的条款区字符 | 24,901 |

**标题与标准条款的对应关系（关键）**

| 指标 | 实测 |
|---|---|
| 标准库内条款 | 94 |
| 手册条款型标题去重后 | 110 个编号（含 0.x / 2.x / 4.0 等手册自有章节） |
| 手册标题能直接命中标准编号 | **76 / 94** |
| 标准有、但手册没单独起标题 | 18 个：`3, 4, 6, 7, 8, 9, 10, 4.4.1, 4.4.2, 5.1.1, 5.1.2, 5.2.1, 5.2.2, 7.5.3.1, 7.5.3.2, 8.2.3.1, 8.2.3.2, 10.2.1, 10.2.2` |
| 这 18 个的性质 | **不是没有内容，而是被父条款章节吸收了**（如 4.4 一节覆盖 4.4.1/4.4.2；7.5.3 覆盖 7.5.3.1/7.5.3.2） |

> 这说明：质量手册的骨架本来就是“按标准条款号组织”的。**标题足以定位到 76 个条款，剩余 18 个可由父节映射解决。**
> 不需要把整本标准正文塞进去做全文语义搜索。

### 2. Markdown 与标准原文的差异

| 指标 | 实测 |
|---|---|
| 标准 Markdown 总字符（`MarkdownChars`） | 30,581 |
| 库内 94 条标准条款正文合计 | 15,558 字符（去标点/空白后 12,313） |
| 标准 Markdown 中“非条款正文”占比（页眉页脚、分页、版式、OCR 噪声） | **约 49%（按原始字符计）** |
| 手册 vs 标准条款正文的 8-gram 重合率 | **7.4%** |
| 手册独有 8-gram 比例 | **92.6%** |

> 两条结论：
> 1. 标准 Markdown 里真正有用的条款措辞约 1.5 万字，另外约 1.5 万字是版式噪声；**把 3 万字标准全文塞进每次提取，是在为噪声付 token 和时间。**
> 2. 手册不是标准原文的复制品（重合率仅 7.4%），它是企业自己的承诺与引用。**把标准全文放在模型眼前，反而会诱导模型用标准措辞“补写”手册摘录**，产生看似合理但手册里没有的 Anchor/Excerpt。

### 3. 当前一次性提取的实测结果

| 指标 | 实测 |
|---|---|
| 提示词总字符 | 59,651（模板 + 条款清单 + 文档段 27,162 + 标准原文 30,000） |
| 输入 tokens | 35,945 |
| 输出上限 | 8,192 tokens（本次 completion 正好 8,192） |
| 耗时 | **183,950 ms（约 3 分 4 秒）** |
| 输出字符 | 15,630，命中 `max_tokens` 截断，靠抢救解析 |
| 落库条款 | **34 / 76 个有标题的条款** |
| 丢弃 | **26 条**（模型返回的编号不在库内清单，含 4.4.1/6.1.1 这类被父节吸收的子条款） |

**为什么必然失败（算术问题）**

- 当前提示词要求每个条款给 1~2 段摘录 + Anchor + Title；
- 76 个条款 × 平均 200~400 字符 ≈ **15,000~30,000 字符**；
- 8,192 token 大约只能装 1.5 万中文字符；
- 只要条款数超过 ~40，就一定会截断；这不是“提示词写得不够好”，是**输出预算装不下全量条款**。

## 二、方案：把“整本一次提取”改成“章节索引 + 按检查项判定”

### 总览

| 层 | 做什么 | 是否调 LLM | 产出 |
|---|---|---|---|
| L0 清洗 | 去封面/更改页/目录/页眉页脚；标题分级纠偏；条款号归一 | 否 | 干净的手册分节树 |
| L1 索引 | 标题 → 条款号映射；父节覆盖子条款；标记空节/不适用 | 否（规则）或 1 次轻量校验 | `SectionMapJson` |
| L2 判定 | 按检查项取 1~3 个相关小节 + 条款要求（≤200 字），逐项判定 | 是 | 覆盖结论 + 原文 Anchor + 疑点 |

> 这与你说的“根据认证计划的检查项，一个一个提问，输入原始文档”是同一件事：
> **不是把整本手册喂给每个条款，而是先用标题把条款定位到小节，再只把这一小节喂给模型。**

### L0 清洗规则（确定性，先做，不改原文事实）

1. **截掉首个条款标题之前的全部内容**：封面、批准页、更改记录、目录对应表。
   - 本次可省 2,150 字符（7.9%）。
   - “目录与标准条款对应表”单独存为 `TocMapJson`，可用于校验标题映射，不进入正文。
2. **标题可信度降级**：满足任一条件 ⇒ 不作为章节标题，合并到上一节正文：
   - 标题文本 > 28 字；
   - 以“。”结尾，或含“组织应/公司应/本手册的…执行《…》”；
   - 下一行是明显续写（以“，”“以便：”“包括：”结尾）。
   - 本次识别出 6 条，典型：`2.3 本手册的编号…的控制执行《文件化信息控制程序》。`
3. **条款号归一**：
   - 去前缀（当前计划明细里出现的 `e 4.2` → `4.2`）；
   - `4.0 → 4`、`5.0 → 5`、`7.0 → 7`；
   - 去中文标点（`8.2.1、` → `8.2.1`）；
   - 保留 `8.3.4.1` 这类真实四级号。
4. **表格降噪**：只保留 `0.6 职能分配表`、`0.7 职责权限` 这类有审核价值的结构化表；更改记录、目录、版本表丢弃。其余表格转为 `TableBlock` 附在所属章节，不参与标题判定。
5. **不适用识别**：标题或首段含“不适用 / 删减 / 除外” ⇒ `IsNa=true`，必须同时抓取理由句；无理由 ⇒ 记为疑点。

### L1 章节索引

为每个章节生成一条：

```json
{
  "ClauseNo": "4.2",
  "HeadingPath": "4.0 组织环境 / 4.2 理解相关方的需求和期望",
  "Level": 2,
  "CharStart": 3412,
  "CharEnd": 3917,
  "TextLength": 505,
  "IsNa": false,
  "ChildrenCovered": ["4.2.1", "4.2.2"],
  "BodyHead": "……前 200 字……"
}
```

映射规则：

- 标题编号能精确命中标准条款 ⇒ 直接绑定；
- 标准有、手册无独立标题的子条款 ⇒ 绑定到最近的父节，标记 `CoverageMode=folded`；
- 标题编号是手册自有章节（0.x/1.0/2.x）⇒ 不参与标准条款映射；
- 章节标题含标准条款号但正文为空 ⇒ `EmptySection=true`，判定时直接给 `none` + 疑点，不调模型。

> 本次可得到约 76 个精确映射 + 18 个 folded 映射，覆盖率 94/94；`SectionMapJson` 体积约 20~40KB，存 mediumtext 足够。

### L2 按检查项取小节 + 判定

以当前计划检查项为例：

| 检查项条款 | 取哪些小节 | 送模型字符 |
|---|---|---|
| `4` | `4.0` 总节（含 4.1~4.5 标题导航） | ~800 |
| `4.2` | `4.2` 小节正文（父节标题作路径） | ~600 |
| `4.4` | `4.4` 小节 + 子条款 `4.4.1/4.4.2` folded 提示 | ~700 |
| `8.5.1` | `8.5.1` 小节 + `8.5.1.1~8.5.1.3` 子段 | ~1,200 |

取小节规则：

1. 精确命中 ⇒ 取本节；
2. 无本节但有父节 ⇒ 取父节，标记 `folded`；
3. 本节 > 3,000 字符 ⇒ 取“开头 1,500 + 结尾 1,000 + 含条款关键词的段落”，总长 ≤3,000；
4. 一次检查项最多取 3 个相邻小节，避免跨章拼接导致模型串读。

### 新提示词（质量手册专用，可直接替换当前 `doc_clause_extract` 的手册分支）

> 设计原则：**只给一节、只判一条/一组条款、只要短摘录、明确 folded/NA/空节。**

```text
你是质量管理体系（ISO 9001）审核员。现在只阅读企业《质量手册》的指定小节，
判断该小节对指定标准条款的覆盖情况，并给出可回查的手册原文依据。

【标准条款】
条款号：{{clause_number}}
条款标题：{{clause_title}}
要求原文（仅供理解要求，不是手册内容，禁止抄进 Excerpt）：
{{clause_requirement}}

【手册小节】
标题路径：{{heading_path}}
小节正文（原文，已清洗）：
<<<SECTION
{{section_text}}
SECTION

【判定口径】
1. 手册是“承诺/引用”，不是执行证据；小节写了“按《XX程序》执行”即算覆盖，但必须在 Excerpt 中保留该程序名。
2. 只依据本小节判断。本小节没有明确对应内容 ⇒ Coverage="none"，不得用标准条款原文补写。
3. 标题有条款号、正文为空或只有标题 ⇒ Coverage="none"，并给一条 Doubt（Type="empty_section"）。
4. 父节覆盖子条款 ⇒ Coverage="partial"，Judgement 必须写明“父节 X 覆盖 Y~Z”。
5. 标注“不适用/删减”的，必须有理由；无理由 ⇒ Doubt（Type="na_no_reason"）。
6. Anchor 必须是本小节里**逐字连续存在**的片段，≤30 字；Excerpt ≤60 字。找不到逐字片段 ⇒ Anchor 留空，不得编造。

【输出】只输出一个 JSON 对象，第一个字符 {、最后一个字符 }，不要代码块、不要解释：
{
  "ClauseNumber": "{{clause_number}}",
  "Coverage": "full | partial | none | na",
  "HeadingPath": "{{heading_path}}",
  "Anchor": "手册原文连续片段，≤30 字，可为空",
  "Excerpt": "手册原文摘录，≤60 字，可为空",
  "Judgement": "一句话结论，≤60 字",
  "Doubts": [
    { "Type": "empty_section | folded | na_no_reason | conflict", "Text": "≤40 字" }
  ],
  "NeedEvidence": ["现场需核实的证据，≤3 条，每条≤20 字"]
}
```

**为什么这样写有效**

- 输入从 59,651 字符降到 **1,500~3,000 字符**；
- 输出从 8,192 token 降到 **300~500 字符**，永远不会撞上限；
- 不给标准全文，模型没有“抄标准”的素材，只能抄手册；
- Anchor 强制逐字，可直接回查 Markdown 偏移，解决“摘录是模型编的”；
- folded/NA/空节三种结构性问题显式建模，不再靠模型自由发挥。

### 落地形态（与现有链路兼容）

| 现有 | 调整 |
|---|---|
| `ClauseExtractExecutor` 一次整本 + 全条款 | 增加 `ManualMode`：先建 `SectionMapJson`，再按条款批量判定 |
| `cert_document_extraction.ClauseNumbers` | 保留；新增 `SectionMapJson`（mediumtext）存索引 |
| `cert_document_extraction.ExtractMode` | 新增 `heading_index` / `section_judge` |
| `DocExtractPromptService` | 保留 `doc_clause_extract` 一个 Code；增加 `{{doc_type}}` 与手册模式分支，页面仍只维护一条提示词 |
| `analyze-item` | 按检查项条款取小节（复用 SectionMap），把小节文本拼进判定提示词，不再传整本手册 |
| 页面“运行测试” | 增加“手册模式”开关/自动识别：识别到条款型标题 ≥20 个 ⇒ 走手册模式；测试结果按条款一行一条显示，而不是整坨 JSON |

### 预期指标

| 指标 | 当前 | 方案后（估算） |
|---|---|---|
| 单次输入 | 59,651 字符 / 35,945 tokens | 1,500~3,000 字符 / 1,000~2,000 tokens |
| 单次耗时 | 184 秒 | 3~8 秒/检查项 |
| 单个检查项 | 不适用（整本一次） | 1 次调用，约 5 秒 |
| 7 个检查项 | 整本跑一次 3 分钟，仍截断 | 约 35~60 秒，且每项都可追溯 |
| 条款覆盖 | 34/76，丢弃 26 | 76/76 精确 + 18 folded，丢弃 0 |
| 截断风险 | 必现（8,192 上限） | 无（输出 ≤500 字符） |
| Anchor 可信度 | 模型自由生成，可能不在原文 | 强制逐字连续片段，可回查偏移 |

## 三、双 Markdown + 文档简介（用户方案，推荐作为最终形态）

### 3.1 结论

**可行，而且比“每次临时清洗原文”更稳。** 但要区分三件事的职责：

| 产物 | 存在哪 | 谁生成 | 用途 | 是不是证据 |
|---|---|---|---|---|
| 标准原始 Markdown | `ISOStandard.MarkdownPath`（已有） | 上传标准文件 | 存档、人工核对、条款来源 | **是**，不可改 |
| 标准条款 Markdown | 新增 `ISOStandard.ClauseMarkdownPath` | `apply-clauses` 成功后由条款表渲染 | 构造条款清单、取当前条款要求、页面预览 | 否，派生视图 |
| 文档原始 Markdown | `EnterpriseDoc.MarkdownPath`（已有） | 上传企业文档转换 | **Anchor / Excerpt 的唯一来源** | **是**，不可改 |
| 文档简介 + 目录 | 新增 `EnterpriseDoc.DocProfileJson` | 转换完成后轻量识别 | 告诉模型“这是什么文档”、选章节 | 否，路由信息 |

一句话：**条款 Markdown 管“标准侧怎么问”，文档简介/目录管“企业文档去哪里找”，原始 Markdown 管“证据原文是什么”。**

### 3.2 标准条款 Markdown 怎么生成

触发点：`/cert/iso-clause` 的「写入条款」成功之后（`apply-clauses` 返回成功即重建），与条款表同一次事务结果。

路径：`/standard-source/{standardCode}/clauses/clauses.md`，覆盖写；原始终身保留在 `MarkdownPath`。

格式（由 `cert_iso_clause` 渲染，**不允许人工编辑**，否则会和条款表分叉）：

```markdown
# ISO 9001:2015 条款索引（派生，非原文）

## 4 组织环境
### 4.1 理解组织及其环境
- 条款号：4.1
- 父条款：4
- 叶子：是
- 标准要求：……（Description 原文，≤300 字）
- 源锚点：原始 Markdown 偏移 1200–1680

### 4.2 理解相关方的需求和期望
……
```

实测规模：iso9001 的 94 条渲染后约 **19,500 字符**，比原始标准 Markdown 30,581 字符少约 36%，而且没有页眉页脚、分页、目录噪声。

**用途只有一个：给提示词提供“当前条款的编号 + 标题 + 要求原文（≤200~300 字）”。**
⛔ 不要把整份条款 Markdown 塞进每次提取；它仍然按条款切片使用。

### 3.3 文档简介 + 目录结构

在现有“文档简单识别”能力上扩展，不新建一套：

```json
{
  "DocType": "quality_manual",
  "DocTypeName": "质量手册",
  "Intro": "公司依据 GB/T 19001-2016 建立的质量管理体系手册，描述组织环境、领导作用、策划、支持、运行、绩效评价和改进。",
  "Purpose": "向内部和外部展示体系范围、职责与过程接口；具体执行见程序文件。",
  "Scope": "常州科斯亚自动化科技有限公司 质量管理体系",
  "Confidence": 0.9,
  "Toc": [
    {
      "ClauseNo": "4.2",
      "Heading": "4.2 理解相关方的需求和期望",
      "Level": 2,
      "CharStart": 3412,
      "CharEnd": 3917,
      "TextLength": 505,
      "HasContent": true,
      "IsNa": false
    }
  ]
}
```

- `Intro / Purpose / Scope` 来自轻量识别：**只送目录 + 开头 2,000 字 + 结尾 1,000 字**，不送全文；
- `Toc` 由标题规则确定性生成，不靠模型编；
- `DocType` 用来选手册/程序文件/记录表的不同提取策略；
- `Toc` 的 `CharStart/CharEnd` 必须指向**原始 Markdown**，这样 Anchor 能回查。

存储位置：`cert_enterprise_doc.DocProfileJson`（文件级、标准无关，一份文档只生成一次，多个标准复用）。
⚠️ 不复用 `cert_enterprise_doc_profile`：那张表挂 `EnterpriseOriginalFile`，是另一条链路，混用会让两套画像互相覆盖。

### 3.4 执行时怎么用（关键）

```text
文档简介（DocType + Intro）
        ↓ 决定“这是手册，按标题找”
目录结构（Toc，含条款号与偏移）
        ↓ 按当前检查项条款，选 1~3 个小节
原始 Markdown 的该小节文本
        ↓ 拼上条款 Markdown 里的当前条款要求（≤200 字）
小提示词 → 覆盖结论 + Anchor + 疑点
```

三条硬约束：

1. **简介不是证据**：它只用于理解文档类型和选章节，Prompt 里明确写“结论只能来自 SECTION 原文”；
2. **目录不是上下文**：不要把整个 Toc 塞给模型，只给命中的那一条 `HeadingPath`；
3. **原文只给小节**：手册 27,162 字，但单个检查项只需要 1~3 节、约 1,500~3,000 字；整本送入会重新回到 3 分钟。

### 3.5 为什么这个方案更容易

| 问题 | 单 Markdown + 每次清洗 | 双 Markdown + 简介 |
|---|---|---|
| 标准侧提示词输入 | 每次读 30,581 字原文，含约一半噪声 | 条款 Markdown 只取当前条款 200~300 字 |
| 条款清单来源 | 每次从标准原文重新解析 | 条款表渲染一次，稳定可复现 |
| 文档定位 | 每次从 27,162 字里重新找标题 | 简介 + Toc 一次生成，按条款直接取小节 |
| 标准切换 | 原文格式不同，解析规则要适配 | 条款表统一口径，换标准只重建条款 Markdown |
| 文档替换 | 旧结果难判断是否过期 | `Sha256` 绑定 profile，hash 变即失效 |
| 可审计 | 模型说“手册里写了”但指不出 | Anchor 强制回查原始 Markdown 偏移 |

### 3.6 两个必须防的坑

1. **条款 Markdown 与条款表分叉**：只允许 `apply-clauses` 重建，⛔ 不允许页面直接编辑；重建时记录 `ClauseMarkdownUpdatedTime` + 条款表 hash，不一致就提示重生成。
2. **文档简介过期**：`DocProfileJson` 必须绑 `EnterpriseDoc.Sha256` 和 `VersionNumber`；文件替换后 profile 与 SectionMap 一并置 stale，重跑后才可用。

1. **先做标准条款 Markdown（最低风险）**：`apply-clauses` 成功后由 `cert_iso_clause` 渲染 `clauses.md`，落 `ClauseMarkdownPath`；原 `MarkdownPath` 不动。先只存不用，核对 94 条是否完整。

6. **页面**：“运行测试”展示按条款表格（条款号/覆盖/Anchor/Excerpt/疑点），不只 `<pre>`。
7. **验收口径**：
   - 76 个精确映射全部可定位；

### 6.7 覆盖口径与 PDF 表符清洗（2026-11-11 补）

**问题 1：上传错标准后，旧条款清不掉。**

- 旧行为：`overwrite=true` 只更新同编号的行，其它编号一直留在 `cert_iso_clause`（实测 iso13485 有 132 条，正确解析只有 94 条）。
- 新行为：`overwrite=true` 先把该标准现有条款 `IsDeleted=1 / IsValid=0`，再全量插入本次解析结果；同一标准的 `cert_clause_attr` 一并软删，避免「挂在已删条款上的孤儿属性」。
- 实测 iso13485：`清空 132，新增 94`，条数从 132 → 94，活跃属性 630 → 0（需按新条款重生成）。
- 备份表：`_bak_20261111_iso13485_clause`（132 行）、`_bak_20261111_iso13485_attr`（630 行）。

**问题 2：标题出现 `\\`，正文出现 `\hline`。**

- 根因：PDF 里的「新旧标准条款对照表」被 anydoc 升成 `### 4.3 确定范围 & 4.1 总要求 \\`，正文只有 `\hline`；它抢先占住编号，真正的 `### 4.3 确定范围` 反而被去重。
- 清洗规则：
  - 识别并跳过「标题含 `& 条款号` 或行尾 `\\`」的对照表伪标题；
  - 标题/正文统一去 `\\`、`\hline`、`\begin{tabular}`、`\end{tabular}`、`\multicolumn`、`\caption` 等 LaTeX 残留；
  - 正文按行丢弃纯表线、纯条款对照行、页码、HTML 分页注释。
- 实测：iso13485 预览 94 条，全部标题无 `\\` / `\hline`；真实条款正文不被误删。
- 追加边界规则：`附录 / 前言 / 参考文献` 与 `0.x / A.x` 标题都作为条款正文硬边界，遇到即收口。9001 的 `10.3` 原来被灌进整个附录 A 表格，现已回填为 116 字正常正文；`clauses.md` 由 21,369 字降为 16,485 字（94 条）。
- 存量复查：全库活跃条款 `Title/Description` 含反斜杠或 `\hline` 的行数 = **0**。
- 备份表：`_bak_20261111_iso9001_clause`（94 行）、`_bak_20261111_iso13485_clause`（132 行）、`_bak_20261111_iso13485_attr`（630 行）。

### 6.8 目录页与“标题+正文同一行”（2026-11-12 补）
