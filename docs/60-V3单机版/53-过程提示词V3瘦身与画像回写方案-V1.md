## 一、V3 改了什么

### 1. 输出结构从 11 个字段压到 6 个

| V2 字段 | V3 处理 |
|---|---|
| `Purpose` / `Scope` / `Inputs` | 合并为一行 `Summary`，≤50 字 |
| `Responsibilities` | 删除；职责并入 `Activities[].Responsible` |
| `Equipment` / `Parameters` / `AcceptanceCriteria` | 删除；只保留 `KeyControls` ≤3 条 |
| `Interfaces` | 删除 |
| `OutputRecords`（顶层） | **删除**；只保留 `Activities[].OutputRecord` |
| `ClauseLinks` | 删除；条款定位由 `doc_profile.ClauseLinks` 负责 |
| 新增 | `DocRole`：策划 / 实施 / 检查 / 改进 / 支持 |

V3 schema：

```json
{
  "DocRole": "实施",
  "Processes": [
    {
      "ProcessName": "设备安全操作",
      "OwnerDept": "生产部",
      "SupportDepts": ["品质部"],
      "Summary": "规定通用设备操作前准备、安全操作和日常检查要求",
      "Activities": [
        {"Activity": "操作前检查设备状态与安全装置", "Responsible": "操作工", "OutputRecord": "设备日常点检表"},
        {"Activity": "按规程启动并运行设备", "Responsible": "操作工", "OutputRecord": "无记录"}
      ],
      "KeyControls": ["未确认安全状态不得启动", "异常立即停机并报告"]
    }
  ]
}
```

### 2. 关键硬规则

1. 程序文件：按文档“工作程序/过程描述”的自然小节拆，保留真实过程数，**2–6 个 Processes**；不得为了省字数把多个过程硬压成 1 个。
2. 作业指导书、操作规程、作业指示书：**只输出 1 个 Process**；`Activities` 3–10 条，合并同类步骤。
3. `OwnerDept` 必填：优先取文件明确职责/审批/发放/使用范围；没有明确职责时按过程使用部门推断；仍无法判断写“未标注”，禁止空串。
4. `OutputRecord` 必填：有记录写名称；确实没有写“无记录”，禁止空串、禁止编造。
5. `Summary` 一行 ≤50 字；`KeyControls` ≤3 条；`SupportDepts` ≤3 个。
6. 不写符合/不符合/充分/缺失/需改进项/建议。

完整提示词：`/tmp/prompt_doc_extract_process_profile_v3.txt`。

## 四、画像回写方案

### 现状

- `rebuild-all` 调 `EnterpriseDocProfileBuilder.BuildAndSaveAsync`，只产出 `DocType/Intro/Purpose/Scope/Confidence/Toc`。
- `doc_profile` LLM 提示词已落库，但 `rebuild-all` 没调用它。
- `ModeOutput` 里有 `OwnerDept`，但没有回写 `DocProfileJson`。
- 列表 99 行 `OwnerDept`、`PrimaryChapter` 全空；`ReadDocProfileBrief` 只能靠中文 `DocType` 派生 `ExtractionMode`。

### 建议：两步回写，不新建表、不新建页面

**第一步：`rebuild-all` 调 `doc_profile` LLM**

每份文档输入：

- `file_name`
- `folder_path`
- `headings`（从 Markdown 标题提取）
- `first_2000`（前 2000 字）

输出并合并到原 `DocProfileJson`：

```json
{
  "DocType": "procedure",
  "DocTypeName": "程序文件",
  "ExtractionMode": "process_profile",
  "ExtractionModeName": "过程画像",
  "StageRole": "实施",
  "PrimaryChapter": "8",
  "SecondaryChapters": ["7"],
  "PrimaryProcess": "生产和服务提供",
  "OwnerDept": "生产部",
  "SupportDepts": ["品质部"],
  "DeptSource": "explicit",
  "StandardRelevance": "direct",
  "Extractability": "full",
  "ClauseLinks": [{"ClauseNumber": "8.5.1", "Relation": "primary"}],
  "Confidence": 0.95,
  "Reason": "程序文件，规定生产和服务提供过程"
}
```

保留原 `Intro/Purpose/Scope/Toc/SourceSha256/VersionNumber/GeneratedAt`，不覆盖。

**第二步：提取完成后补空**

`ClauseExtractExecutor` 写完 `ModeOutput` 后，如果 `DocProfileJson.OwnerDept` 为空，而 `ModeOutput.Processes[].OwnerDept` 有值，则把第一个非空值写回；`PrimaryChapter` 为空时同理从 `doc_profile` 或 `ClauseLinks` 取。只补空，不覆盖 LLM 画像的明确值。

**读侧调整**

- `ReadDocProfileBrief.DocType` 优先读 `DocTypeName`，没有则读 `DocType`。
- `ExtractionMode` 优先读新字段；没有才用 `DeriveExtractionMode(DocType)`。
- 页面“文档类型 / 提取方式”列显示 `DocTypeName` + `ExtractionModeName`；没有中文名时回落原字段。
- 路由器 `EnterpriseDocExtractionRouter` 优先 `ExtractionMode`，其次英文/中文 `DocType`，最后文件名兜底。

### 为什么不建议只靠提取后回写

- 提取只覆盖 4 类模式；手册、索引、制度类不产生 `ModeOutput`，`OwnerDept/PrimaryChapter` 仍空。
- 页面“重新分析”应先看到画像，再决定提取模式；只靠提取后回写，顺序反了。
- `doc_profile` 输入小（标题 + 前 2000 字），单份约 3–5 秒；99 份并发 3 路约 2–3 分钟，可接受。
