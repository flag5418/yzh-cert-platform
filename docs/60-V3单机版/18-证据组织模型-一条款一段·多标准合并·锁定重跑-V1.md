# 证据组织模型：一条款一段 · 多标准合并 · 锁定与重跑 V1

> 前提已定：文档 → 条款的路通了（按条款号能找回该条款下所有文档已提取的内容）。本文只解决最后一公里：**这些内容怎么组织成一段一段的审核证据**。

---

## 一、先看真实报告是怎么"分段"的

| 报告 | 标准 | 条款块数 | 块内结构 |
|---|---|---:|---|
| 科斯亚 | 9001 单标准 | 32 | 一块一条款；证据句偶带 `Q8.1` 前缀 |
| 尚龙 | 13485 单标准 | 56 | 一块一条款；无标准前缀 |
| 双尼 | QES 三标准 | 13（解析欠拆，实际应≈32） | **一块一条款号，块内按标准分行**：`Q4.4` / `E4.4` / `H4.4`，同义时写 `EH5.1` |

双尼 4.1 块的实例（节选）：

```
要求：Understanding the organization and its ...
证据：1、请阐述组织的现状和背景（如发展史、所处的地理位置…）
      与总经理唐骞面谈沟通：企业成立于2015年08月28日…
```

双尼 4.4 块的实例（同一块里三段并列）：

```
Environmental management system 环境   E4.4  质量/环境/职业健康安全管理手册中明确了…
OH&S management system 职业健康安全管理  H4.4  质量/环境/职业健康安全管理手册明确了…
```

**由此得出三条硬结论：**

1. **段的粒度是"条款"，不是"检查项"、不是"部门"、也不是"标准"。** 块头永远是单一条款号。
2. 多标准**不是把三个标准合成一句话**，而是**同号归并成一个块，块内按标准各成一段**；内容高度重合时可合并写 `QEH`。
3. 部门不进段头。一个条款下的多个部门，是在同一段里**按部门顺序叙述**（先访谈最高管理者 → 再部门），不拆成"部门×条款"的多个段。

> 所以你说的"多标准去重、只针对一个标准的一个条款执行"——**成立，但只成立在"块"这一层**：同号条款只开一个块，块内该分几段就分几段。巡检生成时按"块"去重，不按"标准×条款"各跑一遍。

## 二、生成主键怎么定

| 概念 | 主键 | 说明 |
|---|---|---|
| 检查项 | 条款 × 部门 × 审核员 | 审核计划产物，决定"谁去查、查什么" |
| 证据段 | **条款**（+ 企业 + 审核阶段） | 报告的实际排版单位，一段一条款 |
| 段内小节 | 标准 | 多标准时 Q/E/H 各一小节 |

**映射关系**：N 个检查项 → 1 个证据段（当它们的条款相同）；1 个检查项 → 1 个证据段（多条款时按条款拆）。

多条款检查项（一个检查项挂了 5.3/6.1/6.2/7.1.2… 十几个号）的处理：

- **按条款拆成多段**（你已定：一条款一段）；
- 拆出来的段若与已有段同号，**合并进同一段**，不新建；
- 段内顺序按条款号排序，不按检查项顺序。

## 三、段的内部结构（固定四层）

```
【段头】条款号 + 条款标题（如 "4.4 质量管理体系及其过程"）
【小节】按标准分：Q / E / H（单标准时省略）
【正文】按角色骨架填槽（F1 引用 → 事实 → 结论；F2 抽样 → 结果 → 判定）
【判定】取自所属检查项的结论（见 §四之三），不是模型自己下的判断
【落款】审核员 + 日期（可选，报告模板决定）
```

正文里部门的自然顺序（不是拆段，是排序）：

1. 最高管理者 / 总经理（R2 领导类必须）
2. 主责部门（按 `process_clause_map` 里该过程的责任部门）
3. 配合部门（抽样类条款，如 8.4 采购、7.2 能力）

## 四、角色骨架的落地节奏

你说"前期角色可能不完整，但前几章的结构和数据可以先验证"——按此排：

| 批次 | 覆盖角色 | 条款 | 可验证内容 |
|---|---|---|---|
| 第 1 批 | R1 情境、R2 领导、R3 策划 | 4.1–4.4、5.1–5.3、6.1–6.3 | 引用式证据（手册/程序）+ 结论，槽位最规整 |
| 第 2 批 | R4 支持（抽样最重） | 7.1–7.5 | 抽样槽位、人员/设备/文件清单 |
| 第 3 批 | R5 运行、R6 绩效、R7 改进 | 8.x、9.x、10.x | 记录抽样、内审/管评/不合格闭环 |

R1–R3 先跑通，报告前三分之一就能出成品；后面按批次扩，不动已有骨架。

## 四之二、生成输入：企业文档 + 审核员挂接证据

一段证据的输入是四样东西，不是一样：

| 输入 | 来源 | 缺了会怎样 |
|---|---|---|
| 条款属性 + 条款原文 | 属性池 | 骨架散、结论空泛 |
| 该条款下的文档发现（含过程归属） | 文档分析 | 段落空洞 |
| 第 1 段的发现与疑点（含文档级、检查项级） | 21 号「发现+疑点」产物 | 无法体现"现场查过" |
| 审核员挂接的现场证据 | 审核员（挂在检查项上） | 只能写"符合"，写不出"经现场确认" |

**现场证据挂检查项，不挂段落。** 一个检查项含多个条款时，证据挂上去之后再按语义分配到各条款段：审核员写的那段话通常自带条款指向（"查见 8.4 供方评价记录…"），分不准的落到"通用观察"里，不硬塞。

现场证据缺省是**允许**的（你早前定过：报告不要挂现场证据也能生成）。这时段落仍成立，但疑点保持"待核查"，并在段末语气上降一档（"未见异常记录"而非"经查符合"）。

## 四之三、结论挂在检查项，段落只承载文字

这是你这次说清的关键一层：**报告文字按条款排，结论按检查项定**。

| 层级 | 承载什么 |
|---|---|
| 证据段（条款） | 引用、事实、抽样、描述性文字 |
| 检查项（条款×部门×审核人） | **结论**：符合 / 不符合 / 观察项 / 不适用；不符合原因；严重程度；NC 卡片（**复用认证检查已有结论，不新建表**） |

规则：

- 模型生成段落时，**只写文字，不写最终结论**；段末的"符合 GB/T X 第 X.X 条"由检查项结论渲染（默认"符合"）。
- 一个条款被多个检查项覆盖（多部门）时，段落合写，**判定取最严**：不符合 > 观察 > 符合。
- 审核员可手动改检查项结论（这是唯一能改判定的地方）；改了原因/严重程度，段末文案跟着变。
- 结论字段沿用 `cert_check_result`（认证检查里已实现），本设计只**读**它渲染，不改库。
- 不符合 → 可开 **NC 卡片**（引用该段的抽样与发现），这一步后置，先把判定与文案分开。

这样"AI 写文字、人定判定"的边界非常清楚，也符合你"所有生成都是建议"的口径。

## 五、锁定与重跑

| 状态 | 谁改 | 重跑行为 |
|---|---|---|
| `Draft`（系统生成建议） | 系统可覆盖 | 勾选重跑 → 覆盖为新建议 |
| `Edited`（审核员改过未锁） | 审核员 | 重跑前提示"将覆盖你的修改"，默认不覆盖 |
| `Locked`（审核员锁定） | 仅审核员解锁 | **一律跳过**，批量跑也不碰 |

规则细节：

- **锁定粒度 = 检查项**（你已定），不是单个段落。理由：报告核对单位是检查项，锁一段留一段会让审核员自己都分不清哪条还没核。
- 批量跑（"全部检查项"）时，锁定的直接跳过，日志记 `Skipped(Locked)`，不报错。
- 单跑某检查项时若已锁，给出提示并允许"解锁后重跑"。
- 每次重跑生成新版本（`Version+1`），旧的留在历史里，便于对比"AI 稿 vs 审核员定稿"——这份对比数据以后就是优化提示词的原料。

## 六、段落表与关键字段

| 字段 | 含义 |
|---|---|
| `ParagraphCode` | 段唯一键（企业 + 阶段 + 条款号） |
| `CheckItemCodes` | 归并到本段的检查项（可多个） |
| `ClauseNumber` / `ClauseTitle` | 段头 |
| `Standards` | 本段涉及的标准（多值时按标准分小节） |
| `Family` | F1 / F2 / F1F2 |
| `Role` | R1–R7（决定骨架） |
| `Text` | 正文（建议稿） |
| `Status` | Draft / Edited / Locked |
| `Version` | 版本号 |
| `SlotFill` | 槽位填充情况（JSON，用于质量校验与"段落很空"诊断） |
| `FindingCodes` | 引用的证据发现（溯源到文档页码与原文） |
| `DoubtCodes` | 关联的疑点（已核实/已排除会影响结论分支） |
| `OnsiteEvidenceCodes` | 审核员挂接的现场证据（检查项级，按语义分配到本段） |
| `ConclusionSource` | 本段判定取自哪些检查项（多值时取最严） |

`SlotFill` 与 `FindingCodes` 是两件"事后能查"的东西：没有它们，段落空了只能靠人眼看；有了它们，能直接说"抽样槽位缺 3 份记录"。

## 七、质量校验（生成后、交付前）

| 校验 | 判据 | 不通过时 |
|---|---|---|
| 引用存在 | F1 段必须含 `《…》` | 降级为"制度未提供"，标提示 |
| 抽样达标 | F2 段必须含 3 份记录标识 | 提示"记录不足，建议补抽" |
| 结论存在 | 段末含 符合/不符合 判定 | 补一句结论 |
| 篇幅 | 单段 60–200 字（ACM 实测 27–39 字/句，3–5 句） | 过长截断要点，过短提示缺料 |
| 溯源率 | `SourceFacts` 非空占比 ≥ 80% | 标记"低溯源段"供人工复核 |

这五条**只提示不阻断**——所有生成都是建议，最终判给审核员。

## 八、队列

| 队列 | 触发 | 粒度 | 典型耗时 |
|---|---|---|---|
| `doc_analyze` | 文档上传 | 每文档 1 次语义 + 按类型 N 次提取 | 秒级/文档 |
| `clause_attr` | 标准导入/属性变更 | 每条款 1 次 | 一次 80 条款 |
| `evidence_gen` | 计划完成后勾选 | **每段 1 次**（按条款去重后） | 3–6 秒/段 |

`evidence_gen` 的去重规则就是第一节的结论：先把勾选的检查项按条款归并、同号合并，再按"段"入队。勾 40 个检查项、实际只有 22 个不同条款 → 只跑 22 次，不是 40 次。

## 九、待验证（一条）

**多标准合并的"重合即合写"要不要自动化。** 双尼 4.1 是合写（无 Q/E/H 分段），4.4 是分写（E4.4/H4.4 各一段）。判定依据是"两标准该条款文本是否高度相似"。

建议做法：**不自动判**，默认按标准分小节；同一段内三小节内容重复度 > 70% 时，提示审核员"可合并"，由人点一下。宁可多一段，不要合错。
