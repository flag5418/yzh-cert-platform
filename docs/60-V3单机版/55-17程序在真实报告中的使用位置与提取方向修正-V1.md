# 55-17程序在真实报告中的使用位置与提取方向修正-V1

> 状态：诊断完成，尚未改提示词、尚未改代码。
> 目的：回答“`17生产和服务提供控制程序` 在真实认证报告里到底中了几条、报告怎么用它”，并据此修正过程类文档的提取方向。
> 关联：`52`（全量诊断）、`53`（V3 瘦身）、`54`（标准 PDCA 投影试验）。

## 一、结论先说

`17生产和服务提供控制程序` 在真实报告里：

- **显式出现 2 条**：`7.5.3`（作为文件化信息示例）、`8.1`（作为生产和服务提供的管理要求）。
- **过程支撑 9 条**：`8.1`、`8.5.1`、`8.5.2`、`8.5.3`、`8.5.4`、`8.5.5`、`8.5.6`、`8.6`、`8.7`。
- **直接证据 0 条**：报告没有把这份程序当作“已执行”的证据；8.5.1–8.7 的证据是生产计划、作业文件、检验记录、不合格记录等。
- **间接关联 2 条**：`7.1.3` 基础设施、`7.1.5` 监视测量资源；但报告这两条用的是设备台账/校准记录，不是这份程序。

所以当前 V3 输出“6 个过程”并非错，但它是**文档结构摘要**，不是**报告使用单元**。报告真正需要的是：这份程序属于哪个过程区域、支撑哪些条款、把哪些记录作为证据入口。

## 二、报告的实际组织方式

结构化报告 `科斯亚-ACM二阶段-结构化.md` 不是“按 94 条逐条平铺”，而是：

```text
Process Area / 过程区域
  负责人 / 部门
  条款 + 审核证据
```

生产/检验区域的条款是：

```text
7.1.3、7.1.5.1、7.1.5.2
8.1
8.5.1、8.5.2、8.5.3、8.5.4、8.5.5、8.5.6
8.6
8.7
```

这与提取输出“6 个过程”的区别：

| 维度 | 当前 V3 输出 | 真实报告需要 |
|---|---|---|
| 组织单位 | 文档里的 6 个过程小节 | **过程区域 + 部门 + 条款** |
| 条款关系 | 无（`ClauseLinks` 被删） | 每条支撑/引用关系 |
| 证据入口 | `Activities[].OutputRecord` | 报告实际引用的记录/作业文件 |
| 文档角色 | 统一“过程画像” | 程序=要求，记录=证据，手册=框架 |

## 三、`17` 在报告中的两处显式出现

### 3.1 `7.5.3` P20

报告原文：

> 见程序文件，如《生产和服务提供控制程序》KSY-QMS-P-17、《不合格输出控制程序》KSY-QMS-P-16……

这里的角色是**“文件化信息示例”**，不是“生产过程已执行”的证据。它证明企业有这份受控程序，不证明 8.5.1 已执行。

### 3.2 `Q8.1` P24

报告原文：

> 4、生产过程：制定了相关管理要求，如《生产和服务提供过程控制程序》、关键工序“圆刀机作业指导书”等。

这里的角色是**“管理要求”**，支撑 8.1 的“过程策划和控制”。它说明企业制定了生产控制要求，但 8.5.1 的具体证据仍是生产计划、作业文件、人员能力、设备状态、检验记录。

## 四、报告 8.5/8.6/8.7 实际用了什么

| 报告条款 | 实际证据 | `17` 是否直接出现 |
|---|---|---|
| `Q8.1` | 生产流程图、检验要求、生产和检验记录策划、生产管理要求、设备、关键/特殊过程、外包 | 是，作为“管理要求” |
| `Q8.5.1` | 生产计划抽样、作业依据/作业文件、人员能力、基础设施、监视测量资源、关键工序、特殊过程 | 否，证据来自生产指令/作业文件/记录 |
| `Q8.5.2` | 标识和可追溯要求、现场标签、批号 | 否 |
| `Q8.5.3` | 顾客财产识别、顾客信息保管 | 否 |
| `Q8.5.4` | 原材料/半成品/成品防护、周转盒/卡板/包装 | 否 |
| `Q8.5.5` | 交付后服务、退换货、顾客满意度 | 否 |
| `Q8.5.6` | 变更评审和控制 | 否 |
| `Q8.6` | 检验规范、原材料/过程/成品检验记录、放行 | 否，证据来自检验记录 |
| `Q8.7` | 不合格品处置、品质异常处理单、纠正措施 | 否，证据来自不合格记录 |

这说明：**程序文件是“要求层”，记录/作业文件才是“证据层”**。当前提取把程序拆成 6 个过程并填 `OutputRecord`，但没有告诉下游“这些记录对应报告哪条”，所以无法直接组织报告。

## 五、提取模型应增加的三组字段

不是推翻 V3，而是在 V3 上补“报告使用层”。

### 5.1 文档角色

```json
{
  "DocUse": "framework | requirement | evidence | reference | audit_record",
  "ReportRole": "framework | supporting_requirement | direct_evidence | index"
}
```

- 质量手册：`framework`，不作证据；
- 程序文件/作业指导书：`requirement`，`supporting_requirement`；
- 记录/表单：`evidence`，`direct_evidence`；
- 清单/汇编/封面：`reference`，`index`；
- 内审/管理评审记录：`audit_record`，`direct_evidence`（仅 9.2/9.3）。

### 5.2 报告过程区域

```json
{
  "ProcessArea": "生产过程、检验过程",
  "OwnerDept": "生产部",
  "SupportDepts": ["品质部"]
}
```

报告是按 `Process Area` 分段的，`17` 属于“生产过程、检验过程”，不是抽象“生产和服务提供”。

### 5.3 条款与证据入口

每个过程/活动增加：

```json
{
  "ReportClauses": ["8.1", "8.5.1", "8.6"],
  "EvidencePointers": ["生产计划", "钉制机设备操作流程", "自检记录", "首件检验报告", "IPQC制程巡核表", "成品检验报告"]
}
```

`ReportClauses` 只允许从标准 brief 的 `SourceClauses` 取；`EvidencePointers` 只写文件里真实出现的记录/文件名称。

## 七、对标准投影的影响

`54` 号文的 PDCA 投影方向仍然成立，但要改两点：

1. `brief` 不应该只按“大章节”给，而应能按 **ProcessArea** 选；`17` 需要 `Operation`，`09` 需要 `Support + Operation`，`04` 需要 `DocumentedInfo + Operation`。
2. `brief` 的输出约束要增加 `ReportClauses` 和 `EvidencePointers`，否则模型还是只会写“过程摘要”。

用 `17` 做一次 V5 试跑：

- 输入：`doc_profile` + `Operation brief` + 文档全文；
- 输出：新增 `DocUse / ReportRole / ProcessArea / ReportClauses / EvidencePointers / ReportUse`；

  1. 6 个过程是否都挂到正确条款；
  2. `EvidencePointers` 是否来自原文；
