# 58-文件控制类文档与按类型分批提取-V1

> 状态：`document_control` 提示词已落库（Id=13），路由与表格解析已接运行时；`00`、`07` 两份真实文档已跑通。
> 目的：把“目录/首页”从“低价值索引”改成“文件控制证据”，解决按条款提取漏掉“谁在什么时间建立了什么制度、包含哪些文件”的问题；同时支持按文档类型单独跑制度/指导/清单。

## 一、报告里的文件控制证据

真实报告 Q7.5.3 不是只说“有文件”，而是给出可核验的文件化信息证据：

| 报告内容 | 证据要素 |
|---|---|
| 质量手册 `KSY-QMS-M-01` | 版本 A/0；编制体系编写小组；审核胥加娟；批准潘明海；发布 2026.6.10 |
| 程序文件 `KSY-QMS-P-01～P-25` | 版本 A/0；发布 2026.6.10；长期保存 |
| 三阶文件 `KSY-QMS-WI-01～WI-13` | 版本 A/0；发布 2026.6.10；长期保存 |
| 记录清单 `KSY-QMS-P-11-07` | 记录名称、编号、保存部门、期限 |
| 外来文件清单 `KSY-QMS-P-11-06` | 编制张丹、审核胥加娟、批准潘明海、2026.6.10 |
| 文件发放回收一览表 `KSY-QMS-P-11-02-1` | 2026.6.10 发放；签收部门/人/日期 |

这些信息原来在 `index_only` 下全部丢失，只剩文件名。报告恰恰要用“谁编制/审核/批准、什么版本、何时发布、包含哪些”证明 7.5.2/7.5.3。所以目录/首页不是低价值，而是**文件控制证据**。

## 二、分类必须再拆细

| 类型 | 典型文件 | 报告用途 | 提取重点 | 是否 document_control |
|---|---|---|---|---|
| 文件清单/汇编封面 | 程序文件汇编、三阶文件汇编、受控文件清单、外来文件清单、发放/销毁清单 | 7.5.2/7.5.3 | 编制/审核/批准、版本、发布/实施日期、清单条目与总数 | 是 |
| 记录清单 | `07记录清单` | 7.5.3 | 记录名称/编号/保存期限；条目与总数 | 是（`DocumentKind=记录清单`） |
| 文件封面 | 质量手册封面、程序文件封面 | 7.5.3 | 文件编号、版本、批准、发布日期、修订记录 | 是（`DocumentKind=汇编封面/其他`） |
| 因素/相关方清单 | `01-外部因素总清单`、`02-内部因素总清单`、相关方清单 | 4.1 | 因素/相关方条目、监视评价 | **否**，应走 `context_list` |
| 合格供应商清单 | `02合格供应商清单` | 8.4 | 供应商名称、评价、合格状态 | **否**，应走 `evidence` |
| 已填写记录 | 生产通知单、检验报告、设备台账 | 8.5/8.6/7.1.3 等 | 字段、日期、批次、人员、结论 | **否**，走 `record_sample` |

`index_only` 太粗，必须至少拆成：
- `document_control`：文件清单/汇编/记录清单/外来文件清单/发放销毁；
- `document_cover`：封面/首页（可复用 `document_control`，用 `DocumentKind` 区分）；
- `context_list`：外部/内部因素、相关方清单（支撑 4.1，不是 7.5.3）；
- `record_sample`：已填写记录（证据层，不是文件控制层）。

## 三、提示词设计：模型只出元数据，代码解析目录

### 3.1 为什么不让模型逐条输出

`07记录清单` 第一版让模型输出 53 条，结果：
- 耗时 68 秒；
- 只输出 52 条，漏掉最后一行 `KSY-QMS-P-24-07`；
- 把输入 `ReportPresence=explicit` 改成 `content_support`。

`00程序文件汇编封面` 输出 25 条也需 34 秒。结论：**长清单不能交给模型枚举**，否则既慢又漏。

### 3.2 v5 结构

模型只输出：
- `DocumentKind/DocumentTitle/DocumentCode/Version/ControlStatus`
- `PreparedBy/ReviewedBy/ApprovedBy/IssueDate/EffectiveDate`
- `Scope/CatalogSummary/CountsHint`
- `PrimaryClauses`（7.5.2/7.5.3）
- `ReportUse`（只写“可作为 Q7.5.3 证据；是否引用由后续报告索引判定”）

`Entries` 不由模型输出；`DocControlTableParser` 从 Markdown 表格逐行解析，回填：
- `Entries[]`：`No/Code/Name/Version/Dept/Retention`
- `EntriesShown`
- `Counts.Total`，并按 `DocumentKind` 填 `Procedures/WorkInstructions/Records`

### 3.3 v5 试跑结果

| 文档 | 耗时 | 字符 | 模型输出 | 代码解析 |
|---|---:|---:|---|---|
| `00程序文件汇编封面` | **6.1s** | **596** | 25 项程序；编制/审核/批准/发布日期齐全；`DocumentCode` 空（封面本身无编号） | 25 条，`Total=25, Procedures=25` |
| `07记录清单` | **6.2s** | **610** | 53 条记录；编制张丹/审核胥加娟/批准潘明海；版本/日期未标注 | 53 条，`Total=53, Records=53`，最后一行 `P-24-07` 未漏 |

运行时候（`document_control` 模式）：

| 文档 | PromptCode | 条目 | 耗时 |
|---|---|---:|---:|
| `00` | `doc_extract_document_control` | 25 | 队列 2 份合计 14s |
| `07` | 同上 | 53 | 同上 |

`07` 的 `DocumentCode` 为空是正确：记录清单正文本身不带编号，报告 Q7.5.3 里的 `KSY-QMS-P-11-07` 是报告给的编号；不能从目录内记录编号借用。

## 五、按类型单独跑

接口：

```http
POST /api/Auditor/EnterpriseDoc/extract
Authorization: Bearer <token>
Content-Type: application/json
```

文件控制类：

```json
{
  "EnterpriseCode": "7f9c7fa37cbf4c14aa1f4bffdc30ae51",
  "DocTypes": ["文件索引"],
  "ReExtract": false
}
```

作业指导类：

```json
{
  "EnterpriseCode": "7f9c7fa37cbf4c14aa1f4bffdc30ae51",
  "DocTypes": ["作业指导书"],
  "ReExtract": false
}
```

制度/规范类：

```json
{
  "EnterpriseCode": "7f9c7fa37cbf4c14aa1f4bffdc30ae51",
  "DocTypes": ["制度规范"],
  "ReExtract": false
}
```

规则：
- `DocTypes` 是包含匹配，空 = 全部；
- 画像为“体系文件”时，按文件名兜底：`作业指示书/作业指导书/操作规程` → 作业指导书；`制度/规范/管理办法` → 制度规范；
- `FileCodes` 与 `DocTypes` 可同时给，先按文件 Code 收窄，再按类型过滤；
- 无匹配返回 `Queued=0` + 人话原因，不报红。

注意：当前 `作业指导书` 仍路由到 `process_profile`（`doc_extract_process_profile`），`制度规范` 还没有专用提示词；本次只完成了文件控制类。下一步再补 `work_instruction_citation` 与 `policy_profile`。
