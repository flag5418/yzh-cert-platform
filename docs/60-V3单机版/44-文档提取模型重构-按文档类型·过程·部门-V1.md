# 文档提取模型重构：按文档类型、过程、部门 V1

> 结论：**当前提取是“按条款逐个过文档”，不是“先识别文档是什么、属于哪个过程、哪个部门”。这是误标的根因，也是审核证据组织不出来的根因。**
> 新模型：**文档画像（DocProfile） + 过程/部门归属 + 记录画像（RecordProfile） + 条款需求画像（ClauseRequirement）**。条款号只是关联字段，不是检索主键。

---

## 一、现状量化

99 份文档的章节跨度：

| 章节跨度 | 文档数 | 说明 |
|---|---:|---|
| 只落 1 个大章 | 35 | 正常，多数程序/指导书应如此 |
| 落 2 个大章 | 26 | 可接受，通常有主/次关系 |
| 落 3 个及以上大章 | 31 | 偏高，含合理与误标 |

跨章最多的文档：

| 条款数 | 章数 | 文档 |
|---:|---:|---|
| 60 | 9 | `01管理手册QMS.doc` |
| 40 | 7 | `内审记录.doc` |
| 25 | 6 | `00程序文件汇编封面.doc` |
| 19 | 6 | `07记录清单.docx` |
| 14 | 5 | `05-3内审检查表（管理层）.docx` |
| 7 | 5 | `24管理评审控制程序.doc` |
| 15 | 4 | `07仓库管理规范.doc` |
| 8 | 4 | `11 IPQC巡线作业指示书.xlsx` |
| 8 | 4 | `02质量目标管理程序.doc` |
| 7 | 4 | `05销售人员客户拜访管理办法.doc` |
| 6 | 4 | `10信息交流沟通控制程序.doc` |

判断：

- 手册跨 9 章正常；
- 内审记录、管理评审记录跨多章正常，但它们是**审核/评审记录**，不是每个条款的一线证据；
- 程序文件汇编封面、记录清单是 **index**，不应参与事实提取；
- 财务、销售、仓库、信息沟通程序跨 3–4 章，多为条款驱动误标。

## 二、新模型总览

```text
企业文档
  ├─ DocProfile（这是什么文档）
  │    ├─ DocType：manual / procedure / work_instruction / record / index / audit_record / review_record
  │    ├─ PrimaryChapter：4/5/6/7/8/9/10
  │    ├─ PrimaryProcess：生产和服务提供 / 采购 / 内审 / 管理评审 / 文件控制 / 人力资源 / 设备管理 / 不合格控制 ...
  │    ├─ OwnerDept：生产部 / 品质部 / 采购部 / 综合部 / 销售部 / 管理层
  │    ├─ Purpose：一句话说明这份文档解决什么问题
  │    ├─ Scope：适用范围
  │    ├─ Inputs / Outputs
  │    ├─ KeyActivities：3–8 个关键活动
  │    ├─ Records：产生的记录
  │    └─ ClauseLinks：[{clause, relation: primary|supporting|reference}]
  │
  ├─ ProcessFacts（过程/指导书事实）
  │    ├─ ProcessName
  │    ├─ Department
  │    ├─ Purpose
  │    ├─ Activities
  │    ├─ Responsibilities
  │    ├─ Equipment / Parameters
  │    ├─ AcceptanceCriteria
  │    └─ OutputRecords
  │
  ├─ RecordFacts（记录事实）
  │    ├─ RecordName
  │    ├─ ProcessName
  │    ├─ Department
  │    ├─ FormFields
  │    ├─ Period / Batch / Sample
  │    ├─ Signoff
  │    └─ LinkedDoc
  │
  └─ ClauseLinks（条款关联，仅作索引）
```

核心区别：

- 条款号不再是提取入口；
- 文档先回答“我是什么、我属于哪个过程、哪个部门”；
- 条款通过 `ClauseRequirement` 去找“应该由哪个过程、哪个部门、哪类文档提供事实”。

## 三、按文档类型提取

### 3.1 质量手册

- 提取层级：条款级；
- 输出：`ClauseNumber / Title / RequirementText / OrganizationSlot / Coverage`；
- 仍需补 4.1.4、4.1.5、a–d 等子条款覆盖；
- 手册是“要求/职责”来源，不等于“已实施”。

### 3.2 程序文件

不再要求“完整条款内容”，提取：

```json
{
  "DocType": "procedure",
  "ProcessName": "生产和服务提供",
  "OwnerDept": "生产部",
  "Purpose": "对生产和服务提供过程进行控制，确保产品满足要求",
  "Scope": "适用于本公司生产和服务提供全过程",
  "Inputs": ["生产计划", "图纸", "工艺文件", "BOM"],
  "Activities": ["生产准备", "设备调整", "首件确认", "过程巡检", "入库"],
  "Responsibilities": [{"role": "生产部", "duty": "组织生产"}],
  "OutputRecords": ["生产日报表", "工序流转卡", "首件报告"],
  "ClauseLinks": [{"clause": "8.5.1", "relation": "primary"}]
}
```

程序文件的价值是**过程归属、部门职责、活动链、输出记录**，不是把 8.5.1 的 a–h 再抄一遍。

### 3.3 作业指导书

提取：

```json
{
  "DocType": "work_instruction",
  "ProcessName": "IPQC 巡线",
  "OwnerDept": "品质部",
  "Station": "制程巡检",
  "Operations": ["检查静电手环", "检查手套/手指套", "记录巡检结果"],
  "Equipment": ["静电测试仪"],
  "Parameters": [],
  "AcceptanceCriteria": "按作业指示书判定",
  "OutputRecords": ["IPQC 巡线记录"]
}
```

作业指导书的核心是**工序、岗位、操作步骤、参数、接收准则、记录**，不是条款全文。

### 3.4 记录/表单

提取：

```json
{
  "DocType": "record",
  "RecordName": "01-1 进料检验报告",
  "ProcessName": "来料检验",
  "OwnerDept": "品质部",
  "FormFields": ["日期", "批次", "数量", "外观", "包装", "材料证明", "判定"],
  "Period": "2026-11",
  "Batch": "见记录",
  "Sample": "AQL 抽样",
  "Signoff": "检验员",
  "LinkedDoc": "10来料检查作业指示书"
}
```

记录的核心是**过程、部门、字段、期间、批次/样本、签署、关联文件**。

### 3.5 清单/封面/汇编

- 只输出 `index` / `reference`；
- 不产出事实；
- 不进入 `AuditFindings` 主表；
- 只用于文件索引、引用关系。

### 3.6 内审/管理评审记录

- `DocType=audit_record / review_record`；
- 可以作为 4.1-P2、9.2、9.3 的二线证据；
- 不进入 8.5.1 等一线过程证据。

## 四、条款需求画像

每个条款不只写“条款内容”，还要写：

```json
{
  "ClauseNumber": "8.5.1",
  "ChapterRole": "run",
  "RequirementPoints": ["a", "b", "c", "d", "e", "f", "g", "h"],
  "RequiredProcesses": ["生产和服务提供", "设备管理", "过程确认"],
  "RequiredDepts": ["生产部", "品质部"],
  "RequiredDocTypes": ["procedure", "work_instruction", "record"],
  "ExpectedFacts": ["受控条件", "工艺文件", "设备/环境", "人员资格", "过程确认", "防错", "放行/交付"],
  "RelatedClauses": ["8.6", "8.5.5", "7.1.3", "7.1.4", "7.1.5"]
}
```

### 4.1 几个关键条款的“过程/部门”映射

| 条款 | 主过程 | 主部门 | 主要文档类型 | 不应作为主证据的文档 |
|---|---|---|---|---|
| 4.1 | 管理/战略/环境识别 | 管理层 | 手册、因素清单、管理评审 | 生产指导书、财务制度、考勤 |
| 4.2 | 相关方管理 | 管理层/销售 | 相关方清单、满意度调查 | 生产记录、设备保养 |
| 4.3 | 体系范围 | 管理层 | 手册、范围说明、营业执照 | 作业指导书 |
| 5.1 | 领导作用 | 管理层 | 手册、方针、管理评审 | 生产日报、检验报告 |
| 6.1 | 风险与机遇 | 管理层/品质 | 风险清单、风险程序、评价表 | 考勤、财务 |
| 7.2 | 人力资源/培训 | 综合部 | 培训计划、培训记录、能力矩阵 | 生产指导书、销售制度 |
| 8.4 | 采购/外部提供 | 采购部/品质部 | 供应商清单、评审表、来料检验 | 财务制度、销售制度 |
| 8.5.1 | 生产和服务提供 | 生产部/品质部 | 生产程序、作业指导书、设备/特殊过程/生产记录 | 财务、考勤、销售、封面 |
| 8.6 | 放行 | 品质部 | 放行程序、检验报告、放行记录 | 生产日报单独 |
| 9.2 | 内审 | 品质部/管理层 | 内审计划、检查表、内审记录 | 生产作业指导书 |

## 五、条款到文档的检索路径

### 5.1 旧路径（问题所在）

```text
ClauseNumber → 扫描所有文档 → 看是否提到该条款 → 提取原文
```

问题：所有文档都可能“提到”条款，造成 4.1/8.5.1 误标。

### 5.2 新路径

```text
ClauseNumber
  → ClauseRequirement（章角色/要求点/过程/部门/文档类型）
  → 按 ProcessName + OwnerDept + DocType 召回文档
  → 读取 DocProfile / ProcessFacts / RecordFacts
  → 按 RequirementPoint 选取事实
  → 形成 AuditFindings
```

条款号只是 `ClauseLinks` 的一个字段；**主检索键是过程、部门、文档类型**。

### 5.3 例：8.5.1

```text
8.5.1
→ RequiredProcesses: 生产和服务提供、设备管理、过程确认
→ RequiredDepts: 生产部、品质部
→ RequiredDocTypes: procedure, work_instruction, record
→ 召回：17生产和服务提供控制程序、10来料检查作业指示书、11 IPQC巡线作业指示书、设备保养记录、特殊过程确认记录、生产日报、工序流转卡
→ 排除：财务制度、考勤制度、销售制度、程序文件汇编封面
```

### 5.4 例：4.1

```text
4.1
→ RequiredProcesses: 管理/战略/环境识别
→ RequiredDepts: 管理层
→ RequiredDocTypes: manual, factor_list, management_review
→ 召回：手册、外部因素清单、内部因素清单、管理评审记录
→ 排除：年度培训计划、风险机遇程序（只作 reference）、记录清单（只作 index）
```

## 六、落地方式（不新建三表）

为遵守“不另建 V3 文档三表”的既有约束，先用现有字段扩展：

### 6.1 `cert_enterprise_doc.DocProfileJson`

补：

```json
{
  "DocType": "procedure",
  "PrimaryChapter": "8",
  "PrimaryProcess": "生产和服务提供",
  "OwnerDept": "生产部",
  "Purpose": "",
  "Scope": "",
  "Inputs": [],
  "Outputs": [],
  "KeyActivities": [],
  "Records": [],
  "ClauseLinks": []
}
```

### 6.2 `cert_document_extraction.ContentJson`

从：

```json
{"DocMeta":{},"Clauses":[]}
```

扩展为：

```json
{"DocMeta":{},"DocProfile":{},"ProcessFacts":[],"RecordFacts":[],"Clauses":[]}
```

`Clauses` 保留，作为手册/条款索引，不再作为所有文档的唯一输出。

### 6.3 `cert_clause_attr`

补：

```text
RequiredProcesses
RequiredDepts
RequiredDocTypes
ExpectedFacts
RelatedClauses
```

这就是属性池真正需要补的字段，不是再加 9 类抽象属性。

## 七、实施顺序

### P0 先做文档画像，不重跑全文

对 99 份文档先跑 `DocType + PrimaryChapter + PrimaryProcess + OwnerDept + Purpose`，只做画像，不做事实提取。  
目的：先把“财务制度不是 8.5.1”“封面不是事实”这类错标挡住。

### P1 按文档类型改提取

- 手册：条款级；
- 程序：过程级；
- 指导书：工序级；
- 记录：记录级；
- 清单/封面：index/reference。

### P2 条款需求画像

先做 4.1、4.2、4.3、5.1、6.1、8.5.1、8.6 七条，验证“过程/部门/文档类型”召回。

### P3 聚合层按新画像召回

`ProjectDocSlices` 不再只按 `ClauseNumber`，而是：

```text
ClauseNumber → RequiredProcesses/Depts/DocTypes → DocProfile 召回 → Facts
```

### P4 对照真实报告

用 4.1、8.5.1 对比真实报告，检查：

- 事实是否来自正确文档；
- 是否还有财务/考勤/销售混入；
- 证据是否能按“过程—部门—活动—记录”组织。

## 八、结论

1. **当前问题的根因不是提示词措辞，而是提取入口错了**：按条款逐篇过，导致所有文档都变成候选。
2. **除手册外，大多数文档应只属于一个大章/一个主过程**；跨章文档应标记主/次/引用，而不是全部当事实。
3. **程序/指导书不需要完整条款内容**，需要过程、部门、作用、活动、输出记录。
4. **记录的核心是过程、部门、字段、期间、批次/样本、签署、关联文件**。
5. **条款检索应从“条款号匹配”改为“条款需求 → 过程/部门/文档类型 → 文档画像 → 事实”**；条款号匹配只是少数场景。
6. 先做 P0 文档画像，再改 P1 提取；不要直接重跑 99 份全文。
