## 通用属性补充（本提示词也必须遵守）

1. **输出顺序**：先通用属性（DocType、DocTitle、StandardRelevant、Extractable、ClauseEligible、ExtractReason、ProcessArea、DocSections、Chapters、OwnerDept、SupportDepts），再 DocUse/ReportRole/ReportDepth/ReportSummary/ReportUse，最后才是类型专属字段。
2. **Extractable 只表示本类型专属事实是否可提取**：false 时仍必须输出 DocType、DocTitle、StandardRelevant、ProcessArea、DocSections、Chapters、OwnerDept、SupportDepts、Metadata、ReportSummary、ReportUse、Warnings；类型专属数组给空。它**不等于**“条款能不能提取”。
3. **ClauseEligible 非手册一律 false**：本提示词不输出条款事实；条款提取只由手册 clause_full 负责。非手册文档即使有条款号，也只用于 PrimaryClauses/SupportClauses 定位。
4. **文档章节与标准条款严格分开**：
   - `DocSections` 只写文档自身章节/小节，逐字抄画像 `Toc` 或正文标题，如 ["1 目的","4 工作流程","5 作业内容"]；没有章节给 []。
   - `Chapters` 只写标准父章节（如 ["4","8.5"]），不写叶子；`PrimaryClauses`/`SupportClauses` 只写标准叶子条款。
   - ⛔ 文档正文里的 4.1、5.1、5.2 等编号只是文档章节号，**不得因为编号相同就直接当成标准条款**；必须按标准条款标题和正文含义判断，语义不一致时只放进 `DocSections`。
   - `KeyControls[].DocSection` / `Records[].DocSection` 写该事实在文档中的真实小节号，找不到给空串；`Clause`/`PrimaryClauses` 仍然只写标准条款号。
5. **Metadata 只取原文**：DocCode / DocVersion / EffectiveDate / IssuedBy / ApprovedBy 取自封面、页眉、修订栏、审批栏；原文没有给空字符串，不许编造。
6. **CoveragePeriod 只给记录/台账/证书/审核/清单**：Start/End 写原文覆盖期；程序、指导书、制度等不适用时给空字符串，不许把发布日期当覆盖期。
7. **Warnings 是结构化数组**：元素形如 {"Code":"missing_metadata","Message":"未识别到文件编号"}；没有问题时给 []。Code 只用 missing_owner_dept / missing_metadata / ambiguous_type / multi_chapter / blank_form / other。
8. **ReportSummary 只写一句、≤60 个汉字**：说明这份文件规定/记录了什么、谁执行/谁记录；不写符合性、不写建议、不写“已实施”。
9. **不判断符合性**：不写符合/不符合/充分/缺失/满足要求/需改进；只回答“这份文档是什么、有什么”。
10. **ProcessArea 只能是以下八类之一**：GM/MR、行政人事、销售过程、采购过程、生产过程、检验过程、仓储/设备、未标注；不得自造“不合格品控制”“文件控制”等新值。不合格品处置按发生环节归入生产过程或检验过程；判不出给“未标注”。

## 硬规则
1. 角色固定 `DocUse=policy`、`ReportRole=management_requirement`、`ReportDepth=summary`；不得写成过程画像或文件控制。
2. `PolicyType` 只能写“制度”“规范”“管理办法”“规定”之一；看标题判断。
3. `PolicyTitle`/`DocumentCode` 逐字取自封面或页眉；没有编号写空串，不得借用正文条款编号。
4. `Issuer`/`EffectiveDate` 只写原文出现的起草/发布部门/日期；没有写“未标注”，不得编造。
5. `Scope` ≤50 字；`Responsibilities` 1–5 条；`KeyRules` 3–6 条，每条 ≤60 字，只写制度原文要求，不写审核结论。
6. `PrimaryClauses` 只取制度直接支撑的条款：客户/合同=8.2；采购=8.4；生产=8.5；文件=7.5；人力=7.2；不得挂 4.1/5.1/6.1 凑数。`SupportClauses` 0–3 条。
7. ★ `OwnerDept` 只写制度执行/归口部门：正文出现“销售人员/业务员负责”→销售部；“生产人员/操作工负责”→生产部；“检验员/IQC 负责”→品质部；“采购员负责”→采购部；“XX部负责执行/实施/管理”→该部。起草/编制/审核/批准/体系编写小组/文控只能放 `Issuer`，不得放 `OwnerDept`。只有正文完全没有执行部门时，才用 `Issuer` 作为 `OwnerDept`。
8. `SupportDepts` 最多 3 个，只写真实配合部门；不得写“各部门/相关部门”。
9. `ProcessArea` 只写 GM/MR、行政人事、销售过程、采购过程、生产过程、检验过程、仓储/设备、未标注；按制度实际归属选一个。
10. `DocumentEvidencePointers` 只列文中真实出现的记录/表单名称，0–6 个；没有写空数组。
11. 如果制度明显与质量管理体系无关（纯财务报销、考勤、宿舍等），输出 `StandardRelevant=false`、`Extractable=false`、`ClauseEligible=false`、`DocUse="irrelevant"`、`ReportRole="none"`、`ReportDepth="skip"`、`KeyRules=[]`、`PrimaryClauses=[]`、`ReportUse="与质量管理体系无直接关系，建议不纳入报告"`。
12. 不输出 `ReportPresence`，不写报告位置/Q 编号；`ReportUse` 固定写“作为管理/作业要求；是否被报告引用由后续报告索引判定”。
13. 只输出 JSON：第一个字符必须是 {，最后一个字符必须是 }。


## 章节概要（V4 必填，供审核员证据发现用）

画像 {{doc_profile}} 里的 Toc 是本文档的客观章节表（系统已从原文切好，含每节的起止位置）。
请在输出 JSON 顶层额外给出 SectionSummaries，为 Toc 中每个 Level ≤ 2 的标题各写一句概要（≤40 个汉字），说明该节实际写了什么。

- Label 必须逐字抄 Toc 的 Title（不许改写、不许增删字、不许换标点）；对不上就丢弃该条。
- Summary 只概括本节实际写到的内容；该节为空或只有标题 ⇒ Summary 给空串。
- 只写概要：不要自己编章节号、页码、偏移或 CharStart/CharEnd —— 章节骨架由系统按 Toc 生成。
- 示例："SectionSummaries": [ { "Label": "3 职责", "Summary": "规定采购、品质、仓储三部门在采购过程中的职责分工" } ]
- Toc 缺失或为空 ⇒ SectionSummaries 给 []。
