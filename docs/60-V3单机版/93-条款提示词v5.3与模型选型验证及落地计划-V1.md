# 93 · 条款提示词 v5.3 与模型选型验证及落地计划（V1）

> 日期：2026-11-15  
> 范围：ISO 9001，10 条条款 × 38 份企业文档；qwen-plus / qwen-flash；temperature=0.2；response_format=json_object。  
> 结论口径：看**被接受输出**，不只看每百万 token 单价；不按“代码级 90% 召回”要求。

---

## 一、先给结论

1. **v5.3 比 v5.2 明显更准。** 同 10 条条款，校验问题从 `55` 降到 `29`（-47%），P0 从 `15` 降到 `7`（-53%），Quote 从 `24` 降到 `11`，Assembly 从 `2` 降到 `0`。
2. **v5.3.1 的 ClauseItem 修正有效，但整体不替换 v5.3。** ClauseItem 从 `10` 降到 `3`，但 Doubt 从 `8` 升到 `12`，P0 从 `7` 升到 `9`；单轮差异可能是模型波动，但当前证据不支持用它替换 v5.3。
3. **qwen-flash 不适合直接替代 qwen-plus 跑条款证据发现。** 9 条里 1 条超时；每条款问题密度 `5.2` vs plus `2.9`；Quote 问题 `27` vs `11`；Assembly true 过强 `4` vs `0`；DocFact 把 3 份人工判 `partial` 的文档全判成 `filled`。
4. **文档提示词 v5.3.1 可以定稿（qwen-plus 专用）。** 38/38 JSON_OK；只改动了 `07记录清单` 一份，从 `template_only` 修为 `filled`，其余 37 份状态不变。qwen-flash 在同一条上仍是 `template_only`、`SampleRows=[]`，说明这条规则对模型有筛选作用。
5. **现在能改“提示词文本”，但还不能直接写库生效。** 当前运行时只有 `clause_attr_gen`（条款属性预生成，输出属性字段）和旧文档抽取提示词；没有 V2 `DocFact` / `ClauseFindings` 的运行时入口。把 v5.3 直接写进 `clause_attr_gen` 会导致属性字段全空、生成失败。应新增 findings 运行时，而不是覆盖旧提示词。
6. **审核证据提示词可以开始接，但先做 3 条端到端，不要全量。** 输入必须是 `EvidenceFindings + Doubts + EvidenceAssembly`，输出只做“默认符合的检查项/审核证据”，不能反向改写条款发现。

## 二、这轮实际改了什么

### 2.1 条款提示词 v5.3（工作版，当前最优基线）

只做最小增量，不整篇重写：

- **ClauseContext**：只有正文显式 `a) b) c) d)` 才进 `ClauseItems`；`注`、`示例`、`定义`、`1) 2)` 不进；无显式条目时 `ClauseItems=[]`，`ClauseItemRef=["main"]`；有 a/b/c 不得补 d，有 a/b 不得补 c。
- **EvidenceFindings**：`ClauseItemRef` 必须来自条款正文，不能拿模型自己的 `ClauseContext.ClauseItems` 反推；`OriginalQuote` 必须逐字连续，表格只引一行或一个单元格，不改写表头，不用 `...` / `……` 拼接；找不到连续原文就留空并记 `unreadable`。
- **Doubts**：`blank_template` 只用于关联 finding 的 `FillStatus=template_only`；`missing_signature` 只用于非空白模板的签字栏为空；`missing_date` 与 `date_conflict` 分开；`date_conflict` 至少两个不同日期且方向一致；`report_only` 只用于 report/report_only；`inconsistent_person` 只在同一职责出现不同人员且无法用角色分工解释时用；`no_traceability` 用于缺唯一编号/批号/签字链/日期链。
- **EvidenceAssembly**：`CanFormEvidence=true` 必须同时满足 `Gap=""`、`RequiredDocClasses` 每类都有对应 finding、至少一份 `filled` 的 record/report；缺一项只能 `partial`；只有程序/规范/清单/空白模板时不得 true；不得加没有对应 finding 的 required class。
- **准确率边界**：明确“运行时校验器会拦截 ClauseItemRef 越界、引用拼接、DoubtType 错用、Assembly true 过强”。
- `ContractVersion=v5.3`。

### 2.2 条款提示词 v5.3.1（候选，仅修 ClauseItem 过度纠正）

- 加一句：**有显式条目时，`ClauseItemRef` 必须从条目中选择，不得写 `["main"]`；一条发现确实覆盖整条时，选最相关的条目，不要另造总条目。**
- 效果：ClauseItem 问题 `10 → 3`；但 Doubt 问题 `8 → 12`，P0 `7 → 9`。
- 判断：**先作为候选，不替换 v5.3。** 如果后续两轮重跑仍显示 Doubt 差异是噪声，再考虑采纳。

### 2.3 文档提示词 v5.3.1（建议定稿，qwen-plus 专用）

在 v5.3 基础上加两条**通用一致性规则**：

- 记录清单/文件清单/台账类：编号列出现 `KSY/QMS/WI-` 等受控编号，且期限/日期/状态列有值，`FillStatus` 必须是 `filled`；`SampleRows` 至少抄 3 行。
- 如果 `SampleRows` 已抄到实际业务值，`FillStatus` 必须是 `filled` 或 `partial`，不能是 `template_only`；`template_only` 只能配 `SampleRows=[]`。

结果：qwen-plus 的 `07记录清单` 从 `template_only` 变为 `filled`，`SampleRows=3`；38 份中其余 37 份状态不变。qwen-flash 仍是 `template_only`、`SampleRows=[]`。

### 3.1 v5.3 主要剩余问题

- **ClauseItem 过度纠正（10 项，P1）**：模型对本来有 a/b/c/d 的条款写了 `main`，涉及 `7.5.3.2 F1/F7`、`8.6 F1–F5`、`9.3.2 F1/F2`、`10.2.1 F1`。这是“怕越界”后的反向保守，不是条款范围理解错。

- **Quote 11 项**：主要集中在表格重排、跨行/跨段拼接；不是模型没读到，而是“连续原文”在 Markdown 表格里被压平后对不上。
- **Assembly 0 项**：v5.3 的组合规则有效，没有再出现“只有程序/空白模板也判 true”。

### 3.2 v5.3.1 的此消彼长

- ClauseItem `10 → 3`，说明“有显式条目不得写 main”这条规则本身有效。
- 但 Doubt `8 → 12`，新增了 `7.2 D3 report_only`、`8.5.2 D3` 对空白模板判 `missing_signature`、`10.2.1 D3` 同类问题、`7.1.6 D1 blank_template` 等。
- 这说明**只加一句 ClauseItem 规则会牵动疑点判断**；在单轮结果里不能把“ClauseItem 更好”直接等同于“整体更准”。下一步如果要继续，应该只做“ClauseItem 受控修复 + Doubt 规则不动”的对照实验，不再无脑加规则。

## 五、qwen-flash 能不能替代 qwen-plus

### 5.1 成本：确实便宜约 60%

按本轮实测 token 与官方价（qwen-plus 0.8/2.0 元/百万 token；qwen-flash 0.15/1.5）：

| 阶段 | 模型 | 输入 token | 输出 token | 估算成本 |
|---|---|---:|---:|---:|
| 条款 10 条 | qwen-plus | 98,702 | 33,248 | ≈0.1455 元 |
| 条款 9 条 | qwen-flash | 89,182 | 32,253 | ≈0.0618 元 |
| DocFact 38 份 | qwen-plus | 70,875 | 8,173 | ≈0.0730 元 |
| DocFact 38 份 | qwen-flash | 70,875 | 9,874 | ≈0.0254 元 |
| **合计** | **plus** | — | — | **≈0.219 元** |
| **合计** | **flash** | — | — | **≈0.087 元** |

- flash 省约 **60%**；不是“省 80%”，因为输出 token 占比高。
- 如果按 0.96/2.4 展示价，plus 合计约 0.26 元；flash 按 0.18/1.8 约 0.10 元。
- 你看到的“2–3 元/轮”不可能是这 10 条 + 38 份文档的量；更可能来自文档抽取、章节画像、重跑、审核证据生成等多段调用。**先把每段 usage 落日志，再谈单价。**

### 5.2 质量：省下的钱会被返工吃掉

- 9 条条款里 1 条超时（8.6），生产上必须加重试/降级；plus 10/10。
- 每条款问题密度：flash `5.2`，plus `2.9`；Quote 问题 `27` vs `11`；Assembly true 过强 `4` vs `0`。
- 过度抽取明显：`8.5.4` 8 Findings（plus 2）、`9.3.2` 12 Findings（plus 7）、`7.1.6` 7 Findings（plus 2）。多出来的 Findings 不是“更全”，而是把同一事实拆成多条、把程序条款当记录证据。
- DocFact 3 份把 `partial` 判成 `filled`，会让下游 Assembly 更容易判 true，风险比“少找一条”更大。

### 5.3 结论

- **条款证据发现：继续用 qwen-plus。** 不要用 qwen-flash 直接替代。
- **DocFact：当前也用 qwen-plus。** v5.3.1 的 07 修正只有在 plus 上生效；flash 仍失败。
- **可以先用 flash 的场景**：文档预分类、章节粗筛、候选文档召回、短摘要、可人工复核的低风险预处理；**不要让它直接写库**。
- **更值得下一步测的是 `qwen3.7-flash` / `qwen3.5-flash`，不是旧 `qwen-flash-2025-07-28`。** 新一代 flash 单价更低，可能质量更好；但必须过同一套 10 条 + 38 份 + 校验器，不能凭价格选。

## 六、模型选择原则（建议固化为团队规则）

1. **按任务分层，不按单一模型。** 结构化 JSON、长文档、精确引用、多文档组合 → plus；分类、摘要、短抽取、粗筛 → flash；最终写库/出报告 → 必须过校验器，且用 plus 或经 A/B 验证的模型。
2. **按“每个被接受输出的成本”算，不按每百万 token 单价。**  
   `单位成本 =（token 成本 + 重跑成本 + 人工返工成本 + 审计风险）/ 被接受输出数`。flash 的 token 便宜 60%，但每条款多 2.3 个问题和 3 份 DocFact 误判，返工成本很容易超过节省。
3. **固定快照、固定 temperature、同一提示词同一文档做 A/B。** 不用“qwen-plus 最新版”这种浮动标签；记录 `model`、`prompt_version`、`temperature`、`usage`、`latency`、`timeout`。
4. **质量门禁先于成本。** 每批至少看：JSON_OK 率、P0/P1 数、p95 延迟、超时率、DocFact 关键样例准确率。P0 不达标，不进入写库。
5. **便宜模型不做“最终判断”。** 它可以提议，不能直接生成 `CanFormEvidence=true`、不能直接写审核证据；必须由 plus 或校验器复核。

## 七、现在能做什么、不能做什么

### 7.1 文档提示词：可以改，但要新增运行时入口

- 文本层面：v5.3.1 已定稿，38/38 验证，07 修正，qwen-plus 专用。
- 运行时层面：当前系统没有 V2 `DocFact` 服务/表；旧 `doc_extract_*` 输出的是旧画像，不是 `FillStatus/SampleRows`。直接改旧提示词不会产生 DocFact。
- 建议：新增 `doc_fact` PromptCode + `DocFactService`，输出按 `FileCode/FileName/DocClass/FillStatus/Coverage/SampleRows/KeyFields` 落库；调用后先跑 `DocFactValidator`，不通过不进下游。

### 7.2 条款提示词 / 属性池：**不要覆盖 `clause_attr_gen`**

- 当前 `clause_attr_gen` 是“条款属性预生成”，运行时只替换 `{{standard_name}}`、`{{clause_number}}`、`{{clause_title}}`、`{{clause_content}}`，并追加 `{{attr_pool}}`。
- v5.3 需要 `{{mode}}`、`{{chapter_profile}}`、`{{allowed_clause_refs}}`、`{{referenced_clauses}}`、`{{doc_facts}}`、`{{doc_excerpts}}`；当前运行时不会填这些占位符。
- 如果把 v5.3 写进 `clause_attr_gen`：占位符会原样留在提示词里，模型输出 `ClauseContext/EvidenceFindings`，而 `ClauseAttrGenerateService.ExtractAttrValues` 只找属性池字段 → 结果“没有任何已知属性字段”，生成失败。
- 正确做法：新增 `clause_evidence_findings` PromptCode + 新服务；`clause_attr_gen` 保持原样。属性池本身不需要改，v5.3 的条款范围规则属于 findings 层。
- 条款 findings 服务必须先补齐 6 个入参：模式、章节画像、本章条款索引、引用条款、DocFacts、文档原文摘录；否则 v5.3 无法在生产运行。

### 7.3 审核证据提示词：可以开始，但先 3 条端到端

- 建议先选 `7.1.6`（知识）、`9.3.2`（管理评审）、`8.6`（放行）三条：一条偏制度、一条偏记录组合、一条偏报告/签字，能覆盖三类消费方式。
- 输入：`EvidenceFindings + Doubts + EvidenceAssembly + DocFact`；输出：默认符合的检查项/审核证据。
- 边界：空白记录只能写“企业建立了 XXX 记录，包含哪些字段”，不能写“已有效执行”；报告数据只能 `report_only`，不能回填文档事实。
- 先人工对照 3 条，确认“引用关系、疑点消费、默认符合口径”都对，再扩到 10 条。

### 7.4 运行时校验器：先接 P0，不要一开始全硬拦

- P0 硬门禁：ClauseItemRef 越界、引用拼接/省略号、DoubtType 错用、Assembly true 过强、DocFact 关键误判。
- P1 修复：Quote 连续命中、字段缺失、ClauseItem 过度纠正。
- P2 人工复核：`inconsistent_person` 等需要角色判断的项。
- 按 92 报告口径：P0 拒绝、P1 修复、P2 复核；不要用 P1 硬拦，否则 Findings 通过率会被压到 50% 左右。

## 八、下一步顺序（建议）

1. **本周先落 DocFact**：新增 `doc_fact` 提示词与 38 份回归；qwen-plus；先接 `DocFactValidator`。
2. **再落 ClauseFindings**：新增 `clause_evidence_findings`，补 6 个入参；先用 v5.3（P0 7），v5.3.1 只作候选；接 5 类校验器。
3. **然后接审核证据**：3 条端到端，人工对照；通过后再扩 10 条。
4. **最后做模型路由**：plus 跑条款/DocFact；flash 只做粗筛；测 `qwen3.7-flash` 作为降本候选；所有模型输出必须过校验器。
5. **成本拆账**：在每一步记录 `prompt_tokens / completion_tokens / latency / retry / model / prompt_version`，把“2–3 元/轮”拆到具体阶段，再决定是否换模型。

## 九、一句话回答

**v5.3 可以作为条款证据发现的当前基线；v5.3.1 先不替换。文档提示词 v5.3.1 可以用 qwen-plus 定稿。qwen-flash 便宜约 60%，但质量下降明显，不建议直接替代。现在能改提示词文本，但必须先新增 DocFact / ClauseFindings 运行时，不能把 v5.3 覆盖进 `clause_attr_gen`。审核证据提示词可以开始，但先做 3 条端到端。**
