# 程序文件 → 条款映射实证（双尼 QES 28 份）V1

> 回答你的问题：这些过程到底归属哪个条款？答案是**能归属，但不能靠正文，只能靠文件名 + 目的段 + 范围段**。本文给出 28 份的完整映射、覆盖率和自动归属方案。

---

## 一、先看一个反直觉的实测结果

把 28 份程序文件用 python-docx 全文提取后，搜"标准条款号"：

| 现象 | 实测 |
|---|---|
| 正文出现"19001""24001""45001"字样的文件 | **1 份**（只有封面目录写了编制依据） |
| 正文出现标准条款号（如"8.4""6.1.2"）的 | **0 份**（抽到的 4.1/8.4 全是文件自己的章节号：1 目的、2 范围、3 职责、4 措施） |
| 正文能读到"同某标准条款对应"的表述 | 0 份 |

**所以"从正文找条款号"这条路走不通。** 能用的线索只有三个：文件编号、文件名、目的/范围那两段（约 200 字）。

这也直接说明：企业做认证资料时，**条款对应关系是"咨询公司脑子里"的，不写在文件里**。所以系统必须自带一份"过程→条款"主数据，不能指望从文档里读出来。

## 三、能不能自动归属？能，但要一份主数据

### 3.1 可自动的部分（不用模型）

| 线索 | 抽取方式 | 命中率（本套 28 份实测） |
|---|---|---|
| 文件编号前缀 `SN/QES-CX-xx` | 正则 | 28/28 |
| 文件名关键词（采购/应急/内审/管评/不合格/校准…） | 词典匹配 | 26/28（"信息收集、分析和处理""相关方管理"需人工确认） |
| 目的段动词 | "识别/评价/控制/监测/管理" → 过程类 | 28/28 |

### 3.2 需要主数据的部分

"文件名 → 条款"不能靠猜。建议在**后台管理端**建一张 `process_clause_map`（过程 → 标准 → 条款号），约 30–60 行/机构，作为系统主数据：

| 过程 | 9001 | 24001 | 45001 |
|---|---|---|---|
| 风险管理 | 6.1 | 6.1.1 | 6.1.1 |
| 采购 | 8.4 | 8.1 | 8.1.4 |
| 应急 | — | 8.2 | 8.2 |
| … | … | … | … |

这张表是**后台管理的核心资产**，不进专家端：专家端只看到"某条款 → 有哪些文档可查"，看不到映射怎么维护。

### 3.3 一个文件可挂多条款，不能只挂一个

实测有 8 份属于一对多（04 合规义务挂 6.1.3+9.1.2；16 改进挂 10.1/10.2/10.3；18 管评挂 9.3 但含 F2 实例）。所以 `clause_hint` 必须是**数组**，不是单值。

与此对应，检查项检索时是"条款 → 文件集合"，不是"文件 → 条款"：一条款可能命中 2–4 份程序文件 + 1 段手册 + N 份记录。

## 四、对文档模型的修正

| 字段 | 修正 |
|---|---|
| `clause_hint` | **数组**，可空；由"文件名 + 目的段 + 主数据表"三者合成 |
| `doc_cluster` | 新增：文件编号前缀（如 `SN/QES-CX`），用于识别"同一套体系文件"，一套文件共享同一版本与签批要求 |
| `sign_required` | 新增布尔：封面/页头是否需手签（这类"合规性瑕疵"在审核里是真实发现点，例如你提到的封面手签） |
| `excerpt_style` | 新增枚举：`cite`（引用式）/ `detail`（明细式）——手册用 `cite`，记录用 `detail` |

---

## 五、结论

1. **过程能归属条款**，依据是文件名 + 目的段 + 主数据表，不是正文条款号（正文根本没有）。
2. **程序文件只覆盖 1/3 条款**，剩下靠手册与记录；这条把 F1/F2 两族落到了具体文档类型上。
3. **一个文件挂多个条款是常态（8/28）**，所以 `clause_hint` 用数组、检索方向是"条款 → 文件"。
4. 映射表属**后台管理端主数据**，专家端只消费；这也符合你第 1 点"后台是核心、不暴露给专家端"。
