## 一、审核机构行业分析

### 1.1 国内 ISO 13485 审核机构规模与分布

获 CNAS 认可的 ISO 13485 认证机构约 **45-55 家**，含外资在华机构实际约 **80-100 家**。

| 类型 | 占比 | 代表机构 | 年审核项目 | 特征 |
|------|------|---------|-----------|------|
| 大型 | ~15% | SGS、TÜV、BSI、CQC、华测 | >2000 | 全国覆盖，价格较高 |
| 中型 | ~35% | 威凯、电科院、地方质检院 | 500-2000 | 区域优势，性价比高 |
| 小型 | ~50% | 各类民营认证机构 | <500 | 专注细分，灵活但资源有限 |

**关键发现**：绝大多数机构是**多类目同时经营**（ISO 9001/13485/14001 等），但 ISO 13485 审核员和报告模板相对独立。同一机构内部正推动"多体系联合审核"以提效降本。

### 1.2 苏州及长三角地区医疗器械审核机构

苏州是国内医疗器械产业最集中区域，以下机构在苏州/长三角有审核团队：

| 外资机构 | 国内机构 |
|---------|---------|
| SGS（苏州工业园区有大型实验室） | CQC（南京/上海/苏州分支） |
| TÜV SÜD 南德（上海/苏州，医疗核心业务） | 华测检测 CTI（苏州分公司，检测+认证一体化） |
| TÜV Rheinland 莱茵（上海覆盖苏州） | 威凯认证 CVC（上海分支） |
| BSI（上海办公室） | 苏州电科院（本地优势） |
| DNV（上海，医疗布局深） | 中检集团 CCIC（苏州分支） |
| ACM（合作审核员覆盖苏州） | — |

**结论**：苏州是绝佳的试点区域。朋友所在机构大概率在上表中，且苏州医疗器械企业密集，审核需求旺盛。

### 1.3 审核报告格式差异 —— 核心结论

**核心字段约 70% 跨机构通用，30% 为机构自定义。不存在行业统一模板。**

| 通用部分（~70%） | 机构自定义（~30%） |
|------------------|-------------------|
| 企业信息、审核日期、审核员 | 机构 Logo、页眉页脚 |
| 审核依据（ISO 13485:2016） | 文档编号规则 |
| 标准条款编号和内容 | 法律声明文字 |
| 审核证据、NC 判定、审核结论 | NC 单格式、审批流程 |
| 审核范围（产品/过程/场所） | 多语言版本 |

**外资 vs 国内机构差异**：

| 维度 | 外资（ACM/SGS/TÜV/BSI） | 国内（CQC/华测/威凯） |
|------|------------------------|---------------------|
| 报告语言 | 中英双语 | 中文为主 |
| 模板格式 | 高度结构化，双栏对照 | 偏 Word 自由文本 |
| NC 判定 | 严格区分 Major/Minor | 同样区分，措辞本土化 |
| 监管报备 | 同步 UKAS/ANAB | 同步 CNAS/CNCA |
| 附加要求 | ISO 13485 + MDSAP/CE 联审 | ISO 13485 + 国内 GMP 联审 |

**ACM 模板能否适配其他机构？** 核心数据结构可复用约 65%，但报告排版和机构专属字段需定制。技术方案：**"核心数据层 + 模板渲染层"分离架构**。

## 二、标准库与规则库策略

### 2.1 能否跳过国家标准库？

**结论：可以，而且这是更聪明的做法。** 直接内置标准原文有版权风险（ISO 对商业性嵌入管控严格），但通过以下路径建立的规则库，既有实用价值又无版权问题：

| 路径 | 说明 | 覆盖率 |
|------|------|--------|
| 从 ACM 报告提取规则 | 分析报告中的审核检查项、判定逻辑，反推为结构化规则 | ~40% |
| 朋友专业解释补充 | 针对报告未覆盖的条款（7.x 设计开发、6.2 人力资源等），由朋友逐一补充审核要点 | ~40% |
| 后续报告样本积累 | 每拿到一份新报告，自动提取未覆盖的检查项，补充规则库 | 逐步逼近 90%+ |

**遗漏风险**：
- ACM 报告仅覆盖部分条款（4.1/4.2/5.1-5.6/6.1/8.1），Stage 2 审核需要完整条款（含 7.x 产品实现）
- 不同产品类型（有源/无源/IVD）审核要点不同，需逐步补充
- NC 判定的隐性经验难以完全规则化 —— 建议保留人工复核环节

### 2.2 竞品如何解决标准库版权？

| 策略 | 代表厂商 | 说明 |
|------|---------|------|
| 条款编号+自编解读 | 智审100、质审通 | 不内置原文，用自研规则替代 |
| 与标准出版社合作 | 企企通（较大厂商） | 付费获得授权，成本高 |
| 引导用户自行上传 | 部分小厂商 | 责任转移至用户，体验差 |

**推荐方案**：条款编号 + 自研规则解读 + 用户可选自行上传标准 PDF。规则库中每条规则标注来源（"来自 ACM 报告字段 X"或"专家经验补充"），形成自有知识产权。

## 三、审核数据采集流程深度分析

### 3.1 审核员的实际工作流（基于朋友描述）

```
企业提交文件夹 → 审核员预审 → 提取关键信息 → 建立审核记录 → 生成报告
     ↓                ↓               ↓                ↓
  资料包.zip      逐文件浏览      对照核查表      逐条填写证据
                  标记缺失项      提取关键字段      NC判定
                  通知企业补交    匹配标准条款      结论输出
```

整个流程中，审核员的工作可分解为四个步骤，每个步骤都有自动化空间：

### 3.2 步骤一：企业资料接收与预审

**现状**：企业通过邮件/云盘提交一个文件夹，包含管理手册、程序文件、记录表单等数十份文件。审核员逐文件打开浏览，判断是否齐全。

**自动化方案**：

| 功能 | 描述 | 优先级 |
|------|------|--------|
| 文件清单自动比对 | 系统预置"应提交文件清单"（管理手册、程序文件清单、内审记录、管理评审记录等），自动扫描文件夹，标记已提交/缺失 | P0 |
| 文件类型智能识别 | 自动识别 PDF/Word/Excel/图片，按文件名和内容特征归类到对应检查项 | P0 |
| 缺失项自动提醒 | 发现缺失文件时，自动生成"补交清单"，一键发送给企业 | P0 |
| 文件版本管理 | 企业多次补交时，自动标记版本，避免审核员用错版本 | P1 |

### 3.3 步骤二：关键信息提取

**现状**：审核员从文件中手动提取关键字段：企业名称、产品名称、质量目标数值、内审日期、管理评审日期、培训记录等。这是最耗时的环节。

**自动化方案**：

| 数据来源 | 提取内容 | 技术方式 |
|---------|---------|---------|
| 管理手册封面/首页 | 企业名称、手册编号、版本号、生效日期 | OCR + 正则匹配 |
| 质量目标页 | 目标指标（满意度≥95分、投诉率≤2%等） | OCR + 数值提取 |
| 内审记录 | 内审日期、审核员、不符合项数量、关闭状态 | OCR + 结构化解析 |
| 管理评审记录 | 评审日期、参与人员、决议事项 | OCR + NLP |
| 组织架构图 | 部门设置、管理层名单 | 图片识别 + 实体提取 |
| 培训记录 | 培训日期、培训主题、参训人员、考核结果 | OCR + 表格解析 |
| 设备清单/校准证书 | 设备编号、校准日期、有效期 | OCR + 日期校验 |
| 供应商名录 | 供应商名称、评价结果 | 表格解析 |

### 3.4 步骤三：审核记录建立

**现状**：审核员在 Word/Excel 中逐条对照标准条款，填入审核证据。如 ACM 报告中的双栏结构："Requirements" 列是标准原文，"Audit Record" 列是审核员手写的证据。

**自动化方案**：

系统自动完成以下映射：

```
提取的数据 → 匹配标准条款 → 自动生成审核记录
     ↓              ↓                ↓
"内审日期: 2026.05.15-16"  →  条款 8.2.4 内部审核  →  "组织于2026年5月15-16日开展了内部审核，覆盖所有部门和ISO 13485全部条款..."
```

| 阶段 | 自动化程度 | 人工角色 |
|------|-----------|---------|
| 文件审查阶段 | 80% 自动 | 审核员确认和微调 |
| 现场审核阶段 | 30% 自动 | AI 辅助录入，人工判断为主 |
| 报告生成阶段 | 90% 自动 | 审核员审核签字 |

### 3.5 步骤四：预审——发现企业资料欠缺

这个环节是审核员的核心价值之一，也是产品差异化的关键。系统可以做到：

1. **文件完整性检查**：根据"应提交文件清单"自动比对，输出缺失清单
2. **文件有效性检查**：检查文件是否受控（有无审批签名、版本号、生效日期）
3. **关键内容缺失检查**：管理手册是否声明了范围？有无删减说明？质量方针是否包含承诺？
4. **逻辑一致性检查**（详见第四章）

## 四、智能校验引擎设计

### 4.1 文件目录与实际文件匹配校验

**问题**：企业提交的管理手册中列出了程序文件目录（如"QP-01 文件控制程序"），但实际提交的文件夹中该文件不存在或内容为空。

**校验方案**：

```
管理手册中的文件清单 → 提取文件编号和名称 → 与实际文件夹对比 → 标记缺失/多余/版本不一致
```

| 校验项 | 方法 | 示例 |
|--------|------|------|
| 目录 vs 实际 | 从管理手册/质量计划中解析文件清单，与上传文件列表交叉比对 | 手册列出 22 个程序文件，实际只有 20 个，标记缺失 2 个 |
| 文件编号一致性 | 检查文件名中的编号是否与手册目录一致 | 手册写"QP-01"，文件名是"QP-01 文件控制程序 Rev.03"，匹配成功 |
| 版本号交叉校验 | 手册引用的版本号 vs 文件实际版本号 | 手册引用"QP-03 Rev.02"，实际文件是"QP-03 Rev.01"，标记版本不一致 |
| 空文件/占位文件检测 | 检查文件大小是否异常（如 0KB 或仅含模板占位符） | 文件大小 0KB，标记"疑似占位文件" |
| 引用文件追溯 | 程序文件中引用了其他文件（如"见《WI-05 操作规程》"），自动检查引用文件是否存在 | 自动构建文件依赖图，标记断链 |

**技术实现**：

使用 Python 解析 PDF/Word 文件中的文件清单表格，提取文件编号正则模式（如 `[A-Z]{2,3}-\d{2,3}`），与文件夹实际文件列表做 diff。

### 4.2 关键日期逻辑校验

**问题**：培训日期晚于考试日期、内审日期晚于管理评审日期、文件生效日期早于批准日期等逻辑矛盾。

**校验规则库**：

| 规则编号 | 校验逻辑 | 严重程度 | 示例 |
|---------|---------|---------|------|
| DT-01 | 文件批准日期 ≤ 文件生效日期 | 高 | 批准日期 2026.06.01，生效日期 2026.05.01 → 异常 |
| DT-02 | 培训日期 ≤ 考核日期 | 高 | 培训 05.20，考核 05.18 → 异常 |
| DT-03 | 内审日期 ≤ 管理评审日期 | 高 | 内审 05.16，管理评审 05.10 → 异常（应先内审后管理评审） |
| DT-04 | 管理评审日期 ≥ 上次管理评审日期 + 11个月 | 中 | 标准要求不超过12个月间隔 |
| DT-05 | 设备校准日期 ≤ 审核日期且校准有效期 > 审核日期 | 高 | 校准证书已过期 |
| DT-06 | 人员入职日期 ≤ 培训日期 | 低 | 入职后应该经过培训 |
| DT-07 | 不符合项关闭日期 ≥ NC 开具日期 | 高 | 关闭日期早于开具日期 → 异常 |
| DT-08 | 体系运行时间 ≥ 3个月（一阶段审核前提） | 高 | 手册生效日期到审核日期不足3个月 → 不满足审核条件 |
| DT-09 | 供应商评价日期在采购合同日期之前 | 中 | 先评价后采购 |
| DT-10 | 设计开发各阶段日期按逻辑顺序（输入→输出→评审→验证→确认） | 中 | 验证日期早于输出日期 → 异常 |

**技术实现**：

- 从文件中提取所有日期字段（通过正则匹配多种日期格式）
- 为每个日期标注语义标签（如"内审日期"、"管理评审日期"、"培训日期"）
- 运行校验规则引擎，输出异常列表
- 对于 OCR 提取的日期，标注置信度，低置信度时提示人工确认

### 4.3 人员一致性校验

**问题**：培训记录中的参训人员不在企业员工名册中；被审核部门负责人不在组织架构图中；内审员审核了自己部门等逻辑错误。

**校验规则库**：

| 规则编号 | 校验逻辑 | 严重程度 |
|---------|---------|---------|
| PR-01 | 培训记录参训人员 ∈ 员工名册 | 中 |
| PR-02 | 内审员不应审核自己所在部门 | 高 |
| PR-03 | 管理者代表应在组织架构中明确任命 | 高 |
| PR-04 | 特殊过程操作人员应持有效资格证书 | 高 |
| PR-05 | 检验人员应独立于生产人员（职责分离） | 中 |
| PR-06 | 管理评审参与人员应覆盖管理层+管代+部门负责人 | 低 |
| PR-07 | 文件审批人应在授权签署人员清单中 | 中 |
| PR-08 | 供应商评价人员不应是同一供应商的联系人 | 低 |

**技术实现**：

1. **建立人员主数据**：从组织架构图、员工名册、岗位说明书等文件中提取所有人员姓名和角色
2. **人名模糊匹配**：处理"张三" vs "张 三" vs "Zhang San" 的同一人多写法问题
3. **角色权限矩阵**：定义每个角色的权限范围（如"内审员不能审自己部门"）
4. **交叉校验**：每条记录中的人名与人员主数据比对，发现不在名册中的人员或角色冲突

### 4.4 数值与指标校验

| 规则编号 | 校验逻辑 | 严重程度 |
|---------|---------|---------|
| NM-01 | 质量目标值应有明确的量化指标（不能只有定性描述） | 中 |
| NM-02 | 实际达成值 vs 目标值（如"一次合格率≥98%，实际97.5%"→标记未达成） | 高 |
| NM-03 | 统计周期数据与报告周期一致 | 中 |
| NM-04 | 设备数量 vs 设备清单数量一致 | 中 |
| NM-05 | 培训学时满足法规最低要求 | 中 |

### 4.5 校验引擎总体架构

```
文件输入 → 数据提取层 → 语义标注层 → 校验规则引擎 → 校验报告
              ↓              ↓              ↓              ↓
         OCR+NLP+正则   日期/人员/数值   规则库匹配     分级输出
                         打标签          执行校验       (高/中/低)
```

**输出格式**：

```
校验报告
├── 文件完整性: 发现 2 项缺失
│   ├── [高] QP-07 设计开发控制程序 — 目录列出但文件未提交
│   └── [中] 外来文件清单 — 未找到最新版法规文件
├── 日期逻辑: 发现 1 项异常
│   └── [高] 管理评审日期 2026.05.25，内审日期 2026.05.15-16 — 内审在前，管理评审在后，逻辑正常 ✓
├── 人员一致性: 发现 1 项异常
│   └── [中] 培训记录中"李四"不在员工名册中 — 可能是新员工或录入错误，请确认
└── 数值指标: 发现 1 项未达标
    └── [高] 投诉率目标≤2%，报告期实际投诉率 2.3% — 未达成目标
```

## 五、综合建议与下一步行动

### 5.1 产品架构总结

基于以上所有分析，推荐产品采用三层架构：

```
┌─────────────────────────────────────┐
│         模板渲染层（机构可配置）        │
│   ACM模板 / SGS模板 / CQC模板 / ...   │
├─────────────────────────────────────┤
│         核心数据层（跨机构通用）        │
│   企业信息 / 审核项目 / 条款映射 /      │
│   审核证据 / NC记录 / 审核结论         │
├─────────────────────────────────────┤
```
