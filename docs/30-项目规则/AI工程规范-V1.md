# AI 工程规范 V1（草稿，待审阅补充）

> 定位：个人化的 AI 辅助工程方法规范——20+ 年传统开发经验 × AI 协作的沉淀。
> 目标：让 AI 在**规范约束**下产出可维护、可演进、不靠代码反推逻辑的工程成果。
> 状态：草稿 | 2026-08-15 | 待补充：§六 留白处

---

## 一、总则

1. **文档是源代码的一部分**：本项目的业务逻辑、表、接口都有文档权威说明；AI 修改代码前必须先读懂对应文档，修改后必须同步文档。
2. **AI 是执行者，规则是唯一标准**：不允许不同 AI（或同一 AI 不同次）按各自理解产出——一切以规范和文档为准（见 80-功能设计 严格规范）。
3. **文档先行，实施在后**：新功能必须先有设计文档（含 TODO 执行计划），评审通过才能实施。

## 二、核心工程原则（本项目中已实践并验证）

| # | 原则 | 含义 | 违背的后果 |
|---|------|------|-----------|
| 1 | **文档先行** | 设计文档 → 评审 → 实施 → 测试 → 通知 | 逻辑靠代码反推，维护困难 |
| 2 | **后端单一约束** | 控制逻辑只在后端；前端不重复约束、不传递控制值（如路径、skill） | 前后端规则冲突，问题难定位 |
| 3 | **表约束优先** | DB 唯一键/外键是硬保障；逻辑先删后插等是软保障，两者都要 | 冗余/脏数据 |
| 4 | **不背历史包袱** | 大版本改造时彻底清除旧数据/旧逻辑，只保留唯一现行标准 | 新旧混存，页面逻辑混乱 |
| 5 | **SQL 自动执行** | 项目规则要求 SQL 由 AI 自动执行并验证，不推给用户手动操作 | 字段/表缺失，运行时报错 |
| 6 | **自动化测试后通知** | 改动完成 → 编译 + 端到端自动化测试 → 通过后才通知用户验证 | 用户重复试错 |
| 7 | **文档与代码一致性** | 每次改动核对并更新文档（含实体注释、设计文档状态）；发现不一致立即修 | 文档说谎 |
| 8 | **标准脚本运维** | 启停走标准脚本（`scripts/backend/` 下 stop/run/restart-backend.sh），禁止裸 nohup/按端口 kill | 进程残留、环境漂移 |
| 9 | **知识库沉淀** | 踩坑记录进 YZH-知识库；经验固化为规范文档 | 同类问题反复踩 |

## 三、AI 协作工作流（本项目标准流程）

```
1. 理解需求 → 2. 读关联文档（80-功能设计 / 20-架构决策）→ 3. 核对代码与文档一致性
→ 4. 设计（新功能先写 80-功能设计 文档）→ 5. 实施（SQL 自动执行 + 后端 + 前端）
→ 6. 编译验证（dotnet build / vite build）→ 7. 自动化端到端测试 → 8. 通知用户验证
→ 9. 同步文档状态（80-功能设计 TODO 更新、状态机推进）
```

## 五、AI 使用纪律（工具层面）

1. 不运行破坏性/不可逆命令（git push、全局安装、生产操作），除非用户明确要求；
2. 不在项目外产生副作用；改动前后检查 git status 与当前分支；
3. 用项目已有的包管理器/技术栈，不随意引入新库；
4. 长任务用 TODO 计划跟踪，逐项完成并更新状态；
5. 结论先给出"根因分析 + 证据"，再给修复；不确定时先验证再下结论。
