## 一、三方结构（`Admin` / `Shared` / `Auditor`）

### 1.1 结构定义

```
src/certplatform-api/
├── CertPlatform.Shared/       ← 公共部分：两端都用得到的实体 / 服务 / 检索入口
├── CertPlatform.Admin/        ← 后台端（独立系统）：维护人员「配规则」
├── CertPlatform.Auditor/      ← 专家端（独立系统）：审核专家「跑任务」
└── CertPlatform.Enterprise/   ← 企业端（Phase 2+，当前空壳）
```

> **口径**：`Admin` 与 `Auditor` 是**两个独立系统**（各有自己的菜单、控制器、页面、端口），  
> `Shared` 是它们的**公共部分**。三者不是「一个系统的三层」。

### 1.2 依赖方向铁律（唯一合法方向）

```
Admin   ──┐
          ├──►  Shared   ──►  YZH.Core.Stand / YZH.Core.DataBase
Auditor ──┘
Enterprise ──► Shared
```

| 边                            | 状态       | 判定方式                            |
| ---------------------------- | -------- | ------------------------------- |
| `Admin → Shared`             | ✅ 必须     | csproj `ProjectReference`       |
| `Auditor → Shared`           | ✅ 必须     | 同上                              |
| `Enterprise → Shared`        | ✅ 必须     | 同上                              |
| **`Admin → Auditor`**        | ⛔ **禁止** | 守卫 **A-R1**（基线 0）               |
| **`Auditor → Admin`**        | ⛔ **禁止** | 守卫 **A-R2**（✅ **2026-10-12 已转正：0 debt**） |
| **`Shared → Admin/Auditor`** | ⛔ **禁止** | 守卫 **A-R3**（基线 0）               |

> **为什么 `Shared` 不能引任何一端**：一旦引了，`Admin → Shared → Auditor` 就成环，  
> 两端重新变成「一个系统」，独立部署与独立演进同时失效。

### 1.3 东西该放哪：四条边界判据（按顺序问）

| #     | 判据                                          | 结论                                               |
| ----- | ------------------------------------------- | ------------------------------------------------ |
| **1** | 是不是**两端都要用**？                               | 只一端用 ⇒ 放那一端（`Admin/` 或 `Auditor/`），⛔ 不放 `Shared` |
| **2** | 有没有**宿主语义**（读登录态 / 写 HTTP 响应 / 依赖当前工作区）？    | 有 ⇒ ⛔ 不进 `Shared`（会污染共享层）                        |
| **3** | 下沉后会不会**引入反向依赖**（`Shared` 需要认识 `Admin` 的类）？ | 会 ⇒ 先解依赖，再下沉                                     |
| **4** | 这个 `WHERE` 是不是**在别处已经出现过**？                 | 是 ⇒ **这就是违规**，应调 `CoreResourceQuery`（见 §三）       |

> **判据 4 是本规则最重要的一条**：它把「重复取数」从「风格问题」升级为「**缺陷**」。

### 1.4 硬纪律：`Shared` 内部的分层

| 目录                              | 纪律                                          |
| ------------------------------- | ------------------------------------------- |
| `Shared/Fill/`、`Shared/Office/` | **纯函数 / 纯计算**，⛔ 不读库、⛔ 不读登录态（守卫 **G-4**）     |
| `Shared/Domain/`（本规则新增）         | **判据与检索入口**，允许读库（走 `IDbOrm`），⛔ 不读登录态、⛔ 不写响应 |
| `Shared/Services/`              | 查库服务（既有约定）                                  |
| `Shared/Entities/`              | 双端共用实体（守卫 **R17** 判定归属）                     |

## 二、归属模型 V2 铁律（强制）

### 2.0 ★★★ 一句话（2026-10-13 用户裁定）

> **「这一行数据是谁的」—— 唯一分类判据 = `EnterpriseCode` 非空。**
>
> 用户原话：「**只要 `EnterpriseCode` 有值，就是企业端的数据**」。

| `OrgCode`       | `EnterpriseCode` | 含义                     | 实例                              |
| --------------- | ---------------- | ---------------------- | ------------------------------- |
| **机构 Code**     | 空                | **机构行**                | `cert_doc_extraction_rule`（规则属机构） |
| 空               | 企业 Code          | **企业行**（无机构冗余）         | 企业目录（若未带机构）                     |
| **机构 Code**     | 企业 Code          | **企业行 + 机构冗余** ← ⛔ **合法** | `cert_fill_param_value`（已存在）    |
| **空**           | **空**             | **平台标准级**              | `cert_iso_clause`（ISO 条款 141 行） |

⇒ ⛔ **不是「两列互斥」**，而是「**`EnterpriseCode` 是分类判据，`OrgCode` 是规则来源**」。  
⇒ ⛔ **不存在**「`OrgCode` = 机构 且 非企业行 且 平台级」的第四种组合。

**★ 关键事实（易错，务必记住）**：

1. **`cert_*.OrgCode` 存的是 `sys_organization.Code`，不是 `sys_organization.OrgCode`。**
   - 实测：`cert_org_standard.OrgCode = '906e8b2a962c4062b21144af4cc4abc0'`，该值正是机构「河北雄安尚龙认证有限公司」的 **`Code`**。
2. **`NULL` 与 `''` 是两种不同形态**：`WHERE OrgCode = ''` 与 `WHERE OrgCode IS NULL OR OrgCode = ''` 会查出**不同结果**（实测 `cert_iso_clause`：0 行 vs 163 行）。
   - ⇒ 所以本模型统一约定：**平台标准级 = 空串 `''`（NOT NULL）**，⛔ 不写 `NULL`。
3. **`cert_cert_stage` 没有 `OrgCode` 列** —— 阶段是**全局基础资料**，不参与归属隔离。

### 2.1 为什么企业行可以带 `OrgCode`（机构冗余）

> 用户原话（2026-10-13）：「很多时候，企业的信息里面存储了真实机构 code，其实**并不能算错误**，  
> 因为我们需要通过机构 code **快速获取后台的规则或标准**，**算是一种冗余**。」

- `OrgCode` 在企业行上的**用途** = 该企业**归属的认证机构** ⇒ 用于**快速定位该机构的规则 / 标准**。
- 这是**刻意的冗余**，⛔ **不是**「一列只能有一个值」的违规。
- ★ **现成样板 = `cert_fill_param_value`**：DB 列注释即「★机构编码（租户隔离键，⛔禁NULL）」+「★企业Code（`cert_enterprise.Code`，⛔禁NULL）」，  
  **两列同时有值** ⇒ 本模型**在库里有先例，不是新发明**。

### 2.2 唯一实现点（⛔ 全仓只此一处）

```csharp
// src/certplatform-api/CertPlatform.Shared/Domain/Scope/OrgScope.cs
public static class OrgScope
{
    /// ★★ 唯一分类判据 —— EnterpriseCode 非空 ⇒ 企业行
    public static bool IsEnterpriseRow(string? enterpriseCode)
        => !string.IsNullOrWhiteSpace(enterpriseCode);

    /// 机构行判据 —— OrgCode 有值（⚠️ 单独用不足以判定「是机构行」，企业行也可能带 OrgCode）
    public static bool IsOrgRow(string? orgCode)
        => !string.IsNullOrWhiteSpace(orgCode);

    /// 平台标准级判据 —— 两列都空
    public static bool IsPlatformLevel(string? orgCode, string? enterpriseCode)
        => !IsEnterpriseRow(enterpriseCode) && !IsOrgRow(orgCode);

    /// 人类可读归属描述（错误消息 / 日志用）
    /// 例：平台标准级 · 机构级(906e8b2a…) · 企业级(906e8b2a…)
    public static string Describe(string? orgCode, string? enterpriseCode);
}
```

**强制要求**：

| # | 要求                                                                                          |
| - | ------------------------------------------------------------------------------------------- |
| 1 | 「这是不是企业行」**一律调 `OrgScope.IsEnterpriseRow`**，⛔ 不许自己写 `IsNullOrEmpty(x.EnterpriseCode)` |
| 2 | 「这是不是平台标准级」**一律调 `OrgScope.IsPlatformLevel`**                                              |
| 3 | ⛔ **全仓禁止**出现 `yzh-std-env` / `YZH-STD-ENT` 字面量（守卫 **A-R10**）；`CoreOrgCodes` 类**已删除**         |
| 4 | ⚠️ **SqlSugar 表达式场景**（`Queryable<T>().Where(x => …)`）内无法调 `OrgScope` 方法 ⇒ 用等价内联 `string.IsNullOrEmpty(x.EnterpriseCode)`（该列 `NOT NULL`） |

### 2.6 ★★ 历史沿革：V1 模型（`yzh-std-env` 两值）为什么被推翻

> **留痕目的**：用户 2026-10-12 原话「**必须理解为什么这样设计，才能找到错误的本质**」。  
> 本节记录 V1 模型及其被推翻的**判据级原因**，⛔ **不要照此执行**。

| 维度    | V1（`yzh-std-env` 两值模型，已作废）                            | V2（三态 + 机构冗余，现行）                |
| ----- | --------------------------------------------------- | -------------------------------- |
| 平台标准级 | `OrgCode = 'yzh-std-env'`（**magic value**）           | **两列都空**                         |
| 机构行   | `OrgCode = 'yzh-std-env'` + `OwnerOrgCode = 机构`（10-13 中间态） | `OrgCode = 机构`（**少一列**）           |
| 企业行   | `EnterpriseCode = 企业`                               | 同                                |
| 机构冗余  | 无此概念                                                | 企业行可带 `OrgCode` = 机构              |

**V1 的三个致命缺陷**：

| # | 缺陷                     | 后果                                                       |
| - | ---------------------- | -------------------------------------------------------- |
| 1 | **magic value 无类型约束**  | `yzh-std-env` 是一个**字符串**，写错一个字母 / 大小写 ⇒ **静默 0 行**，无编译期保护 |
| 2 | **同一列承担两个语义**          | `OrgCode` 既表示「平台」（=常量）又表示「机构」（=真实 Code）⇒ **列名同形不同义**（见 §2.7） |
| 3 | **机构归属无处安放**           | 需要「具体机构」时只能**再加一列**（`OwnerOrgCode`）⇒ 列越加越多，模型未收敛     |

**V1 残留教训（仍然有效）**：

> ★ **判「某表该填什么归属值」，判据是「它是不是后台管理的模块 / 这行是不是企业数据」，  
> ⛔ 不是「历史上怎么写」，⛔ 不是「路径格式长什么样」。**
> 「取值分布」与「路径格式」都只能证明「现在是什么」，**不能证明「应该是什么」**。

**V1 曾经的两条「看似正确」的论证（留痕，⛔ 不要重犯）**：

| 错误论证                                                     | 为什么站不住                                |
| -------------------------------------------------------- | ------------------------------------- |
| 「值不同（`YZH-STD-ENT` vs `yzh-std-env`）⇒ 两个常量各管各的」           | 值不同**恰恰是问题本身** —— 同一件事有两套写法            |
| 「列不同（`EnterpriseCode` vs `OrgCode`）⇒ 不可能同义」               | 列不同**恰恰是问题本身** —— 同一件事有两套列             |
| 「`cert_standard_directory_file` 无 `OrgCode` 列 ⇒ 概念上不同」     | 把「**物理上不在同一列**」当成了「**概念上不同**」          |

> ★ **教训**：判「是否重复」**不能只看物理形态**（列名 / 取值 / 所在表），  
> 要看**它回答的是不是同一个业务问题**。两个字段回答同一个问题 ⇒ **就是重复**。

### 2.7 ★★★ 「错误的本质」：`OrgCode` 列名同形不同义（2026-10-13 实测定案）

> 这是本仓**最容易误判**的一处：同一个列名 `OrgCode`，全库有 **4 种含义**。  
> **读代码 / 写 `WHERE` 前，必须先确认是哪一层。**

| 表                                                                                  | DB 列             | **实际存什么**                     | 实体属性名            |

| `cert_iso_clause` · `cert_fill_param_def` · `cert_nc_*` · `cert_conclusion_rule` … | `OrgCode`        | **平台标准级（空）或机构**               | `OrgCode`        |
| `cert_standard_directory_config` · `_file`                                         | `OrgCode`        | **机构**                        | `OrgCode`        |
| `cert_report_section` · `cert_validation_rule` · `cert_doc_template` · `cert_doc_extraction_rule` | `OrgCode`        | **机构**                        | `OrgCode`        |
| `cert_org_standard` · `cert_org_stage`                                             | `OrgCode`        | **机构**                        | `OrgCode`        |
| **`cert_fill_param_value`**                                                        | `OrgCode` + `EnterpriseCode` | **机构 + 企业**（企业行带机构冗余）         | 同名               |
| **`cert_extraction_result` / `cert_table_extraction_result`**                      | `EnterpriseCode` | **企业**（2026-10-13 已列改名）        | `EnterpriseCode` |

## 三、核心资源检索铁律（唯一入口）

### 3.1 「核心资源」的范围（权威清单）

| 类别        | 表                                                                                                            | 说明                  |
| --------- | ------------------------------------------------------------------------------------------------------------ | ------------------- |
| **机构**    | `sys_organization`                                                                                           | 含虚拟机构行 `yzh-std-env`（§2.4 例外，已标记废弃） |
| **标准**    | `cert_iso_standard` · `cert_iso_clause`                                                                      | 标准 + 章节             |
| **阶段**    | `cert_cert_stage`                                                                                            | 全局基础资料（无 `OrgCode`） |
| **关联**    | `cert_org_standard` · `cert_org_stage`                                                                       | 机构×标准 / 机构×阶段       |
| **NC 规则** | `cert_conclusion_rule` · `cert_nc_judge_prompt` · `cert_nc_conclude_prompt`                                  | 结论规则 + 判定/结论提示词     |
| **章节规则**  | `cert_clause_extraction_rule`                                                                                | 章节提取规则              |
| **填写规则**  | `cert_fill_param_def` · `cert_doc_fill_prompt`                                                               | 参数定义 + 填写提示词        |
| **提取规则**  | `cert_doc_extraction_rule`                                                                                   | 文档提取规则              |
| **标准文档**  | `cert_doc_template` · `cert_standard_directory_config` · `cert_directory_template` · `cert_file_requirement` | 模板 + 目录配置           |

### 3.2 铁律 L5：一个业务概念一个检索入口

> **「机构 + 标准 + 阶段」及其派生规则（NC / 章节 / 填写 / 提取）的取数，  
> 只允许在 `CoreResourceQuery` 内实现。端内只允许「投影」。**

**「投影」的定义**（允许做的事）：

- 选字段（`Select`）
- 加派生列（`Count` / `Max` / 拼接）
- 排序 / 分页
- 组装成页面需要的 DTO 形状

**⛔ 不允许做的事**：

- 自己写 `Queryable<ISOStandard>()` / `GetListAsync<CertStage>()` / `GetOneAsync<FillParamDef>()`
- 自己拼 `WHERE` 条件（含 `OrgCode` / `EnterpriseCode` 归属判据、`IsValid`、`IsDeleted`、`Status`）
- 自己在端内再写一遍「取后台标准」的逻辑

### 3.3 唯一入口签名（设计稿，落地以 `CoreResourceQuery.cs` 为准）

```csharp
// src/certplatform-api/CertPlatform.Shared/Domain/Scope/CoreResourceQuery.cs
namespace CertPlatform.Shared.Domain.Scope;

/// <summary>
/// 核心资源检索唯一入口。
/// 规则：所有「机构 + 标准 + 阶段」及其派生规则的取数，一律走本接口。
/// </summary>
public interface ICoreResourceQuery
{
    // ── 标准 ──
    Task<List<ISOStandard>> GetStandardsAsync(string enterpriseCode, CancellationToken ct = default);
    Task<List<ISOClause>>    GetClausesAsync(string standardCode, CancellationToken ct = default);

    // ── 阶段 ──
    Task<List<CertStage>>    GetStagesAsync(CancellationToken ct = default);

    // ── 机构×标准 / 机构×阶段 ──
    Task<List<CertOrgStandard>> GetOrgStandardsAsync(string enterpriseCode, CancellationToken ct = default);
    Task<List<CertOrgStage>>    GetOrgStagesAsync(string enterpriseCode, CancellationToken ct = default);

    // ── 派生规则（按归属范围取：平台标准级 or 机构级 or 企业专属）──
    Task<ConclusionRule?>      GetConclusionRuleAsync(string scopeOrgCode, CancellationToken ct = default);
    Task<NcJudgePrompt?>       GetNcJudgePromptAsync(string scopeOrgCode, CancellationToken ct = default);
    Task<NcConcludePrompt?>    GetNcConcludePromptAsync(string scopeOrgCode, CancellationToken ct = default);
    Task<List<FillParamDef>>   GetFillParamDefsAsync(string scopeOrgCode, CancellationToken ct = default);
    Task<DocFillPrompt?>       GetDocFillPromptAsync(string scopeOrgCode, CancellationToken ct = default);
    Task<List<DocExtractionRule>> GetDocExtractionRulesAsync(string scopeOrgCode, CancellationToken ct = default);

    // ── 树 ──
    Task<List<CoreTreeNode>> GetOrgStandardStageTreeAsync(string enterpriseCode, CancellationToken ct = default);
}
```
