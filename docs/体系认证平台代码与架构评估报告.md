### 1.2 总体判断

> **该平台处于"骨架可用、可继续演进，但必须先做一次结构性收口"的水平，综合评分 3.0/5。**

判断依据分三层：

1. **工程自觉性显著高于同类单人主导项目**。后端全工程开启 Nullable 与隐式 using，`dotnet build` 零错误、`dotnet test` 166/166 全通过；前端 20 条架构守卫规则（R1–R16 家族，含 R12 跨文件交叉校验、R14–R16 需跨行上下文的自定义规则）在全仓 999 个文件上零违规；迁移脚本中"统一字符集 utf8mb4_0900_ai_ci""统一 `IsValid` 布尔字段""统一响应信封"等已被固化为成文铁律。这些不是靠人记性维持的约定，而是可执行、可回归的规则。
2. **三处结构性风险已开始产生实际成本**：框架层（`YZH.Core.Web`）反向依赖业务层且框架自述能力与业务实际接入面严重倒挂；工作流引擎"能跑通"但缺少断点续跑、失败重试、事务包裹与幂等四件运行态保障；配置来源、迁移命名、任务项数据模型三处均双轨并存，导致同一事实有两套以上表述。
3. **一处必须立即修复的安全问题**：JWT 签名密钥以硬编码 fallback 形式存在于 `Program.cs`，且与仓库内 `appsettings.json` 中的值相同——密钥已进入版本库，等同于公开。

### 1.4 三条结构性结论（全文主线）

| 编号 | 结构性结论 | 直接后果 | 展开章节 |
|---|---|---|---|
| S1 | **框架层与业务接入面倒挂**：框架自述的能力（`YzhCrudPage`、`YzhControllerBase` 等）在业务中几乎未被引用，而框架又反向依赖业务工程 | 框架既无法独立复用，也无法独立测试；任何业务改动都可能牵动框架编译 | 第 2 章 |
| S2 | **引擎缺运行态保障**：执行链路一次性串行跑完，无断点续跑、无节点级重试、无事务边界、无幂等键 | 长耗时 AI 审核任务一旦中断即需重跑；失败节点无法单独重试；跨表写入可能半成功 | 第 3 章 |
| S3 | **同一事实多轨表述**：工作流配置源（`wf_workflow_definition` 表 vs `cert_validation_rule.RuleJson`）、迁移脚本命名（日期 vs phase）、任务项模型（两种表 + 两种 DAG 列名 `RuleJson` / `WorkflowConfig`） | 每新增一个功能都要额外维护"归一"代码，是最主要的长期维护成本来源 | 第 3、4 章 |

### 2.2 依赖方向核查（本章核心发现）

实测得到的工程引用关系（`grep ProjectReference`，全量）：

```
YZH.Core.Web  ──► YZH.Core.Api / DataBase / Stand
              ──► 【CertPlatform.Shared / Admin / Auditor / Enterprise】   ← 框架宿主依赖业务层
CertPlatform.Admin    ──► YZH.Core.Api / DataBase / Shared
CertPlatform.Auditor  ──► YZH.Core.Api / DataBase / Shared
                      ──► 【CertPlatform.Admin】                          ← 业务横向依赖业务
CertPlatform.Shared   ──► YZH.Core.Stand（唯一依赖，边界干净）
YZH.Core.Api.Tests    ──► YZH.Core.Web（测试依赖宿主）
```

三个结构性问题：

| 编号 | 问题 | 证据 | 影响 |
|---|---|---|---|
| A-1 | **框架宿主反向依赖业务层** | `YZH.Core.Web.csproj` 引用 `CertPlatform.Shared/Admin/Auditor/Enterprise` 四个业务工程 | 框架层无法独立编译、独立测试、独立复用；"框架"被降格为"本项目的启动器"，后续任何其他系统想复用 `yzh-core` 都必须剥离宿主 |
| A-2 | **业务工程横向依赖** | `CertPlatform.Auditor.csproj` 引用 `CertPlatform.Admin.csproj` | 审核端与管理端无法独立部署/独立演进；Auditor 改动会触发 Admin 重编译，且职责边界（审核域 vs 管理域）在编译期被抹平。审核端是**对外交付给认证机构审核员**的一侧，与内部管理端耦合过高 |
| A-3 | **空壳工程被引用** | `CertPlatform.Enterprise` 源文件 0、`Controllers/Entities/Services` 三目录皆空，但被 `YZH.Core.Web` 引用 | 预留的扩展位形同虚设；同时 `CertPlatform.Shared/WorkflowEngine` 目录也是空目录，说明"预留结构"已成为一种习惯，反而增加了目录噪音 |

**框架落地度的真实测量**（避免仅凭框架自述判断其价值）：

| 框架抽象 | 业务工程引用文件数 | 判定 |
|---|---|---|
| `YZH.Core.Stand.Interfaces`（using） | 87 处 | 实际在用，基础契约层是真实资产 |
| `EntityService`（实体服务） | 22 | 在用 |
| `YzhControllerBase`（控制器基类） | 20（Admin 20 个控制器中的 12 个 + Auditor 9 个中的 8 个） | 部分在用，仍有 9 个控制器未走基类 |
| `QueueManager`（队列管理） | 11 | 在用 |
| `YzhCrudPage`（前端 CRUD 抽象） | **0** | 未被业务引用 |
| `CrudPageLogic`（前端页面逻辑基类） | **0**（业务侧） | 未被业务引用 |

> 结论：**后端框架层是"部分兑现"（契约层、实体服务、队列在真实支撑业务），前端框架层是"基本未兑现"**。前端体量最大的抽象（`YzhCrudPage`/`CrudPageLogic` 等）没有业务接入，同时 `cert-share` 反而长到 11657 行——说明该进框架的统一逻辑被写进了业务共享层，抽象位置放错了。

### 2.3 模块划分评估

**做得对的部分：**

- `CertPlatform.Shared` 只依赖 `YZH.Core.Stand`，边界干净，是唯一符合分层原则的业务工程；实体集中（`Entities/Cert`、`Entities/Wf`、`Entities/Expert`、`Entities/Rpt`）便于跨端复用。
- `Admin` / `Auditor` 按**使用者角色**切分而非按技术分层切分，与"管理端 Element Plus / 审核端 Naive UI"的双端形态一致，方向正确。
- 后端控制器按业务子域组织（`Controllers/Foundation`、`Controllers/Cert`、`Controllers/Workflow`），可读性好。

**划分存在的问题：**

| 编号 | 问题 | 说明 |
|---|---|---|
| A-4 | 工作流引擎落在 `CertPlatform.Admin` 内的 `Services/Workflow`（39 文件 9703 行）+ `Controllers/Workflow`（9 文件 2736 行），合计约 **12439 行**，而 `CertPlatform.Shared/WorkflowEngine` 是空目录 | 引擎作为平台级能力却寄居在管理端工程内，导致 Auditor 侧要执行工作流必须依赖 Admin（即 A-2 的根因之一）。引擎应下沉为独立工程（如 `CertPlatform.Workflow`），Admin/Auditor 都只依赖它 |
| A-5 | 框架层（`YZH.Core.Api`）与业务层（`CertPlatform.Shared`）职责存在重叠：Shared 已含实体与共享服务，Api 又含 `EntityService` 等通用服务 | 边界模糊，新增功能时容易"两边都写一点"，这是当前 9 个控制器不走 `YzhControllerBase` 的可能成因 |
| A-6 | 队列执行逻辑分散：`QueueManager`（框架，800 行）+ 业务侧各执行器（企业文件、Office 转换、企业抽取等） | 缺少统一队列内核与统一的任务状态机，可观测性依赖各执行器自觉 |

## 第 3 章 工作流引擎专项评估

> 评估对象：`CertPlatform.Admin/Services/Workflow`（39 个文件 / **9703 行**）+ `Admin/Controllers/Workflow`（9 个文件 / **2736 行**）+ `Shared/Entities/Wf`（实体）+ DDL 中 **12 张 `wf_*` 表**，合计约 12439 行，是全系统技术密度最高的部分。评估人视角：工作流引擎设计负责人。

### 3.1 引擎的真实接入面（先厘清"谁在跑它"）

| 接入方 | 调用方式 | 说明 |
|---|---|---|
| `Auditor/Expert/ExpertItemExecutors.cs` | `WfExecutionTaskService.CreateAndRunAsync`，2 处（第 186、517 行） | `TaskType = NC_CHECK` / `REPORT_GENERATE`，由专家任务队列驱动，是**唯一生产链路** |
| `Admin/Controllers/Workflow/WorkflowTestController.cs` | `CreateAndRunAsync` | 管理端"整流程测试"（`TestScope=FULL`） |
| 前端 `WorkflowDesigner.vue` | 无直接调用，仅产出配置 | 设计器 JSON 落 `cert_validation_rule.rule_json` |
| `WorkflowTestController` 节点测试 | `RunSingleNodeAsync` / `RunAiNodeAsync` | `TestScope=NODE` / `AI_NODE`，单节点调试 |

**配置真相源（关键事实）**：引擎读取的是 `cert_validation_rule.rule_json`，而非 `wf_workflow_definition` 表——`wf_execution_task.config_snapshot` 的 DDL 注释原文即"从 cert_validation_rule.rule_json 锁定"。实测 `WorkflowDefinition` 实体（`Shared/Entities/Wf/WorkflowDefinition.cs`）除自身定义外**全代码零引用**，即 `wf_workflow_definition` 是一张**无消费方的表**。

> 结论：引擎的 DAG 配置寄生在"校验规则"的 JSON 字段内。同一份事实被 5 个以上模块读写（`ExpertTaskService`、`ExpertItemExecutors`、`GapDetector`、`ValidationRuleController`、引擎自身），跨 Admin/Auditor 两个应用——这是第 1 章 S3（同事实多轨表述）的具象载体，也是引擎最需要收口的地方。

### 3.2 运行架构（机制层面）

引擎分层清晰，是"解释器 + 节点执行器 + Skill 插件"的经典结构：

```
WfExecutionTaskService（入口/落库/收口，599+540+323 行）
   └─ WorkflowConfigParser（389 行）      ：ruleJson → 节点/边/拓扑校验/路径枚举
   └─ WorkflowInterpreter（389 行）       ：按路径执行、跨路径结果池复用
        └─ NodeExecutor（566 行）         ：分派 node_type（start/end/skill/ai_node/logic/branch/docField/docTable）
             ├─ SkillExecutor（271 行）+ CertSkillRegistry + 22 个 Skill（Skills/*，含 Nc* 3 个）
             └─ AiNodeExecutor（758 行）  ：LLM 调用
   └─ TaskCacheService（275 行）/ PromptMarkdownCache（160 行）：任务级缓存 + 提示词缓存（TTL 8h）
   └─ WorkflowLogger（185 行）/ PromptWorkbenchService（1132 行）：可观测与提示词工作台
```

**值得肯定的设计（本次实测确认）：**

| 编号 | 亮点 | 证据与价值 |
|---|---|---|
| P-1 | **路径枚举有硬上限** | `WorkflowConfigParser.MaxTotalPathNodes = 5000`，超限抛异常（"路径枚举节点总数超限…工作流配置可能过于复杂"）。多分支 DAG 的路径爆炸是工作流引擎最常见的事故源，此处做了显式防御 |
| P-2 | **执行配置快照落库** | `wf_execution_task.config_snapshot json NOT NULL`，注释"执行时的工作流配置快照"；配合 `WorkflowLogger` 的 `TaskCreate/NodeReuse/ItemDone` 事件，事后可还原"当时测的是什么"。这是审核场景**证据链**要求的正确响应 |
| P-3 | **跨路径复用有真实实现** | `WorkflowInterpreter` 按 `node_id` 维护结果池，命中则 `IsReused=true` 直接从结果池取、不重跑（第 191-205 行）；`wf_node_execution` 唯一键 `uk_task_item_node` 保证幂等落库 |
| P-4 | **三个测试入口同构** | 单节点测试用"伪路径"（`TestScope=NODE` 合成 `[目标节点]`；`AI_NODE` 由 ruleJson 反向 BFS 出上游链），使 `PathResults/落库行/日志 Tag 与整流测试完全同构`，前端 `ExecutionResultPanel` 无需写分支 |
| P-5 | **AI 结论有二次校验** | `NcConclusionCalculator`（415 行）+ `NcOutputValidator`（245 行）+ `NcValidateSkill`，对 LLM 输出做规则化计算与校验，而非直接采信 |
| P-6 | **缓存有明确业务语义** | `cache_keys` 落库 + `PromptMarkdownCache` 注释"TTL 8 小时覆盖一个完整工作日的『改提示词 → 重跑』循环"——缓存策略与真实工作节奏对齐，非拍脑袋 |

### 3.3 关键缺陷与风险

| 编号 | 问题 | 等级 | 证据 |
|---|---|---|---|
| E-1 | **执行阶段无兜底收口，异常逃逸即产生僵尸任务** | **严重** | `CreateAndRunAsync` 仅对"配置解析"做了 try-catch；第 4-6 步（解释执行 → `SavePathExecutions` → `SaveNodeExecutions` → `FinishRunAsync`）**无 try/finally 包裹**。任何未捕获异常（DB 抖动、Skill 反射失败、CancellationToken 取消）都会让 `task_status` 永久停留在 `executing` |
| E-2 | **无卡死任务回收机制** | **严重** | 引擎侧未发现任何租约/超时/回收逻辑（全目录 grep `retry/resume/续跑/断点` 无命中）。对照同仓的 `ExpertTaskQueueRunner`：它有 10 分钟租约 + 启动时 `ReapStaleAsync` 回收中断项 + 指数退避。**同一系统内两套成熟度**，引擎侧缺少对等保障 |
| E-3 | **状态机名存实亡，字段与运行事实不符** | 中等 | DDL：`task_status` 默认 `queued`，枚举含 `queued\|executing\|completed\|failed\|cancelled`，并设 `idx_queue`/`idx_type_status` 索引与 `queue_code` 列；但 `BeginRunAsync` 直接以 `"executing"` 插入，**引擎从不写 `queued` 与 `queue_code`**（引擎为同步内联执行）。运维看板若按状态机口径统计会失真 |
| E-4 | **收口非原子，无幂等/续跑语义** | 中等 | "路径落库 → 节点落库 → 收口+清缓存"为三段独立 `Insertable/Updateable`，无事务；任务 `code` 每次 `Guid.NewGuid()` 新生成（非业务幂等键），失败后只能整任务重跑，**无法基于 `wf_node_execution` 已完成的 `completed` 行做断点续跑**——表里存了状态，却没有消费者 |
| E-5 | **LLM 调用无引擎级重试/降级** | 中高 | `AiNodeExecutor`（758 行）有 `CancellationToken` 透传，但引擎层无退避重试、无模型降级、无"AI 节点失败可人工接管"的通道。LLM 是外部不稳定依赖，单次抖动即让整条路径判 `failed` |
| E-6 | **配置真相源割裂 + 死表** | 中等 | DAG 配置在 `cert_validation_rule.rule_json`（跨 5+ 模块、跨两应用读写）；`wf_workflow_definition` 表与 `WorkflowDefinition` 实体零引用。设计愿景与实际实现不一致，新人按表结构理解系统必然误判 |
| E-7 | **成本与复用收益不可度量** | 中等 | `wf_node_execution` 字段清单（`node_id/node_type/node_title/skill_code/exec_status/output_json/error_message/started_at/completed_at/execution_time_ms/is_reused`）**无 token/成本列**；且因落库按 `node_id` 分组只保留真执行那次，DB 里 `IsReused` **恒为 0**（代码注释已自陈该取舍）。结果：复用节省率、单次审核的 LLM 成本均无数据支撑 |
| E-8 | **节点 ID 由前端生成、无版本语义** | 中等 | DDL 注释：`node_id` 为"前端生成的 classCode_n 序号"；`wf_node_execution` 按 `node_id` 关联历史。节点重命名/重建会切断历史追溯；Skill 实现也**无版本号**（`skill_code` 无版本维度），配置快照可复现"配置"，却无法复现"当时那版实现" |
| E-9 | **Skill 执行缺沙箱与超时** | 轻微 | `SkillExecutor` 全目录 grep 未见重试/事务/超时控制；统一按反射+注册表（`CertSkillRegistry`、`SkillAttributes`、`SkillContext`）分发。Skill 数量增长后，单个 Skill 的异常/慢查询会拖垮整个任务 |

### 3.4 成熟度落差：同一仓库内的两个标杆对比

| 能力 | 专家任务队列 `ExpertTaskQueueRunner`（569 行） | 工作流引擎 `WfExecutionTaskService` |
|---|---|---|
| 调度形态 | `BackgroundService`，轮询 + 乐观领取（`UPDATE … WHERE ItemStatus='pending'` 校验影响行数） | 同步内联执行 |
| 并发控制 | `MaxConcurrent = 3` + 同队列串行（保证 Seq 顺序、不打爆 LLM 配额） | 无并发上限约束 |
| 租约/回收 | 10 分钟租约 + 启动 `ReapStaleAsync` 回收中断项 | **无** |
| 退避 | 指数退避 + `ItemExecOutcome{Success, Retryable, Message}` 重试语义 | **无** |
| 收口 | 独立 scope + `FinalizeAsync`，失败兜底 `try/catch` 包裹 | 三段写入，无兜底 |
| 幂等 | `WHERE ItemStatus='pending'` 抢占即幂等 | 每次新 Guid 任务码，不可续跑 |

> **这是本次评估最重要的单一洞察**：引擎需要的运行态保障，团队**已经写过一遍**，就在隔壁文件里。E-1/E-2/E-4 的修复不需要发明新机制，只需要把 `ExpertTaskQueueRunner` 已验证的"租约 + 回收 + 乐观领取 + 统一收口"范式移植到引擎，并让 `task_status` 真正承担状态机职责。

### 3.5 本章问题清单（按修复优先级）

| 优先级 | 问题 | 建议动作（详见第 5 章） |
|---|---|---|
| P0 | E-1 无兜底收口、E-2 无卡死回收 | 引擎侧加 `try/finally` + 状态兜底；引入租约与回收任务；`task_status` 落真实状态机 |
| P0 | E-6 配置真相源割裂 | 明确 `rule_json` 为唯一真相源并文档化，删除/标注 `wf_workflow_definition` 死表；或将配置上收为独立表 |
| P1 | E-4 无幂等/续跑、E-7 成本不可度量 | 任务码改为业务幂等键；补 token/成本列与复用指标口径；补断点续跑入口 |
| P1 | E-5 无重试/降级、E-9 无超时 | 节点级超时 + 退避重试 + AI 节点人工接管通道 |

## 第 4 章 数据层、前端与交付链路评估

### 4.1 数据层

**规模与形态（实测）**：`scripts/db/all_tables_ddl.sql` 191 KB / **95 张表**；`CertPlatform.Shared/Entities` 下 **73 个实体文件**；迁移脚本 `scripts/db` 目录 **119 个文件**（仓库内 `.sql` 合计 240 个，已排除 `old/`）；DDL 含 **61 条外键约束**。

**做得对的部分：**

| 编号 | 亮点 | 说明 |
|---|---|---|
| DL-1 | DDL 成文且带表级/列级 COMMENT | 每张表有 `COMMENT`，关键表（如 `wf_execution_task`）的注释直接写明语义来源（"从 cert_validation_rule.rule_json 锁定"）与任务类型枚举 `TEST \| NC_CHECK \| REPORT_GENERATE`。这是评估中能快速建立准确认知的前提，也是文档化水平高的直接体现 |
| DL-2 | 引擎状态有独立的表承载 | `wf_execution_task` / `wf_execution_task_item` / `wf_node_execution` / `wf_path_execution` 分层落库，`wf_node_execution` 有唯一键 `uk_task_item_node`（天然幂等）与 `idx_exec_status`，且注释标明"节点执行状态（跨路径复用的核心载体）"——状态设计是有意图的，不是随手建表 |
| DL-3 | 有真实外键约束 | 95 表含 61 条 FK。多数同类项目为规避 ORM 迁移麻烦会直接放弃外键，此处保留了引用完整性 |
| DL-4 | 关键索引到位 | `wf_execution_task` 上 `idx_type_status`（类型+状态）、`idx_rule`、`idx_enterprise`、`idx_phase` 覆盖了查询面板的主要过滤维度 |

**存在的问题：**

| 编号 | 问题 | 等级 | 证据 |
|---|---|---|---|
| D-1 | **软删口径双轨**：95 表中 67 张有 `IsDeleted`（PascalCase）、21 张有 `delete_time`（snake_case），其中 **14 张两者并存**（含全部 `wf_*` 表） | 中等 | 同一张表里 `delete_time` 与 `IsDeleted` 并存，删除语义取决于各 Service 选哪个字段——与第 1 章 S3"同事实多轨表述"同源。`wf_execution_task`、`wf_node_execution` 均是双标记表 |
| D-2 | **命名风格在同一张表内混用**：`snake_case` 业务列 + `PascalCase` 的 `IsDeleted` | 中等 | 95 张表统一存在该混用；**且 `wf_execution_task` 同时出现 `create_date` 与 `CreateTime`（实体）、`delete_time` 与 `IsDeleted`**。驼峰/下划线映射依赖 ORM 配置，任何直写 SQL 的地方都要记两套名字，是最容易出错的一类债务 |

| D-4 | **迁移脚本三种命名规范并存、无顺序声明** | 中等 | 同目录下并存 `001-create-api-permission-tables.sql`（序号-连字符）、`001_skill_tables_V1.sql`（序号_下划线_版本）、`20260915_report_definition_alter.sql`（日期_语义_动作）。序号均从 001 起，**存在序号冲突**，无法靠文件名确定执行顺序；119 个脚本无统一 changelog |
| D-5 | **列定义与实体标注不一致（已发生）** | 中等 | `wf_execution_task.phase_code` 在 DDL 为 `varchar(30)`，实体标注 36，且需多份迁移逐步修正（第 1 章已记录）。说明"DDL 与实体谁是真源"未定，靠迁移打补丁追平 |

**存在的问题：**

### 4.3 交付与运维链路

**实测现状**：`docker/compose.yml` 编排 5 个**基础设施/工具**服务——MySQL 8.0、Redis 7、MinIO、LibreOffice（自建镜像 + CJK 字体）、anydoc（自建镜像），全部带 `healthcheck`；`Dockerfile` 仅存在于 `docker/libreoffice` 与 `docker/anydoc`；**无 `.github/workflows`（无 CI）**；应用自身（后端、前端）均以本机方式运行。

**意外的亮点（应保留）：**

| 编号 | 亮点 | 说明 |

### 5.2 推进节奏与优先级原则

单人主导、长期独立演进的前提下，排序遵循三条原则：

1. **先止血，再强身**：能被外部利用或造成不可逆数据状态的问题（SEC-1、E-1/E-2）先处理。
2. **先接已有能力，再新建能力**：CI 三件套、队列租约范式、DDL 已成文——**优先复用已写过的代码与规则**，新增机制排后。
3. **结构性改动集中一次做**：引擎下沉（A-4）一旦动手，会同时暴露 A-2、E-6、F-1 等依赖问题；分散改动等于重复扰动。原则是**攒够动因、一次迁移、一次回归**。

### 5.3 阶段 0：立即处置（1–3 天，不涉及架构改动）

| 序 | 动作 | 具体做法 | 验收口径 |
|---|---|---|---|
| 0-1 | **轮换 JWT 密钥并移除硬编码 fallback**（SEC-1） | 生成新密钥写入环境变量/用户机密（`dotnet user-secrets` 或部署环境变量）；`Program.cs` 中 fallback 改为"缺失即启动失败"，不再提供默认值 | 代码中 grep 不到任何密钥字面量；旧 Token 全部失效 |
| 0-2 | **评估历史泄露面**（SEC-2） | 确认 `appsettings.json` 是否曾在未忽略状态下被提交；若已提交，同步轮换 MySQL/MinIO/Redis 凭据 | 有书面结论（是否需清史 / 各凭据是否已轮换） |
| 0-3 | **把"配置真相源"写成一行铁律**（E-6 前置） | 在 `项目全局规则.md` 明确："工作流 DAG 以 `cert_validation_rule.rule_json` 为唯一真相源；`wf_workflow_definition` 为历史预留、当前无消费方，禁止新逻辑写入" | 规则条目落文并可被后续 AI/协作者检索 |

### 5.7 明确不建议做的事（避免过度工程化）

在单人主导、以"能长期独立演进"为目标的约束下，以下动作**现在做会亏**：

| 不建议 | 原因 |
|---|---|
| 现在就把微服务拆分、引入消息中间件（Kafka/RabbitMQ） | 当前瓶颈是"运行态保障缺位"，不是吞吐；`ExpertTaskQueueRunner` 的数据库队列已够用。先补租约与回收，观测到真实瓶颈再评估 |
