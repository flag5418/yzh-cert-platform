# 标准目录 - 批量上传架构设计

> 创建时间：2026-08-09
> 状态：设计阶段

---

## 一、核心思路

**先规划后执行，预建后上传，失败全回滚。**

传统逐文件上传的问题：170个文件 = 510+次DB操作 + 170次HTTP请求，慢、易出错、无回滚。

新方案：后端一次性预处理（生成编码、建记录、初始化OSS路径），客户端拿到增强清单后再逐个上传文件到MinIO，任一失败立即全量回滚。

**双重安全保障：**
1. **TaskId 维度**：主动调用 cancel 清理本次任务数据
2. **有效标志维度**：被动发现残留，新任务启动时自动清理上次未完成的脏数据

## 三、数据结构定义

### 3.1 客户端基础清单（upload-init 请求体）

用户选择文件后，在本地生成此JSON，包含所有待上传文件的原始信息：

```json
{
  "directoryCode": "SDC-ISO134852016|STAGE01",
  "folders": [
    { "path": "4记录文件" },
    { "path": "4记录文件/内审记录" },
    { "path": "4记录文件/管理评审" }
  ],
  "files": [
    {
      "relativePath": "4记录文件/内审记录/陪审人员.doc",
      "fileName": "陪审人员.doc",
      "fileSize": 35328,
      "mimeType": "application/msword"
    },
    {
      "relativePath": "4记录文件/内审记录/风险管理报告.doc",
      "fileName": "风险管理报告.doc",
      "fileSize": 52224,
      "mimeType": "application/msword"
    },
    {
      "relativePath": "4记录文件/管理评审/评审记录.pdf",
      "fileName": "评审记录.pdf",
      "fileSize": 1048576,
      "mimeType": "application/pdf"
    }
  ]
}
```

**字段说明：**
- `directoryCode`：目标目录编码（前端从 currentConfig 取）
- `folders`：需要创建的文件夹列表（前端从文件路径中提取去重）
- `files`：待上传文件列表
  - `relativePath`：文件的相对路径（含文件夹层级）
  - `fileName`：文件名
  - `fileSize`：文件大小（字节）
  - `mimeType`：MIME类型

### 3.2 服务端增强清单（upload-init 响应体）

服务端处理后，返回增强清单。每个文件补充了编码、OSS路径、上传索引等信息：

### 3.3 客户端上传循环逻辑

```javascript
// 伪代码
async function uploadFiles(manifest) {
  const { taskId, files } = manifest
  let failed = false

  for (let i = 0; i < files.length; i++) {
    if (failed) break

    const file = files[i]
    const formData = new FormData()
    formData.append('File', localFileMap[file.relativePath])  // 本地文件对象
    formData.append('StoragePath', file.storagePath)
    formData.append('FileCode', file.fileCode)
    formData.append('TaskId', taskId)

    try {
      const res = await http.post('/api/standard-directory/upload-file', formData)
      if (res.Status) {
        updateProgress(i + 1, files.length)  // 更新进度条
      } else {
        failed = true
        await cancelUpload(taskId)
        ElMessage.error(`上传失败: ${file.fileName}`)
      }
    } catch (err) {
      failed = true
      await cancelUpload(taskId)
      ElMessage.error(`上传异常: ${file.fileName}`)
    }
  }

  if (!failed) {
    await confirmUpload(taskId)
    ElMessage.success('全部上传成功')
  }
}
```

**关键规则：任一文件失败 -> 立即停止 -> 调用 cancel -> 不再允许上传新文件。**

## 四、API 设计

### 4.1 POST /api/standard-directory/upload-init

**用途：** 接收客户端清单，预创建编码和数据库记录，返回增强清单。

**请求体：** 3.1 节的基础清单

**响应体：**
```json
{
  "Status": true,
  "Code": null,
  "Message": null,
  "Data": { /* 3.2 节的增强清单 */ }
}
```

**服务端处理逻辑：**
1. 校验 directoryCode 对应的配置是否存在
2. **检查并清理残留数据**：查找该 directoryCode 下 IsValid=0 的文件夹和文件记录，删除对应的 MinIO 文件和 DB 记录
3. 处理文件夹列表（去重、创建编码、写入DB、复用已有文件夹）
4. 处理文件列表（生成 fileCode、storagePath、写入DB记录 status=pending, IsValid=0）
5. 创建 cert_upload_task 记录（Status=initialized, ExpireTime=当前+30分钟）
6. 返回增强清单

### 4.2 POST /api/standard-directory/upload-file

**用途：** 上传单个文件到 MinIO（沿用现有接口，增加 TaskId 参数）。

**请求体（FormData）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| File | IFormFile | 文件内容 |
| FileCode | string | 增强清单中的 fileCode |
| StoragePath | string | 增强清单中的 storagePath |
| TaskId | string | 任务ID |

**响应体：**
```json
{
  "Status": true,
  "Message": "文件上传成功：陪审人员.doc"
}
```

**服务端处理逻辑：**
1. 校验 TaskId 对应的任务是否存在且 Status=initialized
2. 校验 FileCode 对应的文件记录是否存在且 status=pending
3. 上传文件到 MinIO 的 StoragePath
4. 更新文件记录 status=active
5. 更新任务记录的 SuccessCount

### 4.3 POST /api/standard-directory/upload-confirm

**用途：** 确认全部文件上传完成。

**请求参数：** `taskId`（query或body均可）

**响应体：**
```json
{
  "Status": true,
  "Message": "上传确认完成，共3个文件"
}
```

**服务端处理逻辑：**
1. 校验 taskId 对应的任务是否存在
2. 检查该任务下所有文件记录 UploadStatus 是否都为 active
3. **批量激活**：将该 taskId 下所有文件夹记录的 IsValid 设为 1
4. **批量激活**：将该 taskId 下所有文件记录的 IsValid 设为 1
5. 更新任务 Status=completed
6. 返回成功

### 4.4 POST /api/standard-directory/upload-cancel

**用途：** 回滚整个上传任务（清理所有预创建的数据）。

**请求参数：** `taskId`（query或body均可）

**响应体：**
```json
{
  "Status": true,
  "Message": "回滚完成，已清理3个文件和3个文件夹"
}
```

**服务端处理逻辑（按顺序执行）：**
1. 查找 taskId 对应的所有 IsValid=0 的文件记录
2. 逐个删除 MinIO 中已上传的文件（通过 StoragePath）
3. 删除这些文件的 DB 记录
4. 查找该 taskId 创建的文件夹记录（仅删除 IsValid=0 的空文件夹）
5. 删除这些文件夹的 DB 记录
6. 删除 cert_upload_task 记录
7. 返回清理结果

### 4.5 GET /api/standard-directory/upload-status（可选）

**用途：** 查询上传任务状态（用于断点续传或页面刷新后恢复）。

**请求参数：** `taskId`

**响应体：**
```json
{
  "Status": true,
  "Data": {
    "taskId": "550e8400-...",
    "status": "initialized",
    "totalFiles": 170,
    "successCount": 45,
    "failCount": 0,
    "files": [
      { "fileCode": "FL-...", "status": "active", "fileName": "陪审人员.doc" },
      { "fileCode": "FL-...", "status": "pending", "fileName": "风险管理报告.doc" }
    ]
  }
}
```

### 5.2 cert_standard_directory_file 增加字段

```sql
ALTER TABLE cert_standard_directory_file 
  ADD COLUMN TaskId VARCHAR(64) NULL COMMENT '上传任务ID',
  ADD COLUMN IsValid TINYINT(1) DEFAULT 1 COMMENT '有效标志: 0=无效(预创建), 1=有效(已确认)',
  ADD COLUMN UploadStatus VARCHAR(20) DEFAULT 'active' COMMENT '上传状态: pending/uploading/active/failed',
  ADD COLUMN StoragePath VARCHAR(512) NULL COMMENT 'MinIO存储路径',

  ADD INDEX idx_is_valid (IsValid),
  ADD INDEX idx_upload_status (UploadStatus);
```

**IsValid 字段说明：**
- `0`（无效）：预创建状态，尚未确认完成。只有新任务启动时才会发现并清理这些残留
- `1`（有效）：已确认上传完成，正常使用

**UploadStatus 枚举值：**
- `pending`：预创建，等待上传
- `uploading`：正在上传中
- `active`：上传完成，已激活
- `failed`：上传失败（回滚后删除）


**Status 枚举值：**
- `initialized`：已预创建，等待上传
- `uploading`：上传中
- `completed`：全部完成
- `cancelled`：已回滚
- `expired`：已过期（定时任务清理）

## 六、错误处理与回滚

### 6.1 各阶段失败处理

| 阶段 | 失败场景 | 处理方式 |
|------|---------|---------|
| upload-init | 目录配置不存在 | 直接返回错误，无需清理 |
| upload-init | DB写入失败 | 直接返回错误，无需清理 |
| upload-file | 单个文件上传失败 | 客户端调用cancel，服务端全量回滚 |
| upload-file | MinIO写入失败 | 同上 |
| upload-confirm | 部分文件未上传 | 返回错误，不改变状态 |
| 页面刷新/关闭 | 任务中断 | 新任务启动时自动清理残留 + 后台定时任务清理 |

### 6.2 回滚规则

**cancel 接口的清理原则：**
1. 只清理本次 taskId 创建的数据，不影响其他用户/任务
2. 文件夹：只删除该任务创建的 IsValid=0 的空文件夹
3. 文件：删除该任务创建的 IsValid=0 的所有文件记录 + MinIO文件
4. 如果文件夹中已有其他有效文件（IsValid=1），保留文件夹不动

### 6.3 残留数据自动清理机制（有效标志）

**问题场景：** 用户上传过程中浏览器崩溃、断网、强制关闭，来不及调用 cancel，数据库和 MinIO 中留下了 IsValid=0 的脏数据。

**解决方案：** 新任务启动时自动清理残留。

```
新任务 upload-init
    |
    v
[检查残留] -- 发现 IsValid=0 的记录？ --是--> [清理残留]
    |                                          |
    | 否                                       | 删除 MinIO 文件
    v                                          | 删除 DB 记录
[继续预处理] <---------------------------------+
    |
    v
[创建新的预处理记录 (IsValid=0)]
```

**清理逻辑（在 upload-init 中执行）：**
```csharp
// 1. 查找该目录下所有 IsValid=0 的文件夹
var orphanFolders = _db.Set<StandardDirectoryFolder>()
    .Where(x => x.DirectoryCode == directoryCode && x.IsValid == false)
    .ToList();

// 2. 删除这些文件夹在 MinIO 中的文件（如果有）
foreach (var folder in orphanFolders)
{
    // 检查是否有文件属于这个文件夹
    var orphanFiles = _db.Set<StandardDirectoryFile>()
        .Where(x => x.FolderCode == folder.FolderCode && x.IsValid == false)
        .ToList();
    
    foreach (var file in orphanFiles)
    {
        // 删除 MinIO 文件
        await _minioService.RemoveObjectAsync(file.StoragePath);
        _db.Set<StandardDirectoryFile>().Remove(file);
    }
    
    // 如果文件夹为空，删除文件夹记录
    if (!_db.Set<StandardDirectoryFile>().Any(x => x.FolderCode == folder.FolderCode))
    {
        _db.Set<StandardDirectoryFolder>().Remove(folder);
    }
}

_db.SaveChanges();
```

**为什么用 IsValid 而不是直接删除？**
1. **安全性**：只有新任务启动时才清理，避免误删正在使用的数据
2. **可追溯**：残留数据保留到下次操作时再清理，方便排查问题
3. **幂等性**：多次调用 upload-init 不会重复清理已清理的数据
4. **兼容性**：不影响现有的 Enable 软删除逻辑

### 6.4 过期清理（后台任务）


## 八、文件对象映射

前端需要维护一个 `本地File对象 <-> 清单relativePath` 的映射关系，因为：

1. 用户选择文件后，File对象存在于内存中
2. upload-init返回的增强清单只有 relativePath，没有File对象
3. 上传时需要根据 relativePath 找到对应的本地File对象

```javascript
// 前端维护的映射
const localFileMap = ref({})  // { relativePath: File对象 }

// 用户选择文件后构建映射
const handleFileSelect = (event) => {
  const files = Array.from(event.target.files)
  for (const file of files) {
    const path = file.webkitRelativePath || file.name
    localFileMap.value[path] = file
    uploadFileList.value.push({ relativePath: path, fileName: file.name, fileSize: file.size })
  }
}

// 上传时查找
const file = localFileMap.value[manifestFile.relativePath]
```

## 九、安全性考虑

1. **TaskId校验**：每次操作都校验TaskId的有效性，防止越权操作
2. **文件类型校验**：upload-init时校验文件类型是否允许上传
3. **文件大小限制**：单文件最大100MB，总大小最大1GB
4. **过期自动清理**：未完成的任务30分钟后自动回滚
5. **并发控制**：同一DirectoryCode同时只允许一个上传任务
6. **有效标志隔离**：预创建数据（IsValid=0）与正式数据（IsValid=1）隔离，新任务启动时自动清理残留

```javascript
if (config) {

    ...config,
    directoryCode: config.DirectoryCode || config.directoryCode
  }
}
```

**现有数据迁移：** 新增 IsValid 字段后，需要将所有现有数据的 IsValid 设为 1（默认有效）：

```sql
UPDATE cert_standard_directory_folder SET IsValid = 1 WHERE IsValid IS NULL;

UPDATE cert_standard_directory_file SET IsValid = 1 WHERE IsValid IS NULL;
```

## 十三、替换场景设计

### 13.1 问题

用户上传的文件可能与已有文件路径重复（同完整路径），此时需要**替换**而非新增。如果不加区分：
- 会产生重复记录
- MinIO 中的旧文件不会被清理（空间浪费）
- 旧文件可能被误清理（如果用 IsValid=0 标记替换状态）

### 13.2 新增字段：FullPath

给 `cert_standard_directory_folder` 和 `cert_standard_directory_file` 各增加 `FullPath VARCHAR(1024)` 字段，存储从根目录到当前节点的完整路径。

**文件夹 FullPath 示例：**
```
4记录文件
4记录文件/内审记录
4记录文件/内审记录/纠正措施
```

**文件 FullPath 示例：**
```
4记录文件/内审记录/陪审人员.doc
4记录文件/管理评审/评审记录.pdf
```

**编码规则不变**，FullPath 仅用于路径判定，不参与编码生成。

### 13.3 判断逻辑（基于完整路径）

**预处理阶段（upload-init）逐文件判定：**

```
对每个待上传文件：
  1. 拼接文件的完整路径 = relativePath（前端直接传入）
  2. 查询 cert_standard_directory_file：
     WHERE DirectoryCode = @directoryCode
       AND FullPath = @fullPath    -- 完整路径精确匹配
       AND IsValid = 1
  3. 如果查到记录 → Mode = "replace"
       记录 ExistingFileId（主键）、ExistingFileCode、OldStoragePath
  4. 如果未查到   → Mode = "create"
```

**对每个待上传文件夹：**
```
  1. 拼接文件夹的完整路径 = folderPath（前端直接传入）
  2. 查询 cert_standard_directory_folder：
     WHERE DirectoryCode = @directoryCode
       AND FullPath = @fullPath
       AND IsValid = 1
  3. 如果查到 → 复用已有文件夹（不创建新记录）
  4. 如果未到 → 新建文件夹
```

**关键：用完整路径判定，不是只看文件名。** 同名但不同路径的文件视为不同文件。

### 13.4 替换模式的核心原则：不建新记录，标记旧记录

**旧方案（有缺陷）：** 替换时创建 `IsValid=0` 的新记录 → cancel 时可能误删旧记录。

**新方案：** 替换时直接标记旧记录的 `UploadStatus = "replacing"`，不创建新记录。

| 操作 | create 模式 | replace 模式 |
|------|------------|-------------|
| init 阶段 | 创建 `IsValid=0, UploadStatus=pending` 新记录 | **不创建新记录**，旧记录 `UploadStatus → replacing` |
| 上传成功 | 无额外 DB 操作 | 无额外 DB 操作（旧记录内容由 confirm 更新） |
| confirm 阶段 | `IsValid=0 → 1` | 用新文件信息**更新旧记录**，`UploadStatus → active` |
| cancel 阶段 | 删除 `IsValid=0` 的新记录 + MinIO 新文件 | **旧记录 `UploadStatus → active`**（恢复原状），删除已上传的 MinIO 新文件 |

**为什么这样更安全：**
- 旧记录从未被删除或标记为无效，cancel 时只需恢复 `UploadStatus`
- 不会产生临时的 `IsValid=0` 新记录，不会被 CleanupOrphanData 误清理
- 旧文件内容只有在 confirm 时才被覆盖，数据丢失风险最小

### 13.5 服务端处理流程

#### upload-init（预处理）

```
1. 校验目录配置
2. 生成 taskId
3. 清理残留数据（IsValid=0 且 TaskId != 当前taskId 的脏数据）

4. 处理文件夹列表（按路径深度排序）：
   对每个文件夹：
     a. 查 DB：FullPath=@fullPath AND DirectoryCode=@dirCode AND IsValid=1
     b. 如果已存在 → 复用，记录 folderMap[path] = existing.FolderCode
     c. 如果不存在 → 新建，IsValid=0, TaskId=当前taskId, FullPath=fullPath
     d. 保存到 enhancedFolders（含 Mode 字段）

5. 处理文件列表：
   对每个文件：
     a. 查 DB：FullPath=@fullPath AND DirectoryCode=@dirCode AND IsValid=1
     b. 如果已存在 → Mode="replace"
          记录 existingFileId, existingFileCode, oldStoragePath
          不创建新记录
     c. 如果不存在 → Mode="create"
          生成 fileCode, storagePath
          创建 IsValid=0, UploadStatus=pending, TaskId=当前taskId 的新记录
     d. 保存到 enhancedFiles（含 Mode, ExistingFileCode, OldStoragePath）

6. 创建 cert_upload_task 记录
7. 返回增强清单
```

#### upload-file-v2（上传单个文件）

```
1. 查找文件记录：
   - create 模式：查 FileCode=@fileCode AND IsValid=0 的记录
   - replace 模式：查 FileCode=@existingFileCode AND IsValid=1 的记录

2. 上传新文件到 MinIO（storagePath）

3. 上传成功后：
   - replace 模式：删除旧 MinIO 对象（oldStoragePath）
   - 更新记录 UploadStatus = "uploaded"

4. 上传失败：
   - 更新记录 UploadStatus = "failed"
```

#### upload-confirm（确认完成）

```
1. 查找 TaskId=@taskId 的所有文件记录

2. 对每条记录：
   - 如果 UploadStatus = "uploaded" 且 IsValid = 0（create 模式）：
       IsValid → 1, UploadStatus → active
   - 如果 UploadStatus = "uploaded" 且 IsValid = 1（replace 模式）：
       更新 FileCode, StoragePath, FileType, FileSize, FullPath
       UploadStatus → active

3. 对每条文件夹记录：
   - IsValid=0 的 → IsValid → 1

4. 任务 Status → completed
```

#### upload-cancel（回滚）

```
1. 查找 TaskId=@taskId 的所有记录

2. create 模式（IsValid=0 的记录）：
   - 删除 MinIO 中已上传的新文件
   - 删除 DB 记录

3. replace 模式（UploadStatus=replacing 的记录）：
   - UploadStatus → active（恢复原状）
   - 删除 MinIO 中已上传的新文件（如有）

4. 删除文件夹 IsValid=0 的记录
5. 删除任务记录
```
