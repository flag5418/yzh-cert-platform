## 第 3 章 P0 · 文档误导治理（本轮最高优先级）

### 3.1 为什么文档治理是 P0（而不是"顺手做掉"）

| 序号 | 危害链条 | 实证 |
|---|---|---|
| 1 | 误导文档 → 后续 AI/开发者读到 → **照做** | 评估报告的 D-1/D-2 结论若被采纳，会对**已 0 违规的 live 库**执行"统一 95 表命名风格 + 软删字段归一"，改动面覆盖 DDL + 73 实体 + 全部 SQL + 前端类型，**风险与收益严重倒挂** |
| 2 | 误导文档 → **错误的"铁律"被写进新文档** → 错误自我复制 | V1 就把"库无法重建"当成事实写进了优化文档。若 V1 也被后续 AI 当权威，会二次污染 |

| 4 | 本项目**已有文档守卫**（`check_docs.mjs`），但**不检查"结论是否与 live 实测一致"** | 只查结构（S1–S6），不查事实。**结构合规 ≠ 内容正确** |

> 相对 V1 大幅收窄。**取消 DB-1（撤回）、保留 DB-2（升为数据层首要）、DB-3/5/6 降级、DB-4/7 降为可选。**

### 4.1 DB-2 列宽不一致（数据层唯一实质问题）

| 语义 | 当前分布 | 问题 |
|---|---|---|
| `Code` | 36×68、50×7、64×3、100×16 | 4 档。`BaseEntity.Code` 声明 `[StringLength(64)]`，**与 36/50/100 全部不符** |
| `CreateBy`/`UpdateBy`/`DeleteBy` | 30×2、50×83、64×9、200×2、**65535×1**（`Sys_RoleAuth`） | 5 档。`65535` 明显误建 |
| `PhaseCode` | 36×8、20×2 | 2 档 |

**危害（按严重度）**：
1. `BaseEntity` 标注 64 是**错的** → 依它生成的 64 位 Code 写入 36 位列，严格模式报错、非严格模式**静默截断** → `Code` 撞车 → 业务键失效。**这是唯一有实际数据损坏路径的一条。**
2. `Code` 宽度不统一 → 跨表关联时 MySQL 隐式转换，索引可能失效
3. `65535` 列使 `Sys_RoleAuth` 单行存储无上限

**方案**：

| 步 | 动作 | 风险 |
|---|---|---|
| a | **先修 `BaseEntity` 标注**：`Code` 的 `[StringLength(64)]` → `[StringLength(36)]`；`*By` 补 `[StringLength(64)]` | 低。改代码不改库，**先让代码说真话** |
| b | 逐表 `SELECT MAX(CHAR_LENGTH(Code))` 验证存量，>36 的先处理数据 | 低 |
| c | `Code` 全部收窄至 36（**只在新表执行；存量表按批次，每批 ≤10 表**） | 中。收窄操作，须备份 |
| d | `*By` 全部放宽至 64（30→64 是放宽，安全）；`Sys_RoleAuth` 65535→64 | 低 |
| e | `PhaseCode` 20→36，或改名 `StageCode`（二选一，登记决策） | 低 |

**验收**：`Code` 全部 36、`*By` 全部 64、`BaseEntity` 标注与库一致；`dotnet test` 166 通过。

### 4.2 DB-5 `verify_naming.sql` 盲区（**分级门禁，不做全量卡口**）

当前只查 2 项，漏 5 项。但**不建议一次性把 7 项全设为卡口**——会一次性暴露 4 类历史偏离，导致门禁长期红、最终被绕过。**分两级**：

| 级别 | 检查项 | 策略 |
|---|---|---|
| **卡口**（新增代码不得违反） | ① 非 PascalCase 列；② Enable 族列（**补 `IsEnabled`/`IsEnabled`/`enable_field`**）；③ 新增表缺 `Code`（**白名单排除 7 张已知表 + 3 张日志表**）；④ 新增表缺 `IsValid`；⑤ 新增表缺 `IsDeleted`（**白名单排除 3 张日志表**） | 立即生效。白名单从规则顶部常量读取，不散落 |
| **基线**（存量偏离，只记录不阻塞） | ⑥ 列宽一致性；⑦ 非 `utf8mb4_general_ci` 列 | 只输出报告，随基线文档更新，**待 DB-2/DB-6 完成后自然归零** |

**必须保留** `verify_naming.sql` 文件头的 `CONVERT(COLUMN_NAME USING utf8mb4) COLLATE utf8mb4_bin` 写法——该文件已详细说明不用它会导致"恒返回 0 行"的假阴性，是本项目最有价值的踩坑记录之一。

### 4.3 其余项（降级，可延后）

| 编号 | 问题 | 重新定位 |
|---|---|---|
| DB-3 | 7 表无 `Code` | **中间表改双关键字会牵动鉴权全链路**，与 `Sys_RoleUser`/`Sys_RoleMenu` 改造同批。**不是紧急项**，登记进基线文档，按业务改动顺带做 |
| DB-6 | `v_workflow.IsActiveName` collation 残留 | 1 列。当前该视图无消费方，未爆。**随下次动该视图时一并修**，不单独立项 |
| DB-4 | 2 张 `z_deprecated_*` 表 | 保留。它们是迁移可回溯的一部分，删了反而破坏回滚能力。**V1 建议删除，撤回** |
| DB-7 | 迁移命名混乱（5 类、序号冲突） | 新脚本按 `scripts/README.md` 规范执行即可；**历史 119 个脚本不重命名**（重命名会破坏已记录的对应关系）。此项 V1 判为"中等"，**降级为低** |
