## 一、总体评价

迁移整体方向正确：复用 `YzhControllerBase` 钩子体系、坚持 PascalCase 契约、`useFileTree` 复合树模式与 ReportDef 对齐。但存在**三类系统性问题**：

1. **响应契约三种并存**（基类 ApiResponse / `{code,msg,data}` / `{code,message,data}`）
2. **实体层脱离架构基类设计**（三种实体写法并存，wf_skill 新表自造列命名规范）
3. **框架层修改缺少文档与测试同步**（违反 §0.1 受控修改双验证要求）

其中 1 个 DB 脚本在 MySQL 8.0 上**必然执行失败**，2 个**安全项**需要立即确认。

## 二、高危问题（正确性 / 安全）

### 🔴 P0-1：`001_skill_tables_V1.sql` 在 MySQL 8.0 上必然失败

```sql
ALTER TABLE `wf_skill_category`
  ADD COLUMN IF NOT EXISTS `is_valid` ...   -- ❌ MariaDB 语法，MySQL 8.0 不支持
```

MySQL 8.0 不支持 `ADD COLUMN IF NOT EXISTS`（MariaDB 特有）。脚本执行到该行直接语法报错。

**建议**：改用存储过程查 `information_schema.COLUMNS` 列存在后再 ADD（`scripts/db/unify_audit_columns_V1_final*.sql` 系列有现成模板），或拆入 Python 迁移脚本（`scripts/db/migrate_*.py` 模式）。

**涉及文件**：`scripts/db/001_skill_tables_V1.sql`

---

### 🔴 P0-2：三个裸 `ControllerBase` 控制器绕过架构基类，鉴权存疑

`ReportDefinitionController`、`StandardDirectoryController`、`FileStorageController` 直接继承 `ControllerBase` 而非 `YzhControllerBase`：

- **失去基类默认 `[YZHAuthorize]`**。若全局认证过滤器未覆盖这些路由，文件下载/删除/上传接口全部未授权暴露。
- 自造响应 `new { code = 200, data }`，与基类 `ApiResponse{success,message,data,code,timestamp}` 冲突 → 项目出现三种响应契约，前端被迫写两套解包逻辑（`res.data` vs `res.data.data`）。
- 错误统一返回 HTTP 200 + body `code=400`，HTTP 状态语义丢失，网关/监控无法感知错误率。

**建议**：
1. 立即确认全局授权过滤器是否覆盖 `api/Workflow/*`、`api/ReportDefinition/*`、`api/FileStorage/*`；
2. CRUD 部分回归 `YzhControllerBase`（钩子扩展）；确需保留的自定义端点（上传/下载）至少补 `[YZHAuthorize]` 并统一 `ApiResponse`。

**涉及文件**：`CertPlatform.Admin/Controllers/Workflow/ReportDefinitionController.cs`、`StandardDirectoryController.cs`、`yzh-core/YZH.Core.Api/Controllers/FileStorageController.cs`

---

### 🔴 P0-3：路径穿越风险需确认

- `StandardDirectoryController.Download([FromQuery] string storagePath)` — 前端传入的存储路径直接交给 `_service.DownloadFileAsync(storagePath)`。若未校验路径前缀白名单（限定 bucket 内 `standard-directory/` 等目录），可构造 `../../` 穿越。
- `ReportDefinitionController.UploadTemplateFile` — `objectName` 拼接了未消毒的 `orgCode/standardCode/phaseCode`，可注入 `../` 污染对象键。

**建议**：对照 `docs/10-YZH架构/` 安全分析文档复核；所有对象键拼接入参做白名单字符校验（仅允许字母数字-_），下载入口校验前缀。

**涉及文件**：`StandardDirectoryController.cs`（Download）、`ReportDefinitionController.cs`（UploadTemplateFile）

---

### 🔴 P0-4：`ValidationRule.json` 缺列 → 后端零校验 + 编辑静默丢字段

EntityConfig 中 `StandardCode` / `PhaseCode` / `OrgCode` 完全未定义。连锁后果：

1. `ValidateEntity` 只校验 `BcFlag && !Yxk` 的列 → 这三个字段**后端零校验**，空值直接打到 DB `NOT NULL` + FK，报裸 400/500（本次会话排查的 400 问题另一半根因）；
2. `UpdateCore` 按 `BcFlag` 列决定可更新字段 → **编辑规则时这三个字段永远不会被更新**（当前场景碰巧无害，属于哑雷）。

**建议**：JSON 中补三列定义（`XsFlag=false, BcFlag=true, Yxk=true`，必填但不显示），或覆盖 `OnCustomValidate` 校验。

**涉及文件**：`yzh-core/YZH.Core.Web/Assets/EntityConfigs/Cert/ValidationRule.json`

---

### 🔴 P0-5：`yzh.vue.core/index.ts` 导出歧义（typecheck 失败）

- `TS2308: Module './utils/treeOps' has already exported a member named 'validate'`
- `TS2308: Module './types' has already exported a member named 'ApiResponse'`

与本次 `index.ts +10 行` 时间点吻合。框架层（受控区）修改必须过 typecheck——当前 `npm run typecheck --workspace=@certplatform/admin` 与 share 均红。

**建议**：显式具名 re-export 消歧（`export { validate as treeValidate }` 方式或收敛导出面）。

**涉及文件**：`src/certplatform-web/yzh.vue.core/src/index.ts`

## 三、架构符合度问题

### 🟡 P1-1：ReportDefinition 迁移不彻底（对照迁移方案 §10）

迁移方案要求"继承 YzhControllerBase，重写 Filter 实现 JOIN"，实际落地为手写 upsert + 手工字段复制（`target.TemplateName = entity.TemplateName; ...` 十余行）：

- **手工复制字段模式脆弱**：`ReportSection` 每加一字段（如本次 `SectionNameEn`）必须同步人肉改 controller 赋值链，漏一行即静默丢数据——本次 `20260915_report_definition_alter.sql` 加列后 controller 又要补一轮，正是该模式的代价；
- upsert 手写：基类 `Insert/Update` + `OnBeforeAdd` 查重钩子本可覆盖；
- 模板/章节两套 CRUD 全手写，放弃了框架约 80% 的既有能力。

**建议**：拆为 `ReportTemplateController`、`ReportSectionController` 两个 `YzhControllerBase`，上传/下载作独立端点挂新控制器；upsert 用 `OnBeforeAdd` 实现同 org+std+phase 查重。

---

### 🟡 P1-2：`ValidationRuleController.OnQueried` 同步阻塞

```csharp
var clauses = _clauseService.GetListAsync(...)
    .GetAwaiter().GetResult();   // ❌ 同步阻塞异步
```

无 SyncContext 环境下通常不死锁，但属反模式；且 JOIN 语义被拆成两次查询。

**建议**：迁移方案 §6 原计划即"覆盖 FilterCore 在 SQL 层 JOIN"；短期至少将 `GetAwaiter().GetResult()` 改为异步管线或条款字典缓存。

---

### 🟡 P1-3：`RuleCode` 自动编号有并发缺陷

```csharp
var seq = (existing.Data?.Count ?? 0) + 1;
entity.RuleCode = $"NC-{entity.StandardCode}-{seq:D3}";
```

- 读-算-写非原子，并发新增撞 `uk_rule_code` 唯一键直接 500；
- `NC-{36位GUID}-001` 可读性极差，违背注释"如 NC-ISO9001-001"的本意。

**建议**：改用 `cert_iso_standard.StandardCode`（如 `ISO13485`）作为编号段；唯一键冲突时重试一次；中期改为每标准一张序列表。

---

### 🟡 P1-4：实体层三种写法并存，wf_skill 表脱离架构设计

| 实体 | 写法 | 问题 |
|------|------|------|
| `ValidationRule` | 继承 + `new` 覆盖全部审计字段（PascalCase） | 与基类重复定义（因表列已是 PascalCase，本可零覆盖） |
| `Skill` / `WfSkillCategory` | 继承 + 蛇形 `SugarColumn` 映射 | **未覆盖基类 `Id`（string Guid）→ 与表 `id bigint auto_increment` 类型冲突**，靠 `InitKeyType.Attribute` 兜底；`creator/create_date/modifier/...` 审计列实体未映射 → 永远 NULL |
| `ReportTemplate` / `ReportSection` | 不继承 BaseEntity | 不享受软删除过滤、审计填充、IsValid 过滤；`GetListAsync(x => x.ReportCode == code)` 可能查出已删除章节（需确认 ORM 全局过滤范围） |

根因：`wf_skill` 新表自造了第四种列命名（蛇形业务列 + PascalCase `IsDeleted` + 蛇形审计列混合）。

**建议**：新表一步到位采用 `cert_*` 已统一的审计规范（PascalCase `CreateBy/CreateTime/...`），实体零覆盖继承基类；`rpt_report_section` 下次迁移对齐；`wf_skill` 出一份列规范化迁移脚本。

---

### 🟡 P1-5：自定义端点未走 `RegisterRowAction` 机制

`toggle-active` / `copy` / `getTree` 手写端点功能正确，但绕过基类行操作注册 → 不自动注入 `/config` 的 `RowButtons.CustomButtons`，前端按钮配置与后端能力脱节（架构 §3.5 核心设计意图）。不阻塞，建议下一迭代统一。

## 四、前端问题

### 🟡 P2-1：nc-config 页面双份表格定义，组件未复用

`logic.ts` 定义了 `tableColumns` / `editFormFields`，`index.vue` 却手写 `el-table` 逐列模板 + 手写 `el-pagination`，两份定义已漂移（后端 `OnQueried` 回填的 `ClauseTitle` 前端未展示）。同迭代的 `job-skill` 用的是 `YzhTable` 标准组件——同一批次两种写法，违反三层同构/组件复用规范。

**建议**：nc-config 切回 `YzhTable + :columns`，删除手写列模板。

---

### 🟡 P2-2：job-skill 字段命名违反 §16 铁律

- `Skill.id?: number` — 铁律要求 TS 属性名 == DB 列名 == C# 属性名；基类 `Id` 是 string，类型也错了；
- `loadData` 过滤字段用蛇形（`Field: 'name'` / `'category_code'`），其他页面全部 PascalCase（`'RuleName'`）；FilterItem→SQL 按属性名解析时蛇形可能**静默失效**（查不到数据也不报错）；
- `getSkillPage(params: any)` 丢失类型。

**建议**：字段全部改 PascalCase；`params` 显式类型。

---

### 🟢 P2-3：小问题清单

- `useFileTree.transformOrgTree` 全程 `any`（`TreeNode` 已定义未用）；复合字符串 ID `"{org}|{std}|{stage}"` 反解 `directoryCode` 脆弱，建议后端直接下发 `directoryCode` 字段；
- `job-skill/index.vue` 技能弹窗未加 `destroy-on-close`（分类弹窗加了），`let formData = reactive(...)` 重新赋值可能与表单内部状态脱钩；
- 条款组树逻辑 `buildClauseTree` 放在 admin 页 `logic.ts`，审核员端将来要用 → 应下沉 `cert-share`；
- nc-config 编辑弹窗打开时 `loadClauseTree` 未防抖/未缓存，同标准重复打开重复拉取。

## 五、性能问题

### 🟡 P3-1：QueueManager 队列列表从 SQL 分页退化为全表内存分页

`GetQueues` 原为 `GetPageAsync`（SQL LIMIT），本次改为 `GetListAsync()` 全捞 + LINQ 内存过滤/分页。`yzh_queue` 高频写入，数据量上万后每次打开队列中心都是全表扫描 + 全量物化。

**建议**：改回 SQL 分页；`executing = pending||running` 组合条件用 `SqlPageOptions.Conditions` 数组下发。

### 🟢 P3-2：`JsonDocument.Parse` 未释放

队列详情解析 payload 时 `JsonDocument` 为 `IDisposable`，循环内多次 parse 不释放。改 `using var doc = ...`。
