## 第一部分：过度设计审查

逐文档排查，识别可裁剪或降级的设计内容。

### 1.1 明确存在过度设计的内容

| 来源 | 设计内容 | 问题 | 建议 | 节省人天 |
|------|---------|------|------|---------|
| **05号** | 6大独立规则引擎（文件完整性、日期逻辑、人员一致性、条款符合性、数值指标、报告生成） | 6个引擎的独立接口+调度器过于重型。MVP 阶段绝大多数规则是简单的 if-else | 合并为**1个规则引擎内核**，6类规则作为该引擎的规则集配置，统一执行 | 8 |
| **03号** | 28条智能校验规则 | 其中约40%是边缘场景（如跨年度日期校验、人员回避冲突），初期数据量小不会触发 | 保留核心 **15 条规则**（覆盖80%常见场景），其余规则集标注"待扩展" | 3 |
| **05号** | Redis + Celery + WebSocket 通知系统 | 单机构3-5人审核团队，并发量极低，不需要消息队列和Redis | 退回到**数据库轮询 + SignalR 推送**，ASP.NET Core 原生支持 | 5 |
| **06号** | ZeroTier 组网 + 本地 ollama 部署 + 云服务器上云架构 | 部署复杂度偏高。但这是用户明确偏好的私有化路线，不应砍 | **保留但简化**：先做单机部署验证，ZeroTier 和上云架构在试点成功后再加 | 3 |
| **13号** | 证据链导出包含离线 HTML 哈希校验工具 | 实用但非 MVP 必需 | 降级到 P1，MVP 阶段仅导出 Excel 证据清单+哈希值 | 2 |
| **11号 P1** | 多标准支持架构预留 | 当前只做 ISO 13485，架构预留不需要现在就实现 | 表设计时字段名通用化即可，无需专门的多标准适配层 | 4 |

**过度设计合计可节省：25 人天**

### 1.2 被质疑但经分析确认不砍的内容

| 设计内容 | 质疑理由 | 保留理由 |
|---------|---------|---------|
| 结构化修改5条路径（10号） | "不就是编辑+保存吗？" | 不同路径触发不同的后续动作（补文件→AI重跑、改判定→审批），合并为通用编辑会丢失关键自动化 |
| 证据溯源面板+文件预览（12号） | "先做结论，溯源后期补" | 没有溯源审核员不敢用 AI 结论，这与 AI 引擎是一体两面，分开了 AI 价值折半 |
| 变更审计日志只追加不删改（09号） | "用操作日志表就行" | 操作日志只能记录动作，不能还原"改了前是什么、改了后是什么、为什么改"，这是 CNAS 评审的核心审查点 |
| 证书管理模块（12号） | "用 Excel 管也行" | 试点机构 ACM 有 10000+ 获证企业，Excel 在 300+ 时就必然遗漏 |

## 第二部分：遗漏补充

### 2.1 13份文档中尚未覆盖的核心遗漏

| 序号 | 遗漏内容 | 为什么重要 | MVP 影响 |
|------|---------|-----------|---------|
| **G1** | **用户与权限管理** | 整个系统没有管理员模块。谁来创建审核员账号？谁分配角色？谁设置审批规则？ | 没有登录系统，所有功能无从谈起 |
| **G2** | **认证机构配置** | 不同机构的 CNAS 编号、证书模板、报告页眉、审批流程可能不同。当前所有设计假设是"一个机构" | 多机构接入时就崩了。MVP 只服务 ACM，但表结构要预留 |
| **G3** | **通知系统** | 09号有审批通知、12号有到期提醒、13号有上传回执，但缺少统一的通知渠道设计 | 各模块各自发通知会导致重复开发和渠道混乱 |
| **G4** | **系统配置与字典管理** | 严重度枚举值（严重/轻微/观察项）、审核类型、证书状态等硬编码在代码里 | 机构可能需要自定义，硬编码改一次要发版 |
| **G5** | **移动端离线支持** | 06号设计了移动端，但没考虑审核员在现场可能无网络 | 拍照/录音/录入发现，没网就废了 |
| **G6** | **数据备份策略** | 审核记录是法律证据，13份文档都没提备份 | 硬盘故障=合规事故 |

### 2.2 补充方案（精简版）

#### G1：用户与权限管理（6 人天）

```
角色模型（MVP 阶段够用）：
├── 超级管理员（机构管理员）：创建账号、分配角色、查看所有项目
├── 审核组长：指派审核组、审批降级/删除、查看管辖项目
├── 审核员：执行审核、录入发现、修改/AI确认
├── 企业管理员：上传文件、查看报告、查看证书
└── 企业查看者：只读查看报告和证书

权限粒度：项目级别（某审核员只能看自己参与的项目）
MVP 不做：字段级权限、数据脱敏
```

#### G2：认证机构配置（2 人天）

```sql
CREATE TABLE agency_config (
    id              UUID PRIMARY KEY,
    agency_name     VARCHAR(200) NOT NULL,
    cnas_no         VARCHAR(50),               -- CNAS 认可号
    report_header   TEXT,                       -- 报告页眉模板
    cert_template   TEXT,                       -- 证书模板
    approval_rules  JSONB DEFAULT '{}',         -- 审批规则（如：降级是否需审批）
    created_at      TIMESTAMP
);
-- MVP：单条记录即可。架构支持多租但前期不用
```

#### G3：通知系统（3 人天）

```
统一通知渠道抽象：

┌────────────────────────────────────┐
│         Notification Service        │
│                                     │
│  ┌─────────┐  ┌─────────┐          │
│  │ 系统内通知│  │ 钉钉通知 │  ...    │
│  │ (WebSocket│  │ (WebHook)│         │
│  │  /SignalR)│  │         │          │
│  └─────────┘  └─────────┘          │
│                                     │
│  通知类型：                          │
│  · 审批请求（组长收到降级审批）        │
│  · 到期提醒（监督审核/证书到期）       │
│  · 任务指派（审核排期通知）           │
│  · 状态变更（NC关闭/证书暂停）         │
└────────────────────────────────────┘
```

MVP 先做系统内通知 + 钉钉（WebHook 对接现有钉钉群机器人），不做邮件/短信。

#### G4：系统字典（1 人天）

一个 `sys_dict` 表解决：
```
dict_type: severity | audit_type | cert_status | finding_status
dict_code: major_nc | initial | active | pending_review
dict_name: 严重不符合 | 初审 | 有效 | 待复核
```

#### G5：移动端离线支持（4 人天）

```
离线模式设计：
  审核员进入企业前 → 同步该项目所有数据到手机本地 SQLite
  现场审核时 → 所有操作写本地 SQLite，拍照存手机相册（临时区）
  回到网络 → 一键同步，文件+数据上传，冲突用"最后写入者胜"
```

#### G6：数据备份（2 人天）

```
定时任务（Hangfire）：每天凌晨2:00 → pg_dump → 压缩 → 存到备份目录
保留策略：最近7天每日备份 + 最近12个月每月一份
恢复演练：首次部署时手动验证一次
```
