# 核心流程穿透评审 —— 基于审核员实际工作场景

> **版本**：V1.0 | **日期**：2026-07-28
>
> **评审方法**：以「一次完整的审核报告生成」为线索，逐环节检查 V2.2 文档是否覆盖了审核员实际工作中的**不可或缺**的步骤。
>
> **评审立场**：
> - 只关注"报告审核和生成"这个核心目标
> - 区分「必须有的」vs「有了更好的」vs「可以没有的」
> - 基于认证行业（ISO 9001/14001/45001）审核员的日常工作

---

## 一、审核员实际工作流程（行业视角）

### 1.1 完整的一次审核（以 ISO 9001 初审 Stage 2 为例）

```
第0天：审核前准备
  │
  │  审核员收到任务 → 了解企业基本情况 → 准备检查表
  │
第1-3天：现场审核（或文件审核）
  │
  │  Day 1: 首次会议 → 现场巡视 → 查阅文件记录 → 开具 NC
  │  Day 2: 继续各部门审核 → 收集证据 → 内部组内讨论
  │  Day 3: 补充审核 → 与企业确认 NC → 末次会议
  │
第4-7天：编写报告
  │
  │  整理检查表 → 汇总 NC → 撰写审核报告 → 报告复核
  │
第8-14天：报告审批与发放
  │
  │  技术负责人审批 → 发放给企业 → 企业确认 → 归档
  │
后续（如需要）：
  │
  │  企业整改 → 提交证据 → 审核员验证 → 关闭 NC
```

### 1.2 核心问题：我们的系统要替代哪些环节？

| 环节 | 当前方式（痛点） | 我们的目标 |
|------|------------------|-----------|
| **资料收集** | 企业微信/邮件发文件，散落各处 | 统一上传到系统 |
| **文件审查** | 人工翻阅每份文件，逐项对照检查表 | **自动提取 + 自动判定 + 复核** |
| **NC 开具** | 手动写 NC，措辞不规范 | AI 辅助生成标准 NC 文本 |
| **报告编写** | 从零开始写 Word，复制粘贴检查表结果 | **一键生成初稿 + 编辑** |
| **整改跟踪** | 微信催促，证据散乱 | 在线提交 + 验证 |

## 二、端到端穿透评审

### 环节 ①：企业建立与资料收集

#### 审核员实际做什么：

```
1. 接到一个新的审核任务（机构指派）
2. 联系企业，告知需要准备的资料清单
3. 企业通过微信/邮箱发送资料
4. 审核员收到后逐一打开查看
5. 发现问题（文件打不开、模糊、缺页）→ 退回让企业重新发
6. 所有资料收齐后，开始正式审核
```

**⚠️ 讨论 1：「资料清单通知」是否为核心？**

- **场景 A**：审核员当面告诉企业"你需要准备这些文件" → 不需要系统通知
- **场景 B**：审核员在系统中生成一份资料清单 → 打印/导出 PDF → 发给企业 → **Phase 1 可不做在线通知**

**判断**：**不是 Phase 1 核心**。审核员可以用 §3.2 定义的目录结构手动告知企业。Phase 2 再做自动通知。

### 环节 ②：文件内容审查（核心中的核心）

#### 审核员实际做什么：

```
对每一份文件：
  1. 打开文件（Word/PDF/Excel）
  2. 找到关键信息（日期、结论、签名等）
  3. 判断是否符合要求
     - 日期是否在有效期内？
     - 内容是否完整？
     - 是否有必要的签字/盖章？
     - 与其他文件是否一致？（如管理评审参与人员 vs 组织架构图）
  4. 记录判定结果（符合/不符合/不适用）
  5. 如有问题 → 记录问题描述 → 可能开 NC
```

**这是审核员耗时最长的环节（约占 60% 的审核时间）。**

#### V2.2 文档覆盖情况：

| 子环节 | 文档是否覆盖 | 对应章节 | 评价 |
|--------|:----------:|---------|------|
| 打开并识别文件类型 | ✅ | §2.4 预审步骤0a | 格式合规检查 |
| 提取关键信息（字段） | ✅✅ | §2.4 步骤3 Skill 字段提取 + §3.4 Skill 管理 | **核心能力** |
| 判断日期有效性 | ✅ | §3.5 数值比较规则 | 如管理评审日期是否过期 |
| 判断内容完整性 | ✅ | §3.5 必填校验规则 | 字段是否为空 |
| 判断格式合规性 | ✅ | §3.5 格式校验规则 | 文件格式是否符合要求 |
| **跨文件一致性判断** | ✅ | §3.5 一致性判断规则（AI） | 如人员名单一致性 |
| **语义级判断** | ✅ | §3.5 语义判断规则（AI） | 如适用范围匹配度 |
| 记录判定结果 | ✅ | §2.6 审计复核页 | 通过/待复核/不通过 |

| 问题标记 / 开 NC | ✅ | §2.6 一键标记 NC + §2.8 NC 管理 | NC 全流程 |

#### 🟢 结论：此环节**覆盖完整且质量高**。

这是整个文档设计最扎实的部分。Skill 提取 + 规则引擎 + 位置溯源 + 增量审核形成了完整的闭环。

**唯一需要注意的点**：

> **§1.2 企业资料分层模型**是这一切的基础。如果「标准文件目录定义」（§3.2）不准确或不完整，整个自动审核就是空谈。

**🔴 关键依赖**：必须在开发前完成 ISO 9001 的标准文件目录定义和字段清单（文档 §六 开发优先级第 1 项已正确识别这一点）。

### 环节 ③：NC（不符合项）管理与整改跟踪

#### 审核员实际做什么：

```
发现问题时：
  1. 明确违反了哪条标准条款（如 ISO 9001 第 7.2 条）
  2. 描述不符合事实（用专业术语）
  3. 判定严重程度（Major / Minor / Observation）
  4. 告知企业 → 企业制定纠正措施 → 整改 → 提交证据
  5. 审核员验证整改效果 → 通过则关闭 NC → 不通过则退回重改
```

#### 🟡 结论：主体流程完整，但**验证环节需要补充细节**。

**⚠️ 讨论 2：NC 验证流程的细节是否需要在 Phase 1 定义？**

**我的判断：需要，但不需要复杂。**

理由：
- NC 整改跟踪是认证行业的**强制性要求**（ISO 17021 明确规定）
- 如果没有验证环节，NC 就只是"开了但没关闭"，不符合规范
- 但 Phase 1 可以简化为：**企业提交证据 → 审核员看一眼 → 点通过/退回**

**建议补充的最小化设计**（直接加入 V2.2 即可）：

```markdown
### NC 验证最小化流程（Phase 1）

1. 企业在 NC 详情页点击「提交整改」
   - 填写纠正描述（文字）
   - 上传整改证据（文件）
   - 提交后 NC 状态变为「待验证」

2. 审核员收到提示（NC 列表中该 NC 显示「待验证」标签）

3. 审核员点击进入 NC 详情
   - 查看原始 NC 内容
   - 查看企业提交的整改描述和证据
   - 操作：【通过】或【退回】

4. 点击【通过】→ NC 状态变为「已关闭」
   点击【退回】→ NC 状态回到「整改中」，需填写退回原因

这就是全部。不需要到期提醒、不需要升级机制、不需要通知推送。
NC 列表的筛选器增加「待验证」选项即可。
```

### 环节 ④：报告生成与编辑

#### 审核员实际做什么：

```
1. 汇总所有检查表的判定结果
2. 汇总所有 NC（编号、条款、描述、严重度）
3. 撰写审核概况（审核依据、范围、日期、组成员）
4. 撰写审核发现（逐条描述）
5. 给出审核结论（推荐认证/不推荐/暂缓决定）
6. 附上审核计划、检查表、NC 清单等附件
7. 自我复核 → 提交技术负责人审批
8. 审批通过后 → 发放给企业 → 归档
```

**报告编写通常需要 1-3 天（取决于 NC 数量和审核复杂度）。**

**⚠️ 讨论 3：报告审批和发放是否是 Phase 1 核心？**

**我的判断：取决于使用场景。**

| 场景 | 是否需要审批 | 说明 |
|------|:-----------:|------|
| **单人审核员独立使用** | ❌ 不需要 | 自己写的报告自己负责，跳过审批 |
| **小团队（2-3 人）** | ⚠️ 可选 | 组长简单看一下即可 |
| **正规认证机构** | ✅ 需要 | 技术负责人/主任审核员签字批准 |

**建议**：

```
Phase 1 最小化状态机：
  草稿 → 已发布

  · 草稿：可编辑、可 AI 增强、可预览
  · 已发布：只读、可下载、可归档
  · 「发布」操作 = 审核员确认"这份报告完成了"
  · 已发布的报告不可编辑，如需修改则创建新版本

Phase 2 再扩展：
  草稿 → 待审批 → 已发布 → 已归档
  增加「审批人」角色和审批操作
```

**关于「发放给企业」**：

- Phase 1：企业端登录后可直接查看已发布报告（§五已有此功能）
- 不需要额外的"发放"动作——**发布即对企业可见**
- Phase 2 可增加「主动通知」（邮件/短信告知企业有新报告）

## 三、「部门/审核范围」是否为核心？

### 审核员实际怎么做：

```
审核前会拿到《审核计划》，其中明确：
  - 本次审核涉及哪些部门
  - 每个部门分配多少时间
  - 重点审核哪些过程/条款
```

### 我的判断：**不是 Phase 1 核心，但是重要的上下文信息**

**理由**：

1. 您的核心模式是「文件上传 → 自动审核 → 生成报告」
2. 这个模式下，**审核范围由上传的文件隐含决定**（企业传了哪些部门的资料，就审核哪些）
3. 「部门」更多是**元数据/标签**，不影响核心审核流程
4. 但它对**报告生成**有用（报告中要写"本次审核覆盖了生产部、质检部..."）

**建议**：

```
Phase 1 最小化方案：
  · 审计任务中仅保留一个「审核说明」文本字段（自由输入）
  · 审核员可填写："本次审核覆盖生产部、质检部，重点检查第7-8章"
  · 该字段仅在报告中作为参考信息展示，不参与规则执行

Phase 2 完善：
  · 增加部门字典 + 多选
  · 增加审核范围（条款范围选择）
  · 用于更精细的报告生成和统计分析
```

## 四、「通知系统」是否为核心？

### 我的判断：❌ **绝对不是 Phase 1 核心**

**理由**：

1. **审核员的工作模式是主动的** — 他打开系统就能看到所有待办
2. **NC 待验证** — 审核员看 NC 列表，筛选「待验证」即可
3. **企业提交了整改** — 审核员下次登录时能看到状态变化
4. **报告已发布** — 企业下次登录时能看到新报告

**Phase 1 的替代方案**：

```
· 登录后首页显示「待办摘要」：
  - 您有 2 个 NC 待验证
  - 企业 XX 刚提交了整改证据
  - 报告 RT-2026-001 还是草稿状态

· 这就够了。不需要实时推送、不需要邮件、不需要短信。
```

**Phase 2 再考虑**：SignalR 实时推送 + 邮件通知。

## 六、关于「标准文件目录定义」的特殊说明

这是整个系统的**阿喀琉斯之踵**（唯一致命弱点）。

### 为什么如此关键？

```
标准文件目录定义不准确 → Skill 提取的字段不对 → 规则校验的依据错了 → 审核结果不可信 → 整个系统失去价值
```

### 它包含什么？

以 ISO 9001 初审为例，需要明确定义：

```
1. 企业基础资料需要哪些文件？
   - 每个文件的必填字段是什么？
   - 每个字段的数据类型？
   - 每个字段用什么 Skill 提取？

2. 每个阶段的阶段资料需要哪些文件？
   - 同上

3. 每个字段关联哪些校验规则？
   - 纯逻辑规则（日期比较、非空检查）
   - AI 规则（语义判断）
```

### 谁来完成？

**必须是懂 ISO 9001 审核的行业专家**（您的顾问朋友），而不是技术人员。

技术人员能做的是：
- 提供「标准文件目录定义」的配置界面（§3.2）
- 实现 Skill 和规则引擎
- 但**填什么内容**必须由专家来

### 建议

```
在正式开发前，先产出一份《ISO 9001 标准文件目录定义 v0.1》
  · 由您和朋友（行业专家）共同完成
  · 格式：Excel 或 Markdown 表格
  · 内容：文件清单 + 字段清单 + 校验规则描述（自然语言）
  · 用这份文档验证整个设计是否合理
  · 确认无误后再进入开发
```
