# 结构化修改流程与审核质量追溯体系
> 日期：2026-07-27

## 一、从"自由编辑"到"结构化操作"

09号文档中的"修改"是一个笼统的按钮，但审核员面临的具体场景各不相同。不同场景的后续动作完全不同——缺文件应该引导上传、文件名错应该引导重命名、判定错误应该引导修正后让 AI 重新跑一遍。

### 1.1 五条结构化修改路径

```
                    审核员发现问题
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
   [信息类问题]      [文件类问题]      [判定类问题]
         │                │                │
    ┌────┴────┐     ┌─────┴─────┐     ┌────┴────┐
    ▼         ▼     ▼           ▼     ▼         ▼
 证据描述   条款   缺文件     文件名/   严重度    发现本身
 不准确    匹配            格式错误   判定错误   应增/删
    │         │     │           │     │         │
    ▼         ▼     ▼           ▼     ▼         ▼
  路径A     路径B  路径C       路径D  路径E     路径E
```

---

### 1.2 路径 A：证据描述修正（纯文本编辑）

**场景**：AI 提取的证据描述措辞不准确但信息正确，审核员修正措辞。

```
操作流程：
  [✎ 编辑证据描述]
       │
       ▼
  内联编辑器打开，审核员直接修改文本
       │
       ▼
  保存 → 自动记录变更（old_text / new_text）
       │
       ▼
  状态标记：[文本已修正]
```

**约束**：不需要理由（属于文字润色性质），不触发审批，不计入"判定变更"统计。

---

### 1.3 路径 B：条款重新匹配

**场景**：AI 把某发现匹配到 7.4.3，但审核员认为应该匹配到 7.4.1。

```
操作流程：
  [✎ 修改条款]
       │
       ▼
  弹出条款选择器（按标准展示条款树）
       │
       ▼
  ┌─────────────────────────────────────┐
  │ 条款匹配修正                          │
  │                                     │
  │ 原条款：ISO 9001:2015 / 7.4.3       │
  │        "外部供方的信息"              │
  │                                     │
  │ 新条款：[7.4.1 采购过程  ▼]          │
  │                                     │
  │ 修正理由 *：                        │
  │ ┌───────────────────────────────┐   │
  │ │ 此发现涉及供应商评价流程缺失，    │   │
  │ │ 属于采购过程管理而非供应商信息    │   │
  │ │ 传递问题                        │   │
  │ └───────────────────────────────┘   │
  │                                     │
  │ [取消]   [确认并更新AI证据引用]      │
  └─────────────────────────────────────┘
       │
       ▼
  确认后 → 条款更新 + 理由写入变更日志
```

**约束**：必须填理由。不需要 AI 重新跑（条款是审核员的专业判断，非 AI 可替代）。

---

### 1.4 路径 C：缺文件——上传后 AI 重新分析（关键路径）

**场景**：AI 判定"缺少内部审核报告"，但企业实际上传了，只是文件命名混乱导致 AI 未识别，或审核员事后补充收集到。

```
操作流程：
  [📎 补充文件]
       │
       ▼
  文件上传器（支持 PDF / DOCX / XLSX / 图片）
       │
       ▼
  ┌─────────────────────────────────────┐
  │ 补充文件                              │
  │                                     │
  │ 关联发现：#03 缺少内部审核报告         │
  │                                     │
  │ 已上传文件：                          │
  │ ✅ 2024年内审报告.pdf (1.2MB)         │
  │ [+] 继续添加                          │
  │                                     │
  │ 补充说明（选填）：                    │
  │ ┌───────────────────────────────┐   │
  │ │ 企业内审报告命名不规范，         │   │
  │ │ AI未自动识别                    │   │
  │ └───────────────────────────────┘   │
  │                                     │
  │ 上传后将自动：[重新AI分析此发现]      │
  │                                     │
  │ [取消]   [上传并重新分析]             │
  └─────────────────────────────────────┘
       │
       ▼
  系统执行：
    1. 文件存入该审核项目的证据库
    2. 将该文件 + 原AI发现上下文重新提交给AI分析
    3. AI返回更新后的判定（可能从"严重不符合"→"符合"或"不适用"）
       │
       ├─ AI 判定变更为"符合" → 自动更新严重度 + 证据描述
       │    变更日志：{action: "rejudge", reason: "补充了内审报告文件"}
       │
       └─ AI 判定仍为"不符合" → 保留原判定
            但证据描述更新为："已查阅2024年内审报告.pdf，但报告缺少..."
```

**约束**：补充文件是真实的证据补全，AI 重新分析的结果仍可被人再次复核。整个过程记录：上传了什么文件 + AI 新判定 + 最终人工确认。

---

### 1.5 路径 D：文件名/格式修正——修正后 AI 重新读取

**场景**：文件实际存在，但文件名写错了、或文件损坏/格式异常导致 AI 无法解析。

```
操作流程：
  [🔄 修正文件并重新读取]
       │
       ▼
  ┌─────────────────────────────────────┐
  │ 修正文件引用                          │
  │                                     │
  │ 发现 #05：管理手册无法解析             │
  │                                     │
  │ ○ 文件名错误 → [修正文件名]           │
  │   当前引用：管理手册.doc               │
  │   修正为：  [质量管理手册V3.2.doc  ]   │
  │                                     │
  │ ○ 格式异常 → [替换正确文件]           │
  │   当前文件：[选择替换文件]             │
  │                                     │
  │ ○ 文件损坏 → [要求企业重新提供]        │
  │   → 生成待办通知                     │
  │                                     │
  │ 修正后将重新提取文件内容并更新证据      │
  │                                     │
  │ [取消]   [修正并重新分析]              │
  └─────────────────────────────────────┘
       │
       ▼
  系统执行：
    1. 更新文件引用（新文件名/新路径）
    2. 对该文件重新OCR/文本提取
    3. AI 基于新提取内容更新证据描述
    4. 记录变更：{action: "file_corrected", old_ref: "...", new_ref: "..."}
```

**与路径 C 的区别**：路径 C 是"之前根本没有这个文件，现在补上"；路径 D 是"文件本来就在，只是引用错了或解析失败"。路径 D 不需要人工重新写证据，AI 自动重新提取即可。

---

### 1.6 路径 E：判定变更——人工修正严重度/增删发现

**场景**：审核员认为 AI 的严重度判定错误，或需要新增/删除一条发现。这是最需要合规约束的路径。

```
操作流程：

  [修正严重度]                        [新增发现]                    [删除发现]
       │                                  │                             │
       ▼                                  ▼                             ▼
  ┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
  │严重度修正         │          │手动新增审核发现    │          │删除AI审核发现      │
  │                  │          │                  │          │                  │
  │原判定：严重不符合  │          │条款：[选择条款 ▼] │          │⚠️ 此操作不可恢复   │
  │新判定：[轻微不符 ▼│          │                  │          │                  │
  │                  │          │证据描述：         │          │删除后该发现将标记   │
  │理由 *：          │          │┌──────────────┐  │          │为"已作废"，保留在   │
  │┌──────────────┐  │          ││              │  │          │审计日志中          │
  ││              │  │          ││              │  │          │                  │
  │└──────────────┘  │          │└──────────────┘  │          │理由 *：           │
  │                  │          │                  │          │┌──────────────┐   │
  │[降级需组长审批]   │          │来源：人工补充     │          ││              │   │
  │                  │          │                  │          │└──────────────┘   │
  │[取消] [确认]     │          │[取消] [保存]     │          │                  │
  └──────────────────┘          └──────────────────┘          │[取消] [申请删除]  │
                                                               └──────────────────┘
```

**审批触发条件**：

| 操作 | 审批要求 |
|------|---------|
| 严重 → 轻微 | 填理由即可，无需审批 |
| 严重 → 观察项（跳级） | **组长审批** |
| 轻微 → 严重（升级） | 填理由即可（从严判定不需要审批） |
| 删除发现 | **组长审批** |
| 手动新增发现 | 无需审批 |

### 1.7 五条路径完整对比

| | 路径A | 路径B | 路径C | 路径D | 路径E |
|---|---|---|---|---|---|
| 操作名 | 修正证据描述 | 修正条款 | 补充文件 | 修正文件引用 | 变更判定 |
| 触发词 | 编辑文本 | 改条款 | 缺文件/补文件 | 文件名错/打不开 | 改严重/增删 |
| 是否重新跑AI | 否 | 否 | **是** | **是** | 否 |
| 必填理由 | 否 | 是 | 建议 | 建议 | 是 |
| 触发审批 | 否 | 否 | 否 | 否 | 降级/删除时是 |
| 产出物 | 润色后文本 | 正确条款 | 更新后证据+判定 | 更新后证据 | 最终判定 |

### 1.8 UI 总入口：发现操作栏

每条 AI 发现的操作栏，把模糊的"修改"拆成明确按钮：

```
[✓ 确认]  [✎ 编辑证据]  [🏷 修改条款]  [📎 补文件]  [🔄 修文件]  [⚠ 改判定]  [✕ 删除]
   路径A默认     路径A          路径B        路径C       路径D        路径E       路径E
```

审核员不需要理解这五条路径——点哪个按钮就走哪条流程，系统引导完成。

## 二、文件证据库

路径 C 和 D 都涉及文件操作，需要一个统一的文件证据库来管理。

### 2.1 设计原则

- 每个审核项目对应一个独立的证据库目录
- 企业原始提交的文件 = 原始证据区（只读，不可修改）
- 审核员补充/更换的文件 = 补充证据区
- 系统自动建立"发现→文件"的引用关系

### 2.2 数据结构

```
审核项目 PRJ-2026-089
├── 原始证据/               （企业提交，只读）
│   ├── 质量手册.pdf
│   ├── 内审报告_2024.docx
│   └── 程序文件/
│       ├── 文件控制程序.doc
│       └── 采购控制程序.doc
│
├── 补充证据/               （审核员添加）
│   ├── 补充_内审签到表.pdf      ← 关联发现 #03
│   └── 修正_内审报告_完整版.pdf  ← 关联发现 #03
│
└── evidence_map.json       （文件→发现映射关系）
    {
      "内审报告_2024.docx": ["F-2026-003"],
      "补充_内审签到表.pdf": ["F-2026-003"]
    }
```

## 三、审核质量追溯模块——"事后被通报，如何回溯？"

这是审核行业最敏感但最真实的需求。一家企业拿了 ISO 证书后，如果在药监局飞检、客户投诉、安全事故中被查出体系问题，监管方一定会追溯："谁审的？怎么审的？审核报告怎么写的？"

CNAS 有明确规定——认证机构必须建立申投诉处理和追溯机制。系统如果不支持，审核机构不敢用。

### 3.1 典型追溯场景

```
时间线：
2026-03 → AI辅助完成审核，出具证书
2026-07 → 药监局飞检发现严重体系缺陷
       → 通报批评，追溯审核责任
       →
         ┌──────────────────────────┐
         │ 认证机构需要回答：          │
         │ 1. 当时是谁审的？           │
         │ 2. 这个条款当时有没有审到？  │
         │ 3. 如果审到了，为什么判符合？ │
         │ 4. 如果没审到，为什么遗漏？  │
         │ 5. AI 当时的判断是什么？     │
         │ 6. 审核员有没有手动改过？    │
         │ 7. 改的依据是什么？         │
         └──────────────────────────┘
```

### 3.2 模块设计：质量事件追溯

#### 事件登记

当企业被通报或出现质量事故，认证机构在系统中登记质量事件：

```

│                                             │

│                                             │
│ 事件类型：[监管通报 ▼]                       │
│          - 监管通报（药监局/市监局）           │
```

#### 自动追溯分析

登记事件后，系统自动回溯原始审核记录：

```
追溯分析报告
═══════════════════════════════════════════════

事件：QE-2026-015 | 河北药监局飞检通报
涉及条款：ISO 13485:2016 / 7.5 生产和服务提供
          ISO 13485:2016 / 8.2.6 产品监视和测量

── 追溯发现 ──────────────────────────────────

【7.5 生产和服务提供】
  审核记录：存在（发现 #F-2026-012）
  AI 原始判定：轻微不符合
  审核员操作：[张三] 于 2026-03-15 将严重度从 "轻微不符合" 
              降级为 "观察项"
  降级理由："企业有基本的生产过程控制文件，仅缺少洁净车间
             环境监测的日检记录，不属于系统性缺失"
  结果：该发现以"观察项"写入终版报告，未构成不符合项。

【8.2.6 产品监视和测量】
  审核记录：存在（发现 #F-2026-028）
  AI 原始判定：符合
  审核员操作：直接确认，未修改
  结果：该条款以"符合"写入终版报告。

── 结论 ──────────────────────────────────────

7.5 条款：AI 已识别风险（轻微不符合），但审核员降级为观察项。
         飞检结果与该降级决定存在关联，需复核该降级是否合理。
         
8.2.6 条款：AI 和审核员均判为符合，飞检在此条款发现问题。
           建议复核 AI 当时引用的证据是否全面、是否存在
           关键文件遗漏。

── 建议 ──────────────────────────────────────
1. 复核 F-2026-012 的降级决策是否合规
2. 检查 F-2026-028 当时的证据文件完整性
3. 导出完整审核记录 + 变更日志，准备向 CNAS 说明
```

#### 追溯报告导出

导出的追溯报告包含：
- 原始审核报告（终版）
- 每个相关发现的完整变更历史
- AI 原始判定 vs 人工最终判定对比
- 审核员操作时间线
- 审批记录
- 结论与改进建议

### 3.3 数据模型

```sql
-- 质量事件表
CREATE TABLE quality_events (
    id              UUID PRIMARY KEY,
    event_no        VARCHAR(20) NOT NULL,       -- QE-2026-015
    enterprise_id   UUID NOT NULL,
    project_id      UUID NOT NULL,              -- 关联审核项目
    event_type      VARCHAR(30) NOT NULL,       -- regulatory_report / complaint / accident / recall / audit_failure
    severity        VARCHAR(20) NOT NULL,       -- critical / major / minor
    event_date      DATE NOT NULL,
    description     TEXT NOT NULL,
    attachment_paths TEXT[],                     -- 通报文件等
    status          VARCHAR(20) DEFAULT 'open',  -- open / investigating / closed
    
    created_at      TIMESTAMP NOT NULL,
    created_by      VARCHAR(50) NOT NULL,
    closed_at       TIMESTAMP,
    conclusion      TEXT
);

-- 追溯分析结果
CREATE TABLE traceability_results (
    id              UUID PRIMARY KEY,
    event_id        UUID NOT NULL REFERENCES quality_events(id),
    finding_id      UUID NOT NULL REFERENCES audit_findings(id),
    
    clause          VARCHAR(100) NOT NULL,
    ai_original_severity   VARCHAR(20),         -- AI原始判定
    final_severity         VARCHAR(20),         -- 最终判定
    human_intervened       BOOLEAN,             -- 是否有人工干预
    change_summary         TEXT,                -- 干预摘要
    risk_level             VARCHAR(20),         -- 关联风险等级
    
    analysis_notes  TEXT                         -- 追溯分析备注
);
```

### 3.4 对 AI 模型的反哺闭环

追溯事件应该反哺给 AI 模型优化——这是系统持续进化的核心数据源：

```
质量事件 → 追溯分析 → 判定出问题了 →
                                    │
          ┌─────────────────────────┘
          ▼
   判定失误类型分类：
   ├─ AI判定过严，审核员降级后出问题 → 复审降级标准
   ├─ AI判定过松，审核员确认后出问题 → 该条款置信度阈值调整
   ├─ AI遗漏，审核员未补充 → 该类型证据的识别算法优化
   └─ 证据覆盖不全 → 该条款的证据清单扩充
          │
          ▼
   输入到规则库/模型 → 下次相似场景更准确
```

这形成了一条完整闭环：

```
审核 → 出证 → 事后监管通报 → 追溯分析 → 改进模型 → 下次审得更准
```
