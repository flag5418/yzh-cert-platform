## 二、文档合并方案（80-功能设计）

### 2.1 合并方向：README.md 为唯一权威入口（用户定调）

**核心原则（用户反馈第 1 点）**：每个文件夹下都应有一个 README.md，记录：该文件夹存放什么文件、每个文件的作用、该文件夹内容应如何组织等核心信息。避免不同 AI 按各自规则编写导致格式混乱、内容不全。

**动作**：
1. **README.md 升级为权威入口**：吸收 index.md 全部独有内容（功能总览表 23 份完整版、编写约束 10 条、11 章文档模板、目录分组树、变更记录），保留自身独有内容（关键词索引、依赖关系），并按规范模板重排章节。
2. **index.md 归档**：内容并入 README.md 后，index.md 移入 `docs/历史文档/`（不物理删除，遵循项目"禁止删除旧文档"规则）。
3. **同步引用**：项目全局规则.md:170、LogicFlow工作流设计器实施分析与建议-V1.md:676 两处引用 index.md → 改 README.md。

### 2.2 目录 README 标准模板（新规范，写入 README.md 附录）

每个文件夹的 README.md 统一采用以下结构，防止多 AI 编写格式混乱：

```markdown
# 目录名

## 作用
（该文件夹在整个项目中的定位，一句话）

## 文件清单
| 文件 | 作用 | 状态 |
|------|------|------|

## 组织规则
（该文件夹内容应如何组织/命名/归档）

## 依赖关系
（依赖哪些文档/目录，被谁引用）

## 维护约定
（新增/修改文件的流程要求）
```

此模板定义写入 80-功能设计/README.md 附录，作为全项目目录 README 的编写规范基准。

### 3.2 就近原则（用户反馈第 5 点，核心新规）

**原则**：脚本与运行文件分两级存储——
- **全局/工具性脚本** → `scripts/` 按用途分子目录；
- **功能性脚本（含测试）** → 与所属功能文档同目录，就近存放，专设 `test/` 子目录存放脚本与 .sh 执行文件。

**收益**：打开功能文档 → 同目录即见对应 test/ 脚本，无需跨多层目录往返；脚本报错时同样就近检查功能文档。

**落地**：
- test_ai_* 5 个一次性验证脚本：**直接删除**（无引用、无保留价值）；
- 删除行为在 80-功能设计/README.md 变更记录中注明；
- 就近原则作为规范写入 80-功能设计/README.md（组织规则节）与 scripts/README.md（存放规范节）；
- 未来功能设计涉及测试脚本时，一律在功能目录下创建 test/ 子目录（如 `80-功能设计/01-系统管理/xxx功能/test/`），脚本命名 `test_功能名.sh/py`。

### 3.3 scripts/README.md 内容规划（详细编写，用户反馈第 3 点）

1. **存放规范**：全局/工具性脚本统一入 scripts/，按用途分子目录；功能性脚本就近存放（见 3.2）；禁止再向根目录散落脚本。
2. **脚本作用表**：逐一列出 scripts/ 下所有脚本（16 个），含所属子目录、功能、用法示例。
3. **编写规范**：
   - .sh 命名 kebab-case（如 run-backend.sh）；.py 命名 snake_case（如 run_db_migration.py）；
   - 脚本须自定位路径（`SCRIPT_DIR` / `PROJECT_DIR`），禁止依赖 cwd；
   - 脚本头部须写注释：作用 / 用法 / 依赖 / 维护人；
   - 新增脚本须同步更新本 README；
   - 版本后缀（V2/V3）仅在确有必要时使用，语义化。
4. **BASH_README.md 内容并入**（原根目录 BASH_README.md 仅描述 3 个后端脚本，并入 backend/ 章节后原文件移入 docs/历史文档/）。

### 3.4 docker/README.md 内容规划（用户反馈第 4 点）

保持 4 脚本原地（与 docker-compose.yml 强绑定），新增 README.md 说明：
