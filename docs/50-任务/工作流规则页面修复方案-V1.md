### F4　补齐 `ISoftDelete` / `IIsValid`（P1-4 + D1 + D2）

**根因**：`ValidationRule : BaseEntity` —— `BaseEntity` **不含** `IsDeleted`/`IsValid`，而 DB 两列都在、其余 **8/9 张配置表**都实现 `IIsValid`（`EnableField` 统计：`IsValid` × 8、`IsActive` × **1**，本表是唯一异类）。

**照抄孪生表 `ReportSection`**（它已修好同一问题，注释写明「旧表用 `IsActive` 违反铁律九 → 现统一 `IsValid`」）：
```csharp
public class ValidationRule : BaseEntity, ISoftDelete, IIsValid
{
    // …业务字段…

    /// <summary>有效标志（1=有效，0=无效）—— 铁律九唯一启用字段</summary>
    public int IsValid { get; set; } = 1;

    // ──── ISoftDelete 接口显式实现 ────
    public bool IsDeleted { get; set; }
    public string? DeleteBy { get; set; }
    public DateTime? DeleteTime { get; set; }

    // ❌ 删除 public bool IsActive（由 IsValid 取代）
}
```

**配套 5 处（缺一即产生「列表显示的行 ≠ 能操作的行」）**

| # | 位置 | 改动 |
|---|---|---|
| a | [ValidationRule.json:4](src/certplatform-api/CertPlatform.Admin/Assets/EntityConfigs/Cert/ValidationRule.json#L4) | `"EnableField": "IsValid"`（对齐另外 8 张表） |
| b | 同上配置的列/表单项 | `IsActive` → `IsValid`（`DesName: 启用`，`Type: Switch` + `active-value: 1` / `inactive-value: 0`） |
| c | [nc-config/index.vue](src/certplatform-web/cert/cert-admin/src/pages/workflow/nc-config/index.vue) 工具栏 | **补「显示已禁用」`el-switch`**（`logic.toggleShowDisabled()`）——后端 `OnBuildingFilter` 会自动追加 `IsValid=1`，仅 `ShowDisabled=true` 才放行；**少了这个开关，禁用即不可逆**。照抄 [cert-stage/index.vue:50-60](src/certplatform-web/cert/cert-admin/src/pages/foundation/cert-stage/index.vue#L50-L60) |
| d | 同上状态列插槽 | `#column-IsActive` → `#column-IsValid`，文案 `row.IsValid === 1 ? '启用' : '禁用'` |
| e | [nc-config/logic.ts](src/certplatform-web/cert/cert-admin/src/pages/workflow/nc-config/logic.ts) | 删 `IsActive` 的 switch 覆写；`ValidationRuleController.SetActiveAsync` 改写 `rule.Data.IsValid` |

**迁移必须是「回填 → 改代码 → 删列」顺序**（实库 `IsValid` 可空，必须兜底）：
```sql
UPDATE cert_validation_rule
   SET IsValid = IF(COALESCE(IsActive, 1) = 1, 1, 0)
 WHERE IsValid IS NULL
    OR IsValid <> IF(COALESCE(IsActive, 1) = 1, 1, 0);
-- 校验：应 0 行
SELECT COUNT(*) FROM cert_validation_rule
 WHERE IsValid <> IF(COALESCE(IsActive, 1) = 1, 1, 0);
```

### 6.2.1 ★ 浏览器验收中新发现的第 5 个缺陷（D5）—— 已修

**现象**：把「显示已禁用」开关加上、列表能看到禁用行之后，点「启用」报 **“规则不存在”**；`/action/enable` 返回 HTTP 200 但 `success:false`，DB 的 `IsValid` 不变 ⇒ **禁用不可逆**。

**根因**：`SqlSugarDbOrm.GetOneAsync` 会**自动附加** `IsDeleted = 0` **与** `IsValid = 1` 两个条件（`SqlSugarDbOrm.cs:56-57`；判据为「实体自身是否声明该属性」，见 `IsDeletedCondition`/`IsValidCondition`）。F4 给 `ValidationRule` 加上 `IIsValid` 后：
```csharp
Entity.GetOne(r => r.Code == code)   // ← 对已禁用行恒返回 null
```
⇒ 任何「按 Code 精确定位」的路径都会把禁用行当“不存在”。

**这是 F4 的必然连带**（不是偶然）：只要一个实体新增 `IsValid` 声明，“按 Code 取自己”的写法就会静默失效。前端开关只解决了「看得见」，**后端取数必须同步放开**。

**修法**：控制器新增唯一定位方法，凡「启停 / 复制 / 详情」一律走它；列表类查询仍走默认口径：
```csharp
private async Task<ValidationRule?> FindByCodeIgnoreValidAsync(string? code)
{
    var result = await Entity.GetListAsync(r => r.Code == code, includeDisabled: true);
    return result.Success ? result.Data?.FirstOrDefault() : null;
}
```

**受影响的 5 处（全部已改）**

| 位置 | 修复前症状 |
|---|---|
| `ValidationRuleController.SetActiveAsync` | **禁用后无法启用**（禁用不可逆） |
| `ValidationRuleController.CopyAction` | 已禁用规则无法复制（“源规则不存在”） |
| `ValidationRuleController.GetByCode` | 已禁用规则详情打不开（设计器 GET `/{code}` 失败） |
| `ExpertItemExecutors` 取规则 | 任务创建后规则被停用 ⇒ 已排队任务报“规则不存在”（而非按冻结快照执行） |
| `ExpertTaskService.UpsertNcItemAsync` | 同上 ⇒ 停用规则的任务落不到规则快照、条款号/严重度全空 |
