## 〇、两条架构铁律

### 铁律① 关联一律走 `Code`

> 定位每条记录的核心字段是 `Code`。禁止 `ParentId` / `Dic_ID` / `CreateID` / `ModifyID` 等一切以 Id 建立关联的字段。

**这不是新增偏好，而是项目早已强制执行的约定。** 全库核查：

| 证据 | 结论 |
|------|------|
| **~60 条业务外键全部指向 `Code`** | `cert_iso_clause.ParentCode → cert_iso_clause.Code`、`audit_task.PhaseCode → ent_enterprise_phase.Code` …… **没有一条指向 Id 列** |
| 框架代码内的明文声明 | `RoleController.cs:194` —— `// 设计原则：Code 是唯一业务键，所有关联必须用 Code` |
| 框架树的关联字段是字符串 | `Sys_Organization.ParentCode`；`Sys_User.OrgCode → Sys_Organization.Code` |

### 铁律② `Code` 与业务编码分离（双键设计）

> `Code` 是系统生成的**随机 32 位 GUID**（`Guid.NewGuid().ToString("N")`），也是唯一的关联键；业务编码（字典编码 `DicNo`）只是**普通属性**，可为空，用于显示，不参与任何关联。

| 表 | `Code` 规范 | 业务编码（独立属性） |
|----|------------|---------------------|
| `Sys_Dictionary`（本次） | **随机 32 位 GUID**（框架自动填充） | `DicNo`（字典编码，可空） |
| `Sys_DictionaryList`（本次） | **随机 32 位 GUID**（框架自动填充） | 无（字典项不设业务编码） |

**由此产生的三处修正**（V3.0 → V4.0）：

| V3.0 的设计 | V4.0 修正 | 原因 |
|------------|----------|------|
| `Code = DICT_000001` 可读序号 | **`Code` 为随机 GUID** | 用户拍板：字典分类名称随时可能调整，所有 `Code` 均为随机唯一不重复 |
| `OnBeforeAddTree` 中手动生成 `Code` | **移除**，框架 `TreeTableControllerBase.AddTreeNode:146-147` 与 `YzhControllerBase.AddCore:218-223` 已自动填充 GUID | 零代码，零竞态 |
| `OnBeforeDeleteTree` 中校验"是否含明细" | **移除**，返回 `(true, null)` | 字典与分类可能被多业务引用，删除前逐项判断逻辑极复杂且必然遗漏；一律软删除，把"是否有引用"的判断交给业务侧按需处理 |

> **"没有具体项的编码，也能进行关联"** 的落地方式：明细表**不设业务编码字段**，只有 `Code`（定位键）+ `DicCode`（父字典 `Code`）。关联能力完全不依赖任何业务编码。

## 一、结论摘要

**字典模块与「机构-人员」是同一形态：左侧一棵树，右侧一张表。**

| 维度 | 机构-人员（已跑通） | 字典-明细（本次） |
|------|-------------------|------------------|
| 左树实体 | `Sys_Organization` | `Sys_Dictionary` |
| 右表实体 | `Sys_User` | `Sys_DictionaryList` |
| 树→表关联 | `Sys_User.OrgCode` → `Sys_Organization.Code` | `Sys_DictionaryList.DicCode` → `Sys_Dictionary.Code` |
| 控制器基类 | `TreeTableControllerBase<Sys_Organization, Sys_User>` | `TreeTableControllerBase<Sys_Dictionary, Sys_DictionaryList>` |
| 前端 Logic | `OrgPageLogic extends TreeTableLogic` | `DictionaryPageLogic extends TreeTableLogic` |

| 判断 | 说明 |
|------|------|
| 后端工作量 | **~330 行**（1 实体改 + 1 实体新建 + 1 控制器 + 2 个 JSON + 2 个消费端点） |
| 前端工作量 | **1 API 文件 + 1 Logic 文件 + 1 页面**（照 organization 页同构改写） |
| 真正难点 | 数据库结构补齐 + 历史数据去重 + 框架契约硬约束对齐（`IsDeleted` bool / `IsValid` int / 实体类名=表名） |
| 一期建议范围 | 静态字典（明细存表）；`DbSql` 动态字典（16 个）列二期 |

> **V1 的 K-4「明细独立控制器 / 自定义端点族」整条作废**——右表就是 `TreeTableControllerBase` 的 `V` 参数，`/filter`、`/add`、`/update`、`/delete`、`/toggle-valid` 全部免费继承。V1 判定的「框架无主从表保存能力」也不再是阻断项，因为左树右表形态**本就不需要一次性保存主从**。

### 3.4 框架陷阱一：`IsValid` 必须映射到真实列且类型严格匹配

`BaseEntity` 的**全部**基类属性都带 `[SugarColumn(IsIgnore = true)]`，包括 `IsValid` 与 `IsDeleted`。

而 `SqlSugarDbOrm.HasProperty<T>()` 对 `IsIgnore` 属性**返回 false**：

```csharp
// SqlSugarDbOrm.cs:370 / :393 —— IsDeletedCondition / IsValidCondition
if (!HasProperty<T>(nameof(IsValid)))   // IsIgnore 属性 → false
    return null;                        // → 过滤条件被跳过
```

**结论**：子实体必须显式重声明，映射到真实列，过滤才生效。

**类型硬约束**（V3.0 错误，V4.0 修正）：

| 字段 | 必须类型 | 框架依据 | V3.0 错误写法 | V4.0 正确写法 |
|------|---------|---------|--------------|--------------|
| `IsValid` | `int` | `IsValidCondition<T>` 用 `Expression.Constant(1)` 比较 | `public new int IsDeleted` | `public new int IsValid { get; set; } = 1;` |
| `IsDeleted` | **`bool`** | `IsDeletedCondition<T>` 用 `Expression.Constant(false)` 比较；`SoftDelete` 执行 `dyn.IsDeleted = true` | `public new int IsDeleted { get; set; } = 0;` | `public new bool IsDeleted { get; set; }` |

### 3.5 框架陷阱二：`Code` 插入后不可修改

```csharp
// SqlSugarDbOrm.cs:190-201
var count = await _client.Updateable(entity)
    .IgnoreColumns(GetIgnoreColumnsForUpdate())          // = { "Code", "Id", "CreateTime", "CreateBy" }
    .Where("Code = @Code", new SugarParameter("@Code", codeValue))
    .ExecuteCommandAsync();
```

**两条硬约束**：
1. **`Code` 不可 UPDATE** → 必须在插入前定值。
2. **`Update` 以 `Code` 为定位键**（不是 `Id`）→ `Code` 必须唯一、稳定，且前端提交的实体必须带上正确的 `Code`。

**V4.0 推论**：`Code` 由框架自动填充 `Guid.NewGuid().ToString("N")`（`TreeTableControllerBase.AddTreeNode:146-147`、`YzhControllerBase.AddCore:218-223`），控制器**零代码**。同时 `UpdateAsync` 会 `IgnoreColumns("Code")`，确保插入后不可改。

### 5.4 必须避开的框架陷阱

| 陷阱 | 现象 | 规避 |
|------|------|------|
| `tree/action/{m}` **只注入 `Code`** | 行操作 handler 里除 `Code` 外全是默认值 | handler 内用 `Code` 反查：`GetByCodeAny(e.Code)` |
| `ExecuteAction` 同样只注入 `Code` | 明细行操作拿不到 `DicCode` | 同上；或不做明细行操作，用工具栏按钮 + 选中行 |
| `IsDeleted` 不是 `bool` | `IsDeletedCondition<T>` 用 `Expression.Constant(false)` 比较 → 表达式类型不匹配异常 | 实体中显式声明 `public new bool IsDeleted { get; set; }` |
| `NumberBox` 不是合法 `ControlType` | `JsonStringEnumConverter` 抛异常 → `EntityConfigHelper` 静默返回空配置 → `treepconfig` 返回 0 列 | JSON 中全部使用合法枚举名：`TextBox` / `Decimal` / `Switch` / `Memo` / `ColorPicker` / `Other` |
| 实体类名 ≠ 表名 | `GetByCodeAny` / `GetChildrenCountBatch` 用 `typeof(T).Name` 当表名 → SQL 报错 | 类名必须等于表名：`Sys_Dictionary`、`Sys_DictionaryList` |
