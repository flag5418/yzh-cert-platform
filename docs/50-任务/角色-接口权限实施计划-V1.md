## 一、评估结论

### 1.1 现状核查矩阵

| # | 原文档描述 | 代码/数据库实际 | 结论 |
|---|-----------|----------------|------|
| 1 | `sys_api` / `sys_role_api` / `sys_user_permission` 三张表 | **三张表均不存在**（库内仅有 `Sys_RoleAuth` / `Sys_RoleMenu` / `Sys_RoleUser`） | ⚠️ 需先建表 |
| 2 | 表字段 `group_path VARCHAR(200)` | 实体 `SysApi` 与建表脚本用的是 **`tree_path VARCHAR(500)`**，无 `group_path` | ⚠️ 字段名不一致 |
| 3 | 展开 SQL `FROM sys_user_role` | **库中无 `sys_user_role`**，实际角色-用户表是 **`Sys_RoleUser`**（`RoleCode` + `UserCode`） | ❌ P0，SQL 必错 |
| 4 | `ApiRepository` 调用 `_dbOrm.QueryAsync<T>` / `QuerySingleAsync` / `ExecuteNonQueryAsync` | `IDbOrm` **没有这三个方法**；实际是 `SqlQueryAsync<T>` / `QueryFirstOrDefaultAsync<T>` / `SqlExecuteAsync`，且返回 `Result<T>` | ❌ P0，编译不过 |
| 5 | `ApiScanner` 用 `method.DeclaringType == type` 过滤 | 基类 `YzhControllerBase` 声明了 `config/filter/add/update/delete/export/import/action/{m}/toggle-valid` 共 **10+ 个 `[Http*]` 动作**；该过滤会把**所有未被重写的继承动作全部漏掉** | ❌ P0，接口列表严重缺失 |
| 6 | 路径取 `FormatPath(routePrefix, method.Name)` | 应为 `HttpMethodAttribute.Template`（如 `[HttpPost("check/add")]`）；且 `[controller]` 占位符未替换、`Route` 多特性只取一个 | ❌ 路径/编码全错 |
| 7 | 反射源 `AppDomain.CurrentDomain.GetAssemblies()` + 名称前缀 | 启动时 `CertPlatform.*` 程序集**未必已加载**，且前缀过滤写死为 `YZH`/`CertPlatform` | ⚠️ 发现不可靠 |
| 8 | DI 注册位置写在 `Program.cs` | 实际 DI 集中在 **`YZH.Core.Web/YzhWebBuilder.cs` → `UseYzhCore()`**；4 个服务已注释、4 个文件被 `Compile Remove` | ⚠️ 位置错误 |
| 9 | `PermissionFilter` 已有接口权限校验 | `CheckPermission()` **恒返回 `true`**（TODO 未实现），且为 `RequirePermission` 显式标注制 | ⚠️ 当前无任何校验效果 |
| 10 | 需新增菜单与路由 | **菜单已存在**：`MENU_00104 角色-接口管理 /system/role-api`、`MENU_00106 接口管理 /system/api`；`router/index.ts` 已注册路由；两个页面均为 **占位页（"功能开发中"）** | ✅ 无需改动，只需替换页面 |
| 11 | `ApiDescriptionAttribute` 新增 `Group` / `Enable` | 当前仅有 `Description` / `Author` / `CreatedAt` / `UpdatedAt` | ⚠️ 需扩展 |

### 1.2 可直接沿用的部分

| 项 | 说明 |
|----|------|
| 页面结构 | 左树右表（角色树 + 接口勾选树表），与 `/system/role-menu` 完全同构，可直接复用 `YzhTree` + `YzhTreeTableCheckSelector` |
| 后端基类 | `TreeTableControllerBase<Sys_Role, SysApi>` 已提供 `checkTree` / `check/add` / `check/remove` / `check/all` 四个虚方法 + `tree/root` / `tree/children` 角色树，与 `RoleMenuController` 用法一致 |
| 前端缓存模式 | "一次性拉取全部关联 + 切换角色本地计算 + 勾选即存" 的 `Logic` 写法可 1:1 迁移 |
| 同步流程骨架 | 扫描 → 比对差异 → 清理无效关联 → 写库 → 刷新缓存 的 6 步流程设计合理 |
| 实体类 | `SysApi` / `SysRoleApi` / `SysUserPermission` 三个实体已存在（`YZH.Core.Stand/Models/SysPermission.cs`） |

### 1.3 与原文档的主要分歧（建议修正）

| 分歧点 | 原文档 | 建议 |
|--------|--------|------|
| ApiCode 是否含参数 | `SHA256(route+method+action+params)` | **去掉参数**。否则"给接口新增一个可选参数"就会生成新 Code，导致该接口已授权的角色权限全部丢失 |
| 树形分组来源 | 新增 `group_path` 人工特性 | **复用 `tree_path`**（已存在），由路径自动派生虚拟分组树，不引入新字段 |
| 分组节点可勾选性 | 未定义 | 分组节点 `NodeType='group'` 且**不可勾选**（后端忽略、全选排除），接口节点 `NodeType='api'` |
| `enable` 语义 | 完全由特性决定 | 特性只决定**新增**记录的初值；已存在记录的 `enable` **不被同步覆盖**，允许在接口管理页手工禁用（更实用） |

## 三、关键设计决策（**待你拍板**）

> 以下 7 项会显著影响实现量与后续维护成本，请逐项确认或修改。

### 决策 1：接口发现方式

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | 注入 MVC `ApplicationPartManager` 枚举已注册程序集 → **反射**枚举 `ControllerBase` 子类与方法 | 精确覆盖"yzh.web.core 引用的所有业务 DLL"；能正确拿到路由模板与 HTTP 方法；与真实路由 100% 一致 | 需要处理继承动作去重 |
| B | 注入 `IActionDescriptorCollectionProvider`，直接读路由表 | 最准，几乎零解析逻辑，天然覆盖继承动作与多 Route | 不体现"反射"过程；拿不到自定义特性的原始声明位置 |
| C | 沿用 `AppDomain.GetAssemblies()` + 名称前缀 | 改动最小 | 程序集可能未加载 → 漏扫；前缀写死不可扩展 |

**建议 A**：满足"引入其他项目 DLL + 反射"的要求，同时修正继承动作漏扫问题。B 作为兜底校验手段（可用来对比 A 的结果是否一致）。

### 决策 2：ApiCode 生成算法

| 方案 | 输入 | 稳定性 |
|------|------|--------|
| A | `METHOD + path` | 改路由模板即失效 |
| **B（推荐）** | `METHOD + ControllerName + ActionName` | 改路由不影响；改方法名失效（语义变更，可接受） |
| C | `ControllerName + ActionName` | 最稳，但同方法名多 HTTP 谓词时冲突 |

**建议 B**，并对"同 Controller+Action+Method 的重载"追加路由模板参与 Hash 以消歧。
`path` 仍单独存表用于展示；路径变化时同步只更新 `path` 字段，不动 `code`。

### 决策 3：树形分组与节点类型

```
📁 系统管理            group  Code="g:api/System"          不可勾选
  📁 角色接口          group  Code="g:api/System/RoleApi"  不可勾选
    ☑ POST /api/System/RoleApi/check/add    api  Code=<apiCode>  可勾选
    ☑ POST /api/System/RoleApi/check/remove api  Code=<apiCode>  可勾选
```

- 分组键 = `path` 去掉最后一段（如 `api/System/RoleApi/check`）。
- 分组节点 Code 前缀 `g:` 避免与 apiCode 碰撞。
- 前端 `:check-all-exclude-types="['group']"`；并**建议给 `YzhTreeTableCheckSelector` 增加 `disabledTypes` 属性**，让分组节点复选框置灰（可选增强，约 10 行）。

### 决策 4：数据库表结构

**建议**：沿用 `scripts/db/001-create-api-permission-tables.sql` 的既有结构（`tree_path`），仅做两处修正：

1. 不新增 `group_path`，分组由 `tree_path` 派生；
2. 展开 SQL 的表名 `sys_user_role` → **`Sys_RoleUser`**；
3. 建议 `sys_api` 追加两个便于检索的冗余列（可选）：`controller_name VARCHAR(64)`、`action_name VARCHAR(64)`。

### 决策 5：控制器放置位置

| 方案 | 位置 | 说明 |
|------|------|------|
| **A（推荐）** | `src/yzh-core/YZH.Core.Web/Controllers/System/RoleApiController.cs` | 与已完成的 `RoleMenuController` 同目录，风格一致 |
| B | `src/certplatform-api/CertPlatform.Admin/Controllers/System/` | 更符合 AGENTS.md"禁止修改 YZH.Core"，但会与 `RoleMenuController` 位置分裂 |

**建议 A**（跟随既有先例）。若你希望收紧 YZH.Core 边界，则 A/B 需一次性统一（含迁移 `RoleMenuController`）。

### 决策 6：是否启用 `ApiSyncHostedService`（启动自动同步）

| 方案 | 说明 |
|------|------|
| **A（推荐）** | **不启用**。仅保留手工【更新接口】按钮，避免启动耗时与不可控写库 |
| B | 启用，启动即同步 | 开发期方便，但会掩盖扫描异常 |

### 决策 7：`sys_user_permission` 展开表本期是否建设

| 方案 | 说明 |
|------|------|
| **A（推荐）** | 本期建表 + 实现展开逻辑（修正表名），但**不接入校验**，仅作为数据准备 |
| B | 本期不建，`ApiSyncService` 移除对 `IPermissionCacheService` 的依赖 | 减少 1 张表与 1 个服务，后续再加 |

**扫描器实现要点**（决策 1 = A 时）：

```csharp
// 1) 程序集来源：ApplicationPartManager（由 DI 注入）
var assemblies = _partManager.ApplicationParts
    .OfType<AssemblyPart>()
    .Select(p => p.Assembly)
    .Where(a => !a.IsDynamic)
    .Distinct()
    .ToList();

// 2) 收集 Controller 级路由（支持多个 [Route]，取第一个）
var routes = type.GetCustomAttributes<RouteAttribute>().Select(r => r.Template).ToList();
var prefix = routes.FirstOrDefault()?.Replace("[controller]", controllerName) ?? "";

// 3) 方法收集：包含继承动作（关键修复）
var methods = type.GetMethods(BindingFlags.Public | BindingFlags.Instance)
    .Where(m => !m.IsSpecialName && !m.IsAbstract)
    .Select(m => (method: m, http: m.GetCustomAttributes(true)
                    .OfType<HttpMethodAttribute>().FirstOrDefault()))
    .Where(x => x.http != null);

// 4) 路径：用 HttpMethodAttribute.Template，回退方法名
var template = x.http!.Template ?? x.method.Name;
var path = Normalize($"{prefix}/{template}");   // 去重斜杠 / 去尾斜杠，保留 {id}

// 5) 去重：override 后以 (METHOD, path) 为键
// 6) ApiCode = SHA256($"{METHOD}|{ControllerName}|{ActionName}")，重载时追加 template
// 7) TreePath = path 去 "api" 段；Name 回退为 $"{ControllerName}.{ActionName}"
```

**验收**：启动后调用 `POST /api/System/ApiSync/list`，返回条数 ≥ 路由条数；`RoleMenuController` 应能同时被扫到 `tree/root`、`checkTree`、`check/add`、`check/remove`、`check/all` 等（含继承动作）。

## 五、风险与应对

| 风险 | 等级 | 应对 |
|------|------|------|
| 扫描结果为空或严重偏少 | 高 | Phase 2 完成后先用 `list` 接口核对数量，再进入 Phase 4；必要时用 `IActionDescriptorCollectionProvider` 做交叉校验 |
| ApiCode 算法变更导致已授权数据失效 | 中 | 本期从零开始，无历史数据；后续如需换算法，必须提供 code 迁移脚本 |
| 同步删除接口时误删权限 | 中 | 删除前先落审计日志；`SyncResult` 返回清理明细；执行前备份数据库 |
| 分组树层级过深（`check/add` 会拆成 3 层） | 低 | 分组键可截断为前 2 段（`api/System/RoleApi`），实现时按需配置 |
| 接口量大导致 `checkTree` 返回体过大 | 低 | 先测实际规模；如超 2000 条再引入按分组懒加载 |
| `YzhTreeTableCheckSelector` 分组节点可勾选 | 低 | 后端忽略非 `api` 类型；或执行 4.7 组件增强 |
| 与旧表 `Sys_RoleAuth` 职责重叠 | 中 | 本期不读取、不迁移、不删除；在文档中登记两者关系待后续决策 |
