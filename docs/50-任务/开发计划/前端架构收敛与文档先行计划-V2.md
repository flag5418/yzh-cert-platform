## 一、为什么必须是这个顺序（回应你的 #6）

### 1.1 为什么「文档先行」不是形式主义

你说「约定贯彻不彻底」是最大差异。实测下来，**贯彻不彻底的 5 个根因（C1–C5）里，C5 最致命**：

> **C5｜文档与代码不一致，文档反成错误源。**

这不是推测，本轮实测到 **10 处**。举 3 个真实例子：

| 文档写 | 代码实际 | 照文档做会发生什么 |
|---|---|---|
| `entity.Enable = 1`（新增默认值） | 启用字段是 **`IsValid`** | 违反 R7；启禁按钮失效，且**不报错** |
| 契约在 `cert-share/src/types/contracts.ts` | 只在 **`yzh.vue.core/src/types/`** | import 报错才发现；`cert-share/src/types/` 根本没这两个文件 |
| `ApiResponse` 是 PascalCase（`Success`/`Data`） | **camelCase**（`success`/`data`） | 断言恒假 → 所有接口判定失败 |

**结论**：不先修文档，改代码就是**按错误图纸施工**。这就是为什么 A 阶段必须排在 B/C 之前。

### 1.2 为什么必须「一次性」而不是「边写边改」

文档之间有**引用关系**（`AGENTS.md → 18 → 19/20 → 03`）。分批写会出现：

- 18 写「活文档 5 份」，20 又新增 3 份 → 两处数字互相矛盾
- 19 写「契约在 core」，03 还写着「契约在 cert-share」→ 新人不知道信谁

**一次给全 → 引用关系可交叉校验**。这也是你说「一次性完成所有文档」的技术理由，不只是效率问题。

### 1.3 为什么评审必须「统一」

15 个决策点里，有 **3 组强耦合**（见 §三.4）。逐条拍板容易产出**自相矛盾组合**，例如：

- D-04 选「A 补全 cert-enterprise 脚手架」 + D-07 选「B 按关键路径迁页面」→ 补全了一个不用的端，白花时间
- D-02 选「B 用包名」 + D-05 选「A 守卫扩内核」→ 守卫 R11 的检查规则要跟着改

**统一评审 = 一次看到全部耦合，避免返工。**

## 六、阶段 ④ 的判据：「模块整改到位」到底指什么（回应你的 #3）

你说不要一次性全量重写。那**「整改到位」必须有可判定的标准**，否则会滑向两个极端：什么都不改（没价值）或全部重写（成本失控）。

### 6.1 什么算「整改到位」（5 条硬判据）

一个模块**同时满足以下 5 条**，才算整改到位：

| # | 判据 | 检查方式 |
|---|---|---|
| **① 无手写 CRUD 骨架** | 页面不含 `handleAdd` / `handleBatchDelete` / `handleRowAction` / `handleSubmit` | `grep -nE "handle(Add\|BatchDelete\|RowAction\|Submit)"` |
| **② 数据加载走内核** | 用 `logic.dataLoader`，不自己写 `loadData` 调 API | 检查 `.vue` 的 `:data-loader` 绑定 |
| **③ 弹窗走内核** | 用 `YzhFormDialog`，不手写 `el-dialog` + `YzhForm` | `grep -n "el-dialog"` 应为 0 |
| **④ 字段名三处一致** | DB 列名 = C# 属性名 = TS 字段名（**PascalCase 逐字一致**） | 对照 `/api/<路由>/config` 返回的 `Columns[].FieldName` |
| **⑤ 双关键字合规** | 无 `WHERE Id` / `ON a.XxxId=b.Id` / `Id>0` 分流 / `row.Id` | `grep -nE "\.Id\b"` 逐条判 |

**附加（有条件时）**：
- ⑥ 表格不用 `el-table` 直写（R6），改用 `YzhTable`
- ⑦ 该模块的 `logic.ts` 行数**不增加**（内核覆盖后应下降）

### 6.2 什么**不算**整改到位（3 个反例）

| 反例 | 为什么不算 |
|---|---|
| 「代码能跑，不动它」 | 能跑 ≠ 合规。**手写 CRUD 也能跑**，但它让 AI 后续改动无规律可循 |
| 「只改了 import 路径 / 缩进 / 命名」 | **表面整改**。判据 ①–⑤ 一条都没过 |
| 「把 `el-table` 换成 `YzhTable` 但 columns 还硬编码」 | **半整改**。R6 只解决渲染，**配置驱动（判据 ②）未达成** |

## 十、★ 执行方式二分（V2.1 新增 · 用户第 4 点）

> 用户原话：「**当前在执行的时候，可以直接针对不合理的架构进行调整，但业务未按架构进行设计的，可以形成清单**」

### 10.1 二分原则

| | **A 类｜架构调整** | **B 类｜业务不合规** |
|---|---|---|
| **判据** | 客观、与业务无关、改错不影响业务语义 | 需业务知识 / 交互设计判断 |
| **处置** | **直接做**（不需用户决策） | **形成清单，交分工 AI** |
| **谁做** | 单一负责人 | AI-A（后台管理）/ AI-B（专家系统）按端归属 |
| **清单** | 本文 §五 Stage A/B/C | `docs/50-任务/分析报告/业务代码不合规清单-V1.md` |

**典型 A 类**：删空目录 / 删死代码 / 补 `.env` / 加令牌文件 / 统一 alias / 改路由装配入口 / **DB 命名修正** / `rebuild` 根因修正
**典型 B 类**：页面手写 CRUD（需理解业务） / 内联 `el-table` 改造（需理解交互） / camelCase 字段修正（需对齐后端） / 控制器行为契约核对

### 10.2 多 AI 分工纪律

| | **AI-A｜后台管理** | **AI-B｜专家系统** |
|---|---|---|
| 负责端 | `cert/cert-admin` | `cert/cert-auditor`（+ 未来 `cert-enterprise`） |
| 主任务 | 测试 + 完善 | **全力以赴实现专家系统** |
| 禁止碰 | ⛔ `cert-auditor/**` | ⛔ `cert-admin/**` |

**★ 唯一冲突面 = L1 `yzh.vue.core` + L2 `cert-share`**（双方共用）：

| # | 纪律 |
|---|---|
| **D1** | **L1/L2 改动由单一负责人执行**。AI-B **只读不写** core；确需改 → **提需求，不直接改** |
| **D2** | L1/L2 改动**必须公告 + 跑三端 build**（`npm run build:all`）+ `guards.mjs` |
| **D3** | **业务页面按端分工**，互不越界 |

### 10.3 执行顺序（避免互相等待）

```
阶段 1（串行 · 必须先做 —— 单一负责人）

  AI-B：专家系统实现（B-03/04 + D 类 5 页）
```
