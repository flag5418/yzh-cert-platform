## 一、★ 先纠正一个事实：标准目录第 4 段不是"机构编码"，是文件夹

你说标准目录现在的结构是「标准目录 → 标准 → 阶段 → **机构编码** → 标准目录 → 标准文件」。

**实测第 4 段是文件夹，不是机构编码：**

| 证据 | 值 |
|---|---|
| `cert_standard_directory_folder` 记录 | `FolderCode = FD-SDC-iso40012016\|03\|L01\|S001` |
| 该记录的 `ParentCode` | **`NULL`**（= 根文件夹） |
| 该记录的 `FolderName` | `CS河北雄安尚龙医疗科技有限公司13485体系材料` |
| 该记录的 `FullPath` | `CS河北雄安尚龙医疗科技有限公司13485体系材料` |
| 文件的 `FullPath` | `CS河北雄安尚龙医疗科技有限公司13485体系材料/4记录文件/风险管理报告.doc` |
| 文件的 `StoragePath` | `/standard-directory/iso40012016/03/CS河北雄安…/4记录文件/风险管理报告.doc` |
| `cert_standard_directory_config` 列 | `Code / DirectoryCode / StandardCode / PhaseCode / RootFolderName / …` —— **无 `OrgCode`** |

→ 真实结构 = `/standard-directory/{StdCode}/{PhaseCode}/{FolderPath…}/{FileName}`
→ 那个"机构编码"位置，实际是**上传时把整家企业的材料当模板传进来，根文件夹被命名成企业名**

**所以"让企业结构对齐标准目录结构"这个前提要改**：不是"企业库去对齐一个已有的机构编码段"，而是**两边都要新增一个 code 段**（这正是你的结论，只是理由需要修正）。

```
企业库： /enterprise-documents/{StdCode}/{PhaseCode}/{EnterpriseCode}/{FolderPath}/{FileName}
```

| 段 | 取值来源 | 实测值 |
|---|---|---|
| `{StdCode}` | `cert_standard_directory_config.StandardCode` | `iso40012016` / `iso90012015` |
| `{PhaseCode}` | `cert_standard_directory_config.PhaseCode` | `03` / `jd01` |

### ★ 这个设计带来一个真正的收益

→ **两库共用同一套文件夹模板**：标准库怎么分文件夹，企业库就怎么分。
→ 这正是你要的"结构一致"，且**不需要复制文件夹表**。

### ⚠️ 代价：标准库需迁移 334 个对象

现有 334 个对象的路径**缺 OrgCode 段**。两个选择：

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **M1（建议）** | 脚本把对象从 `/{Std}/{Phase}/…` 移到 `/{Std}/{Phase}/{OrgCode}/…`，同步改 DB 的 `StoragePath` / `FullPath` / `PreviewPdfPath` / `MarkdownPath` | 一次性脚本。文件最大 359KB → `RenameAsync`（内存缓冲）无压力 | 中途失败会产生半迁移状态 → **必须幂等 + 可断点续跑** |
| **M2** | 新上传走新格式，老数据不动 | 零迁移 | **两套格式并存** → `DeriveOrgCodeFromPath` 无法判断该取哪段 → 每次都要特判，长期债 |

**建议 M1**，但**排期放在功能之后**（见 §八）。

## 三、你的第 3 条：删 `FileCode` —— 同意，但理由比"没必要"更硬

### 3.1 为什么同意

`FileCode = FL-{FolderCode}|{FileName}` 是**派生键**，嵌了 `FolderCode` + `FileName`。
而你的第 4 条要求**覆盖时把旧文件重命名丢进归档** → 一旦重命名，`FileCode` 就变了。

但它被当作**稳定引用**用在 7 类地方：

| 引用方 | 位置 |
|---|---|
| **提取规则键** | `ExtractionResult.FileCode`、`TableExtractionResult.FileCode`、`DocExtractionRule.FileCode`（注释："规则键：实际文件 FileCode 或模板 Code"） |
| 队列资源锁 | `ResourceCode = f.FileCode` |
| 转换任务载荷 | `OfficeConvertService` payload `FileCode`（`:544`）+ 按 FileCode 查文件（`:89`） |
| 查询/映射 | `StandardDirectoryService` `:397` / `:411` / `:430` / `:527` |
| 上传清单 | `UploadManifestDto` 的 `FileCode` / `ExistingFileCode` / `FileCodes` / `OldStoragePath` 等 **7 处** |
| 前端类型 | `cert-share/src/types/cert.ts:283`、`:376` |
| DB | `uk_file_code (FileCode)` UNIQUE（334 行） |

→ **一个会变的派生键，不能当稳定引用用。** 这是必须换掉的根本原因。

### 3.2 替代方案

全部改用 **`Code`**（GUID 业务键，已有 `uk_code` 唯一索引）：

- 提取规则键：`FileCode` → `Code`（模板侧继续用 `FR-xxx` 的 `Code`，语义不变）
- 队列锁 `ResourceCode`：→ `Code`
- 转换载荷：→ `Code`
- 前端类型：→ `Code`

**改动面 ≈ 20 处后端 + 2 处前端类型 + 1 个 DB 列**（破坏性，334 行数据）。

### 3.3 建议分两步

```
第一步（本阶段）：GenerateFileCode 里的 `|` 换成不会出现在文件名里的符号（如 `~`）
                   —— 因为第 4 条已让版本号不进文件名，`|` 冲突实际上已消失，
                      这一步只是把埋雷彻底拆除，改动 1 行
第二步（P6）    ：删 FileCode 列，全面换 Code —— 纯技术债，不影响功能
```

> **需要你定**：是否接受"先换符号、后删列"？还是一步到位现在就删？

## 四、你的第 4 条：归档机制 —— 设计建议

**这是本轮最有价值的一条**，它同时解决了 `|` 冲突和版本号（版本不进路径 → 无分隔符问题）。

### 4.1 路径约定

```
{FolderPath}/{FileName}                                ← 当前源文件（永远最新名）
{FolderPath}/_archive/{FileName}.v{n}                  ← 历史源文件   ★ 见 4.4
{FolderPath}/pdf/{FileName}.pdf                        ← 当前 PDF
{FolderPath}/pdf/_archive/{FileName}.pdf.v{n}          ← 历史 PDF
{FolderPath}/markdown/{FileName}.doc.md                ← 当前 Markdown
{FolderPath}/markdown/_archive/{FileName}.doc.md.v{n}  ← 历史 Markdown
```

- `.v{n}` 与历史表 `VersionNumber` **对齐** → 路径本身即可反查历史记录
- 与现有 `BuildProductPath`（`CodeGeneratorService.cs:129`）**完全兼容**：
  归档路径 = 在 `pdf`/`markdown` 段后再插 `_archive`，文件名加 `.v{n}` 后缀
- 建议新增 `BuildArchivePath(storagePath, productKind, version)`，与 `BuildProductPath` 并列

### 4.2 新表：`cert_standard_directory_file_history`

| 列 | 类型 | 说明 |
|---|---|---|
| `Code` | varchar(36) | GUID 业务键（唯一） |
| `FileCode` | varchar(150) | 源文件引用（若 §3 已换成 `Code`，此处同改） |
| `VersionNumber` | int | 从 1 递增 |
| `FileName` | varchar(500) | 归档时的文件名 |
| `StoragePath` | varchar(512) | **归档后**的源路径 |
| `PreviewPdfPath` | varchar(512) | 归档后的 PDF 路径 |
| `MarkdownPath` | varchar(512) | 归档后的 MD 路径 |
| `FileSize` | bigint | |
| **`FileHash`** | varchar(64) | **SHA256** —— 体系认证追溯的硬证据 ★ |
| `ChangeNotes` | text | 变更说明 |
| `UploadBy` / `UploadTime` | | |
| `IsDeleted` / `IsValid` / `CreateTime` / `UpdateTime` / `CreateBy` / `UpdateBy` | | 遵循铁律九 |

唯一键：`uk_file_version (FileCode, VersionNumber)` —— 照旧系统 `ent_file_version` 的成熟设计。

> ⚠️ **`FileHash` 建议现在就加**。旧系统 `ent_enterprise_file.file_hash` 注释写着
> "SHA256哈希（增量审核依据）"，而现有 `cert_standard_directory_file` **没有这个列**。
> 体系认证追溯"这份文件有没有被改过"靠的就是它 —— 归档机制不带 hash 是不完整的。

### 4.3 覆盖流程（改造点精确定位）

现有 replace 分支在 `StandardDirectoryService.cs:747-800`：

```
existingFile != null →
  existingFile.UploadStatus = "replacing"
  existingFile.StoragePath  = storagePath      ← 直接指向新路径（同路径则就地覆盖）
  existingFile.Remark       = $"[upload-replace:{taskId}]"
  await _db.UpdateAsync(existingFile)          ← ⚠️ 全列写回（陷阱 ㉑）
  ... OldStoragePath = oldStoragePath          ← 只回传，**无人消费**
```

**改为：**

```
existingFile != null →
  ① 归档旧对象（三个都做）：
       RenameAsync( 旧 StoragePath    → {FolderPath}/_archive/{FileName}.v{n} )
       RenameAsync( 旧 PreviewPdfPath → {FolderPath}/pdf/_archive/{FileName}.pdf.v{n} )
       RenameAsync( 旧 MarkdownPath   → {FolderPath}/markdown/_archive/{FileName}.doc.md.v{n} )
  ② 插历史行（记归档后的三个路径 + FileHash + VersionNumber）
  ③ 更新当前行：StoragePath = 新路径、VersionNumber + 1、双链置 pending
       ★ 必须**列级写入** UpdateAsync(entity, cols)，不要全列写回
  ④ 重新入队转换（新文件重转 PDF + MD）
```

### 4.4 ⚠️ 三个必须处理的边界

**① 源文件也要归档（你没提到）**

你只说"在 pdf 和 markdown 文件夹下增加归档文件夹"。但**源文件本身**也会被覆盖 —— 若只归档产物，**原始字节永久丢失**，PDF/MD 归档与源文件脱钩，追溯链断裂。

建议补上 `{FolderPath}/_archive/`（与 `pdf/`、`markdown/` 平级）。

**② 正在转换的文件被覆盖 → 竞态**

归档一个 `ConvertStatus/MarkdownStatus ∈ {pending, converting}` 的文件，会与正在跑的执行器冲突
（**与已实测的陷阱 ㉕「全实体写回」同源**）。

建议：**上传时若该文件正在转换 → 拒绝并提示"文件正在转换，请稍后重试"**。
（不要试图取消队列任务 —— 队列锁不参与调度，取消会产生孤儿任务。）

**③ 归档失败不能静默**

`RenameAsync` 是「下载 → 上传 → 删除」三步。若中途失败，可能出现**旧字节已删、新文件未写**的两头空。
这是本方案**唯一必须做成补偿/幂等**的地方：

- 顺序：**先 Rename 到归档路径（成功）→ 再上传新文件**
- `RenameAsync` 失败 → **中止替换**，返回业务失败（恒 HTTP 200 + `success=false`）
- 上传新文件失败 → 归档已成功，可安全重试（归档目标带 `.v{n}`，重试幂等）

### 4.5 `IsProductPath` / 保留名

`CodeGeneratorService.IsProductPath`（`:156`）判断"任一段 == `pdf`/`markdown`" → 归档产物仍在 `pdf/` 下 ✓。

但需**新增 `_archive` 为保留段名** —— 防止有人建一个叫 `_archive` 的业务文件夹与归档目录撞车。
建议在「建文件夹」校验里拦掉以 `_` 开头的段名。

## 七、判重 —— 一个必须补的缺口

现有判重（`StandardDirectoryService.cs:740-742`）：

```csharp
x.DirectoryCode == manifest.DirectoryCode && x.FullPath == fullPath && x.IsValid == 1
```

**但实测索引只有：**

| 索引 | 列 | 唯一 |
|---|---|---|
| `PRIMARY` | `Id` | ✓ |
| `uk_code` | `Code` | ✓ |
| `uk_file_code` | `FileCode` | ✓ |
| `idx_directory_code` | `DirectoryCode` | ✗ |
| `idx_folder_code` | `FolderCode` | ✗ |

→ **`(DirectoryCode, FullPath)` 没有唯一索引**，且应用层判重是"先查后写"，**非原子**。
→ 并发上传同名文件会插入两行同 `FullPath`。

归档机制**依赖这个判重**（判不出重复 = 不归档 = 历史丢失）。

**必须补**：`uk_dir_fullpath (DirectoryCode, FullPath, IsValid)`
（`IsValid` 参与唯一键是为了软删后能重建 —— 需确认业务上是否允许同路径既有有效行又有失效行）
