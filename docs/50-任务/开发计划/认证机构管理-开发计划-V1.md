## 〇、一句话结论

```
认证机构模块  =  YZH 标准单表 CRUD（四件套，照抄 CertStage）
                 ＋ 偏差 1：后端新增/修改/删除时，在【事务内】同步 Sys_Organization 机构记录
                 ＋ 偏差 2：实体补全审计/软删除字段重声明（当前是坏的）
```

**所属范围**：本项目**数据权限的第一个试点**。本期只做一件事——
**把"机构-attach 契约"建立起来**（业务表带 `OrgCode` + 建立机构时同步写 `Sys_Organization`），
为后续数据权限提供数据基础。**本期不实现任何数据权限过滤逻辑**。

## 一、为什么是"单表 + 两偏差"

### 1.1 YZH 单表 CRUD 的标准形态（四件套）

以 `CertStage`（认证阶段）为样板，它已经跑通且是当前最标准的单表实现：

| # | 层 | 文件 | 内容 |
|:-:|----|------|------|
| 1 | 实体 | `CertPlatform.Shared/Entities/Cert/CertStage.cs` | `[SugarTable]` + `BaseEntity` + 重声明字段 |
| 2 | 控制器 | `CertPlatform.Admin/Controllers/Foundation/CertStageController.cs` | `YzhControllerBase<V>` + `LoadConfig()` + `OnBeforeAdd/Update` 唯一性 |
| 3 | 配置 | `YZH.Core.Web/Assets/EntityConfigs/Foundation/CertStage.json` | 新版 JSON（`Columns`/`FormColumns`/`SearchForm`/`Rules`） |
| 4 | 前端 | `cert-admin/.../pages/foundation/cert-stage/index.vue` + `cert-share/src/api/cert/cert-stage.ts` | `YzhTable` + `YzhForm` 单文件页面 + API |

> 认证机构四件套**已存在**，但都偏离了标准形态（见 §三）。修正后即回归标准。

### 1.2 本模块的两个偏差

| 偏差 | 性质 | 处理 |
|------|------|------|
| **偏差 1：跨表事务** | 新增/改/删时必须同步 `Sys_Organization` | override 三个原子方法，在事务内编排 |
| **偏差 2：软删除补全** | 实体当前未重声明审计字段 → 软删除实际失效 | 按 `CertStage` 样板补 `new` 属性 |

**除这两个偏差外，其余 100% 与单表逻辑相同**（列表、搜索、新增表单、编辑、唯一性校验、启停、分页，全部走基类与标准前端）。

## 二、已验证的框架机制（事务可行）

前一版把"事务是否可行"列为高风险。**读源码后已确认可行**，依据如下：

| 事实 | 位置 | 含义 |
|------|------|------|
| `IDbOrm` 为 **Scoped** 注册：`AddScoped<IDbOrm>(sp => factory.GetDefault())` | `YZH.Core.Web/YzhWebBuilder.cs:49` | 一个请求内只解析一次 → 一个 `SqlSugarClient` |
| `EntityService<>` 为 **Scoped**：`AddScoped(typeof(EntityService<>))` | `YzhWebBuilder.cs:63` | `EntityService<T1>` 与 `EntityService<T2>` 共用同一个 `IDbOrm` |
| `BeginTransaction()` → `_client.Ado.BeginTran()`，返回 `SqlSugarTransaction` | `YZH.Core.DataBase/Implementations/SqlSugarDbOrm.cs:369` | 事务挂在共享 client 上 |
| `EntityService.Insert` 失败**返回 `Result.Fail`（不抛异常）** | `EntityService.cs:385+` | 编排方必须**检查 `.Success` 后手动 Rollback** |

**结论**：在 Controller 中注入 `IDbOrm` + `EntityService<Sys_Organization>`，
`BeginTransaction()` → `orgService.Insert(...)` → `base.AddCore(...)` → `Commit()`，两条写落在同一连接同一事务内。✅

> 附带发现（非本任务范围）：`DbContextFactory` 每次 `GetByAlias` 都 new 一个 `SqlSugarClient`，
> 靠 Scoped 注册保证"一请求一实例"。若将来有跨请求复用 client 的改动，事务会退化为全局事务，需重新评估。

### 3.2 重点缺陷：软删除实际失效（偏差 2 的根因）

`BaseEntity` 中审计与软删除字段全部标注了 `[SugarColumn(IsIgnore = true)]`：

```csharp
// src/yzh-core/YZH.Core.Stand/Models/Entity/BaseEntity.cs
[SugarColumn(IsIgnore = true)] public bool IsDeleted { get; set; }
[SugarColumn(IsIgnore = true)] public DateTime? DeleteTime { get; set; }
[SugarColumn(IsIgnore = true)] public string? DeleteBy { get; set; }
// CreateTime/CreateBy/UpdateTime/UpdateBy/IsValid 同理
```

而 `SqlSugarDbOrm.IsDeletedCondition<T>()` 的逻辑是：**属性带 `IsIgnore` 就跳过软删除过滤**（`return _ => true;`）。
`EntityService.SoftDelete()` 又只更新 `new[] { "IsDeleted", "DeleteTime", "DeleteBy" }` 三个字段。

⇒ `CertificationBody` 不重声明这些字段，则：**删除不落库、查询不过滤已删数据**。
`CertStage` 之所以正常，就是因为它把所有字段用 `new` 重声明了一遍（脱离 `IsIgnore`）。
**这是本模块必须补的第一件事。**

### 3.3 数据库现状（已 `information_schema` 实测，2026-09-13）

`cert_certification_body` 实际列（按序）：

## 四、机构-Attach 契约（本期唯一的"新东西"）

### 4.1 契约定义

```
Sys_Organization（权限主体）              cert_certification_body（业务主体 = Attach）
├─ Code      ← attach.Code（同一个 GUID）
├─ OrgName   ← attach.Name
├─ OrgCode   ← attach.CbCode（CNAS 认可编号，对外业务编号）
├─ ParentCode = 运行时解析出的根节点（OrgType='CertBody' 且无父节点）
├─ OrgType   = 'CertBody'
├─ OrgLevel  = 2
├─ OrgPath   = '/{根节点Code}/{Code}'
├─ Enable    ← attach.IsValid（1↔1, 0↔0）
└─ IsDeleted / DeleteTime / DeleteBy  ← 与 attach 同步

                                       ├─ OrgCode → Sys_Organization.Code（隔离键）
                                       └─ Status / Sort / 业务字段
```

**挂载点（决策 D4）**：**不硬编码**具体根节点 Code，而是运行时查询
`OrgType='CertBody' AND (ParentCode IS NULL OR ParentCode='')` 中 `Sort` 最小者（见 `ResolveCertBodyRootCodeAsync`）。
这样换环境/换种子数据不需要改代码；查不到则返回明确中文提示。

**Code 策略（决策 D1）**：**单 Code**——`attach.Code == Sys_Organization.Code`。
依据 `多角色复杂权限体系设计-V1.md` §0.2 的 attach 基类约定 `code (↔ Org.Code)`；
`OrgCode` 字段保留为**全项目统一的数据权限隔离键**（未来任意业务表统一按 `OrgCode` 过滤）。

### 4.2 同步矩阵

| 操作 | `cert_certification_body` | `Sys_Organization` | 事务 |
|------|---------------------------|--------------------|:----:|
| 新增 | INSERT | INSERT（`ParentCode=根节点`，`OrgType='CertBody'`） | ✅ |
| 修改 | UPDATE | UPDATE `OrgName` / `OrgCode` / `Enable` | ✅ |
| 删除 | 软删 | 软删；**存在子机构则拒绝**（对齐 `OrganizationController.OnBeforeDeleteTree`） | ✅ |
| 启停（`toggle-valid`） | UPDATE `IsValid` / `Status` | UPDATE `Enable` | ✅ |

枚举状态：`Status ∈ { active, suspended, inactive }`；`active ↔ IsValid=1 ↔ Enable=1`，其余均 `0`。

### 5.2 控制器（偏差 1）

保持单表骨架不变，只 **override 三个原子方法**——它们是框架设计好的扩展点
（`YzhControllerBase` 注释：「`*Core()` 方法：原子操作，返回 `Result<T>`，供任意代码调用」）。

```csharp
[ApiController]
[Route("api/Foundation/[controller]")]
public class CertificationBodyController : YzhControllerBase<CertificationBody>
{
    private readonly EntityService<Sys_Organization> _orgService;
    private readonly IDbOrm _dbOrm;
    // 挂载点不硬编码，运行时按 OrgType='CertBody' 解析（决策 D4）

    public CertificationBodyController(
        EntityService<CertificationBody> entityService,
        EntityService<Sys_Organization> orgService,
        IDbOrm dbOrm,
        IUserContext userContext)
        : base(entityService, userContext)
    {
        _orgService = orgService;
        _dbOrm = dbOrm;
    }

    protected override EntityConfig LoadConfig() => EntityConfigHelper.GetConfig<CertificationBody>();
    protected override bool StrictConfigLoad => true;   // 缺 JSON 直接抛，开发期暴露

    /// <summary>唯一性校验（与 CertStage 同款）</summary>
    protected override async Task<(bool ok, string? msg)> OnBeforeAdd(CertificationBody e)
    { /* Name / CbCode 唯一 */ }

    protected override async Task<(bool ok, string? msg)> OnBeforeUpdate(CertificationBody e)
    { /* Name / CbCode 唯一（排除自身） */ }

    // ── 偏差 1：事务内同步机构主体 ──────────────────────────────
    public override async Task<Result<CertificationBody>> AddCore(CertificationBody entity)
    {
        if (string.IsNullOrEmpty(entity.Code))
            entity.Code = Guid.NewGuid().ToString("N");
        entity.OrgCode = entity.Code;                      // 单 Code 契约

        var org = BuildOrgNode(entity);
        using var tx = _dbOrm.BeginTransaction();

        var orgResult = await _orgService.Insert(org, UserContext.ClientIp);
        if (!orgResult.Success) { tx.Rollback(); return Result<CertificationBody>.Fail(orgResult.Error!); }

        var result = await base.AddCore(entity);           // 校验 → OnBeforeAdd → Insert → OnAfter*
        if (!result.Success) { tx.Rollback(); return result; }

        tx.Commit();
        return result;
    }

    public override async Task<Result<CertificationBody>> UpdateCore(CertificationBody entity)
    { /* 事务内：更新 attach + 同步 org.OrgName/OrgCode/Enable */ }

    public override async Task<Result<int>> DeleteCore(params string[] codes)
    { /* 事务内：校验无子机构 → 软删 attach → 软删 org */ }

    private static Sys_Organization BuildOrgNode(CertificationBody e, string rootCode) => new()
    {
        Code = e.Code, OrgName = e.Name, OrgCode = e.CbCode,
        ParentCode = rootCode, OrgType = "CertBody", OrgLevel = 2,
        OrgPath = $"/{rootCode}/{e.Code}",
        LeaderName = e.ContactName, LeaderPhone = e.ContactPhone,
        Sort = e.Sort, Enable = (byte)(e.IsValid == 1 ? 1 : 0),
        IsValid = 1, Remark = e.Remark
    };
}
```

**注意点**
1. `base.AddCore` 内部已含 `ValidateEntity` + `OnBeforeAdd` + `Insert` + `OnAfterAdd/OnAfterCommitted`，**不要重复实现**。
2. `EntityService.Insert` 失败不抛异常 → 必须判 `.Success` 再 `Rollback()`。
3. `EntityService<Sys_Organization>` 可被 DI 注入，因为基类 `Sys_Organization : BaseEntity`，且 `EntityService<>` 是开放泛型 Scoped 注册。
4. 删除时若 `Sys_Organization` 下有子机构（如未来挂虚拟机构），返回 `Fail` 拒绝，避免孤儿数据。

### 7.2 关于「系统机构可禁用」

`Sys_Organization.Enable` 是机构主体的启用位，与 Attach 的 `IsValid` 是**同一语义的两个载体**。
本期实现为**双向同步**：

| 操作入口 | Attach | Sys_Organization |
|---------|--------|------------------|
| 页面「启用/禁用」按钮（`toggle-valid`） | `IsValid` 0↔1，`Status` active↔inactive | `Enable` 0↔1 |
| 新增 | `IsValid=1` | `Enable=1` |
| 编辑保存 | 按 `IsValid` 现值 | `Enable` 同值 |

即：**禁用认证机构 = 同时禁用其机构主体**，为后续数据权限（禁用的机构不参与授权/过滤）预留语义一致性。

### 9.1 框架 bug 详录（已修复）

**现象**：新增认证机构时，`Sys_Organization` 已插入成功，随后 Attach 插入报错 `Table 'certification_body' doesn't exist`，事务回滚导致整体失败。

**根因**：`EntityService.GetQueryTableName(Type)`（`YZH.Core.Api/Services/EntityService.cs:351`）的优先级链只实现了 `[ViewName]` → `[Table]` → 类型名，**漏了 SqlSugar 的 `[SugarTable]`**。
YZH 新架构实体标准用法是 `[SugarTable("cert_certification_body")]`，于是 `GetByCodeAny` / `SoftDelete` 等少数走该方法的路径把表名退化成了类名 `certification_body`。

```csharp
// 修复后优先级：[ViewName] > [SugarTable] > [Table] > 类型名
var sugarAttr = type.GetCustomAttributes(typeof(SqlSugar.SugarTable), inherit: true)
    .Cast<SqlSugar.SugarTable>().FirstOrDefault();
if (!string.IsNullOrEmpty(sugarAttr?.TableName))
    return sugarAttr.TableName;
```

**已同步**：`docs/10-YZH架构/08-常见错误与修复.md`。

> 附带发现：`YZH.Core.Api.Tests` 测试工程**缺失 xunit 依赖，本身无法编译**（与本次改动无关，属既有问题），
> 故本次框架改动采用「`dotnet build` + 重启后端 + 接口冒烟」三验代替 `dotnet test`。
