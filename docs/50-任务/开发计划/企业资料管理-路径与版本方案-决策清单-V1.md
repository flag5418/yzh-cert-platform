## 一、三方不一致的路径格式（核心问题）

| 来源 | 标准库格式 | 企业库格式 |
|---|---|---|
| **代码声明** `CodeGeneratorService.cs:47` | `/standard-directory/{OrgCode}/{StdCode}/{PhaseCode}/...`（5 段） | — |
| **旧企业格式** 旧 `CodeGeneratorService.cs:177` | — | `/enterprise-documents/{EnterpriseNo}/{OrgCode}/{StdCode}/{PhaseCode}/...`（6 段） |
| **文档 §5.1 声称** | `/standard-directory/{OrgCode}/{StdCode}/{PhaseCode}/...`（5 段） | `/enterprise-documents/{EnterpriseCode}/{StdCode}/{PhaseCode}/...`（5 段） |
| **数据库实测** | `/standard-directory/{StdCode}/{PhaseCode}/{FolderPath}/{FileName}`（**4 段，无 OrgCode**） | 0 行（未启用） |

**实测样本**（`cert_standard_directory_file.StoragePath`，6 行一致）：

```
/standard-directory/iso40012016/03/CS河北雄安尚龙医疗科技有限公司13485体系材料/3制度文件（可根据企业实际修改）/制度文件/XASL-QD-007 产品退货管理制度.doc
```

段位：`[0]standard-directory [1]iso40012016(StdCode) [2]03(PhaseCode) [3..]文件夹 [n]文件名`

### 连带影响：`DeriveOrgCodeFromPath` 的 `idx` 是按「声明格式」写的

`StandardDirectoryService.cs:2124-2133`：

```csharp
int idx = 0;
if (segments[idx] == "standard-directory") idx = 1;
else if (segments[idx] == "enterprise-documents") idx = 2;
return segments.Length > idx ? segments[idx] : null;
```

| 分支 | 按声明格式 | 实测数据 | 结果 |
|---|---|---|---|
| `standard-directory` | 5 段 → `idx=1` 得 OrgCode ✅ | 4 段 → `idx=1` 得 **StdCode** | ❌ **静默取错** |
| `enterprise-documents` | 旧 6 段 → `idx=2` 得 OrgCode ✅ | 若按文档 5 段 → `idx=2` 得 **StdCode** | ❌ **静默取错** |

该函数被用于构造队列作用域键（`:2061`、`:2240`）：

```csharp
var scopeKey = $"{orgCode}|{config?.StandardCode}|{config?.PhaseCode}";
```

→ **取错 = 队列作用域串味**（不同标准/阶段的转换任务被判为同一作用域），且**零报错**。

## 二、需要你决策的 6 项

### 决策 A：标准库路径要不要租户段？

- **A1（建议）改代码认 4 段**：标准库 = 共享模板库，本就不该有租户段。删掉 `idx=1` 假设，`scopeKey` 改用其他键。**数据不动、零迁移**。
- **A2 补数据到 5 段**：需迁移 167 个 MinIO 对象 + 全部产物，且要决定存量归哪个工作区。**代价大、收益低**。

> **请裁决：标准库是否需要按工作区隔离？**
> 不要 → A1（推荐）｜要 → A2，且需回答「存量 167 行归哪个工作区」

### 决策 B：企业库路径用几个租户段？

实测 `cert_enterprise` 两列的性质完全不同：

| 列 | 类型 | 实测值 | 性质 |
|---|---|---|---|
| `Code` | varchar(36) | `bfa7bd00cc4b4b9c96c8a708313574ab` | GUID，稳定、唯一 |
| `EnterpriseNo` | varchar(20) | `热热` / `3443` / `43343` | **人读编号，可空、含中文、可改** |
| `OrgCode` | varchar(50) | `66bbf572…`（工作区） | 租户键 |

- **B1（建议）单段 `{EnterpriseCode}`**：`Code` 是稳定 GUID，天然全局唯一。代价：路径里看不出是哪家企业，人工排查 MinIO 不便。**必须同步把 `DeriveOrgCodeFromPath` 的 `idx` 从 2 改成 1**。
- **B2 双段 `{EnterpriseNo}/{OrgCode}`**（旧方案）：可读性好，但 `EnterpriseNo` 可空/含中文/可改 → **路径不稳定**（企业改名即换路径；空值导致段塌陷）。
- **B3 双段 `{OrgCode}/{EnterpriseCode}`**：语义清晰，但 `idx` 需改为 1。

> **请裁决：路径要「稳定」还是「可读」？**
> 若选可读（B2），`EnterpriseNo` 必须补：非空 + 唯一 + 禁中文 + 禁止修改。这三条现在都没有。

### 决策 C：版本号的落点（★ 最关键）

你的方案：对象名 = `{原名}|{版本号}.{扩展名}`。

**问题：`|` 已经是本项目的结构性分隔符，共 6 处在用：**

| 用途 | 代码位置 | 形态 |
|---|---|---|
| 目录编码 | `CodeGeneratorService.cs:22` | `SDC-{StdCode}\|{PhaseCode}` |
| 文件夹编码 | `:30` | `FD-{DirectoryCode}\|L{level}\|S{seq}` |
| **文件编码** | `:38` | `FL-{FolderCode}\|{FileName}` ← **文件名嵌在这里** |
| 队列作用域键 | `StandardDirectoryService.cs:2062` | `{orgCode}\|{StdCode}\|{PhaseCode}` |
| 队列资源锁 | `QueueManager.cs:135` | `{ResourceTable}\|{ResourceCode}` |
| 专家端关联树叶子 | `EnterpriseStageController.cs:71` | `CodeSeparator = '\|'` |

**且已有代码在按 `|` 反解**：`StandardDirectoryService.cs:1252` → `f.FolderCode.Split('|')`

**风险链**：

```
文件名 = 营业执照正本.doc
FileCode = FL-FD-SDC-iso40012016|03|L01|S001|营业执照正本.doc     ← 5 个 | 段
加上版本 → 营业执照正本.doc|2
FileCode = FL-FD-SDC-iso40012016|03|L01|S001|营业执照正本.doc|2   ← 6 个 | 段 → 错位
```

**今天是安全的**（当前无人解析 `FileCode`），**但这是埋雷** —— 一旦要实现「按标准副本」就需要从 `FileCode` 反查，届时必然踩。

**另有一处待遇不一致**：`GenerateStandardDirectoryPath` 对 `folderPath` 做 `.Replace("|","-")`，对 `fileName` 只做 `SanitizeFileName`（**不删 `|`**）。
→ **同一个 `|`，在文件夹名里被消灭，在文件名里被放行。**

**选项：**

| 选项 | 做法 | 代价 |
|---|---|---|
| **C1** | 照你说的做（对象名带 `\|版本号`），**同时**把 `FileCode` 的分隔符换掉或不再嵌 `FileName` | 要改 `GenerateFileCode` + 回填 167 行 `FileCode` |
| **C2** | 版本号只进 DB（旧系统做法），对象名不含版本 | ❌ **旧系统就埋在这**：`ent_file_version.storage_path` 每版写同一路径 → v2 覆盖 v1 字节 |
| **C3** | 版本号进对象名，但用 `~` 等不会出现在真实文件名里的符号 | 零冲突、不动 `FileCode`。你的顾虑（`-`/`_` 常见）成立，`~` 几乎不出现 |
| **C4（建议）** | 版本号放**目录段**：`.../v2/文件名.doc` | 完全不碰文件名；`|` 冲突消失；MinIO 控制台里多版本天然分组、肉眼可读；`BuildProductPath` 派生法天然兼容 |

> **请裁决：C1 / C3 / C4 三选一（C2 不建议）。**
> 我倾向 **C4** —— 它把版本从「文件名的一部分」提升为「目录的一层」，既解决 `|` 冲突，又符合你"版本是文件的一个维度"的本意。

### 决策 D：`FullPath`（判重键）与 `StoragePath`（物理键）必须分离

实测：`StandardDirectoryFile` 同时有 `FullPath` 和 `StoragePath`，且**判重用的是 `FullPath`**：

```csharp
// StandardDirectoryService.cs:740-742
var existingFile = (await _db.GetOneAsync<StandardDirectoryFile>(
    x => x.DirectoryCode == manifest.DirectoryCode
        && x.FullPath == fullPath && x.IsValid == 1)).Data;
```

`FullPath` 是**逻辑相对路径**（`:1546` = `父路径 + 文件名`，`:1552` = `文件名`）。

**逻辑闭环**：
- 若 `FullPath` **含**版本号 → 每次上传都是新 `FullPath` → 永远查不到重 → 永远 v1 → **版本机制永不触发**
- 若 `FullPath` **不含**版本号、`StoragePath` **含** → 判重正常，版本正确递增 ✅

> **请裁决：确认「`FullPath` 存逻辑路径（无版本）/ `StoragePath` 存物理路径（含版本）」这个分离规则写进文档。**
> 这是版本机制能否工作的**前提**，文档目前没写。

### 决策 E：新增版本 = 新行还是原地更新？

现有 `cert_standard_directory_file` **没有版本表**（旧系统的 `ent_file_version` 未迁移）。

- **E1 新行 + 旧行软删（`IsValid=0`）**：`GetOneAsync` 的 `IsValid=1` 过滤会自然只返回最新版 ✅ 与现有过滤语义一致。
- **E2 新行 + 旧行保留**：判重查询会命中多行，`GetOneAsync` 取"第一行"（顺序不确定）→ ⚠️ **静默取到旧版**（陷阱 ⑱ 同类）。
- **E3 原地更新**：历史版本字节在 MinIO 里保留但 DB 无记录 → 无法追溯。

> **请裁决：E1（建议）/ E2 / E3。**
> 若选 E2，必须给判重查询补 `OrderByDescending(版本)`。

### 决策 F：N 份副本转换几次？

你确认了副本的必要性（同一资料在多个标准里有不同目录/文件名）。但**副本内容字节完全相同**，而产物路径由源路径派生（`BuildProductPath`）。

- **F1 每份副本各转一次**：实现直接，但队列负载 **×N**（同一份字节转 N 次 `office2pdf` + N 次 `anydoc2md`）。
- **F2（建议）转 1 次、产物复制 N−1 份**：队列负载 **1×**。需要"主副本"概念 + 产物复制 —— **正好用上 A1 的 `CopyObjectAsync`**。
  - P6 延后不受影响：提取差异来自**规则**（作用在 Markdown 上），不来自**内容** → 共享 Markdown 完全够用。
- **F3 产物只存一份、N 份副本共享引用**：最省，但破坏「产物与源同路径」的现有派生约定。

> **请裁决：F1 还是 F2。**
> 我建议 **F2**。注意这**提高了 A1 的优先级** —— 没有服务端复制能力，F2 只能退化成 `RenameAsync` 那样的内存缓冲复制。

|---|---|
| 旧 DDL `ent_enterprise_file` | 有 `current_version int DEFAULT 1` ✅ |
| 旧 DDL `ent_file_version` | 有 `version_number` + `storage_path` + `uk(file_code, version_number)` ✅ |
| 旧上传服务 `EnterpriseFileService.cs:57` | 路径生成传的是**原始 `fileName`，无版本** ❌ |

| 旧前端 `vol.web` | **零处**文件版本逻辑 ❌ |

→ 若你选 **C2**（版本只进 DB），**必须同时改路径生成**，否则重演。
