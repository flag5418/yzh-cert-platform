> 方法：逐行对比老项目（`src/old/server/Vue.NetCore/vol.api/`，已测试通过的完整逻辑）与新实现（`src/certplatform-api/` + `src/yzh-core/YZH.Core.Web`），按新架构分层方式给出可执行的修复清单。

## 一、结论摘要（先看这个）

新实现**骨架完整但业务逻辑不完整**：控制器路由/方法签名基本对齐，但服务层缺失了大量老项目已验证的关键业务规则。按严重程度排序：

| 级别 | 问题 | 后果 |
|:----:|------|------|
| 🔴 P0 | **目标路径生成错误**：`UploadConfirmAsync` 用 `GenerateConvertedStoragePath("","","","",f.FileName)` 传空参数 | 转换目标路径不含 org/std/phase/folder 段，与老项目 `/xxx/.converted/{name}.docx` 规则完全不符；转换完成后 `ConvertedStoragePath` 指向错误对象 |
| 🔴 P0 | **缺少失败转换重试**：老项目 `RetryFailedConversionsAsync`（约 150 行）未迁移，`QueueController` 里被注释的 `file-convert/retry-failed` 端点在新项目也没承接 | 转换失败后用户永远无法恢复，只能改数据库 |
| 🔴 P0 | **队列 ScopeKey 语义不一致**：老项目 `"{orgCode}|{standardCode}|{phaseCode}"` 且 `GetQueueLockError` 用同 key 匹配；新实现 `CreateQueue` 用 `DirectoryCode`、查询也用 `DirectoryCode`，但队列创建时**没有把 DIR + 每个 FILE 都加资源锁**（只加了 DIR），文件级互斥失效 | 文件锁检查（`GetFileLockErrorAsync`）永远查不到锁 → 删除/替换正在转换的文件不会被阻止 |
| 🔴 P0 | **转换流程状态机不完整**：新 `OfficeConvertService` 是骨架（`PerformConversion` 返回原文件），老项目 `XlsToXlsxConverter`（NPOI 226 行）+ `DocToDocxConverter`（LibreOffice 249 行）完全未迁移；`OnTaskStateChangedAsync` 只记日志，不联动文件可见性/失败原因 | doc/xls 上传后"转换"实际没发生，`ConvertStatus` 可能停在 `converting`，文件永久隐藏 |
| 🟠 P1 | **取消语义错误**：新 `UploadQueueCancelHandler` 只把文件置 `IsValid=1 + ConvertStatus=failed`；老项目语义是"**彻底清理本次上传**（DB 记录 + MinIO 对象，create 删除/replace 恢复）" | 取消转换队列后残留大量半可见孤儿文件与 MinIO 垃圾对象 |
| 🟠 P1 | **UpdateFolder 不改 MinIO/子项**：新实现只改 `FolderName`；老项目经 `FolderFileManager.RenameFolderAsync`（525 行）级联更新所有后代文件夹 FullPath、所有文件 FullPath/StoragePath 并同步 MinIO 路径 | 重命名后 DB 与 MinIO 实际存储脱节，后续下载 404 |
| 🟠 P1 | **模板管理服务被简化**：新 `DirectoryTemplateService` 没有 `FileRequirement`（文件要求）支持，没有 `GetFileRequirements/SaveFileRequirement/DeleteFileRequirement`，模板文件路径用 `templates/{configCode}/{fileName}` 而非 V3 路径；删除文件夹不级联删 requirements 与 MinIO 模板文件 | 目录模板模块功能缺失约 60%，老前端 `fileRequirements` 系列接口无对应实现 |
| 🟠 P1 | **DB 字段不存在**：实体/service 大量使用 `Enable`（bool）+ `x.Enable == true`，但 DDL 已把 `enable` 重命名为 `IsValid`（`unify_audit_columns_V1*.sql`），`cert_standard_directory_file/folder/config` 均无 `Enable` 列 | 运行时 SqlSugar 查询 `Unknown column 'Enable'`，**所有列表/树查询直接报错**（除非本地库未跑迁移脚本，需实测确认） |
| 🟠 P1 | **全局过滤与上传流程冲突**：`SqlSugarDbOrm` 的 `GetOneAsync/GetListAsync` 自动追加 `IsDeleted=0 AND IsValid=1`；上传预创建记录 `IsValid=0`，新代码在 `UploadCancelAsync/GetUploadStatusAsync` 中用 `GetListAsync(x => x.TaskId == taskId)` 查询 | **取消/状态查询永远查不到正在上传中的文件**（IsValid=0 被过滤），回滚失效、状态查询返回空 |
| 🟡 P2 | 组织树关联字段对不上：新代码 `orgStandards.Where(x.OrgCode == org.Code).Select(x => x.StandardCode)` 但 `ISOStandard.Code` 才是关联键（老项目 `x.StdCode` 对 `ISOStandard.Code`）；`CertOrgStage.StandardCode` 匹配 `std.Code` 正确但阶段节点缺 `children` 与排序 `SortOrder` | 树可能空/错序，阶段节点展开报错风险 |
| 🟡 P2 | 请求模型不一致：老 `upload-confirm/upload-cancel` 用 `[FromQuery] taskId`，新实现用 `[FromBody] UploadConfirmRequest`；前端 `useDirectoryApi.ts` 已按 Body 实现，需保持一致并回写文档；`convert/progress` 老项目 Body `{taskId}`，新实现 `[FromQuery]` | 前后端联调 400 |
| 🟡 P2 | 大小写/命名：新代码 SqlSugar `ColumnName = "TaskId"` 与 DDL `TaskId` 一致但库内其他列混合大小写（`convert_status` vs `IsValid`），原生 SQL（`upload-status` 等）必须逐字段核对 | 运行时 SQL 错误 |
| 🟡 P2 | 前端 API 契约缺口：`getRootFiles` 新后端存在，但老项目 `stage-files/{directoryCode}`（文档提取规则页依赖）、`directory-files`、`export ZIP`、`file-lock-status`、`codes/*`、`paths/storage` 未迁移 | V3 计划 §五 API 清单不全，P2 前端开工时会发现接口缺失 |

**总体判断**：老项目逻辑可按新架构完整移植，但当前"重新整理后的代码"是**按 API 表面清单重写的简化版**，不是老项目逻辑的忠实迁移。修复思路 = 保留新架构分层（Controller 薄 + Service + IDbOrm + IObjectStorage + QueueManager），把老项目 Service/Helper/Converter 的**业务方法体**逐个搬过来。

## 三、逐文件详细对比

### 3.1 StandardDirectoryService（2575 行 vs 1089 行）

#### 3.1.1 组织树 `GetOrganizationTree`

| 项 | 老项目 | 新实现 | 差异与修复 |
|----|--------|--------|-----------|
| 机构过滤 | `Enable == true` + `OrderBy(Id)` | `IsValid == 1`，无排序 | ✅ 语义等价（IsValid 接替 Enable）；➕ 补 `OrderBy(SortOrder/Id)` |
| 标准关联 | `orgStandards.Where(x.OrgCode == org.Code).Select(x.StdCode)` 匹配 `ISOStandard.Code` | `Select(x => x.StandardCode)` 匹配 `ISOStandard.Code` | 🔴 **字段语义错**：`CertOrgStandard.StandardCode` 存的是 `ISOStandard.Code`（外键），而节点 `id` 用 `std.StandardCode` 展示。逻辑上新实现歪打正着能查到（因为比较对象是 `std.Code`），但变量名误导。**修复：改回 `Select(x => x.StandardCode)` 比较 `std.Code`，节点 id 保持 `org.Code|std.StandardCode`，与老项目一致** |

#### 3.1.5 上传 4 步（核心！）

**Step1 UploadInit：**

| 项 | 老项目 | 新实现 | 修复 |
|----|--------|--------|------|
| 自动建配置 | 从 DirectoryCode 解析 std/phase → 自动创建 config | 同（`ParseDirectoryCode`）✅ | 一致 |
| 队列互斥 | `GetQueueLockErrorAsync(directoryCode, orgCode)` → ScopeKey=`{org}|{std}|{phase}` 查运行队列 | `GetQueueLockErrorAsync(directoryCode)` → `FindRunningQueueByScopeKeyAsync(directoryCode)` | 🔴 **二选一统一**：建议保持老项目 scopeKey 三段式（`{orgCode}|{stdCode}|{phaseCode}`），因为队列监控页/日志可读；若嫌解析麻烦，可全链路统一用 DirectoryCode，**但必须前后一致**。当前实现建队用 DirectoryCode ✅ 查询也用 DirectoryCode ✅，其实自洽 —— 真正的问题是**老项目在锁检查上还会加 DIR 资源锁**，新实现没有 |

| 机构解析 | `ResolveOrgCodeAsync`：前端 cbCode → 存储路径推导 → 登录用户机构，三级兜底 | ❌ **完全没有 orgCode 解析**，`GenerateStandardDirectoryPath(manifest.OrgCode, ...)` 直接用 manifest（可能为空）→ 路径变成 `/standard-directory//ISO.../...` | 🔴 **移植 `ResolveOrgCodeAsync` + `DeriveOrgCodeFromPath` + `GetCurrentOrgCodeAsync`（映射 IUserContext）**，空 orgCode 时报错"无法确定机构信息" |
| 文件类型校验 | `ValidateUploadFileType`：白名单（pdf/doc/docx/xls/xlsx/ppt/pptx/txt/rtf + 8 种图片）+ 隐藏文件过滤，命中**跳过该文件** | 只有 `IgnoredFileExtensions` 黑名单（.DS_Store 等 3 项） | 🔴 移植白名单 `_allowedUploadExts` + `ValidateUploadFileType`（老项目防绕过方案） |
| 根目录文件归属 | 无文件夹时挂到第一个根文件夹，再兜底挂 `DirectoryCode` | `folderCode = ""`（空字符串） | 🟠 移植两级兜底，否则 MinIO 路径少一级、前端展示异常 |
| replace 模式 | `UploadStatus=replacing` + Remark 标记 `[upload-replace:{taskId}]` + **不创建新记录** + StoragePath 按新约定重新生成 + `MarkModified` | 结构一致 ✅ 但新实现同时改了 `existingFile.StoragePath` 又存 `OldStoragePath` 在响应 DTO 里（DB 不落），且 UploadFile 阶段"简化处理：不做旧路径删除，由 confirm 统一处理"——confirm 里也没删 | 🟠 按老项目：`UploadFileWithTask` 上传成功后**若新旧路径不同则删旧对象**（新实现 confirm/cancel 都没删，MinIO 会积累旧对象） |
| doc/xls 预标记 | create 模式预创建时 `ConvertStatus="pending"` | ❌ 未标记 | 🟠 补（CleanupOrphanData 依赖该语义防清不掉） |
| 任务记录 | Creator = UserContext.Current?.UserName | 无 Creator | 🟡 从 IUserContext 取 |
| 过滤后空批次 | 明确错误"没有可上传的有效文件（文件均被过滤）" | "没有有效的文件需要上传" | ✅ 等价 |
