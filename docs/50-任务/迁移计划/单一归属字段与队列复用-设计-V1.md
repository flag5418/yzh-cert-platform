### 1.4 ★★ 暴露的现存静默失效（比重复更严重）

`StandardDirectoryService.cs:1047-1049` 的注释写着：

> 「**模板行的标识是 `YZH-STD-ENT` 而不是空串**：库里有 23 行历史遗留的 `EnterpriseCode = ''`（全部 `StandardFileCode` 为 NULL），**属于脏数据，不纳入选项**。真正的模板行 168 行全部是 `YZH-STD-ENT`。」

**但实测（2026-10-12 当前库）：**
- `cert_standard_directory_file` 总行数 = **23**
- 这 23 行 `EnterpriseCode` **全是空串 `''`**
- `EnterpriseCode = 'YZH-STD-ENT'` = **0 行**

⇒ **按代码自己的口径，现在这 23 行「全是脏数据」** ⇒ `GetTemplateFilesAsync()`
（`x.EnterpriseCode == YzhVirtualEnterprise.Code && x.IsValid == 1`）**恒返回 0 行**。

**连带影响**：所有依赖「模板行」的功能（目录模板选项、标准文档生成的前置、`ExtractionScopeResolver` 的四元组定位）**全部取不到输入**，且**不报错**（返回空列表）。

> ⚠️ 这与 `cert_doc_template` 全表 0 行是**两个独立的阻断**，但症状一样：**功能静默无输出**。
> ⚠️ 归因：`168 行 YZH-STD-ENT 模板行` 属于已删除的 iso9001 数据（本轮「只保留 iso13485」清理），
> 而保留的 23 行 iso13485 文件是 `EnterpriseCode=''` 形态 ⇒ **清理后该口径彻底落空**。

> **⚠️ 2026-10-12 修正（本节两处判断有误，见 §1.7）**
> 1. 那 23 行**不是「脏数据」** —— 它们是**认证机构的标准目录行**（有真实 `StoragePath`、物理路径
>    `/standard-directory/{机构Code}/…`，例：尚龙 `XASL-QD-001 工作环境管理制度.doc`）。
> 2. 「`GetTemplateFilesAsync` 恒返回 0 行」的根因是**模板行数据尚未建立**，
>    ⛔ **不是判据写错** —— 换成新判据（`OrgCode`/`EnterpriseCode = CoreOrgCodes.StdEnv`）后**仍为 0 行**，
>    且这是**正确**的（库里确实一行模板行都没有）。
> ⇒ 本节标题里的「静默失效（判据 bug）」定性**作废**，正确表述是「**模板行数据缺口**」。

### 1.5 两个方案 + 白话说明书

#### 方案 A（★ 推荐）：`OrgCode` 唯一判据，`EnterpriseCode` 收窄为企业指针

**白话**：让「这行是后台的还是企业的」**只看一个字段** —— `OrgCode`。后台的写 `yzh-std-env`，企业的写企业编码。
`EnterpriseCode` 这个列**保留**，但只回答「这是哪家企业的」这一个问题，**不再兼任「是不是模板行」**。

| 项 | 内容 |
|---|---|
| 保留常量 | **`CoreOrgCodes.StdEnv`** = `yzh-std-env` |
| 删除常量 | **`YzhVirtualEnterprise`**（`YZH-STD-ENT`）—— 31 处引用改判据 |
| 判据函数 | `OrgScope.IsBackendBuilt(OrgCode)`（已存在，已注册） |

| 与既有裁决 | ✅ **完全一致**（10-12「`OrgCode` 判据铁律」已落地 199 行，守卫 A-R8/A-R9 已就位） |
| 风险 | **低** |

#### 方案 B：`EnterpriseCode` 唯一判据，`OrgCode` 收窄为租户指针

| 项 | 内容 |

| 删除常量 | `CoreOrgCodes` |

| 风险 | **高** |

**⇒ 推荐 A**，三条理由：
1. **数据已经站在 A 这边**：156 行后台标记已在 `OrgCode` 上；`EnterpriseCode` 是 0 行空列。
2. **A 不推翻任何既有裁决**，B 要推翻 10-12 刚做完的 199 行迁移 + 两个守卫。
3. **A 的语义更干净**：`OrgCode` 天然是「归属」维度（后台/机构/专家/企业都能表达），

## 二 事项 2：队列复用（用户点 2）

### 2.1 用户意图（复述确认）

> 「第一次建立规则检查的时候，就考虑就是希望**测试也采用和专家端一样的逻辑和队列**，就是为了在测试的时候，发现是否存在问题。
> 一旦规则的流程跑通了，我们专家端执行的时候，也是**按 NC 检查项或章节进行最小队列组织**，最大限度的进行逻辑复用，减少不必要的重复代码，降低系统稳定性（风险）。」

**⇒ 核心诉求三条：**
1. **测试 = 专家端的同一套队列 + 同一套执行逻辑**（不是「长得像」，是**同一套**）—— 目的是让测试暴露的是**真实链路**的问题
2. **最小队列单元 = NC 检查项 / 章节**（不是「整个任务一个大队列」）
3. **复用优先于隔离** —— 宁可让 Shared 承载更多，也不要两套并行

### 2.2 两套队列表结构差异（实测，方案 C 的输入）

| 维度 | 框架 `yzh_queue` + `yzh_queue_task` + `yzh_queue_resource_lock` | 专家 `cert_expert_task_queue` + `_item` |
|---|---|---|
| 层级 | **队列 → 任务**（两级） | **队列 → 明细项**（两级） |
| 主表定位键 | `QueueCode` / `ScopeKey` / `SourceType`+`SourceId` | `TaskCode` / `SubTaskCode` / `StandardCode` / `ScopeKey` |
| 主表计数 | `TotalCount`/`PendingCount`/`ProcessingCount`/`CompletedCount`/`FailedCount`/`CancelledCount` | `TotalCount`/`DoneCount`/`FailedCount`/**`SkippedCount`** |
| 主表进度 | `Progress` **int** | `Progress` **decimal(5,2)** |
| 主表重试/锁 | ❌ 无 | `Priority` · `LockCode` · `LockedUntil` · `RetryCount` · `MaxRetryCount` · `LastError` |
| 明细定位 | `TaskType` + `Payload(text)` | `ItemType` + **`ItemCode`** + **`Seq`** + `Payload(json)` + **`ExtractVersionStamp`** |
| 明细重试/锁 | `RetryCount` · `MaxRetryCount` · `NextRetryAt` · `LockedUntil`/`LockedBy`/`LockedAt` · `LockCodes` · `Priority` | 同左（+`LockCode`） |
| 明细外键 | ❌ 无 `WorkflowExecTaskCode` | **`WorkflowExecTaskCode`** |
| 资源锁 | **独立表** `yzh_queue_resource_lock`（`ResourceTable`+`ResourceCode`+`ActiveKey`） | 无（靠 `LockCode`） |

**⇒ 框架队列缺的 6 类（方案 C 必须补）**：

| # | 缺什么 | 为什么要 |
|---|---|---|
| 1 | 主表 `SkippedCount` | 「跳过」与「失败」必须分开（用户明确：跳过 ≠ 失败） |
| 2 | 主表 `Priority` / `RetryCount` / `MaxRetryCount` / `LockCode` / `LockedUntil` / `LastError` | 队列级抢占与整体重试 |
| 3 | 明细 `ItemCode`（业务实体 Code） | 「最小队列单元 = NC 检查项 / 章节」需要**指向具体业务对象** |
| 4 | 明细 `Seq` | 明细顺序稳定（章节天然有序） |
| 5 | 明细 `ExtractVersionStamp` | 提取结果版本戳（结果变了要重跑） |
| 6 | 明细 `WorkflowExecTaskCode` | 与工作流执行留痕对齐 |

> ⚠️ `Payload` 类型差异：框架是 `text`，专家是 `json` ⇒ 若统一用 `json`，需确认历史 `text` 数据兼容（当前两表 **均 0 行** ⇒ **无兼容负担**）。

### 2.3 最小队列组织（用户点 2 的落地形态）

**现状**：专家端是「任务 → 队列」，队列粒度较粗。

**目标**（用户裁决）：
```
专家任务（cert_expert_task，TaskType = NC_CHECK / REPORT_GENERATE / DOC_NORMALIZE）
   └── 队列（yzh_queue，ScopeKey = entnorm:{企业}:{阶段} 或 nc:{企业}:{检查项Code}）
         └── 明细（yzh_queue_task，ItemType = NC_ITEM / CLAUSE，ItemCode = 检查项 Code / 章节 Code）
```

**★ 关键收益**：粒度到「NC 检查项 / 章节」后 ——
1. **可续跑**：只重跑失败的那几个检查项，不用整任务重来
2. **可并行**：不同检查项之间无依赖，可多 worker
3. **测试即生产**：后台测试跑的就是这条链，专家端跑的还是这条链 ⇒ 测试发现的问题 100% 是真问题
4. **一处修、两端好**：执行逻辑（`IWorkflowRunner` 已在 Shared）只有一份
