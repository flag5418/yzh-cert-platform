## 二、MinIO 存储结构分析

### 2.1 Bucket 与路径规则

```
Bucket: cert-platform（appsettings.json → MinIO:BucketName）

V3 路径格式（当前生产）：
/standard-directory/{OrgCode}/{StandardCode}/{PhaseCode}/{FolderPath}/{FileName}

示例：
/standard-directory/CB001/ISO134852016/STAGE01/质量手册/程序文件.docx
/standard-directory/CB001/ISO134852016/STAGE01/质量手册/.converted/程序文件.docx
```

### 2.2 路径生成规则

| 组件 | 清洗规则 | 示例 |
|------|---------|------|
| OrgCode | 去掉 `:-空格/\` | `CB-001` → `CB001` |
| StandardCode | 去掉 `:-空格/\` | `ISO13485:2016` → `ISO134852016` |
| PhaseCode | 去掉 `:-空格/\` | `STAGE-01` → `STAGE01` |
| FolderPath | 仅替换 `\|` → `-`，去掉首尾 `/` | `质量手册\|子目录` → `质量手册-子目录` |
| FileName | 去掉路径分隔符 `/\\` | `my/file.pdf` → `myfile.pdf` |

### 2.3 转换文件路径

```
源文件: /standard-directory/CB001/ISO134852016/STAGE01/质量手册/程序文件.doc
转换后: /standard-directory/CB001/ISO134852016/STAGE01/质量手册/.converted/程序文件.docx
                                                          ^^^^^^^^^
                                                          隐藏子目录
```

### 2.4 文件夹在 MinIO 中的表现

MinIO 中**文件夹是虚拟的**——不存在显式的文件夹对象。文件夹由对象键中的 `/` 分隔符隐式创建。

例如上传 `standard-directory/CB001/ISO134852016/STAGE01/doc.pdf` 时，MinIO 自动创建 `CB001/`、`ISO134852016/`、`STAGE01/` 等"目录"。

**文件夹元数据存储在数据库** `cert_standard_directory_folder` 表中：
- `ParentCode`: 父文件夹编码
- `Depth`: 层级深度
- `FullPath`: 人类可读路径（如 `质量手册/程序文件`）

### 2.5 上传流程（4 步）

```
┌─────────────────────────────────────────────────────────────┐
│ 1. UploadInit（预初始化）                                    │
│    POST /api/standard-directory/upload-init                  │
│    输入: directoryCode, fileList[{folderName,fileName,...}]  │
│    处理: 生成 StoragePath, 创建 DB 记录(IsValid=false)       │
│    输出: taskId, fileList[+fileCode, +storagePath]          │
├─────────────────────────────────────────────────────────────┤
│ 2. UploadFileV2（逐文件上传）                                │
│    POST /api/standard-directory/upload-file-v2               │
│    输入: file(multipart), fileCode, taskId                  │
│    处理: 从 DB 读 StoragePath → 上传 MinIO                   │
│    输出: {ok}                                               │
├─────────────────────────────────────────────────────────────┤
│ 3. UploadConfirm（确认激活）                                  │
│    POST /api/standard-directory/upload-confirm?taskId=xxx   │
│    处理: IsValid=true, 扫描 .doc/.xls → 创建转换队列         │
│    输出: {ok, convertTaskId?}                               │
├─────────────────────────────────────────────────────────────┤
│ 4. UploadCancel（回滚）                                      │
│    POST /api/standard-directory/upload-cancel?taskId=xxx    │
│    处理: 删除 DB 记录 + MinIO 对象, 恢复被替换文件            │
│    输出: {ok}                                               │
└─────────────────────────────────────────────────────────────┘
```

### 2.6 Content-Type 映射

| 文件类型 | Content-Type |
|---------|-------------|
| 默认 | `application/octet-stream` |
| .docx | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| .xlsx | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| .pdf | `application/pdf` |
| .jpg/.jpeg | `image/jpeg` |
| .png | `image/png` |

## 三、AI 分析功能分析

### 3.1 功能说明

在文件列表中点击「AI 分析」按钮，弹出对话框：
1. 选择提示词模板（从 `wf_prompt_template` 表加载）
2. 点击「开始分析」
3. 后端下载文件 → 提取内容 → 调用 LLM → 返回结构化结果

### 3.2 API 调用

```
POST /api/DocExtractionRule/analyze
Body: { "fileCode": "FL-xxx", "templateId": "xxx" }

返回: {
  "success": true,
  "data": {
    "fields": [{ "name": "企业名称", "code": "companyName", "type": "string", ... }],
    "tables": [{ "name": "员工花名册", "code": "employeeRoster", "columns": [...], ... }]
  }
}
```

### 3.3 处理流程

```
文件 → MinIO 下载 → IFileExtractor 提取内容(Sections+Tables+FullText)
    → 构建 Prompt(模板 or 默认) → WorkflowEngine 调用 LLM
    → 解析结果 → 返回 FieldDefDto[] + TableDefDto[]
```

### 3.4 默认 Prompt 模板

```
你是专业的文档分析助手。请分析以下{Word/Excel/PDF}的内容结构，
推荐需要提取的字段和表格。

输出要求：
1. fields: 数组，每项含 field_code（英文驼峰）、field_name（中文名称）、
   field_type（string/number/date）、description
2. tables: 数组，每项含 table_code、table_name、description、columns

规则：
- 表格内的内容禁止作为 fields 提取
- fields 只从普通段落中提取
- 字段名称必须与文档中的实际标签一致
```

### 3.5 AI 功能依赖

| 依赖 | 说明 |
|------|------|
| `IFileExtractor` | 文档内容提取（PDF/Word/Excel → 结构化文本） |
| `WorkflowEngine` | LLM 调用引擎（`llm_extract` skill） |
| `cert_sys_config.ai_model_name` | LLM 模型名（默认 `qwen-turbo`） |
| `wf_prompt_template` | 提示词模板表 |

### 3.6 建议：AI 功能分阶段实施

| 阶段 | 范围 | 说明 |
|------|------|------|
| **Phase 1** | 文件管理核心 | 上传/下载/文件夹/转换（不含 AI） |
| **Phase 2** | 队列监控 | 转换进度/取消/重试 |
| **Phase 3** | AI 分析 | 需要 IFileExtractor + WorkflowEngine，独立模块 |

**本次实施范围：Phase 1 + Phase 2（不含 AI 分析）**
