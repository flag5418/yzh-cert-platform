## 二、★ 严重问题 1（最严重）：缺少「审核对象 / 过程 / 部门」维度

### 为什么这是"严重不符合体系认证规则"

**规范事实：体系审核是「按部门/过程」审的，不是「按条款」审的。**

> 规范原文：「三体系整合审核，可以按**同一作业活动**同时查三套证据：比如**焊接工序**，查工艺参数（9001）、烟尘排放（14001）、防护用品和职业健康监测（45001）。」

→ **审核员到现场去的是「生产部」「采购部」「人力资源部」，不是「7.5 条款」。**

**实测确认：你的库里没有任何「过程 / 部门 / 审核对象」表。**

### 影响（关键：**即使单标准也致命**）

- 检查表若只能**按条款编号**输出 → 审核员拿到"300 条按 7.1/7.2/7.5 排的清单"，**在现场没法用**
- 多标准时，**部门是天然的合并点**（同一个部门一次访谈覆盖三标准）→ 有过程维度，整合是**顺带**的
- ★ **这比"没整合"更可能是"审核员不认可"的真正原因** → 见 §五

## 三、★ 严重问题 2：标准目录表「要求」与「实例」混在一起

`cert_standard_directory_folder` / `cert_standard_directory_file` **同一张表既有要求又有实例**：

| 类别 | 现有列 |
|---|---|
| 要求定义 | `FilePattern` `IsRequired` `MaxFileSizeMB` `ExtractionEnabled` `ExtractionRules` `PreCheckRequired` `ComplianceRequired` `FolderName` `Depth` `SortOrder` |
| 上传实例 | `TaskId` `UploadStatus` `StoragePath` `FullPath` `ConvertStatus` `ConvertMessage` `PreviewPdfPath` `MarkdownPath` `MarkdownStatus` `FileName` `FileSize` |

**后果**：后台改一次标准目录 → **波及所有企业已上传记录**。
**补正**：拆 **要求侧**（按 标准+阶段，全企业共用）/ **实例侧**（按 企业+阶段）。

---

## 四、★ 严重问题 3：缺「版本管理」

| 对象 | 会变什么 | 后果 |
|---|---|---|
| 标准 | 9001:2015 → 9001:2026，条款会变 | **老企业按 2015 版发证，审核还要按 2015 版** → 无法复现 |
| 规则 / 报告模板 | 会迭代 | **改了规则，去年的报告就重算不出来** |

**实测**：`cert_validation_rule` 有 `IsActive` **无 `Version`**；`rpt_report_section` 有 `IsActive` **无 `Version`**。
**补正**：加 `Version` + `EffectiveDate`，或建规则快照表。

## 五、★ 严重问题 4：报告结构用「自由流程引擎」定义 —— 有合规风险

**实测**：`rpt_report_section` 有 `WorkflowCode` + `WorkflowConfig` + `LayoutJson` + `SectionJson`。

**风险**：**报告是规范性文件**（认证机构的报告格式有 CNAS 等要求）。**用自由流程引擎生成，产出的报告可能不符合规范格式。**

**补正建议**：
- **报告 = 固定骨架模板 + 数据填充**
- **流程引擎只用于「判定逻辑 / 取数逻辑」，不用于「排版结构」**

## 六、两处需要精确化的措辞

### 6.1 NC：「检查项」vs「规则」是两件事，但你只建了「规则」

| | 定义 | 谁看 | 实测 |
|---|---|---|---|
| **检查项 CheckItem** | 一个**可判定的问题**（"是否建立了文件控制程序？"） | **审核员（人）** | ❌ **表不存在** |
| **检查规则 Rule** | **判定逻辑**（"程序应含 A/B/C 三要素，缺则不符合"） | **引擎（机器）** | ✅ `cert_validation_rule` |

**你把它们分成两项是对的**，但实测 **只有「规则」表，没有「检查项」表**。
现状 `cert_validation_rule` 一个表同时装 `RuleJson`（判定逻辑）和 `NcDescriptionTemplate`（描述）→ **两类东西混在一起了**。

### 6.2 报告：「内容」vs「规则」—— ★ 这一块你的设计其实已经对了

| | 定义 | 实测 |
|---|---|---|
| **报告内容 Section** | **章节结构**（有哪些章节、写什么） | ✅ `rpt_report_section`（`SectionName` / `SectionContent` / `LayoutJson`） |
| **报告规则 Rule** | **每个章节的数据从哪来** | ✅ `rpt_report_section_source` |

**★★ 好消息**：`rpt_report_section_source.SourceType` 的枚举是
**`extraction` / `finding` / `nc` / `manual` / `template` / `compliance`**

→ **一个章节可以挂多个数据来源** → **这天然就是「一体化报告」的基础**。
→ 缺的只是**按标准分列**用的 `StandardCode`（或经 `ClauseCode` 反查）。

| # | 缺什么 | 为什么必须有 | 优先级 |
|---|---|---|---|
| 1 | **审核对象/过程/部门表** | 检查表按部门分组输出（**即使单标准也需要**） | ★★★ 最高 |

# 第二部分：分标准形态对审核员有价值吗？

## 八、诚实答案：**有部分价值，作为第一步是对的；但"不认可"的风险不在"没整合"**

### 8.1 三种形态的价值对照

| 形态 | 审核员现场作业 | 客户交付 | 认证决定 | 开发成本 |
|---|---|---|---|---|
| **逐标准 NC 罗列** | ✅ **够用**（本来就按标准分工） | ⚠️ 一般 | ⚠️ 一般 | **极低** |
| **逐标准报告** | ✅ 够用 | ⚠️ 客户可能嫌碎 | ⚠️ | **极低** |
| **一体化报告** | ⚠️ **现场反而用不上** | ✅ 好 | ✅ 好 | **中** |

### 8.2 四条关键判断

**★ 判断 1：单标准认证是市场主流。**
大量中小企业只做 ISO 9001 → 对这些客户，**"逐标准"就是"一个报告"，不存在整合问题**。
→ **不需要为少数多标准客户，牺牲多数单标准客户的开发进度。**

**★ 判断 2：即使是多标准一体化，"分标准"在实践中也常见。**
- 审核组内部**本来就按标准分工**（每个审核员负责一个标准）
- 认证机构出报告常有 **"一份总报告 + 三个标准分报告"** 的形态
→ **"逐标准"不是错误，是"降级但可用"。**

**★★★ 判断 3（这才是关键）：审核员"不认可"的最可能原因，不是"没整合"，而是这四条 ——**

| # | 问题 | 与多标准有关吗 |
|---|---|---|
| 1 | **检查表不能按部门/过程分组**（§二） | ❌ 无关（**单标准也不可用**） |
| 2 | **只有判定逻辑，没有"问题描述"**（缺检查项表，§6.1） | ❌ 无关 |
| 3 | **没有审核方法 / 抽样要求**（问/查/看、抽几个） | ❌ 无关 |
| 4 | **没有证据记录位置**（现场记录、照片、文件号） | ❌ 无关 |

→ **这四条补齐，单标准检查表就已经能用了。** 而它们**和"多标准整合"完全无关**。

**★ 判断 4：整合的难度被高估了。**
- **报告侧**：`rpt_report_section_source` 已支持"章节 ← 多来源" → **天然是一体化基础**
- **NC 侧**：只需给 `audit_nonconformity` 加 `StandardCode`
- **真正的成本在「后台配置工作量」**（专家配映射表 + 报告模板按 HLS 重做），**不在「系统改造」**
→ **"整合需要全系统大改"这个担心，实测下来不成立。**

### 8.3 ★ 但有一个真会卡住的地方：**"整合报告格式"能否标准化**

- 每家认证机构的报告格式不同（有各自模板）
- **要通用 → 必须做成「配置」（模板 + 映射表），不是「开发」**
- 若要给每家机构"量身定制" → **按次收费就不成立**（定制成本摊不平）

# 第三部分：商业可行性评估

## 九、★★★ 你的判断是对的：散乱文档自动结构化，商业价值最高

| 维度 | 报告整合 | **散乱文档自动整理** |
|---|---|---|
| 客户痛点强度 | 中（机构自己也能凑） | **高**（企业/咨询顾问的真实痛点） |
| 是否依赖规范格式 | ✅ **强依赖**（CNAS 格式要求） | ❌ **不依赖**（像样就行） |
| 能否标准化 | ⚠️ **难**（每家机构不同） | ✅ **能**（文档类型是通用的） |
| 可复用性 | 中 | **高**（"文档类型 → 标准要求"映射复用） |
| 是否省人力 | 中 | **高**（替代体系专员/咨询顾问的整理工作） |

### ★★ 关键：它和"多标准合并"是同一件事的两面

- **多标准合并** = **要求侧**去重（9001 的营业执照 = 14001 的营业执照）
- **散乱文档整理** = **企业侧**归类（这堆文件里哪个是"营业执照"）
- → **两个都需要「文档类型映射表」** → **建一次，两处受益**

> **★★★ 本轮最关键结论：你要建的那张映射表，做「文档整理」比做「报告整合」回报高得多。**

## 十、按次收费的可行性

- **可行**，但 **按次收费 → 客单价低 → 必须走量 → 必须降低实施成本**
- **"能否标准化"是生死线**：
  - 标准化程度高 → 实施成本低 → **按次收费成立** ✅
  - 每家都要专家定制 → 实施成本高 → **按次收费不成立** ❌
- → **这恰好论证了"先做逐标准、不做深度整合"是对的**：**逐标准 = 可标准化；整合 = 难标准化**

## 十一、明确回答「能否继续往下进行」

| 判断项 | 结论 |
|---|---|
| 逐标准 NC + 逐标准报告，**系统改造量** | ✅ **极小**（加 1 个 `StandardCode`；报告模板本就按标准建） |
| 逐标准形态**能否收钱** | ✅ **能**，尤其单标准客户 |
| 一体化整合的**系统改造量** | ✅ **中**（报告侧已具备基础；主要是后台配置工作量） |
| 一体化整合**能否通用化** | ⚠️ **难**（每家机构报告格式不同）→ **必须做成"配置"** |
| **散乱文档自动整理** | ✅ **价值最高**，且与映射表复用 |
| **按次收费** | ✅ 可行，**前提是标准化程度够高** |

> **总判断：可以继续。而且"先逐标准、不做整合"的路线是对的，不是妥协。**

# 第四部分：现在做什么 / 什么延后 / 为什么

## 现在做

| # | 事项 | 理由 |
|---|---|---|
| 1 | **补「审核对象/过程/部门」维度** | 检查表按部门分组输出 —— **即使单标准也需要**，这是审核员认可与否的关键 |
| 2 | **把「检查项」从「规则」里拆出来**（问题描述 + 审核方法 + 抽样要求） | 审核员看的是"问题"，不是"判定逻辑" |
| 3 | **拆 `cert_standard_directory_*`** 要求/实例 | **0 行时拆 = 改 DDL**；有数据后成本 ×10 |
| 4 | **给 `audit_nonconformity` 加 `StandardCode`** | 分标准罗列的前提（分标准是当前路线） |
| 5 | **逐标准跑通 NC + 报告** | 能交付、能收钱 |

## 延后

| 项 | 为什么 |
|---|---|
| **条款映射表**（多标准合并） | 等客户明确要求再做；**且做成配置不是开发** |
| **一体化报告整合** | 报告侧已有基础，成本在配置不在代码 |
| **报告按 HLS 骨架重做** | 同上 |

## 为什么这么排

1. **检查表不能按部门分组 → 单标准也不可用**（最致命，且与多标准无关）
2. **拆表 / 加列都是 0 行时的操作**，成本最低
3. **逐标准能立刻收钱**；整合是加分项，且**难度在配置不在代码**
4. **散乱文档整理的映射表同时服务两个方向** → 优先建
