# 业务代码不合规清单 V1

> **用户原话**：「当前在执行的时候，**可以直接针对不合理的架构进行调整，但业务未按架构进行设计的，可以形成清单**，因为我是**多 ai 共同执行**，而且现在项目开始分工了，**计划一个 ai 专门负责后台管理的测试和完善，另一个 ai 开始全力以赴实现专家系统，互补矛盾**」
>
> **本文按「谁能做」二分**：
> - **A 类｜架构调整** —— 与业务无关、判据客观、**可直接做，不需用户决策**
> - **B 类｜业务不合规清单** —— 需要业务知识/交互判断，**形成清单交分工 AI**
>
> **配套**：`21-项目结构设计规范-V1.md`（结构权威）｜`命名规范违规清单与消灭方案-V1.md`（DB 命名）｜`18-YZH架构规则-V1.md`（规则总集）

## 〇、一页纸

| 分类 | 数量 | 谁做 | 依据 |
|---|---|---|---|
| **A 架构调整** | **11 项** | 单一负责人（可直接做） | 客观判据，无业务判断 |
| **B 业务不合规** | **前端 12 个页面** + **后端 13 个控制器** | 分工 AI（按端归属） | 需业务知识 / 交互设计 |
| **C 职能特殊（允许）** | 6 个页面 | 无需改，**登记即可** | 非 CRUD 页面，基类不适用 |
| **D 未开工（不是违规）** | 5 个占位页 | AI-B 实现时按样板写 | `CertPagePlaceholder` |

**★ 最重要的一条**：**`iso-standard/index.vue` 与 `skill-manage/index.vue` 手写了全部 CRUD —— 而 `iso-standard` 正是《样板页面指南》指定的「唯一左树右表样板」。**
→ **样板本身不合规**。这会让后续 AI「照抄样板」继续复制违规。**优先级最高**。

## 一、判据（什么算不合规）

| # | 判据 | 出处 |
|---|---|---|
| J1 | 页面有 `useSingleTable` / `useTreeTable` 内核 **或** 同目录 `logic.ts` | `样板页面指南-V1.md` |
| J2 | ⛔ 禁止手写 `handleAdd` / `handleBatchDelete` / `handleRowAction` / `handleSubmit` | `AGENTS.md` §① |
| J3 | ⛔ 禁止内联 `<el-table`（必须用 `YzhTable`） | 守卫 **R6** |
| J4 | ⛔ 禁止 `.vue` 内直接 `fetch(`；禁止 `axios` | 守卫 **R4/R5** |
| J5 | ⛔ 禁止 `view-grid` / `VolBox` / `VolForm` / `VolProvider` | `AGENTS.md` §① |
| J6 | **字段名 PascalCase 逐字一致**（DB 列 = C# 属性 = TS 字段） | **铁律七** |
| J7 | 页面不得直连 `@/api/`（应走 `@share/api` 或 core API） | 守卫 **R1**（core 层）/ 债务 A |
| J8 | 控制器按职能选基类；**裸 `ControllerBase` 允许**，但须满足行为契约（401 / `ApiResponse` 信封 / 列名 PascalCase） | `AGENTS.md` §② + 用户纠正① |

> **⚠️ 判据 J8 的注意事项（用户已明确纠正）**：**不要用「基类覆盖率」当合规指标。**
> 抽象基类只覆盖**一部分**后端形态；职能特殊的控制器直接继承 `ControllerBase` **是允许的**。
> **判断合规看行为契约，不看 `:` 后面写了什么。**

## 六、多 AI 分工纪律（★ 用户第 4 点的落地）

### 6.1 分工边界

| | **AI-A｜后台管理** | **AI-B｜专家系统** |
|---|---|---|
| **负责端** | `cert/cert-admin` | `cert/cert-auditor`（+ 未来 `cert-enterprise`） |
| **主任务** | 测试 + 完善（修 B-01/02/05–12） | **全力以赴实现专家系统**（D 类 5 页 + B-03/04） |
| **后端范围** | `CertPlatform.Admin` 控制器 | `CertPlatform.Auditor` 控制器 |
| **禁止碰** | ⛔ `cert-auditor/**` | ⛔ `cert-admin/**` |

### 6.2 ★ 冲突面：**L1 `yzh.vue.core` 与 L2 `cert-share` 是双方共用的**

> 这是**唯一的冲突面**。两边都在改 core → 互相覆盖 → **单人维护时极难排查**。

**纪律（三条）**：

| # | 纪律 |
|---|---|
| **D1** | **L1/L2 改动由单一负责人执行**（建议：AI-A 或用户本人）。AI-B **只读不写** core；确需改 → **提需求，不直接改** |
| **D2** | L1/L2 改动**必须公告 + 跑三端 build**（`npm run build:all`）+ `guards.mjs`（规则 **R-S7**） |
| **D3** | **业务页面按端分工**，互不越界（见 6.1 禁止碰） |

### 6.3 执行顺序（避免互相等待）

```
阶段 1（串行，必须先做 —— 单一负责人）
  A-01 DB 命名 + Enable 清零      ← 不先做，AI-A/AI-B 都会在错误列名上写代码
  A-02 rebuild 根因修正            ← 不做，阶段 1 成果会回退
  A-04 useAuth.ts 删除             ← 清理歧义源
  A-05 core tokens.css             ← AI-B 写专家端页面要用

阶段 2（并行，互不干扰）
  AI-A：B-01 → B-02 → B-05~B-12（后台管理修复）
  AI-B：B-03 → B-04 → D 类 5 页（专家系统实现）

阶段 3（并行）
  A-06 .env / A-07 空目录 / A-08 / A-09 / A-10（各自宿主内）
  A-11 sys_api 迁移（需重启后端验证 ApiSync）
```

## 七、交付给分工 AI 的「单页速查」
