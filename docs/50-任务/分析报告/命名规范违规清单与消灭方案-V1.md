> **本文回答 3 个问题**：① 违规到底有多少（**实测，不靠感觉**）② 为什么修了多轮还没修完（**根因**）③ 怎么一次修干净并且**不回退**

## 一、实测基线（怎么测的）

### 1.1 判定规则

```python
PASCAL = re.compile(r'^[A-Z][A-Za-z0-9]*$')   # 合规 = 首字母大写 + 后续仅字母数字
```

- **合规**：`UserName` `IsValid` `Code` `Status` `Sxh`
- **违规**：`name` `id` `status` `enable` `create_time` `EnableField`（含下划线）

### 1.2 数据来源

```bash
docker exec yzh-mysql mysql -uroot -pYzh123456. --default-character-set=utf8mb4 -N -B -e "
  SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT, EXTRA, COLUMN_COMMENT
  FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='yzh_cert_platform' ORDER BY TABLE_NAME, ORDINAL_POSITION;"
```

### 1.3 ⚠️⚠️ 一个会让「验收」永远通过的假阴性（本次踩到）

**`information_schema.COLUMN_NAME` 的排序规则是大小写不敏感（`_ci`）**，因此：

```sql
-- ⛔ 错误写法：永远返回 0 行
SELECT COUNT(*) FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA='yzh_cert_platform'
   AND COLUMN_NAME NOT REGEXP '^[A-Z][A-Za-z0-9]*$';
-- → 0（因为 'id' 里的 'i' 被 _ci 规则当成 [A-Z] 匹配上了）
```

```sql
-- ✅ 正确写法
SELECT COUNT(*) FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA='yzh_cert_platform'
   AND CONVERT(COLUMN_NAME USING utf8mb4) COLLATE utf8mb4_bin
         NOT REGEXP '^[A-Z][A-Za-z0-9]*$';
-- → 122（正确）
```

- 同理 `BINARY COLUMN_NAME` **不能**用于 `REGEXP`（报 `ERROR 3995`），但**可以**用于 `IN ('enable','Enable')` 精确比对。
- **影响面**：任何「按正则判命名」的验收脚本都会**静默通过**。本次 dry-run 第一轮就被它骗过一次（报「残留 0」实际残留 35）。
- **已写入**：`scripts/db/fix/fix-column-naming-2026-09-24.sql` 文末验证 SQL 的注释块。

> **这是「浪费一周」的一个具体机制**：改完 → 用错误 SQL 验收 → 看到 0 → 以为修好了 → 下次又踩。

### B 类｜语义冲突（**比命名更严重**）—— 25 张表 `enable` + `IsValid` 并存

**违反 R3-3 / 铁律九**（`IsValid` 是唯一启禁契约）。

| 事实 | 实测 |
|---|---|
| 小写 `enable` 列 | **27 个**（正式表 25 + 备份表 2） |
| 大写 `Enable` 列 | **20 个**（正式表 10 + 备份表 10） |
| **与 `IsValid` 并存**（可直接 DROP） | 小写 25 个全中 + 大写 `sys_config.Enable` = **26 个** |
| 无 `IsValid`（需代码/决策） | **9 个**：`sys_api`｜`sys_log`｜`Sys_TableColumn`｜`Sys_TableInfo`｜`Sys_UserDepartment`｜`Sys_WorkFlow`｜`Sys_WorkFlowStep`｜`Sys_WorkFlowTable`｜`Sys_WorkFlowTableStep` |

**为什么「并存」比「命名错」更严重**：

> 一个表里同时有 `enable` 和 `IsValid` → **两个启禁语义** →
> 后端按 `IsValid` 过滤、前端按钮按 `EnableField`（值可能是 `enable`）渲染 →
> **列表显示的行 ≠ 能操作的行**，且**两边都不报错**。
> 这是「隐蔽 bug」的另一个高发源。

**9 个无 `IsValid` 的逐一处置**：

| 表 | 实体 | 行数 | 处置 | 依据 |
|---|---|---|---|---|
| `sys_api` | `SysApi`（`SysPermission.cs:41 public bool Enable`） | **398** | **RENAME → `IsValid`** + 改代码 3 处 | **ApiSync 同步源**，`RoleApiController.cs:135` 读 `api.Enable`；实体未实现 `IIsValid` |

| `Sys_WorkFlowStep` | 无映射 | 9 | 决策 **D-E1** | Vol 遗留 |

| 项 | 为什么不是违规 |

## 四、★ 根因：为什么修了多轮还没修完（「浪费一周」的答案）

### 4.2 根因（★ 一句话）

> **`scripts/db/rebuild/rebuild_db.sh` 导入的是 `schema_before.sql` —— 一个「重建前导出的旧快照」。**
> **30+ 个修正脚本的成果从未被 rebuild 吸收 → 每次清库重建，结构被冲回旧版本。**

**证据链**：

```bash
# scripts/db/rebuild/rebuild_db.sh
echo "== 2. Import schema =="
docker exec -i yzh-mysql mysql ... "${DB}" < "${REBUILD_DIR}/schema_before.sql"   # ★ 旧快照
```

```sql
-- scripts/db/rebuild/schema_before.sql:3772（wf_skill 的 DDL，实测）
CREATE TABLE `wf_skill` (
  `id` bigint NOT NULL AUTO_INCREMENT,          -- ★ 违规
  `Code` varchar(100) ... NOT NULL,
  `SkillCode` varchar(100) ... NOT NULL,
  `name` varchar(200) ... NOT NULL,             -- ★ 违规
  `description` text,                            -- ★ 违规
  `version` varchar(20) DEFAULT '1.0',           -- ★ 违规
  `icon` varchar(50),                            -- ★ 违规
  `color` varchar(20),                           -- ★ 违规
  `remark` varchar(500),                         -- ★ 违规
  ...
  PRIMARY KEY (`id`),                            -- ★ 主键也是 id
```

→ **`schema_before.sql` 里 `wf_skill` 的 DDL 至今仍含全部 7 个违规列**。修正脚本跑得再多，重建一次就归零。

**为什么这个根因特别隐蔽**：
- 修正脚本**执行成功**（`ALTER TABLE ... OK`）→ 看到成功就以为修好了
- 当下查 DB 也**确实是 PascalCase**
- **只有下次 `rebuild_db.sh` 之后才会回退** → 时间上错开 → **归因不到重建**

### 4.3 修正方案（二选一，推荐 A）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 把 `schema_before.sql` **重命名为 `schema_pascalcase.sql` 并原地应用本次修正**，`rebuild_db.sh` 改指向新文件；旧文件归档到 `scripts/db/archive/` | **单一真相源**：重建出来的结构 = 正式结构，无「事后修补」环节 |
| B | 在 `rebuild_db.sh` 末尾追加「应用全部 `scripts/db/*snake_to_pascal*.sql`」 | 可行但脆弱：脚本会越堆越多，顺序敏感，且**新表仍可能从旧快照带出旧结构** |

**无论选哪个，必须同时做**：

1. **归档 30+ 个历史迁移脚本**到 `scripts/db/archive/2026-09/`（避免与新方案双源）
2. **删除反向脚本** `fix_yzh_columns_to_snake_case.sql`（它会把 `yzh_*` 改回 snake_case，是明确的错误方向）
3. **`rebuild_db.sh` 头部加注释**：说明「schema 文件是唯一结构来源，改结构必须改 schema 文件，不得只写 patch」
