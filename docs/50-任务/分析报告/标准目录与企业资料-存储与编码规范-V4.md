## 0. 一条原则统管全部（★ 先看这个）

> **① 所有「引用」列，一律存被引用实体的 `Code`（GUID 业务键）—— 不存人读码、不存派生复合串。**
> **② 所有「复合派生编码」（`FileCode` / `DirectoryCode` / `FolderCode`）一律删除。**
> **③ MinIO 路径中的身份段，一律取该实体的 `Code` 原文，不做 `CleanCode`。**

这三条是你第 1 条「统一口径」的完整展开，也是本方案的全部基础。

**为什么必须连 `DirectoryCode`/`FolderCode` 一起删** —— 它们和 `FileCode` 是**同一类东西**：

| 编码 | 形态 | 派生自 | 长度风险 | `\|` 分隔符 |
|---|---|---|---|---|
| `FileCode` | `FL-{FolderCode}\|{FileName}` | 文件夹 + 文件名 | — | ✅ 有 |
| `DirectoryCode` | `SDC-{Std}\|{Phase}` | 标准 + 阶段 | ★ **换 GUID 后超长** | ✅ 有 |
| `FolderCode` | `FD-{DirectoryCode}\|L{level}\|S{seq}` | 目录 + 层级 + 序号 | ★ **换 GUID 后超长** | ✅ 有 |

**★ 长度实测**：若 `DirectoryCode = SDC-{OrgCode}|{StandardCode}|{StageCode}`，三个 GUID 相加 = `4+32+1+32+1+32 = 102` 字符，而该列是 **`varchar(100)`** ⇒ **直接超长**。
⇒ **不删复合编码，就必须改列宽；删了则连列宽问题一起消失。**

## 1. 路径规范（Path Spec）

### 1.1 身份段统一取 `Code`

| 段 | 来源表 | 列 | 实测值 |
|---|---|---|---|
| `{OrgCode}` | `Sys_Organization` | **`Code`** | `66bbf57219d74e21bf164b7e42380c19` |
| `{StandardCode}` | `cert_iso_standard` | **`Code`** | `846dec4b-c534-4983-94e6-8cf04982b7d9` |
| `{StageCode}` | `cert_cert_stage` | **`Code`** | `c42582d5f95f4318a1a5548eee7ed463` |
| `{EnterpriseCode}` | `cert_enterprise` | **`Code`** | `bfa7bd00cc4b4b9c96c8a708313574ab` |

### 1.2 两库路径（2026-09-27 用户裁定终稿）

```
标准库：/standard-directory/{OrgCode}/{StandardCode}/{StageCode}/{FolderPath}/{FileName}
企业库：/enterprise-documents/{EnterpriseCode}/{StandardCode}/{StageCode}/{FolderPath}/{FileName}
```

**统一规则：首段 = 资料归属主体的 Code** —— 标准目录的归属主体是**机构**（各机构的标准落地目录模板，主表按机构隔离）；企业资料的归属主体是**企业**（`cert_enterprise` 与机构严格 1:1，`EnterpriseCode` 已隐含 `OrgCode`，无需冗余机构段，且企业全部材料聚在同一前缀下，整企业导出/清理是单前缀操作）。

- **标准库必须含 `{OrgCode}`**（决策⑳修订）：主表 uk = (OrgCode, StandardCode, StageCode)，两机构各自合法的同名文件若无机构段会算出**相同物理 key**，标准库纯覆盖语义 ⇒ 互相覆盖丢数据。
- **企业库原 `{Org}/{Std}/{Stage}/{Enterprise}` 结构作废**：企业段夹在第 4 层，一个企业的材料散落在每个标准 × 阶段组合下，无法单前缀取全。
- 按机构枚举对象走 DB（`WHERE OrgCode=?` 取配置/企业列表再拼前缀）—— 本项目无任何按前缀列举 MinIO 的代码路径。
- **段序与左树「机构 → 标准 → 阶段」同序**（标准库）；两库中段 `{StandardCode}/{StageCode}` 完全一致 ⇒ 转换链/预览链/提取链共用同一套派生实现（`Product()`/`Archive()` 从源路径派生，零改动）。

### 1.3 清洗规则（★ 与现状不同，必须改）

**现状**：`CleanCode` 会删 `-`、`:`、空格、`/`、`\`。而 GUID 含 `-`。
若对 GUID 做 `CleanCode`，路径段 = `846dec4bc534...` ≠ DB 的 `846dec4b-c534-...`
⇒ **路径段与 DB 值不可逆地不一致** —— 违反"统一口径"。

**新规则**：
```
身份段：直接取 Code 原文，只做「Trim + 去 / 和 \」最小清洗，⛔ 不删 `-`
文件夹段：取 FolderName，只做「去 / 和 \」
文件名段：原名，只做「去 / 和 \」
```
GUID 只含 `[0-9a-f-]`，天然路径安全，**不需要任何清洗**。

### 1.4 文件夹段（`{FolderPath}`）—— 需要你确认

这是唯一没有"用 `Code`"的段。两个选择：

| 选项 | 段值 | 优点 | 缺点 |
|---|---|---|---|
| **F1（建议）** | `FolderName`（人读，现状） | 路径可读，`质量手册/程序文件` 一眼看懂 | 文件夹改名 ⇒ 其下所有对象路径失配 |
| **F2** | 文件夹的 `Code`（GUID） | 完全稳定，改名零影响 | 路径完全不可读 |
| **F3** | `FolderCode`（复合串） | — | ❌ 含 `\|`，且极丑，**已否决** |

**我建议 F1**，理由：文件夹路径本身就是**业务语义**（"标准目录"的价值就在于镜像真实目录结构），而"统一口径"要解决的是**同一事物多种拼写**的歧义 —— 文件夹名只有一种拼写，不存在该问题。

**但 F1 有个必须配套的规则**：**文件夹改名时，必须同步 `RenameAsync` 其下所有对象（源 + pdf + markdown）并更新 DB 路径**；否则路径失配。
若你觉得这条太难保证 → 选 **F2**（放弃可读性换绝对稳定），或 **禁止文件夹改名**（只能删了重建）。

### 1.5 归档路径（仅企业库）

```
{FolderPath}/{FileName}                                 ← 当前源文件（永远最新名）
{FolderPath}/_archive/{FileName}.v{n}                    ← 历史源文件
{FolderPath}/pdf/{FileName}.pdf                          ← 当前 PDF
{FolderPath}/pdf/_archive/{FileName}.pdf.v{n}            ← 历史 PDF
{FolderPath}/markdown/{FileName}.doc.md                  ← 当前 Markdown
{FolderPath}/markdown/_archive/{FileName}.doc.md.v{n}    ← 历史 Markdown
```
- `.v{n}` 与历史表 `VersionNumber` 对齐 ⇒ 路径即可反查历史
- `_archive` 需登记为**保留段名**，禁止用作业务文件夹（防撞车）
- `IsProductPath` 判断"任一段 == `pdf`/`markdown`" → 归档产物仍在 `pdf/` 下 ✓

## 5. 上传 / 覆盖 / 归档流程

### 5.1 标准库 = 单纯覆盖（你第 3 条）

```
上传 → 算 StoragePath → 若已存在（DirectoryCode + FullPath）则就地覆盖
     → 更新行（列级写入）→ 双链置 pending → 入队转换
无归档、无历史、无版本号、无 FileHash
```
**即现状行为不变**（除了路径格式与编码变更）。

### 5.2 企业库 = 覆盖 + 归档 + 版本

```
上传 → 算 StoragePath
  ├─ 不存在 → 新建行（VersionNo = 1）→ 入队转换
  └─ 已存在 →
       ① 拒绝条件：ConvertStatus / MarkdownStatus ∈ {pending, converting}
          → 返回业务失败「文件正在转换，请稍后重试」（不取消队列任务）
       ② 归档旧对象（三个都做，顺序不可颠倒）：
            RenameAsync(旧 StoragePath    → {FolderPath}/_archive/{FileName}.v{n})
            RenameAsync(旧 PreviewPdfPath → {FolderPath}/pdf/_archive/{FileName}.pdf.v{n})
            RenameAsync(旧 MarkdownPath   → {FolderPath}/markdown/_archive/{FileName}.doc.md.v{n})
       ③ 归档成功后，插历史行（三个归档路径 + FileHash + VersionNumber）
       ④ 更新当前行：StoragePath = 新路径、VersionNo + 1、双链置 pending
          ★ 列级写入 UpdateAsync(entity, cols)，⛔ 不全列写回
       ⑤ 入队转换
```

**★ 顺序铁律**：**先归档成功 → 再上传新文件**。
`RenameAsync` 是「下载→上传→删除」三步，中途失败会两头空。归档目标带 `.v{n}` 保证**重试幂等**。

### 5.3 仍待你定：归档触发条件

| 选项 | 含义 |
|---|---|
| **A** | **内容变了才归档**（比对 `FileHash`）；未变则只更新时间 + 记一条"内容未变"历史 |
| **B** | **每次上传都归档一版**（追溯最完整，版本表会有大量内容相同的记录） |

## 11. ⑬ 软删除契约（源码逐行核对，2026-09-26）

| 环节 | 位置 | 事实 |
|---|---|---|
| 接口 | `YZH.Core.Stand/Interfaces/ISoftDelete.cs` | `bool IsDeleted` + `string? DeleteBy` + `DateTime? DeleteTime` |
| 过滤 | `SqlSugarDbOrm.cs:510-520` `IsDeletedCondition<T>` | **仅当 `IsDeclaredOnType<T>("IsDeleted")` 为真才加 `WHERE IsDeleted = 0`**，否则返回恒真 |
| 判据 | `SqlSugarDbOrm.cs:494-505` `IsDeclaredOnType<T>` | `prop.DeclaringType == typeof(T)`；`[SugarColumn(IsIgnore = true)]` 直接返回 false |
| 执行 | `EntityService.cs:673-703` `SoftDelete` | 只写 3 列 `UpdateAsync(entity, ["IsDeleted","DeleteTime","DeleteBy"])`；**未实现接口的实体走硬删除** |

**结论**：⑬ 可行，且三个 Dir 实体（`StandardDirectoryConfig` / `_Folder` / `_File`）**已经显式声明**了软删字段 ⇒ 过滤当下即生效。DB 列 `IsDeleted tinyint(1) NOT NULL DEFAULT 0` ↔ C# `bool` 映射正确。

### 11.1 ★ 唯一键 × 软删：为什么唯一键**不能**含 `IsDeleted`

软删行**仍留在表里**。因此：

| 方案 | 第一次「建 → 删」 | 第二次「建 → 删」 | 结论 |
|---|---|---|---|
| 唯一键**不含** `IsDeleted` | 删后行仍占键位 → 再建撞 1062 | — | ❌ 需配套复活 |
| 唯一键**含** `IsDeleted` | `(k,0)` 删成 `(k,1)` → 再建 `(k,0)` ✅ | `(k,0)` 删成 `(k,1)` → **撞 `(k,1)`** | ❌ 只能存 1 条已删行 |

**正解 = 唯一键不含 `IsDeleted` + 强制"复活"**：

```
建前：按业务键查「含已删」的行（includeDisabled / 不用默认过滤）
  ├─ 命中且 IsDeleted = 1 → 复活：IsDeleted = 0、清空 DeleteBy/DeleteTime、刷新业务字段（同一行，Id 不变）
  ├─ 命中且 IsDeleted = 0 → 报「已存在」
  └─ 未命中 → INSERT
```

⇒ 不变式：**一行一个逻辑键，永久**；`IsDeleted` 只在 0 / 1 之间翻转。这正是 `cert_enterprise_stage` 的 `check/add` 复活模式（`REFERENCE.md §二十二`）的泛化。

**落地要求**：所有「新建文件夹 / 文件 / 配置」入口都必须用**含已删**的查询；⛔ 不能用默认 `GetListAsync` / `GetOneAsync`（默认加 `IsValid = 1`，且软删过滤会把已删行藏掉）—— 否则复活逻辑永远命中不到，直接撞 1062。

### 11.2 反向陷阱（已登记 `REFERENCE.md §二十` ㉚）

把 `IsDeleted` / `IsValid` **上提到 `BaseEntity`** 做 DRY ⇒ `DeclaringType` 变成 `BaseEntity` ≠ `T` ⇒ **全库软删过滤 + 启用过滤同时静默关闭**（已删 / 已禁用的行重新出现在所有列表里，零报错）。这是「静默失败」类里**杀伤面最大**的一条 —— 一次改动影响全库所有实体。
