## 一、后台管理：不用大调整 —— 精确结论

### 1.1 结构不用动，只补 3 类字段

| # | 表 | 要补 | 服务哪一步 | 挡不挡 10-15 |
|---|---|---|---|---|
| ① | `cert_validation_rule` | **`JudgeMode`**（`auto`/`manual`/`semi`） | 你的「人工 / AI 复核」 | **挡**（你的核心需求） |
| ② | `audit_task` | `EnterpriseCode` + `EnterpriseStageCode` + `TaskType` | 第六步「开启任务」 | **挡**（任务无法归属企业） |
| ③ | `audit_nonconformity` | `StandardCode` | 第六步「NC 按标准」 | **挡**（多标准 NC 无法标注） |

**已实测确认**：`cert_validation_rule` 现有列为
`Id, Code, OrgCode, 审计字段, Status, IsValid, Sort, Remark, StandardCode, PhaseCode, ClauseCode, WorkflowCode, RuleCode, RuleName, RuleNameEn, SeverityIfViolated, RuleJson, LayoutJson, NcDescriptionTemplate, IsActive`
→ **确实没有 `JudgeMode`**。但它已有 `WorkflowCode`（可挂工作流）和 `IsActive`。

### 1.2 ★ 术语要精确：不是「复核」，是「判定方式」

你举的例子是「**某个该有的设备是否存在**」→ 这**不是**"复核"，而是**这条检查项本来就必须人工去现场看**。

→ 建议命名为 **`JudgeMode`（判定方式）**，值域：
| 值 | 含义 | 对应审核方法 |
|---|---|---|
| `auto` | 系统自动判定 | **查阅文件**（✅ 可自动化） |
| `manual` | 必须人工判定 | **现场观察 / 访谈**（❌ 不能自动化） |
| `semi` | 系统给初判 + 人工确认 | 综合判定 |

**★ 这与上轮已确立的结论完全一致**：**人工 / 自动按「审核方法」划分**（查阅文件 / 现场观察 / 访谈）。你说的「设备是否存在」正好落在 `manual`。

**落点**：
- DB：`cert_validation_rule` 加 `JudgeMode varchar(10) NOT NULL DEFAULT 'auto'`
- 后端：`CertPlatform.Admin/Controllers/Workflow/ValidationRuleController.cs`（现有控制器）— 只需 EntityConfig 加一列，**无需改控制器代码**
- 前端：`business/nc-config/designer.vue` + `business/workflow-rules` 加一个下拉
- ⚠️ **EntityConfig 改完必须重启后端**（业务 JSON 不热加载，见静默陷阱⑯）

## 二、★★ MinIO（mimo）结构 —— 本轮最关键的技术核对

> 我理解你说的「mimo」= **MinIO**（对象存储）。以下全部基于**源码实测**。

### 2.1 实际代码里的路径（已核实）

```csharp
// CodeGeneratorService.GenerateStandardDirectoryPath()
/standard-directory/{OrgCode}/{StandardCode}/{PhaseCode}/{FolderPath}/{FileName}

// CodeGeneratorService.GenerateConvertedStoragePath()  —— 转换后产物
/standard-directory/{OrgCode}/{StandardCode}/{PhaseCode}/{FolderPath}/.converted/{FileName}
```

**与你描述的「标准目录 → 机构 → 标准 → 阶段 → 标准目录 → 文件」逐层完全一致 ✅**
（`标准目录` = `/standard-directory`｜`机构` = `OrgCode`｜`标准` = `StandardCode`｜`阶段` = `PhaseCode`｜`标准目录` = `FolderPath`｜`文件` = `FileName`）

### 2.2 你说的「企业资料」结构 —— **现在完全不存在**

全仓搜索：**只有 `/standard-directory/` 一个前缀**，**没有任何企业维度的路径**。
→ 这是**要新建**的，不是要改的。

### 2.3 两个结构的真实差异 —— 你说「首先是大的目录文件夹」，实际有 **4 处**

| # | 差异 | 标准目录侧 | 你提的企业侧 | 评估 |
|---|---|---|---|---|
| ① | 根前缀 | `/standard-directory/` | `企业资料` | ✅ 对，建议用 `/enterprise-docs/` |
| ② | **机构层** | `{OrgCode}` | **无** | ⚠️⚠️ **必须补！** 见下 |
| ③ | 第 2 层 | `{StandardCode}` | `{标准}` | ⚠️ **顺序有问题**，见 §2.4 |
| ④ | 第 4 层 | `{FolderPath}`（**要求**目录） | `{企业文件夹}`（**实例**） | ✅ 对 —— 这正是「要求 vs 实例」的本质差异 |

**★★ 差异 ② 是缺陷级，必须补**：
如果企业端路径**不含 `OrgCode`**，那么**两个工作区各自建了 Code 相同的企业**（`ENT-0001` 在每个工作区都会从 1 开始编号）→ **MinIO key 完全相同 → 后上传的覆盖先上传的**，且**跨租户数据泄露**。
→ 企业端路径**必须**是 `/enterprise-docs/{OrgCode}/{EnterpriseCode}/...`。

### 2.4 ★★★ `{标准}/{阶段}` 顺序与「按阶段管理一套资料」**冲突**（本轮最重要的发现）

**你的三句话互相矛盾**：
1. 第二步：「一个企业在**不同阶段**，可能申请**一个到多个标准**的认证」
2. 第三步：`企业code -> **标准 -> 阶段** -> 文件夹 -> 文件`
3. 第三轮（原话）：「**按阶段管理一套企业资料**，这个是否是合理的设计」

**若按 `{标准}/{阶段}`，后果是**：
```
/enterprise-docs/{Org}/ENT-0001/iso9001-2015/jd01/营业执照.pdf
/enterprise-docs/{Org}/ENT-0001/iso14001-2015/jd01/营业执照.pdf   ← 同一份文件，两份
```

| # | 后果 | 严重性 |
|---|---|---|
| 1 | **同一份文件（营业执照）在 N 个标准下重复 N 份** → 替换一次要改 N 处 → **版本管理失控**（而你第三步明确要求「版本号 + 有效标志」） | 🔴 高 |
| 2 | **一次上传无法同时满足多标准** → 用户要按标准**重复上传 N 次** | 🔴 高 |
| 3 | 与「按阶段管理**一套**企业资料」**直接冲突** | 🔴 高 |
| 4 | 与你自己说的「上传后针对该阶段下**所有标准**统一校验」**冲突**（校验要跨标准，存储却按标准拆开了） | 🔴 高 |

**★ 建议：企业端去掉「标准」层**

```
/enterprise-docs/{OrgCode}/{EnterpriseCode}/{PhaseCode}/{FolderPath}/{FileName}
```

| 理由 | 说明 |
|---|---|
| 一次上传、一套目录、一份版本 | 对上你「按阶段管理一套企业资料」的诉求 |
| 标准**不进路径，只进数据库** | `cert_enterprise_document` 记「这个文件满足哪些标准」 |
| 多标准 = **要求清单的并集** | 排重判据 = **文档类型** → 一个文件可同时满足多个标准 |
| 替换只改一处 | 版本管理简单、可靠 |
| 「按标准导出资料包」仍然能做 | 导出时按 DB 里的标准标注**筛选**，不靠目录结构 |

**⚠️ 但这是需要你拍板的点**（见 §六-A）。若你坚持标准进路径（例如为了直观的目录浏览），**代价是版本管理复杂度翻 N 倍**。

### 2.5 版本与替换 —— 你的设想**可行，且已有基础**

你说：「过期的文件名还是应该存储在标准文件夹下，但**文件名后面要带版本号或 file code**」

| 你的设想 | 评估 |
|---|---|
| 文件名带版本号 / fileCode | ✅ **正确做法**。MinIO 是**对象存储，没有真正的目录**，路径只是 key 前缀 → **必须靠 key 唯一来区分版本**，不能靠"目录"做逻辑 |
| 旧版本仍然保留 | ✅ **必须保留** —— 报告有法律效力，要能回答「当时用的是哪一版」 |

**已有基础（实测）**：上传流程**已经支持替换**
`EnhancedFileItem.Mode = "create" | "replace"` + `ExistingFileCode` + `ExistingFileId` + `OldStoragePath`
→ 替换时用 `OldStoragePath` 删旧对象。

**⚠️ 但现有实现是「覆盖式」**：`cert_standard_directory_file` **一个要求只有 1 行** → 替换 = 覆盖 DB 行 + 删掉旧 MinIO 对象 → **旧版本被物理删除，无法追溯**。

**★ 建议**（与上轮一致）：
- 实例表用 **`Version`（int）+ `IsCurrent`（tinyint）** → 旧版 `IsCurrent=0` **不删**
- 路径带版本：`.../{FolderPath}/v{Version}/{FileName}` 或 `.../{FolderPath}/{FileName}.v{Version}.{FileCode}.{ext}`

### 2.6 「逐个审批」—— 不必新建表

你说「从『标准目录 → 文件』中对企业上传的资料进行**逐个审批**，排查企业缺失的文件」

**现在没有「审批」载体**，但**不必新建表** —— 加在实例表上即可：

| 列 | 用途 |
|---|---|
| `DocStatus` | `pending` / `matched` / `unmatched` / `verified` / `rejected` |
| `ReplaceReason` | 不合格原因（驱动"重新替换"） |
| `ReviewBy` / `ReviewTime` / `ReviewNote` | 谁审的、何时、备注 |

**「缺失文件清单」不用存表** —— 它是**要求清单 ∖ 实例清单**的**查询结果**（动态算，避免两张数据不一致）。

**★★ 「增量重跑」为什么是卖点**：
体系认证里**资料会被反复替换**（企业补交、整改）。如果每次都全量重跑 → 慢、贵（AI 调用）、且**已人工确认过的结果会被冲掉**。
→ **只重跑受影响的部分** = 快 + 省 + **保护人工已确认的成果**。这是**真实痛点**，不是锦上添花。

**落点**：

| 表 | 补什么 |
|---|---|
| `audit_task` | `EnterpriseCode` + `EnterpriseStageCode` + `TaskType`(`nc_check`/`report`/`doc_generate`) + **`ScopeJson`**（本次要跑哪些 `cert_validation_rule.Code` / `rpt_report_section.Code`；NULL = 全量） |
| `audit_nonconformity` | `StandardCode` |
| `rpt_report_task` | 已有 `BasedOnAuditTaskCode` / `LockedAt` / `LockedBy` → **够用**，增量范围复用 `ScopeJson` 或加同名列 |

**★ 你设计的「NC 与报告的差异」是对的**：
| | NC 检查 | 报告生成 |
|---|---|---|
| 全量 | 所有规则跑一遍 | 所有章节重新生成 |
| 增量 | 只跑勾选的规则 | 只重生成勾选的章节 |
| 触发原因 | 替换了文档 | 改了某章节 / 补了资料 |

**工作量**：补列 1h + 增量范围 2h + 队列执行器 2h + 页 2h = **7h**
