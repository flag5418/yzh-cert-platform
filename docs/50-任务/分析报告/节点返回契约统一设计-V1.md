# 节点返回契约统一设计

> **触发**：`http://127.0.0.1:9990/business/nc-config` 拖「文档字段」节点 → 选字段 `certificateNo` → 「测试提取」返回
> `{"fieldCode":"certificateNo","confidence":1,"message":"sample_data 中无字段 certificateNo 的值"}`
> 用户判断：**分不清「配置错误」还是「企业没填值」**；且 skill 返回不统一 ⇒ **节点极难组合**。
> **诊断方式**：源码静态分析 + 后端 metadata 接口实测（curl 带 Token）
> **日期**：2026-10-12　**状态**：**第二批已实施并实测通过**（见 §十）｜**第一批（配置期信封）未实施**，待裁决 A/B（见 §十一）

## 〇、结论摘要

用户上报的**两个判断都成立**，而且是**两个独立的问题**，⛔ 不能合并成一次改动：

| # | 问题 | 根因一句话 | 影响面 |
|---|------|-----------|--------|
| 1 | 「测试提取」把**配置错误**和**数据缺失**说成同一件事 | 配置期试运行走 `TestFieldResponse`（**无 `success`/`error` 字段**），5 种失败原因全塞进 `message` 文本 | 配置期全部 docField / docTable 测试 |
| 2 | 节点**难组合** | `result` 键的语义**不统一**（有的是单值、有的是整包字典）⇒ 下游取到的可能是值、也可能是字典 | 执行期全部 skill 节点串联 |

**问题 1 是「信封缺失」，问题 2 是「语义分叉」** —— 前者小、可立刻改；后者动执行语义，风险大，建议下一批。

## 一、现状：同一个「节点输出」有 4 套形状

| # | 场景 | 类型 | 形状 | `success` | `error` | `result` 语义 |
|---|------|------|------|:---:|:---:|------|
| 1 | 引擎内部单节点 | `NodeExecutionResult` | `{Success, Error, ErrorCode, Output, DurationMs}` | ✅ | ✅ | — |
| 2 | skill 节点输出 | `SkillExecutor` 包装 | `{success, error, result, ...业务键平铺}` | ✅ | ✅ | **整包字典**（`= Outputs`） |
| 3 | docField / docTable 输出 | `NodeExecutor` 手写 | `{fieldValue, result, hasValue, dataState, confidence, ...}` | ❌ | ❌ | **单值**（`fieldValue`） |
| 4 | **配置期「测试提取」** | `TestFieldResponse` | `{fieldCode, value, confidence, sampleData, message}` | ❌ | ❌ | — |

**问题**：`#2` 和 `#3` 都是「节点输出」，但 `result` 一个是**字典**、一个是**单值**；`#4` 干脆没有信封。
⇒ 下游节点面对上游输出时，**无法用一套统一规则取值**，只能猜（见 §三）。

## 二、问题一：配置期测试没有信封（用户上报的现象）

### 2.1 缺陷链（三层叠加）

| 层 | 位置 | 事实 |
|---|---|---|
| ① DTO | `CertPlatform.Shared/DocExtraction/DocExtractionDtos.cs:227-234` | `TestFieldResponse` 只有 `fieldCode / value / confidence / sampleData / message` —— **没有 `success`、没有 `error`** |
| ② 默认值 | 同上 `:231` | `Confidence` 默认 **`1.0`** ⇒ 失败分支不设值，序列化出来就是「满分置信度」 |
| ③ 服务 | `DocExtractionRuleService.AI.cs:889-923` | 5 个失败出口（规则不存在 / 字段不存在 / 未验证 / 无该字段值 / 解析失败）**只设 `Message`**，`Value` 不设、`Confidence` 不降 |
| ④ 控制器 | `DocExtractionRuleController.cs:170-174` | `return Ok(ApiResponse<object?>.Ok(data: result))` —— **恒 `Ok`** ⇒ 信封 `success` 恒 `true` |
| ⑤ 前端 | `WorkflowDesigner.vue:1369-1385` | 注释已自承「后端永不抛异常、信封恒 true」⇒ 只能**按 `value` 空否猜** |

前端现有判据（`WorkflowDesigner.vue:1381-1385`）：

```js
const ok = nodeType === 'docField'
  ? data.value !== undefined && data.value !== null && data.value !== ''
  : Array.isArray(data.rows) && data.rows.length > 0
if (ok) onSuccess(data); else onError(data.message || '提取失败：未取到值', data)
```

⇒ **`value` 为空时，5 种原因被压成同一句 `message`**。前端拿不到机器可读的分类，
「规则 Code 打错了」和「企业确实没填」在界面上**长得一模一样**。

### 2.2 为什么 `confidence: 1` 是最误导的一处

`confidence` 的语义是「提取可信度」。失败时它不设值 ⇒ 保留默认 `1.0`。
用户看到 `confidence: 1` + `message: 无字段值`，**两个字段互相矛盾**，且 `value` 因为 `null` 被 JSON 省略
（本项目约定：**JSON 省略 null 字段**）⇒ 连「有没有值」都要靠字段缺失来推断。

## 三、问题二：`result` 语义不统一 ⇒ 组合靠命名巧合

### 3.1 组合的机制

1. 画布连线在 `useWorkflowStore.connect()` 里**只把源节点 ID 写进 `inputs[目标端口]`**，**源端口名被丢弃**。
2. 执行期 `NodeExecutor.ResolveInputValue`（`:197-259`）用节点 ID 从 `sharedOutputs` 取出**整个输出字典**。
3. 再交给 `PickFromOutput`（`:279-293`）四段式猜：① 目标端口名同名键 → ② **`result` 键** → ③ 唯一键 → ④ 整包。

⇒ **只要命中 ②，下游拿到的就是 `result` 的值** —— 而 `result` 是什么，取决于上游是哪个 skill。

### 3.2 实测反例（同一份代码，两种结果）

| 上游节点 | `result` 实际内容 | 下游 `is_empty`（端口名 `value`）拿到 | 判定 |
|---|---|---|---|
| `docField` | `fieldValue`（**单值**，无值时为 `null`） | `null` | ✅ **正确**判「空」 |
| `docTable` | `rows`（**数组**，空表为 `[]`） | `[]` | ✅ **正确**判「空」 |
| `get_field` | **整包字典** `{field_code, field_name, field_value, confidence, is_manual_edited}` | 5 键字典 | ❌ **恒判「非空」** |
| `assemble` | **整包字典** `{assembled_text: "X"}` | 1 键字典 | ❌ **空串也判「非空」** |

**根因**：`SkillExecutor.cs:89` 把 `result` 设成**业务输出整包**（`standardOutputs["result"] = result.Outputs`），
而 `docField`/`docTable` 是手写输出、把 `result` 设成**单值**。两套语义并存 ⇒ 下游行为取决于上游实现方式。

`IsEmptySkill.Judge`（`IsEmptySkill.cs:80`）对字典的判据是 `dict.Count == 0` ——
拿到 `{field_value: ""}` 这种「**有键但值为空**」的字典，**必然判成非空**。

### 3.3 潜伏风险：`branch` 的 `success` 兜底

`ExecuteBranch`（`NodeExecutor.cs:346-355`）对字典的兜底顺序是
`result`(bool) → `compare_result`(bool) → **`success`**(bool)。

`success` 是 `SkillExecutor` 加的**信封键，恒 `true`** ⇒ 一旦前两者都不命中而落到第三档，
**branch 恒走成功分支**（静默错误）。当前因为 `SkillExecutor` 总会写 `result`、② 恒命中，所以基本走不到 ——
但这是**靠巧合成立**，不是靠契约成立。

## 四、统一契约设计

### 4.1 唯一形状（三层同形）

```json
{
  "success":  true,            // ★ 程序层：这个节点「跑完了没有」
  "errorCode": null,           // 失败分类码（见 4.2）；成功时 null
  "error":    null,            // 人读原因；成功时 null
  "result":   "实际的值",       // ★ 主输出，语义统一为「单值 / 数组」，⛔ 不再是整包字典
  "outputs":  { "端口名": "值" }, // 全量端口值（含 result），供多输出节点使用
  "durationMs": 12
}
```

**`result` 语义统一（这是「能组合」的关键）**：
- **单值型节点**（`get_field` / `assemble` / `compare` / `docField`）→ `result` = 那个值
- **表格型节点**（`docTable` / `get_table`）→ `result` = 行数组
- **多值节点** → `result` 仍是「**最该被连线的那个值**」，其余走 `outputs`
- ⛔ **`result` 不得是「业务输出的整包字典」** —— 这正是 `SkillExecutor.cs:89` 现在的写法

### 4.2 失败分类码（在现有 2 个基础上扩到 5 类）

现状：`WorkflowErrorCodes`（`Models/NodeExecutionResult.cs:82-93`）只有 `DATA_MISSING` / `SYSTEM_ERROR`。

| 码 | 语义 | 信封 | UI | 谁能解决 |
|---|---|---|---|---|
| （无） | **执行成功**（含「取到空值」） | `success:true` | 绿 / 黄 | — |
| `CONFIG_ERROR` | **新增**：规则 / 字段 / 表格 Code 不存在，必填端口为空 | `Fail` | 灰 · 「改配置」 | 规则作者 |
| `PRECONDITION_EMPTY` | **新增**：前置未就绪 / 上游没给值（消费节点发现空） | `Fail` | 灰 · 「先去验证 / 去补录」 | 规则作者 / 企业 |

> **实现口径（2026-10-12 落地）**：常量名 = `WorkflowErrorCodes.PreconditionEmpty = "PRECONDITION_EMPTY"`
> （⛔ 不叫 `PRECONDITION_MISSING`）。分工按用户 10-12 裁定「**控制空值还是节点自身的行为来判断**」：
> `DATA_MISSING` 由**取数节点**自己发现数据没有；`PRECONDITION_EMPTY` 由**消费节点**
> （`compare` / `ai_node` / `assemble` …）发现上游没给值 —— 后者走
> `WorkflowDataMissingException` ⇒ **全局中断该检查项** + 落补录缺口。
| `DATA_MISSING` | 数据缺失（企业没填 / 没传） | **`Ok` + `result:null`** ⚠️ | 黄 · 「无值（正常）」 | 企业 |
| `SYSTEM_ERROR` | 系统异常（解析失败 / IO / 未预期） | `Fail` | 灰 · 「报 bug」 | 开发 |

### 4.3 ⚠️ 与现有语义的冲突点（必须裁决）

`DATA_MISSING` 现在的实现是 `WorkflowDataMissingException` ⇒ **抛异常** ⇒ 任务项 failed + 落补录缺口。

但 **2026-10-11 用户已裁定**：`docField` / `docTable` **不再抛该异常，改为返回空值**
（`NodeExecutor.cs:412-429` 注释原文：取数与判空正交，分流交给 `is_empty` + `branch`）。

⇒ **执行期事实上已经是「空值 = 成功」了，只有配置期还停在「空值 = 失败」。**
本方案 = 让配置期与执行期同口径 —— 这本身就是「统一」二字的本意。

## 六、待裁决（3 条 · 每条附白话说明）

### 裁决点 1：企业没填值时，「测试提取」算成功还是失败？

- **A（推荐）算成功，结果是「空」** —— `success:true` + `result:null` + `dataState:"empty"`
  - **白话**：系统成功查了，答案是「企业确实没填」。界面上显示黄色「无值（正常）」，用户一眼知道**不是自己配错了**，该去找企业要资料。
  - 好处：与执行期 `docField` 现在的行为**完全一致**；配置期测出「无值」不再被误当成配置错误。
- **B 算失败** —— `success:false` + `errorCode:DATA_MISSING`
  - **白话**：系统说「这次测试失败了，原因是缺数据」。界面上显示红/灰错误。
  - 代价：配置期与执行期**继续两套口径**；用户仍然要读 `message` 才知道到底是哪一类。

### 裁决点 2：统一到哪种形状？

- **A（推荐）废弃 `TestFieldResponse`，直接用统一信封**（§4.1）
  - **白话**：全项目只有一种「节点输出」长相，前端一套代码处理所有节点。
  - 代价：要改前端读法（`data.value` → `data.result`），改动面稍大但**一次性**。
- **B 保留 DTO，只补 `success`/`errorCode` 字段**
  - **白话**：改动最小，不动现有字段名。
  - 代价：`TestFieldResponse` 变成**第 5 套形状**，与 §4.1 依然不一致，「统一」只完成一半。

### 裁决点 3：第二批（`result` 语义 + 组合收敛）现在做还是下一批？

- **A（推荐）下一批** —— 本批只做配置期信封，先验证；第二批单独评估
  - **白话**：先修「看得见的那半个」（测试提取分不清原因），把执行语义的改动留到有独立验证窗口时做。
  - 理由：`result` 语义一改，**所有既有工作流配置的取值行为都会变**，需要回归。
- **B 本批一起做**
  - **白话**：一次到位，但风险集中；`get_field → is_empty` 等既有连线的行为会变。

## 七、执行策略：与 n8n / 扣子对照（2026-10-12 新增）

> 本节回答四个问题：① NC/报告场景的节点能否统一输出 ② 节点报错能否立即中断路径
> ③ 没值时下游怎么继续 ④ n8n / 扣子是怎么设计的。

### 7.1 节点盘点（★ 问题 ① 的前提）

**skill 节点 10 个**（实测 `wf_skill`：NC 与报告两列**完全相同**，全为 1）：

`llm_extract` · `build_nc_prompt` · `is_empty` · `is_std_file_missing` · `nc_validate` ·
`nc_conclusion_calc` · `compare` · `get_table` · `get_field` · `assemble`

**特殊节点 9 个**（`specialNodes.ts` 的 `SPECIAL_NODES`）：

`start` · `end` · `branch` · `ai_node` · `constant` · `loop` · `docField` · `docTable` · `is_std_file_missing`

⚠️ 两处发现：

1. **`is_std_file_missing` 重复出现**（既是 skill 又是特殊节点）—— 因为它的执行需要
   `start` 注入的上下文，普通 skill 表达不了（`NodeExecutor.cs:605-634` 有专门分支）。
2. **⛔ `constant` / `loop` 没有后端执行分支** —— `NodeExecutor.ExecuteAsync:98-110` 的
   `switch` 只有 8 个分支（`start`/`end`/`branch`/`docfield`/`doctable`/`is_std_file_missing`/`skill`/`ai_node`），
   落到 `_ => throw new NotSupportedException("不支持的节点类型")`。
   ⇒ **这两个节点拖到画布上执行必然抛异常**。前端画布有入口、后端无实现 —— 待确认是「未实现」还是「不该出现」。

⇒ **去重后共 18 个节点**，其中「有输出」的 17 个（`start` 只注入上下文）。**规模小、完全可控**。

**结论（问题 ①）**：**能统一。** 代价是把 3 套写法对齐到 1 套 ——
`docField`/`docTable` 的输出（`result` 单值 + `hasValue` + `dataState`）**已经是正确的那一版**，
应当作为基准，其余向它对齐。

### 7.2 n8n 与扣子的设计（问题 ④）

| 维度 | **n8n** | **扣子（Coze）** |
|---|---|---|
| 节点失败**默认**行为 | **停止整个执行**，标记 failed | **中断工作流** |
| 节点级开关 | `Continue On Fail`（忽略错误继续） | 「**忽略异常**」开关 |
| 忽略后下游拿到什么 | 空项 / 错误数据 | 该节点**预先配置的默认输出内容** |
| 错误**独立出口** | ✅ 节点第二个输出口 **Error output**，可接 IF / 日志 / 通知 | ✅ **异常分支** |
| 重试 | ✅ `Retry On Fail`（Max Tries / Wait Between Tries） | ✅ 重试次数 + 间隔 |
| **空值 ≠ 失败** | ✅ `Always Output Data`（无数据也产出空项，避免下游静默不执行） | ✅ 默认输出内容 + 条件判空 |
| 全局兜底 | ✅ **Error Trigger + 独立错误工作流**（告警 / 重试 / 死信） | ✅ 告警节点 + 三级兜底（静默降级 / 降级通知 / 熔断告警） |

**两家的共同点（这才是要抄的东西）**：

1. **失败默认 = 中断**（⛔ 不是「继续」）
2. **「继续还是中断」由节点自己声明**（一个开关），⛔ 不是引擎全局一刀切
3. **错误有独立出口**，可以接线处理 —— 而不是只留一句错误字符串
4. **「空值」与「失败」是两件事**，分别用 `Always Output Data` / 默认输出去承接
5. **重试是节点级配置**，有上限

### 7.3 我们的现状对照

| 维度 | n8n | 扣子 | **我们** |
|---|---|---|---|
| 失败默认行为 | 中断整个执行 | 中断工作流 | **中断当前路径**（`WorkflowInterpreter.cs:218-221`）✅ 已实现 |
| 节点级「失败时」开关 | ✅ | ✅ | ❌ **无** |
| 错误独立出口 | ✅ | ✅ | ❌ **无**（错误只躺在 `Error` 字符串里） |
| 空值处理 | `Always Output Data` | 默认输出内容 | ⚠️ 返回 `null`，靠 `is_empty` + `branch` **手动**判 |
| 重试 | ✅ | ✅ | ❌ 无 |
| 全局兜底 | Error Trigger 工作流 | 告警节点 | ⚠️ 有 `ErrorCode` 分类，**无兜底路径** |

**★ 关键缺口（问题 ② 的答案）**：中断机制**已实现**，但**只对「抛异常」生效**：

| 情况 | 现在会中断路径吗 | 原因 |
|---|---|---|
| 抛异常（缺 `fieldCode` 配置、AI 节点失败、未预期异常） | ✅ 中断 | `NodeExecutor.cs:144-155` catch → `Fail` + `SYSTEM_ERROR` |

| 取到空值（企业没填） | ❌ 不中断 | **有意**（2026-10-11 裁定：取数与判空正交） |

⇒ 「业务失败」和「取到空值」在输出里长得一样，**两者都不会中断路径**，下游无法区分。

### 7.4 建议策略（问题 ③ 的落点）

1. **失败默认中断当前路径** —— 保持现状（与两家一致），但**必须把 skill 业务失败接上**
   （让 `SkillExecutor` 的 `SkillResult.Success` 真实反映业务成败）。
2. **空值不自动传播**，仍靠显式 `is_empty` + `branch` —— 但**保存时校验**：
   画布上对「上游可能为空、且未接 `is_empty`」的连线给出提示。
   ⛔ 不做「引擎自动短路」：n8n 的 `Always Output Data` 正是为了避免**静默不执行**，
   自动短路会让用户不知道为什么没跑。
3. **加节点级「失败时」开关**（3 选 1）：`中断路径`（默认）/ `继续（用默认值）` / `走异常出口`。
   ⚠️ 「走异常出口」需要画布支持**第二个输出口**（error port），涉及画布数据模型 —— **是本批最大的一个裁决点**。

## 八、空值防御与统一判断标准（2026-10-12 用户澄清后的落地方案）

### 8.1 ★★★ 关键发现：`ValidateRequired` 早已实现空值校验，但**被判据废掉，是死代码**

`SkillExecutor.cs:231-250` 的 `ValidateRequired` **判据里已经包含「值为空」**：

```csharp
if (context.Inputs == null ||
    !context.Inputs.TryGetValue(p.Name!, out var v) ||
    v == null ||
    string.IsNullOrWhiteSpace(v?.ToString()))   // ← 已经查空值了
{
    missing.Add(p.Name!);
}
```

**但它永远不会被触发** —— 第 238 行：

```csharp
if (p.HasDefaultValue) continue;   // 有默认值 = 选填
```

而**所有 skill 的参数都写了 C# 默认值**（`string? prefix_text = null` / `object? value = null` …）
⇒ `HasDefaultValue` 恒 `true` ⇒ 全部被判为「选填」⇒ `missing` **恒为空列表**。

**同一个错误还在元数据端**：`SkillExecutor.Analyze:142` 用 `Required = !p.HasDefaultValue`
⇒ 后端下发的 `Required` **恒 `false`** ⇒ 前端端口上**从来没有出现过 REQ 标签**。

⇒ **结论：「必填」这个概念在整个系统里从未生效过**（前后端一致地静默失效）。
这正是用户第 3 条方案 A 的**现成挂载点** —— 修好判据，机制立刻就活了。

### 8.2 第 1 条的落点：复用 `WorkflowDataMissingException`，但**改由消费方声明**

用户要的「上游为空 ⇒ 终止整个流程」，**语义上与 2026-09-30 的 `WorkflowDataMissingException` 完全相同**。
该异常类的注释里逐字记录了当时的用户原话：

> 「虽然不影响流程的执行，但对结果有非常严重的影响」
> 「语义：这不是「系统故障」，也不是「不符合」，而是**无法判定**。
> 因此工作流必须**自动失败**并提示「缺失必要数据」，⛔ 不得产出一个看起来正常的结论。」

**现状**：该异常**仍然完整存在**，且已接线到底 ——
`NodeExecutor.cs:125-143` 穿透不吞 → `WorkflowInterpreter.cs:103-130` 全局中断当前 item +
`ErrorCode = DATA_MISSING` + `MissingData`（8 个结构化属性）→ 上层落 `cert_expert_task_data_gap` 补录缺口。

**但 2026-10-11 把它从 `docField` / `docTable` 上摘掉了**（改为返回空值，交 `is_empty` + `branch` 分流）。
当时的代价（代码注释自承）：「页面『缺失必要数据 · 去补录』红徽标在 docField/docTable 路径上不再出现」。

**⇒ 用户本次的提法正好是更精确的解法，⛔ 不需要推翻 10-11 的裁定**：

| | 10-11 之前 | 10-11 之后 | **本次建议** |
|---|---|---|---|
| 谁决定「空值算不算问题」 | **取数节点**（一律算问题） | **无人**（一律返回空，静默） | **消费方节点**（自己声明） |
| 取数节点 | 抛异常 | 返回空值 | **返回空值**（保持不变） |
| 消费节点（compare / ai_node / assemble …） | 无法分流 | 拿到空值静默算错 | **声明「不接受空」⇒ 抛 `WorkflowDataMissingException` ⇒ 全局中断 + 落补录** |

这样两个诉求同时满足：**规则作者仍可用 `is_empty` + `branch` 分流**，而**不能接受空的节点会明确失败而不是算出一个错的结论**。

### 8.3 第 3 条：方案 A 与方案 B 对比

| | **A. 节点上声明（推荐）** | **B. 节点函数内部判断** |
|---|---|---|
| 声明方式 | 扩 `[SkillParam]`：新增 `AllowEmpty`（或复用 `Required`） | 每个 skill 的 `ExecuteAsync` 里手写 |
| 实现量 | **≈0**（`ValidateRequired` 已写好，只修判据） | 19 个节点 × 逐个写 |
| 一致性 | 引擎**唯一一处**校验，口径不会分叉 | 19 处口径，必然漂移 |
| 可发现性 | 元数据下发 ⇒ 前端能显示 REQ / 画布能校验 | 藏在代码里，前端看不见 |
| 灵活度 | 够用（「允许空 / 不允许空」二元） | 高（可做复杂判断） |

**建议：A 为主，B 作为逃生舱** —— 确实需要复杂判断的个别节点（如 `is_empty` 本身就是判空节点，
它的入参天然允许为空），在函数内部自行处理，**但要显式标注「本节点刻意允许空」**，⛔ 不是默认行为。

**方案 A 的落地要点（3 步）**：

1. `SkillParamAttribute` 增 `AllowEmpty`（默认 `false` = 不允许空）；同时修 `ValidateRequired` 的判据
   （⛔ 不再用 `HasDefaultValue` 判「选填」）+ 修 `Analyze` 的 `Required`
2. `ValidateRequired` 失败时 ⛔ **不再返回 `SkillResult.Ok`** —— 改为
   `SkillResult.Fail` 并带上 `errorCode = DATA_MISSING` 与结构化信息（DataKind / DataCode / RuleCode）
3. `NodeExecutor.ExecuteSkillAsync` 识别该 `errorCode` ⇒ 抛 `WorkflowDataMissingException`
   ⇒ 引擎全局中断 + 落补录缺口（链路已存在，直接复用）

### 8.4 第 2 条：统一判断标准（引擎只认两个字段）

统一之后，引擎判断后续动作**只看 `success` + `errorCode`**，⛔ 不为任何单个 skill 写特殊逻辑：

| `success` | `errorCode` | 含义 | 引擎动作 |
|:---:|---|---|---|
| `true` | — | 正常产出（**含合法的空**） | 继续下游 |
| `false` | `PRECONDITION_EMPTY`（新增） | **输入为空且本节点不允许** | **全局中断当前检查项** + 落补录缺口 + 标「不可判定」 |
| `false` | `CONFIG_ERROR` | 配置错（ruleCode / fieldCode 不存在） | 终止当前**路径** |
| `false` | `SYSTEM_ERROR` | 系统异常 | 终止当前**路径** |
| `false` | `DATA_MISSING` | 数据缺失（**保留**，供 `is_std_file_missing` 等复用） | 全局中断当前检查项 |

**⚠️ 「终止」的粒度必须澄清**：`WorkflowDataMissingException` 现在的粒度是
**当前检查项（item）**（`WorkflowInterpreter.ExecuteItemAsync` 层面 catch，其他 item 继续）。

⛔ **不建议扩到「整个任务」**：一个字段缺失就让该标准下 40 条规则全部不跑，太粗暴；
且与 §7.5 的补录机制衔接不上（补录是任务级的，但「不可判定」是检查项级的）。
⇒ **建议粒度 = 当前检查项**，任务级只做汇总提示（「N 个检查项因数据缺失不可判定」）。

### 8.5 ★ 分工：图上显式分流 vs 节点自身行为（2026-10-12 用户主张 + 补充）

**用户主张**：「控制空值还是**节点自身的行为**来判断，人工干预容易出问题」；
「用**值判断节点**来进行控制，待有结果后，再连接 ai 节点」。

**✅ 主张成立的部分**：`AllowEmpty` ⛔ **不是规则作者在界面上配的开关** ——
它是 **skill 开发者在代码里声明一次**的（`[SkillParam(AllowEmpty = false)]`），
规则作者在画布上**根本看不到它**。⇒ 它不属于「人工干预」，正是用户说的「节点自身的行为」。

**⚠️ 需要补上的一层**：图上的 `is_empty` + `branch` **只能防住「作者连对了图」**。
若作者忘连 `is_empty` 直接连 AI 节点 ⇒ 会静默产出错误结论（见下方实测）。

**⇒ 不是二选一，而是分工**（这也正是 n8n / 扣子的实际做法）：

| 机制 | 管什么 | 谁负责 | 规则作者看得见吗 |
|---|---|---|---|
| **图上 `is_empty` + `branch`** | **业务分流**：空值意味着什么后果（走兜底 / 判 NC 不合规 / 跳过） | 规则作者（显式连线） | ✅ 看得见，图即真相 |
| **节点自身声明「参数不能为空」** | **安全网**：作者忘连时不静默算错 | skill 开发者（代码里写死） | ❌ 看不见，非界面开关 |

### 8.6 ★★ 实测：AI 节点拿到空值时**既不失败也不警告**（最危险的一处）

`AiNodeExecutor.ResolveTemplateRefs:643-648`：

```csharp
if (resolved != null)
{
    paramPool[fullKey] = resolved;
    _logger.LogDebug(...);          // 仅 Debug 级
}
// ⛔ resolved == null 时：什么都不做 —— paramPool 里没有这个 key，
//    且只留一条 Debug 日志（生产环境看不到）
```

⇒ 后果：提示词里的 `{{文档字段.result}}` **没有被替换**，带着占位符原文（或空值）
**直接送去问大模型**，节点**照常返回成功**。这正是用户说的「提示词没办法跑通」，
且它**不会中断、不会报错** —— 是最典型的「静默产出错误结论」。

### 8.7 `is_empty` 必须返回「成功」（否则失去分流能力）

**用户疑问**：「值判断是返回成功还是失败？」

**答案：永远返回成功。** 理由：

- `is_empty` **成功完成了「判断」这个动作**，判断结论放在 `result`（bool，`true` = 空）里
- ⛔ 若让「为空 = 失败」，`is_empty` 就退化成「必填校验」，**失去分流能力** ——
  规则作者再也无法用 `branch` 走兜底分支（而这正是 2026-10-11 裁定的本意）
- 「为空 ⇒ 失败」这个行为应该由**不能接受空的节点**（AI / compare）来做，⛔ 不是 `is_empty`

**正确的图例**：

```
docField（取不到 ⇒ 返回空值，success: true）
   ↓
is_empty（success: true，result = true/false）
   ↓
branch
   ├─ result = false（有值）→ AI 节点          ✅ 正常业务
   └─ result = true （为空）→ 中断 / 兜底分支    ✅ 业务分流
```

而 AI 节点自身的 `AllowEmpty = false` 是**安全网**：万一作者漏连 `is_empty`，
AI 节点会**明确失败**（`PRECONDITION_EMPTY` + 全局中断 + 落补录），
而不是带着未替换的占位符去问大模型。

### 8.8 关于 REQ 标签

- `REQ` = `Required`（**必选参数**）的界面标签，✅ 用户理解正确
- **取消的是界面标签，⛔ 不是校验机制** —— 两者由**同一个 `Required` 字段**驱动：
  - 界面：决定是否显示 `REQ`
  - 执行期：决定参数为空时是否中断
- **建议**：机制保留；界面标签可去掉（或换成更直观的「必填」文案写在参数说明里）。
  ⚠️ 若完全不给提示，规则作者将无法知道哪个参数必填 —— 需权衡。

### 8.9 与 §7.5 的衔接（闭环）

```
启动前 precheck（✅已有）→ 弹窗补录（✅已有）→ 用户跳过（✅已有）
                                    ↑                        ↓
                        补录后重跑 ──┘          执行期消费节点发现空（★新做）
                                                              ↓
                                            全局中断该检查项 + 落 gap + 标「不可判定」
                                                              ↓
                                            回到「弹窗补录」—— 闭环
```

⇒ **执行期发现的新缺口，能回到启动前的补录通道** —— 这就是用户说的「客户就是不填，只能靠节点自己控制」
的完整解法：节点控制的是「**要不要中断**」，中断后**仍然给用户补录的机会**，而不是静默算错。

### 10.2 ★ 构建期踩坑：`bool?` 不能作特性参数（59 个 `CS0655`）

**现场**：`SkillParamAttribute.AllowEmpty` 最初声明为 `bool?`（用 `null` 表示「未表态」的三态），
全部 59 处 `AllowEmpty = true/false` 编译报：

```
error CS0655: 'AllowEmpty' is not a valid named attribute argument
because it is not a valid attribute parameter type
```

**根因**：C# 规范规定**特性具名实参的类型不得为可空值类型**（`Nullable<T>` 不在合法清单内，
合法清单 = `bool/byte/char/double/float/int/long/short/string/Type/枚举/object` 及其一维数组）。

**修法**：改为**三值枚举** `SkillParamEmptyPolicy { Unspecified=0, Allow=1, Deny=2 }`。

⛔ **不用 `object?`**（虽然它是合法特性参数类型、改动更小）：`object?` 下若有人误写
`AllowEmpty = "true"`，判读会**静默回落到 `HasDefaultValue`** —— 正是本项目反复踩的
「配了不生效且不报错」陷阱；枚举由编译器直接拦下。

### 10.6 ★★ 用户上报「constant 节点不支持」→ 暴露两个更深的缺陷

**现象**（用户 curl `POST /api/Admin/Workflow/test/run` 原文）：
`路径0@constant_n1: 不支持的节点类型: constant; 路径1@constant_n2: 不支持的节点类型: constant`

**缺陷 1 — 画布能配、后端没实现**：`NodeExecutor` 的 `switch` 无 `constant`（也无 `loop`）分支 ⇒
落 `_ => throw new NotSupportedException`，再被外层 `catch (Exception)` 压成 `SYSTEM_ERROR`
（界面显示「系统故障 · 报 bug」—— **归因错误**，明明该说「改配置」）。

- 修：新增 `ExecuteConstant`，输出 `{ result: 配置值 }`（键名必须是 `result`，见 `specialNodes.ts` 契约；
  值恒按**字符串**处理，⛔ 不猜数字/布尔）。
- 修：未知类型改抛 `WorkflowNodeFailureException(ConfigError)`，错误文案直说
  「该节点能在画布上配置，但执行期没有对应分支」，并点名节点类型。
- 实测：用户原流 `Status=completed`，`constant_n1 → "1"`、`constant_n2 → "0"`。

**缺陷 2（更严重）— `if/else` 两个分支都会跑**：

- 根因：路径在**解析期**静态枚举（`WorkflowConfigParser.EnumeratePaths` 用 DFS 把 `branch` 的
  `success`/`failure` 两条臂都枚举成独立路径），而 `ExecutePathAsync` **无条件逐条执行全部路径**
  ⇒ `branch` 判定出的 `decision` 成了**死数据**。
- 实测（修复前）：`branch_n1` 判定 `success`，但 failure 臂的路径照样完整执行，
  `successPaths=[0,1]` —— 也就是**没走的分支也在跑，还会把它的结果算进汇总**。
- 修：`ExecutePathAsync` 增 `adjacency` 参数；每步先看当前节点是否 `branch`，若是则按
  `decision` 用 `SourceHandle` 找出**该走的目标节点**，与路径上的下一个节点比对，
  不一致 ⇒ 整条路径 `skipped`（新增状态）+ `SkipReason` 写明「谁判的、判成什么、该走谁、本路径是谁」。
- 实测（修复后，**两方向对称**）：
  - 条件真 ⇒ `executedPaths=[0]` / `skippedPaths=[1]`
  - 条件假 ⇒ `executedPaths=[1]` / `skippedPaths=[0]`
- **风险控制**：`cert_validation_rule.RuleJson` 全为 `NULL`（无已保存工作流图）⇒ 回归面为零。
  策略保守：**拿不到 `decision` / 该臂没接线 ⇒ 不跳过**（宁可多跑，不可错杀）。

### 10.7 ★ `SkipReason` / `ErrorCode` 到不了前端（投影丢失）

**现象**：实测 `path1 status=skipped` 但 `skipReason=None`；用户原始响应里 `PathResults` 项也缺 `ErrorCode`。

修复前 `TaskPathResult` 缺 `SkipReason` 与 `ErrorCode` 两个字段。

- 修：`TaskPathResult` 增 `SkipReason` / `ErrorCode` 两属性；投影处显式赋值。

- ⚠️ **教训**：加内部模型字段后，**必须同步检查对外 DTO 的投影**，否则「加了但看不见」。
