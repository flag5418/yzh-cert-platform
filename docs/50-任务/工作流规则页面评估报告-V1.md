## 一、页面实质：名字叫"工作流规则"，实际是"NC 检查规则"

四层命名各说各话：

| 层 | 实际名称 |
|---|---|

| 后端控制器 | `ValidationRuleController` |

**一条规则 = 一个 DAG 工作流 + 一条 NC 文案模板**。业务定位是"某标准的某阶段、某条款，用什么流程去检查、怎么判定"，不是审批流条件，也不是路由规则。

业务用户看到"工作流规则"，第一反应是配审批流 —— 这是本页最大的认知成本。

**建议**：路由 / 菜单 / 前端目录 / 控制器统一为一个业务词（如"检查规则"或"NC 校验规则"）。

## 三、问题清单

### P0-1　RuleCode 语义混用（功能级，最该先验）

- 传入值实际是 `cert_validation_rule.Code`（GUID）：`WorkflowDesigner.vue` 运行分支 `RuleCode: currentLeaf.value.Code`；`ExpertItemExecutors` 传 `p.ItemCode`，而 `CertExpertNcItem.ItemCode` 注释即"`cert_validation_rule.Code`（业务键）"
- 但落库与查询按 `RuleCode` **列**比对：`WfExecutionTaskService.cs` L215 `.Where(x => x.RuleCode == ruleCode)`、L225/L240 `RuleCode = ruleCode`；`Query.cs` L203 `r.RuleCode == task.RuleCode`
- 而 `OnBeforeAdd` 自动生成 `RuleCode = NC-{Standard}-{seq}`

**两者不是一回事。** 后果：规则名 / 严重度快照与详情页 `RuleContext` 可能取不到。

**修法**：执行表一律用 `Code`(GUID) 关联，`RuleCode` 降级为显示用业务编号。

> 注意：这与族表上已定的命名纪律是**同一个坑的第二次出现** —— 族表特意禁止把 `FamilyNo` 叫 `FamilyCode` 来避免混淆，但 `ValidationRule` 里 `Code`(GUID) 与 `RuleCode`(业务号) 正混着用。

### P0-2　RuleJson 空值语义三口径不一致

| 口径 | 取值 |
|---|---|
| DB | `RuleJson json NOT NULL` |
| 实体 | `string? RuleJson` |
| 运行时 | 空值 = "无工作流"判据（`HasWorkflow`、`ExpertItemExecutors` 跳过分支） |

"未配 DAG"无法用空值表达，语义全靠约定；而 `NOT NULL` 又要求必须塞一个空 JSON —— 塞 `{}` 还是 `null` 无约定。

**这条直接决定"某些阶段不出 NC"怎么落地**（见第五节）。

### P1-3　WorkflowCode 是僵尸列

- DDL `NOT NULL`，快照仍挂 `fk_valrule_workflow → wf_workflow_definition`
- 而 `wf_workflow_definition` **已废**（`20260922_create_wf_path_execution_V1.sql` L73 明写"0 行，已被 `cert_validation_rule.workflow_config` 取代"）
- 前端唯一触点是 `designer.vue` 透传，`WorkflowDesigner` 从不生成该值 → **没有采集入口**

`NOT NULL` 的死列会污染每一次新增。要么删列解 FK，要么补入口。

### P1-4　启停字段不合自家铁律

`ValidationRule` 仅继承 `BaseEntity`，无 `IsDeleted / IsValid`，启停判据用 `IsActive`。代码注释已自标"违反铁律九，已知问题 README P0-19"。与其余配置表判据不统一。

### P1-5　命名漂移：Workflow 这个词已经悬空

`wf_workflow_definition` 已废、`WorkflowCode` 是僵尸列，但页面 / 控制器 / 前端目录还叫 Workflow。概念正在漂移，建议借这次统一命名一并收口。

### P2-6　测试运行不代表已保存

`handleExecuteTest` 用内存画布 JSON 直发 `test/run`，**未保存也能跑通**，用户易误判"跑通 = 已落库"。建议运行时明确提示"当前测试使用未保存草稿"。

### P2-7　DDL 快照不能作为判断依据（现状已有自我警示）

`all_tables_ddl.sql` 文件头自声明"时点参考件·禁止作为判断依据"，且确实滞后：快照中 `cert_validation_rule` 尚无 `RuleJson / LayoutJson / JudgeMode / RuleNameEn` 四列（真实列由迁移脚本补齐）。这个警示很好，建议在评审材料里统一标注，避免后人被带偏。

## 五、衔接上轮议题：阶段是否出 NC 的落点就在这里

结论明确：

- **单条 NC 是"规则行级（条款级）"的产出** —— 每条规则带 `ClauseCode`
- **"该阶段是否出 NC"是聚合判断** —— 该 (标准 × 阶段) 下存在任意 `IsActive = 1` 的规则 = 出 NC

因此：

1. 若走"不加开关、靠配置控制"（上轮结论），**控制点就是这张表的"有行 / 无行"**。
2. 但**粒度要分清**：删掉一条规则 = 该条款不检查，**不等于**该阶段不出 NC。用"删规则"实现"阶段不出 NC"会误伤条款覆盖。
3. 更稳的做法：**用 `IsActive` 停用而不是删行** —— 停用保留配置痕迹（呼应上轮"删配置 vs 停配置"的结论），且 `IsActive` 已在候选项筛选中生效（`ExpertTaskService` L429-469 按 `PhaseCode == stageCode && IsActive` 取规则）。

**综上：这个页面天然支持"阶段不出 NC"的实现，且不需要新增字段** —— 前提是 P0-2 的空值语义定清楚，并用停用代替删行。
