## 一、已拍板决策（本计划的前提）

| 编号 | 决策 | 内容 | 影响 |
|:----:|------|------|------|
| **D-5** | 提取引擎落位 | 文档转换/内容提取/AI 调用放 `CertPlatform.Shared`（共享层）。理由：管理员配置规则、审核员/企业端上传材料都需要文档提取，属于公共核心能力 | 新增共享服务 4 个；Admin/Auditor/Enterprise 三端均可复用 |
| **D-6** | 技术方案调整 | **放弃**旧"doc→docx 中转 + NPOI/PdfPig 提取"链路，改为：**预览一律转 PDF**，**提取一律转 Markdown**（anydoc），Markdown 直接作为 LLM 上下文。**与既有设计稿《[文档预览链路改造方案-V1.md](../20-体系认证/03-详细设计/01-系统管理/基础资料管理/文档预览链路改造方案-V1.md)》（2026-08-25）完全一致**，本计划是该设计稿在文档提取规则模块的落地实例 | 新增 PDF 产物列与 Markdown 产物列；转换队列任务类型扩展 |

### 1.1 D-6 可行性结论（用户要求的分析）

| 链路 | 方案 | 可行性 | 说明 |
|------|------|:------:|------|
| **预览：doc/docx → PDF** | `yzh-libreoffice` 容器 headless 直转 `soffice --convert-to pdf` | ✅ 高 | 不再经 doc→docx 中转，旧方案"doc→docx 格式问题"对预览**不再构成风险**；认证材料（正文/表格/页眉页脚）还原度足够 |
| **预览：xls/xlsx → PDF** | LibreOffice 直转，宽表按打印缩放 | ✅ 中高 | 宽表会分页，转换前按 `scale-to-width` 设置即可接受 |
| **预览：pdf** | 原样透传 | ✅ 100% | 无转换 |
| **预览：jpg/png** | 不转 PDF，前端 `<img>` 直显 | ✅ | 扫描件图片本来无文本层 |
| **预览渲染** | 显示层仅 PDF + 图片两分支：`@vue-office/pdf` + iframe 降级；图片 `el-image`/`img` 降级 | ✅ 成熟 | 按设计稿 §4.2：删除 docx/excel 前端解析分支，卸载 `@vue-office/docx`、`@vue-office/excel` |
| **提取：docx/xlsx/pdf/csv/pptx → Markdown** | `yzh-anydoc` 容器（@firecrawl/anydoc v0.2.3，14 格式 → GFM） | ✅ 高（实证） | **已入 compose + start.sh**；实测 .docx 66ms、.doc 8ms；合并单元格复杂报表 GFM 还原质量高（见 §9.1） |
| **提取：.doc/.xls（旧格式）** | **anydoc 直接转换，无需 doc→docx 中转**（V1.1 实证修正：原计划 LibreOffice 中转步骤取消） | ✅ 高（实证） | 旧格式样式漂移问题**整链消除**；提取链路只需 anydoc 一个容器 |
| **提取：扫描件 PDF/图片** | 无文本层 → 沿用旧提示"需要 OCR（未接入）" | ⚠️ 同旧 | 与旧架构行为一致，不在本期范围 |

> **结论（V1.1 实证强化）**：D-6 方案可行，且相比旧方案（NPOI 三套提取器 + doc→docx 预览中转）**链路更短、格式风险更低**：
> ①旧格式 .doc/.xls 由 anydoc **直接转换**（EXIT=0 实测），doc→docx 中转步骤从提取链路中彻底移除；
> ②复杂合并单元格报表（目标分解考核统计报表 17 列×双层表头）GFM 还原质量高，行列语义完整；
> ③新架构由此**无需引入 NPOI / PdfPig 包**，旧 `DocExtractionRuleService.AI.cs` 的 `IFileExtractor` 调用层整体废弃，**但业务编排层（analyze/verify/字段表格推荐规则）完整保留**（见 §9.1 复调研结论 1）。
>
> **边界差异**：设计稿 §五含"扫描版 → MinerU OCR 兜底"，但 MinerU 容器**未入 compose**。本期维持旧架构行为（扫描件返回"需要 OCR 链路（暂未接入）"提示），OCR 兜底随《文档预览链路改造方案》单独立项，不阻塞本模块。

## 九、V1.1 复调研结论（2026-09-16，应用户要求对三个问题重新调研）

### 9.1 结论一：AI 提取核心（提示词 + 业务编排）完整保留，仅替换上下文载体与执行器

> 用户关注：放弃 LibreOffice（指旧 doc→docx 中转链路）后，AI 提取字段/表格的核心是否仍可不变。

**结论：可以，且必须区分三层**——

| 层 | 旧实现 | 处置 |
|----|--------|------|
| **业务编排层**（analyze→推荐字段表格、verify→按 Prompt 提取、test-field/test-table、`SaveExtractionRule` 同步提取值） | `DocExtractionRuleService.cs`（1,094 行） | ✅ **逻辑完整保留**：提取规则（表格内容禁止拆字段、字段名禁止角色替换、fields 只从段落提取等约束）全部在提示词与编排层，与文档解析方式解耦 |
| **上下文载体** | `BuildStructuredContext()`：NPOI 提取 Sections/Tables → 拼带位置标记伪文本 | 🔄 **替换为 Markdown**：GFM 表格本身就是结构化标记，行列语义优于旧伪文本协议；analyze/verify 的 Prompt 模板（`analyze_word`/`analyze_excel` v2 已激活）无需改动，`{document_content}` 占位符语义不变 |
| **执行器** | `IFileExtractor`（NPOI/PdfPig）+ `IWorkflowEngine + LlmExtractSkill` | 🔄 替换为 `DocumentConvertClient`（anydoc）+ `LlmInvokeService`（HttpClient 直连），旧执行器废弃 |

**实证**：用真实案例文档验证 Markdown 载体对复杂结构的还原能力——《目标分解考核统计报表》（17 列×双层表头×合并单元格）：部门/目标内容/考核方式/月度值全部按行列还原，语义完整；《员工培训档案》（xls 旧格式）：表头“姓名/部门/岗位”+7 列明细表头直接还原能力可用。对比旧伪文本协议（`[Section:3(table)]`），Markdown 让 LLM 无需学习私有协议，通用性更强。

**附带实证**：anydoc 对 .doc/.xls **直接转换成功**（EXIT=0，8~66ms）——旧链路“doc→docx 中转”从提取路径中彻底移除，这是比原计划更简化的修正。

### 9.2 结论二：Markdown 提取的效率与准确性评估

| 指标 | 实测/依据 | 评估 |
|------|----------|------|
| 转换耗时 | .docx 66ms / .doc 8ms（docker exec 含进程启动） | ✅ 毫秒级，无需异步化，可与队列解耦按需转换 |
| 覆盖格式 | doc/docx/xls/xlsx/pdf/csv/pptx/epub 等 14 种 | ✅ 覆盖认证材料全部常见格式 |
| 表格还原 | GFM 管道表，合并单元格按行平铺 | ✅ 行列语义完整；对“跨行合并”呈现为空单元格，LLM 可结合上下文理解 |
| 通用性 | GFM 是公开标准，任意 LLM 原生理解 | ✅ 优于旧私有伪文本协议 |
| 兑价 | Markdown 丢失字号/颜色/页眉页脚位置信息 | ⚠️ 可接受：提取场景只关心字段名-值对与表格行列，不关心版式 |

### 9.3 结论三：AI 接入必要性 + 系统参数驱动调用

> 用户关注：AI 是否必须接入，如何按系统参数调用。

**结论：AI 是“增强能力”而非“硬依赖”，架构上做成可开关、可降级**——

| 能力 | 无 AI 时 | 有 AI 时 |
|------|---------|---------|
| 规则 CRUD/字段表格定义/保存/详情 | ✅ 完整可用 | 同左 |
| 字段/表格定义来源 | **手动添加**（旧前端已有手动添加入口） | AI analyze 一键推荐 + 手动微调 |
| Prompt 验证 | ⚠️ 无意义（Prompt 提取本质是 AI 能力） | verify 实际提取 + sample_data 落库 |

**配置链（按系统参数调用，三层优先级）**：

1. **总开关**（新增）：`cert_sys_config` 键 `ai_extract_enabled`（Category=`ai_model`，默认 `true`；`false` 时 analyze/verify 返回“AI 提取未启用，请手动定义字段表格”降级消息而非报错）
2. **连接参数**（已有，实测 6 键在库）：`ai_provider`（qianwen）/ `ai_api_key` / `ai_base_url`（dashscope compatible-mode）/ `ai_model_name`（qwen-turbo）/ `ai_max_tokens` / `ai_temperature`
3. **Prompt 模板**（已有）：`wf_prompt_template` 按 `analyze_{skill}` 取激活版本（实测 analyze_word v2 / analyze_excel v2 激活），缺失回退内嵌默认

> **安全注记**：`ai_api_key` 明文可读，本期不处理加密（与旧架构行为一致）；建议列入《系统参数管理》模块的后续安全项。

**对 V1 计划的修订**：

- 原 `LlmInvokeService` 设计（配置由调用方传入 DTO）升级为：内部先读 `cert_sys_config` 六键 + `ai_extract_enabled` 开关，Shared 层保留纯 HTTP 执行，Admin 层负责读参组装（保持 Shared 零 DB 依赖）
- 旧 `GetActiveModelFromSysConfig`（模型名唯一真相源）机制**原样保留**，扩展为读全六键
- AI 调用耗时/Token 落 `cert_ai_usage_log`（表已建），供 AI 费用监控页
- analyze/verify 前置检查 `ai_extract_enabled`，关闭时优雅降级
