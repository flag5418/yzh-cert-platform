## 三、能力详表（含"项目如何利用"）

> 这一节是本文的核心。每项能力都给出**项目侧的正确使用方式**。

### 3.1 组织与人员

#### 能力 1：机构管理 ✅

| 项 | 内容 |
|----|------|
| 数据表 | `Sys_Organization`（树形，18 行） |
| 框架实体 | `YZH.Core.Api/Models/Organization/Sys_Organization.cs` |
| 后端 | `OrganizationController`，路由 `api/System/Organization` + `api/Organization` |
| 基类 | `TreeTableControllerBase`（树 + 表格联动） |
| 前端 | `cert-admin/src/pages/system/organization/index.vue`（413 行） |
| 关键字段 | `Code`（业务主键）、`ParentCode`（父节点）、`OrgName`、`OrgType`、`OrgLevel`、`OrgPath`（物化路径）、`LeaderName`、`IsValid`、`IsDeleted` |
| 可用端点 | `/tree/root` `/tree/children` `/tree/add` `/tree/update` `/tree/delete` `/filter` `/add` `/update` `/delete` `/config` |

**项目如何利用**：
- 业务实体继承 `BaseEntity` 后带 `OrgCode` 字段，即自动获得按机构隔离的能力；框架的 `OrgCode` 语义统一指向 `Sys_Organization.Code`。
- 需要机构树选择器时，直接用 `YzhTree` + `/tree/root`、`/tree/children` 懒加载，不要自己拼平铺列表。
- 机构层级判断用 `OrgPath`（形如 `/A/B/C`），不要递归查父节点。

#### 能力 2：用户管理 🔄

| 项 | 内容 |
|----|------|
| 数据表 | `Sys_User`（15 行） |
| 框架实体 | `YZH.Core.Api/Models/Users/Sys_User.cs` |
| 后端 | `UserController`，路由 `api/System/User` |
| 前端 | `cert-admin/src/pages/system/user/index.vue`（89 行） |

**已实现**：基础 CRUD（分页、新增、编辑、删除）、用户名/姓名搜索、启用状态切换。

**缺口**：
1. 前端页**无机构归属设置**、**无角色分配**（角色分配在独立的 `role-user` 页做，需人工跳转）。
2. 前端 API 路由失配：`cert-admin/src/api/system/user.ts` 调 `/api/Sys_User/*`，而后端实际路由是 `api/System/User`。**这是必现故障**。
3. 前端主键字段用 `User_Id`（旧 Vol 命名），与框架 `Code` 主键约定不一致。

**项目如何利用**：
- ⚠️ **当前不要依赖 `system/user` 页做完整用户管理**——机构与角色需另行处理。
- 用户信息读取请走 `Sys_User` 的 `Code` 字段（业务主键），`User_Id` 仅用于自增排序。
- 需要"某机构下的用户列表"时，用 `Sys_User.OrgCode` 过滤，不要用 `Dept_Id`。

#### 能力 3：用户-机构归属 📋

| 项 | 内容 |
|----|------|
| 数据表 | `Sys_UserDepartment`（**0 行**） |
| 实体 | ❌ 无 |
| 后端 | ❌ 无 |
| 前端 | ❌ 无 |

**实测结论**：该表在全项目**零引用**（`grep Sys_UserDepartment` 无任何 C# 命中），且存在**类型不匹配缺陷**：

```
Sys_UserDepartment.UserId          : int          → 对应 Sys_User.User_Id (int) ✓
Sys_UserDepartment.DepartmentId    : varchar(36)  → 对应 Sys_Organization.Id (int) ✗
```

`DepartmentId` 是 `varchar(36)`，而 `Sys_Organization` 的主键 `Id` 是 `int`，二者无法关联。这很可能是该表从未启用的直接原因。

**决策建议**（二选一，需项目侧拍板）：
- **方案 A（推荐）**：**弃用**该表。`Sys_User` 已具备 `OrgCode` / `OrgId` / `Dept_Id` / `DeptName` / `DeptIds` 五个归属相关字段，单机构归属直接用 `Sys_User.OrgCode` 即可，多机构归属用 `DeptIds`。
- **方案 B**：**修复启用**。将 `DepartmentId` 改为 `int`（或 `varchar(64)` 且统一存 `Code`），补实体与控制器，并在 `system/user` 页加入归属设置。

### 3.2 授权关联（框架核心）

> 这一组是 YZH 权限体系的数据基础。三张关联表**分工明确，不要混用**。

#### 能力 5：角色-人员关联 ✅

| 项 | 内容 |
|----|------|
| 数据表 | `Sys_RoleUser`（26 行） |
| 框架实体 | `YZH.Core.Api/Models/System/Sys_RoleUser.cs` |
| 后端 | **`RoleController`**（注意：不是独立的 RoleUserController） |
| 前端 | `cert-admin/src/pages/system/role-user/index.vue`（222 行） |

**关键澄清（易误解点）**：`Sys_RoleUser` **没有独立的控制器**，它由 `RoleController` 的 `check*` 端点族承载：

| 端点 | 作用 | 落库行为 |
|------|------|----------|
| `POST api/Role/checkTree` | 查当前角色已关联的用户（带勾选态） | 读 `Sys_RoleUser` |
| `POST api/Role/check/add` | 勾选保存 | 写入 `Sys_RoleUser` |
| `POST api/Role/check/remove` | 取消勾选 | 删除 `Sys_RoleUser` |
| `POST api/Role/check/all` | 全量关联（供前端本地缓存） | 读 `Sys_RoleUser` |

**表结构特殊性**：`Sys_RoleUser` 只有 `Id` / `RoleCode` / `UserCode` / `OrderNo` / `CreateTime` / `CreateBy`，**没有 `Code` 列**——这是框架内 `Code` 主键约定的一处**已知例外**，删除时必须用 `Id`（代码中已用原生 SQL `DELETE FROM Sys_RoleUser WHERE Id = @Id`）。

**项目如何利用**：
- 给角色分配人员 → 直接用 `system/role-user` 页，或调 `/api/Role/check/add`。
- 判断"当前用户有哪些角色" → 查 `Sys_RoleUser` 按 `UserCode` 过滤，**不要**读 `Sys_User.Role_Id`（该字段是旧 Vol 单角色遗留，与多角色模型并存，属于历史包袱）。

#### 能力 6：角色-菜单关联 ✅

| 项 | 内容 |
|----|------|
| 数据表 | `Sys_RoleMenu`（19 行） |
| 框架实体 | `YZH.Core.Api/Models/System/Sys_RoleMenu.cs` |
| 后端 | `RoleMenuController`，路由 `api/System/RoleMenu` + `api/RoleMenu` |
| 前端 | `cert-admin/src/pages/system/role-menu/index.vue`（220 行） |

**端点**：与角色-人员**同名同形**——`/checkTree` `/check/add` `/check/remove` `/check/all`。

**为什么 `RoleController` 和 `RoleMenuController` 端点完全一样？**
—— 这是设计使然，不是冗余：两者的 `check*` 端点**操作对象不同**（前者操作 `Sys_RoleUser`，后者操作 `Sys_RoleMenu`）。路由分别为 `api/Role/*` 与 `api/RoleMenu/*`，前端也分别调用。**改动时务必确认改的是哪一个。**

**项目如何利用**：
- 新增业务菜单后，需在 `system/role-menu` 页为相应角色勾选，否则菜单不显示。
- 菜单权限标识存在 `Sys_Menu.Auth` 字段（text），前端按钮级权限判断读此字段。

#### 能力 9：系统参数 📋

| 项 | 内容 |
|----|------|
| 框架表 | `sys_config`（21 字段，含完整 YZH 审计字段，**0 行**，**无实体**） |
| 项目表 | `cert_sys_config`（14 字段，**22 行**，实体 `CertPlatform.Shared/Entities/Sys/SysConfig.cs`） |
| 后端 | ❌ 无控制器 |
| 前端 | `cert-admin/src/pages/system/config/index.vue`（16 行，占位） |

**⚠️ 双表并存问题（需决策）**

实测存在**两张系统参数表**：

| 表 | 前缀 | 字段数 | 行数 | 实体 | 定位 |
|----|------|:------:|:----:|------|------|
| `sys_config` | 框架（无前缀） | 21 | 0 | ❌ | 框架层设计 |
| `cert_sys_config` | 项目（`cert_`） | 14 | 22 | ✅ `SysConfig.cs` | 实际在用 |

- 框架表 `sys_config` 含完整 YZH 审计字段（`Code`/`OrgCode`/`Creator`/`ModifyID`/`Deleter`/`Enable`/`Sort`/`Remark`），且其业务字段（`ConfigKey`/`ConfigValue`/`ValueType`/`Description`/`IsSystem`）与 `数据库表设计-V2.md` 域 E 的设计**完全一致**——说明设计是对的，只是**实体指向了项目表**。
- 项目表 `cert_sys_config` 字段更少（无 `OrgCode`、无 `Creator`/`ModifyID` 等审计字段，只有 `enable`/`status`/`remark`/`code`）。

**决策建议**（需项目侧拍板）：
- **方案 A（推荐）**：把 `SysConfig.cs` 的 `[Table]` 指向 `sys_config`，将 22 行数据迁移过去，删除 `cert_sys_config`。理由：系统参数是**框架能力**，不应建在项目层；且框架表审计字段更完整。
- **方案 B**：保留 `cert_sys_config` 作为项目级参数，`sys_config` 留作框架级参数，**明确两级语义**（框架级不可被项目改，项目级可改）。若选此方案，需补实体与控制器各一套。

**项目如何利用**：
- 当前读取参数走 `cert_sys_config`（实体 `SysConfig`，`UniqueField` 标记 `ConfigKey`）。
- ⚠️ 参数缓存使用方式见 `60-AI工程设计/YZH-知识库/04-开发指南/系统参数缓存使用指南.md`。

来源：`src/yzh-core/YZH.Core.Stand/BizConventions/BizNamingRules.cs`

| 域 | 禁止类名 |
|----|----------|
| 用户域 | `Sys_User`、`Sys_Role`、`Sys_UserRole`、`Sys_Menu`、`Sys_RoleMenu` |
| 组织机构域 | `Sys_Organization` |
| 字典域 | `Sys_Dictionary`、`Sys_DictionaryList` |
