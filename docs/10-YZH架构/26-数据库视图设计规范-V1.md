# 数据库视图设计规范 · V1

> 2026-10-13 首版｜**用户裁定**：视图不固化业务有效性｜**试点**：`v_org_standard_stage`
> 用户原话：「*系统数据量可能比较巨大，关系非常复杂，为了照顾效率和复杂度，我觉得可以适当引入视图
> ……需要使用视图的时候，不要吝啬通过视图进行设计*」

---

## 〇 一句话

**多表固定投影、且不含聚合 ⇒ 用视图（`MERGE`，谓词可下推）；含聚合/去重/计数 ⇒ 不用视图（退化为 `TEMPTABLE`）。**
视图**固化 `IsDeleted`、⛔ 不固化 `IsValid`** —— 业务有效性一律以列暴露，由唯一检索入口判。

**D-4 详情**（2026-10-13 实测）：

- **现象**：`/api/System/User/filter` 与 `/api/User/getCurrentUserInfo` 响应里**没有** `RoleName` / `OrgName`
  两个字段；个人中心 `OrgName` 恒空（`RoleName` 被 `UserController.GetCurrentUserInfo` 的手工回填兜住）。
- **根因**：`YZH.Core.Api/Models/Users/Sys_User.cs` 用 `[SugarColumn(IsIgnore = true)]` 声明这两列，
  而 `IsIgnore` 会把该列**从 `SELECT` 一并剔除**（§四 陷阱表第 2 行，`CertStageView` 2026-10-08 已踩同一坑）。
- **⛔ 为什么不能直接改成 `IsOnlyIgnoreInsert/Update`**：登录链路
  `YZH.Core.Web/Controllers/AuthController.cs:67` 是 `_db.Client.Queryable<Sys_User>()` —— **直连物理表**
  （无 `.AS("v_sys_user")`）。解禁后 `SELECT` 会带上 `RoleName` / `OrgName` ⇒
  `Unknown column` ⇒ **登录直接失败**。同类直连点还有 `YZHAnonymousAttribute.cs:85`。
- **修复前置条件**：先把上述直连物理表的查询改走视图（或改显式列投影），再解禁实体列。属独立一轮。

## 二 判据：什么时候该用视图

> **口诀**：**「多表 JOIN + 固定投影 + 无聚合」⇒ 用视图**。

| 情形 | 用视图？ | 理由 |
| --- | --- | --- |
| 3+ 表固定 `JOIN`，投影列稳定（关联链 / 详情页） | ✅ **宜** | `MERGE` 算法把视图展开进外层查询 ⇒ **谓词下推、索引照用**，与手写 JOIN 同效 |
| 关联链要跨端复用（后台 / 专家端同一份口径） | ✅ **宜** | 口径只定义一次（DDL），⛔ 不在两处 C# 里各写一遍 JOIN |
| 含 `GROUP BY` / `UNION` / `DISTINCT` / 聚合（`COUNT`/`SUM`） | ⛔ **不宜** | MySQL 退化为 **`TEMPTABLE`**：先物化全表再过滤 ⇒ **大表反而更慢** |
| **计数类**（`COUNT` / 分组统计） | ⛔ **不宜** | 同上；且计数随数据变化，⛔ 不该固化 |
| 单表简单过滤 | ⛔ 不必 | 直接 `WHERE` 即可，视图只增加一层间接 |
| 需要 `INSERT` / `UPDATE` 的目标 | ⛔ 不可 | 视图不可更新（本仓 T+V 模式下写操作走 T 实体） |

**验证算法是否 `MERGE`**（必做）：

```sql
EXPLAIN SELECT * FROM v_xxx WHERE 主键列 = '...';
-- ✅ 期望：select_type 全为 SIMPLE，table 列出现全部基表，Extra 无 "Using temporary"
-- ⛔ 若出现 <derivedN> / select_type=PRIMARY + SUBQUERY ⇒ 已物化，需重写视图
```

**试点实测**（`v_org_standard_stage`，7 表）：`EXPLAIN` 输出 **7 行全 `SIMPLE`**，
`WHERE OrgCode='...'` 被下推为 `cb` 的 `const`，`os`/`og` 走 `idx_org_code` / `uk_org_std_stage`，
`cfg_any` 走 `uk_org_ent_std_stage` —— **零 `TEMPTABLE`**。

**⚠️ 第 4 条隐藏判据：SELECT 列表里的相关标量子查询会让视图无法 `MERGE`**（2026-10-13 实测）

`v_sys_user` 的 `EXPLAIN` 是 `id=1 PRIMARY <derived2>` + `id=2 DERIVED` ⇒ **视图被整体物化**。
根因**不是** `LEFT JOIN`，而是投影里的这一段：

```sql
(SELECT GROUP_CONCAT(r.RoleName SEPARATOR ',')
   FROM sys_roleuser ru JOIN sys_role r ON ru.RoleCode = r.Code
  WHERE ru.UserCode = u.Code) AS RoleName
```

**反证**（去掉该子查询后的等价查询）：`EXPLAIN` 立刻变 `SIMPLE`（`u` / `o` 两行），确认是子查询所致。

> 判据补充：**「无聚合」要连 `SELECT` 列表一起看** —— 相关标量子查询同样是「先算一遍再筛」，
> 效果等价于 `TEMPTABLE`。需要「一对多聚合成一列」时，优先考虑：
> ① 由**消费侧**另发一次查询再在内存拼（本仓 `UserController` 的回填即此路）；
> ② 接受物化但把视图**限制在维表规模**（`v_sys_user` 即属此类）。

## 三 ★ 有效性规范（2026-10-13 用户裁定）

> **用户裁定**：「**视图不固化（业务有效性过滤）**」。

| 列 | 处置 | 理由 |
| --- | --- | --- |
| `IsDeleted` | ✅ **固化 `IsDeleted = 0`** | 软删行 = **逻辑不存在**。不固化会让视图列翻倍，且 `LEFT JOIN` 下 `NULL` 语义复杂（「行不存在」与「行存在但已删」无法区分） |
| `IsValid` | ⛔ **不固化** —— 以列**暴露** | 业务启用状态是**判据**，必须只有一处 ⇒ 由唯一检索入口 `CoreResourceQuery` 统一判 |
| 关联表 `IsValid`（如 `cert_org_standard.IsValid`） | ⛔ **不固化** —— 同样暴露 | 关联行的启停同样是业务判据 |

**命名**：`<维度>IsValid` —— `OrgIsValid` / `StandardIsValid` / `OrgStandardIsValid` /
`StageIsValid` / `OrgStageIsValid` / `ConfigIsValid`。

**⚠️ 三值陷阱**：`LEFT JOIN` 未命中的一侧为 `NULL` ⇒ 消费方必须判 **`== 1`**，
⛔ **不可判 `!= 0`**（`NULL != 0` 为 `UNKNOWN`，会被误当「有效」或静默丢弃，取决于写法）。
类型一律 `int?`。

**消费侧归一（唯一判据点）**：见 `CoreResourceQuery.GetOrgStandardStageChainAsync` ——
`OrgIsValid != 1` ⇒ **整行剔除**；标准/阶段/配置维无效 ⇒ **逐级置空**（⛔ 不删行，
否则上级维度会跟着消失）。

**备注（存量偏差已于 2026-10-13 清零）**：

- `v_cert_configured_rules` 原在 `WHERE` 固化 `IsValid = 1`（2026-09-20 建，早于本规范）
  ⇒ **已改造**：改为暴露 `RuleIsValid` 列，消费侧 `GetConfiguredRulesAsync` 显式传 `x.RuleIsValid == 1`，
  可见行与改造前逐行一致（偏差 **D-2**）。
- `v_cert_stage` / `v_iso_standard` / `v_sys_user` 原缺 DDL 文件 ⇒ **已补录**并加固 `IsDeleted = 0`（偏差 **D-1**）。
- 新增 `bash scripts/db/views/verify-views.sh` 防复发（缺档 / 孤儿 / 固化 `IsValid` 三项）。
- ⚠️ **仍有两条登记偏差未修**：**D-3**（`v_sys_user` 物化）、**D-4**（`v_sys_user` 视图列被实体 `IsIgnore` 剔除）——
  详见 §一「偏差登记」。

## 四 T+V 视图实体模板（⛔ 缺一即静默失效）

```csharp
[ViewName("v_xxx")]          // ① 只读路由：SqlSugarDbOrm.QueryableRead<T> 走 .AS(视图名)
[SugarTable("v_xxx")]        // ② ⛔ 必须显式写：SqlSugar GetTableName(inherit:false) 不继承基类特性
[NotMapped]                  // ③ 阻止 EF Core 映射
public class XxxView { /* 列 = 视图列，一律 PascalCase */ }
```

| 陷阱 | 症状 | 正解 |
| --- | --- | --- |
| 漏 `[SugarTable]` | 查询打到表名 `XxxView` ⇒ 表不存在 | 显式写表名/视图名 |
| 用 `[SugarColumn(IsIgnore = true)]` 标视图专属列 | **该列从 `SELECT` 里也被剔除** ⇒ `/filter` 恒空串（`CertStageView` 已踩，2026-10-08） | 用 **`IsOnlyIgnoreInsert` + `IsOnlyIgnoreUpdate`**（只从写语句剔除，`SELECT` 保留） |
| 加了 `[Table]`（EF 属性） | 覆盖父类表名配置 | ⛔ 不加 |
| 视图列无对应实体属性 | 静默取不到值 | 属性名 == 视图列名 |
| 实体放 `Shared/Entities/` 但只有一端引用 | 前端守卫 **`R17`** 拦下 | 要么下沉到该端，要么走 `R17_SHARED_ALLOW` 登记（**检索入口的返回类型**必须留 `Shared`） |

**纯只读 V（无 T 对应物）**：本仓既有 T+V 是「V 继承 T」（`CertStageView : CertStage`）。
**关联链视图**没有自己的物理表 ⇒ 用**独立类**（不继承），并在类注释里写明「⛔ 没有 T 表对应物」。

## 五 命名 / 目录 / 回滚

| 项 | 约定 |
| --- | --- |
| 视图命名 | `v_<域>_<实体/链>`，全小写 + 下划线，如 `v_org_standard_stage` |
| DDL 目录 | `scripts/db/views/<视图名>.sql`（**一视图一文件**），目录说明见 `scripts/db/views/README.md` |
| 一致性校验 | `bash scripts/db/views/verify-views.sh` —— ① 缺档 ② 孤儿 ③ 固化 `IsValid` 反模式；退出码 1 = 有偏差 |
| DDL 头部 | 注释块：视图名 / 用途 / 引用表 / **算法** / 日期 / **有效性规范** / **结构语义** / **与库中现定义的差异** / **回滚语句** |
| 幂等 | `CREATE OR REPLACE VIEW` ⇒ 可重复执行 |
| 回滚 | 文件末注释给出 `DROP VIEW IF EXISTS \`v_xxx\`;` |
| 变更后 | ⚠️ **必须重建 + 重启后端**（`[SugarTable]`/实体改动同理） |

## 六 接线清单（一处都不能漏）

1. **DDL** 落 `scripts/db/views/` 并执行（改完跑 `verify-views.sh`）；
2. **视图实体**（§四 三件套）；
3. **取数** 加进 `CoreResourceQuery`（唯一检索入口）—— ⛔ 端内不直查；
4. **有效性判据** 收口在 `CoreResourceQuery`（§三 消费侧归一）；
5. **前端守卫 `R17`** 若拦 ⇒ 按 §四 末行处理；
6. **`EXPLAIN` 验 `MERGE`**（§二）；
7. **逐字段 diff**：改造前后各跑一次同一份数据，JSON 逐字段比对（⛔ 不允许「看起来一样」）。
