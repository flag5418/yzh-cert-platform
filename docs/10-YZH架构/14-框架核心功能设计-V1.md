## 一、框架运行机制总览

### 1.1 统一基类

所有框架与业务控制器都继承框架基类，自动获得标准端点与生命周期钩子。

| 基类 | 位置 | 适用场景 |
|------|------|----------|
| `YzhControllerBase<V>` | `YZH.Core.Api/Controllers/` | 单表 CRUD |
| `TreeTableControllerBase<T,V>` | 同上 | 树 + 表格联动（机构、角色、菜单） |

### 1.2 标准端点（基类内置，无需手写）

| 端点 | 动词 | 入参 | 用途 |
|------|:----:|------|------|
| `/{controller}/config` | GET | — | 获取页面配置（`EntityConfig`） |
| `/{controller}/filter` | POST | `FilterRequest` | **分页查询**（唯一查询入口） |
| `/{controller}/add` | POST | 实体 | 新增 |
| `/{controller}/update` | POST | 实体 | 修改 |
| `/{controller}/delete` | POST | `string[] codes` | 删除（**按 Code 数组**） |
| `/{controller}/export` | POST | `ExportRequest` | 导出 Excel |
| `/{controller}/import` | POST | `IFormFile` | 导入 Excel |
| `/{controller}/import/template` | GET | — | 下载导入模板 |
| `/{controller}/action/{methodName}` | POST | 实体 JSON | 执行注册的行操作 |
| `/{controller}/toggle-valid` | POST | 实体 JSON | 切换有效状态 |

> ⚠️ **重要**：**没有 `getPageData` 端点**。查询一律走 `POST /{controller}/filter`。
> 框架前端中形如 `/api/Sys_User/getPageData` 的调用是**旧 Vol 路由**，在新架构中不存在（详见 §8 缺口）。

### 1.3 生命周期钩子（覆盖 `virtual` 方法即可介入）

| 钩子 | 时机 | 典型用途 |
|------|------|----------|
| `LoadConfig()` | 加载配置 | 返回自定义 `EntityConfig` |
| `OnConfigLoading(EntityConfig)` | 配置加载时 | 修改配置 |
| `OnConfigMissing(string)` | 配置缺失时 | 降级处理 |
| `OnBuildingFilter(List<FilterItem>)` | 构建查询条件时 | 注入机构隔离等隐式条件 |
| `OnQueried(PagedResult<V>)` | 查询结果返回前 | 填充冗余字段 |
| `OnBeforeAdd(V)` | 新增前 | 唯一性校验（返回 `(ok, msg)`） |
| `OnAfterAdd(V)` | 新增后 | 副作用 |
| `OnBeforeUpdate(V)` / `OnAfterUpdate(V)` | 修改前后 | 同上 |
| `OnBeforeDelete(string[] codes)` / `OnAfterDelete(int count)` | 删除前后 | 引用检查 |
| `OnAfterCommitted()` | 事务提交后 | 发消息、清缓存 |
| `OnCustomValidate(V)` | 校验阶段 | 返回错误消息（`null` 表示通过） |
| `ValidateEntity(V)` | 实体校验 | 返回 `(ok, msg)` |
| `HardDelete` | 属性 | `true` 时物理删除（默认软删除） |
| `StrictConfigLoad` | 属性 | `true` 时配置缺失即报错 |

### 1.4 Core 方法（可覆盖，用于定制核心逻辑）

`FilterCore` / `GetConfigCore` / `AddCore` / `UpdateCore` / `DeleteCore` / `ExportCore` / `ImportCore`

> **选择建议**：能用钩子解决就用钩子；钩子不够时再覆盖 Core 方法。

### 1.5 行操作注册（自定义动作）

```csharp
// 构造函数中注册
RegisterRowAction("Enable", EnableDict);
RegisterRowAction("Disable", DisableDict);
RegisterRowAction("GetItems", GetDictItemsAsync);
```

调用方式：`POST /{controller}/action/{methodName}`，body 为实体 JSON。

## 二、认证与账号

### 2.1 用户登录 ✅

**端点**：`POST /api/User/login`
**实现**：`AuthController.Login`（`YZH.Core.Web/Controllers/AuthController.cs`）

#### 完整流程

```
① 参数校验
   UserName / Password 非空 → 否则 400 "用户名和密码不能为空"

② 验证码校验（Release 模式生效）
   见 §2.2，⚠️ 当前存在 key 不匹配缺陷

③ 查询用户（Dapper 强类型 + 参数化）
   SELECT UserName, UserPwd, UserTrueName, Role_Id, Enable, Code
   FROM Sys_User
   WHERE UserName = @UserName AND IsDeleted = 0
   → 无结果 → 401 "用户不存在"

④ 账号状态检查
   Enable == 0 → 401 "账号已被禁用"

⑤ 密码校验
   _password.VerifyDes(明文, user.UserPwd)
   → 失败 → 401 "密码错误"

⑥ SSO 版本号生成（挤号核心）
   userCode = user.Code ?? user.UserName
   ssoVersion = TokenVersionService.BumpVersionAsync(userCode)

⑦ 查询角色编码
   SELECT Code FROM Sys_Role WHERE Role_Id = @RoleId

⑧ 生成 JWT Token
   claims: sub=userCode, name=UserName, roles=[RoleId, RoleCode], ver=ssoVersion

⑨ 更新登录痕迹
   UPDATE Sys_User SET Token=@Token, LastLoginDate=@Now WHERE UserName=@UserName

⑩ 返回 LoginResponse
   { Token, UserCode, UserName, UserTrueName, RoleId }
```

#### 关键实现细节

| 项 | 实现 | 说明 |
|----|------|------|
| 密码算法 | `PasswordHelper.VerifyDes` | ⚠️ **命名误导**：方法名为 `VerifyDes`，但实现是 **AES**（注释明确写"Vol 框架内部使用 `Aes.Create()` 但命名为 DES"）。另有 `Md5` / `Sha256` 静态方法 |
| 数据访问 | Dapper `IDbOrm.QueryFirstOrDefaultAsync<T>` | 登录走原生 SQL，**不走 EntityService** |
| 软删除 | `IsDeleted = 0` | 登录查询显式排除已删除用户 |
| 返回结构 | `ApiResponse<LoginResponse>` | 统一响应包装 |

#### ⚠️ 已知问题

**问题 1：登录角色用的是单角色模型，与多角色能力不一致**

登录时角色来源是 `Sys_User.Role_Id`（**单角色**），而框架已具备 `Sys_RoleUser`（**多角色**）能力：

```csharp
SELECT Code FROM Sys_Role WHERE Role_Id = @RoleId     // 单角色
```

后果：Token 中只携带**一个**角色，多角色用户的权限不完整。

**建议**：改为查 `Sys_RoleUser` 按 `UserCode` 取全部 `RoleCode`，写入 roles claim。同时评估 `Sys_User.Role_Id` 是否废弃。

**问题 2：`Sys_User.Token` 字段写入后无校验逻辑**

登录时把 Token 写入了 `Sys_User.Token`，但 Token 校验走的是 `TokenVersionService`（Redis），`Sys_User.Token` 字段实际未被校验使用。存在双份 Token 记录，需明确该字段定位（建议仅作审计留痕）。

### 2.2 图形验证码 ✅（存在缺陷）

**端点**：`GET /api/User/captcha`

```
① 生成随机文本：VierificationCode.RandomText()
② 生成 Base64 图片：VierificationCodeHelpers.CreateBase64Image(code)
③ 生成 uuid
④ 写入内存缓存：_cache.Set(uuid, code, TimeSpan.FromMinutes(5))
⑤ 返回 { img, uuid }
```

#### ⚠️ 已知缺陷：缓存 key 不匹配（必现）

| 位置 | 代码 | 实际 key |
|------|------|----------|
| `GetCaptcha`（写入） | `_cache.Set(data.uuid, code, ...)` | `{uuid}` |
| `Login`（读取） | `var captchaKey = $"captcha_{req.Uuid}"` | `captcha_{uuid}` |

**两者 key 不一致** → Release 模式下验证码**永远校验失败**。

该缺陷目前被 `#if DEBUG` 跳过验证码校验掩盖，**一旦发布 Release 版即暴露**。

**修复建议**（二选一）：
- 改 `GetCaptcha` 写入 key 为 `$"captcha_{data.uuid}"`
- 或改 `Login` 读取 key 为 `req.Uuid`

**另一处注意**：缓存实现是 `IMemoryCache`（进程内），多实例部署时验证码会失效。若需集群部署，应改用 `IDistributedCache`（Redis）。

### 2.3 SSO 单点登录（挤号）✅

**实现**：`TokenVersionService`（`YZH.Core.Stand/Helpers/TokenVersionService.cs`）

#### 原理

```
Redis Key : token_ver:{userCode}
Redis Val : version（Guid "N" 格式）
TTL       : 默认 30 天（与 Token 过期时间一致）
```

```
登录时：
  version = BumpVersionAsync(userCode)   → 新 version 写入 Redis
  JWT 中写入 claim "ver" = version

校验时：
  从 Redis 取当前 version
  与 JWT 中的 version 比对
  → 不一致 或 Redis 无记录 → Token 失效
```

**效果**：新登录生成新 version 后，该用户所有旧 Token 立即失效 → 实现"新登录挤掉旧登录"。

#### 方法清单

| 方法 | 用途 |
|------|------|
| `GenerateVersionAsync(userCode, ttl?)` | 生成新版本号 |
| `BumpVersionAsync(userCode, ttl?)` | 生成新版本号（**登录时调用**） |
| `ValidateVersionAsync(userCode, tokenVersion)` | 校验版本是否有效 |
| `InvalidateVersionAsync(userCode)` | 使版本失效（**登出时调用**） |

> **能力归属**：SSO 挤号是框架已具备的通用能力，业务侧无需自行实现。

### 2.4 更改密码 📋 未实现

| 项 | 内容 |
|----|------|
| 端点 | ❌ 无 |
| 字段 | ✅ `Sys_User.LastModifyPwdDate` 已预留 |

**实测**：`AuthController` 仅有 `login` / `captcha` / `ping` 三个端点，无任何改密接口。

**实现建议**：

```
POST /api/User/change-password
Body: { oldPassword, newPassword }

① 从 JWT 取 userCode，查 Sys_User
② 校验 oldPassword（PasswordHelper.VerifyDes）
③ 校验 newPassword 强度（长度、复杂度）
④ 加密写入 UserPwd（须与登录校验算法一致 —— AES）
⑤ 更新 LastModifyPwdDate = Now
⑥ 调用 TokenVersionService.InvalidateVersionAsync(userCode) → 强制重新登录
```

> **注意事项**：
> 1. 密码算法必须与登录保持一致（当前是 AES，见 §2.1）。若未来升级算法，需考虑存量密码的兼容或强制重置。
> 2. 改密后**必须**失效 Token，否则旧会话仍有效。
> 3. 建议同时提供管理端"重置用户密码"能力（管理员操作，无需旧密码）。

### 3.1 机构树管理 ✅

**实现**：`OrganizationController : TreeTableControllerBase<...>`
**路由**：`api/System/Organization` + `api/Organization`（双路由）

#### 树能力端点

| 端点 | 动词 | 用途 |
|------|:----:|------|

#### 树 → 表格联动

选中树节点后，基类**自动把选中节点的 Code 注入 `/filter` 的过滤条件**，表格自动刷新为该节点下的数据。业务侧无需手写联动逻辑。

#### 前端用法

```vue
<YzhTree
  :load-data="logic.loadTreeChildren"
  node-key="Code"
/>
```

**关键点**：`node-key` 必须是 `Code`（业务主键），不是 `Id`。

## 四、授权体系 ★ 框架核心

> YZH 采用**三层权限模型**（详见 `05-权限体系.md`）。本节描述三层的数据写入流程。

### 4.1 三层权限的数据映射

| 层 | 问题 | 数据载体 | 框架能力 |
|:--:|------|----------|:--------:|
| 第 1 层 | 能看到哪些**菜单**？ | `Sys_RoleMenu` | ✅ |
| 第 2 层 | 能调用哪些**接口**？ | `Sys_RoleAuth`（旧）/ `sys_role_api`（未建） | 🔄 |
| 第 3 层 | 能操作哪些**数据**？ | 业务表 `OrgCode` 隔离 | ✅ |

### 4.2 角色管理 ✅

**实现**：`RoleController : TreeTableControllerBase<Sys_Role, Sys_Role>`
**路由**：`api/System/Role` + `api/Role`

| 项 | 配置 |
|----|------|
| 树配置 | `RelateField = "ParentCode"`、`NameField = "RoleName"` |
| 端点 | 基类树端点 + 表格端点（见 §1.2、§3.1） |

**角色支持树形**（`ParentCode`），可做角色继承分层。

### 4.3 角色-菜单关联 ✅

**实现**：`RoleMenuController`
**路由**：`api/System/RoleMenu` + `api/RoleMenu`
**操作表**：`Sys_RoleMenu`（`RoleCode` + `MenuCode`）

#### `check*` 端点族流程

```
POST /api/RoleMenu/checkTree
  入参: { ContextCode: 角色Code }
  ① 查菜单树（Sys_Menu，ParentCode 组织）
  ② 查该角色已关联的 MenuCode 集合（Sys_RoleMenu）
  ③ 逐节点标记 CheckFlag = 已关联?
  → 返回带勾选态的树

POST /api/RoleMenu/check/add
  入参: { ContextCode: 角色Code, TargetCodes: [菜单Code...] }
  ① 查已有 RoleCode 关联集合
  ② 差集计算 → 仅插入新增项
  ③ 批量写入 Sys_RoleMenu（RoleCode + MenuCode + OrderNo + CreateTime + CreateBy）
  → 返回 { Updated: n }

POST /api/RoleMenu/check/remove
  入参: { ContextCode, TargetCodes }
  ① 按 RoleCode + MenuCode 定位记录
  ② 批量删除
  → 返回 { Updated: n }

POST /api/RoleMenu/check/all
  入参: {}
  → 返回全部 角色-菜单 关联（供前端本地缓存，减少请求）
```

**设计要点**：
- **差集写入**：`check/add` 只插入新增关联，不重复插入（幂等）。
- **Code 关联**：`RoleCode` ↔ `Sys_Role.Code`，`MenuCode` ↔ `Sys_Menu.Code`。
- **无 `Code` 列**：`Sys_RoleMenu` 仅有 `Id`，删除按 `RoleCode` + `MenuCode` 定位。

### 4.4 角色-人员关联 ✅

**实现**：**`RoleController`**（⚠️ 不是独立的 RoleUserController）
**路由**：`api/Role`（注意：**不是** `api/RoleUser`）
**操作表**：`Sys_RoleUser`（`RoleCode` + `UserCode`）

#### `check*` 端点族流程

```
POST /api/Role/checkTree
  ① 查用户树（按 Sys_Organization 组织，用户挂机构下）
  ② 查当前角色已关联的 UserCode 集合（Sys_RoleUser）
  ③ 逐节点标记 CheckFlag
  → 返回带勾选态的用户树

POST /api/Role/check/add
  入参: { ContextCode: 角色Code, TargetCodes: [用户Code...] }
  ① 查已有 RoleCode 关联集合
  ② 差集 → 仅插入新增
  ③ 写入 Sys_RoleUser（RoleCode + UserCode + OrderNo + CreateTime + CreateBy）
  → 返回 { Updated: n }

POST /api/Role/check/remove
  ① 按 RoleCode + UserCode 定位
  ② 删除 —— ⚠️ 因 Sys_RoleUser 无 Code 列，走原生 SQL：
     DELETE FROM Sys_RoleUser WHERE Id = @Id
  → 返回 { Updated: n }

POST /api/Role/check/all
  → 返回全部 角色-用户 关联（供前端本地缓存）
```

#### ⚠️ 易混淆点：两个 `check*` 端点族

| | `RoleController` | `RoleMenuController` |
|---|---|---|
| 路由 | `api/Role/*` | `api/RoleMenu/*` |
| 操作表 | `Sys_RoleUser` | `Sys_RoleMenu` |
| 关联维度 | `RoleCode` + `UserCode` | `RoleCode` + `MenuCode` |
| 前端调用 | `cert-admin/src/api/system/role-user.ts` | `cert-admin/src/api/system/role-menu.ts` |
| 端点名 | 完全相同（`checkTree`/`check/add`/`check/remove`/`check/all`） | 同左 |

> **改动时必须确认改的是哪一个控制器**。这是框架内最容易改错的地方。

#### 与登录的角色模型冲突

登录时 Token 只携带 `Sys_User.Role_Id`（单角色），而 `Sys_RoleUser` 支持多角色关联（26 行数据）。

**建议**：登录改为从 `Sys_RoleUser` 取全部角色写入 claims，使三层权限模型自洽。

### 4.5 接口权限（第 2 层）🔄

| 项 | 现状 |
|----|------|
| 现行载体 | `Sys_RoleAuth`（330 行，有数据） |
| 表结构 | `Auth_Id` / `AuthValue` / `Menu_Id` / `MenuCode` / `Role_Id` / `RoleCode` / `User_Id` / `UserCode` |

### 6.2 队列中心 ✅

**数据表**：`yzh_queue` / `yzh_queue_task` / `yzh_queue_resource_lock`
**前端 API**：`cert-share/src/api/workflow/queue.ts`

#### 三表职责

| 表 | 职责 |
|----|------|
| `yzh_queue` | 队列主表（一次批量作业） |
| `yzh_queue_task` | 队列子任务 |
| `yzh_queue_resource_lock` | 资源锁（防并发） |

#### 调度流程

```
① 创建队列 → yzh_queue（status=pending, total_count=N）
② 拆分子任务 → yzh_queue_task（status=pending, priority 排序）
③ 工作进程取任务
   ├─ 按 priority + next_retry_at 选取可执行任务
   ├─ 加锁：UPDATE ... SET locked_until, locked_by  （乐观锁）
   └─ 资源互斥：插入 yzh_queue_resource_lock（active_key 唯一约束）
④ 执行任务
   ├─ 成功 → status=completed, complete_time=Now
   └─ 失败 → retry_count++
              ├─ 未超 max_retry_count → status=pending, next_retry_at=指数退避
              └─ 已超 → status=failed, error_type/error_message
⑤ 释放资源锁 → release_time=Now
⑥ 更新队列进度 → yzh_queue.progress / 各状态计数
```

#### 关键设计

| 项 | 实现 |
|----|------|
| 并发控制 | `yzh_queue_task.locked_until` + `locked_by`（乐观锁，非应用层锁） |
| 资源互斥 | `yzh_queue_resource_lock.active_key` **唯一约束** |
| 锁过期 | `expire_at` 字段（防止进程崩溃导致死锁） |
| 重试 | `next_retry_at` + `max_retry_count`（指数退避） |
| 进度 | `progress`(0-100) + 各状态计数 |

**使用建议**：
- 批量作业（批量文档转换、批量提取）**统一走队列中心**，不要自己起 `Task.Run` 或后台线程。
- 资源互斥**不要用应用层锁**，用 `active_key` 唯一约束。
- 队列任务有 `user_code` / `user_name` / `org_code`，天然支持机构隔离与归属追踪。

## 八、前端路由失配清单（P0 必现故障）

框架前端 API 层存在**系统性路由失配**：部分文件仍指向旧 Vol 路由 `/api/Sys_Xxx/*`，而新架构实际路由是 `api/System/Xxx`。

| 前端文件 | 当前调用（错误） | 后端实际路由 | 状态 |
|----------|------------------|--------------|:----:|
| `api/system/user.ts` | `/api/Sys_User/getPageData`<br>`/api/Sys_User/add`<br>`/api/Sys_User/update`<br>`/api/Sys_User/delete` | `api/System/User/filter`<br>`api/System/User/add`<br>`api/System/User/update`<br>`api/System/User/delete` | ❌ 失配 |
| `api/system/dictionary.ts` | `/api/Sys_Dictionary/getPageData`<br>`/api/Sys_DictionaryList/getList` | `api/System/Dictionary/filter`<br>（明细无端点） | ❌ 失配 |
| `api/system/log.ts` | `/api/Sys_Log/getPageData` | ❌ 无控制器 | ❌ 失配 |
| `api/system/param.ts` | `/api/Sys_Parameter/*`（5 处） | ❌ 无控制器 | ❌ 失配 |
| `api/system/organization.ts` | `/api/System/Organization/*` | 一致 | ✅ |
| `api/system/role.ts` | `/api/System/Role/filter` | 一致 | ✅ |
| `api/system/role-menu.ts` | `/api/RoleMenu/*` | 一致 | ✅ |
| `api/system/role-user.ts` | `/api/Role/check*` | 一致 | ✅ |
| `api/system/menu.ts` | — | 一致 | ✅ |

**根因**：`getPageData` 是**旧 Vol 端点名**，新架构统一为 `filter`（`POST`，入参 `FilterRequest`）。基类**没有 `getPageData` 端点**。

**修复方式**：将失配的 4 个文件改为新路由：

```typescript
// 错误
return yzhApi.post<Page<SysUser>>('/api/Sys_User/getPageData', params)

// 正确
return yzhApi.post<Page<SysUser>>('/api/System/User/filter', params)
```

**额外问题**：`log/index.vue` 引入 `@share/api/system-log`，**该模块不存在**（实际定义在 `cert-admin/src/api/system/log.ts`），属 import 路径错误。
