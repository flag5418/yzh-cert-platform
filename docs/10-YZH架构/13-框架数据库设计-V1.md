> 这是框架层的**静态结构权威源**。业务表（`cert_` / `ent_` / `wf_` / `dir_` / `rpt_`）不在本文范围，见 `20-体系认证/02-数据库设计/`。
>
> **数据库**：`yzh_cert_platform` @ MySQL 8.0（`yzh-mysql` 容器，端口 3307）

## 一、范围与边界

### 1.1 覆盖范围

本文覆盖 `yzh_cert_platform` 库中符合 `^(Sys_|sys_|yzh_)` 命名的 **28 张表**。

### 1.2 框架表 vs 业务表的判定规则

> **判定问题**：这条数据模型"换一个项目还成立吗？"

| | 框架层 | 项目层 |
|---|---|---|
| **成立条件** | 换任何项目都需要 | 只在本项目成立 |
| **命名** | `Sys_*` / `sys_*` / `yzh_*` | `cert_` / `ent_` / `wf_` / `dir_` / `rpt_` |
| **归属文档** | 本文 | `20-体系认证/02-数据库设计/` |
| **变更节奏** | 随框架版本演进，可整体抽取 | 随业务需求演进 |
| **实体位置** | `src/yzh-core/YZH.Core.Api/Models/` | `src/certplatform-api/CertPlatform.Shared/Entities/` |

**边界模糊时的补充规则**：**按表的定义位置判归属**——建在框架初始化 SQL 里的归框架，建在项目 SQL 里的归项目；两边各加一行指针，避免"都以为对方写了"。

## 三、通用约定

### 3.1 `Code` 作为业务主键（架构铁律）

| 规则 | 说明 |
|------|------|
| 业务关联**一律用 `Code`** | 不用自增 `Id` 做关联 |
| `Id` 的职责 | 仅用于自增排序、物理定位 |
| 关联表 | 存 `RoleCode` + `MenuCode` / `UserCode`，不存 Id |
| 树形结构 | 用 `Code` + `ParentCode`，不用 `Id` + `ParentId` |

**已知例外**：

| 表 | 例外说明 |
|----|----------|
| `Sys_RoleUser` | **无 `Code` 列**（仅 `Id`/`RoleCode`/`UserCode`），删除须用 `Id`（代码中已用原生 SQL） |
| `Sys_RoleMenu` | 同上 |
| `Sys_User` | 主键字段名为 `User_Id`（旧 Vol 命名），业务键为 `Code` |
| `Sys_Role` | 主键字段名为 `Role_Id`，业务键为 `Code` |
| `Sys_Menu` | 主键字段名为 `Menu_Id`，业务键为 `Code` |
| `Sys_Dictionary` | 主键字段名为 `Dic_ID`，业务键为 **`DicNo`**（无 `Code` 列） |

### 3.2 两套审计字段风格（并存）

实测框架表存在**两种**审计字段风格：

**风格 1：YZH 标准审计字段（15 个）** —— 用于 `sys_config`、`sys_log`、`yzh_queue*`

```
Id:bigint(自增)
Code:varchar(36)          -- 业务主键
OrgCode:varchar(50)       -- 机构隔离
CreateID:int / Creator:varchar(50) / CreateDate:datetime
ModifyID:int / Modifier:varchar(50) / ModifyDate:datetime
DeleteID:int / Deleter:varchar(50) / DeleteTime:datetime
Status:varchar(50) / Enable:tinyint / Sort:int / Remark:varchar(500)
```

**风格 2：Vol 遗留审计字段** —— 用于 `Sys_User`、`Sys_Role`、`Sys_Menu`、`Sys_Dictionary` 等

```
CreateID:int / Creator:varchar(30~200) / CreateDate:datetime
ModifyID:int / Modifier:varchar(30~200) / ModifyDate:datetime
（部分表有 DeleteID / Deleter / DeleteTime / IsDeleted）
```

> ⚠️ **注意**：风格 2 的表**缺少 `OrgCode` 字段**（`Sys_User` 例外，它有自己的 `OrgCode`/`OrgId`）。这意味着这些表**不具备机构级数据隔离能力**。
>
> **实践建议**：新表一律用**风格 1**；存量表改造时再统一。

### 3.3 软删除模型

| 表 | 软删除字段 |
|----|-----------|
| `Sys_Organization` | `IsDeleted` + `DeleteTime` + `DeleteID` + `Deleter` |
| `Sys_User` | `IsDeleted` + `DeleteTime` + `DeleteBy` |
| `Sys_UserDepartment` | 无（仅 `Enable`） |
| `yzh_queue*` | `deleter` + `delete_time` + `delete_by` |

### 4.3 `Sys_UserDepartment`（用户-机构归属）⛔ 未启用

| 字段 | 类型 | 说明 |
|------|------|------|
| `Id` | varchar(36) | 主键 |
| `UserId` | int | → `Sys_User.User_Id` ✓ 类型匹配 |
| `DepartmentId` | **varchar(36)** | → `Sys_Organization.Id`（**int**）✗ **类型不匹配** |
| `Enable` | int | 启用 |

**实测结论**：行数 0、全项目零引用（无实体/无控制器/无前端）。

**缺陷根因**：`DepartmentId` 为 `varchar(36)`，而 `Sys_Organization` 主键 `Id` 为 `int`，**无法建立关联**。这很可能是该表从未启用的直接原因。

**处置建议**：
- **方案 A（推荐）**：弃用。`Sys_User` 已有 `OrgCode`/`OrgId`/`Dept_Id`/`DeptName`/`DeptIds` 五个归属字段，单机构用 `OrgCode`，多机构用 `DeptIds`。
- **方案 B**：修复。`DepartmentId` 改为 `int` 或统一存 `Code`，补实体与控制器。
