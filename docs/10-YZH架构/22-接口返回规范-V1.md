## 一、为什么需要这份文档（一次真实故障）

**症状**：禁用一个不存在的机构 → 界面弹**绿色成功**提示「机构不存在」；删除一个有子节点的机构 → 先弹红色「删除失败」，紧接着**又弹绿色「已删除」**，树上节点纹丝不动。

**根因（三段式，每段单独看都"没错"）**：

```csharp
// ① 后端 handler 用「返回字符串」表达失败 —— 字符串是值，不是结果
private async Task<object?> DisableOrgRecursiveAsync(Sys_Organization entity)
{
    var result = await TreeEntity.GetByCodeAny(entity.Code);
    if (!result.Success || result.Data == null)
        return "机构不存在";          // ← 返回了一个"字符串值"
    ...
}
// ② 基类无条件把 handler 的返回值包成成功
var result = await handler(entity);
return Ok(ApiResponse<object?>.Ok(result));   // ← TreeTableControllerBase.cs:305，success 恒 true
// ③ 前端只要 HTTP 200 就报喜
await this.deleteTreeNode(node, true)
ElMessage.success('已删除')                    // ← TreeTableCore.ts:662，不看 deleteTreeNode 的结果
```

**结论**：这不是一个 bug，是**契约缺失** —— 后端没有"失败该怎么说"的统一说法，前端就没有"失败该怎么听"的统一听法。本文就是补齐这个契约。

## 二、唯一信封

### 2.1 字段定义

```jsonc
{
  "success": true,              // 布尔 · 业务结果唯一判据
  "code": 200,                  // 数字 · 200 成功 / 400 业务拒绝 / 500 系统异常（前端不读）
  "message": "操作成功",         // 字符串 · 成功提示（给人看的"好消息"）
  "err": "",                    // 字符串 · 失败原因（给人看的"坏消息"）★ 新增
  "data": { "Items": [] },      // 载荷 · 唯一数据出口，无数据时为 null
  "timestamp": "2026-09-25T10:00:00"  // ISO 时间
}
```

| 字段 | 类型 | 语义 | 何时非默认值 |
|---|---|---|---|
| `success` | `bool` | **业务结果的唯一真相** | 恒存在 |
| `code` | `number` | 与 HTTP 解耦的业务码 | 恒存在 |
| `message` | `string` | 成功提示 | 成功时为提示语，失败时为 `""` |
| **`err`** | `string` | **失败原因（唯一错误出口）** | **失败时必非空；成功时必为 `""`** |
| `data` | `T \| null` | 唯一载荷 | 无数据时 `null`（序列化时省略） |
| `timestamp` | `string` | 排障用时间戳 | 恒存在 |

### 2.2 三种标准响应

```jsonc
// ① 成功
{ "success": true, "code": 200, "message": "已删除 1 个节点（含子节点）",
  "err": "", "data": { "TotalCount": 12 }, "timestamp": "..." }

// ② 业务拒绝（请求本身是好的，只是这件事不能做）
{ "success": false, "code": 400, "message": "",
  "err": "该机构下存在子机构，请先删除子机构", "data": null, "timestamp": "..." }

// ③ 系统异常（代码/数据库出问题了）
{ "success": false, "code": 500, "message": "",
  "err": "操作失败，请联系管理员", "data": null, "timestamp": "..." }
```

> **顶层字段一律 camelCase** —— 已登记例外 **E1**（`[JsonPropertyName]` 显式输出）。`data` **里面**的业务对象一律 PascalCase（铁律七）。判据见 [20 §二 命名三分法](./20-前后端契约权威表-V1.md)。

## 三、语义矩阵（HTTP × body）

| 场景 | HTTP | `code` | `success` | `message` | `err` | 前端动作 |
|---|---|---|---|---|---|---|
| 业务成功 | **200** | 200 | `true` | 提示语 | `""` | 绿色提示 / 继续 |
| **业务拒绝**（校验不过 / 不存在 / 重复 / 被引用 / 有子节点 / 权限业务规则） | **200** | 400 | `false` | `""` | **非空** | 红色，显示 `err` |
| **系统异常**（未处理异常） | **500** | 500 | `false` | `""` | 非空（脱敏） | 红色，显示 `err` |
| 未登录 / Token 过期 | **401** | — | — | — | — | 清 Token，跳登录 |
| 无权限（角色未关联接口） | **403** | — | — | — | — | 红色「无权限」 |
| 接口不存在 / 路由 404 | **404** | — | — | — | — | 红色「接口不存在」 |
| 网络失败 / 域名错 / CORS | 无响应 | — | — | — | — | 红色「网络错误」 |

### 3.1 为什么业务失败用 HTTP 200

用户理念：**「请求肯定是成功的」** —— HTTP 状态码描述的是「这次 HTTP 交互本身有没有问题」，不是「业务有没有办成」。业务办没办成，是**响应体**的事。

| 做法 | 后果 |
|---|---|
| 业务失败 → 400/404/409（**现状**） | 前端必须**同时**判断两套信号（HTTP + body），漏判任意一套就出 bug；监控里 4xx 混杂「真错误」与「正常业务拒绝」，无法区分 |
| 业务失败 → 200 + `success:false`（**目标**） | `!res.ok` 只剩 401/403/404/500 四种**基础设施错误**，业务判断全部收敛到 `success` 一个点；4xx/5xx 回归「系统真的有问题」的本义 |

### 3.2 为什么保留 `code` 而不造 999

- `code` 现有语义（200/400/500）保留，**与 HTTP 解耦**，仅供日志/排障/监控聚合。
- **不引入自造编号**（如 999「业务异常」）：参考实现 `ApiResult.cs` 中**不存在任何数字错误码**，编号会成为第二套需要维护的真相。
- **前端禁止读 `code`**（守卫 `guards.mjs` R3/R3b 已禁 `res.code === 200` 写法，现存 3 处为 E7 存量，待 §十 消灭）。
- 错误**分类**不靠编号，靠 `err` 文案 + 后端 `data.errorCode`（见 §九）。

## 四、四条不变量（放行红线）

```
① success === false   ⇒   err !== ""      // 禁止「失败了却没说为什么」
② success === true    ⇒   err === ""      // 禁止「成功了却带着错误」
③ 业务失败不得翻转 HTTP 状态码              // 业务拒绝必须 200
④ 响应体必须是 ApiResponse / ApiResponse<T>  // 禁止匿名对象、禁止 Result 直接外泄、禁止 msg/error 等变体字段
```

- **守卫抓手**：① ② 是**新字段 `err`，基线天然为 0**，规则第一天就能启用（不违反「基线不为 0 不许启用」铁律）；④ 由后端 `scripts/backend/guards.mjs` 新增 B-R1（禁 `Ok(new {`）/ B-R2（禁 `new ApiResponse`）覆盖。
- **运行时抓手**：`ApiResponseContractFilter`（ActionFilter）在**放行前**校验 ①②，违规即抛错，绝不让违规响应流到前端。

## 五、错误的四分类（前端要区分的）

| 分类 | 触发 | 判据 | 文案 |
|---|---|---|---|
| **① 网络错误** | 断网 / 域名错 / CORS | `fetch` reject | 网络连接失败，请检查网络 |
| **② 接口不可达** | 服务没起 / 路由 404 / 500 | `!res.ok`（401/403/404/500） | 401→跳登录；403→无权限；404→接口不存在；500→系统异常，请联系管理员 |
| **③ 业务拒绝** | 规则不满足 | `res.success === false` | **原文显示 `res.err`** |
| **④ 信封违规** | 后端返回体没有 `success` | `typeof res.success !== 'boolean'` | 开发环境告警「信封违规」，生产按 E7 兼容分支 |

> **`success` 是唯一业务判据**（不变量①的对偶）。**禁止**用 `message` 是否为空、`code` 是否为 200、`data` 是否为 null 去反推成败。

## 六、前端唯一读取顺序（L1 → L4）

```ts
async function request<T>(...) {
  // L1 网络层 —— fetch reject
  let res: Response
  try { res = await fetch(url, opts) }
  catch { throw new ApiError('network', '网络连接失败，请检查网络') }

  // L2 HTTP 层 —— 只剩 401/403/404/500 四种基础设施错误
  if (res.status === 401) { tokenStore.clear(); onUnauthorized(); throw new ApiError('http', '登录已过期', 401) }
  if (!res.ok) {
    const body = await res.json().catch(() => null)   // ⚠️ 401/403 可能是空响应体，不 catch 会抛 JSON 解析错
    throw new ApiError('http', body?.message ?? httpText(res.status), res.status)
  }

  // L3 业务层 —— 唯一业务判据
  const body = await res.json().catch(() => null)
  if (body && body.success === false) throw new ApiError('business', body.err || body.message || '操作失败')

  // L4 信封层 —— 无 success 字段 = 违规
  if (!body || typeof body.success !== 'boolean') warnEnvelope(body)
  return body as ApiResponse<T>
}
```

**顺序不可交换**：先看 HTTP 才知道该不该读 body；先读 body 会踩空响应体；先看 `success` 会把 500 当成业务拒绝。

**宿主必须注入错误出口**（`onError`），否则 L1/L2 抛出的异常会变成 `unhandledrejection`，屏幕上什么都不显示：

```ts
// cert-admin/src/main.ts · cert-auditor/src/main.ts
configureYzhApi({
  baseURL: import.meta.env.VITE_API_BASE ?? '',
  onError: (e) => { if (!e.handled) ElMessage.error(e.message) },   // ApiError.handled 防双弹
})
app.config.errorHandler = (err) => console.error('[YZH]', err)
```

## 七、后端怎么返回（写法规范）

### 7.1 ✅ 必须用这 5 种

| 场景 | 写法 | 落点 |
|---|---|---|
| 成功（有数据） | `return Ok(ApiResponse<T>.Ok(data, "保存成功"))` | `ApiResponse.cs` |
| 成功（无数据） | `return Ok(ApiResponse.Ok("已删除"))` | 同上 |
| **业务失败** | `return Ok(ApiResponse.Fail("该机构下存在子机构"))` | 同上（P1 起新增 `BizFail`，HTTP 恒 200） |
| 系统异常 | 抛 `YZHBusinessException` 等业务异常族，由 `GlobalExceptionFilter` 统一包装 | `Filters/GlobalExceptionFilter.cs` |
| 服务层结果 | `Result<T>` / `Result` → `result.ToApiResponse()`（**必须转换，不得直接外泄**） | `Result.cs` |

### 7.2 ⛔ 禁止这 7 种（每条都是实测病灶）

| # | 禁止写法 | 症状 | 实测现状（2026-09-25） |
|---|---|---|---|
| **B01** | `return Ok(ApiResponse.Ok(result))` **无条件包成功** | handler 返回任何东西都是 `success:true` | `TreeTableControllerBase.cs:305` |
| **B02** | handler 用「返回字符串」表达失败 | 错误文本进 `data`，`success:true` | `OrganizationController.cs:331,345` 等 |
| **B03** | `Ok(new { code=400/500, ... })` 匿名对象 | **无 `success` 字段**，前端只能读 `code`（E7） | **132 处**，Top：`StandardDirectoryController`(35) / `ReportDefinitionController`(25) / `DocExtractionRuleController`(21) / `FileStorageController`(13) |
| **B04** | `return BadRequest(msg)` 表达业务拒绝 | 翻转 HTTP 状态码，触发前端 L2 而非 L3 | **130 处**（三基类 56：TreeTable 24 / Tree 17 / Yzh 15） |
| **B05** | `await Xxx.Update(...)` **丢弃返回值** | 更新失败仍 `count++`，报「已禁用 N 个」 | `OrganizationController.cs:338,358,373,389` |
| **B06** | `catch { return 0; }` / `SoftDelete` 结果不判 | **假 0 / 假成功**，绕过「有子节点禁删」拦截 | `EntityService.cs:284-323,568-586` |
| **B07** | 直接 `return result`（`Result`/`Result<T>`） | 泄漏 `error` 字段的**第二套信封** | 实测 0 处，**保持 0** |

### 7.3 错误信息脱敏规则

| 异常类型 | `err` 内容 | HTTP |
|---|---|---|
| **业务拒绝**（`YZHNotFound` / `YZHDuplicate` / `YZHReferenced` / `YZHBusiness` / `YZHValidation`） | **原文返回**（已知业务语义，用户必须看到） | **200** |
| **系统异常**（`NullReference` / `SqlException` 等未处理） | 生产环境**脱敏**：「操作失败，请联系管理员」 | **500** |

> ⛔ **永不返回**：`StackTrace`、SQL 语句、连接串、服务器物理路径。
> ⚠️ **现状缺陷**：`GlobalExceptionFilter.cs:106` 在非开发环境把**业务异常的原文也一并替换**成「操作失败，请联系管理员」→ 用户永远看不到「机构不存在」这类真实原因。改造时应**只脱敏系统异常，业务拒绝保留原文**。

### 7.4 禁止直接外泄 `Result` 的原因

`Result<T>` 自带另一套 JSON 形状（`{data, error, code, success, timestamp}`，错误字段叫 **`error`** 而非 `err`/`message`）。一旦直接返回，前端会拿到**两种信封**，`error` 与 `err` 只差一个字母，是最容易写错的一类 bug。→ 统一走 `ToApiResponse()`，错误文本**在转换时写入 `err`**。

## 八、字段语义细则（谁负责说什么）

| 字段 | 谁写 | 说给谁 | 内容约束 |
|---|---|---|---|
| `message` | 后端（成功时） | **用户** | 短、肯定句、「已删除 1 个节点」；失败时 `""` |
| **`err`** | 后端（失败时） | **用户** | 可执行的失败原因，带定位信息（哪个机构、哪一步）；**禁止**技术术语、堆栈、英文异常名 |
| `data` | 后端 | **程序** | 业务数据；错误元数据若需结构化放 `data.errorCode` |
| `data.errorCode` | `GlobalExceptionFilter` | **程序** | `NOT_FOUND` / `DUPLICATE` / `REFERENCED` / `FORBIDDEN` / `INTERNAL_ERROR` —— **已存在的半个错误码体系**，前端做**分支跳转**可用，做**文案**不可用 |
| `code` | 后端 | **日志/监控** | 200/400/500；**前端禁止读** |
| `Result.Error` | 服务层 | **转换层** | 只在服务层内部流转，`ToApiResponse()` 时落到 `err` |

**`err` 命名取证**（为什么不是 `error`）：前端 `error` 已被占用 **103 处**（`ApiError` 属性、DOM、catch 变量）；`err` 实测占用 **0 处** → 零冲突。
