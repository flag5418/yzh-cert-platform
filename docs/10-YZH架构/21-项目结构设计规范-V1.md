# 项目结构设计规范 V1

> **本文定位**：**框架层规范**（L1 视角，非本项目目录说明 —— 见 §〇之前「本文的层次定位」）。
> 回答**唯一一个问题** —— **「这段代码该放哪？」**
> 具体说，回答 7 个子问题：
> ① **哪些东西必须放进 `yzh.vue.core`**（框架层）② **哪些必须留在项目代码里**（宿主层）
> ③ **项目如何调用 `yzh.vue.core`**（三条链路）④ **多角色端（后台管理 / 专家系统 / 未来机构平台）如何遵循同一套结构**
> ⑤ **项目如何「覆盖 / 穿透」框架默认**（路由 · 样式 · 环境配置 · 实体复用 —— §3.5–3.8）
> ⑥ **core 导出哪些能力、宿主该如何引用**（export 契约 —— §十）
> ⑦ **当前结构有哪些问题、怎么演进**（S1–S11 · R-S1–R-S10 —— §八 / §九）
>
> **为什么需要本文**：本项目是**多角色项目**（后台管理系统 + 专家系统 + 未来机构平台）。
> 没有统一结构 → 每个端各长一套 → **单人维护时无法理解全貌** → 改一处影响整体。
> **本文是结构的唯一权威。** 新增角色端前必读。
>
> **一句话记住核心**：**core 保留能力并导出，宿主只做组装与覆盖。**
> - **能覆盖的**：路由 / 页面 / 样式 / 环境配置 / 品牌（§3.5–3.7）
> - **只能引用的**：用户 / 机构 / 角色 / 字典 / 认证 / 表格表单内核（§3.8）
> - **只能放宿主的**：业务页面 / 业务 API / 业务文案（§2.2）
>
> **配套文档**：`19-前端分层与宿主接入规范-V1.md`（技术接缝细节）｜`18-YZH架构规则-V1.md`（规则总集）｜`样板页面指南-V1.md`（动手）

> 用户 2026-09-24 指出：「**针对项目的结构设计，还是一个框架性的东西**」。

**本文是「框架层规范」，不是「本项目目录说明」。**

| 维度 | 说明 |
|---|---|
| **归属层** | **L1 框架层**。它约束的是**框架如何被任何项目接入**，而不是本项目有哪些页面 |
| **可迁移性** | **换一个业务域、换一个项目，本文的骨架仍然成立** —— 只要它复用 `yzh.vue.core` |
| **本体 vs 实例** | 本文给出的是**本体（结构契约）**；`cert-admin` / `cert-auditor` / `cert-enterprise` 只是**实例（示例）** |
| **失效判据** | 若某个结论**只对"体系认证"这个业务成立**，它就不该写在本文，应写进 `20-体系认证/` |

### 本体 / 实例 二分（读本文时始终带着这个分界）

| 类型 | 内容 | 位置 | 换项目时 |
|---|---|---|---|
| **★ 本体（框架通用）** | 三层结构 L1/L2/L3 · 四问决策树 · 引用方向单向 · 路由覆盖机制 · 样式令牌穿透 · 环境配置三层 · 能力导出面 | **本文 §一–§十** | **不变** |
| **实例（本项目）** | 具体端名 `cert-admin`/`cert-auditor`/`cert-enterprise` · 具体令牌值（`#1e3a8a`）· 具体业务路由 · 具体 11 个 system 页面清单 | 本文中的**举例**，权威在代码与 `20-体系认证/` | 替换 |

**一条自检**：读本文任何一句，问 **「换一个业务域，这句还成立吗？」**

**本文的可迁移用法**：新增一个角色端 / 开一个新项目时，直接照 §四「标准目录骨架」+ §六「checklist 6 步」执行 ——
**不需要重新设计结构**，因为结构是框架给的，不是项目定的。

## 〇、一页纸

```
┌────────────────────────────────────────────────────────────────────┐
│  L1  yzh.vue.core/          ← 框架层：与业务无关，任何新角色零改动复用  │
│      （原子组件 / 内核 / 契约 / 适配器 / 装配原语 / 平台底座页面）        │
├────────────────────────────────────────────────────────────────────┤
│  L2  cert/cert-share/       ← 共享业务层：被 ≥2 个角色端使用的业务能力   │
│      （业务 API / 业务组件 / 业务类型）                                │
├────────────────────────────────────────────────────────────────────┤
│  L3  cert/cert-admin/       ← 宿主层：只被本端使用的页面/路由/store     │
│      cert/cert-auditor/        每端 = 一个独立可运行的 Vue 启动框架      │
│      cert/cert-enterprise/                                            │
│      cert/cert-{未来角色}/                                            │
└────────────────────────────────────────────────────────────────────┘
        ▲ 引用方向严格单向：L3 → L2 → L1。⛔ 反向引用 = 结构违规。
```

**一句话判据**：**「换一个业务域 / 换一个角色端，它还能用吗？」** 能 → L1；被两个以上端用 → L2；只被一个端用 → L3。

## 一、三层结构定义

### 1.1 与参考项目家族的对应（不是巧合，是同构）

| 本项目（Vue/TS） | 参考项目家族（WPF/C#） | 职责 |
|---|---|---|
| `yzh.vue.core` | `YZH.WPF.Core` | **框架层**：与业务无关的通用能力 |
| `cert/cert-share` | `Share/YZH.Survey.Lib` | **共享业务层**：被多个宿主复用的业务 |
| `cert/cert-admin` / `cert-auditor` / `cert-enterprise` | `SurveyResult.Lib` 等宿主 | **宿主层**：具体角色的可运行程序 |

**这套三层不是为整齐而设**，它在参考项目家族里已被验证：**庞大的系统没有几个真页面**，因为「基类即页面」—— 能力在 L1/L2，宿主只做组装。

### 1.2 逐层定义

| 层 | 目录 | 放什么 | 不放什么 |
|---|---|---|---|
| **L1 框架层** | `src/certplatform-web/yzh.vue.core/src/` | ① 原子组件（`YzhTable`/`YzhForm`/`YzhTree`…）② 页面逻辑内核（`SingleTableCore`/`TreeTableCore`…）③ **契约**（`types/contracts.ts`）④ 适配器（`adapters/`，EntityConfig → 组件契约）⑤ 装配原语（`composables/`）⑥ **平台底座页面**（`pages/system/` 用户/角色/菜单/字典 —— **所有角色端都要**，故属框架层）⑦ 通用工具（`utils/`） | ⛔ 业务实体名（`CertStage`/`ISOStandard`）⛔ 具体后端地址 ⛔ 业务文案 ⛔ 单一角色专属页面 |
| **L2 共享业务层** | `src/certplatform-web/cert/cert-share/src/` | ① 跨端业务 API（`api/cert/`、`api/workflow/`）② 跨端业务组件（`components/workflow/`）③ 跨端业务类型（`types/cert.ts`）④ 跨端业务 composable | ⛔ **Logic 基类**（在 L1）⛔ **契约类型**（在 L1 `types/contracts.ts`）⛔ 单一端页面 |
| **L3 宿主层** | `src/certplatform-web/cert/cert-{role}/src/` | ① 本端页面（`pages/`）② 本端路由表（`router/`）③ 本端 store（`store/`）④ 启动入口（`main.ts`/`App.vue`）⑤ 构建配置（`vite.config.ts`/`tsconfig.json`） | ⛔ 通用组件（应上移 L1）⛔ 跨端 API（应上移 L2） |

> **⚠️ 常见误判**：以为 `yzh.vue.core/src/pages/system/` 是「业务页面放错层」。
> **不是** —— 用户/角色/菜单/字典/日志是**平台底座**，**每个角色端都要**（超管进任何端都要管用户），
> 且它**只依赖 L1 契约**、不依赖任何业务实体。**符合 L1 判据**（换角色端仍能用）。

## 二、★ 边界判据：一个东西该放哪

### 2.1 四问决策树（按顺序问，第一个「是」即为答案）

```
Q1  它是否与具体业务域无关？（换一个业务域还能用）
     ├─ 是 → 【L1 yzh.vue.core】
     └─ 否 → Q2

Q2  它是否定义「契约」？（后端返回什么形状 / 前端怎么解析）
     ├─ 是 → 【L1 yzh.vue.core】   ← 契约必须单点，否则各端解析不一致
     └─ 否 → Q3

Q3  它是否被 ≥2 个角色端使用？
     ├─ 是 → 【L2 cert-share】
     └─ 否 → Q4

Q4  它是否只被 1 个角色端使用？
     └─ 是 → 【L3 该端宿主】
```

**快速判据（口语版）**：

| 场景 | 归属 | 为什么 |
|---|---|---|
| 我要加一个「表格列自动按 `Sxh` 排序」的能力 | **L1** | 与业务无关，所有端都要 |
| 我要加一个「认证标准选择器」组件 | **L2** | 认证业务，admin + auditor 都要 |
| 我要加一个「专家任务列表」页面 | **L3 auditor** | 只有专家端有 |
| 我要加一个「企业档案表单」类型 | **L2** | 企业端 + 专家端都要读 |
| 我要改 `ApiResponse` 的字段 | **L1** | 契约，单点权威 |
| 我要加「上传文件到 MinIO」 | **L1** | 通用能力（已在 `api/file-storage.ts`） |

### 2.2 反向禁止清单（**必须留在项目代码里，不得进 core**）

| ⛔ 禁止进 `yzh.vue.core` | 理由 |
|---|---|
| 业务实体名（`Sys_User` 之外的 `CertStage` / `ISOStandard` / `Ent_Enterprise`） | 换业务域就废 → 违反 Q1 |
| 具体后端路由（`/api/CertStage/filter`） | 框架层零硬编码后端地址（守卫 **R11**） |
| 业务文案（「请先选择机构」） | 文案属业务，core 只给默认文案 + 允许覆写 |
| 具体业务字典（`stage_category`） | 字典是数据不是能力 |
| 单一角色专属页面 | 违反 Q4 |

### 2.3 结构演进规则（什么时候该搬家）

| 触发 | 动作 | 判据 |
|---|---|---|
| 第 2 个端开始用同一个组件/API | **L3 → L2** 上移 | 被 ≥2 端使用 |
| 发现它其实与业务无关 | **L2/L3 → L1** 上移 | 换业务域仍能用 |
| 发现它只被 1 个端用 | **L2 → L3** 下移 | 只被 1 端用 |
| 发现它在 core 里 import 了业务实体 | **立即上移/改写** | ⛔ 结构性违规 |

> **上移必须同步 3 件事**：① 改 import 路径 ② 更新 `yzh.vue.core/src/index.ts` 导出 ③ 跑 `guards.mjs`。

## 三、★ 项目如何调用 `yzh.vue.core`（三条链路）

**三条链路缺一不可**，分别解决「代码从哪来」「后端地址从哪来」「页面怎么挂上」。

### 链路 1｜构建期：源码 alias（**不走 dist**）

宿主 `vite.config.ts` + `tsconfig.json` 都指向 **core 的源码**，而不是打包产物：

```ts
// cert/cert-admin/vite.config.ts（实测）
resolve: {
  alias: [
    { find: '@',          replacement: resolve(__dirname, 'src') },
    { find: '@yzh-core',  replacement: resolve(__dirname, '../../yzh.vue.core/src') },
    { find: '@share',     replacement: resolve(__dirname, '../cert-share/src') },
  ],
}
```

```jsonc
// cert/cert-admin/tsconfig.json（实测）
"paths": {
  "@/*":        ["./src/*"],
  "@yzh-core":  ["../../yzh.vue.core/src/index.ts"],
  "@yzh-core/*":["../../yzh.vue.core/src/*"],
  "@share/*":   ["../cert-share/src/*"]
}
```

**为什么走源码不走 dist**：
- 改 core **立即在宿主生效**，无需先 `build:core`
- 类型定义**直接可跳转**（`F12` 进 core 源码）
- 避免「dist 没更新 → 宿主行为与源码不符」这类难查问题

**代价**：宿主构建会编译 core 源码 → 构建稍慢；且 core 的**类型错误会在宿主 build 时暴露**（这是好事）。

### 链路 2｜启动期：注入后端地址

`yzh.vue.core` **不感知后端地址**（守卫 **R11** 保证 core 零硬编码）。
宿主在 `main.ts` 里注入：

```ts
// cert/cert-admin/src/main.ts（实测，auditor 逐行一致）
import { configureYzhApi } from '@yzh-core'

configureYzhApi({ baseURL: import.meta.env.VITE_API_BASE ?? '' })
```

→ 开发期 `''` 走 vite proxy（`/api` → `127.0.0.1:9992`）；生产期由 `VITE_API_BASE` 指定。

### 链路 3｜装配期：宿主拼路由，core 提供路由片段

core 提供**路由片段**，宿主负责**组装**：

```ts
// core 提供（yzh.vue.core/src/router/index.ts，实测）
export const yzhLoginRoute        // 登录
export const yzhHomeRoute         // 首页
export const yzhSystemRoutes      // 系统底座 11 条（用户/角色/菜单/字典…）
export function createYzhRoutes(options)   // 统一装配入口

// 宿主组装（cert/cert-admin/src/router/index.ts）
// ⚠️ 现状：宿主手写 routes 表，只借用了 yzhSystemRoutes（未用 createYzhRoutes）→ 见 §八 S2
```

### 3.4 三种调用姿势速查

| 我想用 | 怎么写 |
|---|---|
| 用组件 | `import { YzhTable, YzhFormDialog } from '@yzh-core'` |
| 用内核 | `import { SingleTableCore, TreeTableCore } from '@yzh-core'` |
| 用契约类型 | `import type { EntityConfigDto, ColumnConfig, TreeNode } from '@yzh-core'` |
| 用共享业务 API | `import { getISOStandardPage } from '@share/api/cert/iso-standard'` |
| 用共享业务组件 | `import { WorkflowDesigner } from '@share/components/workflow'` |
| ⛔ 不要用 | `import ... from '../../../yzh.vue.core/src/...'`（相对路径穿透）｜`from 'yzh.vue.core'`（包名，与 alias 双源） |

### 3.5 ★ 路由与页面的「覆盖」：宿主决定**去哪**

core 提供 `createYzhRoutes(options)`，**4 个覆盖开关**：

| 开关 | 作用 | 缺省 |
|---|---|---|
| `login?: boolean` | 是否注册 core 原子登录页 | `true` |
| `home?: boolean \| RouteRecordRaw` | 首页：`true`=core 占位首页｜`false`=不注册（宿主自供）｜传路由=自定义仪表盘 | `true` |
| `businessRoutes?: RouteRecordRaw[]` | 宿主业务路由（挂 shell 子路由） | `[]` |
| `branding?: {...}` | 品牌注入（`logoText`/`appTitle`/`login.*`） | `{}` |

**两种姿势（二选一）**：

| 姿势 | 写法 | 何时用 |
|---|---|---|
| **A 引用原子路由** | `createYzhRoutes({ ... })` 或 `...yzhSystemRoutes` | 少写代码、跟随 core 演进 |
| **B 手写覆盖** | 自己写 `{ path: '/login', component: () => import('@/pages/my/Login.vue') }` | 换皮肤 / 换交互 |

> **★ 铁律：`path` 单一来源。** 同一条 path 在宿主与 core 各注册一次 → vue-router 只认先注册的，**后注册静默失效**（不报错、不警告）。

**覆盖登录页 / 首页（专家端、机构平台一定会用到）**：

```ts
// 姿势 B：手写覆盖（cert-admin 现用此姿势的变体）
const routes: RouteRecordRaw[] = [
  { path: '/login', name: 'Login', component: () => import('@/pages/auth/MyLogin.vue') }, // ← 覆盖
  { path: '/', component: () => import('@yzh-core/layouts/YzhAppLayout.vue'),
    props: { menuTag: 'auditor', logoText: 'YZH', appTitle: '体系认证专家平台' },
    children: [...yzhSystemRoutes, ...myBusinessRoutes] },
]

// 姿势 A：统一装配入口
const routes = createYzhRoutes({
  menuTag: 'auditor',
  login: false,                                   // ← 不注册 core 登录页
  home: { path: '', name: 'Home', component: () => import('@/pages/dashboard/index.vue') },
  branding: { appTitle: '体系认证专家平台', login: { appTitle: '专家登录' } },
  businessRoutes: [{ path: 'tasks', component: () => import('@/pages/tasks/index.vue') }],
})
```

**实测现状**：`cert-admin` 走**混合姿势**（手写整表 + 引用 `yzhSystemRoutes`），见 §八 S2。

#### ★ 3.5b `path` 单一来源的机器校验：守卫 R12（2026-09-24 新增）

`Sys_Menu.Url` 与前端路由 `path` **是同一事实源的两种表示**（实测：24 条叶子菜单 ↔ 24 条路由，逐字一致）。据此把「靠人遵守」升级为「机器可查」：

| 约束 | 内容 |
|---|---|
| **菜单 → 路由** | 每条菜单 `Url`（`Url = '/'` 的分类节点除外）**必须**有对应路由，否则点击必白屏 |
| **路由 → 菜单** | 每条路由**必须**能从菜单到达；确需隐藏（详情页等）→ 登记进 `guards.mjs` 的 `ORPHAN_ALLOW` 并写明理由 |
| **结构性豁免** | `/login`、`/register`、`/`（应用壳）永远不需要菜单入口 |

执行方：`src/certplatform-web/scripts/guards.mjs` 的 **R12**；数据源：`scripts/db/verify/menu-urls.tsv`（由 `sync_menu_urls.sh` 从 `Sys_Menu` 只读导出）。

```bash
./scripts/db/verify/sync_menu_urls.sh                 # 菜单变更后重新生成快照
cd src/certplatform-web && node scripts/guards.mjs    # R12 双向校验（已挂 build / pre-commit）
```

> **为什么用快照而非直连数据库**：守卫必须能在无数据库环境（CI / 干净检出）运行。代价：菜单变更后须重跑 sync，否则基于过期数据。

#### ★ 3.5c 动态路由（菜单即路由）—— 已评估，**方向正确但当前不引入**

2026-09-24 实测结论：

| 维度 | 事实 |
|---|---|
| `Url` 能否直接当 `path` | ✅ 能（33 条菜单的 `Url` 与前端 `path` 逐字一致） |
| `Url` 能否推导**组件路径** | ⛔ **不能** —— 4 处硬反例（`/cert/iso-standard` → `pages/foundation/…`；`/business/nc-config` → `pages/workflow/nc-config/designer.vue`）⇒ **`Component` 字段省不掉**，须 DB 迁移 + 菜单管理页加录入项 |
| 组件动态解析机制 | 项目**从未用过** `import.meta.glob`（动态路由的必需依赖）⇒ 属"引入新构建期机制"，须实测打包行为 |
| 收益 | 「改路径不发前端版」在**单人同机部署**下 ≈ 0；「菜单与路由单一事实源」**已由 R12 以零运行时风险拿到** |
| 风险 | `Component` 字符串 ↔ 前端文件路径**无编译期保护** ⇒ 拼错 = 运行时白屏 + 控制台零报错（铁律七症状的翻版） |

**重启条件**（满足任一即应重新评估）：需要多端 / 多客户部署｜菜单需频繁增改｜有第二人参与前端开发。
**实施前提**：先出设计文档 → 评审 → 实施；**不与正在进行的端开发并行**（改 `router/index.ts` 会撞车）。

### 3.6 ★ 样式穿透：宿主决定**长什么样**

**机制 = CSS 自定义属性（design tokens）。** 一句话：

> **core 组件不写死颜色/间距，只写 `var(--yzh-*, fallback)`；宿主在 `:root` 里给值 → 换主题 = 换一个 CSS 文件。**

| 事实（实测） | 值 |
|---|---|
| core 自带样式文件 | **0 个**（`core/src/assets/` 只有 `README.md`） |
| core 组件引用令牌方式 | `var(--yzh-color-bg-card, #fff)` —— **全部带兜底值** |
| 宿主令牌定义处 | `cert/cert-admin/src/assets/css/main.css` 的 `:root`（**85 个令牌**） |
| 令牌两类 | `--yzh-*` 自有（color 28 / font 13 / space 9 / radius 4 / shadow 4 …）＋ `--el-*`（**覆盖 Element Plus**） |
| 加载顺序 | `element-plus/dist/index.css` → `./assets/css/main.css`（**main.css 必须后加载**，否则覆盖失效） |

**为什么这样设计是对的**：core **零样式依赖** → 换角色端不改 core；宿主换品牌色只改 `:root`，**不动任何组件**；`var()` 带兜底 → 宿主没定义也能看（只是不是主题色）。

**⚠️ 当前两个穿透缺口（G20，待补）**：

| 缺口 | 实测清单 | 影响 |
|---|---|---|
| **6 个 `--yzh-*` 被引用但未定义** | `--yzh-color-bg-card`｜`--yzh-color-text-regular`｜`--yzh-color-success-light-9`｜`--yzh-color-warning-light-9`｜`--yzh-color-danger-light-9`｜`--yzh-color-info-light-9` | 这 6 处**永远走 fallback 硬编码色**，宿主改主题**不生效** |
| **15 处硬编码 hex** | `YzhAppLayout.vue` 6｜`Home.vue` 5｜`Login.vue` 2｜`YzhStatusBadge.vue` 1｜`YzhSearchBar.vue` 1 | 同上，无法被宿主覆盖 |

**修法（约 0.5h）**：core 新增 `src/assets/css/tokens.css`，把 **85 个令牌的缺省值**从 `cert-admin/main.css` 搬进 core（作为「默认皮肤单一来源」），15 处 hex 改为 `var()`；宿主 `main.css` 只保留**品牌差异**部分。

### 3.7 ★ 环境与后端配置：宿主决定**对谁说**

**配置分三层，越往下越「项目私有」**：

| 层 | 放哪 | 例子 | 谁能改 |
|---|---|---|---|
| **L1 框架层** | ⛔ core **零配置** | —— | —— |
| **L2 环境配置** | `cert-{role}/.env.{development,staging,production}` | `VITE_API_BASE`、`VITE_APP_TITLE` | 部署 |
| **L3 项目配置** | `cert-{role}/src/config/*.ts` | 默认首页 path、菜单 Tag、品牌文案 | 开发者 |

**机制（实测已接线）**：

```ts
// cert-admin/src/main.ts:13（auditor 逐行一致）
configureYzhApi({ baseURL: (import.meta as any).env?.VITE_API_BASE ?? '' })
```

- `''`（缺省）→ 相对路径 `/api/*`：dev 由宿主 `vite.config.ts` proxy（`/api` → `127.0.0.1:9992`）承接；prod 由同源 / nginx 承接
- 绝对地址 → 跨域部署（前端与后端不同源）

**⚠️ 当前缺口（S9）**：**全仓没有任何 `.env` 文件** → `VITE_API_BASE` 恒为 `undefined` → 只能走相对路径 + proxy。**跨域部署 / 多环境目前没有配置入口。**

**规范（新增）**：

```
cert/cert-admin/
├── .env                  # 公共（提交）：VITE_APP_TITLE=映智汇认证平台
├── .env.development      # 开发（提交）：VITE_API_BASE=            # 空 = 走 proxy
├── .env.staging          # 预发（提交）：VITE_API_BASE=https://stg-api.example.com
└── .env.production       # 生产（提交）：VITE_API_BASE=https://api.example.com
```

- 只有 **`VITE_` 前缀**的变量会注入前端（Vite 约定）
- ⛔ **禁止在 `.env*` 里放密钥**（前端可见，等于公开）
- ⛔ **core 不得读 `import.meta.env`**（守卫 **R11**：core 零环境依赖，一律由宿主注入）
- 每个 `.env.*` 必须同步补 `src/vite-env.d.ts` 的 `ImportMetaEnv` 声明（否则 TS 退化为 `any`）

### 3.8 ★ 平台能力复用：core 已提供，⛔ 禁止重复建设

**core 的定位 = 「各种信息的保留 + 通过 export 导出能力」**。凡 core 已有，宿主**只引用不重建**。

| core 已提供 | 路径 | 宿主正确用法 |
|---|---|---|
| **平台底座 11 页** | `core/src/pages/system/{user,organization,role,menu,dictionary,config,log,api,role-user,role-menu,role-api}` | 直接用 `...yzhSystemRoutes`；⛔ **不得在宿主复制一份** |
| 登录页 / 首页 | `core/src/pages/auth/Login.vue`｜`core/src/pages/home/Home.vue` | 需要定制 → **覆盖**（§3.5），不是复制 |
| 应用壳布局 | `core/src/layouts/YzhAppLayout.vue` | 传 `props: { menuTag, logoText, appTitle }` |
| 系统 API 封装 | `core/src/api/system/{api,menu,role-api,role-menu,role-user}.ts` | `import { ... } from '@yzh-core'` |
| 认证能力 | `core/src/composables/useAuthState.ts`（**模块级单例**） | 宿主 `store/auth.ts` **只做 pinia 薄适配** |
| 装配原语 | `useAuth` / `useMenuTree` / `useMenuChanged` / `useConfirm` / `useCores` / `useTable` | 直接引用 |
| 表格/表单内核 | `logic/{SingleTableCore,TreeTableCore,AssociationTreeCore}` | 继承，不重写 |

**「薄适配层」范式（实测正确样例，`cert-admin/src/store/auth.ts` 全文）**：

```ts
import { defineStore } from 'pinia'
import { useAuthState, type UserInfo } from '@yzh-core/composables/useAuthState'

export type { UserInfo }
export const useAuthStore = defineStore('auth', () => useAuthState())
```

→ 真源在 core，宿主只保留 pinia 外观（使既有调用方零改动）。**这就是「引入架构的实体，不重复建设」的标准姿势** —— 用户/机构/角色/字典同理。

**⛔ 禁止清单**（在宿主出现 = 结构违规）：

- 复制 `pages/system/*`（P8 已收口，`cert-admin` 不得再抄）
- 自己实现 `login/logout/currentUser`（应走 `useAuthState`）
- 自己实现表格分页 / 搜索 / CRUD（应继承 `SingleTableCore`）
- 自己写 `fetch(` / `axios`（应走 `yzhApi`）

| # | 约束 | 检查 |

### 5.3 多 AI 分工下的结构纪律

> **用户已定分工**：一个 AI 负责**后台管理的测试和完善**，另一个 AI 全力实现**专家系统**。

| 分工 | 允许改 | 禁止改 | 冲突规避 |
|---|---|---|---|
| AI-A（后台管理） | `cert/cert-admin/src/**` | `cert/cert-auditor/src/**` | — |
| AI-B（专家系统） | `cert/cert-auditor/src/**` | `cert/cert-admin/src/**` | — |
| **共享区（L1 + L2）** | **改前必须公告 + 跑 `guards.mjs` + 三端 build** | — | **L1/L2 是唯一冲突面** |

**★ 结论**：**L1（`yzh.vue.core`）与 L2（`cert-share`）是多人/多 AI 的冲突面**。
→ 所以：**架构调整（L1/L2）由单一负责人执行**；**业务页面（L3）按端分工**。
→ 这正是「**架构不合理 → 直接调整；业务未按架构设计 → 形成清单**」的**结构学理由**。

## 七、core 内部目录职责（一句话速查）

## 九、结构演进规则

| 规则 | 内容 |
|---|---|
| **R-S1** | **引用方向严格单向**：L3 → L2 → L1。⛔ 反向引用 = 结构违规 |
| **R-S2** | 新增能力**先问四问决策树**（§2.1），**再决定放哪** |
| **R-S3** | 上移（L3→L2→L1）**必须同步**：import 路径 + `index.ts` 导出 + `guards.mjs` |
| **R-S4** | 新增角色端**必须复制 L3 骨架**（§4.3），**不得自创目录** |
| **R-S5** | 新增角色端**必须登记守卫 roots**（§六 ④），否则新端在守卫盲区 |
| **R-S6** | 宿主**不得出现** `app/` / `router/modules/` / `assets/gridconfig`（§4.3 ⛔ 清单） |
| **R-S7** | **L1/L2 改动 = 跨端影响** → 多 AI 协作时**必须公告 + 跑三端 build** |
| **R-S8** | 结构问题（S1–S11）**属于架构调整 → 直接做**；**业务页面未按结构 → 形成清单**（见 `输出产物/业务代码不合规清单-V1.md`） |
| **R-S9** | **覆盖而非复制**：core 已有能力（§3.8 表）宿主只能**覆盖**（§3.5）或**引用**，⛔ 不得复制第二份 |
| **R-S10** | **`path` 单一来源**：同一条路由 path ⛔ 不得在 core 与宿主各注册一次（vue-router 静默取先注册者） |
| **R-S11** | **样式只经令牌穿透**：宿主 ⛔ 不得用选择器覆盖 core 组件内部样式；要改 → 改 `--yzh-*` 令牌（§3.6） |
| **R-S12** | **core 零环境依赖**：core ⛔ 不得读 `import.meta.env` / 不得硬编码后端地址（守卫 **R11**）；一切由宿主 `main.ts` 注入 |
| **R-S13** | ★ **结构问题验收回到代码本身**：「已修复」的判据是 `grep` 到实现/声明消失 + 守卫基线 0 + 对应端 build 通过，**不认文档里的结论句**。发现文档写「已修」而实测未修 → 立即补修并更新文档（S12 教训） |
| **R-S14** | ★ **守卫规则必须核查扫描面**：新增/修改 `guards.mjs` 规则时，**必须确认 `roots` 覆盖该规则声称的范围**（R4 曾因 `CORE` 只指 `components/` 而漏扫 `utils/`，S13）。核查方式：`--report` 看扫描文件数是否随范围变化 |
| **R-S15** | ★ **框架能力须有真实调用方**：core 新增的能力（路由工厂 / composable / 内核）若长期零调用方 = 死代码，要么接入、要么删除（`createYzhRoutes` 曾是死代码，S15） |

## 十、★ core 能力导出面（export 契约）

> **core 的职责是「保留 + 导出」**：把与业务无关的一切**收进来**，通过 `index.ts` barrel **导出去**，宿主**只组装**。
> **判断 core 做得好不好，只看一件事：宿主能不能不写实现代码，只写装配代码。**

### 10.1 唯一入口：`yzh.vue.core/src/index.ts`（实测导出面）

```ts
// 组件
export { YzhForm, YzhFormDialog }                     // 表单
export { YzhDialog, YzhPageLayout, YzhPagination, YzhSearchBar, YzhToolbar,
         YzhTree, YzhTreeTableLayout, YzhTreeTableSelector, YzhTreeTableCheckSelector }
export { YzhTable, YzhTreeTable }
export { YzhCard, YzhEmptyState, YzhStatusBadge }

// 适配层（EntityConfig → 组件契约，纯函数）
export * from './adapters/entityAdapters'

// API
export { YzhApiClient, tokenStore, yzhApi }
export { uploadFile, uploadFileBatch, getFileUrl, deleteStorageFile, fileExists, listFiles }

// Composables / 内核 / 契约 / 工具
export * from './composables'
export * from './logic'
export * from './types/{Page,contracts,tree,association}'
export * from './utils/{treeOps,treeUtils,case}'

// ⚠️ router 不进 barrel —— 走子路径 @yzh-core/router
// ⚠️ configureYzhApi 从 @yzh-core/api/client 引（见 §3.7）
```

> **为什么 `router` 不进 barrel**：宿主 `router/index.ts` 是**启动链上的入口文件**，barrel 会把它牵连到全量组件 → 首屏体积与循环依赖风险。**子路径导入 = 精准拿所需。**

### 10.2 能力域 → 宿主用法速查

| 能力域 | 代表符号 | 宿主用法 |
|---|---|---|
| 组件 | `YzhTable` `YzhFormDialog` `YzhTree` `YzhCard` | 模板直接用 |
| 内核 | `SingleTableCore` `TreeTableCore` `AssociationTreeCore` | `class X extends SingleTableCore<any>` |
| 装配原语 | `useSingleTable` `useTreeTable` `useAuthState` `useMenuTree` `useConfirm` | 页面 `setup` 里调 |
| 契约类型 | `EntityConfigDto` `ColumnConfig` `TreeNode` `FilterRequest` `PagedData` | `import type { … }` |
| API | `yzhApi` `configureYzhApi` `tokenStore` | 宿主 `main.ts` 注入 baseURL |
| 适配器 | `toTableColumns` `toFormFields` `toSearchFields` `toFormLayoutCols` | 一般由内核代调，页面不直接调 |
| 路由 | `yzhLoginRoute` `yzhHomeRoute` `yzhSystemRoutes` `createYzhRoutes` | 宿主 `router` 组装（§3.5） |

### 10.3 三条导出原则

| # | 原则 | 说明 |
|---|---|---|
| **E-1** | **契约单点** | `types/contracts.ts` 是前后端字段契约的唯一来源。宿主 ⛔ 不得再定义一份 `ColumnConfig` / `TreeNode` |
| **E-2** | **导出能力，而非复制能力** | core 已有的一律 `import`。复制 = 分叉 = **单人维护时必踩**（这是本项目的核心约束） |
| **E-3** | **子路径 vs barrel 分治** | `@yzh-core/router` 走子路径（启动链入口）；其余走 barrel `@yzh-core`。新增能力默认进 barrel，**除非它在启动链上** |

### 10.4 反向：宿主必须自己保留的（不得进 core）

见 §2.2 反向禁止清单（业务实体名 / 后端路由 / 业务文案 / 业务字典 / 单角色页面），此处不重复。
