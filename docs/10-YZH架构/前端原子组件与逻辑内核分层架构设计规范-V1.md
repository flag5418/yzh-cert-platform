## 一、问题与目标

### 1.1 当前的核心问题

`YzhTable` 已经具备相当多的原子能力（行操作列自动生成、列设置、选择恢复、Split 行操作、搜索/分页）；但**边界不清**，导致三类问题：

| 问题 | 现象 | 根因 |
|------|------|------|
| **能力放错层** | 行按钮的颜色/宽度在组件里，但"该显不显示、点了做什么"散在业务 `.vue` 的 `switch`；工具栏按钮在业务 `.vue` 里手写 `v-if` | 未区分"呈现"与"业务处理" |
| **双实现** | `YzhCrudPage.vue` 直接 import `CrudPageLogic` 与 `@share/api/generic`，把整套 CRUD 又实现一遍；`YzhTreeTableCheckSelector` 与 `BaseRoleTreeLogic` 各自维护勾选/差集/级联 | 组件层与内核层互相渗透 |
| **特殊业务被迫复制** | `cert-org-standard` / `cert-org-stage` 两个页面逐行重复；非 CRUD 业务只能"抄一个 CRUD 页面再删" | 原子组件**必须**能独立组合，但缺少稳定的组合契约 |

### 1.2 目标

1. **原子组件可独立使用**：不依赖任何 Logic 基类，仅靠 props/events/expose 就能完成任意特殊业务。
2. **逻辑内核只保留"非 UI"职责**：端点、契约、生命周期、业务规则。
3. **能力下沉**：把基类里本质属于 UI 的能力（行按钮控制/工具栏声明/节点菜单/弹窗壳/状态列渲染）下沉到原子组件。
4. **动作统一分发**：消灭每个页面重复的 `handleRowAction` / `handleToolbarClick` switch。

### 1.3 分层模型

```
┌──────────────────────────────────────────────────────────────┐
│  业务页面层  pages/**                                         │
│  职责：选内核 + 选原子组件 + 业务 slot。不写端点、不写 UI 机制 │
└───────────────┬───────────────────────────┬──────────────────┘
                │ 使用                        │ 使用（可只用组件）
                ▼                            ▼
┌───────────────────────────────┐   ┌──────────────────────────┐
│  逻辑内核层  logic/*.ts        │   │  原子组件层  components/* │
│  CrudPageLogic                │   │  YzhTable / YzhTree      │
│  TreeTableLogic               │   │  YzhToolbar / YzhForm    │
│  AssociationTreeLogic …       │   │  YzhDialog / YzhTable / …  │
│  职责：端点、契约、生命周期、   │   │  YzhTreeTableLayout 为布局壳│
│  业务规则、动作分发             │   │  （非原子）见 06-§4.3      │
└───────────────────────────────┘   └──────────────────────────┘
        ▲  仅通过 Composable 装配（ref/事件）  ▲
        │                                      │
        └──────────── 依赖方向：页面 → 内核 ──────┘
```

**依赖铁律**：
- 组件 **禁止** import 任何 Logic / 任何 `@/api` / `@share/api`。
- 内核 **禁止** import 任何 Vue 组件（只允许 `vue` 响应式 API + `element-plus` 的 `ElMessage/ElMessageBox`）。
- 页面 **禁止** 直接 import `@/api/**`（除显式声明的白名单）。
- 装配只发生在 `composables/*`（把内核实例与组件 ref 连起来），页面只消费。

## 二、职责归属矩阵（核心）

> 判据三问：① 这条逻辑与"业务实体/端点"相关吗？② 它是"呈现/交互"还是"数据/规则"？③ 换个业务实体它是否原样复用？

| 能力 | 当前所在 | 目标归属 | 动作 |
|------|---------|---------|------|
| 列渲染 / formatter / `#column-x` slot | 组件 | **组件** | 保持 |
| 列设置 / 列排序 / 列显隐 | 组件 | **组件** | 保持 |
| 分页 / 加载态 / 空态 / 错误 + 重试 | 组件 | **组件** | 保持 |
| 多选 / 选择恢复 / `setCheckedRows` | 组件 | **组件** | 保持 |
| Split 行操作（insert/replace/remove） | 组件（内核转发） | **组件** | 保持 |
| **行操作列渲染：宽度估算/颜色/溢出/图标/禁用态** | 组件（部分） | **组件** | 补全图标/禁用/溢出菜单/loading |
| **行按钮的"有哪些、文案、是否可见"** | 内核 getter → 页面 switch | **描述符（data）+ 适配器** | 统一 `YzhAction` |
| **行按钮点击的"业务处理"** | 页面 `handleRowAction` switch | **内核 dispatch** | 新增统一分发 |
| **工具栏渲染** | 页面手写 `el-button v-if` | **组件 `<YzhToolbar :buttons>`** | 声明式下沉 |
| **工具栏按钮描述** | 内核 `toolbarButtons` | **描述符 + 适配器** | 统一 `YzhAction[]` |
| **工具栏业务处理** | 页面 `handleToolbarClick` | **内核 dispatch** | 新增统一分发 |
| 树节点下拉菜单渲染 / 动态文案 | 组件 `YzhTree` + 内核 `getNodeActionLabel` | **组件**（resolver 下沉） | 补 disabled/icon/divider |
| 树加载 / 懒加载 / 索引 | 内核 | **内核** | 保持 |
| 树搜索渲染 / 展开折叠 | 组件 | **组件** | 保持 |
| 表单渲染 / 校验展示 / 布局 | 组件 `YzhForm` | **组件** | 保持 |
| **弹窗壳（标题/页脚/loading/提交）** | 页面手写 `el-dialog` | **组件 `YzhFormDialog`** | 新增组件 |
| 弹窗状态（visible/mode/formData） | 内核 | **内核** | 保持 |
| CRUD 端点调用 / 流程 | 内核 | **内核** | 保持 |
| 通用确认弹窗（ElMessageBox 封装） | 内核 | **组件能力（hook）+ 内核文案** | 抽通用 `useConfirm` |
| 乐观更新 / 回滚策略 | 业务页面 | **内核** | 下沉 |
| 字典/状态列渲染（IsValid→tag） | 页面 `#column-IsValid` | **组件（列 `render:'tag'`）** | 下沉 |
| 字段映射（EntityConfig→columns/fields） | 内核 getter | **纯适配器模块** | 抽 `adapters/` |
| 权限/按钮可见性 | 未统一 | **待定（内核或指令）** | 见 R6 |

### 2.1 一句话边界

> **组件负责"怎么呈现与交互"，内核负责"数据是什么、来自哪里、业务规则是什么"。**
> **按钮的"控制"（显示/禁用/颜色/溢出）属于组件；按钮的"实现"（点了做什么）属于内核。**

## 二·补、原子组件自洽契约原则（零领域依赖）★核心原则

> **原子组件与后端接口无关、与具体实体类结构无关、与业务无关。**
> **每个原子组件拥有独立、完备的 props 与 events；只要参数正确、属性正确，组件即可工作。**

### 2.2 五大零依赖

| 零依赖 | 含义 | 不合格判据 |
|--------|------|-----------|
| **零端点** | 组件不发起任何 HTTP，不 import 任何 `@/api`、`@share/api` | 组件内出现 `yzhApi` / `fetch` / `axios` |
| **零实体** | 不 import 业务实体或共享类型（`@share/types/**`）；不假设字段名 | 组件内出现 `@share/*`；出现 `row.Code` / `node.Name` 之类常量 |
| **零业务** | 不认识 `IsValid` / `org` / `user` / 菜单等业务语义 | 出现 `=== 'IsValid'`、内置中文业务标签 |
| **零全局状态** | 不依赖 pinia / router / i18n / 鉴权 store | 组件内出现 `useStore()` / `useRoute()` |
| **零编排** | 不 import 任何 Logic / Composable | 出现 `CrudPageLogic` 等引用 |

### 2.3 属性完备性（"参数正确即可工作"）

> 组件的输出 = **F(props)**。除 `props / emits / expose / slots` 外，组件不得读取任何外部输入。

| 要求 | 说明 |
|------|------|
| 行为完全由 props 决定 | 相同 props ⇒ 相同渲染与相同事件序列（可预测、可测试） |
| **字段名参数化** | 所有数据字段读取必须来自 props（`rowKey / nodeKey / labelField / childrenField / parentField / checkField / ...`），禁止写死 `Code/Name/Children` |
| **语义映射外置** | 值→文案/颜色/标签的映射由 props 传入（`dict` / `valueMap` / `tagMap`），组件不内置业务映射 |
| **文案中立** | 组件仅保留通用 UI 文案（"暂无数据""取消"）；业务文案一律由 props 传入 |
| 可隔离运行 | 仅用 mock props 即可在无后端、无路由、无 store 的环境渲染交互 |
| 无副作用假设 | 不注册 window/document 全局监听，不假设运行时环境 |

### 2.4 适配层：唯一同时认识"两个世界"的翻译者

```
后端世界（约定 / 契约 / 实体 PascalCase / IsValid / dictCode）
        │  纯函数适配器（唯一同时认识两端）
        │  adapters/:  EntityConfig → 组件 props（columns / formFields / YzhAction）
        ▼
组件世界（纯 props / events，领域无关，可完全脱离后端工作）
        ▲
        │  内核持有适配器并做编排
逻辑内核（端点 / 数据 / 业务规则 / dispatch）
```

**只有适配器层允许出现业务字段名。** 组件层与实体彻底解耦；内核层只消费适配器输出。这样"特殊业务"既可以用组件 + 自有函数（无需后端约定），也可以走内核 + 适配器（遵守约定）。

### 2.5 现状违反点审计（实测证据）

| 组件 | 违反 | 证据 | 修复方向 |
|------|------|------|---------|
| `YzhTree.vue` | 零实体 ✗ | `import type { TreeNode } from '@share/types/tree'`（业务共享层，`@share → ../share/src`） | 改用组件自身 `../types` 的结构化类型 |
| `YzhTree.vue` | 字段硬编码 ✗ | `hoveredNode = data.Code`、`treeProps.label='Name'`、`children:'children'`；filter/expand 用 `node.Name/node.Code/node.Children` | 增 `nodeKey / labelField / childrenField` props |
| `YzhTreeTableLayout.vue`（布局壳） | 零实体 ✗ | `import TreeNode from '@share/types/tree'` | 同上 |
| `YzhTreeTableLayout.vue`（布局壳） | 字段硬编码 ✗ | `filterTreeData` 用 `node.Name/node.Children`；`nodeActions` 用 `data.Code` | 字段 props 化 |
| `YzhTreeTableCheckSelector.vue` | 零业务 ✗ | `DEFAULT_TYPE_LABELS={org:'机构',user:'用户'}`、`checkAllExcludeTypes:['org']`、`searchPlaceholder:'搜索接口名称 / 路径'` | 去默认业务语义，全部 props |
| `YzhTable.vue` | 零业务 ✗ | `getRowActionType` 内置 `edit/delete/disable/enable/toggle-valid → 颜色`（假设了 action key 语义） | 颜色取自 `YzhAction.type`，兜底通用色 |

| `YzhCrudPage.vue` | 零端点/零实体/零编排 ✗✗✗ | import `@share/api/generic`、`@share/types/contracts`、`CrudPageLogic` | 废弃或重构为纯组合 |

> 此表即"让组件真正业务无关"的施工清单，纳入 C 阶段；并用守卫固化（见 R9）。

## 三、契约设计：描述符 + 事件 + 命令

### 3.1 统一动作描述符 `YzhAction`

把"按钮"从"UI 元素"提升为"数据"，三层共享同一类型：

```ts
// components/table/types.ts（或 components/actions/types.ts）
export interface YzhAction {
  /** 动作键（业务/内置：edit/delete/toggle-valid/add-child/custom:xxx） */
  key: string
  /** 显示文字（支持函数：按行/节点动态） */
  text: string | ((target: any) => string)
  /** 按钮类型 */
  type?: 'primary' | 'success' | 'warning' | 'danger' | 'info'
  /** 图标（Element Plus 图标名） */
  icon?: string
  /** 是否禁用（按行/节点） */
  disabled?: boolean | ((target: any) => boolean)
  /** 是否可见（按行/节点） */
  visible?: boolean | ((target: any) => boolean)
  /** 是否次级（溢出到"更多"下拉） */
  overflow?: boolean
  /** 点击是否需要二次确认（通用文案由内核提供，见 useConfirm） */
  confirm?: boolean | string
  /** 排序权重 */
  order?: number
}

/** 行/节点动作集合：静态或按目标动态 */
export type YzhActions = Record<string, YzhAction> | ((target: any) => Record<string, YzhAction>)
```

> 兼容：现有 `Record<string,string>`（`{edit:'编辑'}`）继续可用，组件内部归一化为 `YzhAction`。

### 3.2 事件契约（组件只上抛"意图"）

| 组件 | 事件 | 载荷 |
|------|------|------|
| `YzhTable` | `row-action` | `(key, row, action)` |
| `YzhTable` | `toolbar-action`（新增） | `(key, action)` |
| `YzhTable` | `selection-change` / `row-click` | 行 |
| `YzhTree` / `YzhTreeTableLayout`（布局壳） | `node-action` | `(key, node, action)` |
| `YzhTreeTableLayout`（布局壳） | `tree-node-click` / `tree-check-change` | 节点 |
| `YzhTreeTableCheckSelector` | `check-change` | `{added,removed}` |
| `YzhFormDialog`（新增） | `submit` / `cancel` | formData |

组件**不**关心 key 的业务含义；内核通过 `dispatch` 解释。

### 3.3 命令契约（组件暴露"怎么做"）

已存在：`YzhTable.{refresh,loadData,insertRow,replaceRow,removeRow,getSelectedRows,setCheckedRows,clearSelection}`；`YzhTree.{expandAll,collapseAll,appendNode,setChecked...}`；`YzhTreeTableCheckSelector.{getCheckedKeys,setCheckedKeys,...}`。

**规范**：内核的增量方法与组件命令**一一对应**，不一致时以内核转发为准（如 `removeRowByCode` → `tableRef.removeRow(match)`）。

## 四、统一动作分发（Action Dispatcher）

> 这是"把按钮实现从页面下沉到内核"的关键机制，直接消灭每页重复的 `switch`。

### 4.1 机制

```ts
// CrudPageLogic / TreeTableLogic 内部
protected customHandlers: Record<string, (target: any) => Promise<void> | void> = {}

/** 统一动作入口：由组件 row-action / toolbar-action / node-action 直接调用 */
async dispatch(key: string, target?: any): Promise<void> {
  // 1) 业务注册的处理器优先
  const custom = this.customHandlers[key]
  if (custom) return await custom(target)

  // 2) 内置动作
  switch (key) {
    case 'add':            return void this.openAddDialog()
    case 'delete':         return await this.confirmDelete(target ? [target] : undefined)
    case 'edit':           return void this.openEditDialog(target)
    case 'toggle-valid':   return await this.toggleRowIsValidWithConfirm(target, { entityName: this.rowDisplayName(target) })
    case 'add-child':      return void this.openTreeNodeDialog('add', null, target)
    case 'node-edit':      return void this.openTreeNodeDialog('edit', target)
    case 'node-delete':    return await this.deleteTreeNodeWithConfirm(target)
    case 'export':         return await this.exportData()
    default:
      if (key.startsWith('custom:')) return await this.executeAction(key.slice(7), target)
  }
}
```

### 4.2 收益

- 页面/composable 里 **不再写** `if (action === 'edit') ... else if ...`。
- 内置动作（edit/delete/toggle-valid/add-child/export）**一次实现，全站生效**。
- 特殊页面只需 `registerHandler('approve', fn)`，不必动基类。

### 4.3 描述符 → 事件的完整链路

```
后端 config (RowButtons/Toolbar/CustomActions)
   │ 纯适配器 buildRowActions(config) / buildToolbarActions(config)
   ▼
YzhAction 描述符  ──props──▶  原子组件（渲染/控制：颜色/禁用/溢出/确认）
   │                                   │ 用户点击
   │                                   ▼
   └──────────────◀── row-action(key,row) ──┐
                                            │
                        内核 dispatch(key, target) ──▶ 内置动作 / 业务注册
```

## 五、原子组件增强清单（下沉任务）

> 以下为"把基类/页面里的 UI 能力下沉到原子组件"的具体项。组件增强必须在**不依赖 Logic** 的前提下可用。

| 行内可编辑（可选） | `editableColumns` | 无 |
| 数据源抽象 | `dataLoader` 已是函数契约，保持（**特殊业务可传任意函数**） | ✅ |

### 5.2 `YzhToolbar`

| 增强 | 说明 |
|------|------|
| `buttons: YzhAction[]` / `left`/`right` 分组 | 声明式渲染，emit `action` |

### 5.3 `YzhTree` / `YzhTreeTableLayout`（布局壳）

| 增强 | 说明 |
|------|------|
| `nodeActions: YzhActions` + `actionResolver` | 动态文案/禁用/图标下沉到组件 |
| 菜单分组/分隔线/danger 样式 | 从 `getDropdownItemClass` 扩展为描述符 |
| 树搜索防抖 + 不拷贝 | 组件内实现（性能） |
| 虚拟滚动（`virtual`） | 大树切换 `ElTreeV2` |
| 懒加载 loading 态 | 节点级 loading |

### 5.4 新增 `YzhFormDialog`（弹窗壳）

| 能力 | 说明 |
|------|------|
| `v-model:visible` + `mode: 'add'|'edit'|'detail'` | 标题按 mode 生成，可覆盖 |
| 组合 `YzhDialog + YzhForm` | 页脚：提交/取消；loading；`@submit`/`@cancel` |
| 插槽 | `#default`（表单）、`#footer`（自定义） |
| 收益 | 页面不再手写 `<el-dialog><YzhForm/></el-dialog>` 三处重复 |

### 5.5 新增 `useConfirm`（通用确认）

把 `ElMessageBox.confirm` 的封装（类型/文案/标题/取消静默）下沉为共享 hook，供组件与内核复用。**业务文案仍由内核传入**。

## 六、逻辑内核保留清单（**不**下沉）

| 保留在内核的能力 | 原因 |
|-----------------|------|
| 端点调用与约定（`config/filter/add/...`） | 业务/契约相关 |
| 数据状态（rows/treeData/selectedNode/pagination） | 数据所有权 |
| 生命周期（init/loadConfig/loadTreeRoot） | 编排 |
| 业务规则（required/默认值/是否允许新增/关联字段） | 业务 |
| 动作分发的**业务分支**（dispatch 的内置语义 + 注册处理器） | 业务 |
| 乐观更新 / 回滚 / 缓存 | 业务语义 |
| 字段映射（EntityConfig→columns/fields） | 建议抽为**纯适配器**，仍提供给它 |

## 七、特殊业务的组合范式

> 原子组件的价值在于**用组合表达标准基类覆盖不到的业务**。以下三种范式必须都成立：

### 范式 1：标准 CRUD（内核 + 组件）
`useCrudPage(Logic)` → `<YzhTable>` + `<YzhFormDialog>`。

### 范式 2：无内核的纯组件页面（特殊业务的核心）
自定义 `dataLoader` 只是普通函数，页面直接用组件：

```vue
<script setup lang="ts">
const load = async (params) => {
  const res = await mySpecialApi(params)     // 业务自有端点
  return { rows: res.list, total: res.total }
}
const actions = { view: { key:'view', text:'查看' } }
function onRowAction(key, row) { /* 特殊处理 */ }
</script>
<template>
  <YzhTable :columns="cols" :data-loader="load"
    :row-actions="actions" @row-action="onRowAction" />
</template>
```

**这是必须保障的契约**：组件不得假设存在 Logic。

### 范式 3：复合布局（原子组件拼装）
`<YzhTreeTableLayout>`（布局壳）内部已由 `YzhTree + slot(YzhTable)` 组成；类似地可用 `YzhToolbar + YzhTable + YzhPagination` 拼任意面板。**新页面优先用已有原子组件组合，而不是新建基类**。

### 7.1 关联型业务（role-* / link-org-*）的组合落点

- 类型A（选中-授权）：`YzhTree`（角色树）+ `YzhTreeTableCheckSelector`（勾选）→ 由 `CheckTreeLogic` 编排。
  - **下沉点**：`check-change` 差集、级联、全选已在组件；内核只做「端点 + 缓存 + 保存编排」。
- 类型B（勾选-关联）：`YzhTree` + `YzhTable`（`selectMode:'multiple'` 或自定义 `Linked` 列）→ 由 `LinkTableLogic` 编排。
  - **下沉点**：`YzhTable` 需补「初始化勾选抑制 + `setCheckedRows`」（已有 `setCheckedRows`）；内核做差集保存 + 乐观回滚。

## 十二、结论

1. **原子组件是前端架构的核心**：它必须能**脱离内核独立使用**，这是特殊业务的生存空间。
2. **能力下沉方向**：把基类里"呈现/交互"的能力（行按钮控制、工具栏声明、节点菜单、弹窗壳、状态列渲染）下沉到组件；把"业务处理"上收为内核统一 `dispatch`。
3. **统一契约**：描述符（`YzhAction`）+ 事件（`action(key,target)`）+ 命令（expose）。
4. **依赖铁律**：组件不碰逻辑/端点，内核不碰 UI，页面只组合。
5. **消灭双实现**：`YzhCrudPage` 与页面 `switch` 是当前最大的两处反模式。
6. **原子组件是自洽的、领域无关的参数化组件**：零端点、零实体、零业务、零全局状态、零编排；只要 props 正确即可工作。当前 `YzhTree`/`YzhTreeTableLayout`（布局壳）/`YzhCrudPage` 存在 `@share` 与字段硬编码违反点，须清零。
7. 待 R1–R10 确认后，按 C1–C9 与主计划 P 阶段并行落地。
