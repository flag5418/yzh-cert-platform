# 审核认知模型总纲

> 本文只讲模型，不讲实现。全文不出现任何表名、字段名、代码名。
> 读完之后你应该能回答：这个系统到底由几个模型组成、它们怎么连、每一层谁说了算、哪一步必须用 AI、哪一步绝不能用 AI。

---

## 零、为什么必须先把模型讲清楚

你现在遇到的困境，本质不是"提示词写得不好"，而是：

> **系统里有四层东西，但只有一层被真正建过，另外三层是用提示词的临时输出顶着。**

这四层是：

```
第一层  条款模型  —— 我们要问什么？（问题的形状）
第二层  文档模型  —— 答案在哪？（答案的容器）
第三层  证据模型  —— 答案是什么？（答案的摘录）
第四层  结论模型  —— 答案够不够？（答案的裁决）
```

现在的系统：第一层建了一半（条款树 + 属性池），第二层建了一小半（文档分类 + 抽取），第三层几乎没建（证据靠人工挂），第四层建了壳（判定词表）。

**缺的不是功能，是模型之间的接口。**而接口一旦没定义，模型就只能靠"一次提示词全干完"来硬凑——这就是为什么每次输出都是"未见记录"。

下面逐层讲。

---

## 一、第一层：条款模型（问什么）

### 1.1 条款的本质：一条可被检验的义务

标准里的条款不是一段文字，是**一条义务**。义务之所以能被"检验"，是因为它必然包含六个成分：

```
条款 = 谁（主体） + 做什么（动作） + 对什么（对象）
      + 在什么条件下（条件） + 留下什么痕迹（证据形式） + 怎样算做到（判定口径）
```

以"采购"为例（8.4.1）：

| 成分 | 内容 |
|---|---|
| 谁 | 采购部门（品质部门参与） |
| 做什么 | 建立准则、评价、选择、监视、再评价 |
| 对什么 | 外部供方 |
| 在什么条件下 | 按准则、定期、变更时 |
| 留下什么痕迹 | 采购控制程序（规定）+ 合格供方名录、评审表、业绩记录（记录） |
| 怎样算做到 | 名录经批准、评审多部门、有业绩记录、有再评价 |

**这六个成分就是"属性池"的理论来源。**属性池不是随便拍一堆属性，而是这六个成分的展开。

> ⚠️ **本节有修正**：上面这个六成分模型默认"所有条款结构相同"，这个假设不成立。
> 第 5 章（领导作用）既没有可查的"痕迹"，也没有可判的"口径"，用它就完全失效。
> 条款必须先按**章节（PDCA 环节）**分层，再谈六成分。
> 详见 [`02-条款的分层模型`](./02-条款的分层模型-V1.md) —— 本文后续章节涉及的"证据形式""可判定度"，均以 02 号为准。

### 1.2 六个成分的"可获取性"完全不同

这是设计的关键判断，也是你现在最该记住的一张表：

| 成分 | 从哪来 | 需不需要 AI |
|---|---|:--:|
| 主体 | 条款原文 + 审核计划的部门分配 | 不需要（查） |
| 动作 | 动词表（建立/保持/实施/评审/批准/监视/测量…） | 不需要（词表） |
| 对象 | 同上 | 不需要（词表） |
| 条件 | 频次词归一（定期/每年/必要时/变更时） | 不需要（正则） |
| **证据形式** | **必须人工配置** | 不需要，但**必须配全** |
| **判定口径** | **只能来自专家经验** | 需人工配 |

**一句话：六个成分里四个能机械得到，一个靠配置，一个靠经验。**

而你现在卡住的正是第五个——"证据形式"没配全，于是召回不知道去哪找，模型就只剩"翻手册"一条路。

### 1.3 条款还需要三个"标签"，现在都没有

除了六个成分，每条条款还必须打三个标签。这三个标签**决定了系统什么时候可以说话、说到什么程度**：

**标签一：可判定度（A / B / C）**

| 级别 | 含义 | 典型 | 系统能力 |
|:--:|---|---|---|
| A | 结构性可判（存在、批准、日期、版本、覆盖期、数量、字段完整） | 文件控制、监视测量资源、采购 | 可下结论 |
| B | 关系性可判（跨文档一致、覆盖充分、频次符合、抽样代表） | 名录与评审是否一致、内审覆盖部门 | 只能说"疑似" |
| C | 价值性判断（有效性、适宜性、风险识别的到位程度） | 领导作用、风险应对有效性、管理评审充分性 | **不判，只出材料** |

这张分级表是整个产品的**免责边界**。你不需要懂 C 级条款，因为系统不做 C 级。

**标签二：强制度（应 / 宜 / 可）**

标准原文里这三个字就是判据，而且能直接正则抽出来：

| 词 | 后果 |
|---|---|
| 应 | 强制要求，可开不符合项 |
| 宜 | 推荐建议，只能提示改进 |
| 可 | 允许，不作判定依据 |

作用很硬：**"宜"类条款永远不该出现"不符合"**。这一条能挡掉大量误报。

**标签三：颗粒度（父条款 / 叶子条款）**

"7.1.5"是父，"7.1.5.1""7.1.5.2"是子。父条款不能直接判，必须落到子条款。现在的系统吃过这个亏：程序文件标了"7.1.5"，检查项是"7.1.5.1"，精确匹配就永远不中。

### 1.4 条款模型还需要一张"检索词表"（这是现在完全缺的）

审核员手里的速查表长这样：

| 条款 | 关键词 | 审核要点 | 常见不符合项 |
|---|---|---|---|

**"关键词"这一列，是"在文档里搜什么词才能把这条款的证据找出来"。**

比如采购条款的关键词是：供应商、供方、采购、进货、合格供方、评审、再评价。
没有这列，召回只能靠条款号和过程名——而企业文档里根本不写条款号。

**这一列是召回率的第一决定因素，比任何提示词都重要。**

"常见不符合项"那一列是经验库，作用是"提示该往哪儿看"，属于加分项，不是必需。

### 1.5 条款模型的现状

| 要素 | 状态 |
|---|---|
| 条款树（父子结构） | ✅ 有，但个别标准的某章缺失 |
| 六成分中的主体/动作/对象 | ⚠️ 有属性，但覆盖不全 |
| 条件 | ⚠️ 部分 |
| 证据形式 | ⚠️ 有，但没配全，且未细分 |
| 判定口径 | ❌ 基本没有 |
| 可判定度 A/B/C | ❌ 没有 |
| 强制度 应/宜/可 | ❌ 没有 |
| 颗粒度归一 | ⚠️ 有树，但匹配时没做父子归一 |
| 检索词表 | ❌ **完全没有** |
| 常见不符合项库 | ❌ 没有 |

## 二、第二层：文档模型（答案在哪）

### 2.1 一份文档其实有三个属性，现在被压成了一个

"这份文档是什么"是三个独立问题的答案：

| 问题 | 属性 | 决定什么 |
|---|---|---|
| 怎么读它？ | **体裁** | 用哪种方式抽取 |
| 能不能当证据？ | **职能** | 是"规定"还是"做过的痕迹" |
| 该给哪个条款看？ | **归属** | 过程、部门、期间 |

现在系统用一个"文档类型"字段同时回答三个问题——这就是四套分类并存的根源。

### 2.2 体裁：靠规则，不靠 AI

```
手册 / 程序文件 / 指导书 / 记录表单 / 方针目标 / 计划 / 外部文件（标准法规客户要求）
```

判据是文件名 + 表头 + 结构特征。这一步准确率很高，不需要模型。

**体裁决定"怎么抽"**：
- 程序文件 → 抽"每条义务"（谁、做什么、多久一次）
- 记录表单 → 抽"每一行数据"（字段、值、签署、日期）
- 手册 → 抽"章节结构与自述段落"
- 结论报告 → 抽"结论值 + 批准人"

### 2.3 职能：三个信号就能判，不需要标注

这是本节最省力的一条。**"规定类"还是"执行类"，用三个信号就能判**：

| 信号 | 判据 |
|---|---|
| 有具体数据 | 出现供应商名、人名、数字、日期、批次号 |
| 有签署 | 签署栏非空 |
| 有覆盖期 | 有起止日期或"第 X 年" |

- 命中 ≥ 2 个 → **执行类**（可以当证据）
- 一个都没有 → **规定类**（只能当依据、引文）
- 只命中 1 个 → **混合类**（模板加少量填写，只能当"有这张表"的证据，不能当"做了这件事"的证据）

**这一条的价值**：它能机械地判掉"企业文档看着齐全、其实都是空白模板"这类问题。而且这个判断永远一致，不像模型每次给不同答案。

### 2.4 归属：三路投票，不信单点

判断"这份文档属于采购过程"，不要信一次判断，用三路投票：

1. 文件名关键词（供应商/采购/供方/进货）
2. 文档里写的责任部门
3. 表头字段（有"供应商名称""供货范围"列）

**两路一致 → 归属成立。**而且失败时可以解释（"因为文件名和部门都指向采购"）。

### 2.5 文档模型的产物：一张"文档卡"

每份文档处理完，应该留下这么一张卡（纯概念）：

```
文档卡
├── 名称 / 日期 / 版本 / 页数
├── 体裁：程序文件
├── 职能：规定类
├── 归属：采购过程 / 采购部 / 覆盖 2026 年度
├── 关键字段：（这份文档实际能抽出的字段清单）
├── 可用角色：只能当"制度依据"，不能当"执行证据"
└── 证据价值：中（缺签署、缺数据）
```

**这张卡是"文档 ↔ 条款"能对上话的唯一桥梁。**没有卡，召回只能看文件名。

### 2.6 文档模型的现状

| 要素 | 状态 |
|---|---|
| 体裁分类 | ⚠️ 有，但分类标准不统一 |
| 职能判定 | ❌ **没有**（现在靠模型猜"文档性质"） |
| 归属判定 | ⚠️ 只靠文件名，没有投票 |
| 文档卡 | ❌ 没有（有个空壳，从没填过） |
| 抽取模式（按体裁） | ✅ 有，且质量不差 |
| 关键字段清单 | ⚠️ 抽取里有，但没有"这类文档应该有哪些字段"的标准 |

## 三、第三层：证据模型（答案是什么）

**这一层是整个系统最缺的，也是最该先建的。**

### 3.1 三个概念必须先分开：事实 / 证据 / 疑点

这是全文最重要的区分：

| 概念 | 定义 | 数量级 |
|---|---|---|
| **事实** | 文档里写着的一句话或一行数据 | 一个检查项几十到上百条 |
| **证据** | 通过三道闸门、能指回原文、能写进报告的事实 | 一个检查项 5–10 条 |
| **疑点** | 事实之间的矛盾、缺失、异常 | 一个检查项 1–5 条 |

**事实不等于证据。**这是关键。

一次检查项会抽出 50 条事实，但只有 8 条能进报告。如果系统不区分，模型就会拿 50 条去凑 8 句话——凑不出来就写"未见记录"。

97 号那次"8.4 有 12 条发现、92% 可用"，和"实跑四次全 ofi、证据全是未见记录"，这看着矛盾，其实是同一件事：**有事实，没有证据，于是模型自己编了。**

### 3.2 事实变证据，必须过三道闸门

这是"证据分析"的实质内容。三道闸门，缺一道就不是证据：

**闸门一：定位闸** —— 能不能指回原文？

一条事实必须能回答"它在哪份文档、哪一页/哪一节"。指不回去的，只能算"印象"，不能进报告。

**闸门二：完整闸** —— 5W1H 齐不齐？

审核员记录事实只有六个格子（培训视频里的"5W1H 记录卡片"）：

| 格子 | 含义 | 来源 |
|---|---|---|
| What | 什么产品/对象 | 抽取的对象字段 |
| Where | 什么地点/部门 | 责任部门 |
| When | 什么时间 | 日期 |
| Who | 谁做的 | 签署人 |
| Why | 什么情况/事由 | 事由/结论 |
| How many | 多少数量 | 记录条数 |

**六个格子缺一半，这条事实就不能写进报告。**这条规则比任何提示词都硬。

**闸门三：归属闸** —— 它是不是这个条款/这个过程的？

两条常见错位（培训视频专门讲过）：
- 培训记录挂了"人员"条款（7.1.2），应该挂"能力"条款（7.2）
- 校准证书挂了"资源"条款，应该挂"测量溯源"条款

**这说明"事实类型 → 条款"存在一张确定的映射表**，而不是让模型每次判断。建这张表（二三十行），就能挡住"串条款"这个老毛病。

### 3.3 过不了闸门的事实去哪？

不要丢掉，也不要硬用。分三条路：

1. 定位不了 → 回抽取层修（问题在抽取，不在分析）
2. 5W1H 不全 → 留在事实池，标"信息不全"，等补
3. 归属错 → 改挂到正确条款（这就是那张映射表的用处）

**关键：这三种情况都不能变成"企业没有"。**现在的系统就是在这里出的事——召回丢了 86% 的记录类文档，然后写成"未见记录"。**"我没找到"和"企业没有"是两件完全不同的事。**

### 3.4 疑点：五个来源，全部可算，不靠模型

疑点不是"让模型想出来"，而是**算出来的**。五个来源：

| 来源 | 判据 | 例子 |
|---|---|---|
| **缺失型** | 条款要求有记录，记录不存在 | 采购条款要求评价记录，但没有评审表 |
| **矛盾型** | 同一事实两处不一致 | 名录里 12 家供应商，评审表只有 3 家 |
| **异常型** | 分布反常 | 四部门同一天签署；编号断号；日期都在月末 |
| **比例型** | 样本或覆盖不足 | 20 家供应商只抽 1 份评审表 |
| **痕迹型** | 模板特征 | 同套话术、空白占比高、引用不存在的文件 |

**这五类都能用规则算出来，不需要 AI。**AI 只负责最后一步：把"规则命中"翻译成审核员看得懂的一句话。

这一点极其重要：**现在的疑点随证据出现而归零（补一份记录，疑点从 2 条变 0 条），正是因为疑点是模型判的。**规则判的疑点不会因为"多看到一份文档"就消失——它只会被"补上证据"消除。

### 3.5 证据有四张"角色脸"

同一条证据，写进报告时只能扮演四种角色之一：

| 角色 | 用在什么场合 | 需要哪些字段 |
|---|---|---|
| 制度依据 | 说明企业"规定了什么" | 文档名 + 编号 + 被引段落（必须是企业自己写的） |
| 执行证据 | 说明企业"做了什么" | 数量 + 抽样行 + 关键值 + 签署 + 日期 |
| 结论证据 | 说明"做完之后评价如何" | 结论值 + 日期 + 批准人 |
| 现场证据 | 说明"现场看到什么" | 观察点 + 照片编号 |

角色由（体裁 + 职能）唯一决定：

```
程序文件 + 规定类 → 制度依据
记录表单 + 执行类 → 执行证据
报告     + 结论类 → 结论证据
—                 → 现场证据
```

**"手册证据变成标准条文"那个错，用这张表就能拦住**——制度依据的证据只能来自企业自述，标准原文的角色不在这里。这是个字段校验，不是提示词问题。

### 3.6 证据模型的现状

| 要素 | 状态 |
|---|---|
| 事实（抽取出的结构化内容） | ✅ 有，质量不错 |
| 证据（过闸门、可写报告的条目） | ❌ **基本没有**（证据靠人工挂） |
| 5W1H 六字段 | ❌ 没有 |
| 三道闸门 | ❌ 没有 |
| 疑点规则引擎 | ❌ 没有（疑点靠模型） |
| 事实类型→条款映射表 | ❌ 没有 |
| 四角色 | ⚠️ 概念上有，未落成规则 |

## 四、第四层：结论模型（答案够不够）

### 4.1 结论只有四种

```
符合 / 一般不符合 / 严重不符合 / 待定（证据不足）
```

**第四种"待定"是最重要的一种，也是现在系统没有的。**没有"待定"，系统就只能二选一，于是它选了"不符合"，用"未见记录"来填。

### 4.2 结论判定矩阵（本文最核心的一张表）

结论不是"看完所有材料再想"，而是由三个变量查表得出：

| 可判定度 | 证据齐备 | 强制度 | 系统能给的结论 |
|:--:|:--:|:--:|---|
| A | 齐 | 应 | **符合 / 一般不符合**（可进报告） |
| A | 缺 | 应 | **待定**（只写"证据不足"，绝不写不符合） |
| A | 齐 | 宜 | 最多"提示改进" |
| A | 缺 | 宜 | 待定 |
| B | 齐 | 应 | **高度疑似**（供审核员确认，不进正式结论） |
| B | 缺 | 任何 | 待定 |
| C | 任何 | 任何 | **不判，只提供材料** |

**这张矩阵就是"AI 能不能下结论"的答案：**

- 只在 A 级、证据齐全时下结论；
- B 级只说"疑似"；
- C 级永远闭嘴；
- "宜"类永远不说"不符合"；
- 证据不齐一律"待定"，不许用"未见记录"来冒充不符合。

**这条规则若早立，你现在那四次实跑全都不会输出"未见记录"**——因为它们全都属于"证据缺 + 应"，正确答案是"待定"。

### 4.3 结论还要一个"证据容量"的约束

一条结论后面能挂几条证据？审核员的实际做法是：**一个不符合项只对应一个问题**（培训视频专门讲过），不能三个问题挤一条。

所以：**一条结论 = 一条证据组 = 一个事实链**。这条约束倒过来要求证据层必须"条目化"——这正是第三层要建的原因。

### 4.4 结论模型的现状

| 要素 | 状态 |
|---|---|
| 四值结论 | ⚠️ 有词表，但用不全（缺"待定"的实际使用） |
| 判定矩阵 | ❌ 没有 |
| 分级（严重/一般） | ❌ 不判（正确，但需要显式声明"不判"） |
| 一条结论一个事实链 | ❌ 没有（现在一个检查项挤 2–3 条疑点） |

## 五、四层怎么连：三张映射表

**整个系统真正的"代码"只有三张表。**其余都是执行这三张表。

### 表一：条款 ↔ 文档（召回表）

```
条款编号 | 需要的体裁 | 需要的过程 | 检索关键词 | 优先级
```

作用：给定一个检查项，算出"该看哪几份文档"。

**这张表的输入是条款模型的第五个成分（证据形式）+ 检索词表 + 文档模型的归属。**

### 表二：文档 ↔ 事实（抽取契约表）

```
体裁 | 必须抽到的字段 | 可选字段 | 缺失判定
```

作用：给定一份文档，算出"能抽出什么、抽出什么算合格"。

**这张表决定抽取质量**，也是"模板痕迹"能被识别的前提（因为知道"应该有签署栏"）。

### 表三：事实 ↔ 报告（装配表）

```
条款 | 角色（四选一） | 句式 | 槽位（对应哪些事实字段）
```

作用：给定一组证据，算出"这句话怎么写"。

**这张表就是"报告"的全部秘密。**报告不是生成出来的，是按这张表填出来的。

### 5.1 三张表的关系

```
条款模型 ──表一──→ 文档模型 ──表二──→ 事实
                                       │
                                     三道闸门
                                       ↓
                                     证据 ──表三──→ 报告
                                       ↓
                                  结论判定矩阵
```

**注意：三张表里没有一处"让模型自由发挥"。**模型只在"表填不了的地方"出现。

## 六、模型和提示词的关联关系

这是你特别要的部分。先给结论：

> **五类提示词，只有第一类必须用强模型，其余四类都是弱模型或纯规则。**

### 6.1 五类提示词的分工

| # | 类型 | 输入 | 输出 | 用不用模型 | 为什么 |
|:--:|---|---|---|:--:|---|
| 1 | **抽取型** | 原始文档文本 | 结构化事实 | **必须，且要强** | 理解文本，非模型不可 |
| 2 | **归集型** | 多份事实 | 按条款归组的候选证据 | 弱模型或不用 | 主要是按字段分组，规则能做 |
| 3 | **解释型** | 规则命中的疑点 | 一句人话 | 弱模型 | 翻译，不需要推理 |
| 4 | **组织型** | 证据 + 句式 + 槽位 | 报告句 | 弱模型（30%） | 模板为主，模型只补语言 |
| 5 | **润色型** | 已写好的句子 | 更顺的句子 | 可不用 | 纯风格 |

### 6.2 判据一句话

> **输入是原始文本 → 必须用模型；输入是结构化字段 → 用模板，模型只润色。**

这条判据解释了你一直想不通的那个现象：为什么"豆包 + 模板"能出可用结果，而你写提示词不行。

因为豆包那个场景，人实际做了两件事：用豆包做第 1 类（理解一份文档说了什么），用模板做第 4 类（把结果填进固定句式）。两件事都在人的眼前完成，中间有人筛。

而你的系统把两件事塞进一条提示词，让模型一次做"理解 + 装配"，中间没有人的判断——它只能猜。

**所以你说的"漏了一步"，漏的不是一个提示词，而是"事实"和"证据"之间那三道闸门。**

### 6.3 模型要素 → 谁消费（这张表是你要的关联关系）

| 模型要素 | 由谁消费 | 形态 |
|---|---|---|
| 条款六成分 | 召回表 + 抽取提示词上下文 | 配置 |
| 条款检索词 | 召回（文档检索） | 配置 |
| 可判定度 A/B/C | 结论矩阵 | 配置 |
| 强制度 应/宜/可 | 结论矩阵 | 规则（可从原文抽） |
| 文档体裁 | 选哪种抽取提示词 | 规则 |
| 文档职能 | 三道闸门 + 角色判定 | 规则 |
| 文档归属 | 召回表 | 规则 + 投票 |
| 事实字段（5W1H） | 抽取提示词的输出契约 | 提示词内 |
| 疑点五规则 | 疑点引擎 | 规则 |
| 结论矩阵 | 判定器 | 规则 |
| 句式与槽位 | 装配器 | 模板 |

**看出来了吗：11 个要素里，只有 1 个（事实字段）真正写在提示词里，其余 10 个都是配置或规则。**

这就是为什么"改提示词边际收益越来越低"——因为提示词根本不承载模型。

### 6.4 五类提示词各自的"失败模式"

知道失败模式，才知道怎么约束：

| 类型 | 典型失败 | 约束手段 |
|---|---|---|
| 抽取型 | 漏字段、编字段、把"没有"写成"未见" | 输出契约（必填字段）+ 抽取后校验 |
| 归集型 | 串条款（把 A 条款的事实挂到 B） | 映射表 + 归属闸门 |
| 解释型 | 说得太笼统（"管理不规范"） | 句式约束（必须带 5W1H 中的至少 3 项） |
| 组织型 | 编造、引用错来源、空话 | 槽位必须来自证据条目 + 来源校验 |
| 润色型 | 改变事实 | 只许改虚词，不许改数字与名称 |

**五类失败模式，正好对应五个可写的校验规则。**这才是"锁定"的正确姿势——不是锁提示词，是锁输出。

## 七、一次检查项的完整流程（纯概念走一遍）

以"采购"检查项为例，从零走到报告里的一段话：

| 步 | 做什么 | 谁做 | 失败会怎样 |
|:--:|---|---|---|
| 1 | 拿到检查项（条款组 + 部门） | 系统 | — |
| 2 | 查条款模型：六成分 + 可判定度 + 强制度 + 检索词 | 规则 | 属性没配 → 后面全瞎 |
| 3 | 查召回表：该看哪几份文档 | 规则 | **召回丢文档 → 后面全错（现在的病根）** |
| 4 | 每份文档过闸门：体裁 / 职能 / 归属 | 规则 | 职能判错 → 把模板当执行证据 |
| 5 | 抽取：文档 → 事实 | 模型（第 1 类） | 漏字段 → 证据不全 |
| 6 | 事实过三道闸门（定位 / 5W1H / 归属） | 规则 | 过不了 → 不能进报告 |
| 7 | 疑点引擎：五类规则算疑点 | 规则 | 规则没建 → 疑点全靠猜（现在的病） |
| 8 | 查结论矩阵：A/B/C × 齐/缺 × 应/宜 | 规则 | 没有"待定" → 只能编"不符合" |
| 9 | 查装配表：选角色 + 句式 + 槽位 | 规则 | 没表 → 模型自由写 |
| 10 | 组织句子 | 模型（第 4 类，弱） | 编造 → 槽位校验拦住 |
| 11 | 审核员确认 | **人** | 这一步永远保留 |

**11 步里，模型只出现在第 5 步和第 10 步。**其余 9 步全是规则和配置。

**这就是整个系统的形状。**你现在的问题不是"模型不够强"，是第 3、6、7、8、9 步根本没建。

## 九、五个需要你先拍板的问题

模型讲完了，但有几处必须你定，否则实施时会来回摇摆：

**问题一：事实和证据的边界画在哪？**

我的建议是画在三道闸门之后。也就是"抽取出来的都叫事实，过闸的才叫证据"。好处是：模型永远不能自己决定"什么算证据"，只能往事实池里放，闸门由规则把。

**问题二：疑点的阈值谁来定？**

比如"20 家供应商只抽 1 份评审表"算不算疑点？这个阈值必须是配置项，由你和专家定，不能写在代码里。

**问题三：允不允许系统说"待定"？**

这是最关键的商业决策。如果允许，系统会显得"不够智能"（很多检查项都是待定）；如果不允许，系统只能编。我强烈建议允许——**因为审核员最恨的不是"没结论"，是"错的结论"。**

**问题四：一段报告能容几个事实？**

一个条款一段，还是一段能合并两个条款？这决定装配表的行数。建议按"一个条款一段"起步。

**问题五：机构差异放内核还是外壳？**

句式、章节顺序、封面格式——这些是机构风格，必须做成配置。而"事实/依据/判定"三段式、"5W1H"是行业共同语言，必须进内核。

分开的标准：**四家机构都一样的进内核，只有一家这样的进配置。**

## 十、这份模型怎么验证（不用专家）

模型最怕"设计得漂亮但没人能核对"。这套模型好在每一层都留了可被打脸的痕迹：

| 层 | 怎么验 | 需要专家吗 |
|---|---|:--:|
| 条款 | 每条属性在真实文档上跑一遍，看抽到值/抽到空/抽失败的比例 | 否 |
| 文档 | 职能三信号判定，与人工看 20 份的结果比对 | 否 |
| 证据 | 三道闸门的通过率；过不了闸的集中在哪一道 | 否 |
| 疑点 | 规则命中的对不对；专家只判"这条能不能用" | 是，20 分钟 |
| 结论 | 拿 4 份真实报告对账，看我们的结论与它的结论差在哪 | 否 |
| 整体 | 4 份真实报告反推句式，四家都一样的进内核 | 否 |

详见 `06-属性与文档模型的自验证方案`。

## 十一、一句话收尾

**这个系统不是"一个会写报告的 AI"，是"三张表 + 五道闸门 + 一个判定矩阵"。**

AI 只在两个地方出现：把文档读成事实，把事实说成人话。
其余全部是配置和规则——**而配置和规则，恰恰是不需要 AI、不需要专家、可以自己一遍遍校准的东西。**

这也是为什么你现在"改提示词没效果"：因为你在改的是最末端那 30%，而前面 70% 的模型是空的。
