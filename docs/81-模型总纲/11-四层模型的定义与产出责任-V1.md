# 11 · 四层模型的定义与产出责任

> 这份不写分析，只写定义：每一层**是什么、长什么样、谁产出、怎么验证、和上下层怎么接**。
> 目标：四层各自能一句话记住，且能立刻判断"这件事该人干还是 AI 干"。

---

## 零、一页看完：链和责任人

```
条款原文（国标）
   │  人设计 —— 拆义务、写成问句      ← AI 干不了，见第七节
   ▼
【第一层】属性池        问句集 + 答案域，版本化
   │  人定规则 —— 按文档分类定抽取项
   ▼
【第二层】提取规则 → 文档属性      身份 / 内容 / 质量 三类
   │  AI 执行 —— 逐项对账，机械回答
   ▼
【第三层】证据发现      事实清单 + 疑点清单（纯客观，不判）
   │  AI 执行 + 句式库 —— 压缩、排序
   ▼
【第四层】证据生成      4 段文字 + 缺口表
```

**四个箭头的含义各不相同，这是最容易混的地方：**

| 箭头 | 谁做 | 产物性质 | 能不能让 AI 自己定 |
|:--:|---|---|:--:|
| 条款 → 属性池 | **人** | **判定标准**（规则） | **不能** |
| 属性池 → 文档属性 | 人定规则、AI 执行 | 数据 | 能（但规则要人写） |
| 文档属性 → 证据发现 | AI | 数据（客观事实） | 能 |
| 证据发现 → 证据生成 | AI + 句式库 | 文本（压缩） | 能 |

**一句话原则：判定标准必须人写死，AI 只负责"对着标准给答案"。**

## 一、第一层：属性池

### 1.1 一句话定义

**属性池 = 一条条款被拆成的一组问句，每个问句的答案只落在有限几种形式里。**

**注意：属性不是"字段"，是"问句"。**

这不是文字游戏。区别在用途：

- 字段是存储形状（`vendor_count int`）
- 问句是判定动作（"名录里有几家供方？"）

产品要 AI 干的事是"回答问句"，不是"填字段"。所以属性池必须是问句形态。

### 1.2 三类属性必须分开（这是最容易混的地方）

很多人一听"属性池"就想成一个大池子，其实里面装的是三种完全不同的东西：

| 类型 | 是什么 | 数量级 | 谁定 | 是否随标准变 |
|---|---|---|---|:--:|
| **A 结构属性** | 一条义务的解剖结构：主体 / 动作 / 对象 / 条件 / 证据形式 / 判定口径 | 6 个，845 条共用 | 人，**一次定完** | 不变 |
| **B 义务属性** | 这条条款具体要求什么，拆成可判定的问句 | 每条 5–12 个 | 人，**逐条写** | 随标准变 |
| **C 判定属性** | 答到什么程度算合格（机构口径） | 每条 1–3 个 | **专家给** | 随机构变 |

**这是关键的数量判断：**

- A 类：6 个，一次性，半天定完
- B 类：**25 条高频条款 × 8 个 ≈ 200 个问句**，一个人一周能写完
- C 类：不需要写，靠专家口头给，或从两家机构真实报告反推

**所以"属性池"的真实工作量不是 845 × 10，是 200 个问句。**这就是你 1 个月能做完的原因。

### 1.3 每个属性的四件套

一个属性必须写清四样东西，缺一样就不能用：

| 项 | 含义 | 例（8.4.1 义务点 5） |
|---|---|---|
| **问句** | 要回答什么 | 外部供方评价准则是否成文，且发布日期早于首份评价记录？ |
| **答案域** | 允许的答案形式 | 是（附日期）/ 否 / 有准则但无日期 / 无法判定 |
| **来源** | 答案该从哪类文档取 | 程序文件 + 评审表模板 + 首份评审记录日期 |
| **权重** | 答"否"时算硬缺失还是软缺失 | 硬（准则缺失 → 直接不可符合） |

**"答案域"是属性池最容易被漏掉的一项。**没有答案域，AI 会自由发挥——写成"基本符合""有待完善"这类话。**把答案域写死，等于把 AI 的自由度锁在四个选项里。**

### 1.4 为什么属性会有"无法判定"这个选项

因为有些问句在文档里查不到答案。比如"组织是否评估了外包对满足顾客要求能力的影响"——如果企业没有风险评估记录，答案是"无法判定"，不是"否"。

**"无法判定"和"否"必须分开。**"否"是"查了，确实没有"；"无法判定"是"这类文档压根不存在，没处查"。

混在一起的后果：一律变成"否"，然后就变成"未见"，然后就变成 OFI。**这是现在系统全出 OFI 的机制之一。**

### 1.5 怎么验证属性写得对不对（你那个困局的操作解）

你不需要专家懂建模，只需要他回答问题。三个封闭式检验：

**检验一 · 可答性**

> 把问句单独念给一个不懂业务的人，只给他企业文档，他能答出来吗？

答不出来 → 这条是"现场题"（要靠看现场或访谈），不属于文档证据范围。**要么剔除，要么单独标记为"访谈证据"。**

**检验二 · 判据唯一性**

> 两个审核员看同一份文档，会不会得出同一个答案？

不会 → 这条的判据不唯一，必须补判据（比如"成文"要定义成"有独立文件且含评分维度"）。

**检验三 · 反向提问**

> 问专家："这条如果答'无'，你会不会开不符合？"
> - 答"会" → **硬属性**，可以用来判
> - 答"看情况" → **软属性**，只能用来提，不能用来判
> - 答"无所谓" → 删掉

**这三个检验每个只要 10 秒，专家一次能过 30 条。**而且他不需要理解"属性池"是什么——他只回答了三个问题。

**这是你那个困局的解：不验证"AI 理解对不对"，只验证"这个问句有没有用"。**

### 1.6 属性的三个常见误解

| 误解 | 实际 |
|---|---|
| 属性是数据库字段 | 属性是问句；字段只是它的存储形式 |
| 属性可以运行时由 AI 抽象 | **不能**。每次抽象结果不同，结果不可复现（见第七节）|
| 属性越多越好 | 一条 5–12 个。超过 15 个说明没抓到主干，是在罗列细枝末节 |

## 二、第二层：文档属性（你的"两个问题"分开答）

你明确拆成两个问题，我按你的拆法答。

### 问题 1：文档有哪些属性

分三类，**这三类的提取方式完全不同，混在一起是现在系统最大的设计问题。**

#### ① 身份属性 —— "这是什么文件"

| 属性 | 取值 | 为什么需要 |
|---|---|---|
| 类型 | 手册 / 程序 / 三阶作业指导 / 记录 / 表单 / 外来文件 | 决定它在证据里的**角色**（制度依据 vs 实施证据） |
| 编号 | KSY-QMS-P-15 | 证据段必须写出来，否则不可溯源 |
| 版本 | A/0 | 同上 |
| 生效日期 | 2026.6.10 | **时序校验的基准**（T5 型疑点全靠它） |
| 受控状态 | 受控 / 非受控 / 未标识 | 判"文件管理"条款 |
| 编制 / 审核 / 批准 | 人名 | 判签署完整性 |
| 所属部门 | 采购部 / 品质部 | 决定归到哪个检查项 |

**这 7 个属性，90% 可以用规则抽（页眉、封面、文件名），不需要模型。**现在的问题是：这些字段抽得不稳，导致后面时序校验全废。

#### ② 内容属性 —— "里面写了什么"

| 属性 | 取值 | 用途 |
|---|---|---|
| **覆盖哪些条款** | 8.4.1 / 8.4.2 … | **第一属性，见 2.3** |
| 涉及哪些过程 | 采购 / 生产 / 检验 | 归到哪个检查项 |
| 涉及哪些对象 | 供方 / 设备 / 工序 / 批次 | **对象维度的来源** |
| 关键要求项 | 抽样方案、频次、阈值、处置路径 | 抽出来才能在证据里引用 |
| 声明的频次 | 每年 / 每月 / 每批 | **T3 型疑点的输入** |
| 声明的阈值 | 2% 不良率、96 分 A 级 | 同上 |
| 引用了哪些文件 | KSY-QMS-WI-10 | 建引用图，做交叉校验 |

**这一类必须用模型抽，而且必须校验。**校验的办法是"抽出来的每一条都要能回到原文某一段落"——点不回去的算抽错。

#### ③ 质量属性 —— "这份文件能不能当证据"

| 属性 | 取值 | 依据 |
|---|---|---|
| 签署完整率 | 编制/审核/批准 3 个里有几个 | 页脚签名栏 |
| 日期完整性 | 关键日期有几个空 | 表头/表尾 |
| 是否空白模板 | 是 / 否 | 字段填充率 < 20% |
| 是否与其他文件冲突 | 冲突项 | 跨文档比对 |
| 是否可读 | 文本层 / 需OCR / 图片 | 解析结果 |
| 归档完整性 | 附件齐全 / 缺附件 | 引用 vs 实物 |

**这一类不靠"抽取"，靠"计算"。**它不需要模型读文档，需要的是"读完之后的核算"。

**这类属性最容易被忽略，但最值钱。**08 号实测的那几条硬货全部来自这里：

- "三份空白模板"→ 空白模板属性
- "两个 doc 都 40,448 字节、内嵌图 0"→ 归档完整性
- "四追溯字段全空"→ 日期完整性
- "附营业执照均在有效期内，但零附件"→ 引用 vs 实物

**换句话说：真实报告里最有杀伤力的发现，全部是质量属性，不是内容属性。**

#### 三类的对比（这张表决定了流水线怎么设计）

| | 身份属性 | 内容属性 | 质量属性 |
|---|---|---|---|
| 提取方式 | **规则**（正则/页眉/文件名） | **模型**（语义） | **计算**（跨文件） |
| 需要模型吗 | 不要 | 要 | 不要 |
| 出错后果 | 溯源断链 | 对账错位 | 疑点漏检 |
| 现在系统的状态 | 不稳（生效日期常缺） | 弱（ClauseNumbers 86/99 为空） | **基本没有** |

### 问题 2：如何提取（提取规则该怎么设计）

现在的做法是"按文档分类，一套规则抽字段"。按上面三类看，**这个设计混了三种不同的动作**。应该拆成三段流水线：

```
第一段 · 归类
  判定：这份文件是手册 / 程序 / 三阶 / 记录 / 表单 / 外来文件
  依据：文件名 + 页眉 + 结构特征（有无条款编号、有无表格、有无签署栏）
  产物：类型 + 该套用的规则编号

第二段 · 抽字段
  按第一段选定的规则，抽身份属性 + 内容属性
  含：覆盖条款、对象、频次、阈值、引用文件
  产物：结构化字段 + 每条字段的原文出处（必须可点）

第三段 · 校
  计算质量属性：签署率、日期完整性、空白判定、跨文档冲突
  产物：质量标记（决定这份文件能不能当证据用）
```

**三段之间不通过，因为判据不同：**

- 第一段错了 → 用错规则，后面全错（**这是现在最可能的失败点**）
- 第二段错了 → 字段错，可校验（每条必须能点回原文）
- 第三段错了 → 疑点漏检，**不可校验**（所以第三段必须显式做，不能靠隐式）

**现在的最大缺陷：第三段根本没有。**系统的抽取只做"把文档变成文字 + 抽条款号"，没有"算这份文件的质量"。

### 2.3 一个必须强调的判断：第一属性是"覆盖哪条条款"

在内容属性里，**"覆盖哪些条款"排在第一位**，因为整个系统是"按条款找文档"的。

如果这个属性抽不出来，后面全断。这不是推测——实测数据：

> 99 份企业文档里，**86 份的"覆盖条款"为空**。

后果是：按条款找文档时，这 86 份被整份丢弃，剩下 13 份里还有一部分是最没有执行证据的（比如只有封面）。**所以喂给模型的材料天然是错的。**

**这不是提示词问题，是第二层的第一属性没抽出来。**

而"覆盖条款"其实是可以抽的：三阶文件正文里通常直接写了"本文件适用于 XX 条款"，程序文件的目录里也写着。**只要把"条款号"当成一个必抽字段、抽不到就标"待人工确认"，就不会静默丢弃。**

## 三、第三层：证据发现

### 3.1 一句话定义

**证据发现 = 对着属性池逐项回答，产出"事实清单"和"疑点清单"，不做任何判定。**

**这一步的产出是纯客观的。**它的判断标准只有一个：**全不全。**

### 3.2 事实长什么样

**一条事实 = 一个属性 + 一个答案 + 一个出处。**

```
属性：评价准则是否含评分维度
答案：是 —— 资质证明 / 供货能力 / 产品质量 / 服务情况 / 交货期 / 价格（六项）
出处：《供应商评审表》第 2 页 表头

属性：名录里有几家供方
答案：1 家（江阴市金祺达金属制品有限公司）
出处：《合格供应商清单》第 1 行

属性：供方绩效监视的频次
答案：每年一次（备注栏声明）
出处：《供应商业绩定期考核评估表》备注
```

**注意：没有任何一条事实带"符合/不符合"。**它只回答"是什么"。

### 3.3 疑点长什么样

**一条疑点 = 一个矛盾 + 两处出处 + 一个类型。**

```
类型：T1 覆盖缺口
矛盾：名录在册 1 家，实际供货含 316L、纸箱、自封袋、塑料盒 4 类，缺 3 类供方评价
出处A：《合格供应商清单》（1 家）
出处B：采购清单 + 进料检验报告的物料名（4 类）
```

```
类型：T5 时序倒置
矛盾：进料检验报告日期 2025-03-19，早于体系文件发布日 2026.6.10
出处A：《进料检验报告》日期栏
出处B：《管理手册》发布日
```

**疑点必须有"两处出处"。**只有一处的不是疑点，是"缺失"——缺失走缺口清单，不走疑点。

### 3.4 事实和疑点的比例，以及为什么必须分开

一个检查项的正常比例（据真实材料估）：

- 事实：**15–30 条**（属性池每项都有一到几条）
- 进报告的：**5–10 条**
- 疑点：**0–3 条**

**三个数量级完全不同，说明它们是三种东西：**

| | 事实 | 疑点 | 缺口 |
|---|---|---|---|
| 数量 | 几十 | 0–3 | 0–5 |
| 判断标准 | 全 | 有矛盾 | 有应无 |
| 去处 | 筛 5–10 条进证据段 | 单独提 | 单独成表 |
| 出错后果 | 漏了 → 证据薄弱 | 编了 → 冤枉企业 | 多了 → 变成指责 |

### 3.5 这一步为什么必须单独存在

因为**它的判断标准（全）和第四层的标准（短）方向相反**。

现在系统把两步合成一步，模型被同时要求"找全"和"写短"，结果必然选一个牺牲另一个——**实测牺牲的是"找全"，产出"查阅程序 + 未见记录"**。

**这就是你说的"漏了一步"的机制解释。**

## 四、第四层：证据生成

### 4.1 一句话定义

**证据生成 = 把事实清单压成段落，把缺口清单整理成表，不新增任何判断。**

**关键：这一层不做判断，只做"压缩 + 排序"。**

### 4.2 压缩规则（这是可以写死的）

**留：**

- 文件类型 + 文件名 + 编号 + 版本
- 数量（几家 / 几份 / 几次）
- 签署与批准（谁签的、几个部门）
- 日期
- 结论词（符合 / 基本符合 / 合格 / 未提供）

**删：**

- 所有论证过程（"因为……所以……"）
- 判据细节（AQL 是多少、CR/MAJ/MIN 怎么分）
- 抽样方法的原理
- 属性的全部答案（只留能撑起句子的那几个）

**一个检验办法：压缩后的每一句，都能倒推回一条事实。**倒推不回去的，说明这句是编的或是废话。

### 4.3 排序规则（也是固定的）

制度 → 准入 → 运行 → 结论（对应 1:2:2:1 配比，见 10 号）。

**为什么这个顺序**：因为它对应审核员阅读时的两个问题——"你有没有规定"（第 1 段）、"你规定了做没做"（第 2、3 段）、"所以到底行不行"（第 4 段）。

**这个顺序不是文风，是逻辑。**机构模板各不相同，但这个顺序在两家机构里是一致的。

### 4.4 这一层真正需要的是"句式"，而句式可以抄

句式来自真实报告，不需要发明。两家机构 8.4 段的骨架几乎一样：

> 查见《XX》（编号，版本），规定了……
> 实施……，查见《XX表》N 份，对……作出评价，经……签署，结论为……
> 抽查《XX》N 份，……结果为合格。
> 综上，……符合 XX 条款的要求。

**所以第四层的建设成本极低**：抄 25 条高频条款的真实段落，拆出槽位，就是句式库。

## 五、四层的接口表（谁给谁什么）

这是"关联关系"最实用的形式：

| 层 | 输入 | 输出 | 输出的最小单位 | 验收标准 |
|:--:|---|---|---|---|
| 属性池 | 条款原文 | 问句 + 答案域 + 来源 + 权重 | 一个问句 | 三个检验全过 |
| 文档属性 | 属性池的"来源"栏 + 企业文档 | 身份/内容/质量 三类字段 | 一个字段 + 出处 | 每个字段能点回原文 |
| 证据发现 | 属性池 + 文档属性 | 事实清单 + 疑点清单 | 一条事实 / 一条疑点 | 全（覆盖全部问句） |
| 证据生成 | 事实清单 + 缺口清单 + 句式库 | 4 段文字 + 缺口表 | 一段话 | 每句可倒推回一条事实 |

**接口上最容易断的三处（也是现在系统实际断的地方）：**

1. **属性池 → 文档属性**：属性池说"来源是程序文件"，但文档属性里没有"这份文件是程序文件"的可靠标记 → 找不到
2. **文档属性 → 证据发现**：文档属性说"覆盖条款为空" → 这一步直接跳过这份文档
3. **证据发现 → 证据生成**：事实清单只有 3 条 → 只能拼出 3 句话 → 凑不够 400 字 → 用"未见"填空

**三处断点，全部在第二层。**这就是"第二层是第一属性的原因"。

| | 属性池 | 文档属性 | 证据发现 | 证据生成 |
|---|---|---|---|---|
| 最小单位 | **问句** | **字段** | **事实** | **段落** |

## 七、为什么属性必须人提前写（你第三个判断的架构理由）

你说："AI 其实并不能立即抽象出条款的属性，这个需要我们提前去设计。"

**这个判断是对的，而且理由比"它抽象不准"更硬：**

### 理由一：抽象结果不稳定，结果不可复现

同一条 8.4.1，今天让模型抽象属性，得到 6 条；明天再抽象，得到 8 条，其中 3 条不一样。

**认证审核要求可复现**——同一个企业、同一份材料、两次跑出来必须一样，否则无法向机构解释。

**属性池是人写的，就固定了；AI 每次只是"照着问句回答"，答案会变，但问句不变。**这才是可复现的结构。

### 理由二：属性是"判定标准"，标准不能由执行者自己定

这是软件工程里最基本的一条：**接口定义由调用方写，实现方照着做。**

如果让 AI 自己定属性、自己回答，等于"裁判和选手是同一个人"。它一定会选对自己有利的问句（容易答"有"的那些），然后所有检查项都会变成"符合"或者"有制度无记录"。

**这不是模型坏，是结构错。**

### 理由三：抽象是"业务判断"，不是"语言理解"

AI 能读懂条款（你验证过了：OCR 打乱的原文它都能还原）——**这是语言能力**。

但从"组织应基于外部供方按照要求提供过程、产品和服务的能力，确定并实施……准则"这句话里，抽象出"准则的事先性"这个属性——**这是业务判断，需要知道"准则晚于评价记录意味着什么"。**

**这两件事的能力来源不同：一个来自语料，一个来自领域知识。**

AI 有前者，没有后者。所以属性必须人写。

### 但有个例外：结构属性（A 类）AI 可以辅助

"主体 / 动作 / 对象 / 条件 / 证据形式 / 判定口径"这 6 个成分，是**语法成分**，AI 可以按语法标注（找出"应"字句的主语、谓语、宾语）。

**所以 A 类可以让 AI 起草、人确认；B 类必须人写。**这个分工能省不少时间。

## 八、这份文档对 1 个月目标的意义

按这四层的定义，工作量变得可算了：

| 工作 | 量 | 时间 |
|---|---|---|
| A 类结构属性（6 个成分） | 1 次性 | 半天（AI 起草 + 人确认） |
| B 类义务属性（25 条高频条款） | 25 × 8 ≈ **200 个问句** | **5–7 天**（人写） |
| 第二层第一属性（覆盖条款） | 1 条规则改动 + 重抽 99 份 | 1–2 天 |
| 第三层对账 | 25 条的机械实现 | 3–5 天 |
| 第四层句式库 | 抄 25 条真实段落 | 2–3 天 |
| 三个检验过一遍 | 专家 1 次，30 条/半小时 | 半天 |
| **合计** | | **约 15–20 天** |

**这是 1 个月能做完的。**而且做完之后，25 条高频条款的产出可以被专家检验；剩下 820 条靠模板套。

**所以你的目标不该是"1 个月做完全部"，是"1 个月做出 25 条能被专家认可的样板，并且证明这套四层结构能复制"。**

这个目标是可以验收的——验收标准就是那三个检验，加上"拿 2 家企业跑，专家看不出是机器写的"。

## 九、如果只记三句话

1. **属性是问句，不是字段；判定标准必须人写，AI 只负责回答。**
2. **文档属性分身份、内容、质量三类；身份靠规则、内容靠模型、质量靠计算——现在第三类根本没有，而真实报告最有杀伤力的发现全在第三类。**
3. **证据发现和证据生成必须分开，因为一个要全、一个要短，合成一步必牺牲"全"。**
