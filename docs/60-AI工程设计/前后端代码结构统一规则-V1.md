## 〇、架构 vs 项目边界（最重要！）

> **这是编码前必须理解的第一个概念。判断错误会导致代码放错位置。**

### 0.1 两个层次的定位

| 层级 | 项目路径 | 定位 | 能否提取为 NuGet 包 | 代码特征 |
|------|----------|------|---------------------|----------|
| **架构（Framework）** | `src/yzh-core/` (`YZH.Core.Stand`、`YZH.Core.Api`、`YZH.Core.Web`) | 跨项目的通用基座 | ✅ 是 | 基类、泛型控制器、Helper、特性、中间件 |
| **项目（Project）** | `src/certplatform-api/CertPlatform.*` (`Admin`、`Auditor`、`Enterprise`) | 认证平台具体业务 | ❌ 否 | 具体业务控制器、实体、业务 Service、EntityConfig |

### 0.2 判断标准：这段代码"每个项目都需要"吗？

| 分类 | 放置位置 | 示例 |
|------|----------|------|
| **基础能力**（每项目都需要） | `YZH.Core.Web/Controllers/` | UserController、RoleController、OrganizationController、MenuController、DictionaryController、AuthController |
| **业务能力**（认证平台独有） | `CertPlatform.Admin/Controllers/` | ISOClauseController、ISOStandardController、CertificationBodyController、WorkflowController、EnterpriseController |

### 0.3 快速判断矩阵

| 问题 | 回答"是" → | 回答"否" → |
|------|-----------|-----------|
| 其他项目也需要用户管理、角色权限吗？ | ✅ 放 `YZH.Core.Web` | 放 `CertPlatform.Admin` |
| 这是 ISO 认证特有的业务吗？ | ❌ 不放 `YZH.Core.Web` | ✅ 放 `CertPlatform.Admin` |
| 这是通用的组织机构管理吗？ | ✅ 放 `YZH.Core.Web` | 放 `CertPlatform.Admin` |
| 这涉及认证流程/NC规则/报告吗？ | ❌ 不放 `YZH.Core.Web` | ✅ 放 `CertPlatform.Admin` |

## 一、核心原则

### 1.1 三层同构

```
后端 Controller 文件路径  =  前端 API 文件路径  =  前端 Pages 文件夹路径

示例：
  后端：YZH.Core.Web/Controllers/System/UserController.cs     → /api/System/User
  前端：share/src/api/system/user.ts                           → /api/System/User
  前端：admin/src/pages/system/user/index.vue                  → /system/user
```

**含义**：新增一个业务模块时，三层同时创建、命名完全一致。

### 1.2 文件夹即模块

| 业务域 | 文件夹名 | 说明 |
|--------|---------|------|
| 系统管理 | `System/` | 用户/角色/机构/菜单/字典/日志 |
| 基础建设 | `Foundation/` | ISO标准/条款/认证机构/认证阶段（静态主数据） |
| 工作流 | `Workflow/` | 企业/工作流/NC规则/模板/报告规则/目录/提取规则/技能/队列/AI用量 |
| 全局 | 无文件夹 | Auth 等跨域服务 |

> **命名说明**：
> - `Foundation/` 对应后端 `Controllers/Foundation/`，前端 `cert/` (API)、`foundation/` (Pages)
> - `Workflow/` 对应后端 `Controllers/Workflow/`，前端 `workflow/` (API+Pages)

### 2.2 路由约定

| 控制器位置 | Route 特性 | 最终 URL | 所属层 |
|-----------|-----------|---------|-------|
| `YZH.Core.Web/Controllers/AuthController.cs` | `[Route("api/[controller]")]` | `/api/Auth` | 架构 |
| `YZH.Core.Web/Controllers/System/UserController.cs` | `[Route("api/System/[controller]")]` | `/api/System/User` | 架构 |
| `CertPlatform.Admin/Controllers/Foundation/ISOClauseController.cs` | `[Route("api/Foundation/[controller]")]` | `/api/Foundation/ISOClause` | 项目 |
| `CertPlatform.Admin/Controllers/Workflow/WorkflowController.cs` | `[Route("api/Workflow/[controller]")]` | `/api/Workflow/Workflow` | 项目 |

> `[controller]` 自动替换为类名去掉 "Controller" 后缀：`UserController` → `User`
> 特例：`Controllers/System/MenuManagementController.cs` → `[Route("api/System/MenuManagement")]` → `/api/System/MenuManagement`

### 2.3 实体类规范

| 规则 | 说明 |
|------|------|
| **文件夹 = 业务域** | `Models/System/`、`Models/Foundation/`、`Models/Workflow/` |
| **文件名 = 类名** | `User.cs` → `public class User` |
| **废弃 Sys 前缀** | `Sys_User.cs` → `User.cs`，`Sys_Organization.cs` → `Organization.cs` |
| **继承 YZHBaseEntity** | 审计字段、Code、Sort 等从基类获得 |
| **SugarTable 特性** | 数据库表名保持原样（`[SugarTable("Sys_User")]`） |

### 2.4 EntityConfig 规范

| 规则 | 说明 |
|------|------|
| **目录与 Controller 同构** | `Assets/EntityConfigs/System/User.json` |
| **文件名 = 实体类名** | `User.json`（不叫 `Sys_User.json`） |
| **表单配置加后缀** | `OrganizationForm.json`（树节点表单专用） |
| **加载支持子目录** | EntityConfigHelper 支持 `{Domain}/{Name}.json` 路径查找（含递归搜索） |

## 五、AI 行为约束

> 以下内容同时写入 `项目全局规则.md` §8.0 AI 编码约定。

### 5.1 新增模块约束

- **禁止跳过任何一层**：创建 Controller 时，必须同时创建 API 文件和 Pages 文件夹
- **禁止扁平化放置**：新文件必须进入对应子目录（`System/`、`Foundation/`、`Workflow/`）
- **禁止命名不一致**：三层名称必须统一（Controller 类名 = API 文件名主体 = Pages 文件夹名）

### 5.2 文件定位规则

已知模块名 → 文件路径直接推算：
- Controller：`Controllers/{Domain}/{Type}Controller.cs`
- API：`share/src/api/{api-domain}/{type}.ts`
  - `api-domain` = `system`（System 域）、`cert`（Foundation 域）、`workflow`（Workflow 域）
- Pages：`admin/src/pages/{domain}/{type}/`
  - `domain` = `system`（System 域）、`foundation`（Foundation 域）、`workflow`（Workflow 域）
- EntityConfig：`Assets/EntityConfigs/{Domain}/{Type}.json`

### 5.3 修改同步约束

- 改名 Controller → 必须同时修改 API 文件内所有 URL 引用
- 改名 Pages 文件夹 → 必须同时修改 Router 路由 path 和 name
- 移动 Controller → 必须同时修改 `[Route(...)]` 特性和 `namespace`

## 九、FAQ

**Q: 代码应该放 YZH.Core.Web 还是 CertPlatform.Admin？**
A: 问自己"其他项目也需要这段代码吗？"。用户管理/角色/机构/菜单/字典 → 每项目都需要 → 放 `YZH.Core.Web`（架构层）。ISO标准/认证流程/NC规则 → 认证平台独有 → 放 `CertPlatform.Admin`（项目层）。

**Q: Foundation/ 和 Workflow/ 怎么区分？**
A: `Foundation/` = ISO 标准体系主数据（标准/条款/机构/阶段），数据静态、变化少；`Workflow/` = 审核业务配置与运行（企业/工作流/NC规则/模板），数据动态、频繁变更。

**Q: MenuController 和 MenuManagementController 有什么区别？**
A: `MenuController` 负责运行时获取当前用户的菜单树（基于角色权限）；`MenuManagementController` 负责菜单的 CRUD 管理（增删改查所有菜单定义）。两者路由分别是 `/api/System/Menu` 和 `/api/System/MenuManagement`。

**Q: Entity 类名和文件名都去掉了 Sys 前缀，但数据库表名还有 Sys_，会有冲突吗？**
A: 不会。EF Core / SqlSugar 使用 `[SugarTable("Sys_User")]` 显式映射，与 C# 类名无关。

**Q: Auth 为什么不放 System/ 子目录？**
A: Auth 是跨域服务（登录、注册、验证码），不属于任何单个业务域，放根目录。

**Q: 为什么后端用 `Foundation/` 而前端 API 用 `cert/`？**
A: 后端 PascalCase 使用完整语义命名 `Foundation`（基础建设）；前端 API 层 kebab-case 保持简短，`cert` 比 `foundation` 更直观。两者映射关系：`Controllers/Foundation/` ↔ `api/cert/` ↔ `pages/foundation/`。
