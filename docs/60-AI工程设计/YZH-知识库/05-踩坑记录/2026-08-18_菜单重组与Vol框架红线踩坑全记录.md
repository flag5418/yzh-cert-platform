## 核心教训（先看这个）

**本次菜单清理工作引发了 5 个连锁问题，根本原因是一个：在未充分理解 Vol 框架运行机制的情况下，对菜单系统进行了大规模 SQL 批量操作。**

| # | 问题 | 根因 | 修复方式 | 耗时 |
|---|------|------|----------|------|
| 1 | 菜单清理后前端白屏 | 删除了菜单但 viewGird.js 路由未同步 | 补齐缺失路由 | 1h |
| 2 | 嵌套路由导致 keep-alive 崩溃 | viewGird.js 中使用了 children 嵌套路由 | 扁平化所有路由 | 30min |
| 3 | MES 组件缺失导致 Vite 编译失败 | 删除了 MES 菜单但组件文件也被引用 | 用 TestService.vue 占位 | 20min |

| 5 | Sys_Department InvalidCastException | 数据库 VARCHAR(36) 存了非 GUID 数据 `dept-xxx` | 修复数据为标准 GUID + 改列类型为 CHAR(36) | 2h |

**关键红线教训**：整个过程一度试图修改 Vol 框架的 `Sys_Department.cs` 实体文件和 `Sys_DepartmentController.cs`，违反了项目 AGENTS.md 中"禁改 Vol 底层"的强制约定。最终确认问题出在**数据层**而非**代码层**，所有 Vol 核心代码恢复原样。

## 一、问题 1：菜单清理后前端白屏

### 1.1 现象

清理菜单（删除 MES/Vol Demo/无效菜单）后，刷新页面出现白屏，控制台报：

```
Unhandled error during execution of component update
TypeError: Cannot read properties of null (reading 'parentNode')
```

### 1.2 根因

菜单数据库中删除了某些菜单项，但 `viewGird.js` 中仍然有路由引用这些已删除菜单对应的组件。反过来，数据库中保留了某些菜单，但其 URL 指向的路由在 `viewGird.js` 中不存在。

**Vol 框架的菜单-路由匹配机制**：
```
数据库 Sys_Menu.Url → 前端路由 path → Vue 组件
```
三者必须一一对应。任何一个断裂都会导致组件渲染失败。

### 1.3 修复

1. **补齐缺失路由**：在 `viewGird.js` 中为所有 `Enable=1` 的菜单 URL 添加对应路由
2. **为缺失组件创建占位文件**：使用 `TestService.vue` 作为临时组件
3. **清除 Redis 缓存**：`docker exec yzh-redis redis-cli DEL inernalMenu`

### 1.4 预防

**菜单变更检查清单**（每次修改菜单后必须执行）：

```bash
# Step 1: 获取所有启用的菜单 URL
docker exec yzh-mysql mysql -uroot -p"Yzh123456." yzh_cert_platform \
  -e "SELECT Url FROM Sys_Menu WHERE Enable=1 AND MenuType=0 AND Url IS NOT NULL AND Url != '' AND Url != '/' ORDER BY Url;"

# Step 2: 检查每个 URL 是否在 viewGird.js 或 index.js 中有对应路由
# Step 3: 检查每个路由的 component 路径是否指向存在的 .vue 文件
# Step 4: 清除 Redis 缓存
docker exec yzh-redis redis-cli DEL inernalMenu

# Step 5: 重启后端（清除静态内存缓存）
./scripts/backend/restart-backend.sh

# Step 6: 硬刷新浏览器 (Cmd+Shift+R)
```

## 二、问题 2：嵌套路由导致 keep-alive 崩溃

### 2.1 现象

点击某些菜单后出现 `parentNode` null 错误，具体是使用了 `children` 嵌套路由的菜单。

### 2.2 根因

`viewGird.js` 中使用了 Vue Router 的嵌套路由定义：

```javascript
// 问题写法：嵌套路由
{
  path: '/CertPlatform/Standard',
  name: 'StandardDirectory',
  redirect: '/CertPlatform/Standard/DirectoryConfig',
  children: [
    {
      path: 'DirectoryConfig',
      name: 'DirectoryConfig',
      component: () => import('...')
    }
  ]
}
```

Vol 框架的 `IndexRouterView.vue` 使用 `<keep-alive>` + `<component :is>` 渲染路由组件。嵌套路由会导致 `keep-alive` 在组件切换时遇到 DOM 节点已销毁的情况，触发 `parentNode` null 错误。

### 2.3 修复

**扁平化所有路由**——每个菜单 URL 直接对应一个独立路由，不使用 `children`：

```javascript
// 正确写法：扁平路由
{
  path: '/CertPlatform/Standard/DirectoryConfig',
  name: 'DirectoryConfig',
  component: () => import('...'),
  meta: { title: '标准文件管理' }
}
```

### 2.4 规则

> **viewGird.js 路由定义铁律**：所有路由必须是扁平结构，禁止使用 `children` 嵌套。菜单 URL = 路由 path = 完整路径，不依赖父路由。

## 三、问题 3：MES 组件缺失导致 Vite 编译失败

### 3.1 现象

Vite 编译报错：`Failed to resolve import '@/views/mes/mes/MES_xxx.vue'`

### 3.2 根因

菜单保留了 MES Demo 路由（用于代码参考），但部分 MES 组件文件不存在（Vol 框架原始包中未包含所有 demo 页面）。

### 3.3 修复

### 3.4 规则

> 保留 Vol Demo/MES 路由用于代码参考时，必须确保每个路由的 `component` 路径指向真实存在的 `.vue` 文件。缺失的用占位组件替代。

## 四、问题 4：LogicFlow 2.0 API 变更

### 4.1 现象

工作流设计器页面报错：`diagram.value?.destroy is not a function`

### 4.2 根因

LogicFlow 2.0 的 API 与 1.x 有重大变更，`destroy()` 方法不再存在。

### 4.3 修复

在 `Designer.vue` 的 `onBeforeUnmount` 中添加安全检查：

```javascript
onBeforeUnmount(() => {
  // LogicFlow 2.0 没有 destroy 方法，使用 clear 替代
  if (diagram.value) {
    try {
      diagram.value.clear?.()
    } catch (e) {
      console.warn('LogicFlow cleanup failed:', e)
    }
  }
})
```

### 4.4 LogicFlow 2.0 API 变更速查

| 功能 | 1.x API | 2.0 API |
|------|---------|---------|
| 添加节点 | `lf.add([config])` | `lf.addNode(config)` |
| 删除节点 | `lf.delete([id])` | `lf.deleteNode(id)` |
| 更新文本 | `lf.update(id, { text })` | `lf.updateText(id, text)` |
| 更新数据 | `data: {}` | `properties: {}` |
| 事件回调 | `data.data` | `data.properties` |
| 销毁实例 | `lf.destroy()` | 不存在，用 `lf.clear()` |

## 五、问题 5：Sys_Department InvalidCastException（重点）

### 5.1 现象

访问组织架构页面 `/Sys_Department` 报错：

```
System.InvalidCastException: Unable to cast object of type 'System.String' to type 'System.Guid'
  at MySqlConnector.Core.Row.GetGuid(Int32 ordinal)
  at FilterQueryableAuthFields[TEntity](IQueryable`1 queryable)
```

后续修改列类型为 CHAR(36) 后，错误变为：

```
System.FormatException: Could not parse CHAR(36) value as Guid: dept-102
  at MySqlConnector.ColumnReaders.GuidChar36ColumnReader.ReadValue(...)
```

### 5.2 根因分析（三层误区）

| 层次 | 误区 | 实际情况 |
|------|------|----------|
| 第一层 | 以为是 Vol 框架代码 bug | Vol 框架代码完全正常 |
| 第二层 | 以为是 Guid 类型映射问题（VARCHAR vs CHAR） | 列类型只是表面原因 |
| 第三层（根因） | **数据库中存了非标准 GUID 格式的测试数据** | `dept-100`、`dept-101` 等字符串不是合法 GUID |

### 5.3 排查过程

```bash
# Step 1: 查看错误堆栈，定位到 FilterQueryableAuthFields → GetGuid
# Step 2: 检查数据库表结构
docker exec yzh-mysql mysql -uroot -p"Yzh123456." yzh_cert_platform \
  -e "DESCRIBE Sys_Department;"
# 发现：DepartmentId varchar(36), ParentId varchar(36)

# Step 3: 检查数据内容（关键！）
docker exec yzh-mysql mysql -uroot -p"Yzh123456." yzh_cert_platform \
  -e "SELECT DepartmentId, DepartmentName, ParentId FROM Sys_Department;"
# 发现：混合了标准 GUID 和自定义字符串 dept-xxx
```

数据内容：
```
41B96EA8-5475-4775-845D-FD66370C75AE  上海市场研究院    NULL
dept-100                              体系认证平台总部   0        ← 非法 GUID
dept-101                              运维部             dept-100 ← 非法 GUID
dept-102                              配置管理部         dept-100 ← 非法 GUID
dept-103                              质量管理部         dept-100 ← 非法 GUID
```

### 5.4 修复方案

**两步修复，缺一不可**：

```sql
-- Step 1: 将 VARCHAR(36) 改为 CHAR(36)
-- 原因：MySqlConnector 的默认 GuidFormat=Binary16 只能从 CHAR(36) 或 BINARY(16) 读取 Guid
-- VARCHAR(36) 不被识别为 Guid 列，直接报 InvalidCastException
ALTER TABLE Sys_Department 
  MODIFY COLUMN DepartmentId CHAR(36) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NOT NULL,
  MODIFY COLUMN ParentId CHAR(36) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NULL;

-- Step 2: 将非标准 GUID 数据替换为标准 GUID
SET @g1 = UUID(); SET @g2 = UUID(); SET @g3 = UUID(); SET @g4 = UUID();
UPDATE Sys_Department SET DepartmentId = @g1 WHERE DepartmentId = 'dept-100';
UPDATE Sys_Department SET DepartmentId = @g2 WHERE DepartmentId = 'dept-101';
UPDATE Sys_Department SET DepartmentId = @g3 WHERE DepartmentId = 'dept-102';
UPDATE Sys_Department SET DepartmentId = @g4 WHERE DepartmentId = 'dept-103';
-- 更新所有引用
UPDATE Sys_Department SET ParentId = @g1 WHERE ParentId = 'dept-100';
UPDATE Sys_Department SET ParentId = @g2 WHERE ParentId = 'dept-101';
UPDATE Sys_Department SET ParentId = @g3 WHERE ParentId = 'dept-102';
UPDATE Sys_Department SET ParentId = @g4 WHERE ParentId = 'dept-103';
UPDATE Sys_Department SET ParentId = NULL WHERE ParentId = '0';
-- 更新关联表
UPDATE Sys_UserDepartment SET DepartmentId = @g1 WHERE DepartmentId = 'dept-100';
UPDATE Sys_UserDepartment SET DepartmentId = @g2 WHERE DepartmentId = 'dept-101';
UPDATE Sys_UserDepartment SET DepartmentId = @g3 WHERE DepartmentId = 'dept-102';
UPDATE Sys_UserDepartment SET DepartmentId = @g4 WHERE DepartmentId = 'dept-103';
```

### 5.5 踩过的弯路（引以为戒）

| 尝试 | 结果 | 教训 |
|------|------|------|
| 修改 `Sys_DepartmentController.cs` 的参数类型 `Guid → string` | 违反 Vol 红线，且治标不治本 | 禁止修改 Vol Controller |
| 修改 `Sys_Department.cs` 实体属性 `Guid → string` | 违反 Vol 红线，破坏 UserContext/WorkFlowManager | 禁止修改 Vol Entity |
| 在连接字符串加 `GuidFormat=Text` | Pomelo EF Core 不支持连接字符串方式 | 只能通过 `UseMySql` options 配置 |
| 修改 `VOLContext.cs` 的 `UseMySql` 添加 GuidFormat | 违反 Vol 红线 | 禁止修改 VOLContext |

### 5.6 正确的排查思路

```
InvalidCastException
  ↓ 第一步：看错误堆栈，定位到 MySqlConnector.GetGuid
  ↓ 第二步：检查数据库列类型 → VARCHAR(36)
  ↓ 第三步：检查数据内容 → 发现 dept-xxx 非法 GUID（这才是根因！）
  ↓ 第四步：检查 Vol 框架原始 SQL 脚本 → 确认 VARCHAR(36) 是 Vol 原始设计
  ↓ 第五步：修复数据（替换为标准 GUID）+ 修复列类型（VARCHAR → CHAR）
  ↓ 结果：Vol 框架代码零修改，问题解决
```

### 5.7 Vol 框架 Guid 映射机制说明

Vol 框架在 `VOLContext.cs` 的 `OnModelCreating` 中，对 Oracle/DM 数据库配置了 Guid ValueConverter：

```csharp
// VOLContext.cs 第 147-168 行（Vol 原始代码，不可修改）
if (DBType.Name == DbCurrentType.Oracle.ToString() || DBType.Name == DbCurrentType.DM.ToString())
{
    foreach (var entity in modelBuilder.Model.GetEntityTypes())
    {
        foreach (var property in entity.GetProperties())
        {
            if (property.ClrType == typeof(Guid))
            {
                property.SetValueConverter(new ValueConverter<Guid, string>(v => v.ToString(), v => new Guid(v)));
            }
        }
    }
}
```

**MySQL 没有配置 ValueConverter**，因为 MySqlConnector 原生支持从 `CHAR(36)` 读取 Guid。但前提是：
1. 列类型必须是 `CHAR(36)`（不能是 `VARCHAR(36)`）
2. 数据内容必须是标准 GUID 格式（`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`）

### 5.8 全库 Guid 字段检查脚本

```sql
-- 检查所有 Sys_ 表中 varchar(36) 的 Guid 字段
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE 
FROM INFORMATION_SCHEMA.COLUMNS 
WHERE TABLE_SCHEMA='yzh_cert_platform' 
  AND DATA_TYPE='varchar' AND CHARACTER_MAXIMUM_LENGTH=36 
  AND TABLE_NAME LIKE 'Sys_%' 
ORDER BY TABLE_NAME, COLUMN_NAME;

-- 检查所有 Guid 字段中是否有非标准格式数据
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_VALUE FROM (
  SELECT 'Sys_Department' AS TABLE_NAME, 'DepartmentId' AS COLUMN_NAME, DepartmentId AS COLUMN_VALUE FROM Sys_Department
  UNION ALL SELECT 'Sys_Department', 'ParentId', ParentId FROM Sys_Department
  UNION ALL SELECT 'Sys_UserDepartment', 'DepartmentId', DepartmentId FROM Sys_UserDepartment
  UNION ALL SELECT 'Sys_WorkFlow', 'WorkFlow_Id', WorkFlow_Id FROM Sys_WorkFlow
  UNION ALL SELECT 'Sys_WorkFlowTable', 'WorkFlowTable_Id', WorkFlowTable_Id FROM Sys_WorkFlowTable
) t 
WHERE COLUMN_VALUE IS NOT NULL 
  AND COLUMN_VALUE NOT REGEXP '^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$';
```

## 六、问题 6：Vue3 keep-alive parentNode 运行时错误

### 6.1 现象

切换菜单时控制台报：
```
TypeError: Cannot read properties of null (reading 'parentNode')
  at runtime-dom.esm-bundler.js:50
```

### 6.2 根因

这是 Vue 3 `keep-alive` 的运行时 DOM 竞争问题，**不是代码错误**。

触发场景：
1. 后端 API 报错（如 InvalidCastException），前端组件渲染了一半（DOM 部分创建），但数据请求失败
2. `keep-alive` 缓存了这个半损坏的组件实例
3. 后续切换菜单时，`keep-alive` 尝试操作已失效的 DOM 节点，触发 `parentNode` null 错误

### 6.3 修复

| 场景 | 修复方式 |
|------|----------|
| 后端报错导致前端状态不一致 | 修复后端问题 → 重启前端 Vite（清除 HMR 缓存）→ 浏览器硬刷新 |
| 快速连续切换菜单 | 降低切换速度；或在前端添加防抖 |
| 组件渲染返回 null | 确保组件模板有根元素 |

### 6.4 清除前端缓存的标准流程

```bash
# Step 1: 停止前端 Vite 服务
kill $(lsof -t -i:9990)

# Step 2: 清除 Vite 缓存
rm -rf src/server/Vue.NetCore/vol.web/node_modules/.vite

# Step 3: 重启前端
cd src/server/Vue.NetCore/vol.web && npx vite --host --port 9990 &

# Step 4: 浏览器硬刷新 (Cmd+Shift+R)
```

