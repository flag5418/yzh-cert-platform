## 📌 核心结论（先看这个）

**Vol 框架菜单不显示的 90% 原因是以下 3 个问题之一：**

| # | 问题 | 现象 | 解决方案 |
|---|------|------|----------|
| 1 | **MenuType 错误** | 菜单在数据库存在但前端不显示 | `MenuType=0`(PC端)，不是 `1`(移动端) |
| 2 | **ParentId 归属错误** | 菜单出现在错误的父菜单下 | 确认 ParentId 指向正确的父菜单 |
| 3 | **缓存未清除** | 修改数据库后仍看不到变化 | 清除 Redis `inernalMenu` 缓存 |

│  │ Menu_Id  │ MenuName │   Url      │ ParentId │  MenuType   │  │
│  ├──────────┼──────────┼────────────┼──────────┼─────────────┤  │

### 1.2 关键字段说明

#### sys_menu 表核心字段

| 字段名 | 类型 | 说明 | ⚠️ 踩坑点 |
|--------|------|------|----------|
| **Menu_Id** | int | 主键，自增 | - |
| **MenuName** | varchar(100) | 菜单显示名称 | - |
| **ParentId** | int | 父菜单 ID（0=顶级） | **错误归属导致菜单出现在错误位置** |
| **Url** | varchar(500) | 路由路径 | **必须与 viewGird.js 的 path 完全一致** |
| **MenuType** | tinyint | **0=PC端, 1=移动端** | **⚠️ 最常见踩坑！PC端必须为 0** |
| **Enable** | tinyint | 0=禁用, 1=启用, 2=启用不显示 | 禁用的菜单完全不显示 |
| **OrderNo** | int | 排序号（越大越靠前） | 影响同级菜单的显示顺序 |
| **Icon** | varchar(50) | 图标类名（如 el-icon-setting） | 可空 |

### 1.3 MenuType 字段详解（⚠️ 重点）

> **Vol 框架机制**：`MenuType` 由 `UserContext.cs` 根据请求头 `uapp` 自动判断。PC 端浏览器请求不包含 `uapp` header → `MenuType=0`；移动端 App 请求包含 `uapp` header → `MenuType=1`。后端 `GetMenuActionList()` 方法按此值过滤菜单。

```csharp
// UserContext.cs 第 182-187 行
public static int MenuType
{
    get
    {
        // PC 端请求没有 uapp header → 返回 0
        // 移动端请求有 uapp header → 返回 1
        return Context.Request.Headers.ContainsKey("uapp") ? 1 : 0;
    }
}
```

**影响范围**：
- 后端 `GetMenuActionList()` 方法会按 `MenuType` 过滤菜单
- `MenuType = 1` 的菜单只在移动端 App 显示
- `MenuType = 0` 或 `NULL` 的菜单只在 PC 端浏览器显示

## 二、布局模式对菜单的影响

### 2.1 两种布局模式

在 `main.js` 第 32 行配置：
```javascript
layout: 'top'  // 或 'classics' 或 'left'
```

| 布局模式 | 菜单显示方式 | 特点 |
|----------|-------------|------|
| **top**（顶部导航） | 顶部横向显示一级菜单，左侧显示当前选中一级的子菜单 | **本项目使用此模式** |
| **classics**（经典导航） | 左侧树形显示所有菜单层级 | 传统后台风格 |
| **left**（左侧导航） | 左侧垂直显示一级菜单 | 类似经典但样式不同 |

### 2.2 top 布局的菜单渲染逻辑

```
前端 IndexMethods.js 第 180-221 行：

1. 从 API 获取所有菜单 (result.menu)
2. 提取 parentId 为空/0 的菜单 → navMenuList（顶部导航栏）
3. 默认选中 navMenuList[0]（OrderNo 最大的）
4. 提取选中菜单的子菜单 → menuData（左侧菜单栏）
5. 子菜单的子菜单也会被提取并平铺展示
```

**关键代码**：
```javascript
// 第 180-185 行：构建顶部导航
if (dataConfig.layout.value != 'classics') {
  navMenuList.push(
    ...data.filter((c) => { return !c.parentId })  // 只取一级菜单
  )
}

// 第 195-208 行：构建左侧菜单（当前选中顶级菜单的子菜单）
navMenuList.forEach((m) => {
  m.children = data.filter((c) => { return c.parentId == m.id })
  // ... 递归获取三级菜单
})
```

## 四、常见问题排查（Troubleshooting）

### 4.1 问题：菜单在数据库存在但前端不显示

**可能原因及排查步骤**：

```bash
# Step 1: 检查 MenuType
docker exec yzh-mysql mysql -u root -p'Yzh123456.' yzh_cert_platform \
  -e "SELECT Menu_Id, MenuName, MenuType, Enable FROM sys_menu WHERE MenuName='你的菜单';"
# ⚠️ 如果 MenuType=1，改成 0

# Step 2: 检查 ParentId
docker exec yzh-mysql mysql -u root -p'Yzh123456.' yzh_cert_platform \
  -e "SELECT Menu_Id, MenuName, ParentId FROM sys_menu WHERE Menu_Name='你的菜单';"
# 确认 ParentId 指向你期望的父菜单

# Step 3: 检查 API 返回
curl -s 'http://localhost:9992/api/menu/getTreeMenu' \
  -H "Authorization: Bearer YOUR_TOKEN" | grep "你的菜单"
# 如果 API 返回中有该菜单，说明后端没问题，检查前端逻辑

# Step 4: 清除缓存
docker exec yzh-redis redis-cli DEL inernalMenu
# 然后刷新页面
```

### 4.2 问题：点击菜单报 404 No match found for location

**原因**：`viewGird.js` 中没有对应的路由配置

**解决**：
1. 确认数据库 `sys_menu.Url` 的值
2. 在 `viewGird.js` 添加相同 `path` 的路由配置
3. 确认 Vue 组件文件存在

### 4.3 问题：菜单显示在错误的位置

**原因**：`ParentId` 设置错误

**示例**：
- 你希望菜单在「体系认证平台」下，但 `ParentId=61`（系统设置）
- 修复：`UPDATE sys_menu SET ParentId = 304 WHERE Menu_Id = xxx;`

### 4.4 问题：修改数据库后菜单不变

**原因**：Vol 框架有内存缓存 + Redis 缓存

**解决**：
```bash
# 清除 Redis 缓存
docker exec yzh-redis redis-cli DEL inernalMenu

# 如果还不行，重启后端（清除内存中的静态变量缓存）
# 后端 Sys_MenuService 有 static List<Sys_Menu> _menus 静态缓存
```

## 五、Vol 框架菜单缓存机制详解

### 5.1 双层缓存架构

```
请求 → Redis 缓存(inernalMenu) → 后端静态变量(_menus) → 数据库
         ↑ 版本号比对              ↑ 单例锁保护
```

**代码位置**：`Sys_MenuService.cs` 第 53-96 行

```csharp
private List<Sys_Menu> GetAllMenu()
{
    // 1. 检查 Redis 缓存版本
    string _cacheVersion = CacheContext.Get(_menuCacheKey);
    if (_menuVersionn != "" && _menuVersionn == _cacheVersion)
    {
        return _menus ?? new List<Sys_Menu>();  // 缓存命中，直接返回
    }
    
    // 2. 双重检查锁
    lock (_menuObj)
    {
        if (_menuVersionn != "" && _menus != null && _menuVersionn == _cacheVersion) 
            return _menus;
        
        // 3. 从数据库加载
        _menus = repository.FindAsIQueryable(x => x.Enable == 1 || x.Enable == 2)
            .OrderByDescending(a => a.OrderNo)
            .ThenByDescending(q => q.ParentId).ToList();
        
        // 4. 更新版本号到 Redis
        CacheContext.Add(_menuCacheKey, DateTime.Now.ToString("yyyyMMddHHMMssfff"));
    }
    return _menus;
}
```

### 5.2 缓存失效时机

| 操作 | 是否自动清除缓存 | 说明 |
|------|-----------------|------|
| 保存菜单 (`Save`) | ✅ 是 | 第 238 行：`CacheContext.Add(_menuCacheKey, ...)` |
| 删除菜单 (`DelMenu`) | ✅ 是 | 第 270 行：同上 |
| 直接 SQL 修改数据库 | ❌ 否 | **必须手动清除 Redis 缓存** |

### 5.3 手动清除缓存的命令

```bash
# 方式 1: Redis CLI
docker exec yzh-redis redis-cli DEL inernalMenu

# 方式 2: 调用后端 API（需要登录 Token）
curl -X POST 'http://localhost:9992/api/menu/save' \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"Menu_Id":61,"MenuName":"系统设置"}'  # 触发任意菜单保存即可刷新缓存
```

## 十、最佳实践总结

### ✅ Do（应该做的）

1. **新增菜单前先确认父菜单 ID**
   ```sql
   SELECT Menu_Id FROM sys_menu WHERE MenuName='xxx' AND ParentId=0;
   ```

2. **始终设置 MenuType=0**（除非明确要做移动端菜单）

3. **Url 与 viewGird.js path 保持完全一致**

4. **修改数据库后清除 Redis 缓存**
   ```bash
   docker exec yzh-redis redis-cli DEL inernalMenu
   ```

5. **用 SQL 脚本管理菜单变更**（方便回滚和团队协作）

### ❌ Don't（不应该做的）

1. **不要直接 SQL 修改后不清缓存**

2. **不要混淆 ParentId**（一级菜单 ParentId=0，子菜单 ParentId=父菜单 ID）

3. **不要忘记 export default viewgird**（路由文件）

4. **不要在 SQL 中用 MenuType=1** 做 PC 端菜单（最常见的低级错误）
